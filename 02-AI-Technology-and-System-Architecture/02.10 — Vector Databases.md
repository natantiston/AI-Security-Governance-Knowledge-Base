# 02.10 — Vector Databases

## Part 1 — Vector Database Foundations, Architecture, Components, and Core Concepts

---

# 1. Introduction to Vector Databases

A vector database is a database system designed to store, manage, index, and retrieve high-dimensional vector representations efficiently.

In AI systems, vectors commonly represent:

* text;
* documents;
* images;
* audio;
* video;
* products;
* users;
* entities;
* other forms of data.

Vector databases are particularly important in AI architectures because they enable systems to search for information based on **semantic similarity** rather than relying exclusively on exact keyword matching.

---

# 2. Why Vector Databases Matter to GRC Professionals

A GRC professional does not necessarily need to become a vector-database administrator.

However, the GRC professional should understand:

* what a vector database stores;
* how vectors are generated;
* how vectors are indexed;
* how similarity search works;
* how metadata is associated with vectors;
* how access is controlled;
* how data is retrieved;
* where security boundaries exist;
* how sensitive information can be exposed;
* how vector databases fit into enterprise AI architecture.

This technical understanding allows governance, risk, security, privacy, and compliance requirements to be translated into meaningful controls.

---

# 3. Traditional Databases and Vector Databases

Traditional relational databases primarily organize structured information into tables, rows, and columns.

For example:

```text
Customer ID | Name | Country | Status
------------|------|---------|--------
1001        | John | Spain   | Active
1002        | Maria| France  | Active
```

A vector database instead stores numerical representations of information.

Example:

```text
Document ID | Vector
------------|------------------------------
DOC-001     | [0.21, -0.14, 0.83, ...]
DOC-002     | [0.17, -0.09, 0.77, ...]
```

The vector represents characteristics of the underlying information in a mathematical space.

---

# 4. Vector Database as an AI Data Layer

A vector database can act as an intermediate knowledge layer between enterprise information and an AI application.

A simplified architecture is:

```text
Enterprise Data
      ↓
Data Processing
      ↓
Embedding Model
      ↓
Vector Database
      ↓
Semantic Retrieval
      ↓
AI Application
```

This architecture is commonly used in retrieval-based AI systems.

---

# 5. Vector Database and Embeddings

A vector database does not normally create semantic meaning by itself.

An embedding model typically converts source information into vectors.

For example:

```text
"Information security policy"
             ↓
      Embedding Model
             ↓
[0.12, -0.43, 0.81, ...]
             ↓
      Vector Database
```

The database then stores and indexes the resulting vector.

---

# 6. Vector Database and Representation Models

Vector databases depend on representation models to generate useful vectors.

Different representation models may be optimized for:

* text;
* images;
* audio;
* video;
* code;
* multilingual information;
* domain-specific information.

Therefore, vector-database governance cannot be separated completely from embedding-model governance.

---

# 7. What a Vector Database Stores

A vector database may store several related types of information.

A conceptual record can contain:

```text
Vector
Metadata
Document Identifier
Source Reference
Timestamp
Permissions
Version
Additional Attributes
```

The vector itself is only one component of the record.

---

# 8. Vector Data

Vector data consists of numerical values.

For example:

```text
[0.124, -0.382, 0.741, 0.092, ...]
```

A vector may contain hundreds or thousands of dimensions depending on the embedding model.

The dimensions are not normally interpreted individually by a human.

Their combined numerical relationship represents semantic or other characteristics learned by the model.

---

# 9. Vector Dimensionality

Dimensionality refers to the number of numerical components in a vector.

For example:

```text
Vector A
[0.2, 0.4, 0.8]
```

has three dimensions.

Another vector might contain:

```text
[0.12, -0.07, 0.44, 0.91, ...]
```

with hundreds or thousands of dimensions.

The dimensionality is determined primarily by the representation model and its output format.

---

# 10. High-Dimensional Data

Vector databases are designed to handle high-dimensional data efficiently.

A vector may look conceptually like:

```text
V =
[v1, v2, v3, v4, ... , vn]
```

where `n` may be large.

Traditional database indexing techniques are generally not sufficient for efficient similarity search across very large high-dimensional datasets.

---

# 11. Vector Space

Vectors can be represented as points within a mathematical space.

For example:

```text
             • A
          /
       /
    • B
                • C
```

Vectors representing semantically similar information may be located closer together depending on the embedding model and similarity function.

---

# 12. Semantic Similarity

Semantic similarity measures how closely two representations relate in meaning or another learned feature space.

For example:

```text
"Cybersecurity policy"
        ↕
"Information security policy"
```

may have a stronger semantic relationship than:

```text
"Cybersecurity policy"
        ↕
"Employee cafeteria menu"
```

A vector database can exploit these relationships during retrieval.

---

# 13. Similarity Search

Similarity search attempts to find vectors that are mathematically close to a query vector.

The process can be represented as:

```text
User Query
    ↓
Query Embedding
    ↓
Vector
    ↓
Similarity Search
    ↓
Nearest Vectors
    ↓
Associated Records
```

---

# 14. Query Vector

A query is often transformed into an embedding before being submitted to the vector-search engine.

For example:

```text
User Query:
"What is our password policy?"

             ↓

Embedding Model

             ↓

Query Vector

[0.14, -0.22, 0.77, ...]
```

The vector database then searches for vectors that are sufficiently similar.

---

# 15. Nearest Neighbor Search

Nearest neighbor search attempts to identify the vectors closest to a query vector.

Conceptually:

```text
Query
  ●
 / \
●   ●
     \
      ●
```

The closest vectors may be returned as the most relevant candidates.

---

# 16. k-Nearest Neighbors

A system can request the top `k` nearest vectors.

For example:

```text
k = 5
```

means that the system attempts to return the five most relevant candidate vectors according to the selected similarity method.

The retrieved records can then be passed to an AI application.

---

# 17. Top-K Retrieval

A typical retrieval process is:

```text
Query
 ↓
Embedding
 ↓
Vector Search
 ↓
Top-K Results
 ↓
Filtering / Ranking
 ↓
Application
```

The value of `k` is an important retrieval configuration parameter.

---

# 18. Similarity Metrics

Vector databases can use different mathematical measures to compare vectors.

Common measures include:

* cosine similarity;
* Euclidean distance;
* squared Euclidean distance;
* dot product;
* inner product.

The appropriate measure depends on the representation model and application.

---

# 19. Cosine Similarity

Cosine similarity measures the angle between two vectors.

A common formulation is:

```text
cos(θ) = (A · B) / (||A|| ||B||)
```

where:

* `A` is the first vector;
* `B` is the second vector;
* `A · B` is the dot product;
* `||A||` and `||B||` are vector magnitudes.

Cosine similarity is commonly used for semantic text retrieval.

---

# 20. Interpretation of Cosine Similarity

A simplified conceptual interpretation is:

```text
Higher similarity
       ↓
Vectors point in more similar directions

Lower similarity
       ↓
Vectors point in less similar directions
```

The exact interpretation depends on the embedding model and implementation.

---

# 21. Euclidean Distance

Euclidean distance measures the geometric distance between vectors.

For two vectors:

```text
A = (a1, a2, ..., an)
B = (b1, b2, ..., bn)
```

the distance can be expressed as:

```text
d(A,B) =
√ Σ(ai - bi)²
```

Smaller distance generally means greater geometric proximity.

---

# 22. Dot Product

The dot product is another method of comparing vectors.

For two vectors:

```text
A = [a1, a2, ..., an]
B = [b1, b2, ..., bn]
```

the dot product is:

```text
A · B =
a1b1 + a2b2 + ... + anbn
```

The meaning of the score depends on vector normalization and the embedding model.

---

# 23. Similarity Metric Selection

The similarity metric should be compatible with the embedding model.

Organizations should avoid selecting a metric simply because it is familiar.

Model documentation and empirical evaluation should guide the choice.

---

# 24. Vector Indexing

Searching every vector individually becomes inefficient as datasets grow.

Vector databases therefore use indexing structures designed to accelerate similarity search.

The index provides a mechanism for finding likely nearest neighbors without comparing every vector against every other vector.

---

# 25. Exact Search

Exact search attempts to compare the query against all relevant vectors to determine the true nearest neighbors.

Conceptually:

```text
Query
 ↓
Compare against Vector 1
 ↓
Compare against Vector 2
 ↓
Compare against Vector 3
 ↓
...
 ↓
Compare against Vector N
```

This can provide high accuracy but may become computationally expensive at scale.

---

# 26. Approximate Nearest Neighbor Search

Approximate nearest neighbor, or ANN, methods attempt to find highly relevant neighbors more efficiently.

The objective is generally:

```text
High Retrieval Quality
+
Lower Computational Cost
+
Lower Latency
```

The result may be very close to exact nearest-neighbor search without requiring exhaustive comparison.

---

# 27. Exact Search Versus Approximate Search

The trade-off can be summarized as:

| Approach           | Accuracy  | Speed          | Computational Cost |
| ------------------ | --------- | -------------- | ------------------ |
| Exact search       | Very high | Lower at scale | Higher             |
| Approximate search | High      | Higher         | Lower              |

The appropriate choice depends on the application's requirements.

---

# 28. Index Structures

Different vector systems use different indexing approaches.

Examples include:

* HNSW;
* IVF;
* product quantization;
* tree-based approaches;
* graph-based approaches.

The specific implementation should be evaluated according to performance, scale, accuracy, and operational requirements.

---

# 29. HNSW

Hierarchical Navigable Small World, commonly abbreviated as HNSW, is a graph-based approximate nearest-neighbor indexing technique.

Conceptually:

```text
Higher-Level Graph
       ↓
Intermediate Graph
       ↓
Detailed Graph
       ↓
Nearest Neighbors
```

It enables efficient navigation through a high-dimensional vector space.

---

# 30. HNSW Search Concept

HNSW creates graph relationships between vectors.

A simplified representation is:

```text
      A -------- B
      |          |
      |          |
      C -------- D ---- E
```

During search, the system navigates the graph toward increasingly relevant vectors.

---

# 31. HNSW Parameters

Important HNSW parameters may include:

* `M`;
* `efConstruction`;
* `efSearch`.

These parameters influence index construction, search quality, memory consumption, and performance.

---

# 32. Inverted File Index

An inverted-file approach, commonly called IVF, partitions the vector space into groups or clusters.

Conceptually:

```text
Vector Space
   ↓
Cluster 1
Cluster 2
Cluster 3
Cluster 4
   ↓
Search Relevant Clusters
   ↓
Candidate Vectors
```

This reduces the amount of data searched for each query.

---

# 33. Product Quantization

Product quantization, or PQ, compresses vectors into smaller representations.

The purpose can include:

* reducing memory usage;
* reducing storage;
* improving search efficiency.

Compression can introduce some loss of precision, so the effect on retrieval quality should be evaluated.

---

# 34. Index Construction

Index construction generally involves:

```text
Vectors
 ↓
Indexing Algorithm
 ↓
Index Structure
 ↓
Searchable Vector Store
```

The index may need to be rebuilt or updated when data or model characteristics change.

---

# 35. Index Updates

Vector databases need mechanisms for:

* insertion;
* modification;
* deletion;
* re-indexing.

Governance should ensure that updates are controlled and auditable.

---

# 36. Insert Operations

A new vector record may be inserted when:

* a document is added;
* a product is created;
* an image is processed;
* a knowledge article is published.

The insertion process should preserve associated metadata and authorization information.

---

# 37. Update Operations

An existing vector may need updating when:

* source information changes;
* metadata changes;
* permissions change;
* the embedding model changes;
* the document is reprocessed.

Changes should be traceable.

---

# 38. Delete Operations

Deletion can occur because:

* the source document was removed;
* retention expired;
* a user exercised a data-right;
* information became obsolete;
* the vector was created incorrectly.

Deletion requirements are particularly important for privacy-sensitive systems.

---

# 39. Hard Deletion

Hard deletion removes the vector record from the active vector store.

However, governance should consider whether copies remain in:

* backups;
* replicas;
* caches;
* logs;
* snapshots.

Therefore, deleting an active record may not automatically mean that all copies have disappeared.

---

# 40. Soft Deletion

Soft deletion may mark a record as inactive without physically removing it immediately.

For example:

```text
Status = Active
```

may become:

```text
Status = Deleted
```

The record may remain temporarily for operational or recovery purposes.

Retention requirements should determine whether this is acceptable.

---

# 41. Metadata

Metadata provides contextual information about a vector.

Example:

```text
Vector
   +
Document ID
   +
Department
   +
Classification
   +
Owner
   +
Timestamp
   +
Access Policy
```

Metadata is often essential for secure retrieval.

---

# 42. Metadata Filtering

A vector search can be combined with metadata filters.

For example:

```text
Semantic Similarity
        +
Department = Security
        +
Classification = Internal
```

The database can then return only results meeting the specified conditions.

---

# 43. Metadata as a Security Boundary

Metadata can become a critical security mechanism.

For example:

```text
User A
 ↓
Search
 ↓
Authorization Filter
 ↓
Only Authorized Vectors
```

If authorization metadata is missing or incorrect, semantic search could retrieve information the user should not see.

---

# 44. Metadata Integrity

Metadata should be protected against unauthorized modification.

An attacker who changes:

```text
Classification = Restricted
```

to:

```text
Classification = Public
```

could potentially bypass downstream controls.

Metadata integrity is therefore a security concern.

---

# 45. Collection

Many vector systems organize vectors into collections, indexes, namespaces, or similar logical structures.

For example:

```text
Enterprise Knowledge
 ├── HR
 ├── Finance
 ├── Security
 ├── Legal
 └── Engineering
```

The exact terminology depends on the platform.

---

# 46. Namespace

A namespace can provide logical separation between groups of vector data.

For example:

```text
tenant-a
tenant-b
tenant-c
```

or:

```text
production
testing
development
```

Namespaces should not automatically be considered a complete security boundary.

---

# 47. Multi-Tenant Vector Databases

A vector database may serve multiple organizational tenants.

For example:

```text
Vector Database
 ├── Customer A
 ├── Customer B
 ├── Customer C
```

Tenant isolation is therefore a major architectural and security concern.

---

# 48. Tenant Isolation

Tenant isolation can be implemented through combinations of:

* separate databases;
* separate collections;
* namespaces;
* metadata filters;
* access-control policies;
* separate infrastructure.

The required level of isolation depends on risk and regulatory requirements.

---

# 49. Cross-Tenant Retrieval Risk

A critical failure could occur if:

```text
Tenant A Query
      ↓
Incorrect Filter
      ↓
Tenant B Vector
      ↓
Tenant A Response
```

This could result in confidentiality breaches and potentially regulatory consequences.

# 55. Authentication

Authentication determines who or what is connecting to the vector database.

Possible mechanisms include:

* API keys;
* service accounts;
* OAuth;
* workload identities;
* certificates;
* identity-provider integration.

---

# 56. Authorization

Authorization determines what an authenticated identity is allowed to do.

Examples:

```text
Application A
 → Search Collection X

Application B
 → Search Collection Y

Administrator
 → Manage Indexes
```

Authentication without appropriate authorization is insufficient.

---

# 57. Role-Based Access Control

RBAC can assign permissions according to roles.

Example:

| Role           | Search | Insert | Delete |   Admin |
| -------------- | -----: | -----: | -----: | ------: |
| Application    |    Yes |     No |     No |      No |
| Data Engineer  |    Yes |    Yes |    Yes |      No |
| Security Admin |    Yes |     No |    Yes | Limited |
| Database Admin |    Yes |    Yes |    Yes |     Yes |

Actual permissions should follow least-privilege principles.

---

# 58. Attribute-Based Access Control

ABAC can evaluate attributes such as:

* user;
* department;
* data classification;
* tenant;
* location;
* device;
* business purpose.

For example:

```text
User Department = Security
+
Document Department = Security
+
Classification <= Authorized Level
```

may be required before retrieval is permitted.

---

# 59. Encryption in Transit

Communication between applications and vector databases should use appropriate encryption in transit.

This protects vector data and associated metadata from interception.

---

# 60. Encryption at Rest

Vector stores should use appropriate encryption at rest where required by organizational policy or applicable regulation.

Encryption may protect:

* vectors;
* metadata;
* indexes;
* backups;
* snapshots.

---

# 61. Key Management

Encryption is dependent on effective key management.

* key ownership;

# 62. Network Segmentation

Vector databases should generally be placed within appropriately controlled network boundaries.

A simplified architecture is:

```text

  ↓
AI Application
  ↓

  ↓
```

# 63. Private Connectivity

Enterprise deployments may use:

* private endpoints;

* private links;

The objective is to minimize unnecessary exposure.

---

# 64. Firewall Controls

Network controls should restrict which systems can connect to the vector database.

For example:

```text
AI Application
      ↓
Allowed
      ↓
Vector Database

Internet
      ↓
Blocked
```

Network restrictions should complement, not replace, application-level authorization.

```text
Retrieval Failure
        ↓
```

Availability requirements should therefore be defined according to business criticality.

For example:

```text

      ↓

   ↓
```

```text
   ↓
```

# 75. Stale Vector Data

A vector database may contain information that is no longer current.

For example:

```text
Current Policy: v5
Vector Store: v3
```

If the AI retrieves the outdated vector, it may produce an incorrect answer.

---

# 76. Knowledge Freshness

Organizations should define freshness requirements for different information types.

Examples:

Freshness requirements should reflect business risk.

# 77. Time-Based Metadata

# 78. Expiration

# 80. Filtering Before Search

Some systems can apply metadata restrictions before similarity search.

Conceptually:

```text

      ↓
Similarity Search
      ↓
Results
```

This can reduce the possibility of retrieving unauthorized candidates.

---

# 81. Filtering After Search

Other architectures may retrieve candidate vectors first and apply authorization filters afterward.

Conceptually:

```text

      ↓

      ↓
Authorization Filter
      ↓

```

Security architecture should ensure that unauthorized information cannot leak through the retrieval process.

# 82. Hybrid Search

Hybrid search combines semantic similarity with traditional search techniques.

For example:

```text
Semantic Search
       +
Keyword Search
       +
Metadata Filtering
       ↓
Combined Ranking
```

This can improve retrieval quality for specialized information.

---

# 83. Keyword Search

Keyword search identifies records based on textual matches.

For example:

```text
Query:
"ISO 27001 access control"
```

may identify documents containing those exact terms.

---

# 84. Semantic Search

Semantic search identifies conceptually related information even when the exact words differ.

For example:

```text
Query:
"How do we restrict privileged accounts?"

Possible result:
"Administrative Access Control Standard"
```

The terms are different but semantically related.

---

# 85. Hybrid Retrieval Architecture

A hybrid system may operate as:

```text
             Query
               ↓
      ┌────────┴────────┐
      ↓                 ↓
Keyword Search     Vector Search
      ↓                 ↓
      └────────┬────────┘
               ↓
          Rank Results
               ↓
             Output
```

This can provide complementary retrieval capabilities.

---

# 86. Ranking

* similarity score;

* freshness;
* authority;

* abnormal data access;
* administrative changes;
* failed authentication;
* privilege escalation;
* large data extraction;
* unexpected ingestion.

---

# 97. Anomalous Retrieval

A user who normally retrieves ten documents per day but suddenly retrieves millions may represent:

* compromised credentials;
* malicious automation;
* data scraping;
* application malfunction.

Behavioral monitoring can help identify such events.

---

# 98. Data Exfiltration Risk

Vector databases may contain valuable enterprise knowledge.

Unauthorized retrieval can expose:

* intellectual property;
* customer information;
* source code;
* internal procedures;
* security documentation;
* confidential business information.

Vector databases should therefore be treated as potentially sensitive data stores.

---

# 99. Vector Data Is Not Automatically Anonymous

A vector is numerical, but that does not mean it is inherently anonymous.

Vectors may be associated with:

* identifiable source documents;
* users;
* customers;
* transactions;
* personal information.

They should therefore be governed according to the sensitivity of the underlying information.

---

# 100. Vector Reconstruction Considerations

Depending on the representation model and surrounding information, vectors may potentially reveal information about their source data.

Organizations should therefore avoid assuming that transforming information into vectors automatically eliminates privacy or confidentiality obligations.

---

# 101. Vector Database as a Sensitive Enterprise Asset

For GRC purposes, a vector database should generally be treated as an enterprise information asset whose sensitivity depends on:

```text
Underlying Data
+
Metadata
+
Access Model
+
Business Context
```

Its protection should therefore be based on risk rather than on the assumption that vectors are merely mathematical values.
