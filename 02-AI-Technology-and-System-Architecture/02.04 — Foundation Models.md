# 02.04 — Foundation Models

## Part 1 — Foundations, Characteristics, Lifecycle, and GRC Context

---

## 1. Introduction to Foundation Models

A **foundation model** is a model trained on broad and diverse data at large scale and designed to support a wide range of downstream tasks and applications.

The important concept is **reuse**.

Instead of building one model specifically for one task:

```text
Data
 ↓
Task-Specific Model
 ↓
Single Application
```

a foundation-model approach looks more like:

```text
Large-Scale Data
       ↓
Large-Scale Pretraining
       ↓
Foundation Model
       ↓
 ┌─────┼─────┬─────┬─────┐
 ↓     ↓     ↓     ↓     ↓
Chat  Search Vision Code Analysis
```

The same underlying model can therefore become the basis for many different systems.

For an AI GRC professional, this creates an important governance question:

> **Who is responsible for the risks embedded in a foundation model when that model is reused across many different applications?**

---

# 2. Why Foundation Models Matter to GRC

Foundation models changed the governance problem.

Traditional machine learning often looked like:

```text
Business Problem
      ↓
Specific Dataset
      ↓
Specific Model
      ↓
Specific Application
```

Foundation models introduce:

```text
Large General Dataset
        ↓
Foundation Model
        ↓
Multiple Organizations
        ↓
Multiple Applications
        ↓
Multiple Use Cases
```

This creates shared dependencies.

A defect, vulnerability, limitation, or inappropriate behavior in a foundation model can potentially affect many downstream systems.

---

# 3. The Foundation Model Concept

The term **foundation model** describes a model that can serve as a foundation for many downstream applications.

Typical characteristics include:

* Broad training data
* Large-scale training
* General-purpose capabilities
* Reusability
* Adaptability
* Transfer to downstream tasks

The model itself is not necessarily the final application.

---

# 4. Foundation Model vs. Traditional ML Model

Consider a fraud model:

```text
Transaction Data
       ↓
Fraud Model
       ↓
Fraud Detection
```

The model is designed for a relatively specific task.

A foundation model may instead support:

```text
                  Foundation Model
                         ↓
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
       Chatbot        Summarization    Search
          ↓              ↓              ↓
       Application    Application    Application
```

The foundation model provides general capabilities that can be adapted to different purposes.

---

# 5. Foundation Model Does Not Mean "One Specific Architecture"

Foundation models are often associated with transformers, particularly in modern generative AI.

However:

> **Foundation model is primarily a functional and lifecycle concept, not simply an architecture name.**

A foundation model can be based on different underlying architectures depending on the modality and use case.

Modern examples frequently involve:

* Transformer architectures
* Vision transformers
* Multimodal architectures
* Other large neural architectures

---

# 6. Pretraining

The foundation-model lifecycle usually begins with large-scale **pretraining**.

Conceptually:

```text
Large-Scale Data
      ↓
Data Preparation
      ↓
Pretraining
      ↓
Learned Parameters
      ↓
Foundation Model
```

During pretraining, the model learns statistical patterns from the training corpus.

---

# 7. What Does the Model Learn?

A foundation model can learn representations associated with:

* Language
* Syntax
* Semantics
* Visual patterns
* Relationships
* Concepts
* Statistical regularities
* Domain information

However, this should not be interpreted as the model possessing human understanding in the same sense as a person.

The model learns computational representations from data.

---

# 8. Scale

Foundation models are generally associated with significant scale in one or more dimensions.

For example:

```text
Data Scale
     +
Parameter Scale
     +
Compute Scale
     ↓
Large-Scale Pretraining
```

Scale is one of the reasons foundation models can support many downstream capabilities.

---

# 9. Parameters

Parameters are learned numerical values within a neural network.

A simplified model can be represented as:

```text
Input
 ↓
Parameters
 ↓
Transformations
 ↓
Output
```

Foundation models can contain extremely large numbers of parameters.

However:

> **Parameter count alone does not determine model quality, security, or suitability.**

---

# 10. Model Size Is Not Model Risk

A larger model is not automatically:

* More accurate
* More secure
* More reliable
* More explainable
* More appropriate

GRC assessment should consider the complete system.

For example:

```text
Model Size
   +
Training Data
   +
Architecture
   +
Deployment
   +
Use Case
   +
Controls
   ↓
Overall Risk
```

---

# 11. Broad Training Data

Foundation models are trained using large datasets that may contain multiple forms of information.

Depending on the model, data can include:

* Text
* Images
* Audio
* Video
* Code
* Documents
* Structured information

The exact composition depends on the model.

---

# 12. Data Diversity

The diversity of training data contributes to the model's broad capabilities.

For example:

```text
Books
Web Content
Code
Articles
Documents
Images
Audio
       ↓
Training Corpus
       ↓
Foundation Model
```

But diversity can also introduce governance challenges.

---

# 13. Training Data Governance

Important questions include:

* Where did the data originate?
* Was it lawfully obtained?
* What licenses apply?
* Does it contain personal information?
* Does it contain confidential information?
* What quality controls were applied?
* What filtering occurred?
* What documentation exists?

These questions become important during third-party model assessment.

---

# 14. Training Data Is Not Always Fully Known

A downstream organization may not have complete visibility into the training data of a third-party foundation model.

For example:

```text
Third-Party Provider
       ↓
Large Training Corpus
       ↓
Foundation Model
       ↓
Enterprise Customer
```

The enterprise may only receive the resulting model or API.

This creates a **transparency and third-party risk challenge**.

---

# 15. Data Provenance

**Data provenance** concerns the origin and history of data.

A simplified provenance chain is:

```text
Source
 ↓
Collection
 ↓
Processing
 ↓
Filtering
 ↓
Transformation
 ↓
Training
```

Strong provenance improves accountability and assurance.

---

# 16. Model Provenance

Similarly, model provenance describes how the model itself was created.

For example:

```text
Training Data
      ↓
Pretraining
      ↓
Base Model
      ↓
Instruction Tuning
      ↓
Alignment
      ↓
Safety Testing
      ↓
Released Model
```

Each stage may affect model behavior.

---

# 17. Foundation Model Lifecycle

A simplified lifecycle is:

```text
Data Acquisition
       ↓
Data Preparation
       ↓
Pretraining
       ↓
Evaluation
       ↓
Model Release
       ↓
Adaptation
       ↓

       ↓
```

Governance should exist across the entire lifecycle.

---

# 18. Pretraining vs. Adaptation

A foundation model generally starts with broad pretraining.

It can then be adapted for specific purposes.

```text
Foundation Model
       ↓
Adaptation
       ↓
Specific Application
```

Adaptation can include:

* Fine-tuning
* Instruction tuning
* Preference optimization
* Prompt engineering
* Retrieval augmentation
* Tool integration

These mechanisms will be covered in greater depth later in Chapter 2.

---

# 19. Base Model

A **base model** is the underlying pretrained model before additional application-specific adaptation.

Conceptually:

```text
Large-Scale Pretraining
        ↓
Base Model
        ↓
Adaptation
        ↓
Application
```

The exact terminology can vary between providers.

---

# 20. Instruction-Tuned Model

A model can be further trained to follow instructions.

```text
Base Model
     ↓
Instruction Training
     ↓
Instruction-Tuned Model
```

This can make the model more useful for conversational and task-oriented applications.

---

# 21. Alignment

Alignment refers broadly to efforts to make model behavior better conform to intended objectives, policies, preferences, or safety requirements.

Conceptually:

```text
Base Model
     ↓
Alignment / Preference Optimization
     ↓
More Desired Behavior
```

Alignment is not a single technology.

It can involve:

* Human feedback
* Preference data
* Reward models
* Policy optimization
* Safety training
* Evaluation

---

# 22. Alignment Is Not Security

This distinction is critical.

A model may be aligned to behave according to certain policies but still have:

* Vulnerable infrastructure
* Weak API security
* Data leakage
* Supply-chain vulnerabilities
* Excessive application privileges

Therefore:

```text
Alignment
    ≠
Security
```

They address different dimensions of risk.

---

# 23. Foundation Model vs. Application

A foundation model is not necessarily an AI application.

For example:

```text
Foundation Model
       ↓
API
       ↓
Enterprise Application
       ↓
Employee
```

The application determines how the model is used.

This distinction is extremely important for accountability.

---

# 24. Shared Responsibility

When an organization uses a third-party foundation model, responsibilities may be distributed.

For example:

```text
Provider
 ├── Model
 ├── Model Infrastructure
 └── Provider Security

Customer
 ├── Application
 ├── User Access
 ├── Customer Data
 └── Business Process
```

The exact responsibility boundary depends on the service model and contract.

---

# 25. Foundation Model as a Shared Dependency

Suppose an enterprise deploys:

```text
Application A
      ↓
Foundation Model

Application B
      ↓
Foundation Model

Application C
      ↓
Foundation Model
```

The model becomes a common dependency.

A major model problem could potentially affect all three applications.

This creates **concentration risk**.

---

# 26. AI Concentration Risk

If an organization relies heavily on one provider or model:

```text
10 AI Applications
       ↓
One Foundation Model
       ↓
One Provider
```

the organization may become highly dependent on that provider.

Potential risks include:

* Service outage
* Provider failure
* Price increases
* Model changes
* Contract changes
* Geographic restrictions
* Security incidents

---

# 27. Model Monoculture

Model monoculture occurs when many systems depend on the same model or provider.

Conceptually:

```text
Many Applications
       ↓
One Model
       ↓
One Provider
```

This can create systemic risk.

A mature AI governance program should therefore understand model dependencies across the organization.

---

# 28. Model Dependency Mapping

An AI inventory can be expanded into a dependency map:

```text
Business Process
      ↓
Application
      ↓
Model
      ↓
Provider
      ↓
Infrastructure
```

This helps identify concentration and systemic risks.

---

# 29. Foundation Model as Infrastructure

In some organizations, foundation models become analogous to shared infrastructure.

For example:

```text
                Foundation Model
                 /     |      \
                /      |       \
           HR App   Legal App   Support App
```

This means the model may require centralized governance.

---

# 30. Centralized vs. Decentralized Governance

### Centralized

```text
Enterprise AI Governance
        ↓
All AI Models
```

Advantages:

* Consistency
* Central visibility
* Standard controls

### Decentralized

```text
Business Unit A → AI
Business Unit B → AI
Business Unit C → AI
```

Advantages:

* Faster local decisions
* Greater business flexibility

A hybrid model often provides a balance.

# 32. Approved Model List

An enterprise can maintain:

```text

      ↓
```

This allows governance to move from "AI is prohibited" toward:

> **Only approved AI models and approved configurations may be used for defined business purposes.**

# 34. Model Evaluation

Before production use, an organization may evaluate:


# 35. Model Cards

A **model card** is documentation intended to describe important characteristics of a model.

It may include:

* Intended use
* Limitations
* Evaluation information
* Performance
* Known risks

Model cards can support governance, but organizations should not assume that a model card provides complete assurance.

---

# 36. System Cards

A system-level document can describe the broader AI system rather than only the model.

This may include:

* Architecture
* Intended use
* Safety measures
* Evaluation
* Limitations
* Deployment context

For GRC, system-level documentation can be especially valuable because risk often exists outside the model itself.

# 38. Model Behavior Risk

Foundation models can exhibit unexpected behavior.

Possible issues include:

* Incorrect factual statements
* Inconsistent responses
* Unsafe recommendations
* Bias
* Unexpected refusals
* Over-compliance
* Under-compliance

These behaviors must be evaluated in the context of the intended use.

---

# 39. General Capability vs. Specific Reliability

A foundation model may demonstrate broad capabilities without being reliably suitable for a specific business task.

For example:

```text
General Capability
       ↓
High

Specific Financial Decision
       ↓
Requires Separate Validation
```

This is an important governance principle.

---

# 40. General-Purpose Does Not Mean General-Purpose Approval

An organization should not conclude:

> "The model is already widely used, so it is automatically approved for everything."

Instead:

```text
Approved Model
      +
Approved Use Case
      +
Approved Data
      +
Approved Configuration
```

should determine whether deployment is permitted.

---

# 41. Foundation Model and Use-Case Risk

The same foundation model can have very different risk profiles.

Example:

```text
Same Model
   │
   ├── Internal brainstorming → Low Risk
   │
   ├── Customer support → Medium Risk
   │
   └── High-impact decision → High Risk
```

Therefore:

> **Model risk and use-case risk must be assessed separately.**

---

# 42. Model Risk vs. Application Risk

A model may have certain limitations.

The application may introduce additional risks.

```text
Model Risk
     +
Application Risk
     +
Data Risk
     +
Operational Risk
     ↓
AI System Risk
```

This layered approach produces a more realistic assessment.

---

# 43. Foundation Model Adaptation

A foundation model can be adapted without retraining the entire model from scratch.

Possible approaches include:

* Prompt engineering
* Fine-tuning
* Parameter-efficient adaptation
* Retrieval augmentation
* Tool integration

Each approach creates different governance requirements.

---

# 44. Prompt-Based Adaptation

An application can customize model behavior through prompts.

```text
Foundation Model
       +
System Prompt
       ↓
Application Behavior
```

The model itself may remain unchanged.

However, the prompt can become a critical configuration artifact.

---

# 45. System Instructions

System instructions can define behavior such as:

* Role
* Policies
* Response format
* Restrictions
* Workflow

For example:

```text
System Instructions
       ↓
Model
       ↓
Application Response
```

Changes to system instructions can therefore materially change system behavior.

---

# 46. Prompt Governance

Organizations may need controls around important prompts:

* Version control
* Approval
* Testing
* Access control
* Change management
* Documentation

A production prompt should not be treated as an informal text file.

---

# 47. Retrieval-Augmented Foundation Models

A foundation model can be combined with enterprise knowledge.

Conceptually:

```text
Enterprise Documents

Retrieval
       ↓
Relevant Context

       ↓
```

This allows organizations to use proprietary information without necessarily retraining the entire foundation model.

# 48. Foundation Models and Enterprise Data

When a foundation model accesses enterprise information, the governance scope expands.

The organization must consider:

* Data authorization
* Retrieval controls
* Data classification
* Tenant isolation
* Logging

* Access boundaries

# 49. Fine-Tuned Foundation Models

Another approach is:

```text

       ↓
Fine-Tuning Data
       ↓
Fine-Tuned Model
       ↓

```

Fine-tuning may change model behavior substantially.

Therefore, the resulting model should generally be treated as a distinct governed artifact.

# 50. Model Derivatives

A derived model may inherit characteristics from its parent.

Conceptually:

```text

       ↓
Fine-Tuning
       ↓

```

The organization should maintain traceability between them.

This is important for:

* Provenance
* Licensing
* Security
* Change management
* Incident response

---

# 51. Open-Weight Models

Some foundation models are distributed with model weights available to users.

This can provide greater control over:

* Deployment
* Infrastructure
* Customization
* Data locality

But it can also increase responsibility for:

* Security
* Infrastructure
* Model updates
* Vulnerability management
* Licensing compliance

---

# 52. Proprietary Models

A proprietary model may be accessible primarily through an API or managed service.

Conceptually:

```text
Enterprise
    ↓
API
    ↓
Provider
    ↓
Foundation Model
```

The provider manages much of the underlying infrastructure.

The customer gains convenience but may have less direct visibility into the model internals and training data.

---

# 53. Open-Weight vs. Proprietary

| Open-Weight                        | Proprietary                        |
| ---------------------------------- | ---------------------------------- |
| Greater deployment control         | Provider-managed                   |
| More infrastructure responsibility | Less infrastructure responsibility |
| Potentially more customization     | Often easier integration           |
| Greater operational burden         | Greater provider dependency        |
| Need to manage model security      | Need to manage provider risk       |

Neither is automatically more secure.

Security depends on architecture, controls, implementation, and use case.

---

# 55. Managed Foundation Models

A managed service may look like:

```text

       ↓

       ↓
```

Potential benefits:

* Faster deployment
* Provider-managed infrastructure
* Elastic capacity

Potential risks:

* Provider dependency
* Data handling concerns
* Configuration errors
* Service changes

---

# 56. Foundation Model APIs

Many organizations access models through APIs.

This means the model may be outside the organization's direct infrastructure boundary.

The GRC professional should determine:

* Where data goes
* What is retained
* How authentication works
* What provider controls exist
* What contractual restrictions apply

---

# 57. Provider Model Updates

A managed provider may update its underlying model.

For example:

```text
Application
       ↓
Provider API
       ↓
Model v1
       ↓
Provider Update
       ↓
Model v2
```

If the application behavior changes, this becomes a governance concern.

---

# 58. Silent Model Changes

A particularly important risk occurs when an application depends on a provider-managed model but the organization does not have sufficient visibility into changes.

Potential impacts include:

* Different outputs
* Performance changes
* Security changes
* Cost changes
* Compliance implications

Organizations should therefore establish appropriate change-notification and validation mechanisms.

---

# 59. Model Version Pinning

Where supported, organizations may pin applications to an approved model version.

Conceptually:

```text
Application
     ↓
Approved Model Version
```

This improves reproducibility.

However, version pinning can also create lifecycle and patching considerations.

# 62. Foundation Model Concentration

Organizations should identify how many critical applications depend on:

* One provider
* One model
* One region
* One infrastructure platform

For example:

```text
25 AI Applications
       ↓
One Provider
       ↓

```

This may create a significant concentration risk.

# 63. Exit Strategy

For critical AI dependencies, organizations should consider:

> **What happens if we can no longer use this foundation model?**

Possible alternatives include:

* Another model
* Another provider
* Self-hosted model
* Manual process

The appropriate strategy depends on business criticality.

At a high level, a modern foundation model consists of several major elements:


Examples include:

* Transformer architectures
* Encoder architectures
* Decoder architectures
* Encoder-decoder architectures
* Vision transformer architectures
* Multimodal architectures

Architecture influences:

* Capability
* Computational requirements
* Latency

# 74. Model Parameters

Parameters are learned numerical values that encode patterns learned during training.

A simplified representation is:

```text
Input
  ↓
Weights + Biases
  ↓
Neural Computation
  ↓
Output
```

A foundation model can contain billions or more parameters.

However, parameter count is only one characteristic of the model.

---

# 75. Model Weights

The trained parameter values are commonly referred to as **model weights**.

Conceptually:

```text
Training
```

# 80. Why Tokenization Matters to GRC

Tokenization affects:

* Cost
* Performance
* Input handling
* Logging

# 81. Tokenization Is Not Anonymization

```text

     ↓

     ↓
```

> **Tokenization used by an AI model should not be confused with privacy anonymization or cryptographic protection.**

# 95. Pretraining

Pretraining is the large-scale learning stage in which the model learns general patterns from its training corpus.

Conceptually:

```text

      ↓
Neural Network
      ↓
Repeated Optimization
      ↓
Learned Parameters
```

Pretraining is computationally expensive.

# 96. Training Objective

The exact objective depends on the architecture and model.

For language models, one common objective involves predicting tokens or related representations.

Conceptually:

```text
Context
  ↓
Model
  ↓
Prediction
  ↓
Compare With Target
  ↓
Calculate Error
  ↓
Update Parameters
```

This process occurs repeatedly across enormous datasets.

---

# 97. Loss Function

A **loss function** measures how different the model's prediction is from the desired training target.

Conceptually:

```text
Prediction
     ↓
Loss Function
     ↓
Error Measurement
     ↓
Optimization
```

Lower training loss generally indicates improved performance against the training objective, but it does not guarantee real-world reliability.

---

# 98. Gradient Descent

Training typically uses optimization algorithms based on gradients.

Simplified:

```text
Prediction
   ↓
Loss
   ↓
Gradient
   ↓
Parameter Update
   ↓
New Prediction
```

The process repeats many times.

The GRC professional does not need to calculate gradients manually but should understand that training progressively adjusts model parameters.

---

# 99. Backpropagation

Backpropagation calculates how model parameters contributed to the error.

Conceptually:

```text
Input
 ↓
Forward Pass
 ↓
Prediction
 ↓
Loss
 ↓
Backward Pass
 ↓
Parameter Updates
```

This is a fundamental mechanism of neural-network training.

For GRC, the most important lessons are:

1. **Model weights are critical assets.**
2. **Training data requires provenance and governance.**
3. **Tokenization is not encryption or anonymization.**
4. **Training infrastructure is part of the AI security boundary.**
5. **Model artifacts require integrity and supply-chain controls.**
6. **Public benchmarks do not replace enterprise validation.**
7. **Model versions must be traceable.**
8. **Model lineage supports incident response.**
9. **Open-weight models shift more responsibility to the customer.**
10. **Managed models shift infrastructure responsibility toward the provider but do not eliminate customer governance.**
11. **Provider model changes can create operational and compliance risk.**
12. **Model concentration can create systemic dependency.**
13. **Model replacement should be treated as a potentially material change.**
14. **Foundation-model approval does not automatically approve every use case.**
15. **The foundation model must be governed as part of the complete AI system.**

# 174. Model Poisoning

**Model poisoning** occurs when malicious or manipulated information influences model training or adaptation.

A simplified attack path:

```text
Attacker
   ↓
Training Data
   ↓
Training Pipeline
   ↓
Model
   ↓
Malicious Behavior
```

This can be especially difficult to detect because the model may appear normal under ordinary testing.

---

# 175. Data Poisoning vs. Model Poisoning

These terms are related but should be distinguished.

### Data poisoning

The attacker manipulates training or adaptation data.

### Model poisoning

The attacker compromises the resulting model or model artifact.

Conceptually:

```text
Data Poisoning
      ↓
Training Process
      ↓
Compromised Model

Model Poisoning
      ↓
Direct Model Artifact Compromise
```

---

# 176. Backdoors

A model backdoor is a hidden behavior that activates under specific conditions.

Conceptually:

```text
Normal Input
    ↓
Normal Output

Trigger Input
    ↓
Unexpected / Malicious Output
```

Backdoors can be difficult to identify through ordinary testing.

# 177. Model Tampering

Model weights or configuration can potentially be modified after training.

For example:

```text
Approved Model
     ↓
Unauthorized Modification
     ↓
Modified Model
     ↓
Production
```

This is why model integrity verification is important.

# 178. Model Integrity Controls

Controls may include:

* Cryptographic hashing
* Digital signatures
* Secure artifact repositories
* Access control
* Immutable storage
* Change monitoring
* Deployment verification

A production environment should be able to determine whether the deployed model matches the approved artifact.

# 179. Model Extraction

**Model extraction** involves attempting to reproduce the behavior of a model by repeatedly querying it.

Conceptually:

```text
Attacker
   ↓
Repeated API Queries
   ↓
Observe Outputs
   ↓
Train Substitute Model
```

Potential consequences include:

* Loss of intellectual property
* Competitive disadvantage
* Reduced model confidentiality

# 180. Model Extraction Risk

Organizations exposing proprietary models through APIs may consider:

* Authentication
* Authorization
* Rate limiting
* Usage monitoring
* Query anomaly detection
* Abuse detection

These controls reduce but do not necessarily eliminate extraction risk.

# 181. Model Inversion

**Model inversion** refers to attacks that attempt to infer sensitive information associated with model behavior.

Conceptually:

```text
Model
  ↓
Queries
  ↓
Observed Outputs
  ↓
Inference
  ↓
Potential Sensitive Information
```

The exact feasibility depends on the model, training process, attack method, and available information.

# 182. Membership Inference

Membership inference attempts to determine whether a particular record was included in a model's training data.

Conceptually:

```text
Candidate Record
      ↓
Attack
      ↓
Model Behavior
      ↓
Was This Record in Training Data?
```

This creates a potential privacy concern.

* Proprietary information

Strong governance should therefore consider both training-data controls and model-output behavior.

# 191. Prompt Injection

Prompt injection occurs when untrusted content influences the instructions given to an AI system.

For example:

```text
User / Document
      ↓
Malicious Instruction
      ↓
AI Application
      ↓
Model
```

Prompt injection becomes particularly important when the model has access to enterprise information or tools.

---

# 192. Direct Prompt Injection

A user may directly provide malicious instructions.

Conceptually:

```text
User
 ↓
Malicious Prompt
 ↓
Model
 ↓
Unexpected Behavior
```

The attack attempts to manipulate the model's behavior.

---

# 193. Indirect Prompt Injection

An application may retrieve external content containing malicious instructions.

```text
User
 ↓
AI Application
 ↓
Retrieve Document
 ↓
Malicious Instruction in Document
 ↓
Model
```

This is particularly relevant to RAG systems and AI agents.

# 194. Jailbreaking

Jailbreaking involves attempts to bypass restrictions imposed on a model.

Conceptually:

```text
Safety Policy
     ↓
User Attempts Circumvention
     ↓
Model
     ↓
Restricted Behavior
```

Jailbreak resistance is an important security and safety consideration, but it should not be the organization's only security control.

---

# 195. Prompt Injection vs. Jailbreaking

These concepts are related but different.

| Prompt Injection                         | Jailbreaking                            |
| ---------------------------------------- | --------------------------------------- |
| Attempts to manipulate instructions      | Attempts to bypass model restrictions   |
| Can originate from external content      | Often directly crafted by users         |
| Particularly relevant to AI applications | Particularly relevant to model behavior |
| Can affect tools and data access         | Often targets safety boundaries         |

# 196. Excessive Agency

A model can become significantly more dangerous when it is granted excessive permissions.

For example:

```text
Foundation Model
      ↓

Database
Cloud
Payments
File System
```

If the model is compromised or manipulated, excessive privileges can increase impact.

# 197. Least Privilege for AI

The principle of least privilege should apply to AI systems.

Instead of:

```text
AI → Full Enterprise Access
```

prefer:

```text
AI
 ↓
Specific Tool
 ↓
Specific Permission
 ↓
Specific Resource
```

This limits blast radius.

# 198. Foundation Model as an Untrusted Component

A useful security architecture principle is:

> **Do not assume the model is a trusted security boundary.**

The model may generate incorrect, manipulated, or unsafe instructions.

Therefore:

```text
Model
  ↓
Policy Enforcement
  ↓
Authorization
  ↓
Tool Execution
```

rather than allowing model output to directly execute privileged operations.

# 199. Deterministic Controls Around Probabilistic Systems

Traditional security controls are often deterministic.

For example:

```text

THEN deny access
```

AI models are probabilistic.

Therefore:

```text
Model Output
      ↓
Deterministic Security Control
      ↓

```

Critical authorization decisions should generally remain enforceable through deterministic controls rather than relying solely on model instructions.

# 204. Security vs. Safety vs. Reliability

These terms should not be conflated.

### Security

Protection against malicious activity.

### Safety

Reduction of harmful model behavior.

### Reliability

Consistency and correctness under expected conditions.

A model can be:

```text
Secure
but unreliable

Reliable
but insecure

Safe
but operationally unreliable
```

These dimensions require separate assessment.

### Question 3

**What is the difference between model risk and AI-system risk?**

Answer:

> Model risk concerns the behavior and characteristics of the model itself. AI-system risk encompasses the model plus the application, data, infrastructure, integrations, users, and business process surrounding it.

---

### Question 4

**How would you handle a new model version from a provider?**

Answer:

> Treat it as a controlled change. Assess materiality, perform regression and security testing, validate business performance, obtain required approval, then deploy and monitor.

---

### Question 5

**How would you respond to an AI data-leakage incident?**

Answer:

> Contain the issue, identify the affected model and application, determine what data was exposed and to whom, investigate the root cause, remediate the control weakness, validate the fix, assess notification obligations, and document lessons learned.

# 352. The GRC Mental Model

The most important concept to retain from **02.04** is:

```text
             FOUNDATION MODEL
                    │
       ┌────────────┼────────────┐
       ↓            ↓            ↓
      DATA       SECURITY     PROVIDER
       │            │            │
       └────────────┼────────────┘
                    ↓
               APPLICATION
                    ↓
                 USE CASE
                    ↓
              BUSINESS IMPACT
```

A GRC professional should **never assess a foundation model in isolation**.

The correct question is not:

> "Is this model secure?"

The better question is:

> **"Is this foundation model, as deployed within this specific AI system and business use case, governed, secure, compliant, resilient, and operating within the organization's risk appetite?"**

That distinction is fundamental to professional **AI Security Governance**.
