# 02.02 — Machine Learning Types and Learning Paradigms

## Part 1 — Foundations, Learning Types and Core Concepts

### 1. Introduction

Machine Learning (ML) is a major subfield of Artificial Intelligence in which systems learn patterns from data or experience and use those learned patterns to perform tasks such as:

* Classification
* Prediction
* Regression
* Clustering
* Recommendation
* Anomaly detection
* Ranking
* Decision-making
* Content generation

For a GRC professional, understanding **how a machine-learning system learns** is important because the learning paradigm affects:

* Data requirements
* Security risks
* Privacy considerations
* Model validation
* Governance controls
* Monitoring
* Explainability
* Operational risk

Machine learning should therefore not be treated as one homogeneous technology.

---

# 2. Major Machine Learning Paradigms

The major learning paradigms include:

```text
Machine Learning
│
├── Supervised Learning
│
├── Unsupervised Learning
│
├── Semi-Supervised Learning
│
├── Self-Supervised Learning
│
├── Reinforcement Learning
│
└── Hybrid / Composite Approaches
```

Modern AI systems may combine several of these approaches.

---

# 3. Supervised Learning

**Supervised learning** uses training examples where the desired output is known.

The training dataset generally contains:

```text
Input → Expected Output
```

For example:

```text
Email → Spam
Email → Legitimate
```

The model learns the relationship between the input and the expected output.

---

# 4. Supervised Learning Process

A simplified supervised-learning process is:

```text
Labeled Data
     ↓
Training
     ↓
Machine-Learning Model
     ↓
New Input
     ↓
Prediction
     ↓
Compare With Expected Result
```

The objective is generally to produce accurate predictions for new data.

---

# 5. Classification

Classification is a supervised-learning task in which the model assigns an input to one or more predefined categories.

Examples include:

* Spam / Not Spam
* Fraud / Legitimate
* Malware / Benign
* High Risk / Low Risk
* Approved / Rejected

Conceptually:

```text
Input
  ↓
Model
  ↓
Class
```

---

# 6. Binary Classification

Binary classification involves two possible classes.

For example:

```text
Transaction
     ↓
Fraud Detection Model
     ↓
Fraud / Not Fraud
```

Other examples include:

* Malicious / Benign
* Pass / Fail
* True / False

Binary classification is common in cybersecurity and risk analytics.

---

# 7. Multiclass Classification

Multiclass classification involves more than two possible classes.

For example, a security system could classify an event as:

```text
Normal
Suspicious
Malware
Phishing
Credential Attack
Data Exfiltration
```

The model selects one or more predefined categories depending on the design.

---

# 8. Multilabel Classification

Multilabel classification allows one input to receive multiple labels.

For example, a document might be classified as:

```text
Confidential
Financial
Personal Data
Regulated
```

Unlike ordinary multiclass classification, several categories can apply simultaneously.

---

# 9. Regression

Regression predicts a numerical value rather than a category.

Examples include:

* Revenue prediction
* Demand forecasting
* Credit risk score
* Temperature prediction
* Equipment failure probability
* Security-risk score

Conceptually:

```text
Input Data
    ↓
Regression Model
    ↓
Numerical Output
```

---

# 10. Classification Versus Regression

The distinction can be summarized as:

| Learning Task             | Typical Output          |
| ------------------------- | ----------------------- |
| Binary classification     | Two classes             |
| Multiclass classification | One class among several |
| Multilabel classification | Multiple classes        |
| Regression                | Numerical value         |

For GRC professionals, understanding the output type helps determine how model decisions should be evaluated.

---

# 11. Unsupervised Learning

**Unsupervised learning** works with data where predefined labels are not supplied.

Instead of learning:

```text
Input → Known Answer
```

the model attempts to discover structure within the data.

Conceptually:

```text
Unlabeled Data
      ↓
ML Algorithm
      ↓
Patterns / Structure
```

---

# 12. Clustering

Clustering groups similar observations together.

For example, an organization could analyze users based on behavior without defining the groups beforehand.

```text
User Data
   ↓
Clustering Algorithm
   ↓
Group A
Group B
Group C
```

Possible applications include:

* Customer segmentation
* Network behavior analysis
* Fraud discovery
* Security analytics
* Market analysis

---

# 13. Anomaly Detection

Anomaly detection attempts to identify observations that differ significantly from expected patterns.

For example:

```text
Normal Behavior
Normal Behavior
Normal Behavior
Anomalous Behavior ← Flag
Normal Behavior
```

Anomaly detection can be used in:

* Cybersecurity
* Fraud detection
* Industrial systems
* Network monitoring
* Financial systems

---

# 14. Why Unsupervised Learning Matters to Security

In cybersecurity, organizations may not have complete labels for every attack.

For example, a security team may have millions of events but only a small number confirmed as malicious.

Unsupervised techniques can help identify unusual behavior that deserves investigation.

However:

> An anomaly is not automatically an attack.

This distinction is important for risk management and operational decision-making.

---

# 15. Dimensionality Reduction

Dimensionality reduction reduces the number of variables used to represent data while attempting to preserve important information.

It may be used for:

* Visualization
* Data analysis
* Feature reduction
* Noise reduction
* Computational efficiency

Common techniques include:

* Principal Component Analysis (PCA)
* t-SNE
* UMAP

---

# 16. Association Learning

Association learning attempts to discover relationships between items or events.

A classic example is market-basket analysis:

```text
Customer buys A
       +
Customer buys B
       ↓
Possible relationship
```

This can support:

* Recommendations
* Marketing
* Fraud analysis
* Behavioral analysis

---

# 17. Semi-Supervised Learning

Semi-supervised learning combines:

* A relatively small amount of labeled data
* A larger amount of unlabeled data

Conceptually:

```text
Small Labeled Dataset
          +
Large Unlabeled Dataset
          ↓
    ML Training
          ↓
        Model
```

This can be useful when labeling data is expensive or difficult.

---

# 18. Why Semi-Supervised Learning Is Important

In many enterprise environments, collecting data is relatively easy while accurately labeling it is difficult.

For example, an organization may have:

```text
10,000,000 security events
        ↓
Only 50,000 manually investigated events
```

The organization may use both labeled and unlabeled data.

This creates governance questions around:

* Label quality
* Data provenance
* Human annotation
* Training methodology
* Validation

---

# 19. Self-Supervised Learning

Self-supervised learning allows a model to create learning signals from the data itself.

Instead of requiring every example to have a human-provided label, the system creates a prediction task from the available data.

For example, a language model may learn by predicting a missing or subsequent token.

Conceptually:

```text
Raw Data
   ↓
Automatically Created Learning Task
   ↓
Model Training
   ↓
Learned Representation
```

Self-supervised learning has become extremely important in modern AI.

---

# 20. Self-Supervised Learning and Foundation Models

Many modern foundation models are trained using self-supervised or related objectives over very large datasets.

A simplified representation is:

```text
Large Dataset
      ↓
Self-Supervised Training
      ↓
Large Model
      ↓
Foundation Model
      ↓
Downstream Applications
```

This helps explain why modern AI systems can learn broad representations from enormous quantities of data without requiring humans to manually label every example.

---

# 21. Supervised Versus Self-Supervised Learning

The difference can be summarized as:

**Supervised learning**

```text
Human / System Label
        ↓
Input → Correct Answer
```

**Self-supervised learning**

```text
Data
 ↓
Automatically Derived Objective
 ↓
Prediction Task
```

Both involve learning from data, but the source of the learning signal differs.

---

# 22. Reinforcement Learning

**Reinforcement Learning (RL)** is a learning paradigm in which an agent learns through interaction with an environment.

The agent takes actions and receives feedback.

Conceptually:

```text
Environment
     ↓
Observation
     ↓
Agent
     ↓
Action
     ↓
Environment
     ↓
Reward / Penalty
```

The agent attempts to learn behavior that maximizes cumulative reward.

---

# 23. Reinforcement Learning Components

A reinforcement-learning system commonly includes:

* Agent
* Environment
* State
* Action
* Reward
* Policy

A simplified architecture is:

```text
              ┌─────────────┐
              │ Environment │
              └──────┬──────┘
                     │
                  State
                     ↓
              ┌─────────────┐
              │    Agent    │
              └──────┬──────┘
                     │
                   Action
                     ↓
              ┌─────────────┐
              │ Environment │
              └──────┬──────┘
                     ↓
                   Reward
```

---

# 24. Agent

The **agent** is the system that makes decisions or takes actions within the environment.

Examples could include:

* A game-playing system
* A robotic controller
* An autonomous system
* An optimization system

Modern agentic AI may use concepts related to reinforcement learning, but not every AI agent is an RL system.

---

# 25. Environment

The environment is the system or world in which the agent operates.

It may be:

* A game
* A simulated environment
* A robotic environment
* A software environment
* A business process

The environment determines what actions are possible and what consequences occur.

---

# 26. State

A state represents the relevant condition of the environment at a particular point in time.

For example:

```text
Network Security Environment
        ↓
Current State
        ↓
Active Connections
Threat Alerts
System Load
User Activity
```

The agent uses state information to determine what action to take.

---

# 27. Action

An action is something the agent can perform.

Examples include:

* Move
* Select
* Block
* Allow
* Recommend
* Execute a command

The available actions should be explicitly understood when assessing an autonomous AI system.

---

# 28. Reward

A reward provides feedback to the agent.

For example:

```text
Good Action → Positive Reward
Bad Action  → Negative Reward
```

The agent learns which actions produce better long-term outcomes.

From a governance perspective, reward design is important because:

> **An AI system optimizes what it is rewarded for, not necessarily what humans intended.**

---

# 29. Reward Function

The reward function defines how actions are evaluated.

A poorly designed reward function can produce undesirable behavior.

For example, if an AI system is rewarded only for maximizing speed, it may sacrifice:

* Safety
* Accuracy
* Security
* Quality

Therefore, reward design can become a governance concern.

---

# 30. Policy

A policy determines how an agent chooses actions based on the current state.

Conceptually:

```text
State
 ↓
Policy
 ↓
Action
```

The policy can be learned or explicitly defined depending on the system.

---

# 31. Exploration and Exploitation

Reinforcement learning commonly involves a balance between:

**Exploration**

Trying actions that may produce new information.

**Exploitation**

Using actions that are already believed to produce good results.

Conceptually:

```text
Exploration ←──────→ Exploitation
```

The balance affects learning efficiency and system behavior.

---

# 32. Reinforcement Learning From Human Feedback

**Reinforcement Learning from Human Feedback (RLHF)** is a technique associated with aligning model behavior using human preferences.

A simplified process is:

```text
Pretrained Model
       ↓
Candidate Outputs
       ↓
Human Preference Data
       ↓
Reward Modeling
       ↓
Optimization
       ↓
Improved Model
```

RLHF became particularly important in the development of conversational AI systems.

---

# 33. Human Feedback

Human feedback can be used to evaluate outputs according to criteria such as:

* Helpfulness
* Relevance
* Safety
* Accuracy
* Instruction following

Human feedback introduces additional governance considerations involving:

* Annotation quality
* Workforce access
* Bias
* Consistency
* Privacy
* Documentation

---

# 34. Direct Preference Optimization

Modern model-alignment techniques can also use approaches that optimize directly from preference data rather than relying exclusively on a conventional reinforcement-learning pipeline.

The important governance principle is that:

> Human or machine preference data can influence the behavior of an AI model.

Therefore, preference datasets and alignment processes should be considered part of the model lifecycle.

---

# 35. Transfer Learning

Transfer learning involves using knowledge learned from one task or dataset to support another task.

Conceptually:

```text
Large-Scale Training
       ↓
Pretrained Model
       ↓
New Task
       ↓
Adapted Model
```

This can significantly reduce the amount of data and computation required for a new task.

---

# 36. Pretrained Models

A pretrained model has already undergone substantial training before being provided to another user or organization.

Organizations may then:

* Use it directly
* Fine-tune it
* Adapt it
* Add retrieval
* Integrate it into an application

This creates important supply-chain and third-party governance considerations.

---

# 37. Fine-Tuning

Fine-tuning adapts a pretrained model using additional training data.

Conceptually:

```text
Pretrained Model
       ↓
Organization-Specific Data
       ↓
Fine-Tuning
       ↓
Adapted Model
```

Fine-tuning may improve performance for a specific domain or task.

However, the additional data introduces new security and governance considerations.

---

# 38. Machine Learning Learning Paradigm Comparison

| Paradigm        | Main Data Characteristic          | Typical Purpose              |
| --------------- | --------------------------------- | ---------------------------- |
| Supervised      | Labeled data                      | Prediction / classification  |
| Unsupervised    | Unlabeled data                    | Pattern discovery            |
| Semi-supervised | Labeled + unlabeled               | Learning with limited labels |
| Self-supervised | Learning signal derived from data | Representation / pretraining |
| Reinforcement   | Interaction + reward              | Sequential decision-making   |

These categories are conceptual and modern AI systems may combine multiple approaches.

---

# 39. Hybrid Learning

Real-world AI systems often use more than one learning paradigm.

For example:

```text
Self-Supervised Pretraining
          ↓
Supervised Fine-Tuning
          ↓
Preference Optimization
          ↓
Production Model
```

A modern AI model may therefore have a complex training history.

GRC professionals should avoid assuming that a model was created using only one learning method.

---

# 40. Learning Paradigm and Risk

The learning paradigm affects the risk profile.

For example:

**Supervised learning**

Potential concerns:

* Label quality
* Label bias
* Data quality
* Training-data security

**Unsupervised learning**

Potential concerns:

* False positives
* Interpretation of clusters
* Anomaly thresholds

**Reinforcement learning**

Potential concerns:

* Reward manipulation
* Unsafe exploration
* Unintended strategies
* Autonomous actions

**Self-supervised learning**

Potential concerns:

* Large-scale data provenance
* Training-data quality
* Sensitive information
* Dataset contamination

---

# 41. Learning Paradigm and Governance

The learning paradigm should be documented as part of the AI system's technical profile.

A model inventory may include:

```text
Model Name
Model Type
Learning Paradigm
Training Data
Training Method
Model Owner
Use Case
Risk Classification
Deployment
```

This creates traceability between the technical model and its governance requirements.

---

# 42. Learning Paradigm and Data Governance

Different learning approaches require different data considerations.

For example:

```text
Supervised
     ↓
Labels + Training Data

Self-Supervised
     ↓
Large-Scale Raw Data

Reinforcement
     ↓
Interaction Data + Rewards
```

Data governance should therefore be aligned with the learning method.

---

# 43. Learning Paradigm and Security Testing

Security testing should reflect how the model learns.

Testing may include:

* Training-data integrity
* Data poisoning resistance
* Adversarial robustness
* Model extraction resistance
* Privacy testing
* Output validation
* Behavioral testing

The exact test strategy should depend on the AI architecture and risk.

---

# 44. Learning Paradigm and Model Lifecycle

The learning paradigm affects the model lifecycle:

```text
Data
 ↓
Learning Method
 ↓
Training
 ↓
Evaluation
 ↓
Deployment
 ↓
Monitoring
 ↓
Retraining / Adaptation
```

Retraining may introduce new data, new risks, and new model behavior.

Therefore, retraining should not automatically be treated as a routine technical operation without governance consideration.

---

# 45. Continuous Learning

Some AI systems can continuously or periodically learn from new data.

Conceptually:

```text
Production Data
      ↓
New Training Data
      ↓
Retraining
      ↓
Updated Model
      ↓
Production
      ↓
More Data
      ↺
```

Continuous learning can introduce additional risks because model behavior may change over time.

Controls may therefore be required around:

* Retraining triggers
* Data approval
* Model validation
* Deployment approval
* Versioning
* Rollback

---

# 46. Static Versus Adaptive Models

A **static model** remains unchanged after deployment until an explicit update occurs.

An **adaptive model** may change based on new information or retraining.

This distinction is important for governance.

Static models generally provide greater behavioral stability.

Adaptive models may respond better to changing environments but can introduce additional change-management challenges.

---

# 47. Batch Retraining

A common enterprise approach is scheduled retraining.

For example:

```text
Production Data
      ↓
Monthly Dataset
      ↓
Training
      ↓
Evaluation
      ↓
Approval
      ↓
New Model
```

This allows organizations to maintain governance gates around model changes.

---

# 48. Online Learning

Online learning updates a model incrementally as new data becomes available.

Conceptually:

```text
Data 1 → Update
Data 2 → Update
Data 3 → Update
Data 4 → Update
```

This can provide adaptability but may make behavior more difficult to control and reproduce.

---

# 49. Reproducibility

Reproducibility means being able to recreate or explain a model-development result using the relevant:

* Data
* Code
* Configuration
* Model version
* Dependencies
* Training process

Reproducibility supports:

* Audit
* Investigation
* Validation
* Change management
* Incident response

---

# 50. Machine Learning Governance Perspective

The fundamental governance principle is:

> **The way an AI model learns determines many of the risks that must be governed.**

A GRC professional should therefore understand:

```text
Learning Paradigm
       ↓
Data Requirements
       ↓
Training Process
       ↓
Model Behavior
       ↓
Security / Risk
       ↓
Controls
       ↓
Monitoring
```

Understanding supervised, unsupervised, semi-supervised, self-supervised, reinforcement, transfer, and hybrid learning provides the foundation for evaluating the technical and governance characteristics of modern AI systems.


# 02.02 — Machine Learning Types and Learning Paradigms

## Part 2 — Machine Learning Algorithms, Model Types, Training Methods and Evaluation

### 51. Machine Learning Algorithm Families

Machine-learning algorithms can be grouped into several broad families:

```text
Machine Learning Algorithms
│
├── Linear Models
├── Tree-Based Models
├── Instance-Based Models
├── Probabilistic Models
├── Clustering Algorithms
├── Dimensionality-Reduction Methods
├── Neural Networks
└── Reinforcement-Learning Algorithms
```

Each family has different characteristics, strengths, limitations, and governance implications.

---

### 52. Linear Regression

Linear regression predicts a numerical value using relationships between input variables and an output.

Conceptually:

```text id="1e6w4x"
Input Variables
      ↓
Linear Regression
      ↓
Numerical Prediction
```

Examples include:

* Revenue forecasting
* Demand prediction
* Cost estimation
* Risk scoring

It is relatively simple and can be easier to interpret than many deep-learning models.

---

### 53. Logistic Regression

Despite its name, logistic regression is commonly used for classification.

For example:

```text id="zpk6xh"
Transaction Data
      ↓
Logistic Regression
      ↓
Probability of Fraud
      ↓
Fraud / Legitimate
```

Its relative simplicity can make it useful when interpretability is important.

---

### 54. Decision Trees

Decision trees make predictions through a sequence of decision rules.

A simplified example:

```text id="0e9j1r"
Transaction > €10,000?
       │
   ┌───┴───┐
  Yes      No
   │        │
High Risk  Low Risk
```

Decision trees are often easier for humans to understand than complex neural networks.

---

### 55. Random Forest

A random forest combines multiple decision trees.

Conceptually:

```text id="h7f3g8"
           Data
             ↓
     ┌───────┼───────┐
     ↓       ↓       ↓
   Tree 1  Tree 2  Tree 3
     ↓       ↓       ↓
     └───────┼───────┘
             ↓
        Final Output
```

The combined approach can improve predictive performance and robustness compared with a single tree.

---

### 56. Gradient Boosting

Gradient boosting builds models sequentially, with later models attempting to improve weaknesses of earlier models.

Examples include:

* XGBoost
* LightGBM
* CatBoost

These algorithms are widely used for structured/tabular data.

---

### 57. Support Vector Machines

Support Vector Machines (SVMs) attempt to identify boundaries that separate classes.

Conceptually:

```text id="e3g5tx"
Class A   ● ● ●
          ● ●

---------------- Boundary ----------------

Class B       ▲ ▲
            ▲ ▲ ▲
```

SVMs can be effective for certain classification problems, particularly with appropriately selected features and kernels.

---

### 58. k-Nearest Neighbors

k-Nearest Neighbors (k-NN) makes predictions based on nearby examples in the data.

Conceptually:

```text id="w3qj17"
Known Data
 ● ● ●
 ● X ●
 ▲ ▲ ▲
```

The algorithm determines which existing observations are most similar to the new observation.

---

### 59. Naive Bayes

Naive Bayes is a probabilistic classification family based on Bayes' theorem with simplifying assumptions about feature independence.

It has historically been useful for:

* Spam detection
* Text classification
* Document categorization

Its simplicity can make it computationally efficient.

---

### 60. Clustering Algorithms

Common clustering approaches include:

* K-means
* Hierarchical clustering
* DBSCAN
* Gaussian mixture models

These algorithms attempt to identify structure within unlabeled data.

---

### 61. K-Means Clustering

K-means divides observations into a predefined number of clusters.

Conceptually:

```text id="z9j4jd"
Dataset
   ↓
Choose K
   ↓
Cluster Assignment
   ↓
Centroid Calculation
   ↓
Repeat
   ↓
Final Clusters
```

A major governance consideration is that the number of clusters may need to be chosen in advance.

---

### 62. Hierarchical Clustering

Hierarchical clustering builds relationships between observations or groups.

The resulting structure can be represented as a hierarchy:

```text id="w8e9cz"
             All Data
             /      \
          Group A   Group B
          /   \      /   \
        A1    A2    B1    B2
```

This can help analysts understand nested relationships within data.

---

### 63. DBSCAN

DBSCAN groups observations based on density.

It can identify:

* Dense clusters
* Sparse regions
* Outliers

This can be useful where cluster shapes are not necessarily spherical.

---

### 64. Principal Component Analysis

Principal Component Analysis (PCA) is a dimensionality-reduction technique.

It transforms variables into a smaller number of components that capture significant patterns in the data.

Conceptually:

```text id="d4qkzo"
Many Variables
      ↓
PCA
      ↓
Fewer Components
      ↓
Simplified Representation
```

---

### 65. Neural Networks as a Machine-Learning Family

Neural networks form another major machine-learning family.

They can be used for:

* Classification
* Regression
* Representation learning
* Image processing
* Speech recognition
* Natural-language processing
* Generative AI

Deep learning is largely based on increasingly sophisticated neural-network architectures.

---

### 66. Algorithm Selection

Selecting a machine-learning algorithm depends on factors such as:

* Problem type
* Data characteristics
* Dataset size
* Performance requirements
* Interpretability
* Computational resources
* Latency requirements
* Security requirements

There is no universally best algorithm.

---

### 67. Accuracy Is Not the Only Objective

A model should not be evaluated solely on predictive accuracy.

Other considerations include:

* Precision
* Recall
* Robustness
* Fairness
* Explainability
* Security
* Latency
* Resource consumption
* Operational stability

For GRC, this is critical because a technically accurate model can still be inappropriate for a high-risk use case.

---

### 68. Confusion Matrix

For classification systems, a confusion matrix compares predictions against actual outcomes.

A simplified structure is:

|                    | Actual Positive | Actual Negative |
| ------------------ | --------------: | --------------: |
| Predicted Positive |   True Positive |  False Positive |
| Predicted Negative |  False Negative |   True Negative |

These four categories are fundamental to classification evaluation.

---

### 69. True Positive

A true positive occurs when:

> The model predicts positive and the actual result is positive.

Example:

```text
Actual: Malware
Prediction: Malware
```

---

### 70. True Negative

A true negative occurs when:

> The model predicts negative and the actual result is negative.

Example:

```text
Actual: Legitimate
Prediction: Legitimate
```

---

### 71. False Positive

A false positive occurs when:

> The model predicts positive but the actual result is negative.

Example:

```text
Actual: Legitimate
Prediction: Malware
```

False positives can create:

* Operational overhead
* Customer inconvenience
* Alert fatigue
* Unnecessary investigations

---

### 72. False Negative

A false negative occurs when:

> The model predicts negative but the actual result is positive.

Example:

```text
Actual: Malware
Prediction: Legitimate
```

False negatives can be particularly serious in security systems.

---

### 73. Precision

Precision measures how many predicted positive cases were actually positive.

Conceptually:

```text id="d9c5b1"
Precision =
True Positives
────────────────────────────
True Positives + False Positives
```

High precision means that positive predictions are generally reliable.

---

### 74. Recall

Recall measures how many actual positive cases were correctly identified.

Conceptually:

```text id="z2f8o1"
Recall =
True Positives
────────────────────────────
True Positives + False Negatives
```

High recall means fewer actual positive cases are missed.

---

### 75. Precision Versus Recall

The appropriate balance depends on the business context.

For example:

**Malware detection**

Missing malware may be very costly.

Therefore, high recall may be important.

**Fraud investigations**

Too many false alerts may overwhelm analysts.

Therefore, precision may also be highly important.

The model objective should reflect the actual business risk.

---

### 76. F1 Score

The F1 score combines precision and recall into a single metric.

It is based on their harmonic mean.

Conceptually:

```text id="f3ik9m"
             Precision × Recall
F1 = 2 × ─────────────────────────
             Precision + Recall
```

It is useful when both false positives and false negatives matter.

---

### 77. ROC Curve

A Receiver Operating Characteristic (ROC) curve illustrates the relationship between:

* True positive rate
* False positive rate

across different classification thresholds.

It helps evaluate how well a classifier separates classes.

---

### 78. AUC

Area Under the Curve (AUC), commonly referring to ROC-AUC, summarizes classifier discrimination across thresholds.

Higher AUC generally indicates better ability to distinguish between classes.

However, AUC should not be interpreted independently of the actual operational requirements.

---

### 79. Classification Threshold

Many classification models produce probabilities rather than direct decisions.

For example:

```text id="1f9f55"
Model Output = 0.82
```

An organization may define:

```text id="r7b5n8"
Probability ≥ 0.70 → High Risk
Probability < 0.70 → Lower Risk
```

The threshold can significantly affect:

* False positives
* False negatives
* Precision
* Recall

Therefore, thresholds are governance-relevant configuration values.

---

### 80. Regression Evaluation

Regression models use different evaluation metrics.

Common metrics include:

* Mean Absolute Error (MAE)
* Mean Squared Error (MSE)
* Root Mean Squared Error (RMSE)
* R²

The appropriate metric depends on the business objective.

---

### 81. Mean Absolute Error

MAE measures the average absolute difference between predictions and actual values.

Conceptually:

```text id="y45pj6"
Prediction
    ↓
Difference from Actual
    ↓
Absolute Error
    ↓
Average
```

It is relatively straightforward to interpret.

---

### 82. Mean Squared Error

MSE calculates the average squared prediction error.

Squaring the errors gives greater weight to larger errors.

This can be useful when large prediction errors are particularly undesirable.

---

### 83. Root Mean Squared Error

RMSE is the square root of MSE.

Because it is expressed in the same units as the predicted variable, it can be easier to interpret than MSE.

---

### 84. R-Squared

R² provides an indication of how much of the variation in the target variable is explained by the model under the chosen evaluation framework.

It should not be treated as a universal measure of model quality.

---

### 85. Training Performance

A model may perform extremely well on training data.

For example:

```text id="x3k9ps"
Training Accuracy
       99.9%
```

This does not prove that the model will perform equally well on unseen data.

---

### 86. Validation Performance

Validation performance helps determine whether a model generalizes during development.

A significant difference between training and validation performance may indicate problems such as:

* Overfitting
* Data leakage
* Dataset differences

---

### 87. Test Performance

The test set provides an additional assessment of generalization.

A simplified process is:

```text id="y7y8n4"
Training
   ↓
Validation
   ↓
Model Selection
   ↓
Final Test
```

The test set should ideally remain sufficiently independent from model-selection decisions.

---

### 88. Data Leakage

Data leakage occurs when information that should not be available to the model during training becomes available inappropriately.

This can create artificially strong performance.

For example:

```text id="4s0b9q"
Training Data
      ↓
Accidentally Contains
Future Information
      ↓
Artificially High Accuracy
```

Data leakage is a major model-governance concern.

---

### 89. Train-Test Contamination

Train-test contamination occurs when information from the test dataset influences model training or development decisions.

This compromises the validity of the evaluation.

Controls should ensure that test data remains appropriately isolated.

---

### 90. Cross-Validation

Cross-validation repeatedly divides available data into training and validation subsets to evaluate model performance.

A common approach is k-fold cross-validation:

```text id="w7yr2b"
Dataset
 ├── Fold 1
 ├── Fold 2
 ├── Fold 3
 ├── Fold 4
 └── Fold 5
```

Different folds are used for validation across multiple iterations.

---

### 91. Hyperparameter Tuning

Hyperparameter tuning attempts to identify suitable configuration values.

Examples include:

* Learning rate
* Tree depth
* Number of trees
* Regularization strength
* Batch size

The tuning process should be appropriately documented for high-risk systems.

---

### 92. Regularization

Regularization introduces constraints intended to reduce overfitting.

It encourages models to avoid relying excessively on particular patterns in the training data.

Examples include:

* L1 regularization
* L2 regularization
* Dropout

---

### 93. Dropout

Dropout is a neural-network training technique that temporarily disables selected units during training.

Conceptually:

```text id="31l8a6"
Neural Network
      ↓
Some Units Temporarily Disabled
      ↓
Training
      ↓
More Generalized Model
```

It can help reduce overfitting in some neural-network architectures.

---

### 94. Class Imbalance

Class imbalance occurs when one class is much more common than another.

For example:

```text id="r1q7ax"
Legitimate Transactions: 99.5%
Fraudulent Transactions: 0.5%
```

A model could achieve high overall accuracy while performing poorly on the minority class.

This is why accuracy alone can be misleading.

---

### 95. Imbalanced Security Data

Security datasets frequently have significant class imbalance.

Examples include:

* Malware detection
* Fraud
* Intrusion detection
* Insider-risk detection

Rare events may be precisely the events an organization cares most about.

Therefore, evaluation should consider appropriate metrics.

---

### 96. Sampling

Organizations may modify datasets through techniques such as:

* Oversampling
* Undersampling
* Synthetic sampling

These techniques can help address class imbalance but may also introduce their own risks.

Data transformations should be documented and validated.

---

### 97. Synthetic Minority Oversampling

SMOTE is an example of a technique that generates synthetic examples of minority classes.

Conceptually:

```text id="5i6u8w"
Minority Data
     ↓
Synthetic Examples
     ↓
More Balanced Dataset
     ↓
Training
```

The resulting synthetic data should still be evaluated for quality and unintended effects.

---

### 98. Feature Selection

Feature selection determines which input variables should be used by a model.

Potential objectives include:

* Reduce complexity
* Improve performance
* Improve interpretability
* Reduce computational cost
* Remove irrelevant variables

Feature selection can also reduce unnecessary exposure of sensitive data.

---

### 99. Feature Importance

Feature importance attempts to identify which variables contribute most to a model's predictions.

This can support:

* Model interpretation
* Validation
* Risk assessment
* Bias investigation

However, feature importance does not necessarily provide a complete causal explanation of model behavior.

---

### 100. Explainable Machine Learning

Machine-learning explainability techniques attempt to help humans understand model predictions.

Approaches include:

* Feature importance
* Partial dependence
* SHAP
* LIME
* Counterfactual explanations

The appropriate method depends on the model and use case.

---

# 101. Model Complexity

Model complexity can range from relatively simple models:

```text
Linear Regression
Decision Tree
```

to highly complex models:

```text
Deep Neural Network
Transformer
Foundation Model
```

Complexity can affect:

* Interpretability
* Compute requirements
* Testing
* Security
* Monitoring
* Governance

---

# 102. Black-Box Models

A model may be described as a "black box" when its internal decision process is difficult to understand or interpret.

Many complex neural networks have characteristics associated with black-box behavior.

This does not mean that they cannot be governed.

Instead, organizations may need stronger evidence through:

* Testing
* Documentation
* Evaluation
* Monitoring
* Model cards
* Human oversight

---

# 103. White-Box Versus Black-Box

Conceptually:

```text id="btr6i3"
White / Transparent
       ↓
Easier to inspect

Black / Complex
       ↓
Harder to inspect
```

The distinction should be understood as a spectrum rather than an absolute classification.

---

# 104. Model Interpretability and Risk

The required degree of interpretability should reflect the use case.

For a low-impact recommendation system:

```text
Lower Consequence
      ↓
Potentially Lower Explainability Requirement
```

For a high-impact decision:

```text
Higher Consequence
      ↓
Greater Need for Explanation,
Validation and Human Oversight
```

Risk should therefore influence model-governance requirements.

---

# 105. Algorithmic Bias

Machine-learning systems can produce systematically different outcomes across groups or conditions.

Potential sources include:

* Training data
* Labels
* Features
* Sampling
* Historical decisions
* Model design
* Deployment context

Bias assessment should therefore examine the entire lifecycle rather than only the final model.

---

# 106. Fairness Metrics

Depending on the use case, organizations may evaluate concepts such as:

* Demographic parity
* Equal opportunity
* Equalized odds
* False-positive-rate parity
* False-negative-rate parity

These metrics can conflict with one another in certain circumstances.

Therefore, fairness requirements must be defined in the context of the specific use case and applicable requirements.

---

# 107. Model Robustness Testing

Robustness testing examines how a model behaves under altered conditions.

Examples include:

```text id="rq7n6h"
Normal Input
Noisy Input
Incomplete Input
Unexpected Input
Adversarial Input
Distribution-Shifted Input
```

The goal is to understand model limitations before and after deployment.

---

# 108. Adversarial Machine Learning

Adversarial machine learning studies attacks and defenses involving machine-learning systems.

Potential attack categories include:

* Evasion
* Poisoning
* Model extraction
* Model inversion
* Membership inference

These attacks can affect confidentiality, integrity, availability, privacy, or decision quality.

---

# 109. Evasion Attacks

An evasion attack attempts to manipulate input at inference time so that the model produces an incorrect result.

Conceptually:

```text id="6a5b3k"
Original Input
      ↓
Manipulated Input
      ↓
Model
      ↓
Incorrect Classification
```

This is particularly relevant to security-sensitive classification systems.

---

# 110. Machine Learning Model Risk

Model risk can be summarized as the possibility that a model:

* Produces incorrect outputs
* Performs poorly under changed conditions
* Is used outside its intended purpose
* Contains data-quality problems
* Is inadequately validated
* Is improperly configured
* Is insufficiently monitored

Machine-learning governance should therefore address both **technical model risk** and **business-use risk**.

### 112. Business Problem Definition

Machine learning should begin with a clearly defined business problem.

The organization should establish:

* Business objective
* Intended users
* Intended decisions
* Expected outcomes
* Success criteria
* Risk tolerance
* Regulatory requirements

A technically impressive model can still be inappropriate if it solves the wrong business problem.

---

### 113. Model Purpose

Every production model should have a clearly defined purpose.

For example:

> Predict whether a transaction is potentially fraudulent.

This is preferable to an ambiguous description such as:

> AI fraud model.

The purpose should describe what the model is intended to accomplish.

---

### 114. Intended Use

The intended-use statement should describe:

* What the model should be used for
* Who may use it
* What decisions it supports
* What data it expects
* What limitations apply

This establishes boundaries around the model.

---

### 115. Prohibited Use

Organizations should also identify situations in which the model should **not** be used.

For example:

```text
Approved Use
     ↓
Fraud-risk screening

Not Approved
     ↓
Automatic customer rejection
```

This distinction is especially important when a model's output could be reused for purposes beyond its original design.

---

### 116. Data Acquisition

Data acquisition involves obtaining data used for:

* Training
* Validation
* Testing
* Inference
* Monitoring

Data sources may include:

* Internal databases
* Applications
* Sensors
* Logs
* Public datasets
* Commercial providers
* Third-party services

Each source introduces potential governance considerations.

---

### 117. Data Provenance

Data provenance describes where data came from and how it was processed.

A simplified chain is:

```text
Source
  ↓
Collection
  ↓
Transformation
  ↓
Storage
  ↓
Training Dataset
  ↓
Model
```

Strong provenance supports:

* Auditability
* Reproducibility
* Data-quality assessment
* Regulatory compliance
* Incident investigation

---

### 118. Data Ownership

Organizations should identify who owns or is responsible for relevant datasets.

Potential roles include:

* Data owner
* Data steward
* System owner
* Privacy owner
* Security owner

Ownership should not be assumed merely because the organization has technical access to the data.

---

### 119. Data Classification

Training and inference data should be classified according to organizational policies.

Possible categories include:

* Public
* Internal
* Confidential
* Restricted
* Sensitive

Classification determines which controls should apply.

---

### 120. Sensitive Training Data

Training data may contain:

* Personal information
* Financial information
* Credentials
* Business secrets
* Customer information
* Security information

The presence of sensitive information can significantly change the risk profile of the AI system.

---

### 121. Data Minimization

Data minimization means collecting and processing only the data necessary for the intended purpose.

For example:

```text
Available Data
      ↓
Relevant Data
      ↓
Required Features
      ↓
Training Dataset
```

This can reduce:

* Privacy exposure
* Security exposure
* Storage requirements
* Unnecessary model complexity

---

### 122. Data Quality

Poor-quality data can produce poor model outcomes.

Important data-quality dimensions include:

* Accuracy
* Completeness
* Consistency
* Timeliness
* Validity
* Uniqueness

The principle is simple:

> **Poor input data can produce unreliable model behavior.**

---

### 123. Data Quality Controls

Controls may include:

* Validation rules
* Duplicate detection
* Missing-value analysis
* Outlier detection
* Schema validation
* Data reconciliation
* Sampling
* Human review

These controls should be appropriate to the model's risk.

---

### 124. Data Labeling

Supervised-learning systems depend heavily on labels.

For example:

```text
Transaction → Fraud
Transaction → Legitimate
```

Labels may be created by:

* Humans
* Existing systems
* Rules
* Historical outcomes
* External providers

The source and quality of labels should be documented.

---

### 125. Label Quality

Labels can contain:

* Errors
* Inconsistencies
* Bias
* Ambiguity
* Outdated information

If the labels are wrong, the model may learn the wrong behavior.

Therefore, label-quality assurance is an important model-control activity.

---

### 126. Human Annotation

Human annotators may classify or label large datasets.

Governance considerations can include:

* Annotation instructions
* Quality assurance
* Sampling
* Reviewer consistency
* Access controls
* Confidentiality
* Worker privacy

Human annotation is therefore both a data-quality and governance issue.

---

### 127. Inter-Annotator Agreement

When multiple people label the same data, organizations may measure how consistently they agree.

Low agreement may indicate:

* Ambiguous definitions
* Poor labeling instructions
* Complex subject matter
* Subjective judgments

Low agreement can indicate that the underlying prediction task itself may require additional definition.

---

### 128. Data Preparation

Raw data normally requires preparation before model training.

Typical activities include:

```text
Raw Data
   ↓
Cleaning
   ↓
Transformation
   ↓
Normalization
   ↓
Feature Engineering
   ↓
Training Dataset
```

Every transformation can potentially affect model behavior.

---

### 129. Missing Data

Missing values can occur for many reasons.

Possible approaches include:

* Removing records
* Imputation
* Default values
* Predictive imputation
* Explicit missing-value indicators

The chosen approach should be documented and validated.

---

### 130. Outliers

Outliers are observations that differ significantly from other observations.

They may represent:

* Genuine rare events
* Data errors
* Fraud
* Attacks
* Sensor problems

Automatically removing outliers can be dangerous if the rare events are precisely what the model needs to detect.

---

### 131. Feature Engineering

Feature engineering transforms raw information into variables suitable for machine learning.

For example:

```text
Raw Data
   ↓
Transactions
   ↓
Transactions per Hour
   ↓
Feature
```

Feature engineering can strongly influence model performance.

---

### 132. Feature Engineering and Security

Features may unintentionally reveal sensitive information.

For example, apparently harmless variables may act as proxies for:

* Location
* Demographics
* Socioeconomic characteristics
* Identity

Therefore, feature selection should be reviewed from both technical and governance perspectives.

---

### 133. Feature Store

Organizations may use feature stores to manage machine-learning features.

A feature store can provide:

* Feature definitions
* Versioning
* Reuse
* Access control
* Data lineage
* Consistency

This becomes particularly important in large enterprise ML environments.

---

### 134. Training Dataset

The training dataset is the data used to teach the model.

A basic structure is:

```text
Training Dataset
├── Inputs
├── Features
└── Labels / Learning Signals
```

The dataset should be appropriately governed and versioned.

---

### 135. Validation Dataset

A validation dataset is used during development to help:

* Select models
* Tune parameters
* Compare configurations
* Evaluate performance

It should be managed carefully to avoid contaminating final evaluation.

---

### 136. Test Dataset

The test dataset is intended to provide an independent assessment of final model performance.

Ideally:

```text
Training → Development
Validation → Model Selection
Testing → Final Evaluation
```

The test dataset should not become another training dataset through repeated tuning.

---

### 137. Data Splitting

A dataset may be divided into:

```text
Training
Validation
Testing
```

For example, an organization might use a 70/15/15 split.

However, there is no universally correct percentage.

The split should reflect:

* Dataset size
* Use case
* Temporal characteristics
* Data dependencies
* Risk

---

### 138. Temporal Data Splitting

For time-dependent problems, random splitting may create misleading results.

For example:

```text
Past Data → Training
Later Data → Validation
Future Data → Testing
```

This may better represent how the model will operate in production.

---

### 139. Data Drift

Data drift occurs when the characteristics of input data change over time.

For example:

```text
Training Distribution
        ↓
Production Distribution
        ↓
Different
```

This may cause model performance to decline.

---

### 140. Concept Drift

Concept drift occurs when the relationship between inputs and outcomes changes over time.

For example, an attack pattern that once indicated fraud may no longer indicate fraud after attackers change their behavior.

Concept drift can therefore be particularly important in cybersecurity and fraud detection.

---

### 141. Model Drift

Model drift is a broad operational concept describing deterioration or change in model behavior over time.

It may result from:

* Data drift
* Concept drift
* Environmental changes
* Changing user behavior
* Infrastructure changes

Monitoring should identify relevant forms of drift.

---

### 142. Distribution Shift

Distribution shift occurs when production data differs from the distribution represented during model development.

This can occur because of:

* New users
* New markets
* New devices
* New attacks
* Economic changes
* Policy changes

Models should be evaluated for their sensitivity to such changes.

---

### 143. Training

Training is the process through which model parameters are learned from data.

Conceptually:

```text
      ↓
Algorithm
      ↓
Model Parameters
      ↓
Trained Model
```

Training may require significant computational resources for modern models.

### 144. Training Infrastructure

Training infrastructure can include:

* Containers
* Cloud services

### 145. Training Configuration

* Framework version

* Configuration files

Datasets should also be versioned where appropriate.

```text
      ↓
```

### 171. Machine Learning Security

Machine-learning security protects the ML system, its data, models, infrastructure, interfaces, and operational processes from unauthorized or malicious activity.

A useful security view is:

```text
                    MACHINE LEARNING SECURITY
                              │
        ┌─────────────────────┼─────────────────────┐
        ↓                     ↓                     ↓
     Data Security       Model Security       Infrastructure
        │                     │                     │
        ↓                     ↓                     ↓
   Training Data         Model Artifacts       Compute
   Labels                Model Access          Storage
   Features              Model Integrity       Network
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              ↓
                     Application Security
                              ↓
                     Monitoring & Response
```

The security boundary should encompass the **entire ML lifecycle**, not just the trained model.

---

### 172. Machine Learning Attack Surface

The ML attack surface can include:

* Data sources
* Training datasets
* Labels
* Feature pipelines
* Feature stores
* Training infrastructure
* Model artifacts
* Model registries
* APIs
* Inference endpoints
* Applications
* Users
* Third-party models
* Dependencies
* Monitoring systems

Every additional integration can introduce additional attack paths.

### 173. Training Data Security

Training data should be protected against:

* Unauthorized access
* Unauthorized modification
* Deletion
* Data leakage
* Poisoning
* Tampering

Controls may include:

* Access control
* Encryption
* Integrity validation
* Data classification
* Versioning
* Audit logging

### 174. Training Data Poisoning

Data poisoning occurs when an attacker deliberately manipulates training data to influence model behavior.

Conceptually:

```text
Legitimate Training Data
          +
Malicious Data
          ↓
      Training
          ↓
   Compromised Model
```

Possible objectives include:

* Lowering accuracy
* Creating targeted misclassifications
* Introducing hidden behavior
* Manipulating decision boundaries

---

### 175. Label Poisoning

Label poisoning specifically targets the labels associated with training examples.

For example:

```text
Actual: Malware
Label: Benign
```

If enough manipulated examples enter the training dataset, the model may learn incorrect relationships.

Controls include:

* Label validation
* Trusted annotation processes
* Sampling
* Independent review
* Data provenance

---

### 176. Feature Poisoning

Attackers may manipulate features rather than labels.

For example, an attacker could alter input characteristics so that the model learns an incorrect relationship.

Feature pipelines should therefore have integrity controls.

---

### 177. Model Integrity

Model integrity means ensuring that the approved model is not improperly modified.

Potential threats include:

* Unauthorized model modification
* Malicious model replacement
* Tampered model files
* Compromised dependencies
* Unauthorized retraining

Controls may include:

* Cryptographic hashes
* Digital signatures
* Access controls
* Version control
* Approved model registries

### 178. Model Artifact Security

* Encryption
* Storage controls
* Backup
* Retention policies

### 179. Model Theft

Model theft can create:

### 180. Model Extraction

Model extraction attempts to reproduce model behavior through repeated queries.

Conceptually:

```text
Attacker
   ↓
Model API
   ↓
Many Queries
   ↓
Observed Outputs
   ↓
Approximate / Substitute Model
```

Controls may include:

* Authentication
* Authorization
* Rate limiting
* Query monitoring
* Abuse detection

---

### 181. Model Inversion

Model inversion attempts to infer information about data associated with a trained model.

Potentially sensitive information could include characteristics of training examples.

The risk depends on:

* Model architecture
* Training data
* Access level
* Output information
* Attack capabilities

---

### 182. Membership Inference

Membership inference attempts to determine whether a specific record was part of a model's training dataset.

For example:

```text
Was Person X's record
included in the training data?

        ↓

Possible inference
```

This can create privacy risks, particularly when the dataset contains sensitive information.

---

### 183. Model Privacy

Machine-learning models may unintentionally retain or expose information about training data.

Privacy controls may include:

* Data minimization
* Access restrictions
* Privacy-preserving techniques
* Appropriate training methods
* Testing for leakage
* Retention controls

Privacy requirements should be determined according to the use case and applicable law.

---

### 184. Differential Privacy

Differential privacy is a mathematical framework intended to limit how much information about an individual can be inferred from statistical outputs.

It generally introduces carefully controlled randomness to reduce the influence of any individual record.

Conceptually:

```text
Sensitive Dataset
      ↓
Privacy Mechanism
      ↓
Statistical / ML Output
      ↓
Reduced Individual-Level Disclosure
```

It is one possible privacy-enhancing approach rather than a universal solution.

---

### 185. Federated Learning

Federated learning allows models to be trained across distributed data sources without necessarily centralizing all raw data.

Conceptually:

```text
Data Source A ──┐
                │
Data Source B ──┼──→ Federated Training
                │
Data Source C ──┘
                       ↓
                Aggregated Model
```

This can reduce the need to centralize raw data.

However, federated learning introduces its own security risks.

The exact implementation should be evaluated based on the threat model.

### 188. Adversarial Machine Learning

```text
├── Evasion
├── Model Extraction
├── Model Inversion
├── Membership Inference
└── Backdoor Attacks
```

The relevant threats depend on the system architecture.

### 189. Evasion Attacks

Evasion attacks manipulate inputs at inference time.

For example:

```text
Normal Input
     ↓
Adversarial Modification
     ↓
ML Model
     ↓
Incorrect Result
```

The attacker does not necessarily modify the model itself.

---

### 190. Adversarial Examples

An adversarial example is an input intentionally modified to cause an incorrect model prediction.

The modification may be difficult for humans to notice while significantly affecting the model.

This is particularly relevant to:

* Computer vision
* Security classification
* Pattern recognition

### 191. Backdoor Attacks

A backdoor attack attempts to create hidden model behavior that activates under specific conditions.

Conceptually:

```text

Trigger Input → Malicious / Unexpected Behavior
```

Backdoors can potentially be introduced through:

* Poisoned training data
* Compromised models
* Malicious third-party components

```text

     ↓

     ↓
```

Least privilege limits the impact of compromised models or applications.


This is one of the most important conceptual models in AI GRC.

### 260. Final GRC Perspective

Machine learning should be governed as a **socio-technical system**, not simply as a mathematical model.

A mature ML governance approach considers:

```text
             MACHINE LEARNING GOVERNANCE
                       │
     ┌─────────────────┼─────────────────┐
     ↓                 ↓                 ↓
   DATA              MODEL            PEOPLE
     │                 │                 │
     ↓                 ↓                 ↓
 Quality           Security          Accountability
 Privacy           Validation        Oversight
 Provenance        Performance       Training
 Access            Drift             Roles
     │                 │                 │
     └─────────────────┼─────────────────┘
                       ↓
                 TECHNOLOGY
                       │
              Infrastructure
              Applications
              APIs
              Cloud
                       ↓
                     RISK
                       ↓
                   CONTROLS
                       ↓
                  ASSURANCE
```

The central lesson of **02.02 — Machine Learning Types and Learning Paradigms** is that different learning approaches create different technical and governance characteristics.

A GRC professional should be able to distinguish **supervised, unsupervised, semi-supervised, self-supervised, reinforcement, transfer, and hybrid learning**, understand how data and models move through the ML lifecycle, recognize major security and model risks, and translate those risks into **governance requirements, control objectives, evidence, monitoring, and assurance activities**.

This technical foundation prepares the GRC professional for the next topic: **02.03 — Neural Networks and Modern AI Architectures**.
