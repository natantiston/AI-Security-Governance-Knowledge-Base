# 02.16 — AI Agents and Agentic AI Architecture

## Part 1 — AI Agent Foundations, Agentic AI Concepts, Components, Architecture, and Core Concepts

---

# 1. Introduction to AI Agents

An **AI agent** is an AI-enabled system that can perceive information, reason about a task, make decisions, and perform actions toward achieving an objective.

Unlike a conventional AI application that primarily responds to an input with an output, an agent can operate through a broader cycle:

```text
Perceive
   ↓
Interpret
   ↓
Reason
   ↓
Plan
   ↓
Act
   ↓
Observe Result
   ↓
Adapt
```

The ability to perform actions is one of the defining characteristics of agentic systems.

---

# 2. Agentic AI

**Agentic AI** refers to AI systems designed to perform tasks with a degree of autonomy by interpreting objectives, planning activities, using tools, interacting with systems, and evaluating results.

Agentic AI can range from relatively simple task automation to complex multi-agent systems.

---

# 3. AI Assistant Versus AI Agent

An AI assistant generally helps a user by responding to requests.

An AI agent can additionally:

* determine steps required to accomplish a goal;
* invoke tools;
* retrieve information;
* interact with external systems;
* maintain task state;
* evaluate results;
* continue execution.

The distinction is not absolute because modern AI assistants increasingly incorporate agentic capabilities.

---

# 4. Agentic Workflow

An agentic workflow is a sequence in which an AI system determines or executes multiple steps to accomplish a task.

Example:

```text
User Objective
      ↓
Task Interpretation
      ↓
Planning
      ↓
Information Retrieval
      ↓
Tool Invocation
      ↓
Result Evaluation
      ↓
Additional Action
      ↓
Final Response
```

---

# 5. Autonomous AI System

An autonomous AI system can perform some activities without requiring a human to approve every intermediate action.

The degree of autonomy is an important governance consideration.

---

# 6. AI Agent Autonomy

Agent autonomy describes the extent to which an agent can make decisions and perform actions without direct human intervention.

Autonomy may be:

* low;
* moderate;
* high;
* fully automated within defined boundaries.

---

# 7. Bounded Autonomy

**Bounded autonomy** allows an agent to operate independently within predefined constraints.

Example:

```text
Agent
  ↓
Allowed Actions
  ↓
Approved Systems
  ↓
Defined Data
  ↓
Spending Limit
  ↓
Human Escalation
```

Bounded autonomy is particularly important for enterprise AI governance.

---

# 8. Agent Goal

An agent goal describes the desired outcome the agent is expected to achieve.

Examples include:

* summarize an incident;
* investigate an alert;
* prepare a report;
* schedule a meeting;
* analyze a dataset;
* retrieve customer information.

---

# 9. Agent Objective

An objective translates a broader business goal into an operational target that an AI agent can pursue.

---

# 10. Agent Task

A task is a specific activity assigned to an agent.

A single objective may contain multiple tasks.

---

# 11. Agent Task Decomposition

Task decomposition breaks a complex objective into smaller executable activities.

Example:

```text
Objective:
Prepare Security Incident Report

        ↓

1. Retrieve incident data
2. Analyze events
3. Identify affected systems
4. Determine timeline
5. Draft findings
6. Produce report
```

---

# 12. Agent Planning

Planning is the process through which an agent determines the steps required to accomplish an objective.

---

# 13. Agent Plan

An agent plan is a representation of the actions the agent intends to perform.

Plans may be:

* predefined;
* dynamically generated;
* partially generated;
* continuously revised.

---

# 14. Dynamic Planning

Dynamic planning allows an agent to modify its planned actions based on new information or changing results.

---

# 15. Static Workflow

A static workflow follows predefined steps.

Example:

```text
Step 1
 ↓
Step 2
 ↓
Step 3
 ↓
Step 4
```

The workflow does not dynamically determine its next action.

---

# 16. Dynamic Agent Workflow

A dynamic agent workflow allows the system to determine the next action based on current context.

```text
Current State
     ↓
Agent Reasoning
     ↓
Next Action
     ↓
Result
     ↓
Updated State
     ↓
Agent Reasoning
```

---

# 17. Agent Perception

Perception is the process through which an agent obtains information about its environment.

Information may originate from:

* user input;
* APIs;
* databases;
* files;
* sensors;
* applications;
* websites;
* enterprise systems.

---

# 18. Agent Environment

The environment is the set of systems, data sources, users, applications, and external conditions with which an agent interacts.

---

# 19. Agent State

Agent state represents information about the current status of an agent's task.

It may include:

* current objective;
* completed steps;
* pending tasks;
* retrieved information;
* tool results;
* errors;
* decisions.

---

# 20. Agent State Management

State management determines how task information is maintained during agent execution.

---

# 21. Stateless Agent

A stateless agent does not retain meaningful execution state between separate interactions.

---

# 22. Stateful Agent

A stateful agent maintains information necessary to continue an ongoing task or workflow.

---

# 23. Agent Memory

Agent memory enables an agent to retain information that can influence future actions.

Memory can exist at different scopes:

* short-term;
* session;
* long-term;
* task-specific;
* organizational.

---

# 24. Short-Term Agent Memory

Short-term memory contains information relevant to the current interaction or execution cycle.

---

# 25. Long-Term Agent Memory

Long-term memory allows an agent to retain selected information beyond a single interaction.

---

# 26. Episodic Agent Memory

Episodic memory stores information about previous events, interactions, or experiences.

---

# 27. Semantic Agent Memory

Semantic memory stores knowledge or facts that can be retrieved independently of a specific event.

---

# 28. Working Memory

Working memory contains information actively used during the current reasoning process.

---

# 29. Agent Context

Agent context is the information available to the model when deciding what to do next.

Context may include:

* user instructions;
* system instructions;
* task state;
* retrieved information;
* tool results;
* previous interactions.

---

# 30. Context Management

Context management determines what information is included, retained, removed, summarized, or retrieved during agent execution.

---

# 31. Context Window

A context window is the amount of information a model can process within a particular interaction or inference operation.

Agent architectures must manage context carefully because extensive execution histories can exceed model context limits.

---

# 32. Agent Reasoning

Agent reasoning refers to the model's processing used to determine what action should be taken based on objectives, context, available information, and constraints.

---

# 33. Agent Decision-Making

Agent decision-making determines which action should be executed next.

---

# 34. Agent Action

An action is an operation performed by the agent or on behalf of the agent.

Examples include:

* querying a database;
* calling an API;
* sending an email;
* creating a ticket;
* modifying a record;
* executing a workflow.

---

# 35. Agent Action Space

The action space represents the set of actions available to an agent.

A larger action space generally increases the potential capability and risk of the agent.

---

# 36. Restricted Action Space

A restricted action space limits the operations an agent is allowed to perform.

This is an important security control for autonomous systems.

---

# 37. Agent Tool

A tool is an external capability that an AI agent can invoke to perform an operation that the model itself cannot directly perform.

Examples include:

* search;
* database query;
* calculator;
* email;
* ticketing;
* code execution;
* cloud API.

---

# 38. Tool Invocation

Tool invocation occurs when an agent requests execution of an external capability.

```text
Agent
 ↓
Tool Selection
 ↓
Tool Call
 ↓
Tool Execution
 ↓
Tool Result
 ↓
Agent
```

---

# 39. Tool Selection

Tool selection is the process through which an agent determines which available tool should be used for a task.

---

# 40. Tool Parameters

Tool parameters specify the inputs supplied to an external tool.

Incorrect or malicious parameters can cause unintended actions.

---

# 41. Tool Output

Tool output is the information returned by a tool after execution.

The agent may use the result for:

* reasoning;
* planning;
* additional tool calls;
* final responses.

---

# 42. Tool Execution Boundary

The tool execution boundary separates model reasoning from the external system that performs an action.

This boundary is important because actions outside the model can have real-world consequences.

---

# 43. Agent Action Boundary

An action boundary defines what an agent is permitted to do.

Examples include:

* read-only access;
* create-only access;
* restricted update access;
* administrative access.

---

# 44. Agent Permissions

Agent permissions determine which resources and operations an agent can access.

---

# 45. Agent Identity

An agent identity represents the identity under which an agent operates.

An enterprise agent should have an identifiable identity rather than operating through an uncontrolled shared credential.

---

# 46. Machine Identity

An agent may operate using a machine identity, service identity, workload identity, or other non-human identity.

---

# 47. Agent Authentication

Authentication establishes the identity of the agent or associated user before access is granted.

---

# 48. Agent Authorization

Authorization determines what an authenticated agent is permitted to access or perform.

---

# 49. Agent Least Privilege

Agent permissions should be limited to the minimum capabilities required to accomplish the authorized task.

---

# 50. Agent Privilege Escalation

Privilege escalation occurs when an agent obtains or exercises greater permissions than originally authorized.

Agent architectures should include controls to prevent unauthorized privilege escalation.

---

# 51. Agent Credential Management

Credentials used by agents should be centrally managed and protected.

Credentials may include:

* API keys;
* OAuth tokens;
* certificates;
* service credentials;
* cloud identities.

---

# 52. Agent Secret Management

Secrets should not be embedded directly into prompts, source code, configuration files, or model context where avoidable.

---

# 53. Agent Execution Environment

The execution environment contains the infrastructure and software in which an agent operates.

It may include:

* application servers;
* containers;
* cloud services;
* runtime environments;
* orchestration platforms.

---

# 54. Agent Runtime

The runtime is the environment responsible for executing the agent's operational logic.

---

# 55. Agent Orchestrator

An orchestrator coordinates agent execution, tools, workflows, state, and external services.

---

# 56. Agent Controller

An agent controller manages execution decisions and operational constraints around an agent.

---

# 57. Agent Loop

A common agent architecture uses an iterative loop:

```text
Observe
  ↓
Reason
  ↓
Plan
  ↓
Act
  ↓
Observe
```

The loop continues until the task is completed, stopped, or escalated.

---

# 58. Observe-Reason-Act Cycle

The observe-reason-act cycle provides a conceptual model for understanding agent behavior.

---

# 59. Perceive-Plan-Act Cycle

Another common abstraction is:

```text
Perceive
   ↓
Plan
   ↓
Act
   ↓
Perceive
```

---

# 60. Agent Feedback Loop

Agent feedback occurs when the result of an action influences subsequent decisions.

---

# 61. Agent Iteration

An iteration is one execution cycle through an agent's reasoning and action process.

---

# 62. Agent Termination

Termination occurs when the agent stops execution.

Termination may occur because:

* the objective is achieved;
* a failure occurs;
* a policy restriction is reached;
* a timeout occurs;
* a human stops execution.

---

# 63. Agent Termination Condition

A termination condition defines when an agent must stop executing.

---

# 64. Agent Timeout

A timeout prevents an agent from continuing execution indefinitely.

---

# 65. Agent Maximum Iterations

A maximum-iteration limit restricts the number of reasoning and action cycles an agent can perform.

---

# 66. Agent Cost Limit

A cost limit restricts the resources an agent can consume.

Resources may include:

* model tokens;
* API calls;
* compute;
* cloud services;
* external transactions.

---

# 67. Agent Rate Limit

Rate limits restrict how frequently an agent can invoke a service or tool.

---

# 68. Agent Budget

An agent budget defines the maximum authorized resource consumption for an execution or period.

---

# 69. Agent Transaction Limit

A transaction limit restricts the financial or operational value of actions an agent may perform.

---

# 70. Human-in-the-Loop

Human-in-the-loop architecture requires human involvement in specified decisions or actions.

```text
Agent Decision
      ↓
Human Review
      ↓
Approve / Reject
      ↓
Agent Action
```

---

# 71. Human-on-the-Loop

Human-on-the-loop architecture allows an agent to operate autonomously while humans monitor its activities and intervene when necessary.

---

# 72. Human-in-Command

Human-in-command places strategic and consequential decision authority with humans while AI supports execution or analysis.

---

# 73. Human Approval Gate

An approval gate requires explicit authorization before an agent performs a specified action.

---

# 74. High-Impact Action Approval

Actions with significant business, financial, legal, security, safety, or privacy consequences may require human approval.

---

# 75. Agent Escalation

Escalation transfers a task or decision to a human or higher-authority system when predefined conditions are met.

---

# 76. Agent Escalation Condition

Escalation conditions may include:

* uncertainty;
* policy violation;
* high-risk transaction;
* unusual behavior;
* insufficient information;
* system failure.

---

# 77. Agent Confidence

Agent confidence represents an assessment associated with the system's certainty about a classification, decision, or response.

Confidence should not automatically be interpreted as correctness.

---

# 78. Agent Uncertainty

Uncertainty represents situations where available information or model reasoning is insufficient to support a reliable decision.

---

# 79. Agent Uncertainty Threshold

An uncertainty threshold can be used to determine when an agent should stop, request more information, or escalate.

---

# 80. Agent Guardrails

Guardrails are technical, procedural, or policy controls that constrain agent behavior.

They can control:

* inputs;
* outputs;
* tools;
* data;
* actions;
* permissions;
* execution.

---

# 81. Preventive Agent Guardrails

Preventive guardrails block prohibited actions before they occur.

---

# 82. Detective Agent Guardrails

Detective guardrails identify potentially unsafe or unauthorized behavior.

---

# 83. Corrective Agent Guardrails

Corrective guardrails trigger remediation after an undesirable event or behavior.

---

# 84. Agent Policy Enforcement

Policy enforcement ensures that agent behavior remains within organizational rules.

---

# 85. Agent Policy Engine

A policy engine evaluates whether a proposed agent action is permitted.

Conceptually:

```text
Agent Action
     ↓
Policy Evaluation
     ↓
Allowed? ─── No → Block / Escalate
     │
    Yes
     ↓
Execute
```

---

# 86. Agent Safety Policy

An agent safety policy defines prohibited or restricted behaviors.

---

# 87. Agent Security Policy

An agent security policy defines requirements for authentication, authorization, data handling, tool use, monitoring, and incident response.

---

# 88. Agent Governance Policy

An agent governance policy establishes organizational requirements for designing, deploying, operating, monitoring, and retiring AI agents.

---

# 89. Agent Scope

Agent scope defines the boundaries of the tasks, systems, data, users, and environments an agent may interact with.

---

# 90. Agent Boundary

The agent boundary defines the controlled environment within which the agent operates.

---

# 91. Agent Trust Boundary

A trust boundary identifies where different levels of trust or control exist between components.

Examples include:

* model to tool;
* agent to API;
* agent to enterprise system;
* agent to external service.

---

# 92. Agent Security Boundary

The security boundary identifies where security controls are applied to protect agent resources and interactions.

---

# 93. Agent Data Boundary

The data boundary defines which information an agent can access, process, retain, or transmit.

---

# 94. Agent Network Boundary

The network boundary controls the network destinations and services an agent can reach.

---

# 95. Agent System Boundary

The system boundary defines the applications, infrastructure, services, and components included within the agent architecture.

---

# 96. Agent Input

Agent input includes information provided to the agent before or during execution.

Inputs may originate from:

* users;
* applications;
* APIs;
* sensors;
* databases;
* documents;
* other agents.

---

# 97. Agent Output

Agent output is the information or action produced by an agent.

Outputs can include:

* text;
* decisions;
* recommendations;
* API calls;
* transactions;
* system changes.

---

# 98. Agent Input Validation

Input validation checks whether incoming information conforms to expected formats and policies.

---

# 99. Agent Output Validation

Output validation checks whether generated responses or actions meet defined requirements before being delivered or executed.

---

# 100. Agent Action Validation

Action validation determines whether an intended action is safe and authorized before execution.

---

# 101. Agent Environment Validation

Environment validation verifies that the target system, resource, or context is appropriate before an action is executed.

---

# 102. Agent Plan Validation

Plan validation evaluates whether an agent's proposed sequence of actions complies with defined policies and constraints.

---

# 103. Agent Execution Validation

Execution validation confirms that the actual action corresponds to the authorized action.

---

# 104. Agent Result Validation

Result validation evaluates whether the result of an action is plausible, complete, and acceptable.

---

# 105. Agent Feedback Validation

Feedback validation prevents untrusted or malicious results from being blindly incorporated into subsequent agent decisions.

---

# 106. Agent Tool Trust

Tools used by agents should be evaluated based on:

* ownership;
* security;
* reliability;
* permissions;
* data access;
* business criticality.

---

# 107. Trusted Agent Tool

A trusted tool is an authorized capability that has been evaluated and approved for agent use.

---

# 108. Untrusted Agent Tool

An untrusted tool has not been sufficiently validated or authorized for use by an enterprise agent.

---

# 109. Agent Tool Registry

A tool registry maintains an inventory of tools available to agents.

It may record:

* tool name;
* owner;
* purpose;
* permissions;
* data access;
* risk classification;
* approval status.

---

# 110. Agent Tool Allowlist

An allowlist restricts agents to explicitly approved tools.

---

# 111. Agent Tool Denylist

A denylist explicitly prevents agents from using specified tools or capabilities.

Allowlisting is generally stronger for controlling sensitive agent capabilities because it defines what is permitted rather than only what is prohibited.

---

# 112. Agent API Access

Agents frequently interact with enterprise systems through APIs.

API access should be controlled through:

* authentication;
* authorization;
* rate limits;
* validation;
* logging;
* monitoring.

---

# 113. Agent API Gateway

An API gateway can provide a controlled boundary between an agent and external services.

---

# 114. Agent Service Mesh

A service mesh may provide communication controls, authentication, authorization, observability, and policy enforcement for distributed agent architectures.

---

# 115. Agent Data Access

Agent data access determines which information sources an agent may query or manipulate.

---

# 116. Agent Data Permissions

Data permissions should follow least-privilege principles.

---

# 117. Agent Database Access

Agents interacting with databases should use restricted database identities and controlled queries.

---

# 118. Agent Read Access

Read access allows an agent to retrieve information without modifying the underlying resource.

---

# 119. Agent Write Access

Write access allows an agent to create or modify information.

Write capabilities generally require stronger governance than read-only capabilities.

---

# 120. Agent Delete Access

Delete access allows an agent to remove information or resources.

Because deletion may be difficult or impossible to reverse, it should normally receive heightened controls.

---

# 121. Agent Administrative Access

Administrative access provides broad control over systems and should be highly restricted.

---

# 122. Agent Transactional Capability

Transactional capability allows an agent to execute actions with direct business consequences.

Examples include:

* purchasing;
* payment;
* account modification;
* order creation;
* infrastructure changes.

---

# 123. Agent Read-Only Architecture

A read-only agent architecture limits the agent to information retrieval and analysis.

This can substantially reduce operational risk compared with unrestricted write access.

---

# 124. Agent Write-Enabled Architecture

A write-enabled agent can modify external systems.

Such architectures require stronger:

* authorization;
* validation;
* monitoring;
* approval;
* rollback controls.

---

# 125. Agent Transactional Architecture

A transactional agent can execute business or financial transactions.

These agents require particularly strong governance because model decisions can directly affect organizational assets.

---

# 126. Agent Rollback

Rollback allows an action or change to be reversed when technically possible.

---

# 127. Agent Reversibility

Reversibility describes whether an agent's action can be safely undone.

Actions can be categorized as:

```text
Fully Reversible
      ↓
Partially Reversible
      ↓
Difficult to Reverse
      ↓
Irreversible
```

---

# 128. Agent Irreversible Action

An irreversible action cannot be reliably undone after execution.

Examples may include:

* permanent deletion;
* external publication;
* certain financial transactions;
* irreversible infrastructure changes.

Such actions should receive heightened controls.

---

# 129. Agent Action Risk Classification

Agent actions can be classified according to potential impact.

Example:

| Action                        | Typical Risk |
| ----------------------------- | ------------ |
| Read public information       | Low          |
| Query internal data           | Moderate     |
| Modify business record        | High         |
| Delete critical data          | Very High    |
| Execute financial transaction | Very High    |

---

# 130. Agent Risk-Based Authorization

Authorization requirements should increase with the potential impact of the agent's action.

---

# 131. Agent Capability Classification

Agent capabilities can be classified into:

* informational;
* analytical;
* operational;
* transactional;
* administrative.

---

# 132. Informational Agent

An informational agent primarily retrieves and presents information.

---

# 133. Analytical Agent

An analytical agent interprets information and produces analysis, recommendations, or assessments.

---

# 134. Operational Agent

An operational agent performs actions within enterprise systems.

---

# 135. Transactional Agent

A transactional agent performs actions that create direct business or financial consequences.

---

# 136. Administrative Agent

An administrative agent can manage systems, identities, configurations, or infrastructure.

Administrative agents represent a high-risk category because of their potentially broad privileges.

---

* approvals;

---

# 160. Agent GRC Perspective

From a GRC perspective, an AI agent should be treated as more than a model.

It is a **socio-technical system consisting of AI models, instructions, memory, data, tools, identities, permissions, workflows, infrastructure, humans, and external dependencies**.

Therefore, effective governance must evaluate the **complete agentic system and its potential actions**, not merely the underlying AI model.
