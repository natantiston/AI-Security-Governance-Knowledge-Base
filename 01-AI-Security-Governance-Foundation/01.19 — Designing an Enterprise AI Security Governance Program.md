# 01.19 — Designing an Enterprise AI Security Governance Program

## Part 1 — Foundations and Program Design

### 1. Introduction to an Enterprise AI Security Governance Program

An Enterprise AI Security Governance Program establishes the organizational structure, policies, processes, controls, responsibilities, and oversight mechanisms required to govern AI security across the enterprise.

The program provides a systematic approach for ensuring that AI systems are:

* Identified
* Classified
* Assessed
* Secured
* Monitored
* Governed throughout their lifecycle
* Subject to appropriate accountability
* Aligned with enterprise risk requirements

The objective is not simply to create an AI policy.

The objective is to establish an **enterprise capability for governing AI security risk**.

---

### 2. Purpose of the Program

An Enterprise AI Security Governance Program should enable the organization to:

* Understand its AI environment
* Establish accountability
* Identify AI security risks
* Define governance requirements
* Apply security controls
* Manage AI throughout its lifecycle
* Govern third-party AI
* Monitor AI security
* Respond to AI-related incidents
* Demonstrate compliance
* Continuously improve governance

The program should support secure AI adoption rather than treating governance as an obstacle to innovation.

---

### 3. Enterprise-Wide Perspective

AI Security Governance should not be limited to the cybersecurity department.

AI affects multiple organizational functions, including:

* Executive leadership
* Business units
* Information technology
* Cybersecurity
* Risk management
* Privacy
* Legal
* Compliance
* Procurement
* Internal audit
* Data management
* Human resources
* Enterprise architecture

An enterprise program provides a common governance structure across these functions.

---

### 4. AI Security Governance as an Enterprise Capability

The program should be treated as an organizational capability rather than a temporary project.

A project typically has:

* A defined start
* A defined end
* Specific deliverables

A governance program requires:

* Continuous ownership
* Ongoing operations
* Monitoring
* Measurement
* Improvement
* Periodic reassessment

AI Security Governance therefore requires permanent organizational capability.

---

### 5. Program Versus Project

An organization may initially establish AI Security Governance through a project.

For example:

**AI Governance Implementation Project**

→ Establish policies, roles, inventory, risk methodology, and initial controls.

After implementation:

**AI Security Governance Program**

→ Operate, monitor, measure, assure, and continuously improve those capabilities.

The project creates the foundation; the program sustains it.

---

### 6. Program Objectives

A mature program should establish measurable objectives.

Examples include:

* Achieve enterprise AI visibility.
* Establish AI ownership.
* Implement risk-based AI classification.
* Integrate security into the AI lifecycle.
* Establish AI security standards.
* Govern third-party AI.
* Establish AI incident-response capabilities.
* Implement AI security monitoring.
* Improve AI literacy.
* Provide executive and board-level assurance.

Objectives should be aligned with enterprise strategy and risk appetite.

---

### 7. Program Scope

The program should clearly define what forms of AI are governed.

Scope may include:

* Machine-learning systems
* Generative AI
* Large language models
* AI-enabled applications
* AI agents
* Predictive analytics
* Recommendation systems
* Computer vision
* Natural-language processing
* AI APIs
* Third-party AI services
* Embedded AI capabilities

The scope should also address AI developed internally and AI acquired from external providers.

---

### 8. Enterprise AI Landscape

Before designing governance, the organization should understand how AI is being used.

AI may exist in:

* Customer applications
* Internal applications
* Cloud platforms
* Software-as-a-service platforms
* Security platforms
* Contact centers
* Human resources systems
* Financial systems
* Engineering systems
* Data analytics platforms

AI capabilities may also exist without being explicitly labeled as "AI."

---

### 9. Shadow AI

Shadow AI refers to AI usage that occurs outside approved organizational governance processes.

Examples may include employees using:

* Public generative AI services
* Unapproved AI assistants
* External AI APIs
* Personal AI accounts
* AI-enabled browser tools

Shadow AI can create risks involving:

* Sensitive information
* Intellectual property
* Privacy
* Security
* Compliance
* Third-party dependency

An effective governance program should address shadow AI without relying exclusively on prohibition.

---

### 10. AI Program Governance Principles

The program should establish foundational principles.

Potential principles include:

**Accountability**

→ AI systems must have identifiable owners.

**Risk-Based Governance**

→ Controls should reflect AI risk.

**Security by Design**

→ Security should be integrated from the beginning.

**Lifecycle Governance**

→ AI should remain governed throughout its lifecycle.

**Least Privilege**

→ AI systems and agents should receive only necessary access.

**Transparency**

→ Relevant stakeholders should understand how AI is governed.

**Continuous Improvement**

→ Governance should evolve with AI risks and technologies.

---

These may include:

* Enterprise strategy

* Existing policies
* Existing security controls
* Existing GRC processes

* Threat landscape

The program should build on existing capabilities wherever practical.

An initial assessment should identify existing:

* Cybersecurity governance
* Information security policies
* Data governance
* Privacy governance
* Enterprise risk management
* Third-party risk management
* Software development governance
* Architecture governance
* Change management
* Incident management

Existing capabilities can often be extended to support AI.

### 13. Governance Gap Assessment

The organization should identify where existing governance does not adequately address AI.

Potential gaps include:

* AI ownership
* AI inventory
* AI risk classification
* AI-specific threat modeling
* Model governance
* AI agent governance
* AI supply-chain security
* Generative AI security
* AI monitoring

The objective is to identify what must be added, modified, or strengthened.

---

* Risk-based
* Scalable
* Proportionate

* Lifecycle-oriented

* Integrated with existing governance
* Measurable
* Adaptable

These principles help prevent the program from becoming unnecessarily complex.

### 20. Risk-Based Decision Escalation

Not every AI system requires executive or committee review.

The program should establish escalation thresholds.

For example:

**Low Risk**

→ Standard business approval.

**Moderate Risk**

→ Security and risk review.

**High Risk**

→ Formal governance review.

**Critical Risk**

→ Executive-level approval and enhanced assurance.

This allows governance to scale with risk.

It can act as the central point of coordination without necessarily owning every AI system.

Business units should retain accountability for the AI systems they use.

Business owners should understand:

* Business purpose

* Business impact

Risk functions should ensure AI risks are appropriately identified, assessed, and escalated.

Responsibilities may include:

* Risk methodology
* Risk reporting
* Risk appetite alignment
* Risk acceptance oversight

* Data minimization

### 27. Legal and Compliance Governance

Legal and compliance functions can support:

* Regulatory interpretation
* Contractual requirements
* AI obligations

* Compliance assessments
* Regulatory reporting

* Security requirements
* Privacy requirements

### 30. Secure AI Development Governance

Governance may cover:

* Requirements

* Autonomy

**Tier 1 — Low Risk**

**Tier 4 — Critical Risk**

Approval may consider:

* Business need
* Risk

* Compensating controls
* Approval authority

### 37. AI Risk Acceptance

The process should identify:

* Risk owner
* Risk description

* Risk appetite

Standards may address:

**Evidence**

→ Demonstration that requirements operate.

This documentation architecture supports consistency and accountability.

# 01.19 — Designing an Enterprise AI Security Governance Program

## Part 2 — Operating Model, Governance Processes and Security Integration

### 41. AI Security Governance Operating Model

An Enterprise AI Security Governance Program requires an operating model that explains how governance activities are performed across the organization.

The operating model should define:

* Who makes decisions
* Who owns AI risks
* Who implements controls
* Who provides oversight
* Who performs assurance
* How information flows
* How issues are escalated

The operating model converts the governance framework into an operational capability.

---

### 42. Centralized AI Security Governance Model

In a centralized model, a central governance function has significant authority over AI governance.

The central function may control:

* AI approval
* AI risk assessments
* AI security standards
* AI inventory
* AI governance reporting
* AI exception management

This model can provide strong consistency but may become a bottleneck as AI adoption increases.

---

### 43. Decentralized AI Security Governance Model

In a decentralized model, individual business units manage most AI governance activities.

Business units may control:

* AI systems
* Risk assessments
* Approvals
* Security implementation
* Monitoring

A decentralized model can provide flexibility but may produce inconsistent governance.

---

### 44. Federated AI Security Governance Model

A federated model distributes responsibility between central governance and business units.

The central function establishes:

* Enterprise policies
* Standards
* Minimum controls
* Risk methodology
* Reporting requirements

Business units remain responsible for:

* AI implementation
* Local risk management
* Operational controls
* System ownership

Federated governance is often useful for large organizations with diverse AI environments.

---

### 45. Hybrid AI Security Governance Model

A hybrid model combines centralized decision-making for high-risk areas with decentralized management for lower-risk AI.

For example:

**Central Governance**

→ High-risk AI approval.

**Business Units**

→ Low-risk AI implementation.

**Security**

→ Security standards and assurance.

**Risk**

→ Risk methodology and independent challenge.

This approach can balance consistency, speed, and risk management.

---

### 46. Selecting the Appropriate Operating Model

The organization should select its operating model based on:

* Organizational size
* AI adoption
* Business complexity
* Geographic distribution
* Regulatory requirements
* Risk appetite
* AI criticality
* Existing governance structure

There is no universally correct AI governance operating model.

---

### 47. AI Governance Decision Rights

The operating model should define decision rights.

Decision rights should identify who can:

* Approve AI use
* Reject AI use
* Approve high-risk AI
* Accept residual risk
* Approve exceptions
* Suspend AI systems
* Approve production deployment
* Authorize changes

Unclear decision rights can cause delays and accountability failures.

---

### 48. AI Governance Escalation

Escalation mechanisms should be defined for situations that exceed normal authority.

Escalation may be triggered by:

* High residual risk
* Regulatory concerns
* Significant security findings
* Sensitive data usage
* High AI autonomy
* Critical business impact
* Material incidents

Escalation thresholds should be documented.

---

### 49. AI Governance Workflow

A standardized workflow can provide consistency.

A typical process may be:

**AI Proposal**

→

**AI Intake**

→

**Classification**

→

**Risk Assessment**

→

**Security Assessment**

→

**Privacy / Compliance Review**

→

**Approval**

→

**Deployment**

→

**Monitoring**

→

**Periodic Reassessment**

→

**Retirement**

The workflow should be risk-based rather than identical for every AI system.

---

### 50. AI Intake and Registration

Every AI system within program scope should enter an appropriate intake process.

Information may include:

* AI system name
* Business purpose
* Business owner
* Technical owner
* AI type
* Model
* Provider
* Data
* Users
* Integrations
* Autonomy
* Business criticality

The intake process provides the foundation for governance visibility.

---

### 51. AI Inventory Management

The AI inventory should function as a living governance record.

It should ideally track:

* Current AI systems
* Owners
* Risk classification
* Data classification
* Provider
* Deployment environment
* Lifecycle status
* Security assessment
* Approval status
* Exceptions

Inventory information should be periodically reconciled.

---

### 52. AI Discovery Mechanisms

Organizations should use multiple mechanisms to discover AI systems.

Potential sources include:

* Procurement systems
* Application inventories
* Cloud platforms
* Network telemetry
* Endpoint data
* Vendor records
* Development repositories
* Business-unit questionnaires

Combining multiple discovery mechanisms reduces the risk of shadow AI.

---

### 53. AI Risk Assessment Process

The AI risk assessment should determine the potential impact and likelihood of AI-related risks.

Assessment factors may include:

* Data sensitivity
* Business criticality
* Decision impact
* AI autonomy
* Security exposure
* Third-party dependency
* Regulatory requirements

The result should inform the required governance level.

---

### 54. Inherent AI Risk

Inherent risk represents the level of risk before considering mitigating controls.

For example, an AI agent capable of executing financial transactions may have high inherent risk because of:

* High autonomy
* High business impact
* External connectivity
* Potential financial loss

Inherent risk provides the baseline for evaluating control requirements.

---

### 55. Residual AI Risk

Residual risk represents the remaining risk after controls are implemented.

The program should determine whether residual risk:

* Falls within appetite
* Requires additional treatment
* Requires formal acceptance
* Requires escalation

Residual risk should remain visible throughout the AI lifecycle.

---

### 56. AI Security Architecture Review

High-risk AI systems should undergo appropriate architecture review.

The review may examine:

* Data flows
* Trust boundaries
* Model hosting
* APIs
* Identity
* Network connectivity
* External services
* Agent tools
* Secrets
* Logging
* Resilience

Architecture review helps identify risks before deployment.

---

### 57. AI Threat Modeling

Threat modeling should identify realistic attack scenarios.

Potential scenarios include:

* Prompt injection
* Data poisoning
* Model theft
* Model manipulation
* Unauthorized access
* Sensitive-data leakage
* Malicious tool invocation
* Supply-chain compromise

Threat modeling should inform security requirements and testing.

---

### 58. AI Secure Development Lifecycle

AI development should be integrated into the organization's secure development lifecycle.

Governance requirements may apply to:

* Requirements
* Architecture
* Data preparation
* Model development
* Code
* Testing
* Deployment
* Monitoring
* Change management

AI security should not be treated as a final-stage review.

---

### 59. AI Data Security Governance

Data governance should be integrated into AI governance.

Controls may address:

* Data classification
* Data access
* Data minimization
* Data lineage
* Data quality
* Data retention
* Encryption
* Sensitive-data protection

AI systems should not receive access to data simply because the technology is capable of processing it.

---

### 60. AI Model Security Governance

Model security should address risks associated with:

* Model access
* Model storage
* Model versions
* Model artifacts
* Model dependencies
* Model modification
* Model deployment

Model governance should integrate security, risk, and lifecycle requirements.

---

### 61. AI Application Security

AI applications should be subject to application-security requirements.

These may include:

* Secure coding
* Dependency management
* API security
* Authentication
* Authorization
* Input validation
* Output handling
* Security testing
* Vulnerability management

AI functionality does not replace traditional application security requirements.

---

### 62. AI Agent Security Governance

AI agents require additional governance because they may perform actions on behalf of users.

Governance should address:

* Agent identity
* Authentication
* Authorization
* Tool permissions
* Data access
* Action boundaries
* Human approval
* Transaction limits
* Monitoring

The level of control should correspond to the potential impact of agent actions.

---

### 63. Least Privilege for AI Agents

AI agents should operate using the minimum permissions required to perform their intended functions.

For example, an agent that needs to retrieve customer information should not automatically receive permission to:

* Delete records
* Modify financial data
* Change security configurations
* Create privileged accounts

Agent permissions should be explicitly defined.

---

### 64. Human Oversight for AI Agents

Human oversight should be established where agent actions could create material consequences.

Human approval may be required for:

* Financial transactions
* High-impact decisions
* Privileged operations
* Sensitive data transfers
* External communications
* Irreversible actions

Human oversight should be designed according to risk rather than applied mechanically.

---

### 65. Third-Party AI Governance

AI providers should be incorporated into third-party risk management.

Assessment may include:

* Security
* Privacy
* Data use
* Model training practices
* Service availability
* Subprocessors
* Incident response
* Contractual protections
* Exit arrangements

Third-party AI should be governed according to its risk and business importance.

---

### 66. AI Vendor Due Diligence

Before adopting an AI provider, organizations may evaluate:

* Provider security controls
* Certifications or assurance reports
* Data-processing practices
* Access controls
* Encryption
* Incident management
* Business continuity
* Vulnerability management

The assessment should be proportional to the AI service's risk.

---

### 67. AI Contractual Governance

AI contracts should address relevant governance requirements.

Potential provisions include:

* Data-use restrictions
* Security requirements
* Privacy obligations
* Incident notification
* Audit rights
* Subprocessor requirements
* Service levels
* Data return
* Data deletion
* Termination rights

Contractual controls should support the organization's AI governance requirements.

---

### 68. AI Supply-Chain Governance

The program should consider the complete AI supply chain.

Dependencies may include:

* Foundation models
* Training datasets
* APIs
* Libraries
* Cloud infrastructure
* AI platforms
* Third-party applications

Supply-chain governance should provide visibility into material dependencies.

---

### 69. AI Identity Governance

AI systems may require identities for:

* Applications
* Services
* Models
* Agents
* APIs
* Automation processes

Each identity should have appropriate authentication, authorization, monitoring, and lifecycle management.

---

### 70. AI Access Governance

Access governance should determine:

* Who can use AI
* Which AI systems they can access
* Which data they can access
* Which functions they can perform
* Which tools AI agents can invoke

Access should be aligned with business need and risk.

---

### 71. Privileged Access for AI

AI systems with privileged access require enhanced controls.

Controls may include:

* Privileged access management
* Strong authentication
* Session monitoring
* Credential rotation
* Just-in-time access
* Approval workflows

Privileged AI access should be tightly controlled.

---

### 72. AI Logging and Auditability

AI systems should generate sufficient records to support:

* Security monitoring
* Investigations
* Compliance
* Accountability
* Incident response

Depending on the system, logs may include:

* User identity
* AI system accessed
* API calls
* Administrative actions
* Agent actions
* Security events

Logging requirements should consider privacy and data minimization.

---

### 73. AI Security Monitoring

Monitoring should detect abnormal or unauthorized behavior.

Potential monitoring areas include:

* Authentication
* API usage
* Model access
* Data transfers
* Agent activity
* Configuration changes
* Security events

Monitoring depth should correspond to AI risk.

---

### 74. AI Security Incident Response

The program should integrate AI incidents into enterprise incident response.

AI-specific scenarios may include:

* Prompt injection attack
* Model compromise
* Sensitive-data exposure
* Malicious AI output
* Unauthorized agent action
* AI provider compromise

Incident procedures should define responsibilities and escalation.

---

### 75. AI Incident Classification

AI incidents should be classified according to impact.

Factors may include:

* Data sensitivity
* Number of affected users
* Business disruption
* Financial impact
* Regulatory impact
* Security impact
* Safety implications

Classification determines escalation and response requirements.

---

### 76. AI Business Continuity

Critical AI systems should be incorporated into business continuity planning.

Planning may address:

* AI provider outages
* Model availability
* Data availability
* API failures
* Infrastructure failures
* Cybersecurity incidents

Organizations should determine whether manual or alternative processes are required.

---

### 77. AI Disaster Recovery

Disaster recovery should address the components required to restore AI services.

These may include:

* Models
* Data
* Configurations
* Infrastructure
* APIs
* Credentials
* Dependencies

Recovery objectives should reflect business criticality.

---

### 78. AI Change Management

AI systems can change through:

* Model updates
* Prompt changes
* Data changes
* Configuration changes
* Software updates
* Provider changes
* Agent capability changes

Material changes should trigger appropriate reassessment.

---

### 79. AI Version Management

Organizations should maintain appropriate version information for:

* Models
* Applications
* Prompts where operationally relevant
* Configurations
* AI agents
* Dependencies

Version tracking supports:

* Security
* Reproducibility
* Incident investigation
* Change management
* Accountability

---

### 80. AI Retirement Governance

AI systems should have formal retirement processes.

Retirement may require:

* Revoking access
* Removing credentials
* Decommissioning infrastructure
* Managing data
* Terminating vendor services
* Archiving required records
* Updating the AI inventory

Retirement is part of AI governance, not merely a technical decommissioning activity.

## Part 3 — Program Controls, Assurance, Metrics and Operational Management

### 81. AI Security Control Framework

An Enterprise AI Security Governance Program should establish a structured control framework that translates governance requirements into specific security expectations.

The control framework should address:

* Preventive controls
* Detective controls
* Corrective controls
* Compensating controls
* Governance controls
* Technical controls
* Administrative controls

Controls should be selected according to AI risk rather than applied identically to every AI system.

---

### 82. AI Security Control Categories

A comprehensive control framework may include:

1. Governance controls
2. Risk management controls
3. Identity and access controls
4. Data security controls
5. Application security controls
6. Model security controls
7. Infrastructure security controls
8. Monitoring controls
9. Incident-response controls
10. Third-party controls
11. Resilience controls
12. Compliance controls

These categories should work together as a unified control environment.

---

### 83. Preventive AI Security Controls

Preventive controls reduce the likelihood of an AI security event.

Examples include:

* Authentication
* Authorization
* Encryption
* Network segmentation
