# 07.08 — AI API Security

## Part 1 — AI API Security Foundations, Architecture, and Threat Surface

### 1. AI API Security

AI API security is the protection of interfaces through which users, applications, AI agents, cloud services, and external systems interact with AI capabilities.

An AI API may expose:

* Model inference.
* Embeddings.
* Retrieval.
* Agents.
* Tools.
* Fine-tuning functions.
* Model management.
* Administrative operations.

Because APIs provide a direct interface to AI capabilities and data, they are a critical part of the AI security architecture.

---

### 2. Why AI APIs Require Specialized Security

Traditional API security controls remain necessary, but AI APIs introduce additional risks.

An AI API may accept:

```text
User
 ↓
Prompt
 ↓
Documents
 ↓
Parameters
 ↓
Tool Instructions
 ↓
Model Request
```

The input may influence model behavior, data retrieval, tool execution, and downstream systems.

Therefore, AI API security must address both **API security** and **AI-specific security risks**.

---

### 3. AI API Security Objectives

The primary objectives are:

1. **Confidentiality** — prevent unauthorized access to data and model capabilities.
2. **Integrity** — prevent unauthorized modification of requests, responses, configurations, and models.
3. **Availability** — prevent abuse that disrupts AI services.
4. **Authentication** — establish the identity of callers.
5. **Authorization** — determine what callers are permitted to do.
6. **Accountability** — maintain sufficient evidence of activity.
7. **Controlled AI behavior** — restrict unsafe or unauthorized AI operations.

---

### 4. AI API Attack Surface

The attack surface may include:

```text
                    AI API
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
    Endpoint         Input         Output
        │              │              │
   Authentication   Prompt        Response
        │              │              │
   Authorization    Files         Tool Calls
        │              │              │
   Rate Limiting    Metadata      External APIs
```

Each component can introduce a different security risk.

---

### 5. AI API Architecture

A secure architecture can use multiple enforcement layers:

```text
Client
  ↓
DNS / Network Protection
  ↓
WAF
  ↓
API Gateway
  ↓
Authentication
  ↓
Authorization
  ↓
AI Security Controls
  ↓
AI Application
  ↓
Model / RAG / Tools
```

The objective is to avoid placing all security responsibility directly inside the model or application.

---

### 6. API Gateway as a Security Control

An API gateway can provide centralized enforcement for:

* Authentication.
* Authorization.
* Rate limiting.
* Request validation.
* Logging.
* Routing.
* Threat filtering.
* API version management.

Example:

```text
Client
  ↓
API Gateway
 ├── Authenticate
 ├── Authorize
 ├── Validate
 ├── Rate Limit
 └── Log
       ↓
    AI Service
```

---

### 7. AI API Endpoint Types

AI environments may contain different endpoint categories.

#### Inference endpoints

Used to submit prompts or data and receive model responses.

#### Embedding endpoints

Used to generate vector representations.

#### Retrieval endpoints

Used to retrieve enterprise knowledge.

#### Agent endpoints

Used to invoke AI agents and their tools.

#### Administrative endpoints

Used to configure models, deployments, policies, or infrastructure.

Each endpoint type should have its own authorization requirements.

---

### 8. Separation of API Functions

Administrative functions should not be exposed through the same security model as ordinary inference.

For example:

```text
User
 ↓
Inference API
 ↓
AI Model
```

while:

```text
Administrator
 ↓
Management API
 ↓
AI Platform
```

Management APIs should have significantly stronger access controls.

---

### 9. Public and Private AI APIs

AI APIs may be:

* Public Internet-facing.
* Internal.
* Private cloud.
* Private network.
* Partner-facing.
* Hybrid.

The exposure level should be explicitly documented.

A sensitive enterprise AI API should not be publicly accessible unless there is a justified business requirement and appropriate security controls.

---

### 10. API Trust Boundary

The API boundary is a security boundary between the caller and the AI system.

```text
UNTRUSTED
   │
   │ API Request
   ↓
┌─────────────────┐
│   API Boundary  │
└─────────────────┘
   ↓
TRUSTED / CONTROLLED
   AI Environment
```

Everything crossing the boundary should be treated as potentially untrusted until validated.

---

### 11. API Authentication

Authentication establishes the identity of the caller.

Common mechanisms include:

* OAuth 2.0.
* OpenID Connect.
* API keys.
* Mutual TLS.
* Signed tokens.
* Workload identities.
* Cloud-native identity mechanisms.

The appropriate mechanism depends on the API's architecture and risk.

---

### 12. Authentication Is Not Authorization

These concepts should remain separate.

**Authentication:**

> Who are you?

**Authorization:**

> What are you allowed to do?

Example:

```text
User authenticated ✓
        ↓
Request analyzed
        ↓
Permission checked
        ↓
Action allowed / denied
```

A valid identity should not automatically receive access to every AI capability.

---

### 13. API Keys

API keys can identify applications or clients.

However, they should be:

* Stored securely.
* Rotated.
* Scoped where possible.
* Monitored.
* Revoked when compromised.

API keys should not be treated as an unrestricted substitute for proper identity and authorization.

---

### 14. API Key Leakage

Keys can be accidentally exposed through:

* Source code.
* Git repositories.
* Logs.
* Screenshots.
* Client-side applications.
* Configuration files.
* Chat messages.
* Container images.

AI API keys should therefore be managed through approved secrets-management mechanisms.

---

### 15. OAuth for AI APIs

OAuth can provide delegated access to APIs using access tokens.

Conceptually:

```text
User
 ↓
Identity Provider
 ↓
Access Token
 ↓
API Gateway
 ↓
AI API
```

Tokens should be appropriately scoped and have suitable lifetimes.

---

### 16. Token Scope

An API token should provide only the permissions required.

Example:

```text
Token A
 ✓ Invoke Model
 ✗ Modify Model
 ✗ Manage Users
 ✗ Delete Data
```

This limits the impact if the token is compromised.

---

### 17. Short-Lived Tokens

Short-lived access tokens reduce the period during which a compromised credential can be abused.

A simplified lifecycle is:

```text
Authenticate
 ↓
Issue Token
 ↓
Use Token
 ↓
Token Expires
 ↓
Reauthenticate / Refresh
```

Long-lived credentials should be avoided where practical.

---

### 18. Mutual TLS

Mutual TLS provides authentication of both communicating parties.

```text
Client Certificate
       ↕
   TLS Session
       ↕
Server Certificate
```

This can be particularly useful for:

* Internal service-to-service communication.
* High-trust partner APIs.
* Sensitive AI services.

---

### 19. Workload Identity

Internal AI services should preferably authenticate using workload identities rather than embedded static credentials.

```text
AI Application
      ↓
Workload Identity
      ↓
Authorized AI API
```

This supports stronger lifecycle and access management.

---

### 20. API Authorization

Authorization should evaluate:

* Caller.
* Application.
* Tenant.
* Resource.
* Action.
* Data classification.
* Environment.
* Risk.

For example:

```text
User = Employee
Application = HR Assistant
Action = Retrieve
Data = HR Records
Environment = Production
```

The authorization engine determines whether the request is permitted.

---

### 21. Role-Based API Authorization

RBAC can assign API permissions based on roles.

Example:

| Role             | Invoke Model | Retrieve Data | Manage Model |
| ---------------- | -----------: | ------------: | -----------: |
| Employee         |            ✓ |       Limited |            ✗ |
| AI Developer     |            ✓ |   Development |      Limited |
| AI Administrator |            ✓ |             ✓ |            ✓ |
| Auditor          |    Read-only |     Read-only |            ✗ |

Permissions should reflect actual job requirements.

---

### 22. Attribute-Based API Authorization

ABAC can evaluate contextual attributes.

For example:

```text
User Role = Finance
Data Class = Confidential
Application = Approved
Environment = Production
Action = Read
```

The policy engine can combine these attributes before granting access.

---

### 23. Tenant-Level Authorization

Multi-tenant AI APIs should enforce tenant isolation.

```text
Tenant A
 ↓
API
 ↓
Tenant A Data ✓
Tenant B Data ✗
```

The tenant boundary must be enforced server-side.

---

### 24. Object-Level Authorization

Authorization should apply to individual resources where required.

For example, a user may have permission to use an AI API but only access:

* Their own documents.
* Their department's records.
* Their assigned projects.

API-level authorization alone may not provide sufficient protection.

---

### 25. Function-Level Authorization

Different API operations should require different permissions.

Example:

```text
POST /inference
     ↓
Standard AI User

POST /models/deploy
     ↓
AI Administrator

DELETE /models
     ↓
Highly Privileged Role
```

A user authorized for inference should not automatically be authorized for administrative functions.

---

### 26. Object and Function Authorization Together

A mature AI API should evaluate both:

```text
WHO
 +
WHAT ACTION
 +
WHICH RESOURCE
 =
AUTHORIZATION DECISION
```

This reduces authorization bypass risks.

---

### 27. API Request Validation

API requests should be validated before reaching the AI application.

Validation may include:

* Schema.
* Data type.
* Size.
* Encoding.
* Required fields.
* Allowed parameters.
* File type.
* Content limits.

Invalid requests should be rejected early.

---

### 28. Input Size Limits

AI APIs should establish limits for:

* Prompt length.
* File size.
* Number of documents.
* Number of tool calls.
* Number of requests.
* Metadata size.

Without limits, attackers may exploit resource consumption.

---

### 29. Prompt Input as Untrusted Data

Prompts should be treated as untrusted input.

A user may intentionally or unintentionally submit:

* Malicious instructions.
* Sensitive information.
* Injection payloads.
* Extremely large content.
* Encoded attacks.

The API layer should therefore apply appropriate validation and security controls.

---

### 30. Prompt Injection

Prompt injection attempts to manipulate AI behavior by introducing instructions that conflict with the intended system behavior.

Example:

```text
Trusted System Instructions
          +
Untrusted User Content
          ↓
       AI Model
          ↓
Potentially Manipulated Behavior
```

API security should not assume that every instruction provided to the model is trustworthy.

---

### 31. Indirect Prompt Injection

Indirect prompt injection can originate from external content.

```text
External Document
       ↓
Retrieved by AI
       ↓
Injected Instructions
       ↓
Model
       ↓
Potentially Unsafe Action
```

This is particularly relevant for RAG systems and AI agents.

---

### 32. Input Trust Classification

AI API inputs can be classified as:

```text
Trusted
 ↓
Authenticated Application Metadata

Semi-Trusted
 ↓
Authenticated User Input

Untrusted
 ↓
External Documents / Websites / Files
```

The AI architecture should not treat these sources as equivalent.

---

### 33. Content Filtering

Content filtering may identify requests containing:

* Malicious instructions.
* Prohibited content.
* Sensitive information.
* Exploit attempts.
* Known attack patterns.

Filtering should be implemented as part of a broader security architecture rather than relied upon as the sole defense.

---

### 34. Prompt Injection Defense Layers

A layered approach can include:

```text
Input Validation
      ↓
Content Classification
      ↓
Prompt Isolation
      ↓
Tool Authorization
      ↓
Output Validation
      ↓
Monitoring
```

No single mechanism can completely eliminate prompt-injection risk.

---

### 35. File Upload Security

AI APIs may allow users to upload:

* PDFs.
* Images.
* Documents.
* Spreadsheets.
* Text files.
* Archives.

Uploads should be treated as untrusted.

Security controls can include:

* File-type validation.
* Size restrictions.
* Malware scanning.
* Content inspection.
* Sandboxing.
* Secure storage.

---

### 36. Malicious Document Risk

A document uploaded to an AI API may contain hidden or malicious instructions.

For example:

```text
User
 ↓
Upload PDF
 ↓
AI Parser
 ↓
Hidden Instruction
 ↓
Model
```

The content should therefore be treated as data rather than trusted instructions.

---

### 37. API File Storage

Uploaded files should be stored with:

* Appropriate encryption.
* Access controls.
* Retention policies.
* Malware scanning.
* Tenant isolation.

Temporary files should not remain indefinitely.

---

### 38. API Request Replay

Attackers may capture and replay legitimate requests.

Potential defenses include:

* Short-lived tokens.
* Nonces.
* Request timestamps.
* Request signatures.
* Idempotency controls.

The appropriate mechanism depends on the API protocol and business function.

---

### 39. API Message Integrity

Sensitive API requests may require integrity protection.

For example:

```text
Request
 ↓
Digital Signature / MAC
 ↓
API Gateway
 ↓
Verification
 ↓
Processing
```

This can help detect unauthorized modification during transmission or processing.

---

### 40. TLS for AI APIs

AI API traffic should use strong transport encryption.

```text
Client
  ═════ TLS ═════
  AI API
```

This protects data in transit against unauthorized interception.

---

### 41. Certificate Management

Certificate-based API security requires lifecycle management:

* Issuance.
* Deployment.
* Monitoring.
* Renewal.
* Revocation.
* Replacement.

Expired or compromised certificates can disrupt services or create security exposure.

---

### 42. API Response Security

Security should not stop at request processing.

Responses may contain:

* Sensitive enterprise data.
* Personal information.
* Internal instructions.
* Credentials.
* Confidential documents.

Responses should therefore be subject to appropriate authorization and output controls.

---

### 43. Sensitive Data Leakage Through Responses

A legitimate API request may still produce an unauthorized response if retrieval or authorization controls are weak.

Example:

```text
Authorized User
      ↓
AI API
      ↓
Overly Broad Retrieval
      ↓
Confidential Data
      ↓
API Response
```

Authorization must control what data the AI can access.

---

### 44. Output Filtering

Output controls may detect:

* Sensitive information.
* Credentials.
* Internal secrets.
* Regulated data.
* Unauthorized content.

Depending on the risk, the system may:

* Allow.
* Mask.
* Redact.
* Block.
* Escalate.

---

### 45. Response Size Limits

Response limits can help control:

* Resource consumption.
* Data leakage.
* Unexpected output.
* Excessive API costs.

They can also help reduce abuse of model endpoints.

---

### 46. API Rate Limiting

Rate limiting restricts how frequently a caller can make requests.

Example:

```text
User A
 ↓
100 requests/minute
 ↓
Limit exceeded
 ↓
Request rejected / delayed
```

Limits should reflect legitimate business requirements.

---

### 47. Rate Limiting Dimensions

Rate limits can be applied by:

* IP address.
* User.
* Application.
* API key.
* Tenant.
* Endpoint.
* Model.

Using multiple dimensions can provide stronger abuse protection.

---

### 48. Adaptive Rate Limiting

Higher-risk behavior can trigger stricter limits.

For example:

```text
Normal Behavior
 ↓
Standard Rate

Suspicious Behavior
 ↓
Reduced Rate

Confirmed Abuse
 ↓
Block
```

This can reduce disruption while preserving legitimate access.

---

### 49. API Quotas

Quotas define resource consumption over a longer period.

Examples:

* Requests per hour.
* Tokens per day.
* Documents per day.
* GPU minutes.
* Maximum concurrent sessions.

Quotas help manage both security and cost.

---

### 50. Token Consumption Controls

Large language model APIs may consume resources based on input and output tokens.

Security controls can establish:

```text
Maximum Input Tokens
+
Maximum Output Tokens
+
Maximum Requests
=
Controlled Consumption
```

This helps mitigate excessive resource use.

---

### 51. Denial-of-Service Protection

AI APIs should be protected against:

* Request floods.
* Large prompts.
* Large file uploads.
* Excessive concurrent requests.
* Repeated expensive operations.

Protection may involve:

* WAF.
* API gateway.
* Rate limiting.
* Quotas.
* Autoscaling controls.
* Circuit breakers.

---

### 52. Economic Denial of Service

AI APIs can be vulnerable to attacks that create excessive cloud costs.

```text
Attacker
 ↓
大量 API Requests
 ↓
GPU / Model Consumption
 ↓
Cloud Cost Increase
```

This is sometimes described as an economic denial-of-service risk.

Cost monitoring should therefore be part of AI API security.

---

### 53. API Abuse Detection

Security monitoring should identify patterns such as:

* Sudden request increases.
* Unusual token consumption.
* New geographic sources.
* New clients.
* Unusual model selection.
* Abnormal request timing.

---

### 54. API Logging

Important API events should be logged.

Potential fields include:

* Timestamp.
* Caller identity.
* Application identity.
* Tenant.
* Endpoint.
* Action.
* Model.
* Result.
* Status code.
* Request size.
* Response size.
* Security decision.

Sensitive payloads should not automatically be logged in full.

---

### 55. Secure API Logging

Logging the complete AI prompt or response can itself create a data-security risk.

A better approach may use:

```text
Metadata
+
Security-relevant indicators
+
Selective payload capture
```

Sensitive content should be handled according to data-classification requirements.

---

### 56. API Auditability

A mature AI API should allow the organization to answer:

> Who invoked the AI service, when, from which application, against which resource, and what security decision was made?

This supports:

* Incident response.
* Compliance.
* Forensics.
* Risk management.

---

### 57. API Monitoring

Monitoring should cover:

```text
Availability
Performance
Authentication
Authorization
Errors
Abuse
Data Movement
Security Events
```

Security and operational monitoring should work together.

---

### 58. API Security Telemetry

Useful telemetry may include:

* Authentication failures.
* Authorization denials.
* Rate-limit violations.
* Unusual endpoints.
* Large requests.
* Large responses.
* Tool invocations.
* External API calls.

These signals can feed security analytics.

---

### 59. API Security Alerts

Examples include:

```text
Multiple failed authentication attempts
          ↓
Security Alert

Large increase in token consumption
          ↓
Security Alert

New administrator API client
          ↓
Security Alert

AI API accessing unusual data source
          ↓
Security Alert
```

Alert severity should reflect business impact and confidence.

---

### 60. AI API Security Baseline

A production AI API should generally have a baseline covering:

```text
✓ Strong Authentication
✓ Least-Privilege Authorization
✓ TLS
✓ Input Validation
✓ Output Controls
✓ Rate Limiting
✓ Quotas
✓ Secure Secrets
✓ Logging
✓ Monitoring
✓ Data Protection
✓ Tenant Isolation
✓ Abuse Detection
✓ Incident Response
✓ Controlled API Administration
```

The exact requirements should be determined by the AI workload's risk, data sensitivity, exposure, and business criticality.


# 07.08 — AI API Security

## Part 2 — AI API Threats, Authentication, Authorization, Input Security, and Data Protection

### 61. AI API Threat Model

AI API security should begin by identifying the possible attack paths against the API ecosystem.

A practical threat model includes:

```text id="api-threat-model"
Client
  ↓
API Gateway
  ↓
Authentication
  ↓
Authorization
  ↓
AI Application
  ↓
Model / RAG / Tools
  ↓
Enterprise Resources
```

Each layer can become an attack target.

---

### 62. External Attacker

An external attacker may target:

* Public AI endpoints.
* Authentication mechanisms.
* API keys.
* API gateways.
* Input processing.
* File-upload functionality.
* Rate limits.
* Application vulnerabilities.

The objective may be unauthorized access, data theft, model abuse, service disruption, or excessive cloud consumption.

---

### 63. Compromised Internal User

An authenticated user should not automatically be considered trustworthy.

A compromised account could attempt:

```text id="compromised-user"
Compromised Account
       ↓
Legitimate API Access
       ↓
Unauthorized Data Retrieval
       ↓
Data Exfiltration
```

Authorization and behavioral monitoring should therefore continue after authentication.

---

### 64. Compromised Application

An application calling an AI API may itself become compromised.

For example:

```text id="compromised-app"
Compromised Application
       ↓
Valid API Credential
       ↓
AI API
       ↓
Sensitive Resources
```

Workload identity, scoped permissions, rate limits, and monitoring reduce the potential impact.

---

### 65. Malicious API Client

An attacker may create a legitimate-looking client specifically to abuse an AI service.

Controls should distinguish between:

* Approved applications.
* Approved users.
* Approved workloads.
* Unknown clients.

Client registration and application identity can help establish this distinction.

---

### 66. API Enumeration

Attackers may attempt to discover:

* API endpoints.
* API versions.
* Administrative functions.
* Model names.
* Debug endpoints.
* Internal services.

Unnecessary endpoints should not be exposed.

API documentation and management interfaces should also have appropriate access restrictions.

---

### 67. Shadow AI APIs

Employees or development teams may deploy AI APIs without security review.

This can create:

```text id="shadow-ai"
Unapproved AI API
       ↓
Unknown Data Flows
       ↓
Unknown Cloud Resources
       ↓
Unknown Security Risk
```

AI API discovery and inventory are therefore important governance controls.

---

### 68. API Inventory

Organizations should maintain an inventory containing:

* API name.
* Owner.
* Business purpose.
* Environment.
* Endpoint.
* Data classification.
* Authentication mechanism.
* Authorization model.
* Model used.
* External dependencies.
* Security assessment status.

---

### 69. API Ownership

Every production AI API should have a clearly identified owner.

Ownership should cover:

* Security.
* Availability.
* Data handling.
* Change management.
* Incident response.
* Lifecycle management.

An API without an accountable owner creates governance gaps.

---

### 70. API Classification

AI APIs can be classified according to exposure and sensitivity.

Example:

| API Type           | Exposure   | Risk      |
| ------------------ | ---------- | --------- |
| Internal chatbot   | Internal   | Medium    |
| Customer AI API    | Internet   | High      |
| Internal model API | Private    | High      |
| Public AI API      | Internet   | Very High |
| Administrative API | Restricted | Critical  |

Classification should drive security requirements.

---

### 71. Authentication Threats

Authentication attacks may include:

* Credential theft.
* API-key theft.
* Token theft.
* Credential stuffing.
* Brute force.
* Session hijacking.
* Token replay.
* Weak client authentication.

Authentication controls should be proportional to API risk.

---

### 72. Strong Authentication

High-value AI APIs should use strong authentication mechanisms.

Depending on architecture, this may include:

* MFA for human users.
* OAuth/OIDC.
* Workload identity.
* mTLS.
* Signed requests.
* Short-lived credentials.

Static shared credentials should be minimized.

---

### 73. Multi-Factor Authentication

MFA adds another verification factor for human access.

```text id="mfa-flow"
Password
   +
Second Factor
   ↓
Identity Verification
   ↓
AI API Access
```

MFA is particularly important for administrative access.

---

### 74. Conditional Access

Access decisions can consider contextual information such as:

* User identity.
* Device status.
* Location.
* Network.
* Application.
* Risk level.

For example:

```text id="conditional-access"
User
 +
Managed Device
 +
Approved Application
 +
Normal Risk
      ↓
    Allow
```

---

### 75. Workload Authentication

Machine-to-machine AI API calls should use workload identities where supported.

```text id="workload-auth"
Application A
      ↓
Workload Identity
      ↓
Authentication
      ↓
AI API
```

This is preferable to embedding permanent credentials inside application code.

---

### 76. Service Account Security

AI API service accounts should:

* Have dedicated identities.
* Use minimum required permissions.
* Avoid interactive login where unnecessary.
* Be monitored.
* Be periodically reviewed.
* Be disabled when no longer required.

---

### 77. Credential Rotation

Credentials should have controlled rotation processes.

```text id="credential-rotation"
Credential Created
       ↓
Active
       ↓
Rotation Due
       ↓
New Credential
       ↓
Validation
       ↓
Old Credential Revoked
```

Rotation should be automated where practical.

---

### 78. Emergency Credential Revocation

Organizations should be able to quickly revoke compromised credentials.

The response should identify:

* Which credential was compromised.
* Which APIs it could access.
* Which resources it could reach.
* Whether it was used maliciously.

---

### 79. Token Replay

If an attacker obtains an access token, they may attempt to reuse it.

Risk reduction mechanisms can include:

* Short token lifetimes.
* Sender-constrained tokens where supported.
* Secure token storage.
* Revocation mechanisms.
* Anomaly detection.

---

### 80. Authorization Architecture

A secure authorization architecture separates policy decisions from AI model behavior.

```text id="authorization-architecture"
API Request
     ↓
Identity
     ↓
Policy Decision
     ↓
Authorization
     ↓
AI Application
     ↓
Resource
```

The model should not independently decide whether a user has access to enterprise resources.

---

### 81. Least-Privilege API Access

Each API client should receive only the permissions required.

For example:

```text id="least-privilege"
Client A
 ✓ Generate Response
 ✓ Read Approved Dataset
 ✗ Modify Model
 ✗ Manage IAM
 ✗ Delete Data
```

This limits the blast radius of credential compromise.

---

### 82. Privilege Separation

AI API capabilities should be separated according to risk.

```text id="privilege-separation"
Inference
   ↓
Standard Privilege

Data Retrieval
   ↓
Elevated Privilege

Tool Execution
   ↓
Higher Privilege

Model Administration
   ↓
Privileged Access
```

Higher-risk functions should require stronger controls.

---

### 83. Administrative API Isolation

Administrative APIs should preferably be separated from user-facing inference APIs.

```text id="admin-isolation"
User
 ↓
Inference API

Administrator
 ↓
Management API
```

This reduces the risk that a compromise of a public endpoint becomes a management-plane compromise.

---

### 84. Management Plane Security

The management plane may include:

* Model configuration.
* Deployment.
* API configuration.
* User management.
* Policy management.
* Key management.

Access should be restricted to authorized administrators.

---

### 85. Data-Level Authorization

API authorization should account for the data being requested.

Example:

```text id="data-auth"
User
 ↓
AI API
 ↓
Data Authorization
 ↓
Confidential Dataset
```

Being authorized to use the AI service does not necessarily mean being authorized to access every dataset.

---

### 86. RAG Authorization

RAG systems require careful authorization.

The secure flow is:

```text id="rag-auth"
User
 ↓
Identity
 ↓
Authorization
 ↓
Permitted Documents
 ↓
Retrieval
 ↓
Model
```

The vector database should not simply return every semantically relevant document.

---

### 87. Vector Database Security

Vector databases may contain sensitive enterprise knowledge.

Security controls should address:

* Authentication.
* Authorization.
* Tenant isolation.
* Encryption.
* Network restrictions.
* Logging.
* Backup protection.

---

### 88. Vector Search Authorization

Semantic similarity is not an authorization mechanism.

A document can be highly relevant to a query while still being inaccessible to the user.

Therefore:

> **Relevance must never override authorization.**

### 89. Tenant Isolation

Multi-tenant AI APIs should enforce strict separation.

```text id="tenant-isolation"
Tenant A
   ↓
Tenant A Context
   ↓
Tenant A Model/Data

Tenant B
   ↓
Tenant B Context
   ↓
Tenant B Model/Data
```

Cross-tenant access should be explicitly prevented.

---

### 90. Tenant Context Validation

Tenant identifiers supplied by clients should not be blindly trusted.

The system should derive or validate tenant context from trusted identity information.

```text id="tenant-validation"
Authenticated Identity
       ↓
Trusted Tenant Context
       ↓
Authorization
       ↓
Tenant Resource
```

### 91. Broken Object-Level Authorization

A common API weakness occurs when an attacker changes an object identifier.

Example:

```text id="bola"
GET /documents/1001
```

changed to:

```text id="bolb"
GET /documents/1002
```

The server must verify whether the caller is authorized to access document 1002.

---

### 92. Broken Function-Level Authorization

An attacker may attempt to call an administrative endpoint using a standard user identity.

Example:

```text id="bflfa"
Standard User
     ↓
POST /admin/model/deploy
```

The API must enforce function-level authorization independently of the client's ability to reach the endpoint.

---

### 93. API Input Validation

AI APIs should validate all externally supplied values.

Validation can include:

* Data type.
* Format.
* Length.
* Allowed values.
* Encoding.
* File type.
* Parameter ranges.

Validation should occur before the request reaches sensitive processing functions.

### 94. Schema Validation

Structured AI API requests should conform to defined schemas.

Example:

```text id="schema-validation"

  prompt: valid_string,
  temperature: allowed_range,
  max_tokens: allowed_range
}
```

Unexpected or invalid parameters should be rejected.

### 95. Parameter Tampering

Attackers may manipulate API parameters to bypass restrictions.

Examples:

* Changing model identifiers.
* Increasing token limits.
* Modifying tenant IDs.
* Changing access scopes.
* Selecting administrative functions.

Server-side validation is required because client-side controls can be bypassed.

```text id="model-selection"
 ↓

 └── Admin Model ✗
```

* Temperature range.
* Top-p range.
* Maximum context.
* Maximum tool calls.

### 98. System Prompt Protection

