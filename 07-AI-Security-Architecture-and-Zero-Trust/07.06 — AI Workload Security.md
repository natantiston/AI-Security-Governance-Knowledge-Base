# 07.06 — AI Workload Security

## Part 1 — Foundations and Core Security Concepts

### 1. AI Workload Security

**AI workload security** is the practice of protecting the computing workloads that execute, train, fine-tune, evaluate, orchestrate, or otherwise process AI models and AI-related data.

An AI workload can include:

* Model inference.
* Model training.
* Fine-tuning.
* Embedding generation.
* RAG processing.
* AI agent execution.
* Data preprocessing.
* Model evaluation.
* Batch processing.
* AI-assisted code execution.

The objective is to ensure that every AI workload is:

```text
Authorized
    ↓
Authenticated
    ↓
Isolated
    ↓
Hardened
    ↓
Monitored
    ↓
Controlled
    ↓
Recoverable
```

---

### 2. AI Workload vs. AI Infrastructure

AI infrastructure and AI workloads are related but should not be treated as the same security object.

**AI infrastructure** provides the environment in which workloads execute.

Examples:

* Servers.
* GPUs.
* CPUs.
* Kubernetes clusters.
* Containers.
* Networks.
* Storage.
* Cloud platforms.
* Operating systems.

**AI workloads** are the actual applications, services, jobs, and processes executing on that infrastructure.

For example:

```text
AI Infrastructure
       ↓
Compute
       ↓
Container
       ↓
AI Workload
       ↓
Model + Code + Data
```

A compromised workload should not automatically result in compromise of the underlying infrastructure.

---

### 3. Why AI Workload Security Matters

Traditional application workloads already require security controls, but AI workloads introduce additional dependencies.

An AI workload may simultaneously interact with:

```text
                 AI Workload
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
     Model           Data          APIs
       ↓              ↓              ↓
     GPU           Storage        Services
       ↓              ↓              ↓
   Runtime        Databases       Identity
```

This creates multiple potential attack paths.

A compromised AI workload could potentially become a bridge between otherwise separated systems.

---

### 4. AI Workload Security Objectives

The primary security objectives are:

#### Confidentiality

Prevent unauthorized access to:

* Training data.
* Prompts.
* Retrieved documents.
* Model artifacts.
* Credentials.
* Application data.
* Internal services.

#### Integrity

Prevent unauthorized modification of:

* Model files.
* Application code.
* Configuration.
* Training datasets.
* Dependencies.
* Deployment artifacts.

#### Availability

Ensure AI workloads remain:

* Available.
* Performant.
* Resilient.
* Recoverable.

#### Accountability

Ensure activities can be attributed to:

* Users.
* Administrators.
* Applications.
* Workloads.
* Service identities.
* Automated processes.

---

### 5. AI Workload Lifecycle

Security must apply across the entire workload lifecycle.

```text
Design
   ↓
Develop
   ↓
Build
   ↓
Test
   ↓
Approve
   ↓
Deploy
   ↓
Operate
   ↓
Monitor
   ↓
Update
   ↓
Retire
```

Security controls applied only during deployment are insufficient because vulnerabilities can be introduced before deployment and configuration can drift after deployment.

---

### 6. AI Workload Categories

AI workloads can be classified according to their purpose.

| Workload         | Primary Function                          |
| ---------------- | ----------------------------------------- |
| Training         | Build a model                             |
| Fine-tuning      | Adapt a base model                        |
| Inference        | Generate predictions or responses         |
| Embedding        | Convert content into vectors              |
| RAG              | Retrieve information for model processing |
| Agent            | Perform tasks using tools                 |
| Evaluation       | Test model behavior                       |
| Data Processing  | Prepare AI data                           |
| Code Execution   | Execute generated or submitted code       |
| Batch Processing | Process large AI jobs                     |

Different workload types require different security controls.

---

### 7. Training Workloads

Training workloads process datasets to create or modify models.

```text
Training Dataset
       ↓
Preprocessing
       ↓
Training Job
       ↓
GPU / Compute
       ↓
Model Artifact
```

Security concerns include:

* Unauthorized dataset access.
* Dataset poisoning.
* Dataset modification.
* Malicious dependencies.
* Credential exposure.
* GPU resource abuse.
* Model artifact tampering.

Training infrastructure can therefore become a high-value target.

---

### 8. Fine-Tuning Workloads

Fine-tuning combines a base model with organization-specific data.

```text
Base Model
     +
Enterprise Dataset
     ↓
Fine-Tuning
     ↓
Customized Model
```

The organization must protect both the base model and the proprietary data used during fine-tuning.

Fine-tuning workloads may therefore require stronger controls than ordinary development workloads.

---

### 9. Inference Workloads

An inference workload executes a model against incoming requests.

```text
User
 ↓
Application
 ↓
Inference Service
 ↓
Model
 ↓
Response
```

Potential security risks include:

* Unauthorized access.
* Excessive requests.
* Model extraction.
* Sensitive input exposure.
* Sensitive output exposure.
* Resource exhaustion.
* Abuse of the inference API.

---

### 10. RAG Workloads

A RAG workload commonly combines an AI model with enterprise information.

```text
User
 ↓
AI Application
 ↓
Retriever
 ↓
Vector Database
 ↓
Enterprise Documents
 ↓
Retrieved Context
 ↓
Model
 ↓
Response
```

Security must therefore protect:

* The AI application.
* The model.
* The vector database.
* The source documents.
* Retrieval mechanisms.
* Access-control logic.

Protecting only the model is insufficient.

---

### 11. AI Agent Workloads

AI agents can introduce additional workload risk because they may perform actions.

For example:

```text
AI Agent
 ├──→ Database
 ├──→ Email
 ├──→ File System
 ├──→ API
 ├──→ Cloud Service
 └──→ Enterprise Application
```

The security concern is not only what information the agent can access, but **what actions the agent can perform**.

Agent workloads should therefore have narrowly defined permissions.

---

### 12. AI Code Execution Workloads

Some AI applications execute code generated by an AI model or supplied by a user.

A safer architecture is:

```text
AI Model
    ↓
Generated Code
    ↓
Security Validation
    ↓
Sandbox
    ↓
Restricted Runtime
    ↓
Execution Result
```

Generated code should not execute directly on the host operating system or with the privileges of the main AI application.

---

### 13. AI Workload Trust Levels

Organizations can classify workloads according to their risk.

Example:

| Trust Level | Example            | Typical Security                     |
| ----------- | ------------------ | ------------------------------------ |
| Low         | Experimental AI    | Development controls                 |
| Moderate    | Internal assistant | Enterprise controls                  |
| High        | Sensitive RAG      | Restricted production                |
| Critical    | Regulated AI       | Dedicated/high-assurance environment |

Trust classification should consider data sensitivity, business criticality, external exposure, and workload privileges.

---

### 14. Workload Identity

Each production AI workload should have a distinguishable identity where technically feasible.

Instead of:

```text
AI Workload
     ↓
Shared Administrator Account
```

use:

```text
AI Workload
     ↓
Dedicated Workload Identity
     ↓
Authorized Resources
```

Workload identity improves:

* Authentication.
* Authorization.
* Accountability.
* Monitoring.
* Incident response.

---

### 15. Workload Identity Attributes

Useful workload identity attributes may include:

* Workload name.
* Application.
* Environment.
* Owner.
* Service account.
* Namespace.
* Deployment.
* Version.
* Risk classification.

Example:

```text
Workload:
CustomerSupportAI

Environment:
Production

Owner:
Customer Operations

Classification:
Confidential

Identity:
customer-support-ai-prod
```

This creates a clear relationship between the workload and its responsible owner.

---

### 16. Least Privilege

AI workloads should receive only the permissions required for their defined function.

For example, a model-serving workload may need:

```text
READ  → Model Registry
READ  → Model Artifact
READ  → Configuration
WRITE → Application Logs
```

It normally should not need:

```text
ADMIN → Cloud Account
WRITE → IAM
DELETE → Production Database
ADMIN → Kubernetes Cluster
```

Least privilege limits the impact of workload compromise.

---

### 17. Workload Privilege Escalation

An attacker may attempt to move from a compromised workload toward higher privileges.

```text
Compromised AI Workload
        ↓
Credential Discovery
        ↓
Privilege Escalation
        ↓
Host Access
        ↓
Cluster Access
        ↓
Cloud Control Plane
```

Security architecture should interrupt this chain at multiple points.

---

### 18. Workload Isolation

Workload isolation prevents one AI workload from freely interacting with another.

Isolation mechanisms can include:

* Containers.
* Kubernetes namespaces.
* Network policies.
* Virtual machines.
* Dedicated hosts.
* Dedicated GPU nodes.
* Separate clusters.
* Separate cloud accounts or subscriptions.

The required isolation level should be proportional to the workload's risk.

---

### 19. Container Isolation

A containerized AI environment might contain:

```text
Host
│
├── AI Workload A
├── AI Workload B
└── AI Workload C
```

Containers should be reinforced with controls such as:

* Non-root execution.
* Restricted Linux capabilities.
* Read-only file systems where practical.
* Resource limits.
* Network policies.
* Approved images.
* Runtime monitoring.

Containerization alone should not be treated as complete isolation.

---

### 20. Virtual Machine Isolation

Higher-risk workloads may require stronger boundaries.

```text
Physical / Cloud Host
        │
   ┌────┴────┐
   ↓         ↓
 VM-A       VM-B
   │         │
 AI-A       AI-B
```

Virtual machines can provide a stronger separation boundary than ordinary process isolation.

The architecture should still address vulnerabilities in the hypervisor, host, operating system, and management plane.

---

### 21. Dedicated GPU Workloads

Sensitive AI workloads may require dedicated GPU resources.

```text
Sensitive AI Workload
        ↓
Dedicated Compute
        ↓
Dedicated GPU
```

This can reduce certain risks associated with shared compute resources and simplify isolation requirements.

Dedicated infrastructure is not automatically secure, however. Identity, network, operating-system, runtime, and application controls remain necessary.

---

### 22. GPU Security

Because AI workloads frequently depend on GPUs, GPU security should form part of the workload threat model.

Potential concerns include:

* Unauthorized GPU access.
* Resource exhaustion.
* Vulnerable GPU drivers.
* Vulnerable firmware.
* Insecure management interfaces.
* Cross-workload exposure.
* Malicious workloads.

GPU components should therefore be included in asset inventories and vulnerability-management processes.

---

### 23. Resource Quotas

AI workloads should have appropriate resource limits.

Example:

```text
CPU:        8 cores
Memory:     32 GB
GPU:        1
Storage:    500 GB
Requests:   100/minute
```

Resource controls help prevent:

* Denial-of-service conditions.
* Accidental resource exhaustion.
* Malicious resource consumption.
* Uncontrolled cloud expenditure.

---

### 24. Workload Scheduling

Workload scheduling determines which workloads can execute on which resources.

```text
Workload Request
       ↓
Identity Verification
       ↓
Policy Evaluation
       ↓
Resource Selection
       ↓
Execution
```

Scheduling policies can consider:

* Workload identity.
* Environment.
* Sensitivity.
* Resource requirements.
* Business criticality.
* Approved infrastructure.

---

### 25. Environment Separation

AI workloads should normally be separated across:

```text
Development
      ↓
Testing
      ↓
Staging
      ↓
Production
```

Production credentials, sensitive data, and privileged infrastructure should not unnecessarily be accessible from development environments.

---

### 26. Development-to-Production Promotion

A secure promotion process may look like:

```text
Development
      ↓
Code Review
      ↓
Security Scanning
      ↓
Testing
      ↓
Approval
      ↓
Artifact Signing
      ↓
Production Deployment
```

The objective is to ensure that production workloads originate from controlled and validated artifacts.

---

### 27. Workload Artifact Integrity

AI workload artifacts can include:

* Container images.
* Model files.
* Python packages.
* Application code.
* Configuration.
* Deployment manifests.
* Infrastructure definitions.

A controlled artifact lifecycle can be:

```text
Build
 ↓
Scan
 ↓
Approve
 ↓
Sign
 ↓
Store
 ↓
Verify
 ↓
Deploy
```

Artifact integrity helps prevent unauthorized or malicious components from entering production.

---

### 28. Container Image Security

AI containers can contain large numbers of dependencies:

```text
Operating System
      ↓
System Libraries
      ↓
Python
      ↓
AI Framework
      ↓
GPU Libraries
      ↓
Application Dependencies
      ↓
AI Application
```

Every layer may contain vulnerabilities.

Container images should therefore be scanned, maintained, and sourced from approved registries.

---

### 29. Software Supply Chain Security

AI workload security includes the entire software dependency chain.

Potential controls include:

* Approved repositories.
* Dependency pinning.
* Vulnerability scanning.
* Package verification.
* Image signing.
* SBOM generation.
* Provenance tracking.
* Controlled build environments.

A secure workload cannot be established by securing only the final application code.

---

### 30. AI Framework Security

AI workloads may depend on frameworks and libraries such as:

* PyTorch.
* TensorFlow.
* JAX.
* Transformers.
* CUDA libraries.
* Python packages.

These dependencies should be managed through approved versions and vulnerability-management processes.

A vulnerable AI framework can undermine otherwise strong workload security.

---

### 31. Software Bill of Materials

An SBOM provides visibility into the components contained within an AI workload.

Example:

```text
AI Workload
│
├── Python
├── AI Framework
├── Transformer Library
├── CUDA Libraries
├── Operating System Packages
└── Application Dependencies
```

SBOM information supports:

* Vulnerability identification.
* Supply-chain risk management.
* Incident response.
* Regulatory evidence.
* Dependency tracking.

---

### 32. Workload Configuration Security

AI workload configuration may define:

* Model endpoints.
* Database connections.
* API endpoints.
* Logging.
* Network settings.
* Resource limits.
* Runtime parameters.

Configuration should be controlled through approved mechanisms and changes should be auditable.

---

### 33. Secrets in AI Workloads

AI workloads frequently require credentials such as:

* API keys.
* Database credentials.
* Service tokens.
* Certificates.
* Private keys.
* Cloud credentials.

These secrets should not be hard-coded into:

```text
Source Code
Container Images
Git Repositories
Infrastructure Templates
Application Logs
```

Instead, workloads should retrieve secrets through approved secrets-management mechanisms.

---

### 34. Workload Network Security

AI workloads should have controlled network communication.

A secure pattern is:

```text
Inbound
   ↓
Approved Gateway
   ↓
AI Workload
   ↓
Approved Dependencies
   ↓
Controlled Egress
```

Unnecessary network paths should be removed.

---

### 35. Default-Deny Networking

Where practical, network policy should begin with:

```text
DEFAULT
   ↓
DENY
   ↓
Explicitly Allow Required Traffic
```

For example:

```text
AI Workload
   ├──→ Model Registry ✓
   ├──→ Vector Database ✓
   ├──→ Logging Service ✓
   └──→ Unknown Internet Destination ✗
```

This limits lateral movement and unauthorized communication.

---

### 36. Workload Egress Security

Outbound connectivity deserves particular attention because a compromised workload could attempt to exfiltrate information.

```text
Compromised Workload
        ↓
Sensitive Data
        ↓
External Connection
        ↓
Attacker Infrastructure
```

Egress controls can restrict:

* Destinations.
* Domains.
* Ports.
* Protocols.
* Data volume.
* Network paths.

---

### 37. Workload Ingress Security

Inbound traffic should also be controlled.

Preferred architecture:

```text
Internet
   ↓
WAF / API Gateway
   ↓
Security Controls
   ↓
AI Service
```

rather than directly exposing an AI workload:

```text
Internet
   ↓
AI Container
```

The gateway can provide centralized authentication, authorization, rate limiting, inspection, and logging.

---

### 38. Workload-to-Workload Communication

Internal AI services should authenticate each other.

```text
AI Application
      ↓
Authenticated Request
      ↓
Policy Evaluation
      ↓
Model Service
```

Being located inside the same network should not automatically establish trust.

---

### 39. Service Accounts

AI workload service accounts should generally be:

* Unique.
* Purpose-specific.
* Least privileged.
* Monitored.
* Revocable.

A single highly privileged service account should not be reused across unrelated workloads.

---

### 40. Privileged AI Workloads

Privileged workloads should be exceptional and justified.

Examples of high-risk privileges include:

```text
Root
Host Network
Host File System
Cluster Administrator
Cloud Administrator
IAM Administrator
```

Where privileged execution is unavoidable, additional controls should address:

* Approval.
* Monitoring.
* Duration.
* Scope.
* Credential protection.
* Auditability.

---

### 41. Rootless Workloads

Where technically feasible, AI containers should execute as non-root users.

```text
Container
   ↓
Non-Root User
   ↓
Restricted Capabilities
   ↓
Limited System Access
```

This reduces the potential impact of application-level compromise.

---

### 42. Runtime Security

Runtime security focuses on what the workload actually does while executing.

Potential indicators include:

* Unexpected processes.
* Unexpected file access.
* Privilege escalation.
* Unexpected network connections.
* Credential access.
* Container escape attempts.
* Unexpected system calls.

Runtime security complements vulnerability scanning because a workload may be technically patched yet still behave maliciously.

---

### 43. Runtime Behavioral Baseline

A normal AI workload may have predictable behavior.

For example:

```text
Expected
   ├── Read Model
   ├── Query Vector DB
   ├── Write Logs
   ├── Generate Metrics
   └── Process API Requests
```

Unexpected activity such as:

```text
Shell Spawn
    +
Credential File Access
    +
External Network Connection
```

may indicate compromise.

---

### 44. Workload Logging

Important workload events should be captured, including:

* Startup.
* Shutdown.
* Authentication.
* Authorization.
* Deployment.
* Administrative actions.
* Model loading.
* Configuration changes.
* Security events.
* Tool execution.

Logs should be protected against unauthorized alteration and retained according to organizational requirements.

---

### 45. Workload Monitoring

AI workload monitoring should cover both operational and security conditions.

**Operational monitoring:**

* CPU utilization.
* GPU utilization.
* Memory.
* Latency.
* Error rates.
* Queue depth.

**Security monitoring:**

* Authentication failures.
* Privilege changes.
* Unexpected connections.
* Unauthorized file access.
* Configuration changes.
* Abnormal resource consumption.

---

### 46. AI Workload Data Access

A workload should access only the data required to perform its defined function.

For example:

```text
Customer Support AI
        ↓
Customer Support Knowledge Base ✓
        ↓
Payroll Database ✗
        ↓
Executive HR Files ✗
```

Data access should be enforced through technical controls rather than relying exclusively on application instructions.

---

### 47. Workload-to-Data Authorization

A stronger architecture evaluates:

```text
Workload Identity
       ↓
Data Authorization Policy
       ↓
Data Classification
       ↓
Access Decision
       ↓
Data
```

This allows the organization to consider both **who or what is requesting access** and **how sensitive the requested data is**.

---

### 48. Data Minimization

AI workloads should process only the information necessary for their intended purpose.

Instead of:

```text
Entire Enterprise Database
          ↓
AI Workload
```

prefer:

```text
Required Dataset
      ↓
AI Workload
```

Data minimization reduces the potential impact of workload compromise.

---

### 49. Temporary AI Workload Data

AI workloads may create temporary information during processing.

```text
Prompt
  ↓
Intermediate Data
  ↓
Embedding
  ↓
Model Processing
  ↓
Output
```

Temporary information should have appropriate:

* Access controls.
* Retention periods.
* Encryption.
* Deletion procedures.

This is particularly important when temporary data contains confidential or regulated information.

---

### 50. AI Workload Security Baseline

A production AI workload baseline can include:

```text
✓ Approved Workload Image
✓ Vulnerability Scanning
✓ Non-Root Execution
✓ Dedicated Workload Identity
✓ Least Privilege
✓ Network Segmentation
✓ Egress Restrictions
✓ Resource Quotas
✓ Secrets Management
✓ Encryption
✓ Logging
✓ Runtime Monitoring
✓ Backup / Recovery
✓ Incident Response
✓ Asset Inventory
✓ Defined Owner
```

The baseline should be risk-based, with stronger requirements for workloads handling sensitive data, possessing elevated privileges, or supporting critical business processes.

# 07.06 — AI Workload Security

## Part 2 — AI Workload Threats, Attack Paths, and Security Controls

### 51. AI Workload Threat Model

An AI workload threat model identifies what can go wrong, what assets could be affected, how an attacker could exploit the workload, and what controls can reduce the risk.

A simplified model is:

```text
Threat Actor
     ↓
Attack Vector
     ↓
AI Workload
     ↓
Compromised Component
     ↓
Privilege / Data / Network Access
     ↓
Business Impact
```

The threat model should consider both traditional infrastructure threats and AI-specific threats.

---

### 52. AI Workload Attack Surface

The attack surface can include:

```text
AI Workload
│
├── Application Code
├── Model
├── Dependencies
├── Container
├── Operating System
├── GPU
├── Storage
├── Network
├── APIs
├── Credentials
├── Data
└── Runtime
```

Every component represents a potential entry point, trust boundary, or escalation path.

---

### 53. Workload Compromise

A workload can be compromised through:

* Vulnerable application code.
* Vulnerable dependencies.
* Malicious packages.
* Stolen credentials.
* Exploited APIs.
* Container vulnerabilities.
* Operating-system vulnerabilities.
* Misconfiguration.
* Supply-chain attacks.

The security architecture should assume compromise is possible and limit the resulting blast radius.

---

### 54. Initial Access to an AI Workload

A simplified attack path may be:

```text
External Attacker
      ↓
Exposed API
      ↓
Application Vulnerability
      ↓
AI Workload
```

Another path may originate from an internal system:

```text
Compromised Enterprise System
          ↓
Internal Network
          ↓
AI Service
```

Zero Trust principles require authorization at each meaningful access point rather than assuming internal traffic is trustworthy.

---

### 55. Container Escape

An attacker who compromises an AI container may attempt to escape its isolation boundary.

```text
Compromised Container
        ↓
Container Escape
        ↓
Host Access
        ↓
Other Workloads
```

Controls can include:

* Minimal container privileges.
* Non-root execution.
* Restricted capabilities.
* Hardened runtimes.
* Host patching.
* Runtime monitoring.
* Appropriate sandboxing.

---

### 56. Host Compromise

If the underlying host is compromised:

```text
Host Compromise
      ↓
AI Workload Access
      ↓
Model / Data / Credentials
```

Therefore, workload security cannot be separated completely from host security.

Hosts supporting sensitive AI workloads should have appropriate:

* Hardening.
* Patch management.
* Access controls.
* Monitoring.
* Endpoint protection.

---

### 57. Lateral Movement

A compromised AI workload may attempt to reach other systems.

```text
AI Workload
     ↓
Internal Network
     ├──→ Database
     ├──→ Storage
     ├──→ API
     ├──→ Kubernetes
     └──→ Other Workloads
```

Network segmentation and workload-level authorization should prevent unnecessary communication.

---

### 58. Blast Radius

**Blast radius** represents the scope of damage following compromise.

Poor architecture:

```text
Compromised AI Workload
        ↓
Broad Network Access
        ↓
Multiple Enterprise Systems
```

Better architecture:

```text
Compromised AI Workload
        ↓
Restricted Identity
        ↓
Restricted Network
        ↓
Limited Data
        ↓
Contained Impact
```

Reducing blast radius is one of the most important workload-security objectives.

---

### 59. Credential Theft

AI workloads may contain or access valuable credentials.

An attacker could attempt:

```text
Compromise Workload
       ↓
Credential Discovery
       ↓
Steal Token
       ↓
Impersonate Workload
       ↓
Access Protected Resource
```

Credentials should therefore be:

* Short-lived where practical.
* Scope-limited.
* Stored securely.
* Rotated.
* Monitored.

---

### 60. Credential Exposure Through Logs

Credentials can accidentally appear in:

* Application logs.
* Debug logs.
* Error messages.
* Stack traces.
* Monitoring systems.
* AI prompts.
* AI responses.

Example:

```text
API Request
   ↓
Error
   ↓
Debug Log
   ↓
API Key Exposed
```

Sensitive values should be masked or prevented from entering logs.

---

### 61. Token Theft

AI workloads may use bearer tokens or service tokens.

If a token is stolen:

```text
Legitimate Workload
       ↓
Token
       ↓
Attacker Obtains Token
       ↓
Unauthorized Resource Access
```

Controls should include:

* Short token lifetimes.
* Audience restrictions.
* Scope restrictions.
* Token rotation.
* Monitoring.
* Revocation.

---

### 62. Excessive Workload Permissions

A workload with excessive privileges increases the consequences of compromise.

For example:

```text
AI Application
     ↓
Cloud Administrator
```

is significantly riskier than:

```text
AI Application
     ↓
Read-Only Model Access
```

Permissions should be designed around actual business requirements.

---

### 63. Privilege Escalation

Attackers may attempt to move from:

```text
Low Privilege
     ↓
Higher Privilege
     ↓
Administrator
```

Potential escalation paths include:

* Weak service-account permissions.
* Vulnerable containers.
* Misconfigured Kubernetes roles.
* Host vulnerabilities.
* Cloud IAM misconfiguration.
* Exposed credentials.

Privilege boundaries should therefore be explicitly designed and tested.

---

### 64. Kubernetes Workload Risks

AI workloads deployed on Kubernetes may inherit risks from:

* Kubernetes API access.
* Service accounts.
* RBAC configuration.
* Secrets.
* Namespaces.
* Network policies.
* Admission controls.
* Container privileges.

A compromised pod should not automatically provide access to the Kubernetes control plane.

---

### 65. Kubernetes Service Account Security

A workload should use a dedicated service account where appropriate.

```text
AI Workload
     ↓
Dedicated Service Account
     ↓
Restricted RBAC
```

Avoid unnecessary permissions such as:

```text
cluster-admin
```

for ordinary AI workloads.

---

### 66. Namespace Isolation

Namespaces can provide organizational and security boundaries.

```text
Cluster
│
├── namespace-ai-prod
│      ├── Model Service
│      └── RAG Service
│
├── namespace-ai-test
│      └── Test Workload
│
└── namespace-monitoring
       └── Monitoring
```

## Part 3 — Workload Hardening, Runtime Protection, Monitoring, and Governance

### 106. AI Workload Hardening

AI workload hardening is the process of reducing unnecessary functionality, privileges, dependencies, interfaces, and attack paths before the workload enters production.

A hardened workload should expose only what is required:

```text
Required Functionality
        ↓
Required Components
        ↓
Required Permissions
        ↓
Required Network Access
        ↓
Required Data Access
```

Everything unnecessary should be removed, disabled, or restricted.

---

### 107. Workload Hardening Baseline

An organization should establish a standard security baseline for AI workloads.

A baseline may address:

* Operating system configuration.
* Container configuration.
* Identity.
* Permissions.
* Network access.
* Secrets.
* Logging.
* Encryption.
* Runtime protection.
* Resource limits.
* Dependency versions.

The baseline provides a consistent minimum security standard across AI environments.

---

### 108. Minimal Workload Design

A workload should contain only the components required to perform its function.

For example:

```text
AI Inference Container
├── Model Runtime
├── Required Libraries
├── Model Artifact
└── Application
```

Unnecessary utilities such as compilers, debugging tools, administrative shells, and unused services should generally be excluded from production images.

---

### 109. Minimal Operating System

Where practical, AI workloads should use minimal operating-system images.

Benefits include:

* Smaller attack surface.
* Fewer vulnerabilities.
* Fewer packages to maintain.
* Reduced attack paths.
* Easier vulnerability management.

The objective is not simply to use a smaller image but to eliminate unnecessary functionality.

---

### 110. Immutable Workloads

An immutable workload is not normally modified directly after deployment.

Instead:

```text
Old Version
     ↓
New Build
     ↓
Security Validation
     ↓
New Deployment
```

Rather than:

```text
Running Workload
     ↓
Manual Package Installation
     ↓
Configuration Changes
```

Immutable deployment improves consistency and reduces configuration drift.

---

### 111. Immutable Infrastructure

For high-value AI workloads, infrastructure can also follow an immutable model.

```text

       ↓

       ↓

       ↓

```

Changes are introduced through controlled deployment processes rather than undocumented manual modifications.

* Version control.

### 115. Container Security Context

Container security contexts can restrict workload capabilities.

Controls may include:

* Non-root execution.
* Read-only root file system.
* Dropping Linux capabilities.
* Restricting privilege escalation.
* Seccomp profiles.
* Mandatory access controls where applicable.

The principle is:

```text

   ↓

```

### 116. Linux Capabilities

Linux capabilities divide traditionally powerful root privileges into more granular permissions.

A workload should not receive capabilities it does not require.

For example:

```text

Unnecessary Capability → Drop
```

Reducing capabilities limits what an attacker can do after compromising the workload.

### 117. Privilege Escalation Prevention

Workloads should be configured to prevent unnecessary privilege escalation.

Controls can include:

* Non-root execution.
* Restricted capabilities.
* Security contexts.
* Policy enforcement.
* Read-only file systems.
* Runtime detection.

A workload that cannot easily escalate privileges provides a stronger containment boundary.

Where possible, production AI workloads can use read-only root file systems.

```text

    ↓

    ↓
```
