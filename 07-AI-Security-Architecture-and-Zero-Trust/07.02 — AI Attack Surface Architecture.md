# 07.02 — AI Attack Surface Architecture

## Part 1 — Foundations and Enterprise Attack Surface Model

## 1. Introduction

An AI system does not have a single attack surface.

Its attack surface is distributed across the entire ecosystem that allows the AI solution to **receive input, process information, retrieve data, invoke models, call tools, communicate with external services, and produce or execute outcomes**.

A useful way to visualize this is:

```text
                         USER
                           │
                           ▼
                    AI APPLICATION
                           │
             ┌─────────────┼─────────────┐
             ▼             ▼             ▼
          PROMPT         FILES          APIs
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                       AI GATEWAY
                           │
                  ┌────────┴────────┐
                  ▼                 ▼
                MODEL             RAG
                  │                 │
                  │            VECTOR DB
                  │                 │
                  └────────┬────────┘
                           ▼
                       AI AGENT
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
             API          TOOLS       SERVICES
              │            │            │
              └────────────┼────────────┘
                           ▼
                    ENTERPRISE DATA
```

Every component and connection represented above can introduce an attack opportunity.

---

# 2. What Is an AI Attack Surface?

The **AI attack surface** is the collection of:

* Components.
* Interfaces.
* identities.
* Data stores.
* APIs.
* Network connections.
* Dependencies.
* Trust relationships.
* Administrative functions.
* Human interactions.

that could potentially be exploited to compromise the **confidentiality, integrity, availability, or authorized behavior** of an AI system.

In traditional cybersecurity, an organization may focus on:

> Servers → Applications → Networks → APIs → Users.

For AI, the architecture expands:

> Users → Prompts → Applications → Models → Context → RAG → Vector Stores → Agents → Tools → APIs → Enterprise Systems → External AI Providers.

---

# 3. Why AI Changes the Attack Surface

Traditional applications generally execute predefined program logic.

AI systems introduce additional variability because the system can interpret:

* Natural-language instructions.
* Documents.
* Images.
* Audio.
* Retrieved information.
* Tool results.
* Model-generated content.

This means that data entering an AI system may influence subsequent behavior.

For example:

```text
Untrusted Document
       ↓
RAG Retrieval
       ↓
AI Context
       ↓
Model Interpretation
       ↓
Agent Decision
       ↓
Tool Invocation
```

The document is technically "data," but it may influence an AI system's behavior.

That makes the boundary between **data and instructions** particularly important.

# 7. Prompt Attack Surface

The prompt itself can become an attack vector.

Example:

```text
User
 ↓
"Ignore previous instructions..."
 ↓
AI Application
 ↓
Model
```

The architecture should not assume that every prompt represents legitimate business intent.

Prompt handling should therefore be considered part of the security architecture.

---

# 8. Prompt Injection as an Architectural Concern

Prompt injection is often discussed as a model problem.

From an architecture perspective, it is broader.

Consider:

```text
External Content
       ↓
Retriever
       ↓
Prompt Context
       ↓
Model
       ↓
Agent
       ↓
Tool
```

If untrusted content can influence the model and the model can control tools, the attack may propagate beyond the model.

Therefore:

> **The architecture must contain the consequences of manipulated model instructions.**

# 13. AI Gateway Attack Surface

# 14. Model Endpoint Attack Surface

Model endpoints may be exposed through:

* Internal APIs.
* Cloud APIs.
* External APIs.
* Private endpoints.
* Public endpoints.

Key questions:

> Is the endpoint publicly accessible?

> How is the caller authenticated?

> What rate limits exist?

> What data can be submitted?

> What outputs can be generated?

> Is the model endpoint isolated from critical infrastructure?

# 38. Attack Surface vs Attack Path

These concepts are different.

### Attack Surface

The components and interfaces that could potentially be attacked.

### Attack Path

The sequence an attacker could use to move from an initial compromise to an objective.

Example:

```text
Attack Surface:
AI Upload + RAG + Agent + API

Attack Path:
Upload → RAG → Agent → API → Data
```

This distinction is important during threat modeling.

---

# 39. Attack Surface Reduction

The objective is not to eliminate every component.

Instead:

> **Reduce unnecessary exposure and unnecessary capability.**

Examples:

```text
Public API
   ↓
Private API

Admin Access
   ↓
Restricted Admin Access

All Tools
   ↓
Approved Tools

Full Database
   ↓
Specific API

Permanent Credential
   ↓
Short-Lived Credential
```

---

# 40. Principle of Least Functionality

AI applications should expose only the functionality required for the approved use case.

If an AI assistant only needs:

> Read customer account status.

It should not receive:

> Full CRM administrative capabilities.

This is the architecture equivalent of least privilege.

---

# 41. Principle of Least Connectivity

The same principle applies to network connectivity.

If the AI only needs:

```text
AI → CRM API
```

there is little justification for:

```text
AI → Internet
AI → Database
AI → Payment
AI → HR
AI → Cloud Admin
```

unless those connections are explicitly required and approved.

---

# 42. Principle of Least Data

The AI should retrieve only the information required for the task.

For example:

```text
Question:
"What is my current invoice balance?"

Required:
Invoice balance

Not necessarily required:
Entire customer profile
Payment history
Other customers
Internal financial records
```

Reducing data exposure reduces attack surface.

---

# 44. Attack Surface and Risk

A useful relationship is:

```text
Exposure
   ×
Privilege
   ×
Data Sensitivity
   ×
Autonomy
   ×
Connectivity
   =
Potential AI Risk
```

This is not a formal quantitative risk equation, but it is a useful architectural reasoning model.

For example:

> Highly autonomous agent + sensitive data + broad API access + unrestricted internet = significantly higher architectural risk.

---

# 45. Attack Surface Prioritization

Not every component requires equal attention.

Prioritize components based on:

### Exposure

Is it internet-facing?

### Privilege

Can it perform sensitive actions?

### Data

Does it process sensitive information?

### Autonomy

Can it act without human approval?

### Criticality

Does it connect to critical systems?

### Connectivity

Can it reach many systems?

---

# 46. Critical Attack Surface

A particularly dangerous combination is:

```text
Internet Exposure
       +
Sensitive Data
       +
High Privilege
       +
High Autonomy
       +
Broad Connectivity
```

This should receive immediate security architecture attention.

A practical GRC register might look like:

| AI API         | Unauthorized access | OAuth            | Weak scope           | High   |

# 48. Attack Surface Ownership

Each major attack surface should have an owner.

For example:

```text
AI Application → Application Owner
Model → AI/ML Owner
Data → Data Owner
API → API Owner
Network → Network Security
Identity → IAM
Risk → Business/Risk Owner
```

GRC coordinates and provides oversight rather than becoming the technical owner of every component.

# 49. Architecture Review Questions

When reviewing an AI architecture, ask:

### Exposure

> What can reach the AI?

### Inputs

> What can influence the AI?

### Data

> What can the AI access?

### Identity

> Which identity does it use?

### Privilege

> What actions can it perform?

### Tools

> Which tools can it invoke?

### APIs

> Which enterprise systems can it reach?

### Network

> Where can it connect?

### Third Parties

> What leaves the enterprise boundary?

### Containment

# 50. GRC Perspective

From a GRC perspective, the objective is not to identify every theoretical attack.

The objective is to determine:

> **Which attack surfaces create material enterprise risk, whether appropriate controls exist, whether those controls are effective, and whether the remaining risk is acceptable.**

The assessment therefore follows:

```text
Attack Surface
      ↓
Threat
      ↓
Vulnerability
      ↓
Potential Impact
      ↓
Existing Controls
      ↓
Residual Risk
      ↓
Risk Decision
```

---

# 51. Senior-Level Mental Model

When looking at an AI architecture, do not ask only:

> "Where is the model?"

Ask:

> **"Where can an attacker influence the AI, where can the AI influence other systems, and what prevents that influence from becoming unauthorized action?"**

That question captures the essence of AI attack surface architecture.
