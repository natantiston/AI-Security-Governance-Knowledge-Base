# 07.01 — AI Security Architecture Foundations

## Part 1 — Foundations, Principles, Components, and Security Architecture Thinking

### 1. Introduction

AI security architecture is the structured design of security controls, trust relationships, identities, data flows, infrastructure, applications, models, and operational processes that protect an AI system throughout its lifecycle.

A traditional application security architecture might focus primarily on:

* Applications.
* Servers.
* Databases.
* Networks.
* Users.
* APIs.

An AI security architecture must extend that view.

An AI system may additionally introduce:

* Foundation models.
* Machine-learning models.
* Training data.
* Fine-tuning data.
* Embeddings.
* Vector databases.
* Prompt processing.
* Retrieval-augmented generation (RAG).
* AI agents.
* Tool integrations.
* Model APIs.
* Model registries.
* AI development pipelines.
* Model-serving infrastructure.

Therefore:

> **AI security architecture is not simply traditional cybersecurity applied to an AI application. It requires understanding the unique components, data flows, trust boundaries, and attack surfaces created by AI.**

---

# 2. Why AI Security Architecture Matters

AI systems increasingly interact with:

* Sensitive enterprise data.
* Internal applications.
* Customers.
* Employees.
* External APIs.
* Cloud platforms.
* Business workflows.
* Critical systems.

As AI becomes more capable, the security impact of an architecture decision increases.

For example:

```text
Traditional chatbot
        ↓
Provides information

AI agent
        ↓
Reads information
        ↓
Calls APIs
        ↓
Changes records
        ↓
Executes business actions
```

The second architecture introduces significantly greater security consequences.

The key question becomes:

> **What is the maximum authority we are giving the AI system, and what security architecture prevents that authority from being abused?**

---

# 3. Security Architecture vs. Security Controls

These concepts are related but different.

### Security Control

A specific safeguard.

Examples:

* MFA.
* Encryption.
* Firewall.
* DLP.
* RBAC.
* Logging.

### Security Architecture

The structured arrangement of:

* Components.
* Trust boundaries.
* Security controls.
* Identity.
* Network paths.
* Data flows.
* Dependencies.
* Enforcement points.

For example:

> MFA is a security control.

But:

> Designing an architecture where every privileged AI service identity must authenticate through centralized identity infrastructure and receive short-lived credentials is an architectural security decision.

---

# 4. Architecture as a Security Decision

Architecture determines:

> **Where security controls can be applied and how much damage can occur if a control fails.**

Consider two architectures.

### Architecture A

```text
AI Application
      ↓
Database
```

The AI application has direct database access.

### Architecture B

```text
AI Application
      ↓
Policy Enforcement
      ↓
Application API
      ↓
Authorization
      ↓
Data Service
      ↓
Database
```

Architecture B creates additional enforcement and authorization boundaries.

This illustrates an important principle:

> **Security should be designed into the architecture rather than added after deployment.**

# 5. AI Security Architecture Objectives

A secure AI architecture should seek to provide:

### Confidentiality

Prevent unauthorized access to:

* Prompts.
* Data.
* Models.
* Credentials.
* Outputs.

### Integrity

Protect:

* Models.
* Training data.
* Configuration.
* Prompts.
* Policies.
* AI-generated actions.

### Availability

Ensure AI services remain:

* Available.
* Resilient.
* Recoverable.

### Authenticity

Ensure:

> Users, services, models, APIs, and systems are what they claim to be.

### Accountability

Ensure:

> Actions can be traced to the responsible identity, system, or process.

# 12. AI Trust Must Be Explicit

A dangerous assumption is:

> "The AI is inside our environment, so we trust it."

The AI system should not automatically receive trust simply because it operates internally.

Instead:

> **Trust should be established based on identity, authorization, context, policy, and verified behavior.**

This becomes especially important for Zero Trust.

---

# 13. Zero Trust Foundation

A fundamental Zero Trust principle is:

> **Never trust implicitly; continuously verify.**

Applied to AI:

Do not assume that:

* An AI agent is trustworthy.
* An internal model is safe.
* A service account is legitimate.
* A tool call is authorized.
* Retrieved data should automatically be trusted.

Instead verify:

* Who?
* What?
* Why?
* What data?
* What action?
* Under what policy?
* Under what context?

---

# 14. Identity Is Central

AI security architecture increasingly depends on machine identities.

An AI system may have:

* Human users.

* Workload identities.
* API identities.

---

# 15. Least Privilege

AI systems should receive:

> **Only the minimum permissions necessary to perform their approved function.**

Example:

A customer-service AI should perhaps be allowed to:

* Read customer order status.

But not necessarily:

* Delete customer accounts.
* Modify billing information.
* Create administrator accounts.

---

# 16. AI Agent Authority

This becomes particularly important with AI agents.

An AI agent may be able to:

```text
Read
 ↓
Write
 ↓
Execute
 ↓
Transact
```

Each additional capability increases potential impact.

Therefore:

> **AI autonomy and privilege should be explicitly governed.**

---

# 17. The Principle of Bounded Autonomy

A useful architecture principle is:

> **Give AI enough authority to perform its intended function, but constrain the authority so that failures or compromise have limited impact.**

For example:

```text
AI Agent
   ↓
Read Customer Data
   ↓
Generate Recommendation
   ↓
Human Approval
   ↓
Execute Transaction
```

Instead of:

```text
AI Agent
   ↓
Full Transaction Authority
```

# 20. Secure-by-Design

Secure-by-design means security is considered during architecture and design rather than after deployment.

Instead of:

> Build → Deploy → Security Review → Fix

Prefer:

> Requirements → Threat Modeling → Secure Architecture → Build → Test → Deploy

# 21. Threat Modeling

AI architecture should be threat-modeled before deployment.

Ask:

* What are the assets?
* Who are the threat actors?
* What are the trust boundaries?
* Where does untrusted input enter?
* Where does sensitive data flow?
* What privileges exist?
* What external services are trusted?
* What happens if the model is compromised?
* What happens if the AI produces a malicious or incorrect instruction?

---

* Sensitive information disclosure.

# 23. Secure Architecture Principle: Minimize Exposure

A secure AI architecture should minimize:

* Unnecessary network exposure.
* Unnecessary data access.
* Excessive privileges.
* Unnecessary integrations.
* Long-lived credentials.
* Uncontrolled model endpoints.

The architectural question is:

> **What can we remove rather than merely protect?**

---

# 24. Secure Architecture Principle: Minimize Blast Radius

If an AI component is compromised:

> **How much of the enterprise can the attacker reach?**

This is the **blast radius** question.

Example:

### Poor architecture

```text
AI Agent
   ↓
Full Enterprise Network
```

### Better architecture

```text
AI Agent
   ↓
Restricted Segment
   ↓
Approved Gateway
   ↓
Specific API
```

The second design limits potential impact.

---

# 25. Secure Architecture Principle: Explicit Boundaries

Important boundaries should be clearly defined between:

* Users.
* AI applications.
* Models.
* Data.
* Tools.
* APIs.
* Providers.
* Administrative systems.

Each boundary should have:

* Identity.
* Authentication.
* Authorization.
* Monitoring.
* Policy enforcement.

---

# 26. Secure Architecture Principle: Fail Securely

If the AI system encounters:

* Uncertainty.
* Authorization failure.
* Tool failure.
* Policy violation.
* Suspicious input.

The secure behavior should be:

> **Deny, restrict, or escalate rather than automatically proceed.**

For example:

```text
Authorization Failure
        ↓
      DENY
        ↓
     LOG
        ↓
    ALERT
```

rather than:

```text
Authorization Failure
        ↓
"Try anyway"
```

---

# 27. Secure Architecture Principle: Assume Compromise

A mature architecture assumes that:

* A credential could be stolen.
* A model could behave unexpectedly.
* A tool could be compromised.
* A provider could experience an incident.
* A user could be malicious.
* A prompt could be hostile.

Therefore:

> **Architecture should remain resilient even when individual components cannot be fully trusted.**

# 07.01 — AI Security Architecture Foundations

## Part 2 — Architecture Components, Security Layers, and Enterprise Implementation

AI security architecture becomes meaningful when the principles from Part 1 are translated into a **structured enterprise architecture**. The objective is to understand where security capabilities belong, how different components interact, and how controls should be positioned across the AI environment.

---

## 1. The AI Security Architecture Stack

A practical enterprise AI environment can be represented as a layered stack:

```text
┌───────────────────────────────────────────────┐
│                 USERS / ACTORS                │
├───────────────────────────────────────────────┤
│             IDENTITY & ACCESS                 │
├───────────────────────────────────────────────┤
│          AI APPLICATION / AGENT               │
├───────────────────────────────────────────────┤
│          AI GATEWAY / POLICY LAYER            │
├───────────────────────────────────────────────┤
│              MODEL SERVICES                  │
├───────────────────────────────────────────────┤
│       RAG / VECTOR / KNOWLEDGE LAYER          │
├───────────────────────────────────────────────┤
│            TOOLS / APIs / SERVICES             │
├───────────────────────────────────────────────┤
│              DATA / STORAGE                   │
├───────────────────────────────────────────────┤
│         COMPUTE / CLOUD / NETWORK             │
├───────────────────────────────────────────────┤
│     SECURITY / MONITORING / GOVERNANCE         │
└───────────────────────────────────────────────┘
```

Security architecture should not be treated as a single layer.

It is a **cross-cutting architecture capability** that protects every layer.

---

# 2. User and Actor Layer

The first layer contains entities interacting with the AI environment.

These may include:

* Employees.
* Customers.
* Administrators.
* Developers.
* Security personnel.
* Business users.
* External partners.
* Other applications.
* AI agents.

The architecture should distinguish between:

> **Human identity and machine identity.**

For example:

```text
Employee
   ↓
Human Identity
   ↓
AI Application
```

versus:

```text
AI Application
   ↓
Workload Identity
   ↓
Enterprise API
```

These require different security mechanisms.

---

# 3. Identity and Access Layer

Identity becomes one of the most important security architecture layers because AI systems increasingly interact with enterprise resources.

The identity architecture should answer:

* Who is the user?
* What application is making the request?
* What workload is executing?
* Which service is being accessed?
* What permissions exist?
* Who owns the identity?

Typical technologies include:

* Identity providers.
* Single sign-on.
* MFA.
* RBAC.
* ABAC.
* Workload identity.
* Privileged access management.
* OAuth.
* OpenID Connect.
* Service principals.

---

# 4. AI Application Layer

The AI application provides the business interface around the model.

Examples include:

* Enterprise chatbot.
* Customer-service assistant.
* Developer assistant.
* Security assistant.
* HR assistant.
* AI-powered business application.

The application may control:

* User sessions.
* Prompt construction.
* Context.
* Model selection.
* Retrieval.
* Tool invocation.
* Business logic.

Therefore, securing the model alone is insufficient.

---

# 5. AI Gateway Layer

An AI gateway can provide centralized enforcement between applications and AI services.

```text
Application
     ↓
AI Gateway
     ↓
Security Policies
     ↓
Model
```

Potential capabilities include:

* Authentication.
* Authorization.
* Rate limiting.
* Usage control.
* Model routing.
* Prompt inspection.
* Output inspection.
* DLP.
* Logging.
* Cost controls.

The gateway can become an important **policy enforcement point**.

---

# 6. Why Centralized Enforcement Matters

Consider an environment where ten applications connect directly to several models:

```text
App 1 ───→ Model A
App 2 ───→ Model A
App 3 ───→ Model B
App 4 ───→ Model C
...
App 10 ──→ Model B
```

Security policies can become inconsistent.

A centralized architecture provides:

```text
App 1 ──┐
App 2 ──┤
App 3 ──┤
App 4 ──┼──→ AI Gateway ──→ Approved Models
...     │
App 10 ─┘
```

This can improve:

* Visibility.
* Policy consistency.
* Monitoring.
* Governance.
* Incident response.

---

# 9. RAG Architecture

```text

                   ↓

                   ↓
                RETRIEVER
                   ↓
             VECTOR DATABASE

                   ↓
```

---

# 10. Authorization-Aware Retrieval

Consider an employee who can access:

```text
Document A
Document B
```

but not:

```text
Document C
```

The AI system should not retrieve Document C simply because the vector database contains it.

A secure design should enforce:

```text
User Identity
      ↓
Authorization
      ↓
Permitted Documents
      ↓
Retrieval
      ↓
Model
```

This is often described as **authorization-aware retrieval**.

> **The model should not be the final authority for access control.**


# 48. Common Architectural Mistakes

The surrounding infrastructure remains exposed.

### Mistake 2 — Trusting internal AI automatically

Users may retrieve data they should not access.

Compromise affects multiple workloads.

### Mistake 7 — No architecture documentation

Security teams cannot accurately assess the environment.

### Mistake 8 — No monitoring

Organizations cannot detect misuse.

# 52. Interview Anchor — Architecture

If asked:

### "How do you approach AI security architecture?"

A strong answer is:

> **"I start with the business use case and map the complete AI architecture, including users, identities, applications, models, data, RAG components, tools, APIs, cloud infrastructure and third-party dependencies. ### "Why isn't securing the model enough?"

> **"Because the model is only one component of the AI system. A secure model can still be deployed in an insecure application, connected to an overprivileged identity, exposed through an insecure API, connected to unauthorized data, or given excessive tool access. I therefore assess the complete execution chain and ensure security controls are independently enforced at the appropriate trust boundaries."**

# 56. Core Architecture Principles

For practical application, retain these principles:

1. **Least privilege** — AI receives only necessary permissions.
2. **Explicit trust** — no implicit trust based on location.
3. **Independent authorization** — model output does not equal authorization.
4. **Defense in depth** — multiple security layers protect critical paths.
5. **Segmentation** — sensitive systems are separated.
6. **Isolation** — compromised workloads have limited blast radius.
7. **Data minimization** — AI receives only required data.
8. **Controlled connectivity** — network paths are explicitly permitted.
9. **Strong identity** — human and machine identities are distinguishable and accountable.
10. **Centralized visibility** — security-relevant activity is observable.
11. **Secure lifecycle** — development, deployment, change and retirement are governed.
12. **Fail securely** — uncertain or unauthorized actions should be denied or escalated.
13. **Traceability** — architecture decisions, controls and evidence remain connected.
14. **Continuous validation** — actual deployment should remain consistent with the approved architecture.

# 07.01 — AI Security Architecture Foundations

## Part 3 — Security Architecture Governance, Risk Assessment, and Control Validation

AI security architecture becomes a GRC discipline when the architecture is evaluated against **business requirements, security requirements, risk appetite, policies, regulatory obligations, and control expectations**.

The GRC objective is not merely to confirm that an architecture diagram exists. It is to determine whether the architecture provides **appropriate protection for the AI use case and its associated risk**.

---

```text

        ↓

        ↓

        ↓

        ↓
Security Requirements
        ↓
Controls
        ↓

        ↓
Residual Risk
        ↓

```

This creates a direct connection between:

> **Business purpose → Technical architecture → Security controls → Risk decision**

# 2. Business Context Comes First

Before assessing an AI architecture, understand what the AI system is intended to accomplish.

Ask:

* What business process does it support?
* Who uses it?
* What decisions does it influence?
* What data does it process?
* What systems does it access?
* What actions can it perform?
* How critical is the business process?

The same technical architecture can represent different levels of risk depending on its business context.

# 3. AI Use Case Classification

An AI architecture should be classified according to its intended use.

For example:

### Low-impact

Internal productivity assistant using non-sensitive information.

### Moderate-impact

AI assistant accessing internal business information.

### High-impact

AI system processing sensitive customer information.

### Critical-impact

AI agent capable of making or executing high-value business decisions.

The security architecture should become more restrictive as potential impact increases.

# 51. Senior Interview Question

### "How would you perform a security architecture review for an AI system?"

A strong answer:

> **"I would start with the business use case and classify the risk based on the data processed, business criticality, level of autonomy and potential impact. I would identify trust boundaries and attack paths, then assess whether controls such as least privilege, authorization, segmentation, encryption, secrets management, monitoring and independent tool authorization are appropriately implemented. # 07.01 — AI Security Architecture Foundations

## Part 4 — Advanced Architecture Patterns, Assessment Methodology, and Practical GRC Application

## 1. Architecture Must Reflect AI-Specific Risk

Traditional enterprise security architecture provides the foundation for AI security, but AI introduces additional characteristics that require architectural consideration.

An AI system can:

* Interpret untrusted natural language.
* Generate unpredictable outputs.
* Retrieve enterprise information.
* Call external tools.
* Invoke APIs.
* Make recommendations.
* Execute actions.
* Dynamically determine which information to use.
* Operate with varying levels of autonomy.

Therefore, the architecture must protect not only **systems and data**, but also the **AI decision and execution pathway**.

A useful model is:

```text
User Intent
    ↓
Prompt / Input
    ↓
AI Reasoning
    ↓
Retrieval / Context
    ↓
Model Output
    ↓
Policy Decision
    ↓
Tool / API Action
    ↓
Enterprise System
```

Every transition represents a potential security boundary.

---

# 2. AI Security Architecture Is About Controlling Authority

One of the most important concepts in AI architecture is **authority**.

A model may generate an instruction, but generating an instruction should not automatically grant permission to execute it.

For example:

```text
AI:
"Delete customer account 12345."

        ↓

Authorization Layer:
Is this action permitted?

        ↓

Policy:
Is deletion allowed?

        ↓

Approval:
Is human approval required?

        ↓

Execution:
Delete account
```

The architecture therefore separates:

> **Intelligence from authority.**

This distinction becomes especially important for AI agents.

---

# 3. AI Agent Security Architecture

A traditional chatbot may primarily generate information.

An agent can:

```text
Observe
   ↓
Reason
   ↓
Select Tool
   ↓
Execute Action
   ↓
Observe Result
   ↓
Continue
```

This creates a larger attack surface.

An agent architecture should therefore include:

* Dedicated identity.
* Least privilege.
* Tool allowlisting.
* API authorization.
* Transaction limits.
* Input validation.
* Output validation.
* Logging.
* Human approval where appropriate.
* Emergency revocation.

---

# 4. Tool Allowlisting

Agents should not automatically have access to every available tool.

Example:

```text
AI Agent
   │
   ├── Search Customer ───── ALLOWED
   ├── Read Invoice ──────── ALLOWED
   ├── Update Address ────── ALLOWED
   ├── Delete Customer ───── BLOCKED
   └── Admin Console ─────── BLOCKED
```

This follows the principle:

> **Deny by default, explicitly allow required capabilities.**

---

# 5. Tool-Level Authorization

Authorization should operate at the tool level, not only at the application level.

For example:

```text
AI Application
      ↓
Agent Identity
      ↓
Tool Gateway
      ↓
┌───────────────────────┐
│ Search       ✓        │
│ Read         ✓        │
│ Update       ✓        │
│ Delete       ✗        │
│ Admin        ✗        │
└───────────────────────┘
```

This reduces the consequences of an agent compromise.

---

# 6. Transaction Controls

For high-impact operations, architectural controls should limit what an AI can execute.

Examples:

* Maximum transaction amount.
* Maximum number of records.
* Restricted operating hours.
* Restricted destination accounts.
* Human approval.
* Dual authorization.

For example:

```text
AI Agent
   ↓
Transfer Request
   ↓
Amount > €5,000?
   ↓
YES
   ↓
Human Approval
   ↓
Execution
```

---

# 7. Human-in-the-Loop Architecture

Human oversight should be applied according to risk rather than automatically to every AI interaction.

### Low-risk

```text
AI → Execute
```

### Medium-risk

```text
AI → Policy Check → Execute
```

### High-risk

```text
AI → Policy Check → Human Approval → Execute
```

### Critical-risk

```text
AI → Policy Check
       ↓
Security Validation
       ↓
Human Approval
       ↓
Second Authorization
       ↓
Execution
```

---

# 8. Human Oversight Is Not a Substitute for Security

A common architectural mistake is assuming:

> "A human reviews the AI output, so the system is secure."

That is insufficient.

Humans can:

* Miss malicious content.
* Approve incorrect recommendations.
* Misinterpret AI output.
* Become overwhelmed by excessive alerts.

Human approval should therefore complement:

* IAM.
* Authorization.
* Validation.
* Segmentation.
* Monitoring.
* Policy enforcement.

---

# 9. Zero Trust Architecture for AI

Zero Trust provides an important architectural foundation.

The core mindset is:

> **Never trust implicitly; continuously evaluate access based on identity, context, policy and risk.**

Applied to AI:

```text
User
 ↓
Identity Verification
 ↓
Device / Context
 ↓
Policy Evaluation
 ↓
AI Application
 ↓
Resource Authorization
 ↓
Action
```

The AI's location should not automatically establish trust.

---

# 10. AI-to-AI Trust

AI systems may communicate with other AI systems.

For example:

```text
Customer AI Agent
       ↓
Financial AI Agent
       ↓
Payment Service
```

The architecture should not assume that:

> "AI systems are internal, therefore they are trusted."

Each system should have an identifiable identity and explicitly authorized communication path.

AI microservices should authenticate and authorize each other.

Example:

```text

   ↓

   ↓

   ↓

   ↓

```

This prevents unauthorized lateral movement.

* Send sensitive data externally.
* Connect to malicious infrastructure.
* Download unapproved components.
* Access unauthorized services.

```text

     ↓

     ↓

     ↓

```

```text

   ↓

   ↓

```

Direct exposure of internal AI services should be avoided where unnecessary.

---

# 15. AI Runtime Isolation

Model execution should be isolated from unrelated workloads.

Possible mechanisms include:

* Containers.
* Kubernetes namespaces.
* Network policies.
* Separate virtual networks.
* Dedicated compute.
* Sandboxing.
* Runtime security.

The goal is to reduce:

> **Blast radius.**

---

# 16. Blast Radius

Blast radius describes the amount of damage that could occur if an AI workload is compromised.

Compare:

### Poor Architecture

```text
Compromised AI
      ↓
Admin Identity
      ↓
All Enterprise Systems
```

### Better Architecture

```text
Compromised AI
      ↓
Restricted Identity
      ↓
Limited API
      ↓
Specific Data
```

The second architecture contains the compromise.

---

# 17. Fail-Secure Architecture

AI systems should fail securely.

If authorization cannot be verified:

```text
Authorization Service Unavailable
          ↓
        DENY
```

not:

```text
Authorization Service Unavailable
          ↓
      Allow Access
```

This is especially important for sensitive actions.

---

# 18. Fail-Safe vs Fail-Secure

These concepts should not be confused.

**Fail-safe** generally emphasizes preventing dangerous outcomes.

**Fail-secure** emphasizes maintaining security controls during failure.

For sensitive AI actions, the architecture should generally avoid turning a security-control failure into automatic authorization.

---

# 19. Secure Defaults

AI architecture should use secure defaults.

Examples:

* Tool access disabled by default.
* Internet access disabled by default.
* Write operations disabled by default.
* Sensitive data access disabled by default.
* Production credentials unavailable by default.

Then explicitly enable only what is required.

---

Examples:

```text

        ↓

        ↓

        ↓

        ↓

        ↓

```

This is stronger than relying on application developers or the model to enforce every rule.

---

# 21. Policy Decision Point vs Policy Enforcement Point

A useful architecture distinction is:

### Policy Decision Point

Determines:

> "Is this action allowed?"

### Policy Enforcement Point

Actually prevents or permits the action.

Example:

```text

   ↓
Request
   ↓
Policy Decision Point
   ↓
ALLOW / DENY
   ↓
Policy Enforcement Point
   ↓

```

This separation can improve governance and consistency.

# 38. Practical GRC Walkthrough

Potentially sensitive/confidential.

Employees and HR personnel.

Read information and generate responses.

Approved enterprise environment/provider.

### Step 8 — Is information logged?

Security-relevant access should be auditable.

### Step 9 — Can the AI access everything?

No.

### Step 10 — What happens if the AI is compromised?

Access should be limited through identity, segmentation and authorization controls.

# 42. Architecture Questions for a GRC Interview

### Question

> "What do you look for first in an AI security architecture?"

Answer:

> **"I first establish the business purpose, data sensitivity, level of autonomy and potential business impact. From there I map the architecture and identify identities, trust boundaries, data flows, external dependencies, tools and APIs. I then assess whether access is least-privilege, whether authorization is independently enforced, whether sensitive paths are segmented and whether the organization has sufficient monitoring and containment capability."**

---

# 43. Interview Question — AI Agent

### "What is your biggest security concern with AI agents?"

A strong answer:

> **"The biggest concern is the combination of autonomy and authority. An agent can potentially interpret instructions, retrieve information and execute actions. If it is given excessive privileges, a compromised identity, malicious input or manipulated context could result in significant business impact. I therefore focus on dedicated identities, least privilege, explicit tool allowlisting, independent authorization, transaction controls, monitoring and rapid credential or tool revocation."**

---

# 44. Interview Question — Zero Trust

### "How would you apply Zero Trust to AI?"

A strong answer:

> **"I would treat the user, application, AI workload, model service and downstream APIs as separate security principals rather than assuming trust based on network location. Each access request should be authenticated and authorized according to identity, resource, action, context and policy. For AI agents, I would apply the same principle to tool calls and service-to-service communication, with least privilege and explicit authorization at each trust boundary."**

---

# 45. Interview Question — Architecture Failure

### "What happens if the AI model is compromised?"

A strong answer:

> **"The architecture should assume that individual components can fail or be compromised. The model should not have unrestricted authority, so a model compromise should not automatically provide access to the enterprise. Dedicated identities, restricted APIs, network segmentation, data authorization, tool allowlisting and monitoring should contain the blast radius. We should also have mechanisms to revoke credentials, disable tools and isolate the workload."**

---

# 46. Interview Question — GRC and Architecture

### "How do you challenge an architect without being overly technical?"

A strong answer:

> **"I focus on risk and control outcomes rather than prescribing a specific technology. I would ask what assets are exposed, who has authority, what trust boundaries exist, what happens if a component is compromised, how the access is controlled, what evidence demonstrates the control is working, and whether the residual risk is within appetite. This allows me to challenge the architecture from a GRC perspective while still understanding the technical implementation."**

---

# 47. Senior-Level Architecture Language

Instead of saying:

> "The AI needs security."

Use:

> **"The architecture should establish explicit trust boundaries and enforce least privilege across the AI execution chain."**

Instead of:

> "We need to protect the API."

Use:

> **"The API represents an authorization boundary and should enforce authenticated, context-aware access independently of the model."**

Instead of:

> "The AI should not have too much access."

Use:

> **"The AI workload should operate under a dedicated identity with the minimum permissions required for its approved business purpose."**

Instead of:

> "We need logs."

Use:

> **"Security-relevant AI activities should generate attributable and tamper-resistant audit evidence sufficient for detection, investigation and assurance."**

# 48. The Five Architecture Tests

A practical senior-level test is:

### Test 1 — Identity

**Who is making the request?**

### Test 2 — Authority

**What is that identity allowed to do?**

### Test 3 — Data

**What information can it access?**

### Test 4 — Path

**Through what network/API/tool path can it reach the resource?**

### Test 5 — Containment

**What happens if the AI or its identity is compromised?**

If these five questions cannot be answered clearly, the architecture likely requires additional analysis.
