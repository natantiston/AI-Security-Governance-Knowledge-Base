# 07.15 — AI Runtime Security and Infrastructure Protection

## Part 1

### 1. Introduction to AI Runtime Security

AI runtime security focuses on protecting the environment in which an AI model is loaded, executed, monitored, and connected to enterprise resources.

The runtime includes more than the model itself:

```text
AI Runtime
├── Model
├── Inference Engine
├── Libraries
├── Operating System
├── Container / VM
├── GPU / CPU
├── Network
├── Storage
├── Credentials
└── Supporting Services
```

A secure AI model can still become a security risk if its runtime environment is poorly protected.

---

### 2. Runtime Security Objective

The primary objective is to ensure that:

> **AI workloads execute only within trusted, hardened, monitored, and appropriately isolated infrastructure.**

This protects against:

* Runtime compromise.
* Unauthorized access.
* Malware.
* Privilege escalation.
* Container escape.
* Resource exhaustion.
* Credential theft.
* Data exfiltration.
* Infrastructure compromise.

---

### 3. AI Runtime as a Security Boundary

The AI runtime should be treated as a security boundary.

```text
                 AI MODEL
                    │
                    ▼
          ┌──────────────────┐
          │  AI RUNTIME      │
          │                  │
          │ Model Engine     │
          │ Libraries        │
          │ Processes        │
          └────────┬─────────┘
                   │
            Security Controls
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    Network      Storage     Identity
```

The runtime should not have unrestricted access to the surrounding infrastructure.

---

### 4. Runtime Attack Surface

The AI runtime introduces multiple attack surfaces.

```text
              AI Runtime
                  │
       ┌──────────┼──────────┐
       ▼          ▼          ▼
    Network    Software    Hardware
       │          │          │
       ▼          ▼          ▼
    APIs       Libraries    GPU
    Ports      Packages     Drivers
    DNS        Runtime      Firmware
```

Security architecture must consider all of these components.

---

### 5. Runtime Components

A typical AI runtime may include:

1. Operating system.
2. Container runtime.
3. Python or other language runtime.
4. AI/ML frameworks.
5. Model-serving software.
6. Model files.
7. GPU drivers.
8. Supporting libraries.
9. APIs.
10. Monitoring agents.

Each component creates potential vulnerabilities.

---

### 6. Runtime Security Layers

A defense-in-depth approach can be represented as:

```text
┌─────────────────────────────┐
│ AI Application Security     │
├─────────────────────────────┤
│ Model Security              │
├─────────────────────────────┤
│ Runtime Security            │
├─────────────────────────────┤
│ Container / VM Security     │
├─────────────────────────────┤
│ Operating System Security   │
├─────────────────────────────┤
│ Network Security            │
├─────────────────────────────┤
│ Infrastructure Security     │
└─────────────────────────────┘
```

No single control should be expected to protect the complete AI environment.

---

### 7. Secure Runtime Baseline

Organizations should establish a standard baseline for AI workloads.

Example:

```text
AI Runtime Baseline
├── Approved OS
├── Approved container image
├── Supported runtime
├── Non-root execution
├── Minimal packages
├── Restricted network
├── Restricted filesystem
├── Approved model
├── Logging enabled
└── Monitoring enabled
```

---

### 8. Hardened Operating System

The underlying operating system should be hardened according to enterprise standards.

Controls may include:

* Security patches.
* Disabled unnecessary services.
* Restricted accounts.
* Secure configuration.
* Host firewall.
* Endpoint protection.
* Logging.
* File-integrity monitoring.

---

### 9. Minimal Operating System

AI runtimes should avoid unnecessary operating-system components.

```text
Full OS
 ↓
Remove unnecessary services
 ↓
Remove unnecessary packages
 ↓
Harden configuration
 ↓
AI Runtime
```

Reducing the number of installed components reduces the attack surface.

---

### 10. Patch Management

AI infrastructure should follow a formal patch-management process.

Patch areas include:

* Operating system.
* Container runtime.
* AI framework.
* Python packages.
* Model-serving software.
* GPU drivers.
* Security tools.

---

### 11. Vulnerability Management

AI infrastructure should be included within the enterprise vulnerability-management program.

```text
Asset Discovery
      ↓
Vulnerability Scan
      ↓
Risk Assessment
      ↓
Remediation
      ↓
Validation
```

---

### 12. AI Runtime Vulnerability Scanning

Scanning should cover multiple layers.

```text
Container Image
      ↓
OS Packages
      ↓
Application Libraries
      ↓
AI Framework
      ↓
Runtime Dependencies
```

A clean application scan does not necessarily mean the entire AI runtime is secure.

---

### 13. Dependency Security

AI frameworks frequently rely on large dependency trees.

For example:

```text
AI Application
     ↓
Framework
     ↓
Library A
     ↓
Library B
     ↓
Library C
```

A vulnerability in a lower-level dependency can affect the AI workload.

---

### 14. Software Bill of Materials

An SBOM can provide visibility into runtime components.

```text
AI Runtime
├── Python
├── PyTorch
├── NumPy
├── CUDA
├── OpenSSL
└── Other Dependencies
```

This improves vulnerability identification and supply-chain governance.

---

### 15. Dependency Version Control

Production AI runtimes should use controlled versions.

Avoid uncontrolled installations such as:

```text
pip install latest
```

Prefer approved and tested dependency versions.

---

### 16. Dependency Pinning

Dependency versions can be explicitly defined.

```text
Application
 ↓
Approved Dependency Versions
 ↓
Reproducible Runtime
```

This reduces unexpected changes during deployment.

---

### 17. Dependency Integrity

Dependencies should be obtained from trusted sources and, where appropriate, verified using:

* Hashes.
* Digital signatures.
* Trusted repositories.
* Package allowlists.

---

### 18. Malicious Package Risk

Attackers may publish packages designed to look legitimate.

```text
Developer
 ↓
Package Repository
 ↓
Malicious Dependency
 ↓
AI Runtime
```

Therefore, AI environments should have software supply-chain controls.

---

### 19. AI Framework Security

AI frameworks such as deep-learning libraries are critical runtime components.

Security teams should monitor:

* Vulnerabilities.
* Supported versions.
* Security advisories.
* Unsafe serialization mechanisms.
* Dependency vulnerabilities.
* Configuration weaknesses.

---

### 20. Model Loading Security

Loading a model can itself introduce security risk.

```text
Model File
   ↓
Loader
   ↓
Runtime
```

An unsafe model format or loader vulnerability could result in code execution.

---

### 21. Model Serialization Risk

Some serialization formats can contain executable or otherwise unsafe content.

Therefore:

```text
Untrusted Model
      ↓
Do NOT directly load
      ↓
Validate / Scan
      ↓
Controlled Environment
```

Model files should be treated as potentially untrusted artifacts until validated.

---

### 22. Trusted Model Registry

Approved models should be stored in a controlled registry.

```text
Model Source
     ↓
Security Validation
     ↓
Approval
     ↓
Model Registry
     ↓
Production Runtime
```

---

### 23. Model Integrity

Model integrity should be verified before deployment.

Possible mechanisms include:

* Cryptographic hashes.
* Digital signatures.
* Version verification.
* Registry controls.

```text
Model
 ↓
Hash / Signature
 ↓
Compare with Approved Version
 ↓
Deploy
```

---

### 24. Runtime Configuration Management

AI runtime configurations should be centrally controlled.

Configuration may include:

* Model version.
* API endpoints.
* Network rules.
* Resource limits.
* Authentication settings.
* Logging.
* Security policies.

---

### 25. Configuration Drift

A secure runtime can become insecure if configuration changes without proper control.

```text
Approved Configuration
        ↓
Production
        ↓
Unauthorized Change
        ↓
Configuration Drift
```

Configuration drift should be detected and remediated.

---

### 26. Infrastructure as Code

Where practical, AI infrastructure should be deployed through controlled Infrastructure as Code.

```text
IaC
 ↓
Review
 ↓
Security Validation
 ↓
Deployment
 ↓
Monitoring
```

This improves consistency and auditability.

---

### 27. Immutable Infrastructure

A preferred approach is to rebuild infrastructure from trusted configurations rather than manually modifying production systems.

```text
Trusted Image
     ↓
Deployment
     ↓
Runtime
     ↓
Compromise
     ↓
Destroy
     ↓
Rebuild Trusted Image
```

---

### 28. Container Image Security

AI container images should be:

* Minimal.
* Scanned.
* Version controlled.
* Signed where appropriate.
* Obtained from trusted repositories.
* Regularly updated.

---

### 29. Container Image Lifecycle


### 30. Image Provenance

Organizations should know:

* Who built the image.
* Which source code was used.
* Which dependencies were included.
* Which model was packaged.
* When it was built.
* Whether it passed security checks.

---

### 31. Image Signing

Signed images provide assurance that the deployed artifact originated from an approved source and has not been modified unexpectedly.

```text
Approved Build
     ↓
Sign
     ↓

     ↓

     ↓

```

---

### 32. Runtime Admission Control

Before deployment, infrastructure can verify whether the workload meets security requirements.

```text
Deployment Request
       ↓
Admission Policy
       ↓
 ┌─────┴─────┐
 ▼           ▼
ALLOW       DENY
```

---

### 33. Non-Root Execution

AI workloads should run as non-root whenever technically possible.

```text
Root
 ↓
Avoid

Restricted User
 ↓
Preferred
```

If the AI process is compromised, non-root execution can reduce the attacker's privileges.

---

### 34. Privilege Escalation Protection

The runtime should prevent unnecessary privilege escalation.

Controls can include:

* Non-root execution.
* Restricted Linux capabilities.
* No privileged containers.
* Read-only filesystem.
* Security profiles.
* Restricted system calls.

---

### 35. Filesystem Protection

The AI runtime should have only the filesystem access it needs.

```text
AI Runtime
├── Model → READ
├── Temporary Workspace → WRITE
├── System Files → DENY
└── Credentials → DENY
```

---

### 36. Read-Only Runtime

Where possible, production runtime components should use read-only filesystems.

This reduces the ability of attackers to establish persistence.

```text
AI Runtime
 ↓
Read-Only Filesystem
 ↓
Reduced Persistence
```

---

### 37. Temporary Workspace

Write operations should preferably occur in controlled temporary directories.

```text
AI Process
 ↓
Temporary Workspace
 ↓
Task Complete
 ↓
Cleanup
```

---

### 38. Credential Isolation

AI runtimes should not contain unnecessary long-lived credentials.

Avoid:

```text
Container
 └── Permanent API Keys
```

Prefer:

```text
Runtime
 ↓
Identity
 ↓
Secret Manager
 ↓
Short-Lived Credential
```

---

### 39. Secret Management

Secrets should be managed through approved enterprise mechanisms.

Examples include:

* Secret managers.
* Vault systems.
* Cloud identity services.
* Workload identities.

The model itself should not be given direct visibility of secrets.

---

### 40. Network Security

Network connectivity should follow least privilege.

```text
AI Runtime
   ↓
Network Policy
 ├── Required API → ALLOW
 ├── Logging → ALLOW
 ├── Internal Admin → DENY
 └── Unapproved Internet → DENY
```

---

### 41. Network Segmentation

AI workloads should be placed in appropriate network segments.

```text
Internet
   ↓
AI Gateway
   ↓
AI Runtime Network
   ↓
Controlled Enterprise Services
```

The runtime should not automatically reside in the same unrestricted network as critical infrastructure.

---

### 42. Egress Filtering

Outbound connections are particularly important because a compromised AI runtime may attempt to exfiltrate information.

```text
AI Runtime
 ↓
Egress Firewall
 ↓
Approved Destinations
```

---

### 43. Ingress Filtering

Inbound access should also be restricted.

```text
Client
 ↓
Gateway
 ↓
Authentication
 ↓
AI Runtime
```

Direct exposure of the runtime to untrusted networks should be minimized.

---

### 44. API Security

AI runtimes frequently expose APIs.

API controls should include:

* Authentication.
* Authorization.
* Rate limiting.
* Input validation.
* TLS.
* Logging.
* Abuse detection.

---

### 45. Runtime Authentication

Only authorized services or users should be able to interact with the runtime.

```text
Requester
 ↓
Identity Verification
 ↓
Authorization
 ↓
AI Runtime
```

---

### 46. Runtime Authorization

Authentication answers:

> **Who are you?**

Authorization answers:

> **What are you allowed to do?**

Both are necessary for secure AI infrastructure.

---

### 47. Runtime Rate Limiting

Rate limiting protects against:

* Abuse.
* Resource exhaustion.
* Automated attacks.
* Runaway agents.
* Excessive inference requests.

```text
Request
 ↓
Rate Limit
 ↓
ALLOW / THROTTLE / DENY
```

---

### 48. Resource Isolation

AI workloads can consume substantial infrastructure resources.

Controls should cover:

* CPU.
* RAM.
* GPU.
* Disk.
* Network bandwidth.
* Concurrent requests.

---

### 49. GPU Security

GPU infrastructure requires additional security consideration.

Relevant areas include:

* GPU drivers.
* CUDA libraries.
* Device permissions.
* GPU memory.
* Multi-tenant GPU sharing.
* Firmware.
* Container-to-GPU access.

---

### 50. Runtime Monitoring

The AI runtime should be continuously monitored for abnormal activity.

```text
AI Runtime
    ↓
Telemetry
    ↓
Security Monitoring
    ↓
Detection
    ↓
Alert / Response
```

Monitoring should cover both **security events and operational behavior**.

## Part 2 — Runtime Hardening, Container/Kubernetes Security, Network Protection, and Infrastructure Controls

### 51. Runtime Hardening

AI runtime hardening reduces the attack surface of the infrastructure supporting the model.

A hardened runtime should follow:

```text
Minimal Components
        ↓
Minimal Privileges
        ↓
Minimal Connectivity
        ↓
Controlled Execution
        ↓
Continuous Monitoring
```

---

### 52. Runtime Hardening Baseline

A standard AI runtime baseline can include:

* Approved operating system.
* Approved container image.
* Supported AI framework.
* Non-root execution.
* Restricted filesystem.
* Restricted network.
* Disabled unnecessary services.
* Vulnerability scanning.
* Logging.
* Monitoring.

---

### 53. Attack Surface Reduction

The principle is simple:

> **Every unnecessary component, privilege, port, service, package, or connection increases the potential attack surface.**

```text
More Components
      ↓
More Attack Surface
      ↓
More Potential Vulnerabilities
```

---

### 54. Service Minimization

Only required services should run inside the AI runtime.

```text
Required Service → RUN
Unnecessary Service → REMOVE
Unknown Service → INVESTIGATE
```

This reduces the number of processes that an attacker could exploit.

---

### 55. Port Minimization

AI infrastructure should expose only required ports.

```text
Required AI API → ALLOW
Administrative Port → RESTRICT
Unused Port → BLOCK
```

---

### 56. Secure Container Runtime

For containerized AI workloads:

```text
AI Container
 ↓
Container Runtime
 ↓
Host Kernel
```

Each layer must be secured because a weakness in the container runtime or host can compromise isolation.

---

### 57. Container Non-Root Execution

A production AI container should preferably run as a dedicated non-root user.

```text
Container
   ↓
Restricted User
   ↓
AI Process
```

This reduces the impact of application compromise.

---

### 58. Linux Capability Reduction

Containers should receive only the Linux capabilities they require.

```text
Default Capabilities
        ↓
Remove Unnecessary Capabilities
        ↓
Minimal Capability Set
```

---

### 59. Privileged Container Prevention

A security policy should prevent unnecessary privileged containers.

```text
AI Container
     ↓
Privileged = TRUE
     ↓
SECURITY POLICY
     ↓
DENY
```

---

### 60. Host Filesystem Protection

Avoid unnecessary host filesystem mounts.

Particularly sensitive resources should not be exposed to the AI workload.

Examples include:

* Host configuration.
* Host credentials.
* System directories.
* Container runtime sockets.

---

### 61. Container Runtime Socket Protection

Access to a container runtime socket can provide powerful control over the host.

Therefore:

```text
AI Container
     X
     ↓
Container Runtime Socket
```

Access should be denied unless explicitly required and strongly controlled.

---

### 62. Read-Only Container Filesystem

Where possible:

```text
Container Filesystem
       ↓
READ ONLY
```

Temporary writes should use controlled temporary storage.

---

### 63. Temporary Storage Isolation

Each AI task should ideally have an isolated workspace.

```text
Task A → Workspace A
Task B → Workspace B
Task C → Workspace C
```

This prevents accidental or malicious cross-task contamination.

---

### 64. Container Image Scanning

Before deployment:

```text
Image
 ↓
Vulnerability Scan
 ↓
Configuration Scan
 ↓
Malware / Integrity Checks
 ↓
Security Approval
```

---

### 65. Container Image Lifecycle

A mature lifecycle is:

```text

 ↓

 ↓
Test
 ↓
Sign
 ↓
Store
 ↓
Deploy
 ↓
Monitor
 ↓
Retire
```

### 66. Kubernetes AI Workloads

Kubernetes can provide orchestration and isolation for AI workloads.

```text
Kubernetes Cluster
│
├── AI Namespace
├── Model Serving
├── Tool Services
└── Monitoring
```

Security controls must be applied at both cluster and workload levels.

---

### 67. Kubernetes Namespace Isolation

Namespaces can logically separate workloads.

```text
Cluster
├── Production AI
├── Development AI
├── Testing AI
└── Monitoring
```

However, namespaces alone should not be treated as complete security isolation.

---

### 68. Kubernetes Network Policies

Network policies can restrict pod-to-pod communication.

```text
AI Pod
 ↓
NetworkPolicy
 ├── Model Service → ALLOW
 ├── Logging → ALLOW
 ├── Database → CONDITIONAL
 └── Admin Network → DENY
```

---

### 69. Kubernetes RBAC

Role-Based Access Control should restrict administrative actions.

```text
Developer
 ↓
Limited Role

AI Service Account
 ↓
Runtime Role

Administrator
 ↓
Privileged Role
```

Permissions should be separated by responsibility.

---

### 70. Dedicated AI Service Accounts

Each workload should have an appropriate service identity.

```text
AI Application
 ↓
AI Service Account
 ↓
Specific Permissions
```

Avoid shared administrative identities.

---

### 71. Kubernetes Secrets

Secrets should not be unnecessarily embedded in:

* Container images.
* Source code.
* Configuration files.
* Prompts.
* Model artifacts.

Instead, use controlled secret-management mechanisms.

---

### 72. Pod Security

AI pods should use restrictive security settings.

Controls can include:

* Non-root execution.
* No privilege escalation.
* Restricted capabilities.
* Read-only filesystem.
* Restricted host access.
* Controlled device access.

---

### 73. Host Network Restrictions

AI workloads should avoid host networking unless there is a justified requirement.

```text
AI Pod
  X
  ↓
Host Network

AI Pod
  ↓
Isolated Pod Network
```

---

### 74. Host PID and IPC Restrictions

AI containers should not automatically have access to host processes or inter-process communication mechanisms.

```text
Container
   X
Host Processes
```

This helps preserve workload boundaries.

---

### 75. Resource Quotas

Kubernetes or equivalent infrastructure should enforce resource quotas.

```text
AI Workload
├── CPU Limit
├── Memory Limit
├── GPU Limit
└── Storage Limit
```

---

### 76. GPU Resource Allocation

GPU resources should be explicitly assigned.

```text
AI Workload A
      ↓
GPU Allocation

AI Workload B
      ↓
Separate / Partitioned Allocation
```

The organization should understand the isolation properties of its chosen GPU-sharing architecture.

---

### 77. GPU Driver Security

GPU drivers are part of the trusted computing environment.

Security teams should monitor:

* Driver vulnerabilities.
* Supported versions.
* Compatibility.
* Configuration.
* Privilege requirements.

---

### 79. Network Segmentation

AI infrastructure should be placed in appropriate security zones.

Possible zones include:

* Public access zone.

* Tool execution zone.
* Data zone.
* Management zone.

### 80. Management Plane Separation

The management plane should be separated from the inference plane.

```text
Inference Plane
      X
      │
Management Plane
```

An AI request should not provide a pathway to administrative infrastructure.

Administrative access should require:

* Strong authentication.
* Least privilege.
* Privileged access management.
* Logging.
* Session monitoring where appropriate.

* DNS logging.

### 88. Data Loss Prevention

### 89. Internal Network Access

Prefer:

### 101. Runtime Threat Detection

AI runtime security requires continuous detection of abnormal activity.

The security team should monitor:

* Unexpected processes.
* Unexpected network connections.
* Unauthorized file access.
* Privilege escalation.
* Unusual resource consumption.
* Unexpected tool execution.
* Changes to model artifacts.
* Configuration changes.

```text
AI Runtime
    ↓
Telemetry
    ↓
Detection
    ↓
Risk Analysis
    ↓
Alert / Response
```

---

### 176. Sample GRC Interview Question

**Answer:**

### 177. Sample Security Architect Question

**Question:**

**Answer:**

> I would not automatically allow unrestricted Internet access. ### 178. Sample Agentic AI Question

**Question:**

> How would you secure an autonomous AI agent?

**Answer:**

> I would separate the agent's reasoning from execution. The agent would have a dedicated identity, limited capabilities, restricted tools, controlled network access, and an isolated execution environment. High-impact actions would require additional authorization or human approval. I would also impose rate, resource, and transaction limits and continuously monitor the agent's behavior.

### 179. Sample Incident Question

**Answer:**

I would preserve relevant evidence, revoke or rotate associated credentials, investigate the runtime and surrounding infrastructure, identify the root cause, and rebuild from a trusted image or artifact. Before restoring service, I would validate that the security weakness has been addressed.

When an AI workload is retired:

* Disable the runtime.
* Revoke identities.
* Remove credentials.
* Archive required evidence.
* Secure or delete data according to policy.
* Remove network access.
* Retire model artifacts where appropriate.

```text
Retirement
 ↓
Access Revoked
 ↓
Credentials Removed
 ↓
Data Handled
 ↓
Runtime Decommissioned
```

### 197. Security Architect-Level Explanation

For a Security Architect interview:

> **My architecture principle is that the model should never become an unrestricted infrastructure principal. I would place the model inside a hardened runtime, separate reasoning from execution, use workload identity and least privilege, restrict network and filesystem access, mediate tool calls through authorization boundaries, and continuously monitor the runtime. The architecture should also support rapid isolation, credential revocation, and trusted rebuild if compromise occurs.**

### 199. The Most Important Principle

The most important concept to remember is:

> **An AI runtime should be designed on the assumption that the model, its inputs, or its generated actions may eventually become compromised.**

Therefore, the infrastructure must remain secure **even when the AI component cannot be trusted**.
