# 07.20 — Designing and Assessing a Secure AI Architecture

## Part 1

### 1. Introduction to Designing and Assessing a Secure AI Architecture

Designing a secure AI architecture means integrating security, privacy, governance, and risk management into the AI system from the beginning.

The objective is not simply to build an AI system that functions.

The objective is to build an AI system that is:

* Secure.
* Resilient.
* Governed.
* Privacy-aware.
* Compliant.
* Auditable.
* Risk-appropriate.

The fundamental principle is:

> **Security must be designed into the AI architecture rather than added after deployment.**

---

A structured architecture lifecycle can be represented as:


---

### 3. Architecture Design vs Architecture Assessment

These are related but different activities.

**Architecture design** asks:

> How should the AI system be built securely?

**Architecture assessment** asks:

> Does the proposed or existing AI system actually meet the required security standards?

```text

   ├── API
   ├── AI Gateway
   ├── Agent
   ├── Model Endpoint
   └── Administration
```

Reducing unnecessary attack surface is an important architectural objective.

### 21. Prompt Attack Surface

AI applications introduce a unique input surface: natural-language instructions.

Attackers may attempt to manipulate the system through:

* Direct prompts.
* Uploaded documents.
* Retrieved content.
* Tool responses.
* External web content.

Therefore, prompt handling should be included in threat modeling.

### 29. Zero Trust Principle

AI systems should not automatically trust:

* Users.
* Applications.
* Agents.
* Models.
* Networks.
* Data sources.

Trust should be explicitly established and continuously evaluated where appropriate.

---

### 30. Least Privilege Principle

Every identity and component should receive only the permissions required for its function.

```text
Required Access
      ↓
     GRANT

Unnecessary Access
      ↓
     DENY
```

---

### 31. Defense-in-Depth Principle

Security should not depend on a single control.

```text

 ↓
Network
 ↓
Gateway
 ↓
Application
 ↓
Data
 ↓
Model
 ↓
Monitoring
```

Multiple layers reduce the likelihood of total control failure.

---

### 32. Secure-by-Design Principle

Security requirements should be established before implementation.

Weak approach:

```text

 ↓
Deploy
 ↓
Security Review
```

Better approach:

```text
Requirements
 ↓
Threat Model
 ↓
Architecture
 ↓
Security Controls
 ↓
Build
 ↓
Test
 ↓
Deploy
```

---

### 33. Data Minimization Principle

The AI system should process only the information required for its business purpose.

This reduces:

* Privacy exposure.
* Data leakage.
* Compliance risk.
* Attack impact.

---

### 34. Separation of Duties

Critical AI activities should not necessarily be controlled by one individual.

Example:

```text
Developer
   ↓
Builds AI Application

Security
   ↓
Assesses Security

Business Owner
   ↓

```

---

### 35. Fail-Secure Principle

When a security control fails, the system should avoid creating unintended access.

Example:

```text
Authorization Service
        ↓
     FAILURE
        ↓
Access Denied
```

The exact behavior should be balanced against availability and business continuity requirements.

### 50. Secure AI Architecture Design Method

A practical method is:

```text
1. Understand the Use Case
2. Identify Stakeholders
3. Define System Boundary
4. Identify Data
5. Map Data Flows
6. Identify Assets
7. Identify Trust Boundaries
8. Threat Model
9. Assess Risk
10. Define Security Requirements
11. Select Architecture Patterns
12. Design Controls
13. Document Architecture
14. Validate Security
15. Obtain Approval
```

The core principle is:

> **A secure AI architecture is created by systematically translating the business use case and AI risk profile into security requirements, architectural controls, and verifiable assurance activities.**

From a GRC perspective, the architecture is not considered complete merely because the technical components are deployed. It is complete when the organization can demonstrate **why the architecture was chosen, what risks it addresses, which controls are implemented, who owns those controls, how they are tested, what evidence exists, and what residual risks remain.**

### 51. Architecture Security Requirements

Once the AI use case, assets, data flows, and threats have been identified, the next step is to translate the findings into **specific security requirements**.

A requirement should describe the security outcome that the architecture must achieve.

For example:

> **Only authorized users and approved AI workloads may access restricted enterprise data.**

This requirement can then be translated into technical controls.

```text id="8q2m7v"
Security Requirement
        ↓
Control Objective
        ↓
Architecture Control
        ↓
Technical Implementation
        ↓
Verification
```

---

### 52. Functional vs Security Requirements

AI architecture requirements should distinguish between what the system **must do** and how it **must be protected**.

**Functional requirement:**

> The AI assistant must retrieve approved HR policies.

**Security requirement:**

> The AI assistant must retrieve only HR policies that the requesting user is authorized to access.

Both are necessary.

---

### 53. Security Requirements by Layer

Requirements can be organized by architecture layer.

| Layer          | Example Requirement                                        |
| -------------- | ---------------------------------------------------------- |
| Identity       | Users must authenticate using approved identity mechanisms |
| Access         | Permissions must follow least privilege                    |
| Application    | Inputs and outputs must be validated                       |
| Data           | Sensitive data must be protected                           |
| Model          | Only approved models may be used                           |
| Agent          | Tools must be explicitly authorized                        |
| Network        | AI workloads must use controlled network paths             |
| Infrastructure | Workloads must follow secure baselines                     |
| Monitoring     | Security-relevant activity must be logged                  |
| Resilience     | Critical AI services must have recovery capabilities       |

---

### 100. Secure AI Architecture Assessment Framework

A practical assessment sequence is:


For GRC, the assessment should ultimately produce a defensible chain from **risk → requirement → control → evidence → finding → remediation → residual risk**.

### 199. Designing and Assessing a Secure AI Architecture — Interview Model

For a GRC or cybersecurity interview, a strong answer can be structured around seven steps:

```text id="r6m2q9"
1. Understand the Business Use Case
2. Classify the AI Risk
3. Map Data and Trust Boundaries
4. Threat Model the Architecture
5. Design Risk-Based Controls
6. Validate Through Testing and Evidence
7. Continuously Monitor and Reassess
```

A concise professional explanation would be:

> **“When designing or assessing a secure AI architecture, I start with the business use case and determine the AI system's risk profile. I then identify the data, assets, trust boundaries, integrations, models, and agent capabilities. From there I perform threat modeling and translate the identified risks into security requirements and architectural controls. I validate those controls through configuration review, security testing, and evidence assessment. Finally, I evaluate residual risk, document exceptions, obtain the appropriate approval, and establish continuous monitoring and reassessment because AI architectures evolve over time.”**
