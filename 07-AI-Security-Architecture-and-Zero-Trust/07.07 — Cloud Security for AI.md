# 07.07 — Cloud Security for AI

## Part 1 — Foundations, Cloud Shared Responsibility, and AI Cloud Architecture

### 1. Cloud Security for AI

Cloud security for AI is the application of cloud security principles to AI workloads, models, data, identities, APIs, infrastructure, and supporting services.

AI workloads deployed in cloud environments may depend on:

* Compute instances.
* GPU infrastructure.
* Containers.
* Kubernetes.
* Object storage.
* Databases.
* Model registries.
* AI platforms.
* APIs.
* Identity services.
* Key-management services.
* Monitoring platforms.

The security architecture must therefore protect both the **AI workload** and the **cloud services supporting it**.

---

### 2. Why Cloud Security for AI Is Different

Traditional cloud applications already have significant security requirements, but AI introduces additional concerns.

An AI workload may involve:

```text
User
 ↓
Application
 ↓
AI API
 ↓
Model
 ↓
Vector Database
 ↓
Enterprise Data
 ↓
External Services
```

Each component may exist in a different cloud service or security boundary.

This increases the number of identities, interfaces, dependencies, and trust relationships that must be secured.

---

### 3. AI Cloud Attack Surface

The cloud-based AI attack surface can include:

* Cloud accounts.
* Subscriptions.
* Projects.
* Virtual networks.
* GPU instances.
* Containers.
* Kubernetes clusters.
* Object storage.
* Databases.
* Model repositories.
* AI APIs.
* Serverless functions.
* IAM roles.
* Service accounts.
* Secrets.
* CI/CD pipelines.
* Third-party integrations.

A weakness in any of these areas can potentially affect the AI workload.

---

### 4. Cloud AI Architecture

A simplified enterprise AI cloud architecture can be represented as:

```text
                    USERS
                      │
                      ↓
               Identity Provider
                      │
                      ↓
                API Gateway
                      │
                      ↓
              AI Application
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       AI Model    Data Store   AI APIs
          │           │           │
          └───────────┼───────────┘
                      ↓
                Cloud Platform
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       Compute      Network     Storage
          │           │           │
          └───────────┼───────────┘
                      ↓
               Security Services
```

Security controls should exist across all layers.

---

### 5. Cloud Shared Responsibility Model

Cloud security generally follows a shared-responsibility model.

The cloud provider secures certain aspects of the underlying platform, while the customer remains responsible for other areas.

Conceptually:

```text
Cloud Provider
├── Physical Infrastructure
├── Data Center
├── Hardware
├── Core Cloud Services
└── Hypervisor / Platform Components

Customer
├── Data
├── Identities
├── Permissions
├── Applications
├── Configurations
├── Workloads
└── Security Policies
```

The exact responsibility boundary depends on the cloud service being consumed.

---

### 6. Shared Responsibility for AI

AI introduces additional customer responsibilities.

For example, an organization using a managed AI service may still be responsible for:

* Prompt security.
* Data classification.
* Data-access permissions.
* Application security.
* AI API authentication.
* Model configuration.
* Logging.
* Retention.
* User authorization.
* Third-party integration security.

Using a managed AI service does not transfer all security responsibility to the provider.

---

### 7. Infrastructure as a Security Boundary

Cloud infrastructure should be treated as part of the AI security architecture.

Important components include:

```text
Cloud Account
      ↓
Network
      ↓
Compute
      ↓
Storage
      ↓
AI Workload
```

A weakness at an infrastructure layer can affect the confidentiality, integrity, or availability of the AI workload.

---

### 8. Cloud Account Structure

Organizations should establish appropriate separation between:

* Development.
* Testing.
* Staging.
* Production.
* Security.
* Shared services.

For example:

```text
Enterprise Cloud
│
├── Development
├── Testing
├── Staging
├── Production
└── Security / Monitoring
```

This separation reduces the likelihood that compromise of one environment directly compromises another.

---

### 9. AI Production Isolation

Production AI workloads should have stronger controls than development workloads.

A typical model is:

```text
Development
   ↓
Lower Trust

Testing
   ↓
Controlled Trust

Production
   ↓
Highest Security Requirements
```

Production should not inherit unnecessary permissions or network access from development environments.

---

### 10. Cloud Landing Zone

A cloud landing zone provides a standardized foundation for cloud workloads.

It may establish:

* Account structure.
* Network architecture.
* Identity.
* Logging.
* Security monitoring.
* Policy enforcement.
* Resource organization.
* Governance.

AI workloads should preferably be deployed into an established secure cloud foundation rather than independently creating unmanaged cloud environments.

---

### 11. AI Landing Zone

An AI-specific landing zone can extend the standard cloud landing zone.

It may provide:

```text
Secure Cloud Foundation
        ↓
AI Platform Services
        ↓
Approved AI Workloads
        ↓
Approved Models
        ↓
Approved Data Sources
```

This creates a controlled environment for enterprise AI adoption.

---

### 12. Cloud Governance for AI

Cloud governance should define:

* Which cloud services may be used.
* Which AI services are approved.
* Which regions may host AI data.
* Which data classifications may enter AI services.
* Who can deploy AI workloads.
* Which identities may access AI resources.
* Required logging.
* Required encryption.
* Required security assessments.

---

### 13. Approved Cloud Services

Organizations should maintain an approved-service model.

For example:

```text
Approved
✓ Managed AI Platform
✓ Enterprise Object Storage
✓ Approved Database
✓ Enterprise Key Management

Restricted
△ Experimental AI Service
△ Unapproved Marketplace Image

Prohibited
✗ Unapproved Public AI Endpoint
✗ Unmanaged Cloud Account
```

The actual classification should be based on organizational policy and risk.

---

### 14. Cloud Service Discovery

Security teams should maintain visibility into cloud services being used by AI workloads.

Discovery should identify:

* Cloud provider.
* Account.
* Region.
* Service.
* Owner.
* Data classification.
* AI workload.
* Internet exposure.
* Identity.
* Security controls.

Unknown cloud resources represent a governance and security risk.

---

### 15. Shadow AI in the Cloud

Shadow AI can occur when employees or teams independently deploy AI services without enterprise approval.

Examples include:

* Personal cloud AI accounts.
* Unapproved AI APIs.
* Temporary GPU instances.
* Public model endpoints.
* Unapproved cloud storage.
* Experimental AI platforms.

These resources may process enterprise information without appropriate security controls.

---

### 16. Cloud Asset Inventory

AI-related cloud assets should be included in a centralized inventory.

Example:

| Asset          | Type     | Environment | Owner     | Classification |
| -------------- | -------- | ----------- | --------- | -------------- |
| AI-Service-01  | VM       | Production  | AI Team   | High           |
| Model-Registry | Storage  | Production  | ML Team   | Restricted     |
| VectorDB-01    | Database | Production  | Data Team | Confidential   |
| AI-Gateway     | API      | Production  | Platform  | High           |

The inventory provides the foundation for security assessment and governance.

---

### 17. Cloud Resource Tagging

Cloud resources should use standardized metadata.

Example:

```text
Application = CustomerAI
Environment = Production
Owner = AI Platform
DataClass = Confidential
Criticality = High
BusinessUnit = Customer Operations
```

Tags can support:

* Governance.
* Cost management.
* Security monitoring.
* Incident response.
* Automated policy enforcement.

---

### 18. AI Cloud Data Classification

AI workloads should process data according to its classification.

A simplified model may be:

```text
Public
  ↓
Internal
  ↓
Confidential
  ↓
Restricted
```

The higher the sensitivity, the stronger the required controls.

---

### 19. Data Residency

Cloud AI workloads may process or store data across geographic regions.

Organizations should determine:

* Where data is stored.
* Where data is processed.
* Where backups are stored.
* Where logs are stored.
* Where model processing occurs.
* Where support personnel may access data.

Data residency requirements can influence cloud architecture.

---

### 20. Data Sovereignty

Data sovereignty concerns the legal and regulatory implications associated with the jurisdiction where data is stored or processed.

For AI workloads, this can become important when:

```text
Customer Data
      ↓
Cloud AI Service
      ↓
Processing Region
      ↓
Storage Region
```

The processing and storage locations should align with applicable organizational and regulatory requirements.

---

### 21. Cloud Region Selection

Region selection should consider:

* Data residency.
* Regulatory requirements.
* Service availability.
* Disaster recovery.
* Latency.
* Security capabilities.
* Business continuity.

The nearest cloud region is not necessarily the appropriate region for sensitive AI workloads.

---

### 22. Availability Zones

High-value AI workloads may use multiple availability zones.

```text
                AI Service
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
       Zone A               Zone B
          │                   │
       Compute              Compute
```

This can improve resilience against localized infrastructure failures.

---

### 23. Multi-Region AI Architecture

For highly critical workloads, organizations may consider multiple regions.

```text
Primary Region
      ↓
AI Workload
      ↓
Replication / Backup
      ↓
Secondary Region
```

However, multi-region architecture introduces additional considerations for:

* Data residency.
* Encryption keys.
* Identity.
* Replication.
* Network security.
* Compliance.

---

### 24. Cloud Network Architecture

AI workloads should operate within a controlled network architecture.

Typical components include:

* Virtual networks.
* Subnets.
* Security groups.
* Network ACLs.
* Firewalls.
* Private endpoints.
* Load balancers.
* API gateways.
* Egress controls.

---

### 25. Public Versus Private AI Workloads

A key architecture decision is whether the workload requires Internet exposure.

Example:

```text
Public AI API
     ↓
Internet
     ↓
API Gateway
     ↓
AI Workload
```

versus:

```text
Enterprise Network
       ↓
Private Endpoint
       ↓
AI Workload
```

Where Internet exposure is unnecessary, private connectivity generally reduces the attack surface.

---

### 26. Private AI Endpoints

Private endpoints can allow workloads to communicate with cloud services without traversing the public Internet.

Example:

```text
AI Workload
     ↓
Private Network
     ↓
Cloud AI Service
```

This can reduce exposure to Internet-based threats.

---

### 27. Internet Exposure Assessment

Every AI cloud resource should be assessed for unnecessary public exposure.

Questions include:

* Does the service require Internet access?
* Is the endpoint publicly reachable?
* Is authentication mandatory?
* Is traffic filtered?
* Is WAF protection required?
* Is egress restricted?
* Can the resource be made private?

---

### 28. Cloud Firewall Controls

Cloud firewalls can control traffic entering and leaving AI workloads.

A policy might follow:

```text
Inbound:
Approved API Gateway → AI Workload ✓
Internet → AI Workload ✗

Outbound:
AI Workload → Approved Database ✓
AI Workload → Approved AI API ✓
AI Workload → Unknown Internet ✗
```

Firewall rules should follow least privilege.

---

### 29. Security Groups

Security groups or equivalent cloud controls should permit only required traffic.

For example:

```text
AI Workload
   ↓
TCP 443 → Approved API ✓
TCP 5432 → Approved Database ✓
TCP 22 → Internet ✗
```

Unused ports should remain closed.

---

### 30. Cloud Network Segmentation

AI workloads can be segmented according to:

* Environment.
* Business function.
* Data sensitivity.
* Criticality.
* Trust level.
* Internet exposure.

Example:

```text
Cloud Network
│
├── Public Services
├── Application Services
├── AI Services
├── Data Services
└── Management Services
```

Each segment should have explicitly defined communication paths.

---

### 31. AI and Data Tier Separation

AI compute should not automatically have unrestricted access to all enterprise data.

A stronger architecture is:

```text
AI Workload
     ↓
Authorized Data API
     ↓
Data Service
     ↓
Approved Dataset
```

This allows data access to be controlled at the service boundary.

---

### 32. Cloud Identity Architecture

Identity is one of the most important security controls for cloud AI.

Relevant identities include:

* Human users.
* Administrators.
* AI workloads.
* Service accounts.
* CI/CD pipelines.
* Cloud services.
* External integrations.

Each should have an appropriate identity and access model.

---

### 33. Human Identity

Human access should use enterprise identity services wherever possible.

Controls can include:

* Single sign-on.
* Multi-factor authentication.
* Conditional access.
* Role-based access control.
* Privileged access management.
* Access reviews.

---

### 34. Workload Identity

AI workloads should have dedicated identities.

```text
AI Workload
     ↓
Workload Identity
     ↓
Approved Resources
```

Avoid using a shared administrator identity for AI workloads.

---

### 35. Least Privilege in Cloud IAM

Cloud IAM permissions should be limited to required actions.

For example:

```text
AI-Service
   ✓ Read Model
   ✓ Read Approved Data
   ✓ Invoke Approved API
   ✗ Delete Database
   ✗ Modify IAM
   ✗ Create Administrator
```

This limits the impact of workload compromise.

---

### 36. Cloud IAM Role Design

Roles should reflect actual responsibilities.

Possible roles include:

* AI Developer.
* AI Engineer.
* AI Platform Administrator.
* Security Administrator.
* Data Owner.
* Model Approver.
* Auditor.

Permissions should be separated according to business and security responsibilities.

---

### 37. Privileged Cloud Access

Cloud administrator access should be tightly controlled.

Controls may include:

* MFA.
* Privileged access management.
* Just-in-time access.
* Session logging.
* Approval workflows.
* Administrative monitoring.

Permanent unrestricted administrator access increases the blast radius of credential compromise.

---

### 38. Service Account Security

Service accounts should have:

* Defined ownership.
* Specific purpose.
* Limited permissions.
* Credential lifecycle management.
* Monitoring.
* Periodic review.

Unused service accounts should be disabled or removed.

---

### 39. Cloud API Authentication

AI workloads frequently communicate through APIs.

API access should use strong authentication such as:

* OAuth 2.0.
* Mutual TLS.
* Signed requests.
* Workload identities.
* Short-lived tokens.

The mechanism should match the service and risk.

---

### 40. Cloud API Authorization

Authentication answers:

> Who or what is calling?

Authorization answers:

> What is the caller allowed to do?

Both are necessary.

```text
Caller
 ↓
Authentication
 ↓
Identity Established
 ↓
Authorization
 ↓
Allowed Action
```

---

### 41. Cloud Secrets Management

Secrets should not be hardcoded into:

* Source code.
* Container images.
* Configuration files.
* Scripts.
* Infrastructure-as-code repositories.

Instead, use an appropriate centralized secrets-management mechanism.

---

### 42. Cloud Key Management

Cloud key-management services can provide controlled management of encryption keys.

They can support:

* Key generation.
* Key storage.
* Key rotation.
* Access control.
* Audit logging.
* Key lifecycle management.

Sensitive AI workloads should use key-management controls appropriate to their risk.

---

### 43. Customer-Managed Keys

For higher-security requirements, an organization may use customer-managed encryption keys.

This can provide greater control over:

* Key ownership.
* Rotation.
* Access.
* Revocation.
* Auditability.

The exact capabilities depend on the cloud service.

---

### 44. Encryption in AI Cloud Environments

Encryption should be considered for:

```text
Data in Transit
       +
Data at Rest
       +
Backup Data
       +
Model Artifacts
       +
Logs
       +
Temporary Storage
```

Encryption requirements should follow data classification and risk.

---

### 45. Cloud Storage Security

AI workloads frequently use object storage for:

* Training datasets.
* Model files.
* Logs.
* Documents.
* Embeddings.
* Backups.

Storage should have:

* Strong IAM.
* Encryption.
* Access logging.
* Versioning where appropriate.
* Retention controls.
* Public-access prevention.

---

### 46. Public Storage Exposure

One of the significant cloud risks is accidental public exposure.

Example:

```text
Restricted AI Dataset
        ↓
Incorrect Storage Policy
        ↓
Public Internet
        ↓
Unauthorized Access
```

Automated controls should detect and prevent unintended public exposure.

---

### 47. Cloud Database Security

AI workloads may interact with:

* Relational databases.
* NoSQL databases.
* Vector databases.
* Data warehouses.
* Data lakes.

Database access should use:

* Strong authentication.
* Least privilege.
* Encryption.
* Network restrictions.
* Monitoring.
* Appropriate data-access policies.

---

### 48. Vector Database Security

Vector databases can contain representations derived from sensitive enterprise information.

Security should therefore consider:

* Access control.
* Tenant isolation.
* Encryption.
* Query authorization.
* Data retention.
* Backup security.
* Administrative access.

A vector database should be treated as a potentially sensitive data repository.

---

### 49. AI Model Storage

Cloud model repositories should protect:

* Model artifacts.
* Model versions.
* Configuration.
* Metadata.
* Evaluation results.
* Deployment packages.

Unauthorized modification of a model can affect the behavior of production AI systems.

---

### 50. Model Artifact Integrity

Model artifacts should ideally have integrity mechanisms such as:

```text
Model
 ↓
Hash
 ↓
Signature
 ↓
Registry
 ↓
Verification
 ↓
Deployment
```

This helps detect unauthorized modification or substitution.

---

### 51. Cloud Container Security

AI workloads deployed in containers should use:

* Approved base images.
* Vulnerability scanning.
* Minimal images.
* Non-root execution.
* Restricted capabilities.
* Image signing.
* Runtime monitoring.

Cloud infrastructure does not eliminate the need for container security.

---

### 52. Kubernetes AI Security

AI workloads running on Kubernetes require security across:

```text
Cluster
 ↓
Node
 ↓
Namespace
 ↓
Pod
 ↓
Container
 ↓
Application
```

Controls should address both Kubernetes infrastructure and the AI workloads operating within it.

---

### 53. Kubernetes Namespace Isolation

Namespaces can provide logical separation between workloads.

Example:

```text
Cluster
│
├── AI-Development
├── AI-Testing
├── AI-Production
└── Security
```

Additional network and authorization controls are still required because namespaces alone should not be treated as complete isolation.

---

### 54. Kubernetes RBAC

Kubernetes role-based access control should follow least privilege.

A developer who needs access to AI application logs should not automatically receive:

```text
Cluster Administrator
```

Permissions should correspond to actual operational requirements.

---

### 55. Kubernetes Network Policies

Network policies can define which workloads may communicate.

```text
AI Pod
 ↓
Approved API ✓

AI Pod
 ↓
Approved Database ✓

AI Pod
 ↓
Unrelated Namespace ✗
```

This limits lateral movement.

---

### 56. Cloud AI Workload Isolation

Higher-risk workloads may require stronger isolation.

Possible approaches include:

* Dedicated nodes.
* Dedicated clusters.
* Dedicated accounts.
* Dedicated networks.
* Confidential computing where appropriate.
* Hardware-backed isolation.

The required level should be based on risk.

---

### 57. Dedicated GPU Infrastructure

Sensitive or high-value AI workloads may use dedicated GPU infrastructure.

Benefits can include:

* Reduced workload sharing.
* Greater resource control.
* Reduced cross-workload exposure.
* More predictable performance.

However, dedicated infrastructure also introduces additional operational and cost considerations.

---

### 58. Confidential Computing

Confidential computing technologies can provide protections for data while it is being processed through hardware-backed trusted execution environments.

Conceptually:

```text
Encrypted Data
      ↓
Trusted Execution Environment
      ↓
Protected Processing
      ↓
Result
```

This can be relevant for highly sensitive AI workloads where protection during processing is important.

---

### 59. AI Training Environment Security

Training environments may have broad access to:

* Large datasets.
* Model repositories.
* GPUs.
* Development tools.
* External libraries.

Training environments should therefore be strongly controlled.

Development convenience should not justify unrestricted access to production data.

---

### 60. AI Inference Environment Security

Inference environments should be designed for controlled production execution.

Typical controls include:

* Dedicated identity.
* Restricted data access.
* API authentication.
* Network segmentation.
* Rate limiting.
* Runtime monitoring.
* Model integrity verification.

Inference workloads should expose only the interfaces required by legitimate consumers.

# 07.07 — Cloud Security for AI

## Part 2 — Cloud Identity, Network Security, Data Protection, and AI Platform Security

### 61. Cloud Identity as the Primary Security Boundary

In cloud environments, identity frequently becomes more important than traditional network location.

For AI workloads, identity should answer:

* Who is accessing the workload?
* Which workload is making the request?
* Which service is being accessed?
* What action is being requested?
* Is the request authorized?

A secure model is:

```text
Request
   ↓
Identity
   ↓
Authentication
   ↓
Authorization
   ↓
Policy Evaluation
   ↓
Resource Access
```

---

### 62. Human and Workload Identity Separation

Human identities and workload identities should be separated.

```text
Human User
    ↓
Enterprise Identity

AI Workload
    ↓
Workload Identity
```

An AI service should not authenticate to cloud resources using a developer's personal account.

---

### 63. Workload Identity Federation

Where supported, workload identity federation can allow an external or platform workload to obtain temporary cloud credentials without storing long-lived cloud access keys.

Conceptually:

```text
AI Workload
    ↓
Federated Identity
    ↓
Cloud Identity Provider
    ↓
Temporary Credential
    ↓
Cloud Resource
```

This reduces the need for static credentials inside AI workloads.

---

### 64. Long-Lived Cloud Credentials

Long-lived access keys create significant risk if stored inside:

* Containers.
* Source repositories.
* CI/CD variables.
* Scripts.
* Configuration files.

A compromised AI workload could expose the credential and allow unauthorized cloud access.

Short-lived authentication should be preferred where technically feasible.

---

### 65. Conditional Access for AI Administration

Administrative access to AI cloud resources can be evaluated using contextual conditions such as:

* User identity.
* Device security posture.
* Location.
* Authentication strength.
* Risk level.
* Requested resource.
* Time or session conditions.

This provides stronger protection than relying solely on a username and password.

---

### 66. Privileged Identity Management

Privileged cloud access should preferably be activated only when required.

```text
Administrator
     ↓
Access Request
     ↓
Approval / Policy
     ↓
Temporary Privilege
     ↓
AI Cloud Resource
     ↓
Privilege Expires
```

This reduces the exposure created by permanently assigned administrative privileges.

---

### 67. Role-Based Access Control

RBAC should map permissions to defined roles.

Example:

```text
AI Developer
 ├── Deploy to Development
 ├── Read Development Logs
 └── Access Approved Models

AI Platform Administrator
 ├── Manage AI Infrastructure
 └── Manage Platform Configuration

Security Administrator
 ├── Review Security Events
 └── Manage Security Policies
```

No role should receive permissions simply because they are convenient.

---

### 68. Attribute-Based Access Control

ABAC can evaluate attributes in addition to static roles.

For example:

```text
User = AI Engineer
Environment = Production
DataClass = Restricted
Action = Read
Risk = Low
```

A policy engine can use these attributes to determine whether access should be granted.

---

### 69. Resource-Based Policies

Cloud resources may also have their own access policies.

Examples include policies governing:

* Object storage.
* AI services.
* Databases.
* Queues.
* Secrets.
* Model repositories.

Security teams should understand how identity policies and resource policies interact.

---

### 70. Policy Conflicts

Cloud IAM policies can become complex when multiple controls apply.

For example:

```text
Identity Policy → Allow
Resource Policy → Allow
Network Policy → Deny
```

The resulting access decision depends on the cloud provider's policy evaluation model.

Security teams must understand the actual enforcement logic rather than assuming that one policy determines access.

---

### 71. Least Privilege for AI Services

An AI workload should have only the permissions required for its function.

Example:

```text
Customer AI
   ✓ Read Customer Knowledge Base
   ✓ Invoke Approved Model
   ✓ Write Application Logs
   ✗ Modify IAM
   ✗ Delete Storage
   ✗ Create Cloud Accounts
```

The objective is to minimize the blast radius of compromise.

---

### 72. Permission Boundaries

Where supported, permission boundaries or equivalent mechanisms can constrain the maximum permissions that an identity may receive.

This creates an additional guardrail against excessive privilege assignment.

---

### 73. Cloud Network Architecture

A secure AI cloud architecture should separate network zones according to trust and function.

```text
Internet
   ↓
WAF / API Gateway
   ↓
Application Zone
   ↓
AI Workload Zone
   ↓
Data Zone
```

Management infrastructure should have separate and restricted access paths.

---

### 74. Private Subnets

AI workloads that do not require direct Internet exposure should preferably operate in private network segments.

```text
Internet
   ✗
    │
Private Network
    │
    ↓
AI Workload
```

Required external communication can be routed through controlled security services.

---

### 75. Controlled Internet Egress

Private AI workloads may still require outbound communication.

For example:

```text
AI Workload
     ↓
Egress Firewall
     ↓
Approved Destination
```

The workload should not automatically receive unrestricted Internet access simply because outbound communication is technically possible.

---

### 76. Egress Allowlisting

An allowlist can specify approved external destinations.

Example:

```text
AI Workload
   ├── Model Repository ✓
   ├── Approved SaaS API ✓
   ├── Enterprise API ✓
   └── Unknown Internet ✗
```

This can significantly reduce data-exfiltration and command-and-control opportunities.

---

### 77. Ingress Restrictions

Inbound traffic should be restricted to approved sources.

```text
Approved API Gateway
        ↓
      AI API ✓

Unknown Internet
        ↓
      AI API ✗
```

Where public exposure is required, additional controls such as WAF, authentication, rate limiting, and threat detection should be considered.

---

### 78. Web Application Firewall

A WAF can protect Internet-facing AI applications against common application-layer attacks.

Potential protections include:

* Malicious HTTP requests.
* Injection attempts.
* Protocol violations.
* Automated abuse.
* Excessive requests.

For AI APIs, WAF controls should complement rather than replace AI-specific security controls.

---

### 79. API Gateway

An API gateway can provide a controlled entry point to AI services.

```text
Client
  ↓
API Gateway
  ├── Authentication
  ├── Authorization
  ├── Rate Limiting
  ├── Logging
  └── Threat Filtering
        ↓
    AI Service
```

This creates a centralized security enforcement point.

---

### 80. AI API Rate Limiting

Rate limiting can prevent excessive requests from overwhelming an AI workload.

Controls may be based on:

* User.
* Application.
* API key.
* Workload.
* IP address.
* Tenant.

Rate limiting supports both availability and abuse prevention.

---

### 81. AI API Quotas

Quotas can limit resource consumption over a defined period.

For example:

```text
Tenant A
   ↓
10,000 requests/day

Tenant B
   ↓
5,000 requests/day
```

Quotas can protect shared AI infrastructure from uncontrolled consumption.

---

### 82. Tenant Isolation

Multi-tenant AI environments must prevent one customer or business unit from accessing another tenant's resources.

Isolation should apply to:

* Data.
* Models.
* Embeddings.
* Logs.
* API credentials.
* Configuration.
* Storage.
* Runtime resources.

* Metadata services.
* Container environments.
* Application logs.
* Source repositories.

AI agents can introduce additional cloud security concerns because an agent may:

### 256. Cloud AI Security Architecture Principles

The architecture should consistently apply:

1. **Least privilege** — grant only required access.
2. **Explicit trust** — do not assume trust based on location.
3. **Defense in depth** — use multiple security layers.
4. **Secure by default** — insecure configurations should require deliberate exceptions.
5. **Continuous verification** — continuously evaluate access and configuration.
6. **Data minimization** — expose only necessary data.
7. **Strong isolation** — separate workloads according to risk.
8. **Traceability** — maintain evidence of important actions.
9. **Resilience** — design for failure and compromise.
10. **Continuous improvement** — adapt controls as threats and architecture evolve.

### 257. Cloud AI Security Assessment Questions

A GRC or security architect should be able to ask:

**Identity**

* Who can access the AI workload?
* Which workload identity is being used?
* Are privileged permissions temporary?
* Are service accounts reviewed?

**Network**

* Is the AI workload publicly exposed?
* Are inbound and outbound connections restricted?
* Are sensitive services privately connected?
* Is segmentation implemented?

**Data**

* What data enters the AI service?
* What is its classification?
* Where is it processed?
* Where is it stored?
* Who can retrieve it?

**Model**

* Where is the model stored?
* How is integrity verified?
* Who can deploy it?
* Is the production version controlled?

**Cloud**

* Is the workload using approved cloud services?
* Is configuration continuously monitored?
* Are vulnerabilities managed?
* Is infrastructure deployed securely?

**Operations**

* Are logs centralized?
* Are AI-specific detections implemented?
* Can compromised workloads be isolated?
* Has recovery been tested?
