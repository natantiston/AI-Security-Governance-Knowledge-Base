# 07.18 — Secure AI Architecture Patterns

## Part 1

### 1. Introduction to Secure AI Architecture Patterns

Secure AI architecture patterns are **repeatable architectural approaches for designing AI systems with security controls embedded into their structure**.

Rather than treating security as an additional layer after implementation, secure architecture patterns establish security boundaries from the beginning.

The objective is:

> **Design AI systems so that trust, access, data movement, model interaction, and infrastructure dependencies are controlled by architecture.**

---

### 2. Why AI Architecture Patterns Matter

AI systems combine multiple technologies:

```text
Users
  ↓
Applications
  ↓
APIs
  ↓
AI Models
  ↓
Data
  ↓
Cloud / Infrastructure
```

Each connection creates a potential trust boundary.

Architecture patterns provide reusable ways to control those boundaries.

---

### 3. Secure-by-Design Architecture

A secure AI architecture should consider security during:

1. Requirements.
2. Architecture.
3. Development.
4. Deployment.
5. Operations.
6. Retirement.

```text
Requirements
     ↓
Threat Modeling
     ↓
Architecture
     ↓
Security Controls
     ↓
Implementation
     ↓
Validation
```

---

### 4. Defense-in-Depth Pattern

Defense in depth uses multiple independent security layers.

```text
┌──────────────────────────────┐
│ Identity Security            │
├──────────────────────────────┤
│ Application Security         │
├──────────────────────────────┤
│ API Security                 │
├──────────────────────────────┤
│ Network Security             │
├──────────────────────────────┤
│ Workload Security            │
├──────────────────────────────┤
│ Data Security                │
└──────────────────────────────┘
```

If one control fails, other controls continue to provide protection.

---

### 5. Zero Trust AI Architecture

A Zero Trust architecture does not automatically trust:

* Users.
* Devices.
* Applications.
* AI agents.
* Services.
* Networks.

Every access request should be evaluated.

```text
Request
  ↓
Identity
  ↓
Context
  ↓
Policy
  ↓
Authorization
  ↓
Resource
```

---

### 6. Zero Trust Workload Pattern

An AI workload should authenticate when communicating with another service.

```text
AI Application
      ↓
Workload Identity
      ↓
Policy Evaluation
      ↓
Approved Service
```

Network location alone should not determine trust.

---

### 7. Segmented AI Architecture

AI environments can be divided into security zones.

```text
Internet
   ↓
DMZ
   ↓
Application Zone
   ↓
AI Runtime Zone
   ↓
Data Zone
```

Each zone should have defined communication rules.

---

### 8. AI DMZ Pattern

Internet-facing AI services can be placed behind a controlled perimeter.

```text
Internet
   ↓
WAF / API Gateway
   ↓
AI DMZ
   ↓
Internal AI Services
```

This reduces direct exposure of internal AI infrastructure.

---

### 9. API Gateway Pattern

An API gateway can act as a centralized control point.

```text
Client
  ↓
API Gateway
  ↓
AI Service
  ↓
Model
```

The gateway can enforce:

* Authentication.
* Authorization.
* Rate limiting.
* Request validation.
* Logging.
* Routing.

---

### 10. AI Gateway Pattern

An AI gateway can provide centralized governance over multiple AI services.

```text
                 AI Gateway
                /    |    \
               /     |     \
             LLM     ML    AI API
```

This is useful where an organization operates multiple AI providers or models.

---

### 11. Centralized AI Control Plane

A central control plane can manage:

* Model access.
* AI policies.
* Provider routing.
* Usage.
* Security controls.
* Audit information.

```text
Users / Applications
         ↓
   AI Control Plane
      /       \
     ↓         ↓
Provider A   Provider B
```

---

### 12. Model Access Gateway

Sensitive models can be placed behind a dedicated access layer.

```text
Application
    ↓
Model Gateway
    ↓
Authorization
    ↓
Model Server
```

This prevents direct access to the model endpoint.

---

### 13. Retrieval-Augmented Generation Pattern

RAG architectures typically combine an AI model with enterprise data.

```text
User
 ↓
Application
 ↓
Retriever
 ↓
Vector Database
 ↓
Relevant Context
 ↓
LLM
 ↓
Response
```

Security must control the entire retrieval path.

---

### 14. Secure RAG Pattern

A secure RAG architecture adds authorization before retrieving information.

```text
User
 ↓
Authentication
 ↓
Authorization
 ↓
Retriever
 ↓
Permission-Filtered Data
 ↓
LLM
```

The model should not receive data that the user is not authorized to access.

---

### 15. RAG Data Isolation

RAG data should be logically separated where necessary.

```text
User A
 ↓
Authorized Documents A

User B
 ↓
Authorized Documents B
```

The retrieval system must enforce the appropriate access boundary.

---

### 16. Document-Level Authorization

Authorization should ideally be enforced at the document or data-object level when required.

```text
Query
 ↓
Identity
 ↓
Document Permissions
 ↓
Authorized Documents
 ↓
LLM
```

---

### 17. Retrieval Security Gateway

A retrieval security layer can enforce policies before information is passed to the model.

Potential checks include:

* User authorization.
* Data classification.
* Tenant.
* Document permissions.
* Sensitivity.
* Geographic restrictions.

---

### 18. Data Loss Prevention Pattern

DLP can inspect data entering or leaving an AI system.

```text
User Input
    ↓
DLP Inspection
    ↓
AI Service
    ↓
DLP Output Inspection
    ↓
User
```

---

### 19. Input Security Gateway

An input security gateway can inspect requests before they reach an AI model.

Controls may include:

* Prompt validation.
* Sensitive-data detection.
* Malware scanning.
* Rate limiting.
* Content policy.
* Authentication.

---

### 20. Output Security Gateway

AI responses can also be inspected before delivery.

```text
LLM
 ↓
Output Security
 ↓
DLP
 ↓
Policy Check
 ↓
User
```

This helps reduce accidental disclosure and unsafe outputs.

---

### 21. Dual-Gateway Pattern

A mature architecture can protect both directions.

```text
User
 ↓
Input Security
 ↓
AI Application
 ↓
LLM / RAG
 ↓
Output Security
 ↓
User
```

---

### 22. Sensitive Data Redaction Pattern

Sensitive information can be removed or transformed before reaching an external AI service.

```text
Enterprise Data
      ↓
Detection
      ↓
Redaction / Tokenization
      ↓
External AI
```

---

### 23. Tokenization Pattern

Sensitive values can be replaced with tokens.

Example:

```text
Original:
Customer Account = 123456789

Tokenized:
Customer Account = TOKEN-78231
```

The AI system may process the token rather than the original value.

---

### 24. Pseudonymization Pattern

Identifying information can be replaced with pseudonymous identifiers.

```text
Jonathan Morales
       ↓
Customer-47281
```

The mapping should remain protected and separately controlled.

---

### 25. External LLM Isolation Pattern

Organizations may isolate external AI providers from internal systems.

```text
Internal Network
      ↓
AI Security Gateway
      ↓
Controlled Internet
      ↓
External LLM
```

The external model does not receive unrestricted enterprise connectivity.

---

### 26. Enterprise LLM Proxy

An enterprise proxy can provide a controlled interface to external AI providers.

```text
Employee
   ↓
Enterprise AI Proxy
   ↓
Security Policies
   ↓
External LLM
```

This provides centralized control over enterprise AI usage.

---

### 27. Bring-Your-Own-Model Pattern

Organizations may deploy approved models internally.

```text
Enterprise Data
      ↓
Internal AI Platform
      ↓
Approved Model
      ↓
Enterprise Application
```

This can provide greater control over data and infrastructure.

---

### 28. Private Model Hosting

Sensitive models may be hosted in:

* Private cloud.
* Dedicated infrastructure.
* Controlled data centers.
* Restricted Kubernetes clusters.

Architecture should match organizational risk requirements.

---

### 29. Dedicated AI Environment

High-risk AI workloads may use dedicated infrastructure.

```text
Dedicated Network
      ↓
Dedicated Compute
      ↓
Dedicated GPU
      ↓
Dedicated Model
```

This can provide stronger isolation than shared infrastructure.

---

### 30. Multi-Tenant AI Architecture

When multiple customers or business units share an AI platform:

```text
                AI Platform
              /      |      \
             /       |       \
        Tenant A  Tenant B  Tenant C
```

Strong tenant isolation must exist across:

* Identity.
* Data.
* Models.
* Storage.
* Network.
* Logs.

---

### 31. Tenant Isolation Pattern

Tenant context should follow the request.

```text
User
 ↓
Tenant Identity
 ↓
AI Gateway
 ↓
Tenant Policy
 ↓
Tenant Data
 ↓
AI Model
```

---

### 32. Shared Model, Isolated Data

Multiple tenants may use the same model while maintaining separate data.

```text
Tenant A ─┐
Tenant B ─┼→ Shared Model
Tenant C ─┘

Data remains isolated.
```

This architecture requires strong authorization controls.

---

### 33. Dedicated Model per Tenant

Higher-risk environments may use dedicated models.

```text
Tenant A → Model A
Tenant B → Model B
Tenant C → Model C
```

This provides stronger separation but increases operational complexity.

---

### 34. Agent Isolation Pattern

AI agents may have tools that interact with enterprise systems.

A secure pattern limits each agent to explicitly authorized tools.

```text
AI Agent
   ↓
Tool Policy
 ┌─┼───────────────┐
 ↓ ↓               ↓
CRM API ✓      Admin API ✗
```

---

### 35. Agent Sandbox Pattern

Agents performing higher-risk operations can execute inside isolated environments.

```text
Agent
 ↓
Sandbox
 ↓
Approved Tools
 ↓
Controlled Environment
```

---

### 36. Human-in-the-Loop Pattern

Sensitive AI actions can require human approval.

```text
AI Agent
   ↓
Proposed Action
   ↓
Human Approval
   ↓
Enterprise System
```

This is especially valuable for high-impact operations.

---

### 37. Human-on-the-Loop Pattern

For lower-risk operations, humans may supervise rather than approve every action.

```text
AI Agent
 ↓
Automated Action
 ↓
Monitoring
 ↓
Human Oversight
```

The appropriate pattern depends on risk.

---

### 38. Least-Privilege Agent Pattern

AI agents should receive only the tools and permissions necessary to perform their assigned tasks.

```text
Agent
 ├── Read CRM ✓
 ├── Create Ticket ✓
 ├── Delete Customer ✗
 └── Modify IAM ✗
```

---

### 39. Agent Permission Broker

A permission broker can dynamically authorize agent actions.

```text
Agent Request
      ↓
Permission Broker
      ↓
Policy Evaluation
      ↓
Allow / Deny
      ↓
Tool
```

---

### 40. Tool Isolation Pattern

Tools used by an AI agent should be separated according to risk.

```text
Low Risk Tools
 ├── Search
 └── Read

High Risk Tools
 ├── Delete
 ├── Transfer
 └── Modify
```

High-risk tools should receive stronger controls.

---

### 41. Read-Only AI Pattern

Where possible, AI systems should initially operate with read-only permissions.

```text
AI
 ↓
Read Enterprise Data
 ↓
Generate Recommendation
```

Write operations can be introduced only when justified.

---

### 42. Approval-Based Write Pattern

AI-generated changes can be routed through an approval process.

```text
AI Recommendation
      ↓
Validation
      ↓
Human Approval
      ↓
Write Operation
```

---

### 43. Policy Enforcement Point

AI architecture should identify where security policies are enforced.

```text
Request
   ↓
Policy Enforcement Point
   ↓
Policy Decision
   ↓
Resource
```

This creates a clear control boundary.

---

### 44. Policy Decision Point

A centralized policy engine can evaluate AI requests.

Inputs may include:

* Identity.
* Role.
* Tenant.
* Data classification.
* Requested action.
* Device.
* Risk level.

---

### 45. Attribute-Based Access Control

ABAC can make decisions based on attributes rather than only roles.

```text
IF
User = Employee
AND
Data = Confidential
AND
Purpose = Approved
THEN
Allow
```

---

### 46. Context-Aware AI Authorization

Authorization can incorporate contextual information.

```text
Identity
 +
Location
 +
Device
 +
Data Sensitivity
 +
Action
 +
Risk
```

The result is a more adaptive access decision.

---

### 47. Microservices AI Pattern

Complex AI platforms can separate functionality into services.

```text
API Service
    ↓
AI Orchestrator
    ↓
Inference Service
    ↓
Retrieval Service
    ↓
Data Service
```

Each service can have a separate identity and permission set.

---

### 48. Service Mesh Pattern

A service mesh can provide centralized controls for service-to-service communication.

Potential capabilities include:

* mTLS.
* Service identity.
* Traffic policies.
* Observability.
* Authorization.

```text
Service A
   ⇄
Service Mesh
   ⇄
Service B
```

---

### 49. Secure AI Architecture Principle

A strong architecture should ensure:

```text
Every User
     ↓
Known Identity

Every Workload
     ↓
Known Identity

Every Data Access
     ↓
Authorized

Every AI Action
     ↓
Policy Controlled

Every Critical Event
     ↓
Auditable
```

---

### 50. Secure AI Architecture Patterns — Core Principle

The fundamental principle is:

> **Security should be expressed through architectural boundaries, identities, policies, isolation, and controlled data flows—not merely through procedural instructions.**

A secure AI architecture therefore establishes:

```text
TRUST BOUNDARIES
       ↓
IDENTITIES
       ↓
POLICIES
       ↓
ISOLATION
       ↓
CONTROLLED DATA FLOWS
       ↓
MONITORING
       ↓
AUDITABILITY
```

These patterns provide reusable building blocks for designing AI environments that can safely integrate **models, applications, agents, enterprise data, external providers, and infrastructure** while maintaining appropriate security and governance controls.

### 51. AI Security Boundary Pattern

A security boundary defines where one level of trust ends and another begins.

Typical AI boundaries include:

```text id="f1x7k2"
User
 ↓
Application Boundary
 ↓
AI Service Boundary
 ↓
Model Boundary
 ↓
Data Boundary
 ↓
Infrastructure Boundary
```

Each boundary should have appropriate security controls.

---

### 52. Trust Boundary Identification

During architecture design, identify:

* User-to-application boundaries.
* Application-to-AI boundaries.
* AI-to-data boundaries.
* AI-to-tool boundaries.
* Internal-to-external boundaries.
* Tenant-to-tenant boundaries.
* Management-to-data-plane boundaries.

---

### 53. AI Data Flow Control

AI data flows should be explicitly documented.

```text id="p4m8r3"
User Input
    ↓
AI Application
    ↓
Security Gateway
    ↓
Model
    ↓
RAG
    ↓
Enterprise Data
```

Every transition should have a defined security policy.

---

### 54. Data Flow Diagram

A Data Flow Diagram (DFD) can identify:

* Data sources.
* Processing components.
* Storage.
* External services.
* Trust boundaries.
* Data movement.

This is particularly useful during AI threat modeling.

---

### 55. Data Flow Classification

Each AI data flow should be classified according to sensitivity.

```text id="x7q3m9"
Public
Internal
Confidential
Restricted
```

Security requirements should increase with sensitivity.

---

### 56. Controlled Data Flow Pattern

Sensitive data should pass only through approved components.

```text id="w5n2k8"
Sensitive Data
      ↓
DLP / Policy Gateway
      ↓
Approved AI Service
      ↓
Authorized Destination
```

---

### 57. Data Diode Concept

In highly restricted environments, architecture may enforce one-way information flows.

```text id="q9m4v7"
Restricted Zone
      │
      │ One-Way Flow
      ▼
Analytics Zone
```

This can be useful where return communication must be prevented.

---

### 58. Air-Gapped AI Environment

For extremely sensitive workloads, an isolated environment may be considered.

```text id="b8r2n5"
Enterprise Network
        ✕
        │
   Air Gap
        │
        ✕
        │
Restricted AI Environment
```

Air gaps increase security but also operational complexity.

---

### 59. Offline AI Pattern

Some AI systems can operate without direct Internet connectivity.

```text id="h4p7s2"
Enterprise Data
      ↓
Private AI Environment
      ↓
Local Model
      ↓
Internal Users
```

This can reduce external data-exposure risk.

---

### 60. Private Connectivity Pattern

Where full isolation is unnecessary, private network connectivity can be used.

```text id="c6m9q3"
Enterprise
    ↓
Private Network
    ↓
AI Service
```

This reduces reliance on public Internet paths.

---

### 61. AI Security Proxy

A security proxy can sit between enterprise users and AI providers.

```text id="j8v4n6"
User
 ↓
Security Proxy
 ↓
Policy Enforcement
 ↓
AI Provider
```

It can centralize:

* Authentication.
* DLP.
* Logging.
* Rate limits.
* Provider selection.

---

### 62. Provider Abstraction Pattern

An enterprise can use an abstraction layer to avoid tightly coupling applications to one AI provider.

```text id="r5k8m2"
Application
     ↓
AI Abstraction Layer
   /      |      \
  ↓       ↓       ↓
LLM A   LLM B   LLM C
```

This also provides a centralized security control point.

---

### 63. Model Routing

An AI gateway can route requests based on:

* Data sensitivity.
* Business purpose.
* Model capability.
* Cost.
* Regulatory requirements.
* Geographic restrictions.

Example:

```text id="n3q7w5"
Public Request
      ↓
External LLM

Confidential Request
      ↓
Private LLM
```

---

### 64. Data Sensitivity-Based Routing

A particularly useful architecture pattern is routing data according to classification.

```text id="v8m2p4"
Input
 ↓
Classification
 ├── Public → External AI
 ├── Internal → Approved AI
 └── Restricted → Private AI
```

---

### 65. Policy-Based Model Selection

Model selection can be governed by policy.

```text id="g6r9n3"
Request
 ↓
Policy
 ↓
Approved Model
 ↓
Execution
```

This prevents applications from arbitrarily selecting unapproved AI services.

---

### 66. AI Model Allowlisting

Organizations can maintain an approved model list.

```text id="x2m7q5"
Approved Models
 ├── Model A ✓
 ├── Model B ✓
 ├── Model C ✓
 └── Unknown Model ✗
```

---

### 67. Model Denylisting

Known unsafe or unauthorized models may be explicitly blocked.

However, allowlisting is generally more controlled for high-risk environments.

---

### 68. Model Fallback Pattern

Applications may use a secondary approved model when the primary model is unavailable.

```text id="k4p8v2"
Primary Model
      ↓
Unavailable?
      ↓
Secondary Approved Model
```

Fallback logic should preserve security and data-handling requirements.

---

### 69. Secure Failover

Failover should not automatically route sensitive information to an unapproved provider.

```text id="m9q3r6"
Primary AI
   ↓
Failure
   ↓
Policy Check
   ↓
Approved Backup AI
```

---

### 70. AI Service Mesh Pattern

An AI platform may use a service mesh to control internal service communication.

```text id="z5v8m3"
API
 ↓
Orchestrator
 ↓
Retriever
 ↓
Model Server
 ↓
Tool Service
```

Each service can have:

* Identity.
* Authentication.
* Authorization.
* Network policy.

---

### 71. Service-to-Service Authorization

Internal AI services should verify not only who is calling, but what the caller is permitted to do.

```text id="p7n4x8"
Service A
 ↓
Identity
 ↓
Authorization
 ↓
Service B
```

---

### 72. AI Service Account Segmentation

Different services should use different identities.

```text id="c3m8q5"
Retriever → Retriever Identity
Inference → Inference Identity
Agent     → Agent Identity
```

Avoid using one shared administrative identity.

---

### 73. Shared Credentials Anti-Pattern

A weak architecture might look like:

```text id="y8r2m6"
All AI Services
      ↓
Shared Admin Credential
```

If compromised, one credential can expose the entire AI platform.

---

### 74. Dedicated Service Identity Pattern

A stronger design is:

```text id="f6q9p3"
Service A → Identity A
Service B → Identity B
Service C → Identity C
```

Permissions can then be independently controlled.

---

### 75. Secrets Isolation

AI services should retrieve secrets only when needed.

```text id="v3m7k8"
AI Workload
     ↓
Secret Manager
     ↓
Authorized Secret
```

Secrets should not be distributed to every workload.

---

### 76. Ephemeral Credentials

Short-lived credentials can reduce the impact of credential compromise.

```text id="r8n4q2"
Request
 ↓
Temporary Credential
 ↓
AI Operation
 ↓
Credential Expires
```

---

### 77. Secure Token Exchange

One service can exchange its identity for a narrowly scoped token.

```text id="j5p9m3"
Workload Identity
      ↓
Token Service
      ↓
Scoped Token
      ↓
Target Service
```

---

### 78. AI Agent Tool Gateway

```text id="x7q4n8"
AI Agent
    ↓
Tool Gateway
    ↓
Policy Check
    ↓
Enterprise API
```

### 79. Tool Allowlisting

Agents should have an explicit list of approved tools.

```text id="m5v8q3"

 ↓

 ↓
Human Approval

Transaction
```

```text id="t7n4p9"
Automatic

Human Approval
```

Rate limits should apply not only to user requests but also to automated AI actions.

Example:

* Version control.
* Code review.

* Deployment controls.

```text id="f6q2m9"
Training Environment
        │
        │ Controlled Promotion
        ▼
Production Environment
```

Training infrastructure should not automatically have production administrative access.

Training pipelines should protect:

* Data ingestion.
* Data transformation.

```text id="v9r4p7"

 ↓
Validation
 ↓
Transformation
 ↓
Training
 ↓
Model
```

### 92. Data Validation Gateway

Data should be validated before entering AI workloads.

Checks may include:

* Format.
* Integrity.
* Source.
* Malware.
* Classification.
* Authorization.

```text id="n3m8q5"
 ↓
```


### 98. Secure AI Disaster Recovery Architecture

Critical AI platforms should consider alternate infrastructure.

```text id="c2v7n5"
Primary AI Platform
       ↓
Failure
       ↓
Approved DR Environment
       ↓
AI Service Restored
```

The recovery environment must also meet security requirements.

---

### 99. Secure AI Architecture Pattern Selection

Architecture patterns should be selected based on:

* Data sensitivity.
* AI workload criticality.
* Threat exposure.
* Regulatory obligations.
* Business requirements.
* Integration complexity.
* Operational capability.

There is no universal architecture that fits every AI use case.

---

### 100. Secure AI Architecture — Core Principle

The strongest architecture pattern is not necessarily the most complex.

It is the architecture that establishes **appropriate trust boundaries and enforceable controls proportional to risk**.

```text id="n6q9m4"
RISK
 ↓
ARCHITECTURE
 ↓
TRUST BOUNDARIES
 ↓
IDENTITY
 ↓
POLICY
 ↓
ISOLATION
 ↓
MONITORING
 ↓
RESILIENCE
```

The GRC perspective is:

> **Secure AI architecture patterns translate security principles into repeatable architectural designs that can be governed, assessed, tested, and evidenced.**

A mature organization should be able to explain **why a particular architecture pattern was selected, what risks it addresses, what assumptions it makes, what controls enforce it, and what residual risks remain**.

# 07.18 — Secure AI Architecture Patterns

### 101. AI Architecture Trust Model

A secure AI architecture begins by explicitly defining **who and what can be trusted, under what conditions, and for what purpose**.

```text

 ↓

 ↓

 ↓
AI Gateway
 ↓
Model / Agent
 ↓
Data / Tools
```

Trust should be established at each boundary rather than assumed across the entire architecture.

### 102. Explicit Trust

AI components should not receive implicit trust simply because they operate inside the corporate network.

For example:

```text
Internal Network ≠ Automatically Trusted
Internal Application ≠ Automatically Trusted
AI Agent ≠ Automatically Trusted
```

Each request should be evaluated according to defined policies.

### 103. Trust Boundary Documentation

Architecture documentation should clearly identify:

* Trusted zones.
* Untrusted zones.
* Semi-trusted services.
* External providers.
* Sensitive data boundaries.
* Administrative boundaries.
* Tenant boundaries.

```text
      ↓

      ↓
```

```text
   ↕
```

North-south traffic represents traffic entering or leaving the AI environment.

```text

   ↓

   ↓
```

```text
   ↓
```

```text
   ↓
```

### 200. Secure AI Architecture Patterns — Final Principle

Secure AI architecture is ultimately about **controlling trust, access, data movement, workload behavior, and failure impact**.

A mature architecture should follow:

```text id="z8r4m6"
IDENTITY
    ↓
AUTHORIZATION
    ↓
SEGMENTATION
    ↓
DATA CONTROL
    ↓
MODEL CONTROL
    ↓
WORKLOAD PROTECTION
    ↓
MONITORING
    ↓
RESPONSE
    ↓
RESILIENCE
    ↓
GOVERNANCE
```

The key principle is:

> **The architecture itself should enforce the security policy as much as technically possible, rather than relying solely on users and administrators to follow procedures.**

From a GRC perspective, the final question is not simply **“Is the AI architecture secure?”**

It is:

> **“Can the organization demonstrate that the architecture implements appropriate controls for its identified risks, that those controls are operating effectively, and that the remaining risk is understood and accepted by the appropriate owner?”**
