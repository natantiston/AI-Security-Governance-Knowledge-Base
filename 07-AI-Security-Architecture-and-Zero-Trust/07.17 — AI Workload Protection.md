# 07.17 — AI Data Security, Privacy, and Protection

## Part 1

### 1. Introduction to AI Data Security

AI systems depend heavily on data.

Data may be used for:

* Training.
* Fine-tuning.
* Retrieval-Augmented Generation (RAG).
* Prompt context.
* Model inference.
* Evaluation.
* Monitoring.
* Analytics.
* AI agent execution.

Therefore, AI security must include strong **data security and privacy controls**.

The fundamental principle is:

> **AI systems should only collect, access, process, retain, and disclose data that is authorized, necessary, protected, and appropriate for the intended purpose.**

---

### 2. AI Data Lifecycle

A complete AI data lifecycle can be represented as:

```text id="7j8w2k"
COLLECT
   ↓
CLASSIFY
   ↓
STORE
   ↓
PROCESS
   ↓
USE
   ↓
SHARE
   ↓
RETAIN
   ↓
ARCHIVE / DELETE
```

Security and privacy controls should exist throughout the lifecycle.

---

### 3. AI Data Security vs AI Privacy

These concepts are related but different.

**Data security** focuses on protecting data from:

* Unauthorized access.
* Modification.
* Loss.
* Destruction.
* Disclosure.

**Privacy** focuses on how personal information is:

* Collected.
* Used.
* Shared.
* Retained.
* Deleted.

```text id="y7o4xq"
AI Data Governance
        │
   ┌────┴────┐
   ▼         ▼
Security   Privacy
```

---

### 4. Types of AI Data

AI environments may contain:

* Personal data.
* Sensitive personal data.
* Financial information.
* Customer information.
* Employee information.
* Authentication data.
* Intellectual property.
* Business-confidential information.
* Public information.
* Operational data.
* Security data.

Each category may require different controls.

---

### 5. Data Classification

Organizations should classify data before allowing AI systems to process it.

Example:

```text id="4h8m5w"
PUBLIC
  ↓
INTERNAL
  ↓
CONFIDENTIAL
  ↓
RESTRICTED
```

The classification should influence:

* Which AI models may process the data.
* Where the data may be stored.
* Who may access it.
* Whether it may be sent to third parties.
* Retention requirements.
* Logging requirements.

---

### 6. Data Classification and AI Model Selection

Not every AI model should process every type of data.

For example:

```text id="8v6y4p"
Public Data
   ↓
Approved Public AI Service

Confidential Data
   ↓
Approved Enterprise AI Environment

Highly Restricted Data
   ↓
Dedicated / Controlled Environment
```

---

### 7. Data Minimization

Data minimization means using only the data required for the intended purpose.

Example:

```text id="k5v3d8"
Customer Record
├── Name
├── Address
├── Phone
├── Email
├── Date of Birth
├── Bank Account
└── Transaction History
```

If an AI task only requires the customer's name and email, there is no justification for sending the complete record.

---

### 8. Purpose Limitation

Data should be processed for a defined and legitimate purpose.

For example:

```text id="j8r1v2"
Purpose:
Customer Support
      ↓
Required Data:
Ticket + Relevant Customer Information
```

The AI application should not automatically gain access to unrelated enterprise data.

---

### 9. Data Access Control

AI applications should use the same principle as other enterprise systems:

> **Users and AI workloads should access only the data they are authorized to access.**

```text id="f7q9m2"
User Identity
      ↓
Authorization
      ↓
Data Access
      ↓
AI Processing
```

---

### 10. AI Should Not Bypass Existing Access Controls

A common architectural mistake is:

```text id="w1z4kp"
User
 ↓
AI
 ↓
Entire Database
```

The AI should not become a shortcut around enterprise authorization.

Prefer:

```text id="u4m8y1"
User
 ↓
Authorization
 ↓
Authorized Data
 ↓
AI
```

---

### 11. Identity-Based Data Access

AI applications should understand the security context of the user.

This can include:

* User identity.
* Role.
* Department.
* Tenant.
* Location where relevant.
* Data entitlements.

```text id="r9v2q5"
Identity
+
Role
+
Resource
+
Action
      ↓
Authorization Decision
```

---

### 12. Row-Level Security

For database-backed AI applications, access may need to be restricted at the record level.

Example:

```text id="y2f7q4"
User A
 ↓
Customer Records
 ↓
Only Records Authorized for User A
```

The model should not receive unauthorized records and then be expected to hide them.

---

### 13. Tenant Isolation

Multi-tenant AI systems require strong tenant separation.

```text id="x5c8v1"
Tenant A
 ├── Users
 ├── Data
 └── AI Context

Tenant B
 ├── Users
 ├── Data
 └── AI Context
```

Tenant A must not retrieve or expose Tenant B's information.

---

### 14. Cross-Tenant Data Leakage

A serious AI security issue occurs when:

```text id="q6z3m8"
Tenant A User
      ↓
AI Query
      ↓
Retriever
      ↓
Tenant B Data
      ↓
AI Response
```

This should be prevented through authorization at the retrieval and data-access layers.

---

### 15. Data at Rest

AI data stored in:

* Databases.
* Vector stores.
* Object storage.
* Backups.
* Logs.
* Model repositories.

should be appropriately protected.

Encryption at rest is a common control.

---

### 16. Data in Transit

Data transmitted between:

```text id="m2r8k5"
User
 ↓
Application
 ↓
AI API
 ↓
RAG
 ↓
Database
 ↓
Tool
```

should use appropriate secure communication mechanisms such as TLS.

---

### 17. Data in Use

Data may also require protection while being processed.

Depending on the environment, organizations may consider:

* Secure enclaves.
* Confidential computing.
* Strong workload isolation.
* Memory protection.
* Restricted administrative access.

---

### 18. Encryption Key Management

Encryption is only as strong as its key-management practices.

Organizations should control:

* Key generation.
* Storage.
* Access.
* Rotation.
* Revocation.
* Recovery.

```text id="v5n9k1"
Encrypted Data
      ↓
Key Management System
      ↓
Authorized Access
```

---

### 19. Secrets Management

AI applications should not expose:

* API keys.
* Passwords.
* Tokens.
* Private keys.
* Database credentials.

inside prompts, source code, or model context.

Prefer:

```text id="n8x3q4"
AI Application
      ↓
Secret Manager
      ↓
Credential
      ↓
Authorized API
```

---

### 20. Prompt Data Security

Prompts may contain sensitive information.

Example:

```text id="e4y7m2"
"Review this employee's salary,
performance, and personal information."
```

The prompt itself may become sensitive data.

Therefore, prompt handling should be included in the organization's data-security and privacy model.

---

### 21. Prompt Logging

Logging every prompt may create another privacy risk.

Organizations should determine:

* Whether prompts need to be logged.
* Which information must be masked.
* Who may access prompt logs.
* How long logs are retained.
* Whether logs are encrypted.

---

### 22. AI Response Security

AI responses may also contain sensitive information.

Example:

```text id="u7m3q9"
User Query
 ↓
AI
 ↓
Confidential Customer Information
```

Output should be subject to appropriate authorization and data-loss controls.

---

### 23. Data Leakage

Data leakage may occur through:

* Prompts.
* Responses.
* RAG.
* Logs.
* APIs.
* Model outputs.
* Conversation memory.
* Fine-tuning datasets.
* Error messages.

---

### 24. Data Loss Prevention

DLP controls can inspect AI input and output.

```text id="k3p7w9"
AI Input / Output
       ↓
DLP Inspection
       ↓
┌──────┼──────┐
▼      ▼      ▼
Allow  Redact  Block
```

---

### 25. Sensitive Information Detection

Organizations may identify:

* Passport numbers.
* National identification numbers.
* Credit-card information.
* Bank details.
* Passwords.
* API keys.
* Health information.
* Confidential business information.

Detection can support automated protection.

---

### 26. Redaction

Sensitive information can sometimes be masked before processing.

Example:

```text id="m9c2x7"
Before:
Credit Card = 4532 1234 5678 9012

After:
Credit Card = **** **** **** 9012
```

The AI may still be able to perform the required task without seeing the full value.

---

### 27. Tokenization

Tokenization replaces sensitive information with a non-sensitive representation.

```text id="g4v6t2"
Real Customer ID
      ↓
Token
      ↓
AI Processing
      ↓
Authorized Detokenization
```

---

### 28. Pseudonymization

Pseudonymization can reduce direct exposure of personal information while maintaining the ability to associate records under controlled conditions.

Example:

```text id="c6r1n9"
Jonathan Morales
      ↓
CUSTOMER_84721
```

The mapping must remain securely controlled.

---

### 29. Anonymization

Anonymization aims to remove the ability to reasonably associate data with an identifiable individual.

It may be appropriate for:

* Analytics.
* Testing.
* Research.
* Model evaluation.

However, the effectiveness of anonymization must be assessed rather than assumed.

---

### 30. Synthetic Data

Synthetic data can reduce exposure to real personal information.

```text id="h7n4m2"
Real Data
   ↓
Synthetic Generation
   ↓
Testing / Development
```

It can be useful where realistic data is needed but production personal information should not be exposed.

---

### 31. Development Environment

Production data should not automatically be copied into AI development environments.

Prefer:

```text id="z3v8q1"
Production Data
       ↓
Controlled Transformation
       ↓
Masked / Synthetic Data
       ↓
Development
```

---

### 32. AI Training Data

Training data can contain sensitive information.

Governance should establish:

* Approved data sources.
* Data ownership.
* Data classification.
* Consent or legal basis where applicable.
* Licensing.
* Retention.
* Access.
* Security.

---

### 33. Training Data Provenance

Organizations should know where training data came from.

```text id="p4w6s2"
Dataset
 ↓
Source
 ↓
Owner
 ↓
License / Rights
 ↓
Classification
 ↓
Approval
```

---

### 34. Training Data Poisoning

Attackers may intentionally insert malicious or misleading data into training datasets.

```text id="y8q2n5"
Attacker
 ↓
Malicious Data
 ↓
Training Dataset
 ↓
Model
 ↓
Changed Behavior
```

Data provenance and validation help reduce this risk.

---

### 35. Training Dataset Integrity

Controls can include:

* Source validation.
* Hashing.
* Digital signatures.
* Version control.
* Approval workflows.
* Dataset scanning.
* Change monitoring.

---

### 36. Fine-Tuning Data Security

Fine-tuning datasets may contain confidential enterprise information.

The organization should determine:

```text id="r6k4p1"
What data?
Who owns it?
Why is it used?
Where is it processed?
Who can access the resulting model?
```

---

### 37. Model Memorization Risk

Models may sometimes retain patterns from their training data.

This creates potential concerns around:

* Sensitive information disclosure.
* Confidential information.
* Personal information.
* Proprietary information.

Security and privacy testing should therefore consider whether sensitive information can be elicited from the model.

---

### 38. Data Extraction Testing

Security testers can attempt to determine whether a model reveals sensitive training or contextual information.

```text id="v3y7k2"
Test Query
 ↓
Model
 ↓
Potential Sensitive Output
 ↓
Security Evaluation
```

---

### 39. RAG Data Security

RAG introduces another data-security layer.

```text id="m5j8r3"
User
 ↓
AI Application
 ↓
Retriever
 ↓
Vector Database
 ↓
Authorized Documents
 ↓
Model
```

Authorization must be enforced before sensitive data enters the model context.

---

### 40. Vector Database Security

Vector stores may contain representations of sensitive enterprise content.

Controls should include:

* Authentication.
* Authorization.
* Encryption.
* Tenant isolation.
* Network controls.
* Logging.
* Backup security.

---

### 41. Data Provenance in RAG

Every important retrieved document should ideally have traceable metadata.

Example:

```text id="j7c4v9"
Document
├── Source
├── Owner
├── Classification
├── Version
├── Date
└── Authorization Scope
```

This improves governance and investigation.

---

### 42. Data Retention

AI systems may create many types of stored information:

* Prompts.
* Responses.
* Conversations.
* Logs.
* RAG documents.
* Embeddings.
* Evaluation datasets.

Retention periods should be defined rather than allowing indefinite storage.

---

### 43. Retention Principle

A useful governance model is:

```text id="w2p5k8"
Collect
 ↓
Use
 ↓
Retain for Defined Purpose
 ↓
Archive / Delete
```

---

### 44. Data Deletion

Deletion should consider all relevant copies.

For example:

```text id="q8n3m5"
Original Data
 ├── Database
 ├── Backup
 ├── Vector Store
 ├── Logs
 ├── Cache
 └── AI Dataset
```

A deletion process must determine which copies need to be removed or otherwise handled.

---

### 45. Backup Security

AI data backups may contain the same sensitive information as production systems.

Controls include:

* Encryption.
* Access control.
* Backup retention.
* Monitoring.
* Recovery testing.

---

### 46. Data Residency

Organizations may have requirements regarding where data is processed or stored.

AI architecture should therefore identify:

```text id="n5y8q3"
Where is data collected?
        ↓
Where is it processed?
        ↓
Where is it stored?
        ↓
Where are backups stored?
```

---

### 47. Cross-Border Data Transfer

Using an external AI service can potentially transfer information across jurisdictions.

Before processing sensitive information, organizations should evaluate:

* Applicable laws.
* Contractual requirements.
* Data-transfer mechanisms.
* Vendor location.
* Subprocessors.
* Data residency requirements.

---

### 48. Third-Party AI Processing

If an external provider processes enterprise data:

```text id="s4m9q2"
Enterprise
 ↓
AI Application
 ↓
Third-Party AI Provider
```

The organization should understand exactly what information leaves its controlled environment.

---

### 49. Data Processing Agreements

Where applicable, contractual arrangements should address:

* Processing purpose.
* Data categories.
* Security requirements.
* Retention.
* Subprocessors.
* Incident notification.
* Deletion.
* Audit rights.

---

### 50. Core AI Data Security Principle

The most important principle for Part 1 is:

> **AI should not receive more data, retain more data, or disclose more data than is necessary and authorized for the intended business purpose.**

The complete mental model is:

```text id="a7r3m9"
CLASSIFY
   ↓
MINIMIZE
   ↓
AUTHORIZE
   ↓
PROTECT
   ↓
MONITOR
   ↓
RETAIN
   ↓
DELETE
```

From a GRC perspective:

```text id="p2m6v8"
AI Data
  ↓
Data Classification
  ↓
Privacy / Security Risk
  ↓
Control Requirements
  ↓
Access & Protection
  ↓
Monitoring
  ↓
Evidence
  ↓
Assurance
```

# 07.17 — AI Data Security, Privacy, and Protection

## Part 2

### 51. AI Data Access Governance

AI data access should be governed using the same fundamental security principles applied to enterprise systems, but with additional consideration for AI-specific data flows.

The organization should define:

* Who can access AI data.
* Which AI application can access it.
* Which model can process it.
* Which users can retrieve it.
* Which tools can act on it.
* How access is monitored.

```text id="a8f2m4"
User
 ↓
Identity
 ↓
Authorization
 ↓
AI Application
 ↓
Authorized Data
```

---

### 52. Least Privilege for AI Data

AI applications should receive only the minimum data permissions necessary.

```text id="m6v9q2"
Required:
Read Customer Tickets

Not Required:
Read Payroll
Read HR Records
Read Executive Files
```

Least privilege should apply to both **users and AI workloads**.

---

### 53. Need-to-Know Principle

Access should be based on legitimate business need.

```text id="r4n8k1"
User
 ↓
Business Need
 ↓
Authorized Data
```

Having access to an AI application does not automatically justify access to every dataset connected to it.

---

### 54. Attribute-Based Access Control

AI applications may benefit from attribute-based controls.

Access can depend on:

* User role.
* Department.
* Tenant.
* Data classification.
* Location.
* Business function.
* Device trust.
* Application identity.

```text id="y3p7w8"
User Attributes
+
Resource Attributes
+
Action
      ↓
Policy Decision
```

---

### 55. Role-Based Access Control

RBAC can define AI data permissions based on organizational roles.

Example:

```text id="q6w2m9"
HR Manager
 → HR AI Assistant
 → Employee HR Records

Finance Analyst
 → Finance AI Assistant
 → Finance Records
```

Roles should be reviewed periodically.

---

### 56. Privileged Data Access

Access to highly sensitive AI datasets should receive stronger controls.

Examples:

* Privileged access management.
* Just-in-time access.
* Approval.
* Enhanced logging.
* Session monitoring.

---

### 57. AI Service Accounts

AI applications should preferably use dedicated service identities.

```text id="n7k3p5"
AI Application
 ↓
Dedicated Service Identity
 ↓
Specific Permissions
```

Avoid using shared administrator accounts.

---

### 58. Workload Identity

Cloud-native AI applications can use workload identities instead of embedding static credentials.

This reduces the risk of:

* Credential leakage.
* Long-lived secrets.
* Manual credential management.

---

### 59. Authentication for AI Services

AI services should use appropriate authentication mechanisms.

Examples include:

* OAuth.
* OpenID Connect.
* Managed identities.
* Mutual TLS.
* Signed tokens.

Authentication establishes **who or what is making the request**.

---

### 60. Authorization for AI Services

Authorization determines:

> **What is this identity allowed to do?**

```text id="u8x5c2"
Authentication
      ↓
Who are you?
      ↓
Authorization
      ↓
What may you access?
```

Both are required.

---

### 61. Dynamic Authorization

For sensitive AI applications, authorization may need to consider context at request time.

```text id="g2j8v4"
User
+
Role
+
Data
+
Action
+
Context
      ↓
Decision
```

This is especially important for agentic AI.

---

### 62. Data Classification Enforcement

Classification should not exist only in documentation.

It should be technically enforced where possible.

```text id="w6m4r1"
Confidential Data
 ↓
Policy
 ↓
Only Approved AI Models
```

---

### 63. AI Model Allowlisting

Organizations can maintain an approved model list.

```text id="x8p2n6"
Approved Models
├── Model A ✓
├── Model B ✓
└── Model C ✗
```

This reduces shadow-AI and uncontrolled processing.

---

### 64. Shadow AI

Shadow AI occurs when employees use AI services without formal organizational approval.

Examples:

* Uploading company documents to public AI tools.
* Using personal AI accounts for business work.
* Connecting unauthorized AI plugins.
* Copying customer information into external chatbots.

---

### 65. Shadow AI Risk

Shadow AI can create:

```text id="z4r7m2"
Sensitive Data
 ↓
Unauthorized AI Service
 ↓
Unknown Processing
 ↓
Potential Data Exposure
```

Organizations should combine:

* Awareness.
* Policy.
* Approved tools.
* Technical controls.
* Monitoring.

---

### 77. Encryption Strategy

AI data should be protected using appropriate encryption:

```text id="r6v2m9"
At Rest
+
In Transit
+
Where Appropriate, In Use
```

Encryption should be combined with access control rather than treated as a substitute for authorization.

### 78. Key Separation

Different environments and sensitivity levels may require separate cryptographic keys.

```text id="j4n8p3"
Production
 → Key A

Development
 → Key B

Restricted AI
 → Key C
```

This reduces the impact of a single key compromise.

### 79. Key Rotation

Key management should support:

* Rotation.
* Revocation.
* Access monitoring.
* Secure backup.
* Emergency replacement.

AI-related data may exist in:

* Relational databases.

* Logs.
* Message queues.
* Model repositories.

Every storage location should have appropriate security controls.

```text id="h5q8m2"
 ↓
```

Retrieval should apply filters such as:


* Incorrect decisions.
* Incorrect recommendations.
* Misleading responses.
* Security-policy errors.

Therefore, data governance and AI security are interconnected.

Controls can include:

* Hashing.
* Digital signatures.
* Version control.
* Immutable logs.
* Access restrictions.


* Integrity verification.
* Access control.
* Change monitoring.

### 95. Personal Data in AI Systems

Personal data requires particular attention because AI applications can process large volumes of information at high speed.

Examples:

* Names.

* Identification numbers.
* Financial records.
* Employment information.
* Location information.
* Customer records.

### 97. Privacy Impact Assessment

### 99. Data Subject Rights

Depending on applicable law, individuals may have rights relating to their personal information.

AI architectures should consider how applicable rights can be supported, including:

* Access.
* Correction.
* Deletion.
* Restriction.
* Objection.

The exact requirements depend on the applicable jurisdiction and processing context.

### 100. Part 2 Core Principle

The central principle of AI data access governance is:

> **The AI system should inherit and enforce the user's and application's authorized data boundaries rather than creating a new, unrestricted data-access layer.**

The practical model is:

```text id="w8r5m3"
IDENTITY
   ↓
AUTHENTICATION
   ↓
AUTHORIZATION
   ↓

   ↓
MINIMIZATION
   ↓
MASKING / DLP
   ↓
SECURE PROCESSING
   ↓
MONITORING
   ↓
RETENTION / DELETION
```
