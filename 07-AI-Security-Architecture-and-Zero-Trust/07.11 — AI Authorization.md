# 07.11 — AI Authorization

## Part 1 — AI Authorization Foundations, Principles, Models, and Architecture

### 1. AI Authorization

AI authorization is the process of determining whether an authenticated identity is permitted to perform a specific action against a specific AI resource under defined conditions.

Authorization answers:

> **“What is this authenticated entity allowed to do?”**

Authentication establishes identity; authorization determines permitted activity.

---

### 2. Authentication vs. Authorization

The distinction is fundamental:

```text
Authentication
      ↓
Who are you?
      ↓
Identity Established
      ↓
Authorization
      ↓
What are you allowed to do?
      ↓
Access Decision
```

A user can successfully authenticate and still be denied access to an AI model, dataset, tool, or administrative function.

---

### 3. Basic Authorization Flow

A simplified AI authorization process is:

```text
Entity
  ↓
Authentication
  ↓
Identity
  ↓
Access Request
  ↓
Policy Evaluation
  ↓
Authorization Decision
  ↓
Allow / Deny
```

Authorization should occur before the protected action is executed.

---

### 4. Authorization Decision

The authorization decision generally produces one of two outcomes:

```text
ALLOW
   or
DENY
```

A more sophisticated system may also produce:

```text
ALLOW
DENY
STEP-UP
REQUIRE APPROVAL
RESTRICT
```

This becomes particularly important for high-impact AI actions.

---

### 5. Authorization Subjects

Authorization can apply to multiple types of subjects:

1. Human users.
2. Administrators.
3. Applications.
4. AI agents.
5. Workloads.
6. Service accounts.
7. APIs.
8. Automated processes.

The subject's identity should be established through a trusted authentication mechanism.

---

### 6. Authorization Resources

AI authorization may protect:

* AI models.
* Model endpoints.
* AI applications.
* APIs.
* Datasets.
* Vector databases.
* Documents.
* AI memory.
* Tools.
* Cloud resources.
* Model registries.
* Prompt repositories.
* Configuration.
* Administrative functions.

---

### 7. Authorization Actions

Authorization should evaluate the specific action being requested.

Examples:

```text
Read
Write
Execute
Invoke
Create
Modify
Delete
Deploy
Approve
Export
Share
Administer
```

A user authorized to **read** a model does not necessarily have permission to **modify** or **delete** it.

---

### 8. Subject-Resource-Action Model

A useful authorization model is:

```text
SUBJECT
   +
ACTION
   +
RESOURCE
   +
CONTEXT
   ↓
AUTHORIZATION DECISION
```

For example:

```text
Subject: Analyst
Action: Read
Resource: Financial Dataset
Context: Corporate Device
        ↓
      ALLOW
```

---

### 9. Authorization Context

Authorization decisions may consider additional context.

Examples include:

* User identity.
* User role.
* Device.
* Location.
* Network.
* Time.
* Risk.
* Data classification.
* Application.
* Agent identity.
* Transaction type.

```text
Identity
+
Resource
+
Action
+
Context
+
Risk
 ↓
Decision
```

---

### 10. Least Privilege

Least privilege means providing only the access required to perform an authorized task.

For AI:

```text
Agent
 ↓
Required Tool
 ↓
Required Function
 ↓
Required Data
```

Not:

```text
Agent
 ↓
All Enterprise Systems
```

---

### 11. Principle of Least Privilege for AI Agents

AI agents should receive the minimum permissions necessary for their intended function.

For example:

**Customer Support Agent**

May need:

```text
Customer Record → Read
Ticket System → Read / Write
Knowledge Base → Read
```

It should not automatically receive:

```text
Payroll → Read
IAM → Admin
Finance → Delete
```

---

### 12. Default Deny

A strong authorization architecture generally follows a default-deny principle.

```text
No Explicit Permission
        ↓
       DENY
```

Access is granted only when an applicable policy authorizes the action.

---

### 13. Explicit Allow

An authorization system should clearly identify the conditions under which access is allowed.

Example:

```text
IF
User = Finance Analyst
AND
Resource = Finance Reports
AND
Action = Read
AND
Device = Managed
THEN
ALLOW
```

---

### 14. Explicit Deny

Explicit deny rules can override otherwise permitted access.

Example:

```text
User Role:
Finance Analyst

General Permission:
Read Financial Reports

Exception:
Confidential M&A Dataset

Result:
DENY
```

This allows organizations to create targeted restrictions.

---

### 15. Authorization Policy

An authorization policy defines who can perform what action against which resource and under what conditions.

A simplified policy can be represented as:

```text
Subject:
AI-Agent-001

Action:
Read

Resource:
HR-Knowledge-Base

Condition:
Authenticated + Approved Environment

Decision:
Allow
```

---

### 16. Policy Enforcement Point

The Policy Enforcement Point (PEP) is responsible for enforcing the authorization decision.

```text
Request
  ↓
PEP
  ↓
Policy Decision
  ↓
ALLOW / DENY
```

The PEP should prevent unauthorized actions from reaching protected resources.

---

### 17. Policy Decision Point

The Policy Decision Point (PDP) evaluates the applicable authorization policies.

```text
Request
   ↓
PEP
   ↓
PDP
   ↓
Policy Evaluation
   ↓
Decision
   ↓
PEP
```

This separation can support centralized policy management.

---

### 18. Policy Information Point

A Policy Information Point (PIP) provides contextual information required for the authorization decision.

Potential information includes:

* Identity attributes.
* Device posture.
* Risk score.
* Data classification.
* Location.
* Time.
* Application identity.

```text
Request
   ↓
PDP ← PIP
   ↓
Decision
```

---

### 19. Policy Administration Point

The Policy Administration Point (PAP) is responsible for managing authorization policies.

```text
Security Administrator
       ↓
Policy Administration
       ↓
Authorization Policies
       ↓
Policy Decision Point
```

---

### 20. Authorization Architecture

A complete model can be represented as:

```text
                    REQUESTER
                        │
                        ▼
                  Authentication
                        │
                        ▼
                    Identity
                        │
                        ▼
                 Access Request
                        │
                        ▼
              Policy Enforcement Point
                        │
                        ▼
              Policy Decision Point
                  │           │
                  │           ▼
                  │          PIP
                  │       Context Data
                  │
                  ▼
                Policy
                  │
                  ▼
             ALLOW / DENY
                  │
                  ▼
             Protected Resource
```

---

### 21. Role-Based Access Control

Role-Based Access Control (RBAC) assigns permissions to roles rather than directly to every individual.

Example:

```text
Role: AI Analyst
      ↓
Permissions
 ├── Model → Invoke
 ├── Dataset → Read
 └── Reports → Read
```

Users are assigned the appropriate role.

---

### 22. AI RBAC Example

An organization may define:

| Role             | Model  | Dataset                | Administration |
| ---------------- | ------ | ---------------------- | -------------- |
| AI User          | Invoke | Limited Read           | No             |
| AI Analyst       | Invoke | Read                   | No             |
| AI Developer     | Invoke | Development Read/Write | Limited        |
| AI Administrator | Manage | Manage                 | Yes            |
| AI Auditor       | Read   | Audit Read             | No             |

Permissions should reflect actual business responsibilities.

---

### 23. RBAC Advantages

RBAC can provide:

* Simpler administration.
* Standardized permissions.
* Easier access reviews.
* Reduced direct permission assignment.
* Better separation of duties.

---

### 24. RBAC Limitations

RBAC can become difficult when access depends heavily on context.

For example:

```text
Same Role
+
Different Dataset Classification
+
Different Location
+
Different Device
```

A role alone may not provide sufficient information for the authorization decision.

---

### 25. Attribute-Based Access Control

Attribute-Based Access Control (ABAC) evaluates attributes associated with the subject, resource, action, and environment.

```text
Subject Attributes
+
Resource Attributes
+
Action
+
Environmental Attributes
 ↓
Authorization Decision
```

---

### 26. ABAC Example

```text
Subject:
Department = Finance

Resource:
Classification = Confidential

Action:
Read

Device:
Managed

Location:
Corporate

Result:
ALLOW
```

Changing any relevant attribute could change the decision.

---

### 27. AI ABAC

ABAC can be particularly useful for AI because AI systems frequently interact with diverse resources and dynamic contexts.

Example:

```text
User = Finance
AND
Data = Confidential
AND
Device = Managed
AND
Risk = Low
AND
Action = Read
       ↓
     ALLOW
```

---

### 28. Relationship-Based Access Control

Relationship-Based Access Control considers the relationship between an identity and a resource.

For example:

```text
User
 ↓
Member Of
 ↓
Project
 ↓
Owns
 ↓
AI Dataset
```

The relationship can determine whether access is allowed.

---

### 29. AI Relationship Example

Consider an AI project:

```text
User
 ↓
Project Member
 ↓
AI Project
 ↓
Project Dataset
```

A user who is not a member of that project may be denied access even if they possess a general AI analyst role.

---

### 30. Policy-Based Access Control

Policy-Based Access Control evaluates requests against centrally defined policies.

```text
Access Request
      ↓
Policy Engine
      ↓
Policy Evaluation
      ↓
Decision
```

This approach can combine roles, attributes, relationships, and contextual information.

---

### 31. RBAC, ABAC, and Policy-Based Authorization

| Model | Primary Concept |
| ----- | --------------- |
| RBAC  | Role            |
| ABAC  | Attributes      |
| ReBAC | Relationships   |
| PBAC  | Policies        |

Modern enterprise AI architectures may combine these approaches rather than relying on only one.

---

### 32. Fine-Grained Authorization

AI systems often require authorization more granular than application-level access.

Instead of:

```text
User → AI Application → Allow
```

a mature architecture evaluates:

```text
User
 ↓
Application
 ↓
Agent
 ↓
Tool
 ↓
Action
 ↓
Dataset
 ↓
Record
```

---

### 33. Function-Level Authorization

An AI application may expose multiple functions.

For example:

```text
AI Assistant
 ├── Search
 ├── Summarize
 ├── Create Report
 ├── Send Email
 └── Delete Record
```

Authorization should distinguish between these operations.

---

### 34. Tool-Level Authorization

AI agents often call external tools.

Each tool should have explicit permissions.

```text
Agent
 ├── Search → Allow
 ├── CRM Read → Allow
 ├── Email Send → Conditional
 └── Database Delete → Deny
```

---

### 35. Tool Function Authorization

Even within a single tool, authorization may differ by function.

```text
CRM Tool
 ├── Read Customer → Allow
 ├── Update Customer → Conditional
 ├── Export Customers → Deny
 └── Delete Customer → Deny
```

This reduces the agent's effective attack surface.

---

### 36. Data-Level Authorization

AI systems may need authorization at the data level.

For example:

```text
Dataset
 ├── Public Data → Allow
 ├── Internal Data → Allow
 ├── Confidential Data → Conditional
 └── Restricted Data → Deny
```

---

### 37. Row-Level Authorization

Some systems require authorization at individual record level.

```text
Database
 ├── Customer A → Allow
 ├── Customer B → Allow
 ├── Customer C → Deny
```

This prevents an AI application from returning records simply because the user has access to the overall database.

---

### 38. Document-Level Authorization

RAG systems may require document-level authorization.

```text
User
 ↓
RAG Query
 ↓
Document Retrieval
 ↓
Authorization Filter
 ↓
Permitted Documents
 ↓
LLM
```

Authorization should be considered during retrieval, not only after generation.

---

### 39. Chunk-Level Authorization

Sensitive documents may be divided into chunks for retrieval.

Authorization may need to remain associated with each chunk.

```text
Document
 ↓
Chunks
 ├── Chunk A → User Allowed
 ├── Chunk B → User Allowed
 └── Chunk C → User Denied
```

The vector similarity score does not determine whether a user is authorized to receive the content.

---

### 40. Vector Database Authorization

Vector databases should not be treated as authorization-free storage.

Access controls may include:

* Tenant.
* User.
* Group.
* Project.
* Classification.
* Document ownership.

```text
Query
 ↓
Vector Search
 ↓
Authorization Filtering
 ↓
Permitted Results
```

---

### 41. AI Memory Authorization

AI memory can contain:

* User preferences.
* Previous conversations.
* Business information.
* Sensitive records.
* Agent state.

Authorization should determine who or what can access each memory store.

---

### 42. User Memory Isolation

A multi-user AI system should prevent cross-user memory access.

```text
User A
 ↓
Memory A

User B
 ↓
Memory B
```

The application should not allow User A to retrieve User B's private AI memory.

---

### 43. Tenant-Level Authorization

Multi-tenant AI platforms require strict tenant boundaries.

```text
Tenant A
 ├── Users
 ├── Models
 ├── Data
 └── Agents

Tenant B
 ├── Users
 ├── Models
 ├── Data
 └── Agents
```

A valid identity in Tenant A should not automatically authorize access to Tenant B resources.

---

### 44. Tenant Context

Authorization decisions should include trusted tenant context.

```text
Authenticated Identity
        ↓
Tenant Context
        ↓
Resource Tenant
        ↓
Authorization
```

Tenant identifiers supplied directly by an untrusted client should not be blindly trusted.

---

### 45. Cross-Tenant Access

Cross-tenant access should be explicitly authorized when required.

Example:

```text
Tenant A User
 ↓
Approved Federation
 ↓
Tenant B Resource
 ↓
Explicit Policy
 ↓
ALLOW
```

Without an applicable policy:

```text
DENY
```

---

### 46. Delegated Authorization

AI systems often perform actions on behalf of users.

```text
User
 ↓
AI Agent
 ↓
Delegated Authorization
 ↓
Enterprise API
```

The delegated authority should be limited to the intended operation.

---

### 47. Effective Permissions

For an AI agent acting on behalf of a user, effective permissions should not automatically exceed the permitted authority.

A useful conceptual model is:

```text
Effective Permission
=
User Authority
∩
Agent Authority
∩
Resource Policy
∩
Context
```

This helps prevent privilege escalation through delegation.

---

### 48. Agent Authorization

AI agents should have explicitly defined capabilities.

Example:

```text
Agent:
HR Assistant

Allowed:
✓ Read HR Policies
✓ Search Employee Benefits
✓ Create HR Requests

Denied:
✗ Modify Payroll
✗ Change IAM Roles
✗ Delete Employee Records
```

---

### 49. Agent Capability Boundaries

An agent's capabilities should be treated as an authorization boundary.

```text
Agent
 ↓
Capability Set
 ├── Tool A
 ├── Tool B
 └── Tool C
```

The agent should not be able to dynamically acquire unrestricted capabilities merely because a prompt requests them.

---

### 50. AI Authorization Reference Architecture

A foundational architecture can be represented as:

```text
                         USER
                           │
                           ▼
                    Authentication
                           │
                           ▼
                      AI Application
                           │
                      User Context
                           │
                           ▼
                        AI Agent
                           │
                    Agent Identity
                           │
                           ▼
                  Access Request
                           │
                           ▼
              Policy Enforcement Point
                           │
                           ▼
               Policy Decision Point
                    │           │
                    │           ├── Identity
                    │           ├── Role
                    │           ├── Attributes
                    │           ├── Resource
                    │           ├── Context
                    │           └── Risk
                    │
                    ▼
             Authorization Decision
                    │
              ┌─────┴─────┐
              ▼           ▼
            ALLOW        DENY
              │
              ▼
       Tool / API / Data
              │
              ▼
       Enterprise Resource
```

A secure AI authorization architecture therefore treats access as an explicit policy decision based on **identity, action, resource, authority, and context**, rather than assuming that successful authentication or network location automatically grants permission.
