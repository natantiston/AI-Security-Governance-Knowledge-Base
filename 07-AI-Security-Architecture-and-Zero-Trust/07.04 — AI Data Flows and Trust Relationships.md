# 07.04 — AI Data Flows and Trust Relationships

## Part 1 — Foundations, Data Flow Mapping, and Trust Relationships

### 1. Introduction to AI Data Flows

AI security architecture depends heavily on understanding how data moves through an AI system.

An AI system rarely consists of only:

```text
User → AI → Response
```

A real enterprise AI architecture may look more like:

```text
User
  ↓
AI Application
  ↓
AI Gateway
  ↓
Model
  ↓
Retriever
  ↓
Vector Database
  ↓
Enterprise Database
  ↓
Tool / API
  ↓
External System
```

Every movement of information creates a potential security, privacy, governance, or compliance consideration.

AI data-flow analysis therefore asks:

> **What data is moving, where is it moving, why is it moving, who or what is moving it, and what trust relationship exists at each transition?**

---

### 2. Why AI Data Flows Are Different

Traditional applications generally have predictable data flows.

For example:

```text
Web Application
      ↓
Application Server
      ↓
Database
```

AI systems can introduce additional and less deterministic flows:

```text
User Prompt
      ↓
Model
      ↓
Retrieved Information
      ↓
Tool Output
      ↓
Model Reasoning
      ↓
Generated Output
      ↓
External Action
```

The model may also dynamically determine which information or tools it needs.

This creates additional security boundaries that must be understood.

---

### 3. AI Data Flow as an Architecture Concept

An AI data flow describes the movement of information between components.

A simplified representation is:

```text
Source
  ↓
Processing
  ↓
Transformation
  ↓
Storage
  ↓
Retrieval
  ↓
Model Processing
  ↓
Output
  ↓
Destination
```

For example:

```text
Customer Document
      ↓
Document Processing
      ↓
Chunking
      ↓
Embedding
      ↓
Vector Database
      ↓
Retrieval
      ↓
LLM
      ↓
Customer-Service Response
```

Each stage can introduce different security requirements.

---

### 4. Data Flow vs. Trust Relationship

A **data flow** describes movement.

A **trust relationship** describes the degree and nature of reliance between the components involved.

For example:

```text
AI Application
      ↓
Customer Database
```

The data flow may be:

```text
Customer Data → AI Application
```

The trust relationship may be:

```text
AI Application
      ↓
Authorized to read
      ↓
Specific customer records
```

These are related but different concepts.

```text

  ↓

  ↓
```

For example:


### 8. AI Data Sources

AI systems may consume data from many sources.

Examples include:

* Databases.
* Data warehouses.
* Data lakes.
* File shares.
* Document repositories.
* APIs.
* SaaS applications.
* Email systems.
* Collaboration platforms.
* IoT systems.
* Security systems.
* Public websites.
* User-provided content.

Each source may have different ownership and security requirements.

---

### 9. Internal Data Sources

Internal enterprise systems may contain:

```text
HR Data
Finance Data
Customer Data
Security Data
Operational Data
Legal Data
Strategic Data
```

The fact that the data is internal does not automatically mean the AI should have unrestricted access.

For example:

```text
Enterprise AI
      ↓
Internal Network
      ↓
HR Database
```

does not establish authorization.

The AI still requires an explicit access decision.

---

### 10. External Data Sources

AI systems may also retrieve information from external sources.

For example:

```text
AI
 ↓
Web Search
 ↓
External Website
```

or:

```text
AI
 ↓
Third-Party API
```

External information should generally be treated as having a different trust level from enterprise-controlled data.

---

### 11. User-Provided Data

The user prompt itself is a data source.

For example:

```text
User
 ↓
Prompt
 ↓
AI
```

The prompt may contain:

* Personal information.
* Confidential information.
* Credentials.
* Business information.
* Proprietary source code.
* Customer information.

Therefore, user input should not automatically be considered safe or non-sensitive.

---

### 12. Untrusted Input

From a security architecture perspective, user input should generally be treated as untrusted.

```text
User Input
    ↓
[ UNTRUSTED ]
    ↓
Validation
    ↓
AI Processing
```

This principle becomes particularly important because prompts can attempt to influence the AI's behavior.

---

### 13. Retrieved Data as a Data Flow

RAG introduces another important data flow:

```text
User
 ↓
Question
 ↓
Retriever
 ↓
Search Index
 ↓
Documents
 ↓
Model Context
```

The retrieved documents may contain information that is:

* Sensitive.
* Incorrect.
* Malicious.
* Outdated.
* Unauthorized for the requesting user.

Therefore, retrieval itself must be governed.

---

### 14. RAG Data Flow

A more complete RAG flow is:

```text
Enterprise Document
        ↓
Document Ingestion
        ↓
Chunking
        ↓
Embedding
        ↓
Vector Store
        ↓
Retrieval
        ↓
Context Assembly
        ↓
AI Model
        ↓
Generated Response
```

Each transition represents a potential trust relationship.

---

### 15. Data Transformation

AI systems frequently transform data.

Examples:

```text
Document
 ↓
Text Extraction
```

```text
Text
 ↓
Embedding
```

```text
Raw Data
 ↓
Summarization
```

```text
Customer Record
 ↓
AI-Generated Profile
```

Transformation does not necessarily remove the sensitivity of the underlying information.

---

### 16. Data Classification Across Transformations

Consider:

```text
Confidential Document
      ↓
Embedding
      ↓
Vector
```

The transformed representation should still be assessed for appropriate protection.

Similarly:

```text
Personal Data
      ↓
AI Summary
```

The resulting summary may still contain personal information.

Data classification should therefore follow the information through relevant transformations.

---

### 17. Data in Transit

Data moving between AI components should be protected according to its sensitivity.

Example:

```text
AI Application
      ↓
Encrypted Connection
      ↓
Model API
```

Typical controls may include:

* TLS.
* Mutual TLS where appropriate.
* Secure API gateways.
* Certificate management.
* Network controls.

---

### 18. Data at Rest

AI systems may store:

* Prompts.
* Responses.
* Documents.
* Embeddings.
* Logs.
* Model artifacts.
* Conversation histories.
* Tool results.

These repositories may require encryption and access controls.

For example:

```text
AI Data
 ↓
Encrypted Storage
 ↓
Restricted Access
```

---

### 19. Data in Use

AI data is also processed in memory.

Conceptually:

```text
Storage
 ↓
Memory
 ↓
Model Processing
```

Security considerations may include:

* Runtime isolation.
* Workload isolation.
* Access restrictions.
* Secure execution environments.
* Protection against unauthorized memory access.

---

### 20. The Three Data States

A basic AI security model considers:

```text
Data at Rest
      +
Data in Transit
      +
Data in Use
```

For example:

| State      | AI Example      | Security Consideration             |
| ---------- | --------------- | ---------------------------------- |
| At Rest    | Vector database | Encryption + access control        |
| In Transit | AI → API        | TLS + authentication               |
| In Use     | Model context   | Runtime isolation + access control |

---

### 21. Trust Zones

A trust zone is an architectural area where components have similar security assumptions and controls.

An AI environment might contain:

```text
Zone 1 — External
Zone 2 — User/Application
Zone 3 — AI Platform
Zone 4 — Enterprise Data
Zone 5 — Critical Systems
```

The architecture should explicitly define the boundaries between these zones.

### 23. Trust Relationships Between Components

Trust should be represented explicitly.

For example:

```text
AI Application
      ↓
Trusted to authenticate users
```

but:

```text
AI Model
      ↓
Not trusted to determine authorization
```

And:

```text
External Content
      ↓
Not trusted as an instruction source
```

This distinction is fundamental to AI security architecture.

---

### 24. Trust Is Not Binary

Trust should not simply be:

```text
Trusted
    OR
Untrusted
```

A more useful approach is contextual:

```text
Identity
+
Purpose
+
Data
+
Action
+
Context
+
Risk
```

This creates a more precise trust decision.

---

### 25. Contextual Trust

For example:

```text
AI Agent
```

may be authorized to:

```text
Read customer orders
```

but not:

```text
Delete customer accounts
```

Therefore:

```text
AI Agent
     ↓
Trusted for Action A
     ↓
Not Trusted for Action B
```

Trust is tied to a specific purpose.

---

### 26. Transitive Trust

A major AI architecture risk occurs when one component indirectly inherits trust from another.

Example:

```text
User
 ↓
AI
 ↓
Tool
 ↓
Database
```

If the database assumes:

```text
"AI is trusted because the user is trusted"
```

without independently validating authorization, the architecture may create excessive trust.

---

### 27. Avoiding Transitive Trust

A stronger model is:

```text
User
 ↓
Authentication
 ↓
AI Authorization
 ↓
Tool Authorization
 ↓
API Authorization
 ↓
Data Authorization
```

Each layer makes an appropriate security decision.

---

### 28. AI as a Trust Broker

An AI application may sit between users and enterprise systems.

```text
User
   ↓
AI
   ↓
Enterprise Systems
```

This makes the AI a potential **trust broker**.

The danger is that the AI could become a privileged intermediary if it receives more authority than users actually possess.

---

### 29. AI as a Privileged Intermediary

Example:

```text
Employee
   ↓
AI Assistant
   ↓
Service Account
   ↓
All HR Records
```

If every employee can ask the AI to retrieve HR records, the AI has effectively become a privilege-escalation mechanism.

The correct architecture should preserve user-level authorization.

---

### 30. Identity Propagation

A secure data flow can propagate identity:

```text
Employee
   ↓
AI Application
   ↓
Employee Context
   ↓
Enterprise API
```

The downstream system can then evaluate:

```text
Who is the user?
What is the AI?
What action is requested?
What resource is being accessed?
```

This is stronger than relying solely on a generic AI service account.

---

### 31. Service Identity

AI components should also have their own service identities.

For example:

```text
AI Application
     ↓
AI-App-001

RAG Service
     ↓
AI-RAG-001

Tool Gateway
     ↓
AI-Tool-001
```

This allows security teams to distinguish different components and activities.

---

### 32. Identity and Data Flow

Every significant data flow should ideally answer:

```text
Who is sending the data?
Who is receiving it?
Under which identity?
For what purpose?
With what permission?
```

For example:

```text
CRM
 ↓
AI-RAG-001
 ↓
Read Customer Data
 ↓
Approved Purpose
```

---

### 33. Authorization at the Data Flow

Authentication establishes identity.

Authorization determines whether the identity may perform the requested operation.

Therefore:

```text
Authentication
      ↓
"Who are you?"

Authorization
      ↓
"What are you allowed to access?"
```

Both are required.

---

### 34. Data Flow Authorization

Suppose:

```text
AI Agent → Customer Database
```

The architecture should define:

```text
Allowed:
READ customer order

Denied:
READ unrelated employee records

Denied:
DELETE customer

Denied:
MODIFY database schema
```

The data flow should therefore have a defined authorization scope.

---

### 35. Least Privilege in Data Flows

Least privilege means that a component should receive only the data and permissions required for its function.

Weak:

```text
AI
 ↓
Entire Enterprise Database
```

Stronger:

```text
AI
 ↓
Approved API
 ↓
Required Dataset
 ↓
Specific Records
```

This reduces the potential blast radius of compromise or misuse.

---

### 36. Data Minimization

Data minimization complements least privilege.

If an AI needs:

```text
Customer Country
Customer Product
Customer Order Status
```

there may be no reason to provide:

```text
Passport Number
Bank Account
Full Address
```

The safest data flow is often the smallest data flow that still satisfies the business requirement.

---

### 37. Purpose Limitation

Data should cross a trust boundary for a defined business purpose.

For example:

```text
Purpose:
Customer Support

Data:
Order Status

Allowed:
Customer Support Agent
```

The same data should not automatically become available for:

```text
Marketing
Employee Analytics
Training
Other AI Applications
```

unless separately authorized.

---

### 38. Data Ownership

Every important AI data source should have an identifiable owner.

Examples:

```text
CRM Data → Customer Data Owner
HR Data → HR Data Owner
Financial Data → Finance Data Owner
Security Data → Security Owner
```

The AI platform owner should not automatically become the data owner.

---

### 39. Data Stewardship

Data stewards may define:

* Classification.
* Permitted use.
* Retention.
* Access rules.
* Quality requirements.
* Sharing restrictions.

This becomes especially important when AI combines information from multiple enterprise sources.

---

### 40. Cross-Domain Data Flows

AI can combine data from different security domains.

Example:

```text
CRM Data ─────┐
              │
HR Data ──────┼──► AI
              │
Finance Data ─┘
```

This creates a composite trust problem.

The AI may be able to combine information that individual systems intentionally keep separate.

---

### 41. Data Aggregation Risk

Consider:

```text
System A:
Customer Location

System B:
Customer Income

System C:
Customer Health Information
```

Individually, each system may have different access restrictions.

If AI combines them:

```text
A + B + C
   ↓
AI Profile
```

the resulting information may have a much higher sensitivity than any single dataset.

---

### 42. Cross-Classification Data Flow

When information from different classification levels is combined:

```text
Public
+
Internal
+
Confidential
+
Restricted
```

the resulting dataset may need to inherit the highest applicable protection level.

Security architecture should define how classification is handled during aggregation.

---

### 43. Data Flow Direction

Direction matters.

For example:

```text
Database → AI
```

is different from:

```text
AI → Database
```

and:

```text
AI ↔ Database
```

Read-only data retrieval presents a different risk from write access.

---

### 44. Read vs. Write Trust Relationships

Compare:

```text
AI → Database
READ
```

with:

```text
AI → Database
WRITE
```

and:

```text
AI → Database
DELETE
```

The potential impact increases significantly as the AI receives greater authority.

---

### 45. Execute Authority

The highest-risk data flows may involve execution.

For example:

```text
AI
 ↓
Command
 ↓
Production Server
```

The architecture should introduce additional controls:

```text
AI
 ↓
Command Validation
 ↓
Policy
 ↓
Approval
 ↓
Controlled Execution
```

---

### 46. Data Flow and Agentic AI

Agentic AI introduces dynamic workflows.

For example:

```text
Goal
 ↓
AI Agent
 ↓
Tool Selection
 ↓
Tool A
 ↓
Tool B
 ↓
Tool C
 ↓
Final Action
```

The exact path may not be known in advance.

Therefore, architecture must control not only individual connections but also possible combinations of actions.

---

### 47. Tool Chaining

Suppose:

```text
Tool A:
Read CRM

Tool B:
Send Email
```

Individually, each may appear low-risk.

But together:

```text
CRM
 ↓
Tool A
 ↓
AI
 ↓
Tool B
 ↓
External Email
```

may create a data-exfiltration path.

Trust analysis must therefore consider **composed data flows**.

---

### 48. Data Flow Composition

Security architecture should ask:

> **What can happen when individually permitted capabilities are combined?**

For example:

```text
Read
+
Transform
+
Send
```

may result in:

```text
Sensitive Data Exfiltration
```

even though no single tool appears malicious.

---

### 49. External Data Transfer

When enterprise information leaves the organization:

```text
Enterprise
    ↓
External AI Provider
```

the trust relationship changes.

The architecture should identify:

* Destination.
* Data type.
* Processing purpose.
* Provider.
* Retention.
* Security controls.
* Contractual protections.
* Geographic location.

---

### 50. Third-Party AI Data Flow

A common architecture is:

```text
Enterprise Application
        ↓
AI API
        ↓
Third-Party Model
        ↓
Response
        ↓
Enterprise Application
```

The external provider becomes part of the data-flow architecture.

The organization should understand exactly what crosses the external boundary.

---

### 51. Model Provider Trust

The enterprise may trust a provider for:

```text
Model Processing
```

without necessarily trusting it for:

```text
Long-Term Data Storage
```

or:

```text
Training on Enterprise Data
```

or:

```text
Secondary Use
```

Trust should therefore be scoped to explicit processing activities.

---

### 52. Data Retention in AI Flows

A data flow does not necessarily end when the AI produces a response.

Data may be retained in:

```text
Application Logs
Model Provider Logs
Vector Databases
Conversation History
Monitoring Systems
Backups
Security Systems
```

Therefore:

```text
Data Flow
```

should include relevant storage and retention points.

---

### 53. Hidden Data Flows

An important architecture challenge is discovering flows that are not visible in the primary application diagram.

Examples:

```text
AI Prompt
 ↓
Application Log
```

or:

```text
AI Request
 ↓
Provider Telemetry
```

or:

```text
Document
 ↓
Backup
```

These secondary flows may create additional security and privacy risks.

---

### 54. Shadow AI Data Flows

Employees may introduce AI services without formal approval.

Example:

```text
Employee
 ↓
Copy Confidential Document
 ↓
Public AI Service
```

This creates an unauthorized external data flow.

GRC and security programs should therefore address both:

```text
Approved AI
```

and:

```text
Unapproved / Shadow AI
```

### 56. Data Flow and Threat Modeling

Data-flow diagrams are particularly useful for threat modeling.

Once the flows are known, security teams can ask:

```text
What can be intercepted?
What can be modified?
What can be injected?
What can be exposed?
What can be replayed?
What can cross an unauthorized boundary?
```

This makes data-flow mapping a foundational security activity.

### 57. Threats at AI Data Flows

Common threats include:

* Prompt injection.
* Indirect prompt injection.
* Data exfiltration.
* Unauthorized retrieval.
* Privilege escalation.
* Credential exposure.
* Man-in-the-middle attacks.
* API abuse.
* Cross-tenant access.
* Malicious tool invocation.
* Data poisoning.
* Supply-chain compromise.

Each threat should be associated with the relevant flow.

---

### 58. Trust Relationship Failure

A trust relationship fails when a component receives more authority or information than intended.

Example:

```text
AI
 ↓
Should Read Customer Orders
```

but actually receives:

```text
All Customer Records
```

This represents excessive trust.

---

### 59. Trust Relationship Drift

Trust relationships can change over time.

Initially:

```text
AI → CRM
Read Only
```

Later:

```text
AI → CRM
Read + Write
```

Later:

```text
AI → CRM
Administrative Access
```

This is **trust drift**.

Change management and access reviews should detect such changes.

---

### 60. Trust Relationship Register

A GRC program can maintain a trust relationship register.

Example:

| Relationship           | Trust Granted          | Risk     |
| ---------------------- | ---------------------- | -------- |
| User → AI              | Submit requests        | Medium   |
| AI → RAG               | Retrieve approved data | Medium   |
| AI → CRM               | Read customer records  | High     |
| AI → Payment API       | Initiate transactions  | Critical |
| AI → External Provider | Process prompts        | High     |

This provides management visibility into where AI has meaningful authority.

---

### 61. Data Flow Security Objectives

A mature AI architecture should establish objectives such as:

```text
DF-01
Data flows are identified.

DF-02
Data classification is maintained.

DF-03
Data flows have defined business purposes.

DF-04
Trust relationships are explicit.

DF-05
Authorization is enforced at relevant boundaries.

DF-06
Sensitive data is minimized.

DF-07
External data transfers are controlled.

DF-08
Data flows are encrypted where required.

DF-09
Significant data flows are logged.

DF-10
Material data-flow changes trigger security review.
```

---

### 62. AI Data Flow Assessment Questions

A practical assessment should ask:

1. What data enters the AI system?
2. Where does that data originate?
3. Who owns it?
4. What classification does it have?
5. Where is it stored?
6. What transformations occur?
7. Which AI components process it?
8. Which identities access it?
9. What systems receive AI output?
10. Does data leave the organization?
11. Does a third-party provider process it?
12. Can the AI initiate actions?
13. What controls enforce authorization?
14. What logs are generated?
15. What happens if the trust relationship is compromised?

---

### 63. Data Flow Security Principle

A useful enterprise principle is:

> **Every significant AI data flow should have a defined source, destination, purpose, identity, authorization scope, classification, and security control.**

This prevents AI architecture from becoming an opaque collection of interconnected systems.

---

### 64. GRC Perspective

From a GRC perspective, AI data-flow architecture connects technical design to governance.

The relationship can be represented as:

```text
Data Flow
   ↓
Trust Relationship
   ↓
Threat
   ↓
Risk
   ↓
Control
   ↓
Control Owner
   ↓
Evidence
   ↓
Testing
```

This allows a cybersecurity GRC consultant to translate an AI architecture into an auditable control environment.

---

### 65. Senior-Level Interview Explanation

A strong interview response could be:

> **"When I assess AI data flows, I don't only map where the data travels. I identify what information is crossing each boundary, its classification and business purpose, which identity is responsible for the transfer, what authorization applies, and what trust relationship exists between the source and destination. I then look for excessive data exposure, transitive trust, uncontrolled external transfers, and agentic tool chains that could create unintended attack paths."**

```text
  ↓
MONITORING
```

Every significant AI flow should be explainable through this model.

# 07.04 — AI Data Flows and Trust Relationships

## Part 2 — Data Flow Security, Trust Evaluation, and AI-Specific Threats

### 67. Data Flow Security Controls

An AI data flow should not be considered secure merely because the communication channel is encrypted.

Security must address the entire flow:

```text
Source
  ↓
Identity
  ↓
Authentication
  ↓
Authorization
  ↓
Data Validation
  ↓
Encryption
  ↓
Processing
  ↓
Destination
  ↓
Monitoring
```

Each stage can introduce a different control requirement.

---

### 68. Source Validation

The first security question is:

> **Can the organization trust the source of the data?**

Examples include:

```text
Enterprise Database → Known Source
Employee Upload     → Potentially Untrusted
Public Website      → Untrusted
Third-Party API     → External Trust
AI-Generated Data   → Requires Validation
```

Source trust should be established according to the type and purpose of the data.

---

### 69. Data Provenance

**Data provenance** identifies where information originated and how it was transformed.

Example:

```text
Original Document
      ↓
Document Processing
      ↓
Chunking
      ↓
Embedding
      ↓
Vector Database
      ↓
Retrieved Context
      ↓
AI Response
```

Maintaining provenance helps determine whether the information is trustworthy and appropriate for the intended use.

---

### 70. Provenance in RAG

For RAG systems, the AI should ideally be able to associate retrieved information with its source.

For example:

```text
AI Response
     ↓
Retrieved Context
     ↓
Document ID
     ↓
Source Repository
     ↓
Original Document
```

This supports:

* Traceability.
* Accuracy validation.
* Access control.
* Auditability.
* Incident investigation.

---

### 71. Data Integrity

Data flowing into an AI system should be protected against unauthorized modification.

For example:

```text
Enterprise Document
       ↓
Integrity Check
       ↓
AI Processing
```

If an attacker modifies a trusted document before retrieval, the AI may process malicious or incorrect information.

---

### 72. Data Poisoning

Data poisoning occurs when malicious or incorrect information is deliberately introduced into an AI data source.

Example:

```text
Attacker
   ↓
Malicious Document
   ↓
Knowledge Repository
   ↓
RAG
   ↓
AI
```

The AI may subsequently retrieve the poisoned information and use it in responses or decisions.

---

### 73. Data Poisoning vs. Prompt Injection

These threats are related but different.

**Prompt injection:**

```text
Malicious Instruction
      ↓
AI Context
```

**Data poisoning:**

```text
Malicious Data
      ↓
Knowledge Source
      ↓
AI Context
```

Prompt injection attempts to manipulate AI behavior directly or indirectly, while poisoning attempts to compromise the information on which the AI relies.

---

### 74. Data Validation Before Ingestion

A controlled ingestion pipeline can reduce poisoning risk.

```text
Data Source
    ↓
Validation
    ↓
Malware Scan
    ↓
Classification
    ↓
Content Analysis
    ↓
Approval
    ↓
AI Knowledge Base
```

High-risk sources may require stronger validation before becoming part of enterprise AI context.

---

### 75. Trust Level of Data Sources

Organizations can classify sources by trust level.

Example:

```text
Level 1 — Enterprise Controlled
Level 2 — Approved Third Party
Level 3 — External Public
Level 4 — User Supplied
Level 5 — Unknown
```

The trust level can influence how the AI is allowed to use the information.

---

### 76. Trust Should Not Equal Truth

A trusted source does not necessarily mean every piece of information from that source is accurate.

For example:

```text
Trusted Repository
       ↓
Incorrect Document
       ↓
AI
```

Therefore, trust relationships should consider both:

* **Security trust**
* **Information reliability**

These are separate dimensions.

---

### 77. Data Quality and AI Security

Poor data quality can create security and governance problems.

For example:

```text
Incorrect Customer Status
       ↓
AI Decision
       ↓
Incorrect Customer Action
```

AI security architecture should therefore consider the integrity and quality of important data flows.

---

### 78. Data Classification Propagation

Classification should be considered as data moves through the architecture.

Example:

```text
Restricted Document
      ↓
Extracted Text
      ↓
Embedding
      ↓
Vector Store
      ↓
Retrieved Context
      ↓
AI Response
```

The security requirements should not disappear merely because the representation changes.

---

### 79. Classification Inheritance

A practical rule can be:

```text
Sensitive Source
      ↓
Derived Data
      ↓
Apply Appropriate Protection
```

For example, an AI-generated summary containing confidential information should continue to receive appropriate confidentiality protections.

---

### 80. Data Transformation Risk

Every transformation can change the security properties of information.

Examples:

```text
Document → Text
Text → Embedding
Database → CSV
Data → Summary
Data → AI Decision
```

The security team should ask:

> **Does the transformation create a new security object that requires independent controls?**

---

### 81. Data Aggregation

AI systems frequently aggregate information.

```text
CRM
  +
Billing
  +
Support
  +
Product
  ↓
AI
```

The resulting dataset may reveal more information than any individual source.

This is known as **aggregation risk**.

---

### 82. Inference Risk

AI can sometimes derive sensitive information from apparently non-sensitive data.

Example:

```text
Public Information
      +
Purchase History
      +
Location
      ↓
AI Inference
      ↓
Sensitive Profile
```

Therefore, security assessment should consider not only the sensitivity of input data but also what can be inferred from combining it.

---

### 83. Derived Data

AI-generated information can itself become an enterprise data asset.

Examples:

* Customer profiles.
* Risk scores.
* Fraud indicators.
* Employee summaries.
* Security assessments.
* Business recommendations.

These outputs may require classification, retention, access control, and ownership.

---

### 84. AI Output as a Data Flow

The output flow may be:

```text
AI
 ↓
Generated Content
 ↓
Application
 ↓
User
```

But it can also be:

```text
AI
 ↓
Generated Decision
 ↓
Enterprise API
 ↓
Business Transaction
```

The second flow creates significantly greater security consequences.

---

### 85. Output Trust

AI output should not automatically be considered trusted.

A useful model is:

```text
AI Output
    ↓
Validation
    ↓
Policy Check
    ↓
Human or System Approval
    ↓
Action
```

The required level of validation should depend on the risk of the action.

---

### 86. Human-in-the-Loop Boundary

For high-impact actions, a human approval boundary can be introduced.

```text
AI Recommendation
       ↓
Human Review
       ↓
Approval
       ↓
Execution
```

This can reduce the risk of autonomous AI making inappropriate decisions.

---

### 87. Human-on-the-Loop

In some systems, the human may supervise rather than approve every action.

```text
AI
 ↓
Automated Action
 ↓
Continuous Monitoring
 ↓
Human Intervention if Required
```

This model may be appropriate for lower-risk activities where real-time human approval would be impractical.

---

### 88. Autonomous AI Trust

The more autonomy an AI system receives, the more important trust-boundary controls become.

A simplified risk progression is:

```text
Read Information
      ↓
Generate Recommendation
      ↓
Create Draft
      ↓
Execute Action
      ↓
Execute High-Impact Action
```

The required controls should increase as the AI's authority increases.

---

### 89. Action Classification

AI actions can be classified by impact.

| Level     | Example                        |
| --------- | ------------------------------ |
| Low       | Generate summary               |
| Moderate  | Create support ticket          |
| High      | Modify customer record         |
| Very High | Execute financial transaction  |
| Critical  | Change security infrastructure |

Higher-impact actions require stronger authorization and validation.

---

### 90. Data Flow and Business Impact

Security architecture should connect data flow to business impact.

Example:

```text
AI
 ↓
Payroll API
 ↓
Salary Modification
```

This is not merely an API-security issue.

Potential business impacts include:

* Financial loss.
* Employee impact.
* Fraud.
* Regulatory exposure.
* Reputational damage.

Therefore, the trust relationship should be classified according to business criticality.

---

### 91. Critical Data Flows

Critical flows commonly involve:

* Financial systems.
* Identity systems.
* Security infrastructure.
* Production systems.
* Customer databases.
* Healthcare information.
* Legal information.
* Privileged administration.

These should receive higher assurance requirements.

---

### 92. Data Flow Segmentation

Sensitive flows should be isolated where practical.

For example:

```text
General AI
    │
    ├── Public Data
    │
    └── Internal Data

Privileged AI
    │
    └── Restricted Systems
```

Not every AI workload needs the same network or data access.

---

### 93. Micro-Segmentation

Micro-segmentation can restrict communication between AI workloads.

```text
AI-Agent-A
    ↓
Allowed: CRM API

AI-Agent-B
    ↓
Allowed: HR API

AI-Agent-C
    ↓
Allowed: Security API
```

This reduces lateral movement opportunities.

---

### 94. Egress Control

Outbound communication is especially important for AI systems.

```text
AI
 ↓
Internet
```

is generally broader than:

```text
AI
 ↓
Approved API Gateway
 ↓
Approved Destinations
```

Egress restrictions can reduce data-exfiltration risk.

---

### 95. Allowlisted Destinations

An AI workload may be restricted to approved destinations.

Example:

```text
Allowed:
✓ api.company.com
✓ approved-ai-provider.com

Denied:
✗ Unknown Internet Destination
✗ Personal Email
✗ Unapproved Cloud Storage
```

This creates an enforceable outbound trust boundary.

---

### 96. DNS and Network Controls

Network-level controls can support AI data-flow security through:

* DNS filtering.
* Firewall policies.
* Proxy controls.
* Private endpoints.
* Security groups.
* Network ACLs.
* Service mesh policies.

These controls can limit where AI workloads communicate.

---

### 97. Private AI Connectivity

Where appropriate, enterprise workloads can use private connectivity.

Example:

```text
Enterprise Network
      ↓
Private Endpoint
      ↓
AI Service
```

This can reduce exposure to the public internet.

The exact architecture depends on the cloud and service model.

---

### 98. API Gateway as a Trust Enforcement Point

An API gateway can act as a controlled boundary:

```text
AI
 ↓
API Gateway
 ↓
Authentication
 ↓
Authorization
 ↓
Rate Limiting
 ↓
Validation
 ↓
Enterprise API
```

This centralizes important controls.

---

### 99. Rate Limiting

AI systems can generate large numbers of requests rapidly.

Without controls:

```text
AI Agent
 ↓↓↓↓↓↓↓↓↓↓↓
API
```

With rate limiting:

```text
AI Agent
 ↓
Rate Limit
 ↓
Controlled Requests
 ↓
API
```

This can reduce abuse, resource exhaustion and accidental runaway activity.

---

### 100. AI Cost Boundary

Data flows can also create financial exposure.

For example:

```text
Compromised Agent
      ↓
Thousands of Model Calls
      ↓
Large Cloud Bill
```

Therefore, AI architecture may require:

* Usage limits.
* Budget controls.
* Rate limits.
* Quotas.
* Alerts.
* Automatic shutdown thresholds.

---

### 101. Token and Context Limits

Large context windows can increase both security and cost exposure.

```text
Large Data Retrieval
       ↓
Large Context
       ↓
Model Processing
```

A retrieval system should avoid sending unnecessary information merely because the model can technically process it.

---

### 102. Context Isolation

Different tasks may require different context.

For example:

```text
Customer Support Agent
      ↓
Customer Support Context
```

should not automatically receive:

```text
HR Context
Finance Context
Security Context
```

Context isolation supports least privilege.

---

### 103. Session Isolation

AI conversations can contain sensitive information.

A secure architecture should prevent unintended sharing between sessions.

Weak:

```text
User A Session
       ↓
Shared Context
       ↓
User B Session
```

Stronger:

```text
User A → Session A → Context A

User B → Session B → Context B
```

---

### 104. Memory as a Data Flow

AI memory introduces additional persistence.

```text
User
 ↓
Conversation
 ↓
AI Memory
 ↓
Future Conversation
```

Memory can create a long-lived trust relationship with the AI system.

Security questions include:

* What is stored?
* Why is it stored?
* Who can access it?
* How long is it retained?
* Can the user delete it?
* Can another user retrieve it?

---

### 105. Long-Term Memory Risk

A system may store information that was originally provided for a temporary purpose.

Example:

```text
User
 ↓
Temporary Sensitive Information
 ↓
AI Memory
 ↓
Future Retrieval
```

This can create unintended data persistence.

---

### 106. Conversation History

Conversation histories may contain:

```text
Business Information
Personal Information
Customer Information
Credentials
Internal Discussions
```

Therefore, conversation history should be treated as a potentially sensitive data repository.

---

### 107. Memory Authorization

AI memory should respect identity and authorization boundaries.

For example:

```text
User A
 ↓
Own Memory
```

should not become:

```text
User B
 ↓
User A Memory
```

Cross-user memory access should require explicit authorization.

---

### 108. Data Flow and Secrets

Secrets should not freely move through AI systems.

Examples include:

* Passwords.
* API keys.
* Access tokens.
* Private keys.
* Database credentials.
* Cloud credentials.

A secure pattern is:

```text
AI
 ↓
Secret Reference
 ↓
Secret Manager
 ↓
Controlled Retrieval
 ↓
Approved Tool
```

rather than placing credentials directly into prompts.

---

### 109. Prompt Secret Exposure

A user may accidentally provide:

```text
"My API key is ABC123..."
```

The system should have controls to prevent secrets from being unnecessarily:

```text
Stored
Logged
Retrieved
Displayed
Forwarded
```

---

### 110. Secret Redaction

A security architecture may introduce:

```text
Input
 ↓
Secret Detection
 ↓
Redaction
 ↓
AI
```

For example:

```text
API Key:
<REDACTED>
```

This reduces the probability that secrets become part of model context or logs.

---

### 111. Logging Data Flows

Logs themselves create another data flow.

```text
AI Request
 ↓
Application
 ↓
Logging System
```

The logged content may contain the original prompt, response or sensitive context.

Therefore, logging must be designed carefully.

---

### 112. Secure Logging

AI logging should consider:

* Data minimization.
* Sensitive-data redaction.
* Access control.
* Encryption.
* Retention.
* Integrity.
* Monitoring.

Logging everything may create a second security problem.

---

### 113. Observability vs. Privacy

Security teams need sufficient visibility to investigate incidents.

Privacy and governance teams may require data minimization.

The architecture must balance:

```text
Security Visibility
        ↕
Data Minimization
```

A mature design collects the evidence necessary for security without unnecessarily duplicating sensitive information.

---

### 114. Trust Boundary Monitoring

Monitoring should identify unusual boundary crossings.

Examples:

```text
AI normally:
CRM → AI

Unexpected:
HR → AI
```

or:

```text
AI normally:
AI → CRM

Unexpected:
AI → External Website
```

Such changes may indicate misuse or compromise.

---

### 115. Behavioral Monitoring

A baseline can identify unusual AI activity.

Example:

```text
Normal:
10 CRM queries/hour

Observed:
4,000 CRM queries/hour
```

Potential explanations include:

* Misconfiguration.
* Automation error.
* Prompt injection.
* Compromised credentials.
* Malicious agent behavior.

---

### 116. Trust Relationship Anomalies

Monitoring should look beyond traditional network anomalies.

Examples include:

```text
Unexpected Tool
Unexpected Data Source
Unexpected User
Unexpected Permission
Unexpected Destination
Unexpected Volume
Unexpected Action
```

These are particularly relevant for AI agents.

---

### 117. Data Flow Attack Path

A complete attack path may look like:

```text
Malicious User
      ↓
Prompt Injection
      ↓
AI Agent
      ↓
Authorized Tool
      ↓
Sensitive Database
      ↓
Data Retrieval
      ↓
External Tool
      ↓
Data Exfiltration
```

The security architecture should identify where the attack path can be interrupted.

---

### 118. Multiple Enforcement Points

A stronger architecture could apply:

```text

      ↓
AI Policy
      ↓
Tool Authorization
      ↓
API Authorization
      ↓
Data Authorization
      ↓
DLP
      ↓
Egress Control
      ↓
Monitoring
```

This provides defense in depth.

---

### 119. Trust Boundary Failure Containment

If an AI component is compromised, the architecture should limit the blast radius.

Example:

```text
Compromised AI Agent
       ↓
Restricted Identity
       ↓
Limited Network
       ↓
Limited Data
       ↓
Limited Tools
       ↓
Contained Impact
```

The goal is not merely preventing compromise but limiting its consequences.

---

### 120. Blast Radius

A useful architecture question is:

> **If this AI identity were completely compromised, what could the attacker reach?**

If the answer is:

```text
Everything
```

the trust relationship is excessively broad.

A better answer is:

```text
Specific API
Specific Dataset
Specific Tools
Specific Actions
```

---

### 121. Trust Relationship Scoring

Organizations can assess relationships based on factors such as:

```text
Data Sensitivity
+
Privilege
+
Autonomy
+
External Exposure
+
Business Criticality
+
Blast Radius
```

A relationship with high values across several dimensions should receive stronger controls and assurance.

---

### 122. High-Risk Trust Relationship

Example:

```text
AI Agent
 ↓
Privileged Identity
 ↓
Production Infrastructure
 ↓
Can Execute Commands
 ↓
Internet Access
```

This represents a high-risk trust relationship.

Potential controls include:

* Strong authentication.
* Least privilege.
* Network segmentation.
* Command allowlisting.
* Human approval.
* Session recording.
* Continuous monitoring.
* Emergency revocation.

---

### 123. Low-Risk Trust Relationship

Example:

```text
AI
 ↓
Public Product Documentation
 ↓
Read Only
 ↓
No External Actions
```

The architecture still requires controls, but the potential impact is substantially lower.

This illustrates why trust assessment should be risk-based rather than identical for every data flow.

---

### 124. Risk-Based Data Flow Controls

```text
 ↓

 ↓

 ↓
```

# 07.04 — AI Data Flows and Trust Relationships

## Part 3 — Advanced Architecture, Zero Trust Integration, and GRC Control Design

### 139. AI Data Flow as a Security Decision Path

An AI data flow should be understood not merely as movement of information, but as a sequence of security decisions.

A typical enterprise flow may look like:

```text
User
  ↓
Identity Verification
  ↓
AI Application
  ↓
Data Access Decision
  ↓
Retrieval
  ↓
Model Processing
  ↓
Tool Authorization
  ↓
Enterprise API
  ↓
Business System
```

At every stage, the architecture should determine whether the next step is permitted.

---

### 140. Trust Evaluation at Every Hop

A secure architecture should avoid assuming that trust established at one point automatically remains valid throughout the entire flow.

For example:

```text
User
 ↓
AI
 ↓
RAG
 ↓
API
 ↓
Database
```

Authentication at the AI application does not automatically authorize:

```text
AI → RAG
RAG → API
API → Database
```

Each interaction may require its own security decision.

---

### 141. Hop-by-Hop Trust

This concept can be represented as:

```text
User → AI
   ↓
Trust Decision 1

AI → RAG
   ↓
Trust Decision 2

RAG → Data Store
   ↓
Trust Decision 3

AI → Tool
   ↓
Trust Decision 4

Tool → API
   ↓
Trust Decision 5
```

This prevents a single compromised component from automatically inheriting the privileges of every downstream system.

---

### 142. End-to-End Trust

Hop-by-hop security should be complemented by end-to-end controls.

For example:

```text
User
 ↓
AI
 ↓
API
 ↓
Database
```

The database should ultimately enforce:

> Is this particular user and workload combination authorized to access this particular resource?

This provides protection even if an intermediate component behaves incorrectly.

---

### 143. Identity Context Propagation

A strong architecture preserves relevant identity context throughout the flow.

```text
Employee
   ↓
AI Application
   ↓
User Identity
   ↓
Authorization Service
   ↓
Enterprise API
```

The downstream system can then make an authorization decision based on the actual user rather than blindly trusting the AI.

---

### 144. Delegated Authorization

In some architectures, the AI acts on behalf of the user.

Conceptually:

```text
User
 ↓
Delegates Limited Authority
 ↓
AI
 ↓
Specific Resource
```

The delegated authority should be:

* Scoped.
* Time-limited where appropriate.
* Auditable.
* Revocable.

---

### 145. Delegation vs. Impersonation

These concepts should be distinguished.

**Impersonation:**

```text
AI → Pretends to be User
```

**Delegation:**

```text
AI → Acts on Behalf of User
```

Delegation can provide stronger accountability because the system can preserve both:

```text
Human Identity
+
AI Identity
```

---

### 146. Dual Identity Model

A useful audit record can contain:

```text
Human:
Jonathan

AI:
Customer-Agent-01

Action:
Read Customer Order

Resource:
Order-12345

Decision:
ALLOW
```

This improves attribution and forensic investigation.

---

### 147. AI Identity as a First-Class Security Principal

AI workloads should be treated as security principals rather than anonymous application components.

Examples:

```text
AI-Agent-CustomerSupport
AI-Agent-Finance
AI-Agent-Security
AI-RAG-Production
AI-Model-Gateway
```

Each identity can then have:

* Defined permissions.
* Ownership.
* Lifecycle management.
* Monitoring.
* Access reviews.

---

### 148. Workload Identity

Where possible, workload identity should replace static credentials.

```text
AI Workload
    ↓
Workload Identity
    ↓
Short-Lived Credential
    ↓
Approved Service
```

This reduces the risk associated with long-lived API keys and passwords.

---

### 149. Short-Lived Credentials

Instead of:

```text
AI
 ↓
Permanent API Key
```

a stronger pattern is:

```text
AI
 ↓
Identity Provider
 ↓
Short-Lived Token
 ↓
API
```

If the token is compromised, its exposure window can be reduced.

---

### 150. Token Scope

Tokens should be limited to the minimum required capability.

Example:

```text
Token:
crm.read
```

rather than:

```text
Token:
crm.read
crm.write
crm.delete
admin
```

The scope should match the AI's actual business function.

---

### 151. Audience Restriction

A credential issued for one service should not automatically be usable against another service.

Example:

```text
AI Token
 ↓
Audience = CRM API
```

Attempting:

```text
AI Token
 ↓
Security Administration API
```

should fail.

This prevents credential reuse across trust boundaries.

---

### 152. Data Flow and Zero Trust

Zero Trust can be applied to AI data flows through several principles:

```text
Never Trust Implicitly
Verify Explicitly
Use Least Privilege
Assume Breach
Continuously Evaluate
```

The AI workload should not receive broad trust merely because it operates inside the corporate network.

---

### 153. AI Inside the Corporate Network

A common architectural misconception is:

```text
AI
 ↓
Internal Network
 ↓
Trusted
```

Internal location does not automatically establish trust.

A better model is:

```text
AI
 ↓
Identity
 ↓
Policy
 ↓
Authorization
 ↓
Specific Resource
```

This is especially important for cloud and hybrid environments.

---

### 154. Zero Trust Data Flow

A Zero Trust AI flow may look like:

```text
User
 ↓
Authenticate
 ↓
Device / Context Evaluation
 ↓
AI Gateway
 ↓
Policy Decision
 ↓
AI Workload
 ↓
Data Authorization
 ↓
Approved Data
 ↓
Tool Authorization
 ↓
Approved Action
```

Trust is evaluated continuously rather than granted permanently.

---

### 155. Policy Decision Point

A **Policy Decision Point (PDP)** determines whether an action should be permitted.

Example:

```text
AI Request
     ↓
┌───────────────┐
│ Policy Engine │
└───────┬───────┘
        ↓
   ALLOW / DENY
```

The AI should not be the ultimate authority for high-risk authorization decisions.

---

### 156. Policy Enforcement Point

A **Policy Enforcement Point (PEP)** applies the decision.

For example:

```text
AI
 ↓
API Gateway
 ↓
Policy Decision
 ↓
Policy Enforcement
 ↓
Enterprise API
```

This separates policy determination from policy enforcement.

---

### 157. AI Policy Architecture

A mature architecture may include:

```text
                ┌───────────────┐
                │ Policy Engine │
                └───────┬───────┘
                        │
                  ALLOW / DENY
                        │
User → AI → Gateway → Tool → API
              │
              └── Enforcement
```

This provides a central point for consistent authorization decisions.

---

### 158. Attribute-Based Access Control

AI data flows can benefit from **ABAC**, where access decisions consider attributes.

Example:

```text
User:
Department = Finance

AI:
Purpose = Financial Reporting

Data:
Classification = Confidential

Action:
Read

Context:
Approved Environment
```

The policy can evaluate these attributes before allowing access.

---

### 159. Role-Based Access Control

RBAC can also be used.

Example:

```text
Role:
Customer Support AI

Permissions:
Read Customer Orders
Create Support Tickets
```

RBAC is useful where permissions are relatively stable.

---

### 160. RBAC and ABAC Together

Enterprise AI environments may combine both models.

```text
RBAC
+
ABAC
+
Risk Context
```

For example:

```text
Role = Finance AI
AND
Department = Finance
AND
Purpose = Approved
AND
Resource = Financial Data
```

This can provide more precise control.

---

### 161. Data-Level Authorization

Authorization should sometimes operate below the application level.

For example:

```text
AI
 ↓
Customer API
 ↓
Customer Record Authorization
```

The system should determine whether the AI is permitted to access the **specific record**, not merely whether it can connect to the API.

---

### 162. Row-Level Security

A database may enforce access at the row level.

Example:

```text
Customer A
Customer B
Customer C
```

User A may only receive:

```text
Customer A
```

even though the AI application can technically query the same database.

This helps prevent broad data exposure.

---

### 163. Attribute-Level Security

Even within an authorized record, not every field may be accessible.

Example:

```text
Customer Record

Name              → Allowed
Order Status      → Allowed
Phone Number      → Allowed
Bank Account      → Denied
Identity Document → Denied
```

This creates finer-grained trust boundaries.

---

### 164. Purpose-Based Data Access

The same user may require different access depending on the task.

For example:

```text
Purpose:
Customer Support

Allowed:
Order Status

Not Required:
Financial Profile
```

Purpose-based restrictions help prevent AI from retrieving excessive information.

---

### 165. Dynamic Data Filtering

A retrieval layer can filter information before it reaches the model.

```text
Enterprise Repository
       ↓
Authorization Filter
       ↓
Relevant + Authorized Data
       ↓
AI Context
```

This is stronger than retrieving first and hoping the model does not disclose unauthorized information.

---

### 166. Security Filtering Before Model Context

A key architecture principle is:

> **Authorization should occur before sensitive information enters the model context whenever practical.**

Weak:

```text
Database
 ↓
Everything Retrieved
 ↓
AI
 ↓
Model Decides What to Show
```

Stronger:

```text
Database
 ↓
Authorization Filter
 ↓
Approved Data
 ↓
AI
```

---

### 167. Why Model-Level Filtering Is Insufficient

An AI model may be capable of following instructions, but it should not be treated as the primary access-control mechanism.

For example:

```text
System:
"Never reveal confidential records."
```

is not equivalent to:

```text
Authorization Service:
User does not have permission.
ACCESS DENIED.
```

The second is an enforceable security control.

---

### 168. Retrieval-Time Authorization

Authorization should ideally be evaluated when information is retrieved.

```text
User Request
 ↓
Retrieval Request
 ↓
Authorization Check
 ↓
Approved Documents
 ↓
Model
```

This reduces the possibility of unauthorized documents entering the model context.

---

### 169. Index-Level Security

Vector indexes should also be protected.

Potential controls include:

* Tenant-specific indexes.
* Namespace isolation.
* Metadata filters.
* Access policies.
* Separate credentials.
* Encryption.
* Administrative controls.

The index should not become a bypass around source-system permissions.

---

### 170. RAG Permission Synchronization

A common challenge is maintaining synchronization between:

```text
Source System Permissions
```

and:

```text
RAG Permissions
```

For example:

```text
Document:
Employee Confidential Report

Source:
HR Repository

User:
No HR Permission

RAG:
Incorrectly Accessible
```

The RAG system has created a new unauthorized trust path.

---

### 171. Permission Revocation

When access is removed from the source system:

```text
User
 ↓
No Longer Authorized
```

the RAG system should not continue granting access indefinitely.

This requires appropriate synchronization, re-indexing, filtering or authorization enforcement.

---

### 172. Stale Data Risk

AI systems may retain information after the source data has changed.

Example:

```text
Original:
Employee Role = Manager

Source Updated:
Employee Role = Employee

AI Index:
Still contains "Manager"
```

Stale information can create both security and business risks.

---

### 173. Data Lifecycle Flow

AI data should be considered throughout its lifecycle:

```text

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

```

Security requirements can change at each stage.

### 174. Data Retention Boundary

A data flow should identify where information becomes persistent.

For example:

```text

 ↓
AI
 ↓
Conversation History
```

The moment the prompt enters persistent storage, a new data lifecycle requirement may apply.

---

### 175. Deletion and Propagation

Deleting source data does not necessarily remove all copies.

Example:

```text

      ↓
AI Index
      ↓
Cache
      ↓
Conversation History
      ↓
Backup
```

A deletion requirement may therefore need to address multiple locations.

### 176. Data Replication

AI platforms may replicate information for:

* Availability.
* Performance.
* Disaster recovery.
* Geographic distribution.

Example:

```text

        ↓
Replica
        ↓
Backup
```

Each replica represents another location where the organization must understand trust and access.

### 177. Geographic Trust Boundaries

Data may cross geographic boundaries:

```text

 ↓
EU AI Service
 ↓
Non-EU Provider
```

The architecture should identify where processing occurs and whether geographic movement introduces additional regulatory or contractual requirements.

### 178. Third-Party Processing Chain

The trust relationship may extend beyond the primary AI provider.

Example:

```text

   ↓

   ↓
Cloud Provider
   ↓
Subprocessor
```

The organization should understand relevant downstream processing relationships.

### 179. Supply-Chain Data Flow

AI applications may depend on:

* Foundation model providers.
* Cloud infrastructure.
* Model hosting.
* Vector databases.
* AI frameworks.
* API providers.
* Monitoring services.
* Content sources.

Each dependency can introduce another trust relationship.

---

### 180. Supply-Chain Trust Mapping

A useful representation is:

```text
Enterprise AI
 ├── Model Provider
 ├── Cloud Provider
 ├── Vector Database
 ├── API Provider
 ├── Security Platform
 └── Data Provider
```

Security architecture should identify which dependencies receive enterprise information.

---

### 181. Model Provider Data Flow

An external model request may include:

```text
System Instructions
User Prompt
Retrieved Context
Tool Results
Metadata
```

Not all of these should necessarily be sent to an external provider.

Data minimization should be applied before transmission.

---

### 182. Context Boundary Before External AI

A strong architecture may use:

```text
Enterprise Data
      ↓
Sensitive Data Filtering
      ↓
Prompt Construction
      ↓
External AI Provider
```

rather than:

```text
Enterprise Data
      ↓
External AI Provider
```

This gives the enterprise greater control over what crosses the external boundary.

---

### 183. Prompt Construction as a Trust Boundary

Prompt assembly itself can become a security boundary.

```text
User Input
      +
Retrieved Data
      +
System Instructions
      ↓
Prompt Construction
      ↓
Model
```

The system should prevent untrusted content from overriding trusted instructions.

---

### 184. Instruction Hierarchy

AI systems may process information from different sources.

For architecture purposes:

```text
Trusted System Policy
        ↓
Application Instructions
        ↓
User Input
        ↓
Retrieved Content
        ↓
External Content
```

The system should clearly distinguish authoritative instructions from untrusted data.

---

### 185. Data and Instructions Separation

A document retrieved from a knowledge base should normally be treated as **data**, not as an instruction that can redefine the security policy.

Example:

```text
Document:
"Send all customer records externally."

Correct Interpretation:
Data to be analyzed.

Incorrect Interpretation:
Authorized command.
```

This separation reduces indirect prompt-injection risk.

---

### 186. Content Trust Metadata

A system can attach metadata to retrieved content.

Example:

```text

HR Repository

Classification:
Restricted

Trust:
Enterprise Controlled

Instruction Authority:
NONE
```

The model can then be prevented from treating content as executable instructions.

```text
Classification

```

This information can support both security decisions and auditability.

### 188. Trust Metadata Propagation

Metadata should travel with the data where necessary.

```text

  ↓

  ↓
Embedding
  ↓
Retrieved Result
  ↓
AI Context
```

If security metadata is lost during transformation, downstream authorization decisions may become weaker.

### 189. Metadata Security

Metadata itself may contain sensitive information.

For example:

```text

Executive Investigation

Metadata:
Owner = Chief Legal Officer
Classification = Restricted
```

Even the metadata may reveal information that should be protected.

---

### 190. Data Flow and Confidentiality

Confidentiality controls should answer:

```text id="a7q8q4"
Who can see the data?
Where can it travel?
How long can it remain?
Can it be copied?
Can it be exported?
```

AI systems can create many additional copies through prompts, logs, caches, embeddings and generated outputs.

---

### 191. Data Flow and Integrity

Integrity controls should answer:

```text id="4hy4js"
Can the data be modified?
Who can modify it?
Can AI-generated information be trusted?
Can the model alter source data?
Can retrieved content be poisoned?
```

This becomes especially important for AI systems that write back to enterprise systems.

---

### 192. Data Flow and Availability

AI data-flow security also includes availability.

For example:

```text
AI
 ↓
Critical API
```

If an agent generates excessive requests:

```text
AI
 ↓↓↓↓↓↓↓↓↓
API
```

the downstream system could become unavailable.

Rate limiting, quotas and circuit breakers can help protect critical services.

---

### 193. Circuit Breakers

A circuit breaker can interrupt abnormal activity.

```text
AI
 ↓
API
 ↓
Threshold Exceeded
 ↓
Circuit Breaker
 ↓
Requests Blocked
```

This is useful for runaway agents or compromised workloads.

---

### 194. Transaction Limits

High-risk AI actions can be constrained.

Example:

```text
AI Payment Agent

Maximum:
€1,000 per transaction

Maximum:
€5,000 per day
```

A request exceeding the limit can be routed for human approval.

---

### 195. Transaction Approval Boundary

A secure financial workflow might be:

```text

 ↓
Prepare Transaction
 ↓
Risk Check
 ↓
Human Approval
 ↓
Payment API
```

The AI does not independently control the complete financial process.

---

### 196. High-Impact Decision Boundary

The same principle can apply to sensitive decisions.

```text
AI
 ↓
Recommendation
 ↓
Human Review
 ↓
Decision
```

This can be particularly relevant where an AI output has significant consequences for individuals or business operations.

---

### 197. Trust Boundary and Non-Repudiation

For high-value actions, the architecture may need strong evidence of:

```text

Which AI?
What data was used?
What policy allowed it?

```

This supports accountability and investigation.

The AI should not be able to freely manipulate the control plane merely because it can access the data plane.

### 223. AI Data Flow Design Principles

A mature enterprise architecture should apply:

**Principle 1 — Explicit Flow**

Every significant data movement must be known.

**Principle 2 — Explicit Trust**

Trust must be established rather than assumed.

**Principle 3 — Least Data**

Transfer only information required for the business purpose.

**Principle 4 — Least Privilege**

Grant only required authority.

**Principle 5 — Independent Authorization**

Do not rely on the model to enforce enterprise authorization.

**Principle 6 — Identity Preservation**

Maintain human and AI identity context where required.

**Principle 7 — Controlled Transformation**

Protect derived and transformed data.

**Principle 8 — Controlled Egress**

Restrict external destinations.

**Principle 9 — Continuous Monitoring**

Detect abnormal data-flow behavior.

**Principle 10 — Containment**

Design boundaries to limit blast radius.

### 225. Senior Security Architecture Principle

The central principle is:

> **The security of an AI system is determined not only by the security of its individual components, but by the trust relationships created when those components exchange data and authority.**

A secure AI architecture therefore treats every meaningful data flow as a potential trust decision and applies appropriate identity, authorization, data protection, monitoring and containment controls.

### 226. AI Data Flow Architecture Model

A practical enterprise AI data-flow model can be represented as:

```text
                                    │
              ┌─────────────────────┼─────────────────────┐
```

### 311. Architecture Review Scenario

Consider:

> An AI assistant is requested to access CRM, HR and finance systems so that it can answer employee questions and perform administrative tasks.

The first architectural response should not be:

> "Give the AI access to all three systems."

Instead, decompose the requirement:

```text
Question Type
      ↓
Required Data
      ↓
Required System
      ↓
Required Action
      ↓
Required Identity
      ↓
Required Permission
```

This prevents broad access from becoming the default design.

```text
       └── CRM → No Access
```

```text
       ↓
```

### 320. AI Data Flow Security Checklist

A senior security review can use:

**Source**

* Is the source known?
* Is the source trustworthy?
* Is provenance maintained?

**Data**

* What is the classification?
* Is sensitive data minimized?
* Can the AI infer additional sensitive information?

**Identity**

* What human identity is involved?
* What AI/workload identity is involved?
* Are identities separated?

**Authorization**

* Is access least privilege?
* Is authorization enforced outside the model?
* Is data-level authorization implemented?

**Boundary**

* Does the flow cross an internal or external trust boundary?
* Is geographic processing relevant?
* Are third parties involved?

**Action**

* Can the AI modify data?
* Can it execute transactions?
* Can it invoke multiple tools?

**Network**

* Is egress controlled?
* Are private connections used where appropriate?
* Is segmentation implemented?

**Monitoring**

* Are prompts and tool calls appropriately logged?
* Are unusual data flows detected?
* Can the activity be correlated to identity?

**Resilience**

* Can the AI identity be revoked?
* Is there a kill switch?
* Is blast radius limited?

### 322. AI Data Flow Control Statement

A formal control statement could be:

Trust relationships between AI workloads, users, data stores, tools, APIs and external services shall be explicitly authorized, monitored and periodically reassessed."**

### 324. Risk Statement

A representative risk statement is:

### 325. Control Objective

The corresponding control objective is:

### 337. Core Principles for AI Data Flows and Trust

1. **Every important AI data flow must be identifiable.**
2. **Every trust relationship must have an explicit business and security purpose.**
3. **Network location must never be the sole basis for trust.**
4. **AI workloads must have distinct identities.**
5. **Human and AI identities should remain attributable.**
6. **Authorization must be enforced outside the model.**
7. **Sensitive data should be filtered before unnecessary exposure.**
8. **RAG must preserve appropriate authorization boundaries.**
9. **AI tools must be independently authorized.**
10. **External AI providers must be treated as separate trust boundaries.**
11. **AI-generated output must not automatically be considered trusted.**
12. **High-impact actions require stronger validation and approval.**
13. **Logging must provide security visibility without creating unnecessary data exposure.**
14. **Trust should be continuously evaluated rather than permanently assumed.**
15. **Architecture must limit blast radius when an AI identity or component is compromised.**
16. **Every material change to an AI data flow should trigger appropriate security reassessment.**
17. **Control effectiveness must be demonstrated through evidence and testing.**
18. **AI data-flow architecture should directly support enterprise risk management and GRC assurance.**
