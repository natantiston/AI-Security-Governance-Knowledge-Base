# 07.04 — AI Data Flows and Trust Relationships

## Part 1 — Foundations, Data Flow Mapping, and Trust Relationships

### 1. Introduction to AI Data Flows

AI security architecture depends heavily on understanding how data moves through an AI system.

An AI system rarely consists of only:

```text
User → AI → Response
```

A real enterprise AI architecture may look more like:

```text
User
  ↓
AI Application
  ↓
AI Gateway
  ↓
Model
  ↓
Retriever
  ↓
Vector Database
  ↓
Enterprise Database
  ↓
Tool / API
  ↓
External System
```

Every movement of information creates a potential security, privacy, governance, or compliance consideration.

AI data-flow analysis therefore asks:

> **What data is moving, where is it moving, why is it moving, who or what is moving it, and what trust relationship exists at each transition?**

---

### 2. Why AI Data Flows Are Different

Traditional applications generally have predictable data flows.

For example:

```text
Web Application
      ↓
Application Server
      ↓
Database
```

AI systems can introduce additional and less deterministic flows:

```text
User Prompt
      ↓
Model
      ↓
Retrieved Information
      ↓
Tool Output
      ↓
Model Reasoning
      ↓
Generated Output
      ↓
External Action
```

The model may also dynamically determine which information or tools it needs.

This creates additional security boundaries that must be understood.

---

### 3. AI Data Flow as an Architecture Concept

An AI data flow describes the movement of information between components.

A simplified representation is:

```text
Source
  ↓
Processing
  ↓
Transformation
  ↓
Storage
  ↓
Retrieval
  ↓
Model Processing
  ↓
Output
  ↓
Destination
```

For example:

```text
Customer Document
      ↓
Document Processing
      ↓
Chunking
      ↓
Embedding
      ↓
Vector Database
      ↓
Retrieval
      ↓
LLM
      ↓
Customer-Service Response
```

Each stage can introduce different security requirements.

---

### 4. Data Flow vs. Trust Relationship

A **data flow** describes movement.

A **trust relationship** describes the degree and nature of reliance between the components involved.

For example:

```text
AI Application
      ↓
Customer Database
```

The data flow may be:

```text
Customer Data → AI Application
```

The trust relationship may be:

```text
AI Application
      ↓
Authorized to read
      ↓
Specific customer records
```

These are related but different concepts.

A useful AI data-flow model identifies six fundamental elements:

```text

  ↓

  ↓
Processing
  ↓

  ↓

  ↓

```

For example:

```text
CRM
 ↓

 ↓
RAG Processing
 ↓

 ↓

```

### 8. AI Data Sources

AI systems may consume data from many sources.

Examples include:

* Databases.
* Data warehouses.
* Data lakes.
* File shares.
* Document repositories.
* APIs.
* SaaS applications.
* Email systems.
* Collaboration platforms.
* IoT systems.
* Security systems.
* Public websites.
* User-provided content.

Each source may have different ownership and security requirements.

---

### 9. Internal Data Sources

Internal enterprise systems may contain:

```text
HR Data
Finance Data
Customer Data
Security Data
Operational Data
Legal Data
Strategic Data
```

The fact that the data is internal does not automatically mean the AI should have unrestricted access.

For example:

```text
Enterprise AI
      ↓
Internal Network
      ↓
HR Database
```

does not establish authorization.

The AI still requires an explicit access decision.

---

### 10. External Data Sources

AI systems may also retrieve information from external sources.

For example:

```text
AI
 ↓
Web Search
 ↓
External Website
```

or:

```text
AI
 ↓
Third-Party API
```

External information should generally be treated as having a different trust level from enterprise-controlled data.

---

### 11. User-Provided Data

The user prompt itself is a data source.

For example:

```text
User
 ↓
Prompt
 ↓
AI
```

The prompt may contain:

* Personal information.
* Confidential information.
* Credentials.
* Business information.
* Proprietary source code.
* Customer information.

Therefore, user input should not automatically be considered safe or non-sensitive.

---

### 12. Untrusted Input

From a security architecture perspective, user input should generally be treated as untrusted.

```text
User Input
    ↓
[ UNTRUSTED ]
    ↓
Validation
    ↓
AI Processing
```

This principle becomes particularly important because prompts can attempt to influence the AI's behavior.

---

### 13. Retrieved Data as a Data Flow

RAG introduces another important data flow:

```text
User
 ↓
Question
 ↓
Retriever
 ↓
Search Index
 ↓
Documents
 ↓
Model Context
```

The retrieved documents may contain information that is:

* Sensitive.
* Incorrect.
* Malicious.
* Outdated.
* Unauthorized for the requesting user.

Therefore, retrieval itself must be governed.

---

### 14. RAG Data Flow

A more complete RAG flow is:

```text
Enterprise Document
        ↓
Document Ingestion
        ↓
Chunking
        ↓
Embedding
        ↓
Vector Store
        ↓
Retrieval
        ↓
Context Assembly
        ↓
AI Model
        ↓
Generated Response
```

Each transition represents a potential trust relationship.

---

### 15. Data Transformation

AI systems frequently transform data.

Examples:

```text
Document
 ↓
Text Extraction
```

```text
Text
 ↓
Embedding
```

```text
Raw Data
 ↓
Summarization
```

```text
Customer Record
 ↓
AI-Generated Profile
```

Transformation does not necessarily remove the sensitivity of the underlying information.

---

### 16. Data Classification Across Transformations

Consider:

```text
Confidential Document
      ↓
Embedding
      ↓
Vector
```

The transformed representation should still be assessed for appropriate protection.

Similarly:

```text
Personal Data
      ↓
AI Summary
```

The resulting summary may still contain personal information.

Data classification should therefore follow the information through relevant transformations.

---

### 17. Data in Transit

Data moving between AI components should be protected according to its sensitivity.

Example:

```text
AI Application
      ↓
Encrypted Connection
      ↓
Model API
```

Typical controls may include:

* TLS.
* Mutual TLS where appropriate.
* Secure API gateways.
* Certificate management.
* Network controls.

---

### 18. Data at Rest

AI systems may store:

* Prompts.
* Responses.
* Documents.
* Embeddings.
* Logs.
* Model artifacts.
* Conversation histories.
* Tool results.

These repositories may require encryption and access controls.

For example:

```text
AI Data
 ↓
Encrypted Storage
 ↓
Restricted Access
```

---

### 19. Data in Use

AI data is also processed in memory.

Conceptually:

```text
Storage
 ↓
Memory
 ↓
Model Processing
```

Security considerations may include:

* Runtime isolation.
* Workload isolation.
* Access restrictions.
* Secure execution environments.
* Protection against unauthorized memory access.

---

### 20. The Three Data States

A basic AI security model considers:

```text
Data at Rest
      +
Data in Transit
      +
Data in Use
```

For example:

| State      | AI Example      | Security Consideration             |
| ---------- | --------------- | ---------------------------------- |
| At Rest    | Vector database | Encryption + access control        |
| In Transit | AI → API        | TLS + authentication               |
| In Use     | Model context   | Runtime isolation + access control |

---

### 21. Trust Zones

A trust zone is an architectural area where components have similar security assumptions and controls.

An AI environment might contain:

```text
Zone 1 — External
Zone 2 — User/Application
Zone 3 — AI Platform
Zone 4 — Enterprise Data
Zone 5 — Critical Systems
```

The architecture should explicitly define the boundaries between these zones.

### 23. Trust Relationships Between Components

Trust should be represented explicitly.

For example:

```text
AI Application
      ↓
Trusted to authenticate users
```

but:

```text
AI Model
      ↓
Not trusted to determine authorization
```

And:

```text
External Content
      ↓
Not trusted as an instruction source
```

This distinction is fundamental to AI security architecture.

---

### 24. Trust Is Not Binary

Trust should not simply be:

```text
Trusted
    OR
Untrusted
```

A more useful approach is contextual:

```text
Identity
+
Purpose
+
Data
+
Action
+
Context
+
Risk
```

This creates a more precise trust decision.

---

### 25. Contextual Trust

For example:

```text
AI Agent
```

may be authorized to:

```text
Read customer orders
```

but not:

```text
Delete customer accounts
```

Therefore:

```text
AI Agent
     ↓
Trusted for Action A
     ↓
Not Trusted for Action B
```

Trust is tied to a specific purpose.

---

### 26. Transitive Trust

A major AI architecture risk occurs when one component indirectly inherits trust from another.

Example:

```text
User
 ↓
AI
 ↓
Tool
 ↓
Database
```

If the database assumes:

```text
"AI is trusted because the user is trusted"
```

without independently validating authorization, the architecture may create excessive trust.

---

### 27. Avoiding Transitive Trust

A stronger model is:

```text
User
 ↓
Authentication
 ↓
AI Authorization
 ↓
Tool Authorization
 ↓
API Authorization
 ↓
Data Authorization
```

Each layer makes an appropriate security decision.

---

### 28. AI as a Trust Broker

An AI application may sit between users and enterprise systems.

```text
User
   ↓
AI
   ↓
Enterprise Systems
```

This makes the AI a potential **trust broker**.

The danger is that the AI could become a privileged intermediary if it receives more authority than users actually possess.

---

### 29. AI as a Privileged Intermediary

Example:

```text
Employee
   ↓
AI Assistant
   ↓
Service Account
   ↓
All HR Records
```

If every employee can ask the AI to retrieve HR records, the AI has effectively become a privilege-escalation mechanism.

The correct architecture should preserve user-level authorization.

---

### 30. Identity Propagation

A secure data flow can propagate identity:

```text
Employee
   ↓
AI Application
   ↓
Employee Context
   ↓
Enterprise API
```

The downstream system can then evaluate:

```text
Who is the user?
What is the AI?
What action is requested?
What resource is being accessed?
```

This is stronger than relying solely on a generic AI service account.

---

### 31. Service Identity

AI components should also have their own service identities.

For example:

```text
AI Application
     ↓
AI-App-001

RAG Service
     ↓
AI-RAG-001

Tool Gateway
     ↓
AI-Tool-001
```

This allows security teams to distinguish different components and activities.

---

### 32. Identity and Data Flow

Every significant data flow should ideally answer:

```text
Who is sending the data?
Who is receiving it?
Under which identity?
For what purpose?
With what permission?
```

For example:

```text
CRM
 ↓
AI-RAG-001
 ↓
Read Customer Data
 ↓
Approved Purpose
```

---

### 33. Authorization at the Data Flow

Authentication establishes identity.

Authorization determines whether the identity may perform the requested operation.

Therefore:

```text
Authentication
      ↓
"Who are you?"

Authorization
      ↓
"What are you allowed to access?"
```

Both are required.

---

### 34. Data Flow Authorization

Suppose:

```text
AI Agent → Customer Database
```

The architecture should define:

```text
Allowed:
READ customer order

Denied:
READ unrelated employee records

Denied:
DELETE customer

Denied:
MODIFY database schema
```

The data flow should therefore have a defined authorization scope.

---

### 35. Least Privilege in Data Flows

Least privilege means that a component should receive only the data and permissions required for its function.

Weak:

```text
AI
 ↓
Entire Enterprise Database
```

Stronger:

```text
AI
 ↓
Approved API
 ↓
Required Dataset
 ↓
Specific Records
```

This reduces the potential blast radius of compromise or misuse.

---

### 36. Data Minimization

Data minimization complements least privilege.

If an AI needs:

```text
Customer Country
Customer Product
Customer Order Status
```

there may be no reason to provide:

```text
Passport Number
Bank Account
Full Address
```

The safest data flow is often the smallest data flow that still satisfies the business requirement.

---

### 37. Purpose Limitation

Data should cross a trust boundary for a defined business purpose.

For example:

```text
Purpose:
Customer Support

Data:
Order Status

Allowed:
Customer Support Agent
```

The same data should not automatically become available for:

```text
Marketing
Employee Analytics
Training
Other AI Applications
```

unless separately authorized.

---

### 38. Data Ownership

Every important AI data source should have an identifiable owner.

Examples:

```text
CRM Data → Customer Data Owner
HR Data → HR Data Owner
Financial Data → Finance Data Owner
Security Data → Security Owner
```

The AI platform owner should not automatically become the data owner.

---

### 39. Data Stewardship

Data stewards may define:

* Classification.
* Permitted use.
* Retention.
* Access rules.
* Quality requirements.
* Sharing restrictions.

This becomes especially important when AI combines information from multiple enterprise sources.

---

### 40. Cross-Domain Data Flows

AI can combine data from different security domains.

Example:

```text
CRM Data ─────┐
              │
HR Data ──────┼──► AI
              │
Finance Data ─┘
```

This creates a composite trust problem.

The AI may be able to combine information that individual systems intentionally keep separate.

---

### 41. Data Aggregation Risk

Consider:

```text
System A:
Customer Location

System B:
Customer Income

System C:
Customer Health Information
```

Individually, each system may have different access restrictions.

If AI combines them:

```text
A + B + C
   ↓
AI Profile
```

the resulting information may have a much higher sensitivity than any single dataset.

---

### 42. Cross-Classification Data Flow

When information from different classification levels is combined:

```text
Public
+
Internal
+
Confidential
+
Restricted
```

the resulting dataset may need to inherit the highest applicable protection level.

Security architecture should define how classification is handled during aggregation.

---

### 43. Data Flow Direction

Direction matters.

For example:

```text
Database → AI
```

is different from:

```text
AI → Database
```

and:

```text
AI ↔ Database
```

Read-only data retrieval presents a different risk from write access.

---

### 44. Read vs. Write Trust Relationships

Compare:

```text
AI → Database
READ
```

with:

```text
AI → Database
WRITE
```

and:

```text
AI → Database
DELETE
```

The potential impact increases significantly as the AI receives greater authority.

---

### 45. Execute Authority

The highest-risk data flows may involve execution.

For example:

```text
AI
 ↓
Command
 ↓
Production Server
```

The architecture should introduce additional controls:

```text
AI
 ↓
Command Validation
 ↓
Policy
 ↓
Approval
 ↓
Controlled Execution
```

---

### 46. Data Flow and Agentic AI

Agentic AI introduces dynamic workflows.

For example:

```text
Goal
 ↓
AI Agent
 ↓
Tool Selection
 ↓
Tool A
 ↓
Tool B
 ↓
Tool C
 ↓
Final Action
```

The exact path may not be known in advance.

Therefore, architecture must control not only individual connections but also possible combinations of actions.

---

### 47. Tool Chaining

Suppose:

```text
Tool A:
Read CRM

Tool B:
Send Email
```

Individually, each may appear low-risk.

But together:

```text
CRM
 ↓
Tool A
 ↓
AI
 ↓
Tool B
 ↓
External Email
```

may create a data-exfiltration path.

Trust analysis must therefore consider **composed data flows**.

---

### 48. Data Flow Composition

Security architecture should ask:

> **What can happen when individually permitted capabilities are combined?**

For example:

```text
Read
+
Transform
+
Send
```

may result in:

```text
Sensitive Data Exfiltration
```

even though no single tool appears malicious.

---

### 49. External Data Transfer

When enterprise information leaves the organization:

```text
Enterprise
    ↓
External AI Provider
```

the trust relationship changes.

The architecture should identify:

* Destination.
* Data type.
* Processing purpose.
* Provider.
* Retention.
* Security controls.
* Contractual protections.
* Geographic location.

---

### 50. Third-Party AI Data Flow

A common architecture is:

```text
Enterprise Application
        ↓
AI API
        ↓
Third-Party Model
        ↓
Response
        ↓
Enterprise Application
```

The external provider becomes part of the data-flow architecture.

The organization should understand exactly what crosses the external boundary.

---

### 51. Model Provider Trust

The enterprise may trust a provider for:

```text
Model Processing
```

without necessarily trusting it for:

```text
Long-Term Data Storage
```

or:

```text
Training on Enterprise Data
```

or:

```text
Secondary Use
```

Trust should therefore be scoped to explicit processing activities.

---

### 52. Data Retention in AI Flows

A data flow does not necessarily end when the AI produces a response.

Data may be retained in:

```text
Application Logs
Model Provider Logs
Vector Databases
Conversation History
Monitoring Systems
Backups
Security Systems
```

Therefore:

```text
Data Flow
```

should include relevant storage and retention points.

---

### 53. Hidden Data Flows

An important architecture challenge is discovering flows that are not visible in the primary application diagram.

Examples:

```text
AI Prompt
 ↓
Application Log
```

or:

```text
AI Request
 ↓
Provider Telemetry
```

or:

```text
Document
 ↓
Backup
```

These secondary flows may create additional security and privacy risks.

---

### 54. Shadow AI Data Flows

Employees may introduce AI services without formal approval.

Example:

```text
Employee
 ↓
Copy Confidential Document
 ↓
Public AI Service
```

This creates an unauthorized external data flow.

GRC and security programs should therefore address both:

```text
Approved AI
```

and:

```text
Unapproved / Shadow AI
```

### 56. Data Flow and Threat Modeling

Data-flow diagrams are particularly useful for threat modeling.

Once the flows are known, security teams can ask:

```text
What can be intercepted?
What can be modified?
What can be injected?
What can be exposed?
What can be replayed?
What can cross an unauthorized boundary?
```

This makes data-flow mapping a foundational security activity.

---

### 57. Threats at AI Data Flows

Common threats include:

* Prompt injection.
* Indirect prompt injection.
* Data exfiltration.
* Unauthorized retrieval.
* Privilege escalation.
* Credential exposure.
* Man-in-the-middle attacks.
* API abuse.
* Cross-tenant access.
* Malicious tool invocation.
* Data poisoning.
* Supply-chain compromise.

Each threat should be associated with the relevant flow.

---

### 58. Trust Relationship Failure

A trust relationship fails when a component receives more authority or information than intended.

Example:

```text
AI
 ↓
Should Read Customer Orders
```

but actually receives:

```text
All Customer Records
```

This represents excessive trust.

---

### 59. Trust Relationship Drift

Trust relationships can change over time.

Initially:

```text
AI → CRM
Read Only
```

Later:

```text
AI → CRM
Read + Write
```

Later:

```text
AI → CRM
Administrative Access
```

This is **trust drift**.

Change management and access reviews should detect such changes.

---

### 60. Trust Relationship Register

A GRC program can maintain a trust relationship register.

Example:

| Relationship           | Trust Granted          | Risk     |
| ---------------------- | ---------------------- | -------- |
| User → AI              | Submit requests        | Medium   |
| AI → RAG               | Retrieve approved data | Medium   |
| AI → CRM               | Read customer records  | High     |
| AI → Payment API       | Initiate transactions  | Critical |
| AI → External Provider | Process prompts        | High     |

This provides management visibility into where AI has meaningful authority.

---

### 61. Data Flow Security Objectives

A mature AI architecture should establish objectives such as:

```text
DF-01
Data flows are identified.

DF-02
Data classification is maintained.

DF-03
Data flows have defined business purposes.

DF-04
Trust relationships are explicit.

DF-05
Authorization is enforced at relevant boundaries.

DF-06
Sensitive data is minimized.

DF-07
External data transfers are controlled.

DF-08
Data flows are encrypted where required.

DF-09
Significant data flows are logged.

DF-10
Material data-flow changes trigger security review.
```

---

### 62. AI Data Flow Assessment Questions

A practical assessment should ask:

1. What data enters the AI system?
2. Where does that data originate?
3. Who owns it?
4. What classification does it have?
5. Where is it stored?
6. What transformations occur?
7. Which AI components process it?
8. Which identities access it?
9. What systems receive AI output?
10. Does data leave the organization?
11. Does a third-party provider process it?
12. Can the AI initiate actions?
13. What controls enforce authorization?
14. What logs are generated?
15. What happens if the trust relationship is compromised?

---

### 63. Data Flow Security Principle

A useful enterprise principle is:

> **Every significant AI data flow should have a defined source, destination, purpose, identity, authorization scope, classification, and security control.**

This prevents AI architecture from becoming an opaque collection of interconnected systems.

---

### 64. GRC Perspective

From a GRC perspective, AI data-flow architecture connects technical design to governance.

The relationship can be represented as:

```text
Data Flow
   ↓
Trust Relationship
   ↓
Threat
   ↓
Risk
   ↓
Control
   ↓
Control Owner
   ↓
Evidence
   ↓
Testing
```

This allows a cybersecurity GRC consultant to translate an AI architecture into an auditable control environment.

---

### 65. Senior-Level Interview Explanation

A strong interview response could be:

> **"When I assess AI data flows, I don't only map where the data travels. I identify what information is crossing each boundary, its classification and business purpose, which identity is responsible for the transfer, what authorization applies, and what trust relationship exists between the source and destination. I then look for excessive data exposure, transitive trust, uncontrolled external transfers, and agentic tool chains that could create unintended attack paths."**
