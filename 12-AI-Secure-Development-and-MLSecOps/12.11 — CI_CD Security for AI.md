# 12.11 — CI/CD Security for AI

## Part 1 — Foundations

### 1. Definition of CI/CD Security for AI

CI/CD Security for AI is the discipline of protecting continuous integration and continuous delivery pipelines used to build, test, package, validate, release, and deploy AI applications, datasets, models, and supporting infrastructure.

Traditional CI/CD security focuses primarily on application source code and software artifacts. AI CI/CD must additionally protect:

* Datasets
* Model artifacts
* Training pipelines
* Model configurations
* Prompts and instructions
* AI dependencies
* Model-serving infrastructure
* Evaluation results
* Security-test results

The fundamental objective is to ensure that **only authorized, validated, traceable, and security-approved AI artifacts can progress through the delivery lifecycle.**

```text id="cicdai1a"
Code / Data / Model Change
          |
          v
      CI Pipeline
          |
          v
    Security Testing
          |
          v
    Artifact Validation
          |
          v
     Security Gates
          |
          v
      CD Pipeline
          |
          v
      Deployment
          |
          v
       Runtime
```

---

### 2. Purpose of CI/CD Security for AI

The purpose of AI CI/CD security is to prevent compromise of the delivery pipeline from becoming compromise of the AI system or enterprise environment.

Security objectives include:

* Protecting source code
* Protecting datasets
* Protecting models
* Protecting build infrastructure
* Protecting pipeline identities
* Preventing unauthorized deployments
* Detecting malicious changes
* Enforcing security requirements
* Preserving artifact integrity
* Maintaining complete traceability

CI/CD therefore becomes a critical AI security control plane.

---

### 3. AI CI/CD Security vs Traditional CI/CD Security

AI CI/CD introduces additional security concerns because AI systems contain artifacts and dependencies that behave differently from conventional software.

| Traditional CI/CD   | AI CI/CD                                    |
| ------------------- | ------------------------------------------- |
| Source code         | Source code + prompts + configurations      |
| Software packages   | Software + models + datasets                |
| Application testing | Application + model + dataset testing       |
| Build artifacts     | Software + model artifacts                  |
| Dependency security | Software + ML dependencies                  |
| Release approval    | Model + application + data release approval |
| Runtime deployment  | Application + model + infrastructure        |

AI CI/CD therefore extends DevSecOps rather than simply duplicating it.

---

### 4. CI/CD as an AI Security Boundary

The CI/CD pipeline is a high-value security boundary because it can transform untrusted changes into trusted production artifacts.

```text id="cicdai4b"
Untrusted Change
      |
      v
+-------------------+
| CI/CD Security    |
| Boundary          |
+-------------------+
      |
      v
Security Validation
      |
      v
Trusted Artifact
```

Compromise of this boundary can allow an attacker to inject malicious code, datasets, models, dependencies, or configurations into production.

### 6. AI Source Code Security

Source repositories may contain application code, training code, inference logic, prompts, configuration, and pipeline definitions.

Security controls should protect against:

* Unauthorized modification
* Malicious commits
* Credential exposure
* Dependency manipulation
* Pipeline manipulation
* Prompt tampering

Source integrity is therefore foundational to AI CI/CD security.

---

### 7. Branch Protection

Protected branches should prevent unauthorized changes from entering security-sensitive pipelines.

Controls may require:

* Authentication
* Pull requests
* Peer review
* Status checks
* Security-test completion
* Signed commits where required

Critical branches should not permit unrestricted direct modification.

---

### 8. Code Review Security

Code review should evaluate security-relevant changes, not only functional correctness.

Reviewers should consider changes involving:

* Authentication
* Authorization
* Data access
* Model invocation
* Tool access
* Prompt processing
* Security controls
* Pipeline configuration

AI-specific security review should be incorporated into the development workflow.

---

### 9. Pipeline Configuration Security

CI/CD configuration itself is a security-sensitive artifact.

Pipeline definitions may control:

* Credentials
* Build steps
* Test execution
* Artifact creation
* Deployment
* Security gates

Unauthorized modification can effectively disable security controls.

---

### 10. Pipeline Identity

Every pipeline execution should have an attributable identity.

The identity should distinguish:

* Human initiator
* Automated trigger
* Pipeline workload
* Environment
* Repository
* Commit

Shared administrative identities should be avoided.

---

### 11. Pipeline Authentication

Pipeline components should authenticate using enterprise-approved mechanisms.

Authentication should support:

* Strong workload identity
* Short-lived credentials
* Mutual authentication where appropriate
* Centralized identity management
* Auditability

Long-lived static credentials should be minimized.

---

### 12. Pipeline Authorization

Authentication establishes who or what is executing a pipeline. Authorization determines what that pipeline is allowed to do.

A build pipeline may be permitted to:

* Read source code
* Read approved dependencies
* Generate artifacts
* Run tests

It should not automatically be permitted to:

* Modify production
* Approve its own deployment
* Change security policies
* Disable security gates

---

### 13. Least Privilege in AI CI/CD

CI/CD workloads should operate with only the permissions necessary for their stage.

```text id="cicdai13d"
Build Pipeline
    |
    +--> Source: Read
    +--> Dependencies: Read
    +--> Artifact Store: Write
    |
    X--> Production Admin
    X--> Security Policy Admin
```

Least privilege limits the impact of pipeline compromise.

---

### 14. Separation of Duties in CI/CD

Security-sensitive actions should not be controlled entirely by a single identity or pipeline.

Examples include:

* Build ≠ approval
* Testing ≠ deployment authorization
* Artifact creation ≠ artifact trust
* Development ≠ production administration

This reduces the possibility of a compromised pipeline approving its own malicious output.

---

### 15. Dataset Security in CI/CD

Datasets can enter AI pipelines through:

* Repository references
* Object storage
* Data platforms
* External sources
* APIs
* Data pipelines

CI/CD must verify that referenced datasets are approved and security-validated.

---

### 16. Dataset Version Control

CI/CD should reference explicit dataset versions rather than floating or mutable datasets.

For example:

```text id="cicdai16e"
Pipeline
   |
   v
Dataset v3.2
   |
   v
Training
   |
   v
Model v7.4
```

This enables reproducibility and security investigation.

---

### 17. Dataset Integrity in CI/CD

The pipeline should validate dataset integrity before using it.

Validation may include:

* Hash comparison
* Signature verification
* Version verification
* Provenance validation

Unexpected changes should cause the pipeline to fail or enter an investigation workflow.

---

### 18. Dataset Provenance in CI/CD

The pipeline should preserve information about the dataset used during training or evaluation.

Provenance should identify:

* Source
* Dataset version
* Transformation
* Pipeline execution
* Training run

This creates traceability between CI/CD activity and model creation.

---

### 19. Model Artifact Security

Models should be treated as security-sensitive build artifacts.

Security validation should include:

* Integrity
* Provenance
* Serialization
* Dependencies
* Artifact structure
* Security-test status

A model should not become trusted simply because a CI pipeline generated it.

---

### 20. Model Artifact Integrity

Model artifacts should have a verifiable identity.

The pipeline should calculate or validate:

* Hash
* Version
* Signature
* Registry identity
* Provenance

Any unauthorized modification should invalidate the artifact's trust status.

---

### 21. Model Signing

Security-approved models should be digitally signed where required.

```text id="cicdai21e"
Model Artifact
      |
      v
Security Validation
      |
      v
Signing Authority
      |
      v
Signed Model
      |
      v
Trusted Registry
```

Signing provides integrity and authenticity assurance.

---

### 22. Artifact Provenance

AI CI/CD should maintain provenance for artifacts generated during the pipeline.

The provenance chain should connect:

```text id="cicdai22f"
Source
  |
  +--> Dependencies
  |
  +--> Dataset
  |
  +--> Configuration
  |
  v
Build / Training
  |
  v
Model Artifact
```

This enables investigation when an artifact is later found to be compromised.

---

### 23. Dependency Security

AI CI/CD pipelines depend on software frameworks, libraries, packages, container images, and external services.

Dependency security should address:

* Vulnerability scanning
* Version control
* Package provenance
* Integrity
* Approved sources
* License requirements

Dependency compromise can become model or application compromise.

---

### 24. AI Software Bill of Materials

An AI CI/CD process should maintain an inventory of relevant software components.

The inventory may include:

* Application libraries
* ML frameworks
* Model-serving libraries
* Container components
* Build tools
* Security tools

This provides visibility into the AI software supply chain.

---

### 25. Model Bill of Materials

Where practical, organizations should maintain model-specific component information.

It may identify:

* Model version
* Dataset version
* Training code
* Dependencies
* Configuration
* Base model
* Fine-tuning components

This provides a more complete representation of model composition.

---

### 26. Build Environment Security

Build environments should be isolated and hardened.

Security controls should address:

* Runner security
* Network access
* Privileges
* Credentials
* Dependencies
* Temporary files
* Artifact output

Build infrastructure should be treated as a privileged security environment.

---

### 27. Build Reproducibility

Reproducible builds allow organizations to verify that an artifact can be recreated from known inputs.

```text id="cicdai27g"
Known Source
Known Dataset
Known Dependencies
Known Configuration
        |
        v
   Reproducible Build
        |
        v
 Expected Artifact
```

Unexpected differences should trigger investigation.

---

### 28. Build Isolation

Build jobs should be isolated from one another where appropriate.

Isolation reduces the possibility that:

* One compromised job affects another
* Secrets persist between jobs
* Malicious artifacts cross boundaries
* Temporary files become attack paths

---

### 29. Security Testing in CI

Security testing should execute automatically at appropriate stages.

Tests may include:

* SAST
* Secret scanning
* Dependency scanning
* API testing
* Dataset security testing
* Model security testing
* Container scanning
* IaC scanning

---

### 30. AI-Specific Security Testing

AI CI/CD should include tests that traditional application pipelines may not require.

Examples include:

* Prompt injection testing
* Dataset poisoning detection
* Model integrity testing
* Model extraction testing
* RAG security testing
* Tool authorization testing
* Model behavioral testing

---

### 31. Security Test Evidence

CI/CD should automatically preserve security-test evidence.

Evidence should identify:

* Commit
* Dataset version
* Model version
* Test suite
* Test result
* Findings
* Pipeline execution
* Environment

This makes security decisions auditable.

---

### 32. Security Gates

Security gates determine whether an artifact can progress.

```text id="cicdai32h"
Security Tests
      |
      v
Risk Evaluation
      |
      v
Security Gate
    /       \
 Pass       Fail
  |           |
  v           v
Continue    Block
```

Security gates should be technically enforceable.

---

### 33. Risk-Based Security Gates

Not every AI system requires identical security testing.

Risk-adaptive gates may consider:

* Data sensitivity
* Model criticality
* External exposure
* Autonomy
* Regulatory impact
* Threat level

Higher-risk systems should require stronger validation.

---

### 34. Fail-Closed CI/CD Security

Critical security gates should fail closed.

```text id="cicdai34i"
Security Check
      |
      v
Result Available?
   /          \
 Yes           No
 |              |
 v              v
Evaluate      Block /
               Escalate
```

A missing security result should not automatically be interpreted as successful validation.

---

### 35. Security Gate Bypass Prevention

The architecture should prevent developers or pipelines from bypassing mandatory security controls.

Potential mechanisms include:

* Protected deployment environments
* Central policy engines
* Registry enforcement
* Signed artifacts
* Independent authorization
* Branch protection

---

### 36. CI/CD Secrets Management

Secrets should not be embedded directly in:

* Source code
* Pipeline files
* Model artifacts
* Datasets
* Container images
* Logs

Secrets should be retrieved from controlled secret-management systems.

---

### 37. Short-Lived Pipeline Credentials

Pipeline credentials should be short-lived whenever possible.

Benefits include:

* Reduced exposure window
* Automatic expiration
* Reduced credential reuse
* Easier revocation
* Better attribution

---

### 38. External Repository Security

External repositories and package sources should be treated as untrusted dependencies until validated.

Controls should verify:

* Source trust
* Integrity
* Version
* Security status
* Approved usage

---

### 39. External Model Security

Externally sourced models should receive additional validation before entering trusted AI pipelines.

Testing should evaluate:

* Provenance
* Integrity
* Serialization
* Dependencies
* Security behavior
* Provider trust

---

### 40. External Dataset Security

External datasets should undergo security and authorization validation.

The pipeline should not assume that public availability means:

* Safe
* Authorized
* Unmodified
* Appropriate for training

---

### 41. Container Security in AI CI/CD

Container images used for AI workloads should be scanned before deployment.

Testing should include:

* Vulnerabilities
* Image provenance
* Signature
* Privileges
* Embedded secrets
* Configuration

---

### 42. Infrastructure-as-Code Security

AI CI/CD frequently creates or modifies infrastructure.

IaC security should validate:

* Identity configuration
* Network exposure
* Storage access
* Encryption
* Privileges
* Public exposure

---

### 43. Environment Separation

Development, testing, staging, and production environments should be separated.

```text id="cicdai43j"
Development
    |
    v
Testing
    |
    v
Staging
    |
    v
Production
```

Promotion should occur through controlled trust transitions.

---

### 44. Production Deployment Authorization

Production deployment should require explicit authorization appropriate to risk.

A CI pipeline should not automatically have unrestricted authority to deploy every artifact it creates.

---

### 45. Deployment Integrity

The deployed artifact should be verified against the approved artifact.

Validation should compare:

* Model identity
* Artifact hash
* Signature
* Version
* Configuration

---

### 46. Release Integrity

A release should represent a specific, validated set of artifacts.

The release should identify:

* Code version
* Model version
* Dataset version where applicable
* Dependencies
* Configuration
* Security-test results

---

### 47. Rollback Security

AI CI/CD should provide secure rollback capabilities.

Rollback should restore a previously validated state rather than simply deploying an arbitrary older artifact.

```text id="cicdai47k"
Current Release
      |
      v
Security Incident
      |
      v
Validated Previous Release
      |
      v
Rollback
      |
      v
Security Verification
```

---

### 48. CI/CD Security Monitoring

Pipeline activity should be monitored for suspicious behavior.

Indicators may include:

* Unexpected pipeline changes
* Unauthorized deployments
* Disabled security tests
* Credential misuse
* Unusual artifact generation
* Unexpected external connections

---

### 49. CI/CD Security Principles

Effective AI CI/CD security should follow these principles:

1. **Treat the pipeline as a security boundary.**
2. **Authenticate every pipeline workload.**
3. **Authorize every security-sensitive action.**
4. **Apply least privilege.**
5. **Protect pipeline configuration.**
6. **Validate datasets before trusted use.**
7. **Validate models before promotion.**
8. **Protect artifact integrity and provenance.**
9. **Automate security testing.**
10. **Enforce security gates.**
11. **Separate development from production authority.**
12. **Preserve security evidence.**
13. **Monitor the pipeline continuously.**
14. **Support secure rollback and recovery.**

---

### 50. Core Principle of CI/CD Security for AI

**AI CI/CD must function as a controlled security boundary in which every code, dataset, model, dependency, configuration, and infrastructure change is authenticated, authorized, validated, tested, traceable, and subject to enforceable security gates before it can become trusted production capability.**

The fundamental trust chain is:

```text id="cicdai50l"
Change
  |
  v
Identity
  |
  v
Authorization
  |
  v
Validation
  |
  v
Security Testing
  |
  v
Artifact Integrity
  |
  v
Provenance
  |
  v
Security Gate
  |
  v
Deployment Authorization
  |
  v
Production
  |
  v
Continuous Monitoring
```

**The critical security principle is that a CI/CD pipeline must never be allowed to convert an untrusted change into trusted AI capability without independent validation and enforceable authorization. Pipeline compromise must be contained within the pipeline security boundary rather than automatically becoming model, application, or enterprise compromise.**
