# 12.03 — Machine Learning Lifecycle and MLOps

## Part 1 — Foundations

### 1. Definition of the Machine Learning Lifecycle

The Machine Learning Lifecycle is the structured sequence through which machine learning systems are conceived, developed, trained, evaluated, deployed, monitored, changed, and retired.

A representative lifecycle is:

```text id="7m4qxn"
Business Objective
       |
       v
Data Acquisition
       |
       v
Data Preparation
       |
       v
Feature Engineering
       |
       v
Model Development
       |
       v
Training
       |
       v
Evaluation
       |
       v
Model Registration
       |
       v
Deployment
       |
       v
Monitoring
       |
       v
Retraining / Change
       |
       v
Retirement
```

Unlike conventional software, the lifecycle can repeatedly return to data and training as new information becomes available.

---

### 2. Definition of MLOps

MLOps is the set of engineering practices, processes, platforms, automation, and operational capabilities used to reliably develop, deploy, manage, monitor, and maintain machine learning systems.

MLOps connects:

* Data engineering
* ML engineering
* Software engineering
* Infrastructure
* Automation
* Deployment
* Monitoring
* Governance

MLOps provides the operational foundation for managing ML systems at scale.

---

### 3. MLOps vs Traditional DevOps

DevOps primarily manages software delivery and operations.

MLOps extends these concepts to accommodate ML-specific lifecycle characteristics.

```text id="m8q4xn"
DevOps
  |
  +--> Source Code
  +--> Build
  +--> Test
  +--> Deploy
  +--> Operate

MLOps
  |
  +--> Source Code
  +--> Data
  +--> Features
  +--> Training
  +--> Model
  +--> Evaluation
  +--> Deploy
  +--> Monitor
```

The additional data and model lifecycle introduces new security and operational requirements.

---

### 4. Purpose of MLOps

The primary purpose of MLOps is to make ML development and operation:

* Repeatable
* Reliable
* Observable
* Scalable
* Traceable
* Automatable
* Maintainable

From a security perspective, MLOps provides the lifecycle infrastructure into which security controls can be embedded.

---

### 5. MLOps as a Lifecycle Discipline

MLOps should not be viewed simply as a collection of deployment tools.

It is a lifecycle discipline covering:

1. Data
2. Development
3. Training
4. Evaluation
5. Packaging
6. Deployment
7. Monitoring
8. Retraining
9. Retirement

Security must be integrated across all of these activities.

---

The application lifecycle and ML lifecycle must remain synchronized.

### 7. Machine Learning Lifecycle Stages

A mature ML lifecycle commonly includes:

* Business problem definition
* Data acquisition
* Data validation
* Data preparation
* Feature engineering
* Model development
* Training
* Evaluation
* Model registration
* Deployment
* Monitoring
* Retraining
* Retirement

Each stage introduces unique security considerations.

---

### 8. Business Problem Definition

The lifecycle should begin with a clearly defined business problem.

The organization should establish:

* Intended outcome
* Business purpose
* Users
* Decisions supported
* Required data
* Expected model behavior
* Security implications

A model should not be developed simply because a dataset or algorithm is available.

---

### 9. ML System Scope

The ML system scope should include all components required to produce and operate the model.

This may include:

* Data sources
* Data pipelines
* Feature stores
* Training infrastructure
* Model code
* Model artifacts
* Model registry
* Serving infrastructure
* Monitoring

Security responsibility should cover the complete ML system.

---

### 10. Data Acquisition

Data acquisition introduces the first major ML security boundary.

Data may originate from:

* Internal databases
* Applications
* Sensors
* External datasets
* APIs
* Partners
* Public repositories

The source, ownership, provenance, and authorized use of data should be established.

---

### 11. Data Provenance

Data provenance records the origin and history of datasets.

It should identify:

* Source
* Owner
* Acquisition method
* Processing
* Transformations
* Version
* Validation

Provenance enables the organization to determine what information contributed to a model.

---

### 12. Data Validation

Data should be validated before entering trusted ML workflows.

Validation may examine:

* Schema
* Format
* Completeness
* Integrity
* Unexpected values
* Source authenticity
* Security characteristics

Invalid or suspicious data should not automatically enter training.

---

### 13. Data Preparation

Data preparation transforms raw information into training-ready data.

Activities may include:

* Cleaning
* Normalization
* Filtering
* Transformation
* Deduplication
* Labeling

Each transformation can alter model behavior and therefore should remain traceable.

---

### 14. Data Quality and Security

Data quality is closely connected to security.

Poor or manipulated data can produce:

* Incorrect models
* Biased outcomes
* Unexpected behavior
* Security weaknesses

Data quality controls therefore contribute to both operational reliability and security assurance.

---

### 15. Data Poisoning

Data poisoning occurs when malicious or inappropriate information is introduced into training data to influence model behavior.

Conceptually:

```text id="x4m8qn"
Trusted Dataset
      |
      +---- Malicious Data
      |
      v
Training
      |
      v
Compromised / Degraded Model
```

Data poisoning demonstrates why dataset security is a fundamental ML lifecycle requirement.

---

### 16. Feature Engineering

Feature engineering transforms data into representations used by models.

Security considerations include:

* Feature provenance
* Access control
* Transformation integrity
* Feature leakage
* Unauthorized modification

Feature engineering pipelines should be controlled and reproducible.

---

### 17. Feature Store Security

Where feature stores are used, they should be treated as security-sensitive infrastructure.

Controls should protect:

* Feature definitions
* Feature values
* Access permissions
* Versioning
* Data lineage
* Integrity

Unauthorized modification of features can influence downstream model behavior.

---

### 18. Training Environment

Training should occur in controlled compute environments.

The environment may include:

* CPU/GPU infrastructure
* Containers
* Storage
* Training frameworks
* Dependencies
* Secrets
* Network connectivity

Training environments should have dedicated identities and restricted privileges.

---

### 19. Training Job

A training job transforms approved data and controlled code into a model artifact.

```text id="p7q4xn"
Code
 +
Dataset
 +
Configuration
 +
Dependencies
 |
 v
Training Job
 |
 v
Model Artifact
```

Each input should be identifiable and controlled.

---

### 20. Training Reproducibility

A training run should be reproducible where practical.

Important inputs include:

* Code version
* Dataset version
* Feature version
* Dependency versions
* Configuration
* Training framework
* Randomization parameters

Reproducibility improves both operational reliability and security investigation.

---

### 21. Training Run Identity

Each significant training run should have a unique identifier.

The identity should connect:

* Training job
* Code
* Dataset
* Configuration
* Environment
* Resulting model

This provides a traceable relationship between development inputs and model outputs.

---

### 22. Experiment Tracking

ML experimentation generates many candidate models.

Experiment tracking should record:

* Training parameters
* Dataset version
* Model version
* Metrics
* Code version
* Environment
* Results

Security-relevant experiments should remain attributable to their creators or workload identities.

---

### 23. Model Development

Model development includes selecting and implementing algorithms, architectures, and configurations.

Security considerations include:

* Trusted frameworks
* Dependency security
* Code security
* Model integrity
* Experiment access
* Resource isolation

Model development should remain within the controlled ML lifecycle.

---

### 24. Model Training Security

Training security should protect against:

* Data poisoning
* Code compromise
* Dependency compromise
* Credential theft
* Unauthorized model modification
* Training environment compromise

The training process should therefore be treated as a security-sensitive workload.

---

### 25. Model Evaluation

A trained model should be evaluated before being considered for deployment.

Evaluation may include:

* Accuracy
* Robustness
* Reliability
* Performance
* Security behavior
* Adversarial resilience

Evaluation establishes whether the model meets its intended requirements.

---

### 26. Model Validation

Model validation determines whether the model is suitable for its intended use.

Validation should consider:

* Functional performance
* Security requirements
* Expected behavior
* Known limitations
* Data characteristics
* Operational constraints

Validation should be based on controlled evidence.

---

### 27. Model Security Evaluation

Model evaluation should include security-specific testing where appropriate.

Security evaluation may assess:

* Adversarial inputs
* Data leakage
* Model manipulation
* Unexpected behavior
* Model extraction
* Robustness

The depth of testing should correspond to risk.

---

### 28. Model Overfitting and Security

Overfitting is primarily a model-quality problem, but it can also affect security characteristics.

An overfit model may:

* Memorize training information
* Generalize poorly
* Behave unpredictably outside expected data

Security evaluation should therefore consider model behavior beyond nominal test performance.

---

### 29. Model Artifact

The output of training is a model artifact that must be treated as a controlled lifecycle object.

It should have:

* Unique identity
* Version
* Provenance
* Integrity information
* Evaluation results
* Security status

The model artifact should not be treated as an ordinary temporary file.

---

### 30. Model Registry

A model registry provides centralized lifecycle management for model artifacts.

It can maintain:

* Model versions
* Metadata
* Provenance
* Evaluation results
* Approval status
* Deployment status

The registry becomes a critical trust boundary in the ML lifecycle.

---

### 32. Model Deployment

Deployment transfers an approved model into an inference environment.

Deployment should verify:

* Model identity
* Model integrity
* Version
* Approval
* Environment
* Configuration

Only authorized models should enter production.

---

### 33. Model Serving

Model serving exposes the model to applications or users.

Serving infrastructure may include:

* APIs
* Containers
* Kubernetes
* Cloud services
* Dedicated inference servers

Security controls should protect both the model and its serving environment.

---

### 34. Model Inference Security

Inference introduces new security considerations.

The system should protect:

* Input data
* Model access
* Output data
* API endpoints
* Authentication
* Authorization
* Rate limits

Production inference should operate within defined security boundaries.

---

### 35. Model Monitoring

Production models should be monitored continuously.

Monitoring may cover:

* Performance
* Accuracy
* Data quality
* Drift
* Security events
* Resource usage
* Unexpected behavior

Monitoring enables early identification of changing security and operational conditions.

---

### 36. Data Drift

Data drift occurs when production input characteristics change relative to the data used during model development.

```text id="q6m4xn"
Training Data
      |
      v
Model
      |
      v
Production Data
      |
      v
Drift Detection
```

Significant drift may require investigation or model reassessment.

---

### 37. Model Drift

Model performance may degrade over time as the operating environment changes.

Model drift can affect:

* Accuracy
* Reliability
* Business outcomes
* Security characteristics

Drift should be monitored and managed through the ML lifecycle.

---

### 38. Concept Drift

Concept drift occurs when the relationship between inputs and expected outcomes changes over time.

A model that was secure and accurate under previous conditions may become inappropriate under new conditions.

Concept drift therefore represents a lifecycle reassessment trigger.

---

### 39. Security Drift in ML Systems

Security drift occurs when the security state of an ML system changes from its approved baseline.

Examples include:

* Model replacement
* Dependency changes
* Configuration changes
* New data sources
* Changed permissions
* Infrastructure changes

Security drift should trigger appropriate reassessment.

---

### 40. Retraining

Retraining creates a new model using updated data or changed parameters.

Retraining should not automatically imply continued trust.

```text id="v8q5xn"
Production Model
       |
       v
New Data
       |
       v
Retraining
       |
       v
New Model
       |
       v
Security Evaluation
       |
       v
Approval
```

Each material retraining event should remain traceable.

---

### 41. Continuous Training

Some ML environments use automated or scheduled retraining.

Continuous training increases the importance of security controls because models can change without direct manual intervention.

Controls should ensure:

* Approved data sources
* Controlled training code
* Security testing
* Model validation
* Artifact integrity
* Deployment authorization

Automation must not eliminate governance.

Automation may cover:

### 48. ML Lifecycle Security Principles

A secure ML lifecycle should follow these principles:

1. Data must be trusted before training.
2. Training environments must be controlled.
3. Training runs must be attributable.
4. Models must have provenance.
5. Model artifacts must maintain integrity.
6. Production models must be approved.
7. Model changes must be controlled.
8. Retraining must not bypass security testing.
9. Production behavior must be monitored.
10. Drift must trigger appropriate reassessment.
11. Automation must remain subject to security controls.
12. Every production model must remain traceable to its lifecycle inputs.

**MLOps must treat data, features, training processes, models, infrastructure, deployment, and monitoring as interconnected lifecycle components whose security, integrity, provenance, and operational state must remain continuously controlled.**

```text id="p6m8qx"

  |

  v
Monitoring
  |

  |
```

## Part 2 — Security Controls

### 51. MLOps Security Control Framework

A secure MLOps environment requires controls across the complete ML lifecycle rather than concentrating security only on the deployed model.

The control framework should cover:

| Lifecycle Area | Primary Security Controls                   |
| -------------- | ------------------------------------------- |
| Data           | Access, integrity, provenance, validation   |
| Features       | Authorization, lineage, integrity           |
| Training       | Identity, isolation, configuration security |
| Experiments    | Access control, traceability                |
| Models         | Validation, signing, provenance             |
| Registry       | Authorization, promotion controls           |
| Deployment     | Approval, integrity verification            |
| Runtime        | Monitoring, authentication, protection      |
| Retraining     | Trigger validation, security gates          |
| Infrastructure | Hardening, vulnerability management         |

---

### 52. ML Data Access Control

Access to datasets should be based on defined identities, roles, and business requirements.

Controls should include:

* Strong authentication
* Role-based or attribute-based authorization
* Dataset-level permissions
* Read/write separation
* Privileged access controls
* Access logging

Training workloads should receive only the data permissions they require.

---

### 53. Dataset Integrity Control

Datasets used by MLOps pipelines should be protected against unauthorized modification.

Integrity mechanisms may include:

* Cryptographic hashes
* Checksums
* Immutable storage
* Version identifiers
* Digital signatures
* Integrity verification during pipeline execution

A dataset that changes unexpectedly should not automatically proceed to training.

---

### 54. Dataset Provenance Control

Dataset provenance should establish where training data originated and how it was processed.

A provenance record should identify:

* Source
* Acquisition time
* Owner
* Processing pipeline
* Transformation history
* Version
* Validation status

This allows investigators to determine which data contributed to a particular model.

---

### 55. Dataset Version Control

Each material dataset state should have a unique version.

```text id="d7m4qx"
Dataset v1
    |
    +--> Training Run A --> Model v1
    |
Dataset v2
    |
    +--> Training Run B --> Model v2
```

Versioning prevents ambiguity about which dataset was used to create a model.

---

### 56. Dataset Immutability Control

Approved training datasets should be immutable whenever practical.

Immutability reduces the possibility that a dataset silently changes after validation.

If modification is necessary, the change should create a new version rather than altering the previously approved dataset.

---

### 57. Dataset Validation Control

Automated validation should occur before datasets enter trusted training workflows.

Validation may examine:

* Schema
* File format
* Record counts
* Data types
* Missing values
* Duplicate records
* Unexpected values
* Integrity
* Provenance

Failed validation should block or quarantine the dataset according to risk.

---

### 58. Dataset Security Scanning

Datasets should be scanned for security-relevant content where appropriate.

Scanning can identify:

* Malicious payloads
* Unexpected executable content
* Embedded files
* Suspicious structures
* Unauthorized sensitive information
* Known malicious indicators

Dataset scanning should complement—not replace—data governance controls.

---

### 59. Training Data Isolation

Training datasets should be isolated according to classification and use.

Sensitive data should not automatically become accessible to:

* Development users
* Test environments
* Unapproved training jobs
* External services
* Production workloads

Data access should follow the principle of least privilege.

---

### 60. Feature Pipeline Integrity

Feature engineering pipelines should be protected against unauthorized modification.

Controls should protect:

* Transformation logic
* Feature definitions
* Feature calculations
* Dependencies
* Feature metadata
* Feature outputs

A compromised feature pipeline can alter model behavior without directly modifying the model.

---

### 61. Feature Lineage Control

Feature lineage should connect production features to their underlying sources and transformations.

```text id="n5q8mx"
Source Data
    |
    v
Transformation
    |
    v
Feature
    |
    v
Training Dataset
    |
    v
Model
```

Lineage provides evidence of how data characteristics propagated into model behavior.

---

### 62. Experiment Tracking Access Control

Experiment tracking platforms should use controlled authentication and authorization.

Users should receive permissions appropriate to their responsibilities.

Controls should protect:

* Experiment metadata
* Parameters
* Metrics
* Dataset references
* Model references
* Results

Unauthorized modification of experiment records can undermine ML traceability.

---

### 63. Experiment Record Integrity

Experiment records should be protected from unauthorized alteration.

Where practical, important records should contain:

* Immutable identifiers
* Timestamps
* Workload identity
* Code version
* Dataset version
* Model version
* Configuration

Experiment evidence should remain trustworthy after a model reaches production.

---

### 64. Training Job Authentication

Every automated training job should operate under a distinct workload identity where practical.

The identity should allow the organization to determine:

* Which workload executed
* Which resources it accessed
* Which data it consumed
* Which model it generated

Shared credentials should be avoided.

---

### 65. Training Job Authorization

Training workloads should receive only the permissions required for their function.

For example:

```text id="r8m4qx"
Training Identity
      |
      +--> Read Approved Dataset
      +--> Read Approved Dependencies
      +--> Write Training Output
      |
      X--> Modify Production Model
      X--> Access Unrelated Secrets
      X--> Deploy Without Authorization
```

Training should not inherently grant production privileges.

---

### 66. Training Environment Isolation

Training workloads should execute in controlled environments.

Isolation should protect against:

* Cross-workload access
* Unauthorized network communication
* Credential theft
* Host compromise
* Lateral movement

High-risk training workloads may require dedicated compute or stronger isolation boundaries.

---

### 67. Training Dependency Control

Training frameworks and libraries should originate from approved sources.

Controls should include:

* Dependency allowlists
* Version pinning
* Vulnerability scanning
* Lock files
* Package integrity verification
* Removal of unnecessary dependencies

A compromised dependency can affect both training infrastructure and model outputs.

---

### 68. Training Configuration Security

Training configuration should be treated as a controlled artifact.

Security-relevant configuration includes:

* Dataset references
* Model parameters
* Resource settings
* Network settings
* Output destinations
* Feature configurations

Unauthorized configuration changes should trigger appropriate validation.

---

### 69. Notebook Security Control

Interactive notebooks can provide powerful access to data and training infrastructure.

Security controls should include:

* Authentication
* Authorization
* Session isolation
* Network restrictions
* Secret protection
* Execution controls
* Activity logging

Notebooks should not become uncontrolled privileged access paths.

---

### 70. Interactive ML Environment Isolation

Development and experimentation environments should remain separated from production environments.

```text id="k5q9mx"
Development
    |
    X---- Direct Production Access
    |
    v
Controlled Promotion
    |
    v
Production
```

Model developers should not bypass lifecycle controls by directly modifying production resources.

---

### 71. Model Serialization Security

Model serialization mechanisms should be treated as security-sensitive.

Serialized models may contain executable or otherwise dangerous content depending on the framework and format.

Controls should include:

* Approved serialization formats
* Trusted loaders
* Artifact scanning
* Source verification
* Restricted deserialization

Untrusted model files should never automatically be loaded into privileged environments.

---

### 72. Model Loading Security

Model loading should occur only after appropriate trust validation.

Validation should consider:

* Source
* Version
* Integrity
* Provenance
* Security status
* Approval state

Model loading should be treated as a security boundary.

---

### 73. Model Artifact Scanning

Model artifacts should be scanned before registration or promotion.

Scanning may include:

* Malware detection
* File structure validation
* Dependency analysis
* Serialization checks
* Configuration inspection
* Known vulnerability checks

The scan depth should correspond to the risk of the model.

---

### 74. Model Integrity Verification

The integrity of a model should be verified before important lifecycle transitions.

A representative process is:

```text id="v4m8qx"
Model Artifact
     |
     v
Hash / Signature Verification
     |
     v
Provenance Verification
     |
     v
Approval Verification
     |
     v
Promotion
```

A mismatch should cause the artifact to fail validation.

---

### 75. Model Signing

Cryptographic signing can establish that a model artifact originated from an authorized build or release process.

Signing should be combined with:

* Trusted signing identities
* Protected keys
* Signature verification
* Certificate/key lifecycle management
* Promotion policies

A signature should prove artifact authenticity, not automatically prove that the model is safe.

---

### 76. Model Provenance Control

Model provenance should connect a model to its creation inputs.

A model provenance record should ideally identify:

* Source code
* Dataset
* Features
* Training run
* Dependencies
* Configuration
* Build environment
* Evaluation results
* Creator or workload identity

This enables end-to-end model traceability.

---

### 77. Model Evaluation Gate

A model should satisfy defined evaluation requirements before promotion.

Evaluation gates may consider:

* Accuracy
* Robustness
* Security
* Bias-related requirements where applicable
* Performance
* Resource consumption
* Business requirements

Failure of mandatory criteria should prevent promotion.

---

### 78. Security Testing Gate for Models

Security testing should occur before a model enters a higher-trust environment.

Testing may include:

* Adversarial testing
* Input manipulation
* Model extraction resistance
* Sensitive information exposure
* Robustness testing
* Abuse-case testing

Testing requirements should be risk-based.

---

### 79. Model Registry Access Control

Model registries should enforce strong access controls.

Permissions should distinguish between:

* Viewing models
* Uploading models
* Registering models
* Modifying metadata
* Approving models
* Promoting models
* Retiring models

Administrative access should be tightly controlled.

---

### 80. Model Registry Promotion Control

Models should move between lifecycle states only through authorized transitions.

```text id="x7q5mn"
Experimental
     |
     | Security + Quality Gates
     v
Validated
     |
     | Approval
     v
Approved
     |
     | Deployment Authorization
     v
Production
```

Direct promotion from development to production should be prohibited unless explicitly governed as an exceptional process.

---

### 81. Model Artifact Immutability

Once a model version is approved, its underlying artifact should be immutable.

If the model changes, a new version should be created.

This prevents a trusted model reference from silently pointing to a modified artifact.

---

### 82. Model Metadata Integrity

Model metadata is part of the trust record.

Important metadata includes:

* Version
* Owner
* Risk classification
* Evaluation status
* Dataset reference
* Training run
* Security status
* Approval history

Metadata should be protected from unauthorized modification.

---

### 83. Model Packaging Control

Model packaging should produce a controlled deployment artifact.

Packaging should account for:

* Model files
* Runtime dependencies
* Configuration
* Required libraries
* Version information
* Security metadata

The deployment artifact should be reproducible or otherwise verifiable.

---

### 84. Model Container Security

Where models are deployed in containers, container images should be subject to standard container security controls.

Controls include:

* Trusted base images
* Image scanning
* Minimal packages
* Non-root execution
* Runtime restrictions
* Image signing
* Registry controls

The model must not become a route around container security requirements.

---

### 85. Model Deployment Authorization

Deployment should require authorization appropriate to the model's risk classification.

Authorization should consider:

* Model version
* Security test status
* Approval status
* Target environment
* Change record
* Deployment identity

Automated deployment does not remove the requirement for authorization.

---

### 86. Deployment Integrity Verification

The deployment system should verify that the artifact being deployed is the artifact that was approved.

```text id="j6m9qx"
      v

      |
      v
```

This prevents substitution between approval and deployment.

### 87. Runtime Model Integrity

Production systems should periodically or continuously verify model integrity where technically feasible.

Verification may compare:

* Hashes
* Signatures
* Artifact identifiers
* Registry versions

Unexpected model changes should generate an alert and potentially trigger containment.

---

### 88. Model Configuration Security

Model configuration can materially affect behavior.

Controlled configuration should include:

* Thresholds
* Endpoints
* Feature settings
* Runtime parameters
* Safety settings
* Resource limits

Configuration changes should follow the same security discipline as other production changes.

---

### 89. MLOps Pipeline Identity Security

Each pipeline component should use controlled identities.

```text id="q8m5xn"
Pipeline
  |
  +--> Data Validation Identity
  +--> Training Identity
  +--> Evaluation Identity
  +--> Registry Identity
  +--> Deployment Identity
```

Separate identities reduce the impact of credential compromise.

---

### 90. MLOps Pipeline Authorization

Pipeline stages should be prevented from performing unauthorized lifecycle operations.

For example, a training stage should not automatically possess the authority to:

* Approve itself
* Promote its own model
* Modify production
* Disable security gates

Authorization should be independently enforced.

---

### 91. Pipeline Configuration Protection

Pipeline definitions should be protected against unauthorized changes.

Controls should cover:

* Pipeline code
* Workflow definitions
* Build configuration
* Security gates
* Deployment targets
* Service connections

A compromised pipeline can undermine multiple downstream controls.

---

### 92. MLOps Build Environment Security

Build environments should be isolated and controlled.

Security measures may include:

* Ephemeral workers
* Restricted network access
* Minimal privileges
* Trusted images
* Dependency controls
* Secret isolation
* Build logging

Build systems should not become persistent privileged environments.

---

### 93. Reproducible ML Build Control

Where practical, the organization should be able to reproduce or independently verify the generation of a model artifact.

This requires controlling:

* Code
* Data
* Dependencies
* Configuration
* Training environment
* Build process

Reproducibility supports incident investigation and assurance.

---

### 94. Artifact Repository Security

Repositories storing models and related artifacts should enforce:

* Authentication
* Authorization
* Encryption
* Integrity
* Version control
* Retention
* Audit logging

Artifact repositories should be treated as critical security infrastructure.

---

### 95. Artifact Traceability Control

Every production model should be traceable back to its originating lifecycle artifacts.

```text id="m7q4xn"

      |
      +--> Release
      +--> Training Run
      +--> Dataset
      +--> Features
      +--> Source Code
      +--> Dependencies
      +--> Configuration
```

Traceability allows rapid investigation when a model is found to be compromised or defective.

---

### 96. Automated Model Promotion Controls

Automated promotion should occur only after mandatory security and quality gates succeed.

The pipeline should verify:

* Test results
* Security status
* Artifact integrity
* Approval requirements
* Risk conditions

Automation should enforce policy rather than bypass it.

---

### 97. Drift Detection Control

Production systems should continuously or periodically detect significant changes in:

* Input distributions
* Feature distributions
* Model performance
* Prediction patterns
* Operating conditions

Drift thresholds should be defined according to system risk.

---

### 98. Data Drift Response Control

A significant data drift event should trigger a defined response.

Possible responses include:

* Alert
* Investigation
* Increased monitoring
* Model evaluation
* Temporary deployment restriction
* Retraining

Drift detection should therefore connect directly to lifecycle controls.

---

### 99. Model Performance Monitoring Control

Production model performance should be monitored against defined baselines.

Monitoring should identify:

* Degradation
* Unexpected behavior
* Error increases
* Prediction anomalies
* Service failures

Performance monitoring should feed into security and lifecycle decision-making.

---

### 100. Model Security Monitoring

Security monitoring should identify abnormal model-related behavior.

Potential indicators include:

* Unexpected model changes
* Unusual inference volumes
* Abnormal access
* Repeated adversarial inputs
* Unauthorized registry activity
* Suspicious deployment activity

These signals should be integrated with enterprise security monitoring where appropriate.

---

### 101. Automated Retraining Control

Automated retraining should operate under predefined security conditions.

Before retraining begins, the system should validate:

* Trigger legitimacy
* Dataset source
* Dataset integrity
* Training code
* Dependencies
* Configuration

A retraining event should not become an uncontrolled path to production.

---

### 102. Retraining Security Gate

A newly retrained model should pass required validation before deployment.

### 103. Model Rollback Control

A known-good model version should be available for rollback.

Rollback mechanisms should verify:

* Artifact integrity
* Version
* Approval status
* Compatibility
* Deployment target

Rollback should be executable without bypassing security controls.

---

### 104. Emergency Model Rollback

Emergency rollback should support rapid containment of unsafe or compromised models.

The mechanism should provide:

* Authorized emergency identities
* Predefined rollback targets
* Audit logging
* Integrity verification
* Post-event review

Emergency capability should be powerful but tightly controlled.

---

### 105. Model Retirement Control

Retired models should be prevented from accidental redeployment.

Retirement controls should address:

* Registry status
* Deployment references
* Access permissions
* Artifact retention
* Dependency relationships
* Documentation

Retirement should create a definitive lifecycle state.

---

### 106. ML Infrastructure Vulnerability Management

Infrastructure supporting MLOps should undergo continuous vulnerability management.

This includes:

* Training hosts
* Containers
* Kubernetes clusters
* Operating systems
* ML frameworks
* Libraries
* Storage
* APIs

Security weaknesses in supporting infrastructure can compromise the entire ML lifecycle.

---

### 107. MLOps Secrets Protection

Credentials used by MLOps pipelines should be stored in dedicated secrets-management systems.

Secrets should not be embedded in:

* Source code
* Notebooks
* Pipeline definitions
* Model files
* Container images
* Dataset files

Pipeline workloads should receive secrets only when required.

Network access should be restricted between ML lifecycle components.

Controls may include:

* Firewall controls
* API gateways

Training environments should not automatically have unrestricted enterprise network access.

* Retraining
* Rollback

Logs should be protected against unauthorized modification.

### 111. MLOps Security Telemetry

### 112. ML Security Alerting

Security-relevant conditions should generate alerts according to risk.

Examples include:

* Unauthorized model promotion
* Dataset integrity failure

* Model signature failure
* Unexpected model change
* Registry privilege escalation
* Significant drift
* Security test failure

Alert thresholds should avoid creating excessive noise.

---

### 113. MLOps Security Gate Enforcement

Security gates should be technically enforced rather than relying solely on developer discipline.

A gate may require:

* Dataset validation
* Dependency scanning
* Model testing
* Artifact verification
* Approval
* Risk assessment

Failure of a mandatory gate should prevent the associated transition.

### 114. Fail-Closed MLOps Controls

Security-critical MLOps controls should fail closed.

```text id="p6q9mx"
     |
```

### 115. Security Exception Control

Exceptions to MLOps security controls should require explicit authorization.

An exception record should identify:

* Control being bypassed
* Business justification
* Risk
* Scope
* Compensating controls
* Approver
* Expiration date

Permanent informal bypasses should be prohibited.

---

MLOps security should operate continuously across the lifecycle.

Controls should cover:

```text id="w5m8qx"
  ↓

  ↓

  ↓
```

### 117. Core Engineering Principle

**Every MLOps lifecycle transition must be treated as a controlled security boundary in which identity, authorization, integrity, provenance, validation, and policy enforcement determine whether the ML artifact or process is permitted to advance.**

The essential control relationship is:

```text id="c7m4qx"

   |
   v

   |
   v

   |
   v

   |

   |

   |
   v

   |
   v

   |
   v
```

No single control should be assumed sufficient to establish trust. Secure MLOps requires **defense in depth across data, code, pipelines, models, artifacts, infrastructure, identities, deployment, and runtime operations**.

## Part 3 — Governance

### 118. MLOps Governance Framework

MLOps governance establishes the organizational policies, responsibilities, decision rights, controls, and oversight mechanisms required to securely manage machine learning throughout its lifecycle.

The governance framework should cover:

* Data
* Features
* Experiments
* Training
* Models
* Pipelines
* Infrastructure
* Deployment
* Monitoring
* Retraining
* Retirement

Governance must remain applicable to both manually initiated and automated ML lifecycle activities.

---

### 119. MLOps Ownership

Every significant MLOps capability should have an accountable owner.

Ownership may be distributed across:

| Capability           | Typical Owner             |
| -------------------- | ------------------------- |
| ML platform          | ML Platform Engineering   |
| Dataset              | Data Owner                |
| Model                | Model Owner               |
| Application          | Application Owner         |
| Infrastructure       | Infrastructure/Cloud Team |
| Security controls    | Cybersecurity             |
| Risk                 | Risk/GRC                  |
| Production operation | Service Owner             |

Ownership must be explicit enough to prevent gaps between technical teams.

---

### 120. MLOps Accountability Model

Accountability defines who is ultimately responsible for decisions and outcomes.

A practical model may distinguish:

* **Accountable:** owns the outcome
* **Responsible:** performs the activity
* **Consulted:** provides expertise
* **Informed:** receives relevant information

For high-risk ML systems, security, model, data, and business accountability should not be implicitly assigned to a single technical team.

---

### 121. MLOps Policy

An enterprise MLOps policy should define mandatory requirements for the ML lifecycle.

The policy should address:

* Approved ML platforms
* Data requirements
* Model lifecycle requirements
* Security controls
* Testing
* Deployment
* Monitoring
* Retraining
* Change management
* Evidence retention
* Exceptions

The policy establishes organizational expectations while detailed standards define implementation requirements.

---

### 122. MLOps Standards

Standards translate policy into measurable technical requirements.

Examples include standards for:

* Dataset versioning
* Model naming
* Model registry usage
* Training environments
* Artifact signing
* Pipeline authentication
* Security testing
* Deployment authorization
* Logging
* Drift monitoring

Standards should be sufficiently specific to support consistent implementation.

---

### 123. MLOps Procedures

Procedures define how teams execute governed ML activities.

Examples include:

* Dataset onboarding
* Model registration
* Model approval
* Model promotion
* Production deployment
* Retraining
* Rollback
* Model retirement

Procedures should define required inputs, approvals, evidence, and outputs.

---

### 124. MLOps Security Baseline

An enterprise should establish a minimum security baseline applicable to MLOps environments.

The baseline may require:

* Strong identity
* Least privilege
* Environment separation
* Dataset controls
* Dependency controls
* Artifact integrity
* Security testing
* Logging
* Monitoring
* Backup and recovery

Higher-risk systems should inherit the baseline and add additional controls.

---

### 125. ML System Risk Classification

ML systems should be classified according to their potential impact.

Classification factors may include:

* Business criticality
* Data sensitivity
* Decision impact
* Regulatory requirements
* User population
* Model autonomy
* Operational dependency
* Potential harm

Classification determines the level of governance and assurance required.

---

### 127. ML Lifecycle Security Requirements Governance

Security requirements should be established before significant ML development begins.

Requirements should address:

* Data protection
* Identity
* Access control
* Model integrity
* Pipeline security
* Infrastructure
* Monitoring
* Incident response
* Recovery

Requirements should remain traceable throughout the lifecycle.

### 130. Data Governance Integration

MLOps governance must integrate with enterprise data governance.

* Data ownership
* Data retention
* Data access
* Data quality
* Privacy
* Data lineage
* Approved use

The MLOps process should not independently redefine enterprise data governance.

Dataset governance should establish:

* Authorized purpose
* Approved sources
* Access rules
* Retention
* Versioning
* Validation
* Security classification
* Retirement requirements

Only appropriately governed datasets should enter trusted training workflows.

### 132. Dataset Change Governance

Changes to training datasets should be assessed according to their potential impact.

Material changes may include:

* New source
* New population
* Changed labels
* Major transformation
* Significant volume change
* New sensitive attributes

Material dataset changes may require model reassessment or retraining validation.

### 133. Feature Governance

Features should have identifiable ownership and lifecycle controls.

Governance should cover:

* Feature definitions
* Data sources
* Transformations
* Business meaning
* Security classification
* Approved consumers
* Versioning

Uncontrolled feature changes can produce uncontrolled model behavior.

### 134. Model Governance Integration

MLOps governance should integrate with the organization's broader model governance framework.

Model governance may establish:

* Approval
* Monitoring
* Change requirements
* Retirement

MLOps provides the operational mechanisms for implementing these governance requirements.

### 136. Model Change Governance

* Changed architecture
* Changed parameters
* New feature set
* Changed dependency
* Changed inference behavior

The required level of review should depend on risk and change impact.

### 137. Retraining Governance

Retraining should be governed even when automated.

Governance should establish:

* Approved triggers
* Authorized data sources
* Maximum retraining frequency
* Required tests
* Approval conditions
* Deployment rules
* Rollback requirements

Automation should execute within predefined governance boundaries.

---

### 138. Continuous Training Governance

Continuous training introduces special governance requirements because models may change repeatedly.

The organization should define:

* Which models qualify
* Which data sources are authorized
* Which tests are mandatory
* Which changes require human approval
* Which changes may be automatically promoted

High-risk models may require human approval for every material model version.

---

### 139. Experiment Governance

ML experiments should be governed according to their environment and data sensitivity.

Governance should establish controls around:

* Dataset access
* Sensitive information
* External models
* External code
* Experiment ownership
* Result retention

Experimental status should not be interpreted as exemption from security requirements.

---

### 140. Training Governance

Training activities should be conducted using approved infrastructure and processes.

Governance should establish:

* Approved training platforms
* Authorized identities
* Dataset restrictions
* Compute restrictions
* Dependency requirements
* Logging
* Artifact handling

Training workloads should remain attributable.

---

### 141. MLOps Pipeline Governance

MLOps pipelines should be treated as governed production systems.

Pipeline governance should address:

* Pipeline ownership
* Change control
* Access control
* Security gates
* Service identities
* Deployment authority
* Emergency procedures

A pipeline capable of creating or deploying production models should receive elevated governance attention.

### 142. Pipeline Change Governance

Changes to pipeline logic should be reviewed according to risk.

Security-sensitive changes include modifications to:

* Security gates
* Deployment targets
* Service identities
* Dataset sources
* Model promotion logic
* Testing requirements

A pipeline should not be permitted to weaken its own security controls without independent authorization.

### 143. Model Registry Governance

The model registry should have formal governance.

Governance should define:

* Who may register models
* Who may modify metadata
* Who may approve models
* Who may promote models
* Who may retire models
* Required evidence

The registry should function as an authoritative lifecycle record.

### 144. Model Approval Governance

Model approval should be based on documented evidence.

Approval should consider:

* Intended purpose
* Model performance
* Security testing
* Data provenance
* Model provenance
* Risk classification
* Operational readiness

Approval should be attributable to an authorized decision-maker.

### 145. Model Promotion Governance

### 146. Security Testing Governance

* Responsible parties

### 147. Adversarial Testing Governance

### 150. MLOps Build Governance

Model builds and training builds should operate under controlled processes.

### 151. Artifact Governance

* Validated

### 153. Model Retirement Governance

Model retirement should be an intentional governance process.

Retirement should address:

* Registry state
* Dependencies
* Artifact retention
* Documentation
* Replacement model

Retired models should not remain accidentally deployable.

### 154. MLOps Change Management

MLOps changes should follow enterprise change-management principles.

* Who initiated it
* Security impact
* Testing
* Approval
* Deployment
* Rollback plan

The process should distinguish routine, material, and emergency changes.

### 155. Security Impact Assessment for ML Changes

Material ML changes should undergo security impact assessment.

The assessment should consider:

* New data
* New dependencies
* Model behavior
* New infrastructure
* Changed permissions
* Changed interfaces
* New threats

The assessment determines whether additional testing or approval is required.

### 156. Emergency MLOps Change Governance

Emergency changes should support rapid response without eliminating accountability.

Emergency procedures should define:

* Emergency controls
* Required logging
* Temporary validity
* Post-change review

Emergency access should not become a permanent alternative deployment mechanism.

### 157. MLOps Release Governance

ML releases should have defined release criteria.

Release readiness should consider:

* Security tests
* Model evaluation
* Artifact integrity
* Configuration
* Approval
* Monitoring readiness
* Rollback capability

A technically deployable model is not necessarily a governance-approved model.

---

### 158. Production Deployment Governance

Production deployment should be authorized according to system risk.

The deployment decision should verify:

* Correct model
* Correct version
* Correct environment
* Required approvals
* Security status
* Operational readiness

Production deployment should remain attributable.

---

### 159. Separation of Duties

### 160. MLOps Risk Acceptance Governance

Residual risk should be formally accepted by an authorized party.

* Business justification
* Affected system
* Existing controls
* Residual exposure
* Risk owner
* Expiration/review date

### 161. MLOps Security Exceptions

Exceptions should be temporary, documented, and risk-based.

* Control being bypassed
* Reason
* Scope
* Duration
* Risk
* Compensating controls
* Approver

Expired exceptions should automatically return to normal control requirements.

### 162. Compensating Controls

When a mandatory control cannot be implemented, alternative controls may reduce the associated risk.

* Additional monitoring
* Restricted deployment
* Manual approval
* Network isolation
* Increased testing
* Shorter review intervals

Compensating controls should provide measurable risk reduction.

---

### 163. MLOps Security Evidence Governance

MLOps activities should generate evidence sufficient to demonstrate compliance and security assurance.

Evidence may include:

* Dataset validation results
* Training records
* Security test results
* Model approval
* Artifact signatures
* Deployment records
* Monitoring events
* Retraining records

### 164. Evidence Retention

Evidence retention should align with:

* Regulatory requirements
* Enterprise retention policy
* Risk classification
* Incident investigation needs
* Model lifecycle duration

Critical model lifecycle evidence should remain available for retrospective investigation.

### 165. MLOps Auditability

An auditor or investigator should be able to reconstruct significant model lifecycle events.

* Who approved it?
* Which artifact was deployed?
* When was it deployed?
* What changed afterward?

Auditability is a fundamental MLOps governance property.

### 166. GRC Integration

* Compliance obligations
* Policy management
* Exception management
* Audit management
* Evidence repositories

### 167. MLOps Risk Register Integration

### 170. Continuous Compliance Governance

* Approved datasets
* Approved dependencies
* Model signatures
* Registry states
* Security test status
* Required approvals
* Deployment configuration

Continuous compliance reduces dependence on periodic manual reviews.

---

### 171. Independent MLOps Security Assurance

High-risk ML systems should receive independent security review.

Independent assurance may assess:

* Control effectiveness
* Pipeline security
* Model lifecycle
* Data governance
* Artifact integrity
* Monitoring
* Incident readiness

Independence reduces the risk of self-assessment bias.

---

### 172. MLOps Governance Review

Governance reviews should evaluate whether the MLOps environment remains appropriate.

Reviews may examine:

* Risk changes
* New ML technologies
* Security incidents
* Control failures
* Regulatory changes
* Platform changes
* Model lifecycle trends

The review frequency should reflect system risk.

---

### 173. MLOps Governance Maturity

MLOps governance maturity can evolve through stages:

| Level      | Characteristics                                   |
| ---------- | ------------------------------------------------- |
| Initial    | Ad hoc ML development                             |
| Managed    | Defined processes                                 |
| Controlled | Security gates and governance                     |
| Integrated | MLOps, MLSecOps and GRC integrated                |
| Optimized  | Continuous assurance and risk-adaptive automation |

Maturity should be assessed based on actual operating capability rather than documentation volume.

### 175. MLOps Reauthorization Governance

Models should not necessarily retain authorization indefinitely.

Reauthorization may be triggered by:

* Significant drift
* Material model change
* New data source
* Security incident
* New vulnerability
* Change in intended use
* Significant infrastructure change

Reauthorization ensures that historical approval does not become permanent uncontrolled trust.

---

### 176. Enterprise Security Principle

**MLOps governance must ensure that no ML artifact, dataset, pipeline, model, or automated lifecycle process receives permanent trust merely because it was previously approved.**

Authorization should remain conditional on:

* Current risk
* Current security status
* Current provenance
* Current lifecycle state
* Current intended use
* Current operational conditions

---

**MLOps governance must establish a controlled chain of accountability from data acquisition through model retirement, ensuring that every material ML lifecycle decision is attributable, risk-informed, independently enforceable where necessary, supported by evidence, and subject to continuous reassessment.**
