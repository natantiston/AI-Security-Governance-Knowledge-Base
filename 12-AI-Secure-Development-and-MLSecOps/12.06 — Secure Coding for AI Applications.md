# 12.06 — Secure Coding for AI Applications

## Part 1 — Foundations

### 1. Definition of Secure Coding for AI Applications

Secure coding for AI applications is the discipline of applying security engineering principles to software that incorporates AI models, AI services, prompts, datasets, agents, inference APIs, and AI-generated outputs.

AI applications introduce security considerations beyond conventional application code because application behavior may depend on probabilistic model outputs, untrusted prompts, external models, retrieved data, and dynamically generated content.

---

### 2. Purpose of Secure AI Coding

The purpose of secure AI coding is to prevent vulnerabilities from being introduced into the application layer that connects users, data, models, tools, APIs, and infrastructure.

Secure coding should protect:

* Application logic
* AI interfaces
* Model interactions
* User data
* System instructions
* Credentials
* APIs
* Tool integrations
* Generated outputs
* Downstream systems

---

### 3. AI Applications as Security Systems

An AI application should be treated as a security-sensitive system rather than simply a software interface to a model.

```text id="c7m4px"
User
  |
  v
AI Application
  |
  +----> Model
  |
  +----> Data
  |
  +----> APIs
  |
  +----> Tools
  |
  +----> External Services
  |
  v
Enterprise Systems
```

Every connection creates a potential security boundary.

---

### 4. Secure-by-Design AI Coding

Security requirements should influence application architecture before implementation begins.

Developers should determine:

* What data the application can access
* Which models it can invoke
* Which tools it can call
* Which APIs it can use
* Which users can operate it
* Which actions require authorization

Security should not depend on developers remembering to add controls at the end.

---

### 5. Security-by-Default

AI applications should begin in a secure state.

Examples include:

* Denied access by default
* Minimal permissions
* Restricted API access
* Protected secrets
* Safe logging
* Disabled unnecessary tools
* Restricted network connectivity

Additional capabilities should require explicit authorization.

---

### 6. Least Privilege in AI Applications

AI applications should operate using the minimum privileges required for their intended purpose.

This applies to:

* Application identities
* Model access
* Database access
* API permissions
* Tool permissions
* File access
* Cloud resources

An AI application should not receive broad privileges simply because its model may need flexibility.

---

### 7. Separation of Model and Application Authority

The AI model should not independently determine what the application is authorized to do.

```text id="m8q5px"
Model
  |
  | Recommendation / Output
  v
Application Policy
  |
  v
Authorization
  |
  v
Permitted Action
```

**Model output is data; application authorization determines authority.**

---

### 8. Model Output Is Untrusted Input

AI-generated output should be treated as potentially untrusted data.

Outputs may contain:

* Incorrect information
* Malicious instructions
* Unexpected commands
* Injection payloads
* Sensitive information
* Unsafe parameters

Applications should validate outputs before passing them to security-sensitive functions.

---

### 9. Input Validation

AI applications should validate inputs before processing them.

Validation should address:

* Data type
* Size
* Format
* Encoding
* Allowed values
* Context
* User permissions

Input validation should apply to both traditional application inputs and AI-specific inputs such as prompts and retrieved content.

---

### 10. Output Validation

AI outputs should be validated according to their intended use.

For example, if an AI model produces:

```text id="q4m7px"
AI Output
    |
    v
Structured Validation
    |
    v
Business Rules
    |
    v
Authorization
    |
    v
Action
```

The application should not directly execute arbitrary model-generated instructions.

---

### 11. Prompt Security

Prompts should be treated as application security components.

Security-sensitive prompts may contain:

* System instructions
* Business rules
* Security constraints
* Tool instructions
* Data-handling requirements

Unauthorized modification of prompts can change application behavior.

---

### 12. Prompt Injection Awareness

AI applications should assume that untrusted content may attempt to influence model instructions.

Potential sources include:

* User prompts
* Retrieved documents
* Web pages
* Emails
* Uploaded files
* Database content
* External APIs

Developers should establish boundaries between trusted instructions and untrusted content.

---

### 13. Instruction Hierarchy

AI applications should clearly distinguish between different sources of instructions.

For example:

```text id="w5m9px"
Trusted System Policy
        |
        v
Application Instructions
        |
        v
User Input
        |
        v
External / Retrieved Content
```

Lower-trust content should not automatically override higher-trust application requirements.

---

### 14. Context Boundary Protection

Application developers should define which information can enter the model context.

Context may contain:

* User information
* Business data
* Retrieved documents
* System instructions
* Tool results
* Previous interactions

Unnecessary information should not be included.

---

### 15. Data Minimization in AI Code

Applications should pass only necessary data to models and AI services.

For example, an application processing a customer request may not need to provide the model with the customer's complete database record.

Data minimization reduces:

* Exposure
* Leakage potential
* Privacy risk
* Attack surface

---

### 16. Sensitive Data Handling

Sensitive information should receive appropriate protection when processed by AI applications.

Developers should consider:

* Classification
* Encryption
* Access control
* Masking
* Redaction
* Retention
* Provider boundaries

Sensitive information should not be exposed to AI components without an approved business purpose.

---

### 17. Secrets Management

Credentials should never be embedded in AI source code, prompts, or model configurations.

Secrets should be retrieved through controlled mechanisms.

```text id="r6m8px"
AI Application
      |
      v
Workload Identity
      |
      v
Secrets Manager
      |
      v
Temporary Credential
```

This reduces the risk of credential exposure through code or model context.

---

### 18. Authentication

AI applications should authenticate users and services before granting access to protected functionality.

Authentication should establish:

* User identity
* Service identity
* Workload identity

Authentication alone should not determine what the user or application is allowed to do.

---

### 19. Authorization

Authorization should independently determine whether an operation is permitted.

Authorization decisions should consider:

* Identity
* Resource
* Action
* Context
* Environment
* Risk

The model should not be treated as an authorization engine.

---

### 20. Object-Level Authorization

AI applications should validate authorization at the level of individual resources.

For example, a user authorized to access customer records should not automatically gain access to every customer record simply because the AI application can retrieve them.

Authorization should be enforced before data reaches the model.

---

### 21. Tool Authorization

Tools exposed to AI applications should have explicit permissions.

Tools may include:

* Database queries
* File operations
* Search
* Email
* Ticketing
* Cloud APIs
* Administrative functions

Tool availability should be determined by authorization policy, not merely by model preference.

---

### 22. API Security

AI applications should protect internal and external APIs.

Controls should include:

* Authentication
* Authorization
* Input validation
* Output validation
* Rate limiting
* TLS
* Error handling
* Logging

AI-specific interfaces should receive the same security rigor as other enterprise APIs.

---

### 23. Tool Input Validation

AI-generated tool parameters should be validated before execution.

```text id="p8m4px"
Model
  |
  v
Tool Request
  |
  v
Schema Validation
  |
  v
Authorization
  |
  v
Business Rules
  |
  v
Tool Execution
```

A valid schema does not automatically make a request authorized.

---

### 24. Tool Output Validation

Tool results should also be treated as potentially untrusted data.

Results may contain:

* Unexpected instructions
* Malicious content
* Sensitive information
* Incorrect data
* Prompt injection payloads

Tool outputs should be bounded before being returned to the model or user.

---

### 25. Database Security

AI applications should use controlled database access.

Developers should enforce:

* Least privilege
* Parameterized queries
* Row-level authorization where appropriate
* Data minimization
* Audit logging

AI-generated queries should never bypass normal database security controls.

---

### 26. Command Execution Security

AI applications should avoid directly executing unrestricted model-generated commands.

Where command execution is required, the application should use:

* Allowlisted operations
* Structured parameters
* Restricted identities
* Sandboxing
* Authorization
* Resource limits

Arbitrary model-generated shell commands should not be treated as trusted instructions.

---

### 27. File Handling Security

AI applications frequently process uploaded or generated files.

Secure file handling should address:

* File type validation
* File size limits
* Malware scanning
* Path traversal
* Access control
* Storage isolation
* Temporary-file management

Uploaded files should be considered untrusted.

---

### 28. Retrieval-Augmented Generation Security

RAG applications introduce additional security boundaries between the model and retrieved information.

The architecture should protect:

* Document stores
* Embeddings
* Vector databases
* Retrieval APIs
* Metadata
* Access permissions

Retrieval should respect the user's authorization.

---

### 29. Retrieval Authorization

The AI application should verify that the user is authorized to retrieve a document before providing it to the model.

```text id="n6m4px"
User
 |
 v
Authentication
 |
 v
Authorization
 |
 v
Document Retrieval
 |
 v
Allowed Content
 |
 v
Model Context
```

The model should never become a mechanism for bypassing document permissions.

---

### 30. Vector Store Security

Vector databases and embedding stores should be treated as sensitive application infrastructure.

Security should address:

* Access control
* Tenant isolation
* Metadata protection
* Query authorization
* Encryption
* Logging

Embeddings should not automatically be considered harmless because they are not human-readable source documents.

---

### 31. Multi-Tenant AI Security

Multi-tenant AI applications must prevent one tenant's data from being exposed to another tenant.

Controls should protect:

* Context
* Retrieval
* Memory
* Files
* Database records
* Model interactions

Tenant identity should remain bound to every security-sensitive request.

---

### 32. Session Security

AI sessions should have appropriate security controls.

These may include:

* Session authentication
* Expiration
* Authorization checks
* Context isolation
* Secure session storage
* Session invalidation

A user's previous context should not automatically be available to another user.

---

### 33. Memory Security

Where AI applications maintain persistent memory, memory should be treated as application data.

Controls should address:

* Access
* Integrity
* Retention
* Deletion
* Tenant isolation
* Sensitive information

Memory should not become an uncontrolled secondary data store.

---

### 34. Logging Security

AI applications should log security-relevant events without unnecessarily exposing sensitive information.

Events may include:

* Authentication
* Authorization failures
* Tool execution
* Model invocation
* Configuration changes
* Security policy decisions

Logs should themselves be protected.

---

### 35. Sensitive Data in Logs

AI applications should prevent unnecessary sensitive information from entering logs.

Developers should consider:

* Prompt content
* Model output
* Personal data
* Credentials
* Tokens
* Retrieved documents

Logging should balance security visibility with data-protection requirements.

---

### 36. Error Handling

AI applications should fail safely when unexpected conditions occur.

Error handling should avoid exposing:

* Secrets
* Internal architecture
* Credentials
* Database details
* Sensitive prompts
* Security configuration

Errors should provide sufficient information for operators without unnecessarily assisting attackers.

---

### 37. Rate Limiting

AI APIs should use appropriate rate limits.

Rate limiting can reduce:

* Abuse
* Resource exhaustion
* Automated attacks
* Excessive model extraction attempts
* Denial-of-service impact

Limits should consider both user identity and application risk.

---

### 38. Resource Controls

AI applications should enforce resource boundaries.

Resources may include:

* Tokens
* Compute
* Memory
* API calls
* Tool invocations
* File size
* Processing time

Resource controls reduce the impact of abusive or unexpected behavior.

---

### 39. Dependency Security in AI Applications

AI applications depend on frameworks, libraries, SDKs, and external services.

Secure coding should require:

* Approved dependencies
* Vulnerability scanning
* Version control
* Dependency pinning
* Software composition analysis

Dependencies should not be trusted merely because they are common in AI development.

---

### 40. Secure Model Integration

Applications should securely integrate external and internal models.

Integration should verify:

* Model identity
* Provider
* Endpoint
* Version
* Security requirements
* Data-handling rules

Changing a model provider should be treated as a potentially security-relevant change.

---

### 41. Model Configuration Security

Model configuration should be protected from unauthorized modification.

Configuration may include:

* Model identifier
* Temperature
* Token limits
* System instructions
* Tool permissions
* Safety parameters
* Provider endpoints

Configuration changes should be traceable and governed.

---

### 42. AI Provider Boundary Security

External AI providers should be treated as explicit trust boundaries.

```text id="h7m5px"
Enterprise Data
      |
      v
Data Policy
      |
      v
Security Gateway
      |
      v
External AI Provider
      |
      v
AI Response
```

Only approved data and operations should cross the provider boundary.

---

### 43. Secure Data Transmission

Data transmitted between AI components should use appropriate transport security.

Controls should include:

* TLS
* Certificate validation
* Secure service identities
* Endpoint validation
* Network restrictions

Sensitive AI traffic should not rely on uncontrolled communication channels.

---

### 44. Secure AI Configuration Management

Security-sensitive configuration should be managed through controlled configuration systems.

Configuration should support:

* Versioning
* Access control
* Review
* Integrity
* Environment separation
* Auditability

Configuration should not be modified directly in production without governance.

---

### 45. Security Testing During Coding

Developers should incorporate security testing throughout implementation.

Testing should address:

* Code vulnerabilities
* Prompt injection
* Authorization
* Data leakage
* Tool abuse
* API security
* Dependency vulnerabilities

Security testing should begin before the release stage.

---

### 46. Secure Coding and CI/CD

Secure coding controls should be integrated into CI/CD pipelines.

---

### 47. Secure Change Management

Changes to AI application code should be assessed for security impact.

Particular attention should be given to changes involving:

* Model integrations
* Data access
* Tool permissions
* Authentication
* Authorization
* Prompt logic
* External APIs

A small code change can materially alter AI security behavior.

---

### 48. Secure Coding Traceability

Security-sensitive implementation decisions should be traceable to their requirements.

```text id="s6m9px"
Threat

  v
Security Requirement
  |
  v
Code Control
  |
  v
Security Test
  |
  v
Release Evidence
```

Traceability allows the organization to demonstrate that security requirements were implemented and tested.

---

### 49. Secure AI Coding Principles

Secure AI application development should consistently apply:

1. Secure by design
2. Secure by default
3. Least privilege
4. Zero Trust
5. Input validation
6. Output validation
7. Explicit authorization
8. Data minimization
9. Secure secrets management
10. Tool isolation
11. Dependency security
12. Model integrity
13. Secure API design
14. Continuous testing
15. Traceability
16. Fail-secure behavior

These principles should be incorporated into engineering standards and development workflows.

---

### 50. Core Principle of Secure Coding for AI Applications

**AI-generated behavior must never be allowed to bypass conventional application security controls.**

The secure AI application model is:

```text id="v5m8px"
User / External Input
          |
          v
     Authentication
          |
          v
      Authorization
          |
          v
      AI Application
          |
     +----+----+
     |         |
     v         v
   Model     Tools
     |         |
     +----+----+
          |
          v
    Output Validation
          |
          v
    Business Policy
          |
          v
      Authorized
        Action
```

**The fundamental principle is that the AI model may generate recommendations, content, or proposed actions, but the application must independently validate, authorize, constrain, and monitor what the system is ultimately permitted to do.**

## Part 2 — Security Controls

### 51. Secure AI Application Control Framework

Secure coding principles must be translated into technical controls that can be consistently enforced across AI applications.

The control framework should cover:

* Application code
* Prompts and instructions
* Model interfaces
* Data access
* Retrieval systems
* Tools
* APIs
* Secrets
* Dependencies
* Containers
* CI/CD
* Runtime behavior

Controls should be measurable, testable, and capable of producing security evidence.

---

### 52. Source Code Repository Control

AI application source code should be stored in controlled repositories.

Controls should include:

* Strong authentication
* Role-based access
* Protected branches
* Pull-request requirements
* Audit logging
* Secret scanning
* Vulnerability scanning

Repository access should follow least privilege.

---

### 53. Branch Protection Control

Production-bound AI application branches should prevent unauthorized direct modification.

Controls should include:

* Required pull requests
* Required reviewers
* Automated security checks
* Restricted force pushes
* Restricted branch deletion
* Status-check enforcement

Security controls should remain active even for urgent development changes.

---

### 54. Secure Code Review Control

AI application changes should receive security-aware code review.

Reviewers should examine:

* Authentication
* Authorization
* Data handling
* Prompt construction
* Model invocation
* Tool execution
* API calls
* Secrets
* Error handling

High-risk changes should receive additional independent review.

---

### 55. Static Application Security Testing Control

SAST should be integrated into AI application development pipelines.

It should identify vulnerabilities such as:

* Injection
* Unsafe deserialization
* Authentication weaknesses
* Authorization failures
* Hardcoded secrets
* Command execution risks
* Insecure API usage

Security findings should feed release decisions.

---

### 56. Secret Scanning Control

AI source code and associated configuration should be automatically scanned for exposed secrets.

Scanning should identify:

* API keys
* Tokens
* Passwords
* Private keys
* Cloud credentials
* Database credentials

Discovered credentials should be treated as potentially compromised.

---

### 57. Dependency Security Control

AI applications should continuously assess dependencies for vulnerabilities.

Coverage should include:

* AI frameworks
* SDKs
* Python packages
* JavaScript packages
* Runtime libraries
* System packages

Dependency security should continue after deployment.

---

### 58. Software Composition Analysis Control

SCA should maintain visibility into application components.

SCA should identify:

* Direct dependencies
* Transitive dependencies
* Versions
* Vulnerabilities
* Component provenance
* License information

The resulting inventory should be associated with the application release.

---

### 59. AI Software Bill of Materials Control

Each governed AI application release should maintain an SBOM appropriate to organizational requirements.

The SBOM should identify relevant software components and versions.

```text id="j5m8px"
Application Release
       |
       v
      SBOM
       |
 +-----+-----+
 |     |     |
Code  AI SDK Runtime
 |     |     |
 +-----+-----+
       |
       v
Vulnerability Analysis
```

---

### 60. Input Validation Control

All externally influenced inputs should be validated before being processed.

Validation should address:

* Type
* Format
* Length
* Encoding
* Allowed values
* Context
* Authorization

AI prompts should not be exempt from application input-validation principles.

---

### 61. Prompt Input Security Control

User-supplied prompts should be treated as untrusted input.

Controls should prevent users from using prompt input to bypass:

* Application policies
* Access controls
* Tool restrictions
* Data boundaries
* Security instructions

Prompt filtering should complement, not replace, authorization controls.

---

### 62. Prompt Template Integrity Control

Security-sensitive prompts and system instructions should be protected from unauthorized modification.

Controls should include:

* Version control
* Access restrictions
* Code review
* Integrity verification
* Change logging

Changes should be associated with identifiable releases.

---

### 63. Instruction Separation Control

Applications should technically separate trusted instructions from untrusted content where possible.

For example:

```text id="r7m4px"
System Policy
     |
     v
Application Instructions
     |
     +----> User Content
     |
     +----> Retrieved Content
     |
     +----> Tool Results
```

Untrusted content should not be allowed to redefine application security policy.

---

### 64. Context Isolation Control

AI applications should limit the information included in each model context.

Controls should prevent unnecessary inclusion of:

* Sensitive records
* Credentials
* Internal instructions
* Unrelated tenant information
* Excessive conversation history

Context should be constructed according to the user's authorization.

---

### 65. Output Validation Control

Model outputs should be validated before being consumed by security-sensitive application functions.

Validation may include:

* Schema validation
* Type validation
* Content validation
* Business-rule validation
* Security policy checks

A model's confidence or apparent correctness should not replace validation.

---

### 66. Structured Output Control

Where applications depend on model-generated structured data, schemas should constrain the expected output.

For example:

```text id="m8q5px"
Model Output
     |
     v
Schema Validation
     |
     +---- Invalid ---> Reject
     |
     v
Business Validation
     |
     v
Authorized Processing
```

Structured outputs reduce ambiguity but do not independently establish authorization.

---

### 67. Model Invocation Control

Applications should invoke only approved models and endpoints.

Controls should verify:

* Model identity
* Model version
* Provider
* Endpoint
* Environment
* Security classification

Applications should not dynamically switch to arbitrary models without governance.

---

### 68. Model Integrity Control

Applications should verify the integrity of locally hosted or internally managed model artifacts.

Verification may use:

* Cryptographic hashes
* Digital signatures
* Registry metadata
* Trusted provenance

Unexpected model changes should prevent use or trigger investigation.

---

### 69. Model Loading Control

Model-loading mechanisms should protect against malicious model files and unsafe loading operations.

Controls should include:

* Approved formats
* Trusted sources
* Integrity validation
* Sandboxed processing
* Secure deserialization

Untrusted model artifacts should not be loaded into privileged processes.

---

### 70. Unsafe Deserialization Control

AI applications should prohibit unsafe deserialization mechanisms where they can result in arbitrary code execution.

Developers should:

* Prefer safe serialization formats
* Validate artifact sources
* Restrict deserialization capabilities
* Scan artifacts
* Isolate model-loading operations

Serialization boundaries should be treated as security boundaries.

---

### 71. Tool Access Control

AI applications should expose tools only when explicitly required.

Tool permissions should be based on:

* Application identity
* User identity
* Requested action
* Resource
* Risk
* Business purpose

The model should not determine its own tool privileges.

---

### 72. Tool Allowlisting Control

Where feasible, applications should maintain explicit allowlists of permitted tools.

For example:

```text id="q6m9px"
AI Application
      |
      v
Tool Policy
      |
 +----+----+------+
 |         |      |
Search   Read DB  Approved API
 |         |      |
 +---------+------+
           |
      Block Others
```

Unapproved tools should remain unavailable.

---

### 73. Tool Parameter Validation Control

AI-generated tool parameters should be validated before execution.

Validation should include:

* Data type
* Allowed values
* Resource scope
* Size
* Syntax
* Business constraints

Valid parameters must still pass authorization.

---

### 74. Tool Execution Authorization Control

Tool execution should require an independent authorization decision.

```text id="w8m5px"
Model Request
     |
     v
Parameter Validation
     |
     v
Authorization
     |
     v
Business Policy
     |
     v
Tool Execution
```

A model request should never directly equal an authorized operation.

---

### 75. High-Risk Tool Approval Control

High-impact operations should require stronger authorization.

Examples include:

* Deleting data
* Sending external communications
* Changing permissions
* Financial transactions
* Administrative changes
* Production modifications

Human approval may be required according to risk.

---

### 76. Command Execution Control

AI applications that execute system commands should use constrained execution mechanisms.

Controls should include:

* Command allowlists
* Parameter restrictions
* Sandboxing
* Restricted identities
* Resource limits
* Execution logging

Arbitrary shell execution should be prohibited unless explicitly justified and strongly controlled.

---

### 77. Database Query Security Control

AI-generated database queries should pass through normal database security controls.

Controls should include:

* Parameterization
* Query allowlists where appropriate
* Least-privileged database identities
* Row-level authorization
* Query limits
* Audit logging

The AI model should not receive unrestricted database authority.

---

### 78. File Access Control

AI applications should restrict file access according to identity and business purpose.

Controls should address:

* File permissions
* Directory boundaries
* Path validation
* Tenant isolation
* File-type restrictions
* Access logging

---

### 79. File Upload Security Control

Uploaded files should be treated as untrusted.

Controls should include:

* File-type validation
* Size limits
* Malware scanning
* Content inspection
* Filename normalization
* Storage isolation

Files should be scanned before being provided to privileged processing environments.

---

### 80. Path Traversal Protection Control

Applications handling AI-generated or user-generated file paths should prevent traversal outside authorized directories.

Controls should:

* Normalize paths
* Reject unauthorized paths
* Restrict filesystem permissions
* Use controlled storage locations

AI-generated paths should never be trusted simply because they originated from the model.

---

### 81. RAG Retrieval Security Control

Retrieval-Augmented Generation systems should enforce authorization before returning information to the model.

The retrieval layer should validate:

* User identity
* Tenant
* Document permissions
* Data classification
* Retrieval scope

Unauthorized documents should never enter model context.

---

### 82. Vector Database Access Control

Vector databases should enforce access controls equivalent to the sensitivity of the underlying information.

Controls should include:

* Authentication
* Authorization
* Tenant isolation
* Query restrictions
* Encryption
* Audit logging

---

### 83. Embedding Security Control

Embeddings should be protected as potentially sensitive derived data.

Controls should address:

* Access
* Storage
* Encryption
* Retention
* Tenant isolation
* Deletion

Embeddings should not automatically be treated as non-sensitive merely because they are machine-generated representations.

---

### 84. Tenant Isolation Control

Multi-tenant AI applications should enforce tenant boundaries throughout the application.

Tenant identity should remain bound to:

* Requests
* Sessions
* Retrieval
* Memory
* Database queries
* Tool calls
* Model interactions

Cross-tenant data access should be blocked by technical controls.

---

### 85. Session Isolation Control

AI sessions should maintain strict isolation between users.

Controls should prevent unauthorized sharing of:

* Conversation history
* Context
* Memory
* Retrieved documents
* Tool results

Session identifiers should not be treated as authorization credentials.

---

### 86. AI Memory Access Control

Persistent AI memory should have explicit access policies.

Controls should define:

* Who can create memory
* Who can read it
* Who can modify it
* Who can delete it
* How long it is retained

Memory should be subject to the same security expectations as other application data.

---

### 87. Authentication Control

AI applications should authenticate users and services before granting access to protected capabilities.

Authentication mechanisms should be integrated with enterprise identity systems where appropriate.

Anonymous access should be limited to explicitly approved use cases.

---

### 88. Authorization Control

Authorization should be enforced independently of the model.

Authorization decisions should evaluate:

* Identity
* Resource
* Action
* Context
* Risk
* Environment

This ensures that model-generated intent cannot bypass enterprise access controls.

---

### 89. Object-Level Authorization Control

Applications should verify authorization for each protected object or resource.

For example:

```text id="s5m9px"
User
 |
 v
Request Customer A
 |
 v
Authorization Check
 |
 +---- Denied ---> Stop
 |
 v
Retrieve Customer A
```

Authorization should not be inferred from general application access.

---

### 90. API Authentication and Authorization Control

AI APIs should require appropriate authentication and authorization.

Controls should include:

* Identity verification
* Token validation
* Scope validation
* Resource authorization
* Rate limiting
* Audit logging

---

### 91. API Input Security Control

AI APIs should validate incoming requests before processing them.

Controls should include:

* Schema validation
* Size limits
* Content validation
* Authentication
* Authorization
* Rate limits

Malformed or unauthorized requests should be rejected before model processing.

---

### 92. API Output Security Control

API responses containing AI-generated content should be validated before being returned or forwarded.

Controls should address:

* Data leakage
* Unauthorized information
* Unsafe content
* Unexpected structures
* Security-sensitive output
