# 12.04 — MLSecOps

## Part 1 — Foundations

### 1. Definition of MLSecOps

MLSecOps is the integration of cybersecurity practices, controls, governance, automation, and continuous assurance into the machine learning lifecycle.

It extends MLOps by embedding security throughout:

* Data
* Feature engineering
* Model development
* Training
* Evaluation
* Packaging
* Deployment
* Runtime
* Monitoring
* Retraining
* Retirement

The objective is not to add security as a final checkpoint, but to make security an inherent property of the ML delivery lifecycle.

---

### 2. Purpose of MLSecOps

The purpose of MLSecOps is to ensure that machine learning systems are developed and operated with security continuously enforced.

MLSecOps addresses the problem that traditional security approaches may protect the surrounding infrastructure while leaving ML-specific attack surfaces insufficiently controlled.

Its objectives include:

* Preventing ML supply-chain compromise
* Protecting datasets
* Protecting models
* Securing ML pipelines
* Detecting ML-specific threats
* Reducing lifecycle risk
* Automating security enforcement
* Maintaining continuous assurance

---

### 3. MLSecOps vs MLOps

MLOps focuses primarily on reliably building, deploying, and operating ML systems.

MLSecOps incorporates security into those same processes.

```text id="m4q8xn"
                 MLOps
                   |
       +-----------+-----------+
       |           |           |
      Data       Model      Pipeline
       |           |           |
       +-----------+-----------+
                   |
                   v
                MLSecOps
                   |
        +----------+----------+
        |          |          |
     Security   Governance   Assurance
```

MLSecOps should therefore be viewed as **security-integrated MLOps**, not as a completely separate lifecycle.

---

### 4. MLSecOps vs DevSecOps

DevSecOps integrates security into conventional software development and operations.

MLSecOps extends the same philosophy to ML-specific lifecycle objects and processes.

| DevSecOps             | MLSecOps                            |
| --------------------- | ----------------------------------- |
| Source code           | Source code + ML artifacts          |
| Software dependencies | Software + ML dependencies          |
| Build pipeline        | Build + training pipelines          |
| Application testing   | Application + model testing         |
| Deployment            | Application + model deployment      |
| Runtime monitoring    | Runtime + model behavior monitoring |
| Software artifacts    | Software + model + dataset lineage  |

MLSecOps therefore complements DevSecOps.

### 6. Shift-Left Security in ML

MLSecOps applies security early in the lifecycle.

Security should begin before:

* Dataset acquisition
* Model selection
* Training
* Pipeline construction

Early security decisions can prevent expensive remediation later.

---

### 7. Shift-Right Security in ML

Security must also continue into production.

Production controls include:

* Runtime monitoring
* Model integrity verification
* Drift detection
* Anomaly detection
* Incident response
* Vulnerability management

MLSecOps therefore combines **shift-left** and **shift-right** security.

---

### 8. Continuous Security in ML

ML systems can change after deployment through:

* New data
* Retraining
* Model replacement
* Dependency updates
* Configuration changes
* Infrastructure changes

Consequently, a model that passed security validation yesterday may require reassessment today.

MLSecOps treats security as continuous rather than one-time.

### 12. Data as an MLSecOps Security Boundary

Data is one of the most important security boundaries in ML.

Threats include:

* Data poisoning
* Unauthorized modification
* Unauthorized access
* Data leakage
* Malicious datasets
* Provenance manipulation

Data should therefore be governed as a security-sensitive lifecycle asset.

---

### 13. Model as a Security Asset

Models should be treated as valuable enterprise assets.

A model may contain:

* Proprietary logic
* Learned organizational knowledge
* Sensitive information
* Business capabilities
* Intellectual property

Model confidentiality, integrity, availability, and provenance should therefore be protected.

---

### 14. Model Integrity

Model integrity means ensuring that the deployed model is the intended and approved model.

Integrity mechanisms may include:

* Hashes
* Digital signatures
* Version identifiers
* Registry verification
* Deployment verification

An unauthorized model modification should be detectable.

---

### 15. Model Confidentiality

Models may contain commercially sensitive or proprietary information.

Security controls may include:

* Access restrictions
* Encryption
* Secure storage
* Controlled model downloads
* Registry authorization

Model confidentiality should be based on business and data classification.

Critical ML services may depend on model availability.

Availability controls may include:

* Redundant serving infrastructure
* Model backups
* Disaster recovery
* Failover
* Known-good model versions
* Rollback mechanisms

Availability requirements should reflect business criticality.

* Non-public endpoints
* Least-privileged workloads
* Mandatory logging
* Disabled anonymous access

Users should explicitly request elevated capabilities rather than receiving them automatically.

### 30. Least Privilege for ML Workloads

For example:

```text id="m6q8xn"

   +--> Write Model Artifact
   |
   X--> Modify Registry Policy
   X--> Approve Model
   X--> Access Production Secrets
```

Least privilege reduces the impact of workload compromise.

### 49. Core MLSecOps Principles

A mature MLSecOps program should follow these principles:

1. Security begins before model training.
2. Data is a security boundary.
3. Models are security-sensitive artifacts.
4. Pipelines are privileged lifecycle components.
5. Trust must be established through provenance and integrity.
6. Security gates must be technically enforceable.
7. Development and production trust must remain separated.
8. Automated retraining must remain governed.
9. Security monitoring must continue after deployment.
10. Material ML changes require reassessment.
11. Security evidence must remain traceable.
12. ML security must integrate with enterprise security operations.
13. Compromise of one ML component must not automatically compromise the enterprise.

---

### 50. Core Principle of MLSecOps

**MLSecOps must integrate security into every stage of the machine learning lifecycle so that data, code, pipelines, models, artifacts, infrastructure, deployments, and runtime behavior remain continuously protected, verified, observable, and governed.**

The fundamental MLSecOps model is:

```text id="z6m8qx"
             ML Lifecycle
                  |
        +---------+---------+
        |                   |
        v                   v
      MLOps              Security
        |                   |
        +---------+---------+
                  |
                  v
              MLSecOps
                  |
      +-----------+-----------+
      |           |           |
      v           v           v
   Prevent      Detect      Respond
      |           |           |
      +-----------+-----------+
                  |
                  v
              Revalidate
                  |
                  +----> Continuous Assurance
```

**The core security principle is that ML systems must never inherit permanent trust from their previous lifecycle state: every material change to data, code, dependencies, pipelines, models, artifacts, infrastructure, configuration, or operating conditions must remain subject to appropriate security validation, authorization, monitoring, and continuous assurance.**

Controls should be preventive, detective, corrective, and compensating.

---

### 52. MLSecOps Identity Control

All users, services, workloads, and automation components should use identifiable identities.

Identity controls should support:

* Unique identities
* Strong authentication
* MFA for human users
* Workload identities
* Privileged identity management
* Credential lifecycle management
* Authentication logging

Shared accounts should be avoided because they weaken attribution.

---

### 53. MLSecOps Access Control

Access should be based on least privilege and explicit authorization.

Permissions should distinguish between:

* Dataset access
* Model access
* Pipeline access
* Registry administration
* Deployment
* Monitoring
* Security administration

Access should be regularly reviewed.

---

### 54. ML Developer Access Control

Developers should receive access appropriate to their responsibilities.

A developer may be authorized to:

* Create code
* Run experiments
* Access approved development data
* Create candidate models

This should not automatically provide authority to:

* Approve models
* Modify production
* Change security gates
* Access production secrets

---

### 55. Workload Identity Control

Automated workloads should use dedicated identities rather than developer credentials.

Examples include:

* Training jobs
* CI/CD pipelines
* Evaluation jobs
* Model registry services
* Deployment systems
* Retraining workflows

This enables precise attribution and limits privilege.

---

### 56. Dataset Authorization Control

Only authorized workloads and users should access ML datasets.

Authorization should consider:

* Dataset classification
* Purpose
* Identity
* Environment
* Operation
* Business need

A training job should not automatically have access to every enterprise dataset.

---

### 57. Dataset Integrity Control

Dataset integrity should be verified before trusted ML processing.

Controls may use:

* Cryptographic hashes
* Checksums
* Digital signatures
* Immutable storage
* Version identifiers

Unexpected changes should trigger validation failure or investigation.

---

### 58. Dataset Provenance Control

The origin and processing history of training data should be recorded.

Provenance should identify:

* Source
* Acquisition
* Processing
* Transformation
* Version
* Owner
* Validation status

Dataset provenance should remain linked to the model produced from it.

---

### 59. Dataset Poisoning Detection Control

MLSecOps should detect indicators of potential data poisoning.

Controls may analyze:

* Unexpected records
* Label anomalies
* Distribution changes
* Suspicious data sources
* Unusual data patterns
* Integrity failures

Potential poisoning should trigger investigation before affected data is used for trusted training.

---

### 60. Dataset Content Security Control

Datasets should be scanned for inappropriate or malicious content where applicable.

Scanning may identify:

* Executable content
* Embedded payloads
* Suspicious files
* Malicious indicators
* Unexpected data structures

The control should be appropriate to the dataset format and risk.

---

### 61. Dataset Versioning Control

Every material dataset version should have a unique identifier.

Versioning should enable the organization to determine:

> Which exact dataset contributed to this model?

Historical versions should remain available according to retention requirements.

---

### 62. Feature Pipeline Security Control

Feature engineering pipelines should be protected against unauthorized changes.

Controls should protect:

* Feature definitions
* Transformation logic
* Feature sources
* Feature values
* Pipeline configurations

Material changes should trigger appropriate testing.

---

### 63. Feature Access Control

Feature stores should enforce access restrictions.

Permissions should distinguish between:

* Creating features
* Modifying features
* Reading features
* Publishing features
* Using features for training
* Using features for inference

Feature access should follow data classification requirements.

---

### 64. Feature Integrity Control

Critical features should be protected against unauthorized modification.

Integrity controls may include:

* Versioning
* Hashing
* Change detection
* Access logging
* Approval controls

Unexpected changes should be investigated.

---

### 65. Source Code Security Control

ML source code should be managed through secured repositories.

Controls should include:

* Authentication
* Branch protection
* Code review
* Commit traceability
* Access control
* Secret scanning
* Security scanning

ML code should be subject to the same fundamental software security discipline as other enterprise applications.

---

### 66. ML Dependency Security Control

ML dependencies should be continuously assessed.

Controls should include:

* Dependency inventories
* Vulnerability scanning
* Version pinning
* Approved package sources
* Lock files
* Integrity verification

This should cover frameworks, libraries, plugins, and supporting packages.

### 67. ML Software Bill of Materials

---

### 68. Model Dependency Control

Models may depend on external libraries, tokenizers, runtimes, or other components.

A model should not be considered secure simply because its model file passed an integrity check.

---

Controls may include:

* Dedicated workloads
* Restricted network access
* Least privilege
* Secure images
* Vulnerability scanning
* Controlled storage
* Ephemeral execution

Training environments should not automatically inherit production privileges.

* Output location
* Compute resources
* Dependencies
* Network settings

* Configuration

* Encryption
* Integrity
* Version control
* Audit logging
* Retention

Repositories should be treated as critical security infrastructure.

---

### 86. Pipeline Security Control

ML pipelines should be protected as privileged systems.

Controls should cover:

* Pipeline source
* Workflow definitions
* Service connections
* Security gates
* Deployment targets
* Pipeline credentials

Pipeline compromise can result in downstream model compromise.

---

### 87. Pipeline Configuration Integrity Control

Pipeline configuration should be protected from unauthorized modification.

Security-sensitive settings include:

* Security gates
* Promotion rules
* Dataset sources
* Deployment environments
* Identity permissions

Changes should require appropriate review.

---

### 88. Pipeline Isolation Control

MLOps pipelines should operate within controlled execution environments.

Isolation should reduce:

* Credential theft
* Lateral movement
* Cross-team access
* Host compromise
* Unauthorized network access

High-risk pipeline stages may require separate workers.

---

### 89. Pipeline Security Gate Control

Security gates should enforce mandatory requirements.

A pipeline may verify:

* Code security
* Dependency status
* Dataset integrity
* Model testing
* Artifact signatures
* Approval status

A failed mandatory gate should stop promotion.

---

### 90. Fail-Closed Pipeline Control

### 91. Build Environment Security Control

ML build environments should be isolated and controlled.

Controls may include:

* Ephemeral workers
* Trusted base images
* Restricted privileges
* Network controls
* Dependency validation
* Build logging

Build systems should not retain unnecessary access after completion.

---

### 92. Reproducible Build Control

Where practical, model and ML artifacts should be generated through reproducible processes.

The build should capture:

* Source
* Dependencies
* Dataset
* Configuration
* Environment
* Build process

### 93. Container Security Control

Containers supporting ML workloads should undergo security validation.

Controls include:

* Image scanning
* Trusted base images
* Minimal packages
* Image signing
* Non-root execution
* Runtime restrictions

Container security should be integrated into MLSecOps gates.

### 94. Infrastructure-as-Code Security Control

MLOps infrastructure should be validated before deployment.

IaC security controls may include:

* Static analysis
* Policy validation
* Secret scanning
* Configuration validation
* Change review
* Drift detection

Infrastructure should not bypass application and ML security requirements.

### 95. Secrets Management Control

Secrets should be stored in approved enterprise secrets-management systems.

Secrets include:

* API keys

* Signing keys

### 100. Runtime Model Integrity Control

Production environments should detect unauthorized model changes.

Controls may compare:

* Deployment metadata

### 101. Runtime Access Control

Production model-serving systems should enforce authorization for inference access.

Controls may include:

* Authorization
* API keys or tokens
* Service identity
* Rate limits

### 102. Model API Security Control

Model-serving APIs should be protected against both conventional and ML-specific threats.

### 103. Model Abuse Detection Control

* Abnormal extraction patterns

### 104. Drift Detection Control

Production ML systems should monitor for:

* Data drift
* Feature drift
* Model drift
* Concept drift
* Performance degradation

Thresholds should be defined according to system risk.

Significant drift should trigger a defined lifecycle response.

Possible actions include:

* Alert
* Investigation
* Increased monitoring
* Model reassessment
* Retraining
* Deployment suspension

Drift should not be treated merely as a dashboard metric.

Automated retraining should operate within predefined security boundaries.

* Dataset

* Dependencies
* Configuration
* Training environment

### 117. Core Engineering Principle

**MLSecOps controls must establish and continuously verify trust across every ML lifecycle boundary, ensuring that data, code, pipelines, models, artifacts, infrastructure, deployments, and runtime processes cannot silently bypass security requirements.**

The control chain is:

```text id="z4m8qx"
Identify
   |
   v
Authenticate
   |
   v
Authorize
   |
   v
Validate
   |
   v
Test
   |
   v
Verify Integrity
   |
   v
Promote
   |
   v
Monitor
   |
   v
Detect
   |
   v
Contain / Revalidate
```

**No single control should be considered sufficient. MLSecOps requires defense in depth, independent enforcement, lifecycle traceability, continuous monitoring, and controlled recovery so that compromise of one ML component does not automatically establish trust or authority across the rest of the enterprise.**
