# 12.02 — AI Software Development Lifecycle

## Part 1 — Foundations

### 1. Definition of the AI Software Development Lifecycle

The AI Software Development Lifecycle (AI SDLC) is the structured process used to plan, design, develop, test, secure, deploy, operate, modify, and retire software applications that incorporate AI capabilities.

It extends the traditional Software Development Lifecycle by introducing security considerations for:

* AI models
* Training and inference data
* Prompts and instructions
* AI APIs
* Model configurations
* AI dependencies
* Model-serving infrastructure
* AI-specific testing
* Model and application interactions

The AI SDLC therefore governs both the software and the AI components that collectively deliver the system.

---

The purpose of the AI SDLC is to provide a repeatable lifecycle through which AI-enabled applications can be developed securely and predictably.

### 3. AI SDLC vs Traditional SDLC

Traditional SDLC primarily governs application code, infrastructure, databases, and interfaces.

AI SDLC must additionally account for:

* Model behavior
* Model provenance
* Dataset dependencies
* Training or fine-tuning
* Prompt logic
* AI provider dependencies
* Model evaluation
* AI-specific threats
* Model version changes

The difference can be represented as:

```text id="q8m3vx"
Traditional SDLC
      |
      +--> Code
      +--> Infrastructure
      +--> Database
      +--> Application
      |
      v
   Software

AI SDLC
      |
      +--> Code
      +--> Infrastructure
      +--> Data
      +--> Model
      +--> Prompts
      +--> AI Services
      |
      v
   AI System
```

---

### 4. AI SDLC as an Integrated Lifecycle

AI application development should not treat AI as an isolated component added at the end of conventional software development.

Instead:

```text id="m5q9xn"
Application Development
          |
          +------+
                 |
AI Development -+----> Integrated AI SDLC
                 |
Security --------+
```

Security, software engineering, data engineering, and AI engineering should operate as connected lifecycle disciplines.

### 5. AI SDLC Lifecycle Stages

A mature AI SDLC generally contains:

1. Initiation
2. Planning
3. Requirements
4. Architecture
5. Threat modeling
6. Development
7. Data integration
8. Model integration or development
9. Security testing
10. Build
11. Release
12. Deployment
13. Operations
14. Monitoring
15. Change management
16. Retirement

The exact implementation may vary by organization.

---

### 6. Initiation Stage

The initiation stage determines whether an AI-enabled solution should be developed.

Initial questions include:

* What business problem is being addressed?
* Why is AI required?
* What data will be involved?
* Who will use the system?
* What decisions will it influence?
* What external services will it require?
* What security risks could result?

This stage establishes the initial security and risk context.

---

Every AI application should have a clearly defined business purpose.

Purpose definition should establish:

* Intended users
* Intended functionality
* Intended decisions
* Intended outputs
* Permitted use
* Prohibited use

A clearly defined purpose creates a boundary against uncontrolled functionality expansion.

Stakeholders may include:

* Security teams

### 11. Security Requirements Discovery

Security requirements should be identified before significant development begins.

Requirements may address:

* Authentication
* Authorization
* Data protection
* Model protection
* API security
* Secrets
* Logging
* Monitoring
* Vulnerability management
* Incident response

Requirements should be specific enough to test.

---

### 12. Functional and Security Requirements

AI SDLC requirements should distinguish functional requirements from security requirements.

For example:

| Requirement Type | Example                                                  |
| ---------------- | -------------------------------------------------------- |
| Functional       | System summarizes approved documents                     |
| Security         | Only authorized users can submit documents               |
| Functional       | Model generates recommendations                          |
| Security         | Recommendations cannot trigger unauthorized transactions |

Security should be treated as a system requirement rather than a post-development activity.

---

### 13. Non-Functional AI Security Requirements

AI systems require security-related non-functional requirements.

Examples include:

* Confidentiality
* Integrity
* Availability
* Traceability
* Resilience
* Auditability
* Explainability where applicable
* Robustness

These characteristics influence architectural decisions.

---

### 14. Architecture and Design Stage

The design stage transforms requirements into a technical architecture.

Design should define:

* Trust boundaries
* Data flows
* AI components
* Model interfaces
* Authentication
* Authorization
* Network boundaries
* Security controls

Security architecture should be established before implementation.

### 16. Trust Boundary Identification

AI systems should identify trust boundaries between components.

Potential boundaries include:

* User to application
* Application to model
* Application to external AI provider
* Application to database
* Development to production
* Internal to external service

Each boundary should have appropriate security controls.

---

### 17. AI Threat Modeling in the SDLC

Threat modeling should occur during architecture and design rather than after implementation.

Threat modeling should consider:

* Malicious input
* Prompt manipulation
* Data poisoning
* Model compromise
* Dependency attacks
* Credential theft
* API abuse
* Data leakage
* Unauthorized model access

The objective is to identify threats before they become implementation weaknesses.

---

### 18. Secure Architecture Decisions

Architecture decisions should explicitly consider security.

Examples include:

* Whether models run internally or externally
* Whether sensitive data can reach an external provider
* Whether inference requires privileged data
* Whether model outputs can trigger actions
* Whether AI services require network isolation

Security implications should be documented with architectural decisions.

---

### 19. Development Stage

During development, engineers implement application functionality and AI integrations according to approved requirements and architecture.

Security activities should remain active during implementation.

These include:

* Secure coding
* Dependency management
* Secret protection
* Code review
* Security scanning
* Access control

---

### 20. Secure AI Coding

AI application code should follow secure software engineering practices.

Developers should protect against:

* Injection
* Improper authentication
* Authorization failures
* Unsafe deserialization
* Insecure file handling
* Hardcoded credentials
* Improper error handling

AI-specific functionality does not eliminate traditional application security requirements.

---

### 21. AI Integration Security

Applications integrating external AI services should establish security controls around the integration.

The integration should define:

* Authentication
* Authorization
* Endpoint
* Data sent
* Data received
* Timeout
* Rate limits
* Logging
* Failure handling

The AI provider should not automatically receive unrestricted application data.

---

### 22. Prompt and Instruction Development

Prompts and system instructions can become security-relevant software components.

They may define:

* Model behavior
* Data access expectations
* Output format
* Security restrictions
* Business rules

Material prompt changes should therefore be treated as controlled lifecycle changes.

---

### 23. AI Dependency Management

AI applications often depend on:

* ML frameworks
* SDKs
* AI APIs
* Vector databases
* Retrieval libraries
* Serialization libraries
* Security libraries

Dependencies should be inventoried, assessed, updated, and monitored.

---

### 24. Data Integration Stage

AI applications may integrate with structured and unstructured data sources.

The lifecycle should establish:

* Data source
* Data owner
* Classification
* Access method
* Purpose
* Retention
* Security requirements

Data should enter the application through controlled interfaces.

---

### 25. Data Minimization

The AI SDLC should minimize unnecessary data exposure.

Only data required for the defined functionality should be:

* Collected
* Processed
* Stored
* Sent to models
* Sent to external providers

Minimization reduces both privacy and security exposure.

---

### 26. Model Integration Stage

Applications may use:

* Internally developed models
* Fine-tuned models
* Open-source models
* Commercial APIs
* Managed cloud models

The lifecycle should define how the selected model is evaluated and integrated.

---

### 27. Model Selection Security

Model selection should consider security characteristics in addition to functional performance.

Evaluation factors may include:

* Provenance
* Provider trust
* Known vulnerabilities
* Data handling
* Security capabilities
* Model behavior
* Intended use

The most accurate model is not necessarily the most appropriate model from a security perspective.

---

### 28. Model Configuration Management

Model configuration should be treated as part of the application's security-sensitive configuration.

Configuration may include:

* Model identifier
* Temperature
* Token limits
* System instructions
* Tool permissions
* Retrieval settings
* Safety parameters

Changes should be versioned and controlled.

---

### 29. Integration Testing

AI systems should undergo integration testing to verify interactions between application components and AI services.

Testing should examine:

* Authentication
* Data flow
* Model invocation
* Error handling
* Output processing
* External APIs
* Authorization

The objective is to ensure security controls remain effective across component boundaries.

---

### 30. Security Testing Stage

Security testing should be integrated into the development lifecycle.

It may include:

* SAST
* SCA
* Secret scanning
* API security testing
* Container scanning
* Infrastructure scanning
* AI-specific security testing

Testing depth should correspond to system risk.

---

### 31. AI-Specific Security Testing

AI applications require additional testing beyond traditional application security.

Testing may evaluate:

* Prompt injection
* Adversarial input
* Data leakage
* Model misuse
* Output manipulation
* Model extraction
* Unsafe tool interaction

AI security testing should focus on realistic attack paths.

---

### 32. Security Test Evidence

Security testing should produce evidence that can be associated with the application version.

Evidence may include:

* Test execution
* Findings
* Severity
* Remediation
* Retest results
* Approval

Testing without retained evidence weakens lifecycle assurance.

The build system should maintain:

### 38. Deployment Stage

Deployment moves an approved AI application into its target environment.

Deployment should verify:

* Artifact identity
* Environment
* Configuration
* Credentials
* Security controls
* Monitoring

Production deployment should use controlled automation wherever practical.

---

### 39. Production Environment Security

Production AI environments should have stronger security boundaries than development environments.

Production should provide:

* Restricted access
* Strong identity
* Network controls
* Secrets protection
* Monitoring
* Audit logging
* Controlled changes

Production should not be treated as an extension of a developer workstation.

---

### 40. Operations Stage

After deployment, the AI application enters operational lifecycle management.

Operational security includes:

* Monitoring
* Vulnerability management
* Incident response
* Access reviews
* Configuration management
* Model management
* Performance monitoring

Security remains part of the SDLC after release.

---

### 41. AI Security Monitoring

Production monitoring should identify security-relevant changes and behavior.

Monitoring may include:

* Unauthorized access
* Abnormal API usage
* Unexpected model changes
* Configuration changes
* Data access anomalies
* Security-control failures

Monitoring provides visibility into the operational security state.

---

### 42. Change Management

AI applications should use controlled change management.

Changes may involve:

* Code
* Model
* Prompt
* Dataset
* Dependencies
* Infrastructure
* Configuration
* AI provider

Each material change should be evaluated for security impact.

---

### 43. AI Model Changes

A model change may alter application security even when application code remains unchanged.

Examples include:

* Model replacement
* Fine-tuning
* Retraining
* Provider change
* Version upgrade

Model changes should therefore participate in the application lifecycle.

---

### 44. AI Application Reassessment

The system should be reassessed when material assumptions change.

Reassessment triggers may include:

* New data source
* New model
* New user population
* New external API
* New business purpose
* New deployment environment
* Significant vulnerability

Security authorization should remain aligned with the current system.

---

### 45. Incident Response Integration

AI application incidents should integrate with enterprise incident response.

Potential incidents include:

* Model compromise
* Credential theft
* Data leakage
* Prompt-based exploitation
* Malicious dependency
* Unauthorized deployment
* Pipeline compromise

Incident response should support both containment and lifecycle remediation.

---

### 49. AI SDLC Security Principles

The AI Software Development Lifecycle should follow these principles:

1. Security begins before development.
2. AI security is integrated with software security.
3. Models and data are lifecycle components.
4. Security requirements are explicit and testable.
5. Threat modeling occurs before deployment.
6. Development and production remain separated.
7. Security testing is continuous.
8. Releases are evidence-based.
9. Material AI changes trigger reassessment.
10. Every production artifact remains traceable.
11. Security monitoring continues after deployment.
12. Retirement removes unnecessary trust and access.

---

### 50. Core Principle of the AI Software Development Lifecycle

**An AI application must be governed as a continuously evolving software system in which code, data, models, configurations, dependencies, infrastructure, and AI services are all treated as lifecycle components subject to security requirements, validation, controlled change, traceability, and continuous assurance.**

### 52. Project Security Intake Control

Every AI software project should pass through a security intake process before significant development begins.

The intake should capture:

* Business purpose
* AI functionality
* Data categories
* Model type
* External providers
* Deployment environment
* Expected users
* Business criticality
* Initial risk classification

The output should establish the security pathway for the project.

---

### 53. AI Project Security Classification

The project should be classified according to its security impact.

Classification factors may include:

* Sensitive data
* External exposure
* Business criticality
* Model impact
* User population
* Autonomous functionality
* Regulatory requirements

The classification should determine which security controls and reviews become mandatory.

---

### 54. AI SDLC Security Checklist

Each lifecycle stage should have defined security exit criteria.

For example:

| Stage        | Security Exit Criteria            |
| ------------ | --------------------------------- |
| Requirements | Security requirements documented  |
| Design       | Architecture and threats reviewed |
| Development  | Secure coding controls passed     |
| Testing      | Required security tests completed |
| Build        | Artifact integrity verified       |
| Release      | Security approval obtained        |
| Deployment   | Environment controls validated    |
| Operations   | Monitoring active                 |

A project should not progress merely because functional work is complete.

---

### 55. Security Requirements Validation

Security requirements should be validated for completeness before development.

Validation should determine whether requirements cover:

* Identity
* Authorization
* Data protection
* Model security
* Application security
* Dependency security
* Secrets
* Logging
* Monitoring
* Incident response

Missing requirements should be addressed before implementation becomes difficult to change.

---

### 56. Architecture Security Review

AI application architecture should undergo security review before production implementation.

The review should examine:

* Trust boundaries
* Data flows
* Model interfaces
* External integrations
* Authentication
* Authorization
* Network architecture
* Secrets
* Failure handling

High-risk architectures should receive enhanced review.

Threat modeling should be a mandatory lifecycle control for AI systems where risk warrants it.

The process should identify:

* Assets
* Actors
* Trust boundaries
* Attack paths
* Threats
* Vulnerabilities
* Security controls
* Residual risks

Threat models should be updated when material architecture changes occur.

---

### 59. Secure Coding Standards

AI application development should use approved secure coding standards.

Standards should address:

* Input validation
* Output handling
* Authentication
* Authorization
* Error handling
* Serialization
* File handling
* API security
* Secrets
* Logging

AI functionality should not be exempt from established application security practices.

---

### 60. Code Repository Controls

Source repositories should enforce:

* Strong authentication
* Role-based access
* Protected branches
* Mandatory reviews
* Audit logging
* Secret scanning
* Security scanning

Production-bound code should originate from controlled repositories.

---

### 61. Code Review Controls

Security-sensitive changes should receive appropriate code review.

Reviewers should consider:

* New data access
* New AI integrations
* New APIs
* Authentication changes
* Authorization changes
* Model-loading logic
* Security-control changes
* External communication

High-risk changes may require security-team participation.

---

### 62. Static Code Analysis

Static analysis should run automatically against AI application code.

SAST should identify weaknesses such as:

* Injection
* Unsafe deserialization
* Authentication flaws
* Authorization flaws
* Insecure cryptography
* Hardcoded secrets
* Unsafe system calls

Critical findings should be integrated into release gates.

---

### 63. Secret Scanning

Secret scanning should be applied throughout the software lifecycle.

Scanning should cover:

* Source code
* Git history
* Configuration
* Notebooks
* CI/CD definitions
* Container build files

Detected credentials should be treated as potentially compromised and rotated when appropriate.

---

### 64. Dependency Security Control

AI applications should continuously assess dependencies.

The control should identify:

* Known vulnerabilities
* Unsupported versions
* Malicious packages
* Transitive dependencies
* Dependency changes

Risk thresholds should determine whether builds continue or stop.

---

### 65. Dependency Locking Control

Critical dependencies should be pinned or locked to known versions.

```text id="x4m8qz"
Application
     |
     v
Dependency Lock
     |
     v
Known Versions
     |
     v
Reproducible Build
```

Unexpected dependency resolution should not silently alter production artifacts.

---

### 66. AI API Security Control

External AI APIs should be accessed through controlled integrations.

Controls should include:

* Strong authentication
* TLS
* Credential protection
* Endpoint restrictions
* Request validation
* Response validation
* Rate limiting
* Logging

External AI providers should receive only authorized information.

---

### 67. Data Access Control

AI applications should access data using least privilege.

Permissions should distinguish:

* Read
* Write
* Modify
* Delete
* Export
* Administrative access

The application should not receive broad database privileges when narrower permissions are sufficient.

---

### 68. Data Flow Validation

Data flows should be validated against the approved architecture.

Controls should detect unauthorized paths such as:

```text id="p9m4xn"

     |
     v

```

Data should not cross trust boundaries without authorization.

---

### 69. Data Classification Enforcement

Data classification should influence how data is handled by the AI application.

For example:

```text id="q5m8xn"

  |

  |
Restricted
```

Higher-sensitivity data should receive stronger access, encryption, monitoring, and transfer controls.

---

### 70. Data Minimization Control

Applications should minimize the information sent to AI models and external services.

Controls may:

* Remove unnecessary fields
* Mask sensitive values
* Filter records
* Restrict context
* Limit retention

Data minimization reduces the potential impact of AI-related compromise.

---

### 71. Prompt Security Control

Prompts and system instructions should be protected from unauthorized modification.

Controls should include:

* Version control
* Access control
* Review
* Integrity validation
* Change tracking

Security-sensitive instructions should not be treated as disposable text.

---

### 72. Prompt Injection Testing

AI applications should test resistance to malicious instructions contained within untrusted inputs.

Testing should evaluate whether untrusted content can:

* Override system instructions
* Exfiltrate information
* Manipulate application behavior
* Trigger unauthorized actions
* Circumvent security controls

Results should feed into release decisions.

---

### 73. Output Validation Control

AI-generated outputs should be validated before being consumed by downstream systems.

Validation may include:

* Schema validation
* Type validation
* Content validation
* Business-rule validation
* Security-policy validation

Model output should not automatically become trusted application input.

---

### 74. AI Tool and API Invocation Control

If the AI application can invoke tools or APIs, those invocations should pass through controlled interfaces.

    |

    |
    v

    |
    v

    |

---

### 75. Model Selection Control

Production applications should use approved models.

Model selection should consider:

* Provenance
* Security assessment
* Intended purpose
* Version
* Provider
* Known vulnerabilities
* Security testing

Unapproved model changes should be blocked or subjected to formal review.

---

### 76. Model Version Control

Every production model should have a unique and traceable version.

The version should connect to:

* Application release
* Model artifact
* Configuration
* Evaluation
* Approval
* Deployment

This allows security teams to identify exactly which model is operating.

---

### 77. Model Integrity Control

Model artifacts should be verified before use.

Verification may include:

* Cryptographic hash
* Digital signature
* Registry verification
* Provenance validation
* Version validation

A modified artifact should not automatically be considered equivalent to the approved model.

---

### 78. Model Evaluation Control

Models should pass defined evaluation requirements before production use.

Evaluation should consider:

* Functional performance
* Security behavior
* Robustness
* Unsafe outputs
* Data leakage
* Adversarial behavior

Evaluation criteria should reflect the model's intended risk.

---

### 79. Integration Security Testing

AI application integrations should be security tested before release.

Testing should include:

* Model API
* Data services
* Authentication
* Authorization
* External providers
* Storage
* Application interfaces

Security weaknesses often emerge at component boundaries rather than inside individual components.

---

### 80. API Security Testing

AI application APIs should be tested for:

* Authentication bypass
* Authorization flaws
* Injection
* Excessive data exposure
* Rate-limit bypass
* Malformed requests
* Improper error handling

AI APIs should be treated as conventional application attack surfaces plus AI-specific risks.

---

### 81. Container Security Control

Production AI containers should be validated before deployment.

Validation should include:

* Base image
* OS packages
* Application dependencies
* Embedded secrets
* Privileges
* Runtime configuration

Only approved container images should reach production.

---

### 82. Infrastructure Security Control

AI infrastructure should be assessed before deployment.

Controls should validate:

* Network segmentation
* IAM
* Encryption
* Storage
* Logging
* Public exposure
* Security configuration

Infrastructure should meet the defined AI security baseline.
