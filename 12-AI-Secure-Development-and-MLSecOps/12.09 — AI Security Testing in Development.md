# 12.09 — AI Security Testing in Development

## Part 1 — Foundations

### 1. Definition of AI Security Testing in Development

AI Security Testing in Development is the systematic process of identifying and validating security weaknesses in AI applications, models, datasets, dependencies, infrastructure, pipelines, and supporting components before they reach production.

It extends conventional software security testing by addressing AI-specific attack surfaces such as:

* Prompt injection
* Model manipulation
* Dataset poisoning
* Unsafe model loading
* AI supply-chain compromise
* Retrieval abuse
* Tool abuse
* Output manipulation
* Model extraction
* AI-specific authorization failures

The objective is to identify security weaknesses while they are still inexpensive and practical to remediate.

---

### 2. Purpose of AI Security Testing in Development

The primary purpose is to establish evidence that security requirements and threat mitigations actually work before deployment.

AI security testing should answer questions such as:

* Can an attacker bypass authentication?
* Can untrusted input manipulate trusted instructions?
* Can unauthorized data be retrieved?
* Can the model invoke a restricted tool?
* Can a malicious artifact enter the build?
* Can a compromised dependency reach production?
* Can sensitive information be extracted?
* Can security controls be bypassed through model behavior?

Testing transforms security assumptions into measurable evidence.

---

### 3. AI Security Testing vs Functional Testing

Functional testing determines whether the AI system performs its intended business functions.

Security testing determines whether those functions can be abused or compromised.

For example:

| Testing Type | Question                                                |
| ------------ | ------------------------------------------------------- |
| Functional   | Does the chatbot answer correctly?                      |
| Security     | Can a user manipulate it into exposing restricted data? |
| Functional   | Can the model call the payment API?                     |
| Security     | Can an unauthorized user cause a payment action?        |
| Functional   | Can the RAG system retrieve documents?                  |
| Security     | Can it retrieve documents belonging to another tenant?  |

An AI system can be functionally correct while remaining fundamentally insecure.

### 5. Shift-Left AI Security Testing

Shift-left testing moves security validation toward the earliest practical development stages.

Developers should be able to detect weaknesses during:

* Coding
* Prompt development
* Dependency selection
* Dataset preparation
* Model integration
* Infrastructure development

Early detection reduces remediation cost and prevents vulnerable designs from becoming embedded in later stages.

---

### 6. Continuous AI Security Testing

AI systems require continuous security validation because their behavior and dependencies can change.

Changes may occur in:

* Models
* Prompts
* Datasets
* Dependencies
* APIs
* Tools
* Configurations
* Infrastructure

A previously secure test result should therefore not be treated as permanent evidence of security.

### 8. AI Security Test Objectives

Each security test should have a clearly defined objective.

Objectives may include:

* Prevent unauthorized access
* Protect sensitive data
* Preserve model integrity
* Prevent privilege escalation
* Prevent tool abuse
* Validate tenant isolation
* Detect malicious input
* Protect supply-chain integrity
* Verify security controls

The objective should be linked to a security requirement or threat wherever possible.

### 10. Risk-Based Testing

Testing depth should correspond to AI system risk.

A low-risk internal application may require standard security testing.

A high-risk AI system may require:

* Extensive adversarial testing
* Independent testing
* Continuous testing
* Stronger release gates
* Negative testing
* Abuse simulation
* Runtime validation

Risk should determine the intensity of testing rather than applying identical testing requirements to every system.

---

### 11. Security Test Categories

AI security testing should combine multiple categories.

| ---------------------- | ------------------------------ |

| Secret Scanning        | Credential exposure            |

---

### 12. Static Application Security Testing for AI

SAST should be applied to AI application source code.

Testing should identify issues such as:

* Injection vulnerabilities
* Unsafe command execution
* Insecure file handling
* Weak authorization
* Hardcoded credentials
* Unsafe API usage
* Dangerous deserialization

AI-specific code paths should receive the same security scrutiny as conventional application code.

---

### 13. Software Composition Analysis

AI applications frequently depend on large software ecosystems.

SCA should identify:

* Known vulnerabilities
* Outdated dependencies
* Transitive dependencies
* Unapproved packages
* License concerns
* Dependency conflicts

Dependency findings should be evaluated according to actual exploitability and system exposure.

---

### 14. Secret Detection Testing

Security testing should identify credentials accidentally introduced into development artifacts.

Potential locations include:

* Source code
* Configuration files
* Notebooks
* Prompts
* Test data
* Scripts
* CI/CD configuration
* Container layers

Secrets discovered during development should be treated as potentially compromised and rotated where appropriate.

---

### 15. API Security Testing

AI APIs should be tested for:

* Authentication bypass
* Authorization bypass
* Injection
* Excessive data exposure
* Rate-limit weaknesses
* Improper error handling
* Object-level authorization failures

API testing should evaluate both conventional API security and AI-specific interaction patterns.

---

### 16. Authentication Testing

Authentication mechanisms should be tested to verify that unauthorized identities cannot access protected AI capabilities.

Testing should include:

* Invalid credentials
* Expired credentials
* Revoked credentials
* Token manipulation
* Session abuse
* Authentication bypass

Workload and service identities should also be tested where they represent significant attack paths.

---

### 17. Authorization Testing

Authorization testing should verify that authenticated users and workloads can perform only permitted actions.

Testing should cover:

* Horizontal privilege escalation
* Vertical privilege escalation
* Object-level authorization
* Function-level authorization
* Tool authorization
* Data authorization

### 18. Least-Privilege Testing

Security tests should verify that AI applications and workloads do not possess unnecessary privileges.

Testing should attempt to determine whether a compromised component can:

* Access unrelated data
* Invoke unnecessary APIs
* Execute privileged operations
* Access administrative functions
* Modify security configurations

The purpose is to validate the actual privilege boundary rather than merely confirm that a least-privilege policy exists.

---

### 19. Prompt Injection Testing

Prompt injection testing evaluates whether untrusted input can manipulate the AI system into violating intended security behavior.

Tests may attempt to:

* Override system instructions
* Reveal protected information
* Alter task objectives
* Bypass application restrictions
* Trigger unauthorized tools

Testing should include both direct and indirect injection scenarios.

---

### 20. Indirect Prompt Injection Testing

Indirect prompt injection occurs when malicious instructions originate from content the AI retrieves or processes rather than directly from the user.

Potential sources include:

* Web pages
* Documents
* Emails
* Knowledge bases
* Uploaded files
* Database records

Testing should determine whether untrusted content can influence trusted system behavior.

---

### 21. Instruction Hierarchy Testing

Security testing should verify that trusted instructions maintain appropriate precedence over untrusted content.

Tests should evaluate interactions between:

* System instructions
* Developer instructions
* Application policies
* User input
* Retrieved content
* Tool output

The objective is to determine whether untrusted content can improperly obtain higher authority.

---

### 22. Context Isolation Testing

AI systems should be tested for unintended context leakage.

Testing should verify separation between:

* Users
* Sessions
* Tenants
* Applications
* Conversations
* Retrieved data
* Persistent memory

A successful request by one identity should not provide access to another identity's context.

---

### 23. Output Validation Testing

Model outputs should be tested before they are trusted by downstream systems.

Testing should determine whether malicious or malformed model output can cause:

* Command execution
* SQL injection
* HTML injection
* Workflow manipulation
* Unauthorized API requests
* Security-policy bypass

The fundamental assumption should be:

**Model output is untrusted until validated.**

---

### 24. Structured Output Security Testing

When AI applications use structured outputs such as JSON or function-call arguments, testing should validate both syntax and security semantics.

Tests should include:

* Invalid types
* Unexpected fields
* Missing fields
* Boundary values
* Unauthorized values
* Malicious parameters

Schema validation alone does not guarantee that the requested action is authorized.

---

### 25. Tool Invocation Security Testing

AI applications capable of tool use should undergo dedicated security testing.

Testing should determine whether the model can cause:

* Unauthorized tool invocation
* Privileged actions
* Parameter manipulation
* Excessive resource use
* Destructive operations

The authorization layer should be tested independently from model behavior.

---

### 26. Tool Parameter Testing

Tool parameters should be tested against malicious and unexpected values.

Testing should include:

* Boundary values
* Invalid identifiers
* Unauthorized resources
* Unexpected commands
* Excessive quantities
* Cross-tenant references

The goal is to determine whether tool validation remains effective even when the model generates malicious parameters.

---

### 27. High-Risk Action Testing

High-impact actions require stronger negative testing.

Examples include:

* Financial transactions
* Data deletion
* Privileged changes
* Production deployments
* Account modification
* External communication

Testing should verify that required approvals and authorization controls cannot be bypassed through AI-generated requests.

---

Retrieval-Augmented Generation systems should be tested for security weaknesses in the complete retrieval chain.

Testing should examine:

* Retrieval authorization
* Document access
* Tenant isolation

Vector stores should be tested for:

* Unauthorized retrieval
* Cross-tenant access
* Metadata leakage
* Index manipulation
* Embedding exposure
* Access-control bypass

### 30. AI Memory Security Testing

Persistent AI memory should be tested for:

* Unauthorized retrieval
* Memory poisoning
* Cross-user leakage
* Cross-tenant leakage
* Improper deletion
* Excessive retention

Testing should validate both read and write security.

---

### 31. Dataset Security Testing

Datasets should undergo security testing before being used for training or evaluation.

Testing may examine:

* Integrity
* Provenance
* Schema
* Malicious content
* Sensitive information
* Unexpected modifications
* Poisoning indicators

Dataset testing should be proportional to the model's risk and the dataset's importance.

---

### 32. Dataset Poisoning Testing

Security teams should test whether malicious or manipulated training data could influence model behavior.

Testing may evaluate:

* Malicious labels
* Trigger patterns
* Anomalous records
* Distribution manipulation
* Targeted data injection

High-impact models should receive more sophisticated poisoning analysis.

---

### 33. Model Integrity Testing

Model artifacts should be tested to verify that they correspond to approved versions.

Testing should validate:

* Hash
* Signature
* Version
* Provenance
* Registry status

Integrity failures should result in rejection or escalation according to risk.

---

### 34. Model Loading Security Testing

AI systems should be tested for unsafe model loading behavior.

Testing should examine whether untrusted model files can:

* Execute unintended code
* Exploit deserialization
* Load malicious components
* Access unauthorized resources

Model loading should occur within appropriately isolated environments.

---

### 35. Model Extraction Testing

Where model confidentiality is important, systems should be tested against model extraction attempts.

Testing may examine:

* Excessive querying
* Systematic probing
* API abuse
* Repeated inference requests
* Reconstruction patterns

Controls should balance security with legitimate application functionality.

---

### 36. Data Extraction Testing

AI systems should be tested for unintended disclosure of sensitive training or contextual information.

Testing may target:

* Memorized information
* System instructions
* Retrieved documents
* User data
* Credentials
* Sensitive prompts

Testing should focus on realistic information-exposure scenarios.

---

### 37. AI Abuse Testing

Security testing should include misuse scenarios beyond traditional vulnerability exploitation.

Examples include:

* Automated abuse
* Resource exhaustion
* Malicious content generation
* Repeated probing
* Tool misuse
* Policy circumvention

Abuse testing helps determine whether the AI system can be exploited without a conventional software vulnerability.

---

### 38. Model Behavior Security Testing

Security testing should examine whether model behavior creates security consequences.

Examples include:

* Incorrect authorization recommendations
* Unsafe instructions
* Security-control circumvention
* Manipulative responses
* Unsafe tool recommendations

Model behavior should be evaluated in relation to the application's actual authority boundaries.

---

### 39. Security Testing of External AI Providers

External AI services should be evaluated as security dependencies.

Testing and assessment should consider:

* API authentication
* Data transmission
* Provider isolation
* Response handling
* Failure behavior
* Data retention assumptions
* Security-control boundaries

The organization should not assume that a third-party model provider satisfies enterprise security requirements automatically.

---

### 40. AI Dependency Security Testing

Dependencies should be tested continuously for newly discovered vulnerabilities.

Testing should include:

* Direct dependencies
* Transitive dependencies
* AI frameworks
* Inference libraries
* Plugins
* Model-serving components

Critical dependency findings should influence release decisions.

---

### 41. Container Security Testing

Containerized AI applications should undergo:

* Image vulnerability scanning
* Configuration testing
* Privilege testing
* Runtime isolation testing
* Network exposure testing
* Secret detection

Testing should occur before deployment to trusted environments.

---

### 42. Infrastructure Security Testing

Infrastructure supporting AI workloads should be security-tested.

Testing may evaluate:

* IAM configuration
* Network segmentation
* Storage permissions
* Public exposure
* Encryption
* Administrative access
* Compute isolation

AI security testing should include the infrastructure on which AI capabilities depend.

---

### 43. Configuration Security Testing

AI configurations should be tested against approved security baselines.

Testing should identify:

* Excessive permissions
* Disabled controls
* Unsafe defaults
* Unapproved providers
* Unrestricted tools
* Insecure network settings

Configuration testing should occur automatically where practical.

---

### 45. Negative Security Testing

AI security testing should deliberately attempt actions that the system is supposed to reject.

Examples include:

* Unauthorized data retrieval
* Unauthorized tool use
* Privilege escalation
* Prompt injection
* Malicious file uploads
* Invalid API requests

Security is demonstrated not only by successful legitimate behavior, but by reliable rejection of prohibited behavior.

---

### 46. Security Test Automation

Security testing should be automated wherever practical.

Automation can provide:

* Faster feedback
* Consistent execution
* Repeatability
* Continuous validation
* Automated security gates
* Evidence generation

Human review remains important for complex, high-risk, or context-dependent security scenarios.

---

### 47. Security Test Evidence

Every material security test should produce evidence sufficient to demonstrate what was tested and what happened.

Evidence should include:

* Test identity
* System/version
* Test scenario
* Expected result
* Actual result
* Timestamp
* Test environment
* Security status

Evidence should be protected from unauthorized modification.

### 49. AI Security Testing Principles

Effective AI security testing should follow these principles:

1. **Test the complete AI system, not only the model.**
2. **Test both expected and prohibited behavior.**
3. **Use threat modeling to determine test priorities.**
4. **Treat model outputs as untrusted.**
5. **Test authorization independently from AI reasoning.**
6. **Test datasets, models, applications, dependencies, and infrastructure.**
7. **Automate repeatable security validation.**
8. **Preserve evidence for material tests.**
9. **Convert important findings into regression tests.**
10. **Repeat testing when material changes occur.**

---

### 50. Core Principle of AI Security Testing in Development

**AI security testing must provide continuous, risk-based, threat-driven evidence that the AI system, its models, data, dependencies, infrastructure, interfaces, and security controls resist realistic attack and misuse scenarios before and throughout the lifecycle.**

### 52. AI Security Test Planning Control

The plan should define:

* Testing scope
* Security objectives
* Test categories
* Required tools
* Test frequency
* Test owners
* Acceptance criteria
* Evidence requirements
* Escalation requirements

Testing plans should be updated when the AI system materially changes.

The testing scope should cover the complete security-relevant architecture.

It should consider:

* Application
* Model
* Dataset
* Prompt
* Retrieval
* Memory
* Tools
* APIs
* Dependencies
* Containers
* Infrastructure
* CI/CD
* External providers

Testing only the model should not be considered sufficient for an integrated AI system.

Categories may include:

* Application security testing
* API security testing
* Model security testing

The environment should provide:

* Appropriate isolation
* Controlled data
* Test identities
* Test credentials

* Safe test targets

Production testing should require explicit authorization and safeguards.

* Test credentials
* Customer data
* Synthetic data

### 62. Authorization Security Testing Control

* Function-level authorization
* Object-level authorization
* Data authorization
* Tool authorization
* Model authorization

Authorization should be evaluated independently from the AI model's response.

---

### 63. Least-Privilege Testing Control

* Access unrelated data

* Malicious user input

* Load unauthorized components

* Malicious payloads

### 117. Core Engineering Principle

**AI security testing must be an enforceable lifecycle control in which threat-driven and risk-based tests continuously validate security requirements across applications, models, datasets, prompts, tools, APIs, dependencies, pipelines, infrastructure, and runtime environments, with failures producing appropriate security actions and evidence.**

```text id="astc117e"

   v

   |

   |

   v        v

   |        |
   v        v
```

**The essential control principle is that security testing must have consequences.** A test that produces a result but cannot influence remediation, release, deployment, or risk decisions provides limited security assurance. For material AI risks, testing must be connected to enforceable gates, accountable remediation, regression protection, and continuous validation.
