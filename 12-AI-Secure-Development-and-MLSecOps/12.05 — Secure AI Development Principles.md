# 12.05 — Secure AI Development Principles

## Part 1 — Foundations

### 1. Definition of Secure AI Development Principles

Secure AI Development Principles are the foundational engineering and governance principles used to ensure that artificial intelligence systems are designed, developed, tested, deployed, and maintained with security embedded throughout their lifecycle.

They establish the decision-making foundation for secure AI engineering.

The principles apply across:

* AI applications
* Machine learning systems
* Foundation models
* Generative AI
* AI agents
* AI APIs
* AI infrastructure
* AI data pipelines
* AI development platforms

---

### 2. Purpose of Secure AI Development Principles

The purpose is to ensure that security is treated as an inherent property of AI systems rather than a final validation activity.

The principles should help organizations:

* Reduce AI attack surface
* Prevent security defects
* Protect AI data
* Protect models and artifacts
* Control AI dependencies
* Prevent unauthorized changes
* Establish trustworthy AI deployment
* Maintain continuous security assurance

---

### 3. Security by Design

Security by design means security requirements are considered when the AI system is being designed rather than after implementation.

```text id="m8q4xn"
Business Requirement
        |
        v
Security Requirement
        |
        v
Secure Architecture
        |
        v
Secure Implementation
        |
        v
Security Testing
        |
        v
Deployment
```

Security architecture should influence fundamental design decisions before significant development investment occurs.

---

### 4. Secure by Default

AI systems should use secure configurations as their default state.

Examples include:

* Restricted access
* Disabled unnecessary interfaces
* Private data stores
* Protected model registries
* Encrypted communications
* Mandatory logging
* Least-privileged identities

Users should explicitly request additional privileges rather than receiving them automatically.

---

### 5. Shift-Left AI Security

AI security should begin as early as possible in the lifecycle.

Security activities should begin during:

* Requirements
* Architecture
* Data selection
* Model selection
* Threat modeling

Early security intervention generally reduces the cost and complexity of remediation.

---

### 6. Continuous AI Security

AI security cannot end when the system is deployed.

AI systems may change through:

* Model updates
* New training data
* Prompt changes
* Dependency updates
* Configuration changes
* Provider changes
* Runtime behavior

Security must therefore continue throughout the operational lifecycle.

---

### 7. Defense in Depth

AI systems should use multiple independent security layers.

```text id="q5m9xn"
Identity
   |
Access Control
   |
Data Security
   |
Model Security
   |
Application Security
   |
Infrastructure Security
   |
Monitoring
   |
Incident Response
```

Compromise of one layer should not automatically result in complete system compromise.

---

### 8. Least Privilege

Every AI component should receive only the permissions required to perform its intended function.

This applies to:

* Developers
* Models
* AI applications
* Training jobs
* APIs
* Agents
* Pipelines
* Service accounts

Least privilege limits the potential blast radius of compromise.

---

### 9. Separation of Duties

Critical AI lifecycle activities should be separated when risk justifies it.

For example:

```text id="x7m4qx"
Developer
    |
    v
Creates AI System
    |
    v
Security Reviewer
    |
    v
Validates Security
    |
    v
Approver
    |
    v
Production Deployment
```

No single person or component should automatically control every critical lifecycle decision.

---

### 10. Explicit Trust

AI components should not receive trust simply because they exist inside an enterprise environment.

Trust should be established through:

* Identity
* Authorization
* Provenance
* Integrity
* Validation
* Security testing
* Policy compliance

Enterprise network location should not independently establish trust.

---

### 11. Zero Trust for AI Development

Zero Trust principles should apply to AI development environments.

Every request should be evaluated according to:

* Who is requesting access
* What resource is being accessed
* What action is requested
* Why access is required
* What environment is involved
* What risk exists

AI development environments should not be implicitly trusted.

---

### 12. AI Identity

Every significant AI component should have an identifiable security identity.

Identity may apply to:

* Human developers
* Applications
* Models
* Pipelines
* Workloads
* Agents
* Services

Identity enables authorization and accountability.

---

### 13. AI Authentication

AI systems and supporting components should authenticate before accessing protected resources.

Authentication should be appropriate to the component.

Examples include:

* Enterprise identity
* Workload identity
* Certificates
* Tokens
* Cryptographic credentials

Authentication should establish identity, not automatically establish authorization.

---

### 14. AI Authorization

Authorization determines what an authenticated entity is permitted to do.

```text id="p6m8xn"
Identity
   |
   v
Authentication
   |
   v
Authorization
   |
   +----> Allow
   |
   +----> Deny
```

AI systems should not treat successful authentication as equivalent to unrestricted authority.

---

### 15. AI Asset Protection

AI assets should be identified and protected according to their value and sensitivity.

Assets include:

* Datasets
* Models
* Prompts
* Source code
* Model weights
* APIs
* Credentials
* Training environments
* AI applications
* Configuration

Asset protection should be risk-based.

---

### 16. Data Minimization

AI systems should collect and process only the data necessary for the intended purpose.

Data minimization reduces:

* Privacy exposure
* Attack surface
* Data leakage consequences
* Unauthorized access opportunities

Unnecessary data should not be introduced into AI pipelines.

---

### 17. Data Classification

AI data should be classified according to enterprise data-classification requirements.

Classification may influence:

* Storage
* Access
* Encryption
* Processing
* Retention
* Model training
* External sharing

Sensitive data should receive stronger controls.

---

### 18. Data Provenance

AI development should preserve information about where data originated and how it was transformed.

```text id="m4q9xn"
Data Source
    |
    v
Ingestion
    |
    v
Transformation
    |
    v
Training Dataset
    |
    v
AI Model
```

Provenance enables investigation of how data influenced system behavior.

---

### 19. Data Integrity

Data used by AI systems should be protected against unauthorized modification.

Integrity mechanisms may include:

* Hashes
* Digital signatures
* Versioning
* Immutable storage
* Validation

Data integrity is fundamental to model integrity.

---

### 20. Model Integrity

The organization should ensure that the model used by an AI system is the intended and approved model.

Controls may include:

* Version identifiers
* Cryptographic hashes
* Digital signatures
* Registry controls
* Deployment verification

Unauthorized model modification should be detectable.

---

### 21. Model Provenance

Models should be traceable to their development inputs.

Model provenance should connect:

* Source code
* Dataset
* Features
* Training process
* Dependencies
* Configuration
* Evaluation
* Model artifact

This creates a defensible chain of trust.

---

### 22. Artifact Integrity

AI artifacts should remain protected throughout their lifecycle.

Artifacts may include:

* Models
* Containers
* Packages
* Configurations
* Prompt templates
* AI workflows

Artifact integrity controls should prevent unauthorized modification.

---

### 23. Secure AI Supply Chain

AI development depends on many external and internal components.

The supply chain may include:

```text id="q8m5xn"
Open Source
    |
Models
    |
Datasets
    |
Libraries
    |
Containers
    |
APIs
    |
Cloud Services
    |
AI Application
```

Each component should be evaluated according to its security and trust requirements.

---

### 24. Trusted Components

AI development should use approved and trusted components whenever possible.

Trust assessment may consider:

* Source
* Integrity
* Provenance
* Security history
* Vulnerabilities
* Maintenance
* Licensing

A component should not become trusted merely because it is widely used.

---

### 25. Dependency Security

AI dependencies should be continuously managed.

Controls should address:

* Versioning
* Vulnerability scanning
* Approved sources
* Dependency pinning
* Integrity verification
* End-of-life components

Dependencies can introduce vulnerabilities into otherwise secure AI applications.

---

### 26. Secure Development Environment

AI development environments should be protected from unauthorized access and compromise.

Controls should include:

* Identity management
* Endpoint security
* Access restrictions
* Secret protection
* Network segmentation
* Logging

Developer environments should not automatically have production authority.

---

### 27. Secure Training Environment

Training environments should be isolated and controlled.

They should protect:

* Training data
* Model code
* Credentials
* Compute resources
* Model artifacts

A compromised training environment can affect downstream model trust.

---

### 28. Secure Model Development

Model development should integrate security into experimentation and implementation.

Security should consider:

* Algorithm selection
* Model source
* Dependencies
* Training data
* Configuration
* Model outputs

Security should be considered alongside functional performance.

---

### 29. Threat Modeling

Threat modeling should identify potential attacks before deployment.

AI threat modeling should consider:

* Data poisoning
* Prompt injection
* Model manipulation
* Model extraction
* Data leakage
* Supply-chain compromise
* Unauthorized access
* Infrastructure compromise

Threat models should evolve as the system changes.

---

### 30. Attack Surface Reduction

AI systems should minimize unnecessary exposed functionality.

Attack surface reduction may involve:

* Removing unused APIs
* Restricting model interfaces
* Limiting dependencies
* Reducing network connectivity
* Disabling unnecessary tools
* Restricting data access

Every unnecessary capability creates additional security exposure.

---

### 31. Secure Coding for AI

AI application code should follow secure coding practices.

Developers should address:

* Input validation
* Authentication
* Authorization
* Error handling
* Secret management
* Dependency security
* API security

AI-specific risks should be incorporated into normal secure coding standards.

---

### 32. Input Validation

AI systems should validate inputs before processing where appropriate.

Validation should consider:

* Format
* Size
* Type
* Encoding
* Allowed content
* Context

Input validation is particularly important where untrusted information can influence model behavior.

---

### 33. Output Validation

AI-generated outputs should not automatically be treated as trusted.

Applications should validate outputs before:

* Executing commands
* Updating records
* Calling APIs
* Making security decisions
* Sending external communications

```text id="v7m5qx"
AI Output
    |
    v
Validation
    |
    +----> Safe --> Continue
    |
    +----> Unsafe --> Block / Review
```

---

### 34. AI Interface Security

AI interfaces should be protected against unauthorized use.

Interfaces include:

* APIs
* Chat interfaces
* Model endpoints
* Internal services
* Tool interfaces

Authentication, authorization, rate limiting, and monitoring should be applied according to risk.

---

### 35. Prompt and Instruction Security

Prompts, system instructions, and AI configurations can influence system behavior and should be treated as security-sensitive components.

Controls should protect against:

* Unauthorized modification
* Prompt injection
* Instruction manipulation
* Configuration leakage

Security-sensitive instructions should be version-controlled.

---

### 36. Secrets Protection

Secrets must not be embedded in:

* Prompts
* Source code
* Notebooks
* Model artifacts
* Configuration files
* Containers

Secrets should be retrieved through controlled secrets-management mechanisms.

---

### 37. Secure Configuration

AI configuration should be protected against unauthorized modification.

Configuration may include:

* Model selection
* API endpoints
* Safety controls
* System instructions
* Access policies
* Runtime parameters

Material configuration changes should trigger appropriate security validation.

---

### 38. Secure AI Build

AI builds should occur in controlled environments.

The build process should protect:

* Source code
* Dependencies
* Build configuration
* Credentials
* Artifacts

Build outputs should be identifiable and verifiable.

---

### 39. Reproducibility

AI systems should be reproducible or independently verifiable where practical.

Reproducibility requires control over:

* Code
* Data
* Dependencies
* Configuration
* Environment
* Build process

This supports security investigation and assurance.

---

### 40. Security Testing

Security testing should occur throughout AI development.

Testing may include:

* Static analysis
* Dependency scanning
* Threat-model validation
* Model security testing
* Adversarial testing
* API security testing
* Infrastructure testing

Testing depth should reflect system risk.

---

### 41. Continuous Security Testing

Security testing should continue after initial deployment.

Testing should be triggered by material changes such as:

* Model updates
* Dataset changes
* Dependency updates
* Configuration changes
* Infrastructure changes

This helps prevent previously secure systems from becoming insecure through lifecycle changes.

---

### 42. Secure Deployment

Production deployment should occur only through controlled mechanisms.

Deployment should verify:

* Artifact identity
* Integrity
* Approval
* Configuration
* Target environment
* Security status

Direct uncontrolled deployment should be prohibited for governed AI systems.

---

### 43. Runtime Security

AI systems require protection after deployment.

Runtime controls may include:

* Access control
* Network security
* Model integrity
* API protection
* Monitoring
* Vulnerability management

Development security does not replace runtime security.

---

### 44. Security Monitoring

AI systems should generate security telemetry throughout their lifecycle.

Monitoring should identify:

* Unauthorized access
* Unexpected model changes
* Suspicious API activity
* Configuration changes
* Abnormal behavior
* Security control failures

Security monitoring should connect to enterprise security operations.

---

### 45. Continuous Vulnerability Management

AI systems should be continuously assessed for vulnerabilities.

Coverage should include:

* Application code
* Dependencies
* Containers
* Infrastructure
* AI frameworks
* Model-serving systems
* External services

Vulnerability management should connect discovery, prioritization, remediation, and verification.

---

### 46. Secure Change Management

AI changes should be governed according to their potential security impact.

Changes may include:

* Model replacement
* Prompt modification
* Dataset update
* Dependency update
* Configuration change
* Infrastructure change

Material changes should trigger appropriate security reassessment.

---

### 47. Secure Recovery

AI systems should have mechanisms for recovering from security incidents or failed changes.

Recovery capabilities may include:

* Known-good models
* Backup configurations
* Artifact backups
* Rollback
* Credential revocation
* Environment restoration

Recovery should preserve security controls rather than bypassing them.

---

### 48. Fail-Secure Design

Security-critical AI controls should fail in a manner that prevents unauthorized trust.

```text id="k5m9qx"
Security Control
      |
  +---+---+
  |       |
PASS     FAIL
  |       |
  v       v
Allow    Block
```

If a critical security decision cannot be reliably established, the system should not silently assume that the operation is safe.

---

### 49. Continuous AI Security Principles

A mature secure AI development program should combine:

1. Security by design
2. Secure defaults
3. Least privilege
4. Zero Trust
5. Defense in depth
6. Separation of duties
7. Data protection
8. Model integrity
9. Supply-chain security
10. Continuous testing
11. Continuous monitoring
12. Controlled change
13. Traceability
14. Fail-secure behavior
15. Continuous reassessment

These principles should apply throughout the AI lifecycle.

---

### 50. Core Principle of Secure AI Development

**Secure AI development must treat security as a fundamental engineering property of the entire AI lifecycle rather than as a final testing activity.**

The secure development model is:

```text id="q6m8xn"
Security Requirements
        |
        v
Secure Architecture
        |
        v
Threat Modeling
        |
        v
Secure Development
        |
        v
Secure Data
        |
        v
Secure Model
        |
        v
Security Testing
        |
        v
Trusted Artifact
        |
        v
Controlled Deployment
        |
        v
Runtime Security
        |
        v
Continuous Monitoring
        |
        v
Change / Reassessment
        |
        +------> Continuous Secure Development
```

**The fundamental principle is that AI security must remain embedded, enforceable, attributable, and continuously reassessed from initial design through production operation and retirement, so that no model, dataset, application, pipeline, dependency, or AI capability can silently become trusted outside the organization's defined security boundaries.**

## Part 2 — Security Controls

### 51. Secure AI Development Control Framework

A Secure AI Development Control Framework translates secure development principles into enforceable technical and operational controls.

The framework should cover the complete AI development lifecycle:

```text id="c7m4px"
Code ───────┐
Data ───────┤
Models ─────┤
Dependencies┤
Pipelines ──┤
Containers ─┤──> Security Controls ──> Trusted Release
IaC ────────┤
Secrets ────┤
Testing ────┤
Artifacts ──┘
```

Controls should be measurable, testable, attributable, and capable of producing evidence.

---

### 52. Secure Source Code Control

AI source code repositories should enforce security controls before code can enter protected branches.

Controls should include:

* Authenticated repository access
* Role-based permissions
* Protected branches
* Mandatory code review
* Commit traceability
* Secret scanning
* Vulnerability scanning
* Repository audit logging

---

### 53. Branch Protection Control

Production-bound AI code should be protected against unauthorized modification.

Branch protection should enforce:

* Pull requests
* Required reviewers
* Status checks
* Successful security scans
* Restricted force pushes
* Restricted branch deletion

Security-critical repositories should not permit uncontrolled direct commits.

---

### 54. Code Review Security Control

AI code changes should undergo security-aware peer review.

Reviewers should assess:

* Authentication
* Authorization
* Input handling
* Output handling
* Data access
* Secrets
* API calls
* AI-specific security behavior

Higher-risk changes should require additional independent review.

---

### 55. Static Application Security Testing

Static Application Security Testing should identify vulnerabilities in AI application source code before deployment.

SAST should examine issues such as:

* Injection vulnerabilities
* Insecure authentication
* Authorization weaknesses
* Unsafe deserialization
* Hardcoded secrets
* Insecure API usage
* Dangerous system calls

Findings should be integrated into development security gates.

---

### 56. Secret Detection Control

AI development repositories should automatically scan for exposed credentials.

Detection should cover:

* API keys
* Access tokens
* Passwords
* Certificates
* Private keys
* Cloud credentials
* Database credentials

Detected secrets should be revoked or rotated according to incident procedures.

---

### 57. Dependency Vulnerability Control

AI dependencies should be scanned for known vulnerabilities.

Coverage should include:

* Python packages
* JavaScript packages
* ML frameworks
* Container dependencies
* System libraries
* Model-serving libraries

Critical vulnerabilities should prevent release when policy requires blocking.

---

### 58. Software Composition Analysis

Software Composition Analysis should identify the components contained within AI applications.

SCA should provide:

* Dependency inventory
* Version information
* Known vulnerabilities
* License information
* Dependency relationships
* Risk classification

This creates visibility into the AI software supply chain.

---

### 59. AI Software Bill of Materials

AI applications should maintain a Software Bill of Materials describing their software composition.

An AI SBOM should identify relevant:

* Libraries
* Frameworks
* Packages
* Runtime components
* Container components
* Build dependencies

The SBOM should be associated with the released artifact.

---

### 60. Dataset Access Control

Dataset access should be controlled according to data classification and AI project requirements.

Controls should enforce:

* Identity-based access
* Role-based authorization
* Least privilege
* Dataset-specific permissions
* Environment restrictions
* Access logging

Development access should not automatically provide unrestricted production-data access.

---

### 61. Dataset Integrity Control

Training datasets should be protected against unauthorized modification.

Integrity mechanisms may include:

* Cryptographic hashes
* Digital signatures
* Immutable storage
* Version identifiers
* Integrity verification during ingestion

A changed dataset should be detectable before training.

---

### 62. Dataset Schema Validation Control

Datasets should be validated against approved schemas before entering controlled AI pipelines.

Validation should detect:

* Unexpected fields
* Missing fields
* Incorrect types
* Structural changes
* Unexpected records

Schema deviations should trigger rejection or controlled review.

---

### 63. Dataset Content Security Scanning

Dataset content should be scanned for security risks appropriate to the use case.

Scanning may detect:

* Malicious payloads
* Embedded scripts
* Sensitive information
* Unexpected file types
* Suspicious content
* Data integrity anomalies

The scanning process should occur before sensitive datasets enter model-development workflows.

---

### 64. Dataset Version Control

Every governed training dataset should have an identifiable version.

Dataset versions should allow security teams to determine:

* What data was used
* When it was created
* Who created it
* What changed
* Which model consumed it

Dataset versioning supports model reproducibility and investigation.

---

### 65. Dataset Immutability Control

Approved training datasets should become immutable during controlled model builds whenever practical.

```text id="r6n4px"
Raw Data
   |
   v
Validated Dataset
   |
   v
Approved Version
   |
   v
Immutable Snapshot
   |
   v
Training
```

Immutability prevents data from silently changing after security approval.

---

### 66. Training Pipeline Authentication

Training pipelines should authenticate before accessing protected resources.

Authentication should apply to:

* Source repositories
* Dataset stores
* Feature stores
* Model registries
* Artifact repositories
* Cloud services

Machine identities should be used instead of shared credentials.

---

### 67. Training Pipeline Authorization

Training jobs should receive only the permissions necessary for their assigned task.

For example, a training job may be allowed to:

* Read an approved dataset
* Write a temporary training artifact
* Publish results to a controlled location

It should not automatically be allowed to modify production models.

---

### 68. Training Environment Isolation

Training environments should be isolated from production environments.

Segmentation should protect:

* Training workloads
* Production models
* Production databases
* Production credentials
* Production APIs

Compromise of a training environment should not automatically create production access.

---

### 69. Notebook Security Control

Interactive notebooks should be treated as controlled development environments.

Controls should address:

* Identity
* Access
* Network connectivity
* Secrets
* Code execution
* Package installation
* Data access
* Audit logging

Notebooks should not become uncontrolled paths into sensitive environments.

---

### 70. Interactive Development Isolation

Interactive development environments should operate within defined security boundaries.

Developers should not be able to use development notebooks to bypass:

* Repository controls
* CI/CD security gates
* Artifact validation
* Production authorization

Interactive access should complement, not circumvent, governed delivery processes.

---

### 71. Model Loading Security

Applications and pipelines should securely validate models before loading them.

Controls should verify:

* Model source
* Model identity
* Model version
* Integrity
* Provenance
* Approved status

Untrusted model files should not be loaded into privileged environments.

---

### 72. Model Serialization Security

Model serialization formats should be treated as potentially dangerous inputs.

Controls should address:

* Unsafe deserialization
* Arbitrary code execution
* Untrusted model files
* Serialization vulnerabilities
* Format-specific attacks

Only approved and validated serialization mechanisms should be permitted.

---

### 73. Model Artifact Scanning

Model artifacts should undergo security scanning before promotion.

Scanning may examine:

* Embedded files
* Serialization structures
* Dependencies
* Metadata
* Malicious payloads
* Known vulnerabilities

Scanning should be appropriate to the model format and deployment architecture.

---

### 74. Model Integrity Verification

The model deployed into an environment should be verified against the approved artifact.

Verification may use:

* Hashes
* Signatures
* Registry identifiers
* Version identifiers
* Provenance metadata

Deployment should fail if the artifact cannot be verified.

---

### 75. Model Signing Control

Approved models should be cryptographically signed where risk and architecture justify it.

Signing establishes an integrity assertion about the artifact.

```text id="w5q9px"
Model Build
    |
    v
Security Validation
    |
    v
Approved Model
    |
    v
Digital Signature
    |
    v
Model Registry
    |
    v
Deployment Verification
```

The deployment environment should verify the signature before accepting the model.

---

### 76. Artifact Provenance Control

AI artifacts should carry provenance information describing their origin.

Provenance should link the artifact to:

* Source code
* Dataset version
* Model version
* Build process
* Dependencies
* Configuration
* Build identity
* Security results

This creates an auditable chain of custody.

---

### 77. Model Registry Access Control

Model registries should enforce strict access controls.

Permissions should distinguish between:

* Model creation
* Model modification
* Model approval
* Model promotion
* Model deployment
* Model retirement

Registry access should not automatically imply deployment authority.

---

### 78. Model Promotion Control

Model promotion should occur only after required security and governance checks pass.

```text id="p4m8qx"
Development
     |
     v
Testing
     |
 Security Gate
     |
     v
Approved
     |
     v
Staging
     |
 Security Gate
     |
     v
Production
```

Each transition should be controlled and traceable.

---

### 79. Artifact Immutability Control

Approved AI artifacts should be immutable.

Once approved:

* The artifact should not be silently modified.
* Changes should create a new version.
* Existing signatures should become invalid if content changes.
* Deployment references should identify the exact artifact.

This prevents substitution attacks.

---

### 80. Container Image Security Control

AI container images should undergo security validation before deployment.

Controls should include:

* Base-image validation
* Vulnerability scanning
* Package inventory
* Secret scanning
* Malware detection where appropriate
* Image signing
* Image provenance

Only approved images should enter production.

---

### 81. Trusted Container Registry Control

Production AI workloads should pull container images from controlled registries.

Registry controls should enforce:

* Authentication
* Authorization
* Image immutability
* Signing verification
* Vulnerability status
* Audit logging

Public registries should not be treated as automatically trusted sources.

---

### 82. Container Runtime Security Control

AI containers should be securely configured at runtime.

Controls may include:

* Non-root execution
* Restricted capabilities
* Read-only filesystems
* Network restrictions
* Resource limits
* Runtime monitoring

Container compromise should be contained within the smallest practical boundary.

---

### 83. Infrastructure Security Control

AI infrastructure should be continuously assessed for security weaknesses.

Coverage should include:

* Compute
* Storage
* Networks
* Kubernetes
* Cloud services
* Model-serving infrastructure
* Training infrastructure

Infrastructure vulnerabilities can directly affect AI security.

---

### 84. Infrastructure-as-Code Security Control

AI infrastructure should be deployed through security-validated Infrastructure-as-Code.

IaC security checks should identify:

* Excessive permissions
* Public exposure
* Insecure network rules
* Weak encryption
* Misconfigured storage
* Insecure workload configurations

Infrastructure should not bypass established security controls simply because it is created through automation.

---

### 85. CI/CD Identity Control

CI/CD systems should use dedicated machine identities.

Each pipeline should have an identifiable security principal.

The identity should be:

* Unique
* Least privileged
* Auditable
* Environment-specific where appropriate

Shared administrative credentials should not be used for pipeline execution.

---

### 86. CI/CD Pipeline Isolation

AI pipelines should be isolated according to environment and risk.

```text id="n6m3px"
Development Pipeline
        |
        X
Production Pipeline
        |
        v
Controlled Promotion
```

Compromise of a development pipeline should not provide unrestricted production control.

---

### 87. Pipeline Configuration Integrity Control

Pipeline definitions should be protected against unauthorized modification.

Controls should cover:

* Pipeline configuration
* Build scripts
* Security gates
* Deployment definitions
* Environment variables
* Pipeline permissions

A compromised pipeline can become a mechanism for bypassing multiple security controls.

---

### 88. Build Environment Isolation

AI builds should execute in controlled and isolated environments.

Build environments should restrict:

* Network access
* Credential access
* Administrative privileges
* External package installation
* Production connectivity

Ephemeral build environments can reduce persistence and cross-build contamination.

---

### 89. Reproducible Build Control

AI builds should produce reproducible or independently verifiable outputs where practical.

The build should control:

* Source versions
* Dependency versions
* Build configuration
* Base images
* Toolchain versions

Unexpected differences should be investigated.

---

### 90. Dependency Pinning Control

Dependencies should be explicitly pinned for controlled builds.

Instead of dynamically obtaining the newest version, the pipeline should use an approved version.

This reduces the possibility of:

* Unexpected changes
* Malicious package replacement
* Dependency confusion
* Build inconsistency

---

### 91. Approved Dependency Control

Only approved dependencies should be permitted in governed AI environments.

Approval criteria may include:

* Security status
* Provenance
* Maintenance
* Vulnerability exposure
* Licensing
* Business necessity

Exceptions should be documented and risk-assessed.

---

### 92. External Model Dependency Control

External models should be evaluated before being integrated into enterprise AI systems.

Assessment should consider:

* Provider
* Model provenance
* Licensing
* Security characteristics
* Known vulnerabilities
* Update behavior
* Data handling

External model dependencies should have an identifiable owner.

---

### 93. External Dataset Control

External datasets should undergo security and provenance validation before use.

Validation should address:

* Source
* Licensing
* Integrity
* Content
* Collection method
* Data classification
* Known risks

Unverified external datasets should not automatically become trusted training inputs.

---

### 94. API Dependency Security Control

AI applications often depend on external APIs.

API dependencies should be governed through:

* Authentication
* Authorization
* TLS
* Input validation
* Output validation
* Rate limiting
* Monitoring
* Provider risk assessment

External APIs should be treated as untrusted boundaries unless explicitly established otherwise.

---

### 95. Secrets Vault Integration Control

AI development and deployment systems should retrieve secrets from approved secrets-management platforms.

Secrets should not be stored directly in:

* Source repositories
* Container images
* Model files
* Pipeline definitions
* Notebooks

Access should be controlled by workload identity.

---

### 96. Credential Rotation Control

Credentials used by AI systems should have controlled rotation processes.

Rotation should cover:

* API credentials
* Service credentials
* Certificates
* Database credentials
* Cloud access keys

Compromised credentials should be capable of emergency revocation.

---

### 97. Short-Lived Credential Control

Where technically possible, AI workloads should use short-lived credentials.

```text id="u7m4px"
Workload Identity
       |
       v
Temporary Credential
       |
       v
Authorized Operation
       |
       v
Credential Expiry
```

Short-lived credentials reduce the impact of credential theft.

---

### 98. Environment Configuration Security Control

Development, testing, staging, and production configurations should be explicitly controlled.

Configuration should define:

* Endpoints
* Access policies
* Model versions
* Security controls
* Runtime parameters
* Logging requirements

Production configuration should not be inherited blindly from development.

---

### 99. Configuration Integrity Control

Security-sensitive configuration should be protected against unauthorized modification.

Integrity mechanisms may include:

* Version control
* Digital signatures
* Change approvals
* Configuration hashes
* Policy enforcement

Unauthorized configuration changes should trigger detection.

---

### 100. Security Policy Enforcement in CI/CD

Security policies should be automatically evaluated within AI pipelines.

Policies may verify:

* Approved dependencies
* Model signatures
* Vulnerability thresholds
* Dataset approval
* Infrastructure security
* Required testing
* Artifact provenance

Policy enforcement should occur before production promotion.

---

### 101. Risk-Based Security Gates

Security gates should reflect the risk of the AI system.

Higher-risk systems may require:

* Additional testing
* Independent review
* Stronger artifact controls
* More restrictive deployment authorization
* Enhanced monitoring

Security gates should not treat every AI system identically.

---

### 102. Mandatory Gate Failure Control

Critical security gates should be fail-closed.

If a mandatory control cannot determine whether a release is secure, the pipeline should not silently proceed.

Examples include:

* Missing vulnerability results
* Invalid artifact signature
* Failed security testing
* Missing approval
* Unverified provenance

---

### 103. Security Exception Control

Security exceptions should follow a controlled process.

Each exception should identify:

* Requirement being bypassed
* Business justification
* Risk
* Duration
* Owner
* Compensating controls
* Approval

Exceptions should expire rather than becoming permanent bypasses.

---

### 104. Deployment Authorization Control

Production deployment should require explicit authorization appropriate to the risk tier.

Authorization should verify:

* Approved artifact
* Security results
* Required approvals
* Target environment
* Change record
* Risk status

Successful pipeline execution alone should not necessarily equal deployment authorization.

---

### 105. Model Deployment Verification Control

The deployment platform should verify that the deployed model corresponds to the approved model.

Verification should include:

* Artifact identity
* Version
* Hash
* Signature
* Registry status
* Deployment configuration

Unexpected model substitution should cause deployment failure.

---

### 106. Rollback Control

AI deployments should have a tested rollback mechanism.

Rollback should restore:

* Known-good model
* Known-good application
* Known-good configuration
* Required dependencies

Rollback should itself be governed and auditable.

---

### 107. AI Release Integrity Control

Every production AI release should have an identifiable security state.

The release record should associate:

```text id="z5m8px"
Release
  |
  +-- Source
  +-- Dataset
  +-- Model
  +-- Dependencies
  +-- Container
  +-- Configuration
  +-- Security Tests
  +-- Approval
```

This allows security teams to reconstruct what was actually released.

---

### 108. Deployment Environment Verification Control

Before deployment, the target environment should be verified against its approved security baseline.

Verification should assess:

* Identity
* Network configuration
* Security agents
* Runtime controls
* Configuration
* Required infrastructure components

Deployment should not proceed into an environment that materially violates its security baseline.

---

### 109. Production Access Restriction Control

Production AI environments should have highly restricted administrative access.

Access should be:

* Identity-based
* Least privileged
* Time-bound where appropriate
* Logged
* Monitored
* Reviewed

Developers should not automatically receive production administrative privileges.

---

### 110. AI Runtime Security Control

AI applications and models should remain protected after deployment.

Runtime controls should include:

* Access control
* Network restrictions
* Model integrity verification
* API protection
* Resource controls
* Security monitoring

---

### 111. Security Logging Control

Security-relevant AI lifecycle events should be logged.

Events may include:

* Dataset access
* Model changes
* Registry actions
* Pipeline executions
* Deployment events
* Configuration changes
* Privileged access

Logs should be protected against unauthorized alteration.

---

### 112. Security Telemetry Control

AI systems should produce security telemetry that can be correlated across the lifecycle.

Telemetry may connect:

```text id="a8m3px"
Developer
   |
Pipeline
   |
Build
   |
Artifact
   |
Model
   |
Deployment
   |
Runtime
```

This supports detection and forensic investigation.

---

### 113. Artifact Traceability Control

Every production artifact should be traceable back to its origin.

Traceability should connect:

* Artifact
* Build
* Source
* Dependencies
* Dataset
* Model
* Approvals
* Deployment

Traceability should work in both directions.

---

### 114. Continuous Vulnerability Management Control

AI environments should continuously reassess vulnerabilities after deployment.

New vulnerabilities may emerge because:

* Dependencies receive new disclosures
* Base images become vulnerable
* AI frameworks are updated
* Infrastructure weaknesses are discovered

A previously approved release may therefore require reassessment.

---

### 115. Security Drift Detection Control

AI development and production environments should be monitored for deviation from approved security baselines.

Drift may involve:

* Configuration
* Permissions
* Network exposure
* Model version
* Dependencies
* Security controls

Detected material drift should trigger investigation or remediation.

---

### 116. Automated Security Enforcement Control

Where practical, security controls should be automatically enforced rather than relying entirely on human intervention.

Automation may:

* Block insecure builds
* Reject unsigned models
* Prevent unauthorized deployment
* Quarantine artifacts
* Revoke credentials
* Detect configuration drift
* Trigger rollback

Automation should operate within clearly defined authorization boundaries.

---

### 117. Core Engineering Principle

**Secure AI development controls must independently verify and enforce trust at every critical transition—code, data, model, artifact, pipeline, infrastructure, deployment, and runtime—so that passing one security layer never creates automatic trust in the next layer.**
