# 12.01 — AI Secure Development Foundations

## Part 1 — Foundations

### 1. Definition of AI Secure Development

AI Secure Development is the discipline of integrating security requirements, threat management, secure engineering practices, testing, governance, and assurance throughout the lifecycle of AI applications, models, datasets, infrastructure, and supporting services.

Unlike conventional software development, AI systems contain additional security-sensitive components:

* Models
* Training datasets
* Validation datasets
* Prompts and instructions
* Feature pipelines
* Model configurations
* Training infrastructure
* Model artifacts
* Inference services
* AI dependencies
* Evaluation systems
* AI APIs

Security must therefore extend beyond application source code.

---

### 2. Purpose of AI Secure Development

The purpose of AI secure development is to ensure that security is designed into AI systems before they reach production.

The lifecycle should establish:

```text id="7m4xqp"
Security Requirements
        |
        v
Secure Design
        |
        v
Threat Modeling
        |
        v
Secure Development
        |
        v
Security Testing
        |
        v
Secure Deployment
        |
        v
Continuous Security
```

The objective is to reduce the probability that vulnerabilities, malicious components, unsafe configurations, or compromised artifacts reach production.

---

### 3. AI Security Begins Before Model Development

AI security should begin before developers train or integrate a model.

Early activities should establish:

* Business purpose
* Security objectives
* Data requirements
* Model requirements
* Threat assumptions
* Regulatory requirements
* Security boundaries
* Ownership
* Risk classification

Security requirements discovered after deployment are generally more expensive and disruptive to address.

---

### 4. AI Secure Development vs Traditional Secure Development

Traditional secure development primarily protects software and infrastructure.

AI secure development must additionally protect:

* Data used to train models
* Data used during inference
* Model behavior
* Model artifacts
* Model supply chain
* Training processes
* Evaluation processes
* AI-specific dependencies
* Model deployment pipelines

Therefore:

**AI security extends secure software development into the data, model, and ML lifecycle.**

---

### 9. Secure-by-Design for AI

Secure-by-design means security requirements are incorporated before implementation.

For AI systems, this includes designing:

* Data boundaries
* Model boundaries
* Access controls
* Training environments
* Model registries
* Deployment controls
* Secrets management
* Testing requirements
* Monitoring
* Incident response

Security should not depend exclusively on post-development testing.

---

### 10. Security-by-Default

AI development environments should use secure defaults.

Examples include:

* Private repositories
* Restricted model registries
* Encrypted storage
* Protected branches
* Mandatory code review
* Restricted credentials
* Isolated training environments
* Approved dependencies
* Controlled model promotion

Developers should not need to manually enable every fundamental security control.

---

### 12. Continuous AI Security

Changes may occur to:

* Models

* Prompts
* Dependencies
* Infrastructure
* Configuration
* APIs
* Training pipelines

Therefore security must continue after initial release.

* Model tampering
* Supply-chain compromise
* Dependency vulnerabilities
* Prompt injection
* Adversarial inputs
* Model extraction
* Unauthorized model access
* Artifact manipulation
* Infrastructure compromise

Threat modeling should cover the complete AI system.

Security risks include:

* Malicious records
* Data poisoning
* Unauthorized modification
* Sensitive information
* Incorrect provenance
* Untrusted sources
* Excessive permissions

Dataset security must therefore be integrated into secure development.

* Approved usage

### 18. Dataset Integrity

Training and evaluation datasets should be protected against unauthorized modification.

Integrity controls may include:

* Checksums
* Cryptographic hashes
* Access controls
* Versioning
* Immutable storage
* Change logging

An unauthorized dataset change can alter model behavior without modifying source code.

Models should be treated as security-sensitive artifacts.

Security risks include:

* Malicious models
* Tampered models
* Vulnerable models
* Unauthorized model replacement
* Model theft
* Backdoors
* Unsafe configurations

Model security should therefore extend from development through production.

> Does the AI system work correctly?

### 49. Core Principles of AI Secure Development

AI secure development should follow these foundational principles:

1. Security begins during requirements.
2. Security must cover the complete AI lifecycle.
3. Data is a security-sensitive development asset.
4. Models are security-sensitive artifacts.
5. AI dependencies require supply-chain controls.
6. Development and production must be separated.
7. Security testing must be continuous.
8. AI artifacts must maintain integrity and provenance.
9. Security gates should prevent unsafe promotion.
10. Changes must trigger appropriate security reassessment.
11. Production systems must remain monitored.
12. Security evidence must be retained.

---

**AI security must be engineered into the complete development and machine-learning lifecycle, from requirements and data acquisition through model development, testing, artifact management, deployment, operation, and continuous change.**

## Part 2 — Security Controls

### 51. AI Secure Development Control Framework

AI secure development controls translate foundational security principles into enforceable technical mechanisms across the development lifecycle.

The control framework should cover:

* Source code
* Developers
* Dependencies
* Datasets
* Training pipelines
* Models
* Artifacts
* Containers
* Infrastructure
* CI/CD
* Registries
* Deployment

Controls should operate both independently and as an integrated security chain.

---

### 52. Secure Source Code Repository Controls

AI source repositories should enforce security controls before code can enter protected branches.

Controls should include:

* Strong developer authentication
* Role-based repository access
* Protected branches
* Mandatory code review
* Commit controls
* Secret scanning
* Security scanning
* Audit logging
* Repository backup

Direct production changes from unmanaged development environments should be prohibited.

---

### 53. Branch Protection

Production-bound AI code should pass through protected branches.

Typical controls include:

```text id="7q4mxn"
Developer
    |
    v
Feature Branch
    |
    v
Code Review
    |
    v
Security Checks
    |
    v
Protected Branch
    |
    v
Build Pipeline
```

Developers should not be able to bypass mandatory security gates through direct commits.

---

### 54. Code Review Security Controls

Code review should evaluate security-sensitive changes, including:

* Authentication
* Authorization
* Data access
* API integrations
* Model loading
* File handling
* Serialization
* External connections
* Secrets
* Infrastructure changes

High-risk changes should require additional reviewers or security approval.

---

### 55. Static Application Security Testing

Static analysis should inspect AI application source code before deployment.

SAST should identify issues such as:

* Injection vulnerabilities
* Unsafe API usage
* Insecure deserialization
* Authentication weaknesses
* Authorization errors
* Hardcoded secrets
* Unsafe file operations

Security findings should be integrated into CI/CD gates.

---

### 56. Secret Detection Controls

Automated secret scanning should inspect:

* Source code
* Git history
* Configuration
* Notebooks
* Infrastructure definitions
* Container build files
* Pipeline definitions

Detected secrets should trigger remediation and, where necessary, credential rotation.

---

### 57. Dependency Vulnerability Scanning

AI dependencies should be automatically scanned for known vulnerabilities.

The process should identify:

* Direct dependencies
* Transitive dependencies
* Version
* Vulnerability severity
* Exploitability
* Available remediation

High-risk vulnerabilities should prevent production promotion when organizational policy requires it.

---

### 58. Software Composition Analysis

Software Composition Analysis should establish visibility into the AI application's software supply chain.

```text id="m8q3vx"
Application
    |
    +--> Direct Packages
    |
    +--> ML Frameworks
    |
    +--> Transitive Packages
    |
    +--> System Libraries
    |
    v
Software Bill of Materials
```

This creates a machine-readable inventory of software components.

---

### 59. AI Software Bill of Materials

An AI application should maintain an SBOM covering relevant software components.

The inventory should identify:

* Package
* Version
* Source
* Dependency relationship
* Vulnerabilities
* Build information

The SBOM should be associated with the corresponding application or model release.

---

### 60. Dataset Access Control

Access to datasets should follow least privilege.

Controls should distinguish:

* Read access
* Write access
* Modify access
* Delete access
* Export access
* Administrative access

Training systems should receive only the dataset access necessary for their assigned workload.

---

### 61. Dataset Integrity Validation

Datasets entering trusted pipelines should undergo automated integrity checks.

Controls may include:

* Hash validation
* File integrity verification
* Schema validation
* Record-count validation
* Version verification
* Source verification

Unexpected changes should trigger investigation or pipeline failure.

---

### 62. Dataset Schema Validation

Automated validation should confirm that datasets conform to expected structures.

Validation may check:

* Required fields
* Data types
* Field counts
* Allowed values
* File formats
* Record structure

Schema violations can indicate corruption, accidental changes, or malicious manipulation.

---

### 63. Dataset Content Security Scanning

Where appropriate, datasets should be scanned for security-sensitive content.

Controls may detect:

* Malware
* Malicious payloads
* Unexpected executable content
* Sensitive information
* Suspicious records
* Disallowed content

The objective is to prevent untrusted data from entering trusted processing environments.

---

### 64. Dataset Version Control

Important datasets should be version controlled.

A dataset version should have a unique identifier that allows the organization to determine exactly which data contributed to a model.

```text id="x5m9qn"
Dataset v1.2
     |
     v
Training Run 847
     |
     v
Model v3.4
```

This supports investigation and reproducibility.

---

### 65. Dataset Immutability Controls

Approved training datasets should be protected against unauthorized modification.

Possible mechanisms include:

* Immutable object storage
* Write-once repositories
* Access-controlled buckets
* Cryptographic integrity verification
* Version locking

Training should reference controlled dataset versions rather than uncontrolled mutable locations.

---

### 66. Training Pipeline Authentication

Training pipelines should authenticate to every security-sensitive service they access.

Authentication should cover:

* Dataset repositories
* Model registries
* Artifact repositories
* Cloud resources
* Databases
* Secret stores
* Container registries

Anonymous or shared credentials should be avoided.

---

### 67. Training Pipeline Authorization

Training workloads should receive only the permissions required to execute their assigned tasks.

For example:

```text id="b7q4mx"
Training Job
    |
    +--> Read Dataset
    +--> Write Model Artifact
    +--> Read Approved Secrets
    |
    X--> Modify Production
    X--> Delete Dataset
    X--> Access Unrelated Systems
```

Training authority should not automatically imply production authority.

---

### 68. Training Environment Isolation

Training workloads should operate within controlled environments.

Isolation mechanisms may include:

* Dedicated compute
* Network segmentation
* Container isolation
* Namespace separation
* Restricted service accounts
* Controlled storage

Compromised training workloads should have limited ability to affect other systems.

---

### 69. Notebook Security Controls

Jupyter notebooks and similar development environments should be treated as executable code.

Controls should address:

* Authentication
* Access control
* Network access
* Package installation
* Secrets
* Code execution
* Data access
* Notebook versioning

Notebooks should not become uncontrolled privileged execution environments.

---

### 70. Interactive Development Isolation

Developer workstations and interactive AI environments should be separated from production authority.

```text id="r4m8xn"
Developer Environment
       |
       v
Development Credentials
       |
       X
Production Authority
       |
       v
Controlled Pipeline
       |
       v
Production Credentials
```

Production deployment should occur through controlled mechanisms rather than personal developer credentials.

---

### 71. Model Loading Security

AI applications should validate model sources before loading model artifacts.

Controls should establish:

* Trusted source
* Expected format
* Integrity
* Version
* Provenance
* Compatibility
* Security status

Untrusted model files should not automatically enter privileged execution environments.

---

### 72. Model Serialization Security

Model serialization formats should be treated as potentially executable or dangerous inputs when applicable.

Controls should include:

* Approved serialization formats
* Trusted model sources
* Integrity validation
* Safe loading mechanisms
* Restricted execution environments

A model file should not be considered safe merely because it has a familiar filename.

---

### 73. Model Artifact Scanning

Model artifacts should undergo security validation before registration or promotion.

Scanning may identify:

* Suspicious components
* Embedded payloads
* Unexpected files
* Malformed structures
* Unauthorized modifications
* Known vulnerabilities

The exact controls depend on the model framework and artifact format.

---

### 74. Model Integrity Verification

Production-bound models should have integrity verification.

      |

      |

---

### 75. Model Signing

Organizations may digitally sign approved model artifacts.

Signing provides a mechanism to establish:

* Artifact origin
* Artifact integrity
* Approval state
* Release identity

Verification should occur before deployment or other high-trust use.

---

### 76. Artifact Provenance Controls

AI artifacts should retain metadata describing their origin.

Provenance may connect:

```text id="k8m4qn"

     |
     +--> Dataset Version
     |
     +--> Training Configuration
     |
     v

     |
     v
Model Artifact
```

This enables traceability from production model back to its development inputs.

---

### 77. Model Registry Access Control

Model registries should enforce granular permissions.

Roles may include:

* Developer
* ML engineer
* Security reviewer
* Model owner
* Release manager
* Deployment service
* Registry administrator

Upload, promotion, modification, and deletion should not necessarily be controlled by the same identity.

---

### 78. Model Registry Promotion Controls

Models should move through controlled lifecycle states.

```text id="p5q8mx"
Development
     |
     v
Evaluation
     |
     v
Security Validation
     |
     v
Approved
     |
     v
Production Candidate
     |
     v
Production
```

Promotion should require the completion of mandatory security conditions.

---

### 79. Artifact Immutability

Once an artifact has been approved, its contents should not be silently modified.

A change should create:

* A new version
* New integrity metadata
* New provenance
* New validation results
* New approval where required

This prevents an approved artifact from being replaced underneath the approval record.

---

### 80. Container Image Security

AI containers should be scanned before deployment.

Scanning should address:

* Operating-system vulnerabilities
* Package vulnerabilities
* Malware
* Misconfiguration
* Embedded secrets
* Unapproved components

Only images meeting organizational policy should reach production.

**Enterprise AI secure development architecture must continuously preserve the integrity, identity, authorization, security validation, provenance, and traceability of every significant AI component as it moves from development toward production.**

The architectural trust chain is:

```text id="r6m9qx"
Requirements
     |
     v
Secure Design
     |
     v
Trusted Development
     |
     v
Controlled Data
     |
     v
Secure Training
     |
     v
Security Testing
     |
     v
Verified Artifact
     |
     v
Trusted Registry
     |
     v
Security Gates
     |
     v
Authorized Deployment
     |
     v
Protected Production
     |
     v
Continuous Monitoring
     |
     v
Continuous Reassessment
     |
     v
Continuous Assurance
```

**A production AI system should never be trusted solely because it was developed inside the enterprise or passed through a development pipeline; trust must be continuously established through independently enforceable security controls, verified artifacts, controlled authorization, and persistent lifecycle assurance.**
