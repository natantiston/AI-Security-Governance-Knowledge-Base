# 12.19 — AI Change and Release Management

## Part 1 — AI Change and Release Management Foundations

### 1. Definition of AI Change and Release Management

AI Change and Release Management is the discipline of controlling, evaluating, approving, implementing, monitoring, and reversing changes to AI systems throughout their lifecycle.

AI changes can affect much more than application code. They may involve:

* Models
* Model weights
* Datasets
* Prompts and instructions
* Dependencies
* AI providers
* Containers
* Infrastructure
* Configuration
* Security controls
* Training pipelines
* CI/CD pipelines

AI change management therefore requires coordinated software, ML, infrastructure, security, and governance processes.

---

### 2. Purpose of AI Change and Release Management

The purpose is to ensure that AI changes do not introduce unacceptable security, operational, compliance, or business risk.

Effective change and release management should ensure that changes are:

* Identified
* Attributable
* Documented
* Risk-assessed
* Security-tested
* Authorized
* Implemented through controlled mechanisms
* Monitored after release
* Reversible when necessary

---

### 3. AI Change Management vs Traditional Change Management

Traditional change management generally focuses on application code and infrastructure.

AI systems introduce additional change dimensions:

| Traditional Change     | AI-Specific Change     |
| ---------------------- | ---------------------- |
| Application code       | Model weights          |
| Software dependency    | Dataset version        |
| Infrastructure         | Training configuration |
| Configuration          | Prompt/instruction     |
| Release package        | Model artifact         |
| Application deployment | Model promotion        |
| Software rollback      | Model rollback         |

These changes can interact with each other and therefore require integrated assessment.

---

A change can modify the security properties of an AI system.

For example:

```text id="acr04a"

    +--> Dependencies
```

Every material change should therefore be treated as a potential security boundary crossing.

### 6. AI Change Identification

Every material AI change should have a unique identity.

Change records should identify:

* Change ID
* Requester
* System
* Asset
* Version
* Reason
* Scope
* Risk
* Approvals
* Implementation time

---

### 7. AI Change Classification

Changes should be classified according to their potential impact.

Possible categories include:

* Standard
* Normal
* Significant
* High-risk
* Emergency

Classification should determine the required security validation and approval.

---

### 8. AI Change Risk

Risk should be evaluated before material changes are implemented.

Risk factors may include:

* Data sensitivity
* Model capability
* Production exposure
* Privilege
* Business criticality
* Security impact
* Regulatory impact
* Dependency impact

---

### 9. Security Impact Assessment

Material changes should receive a security impact assessment.

The assessment should determine whether the change affects:

* Threat model
* Security requirements
* Identity
* Authorization
* Data access
* Model security
* Infrastructure security
* Monitoring
* Incident response

---

### 10. AI Change Scope

The scope of an AI change should be explicitly defined.

A change may affect:

* One model
* One application
* One environment
* Multiple AI workloads
* Shared infrastructure
* Enterprise AI platforms

Scope determines the required level of assurance.

---

### 11. AI Change Ownership

Every change should have an accountable owner.

The owner should be responsible for:

* Change justification
* Risk assessment
* Required testing
* Implementation
* Documentation
* Post-release validation

Ownership does not eliminate the need for independent security approval.

---

### 12. Change Authorization

Changes should be authorized before implementation according to risk.

```text id="acr12c"
Change
  |
  v
Risk Assessment
  |
  v
Security Validation
  |
  v
Authorization
  |
  v
Implementation
```

A developer's ability to make a change should not automatically establish authority to approve it.

---

### 13. Separation of Duties

High-risk changes should separate:

* Change development
* Security validation
* Approval
* Production implementation

This reduces the possibility of unauthorized changes entering production.

---

### 14. AI Change Requirements

Every material change should have defined requirements.

Requirements may address:

* Security
* Functionality
* Performance
* Data protection
* Model integrity
* Availability
* Compliance

### 16. Model Changes

Model changes can include:

* New model
* New weights
* Fine-tuning
* Retraining
* Architecture changes
* Model provider changes
* Model configuration changes

Model changes should receive security evaluation appropriate to their risk.

---

### 17. Dataset Changes

Dataset changes may affect model behavior and security.

Examples include:

* New data sources
* Dataset versions
* Data transformations
* Feature changes
* Removal of data
* Training-data corrections

Material dataset changes may require model reassessment.

---

### 18. Training Changes

Changes to training processes may alter model behavior.

Examples include:

* Hyperparameters
* Training code
* Framework versions
* Training data
* Hardware
* Optimization methods

Training changes should therefore be traceable to the resulting model artifact.

---

### 19. Prompt and Instruction Changes

Prompts, system instructions, policies, and AI configuration can influence security behavior.

Material changes should be evaluated for:

* Prompt injection resistance
* Authorization behavior
* Data exposure
* Tool usage
* Output safety

---

### 20. AI Dependency Changes

Dependency changes can introduce security vulnerabilities.

Changes should consider:

* Version
* Source
* Vulnerabilities
* Provenance
* Compatibility
* Supply-chain risk

---

### 21. AI Provider Changes

Changing an external AI provider can materially alter the system's security posture.

Assessment should consider:

* Data handling
* Authentication
* API security
* Model behavior
* Provider trust
* Geographic requirements
* Availability

---

### 22. Container Changes

Container changes should be managed as security-sensitive releases.

Security assessment should include:

* Base image
* Dependencies
* Image provenance
* Vulnerabilities
* Runtime privileges
* Model access
* Dataset access

---

### 23. Infrastructure Changes

Infrastructure changes can alter AI security boundaries.

Examples include:

* Network changes
* IAM changes
* Storage changes
* GPU changes
* Kubernetes changes
* Firewall changes

High-risk infrastructure changes should receive appropriate independent security validation.

---

### 24. Configuration Changes

Configuration can materially change AI security behavior without changing application code.

Examples include:

* Authentication settings
* Authorization policies
* Model parameters
* API endpoints
* Network rules
* Security thresholds

Configuration changes should therefore be version-controlled and auditable.

---

### 25. Security-Control Changes

Changes to security controls require elevated scrutiny.

Examples include:

* Security gates
* Monitoring rules
* Authentication policies
* Authorization policies
* Detection rules
* Network controls

Security controls should not be weakened through ordinary application change processes.

* Shared infrastructure

### 29. Regression Testing

### 49. AI Change and Release Management Principles

AI change and release management should follow these principles:

1. Every material change must be identifiable.
2. Changes must be risk-assessed before implementation.
3. Security impact must be evaluated.
4. Changes must remain attributable.
5. High-risk changes require appropriate separation of duties.
6. Code, data, models, infrastructure, and configuration must be assessed together.
7. Security testing must reflect the change and system risk.
8. Production release requires explicit authorization.
9. Releases must be observable and reversible.
10. Previously approved changes remain subject to continuous reassessment.

---

### 50. Core Principle of AI Change and Release Management

**AI change and release management must treat every material modification to code, datasets, models, dependencies, prompts, configurations, containers, infrastructure, pipelines, or external AI services as a potential change to the security posture of the AI system. Every material change must therefore be identifiable, attributable, risk-assessed, security-tested, traceable, appropriately approved, securely released, continuously monitored, and reversible where necessary. Production trust must never be established solely because a change passed functional testing or was previously approved; security authority must independently determine whether the changed AI capability remains within the organization's defined risk tolerance throughout its lifecycle.**
