# 12.08 — AI Threat Modeling

## Part 1 — Foundations

### 1. Definition of AI Threat Modeling

AI Threat Modeling is the structured process of identifying, analyzing, prioritizing, and communicating threats against an AI system throughout its lifecycle.

It examines how an AI system can be attacked, manipulated, misused, compromised, or indirectly exploited through its:

* Applications
* Models
* Data
* Prompts
* Tools
* APIs
* Infrastructure
* Dependencies
* Users
* External providers
* Development pipelines

AI threat modeling extends traditional threat modeling because AI systems introduce additional security properties, trust relationships, and attack paths.

---

### 2. Purpose of AI Threat Modeling

The primary purpose of AI threat modeling is to identify security risks **before they become security incidents**.

It allows security and engineering teams to determine:

* What must be protected
* Who may attack the system
* How attacks could occur
* Which components could be compromised
* What business impact could result
* Which controls are required

The fundamental objective is to move security from reactive incident response toward proactive risk reduction.

```text id="m7q4px"

Identify Trust Boundaries
    |

Identify Threats

Analyze Attack Paths
    |

Assess Risk
    |
    v

```

### 3. AI Threat Modeling vs Traditional Threat Modeling

Traditional threat modeling focuses primarily on software, infrastructure, identities, data flows, and interfaces.

AI threat modeling must additionally consider:

* Model behavior
* Training data
* Inference inputs
* Prompt manipulation
* Model outputs
* Retrieval systems
* AI memory
* Tool invocation
* Model supply chains
* AI-specific abuse
* Model extraction
* Data poisoning

The difference is not that traditional security concepts become irrelevant. Rather, AI introduces additional attack surfaces that must be incorporated into the existing threat-modeling discipline.

### 5. Threat Modeling Begins with Business Context

AI threats cannot be evaluated correctly without understanding what the system is intended to accomplish.

Business context establishes:

* Business purpose
* Critical processes
* Users
* Data involved
* Business dependencies
* Regulatory obligations
* Acceptable risk
* Potential consequences of compromise

The same technical vulnerability may have very different risk levels depending on business context.

---

### 6. AI System Scope

The threat model should define the complete security boundary of the AI system.

Scope may include:

* User interfaces
* AI applications
* Models
* Model APIs
* Datasets
* Vector stores
* Memory stores
* Tools
* External APIs
* Cloud services
* CI/CD pipelines
* Development environments
* Production infrastructure

The model should avoid focusing only on the model itself.

---

### 7. AI Asset Identification

Threat modeling begins by identifying assets that require protection.

Typical AI assets include:

| Asset               | Security Concern           |
| ------------------- | -------------------------- |
| Model               | Integrity, confidentiality |
| Dataset             | Integrity, confidentiality |
| Prompt              | Integrity, confidentiality |
| System Instructions | Integrity                  |
| Credentials         | Confidentiality            |
| User Data           | Confidentiality            |
| Tool Permissions    | Integrity, authorization   |
| Source Code         | Integrity, confidentiality |
| Model Artifacts     | Integrity                  |
| Vector Store        | Confidentiality, integrity |
| Infrastructure      | Availability, integrity    |

Asset identification establishes what an attacker could attempt to compromise.

---

### 8. AI Security Objectives

Threat modeling should define the security objectives that must be preserved.

Core objectives include:

* Confidentiality
* Integrity
* Availability
* Authentication
* Authorization
* Accountability
* Traceability
* Non-repudiation where applicable
* Privacy
* Safety

AI systems may require additional objectives around model behavior and decision integrity.

---

### 9. Confidentiality Threats

Confidentiality threats seek unauthorized access to information.

Examples include:

* Sensitive prompt disclosure
* Training-data extraction
* RAG data leakage
* Cross-tenant data exposure
* Credential disclosure
* Model extraction
* Memory leakage
* Excessive logging

Threat modeling should identify every location where sensitive information enters, moves through, or leaves the AI system.

---

### 10. Integrity Threats

Integrity threats seek to manipulate trusted AI components or their outputs.

Examples include:

* Dataset poisoning
* Model tampering
* Prompt modification
* Dependency compromise
* Pipeline manipulation
* Artifact replacement
* Configuration modification

Integrity is particularly important because attackers may attempt to make malicious components appear legitimate.

---

### 11. Availability Threats

Availability threats seek to prevent legitimate users or systems from accessing AI capabilities.

Examples include:

* Resource exhaustion
* Denial-of-service attacks
* Excessive inference requests
* Pipeline disruption
* Model-serving failure
* Dependency outages
* Malicious workload generation

Threat models should consider both technical availability and business-service availability.

---

### 12. Authentication Threats

Authentication threats target the mechanisms used to establish identity.

Potential attacks include:

* Credential theft
* Token theft
* Session hijacking
* Workload identity compromise
* API-key exposure
* Weak service authentication

AI architectures should distinguish between human, application, workload, and external-provider identities.

---

### 13. Authorization Threats

Authorization threats attempt to cause an AI system to perform actions beyond the requester's permitted authority.

Examples include:

* Privilege escalation
* Unauthorized tool execution
* Cross-tenant access
* Object-level authorization bypass
* Unauthorized data retrieval
* Model access escalation

A critical AI security principle is:

**Model output must not be treated as authorization.**

---

### 15. Trust Boundaries in AI Systems

A trust boundary exists wherever data, authority, identity, or control moves between environments with different trust assumptions.

Examples include:

* User to application
* Application to model
* Application to vector database
* Model to tool
* Application to external provider
* Development to production
* Dataset source to training environment

Threat modeling should explicitly identify these boundaries.

### 17. AI Threat Actors

Threat models should identify potential threat actors.

Actors may include:

* External attackers
* Malicious users
* Compromised users
* Insiders
* Contractors
* Developers
* Supply-chain attackers
* Compromised service providers
* Automated attackers
* Other AI systems

Different actors have different capabilities and access paths.

---

### 18. External Attackers

External attackers may target publicly accessible AI systems.

Potential objectives include:

* Data extraction
* Prompt injection
* Account compromise
* API abuse
* Model probing
* Resource exhaustion
* Tool exploitation

External exposure should therefore influence AI threat-model risk.

---

### 19. Malicious or Compromised Users

An authenticated user can still represent a threat.

Potential behavior includes:

* Privilege abuse
* Data extraction
* Prompt manipulation
* Tool misuse
* Excessive requests
* Cross-tenant attacks

Authentication alone does not establish trustworthiness.

---

### 20. Insider Threats

Employees, contractors, administrators, and developers may possess legitimate access that can be abused.

Threat modeling should consider:

* Excessive privileges
* Unauthorized data access
* Model manipulation
* Credential misuse
* Pipeline manipulation
* Intentional or accidental disclosure

Least privilege and separation of duties reduce insider attack opportunities.

---

### 21. Supply-Chain Threat Actors

AI systems depend on many external components.

Attackers may compromise:

* Open-source packages
* Model repositories
* Datasets
* Container images
* Development tools
* CI/CD dependencies
* Cloud services
* External AI providers

Supply-chain threats should therefore be modeled as first-class attack scenarios.

### 23. Dataset Threat Modeling

Datasets should be analyzed as security-sensitive assets.

Threats include:

* Poisoning
* Unauthorized modification
* Malicious records
* Sensitive-data leakage
* Provenance manipulation
* Unauthorized access
* Dataset substitution

The threat model should determine which dataset controls are required.

---

### 24. Training Pipeline Threat Modeling

Training pipelines can become high-value attack targets.

Attackers may attempt to:

* Modify training code
* Inject malicious dependencies
* Alter datasets
* Manipulate configurations
* Compromise training credentials
* Replace model artifacts

A compromised training pipeline can produce a compromised model.

---

### 25. Model Threat Modeling

Models should be evaluated for threats affecting:

* Integrity
* Confidentiality
* Availability
* Behavior
* Deployment
* Provenance

Threat scenarios may include:

* Model tampering
* Model theft
* Model extraction
* Backdoors
* Adversarial manipulation
* Unauthorized replacement

---

### 26. Prompt Threat Modeling

Prompts and instructions can influence AI behavior and therefore require threat analysis.

Threats include:

* Prompt injection
* Instruction manipulation
* System-prompt disclosure
* Context manipulation
* Malicious retrieved content

The threat model should distinguish between trusted instructions and untrusted content.

---

### 27. Retrieval Threat Modeling

RAG architectures introduce additional attack paths.

Threats include:

* Malicious documents
* Unauthorized retrieval
* Cross-tenant leakage
* Retrieval poisoning
* Sensitive document exposure
* Manipulated embeddings

Retrieval security should therefore be modeled separately from ordinary application security.

---

### 28. Tool Threat Modeling

Tools can transform an AI application from an information system into an action-capable system.

Potential threats include:

* Unauthorized tool execution
* Parameter manipulation
* Privilege escalation
* Destructive operations
* External system abuse
* Credential misuse

The threat model should evaluate both the model's ability to request an action and the authorization system's ability to control it.

---

### 29. AI Memory Threat Modeling

Persistent memory introduces additional attack surfaces.

Threats include:

* Unauthorized memory access
* Memory poisoning
* Cross-user leakage
* Cross-tenant leakage
* Sensitive information retention
* Malicious persistent context

Memory should be treated as a controlled data store rather than merely a model feature.

---

### 30. AI API Threat Modeling

AI APIs should be evaluated as externally reachable attack surfaces.

Threats may include:

* Authentication bypass
* Authorization bypass
* Abuse
* Injection
* Excessive requests
* Data leakage
* API manipulation

API threat modeling should include both inbound and outbound interfaces.

---

### 31. Model Supply-Chain Threat Modeling

Model supply chains introduce risks beyond conventional software dependencies.

Threats include:

* Malicious models
* Tampered model artifacts
* Fake model versions
* Compromised model repositories
* Untrusted pretrained models
* Hidden malicious behavior

Model provenance and artifact integrity should therefore be central to the threat model.

---

### 32. AI Dependency Threat Modeling

AI applications often rely on specialized libraries, frameworks, inference engines, and plugins.

Threat modeling should consider:

* Vulnerable dependencies
* Malicious packages
* Dependency confusion
* Transitive dependencies
* Unmaintained components
* Compromised build dependencies

Dependencies should be treated as potential trust-boundary crossings.

---

### 33. Infrastructure Threat Modeling

AI workloads may operate on:

* Cloud infrastructure
* Kubernetes
* GPUs
* Virtual machines
* Containers
* Serverless platforms
* Specialized AI platforms

Infrastructure threats may affect confidentiality, integrity, availability, or isolation.

---

### 34. AI Configuration Threat Modeling

Configuration can materially affect AI security.

Threats include:

* Excessive permissions
* Unsafe model settings
* Disabled security controls
* Incorrect provider configuration
* Weak API settings
* Insecure tool configuration

Configuration should therefore be treated as a security asset.

---

### 35. Human Interaction Threat Modeling

AI systems frequently interact with humans in ways that traditional applications do not.

Threats may involve:

* Social engineering
* Manipulative outputs
* Misleading recommendations
* Excessive user trust
* Approval manipulation
* Human-review bypass

Threat models should consider human decision points as security boundaries.

---

### 36. AI-to-AI Threat Modeling

Systems may communicate with other AI systems, agents, or automated services.

Potential threats include:

* Malicious instructions
* Trust propagation
* Identity confusion
* Authorization confusion
* Data leakage
* Cascading compromise

An AI system should not automatically trust another AI simply because it is part of the same enterprise.

---

### 37. Threat Modeling for Autonomous Behavior

AI systems capable of autonomous action require additional analysis.

The threat model should distinguish:

* What the model can suggest
* What the application can request
* What the user can authorize
* What the tool can execute

       v

       |

### 39. Attack Surface Reduction

Threat modeling should identify opportunities to remove unnecessary attack paths.

Reduction strategies include:

* Removing unnecessary tools
* Reducing API exposure
* Limiting data access
* Eliminating unused dependencies
* Restricting network connectivity
* Reducing privileges
* Removing unnecessary model capabilities

The strongest attack path is often the one that no longer exists.

Not every identified threat represents the same level of risk.

Risk assessment should consider:

* Likelihood
* Impact
* Exploitability
* Exposure
* Asset criticality
* Existing controls
* Attacker capability

Threats should be prioritized according to actual organizational risk.

A threat that cannot be tested should still have an explicitly defined assurance approach.

Threat modeling should therefore inform security telemetry requirements.

### 49. Core Principles of AI Threat Modeling

Effective AI threat modeling follows several fundamental principles:

1. **Model the entire AI system, not only the model.**
2. **Treat data as an attack surface.**
3. **Treat model artifacts as security-sensitive assets.**
4. **Identify every meaningful trust boundary.**
5. **Model identity and authorization independently from AI behavior.**
6. **Analyze attack chains rather than isolated vulnerabilities.**
7. **Translate significant threats into security requirements and controls.**
8. **Connect threat scenarios to security testing.**
9. **Consider development, deployment, and runtime threats.**
10. **Reassess the threat model whenever material changes occur.**

---

### 50. Core Principle of AI Threat Modeling

**AI threat modeling must transform the complexity of an AI system into a structured understanding of assets, trust boundaries, threat actors, attack paths, security objectives, risks, and required controls so that security decisions are made before and throughout the system's lifecycle rather than after an AI-related incident occurs.**
