# 12.08 — AI Threat Modeling

## Part 1 — Foundations

### 1. Definition of AI Threat Modeling

AI Threat Modeling is the structured process of identifying, analyzing, prioritizing, and communicating threats against an AI system throughout its lifecycle.

It examines how an AI system can be attacked, manipulated, misused, compromised, or indirectly exploited through its:

* Applications
* Models
* Data
* Prompts
* Tools
* APIs
* Infrastructure
* Dependencies
* Users
* External providers
* Development pipelines

AI threat modeling extends traditional threat modeling because AI systems introduce additional security properties, trust relationships, and attack paths.

---

### 2. Purpose of AI Threat Modeling

The primary purpose of AI threat modeling is to identify security risks **before they become security incidents**.

It allows security and engineering teams to determine:

* What must be protected
* Who may attack the system
* How attacks could occur
* Which components could be compromised
* What business impact could result
* Which controls are required

The fundamental objective is to move security from reactive incident response toward proactive risk reduction.

```text id="m7q4px"

    |
    v
Identify Trust Boundaries
    |
    v
Identify Threats
    |
    v
Analyze Attack Paths
    |
    v
Assess Risk
    |
    v
Define Controls
```

---

### 3. AI Threat Modeling vs Traditional Threat Modeling

Traditional threat modeling focuses primarily on software, infrastructure, identities, data flows, and interfaces.

AI threat modeling must additionally consider:

* Model behavior
* Training data
* Inference inputs
* Prompt manipulation
* Model outputs
* Retrieval systems
* AI memory
* Tool invocation
* Model supply chains
* AI-specific abuse
* Model extraction
* Data poisoning

The difference is not that traditional security concepts become irrelevant. Rather, AI introduces additional attack surfaces that must be incorporated into the existing threat-modeling discipline.

---

### 5. Threat Modeling Begins with Business Context

AI threats cannot be evaluated correctly without understanding what the system is intended to accomplish.

Business context establishes:

* Business purpose
* Critical processes
* Users
* Data involved
* Business dependencies
* Regulatory obligations
* Acceptable risk
* Potential consequences of compromise

The same technical vulnerability may have very different risk levels depending on business context.

* CI/CD pipelines

### 8. AI Security Objectives

Threat modeling should define the security objectives that must be preserved.

Core objectives include:

* Confidentiality
* Integrity
* Availability
* Authentication
* Authorization
* Accountability
* Traceability
* Non-repudiation where applicable
* Privacy
* Safety

AI systems may require additional objectives around model behavior and decision integrity.

---

### 9. Confidentiality Threats

Confidentiality threats seek unauthorized access to information.

Examples include:

* Sensitive prompt disclosure
* Training-data extraction
* RAG data leakage
* Cross-tenant data exposure
* Credential disclosure
* Model extraction
* Memory leakage
* Excessive logging

Threat modeling should identify every location where sensitive information enters, moves through, or leaves the AI system.

---

### 10. Integrity Threats

Integrity threats seek to manipulate trusted AI components or their outputs.

Examples include:

* Dataset poisoning
* Model tampering
* Prompt modification
* Dependency compromise
* Pipeline manipulation
* Artifact replacement
* Configuration modification

Integrity is particularly important because attackers may attempt to make malicious components appear legitimate.

---

### 11. Availability Threats

Availability threats seek to prevent legitimate users or systems from accessing AI capabilities.

Examples include:

* Resource exhaustion
* Denial-of-service attacks
* Excessive inference requests
* Pipeline disruption
* Model-serving failure
* Dependency outages
* Malicious workload generation

Threat models should consider both technical availability and business-service availability.

---

### 12. Authentication Threats

Authentication threats target the mechanisms used to establish identity.

Potential attacks include:

* Credential theft
* Token theft
* Session hijacking
* Workload identity compromise
* API-key exposure
* Weak service authentication

AI architectures should distinguish between human, application, workload, and external-provider identities.

---

### 13. Authorization Threats

Authorization threats attempt to cause an AI system to perform actions beyond the requester's permitted authority.

Examples include:

* Privilege escalation
* Unauthorized tool execution
* Cross-tenant access
* Object-level authorization bypass
* Unauthorized data retrieval
* Model access escalation

A critical AI security principle is:

**Model output must not be treated as authorization.**

### 15. Trust Boundaries in AI Systems

A trust boundary exists wherever data, authority, identity, or control moves between environments with different trust assumptions.

Examples include:

* User to application
* Application to model
* Application to vector database
* Model to tool
* Application to external provider
* Development to production
* Dataset source to training environment

Threat modeling should explicitly identify these boundaries.

### 20. Insider Threats

Threat modeling should consider:

* Excessive privileges
* Unauthorized data access
* Model manipulation
* Credential misuse
* Pipeline manipulation
* Intentional or accidental disclosure

Least privilege and separation of duties reduce insider attack opportunities.

Threats include:

* Malicious documents
* Unauthorized retrieval
* Cross-tenant leakage
* Retrieval poisoning
* Sensitive document exposure
* Manipulated embeddings

Retrieval security should therefore be modeled separately from ordinary application security.

### 28. Tool Threat Modeling

Potential threats include:

* Unauthorized tool execution
* Parameter manipulation
* Privilege escalation
* Destructive operations
* External system abuse
* Credential misuse

The threat model should evaluate both the model's ability to request an action and the authorization system's ability to control it.

Threats include:

* Unauthorized memory access
* Memory poisoning

* Cross-tenant leakage

* Reducing privileges
* Removing unnecessary model capabilities

### 49. Core Principles of AI Threat Modeling

Effective AI threat modeling follows several fundamental principles:

1. **Model the entire AI system, not only the model.**
2. **Treat data as an attack surface.**
3. **Treat model artifacts as security-sensitive assets.**
4. **Identify every meaningful trust boundary.**
5. **Model identity and authorization independently from AI behavior.**
6. **Analyze attack chains rather than isolated vulnerabilities.**
7. **Translate significant threats into security requirements and controls.**
8. **Connect threat scenarios to security testing.**
9. **Consider development, deployment, and runtime threats.**
10. **Reassess the threat model whenever material changes occur.**

---

### 50. Core Principle of AI Threat Modeling

**AI threat modeling must transform the complexity of an AI system into a structured understanding of assets, trust boundaries, threat actors, attack paths, security objectives, risks, and required controls so that security decisions are made before and throughout the system's lifecycle rather than after an AI-related incident occurs.**

The fundamental relationship is:

```text id="c8m5px"
    |
    v

    |
    v

    |
    v
Security Controls
    |
    v
Testing
    |
    v

    |
```

**A mature AI threat model therefore becomes a living security artifact that continuously connects what the AI system is capable of doing with what an attacker could manipulate, what the organization must protect, what controls must exist, and what evidence must demonstrate that those protections remain effective.**

## Part 2 — AI Threat Modeling Control Framework

### 51. AI Threat Modeling Control Framework

An AI threat modeling control framework translates identified threats and attack paths into enforceable security controls.

The framework should connect:

```text id="tmc51a"

   v

   |

   |
   v

   |
   v

   |
   v

```

Controls should address preventive, detective, corrective, and compensating security measures across the AI lifecycle.

---

### 52. Threat Modeling Scope Control

Every AI threat model should have a formally defined scope.

The scope should identify:

* AI applications
* Models
* Datasets
* APIs
* Tools
* Retrieval systems
* Memory
* Infrastructure
* CI/CD
* External providers
* Users
* Supporting services

Scope changes should trigger reassessment.

---

### 53. AI Asset Inventory Control

All security-relevant AI assets should be recorded in an authoritative inventory.

The inventory should identify:

* Asset owner
* Asset type
* Business purpose
* Environment
* Classification
* Dependencies
* Risk tier
* Security requirements

Unknown assets represent unmanaged attack surface.

---

### 54. AI Trust Boundary Control

Trust boundaries identified during threat modeling should be documented and validated.

Examples include:

* User-to-application
* Application-to-model
* Application-to-database
* Model-to-tool
* Development-to-production
* Enterprise-to-provider

Controls should exist at each material boundary.

---

### 55. Data Flow Analysis Control

AI data flows should be documented and reviewed.

The analysis should identify:

* Source
* Destination
* Processing
* Storage
* Transformation
* External transfer
* Authorization

Unexpected data flows should trigger investigation.

---

### 56. Threat Actor Identification Control

Threat models should identify realistic threat actors and their capabilities.

Threat actors may include:

* External attackers
* Malicious users
* Insiders
* Compromised accounts
* Developers
* Supply-chain attackers
* Third-party providers
* Automated attackers

Actor capabilities should be based on realistic access and technical assumptions.

---

### 57. Threat Scenario Identification Control

Threat scenarios should describe specific ways an attacker could compromise or misuse the AI system.

A scenario should identify:

* Threat actor
* Entry point
* Target
* Attack technique
* Security objective affected
* Potential impact

Generic statements such as "AI could be hacked" are insufficient.

---

### 58. Attack Path Analysis Control

Threat models should identify multi-step attack paths.

---

### 59. AI Threat Categorization Control

Threats should be categorized consistently to support enterprise analysis.

Categories may include:

* Identity threats
* Data threats
* Model threats
* Application threats
* Prompt threats
* Tool threats
* API threats
* Supply-chain threats
* Infrastructure threats
* Operational threats

Consistent categorization enables reporting and trend analysis.

---

### 60. Confidentiality Threat Control

Threat models should explicitly identify confidentiality risks.

Controls should address:

* Data leakage
* Training-data exposure
* Prompt disclosure
* RAG leakage
* Memory leakage
* Cross-tenant exposure
* Model extraction

Sensitive information should have clearly defined protection requirements.

---

### 61. Integrity Threat Control

Integrity controls should protect AI components against unauthorized modification.

Protected assets include:

* Code
* Datasets
* Prompts
* Models
* Artifacts
* Configurations
* Policies

Integrity mechanisms may include hashing, signatures, access controls, immutable storage, and change detection.

---

### 62. Availability Threat Control

AI availability threats should be addressed through preventive and recovery mechanisms.

Controls may include:

* Rate limiting
* Resource quotas
* Capacity controls
* Service redundancy
* Circuit breakers
* Failover
* Recovery procedures

Availability controls should reflect business criticality.

---

### 63. Authentication Threat Control

Threat models should identify authentication weaknesses affecting AI components.

Controls should address:

* Human identities
* Service identities
* Workload identities
* API credentials
* Tokens
* External provider authentication

Authentication mechanisms should be appropriate to the risk of the protected resource.

---

### 64. Authorization Threat Control

Authorization should be modeled independently from authentication.

Controls should verify:

* Who is requesting access
* What resource is requested
* What action is requested
* Under which context
* Whether the action is permitted

The fact that an AI model requests an action must never be treated as sufficient authorization.

---

### 65. Least-Privilege Control

AI components should operate using the minimum privileges required.

Least privilege should apply to:

* Applications
* Models
* Tools
* Databases
* Service accounts
* CI/CD pipelines
* Training jobs
* Developers

Excessive privileges increase the potential blast radius of compromise.

---

### 66. Zero Trust Control

AI system interactions should be authenticated and authorized based on explicit security context.

Zero Trust controls should avoid assumptions such as:

* "Internal means trusted."
* "The model is trusted."
* "The pipeline is trusted."
* "The service is trusted because it is part of the same application."

Trust should be continuously evaluated where risk warrants it.

---

### 67. Dataset Integrity Control

Datasets should be validated before use in AI systems.

Controls should include:

* Hash validation
* Version verification
* Schema validation
* Provenance validation
* Access control
* Change detection

Unverified datasets should not automatically enter trusted training pipelines.

---

### 68. Dataset Poisoning Detection Control

Organizations should implement controls to identify potentially poisoned datasets.

Detection mechanisms may examine:

* Unexpected records
* Statistical anomalies
* Malicious content
* Label manipulation
* Source inconsistencies
* Unusual distribution changes

High-risk datasets should receive stronger validation.

---

### 69. Dataset Provenance Control

Dataset provenance should identify where data originated and how it was transformed.

Provenance should capture:

```text id="tmc69c"

  |
  v

  |
  v

  |
  v

  |
  v

  |
  v
```

---

### 70. Model Integrity Control

Model integrity should be verified before deployment and, where appropriate, during runtime.

Controls may include:

* Cryptographic hashes
* Digital signatures
* Trusted registries
* Version validation
* Provenance verification

A model should not be trusted solely because it has a valid filename or version label.

---

### 71. Model Provenance Control

Model provenance controls should establish how a model was created.

Evidence should identify:

* Training dataset
* Training code
* Dependencies
* Configuration
* Training environment
* Training run
* Evaluation results
* Model version

This allows security teams to determine whether a model originated from an approved process.

---

### 72. Model Artifact Security Control

Model artifacts should be scanned and validated before entering trusted repositories.

Controls should identify:

* Malicious components
* Unsafe serialization
* Embedded payloads
* Unexpected files
* Integrity violations
* Suspicious metadata

Artifact validation should occur before promotion.

---

### 73. Prompt Integrity Control

Security-sensitive prompts and system instructions should be protected from unauthorized modification.

Controls should include:

* Access control
* Version control
* Integrity validation
* Review
* Security testing
* Controlled deployment

Material prompt changes should be treated as security-relevant changes.

---

### 74. Prompt Injection Testing Control

AI applications should be tested against prompt injection.

Testing should evaluate whether untrusted content can:

* Override instructions
* Alter intended behavior
* Access restricted information
* Trigger unauthorized tools
* Circumvent security controls

Testing should cover both direct and indirect prompt injection.

---

### 75. Context Boundary Control

### 76. Input Validation Control

Inputs entering AI applications should be validated according to their security context.

* Type validation
* Length restrictions
* Encoding checks
* Content filtering
* Authorization checks

Input validation should occur before sensitive processing.

### 77. Output Validation Control

Model outputs should be treated as potentially untrusted.

Controls should validate outputs before they are:

* Displayed
* Stored
* Sent to external systems
* Used as commands
* Used for authorization
* Passed to tools

AI-generated output should not automatically become trusted application input.

### 79. Tool Parameter Validation Control

Tool parameters should be independently validated.

Validation should consider:

* Resource
* User identity
* Allowed values
* Business rules
* Risk level

### 80. High-Risk Action Control

High-impact actions should receive stronger security controls.

Examples include:

* Financial transactions
* Privileged account changes
* Data deletion
* Production changes
* External communications
* Security-control modifications

### 81. AI API Security Control

AI APIs should be protected against unauthorized and abusive use.

Controls should include:

* Strong authentication
* Authorization
* Rate limiting
* Input validation
* Output validation
* Logging
* Abuse detection

API exposure should be incorporated into the threat model.

### 82. Retrieval Authorization Control

Retrieval systems should enforce authorization before returning data to an AI application.

Controls should validate:

* User identity
* Tenant
* Resource
* Data classification
* Purpose
* Access rights

### 117. Core Engineering Principle

**AI threat modeling becomes an effective security control only when identified threats are translated into enforceable requirements, implemented through technical and procedural controls, validated through security testing, continuously monitored, supported by evidence, and reassessed whenever the AI system or its threat environment changes.**

The complete control chain is:

```text id="tmc117l"
Threat
   |
   v
Attack Path
   |
   v
Risk
   |
   v
Security Requirement
   |
   v
Preventive / Detective Control
   |
   v
Security Test
   |
   v
Security Gate
   |
   v
Runtime Monitoring
   |
   v
Evidence
   |
   v
Continuous Reassessment
```

A threat model that identifies threats without driving controls, testing, monitoring, and reassessment is primarily a documentation artifact rather than an effective security control mechanism.
