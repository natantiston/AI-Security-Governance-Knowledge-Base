# 12.15 — Container Security for AI

## Part 1 — Container Security for AI Foundations

### 1. Definition of Container Security for AI

Container Security for AI is the discipline of protecting containerized AI applications, machine learning workloads, model-serving systems, training environments, and their supporting infrastructure throughout the container lifecycle.

It addresses security risks associated with:

* Container images
* Base images
* AI frameworks
* Model runtimes
* Python and system packages
* Container configuration
* Container registries
* Build processes
* Runtime execution
* Kubernetes or container orchestration
* Secrets
* Network connectivity
* GPU and accelerator access
* Model artifacts
* Persistent storage

Container security for AI must therefore address both traditional container risks and AI-specific risks.

---

### 2. Purpose of Container Security for AI

The purpose is to ensure that containers running AI workloads are:

* Trusted
* Hardened
* Authenticated
* Authorized
* Isolated
* Integrity-protected
* Continuously monitored
* Vulnerability-managed
* Traceable
* Recoverable

The objective is not simply to produce a secure image.

The entire container lifecycle must remain secure:


---

### 3. AI Container Security vs Traditional Container Security

AI containers inherit traditional container security requirements but introduce additional security concerns.

Traditional container security focuses heavily on:

* Image vulnerabilities
* Container isolation
* Runtime privileges
* Registry security
* Host security
* Network security

AI container security additionally considers:

* Model artifacts
* ML frameworks
* GPU libraries
* Training datasets
* Model-serving runtimes
* AI dependencies
* Model loading
* Serialization formats
* Inference APIs
* Training workloads
* Large computational resources

Therefore, an AI container should be treated as a composite security asset rather than merely a software packaging mechanism.

---

### 4. Containers as an AI Security Boundary

A container creates a security boundary around an AI workload.

However, the boundary is not absolute.

Security can be weakened through:

* Excessive privileges
* Host access
* Insecure mounts
* Shared networks
* Shared credentials
* Vulnerable runtimes
* Kernel vulnerabilities
* GPU interfaces
* Misconfigured orchestration

The security objective is therefore to ensure that compromise of one container does not automatically compromise the host, cluster, or other AI workloads.

### 6. Container Image as a Security Asset

A container image should be treated as a security-sensitive artifact.

An AI container image may contain:

* Application code
* AI frameworks
* Dependencies
* Model runtimes
* Configuration
* System libraries
* Security components
* Model artifacts

Compromise of an image can therefore introduce malicious behavior directly into the AI environment.

---

### 7. Container Image Identity

Every approved AI container image should have a unique and verifiable identity.

Identity may include:

* Repository
* Image name
* Version
* Digest
* Build identifier
* Signing information
* Provenance metadata

Tags alone should not be considered sufficient identity because tags can potentially be changed.

---

### 8. Container Image Versioning

AI container images must use controlled versioning.

Version management should make it possible to determine:

* Which image was deployed
* Which dependencies it contains
* Which model it serves
* Which build produced it
* Which security tests were performed

Immutable image digests provide stronger identity than mutable tags.

---

### 9. Base Image Security

The base image establishes the foundational software environment of the AI container.

Security evaluation should consider:

* Operating-system vulnerabilities
* Package lifecycle
* Image publisher
* Image provenance
* Minimality
* Maintenance status
* Security update availability

Untrusted base images should not be used for production AI workloads.

---

### 10. Minimal Container Images

AI container images should contain only the software required for their intended function.

Unnecessary:

* Packages
* Services
* Utilities
* Compilers
* Shell tools
* Debugging components

should be removed from production images where practical.

Image minimization reduces attack surface.

---

### 11. Trusted Base Images

Organizations should establish approved base images for AI workloads.

A trusted base image should have:

* Known provenance
* Defined owner
* Security baseline
* Vulnerability status
* Supported lifecycle
* Controlled update process

---

### 12. AI Framework Security

AI frameworks embedded in containers must be treated as security-sensitive components.

Examples include frameworks used for:

* Model training
* Model inference
* Data processing
* Model transformation
* GPU acceleration

Framework vulnerabilities can directly affect the security of the AI workload.

---

### 13. Container Dependency Security

All software dependencies inside AI containers must be inventoried and assessed.

This includes:

* Python packages
* System packages
* AI frameworks
* ML libraries
* GPU libraries
* SDKs
* Native libraries
* Runtime components

A container should not be considered secure simply because the container image itself successfully builds.

---

### 14. Container Software Bill of Materials

AI container images should have an associated Software Bill of Materials.

The SBOM should provide visibility into the components contained within the image.

```text id="cont14c"
Container Image
      |
      +--> OS Packages
      +--> AI Frameworks
      +--> Python Packages
      +--> GPU Libraries
      +--> Application Code
      +--> Runtime Components
      |
      v
     SBOM
```

---

### 15. Container Image Provenance

Organizations should maintain evidence showing where an AI container image originated and how it was produced.

Provenance may include:

* Source repository
* Build pipeline
* Builder identity
* Build timestamp
* Dependency inputs
* Build configuration
* Resulting digest

---

### 16. Container Image Integrity

Container images must be protected against unauthorized modification.

Integrity mechanisms may include:

* Cryptographic digests
* Signed images
* Registry integrity controls
* Immutable artifacts
* Deployment-time verification

A changed image should not automatically retain the trust status of the original image.

---

### 17. Container Image Signing

Production AI container images should be digitally signed where supported by the enterprise architecture.

Signing establishes evidence that the image was produced or approved by an authorized source.

Signing does not replace vulnerability scanning or policy validation.

---

### 18. Container Signature Verification

Container platforms should verify signatures before permitting trusted images to enter controlled environments.

```text id="cont18d"
Container Image
      |
      v

    /          \
 Valid        Invalid
   |             |
   v             v

```

---

### 19. Container Registry Security

Container registries are critical AI supply-chain components.

Registry security should protect:

* Images
* Tags
* Digests
* Metadata
* Signatures
* Access credentials
* Repository configuration

Unauthorized registry access could enable malicious image replacement.

---

### 20. Trusted Container Registries

Production AI workloads should consume images from approved registries.

Registry trust should be established through:

* Ownership
* Security controls
* Authentication
* Authorization
* Vulnerability scanning
* Auditability
* Availability

Public registries should not automatically be treated as trusted production sources.

---

### 21. Container Registry Access Control

Registry access should follow least privilege.

Developers, build pipelines, security systems, and deployment systems should receive only the permissions required for their roles.

For example:

```text id="cont21e"
Developer
   |
   +--> Pull
   |
Build Pipeline
   |
   +--> Pull / Push
   |
Deployment System
   |
   +--> Pull
   |
Registry Administrator
   |
   +--> Administrative Operations
```

---

### 22. Container Image Immutability

Approved production images should be immutable.

Once an image has been approved, its underlying content should not change without generating a new artifact identity and undergoing appropriate validation.

---

### 23. Container Tag Security

Mutable tags can create ambiguity about which image is actually deployed.

Production deployment should preferably reference immutable identifiers such as image digests.

---

### 24. Container Build Security

The container build process must be treated as a security-sensitive operation.

Build security should address:

* Build identity
* Dependency acquisition
* Build environment isolation
* Secrets
* Base images
* Build scripts
* Artifact generation

A compromised build process can produce a malicious image even when the source code appears legitimate.

---

### 25. Container Build Environment Isolation

Container builds should occur in isolated environments.

Build processes should not have unnecessary access to:

* Production networks
* Production credentials
* Sensitive datasets
* Unrelated repositories
* Administrative infrastructure

---

### 26. Container Build Reproducibility

Where practical, AI container builds should be reproducible.

The organization should be able to identify:

* Source inputs
* Base image
* Dependency versions
* Build configuration
* Resulting image digest

Reproducibility strengthens integrity investigation.

---

### 27. Containerfile Security

Dockerfiles, Containerfiles, and equivalent build specifications should be treated as source code requiring security review.

Security concerns include:

* Untrusted downloads
* Embedded credentials
* Excessive privileges
* Unverified packages
* Insecure configuration
* Arbitrary command execution

---

### 28. Container Secrets Security

Secrets must not be embedded directly into AI container images.

Examples of prohibited embedded secrets include:

* API keys
* Cloud credentials
* Database passwords
* Private keys
* AI provider credentials

Secrets should be provided through approved secrets-management mechanisms.

---

### 29. Container Runtime Security

Container runtime security protects the AI workload while it executes.

Controls should address:

* Privileges
* Processes
* Filesystems
* Network access
* System calls
* Resource usage
* Host interaction

---

### 30. Container Privilege Minimization

AI containers should run with the minimum privileges required.

Where practical:

* Avoid root
* Drop unnecessary Linux capabilities
* Restrict privileged operations
* Restrict host access

---

### 31. Rootless Container Security

Rootless execution can reduce the impact of container compromise by limiting the privileges available to processes running inside the container.

It should be used where compatible with the AI workload and infrastructure.

---

### 32. Container Filesystem Security

AI containers should use controlled filesystem permissions.

Where practical, production containers should use read-only filesystems with explicit writable locations for required runtime operations.

---

### 33. Container Host Isolation

The host operating system must be protected from container compromise.

Security boundaries should restrict:

* Host filesystem access
* Host process visibility
* Device access
* Kernel interfaces
* Privileged operations

---

### 34. Container Network Security

AI containers should have explicitly defined network permissions.

Network access should be based on workload requirements rather than unrestricted outbound connectivity.

---

### 35. Container Network Segmentation

AI workloads should be segmented according to trust and function.

```text id="cont35f"
                 AI Container Platform
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
     Training Zone   Inference Zone   Management
          |              |              |
          +------ Restricted Flows -----+
```

Compromise of an inference container should not automatically provide unrestricted access to training infrastructure.

---

### 36. Container-to-Container Security

Communication between AI containers should be authenticated and authorized where required.

Workloads should not automatically trust other containers simply because they operate within the same cluster or network.

---

### 37. Container Orchestration Security

AI container orchestration platforms introduce additional security boundaries.

Security must address:

* Cluster identity
* Namespace isolation
* Workload permissions
* Secrets
* Network policies
* Admission controls
* Scheduling
* Node security

---

### 38. Kubernetes Security for AI

Where Kubernetes is used, AI security should incorporate Kubernetes-specific controls.

These may include:

* RBAC
* Namespace isolation
* Network policies
* Pod security
* Admission policies
* Secret management
* Image verification

---

### 39. AI Workload Identity

Each containerized AI workload should have a distinct identity where practical.

Workload identity enables:

* Authentication
* Authorization
* Auditability
* Least privilege
* Policy enforcement

Identity should be tied to the workload rather than relying on shared credentials.

---

### 40. Container Service Account Security

Service accounts assigned to AI containers should have only the permissions necessary for the workload.

A model-serving container should not automatically possess administrative permissions over the cluster.

---

### 41. GPU and Accelerator Security

AI containers frequently require access to GPUs or other accelerators.

This creates additional security considerations involving:

* Device permissions
* Driver interfaces
* GPU runtime libraries
* Shared accelerator resources
* Host interaction

GPU access should therefore be explicitly authorized.

---

### 42. GPU Isolation

Where multiple workloads share accelerator infrastructure, appropriate isolation controls should prevent one workload from gaining unauthorized access to another workload's resources or data.

---

### 43. Model Artifact Security Inside Containers

If a container includes a model artifact, the model should retain its own security controls.

These may include:

* Model integrity
* Model provenance
* Model version
* Model signature
* Model authorization

Container trust must not automatically establish model trust.

---

### 44. Secure Model Loading

AI containers should validate model artifacts before loading them.

Model-loading mechanisms should be protected against malicious or unsafe serialization formats and unauthorized model replacement.

---

### 45. Dataset Access from Containers

Training containers should receive only the datasets required for their authorized workload.

```text id="cont45g"

       |
       v
Workload Identity
       |
       v
Dataset Authorization
       |
    +--+--+
    |     |
 Allowed Denied
    |       |
    v       v
 Access    Block
```

Container access should not provide unrestricted access to enterprise data stores.

---

### 46. Container Resource Security

AI workloads can consume substantial CPU, memory, GPU, storage, and network resources.

Resource controls should establish:

* CPU limits
* Memory limits
* GPU allocation
* Storage limits
* Network restrictions

This reduces denial-of-service and resource-exhaustion risks.

---

### 47. Container Runtime Monitoring

Running AI containers should be continuously monitored for security-relevant behavior.

Monitoring may identify:

* Unexpected processes
* Unexpected network connections
* Privilege changes
* File modifications
* Resource anomalies
* Unexpected package activity

---

### 48. Container Vulnerability Management

Container vulnerabilities must be continuously assessed.

Scanning should cover:

* Base image
* OS packages
* AI frameworks
* Application dependencies
* Runtime libraries
* GPU components where applicable

A clean image at build time can become vulnerable after deployment when new vulnerabilities are discovered.

---

Container security must continue after image creation.

---

### 50. Core Principle of Container Security for AI

**Every container supporting an AI system must be treated as a security-sensitive workload and supply-chain artifact whose image integrity, provenance, dependencies, identity, privileges, runtime behavior, data access, model access, and infrastructure interactions are explicitly controlled throughout its lifecycle. Containerization must reduce the blast radius of AI compromise rather than become an implicit trust boundary that allows compromise of one AI workload to propagate to the host, cluster, data, models, or other enterprise systems.**
