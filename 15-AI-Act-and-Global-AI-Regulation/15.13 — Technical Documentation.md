# 15.13 — Technical Documentation

## Part 1 — Foundations, Regulatory Purpose, Scope, and Documentation Governance

1. **Technical Documentation as an AI Governance Control**
   Technical documentation is a foundational AI compliance control that provides structured evidence about how an AI system was designed, developed, validated, deployed, and maintained. In an AI Security Governance and GRC framework, technical documentation should be treated as controlled compliance evidence rather than merely engineering documentation.

2. **Purpose of Technical Documentation**
   The primary purpose of technical documentation is to enable relevant stakeholders, conformity-assessment bodies, competent authorities, market-surveillance authorities, and other authorized parties to understand the AI system sufficiently to evaluate its regulatory compliance, characteristics, limitations, risks, and controls.

3. **EU AI Act Documentation Requirement**
   For AI systems subject to specific EU AI Act documentation requirements, providers must maintain the documentation required by the applicable provisions and annexes. The exact documentation requirements depend on the system's regulatory classification, particularly whether the system is a high-risk AI system.

4. **Technical Documentation and Accountability**
   Technical documentation establishes an evidence trail connecting regulatory requirements to the actual characteristics and controls of an AI system. It supports accountability by making it possible to determine what was built, for what purpose, under which assumptions, using which data and processes, and subject to which controls.

5. **Documentation Versus Marketing Material**
   Technical documentation should not be confused with product brochures, marketing claims, sales presentations, or general product descriptions. Marketing material may describe capabilities, but technical documentation must provide sufficiently precise and reliable information to support compliance and assurance.

6. **Documentation Versus Source Code**
   Technical documentation is not synonymous with source code. Source code may constitute supporting technical evidence, but technical documentation must explain the system in a structured manner that allows qualified reviewers to understand its architecture, functionality, development process, limitations, and compliance controls without necessarily inspecting every line of code.

7. **Documentation Versus Security Documentation**
   Security documentation is an important component of an AI documentation package, but technical documentation has broader scope. Depending on the system and applicable requirements, it may include architecture, data, model development, testing, risk management, human oversight, performance, cybersecurity, logging, conformity, and post-market information.

8. **Documentation Versus Risk Management Records**
   Risk registers and risk assessments are related to technical documentation but should not automatically be treated as substitutes for it. Technical documentation should demonstrate how identified risks were addressed through design, development, testing, controls, and operational safeguards.

9. **Documentation as Compliance Evidence**
   A well-controlled technical documentation package should allow an independent reviewer to trace material compliance assertions to objective evidence.

10. **Documentation Completeness**
    Documentation should be sufficiently complete to describe the AI system and its compliance characteristics relevant to the applicable regulatory requirements. Completeness should be evaluated against the system's risk, intended purpose, architecture, lifecycle, and legal obligations.

11. **Documentation Accuracy**
    Technical documentation should accurately describe the actual AI system. Documentation that describes an earlier model, configuration, dataset, architecture, or intended purpose may create a material compliance and assurance gap if the production system has changed.

12. **Documentation Currency**
    Documentation should remain current throughout the applicable lifecycle. Material changes to the AI system, model, data, architecture, intended purpose, performance, cybersecurity posture, or regulatory classification should trigger documentation review.

13. **Documentation Traceability**
    Every material technical-documentation statement should be traceable to an appropriate source, such as engineering records, configuration repositories, test results, model artifacts, datasets, risk assessments, validation records, security assessments, or approved governance decisions.

14. **Documentation Ownership**
    A designated organizational function should own the technical documentation process. Ownership should include defining documentation requirements, coordinating contributors, reviewing completeness, approving controlled versions, managing changes, and ensuring appropriate retention.

15. **Documentation Contributors**
    Technical documentation may require contributions from multiple functions, including:

* AI/ML engineering;
* software engineering;
* data engineering;
* cybersecurity;
* privacy;
* legal and compliance;
* risk management;
* quality assurance;
* product management;
* operations;
* human-factors specialists; and
* internal assurance functions.

16. **Single Documentation Accountability**
    Although many teams may contribute information, accountability for the completeness and integrity of the overall documentation package should be clearly assigned.

17. **AI-TD-01 — Technical Documentation Governance**
    The organization should establish a documented governance process defining:

* documentation requirements;
* accountable owner;
* contributors;
* approval authority;
* version control;
* change triggers;
* review frequency;
* evidence standards;
* retention requirements; and
* access controls.

18. **Documentation Classification by AI Risk**
    Documentation requirements should be proportional to the AI system's regulatory classification and risk. High-risk AI systems generally require substantially more structured evidence than low-risk applications.

19. **High-Risk Technical Documentation**
    For high-risk AI systems, technical documentation is a central component of the provider's conformity and compliance framework. The documentation should address the applicable information required under the EU AI Act and its relevant annexes.

20. **AI-TD-02 — High-Risk Documentation Control**
    Organizations providing high-risk AI systems should establish a dedicated technical-documentation control ensuring that required documentation is complete, reviewed, approved, maintained, and available to authorized parties.

21. **GPAI Documentation Distinction**
    General-purpose AI models are subject to their own documentation requirements. Documentation for a GPAI model should not automatically be treated as equivalent to technical documentation for a downstream high-risk AI system incorporating that model.

22. **GPAI Provider Documentation**
    Where applicable, GPAI providers must maintain documentation concerning the model and provide relevant information to downstream providers. The documentation framework should therefore distinguish model-level evidence from system-level evidence.

23. **Downstream AI System Documentation**
    An organization integrating a third-party model into a larger AI system should maintain sufficient documentation for the resulting system. Upstream provider documentation may support this obligation but may not cover downstream architecture, configuration, intended purpose, deployment environment, human oversight, or system-specific risks.

24. **AI-TD-03 — Upstream Documentation Integration**
    Organizations using third-party AI components should establish controls for receiving, evaluating, versioning, and incorporating relevant supplier documentation into the system's controlled documentation package.

25. **Provider and Deployer Documentation Responsibilities**
    The EU AI Act distinguishes responsibilities among providers and deployers. The organization should therefore avoid assuming that all documentation obligations can be transferred to the provider or that provider documentation eliminates downstream governance responsibilities.

26. **Importer and Distributor Documentation Interface**
    Importers and distributors may have verification and documentation-related responsibilities for applicable AI systems. Their records should be capable of demonstrating that required documentation was available and appropriately verified where applicable.

27. **Documentation as Supply-Chain Evidence**
    For AI systems obtained from external providers, documentation should form part of supplier due diligence and supply-chain governance. Missing or inconsistent technical documentation can be an indicator of elevated compliance risk.

28. **AI-TD-04 — Supplier Documentation Due Diligence**
    Organizations should assess whether providers supply the documentation necessary to support the organization's applicable regulatory responsibilities before approving material AI systems.

29. **Documentation Before Market Availability**
    For systems subject to pre-market compliance requirements, documentation should be sufficiently complete before the applicable market-placement or conformity process is completed.

30. **Documentation Before Deployment**
    For internal deployment, the organization should establish a risk-based documentation gate ensuring that critical technical, security, privacy, human-oversight, and compliance information is available before production use.

31. **AI-TD-05 — Documentation Readiness Gate**
    A documentation readiness gate should identify mandatory documentation elements and prevent approval of applicable AI systems when material documentation deficiencies remain unresolved.

32. **Documentation and Conformity Assessment**
    Technical documentation supports conformity assessment by providing evidence that the provider has addressed applicable regulatory requirements. Documentation should therefore be designed with conformity-assessment needs in mind where a conformity assessment is required.

33. **Documentation and Declaration of Conformity**
    Where an EU declaration of conformity is required, the underlying documentation should support the assertions made in that declaration. The declaration should not be treated as a substitute for the supporting technical evidence.

34. **Documentation and CE Marking**
    Where CE marking is applicable, the technical documentation should support the conformity basis underlying the marking. An organization should not infer compliance merely from the presence of a CE mark.

35. **Documentation and Registration**
    Where registration requirements apply, the technical documentation should be consistent with the information submitted or maintained through applicable regulatory registration processes.

36. **AI-TD-06 — Conformity Evidence Linkage**
    The organization should establish a linkage between technical documentation, conformity assessment records, declaration of conformity, registration information, and the actual AI system version.

37. **Documentation and Intended Purpose**
    Intended purpose is a critical documentation attribute because regulatory classification and applicable obligations may depend on how an AI system is intended to be used.

38. **AI-TD-07 — Intended-Purpose Documentation**
    The technical documentation should clearly define the intended purpose, relevant users, operating environment, affected persons or groups where relevant, expected outputs, and material use limitations.

39. **Foreseeable Misuse Documentation**
    Where relevant to risk management, documentation should identify reasonably foreseeable misuse and explain controls intended to prevent or mitigate associated risks.

40. **Documentation of System Boundaries**
    The documentation should define the boundaries of the AI system, including relevant interfaces, dependencies, external models, APIs, data sources, software components, infrastructure, and human processes.

41. **AI-TD-08 — System Boundary Control**
    The organization should maintain a documented system boundary identifying which components are inside the regulated AI system and which are external dependencies.

42. **Architecture Documentation**
    Technical documentation should describe the system architecture at an appropriate level of detail. Depending on system complexity, this may include:

* logical architecture;
* physical or deployment architecture;
* model architecture;
* data flows;
* interfaces;
* APIs;
* dependencies;
* infrastructure;
* security boundaries; and
* human interaction points.

43. **AI-TD-09 — Architecture Documentation Control**
    Architecture diagrams and descriptions should be version-controlled and updated following material architectural changes.

44. **Model Documentation**
    Where machine-learning or other model-based components are used, documentation should describe relevant model characteristics, development methodology, model type, major parameters, training approach, evaluation approach, and known limitations to the extent applicable.

45. **AI-TD-10 — Model Documentation Control**
    Model documentation should identify the model version and maintain traceability to the corresponding model artifact, development records, evaluation results, and production deployment.

46. **Model Version Identification**
    A model identifier should uniquely distinguish materially different versions. Version information should be linked to the AI system release and associated documentation.

47. **AI-TD-11 — Model-to-System Traceability**
    The organization should maintain a traceability relationship between model versions and the AI systems, products, configurations, or deployments in which they are used.

48. **Data Documentation**
    Technical documentation should describe relevant data used in the development and operation of the AI system. Depending on applicability, this may include data sources, acquisition methods, characteristics, preprocessing, labeling, representativeness, quality controls, and limitations.

49. **AI-TD-12 — Data Documentation Control**
    The organization should document material datasets and data-processing activities sufficiently to demonstrate how data quality and suitability were addressed.

50. **Training Data Documentation**
    Where training data is relevant, documentation should describe the principal characteristics of training data and the processes used to prepare, govern, and validate it.

51. **Validation and Testing Data Documentation**
    Validation and test datasets should be distinguishable from training data where applicable. Documentation should identify their purpose, characteristics, methodology, and relationship to the evaluation process.

52. **Data Provenance**
    Where feasible and appropriate, data provenance should identify the source and lineage of material datasets and transformations.

53. **AI-TD-13 — Data Lineage Documentation**
    Data lineage should enable reviewers to understand how material data moved from source through processing, preparation, model development, testing, and deployment.

54. **Data Quality Documentation**
    Documentation should describe relevant data-quality characteristics, including accuracy, completeness, relevance, representativeness, consistency, and known limitations, where applicable to the AI system.

55. **Bias and Data Limitations Documentation**
    Where relevant, technical documentation should identify known data limitations, potential biases, coverage gaps, demographic limitations, and other factors that could affect system performance or regulatory risk.

56. **AI-TD-14 — Data Limitation Disclosure**
    Material data limitations should be documented together with the associated risk assessment and mitigation measures.

57. **Data Governance Evidence**
    Technical documentation should link relevant data governance controls to supporting evidence such as data-quality assessments, dataset approval records, lineage records, validation results, and access controls.

58. **Documentation of Development Process**
    The documentation should describe the development methodology sufficiently to establish how the AI system was designed, implemented, tested, and approved.

59. **AI-TD-15 — Development Lifecycle Documentation**
    The organization should document material development lifecycle stages, including requirements, design, implementation, testing, validation, release, and approval.

60. **Requirements Traceability**
    Material AI requirements should be traceable from business and regulatory requirements through system design, implementation, verification, and release evidence.

61. **AI-TD-16 — Requirements-to-Evidence Traceability**
    The organization should maintain a traceability mechanism connecting applicable requirements to controls, implementation elements, test cases, results, and approval evidence.

62. **Design Decisions**
    Material design decisions affecting AI behavior, safety, security, privacy, performance, human oversight, or compliance should be documented together with their rationale.

63. **AI-TD-17 — Design Decision Records**
    Material architectural and model-design decisions should have controlled decision records identifying the decision, alternatives considered where appropriate, rationale, owner, date, and affected components.

64. **Technical Assumptions**
    Documentation should identify material assumptions underlying system design, data quality, performance, operating conditions, user behavior, infrastructure, and security.

65. **AI-TD-18 — Assumption Management**
    Material assumptions should be periodically reviewed and reassessed when operational conditions change.

66. **System Limitations**
    The technical documentation should identify known limitations that could affect performance, reliability, safety, security, privacy, fairness, or appropriate use.

67. **AI-TD-19 — Limitation Register**
    Material limitations should be maintained in a controlled register linked to risk assessments, mitigations, user instructions, monitoring controls, and relevant test evidence.

68. **Performance Documentation**
    Documentation should identify relevant performance characteristics and evaluation methodology appropriate to the AI system's intended purpose.

69. **AI-TD-20 — Performance Evidence Control**
    Performance claims should be supported by documented test methods, datasets, metrics, thresholds, results, and evaluation dates.

70. **Accuracy Documentation**
    Where accuracy is a relevant system characteristic, documentation should identify the applicable accuracy metrics, evaluation conditions, limitations, and acceptance criteria.

71. **Robustness Documentation**
    Documentation should address relevant robustness characteristics, including behavior under expected variation, degraded conditions, adversarial conditions, or other foreseeable operating challenges.

72. **AI-TD-21 — Robustness Evidence**
    Robustness claims should be supported by documented testing and evidence appropriate to the system's risk and intended purpose.

73. **Cybersecurity Documentation**
    Technical documentation should include or reference applicable cybersecurity controls and evidence, including security architecture, threat analysis, vulnerability management, secure development, access controls, integrity protections, and security testing where relevant.

74. **AI-TD-22 — Cybersecurity Documentation Control**
    The organization should maintain traceable cybersecurity documentation demonstrating how relevant AI-specific and general cybersecurity risks were identified and addressed.

75. **Threat Model Documentation**
    Where appropriate, the system should have a documented threat model covering threats to confidentiality, integrity, availability, model behavior, data, interfaces, dependencies, and supply-chain components.

76. **AI-TD-23 — Threat Model Traceability**
    Threats identified through security analysis should be traceable to mitigations, implementation controls, test results, and residual-risk decisions.

77. **Adversarial Testing Documentation**
    Where relevant to the AI system, adversarial testing should be documented, including the scope, threat scenarios, methodology, findings, mitigations, and retesting results.

78. **AI-TD-24 — Security Test Evidence**
    Security testing evidence should be associated with the applicable system and version and should remain retrievable throughout the relevant lifecycle.

79. **Human Oversight Documentation**
    Where human oversight is required or relevant, technical documentation should explain the human-oversight mechanisms, responsibilities, intervention capabilities, limitations, escalation paths, and operating conditions.

80. **AI-TD-25 — Human Oversight Documentation Control**
    Human-oversight requirements should be documented and linked to system functionality, user instructions, training, monitoring, and validation evidence.

81. **Human Intervention Capability**
    Documentation should explain how authorized humans can interpret, intervene in, override, or stop system operation where applicable.

82. **Automation Bias Documentation**
    Where reliance on AI outputs could create automation bias or inappropriate human deference, documentation should identify the relevant risk and associated mitigation measures.

83. **AI-TD-26 — Human Decision Control Documentation**
    Where AI outputs support consequential decisions, documentation should identify the intended role of the human decision-maker and the boundaries of permissible reliance on AI outputs.

84. **Transparency Documentation**
    Where transparency obligations apply, technical documentation should identify the mechanisms used to provide required disclosures, notices, labeling, or other transparency measures.

85. **AI-TD-27 — Transparency Evidence Linkage**
    Transparency controls should be linked to relevant system functionality, user interfaces, generated-content mechanisms, configuration settings, and test evidence.

86. **Logging Documentation**
    Where logging requirements apply, documentation should describe the logging architecture, relevant events, retention arrangements, access controls, integrity protections, and monitoring processes.

87. **AI-TD-28 — Logging Documentation Control**
    Logging documentation should identify which events are recorded, where records are stored, how integrity is protected, and how authorized personnel retrieve relevant records.

88. **Monitoring Documentation**
    The documentation should describe applicable post-deployment monitoring mechanisms, performance monitoring, drift detection, incident monitoring, and corrective-action processes.

89. **AI-TD-29 — Monitoring Documentation Control**
    Monitoring controls should be documented with their objectives, metrics, thresholds, alerting mechanisms, responsible owners, and escalation procedures.

90. **Change Management Documentation**
    Material changes to the AI system should generate corresponding documentation updates.

91. **AI-TD-30 — Change-to-Documentation Control**
    The organization's change-management process should require an assessment of whether technical documentation, risk assessments, test evidence, user instructions, conformity records, or other compliance artifacts must be updated.

92. **Configuration Documentation**
    Where configuration affects system behavior or compliance, approved configurations should be documented and version-controlled.

93. **AI-TD-31 — Configuration Baseline Documentation**
    Production configuration baselines should be linked to the corresponding system version and technical documentation.

94. **Dependency Documentation**
    The technical documentation should identify material dependencies such as:

* third-party models;
* libraries;
* APIs;
* cloud platforms;
* datasets;
* hardware;
* identity services;
* security services; and
* external processing components.

95. **AI-TD-32 — Dependency Inventory**
    Material dependencies should be maintained in a controlled inventory with ownership, version information, supplier information, and relevant risk attributes.

96. **Third-Party Component Documentation**
    Documentation for third-party AI or software components should be retained and linked to the system that uses them.

97. **AI-TD-33 — Third-Party Documentation Linkage**
    The organization should maintain traceability between supplier documentation and the internal AI system, including relevant versions and configurations.

98. **Open-Source Component Documentation**
    Where open-source software, models, datasets, or other components are used, relevant licenses, provenance, versions, restrictions, and security considerations should be documented.

99. **AI-TD-34 — Open-Source Evidence Control**
    Material open-source dependencies should be identified and linked to appropriate license, security, provenance, and compliance records.

100. **Documentation of Interfaces**
     Technical documentation should describe interfaces between the AI system and other systems, including APIs, data exchanges, identity mechanisms, human interfaces, and external services where relevant.

101. **AI-TD-35 — Interface Documentation Control**
     Material interfaces should be documented and updated when interface behavior, security boundaries, data flows, or dependencies change.

102. **Deployment Environment Documentation**
     The documentation should identify relevant deployment environments and infrastructure characteristics necessary to understand system operation and associated risks.

103. **AI-TD-36 — Deployment Documentation**
     Deployment architecture, environments, infrastructure dependencies, and material configuration characteristics should be documented and version-controlled.

104. **Operational Constraints**
     Technical documentation should identify material operational constraints such as hardware requirements, environmental conditions, supported configurations, processing limitations, latency requirements, or resource dependencies.

105. **AI-TD-37 — Operational Constraint Control**
     Operational constraints should be linked to deployment procedures, user instructions, monitoring controls, and risk assessments.

106. **Documentation of Intended Users**
     The documentation should identify intended user categories and relevant assumptions about their technical competence, authorization, training, or responsibilities.

107. **AI-TD-38 — User Profile Documentation**
     User profiles should be documented where they materially affect safe, secure, compliant, or effective use of the AI system.

108. **Affected Persons and Groups**
     Where relevant, documentation should identify categories of persons or groups potentially affected by the system and associated risk considerations.

109. **AI-TD-39 — Affected-Person Risk Documentation**
     Material risks affecting individuals or groups should be linked to relevant design controls, testing, human oversight, transparency, and monitoring measures.

110. **Documentation of Regulatory Classification**
     Technical documentation should identify the organization's determination of the applicable AI Act classification and the rationale supporting that determination.

111. **AI-TD-40 — Classification Evidence Control**
     Classification should be supported by documented intended purpose, system characteristics, applicable legal provisions, risk analysis, and approval.

112. **Classification Change Monitoring**
     A material change to intended purpose, functionality, deployment context, or applicable regulation should trigger reassessment of classification.

113. **AI-TD-41 — Classification-to-Documentation Update**
     When classification changes, the organization should assess and update affected technical documentation and compliance records.

114. **Documentation of Applicable Requirements**
     The documentation framework should identify the regulatory and internal requirements applicable to the AI system.

115. **AI-TD-42 — Requirement Register Linkage**
     Applicable requirements should be linked to technical controls, evidence, responsible owners, and relevant documentation sections.

116. **Fundamental-Rights Considerations**
     Where applicable, technical documentation should identify relevant fundamental-rights risks and controls associated with the AI system's intended purpose and deployment.

117. **AI-TD-43 — Fundamental-Rights Evidence**
     Material fundamental-rights assessments and mitigation measures should be linked to the technical documentation where relevant.

118. **Privacy Documentation**
     Where personal data is processed, relevant privacy considerations should be documented and linked to applicable privacy governance records.

119. **AI-TD-44 — Privacy Documentation Linkage**
     Privacy impact assessments, data-protection analyses, data-processing records, and relevant controls should be cross-referenced with the AI system documentation where appropriate.

120. **Security and Privacy Boundary**
     Security and privacy documentation should remain connected to technical documentation while retaining their respective governance ownership and legal distinctions.

121. **Quality Management Integration**
     Where a quality management system is required or established, technical documentation should integrate with applicable quality processes without duplicating or contradicting controlled quality records.

122. **AI-TD-45 — QMS Documentation Integration**
     Technical documentation should be mapped to relevant quality-management procedures, approvals, nonconformities, corrective actions, and change records.

123. **Documentation Review**
     Technical documentation should undergo appropriate review before release and after material changes.

124. **AI-TD-46 — Documentation Review Control**
     Review should confirm, as applicable:

* completeness;
* accuracy;
* consistency;
* traceability;
* regulatory alignment;
* version correctness;
* evidence availability; and
* approval status.

125. **Independent Documentation Review**
     For high-risk or otherwise material AI systems, an independent review by a qualified function may be appropriate to challenge completeness and accuracy before conformity or release decisions.

126. **Documentation Approval**
     Material technical documentation should have formal approval by authorized personnel before being treated as the authoritative compliance record.

127. **AI-TD-47 — Documentation Approval Control**
     Approval records should identify the approver, date, documentation version, affected AI system, and scope of approval.

128. **Version Control**
     Technical documentation should use controlled versioning to distinguish revisions and preserve historical versions where required.

129. **AI-TD-48 — Documentation Version Control**
     Each documentation package should have a unique version identifier and revision history.

130. **Change History**
     The documentation package should record material changes, including what changed, why it changed, who approved the change, and which AI system version is affected.

131. **AI-TD-49 — Documentation Change Log**
     A controlled change log should be maintained for material documentation changes and linked to the corresponding system or configuration change.

132. **Consistency Across Documentation**
     Information should remain consistent across technical documentation, user instructions, conformity records, declarations, registration information, supplier documentation, product records, and GRC records.

133. **AI-TD-50 — Cross-Document Consistency Control**
     The organization should periodically reconcile material system attributes across controlled documentation sources.

134. **Documentation Discrepancy Management**
     Conflicting information should be investigated and resolved rather than allowing multiple authoritative versions to coexist.

135. **AI-TD-51 — Documentation Discrepancy Control**
     Material documentation discrepancies should generate tracked issues with an accountable owner, risk assessment, resolution, and validation.

136. **Documentation Access Control**
     Technical documentation should be accessible to authorized personnel who require it for compliance, engineering, security, quality, operations, audit, or regulatory activities.

137. **AI-TD-52 — Documentation Access Control**
     Access should be based on role and business need, with stronger restrictions applied to sensitive technical, security, proprietary, or personal information.

138. **Documentation Confidentiality**
     Technical documentation may contain commercially sensitive information, security architecture, proprietary algorithms, source references, data characteristics, or other confidential material. Appropriate confidentiality controls should therefore be implemented.

139. **Documentation Integrity**
     Technical documentation should be protected against unauthorized modification because inaccurate records can undermine regulatory compliance and assurance.

140. **AI-TD-53 — Documentation Integrity Control**
     Controlled repositories should provide appropriate access controls, audit trails, version history, and integrity mechanisms.

141. **Documentation Availability**
     Required documentation should remain available to authorized stakeholders throughout the applicable retention period.

142. **AI-TD-54 — Documentation Availability Control**
     Organizations should implement backup, recovery, redundancy, and continuity controls appropriate to the criticality of technical documentation.

143. **Documentation Retention**
     Technical documentation should be retained for the period required by applicable law and organizational policy. Retention requirements should be determined based on the relevant AI system classification and regulatory provisions.

144. **AI-TD-55 — Documentation Retention Control**
     The organization should define retention periods for technical documentation and ensure that disposal processes do not remove records that remain subject to legal, regulatory, audit, investigation, or contractual preservation requirements.

145. **Documentation Retrieval**
     Authorized personnel should be able to retrieve the relevant documentation package without relying on individual employee memory or undocumented locations.

146. **AI-TD-56 — Documentation Retrieval Control**
     The organization should periodically test whether a complete documentation package can be retrieved for a selected AI system within an appropriate timeframe.

147. **Regulatory Evidence Package**
     For material AI systems, the organization should be capable of assembling a coherent evidence package containing the applicable technical documentation, conformity records, risk records, testing evidence, system versions, and relevant lifecycle records.

148. **AI-TD-57 — Regulatory Evidence Assembly**
     A controlled process should define how technical documentation is assembled and validated when requested by authorized regulatory or assurance functions.

149. **Documentation and Auditability**
     Technical documentation should enable auditors and assurance functions to trace material assertions to objective evidence without requiring uncontrolled reconstruction of historical events.

150. **AI-TD-58 — Audit Traceability**
     The organization should maintain sufficient documentation traceability to reconstruct material design, compliance, security, testing, approval, and change decisions.

151. **Documentation and Incident Management**
     Material incidents may require updates to technical documentation when investigations reveal previously undocumented risks, system characteristics, limitations, dependencies, or control weaknesses.

152. **AI-TD-59 — Incident-to-Documentation Update**
     Incident management should include a determination of whether technical documentation must be corrected or updated following a material incident.

153. **Documentation and Corrective Actions**
     Corrective actions affecting the AI system should be reflected in the appropriate technical documentation and linked to the relevant remediation evidence.

154. **AI-TD-60 — Corrective-Action Documentation Linkage**
     Corrective-action records should identify affected documentation and confirm when required updates have been completed and validated.

155. **Documentation and Post-Market Monitoring**
     Post-market monitoring should feed material findings back into technical documentation where those findings change the understanding of system performance, limitations, risks, incidents, or controls.

156. **AI-TD-61 — Monitoring-to-Documentation Feedback**
     Material monitoring results should trigger documentation review where they indicate a change to documented system characteristics or risks.

157. **Documentation and Model Drift**
     Where model or data drift can materially affect documented performance or limitations, monitoring processes should trigger reassessment and documentation updates.

158. **AI-TD-62 — Drift Documentation Control**
     Material drift findings should be linked to affected model versions, performance evidence, risk assessments, and documentation revisions.

159. **Documentation and Cybersecurity Vulnerabilities**
     Material cybersecurity vulnerabilities may require updates to system architecture descriptions, threat models, security controls, risk assessments, and operational limitations.

160. **AI-TD-63 — Vulnerability-to-Documentation Control**
     Material vulnerabilities should trigger assessment of whether technical documentation requires correction or additional security information.

161. **Documentation and Regulatory Change**
     Changes in applicable legislation, guidance, standards, or authoritative interpretations may require changes to the documentation structure or content.

162. **AI-TD-64 — Regulatory Change Documentation Review**
     Regulatory-change management should identify technical documentation affected by new or amended requirements and assign controlled remediation.

163. **Documentation and Organizational Change**
     Changes in provider, ownership, organizational responsibility, outsourcing arrangements, or supply-chain structure may require documentation updates.

164. **AI-TD-65 — Organizational Change Documentation Control**
     Material organizational or supplier changes should trigger assessment of documentation ownership, contact information, system boundaries, dependencies, and accountability.

165. **Documentation Quality Metrics**
     Organizations should monitor documentation quality using metrics such as:

* completeness;
* accuracy;
* currency;
* overdue reviews;
* unresolved discrepancies;
* missing evidence;
* documentation defects;
* version mismatches; and
* retrieval performance.

166. **AI-TD-66 — Documentation Quality Monitoring**
     Documentation quality metrics should be incorporated into appropriate AI governance or GRC reporting.

167. **Documentation Risk Indicators**
     KRIs may include increasing documentation gaps, outdated system descriptions, repeated version mismatches, missing supplier evidence, overdue reviews, or inability to retrieve required records.

168. **AI-TD-67 — Documentation KRI Monitoring**
     Material documentation risk indicators should trigger investigation and remediation according to predefined thresholds.

169. **Documentation Exceptions**
     Where required documentation cannot be completed within the expected timeframe, the deficiency should be formally recorded rather than silently accepted.

170. **AI-TD-68 — Documentation Exception Management**
     Exceptions should identify the missing element, affected AI system, reason, risk, compensating measures where appropriate, accountable owner, approval authority, and remediation deadline.

171. **Documentation Nonconformity**
     A documentation deficiency may constitute a control failure even when the underlying technical system appears to operate correctly, because inability to demonstrate compliance can itself create regulatory and assurance exposure.

172. **AI-TD-69 — Documentation Nonconformity Control**
     Material documentation nonconformities should enter the organization's corrective-action process and should be tracked through validated closure.

173. **Documentation and Three Lines**
     Technical documentation should be subject to appropriate first-line ownership, second-line challenge, and third-line independent assurance according to risk.

174. **First-Line Documentation Responsibility**
     Engineering, product, operations, and other first-line functions should create and maintain the technical information generated through system development and operation.

175. **Second-Line Documentation Oversight**
     Compliance, risk, security, privacy, quality, and other second-line functions should challenge whether documentation adequately supports applicable obligations and risks.

176. **Third-Line Documentation Assurance**
     Internal Audit should independently assess documentation governance and effectiveness where the risk-based audit plan identifies it as material.

177. **AI-TD-70 — Three-Lines Documentation Assurance**
     The organization should periodically assess whether documentation responsibilities and assurance activities operate effectively across the Three Lines.

178. **Documentation Training**
     Personnel responsible for preparing or reviewing technical documentation should receive role-appropriate training on documentation standards, regulatory requirements, evidence quality, version control, and secure handling.

# Part 3 — Documentation Governance, Accountability, Risk Management, and Assurance

521. **Technical Documentation Governance Model**
     Technical documentation should operate within the organization's AI governance framework, with defined accountability for creation, review, approval, maintenance, security, retention, and assurance.

     For material AI systems, the organization should define a documentation governance charter establishing scope, objectives, responsibilities, decision rights, escalation mechanisms, and assurance expectations.

     Accountability for technical documentation should remain clearly assigned even when individual documentation activities are distributed among engineering, security, compliance, suppliers, or other functions.

524. **AI-TD-353 — Documentation Accountability Matrix**
     The organization should maintain an accountability matrix identifying responsible and accountable parties for each major documentation domain.

     A RACI model should distinguish responsibility for producing information from accountability for the integrity of the final technical documentation package.

     The RACI should cover, as applicable:

* system description;
* architecture;
* model;
* data;
* risk;
* testing;
* cybersecurity;
* privacy;
* human oversight;
* conformity;
* monitoring;
* incidents; and
* change management.

527. **Documentation Governance Committee**
     Organizations with significant AI portfolios should assign technical-documentation oversight to an AI governance committee, technology-risk committee, quality committee, or another appropriate governance body.

528. **AI-TD-355 — Governance Committee Oversight**
     The designated committee should periodically review material documentation deficiencies, high-risk systems, unresolved documentation risks, significant changes, and assurance findings.

529. **Executive Responsibility**
     Senior management should understand whether the organization can demonstrate the technical and regulatory characteristics of material AI systems.

530. **AI-TD-356 — Executive Documentation Reporting**
     Management reporting should include material documentation gaps, overdue reviews, significant discrepancies, high-risk documentation deficiencies, regulatory requests, and remediation status.

532. **AI-TD-357 — Board-Level Documentation Reporting**
     Board or board-committee reporting should focus on material documentation risks rather than operational document-management statistics alone.

533. **Three Lines of Documentation Governance**
     Technical-documentation governance should align with the Three Lines Model.

534. **AI-TD-358 — First-Line Documentation Responsibility**
     Engineering, product, operations, and other first-line functions should create and maintain the technical information generated through system development and operation.

535. **AI-TD-359 — Second-Line Documentation Oversight**
     Risk, compliance, security, privacy, quality, and other oversight functions should challenge whether documentation sufficiently supports applicable requirements and risks.

536. **AI-TD-360 — Third-Line Documentation Assurance**
     Internal Audit should independently evaluate documentation governance and control effectiveness where included within the risk-based audit plan.

537. **Segregation of Duties**
     Where documentation has material regulatory significance, preparation, technical review, compliance review, and final approval should be appropriately separated.

538. **AI-TD-361 — Documentation SoD Control**
     The organization should identify documentation activities requiring segregation of duties and implement appropriate workflow restrictions.

539. **Documentation Control Ownership**
     Every material documentation control should have a named owner responsible for execution and evidence.

     Control ownership records should identify:

* control objective;
* control owner;
* frequency;
* evidence;
* testing method;
* escalation threshold; and

     Organizations should establish an appropriate tolerance for documentation risk. Zero tolerance may be appropriate for certain legally mandatory records or critical compliance evidence, while other documentation deficiencies may be risk-managed.

542. **AI-TD-363 — Documentation Risk Appetite**
     Risk appetite should distinguish between:

* mandatory regulatory documentation;
* critical safety or security evidence;
* material supporting evidence;
* operational documentation; and
* discretionary documentation.

     Documentation risks should identify the affected AI system, deficiency, consequence, likelihood, risk owner, treatment, target date, and residual risk.

     Documentation risks may include:

* incomplete information;
* inaccurate information;
* stale information;
* inconsistent information;
* missing evidence;
* incorrect version association;
* unauthorized modification;
* unavailable records;
* inadequate retention;
* supplier documentation failure; and

546. **AI-TD-365 — Documentation Risk Classification**
     The organization should classify documentation risks using standardized severity criteria.

     Risk scoring should consider the impact of documentation failure on regulatory compliance, safety, security, privacy, fundamental rights, operational continuity, and auditability.

     High-impact deficiencies should receive priority remediation and appropriate management escalation.

     Treatment options may include:

* remediation;
* additional evidence collection;
* enhanced review;

550. **AI-TD-367 — Documentation Risk Treatment Control**
     Risk treatment decisions should be documented and approved by the appropriate authority.

     Exceptions should have:

970. **AI-TD-699 — Technical Documentation Lifecycle Control**
     The organization should maintain controlled technical documentation throughout the complete AI lifecycle, from requirements and design through development, validation, deployment, operation, change, incident response, regulatory review, and retirement.

971. **AI-TD-700 — End-to-End Technical Documentation Assurance**
     The organization should maintain demonstrable assurance that material AI technical documentation is complete, accurate, current, version-aligned, traceable, protected, retrievable, appropriately approved, and capable of supporting regulatory, governance, operational, security, privacy, safety, and audit requirements throughout the AI system lifecycle.
