# 18.07 — AI Security Metrics

## Part 1 — AI Security Metric Foundations, Measurement Principles, Governance and Interpretation

### 1. Definition of AI Security Metrics

AI security metrics are defined measurements used to evaluate the security condition, security control performance, security exposure, and security outcomes associated with AI systems.

AI security metrics may measure:

* AI attack activity
* Security-control coverage
* Vulnerability exposure
* Model security
* Data security
* Identity and access security
* API security
* Prompt-injection activity
* Adversarial activity
* Security incidents
* Detection capability
* Response capability
* Security configuration
* Security testing
* Security remediation
* Security resilience

AI security metrics should be selected according to the AI system's architecture, threat model, attack surface, business context, and security objectives.

**AI security metric ≠ Complete AI security assurance.**

A metric measures a defined security condition. It does not automatically establish that all security risks have been identified or controlled.

---

### 2. Purpose of AI Security Metrics

The purpose of AI security metrics is to provide measurable information about the security condition of AI systems and the effectiveness of security-related activities and controls.

AI security metrics may support:

* Security governance
* AI risk management
* Security operations
* Model security
* Application security
* Cloud security
* Data security
* Identity governance
* Incident management
* Vulnerability management
* Security testing
* Supplier assurance
* Executive reporting
* Board oversight
* Continuous improvement

Metrics should be connected to decisions.

A metric that is collected but does not support investigation, prioritization, remediation, escalation, or assurance may have limited governance value.

---

### 3. AI Security Metric vs KPI

An AI security metric is a measurement.

A KPI is a metric selected because it is particularly important to an organizational objective.

For example:

> Percentage of AI systems with security monitoring enabled

is an AI security metric.

An organization may designate:

> Security monitoring coverage of critical production AI systems

as an AI security KPI.

Therefore:

**AI security metric ≠ KPI automatically.**

A metric becomes a KPI when it is formally designated as a key performance indicator.

---

### 4. AI Security Metric vs KRI

A KRI provides an indication of changing risk exposure.

An AI security metric may measure a specific security condition without directly representing the broader risk.

For example:

* Number of exposed AI endpoints = security metric
* Percentage of critical AI endpoints exposed = potential KRI
* Number of unresolved critical AI vulnerabilities = security metric
* AI cyber-risk exposure exceeding approved tolerance = potential KRI

The distinction is important because a technical measurement may contribute to risk analysis without itself being the complete risk indicator.

**Security measurement ≠ Risk measurement automatically.**

---

### 5. AI Security Metric vs Control

A control is a measure designed to prevent, detect, respond to, or reduce a risk.

An AI security metric measures a condition associated with that control or risk.

For example:

> 98% of AI workloads have MFA enabled

is a metric.

The control may be:

> Require strong authentication for privileged access to AI systems.

The metric provides evidence about implementation or coverage.

It is not the control itself.

---

### 6. AI Security Metric vs Control Objective

A control objective describes the security condition a control is intended to achieve.

For example:

> Unauthorized users should not gain access to production AI systems.

Potential metrics include:

* Percentage of privileged accounts using MFA
* Number of unauthorized access attempts
* Number of privileged accounts without MFA
* Mean time to revoke access

The control objective establishes the desired condition.

The metrics measure relevant aspects of that condition.

---

### 7. AI Security Metric vs Target

A target establishes a desired performance or security level.

For example:

> Target: 100% of critical AI systems have centralized security logging.

The observed metric may be:

> Actual coverage: 94%.

The metric represents the observed condition.

The target represents the desired condition.

**Metric ≠ Target.**

An internal security target should not be represented as a legal or regulatory requirement unless an applicable authoritative source establishes it.

---

### 8. AI Security Metric vs Threshold

A threshold establishes a boundary at which a defined governance action may occur.

For example:

> More than five critical AI vulnerabilities open for longer than 30 days triggers escalation.

The number of vulnerabilities is the metric.

The five-vulnerability boundary is the threshold.

**Metric ≠ Threshold.**

Thresholds are generally internal governance mechanisms unless an applicable external requirement establishes a specific threshold.

---

### 9. AI Security Measurement Scope

Measurement scope defines the AI security population and conditions covered by the metric.

Scope may include:

* AI systems
* Models
* Agents
* Applications
* APIs
* Data stores
* Cloud environments
* Suppliers
* Business units
* Geographic regions
* Production environments
* Development environments

A security metric without a defined scope can be misleading.

For example:

> “90% of AI systems are monitored”

requires clarification of:

* Which AI systems?
* Which environments?
* Which monitoring capabilities?
* Which time period?
* Which definition of monitoring?

### 14. AI Security Metric Definition

Each material AI security metric should have a precise definition.

The definition should identify:

* What is measured
* Why it is measured
* Population
* Unit
* Formula
* Data source
* Measurement period
* Inclusion criteria
* Exclusion criteria

For example:

> Critical AI vulnerability remediation rate = number of critical AI vulnerabilities remediated within the approved remediation period divided by the total number of critical AI vulnerabilities subject to the measurement period.

A precise definition supports reproducibility.

---

### 15. AI Security Metric Formula

Where applicable, the calculation formula should be documented.

For example:

\[
Security\ Coverage = \frac{AI\ Systems\ With\ Required\ Security\ Control}{AI\ Systems\ Within\ Scope} \times 100
\]

Another example:

\[
MTTD = \frac{\sum Detection\ Time - Event\ Occurrence\ Time}{Number\ of\ Detected\ Events}
\]

The formula should be accompanied by definitions for:

* Population
* Numerator
* Denominator
* Time period
* Classification rules

A mathematically correct formula can still produce a misleading result if the underlying population is incorrect.

---

### 16. AI Security Metric Numerator

The numerator represents the number of observations satisfying the defined metric condition.

For example:

> Number of critical AI systems with centralized security monitoring.

The numerator should be:

* Clearly defined
* Traceable
* Reproducible
* Consistent
* Validated

An incorrect numerator can distort the reported security condition.

---

### 17. AI Security Metric Denominator

The denominator defines the population against which the numerator is measured.

For example:

\[
Coverage = \frac{Systems\ Monitored}{Systems\ In\ Scope}
\]

The denominator might include:

* Production AI systems
* Critical AI systems
* Registered models
* AI APIs
* AI suppliers

Denominator integrity is critical.

**Denominator reduction ≠ Security improvement automatically.**

Removing systems from the denominator can increase a coverage percentage without improving actual security.

---

### 18. AI Security Metric Population

The population is the complete set of entities or events to which the metric applies.

Population may include:

* All production AI systems
* All critical models
* All AI APIs
* All privileged AI identities
* All AI security incidents
* All open vulnerabilities

Population definitions should be consistent with the intended security objective.

---

### 19. AI Security Metric Inclusion Criteria

Inclusion criteria identify which observations belong to the metric population.

Examples include:

* Production systems
* Critical models
* Internet-facing AI APIs
* Active suppliers
* Confirmed security incidents
* Vulnerabilities above a defined severity

Inclusion criteria should be documented and controlled.

---

### 20. AI Security Metric Exclusion Criteria

Exclusion criteria identify observations intentionally excluded.

Potential exclusions include:

* Retired systems
* Approved test environments
* Duplicate records
* Out-of-scope suppliers
* False-positive security events
* Non-production assets

Exclusions should be justified.

Uncontrolled exclusions can artificially improve reported security performance.

---

### 21. AI Security Measurement Period

The measurement period establishes when the measured security condition occurred.

Examples include:

* Real-time
* Daily
* Weekly
* Monthly
* Quarterly
* Incident-specific
* Assessment-specific

The period should be clearly stated in reporting.

A monthly security metric should not be compared directly with a quarterly metric without normalization and contextual interpretation.

### 26. AI Security Threshold

A threshold establishes a boundary that may trigger investigation or escalation.

Examples include:

* Critical vulnerability aging
* Excessive failed authentication

### 27. AI Security Tolerance

Tolerance defines an acceptable range of variation around a desired security condition.

For example:

> Security telemetry coverage target = 100%

> Approved tolerance = 98–100%

Tolerance should reflect:

* Risk
* Criticality
* Operational conditions
* Control dependencies

**Within tolerance ≠ Security risk eliminated.**

---

### 28. AI Security Variance

Variance measures the difference between an observed security condition and a reference value.

For example:

\[
Variance = Actual\ Security\ Result - Target
\]

If:

> Target = 98%

> Actual = 94%

then:

> Variance = −4 percentage points.

Variance should be interpreted with context.

A negative variance does not automatically establish that a security control failed.

---

### 29. AI Security Trend

A trend describes the direction of a security measurement over time.

Possible trends include:

* Improving
* Deteriorating
* Stable
* Volatile
* Cyclical

Trend analysis may be applied to:

* Vulnerabilities
* Security incidents
* Attack attempts
* Control coverage
* Detection performance
* Remediation
* Exposure

A single security measurement does not establish a trend.

---

### 30. AI Security Stability

Security stability describes the consistency of a security condition over time.

For example:

> Security-control coverage averages 98%.

does not show whether coverage is consistently 98% or fluctuates between 90% and 100%.

Therefore:

**Average security performance ≠ Security stability.**

Stability should be evaluated for material security measurements.

---

### 31. AI Security Metric Directionality

Directionality defines whether an increase or decrease in a metric generally represents an improvement or deterioration.

Examples:

* Higher control coverage → generally favorable
* Higher vulnerability count → generally unfavorable
* Higher MTTD → generally unfavorable
* Higher detection coverage → generally favorable
* Higher false-positive rate → potentially unfavorable
* Higher security-test coverage → generally favorable

Directionality should be explicitly documented.

Some metrics are context-dependent.

For example, an increase in detected security events may indicate either greater attack activity or improved detection capability.

### 43. AI Security Metric Evidence Sufficiency

Evidence sufficiency means that the available evidence is adequate for the security conclusion being made.

For example:

> A vulnerability scan may demonstrate that a defined set of systems was scanned.

It may not establish:

> All AI vulnerabilities have been identified.

Evidence sufficiency depends on the claim.

* Audit trails
* Timestamping

**Evidence integrity ≠ Evidence correctness.**

### 50. Core Principle of AI Security Metrics

AI security metrics should provide **defined, reproducible, contextualized, and appropriately assured measurements of AI security conditions, control performance, exposure, and security outcomes**.

The fundamental distinctions should remain explicit:

**AI security metric ≠ KPI.**

**AI security metric ≠ KRI.**

**AI security metric ≠ Control.**

**AI security metric ≠ Control Objective.**

**Metric ≠ Target.**

**Metric ≠ Threshold.**

**Metric ≠ Risk.**

**Metric ≠ Compliance.**

**Metric ≠ Assurance.**

**Security coverage ≠ Security effectiveness.**

**Security activity ≠ Security outcome.**

**Security configuration ≠ Security effectiveness.**

**Security monitoring ≠ Security prevention.**

**Security event ≠ Security incident automatically.**

**Security alert ≠ Confirmed compromise.**

**Vulnerability count ≠ Actual risk automatically.**

**Incident count ≠ Security posture automatically.**

**More detected events ≠ Worse security automatically.**

**Fewer reported incidents ≠ Better security automatically.**

**Data quality ≠ Security posture.**

**Data provenance ≠ Data quality.**

**Evidence integrity ≠ Evidence correctness.**

**Measurement confidence ≠ Absence of security risk.**

**Internal target ≠ Legal requirement.**

**Internal threshold ≠ Statutory threshold.**

**Internal escalation trigger ≠ Regulatory notification obligation.**

**Security metric improvement ≠ Risk elimination.**

**Automation ≠ Accountability.**

**AI security measurement is valuable only when it measures a defined security condition using an appropriate population, reliable evidence, controlled methodology, sufficient context, and a clear connection to accountable security decisions.**
