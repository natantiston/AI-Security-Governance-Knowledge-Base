# 18.06 — Model Performance Metrics

## Part 1 — Model Performance Metrics Foundations, Measurement Principles, Governance and Interpretation

### 1. Definition of Model Performance Metrics

Model performance metrics are defined measurements used to evaluate how an AI model performs against specified objectives, evaluation criteria, operating conditions, and intended use.

Model performance metrics may measure different dimensions, including:

* Predictive accuracy
* Precision
* Recall
* F1 score
* Error rate
* Calibration
* Robustness
* Reliability
* Latency
* Availability
* Resource efficiency
* Fairness-related performance
* Safety-related performance
* Security-related performance
* Task completion
* Output quality
* Abstention behavior
* Stability over time

The appropriate metric depends on the model type, use case, risk profile, population, decision context, and intended outcome.

A model performance metric should therefore never be interpreted independently of its measurement objective.

**Model performance metric ≠ model quality in every dimension.**

A model may perform strongly against one metric while performing poorly against another.

---

### 2. Purpose of Model Performance Metrics

The primary purpose of model performance measurement is to provide evidence about whether an AI model is performing as intended.

Performance metrics may support:

* Model development
* Model validation
* Model approval
* Production monitoring
* Model risk management
* Security monitoring
* Safety monitoring
* Regulatory assessment
* Change management
* Incident investigation
* Model retirement
* Executive governance

Metrics should be selected according to the decisions they are intended to support.

A metric that does not influence a meaningful governance, technical, operational, or risk decision may have limited value.

---

### 3. Model Performance Metric vs KPI

A model performance metric is a measurement of model behavior or performance.

A KPI is a selected measurement used to evaluate performance against an important organizational objective.

For example:

> Model precision = 94%

is a model performance measurement.

An organization may designate:

> Critical fraud-detection precision maintained above the approved operational target

as a KPI.

Therefore:

**Model performance metric ≠ KPI automatically.**

A model performance measurement becomes a KPI only when the organization formally designates it as a key performance indicator.

---

### 4. Model Performance Metric vs KRI

A Key Risk Indicator identifies or signals changes in risk exposure.

A model performance metric measures a model characteristic or outcome.

For example:

* Precision = model performance metric
* False-negative rate = model performance metric
* Number of material model failures = potential KRI
* Percentage of critical models exceeding error tolerance = potential KRI

A model performance metric can contribute to a KRI, but the two concepts serve different purposes.

**Performance measurement ≠ risk measurement.**

---

### 5. Model Performance Metric vs Control

A control is a measure designed to prevent, detect, or respond to a risk or to ensure a required condition.

A model performance metric measures model behavior.

For example:

> Recall of 91%

is a measurement.

A control may require:

> Production models must undergo performance validation before release.

The metric provides evidence relevant to the control.

It is not itself the control.

---

### 6. Model Performance Metric vs Control Objective

A control objective describes the condition a control is intended to achieve.

For example:

> Model performance must remain within approved operating parameters.

The metrics used to evaluate this condition may include:

* Accuracy
* Recall
* Precision
* Error rate
* Calibration
* Drift

Therefore:

**Control objective ≠ metric.**

The objective establishes the desired governance condition; the metric measures a relevant aspect of that condition.

---

### 7. Model Performance Metric vs Target

A target specifies a desired performance level.

For example:

> Target precision = 95%

The observed metric may be:

> Actual precision = 93.7%

The metric provides the measured result.

The target provides the intended level.

**Metric ≠ Target.**

A target should not be confused with an externally mandated requirement unless an authoritative source explicitly establishes that requirement.

---

### 8. Model Performance Metric vs Threshold

A threshold defines a boundary that may trigger review, escalation, intervention, or another governance action.

For example:

> Precision below 90% triggers model review.

The observed precision is the metric.

The 90% boundary is the threshold.

```text id="aigmet18-06-p1-01"
Observed Metric
      |
      v
   93.7%
      |
      v
Compare with Threshold
      |
      v
   90.0%
      |
      v
Governance Decision
```

**Metric ≠ Threshold.**

Thresholds may be internal governance decisions unless an applicable external requirement establishes a specific threshold.

---

### 9. Model Performance Measurement Scope

Measurement scope defines what model performance is being evaluated.

Scope may include:

* Specific model
* Model version
* AI system
* Business process
* Dataset
* Geographic population
* User population
* Operating environment
* Time period
* Specific task
* Specific output type

A performance result is meaningful only when its scope is understood.

For example:

> Accuracy = 95%

is incomplete without understanding:

* On which dataset?
* For which population?
* During which period?
* Under which operating conditions?
* For which model version?
* Using which evaluation methodology?

---

### 10. Model Performance Measurement Domain

Model performance may be evaluated across multiple domains.

Common domains include:

| Domain | Example Measurement |
|---|---|
| Predictive | Accuracy |
| Classification | Precision / Recall |
| Ranking | NDCG |
| Generation | Output quality |
| Calibration | Probability calibration |
| Reliability | Failure rate |
| Robustness | Performance under perturbation |
| Latency | Response time |
| Availability | Service availability |
| Fairness | Group performance differences |
| Safety | Unsafe-output rate |
| Security | Attack success rate |
| Operational | Resource utilization |

No single measurement domain provides complete model performance assurance.

---

### 11. Model Performance Governance

Model performance measurement should operate under defined governance.

Governance should establish:

* Metric definitions
* Measurement methodology
* Data requirements
* Ownership
* Validation
* Reporting
* Thresholds
* Targets
* Change management
* Evidence retention
* Escalation

Governance should also define which performance measurements are required before:

* Deployment
* Production use
* Material model change
* Model revalidation
* Continued operation

---

### 12. Model Performance Metric Owner

Each material performance metric should have an accountable owner.

The metric owner may be responsible for:

* Definition
* Methodology
* Interpretation
* Threshold recommendation
* Reporting
* Change management
* Exception management

Ownership of the metric does not necessarily mean ownership of the model.

For example:

> Model owner ≠ Metric owner automatically.

Responsibilities should be explicitly defined.

---

### 13. Model Performance Data Owner

The data owner is responsible for the relevant measurement data or dataset.

Responsibilities may include:

* Data availability
* Data quality
* Data access
* Data classification
* Data lineage
* Data retention
* Data integrity

The model performance metric owner and data owner may be different individuals or functions.

---

### 14. Model Performance Metric Definition

Every material performance metric should have a precise definition.

A definition should identify:

* What is measured
* Why it is measured
* Population
* Unit
* Calculation method
* Measurement period
* Applicable model version
* Inclusion criteria
* Exclusion criteria

For example:

> Recall = true positives divided by all actual positive cases within the approved evaluation population.

The definition should be sufficiently precise for independent reproduction.

---

### 15. Model Performance Formula

Where a metric is calculated mathematically, the formula should be documented.

For example:

**Accuracy**

\[
Accuracy = \frac{Correct\ Predictions}{Total\ Predictions}
\]

**Precision**

\[
Precision = \frac{True\ Positives}{True\ Positives + False\ Positives}
\]

**Recall**

\[
Recall = \frac{True\ Positives}{True\ Positives + False\ Negatives}
\]

The formula alone is insufficient.

The organization must also define the population and classification rules used to generate the underlying values.

---

### 16. Model Performance Numerator

The numerator represents the quantity counted as satisfying the metric condition.

For example, for precision:

> True positives

are included in the numerator.

The numerator should be:

* Clearly defined
* Reproducible
* Traceable to source data
* Consistent with the approved methodology

An incorrect numerator can produce a mathematically correct but substantively misleading metric.

---

### 17. Model Performance Denominator

The denominator defines the population against which the numerator is measured.

For example:

\[
Recall = \frac{TP}{TP + FN}
\]

The denominator is the number of actual positive cases.

Denominator integrity is particularly important because changing the denominator can materially alter the reported result.

**Denominator change ≠ Performance improvement automatically.**

---

### 18. Model Performance Population

The population is the complete set of observations or cases to which the metric applies.

Population may be defined by:

* Dataset
* Customer group
* Geographic area
* Transaction type
* Model version
* Time period
* Production environment

A metric should identify whether it is based on:

* Full population
* Sample
* Test set
* Validation set
* Production observations

---

### 19. Model Performance Inclusion Criteria

Inclusion criteria specify which observations are included in the metric population.

Criteria may include:

* Valid records
* Specific transaction types
* Defined customer segments
* Approved data sources
* Production cases
* Specific model outputs

Inclusion criteria should be documented before measurement where practical.

---

### 20. Model Performance Exclusion Criteria

Exclusion criteria identify observations intentionally excluded from measurement.

Examples include:

* Invalid records
* Missing labels
* Known corrupted observations
* Out-of-scope use cases
* Test transactions
* Duplicate records

Exclusions should be justified.

Unexplained exclusions can produce misleading performance results.

---

### 21. Model Performance Measurement Period

The measurement period defines when the observations were generated.

Examples include:

* Development evaluation
* Validation period
* Pre-production testing
* Monthly production monitoring
* Quarterly performance review

Performance results should not be compared across periods without considering changes in:

* Model version
* Population
* Data
* Environment
* Methodology

---

### 22. Model Performance Measurement Frequency

Measurement frequency should reflect model risk and operating conditions.

Possible frequencies include:

* Continuous
* Real-time
* Daily
* Weekly
* Monthly
* Quarterly
* Event-driven

High-risk or rapidly changing models may require more frequent measurement.

Low-frequency measurement may be insufficient when performance can deteriorate rapidly.

---

### 23. Model Performance Reporting Frequency

Measurement frequency and reporting frequency are not necessarily identical.

A model may be measured continuously but reported:

* Daily
* Weekly
* Monthly
* On threshold breach
* On material deterioration

For example:

```text id="aigmet18-06-p1-02"
Continuous Measurement
        |
        v
Continuous Data Collection
        |
        v
Daily Analysis
        |
        v
Monthly Executive Reporting
        |
        +----> Immediate Escalation if Material
```

---

### 24. Model Performance Baseline

A baseline provides a reference point against which subsequent performance may be compared.

Possible baselines include:

* Initial validation performance
* Approved production performance
* Historical average
* Previous model version
* Benchmark model
* Defined reference dataset

A baseline should remain stable enough to support meaningful comparison.

---

### 25. Model Performance Target

A performance target establishes a desired level of model performance.

Examples include:

* Accuracy target
* Recall target
* Latency target
* Availability target
* Calibration target

Targets should consider:

* Model purpose
* Business requirements
* Risk
* Cost
* Technical feasibility
* User impact

A target is an organizational governance decision unless an applicable external requirement establishes a mandatory performance level.

---

### 26. Model Performance Threshold

A threshold establishes a boundary requiring defined action.

For example:

> Recall below 85% triggers investigation.

Thresholds should have:

* Owner
* Rationale
* Approval
* Review frequency
* Escalation process

Thresholds may differ from targets.

A model may miss its target without crossing a formal escalation threshold.

---

### 27. Model Performance Tolerance

Tolerance represents the acceptable range of variation around an expected performance condition.

For example:

> Approved performance target = 95%

> Tolerance = ±2 percentage points

The tolerance should be interpreted within the model's risk and operating context.

---

### 28. Model Performance Variance

Variance represents the difference between observed performance and a reference value.

For example:

\[
Variance = Actual\ Performance - Target
\]

If:

> Target = 95%

> Actual = 92%

then:

> Variance = −3 percentage points.

Variance should be interpreted together with the measurement population and uncertainty.

---

### 29. Model Performance Trend

A trend describes the direction of performance over time.

Possible trends include:

* Improving
* Stable
* Deteriorating
* Volatile
* Cyclical

A single measurement cannot establish a reliable trend.

Trend analysis should use sufficient historical observations.

---

### 30. Model Performance Stability

Performance stability describes the consistency of model behavior over time or across relevant populations.

A model may have:

> High average accuracy but significant performance volatility.

Therefore:

**Average performance ≠ Performance stability.**

Stability may be evaluated across:

* Time
* Geography
* User groups
* Data segments
* Operating environments
* Model versions

---

### 31. Model Performance Directionality

Directionality describes whether a change in a metric represents improvement or deterioration.

For example:

* Higher recall may be desirable.
* Higher false-positive rate may be undesirable.
* Lower latency may be desirable.
* Higher error rate may be undesirable.

Directionality should be explicitly documented.

---

### 32. Model Performance Interpretation

Interpretation converts a numerical result into meaningful model-performance information.

Interpretation should consider:

* Metric definition
* Model purpose
* Population
* Baseline
* Target
* Threshold
* Trend
* Uncertainty
* Business context

A numerical value without interpretation may be insufficient for governance.

---

### 33. Model Performance Context

Context provides information necessary to understand the significance of a performance result.

Context may include:

* Model use case
* User population
* Data characteristics
* Operating environment
* Business process
* Risk level
* Model version
* Recent changes

For example:

> Accuracy decreased from 96% to 93%

may have a different significance depending on whether the model moved into a substantially different production population.

---

### 34. Model Performance Comparability

Performance measurements are comparable only when the relevant measurement conditions are sufficiently consistent.

Comparability may be affected by:

* Dataset changes
* Population changes
* Model version
* Metric methodology
* Labeling changes
* Evaluation environment
* Operating conditions

A higher score does not necessarily mean better performance if the underlying populations differ materially.

---

### 35. Model Performance Consistency

Consistency requires that the same approved methodology produce comparable measurements under equivalent conditions.

Consistency controls should address:

* Formula
* Dataset
* Population
* Evaluation procedure
* Labeling
* Sampling
* Calculation

Methodological inconsistency can create artificial performance trends.

---

### 36. Model Performance Methodology

The methodology defines how model performance is measured.

It should specify:

* Metric
* Data
* Population
* Evaluation procedure
* Sampling
* Labels
* Formula
* Statistical treatment
* Reporting

The methodology should be approved according to the organization's model governance requirements.

---

### 37. Model Performance Methodology Change

Changes to performance methodology may materially affect reported performance.

Examples include:

* New test dataset
* New labeling methodology
* Different sampling approach
* Revised metric formula
* Different exclusion criteria
* New evaluation environment

A methodology change should be documented.

**Measurement methodology change ≠ Model performance change automatically.**

---

### 38. Model Performance Restatement

A restatement occurs when a previously reported performance measurement is corrected.

Potential reasons include:

* Calculation error
* Data-quality problem
* Incorrect population
* Methodology defect
* Duplicate records
* Labeling error

Restatement should preserve the original result and explain the correction.

---

### 39. Model Performance Data Quality

Data quality directly affects performance measurement reliability.

Relevant dimensions include:

* Accuracy
* Completeness
* Consistency
* Timeliness
* Validity
* Uniqueness
* Integrity

Poor evaluation data can produce misleading performance results even when the model itself has not changed.

---

Data lineage identifies how performance data moves from source to measurement.

---

### 41. Model Performance Data Provenance

Provenance identifies the origin and history of the data used for performance measurement.

Provenance may include:

* Source
* Collection date
* Dataset version
* Transformation
* Labeling process
* Custodian
* Processing history

**Data provenance ≠ Data quality automatically.**

A dataset can have strong provenance while still containing poor-quality data.

---

### 42. Model Performance Evidence

Evidence supports the reported performance result.

Evidence may include:

* Evaluation datasets
* Test results
* Validation reports
* Calculation outputs
* Experiment records
* Model version
* Configuration
* Monitoring records

Evidence should be sufficiently detailed to support the intended governance decision.

---

### 43. Model Performance Evidence Sufficiency

Evidence sufficiency means that the available evidence is adequate for the conclusion being drawn.

For example:

> A single benchmark result may be sufficient to demonstrate performance on that benchmark.

It may not be sufficient to establish:

> Robust performance across all production populations.

Evidence sufficiency depends on the claim being made.

---

### 44. Model Performance Evidence Integrity

Evidence integrity requires confidence that evidence has not been improperly altered, substituted, or corrupted.

Controls may include:

* Access control
* Versioning
* Hashing
* Audit trails
* Immutable storage
* Approval records

Cryptographic integrity can help establish evidence integrity.

**Evidence integrity ≠ Evidence correctness automatically.**

---

### 45. Model Performance Calculation Integrity

Calculation integrity means that the approved formula and methodology were correctly applied to the intended data.

Controls may include:

* Automated calculations
* Independent recalculation
* Code review
* Test cases
* Reconciliation
* Version control

A mathematically correct calculation can still produce an incorrect conclusion if the wrong population was used.

---

### 46. Model Performance Validation

Validation provides structured evaluation of whether performance measurements and their methodology are appropriate.

Validation may examine:

* Dataset
* Population
* Formula
* Labels
* Calculation
* Statistical assumptions
* Reproducibility
* Interpretation

Validation should be proportionate to model criticality and risk.

---

### 47. Model Performance Assurance

Assurance provides confidence that model performance measurement is sufficiently reliable for its intended governance purpose.

Assurance may involve:

* Independent review
* Recalculation
* Sampling
* Dataset review
* Methodology review
* Model validation
* Audit

**Performance measurement ≠ Performance assurance.**

A metric can be calculated correctly without receiving independent assurance.

---

### 48. Model Performance Decision Usefulness

A model performance metric is decision-useful when it provides information that can support an appropriate decision.

Examples include decisions to:

* Approve deployment
* Continue operation
* Retrain
* Recalibrate
* Change thresholds
* Restrict use
* Investigate deterioration
* Retire a model

Decision usefulness depends on relevance, timeliness, reliability, and context.

---

Enterprise model performance measurement should connect model objectives, evaluation methodology, measurements, governance interpretation, and decisions.

The model performance measurement system should also recognize that different AI systems require different measurement strategies.

A classification model, generative AI system, recommendation model, computer-vision system, forecasting model, and autonomous agent may require substantially different performance measures.

There should therefore be no assumption that a single enterprise metric can represent all forms of AI performance.

---

### 50. Core Principle

Model performance metrics should provide **defined, reproducible, contextualized, and appropriately assured measurements of AI model behavior and outcomes**.

The following distinctions should remain explicit:

**Model performance metric ≠ KPI.**

**Model performance metric ≠ KRI.**

**Model performance metric ≠ Control.**

**Model performance metric ≠ Control Objective.**

**Metric ≠ Target.**

**Metric ≠ Threshold.**

**Metric ≠ Risk.**

**Metric ≠ Compliance.**

**Metric ≠ Assurance.**

**Accuracy ≠ Complete Model Quality.**

**Average Performance ≠ Performance Stability.**

**Benchmark Performance ≠ Production Performance automatically.**

**Test-Set Performance ≠ Real-World Performance automatically.**

**Model Performance ≠ Business Outcome automatically.**

**Metric Improvement ≠ Risk Reduction automatically.**

**Methodology Change ≠ Model Improvement.**

**Data Quality ≠ Model Performance.**

**Data Provenance ≠ Data Quality.**

**Evidence Integrity ≠ Evidence Correctness.**

**Calculation Accuracy ≠ Measurement Validity automatically.**

**Internal Target ≠ Legal Requirement.**

**Internal Threshold ≠ Statutory Threshold.**

**Performance Measurement ≠ Performance Assurance.**

**A strong performance score on one dimension does not establish that the model is reliable, safe, secure, fair, robust, compliant, or appropriate for every intended use.**

Model performance measurement should therefore remain aligned with the model's intended purpose, risk profile, operating context, evaluation population, and governance requirements.
