# 18.01 — AI Security Monitoring Foundations

## Part 1 — AI Security Monitoring Foundations, Measurement Concepts, Observability, Governance and Assurance

### 1. AI Security Monitoring

AI security monitoring is the structured and ongoing observation of AI systems, models, data, infrastructure, users, agents, dependencies, controls, and security-relevant conditions to identify changes, anomalies, risks, incidents, and control weaknesses.

Monitoring provides the operational evidence required to understand whether AI security controls continue to function as intended.

Monitoring should be distinguished from measurement, assurance, and response.

### 2. Monitoring Objective

The primary objective of AI security monitoring is to provide timely and reliable visibility into conditions that may affect:

- confidentiality;
- integrity;
- availability;
- authenticity;
- privacy;
- safety;
- model security;
- data security;
- infrastructure security;
- regulatory exposure;
- control effectiveness.

### 3. Monitoring Scope

AI security monitoring may cover:

- AI models;
- model artifacts;
- training environments;
- datasets;
- inference systems;
- APIs;
- agents;
- tools;
- retrieval systems;
- vector stores;
- memory systems;
- cloud infrastructure;
- identities;
- endpoints;
- networks;
- applications;
- suppliers;
- fourth parties;
- security controls;
- governance processes.

### 4. Monitoring Boundary

The monitoring boundary defines which components, activities, dependencies, and environments are included within monitoring.

A monitoring boundary should account for:

- production;
- development;
- testing;
- training;
- fine-tuning;
- deployment;
- inference;
- retirement.

### 5. Monitoring Coverage

Monitoring coverage represents the portion of relevant AI assets, activities, controls, and risks that are observable through defined monitoring mechanisms.

High monitoring volume does not necessarily indicate high monitoring coverage.

### 6. Monitoring Gap

A monitoring gap exists when a relevant AI security condition cannot be adequately observed or evaluated.

Examples include:

- an unmonitored model endpoint;
- missing security telemetry;
- incomplete supplier visibility;
- unavailable model-version information;
- insufficient logging.

### 8. Monitoring Signal

A monitoring signal is an observable indication that may provide information about an AI security condition.

Signals may originate from:

- logs;
- events;
- metrics;
- traces;
- model outputs;
- access records;
- configuration changes;
- security alerts;
- control assessments.

### 9. Security Telemetry

Security telemetry is data generated by AI systems and supporting infrastructure that can be used to detect, investigate, measure, and understand security-relevant conditions.

Telemetry may include:

- authentication events;
- authorization events;
- API calls;
- model requests;
- model responses;
- tool invocation;
- data access;
- configuration changes;
- deployment events;
- administrative actions.

### 10. Security Log

A security log is a recorded representation of an event or activity relevant to security monitoring.

Logs should support appropriate:

- timestamping;
- identity;
- source identification;
- event context;
- integrity;
- retention;
- access control.

### 11. Security Event

A security event is an observable occurrence relevant to security.

An event does not automatically constitute:

- an incident;
- a breach;
- a compromise;
- a control failure.

### 12. Security Alert

A security alert is a notification generated when monitoring identifies a condition requiring attention according to defined criteria.

An alert is not necessarily confirmation of malicious activity.

### 13. Monitoring Rule

A monitoring rule defines conditions under which an observed signal should generate:

- an alert;
- a metric;
- an investigation;
- an escalation;
- another defined action.

### 14. Detection Logic

Detection logic translates observable signals into conditions considered potentially significant.

Detection logic may be:

- signature-based;
- threshold-based;
- anomaly-based;
- behavioral;
- correlation-based;
- model-based;
- rule-based.

### 15. Threshold

A threshold is a defined boundary used to determine whether an observed value or condition requires attention.

Thresholds may apply to:

- authentication failures;
- API activity;
- model errors;
- data access;
- latency;
- abnormal tool use;
- security events.

An internal threshold is not automatically a statutory or regulatory threshold.

### 16. Baseline

A baseline represents an established reference condition against which subsequent observations may be compared.

Baselines may represent:

- normal traffic;
- normal model behavior;
- normal user activity;
- normal API consumption;
- normal tool invocation;
- normal resource utilization.

### 17. Anomaly

An anomaly is an observation that differs materially from an established baseline or expected condition.

An anomaly does not automatically establish:

- an attack;
- malicious intent;
- compromise;
- a security incident.

### 18. Deviation

Deviation represents the difference between observed behavior and an expected, approved, or established state.

Deviation may be:

- intentional;
- accidental;
- environmental;
- operational;
- malicious.

### 19. Expected State

The expected state represents the approved or intended condition of an AI system, model, configuration, identity, process, or control.

Monitoring should identify material deviations from the expected state.

### 20. Security State

Security state represents the current observable security condition of an AI system or supporting environment.

It may include:

- identity state;
- configuration state;
- deployment state;
- model state;
- access state;
- vulnerability state;
- control state.

### 21. Monitoring Context

Monitoring context provides the information necessary to interpret a signal correctly.

Context may include:

- user;
- application;
- model;
- model version;
- dataset;
- tool;
- geographic location;
- time;
- transaction;
- business process.

### 22. Contextual Monitoring

Contextual monitoring correlates observations with relevant environmental and business information.

A security event without context may be difficult to interpret accurately.

### 23. Monitoring Correlation

Correlation combines multiple signals to identify relationships that may not be visible from individual events.

For example:

```text id="k4v8mx"
UNUSUAL LOGIN
      +
UNUSUAL API ACCESS
      +
UNUSUAL MODEL REQUESTS
      +
UNUSUAL DATA ACCESS
      |
      v
CORRELATED SECURITY SIGNAL
```

Correlation does not automatically establish causation.

### 24. Monitoring Coverage vs Monitoring Volume

A large number of monitored events does not necessarily indicate effective monitoring.

Monitoring quality depends on:

- relevant coverage;
- signal quality;
- contextual information;
- detection capability;
- timeliness;
- analytical usefulness.

### 25. Monitoring Quality

Monitoring quality reflects the degree to which monitoring produces information that is:

- relevant;
- accurate;
- timely;
- complete;
- consistent;
- actionable.

### 26. Monitoring Accuracy

Monitoring accuracy represents the degree to which monitoring correctly identifies the condition it is intended to observe.

Incorrect monitoring can generate:

- false positives;
- false negatives;
- misleading metrics;
- inappropriate escalation.

### 27. False Positive

A false positive occurs when monitoring identifies a condition as significant when the condition does not meet the intended criteria.

High false-positive rates can reduce:

- analyst attention;
- trust;
- response efficiency.

### 28. False Negative

A false negative occurs when a monitoring mechanism fails to identify a condition that should have been detected.

False negatives may create significant security exposure.

### 29. Detection Sensitivity

Detection sensitivity reflects the ability of a monitoring mechanism to identify relevant conditions.

Higher sensitivity may increase detection while also increasing false positives.

### 30. Detection Specificity

Detection specificity reflects the ability of a monitoring mechanism to distinguish relevant conditions from benign activity.

Sensitivity and specificity should be evaluated together rather than independently.

### 31. Monitoring Latency

Monitoring latency is the time between the occurrence of a relevant condition and its availability for monitoring or analysis.

Lower latency may be important for:

- active attacks;
- account compromise;
- data exfiltration;
- autonomous agent activity;
- high-impact AI systems.

### 32. Detection Latency

Detection latency is the time between an observable security condition and its identification by monitoring mechanisms.

Detection latency differs from response latency.

### 33. Response Latency

Response latency is the time between identification of a condition and initiation of an appropriate response.

Monitoring itself does not constitute response.

### 34. Monitoring Frequency

Monitoring frequency defines how often observations are collected, evaluated, or reported.

Frequency may vary by:

- risk;
- system criticality;
- event type;
- operational requirement;
- regulatory context.

### 35. Continuous Monitoring

Continuous monitoring is an ongoing monitoring capability designed to identify relevant changes or conditions without relying exclusively on periodic manual assessments.

Continuous monitoring does not mean every AI security variable must be observed continuously.

### 36. Periodic Monitoring

Periodic monitoring evaluates defined conditions at scheduled intervals.

Periodic monitoring may be appropriate where:

- conditions change slowly;
- continuous telemetry is unnecessary;
- manual assessment provides sufficient assurance.

### 37. Real-Time Monitoring

Real-time monitoring provides observations with sufficiently low latency to support immediate or near-immediate operational decisions.

Real-time does not have one universally applicable technical definition.

### 38. Near-Real-Time Monitoring

Near-real-time monitoring provides observations with limited delay that remains appropriate for the intended security use case.

### 39. Historical Monitoring

Historical monitoring analyzes previously collected information to identify:

- trends;
- recurring events;
- control weaknesses;
- changes;
- emerging risks.

### 40. Monitoring Retention

Monitoring retention defines how long monitoring information is preserved.

Retention should consider:

- security investigations;
- regulatory requirements;
- contractual obligations;
- privacy requirements;
- operational needs;
- forensic requirements.

### 41. Monitoring Integrity

Monitoring integrity is the degree to which monitoring information remains accurate and protected against unauthorized alteration.

Monitoring integrity may require:

- access control;
- tamper resistance;
- integrity verification;
- secure transmission;
- controlled administration.

### 42. Monitoring Availability

Monitoring availability represents the ability to obtain required monitoring information when needed.

Monitoring outages may create blind spots.

### 43. Monitoring Resilience

Monitoring resilience is the ability of monitoring capabilities to continue operating or recover appropriately during disruption.

Monitoring resilience may require:

- redundant collectors;
- alternate telemetry paths;
- resilient storage;
- recovery procedures;
- manual fallback.

### 44. Monitoring Blind Spot

A monitoring blind spot is an area where relevant AI security activity cannot be adequately observed.

Blind spots may arise from:

- unsupported systems;
- uninstrumented APIs;
- encrypted traffic;
- supplier limitations;
- telemetry failure;
- configuration gaps.

### 45. Monitoring Dependency

A monitoring dependency is a component required for monitoring capability to function.

Examples include:

- telemetry collectors;
- SIEM platforms;
- identity systems;
- cloud services;
- network infrastructure;
- storage.

### 46. Monitoring Single Point of Failure

A monitoring single point of failure exists when loss of one dependency can materially impair monitoring capability.

### 47. Monitoring Common-Mode Failure

A common-mode monitoring failure occurs when multiple monitoring mechanisms fail because they depend on the same underlying component, configuration, provider, or infrastructure.

### 48. Monitoring Governance

AI security monitoring should operate under defined governance covering:

- scope;
- ownership;
- responsibilities;
- data handling;
- escalation;
- retention;
- assurance;
- exceptions.

### 49. Monitoring Accountability

Monitoring accountability should identify who is responsible for:

- defining monitoring objectives;
- approving monitoring scope;
- maintaining detection logic;
- reviewing monitoring results;
- addressing monitoring gaps.

### 50. Core Principle

**AI security monitoring should provide reliable, contextual, timely, and governed visibility into security-relevant conditions across AI models, data, infrastructure, identities, applications, agents, dependencies, and controls. Monitoring should support informed governance and operational decisions without being confused with incident response, assurance, legal compliance, or proof of security.**

Internal `AI-SM-*` identifiers used throughout this topic represent knowledge-base taxonomy identifiers and do not represent statutory provisions, regulatory article numbers, certification requirements, or legal obligations.

## Part 3 — Continuous AI Security Monitoring, Advanced Detection, Correlation, Assurance and Resilience

### 126. AI Security Continuous Monitoring

Continuous AI security monitoring extends monitoring beyond periodic review by continuously evaluating relevant security signals, control states, system behavior, and material changes.

Continuous monitoring should be proportionate to:

- AI system criticality;
- threat exposure;
- autonomy;
- data sensitivity;
- business impact;
- regulatory significance.

### 127. AI Security Monitoring State

The organization should maintain visibility into the current security state of material AI systems.

Security state may include:

- identity state;
- access state;
- configuration state;
- model state;
- deployment state;
- data state;
- control state;
- dependency state.

### 128. AI Security Monitoring State Transition

Material transitions should be observable where appropriate.

Examples include:

- model deployment;
- configuration change;
- privilege change;
- dataset change;
- agent activation;
- tool authorization;
- supplier change.

### 129. AI Security Monitoring Change Detection

Monitoring should identify material changes to:

- models;
- datasets;
- configurations;
- identities;
- permissions;
- infrastructure;
- dependencies.

### 130. AI Security Monitoring Change Correlation

Changes should be correlated with security events to determine whether unexpected behavior follows a material change.

Correlation does not by itself establish causation.

### 131. AI Security Monitoring Deployment Correlation

Model deployments should be correlated with:

- model version;
- configuration;
- identity;
- deployment environment;
- security events;
- performance changes.

### 132. AI Security Monitoring Version Correlation

Monitoring should retain sufficient model-version context to determine which version was active when an event occurred.

### 133. AI Security Monitoring Configuration Correlation

Security events should be correlated with relevant configuration changes where possible.

### 134. AI Security Monitoring Identity Correlation

Monitoring should correlate activity with the responsible:

- user;
- service identity;
- workload;
- agent;
- administrator.

### 135. AI Security Monitoring Session Correlation

Where appropriate, related activity should be associated with a common session or transaction context.

### 136. AI Security Monitoring Transaction Correlation

AI actions affecting business transactions should be traceable across relevant:

- requests;
- model decisions;
- tool actions;
- approvals;
- outcomes.

### 137. AI Security Monitoring Attack-Path Correlation

Multiple observations may be correlated to identify potential attack paths.

### 138. AI Security Monitoring Threat-Intelligence Correlation

Threat intelligence may enrich AI security monitoring by providing information about:

- known attack techniques;
- malicious infrastructure;
- compromised credentials;
- emerging AI-specific threats.

Threat intelligence is contextual evidence and does not automatically establish compromise.

### 139. AI Security Monitoring Threat-Pattern Detection

Monitoring should identify patterns associated with known or emerging AI attack techniques.

Potential patterns include:

- prompt injection;
- model extraction;
- data exfiltration;
- credential abuse;
- tool abuse;
- model artifact tampering.

### 140. AI Security Monitoring Behavioral Detection

Behavioral detection identifies activity that differs from expected behavior.

Behavioral detection should account for:

- normal operational variation;
- legitimate workload changes;
- model updates;
- seasonal patterns;
- business events.

### 141. AI Security Monitoring Anomaly Detection

Anomaly detection may identify deviations involving:

- request volume;
- access patterns;
- model outputs;
- tool activity;
- resource usage;
- data access.

An anomaly is not equivalent to a confirmed security incident.

### 142. AI Security Monitoring Statistical Detection

Statistical methods may identify significant deviations from established baselines.

Statistical significance does not automatically establish security significance.

### 143. AI Security Monitoring Machine-Learning Detection

Machine-learning techniques may be used to identify complex security patterns.

Such detection mechanisms should themselves be governed for:

- accuracy;
- drift;
- false positives;
- false negatives;
- explainability;
- security.

### 144. AI Security Monitoring Detection-Model Drift

Detection models may degrade when the underlying environment changes.

Detection-model monitoring should identify:

- distribution changes;
- performance degradation;
- increased false positives;
- increased false negatives.

### 145. AI Security Monitoring Detection Coverage

Detection coverage should assess whether material threat scenarios have corresponding monitoring capabilities.

### 146. AI Security Monitoring Detection Gap Analysis

Detection gaps should be identified against:

- threat models;
- attack paths;
- incident history;
- control objectives;
- system changes.

### 147. AI Security Monitoring Detection Recurrence

Recurring incidents should be assessed to determine whether existing monitoring should be enhanced.

### 148. AI Security Monitoring Detection Effectiveness

Detection effectiveness should consider:

- detection rate;
- false-positive rate;
- false-negative rate;
- detection latency;
- coverage;
- investigation usefulness.

### 149. AI Security Monitoring Detection Validation

Detection mechanisms should be periodically validated against representative scenarios.

### 150. AI Security Monitoring Adversarial Validation

Where appropriate, adversarial testing may assess whether monitoring can detect:

- evasion;
- obfuscation;
- prompt manipulation;
- abnormal tool use;
- unauthorized model changes.

### 151. AI Security Monitoring Red-Team Integration

Red-team exercises should provide realistic conditions for evaluating monitoring coverage and detection effectiveness.

### 152. AI Security Monitoring Purple-Team Integration

Purple-team exercises should connect simulated attack activity with:

- telemetry;
- detection;

### 153. AI Security Monitoring Control-Failure Correlation

Monitoring should correlate security signals with control failures where evidence supports such relationships.

### 154. AI Security Monitoring Compensating-Control Monitoring

When a primary control is unavailable, monitoring should determine whether compensating controls remain effective.

- collector health;

- processing latency.

### 167. AI Security Monitoring Coverage Monitoring

Monitoring coverage should itself be measured.

Possible measures include:

- percentage of production models monitored;
- percentage of critical endpoints covered;
- percentage of material controls monitored;
- percentage of critical dependencies with telemetry.

### 168. AI Security Monitoring Coverage Drift

Monitoring coverage may decline when:

- new AI systems are deployed;
- new models are introduced;
- suppliers change;
- integrations fail;
- telemetry configurations are removed.

### 169. AI Security Monitoring Asset-Onboarding Control

New AI assets should enter monitoring according to defined onboarding criteria.

### 170. AI Security Monitoring Decommissioning Control

Retired AI assets should be removed from monitoring appropriately while preserving required historical evidence.

### 171. AI Security Monitoring Monitoring-Exemption Governance

Monitoring exemptions should be:

- documented;
- justified;
- approved;
- time-bound where appropriate;
- periodically reviewed.

### 172. AI Security Monitoring Compensating Telemetry

Where required telemetry cannot be collected, alternative sources may provide compensating visibility.

Compensating telemetry should be assessed for adequacy rather than assumed equivalent.

### 173. AI Security Monitoring Supplier-Visibility Assessment

Supplier-dependent AI systems should be assessed for the monitoring visibility provided by the supplier.

### 174. AI Security Monitoring Supplier-Telemetry Assurance

Supplier telemetry should be assessed for:

- completeness;

- timeliness;
- contractual availability;
- evidence quality.

### 175. AI Security Monitoring Fourth-Party Visibility

Where critical fourth parties affect AI services, the organization should consider whether sufficient visibility exists into relevant upstream dependencies.

### 176. AI Security Monitoring Provider Concentration

Monitoring architecture should assess concentration risks involving:

- one telemetry provider;
- one SIEM;
- one cloud platform;
- one identity provider;
- one logging infrastructure.

### 177. AI Security Monitoring Common-Mode Monitoring Failure

Multiple monitoring mechanisms may fail simultaneously when they depend on a common:

- cloud platform;
- network;
- identity system;
- configuration;
- provider.

### 178. AI Security Monitoring Alternative Telemetry Path

Critical monitoring functions may require alternative telemetry paths to maintain visibility during primary-path failure.

### 179. AI Security Monitoring Manual Fallback

Manual monitoring procedures may be required when automated telemetry or detection mechanisms are unavailable.

### 180. AI Security Monitoring Monitoring Recovery

Monitoring recovery procedures should restore:

- telemetry collection;
- processing;
- storage;
- detection;
- alerting;
- reporting.

### 181. AI Security Monitoring Recovery Validation

After monitoring recovery, the organization should validate that monitoring is functioning correctly before relying on it for material security decisions.

### 182. AI Security Monitoring Trusted Monitoring State

A trusted monitoring state exists when monitoring has been sufficiently validated to provide reliable security visibility.

Successful technical restoration does not automatically establish a trusted monitoring state.

Security events should be correlated across relevant:

### 184. AI Security Monitoring Cross-Model Correlation

### 187. AI Security Monitoring Cross-Service Correlation

AI security signals should be correlated across supporting services where relevant to the security use case.

### 188. AI Security Monitoring Cross-Supplier Correlation

Events involving multiple suppliers should be correlated when a shared incident or dependency may exist.

### 195. AI Security Monitoring Containment Validation

### 196. AI Security Monitoring Eradication Validation

Monitoring should help determine whether indicators of compromise or other unwanted conditions remain after eradication activities.

### 197. AI Security Monitoring Recovery Monitoring

Recovered AI services should remain under enhanced monitoring until appropriate recovery validation criteria are satisfied.

### 198. AI Security Monitoring Regression Monitoring

Following a material change or recovery, monitoring should identify unexpected regression in:

### 199. AI Security Monitoring Continuous Assurance

Continuous monitoring may contribute evidence to continuous assurance.

### 201. AI Security Monitoring Control-Effectiveness Assessment

Monitoring evidence may be used to evaluate whether security controls operate effectively.

### 203. AI Security Monitoring Evidence Confidence

### 204. AI Security Monitoring Uncertainty Management

- confirmed facts;

- timeline reconstruction;

### 210. AI Security Monitoring Continuous-Assurance Principle

**Effective AI security monitoring requires continuous visibility into material security conditions, continuous validation of telemetry and detection capability, and continuous improvement of monitoring coverage. Monitoring should provide reliable evidence for security operations and governance while recognizing that monitoring, detection, assurance, and response are distinct capabilities.**

The following distinctions remain fundamental:

- monitoring ≠ detection;
- detection ≠ response;
- anomaly ≠ attack;
- anomaly ≠ compromise;
- alert ≠ incident;
- correlation ≠ causation;
- threat intelligence ≠ proof of compromise;
- telemetry ≠ assurance;
- telemetry volume ≠ monitoring effectiveness;
- monitoring coverage ≠ monitoring volume;
- technical restoration ≠ trusted monitoring state;
- supplier telemetry ≠ independent assurance;
- alternative telemetry ≠ independent telemetry;
- redundancy ≠ independence;
- monitoring ≠ prevention;
- continuous monitoring ≠ continuous assurance;
- internal threshold ≠ statutory threshold;
- internal classification ≠ legal classification;
- documentation ≠ demonstrated capability;
- automation ≠ accountability.
