# 22.04 — Large Language Model (LLM) Terminology

## Part 1 — LLM Fundamentals, Architecture, Core Components, and Language Processing

## 1. Introduction to Large Language Models

Large Language Models (LLMs) are among the most widely adopted technologies in Generative AI. They power conversational assistants, enterprise knowledge systems, coding assistants, document analysis platforms, AI-powered customer service, and numerous other business applications.

For cybersecurity and GRC professionals, understanding LLM terminology is essential because LLMs introduce specific technical characteristics, operational dependencies, security threats, and governance requirements.

An LLM is not simply a chatbot. It is a trained computational model that processes language-related information and generates outputs based on learned patterns, input context, and its model architecture.

This lesson establishes the technical vocabulary required to understand how LLMs operate, how they are deployed, and how their components influence enterprise security and governance.

### 1.1 Learning Objectives

By the end of this lesson, you should be able to:

- Explain the fundamental concepts behind LLMs.
- Distinguish LLMs from foundation models and other AI models.
- Understand Transformer-based architecture and its components.
- Explain tokenization, embeddings, attention, and context windows.
- Understand how LLMs process input and generate output.
- Distinguish model parameters, weights, and hyperparameters.
- Understand LLM inference and decoding terminology.
- Identify the enterprise security and governance implications of LLM architecture.

### 1.2 What Is a Large Language Model?

Definition:

A Large Language Model (LLM) is a machine learning model designed to process and generate human language by learning statistical and contextual patterns from large amounts of training data.

LLMs typically use neural network architectures, particularly Transformer-based architectures, although not every language model uses the same architecture.

They can perform a variety of language-related tasks, including:

- Text generation.
- Question answering.
- Summarization.
- Translation.
- Classification.
- Information extraction.
- Conversational interaction.
- Code generation.
- Document analysis.
- Language transformation.

Example:

A telecommunications operator deploys an LLM-based internal assistant.

An employee asks:

"Explain the security requirements for integrating Salesforce with our customer-facing e-commerce platform."

The LLM processes the request and generates a natural-language response based on its learned capabilities and any additional context supplied by the application.

GRC implications:

An LLM should be treated as an AI asset that requires:

- Defined ownership.
- Approved business purpose.
- Model identification and versioning.
- Security assessment.
- Data governance.
- Access control.
- Performance evaluation.
- Monitoring.
- Lifecycle management.

### 1.3 Large Language Model vs. Foundation Model

These concepts are related but not identical.

| Concept              | Definition                                                          | Distinction                                |
| -------------------- | ------------------------------------------------------------------- | ------------------------------------------ |
| Foundation Model     | A broadly trained model adaptable to multiple downstream tasks      | Broad category of reusable models          |
| Large Language Model | A model specialized in processing and generating language           | Focuses on language-related capabilities   |
| Generative AI Model  | A model capable of generating new content                           | Covers different content modalities        |
| Multimodal Model     | A model that processes or generates multiple information modalities | May support text, images, audio, and video |

Example:

A foundation model may be designed to process images and generate visual content.

An LLM focuses primarily on language-related processing and generation.

A multimodal LLM may combine language capabilities with image, audio, or video processing.

Important distinction:

Not every foundation model is an LLM, and not every LLM necessarily supports multimodal capabilities.

### 1.4 Language Model

Definition:

A Language Model is a computational model that learns statistical relationships between linguistic units and estimates the probability of language sequences.

It can predict likely subsequent tokens based on preceding context.

Example:

Given the input:

"The capital of France is..."

A language model may assign a high probability to the token sequence:

"Paris."

The model does not need to retrieve a fixed answer from a traditional database. It generates a continuation based on learned statistical relationships and the supplied context.

GRC implications:

Language models generate outputs based on learned patterns. Their responses must not automatically be treated as verified facts or authoritative business information.

### 1.5 Autoregressive Language Model

Definition:

An Autoregressive Language Model generates a sequence by predicting the next token based on previously available tokens.

It repeatedly generates additional tokens until a stopping condition is reached.

Example:

Input:

"Cybersecurity governance is important because"

Possible generation sequence:

```
Cybersecurity governance is important because
        |
        v
organizations
        |
        v
must
        |
        v
manage
        |
        v
security
        |
        v
risks.
```

Each generated token becomes part of the context used to predict subsequent tokens.

GRC implications:

Autoregressive generation can produce coherent but incorrect statements.

Organizations should validate outputs used in regulatory, contractual, financial, and security decisions.

### 1.6 Next-Token Prediction

Definition:

Next-Token Prediction is a training or inference objective in which a language model predicts the next token in a sequence based on the preceding context.

It is a central mechanism used by many autoregressive LLMs.

Example:

Input:

"An effective information security management system requires..."

The model estimates the probability of possible next tokens based on the context.

Possible continuation:

"...leadership commitment, risk management, and continual improvement."

GRC implications:

Next-token prediction explains why an LLM can generate plausible language without necessarily verifying factual correctness.

### 1.7 Language Generation

Definition:

Language Generation is the process through which a model produces new textual content based on its input, learned representations, and generation strategy.

Examples:

- Drafting emails.
- Writing technical documentation.
- Generating cybersecurity reports.
- Producing risk assessment narratives.
- Summarizing audit findings.

GRC implications:

Generated business documentation should be subject to appropriate review, approval, and traceability requirements.

## 2. LLM Architecture Fundamentals

Many modern LLMs use the Transformer architecture, introduced in the research paper Attention Is All You Need (2017).

The Transformer architecture changed natural language processing by enabling models to process relationships between tokens through attention mechanisms.

Understanding its components helps GRC professionals identify where security and operational risks may arise.

### 2.1 Transformer Architecture

Definition:

A Transformer is a neural network architecture that uses attention mechanisms to process relationships between elements in a sequence.

It is widely used in modern language models and other AI applications.

Core components:

- Tokenization.
- Token embeddings.
- Positional information.
- Attention mechanisms.
- Feed-forward neural networks.
- Normalization.
- Output layers.

Simplified architecture:

```
                 Input Text
                     |
                     v
                 Tokenization
                     |
                     v
               Token Embeddings
                     |
                     v
             Positional Information
                     |
                     v
               Transformer Layers
                     |
          +----------+----------+
          |                     |
          v                     v
      Attention            Feed-Forward
      Mechanism              Network
          |                     |
          +----------+----------+
                     |
                     v
                Output Layer
                     |
                     v
              Probability Scores
                     |
                     v
               Token Selection
                     |
                     v
              Generated Text
```

GRC implications:

Transformer architecture introduces important considerations involving model complexity, computational requirements, model security, data processing, and inference infrastructure.

### 2.2 Transformer Block

Definition:

A Transformer Block is a repeated computational unit within a Transformer architecture.

It typically contains an attention component and a feed-forward neural network, together with normalization and residual connection mechanisms.

A model generally contains multiple Transformer blocks stacked together.

Conceptual structure:

```
            Input Representation
                     |
                     v
              Self-Attention
                     |
                     v
              Residual Connection
                     |
                     v
               Normalization
                     |
                     v
             Feed-Forward Network
                     |
                     v
              Residual Connection
                     |
                     v
               Normalization
                     |
                     v
              Output Representation
```

The precise arrangement varies across Transformer implementations.

GRC implications:

The number and configuration of Transformer blocks contribute to computational requirements and model complexity.

However, the number of layers alone does not establish a model's security, accuracy, or suitability.

### 2.3 Encoder

Definition:

An Encoder is a neural network component that transforms input information into contextual representations.

In the original Transformer architecture, the encoder uses self-attention and feed-forward layers to process input sequences.

Example:

An encoder processes a sentence and generates contextual representations that capture relationships between words.

GRC implications:

Encoder-based models are commonly used for tasks such as classification, semantic representation, and information extraction.

### 2.4 Decoder

Definition:

A Decoder is a neural network component that generates or transforms output sequences using previously available information.

In the original Transformer architecture, the decoder uses masked self-attention and cross-attention mechanisms.

In decoder-only LLMs, the architecture uses decoder-style Transformer blocks with causal attention.

Example:

A decoder-only LLM receives a prompt and generates a response token by token.

GRC implications:

Understanding whether a model is encoder-based, decoder-based, or encoder-decoder helps clarify its architecture and intended capabilities.

### 2.5 Encoder-Only Model

Definition:

An Encoder-Only Model uses Transformer encoder layers to create contextual representations of input information.

These models are commonly used for language understanding tasks rather than unrestricted autoregressive text generation.

Example:

A model classifies customer support messages into categories:

- Billing.
- Technical support.
- Complaints.
- Account management.

GRC implications:

Encoder-only models may be suitable for classification and information analysis use cases. Their suitability should be evaluated against the actual business requirements.

### 2.6 Decoder-Only Model

Definition:

A Decoder-Only Model uses decoder-style Transformer layers and typically generates outputs through autoregressive next-token prediction.

This architecture is widely used in modern generative LLMs.

Examples of applications:

- Conversational assistants.
- Text generation.
- Code generation.
- Summarization.
- Question answering.

GRC implications:

Decoder-only models may generate extensive outputs and therefore require appropriate controls for content safety, sensitive information disclosure, and output validation.

### 2.7 Encoder-Decoder Model

Definition:

An Encoder-Decoder Model uses an encoder to process input information and a decoder to generate an output sequence.

The decoder can use information from the encoder through cross-attention.

Example:

A machine translation system processes an English sentence through its encoder and generates a corresponding Spanish sentence through its decoder.

GRC implications:

Organizations should understand the architecture when assessing model suitability, integration requirements, performance, and security characteristics.

### 2.8 Causal Language Modeling

Definition:

Causal Language Modeling is a training objective in which a model learns to predict subsequent tokens using only the preceding context.

It is commonly associated with autoregressive decoder-only language models.

Example:

Given:

"Information security protects"

The model learns to predict likely continuations such as:

"information", "systems", or "organizations".

GRC implications:

Causal language modeling explains the sequential generation process but does not provide an assurance mechanism for factual correctness.

### 2.9 Masked Language Modeling

Definition:

Masked Language Modeling is a training objective in which selected tokens within an input sequence are hidden, and the model learns to predict the missing information using surrounding context.

It is commonly associated with encoder-based language models.

Example:

Input:

"ISO 27001 provides requirements for an Information Security [MASK] System."

Expected prediction:

"Management."

GRC implications:

Masked language modeling is useful for understanding language representation and model training. It should not be confused with the autoregressive generation process used by many conversational LLMs.

### 2.10 Cross-Attention

Definition:

Cross-Attention is an attention mechanism that allows one sequence or representation to attend to another sequence or representation.

In an encoder-decoder Transformer, the decoder uses cross-attention to access information generated by the encoder.

Example:

During translation, the decoder attends to the encoded representation of the original sentence while generating the translated sentence.

GRC implications:

Cross-attention is relevant when assessing architectures that combine different input and output representations, including certain multimodal and encoder-decoder systems.

## 3. Tokenization and Text Representation

An LLM does not normally process human-readable sentences directly as complete words.

Text is first converted into smaller units called tokens, which are then represented numerically for model processing.

Understanding tokenization is important because it affects model input, output length, context capacity, computational cost, and potentially security behavior.

### 3.1 Token

Definition:

A Token is a discrete unit of information processed by a language model.

A token may represent:

- A complete word.
- Part of a word.
- A punctuation mark.
- A whitespace-related unit.
- A character or character sequence.
- Other language-specific units.

Example:

The sentence:

"Cybersecurity governance matters."

May be divided into several tokens.

A simplified illustration:

```
Cybersecurity | governance | matters | .
```

Actual tokenization depends on the tokenizer and model vocabulary.

GRC implications:

Token counts influence:

- Input and output limits.
- Model API costs.
- Context window utilization.
- Processing latency.
- Resource consumption.

Organizations should understand token-based pricing and usage limits when procuring hosted LLM services.

### 3.2 Tokenization

Definition:

Tokenization is the process of converting input text into tokens that can be represented and processed by a language model.

Example:

```
Input:
"AI governance requires accountability."

              |
              v

Tokenization:
["AI", " governance", " requires", " accountability", "."]

              |
              v

Token IDs:
[1452, 8921, 4510, 12034, 13]
```

The token IDs above are illustrative, not actual identifiers for a specific tokenizer.

GRC implications:

Tokenization affects processing cost, context limits, and the handling of multilingual or specialized enterprise information.

### 3.3 Tokenizer

Definition:

A Tokenizer is the software component responsible for converting text into tokens and mapping those tokens to numerical identifiers.

It may also convert token IDs back into readable text during output decoding.

Common tokenization approaches:

- Byte Pair Encoding (BPE).
- WordPiece.
- Unigram Language Model.
- SentencePiece-based tokenization.

GRC implications:

Organizations should ensure that the tokenizer used during model training and inference is compatible with the model.

Tokenizer mismatch can degrade output quality or cause processing inconsistencies.

### 3.4 Vocabulary

Definition:

A Vocabulary is the collection of tokens that a tokenizer recognizes and maps to token identifiers.

The vocabulary determines the available token units used by the model's text processing pipeline.

Example:

A tokenizer vocabulary may contain:

- Common words.
- Word fragments.
- Punctuation.
- Special tokens.
- Multilingual token units.

GRC implications:

Vocabulary design can influence language coverage, token efficiency, and performance on specialized terminology.

### 3.5 Token ID

Definition:

A Token ID is a numerical identifier assigned to a token within a tokenizer's vocabulary.

The model uses token IDs as inputs to its numerical processing pipeline.

Example:

```
Token: "security"
Token ID: 4821
```

This is a hypothetical example. Actual token IDs vary by tokenizer.

GRC implications:

Token IDs are model-specific representations. They should not be assumed to have the same meaning across different models or tokenizers.

### 3.6 Special Token

Definition:

A Special Token is a predefined token used to represent structural or control information within a model's input or output sequence.

Examples may include tokens representing:

- Beginning of a sequence.
- End of a sequence.
- Padding.
- Separation between segments.
- Role boundaries.
- Image or audio markers.
- Other model-specific instructions.

GRC implications:

Special tokens can influence how an application structures messages and how a model interprets input.

Incorrect handling may result in unexpected model behavior or integration problems.

### 3.7 Byte Pair Encoding (BPE)

Definition:

Byte Pair Encoding is a tokenization technique that builds a vocabulary by iteratively combining frequently occurring sequences of characters or bytes.

It is commonly used in language model tokenizers.

Conceptual example:

A word may initially be represented as smaller units:

```
governance
    |
    v
go + ver + nance
```

A tokenizer may combine frequently occurring sequences into larger token units.

The actual segmentation depends on the learned vocabulary.

GRC implications:

BPE can represent common language efficiently, but uncommon words, technical terminology, and multilingual content may require more tokens.

### 3.8 WordPiece

Definition:

WordPiece is a subword tokenization method that builds a vocabulary of frequently occurring word units and uses them to represent text.

It can split uncommon words into smaller subword components.

Example:

A hypothetical representation:

```
cybersecurity
      |
      v
cyber + ##security
```

The `##` notation is commonly associated with WordPiece implementations to indicate a continuation subword.

GRC implications:

WordPiece tokenization can influence how technical terms and unfamiliar vocabulary are represented during model processing.

### 3.9 SentencePiece

Definition:

SentencePiece is a tokenizer framework that can train subword tokenization models directly from raw text without requiring conventional word segmentation.

It supports approaches such as BPE and Unigram Language Model tokenization.

GRC implications:

SentencePiece is relevant when assessing multilingual model compatibility and the consistency of text processing across different languages.

### 3.10 Detokenization

Definition:

Detokenization is the process of converting token sequences or token IDs back into readable text.

It is commonly performed after a model generates its output.

Example:

```
Generated token IDs
        |
        v
Token sequence
        |
        v
Detokenization
        |
        v
Readable response
```

GRC implications:

Applications should correctly handle generated output, including encoding, formatting, and potentially unsafe content.

### 3.11 Subword Tokenization

Definition:

Subword Tokenization is a technique that divides text into units smaller than complete words but potentially larger than individual characters.

It helps language models represent common and uncommon words using a manageable vocabulary.

Example:

The word "misconfiguration" may be divided into smaller units rather than requiring a single vocabulary entry.

GRC implications:

Subword tokenization affects multilingual processing, technical terminology, token consumption, and model performance.

### 3.12 Token Efficiency

Definition:

Token Efficiency describes how effectively a tokenizer represents information using a limited number of tokens.

More efficient tokenization can reduce context consumption and computational requirements for equivalent content.

Example:

A technical document may require different token counts depending on:

- Language.
- Formatting.
- Special characters.
- Technical terminology.
- Tokenizer vocabulary.

GRC implications:

Token efficiency affects AI service cost management and operational capacity planning.

## 4. Embeddings and Numerical Representations

Language models process numerical representations rather than directly performing neural network computations on ordinary text.

Embeddings provide a mechanism for representing tokens and other information as vectors in a mathematical space.

### 4.1 Embedding

Definition:

An Embedding is a numerical vector representation of an object, such as a token, word, sentence, image, or other information, in a multidimensional space.

Embeddings allow machine learning systems to represent information in a form suitable for computational processing.

Example:

The words:

- Network.
- Router.
- Switch.
- Cybersecurity.

May be represented as numerical vectors.

Depending on the embedding model, semantically related concepts may have similar vector representations.

GRC implications:

Embeddings generated from confidential enterprise information may require security and privacy protections.

Organizations should consider access control, encryption, storage security, and data retention.

### 4.2 Token Embedding

Definition:

A Token Embedding is the numerical vector representation associated with a token in a model's embedding layer.

It converts a token ID into a vector that can be processed by subsequent neural network layers.

Example:

```
Token ID
   |
   v
Embedding Layer
   |
   v
Numerical Vector
   |
   v
Transformer Layers
```

GRC implications:

Token embeddings form part of the model's internal representation and are not equivalent to a human-readable definition of a word.

### 4.3 Embedding Dimension

Definition:

Embedding Dimension refers to the number of numerical values contained in an embedding vector.

Example:

A token embedding may be represented by a vector containing 768 numerical values.

This is an illustrative dimension, not a universal LLM configuration.

GRC implications:

Embedding dimensions contribute to model architecture, memory requirements, and computational characteristics.

### 4.4 Embedding Space

Definition:

An Embedding Space is the mathematical space in which vector representations are located.

The positions and relationships between vectors can reflect learned semantic or structural characteristics.

Example:

Concepts such as:

- Router.
- Network switch.
- Firewall.

May have related representations within an embedding space.

GRC implications:

Embedding similarity should not be treated as proof of factual equivalence or authorization to access information.

### 4.5 Positional Encoding

Definition:

Positional Encoding is a mechanism used in Transformer architectures to provide information about the position or order of tokens within a sequence.

Traditional attention mechanisms do not inherently encode sequence order, so positional information is introduced through the architecture.

Example:

Consider:

- "The employee approved the request."
- "The request approved the employee."

The words are similar, but their positions affect meaning.

Positional information helps the model distinguish token order.

GRC implications:

Positional mechanisms influence how models interpret long sequences and context. Their implementation varies between architectures.

### 4.6 Positional Embedding

Definition:

A Positional Embedding is a learned or otherwise constructed vector representation used to encode positional information within a sequence.

It may be combined with token embeddings before information is processed by Transformer layers.

GRC implications:

The positional representation method is relevant when evaluating architecture compatibility and context-length capabilities.

### 4.7 Relative Positional Encoding

Definition:

Relative Positional Encoding represents relationships between token positions rather than relying exclusively on absolute positions within a sequence.

It allows attention mechanisms to incorporate information about the relative distance or ordering between tokens.

GRC implications:

Relative position methods may influence long-context behavior and model architecture, but their presence does not automatically guarantee reliable long-context processing.

### 4.8 Rotary Positional Embedding (RoPE)

Definition:

Rotary Positional Embedding (RoPE) is a positional encoding technique that incorporates positional information through rotations applied to query and key representations within attention mechanisms.

It is used in several modern Transformer architectures.

GRC implications:

RoPE is relevant when assessing LLM architecture, context extension techniques, and compatibility between model configurations.

### 4.9 Latent Representation

Definition:

A Latent Representation is an internal numerical representation learned by a model that captures underlying patterns or features of input information.

These representations are not necessarily directly interpretable by humans.

Example:

An LLM internally represents relationships among concepts, language patterns, and contextual information through numerical activations.

GRC implications:

Latent representations should not be assumed to provide transparent explanations of model behavior.

### 4.10 Hidden State

Definition:

A Hidden State is an internal representation generated by a neural network layer during processing.

In a Transformer, hidden states represent contextual information associated with tokens as they pass through the model.

Example:

The hidden state associated with a token may change as it passes through multiple Transformer layers and incorporates contextual information.

GRC implications:

Hidden states are internal model computations. They should not be confused with stored conversation history, user memory, or an explicit knowledge database.

### 4.11 Activation

Definition:

An Activation is the numerical output produced by a neuron or neural network component after processing its input.

Activations represent intermediate computational results within the model.

GRC implications:

Activation analysis may be relevant to model interpretability and security research, but activations alone do not establish why a model produced a particular response.

## 5. Attention Mechanisms

Attention is one of the central concepts in Transformer-based LLMs.

It allows the model to evaluate relationships between tokens and determine which contextual information is relevant when processing a sequence.

### 5.1 Attention Mechanism

Definition:

An Attention Mechanism is a neural network mechanism that dynamically assigns importance to different elements of an input sequence when generating a representation or processing information.

Example:

Consider:

"The network engineer configured the firewall because it was vulnerable."

The model must interpret the relationship between "it" and the relevant preceding context.

Attention helps the model process contextual relationships between tokens.

GRC implications:

Attention mechanisms contribute to language processing, but attention weights should not automatically be interpreted as reliable explanations of model reasoning.

### 5.2 Self-Attention

Definition:

Self-Attention is an attention mechanism in which elements of a sequence evaluate relationships with other elements within the same sequence.

It allows a model to incorporate contextual information from multiple tokens when generating representations.

Example:

In the sentence:

"The security team investigated the incident after it was detected."

Self-attention helps the model process relationships between words across the sentence.

GRC implications:

Self-attention enables contextual language processing, but it does not guarantee that the model correctly interprets every sentence or factual relationship.

### 5.3 Scaled Dot-Product Attention

Definition:

Scaled Dot-Product Attention is the attention calculation used in the original Transformer architecture.

It calculates relationships between query and key vectors, scales the resulting scores, applies a softmax function, and uses the resulting weights to combine value vectors.

The formula is:

\\[ \operatorname{Attention}(Q,K,V) = \operatorname{softmax} \left( \frac{QK^T}{\sqrt{d_k}} \right)V \\]

Where:

- \\(Q\\) = Query matrix.
- \\(K\\) = Key matrix.
- \\(V\\) = Value matrix.
- \\(d_k\\) = Dimension of the key vectors.

Conceptual explanation:

The attention mechanism calculates how strongly each query relates to available keys and uses those relationships to combine corresponding values.

GRC implications:

Understanding this mechanism is useful for architecture discussions and model performance analysis, although GRC assessments normally focus on its operational implications rather than the underlying mathematical implementation.

### 5.4 Query, Key, and Value (QKV)

Definition:

Query, Key, and Value are three vector representations used in attention mechanisms.

- Query (Q): Represents the information being used to search for relevant context.
- Key (K): Represents information against which the query is compared.
- Value (V): Contains the information combined according to the calculated attention weights.

Example:

A model processes a sentence and calculates relationships between tokens.

The query and key representations determine which token relationships receive greater attention, while the value representations contribute contextual information.

GRC implications:

QKV are internal architectural components. They should not be confused with application-level queries, database keys, or encryption keys.

### 5.5 Multi-Head Attention

Definition:

Multi-Head Attention is an attention mechanism that performs multiple attention operations in parallel using different learned projections of the input representations.

The outputs of the attention heads are combined to form a richer representation.

Conceptual explanation:

Different attention heads can learn different patterns or relationships within the input sequence.

For example, some heads may capture relationships involving nearby tokens, while others may capture longer-distance relationships.

These are learned behaviors, not fixed semantic roles.

GRC implications:

Multi-head attention contributes to model complexity and computational requirements. It does not provide a direct guarantee of model explainability or security.

### 5.6 Attention Head

Definition:

An Attention Head is an individual attention operation within a multi-head attention mechanism.

Each head uses its own learned projections to calculate relationships between input representations.

GRC implications:

Attention heads are internal model components and are not independently equivalent to business functions, security controls, or separate AI agents.

### 5.7 Causal Attention

Definition:

Causal Attention is an attention mechanism that prevents a model from attending to future tokens when processing a sequence.

It is commonly used in autoregressive language models to preserve the next-token prediction objective.

Example:

When generating the next token, the model can use preceding tokens but cannot use tokens that have not yet been generated.

GRC implications:

Causal attention helps establish the generation process. It is not a security boundary and does not prevent malicious prompts or harmful outputs.

### 5.8 Attention Mask

Definition:

An Attention Mask is a mechanism that restricts which positions or tokens can participate in attention calculations.

Masks may be used to prevent attention to future tokens, padding positions, or otherwise restricted sequence elements.

GRC implications:

Attention masks are part of model computation. They should not be confused with application authorization or data access controls.

### 5.9 FlashAttention

Definition:

FlashAttention is an optimized attention algorithm designed to improve the efficiency of attention computation by reducing data movement between high-bandwidth memory and faster on-chip memory.

It can improve performance and memory efficiency when processing attention operations.

GRC implications:

FlashAttention is primarily an implementation and performance optimization.

Organizations should consider its relevance when assessing infrastructure requirements, model serving performance, and deployment compatibility.

### 5.10 Grouped-Query Attention (GQA)

Definition:

Grouped-Query Attention is an attention architecture in which multiple query heads share a smaller number of key and value heads.

It is designed to reduce memory and computational requirements compared with conventional multi-head attention configurations.

GRC implications:

GQA can influence inference efficiency and deployment resource requirements.

### 5.11 Multi-Query Attention (MQA)

Definition:

Multi-Query Attention is an attention architecture in which multiple query heads share a single key head and a single value head.

It reduces the memory requirements associated with key-value representations during inference.

GRC implications:

MQA is relevant to model-serving efficiency and inference infrastructure planning.

### 5.12 Key-Value Cache (KV Cache)

Definition:

A Key-Value Cache is a mechanism used during autoregressive inference to retain previously calculated key and value representations so that they do not need to be recomputed for every generated token.

Example:

When a model generates a long response, the KV cache stores attention information from previously processed tokens.

This can improve generation efficiency.

GRC implications:

KV caches may contain contextual information from prompts and generated sequences.

Organizations should assess:

- Memory isolation.
- Multi-tenant separation.
- Cache retention.
- Sensitive information exposure.
- Secure infrastructure configuration.
- Resource consumption.

## 6. LLM Parameters and Model Configuration

LLM parameters define the learned numerical structure and behavior of a trained model.

It is important to distinguish between model parameters, model weights, and hyperparameters because they have different technical and governance implications.

### 6.1 Model Parameters

Definition:

Model Parameters are the internal numerical values learned during model training that determine how a neural network processes information.

In neural networks, parameters commonly include weights and biases.

Example:

A Transformer model contains a large number of learned parameters across its attention layers, feed-forward networks, and other components.

GRC implications:

Model parameters represent valuable intellectual property and should be protected against unauthorized access, modification, and disclosure.

### 6.2 Model Weights

Definition:

Model Weights are learned numerical values that determine the strength of connections and transformations within a neural network.

They are a major component of a model's learned parameters.

GRC implications:

Model weights should be protected through secure storage, access control, integrity verification, and controlled distribution.

### 6.3 Bias

Definition:

A Bias is a learned parameter that adjusts a neuron's output independently of the weighted input contribution.

In neural networks, bias parameters help models learn flexible transformations.

Important distinction:

In neural network mathematics, a bias parameter is different from social or algorithmic bias.

- Neural network bias: A mathematical model parameter.
- Algorithmic bias: Systematic unfairness or undesirable differences in model outcomes.

GRC implications:

GRC assessments must distinguish between technical model components and fairness-related risks to avoid ambiguous terminology.

### 6.4 Hyperparameter

Definition:

A Hyperparameter is a configuration value selected outside the model's ordinary parameter-learning process that influences model training, architecture, or operation.

Examples:

- Learning rate.
- Batch size.
- Number of training epochs.
- Number of Transformer layers.
- Number of attention heads.
- Dropout rate.
- Maximum sequence length.

GRC implications:

Hyperparameter configurations should be documented and controlled because changes can affect model performance, reproducibility, and operational behavior.

### 6.5 Model Size

Definition:

Model Size refers to the scale of a model, commonly measured by the number of parameters, storage requirements, or other architectural characteristics.

Example:

An LLM may be described as having 7 billion parameters or 70 billion parameters.

GRC implications:

Model size influences deployment resources and operational costs, but parameter count alone does not establish quality, accuracy, or security.

### 6.6 Parameter Count

Definition:

Parameter Count is the total number of learned numerical parameters in a model.

Example:

A model with 7 billion parameters has approximately seven billion learned parameter values.

GRC implications:

Parameter count can help estimate model storage and computational requirements.

It should not be used as the sole measure of model capability or enterprise suitability.

### 6.7 Dense Model

Definition:

A Dense Model is a model architecture in which the relevant model parameters are generally activated and used during each forward pass, subject to the specific architecture and implementation.

Traditional dense Transformer models process tokens through their configured network layers.

GRC implications:

Dense models may have substantial computational requirements, depending on model size and deployment configuration.

### 6.8 Mixture of Experts (MoE)

Definition:

Mixture of Experts (MoE) is a neural network architecture that uses multiple specialized sub-networks, called experts, and a gating or routing mechanism to select which experts process particular inputs.

In many MoE architectures, only a subset of experts is activated for a given token.

Conceptual architecture:

```
                 Input Token
                      |
                      v
                 Router / Gate
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Expert 1    Expert 2    Expert 3
          |           |           |
          +-----------+-----------+
                      |
                      v
                Combined Output
```

GRC implications:

MoE architectures may introduce complexity in model performance, deployment, resource planning, and technical assurance.

### 6.9 Router

Definition:

A Router is a component in an MoE architecture that determines which expert networks should process a particular input or token.

GRC implications:

Routing behavior is an architectural feature that may influence computational efficiency and model execution characteristics.

### 6.10 Expert

Definition:

An Expert is an individual sub-network within a Mixture of Experts architecture.

Each expert is a learned computational component that processes information when selected by the routing mechanism.

GRC implications:

Experts are internal model components. Their existence does not necessarily imply that each expert is independently trained, governed, or specialized for a human-defined business function.

### 6.11 Active Parameters

Definition:

Active Parameters are the model parameters used during a particular forward pass or inference operation.

In sparse MoE architectures, only a subset of the total parameters may be active for a given token.

GRC implications:

Active parameter count may influence inference resource requirements, but it does not by itself determine the model's security or reliability.

### 6.12 Total Parameters vs. Active Parameters

| Concept           | Meaning                                                            |
| ----------------- | ------------------------------------------------------------------ |
| Total Parameters  | All learned parameters contained in the model                      |
| Active Parameters | Parameters used during a particular computation                    |
| Dense Model       | Generally uses its configured network parameters during processing |
| Sparse MoE Model  | Activates selected experts for particular inputs or tokens         |

Example:

An MoE model may contain 100 billion total parameters while activating only a smaller subset during the processing of an individual token.

The exact behavior depends on its architecture.

## 7. LLM Context and Sequence Management

LLMs operate on sequences of tokens. Their ability to process long documents, conversations, and complex instructions depends on architectural limits and runtime configuration.

### 7.1 Context

Definition:

Context is the information available to a model when processing an input and generating an output.

It may include:

- System instructions.
- Developer instructions.
- User prompts.
- Conversation history.
- Retrieved documents.
- Tool outputs.
- Other application-supplied information.

GRC implications:

Context may contain confidential information, so organizations should apply appropriate data access, retention, and isolation controls.

### 7.2 Context Window

Definition:

A Context Window is the maximum amount of token information that a model can process within a particular inference context.

The context window may include both input tokens and generated output tokens, depending on the model's implementation and service configuration.

Example:

A model supports a context window of 128,000 tokens.

The application must manage system instructions, user input, conversation history, and retrieved information within the available capacity.

GRC implications:

Context windows influence:

- Information exposure.
- Processing costs.
- Application performance.
- Retrieval architecture.
- Conversation management.
- Potential context overflow.

### 7.3 Context Length

Definition:

Context Length refers to the number of tokens included in a model's current input sequence or supported context configuration.

Distinction:

Context length describes the size of the sequence being processed. Context window describes the model's maximum supported context capacity under a particular configuration.

### 7.4 Sequence Length

Definition:

Sequence Length is the number of tokens contained in a sequence processed by a model.

Example:

A user submits a prompt containing 2,000 tokens.

The input sequence length is 2,000 tokens, excluding any additional context inserted by the application.

GRC implications:

Sequence length affects memory usage, processing time, and resource consumption.

### 7.5 Maximum Sequence Length

Definition:

Maximum Sequence Length is the maximum token sequence length supported by a model or a particular model configuration.

It may be constrained by architecture, training configuration, runtime implementation, or service limits.

GRC implications:

Organizations should validate the maximum sequence length against actual business requirements, especially when processing large contracts, audit reports, or technical documentation.

### 7.6 Context Overflow

Definition:

Context Overflow occurs when the total token content supplied to a model exceeds its supported context capacity.

Example:

An application attempts to submit:

- 10,000 tokens of system and developer instructions.
- 90,000 tokens of conversation history.
- 40,000 tokens of retrieved documents.

The combined input exceeds a model configured for a 128,000-token context window.

Potential consequences:

- Request rejection.
- Truncation.
- Loss of relevant context.
- Processing errors.
- Increased application complexity.

GRC implications:

Applications should implement context management, prioritization, truncation policies, and error handling.

### 7.7 Context Truncation

Definition:

Context Truncation is the removal of some input or conversation content when the available context capacity is insufficient.

The application or model-serving system may remove older, lower-priority, or otherwise selected content.

GRC implications:

Truncation may remove important qualifications, instructions, or evidence.

Critical business applications should detect and manage truncation rather than silently assuming that the model received the complete information.

### 7.8 Long-Context Model

Definition:

A Long-Context Model is a model designed or configured to process substantially longer token sequences than models with shorter context limits.

Example:

A model capable of processing large technical documents may be used to summarize lengthy security audit reports.

GRC implications:

Long-context capabilities increase processing capacity but do not guarantee that every relevant detail will be correctly identified or interpreted.

### 7.9 Long-Context Retrieval

Definition:

Long-Context Retrieval is the process of identifying and using relevant information from a large context supplied to a model.

It is concerned with the model's ability to locate and use relevant information within extensive input sequences.

GRC implications:

Organizations should evaluate whether critical information is correctly retrieved and used when supplied with long documents or extensive conversation histories.

### 7.10 Lost in the Middle

Definition:

Lost in the Middle describes an observed limitation in some long-context language model configurations where information positioned in the middle of a long input may be used less reliably than information placed near the beginning or end.

The effect varies by model, task, and context configuration.

Example:

An AI assistant receives a lengthy audit report containing a critical finding in the middle of the document.

The generated summary omits that finding despite the full document being supplied.

GRC implications:

Long-document processing should be evaluated with representative tests to ensure that critical evidence is not overlooked.

### Core Principle

An LLM processes language through numerical representations, learned model parameters, and computational mechanisms such as attention and token prediction. Understanding these internal components is essential for assessing model capabilities, limitations, performance, and security dependencies. However, technical sophistication and architectural scale do not establish factual accuracy, security, or suitability for enterprise use.
