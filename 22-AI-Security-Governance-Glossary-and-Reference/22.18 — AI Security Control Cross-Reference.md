# 22.18 — AI Security Control Cross-Reference

## Part 1 — AI Security Control Mapping Foundations, Governance Principles, and Control Framework Architecture

### 1. Introduction

AI security governance requires organizations to translate security requirements, regulatory obligations, and risk-management expectations into measurable and testable controls.

Organizations often adopt multiple frameworks, including:

- ISO/IEC 42001.
- ISO/IEC 27001 and ISO/IEC 27002.
- NIST AI Risk Management Framework.
- NIST Cybersecurity Framework.
- NIST SP 800-53.
- NIST Secure Software Development Framework.
- OWASP Top 10 for LLM Applications.
- MITRE ATLAS.
- EU AI Act.
- GDPR.
- CIS Controls.
- Cloud Security Alliance Cloud Controls Matrix.

The challenge is that these references frequently address overlapping security and governance objectives using different terminology, structures, and levels of detail.

For example:

- ISO/IEC 42001 addresses AI management-system requirements.
- ISO/IEC 27001 addresses information security management.
- NIST AI RMF addresses AI risk management.
- OWASP identifies application-level AI security risks.
- MITRE ATLAS describes adversarial techniques targeting AI systems.
- The EU AI Act establishes legally binding obligations for applicable AI systems and actors.

A mature organization should not create an entirely separate control environment for each framework.

Instead, it should establish a unified AI security control framework that maps requirements to common control objectives, implementation activities, accountable owners, and evidence.

The central objective of this chapter is to create a practical cross-reference between AI governance requirements, cybersecurity controls, technical safeguards, regulatory obligations, and audit evidence.

### 2. Understanding Control Cross-Referencing

Control cross-referencing is the process of mapping requirements from multiple standards, frameworks, regulations, and security references to a common set of organizational controls.

It allows an organization to identify:

1. Overlapping requirements.
2. Unique regulatory obligations.
3. Existing control coverage.
4. Missing controls.
5. Control implementation gaps.
6. Evidence requirements.
7. Control ownership.
8. Opportunities to reduce duplicated compliance activities.

#### 2.1 What Is a Control?

A control is a measure designed to modify risk.

Controls can be policies, procedures, technical mechanisms, organizational activities, or combinations of these.

Examples include:

- AI governance policy.
- AI system inventory.
- AI risk assessment.
- Role-based access control.
- Encryption.
- Prompt injection testing.
- Model validation.
- Human oversight.
- Third-party security assessments.
- Security incident response.

A control should have a defined objective and sufficient implementation detail to allow its effectiveness to be evaluated.

#### 2.2 Control Cross-Reference Example

Consider an enterprise requirement:

All production AI systems must undergo documented security risk assessments before deployment.

This requirement can be mapped to several references.

| Reference        | Relevant requirement or area                            | Relationship                                     |
| ---------------- | ------------------------------------------------------- | ------------------------------------------------ |
| ISO/IEC 42001    | Clause 6.1 — Actions to address risks and opportunities | AI management-system risk planning               |
| ISO/IEC 27001    | Clause 6.1.2 — Information security risk assessment     | Information security risk assessment methodology |
| ISO/IEC 23894    | AI risk management guidance                             | AI-specific risk identification and assessment   |
| NIST AI RMF      | MAP and MEASURE                                         | AI context and risk measurement                  |
| EU AI Act        | Article 9, where applicable                             | Risk management for high-risk AI systems         |
| NIST SP 800-53   | RA-3 — Risk Assessment                                  | Security risk assessment                         |
| OWASP LLM Top 10 | Relevant application threat categories                  | Identification of AI application security risks  |

These references are related, but they are not identical.

For example, an ISO/IEC 27001 information security risk assessment does not automatically satisfy every requirement of an AI-specific risk assessment under ISO/IEC 42001 or the EU AI Act.

The organization must assess the scope and intended purpose of each requirement.

### 3. Standards, Frameworks, Regulations, and Threat Models — Different Control Mapping Purposes

Before creating a cross-reference matrix, it is important to understand the role of each reference.

| Reference type                 | Primary purpose                                        | Example                           | Control mapping contribution                            |
| ------------------------------ | ------------------------------------------------------ | --------------------------------- | ------------------------------------------------------- |
| Management system standard     | Establish management-system requirements               | ISO/IEC 42001                     | Governance, accountability, continual improvement       |
| Security management standard   | Establish information security management requirements | ISO/IEC 27001                     | Security policies, risk treatment, assurance            |
| Control standard               | Describe security controls                             | ISO/IEC 27002                     | Detailed control objectives and implementation guidance |
| Risk management framework      | Structure risk identification and treatment            | NIST AI RMF                       | AI risk-management activities                           |
| Cybersecurity framework        | Organize cybersecurity capabilities                    | NIST CSF 2.0                      | Governance, protection, detection, response, recovery   |
| Regulatory framework           | Establish legally enforceable obligations              | EU AI Act                         | Mandatory legal requirements within scope               |
| Application security framework | Identify technical security risks                      | OWASP Top 10 for LLM Applications | AI application threat coverage                          |
| Threat framework               | Describe adversarial behavior                          | MITRE ATLAS                       | Threat modeling and security testing                    |
| Assurance framework            | Define criteria for evaluating controls                | SOC 2 Trust Services Criteria     | Independent control assurance                           |

Important distinction: A threat framework is not automatically a control framework, and a control framework is not automatically a regulatory compliance framework.

For example, MITRE ATLAS helps organizations understand adversarial techniques targeting AI systems. It does not independently establish a complete set of mandatory enterprise governance controls.

### 4. The Three Levels of Control Mapping

A practical AI security control cross-reference should operate at three levels.

## Three-Level Control Mapping Model

Level 1 — Regulatory and Framework Requirements

What must the organization achieve?

Examples: EU AI Act Article 9, ISO/IEC 42001 requirements, NIST AI RMF outcomes.

Level 2 — Enterprise Control Objectives

What organizational control must exist?

Examples: AI risk assessment, access control, model validation, incident response.

Level 3 — Technical and Operational Implementation

How is the control implemented and evidenced?

Examples: IAM configurations, risk registers, testing reports, approval records, audit logs.

#### 4.1 Level 1 — Regulatory and Framework Requirements

This level identifies the source requirements.

Examples:

- ISO/IEC 42001 Clause 6.1.
- ISO/IEC 27001 Annex A.
- NIST AI RMF GOVERN.
- EU AI Act Article 9.
- GDPR Article 32.
- NIST SP 800-53 RA-3.

The organization must record the exact requirement, applicability, and source.

#### 4.2 Level 2 — Enterprise Control Objectives

This level converts multiple requirements into common control objectives.

Examples:

- Establish an enterprise AI governance policy.
- Maintain an AI system inventory.
- Perform AI security risk assessments.
- Enforce access restrictions.
- Conduct AI security testing.
- Establish AI incident response.
- Monitor third-party AI providers.

This is where overlapping requirements can be consolidated.

#### 4.3 Level 3 — Technical and Operational Implementation

This level defines how the controls operate in practice.

For example:

| Control objective                  | Implementation                                            | Evidence                       |
| ---------------------------------- | --------------------------------------------------------- | ------------------------------ |
| Restrict AI system access          | Integrate AI applications with enterprise IAM and RBAC    | Access-control configurations  |
| Protect AI data                    | Encrypt data at rest and in transit                       | Encryption configurations      |
| Prevent unauthorized RAG retrieval | Enforce source-system authorization during retrieval      | RAG authorization test results |
| Detect prompt injection            | Perform adversarial testing and monitor suspicious inputs | AI red-team reports            |
| Govern model changes               | Require documented approval before production deployment  | Change approval records        |

A control is not complete simply because a policy describes it.

The organization must demonstrate that it is implemented and operating effectively.

### 9. Control Design, Implementation, and Operating Effectiveness

One of the most important distinctions in GRC is the difference between control design, implementation, and operating effectiveness.

These are three separate assessment dimensions.

| Assessment dimension    | Question                                                   | Example                                                                        |
| ----------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Design effectiveness    | Is the control appropriately designed to address the risk? | Does the access-control design prevent unauthorized customer record retrieval? |
| Implementation          | Has the control actually been deployed?                    | Is authorization integrated into the production retrieval service?             |
| Operating effectiveness | Does the control work consistently over time?              | Do periodic tests demonstrate that unauthorized users are blocked?             |

#### 9.1 Example — RAG Authorization Control

Risk:

An employee retrieves customer records through an AI assistant without having authorization in Salesforce.

Control objective:

Prevent unauthorized retrieval and disclosure of customer information.

Control design:

The AI application must validate the authenticated user's identity and enforce Salesforce record-level permissions before retrieving information.

Implementation:

- Integrate enterprise identity.
- Pass user context to the retrieval service.
- Enforce record-level authorization.
- Log retrieval activity.
- Prevent unauthorized service-account access.

Operating effectiveness testing:

1. Select a sample of employee accounts.
2. Identify records accessible to each employee.
3. Submit AI retrieval requests for authorized records.
4. Submit AI retrieval requests for unauthorized records.
5. Verify that unauthorized retrieval is denied.
6. Review the corresponding logs.
7. Investigate exceptions.

Audit conclusion: A written access-control policy is not sufficient evidence that RAG authorization works. The organization must validate the technical enforcement mechanism.

### 10. Common Control Mapping Mistakes

Control cross-referencing can create a false impression of compliance if performed incorrectly.

| Mistake                                         | Why it is problematic                                                   | Correct approach                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| Treating all framework references as identical  | Different references have different scopes and requirements             | Map the actual requirement and control objective          |
| Assuming one control satisfies every regulation | Legal obligations may require additional measures                       | Assess each obligation independently                      |
| Mapping only by keywords                        | Similar terminology does not prove equivalent control coverage          | Compare intent, scope, applicability, and evidence        |
| Treating policies as proof of effectiveness     | Policies do not demonstrate operational performance                     | Test implementation and operating effectiveness           |
| Ignoring AI-specific threats                    | Traditional security controls may miss prompt injection and model risks | Add AI-specific controls and threat testing               |
| Duplicating controls across frameworks          | Creates unnecessary administrative overhead                             | Establish common controls with multiple mappings          |
| Ignoring regulatory applicability               | Not every law applies to every AI system                                | Document scope and legal applicability                    |
| Treating threat frameworks as control standards | Threat descriptions do not automatically establish mandatory controls   | Convert relevant threats into explicit defensive controls |
| Treating certification as universal compliance  | Certification covers a defined scope and criteria                       | Assess every applicable legal obligation separately       |
| Ignoring control ownership                      | Controls may exist without accountable operators                        | Assign control owners and evidence responsibilities       |

### 12. Summary and Core Principle

This part established the foundations for creating an enterprise AI security control cross-reference.

The main concepts are:

- Control cross-referencing maps multiple requirements to common enterprise control objectives.
- Regulatory requirements, management-system standards, cybersecurity frameworks, and threat models serve different purposes.
- A three-level mapping structure connects requirements, control objectives, and implementation evidence.
- ISO/IEC 42001 provides the AI management-system foundation.
- ISO/IEC 27001 and ISO/IEC 27002 provide the information security management and control foundation.
- NIST AI RMF and NIST CSF provide structured risk and cybersecurity outcomes.
- NIST SP 800-53 provides detailed security and privacy controls.
- OWASP and MITRE ATLAS support AI-specific application security and threat-informed testing.
- Control design, implementation, and operating effectiveness must be evaluated separately.

Core Principle: A control cross-reference is valuable only when it establishes a defensible connection between an applicable requirement, a clearly defined control objective, an implemented safeguard, an accountable owner, and verifiable evidence. Mapping framework references without validating actual control effectiveness creates an appearance of compliance rather than effective AI security governance.
