# 22.18 — AI Security Control Cross-Reference

## Part 1 — AI Security Control Mapping Foundations, Governance Principles, and Control Framework Architecture

### 1. Introduction

AI security governance requires organizations to translate security requirements, regulatory obligations, and risk-management expectations into measurable and testable controls.

Organizations often adopt multiple frameworks, including:

- ISO/IEC 42001.
- ISO/IEC 27001 and ISO/IEC 27002.
- NIST AI Risk Management Framework.
- NIST Cybersecurity Framework.
- NIST SP 800-53.
- NIST Secure Software Development Framework.
- OWASP Top 10 for LLM Applications.
- MITRE ATLAS.
- EU AI Act.
- GDPR.
- CIS Controls.
- Cloud Security Alliance Cloud Controls Matrix.

The challenge is that these references frequently address overlapping security and governance objectives using different terminology, structures, and levels of detail.

For example:

- ISO/IEC 42001 addresses AI management-system requirements.
- ISO/IEC 27001 addresses information security management.
- NIST AI RMF addresses AI risk management.
- OWASP identifies application-level AI security risks.
- MITRE ATLAS describes adversarial techniques targeting AI systems.
- The EU AI Act establishes legally binding obligations for applicable AI systems and actors.

A mature organization should not create an entirely separate control environment for each framework.

Instead, it should establish a unified AI security control framework that maps requirements to common control objectives, implementation activities, accountable owners, and evidence.

The central objective of this chapter is to create a practical cross-reference between AI governance requirements, cybersecurity controls, technical safeguards, regulatory obligations, and audit evidence.

### 2. Understanding Control Cross-Referencing

Control cross-referencing is the process of mapping requirements from multiple standards, frameworks, regulations, and security references to a common set of organizational controls.

It allows an organization to identify:

1. Overlapping requirements.
2. Unique regulatory obligations.
3. Existing control coverage.
4. Missing controls.
5. Control implementation gaps.
6. Evidence requirements.
7. Control ownership.
8. Opportunities to reduce duplicated compliance activities.

#### 2.1 What Is a Control?

A control is a measure designed to modify risk.

Controls can be policies, procedures, technical mechanisms, organizational activities, or combinations of these.

Examples include:

- AI governance policy.
- AI system inventory.
- AI risk assessment.
- Role-based access control.
- Encryption.
- Prompt injection testing.
- Model validation.
- Human oversight.
- Third-party security assessments.
- Security incident response.

A control should have a defined objective and sufficient implementation detail to allow its effectiveness to be evaluated.

#### 2.2 Control Cross-Reference Example

Consider an enterprise requirement:

All production AI systems must undergo documented security risk assessments before deployment.

This requirement can be mapped to several references.

| Reference        | Relevant requirement or area                            | Relationship                                     |
| ---------------- | ------------------------------------------------------- | ------------------------------------------------ |
| ISO/IEC 42001    | Clause 6.1 — Actions to address risks and opportunities | AI management-system risk planning               |
| ISO/IEC 27001    | Clause 6.1.2 — Information security risk assessment     | Information security risk assessment methodology |
| ISO/IEC 23894    | AI risk management guidance                             | AI-specific risk identification and assessment   |
| NIST AI RMF      | MAP and MEASURE                                         | AI context and risk measurement                  |
| EU AI Act        | Article 9, where applicable                             | Risk management for high-risk AI systems         |
| NIST SP 800-53   | RA-3 — Risk Assessment                                  | Security risk assessment                         |
| OWASP LLM Top 10 | Relevant application threat categories                  | Identification of AI application security risks  |

These references are related, but they are not identical.

For example, an ISO/IEC 27001 information security risk assessment does not automatically satisfy every requirement of an AI-specific risk assessment under ISO/IEC 42001 or the EU AI Act.

The organization must assess the scope and intended purpose of each requirement.

### 3. Standards, Frameworks, Regulations, and Threat Models — Different Control Mapping Purposes

Before creating a cross-reference matrix, it is important to understand the role of each reference.

| Reference type                 | Primary purpose                                        | Example                           | Control mapping contribution                            |
| ------------------------------ | ------------------------------------------------------ | --------------------------------- | ------------------------------------------------------- |
| Management system standard     | Establish management-system requirements               | ISO/IEC 42001                     | Governance, accountability, continual improvement       |
| Security management standard   | Establish information security management requirements | ISO/IEC 27001                     | Security policies, risk treatment, assurance            |
| Control standard               | Describe security controls                             | ISO/IEC 27002                     | Detailed control objectives and implementation guidance |
| Risk management framework      | Structure risk identification and treatment            | NIST AI RMF                       | AI risk-management activities                           |

### 4. The Three Levels of Control Mapping

A practical AI security control cross-reference should operate at three levels.

## Three-Level Control Mapping Model

Level 1 — Regulatory and Framework Requirements

What must the organization achieve?

Examples: EU AI Act Article 9, ISO/IEC 42001 requirements, NIST AI RMF outcomes.

Level 2 — Enterprise Control Objectives

What organizational control must exist?

Examples: AI risk assessment, access control, model validation, incident response.

Level 3 — Technical and Operational Implementation

How is the control implemented and evidenced?

Examples: IAM configurations, risk registers, testing reports, approval records, audit logs.

#### 4.1 Level 1 — Regulatory and Framework Requirements

This level identifies the source requirements.

Examples:

- ISO/IEC 42001 Clause 6.1.
- ISO/IEC 27001 Annex A.
- NIST AI RMF GOVERN.
- EU AI Act Article 9.
- GDPR Article 32.
- NIST SP 800-53 RA-3.

The organization must record the exact requirement, applicability, and source.

#### 4.2 Level 2 — Enterprise Control Objectives

This level converts multiple requirements into common control objectives.

Examples:

- Establish an enterprise AI governance policy.
- Maintain an AI system inventory.
- Perform AI security risk assessments.
- Enforce access restrictions.
- Conduct AI security testing.
- Establish AI incident response.
- Monitor third-party AI providers.

This is where overlapping requirements can be consolidated.

#### 4.3 Level 3 — Technical and Operational Implementation

This level defines how the controls operate in practice.

For example:

| Control objective                  | Implementation                                            | Evidence                       |
| ---------------------------------- | --------------------------------------------------------- | ------------------------------ |
| Restrict AI system access          | Integrate AI applications with enterprise IAM and RBAC    | Access-control configurations  |
| Protect AI data                    | Encrypt data at rest and in transit                       | Encryption configurations      |
| Prevent unauthorized RAG retrieval | Enforce source-system authorization during retrieval      | RAG authorization test results |
| Detect prompt injection            | Perform adversarial testing and monitor suspicious inputs | AI red-team reports            |
| Govern model changes               | Require documented approval before production deployment  | Change approval records        |

A control is not complete simply because a policy describes it.

The organization must demonstrate that it is implemented and operating effectively.

### 9. Control Design, Implementation, and Operating Effectiveness

One of the most important distinctions in GRC is the difference between control design, implementation, and operating effectiveness.

These are three separate assessment dimensions.

| Assessment dimension    | Question                                                   | Example                                                                        |
| ----------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Design effectiveness    | Is the control appropriately designed to address the risk? | Does the access-control design prevent unauthorized customer record retrieval? |
| Implementation          | Has the control actually been deployed?                    | Is authorization integrated into the production retrieval service?             |
| Operating effectiveness | Does the control work consistently over time?              | Do periodic tests demonstrate that unauthorized users are blocked?             |

#### 9.1 Example — RAG Authorization Control

Risk:

An employee retrieves customer records through an AI assistant without having authorization in Salesforce.

Control objective:

Prevent unauthorized retrieval and disclosure of customer information.

Control design:

The AI application must validate the authenticated user's identity and enforce Salesforce record-level permissions before retrieving information.

Implementation:

- Integrate enterprise identity.
- Pass user context to the retrieval service.
- Enforce record-level authorization.
- Log retrieval activity.
- Prevent unauthorized service-account access.

Operating effectiveness testing:

1. Select a sample of employee accounts.
2. Identify records accessible to each employee.
3. Submit AI retrieval requests for authorized records.
4. Submit AI retrieval requests for unauthorized records.
5. Verify that unauthorized retrieval is denied.
6. Review the corresponding logs.
7. Investigate exceptions.

Audit conclusion: A written access-control policy is not sufficient evidence that RAG authorization works. The organization must validate the technical enforcement mechanism.

### 10. Common Control Mapping Mistakes

Control cross-referencing can create a false impression of compliance if performed incorrectly.

| Mistake                                         | Why it is problematic                                                   | Correct approach                                          |
| ----------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| Treating all framework references as identical  | Different references have different scopes and requirements             | Map the actual requirement and control objective          |
| Assuming one control satisfies every regulation | Legal obligations may require additional measures                       | Assess each obligation independently                      |
| Mapping only by keywords                        | Similar terminology does not prove equivalent control coverage          | Compare intent, scope, applicability, and evidence        |
| Treating policies as proof of effectiveness     | Policies do not demonstrate operational performance                     | Test implementation and operating effectiveness           |
| Ignoring AI-specific threats                    | Traditional security controls may miss prompt injection and model risks | Add AI-specific controls and threat testing               |
| Duplicating controls across frameworks          | Creates unnecessary administrative overhead                             | Establish common controls with multiple mappings          |
| Ignoring regulatory applicability               | Not every law applies to every AI system                                | Document scope and legal applicability                    |
| Treating threat frameworks as control standards | Threat descriptions do not automatically establish mandatory controls   | Convert relevant threats into explicit defensive controls |
| Treating certification as universal compliance  | Certification covers a defined scope and criteria                       | Assess every applicable legal obligation separately       |
| Ignoring control ownership                      | Controls may exist without accountable operators                        | Assign control owners and evidence responsibilities       |

### 12. Summary and Core Principle

This part established the foundations for creating an enterprise AI security control cross-reference.

The main concepts are:

- Control cross-referencing maps multiple requirements to common enterprise control objectives.
- Regulatory requirements, management-system standards, cybersecurity frameworks, and threat models serve different purposes.
- A three-level mapping structure connects requirements, control objectives, and implementation evidence.
- ISO/IEC 42001 provides the AI management-system foundation.
- ISO/IEC 27001 and ISO/IEC 27002 provide the information security management and control foundation.
- NIST AI RMF and NIST CSF provide structured risk and cybersecurity outcomes.
- NIST SP 800-53 provides detailed security and privacy controls.
- OWASP and MITRE ATLAS support AI-specific application security and threat-informed testing.
- Control design, implementation, and operating effectiveness must be evaluated separately.

Core Principle: A control cross-reference is valuable only when it establishes a defensible connection between an applicable requirement, a clearly defined control objective, an implemented safeguard, an accountable owner, and verifiable evidence. Mapping framework references without validating actual control effectiveness creates an appearance of compliance rather than effective AI security governance.

### 6. Control Domain IAM — Identity and Access Management



IAM

&#x20;Identity and Access Management



AI systems introduce additional identities, permissions, and access paths.

Traditional IAM must be extended to cover:

- Human users.
- AI application identities.
- Model service accounts.
- API identities.
- AI agents.
- External provider accounts.
- Vector database identities.
- Administrative and privileged accounts.
- Tool execution permissions.

One of the most important AI security principles is that an AI model must not be treated as an authorized security principal merely because it generates a request.

An AI agent requesting an action does not automatically have permission to execute it.

Authorization must be enforced by the application, identity provider, API gateway, or target system.

#### 6.3 AI Agent Authorization Architecture

Consider an AI assistant that can:

- Retrieve customer records.
- Create service tickets.
- Update customer details.
- Initiate billing adjustments.
- Submit requests to external APIs.

The application must enforce permissions independently of the model's instructions.

```
                 AUTHENTICATED USER
                         |
                         v
                 AI APPLICATION
                         |
                         v
                 AI AGENT / LLM
                         |
                         v
                  TOOL REQUEST
                         |
                         v
                AUTHORIZATION GATE
                         |
                 +-------+-------+
                 |               |
              APPROVED         DENIED
                 |               |
                 v               v
           EXECUTE ACTION    BLOCK ACTION
                 |
                 v
          TARGET ENTERPRISE API
                 |
                 v
              AUDIT LOG
```

#### 6.4 Required Authorization Controls

| Control                  | Implementation                                                                |
| ------------------------ | ----------------------------------------------------------------------------- |
| User authentication      | Authenticate the human user before AI interaction                             |
| Identity propagation     | Pass trusted identity context to downstream services                          |
| Tool authorization       | Verify permission for every requested tool action                             |
| Least privilege          | Grant agents only the minimum necessary permissions                           |
| Transaction restrictions | Apply limits to financial or sensitive actions                                |
| Human approval           | Require approval for high-impact or irreversible operations where appropriate |
| Credential protection    | Store API secrets in an approved secrets-management system                    |
| Session control          | Apply appropriate session expiration and revocation                           |
| Audit logging            | Record user, agent, tool, action, authorization result, and timestamp         |
| Access review            | Periodically validate human and non-human permissions                         |

Example: A customer-service employee may have permission to view customer account details but not to approve a financial credit adjustment. The AI assistant must not bypass that restriction simply because the employee asks it to execute the action.

#### 3.4 AI Development Security Requirements

A. Source code security

- Enforce repository access controls.
- Protect critical branches.
- Require peer review for sensitive changes.
- Apply static application security testing (SAST).
- Scan dependencies for known vulnerabilities.
- Detect exposed credentials and secrets.
- Maintain code provenance and commit traceability.

B. Dataset security

- Validate dataset sources.
- Record dataset ownership and provenance.
- Check for unauthorized modifications.
- Establish dataset versioning.
- Restrict access to sensitive training data.
- Detect suspicious or anomalous dataset changes.
- Document dataset approval before training.

C. Model artifact security

- Restrict access to model repositories.
- Validate model integrity using cryptographic hashes or signatures.
- Maintain model version history.
- Scan model packages and associated dependencies.
- Restrict untrusted model loading.
- Secure model serialization and deserialization.
- Maintain provenance of externally sourced models.

D. Deployment security

- Require documented security approval.
- Apply production configuration baselines.
- Restrict deployment permissions.
- Use approved model registries.
- Maintain rollback capability.
- Separate production from development environments.
- Log deployment and configuration changes.

#### 4.3 Model Security Threats

| Threat                        | Description                                                                       | Security objective                     |
| ----------------------------- | --------------------------------------------------------------------------------- | -------------------------------------- |
| Model extraction              | An attacker queries a model to reproduce its behavior or functionality            | Protect model intellectual property    |
| Model inversion               | An attacker attempts to infer information about training data from model behavior | Protect sensitive training information |
| Membership inference          | An attacker tests whether a particular record was included in training data       | Protect training-data privacy          |
| Data poisoning                | Malicious or manipulated training data influences model behavior                  | Preserve training-data integrity       |
| Model poisoning               | Model parameters or the model-learning process are maliciously manipulated        | Preserve model integrity               |
| Adversarial evasion           | Carefully crafted inputs cause incorrect model predictions or behavior            | Improve robustness                     |
| Backdoor attack               | A model is manipulated to behave maliciously when a trigger condition occurs      | Detect hidden malicious behavior       |
| Model theft                   | Unauthorized acquisition of model files or weights                                | Protect confidentiality                |
| Model supply-chain compromise | Malicious model components or dependencies enter the model lifecycle              | Protect model provenance               |

These attack categories are related but not interchangeable. For example, model extraction targets model behavior, whereas model inversion targets information that may be inferred from model behavior.

#### 4.5 Model Security Implementation Requirements

Model provenance

- Record model name, version, provider, and source.
- Record whether the model is internally developed or externally acquired.
- Document licensing and usage restrictions.
- Verify model package integrity.
- Maintain model lineage and approval history.

Model confidentiality

- Restrict access to model weights and artifacts.
- Protect model repositories.
- Apply access monitoring.
- Implement appropriate rate limits and abuse detection for model endpoints.
- Evaluate model extraction exposure.

Model integrity

- Validate model artifacts before deployment.
- Protect training and fine-tuning pipelines.
- Monitor unauthorized model modifications.
- Maintain signed or otherwise verifiable artifacts where supported.
- Apply controlled model promotion between environments.

Model robustness

- Conduct adversarial testing.
- Evaluate model behavior against representative attack scenarios.
- Test robustness against selected input manipulations.
- Assess limitations and failure conditions.
- Document known model weaknesses.

Model monitoring

- Monitor model performance.
- Monitor data drift and concept drift where relevant.
- Detect anomalous inference behavior.
- Review changes in output quality and security.
- Trigger reassessment when material changes occur.

#### 5.4 Example — AI Agent Connected to Salesforce

An AI agent receives a request from a customer-service employee:

> "Find the customer's account, change the billing address, and issue a €200 credit."

The application should not allow the model to execute all requested actions without independent authorization.

| Requested action          | Required security validation                         |

| Execute API calls         | Apply tool-specific authorization                    |
| Return result             | Validate response and prevent sensitive data leakage |

A secure implementation should enforce authorization at the application and target-system layers. A system prompt instructing the model not to issue credits is not an adequate control.

### 6. Control Domain RAG — Retrieval-Augmented Generation Security



RAG

&#x20;Retrieval-Augmented Generation



Retrieval-Augmented Generation (RAG) combines a generative model with an external information retrieval mechanism.

Rather than relying exclusively on information encoded in model parameters, the application retrieves relevant information from an external knowledge source and provides it as context to the model.

RAG introduces additional security considerations because the application must protect:

- Source documents.
- Data ingestion pipelines.
- Document permissions.
- Vector databases.
- Embedding models.
- Retrieval queries.
- Retrieved context.
- Generated responses.
- Synchronization and deletion processes.

A RAG system is not automatically secure because it uses an enterprise knowledge base. Its security depends on the authorization, integrity, and governance of every component.

#### 6.3 RAG Security Architecture

```
             APPROVED KNOWLEDGE SOURCES
                         |
                         v
                 DOCUMENT INGESTION
                         |
                         v
                SOURCE VALIDATION
                         |
                         v
              CLASSIFICATION / LABELING
                         |
                         v
                 EMBEDDING PROCESS
                         |
                         v
                 VECTOR DATABASE
                         |
                         v
                 RETRIEVAL ENGINE
                         |
                 AUTHORIZATION CHECK
                         |
                         v
               RETRIEVED CONTEXT
                         |
                         v
                 LLM / AI MODEL
                         |
                         v
                OUTPUT VALIDATION
                         |
                         v
                 AUTHORIZED USER
```

The authorization check must be enforced before protected information is released to the model. Filtering the final generated answer alone is insufficient because unauthorized data may already have entered the model's context.

#### 6.4 RAG Security Implementation Requirements

Document ingestion

- Accept documents only from approved sources.
- Validate document origin and ownership.
- Scan uploaded files for malware.
- Detect suspicious embedded instructions.
- Apply classification labels.
- Maintain document version and source metadata.

Authorization and retrieval

- Authenticate the requesting user.
- Enforce source-system permissions.
- Apply document-level and, where necessary, record-level authorization.
- Propagate trusted identity context.
- Restrict retrieval to authorized content.
- Revalidate permissions when access rights change.

Vector database protection

- Enforce network and identity restrictions.
- Encrypt data at rest and in transit.
- Restrict administrative access.
- Monitor unusual queries and bulk retrieval.
- Protect backups and replicas.
- Apply retention and deletion requirements.

Prompt injection protection

- Treat retrieved documents as untrusted content.
- Separate system instructions from retrieved context.
- Prevent retrieved content from granting permissions.
- Test malicious documents and embedded instructions.
- Apply tool authorization independently of model-generated instructions.

Output protection

- Apply data-loss prevention where appropriate.
- Validate sensitive information disclosure.
- Provide source references where the application supports them.
- Record retrieval and response activity.
- Avoid representing retrieved information as verified truth without appropriate validation.

#### 6.5 Example — Salesforce CRM RAG Assistant

A customer-service employee asks:

> "Show me the customer's current billing status and previous complaints."

The assistant retrieves information from Salesforce CRM and the billing platform.

The authorization process should be:

1. Authenticate the employee.
2. Retrieve the employee's trusted identity and role.
3. Determine the customer's record-level permissions.
4. Apply the relevant permissions to retrieval queries.
5. Retrieve only authorized records.
6. Pass authorized context to the model.
7. Validate the generated response.
8. Record the access and retrieval event.

Critical security distinction: If an employee is not authorized to access a customer's record in Salesforce, the RAG assistant must not retrieve that record through a separate vector database and expose it through the AI interface.

This is a common architectural failure: the enterprise application enforces record-level permissions, but the independently maintained vector database does not.

### 8. Control Domain TST — AI Security Testing and Validation



TST

&#x20;AI Security Testing



AI security testing validates whether the AI system operates securely under expected conditions and whether it can withstand relevant attack scenarios.

Conventional application security testing remains necessary, but AI systems require additional testing methods.

These include:

- AI threat modeling.
- Adversarial testing.
- Prompt injection testing.
- Model robustness testing.
- RAG authorization testing.
- AI agent permission testing.
- Data leakage testing.
- Model extraction testing.
- Model poisoning assessment.
- AI output validation.
- AI red teaming.

AI security testing must be risk-based and appropriate to the system's intended purpose, exposure, architecture, and potential impact.
