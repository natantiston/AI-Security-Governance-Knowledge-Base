# 22.20 AI Reference Architectures and Frequently Confused Concepts

## Part 1 — AI Reference Architecture Foundations, Core Components, Architectural Layers, and System Boundaries

### 1. Introduction to AI Reference Architectures

An AI reference architecture is a structured representation of the components, services, interfaces, data flows, security boundaries, and governance capabilities required to design, deploy, operate, and manage AI systems.

It provides a reusable architectural foundation that organizations can adapt to different AI use cases.

Unlike a specific implementation architecture, a reference architecture is not necessarily tied to one cloud provider, AI model, application, or technology stack. It defines the architectural capabilities and relationships that an organization should consider when designing AI-enabled solutions.

For AI security governance professionals, reference architectures are particularly important because AI risks are distributed across multiple technical and organizational layers.

An AI system may depend on:

- Business applications.
- AI models and inference services.
- Training and inference datasets.
- Data pipelines.
- APIs and integrations.
- Cloud infrastructure.
- Identity and access management.
- Model orchestration.
- Retrieval-Augmented Generation (RAG).
- External AI providers.
- Human operators.
- Security monitoring and governance processes.

A security assessment that examines only the AI model will miss risks in the surrounding application, data, infrastructure, identity, and operational environments.

Core architectural principle: An AI system must be assessed as an interconnected enterprise system, not merely as an isolated model.

#### 1.1 Purpose of an AI Reference Architecture

An AI reference architecture serves several purposes.

| Purpose                       | Description                                                  | Governance value                     |
| ----------------------------- | ------------------------------------------------------------ | ------------------------------------ |
| Architectural standardization | Establishes reusable architectural patterns                  | Reduces inconsistent implementations |
| Technology alignment          | Defines how AI components interact with enterprise systems   | Improves integration governance      |
| Security by design            | Identifies security requirements across architectural layers | Reduces design-stage security gaps   |
| Data governance               | Defines data sources, processing, storage, and movement      | Supports privacy and data protection |
| Identity governance           | Establishes authentication and authorization boundaries      | Reduces excessive access             |
| Risk management               | Identifies architectural threats and dependencies            | Supports AI risk assessments         |
| Operational governance        | Defines monitoring, maintenance, and incident processes      | Improves operational accountability  |
| Regulatory alignment          | Supports mapping architecture to applicable obligations      | Facilitates compliance assessments   |
| Third-party governance        | Identifies external services and provider dependencies       | Supports supplier risk management    |

An organization can use a reference architecture to assess whether different AI solutions follow common enterprise requirements.

For example, a company may deploy:

- An AI-powered customer service assistant.
- An internal employee knowledge assistant.
- An AI-powered fraud detection platform.
- A document processing solution.
- An autonomous AI agent supporting business operations.

Although these solutions have different business purposes, they may share common architectural requirements such as identity management, data protection, logging, model governance, security testing, and incident response.

#### 1.2 Reference Architecture vs. Solution Architecture

These concepts are frequently confused.

A reference architecture provides a reusable conceptual or logical design. A solution architecture describes how a particular system is implemented within a defined environment.

| Dimension   | Reference architecture                       | Solution architecture                               |
| ----------- | -------------------------------------------- | --------------------------------------------------- |
| Purpose     | Establish reusable architectural guidance    | Design a specific implementation                    |
| Scope       | General architectural capabilities           | Defined business use case                           |
| Technology  | May be technology-neutral                    | Uses selected technologies                          |
| Reusability | Designed for reuse                           | Usually specific to a solution                      |
| Detail      | Logical components and relationships         | Detailed components, configurations, and interfaces |
| Security    | Defines common security principles           | Specifies implemented security controls             |
| Governance  | Establishes reusable governance requirements | Identifies accountable owners and actual evidence   |

Example

A reference architecture may require an AI application to use centralized identity management, encryption, logging, and controlled API access.

A solution architecture may implement those requirements using:

- Microsoft Entra ID.
- Azure Key Vault.
- Azure API Management.
- Azure Monitor.
- Azure AI Foundry.

The reference architecture defines what capabilities are required. The solution architecture explains how those capabilities are implemented.

#### 1.3 AI Reference Architecture vs. AI Framework

An AI reference architecture and an AI governance framework address different problems.

| Dimension     | AI reference architecture                          | AI governance framework                                    |
| ------------- | -------------------------------------------------- | ---------------------------------------------------------- |
| Primary focus | Technical and logical system structure             | Organizational governance and accountability               |
| Main question | How should the AI system be structured?            | How should the organization govern AI?                     |
| Components    | Models, APIs, data, applications, infrastructure   | Policies, roles, risk processes, controls                  |
| Security      | Architectural security boundaries and mechanisms   | Security governance requirements and oversight             |
| Outputs       | Architecture diagrams, design patterns, interfaces | Policies, procedures, risk registers, governance decisions |
| Typical users | Architects, engineers, security specialists        | Governance, risk, compliance, audit, management            |

The two must work together.

An architecture can be technically secure but poorly governed if there is no accountable system owner, risk acceptance process, provider oversight, or regulatory assessment.

Likewise, an organization can have an excellent AI governance policy while deploying insecure architectures.

#### 2.2 Layer 1 — Infrastructure and Platform

The infrastructure layer provides the computing, networking, storage, and hosting capabilities required to operate AI systems.

Typical components include:

- Cloud infrastructure.
- On-premises infrastructure.
- Virtual machines.
- Containers and Kubernetes.
- GPU infrastructure.
- Network services.
- Storage systems.
- Operating systems.
- Hardware security modules.
- Backup and recovery infrastructure.

Examples of cloud platforms include:

- Microsoft Azure.
- Amazon Web Services.
- Google Cloud Platform.

Security and governance considerations

| Risk area                    | Example risk                       | Governance requirement                        |
| ---------------------------- | ---------------------------------- | --------------------------------------------- |
| Infrastructure configuration | Misconfigured cloud resources      | Secure configuration baseline                 |
| Network security             | Unauthorized network access        | Segmentation and controlled connectivity      |
| Compute security             | Compromised AI hosting environment | Vulnerability and patch management            |
| Storage security             | Unauthorized access to AI data     | Encryption and access control                 |
| Availability                 | Infrastructure outage              | Resilience and recovery planning              |
| Hardware security            | Exposure of sensitive workloads    | Appropriate hardware and platform protections |
| Cloud dependency             | Excessive provider concentration   | Supplier and concentration risk management    |

GRC assessment questions

1. Where is the AI system hosted?
2. Is the environment cloud-based, on-premises, or hybrid?
3. Who owns and operates the infrastructure?
4. Are network boundaries documented?
5. Are storage services encrypted?
6. Are vulnerabilities assessed and remediated?
7. Are backup and recovery requirements defined?
8. Are cloud provider responsibilities documented?
9. Are infrastructure changes controlled?
10. Are critical infrastructure dependencies included in business continuity planning?

#### 2.3 Layer 2 — Data and Knowledge

The data layer provides the information used by AI systems for training, fine-tuning, retrieval, inference, and evaluation.

Typical components include:

- Structured databases.
- Unstructured document repositories.
- Data lakes and data warehouses.
- Object storage.
- Data pipelines.
- Feature stores.
- Vector databases.
- Embedding repositories.
- Knowledge bases.
- External data sources.

AI systems may process different categories of information:

| Data category    | Description                                     | Example                        |
| ---------------- | ----------------------------------------------- | ------------------------------ |
| Training data    | Data used to train a model                      | Historical labeled datasets    |
| Fine-tuning data | Data used to adapt a pretrained model           | Domain-specific examples       |
| Inference input  | Data submitted when using the model             | Customer query                 |
| Retrieval data   | Information retrieved to support a response     | Internal policy document       |
| Embedding data   | Numerical vector representations of content     | Document embeddings            |
| Evaluation data  | Data used to measure model performance          | Benchmark dataset              |
| Output data      | Information generated by the AI system          | AI-generated customer response |
| Telemetry data   | Operational information generated by the system | Usage and performance logs     |

Security and governance considerations

- Data classification.
- Data ownership.
- Data provenance.
- Data quality.
- Data minimization.
- Data retention.
- Encryption.
- Access control.
- Privacy protection.
- Dataset integrity.
- Data poisoning protection.
- Secure data deletion.
- Cross-border data transfers.

A common governance mistake is assuming that data stored in a vector database is automatically protected because the original documents are access-controlled.

This is incorrect.

Embeddings and retrieved content may expose information about the underlying source material. The organization must assess how access permissions, indexing, retrieval, storage, and deletion are enforced.

GRC assessment questions

1. What data sources are used by the AI system?
2. Are data owners identified?
3. Is the data classified?
4. Does the system process personal or confidential information?
5. Is data provenance documented?
6. Are retrieval permissions enforced?
7. Are embeddings and vector databases protected?
8. Are data retention and deletion requirements defined?
9. Can unauthorized users retrieve restricted information?
10. Are training and evaluation datasets protected against unauthorized modification?

#### 2.4 Layer 3 — Model and Inference

The model layer contains the AI models that perform prediction, classification, generation, reasoning-like language processing, or other AI tasks.

Typical components include:

- Foundation models.
- Large Language Models (LLMs).
- Machine learning models.
- Deep learning models.
- Computer vision models.
- Speech recognition models.
- Embedding models.
- Fine-tuned models.
- Model inference endpoints.

The model may be:

- Developed internally.
- Obtained as an open-weight model.
- Accessed through an external provider.
- Hosted by a cloud provider.
- Deployed in an organization's own infrastructure.

Model lifecycle

```
Model Selection or Development
              |
              v
        Data Preparation
              |
              v
          Training
              |
              v
        Model Evaluation
              |
              v
       Security Validation
              |
              v
       Model Registration
              |
              v
          Deployment
              |
              v
       Inference Operations
              |
              v
     Monitoring and Review
              |
              v
    Retraining or Retirement
```

The exact lifecycle differs depending on whether the organization develops a model, fine-tunes an existing model, or consumes a third-party model as a service.

Security and governance considerations

| Risk                 | Description                                                  | Example control                           |
| -------------------- | ------------------------------------------------------------ | ----------------------------------------- |
| Model poisoning      | Manipulation of training or model development processes      | Dataset integrity and provenance controls |
| Model extraction     | Attempts to reproduce model behavior through queries         | API protection and abuse monitoring       |
| Model inversion      | Attempts to infer sensitive information from model behavior  | Privacy testing and output restrictions   |
| Membership inference | Attempts to determine whether a record was in training data  | Privacy risk assessment                   |
| Model tampering      | Unauthorized modification of model artifacts                 | Artifact integrity verification           |
| Model drift          | Changes in model behavior or input characteristics over time | Performance and drift monitoring          |
| Model provider risk  | Dependency on an external model provider                     | Third-party risk assessment               |
| Model vulnerability  | Weaknesses in the model or its deployment                    | Model security testing                    |

GRC assessment questions

1. Who owns the model?
2. Who developed or supplied it?
3. Is the model internally hosted or externally accessed?
4. Is the model version recorded?
5. Is model provenance documented?
6. Has the model been evaluated for its intended use?
7. Are model access permissions controlled?
8. Are model artifacts protected against tampering?
9. Are performance and drift monitored?
10. Is there an approved process for model updates and retirement?

An important architectural distinction is that model security does not guarantee application security.

A model may be protected against unauthorized modification while the application using it remains vulnerable to prompt injection, insecure output handling, or excessive tool permissions.

#### 2.5 Layer 4 — Orchestration and AI Services

The orchestration layer coordinates interactions between models, data sources, tools, external services, and application workflows.

This layer is especially important in generative AI and agentic AI architectures.

Typical components include:

- Prompt management.
- Model routing.
- Retrieval-Augmented Generation.
- Agent orchestration.
- Tool calling.
- Workflow engines.
- Context management.
- Memory services.
- Content filtering.
- Output validation.
- Model gateways.

For example, an AI assistant may receive a user question, retrieve relevant documents, send the context to an LLM, invoke a CRM API, and return a response.

The orchestration layer coordinates these activities.

Illustrative orchestration flow

```
User Request
     |
     v
Application Gateway
     |
     v
Authentication and Authorization
     |
     v
Prompt and Context Management
     |
     +----------------------+
     |                      |
     v                      v
Knowledge Retrieval     External Tool/API
     |                      |
     v                      v
Retrieved Context       Authorized Result
     |                      |
     +----------+-----------+
                |
                v
          Model Inference
                |
                v
        Output Validation
                |
                v
          User Response
```

This diagram represents one possible implementation. Actual systems may execute these activities in different sequences.

Security and governance considerations

| Risk                        | Description                                           | Governance requirement                        |
| --------------------------- | ----------------------------------------------------- | --------------------------------------------- |
| Prompt injection            | Malicious instructions influence model behavior       | Adversarial testing and instruction isolation |
| Excessive agency            | AI system has unnecessary permissions or capabilities | Least privilege and action authorization      |
| Unauthorized tool execution | AI invokes tools without appropriate authorization    | Runtime authorization and approval controls   |
| Context leakage             | Sensitive context is exposed to unauthorized users    | Context access restrictions                   |
| Insecure orchestration      | Workflow components introduce security weaknesses     | Secure integration design                     |
| Memory poisoning            | Persistent agent memory is manipulated                | Memory integrity and lifecycle controls       |
| Uncontrolled model routing  | Requests are sent to unapproved models                | Approved model registry and routing controls  |

GRC assessment questions

1. Which orchestration framework or service is used?
2. Can the AI system invoke external tools?
3. Are tool permissions restricted?
4. Does the application independently authorize every sensitive action?
5. Can retrieved documents influence privileged actions?
6. Are prompts and context managed securely?
7. Is persistent agent memory used?
8. Are model routing decisions controlled?
9. Are sensitive tool calls logged?
10. Is human approval required for defined high-impact actions?

A prompt that instructs an AI agent not to perform unauthorized actions is not an enforceable access control.

Authorization must be implemented by the application, API, identity provider, or execution environment.

#### 2.6 Layer 5 — Application and Experience

The application layer exposes AI capabilities to users and business processes.

Typical components include:

- Web applications.
- Mobile applications.
- Enterprise chatbots.
- CRM systems.
- Customer service platforms.
- Employee productivity tools.
- Business workflow applications.
- AI-enabled decision-support applications.
- API-based enterprise integrations.

The application determines how users interact with AI capabilities and how AI functionality is embedded into business processes.

For example, an enterprise AI assistant may be integrated into Salesforce to support customer service representatives.

The application may allow users to:

- Retrieve customer records.
- Summarize interactions.
- Generate responses.
- Recommend actions.
- Search knowledge articles.
- Initiate workflows.

Security and governance considerations

- User authentication.
- Role-based access control.
- Application authorization.
- Session management.
- API security.
- Input validation.
- Output handling.
- Secure error handling.
- User consent and transparency where applicable.
- Human review and approval.
- Application logging.

GRC assessment questions

1. Which business applications use AI functionality?
2. Who are the authorized users?
3. Are access permissions aligned with business roles?
4. Can the application expose sensitive information?
5. Are AI-generated outputs validated before critical use?
6. Can users initiate financial or operational transactions?
7. Are high-impact actions subject to appropriate approval?
8. Are AI-generated decisions distinguishable from human decisions where required?
9. Are application vulnerabilities assessed?
10. Are business owners accountable for the use of AI functionality?

The application layer is where model capabilities become business capabilities. Consequently, application-level controls are essential for translating AI security requirements into enforceable behavior.

#### 2.7 Layer 6 — Security and Trust

Security is not a standalone feature that can be added after the AI system has been developed.

It is a cross-cutting architectural capability that protects infrastructure, data, models, orchestration, applications, users, and integrations.

Typical security capabilities include:

- Identity and access management.
- Privileged access management.
- Encryption and key management.
- Secrets management.
- Network security.
- Data loss prevention.
- API protection.
- Vulnerability management.
- Security monitoring.
- Threat detection.
- Incident response.
- Security testing.
- Supply-chain security.

Security architecture principles

| Principle             | Application to AI systems                                                        |
| --------------------- | -------------------------------------------------------------------------------- |
| Least privilege       | Limit model, agent, user, and service permissions                                |
| Defense in depth      | Apply multiple independent security controls                                     |
| Zero trust            | Continuously validate access based on identity, context, and policy              |
| Secure by design      | Include security requirements from the architecture stage                        |
| Separation of duties  | Separate development, approval, deployment, and risk acceptance responsibilities |
| Data minimization     | Limit the information processed by AI systems                                    |
| Fail securely         | Prevent failures from creating unauthorized access                               |
| Continuous monitoring | Monitor security and operational behavior                                        |
| Secure supply chain   | Validate model, dataset, software, and provider dependencies                     |

GRC assessment questions

1. Is an AI-specific threat model available?
2. Are identities and service accounts governed?
3. Are privileged AI actions restricted?
4. Are secrets and API credentials protected?
5. Are security events monitored?
6. Are AI components included in vulnerability management?
7. Are security tests performed before deployment?
8. Are third-party AI dependencies assessed?
9. Are incident response procedures AI-aware?
10. Is security control effectiveness periodically evaluated?

#### 2.8 Layer 7 — Governance, Risk, Compliance, and Oversight

The governance layer establishes the organizational requirements, responsibilities, decision-making processes, and assurance mechanisms for AI systems.

It is concerned with whether AI is being developed, acquired, deployed, and operated in accordance with organizational objectives and applicable requirements.

Typical capabilities include:

- AI governance policies.
- AI system inventory.
- AI risk management.
- AI impact assessments.
- Regulatory applicability assessments.
- AI management system processes.
- Model governance.
- Third-party oversight.
- Human oversight.
- Internal audit.
- Compliance monitoring.
- Executive reporting.

Relevant references may include:

| Reference     | Architectural governance relevance                                 |
| ------------- | ------------------------------------------------------------------ |
| ISO/IEC 42001 | AI management system requirements and controls                     |
| ISO/IEC 23894 | AI risk management                                                 |
| NIST AI RMF   | AI risk governance and management                                  |
| NIST CSF 2.0  | Enterprise cybersecurity governance                                |
| ISO/IEC 27001 | Information security management                                    |
| EU AI Act     | Applicable AI-related legal obligations                            |
| GDPR          | Personal data protection obligations                               |
| COBIT         | Enterprise governance and management of information and technology |

GRC assessment questions

1. Is the AI system formally registered?
2. Is there an accountable business owner?
3. Are system and model responsibilities defined?
4. Has an AI risk assessment been completed?
5. Has regulatory applicability been determined?
6. Are applicable controls mapped to evidence?
7. Are human oversight responsibilities defined?
8. Are third-party dependencies governed?
9. Is residual risk formally accepted by an authorized owner?
10. Are governance performance and control effectiveness reported to management?

A governance framework must operate in practice. The existence of policies and committees alone does not demonstrate effective AI governance.

### 3. Cross-Cutting Architectural Capabilities

The seven-layer model provides a useful way to understand AI systems, but some capabilities operate across every layer.

These cross-cutting capabilities should be included in architecture assessments rather than assigned exclusively to one component.

#### 3.1 Identity and Access Management

Identity and access management controls who or what can access AI resources.

AI environments may involve several identity types:

| Identity type           | Example                                          |
| ----------------------- | ------------------------------------------------ |
| Human identity          | Employee accessing an AI assistant               |
| Application identity    | CRM application calling an AI service            |
| Service identity        | Backend service accessing a model endpoint       |
| Agent identity          | AI agent operating within an approved workflow   |
| Provider identity       | External service accessing a managed integration |
| Administrative identity | Engineer managing model infrastructure           |

The organization must establish clear authorization rules for each identity type.

A particularly important issue arises when an AI agent acts on behalf of a human user.

The organization must determine whether the agent:

- Uses the user's delegated permissions.
- Uses a separate service identity.
- Operates with restricted task-specific permissions.
- Requires approval for sensitive operations.

An agent must not receive broad permissions merely because it is expected to perform multiple tasks.

#### 3.2 Data Governance and Protection

Data governance operates across training, inference, retrieval, storage, output, and monitoring processes.

Controls should address:

- Data classification.
- Data ownership.
- Data provenance.
- Data quality.
- Data access.
- Data minimization.
- Retention and deletion.
- Privacy requirements.
- Data integrity.
- Cross-border data processing.

An organization should also distinguish between data used to train a model and data submitted to an externally hosted model during inference.

The contractual, technical, and regulatory implications may differ substantially.

#### 3.3 Observability and Monitoring

AI observability involves collecting and analyzing information about system behavior, performance, and operational conditions.

It may include:

- Model latency.
- API usage.
- Token consumption.
- Model errors.
- Retrieval failures.
- Tool invocation events.
- Prompt injection indicators.
- Data access events.
- Model performance.
- Drift indicators.
- Security alerts.

Monitoring should balance security requirements with privacy and confidentiality obligations. Logging every prompt and response without appropriate controls may itself create sensitive data exposure.

#### 3.4 Human Oversight

Human oversight should be designed into relevant business workflows.

Examples include:

- Reviewing AI-generated recommendations.
- Approving high-impact decisions.
- Confirming sensitive transactions.
- Reviewing unusual agent actions.
- Escalating uncertain or conflicting outputs.
- Overriding automated recommendations.

Human oversight must be meaningful. A human reviewer who lacks adequate information, authority, time, or competence may provide little effective control.

#### 3.5 Resilience and Lifecycle Management

AI systems require operational resilience throughout their lifecycle.

This includes:

- Model version management.
- Backup and recovery.
- Provider outage planning.
- Model rollback.
- Alternative service arrangements.
- Data recovery.
- Dependency management.
- Retirement and decommissioning.
- Secure data deletion.
- Access revocation.

A system that can be deployed securely but cannot be safely updated, recovered, or retired has an incomplete security architecture.

### 4. Architectural Boundaries, Trust Zones, and Data Flow

Understanding architectural boundaries is fundamental to AI security governance.

An AI system can interact with internal and external environments, each with different trust assumptions and security requirements.

#### 4.1 Understanding Trust Boundaries

A trust boundary separates components or environments with different security assumptions, identities, privileges, or levels of control.

Examples include:

- Internal enterprise network and public internet.
- Enterprise application and external AI provider.
- User interface and backend services.
- Internal database and vector database.
- AI model and external tools.
- Trusted enterprise documents and untrusted external content.
- Development environment and production environment.

Crossing a trust boundary should trigger an assessment of authentication, authorization, data protection, validation, monitoring, and failure behavior.

#### 4.2 Example: Enterprise AI Assistant Trust Boundaries

Consider an AI assistant integrated with Salesforce CRM and an external LLM provider.

```
                 ENTERPRISE USERS
                        |
                        v
              +-------------------+
              | Salesforce CRM    |
              | User Interface    |
              +-------------------+
                        |
                 Trust Boundary 1
                        |
                        v
              +-------------------+
              | AI Application    |
              | API Gateway       |
              +-------------------+
                   |          |
                   |          |
                   v          v
          +-------------+  +----------------+
          | Enterprise  |  | External LLM   |
          | Data / RAG  |  | Provider       |
          +-------------+  +----------------+
                   |          |
                   |          |
                   v          v
          +-------------+  +----------------+
          | Vector DB   |  | Model Inference|
          +-------------+  +----------------+
                   |
                   v
          +-------------------+
          | Internal Systems  |
          | CRM / ERP / BSS    |
          +-------------------+
```

This simplified diagram illustrates major components, not a complete production architecture.

Important trust boundaries include:

Boundary 1 — User to Salesforce

- Is the user authenticated?
- Are CRM permissions enforced?
- Is session management secure?

Boundary 2 — Salesforce to AI application

- Is the integration authenticated?
- Are API permissions restricted?
- Is the data transmitted securely?

Boundary 3 — AI application to enterprise data

- Is access authorized at source level?
- Are retrieval results filtered according to user permissions?
- Is the vector database protected?

Boundary 4 — AI application to external model provider

- What information is transmitted?
- Is sensitive data minimized?
- Are provider data-use and retention terms acceptable?
- Are encryption and contractual protections established?

Boundary 5 — AI application to internal systems

- Are service identities restricted?
- Can the AI initiate transactions?
- Are privileged actions independently authorized?
- Is human approval required for sensitive operations?

The data flow assessment should identify:

- Data classification.
- Source and destination.
- Processing purpose.
- Data owner.
- Authentication method.
- Authorization mechanism.
- Encryption.
- Retention.
- External recipients.
- Logging.
- Applicable regulatory requirements.

A data flow diagram is not simply a technical drawing. It is also an important governance artifact because it supports privacy assessments, threat modeling, risk assessments, and regulatory applicability analysis.

### 5. Reference Architecture Assessment from a GRC Perspective

A GRC professional should translate architectural components into governance questions, risk scenarios, control requirements, and evidence.

The objective is not to redesign the system personally but to establish whether the architecture supports the organization's security, regulatory, and business requirements.

#### 5.1 Architecture-to-GRC Mapping

| Architectural layer | Primary risk domains                                   | Example governance evidence          |
| ------------------- | ------------------------------------------------------ | ------------------------------------ |
| Infrastructure      | Cloud, network, availability, configuration            | Infrastructure security assessment   |
| Data and knowledge  | Privacy, confidentiality, integrity, provenance        | Data inventory and classification    |
| Model and inference | Model integrity, performance, privacy                  | Model documentation and evaluation   |
| Orchestration       | Prompt injection, excessive agency, unauthorized tools | Agent permissions and security tests |
| Application         | Access control, API security, output handling          | Application security assessment      |
| Security and trust  | IAM, encryption, monitoring, incident response         | Security control matrix              |
| Governance          | Accountability, compliance, risk acceptance            | AI governance records and approvals  |

#### 5.2 Architecture Review: Questions a GRC Professional Should Ask

A structured review should address five dimensions.

A. Business and accountability

- What business problem does the AI system solve?
- Who is accountable for its use?
- Which business processes depend on it?
- What is the impact if the system produces incorrect results?
- Who approves changes to its intended purpose?

B. Technology and architecture

- Which model and AI services are used?
- Is the architecture documented?
- Which internal and external systems are connected?
- Are trust boundaries identified?
- Are dependencies recorded?

C. Security and privacy

- Are identities and permissions properly controlled?
- Is sensitive data protected?
- Can untrusted content influence privileged actions?
- Are AI-specific threats assessed?
- Is the system tested before production deployment?

D. Compliance and assurance

- Have applicable regulations been identified?
- Are contractual obligations documented?
- Are control owners assigned?
- Is evidence available?
- Is independent assurance performed where appropriate?

E. Operations and resilience

- Is the system monitored?
- Are incidents classified and escalated?
- Can the system be disabled or rolled back?
- Is provider outage planning documented?
- Is there a secure retirement process?

#### 5.3 Example of an Architecture-Driven Risk

Scenario: An AI assistant connected to Salesforce retrieves customer information from a vector database. The retrieval service does not consistently enforce the permissions of the requesting user.

| Risk element       | Assessment                                                          |
| ------------------ | ------------------------------------------------------------------- |
| Asset              | Customer information and Salesforce records                         |
| Threat             | Unauthorized user or malicious actor                                |
| Vulnerability      | Missing source-level authorization during retrieval                 |
| Attack path        | User submits a query that retrieves restricted customer information |
| Risk event         | AI assistant returns data the user is not authorized to access      |
| Business impact    | Confidentiality breach, privacy violation, regulatory exposure      |
| Preventive control | Enforce source-level authorization before retrieval                 |
| Detective control  | Monitor and alert on unauthorized retrieval attempts                |
| Corrective control | Revoke access, contain exposure, investigate and remediate          |
| Evidence           | Authorization test results, configuration records, access logs      |
| Risk owner         | Assigned business or technology risk owner                          |

This example illustrates why architecture-level controls must be evaluated at the actual enforcement point.

A prompt telling the model not to disclose restricted information is not an adequate substitute for authorization enforcement in the retrieval service.

### Summary

An AI reference architecture provides a reusable foundation for understanding how AI systems are structured and how their components interact.

The seven-layer model introduced in this lesson covers:

1. Infrastructure and platform.
2. Data and knowledge.
3. Model and inference.
4. Orchestration and AI services.
5. Application and experience.
6. Security and trust.
7. Governance, risk, compliance, and oversight.

The architecture must also account for cross-cutting capabilities such as identity management, data governance, observability, human oversight, and operational resilience.

For GRC professionals, the primary objective is to translate architectural components and trust boundaries into assessable risks, enforceable controls, accountable ownership, and verifiable evidence.

### Core Principle

A secure and governable AI system requires end-to-end architectural visibility. Security and governance must cover the infrastructure, data, model, orchestration, application, operational environment, and organizational decision-making—not just the AI model itself.

Excessive agency risk

One of the most important security risks in agentic AI is excessive agency.

An AI agent may be granted permissions that exceed what is necessary for its intended task.

For example, a customer service assistant may only need permission to:

- Read selected customer records.
- Retrieve approved knowledge articles.
- Create a support ticket.

Giving that agent administrator privileges over the CRM platform would introduce unnecessary risk.

A compromised prompt, manipulated retrieval result, or application vulnerability could potentially turn those excessive permissions into a serious business incident.

GRC assessment questions

1. What actions can the agent perform?
2. Which tools and APIs can it access?
3. Are permissions limited to the intended task?
4. Does each sensitive action require independent authorization?
5. Are high-impact actions subject to human approval?
6. Can agent memory be manipulated?
7. Are tool calls recorded?
8. Can the agent be stopped or disabled?
9. Are actions reversible?
10. Is there an accountable owner for agent behavior?

#### 6.6 Hybrid AI Architecture

A hybrid AI architecture combines different AI approaches, models, or processing methods within one solution.

Examples include:

- Machine learning combined with rules-based systems.
- LLMs combined with knowledge graphs.
- Generative AI combined with traditional analytics.
- Predictive models combined with human decision-making.
- Multiple models selected through a model gateway.

A telecom fraud detection platform may use:

1. A machine learning model to identify suspicious transaction patterns.
2. A rules engine to apply business and regulatory thresholds.
3. An LLM to summarize investigation findings.
4. A human analyst to make the final decision.

This design separates detection, rule enforcement, explanation, and decision authority.

Governance considerations

- Clear allocation of decision responsibility.
- Validation of each model and rules engine.
- Data consistency between components.
- Secure communication between services.
- Traceability of recommendations and decisions.
- Independent authorization of business actions.
- Monitoring for cascading failures.

A hybrid architecture can improve system capabilities, but combining multiple components also increases dependencies and the number of interactions that require governance.

### 7. AI Deployment Models and Hosting Architectures

AI systems can be deployed through different hosting and service models.

The deployment model affects data exposure, operational responsibility, security controls, regulatory considerations, resilience, and provider dependency.

#### 7.1 On-Premises AI Deployment

An on-premises AI deployment operates within infrastructure controlled by the organization.

Typical components include:

- Organization-managed servers.
- GPU infrastructure.
- Internal model hosting.
- Internal databases.
- Enterprise network connectivity.
- Organization-managed security controls.

Advantages

- Greater direct control over infrastructure.
- Greater flexibility over deployment configurations.
- Potentially stronger isolation from external services.
- Greater control over data location and processing.

Limitations

- High infrastructure investment.
- Hardware and capacity management.
- Internal operational responsibility.
- Specialized skills requirements.
- Model lifecycle maintenance.
- Scalability constraints.

GRC considerations

The organization must assess infrastructure security, physical security, model hosting, access control, patching, backup, resilience, and operational ownership.

On-premises hosting does not automatically mean that the AI system is secure or compliant. Poorly configured internal infrastructure can create substantial exposure.

#### 7.2 Cloud-Hosted AI Deployment

A cloud-hosted AI system operates using cloud infrastructure and services.

Examples include AI services provided through Azure, AWS, or Google Cloud.

Advantages

- Scalable infrastructure.
- Managed AI capabilities.
- Reduced need to operate all underlying infrastructure.
- Integration with cloud security services.
- Flexible deployment options.

Limitations

- Provider dependency.
- Shared responsibility complexity.
- Data processing and residency considerations.
- Potential service availability dependencies.
- Consumption and cost management.
- Vendor lock-in.

GRC considerations

The organization must understand which security responsibilities belong to the cloud provider and which remain with the customer.

For example, a provider may secure the underlying physical infrastructure, but the customer may remain responsible for:

- User permissions.
- Application authorization.
- Data classification.
- API credentials.
- Configuration.
- Business process controls.
- Risk acceptance.
- Regulatory accountability.

#### 7.3 Hybrid AI Deployment

A hybrid AI deployment combines on-premises and cloud-based components.

For example:

- Customer data remains in internal systems.
- An internal application performs data preparation.
- A managed cloud AI service performs inference.
- Results are returned to an internal business application.

Architectural considerations

- Secure connectivity between environments.
- Data transfer restrictions.
- Identity federation.
- Encryption.
- Network segmentation.
- Data residency.
- Centralized logging.
- Dependency management.
- Consistent security policies.

Hybrid environments can introduce complex trust boundaries because information moves between systems governed by different security controls and operational teams.

#### 7.4 SaaS-Based AI Deployment

A Software-as-a-Service AI solution is delivered through a provider-managed application.

The organization generally accesses the AI functionality through a web interface, API, or integrated business application.

Examples may include AI features embedded in CRM, productivity, customer service, or enterprise collaboration platforms.

Advantages

- Faster deployment.
- Reduced infrastructure management.
- Provider-managed updates.
- Integrated business functionality.

Limitations

- Reduced infrastructure-level control.
- Provider dependency.
- Limited visibility into model operations.
- Contractual and data-use considerations.
- Configuration and integration risks.

GRC assessment questions

1. Where is organizational data processed?
2. Does the provider use submitted information for model training?
3. Which subprocessors are involved?
4. What are the retention and deletion arrangements?
5. How are identities and access permissions managed?
6. What security certifications or assurance reports are available?
7. What incident notification obligations apply?
8. Can the organization export its data?
9. Can the organization terminate the service and securely delete its information?
10. What happens if the provider discontinues the service?

| Scalability                | Organization-managed   | Generally flexible                   | Depends on design          | Provider-managed                                         |
| Operational responsibility | Primarily organization | Shared                               | Shared across environments | Primarily provider for service infrastructure            |

#### 9.1 Architecture Selection Decision Criteria

Before approving an AI architecture, assess the following:

Business requirements

- What problem must the system solve?
- Is AI necessary, or could conventional automation achieve the objective?
- What level of accuracy and availability is required?
- What decisions or actions will the system influence?

Data requirements

- What information is needed?
- Is personal or confidential data involved?
- Does the system require external data access?
- Can the data remain within approved environments?

Technical requirements

- Is model training required?
- Is inference sufficient?
- Is RAG needed?
- Does the system require tool execution?
- Is low-latency processing necessary?

Security requirements

- What are the trust boundaries?
- Which identities and permissions are required?
- What happens if the model is manipulated?
- Can the system initiate sensitive actions?
- How will incidents be contained?

Governance requirements

- Who owns the system?
- Which standards and regulations apply?
- Is human oversight necessary?
- How will the system be tested and monitored?
- Who can accept residual risk?

Operational requirements

- Who operates the system?
- What happens during provider outages?
- Can the model be replaced?
- Can data and configurations be exported?
- How will the system be retired?

| Traditional ML       | Data poisoning, model manipulation, drift               | Data provenance, model validation, monitoring                       |
| Generative AI        | Prompt injection, hallucination, information disclosure | Input/output controls, access management, human review              |
| RAG                  | Unauthorized retrieval, indirect prompt injection       | Source-level authorization, retrieval testing, data protection      |
| Single-agent AI      | Excessive agency, unauthorized tool execution           | Least privilege, runtime authorization, action approval             |
| Multi-agent AI       | Privilege escalation, uncontrolled agent communication  | Agent identity governance, permission boundaries, traceability      |
| Hybrid AI            | Inconsistent decisions, component dependencies          | Component validation, integration controls, decision accountability |
| Cloud AI             | Misconfiguration, provider dependency                   | Shared responsibility, cloud security, supplier oversight           |
| SaaS AI              | Data exposure, limited visibility, vendor lock-in       | Contractual controls, data governance, provider assurance           |
| API-based AI         | Unauthorized access, abuse                              | API security, identity validation, rate limiting                    |
| Event-driven AI      | Replay, duplicate execution, message manipulation       | Event integrity, idempotency, monitoring                            |

This mapping is a starting point for architecture risk assessments. It does not replace system-specific threat modeling or regulatory applicability analysis.

### Summary

AI architectural patterns determine how AI capabilities are implemented and integrated into business environments.

The principal patterns covered in this part are:

1. Traditional machine learning.
2. Generative AI.
3. Retrieval-Augmented Generation.
4. Single-agent AI.
5. Multi-agent AI.
6. Hybrid AI.
7. On-premises, cloud, hybrid, and SaaS deployment.
8. API-based, event-driven, and middleware integration.

Each pattern introduces different security requirements and governance challenges.

The most important assessment considerations are data access, model integrity, application security, tool authorization, provider dependency, human oversight, operational resilience, and traceability.

### Core Principle

AI architecture must be selected according to business purpose, data sensitivity, operational requirements, and risk exposure. Every architectural pattern requires explicit security boundaries, enforceable authorization, accountable ownership, and controls that can be independently tested.

## Part 3 — AI Security Architecture, Threat Modeling, Security Controls, and Architectural Risk Assessment

### 11. Security-by-Design Principles for AI Architectures

AI security must be incorporated throughout the system lifecycle rather than introduced as a corrective activity after deployment.

Traditional cybersecurity principles remain relevant, but AI systems introduce additional risks involving model behavior, training data, inference inputs, retrieval mechanisms, agent permissions, and interactions between AI components.

An effective AI security architecture must therefore combine conventional enterprise security controls with AI-specific protections.

#### 11.1 Security by Design

Security by design means incorporating security requirements into the architecture, development, acquisition, and deployment of a system from the beginning.

For AI systems, this includes:

- Identifying security requirements before selecting an AI model.
- Establishing trust boundaries.
- Defining data access and processing restrictions.
- Enforcing authorization outside the model.
- Protecting model and data assets.
- Securing APIs and integrations.
- Testing AI-specific attack scenarios.
- Establishing monitoring and incident response.
- Defining secure model updates and retirement.

Example

An organization wants to deploy an AI assistant that can retrieve customer records from Salesforce.

A weak approach is to deploy the LLM first and subsequently add instructions telling it not to disclose confidential information.

A security-by-design approach establishes the following requirements before deployment:

1. Authenticate every user.
2. Establish the user's authorization context.
3. Enforce Salesforce permissions during retrieval.
4. Restrict the AI application's service identity.
5. Treat retrieved documents as untrusted content.
6. Validate AI-generated outputs.
7. Require authorization before sensitive actions.
8. Record relevant access and execution events.
9. Test prompt injection and unauthorized retrieval.
10. Establish an incident response procedure.

The difference is fundamental: the second approach establishes enforceable security mechanisms rather than relying on model behavior.

#### 11.2 Defense in Depth

Defense in depth uses multiple layers of security controls to reduce the likelihood and impact of successful attacks.

An AI application should not depend on one security mechanism.

For example, protecting an AI assistant against unauthorized data disclosure may require:

| Security layer    | Example control                                |
| ----------------- | ---------------------------------------------- |
| Identity          | Authenticate the user                          |
| Authorization     | Verify access to requested records             |
| Data              | Apply data classification and minimization     |
| Retrieval         | Enforce source-level permissions               |
| Model             | Apply appropriate model safety controls        |
| Application       | Validate outputs and prevent unsafe processing |
| Tool execution    | Independently authorize sensitive actions      |
| Monitoring        | Detect unusual access and disclosure patterns  |
| Incident response | Contain and investigate security events        |

A prompt instruction such as "never disclose confidential information" is not an independent security boundary.

If an attacker manipulates the model, the surrounding application and authorization controls must still prevent unauthorized access.

#### 11.3 Least Privilege

Least privilege means granting users, services, applications, and agents only the permissions necessary to perform their authorized functions.

In AI environments, least privilege applies to:

- Human users.
- Model-serving identities.
- AI application service accounts.
- Agent identities.
- API integrations.
- Data retrieval services.
- Administrative accounts.
- Model development pipelines.

Example: AI customer service agent

| Permission                         | Required?      | Reason                                               |
| ---------------------------------- | -------------- | ---------------------------------------------------- |
| Read assigned customer records     | Yes            | Required to answer authorized customer queries       |
| Search approved knowledge articles | Yes            | Required to retrieve service information             |
| Create support tickets             | Possibly       | Required if ticket creation is an approved function  |
| Modify customer billing details    | Not by default | Sensitive operation requiring separate authorization |
| Delete customer accounts           | No by default  | High-impact action requiring strong controls         |
| Administer Salesforce              | No             | Exceeds the intended business function               |

The agent should not inherit broad administrative permissions merely because its application needs to access several services.

#### 11.4 Zero Trust Architecture

Zero Trust is a security approach based on the principle that access should not be granted solely because a user, device, or service is inside a trusted network.

Access decisions should consider identity, resource, context, policy, and risk.

In AI architectures, Zero Trust principles can apply to:

- User access to AI applications.
- Application access to model endpoints.
- Agent access to tools.
- Retrieval access to enterprise data.
- Service-to-service communication.
- Administrative access to model infrastructure.

AI Zero Trust access flow

```
User or Service Request
          |
          v
Identity Verification
          |
          v
Device and Context Evaluation
          |
          v
Authorization Policy Evaluation
          |
          v
Resource-Level Access Decision
          |
     +----+----+
     |         |
     v         v
   Allow      Deny
     |
     v
Continuous Monitoring
```

The critical point is that authentication and authorization are separate.

Authentication establishes who or what is making a request. Authorization determines what that identity is permitted to do.

An authenticated AI agent must not automatically be authorized to access every enterprise resource.

#### 11.5 Separation of Duties

Separation of duties prevents one individual or process from controlling incompatible activities without appropriate oversight.

Relevant AI activities include:

- Model development.
- Model validation.
- Security testing.
- Production deployment.
- Risk acceptance.
- Privileged access approval.
- Compliance assessment.
- Independent audit.

For example, a model developer should not automatically be the sole authority approving the production deployment of a high-impact AI system.

The organization should establish appropriate independent review and approval according to the system's risk.

#### 11.6 Secure Failure and Fail-Safe Design

AI systems must be designed to fail safely when components malfunction, become unavailable, or produce unexpected behavior.

Examples include:

- Denying access when authorization cannot be verified.
- Preventing sensitive actions when policy evaluation fails.
- Disabling an agent when its behavior becomes abnormal.
- Falling back to a non-AI workflow when model availability is lost.
- Preventing incomplete transactions from being executed.
- Requiring human review when confidence or validation requirements are not met.

A critical design decision is whether a component should fail open or fail closed.

For sensitive operations, an authorization service failure should generally not result in unrestricted access.

### 12. AI Threat Modeling and Attack Surface Analysis

Threat modeling is a structured process for identifying threats, vulnerabilities, attack paths, and appropriate security controls.

AI threat modeling extends conventional application and infrastructure threat modeling to account for AI-specific components and attack techniques.

It should be performed during architecture design and revisited when significant changes occur.

#### 12.1 AI Attack Surface

The AI attack surface consists of the components, interfaces, data flows, and operational processes that could be targeted by an attacker.

Typical attack surfaces include:

| Attack surface                | Potential threat                                   |
| ----------------------------- | -------------------------------------------------- |
| User input                    | Prompt injection and malicious input               |
| Model API                     | Unauthorized access and abuse                      |
| Training data                 | Data poisoning                                     |
| Model artifacts               | Unauthorized modification                          |
| Vector database               | Unauthorized retrieval                             |
| Document ingestion            | Malicious content and indirect prompt injection    |
| Agent tools                   | Unauthorized actions                               |
| Application backend           | API and application vulnerabilities                |
| Cloud infrastructure          | Misconfiguration and compromise                    |
| Third-party provider          | Supply-chain and provider risk                     |
| Monitoring pipeline           | Log manipulation or sensitive information exposure |
| Model development environment | Compromised dependencies or training processes     |

The attack surface is not limited to the model endpoint. It includes the entire environment required to develop, operate, and maintain the AI solution.

#### 12.2 AI Threat Modeling Methodology

A practical threat modeling process can be organized into eight steps.

```
1. Define Business Purpose and Scope
                 |
                 v
2. Identify AI Components and Assets
                 |
                 v
3. Map Data Flows and Trust Boundaries
                 |
                 v
4. Identify Threat Actors and Attack Paths
                 |
                 v
5. Analyze Vulnerabilities and Impact
                 |
                 v
6. Define Security Controls
                 |
                 v
7. Validate Controls Through Testing
                 |
                 v
8. Document Residual Risk and Ownership
```

Step 1 — Define business purpose and scope

Identify:

- Business process.
- Intended AI functionality.
- Users and stakeholders.
- System boundaries.
- Deployment environment.
- Critical business dependencies.

Step 2 — Identify assets

Examples:

- Customer records.
- Employee information.
- Training datasets.
- Model weights.
- API credentials.
- Vector databases.
- System prompts.
- Agent memory.
- Business workflows.

Step 3 — Map data flows and trust boundaries

Document where data originates, how it is processed, where it is stored, and which external services receive it.

Step 4 — Identify threat actors and attack paths

Potential threat actors include:

- External attackers.
- Malicious insiders.
- Compromised suppliers.
- Malicious data contributors.
- Unauthorized application users.
- Attackers exploiting exposed APIs.

Step 5 — Analyze vulnerabilities and impact

Evaluate weaknesses and their potential consequences for confidentiality, integrity, availability, privacy, safety, and business operations.

Step 6 — Define controls

Identify preventive, detective, and corrective controls.

Step 7 — Validate controls

Use architecture reviews, configuration reviews, security testing, adversarial testing, and operational evidence.

Step 8 — Document residual risk

Assign owners, define remediation, and establish appropriate risk acceptance and monitoring.

#### 12.3 STRIDE Applied to AI Systems

STRIDE is a threat modeling classification developed for identifying common system security threats.

It covers six categories:

| STRIDE category        | Meaning                           | AI example                                         |
| ---------------------- | --------------------------------- | -------------------------------------------------- |
| Spoofing               | Impersonating an identity         | Attacker impersonates an AI service account        |
| Tampering              | Unauthorized modification         | Attacker modifies model artifacts or training data |
| Repudiation            | Denying an action                 | Agent execution lacks reliable audit records       |
| Information disclosure | Unauthorized exposure             | RAG returns restricted customer information        |
| Denial of service      | Preventing legitimate service use | Attacker exhausts model API capacity               |
| Elevation of privilege | Gaining unauthorized privileges   | Agent uses an overprivileged tool integration      |

STRIDE is useful for conventional system threats and can be applied to AI architecture components.

However, it does not independently provide a complete AI-specific threat taxonomy. It should be complemented with AI-focused resources such as MITRE ATLAS and OWASP GenAI security guidance.

#### 12.4 AI-Specific Threat Categories

AI threat modeling should consider attacks that target models, training data, inference inputs, retrieval systems, and agent behavior.

| Threat category                  | Description                                                            | Example                                         |
| -------------------------------- | ---------------------------------------------------------------------- | ----------------------------------------------- |
| Data poisoning                   | Manipulation of training data or learning processes                    | Malicious records influence model behavior      |
| Evasion attack                   | Manipulation of inference inputs to cause incorrect predictions        | Adversarial input bypasses a classifier         |
| Model extraction                 | Reproducing model behavior through repeated queries                    | Attacker builds a substitute model              |
| Model inversion                  | Attempting to infer sensitive training information from model behavior | Recovering information about training examples  |
| Membership inference             | Testing whether a specific record was included in training data        | Inferring dataset membership                    |
| Prompt injection                 | Manipulating model instructions through crafted input                  | User attempts to override intended instructions |
| Indirect prompt injection        | Malicious instructions embedded in retrieved content                   | A document attempts to influence an AI agent    |
| Model supply-chain attack        | Compromising model-related dependencies or artifacts                   | Malicious model package                         |
| Excessive agency                 | Granting agents unnecessary capabilities                               | Agent can perform unrestricted CRM operations   |
| Sensitive information disclosure | Exposure of protected information                                      | AI response reveals confidential records        |

These threats are not interchangeable.

For example, data poisoning targets the training or learning process, while evasion targets model behavior at inference time.

Likewise, prompt injection is not the same as traditional SQL injection, even though both involve manipulating system behavior through crafted input.

#### 12.5 Mapping AI Threats to MITRE ATLAS and OWASP

MITRE ATLAS and OWASP GenAI resources provide complementary perspectives.

| Assessment objective          | MITRE ATLAS                        | OWASP GenAI                                |
| ----------------------------- | ---------------------------------- | ------------------------------------------ |
| Understand adversary behavior | Adversarial tactics and techniques | Application-level security weaknesses      |
| Model and data attacks        | AI-focused attack techniques       | Model and supply-chain risks               |
| LLM application security      | Relevant AI attack techniques      | LLM application risk taxonomy              |
| Agent security                | AI adversarial techniques          | Excessive agency and related risks         |
| Threat intelligence           | Adversarial knowledge base         | Security guidance and risk identification  |
| Control development           | Supports threat-informed defenses  | Supports application security requirements |

The organization should use the actual edition and version of each reference when performing formal mapping.

### 13. AI Security Controls and Defensive Architecture

AI security controls must be designed according to the threats, assets, business requirements, and system architecture.

A control should have a clear objective, implementation mechanism, owner, and evidence requirement.

#### 13.1 Preventive, Detective, and Corrective Controls

| Control type | Purpose                                         | AI example                            |
| ------------ | ----------------------------------------------- | ------------------------------------- |
| Preventive   | Prevent or reduce the likelihood of an incident | Enforce retrieval authorization       |
| Detective    | Identify suspicious or unauthorized activity    | Detect abnormal model API usage       |
| Corrective   | Contain or recover from an incident             | Disable compromised agent credentials |

An effective AI security architecture requires all three categories.

For example, preventing unauthorized agent execution is preferable, but monitoring and response capabilities are still required in case preventive controls fail.

#### 13.2 AI Identity and Access Controls

Identity controls must cover both human users and non-human identities.

Recommended controls include:

- Centralized identity management.
- Strong authentication.
- Role-based or attribute-based authorization.
- Least privilege.
- Privileged access management.
- Service account governance.
- Credential rotation.
- API authorization.
- Segregation of development and production.
- Periodic access reviews.

Example: Agent authorization

An agent that creates customer support tickets should have a narrowly scoped identity.

The API should independently validate:

- The identity of the calling application.
- The requested operation.
- The applicable customer or record scope.
- The agent's permissions.
- Whether approval is required.

The LLM should not be responsible for making the final authorization decision.

#### 13.3 Data Security Controls

| Control             | Security objective                              |
| ------------------- | ----------------------------------------------- |
| Data classification | Identify sensitivity and handling requirements  |
| Data minimization   | Reduce unnecessary information processing       |
| Encryption          | Protect information at rest and in transit      |
| Access control      | Restrict access to authorized identities        |
| Data provenance     | Establish source and lineage                    |
| Data integrity      | Detect unauthorized modifications               |
| Retention controls  | Prevent excessive data retention                |
| Secure deletion     | Remove data according to approved requirements  |
| Dataset validation  | Identify malicious or unsuitable data           |
| Privacy testing     | Assess potential disclosure and inference risks |

Special attention should be given to vector databases, embedding stores, training datasets, and agent memory.

These assets may contain or expose information derived from sensitive source data.

#### 13.4 Model Security Controls

Model security should cover development, acquisition, registration, deployment, operation, and retirement.

Recommended controls:

- Model provenance verification.
- Approved model registry.
- Model artifact integrity checks.
- Version control.
- Secure model storage.
- Access restrictions.
- Model evaluation.
- Adversarial testing.
- Model update approval.
- Model performance monitoring.
- Controlled retirement.

An organization consuming an externally hosted model may not have access to its weights or internal training process.

In that situation, governance should focus on the available assurance information, contractual commitments, provider transparency, testing capabilities, usage restrictions, and risks that can be controlled at the application boundary.

#### 13.5 Prompt and Input Security Controls

Prompt security is an important AI application control area, but prompt instructions alone cannot enforce system authorization.

Recommended controls include:

- Input validation.
- Separation of system instructions and user content.
- Treating retrieved content as untrusted.
- Context minimization.
- Prompt injection testing.
- Restricted tool availability.
- Output validation.
- Monitoring suspicious requests.
- Human approval for sensitive operations.

The organization should assume that user input and retrieved external content may be malicious.

#### 13.6 RAG Security Controls

| Risk                      | Required control                                      |
| ------------------------- | ----------------------------------------------------- |
| Unauthorized retrieval    | Enforce source-level permissions                      |
| Malicious documents       | Validate and scan ingestion content                   |
| Indirect prompt injection | Treat retrieved content as untrusted                  |
| Sensitive embeddings      | Protect vector stores and metadata                    |
| Cross-tenant leakage      | Enforce tenant isolation                              |
| Stale information         | Establish re-indexing and document lifecycle controls |
| Unauthorized deletion     | Control indexing and deletion operations              |
| Retrieval abuse           | Monitor queries and access patterns                   |

A RAG solution should preserve the source system's authorization model wherever required by the business and security design.

#### 13.7 Agent and Tool Security Controls

Agentic systems require additional controls because they can initiate actions through connected tools.

Recommended controls include:

1. Assign unique identities to agents or execution services.
2. Restrict tool access according to business purpose.
3. Validate every sensitive action outside the model.
4. Enforce transaction and resource limits.
5. Require approval for high-impact actions.
6. Record tool calls and execution results.
7. Protect agent memory.
8. Restrict agent-to-agent permissions.
9. Establish emergency disablement procedures.
10. Test for unauthorized and unintended actions.

An agent should not be granted permission to execute a transaction merely because its model-generated plan recommends doing so.

### 14. AI Security Testing and Validation Architecture

A secure architecture must be validated through appropriate testing.

Documentation and design reviews provide important evidence, but they cannot independently demonstrate that security controls operate effectively.

#### 14.1 Security Testing Layers

#### 15.3 Architecture Risk Assessment Scoring

Organizations may use an internal risk scoring methodology to prioritize architecture-related risks.

For example:

\\[ \text{Inherent Risk Score} = \text{Likelihood} \times \text{Impact} \\]

A simple illustrative five-point scale:

| Score | Likelihood     | Impact     |
| ----- | -------------- | ---------- |
| 1     | Rare           | Negligible |
| 2     | Unlikely       | Minor      |
| 3     | Possible       | Moderate   |
| 4     | Likely         | Major      |
| 5     | Almost certain | Severe     |

An organization may multiply likelihood by impact to produce a prioritization score between 1 and 25.

This is an internal assessment convention, not a universal mathematical probability of loss.

Residual risk should be determined after evaluating control design, implementation, and operating effectiveness. It should not be calculated by automatically subtracting an arbitrary control score from the inherent risk score.

| Gate 4 — Validation   | Model evaluation and security testing                  | Testing sign-off            |
| Gate 5 — Production   | Risk acceptance, compliance, operational readiness     | Production authorization    |
| Gate 6 — Operations   | Monitoring, incidents, changes, performance            | Periodic governance review  |
| Gate 7 — Retirement   | Data deletion, access revocation, provider termination | Decommissioning approval    |

These gates are an illustrative governance model. The organization should adapt approval requirements to system risk and business criticality.

A low-risk internal productivity assistant should not necessarily require the same approval process as an AI system that makes consequential decisions or initiates sensitive transactions.

# 22.20 AI Reference Architectures and Frequently Confused Concepts

## Part 4 — Frequently Confused AI Concepts, Architectural Distinctions, Governance Implications, and Reference Models

### 16. Frequently Confused AI Architectural Concepts

AI architecture contains several concepts that are often used interchangeably despite having different technical meanings and security implications.

For AI security governance professionals, misunderstanding these distinctions can result in incorrect architecture assessments, incomplete risk registers, inappropriate control selection, and misleading compliance conclusions.

This section establishes the distinctions that should be understood when evaluating enterprise AI systems.

#### 16.1 AI Model vs. AI System

These are not interchangeable terms.

An AI model is a computational component that processes inputs and produces outputs based on its learned parameters or configured behavior.

An AI system is a broader system that incorporates one or more AI models alongside other technical and organizational components.

| Dimension        | AI model                                     | AI system                                                         |
| ---------------- | -------------------------------------------- | ----------------------------------------------------------------- |
| Definition       | Computational model performing an AI task    | Integrated system incorporating AI functionality                  |
| Components       | Model architecture, parameters, weights      | Models, data, applications, infrastructure, interfaces, workflows |
| Security scope   | Model integrity, robustness, confidentiality | End-to-end system security                                        |
| Governance scope | Model ownership and lifecycle                | System ownership, risk, compliance, operations                    |
| Example          | A language model                             | A customer service assistant using that model and Salesforce data |

Example

An organization uses an externally hosted LLM to power an internal HR assistant.

The LLM is the model.

The complete AI system includes:

- Employee-facing application.
- Authentication service.
- Authorization mechanisms.
- LLM provider.
- HR document repository.
- Retrieval service.
- Vector database.
- API gateway.
- Logging and monitoring.
- Human escalation workflow.

Assessing only the LLM would overlook most of the system's attack surface.

Governance implication: AI risk assessments must define the complete system boundary, not just identify the model.

#### 16.2 Foundation Model vs. Large Language Model

A foundation model is a model trained on broad data and intended to support multiple downstream tasks.

An LLM is a model designed to process and generate natural language.

Many LLMs are foundation models, but the concepts are not synonymous.

| Dimension               | Foundation model                                     | Large Language Model                                        |
| ----------------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| Scope                   | Broad model category                                 | Language-focused model category                             |
| Input and output        | May support text, images, audio, or other modalities | Primarily language-oriented, although multimodal LLMs exist |
| Downstream applications | Multiple tasks and modalities                        | Language understanding and generation tasks                 |
| Example                 | A multimodal foundation model                        | A text-oriented LLM                                         |

A foundation model may support language, image, audio, or other modalities. It does not have to be an LLM.

Governance implication: Model inventories should record model type, modality, provider, intended use, version, and capabilities rather than treating all AI models as LLMs.

#### 16.3 Generative AI vs. Predictive AI

Generative AI produces new content or outputs, whereas predictive AI estimates outcomes, classifications, probabilities, or future values.

| Dimension        | Generative AI                                           | Predictive AI                             |
| ---------------- | ------------------------------------------------------- | ----------------------------------------- |
| Primary function | Generate content                                        | Estimate or predict outcomes              |
| Typical output   | Text, images, audio, code                               | Scores, labels, probabilities, forecasts  |
| Example          | Customer service response generation                    | Customer churn prediction                 |
| Common risks     | Hallucination, prompt injection, information disclosure | Bias, model drift, inaccurate predictions |
| Evaluation       | Output quality, safety, factuality, task performance    | Accuracy, precision, recall, calibration  |

Some AI systems combine both approaches.

For example, a fraud detection platform may use a predictive model to identify suspicious transactions and a generative model to summarize investigation findings.

Governance implication: Risk assessment and testing must reflect the actual model function. Generative output controls are not a substitute for predictive model validation.

#### 16.4 Training vs. Inference

Training and inference are different stages of an AI model lifecycle.

| Dimension              | Training                                                       | Inference                                               |
| ---------------------- | -------------------------------------------------------------- | ------------------------------------------------------- |
| Purpose                | Learn or adjust model parameters                               | Generate predictions or outputs using a model           |
| Data                   | Training datasets                                              | Inference inputs                                        |
| Processing             | Optimization and parameter updates                             | Model execution                                         |
| Main security concerns | Data poisoning, model tampering, compromised training pipeline | Input manipulation, model abuse, information disclosure |
| Output                 | Trained or updated model                                       | Prediction or generated response                        |

A model may also undergo fine-tuning, which modifies an existing model using additional training data.

An enterprise consuming an external model through an API may only perform inference and have no direct control over the provider's training process.

Governance implication: Organizations must distinguish between risks they directly control and risks that depend on external provider practices and contractual assurance.

#### 16.5 Model Fine-Tuning vs. RAG

Fine-tuning and RAG are two different methods of adapting an AI application to specific tasks or knowledge requirements.

| Dimension           | Fine-tuning                                      | RAG                                                        |
| ------------------- | ------------------------------------------------ | ---------------------------------------------------------- |
| Main purpose        | Adapt model behavior through additional training | Supply relevant external information at inference time     |
| Model parameters    | May be modified                                  | Usually remain unchanged                                   |
| Knowledge updates   | May require further training                     | Can often be updated by modifying the knowledge repository |
| Data requirements   | Training examples                                | Searchable documents or knowledge sources                  |
| Main security risks | Training data poisoning and model integrity      | Unauthorized retrieval and indirect prompt injection       |
| Typical use         | Domain-specific behavior or task adaptation      | Enterprise knowledge retrieval                             |

Example

A company wants an AI assistant to understand its internal policies.

- Fine-tuning may help adapt the model's behavior or task performance.
- RAG can retrieve the current approved policy documents and provide them as context.

The two approaches can also be combined.

An important distinction is that fine-tuning does not automatically provide reliable access to current enterprise information, and RAG does not guarantee factual accuracy.

Governance implication: Select the approach based on business requirements, information sensitivity, update frequency, cost, operational complexity, and security exposure.

#### 16.6 RAG vs. Vector Database

RAG is an architectural pattern. A vector database is one possible component used within that architecture.

| Dimension      | RAG                                                     | Vector database                                          |
| -------------- | ------------------------------------------------------- | -------------------------------------------------------- |
| Nature         | Application architecture pattern                        | Data storage and retrieval technology                    |
| Function       | Retrieve external information to support generation     | Store and search vector representations                  |
| Components     | Ingestion, retrieval, context assembly, model inference | Embeddings, indexes, metadata, storage                   |
| Security scope | End-to-end retrieval and generation security            | Data access, integrity, isolation, storage               |
| Relationship   | May use a vector database                               | May support RAG and other similarity-search applications |

A RAG solution does not necessarily require a dedicated vector database. Alternative retrieval approaches may use conventional databases, search engines, or hybrid retrieval mechanisms.

Governance implication: Assess the complete retrieval process, including source permissions, indexing, metadata, storage, filtering, and context assembly.

#### 16.7 Embeddings vs. Tokens

These concepts are fundamentally different.

| Dimension         | Embeddings                                        | Tokens                                                                   |
| ----------------- | ------------------------------------------------- | ------------------------------------------------------------------------ |
| Definition        | Numerical vector representations of information   | Units into which input or output content is divided for model processing |
| Representation    | Multidimensional numerical vectors                | Text or other modality-specific token units                              |
| Purpose           | Represent semantic or other learned relationships | Support model input and output processing                                |
| Typical use       | Similarity search and retrieval                   | Model inference and generation                                           |
| Security concerns | Information exposure and unauthorized retrieval   | Excessive input, output, or usage consumption                            |

An embedding is not simply a token, and a token is not an embedding.

Governance implication: Both may have security and privacy implications, but their storage, processing, and access-control requirements should be evaluated according to their actual function.

#### 16.8 Model Gateway vs. API Gateway

These components can overlap in implementation, but their architectural responsibilities are different.

| Dimension             | Model gateway                                                       | API gateway                                          |
| --------------------- | ------------------------------------------------------------------- | ---------------------------------------------------- |
| Primary purpose       | Manage access to AI models and model services                       | Manage API traffic and interfaces                    |
| Typical capabilities  | Model routing, provider selection, model quotas, inference controls | Authentication, routing, rate limiting, API policies |
| AI-specific functions | Model selection and inference-related policies                      | May not understand model-specific requirements       |
| Security relevance    | Controls model access and usage                                     | Protects application and service interfaces          |

An organization may use a conventional API gateway, a specialized model gateway, or a platform combining both sets of capabilities.

Governance implication: Clearly identify where identity, authorization, model routing, data filtering, and usage controls are actually enforced.

### 17. Frequently Confused AI Security and Governance Concepts

#### 17.1 AI Safety vs. AI Security

AI safety and AI security are related but distinct disciplines.

AI safety focuses on preventing harmful, unreliable, or unintended AI behavior and outcomes.

AI security focuses on protecting AI systems against malicious attacks, unauthorized access, manipulation, and compromise.

| Dimension    | AI safety                                                     | AI security                                        |
| ------------ | ------------------------------------------------------------- | -------------------------------------------------- |
| Main concern | Harmful or unintended outcomes                                | Malicious activity and system compromise           |
| Examples     | Unsafe recommendations, harmful outputs, unreliable decisions | Prompt injection, model theft, unauthorized access |
| Focus        | System behavior and consequences                              | Threats, vulnerabilities, and defenses             |
| Controls     | Evaluation, safeguards, oversight, risk mitigation            | Authentication, authorization, testing, monitoring |

There is overlap. A successful security attack may produce an unsafe outcome, while an unsafe model behavior may occur without any malicious attacker.

Governance implication: AI governance programs should address both safety and security rather than treating one as a substitute for the other.

#### 17.2 AI Security vs. Security of AI

These phrases are sometimes used interchangeably, but they can have different scopes depending on context.

- Security of AI: Protecting AI systems, models, data, infrastructure, and applications.
- AI security: May also refer more broadly to the security discipline covering AI systems and AI-enabled environments.
- AI for cybersecurity: Using AI technologies to improve cybersecurity activities, such as threat detection, alert analysis, and security operations.

The distinction between securing AI and using AI to secure enterprise environments is especially important.

| Area                                   | Example                                            |
| -------------------------------------- | -------------------------------------------------- |
| Security of AI                         | Protecting an LLM from prompt injection            |
| AI for cybersecurity                   | Using an LLM to summarize SOC alerts               |
| Cybersecurity of AI-enabled operations | Securing an AI-driven security automation workflow |

Governance implication: An organization using AI in its SOC must govern both the AI system itself and the cybersecurity processes that depend on it.

#### 17.3 Authentication vs. Authorization

These concepts must never be confused.

| Concept        | Meaning                      | AI example                                                             |
| -------------- | ---------------------------- | ---------------------------------------------------------------------- |
| Authentication | Establishes identity         | Verify the employee accessing an AI assistant                          |
| Authorization  | Determines permitted actions | Determine whether the employee can retrieve a specific customer record |

An AI agent may be authenticated through a service identity but still lack authorization to access a particular resource.

Governance implication: Every sensitive AI action must be independently authorized at the relevant application, API, or resource boundary.

#### 17.4 Guardrails vs. Security Controls

Guardrails are mechanisms designed to constrain or guide AI behavior.

Security controls are broader mechanisms intended to protect systems, data, services, and business processes.

| Dimension    | AI guardrails                                         | Security controls                                                             |
| ------------ | ----------------------------------------------------- | ----------------------------------------------------------------------------- |
| Main purpose | Guide or constrain model behavior                     | Protect assets and enforce security requirements                              |
| Examples     | Content filters, output restrictions, prompt policies | IAM, encryption, API authorization, network segmentation                      |
| Enforcement  | May depend on model or application behavior           | Should be enforced through appropriate technical or organizational mechanisms |
| Limitation   | May be bypassed or fail                               | Can also fail, but can provide independent enforcement boundaries             |

Guardrails are useful, but a prompt-based guardrail should not be treated as an access-control mechanism.

For example, telling an LLM not to retrieve confidential customer records does not prevent the retrieval service from returning those records.

#### 17.5 Explainability vs. Interpretability

These terms are related but are not always used identically.

- Interpretability generally concerns how understandable a model's internal mechanisms or behavior are.
- Explainability generally concerns how explanations of model behavior or outputs are produced and communicated.

The precise usage can vary across research and standards contexts.

| Dimension            | Interpretability                                    | Explainability                                            |
| -------------------- | --------------------------------------------------- | --------------------------------------------------------- |
| Main focus           | Understanding model behavior or internal mechanisms | Providing explanations of predictions or outputs          |
| Example              | An inherently interpretable decision tree           | An explanation generated for a complex model's prediction |
| Governance relevance | Understanding model behavior                        | Supporting transparency, review, and accountability       |

An explanation does not automatically prove that a model is correct, fair, or reliable.

Governance implication: Assess explanation quality, limitations, intended audience, and whether the explanation is sufficient for the relevant business or regulatory purpose.

#### 17.6 Accuracy vs. Reliability vs. Robustness

These are separate model quality and security properties.

| Concept     | Meaning                                                                   | Example                                    |
| ----------- | ------------------------------------------------------------------------- | ------------------------------------------ |
| Accuracy    | Correctness of outputs against an evaluation reference                    | Percentage of correctly classified records |
| Reliability | Consistency of performance under expected operating conditions            | Stable service behavior over time          |
| Robustness  | Ability to maintain acceptable behavior under variations or perturbations | Resistance to selected adversarial inputs  |

A model can be accurate on a benchmark dataset but unreliable in production because its input data changes.

Likewise, a model can perform well under normal conditions but be vulnerable to adversarial manipulation.

Governance implication: Model evaluation should include performance, robustness, reliability, and operational suitability rather than relying on a single accuracy metric.

#### 17.7 Data Drift vs. Concept Drift

These terms describe different changes that can affect model performance.

| Dimension        | Data drift                                          | Concept drift                                                         |
| ---------------- | --------------------------------------------------- | --------------------------------------------------------------------- |
| Meaning          | Changes in input data distribution                  | Changes in the relationship between inputs and target outcomes        |
| Example          | Customer demographic distribution changes           | Customer purchasing behavior changes in response to market conditions |
| Potential impact | Model receives inputs different from those expected | Previously learned relationships become less reliable                 |
| Monitoring       | Input distribution analysis                         | Model performance and relationship analysis                           |

Not every data distribution change causes concept drift, and concept drift may occur without obvious changes in all input distributions.

Governance implication: Define monitoring methods and escalation thresholds appropriate to the model's purpose and operating environment.

#### 17.8 Model Validation vs. Model Monitoring

| Dimension | Model validation                                          | Model monitoring                                     |
| --------- | --------------------------------------------------------- | ---------------------------------------------------- |
| Purpose   | Assess whether the model is suitable for its intended use | Observe model behavior during operation              |
| Timing    | Before deployment and at defined reassessment points      | During operational use                               |
| Examples  | Performance testing, bias evaluation, robustness testing  | Drift monitoring, error tracking, performance alerts |
| Output    | Validation findings and approval decision                 | Operational metrics and alerts                       |

A model that passed validation before deployment may become unsuitable later due to changes in data, users, business processes, or operating conditions.

Governance implication: Validation and monitoring must be connected through lifecycle governance.

#### 17.9 Human-in-the-Loop vs. Human-on-the-Loop

These approaches describe different forms of human involvement.

| Dimension          | Human-in-the-loop                                       | Human-on-the-loop                                    |
| ------------------ | ------------------------------------------------------- | ---------------------------------------------------- |
| Human role         | Participates directly in the decision or action process | Supervises the automated process                     |
| Intervention       | Often required before a defined action proceeds         | May intervene when predefined conditions occur       |
| Example            | Human approves an AI-generated transaction              | Human monitors an automated workflow and can stop it |
| Governance concern | Review quality and decision authority                   | Monitoring effectiveness and intervention capability |

Neither model automatically guarantees meaningful oversight.

A human reviewer must have adequate competence, information, authority, and time to perform the assigned responsibility.

### 18. AI Provider, Deployment, and Ownership Concepts

AI architecture also involves several organizational and commercial distinctions that directly affect governance responsibilities.

#### 18.1 AI Provider vs. AI Deployer

The EU AI Act distinguishes roles such as providers and deployers.

In general:

- A provider develops an AI system or general-purpose AI model, or has one developed, and places it on the market or puts the AI system into service under its name or trademark, according to the applicable legal definitions.
- A deployer uses an AI system under its authority, except where use is in a personal non-professional activity.

Other roles, including importers, distributors, product manufacturers, and authorized representatives, may also be relevant.

An organization can occupy more than one role depending on its activities and the applicable legal provisions.

| Dimension              | Provider                                                                 | Deployer                                                                          |
| ---------------------- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Main activity          | Develops or supplies the AI system                                       | Uses the AI system                                                                |
| Typical responsibility | Provider obligations under applicable legislation                        | Deployer obligations under applicable legislation                                 |
| Governance focus       | Development, documentation, conformity and other applicable requirements | Appropriate use, operational controls, monitoring, and applicable deployer duties |
| Example                | Company placing its own AI product on the market                         | Telecom operator using a third-party AI assistant                                 |

The legal role must be determined from actual activities and the applicable legislation. Simply purchasing a model API does not automatically make an organization the provider of that model.

Governance implication: Third-party contracts and governance procedures must clearly identify the parties' actual responsibilities.

#### 18.2 Cloud Service Provider vs. AI Model Provider

A cloud provider and an AI model provider may be the same company, but they are not necessarily the same entity or service.

| Dimension               | Cloud service provider                                 | AI model provider                                  |
| ----------------------- | ------------------------------------------------------ | -------------------------------------------------- |
| Main service            | Computing, networking, storage, and platform services  | AI model development or provision                  |
| Example responsibility  | Hosting infrastructure and managed services            | Model capabilities and model-related documentation |
| Security considerations | Infrastructure, cloud configuration, platform security | Model behavior, model updates, model limitations   |
| Governance              | Cloud supplier risk                                    | AI model supplier risk                             |

An enterprise may host a third-party model on its own cloud infrastructure. It may also use a cloud provider's managed model service or access a model through an unrelated provider.

The organization must identify the complete supplier and subprocessor chain.

#### 18.3 Open Source vs. Open Weight

These terms are frequently confused.

| Dimension             | Open source                                                                                                               | Open weight                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Meaning               | Software or model-related materials made available under a defined open-source license or applicable open-source criteria | Model weights are made available for use under specified terms         |
| Source code           | Depends on the specific project and license                                                                               | Not necessarily provided                                               |
| Training data         | Not automatically available                                                                                               | Not necessarily available                                              |
| Training methodology  | Not automatically disclosed                                                                                               | Not necessarily disclosed                                              |
| Modification          | Depends on license and available materials                                                                                | May be technically possible, subject to license and implementation     |
| Security transparency | Depends on the materials and development process                                                                          | Weights alone provide limited transparency into the complete lifecycle |

The term "open source AI" should not be assumed to mean that model weights, training data, datasets, code, and development documentation are all publicly available.

Governance implication: Assess licensing, provenance, security maintenance, dependencies, documentation, and actual transparency rather than relying on marketing terminology.

#### 18.4 AI Model Inventory vs. AI System Inventory

An AI model inventory and an AI system inventory serve different purposes.

| Dimension        | Model inventory                                 | AI system inventory                                                    |
| ---------------- | ----------------------------------------------- | ---------------------------------------------------------------------- |
| Scope            | Models used or managed by the organization      | Complete AI-enabled systems and use cases                              |
| Information      | Model name, version, provider, type, provenance | Business purpose, owner, users, data, architecture, model dependencies |
| Governance focus | Model lifecycle and integrity                   | Enterprise risk, regulatory applicability, operations                  |
| Example          | LLM version and provider                        | Customer service assistant using that LLM, CRM, RAG, and APIs          |

An organization may use one model across several applications.

Likewise, one AI system may use multiple models.

A mature governance program should maintain a clear relationship between model records and system records.

#### 18.5 Model Owner vs. System Owner vs. Risk Owner

These roles may be held by different individuals or organizational functions.

| Role            | Primary responsibility                                                       |
| --------------- | ---------------------------------------------------------------------------- |
| Model owner     | Accountable for model lifecycle, documentation, and model-related governance |
| System owner    | Accountable for the integrated AI system and its operation                   |
| Business owner  | Accountable for the business purpose and intended use                        |
| Risk owner      | Accountable for managing a defined risk and its treatment                    |
| Control owner   | Responsible for operating an assigned control                                |
| Data owner      | Accountable for defined data assets and associated governance                |
| Technical owner | Responsible for technical implementation and maintenance                     |

For example, a telecom operator's customer service director may own the business use case, the IT department may own the integrated AI system, a data science team may own an internal model, and a designated risk owner may oversee a specific operational risk.

Governance implication: Accountability must be explicitly assigned. A general statement that "IT owns the AI system" is insufficient when business, data, model, and risk responsibilities are distributed.

A telecommunications operator plans to deploy an AI-powered customer service assistant integrated with Salesforce CRM.

- Search internal knowledge articles.
- Summarize customer interactions.
- Generate customer service responses.
- Recommend service actions.

The solution uses:

- Salesforce CRM.
- An AI application backend.

#### 20.4 Governance and Security Approval Checklist

Before production deployment, the organization should verify:

Business governance

- Business purpose is approved.
- System owner and business owner are assigned.
- Intended use and prohibited use are documented.
- AI system inventory is updated.
- Risk assessment is completed.

Architecture

- Architecture diagrams are approved.
- Data flows are documented.
- Trust boundaries are identified.
- External dependencies are recorded.
- Model and system versions are documented.

Security

- Identity and access controls are validated.
- CRM authorization is enforced.
- API security is tested.
- RAG retrieval permissions are validated.
- Agent permissions are restricted.
- Prompt injection testing is completed.
- Sensitive data protections are implemented.

Privacy and compliance

- Regulatory applicability is assessed.
- Data processing purposes are documented.
- Provider data-use terms are reviewed.
- Retention and deletion requirements are defined.
- Required privacy assessments are completed.

Operations and assurance

- Monitoring is implemented.
- Incident response procedures are approved.
- Fallback and recovery procedures are tested.
- Security findings are remediated or formally risk-accepted.
- Production authorization is documented.

#### 20.5 Final Governance Decision

The system should not be approved solely because the model produces acceptable responses or passes a functional demonstration.

Production approval should consider:

1. Business suitability.
2. Architectural completeness.
3. Security control implementation.
4. Data protection.
5. Regulatory applicability.
6. Third-party dependencies.
7. Human oversight.
8. Operational resilience.
9. Testing evidence.
10. Residual risk acceptance.

The approval decision must be made by appropriately authorized stakeholders based on documented evidence and the organization's risk governance process.
