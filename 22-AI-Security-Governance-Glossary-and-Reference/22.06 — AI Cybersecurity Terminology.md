# 22.06 — AI Cybersecurity Terminology

## Part 1 — AI Security Foundations, Architecture, Core Principles, and Threat Landscape

### 1. Introduction to AI Cybersecurity

Artificial Intelligence introduces new capabilities into enterprise environments, but it also creates security risks that traditional cybersecurity controls may not fully address.

AI systems process data, identify patterns, generate outputs, make predictions, and increasingly interact with applications and infrastructure. These capabilities introduce additional attack surfaces involving models, datasets, training pipelines, inference services, prompts, APIs, AI agents, and third-party AI components.

AI cybersecurity focuses on protecting these systems against unauthorized access, manipulation, exploitation, data leakage, service disruption, and other security threats.

The challenge is not simply to protect the AI model. Organizations must protect the entire AI ecosystem, including its data, infrastructure, development processes, integrations, and operational environment.

For cybersecurity GRC professionals, the central question is:

How can an organization ensure that AI systems remain secure, trustworthy, resilient, and protected against malicious manipulation throughout their lifecycle?

#### 1.1 AI Security

AI security refers to the protection of AI systems, models, datasets, infrastructure, applications, and associated processes against threats that could compromise their confidentiality, integrity, availability, or intended behavior.

AI security addresses risks such as:

- Unauthorized access to AI systems.
- Training data poisoning.
- Model manipulation.
- Adversarial attacks.
- Model theft and extraction.
- Prompt injection.
- Sensitive information disclosure.
- Inference endpoint abuse.
- AI supply chain compromise.
- Unauthorized tool execution.
- Model denial of service.
- Compromised AI infrastructure.

Example:

A financial institution deploys an AI model to detect fraudulent transactions.

An attacker manipulates the model's training data to influence its classification behavior, causing fraudulent transactions to be incorrectly classified as legitimate.

The security failure affects the integrity and reliability of the AI system.

GRC perspective:

AI security must be integrated into enterprise cybersecurity governance, risk management, secure development, third-party risk management, and operational security monitoring.

#### 1.2 AI Cybersecurity

AI cybersecurity refers to the application of cybersecurity principles, technologies, and governance practices to protect AI-enabled systems and their supporting environments.

It includes both:

1. Protecting AI systems against cyberattacks.
2. Addressing security risks introduced when AI is used within cybersecurity operations.

These are related but different activities.

| Area                 | Objective                             | Example                                           |
| -------------------- | ------------------------------------- | ------------------------------------------------- |
| Cybersecurity for AI | Protect AI systems and infrastructure | Prevent model poisoning and unauthorized access   |
| AI for Cybersecurity | Use AI to improve security operations | AI-powered threat detection and incident analysis |

Important distinction:

Using AI to detect cyber threats does not automatically make the AI system secure. An AI-powered SOC platform also requires model security, data protection, access control, validation, and monitoring.

#### 1.3 AI System Security

AI system security refers to the security of the complete AI system, including its model, data, software, infrastructure, integrations, interfaces, and operational processes.

Example:

An enterprise AI-powered fraud detection system may include:

- Transaction databases.
- Data ingestion pipelines.
- Feature engineering processes.
- Machine learning models.
- Model training infrastructure.
- Inference endpoints.
- API gateways.
- Monitoring platforms.
- Security administration interfaces.

A vulnerability in any of these components may compromise the overall system.

GRC concern:

Security assessments must consider the complete AI system architecture rather than evaluating only the model or its provider.

#### 1.4 AI Security vs. AI Safety

These concepts are related but have different objectives.

AI security focuses on protecting AI systems against malicious attacks, unauthorized access, exploitation, and compromise.

AI safety focuses on preventing unacceptable harm arising from AI system behavior, including unintended, unsafe, or harmful outcomes.

| Dimension        | AI Security                                                       | AI Safety                                                          |
| ---------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------ |
| Primary concern  | Malicious exploitation and compromise                             | Harmful or unsafe behavior                                         |
| Main objective   | Protect system confidentiality, integrity, and availability       | Ensure behavior remains within acceptable safety boundaries        |
| Typical threats  | Data poisoning, model theft, prompt injection                     | Unsafe recommendations, harmful outputs, uncontrolled behavior     |
| Primary controls | IAM, encryption, secure development, monitoring, threat detection | Safety testing, guardrails, human oversight, behavioral evaluation |
| Example          | Prevent unauthorized access to a model endpoint                   | Prevent an AI system from recommending dangerous actions           |

An AI system can be secure but unsafe.

For example, an AI system may have strong access controls and encryption but still produce dangerous recommendations.

Conversely, an AI system may produce generally safe outputs but remain vulnerable to unauthorized access or data theft.

GRC principle: AI security and AI safety should be governed together where appropriate, but they must not be treated as interchangeable disciplines.

### 2. The AI Security Triad: Confidentiality, Integrity, and Availability

The traditional CIA Triad remains fundamental to AI cybersecurity. However, AI systems introduce specific threats and failure scenarios that require additional security considerations.

#### 2.1 Confidentiality

Confidentiality ensures that information is accessible only to authorized individuals, systems, and processes.

In AI environments, confidentiality applies to:

- Training datasets.
- Model parameters and weights.
- Inference inputs.
- Prompts and conversation history.
- Embeddings.
- Vector databases.
- Model outputs.
- API credentials.
- Agent memory.
- Enterprise knowledge repositories.

Example:

A company deploys an internal LLM that processes confidential customer information.

If the system exposes customer data through unauthorized retrieval, insecure logging, or cross-tenant access, confidentiality is compromised.

AI confidentiality threats include:

- Training data extraction.
- Membership inference.
- Model inversion.
- Sensitive information disclosure.
- Unauthorized model access.
- Prompt leakage.
- Cross-tenant data exposure.
- Insecure memory access.
- Data exfiltration through AI integrations.

GRC controls:

- Data classification.
- Encryption at rest and in transit.
- Role-Based Access Control (RBAC).
- Attribute-Based Access Control (ABAC).
- Data Loss Prevention (DLP).
- Data minimization.
- Secure secrets management.
- Tenant isolation.
- Retention and deletion controls.

#### 2.2 Integrity

Integrity ensures that data, models, configurations, and system operations remain accurate, complete, and protected against unauthorized modification.

In AI environments, integrity applies to:

- Training data.
- Validation datasets.
- Model parameters.
- Model artifacts.
- Feature pipelines.
- Model configurations.
- Inference requests.
- AI-generated outputs.
- Knowledge repositories.
- Agent memory.
- Tool execution results.

Example:

An attacker manipulates a machine learning training dataset to influence a fraud detection model.

The model subsequently fails to identify certain fraudulent transactions.

This is a data integrity and model integrity problem.

AI integrity threats include:

- Data poisoning.
- Model poisoning.
- Backdoor insertion.
- Adversarial manipulation.
- Unauthorized model modification.
- Compromised model artifacts.
- Feature manipulation.
- Memory poisoning.
- Inference output manipulation.

GRC controls:

- Dataset provenance.
- Data validation.
- Cryptographic integrity verification.
- Model version control.
- Signed model artifacts.
- Secure development pipelines.
- Controlled model deployment.
- Independent model validation.
- Change management.
- Continuous integrity monitoring.

#### 2.3 Availability

Availability ensures that AI systems, models, infrastructure, and supporting services remain accessible and operational when required.

AI availability depends on:

- Model endpoints.
- Compute infrastructure.
- Storage services.
- Data pipelines.
- APIs.
- Network connectivity.
- Model-serving platforms.
- External providers.
- Orchestration services.

Example:

An attacker sends excessive requests to an AI inference endpoint, exhausting GPU resources and preventing legitimate users from accessing the service.

AI availability threats include:

- Denial of Service (DoS).
- Distributed Denial of Service (DDoS).
- Model inference flooding.
- Resource exhaustion.
- Denial of Wallet.
- Excessive agent execution.
- API abuse.
- Infrastructure failure.
- Third-party model provider outages.

GRC controls:

- Rate limiting.
- Resource quotas.
- Capacity planning.
- Infrastructure redundancy.
- Load balancing.
- Monitoring and alerting.
- Disaster recovery.
- Business continuity planning.
- Provider resilience assessments.
- Circuit breakers and execution limits.

#### 2.4 CIA Triad Applied to AI Systems

| Security Objective | AI Asset               | Example Threat                   | Example Control                      |
| ------------------ | ---------------------- | -------------------------------- | ------------------------------------ |
| Confidentiality    | Training dataset       | Unauthorized data extraction     | Access controls and encryption       |
| Confidentiality    | Model weights          | Model theft                      | Restricted model repository          |
| Confidentiality    | Prompts and context    | Sensitive information disclosure | DLP and context isolation            |
| Integrity          | Training dataset       | Data poisoning                   | Data validation and provenance       |
| Integrity          | Model artifact         | Unauthorized model modification  | Artifact signing and version control |
| Integrity          | Inference output       | Manipulated response             | Output validation                    |
| Availability       | Model endpoint         | Inference flooding               | Rate limiting                        |
| Availability       | GPU infrastructure     | Resource exhaustion              | Resource quotas and scaling          |
| Availability       | External model service | Provider outage                  | Resilience and fallback planning     |

#### 2.5 AI Security Beyond the CIA Triad

Although CIA remains foundational, AI systems introduce additional security and assurance properties.

| Property        | Meaning                                                               | AI Security Application                               |
| --------------- | --------------------------------------------------------------------- | ----------------------------------------------------- |
| Authenticity    | Assurance that an entity or information source is genuine             | Verify model and dataset provenance                   |
| Accountability  | Ability to assign responsibility for actions                          | Identify model, agent, and system owners              |
| Traceability    | Ability to follow data and operations through a system                | Track model versions and inference activity           |
| Non-repudiation | Evidence supporting the attribution of an action                      | Preserve reliable transaction and audit records       |
| Resilience      | Ability to withstand and recover from disruption                      | Recover AI services after compromise                  |
| Robustness      | Ability to maintain expected performance under challenging conditions | Evaluate adversarial and distribution-shift scenarios |
| Provenance      | Origin and history of data or artifacts                               | Track training data and model lineage                 |

These properties complement the CIA Triad and help establish a more complete AI security governance model.

### 3. AI Security Architecture and Attack Surface

AI security architecture defines how security controls are designed and implemented across the AI system lifecycle.

It considers the interaction between data, models, infrastructure, applications, users, and external dependencies.

#### 3.1 AI Security Architecture

AI security architecture refers to the design of technical and organizational security controls used to protect AI systems and their supporting environments.

It should address:

- Data ingestion.
- Data storage.
- Model development.
- Model training.
- Model repositories.
- Model deployment.
- Inference services.
- Application integrations.
- User access.
- Monitoring.
- Incident response.
- Third-party dependencies.

A secure AI architecture must establish trust boundaries, enforce access restrictions, protect data flows, and provide sufficient observability.

#### 3.2 AI Attack Surface

The AI attack surface consists of all interfaces, components, processes, and dependencies that may be exploited to compromise an AI system.

| AI Component          | Potential Attack Surface                  |
| --------------------- | ----------------------------------------- |
| Data sources          | Malicious or manipulated datasets         |
| Data ingestion        | Unauthorized data insertion               |
| Data preprocessing    | Pipeline manipulation                     |
| Feature engineering   | Feature manipulation                      |
| Training environment  | Unauthorized access or poisoning          |
| Model artifacts       | Model replacement or tampering            |
| Model registry        | Unauthorized model publication            |
| Inference endpoint    | API abuse and adversarial inputs          |
| Prompt interface      | Prompt injection and manipulation         |
| Vector database       | Unauthorized retrieval and data poisoning |
| Agent tools           | Unauthorized function execution           |
| Cloud infrastructure  | Workload compromise                       |
| Monitoring systems    | Log manipulation and detection evasion    |
| Third-party providers | Supply chain compromise                   |

GRC concern:

An AI attack surface assessment must consider every component that can influence model behavior, access sensitive information, or execute an operation.

#### 3.3 AI Trust Boundary

An AI trust boundary is a logical or technical boundary separating components, users, data, and services with different levels of trust.

Example:

An enterprise AI application may interact with:

- Authenticated employees.
- Customer-uploaded documents.
- Internal knowledge repositories.
- External APIs.
- Third-party model providers.

These sources have different trust levels.

The system must not assume that all input data, model responses, or external integrations are trustworthy.

Trust boundaries should be documented in:

- Architecture diagrams.
- Data flow diagrams.
- Threat models.
- Security design documents.
- Access control specifications.

#### 3.4 AI Threat Modeling

AI threat modeling is the systematic process of identifying, analyzing, prioritizing, and mitigating threats affecting AI systems.

A comprehensive assessment should consider:

1. AI business purpose.
2. System architecture.
3. Data assets and classification.
4. Model type and deployment.
5. User and workload identities.
6. External integrations.
7. Trust boundaries.
8. Potential threat actors.
9. Attack vectors.
10. Business impact.
11. Existing controls.
12. Residual risk.

Traditional threat modeling methodologies such as STRIDE can be used alongside AI-specific threat taxonomies.

AI-specific frameworks and resources, such as MITRE ATLAS and OWASP guidance, help identify threats that may not be sufficiently represented in conventional application threat models.

#### 3.5 AI Threat Actor

An AI threat actor is an individual, group, organization, or compromised system that attempts to exploit, manipulate, disrupt, or gain unauthorized access to an AI system.

Potential threat actors include:

| Threat Actor           | Possible Motivation         | Example                                              |
| ---------------------- | --------------------------- | ---------------------------------------------------- |
| Cybercriminal          | Financial gain              | Steal customer information through an AI application |
| Nation-state actor     | Espionage or disruption     | Target sensitive AI research                         |
| Malicious insider      | Fraud or sabotage           | Manipulate model training data                       |
| Competitor             | Intellectual property theft | Extract proprietary model information                |
| Hacktivist             | Ideological objectives      | Disrupt an AI-powered public service                 |
| Malicious supplier     | Supply chain compromise     | Introduce malicious code into an AI component        |
| Opportunistic attacker | Exploitation                | Abuse exposed inference endpoints                    |

#### 3.6 AI Attack Vector

An AI attack vector is the method or pathway through which an attacker attempts to compromise an AI system.

Examples include:

- Malicious training data.
- Manipulated inference inputs.
- Prompt injection.
- Compromised model repositories.
- Insecure APIs.
- Stolen credentials.
- Vulnerable agent tools.
- Malicious third-party components.
- Unsecured vector databases.

#### 3.7 AI Attack Path

An AI attack path describes the sequence of steps an attacker uses to exploit one or more vulnerabilities to achieve an objective.

Example:

```
Attacker
   |
   v
Compromised External Document
   |
   v
AI Application Retrieves Document
   |
   v
Indirect Prompt Injection
   |
   v
Agent Manipulated
   |
   v
Unauthorized Tool Invocation
   |
   v
Sensitive Data Access
   |
   v
Potential Data Exfiltration
```

This example demonstrates how an apparently harmless external document can become an entry point into an enterprise AI environment.

GRC concern:

Threat modeling should identify complete attack paths rather than assessing individual vulnerabilities in isolation.

### 4. AI Security Threat Classification

AI security threats can be categorized according to the component targeted, the attack technique, and the security property affected.

This classification helps organizations develop consistent risk registers and security control mappings.

#### 4.1 Data-Level Attacks

Data-level attacks target the datasets and information used by AI systems.

Examples include:

- Training data poisoning.
- Data manipulation.
- Unauthorized data insertion.
- Data exfiltration.
- Data integrity compromise.
- Data provenance manipulation.
- Label manipulation.

These attacks may affect model training, validation, inference, or retrieval.

#### 4.2 Model-Level Attacks

Model-level attacks target the model itself, its parameters, behavior, or intellectual property.

Examples include:

- Model extraction.
- Model inversion.
- Membership inference.
- Backdoor attacks.
- Model poisoning.
- Unauthorized model modification.
- Model theft.

The objective may be to steal model intellectual property, reveal sensitive training information, or manipulate model behavior.

#### 4.3 Inference-Level Attacks

Inference-level attacks target the deployed model during prediction or generation.

Examples include:

- Adversarial examples.
- Evasion attacks.
- Malicious prompts.
- Prompt injection.
- Inference endpoint abuse.
- Output manipulation.
- Sensitive information disclosure.

These attacks can affect the model's responses or decisions during production operation.

#### 4.4 Infrastructure-Level Attacks

Infrastructure-level attacks target the systems supporting AI development, training, deployment, and inference.

Examples include:

- Cloud account compromise.
- Container vulnerabilities.
- GPU infrastructure abuse.
- API exploitation.
- Runtime compromise.
- Network attacks.
- Secrets theft.
- Software supply chain compromise.

#### 4.5 Application-Level Attacks

Application-level attacks target AI-enabled applications and their integrations.

Examples include:

- Broken access control.
- Insecure output handling.
- Prompt injection.
- Excessive agency.
- Unauthorized function execution.
- Insecure file processing.
- API abuse.
- Cross-tenant information disclosure.

#### 4.6 Supply Chain Attacks

AI supply chain attacks target external components or providers used to develop, deploy, or operate AI systems.

Potential targets include:

- Foundation model providers.
- Pretrained models.
- Open-weight model repositories.
- Training datasets.
- AI frameworks.
- Software dependencies.
- Container images.
- Plugins and connectors.
- External inference services.

#### 4.7 AI Security Threat Classification Matrix

| Threat Category      | Target                     | Example Threat           | Potential Security Impact        |
| -------------------- | -------------------------- | ------------------------ | -------------------------------- |
| Data-level           | Dataset                    | Data poisoning           | Model integrity compromise       |
| Model-level          | Model parameters           | Model theft              | Intellectual property loss       |
| Inference-level      | Model endpoint             | Adversarial input        | Incorrect prediction             |
| Application-level    | AI application             | Prompt injection         | Unauthorized actions             |
| Infrastructure-level | Cloud environment          | Credential compromise    | System compromise                |
| Supply chain         | Third-party model          | Malicious model artifact | Backdoor or compromised behavior |
| Agentic              | Agent tools                | Excessive agency         | Unauthorized system operations   |
| Privacy              | Training or inference data | Membership inference     | Sensitive information exposure   |

### 5. AI Security Principles and Defensive Strategies

AI security requires a layered defensive approach that combines conventional cybersecurity controls with AI-specific protections.

#### 5.1 Security by Design

Security by Design means integrating security requirements and controls into the architecture and development of an AI system from the beginning.

Security should not be treated as a final deployment activity.

Example:

A company designing an AI-powered fraud detection platform incorporates:

- Data access restrictions.
- Secure training pipelines.
- Model artifact integrity.
- Inference API authentication.
- Monitoring.
- Incident response.
- Secure deployment processes.

GRC concern:

Security requirements should be documented during project initiation and validated before production approval.

#### 5.2 Secure by Default

Secure by Default means AI systems should initially operate with restrictive security settings rather than requiring administrators to discover and correct unsafe configurations.

Examples:

- Private model endpoints by default.
- Restricted API access.
- Disabled unnecessary tools.
- Read-only permissions unless write access is required.
- Secure logging configuration.
- Restricted external network connectivity.
- Encryption enabled.

#### 5.3 Least Privilege

Least privilege means granting users, applications, workloads, and AI agents only the permissions necessary to perform their approved functions.

Example:

An AI model serving application may require read access to a designated model repository but should not receive administrative permissions over the entire cloud environment.

Least privilege should apply to:

- Human users.
- Service accounts.
- AI agents.
- APIs.
- Databases.
- Model repositories.
- Cloud workloads.
- Training pipelines.

#### 5.4 Defense in Depth

Defense in Depth is the use of multiple independent security controls to protect an asset or system.

For AI environments, this may include:

1. Identity and access management.
2. Data protection.
3. Secure development.
4. Model artifact protection.
5. API security.
6. Runtime isolation.
7. Monitoring and detection.
8. Incident response.

If one security control fails, additional controls should reduce the likelihood or impact of compromise.

#### 5.5 Zero Trust

Zero Trust is a security approach that avoids implicit trust based solely on network location or previous authentication.

Access decisions should consider identity, resource, context, and applicable policy.

For AI environments, Zero Trust can be applied to:

- Model endpoint access.
- Data retrieval.
- API communication.
- Agent tool execution.
- Model repositories.
- Cloud workloads.
- Third-party integrations.

An AI workload operating inside a corporate network should not automatically be trusted with access to every internal resource.

#### 5.6 Secure AI Development Lifecycle

A Secure AI Development Lifecycle integrates security activities into AI system design, development, training, testing, deployment, operation, and retirement.

| Lifecycle Stage   | Security Activity                                      |
| ----------------- | ------------------------------------------------------ |
| Requirements      | Define security and privacy requirements               |
| Architecture      | Identify trust boundaries and attack surfaces          |
| Data acquisition  | Assess data sources and provenance                     |
| Data preparation  | Validate and protect datasets                          |
| Model development | Secure training environments and artifacts             |
| Testing           | Conduct security and adversarial testing               |
| Deployment        | Enforce IAM, API security, and infrastructure controls |
| Operation         | Monitor model and system behavior                      |
| Change management | Review model, data, and configuration changes          |
| Retirement        | Revoke access and securely dispose of assets           |

#### 5.7 Secure AI Supply Chain

Secure AI supply chain refers to the protection and verification of external components and dependencies used throughout the AI lifecycle.

Controls include:

- Supplier assessments.
- Model provenance verification.
- Dataset source validation.
- Software Bill of Materials (SBOM).
- Dependency scanning.
- Model artifact integrity.
- Approved repositories.
- Secure build pipelines.
- Version control.
- Vulnerability management.

#### 5.8 Continuous Monitoring

Continuous AI security monitoring refers to the ongoing observation of AI systems for security threats, abnormal behavior, unauthorized access, and operational weaknesses.

Monitoring should cover:

- Authentication activity.
- Model endpoint usage.
- API requests.
- Data access.
- Model deployment events.
- Model artifact changes.
- Inference anomalies.
- Resource consumption.
- Agent execution.
- Security alerts.

Monitoring should be integrated into the organization's existing SOC, SIEM, and incident response capabilities.

### 6. AI Security Governance and GRC Foundations

AI cybersecurity must be governed through an established organizational framework with clear responsibilities, risk ownership, security requirements, and assurance mechanisms.

#### 6.1 AI Security Governance

AI security governance refers to the organizational structures, policies, roles, responsibilities, and oversight mechanisms used to manage cybersecurity risks affecting AI systems.

It should establish:

- AI security policies.
- Security ownership.
- AI asset inventories.
- Risk assessment requirements.
- Security architecture standards.
- Data protection requirements.
- Secure development standards.
- Third-party security requirements.
- Monitoring responsibilities.
- Incident response procedures.
- Audit and assurance requirements.

#### 6.2 AI Security Risk Assessment

An AI security risk assessment identifies and evaluates threats, vulnerabilities, likelihood, and potential impacts affecting AI systems.

The assessment should consider:

- AI assets.
- Business criticality.
- Data sensitivity.
- Threat actors.
- Attack vectors.
- Vulnerabilities.
- Existing security controls.
- Inherent risk.
- Residual risk.
- Risk treatment.

Example:

An AI model used to detect suspicious financial transactions may have significant integrity risk if attackers can manipulate its training dataset or inference inputs.

#### 6.3 AI Security Risk Register

An AI security risk register documents identified security risks, their potential impact, existing controls, remediation activities, and residual exposure.

Typical fields include:

| Field             | Description                                       |
| ----------------- | ------------------------------------------------- |
| Risk ID           | Unique risk identifier                            |
| AI asset          | Affected model, dataset, platform, or application |
| Threat            | Potential attack or security event                |
| Vulnerability     | Weakness enabling the threat                      |
| Risk scenario     | Cause, event, and consequence                     |
| Likelihood        | Estimated probability                             |
| Impact            | Potential business consequence                    |
| Inherent risk     | Risk before controls                              |
| Existing controls | Current safeguards                                |
| Residual risk     | Remaining exposure                                |
| Risk owner        | Accountable person or function                    |
| Treatment         | Mitigate, avoid, transfer, or accept              |
| Evidence          | Supporting assessment and control documentation   |

#### 6.4 AI Security Control Framework

An AI security control framework is a structured collection of security requirements designed to address risks affecting AI systems.

A practical framework may contain:

| Control Domain          | Security Objective                                         |
| ----------------------- | ---------------------------------------------------------- |
| Governance              | Establish accountability and security oversight            |
| Asset Management        | Maintain AI inventory and ownership                        |
| Data Security           | Protect AI datasets and information                        |
| Model Security          | Protect model artifacts and behavior                       |
| Identity and Access     | Restrict access to AI assets                               |
| Infrastructure Security | Secure AI hosting and execution                            |
| Application Security    | Protect AI interfaces and integrations                     |
| AI-Specific Security    | Address poisoning, evasion, extraction, and prompt attacks |
| Supply Chain Security   | Manage third-party AI dependencies                         |
| Monitoring              | Detect unauthorized or abnormal behavior                   |
| Incident Response       | Contain and recover from AI security incidents             |
| Assurance               | Verify control effectiveness                               |

#### 6.5 AI Security Control Effectiveness

Control effectiveness evaluates whether security controls are appropriately designed, implemented, and operating as intended.

For example, an organization may have a policy requiring all production models to be stored in an approved repository.

A control effectiveness assessment should verify:

- Whether the repository is approved.
- Whether access is restricted.
- Whether model artifacts are integrity-protected.
- Whether unauthorized changes are detected.
- Whether access reviews are performed.
- Whether exceptions are documented.

A policy statement alone is not evidence that a control is operating effectively.

### 8. Key Conceptual Distinctions

| Concept A            | Concept B              | Key Difference                                                                     |
| -------------------- | ---------------------- | ---------------------------------------------------------------------------------- |
| AI security          | AI safety              | Protection against compromise versus prevention of harmful behavior                |
| Cybersecurity for AI | AI for cybersecurity   | Protecting AI systems versus using AI to improve cybersecurity                     |
| AI model security    | AI system security     | Protecting the model versus protecting the complete system                         |
| Confidentiality      | Integrity              | Preventing unauthorized disclosure versus preventing unauthorized modification     |
| Integrity            | Availability           | Protecting correctness versus ensuring accessibility                               |
| Threat               | Vulnerability          | Potential source of harm versus weakness that can be exploited                     |
| Attack vector        | Attack path            | Entry method versus sequence of exploitation steps                                 |
| Data poisoning       | Adversarial evasion    | Manipulating training data versus manipulating inputs during operation             |
| Model theft          | Model inversion        | Extracting a model versus inferring information about its training data            |
| Security by Design   | Secure by Default      | Integrating security during design versus starting with restrictive configurations |
| Model monitoring     | AI security monitoring | Observing model performance versus detecting security threats across the AI system |
| AI risk assessment   | AI security testing    | Evaluating risk versus testing whether security controls withstand attacks         |

### 9. Summary

AI cybersecurity protects AI systems and their supporting environments against unauthorized access, manipulation, exploitation, and disruption.

The traditional CIA Triad remains fundamental, but AI security also requires attention to authenticity, accountability, traceability, provenance, robustness, and resilience.

The AI attack surface extends across datasets, training pipelines, model artifacts, inference endpoints, applications, APIs, cloud infrastructure, agents, and third-party components.

Effective AI security requires security-by-design principles, least privilege, Zero Trust, defense in depth, secure AI development, supply chain protection, and continuous monitoring.

From a GRC perspective, AI security must be supported by formal governance, documented risk assessments, control ownership, evidence collection, and periodic assurance.

### Core Principle

AI security must protect the entire AI ecosystem, not merely the model. Every dataset, model artifact, API, infrastructure component, integration, and operational process must have defined security requirements, accountable ownership, and verifiable controls.

## Part 2 — AI Data Security, Model Security, Adversarial Attacks, and Machine Learning Security Mechanisms

### 10. AI Data Security and Protection

Data is one of the most valuable assets in an AI environment. AI systems depend on data for training, validation, testing, retrieval, inference, and continuous evaluation.

Compromised, manipulated, or improperly protected data can affect model behavior, expose confidential information, and undermine the reliability of AI-driven decisions.

AI data security focuses on protecting information throughout its lifecycle, from acquisition and ingestion to storage, processing, training, inference, retention, and deletion.

For cybersecurity GRC professionals, the central question is:

How can an organization ensure that data used by AI systems is trustworthy, protected, authorized, and resistant to malicious manipulation?

#### 10.1 AI Data Security

AI data security refers to the policies, processes, and technical controls used to protect data processed, stored, transmitted, or generated by AI systems against unauthorized access, modification, disclosure, destruction, and misuse.

It applies to:

- Training datasets.
- Validation and testing datasets.
- Inference inputs.
- Customer prompts.
- Enterprise knowledge repositories.
- Feature datasets.
- Embeddings.
- Vector databases.
- Agent memory.
- Model outputs.
- AI-generated synthetic data.

Example:

A telecom operator uses customer records and network telemetry to train a machine learning model for fraud detection.

The organization must ensure that the datasets are appropriately classified, access-controlled, validated, protected against manipulation, and processed according to applicable privacy requirements.

#### 10.2 Data Classification

Data classification is the process of categorizing information according to its sensitivity, confidentiality, business value, and regulatory requirements.

A practical enterprise classification model may include:

| Classification | Description                                                | AI Data Example                                    |
| -------------- | ---------------------------------------------------------- | -------------------------------------------------- |
| Public         | Approved for unrestricted public distribution              | Public product documentation                       |
| Internal       | Intended for authorized organizational use                 | Internal operational procedures                    |
| Confidential   | Sensitive business or customer information                 | Customer account records                           |
| Restricted     | Highly sensitive information requiring enhanced protection | Authentication secrets and sensitive security data |

AI data classification should determine:

- Who can access the data.
- Which models may process it.
- Whether external model providers may receive it.
- Whether it can be used for training.
- How it may be stored.
- How long it may be retained.
- Whether it can be included in prompts or agent memory.
- Whether additional encryption or DLP controls are required.

GRC concern:

An AI application must not automatically inherit permission to process every dataset accessible to its hosting environment.

#### 10.3 Data Provenance

Data provenance refers to the origin, history, ownership, and processing lineage of data.

It helps organizations establish:

- Where data originated.
- Who supplied it.
- Whether its source is trusted.
- How it was transformed.
- Whether it was modified.
- Which datasets were used for training.
- Whether appropriate usage rights exist.

Example:

A machine learning model is trained using network telemetry collected from several telecom regions.

Data provenance records should identify the source systems, collection periods, transformation activities, and responsible data owners.

GRC concern:

Poor data provenance makes it difficult to investigate poisoning, validate training datasets, establish lawful data usage, and demonstrate accountability.

#### 10.4 Data Lineage

Data lineage describes how data moves through systems and how it is transformed, combined, processed, and consumed.

Example:

```
SOURCE SYSTEMS
      |
      v
DATA INGESTION
      |
      v
DATA VALIDATION
      |
      v
DATA CLEANING
      |
      v
FEATURE ENGINEERING
      |
      v
TRAINING DATASET
      |
      v
MODEL TRAINING
      |
      v
MODEL DEPLOYMENT
```

Data lineage is important for identifying where compromised or inaccurate information entered the AI pipeline.

Distinction:

- Data provenance focuses on the origin and history of data.
- Data lineage focuses on the flow and transformation of data across systems.

They are complementary capabilities.

#### 10.5 Data Integrity

Data integrity ensures that information remains accurate, complete, consistent, and protected against unauthorized modification.

AI data integrity controls may include:

- Input validation.
- Schema validation.
- Data quality checks.
- Cryptographic hashes.
- Digital signatures.
- Access controls.
- Version control.
- Dataset validation.
- Controlled transformation pipelines.

Example:

A financial institution verifies the integrity of a training dataset before using it to retrain a fraud detection model.

#### 10.6 Data Poisoning

Data poisoning is an attack in which an attacker manipulates training or learning data to influence the behavior of an AI model.

The objective may be to degrade model performance, introduce incorrect associations, or cause specific predictions under particular conditions.

Example:

An attacker injects manipulated transaction records into a fraud detection training dataset.

The model learns incorrect patterns and may subsequently classify certain fraudulent transactions as legitimate.

Data poisoning may affect:

- Training datasets.
- Labels.
- Features.
- Data collection mechanisms.
- Online learning pipelines.
- Feedback datasets.

GRC controls:

- Trusted data sources.
- Data provenance.
- Dataset integrity verification.
- Access restrictions.
- Data quality monitoring.
- Training data validation.
- Controlled dataset approval.
- Anomaly detection.

#### 10.7 Label Poisoning

Label poisoning is a type of data poisoning in which an attacker manipulates the labels associated with training examples.

Example:

A cybersecurity model uses labeled network traffic to distinguish malicious activity from legitimate traffic.

An attacker changes labels associated with malicious traffic so that the model learns to classify those patterns as benign.

The model's classification performance may deteriorate or become systematically biased.

GRC concern:

Organizations should establish controls over labeling processes, including access restrictions, reviewer validation, dataset versioning, and quality assurance.

#### 10.8 Feature Poisoning

Feature poisoning involves manipulating the feature values used by a machine learning model during training or learning.

Example:

An attacker modifies transaction attributes such as transaction frequency, device characteristics, or location-related features to influence the model's fraud detection behavior.

Feature poisoning can be difficult to detect because the manipulated data may still satisfy basic structural validation.

#### 10.9 Data Leakage

Data leakage occurs when sensitive or unauthorized information is exposed through an AI system or its supporting processes.

Potential leakage points include:

- Training datasets.
- Model outputs.
- Prompts.
- Inference logs.
- Embeddings.
- Vector databases.
- Agent memory.
- External integrations.
- Development environments.

Data leakage can occur even when the underlying model has not been directly compromised.

#### 10.10 Data Exfiltration

Data exfiltration is the unauthorized transfer of information from an organization's environment to an external or unauthorized destination.

In AI environments, exfiltration may occur through:

- Inference APIs.
- Prompt-based interactions.
- Agent tools.
- External model providers.
- Compromised connectors.
- Unauthorized file operations.
- Malicious plugins.
- Insecure application integrations.

GRC controls:

- DLP.
- Egress filtering.
- API monitoring.
- Data minimization.
- Approved destination controls.
- Network segmentation.
- Access logging.
- Encryption.

#### 10.11 Data Leakage vs. Data Exfiltration

| Concept           | Meaning                                                    | Example                                                 |
| ----------------- | ---------------------------------------------------------- | ------------------------------------------------------- |
| Data leakage      | Unauthorized exposure or disclosure of information         | An LLM reveals confidential information in its response |
| Data exfiltration | Unauthorized transfer of information out of an environment | An agent sends customer records to an external endpoint |

Data leakage describes an exposure outcome, while exfiltration describes an unauthorized transfer mechanism or event.

#### 10.12 Data Minimization

Data minimization is the principle of collecting and processing only the information necessary for a defined purpose.

Example:

A customer-service agent needs the customer's service identifier and current service status to troubleshoot connectivity.

It does not necessarily need the customer's full payment history or unrelated personal information.

Data minimization reduces:

- Exposure of personal data.
- Impact of data breaches.
- Unnecessary model context.
- Unauthorized information disclosure.
- Regulatory compliance risks.

#### 10.13 Data Anonymization

Data anonymization is the process of transforming personal data so that individuals are no longer identifiable, taking into account the means reasonably likely to be used for identification.

Example:

A telecom operator prepares a dataset for analytical use by removing or transforming identifying information and assessing whether individuals can still be reidentified.

Anonymization is more demanding than simply removing names or account numbers.

#### 10.14 Data Pseudonymization

Data pseudonymization is the processing of personal data so that it can no longer be attributed to a specific individual without additional information, which is kept separately and protected.

Example:

Customer identifiers are replaced with randomly generated reference codes, while the mapping table is stored separately with restricted access.

Important distinction:

Pseudonymized data remains personal data under the GDPR when reidentification remains possible using additional information.

#### 10.15 Synthetic Data

Synthetic data is artificially generated data designed to reproduce selected characteristics or statistical patterns of real-world data.

It may be used for:

- Model development.
- Testing.
- Validation.
- Simulation.
- Data augmentation.
- Privacy risk reduction.

However, synthetic data is not automatically anonymous or safe.

If it closely reproduces identifiable records or memorized training examples, privacy risks may remain.

#### 10.16 Differential Privacy

Differential privacy is a mathematical framework that limits how much the output of a data analysis can reveal about the participation of any individual in the underlying dataset.

It commonly introduces calibrated randomness to reduce the influence of individual records.

Example:

An organization analyzes customer behavior while applying differential privacy techniques to reduce the ability to infer whether a particular customer's record was included in the dataset.

GRC concern:

Differential privacy requires careful parameter selection and privacy-budget management. Merely claiming that a system uses differential privacy does not establish that the privacy protection is sufficient.

#### 10.17 AI Data Security Control Matrix

| Control Area              | Security Objective              | Example Control                       |
| ------------------------- | ------------------------------- | ------------------------------------- |
| Data classification       | Identify sensitivity            | Enterprise data classification        |
| Data provenance           | Establish source reliability    | Dataset source records                |
| Data lineage              | Track transformations           | Data lineage documentation            |
| Data integrity            | Prevent unauthorized changes    | Hashing and validation                |
| Data poisoning prevention | Protect training quality        | Dataset validation and access control |
| Data leakage prevention   | Prevent unauthorized disclosure | DLP and access controls               |
| Data minimization         | Reduce unnecessary exposure     | Purpose-based data selection          |
| Privacy protection        | Protect personal information    | Anonymization and pseudonymization    |
| Data retention            | Limit unnecessary storage       | Retention and deletion policies       |
| Data access               | Restrict data availability      | RBAC and ABAC                         |

### 11. Machine Learning Model Security

Machine learning models are valuable organizational assets. They may contain proprietary logic, learned patterns, sensitive information, and business-critical functionality.

Model security focuses on protecting model artifacts, parameters, configurations, training processes, deployment mechanisms, and inference behavior.

#### 11.1 Model Security

Model security refers to the controls used to protect AI models against unauthorized access, theft, modification, manipulation, exploitation, and compromise.

It covers:

- Model architecture.
- Model weights.
- Model parameters.
- Model checkpoints.
- Model artifacts.
- Model configurations.
- Model repositories.
- Training environments.
- Model deployment.
- Inference endpoints.

#### 11.2 Model Weights

Model weights are numerical parameters learned during model training that determine how a model processes inputs and produces outputs.

They represent a significant portion of a trained model's learned behavior.

For many models, unauthorized access to weights can expose valuable intellectual property or enable the attacker to reproduce and misuse the model.

#### 11.3 Model Theft

Model theft refers to the unauthorized acquisition or reproduction of a model's proprietary parameters, architecture, or behavior.

It may occur through:

- Unauthorized repository access.
- Compromised development environments.
- Stolen model artifacts.
- Insecure storage.
- Inference-based extraction.
- Insider threats.

Example:

A competitor obtains a proprietary fraud detection model through unauthorized access to a cloud model repository.

GRC controls:

- Restricted model repositories.
- IAM.
- Encryption.
- Artifact integrity verification.
- Secure deployment pipelines.
- Monitoring.
- Intellectual property protection.

#### 11.4 Model Extraction

Model extraction is an attack in which an adversary attempts to reproduce a target model by querying its accessible inference interface and using the returned outputs to train a substitute model.

Example:

An attacker repeatedly queries a commercial classification API using carefully selected inputs and collects its predictions.

The attacker uses the resulting input-output pairs to train a substitute model that approximates the original model's behavior.

Model extraction may result in:

- Intellectual property loss.
- Competitive disadvantage.
- Unauthorized model replication.
- Increased exposure of proprietary functionality.

GRC controls:

- Authentication.
- Query rate limits.
- Usage monitoring.
- Abuse detection.
- Access restrictions.
- API usage controls.

#### 11.5 Model Inversion

Model inversion is an attack that attempts to infer sensitive characteristics or information about the model's training data by analyzing model outputs or behavior.

Example:

An attacker queries a model trained using sensitive customer information and attempts to infer characteristics of individual training records.

Model inversion does not necessarily reconstruct the entire original dataset. Its objective is to infer information about the data from model behavior.

#### 11.6 Membership Inference

Membership inference is an attack that attempts to determine whether a particular data record was included in a model's training dataset.

Example:

An attacker attempts to determine whether a specific customer's medical record was used to train a healthcare prediction model.

This can expose sensitive information about individuals even if the model never directly returns the original record.

GRC concern:

Membership inference should be considered in privacy risk assessments, particularly when models are trained on sensitive or regulated data.

#### 11.7 Model Backdoor

A model backdoor is a hidden mechanism that causes a model to behave in a specific unintended way when a particular trigger or condition is present.

Example:

A compromised image classification model correctly classifies normal images but misclassifies images containing a particular hidden pattern.

Backdoors may be introduced through poisoned training data, compromised model artifacts, or malicious modifications.

#### 11.8 Model Poisoning

Model poisoning refers to manipulation of a model or its learning process to influence the model's behavior.

The attack may target:

- Training data.
- Model parameters.
- Model updates.
- Distributed learning participants.
- Model artifacts.

The terminology can overlap with data poisoning, but the distinction is useful:

- Data poisoning manipulates the data used for learning.
- Model poisoning can manipulate the model or learning process itself.

#### 11.9 Model Artifact Integrity

Model artifact integrity ensures that model files, weights, checkpoints, and associated deployment packages have not been modified without authorization.

Controls may include:

- Cryptographic hashing.
- Digital signatures.
- Approved artifact repositories.
- Version control.
- Access restrictions.
- Build provenance.
- Integrity verification before deployment.

#### 11.10 Model Registry Security

A model registry is a centralized repository used to store, organize, version, and manage machine learning models.

Security requirements should include:

- Authentication.
- Role-based access.
- Model ownership.
- Version control.
- Approval workflows.
- Artifact integrity.
- Deployment history.
- Audit logging.

An attacker who compromises a model registry may be able to replace an approved model with a malicious or unvalidated artifact.

#### 11.11 Model Security Control Matrix

| Control Area     | Security Objective               | Example Control                            |
| ---------------- | -------------------------------- | ------------------------------------------ |
| Model repository | Protect model artifacts          | Restricted IAM                             |
| Model weights    | Prevent unauthorized access      | Encryption and access restrictions         |
| Model versioning | Maintain traceability            | Controlled version management              |
| Model integrity  | Detect unauthorized modification | Hashes and digital signatures              |
| Model deployment | Prevent unapproved releases      | Deployment approval                        |
| Model extraction | Limit unauthorized querying      | Rate limits and anomaly detection          |
| Model privacy    | Reduce information leakage       | Privacy-preserving techniques              |
| Model backdoors  | Detect malicious behavior        | Dataset validation and adversarial testing |

### 12. Adversarial Machine Learning

Adversarial machine learning examines attacks and defensive techniques involving deliberate manipulation of data or inputs to influence machine learning behavior.

These attacks can target training, inference, model evaluation, and learning processes.

Understanding adversarial machine learning is essential for organizations using AI in fraud detection, cybersecurity, biometric authentication, industrial monitoring, and other security-sensitive applications.

#### 12.1 Adversarial Machine Learning

Adversarial machine learning is the study of how attackers exploit or manipulate machine learning systems and how those systems can be designed to resist such attacks.

It includes:

- Adversarial examples.
- Evasion attacks.
- Poisoning attacks.
- Backdoor attacks.
- Model extraction.
- Model inversion.
- Membership inference.
- Adversarial training.
- Robustness evaluation.

#### 12.2 Adversarial Example

An adversarial example is an input deliberately modified to cause a machine learning model to produce an incorrect or unintended output.

The modification may be small or difficult for a human to notice.

Example:

An attacker slightly modifies an image so that an image classification model incorrectly identifies a stop sign as another object.

The modified image may appear almost identical to the original to a human observer.

Adversarial examples demonstrate that high conventional model accuracy does not necessarily mean strong resistance to malicious inputs.

#### 12.3 Evasion Attack

An evasion attack occurs when an attacker manipulates inputs at inference time to avoid detection or cause an incorrect prediction.

Example:

An attacker modifies network traffic characteristics so that malicious traffic is classified as normal by a network anomaly detection model.

The attack does not necessarily require modification of the model's training data or parameters.

#### 12.4 Targeted Evasion

Targeted evasion attempts to manipulate a model into producing a specific incorrect output.

Example:

An attacker modifies an input to make a fraud detection model classify a fraudulent transaction as legitimate.

#### 12.5 Untargeted Evasion

Untargeted evasion attempts to cause an incorrect prediction without requiring a particular alternative classification.

Example:

An attacker modifies an input so that a malware classification model produces any incorrect classification.

#### 12.6 White-Box Attack

A white-box attack assumes the attacker has access to internal information about the model.

This may include:

- Model architecture.
- Parameters.
- Weights.
- Gradients.
- Internal representations.

Such knowledge may help the attacker construct more effective adversarial inputs.

#### 12.7 Black-Box Attack

A black-box attack assumes the attacker cannot directly inspect the model's internal parameters or architecture but can interact with the model through an accessible interface.

Example:

An attacker submits queries to a fraud detection API and observes the returned classifications.

The attacker uses these observations to identify weaknesses or approximate the model.

#### 12.8 Gray-Box Attack

A gray-box attack assumes the attacker has partial information about the model or its environment.

For example, the attacker may know the model type and input format but not its exact parameters.

#### 12.9 Transferability

Transferability refers to the phenomenon in which adversarial inputs developed against one model may also cause incorrect behavior in another model.

This can enable attackers to develop adversarial examples using a substitute model and then test them against a target model.

#### 12.10 Adversarial Robustness

Adversarial robustness refers to a model's ability to maintain acceptable behavior when exposed to intentionally manipulated inputs.

Robustness evaluation should consider:

- Attack types.
- Perturbation limits.
- Model architecture.
- Input characteristics.
- Operational environment.
- Acceptable performance degradation.

#### 12.11 Adversarial Training

Adversarial training is a training approach that incorporates adversarially generated examples into the training process to improve model robustness against selected attacks.

It may improve resistance to specific attack classes, but it does not guarantee immunity to all adversarial attacks.

#### 12.12 Adversarial Attack Comparison

| Attack               | Target                    | Timing                                 | Primary Objective                          |
| -------------------- | ------------------------- | -------------------------------------- | ------------------------------------------ |
| Data poisoning       | Training data             | Training                               | Manipulate learned behavior                |
| Label poisoning      | Training labels           | Training                               | Corrupt classification learning            |
| Model poisoning      | Model or learning process | Training / update                      | Compromise model behavior                  |
| Backdoor attack      | Model behavior            | Usually training or model introduction | Trigger hidden behavior                    |
| Evasion attack       | Model input               | Inference                              | Avoid detection or cause misclassification |
| Targeted evasion     | Model input               | Inference                              | Force a specific incorrect prediction      |
| Model extraction     | Inference interface       | Inference                              | Reproduce model behavior                   |
| Model inversion      | Model outputs             | Inference                              | Infer sensitive training information       |
| Membership inference | Model outputs             | Inference                              | Determine training-set membership          |

#### 12.13 AI Adversarial Testing and GRC Assessment

An enterprise security assessment should establish:

1. Which models are exposed to external inputs?
2. Which inputs could be deliberately manipulated?
3. Has adversarial testing been performed?
4. Are training datasets protected against poisoning?
5. Are model artifacts integrity-protected?
6. Are model endpoints monitored for abnormal queries?
7. Are model robustness requirements documented?
8. Are attack scenarios included in the AI risk register?
9. Are remediation actions tracked?
10. Has residual risk been formally accepted?

### 14. Summary

AI data security protects the information used and generated by AI systems throughout its lifecycle. Data classification, provenance, lineage, integrity, minimization, privacy protection, and retention are essential components of a secure AI environment.

For enterprise GRC, data and model protection must be supported by documented ownership, secure development, controlled access, artifact integrity, adversarial testing, monitoring, and evidence-based assurance.

### Core Principle

An AI model is only as trustworthy as the integrity of its data, the security of its development and deployment processes, and its resilience against deliberate manipulation. Protecting AI requires securing both the information it learns from and the behavior it produces.

## Part 3 — AI Application Security, Infrastructure Security, Supply Chain Security, and Defensive Controls

### 15. AI Application Security

AI application security focuses on protecting the software applications that integrate AI models, data sources, APIs, tools, and business processes.

An AI model may be technically secure while the application using it remains vulnerable. For example, an organization may deploy a well-protected LLM but expose sensitive customer information through an insecure application interface or improperly authorized backend integration.

The security boundary is therefore larger than the model itself.

#### 15.1 AI Application Security

AI application security refers to the policies, architecture, and technical controls used to protect applications that incorporate AI capabilities against unauthorized access, exploitation, manipulation, and misuse.

It covers:

- User interfaces and application logic.
- AI model integrations.
- APIs and gateways.
- Prompt construction and processing.
- Data retrieval mechanisms.
- External tools and plugins.
- Authentication and authorization.
- Input and output handling.
- Application logging and monitoring.

Example:

A telecom operator integrates an LLM into its customer-service platform. The application retrieves customer account information, generates responses, and allows authorized users to initiate service requests.

Security must protect both the LLM interaction and the application functions that access customer records or execute business operations.

#### 15.2 AI Application Attack Surface

The AI application attack surface is the collection of application components, interfaces, integrations, and execution paths that an attacker could exploit.

Typical attack surfaces include:

| Component              | Potential Security Exposure                    |
| ---------------------- | ---------------------------------------------- |
| Web interface          | Authentication bypass, session compromise      |
| Prompt interface       | Prompt injection and malicious input           |
| Model API              | Unauthorized queries and abuse                 |
| Retrieval system       | Unauthorized document access                   |
| Vector database        | Data exposure and access-control failures      |
| Tool integrations      | Unauthorized actions                           |
| Application backend    | Business logic vulnerabilities                 |
| Logging infrastructure | Sensitive information disclosure               |
| External plugins       | Third-party compromise                         |
| Administrative console | Privilege escalation and configuration changes |

GRC concern: An AI security assessment must identify the complete application attack surface rather than limiting its scope to model vulnerabilities.

#### 15.3 Input Validation

Input validation is the process of checking whether data supplied to an application meets defined requirements before it is processed.

In AI applications, validation may include:

- Input format validation.
- File type validation.
- File size restrictions.
- Character and token limits.
- Schema validation.
- Malicious content detection.
- Content-type restrictions.
- Prompt and instruction boundary handling.

Input validation helps reduce application-layer vulnerabilities, but it does not reliably eliminate semantic attacks such as prompt injection.

#### 15.4 Output Validation

Output validation is the process of checking AI-generated content before it is displayed, stored, or used by downstream systems.

Controls may include:

- Schema validation.
- Type validation.
- Content filtering.
- Sensitive information detection.
- Business rule validation.
- Authorization checks.
- Human approval.
- Safe rendering.

Example:

An LLM generates a JSON response containing a proposed customer account modification. The application validates the schema, checks the user's authorization, and requires approval before executing the transaction.

Important distinction: A syntactically valid output is not necessarily accurate, safe, authorized, or appropriate for execution.

#### 15.5 Insecure Output Handling

Insecure output handling occurs when an application trusts or processes AI-generated content without appropriate validation, sanitization, or security enforcement.

Potential consequences include:

- Cross-site scripting (XSS).
- SQL injection in downstream integrations.
- Command injection.
- Unsafe file operations.
- Unauthorized workflow execution.
- Incorrect business transactions.

Example:

An AI assistant generates a string containing malicious HTML. The application renders the output directly in a browser without sanitization, potentially enabling cross-site scripting.

The vulnerability exists in the application handling of the output, not necessarily in the model itself.

#### 15.6 Prompt Injection

Prompt injection is an attack in which malicious instructions are introduced into the context processed by an AI model to influence its behavior.

Prompt injection may target:

- System instructions.
- Application instructions.
- Retrieved documents.
- User-provided content.
- Tool outputs.
- External websites.
- Agent memory.

Two important forms are:

| Type                      | Description                                                                    | Example                                                                                        |
| ------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| Direct prompt injection   | Malicious instructions are submitted directly by a user                        | A user instructs an assistant to disregard its intended task and reveal restricted information |
| Indirect prompt injection | Malicious instructions are embedded in external content processed by the model | A retrieved document contains instructions designed to influence an AI assistant               |

Prompt injection is particularly relevant to RAG applications and AI agents because they process information from multiple sources.

GRC concern: Prompt injection testing must include the complete application context, including retrieved content and connected tools.

#### 15.7 Jailbreaking

Jailbreaking refers to attempts to bypass an AI system's intended behavioral restrictions or safety mechanisms.

Example:

A user attempts to manipulate a chatbot into generating content that its policies are intended to prohibit.

Jailbreaking and prompt injection are related but not identical:

- Prompt injection introduces malicious instructions into model context.
- Jailbreaking attempts to circumvent the model's intended restrictions.

A jailbreak may use prompt injection techniques, but the terms should not be treated as interchangeable.

#### 15.8 System Prompt Leakage

System prompt leakage occurs when an attacker causes an AI application to disclose internal instructions, configuration information, or other prompt content that was not intended for disclosure.

Example:

An attacker attempts to retrieve hidden application instructions containing internal workflow details.

A system prompt should not contain passwords, API keys, confidential credentials, or information that must be protected through access controls.

Control principle: Treat system prompts as application configuration, not as a security boundary.

#### 15.9 Excessive Agency

Excessive agency occurs when an AI application or agent has more authority, permissions, or operational capability than necessary to perform its intended tasks.

Example:

A customer-service agent needs read-only access to account information but is also granted unrestricted permissions to modify customer records, issue refunds, and terminate services.

Potential consequences include:

- Unauthorized transactions.
- Data modification.
- Privilege misuse.
- Financial loss.
- Operational disruption.

Controls include least privilege, narrowly scoped tool permissions, transaction limits, approval gates, and runtime policy enforcement.

#### 15.10 Business Logic Abuse

Business logic abuse occurs when an attacker exploits the way an application implements business rules rather than exploiting a conventional technical vulnerability.

AI may increase this risk when model-generated recommendations or automated actions are allowed to bypass normal business controls.

Example:

An AI-powered refund assistant recommends a refund. The application executes the refund without validating the transaction history, eligibility conditions, or approval requirements.

Controls must ensure that business rules are enforced independently of model-generated recommendations.

| Input validation   | Restrict malicious or invalid input  | Validation and content inspection        |
| Output validation  | Prevent unsafe downstream processing | Schema and content validation            |
| Prompt security    | Reduce instruction manipulation      | Prompt isolation and adversarial testing |
| Authentication     | Verify user identity                 | MFA and enterprise SSO                   |

| Business logic     | Enforce business rules               | Backend policy enforcement               |
| Data retrieval     | Prevent unauthorized access          | Document-level access controls           |
| Session management | Protect user sessions                | Secure session handling                  |
| Monitoring         | Detect abuse and anomalies           | Application security logging             |

### 16. AI Infrastructure and Platform Security

AI infrastructure security protects the underlying computing, storage, networking, and platform services used to develop, train, deploy, and operate AI systems.

AI workloads can consume substantial computing resources and often rely on specialized hardware, distributed infrastructure, cloud services, and complex software dependencies.

A compromise of the infrastructure may affect multiple AI applications or models simultaneously.

#### 16.1 AI Infrastructure Security

AI infrastructure security refers to the controls used to protect the infrastructure supporting AI workloads against unauthorized access, compromise, disruption, and misuse.

It includes:

- Cloud infrastructure.
- On-premises infrastructure.
- GPU computing environments.
- Container platforms.
- Kubernetes clusters.
- Storage systems.
- Network infrastructure.
- AI development platforms.
- Model-serving platforms.
- Data processing environments.

#### 16.2 AI Compute Security

AI compute security protects the computing resources used to train, fine-tune, and run AI models.

These resources may include:

- CPUs.
- GPUs.
- TPUs and other accelerators.
- Distributed computing clusters.
- High-performance computing environments.

Security controls should address access restrictions, workload isolation, resource allocation, monitoring, and protection against unauthorized workloads.

#### 16.3 GPU Security

GPU security concerns the protection of graphics processing units and their associated workloads, memory, drivers, and computing environments.

Potential risks include:

- Vulnerable GPU drivers.
- Unauthorized workload execution.
- Insecure GPU sharing.
- Memory isolation weaknesses.
- Resource exhaustion.
- Compromised GPU software components.

Example:

A shared GPU cluster hosts several AI development projects. Inadequate workload isolation may expose one project's resources or data to another workload.

#### 16.4 Container Security

Container security protects container images, runtime environments, configurations, and associated workloads.

AI applications commonly use containers to package model-serving services, inference engines, data processing components, and supporting dependencies.

Controls include:

- Trusted base images.
- Image scanning.
- Signed container images.
- Vulnerability management.
- Runtime protection.
- Restricted container privileges.
- Secrets management.
- Network policies.

#### 16.5 Kubernetes Security

Kubernetes security protects container orchestration environments used to deploy and manage AI workloads.

Relevant security controls include:

- Role-Based Access Control (RBAC).
- Network policies.
- Pod security controls.
- Namespace isolation.
- Secrets protection.
- Admission controls.
- Image provenance.
- Audit logging.
- Runtime monitoring.

Example:

An organization deploys several LLM inference services in a Kubernetes cluster. Network policies should prevent an inference workload from accessing unrelated internal systems unless explicitly authorized.

#### 16.6 Workload Isolation

Workload isolation is the separation of computing processes, applications, users, or tenants to reduce unauthorized interaction and limit the impact of compromise.

AI environments may require isolation between:

- Development and production.
- Training and inference.
- Different business units.
- Different customers.
- Different model workloads.
- Different agents and execution environments.

Isolation mechanisms may include virtual machines, containers, namespaces, dedicated clusters, network segmentation, and hardware-backed isolation.

#### 16.7 Sandbox

A sandbox is an isolated execution environment designed to restrict the activities of potentially untrusted code, applications, or processes.

AI agents may require sandboxing when they execute:

- Code.
- Scripts.
- File operations.
- Data transformations.
- External commands.
- Experimental workloads.

Example:

An AI development assistant is permitted to execute generated code only inside an isolated container with restricted filesystem and network access.

A sandbox reduces risk but does not automatically guarantee complete containment.

#### 16.8 Secrets Management

Secrets management is the controlled creation, storage, distribution, rotation, and revocation of sensitive credentials and authentication material.

AI environments may use:

- API keys.
- Database credentials.
- Cloud service credentials.
- Service account tokens.
- Private keys.
- Certificates.
- Model repository credentials.

Secrets must not be embedded in:

- Prompts.
- Source code.
- Model weights.
- Configuration files without appropriate protection.
- Logs.
- Training datasets.
- Public repositories.

#### 16.9 AI Workload Identity

AI workload identity is the identity assigned to an AI application, model-serving process, agent, or workload so that it can authenticate to other services.

Example:

An AI inference service uses a managed workload identity to access an approved document repository.

The identity should have only the permissions required for the intended operation.

Important distinction:

- Human identity identifies a person.
- Workload identity identifies an application, service, or machine workload.
- Agent identity identifies an AI agent or agent instance within an authorization and accountability model.

These identities may interact, but they should not be treated as equivalent.

#### 16.10 Network Segmentation

Network segmentation divides an infrastructure environment into separate network zones to restrict communication and limit the spread of compromise.

An AI architecture may use separate zones for:

- Data ingestion.
- Model training.
- Model registry.
- Inference services.
- Administrative management.
- External integrations.
- Monitoring and logging.

Example:

A model-serving environment should not automatically have unrestricted access to the organization's internal database network.

#### 16.11 Infrastructure as Code Security

Infrastructure as Code (IaC) security concerns the secure development, review, deployment, and management of infrastructure configurations defined through machine-readable files.

AI infrastructure may be deployed through templates and automation tools that configure:

- Cloud services.
- Storage.
- Networks.
- Compute resources.
- Kubernetes clusters.
- Access policies.
- Model-serving environments.

Security controls should include configuration scanning, code review, policy enforcement, change approval, and drift detection.

#### 17.3 Model Supply Chain

The model supply chain includes the sources, processes, artifacts, and services involved in obtaining, training, fine-tuning, distributing, and deploying AI models.

#### 17.7 Software Bill of Materials (SBOM)

A Software Bill of Materials (SBOM) is a formal inventory of software components and dependencies included in a software product.

It helps organizations identify:

- Software components.
- Dependency relationships.
- Component versions.
- Known vulnerabilities.
- License information.
- Supply chain exposure.

An SBOM is useful for AI applications because they may contain extensive software dependencies.

However, a traditional SBOM does not necessarily capture every AI-specific component, dataset, model weight, or model artifact.

#### 17.8 AI Bill of Materials (AI BOM)

An AI Bill of Materials (AI BOM) is an inventory concept intended to describe components and dependencies associated with an AI system.

Depending on its scope, it may document:

- Models.
- Datasets.
- Software dependencies.
- Model providers.
- Model versions.
- Training frameworks.
- Inference components.
- External services.
- Model artifacts.

The exact content and format depend on the organization's chosen methodology or specification.

Important distinction:

An AI BOM should not automatically be treated as a universally standardized document with one mandatory structure. Organizations should define its scope, required fields, ownership, and update process.

#### 17.9 Model Provenance

Model provenance refers to the documented origin, history, development process, and ownership of an AI model.

It may include:

- Original model provider.
- Base model.
- Training methodology.
- Fine-tuning history.
- Dataset sources.
- Model versions.
- Model modifications.
- Evaluation results.
- Deployment history.

Model provenance helps establish whether an AI model is authentic, traceable, and approved for use.

#### 17.10 Model Signing

Model signing is the use of cryptographic signatures to establish the authenticity and integrity of model artifacts.

It can help verify that a model was produced or approved by a trusted source and has not been modified after signing.

A signature does not establish that a model is secure or free of vulnerabilities. It establishes authenticity and integrity relative to the trusted signing process.

#### 17.11 Artifact Attestation

Artifact attestation is evidence about the origin, creation process, identity, or integrity of a software or model artifact.

It may document:

- Build environment.
- Build process.
- Source repository.
- Artifact digest.
- Signing identity.
- Approved release pipeline.

Attestation supports supply chain assurance by helping organizations verify how an artifact was produced.

#### 17.12 Supply Chain Compromise

Supply chain compromise occurs when an attacker compromises a supplier, dependency, component, or distribution process to affect downstream organizations.

Example:

A malicious modification is introduced into a third-party AI library. An enterprise incorporates the compromised dependency into its model-serving application.

Potential impacts include:

- Unauthorized access.
- Data exposure.
- Model compromise.
- Remote code execution.
- Operational disruption.
- Compromised model outputs.

### 18. AI Security Operations, Monitoring, and Incident Response

#### 18.1 AI Security Operations

AI security operations refers to the activities used to continuously monitor and protect AI systems against security incidents, misuse, unauthorized activity, and operational compromise.

- Security testing.
- Risk monitoring.

- Data ingestion events.
- Model registry activity.

- Agent actions.
- Infrastructure telemetry.

#### 20.4 GRC Interview Questions and Model Answers

Question 1: What is the difference between AI security and traditional cybersecurity?

AI security applies established cybersecurity principles to AI systems while addressing additional risks associated with data-driven learning, model behavior, training processes, inference, model artifacts, and AI-specific attack techniques.

Traditional cybersecurity remains essential, but AI systems introduce additional attack surfaces such as data poisoning, adversarial examples, model extraction, and prompt injection.

Question 2: How would you secure an AI model used by a telecom operator?

I would start by identifying the model's purpose, architecture, data sources, users, integrations, and operational dependencies.

I would then perform threat modeling and assess the security of the training data, model artifacts, inference endpoints, infrastructure, identities, and external integrations.

I would define controls covering data integrity, access management, model provenance, secure deployment, adversarial testing, monitoring, and incident response.

Finally, I would document the risks, assign control owners, track remediation, validate control effectiveness, and obtain formal residual risk acceptance.

Question 3: What is the difference between data poisoning and adversarial evasion?

Data poisoning manipulates the data used during model training or learning to influence the model's learned behavior.

Adversarial evasion manipulates inputs at inference time to cause an incorrect prediction or avoid detection.

The primary distinction is the attack stage: poisoning generally targets learning, while evasion targets model operation.

Question 4: How would you assess AI supply chain risk?

I would identify all third-party models, datasets, frameworks, libraries, cloud services, and external AI providers.

I would evaluate their provenance, security controls, vulnerabilities, licensing, data handling, subcontractors, incident notification, and contractual obligations.

I would also request relevant assurance evidence, such as SBOMs, model documentation, security assessment reports, and artifact integrity records.

Question 5: Why is model accuracy insufficient to demonstrate AI security?

Accuracy measures predictive performance against a defined evaluation dataset. It does not establish resistance to malicious manipulation, unauthorized access, model theft, data leakage, or infrastructure compromise.

A model can have high accuracy while remaining vulnerable to adversarial attacks or security weaknesses.

Question 6: What evidence would you request during an AI cybersecurity assessment?

I would request the AI architecture, data flow diagrams, threat model, asset inventory, dataset provenance, model documentation, model registry records, IAM reviews, vulnerability reports, penetration testing and red-team results, SBOMs, incident response procedures, monitoring evidence, and the AI security risk register.

I would verify not only whether the documents exist, but whether the controls are implemented and operating effectively.

Question 7: How do you determine whether an AI security control is effective?

I would establish the control objective, design requirements, accountable owner, implementation evidence, and expected operating frequency.

I would then test the control using inspection, inquiry, observation, and, where appropriate, technical testing or sample-based validation.

The result should distinguish between design effectiveness, implementation, and operating effectiveness.

### 21. Summary

AI cybersecurity extends beyond protecting the underlying model. It encompasses the complete application, infrastructure, data, software dependencies, suppliers, and operational processes that enable AI systems to function.

Application security addresses prompt handling, input and output validation, authentication, authorization, tool execution, and business logic enforcement. Infrastructure security protects computing environments, containers, orchestration platforms, secrets, workload identities, and network boundaries.

Supply chain security establishes trust in external models, datasets, software dependencies, hardware, and AI service providers. Security operations provide the monitoring, detection, investigation, response, and recovery capabilities needed to maintain protection throughout the system lifecycle.

For GRC professionals, the essential task is to translate these security domains into measurable control requirements, assigned responsibilities, documented evidence, risk treatment actions, and continuous assurance.

### Core Principle

AI cybersecurity is an ecosystem security discipline. A secure model cannot compensate for an insecure application, compromised infrastructure, untrusted supply chain, or ineffective security operations. Effective protection requires coordinated controls across every component and lifecycle stage of the AI system.
