# 21.17 — Enterprise AI Cloud Migration
## Part 1: Business Context, Cloud Architecture, Migration Strategy, and Risk Landscape

### 1. Introduction to Enterprise AI Cloud Migration

Enterprise AI cloud migration is the process of moving AI workloads, data pipelines, machine learning models, AI-enabled applications, and supporting infrastructure from on-premises environments or existing hosting platforms into cloud environments.

The migration may involve public cloud platforms, private cloud infrastructure, hybrid environments, or multicloud architectures.

Unlike a conventional infrastructure migration, an AI cloud migration must address additional considerations involving model integrity, data governance, AI workload dependencies, training and inference requirements, model lifecycle management, third-party AI services, and the security of AI-specific interfaces.

An organization might migrate an existing machine learning platform to Microsoft Azure, deploy a generative AI application using Amazon Web Services, move analytics workloads to Google Cloud, or introduce managed AI services into an existing hybrid architecture.

Each scenario creates different technical and governance requirements.

The migration decision should not be reduced to selecting a cloud provider and moving workloads. It requires a structured assessment of business objectives, architecture, data sensitivity, regulatory obligations, security controls, operational resilience, and long-term cost.

#### 1.1 What Is Enterprise AI Cloud Migration?

Enterprise AI cloud migration involves transferring or redesigning some or all of the following components:

- AI-enabled business applications.
- Machine learning training environments.
- Model inference services.
- Generative AI applications.
- Retrieval-augmented generation (RAG) platforms.
- Vector databases and embedding services.
- Data ingestion and transformation pipelines.
- Model registries and artifact repositories.
- AI development and deployment pipelines.
- AI monitoring and observability platforms.
- Identity and access management integrations.
- Security monitoring and logging infrastructure.
- Governance, compliance, and audit evidence repositories.

The organization must determine whether each component should be migrated without modification, modernized, replaced with a managed service, or retired.

For example, a company operating an on-premises predictive maintenance platform might migrate its historical data to a cloud data platform, deploy its model through a managed inference service, and retain industrial data collection systems locally.

This would create a hybrid architecture rather than a complete migration of every component.

The resulting architecture must preserve the security and operational requirements of the original system while addressing the risks introduced by the new cloud environment.

#### 1.2 AI Cloud Migration Versus Conventional Cloud Migration

AI workloads introduce risks that are not always present in conventional infrastructure migrations.

| Dimension | Conventional cloud migration | AI cloud migration |
|---|---|---|
| Primary workload | Applications, servers, databases, and infrastructure | Applications, data pipelines, models, inference services, and AI platforms |
| Data requirements | Application data, transactional records, and configuration data | Training data, evaluation data, prompts, embeddings, model outputs, and application data |
| Integrity concerns | Application and database integrity | Application, data, model artifact, and inference integrity |
| Security architecture | Identity, network security, workload protection, and data security | Conventional controls plus AI-specific input, output, model, retrieval, and agent controls where applicable |
| Access management | User, administrator, and service identities | User, administrator, service, model-serving, pipeline, and AI tool identities |
| Deployment validation | Application functionality and performance | Application functionality plus model quality, robustness, behavior, and intended-use validation |
| Monitoring | Availability, performance, logs, and infrastructure events | Infrastructure monitoring plus model performance, data quality, drift, and AI-specific security signals |
| Change management | Application and infrastructure changes | Infrastructure, application, data, model, prompt, retrieval, and AI configuration changes |
| Third-party dependencies | Hosting, software, and infrastructure suppliers | Hosting, model providers, AI APIs, managed AI services, data providers, and supporting suppliers |
| Governance | IT governance, security, compliance, and operational risk | IT governance plus AI lifecycle governance and AI-specific risk management |

These differences do not mean that every AI system requires every possible AI-specific control. The appropriate control set depends on the use case, architecture, model type, data sensitivity, and operational consequences.

A simple internal classification model may help determine the required assurance level.

For example:

- **Low complexity:** An internal analytical model with limited data sensitivity and no consequential automated actions.
- **Moderate complexity:** An enterprise RAG application accessing confidential business documents.
- **High complexity:** An AI system processing regulated personal data or supporting consequential business decisions.
- **Critical complexity:** An AI-enabled platform supporting safety-sensitive or essential operational services.

These categories are illustrative governance groupings, not universal regulatory classifications.

**Core Principle:** AI cloud migration is an architectural and governance transformation, not merely an infrastructure relocation. The migration must preserve the integrity, confidentiality, availability, and intended behavior of the AI system while establishing controls appropriate to the new environment.

### 2. Business Context and Strategic Drivers

Organizations migrate AI workloads to the cloud for several reasons, including scalability, access to managed services, faster deployment, improved collaboration, and integration with enterprise data platforms.

However, migration introduces costs and dependencies that may offset these benefits.

A credible business case must therefore compare the expected benefits with the full lifecycle cost and risk of the proposed architecture.

#### 2.1 Common Business Drivers

**Scalability**

Cloud infrastructure can provide access to additional compute, storage, and managed AI resources when workloads increase.

This is particularly relevant to model training, large-scale inference, document processing, and variable-demand generative AI applications.

Scalability does not automatically guarantee cost efficiency. Uncontrolled resource provisioning, excessive inference requests, and inefficient model selection can create significant expenditure.

**Access to managed AI services**

Cloud providers offer managed services for model hosting, machine learning operations, data engineering, AI application development, and monitoring.

These services can reduce the operational burden of managing underlying infrastructure.

However, they may introduce provider-specific dependencies, contractual restrictions, service limitations, and data-processing considerations.

**Accelerated deployment**

Cloud platforms can provide standardized environments, deployment pipelines, and reusable infrastructure components.

This may reduce the time required to provision development, testing, and production environments.

The organization must still maintain appropriate security reviews, testing, approval gates, and segregation of duties.

**Enterprise data integration**

Cloud AI platforms can integrate with enterprise data lakes, data warehouses, application platforms, identity systems, and analytics services.

Integration can improve access to business information, but it can also increase the number of pathways through which sensitive information is accessed or exposed.

**Operational resilience**

Cloud services may provide geographically distributed infrastructure, managed backups, and recovery capabilities.

Nevertheless, resilience depends on the actual architecture, service configuration, contractual commitments, regional dependencies, and tested recovery procedures.

Moving to the cloud does not automatically eliminate outages or operational risk.

**Innovation and modernization**

Cloud migration may enable an organization to introduce new capabilities such as enterprise RAG, managed foundation models, AI-assisted analytics, and automated model deployment.

These capabilities should be introduced through approved use cases and controlled lifecycle processes.

#### 2.2 Business Objectives and Measurable Outcomes

A migration program should define business objectives before selecting the target architecture.

| Business objective | Example KPI | Governance consideration |
|---|---|---|
| Reduce infrastructure management effort | Reduction in operational hours spent maintaining AI infrastructure | Confirm that responsibility has not simply shifted to a supplier without appropriate oversight |
| Improve deployment speed | Time from approved model release to production | Preserve required security and validation gates |
| Improve workload scalability | Time required to provision approved capacity | Establish provisioning limits and resource controls |
| Improve AI service reliability | Availability against approved service objectives | Include provider and integration dependencies |
| Improve data accessibility | Percentage of approved data sources integrated successfully | Enforce data classification and access restrictions |
| Improve model lifecycle management | Percentage of production models with complete version and approval records | Ensure that records correspond to deployed artifacts |
| Improve governance visibility | Percentage of in-scope AI systems with assigned owners and current risk assessments | Define completeness criteria and accountable owners |
| Control operating expenditure | Actual cloud expenditure against approved budget | Include model inference, storage, data transfer, logging, and managed-service costs |
| Improve recovery capability | Results of recovery and continuity tests | Verify recovery of trusted configurations, data, and model artifacts |
| Reduce security exposure | Closure rate for material security findings within approved timelines | Avoid treating closure metrics as proof of control effectiveness |

These KPIs should be supported by baselines, measurement methods, accountable owners, and reporting requirements.

The organization should also define negative indicators, such as unauthorized resource provisioning, unexplained expenditure growth, unresolved critical vulnerabilities, or failures in data-residency controls.

#### 2.3 Business Case and Total Cost of Ownership

Cloud migration decisions should account for total cost of ownership (TCO), rather than comparing only the cost of on-premises servers with cloud compute prices.

A complete assessment may include:

- Cloud compute and storage.
- GPU or other specialized accelerator capacity.
- Managed AI services.
- Model inference charges.
- Data ingestion and transformation.
- Data transfer and egress.
- Vector databases and retrieval services.
- Logging, monitoring, and security tooling.
- Backup and disaster recovery.
- Licensing and software subscriptions.
- Migration services and implementation effort.
- Security assessment and compliance assurance.
- Training and organizational change.
- Supplier management and contractual oversight.
- Exit planning and potential repatriation costs.

AI workloads can be particularly sensitive to usage patterns. A model serving a large number of requests may generate substantial variable costs even when the underlying application appears inexpensive to operate.

The business case should therefore evaluate expected demand, peak demand, model choice, retention requirements, data transfer patterns, and contingency capacity.

#### 2.4 Strategic Risks of Cloud Dependency

Cloud adoption may create long-term dependencies on a provider's infrastructure, proprietary services, APIs, and operational model.

These dependencies can affect:

- Portability of applications and data.
- Ability to change model providers.
- Availability of specialized AI services.
- Negotiating leverage.
- Recovery options during provider disruption.
- Compliance with changing legal obligations.
- Costs associated with migration or termination.
- Access to operational and audit evidence.

A provider's technical capability does not remove the organization's accountability for its own risk decisions.

The enterprise should identify which services are difficult to replace and evaluate whether the resulting dependency is acceptable.

**Core Principle:** The business case for AI cloud migration must demonstrate measurable value while accounting for lifecycle costs, provider dependency, security, compliance, and resilience. Faster deployment or access to advanced AI services is not sufficient justification when the organization cannot manage the associated risks.

### 3. Reference Architecture for Enterprise AI Cloud Migration

A secure AI cloud migration begins with an understanding of the existing environment and the target architecture.

The target architecture should define where applications, data, models, identities, integrations, and governance functions will operate.

It should also distinguish the responsibilities of the cloud provider, the enterprise, and other suppliers.

#### 3.1 Existing Environment Assessment

Before designing the target state, the organization should inventory the current AI environment.

The assessment should identify:

- Applications and business processes.
- AI models and model versions.
- Data sources and data classifications.
- Training and inference environments.
- Development and deployment pipelines.
- Integration interfaces.
- Identity providers and service accounts.
- Network dependencies.
- Security and monitoring controls.
- Regulatory and contractual obligations.
- Operational support arrangements.
- Recovery and continuity requirements.

The organization should identify undocumented systems and dependencies before approving the migration plan.

An undocumented dependency may become a migration blocker if the target cloud environment cannot reproduce its functionality, security requirements, or connectivity.

#### 3.2 Target-State Architecture Layers

A reference architecture can be organized into the following logical layers.

**Layer 1 — Enterprise Identity and Governance**

This layer provides identity federation, access policies, privileged access management, governance approvals, and enterprise risk oversight.

**Layer 2 — Cloud Landing Zone**

The landing zone establishes the foundational cloud environment, including account or subscription structure, network connectivity, security policies, logging, and resource-management controls.

**Layer 3 — Data Platform**

This layer contains approved data ingestion, transformation, storage, cataloguing, classification, and access-control services.

**Layer 4 — AI Development and Model Lifecycle**

This layer supports experimentation, model training or adaptation, evaluation, artifact management, version control, and controlled deployment.

**Layer 5 — AI Inference and Application Services**

This layer hosts model endpoints, AI application services, RAG pipelines, prompt management, and approved application integrations.

**Layer 6 — Enterprise Integration**

This layer connects AI applications to business systems through controlled APIs, message interfaces, data services, and other approved integration mechanisms.

**Layer 7 — Security Monitoring and Operational Management**

This layer provides security telemetry, centralized monitoring, vulnerability management, configuration assessment, incident response, and operational reporting.

These layers are logical categories. An actual deployment may implement several of them through shared cloud services or separate technical environments.

#### 3.4 Cloud Landing Zone and Governance Guardrails

The landing zone is the foundational environment in which cloud workloads are deployed.

It should establish consistent controls before AI workloads are migrated.

Typical components include:

- Cloud account, project, or subscription structure.
- Identity federation and centralized access management.
- Network segmentation and connectivity.
- Centralized logging.
- Resource tagging and ownership.
- Approved deployment regions.
- Encryption and key-management requirements.
- Security policies and configuration baselines.
- Vulnerability management integration.
- Resource provisioning restrictions.
- Budget controls and usage monitoring.
- Backup and recovery standards.
- Policy exception management.

The organization should enforce important requirements through technical guardrails where possible.

For example, if certain data categories may only be processed in approved regions, the organization should use appropriate configuration policies and deployment controls to prevent unauthorized placement where the platform supports those controls.

However, a policy configuration is not sufficient evidence by itself. The organization must verify that the control applies to all relevant resources and that exceptions are appropriately managed.

#### 3.5 AI Workload Segregation

AI workloads should be separated according to their purpose, sensitivity, and operational risk.

A common design distinguishes:

- Development environments.
- Testing and evaluation environments.
- Pre-production environments.
- Production environments.
- Restricted data-processing environments.
- Model training environments.
- Model inference environments.
- Administrative and management environments.

The exact separation mechanisms depend on the cloud platform and enterprise requirements.

They may include separate accounts or subscriptions, projects, networks, identities, encryption keys, and access policies.

Production model artifacts should not be replaceable by an ordinary development identity. Similarly, access to sensitive training data should not automatically grant permission to deploy a model into production.

Segregation of duties is particularly important when the same platform supports data preparation, model development, model approval, and production deployment.

#### 3.6 Shared Responsibility Model

Cloud security responsibilities are divided between the provider and the customer, with the allocation depending on the service model and contractual arrangement.

| Responsibility area | Cloud provider responsibilities may include | Enterprise responsibilities typically include |
|---|---|---|
| Physical infrastructure | Data-center facilities and physical infrastructure security | Assessing provider assurance and service suitability |
| Cloud platform | Underlying infrastructure and managed platform components | Secure configuration of customer-controlled resources |
| Identity | Platform identity capabilities | User access, roles, service identities, and privileged access |
| Data protection | Available encryption and data-protection capabilities | Data classification, access policies, retention, and lawful processing |
| AI models | Operation of a provider-managed model service, where applicable | Approved use, input/output handling, application controls, and risk assessment |
| Applications | Service capabilities and underlying hosting | Application security, authorization, integration, and business logic |
| Logging | Platform logging capabilities | Appropriate configuration, retention, monitoring, and investigation |
| Vulnerability management | Security of provider-managed components within the service model | Customer-managed workloads, dependencies, and applicable remediation |
| Resilience | Service-level commitments and provider recovery mechanisms | Architecture, backups, continuity, recovery testing, and dependency management |
| Compliance | Provider certifications and assurance evidence | Determining applicability and demonstrating the organization's own compliance |

This table is a general guide, not a contractual responsibility matrix.

The organization should validate the allocation for each selected service, including managed AI platforms, foundation model APIs, data services, and supporting infrastructure.

A cloud provider's certification does not automatically establish that the customer's deployment complies with every applicable requirement.

**Core Principle:** A secure target architecture requires controlled landing zones, workload segregation, governed data and model pipelines, protected identities, and explicit responsibility allocation. Cloud security depends on both the provider's controls and the enterprise's configuration, application design, and operational governance.

### 4. AI Cloud Migration Strategies and Workload Classification

Not every AI workload should be migrated using the same strategy.

The organization should evaluate each workload according to technical compatibility, business criticality, data sensitivity, regulatory obligations, operational dependencies, and expected benefits.

A migration strategy should be selected for each workload rather than imposed uniformly across the portfolio.

#### 4.1 The Main Migration Strategies

The following categories are commonly used in cloud migration planning.

**Rehost**

Move the workload to cloud infrastructure with minimal application changes.

For example, an existing AI application may be moved to cloud-hosted virtual machines while retaining its current application architecture.

Advantages:

- Potentially faster migration.
- Limited initial application redesign.
- May reduce immediate dependence on on-premises hardware.

Limitations:

- Legacy security weaknesses may be preserved.
- Infrastructure management responsibilities may remain substantial.
- The workload may not benefit fully from managed cloud services.
- Existing AI lifecycle limitations may remain unresolved.

Rehosting should not be treated as a reason to transfer insecure configurations into the cloud unchanged.

**Replatform**

Make targeted changes to use selected cloud capabilities without fundamentally redesigning the application.

For example, an organization may move an existing AI application's database to a managed database service while retaining its main application components.

Advantages:

- Potential reduction in infrastructure management.
- Access to selected managed capabilities.
- Moderate modernization effort.

Limitations:

- Additional service dependencies.
- Changes in operational responsibility.
- Potential differences in logging, backup, and access-control behavior.

**Refactor or Rearchitect**

Redesign the application or AI platform to take advantage of cloud-native services.

For example, an organization may separate its inference service, data ingestion pipeline, model registry, and application interface into independently managed components.

Advantages:

- Greater architectural flexibility.
- Improved automation opportunities.
- Potentially stronger separation of responsibilities.
- Better integration with cloud-native monitoring and security capabilities.

Limitations:

- Higher migration complexity.
- More extensive testing and assurance requirements.
- Increased risk of introducing new defects.
- Potential changes to model behavior, latency, and cost.

**Repurchase or Replace**

Replace an internally operated AI capability with a managed or third-party AI service.

For example, an organization may replace an internally hosted text-classification model with a managed AI service.

Advantages:

- Reduced responsibility for certain infrastructure components.
- Potential access to maintained and scalable services.
- Faster availability of some capabilities.

Limitations:

- Reduced control over underlying implementation.
- Provider dependency.
- Data-processing and confidentiality concerns.
- Possible limitations on model transparency, portability, or customization.
- Contractual and service-availability risks.

**Retain**

Keep a workload in its current environment.

Retention may be appropriate when the workload has unresolved dependencies, strict latency requirements, specialized hardware, legal restrictions, or insufficient business justification for migration.

Retaining a workload does not exempt it from security or AI governance requirements.

**Retire**

Decommission a workload that is no longer needed or whose business value does not justify continued operation.

Retirement should include data disposition, credential revocation, integration removal, asset inventory updates, and evidence retention where required.

#### 4.2 Migration Strategy Comparison

| Strategy | Typical objective | Relative complexity | Principal governance concern |
|---|---|---|---|
| Rehost | Move quickly with limited redesign | Low to moderate | Preserving legacy weaknesses |
| Replatform | Improve selected platform components | Moderate | New service dependencies and configuration changes |
| Refactor | Modernize architecture | High | Migration defects, new trust boundaries, and expanded testing |
| Repurchase | Adopt a replacement service | Variable | Third-party risk, data processing, and contractual dependency |
| Retain | Keep the workload in place | Low immediate migration effort | Continuing to manage existing technical and operational risk |
| Retire | Remove an unnecessary capability | Variable | Secure decommissioning and data disposition |

These complexity ratings are indicative. Actual effort depends on workload size, integration requirements, data volumes, and the condition of the existing environment.

#### 4.3 AI Workload Classification Matrix

Before choosing a strategy, classify each workload against key characteristics.

| Classification dimension | Example categories | Why it matters |
|---|---|---|
| Business criticality | Low, moderate, high, essential | Determines availability and continuity expectations |
| Data sensitivity | Public, internal, confidential, restricted | Influences storage, access, encryption, and processing requirements |
| AI function | Predictive model, classification, RAG, generative AI, autonomous agent | Determines relevant AI-specific controls |
| Model ownership | Internally developed, adapted, third-party managed | Affects lifecycle control and assurance options |
| Operational authority | Advisory, human-approved action, autonomous action | Determines the level of authorization and oversight required |
| Regulatory exposure | Unregulated, contractually regulated, legally regulated, sector-specific | Influences applicable obligations and evidence requirements |
| Latency requirement | Flexible, time-sensitive, strict real-time | Affects architecture and placement |
| Portability | High, moderate, low | Influences provider dependency and exit planning |
| Data location constraints | Flexible, approved regions, restricted environment | Affects deployment design and legal review |
| Dependency complexity | Limited, moderate, extensive | Affects sequencing and migration risk |

This classification should be documented and reviewed by the relevant business, security, architecture, and compliance stakeholders.

#### 4.5 Migration Waves and Sequencing

Large enterprises should normally organize migration into controlled waves.

A possible sequence is:

1. Inventory and discovery.
2. Workload classification and dependency mapping.
3. Target architecture and landing-zone preparation.
4. Migration of low-risk, non-production workloads.
5. Migration of selected development and evaluation services.
6. Controlled migration of production inference services.
7. Migration or redesign of sensitive data pipelines.
8. Migration of high-criticality workloads after additional assurance.
9. Post-migration validation and optimization.
10. Retirement of obsolete infrastructure.

The sequence should be adapted to the actual environment.

A low-criticality workload is not automatically a good first migration candidate if it has complex dependencies or sensitive data.

Likewise, a technically simple workload may be a poor candidate if it supports a critical business process and lacks a validated fallback.

#### 4.6 Migration Acceptance Criteria

Before migrating a workload, the organization should define the evidence required to approve the transition.

Acceptance criteria may include:

- Business owner approval.
- Approved target architecture.
- Documented data classification.
- Validated data-transfer procedures.
- Appropriate identity and access controls.
- Approved encryption and key-management arrangements.
- Completed security assessment.
- Tested deployment and rollback procedures.
- Validated model performance.
- Confirmed monitoring and logging.
- Recovery and continuity arrangements.
- Supplier and contractual review.
- Compliance assessment.
- Documented residual-risk decisions.

For AI workloads, functional equivalence must be evaluated carefully.

A model running in a different environment may exhibit changes in latency, numerical behavior, data processing, dependency versions, or output quality.

The organization should determine whether those changes are acceptable for the approved use case.

**Core Principle:** Migration strategy must be selected according to the workload's business purpose, technical dependencies, data sensitivity, and risk profile. Rehosting, refactoring, replacing, retaining, and retiring are distinct decisions, and each requires explicit acceptance criteria.

### 5. AI Cloud Migration Risk Landscape and Threat Model

Cloud migration changes the environment in which AI systems operate.

It can introduce new identity boundaries, management interfaces, data-transfer paths, supplier dependencies, service configurations, and operational assumptions.

The organization should assess these changes before migration and validate the resulting controls after deployment.

#### 5.1 Principal Risk Categories

**Data exposure during migration**

Sensitive training data, prompts, model artifacts, business documents, or evaluation datasets may be exposed during transfer, temporary storage, or migration testing.

Potential causes include excessive permissions, insecure transfer mechanisms, public storage exposure, and inappropriate access by migration personnel.

**Cloud misconfiguration**

Cloud resources may be exposed through incorrect network rules, overly permissive identities, public endpoints, weak encryption settings, or inadequate logging.

The risk is particularly significant when migration teams create resources quickly without applying approved landing-zone controls.

**Identity and privilege compromise**

Compromised user accounts, service identities, deployment credentials, or API keys may enable unauthorized access to data, models, or production services.

Migration pipelines can be especially sensitive because they may have access to both source and destination environments.

**Model integrity compromise**

Model artifacts may be replaced, corrupted, or deployed without authorization.

This can occur through compromised repositories, insecure artifact transfer, excessive deployment permissions, or weaknesses in the model promotion process.

**Data and model incompatibility**

A migrated model may perform differently because of dependency changes, altered preprocessing, different runtime versions, numerical precision, or changed data access behavior.

The result may be reduced accuracy, increased false positives, missed anomalies, or unsuitable recommendations.

**Third-party and provider dependency**

The target architecture may rely on provider-managed models, APIs, data services, or proprietary capabilities.

Service changes, outages, contract limitations, or provider-specific restrictions can affect availability, portability, and governance.

**Regulatory and data-residency failures**

Data may be stored, processed, logged, or accessed in ways that conflict with applicable legal obligations or contractual commitments.

The organization must evaluate the actual processing arrangement rather than assuming that selecting a particular cloud region resolves all data-protection questions.

**Operational continuity failures**

The migration may disrupt dependencies, alter recovery procedures, or leave the organization unable to restore a trusted service.

The risk includes not only application downtime but also the inability to recover verified model artifacts, configuration, data, and access controls.

**AI-specific attack exposure**

Cloud-hosted AI services may be exposed to prompt injection, unsafe retrieval, unauthorized tool use, malicious input data, or misuse of model-serving interfaces, depending on their architecture.

Moving an AI application to the cloud does not automatically create these vulnerabilities, but it may change the available attack paths and control requirements.

**Uncontrolled cost and resource consumption**

Unrestricted inference endpoints, excessive model calls, oversized compute resources, or unbounded processing jobs may create substantial costs or reduce service availability.

Cost governance is therefore part of the operational risk model.

| ACM-04 | Model artifacts are altered during transfer or deployment | Untrusted or unreliable model behavior | 16 | Artifact integrity validation, protected registries, and controlled promotion |
| ACM-05 | Model performance changes after migration | Reduced decision quality or operational effectiveness | 16 | Baseline testing, representative evaluation, and post-migration monitoring |
| ACM-06 | Data residency or processing obligations are not satisfied | Regulatory or contractual breach | 20 | Legal applicability assessment, approved processing locations, and verified service configuration |
| ACM-07 | A cloud provider outage disrupts a critical AI-dependent process | Operational interruption | 16 | Resilience design, fallback procedures, and tested recovery |
| ACM-08 | Provider-specific services create excessive lock-in | Increased exit cost and reduced strategic flexibility | 12 | Portability assessment, dependency inventory, and exit planning |
| ACM-09 | Inadequate logging prevents investigation of a cloud AI incident | Delayed detection and weak accountability | 16 | Centralized logging, retention controls, alert testing, and evidence preservation |
| ACM-10 | Compromised deployment automation introduces unauthorized changes | Production compromise or service disruption | 20 | Pipeline access controls, protected credentials, approval gates, and deployment verification |
| ACM-11 | AI application interfaces are exposed to prompt injection or unsafe inputs | Data disclosure or unauthorized application behavior | 16 | Input handling, retrieval controls, output validation, and restricted tool permissions |
| ACM-12 | Unbounded AI usage causes excessive expenditure or service exhaustion | Financial loss or reduced availability | 12 | Usage quotas, rate limits, budget alerts, and anomaly monitoring |
| ACM-13 | Migration dependencies are incompletely documented | Failed migration or unexpected service interruption | 16 | Dependency mapping, integration testing, and cutover validation |
| ACM-14 | Backup and recovery procedures fail to restore a trusted AI environment | Prolonged outage or restoration of compromised artifacts | 20 | Protected backups, integrity checks, and tested recovery procedures |
| ACM-15 | Cloud-provider and enterprise responsibilities are misunderstood | Control gaps and delayed incident response | 16 | Service-specific responsibility matrix, contracts, and operational procedures |
| ACM-16 | Production migration proceeds without sufficient security and governance evidence | Unacceptable residual risk | 20 | Formal release gates, evidence requirements, and authorized risk decisions |

The scores are not universal benchmarks. For example, the impact of a residency failure depends on the data involved, applicable obligations, and the consequences of noncompliance.

#### 5.4 Risk Ownership and Accountability

Each material migration risk should have an accountable owner.

Potential responsibilities include:

| Role | Principal accountability |
|---|---|
| Executive sponsor | Business justification, funding, and strategic direction |
| Business system owner | Intended use, business requirements, and operational acceptance |
| Enterprise architect | Target architecture, integration design, and dependency mapping |
| Cloud platform owner | Landing-zone controls and cloud platform configuration |
| CISO or security leader | Cybersecurity governance and risk oversight |
| AI system owner | AI lifecycle governance, intended-use restrictions, and performance assurance |
| Data owner | Data classification, permitted use, quality, and access |
| Data protection or privacy lead | Assessment of applicable personal-data obligations |
| Legal and compliance teams | Legal applicability, contractual obligations, and compliance interpretation |
| Cloud operations team | Monitoring, service management, and operational support |
| Internal audit | Independent assurance within the approved audit mandate |
| Third-party risk team | Supplier assessment and dependency oversight |

The precise allocation depends on the organization's governance model.

Risk ownership should not be confused with control operation. A business owner may be accountable for a risk while cloud engineering, cybersecurity, or data teams implement the relevant controls.

#### 5.5 Migration Risk Assessment Method

The organization should use a repeatable assessment process.

**Step 1 — Identify the assets**

Record applications, models, datasets, identities, interfaces, infrastructure, and dependencies.

**Step 2 — Define the migration change**

Document what is changing, including the hosting model, service provider, data location, access model, runtime, and integration architecture.

**Step 3 — Identify threats and failure scenarios**

Consider malicious activity, configuration errors, supplier failures, model degradation, migration defects, and operational failures.

**Step 4 — Assess existing controls**

Determine which source-environment controls remain applicable, which require redesign, and which new controls are needed.

**Step 5 — Evaluate inherent risk**

Assess the potential likelihood and impact before considering the proposed new controls.

**Step 6 — Define treatment actions**

Specify preventive, detective, corrective, and recovery controls, together with accountable owners and target dates.

**Step 7 — Verify control effectiveness**

Review configuration evidence and conduct appropriate testing.

**Step 8 — Evaluate residual risk**

Determine what exposure remains after the controls have been implemented and tested.

**Step 9 — Obtain required approval**

Secure the decisions required by the organization's governance process before production cutover.

**Step 10 — Monitor after migration**

Reassess the system after cutover and when material changes affect the approved risk assumptions.

#### 5.6 Migration Threats Versus Steady-State Threats

Migration introduces temporary risks that differ from those present during normal cloud operations.

| Risk dimension | Migration phase | Steady-state operation |
|---|---|---|
| Identity | Temporary access across source and target environments | Ongoing access to production services |
| Data | Bulk transfer, temporary copies, staging locations | Continuous ingestion, storage, retrieval, and processing |
| Configuration | Rapid provisioning and transitional settings | Persistent configuration drift and policy exceptions |
| Model artifacts | Export, transfer, conversion, and deployment | Ongoing updates and production model management |
| Monitoring | Potential gaps between old and new tools | Continuous detection and incident response |
| Availability | Cutover, rollback, and dependency transition | Provider outages, service failures, and operational incidents |
| Governance | Migration approvals and acceptance gates | Continuous risk review and lifecycle change management |
| Supplier dependency | New contracts and service onboarding | Long-term provider dependency and exit readiness |

A migration can be secure at cutover but become insecure later if configuration drift, uncontrolled model updates, or access changes are not managed.

Conversely, a mature operational control environment cannot compensate for an unsafe migration process that exposes sensitive data or deploys unvalidated artifacts.

**Core Principle:** AI cloud migration creates both transitional and long-term risks. A defensible migration program must identify assets and dependencies, assess new attack paths, establish accountable risk ownership, verify controls, and retain evidence that the target environment meets its approved security and operational requirements.

# 21.17 — Enterprise AI Cloud Migration
## Part 2: Governance Frameworks, Cloud Security Architecture, Migration Controls, and Risk Treatment

### 6. Governance Frameworks, Standards, and Regulatory Considerations for AI Cloud Migration

Enterprise AI cloud migration must be governed as a combined **cloud transformation, cybersecurity, data governance, and AI risk management initiative**. Conventional cloud migration controls remain necessary, but AI workloads introduce additional concerns involving training data, model artifacts, inference endpoints, model behavior, AI-specific dependencies, and the potential for sensitive information to be exposed through AI interactions.

The governance objective is not simply to verify that workloads have been migrated securely. It is to demonstrate that the migrated AI environment remains appropriately controlled, legally compliant, operationally resilient, and aligned with enterprise risk appetite.

#### 6.1 Governance Frameworks and Their Roles

Different frameworks address different parts of the migration risk landscape. Organizations should avoid treating them as interchangeable certifications or assuming that adopting one framework automatically satisfies all other obligations.

| Framework or standard | Primary focus | Application to AI cloud migration | Important limitation |
|---|---|---|---|
| ISO/IEC 27001 | Information security management system | Risk assessment, security policies, control ownership, internal audits, corrective actions, and continual improvement | Does not independently provide a complete AI-specific governance framework |
| ISO/IEC 42001 | AI management system | AI governance policies, defined responsibilities, AI risk management, lifecycle controls, and continual improvement | Does not replace cloud infrastructure security or applicable legal obligations |
| ISO/IEC 27017 | Cloud-specific information security controls | Cloud service responsibilities, tenant isolation, cloud operations, and provider-customer control considerations | Must be applied in the context of the organization's broader security program |
| ISO/IEC 27018 | Protection of personally identifiable information in public clouds acting as PII processors | Privacy-related controls for applicable cloud processing arrangements | Does not cover every privacy obligation or every cloud deployment model |
| NIST Cybersecurity Framework (CSF) | Cybersecurity risk management | Organizing migration security activities around Govern, Identify, Protect, Detect, Respond, and Recover | A risk-management framework, not a substitute for detailed implementation requirements |
| NIST AI Risk Management Framework (AI RMF) | AI risk management | Governing AI use cases, measuring AI-related risks, and managing risks throughout the AI lifecycle | Does not prescribe a single mandatory cloud architecture |
| NIST SP 800-53 | Security and privacy controls | Selecting and tailoring security controls for cloud-hosted enterprise systems | Control selection must reflect the system's context and applicable requirements |
| NIST SP 800-207 | Zero Trust Architecture | Defining resource-centered access decisions, continuous evaluation, and explicit trust boundaries | Does not eliminate the need for network segmentation, identity governance, or workload protection |
| NIST SP 800-207A | Zero Trust Architecture models for access control in cloud-native applications | Informing application-level identity and access control for cloud-native environments | Implementation must be adapted to the actual platform and workload |
| CIS Critical Security Controls and applicable CIS Benchmarks | Security practices and configuration hardening | Establishing security baselines for cloud accounts, workloads, operating systems, and supported services | Recommendations must be mapped to the actual technology and operating model |
| OWASP Top 10 for LLM Applications | Common risks in LLM applications | Identifying risks such as prompt injection, sensitive information disclosure, insecure output handling, and excessive agency | Primarily application-oriented; it does not replace enterprise cloud security controls |
| Cloud Security Alliance guidance | Cloud security architecture and governance | Supporting cloud control design, shared-responsibility analysis, and cloud risk management | Guidance should be mapped to the organization's requirements and control environment |

**Governance principle:** Select frameworks according to the organization's obligations, risk profile, architecture, and assurance objectives. Maintain a control mapping that shows how each applicable requirement is implemented, tested, evidenced, and assigned to an accountable owner.

A control mapping translates broad governance requirements into concrete migration activities.

| AI risk management | Evaluate changes to model behavior, data processing, and AI dependencies | AI impact assessment and model validation report | AI Governance / Model Owner |
| Identity and access management | Redesign access permissions for cloud identities and AI services | IAM design, role assignments, access review results | IAM / Cloud Security |
| Data protection | Classify migrated data and approve destination locations | Data inventory, classification records, transfer assessment | Data Owner / Privacy |
| Secure configuration | Apply approved landing-zone and workload baselines | Configuration compliance reports | Cloud Platform / Security Engineering |
| Vulnerability management | Scan workloads, images, dependencies, and exposed services | Scan results and remediation tickets | Vulnerability Management / Engineering |

A framework mapping is not sufficient if it only states that a control is implemented. The organization needs evidence that the control operates effectively.

#### 6.3 Regulatory Applicability Assessment

Regulatory applicability depends on the organization, industry, customer locations, data subjects, processing activities, AI use case, and deployment model.

For an enterprise operating in Spain or elsewhere in the European Union, the applicability assessment may include:

- **General Data Protection Regulation (GDPR):** Personal-data processing, lawful basis, data minimization, processor relationships, international transfers, data-subject rights, security, and data protection impact assessments where required.
- **EU AI Act:** Requirements depend on the AI system's classification, intended purpose, provider/deployer role, and applicable implementation dates. Certain high-risk AI systems have additional obligations. Not every enterprise AI application is automatically classified as high-risk.
- **NIS2 Directive and national implementing legislation:** Applicability depends on the organization's sector, size, designation, and relevant national law. Organizations should not assume that every company using cloud AI is directly in scope.
- **DORA:** Relevant to financial entities and other parties within its defined scope. Cloud migration may affect ICT risk management, resilience testing, incident handling, and third-party ICT risk arrangements.
- **Sector-specific obligations:** Healthcare, telecommunications, energy, transport, and other regulated sectors may have additional security, safety, resilience, or data-handling requirements.
- **Contractual and customer requirements:** Security addenda, data residency commitments, customer assurance requirements, and industry-specific obligations may apply even where a particular regulation does not directly impose the same requirement.

The compliance team should document the applicability rationale, accountable legal or compliance reviewer, relevant requirements, required controls, and evidence needed to demonstrate compliance.

**Do not confuse cloud-provider certifications with customer compliance.** A provider's certifications may support assurance, but they do not automatically establish that the customer's AI application, data-processing activities, access controls, or operational practices comply with applicable requirements.

### 7. Secure Cloud Architecture for Enterprise AI Workloads

An AI cloud migration should establish a target architecture that separates management responsibilities, limits trust relationships, protects data, and controls how AI workloads interact with enterprise systems.

A common architectural mistake is to migrate an AI workload into a cloud environment while retaining overly permissive identities, unrestricted network access, weak data boundaries, and insufficient monitoring. Such a migration may modernize infrastructure without materially reducing security risk.

#### 7.1 Architecture Design Principles

The target architecture should implement the following principles.

**1. Identity-first security**

Every human, application, workload, model-serving component, and automation process should use a clearly defined identity. Access should be based on business need and least privilege.

Avoid relying on network location as the primary indicator of trust.

**2. Segmentation by trust boundary**

Separate production, development, testing, model training, model serving, and sensitive-data environments where their risk profiles justify separation.

Segmentation should apply to identities, networks, data stores, management planes, and service permissions—not just virtual networks.

**3. Controlled data movement**

Data should move between systems only through approved paths with defined purposes, authorization, validation, and monitoring.

A data classification label alone does not enforce security. The architecture must translate the classification into storage, access, encryption, retention, and transfer restrictions.

**4. Controlled model and artifact deployment**

Models, container images, notebooks, packages, prompts, configuration files, and supporting artifacts should be managed through controlled repositories and deployment pipelines.

Production systems should not automatically trust a model artifact simply because it was uploaded to an internal storage location.

**5. Separation of inference and administrative privileges**

A workload that serves AI inference should not automatically possess the permissions needed to administer the model platform, modify security policies, access unrelated datasets, or create additional privileged identities.

**6. Secure integration with enterprise systems**

AI services connecting to ERP, CRM, identity systems, ticketing platforms, or operational technology should use scoped APIs and narrowly defined permissions.

A model should not receive broad access to an enterprise application simply because it may need one specific business function.

The landing zone establishes the foundational controls under which cloud workloads are deployed.

| Control domain | Required capability | Example validation |
|---|---|---|
| Organizational structure | Separate production, non-production, and restricted environments as appropriate | Confirm subscription, account, project, or organizational-unit boundaries |

| Encryption | Approved encryption for data at rest and in transit | Verify encryption settings and key-access permissions |

#### 7.4 AI-Specific Architecture Controls

AI workloads require controls beyond the standard infrastructure baseline.

| AI component | Key risk | Architectural control |
|---|---|---|
| Model registry | Unauthorized or unverified model artifacts | Approved registry, provenance validation, access restrictions, and version control |
| Training pipeline | Data poisoning or unauthorized dataset changes | Dataset provenance, controlled ingestion, integrity checks, and restricted write permissions |
| Inference endpoint | Unauthorized use, abuse, or data leakage | Authenticated access, rate limits, request validation, and output monitoring |
| Retrieval-augmented generation (RAG) | Retrieval of unauthorized or poisoned content | Source validation, document-level authorization, retrieval filtering, and provenance tracking |
| Vector database | Cross-user or cross-tenant information disclosure | Strong tenant boundaries, access enforcement, and secure metadata filtering |
| Prompt and system instructions | Unauthorized changes or instruction manipulation | Version control, access restrictions, testing, and controlled deployment |
| AI agent | Excessive tool permissions or unauthorized actions | Tool mediation, scoped identities, action policies, and approval gates |
| Model evaluation service | Biased or incomplete evaluation results | Independent test datasets, documented acceptance criteria, and evidence retention |
| AI telemetry | Sensitive prompts or outputs exposed through logs | Data minimization, masking, restricted access, and retention controls |
| External model API | Unapproved transfer of sensitive information | Provider assessment, contractual review, data-flow restrictions, and approved API gateway policies |

AI-specific controls must be tested against the actual application behavior. For example, confirming that a vector database requires authentication does not prove that a user cannot retrieve another user's documents through an application-level authorization flaw.

#### 7.5 Cloud Security Architecture Review Checklist

Before approving the target architecture, reviewers should confirm:

- [ ] All AI workloads and dependencies are inventoried.
- [ ] Data flows and trust boundaries are documented.
- [ ] Production and non-production access paths are appropriately separated.
- [ ] Human and workload identities are uniquely attributable.
- [ ] Privileged access is limited and monitored.
- [ ] Public exposure is explicitly justified and approved.
- [ ] Outbound network access is controlled according to workload requirements.
- [ ] Sensitive data cannot be accessed solely by bypassing application authorization.
- [ ] Model and data artifacts have documented provenance and controlled deployment paths.
- [ ] AI agent actions are constrained by explicit tool and transaction permissions.
- [ ] Security and AI-relevant logs are collected without unnecessary sensitive-data exposure.
- [ ] Backup, restoration, and disaster recovery are tested.
- [ ] Security architecture exceptions have owners, expiry dates, and compensating controls.
- [ ] The architecture has been reviewed by the appropriate security, data, AI, and service owners.

**Core Principle:** A secure AI cloud architecture must enforce trust boundaries at identity, data, application, model, and integration layers. Network security alone cannot compensate for excessive permissions or weak application-level authorization.

### 8. Cloud Migration Security Controls and Implementation Requirements

A secure migration requires a defined control baseline, implementation ownership, validation procedures, and a process for managing exceptions. The organization should identify the controls that must be in place before data transfer, before production cutover, and during steady-state operations.

Controls should be proportionate to workload criticality, data sensitivity, AI capabilities, and potential business impact.

#### 8.1 Identity and Access Management

Cloud migration frequently changes how identities are created, how permissions are assigned, and how administrative access is performed.

Legacy systems may rely on service accounts, embedded credentials, static API keys, shared administrative accounts, or network-based trust. These mechanisms should be reviewed rather than copied into the cloud unchanged.

**Minimum implementation requirements**

1. Establish a central identity and access management model.
2. Require strong authentication for privileged and sensitive access.
3. Use role-based access control (RBAC) and, where useful, attribute-based access control (ABAC).
4. Prefer managed workload identities or short-lived credentials over long-lived secrets.
5. Separate administrative, deployment, inference, and data-access permissions.
6. Implement periodic access reviews and prompt removal of unnecessary access.
7. Record privileged activity and alert on suspicious access patterns.
8. Define break-glass access with restricted use, monitoring, and post-use review.

**Example:**

A migrated AI summarization service needs to read documents from an approved storage location and invoke an inference endpoint. It should not automatically receive permission to delete source documents, change storage policies, create cloud administrators, or read unrelated business datasets.

#### 8.2 Data Protection and Privacy

Migration changes can create new data flows, processing locations, administrative access paths, and third-party dependencies. These changes require explicit data governance.

The organization should classify data before migration and determine which controls are necessary for each data category.

| Data category | Example | Typical control considerations |
|---|---|---|
| Public | Approved public documentation | Integrity, availability, and protection against unauthorized modification |
| Internal | Internal operational procedures | Authenticated access, approved storage, and controlled sharing |
| Confidential | Business plans, internal financial records | Strong access restrictions, encryption, monitoring, and retention controls |
| Restricted | Personal data, credentials, regulated information, sensitive intellectual property | Strict authorization, data minimization, key governance, enhanced monitoring, and carefully controlled processing |
| AI training data | Curated datasets used for training or fine-tuning | Provenance, lawful use, integrity, access restrictions, and documented lineage |
| AI inference data | Prompts, uploaded files, retrieved passages, and generated outputs | Data minimization, access controls, retention decisions, output handling, and disclosure prevention |
| Model artifacts | Weights, embeddings, adapters, configuration files | Integrity, provenance, access restrictions, version control, and protection against unauthorized extraction |

The organization should also evaluate:

- Data residency and international transfer requirements.
- Whether the cloud provider acts as a processor or another legally relevant role.
- Whether prompts and outputs are retained by the service.
- Whether submitted information is used for provider model training or service improvement.
- Whether logs contain personal, confidential, or regulated information.
- Whether deletion requests can be propagated to relevant copies, indexes, caches, and derived artifacts where required.
- Whether model training or fine-tuning creates additional data protection considerations.
- Whether the new processing requires a data protection impact assessment or other formal review.

Encryption is necessary but insufficient. An authorized application that retrieves confidential data and sends it to an unapproved external AI endpoint can still cause a serious disclosure even when the data is encrypted in storage and transit.

#### 8.3 Encryption and Key Management

Encryption controls should be aligned with data classification and threat scenarios.

**At rest:** Protect databases, object storage, snapshots, backups, model repositories, and relevant temporary storage.

**In transit:** Protect data moving between users, applications, cloud services, AI endpoints, and enterprise integrations.

**Key management:** Define who can create, rotate, disable, recover, and administer cryptographic keys. Separate key administration from routine application access where appropriate.

**Customer-managed keys:** Consider them when required by policy, regulation, contractual commitments, or the risk assessment. They introduce additional operational responsibilities, including availability, rotation, recovery, and monitoring.

Validation should confirm actual configuration and access behavior rather than relying solely on a statement that the cloud service supports encryption.

#### 8.4 Network Security and Egress Control

AI workloads may communicate with model endpoints, package repositories, data sources, telemetry services, external APIs, and other enterprise systems. Uncontrolled outbound connectivity can enable data exfiltration, command-and-control communication, and unauthorized use of external AI services.

Controls should include:

- Private connectivity for sensitive services where appropriate.
- Explicitly approved inbound exposure.
- Restrictive egress policies for workloads that do not require unrestricted internet access.
- API gateways or controlled service interfaces for external integrations.
- DNS monitoring and appropriate filtering.
- Web application firewall controls for exposed web applications and APIs.
- Network segmentation between management, data, inference, and integration components.
- Monitoring for unexpected destinations, unusual transfer volumes, and anomalous service-to-service communication.

For AI applications, egress controls should account for more than malware. They should also consider whether prompts, retrieved documents, embeddings, source code, or generated outputs could be transmitted to unauthorized destinations.

Migration often involves rebuilding applications, creating new containers, changing dependencies, or moving model-serving components into managed platforms.

#### 8.6 Vulnerability and Configuration Management

Cloud migration can introduce vulnerabilities through new services, misconfigured storage, overly permissive IAM policies, exposed management interfaces, vulnerable packages, insecure containers, and unpatched operating systems.

A mature vulnerability management process should define:

1. Asset and workload discovery.
2. Vulnerability scanning and configuration assessment.
3. Risk-based prioritization.
4. Remediation ownership and target dates.
5. Exception approval and compensating controls.
6. Retesting and closure evidence.
7. Reporting of overdue critical and high-risk findings.

Prioritization should consider exploitability, internet exposure, privileges required, data sensitivity, business criticality, available mitigations, and potential impact on AI services.

For example, a vulnerable library in an isolated test environment may have a different risk profile from the same library in a publicly accessible inference service with access to confidential documents and external tools.

#### 8.7 Logging, Monitoring, and Detection

The migration should preserve or improve security visibility. Moving workloads to the cloud can fragment telemetry if each service logs independently or if cloud audit logs are not integrated into the enterprise monitoring environment.

Relevant log sources may include:

- Cloud control-plane activity.
- Identity provider and privileged-access events.
- Network flow and firewall logs.
- API gateway and application logs.
- Storage and database access logs.
- Container, virtual machine, and workload protection telemetry.
- Model endpoint invocation records.
- AI application security events.
- Agent tool invocations and transaction outcomes.
- Configuration changes and policy violations.

Logging should be designed to preserve security evidence without unnecessarily collecting sensitive prompts, personal data, secrets, or complete confidential documents.

For AI systems, monitoring may need to detect unusual inference volume, abnormal token consumption, suspicious tool invocation, repeated authorization failures, unexpected data retrieval, prompt-injection attempts, and anomalous output patterns.

#### 8.8 Control Implementation and Evidence Matrix

| Control ID | Control requirement | Implementation evidence | Test procedure | Example failure condition |
|---|---|---|---|---|
| ACM-IAM-01 | Privileged access is restricted | Role assignments and privileged-access policy | Review privileged identities and test access boundaries | Unapproved users retain administrative privileges |
| ACM-IAM-02 | Workload identities use least privilege | Identity definitions and permission policies | Attempt prohibited actions using the workload identity | Workload can modify unrelated resources |
| ACM-DAT-01 | Sensitive data is classified | Approved data inventory | Sample datasets and compare classifications with handling rules | Restricted data has no owner or classification |
| ACM-DAT-02 | Data transfers are authorized | Data-flow diagram and approved destination list | Test whether unapproved destinations are blocked | Sensitive prompts can be sent to unapproved endpoints |
| ACM-NET-01 | Egress is controlled | Firewall and routing policies | Attempt connections to prohibited destinations | Workload can establish unrestricted outbound connections |
| ACM-ART-01 | Production artifacts have verified provenance | Registry records, signatures, and pipeline logs | Attempt deployment of an unapproved artifact | Unverified model or container can reach production |
| ACM-LOG-01 | Security events are centrally collected | Logging configuration and SIEM ingestion records | Generate test events and confirm detection | Critical administrative actions are not recorded |
| ACM-REC-01 | Recovery capability is validated | Backup configuration and restoration reports | Restore a representative service and validate data integrity | Recovery fails to meet approved objectives |
| ACM-AI-01 | AI behavior is evaluated before release | Evaluation plan and test results | Execute approved abuse and regression test cases | Critical AI security failure remains unresolved |
| ACM-AI-02 | Agent tools enforce authorization | Tool permissions and action policies | Attempt prohibited actions under realistic conditions | Agent performs unauthorized or out-of-scope actions |

The evidence matrix should be linked to the enterprise risk register and control library. A control that has not been tested should not be reported as fully effective solely because the relevant configuration exists.

**Core Principle:** Migration security is demonstrated through effective, testable controls—not by architecture diagrams, cloud-provider assurances, or policy statements alone.

### 9. Migration Risk Assessment and Treatment Methodology

Enterprise AI cloud migration introduces changes to technology, data flows, identity, supplier dependencies, operating procedures, and AI behavior. Risk assessment must therefore be performed at both the migration-project level and the target-service level.

The project may complete successfully from a delivery perspective while leaving the migrated service with unacceptable residual risk. Conversely, a technically secure target architecture can still fail if migration activities cause data loss, operational disruption, or an unplanned service outage.

#### 9.1 Distinguish Migration Risks from Steady-State Risks

| Risk category | Migration-phase example | Steady-state example |
|---|---|---|
| Data confidentiality | Sensitive data copied to an unauthorized staging location | Production AI endpoint discloses confidential information |
| Data integrity | Dataset altered during transfer without detection | Unauthorized modification of model artifacts or retrieval sources |
| Availability | Cutover causes prolonged service interruption | Cloud-region or provider-service outage affects production inference |
| Identity | Legacy credentials copied into migration scripts | Excessive persistent privileges remain assigned to AI workloads |
| Network | Temporary migration connectivity exposes internal systems | Production workload permits unrestricted outbound communication |
| AI model | Model or dataset version changes without validation | Model drift or poisoned content degrades system behavior |
| Third-party dependency | Migration introduces an unassessed external service | Provider changes service behavior, retention, or availability |
| Compliance | Data moved before transfer requirements are reviewed | Ongoing processing violates an applicable contractual or legal requirement |
| Operational resilience | Rollback plan is incomplete or untested | Recovery objectives cannot be met after a major outage |
| Governance | Project bypasses required risk approvals | No accountable owner monitors the AI system after launch |

The distinction matters because a migration plan should contain temporary safeguards and exit criteria, while the production operating model must provide enduring controls.

#### 9.2 Define the Risk Assessment Scope

A complete assessment should consider:

**Business process:** What business service depends on the AI workload? What happens if the service is unavailable, inaccurate, or compromised?

**Data:** What data is collected, transferred, stored, retrieved, generated, or sent to third parties?

**AI functionality:** Is the workload performing inference, retrieval, training, fine-tuning, decision support, or autonomous actions?

**Architecture:** Which identities, APIs, cloud services, model endpoints, databases, and enterprise integrations are involved?

**Threat actors:** Could a risk arise from external attackers, malicious insiders, compromised suppliers, accidental misconfiguration, or unintended AI behavior?

**Migration method:** Will the workload be rehosted, replatformed, refactored, replaced, retained, or retired?

**Operational model:** Who owns the workload, who responds to incidents, and which responsibilities remain with the cloud provider?

**Regulatory and contractual requirements:** Which obligations apply to the service and its data flows?

**Recovery:** What service interruption, data loss, or model unavailability can the business tolerate?

#### 9.3 Risk Scoring Method

A consistent scoring model helps prioritize remediation and support governance decisions. The enterprise should use its approved risk methodology where one already exists.

A simplified illustrative model is:

**Risk Score = Likelihood × Impact**

Where:

- **Likelihood:** 1 = Rare, 2 = Unlikely, 3 = Possible, 4 = Likely, 5 = Almost Certain.
- **Impact:** 1 = Negligible, 2 = Minor, 3 = Moderate, 4 = Major, 5 = Severe.

| Score | Illustrative classification | Typical treatment |
|---:|---|---|
| 1–4 | Low | Manage through routine controls and monitoring |
| 5–9 | Moderate | Assign an owner and implement proportionate treatment |
| 10–16 | High | Prioritize treatment and require appropriate management review |
| 17–25 | Critical | Escalate promptly; production progression may need to be blocked |

These thresholds are examples, not universal risk standards. Organizations must define their own scoring scales, escalation thresholds, and risk acceptance authority.

The assessment should record inherent risk, existing controls, residual risk, treatment decisions, evidence, and reassessment triggers.

#### 9.4 Risk Treatment Options

The standard treatment options are:

- **Avoid:** Do not migrate or deploy the workload where the risk cannot be justified or managed.
- **Mitigate:** Implement preventive, detective, corrective, or resilience controls to reduce risk.
- **Transfer or share:** Allocate certain financial or contractual consequences through insurance or contractual arrangements, while recognizing that accountability and many obligations cannot simply be transferred.
- **Accept:** Formally accept residual risk through an authorized decision-maker, within the organization's risk appetite and applicable legal requirements.

Risk acceptance should not be used to bypass mandatory legal requirements or to legitimize a control failure that the organization is not authorized to waive.

#### 9.6 Risk Ownership and Escalation

Risk ownership must be assigned to individuals or roles with authority to make relevant decisions.

| Role | Principal responsibility |
|---|---|
| Executive sponsor | Owns business objectives, funding, and escalation of major delivery conflicts |
| Business service owner | Defines business impact, operational requirements, and service acceptance criteria |
| AI system owner | Owns the AI use case, intended purpose, model-related risks, and ongoing performance |
| Data owner | Approves data use, classification, access, and relevant handling requirements |
| Cloud platform owner | Owns cloud platform design, foundational controls, and platform operations |
| Information Security / GRC | Coordinates risk assessment, control mapping, risk reporting, and assurance |
| Privacy / Legal | Assesses applicable privacy, contractual, and legal obligations |
| Migration lead | Coordinates execution, cutover, dependencies, and project-level risk treatment |
| SOC / Incident Response | Defines monitoring requirements and investigates security incidents |
| Risk acceptance authority | Accepts residual risk within formally delegated authority |

The control owner is responsible for operating the control. The risk owner is accountable for the risk and its treatment decision. These roles may overlap, but they are not automatically identical.

#### 9.7 Risk Acceptance Requirements

Before accepting residual risk, the decision-maker should have access to:

1. A clear description of the risk scenario and affected business service.
2. The assessed likelihood and impact.
3. Existing controls and their effectiveness.
4. Remaining control gaps and possible treatment alternatives.
5. Business justification for acceptance.
6. Relevant legal, regulatory, contractual, and safety constraints.
7. The proposed acceptance period and review date.
8. The name of the accountable risk owner.
9. Any compensating controls and monitoring requirements.
10. Explicit approval from the appropriate authority.

Risk acceptance should be time-bound where practical and reviewed when the architecture, data, model, threat landscape, or business use changes materially.

**Core Principle:** A migration risk register is a decision instrument, not a compliance form. Every material risk must have a defined scenario, accountable owner, defensible treatment, and verifiable closure or acceptance decision.

### 10. Migration Validation, Security Testing, and Production Readiness

A workload should not be considered secure merely because it has been deployed successfully in the target cloud environment. Production readiness requires evidence that the migrated system meets functional, security, privacy, AI behavior, resilience, and operational requirements.

Testing should begin during design and continue through migration rehearsal, cutover, and post-migration validation.

#### 10.1 Establish a Validation Strategy

The validation plan should be based on the workload's criticality, architecture, data classification, AI capabilities, and identified risks.

| Test category | Objective | Example validation |
|---|---|---|
| Functional testing | Confirm that business functions work correctly | Validate expected application workflows and outputs |
| Integration testing | Confirm that connected systems exchange data correctly | Test CRM, ERP, identity, and approved API interactions |
| Identity and authorization testing | Confirm that only authorized identities can perform actions | Attempt access using unauthorized roles and accounts |
| Configuration testing | Confirm that cloud services follow approved baselines | Evaluate IAM, network, storage, encryption, and logging settings |
| Vulnerability testing | Identify known software and infrastructure weaknesses | Scan dependencies, containers, hosts, and exposed services |
| Penetration testing | Assess exploitable weaknesses under an authorized test scope | Test approved application and API attack scenarios |
| Data protection testing | Verify privacy and data-handling controls | Test access restrictions, masking, retention, and deletion workflows |
| AI security testing | Assess AI-specific attack and failure scenarios | Test prompt injection, data leakage, unsafe outputs, and unauthorized tool actions |
| Model validation | Confirm that model behavior remains acceptable | Compare relevant accuracy, quality, robustness, and drift measures |
| Performance testing | Verify performance under expected and peak load | Measure latency, throughput, and resource consumption |
| Resilience testing | Verify recovery and fault tolerance | Test restoration, failover, and degraded-service behavior |
| Operational readiness testing | Confirm that support teams can operate the service | Validate alerts, runbooks, escalation paths, and incident procedures |

The testing strategy should define test owners, environments, prerequisites, acceptance thresholds, evidence retention, and how failures affect the release decision.

#### 10.2 AI-Specific Security Test Scenarios

AI cloud migration may change model versions, inference configurations, data retrieval paths, access permissions, or provider behavior. The organization should test whether these changes introduce new risks.

**Scenario A: Sensitive information disclosure**

A user asks the AI assistant to reveal confidential information contained in a dataset they are not authorized to access.

Expected result:
- Authorization is enforced independently of the model's instructions.
- Unauthorized records are not retrieved or disclosed.
- Relevant attempts are logged in accordance with privacy and security requirements.
- The test does not depend solely on a prompt telling the model to refuse.

**Scenario B: Prompt injection through retrieved content**

A RAG application retrieves a document containing malicious instructions designed to override the application's intended behavior.

Expected result:
- Retrieved content is treated as untrusted data.
- The application does not grant the document authority to change system policy.
- Tool calls and sensitive actions remain subject to independent authorization.
- Security-relevant behavior is recorded for investigation.

**Scenario C: Unauthorized agent action**

An AI agent can create support tickets and access a business system. A test attempts to make it export a full customer database.

Expected result:
- The tool interface rejects the unauthorized operation.
- The agent's identity lacks unnecessary permissions.
- Any permitted export operation is constrained by policy and scope.
- Alerts are generated when defined suspicious activity thresholds are met.

**Scenario D: Model endpoint abuse**

A test client attempts repeated inference requests, oversized payloads, or unauthorized API calls.

Expected result:
- Authentication and authorization are enforced.
- Rate limits and resource controls operate as intended.
- Errors do not disclose secrets or internal implementation details.
- Abnormal activity can be detected and investigated.

**Scenario E: Model and data integrity**

A test attempts to deploy an unapproved model artifact or alter a production dataset outside the approved pipeline.

Expected result:
- The deployment or modification is blocked, or detected and contained according to the control design.
- Provenance and version information remain traceable.
- Relevant alerts and audit evidence are retained.

Testing must be authorized, scoped, and performed in an environment appropriate to the potential impact. Destructive tests against critical production services require explicit approval and suitable safeguards.

#### 10.3 Model and Application Baseline Comparison

Where the migration changes the model, runtime, framework, inference configuration, data pipeline, or retrieval architecture, the organization should establish a baseline before cutover.

Baseline comparison may include:

- Model version and provider configuration.
- Input and output schema.
- Quality and accuracy measures appropriate to the use case.
- Latency and throughput.
- Retrieval precision and relevance for RAG systems.
- Authorization behavior.
- Refusal behavior and handling of prohibited requests.
- Data leakage test results.
- Tool invocation patterns and action constraints.
- Cost per request or transaction.
- Error rates and availability.

A model producing broadly similar outputs does not prove that its security properties remain equivalent. For example, a migrated RAG application may retain similar answer quality while inadvertently losing document-level authorization enforcement.

Acceptance thresholds should be established before testing. Otherwise, teams may be tempted to redefine success after observing poor results.

#### 10.4 Migration Cutover and Rollback Controls

Cutover should be treated as a controlled change with explicit entry criteria, execution steps, verification activities, and rollback conditions.

**Before cutover**
- Confirm that the target environment meets approved security requirements.
- Verify data synchronization and integrity.
- Confirm that required backups are available.
- Validate identity, network, logging, and monitoring controls.
- Obtain approval from service, security, data, and other required owners.
- Confirm the rollback decision-maker and communication plan.

**During cutover**
- Execute the approved migration runbook.
- Record material changes and exceptions.
- Validate application health and critical dependencies.
- Monitor security events, error rates, latency, and transaction failures.
- Preserve the ability to stop the migration if a defined threshold is breached.

**After cutover**
- Verify data integrity and business transactions.
- Confirm that old endpoints and temporary access paths are disabled or appropriately restricted.
- Rotate or revoke temporary credentials.
- Validate logging, alerts, backups, and recovery procedures.
- Obtain formal service acceptance.
- Record unresolved defects and residual risks.

Rollback should be based on predefined criteria. It may be triggered by data-integrity failures, unacceptable business disruption, security control failure, significant AI behavior regression, or inability to meet critical service objectives.

Rollback itself can introduce risk. For example, returning to the old environment may cause data divergence, duplicate transactions, or reactivation of vulnerable legacy components. These risks must be considered in the migration plan.

| Data | Are data flows, locations, and access restrictions approved? | Data inventory and data-flow assessment |

| Supplier assurance | Are provider and third-party risks reviewed? | Supplier assessment and relevant contracts |

#### 10.7 Migration Validation Evidence Pack

The migration team should maintain a structured evidence pack that allows internal audit, risk owners, security reviewers, and service owners to understand what was implemented and tested.

Typical evidence includes:

- Approved current-state and target-state architecture.
- Data-flow diagrams and data classification records.
- Framework and regulatory applicability assessment.
- Risk register and treatment decisions.
- Cloud landing-zone and security configuration results.
- Identity and access review evidence.
- Vulnerability and penetration test reports.
- AI evaluation and security testing results.
- Change approvals and migration runbooks.
- Backup, recovery, and rollback test results.
- Monitoring and incident response validation.
- Supplier assurance and contractual reviews.
- Residual risk acceptance and production release approvals.
- Post-migration findings, remediation ownership, and closure evidence.

Evidence should be traceable to specific control requirements and test outcomes. Sensitive information should be protected, and evidence retention should follow the organization's policies and applicable obligations.

**Core Principle:** Production readiness is an evidence-based decision. Successful deployment is not enough; the organization must demonstrate that security, data protection, AI behavior, resilience, and operational controls meet predefined acceptance criteria.

## Part 2 — Core Governance Principle

Enterprise AI cloud migration should be governed through an integrated lifecycle of **framework mapping, secure architecture, control implementation, risk treatment, and evidence-based release validation**.

The key conceptual distinctions are:

- **Framework adoption vs. control effectiveness:** Selecting a framework establishes structure; testing and evidence demonstrate whether controls work.
- **Cloud security vs. AI security:** Infrastructure controls protect the environment, while AI-specific controls address model behavior, data retrieval, prompt injection, and autonomous actions.
- **Migration risk vs. operational risk:** Temporary migration activities create different exposures from the ongoing operation of the target service.
- **Inherent risk vs. residual risk:** Inherent risk reflects the exposure before considering controls; residual risk reflects the remaining exposure after accounting for control effectiveness.
- **Control ownership vs. risk ownership:** Control owners operate safeguards; risk owners remain accountable for the risk and its treatment.
- **Deployment success vs. production readiness:** A workload can deploy successfully and still fail security, privacy, AI validation, or resilience requirements.
- **Provider assurance vs. customer accountability:** Cloud-provider certifications and contractual commitments support assurance but do not remove the customer's responsibility for its own systems, data, and use of AI.
- **Risk acceptance vs. compliance waiver:** Authorized risk acceptance may be possible for certain residual risks, but it cannot automatically override mandatory legal, contractual, or safety requirements.

A defensible migration program connects every material risk to a control, every control to an owner, every release condition to evidence, and every residual-risk decision to an authorized accountable decision-maker.
