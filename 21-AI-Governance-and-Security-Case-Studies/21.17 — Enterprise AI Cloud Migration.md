# 21.17 — Enterprise AI Cloud Migration
## Part 1: Business Context, Cloud Architecture, Migration Strategy, and Risk Landscape

### 1. Introduction to Enterprise AI Cloud Migration

Enterprise AI cloud migration is the process of moving AI workloads, data pipelines, machine learning models, AI-enabled applications, and supporting infrastructure from on-premises environments or existing hosting platforms into cloud environments.

The migration may involve public cloud platforms, private cloud infrastructure, hybrid environments, or multicloud architectures.

Unlike a conventional infrastructure migration, an AI cloud migration must address additional considerations involving model integrity, data governance, AI workload dependencies, training and inference requirements, model lifecycle management, third-party AI services, and the security of AI-specific interfaces.

An organization might migrate an existing machine learning platform to Microsoft Azure, deploy a generative AI application using Amazon Web Services, move analytics workloads to Google Cloud, or introduce managed AI services into an existing hybrid architecture.

Each scenario creates different technical and governance requirements.

The migration decision should not be reduced to selecting a cloud provider and moving workloads. It requires a structured assessment of business objectives, architecture, data sensitivity, regulatory obligations, security controls, operational resilience, and long-term cost.

#### 1.1 What Is Enterprise AI Cloud Migration?

Enterprise AI cloud migration involves transferring or redesigning some or all of the following components:

- AI-enabled business applications.
- Machine learning training environments.
- Model inference services.
- Generative AI applications.
- Retrieval-augmented generation (RAG) platforms.
- Vector databases and embedding services.
- Data ingestion and transformation pipelines.
- Model registries and artifact repositories.
- AI development and deployment pipelines.
- AI monitoring and observability platforms.
- Identity and access management integrations.
- Security monitoring and logging infrastructure.
- Governance, compliance, and audit evidence repositories.

The organization must determine whether each component should be migrated without modification, modernized, replaced with a managed service, or retired.

For example, a company operating an on-premises predictive maintenance platform might migrate its historical data to a cloud data platform, deploy its model through a managed inference service, and retain industrial data collection systems locally.

This would create a hybrid architecture rather than a complete migration of every component.

The resulting architecture must preserve the security and operational requirements of the original system while addressing the risks introduced by the new cloud environment.

#### 1.2 AI Cloud Migration Versus Conventional Cloud Migration

AI workloads introduce risks that are not always present in conventional infrastructure migrations.

| Dimension | Conventional cloud migration | AI cloud migration |
|---|---|---|
| Primary workload | Applications, servers, databases, and infrastructure | Applications, data pipelines, models, inference services, and AI platforms |
| Data requirements | Application data, transactional records, and configuration data | Training data, evaluation data, prompts, embeddings, model outputs, and application data |
| Integrity concerns | Application and database integrity | Application, data, model artifact, and inference integrity |
| Security architecture | Identity, network security, workload protection, and data security | Conventional controls plus AI-specific input, output, model, retrieval, and agent controls where applicable |
| Access management | User, administrator, and service identities | User, administrator, service, model-serving, pipeline, and AI tool identities |
| Deployment validation | Application functionality and performance | Application functionality plus model quality, robustness, behavior, and intended-use validation |
| Monitoring | Availability, performance, logs, and infrastructure events | Infrastructure monitoring plus model performance, data quality, drift, and AI-specific security signals |
| Change management | Application and infrastructure changes | Infrastructure, application, data, model, prompt, retrieval, and AI configuration changes |
| Third-party dependencies | Hosting, software, and infrastructure suppliers | Hosting, model providers, AI APIs, managed AI services, data providers, and supporting suppliers |
| Governance | IT governance, security, compliance, and operational risk | IT governance plus AI lifecycle governance and AI-specific risk management |

These differences do not mean that every AI system requires every possible AI-specific control. The appropriate control set depends on the use case, architecture, model type, data sensitivity, and operational consequences.

A simple internal classification model may help determine the required assurance level.

For example:

- **Low complexity:** An internal analytical model with limited data sensitivity and no consequential automated actions.
- **Moderate complexity:** An enterprise RAG application accessing confidential business documents.
- **High complexity:** An AI system processing regulated personal data or supporting consequential business decisions.
- **Critical complexity:** An AI-enabled platform supporting safety-sensitive or essential operational services.

These categories are illustrative governance groupings, not universal regulatory classifications.

**Core Principle:** AI cloud migration is an architectural and governance transformation, not merely an infrastructure relocation. The migration must preserve the integrity, confidentiality, availability, and intended behavior of the AI system while establishing controls appropriate to the new environment.

### 2. Business Context and Strategic Drivers

Organizations migrate AI workloads to the cloud for several reasons, including scalability, access to managed services, faster deployment, improved collaboration, and integration with enterprise data platforms.

However, migration introduces costs and dependencies that may offset these benefits.

A credible business case must therefore compare the expected benefits with the full lifecycle cost and risk of the proposed architecture.

#### 2.1 Common Business Drivers

**Scalability**

Cloud infrastructure can provide access to additional compute, storage, and managed AI resources when workloads increase.

This is particularly relevant to model training, large-scale inference, document processing, and variable-demand generative AI applications.

Scalability does not automatically guarantee cost efficiency. Uncontrolled resource provisioning, excessive inference requests, and inefficient model selection can create significant expenditure.

**Access to managed AI services**

Cloud providers offer managed services for model hosting, machine learning operations, data engineering, AI application development, and monitoring.

These services can reduce the operational burden of managing underlying infrastructure.

However, they may introduce provider-specific dependencies, contractual restrictions, service limitations, and data-processing considerations.

**Accelerated deployment**

Cloud platforms can provide standardized environments, deployment pipelines, and reusable infrastructure components.

This may reduce the time required to provision development, testing, and production environments.

The organization must still maintain appropriate security reviews, testing, approval gates, and segregation of duties.

**Enterprise data integration**

Cloud AI platforms can integrate with enterprise data lakes, data warehouses, application platforms, identity systems, and analytics services.

Integration can improve access to business information, but it can also increase the number of pathways through which sensitive information is accessed or exposed.

**Operational resilience**

Cloud services may provide geographically distributed infrastructure, managed backups, and recovery capabilities.

Nevertheless, resilience depends on the actual architecture, service configuration, contractual commitments, regional dependencies, and tested recovery procedures.

Moving to the cloud does not automatically eliminate outages or operational risk.

**Innovation and modernization**

Cloud migration may enable an organization to introduce new capabilities such as enterprise RAG, managed foundation models, AI-assisted analytics, and automated model deployment.

These capabilities should be introduced through approved use cases and controlled lifecycle processes.

#### 2.2 Business Objectives and Measurable Outcomes

A migration program should define business objectives before selecting the target architecture.

| Business objective | Example KPI | Governance consideration |
|---|---|---|
| Reduce infrastructure management effort | Reduction in operational hours spent maintaining AI infrastructure | Confirm that responsibility has not simply shifted to a supplier without appropriate oversight |
| Improve deployment speed | Time from approved model release to production | Preserve required security and validation gates |
| Improve workload scalability | Time required to provision approved capacity | Establish provisioning limits and resource controls |
| Improve AI service reliability | Availability against approved service objectives | Include provider and integration dependencies |
| Improve data accessibility | Percentage of approved data sources integrated successfully | Enforce data classification and access restrictions |
| Improve model lifecycle management | Percentage of production models with complete version and approval records | Ensure that records correspond to deployed artifacts |
| Improve governance visibility | Percentage of in-scope AI systems with assigned owners and current risk assessments | Define completeness criteria and accountable owners |
| Control operating expenditure | Actual cloud expenditure against approved budget | Include model inference, storage, data transfer, logging, and managed-service costs |
| Improve recovery capability | Results of recovery and continuity tests | Verify recovery of trusted configurations, data, and model artifacts |
| Reduce security exposure | Closure rate for material security findings within approved timelines | Avoid treating closure metrics as proof of control effectiveness |

These KPIs should be supported by baselines, measurement methods, accountable owners, and reporting requirements.

The organization should also define negative indicators, such as unauthorized resource provisioning, unexplained expenditure growth, unresolved critical vulnerabilities, or failures in data-residency controls.

#### 2.3 Business Case and Total Cost of Ownership

Cloud migration decisions should account for total cost of ownership (TCO), rather than comparing only the cost of on-premises servers with cloud compute prices.

A complete assessment may include:

- Cloud compute and storage.
- GPU or other specialized accelerator capacity.
- Managed AI services.
- Model inference charges.
- Data ingestion and transformation.
- Data transfer and egress.
- Vector databases and retrieval services.
- Logging, monitoring, and security tooling.
- Backup and disaster recovery.
- Licensing and software subscriptions.
- Migration services and implementation effort.
- Security assessment and compliance assurance.
- Training and organizational change.
- Supplier management and contractual oversight.
- Exit planning and potential repatriation costs.

AI workloads can be particularly sensitive to usage patterns. A model serving a large number of requests may generate substantial variable costs even when the underlying application appears inexpensive to operate.

The business case should therefore evaluate expected demand, peak demand, model choice, retention requirements, data transfer patterns, and contingency capacity.

#### 2.4 Strategic Risks of Cloud Dependency

Cloud adoption may create long-term dependencies on a provider's infrastructure, proprietary services, APIs, and operational model.

These dependencies can affect:

- Portability of applications and data.
- Ability to change model providers.
- Availability of specialized AI services.
- Negotiating leverage.
- Recovery options during provider disruption.
- Compliance with changing legal obligations.
- Costs associated with migration or termination.
- Access to operational and audit evidence.

A provider's technical capability does not remove the organization's accountability for its own risk decisions.

The enterprise should identify which services are difficult to replace and evaluate whether the resulting dependency is acceptable.

**Core Principle:** The business case for AI cloud migration must demonstrate measurable value while accounting for lifecycle costs, provider dependency, security, compliance, and resilience. Faster deployment or access to advanced AI services is not sufficient justification when the organization cannot manage the associated risks.

### 3. Reference Architecture for Enterprise AI Cloud Migration

A secure AI cloud migration begins with an understanding of the existing environment and the target architecture.

The target architecture should define where applications, data, models, identities, integrations, and governance functions will operate.

It should also distinguish the responsibilities of the cloud provider, the enterprise, and other suppliers.

#### 3.1 Existing Environment Assessment

Before designing the target state, the organization should inventory the current AI environment.

The assessment should identify:

- Applications and business processes.
- AI models and model versions.
- Data sources and data classifications.
- Training and inference environments.
- Development and deployment pipelines.
- Integration interfaces.
- Identity providers and service accounts.
- Network dependencies.
- Security and monitoring controls.
- Regulatory and contractual obligations.
- Operational support arrangements.
- Recovery and continuity requirements.

The organization should identify undocumented systems and dependencies before approving the migration plan.

An undocumented dependency may become a migration blocker if the target cloud environment cannot reproduce its functionality, security requirements, or connectivity.

#### 3.2 Target-State Architecture Layers

A reference architecture can be organized into the following logical layers.

**Layer 1 — Enterprise Identity and Governance**

This layer provides identity federation, access policies, privileged access management, governance approvals, and enterprise risk oversight.

**Layer 2 — Cloud Landing Zone**

The landing zone establishes the foundational cloud environment, including account or subscription structure, network connectivity, security policies, logging, and resource-management controls.

**Layer 3 — Data Platform**

This layer contains approved data ingestion, transformation, storage, cataloguing, classification, and access-control services.

**Layer 4 — AI Development and Model Lifecycle**

This layer supports experimentation, model training or adaptation, evaluation, artifact management, version control, and controlled deployment.

**Layer 5 — AI Inference and Application Services**

This layer hosts model endpoints, AI application services, RAG pipelines, prompt management, and approved application integrations.

**Layer 6 — Enterprise Integration**

This layer connects AI applications to business systems through controlled APIs, message interfaces, data services, and other approved integration mechanisms.

**Layer 7 — Security Monitoring and Operational Management**

This layer provides security telemetry, centralized monitoring, vulnerability management, configuration assessment, incident response, and operational reporting.

These layers are logical categories. An actual deployment may implement several of them through shared cloud services or separate technical environments.

#### 3.4 Cloud Landing Zone and Governance Guardrails

The landing zone is the foundational environment in which cloud workloads are deployed.

It should establish consistent controls before AI workloads are migrated.

Typical components include:

- Cloud account, project, or subscription structure.
- Identity federation and centralized access management.
- Network segmentation and connectivity.
- Centralized logging.
- Resource tagging and ownership.
- Approved deployment regions.
- Encryption and key-management requirements.
- Security policies and configuration baselines.
- Vulnerability management integration.
- Resource provisioning restrictions.
- Budget controls and usage monitoring.
- Backup and recovery standards.
- Policy exception management.

The organization should enforce important requirements through technical guardrails where possible.

For example, if certain data categories may only be processed in approved regions, the organization should use appropriate configuration policies and deployment controls to prevent unauthorized placement where the platform supports those controls.

However, a policy configuration is not sufficient evidence by itself. The organization must verify that the control applies to all relevant resources and that exceptions are appropriately managed.

#### 3.5 AI Workload Segregation

AI workloads should be separated according to their purpose, sensitivity, and operational risk.

A common design distinguishes:

- Development environments.
- Testing and evaluation environments.
- Pre-production environments.
- Production environments.
- Restricted data-processing environments.
- Model training environments.
- Model inference environments.
- Administrative and management environments.

The exact separation mechanisms depend on the cloud platform and enterprise requirements.

They may include separate accounts or subscriptions, projects, networks, identities, encryption keys, and access policies.

Production model artifacts should not be replaceable by an ordinary development identity. Similarly, access to sensitive training data should not automatically grant permission to deploy a model into production.

Segregation of duties is particularly important when the same platform supports data preparation, model development, model approval, and production deployment.

#### 3.6 Shared Responsibility Model

Cloud security responsibilities are divided between the provider and the customer, with the allocation depending on the service model and contractual arrangement.

| Responsibility area | Cloud provider responsibilities may include | Enterprise responsibilities typically include |
|---|---|---|
| Physical infrastructure | Data-center facilities and physical infrastructure security | Assessing provider assurance and service suitability |
| Cloud platform | Underlying infrastructure and managed platform components | Secure configuration of customer-controlled resources |
| Identity | Platform identity capabilities | User access, roles, service identities, and privileged access |
| Data protection | Available encryption and data-protection capabilities | Data classification, access policies, retention, and lawful processing |
| AI models | Operation of a provider-managed model service, where applicable | Approved use, input/output handling, application controls, and risk assessment |
| Applications | Service capabilities and underlying hosting | Application security, authorization, integration, and business logic |
| Logging | Platform logging capabilities | Appropriate configuration, retention, monitoring, and investigation |
| Vulnerability management | Security of provider-managed components within the service model | Customer-managed workloads, dependencies, and applicable remediation |
| Resilience | Service-level commitments and provider recovery mechanisms | Architecture, backups, continuity, recovery testing, and dependency management |
| Compliance | Provider certifications and assurance evidence | Determining applicability and demonstrating the organization's own compliance |

This table is a general guide, not a contractual responsibility matrix.

The organization should validate the allocation for each selected service, including managed AI platforms, foundation model APIs, data services, and supporting infrastructure.

A cloud provider's certification does not automatically establish that the customer's deployment complies with every applicable requirement.

**Core Principle:** A secure target architecture requires controlled landing zones, workload segregation, governed data and model pipelines, protected identities, and explicit responsibility allocation. Cloud security depends on both the provider's controls and the enterprise's configuration, application design, and operational governance.

### 4. AI Cloud Migration Strategies and Workload Classification

Not every AI workload should be migrated using the same strategy.

The organization should evaluate each workload according to technical compatibility, business criticality, data sensitivity, regulatory obligations, operational dependencies, and expected benefits.

A migration strategy should be selected for each workload rather than imposed uniformly across the portfolio.

#### 4.1 The Main Migration Strategies

The following categories are commonly used in cloud migration planning.

**Rehost**

Move the workload to cloud infrastructure with minimal application changes.

For example, an existing AI application may be moved to cloud-hosted virtual machines while retaining its current application architecture.

Advantages:

- Potentially faster migration.
- Limited initial application redesign.
- May reduce immediate dependence on on-premises hardware.

Limitations:

- Legacy security weaknesses may be preserved.
- Infrastructure management responsibilities may remain substantial.
- The workload may not benefit fully from managed cloud services.
- Existing AI lifecycle limitations may remain unresolved.

Rehosting should not be treated as a reason to transfer insecure configurations into the cloud unchanged.

**Replatform**

Make targeted changes to use selected cloud capabilities without fundamentally redesigning the application.

For example, an organization may move an existing AI application's database to a managed database service while retaining its main application components.

Advantages:

- Potential reduction in infrastructure management.
- Access to selected managed capabilities.
- Moderate modernization effort.

Limitations:

- Additional service dependencies.
- Changes in operational responsibility.
- Potential differences in logging, backup, and access-control behavior.

**Refactor or Rearchitect**

Redesign the application or AI platform to take advantage of cloud-native services.

For example, an organization may separate its inference service, data ingestion pipeline, model registry, and application interface into independently managed components.

Advantages:

- Greater architectural flexibility.
- Improved automation opportunities.
- Potentially stronger separation of responsibilities.
- Better integration with cloud-native monitoring and security capabilities.

Limitations:

- Higher migration complexity.
- More extensive testing and assurance requirements.
- Increased risk of introducing new defects.
- Potential changes to model behavior, latency, and cost.

**Repurchase or Replace**

Replace an internally operated AI capability with a managed or third-party AI service.

For example, an organization may replace an internally hosted text-classification model with a managed AI service.

Advantages:

- Reduced responsibility for certain infrastructure components.
- Potential access to maintained and scalable services.
- Faster availability of some capabilities.

Limitations:

- Reduced control over underlying implementation.
- Provider dependency.
- Data-processing and confidentiality concerns.
- Possible limitations on model transparency, portability, or customization.
- Contractual and service-availability risks.

**Retain**

Keep a workload in its current environment.

Retention may be appropriate when the workload has unresolved dependencies, strict latency requirements, specialized hardware, legal restrictions, or insufficient business justification for migration.

Retaining a workload does not exempt it from security or AI governance requirements.

**Retire**

Decommission a workload that is no longer needed or whose business value does not justify continued operation.

Retirement should include data disposition, credential revocation, integration removal, asset inventory updates, and evidence retention where required.

#### 4.2 Migration Strategy Comparison

| Strategy | Typical objective | Relative complexity | Principal governance concern |
|---|---|---|---|
| Rehost | Move quickly with limited redesign | Low to moderate | Preserving legacy weaknesses |
| Replatform | Improve selected platform components | Moderate | New service dependencies and configuration changes |
| Refactor | Modernize architecture | High | Migration defects, new trust boundaries, and expanded testing |
| Repurchase | Adopt a replacement service | Variable | Third-party risk, data processing, and contractual dependency |
| Retain | Keep the workload in place | Low immediate migration effort | Continuing to manage existing technical and operational risk |
| Retire | Remove an unnecessary capability | Variable | Secure decommissioning and data disposition |

These complexity ratings are indicative. Actual effort depends on workload size, integration requirements, data volumes, and the condition of the existing environment.

#### 4.3 AI Workload Classification Matrix

Before choosing a strategy, classify each workload against key characteristics.

| Classification dimension | Example categories | Why it matters |
|---|---|---|
| Business criticality | Low, moderate, high, essential | Determines availability and continuity expectations |
| Data sensitivity | Public, internal, confidential, restricted | Influences storage, access, encryption, and processing requirements |
| AI function | Predictive model, classification, RAG, generative AI, autonomous agent | Determines relevant AI-specific controls |
| Model ownership | Internally developed, adapted, third-party managed | Affects lifecycle control and assurance options |
| Operational authority | Advisory, human-approved action, autonomous action | Determines the level of authorization and oversight required |
| Regulatory exposure | Unregulated, contractually regulated, legally regulated, sector-specific | Influences applicable obligations and evidence requirements |
| Latency requirement | Flexible, time-sensitive, strict real-time | Affects architecture and placement |
| Portability | High, moderate, low | Influences provider dependency and exit planning |
| Data location constraints | Flexible, approved regions, restricted environment | Affects deployment design and legal review |
| Dependency complexity | Limited, moderate, extensive | Affects sequencing and migration risk |

This classification should be documented and reviewed by the relevant business, security, architecture, and compliance stakeholders.

#### 4.5 Migration Waves and Sequencing

Large enterprises should normally organize migration into controlled waves.

A possible sequence is:

1. Inventory and discovery.
2. Workload classification and dependency mapping.
3. Target architecture and landing-zone preparation.
4. Migration of low-risk, non-production workloads.
5. Migration of selected development and evaluation services.
6. Controlled migration of production inference services.
7. Migration or redesign of sensitive data pipelines.
8. Migration of high-criticality workloads after additional assurance.
9. Post-migration validation and optimization.
10. Retirement of obsolete infrastructure.

The sequence should be adapted to the actual environment.

A low-criticality workload is not automatically a good first migration candidate if it has complex dependencies or sensitive data.

Likewise, a technically simple workload may be a poor candidate if it supports a critical business process and lacks a validated fallback.

#### 4.6 Migration Acceptance Criteria

Before migrating a workload, the organization should define the evidence required to approve the transition.

Acceptance criteria may include:

- Business owner approval.
- Approved target architecture.
- Documented data classification.
- Validated data-transfer procedures.
- Appropriate identity and access controls.
- Approved encryption and key-management arrangements.
- Completed security assessment.
- Tested deployment and rollback procedures.
- Validated model performance.
- Confirmed monitoring and logging.
- Recovery and continuity arrangements.
- Supplier and contractual review.
- Compliance assessment.
- Documented residual-risk decisions.

For AI workloads, functional equivalence must be evaluated carefully.

A model running in a different environment may exhibit changes in latency, numerical behavior, data processing, dependency versions, or output quality.

The organization should determine whether those changes are acceptable for the approved use case.

**Core Principle:** Migration strategy must be selected according to the workload's business purpose, technical dependencies, data sensitivity, and risk profile. Rehosting, refactoring, replacing, retaining, and retiring are distinct decisions, and each requires explicit acceptance criteria.

### 5. AI Cloud Migration Risk Landscape and Threat Model

Cloud migration changes the environment in which AI systems operate.

It can introduce new identity boundaries, management interfaces, data-transfer paths, supplier dependencies, service configurations, and operational assumptions.

The organization should assess these changes before migration and validate the resulting controls after deployment.

#### 5.1 Principal Risk Categories

**Data exposure during migration**

Sensitive training data, prompts, model artifacts, business documents, or evaluation datasets may be exposed during transfer, temporary storage, or migration testing.

Potential causes include excessive permissions, insecure transfer mechanisms, public storage exposure, and inappropriate access by migration personnel.

**Cloud misconfiguration**

Cloud resources may be exposed through incorrect network rules, overly permissive identities, public endpoints, weak encryption settings, or inadequate logging.

The risk is particularly significant when migration teams create resources quickly without applying approved landing-zone controls.

**Identity and privilege compromise**

Compromised user accounts, service identities, deployment credentials, or API keys may enable unauthorized access to data, models, or production services.

Migration pipelines can be especially sensitive because they may have access to both source and destination environments.

**Model integrity compromise**

Model artifacts may be replaced, corrupted, or deployed without authorization.

This can occur through compromised repositories, insecure artifact transfer, excessive deployment permissions, or weaknesses in the model promotion process.

**Data and model incompatibility**

A migrated model may perform differently because of dependency changes, altered preprocessing, different runtime versions, numerical precision, or changed data access behavior.

The result may be reduced accuracy, increased false positives, missed anomalies, or unsuitable recommendations.

**Third-party and provider dependency**

The target architecture may rely on provider-managed models, APIs, data services, or proprietary capabilities.

Service changes, outages, contract limitations, or provider-specific restrictions can affect availability, portability, and governance.

**Regulatory and data-residency failures**

Data may be stored, processed, logged, or accessed in ways that conflict with applicable legal obligations or contractual commitments.

The organization must evaluate the actual processing arrangement rather than assuming that selecting a particular cloud region resolves all data-protection questions.

**Operational continuity failures**

The migration may disrupt dependencies, alter recovery procedures, or leave the organization unable to restore a trusted service.

The risk includes not only application downtime but also the inability to recover verified model artifacts, configuration, data, and access controls.

**AI-specific attack exposure**

Cloud-hosted AI services may be exposed to prompt injection, unsafe retrieval, unauthorized tool use, malicious input data, or misuse of model-serving interfaces, depending on their architecture.

Moving an AI application to the cloud does not automatically create these vulnerabilities, but it may change the available attack paths and control requirements.

**Uncontrolled cost and resource consumption**

Unrestricted inference endpoints, excessive model calls, oversized compute resources, or unbounded processing jobs may create substantial costs or reduce service availability.

Cost governance is therefore part of the operational risk model.

| ACM-04 | Model artifacts are altered during transfer or deployment | Untrusted or unreliable model behavior | 16 | Artifact integrity validation, protected registries, and controlled promotion |
| ACM-05 | Model performance changes after migration | Reduced decision quality or operational effectiveness | 16 | Baseline testing, representative evaluation, and post-migration monitoring |
| ACM-06 | Data residency or processing obligations are not satisfied | Regulatory or contractual breach | 20 | Legal applicability assessment, approved processing locations, and verified service configuration |
| ACM-07 | A cloud provider outage disrupts a critical AI-dependent process | Operational interruption | 16 | Resilience design, fallback procedures, and tested recovery |
| ACM-08 | Provider-specific services create excessive lock-in | Increased exit cost and reduced strategic flexibility | 12 | Portability assessment, dependency inventory, and exit planning |
| ACM-09 | Inadequate logging prevents investigation of a cloud AI incident | Delayed detection and weak accountability | 16 | Centralized logging, retention controls, alert testing, and evidence preservation |
| ACM-10 | Compromised deployment automation introduces unauthorized changes | Production compromise or service disruption | 20 | Pipeline access controls, protected credentials, approval gates, and deployment verification |
| ACM-11 | AI application interfaces are exposed to prompt injection or unsafe inputs | Data disclosure or unauthorized application behavior | 16 | Input handling, retrieval controls, output validation, and restricted tool permissions |
| ACM-12 | Unbounded AI usage causes excessive expenditure or service exhaustion | Financial loss or reduced availability | 12 | Usage quotas, rate limits, budget alerts, and anomaly monitoring |
| ACM-13 | Migration dependencies are incompletely documented | Failed migration or unexpected service interruption | 16 | Dependency mapping, integration testing, and cutover validation |
| ACM-14 | Backup and recovery procedures fail to restore a trusted AI environment | Prolonged outage or restoration of compromised artifacts | 20 | Protected backups, integrity checks, and tested recovery procedures |
| ACM-15 | Cloud-provider and enterprise responsibilities are misunderstood | Control gaps and delayed incident response | 16 | Service-specific responsibility matrix, contracts, and operational procedures |
| ACM-16 | Production migration proceeds without sufficient security and governance evidence | Unacceptable residual risk | 20 | Formal release gates, evidence requirements, and authorized risk decisions |

The scores are not universal benchmarks. For example, the impact of a residency failure depends on the data involved, applicable obligations, and the consequences of noncompliance.

#### 5.4 Risk Ownership and Accountability

Each material migration risk should have an accountable owner.

Potential responsibilities include:

| Role | Principal accountability |
|---|---|
| Executive sponsor | Business justification, funding, and strategic direction |
| Business system owner | Intended use, business requirements, and operational acceptance |
| Enterprise architect | Target architecture, integration design, and dependency mapping |
| Cloud platform owner | Landing-zone controls and cloud platform configuration |
| CISO or security leader | Cybersecurity governance and risk oversight |
| AI system owner | AI lifecycle governance, intended-use restrictions, and performance assurance |
| Data owner | Data classification, permitted use, quality, and access |
| Data protection or privacy lead | Assessment of applicable personal-data obligations |
| Legal and compliance teams | Legal applicability, contractual obligations, and compliance interpretation |
| Cloud operations team | Monitoring, service management, and operational support |
| Internal audit | Independent assurance within the approved audit mandate |
| Third-party risk team | Supplier assessment and dependency oversight |

The precise allocation depends on the organization's governance model.

Risk ownership should not be confused with control operation. A business owner may be accountable for a risk while cloud engineering, cybersecurity, or data teams implement the relevant controls.

#### 5.5 Migration Risk Assessment Method

The organization should use a repeatable assessment process.

**Step 1 — Identify the assets**

Record applications, models, datasets, identities, interfaces, infrastructure, and dependencies.

**Step 2 — Define the migration change**

Document what is changing, including the hosting model, service provider, data location, access model, runtime, and integration architecture.

**Step 3 — Identify threats and failure scenarios**

Consider malicious activity, configuration errors, supplier failures, model degradation, migration defects, and operational failures.

**Step 4 — Assess existing controls**

Determine which source-environment controls remain applicable, which require redesign, and which new controls are needed.

**Step 5 — Evaluate inherent risk**

Assess the potential likelihood and impact before considering the proposed new controls.

**Step 6 — Define treatment actions**

Specify preventive, detective, corrective, and recovery controls, together with accountable owners and target dates.

**Step 7 — Verify control effectiveness**

Review configuration evidence and conduct appropriate testing.

**Step 8 — Evaluate residual risk**

Determine what exposure remains after the controls have been implemented and tested.

**Step 9 — Obtain required approval**

Secure the decisions required by the organization's governance process before production cutover.

**Step 10 — Monitor after migration**

Reassess the system after cutover and when material changes affect the approved risk assumptions.

#### 5.6 Migration Threats Versus Steady-State Threats

Migration introduces temporary risks that differ from those present during normal cloud operations.

| Risk dimension | Migration phase | Steady-state operation |
|---|---|---|
| Identity | Temporary access across source and target environments | Ongoing access to production services |
| Data | Bulk transfer, temporary copies, staging locations | Continuous ingestion, storage, retrieval, and processing |
| Configuration | Rapid provisioning and transitional settings | Persistent configuration drift and policy exceptions |
| Model artifacts | Export, transfer, conversion, and deployment | Ongoing updates and production model management |
| Monitoring | Potential gaps between old and new tools | Continuous detection and incident response |
| Availability | Cutover, rollback, and dependency transition | Provider outages, service failures, and operational incidents |
| Governance | Migration approvals and acceptance gates | Continuous risk review and lifecycle change management |
| Supplier dependency | New contracts and service onboarding | Long-term provider dependency and exit readiness |

A migration can be secure at cutover but become insecure later if configuration drift, uncontrolled model updates, or access changes are not managed.

Conversely, a mature operational control environment cannot compensate for an unsafe migration process that exposes sensitive data or deploys unvalidated artifacts.

**Core Principle:** AI cloud migration creates both transitional and long-term risks. A defensible migration program must identify assets and dependencies, assess new attack paths, establish accountable risk ownership, verify controls, and retain evidence that the target environment meets its approved security and operational requirements.

# 21.17 — Enterprise AI Cloud Migration
## Part 2: Governance Frameworks, Cloud Security Architecture, Migration Controls, and Risk Treatment

### 6. Governance Frameworks, Standards, and Regulatory Considerations for AI Cloud Migration

Enterprise AI cloud migration must be governed as a combined **cloud transformation, cybersecurity, data governance, and AI risk management initiative**. Conventional cloud migration controls remain necessary, but AI workloads introduce additional concerns involving training data, model artifacts, inference endpoints, model behavior, AI-specific dependencies, and the potential for sensitive information to be exposed through AI interactions.

The governance objective is not simply to verify that workloads have been migrated securely. It is to demonstrate that the migrated AI environment remains appropriately controlled, legally compliant, operationally resilient, and aligned with enterprise risk appetite.

#### 6.1 Governance Frameworks and Their Roles

Different frameworks address different parts of the migration risk landscape. Organizations should avoid treating them as interchangeable certifications or assuming that adopting one framework automatically satisfies all other obligations.

| Framework or standard | Primary focus | Application to AI cloud migration | Important limitation |
|---|---|---|---|
| ISO/IEC 27001 | Information security management system | Risk assessment, security policies, control ownership, internal audits, corrective actions, and continual improvement | Does not independently provide a complete AI-specific governance framework |
| ISO/IEC 42001 | AI management system | AI governance policies, defined responsibilities, AI risk management, lifecycle controls, and continual improvement | Does not replace cloud infrastructure security or applicable legal obligations |
| ISO/IEC 27017 | Cloud-specific information security controls | Cloud service responsibilities, tenant isolation, cloud operations, and provider-customer control considerations | Must be applied in the context of the organization's broader security program |
| ISO/IEC 27018 | Protection of personally identifiable information in public clouds acting as PII processors | Privacy-related controls for applicable cloud processing arrangements | Does not cover every privacy obligation or every cloud deployment model |
| NIST Cybersecurity Framework (CSF) | Cybersecurity risk management | Organizing migration security activities around Govern, Identify, Protect, Detect, Respond, and Recover | A risk-management framework, not a substitute for detailed implementation requirements |
| NIST AI Risk Management Framework (AI RMF) | AI risk management | Governing AI use cases, measuring AI-related risks, and managing risks throughout the AI lifecycle | Does not prescribe a single mandatory cloud architecture |
| NIST SP 800-53 | Security and privacy controls | Selecting and tailoring security controls for cloud-hosted enterprise systems | Control selection must reflect the system's context and applicable requirements |
| NIST SP 800-207 | Zero Trust Architecture | Defining resource-centered access decisions, continuous evaluation, and explicit trust boundaries | Does not eliminate the need for network segmentation, identity governance, or workload protection |
| NIST SP 800-207A | Zero Trust Architecture models for access control in cloud-native applications | Informing application-level identity and access control for cloud-native environments | Implementation must be adapted to the actual platform and workload |
| CIS Critical Security Controls and applicable CIS Benchmarks | Security practices and configuration hardening | Establishing security baselines for cloud accounts, workloads, operating systems, and supported services | Recommendations must be mapped to the actual technology and operating model |
| OWASP Top 10 for LLM Applications | Common risks in LLM applications | Identifying risks such as prompt injection, sensitive information disclosure, insecure output handling, and excessive agency | Primarily application-oriented; it does not replace enterprise cloud security controls |
| Cloud Security Alliance guidance | Cloud security architecture and governance | Supporting cloud control design, shared-responsibility analysis, and cloud risk management | Guidance should be mapped to the organization's requirements and control environment |

**Governance principle:** Select frameworks according to the organization's obligations, risk profile, architecture, and assurance objectives. Maintain a control mapping that shows how each applicable requirement is implemented, tested, evidenced, and assigned to an accountable owner.

A control mapping translates broad governance requirements into concrete migration activities.

| AI risk management | Evaluate changes to model behavior, data processing, and AI dependencies | AI impact assessment and model validation report | AI Governance / Model Owner |
| Identity and access management | Redesign access permissions for cloud identities and AI services | IAM design, role assignments, access review results | IAM / Cloud Security |
| Data protection | Classify migrated data and approve destination locations | Data inventory, classification records, transfer assessment | Data Owner / Privacy |
| Secure configuration | Apply approved landing-zone and workload baselines | Configuration compliance reports | Cloud Platform / Security Engineering |
| Vulnerability management | Scan workloads, images, dependencies, and exposed services | Scan results and remediation tickets | Vulnerability Management / Engineering |

A framework mapping is not sufficient if it only states that a control is implemented. The organization needs evidence that the control operates effectively.

#### 6.3 Regulatory Applicability Assessment

Regulatory applicability depends on the organization, industry, customer locations, data subjects, processing activities, AI use case, and deployment model.

For an enterprise operating in Spain or elsewhere in the European Union, the applicability assessment may include:

- **General Data Protection Regulation (GDPR):** Personal-data processing, lawful basis, data minimization, processor relationships, international transfers, data-subject rights, security, and data protection impact assessments where required.
- **EU AI Act:** Requirements depend on the AI system's classification, intended purpose, provider/deployer role, and applicable implementation dates. Certain high-risk AI systems have additional obligations. Not every enterprise AI application is automatically classified as high-risk.
- **NIS2 Directive and national implementing legislation:** Applicability depends on the organization's sector, size, designation, and relevant national law. Organizations should not assume that every company using cloud AI is directly in scope.
- **DORA:** Relevant to financial entities and other parties within its defined scope. Cloud migration may affect ICT risk management, resilience testing, incident handling, and third-party ICT risk arrangements.
- **Sector-specific obligations:** Healthcare, telecommunications, energy, transport, and other regulated sectors may have additional security, safety, resilience, or data-handling requirements.
- **Contractual and customer requirements:** Security addenda, data residency commitments, customer assurance requirements, and industry-specific obligations may apply even where a particular regulation does not directly impose the same requirement.

The compliance team should document the applicability rationale, accountable legal or compliance reviewer, relevant requirements, required controls, and evidence needed to demonstrate compliance.

**Do not confuse cloud-provider certifications with customer compliance.** A provider's certifications may support assurance, but they do not automatically establish that the customer's AI application, data-processing activities, access controls, or operational practices comply with applicable requirements.

### 7. Secure Cloud Architecture for Enterprise AI Workloads

An AI cloud migration should establish a target architecture that separates management responsibilities, limits trust relationships, protects data, and controls how AI workloads interact with enterprise systems.

A common architectural mistake is to migrate an AI workload into a cloud environment while retaining overly permissive identities, unrestricted network access, weak data boundaries, and insufficient monitoring. Such a migration may modernize infrastructure without materially reducing security risk.

#### 7.1 Architecture Design Principles

The target architecture should implement the following principles.

**1. Identity-first security**

Every human, application, workload, model-serving component, and automation process should use a clearly defined identity. Access should be based on business need and least privilege.

Avoid relying on network location as the primary indicator of trust.

**2. Segmentation by trust boundary**

Separate production, development, testing, model training, model serving, and sensitive-data environments where their risk profiles justify separation.

Segmentation should apply to identities, networks, data stores, management planes, and service permissions—not just virtual networks.

**3. Controlled data movement**

Data should move between systems only through approved paths with defined purposes, authorization, validation, and monitoring.

A data classification label alone does not enforce security. The architecture must translate the classification into storage, access, encryption, retention, and transfer restrictions.

**4. Controlled model and artifact deployment**

Models, container images, notebooks, packages, prompts, configuration files, and supporting artifacts should be managed through controlled repositories and deployment pipelines.

Production systems should not automatically trust a model artifact simply because it was uploaded to an internal storage location.

**5. Separation of inference and administrative privileges**

A workload that serves AI inference should not automatically possess the permissions needed to administer the model platform, modify security policies, access unrelated datasets, or create additional privileged identities.

**6. Secure integration with enterprise systems**

AI services connecting to ERP, CRM, identity systems, ticketing platforms, or operational technology should use scoped APIs and narrowly defined permissions.

A model should not receive broad access to an enterprise application simply because it may need one specific business function.

The landing zone establishes the foundational controls under which cloud workloads are deployed.

| Control domain | Required capability | Example validation |
|---|---|---|
| Organizational structure | Separate production, non-production, and restricted environments as appropriate | Confirm subscription, account, project, or organizational-unit boundaries |

| Encryption | Approved encryption for data at rest and in transit | Verify encryption settings and key-access permissions |

#### 7.4 AI-Specific Architecture Controls

AI workloads require controls beyond the standard infrastructure baseline.

| AI component | Key risk | Architectural control |
|---|---|---|
| Model registry | Unauthorized or unverified model artifacts | Approved registry, provenance validation, access restrictions, and version control |
| Training pipeline | Data poisoning or unauthorized dataset changes | Dataset provenance, controlled ingestion, integrity checks, and restricted write permissions |
| Inference endpoint | Unauthorized use, abuse, or data leakage | Authenticated access, rate limits, request validation, and output monitoring |
| Retrieval-augmented generation (RAG) | Retrieval of unauthorized or poisoned content | Source validation, document-level authorization, retrieval filtering, and provenance tracking |
| Vector database | Cross-user or cross-tenant information disclosure | Strong tenant boundaries, access enforcement, and secure metadata filtering |
| Prompt and system instructions | Unauthorized changes or instruction manipulation | Version control, access restrictions, testing, and controlled deployment |
| AI agent | Excessive tool permissions or unauthorized actions | Tool mediation, scoped identities, action policies, and approval gates |
| Model evaluation service | Biased or incomplete evaluation results | Independent test datasets, documented acceptance criteria, and evidence retention |
| AI telemetry | Sensitive prompts or outputs exposed through logs | Data minimization, masking, restricted access, and retention controls |
| External model API | Unapproved transfer of sensitive information | Provider assessment, contractual review, data-flow restrictions, and approved API gateway policies |

AI-specific controls must be tested against the actual application behavior. For example, confirming that a vector database requires authentication does not prove that a user cannot retrieve another user's documents through an application-level authorization flaw.

#### 7.5 Cloud Security Architecture Review Checklist

Before approving the target architecture, reviewers should confirm:

- [ ] All AI workloads and dependencies are inventoried.
- [ ] Data flows and trust boundaries are documented.
- [ ] Production and non-production access paths are appropriately separated.
- [ ] Human and workload identities are uniquely attributable.
- [ ] Privileged access is limited and monitored.
- [ ] Public exposure is explicitly justified and approved.
- [ ] Outbound network access is controlled according to workload requirements.
- [ ] Sensitive data cannot be accessed solely by bypassing application authorization.
- [ ] Model and data artifacts have documented provenance and controlled deployment paths.
- [ ] AI agent actions are constrained by explicit tool and transaction permissions.
- [ ] Security and AI-relevant logs are collected without unnecessary sensitive-data exposure.
- [ ] Backup, restoration, and disaster recovery are tested.
- [ ] Security architecture exceptions have owners, expiry dates, and compensating controls.
- [ ] The architecture has been reviewed by the appropriate security, data, AI, and service owners.

**Core Principle:** A secure AI cloud architecture must enforce trust boundaries at identity, data, application, model, and integration layers. Network security alone cannot compensate for excessive permissions or weak application-level authorization.

### 8. Cloud Migration Security Controls and Implementation Requirements

A secure migration requires a defined control baseline, implementation ownership, validation procedures, and a process for managing exceptions. The organization should identify the controls that must be in place before data transfer, before production cutover, and during steady-state operations.

Controls should be proportionate to workload criticality, data sensitivity, AI capabilities, and potential business impact.

#### 8.1 Identity and Access Management

Cloud migration frequently changes how identities are created, how permissions are assigned, and how administrative access is performed.

Legacy systems may rely on service accounts, embedded credentials, static API keys, shared administrative accounts, or network-based trust. These mechanisms should be reviewed rather than copied into the cloud unchanged.

**Minimum implementation requirements**

1. Establish a central identity and access management model.
2. Require strong authentication for privileged and sensitive access.
3. Use role-based access control (RBAC) and, where useful, attribute-based access control (ABAC).
4. Prefer managed workload identities or short-lived credentials over long-lived secrets.
5. Separate administrative, deployment, inference, and data-access permissions.
6. Implement periodic access reviews and prompt removal of unnecessary access.
7. Record privileged activity and alert on suspicious access patterns.
8. Define break-glass access with restricted use, monitoring, and post-use review.

**Example:**

A migrated AI summarization service needs to read documents from an approved storage location and invoke an inference endpoint. It should not automatically receive permission to delete source documents, change storage policies, create cloud administrators, or read unrelated business datasets.

#### 8.2 Data Protection and Privacy

Migration changes can create new data flows, processing locations, administrative access paths, and third-party dependencies. These changes require explicit data governance.

The organization should classify data before migration and determine which controls are necessary for each data category.

| Data category | Example | Typical control considerations |
|---|---|---|
| Public | Approved public documentation | Integrity, availability, and protection against unauthorized modification |
| Internal | Internal operational procedures | Authenticated access, approved storage, and controlled sharing |
| Confidential | Business plans, internal financial records | Strong access restrictions, encryption, monitoring, and retention controls |
| Restricted | Personal data, credentials, regulated information, sensitive intellectual property | Strict authorization, data minimization, key governance, enhanced monitoring, and carefully controlled processing |
| AI training data | Curated datasets used for training or fine-tuning | Provenance, lawful use, integrity, access restrictions, and documented lineage |
| AI inference data | Prompts, uploaded files, retrieved passages, and generated outputs | Data minimization, access controls, retention decisions, output handling, and disclosure prevention |
| Model artifacts | Weights, embeddings, adapters, configuration files | Integrity, provenance, access restrictions, version control, and protection against unauthorized extraction |

The organization should also evaluate:

- Data residency and international transfer requirements.
- Whether the cloud provider acts as a processor or another legally relevant role.
- Whether prompts and outputs are retained by the service.
- Whether submitted information is used for provider model training or service improvement.
- Whether logs contain personal, confidential, or regulated information.
- Whether deletion requests can be propagated to relevant copies, indexes, caches, and derived artifacts where required.
- Whether model training or fine-tuning creates additional data protection considerations.
- Whether the new processing requires a data protection impact assessment or other formal review.

Encryption is necessary but insufficient. An authorized application that retrieves confidential data and sends it to an unapproved external AI endpoint can still cause a serious disclosure even when the data is encrypted in storage and transit.

#### 8.3 Encryption and Key Management

Encryption controls should be aligned with data classification and threat scenarios.

**At rest:** Protect databases, object storage, snapshots, backups, model repositories, and relevant temporary storage.

**In transit:** Protect data moving between users, applications, cloud services, AI endpoints, and enterprise integrations.

**Key management:** Define who can create, rotate, disable, recover, and administer cryptographic keys. Separate key administration from routine application access where appropriate.

**Customer-managed keys:** Consider them when required by policy, regulation, contractual commitments, or the risk assessment. They introduce additional operational responsibilities, including availability, rotation, recovery, and monitoring.

Validation should confirm actual configuration and access behavior rather than relying solely on a statement that the cloud service supports encryption.

#### 8.4 Network Security and Egress Control

AI workloads may communicate with model endpoints, package repositories, data sources, telemetry services, external APIs, and other enterprise systems. Uncontrolled outbound connectivity can enable data exfiltration, command-and-control communication, and unauthorized use of external AI services.

Controls should include:

- Private connectivity for sensitive services where appropriate.
- Explicitly approved inbound exposure.
- Restrictive egress policies for workloads that do not require unrestricted internet access.
- API gateways or controlled service interfaces for external integrations.
- DNS monitoring and appropriate filtering.
- Web application firewall controls for exposed web applications and APIs.
- Network segmentation between management, data, inference, and integration components.
- Monitoring for unexpected destinations, unusual transfer volumes, and anomalous service-to-service communication.

For AI applications, egress controls should account for more than malware. They should also consider whether prompts, retrieved documents, embeddings, source code, or generated outputs could be transmitted to unauthorized destinations.

Migration often involves rebuilding applications, creating new containers, changing dependencies, or moving model-serving components into managed platforms.

#### 8.6 Vulnerability and Configuration Management

Cloud migration can introduce vulnerabilities through new services, misconfigured storage, overly permissive IAM policies, exposed management interfaces, vulnerable packages, insecure containers, and unpatched operating systems.

A mature vulnerability management process should define:

1. Asset and workload discovery.
2. Vulnerability scanning and configuration assessment.
3. Risk-based prioritization.
4. Remediation ownership and target dates.
5. Exception approval and compensating controls.
6. Retesting and closure evidence.
7. Reporting of overdue critical and high-risk findings.

Prioritization should consider exploitability, internet exposure, privileges required, data sensitivity, business criticality, available mitigations, and potential impact on AI services.

For example, a vulnerable library in an isolated test environment may have a different risk profile from the same library in a publicly accessible inference service with access to confidential documents and external tools.

#### 8.7 Logging, Monitoring, and Detection

The migration should preserve or improve security visibility. Moving workloads to the cloud can fragment telemetry if each service logs independently or if cloud audit logs are not integrated into the enterprise monitoring environment.

Relevant log sources may include:

- Cloud control-plane activity.
- Identity provider and privileged-access events.
- Network flow and firewall logs.
- API gateway and application logs.
- Storage and database access logs.
- Container, virtual machine, and workload protection telemetry.
- Model endpoint invocation records.
- AI application security events.
- Agent tool invocations and transaction outcomes.
- Configuration changes and policy violations.

Logging should be designed to preserve security evidence without unnecessarily collecting sensitive prompts, personal data, secrets, or complete confidential documents.

For AI systems, monitoring may need to detect unusual inference volume, abnormal token consumption, suspicious tool invocation, repeated authorization failures, unexpected data retrieval, prompt-injection attempts, and anomalous output patterns.

#### 8.8 Control Implementation and Evidence Matrix

| Control ID | Control requirement | Implementation evidence | Test procedure | Example failure condition |
|---|---|---|---|---|
| ACM-IAM-01 | Privileged access is restricted | Role assignments and privileged-access policy | Review privileged identities and test access boundaries | Unapproved users retain administrative privileges |

| ACM-DAT-01 | Sensitive data is classified | Approved data inventory | Sample datasets and compare classifications with handling rules | Restricted data has no owner or classification |

| ACM-NET-01 | Egress is controlled | Firewall and routing policies | Attempt connections to prohibited destinations | Workload can establish unrestricted outbound connections |
| ACM-ART-01 | Production artifacts have verified provenance | Registry records, signatures, and pipeline logs | Attempt deployment of an unapproved artifact | Unverified model or container can reach production |

The evidence matrix should be linked to the enterprise risk register and control library. A control that has not been tested should not be reported as fully effective solely because the relevant configuration exists.

**Core Principle:** Migration security is demonstrated through effective, testable controls—not by architecture diagrams, cloud-provider assurances, or policy statements alone.

### 9. Migration Risk Assessment and Treatment Methodology

Enterprise AI cloud migration introduces changes to technology, data flows, identity, supplier dependencies, operating procedures, and AI behavior. Risk assessment must therefore be performed at both the migration-project level and the target-service level.

The project may complete successfully from a delivery perspective while leaving the migrated service with unacceptable residual risk. Conversely, a technically secure target architecture can still fail if migration activities cause data loss, operational disruption, or an unplanned service outage.

#### 9.1 Distinguish Migration Risks from Steady-State Risks

| Risk category | Migration-phase example | Steady-state example |
|---|---|---|
| Data confidentiality | Sensitive data copied to an unauthorized staging location | Production AI endpoint discloses confidential information |
| Data integrity | Dataset altered during transfer without detection | Unauthorized modification of model artifacts or retrieval sources |
| Availability | Cutover causes prolonged service interruption | Cloud-region or provider-service outage affects production inference |
| Identity | Legacy credentials copied into migration scripts | Excessive persistent privileges remain assigned to AI workloads |
| Network | Temporary migration connectivity exposes internal systems | Production workload permits unrestricted outbound communication |
| AI model | Model or dataset version changes without validation | Model drift or poisoned content degrades system behavior |
| Third-party dependency | Migration introduces an unassessed external service | Provider changes service behavior, retention, or availability |
| Compliance | Data moved before transfer requirements are reviewed | Ongoing processing violates an applicable contractual or legal requirement |
| Operational resilience | Rollback plan is incomplete or untested | Recovery objectives cannot be met after a major outage |
| Governance | Project bypasses required risk approvals | No accountable owner monitors the AI system after launch |

The distinction matters because a migration plan should contain temporary safeguards and exit criteria, while the production operating model must provide enduring controls.

#### 9.2 Define the Risk Assessment Scope

A complete assessment should consider:

**Business process:** What business service depends on the AI workload? What happens if the service is unavailable, inaccurate, or compromised?

**Data:** What data is collected, transferred, stored, retrieved, generated, or sent to third parties?

**AI functionality:** Is the workload performing inference, retrieval, training, fine-tuning, decision support, or autonomous actions?

**Architecture:** Which identities, APIs, cloud services, model endpoints, databases, and enterprise integrations are involved?

**Threat actors:** Could a risk arise from external attackers, malicious insiders, compromised suppliers, accidental misconfiguration, or unintended AI behavior?

**Migration method:** Will the workload be rehosted, replatformed, refactored, replaced, retained, or retired?

**Operational model:** Who owns the workload, who responds to incidents, and which responsibilities remain with the cloud provider?

**Regulatory and contractual requirements:** Which obligations apply to the service and its data flows?

**Recovery:** What service interruption, data loss, or model unavailability can the business tolerate?

#### 9.3 Risk Scoring Method

A consistent scoring model helps prioritize remediation and support governance decisions. The enterprise should use its approved risk methodology where one already exists.

A simplified illustrative model is:

**Risk Score = Likelihood × Impact**

Where:

- **Likelihood:** 1 = Rare, 2 = Unlikely, 3 = Possible, 4 = Likely, 5 = Almost Certain.
- **Impact:** 1 = Negligible, 2 = Minor, 3 = Moderate, 4 = Major, 5 = Severe.

| Score | Illustrative classification | Typical treatment |
|---:|---|---|
| 1–4 | Low | Manage through routine controls and monitoring |
| 5–9 | Moderate | Assign an owner and implement proportionate treatment |
| 10–16 | High | Prioritize treatment and require appropriate management review |
| 17–25 | Critical | Escalate promptly; production progression may need to be blocked |

These thresholds are examples, not universal risk standards. Organizations must define their own scoring scales, escalation thresholds, and risk acceptance authority.

The assessment should record inherent risk, existing controls, residual risk, treatment decisions, evidence, and reassessment triggers.

#### 9.4 Risk Treatment Options

The standard treatment options are:

- **Avoid:** Do not migrate or deploy the workload where the risk cannot be justified or managed.
- **Mitigate:** Implement preventive, detective, corrective, or resilience controls to reduce risk.
- **Transfer or share:** Allocate certain financial or contractual consequences through insurance or contractual arrangements, while recognizing that accountability and many obligations cannot simply be transferred.
- **Accept:** Formally accept residual risk through an authorized decision-maker, within the organization's risk appetite and applicable legal requirements.

Risk acceptance should not be used to bypass mandatory legal requirements or to legitimize a control failure that the organization is not authorized to waive.

#### 9.6 Risk Ownership and Escalation

Risk ownership must be assigned to individuals or roles with authority to make relevant decisions.

| Role | Principal responsibility |
|---|---|
| Executive sponsor | Owns business objectives, funding, and escalation of major delivery conflicts |
| Business service owner | Defines business impact, operational requirements, and service acceptance criteria |
| AI system owner | Owns the AI use case, intended purpose, model-related risks, and ongoing performance |
| Data owner | Approves data use, classification, access, and relevant handling requirements |
| Cloud platform owner | Owns cloud platform design, foundational controls, and platform operations |
| Information Security / GRC | Coordinates risk assessment, control mapping, risk reporting, and assurance |
| Privacy / Legal | Assesses applicable privacy, contractual, and legal obligations |
| Migration lead | Coordinates execution, cutover, dependencies, and project-level risk treatment |
| SOC / Incident Response | Defines monitoring requirements and investigates security incidents |
| Risk acceptance authority | Accepts residual risk within formally delegated authority |

The control owner is responsible for operating the control. The risk owner is accountable for the risk and its treatment decision. These roles may overlap, but they are not automatically identical.

#### 9.7 Risk Acceptance Requirements

Before accepting residual risk, the decision-maker should have access to:

1. A clear description of the risk scenario and affected business service.
2. The assessed likelihood and impact.
3. Existing controls and their effectiveness.
4. Remaining control gaps and possible treatment alternatives.
5. Business justification for acceptance.
6. Relevant legal, regulatory, contractual, and safety constraints.
7. The proposed acceptance period and review date.
8. The name of the accountable risk owner.
9. Any compensating controls and monitoring requirements.
10. Explicit approval from the appropriate authority.

Risk acceptance should be time-bound where practical and reviewed when the architecture, data, model, threat landscape, or business use changes materially.

**Core Principle:** A migration risk register is a decision instrument, not a compliance form. Every material risk must have a defined scenario, accountable owner, defensible treatment, and verifiable closure or acceptance decision.

### 10. Migration Validation, Security Testing, and Production Readiness

A workload should not be considered secure merely because it has been deployed successfully in the target cloud environment. Production readiness requires evidence that the migrated system meets functional, security, privacy, AI behavior, resilience, and operational requirements.

Testing should begin during design and continue through migration rehearsal, cutover, and post-migration validation.

#### 10.1 Establish a Validation Strategy

The validation plan should be based on the workload's criticality, architecture, data classification, AI capabilities, and identified risks.

| Test category | Objective | Example validation |
|---|---|---|
| Functional testing | Confirm that business functions work correctly | Validate expected application workflows and outputs |
| Integration testing | Confirm that connected systems exchange data correctly | Test CRM, ERP, identity, and approved API interactions |
| Identity and authorization testing | Confirm that only authorized identities can perform actions | Attempt access using unauthorized roles and accounts |
| Configuration testing | Confirm that cloud services follow approved baselines | Evaluate IAM, network, storage, encryption, and logging settings |
| Vulnerability testing | Identify known software and infrastructure weaknesses | Scan dependencies, containers, hosts, and exposed services |
| Penetration testing | Assess exploitable weaknesses under an authorized test scope | Test approved application and API attack scenarios |
| Data protection testing | Verify privacy and data-handling controls | Test access restrictions, masking, retention, and deletion workflows |
| AI security testing | Assess AI-specific attack and failure scenarios | Test prompt injection, data leakage, unsafe outputs, and unauthorized tool actions |
| Model validation | Confirm that model behavior remains acceptable | Compare relevant accuracy, quality, robustness, and drift measures |
| Performance testing | Verify performance under expected and peak load | Measure latency, throughput, and resource consumption |
| Resilience testing | Verify recovery and fault tolerance | Test restoration, failover, and degraded-service behavior |
| Operational readiness testing | Confirm that support teams can operate the service | Validate alerts, runbooks, escalation paths, and incident procedures |

The testing strategy should define test owners, environments, prerequisites, acceptance thresholds, evidence retention, and how failures affect the release decision.

#### 10.2 AI-Specific Security Test Scenarios

AI cloud migration may change model versions, inference configurations, data retrieval paths, access permissions, or provider behavior. The organization should test whether these changes introduce new risks.

**Scenario A: Sensitive information disclosure**

A user asks the AI assistant to reveal confidential information contained in a dataset they are not authorized to access.

Expected result:
- Authorization is enforced independently of the model's instructions.
- Unauthorized records are not retrieved or disclosed.
- Relevant attempts are logged in accordance with privacy and security requirements.
- The test does not depend solely on a prompt telling the model to refuse.

**Scenario B: Prompt injection through retrieved content**

A RAG application retrieves a document containing malicious instructions designed to override the application's intended behavior.

Expected result:
- Retrieved content is treated as untrusted data.
- The application does not grant the document authority to change system policy.
- Tool calls and sensitive actions remain subject to independent authorization.
- Security-relevant behavior is recorded for investigation.

**Scenario C: Unauthorized agent action**

An AI agent can create support tickets and access a business system. A test attempts to make it export a full customer database.

Expected result:
- The tool interface rejects the unauthorized operation.
- The agent's identity lacks unnecessary permissions.
- Any permitted export operation is constrained by policy and scope.
- Alerts are generated when defined suspicious activity thresholds are met.

**Scenario D: Model endpoint abuse**

A test client attempts repeated inference requests, oversized payloads, or unauthorized API calls.

Expected result:
- Authentication and authorization are enforced.
- Rate limits and resource controls operate as intended.
- Errors do not disclose secrets or internal implementation details.
- Abnormal activity can be detected and investigated.

**Scenario E: Model and data integrity**

A test attempts to deploy an unapproved model artifact or alter a production dataset outside the approved pipeline.

Expected result:
- The deployment or modification is blocked, or detected and contained according to the control design.
- Provenance and version information remain traceable.
- Relevant alerts and audit evidence are retained.

Testing must be authorized, scoped, and performed in an environment appropriate to the potential impact. Destructive tests against critical production services require explicit approval and suitable safeguards.

#### 10.3 Model and Application Baseline Comparison

Where the migration changes the model, runtime, framework, inference configuration, data pipeline, or retrieval architecture, the organization should establish a baseline before cutover.

Baseline comparison may include:

- Model version and provider configuration.
- Input and output schema.
- Quality and accuracy measures appropriate to the use case.
- Latency and throughput.
- Retrieval precision and relevance for RAG systems.
- Authorization behavior.
- Refusal behavior and handling of prohibited requests.
- Data leakage test results.
- Tool invocation patterns and action constraints.
- Cost per request or transaction.
- Error rates and availability.

A model producing broadly similar outputs does not prove that its security properties remain equivalent. For example, a migrated RAG application may retain similar answer quality while inadvertently losing document-level authorization enforcement.

Acceptance thresholds should be established before testing. Otherwise, teams may be tempted to redefine success after observing poor results.

#### 10.4 Migration Cutover and Rollback Controls

Cutover should be treated as a controlled change with explicit entry criteria, execution steps, verification activities, and rollback conditions.

**Before cutover**
- Confirm that the target environment meets approved security requirements.
- Verify data synchronization and integrity.
- Confirm that required backups are available.
- Validate identity, network, logging, and monitoring controls.
- Obtain approval from service, security, data, and other required owners.
- Confirm the rollback decision-maker and communication plan.

**During cutover**
- Execute the approved migration runbook.
- Record material changes and exceptions.
- Validate application health and critical dependencies.
- Monitor security events, error rates, latency, and transaction failures.
- Preserve the ability to stop the migration if a defined threshold is breached.

**After cutover**
- Verify data integrity and business transactions.
- Confirm that old endpoints and temporary access paths are disabled or appropriately restricted.
- Rotate or revoke temporary credentials.
- Validate logging, alerts, backups, and recovery procedures.
- Obtain formal service acceptance.
- Record unresolved defects and residual risks.

Rollback should be based on predefined criteria. It may be triggered by data-integrity failures, unacceptable business disruption, security control failure, significant AI behavior regression, or inability to meet critical service objectives.

Rollback itself can introduce risk. For example, returning to the old environment may cause data divergence, duplicate transactions, or reactivation of vulnerable legacy components. These risks must be considered in the migration plan.

## Part 2 — Core Governance Principle

Enterprise AI cloud migration should be governed through an integrated lifecycle of **framework mapping, secure architecture, control implementation, risk treatment, and evidence-based release validation**.

The key conceptual distinctions are:

- **Framework adoption vs. control effectiveness:** Selecting a framework establishes structure; testing and evidence demonstrate whether controls work.
- **Cloud security vs. AI security:** Infrastructure controls protect the environment, while AI-specific controls address model behavior, data retrieval, prompt injection, and autonomous actions.
- **Migration risk vs. operational risk:** Temporary migration activities create different exposures from the ongoing operation of the target service.
- **Inherent risk vs. residual risk:** Inherent risk reflects the exposure before considering controls; residual risk reflects the remaining exposure after accounting for control effectiveness.
- **Control ownership vs. risk ownership:** Control owners operate safeguards; risk owners remain accountable for the risk and its treatment.
- **Deployment success vs. production readiness:** A workload can deploy successfully and still fail security, privacy, AI validation, or resilience requirements.
- **Provider assurance vs. customer accountability:** Cloud-provider certifications and contractual commitments support assurance but do not remove the customer's responsibility for its own systems, data, and use of AI.
- **Risk acceptance vs. compliance waiver:** Authorized risk acceptance may be possible for certain residual risks, but it cannot automatically override mandatory legal, contractual, or safety requirements.

A defensible migration program connects every material risk to a control, every control to an owner, every release condition to evidence, and every residual-risk decision to an authorized accountable decision-maker.

## Part 3: Migration Execution, Operational Governance, Continuous Monitoring, and Incident Response

### 11. Enterprise AI Cloud Migration Execution Strategy

Enterprise AI cloud migration requires more than transferring applications, databases, and model artifacts into a cloud environment. It requires coordinated execution across infrastructure, data, AI services, cybersecurity, business operations, and governance.

The migration team must maintain control over the entire transition, including temporary environments, data movement, identity changes, model deployment, integration testing, production cutover, and retirement of legacy components.

A migration can meet its delivery deadlines and still fail from a governance perspective if the organization loses control of sensitive data, introduces unapproved AI services, weakens security boundaries, or cannot demonstrate that the migrated system behaves as intended.

The objective is therefore to execute migration activities through controlled workstreams, explicit decision gates, measurable acceptance criteria, and traceable evidence.

#### 11.1 Establish the Migration Workstreams

A complex enterprise AI migration should be divided into coordinated workstreams with clear ownership.

| Workstream | Primary responsibilities | Key deliverables | Accountable owner |
|---|---|---|---|
| Program governance | Scope, budget, schedule, dependencies, steering decisions, and escalation | Program plan, governance calendar, decision log | Program Sponsor / Program Director |
| Enterprise architecture | Target architecture, technology selection, integration patterns, and design standards | Approved target architecture and architecture decisions | Enterprise Architect |
| Cloud platform | Landing zone, account structure, network foundation, platform services, and resource provisioning | Operational cloud foundation | Cloud Platform Owner |
| Cybersecurity | Security architecture, threat modeling, control implementation, vulnerability management, and security testing | Security assessment, control evidence, remediation plan | Security Lead |
| AI governance | AI inventory, use-case assessment, model validation, intended-purpose review, and lifecycle governance | AI risk assessment, model evaluation, AI approval records | AI Governance Lead |
| Data governance | Data classification, migration mapping, quality, lineage, retention, and access controls | Data inventory, lineage records, transfer approvals | Data Governance Lead |
| Privacy and legal | Privacy assessment, contractual review, data transfer requirements, and regulatory applicability | Privacy assessment, legal review, compliance decisions | Privacy / Legal |
| Application migration | Refactoring, application deployment, dependency management, and functional validation | Migrated application and test results | Application Owner |
| Model engineering / MLOps | Model packaging, registry management, deployment pipeline, evaluation, and rollback | Approved model artifacts and deployment evidence | AI Platform / Model Owner |
| Integration | APIs, event streams, identity federation, enterprise connections, and transaction validation | Tested integration interfaces | Integration Lead |
| Operations and resilience | Monitoring, incident response, backups, recovery, service desk, and support transition | Runbooks, service-level objectives, recovery procedures | IT Operations |
| FinOps | Budgeting, tagging, consumption monitoring, cost optimization, and forecasting | Cost baseline, budget controls, financial reporting | FinOps Lead |
| Internal audit / assurance | Independent review of governance, control design, evidence, and risk acceptance | Assurance findings and audit evidence | Internal Audit / Assurance |

Internal audit should retain appropriate independence from the teams implementing the migration. It can provide assurance and challenge the evidence, but it should not become the operational owner of the controls it is expected to evaluate independently.

#### 11.2 Define Migration Execution Phases

A practical execution model divides the migration into controlled phases.

| Phase | Principal activities | Exit criteria |
|---|---|---|
| Phase 1: Discovery | Inventory applications, models, datasets, integrations, identities, and dependencies | Scope and dependency inventory approved |
| Phase 2: Assessment | Evaluate business criticality, data sensitivity, technical readiness, and risks | Migration strategy and risk treatment approved |
| Phase 3: Foundation | Build the landing zone, security baselines, identity controls, network boundaries, and logging | Foundation passes required validation |
| Phase 4: Preparation | Clean data, resolve dependencies, prepare deployment artifacts, and establish test environments | Workloads and datasets meet migration prerequisites |
| Phase 5: Pilot | Migrate a limited workload to validate the approach | Pilot acceptance criteria satisfied |
| Phase 6: Migration waves | Execute prioritized migrations with controlled change windows | Each workload passes its wave-specific exit criteria |
| Phase 7: Production cutover | Switch approved traffic and business processes to the target environment | Production service passes cutover validation |
| Phase 8: Stabilization | Monitor service health, security, AI behavior, and business performance | Service meets agreed stability criteria |
| Phase 9: Legacy retirement | Decommission obsolete components, credentials, routes, and data copies | Retirement verified and residual dependencies resolved |
| Phase 10: Operational handover | Transfer ownership to operational teams and establish ongoing assurance | Service owner formally accepts the operating model |

The organization should not assume that all workloads must follow the same sequence. A low-risk internal summarization service may need a different migration path from an AI system that supports financial transactions, customer identity verification, or critical infrastructure operations.

#### 11.3 Workload Prioritization and Migration Waves

Migration sequencing should balance business value, technical complexity, risk, and dependency constraints.

A workload can be technically easy to migrate but unsuitable for an early wave if it processes highly sensitive data or has untested dependencies.

An illustrative prioritization matrix is shown below.

| Workload profile | Business criticality | Technical complexity | Risk exposure | Suggested approach |
|---|---|---|---|---|
| Internal knowledge assistant using approved public documents | Low to moderate | Low | Low to moderate | Candidate for an early pilot |
| Enterprise RAG application containing confidential internal documents | Moderate to high | Moderate | High if authorization is weak | Migrate after document-level access controls are validated |
| AI service integrated with CRM and customer personal data | High | High | High | Require detailed privacy, integration, and security validation |
| AI fraud detection system supporting financial transactions | High | High | High | Use controlled migration waves, parallel validation, and strong rollback capability |
| AI system used in safety-critical operational decisions | Very high | High | Potentially severe | Require sector-specific assurance, safety analysis, and tightly controlled change approval |
| Legacy AI workload with unsupported dependencies | Variable | Very high | High or uncertain | Assess refactoring, replacement, isolation, or retirement before migration |

Prioritization should consider:

- Business criticality and the impact of service interruption.
- Data classification and sensitivity.
- AI autonomy and potential consequences of incorrect outputs.
- Regulatory and contractual obligations.
- Technical dependencies and integration complexity.
- Cloud service maturity and provider limitations.
- Security testing requirements.
- Recovery capability and rollback complexity.
- Availability of skilled operational support.
- Cost and resource constraints.

**Important distinction:** Migration priority is not the same as business importance. A critical business workload may deserve early investment and planning while being deliberately scheduled for a later production migration because its risk and dependency profile require more preparation.

#### 11.5 Data Migration Integrity and Chain of Custody

Data migration is a major control point because data can be lost, corrupted, duplicated, exposed, or transformed incorrectly during extraction, transfer, conversion, loading, and indexing.

AI workloads create additional complexity because the relevant information may exist in multiple forms:

- Original source datasets.
- Cleaned or transformed datasets.
- Training and validation datasets.
- Model artifacts and checkpoints.
- Embeddings and vector indexes.
- Retrieval metadata and document permissions.
- Cached prompts and responses.
- Evaluation datasets and results.
- Audit records and operational logs.

A controlled data migration process should establish:

**Source authorization:** Confirm that the organization is authorized to migrate and process the data.

**Data classification:** Apply the appropriate handling requirements before extraction and transfer.

**Transfer protection:** Use approved transfer methods, encryption, access controls, and logging.

**Integrity verification:** Validate record counts, checksums where applicable, schema consistency, and representative business records.

**Transformation validation:** Document and test changes to data formats, fields, encodings, schemas, or normalization procedures.

**Access validation:** Confirm that data permissions remain correct after migration.

**Lineage preservation:** Maintain traceability between original sources, transformed data, indexes, and relevant model artifacts.

**Retention and deletion:** Verify how temporary copies, staging files, legacy data, and redundant artifacts are handled.

**Exception management:** Record unexplained discrepancies, failed transfers, missing records, and deviations from the approved migration plan.

For RAG systems, validating the number of migrated documents is insufficient. The organization must also validate document metadata, access-control attributes, index freshness, retrieval behavior, and authorization enforcement.

For machine learning systems, dataset integrity alone does not establish model validity. The organization should separately evaluate whether the migrated model produces acceptable results under the target runtime and operating conditions.

#### 11.6 Migration Execution Metrics

The migration program should measure progress without confusing delivery activity with security effectiveness.

| Metric | Definition | Governance purpose |
|---|---|---|
| Workload migration completion | Percentage of in-scope workloads migrated and accepted | Measures delivery progress |
| Migration failure rate | Percentage of migration attempts that fail defined acceptance criteria | Identifies execution instability |
| Critical dependency closure | Percentage of critical dependencies resolved or formally accepted | Measures readiness |
| Security control compliance | Percentage of applicable controls passing defined validation | Measures control implementation |
| Open critical findings | Number of unresolved critical security or compliance findings | Supports release decisions |
| Data integrity exception rate | Number of unresolved data discrepancies relative to the migration scope | Identifies data migration defects |
| AI evaluation pass rate | Percentage of required AI test cases meeting approved acceptance criteria | Measures AI validation outcomes |
| Rollback readiness | Percentage of workloads with validated rollback procedures | Measures recovery preparedness |
| Operational handover completion | Percentage of required runbooks, owners, and support procedures accepted | Measures operating-model readiness |
| Cost variance | Difference between forecast and actual migration or operating costs | Supports financial governance |
| Post-migration incident rate | Security and service incidents attributable to migrated workloads | Measures stabilization outcomes |

Each metric should have a defined calculation, reporting frequency, owner, target, and escalation threshold.

A high migration completion rate does not demonstrate a secure migration. It must be considered alongside unresolved findings, control effectiveness, data integrity, service availability, and AI validation results.

**Core Principle:** Migration execution should be governed at the workload and wave levels, with explicit entry criteria, tested rollback capability, and independent evidence that the target service is ready for operation.

### 12. AI Cloud Operational Governance and Shared Responsibility

After migration, the enterprise must transition from project governance to continuous service governance. This is a substantive change: the migration program is temporary, but the obligations to manage security, AI risk, privacy, cost, resilience, and supplier dependencies continue for the life of the service.

The organization must define who operates each control, who responds when a control fails, and who has authority to accept or escalate the resulting risk.

#### 12.1 Understand the Cloud Shared-Responsibility Model

Cloud providers and customers have different responsibilities depending on the service model and the contractual arrangement.

In general, infrastructure as a service (IaaS) leaves the customer with substantial responsibility for operating systems, workloads, network configuration, identities, applications, and data. Platform as a service (PaaS) transfers more underlying infrastructure responsibilities to the provider. Software as a service (SaaS) transfers more of the application operation to the provider, but the customer still retains responsibilities for its users, data, configuration, business processes, and appropriate use of the service.

AI services introduce additional distinctions. The provider may operate the foundation model and inference infrastructure, while the customer remains responsible for the application design, access permissions, prompt construction, retrieved data, tool permissions, and business decisions made using the outputs.

The exact boundary must be confirmed using provider documentation, the service contract, and the actual deployment architecture.

| Responsibility | IaaS | PaaS | SaaS / managed AI service |
|---|---|---|---|
| Physical data center security | Primarily provider | Primarily provider | Primarily provider |
| Physical host infrastructure | Primarily provider | Primarily provider | Primarily provider |
| Guest operating system | Usually customer | Usually provider for managed platform components | Usually provider |
| Application code | Customer | Customer for customer-developed applications | Provider for the core SaaS application; customer may manage extensions |
| Cloud identity configuration | Shared according to service | Shared according to service | Shared according to service |
| Data classification and lawful use | Customer | Customer | Customer |
| Application-level authorization | Customer | Customer | Shared; customer must validate available configuration and enforcement |
| AI prompt and workflow design | Customer | Customer | Customer for customer-defined workflows and integrations |
| Foundation model infrastructure | Depends on deployment | Often provider-managed | Usually provider-managed |
| Customer-specific AI agent permissions | Customer | Customer | Customer where the service exposes configurable tools or integrations |
| Security logging configuration | Shared | Shared | Shared, depending on service capabilities |
| Data retention and deletion configuration | Customer-controlled where supported | Shared | Depends on the service and contract |
| Incident response | Shared | Shared | Shared, with provider and customer responsibilities defined contractually |
| Regulatory compliance | Shared obligations; customer remains accountable for its applicable obligations | Shared obligations; customer remains accountable for its applicable obligations | Shared obligations; customer remains accountable for its applicable obligations |

This table is illustrative. It should not be used as a contractual responsibility matrix without verifying the exact service.

#### 12.2 Create a Service Responsibility Matrix

The organization should document responsibilities for each production AI service rather than assuming that generic cloud documentation covers all operational details.

A service responsibility matrix should identify:

- Control or operational activity.
- Cloud provider responsibility.
- Enterprise responsibility.
- Service owner.
- Operational team.
- Required evidence.
- Escalation route.
- Review frequency.
- Relevant contractual commitment or service limitation.

Example:

| Operational activity | Provider responsibility | Enterprise responsibility | Enterprise evidence |
|---|---|---|---|
| Underlying infrastructure maintenance | Operate provider-managed infrastructure | Understand service dependencies and review assurance | Provider assurance documentation |
| Identity configuration | Supply supported identity capabilities | Configure identities, permissions, and authentication requirements | IAM review and access logs |
| Data access | Operate service components according to service design | Define data access policy and validate enforcement | Access-control tests |
| AI model version changes | Provide documented service behavior and applicable change information | Assess impact and validate suitability where possible | Model-change review and evaluation results |
| Application integration | Operate provider APIs according to contractual service commitments | Secure API credentials, scopes, and business logic | Integration test results |
| Service incident | Investigate provider-side issues within contractual scope | Detect customer-side incidents, report issues, and coordinate response | Incident records and escalation evidence |
| Data deletion | Execute supported deletion mechanisms according to service commitments | Initiate deletion, verify completion where possible, and manage customer-controlled copies | Deletion records and verification results |
| Recovery | Maintain provider-defined resilience capabilities | Define business recovery requirements and test customer recovery procedures | Recovery plan and exercise results |

The organization should identify gaps where the provider does not expose sufficient configuration, logging, or validation capability. Such gaps may require compensating controls, architectural changes, supplier escalation, or a decision not to use the service for a particular workload.

#### 12.4 Define Decision Rights

Unclear decision rights are a common governance weakness. Teams may identify a serious problem but lack clarity about who can stop a release, disable an AI feature, authorize a temporary exception, or accept residual risk.

| Decision | Recommended accountable authority | Required consultation |
|---|---|---|
| Approve target cloud architecture | Designated architecture authority | Cloud, security, AI, data, application owners |
| Approve AI use case for production | Designated AI governance and business approval authorities | Legal, privacy, security, data owner |
| Approve migration cutover | Authorized change or service-release authority | Migration lead, operations, security, service owner |

Decision rights should be documented in policies, runbooks, and service procedures. High-impact actions should not depend on informal assumptions about who has authority.

#### 12.5 Change Management for Cloud and AI Services

Cloud AI services can change through infrastructure configuration, application deployment, model version updates, data pipeline modifications, prompt changes, provider updates, and changes to connected tools.

Not every change requires the same level of review. The organization should use risk-based change classification.

| Change type | Example | Typical governance treatment |
|---|---|---|
| Routine infrastructure change | Approved patch under a tested standard procedure | Standard change controls and validation |
| Security configuration change | Modification to firewall or IAM policy | Security impact assessment and appropriate approval |
| Model version change | Replacement of the production model | Model evaluation, regression testing, and change approval based on impact |
| Data pipeline change | New data source added to training or retrieval | Data governance review, security assessment, and relevant validation |
| AI prompt or policy change | Modification to system instructions or action rules | Version control, abuse-case testing, and approval appropriate to risk |
| New tool integration | AI agent gains access to a CRM or financial system | Threat assessment, permission review, transaction controls, and authorization tests |
| Provider service change | Provider changes model behavior or service capabilities | Impact assessment and monitoring, subject to available change information |
| Emergency security change | Rapid restriction of compromised credentials | Emergency authorization, evidence preservation, and post-change review |

For AI systems, change management should consider not only whether the software was deployed correctly but also whether the change alters the system's intended purpose, decision impact, data processing, autonomy, or risk profile.

### 13. Continuous Security Monitoring and AI Cloud Risk Indicators

Continuous monitoring provides evidence about whether the migrated environment remains within approved security, operational, and AI risk limits.

A point-in-time assessment cannot establish that a cloud AI service will remain secure. Cloud configurations change, identities accumulate permissions, vulnerabilities emerge, model behavior shifts, datasets evolve, providers update services, and attackers adapt their techniques.

Monitoring should therefore combine cloud security telemetry, application and identity events, AI-specific signals, business-service performance, and governance indicators.

#### 13.1 Establish a Layered Monitoring Model

An effective monitoring model covers several complementary domains.

**Cloud control plane:** Detect unauthorized resource creation, security-policy changes, public exposure, changes to logging, and privileged administrative actions.

**Identity and access:** Detect unusual authentication, suspicious privilege escalation, credential misuse, and access inconsistent with normal workload behavior.

**Network and infrastructure:** Monitor unusual traffic, unexpected egress, exposed services, resource abuse, and anomalous communication.

**Application and API:** Detect authorization failures, unusual request patterns, abuse of business functions, and suspicious input or output behavior.

**Data security:** Monitor unusual data access, mass downloads, unauthorized transfers, unexpected changes to datasets, and violations of data-handling policies.

**AI application and model:** Monitor prompt-injection indicators, unsafe outputs, unexpected model behavior, unauthorized retrieval, model endpoint abuse, and anomalous tool invocation.

**Business service:** Monitor availability, latency, transaction failures, model quality, and the business impact of degraded or incorrect AI behavior.

**Governance:** Monitor overdue risk treatments, expired exceptions, failed control tests, and unapproved changes.

No single telemetry source is sufficient. For example, a cloud audit log may show that an AI endpoint was invoked, but it may not reveal whether the application returned information to an unauthorized user.

#### 13.2 Define Security Monitoring Use Cases

| Use-case ID | Detection scenario | Relevant telemetry | Example response |
|---|---|---|---|
| ACM-MON-01 | Public exposure of a restricted storage resource | Cloud configuration and audit events | Validate exposure, restrict access, and investigate potential disclosure |
| ACM-MON-02 | Privileged role assigned outside the approved workflow | IAM audit events and change records | Revoke unauthorized access and investigate the initiating identity |
| ACM-MON-03 | Unusual outbound transfer from an AI workload | Network flow, firewall, and application logs | Investigate destination and content classification; contain if warranted |
| ACM-MON-04 | Unusual volume of AI inference requests | Endpoint metrics, application logs, and identity events | Apply rate limits, investigate abuse, and assess cost impact |
| ACM-MON-05 | Attempts to retrieve unauthorized documents | Retrieval logs and authorization failures | Validate access enforcement and investigate repeated attempts |
| ACM-MON-06 | AI agent invokes a high-impact tool unexpectedly | Agent telemetry, tool audit logs, and transaction records | Suspend affected tool access and assess completed actions |
| ACM-MON-07 | Unapproved model artifact deployed | Registry, pipeline, and deployment events | Stop or roll back the deployment and verify artifact provenance |
| ACM-MON-08 | Security logging disabled or altered | Cloud audit logs and monitoring configuration | Restore logging, investigate the change, and preserve available evidence |
| ACM-MON-09 | Sudden deterioration in model quality | Evaluation metrics, drift indicators, and business feedback | Investigate data or model changes and apply predefined fallback procedures |
| ACM-MON-10 | Unexpected cloud cost spike associated with AI inference | Billing telemetry, endpoint usage, and request metrics | Identify the driver, apply approved limits, and assess service abuse |
| ACM-MON-11 | Unapproved external model endpoint introduced | Application configuration, network telemetry, and change records | Block or restrict the endpoint and investigate data exposure |
| ACM-MON-12 | Repeated failed authorization followed by successful access | Identity, application, and data-access logs | Investigate possible credential compromise or authorization bypass |

Detection logic should be tuned to the environment. Excessive alerts can overwhelm responders, while overly restrictive thresholds can conceal genuine attacks or operational failures.

#### 13.3 Monitor AI-Specific Risks

Traditional cloud monitoring should be supplemented with AI-specific monitoring appropriate to the application.

**Prompt injection:** Identify known patterns and suspicious attempts to override system instructions, manipulate retrieved content, or induce prohibited actions. Detection must not depend exclusively on keyword matching because prompt injection can be indirect or expressed in many forms.

**Sensitive information disclosure:** Monitor for unauthorized retrieval and output of protected data, while minimizing the sensitive content collected in telemetry.

**Unauthorized tool use:** Record tool invocations, the requesting identity, authorization result, action parameters where appropriate, and transaction outcome.

**Model abuse:** Detect anomalous request volume, repeated policy violations, unusual query patterns, and resource consumption that may indicate misuse.

**Retrieval security:** Monitor access-denied events, unusual document-access patterns, and changes to retrieval indexes or source permissions.

**Model and data integrity:** Track approved model versions, relevant dataset versions, registry changes, pipeline provenance, and unexpected changes to model behavior.

**Model drift:** Detect changes in input characteristics, output quality, error rates, or other measures appropriate to the use case.

**AI reliability:** Track unsupported answers, failed requests, confidence or uncertainty indicators where meaningful, and business outcomes. These indicators should be interpreted carefully because many AI systems do not provide calibrated confidence estimates.

**Agentic behavior:** Monitor repeated tool calls, unexpected action sequences, excessive retries, privilege-boundary violations, and attempts to perform operations outside the approved workflow.

A monitoring system should distinguish between suspicious activity, confirmed control violations, and normal model variability. A single unusual output is not necessarily evidence of a security incident, but a repeated pattern of unauthorized retrieval or prohibited tool execution warrants investigation.

#### 13.4 Establish KPIs, KRIs, and Control Effectiveness Indicators

Key performance indicators (KPIs) measure operational performance or progress. Key risk indicators (KRIs) provide warning signals about changing exposure. Control effectiveness indicators assess whether a control is functioning as intended.

These measures should not be treated as interchangeable.

| Indicator | Type | Illustrative measure | Governance interpretation |
|---|---|---|---|
| Production workload coverage | KPI | Percentage of in-scope workloads onboarded to approved monitoring | Identifies visibility gaps |
| Critical alert acknowledgement time | KPI | Time between alert generation and acknowledgement | Measures response performance |
| Mean time to contain | KPI | Time between incident confirmation and effective containment | Measures containment effectiveness |
| Unresolved critical vulnerabilities | KRI | Count of unresolved critical vulnerabilities beyond the approved deadline | Indicates exposure requiring escalation |
| Excessive privilege findings | KRI | Number of material least-privilege violations | Indicates access-control weaknesses |
| Unapproved external AI connections | KRI | Count of detected connections to prohibited or unassessed services | Indicates potential data and supplier risk |
| Failed retrieval authorization tests | Control effectiveness indicator | Percentage of required tests passing | Measures retrieval access-control effectiveness |
| AI abuse-test pass rate | Control effectiveness indicator | Percentage of required abuse cases meeting acceptance criteria | Measures tested AI safeguards |
| Model evaluation regression | KRI | Change in predefined model-quality or safety measures | Indicates potential degradation |
| Expired risk exceptions | KRI | Number of active exceptions beyond their approved expiry date | Indicates governance-process failure |
| Logging coverage | Control effectiveness indicator | Percentage of required event types successfully collected and validated | Measures monitoring coverage |
| Recovery-test success rate | Control effectiveness indicator | Percentage of required recovery tests meeting objectives | Measures recovery readiness |
| AI service availability | KPI | Availability against the agreed service objective | Measures service reliability |
| AI cost variance | KRI / financial indicator | Actual usage or cost compared with approved thresholds | Indicates potential inefficiency or abuse |

Thresholds should be defined according to business criticality and risk appetite. The same model-quality regression or response delay may have very different implications for a low-impact internal assistant and an AI system supporting high-impact business decisions.

#### 13.5 Example Executive Risk Dashboard

An executive dashboard should present the information required to make decisions, not merely display large volumes of telemetry.

| Domain | Status measure | Example escalation condition | Required management response |
|---|---|---|---|
| Security posture | Critical vulnerabilities and control failures | A release-blocking finding remains unresolved | Require remediation or formally block the affected release |
| Data protection | Unauthorized data access and transfer indicators | Credible evidence of sensitive-data disclosure | Initiate incident response and applicable notification assessment |
| AI behavior | Quality, safety, and policy compliance measures | A predefined high-impact failure threshold is breached | Restrict functionality, activate fallback, or suspend the affected use |
| Identity | Privileged access and access-review findings | Unauthorized high-privilege access is confirmed | Revoke access and investigate |
| Resilience | Recovery readiness and service availability | Recovery capability fails to meet approved objectives | Escalate and implement remediation |
| Supplier risk | Provider incidents and unresolved assurance gaps | Provider issue threatens a critical service or obligation | Invoke supplier escalation and continuity arrangements |
| Governance | Overdue risk actions and expired exceptions | Material risk remains without valid ownership or approval | Escalate to the appropriate risk authority |
| Financial | Consumption and cost variance | Usage exceeds an approved limit or indicates possible abuse | Investigate, constrain usage, and adjust forecasts |

The dashboard should show trends, ownership, deadlines, and decisions required. Green status should be supported by valid evidence; it should not mean simply that no alert was generated.

#### 13.6 Continuous Control Validation

Controls can degrade without an obvious security incident. A policy may be changed, a new cloud service may be deployed, an identity may accumulate permissions, or a logging integration may silently stop working.

Continuous control validation should therefore test selected controls repeatedly.

Examples include:

- Periodic checks that restricted storage cannot become publicly accessible.
- Automated verification of required logging and retention settings.
- Regular review of privileged identities and workload permissions.
- Detection of unapproved cloud regions or AI endpoints.
- Validation that production model deployment follows the approved pipeline.
- Automated checks for required resource tags and ownership metadata.
- Recurring tests of document-level authorization in RAG systems.
- Periodic review of AI agent tool permissions.
- Scheduled restoration tests for representative workloads.
- Verification that risk exceptions remain valid and have not expired.

Automated validation should have a documented response path. Detecting a failed control without assigning an owner, defining remediation, and tracking closure does not establish effective control management.

#### 13.7 Monitoring Limitations and False Confidence

Monitoring is a detective capability, not a replacement for preventive controls.

Several limitations require explicit attention:

- Some AI security failures are difficult to detect from outputs alone.
- Providers may not expose all relevant model telemetry.
- Logs may be incomplete, delayed, or unavailable during an incident.
- Excessive logging can create additional privacy and confidentiality risks.
- A lack of alerts does not prove that the system is secure.
- Model behavior can change without a conventional software deployment.
- Detection models can produce false positives and false negatives.
- Attackers may exploit gaps between cloud, application, and AI telemetry.
- Monitoring may identify an event without proving whether protected information was disclosed.

The organization should document monitoring limitations, compensating controls, and residual risk. Where essential visibility cannot be obtained, the risk assessment should consider whether the workload remains suitable for the service.

**Core Principle:** Continuous monitoring must connect technical signals to risk thresholds, accountable owners, and predefined response actions. Visibility without effective response is not a complete security control.

### 14. AI Cloud Incident Response, Business Continuity, and Recovery

Enterprise AI cloud incidents can affect confidentiality, integrity, availability, regulatory compliance, financial performance, and trust in automated decisions.

The incident may originate in the cloud infrastructure, application code, identity platform, data pipeline, model provider, retrieval system, AI agent, or a connected enterprise service. Effective response requires coordination across cybersecurity, cloud operations, AI engineering, data governance, privacy, legal, business continuity, and service ownership.

Incident response must also account for a distinctive AI challenge: an AI system may continue operating while producing unsafe or unauthorized results. A service can remain technically available even when its business behavior is no longer trustworthy.

#### 14.1 Define AI Cloud Incident Categories

| Incident category | Example | Potential impact |
|---|---|---|
| Cloud infrastructure compromise | Unauthorized administrative access to the cloud environment | Data exposure, service manipulation, or broader compromise |
| Identity compromise | Stolen workload credentials used to access production resources | Unauthorized data access or control-plane changes |
| Data breach | Confidential documents exposed through a storage or retrieval misconfiguration | Privacy, contractual, legal, and reputational consequences |
| Prompt injection | Malicious instructions cause an AI application to disregard intended restrictions | Unauthorized retrieval or prohibited actions |
| AI agent misuse | Agent invokes an authorized tool for an unauthorized purpose | Unauthorized transactions, changes, or data exports |
| Model artifact compromise | Unapproved model or configuration deployed into production | Manipulated outputs or compromised behavior |
| Data poisoning | Malicious or corrupted content influences training or retrieval | Degraded reliability, manipulated results, or unsafe recommendations |
| Service outage | Cloud provider or model endpoint becomes unavailable | Business interruption or loss of critical functionality |
| AI behavior regression | Model update causes unacceptable errors or policy violations | Incorrect decisions, customer harm, or operational disruption |
| Provider security incident | A third-party AI or cloud service experiences a security event | Exposure or disruption depending on the provider's role and data access |
| Resource abuse | Automated requests cause excessive consumption or unexpected costs | Financial loss and potential service degradation |
| Compliance incident | Data is processed or transferred contrary to applicable requirements | Legal exposure, remediation costs, and potential notification obligations |

Incident classification should be based on impact and the nature of the event, not only on the technical source.

#### 14.2 Establish the AI Cloud Incident Response Lifecycle

The incident response process should align with the enterprise incident management framework while adding AI-specific investigation and containment activities.

```text id="s4nq2c"
                    PREPARATION
                         |
                         v
                 DETECTION AND REPORTING
                         |
                         v
                TRIAGE AND CLASSIFICATION
                         |
                         v
             CONTAINMENT AND RISK REDUCTION
                         |
                         v
               INVESTIGATION AND EVIDENCE
                         |
                         v
              ERADICATION AND REMEDIATION
                         |
                         v
              RECOVERY AND SERVICE VALIDATION
                         |
                         v
              BUSINESS AND GOVERNANCE REVIEW
                         |
                         v
               LESSONS LEARNED AND CONTROL
                       IMPROVEMENT
```

**Preparation:** Define response roles, service inventories, escalation contacts, evidence requirements, recovery options, and provider communication procedures.

**Detection and reporting:** Identify suspicious activity through monitoring, user reports, provider notifications, and control failures.

**Triage and classification:** Determine the affected service, likely scope, potential data exposure, business impact, and urgency.

**Containment:** Restrict access, disable compromised credentials, suspend risky tools, isolate affected workloads, or activate safe fallback behavior.

**Investigation:** Establish what happened, which identities and resources were involved, what data was accessed, and whether AI-generated actions caused downstream consequences.

**Eradication:** Remove unauthorized access, correct configurations, replace compromised artifacts, and address the underlying weakness.

**Recovery:** Restore the service using trusted components and validate security, data integrity, AI behavior, and operational readiness.

**Review and improvement:** Document root causes, corrective actions, residual risks, and changes required to prevent recurrence.

#### 14.3 AI-Specific Containment Strategies

Containment should be proportional to the incident and designed to limit harm while preserving necessary evidence.

| Incident scenario | Potential containment action | Key consideration |
|---|---|---|
| Compromised workload identity | Disable or rotate credentials and revoke affected permissions | Determine whether other identities or services were also compromised |
| Unauthorized model endpoint exposure | Restrict network access and enforce authentication | Check whether data or model artifacts were accessed |
| RAG authorization bypass | Disable affected retrieval paths or restrict the application to safe datasets | Preserve evidence and validate document-level authorization before reactivation |
| Prompt injection leading to unsafe behavior | Disable affected tools or suspend the risky workflow | Do not rely solely on rewriting the prompt if the underlying authorization weakness remains |
| Unauthorized AI agent transaction | Suspend the relevant tool or agent capability and contact the business system owner | Identify completed actions and assess reversal or remediation options |
| Unapproved model deployment | Roll back to a trusted version if appropriate and preserve the deployed artifact for investigation | Verify provenance and evaluate whether data or configuration changes persist |
| Data poisoning suspicion | Isolate affected data sources or model versions and suspend use where justified | Preserve source data and lineage evidence for forensic analysis |
| External AI service disclosure | Restrict the affected integration and prevent further sensitive-data transmission | Establish what information was sent and evaluate contractual and legal obligations |
| Cloud provider outage | Activate an approved fallback or recovery arrangement | Consider data consistency, model availability, and dependency limitations |
| AI output quality failure | Disable high-impact automated decisions or require human review | Determine whether the failure affects prior decisions or transactions |

Containment should not destroy evidence unnecessarily. For example, deleting a compromised model artifact immediately may eliminate useful forensic evidence. Where practical, preserve relevant artifacts securely before replacement, subject to incident urgency and legal requirements.

#### 14.4 Incident Response Roles and Escalation

The incident response plan should define roles before an incident occurs.

| Role | Principal responsibility during an incident |
|---|---|
| Incident Commander | Coordinates response priorities, decisions, and cross-functional activity |
| Security Operations / Incident Response | Detects, investigates, contains, and coordinates technical response |
| Cloud Platform Team | Investigates cloud resources, identity events, network activity, and platform changes |
| AI / Model Engineering | Assesses model versions, evaluation results, behavior changes, and AI-specific failure modes |
| Application Owner | Evaluates application functionality, authorization, integrations, and business consequences |
| Data Owner | Assesses affected datasets, access scope, integrity, and recovery requirements |
| Privacy / Data Protection Officer, where applicable | Advises on personal-data exposure, assessment, and relevant notification obligations |
| Legal / Compliance | Assesses legal, contractual, regulatory, and evidence-preservation requirements |
| Business Service Owner | Determines business impact and approves relevant service-continuity decisions |
| Supplier / Provider Management | Coordinates escalation with cloud and AI providers |
| Communications / Public Relations | Manages approved external communications where required |
| Executive Risk Authority | Makes decisions on material business exposure and risk acceptance |
| Internal Audit / Independent Assurance | Provides appropriate independent review after the incident, without replacing operational response |

The organization should define severity levels, escalation timelines, decision authority, and communication channels in its incident response policy.

#### 14.5 AI Cloud Incident Severity Model

A severity model helps prioritize response and escalation.

| Severity | Illustrative criteria | Example response |
|---|---|---|
| SEV-1: Critical | Confirmed major compromise, significant sensitive-data exposure, severe business disruption, or unsafe high-impact automated actions | Immediate escalation, incident command, containment, and executive notification |
| SEV-2: High | Significant control failure or suspected compromise with credible potential for material impact | Urgent investigation, restricted operation where necessary, and senior security oversight |
| SEV-3: Moderate | Limited incident or control weakness with contained impact | Assigned investigation, documented remediation, and regular status reporting |
| SEV-4: Low | Minor anomaly or low-impact issue without evidence of material compromise | Routine investigation and tracking under normal procedures |

These are illustrative categories. Organizations should define severity based on their own incident classification scheme, regulatory obligations, service criticality, and potential harm.

A high-impact AI failure may warrant severe classification even when no conventional cyberattack is identified. For example, an AI agent that executes a large number of unauthorized transactions may create a critical business incident even if the cloud infrastructure itself remains uncompromised.

#### 14.6 Evidence Preservation and Investigation

AI cloud investigations may require evidence from several layers.

Relevant evidence includes:

- Cloud administrative and audit logs.
- Identity-provider authentication and privilege events.
- Network and API gateway telemetry.
- Application logs and transaction records.
- Model version, configuration, and deployment history.
- Relevant prompt, response, and tool-invocation metadata.
- Data access and retrieval records.
- Dataset and model artifact provenance.
- Pipeline execution history.
- Configuration and policy changes.
- Provider incident notifications and service status records.
- Backup and recovery records.
- User reports and timestamps.
- Relevant change approvals and risk decisions.

The organization should preserve evidence according to its incident response procedures and applicable legal requirements.

AI evidence collection requires particular care. Prompts, retrieved documents, generated responses, and tool parameters may contain personal data, credentials, confidential business information, or sensitive intellectual property. Evidence collection should be targeted, access-restricted, and documented.

Investigators should distinguish among:

1. **Observed facts:** Events supported by logs, records, or validated evidence.
2. **Technical hypotheses:** Explanations that remain under investigation.
3. **Confirmed root causes:** Causes supported by sufficient evidence.
4. **Business impact:** Actual or reasonably established consequences.
5. **Potential impact:** Consequences that may have occurred but remain unconfirmed.

This distinction prevents incident reports from overstating certainty.

#### 14.7 Business Continuity and Disaster Recovery

AI cloud services should have recovery strategies based on business criticality and dependencies.

Recovery planning should consider:

- Cloud-region and availability-zone failures.
- Cloud provider service disruption.
- Model endpoint unavailability.
- Third-party API failure.
- Loss or corruption of model artifacts.
- Loss of retrieval indexes or data pipelines.
- Compromised deployment credentials.
- Ransomware or destructive administrative actions.
- Network connectivity failures.
- Excessive inference costs or resource exhaustion.
- Security incidents requiring temporary service shutdown.

The business impact analysis should determine recovery time objectives (RTOs) and recovery point objectives (RPOs), where applicable.

**Recovery Time Objective (RTO):** The target time within which a service should be restored after disruption.

**Recovery Point Objective (RPO):** The target maximum amount of data loss measured in time that the organization is prepared to tolerate.

These objectives must be approved by the business and translated into technically feasible recovery designs.

#### 14.8 Recovery Strategies for AI Workloads

| Recovery strategy | Description | Suitable considerations |
|---|---|---|
| Restore from backup | Recover data, configuration, or artifacts from protected backups | Backup integrity, recovery speed, and restoration testing |
| Redeploy from trusted artifacts | Rebuild workloads using approved source code, images, and deployment pipelines | Artifact provenance and integrity |
| Roll back model version | Return to a previously validated model or configuration | Compatibility, known defects, and data consistency |
| Fail over to an alternate region | Operate from a separate approved cloud region | Data replication, regional availability, legal constraints, and cost |
| Use an alternate model endpoint | Route inference to another approved model service | Behavioral equivalence, data-transfer implications, and provider dependency |
| Switch to deterministic fallback | Use predefined rules or a non-AI workflow when AI is unavailable or untrusted | Business suitability and validation of fallback behavior |
| Require human review | Suspend automated decisions and route cases to authorized personnel | Human capacity, service delay, and review quality |
| Disable selected AI tools | Continue limited functionality while removing risky capabilities | Dependency mapping and operational impact |

Fallback arrangements must be tested. An alternate model may not behave identically to the primary model, and a manual fallback may not have enough staffing capacity to sustain the business service for an extended period.

#### 14.9 AI-Specific Recovery Validation

Before restoring a service to normal operation, the organization should verify more than basic infrastructure health.

Validation should confirm:

- The deployed model and configuration are approved.
- The deployment pipeline and artifacts are trusted.
- Required security patches and configuration fixes are applied.
- Relevant credentials have been rotated or revoked.
- Data integrity has been checked.
- Retrieval indexes and document permissions are consistent.
- Access-control enforcement has been retested.
- Relevant AI abuse and regression tests pass.
- Agent tool permissions remain within the approved scope.
- Monitoring and alerting operate correctly.
- Business transactions and dependent systems are functioning as expected.
- Required incident-related approvals are recorded.

If the incident involved a model or data integrity compromise, restoration should not rely solely on the assumption that the previous version was safe. The organization should verify provenance and determine whether the incident could have affected the supposedly trusted baseline.

#### 14.10 Post-Incident Review and Corrective Actions

After containment and recovery, the organization should conduct a structured review.

The review should address:

- What happened and when.
- Which systems, identities, data, models, and business processes were affected.
- How the incident was detected.
- Whether existing controls operated as intended.
- Which control gaps contributed to the event.
- Whether provider or supplier actions contributed.
- Whether notification, reporting, or contractual obligations were triggered.
- Whether AI outputs or automated actions caused downstream consequences.
- Whether recovery objectives were achieved.
- Which corrective actions are required.
- Who owns each action and when it must be completed.
- Whether the risk assessment and AI system record require updates.
- Whether similar weaknesses exist in other migrated workloads.

Corrective actions should address root causes rather than only the immediate symptoms.

For example, if prompt injection causes an AI agent to export unauthorized information, changing the prompt may reduce one attack pattern but does not resolve the fundamental problem if the agent still has excessive export permissions. A durable correction would include authorization enforcement at the tool boundary, reduced permissions, relevant testing, and monitoring.

#### 14.11 Incident Response and Recovery Exercise Program

The organization should validate its procedures through tabletop exercises, technical simulations, and recovery tests appropriate to the system's risk.

Example exercises include:

| Exercise | Scenario | Key learning objective |
|---|---|---|
| Tabletop exercise | External AI provider reports a potential data exposure | Validate escalation, supplier communication, and privacy assessment |
| Identity compromise simulation | Workload identity is used to access unauthorized resources | Validate containment, credential rotation, and scope investigation |
| RAG authorization exercise | Users can retrieve documents outside their permissions | Validate detection, containment, and access-control remediation |
| AI agent exercise | An agent attempts an unauthorized high-impact transaction | Validate tool shutdown, transaction investigation, and business recovery |
| Model integrity exercise | An unapproved model version is deployed | Validate artifact provenance, rollback, and release controls |
| Cloud outage exercise | The primary inference service becomes unavailable | Validate fallback behavior and business continuity |
| Data recovery exercise | Retrieval indexes or required datasets become corrupted | Validate restoration, integrity checks, and lineage |
| Logging failure exercise | Security telemetry stops reaching the central monitoring platform | Validate detection of monitoring failure and restoration |
| Ransomware or destructive-action exercise | Critical cloud resources or artifacts are rendered unavailable | Validate protected backups, recovery access, and rebuild procedures |

Exercise findings should be tracked to closure. A successful exercise is not simply one in which the service is restored; it is one that tests whether people, controls, evidence, and decision-making work under realistic conditions.

**Core Principle:** AI cloud incident response must address both infrastructure compromise and unsafe AI behavior. Effective recovery requires trusted artifacts, validated data integrity, restored authorization boundaries, tested AI behavior, and a formal decision to resume normal operations.

## Part 3 — Core Governance Principle

Enterprise AI cloud migration must transition from a controlled delivery project into a continuously governed production service. The organization needs clear ownership, secure execution, measurable monitoring, and tested incident response to maintain control over the migrated environment.

The key conceptual distinctions are:

- **Migration delivery vs. migration assurance:** Completing a migration wave does not prove that the workload meets security and governance requirements.
- **Business criticality vs. migration priority:** A highly critical service may require more preparation and therefore be migrated later.
- **Cloud provider responsibility vs. enterprise accountability:** Providers operate defined service components, but customers remain responsible for their own data use, configurations, business processes, and applicable obligations.
- **KPI vs. KRI vs. control effectiveness indicator:** Performance measures delivery, risk indicators signal changing exposure, and control indicators assess whether safeguards work.
- **Monitoring vs. prevention:** Detection provides visibility but does not replace preventive controls or effective response.
- **Technical availability vs. trustworthy AI behavior:** An AI service can be online while producing unsafe, unauthorized, or materially incorrect outputs.
- **Containment vs. eradication:** Containment limits immediate impact; eradication addresses the underlying compromise or weakness.
- **Infrastructure recovery vs. service recovery:** Restoring cloud resources is insufficient unless data integrity, access control, AI behavior, and business functionality are also validated.
- **Risk ownership vs. incident execution:** The incident commander coordinates the response, while designated risk and business owners retain their respective decision-making responsibilities.
- **Successful recovery vs. completed remediation:** Restoring the service does not close the incident's underlying control weaknesses; corrective actions must be tracked and verified.

A mature AI cloud operating model connects every production workload to accountable owners, validated controls, actionable monitoring, tested recovery procedures, and a continual process for reducing residual risk.

# 21.15 — Autonomous AI Agent with Tool Access
## Part 4: Implementation Roadmap, Governance Operating Model, Audit Readiness, and Executive Risk Decisions

### 21. Enterprise Implementation Roadmap for Autonomous AI Agents

Deploying an autonomous AI agent in an enterprise requires a controlled implementation program that integrates business objectives, AI governance, cybersecurity, identity management, operational controls, legal compliance, and risk management.

Unlike a conventional software deployment, an agent's risk profile depends not only on its software configuration but also on its autonomy, model behavior, available tools, data sources, and authority to execute actions.

An agent that initially provides recommendations may become substantially riskier when granted permission to execute transactions, modify enterprise records, communicate externally, or administer infrastructure.

Consequently, implementation must establish a clear relationship between **business value, authorized autonomy, enforceable controls, and accepted residual risk**.

#### 21.1 Implementation Principles

The following principles should guide the implementation program.

| Principle | Implementation requirement | Governance objective |
|---|---|---|
| Business-purpose limitation | Define the business problem and permitted activities | Prevent unauthorized expansion of the agent's purpose |
| Risk-based autonomy | Assign autonomy according to the potential consequences of an action | Prevent disproportionate operational authority |
| Least privilege | Grant only the permissions required for approved tasks | Limit the impact of misuse or compromise |
| Independent enforcement | Enforce action restrictions outside the model's reasoning process | Prevent model instructions from becoming the sole security boundary |
| Human accountability | Assign accountable business and technical owners | Establish clear decision rights |
| Secure-by-design architecture | Incorporate security and privacy controls before deployment | Reduce the cost and complexity of remediation |
| Continuous assurance | Monitor behavior and periodically validate controls | Detect deterioration and changing risks |
| Controlled change | Assess material model, prompt, tool, and permission changes | Maintain the validity of the original risk assessment |
| Evidence-based approval | Require documented evidence before production release | Support auditability and management accountability |
| Reversibility | Establish suspension, rollback, and recovery procedures | Reduce the consequences of unsafe behavior |

These principles should be embedded in the enterprise AI governance framework and applied consistently across agent development, procurement, deployment, and retirement.

**Phase 1 — Business Definition**

The business owner defines the intended outcome, users, operating environment, and permitted activities.

Key activities:

- Document the business case and expected benefits.
- Identify the process the agent will support.
- Define permitted and prohibited actions.
- Establish the maximum acceptable level of autonomy.
- Identify affected stakeholders and enterprise systems.
- Determine whether a non-agentic solution would satisfy the requirement with less risk.

Deliverables include an approved business case, use-case definition, and preliminary autonomy classification.

**Phase 2 — Agent Inventory and Risk Classification**

The organization records the agent in its AI inventory and evaluates its risk.

Key activities:

- Identify the model, orchestration platform, tools, and external dependencies.
- Classify the data the agent can access.
- Assess the consequences of incorrect or unauthorized actions.
- Determine whether the agent affects regulated processes or sensitive information.
- Identify applicable legal, contractual, and internal policy requirements.
- Assign accountable owners.

Deliverables include an AI inventory record, preliminary risk assessment, and initial risk register.

**Phase 3 — Architecture and Threat Modeling**

Security and architecture teams define how the agent will operate and where controls must be enforced.

Key activities:

- Document the agent's architecture and data flows.
- Identify trust boundaries.
- Map every tool and its permissions.
- Analyze prompt injection, data exfiltration, identity abuse, and unauthorized execution scenarios.
- Assess delegation, memory, retrieval, and third-party dependencies.
- Define logging, monitoring, and incident-response requirements.

Deliverables include architecture diagrams, threat models, trust-boundary documentation, and a security requirements specification.

**Phase 4 — Control Design and Implementation**

Technical teams implement the controls required by the approved risk treatment plan.

Key activities:

- Establish the agent's identity and access permissions.
- Configure tool allowlists and action-level authorization.
- Implement human approval workflows for sensitive operations.
- Apply data classification, filtering, and output restrictions.
- Configure execution limits, timeouts, and circuit breakers.
- Implement protected logging and monitoring.
- Establish emergency-stop and recovery mechanisms.

Deliverables include implemented control configurations, testable security requirements, and updated technical documentation.

**Phase 5 — Security Testing and Validation**

The organization tests whether the agent and its controls behave as intended.

Key activities:

- Perform functional and integration testing.
- Test authorization and least-privilege boundaries.
- Conduct adversarial testing and prompt-injection assessments.
- Test prohibited actions and approval bypass attempts.
- Validate data-access restrictions.
- Test emergency-stop, recovery, and failure-mode behavior.
- Record findings, remediation activities, and residual risks.

Deliverables include test plans, results, remediation evidence, and a control-effectiveness assessment.

**Phase 6 — Controlled Pilot**

The agent operates within a limited and closely monitored scope.

Key activities:

- Limit access to approved users and systems.
- Restrict the agent to a narrow set of tools.
- Prefer read-only or recommendation-only operation where feasible.
- Require human approval for state-changing operations.
- Monitor execution traces, errors, policy denials, and business outcomes.
- Collect feedback from users and control owners.
- Evaluate whether the initial risk assumptions remain valid.

Deliverables include pilot results, operational metrics, updated risk assessments, and recommendations for production readiness.

**Phase 7 — Production Authorization**

The authorized release authority determines whether the agent may enter production.

Key activities:

- Confirm that mandatory security controls are operational.
- Review unresolved high-risk findings.
- Verify that required approvals and contractual obligations are satisfied.
- Confirm that incident-response procedures have been tested.
- Review residual-risk assessments.
- Obtain formal acceptance from the authorized risk owner.
- Define the approved operating scope and restrictions.

Deliverables include a production release decision, residual-risk acceptance record where required, and operational handover documentation.

**Phase 8 — Continuous Monitoring and Assurance**

The organization maintains oversight throughout the agent's operational life.

Key activities:

- Monitor security and operational indicators.
- Review changes to models, prompts, tools, and permissions.
- Reassess risks after material changes or incidents.
- Conduct periodic access reviews and control testing.
- Track exceptions and remediation deadlines.
- Review continued business justification.
- Suspend or retire the agent when the approved conditions are no longer satisfied.

Deliverables include monitoring reports, periodic assurance results, updated risk registers, and documented decisions concerning continued operation.

#### 21.3 Implementation Gate Criteria

Each phase should have explicit exit criteria.

| Gate | Required decision | Example failure condition |
|---|---|---|
| Business gate | Is the use case justified and sufficiently defined? | No accountable business owner |
| Risk gate | Are material risks identified and assigned? | Critical risks remain unidentified or unowned |
| Architecture gate | Are trust boundaries and tool permissions documented? | Unrestricted access to production systems |
| Control gate | Are mandatory controls implemented? | Sensitive actions bypass the authorization layer |
| Testing gate | Have required security tests passed? | Unauthorized actions can be executed |
| Pilot gate | Is behavior acceptable under real operating conditions? | Repeated unexplained policy violations |
| Production gate | Is the residual risk formally acceptable? | Mandatory control deficiencies remain unresolved |
| Operational gate | Can the enterprise monitor, contain, and recover from failures? | No effective emergency-stop or incident-response process |

A failed gate should trigger remediation, scope reduction, or a formal rejection decision. The project schedule should not override mandatory security requirements.

### 23. Governance Operating Model, RACI, and Decision Rights

An autonomous AI agent requires an operating model that connects business accountability, AI governance, cybersecurity, technology operations, legal compliance, and independent assurance.

Without clearly assigned responsibilities, technical teams may implement controls without owning business consequences, while business teams may authorize capabilities without understanding their security implications.

The operating model must establish who can propose, approve, operate, suspend, and retire the agent.

#### 23.1 Core Governance Roles

| Role | Primary responsibility |
|---|---|
| Executive sponsor | Confirms strategic alignment and provides executive oversight |
| Business owner | Owns the use case, business outcomes, and operational consequences |
| AI system owner | Coordinates the agent's lifecycle and governance obligations |
| Technical owner | Maintains the implementation, integrations, and technical configuration |
| AI governance function | Maintains governance standards, inventory requirements, and oversight processes |
| Information security | Defines security requirements and evaluates threats and controls |
| IAM team | Manages identities, permissions, authentication, and credential controls |
| Data owner | Approves data access, classification, and permitted uses |
| Privacy or data protection function | Assesses applicable privacy obligations and associated risks |
| Legal and compliance | Interprets relevant legal, contractual, and regulatory requirements |
| Model or AI engineering team | Maintains model configuration, evaluations, and model-related safeguards |
| Application owner | Maintains connected systems and their native authorization controls |
| Security operations | Monitors alerts, investigates suspicious activity, and coordinates containment |
| IT operations or SRE | Maintains service reliability, recovery, and operational procedures |
| Internal audit | Independently evaluates governance and control effectiveness |
| Risk acceptance authority | Accepts residual risk within formally delegated authority |

One person may hold multiple roles in a smaller organization, but incompatible duties should remain appropriately separated. For example, the person responsible for implementing a control should not automatically be the sole independent assessor of that control's effectiveness.

#### 23.2 RACI Matrix

RACI means:

- **R — Responsible:** Performs the work.
- **A — Accountable:** Owns the outcome and final decision.
- **C — Consulted:** Provides required input.
- **I — Informed:** Receives relevant information.

The following matrix is illustrative and should be adapted to the enterprise's organizational structure.

| Activity | Business owner | AI governance | Security | Technical owner | Legal/privacy | Risk authority | Internal audit |
|---|---|---|---|---|---|---|---|
| Define business use case | A/R | C | C | C | C | I | I |
| Register the AI agent | C | A/R | C | R | I | I | I |
| Classify agent risk | A | R | R | C | C | C | I |
| Approve security architecture | C | C | A | R | C | I | I |
| Define tool permissions | C | I | A/C | R | I | I | I |
| Approve data access | C | I | C | R | C | A/R where delegated | I |
| Conduct security testing | I | C | A/R | R | C | I | I |
| Approve production release | A/C | C | C | R | C | A where delegated | I |
| Monitor operational performance | A | C | C | R | I | I | I |
| Respond to security incidents | I | C | A/R | R | C | I | I |
| Accept residual risk | C | C | C | C | C | A/R | I |
| Conduct independent assurance | I | C | C | C | C | I | A/R |
| Approve material changes | A/C | C | C | R | C | A where delegated | I |
| Retire the agent | A | C | C | R | C | C | I |

**Important:** A RACI matrix is not a substitute for a formal delegation-of-authority policy. The enterprise must explicitly identify which role has final authority for production release, acceptance of high residual risk, and suspension or reactivation following a significant incident.

#### 23.3 Governance Decision Rights

The following decisions should have explicit approval requirements.

**Business-purpose approval**

The business owner determines whether the use case is justified and whether the expected benefits warrant the associated risks.

**Technical design approval**

Architecture and security stakeholders determine whether the proposed design meets mandatory security and operational requirements.

**Data-access approval**

Relevant data owners authorize the agent's access according to data classification, business purpose, and applicable obligations.

**Production release approval**

The designated release authority confirms that mandatory controls are operational and that the agent's operating scope is approved.

**Residual-risk acceptance**

The formally authorized risk owner accepts remaining risk within the enterprise's delegated risk appetite and approval thresholds.

**Emergency suspension**

Designated operational or security personnel must be able to suspend the agent or restrict its tools when predefined incident criteria are met. Emergency containment should not depend on obtaining routine project approval.

**Post-incident reactivation**

The organization defines who may authorize reactivation after a significant security incident and what evidence must be available before the decision.

**Material change approval**

Changes to model capabilities, permissions, tools, autonomy, data access, or business purpose must be assessed to determine whether additional testing or approval is required.

#### 23.4 Three Lines and Independent Assurance

The Three Lines Model can help structure governance responsibilities.

| Line | Typical participants | Responsibility |
|---|---|---|
| First line | Business owner, application owner, engineering, IT operations | Owns and manages operational risks and controls |
| Second line | Enterprise risk, AI governance, compliance, information security oversight | Establishes frameworks, challenges risk decisions, and monitors compliance |
| Third line | Internal audit | Independently assesses governance, risk management, and control effectiveness |

The exact organizational allocation varies. In some enterprises, security engineering operates as part of the first line while security risk oversight sits in the second line.

The important requirement is that independent oversight remains meaningful and that operational ownership is not confused with independent assurance.

### 24. Key Performance Indicators, Key Risk Indicators, and Executive Reporting

Enterprise leadership needs evidence that an autonomous AI agent is delivering value without exceeding its approved risk boundaries.

Key Performance Indicators (KPIs) measure business or operational performance. Key Risk Indicators (KRIs) signal increasing exposure or deterioration in risk conditions.

A balanced scorecard should include both.

#### 24.1 Business and Operational KPIs

| KPI | Purpose | Example measurement |
|---|---|---|
| Task completion rate | Measures the percentage of tasks completed successfully | Successful tasks divided by eligible tasks |
| Mean time to resolution | Measures average time required to resolve an eligible issue | Average elapsed time from incident acceptance to resolution |
| Human intervention rate | Measures how frequently human assistance is required | Tasks requiring intervention divided by total tasks |
| First-pass resolution rate | Measures how often tasks are resolved without rework | Tasks resolved on the first attempt divided by eligible tasks |
| Cost per completed task | Measures operational cost efficiency | Total attributable operating cost divided by completed tasks |
| Tool execution success rate | Measures whether authorized tool calls complete successfully | Successful authorized calls divided by attempted authorized calls |
| User satisfaction | Measures user experience where applicable | Approved satisfaction survey metric |
| Service availability | Measures the availability of the agent service | Availability calculated under the approved service definition |

These metrics must be interpreted in context. A high task-completion rate does not establish that the agent performed the correct actions or complied with security requirements.

#### 24.2 Security and Governance KRIs

| KRI | Risk represented | Example escalation condition |
|---|---|---|
| Confirmed unauthorized action count | Failure of action authorization | Any confirmed prohibited execution |
| Sensitive-data disclosure incidents | Confidentiality and privacy exposure | Any confirmed unauthorized disclosure |
| High-risk policy violations | Agent activity outside approved boundaries | Any material violation |
| Excessive permission findings | Identity and access-control weakness | Any unresolved critical permission issue |
| Human approval bypass rate | Failure of oversight controls | Any confirmed bypass of a mandatory approval |
| Prompt-injection success rate | Susceptibility to malicious instruction manipulation | A test or incident demonstrates an unsafe control bypass |
| Unresolved high-severity findings | Accumulated control deficiencies | Any finding beyond its approved remediation deadline |
| Incident containment time | Ability to limit operational damage | Exceeds the established incident-response objective |
| Unreviewed material changes | Weak change governance | Any production change lacking required approval |
| Overdue access reviews | Weak identity lifecycle governance | Required review remains incomplete beyond the approved deadline |
| Logging coverage gaps | Reduced investigation capability | A required execution path lacks sufficient audit evidence |
| Repeated execution anomalies | Potential loops, misuse, or unstable behavior | Exceeds an approved threshold or triggers a critical event |

Thresholds should be risk-based and formally approved. For some events, such as confirmed unauthorized execution of a privileged production action, the appropriate threshold is zero.

#### 24.4 Escalation and Management Actions

Reporting should connect indicators to predefined actions.

| Condition | Expected management response |
|---|---|
| Task performance declines | Investigate technical failures, workflow design, and model behavior |
| Policy denials increase unexpectedly | Investigate attack attempts, configuration changes, or incorrect tool selection |
| Unauthorized action is confirmed | Contain the agent, investigate, and initiate the incident-response process |
| A critical security finding remains open | Restrict deployment or suspend affected capabilities according to policy |
| Agent permissions exceed the approved scope | Remove excessive permissions and assess potential exposure |
| A material model or tool change is proposed | Conduct change assessment and required regression testing |
| Risk exceeds approved tolerance | Reduce autonomy, restrict scope, suspend operations, or escalate for a formal decision |
| Business benefits no longer justify operating costs or risk | Reassess the business case and consider retirement |

Management reporting should distinguish between indicators requiring routine investigation and events requiring immediate containment.

### 25. Final Governance Decision, Residual Risk, and Continuous Improvement

The final governance decision determines whether the agent should be approved, restricted, returned for remediation, suspended, or rejected.

This decision must consider the entire operating environment, not just the model's technical performance.

#### 25.1 Production Approval Criteria

Before production authorization, the organization should confirm the following.

| Domain | Required confirmation |
|---|---|
| Business justification | The use case has an approved purpose and accountable owner |
| Risk assessment | Material risks have been identified and assigned |
| Architecture | Trust boundaries and enterprise integrations are documented |
| Identity | The agent has a distinct and appropriately controlled identity |
| Authorization | Tool and action permissions enforce the approved operating scope |
| Data governance | Data access and processing are appropriately authorized |
| Human oversight | Required approval and escalation processes are operational |
| Security testing | Mandatory functional and adversarial tests have passed |
| Monitoring | Security and operational monitoring are active |
| Incident response | Containment, investigation, and recovery procedures are defined and tested |
| Auditability | Required activity and control decisions can be reconstructed |
| Change management | Model, prompt, tool, and policy changes are controlled |
| Legal and compliance | Applicable obligations have been assessed and addressed |
| Third-party assurance | Relevant vendor and contractual risks have been assessed |
| Residual risk | Remaining risk is documented and accepted by the authorized authority |
| Operational readiness | Support, maintenance, recovery, and retirement responsibilities are assigned |

A checklist is evidence of review, not an automatic approval mechanism. Any failed mandatory requirement must be handled under the organization's security and risk policies.

#### 25.2 Residual-Risk Assessment

Residual risk is the risk remaining after the planned or implemented controls have been considered.

The organization should evaluate:

- The probability of an adverse event.
- The potential business, financial, operational, legal, and reputational impact.
- The effectiveness of preventive, detective, and corrective controls.
- Dependencies on model providers, tools, and external services.
- Remaining uncertainties in model behavior.
- The extent of human oversight.
- The agent's ability to affect critical systems or sensitive data.
- The ability to detect, contain, and recover from failures.

Residual risk must not be accepted solely because a project has reached its target launch date or because the vendor claims that the model is secure.

The acceptance authority must have sufficient information and delegated authority to make the decision.

#### 25.3 Autonomy-Based Release Decisions

The organization can use different release decisions depending on the agent's demonstrated controls and remaining risk.

| Release option | Operating model | Appropriate governance condition |
|---|---|---|
| Reject | Agent is not authorized to operate | Fundamental requirements cannot be satisfied or risk is unacceptable |
| Remediate | Deployment is delayed pending corrective action | Mandatory controls or evidence are incomplete |
| Restricted pilot | Limited users, tools, data, and operating scope | Pilot controls are adequate and limitations are enforceable |
| Read-only production | Agent retrieves information and provides recommendations without state-changing actions | Read access is authorized and data disclosure risks are controlled |
| Human-approved execution | Agent proposes actions that require human approval before execution | Approval is meaningful and the technical enforcement is effective |
| Limited autonomous execution | Agent executes a defined set of low- or moderate-risk actions independently | Action-level controls, monitoring, and recovery are effective |
| Expanded autonomous execution | Agent performs a broader set of approved operations | Strong evidence supports the expanded scope and required risk approvals are complete |
| Suspend | Agent is temporarily prevented from operating or from using affected capabilities | A material incident, control failure, or unacceptable risk requires containment |
| Retire | Agent is permanently decommissioned | Business justification has ended or continued operation is no longer acceptable |

Expanded autonomy should be earned through evidence of safe performance and effective controls. It should not be granted merely because the agent has operated for a particular number of days.

#### 25.4 Formal Risk Acceptance Record

A risk acceptance record should document the decision to operate despite identified residual risk.

The record should contain:

- Agent name and unique identifier.
- Business purpose and approved operating scope.
- Risk assessment reference.
- Description of the remaining risk.
- Existing and planned controls.
- Evidence supporting control effectiveness.
- Known limitations and assumptions.
- Business justification for accepting the risk.
- Name or role of the authorized risk owner.
- Approval date.
- Any conditions or operating restrictions.
- Required monitoring and reporting.
- Review date or reassessment trigger.
- Expiration date where required by policy.
- Circumstances that automatically invalidate the acceptance.

Risk acceptance must not be used to bypass mandatory legal obligations or non-waivable enterprise security requirements.

Where the risk exceeds the authority of the designated owner, it must be escalated through the organization's formal risk governance process.

- A significant incident or near miss.
- A change in applicable legal or contractual requirements.
- A change in the threat environment.
- Evidence that controls are ineffective.
- A change in the agent's business justification.

#### 25.6 Retirement and Decommissioning

Governance must also address the end of the agent's operational life.

Retirement activities should include:

1. Obtain authorization to retire the agent.
2. Identify dependent workflows, systems, and business processes.
3. Disable new task submissions.
4. Terminate or safely complete active tasks.
5. Revoke service identities, credentials, and tokens.
6. Remove obsolete API permissions and tool integrations.
7. Disable scheduled tasks and delegated workflows.
8. Preserve required audit and incident evidence.
9. Apply approved data-retention and deletion requirements.
10. Update the AI inventory and risk register.
11. Notify relevant users and system owners.
12. Verify that no unauthorized access or execution path remains.
13. Record the final decommissioning evidence.

Simply disabling the user interface is not sufficient if the agent retains valid credentials, scheduled jobs, API integrations, or delegated processes.

The retirement process should verify that the agent can no longer perform unauthorized actions and that its remaining records are handled according to organizational policy.

#### 25.7 Final Executive Decision Framework

The executive decision should answer five questions.

**1. Is the business purpose legitimate and sufficiently valuable?**

The agent should address a clearly defined business need with measurable expected benefits.

**2. Are the agent's capabilities limited to its approved purpose?**

The organization should be able to demonstrate that identity permissions, tool restrictions, data boundaries, and authorization policies enforce the approved scope.

**3. Are the material risks understood and treated?**

The organization should have an evidence-based risk assessment, defined owners, effective controls, and an explicit approach to residual risk.

**4. Can the organization detect, contain, and recover from failures?**

Monitoring, incident response, emergency suspension, and recovery procedures should be operational and appropriately tested.

**5. Is the organization prepared to remain accountable after deployment?**

The business owner, technical owner, security function, and authorized risk authority should have the resources and decision rights necessary to govern the agent throughout its lifecycle.

A positive answer to all five questions supports a release decision, subject to mandatory controls and formal approvals. An unresolved critical issue should lead to remediation, a narrower operating scope, suspension, or rejection as appropriate.

### Core Principle

An autonomous AI agent should be authorized to operate only within a documented business purpose, an enforceable technical boundary, and an explicitly accepted level of residual risk. Its governance must continue throughout deployment, operation, material change, incident recovery, and retirement.

**Key conceptual distinctions:**

- **Deployment approval vs. ongoing authorization:** Initial approval does not remove the need for periodic reassessment.
- **Business ownership vs. technical ownership:** Business owners are accountable for business outcomes and operational consequences; technical owners maintain the implementation and its controls.
- **Risk assessment vs. risk acceptance:** Identifying and evaluating risk does not mean that the risk has been formally accepted.
- **Control implementation vs. control effectiveness:** A configured control must be validated under realistic operating conditions.
- **Autonomy vs. authority:** The ability to execute independently does not imply permission to perform unrestricted actions.
- **Operational performance vs. security assurance:** Efficiency and task completion do not establish that an agent is safe or compliant.
- **Monitoring vs. governance:** Telemetry provides evidence, while governance determines accountability, escalation, and authorized decisions.
- **Temporary suspension vs. retirement:** Suspension restricts operations pending a decision; retirement permanently ends the agent's authorized lifecycle.
- **Human approval vs. meaningful oversight:** Approval is effective only when the reviewer has sufficient information, appropriate authority, and the ability to prevent execution.
- **Continuous improvement vs. uncontrolled experimentation:** Agent behavior may be improved through controlled evaluation and change management without permitting unapproved changes to production capabilities.
