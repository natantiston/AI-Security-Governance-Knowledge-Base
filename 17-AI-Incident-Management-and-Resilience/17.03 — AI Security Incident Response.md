# 17.03 — AI Security Incident Response

## Part 1 — AI Security Incident Response Foundations, Response Lifecycle, Roles, Evidence and Governance

### 1. AI Security Incident Response

AI Security Incident Response is the organized capability used to detect, analyze, contain, eradicate, recover from, and learn from security incidents involving AI systems.

An AI security incident may involve:

* unauthorized access to an AI system;
* compromise of an AI model;
* prompt injection;
* data poisoning;
* model extraction;
* credential compromise;
* unauthorized tool execution;
* AI API abuse;
* malicious manipulation of AI outputs;
* compromise of AI software dependencies;
* attacks against AI infrastructure;
* misuse of AI capabilities for malicious purposes.

AI security incident response extends conventional cybersecurity incident response by incorporating AI-specific assets, behaviors, dependencies, model lifecycle characteristics, and attack surfaces.

Control ID: `AI-IMR-SIR-001`

### 2. Objective of AI Security Incident Response

The objective of AI security incident response is to reduce the impact and duration of AI security incidents while preserving evidence and restoring the affected capability to a trustworthy operating state.

Core objectives include:

* detect incidents rapidly;
* establish whether an actual security incident exists;
* understand the attack or failure mechanism;
* limit further compromise;
* protect affected data and systems;
* preserve evidence;
* eradicate malicious or unauthorized conditions;
* recover securely;
* validate recovery;
* identify root causes;
* prevent recurrence.

Incident response should not focus solely on restoring service.

Control ID: `AI-IMR-SIR-002`

### 3. AI Security Incident

An AI security incident is a security-related event involving an AI system, AI component, AI dependency, or AI-enabled process that has caused or may cause unauthorized access, compromise, manipulation, disclosure, disruption, or other security impact.

Examples include:

* compromised AI credentials;
* unauthorized model access;
* malicious model modification;
* poisoned training data;
* unauthorized retrieval of confidential information;
* compromised AI agent tools;
* malicious prompt injection resulting in unauthorized actions;
* exploitation of an AI API;
* compromise of an AI software dependency.

Not every AI anomaly is a security incident.

Control ID: `AI-IMR-SIR-003`

### 4. AI Security Event versus AI Security Incident

An AI security event is an observable occurrence that may have security relevance.

An AI security incident is an event or series of events that meets the organization's defined criteria for security incident handling.

```text id="q7m4xp"
Security Event
      |
      v
Security Assessment
      |
      +---- No Material Security Condition
      |             |
      |             v
      |        Event Record
      |
      +---- Security Incident
                    |
                    v
             Incident Response
```

For example, an unusual API request may be an event. Evidence that the request resulted from compromised credentials may elevate it to a security incident.

Control ID: `AI-IMR-SIR-004`

### 6. AI Security Incident Attack Surface

The AI attack surface represents the interfaces and components through which an attacker may compromise or abuse an AI system.

Potential attack surfaces include:

* user prompts;
* APIs;
* authentication interfaces;
* model endpoints;
* retrieval systems;
* datasets;
* plugins;
* agent tools;
* model files;
* software dependencies;
* cloud infrastructure;
* CI/CD pipelines;
* model repositories;
* administrative interfaces.

AI security response should consider both traditional infrastructure attack surfaces and AI-specific attack surfaces.

Control ID: `AI-IMR-SIR-006`

### 7. AI Security Incident Trust Boundaries

Trust boundaries identify transitions between components with different security assumptions or authorization domains.

Examples include:

```text id="m5r8ta"

  |

  |
```

Security incidents may cross multiple trust boundaries.

Incident investigation should therefore identify where trust assumptions were violated or bypassed.

A playbook should provide actionable procedures rather than merely describe the incident type.

The response team should include personnel with the expertise necessary to investigate and contain AI security incidents.

Potential participants include:

* security operations;
* incident response;
* AI engineering;
* ML engineering;
* cloud security;
* application security;
* data security;
* privacy;
* legal;
* AI governance;
* risk;
* business operations;
* supplier-management personnel.

The composition should reflect the nature and severity of the incident.

Control ID: `AI-IMR-SIR-013`

### 14. AI Security Incident Commander

The incident commander coordinates the response to a material incident.

Responsibilities may include:

* establishing incident objectives;
* assigning tasks;
* coordinating teams;
* managing escalation;
* maintaining situational awareness;
* controlling decision flow;
* coordinating communications;
* authorizing response actions within delegated authority.

The incident commander does not necessarily perform the technical investigation personally.

Control ID: `AI-IMR-SIR-014`

### 15. AI Security Incident Response Roles

Response roles should be clearly defined before a major incident occurs.

Possible roles include:

* incident commander;
* technical lead;
* forensic lead;
* AI/ML specialist;
* cloud specialist;
* communications lead;
* legal adviser;
* privacy specialist;
* supplier coordinator;
* business owner;
* recovery lead;
* evidence custodian.

Role clarity reduces duplicated or conflicting actions during an incident.

Control ID: `AI-IMR-SIR-015`

### 16. AI Security Incident Escalation

Escalation transfers an incident to a higher level of authority or specialized expertise when predefined conditions are met.

Escalation criteria may include:

* severity;
* affected population;
* safety implications;
* privacy impact;
* regulatory relevance;
* strategic system involvement;
* supplier dependency;
* inability to contain;
* rapid propagation.

Escalation criteria should be documented.

Control ID: `AI-IMR-SIR-016`

### 17. AI Security Incident Triage

Triage is the initial assessment used to determine the nature, severity, scope, and required response to a suspected incident.

Triage may assess:

* whether compromise is plausible;
* affected systems;
* affected accounts;
* model involvement;
* data involvement;
* attack vector;
* severity;
* containment urgency;
* evidence availability.

Triage should be rapid but should not convert assumptions into confirmed facts.

Control ID: `AI-IMR-SIR-017`

### 18. AI Security Incident Identification

Identification determines whether an observed event meets the organization's criteria for an AI security incident.

Identification should establish, where possible:

* what occurred;
* when it occurred;
* which systems were affected;
* whether unauthorized activity occurred;
* whether security controls were bypassed;
* whether the condition remains active.

Identification may remain provisional when evidence is incomplete.

Control ID: `AI-IMR-SIR-018`

### 19. AI Security Incident Classification

AI security incidents should be classified using the organization's approved incident taxonomy.

Relevant dimensions may include:

* security category;
* attack vector;
* root cause;
* affected asset;
* confidentiality impact;
* integrity impact;
* availability impact;
* severity;
* scope;
* confidence.

The taxonomy should support reclassification as evidence develops.

Control ID: `AI-IMR-SIR-019`

### 20. AI Security Incident Severity

Severity represents the organizational significance and urgency of an incident.

Severity may consider:

* impact;
* scope;
* duration;
* criticality;
* propagation;
* recoverability;
* safety relevance;
* privacy relevance;
* regulatory relevance.

Severity should not be determined solely from technical complexity.

Control ID: `AI-IMR-SIR-020`

### 21. AI Security Incident Confidentiality Impact

Confidentiality impact occurs when information is accessed, disclosed, exposed, inferred, or otherwise made available to unauthorized parties.

Potential information includes:

* prompts;
* system instructions;
* training data;
* customer data;
* credentials;
* model artifacts;
* proprietary information;
* security configurations.

Confidentiality impact should be assessed separately from integrity and availability.

Control ID: `AI-IMR-SIR-021`

### 22. AI Security Incident Integrity Impact

Integrity impact involves unauthorized or unintended alteration of AI-related assets.

Potential targets include:

* models;
* datasets;
* prompts;
* configurations;
* policies;
* outputs;
* tool parameters;
* deployment artifacts.

Model-integrity impact does not necessarily mean the model artifact itself was modified. A compromised deployment configuration may also affect the integrity of AI behavior.

Control ID: `AI-IMR-SIR-022`

### 23. AI Security Incident Availability Impact

Availability impact involves interruption or degradation of an AI capability.

Examples include:

* model endpoint outage;
* API denial of service;
* infrastructure failure caused by attack;
* resource exhaustion;
* malicious shutdown;
* compromised infrastructure requiring isolation.

Availability should be assessed in relation to the criticality of the affected AI capability.

Control ID: `AI-IMR-SIR-023`

### 24. AI Security Incident Authentication

Authentication determines whether an entity attempting to access an AI resource can be verified as the claimed identity.

Incident investigation should determine whether:

* credentials were compromised;
* authentication was bypassed;
* authentication controls failed;
* unauthorized identities were created;
* service identities were abused.

Authentication should be distinguished from authorization.

Control ID: `AI-IMR-SIR-024`

### 25. AI Security Incident Authorization

Authorization determines whether an authenticated identity was permitted to perform the relevant action.

An incident may occur when an authenticated user or service:

* accesses unauthorized data;
* invokes restricted tools;
* changes model configuration;
* modifies datasets;
* performs privileged operations.

Valid authentication does not establish valid authorization.

Control ID: `AI-IMR-SIR-025`

### 26. AI Security Incident Privilege Escalation

Privilege escalation occurs when an attacker or unauthorized process obtains greater permissions than originally authorized.

Potential targets include:

* model administration;
* dataset administration;
* cloud infrastructure;
* agent tools;
* API credentials;
* deployment pipelines.

Incident response should determine the original privilege, obtained privilege, and actions performed.

Control ID: `AI-IMR-SIR-026`

### 27. AI Security Incident Credential Compromise

Credential compromise involves unauthorized acquisition, use, exposure, or suspected compromise of credentials associated with AI systems.

Credentials may include:

* API keys;
* service-account credentials;
* cloud credentials;
* administrator accounts;
* tokens;
* certificates;
* secrets.

Containment may require credential revocation or rotation.

Control ID: `AI-IMR-SIR-027`

### 28. AI Security Incident Model Compromise

Model compromise occurs when an attacker or unauthorized party gains unauthorized control over, access to, or influence over an AI model or its operational behavior.

Potential forms include:

* unauthorized model modification;
* malicious model replacement;
* unauthorized fine-tuning;
* model artifact theft;
* deployment manipulation;
* malicious configuration changes.

A model compromise should be distinguished from ordinary model error.

Control ID: `AI-IMR-SIR-028`

### 29. AI Security Incident Model Artifact Integrity

Incident response should verify the integrity of affected model artifacts where compromise is suspected.

Verification may include:

* cryptographic hashes;
* digital signatures;
* trusted registry records;
* version comparison;
* provenance records;
* deployment metadata.

Integrity verification establishes whether the artifact changed according to the verification mechanism. It does not establish that the model is secure, safe, or behaviorally correct.

Control ID: `AI-IMR-SIR-029`

### 30. AI Security Incident Deployment Integrity

An AI model may remain unchanged while its deployment environment is compromised.

Investigation should therefore examine:

* runtime configuration;
* system prompts;
* access controls;
* model endpoint configuration;
* network controls;
* tool permissions;
* environment variables;
* secrets;
* middleware.

```text id="t3v7qs"
Trusted Model Artifact
        |
        v
Compromised Configuration
        |
        v
Compromised Deployment
        |
        v
Unauthorized AI Behavior
```

Artifact integrity alone is insufficient to establish deployment integrity.

Control ID: `AI-IMR-SIR-030`

### 31. AI Security Incident Prompt Injection

Prompt injection is an attack technique in which malicious or adversarial instructions influence an AI system to perform unintended behavior.

Potential sources include:

* direct user prompts;
* retrieved documents;
* web content;
* tool outputs;
* emails;
* uploaded files;
* external data.

Incident response should determine whether the injected instruction merely affected output or caused unauthorized access or action.

Control ID: `AI-IMR-SIR-031`

### 32. AI Security Incident Indirect Prompt Injection

Indirect prompt injection occurs when malicious instructions are embedded in content that the AI system retrieves or processes.

Potential sources include:

* websites;
* documents;
* databases;
* emails;
* knowledge bases;
* external APIs.

The investigation should identify:

* source content;
* retrieval path;
* model interaction;
* resulting behavior;
* affected tools or data.

Control ID: `AI-IMR-SIR-032`

### 33. AI Security Incident Data Poisoning

Data poisoning involves deliberate manipulation of data used by an AI system with the objective of influencing model behavior, evaluation, retrieval, or downstream decisions.

Potential targets include:

* training datasets;
* fine-tuning datasets;
* evaluation datasets;
* retrieval stores;
* knowledge bases;
* labels.

Incident response should determine whether malicious manipulation occurred and whether the affected data reached production processes.

Control ID: `AI-IMR-SIR-033`

### 34. AI Security Incident Data Integrity Investigation

Data-related investigations should establish:

* affected dataset;
* affected version;
* source;
* modification history;
* access history;
* integrity evidence;
* downstream models;
* downstream applications.

Dataset corruption does not automatically prove malicious poisoning.

Control ID: `AI-IMR-SIR-034`

### 35. AI Security Incident Model Extraction

Model extraction occurs when an unauthorized party attempts to reproduce or infer a model through repeated interaction or other techniques.

Investigation may consider:

* unusual API activity;
* excessive queries;
* repeated structured probing;
* account patterns;
* output collection;
* rate-limit violations.

The organization should distinguish legitimate high-volume usage from malicious extraction based on evidence.

Control ID: `AI-IMR-SIR-035`

### 36. AI Security Incident Membership-Inference Risk

Where an attacker attempts to determine whether particular information was included in model training data, the incident may involve membership-inference risk.

Investigation should consider:

* model type;
* exposed outputs;
* query behavior;
* affected dataset;
* sensitivity of the information;
* confidence of the inference.

Potential inference should not automatically be treated as confirmed data disclosure.

Control ID: `AI-IMR-SIR-036`

### 37. AI Security Incident Data Exfiltration

Data exfiltration involves unauthorized transfer or extraction of information from an AI environment.

Potential sources include:

* model endpoints;
* retrieval systems;
* databases;
* agent tools;
* APIs;
* logs;
* model artifacts.

Incident response should determine what data was potentially accessed, what data was confirmed to have left the environment, and through which channel.

Control ID: `AI-IMR-SIR-037`

### 38. AI Security Incident Tool Abuse

Tool abuse occurs when an AI system or attacker uses an integrated tool in an unauthorized or harmful manner.

Examples include:

* unauthorized database queries;
* unauthorized file access;
* malicious API invocation;
* unauthorized transaction;
* privilege misuse;
* external communication.

Tool abuse may create consequences outside the AI system itself.

Control ID: `AI-IMR-SIR-038`

### 39. AI Security Incident Agent Compromise

Agent compromise occurs when an AI agent's execution capability, instructions, credentials, memory, tools, or environment are compromised.

Investigation should consider:

* agent identity;
* system instructions;
* memory;
* tools;
* permissions;
* execution history;
* downstream actions.

An agent can remain available while being security-compromised.

Control ID: `AI-IMR-SIR-039`

### 40. AI Security Incident Memory Compromise

Where an AI system maintains persistent memory, incident response should investigate whether unauthorized parties altered, inserted, extracted, or manipulated memory content.

Potential consequences include:

* persistent malicious instructions;
* altered user context;
* data leakage;
* manipulation of future behavior.

Memory compromise should be treated separately from transient prompt injection where persistence is materially different.

Control ID: `AI-IMR-SIR-040`

### 41. AI Security Incident Retrieval Compromise

Retrieval systems may be compromised through:

* unauthorized document modification;
* malicious indexing;
* access-control failure;
* poisoned knowledge sources;
* retrieval manipulation;
* unauthorized database access.

Investigation should examine the retrieval source, index, query path, and model interaction.

Control ID: `AI-IMR-SIR-041`

### 42. AI Security Incident API Abuse

AI APIs may be abused through:

* credential theft;
* excessive requests;
* unauthorized endpoints;
* parameter manipulation;
* automated extraction;
* denial-of-service activity.

API incident response should correlate API telemetry with identity, network, application, and model activity.

Control ID: `AI-IMR-SIR-042`

### 43. AI Security Incident Denial of Service

AI denial-of-service incidents seek to reduce or eliminate availability through resource exhaustion, malicious requests, infrastructure attacks, or other mechanisms.

AI-specific resource exhaustion may involve:

* excessive inference;
* expensive prompts;
* oversized inputs;
* repeated tool execution;
* computationally intensive workflows.

Response should consider both technical containment and business-service impact.

Control ID: `AI-IMR-SIR-043`

### 44. AI Security Incident Supply-Chain Compromise

Supply-chain compromise occurs when a malicious or compromised third-party component introduces security risk into an AI system.

Potential components include:

* models;
* datasets;
* libraries;
* SDKs;
* containers;
* APIs;
* plugins;
* cloud services;
* deployment tools.

Investigation should establish provenance and dependency relationships.

Control ID: `AI-IMR-SIR-044`

### 45. AI Security Incident Software Dependency Compromise

AI applications frequently depend on software packages and frameworks.

Incident response should assess:

* vulnerable packages;
* malicious packages;
* compromised repositories;
* dependency substitution;
* transitive dependencies;
* build artifacts.

A known vulnerable dependency is not equivalent to confirmed exploitation.

### 46. AI Security Incident Infrastructure Compromise

AI infrastructure incidents may involve:

* cloud resources;

* virtual machines;
* orchestration platforms;

Infrastructure compromise may affect multiple AI systems simultaneously.

Incident response should therefore assess the potential blast radius beyond the initially observed component.

### 49. AI Security Incident Response Governance Principle

Effective AI security incident response requires a structured capability that combines conventional cybersecurity incident response with AI-specific understanding of:

* model behavior;
* model and dataset integrity;
* prompts;
* retrieval;
* agents;
* tools;
* AI APIs;
* AI supply chains;
* model deployment;
* AI-specific attack surfaces;
* AI system dependencies.

The response process should preserve the distinction between:

* security event and security incident;
* anomaly and compromise;
* vulnerability and exploitation;
* model failure and model compromise;
* artifact integrity and behavioral integrity;
* authentication and authorization;
* attack vector and root cause;
* observed impact and potential impact;
* confirmed evidence and hypothesis;
* supplier incident and organizational responsibility.

Control ID: `AI-IMR-SIR-049`

### 50. Core Principle of AI Security Incident Response Foundations

AI security incident response should restore security and trustworthy operation, not merely restore technical availability.

A mature response capability should be able to:

* detect suspicious AI activity;
* determine whether a security incident exists;
* classify the incident consistently;
* preserve evidence;
* identify affected AI assets and dependencies;
* contain malicious activity;
* protect credentials and sensitive data;
* investigate models, datasets, prompts, agents, tools, and infrastructure;
* eradicate unauthorized conditions;
* recover from a trusted state;
* validate the security of the recovered environment;
* document uncertainty and evidence;
* support applicable legal, regulatory, and contractual assessments;
* learn from incidents and strengthen controls.

The following distinctions are fundamental:

* **AI security incident ≠ AI anomaly**
* **AI security incident ≠ every AI failure**
* **vulnerability ≠ exploitation**
* **model failure ≠ model compromise**
* **artifact integrity ≠ behavioral integrity**
* **authentication ≠ authorization**
* **prompt injection ≠ confirmed compromise**
* **data poisoning ≠ ordinary data-quality error**
* **supplier notification ≠ fulfillment of the organization's own obligations**
* **incident response ≠ recovery alone**
* **service restoration ≠ security validation**
* **internal incident classification ≠ legal classification**
* **internal governance control ≠ statutory requirement**
* **recommended implementation practice ≠ legal obligation**

Internal identifiers such as `AI-IMR-SIR-*` are knowledge-base taxonomy identifiers and do not represent statutory provisions, regulatory article numbers, or legal requirements unless explicitly mapped to an authoritative source.

Control ID: `AI-IMR-SIR-050`

## Part 2 — AI Security Incident Response Controls, Detection, Investigation, Containment, Eradication and Recovery

### 51. AI Security Incident Response Control Framework

An AI security incident-response control framework defines the controls required to identify, investigate, contain, eradicate, recover from, and learn from AI security incidents.

The framework should connect:

* incident detection;
* security telemetry;
* AI asset inventory;
* model and dataset lineage;
* identity and access management;
* vulnerability management;
* threat intelligence;
* incident classification;
* evidence preservation;
* containment;
* eradication;
* recovery;
* validation;
* post-incident improvement.

The framework should distinguish mandatory organizational controls from recommended implementation practices.

Control ID: `AI-IMR-SIR-051`

### 52. AI Security Incident Response Scope Control

The organization should formally define which AI systems, components, environments, suppliers, and dependencies are covered by its security incident-response capability.

Scope should consider:

* production AI;
* development AI;
* testing environments;
* models;
* datasets;
* AI applications;
* agents;
* APIs;
* retrieval systems;
* model registries;
* AI infrastructure;
* third-party AI services.

Scope should be reviewed when the AI environment changes materially.

The organization should maintain an incident register capable of recording AI security incidents and their lifecycle.

The register should support:

* incident identification;
* classification;
* severity;
* affected systems;
* evidence;
* actions;

* containment;

The register should preserve an audit history of material changes.

Detection controls should identify suspicious or unauthorized activity involving AI systems.

* API telemetry;

* DLP;
* anomaly detection;
* application security monitoring.

Detection coverage should be documented and periodically assessed.

Control ID: `AI-IMR-SIR-055`

### 56. AI Behavioral Anomaly Detection

AI behavioral anomaly detection identifies deviations from expected AI behavior that may indicate security compromise.

Examples include:

* unexpected tool invocation;
* unusual data retrieval;
* abnormal API usage;
* unexpected model configuration changes;
* unusual output patterns;
* unexpected administrative actions.

A behavioral anomaly is an investigation signal and does not automatically establish compromise.

Control ID: `AI-IMR-SIR-056`

Security telemetry should capture information necessary to investigate AI security events.

Potential telemetry includes:

* authentication;

* API requests;

* tool calls;
* retrieval activity;
* configuration changes;
* model deployment;
* dataset access;
* administrative actions.

Monitoring should identify:

* current version;

* deployment time;
