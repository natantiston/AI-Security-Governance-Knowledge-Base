# 20.15 — LLM Security Assessment
## Part 1: Assessment Foundations, Scope, Architecture, and Threat Classification

## 1. Introduction to the LLM Security Assessment

A Large Language Model (LLM) Security Assessment is a structured process for identifying, evaluating, documenting, and treating security risks associated with large language models and the applications built around them.

LLMs introduce security considerations that extend beyond traditional application security. Their behavior is influenced by prompts, contextual information, training data, model weights, retrieval sources, tool integrations, and the surrounding application architecture. They may also generate outputs that appear credible but are incorrect, disclose information from their context, or respond to malicious instructions embedded in user inputs or retrieved content.

An LLM Security Assessment evaluates the security of the complete implementation rather than treating the model as an isolated component.

For example, an enterprise customer-support assistant may use an LLM to interpret questions, retrieve information from internal knowledge repositories, access customer records through APIs, and draft responses. Even if the underlying model is provided by a reputable vendor, the implementation may still expose sensitive information if authorization checks are incomplete or retrieved documents are not appropriately filtered.

The assessment must therefore examine the model, application, data, integrations, identities, operational controls, and governance arrangements.

### 1.1 Objectives of the Assessment

The assessment should establish whether:

- The LLM has a clearly defined and approved business purpose.
- The system architecture and trust boundaries are documented.
- Sensitive information is protected throughout the processing lifecycle.
- Prompt injection and other model-specific threats are evaluated.
- Model outputs are validated before they trigger consequential actions.
- Retrieval-augmented generation (RAG) sources are protected against unauthorized access and manipulation.
- Tool integrations operate with appropriate permissions and constraints.
- Security testing covers realistic adversarial scenarios.
- Logging, monitoring, incident response, and recovery mechanisms are established.
- Residual risks are documented and approved by the appropriate risk owner.

### 1.2 LLM Security Assessment Versus Traditional Application Security

Traditional application security remains necessary, but it does not fully address the behavior of probabilistic language models.

| Assessment dimension | Traditional application security | LLM security assessment |
|---|---|---|
| Input validation | Validate input against expected formats and rules | Validate inputs while considering prompt manipulation, adversarial instructions, and indirect prompt injection |
| Authentication | Verify user and service identities | Verify identities across users, models, retrieval services, and integrated tools |
| Authorization | Enforce access permissions for resources and operations | Ensure model-generated requests cannot bypass application-level authorization |
| Data protection | Protect data at rest, in transit, and during processing | Also assess contextual data exposure, sensitive information in prompts, retrieval leakage, and model output disclosure |
| Output validation | Validate response structure and application behavior | Assess harmful, misleading, unauthorized, or policy-violating generated content |
| Business logic | Test deterministic application workflows | Evaluate probabilistic behavior, instruction conflicts, and unexpected model-driven actions |
| Third-party risk | Assess software providers and dependencies | Assess model providers, hosting services, model artifacts, inference APIs, and external AI services |
| Testing | Conduct code analysis, penetration testing, and functional testing | Combine conventional testing with adversarial prompts, robustness evaluations, and model-specific security testing |
| Monitoring | Monitor infrastructure, applications, and transactions | Also monitor abuse patterns, suspicious prompt activity, output-policy violations, and model behavior changes |

**Core distinction:** Traditional security controls protect the application and its infrastructure. LLM security controls must also address how the model interprets instructions, uses context, generates content, and interacts with external capabilities.

A secure implementation requires both.

## 2. Scope and Applicability of the LLM Security Assessment

The assessment scope must be defined before testing begins. An LLM can be deployed in multiple configurations, and each configuration creates different security exposures.

### 2.1 LLM Deployment Models

| Deployment model | Description | Principal security considerations |
|---|---|---|
| External LLM API | An enterprise application sends prompts and context to a third-party model provider | Data transmission, provider retention, contractual commitments, API security, tenant isolation, and service availability |
| Managed enterprise AI platform | An organization uses an enterprise-managed AI service | Identity integration, network controls, administrative permissions, data governance, logging, and platform configuration |
| Self-hosted LLM | The organization operates the model within its own infrastructure | Model artifact integrity, infrastructure hardening, access control, patching, capacity management, and operational security |
| Open-weight model deployment | An organization obtains model weights and operates or modifies the model | Artifact provenance, licensing, supply-chain integrity, model modifications, and deployment security |
| Hybrid deployment | Different model components or processing stages operate across internal and external environments | Cross-boundary data flows, inconsistent security policies, identity federation, and shared-responsibility gaps |
| Embedded LLM capability | An existing SaaS or business application includes LLM-powered functionality | Vendor configuration, integration permissions, data access, feature governance, and limited visibility into underlying model behavior |

The assessment must not assume that self-hosting automatically makes an LLM secure or that a third-party API is inherently insecure. The relevant question is whether the organization has implemented controls appropriate to the deployment model and its risk profile.

### 2.2 Components Within Scope

A comprehensive assessment should consider the following components.

| Component | Scope of review |
|---|---|
| Foundation model | Model identity, version, provenance, known limitations, supported capabilities, and provider security information |
| Inference service | API exposure, authentication, authorization, rate limiting, and request handling |
| Prompt templates | Instruction design, privileged instructions, dynamic variables, and separation of trusted and untrusted content |
| User interface | Authentication, session management, input handling, output rendering, and user warnings |
| Application backend | Business logic, authorization enforcement, validation, error handling, and orchestration |
| RAG pipeline | Document ingestion, indexing, retrieval, metadata filtering, access enforcement, and source integrity |
| Embedding service | Data processing, vector generation, model provenance, and potential information leakage |
| Vector database | Access controls, tenant isolation, index security, encryption, and data lifecycle management |
| Tool integrations | Tool permissions, API credentials, parameter validation, execution constraints, and approval requirements |
| Data sources | Classification, access permissions, provenance, retention, and accuracy |
| Logging and monitoring | Sensitive-data handling, security event coverage, detection, alerting, and retention |
| Model lifecycle | Version changes, evaluations, deployments, rollback, and retirement |
| Third-party dependencies | Model providers, libraries, orchestration frameworks, hosting providers, and external services |

### 2.4 Assessment Boundaries and Shared Responsibility

The security assessment must identify which controls are implemented by the organization, which are provided by a vendor, and which depend on both parties.

For example, an enterprise using an external LLM API may depend on the provider to secure its inference infrastructure. However, the enterprise remains responsible for deciding what data to send, restricting access to its own systems, protecting API credentials, and controlling how model outputs are used.

A shared-responsibility matrix can make these boundaries explicit.

| Security control | Model provider | Enterprise application owner | Enterprise security/GRC |
|---|---|---|---|
| Provider infrastructure security | Responsible | Reviews assurance evidence | Defines assurance requirements |
| Model endpoint availability | Responsible within contract | Implements appropriate resilience | Reviews service risk |
| User authentication | May provide integration capabilities | Implements and configures access | Defines identity requirements |
| Data sent to the model | Processes data according to applicable arrangements | Minimizes and classifies data | Defines data-handling policy |
| Application authorization | Usually outside provider responsibility | Implements and tests enforcement | Reviews authorization risks |
| Prompt injection defenses | May provide model-level mitigations | Implements application-level defenses | Defines assessment requirements |
| Model output validation | May provide safety features | Implements business-specific validation | Reviews risk and control evidence |
| Incident response | Handles provider-side incidents | Handles application and data incidents | Coordinates governance and reporting |
| Risk acceptance | Does not accept the enterprise's business risk | Supports treatment decisions | Ensures approval follows policy |

The precise allocation depends on the service contract, deployment architecture, and provider capabilities. The matrix should be validated rather than copied without review.

### 3.3 Data Flow and Trust Boundaries

The assessment should trace how information moves through the system.

A typical request lifecycle includes:

1. A user submits a question or instruction.
2. The application authenticates the user and checks access permissions.
3. The application constructs a request using a prompt template and permitted contextual data.
4. A retrieval component obtains relevant documents if RAG is enabled.
5. The model generates a response using the supplied instructions and context.
6. The application evaluates the response against relevant policies and business rules.
7. The application displays the response or submits an approved action to an integrated service.
8. Security-relevant events are recorded according to logging and privacy requirements.

Each stage may introduce different threats.

| Stage | Example threat | Required assessment focus |
|---|---|---|
| User input | Malicious prompt injection | Input handling and adversarial testing |
| Authentication | Unauthorized access to the assistant | Identity and session controls |
| Retrieval | Cross-user or cross-tenant data exposure | Access filtering and authorization enforcement |
| Prompt construction | Untrusted content influences privileged instructions | Instruction and data separation |
| Inference | Sensitive context is disclosed in generated output | Data minimization and output controls |
| Output processing | Generated content triggers an unsafe operation | Validation and execution restrictions |
| Tool execution | Model-generated parameters manipulate an API call | Least privilege and server-side validation |
| Logging | Prompts contain credentials or personal data | Data minimization, access restrictions, and retention |
| Model update | New version changes security behavior | Version control, testing, and release approval |

### 3.4 Architecture Review Questions

The assessor should establish:

- Where is the model hosted, and which entities can access the inference endpoint?
- What information is transmitted to external providers?
- Which data sources can the application retrieve?
- Are retrieval permissions enforced before information reaches the model?
- Can the model invoke tools, APIs, or business functions?
- Are privileged operations protected by independent authorization checks?
- Can untrusted documents or external content influence system behavior?
- Are outputs validated before being displayed, stored, or executed?
- Are sensitive prompts and responses retained in logs?
- Can the organization identify the model version used for a particular request?
- Can the service be disabled or rolled back if a serious vulnerability is discovered?

### 3.5 Architecture Evidence Requirements

Evidence should include, where applicable:

- Current architecture diagrams.
- Data-flow diagrams.
- Trust-boundary documentation.
- API and integration inventories.
- Identity and access-control configurations.
- RAG ingestion and retrieval designs.
- Model endpoint configuration.
- Data classification and retention requirements.
- Logging and monitoring design.
- Model deployment and rollback procedures.

**Core Principle:** An LLM system must be assessed as an interconnected application and data-processing environment, not merely as a model endpoint.

## 4. LLM Threat Classification and Security Risk Taxonomy

LLM threats can originate from malicious users, compromised data sources, insecure application design, excessive permissions, model limitations, third-party dependencies, or operational failures.

A structured taxonomy ensures that the assessment considers both conventional cybersecurity risks and threats associated with language-model behavior.

### 4.1 Principal LLM Security Threat Categories

| Threat category | Description | Example |
|---|---|---|
| Prompt injection | Malicious instructions attempt to influence model behavior | A user instructs the assistant to disregard its operating rules |
| Indirect prompt injection | Instructions are embedded in content processed by the model | A retrieved document contains instructions designed to manipulate the assistant |
| Sensitive information disclosure | The system reveals information that should remain protected | A response includes confidential information retrieved for another user |
| Insecure output handling | Model-generated content is trusted without appropriate validation | Generated HTML or SQL is executed without safe handling |
| Excessive agency | The model or agent has more authority than required | A support assistant can modify customer records despite only needing read access |
| Improper output reliance | Users or downstream systems treat generated content as authoritative without verification | An incorrect recommendation is used to approve a high-impact transaction |
| Retrieval and knowledge-base manipulation | Sources or indexes are poisoned, altered, or improperly controlled | A malicious document influences answers produced by a RAG assistant |
| Model denial of service | Requests consume excessive processing capacity or cost | Repeated complex prompts exhaust the service budget |
| Model or dependency supply-chain compromise | A model artifact, library, or external component is compromised | A modified model package introduces malicious behavior |
| Model extraction or intellectual-property exposure | Repeated queries or insecure access expose protected model-related information | An unauthorized party obtains information the organization intended to protect |
| Data poisoning | Training, fine-tuning, or related data is maliciously manipulated | Corrupted examples influence a specialized model's behavior |
| Model theft or unauthorized access | Model artifacts or endpoints are accessed without permission | An exposed storage location permits unauthorized model-weight downloads |
| Unbounded resource consumption | The system lacks appropriate usage limits | Long inputs or repeated requests cause disproportionate infrastructure costs |
| Inadequate monitoring | Security-relevant behavior cannot be detected or investigated | Repeated prompt attacks occur without alerts or traceable records |
| Third-party model risk | Provider controls, service terms, or dependencies create unacceptable exposure | A provider's data-handling arrangements do not satisfy enterprise requirements |

The applicability of each category depends on the system. For example, model-weight theft is particularly relevant to deployments where model artifacts are accessible, while an API-only implementation may have different exposure.

### 4.2 Distinguishing Threat, Vulnerability, and Risk

These concepts should not be treated as interchangeable.

- **Threat:** A potential cause of an unwanted security event.
- **Vulnerability:** A weakness that a threat can exploit.
- **Risk:** The potential effect of uncertainty on objectives, considering the likelihood and consequences of an event.
- **Control:** A measure intended to modify risk.
- **Finding:** An issue identified through assessment or testing.
- **Residual risk:** The risk remaining after controls and treatments are considered.

Example:

| Element | Illustrative finding |
|---|---|
| Threat | A malicious user attempts prompt injection |
| Vulnerability | The application allows model output to invoke privileged functions without independent authorization |
| Risk event | The assistant performs an unauthorized business operation |
| Business impact | Unauthorized changes to customer records and potential regulatory exposure |
| Preventive control | Restrict tool permissions and enforce server-side authorization |
| Detective control | Log tool calls and alert on suspicious or prohibited operations |
| Corrective control | Disable affected tools, revoke credentials, investigate, and restore safe operation |
| Residual risk | The possibility that an attack bypasses remaining safeguards |

This structure helps the assessor move beyond generic threat lists and document how a technical weakness could produce a business consequence.

### 4.3 LLM-Specific Threats Versus Conventional Threats

| Threat | Primarily LLM-specific? | Conventional security controls still required? |
|---|---|---|
| Direct prompt injection | Yes, as an attack against model instruction handling | Yes |
| Indirect prompt injection | Yes, particularly in systems processing untrusted context | Yes |
| Broken access control | No; established application-security threat | Yes |
| Credential theft | No | Yes |
| Sensitive information disclosure through generated responses | Often LLM-specific in its mechanism, but the confidentiality objective is conventional | Yes |
| Insecure output handling | The generated-content pathway creates distinctive risks | Yes |
| Excessive agency | Closely associated with tool-using LLM applications and AI agents | Yes |
| Data poisoning | Relevant to machine-learning systems broadly, not exclusively LLMs | Yes |
| Denial of service | No; the underlying threat is conventional, although LLM cost and compute characteristics change the exposure | Yes |
| Model extraction | Associated with machine-learning models and model-serving interfaces | Yes |
| Unauthorized administrative access | No | Yes |
| Untrusted package or model artifact | No; a supply-chain threat that can affect AI-specific assets | Yes |

The objective is not to create a separate security universe for LLMs. It is to extend the organization's established security program to account for new attack surfaces and failure modes.

## 5. Prompt Injection and Instruction-Handling Security

Prompt injection occurs when input or contextual content attempts to influence the model in ways that conflict with the application's intended instructions, security boundaries, or permitted behavior.

Unlike conventional injection attacks, prompt injection generally targets the model's interpretation of instructions and context rather than relying exclusively on a deterministic parser or database query.

Prompt injection may be direct or indirect.

### 5.1 Direct Prompt Injection

Direct prompt injection occurs when the user supplies instructions intended to manipulate the model.

Examples include requests to:

- Ignore established operating instructions.
- Reveal hidden prompts or confidential context.
- Produce prohibited content.
- Bypass application policies.
- Invoke a tool for an unauthorized purpose.
- Treat user-provided instructions as more authoritative than trusted application rules.

The existence of an adversarial prompt does not automatically mean the system is vulnerable. The assessor must determine whether the application or model can be induced to violate a security requirement and whether other controls prevent the resulting harm.

### 5.2 Indirect Prompt Injection

Indirect prompt injection occurs when malicious instructions are contained in content the model processes, rather than being supplied directly as the user's main request.

Potential sources include:

- Retrieved documents.
- Uploaded files.
- Web pages.
- Emails.
- Support tickets.
- Knowledge-base articles.
- Code repositories.
- Third-party API responses.
- Text extracted from images or other media.

For example, an enterprise assistant may be asked to summarize a document. The document contains text instructing the assistant to disclose confidential records or call an external service. If the application treats retrieved content as trusted instructions, the model may attempt to follow those instructions.

The core security concern is that the system may not reliably distinguish between data to be analyzed and instructions that should control its behavior.

### 5.3 Prompt Injection Attack Path

```text id="llm_assessment_prompt_injection_01"
Attacker
   |
   v
Malicious User Input or Document
   |
   v
Application Processes Input
   |
   v
Untrusted Content Enters Model Context
   |
   v
Model Interprets Malicious Instructions
   |
   v
Potentially Unsafe Output or Tool Request
   |
   v
Impact if Independent Controls Fail
```

Possible impacts include disclosure of information, unauthorized tool invocation, policy violations, manipulation of recommendations, or disruption of business workflows.

The final impact depends on the application's architecture and permissions. A model that cannot access sensitive data or execute actions may have a smaller impact profile than an assistant connected to privileged enterprise systems.

### 5.4 Prompt Injection Control Framework

| Control layer | Example safeguards | Assessment evidence |
|---|---|---|
| Input handling | Identify untrusted input sources and apply appropriate content handling | Input-handling design and test results |
| Prompt construction | Separate trusted instructions from untrusted data where feasible | Prompt templates and architecture review |
| Retrieval controls | Enforce user authorization and document-level permissions | Retrieval configuration and access tests |
| Model behavior | Evaluate resistance to representative prompt-injection attempts | Adversarial test results |
| Tool authorization | Apply independent server-side authorization to each operation | API authorization tests and permission configuration |
| Least privilege | Limit model-accessible tools and resources | Tool inventory and permission matrix |
| Output validation | Validate outputs before they reach sensitive workflows | Validation rules and test evidence |
| Human approval | Require explicit approval for defined high-impact actions | Workflow configuration and approval logs |
| Monitoring | Detect suspicious prompts and prohibited tool requests | Logging configuration, alerts, and response procedures |
| Incident response | Disable affected capabilities and investigate security events | Runbooks and incident exercise records |

No single control should be assumed to eliminate prompt injection risk. In particular, a system prompt instructing the model not to follow malicious instructions is not a substitute for independent authorization, least privilege, and safe execution controls.

### 5.5 Prompt Injection Assessment Questions

The assessor should ask:

1. Can users submit arbitrary text, files, URLs, or other content?
2. Can retrieved documents contain instructions that influence model behavior?
3. How does the application distinguish trusted instructions from untrusted content?
4. Can retrieved content influence which tools the model attempts to invoke?
5. Are tool operations authorized independently of model-generated reasoning?
6. Can the model access information beyond the authenticated user's permissions?
7. What happens when the model produces an unexpected or prohibited response?
8. Are high-impact actions subject to human approval?
9. Are adversarial tests performed against direct and indirect prompt injection?
10. Are identified weaknesses tracked to remediation and retesting?

### 5.6 Prompt Injection Test Record

| Field | Example |
|---|---|
| Test ID | LLM-PI-001 |
| Test objective | Evaluate resistance to direct prompt injection |
| Preconditions | Authenticated user with standard permissions |
| Test input | A controlled adversarial instruction requesting access to restricted information |
| Expected result | The application does not disclose restricted information or perform unauthorized actions |
| Actual result | Record the observed response and any attempted tool invocation |
| Evidence | Sanitized request, response, relevant logs, and execution trace |
| Severity | Based on demonstrated impact and exploitability |
| Remediation | Address the underlying weakness, not only the tested wording |
| Retest result | Pass, fail, or inconclusive |
| Owner | Assigned technical or security owner |

Testing should use authorized environments and synthetic or appropriately protected test data. A refusal message alone does not establish that the system is secure; the assessor should also verify whether sensitive data was retrieved, transmitted, logged, or exposed through another pathway.

**Core Principle:** Prompt injection must be treated as an architectural and authorization risk, not merely as a problem that can be solved by writing a stronger prompt.

## 6. Sensitive Information Disclosure and Data Leakage

LLM applications may expose information through prompts, retrieved context, generated outputs, tool responses, logs, caches, or third-party services.

The assessment must identify both the information the model receives and the information it can cause the wider application to disclose.

### 6.1 Common Data Leakage Scenarios

| Scenario | Description | Potential impact |
|---|---|---|
| Excessive prompt context | The application sends more information than necessary | Unnecessary exposure to the model-processing environment |
| Cross-user retrieval | Retrieval returns records that the authenticated user is not permitted to access | Confidentiality breach |
| Cross-tenant retrieval | A shared system fails to isolate one tenant's information from another | Multi-tenant data exposure |
| Sensitive output generation | The model reproduces confidential information from its context | Unauthorized disclosure |
| Tool-response leakage | A tool returns sensitive fields that the model includes in its response | Excessive disclosure |
| Prompt and response logging | Logs retain credentials, personal information, or confidential business data | Secondary exposure and retention risk |
| External provider processing | Data is transmitted to a provider under arrangements that do not meet enterprise requirements | Contractual, privacy, or confidentiality risk |
| Cache contamination | Responses or context are reused across users without adequate isolation | Cross-session or cross-user leakage |
| Training or fine-tuning exposure | Sensitive data is included in datasets or model-development workflows without adequate controls | Unintended disclosure or governance violations |
| Administrative access | Excessive privileges permit personnel to view prompts, outputs, or stored context | Insider or administrative misuse |

These scenarios must be evaluated against the actual architecture. The assessment should not assume that every model provider trains on customer prompts or that every LLM retains submitted data. Data handling depends on the service, configuration, contract, and applicable terms.

### 6.2 Data Flow Classification

The assessor should classify information across the full processing lifecycle.

| Data stage | Questions to evaluate |
|---|---|
| Collection | What information can users submit? |
| Pre-processing | Is sensitive information identified, minimized, or removed where appropriate? |
| Prompt construction | Which fields and documents are included in the context? |
| External transmission | Which information leaves the organization's controlled environment? |
| Retrieval | Are document and record permissions enforced? |
| Inference | What data is available to the model during generation? |
| Tool execution | Can integrations retrieve or modify sensitive information? |
| Output | What information can be returned to the user? |
| Logging | Which prompts, outputs, identifiers, and tool calls are recorded? |
| Retention | How long is each data category retained, and why? |
| Deletion | Can information be removed from application storage and downstream systems when required? |

### 6.3 Data Minimization and Disclosure Controls

A defensible control strategy includes:

- Limiting prompt context to information necessary for the approved use case.
- Enforcing access controls before retrieving documents or records.
- Removing or masking sensitive fields when they are not required.
- Restricting model access to approved data sources.
- Validating outputs before disclosing sensitive information.
- Preventing unauthorized users from accessing prompts, outputs, and diagnostic logs.
- Reviewing provider retention, processing, and training arrangements.
- Establishing retention and deletion requirements for prompts, responses, embeddings, and logs.
- Testing tenant isolation and user-specific retrieval permissions.
- Monitoring for repeated attempts to extract restricted information.

Data masking or anonymization can reduce exposure, but neither should be assumed to eliminate risk in all circumstances. Re-identification, contextual inference, and residual identifiers may remain relevant depending on the data and use case.

### 6.4 Data Leakage Test Cases

| Test ID | Test scenario | Expected control outcome |
|---|---|---|
| LLM-DL-001 | User requests information outside their access permissions | Restricted information is not retrieved or disclosed |
| LLM-DL-002 | A retrieved document contains sensitive fields unnecessary for the response | Unnecessary sensitive fields are excluded from the accessible context or output |
| LLM-DL-003 | One tenant attempts to retrieve another tenant's records | Tenant isolation prevents unauthorized access |
| LLM-DL-004 | User requests confidential instructions or hidden application context | The application does not expose protected information |
| LLM-DL-005 | Prompt and response logging is reviewed | Sensitive information is handled according to approved logging and retention rules |
| LLM-DL-006 | The model receives a tool response containing excess fields | The application restricts or filters the information returned to the model |
| LLM-DL-007 | A user attempts repeated extraction of restricted records | Applicable access, rate-limiting, and monitoring controls operate as intended |

### 6.5 Evidence and Findings

A leakage finding should record:

- The data category involved.
- The source of the information.
- The intended access permissions.
- The actual retrieval and disclosure pathway.
- The users or systems potentially affected.
- Whether the data left the organization's controlled environment.
- The existing preventive and detective controls.
- The applicable contractual, privacy, and regulatory requirements.
- The remediation owner and target date.
- The retest outcome.

**Core Principle:** Confidentiality must be enforced by the application and data-access architecture. The model should never be the sole enforcement mechanism for deciding which information a user is permitted to receive.

## 7. Retrieval-Augmented Generation (RAG) Security Assessment

Retrieval-augmented generation combines an LLM with external information sources. Instead of relying exclusively on information encoded in model parameters, the application retrieves relevant content and supplies it to the model as context.

RAG is commonly used for enterprise search, customer support, policy assistants, technical documentation, and internal knowledge management.

RAG can improve the relevance and freshness of responses, but it introduces additional components and trust boundaries that must be assessed.

The security design must account for the ingestion pipeline as well as the runtime retrieval process. A secure query interface cannot compensate for a knowledge base that was populated with unauthorized or malicious content.

### 7.2 Principal RAG Security Risks

| Risk | Description | Example control |
|---|---|---|
| Unauthorized ingestion | Documents are indexed without approval | Source allowlisting and ingestion authorization |
| Malicious document content | Documents contain adversarial instructions | Source validation and indirect prompt-injection testing |
| Broken document-level authorization | Retrieval ignores source access permissions | Permission-aware retrieval and authorization testing |
| Cross-tenant retrieval | One tenant's documents appear in another tenant's results | Strong tenant isolation and negative access tests |
| Stale or inaccurate content | Outdated documents influence generated responses | Content ownership, review dates, and expiry controls |
| Index manipulation | Unauthorized parties alter vectors, metadata, or indexed content | Restricted write access, integrity monitoring, and audit logs |
| Embedding exposure | Embeddings or associated metadata are accessible to unauthorized parties | Access control, data minimization, and appropriate storage protections |
| Retrieval poisoning | Malicious content is introduced to influence answers | Provenance checks, ingestion controls, and anomaly review |
| Excessive context | Too many or overly sensitive documents are included | Context minimization and filtering |
| Source ambiguity | The answer cannot be traced to the information used | Source attribution and retrieval logging |
| Insecure deletion | Removed documents remain accessible through indexes or caches | Defined deletion and index-refresh procedures |
| Retrieval manipulation | Queries or metadata filters cause irrelevant or unauthorized content to be selected | Query validation and retrieval evaluation |

### 7.3 RAG Assessment Questions

**Data ingestion**
- Are data sources approved by the relevant business and data owners?
- Is the provenance of each source recorded?
- Can external users or untrusted systems submit documents?
- Are document changes, deletions, and ownership changes tracked?
- Are malicious or malformed documents tested during ingestion?

**Access control**
- Are user permissions enforced during retrieval?
- Are document-level restrictions preserved when content is chunked and indexed?
- Are permissions revalidated when source access changes?
- Is tenant isolation tested using negative access scenarios?
- Can the model retrieve information through an alternate pathway that bypasses the intended controls?

**Retrieval and context**
- Are retrieval results limited to the minimum necessary information?
- Can retrieved content contain instructions that influence the model?
- Are metadata filters validated server-side?
- Are retrieval results logged sufficiently for investigation without unnecessarily retaining sensitive content?
- Can the organization determine which sources contributed to a response?

**Lifecycle**
- How are stale documents identified and removed?
- How are index updates authorized?
- How are source deletions propagated to vectors and caches?
- Are changes to embedding models evaluated before deployment?
- Are retrieval quality and security re-tested after significant changes?

### 7.4 RAG Security Test Matrix

| Test ID | Test scenario | Expected result |
|---|---|---|
| LLM-RAG-001 | A user asks for a document they are not authorized to access | The document is excluded from retrieval and not disclosed |
| LLM-RAG-002 | A document contains indirect prompt-injection instructions | The system does not permit the document to override application controls |
| LLM-RAG-003 | A malicious user attempts to upload an unauthorized document | Ingestion controls reject or quarantine the content according to policy |
| LLM-RAG-004 | A document is deleted from the approved source | The document becomes inaccessible through relevant indexes and caches within the defined deletion window |
| LLM-RAG-005 | A source is updated with a new version | The indexed content and provenance reflect the approved version |
| LLM-RAG-006 | A user attempts cross-tenant retrieval | The system prevents access to other tenants' information |
| LLM-RAG-007 | The assistant produces an answer based on retrieved content | The system provides appropriate source traceability where required |
| LLM-RAG-008 | A retrieval filter is manipulated | Server-side authorization prevents unauthorized retrieval |
| LLM-RAG-009 | The vector database is accessed by an unauthorized identity | Access controls deny the operation and record relevant security events |
| LLM-RAG-010 | The embedding model or chunking configuration changes | Required evaluation and release controls are followed |

### 7.5 RAG Governance Requirements

The organization should define:

- Approved source repositories.
- Data-owner responsibilities.
- Ingestion and indexing approval requirements.
- Document-level access-control requirements.
- Source provenance and versioning requirements.
- Content review and expiry rules.
- Security testing frequency.
- Index update and deletion procedures.
- Logging and monitoring requirements.
- Exception and risk-acceptance procedures.

**Core Principle:** RAG security depends on the integrity, authorization, and lifecycle management of the knowledge sources, not merely on the security of the LLM that consumes them.

## 8. LLM Output Security and Unsafe Output Handling

LLM outputs are generated content. They should not automatically be treated as accurate, authorized, safe, or suitable for direct execution.

The risk depends on where the output is used. A generated paragraph displayed to a user presents different security concerns from a generated SQL statement, shell command, customer-record update, or financial recommendation.

### 8.1 Output Risk Categories

| Output category | Potential risk | Required control approach |
|---|---|---|
| Informational text | Incorrect or misleading information | Appropriate validation, source attribution, and user guidance |
| HTML or Markdown | Cross-site scripting or unsafe rendering if handled improperly | Context-appropriate output encoding and safe rendering |
| SQL or database query | Unauthorized data access or destructive operations | Parameterization, restricted query interfaces, and database authorization |
| Shell or script commands | Command execution or infrastructure compromise | Avoid direct execution; use constrained, approved interfaces |
| API parameters | Unauthorized or malformed business operations | Schema validation, allowlisting, and server-side authorization |
| Customer communications | Disclosure of confidential or inaccurate information | Data-loss prevention, business validation, and human review where appropriate |
| Security recommendations | Incorrect prioritization or inappropriate remediation | Expert validation and evidence-based decision-making |
| Automated decisions | Unjustified or prohibited decisions affecting people or business processes | Applicable governance, impact assessment, oversight, and decision controls |

### 8.2 Output Validation Architecture

The application should validate output according to its intended use. For example, a structured response used to update a customer record should be checked against an explicit schema and business rules. The system should also independently verify that the authenticated user is permitted to make the requested change.

Output filtering alone cannot guarantee safety. Validation must be combined with authorization, constrained interfaces, and appropriate human approval.

### 8.3 Assessment Questions

- Is generated content rendered safely in the user interface?
- Can model output be interpreted as executable code or a database query?
- Are outputs validated against expected schemas?
- Can generated content trigger actions without independent authorization?
- Are sensitive fields filtered before responses are returned?
- Are business-critical outputs subject to appropriate review?
- Are validation failures handled safely?
- Does the system fail closed when a required security check cannot be completed?
- Are output-validation controls tested against adversarial inputs?
- Are output-related incidents logged and assigned for investigation?

### 8.4 Output Security Test Record

|---|---|

| Risk scenario | Unsafe, malformed, unauthorized, or sensitive output |

| Expected behavior | Defined security requirement |
| Observed behavior | Actual output and downstream effect |
| Validation result | Pass, fail, or inconclusive |

| Finding severity | Based on demonstrated business impact and exploitability |
| Remediation | Required technical or procedural change |
| Retest result | Evidence that the correction is effective |

**Core Principle:** Model output must be treated as untrusted input to downstream systems until the relevant validation, authorization, and execution controls have succeeded.

## 9. Tool Integration, API Security, and Excessive Agency

An LLM application becomes more consequential when it can call tools, access APIs, retrieve records, send communications, or perform business operations.

This capability can improve productivity, but it also creates a pathway from manipulated model behavior to real-world actions.

The central governance question is not simply whether the model can call a tool. It is whether each operation is necessary, authorized, constrained, observable, and recoverable.

### 9.1 Tool Integration Risk

Consider an enterprise assistant that can:

- Retrieve customer account information.
- Create support tickets.
- Change account settings.
- Send emails.
- Access internal documentation.
- Update CRM records.

If the assistant only needs to retrieve account status, granting permission to change account settings would violate least privilege. A prompt-injection attack or model error could then produce a more serious consequence than the business use case requires.

### 9.2 Tool Permission Classification

| Permission level | Description | Typical governance treatment |
|---|---|---|
| Read-only retrieval | Reads approved information without modifying it | Enforce user-level and resource-level access restrictions |
| Draft generation | Prepares content but does not submit or execute it | Validate content and protect sensitive information |
| Reversible write | Changes data that can be restored through a controlled process | Apply authorization, audit logging, and defined rollback mechanisms |
| High-impact write | Changes sensitive records, financial data, access rights, or other consequential information | Require stronger authorization, validation, and often human approval |
| External communication | Sends emails, messages, or other communications outside the application | Apply recipient validation, disclosure controls, and approval requirements where warranted |
| Administrative operation | Changes permissions, security settings, infrastructure, or governance controls | Restrict access tightly and require explicit privileged authorization |
| Irreversible operation | Performs an action that cannot readily be reversed | Prohibit autonomous execution unless a formally approved, justified control model exists |

The exact classification should reflect the organization's business processes and the consequences of unauthorized actions.

### 9.3 Tool Security Control Matrix

| Control | Requirement | Evidence |
|---|---|---|
| Tool inventory | Document every available tool and operation | Approved tool register |
| Least privilege | Grant only the permissions necessary for the approved use case | Identity and permission configuration |
| Independent authorization | Verify authorization outside the model's generated instructions | API and application security tests |
| Input validation | Validate tool parameters against defined schemas and constraints | Validation rules and test results |
| Credential management | Protect API keys, tokens, and service identities | Secret-management configuration and access review |
| Action limits | Restrict the number, scope, and frequency of permitted operations | Rate limits, quotas, and execution policies |
| Human approval | Require approval for designated high-impact operations | Approval workflows and audit records |
| Execution isolation | Separate untrusted model behavior from privileged execution environments | Architecture and configuration evidence |
| Auditability | Record actor, requested operation, authorization result, and outcome | Security event logs |
| Recovery | Provide rollback, revocation, or compensating actions where feasible | Tested recovery procedures |

A failed validation or authorization check must prevent execution. The model must not be able to bypass that decision by changing its explanation, proposing alternative parameters, or issuing repeated requests.

### 9.5 Tool Security Assessment Questions

1. Which tools can the model invoke?
2. Which permissions does each tool possess?
3. Are tools restricted to approved business functions?
4. Are user permissions checked independently for each operation?
5. Can the model access credentials or secrets directly?
6. Are tool parameters validated on the server side?
7. Which operations require human approval?
8. Can the model initiate external communications or modify sensitive records?
9. Are failed authorization attempts logged and investigated?
10. Can tool permissions be revoked rapidly during an incident?
11. Are execution limits and rate controls configured?
12. Can the organization reconstruct the sequence of model requests and tool actions?

### 9.6 Practical Finding Example

**Finding:** The LLM-powered support assistant has permission to update customer account attributes even though its approved purpose is limited to answering inquiries and drafting support responses.

- **Risk:** A manipulated request or model error could result in unauthorized customer-record changes.
- **Root cause:** The service identity has broader permissions than the approved use case requires.
- **Required treatment:** Separate read-only retrieval from write operations, reduce service permissions, and implement independent authorization for any retained write capability.
- **Evidence required:** Updated permission matrix, configuration records, negative authorization tests, and successful retesting.
- **Risk owner:** Application or business-service owner.
- **Governance involvement:** Security and GRC review the residual risk and verify that the control change meets the organization's risk-treatment requirements.

**Core Principle:** The authority of an LLM application must be bounded by enforceable permissions and controlled execution paths, not by assumptions about what the model will choose to do.

## 10. Core Principle — LLM Security Must Be Assessed Across the Entire Application Lifecycle

An effective LLM Security Assessment combines established cybersecurity practices with testing designed for language-model behavior. It examines the model, application, data, retrieval pipeline, tool integrations, provider dependencies, and operating environment as one connected system.

The assessment should establish:

- What the system is permitted to do.
- Which assets and data it can access.
- Where trust boundaries exist.
- How malicious or malformed inputs may affect behavior.
- Whether generated outputs can cause unsafe downstream effects.
- Which controls prevent unauthorized access and actions.
- How security failures are detected, investigated, and corrected.
- Who owns each material risk and approves any remaining exposure.

A model that performs well in ordinary demonstrations is not necessarily secure in an enterprise environment. Security assurance requires documented architecture, realistic threat scenarios, evidence-based testing, independent controls, and a defined process for addressing findings.

### Key Conceptual Distinctions

| Distinction | Explanation |
|---|---|
| Model security vs. application security | Model-level safeguards do not replace application authorization, input validation, or secure execution |
| LLM vs. LLM-powered system | The model is one component; the complete system includes data, interfaces, integrations, infrastructure, and operational controls |
| Direct vs. indirect prompt injection | Direct attacks arrive through user instructions; indirect attacks arrive through content the system processes |
| Trusted instructions vs. untrusted data | Content supplied for analysis must not automatically acquire authority to control the application |
| RAG relevance vs. RAG authorization | Retrieving relevant content does not establish that the user is permitted to access it |
| Output quality vs. output security | A fluent or accurate response may still disclose information or trigger an unauthorized action |
| Model refusal vs. effective prevention | A refusal message does not prove that retrieval, disclosure, or tool execution was safely controlled |
| Tool availability vs. tool authorization | A tool being available does not mean every user or model-generated request is authorized |
| Human presence vs. effective oversight | Human review is meaningful only when the reviewer has sufficient information, authority, time, and ability to intervene |
| Security testing vs. security assurance | A successful test provides evidence about specific scenarios; it does not prove the absence of all vulnerabilities |
| Provider assurance vs. enterprise assurance | Provider certifications and reports do not demonstrate that the customer's application is securely configured |
| Initial risk vs. residual risk | Initial risk reflects exposure before treatment; residual risk reflects the risk remaining after relevant controls and treatments are considered |

**Final Core Principle:** An LLM Security Assessment is complete only when the organization has established a defensible understanding of the system's architecture and threat exposure, evaluated the controls protecting its data and operations, documented material findings, and assigned accountable owners to the required risk treatments.
