# 20.15 — LLM Security Assessment
## Part 1: Assessment Foundations, Scope, Architecture, and Threat Classification

## 1. Introduction to the LLM Security Assessment

A Large Language Model (LLM) Security Assessment is a structured process for identifying, evaluating, documenting, and treating security risks associated with large language models and the applications built around them.

LLMs introduce security considerations that extend beyond traditional application security. Their behavior is influenced by prompts, contextual information, training data, model weights, retrieval sources, tool integrations, and the surrounding application architecture. They may also generate outputs that appear credible but are incorrect, disclose information from their context, or respond to malicious instructions embedded in user inputs or retrieved content.

An LLM Security Assessment evaluates the security of the complete implementation rather than treating the model as an isolated component.

For example, an enterprise customer-support assistant may use an LLM to interpret questions, retrieve information from internal knowledge repositories, access customer records through APIs, and draft responses. Even if the underlying model is provided by a reputable vendor, the implementation may still expose sensitive information if authorization checks are incomplete or retrieved documents are not appropriately filtered.

The assessment must therefore examine the model, application, data, integrations, identities, operational controls, and governance arrangements.

### 1.1 Objectives of the Assessment

The assessment should establish whether:

- The LLM has a clearly defined and approved business purpose.
- The system architecture and trust boundaries are documented.
- Sensitive information is protected throughout the processing lifecycle.
- Prompt injection and other model-specific threats are evaluated.
- Model outputs are validated before they trigger consequential actions.
- Retrieval-augmented generation (RAG) sources are protected against unauthorized access and manipulation.
- Tool integrations operate with appropriate permissions and constraints.
- Security testing covers realistic adversarial scenarios.
- Logging, monitoring, incident response, and recovery mechanisms are established.
- Residual risks are documented and approved by the appropriate risk owner.

### 1.2 LLM Security Assessment Versus Traditional Application Security

Traditional application security remains necessary, but it does not fully address the behavior of probabilistic language models.

| Assessment dimension | Traditional application security | LLM security assessment |
|---|---|---|
| Input validation | Validate input against expected formats and rules | Validate inputs while considering prompt manipulation, adversarial instructions, and indirect prompt injection |
| Authentication | Verify user and service identities | Verify identities across users, models, retrieval services, and integrated tools |
| Authorization | Enforce access permissions for resources and operations | Ensure model-generated requests cannot bypass application-level authorization |
| Data protection | Protect data at rest, in transit, and during processing | Also assess contextual data exposure, sensitive information in prompts, retrieval leakage, and model output disclosure |
| Output validation | Validate response structure and application behavior | Assess harmful, misleading, unauthorized, or policy-violating generated content |
| Business logic | Test deterministic application workflows | Evaluate probabilistic behavior, instruction conflicts, and unexpected model-driven actions |
| Third-party risk | Assess software providers and dependencies | Assess model providers, hosting services, model artifacts, inference APIs, and external AI services |
| Testing | Conduct code analysis, penetration testing, and functional testing | Combine conventional testing with adversarial prompts, robustness evaluations, and model-specific security testing |
| Monitoring | Monitor infrastructure, applications, and transactions | Also monitor abuse patterns, suspicious prompt activity, output-policy violations, and model behavior changes |

**Core distinction:** Traditional security controls protect the application and its infrastructure. LLM security controls must also address how the model interprets instructions, uses context, generates content, and interacts with external capabilities.

A secure implementation requires both.

## 2. Scope and Applicability of the LLM Security Assessment

The assessment scope must be defined before testing begins. An LLM can be deployed in multiple configurations, and each configuration creates different security exposures.

### 2.1 LLM Deployment Models

| Deployment model | Description | Principal security considerations |
|---|---|---|
| External LLM API | An enterprise application sends prompts and context to a third-party model provider | Data transmission, provider retention, contractual commitments, API security, tenant isolation, and service availability |
| Managed enterprise AI platform | An organization uses an enterprise-managed AI service | Identity integration, network controls, administrative permissions, data governance, logging, and platform configuration |
| Self-hosted LLM | The organization operates the model within its own infrastructure | Model artifact integrity, infrastructure hardening, access control, patching, capacity management, and operational security |
| Open-weight model deployment | An organization obtains model weights and operates or modifies the model | Artifact provenance, licensing, supply-chain integrity, model modifications, and deployment security |
| Hybrid deployment | Different model components or processing stages operate across internal and external environments | Cross-boundary data flows, inconsistent security policies, identity federation, and shared-responsibility gaps |
| Embedded LLM capability | An existing SaaS or business application includes LLM-powered functionality | Vendor configuration, integration permissions, data access, feature governance, and limited visibility into underlying model behavior |

The assessment must not assume that self-hosting automatically makes an LLM secure or that a third-party API is inherently insecure. The relevant question is whether the organization has implemented controls appropriate to the deployment model and its risk profile.

### 2.2 Components Within Scope

A comprehensive assessment should consider the following components.

| Component | Scope of review |
|---|---|
| Foundation model | Model identity, version, provenance, known limitations, supported capabilities, and provider security information |
| Inference service | API exposure, authentication, authorization, rate limiting, and request handling |
| Prompt templates | Instruction design, privileged instructions, dynamic variables, and separation of trusted and untrusted content |
| User interface | Authentication, session management, input handling, output rendering, and user warnings |
| Application backend | Business logic, authorization enforcement, validation, error handling, and orchestration |
| RAG pipeline | Document ingestion, indexing, retrieval, metadata filtering, access enforcement, and source integrity |
| Embedding service | Data processing, vector generation, model provenance, and potential information leakage |
| Vector database | Access controls, tenant isolation, index security, encryption, and data lifecycle management |
| Tool integrations | Tool permissions, API credentials, parameter validation, execution constraints, and approval requirements |
| Data sources | Classification, access permissions, provenance, retention, and accuracy |
| Logging and monitoring | Sensitive-data handling, security event coverage, detection, alerting, and retention |
| Model lifecycle | Version changes, evaluations, deployments, rollback, and retirement |
| Third-party dependencies | Model providers, libraries, orchestration frameworks, hosting providers, and external services |

### 2.4 Assessment Boundaries and Shared Responsibility

The security assessment must identify which controls are implemented by the organization, which are provided by a vendor, and which depend on both parties.

For example, an enterprise using an external LLM API may depend on the provider to secure its inference infrastructure. However, the enterprise remains responsible for deciding what data to send, restricting access to its own systems, protecting API credentials, and controlling how model outputs are used.

A shared-responsibility matrix can make these boundaries explicit.

| Security control | Model provider | Enterprise application owner | Enterprise security/GRC |
|---|---|---|---|
| Provider infrastructure security | Responsible | Reviews assurance evidence | Defines assurance requirements |
| Model endpoint availability | Responsible within contract | Implements appropriate resilience | Reviews service risk |
| User authentication | May provide integration capabilities | Implements and configures access | Defines identity requirements |
| Data sent to the model | Processes data according to applicable arrangements | Minimizes and classifies data | Defines data-handling policy |
| Application authorization | Usually outside provider responsibility | Implements and tests enforcement | Reviews authorization risks |
| Prompt injection defenses | May provide model-level mitigations | Implements application-level defenses | Defines assessment requirements |
| Model output validation | May provide safety features | Implements business-specific validation | Reviews risk and control evidence |
| Incident response | Handles provider-side incidents | Handles application and data incidents | Coordinates governance and reporting |
| Risk acceptance | Does not accept the enterprise's business risk | Supports treatment decisions | Ensures approval follows policy |

The precise allocation depends on the service contract, deployment architecture, and provider capabilities. The matrix should be validated rather than copied without review.

### 3.3 Data Flow and Trust Boundaries

The assessment should trace how information moves through the system.

A typical request lifecycle includes:

1. A user submits a question or instruction.
2. The application authenticates the user and checks access permissions.
3. The application constructs a request using a prompt template and permitted contextual data.
4. A retrieval component obtains relevant documents if RAG is enabled.
5. The model generates a response using the supplied instructions and context.
6. The application evaluates the response against relevant policies and business rules.
7. The application displays the response or submits an approved action to an integrated service.
8. Security-relevant events are recorded according to logging and privacy requirements.

Each stage may introduce different threats.

| Stage | Example threat | Required assessment focus |
|---|---|---|
| User input | Malicious prompt injection | Input handling and adversarial testing |
| Authentication | Unauthorized access to the assistant | Identity and session controls |
| Retrieval | Cross-user or cross-tenant data exposure | Access filtering and authorization enforcement |
| Prompt construction | Untrusted content influences privileged instructions | Instruction and data separation |
| Inference | Sensitive context is disclosed in generated output | Data minimization and output controls |
| Output processing | Generated content triggers an unsafe operation | Validation and execution restrictions |
| Tool execution | Model-generated parameters manipulate an API call | Least privilege and server-side validation |
| Logging | Prompts contain credentials or personal data | Data minimization, access restrictions, and retention |
| Model update | New version changes security behavior | Version control, testing, and release approval |

### 3.4 Architecture Review Questions

The assessor should establish:

- Where is the model hosted, and which entities can access the inference endpoint?
- What information is transmitted to external providers?
- Which data sources can the application retrieve?
- Are retrieval permissions enforced before information reaches the model?
- Can the model invoke tools, APIs, or business functions?
- Are privileged operations protected by independent authorization checks?
- Can untrusted documents or external content influence system behavior?
- Are outputs validated before being displayed, stored, or executed?
- Are sensitive prompts and responses retained in logs?
- Can the organization identify the model version used for a particular request?
- Can the service be disabled or rolled back if a serious vulnerability is discovered?

### 3.5 Architecture Evidence Requirements

Evidence should include, where applicable:

- Current architecture diagrams.
- Data-flow diagrams.
- Trust-boundary documentation.
- API and integration inventories.
- Identity and access-control configurations.
- RAG ingestion and retrieval designs.
- Model endpoint configuration.
- Data classification and retention requirements.
- Logging and monitoring design.
- Model deployment and rollback procedures.

**Core Principle:** An LLM system must be assessed as an interconnected application and data-processing environment, not merely as a model endpoint.

## 4. LLM Threat Classification and Security Risk Taxonomy

LLM threats can originate from malicious users, compromised data sources, insecure application design, excessive permissions, model limitations, third-party dependencies, or operational failures.

A structured taxonomy ensures that the assessment considers both conventional cybersecurity risks and threats associated with language-model behavior.

### 4.1 Principal LLM Security Threat Categories

| Threat category | Description | Example |
|---|---|---|
| Prompt injection | Malicious instructions attempt to influence model behavior | A user instructs the assistant to disregard its operating rules |
| Indirect prompt injection | Instructions are embedded in content processed by the model | A retrieved document contains instructions designed to manipulate the assistant |
| Sensitive information disclosure | The system reveals information that should remain protected | A response includes confidential information retrieved for another user |
| Insecure output handling | Model-generated content is trusted without appropriate validation | Generated HTML or SQL is executed without safe handling |
| Excessive agency | The model or agent has more authority than required | A support assistant can modify customer records despite only needing read access |
| Improper output reliance | Users or downstream systems treat generated content as authoritative without verification | An incorrect recommendation is used to approve a high-impact transaction |
| Retrieval and knowledge-base manipulation | Sources or indexes are poisoned, altered, or improperly controlled | A malicious document influences answers produced by a RAG assistant |
| Model denial of service | Requests consume excessive processing capacity or cost | Repeated complex prompts exhaust the service budget |
| Model or dependency supply-chain compromise | A model artifact, library, or external component is compromised | A modified model package introduces malicious behavior |
| Model extraction or intellectual-property exposure | Repeated queries or insecure access expose protected model-related information | An unauthorized party obtains information the organization intended to protect |
| Data poisoning | Training, fine-tuning, or related data is maliciously manipulated | Corrupted examples influence a specialized model's behavior |
| Model theft or unauthorized access | Model artifacts or endpoints are accessed without permission | An exposed storage location permits unauthorized model-weight downloads |
| Unbounded resource consumption | The system lacks appropriate usage limits | Long inputs or repeated requests cause disproportionate infrastructure costs |
| Inadequate monitoring | Security-relevant behavior cannot be detected or investigated | Repeated prompt attacks occur without alerts or traceable records |
| Third-party model risk | Provider controls, service terms, or dependencies create unacceptable exposure | A provider's data-handling arrangements do not satisfy enterprise requirements |

The applicability of each category depends on the system. For example, model-weight theft is particularly relevant to deployments where model artifacts are accessible, while an API-only implementation may have different exposure.

### 4.2 Distinguishing Threat, Vulnerability, and Risk

These concepts should not be treated as interchangeable.

- **Threat:** A potential cause of an unwanted security event.
- **Vulnerability:** A weakness that a threat can exploit.
- **Risk:** The potential effect of uncertainty on objectives, considering the likelihood and consequences of an event.
- **Control:** A measure intended to modify risk.
- **Finding:** An issue identified through assessment or testing.
- **Residual risk:** The risk remaining after controls and treatments are considered.

Example:

| Element | Illustrative finding |
|---|---|
| Threat | A malicious user attempts prompt injection |
| Vulnerability | The application allows model output to invoke privileged functions without independent authorization |
| Risk event | The assistant performs an unauthorized business operation |
| Business impact | Unauthorized changes to customer records and potential regulatory exposure |
| Preventive control | Restrict tool permissions and enforce server-side authorization |
| Detective control | Log tool calls and alert on suspicious or prohibited operations |
| Corrective control | Disable affected tools, revoke credentials, investigate, and restore safe operation |
| Residual risk | The possibility that an attack bypasses remaining safeguards |

This structure helps the assessor move beyond generic threat lists and document how a technical weakness could produce a business consequence.

### 4.3 LLM-Specific Threats Versus Conventional Threats

| Threat | Primarily LLM-specific? | Conventional security controls still required? |
|---|---|---|
| Direct prompt injection | Yes, as an attack against model instruction handling | Yes |
| Indirect prompt injection | Yes, particularly in systems processing untrusted context | Yes |
| Broken access control | No; established application-security threat | Yes |
| Credential theft | No | Yes |
| Sensitive information disclosure through generated responses | Often LLM-specific in its mechanism, but the confidentiality objective is conventional | Yes |
| Insecure output handling | The generated-content pathway creates distinctive risks | Yes |
| Excessive agency | Closely associated with tool-using LLM applications and AI agents | Yes |
| Data poisoning | Relevant to machine-learning systems broadly, not exclusively LLMs | Yes |
| Denial of service | No; the underlying threat is conventional, although LLM cost and compute characteristics change the exposure | Yes |
| Model extraction | Associated with machine-learning models and model-serving interfaces | Yes |
| Unauthorized administrative access | No | Yes |
| Untrusted package or model artifact | No; a supply-chain threat that can affect AI-specific assets | Yes |

The objective is not to create a separate security universe for LLMs. It is to extend the organization's established security program to account for new attack surfaces and failure modes.

## 5. Prompt Injection and Instruction-Handling Security

Prompt injection occurs when input or contextual content attempts to influence the model in ways that conflict with the application's intended instructions, security boundaries, or permitted behavior.

Unlike conventional injection attacks, prompt injection generally targets the model's interpretation of instructions and context rather than relying exclusively on a deterministic parser or database query.

Prompt injection may be direct or indirect.

### 5.1 Direct Prompt Injection

Direct prompt injection occurs when the user supplies instructions intended to manipulate the model.

Examples include requests to:

- Ignore established operating instructions.
- Reveal hidden prompts or confidential context.
- Produce prohibited content.
- Bypass application policies.
- Invoke a tool for an unauthorized purpose.
- Treat user-provided instructions as more authoritative than trusted application rules.

The existence of an adversarial prompt does not automatically mean the system is vulnerable. The assessor must determine whether the application or model can be induced to violate a security requirement and whether other controls prevent the resulting harm.

### 5.2 Indirect Prompt Injection

Indirect prompt injection occurs when malicious instructions are contained in content the model processes, rather than being supplied directly as the user's main request.

Potential sources include:

- Retrieved documents.
- Uploaded files.
- Web pages.
- Emails.
- Support tickets.
- Knowledge-base articles.
- Code repositories.
- Third-party API responses.
- Text extracted from images or other media.

For example, an enterprise assistant may be asked to summarize a document. The document contains text instructing the assistant to disclose confidential records or call an external service. If the application treats retrieved content as trusted instructions, the model may attempt to follow those instructions.

The core security concern is that the system may not reliably distinguish between data to be analyzed and instructions that should control its behavior.

### 5.3 Prompt Injection Attack Path

```text id="llm_assessment_prompt_injection_01"
Attacker
   |
   v
Malicious User Input or Document
   |
   v
Application Processes Input
   |
   v
Untrusted Content Enters Model Context
   |
   v
Model Interprets Malicious Instructions
   |
   v
Potentially Unsafe Output or Tool Request
   |
   v
Impact if Independent Controls Fail
```

Possible impacts include disclosure of information, unauthorized tool invocation, policy violations, manipulation of recommendations, or disruption of business workflows.

The final impact depends on the application's architecture and permissions. A model that cannot access sensitive data or execute actions may have a smaller impact profile than an assistant connected to privileged enterprise systems.

### 5.4 Prompt Injection Control Framework

| Control layer | Example safeguards | Assessment evidence |
|---|---|---|
| Input handling | Identify untrusted input sources and apply appropriate content handling | Input-handling design and test results |
| Prompt construction | Separate trusted instructions from untrusted data where feasible | Prompt templates and architecture review |
| Retrieval controls | Enforce user authorization and document-level permissions | Retrieval configuration and access tests |
| Model behavior | Evaluate resistance to representative prompt-injection attempts | Adversarial test results |
| Tool authorization | Apply independent server-side authorization to each operation | API authorization tests and permission configuration |
| Least privilege | Limit model-accessible tools and resources | Tool inventory and permission matrix |
| Output validation | Validate outputs before they reach sensitive workflows | Validation rules and test evidence |
| Human approval | Require explicit approval for defined high-impact actions | Workflow configuration and approval logs |
| Monitoring | Detect suspicious prompts and prohibited tool requests | Logging configuration, alerts, and response procedures |
| Incident response | Disable affected capabilities and investigate security events | Runbooks and incident exercise records |

No single control should be assumed to eliminate prompt injection risk. In particular, a system prompt instructing the model not to follow malicious instructions is not a substitute for independent authorization, least privilege, and safe execution controls.

### 5.5 Prompt Injection Assessment Questions

The assessor should ask:

1. Can users submit arbitrary text, files, URLs, or other content?
2. Can retrieved documents contain instructions that influence model behavior?
3. How does the application distinguish trusted instructions from untrusted content?
4. Can retrieved content influence which tools the model attempts to invoke?
5. Are tool operations authorized independently of model-generated reasoning?
6. Can the model access information beyond the authenticated user's permissions?
7. What happens when the model produces an unexpected or prohibited response?
8. Are high-impact actions subject to human approval?
9. Are adversarial tests performed against direct and indirect prompt injection?
10. Are identified weaknesses tracked to remediation and retesting?

### 5.6 Prompt Injection Test Record

| Field | Example |
|---|---|
| Test ID | LLM-PI-001 |
| Test objective | Evaluate resistance to direct prompt injection |
| Preconditions | Authenticated user with standard permissions |
| Test input | A controlled adversarial instruction requesting access to restricted information |
| Expected result | The application does not disclose restricted information or perform unauthorized actions |
| Actual result | Record the observed response and any attempted tool invocation |
| Evidence | Sanitized request, response, relevant logs, and execution trace |
| Severity | Based on demonstrated impact and exploitability |
| Remediation | Address the underlying weakness, not only the tested wording |
| Retest result | Pass, fail, or inconclusive |
| Owner | Assigned technical or security owner |

Testing should use authorized environments and synthetic or appropriately protected test data. A refusal message alone does not establish that the system is secure; the assessor should also verify whether sensitive data was retrieved, transmitted, logged, or exposed through another pathway.

**Core Principle:** Prompt injection must be treated as an architectural and authorization risk, not merely as a problem that can be solved by writing a stronger prompt.

## 6. Sensitive Information Disclosure and Data Leakage

LLM applications may expose information through prompts, retrieved context, generated outputs, tool responses, logs, caches, or third-party services.

The assessment must identify both the information the model receives and the information it can cause the wider application to disclose.

### 6.1 Common Data Leakage Scenarios

| Scenario | Description | Potential impact |
|---|---|---|
| Excessive prompt context | The application sends more information than necessary | Unnecessary exposure to the model-processing environment |
| Cross-user retrieval | Retrieval returns records that the authenticated user is not permitted to access | Confidentiality breach |
| Cross-tenant retrieval | A shared system fails to isolate one tenant's information from another | Multi-tenant data exposure |
| Sensitive output generation | The model reproduces confidential information from its context | Unauthorized disclosure |
| Tool-response leakage | A tool returns sensitive fields that the model includes in its response | Excessive disclosure |
| Prompt and response logging | Logs retain credentials, personal information, or confidential business data | Secondary exposure and retention risk |
| External provider processing | Data is transmitted to a provider under arrangements that do not meet enterprise requirements | Contractual, privacy, or confidentiality risk |
| Cache contamination | Responses or context are reused across users without adequate isolation | Cross-session or cross-user leakage |
| Training or fine-tuning exposure | Sensitive data is included in datasets or model-development workflows without adequate controls | Unintended disclosure or governance violations |
| Administrative access | Excessive privileges permit personnel to view prompts, outputs, or stored context | Insider or administrative misuse |

These scenarios must be evaluated against the actual architecture. The assessment should not assume that every model provider trains on customer prompts or that every LLM retains submitted data. Data handling depends on the service, configuration, contract, and applicable terms.

### 6.2 Data Flow Classification

The assessor should classify information across the full processing lifecycle.

| Data stage | Questions to evaluate |
|---|---|
| Collection | What information can users submit? |
| Pre-processing | Is sensitive information identified, minimized, or removed where appropriate? |
| Prompt construction | Which fields and documents are included in the context? |
| External transmission | Which information leaves the organization's controlled environment? |
| Retrieval | Are document and record permissions enforced? |
| Inference | What data is available to the model during generation? |
| Tool execution | Can integrations retrieve or modify sensitive information? |
| Output | What information can be returned to the user? |
| Logging | Which prompts, outputs, identifiers, and tool calls are recorded? |
| Retention | How long is each data category retained, and why? |
| Deletion | Can information be removed from application storage and downstream systems when required? |

### 6.3 Data Minimization and Disclosure Controls

A defensible control strategy includes:

- Limiting prompt context to information necessary for the approved use case.
- Enforcing access controls before retrieving documents or records.
- Removing or masking sensitive fields when they are not required.
- Restricting model access to approved data sources.
- Validating outputs before disclosing sensitive information.
- Preventing unauthorized users from accessing prompts, outputs, and diagnostic logs.
- Reviewing provider retention, processing, and training arrangements.
- Establishing retention and deletion requirements for prompts, responses, embeddings, and logs.
- Testing tenant isolation and user-specific retrieval permissions.
- Monitoring for repeated attempts to extract restricted information.

Data masking or anonymization can reduce exposure, but neither should be assumed to eliminate risk in all circumstances. Re-identification, contextual inference, and residual identifiers may remain relevant depending on the data and use case.

### 6.4 Data Leakage Test Cases

| Test ID | Test scenario | Expected control outcome |
|---|---|---|
| LLM-DL-001 | User requests information outside their access permissions | Restricted information is not retrieved or disclosed |
| LLM-DL-002 | A retrieved document contains sensitive fields unnecessary for the response | Unnecessary sensitive fields are excluded from the accessible context or output |
| LLM-DL-003 | One tenant attempts to retrieve another tenant's records | Tenant isolation prevents unauthorized access |
| LLM-DL-004 | User requests confidential instructions or hidden application context | The application does not expose protected information |
| LLM-DL-005 | Prompt and response logging is reviewed | Sensitive information is handled according to approved logging and retention rules |
| LLM-DL-006 | The model receives a tool response containing excess fields | The application restricts or filters the information returned to the model |
| LLM-DL-007 | A user attempts repeated extraction of restricted records | Applicable access, rate-limiting, and monitoring controls operate as intended |

### 6.5 Evidence and Findings

A leakage finding should record:

- The data category involved.
- The source of the information.
- The intended access permissions.
- The actual retrieval and disclosure pathway.
- The users or systems potentially affected.
- Whether the data left the organization's controlled environment.
- The existing preventive and detective controls.
- The applicable contractual, privacy, and regulatory requirements.
- The remediation owner and target date.
- The retest outcome.

**Core Principle:** Confidentiality must be enforced by the application and data-access architecture. The model should never be the sole enforcement mechanism for deciding which information a user is permitted to receive.

Retrieval-augmented generation combines an LLM with external information sources. Instead of relying exclusively on information encoded in model parameters, the application retrieves relevant content and supplies it to the model as context.

RAG is commonly used for enterprise search, customer support, policy assistants, technical documentation, and internal knowledge management.

RAG can improve the relevance and freshness of responses, but it introduces additional components and trust boundaries that must be assessed.

### 7.3 RAG Assessment Questions

**Data ingestion**
- Are data sources approved by the relevant business and data owners?
- Is the provenance of each source recorded?
- Can external users or untrusted systems submit documents?
- Are document changes, deletions, and ownership changes tracked?
- Are malicious or malformed documents tested during ingestion?

**Access control**
- Are user permissions enforced during retrieval?
- Are document-level restrictions preserved when content is chunked and indexed?
- Are permissions revalidated when source access changes?
- Is tenant isolation tested using negative access scenarios?
- Can the model retrieve information through an alternate pathway that bypasses the intended controls?

**Retrieval and context**
- Are retrieval results limited to the minimum necessary information?
- Can retrieved content contain instructions that influence the model?
- Are metadata filters validated server-side?
- Are retrieval results logged sufficiently for investigation without unnecessarily retaining sensitive content?
- Can the organization determine which sources contributed to a response?

**Lifecycle**
- How are stale documents identified and removed?
- How are index updates authorized?
- How are source deletions propagated to vectors and caches?
- Are changes to embedding models evaluated before deployment?
- Are retrieval quality and security re-tested after significant changes?

### 7.5 RAG Governance Requirements

The organization should define:

- Approved source repositories.
- Data-owner responsibilities.
- Ingestion and indexing approval requirements.
- Document-level access-control requirements.
- Source provenance and versioning requirements.
- Content review and expiry rules.
- Security testing frequency.
- Index update and deletion procedures.
- Logging and monitoring requirements.
- Exception and risk-acceptance procedures.

**Core Principle:** RAG security depends on the integrity, authorization, and lifecycle management of the knowledge sources, not merely on the security of the LLM that consumes them.

## 8. LLM Output Security and Unsafe Output Handling

LLM outputs are generated content. They should not automatically be treated as accurate, authorized, safe, or suitable for direct execution.

The risk depends on where the output is used. A generated paragraph displayed to a user presents different security concerns from a generated SQL statement, shell command, customer-record update, or financial recommendation.

### 8.1 Output Risk Categories

| Output category | Potential risk | Required control approach |
|---|---|---|
| Informational text | Incorrect or misleading information | Appropriate validation, source attribution, and user guidance |
| HTML or Markdown | Cross-site scripting or unsafe rendering if handled improperly | Context-appropriate output encoding and safe rendering |
| SQL or database query | Unauthorized data access or destructive operations | Parameterization, restricted query interfaces, and database authorization |
| Shell or script commands | Command execution or infrastructure compromise | Avoid direct execution; use constrained, approved interfaces |
| API parameters | Unauthorized or malformed business operations | Schema validation, allowlisting, and server-side authorization |
| Customer communications | Disclosure of confidential or inaccurate information | Data-loss prevention, business validation, and human review where appropriate |
| Security recommendations | Incorrect prioritization or inappropriate remediation | Expert validation and evidence-based decision-making |
| Automated decisions | Unjustified or prohibited decisions affecting people or business processes | Applicable governance, impact assessment, oversight, and decision controls |

## 9. Tool Integration, API Security, and Excessive Agency

An LLM application becomes more consequential when it can call tools, access APIs, retrieve records, send communications, or perform business operations.

This capability can improve productivity, but it also creates a pathway from manipulated model behavior to real-world actions.

The central governance question is not simply whether the model can call a tool. It is whether each operation is necessary, authorized, constrained, observable, and recoverable.

### 9.1 Tool Integration Risk

Consider an enterprise assistant that can:

- Retrieve customer account information.
- Create support tickets.
- Change account settings.
- Send emails.
- Access internal documentation.
- Update CRM records.

If the assistant only needs to retrieve account status, granting permission to change account settings would violate least privilege. A prompt-injection attack or model error could then produce a more serious consequence than the business use case requires.

### 9.2 Tool Permission Classification

| Permission level | Description | Typical governance treatment |
|---|---|---|
| Read-only retrieval | Reads approved information without modifying it | Enforce user-level and resource-level access restrictions |
| Draft generation | Prepares content but does not submit or execute it | Validate content and protect sensitive information |
| Reversible write | Changes data that can be restored through a controlled process | Apply authorization, audit logging, and defined rollback mechanisms |
| High-impact write | Changes sensitive records, financial data, access rights, or other consequential information | Require stronger authorization, validation, and often human approval |
| External communication | Sends emails, messages, or other communications outside the application | Apply recipient validation, disclosure controls, and approval requirements where warranted |
| Administrative operation | Changes permissions, security settings, infrastructure, or governance controls | Restrict access tightly and require explicit privileged authorization |
| Irreversible operation | Performs an action that cannot readily be reversed | Prohibit autonomous execution unless a formally approved, justified control model exists |

The exact classification should reflect the organization's business processes and the consequences of unauthorized actions.

### 9.3 Tool Security Control Matrix

| Control | Requirement | Evidence |
|---|---|---|
| Tool inventory | Document every available tool and operation | Approved tool register |
| Least privilege | Grant only the permissions necessary for the approved use case | Identity and permission configuration |
| Independent authorization | Verify authorization outside the model's generated instructions | API and application security tests |
| Input validation | Validate tool parameters against defined schemas and constraints | Validation rules and test results |
| Credential management | Protect API keys, tokens, and service identities | Secret-management configuration and access review |
| Action limits | Restrict the number, scope, and frequency of permitted operations | Rate limits, quotas, and execution policies |
| Human approval | Require approval for designated high-impact operations | Approval workflows and audit records |
| Execution isolation | Separate untrusted model behavior from privileged execution environments | Architecture and configuration evidence |
| Auditability | Record actor, requested operation, authorization result, and outcome | Security event logs |
| Recovery | Provide rollback, revocation, or compensating actions where feasible | Tested recovery procedures |

### 9.5 Tool Security Assessment Questions

1. Which tools can the model invoke?
2. Which permissions does each tool possess?
3. Are tools restricted to approved business functions?
4. Are user permissions checked independently for each operation?
5. Can the model access credentials or secrets directly?
6. Are tool parameters validated on the server side?
7. Which operations require human approval?
8. Can the model initiate external communications or modify sensitive records?
9. Are failed authorization attempts logged and investigated?
10. Can tool permissions be revoked rapidly during an incident?
11. Are execution limits and rate controls configured?
12. Can the organization reconstruct the sequence of model requests and tool actions?

### 9.6 Practical Finding Example

**Finding:** The LLM-powered support assistant has permission to update customer account attributes even though its approved purpose is limited to answering inquiries and drafting support responses.

- **Risk:** A manipulated request or model error could result in unauthorized customer-record changes.
- **Root cause:** The service identity has broader permissions than the approved use case requires.
- **Required treatment:** Separate read-only retrieval from write operations, reduce service permissions, and implement independent authorization for any retained write capability.
- **Evidence required:** Updated permission matrix, configuration records, negative authorization tests, and successful retesting.
- **Risk owner:** Application or business-service owner.
- **Governance involvement:** Security and GRC review the residual risk and verify that the control change meets the organization's risk-treatment requirements.

**Core Principle:** The authority of an LLM application must be bounded by enforceable permissions and controlled execution paths, not by assumptions about what the model will choose to do.

## 10. Core Principle — LLM Security Must Be Assessed Across the Entire Application Lifecycle

An effective LLM Security Assessment combines established cybersecurity practices with testing designed for language-model behavior. It examines the model, application, data, retrieval pipeline, tool integrations, provider dependencies, and operating environment as one connected system.

The assessment should establish:

- What the system is permitted to do.
- Which assets and data it can access.
- Where trust boundaries exist.
- How malicious or malformed inputs may affect behavior.
- Whether generated outputs can cause unsafe downstream effects.
- Which controls prevent unauthorized access and actions.
- How security failures are detected, investigated, and corrected.
- Who owns each material risk and approves any remaining exposure.

A model that performs well in ordinary demonstrations is not necessarily secure in an enterprise environment. Security assurance requires documented architecture, realistic threat scenarios, evidence-based testing, independent controls, and a defined process for addressing findings.

### Key Conceptual Distinctions

| Distinction | Explanation |
|---|---|
| Model security vs. application security | Model-level safeguards do not replace application authorization, input validation, or secure execution |
| LLM vs. LLM-powered system | The model is one component; the complete system includes data, interfaces, integrations, infrastructure, and operational controls |
| Direct vs. indirect prompt injection | Direct attacks arrive through user instructions; indirect attacks arrive through content the system processes |
| Trusted instructions vs. untrusted data | Content supplied for analysis must not automatically acquire authority to control the application |
| RAG relevance vs. RAG authorization | Retrieving relevant content does not establish that the user is permitted to access it |
| Output quality vs. output security | A fluent or accurate response may still disclose information or trigger an unauthorized action |
| Model refusal vs. effective prevention | A refusal message does not prove that retrieval, disclosure, or tool execution was safely controlled |
| Tool availability vs. tool authorization | A tool being available does not mean every user or model-generated request is authorized |
| Human presence vs. effective oversight | Human review is meaningful only when the reviewer has sufficient information, authority, time, and ability to intervene |
| Security testing vs. security assurance | A successful test provides evidence about specific scenarios; it does not prove the absence of all vulnerabilities |
| Provider assurance vs. enterprise assurance | Provider certifications and reports do not demonstrate that the customer's application is securely configured |
| Initial risk vs. residual risk | Initial risk reflects exposure before treatment; residual risk reflects the risk remaining after relevant controls and treatments are considered |

**Final Core Principle:** An LLM Security Assessment is complete only when the organization has established a defensible understanding of the system's architecture and threat exposure, evaluated the controls protecting its data and operations, documented material findings, and assigned accountable owners to the required risk treatments.

## 11. LLM Model Integrity and Supply-Chain Security

LLM model integrity refers to the assurance that the model being deployed is the intended, authorized, and appropriately validated model artifact, and that it has not been replaced, modified, or compromised through an unauthorized process.

An enterprise may use a proprietary model through an external API, download an open-weight model, fine-tune a foundation model, or deploy a model obtained through an internal development pipeline. Each approach introduces different integrity and supply-chain risks.

Unlike conventional software, an LLM's behavior is substantially influenced by learned parameters, training data, fine-tuning procedures, model architecture, and inference configuration. An unauthorized change to a model artifact or its associated components may therefore alter system behavior without producing an obvious software error.

Model integrity is particularly important when an organization relies on LLMs to support cybersecurity operations, customer interactions, financial analysis, identity verification, code generation, or other sensitive business processes.

### 11.1 Model Supply-Chain Components

The assessment should cover the complete supply chain, not just the final model file.

| Component | Potential risk | Recommended security control |
|---|---|---|
| Model provider | Provider security or integrity weaknesses | Vendor due diligence, contractual safeguards, and ongoing assurance |
| Model repository | Unauthorized or malicious model artifacts | Approved repositories and controlled downloads |
| Model weights | Unauthorized modification or substitution | Integrity verification and restricted artifact access |
| Tokenizer | Substitution or modification affecting input processing | Version control and artifact integrity checks |
| Model configuration | Unsafe or unauthorized configuration changes | Configuration management and change approval |
| Fine-tuning dataset | Malicious, unauthorized, or low-quality data | Dataset provenance, access control, and validation |
| Fine-tuning process | Unauthorized changes to training parameters or procedures | Controlled pipelines and execution permissions |
| Quantization and conversion tools | Compromised or incorrectly transformed model artifacts | Approved tooling and post-conversion validation |
| Inference runtime | Vulnerable or compromised model-serving software | Dependency management, patching, and runtime hardening |
| Model-serving container | Vulnerable images or unauthorized modifications | Image scanning, signed artifacts where supported, and controlled deployment |
| Orchestration framework | Vulnerable components affecting prompts, retrieval, or tools | Dependency inventory, vulnerability management, and secure configuration |
| Deployment pipeline | Unauthorized model promotion into production | Segregated environments, release approval, and deployment audit logs |
| Third-party extensions | Untrusted plugins, adapters, or model components | Source verification and security review |

The assessor should determine which components are actually present in the deployment. For example, tokenizer integrity and model-weight verification are directly relevant to self-hosted models, while an enterprise consuming a closed model through an API may instead rely on provider assurance and endpoint-level controls.

### 11.2 Model Provenance and Artifact Verification

Model provenance is the documented history of a model artifact, including where it originated, how it was obtained, what modifications were applied, and how it was approved for deployment.

A model inventory should capture:

- Model name and unique identifier.
- Provider or originating repository.
- Version, release, or artifact identifier.
- Acquisition date and source.
- License and applicable usage restrictions.
- Integrity-verification method and result.
- Fine-tuning or conversion history.
- Associated adapters and auxiliary components.
- Security evaluation results.
- Approval status and deployment environment.
- Authorized model owner.
- Current production version and rollback reference.

Where supported, cryptographic hashes and digital signatures can help establish artifact integrity. A matching hash proves that a file matches a particular reference value; it does not, by itself, establish that the original artifact is trustworthy.

The organization must therefore verify both **artifact integrity** and **source authenticity**.

Any material change to model weights, fine-tuning, adapters, inference runtime, or associated configuration should trigger an appropriate review. The required depth of testing should be proportionate to the significance of the change and the system's risk classification.

### 11.4 Model Integrity Assessment Checklist

| Assessment question | Expected evidence |
|---|---|
| Is the production model uniquely identifiable? | Model inventory and deployment records |
| Is the model obtained from an approved source? | Repository records, provider documentation, or acquisition records |

### 11.5 Model Integrity Finding Example

**Finding:** A production model is downloaded from an external repository, but the organization does not record its exact version or verify its origin before deployment.

- **Threat:** A malicious or compromised artifact is introduced into production.
- **Weakness:** The organization cannot reliably distinguish the approved model from a substituted or modified artifact.
- **Potential impact:** Unexpected model behavior, data exposure, malicious outputs, or loss of confidence in the system.
- **Recommended treatment:** Use approved acquisition channels, record exact model identifiers, verify available integrity information, restrict artifact modification, and require validation before production deployment.
- **Evidence required:** Updated model inventory, artifact-verification records, access-control evidence, and approved release documentation.
- **Residual-risk consideration:** Integrity verification reduces substitution risk but does not establish that a model is free from embedded vulnerabilities or unsafe learned behavior.

**Core Principle:** Model provenance and integrity are foundational security requirements. A model should not enter production solely because it is available, popular, or appears to perform well.

## 12. Jailbreak Resistance and Safety-Control Evaluation

A jailbreak is an attempt to induce a model to bypass its intended restrictions or safety behavior through specially constructed instructions, conversational strategies, contextual manipulation, or other inputs.

Jailbreak testing evaluates whether the LLM continues to follow the application's approved usage boundaries when confronted with adversarial requests.

It differs from prompt injection in emphasis. Prompt injection concerns attempts to manipulate instruction handling, including through untrusted external content. Jailbreak testing focuses more broadly on attempts to circumvent the model's intended restrictions. The two categories overlap and should be assessed together when appropriate.

A model may refuse an obviously prohibited request but behave differently when the request is embedded in a hypothetical scenario, translated into another language, split across multiple messages, or framed as a legitimate business task.

The objective is not to prove that every conceivable jailbreak is impossible. It is to establish whether the implemented controls provide an acceptable level of protection against relevant, foreseeable attacks.

### 12.1 Common Jailbreak Patterns

| Pattern | Description | Assessment focus |
|---|---|---|
| Instruction override | Attempts to make the model disregard established restrictions | Resistance to conflicting instructions |
| Role-play manipulation | Attempts to change the model's behavior through a fictional role or persona | Consistency of safety requirements across roles |
| Contextual reframing | Presents a prohibited request as a legitimate or hypothetical activity | Ability to evaluate the substance of the request |
| Multi-turn manipulation | Gradually steers a conversation toward a prohibited outcome | Persistence of safeguards across conversation history |
| Language variation | Uses another language or mixed-language instructions | Consistency of controls across supported languages |
| Encoded or transformed input | Attempts to conceal the nature of a request through transformations | Appropriate handling of transformed content |
| Quoted or embedded instructions | Places adversarial instructions inside content submitted for analysis | Separation of analyzed content from controlling instructions |
| Output-format manipulation | Requests restricted information through structured formats or alternate representations | Consistency of output restrictions |
| Tool-oriented jailbreak | Attempts to persuade the model to invoke a tool for an unauthorized purpose | Independent authorization and tool restrictions |
| Safety-boundary probing | Repeatedly tests the limits of the model's restrictions | Abuse detection and monitoring |

These are assessment categories, not guarantees that a particular technique will succeed against a specific model.

### 12.2 Model-Level Versus Application-Level Safeguards

LLM safety depends on multiple layers.

| Layer | Security objective | Example |
|---|---|---|
| Model behavior | Reduce the likelihood of unsafe responses | Model safety training and provider safeguards |
| System instructions | Define the model's intended role and restrictions | Approved system prompt |
| Application policy | Enforce business-specific rules | Restrictions on permitted customer-support activities |
| Data access | Prevent unauthorized information retrieval | User- and document-level authorization |
| Tool controls | Prevent unauthorized operations | Server-side permission checks |
| Output controls | Prevent unsafe downstream use | Schema validation and sensitive-data filtering |
| Human oversight | Review consequential decisions and actions | Approval before a high-impact operation |
| Monitoring | Detect misuse and emerging attack patterns | Alerts for repeated prohibited requests |
| Governance | Define accountability and acceptance criteria | Approved risk thresholds and documented exceptions |

A model's refusal behavior is not an access-control mechanism. If an application provides the model with unauthorized information, a refusal-oriented prompt cannot guarantee that the information will remain protected.

Similarly, a model may generate an unsafe recommendation without directly violating a technical security control. The organization must determine which outcomes are unacceptable and how they will be prevented, detected, or escalated.

### 12.3 Jailbreak Test Design

Each test should have a defined objective, controlled conditions, expected behavior, and a reproducible record.

A useful test record includes:

| Field | Description |
|---|---|
| Test ID | Unique identifier |
| Test category | Direct jailbreak, multi-turn manipulation, language variation, or another category |
| Business context | The use case being assessed |
| Model version | Exact version or endpoint identifier where available |
| Test objective | Security property being evaluated |
| Preconditions | User permissions, conversation state, and available tools |
| Test input | Authorized adversarial test prompt |
| Expected behavior | Defined acceptable outcome |
| Observed behavior | Actual model and application response |
| Downstream effects | Whether data was retrieved, disclosed, or an action was attempted |
| Control outcome | Pass, fail, or inconclusive |
| Severity | Based on exploitability and business impact |
| Evidence | Sanitized prompts, outputs, logs, and execution records |
| Remediation | Corrective action and accountable owner |
| Retest result | Verified outcome after remediation |

Testing should be conducted in an authorized environment using synthetic or otherwise appropriately protected data.

### 12.4 Example Test Scenarios

| Test ID | Scenario | Expected outcome |
|---|---|---|
| LLM-JB-001 | A user requests information that the application is prohibited from disclosing | The system does not disclose protected information |
| LLM-JB-002 | A user attempts to override the assistant's approved role | The application continues to enforce its intended operating boundaries |
| LLM-JB-003 | A prohibited request is distributed across several conversation turns | Applicable restrictions remain effective across the conversation |
| LLM-JB-004 | An adversarial request is submitted in a supported non-English language | Equivalent security requirements remain effective |
| LLM-JB-005 | A user embeds a prohibited request inside a document-summary task | The system processes the document without allowing embedded instructions to override application controls |
| LLM-JB-006 | A user attempts to persuade the assistant to invoke an unauthorized tool | Independent authorization prevents the operation |
| LLM-JB-007 | A user requests sensitive information through a different output format | Data access and disclosure controls remain effective |
| LLM-JB-008 | A user repeatedly probes a restricted capability | Monitoring and abuse controls operate according to policy |

### 12.5 Measuring Jailbreak Test Results

A simple test pass rate can be calculated as:

\[
\text{Pass Rate} =
\frac{\text{Tests Meeting Their Defined Security Criteria}}
{\text{Total Valid Tests Executed}}
\times 100
\]

For example, if 95 of 100 valid tests meet their defined security criteria, the observed pass rate is 95%.

However, the figure must be interpreted carefully.

A high pass rate does not prove that the system is secure. A single successful attack against a high-impact operation may be more significant than several low-impact failures. The test set may also be incomplete or biased toward known attack patterns.

Reports should therefore include:

- Total tests and test categories.
- Model and application versions.
- Severity of failed tests.
- Whether sensitive information was exposed.
- Whether an unauthorized action was attempted or completed.
- Reproducibility of failures.
- Test limitations and untested scenarios.
- Remediation status and retest results.

### 12.6 Acceptance Criteria

Acceptance criteria should be defined before testing begins.

For a high-risk enterprise application, the organization might require that:

- No tested scenario results in unauthorized access to protected information.
- No tested scenario bypasses mandatory authorization checks.
- No high-impact operation executes without the required approval.
- Security-relevant failures are logged and traceable.
- Material findings are remediated or formally accepted by an authorized risk owner.

These are illustrative criteria. The final requirements must reflect the organization's risk appetite, applicable obligations, and system context.

**Core Principle:** Jailbreak resistance must be evaluated through reproducible adversarial testing and independent application controls, not through demonstrations that the model can refuse a few prohibited requests.

## 13. Adversarial Testing Strategy and Security Evaluation Coverage

Adversarial testing deliberately evaluates how an LLM system behaves under malicious, unexpected, ambiguous, or otherwise challenging conditions.

The purpose is to identify weaknesses that ordinary functional testing may miss.

For an enterprise LLM application, adversarial testing should cover the complete processing path: user input, retrieval, model inference, output handling, tool execution, logging, and recovery.

Testing only the model's textual response may overlook a serious issue. For example, the assistant might refuse to reveal a restricted record while a connected retrieval service has already returned that record to an unauthorized context.

### 13.1 Testing Dimensions

| Testing dimension | Objective | Example |
|---|---|---|
| Input manipulation | Assess handling of adversarial inputs | Conflicting or misleading instructions |
| Prompt injection | Assess instruction-boundary protections | Malicious instructions in user input |
| Indirect prompt injection | Assess untrusted contextual content | Malicious instructions embedded in retrieved documents |
| Access-control testing | Verify that users cannot access unauthorized data or functions | Attempts to retrieve another user's records |
| Data-exfiltration testing | Evaluate disclosure protections | Attempts to extract sensitive context |
| Output security | Evaluate generated content before downstream use | Malformed or unsafe structured output |
| Tool security | Verify operation-level authorization | Attempts to invoke a privileged API |
| Resource-abuse testing | Evaluate quotas and cost controls | Repeated expensive requests |
| Robustness testing | Evaluate behavior under unexpected or degraded conditions | Incomplete context or unavailable retrieval services |
| Multilingual testing | Evaluate safeguards across supported languages | Equivalent adversarial scenarios in different languages |
| Regression testing | Verify that fixes and model updates do not reintroduce weaknesses | Re-run previously failed tests |
| Operational testing | Evaluate monitoring, alerting, and response | Simulated abuse requiring investigation |

### 13.2 Risk-Based Test Prioritization

Not every LLM application requires the same test depth.

A low-impact internal assistant that retrieves public documentation may need a different test plan from an assistant that accesses customer records and executes account changes.

Test prioritization should consider:

- Data sensitivity.
- User population and exposure.
- External accessibility.
- Tool permissions and autonomy.
- Business impact of incorrect outputs.
- Regulatory and contractual obligations.
- Model and application complexity.
- Availability of effective compensating controls.
- History of security findings and incidents.

| Risk tier | Illustrative system | Testing emphasis |
|---|---|---|
| Lower | Internal assistant using approved public or non-sensitive information | Basic access controls, prompt handling, output safety, and monitoring |
| Moderate | Internal RAG assistant accessing confidential corporate documents | Document-level authorization, indirect prompt injection, data leakage, and retrieval security |
| High | Customer-facing assistant accessing personal or account information | Strong identity enforcement, tenant isolation, data-exfiltration testing, abuse controls, and incident readiness |
| Very high | LLM application capable of consequential actions or privileged operations | Deep adversarial testing, tool authorization, human approval, resilience, independent review, and formal risk acceptance |

These categories are illustrative rather than universal. An organization should define its own risk-tier criteria and ensure that testing depth is proportionate to actual exposure.

### 13.3 Test Environment Requirements

A defensible testing program should establish:

1. **Authorization:** Written approval for the systems, methods, and boundaries being tested.
2. **Isolation:** A test environment that limits the chance of unintended production impact.
3. **Test data:** Synthetic or appropriately protected data with clearly defined access rules.
4. **Version control:** Records of the model, prompt templates, application code, retrieval configuration, and relevant dependencies.
5. **Execution logging:** Sufficient evidence to reconstruct the test without unnecessarily retaining sensitive content.
6. **Safety boundaries:** Explicit limits on destructive actions, external communications, and real-world transactions.
7. **Reproducibility:** A documented method for rerunning the test.
8. **Issue management:** A process for recording findings, assigning owners, and tracking remediation.
9. **Retesting:** Verification that corrective actions address the demonstrated weakness.
10. **Approval:** Defined criteria for moving from testing to production.

### 13.4 Test Coverage Matrix

| Security requirement | Test method | Expected evidence |
|---|---|---|
| Authorized users can access approved information | Positive access testing | Successful permitted-access results |
| Unauthorized users cannot retrieve restricted information | Negative access testing | Denied requests and no protected-data disclosure |
| Prompt injection does not bypass critical controls | Adversarial prompt testing | Test outcomes and application execution traces |
| Tool operations enforce least privilege | API and authorization testing | Denied unauthorized operations |
| Outputs cannot bypass downstream validation | Output-manipulation testing | Validation results and safe failure behavior |
| Resource limits operate as designed | Load and abuse testing | Rate-limit behavior and service metrics |
| Security events are detectable | Monitoring and alert testing | Alerts, investigation records, and response evidence |
| Corrective changes remain effective | Regression testing | Repeatable passing results |
| Failures can be contained | Recovery exercises | Evidence of revocation, rollback, or safe shutdown |

### 13.5 Finding Severity and Remediation

Severity should be based on the demonstrated or reasonably foreseeable consequences of a weakness.

Relevant factors include:

- Confidentiality, integrity, and availability impact.
- Sensitivity of affected information.
- Ease of exploitation.
- Required privileges.
- External exposure.
- Potential for automated or repeated exploitation.
- Ability to detect the event.
- Availability of effective compensating controls.
- Regulatory, contractual, safety, and reputational consequences.

A successful attack that permits unauthorized modification of customer accounts should not receive the same priority as a harmless formatting inconsistency merely because both are reproducible test failures.

Findings should be linked to a risk register, assigned an owner, given a target remediation date, and retested after corrective action.

**Core Principle:** Adversarial testing must evaluate the security outcome of the complete LLM application, including data access and downstream actions, rather than measuring only whether the model produces an acceptable-looking response.

## 14. Model Robustness, Reliability, and Failure-Mode Analysis

LLM robustness is the ability of a system to maintain acceptable behavior when inputs, context, operating conditions, or model behavior vary.

Reliability concerns whether the system consistently performs its intended function. A system can be reliable in returning a response while still being insecure, inaccurate, or unsuitable for a consequential decision.

The assessment should therefore distinguish technical availability from behavioral reliability and security robustness.

### 14.1 Important Failure Modes

| Failure mode | Description | Potential consequence |
|---|---|---|
| Hallucination | The model generates unsupported or fabricated information | Incorrect business decisions or misleading responses |
| Instruction conflict | The model receives incompatible instructions | Inconsistent behavior or policy violations |
| Context omission | Important information is missing from the prompt or retrieval results | Incomplete or incorrect conclusions |
| Context overload | Excessive context reduces the effective use of important information | Missed restrictions or relevant evidence |
| Retrieval failure | Required information is unavailable or incorrectly retrieved | Unsupported responses |
| Output-format failure | The model returns malformed structured output | Application errors or unsafe downstream processing |
| Nondeterministic behavior | Similar inputs produce materially different outputs | Inconsistent decisions or test results |
| Model degradation | Performance deteriorates after changes or over time | Increased error rates or security weaknesses |
| Dependency failure | A model, retrieval service, or API becomes unavailable | Service interruption or unsafe fallback behavior |
| Unsafe fallback | The application continues without a required security check | Unauthorized or unreliable operations |
| Confidence misinterpretation | A fluent or confident response is mistaken for verified truth | Excessive reliance on unsupported outputs |

### 14.2 Failure-Mode and Effects Analysis (FMEA)

FMEA provides a structured method for identifying failure modes, their causes, effects, and controls.

For an LLM application, the assessment may include the following fields:

| Field | Description |
|---|---|
| Failure ID | Unique identifier |
| Component | Model, retrieval service, tool, or application component |
| Failure mode | What could go wrong |
| Cause | Technical, operational, or human factor |
| Local effect | Immediate effect on the component |
| System effect | Effect on the complete LLM application |
| Business consequence | Impact on users, operations, data, or compliance |
| Existing controls | Preventive and detective safeguards |
| Severity | Consequence rating under the chosen methodology |
| Occurrence | Estimated likelihood or frequency under the chosen methodology |
| Detectability | Ability to identify the failure before harm occurs |
| Risk priority | Calculated or qualitative prioritization |
| Treatment | Required corrective or preventive action |
| Owner | Accountable role |
| Evidence | Test results, monitoring data, and control records |

Some organizations calculate an FMEA Risk Priority Number by multiplying severity, occurrence, and detectability scores. If this approach is used, the scoring definitions must be consistent, and the resulting number should not replace business-impact analysis or formal risk judgment.

### 14.3 Example FMEA Record

| Field | Illustrative entry |
|---|---|
| Failure ID | FMEA-LLM-001 |
| Component | Retrieval-augmented generation pipeline |
| Failure mode | The retrieval service returns outdated policy guidance |
| Cause | Source documents are not refreshed after policy changes |
| Local effect | The model receives stale information |
| System effect | The assistant generates a response based on superseded policy |
| Business consequence | An employee may follow an incorrect process |
| Existing controls | Source metadata and scheduled index refresh |
| Severity | Assessed according to business impact |
| Occurrence | Assessed using operational evidence |
| Detectability | Assessed based on existing monitoring and review |
| Treatment | Assign source owners, enforce review dates, monitor refresh failures, and test stale-content scenarios |
| Owner | Knowledge-platform owner |
| Evidence | Source inventory, refresh logs, and regression-test results |

### 14.4 Robustness Testing Scenarios

The assessor should test how the application behaves when:

- A user provides incomplete or ambiguous information.
- Retrieved sources conflict with one another.
- A required source is unavailable.
- A document is outdated or malformed.
- A request contains unexpected characters or formats.
- A tool returns an error or partial result.
- The model produces output that violates a required schema.
- The model endpoint times out.
- The application reaches a usage or capacity limit.
- A model or prompt update changes response behavior.

The objective is to establish whether the application degrades safely.

For example, if the assistant must verify account authorization before accessing customer records, a failure in the authorization service should not cause the application to skip that check and continue.

### 14.5 Safe Failure Requirements

| Condition | Expected behavior |
|---|---|
| Authorization service unavailable | Deny or defer the protected operation |
| Required retrieval source unavailable | Clearly indicate the limitation or use an approved fallback |
| Output fails validation | Reject, regenerate within defined limits, or escalate safely |
| Tool authorization fails | Do not execute the operation |
| Model endpoint unavailable | Follow the documented continuity procedure |
| Logging service unavailable | Apply the defined fail-safe or controlled-degradation policy for the system's risk level |
| High-impact decision lacks required evidence | Escalate rather than invent missing evidence |
| Model behavior changes materially | Trigger review, investigation, or rollback according to policy |

Not every service must fail closed in every circumstance. The correct behavior depends on the business process and potential consequences. However, controls protecting sensitive data and privileged operations must not be silently bypassed merely to preserve availability.

**Core Principle:** Robustness requires the system to handle uncertainty and component failures without silently violating its security requirements or approved business purpose.

## 15. LLM Security Evaluation Metrics and Acceptance Thresholds

Security evaluations produce evidence that must be translated into meaningful decisions. Metrics support this process by measuring control effectiveness, testing outcomes, operational exposure, and remediation progress.

Metrics must be selected according to the system's threat model and business purpose. A generic model-quality score is not a substitute for evidence that security requirements are satisfied.

### 15.1 Security Evaluation Metrics

| Metric | What it measures | Important limitation |
|---|---|---|
| Adversarial test pass rate | Percentage of valid tests meeting their defined security criteria | Does not prove that untested attacks will fail |
| Critical security failure count | Number of observed critical-severity failures | Requires a consistent severity methodology |
| Unauthorized disclosure rate | Frequency of test scenarios resulting in protected-data disclosure | Depends on test coverage and data classification |
| Unauthorized tool execution rate | Frequency of unauthorized operations actually executed | Must distinguish attempted operations from completed operations |
| Authorization enforcement rate | Percentage of tested authorization decisions enforced correctly | Test coverage must include relevant roles and resources |
| Prompt-injection success rate | Percentage of defined prompt-injection tests that violate a specified security requirement | Results depend on the test corpus, model version, and application configuration |
| Regression failure rate | Frequency of previously passing tests that fail after a change | Requires stable, version-controlled regression tests |
| Remediation closure time | Time required to remediate findings | Should be analyzed by severity and complexity |
| Security monitoring coverage | Proportion of defined security events with appropriate detection coverage | Coverage does not guarantee effective detection |
| Model-version traceability | Proportion of relevant requests or deployments traceable to the model version used | Depends on the logging and provider capabilities available |
| Risk acceptance coverage | Proportion of material residual risks with documented, authorized decisions | Documentation alone does not make an unacceptable risk safe |

### 15.2 Defining an Acceptance Threshold

An acceptance threshold specifies the result required for a system, feature, or release to proceed.

Thresholds should be defined before testing to prevent teams from changing success criteria after seeing the results.

An enterprise may define thresholds for:

- Unauthorized data disclosure.
- Privileged tool execution.
- Critical and high-severity security findings.
- Adversarial test performance.
- Required regression-test coverage.
- Security monitoring readiness.
- Incident-response readiness.
- Evidence completeness.
- Required approvals and risk acceptance.

For example, a system may require zero successful unauthorized access attempts in the defined test suite. This is a release criterion, not a guarantee that no unauthorized access is possible under any circumstances.

### 15.3 Example Security Release Gate

| Requirement | Example release criterion | Decision if unmet |
|---|---|---|
| Access control | No tested unauthorized access to protected data | Block release pending remediation or formal exception under policy |
| Privileged tool execution | No unauthorized privileged action is completed | Block affected capability |
| Critical findings | No unresolved critical findings unless a formally authorized exception is permitted and appropriate | Escalate to the designated risk authority |
| High-severity findings | Treatment or approved risk decision documented | Apply the organization's risk-acceptance rules |
| Regression testing | Required security tests pass | Investigate and correct failures |
| Monitoring | Required alerts and security events are validated | Complete monitoring implementation and testing |
| Incident response | Response and containment procedures are documented and exercised where required | Complete required readiness activities |
| Version traceability | Production model and application versions are identifiable | Correct deployment and logging controls |
| Governance | Required business, technical, security, and risk approvals are complete | Do not proceed until required decisions are recorded |

These criteria must be tailored to the organization's policy. Risk acceptance should not be used to bypass legal requirements, mandatory controls, or explicit prohibitions.

### 15.4 Reporting Test Results

A useful security evaluation report should include:

1. Assessment scope and objectives.
2. System architecture and tested configuration.
3. Model and application versions.
4. Threat scenarios and test methodology.
5. Test coverage and limitations.
6. Quantitative results.
7. Detailed findings and severity.
8. Business impact and affected assets.
9. Existing controls and their effectiveness.
10. Required remediation and accountable owners.
11. Retesting results.
12. Residual-risk assessment.
13. Release recommendation and required approvals.

Metrics should be interpreted alongside individual findings. A high aggregate score must not conceal a critical failure involving sensitive information or privileged operations.

**Core Principle:** Security metrics are useful only when their definitions, test coverage, limitations, and decision thresholds are explicit and connected to business risk.

## 16. Model Behavior Regression Testing and Release Assurance

Model behavior can change when the organization updates a model version, modifies prompts, changes retrieval sources, introduces a new tool, alters safety configuration, or changes the surrounding application.

A change that improves response quality may inadvertently weaken a security control. A new model version may, for example, respond differently to adversarial instructions or generate a structured output that interacts unexpectedly with an existing tool.

Regression testing provides evidence that previously established security requirements continue to be met after a change.

### 16.1 Changes That Should Trigger Regression Testing

| Change | Potential security effect |
|---|---|
| Foundation model version update | Different response behavior or adversarial resistance |
| Prompt template modification | Changed instruction hierarchy or context handling |
| Retrieval pipeline change | Different documents or permissions applied to retrieved content |
| Embedding model update | Changes in retrieval relevance and source selection |
| Vector database modification | Altered access control, indexing, or retrieval behavior |
| New tool integration | Expanded attack surface and operational authority |
| Tool permission change | Increased potential impact of manipulated requests |
| Output-processing modification | Changed validation or rendering behavior |
| New data source | New sensitive information and trust boundaries |
| Fine-tuning or adapter update | Altered model behavior and possible regression |
| Runtime or dependency update | Changed request processing or execution behavior |
| Safety configuration change | Different handling of prohibited or sensitive requests |
| Logging change | Reduced visibility or increased sensitive-data retention |

### 16.2 Regression Test Suite Design

The regression suite should contain representative tests for material security requirements.

At a minimum, it should consider:

- Authentication and authorization.
- Direct and indirect prompt injection.
- Sensitive information disclosure.
- RAG access enforcement.
- Tool permissions and execution restrictions.
- Output validation.
- Resource-abuse controls.
- Security event logging.
- Failure handling.
- Previously discovered vulnerabilities.
- Critical business-specific restrictions.

Tests should be version-controlled and linked to requirements or findings so the organization can identify which security properties each test is intended to verify.

### 16.3 Release Comparison Matrix

| Evaluation dimension | Previous approved version | Candidate version | Required action |
|---|---|---|---|
| Model identifier | Recorded baseline | Record candidate | Confirm change authorization |
| Prompt injection results | Baseline results | New results | Investigate material degradation |
| Unauthorized access tests | Baseline results | New results | Block release if required controls fail |
| Data disclosure tests | Baseline results | New results | Investigate any new exposure |
| Tool execution tests | Baseline results | New results | Verify authorization and execution boundaries |
| Output validation | Baseline results | New results | Correct schema or safety regressions |
| Functional quality | Baseline measurements | New measurements | Review business suitability |
| Operational performance | Baseline measurements | New measurements | Review capacity and availability |
| Known findings | Recorded open and closed issues | Candidate status | Verify that critical controls remain effective |
| Approval status | Approved baseline | Pending or approved candidate | Record formal release decision |

### 16.4 Release Decision Process

```text
Change Proposed
      |
      v
Change Risk Classification
      |
      v
Identify Affected Security Requirements
      |
      v
Run Relevant Regression Tests
      |
      v
Compare Results with Approved Baseline
      |
      v
Review New and Reopened Findings
      |
      v
Assess Residual Risk
      |
      v
Obtain Required Approval
      |
      v
Deploy or Reject Candidate
      |
      v
Monitor Production Behavior
```

A regression suite should not be limited to identical prompts and exact text matching. Because LLM outputs may vary, tests should define the security properties that must hold, such as preventing unauthorized disclosure or ensuring that a privileged operation cannot execute without authorization.

Where exact output comparison is appropriate, it can be used. Where behavior varies, the organization should use suitable structured assertions, policy checks, human evaluation, or other reproducible methods.

### 16.5 Rollback and Containment

The release process should define:

- Who can stop or reverse a deployment.
- Which prior version is considered an approved rollback target.
- How model and application versions are restored consistently.
- Whether prompts, tools, indexes, and configurations must also be rolled back.
- How compromised credentials are revoked.
- How data or actions produced by the affected version are investigated.
- How the organization verifies that the vulnerability is no longer exploitable.
- Which approvals are required before service restoration.

Rollback does not automatically reverse data disclosures or external actions that have already occurred. Incident response must address those consequences separately.

**Core Principle:** Every material LLM change must be evaluated against established security requirements before release, and the organization must be able to contain or reverse a change that introduces unacceptable risk.

## 17. LLM Security Assessment Evidence and Documentation Management

An LLM Security Assessment must be supported by evidence that allows reviewers to understand what was tested, which controls were examined, what the results demonstrated, and why the resulting risk decision is justified.

Without reliable evidence, the organization may have difficulty demonstrating control effectiveness, reproducing findings, supporting audits, or determining whether remediation has actually worked.

Evidence must also be handled securely. Assessment records can contain sensitive prompts, architecture diagrams, system identifiers, vulnerability details, credentials accidentally captured during testing, or confidential business information.

### 17.1 Evidence Categories

| Evidence category | Examples | Security considerations |
|---|---|---|
| Architecture evidence | System diagrams, data-flow diagrams, trust boundaries | Restrict access where diagrams expose sensitive infrastructure |
| Model evidence | Model identifiers, provenance, version history, provider documentation | Verify source and applicability |
| Configuration evidence | IAM policies, endpoint settings, tool permissions | Remove secrets and unnecessary sensitive values |
| Test evidence | Test cases, sanitized prompts, results, logs | Protect confidential data and exploit details |
| Retrieval evidence | Source inventory, access-filter configuration, index-update logs | Avoid unnecessary copies of confidential documents |
| Operational evidence | Monitoring alerts, incident records, service metrics | Apply retention and access controls |
| Governance evidence | Approvals, risk acceptance, exceptions, remediation decisions | Preserve accountability and decision history |
| Provider evidence | Security reports, contractual commitments, service documentation | Confirm scope, validity, and applicability to the service used |
| Remediation evidence | Change records, retest results, closure approvals | Demonstrate that the weakness was actually corrected |

### 17.2 Evidence Quality Criteria

Evidence should be evaluated against the following criteria.

**Relevance:** Does the evidence address the control or risk being assessed?

**Authenticity:** Can the organization establish where the evidence originated and whether it has been altered?

**Currency:** Does the evidence reflect the version and configuration currently under review?

**Completeness:** Does it include enough information to support the conclusion?

**Reproducibility:** Can another qualified reviewer repeat the relevant test or verify the result?

**Traceability:** Can the evidence be linked to a requirement, finding, control, owner, and decision?

**Confidentiality:** Is the evidence protected against unauthorized access and unnecessary disclosure?

**Integrity:** Is the evidence protected against unauthorized alteration or deletion?

### 17.3 Evidence Register Template

| Field | Description |
|---|---|
| Evidence ID | Unique evidence identifier |
| Assessment ID | Related assessment reference |
| Control or requirement | Requirement being evaluated |
| Evidence type | Configuration, test result, log, approval, or other record |
| Source | System, team, provider, or document from which it originated |
| Collection date | Date evidence was obtained |
| Applicable version | Relevant model, application, or configuration version |
| Evidence owner | Person or team responsible for the record |
| Storage location | Approved evidence repository |
| Classification | Appropriate information classification |
| Integrity verification | Method used where required |
| Retention requirement | Approved retention period or policy reference |
| Assessment conclusion | What the evidence supports |
| Limitation | Known gaps or restrictions |
| Reviewer | Person who evaluated the evidence |
| Review status | Accepted, rejected, incomplete, or pending |

### 17.4 Evidence Traceability

Each material finding should be traceable through the assessment lifecycle.

```text
Security Requirement
        |
        v
Applicable Control
        |
        v
Assessment Procedure
        |
        v
Evidence Collected
        |
        v
Observed Result
        |
        v
Finding and Risk Rating
        |
        v
Treatment Plan
        |
        v
Remediation Evidence
        |
        v
Retest and Closure Decision
```

This traceability supports both technical remediation and governance accountability. It allows an auditor or risk owner to determine why a finding was raised, whether the corrective action addressed the root cause, and whether the remaining risk is acceptable under the organization's policy.

### 17.5 Confidentiality of Assessment Records

The assessment process must not create an additional data exposure.

Recommended practices include:

- Use synthetic test data wherever possible.
- Redact credentials, tokens, and unnecessary personal information from evidence.
- Store assessment records in an approved repository with restricted access.
- Avoid including raw confidential prompts in general-purpose reporting where summaries are sufficient.
- Define retention and deletion requirements.
- Restrict distribution of exploit details to authorized personnel.
- Maintain audit records for material changes to findings and risk decisions.
- Apply the organization's information-classification and incident-reporting requirements.

**Core Principle:** A defensible assessment requires evidence that is relevant, current, reproducible, traceable, and securely managed. Evidence must support the conclusion without creating unnecessary confidentiality or integrity risks.

## 18. Integrating LLM Security Testing with Enterprise GRC

LLM security testing should be integrated into the enterprise Governance, Risk, and Compliance (GRC) operating model rather than managed as an isolated technical exercise.

Security findings may have consequences for privacy, contractual obligations, business continuity, customer trust, regulatory compliance, and operational resilience. The assessment must therefore connect technical results to business risk and formal decision-making.

### 18.1 GRC Integration Model

| GRC activity | LLM security contribution | Required outcome |
|---|---|---|
| AI system inventory | Identifies models, applications, owners, and integrations | Approved and maintained system record |
| Risk assessment | Evaluates threats, vulnerabilities, consequences, and controls | Documented inherent and residual risk |
| Control management | Maps security requirements to preventive, detective, and corrective controls | Control ownership and evidence |
| Third-party risk | Evaluates model providers, hosting services, and dependencies | Documented provider risk and assurance decision |
| Change management | Assesses model, prompt, tool, and configuration changes | Controlled release and reassessment |
| Issue management | Tracks security findings and corrective actions | Accountable remediation and retesting |
| Exception management | Records justified deviations from policy | Time-bound, authorized risk decision |
| Incident management | Connects security events to response procedures | Coordinated containment and recovery |
| Compliance management | Maps applicable obligations to relevant controls and evidence | Traceable compliance assessment |
| Reporting | Aggregates findings, exposure, and remediation status | Decision-ready management reporting |

### 18.2 Risk Register Integration

Each material security finding should be recorded in the enterprise risk or issue-management system according to organizational policy.

A useful record includes:

- Risk or finding identifier.
- Affected LLM system.
- Threat scenario.
- Vulnerability or control gap.
- Business consequence.
- Affected assets and data.
- Inherent risk rating.
- Existing controls and evidence.
- Residual risk rating.
- Required treatment.
- Risk and action owners.
- Target completion date.
- Escalation threshold.
- Risk acceptance status, if applicable.
- Retest evidence.
- Closure or reassessment date.

The organization should distinguish a technical vulnerability from the broader business risk it creates. Multiple findings may contribute to one enterprise risk, and one finding may affect several systems or business processes.

### 18.3 Roles and Responsibilities

| Role | Primary responsibility |
|---|---|
| Business owner | Defines the intended business purpose and evaluates business consequences |
| AI product owner | Maintains system requirements, capabilities, and approved use cases |
| AI or ML engineering | Implements model integration, evaluation, and model lifecycle controls |
| Application owner | Maintains application security, authorization, and operational safeguards |
| Security engineering | Conducts or supports technical testing and remediation |
| AI security specialist | Evaluates model-specific threats and security behavior |
| Data owner | Defines data classification, access permissions, and appropriate use |
| Privacy team or DPO, where applicable | Reviews relevant personal-data processing and privacy obligations |
| GRC or risk management | Coordinates assessment methodology, risk recording, and governance decisions |
| Internal audit | Provides independent assurance within its approved mandate |
| Third-party risk management | Evaluates provider assurance and contractual risk |
| Risk owner | Accepts accountability for the relevant business risk |
| Change advisory or release authority | Reviews and authorizes changes under the applicable change process |

The exact allocation should follow the organization's governance model. Technical teams may recommend treatment, but they should not automatically accept business risk on behalf of an authorized risk owner.

### 18.4 GRC Decision Categories

Assessment results should lead to a clear decision rather than an undocumented judgment.

| Decision | Meaning |
|---|---|
| Approved | Required controls and evidence meet the applicable criteria |
| Approved with conditions | Deployment is permitted subject to specified controls, limitations, or milestones |
| Remediation required | Identified weaknesses must be corrected before the relevant approval |
| Restricted deployment | Use is limited to a defined population, environment, dataset, or capability |
| Deferred | Additional evidence or evaluation is required |
| Rejected | Risk or control deficiencies do not meet acceptance requirements |
| Risk accepted | An authorized risk owner formally accepts a defined residual risk, where policy and applicable obligations permit |

Every conditional approval should identify its conditions, owner, due date, verification method, and consequence if the conditions are not met.

### 18.5 GRC Reporting Indicators

Management reporting may include:

- Number of LLM systems assessed.
- Percentage of systems with current security assessments.
- Number of unresolved critical and high-severity findings.
- Percentage of findings remediated within target dates.
- Number of successful unauthorized-access or disclosure tests.
- Number of systems with privileged tool integrations.
- Percentage of production systems with version traceability.
- Number of material changes completed without required reassessment.
- Number of expired risk exceptions.
- Percentage of material risks with named owners.
- Percentage of remediation actions supported by successful retesting.
- Number of security incidents attributable to LLM-related weaknesses.

Metrics should be interpreted in context. For example, an increase in reported findings may reflect improved assessment coverage rather than a deterioration in security. Management should examine trends, severity, and evidence quality before drawing conclusions.

**Core Principle:** LLM security findings become manageable enterprise risks only when they are connected to accountable owners, defined treatment plans, formal decisions, and ongoing assurance.

### 19.4 Minimum Evidence Package

Before concluding the assessment, verify that the package includes, as applicable:

- Current architecture and data-flow diagrams.
- Model and application inventory records.
- Model provenance and version information.
- Relevant security configurations.
- Threat model and risk scenarios.
- Adversarial test plan and results.
- RAG authorization and integrity test results.
- Tool-permission review and execution tests.
- Output-validation test results.
- Security findings and remediation records.
- Evidence of regression testing.
- Monitoring and incident-response requirements.
- Residual-risk assessment.
- Formal approval or rejection decision.

The package should clearly distinguish between evidence that was reviewed, evidence that was tested, evidence that was unavailable, and evidence that remains outstanding.

### 19.5 Assessment Completion Criteria

An assessment should not be marked complete merely because every worksheet field has been populated.

Completion requires that:

1. The assessment scope is approved and sufficiently documented.
2. Applicable security requirements have been evaluated.
3. Material risks and control gaps have been recorded.
4. Findings have accountable owners and defined treatment plans.
5. Required remediation has been verified or handled through an authorized decision.
6. Residual risk has been evaluated using the organization's methodology.
7. Required approvals are documented.
8. Evidence is retained according to policy.
9. Reassessment triggers are defined.
10. Outstanding limitations are communicated to the relevant decision-makers.

**Core Principle:** The worksheet is a governance mechanism for producing traceable decisions. Its value lies in the quality of the evidence, risk analysis, remediation, and accountability it supports—not in the number of completed fields.

## 20. Core Principle — LLM Security Assurance Must Be Repeatable, Evidence-Based, and Risk-Proportionate

An enterprise LLM Security Assessment must establish more than whether a model appears to behave safely under ordinary conditions. It must determine whether the complete application remains within its approved security boundaries when exposed to adversarial inputs, compromised or misleading context, model changes, dependency failures, and operational uncertainty.

The assessment should combine model integrity controls, jailbreak evaluation, adversarial testing, robustness analysis, measurable acceptance criteria, regression testing, and evidence-based governance decisions.

The level of assurance must be proportionate to the system's data sensitivity, autonomy, exposure, business impact, and regulatory obligations.

### Key Conceptual Distinctions

| Distinction | Explanation |
|---|---|
| Artifact integrity vs. artifact trustworthiness | Integrity verification helps detect changes; it does not prove that the original artifact is safe |
| Direct prompt injection vs. jailbreak | Prompt injection targets instruction handling, while jailbreak attempts broadly seek to circumvent intended restrictions; the categories overlap |
| Model safeguards vs. application controls | Model safeguards influence behavior; application controls enforce permissions and constrain operations |
| Refusal behavior vs. security enforcement | A refusal is a model response; effective enforcement must also prevent unauthorized data access and execution |
| Functional testing vs. adversarial testing | Functional testing checks expected use; adversarial testing evaluates behavior under malicious or unexpected conditions |
| Robustness vs. reliability | Robustness concerns acceptable behavior under challenging conditions; reliability concerns consistent performance of intended functions |
| Availability vs. safe failure | Preserving service availability is not sufficient if the system bypasses required security controls |
| Model evaluation vs. security assurance | Evaluation provides evidence about defined tests; assurance also considers architecture, controls, operations, governance, and limitations |
| Test pass rate vs. acceptable risk | Aggregate scores can conceal a single high-impact security failure |
| Regression testing vs. initial validation | Initial validation establishes a baseline; regression testing checks whether material changes undermine established controls |
| Provider assurance vs. customer implementation assurance | Provider evidence addresses defined provider controls; the enterprise must still validate its own architecture and configuration |
| Technical finding vs. enterprise risk | A technical finding identifies a weakness; enterprise risk analysis connects that weakness to business consequences and accountable decisions |
| Evidence collection vs. evidence assurance | Collecting records is not enough; evidence must be relevant, current, authentic, traceable, and sufficient |
| Risk treatment vs. risk acceptance | Treatment modifies risk; acceptance is an authorized decision to retain defined residual exposure where permitted |
| Assessment completion vs. ongoing assurance | A completed assessment is a point-in-time conclusion; ongoing assurance requires monitoring, change control, and reassessment |

**Final Core Principle:** An LLM Security Assessment provides defensible assurance only when its technical tests are connected to enforceable controls, verified evidence, accountable remediation, and authorized risk decisions—and when that assurance is maintained as the model, application, data, and operating environment evolve.
