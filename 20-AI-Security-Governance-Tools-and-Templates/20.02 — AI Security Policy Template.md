# 20.02 — AI Security Policy Template

## Part 1 — AI Security Policy Template Foundations

### 1. Purpose of the AI Security Policy

The AI Security Policy establishes the organization's mandatory requirements for protecting Artificial Intelligence (AI) systems, models, data, infrastructure, applications, users, and supporting services against security threats throughout the AI lifecycle.

The policy should establish the security governance foundation for:

- AI system development
- AI acquisition
- AI deployment
- AI operations
- Model security
- Data security
- Identity and access management
- AI application security
- API security
- AI supply-chain security
- AI monitoring
- AI incident response
- AI resilience
- AI security assurance
- AI system retirement

The policy should define **what security requirements must be satisfied**, while security standards, procedures, architecture requirements, and technical controls define **how those requirements are implemented**.

### 2. Purpose of AI Security Governance

AI introduces security risks that extend beyond traditional application and infrastructure security.

AI security governance should address risks involving:

- Models
- Training data
- Inference data
- Prompts
- System instructions
- Retrieval systems
- AI agents
- Model APIs
- AI applications
- AI infrastructure
- Third-party models
- Foundation-model providers
- MLOps pipelines
- AI development environments
- Autonomous actions

The policy should therefore establish security requirements that apply across the complete AI ecosystem.

### 3. AI Security Policy as an Enterprise Security Control

The AI Security Policy should function as the authoritative security governance layer for AI.

It should translate enterprise security objectives into mandatory AI-specific requirements.

```text id="ais20p1-01"
Enterprise Security Strategy
          │
          ▼
AI Security Policy
          │
          ├── AI Security Standards
          ├── AI Security Procedures
          ├── AI Architecture Requirements
          ├── AI Security Controls
          ├── AI Threat Management
          └── AI Security Monitoring
                    │
                    ▼
              AI Environment
```

The policy should be aligned with the organization's broader cybersecurity framework rather than creating an isolated AI security program.

The scope should cover development, testing, deployment, operation, modification, and retirement.

- Regulatory obligations
- Contractual requirements
- Information security governance

The policy should clearly identify who has authority to approve and interpret AI security requirements.

- Policy review

Typical responsibilities include:

- Data owner — data security
- Model owner — model security
- Cloud/platform teams — infrastructure security

- Incident response — AI security incidents
- Risk management — risk oversight
- Internal audit — independent assurance

The organization should distinguish accountability from operational responsibility.

### 10. AI Security Risk Management

AI security risks should be identified, assessed, treated, monitored, and reassessed throughout the AI lifecycle.

Security risk assessment should consider:

- Threat exposure
- Attack surface
- Data sensitivity
- Model sensitivity
- Business criticality
- External connectivity
- AI autonomy
- Provider dependency
- Regulatory exposure
- Potential impact

Security controls should be proportional to the risk.

- Low
- Moderate
- High

- Data sensitivity
- System criticality
- User population
- External exposure
- Privileged access
- Autonomous capability
- Financial impact
- Safety impact
- Regulatory significance

Security classification should determine the required control depth.

- Infrastructure security
- Monitoring
- Resilience
- Incident response

### 14. AI Security by Default

- Restricted access
- Disabled unnecessary features
- Encryption
- Logging
- Monitoring
- Safe tool permissions
- Restricted network access
- Protected secrets
- Data minimization
- Limited agent autonomy

Users should not be required to discover and manually correct basic security weaknesses after deployment.

### 40. Core Principle of the AI Security Policy Template

The AI Security Policy should establish the authoritative security requirements for protecting AI systems, models, data, applications, infrastructure, users, and supporting services throughout the AI lifecycle.

The security lifecycle should follow:

```text id="ais20p1-03"
Identify
   ↓
Classify
   ↓
Threat Model
   ↓
Protect
   ↓
Test
   ↓
Monitor
   ↓
Detect
   ↓
Respond
   ↓
Recover
   ↓
Reassess
```

The fundamental security separations remain:

- **AI governance ≠ AI security**
- **Security policy ≠ security implementation**
- **AI inventory ≠ attack-surface management**
- **Model security ≠ application security**
- **Data security ≠ model security**
- **Authentication ≠ authorization**
- **Access control ≠ least privilege**
- **Encryption ≠ complete data security**
- **Monitoring ≠ prevention**
- **Security testing ≠ security assurance**
- **Third-party security ≠ enterprise security accountability**
- **Model provenance ≠ model integrity**
- **Secure development ≠ secure operation**
- **Security control implementation ≠ control effectiveness**
- **Incident detection ≠ incident response**
- **Risk acceptance ≠ elimination of security risk**

The policy is effective only when:

- AI assets are identified
- AI attack surfaces are understood
- Security risks are assessed
- Threats are modeled
- Security requirements are defined
- Identity and access are controlled
- Data and models are protected
- AI supply chains are governed
- Security testing is performed
- Security monitoring is operational
- Incidents are detected and managed
- Material changes trigger reassessment
- Security evidence is retained
- Independent assurance can evaluate security effectiveness

**Core Principle:**

> **The AI Security Policy should establish risk-based, enforceable security requirements that protect AI systems, models, data, applications, infrastructure, and AI-enabled actions throughout the complete AI lifecycle while maintaining continuous visibility of emerging threats and material security changes.**

## Part 2 — AI Security Policy Template Controls

### 41. AI Security Control Framework

The AI Security Policy should be supported by a formal control framework that converts security requirements into measurable and testable controls.

Each control should identify:

- Security objective
- Threat addressed
- Control requirement
- Control owner
- Applicable AI systems
- Risk classification
- Implementation requirement
- Evidence requirement
- Testing frequency
- Monitoring mechanism
- Exception process
- Assurance requirement

The control framework should provide traceability from AI security policy requirements to operational security evidence.

### 42. AI Security Policy Approval Control

The AI Security Policy should be formally approved by an authorized security governance authority.

Approval should establish:

- Policy owner
- Approver
- Version
- Approval date
- Effective date
- Review date
- Superseded version

Unapproved drafts should not be treated as mandatory security requirements.

### 43. AI Security Policy Version-Control Control

The policy should use controlled version management.

Each version should record:

- Version number
- Change date
- Change description
- Author
- Reviewer
- Approver
- Effective date
- Superseded version

Historical versions should be retained where required for audit, legal, or regulatory purposes.

### 44. AI Security Policy Review Control

The policy should be reviewed periodically and following material security changes.

Review triggers may include:

- Significant AI incidents
- New AI threats
- Major vulnerabilities
- New AI technologies
- Regulatory changes
- Security framework changes
- Major architecture changes
- Material audit findings
- Significant provider changes

Event-driven review should supplement scheduled review.

### 45. AI Security Policy Communication Control

The organization should communicate applicable AI security requirements to relevant personnel.

Communication should be appropriate to role and may include:

- AI users
- Developers
- Data scientists
- AI system owners
- Security teams
- Administrators
- Executives
- Contractors
- Third-party personnel

Communication records should be maintained where appropriate.

### 46. AI Security Policy Acknowledgment Control

Personnel with material AI security responsibilities should acknowledge applicable security requirements.

Acknowledgment may include:

- Policy acceptance
- Annual attestation
- Role-based certification
- Electronic acknowledgment
- Security training confirmation

Acknowledgment demonstrates awareness but does not demonstrate effective security compliance.

### 47. AI Security Training Control

The organization should provide role-specific AI security training.

Training should address relevant risks such as:

- Prompt injection
- Data leakage
- Unauthorized AI usage
- Sensitive-data handling
- Model security
- Credential protection
- AI supply-chain risks
- Agent security
- Incident reporting

Training should be updated when material threats or policy requirements change.

### 48. AI Security Competency Control

Personnel responsible for specialized AI security activities should possess appropriate competency.

Competency requirements may apply to:

- AI threat modeling
- AI security architecture
- AI red teaming
- Model security
- Cloud AI security
- AI incident response
- AI application security
- AI supply-chain security

Competency should be based on the complexity and risk of the assigned responsibilities.

### 49. AI Security Role Definition Control

AI security roles should be formally defined.

Roles should specify:

- Responsibilities
- Authority
- Decision rights
- Escalation responsibilities
- Required competencies
- Independence requirements

Ambiguous security ownership can create unmanaged attack paths.

### 50. AI Security RACI Control

The organization should maintain a RACI or equivalent responsibility model.

The RACI should define responsibility for:

- AI security assessment
- Threat modeling
- Architecture review
- Security testing
- Access management
- Data protection
- Monitoring
- Incident response
- Vulnerability management
- Security exceptions
- Risk acceptance
- Security assurance

### 51. AI Security Segregation-of-Duties Control

Material AI security activities should maintain appropriate segregation of duties.

For example, the same individual should not unnecessarily:

- Design a security control
- Approve the control
- Operate the control
- Independently assess the control

Where separation is impractical, compensating controls should be documented.

### 52. AI Security Conflict-of-Interest Control

Individuals performing independent AI security assessments should disclose material conflicts of interest.

Potential conflicts may occur when an assessor:

- Developed the system
- Owns the system
- Approved the deployment
- Operates the control
- Has a financial interest in the provider

Conflicts should be evaluated and managed.

All governed AI systems and security-relevant assets should be inventoried.

The inventory should capture, where applicable:

- Model
- Application
- Environment
- Data

Every material AI security asset should have an accountable owner.

Ownership should cover:

- AI system

- Dataset
- Application
- Infrastructure
- API
- Agent

- Storage
- Secrets
- Model endpoints

- Access policies
- Network rules
- Model endpoints
- Agent tools

- Security controls
- Logging
- Encryption
- Provider settings

### 62. AI Identity Management Control

AI systems should integrate with approved enterprise identity-management mechanisms where technically feasible.

Identity management should address:

- Human users
- Administrators
- Service accounts
- API clients
- Agents
- Applications
- Automated processes

Identities should be uniquely attributable.

### 63. AI Authentication Control

AI systems should implement authentication mechanisms appropriate to risk.

Controls may include:

- Strong authentication
- Multi-factor authentication
- Federated identity
- Service authentication
- Certificate-based authentication
- Token-based authentication

Authentication requirements should reflect the sensitivity and criticality of the AI system.

### 64. AI Authorization Control

Access to AI capabilities should be explicitly authorized.

Authorization should determine:

- Who may access the system
- What functionality may be used
- What data may be accessed
- What tools may be invoked
- What actions may be executed

Authorization should be enforced at appropriate architectural boundaries.

### 65. AI Least-Privilege Control

AI users, services, agents, and applications should receive only the permissions necessary for authorized activities.

Least privilege should apply to:

- Data
- APIs
- Tools
- Databases
- Cloud resources
- Model administration
- System administration

Excessive AI permissions can amplify the impact of prompt injection or compromised identities.

### 66. AI Privileged Access Management Control

Privileged AI administration should be governed through appropriate privileged-access mechanisms.

Privileged activities may include:

- Model deployment
- Model administration
- Dataset administration
- Agent configuration
- Security configuration
- Provider administration
- Infrastructure administration

Privileged actions should be logged and periodically reviewed.

### 67. AI Access Review Control

Access to AI systems should be periodically reviewed.

Reviews should confirm:

- User remains authorized
- Role remains appropriate
- Privileges remain necessary
- Departed users are removed
- Excessive access is corrected
- Service identities remain justified

High-risk AI should receive more frequent access review.

### 68. AI Access Revocation Control

Access should be revoked promptly when authorization ends.

Revocation triggers may include:

- Employment termination
- Role change
- Contract termination
- Provider termination
- Security incident
- Loss of business need

Revocation should cover both human and non-human identities.

### 69. AI Data Classification Control

Data processed by AI should be classified according to enterprise data-classification requirements.

Classification should consider:

- Public information
- Internal information
- Confidential information
- Sensitive information
- Personal information
- Highly restricted information

AI-specific restrictions should be applied where required.

### 70. AI Data Access Control

AI systems should access only data necessary for authorized purposes.

Data-access controls should enforce:

- Least privilege
- Purpose limitation
- Role-based access
- Attribute-based access where appropriate
- Tenant separation
- Dataset authorization

AI systems should not receive unrestricted enterprise data access by default.

### 71. AI Data Loss Prevention Control

The organization should implement appropriate controls to prevent unauthorized disclosure of sensitive information through AI.

Controls may include:

- DLP
- Content inspection
- Data classification
- Prompt filtering
- Output inspection
- Access controls
- Network controls
- Monitoring

DLP requirements should reflect the AI use case and data sensitivity.

### 72. AI Encryption Control

Sensitive AI data should be protected through appropriate encryption.

Encryption requirements should address:

- Data at rest
- Data in transit
- Backups
- Model artifacts
- Sensitive datasets
- Credentials
- Provider communications

Key management should be separately governed.

### 73. AI Key Management Control

Cryptographic keys supporting AI systems should be centrally managed where appropriate.

Controls should include:

- Key generation
- Key storage
- Key rotation
- Key access
- Key revocation
- Key backup
- Key destruction

AI teams should not independently create unmanaged cryptographic infrastructure for production systems.

### 74. AI Training Data Integrity Control

Training datasets should be protected against unauthorized modification.

Controls may include:

- Dataset versioning
- Integrity validation
- Access control
- Provenance
- Hashing
- Approval
- Controlled repositories

Material dataset changes should trigger reassessment.

### 75. AI Data Poisoning Protection Control

The organization should implement controls against malicious or unintended poisoning of AI data.

Controls may include:

- Source validation
- Dataset provenance
- Anomaly detection
- Data-quality controls
- Access restrictions
- Dataset approval
- Integrity validation

Data poisoning controls should be proportional to model risk.

### 76. AI Model Access Control

Access to model artifacts should be restricted according to sensitivity and business need.

Access should cover:

- Model weights
- Model configurations
- Fine-tuning artifacts
- Training artifacts
- Model registries
- Model endpoints

Highly sensitive models should receive enhanced protection.

### 77. AI Model Integrity Control

The organization should verify model integrity before deployment and following material changes.

Verification may use:

- Cryptographic hashes
- Digital signatures
- Trusted repositories
- Version control
- Deployment verification

### 78. AI Model Registry Security Control

Model registries should be protected as security-sensitive systems.

Controls should address:

- Authentication

- Access logging
- Approval
- Model promotion
- Retention

Only authorized personnel should be able to promote models into production.

### 79. AI Model Deployment Control

Production model deployment should require appropriate authorization.

Deployment should validate:

- Approved model version
- Security testing
- Model integrity
- Required assessments
- Configuration
- Monitoring
- Owner
- Deployment approval

Unauthorized deployment should be prevented or detected.

### 80. AI Model Extraction Protection Control

The organization should assess the risk of unauthorized model extraction.

Potential controls include:

- Authentication
- Rate limiting
- Query controls
- Output restrictions
- Abuse monitoring
- API protections
- Model endpoint security

Controls should reflect the sensitivity of the model.

### 81. AI Model Theft Protection Control

Sensitive model artifacts should be protected against unauthorized access and exfiltration.

Controls may include:

- Access restrictions
- Encryption
- Network controls
- Repository security
- Privileged-access management
- Monitoring

Model theft should be incorporated into threat modeling.

### 82. AI Prompt Security Control

Prompts and system instructions should be protected where they contain sensitive business logic, security requirements, or confidential information.

Controls should address:

- Prompt confidentiality
- Access
- Versioning
- Change management
- Injection resistance
- Secret handling

Secrets should never be embedded in prompts.

### 83. AI Prompt Injection Protection Control

AI systems exposed to untrusted input should implement controls against prompt injection.

Potential controls include:

- Input validation
- Trust-boundary separation
- Instruction hierarchy
- Content filtering
- Tool authorization
- Output validation
- Context isolation
- Human approval for sensitive actions

Prompt injection should be treated as an architectural security risk rather than merely a user-behavior issue.

### 84. AI Jailbreak Protection Control

Generative AI systems should implement appropriate defenses against attempts to bypass security or policy restrictions.

Controls may include:

- Input detection
- Policy enforcement
- Output filtering
- Model configuration
- Monitoring
- Rate limiting
- Abuse detection

Controls should be tested against realistic attack techniques.

### 85. AI Output Security Control

AI-generated output should be handled according to its risk and destination.

Controls may include:

- Output validation
- Content filtering
- Data-loss prevention
- Human review
- Safe rendering
- Injection prevention
- Downstream authorization

AI output should not automatically be treated as trusted input.

### 86. AI Insecure Output Handling Control

AI-generated content consumed by applications should undergo appropriate validation before being interpreted as:

- Code
- SQL
- Commands
- HTML
- Configuration
- Workflow instructions
- API requests

AI output should not be directly executed without appropriate security controls.

### 87. AI Retrieval Security Control

Retrieval-augmented AI systems should secure their retrieval architecture.

Controls should address:

- Source authorization
- Document access
- Index security
- Vector database security
- Retrieval permissions
- Data classification
- Content integrity

The model should not retrieve information that the requesting user is not authorized to access.

### 88. AI Vector Database Security Control

Vector databases and embedding stores should be treated as governed data repositories.

Controls should address:

- Authentication
- Authorization
- Encryption
- Tenant isolation
- Data classification
- Access logging
- Data retention
- Index integrity

Embeddings should not automatically be considered non-sensitive.

### 89. AI Context Security Control

AI context windows may contain sensitive information.

Security controls should address:

- Context composition
- Data authorization
- Context isolation
- Sensitive-data filtering
- Retention
- Logging
- Cross-user isolation

The system should prevent unauthorized information from entering the model context.

### 90. AI Agent Identity Control

Each autonomous or semi-autonomous AI agent should have an identifiable security identity.

The identity should support:

- Authentication
- Authorization
- Attribution
- Logging
- Access control
- Incident investigation

Agents should not operate using unrestricted shared identities.

### 91. AI Agent Permission Control

Agent permissions should be explicitly defined and constrained.

Permissions should identify:

- Tools
- APIs
- Data
- Systems
- Transactions
- Administrative functions

Agent permissions should follow least privilege.

### 92. AI Agent Tool Authorization Control

Agents should be authorized before invoking sensitive tools.

Sensitive tools may include:

- Financial systems
- Identity systems
- Production systems
- Databases
- Email
- External communications
- Administrative interfaces

Tool authorization should be enforced independently of the model's instructions.

### 93. AI Agent Action Validation Control

High-impact agent actions should be validated before execution.

Validation may include:

- Policy checks
- Risk checks
- Parameter validation
- Authorization
- Human approval
- Transaction limits

The model should not have unrestricted authority to execute consequential actions.

### 94. AI Agent Human-Approval Control

Human approval should be required for defined high-risk agent actions.

Approval requirements should be based on:

- Financial impact
- Security impact
- Privacy impact
- Irreversibility
- Regulatory significance
- Business criticality

Human approval should provide meaningful authority to stop or modify the action.

### 95. AI Agent Transaction-Limit Control

Agents should operate within defined transaction and resource limits.

Limits may include:

- Financial amount
- Number of transactions
- API calls
- Data volume
- Execution duration
- Tool frequency
- External communications

Limits should reduce the potential impact of compromised or misbehaving agents.

### 96. AI Agent Memory Security Control

Persistent AI agent memory should be protected against unauthorized modification and retrieval.

Controls should address:

- Memory access
- Memory integrity
- Data classification
- Retention
- User isolation
- Poisoning
- Deletion

Persistent memory should not become an uncontrolled source of sensitive information.

### 97. AI Plugin and Tool Security Control

AI plugins, tools, and external integrations should undergo security assessment before use.

Assessment should consider:

- Permissions
- Data access
- Provider trust
- API security
- Authentication
- Logging
- Supply-chain risk
- Failure behavior

- Prompt injection

- Recovery

- Evidence preservation

- Existing controls
- Residual risk
- Business justification
- Acceptance authority

AI security events should be incorporated into enterprise detection capabilities.

- Are correctly implemented
- Operate effectively
- Produce appropriate evidence
- Address the intended threat

- Due date
- Status
- Validation requirement

Security findings should only be closed after sufficient evidence demonstrates that remediation is effective.

Closure should verify:

- Corrective action completed
- Control implemented
- Vulnerability addressed
- Residual risk acceptable
- Evidence available

AI security controls should be continuously improved based on:

Continuous improvement should be incorporated into the AI security governance lifecycle.

### 112. Core AI Security Policy Control Principle

The AI Security Policy control framework should establish a traceable relationship between security requirements, threats, controls, evidence, monitoring, and remediation.

```text id="ais20p2-01"
Security Requirement
        │
        ▼
Threat / Risk
        │
        ▼
Security Control
        │
        ▼
Implementation
        │
        ▼
Security Evidence
        │
        ▼
Monitoring / Testing
        │
        ▼
Detection / Finding
        │
        ▼
Remediation
        │
        ▼
Validation
        │
        ▼
Continuous Improvement
```

The fundamental control separations remain:

- **Security policy ≠ security control**
- **Control existence ≠ control effectiveness**
- **Authentication ≠ authorization**
- **Authorization ≠ least privilege**
- **Encryption ≠ complete data protection**
- **Model integrity ≠ model provenance**
- **Inventory ≠ attack-surface visibility**
- **Security testing ≠ continuous security**
- **Monitoring ≠ prevention**
- **Detection ≠ response**
- **Incident response ≠ recovery**
- **Provider assurance ≠ enterprise security assurance**
- **Agent identity ≠ agent authorization**
- **Human approval ≠ unrestricted human responsibility**
- **Security exception ≠ risk elimination**
- **Risk acceptance ≠ vulnerability remediation**
- **Logging ≠ effective monitoring**
- **Security monitoring ≠ independent assurance**
- **Automated security control ≠ automatically effective control**

The control framework is effective only when:

- AI assets are identified
- Threats and vulnerabilities are understood
- Security requirements are risk-based
- Controls address defined threats
- Identity and access are controlled
- Data and models are protected
- AI applications and APIs are secured
- Agents operate within defined boundaries
- Security events are monitored
- Incidents are detected and managed
- Security findings are remediated
- Remediation is validated
- Exceptions are controlled
- Security evidence is reliable
- Material changes trigger reassessment
- Independent assurance can evaluate control effectiveness

**Core Principle:**

> **AI Security Policy controls should establish a continuous, evidence-driven security chain from AI threats and risks through preventive and detective controls, monitoring, incident response, remediation, validation, and continuous improvement.**
