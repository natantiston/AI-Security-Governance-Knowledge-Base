# 20.02 — AI Security Policy Template

## Part 1 — AI Security Policy Template Foundations

### 1. Purpose of the AI Security Policy

The AI Security Policy establishes the organization's mandatory requirements for protecting Artificial Intelligence (AI) systems, models, data, infrastructure, applications, users, and supporting services against security threats throughout the AI lifecycle.

The policy should establish the security governance foundation for:

- AI system development
- AI acquisition
- AI deployment
- AI operations
- Model security
- Data security
- Identity and access management
- AI application security
- API security
- AI supply-chain security
- AI monitoring
- AI incident response
- AI resilience
- AI security assurance
- AI system retirement

The policy should define **what security requirements must be satisfied**, while security standards, procedures, architecture requirements, and technical controls define **how those requirements are implemented**.

### 2. Purpose of AI Security Governance

AI introduces security risks that extend beyond traditional application and infrastructure security.

AI security governance should address risks involving:

- Models
- Training data
- Inference data
- Prompts
- System instructions
- Retrieval systems
- AI agents
- Model APIs
- AI applications
- AI infrastructure
- Third-party models
- Foundation-model providers
- MLOps pipelines
- AI development environments
- Autonomous actions

The policy should therefore establish security requirements that apply across the complete AI ecosystem.

### 3. AI Security Policy as an Enterprise Security Control

The AI Security Policy should function as the authoritative security governance layer for AI.

It should translate enterprise security objectives into mandatory AI-specific requirements.

```text id="ais20p1-01"
Enterprise Security Strategy
          │
          ▼
AI Security Policy
          │
          ├── AI Security Standards
          ├── AI Security Procedures
          ├── AI Architecture Requirements
          ├── AI Security Controls
          ├── AI Threat Management
          └── AI Security Monitoring
                    │
                    ▼
              AI Environment
```

The policy should be aligned with the organization's broader cybersecurity framework rather than creating an isolated AI security program.

### 4. AI Security Policy Scope

The policy should define the AI assets and activities subject to security requirements.

The scope may include:

- Machine-learning systems
- Generative AI
- Large language models
- Foundation models
- AI applications
- AI agents
- Predictive models
- Computer-vision systems
- Natural-language-processing systems
- AI APIs
- Model-serving infrastructure
- Training environments
- Inference environments
- MLOps platforms
- AI-enabled SaaS
- Third-party AI services

The scope should cover development, testing, deployment, operation, modification, and retirement.

### 5. Organizational Applicability

The AI Security Policy should apply to functions that develop, acquire, operate, secure, administer, or use AI systems.

Applicable functions may include:

- Information security
- Cybersecurity
- IT
- Engineering
- Data science
- AI development
- Cloud engineering
- Enterprise architecture
- Data governance
- Privacy
- Risk management
- Compliance
- Procurement
- Legal
- Business operations
- Internal audit

The policy should also establish requirements for contractors and third parties where they operate or access organizational AI systems.

### 6. AI Security Policy Authority

The policy should identify the organizational authority responsible for establishing AI security requirements.

Policy authority may derive from:

- Enterprise security governance
- Executive management
- Board-approved security policy
- Enterprise risk management
- Regulatory obligations
- Contractual requirements
- Information security governance

The policy should clearly identify who has authority to approve and interpret AI security requirements.

### 7. AI Security Policy Ownership

A designated security authority should own the AI Security Policy.

Potential owners include:

- Chief Information Security Officer
- AI Security Officer
- Head of Cybersecurity
- AI Security Governance function
- Information Security Governance function

The policy owner should be responsible for:

- Policy maintenance
- Security requirement updates
- Regulatory alignment
- Threat-informed updates
- Control alignment
- Security stakeholder coordination
- Policy review

### 8. AI Security Accountability

AI security accountability should be distributed according to the AI lifecycle.

Typical responsibilities include:

- Executive leadership — enterprise security accountability
- CISO/security leadership — security governance
- AI system owner — system security accountability
- Engineering — secure implementation
- Data owner — data security
- Model owner — model security
- Cloud/platform teams — infrastructure security
- Security operations — monitoring and detection
- Incident response — AI security incidents
- Risk management — risk oversight
- Internal audit — independent assurance

The organization should distinguish accountability from operational responsibility.

### 9. AI Security Governance Roles

AI security roles should be explicitly defined.

Relevant roles may include:

- AI system owner
- AI security owner
- Model owner
- Data owner
- Application owner
- Infrastructure owner
- Security architect
- Security operations
- Risk owner
- Privacy owner
- Vendor owner
- Incident manager
- Assurance function

Each role should have defined responsibilities and decision rights.

### 10. AI Security Risk Management

AI security risks should be identified, assessed, treated, monitored, and reassessed throughout the AI lifecycle.

Security risk assessment should consider:

- Threat exposure
- Attack surface
- Data sensitivity
- Model sensitivity
- Business criticality
- External connectivity
- AI autonomy
- Provider dependency
- Regulatory exposure
- Potential impact

Security controls should be proportional to the risk.

### 11. AI Security Risk Classification

The organization should establish security risk classifications for AI systems.

A classification model may include:

- Low
- Moderate
- High
- Critical

Classification should consider factors such as:

- Data sensitivity
- System criticality
- User population
- External exposure
- Privileged access
- Autonomous capability
- Financial impact
- Safety impact
- Regulatory significance

Security classification should determine the required control depth.

Security requirements should apply throughout the AI lifecycle.

Security should not be introduced only after an AI system is operational.

### 13. Security by Design for AI

AI systems should incorporate security requirements during design rather than relying exclusively on compensating controls after deployment.

Security-by-design should address:

- Threat modeling
- Trust boundaries
- Identity
- Access
- Data protection
- Model protection
- Application security
- Infrastructure security
- Monitoring
- Resilience
- Incident response

Security architecture should reflect the specific characteristics of the AI system.

### 14. AI Security by Default

AI systems should be deployed using secure default configurations.

Secure defaults may include:

- Restricted access
- Disabled unnecessary features
- Encryption
- Logging
- Monitoring
- Safe tool permissions
- Restricted network access
- Protected secrets
- Data minimization
- Limited agent autonomy

Users should not be required to discover and manually correct basic security weaknesses after deployment.

### 15. AI Asset Identification

The organization should identify the security-relevant assets supporting each AI system.

Assets may include:

- Models
- Training datasets
- Validation datasets
- Production data
- Prompts
- System instructions
- Embeddings
- Vector databases
- APIs
- Applications
- Servers
- Containers
- Cloud services
- Model registries
- MLOps pipelines
- Credentials
- Secrets
- Agent tools

Asset identification should support security risk assessment and protection.

### 16. AI System Inventory Security Requirement

Every governed AI system should have sufficient inventory information to support security management.

The inventory should identify:

- AI system
- Owner
- Model
- Provider
- Environment
- Data classification
- Risk classification
- Internet exposure
- External integrations
- Criticality
- Security assessment status
- Monitoring status

An unknown AI system represents an unmanaged security exposure.

### 17. AI Attack Surface Management

The organization should identify and manage the attack surface associated with AI.

The attack surface may include:

- Public interfaces
- APIs
- Model endpoints
- Applications
- Data pipelines
- Model repositories
- Development environments
- Cloud infrastructure
- Third-party integrations
- Agent tools
- Plugins
- Retrieval systems

Attack-surface analysis should be performed during design and updated following material changes.

### 18. AI Threat Modeling

AI systems should undergo threat modeling proportional to their security risk.

Threat modeling should consider:

- Threat actors
- Attack vectors
- Assets
- Trust boundaries
- Security assumptions
- Abuse cases
- Attack impact
- Existing controls
- Residual risk

AI-specific threats should be incorporated into the threat model rather than relying solely on traditional application threats.

### 19. AI Security Threat Categories

The policy should recognize security threats specific to AI.

Relevant threat categories may include:

- Prompt injection
- Jailbreaking
- Data poisoning
- Model theft
- Model extraction
- Adversarial inputs
- Membership inference
- Model inversion
- Sensitive-data leakage
- Supply-chain compromise
- Malicious model manipulation
- Tool abuse
- Agent hijacking
- Retrieval manipulation
- Unauthorized model access

The applicable threat categories should depend on the AI architecture.

### 20. AI Identity and Access Management

Access to AI systems should follow enterprise identity and access management principles.

Requirements should address:

- User authentication
- Authorization
- Privileged access
- Service identities
- API identities
- Agent identities
- Role-based access
- Least privilege
- Access reviews
- Access revocation

AI-specific identities should not bypass enterprise identity controls without explicit authorization.

### 21. AI Privileged Access

Privileged access to AI systems should receive enhanced controls.

Privileged access may include:

- Model administration
- Model deployment
- Training infrastructure
- Data administration
- Prompt configuration
- Agent tool configuration
- Security configuration
- Provider administration

Privileged actions should be strongly authenticated, logged, monitored, and periodically reviewed.

### 22. AI Secrets Management

Credentials and secrets used by AI systems should be managed through approved enterprise mechanisms.

Secrets may include:

- API keys
- Cloud credentials
- Database credentials
- Service tokens
- Signing keys
- Encryption keys
- Provider credentials

Secrets should not be embedded in:

- Prompts
- Source code
- Model artifacts
- Configuration files
- Training datasets
- Documentation

### 23. AI Data Security

Data used by AI systems should be protected according to its classification and sensitivity.

Data-security requirements should address:

- Data classification
- Encryption
- Access control
- Data transfer
- Storage
- Retention
- Data masking
- Data loss prevention
- Data monitoring

AI processing should not weaken existing enterprise data-security requirements.

### 24. AI Training Data Security

Training data should be protected against unauthorized access, manipulation, and poisoning.

Controls should address:

- Source validation
- Integrity
- Provenance
- Access
- Modification
- Quality
- Data poisoning
- Unauthorized inclusion
- Sensitive-data exposure

Training data should be treated as a security-sensitive AI asset.

### 25. AI Inference Data Security

Data submitted to AI systems during inference should be protected.

The organization should control:

- User inputs
- API requests
- Uploaded files
- Retrieved information
- Conversation data
- Generated context
- Agent inputs

Controls should prevent unauthorized disclosure or unintended reuse.

### 26. AI Model Security

Models should be protected throughout their lifecycle.

Model security should address:

- Model access
- Model storage
- Model integrity
- Model provenance
- Model versioning
- Model deployment
- Model extraction
- Model theft
- Unauthorized modification

Model artifacts should be treated as security-sensitive assets where appropriate.

### 27. AI Model Integrity

The organization should maintain confidence that deployed models have not been unauthorizedly altered.

Integrity controls may include:

- Cryptographic hashes
- Digital signatures
- Controlled repositories
- Version control
- Deployment verification
- Artifact integrity checks

Model integrity should be verified before deployment and after material changes.

### 28. AI Model Provenance

The organization should maintain information about model origin and lineage.

Provenance may include:

- Model developer
- Provider
- Model version
- Training origin
- Fine-tuning
- Modification history
- Approval history
- Deployment history

Model provenance supports supply-chain security and assurance.

Controls should address:

- Input validation
- Output handling
- API security

- Vulnerability management

- Security testing
- Dependency vulnerabilities
- Model approval
- Data validation
- Artifact integrity
- Configuration
- Required assessments

Testing may include:

- Vulnerability assessment
- Penetration testing
- Adversarial testing
- Red teaming
- Prompt-injection testing
- Model abuse testing
- API testing
- Configuration testing
- Access-control testing

Monitoring may identify:

- Prompt injection
- Data exfiltration
- Model abuse
- Tool misuse
- Privilege escalation
- Suspicious model behavior
- Security control failures

Monitoring requirements should be proportional to AI risk.

### 40. Core Principle of the AI Security Policy Template

The AI Security Policy should establish the authoritative security requirements for protecting AI systems, models, data, applications, infrastructure, users, and supporting services throughout the AI lifecycle.

The security lifecycle should follow:

```text id="ais20p1-03"
Identify
   ↓
Classify
   ↓
Threat Model
   ↓
Protect
   ↓
Test
   ↓
Monitor
   ↓
Detect
   ↓
Respond
   ↓
Recover
   ↓
Reassess
```

The fundamental security separations remain:

- **AI governance ≠ AI security**
- **Security policy ≠ security implementation**
- **AI inventory ≠ attack-surface management**
- **Model security ≠ application security**
- **Data security ≠ model security**
- **Authentication ≠ authorization**
- **Access control ≠ least privilege**
- **Encryption ≠ complete data security**
- **Monitoring ≠ prevention**
- **Security testing ≠ security assurance**
- **Third-party security ≠ enterprise security accountability**
- **Model provenance ≠ model integrity**
- **Secure development ≠ secure operation**
- **Security control implementation ≠ control effectiveness**
- **Incident detection ≠ incident response**
- **Risk acceptance ≠ elimination of security risk**

The policy is effective only when:

- AI assets are identified
- AI attack surfaces are understood
- Security risks are assessed
- Threats are modeled
- Security requirements are defined
- Identity and access are controlled
- Data and models are protected
- AI supply chains are governed
- Security testing is performed
- Security monitoring is operational
- Incidents are detected and managed
- Material changes trigger reassessment
- Security evidence is retained
- Independent assurance can evaluate security effectiveness

**Core Principle:**

> **The AI Security Policy should establish risk-based, enforceable security requirements that protect AI systems, models, data, applications, infrastructure, and AI-enabled actions throughout the complete AI lifecycle while maintaining continuous visibility of emerging threats and material security changes.**
