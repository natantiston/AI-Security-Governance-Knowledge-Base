# 20.08 — AI Security Assessment Template

## Part 1 — AI Security Assessment Foundations

### 1. Introduction to the AI Security Assessment

An AI Security Assessment is a structured evaluation of the security risks, vulnerabilities, threats, control weaknesses, and abuse scenarios associated with an AI system throughout its lifecycle.

Its purpose is to determine whether the system can be developed, acquired, integrated, deployed, and operated with security controls appropriate to its intended purpose, threat environment, data sensitivity, autonomy, and business criticality.

Traditional application security assessments remain necessary, but AI systems introduce additional security considerations. These may include prompt injection, insecure tool use, sensitive information disclosure through model interactions, training-data poisoning, model extraction, unsafe output handling, retrieval-augmented generation (RAG) weaknesses, and attacks against AI supply chains.

The assessment must consider the complete AI-enabled system rather than evaluating the model in isolation.

Relevant components may include:

- Foundation models and specialized models.
- Training, fine-tuning, and evaluation datasets.
- System prompts and model configuration.
- Retrieval pipelines and vector databases.
- Application interfaces and orchestration services.
- Plugins, tools, agents, and external APIs.
- Identity and access management.
- Cloud infrastructure and model-serving environments.
- Logging, monitoring, and security operations.
- Human operators and administrative interfaces.
- Third-party providers and software dependencies.

An AI system may use a well-secured model and still be vulnerable because the application grants excessive permissions, retrieves unauthorized information, or executes model-generated instructions without adequate validation.

The AI Security Assessment should therefore evaluate the security of the entire architecture, including the trust boundaries between models, applications, data sources, tools, users, and external services.

**Core objective:** Establish whether the AI system's security controls are appropriate, implemented, tested, and effective against the threats relevant to its intended operating environment.

### 2. Purpose of the AI Security Assessment Template

The AI Security Assessment Template standardizes how an organization evaluates AI-specific and conventional cybersecurity risks.

It provides a repeatable method for documenting the system's architecture, identifying threats, evaluating vulnerabilities, assessing control effectiveness, recording residual risks, and determining whether deployment is permitted.

The template should answer eight fundamental questions:

1. What AI system and business use case are being assessed?
2. What assets, identities, data, models, and capabilities require protection?
3. Which threat actors and attack paths are relevant?
4. How could the AI system be manipulated, compromised, misused, or abused?
5. Which preventive, detective, and corrective controls are required?
6. How effectively have the controls been implemented and tested?
7. What security risks remain after mitigation?
8. Who is authorized to approve the system's deployment and residual security exposure?

A complete assessment should contain the following components:

| Component                     | Purpose                                                            |
| ----------------------------- | ------------------------------------------------------------------ |
| Assessment identification     | Establishes the assessment record, scope, owner, and version       |
| System context                | Describes the use case, architecture, deployment, and dependencies |
| Asset and data inventory      | Identifies assets requiring protection                             |
| Threat model                  | Documents threat actors, attack surfaces, and attack paths         |
| Vulnerability assessment      | Identifies weaknesses in components and integrations               |
| AI-specific security analysis | Evaluates threats unique to or amplified by AI capabilities        |
| Control assessment            | Evaluates existing security safeguards                             |
| Security testing              | Records testing scope, methodology, findings, and limitations      |
| Remediation plan              | Assigns actions, owners, and deadlines                             |
| Residual risk evaluation      | Determines remaining exposure after mitigation                     |
| Approval decision             | Records authorization, restrictions, or rejection                  |
| Monitoring and reassessment   | Defines ongoing security oversight                                 |
| Evidence repository           | Preserves the basis for conclusions and decisions                  |

The template should integrate with the organization's existing security risk management process, vulnerability management, architecture review, penetration testing, third-party risk management, and change management.

It should not become a parallel security process that duplicates existing assessments without adding AI-specific coverage.

### 3. AI Security Assessment as a Lifecycle Control

The assessment should operate as a security governance control across the AI system lifecycle.

It should begin early enough to influence architecture, supplier selection, data handling, and security design. It should also be revisited when the system's capabilities, permissions, model, data, or operating environment change materially.

A practical lifecycle is:

```
AI Use Case Proposed
        |
        v
Initial Security Screening
        |
        v
System and Threat Modeling
        |
        v
Security Requirements Defined
        |
        v
Architecture and Control Review
        |
        v
Security Testing and Validation
        |
        v
Findings and Remediation
        |
        v
Residual Risk Evaluation
        |
        v
Authorized Security Decision
        |
        v
Controlled Deployment
        |
        v
Monitoring, Incident Response,
and Periodic Reassessment
```

The assessment should be coordinated with secure software development, AI development and deployment processes, and operational security monitoring.

For systems developed internally, security requirements should be incorporated into design reviews, development pipelines, testing, and release authorization.

For third-party AI systems, the assessment should include supplier assurance, contractual controls, available technical evidence, integration security, and validation in the organization's intended deployment context.

Completion of an assessment does not itself authorize deployment. Deployment remains subject to the applicable security gates and risk acceptance requirements.

### 4. Scope of the AI Security Assessment

The scope should be defined according to the AI system's architecture, intended purpose, deployment model, exposed interfaces, data sensitivity, and potential consequences of compromise.

The assessment may cover:

- Internally developed AI applications.
- Commercial AI products and SaaS services.
- Foundation models and model APIs.
- Fine-tuned or customized models.
- Retrieval-augmented generation systems.
- AI-enabled business applications.
- AI agents with tool access.
- AI development and training environments.
- Model registries and artifact repositories.
- AI inference endpoints.
- Data pipelines and vector databases.
- AI-related cloud infrastructure.
- Third-party plugins and integrations.
- Material updates to deployed systems.

The scope should identify relevant trust boundaries and external dependencies.

For example, assessing a customer-service chatbot should not stop at the chatbot interface. The assessment may need to include the identity provider, customer database, retrieval system, model API, orchestration service, administrative console, and any tools capable of modifying customer records.

The scope statement should document:

- System and use-case identifiers.
- Business owner and technical owner.
- Intended purpose and users.
- Deployment environment.
- Model and provider information.
- Data classifications.
- External interfaces and dependencies.
- Administrative and service identities.
- Tools and actions available to the AI.
- Relevant environments and lifecycle stages.
- Assessment exclusions and their rationale.

Where a component is excluded from scope, the organization should document the boundary and explain how risks arising from the excluded component are addressed.

### 5. Distinction Between AI Security Assessment, AI Risk Assessment, and AI Impact Assessment

These assessments are related but have different primary objectives.

| Assessment                    | Primary focus                                                                            | Typical question                                                                        |
| ----------------------------- | ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| AI Security Assessment        | Cybersecurity threats, vulnerabilities, attack paths, and security control effectiveness | Can the AI system or its supporting environment be compromised or abused?               |
| AI Risk Assessment            | Identification, analysis, evaluation, and treatment of broader AI-related risks          | What could go wrong, how significant is the exposure, and how should it be managed?     |
| AI Impact Assessment          | Potential consequences for individuals, groups, organizations, and society               | Who or what may be affected, and what consequences could arise?                         |
| AI Privacy Assessment or DPIA | Personal data processing and associated risks to individuals                             | Does the processing create privacy risks or trigger formal data protection obligations? |
| AI Model Evaluation           | Model performance, behavior, limitations, and task-specific quality                      | Does the model perform adequately against the defined evaluation criteria?              |
| AI Red Teaming                | Adversarial probing of system behavior and defenses                                      | Can an attacker induce unsafe, unauthorized, or otherwise undesirable behavior?         |

The AI Security Assessment may identify prompt injection as a vulnerability or attack scenario. The AI Risk Assessment may record the associated business and operational exposure. The AI Impact Assessment may evaluate the consequences if the attack results in disclosure of customer information or unauthorized action.

AI red teaming and penetration testing can provide valuable evidence, but neither automatically replaces the broader security assessment.

The assessment types should share identifiers and evidence where practical while retaining their distinct purposes and decision requirements.

### 6. Security Standards and Framework Alignment

The assessment methodology should align with the organization's security governance framework and relevant AI security guidance.

Potential reference points include:

- NIST AI Risk Management Framework.
- NIST Cybersecurity Framework.
- NIST SP 800-53 security and privacy controls.
- NIST SP 800-218, Secure Software Development Framework.
- OWASP Top 10 for Large Language Model Applications.
- OWASP guidance for securing AI agents and related AI applications.
- MITRE ATLAS, the adversarial threat landscape for AI systems.
- ISO/IEC 27001 information security management systems.
- ISO/IEC 27002 information security controls.
- ISO/IEC 42001 AI management systems.
- ISO/IEC 23894 AI risk management.
- Cloud provider security architecture and AI service guidance.
- Internal security policies, architecture standards, and secure development requirements.

These sources serve different purposes. Some define management-system requirements, some provide security controls, and others organize AI-specific attack techniques or application security risks.

The organization should select and map the references that fit its environment rather than treating every framework as a mandatory checklist.

For example, ISO/IEC 27001 may establish the organization's overall information security management framework, while OWASP guidance may help identify LLM application weaknesses and MITRE ATLAS may inform AI-specific threat modeling.

Framework alignment does not establish that the system is secure. The assessment must still verify the actual architecture, controls, testing results, and residual exposure.

### 7. AI Security Assessment Ownership and Responsibilities

The assessment requires clear accountability across business, engineering, cybersecurity, AI governance, privacy, and operational teams.

Representative responsibilities include:

| Role                         | Core responsibility                                                                            |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| Business owner               | Defines business purpose and accepts accountability for the use case                           |
| AI system owner              | Provides system context, architecture, dependencies, and lifecycle information                 |
| Security assessment lead     | Coordinates the assessment and ensures that findings are documented                            |
| Security architect           | Evaluates trust boundaries, security design, and architectural controls                        |
| Application security team    | Reviews application code, interfaces, authentication, authorization, and input/output handling |
| AI or ML engineering team    | Provides model, data pipeline, inference, evaluation, and deployment information               |
| Cloud or infrastructure team | Reviews infrastructure, network boundaries, secrets, and platform controls                     |
| Data owner                   | Defines data classification, access requirements, and permitted data use                       |
| Privacy function             | Reviews privacy-related security concerns and applicable data protection obligations           |
| AI governance function       | Ensures consistency with AI governance requirements                                            |
| Security operations          | Defines monitoring, detection, and incident-response integration                               |
| Risk acceptance authority    | Makes security risk decisions within delegated authority                                       |
| Independent assurance        | Evaluates the adequacy of the process where required                                           |

One person may hold multiple roles in a smaller organization, but responsibilities and approval authority must remain explicit.

The individual responsible for implementing a control should not automatically have unrestricted authority to approve the residual risk arising from that control's failure.

### 8. AI Security Assessment Record Identification

Each formal assessment should have a unique identifier that supports traceability across the AI system inventory, risk register, security testing records, remediation tasks, and approval workflow.

A suggested naming convention is:

`AIS-[BUSINESS_UNIT]-[YEAR]-[SEQUENCE]`

Example:

`AIS-CRM-2026-0018`

The naming convention is illustrative and should be adapted to the organization's existing GRC conventions.

The assessment record should include:

- Assessment ID.
- Assessment title.
- AI system ID.
- Use-case ID.
- Assessment owner.
- Technical owner.
- Business unit.
- Assessment scope.
- Assessment version.
- Initiation date.
- Planned completion date.
- Current status.
- Assessment methodology and version.
- Related risk register identifiers.
- Related vulnerability and penetration-testing records.
- Approval decision and reference.
- Next review date.

The identifier should remain stable across revisions of the same assessment record. Material changes should be captured through controlled versioning or linked reassessments.

This allows the organization to establish which findings, controls, and approvals applied to a specific system version at a particular point in time.

### 9. AI Security Assessment Lifecycle Status

The organization should define controlled lifecycle statuses that communicate the assessment's current state.

| Status                   | Meaning                                                              |
| ------------------------ | -------------------------------------------------------------------- |
| Draft                    | Initial assessment record is being prepared                          |
| Screening                | Scope and assessment requirements are being determined               |
| In Progress              | Threat analysis and control evaluation are underway                  |
| Pending Evidence         | Required technical information or supporting evidence is outstanding |
| Under Review             | Security or specialist review is underway                            |
| Remediation Required     | Findings require action before the relevant approval decision        |
| Pending Retest           | Remediation has been implemented and requires validation             |
| Pending Decision         | Required risk or deployment decision is outstanding                  |
| Approved                 | The assessment has received the required authorization               |
| Approved with Conditions | Authorization is subject to documented conditions                    |
| Restricted               | Operation is permitted only within defined boundaries                |
| Rejected                 | The proposed deployment is not authorized                            |
| Superseded               | A newer assessment has replaced the record for current decisions     |
| Closed                   | The assessment lifecycle has been formally completed                 |

The status model should distinguish assessment progress from the security authorization state.

A system may have a completed assessment but remain blocked from deployment because critical findings are unresolved. Likewise, an approved system may require additional monitoring or restrictions.

Status changes should be logged with timestamps, responsible actors, and relevant decision references.

### 10. AI System Context and Architecture Description

The assessment should include a clear description of the system's architecture and operating context.

The description should identify the components, data flows, interfaces, identities, and decision or action pathways that could affect security.

Relevant information includes:

- Model type and provider.
- Application and orchestration components.
- Input and output interfaces.
- Data sources and repositories.
- Retrieval and embedding services.
- System prompts and configuration.
- Tools, plugins, and agent capabilities.
- Identity and authorization mechanisms.
- External APIs and integrations.
- Hosting and deployment environment.
- Logging and monitoring components.
- Administrative interfaces.
- Human approval and intervention points.

The architecture description should be sufficiently detailed to support threat modeling and control evaluation.

A statement such as "the system uses a commercial LLM" is insufficient because it does not explain how data reaches the model, what the model can access, or what actions can be taken using its outputs.

A stronger description would identify the model endpoint, orchestration service, retrieval data store, user identity context, tool permissions, and downstream systems.

Where the architecture changes materially, the security assessment should be updated to reflect the new attack surface and trust boundaries.

### 11. Security Objectives and Protection Requirements

The assessment should define the security objectives that the system must satisfy.

These objectives should be derived from the business purpose, data classification, threat model, regulatory requirements, and enterprise security policy.

Core security objectives include:

- **Confidentiality:** Prevent unauthorized disclosure of information.
- **Integrity:** Prevent unauthorized or malicious modification of data, models, configurations, and outputs used for consequential operations.
- **Availability:** Maintain required services and recover from disruption.
- **Authenticity:** Establish confidence in identities, data sources, and system interactions.
- **Authorization:** Ensure that users, models, and tools can perform only permitted actions.
- **Accountability:** Maintain records that support investigation and attribution.
- **Resilience:** Preserve essential security properties under failure, attack, or unexpected behavior.

AI systems may require additional objectives, such as protecting model artifacts, preserving the integrity of retrieval sources, constraining agent actions, and preventing unauthorized use of model capabilities.

The organization should define measurable requirements where feasible.

For example, an AI assistant connected to confidential documents should enforce document-level authorization during retrieval, rather than relying exclusively on a system prompt instructing the model not to disclose restricted information.

### 12. Asset Identification and Security Classification

The assessment should identify the assets that require protection and determine their security significance.

Assets may include:

- Model weights and artifacts.
- Training and fine-tuning datasets.
- Inference inputs and outputs.
- System prompts and orchestration instructions.
- Vector databases and retrieval indexes.
- Source documents.
- API keys and service credentials.
- Tool execution environments.
- Application code and dependencies.
- Evaluation datasets and results.
- Logs and telemetry.
- Administrative accounts.
- Model registry and deployment configurations.
- Security policies and guardrails.

Each asset should have an owner, classification, relevant security requirements, and relationship to the AI system.

The classification should consider the consequences of disclosure, modification, loss, misuse, or unavailability.

For example, system prompts may reveal internal workflow logic or security assumptions, while service credentials may enable direct access to external systems. Their security significance depends on their content and privileges, not simply their file type.

**Required evidence:** Asset inventory, classification rationale, ownership record, and relevant protection requirements.

### 13. AI-Specific Attack Surface Identification

The assessment should identify attack surfaces introduced by AI capabilities and the systems supporting them.

AI-specific attack surfaces may include:

- Prompt and instruction inputs.
- Model inference APIs.
- System prompts and contextual instructions.
- Retrieval and grounding pipelines.
- Embedding generation and vector search.
- Model training and fine-tuning pipelines.
- Model artifact storage.
- Tool invocation and agent orchestration.
- External plugins and connectors.
- Multimodal input processing.
- Model output processing.
- Evaluation and feedback pipelines.
- Provider management interfaces.

The assessment should also consider conventional attack surfaces, including identity providers, web interfaces, cloud control planes, databases, network endpoints, and software dependencies.

Attack surface analysis should identify where untrusted data enters the system, where trust decisions occur, and where an attacker could cross a security boundary.

For example, a RAG application may expose a retrieval endpoint to users while also accepting documents from external sources. Both the user-facing interface and the document ingestion pipeline require security analysis.

The resulting attack surface inventory should inform the threat model, security testing plan, and control selection.

### 14. Threat Actor Identification

The assessment should identify plausible threat actors and their capabilities in the context of the specific AI system.

Potential threat actors include:

- External cybercriminals.
- Malicious or compromised users.
- Malicious insiders.
- Compromised suppliers.
- Competitors seeking confidential information.
- Automated bots and abusive clients.
- Attackers attempting to manipulate model behavior.
- Threat actors seeking unauthorized actions through AI agents.
- Adversaries targeting training or retrieval data.
- Opportunistic attackers exploiting misconfigured cloud services.

Threat actor analysis should consider motivation, access, technical capability, resources, and opportunities to interact with the system.

A public-facing generative AI service may be exposed to anonymous users and automated abuse. An internal AI assistant may face greater risk from compromised employee accounts, excessive permissions, or confidential data inadvertently exposed through retrieval.

The organization should avoid assuming that only sophisticated external attackers matter. Many AI security failures arise from ordinary users, compromised credentials, unsafe integrations, or insufficiently constrained system capabilities.

**Required evidence:** Threat actor assumptions, access-path analysis, capability assessment, and rationale for including or excluding material threat scenarios.

### 15. AI Security Threat Scenario Construction

Each material threat should be expressed as a scenario that describes how an attacker or unsafe interaction could compromise a security objective.

A useful structure is:

**Threat actor + attack path or enabling condition + vulnerable component or control + security consequence.**

Example:

- **Threat actor:** Malicious external user.
- **Attack path:** Crafted input containing indirect prompt injection.
- **Vulnerable component:** AI agent retrieves untrusted content and can invoke privileged tools without adequate authorization checks.
- **Security consequence:** The agent performs an unauthorized action or discloses restricted information.

The scenario should be specific enough to support control selection and testing.

Weak statement: "Prompt injection is a risk."

Stronger statement: "An attacker may place malicious instructions in a document that is later retrieved by the AI agent, causing the agent to misuse its connected email tool because tool authorization is not independently enforced."

The assessment should distinguish a plausible attack path from a confirmed vulnerability. Where a scenario has not been validated, it should be documented as a threat hypothesis or testing requirement.

### 16. Threat Modeling Methodology

The organization should select a repeatable threat modeling methodology appropriate to its architecture and security maturity.

Possible approaches include:

- STRIDE for structured threat categorization.
- Attack trees for analyzing sequences of actions.
- Data-flow-based threat modeling.
- MITRE ATLAS for AI-related adversarial techniques.
- OWASP guidance for LLM and AI application risks.
- Abuse-case analysis for misuse of system capabilities.
- Attack-surface and trust-boundary analysis.

These approaches are complementary rather than interchangeable.

For example, STRIDE can help identify threats to authentication, authorization, data integrity, and information disclosure, while MITRE ATLAS can help identify AI-specific adversarial techniques relevant to the system.

The selected methodology should define how threats are identified, prioritized, mapped to controls, and validated through testing.

The organization should document the methodology version and explain any significant deviations from the standard process.

**Required evidence:** Threat model, methodology reference, assumptions, attack-path diagrams, and review records.

### 17. Trust Boundaries and Data Flow Analysis

Trust boundaries define where information or control passes between components with different trust assumptions or security privileges.

The assessment should identify boundaries between:

- Users and AI applications.
- Applications and model providers.
- Trusted instructions and untrusted content.
- Retrieval systems and source documents.
- Models and external tools.
- Agent orchestration and execution environments.
- Development and production environments.
- Internal systems and third-party services.
- Administrative identities and runtime identities.

A representative data-flow model is:

```
User Input
    |
    v
Application Gateway
    |
    v
Identity and Authorization
    |
    v
AI Orchestration Layer
    |
    +------> Retrieval System ------> Data Sources
    |
    +------> Model Endpoint
    |
    +------> Tool Execution Layer
                    |
                    v
             External Systems
    |
    v
Output Validation and Policy Checks
    |
    v
Response or Authorized Action
```

Each transition should be assessed for authentication, authorization, input validation, data handling, integrity, logging, and failure behavior.

The diagram is illustrative. The actual architecture may differ, and the assessment should reflect the deployed implementation rather than an assumed reference design.

A key principle is that model-generated content must not automatically acquire the trust level of the application or system that processes it.

### 18. AI Security Risk Categories

The assessment should use a consistent taxonomy to classify security findings and support enterprise reporting.

Relevant categories include:

| Security category               | Representative concerns                                             |
| ------------------------------- | ------------------------------------------------------------------- |
| Identity and access management  | Excessive privileges, weak authentication, unauthorized tool access |
| Data security                   | Leakage, unauthorized retrieval, inadequate retention controls      |
| Model security                  | Model theft, manipulation, unauthorized modification                |
| Prompt and instruction security | Prompt injection, instruction confusion, unsafe context handling    |
| Retrieval security              | Cross-user data exposure, poisoned sources, authorization failures  |
| Agent and tool security         | Unrestricted actions, unsafe delegation, excessive permissions      |
| Application security            | Injection, insecure output handling, broken access control          |
| Infrastructure security         | Misconfiguration, exposed endpoints, vulnerable dependencies        |
| AI supply-chain security        | Compromised models, datasets, libraries, or providers               |
| Availability and abuse          | Denial of service, resource exhaustion, automated misuse            |
| Monitoring and response         | Inadequate telemetry, missing detection, delayed response           |
| Governance and configuration    | Uncontrolled changes, undocumented exceptions, missing approvals    |

One finding may belong to several categories.

For example, an agent that retrieves unauthorized documents and sends them through an external API may involve retrieval authorization, data confidentiality, tool security, and supplier-boundary weaknesses.

The taxonomy should support consistent classification without preventing assessors from documenting novel threats.

### 19. Confidentiality, Integrity, and Availability Analysis

The assessment should evaluate the confidentiality, integrity, and availability requirements of the AI system and its supporting assets.

**Confidentiality** analysis should consider whether unauthorized users could obtain prompts, model outputs, source documents, training data, credentials, or other sensitive information.

**Integrity** analysis should consider whether an attacker could manipulate data, model artifacts, retrieval sources, configuration, system instructions, or downstream actions.

**Availability** analysis should consider whether the system could be disrupted through resource exhaustion, dependency failure, destructive actions, or denial of service.

AI-specific scenarios may affect several objectives simultaneously.

For example, poisoned retrieval content may compromise output integrity and lead to unauthorized disclosure. A compromised agent credential may affect both confidentiality and integrity by allowing access to sensitive records and modification of business data.

The assessment should document which security objectives are affected and the consequences for the business use case.

### 20. Prompt Injection and Instruction-Handling Security

Prompt injection occurs when untrusted input influences a model to disregard intended instructions, misuse available context, or perform an action outside the intended task.

It may be direct, through user-provided input, or indirect, through content retrieved from documents, web pages, emails, or other external sources.

The assessment should examine:

- Whether the system processes untrusted instructions.
- Whether retrieved content is clearly treated as untrusted data.
- Whether model outputs can trigger privileged actions.
- Whether authorization is enforced outside the model.
- Whether tool calls are independently validated.
- Whether sensitive context is exposed to the model unnecessarily.
- Whether testing covers direct and indirect prompt injection.
- Whether failures can be detected and contained.

Prompt instructions alone should not be treated as a reliable security boundary.

For example, telling an agent not to send confidential data externally is insufficient if the agent can invoke an email API with broad permissions and the application does not validate the destination or data classification.

The assessment should evaluate the complete attack path, including the model, orchestration layer, authorization logic, tools, and downstream systems.

### 21. Sensitive Information Disclosure and Data Leakage

The assessment should examine how sensitive information could be disclosed through model inputs, outputs, retrieval, logs, integrations, or provider services.

Potential scenarios include:

- Unauthorized retrieval of confidential documents.
- Disclosure of personal data in model outputs.
- Cross-user or cross-tenant information leakage.
- Exposure of credentials or secrets.
- Inappropriate retention of sensitive prompts.
- Leakage through diagnostic logs.
- Disclosure through tool outputs or connected services.
- Re-identification or inference from combined information.

Controls should address data minimization, access enforcement, tenant isolation, output handling, logging, retention, and secure integration.

The assessment should distinguish between the model producing sensitive information and the application authorizing its disclosure. Many disclosure scenarios are caused by inadequate data access controls rather than by the model alone.

Where a system uses retrieval, access permissions should be enforced at the appropriate data and retrieval layers. A prompt telling the model to respect document permissions is not an adequate substitute for authorization enforcement.

**Required evidence:** Data-flow analysis, access-control testing, leakage testing, retention configuration, and relevant security findings.

### 22. Training-Data and Retrieval-Data Poisoning

Data poisoning involves manipulating data used to train, fine-tune, evaluate, or inform an AI system in ways that can compromise its behavior or outputs.

Retrieval-data poisoning may involve introducing malicious or misleading content into a knowledge base or other source used to ground responses.

The assessment should consider:

- Who can submit or modify data.
- How data provenance is verified.
- Whether ingestion processes validate sources.
- Whether unauthorized changes are detected.
- Whether training and evaluation datasets are protected.
- Whether retrieval sources are reviewed.
- Whether changes are version-controlled.
- Whether suspicious data can be quarantined or removed.
- Whether model or retrieval behavior is tested after material changes.

The relevant controls depend on the system. A RAG application with frequently updated documents may require strong source authentication, content validation, access controls, and change monitoring. A model-training pipeline may require stronger dataset provenance, access restrictions, and training-artifact integrity controls.

The assessment should distinguish a confirmed poisoning vulnerability from a theoretical possibility and identify the evidence needed to validate the scenario.

### 23. Model Theft, Extraction, and Unauthorized Replication

The assessment should evaluate whether an attacker could obtain model artifacts, reconstruct valuable model behavior, or access proprietary model capabilities beyond authorized limits.

Potential scenarios include:

- Unauthorized access to model weights.
- Exposure of model artifacts in storage or registries.
- Excessive access to model-serving infrastructure.
- Abuse of inference APIs to approximate model behavior.
- Extraction of proprietary information through repeated queries.
- Unauthorized copying of fine-tuned models.
- Leakage of model configuration or intellectual property.

Relevant controls may include access restrictions, artifact encryption, secure storage, API authentication, usage monitoring, rate limiting, and protection of administrative interfaces.

The appropriate safeguards depend on the model's deployment arrangement. A hosted third-party model may not expose weights, while a self-hosted model may create additional artifact-management and infrastructure risks.

The assessment should document the organization's actual exposure rather than assume that every model is susceptible to the same extraction techniques.

### 24. Insecure Output Handling

Insecure output handling occurs when AI-generated content is passed to another component without appropriate validation, encoding, authorization, or policy enforcement.

Potential consequences include:

- Cross-site scripting.
- SQL or command injection.
- Unsafe code execution.
- Improper file operations.
- Unauthorized transactions.
- Incorrect access-control decisions.
- Unsafe configuration changes.
- Manipulation of downstream automated processes.

The assessment should examine how outputs are consumed by the application, APIs, databases, tools, and users.

For example, an AI-generated SQL statement should not be executed against a production database solely because it appears syntactically valid. The application should enforce permissions, validate the operation, constrain the query, and require additional authorization where appropriate.

Security controls should be implemented at the receiving component rather than relying on the model to generate safe output consistently.

**Required evidence:** Output-handling design, input/output validation rules, authorization tests, code review, and relevant security testing results.

### 25. Excessive Agency and Unsafe Tool Execution

Excessive agency occurs when an AI system can perform actions beyond what is necessary for its intended purpose or without adequate authorization and control.

The assessment should identify all tools and actions available to the AI, including read, write, delete, communication, transaction, administrative, and external-service operations.

For each capability, assess:

- Business justification.
- Required privilege level.
- Permitted targets and resources.
- Scope of accessible data.
- Human approval requirements.
- Transaction or action limits.
- Validation of model-generated parameters.
- Logging and attribution.
- Failure and recovery behavior.
- Ability to revoke access or stop execution.

A common architectural weakness is granting an agent the same broad privileges as a human administrator when the agent requires only a narrow subset of those capabilities.

The organization should use least privilege, scoped credentials, independent authorization, constrained execution environments, and approval gates for consequential actions.

The model should not be the sole authority determining whether an action it proposes is permitted.

### 26. Vector Database and Retrieval-Augmented Generation Security

Retrieval-augmented generation introduces additional security requirements because the system retrieves information from external or internal repositories and incorporates it into model context.

The assessment should evaluate:

- Document-level authorization.
- Tenant and user isolation.
- Source authenticity.
- Data ingestion controls.
- Embedding and index integrity.
- Metadata validation.
- Retrieval filtering.
- Access revocation.
- Sensitive information exposure.
- Index updates and deletion propagation.
- Logging and auditability.
- Resistance to malicious or misleading source content.

A retrieval system may enforce access restrictions at the application level, retrieval layer, source repository, or a combination of these. The assessment should verify that the chosen design prevents unauthorized access under realistic attack scenarios.

The organization should also examine stale permissions. If a user loses access to a source document, the retrieval system should not continue exposing its content through an outdated index or cached representation.

**Required evidence:** Retrieval architecture, authorization tests, source-ingestion controls, index-update procedures, and cross-user isolation results.

### 27. AI Supply-Chain Security

The assessment should evaluate security risks introduced by third-party models, datasets, libraries, frameworks, plugins, hosted services, and other dependencies.

The supply chain may include:

- Model providers.
- Model registries and artifact repositories.
- Open-source libraries.
- Training and evaluation datasets.
- Embedding and reranking models.
- Container images.
- AI orchestration frameworks.
- External tools and connectors.
- Cloud infrastructure.
- Managed inference services.

Relevant concerns include compromised artifacts, malicious dependencies, unverified model provenance, inadequate supplier security, unauthorized changes, and limited visibility into upstream components.

Controls may include supplier assessment, provenance verification, dependency management, artifact integrity checks, vulnerability scanning, contractual security requirements, and change monitoring.

The assessment should distinguish between supplier assurances and independently verifiable evidence.

Where the organization cannot inspect a provider's internal model development process, it should document the limitation and identify alternative assurance measures appropriate to the use case.

### 28. Security Logging, Monitoring, and Incident Response

The assessment should determine whether the system produces sufficient security telemetry to detect and investigate material threats.

Relevant events may include:

- Authentication and authorization failures.
- Administrative configuration changes.
- Unusual inference activity.
- Repeated abuse patterns.
- Suspicious tool calls.
- Unauthorized retrieval attempts.
- Changes to models and datasets.
- Access to sensitive resources.
- Policy enforcement failures.
- Unexpected agent behavior.
- Security control degradation.
- Provider incidents affecting the deployment.

Logging should support investigation without collecting unnecessary sensitive data or creating a new information exposure risk.

The assessment should also establish how AI-related findings are routed to security operations and incident response.

For example, repeated attempts to use prompt injection against an agent may require correlation with tool execution logs to determine whether the attack resulted in an unauthorized action.

**Required evidence:** Logging specification, detection rules, incident-response procedures, retention settings, and testing results.

### 29. AI Security Assessment Evidence and Traceability

The assessment should preserve sufficient evidence to support its conclusions and demonstrate how security decisions were reached.

Evidence may include:

- Architecture diagrams.
- Data-flow diagrams.
- Threat models.
- Asset inventories.
- Configuration records.
- Vulnerability scan results.
- Penetration-test reports.
- AI red-team findings.
- Access-control test results.
- Supplier assurance documentation.
- Model and data provenance records.
- Secure development evidence.
- Monitoring and incident records.
- Remediation validation.
- Risk acceptance and approval records.

Each material finding should be traceable to the relevant system component, threat scenario, security objective, control, and remediation action.

Evidence should be version-controlled and protected against unauthorized modification.

A completed checklist without supporting technical evidence may demonstrate that a review took place, but it does not establish that the system's security controls are effective.

### 30. AI Security Assessment Core Implementation Principle

The AI Security Assessment Template should provide a repeatable method for evaluating the security of the complete AI-enabled system, including models, data, applications, tools, identities, infrastructure, providers, and operational processes.

It should connect threat modeling, vulnerability identification, control validation, security testing, remediation, residual risk evaluation, and deployment authorization.

The assessment must distinguish between **a model and the complete AI system**, **a threat scenario and a confirmed vulnerability**, **a documented security control and an effective control**, **model instructions and enforceable security boundaries**, and **assessment completion and authorization to deploy**.

**Core Principle:** An AI Security Assessment is effective when it identifies credible attack paths, verifies the controls intended to prevent or contain them, documents unresolved exposure, and ensures that deployment decisions reflect the system's actual security posture.

# 20.08 — AI Security Assessment Template

## Part 2 — Security Controls, Threat Validation, and Technical Testing

### 31. Security Assessment Control Framework

The AI Security Assessment should use a structured control framework to evaluate whether security requirements are implemented and effective across the AI system lifecycle.

The framework should combine conventional cybersecurity controls with AI-specific safeguards. Conventional controls remain essential for identity, infrastructure, application security, data protection, and incident response. AI-specific controls address additional attack surfaces arising from model behavior, untrusted instructions, retrieval systems, generated outputs, and autonomous tool execution.

The organization should define control objectives across the following domains:

| Control domain                      | Primary objective                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------- |
| Governance and accountability       | Establish security ownership, approval authority, and assessment requirements         |
| Asset and configuration management  | Maintain visibility into models, data, applications, tools, and dependencies          |
| Identity and access management      | Restrict access to authorized identities and actions                                  |
| Data security                       | Protect data confidentiality, integrity, provenance, and permitted use                |
| Model and artifact security         | Protect model files, configurations, registries, and deployment artifacts             |
| Application security                | Secure interfaces, orchestration, input processing, and output handling               |
| AI-specific security                | Address prompt injection, retrieval abuse, unsafe tool execution, and related threats |
| Infrastructure and network security | Protect hosting environments, network boundaries, and runtime services                |
| Supply-chain security               | Manage third-party models, datasets, software, and service dependencies               |
| Security testing                    | Validate control effectiveness through appropriate technical testing                  |
| Monitoring and incident response    | Detect, investigate, contain, and recover from security events                        |
| Change and release management       | Reassess security when material changes occur                                         |

The framework should identify mandatory controls, risk-based controls, compensating controls, and controls that are not applicable to a particular system.

A control should be considered satisfied only when its implementation and effectiveness have been evaluated using evidence appropriate to its purpose.

**Required evidence:** Approved control framework, control ownership matrix, assessment methodology, and documented control applicability decisions.

### 32. Mandatory Security Registration and Assessment Initiation

Every AI system within the organization's defined scope should be registered and screened to determine the security assessment requirements.

The initiation process should be connected to AI inventory registration, procurement, architecture review, development, and production-release workflows.

The screening record should identify:

- AI system and use-case identifiers.
- Business and technical owners.
- Deployment environment.
- Data classification.
- Model and provider.
- External interfaces.
- Connected tools and services.
- Degree of autonomy.
- Business criticality.
- Exposure to external users.
- Initial security assessment tier.
- Required specialist reviews.

The organization should define the circumstances under which a full security assessment, targeted review, penetration test, or AI red-team exercise is required.

A pilot, proof of concept, or internal-only deployment should not automatically be exempt. Such environments may still process sensitive information or provide pathways into production systems.

**Required evidence:** Registration record, screening decision, assessment scope, and approval of any permitted exclusion.

### 33. Security Assessment Tiering and Proportionality

The organization should determine assessment depth according to the system's exposure, privileges, data sensitivity, business criticality, potential consequences of compromise, and technical complexity.

A practical internal tiering model may include:

| Tier                   | Indicative characteristics                                                                          | Assessment expectations                                                                              |
| ---------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Tier 1 — Limited       | Restricted internal use, low sensitivity, no privileged actions                                     | Standard security review, baseline controls, and configuration validation                            |
| Tier 2 — Material      | Sensitive data, external integrations, consequential business workflows                             | Detailed threat model, control testing, and targeted security testing                                |
| Tier 3 — High exposure | Privileged agents, critical services, highly sensitive data, or substantial external attack surface | Enhanced threat modeling, independent review, adversarial testing, and formal security authorization |

These tiers are illustrative internal categories, not universal regulatory classifications.

Assessment depth should increase when an AI system can execute actions, access sensitive repositories, affect essential services, or operate with limited human intervention.

The organization should document the rationale for the assigned tier and identify any conditions that would require reassessment.

**Required evidence:** Approved tiering criteria, system classification, rationale, and reviewer confirmation.

### 34. Asset Inventory and Ownership Control

The organization should maintain an inventory of the assets relevant to the security assessment.

The inventory should include assets directly used by the AI system and dependencies that could affect its security.

Relevant assets include:

- Models and model artifacts.
- Training and evaluation datasets.
- Application code.
- System prompts and configuration.
- Retrieval indexes and source documents.
- Vector databases.
- API endpoints.
- Service identities and credentials.
- Tool integrations.
- Cloud resources.
- Containers and software packages.
- Logging and monitoring services.
- Administrative interfaces.
- Third-party AI services.

Each material asset should have an identifiable owner, security classification, and relationship to the assessed system.

The inventory should distinguish between assets managed by the organization and those controlled by suppliers.

Where the organization lacks direct visibility into a provider-managed component, the assessment should record the limitation and identify the available assurance evidence.

**Required evidence:** Asset inventory, ownership records, classification decisions, and dependency mapping.

### 35. Attack Surface Discovery and Coverage Control

The assessment should verify that the system's attack surface has been identified comprehensively enough to support meaningful threat analysis.

Discovery should cover public and internal interfaces, model endpoints, data ingestion pipelines, administrative services, tool integrations, retrieval systems, and relevant cloud resources.

The process should identify:

- Network-exposed endpoints.
- Authentication and authorization boundaries.
- Input and output channels.
- Data import and export mechanisms.
- Privileged execution paths.
- External API connections.
- Administrative and maintenance interfaces.
- Model and dataset update mechanisms.
- Dependencies outside the primary application boundary.

The organization should compare the documented attack surface with the actual deployed architecture and available technical discovery results.

An architecture diagram alone may be insufficient if it omits dynamically provisioned services, undocumented integrations, or externally exposed endpoints.

**Required evidence:** Attack surface inventory, architecture reconciliation, endpoint discovery results, and documented exclusions.

### 36. Threat Model Quality and Review Control

The organization should maintain a threat model that reflects the actual architecture, trust boundaries, threat actors, and security objectives.

The threat model should be reviewed when the system's capabilities or environment change materially.

Quality checks should verify that:

- Relevant trust boundaries are documented.
- Untrusted data sources are identified.
- Threat actors and access paths are plausible.
- AI-specific and conventional threats are considered.
- Security consequences are described clearly.
- Existing controls are mapped to relevant threats.
- Testing requirements are identified.
- Material assumptions and limitations are documented.
- Threat-model ownership is assigned.

A threat model that lists generic attack categories without connecting them to actual system components is insufficient.

For example, identifying prompt injection as a threat should lead to an analysis of which inputs can contain untrusted instructions, what privileges the model or agent has, and how proposed actions are authorized.

**Required evidence:** Reviewed threat model, threat-to-control mapping, testing plan, and approval record.

### 37. Identity and Authentication Control

The assessment should evaluate how users, services, administrators, agents, and external integrations establish identity.

Controls should address:

- Strong authentication appropriate to the exposure.
- Centralized identity management where suitable.
- Service identity lifecycle management.
- Credential rotation and revocation.
- Secure authentication for model and tool APIs.
- Protection of administrative accounts.
- Session and token management.
- Authentication of external service connections.
- Prevention of unauthorized impersonation.

AI systems may operate through several identities at once: the human user, the application service, the model provider account, and the tool-execution identity.

The assessment should establish whether the system preserves the appropriate user context and whether service identities can be abused to bypass user-level restrictions.

For example, a retrieval service using one highly privileged service account must not expose documents to every user simply because the service itself is authorized to retrieve them.

**Required evidence:** Identity architecture, authentication configuration, service-account inventory, and access testing.

### 38. Authorization and Least-Privilege Control

The organization should verify that access to data, tools, models, and system functions is restricted to the minimum permissions required for the intended purpose.

Authorization must be enforced by trusted application and infrastructure components, not solely by model instructions.

The assessment should examine:

- User-level access controls.
- Service-account permissions.
- Model endpoint permissions.
- Tool-specific authorization.
- Document and record-level access.
- Administrative privileges.
- Cross-tenant isolation.
- Privileged operation approval.
- Revocation and access review.
- Separation of read and write permissions.

For agentic systems, the assessment should verify that each tool has narrowly scoped permissions and that the agent cannot expand its own privileges through model-generated instructions.

A model that is told not to delete records should not have unrestricted deletion capability if deletion is unnecessary for its assigned task.

**Required evidence:** Permission matrices, authorization tests, privileged-access review, and documented exceptions.

### 39. Secrets and Credential Management

The assessment should verify that credentials and secrets used by AI applications are stored, transmitted, accessed, and rotated securely.

Relevant secrets may include:

- Model provider API keys.
- Cloud service credentials.
- Database passwords.
- Tool integration tokens.
- Signing keys.
- Encryption keys.
- Administrative credentials.
- Secrets embedded in development or deployment pipelines.

Controls should include secure secret storage, least-privilege access, rotation, revocation, protection against accidental disclosure, and monitoring for misuse.

Secrets should not be embedded unnecessarily in source code, system prompts, model context, application logs, or generated responses.

Where an AI system can inspect configuration files or invoke tools, the assessment should consider whether it could expose credentials through model outputs or unintended tool execution.

**Required evidence:** Secrets-management design, configuration review, scanning results, access records, and rotation procedures.

### 40. Data Classification and Handling Control

The organization should establish how data is classified and handled throughout the AI system lifecycle.

The assessment should consider data used for:

- Model training and fine-tuning.
- Inference requests.
- Retrieval and grounding.
- Evaluation and testing.
- Logging and monitoring.
- Human feedback.
- Incident investigation.
- Model improvement.

The security review should determine whether the system's data flows comply with the organization's classification and handling requirements.

Controls may include data minimization, encryption, access restrictions, tenant isolation, retention limits, secure deletion, and restrictions on external processing.

The assessment should also consider whether data classification is preserved when information moves between repositories, models, tools, and downstream systems.

**Required evidence:** Data-flow diagrams, classification records, handling requirements, and validation results.

### 41. Training, Fine-Tuning, and Evaluation Data Integrity

The organization should protect datasets used for training, fine-tuning, and evaluation against unauthorized modification, substitution, contamination, and loss of provenance.

Controls should address:

- Source authentication.
- Data acquisition approval.
- Integrity verification.
- Dataset versioning.
- Access restrictions.
- Change logging.
- Separation of training and evaluation data where appropriate.
- Review of unexpected or suspicious content.
- Protection of evaluation baselines.
- Reproducibility of dataset selection.

The assessment should determine whether an attacker or unauthorized insider could influence model behavior by modifying data or introducing misleading examples.

For systems using externally supplied datasets, the organization should evaluate provenance, supplier assurances, and the ability to validate the data's integrity and suitability.

**Required evidence:** Dataset lineage, version records, integrity checks, access logs, and data validation results.

### 42. Model Artifact and Registry Security

The assessment should evaluate the protection of model weights, serialized artifacts, configuration files, adapters, and other components used to deploy or reproduce the model.

Relevant controls include:

- Restricted registry access.
- Artifact integrity verification.
- Approved model provenance.
- Version control.
- Secure artifact storage.
- Protection against unauthorized replacement.
- Controlled promotion between environments.
- Vulnerability and malware checks where appropriate.
- Deployment approval.
- Traceability between evaluated and deployed artifacts.

The organization should verify that the model deployed to production is the model that was approved and tested.

For example, a model registry that allows unreviewed users to replace a production artifact creates an integrity risk even if the inference endpoint itself is strongly authenticated.

**Required evidence:** Registry access configuration, artifact hashes or equivalent integrity records, provenance documentation, and release records.

### 43. Prompt and Configuration Integrity

System prompts, orchestration instructions, guardrails, model parameters, and tool definitions can materially influence AI behavior and should be treated as controlled configuration.

The assessment should evaluate:

- Who may modify system instructions.
- How configuration changes are reviewed.
- Whether changes are version-controlled.
- How configuration is tested before release.
- Whether secrets are excluded.
- Whether unauthorized overrides are prevented.
- Whether production and development configurations are separated.
- Whether changes can be traced to an approved request.

The organization should distinguish between configuration integrity and the model's ability to resist malicious user inputs.

Protecting a system prompt from unauthorized modification does not by itself prevent prompt injection. Both configuration integrity and runtime defenses must be assessed.

**Required evidence:** Configuration repository, access controls, version history, testing results, and approval records.

### 44. Input Validation and Untrusted Content Handling

The organization should validate inputs before they enter the AI application or are passed to downstream components.

Input controls may address:

- Request size and format.
- File type and content validation.
- Malformed payloads.
- Unsupported input types.
- Rate and resource limits.
- External content retrieval.
- Malicious document content.
- Multimodal inputs.
- Untrusted instructions.
- Data classification and policy restrictions.

Validation should occur at the appropriate application boundary and should not rely exclusively on the model's interpretation of the input.

For example, a document-ingestion service should validate files and apply access controls before adding content to a retrieval index. It should not assume that the model will ignore malicious instructions embedded in an uploaded document.

The assessment should also consider whether rejected inputs are logged safely and whether validation errors reveal sensitive implementation details.

**Required evidence:** Input validation specification, negative test cases, file-handling controls, and test results.

### 45. Prompt Injection Defense-in-Depth Control

The organization should implement layered controls to reduce the likelihood and consequences of direct and indirect prompt injection.

Possible safeguards include:

- Treating user and retrieved content as untrusted.
- Separating trusted configuration from external content.
- Limiting the information supplied to the model.
- Restricting tool permissions.
- Validating proposed actions outside the model.
- Requiring approval for consequential operations.
- Enforcing destination and data-access policies.
- Monitoring suspicious input and tool-call patterns.
- Testing direct and indirect injection scenarios.

No single prompt pattern or filtering mechanism should be assumed to eliminate prompt injection.

The effectiveness of the controls depends on the complete architecture, especially whether an attack can lead to unauthorized data access or actions.

The assessment should verify that successful manipulation of model behavior does not automatically grant the attacker additional privileges.

**Required evidence:** Threat scenarios, defense-in-depth design, adversarial testing results, and documented residual limitations.

### 46. Output Validation and Downstream Execution Control

The assessment should verify that model-generated outputs are validated before being used by applications, databases, tools, or business workflows.

Controls should address:

- Schema validation.
- Context-appropriate encoding.
- Command and query restrictions.
- Output size and format limits.
- Authorization of proposed actions.
- Validation of target resources.
- Safe handling of generated code.
- Human approval for consequential actions.
- Rejection of malformed or unauthorized requests.

The system should distinguish between generating a recommendation and executing an operation.

For example, an AI model may suggest a command to modify a cloud resource, but a trusted execution layer should independently verify the command, validate the target, enforce permissions, and apply required approvals.

The receiving component should remain responsible for enforcing its own security policy.

**Required evidence:** Output-handling design, validation rules, authorization checks, and negative testing results.

### 47. Retrieval Authorization and Tenant Isolation

For RAG and knowledge-based AI systems, the assessment should verify that retrieval respects the permissions of the requesting user and the applicable tenant or data boundary.

The control should address:

- Document-level authorization.
- Metadata integrity.
- Tenant isolation.
- Access revocation.
- Cache isolation.
- Index synchronization.
- Search-result filtering.
- Retrieval-service privileges.
- Authorization of citations and source links.

Filtering only the final model response is insufficient if unauthorized documents have already been retrieved and exposed to the model.

The assessment should verify that access restrictions are enforced before sensitive content enters the model context whenever the architecture permits, and that subsequent processing does not reintroduce unauthorized disclosure.

**Required evidence:** Retrieval access model, cross-user and cross-tenant tests, revocation tests, and index synchronization records.

### 48. Model Endpoint and API Security

The assessment should verify that model-serving endpoints and related APIs are protected against unauthorized access, abuse, manipulation, and resource exhaustion.

Controls may include:

- Strong authentication.
- Fine-grained authorization.
- Rate limiting.
- Request quotas.
- Input validation.
- Network restrictions.
- Secure transport.
- Usage monitoring.
- Abuse detection.
- Error handling.
- Version management.
- Protection of administrative operations.

Where an endpoint is publicly accessible, the organization should assess anonymous abuse, automated traffic, cost exhaustion, and attempts to infer sensitive information through repeated queries.

Where the model is hosted by a third party, the organization should evaluate the provider's available controls and independently secure its own integration.

**Required evidence:** API security configuration, authentication tests, rate-limit tests, monitoring rules, and provider security documentation where applicable.

### 49. AI Agent Tool Authorization and Action Boundaries

AI agents should operate within explicit action boundaries that are enforced independently of model-generated reasoning.

The assessment should inventory each tool and classify its potential consequences.

Example:

| Tool capability         | Security concern                          | Potential safeguard                          |
| ----------------------- | ----------------------------------------- | -------------------------------------------- |
| Read internal documents | Unauthorized information access           | Document-level authorization                 |
| Send email              | Data disclosure or external communication | Recipient restrictions and approval gates    |
| Modify customer records | Unauthorized or incorrect changes         | Scoped permissions and validation            |
| Execute cloud commands  | Infrastructure compromise                 | Restricted execution and privileged approval |
| Initiate payments       | Financial loss                            | Transaction limits and human authorization   |
| Delete records          | Irreversible data loss                    | Restricted permissions and recovery controls |

The assessment should verify that tools cannot be invoked with privileges beyond the approved use case.

Where a tool can perform irreversible or externally consequential actions, stronger approval, transaction limits, logging, and recovery controls may be required.

**Required evidence:** Tool inventory, permission matrix, action policy, execution logs, and negative test results.

### 50. Human Approval and High-Impact Action Control

The organization should identify AI-generated actions that require human approval before execution.

Approval requirements should be based on the consequence, reversibility, sensitivity, and authorization requirements of the action.

Examples may include:

- Sending confidential information externally.
- Making financial commitments.
- Modifying privileged infrastructure.
- Deleting important records.
- Changing access permissions.
- Taking actions that materially affect individuals.
- Executing high-impact business transactions.

The approval mechanism should present sufficient context for the reviewer to understand the proposed action and its potential consequences.

A generic approval button that does not expose the target, operation, and relevant data may provide weak protection.

The system should also prevent the AI agent from altering or bypassing the approval workflow through an alternative execution path.

**Required evidence:** Approval policy, workflow configuration, authorization tests, and audit records.

### 51. Infrastructure and Network Security

The assessment should evaluate the security of the infrastructure hosting the AI application, model, data stores, and related services.

Controls may include:

- Network segmentation.
- Private endpoints where appropriate.
- Restricted administrative access.
- Secure cloud configuration.
- Firewall and egress controls.
- Container and workload hardening.
- Patch and vulnerability management.
- Encryption in transit and at rest.
- Secure service-to-service communication.
- Infrastructure monitoring.
- Environment separation.

AI applications may introduce additional egress risks because model-generated instructions or retrieved content can influence interactions with external services.

The organization should verify that network controls restrict access according to the intended architecture and do not rely solely on model-level behavior.

**Required evidence:** Network architecture, cloud configuration review, infrastructure scan results, and remediation records.

### 52. Dependency and Software Supply-Chain Security

The assessment should evaluate the security of software libraries, frameworks, model-serving components, container images, plugins, and other dependencies.

Controls may include:

- Software composition analysis.
- Dependency inventory.
- Vulnerability scanning.
- Approved package sources.
- Version pinning where appropriate.
- Integrity verification.
- Secure build pipelines.
- Dependency update management.
- Supplier risk assessment.
- Monitoring for newly disclosed vulnerabilities.

The organization should consider dependencies used in AI orchestration, retrieval, vector search, model loading, and tool integration.

A vulnerability in a supporting library may expose credentials, permit remote code execution, or compromise the integrity of model outputs and downstream actions.

**Required evidence:** Dependency inventory, scan results, vulnerability triage, approved exceptions, and remediation records.

### 53. Model and Data Provenance Control

The assessment should verify that the organization can establish where models and material datasets originated and how they have changed.

Provenance controls should address:

- Provider and source identity.
- Model and dataset versions.
- Acquisition records.
- Licensing and permitted use where relevant.
- Integrity verification.
- Transformation history.
- Fine-tuning and evaluation lineage.
- Approval before production use.
- Traceability of deployed artifacts.

Provenance is important for security because an unverified model or dataset may contain unexpected behavior, malicious modifications, or undisclosed dependencies.

The level of evidence available will vary by acquisition model. An organization may have detailed lineage for an internally trained model but limited visibility into a proprietary hosted model.

Where provenance cannot be fully verified, the organization should document the limitation and evaluate compensating assurance measures.

**Required evidence:** Provenance records, version history, supplier documentation, artifact verification, and approval records.

### 54. Logging and Security Telemetry Control

The assessment should determine whether relevant security events are logged and available for investigation.

Logging should cover, as appropriate:

- Authentication and authorization events.
- Administrative changes.
- Model and configuration updates.
- Access to sensitive data.
- Tool invocations.
- Failed or blocked actions.
- API abuse indicators.
- Security-policy violations.
- Unexpected retrieval behavior.
- Changes to data sources.
- Security findings and remediation.
- Incident response actions.

The logging design should define event fields, time synchronization, access restrictions, retention, integrity protection, and integration with security monitoring.

The organization should balance investigative value against privacy and confidentiality risks. Logging full prompts or model outputs may be inappropriate if those records contain credentials, personal data, or confidential information.

**Required evidence:** Logging specification, sample event records, access controls, retention settings, and monitoring integration tests.

### 55. Security Monitoring and Detection Engineering

The organization should establish detection mechanisms for material AI security threats and control failures.

Detection scenarios may include:

- Repeated prompt-injection attempts.
- Unusual model endpoint usage.
- Unexpected access to sensitive documents.
- Suspicious tool execution.
- Repeated authorization failures.
- Unauthorized configuration changes.
- Abnormal data export.
- Resource exhaustion.
- Changes to model or dataset artifacts.
- Use of unapproved providers or integrations.

Detection rules should be mapped to threat scenarios and assigned to accountable security operations owners.

The organization should test whether alerts are generated, routed, investigated, and resolved appropriately.

A monitoring dashboard without actionable detection rules and response procedures should not be treated as an effective security control.

**Required evidence:** Detection catalogue, alert tests, use cases, incident-routing configuration, and review records.

### 56. Vulnerability Management and Remediation Control

Security findings should be recorded, prioritized, assigned, remediated, and validated through the organization's vulnerability and risk management processes.

Each finding should include:

- Finding identifier.
- Affected system and component.
- Vulnerability or weakness description.
- Evidence and reproduction details where appropriate.
- Severity and business context.
- Exploitability and exposure.
- Recommended remediation.
- Accountable owner.
- Target date.
- Exception or risk acceptance reference.
- Retest outcome.

AI-specific findings may require additional context because the security consequence depends on the model's privileges, access to sensitive information, and ability to invoke tools.

For example, prompt injection affecting an isolated text generator may have a different consequence from prompt injection affecting an agent with write access to production systems.

The organization should prioritize remediation based on the actual attack path and consequence, not merely the name of the vulnerability category.

**Required evidence:** Finding register, remediation records, retest results, and overdue-finding escalation.

### 57. Penetration Testing and AI Red-Team Validation

The organization should determine which systems require penetration testing, AI red teaming, or a combination of both.

Penetration testing evaluates technical weaknesses in applications, infrastructure, interfaces, and access controls. AI red teaming examines adversarial behavior and system weaknesses arising from AI-specific capabilities and use contexts.

Relevant testing may include:

- Prompt injection.
- Sensitive information disclosure.
- Retrieval authorization bypass.
- Tool misuse.
- Insecure output handling.
- Model endpoint abuse.
- Agent permission escalation.
- Data poisoning scenarios where applicable.
- Abuse of multimodal inputs.
- Cross-user or cross-tenant access.
- Denial of service and resource exhaustion.

Testing should be scoped, authorized, and conducted in a controlled environment with appropriate safeguards.

The organization should define how findings are documented, prioritized, remediated, and retested. Testing limitations must be recorded; a successful test campaign does not prove that every possible attack has been eliminated.

**Required evidence:** Approved test scope, methodology, findings, remediation records, retest results, and documented coverage limitations.

### 58. AI Security Exception Management

The organization should establish a formal process for exceptions to internal AI security requirements.

An exception should not be used to bypass applicable law, contractual obligations, or non-negotiable security requirements.

Each exception should document:

- Requirement being excepted.
- Affected system and use case.
- Business justification.
- Threat and impact analysis.
- Existing safeguards.
- Compensating controls.
- Accountable owner.
- Approval authority.
- Expiry or review date.
- Conditions for closure.

Exceptions should be time-bound where appropriate and monitored until resolved.

For example, a system may temporarily lack a planned security integration. The exception must establish whether deployment is permitted, which compensating controls apply, and when the deficiency must be corrected.

**Required evidence:** Exception register, approval record, compensating-control validation, expiry monitoring, and closure evidence.

### 59. Security Risk Acceptance and Deployment Authorization

The organization should define who may accept residual security risks and authorize deployment.

The decision should consider:

- Finding severity and exploitability.
- Exposure of sensitive information.
- System privileges and capabilities.
- Effectiveness of implemented safeguards.
- Availability of safer alternatives.
- Business criticality.
- Legal and contractual requirements.
- Monitoring and incident-response readiness.
- Remaining uncertainty.
- Conditions or restrictions required.

The assessment should distinguish between a security team's recommendation and the formal decision of the authorized risk owner.

Unresolved critical findings should follow the organization's mandatory escalation rules. They should not be treated as acceptable merely because a business deadline is approaching.

**Required evidence:** Residual-risk analysis, risk acceptance record, authorized approval, deployment conditions, and review date.

### 60. Secure Development and CI/CD Integration

For internally developed AI systems, the assessment should verify that security controls are incorporated into the development and deployment lifecycle.

Relevant controls include:

- Secure design review.
- Threat modeling.
- Code review.
- Static and dynamic application security testing.
- Dependency scanning.
- Secret scanning.
- Infrastructure-as-code validation.
- Container scanning.
- Model and artifact integrity checks.
- AI-specific testing.
- Release authorization.
- Post-deployment verification.

Where feasible, the organization should enforce mandatory security gates in the delivery pipeline.

A deployment pipeline should not permit release simply because conventional software tests pass if required AI security checks or critical remediation actions remain incomplete.

The organization should also manage exceptions and emergency releases through documented, authorized procedures.

**Required evidence:** Pipeline configuration, test results, release records, security-gate outcomes, and approved exceptions.

### 61. Environment Separation and Production Protection

The organization should separate development, testing, staging, and production environments according to the sensitivity and criticality of the system.

Controls should address:

- Environment-specific identities.
- Separate credentials.
- Network boundaries.
- Access restrictions.
- Data segregation.
- Model artifact promotion.
- Configuration management.
- Production logging.
- Deployment approvals.
- Protection of sensitive test data.

Development and testing environments should not automatically inherit production privileges or unrestricted access to production data.

For AI systems, environment separation should also cover model endpoints, retrieval indexes, agent tools, and evaluation datasets.

The assessment should verify that test prompts, experiments, and model configurations cannot unintentionally alter production behavior.

**Required evidence:** Environment architecture, identity and network controls, release procedures, and access testing.

### 62. Backup, Recovery, and Secure Failure Handling

The assessment should evaluate how the AI system behaves during service disruption, dependency failure, model unavailability, or security incidents.

The recovery design should address:

- Backup and restoration of critical data.
- Model and configuration recovery.
- Recovery of retrieval indexes.
- Credential revocation and replacement.
- Failover and service continuity.
- Integrity verification after restoration.
- Recovery-point and recovery-time objectives.
- Safe fallback behavior.
- Restrictions on automated actions during failure.

An AI system should not automatically bypass security controls because a model provider, authorization service, or monitoring component becomes unavailable.

For example, if an agent cannot verify authorization, it should not default to unrestricted access to complete a task.

**Required evidence:** Recovery plan, backup configuration, restoration tests, failure-mode tests, and documented continuity procedures.

### 63. Third-Party AI Security Assurance

The organization should evaluate security risks associated with external AI providers, hosted models, plugins, APIs, and managed services.

The assessment should consider:

- Provider security documentation.
- Independent assurance reports where available.
- Data processing and retention practices.
- Identity and access controls.
- Tenant isolation.
- Encryption and key management.
- Vulnerability and incident handling.
- Model and service change notification.
- Subprocessor dependencies.
- Audit rights and contractual commitments.
- Service continuity and exit arrangements.

Supplier certifications and assurance reports can provide useful evidence, but they do not automatically establish that the provider is suitable for the organization's intended use case.

The organization should assess the integration itself, including the data sent to the provider, the permissions granted, the behavior of returned outputs, and the controls available to detect or contain failures.

**Required evidence:** Supplier assessment, assurance documentation, contractual review, integration security tests, and residual-risk decision.

### 64. Security Assessment Quality Assurance

The organization should establish quality checks to ensure that assessments are complete, technically credible, evidence-based, and suitable for deployment decisions.

The review should verify that:

- The assessment scope matches the deployed architecture.
- Relevant assets and dependencies are identified.
- Trust boundaries are documented.
- Threat scenarios are specific and plausible.
- AI-specific attack paths are considered.
- Conventional security controls are evaluated.
- Findings are supported by evidence.
- Control effectiveness is distinguished from control documentation.
- Critical findings receive appropriate treatment.
- Residual risks are justified.
- Required approvals are obtained.
- Testing limitations are disclosed.
- Monitoring and reassessment requirements are defined.

High-exposure systems should receive a level of review proportionate to their consequences and technical complexity.

**Required evidence:** Quality-review checklist, reviewer findings, remediation records, and final assessment recommendation.

### 65. Security Assessment Integration with the AI System Inventory

The AI Security Assessment should be linked to the authoritative AI System Inventory.

The inventory should record whether an assessment is required, its current status, the latest approved version, and the next review date.

The integration should support:

- Identification of unassessed AI systems.
- Visibility into system ownership.
- Tracking of security approval status.
- Linking of material findings.
- Identification of systems with expired reviews.
- Monitoring of deployment restrictions.
- Reassessment after material system changes.

The inventory should not mark a system as security-approved merely because an assessment record exists.

The status should reflect whether required testing has been completed, material findings have been addressed or formally handled, and the appropriate authorization has been obtained.

**Required evidence:** Inventory linkage, reconciliation reports, status-validation results, and records of missing or overdue assessments.

### 66. Security Assessment Integration with the AI Risk Register

Material security findings should be linked to the AI Risk Register or the organization's established security risk management repository.

The relationship should preserve the distinction between a technical finding, a threat scenario, and a risk requiring governance treatment.

For example:

- **Finding:** An agent's tool execution layer does not independently validate authorization.
- **Threat scenario:** A prompt-injection attack causes the agent to invoke an unauthorized operation.
- **Risk:** Unauthorized modification or disclosure of business information.
- **Treatment:** Enforce server-side authorization, restrict tool permissions, test attack paths, and monitor unauthorized attempts.

The organization should avoid unnecessary duplication of risk records while preserving traceability between findings, remediation actions, and accepted residual risks.

**Required evidence:** Finding-to-risk mapping, linked identifiers, treatment records, and reconciliation results.

### 67. Security Assessment Integration with Change Management

Changes to an AI system may introduce new attack surfaces or invalidate previously tested security assumptions.

The assessment process should integrate with change management to identify when targeted security review or full reassessment is required.

Potential triggers include:

- A model or provider change.
- New tools or agent capabilities.
- New data sources.
- Changes to retrieval architecture.
- New external integrations.
- Expanded permissions.
- Changes to system prompts or guardrails.
- Changes in hosting or network architecture.
- New user populations.
- Material changes in deployment scale.

The organization should define how changes are classified and what security evidence is required before release.

**Required evidence:** Change record, security impact analysis, test results, reassessment decision, and release approval.

### 68. Post-Deployment Security Monitoring and Reassessment

The organization should establish ongoing monitoring to identify threats, control failures, and changes in the security posture of the AI system.

Monitoring may include:

- Unusual API usage.
- Repeated injection attempts.
- Unauthorized retrieval attempts.
- Abnormal tool execution.
- Model or configuration changes.
- New vulnerabilities in dependencies.
- Provider security advisories.
- Unexpected data movement.
- Security incidents and near misses.
- Failures of access or validation controls.

Monitoring should be linked to defined response procedures and reassessment triggers.

The organization should determine when a finding requires an incident investigation, a targeted security review, a full reassessment, a deployment restriction, or suspension.

**Required evidence:** Monitoring plan, detection rules, review records, incident links, and reassessment decisions.

### 69. Security Metrics and Management Reporting

The organization should define metrics that evaluate both assessment-process performance and the security condition of the AI portfolio.

Potential indicators include:

- Percentage of in-scope systems with current security assessments.
- Percentage of required assessments completed before deployment.
- Number of unresolved critical and high-severity findings.
- Age of overdue remediation actions.
- Percentage of critical findings successfully retested.
- Number of systems with expired exceptions.
- Percentage of high-exposure systems subjected to required adversarial testing.
- Number of security incidents involving AI systems.
- Percentage of material changes triggering security review.
- Percentage of assessments with validated threat models.

Metrics should have defined owners, data sources, calculations, thresholds, and reporting cadence.

A high assessment-completion rate does not establish that systems are secure. Reporting should include control effectiveness, unresolved findings, incident trends, and the quality of remediation.

**Required evidence:** Metric definitions, dashboard records, trend analysis, and documented management actions.

### 70. Security Deficiency and Corrective Action Management

The organization should maintain a formal process for addressing deficiencies identified through assessment, technical testing, monitoring, incident investigation, and independent assurance.

Each deficiency should include:

- Finding identifier.
- Affected system and component.
- Description and supporting evidence.
- Threat scenario and potential consequence.
- Severity and priority.
- Root cause where appropriate.
- Corrective action.
- Accountable owner.
- Target completion date.
- Retest criteria.
- Closure evidence.

Material deficiencies should be escalated according to the organization's security risk thresholds.

Closure should require evidence that the weakness has been addressed sufficiently for the intended purpose. A ticket marked "resolved" is not equivalent to a successful validation test.

**Required evidence:** Deficiency register, remediation records, retest results, and closure approval.

### 71. Periodic Control Testing and Sampling

The organization should periodically test whether the AI Security Assessment process and its associated controls operate as designed.

Testing may sample systems across business units, deployment environments, impact tiers, and AI technology types.

Representative test procedures include:

- Verify that in-scope systems are registered.
- Confirm that security assessments precede required deployment gates.
- Trace findings to supporting evidence.
- Verify that critical vulnerabilities are remediated or appropriately escalated.
- Test selected identity and authorization controls.
- Verify tool permissions against approved requirements.
- Confirm that provider or model changes trigger review.
- Verify that security exceptions are valid and current.
- Confirm that monitoring findings are investigated.
- Test whether historical decisions can be reconstructed.

Sampling should be risk-based. High-exposure systems, systems with previous control failures, and systems capable of consequential automated actions may require more intensive testing.

**Required evidence:** Test plan, sample selection, workpapers, findings, remediation assignments, and retest results.

### 72. Security Assessment Automation and Workflow Enforcement

The organization may automate assessment initiation, control mapping, evidence collection, finding creation, reviewer assignment, deadline tracking, and reporting.

Automation should improve consistency and traceability without replacing professional judgment in material threat analysis or risk acceptance.

Suitable automation includes:

- Triggering security screening when a system is registered.
- Routing high-exposure systems to specialist reviewers.
- Linking vulnerability findings to assessment records.
- Creating remediation tasks.
- Alerting owners about overdue actions.
- Detecting missing approval records.
- Triggering reassessment after defined changes.
- Reconciling inventory and assessment status.

Automated rules should be tested and version-controlled. Incorrect logic can create systemic failures, such as allowing an unassessed agent to enter production or failing to trigger review after a permission expansion.

**Required evidence:** Workflow configuration, rule definitions, test results, audit logs, and approved changes.

### 73. Part 2 Core Implementation Principle

The AI Security Assessment control framework should connect asset identification, threat modeling, identity and access management, data security, AI-specific safeguards, technical testing, remediation, and deployment authorization.

Controls should be selected according to the actual architecture and threat environment. Their effectiveness should be validated through appropriate evidence rather than inferred from policy documentation or the presence of security tooling.

The assessment must distinguish between **a threat and a vulnerability**, **a vulnerability and a business risk**, **a configured control and an effective control**, **model-level instructions and independently enforced authorization**, and **remediation completion and validated remediation**.

**Core Principle:** An AI Security Assessment becomes an effective security control when credible threats are mapped to enforceable safeguards, material weaknesses are tested and remediated, and residual exposure is reviewed by an authorized decision-maker before deployment and throughout operation.

## Part 3 — Governance, Accountability, Risk Acceptance, and Security Oversight

### 74. AI Security Assessment Governance Model

The organization should establish a formal governance model that defines how AI security assessments are initiated, performed, reviewed, approved, monitored, and periodically reassessed.

The governance model should integrate AI security assessment into the enterprise cybersecurity program and the broader AI governance operating model. It should ensure that technical findings are translated into risk decisions, deployment conditions, and accountable remediation commitments.

The model should define:

- Executive accountability for AI security risk.
- Business ownership of AI use cases.
- Technical ownership of AI architecture and controls.
- Independent security assessment responsibilities.
- Risk acceptance authority.
- Deployment authorization requirements.
- Escalation and exception procedures.
- Ongoing monitoring and reassessment obligations.
- Reporting to relevant management and oversight committees.

Governance should distinguish between the team that develops or operates an AI system and the personnel responsible for independently challenging its security posture.

A development team may provide evidence and remediate findings, but it should not automatically have unrestricted authority to approve its own unresolved material risks.

**Required evidence:** AI security governance charter, assessment operating procedure, responsibility matrix, approval framework, and escalation criteria.

### 75. Three Lines of Accountability and Independent Oversight

AI security assessments should operate within the organization's established accountability and assurance structure.

A practical model distinguishes between operational ownership, independent risk and control oversight, and independent assurance.

| Accountability layer                                              | Typical responsibilities                                          | AI security assessment application                                                                          |
| ----------------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| First line — Business and technology operations                   | Own systems, implement controls, manage risks, remediate findings | Register AI systems, provide architecture evidence, implement safeguards, resolve deficiencies              |
| Second line — Risk, security governance, and compliance oversight | Define requirements, challenge risk decisions, monitor adherence  | Establish assessment methodology, review material risks, challenge exceptions, monitor portfolio exposure   |
| Third line — Internal audit                                       | Independently evaluate governance and control effectiveness       | Test assessment completeness, verify approval integrity, evaluate remediation and risk acceptance processes |

The precise organizational structure may vary. In smaller organizations, some responsibilities may be combined, but incompatible duties should remain appropriately separated.

Internal audit should retain sufficient independence to evaluate the effectiveness of the assessment program rather than becoming the operational owner of the controls it later audits.

**Required evidence:** Accountability mapping, independence safeguards, oversight records, and audit responsibilities.

### 76. Executive Accountability for AI Security Risk

Executive management should establish the level of AI security risk the organization is prepared to accept and ensure that sufficient resources are available to manage that exposure.

Executive accountability should include:

- Approving the AI security governance framework.
- Establishing risk tolerance and escalation thresholds.
- Assigning accountable business and technology owners.
- Ensuring appropriate security assessment capability.
- Reviewing material unresolved security risks.
- Authorizing risk acceptance within delegated limits.
- Ensuring that critical findings are not bypassed through informal decisions.
- Monitoring systemic weaknesses across the AI portfolio.

Executives do not need to approve every technical finding. Their involvement should be proportionate to the risk, business consequence, and limits of delegated authority.

For example, a material unresolved vulnerability affecting an AI agent with privileged access to production infrastructure may require executive-level escalation if it exceeds the organization's approved risk tolerance.

**Required evidence:** Executive approvals, risk appetite documentation, management reporting, and records of material security decisions.

### 77. AI Security Governance Committee Charter

Where organizational scale and risk justify it, an AI security governance committee should coordinate oversight of material AI security risks and assessment outcomes.

The committee may include representatives from:

- Information security.
- AI governance.
- Enterprise risk management.
- Architecture and engineering.
- Data governance.
- Privacy and legal functions.
- Business operations.
- Compliance.
- Procurement and third-party risk management.
- Security operations.
- Internal audit as an independent observer, where appropriate.

The charter should define the committee's purpose, membership, decision rights, quorum, meeting cadence, escalation responsibilities, and reporting obligations.

Typical responsibilities include reviewing material security findings, resolving cross-functional ownership disputes, approving designated exceptions, evaluating recurring weaknesses, and monitoring remediation of systemic issues.

The committee should not replace accountable system owners or specialist technical reviewers. Its purpose is to ensure consistent governance and appropriate decisions across organizational boundaries.

**Required evidence:** Approved committee charter, membership record, meeting minutes, decision log, and action tracker.

### 78. Decision Rights and Approval Authority

The organization should document who has authority to make each significant decision arising from an AI Security Assessment.

Decision rights should cover:

- Assessment scope and classification.
- Acceptance of assessment evidence.
- Security finding severity.
- Remediation priorities.
- Deployment restrictions.
- Security exception approval.
- Residual-risk acceptance.
- Production authorization.
- Emergency deployment.
- Suspension or withdrawal.
- Reassessment following material change.

Decision authority should be based on the organization's delegated approval framework and the risk's materiality.

Technical personnel may determine whether a control has passed a defined test, but acceptance of the resulting business risk may belong to a separate authorized risk owner.

An assessment recommendation should not be interpreted as formal deployment authorization unless the approving role has the necessary delegated authority.

**Required evidence:** Decision-rights matrix, approval thresholds, delegated authority records, and workflow configuration.

### 79. Business Owner Accountability

Each AI system should have an accountable business owner responsible for ensuring that the system's intended purpose, business consequences, and operational constraints are reflected in the security assessment.

The business owner should:

- Confirm the intended use and business justification.
- Identify critical business processes and dependencies.
- Ensure that relevant stakeholders participate.
- Support the identification of credible security consequences.
- Fund and prioritize remediation.
- Ensure that deployment conditions are followed.
- Accept residual risk only within delegated authority.
- Notify security teams of material changes.
- Ensure that the system is suspended or restricted when required.

Business ownership does not transfer the responsibility for technical control implementation away from engineering or security teams.

The business owner remains accountable for ensuring that security risk is considered in business decisions and that the organization does not continue operating a system under conditions that violate its approved authorization.

**Required evidence:** Named business owner, ownership acceptance, remediation commitments, and documented risk decisions.

### 80. Independent Security Review and Technical Challenge

The organization should determine which AI Security Assessments require independent review based on exposure, complexity, consequence, and uncertainty.

Independent review may be appropriate for:

- Systems with privileged agent capabilities.
- Systems handling highly sensitive information.
- Public-facing AI services with substantial attack surfaces.
- AI supporting critical business operations.
- Systems with unresolved high-severity findings.
- Material changes to previously approved architecture.
- Systems with significant third-party dependencies.
- Systems for which testing evidence is incomplete or disputed.

The reviewer should evaluate the quality of the threat model, adequacy of testing, credibility of findings, effectiveness of remediation, and justification for residual-risk acceptance.

Independence should be assessed in substance rather than merely by job title. A reviewer who designed and implemented the control may lack the necessary objectivity to provide an independent challenge of that control.

**Required evidence:** Review criteria, reviewer assignment, independence declaration where required, challenge log, and review outcome.

### 81. Enterprise AI Security Risk Appetite

The organization should establish how much AI-related security exposure it is willing to tolerate in pursuit of business objectives.

Risk appetite should be expressed in operationally meaningful terms, including non-negotiable requirements and thresholds that trigger escalation.

Examples include:

- No unauthorized access to restricted information.
- No production deployment with specified categories of unresolved critical vulnerabilities.
- No unrestricted agent execution of designated high-impact actions.
- No use of unapproved AI providers for restricted data.
- Mandatory independent review for defined high-exposure systems.
- Defined remediation timelines for material security findings.
- Mandatory escalation for security control failures affecting critical services.

Risk appetite should distinguish between tolerable uncertainty and unacceptable exposure.

It should also recognize that a risk may be unacceptable because of legal, contractual, safety, or other mandatory obligations, even if its estimated financial impact appears limited.

**Required evidence:** Approved AI security risk appetite statement, risk thresholds, mandatory control requirements, and escalation rules.

### 82. Security Severity and Escalation Thresholds

The organization should establish consistent criteria for assigning security finding severity and determining when escalation is required.

Severity should consider:

- Exploitability.
- Attacker prerequisites.
- Required privileges.
- Data sensitivity.
- Potential impact on confidentiality, integrity, and availability.
- Scope of affected users or systems.
- Business criticality.
- Availability of effective safeguards.
- Persistence and reversibility.
- Potential for lateral movement or privilege escalation.

AI-specific scenarios should be evaluated in their actual operating context.

A prompt-injection weakness should not be classified solely by the presence of malicious instructions. The analysis should determine whether the weakness can lead to unauthorized disclosure, unsafe execution, privilege abuse, or another material consequence.

The organization should define mandatory escalation criteria for critical findings, repeated control failures, overdue remediation, and circumstances where the security posture materially deteriorates.

**Required evidence:** Severity methodology, escalation matrix, finding records, and evidence of escalation compliance.

### 83. Residual Security Risk Acceptance

Residual security risk is the exposure that remains after applicable safeguards and remediation measures have been implemented.

The organization should require a documented decision before accepting material residual risk.

The decision should consider:

- The original threat scenario.
- The weakness that creates exposure.
- Existing and proposed safeguards.
- Evidence of control effectiveness.
- Remaining attack paths.
- Consequences if exploitation succeeds.
- Uncertainty and assessment limitations.
- Available alternatives.
- Remediation feasibility and timing.
- Monitoring and contingency arrangements.

The risk owner should understand what remains possible despite the safeguards.

For example, a system may have strong authentication and logging while remaining vulnerable to indirect prompt injection. Those controls may reduce unauthorized access and improve detection, but they do not necessarily prevent an agent from performing an improperly authorized action.

Risk acceptance should be specific to the assessed system, use case, architecture, and operating conditions.

**Required evidence:** Residual-risk analysis, compensating-control evidence, authorized acceptance, expiry or review date, and operating restrictions.

### 84. Segregation of Duties

The organization should establish appropriate segregation of duties across assessment, remediation, verification, and approval.

The objective is to reduce conflicts of interest, unauthorized changes, and self-approval of material risks.

The operating model should distinguish, where practical:

- System development and independent security review.
- Control implementation and control-effectiveness verification.
- Finding remediation and closure validation.
- Risk analysis and residual-risk acceptance.
- Supplier selection and independent security assurance.
- Emergency change implementation and subsequent review.

Smaller organizations may not have sufficient personnel to separate every activity. In such cases, compensating safeguards may include independent external review, secondary approval, enhanced logging, or post-implementation verification.

The organization should document exceptions to segregation requirements and the controls used to manage the resulting conflict.

**Required evidence:** Segregation-of-duties matrix, role assignments, approval records, and documented compensating safeguards.

### 85. Escalation of Material Security Findings

The organization should define a formal escalation process for findings that exceed approved thresholds or threaten the safe and secure operation of an AI system.

Escalation may be required when:

- A critical vulnerability is discovered.
- An agent can perform unauthorized privileged actions.
- Sensitive data is exposed through a credible attack path.
- A mandatory security control is absent.
- A remediation deadline is missed.
- A previously accepted risk materially worsens.
- A provider discloses a significant security incident.
- A security assessment identifies an unacceptable deployment condition.
- A control failure affects multiple systems.

The escalation process should identify the accountable recipient, required response time, interim safeguards, decision authority, and documentation requirements.

For active exploitation or imminent material harm, the organization should use its incident response and emergency decision processes rather than waiting for a routine governance meeting.

**Required evidence:** Escalation procedure, incident or finding records, notifications, decisions, and tracked actions.

### 86. Remediation Prioritization and Resource Allocation

Security remediation should be prioritized according to risk rather than administrative convenience or the order in which findings were reported.

Prioritization should consider:

- Severity and exploitability.
- Exposure to external or untrusted inputs.
- Privilege level of affected components.
- Sensitivity of accessible information.
- Potential business disruption.
- Availability of compensating controls.
- Remediation complexity.
- Dependency on other projects.
- Regulatory or contractual deadlines.
- The possibility of restricting or disabling the affected capability.

The organization should assign accountable owners and realistic completion dates.

Where remediation cannot be completed promptly, the system owner should evaluate whether to reduce functionality, restrict access, disable a tool, limit data exposure, or suspend the system until the weakness is addressed.

Resource constraints should be documented, but they should not automatically justify continued operation outside approved risk tolerance.

**Required evidence:** Prioritized remediation plan, resource commitments, interim safeguards, deadlines, and escalation records.

### 87. Remediation Dependencies and Cross-System Risk

Some security weaknesses cannot be resolved by a single system owner because they depend on shared infrastructure, identity platforms, common AI services, or organization-wide controls.

The governance process should identify these dependencies and assign responsibility for coordinating remediation.

Examples include:

- A shared model gateway with weak authorization.
- A common retrieval service that fails to enforce document permissions.
- A centralized secrets-management deficiency.
- An organization-wide logging gap.
- A shared agent framework with unsafe default tool permissions.
- A common model registry with insufficient integrity protection.

The organization should identify which systems inherit exposure from the shared component and determine whether temporary restrictions are necessary.

Remediation should address the root cause rather than repeatedly closing individual findings while leaving the shared weakness unresolved.

**Required evidence:** Dependency mapping, common-control findings, accountable remediation owner, affected-system list, and root-cause verification.

### 88. Shared AI Platforms and Inherited Security Controls

Organizations often provide common AI platforms, gateways, retrieval services, model hosting, or agent orchestration frameworks for multiple business units.

The security governance model should define which controls are provided centrally and which remain the responsibility of individual system owners.

A shared platform may provide centralized authentication, network controls, logging, and model access restrictions. However, an individual application may still be responsible for its data permissions, business authorization, output validation, and use-case-specific safeguards.

The organization should document inherited controls and validate that they are appropriate for each consuming system.

A control should not be marked effective solely because a shared platform advertises the capability. The assessment should verify the control's configuration, applicability, and effectiveness in the assessed deployment.

**Required evidence:** Shared responsibility model, inherited-control mapping, platform assurance evidence, and system-specific validation.

### 89. Third-Party Provider Accountability

The organization should establish clear accountability for security risks involving external AI providers.

Outsourcing model hosting or inference does not remove the organization's responsibility to assess the security of its own use case, integration, data flows, and operational decisions.

Governance should identify:

- Which controls the provider operates.
- Which controls the organization operates.
- Which controls require shared implementation.
- What evidence is available.
- Which risks cannot be independently verified.
- How material provider changes are communicated.
- How incidents are reported and coordinated.
- How the organization can restrict or terminate the service.

Supplier assurance should be evaluated against the actual service and contract rather than generalized across every product offered by the same provider.

Where material risks depend on provider-controlled mechanisms, the organization should document the assurance gap and determine whether the remaining exposure is acceptable.

**Required evidence:** Shared responsibility matrix, provider assurance records, contractual requirements, incident coordination procedures, and risk decisions.

### 90. Model and Provider Change Governance

Changes to a model, AI provider, model configuration, or service capability may invalidate prior security assumptions.

The organization should establish governance requirements for identifying, evaluating, and approving such changes.

Material changes may include:

- Switching model providers.
- Changing model versions.
- Enabling new model capabilities.
- Changing data retention or processing terms.
- Adding multimodal inputs.
- Expanding tool-use functionality.
- Modifying model hosting arrangements.
- Changing model access permissions.
- Altering safety or security controls.
- Changing a provider's subprocessors or critical dependencies.

The organization should determine whether the change requires targeted testing, a full reassessment, additional supplier review, or renewed deployment authorization.

Provider updates that occur outside the organization's direct release process should be managed through available change-notification mechanisms, contractual arrangements, monitoring, and contingency planning.

**Required evidence:** Change-impact analysis, provider notification records, regression tests, updated risk assessment, and approval decision.

### 91. Agentic AI and Delegated Authority Governance

AI agents introduce governance challenges because they may plan actions, invoke tools, access information, and interact with external systems with limited human intervention.

The organization should define the boundaries of delegated authority before an agent is deployed.

Governance requirements should establish:

- Permitted tasks.
- Prohibited actions.
- Authorized tools.
- Accessible data.
- Maximum privileges.
- Transaction or resource limits.
- Approval requirements.
- Conditions requiring human intervention.
- Stop and suspension mechanisms.
- Monitoring and accountability requirements.

Delegated authority should be limited to the approved business purpose.

An agent should not be permitted to expand its own authority simply because a model-generated plan identifies additional permissions as useful.

The organization should also evaluate whether the agent can delegate work to other agents or services, and whether the original security restrictions remain effective across those delegation paths.

**Required evidence:** Agent authorization policy, capability inventory, delegation model, tool permissions, and action-boundary tests.

### 92. Human Oversight and Security Decision Governance

Human oversight should be designed around decisions that require accountability, contextual judgment, or intervention beyond the system's authorized operating boundaries.

The governance model should identify:

- Which actions require human approval.
- Who is authorized to approve them.
- What information the reviewer must receive.
- Which actions are prohibited regardless of approval.
- When the system must pause or escalate.
- How overrides are recorded.
- How emergency suspension is initiated.
- How reviewer availability and response times are managed.

Oversight should not be treated as an effective safeguard merely because a human is nominally included in the workflow.

The reviewer must have sufficient information, authority, competence, and practical opportunity to evaluate the proposed action.

The organization should also prevent approval fatigue and ensure that reviewers can reject or modify an action without being pressured to accept the model's recommendation.

**Required evidence:** Human oversight policy, approval criteria, workflow tests, reviewer training records, and override logs.

### 93. Governance of Security Risks Affecting Individuals

AI systems may create security consequences that extend beyond traditional infrastructure or data loss.

For example, unauthorized access or manipulation of an AI system may lead to disclosure of personal information, incorrect consequential decisions, or misuse of automated capabilities.

The security assessment should coordinate with relevant privacy, safety, legal, and AI impact assessment processes when a security threat could affect individuals.

The governance process should consider:

- Exposure of personal or confidential information.
- Unauthorized alteration of records.
- Manipulation of decision-support outputs.
- Abuse of automated workflows.
- Risks to vulnerable or affected populations.
- Availability of correction and recovery mechanisms.
- Escalation where security incidents create broader harm.

This coordination should not collapse different assessment disciplines into a single score. Security risk, privacy risk, safety risk, and broader impact risk should retain their respective methodologies while sharing relevant evidence.

**Required evidence:** Cross-assessment references, stakeholder consultation records, relevant risk entries, and documented treatment decisions.

### 94. Privacy and Data Protection Coordination

AI Security Assessment governance should define how security findings are coordinated with privacy and data protection functions.

Security safeguards may support privacy objectives, but the existence of security controls does not establish that personal data processing is lawful or otherwise compliant.

Coordination should address:

- Access to personal data.
- Unauthorized disclosure.
- Data minimization.
- Logging and monitoring of personal information.
- Retention and deletion.
- Provider data processing.
- Data-subject rights implications.
- Cross-border data flows where relevant.
- Security incident notification and response.
- Reuse of data for model improvement.

Where a security weakness could result in personal data exposure, the organization should ensure that the privacy function receives the information needed to evaluate its implications.

The organization should also avoid collecting excessive personal information in assessment evidence or security logs.

**Required evidence:** Security and privacy review linkage, data-flow records, incident coordination procedures, and documented decisions.

### 95. Regulatory and Contractual Security Obligations

The organization should determine which legal, regulatory, contractual, and internal requirements apply to the assessed AI system.

Applicability may depend on the industry, jurisdiction, intended use, data categories, deployment environment, and contractual relationships.

The assessment should identify relevant obligations concerning areas such as:

- Information security.
- Personal data protection.
- Critical services.
- Financial or sector-specific controls.
- Supplier security.
- Incident reporting.
- Record retention.
- Auditability.
- Access control.
- Business continuity.

The organization should maintain traceability between applicable obligations, internal security requirements, implemented controls, and assessment evidence.

The assessment should not assume that alignment with a voluntary framework automatically establishes legal compliance.

Where the applicability or interpretation of an obligation is uncertain, the organization should document the issue and seek appropriate legal or compliance review.

**Required evidence:** Applicability assessment, obligations register, control mapping, legal or compliance review, and evidence of required approvals.

### 96. Portfolio-Level AI Security Risk Concentration

Individual assessments may appear acceptable while the organization remains exposed to a common or concentrated weakness across many AI systems.

Portfolio governance should identify systemic exposure arising from:

- Common AI providers.
- Shared model gateways.
- Reused agent frameworks.
- Centralized retrieval platforms.
- Common identity services.
- Shared software dependencies.
- Similar configuration weaknesses.
- Concentrated supplier dependencies.
- Repeated assessment deficiencies.
- Commonly accepted security exceptions.

The organization should aggregate findings by technology, business unit, control domain, provider, and risk category.

Portfolio analysis should identify whether a single failure could affect multiple AI systems or business processes.

For example, a weakness in a shared tool-execution framework may expose several agents simultaneously, even if each application has its own individual assessment record.

**Required evidence:** Portfolio risk analysis, common-control mapping, concentration metrics, and systemic remediation plans.

### 97. Emerging Threats and Threat Intelligence Governance

The organization should define how new AI-related attack techniques, vulnerabilities, and provider advisories influence existing assessments.

Relevant information sources may include internal incident data, vulnerability disclosures, supplier notifications, security research, threat intelligence, and established security advisories.

The governance process should determine:

- Which sources are monitored.
- Who evaluates relevance.
- How affected systems are identified.
- What triggers urgent reassessment.
- How interim mitigations are approved.
- How material findings are escalated.
- How lessons are incorporated into the assessment methodology.

Not every newly published attack technique requires a full reassessment of every AI system.

The organization should evaluate applicability according to actual architecture, exposure, capabilities, and available safeguards.

Where the potential consequence is significant and applicability is uncertain, a targeted investigation may be warranted before a definitive risk conclusion is reached.

**Required evidence:** Threat-intelligence procedure, advisory records, applicability decisions, affected-system mapping, and resulting actions.

### 98. Security Incidents, Near Misses, and Lessons Learned

Security incidents and near misses should inform future AI Security Assessments.

The organization should analyze whether an event reveals weaknesses in threat modeling, control design, testing, deployment approval, monitoring, or incident response.

Relevant events may include:

- Unauthorized disclosure through model outputs.
- Prompt injection leading to attempted or successful misuse.
- Unauthorized tool execution.
- Compromise of an AI application dependency.
- Model or dataset integrity violations.
- Excessive API usage or service exhaustion.
- Misconfigured retrieval permissions.
- Unauthorized configuration changes.
- Provider security incidents affecting the organization.

Lessons learned should be translated into actionable improvements, such as new threat scenarios, revised test cases, updated control requirements, additional monitoring, or stronger deployment gates.

Incident findings should be linked to affected systems and the enterprise risk register where appropriate.

**Required evidence:** Incident reports, root-cause analysis, lessons-learned records, updated assessment methodology, and verification of corrective actions.

### 99. Organizational Change and Security Capability Governance

AI security controls depend on people, processes, skills, and organizational arrangements as well as technology.

The organization should evaluate whether significant organizational changes affect the ability to operate and maintain the approved security posture.

Relevant changes may include:

- Transfer of system ownership.
- Changes to security operations responsibilities.
- Outsourcing of AI development or hosting.
- Changes in support coverage.
- Loss of specialist security expertise.
- Changes to incident escalation arrangements.
- Restructuring of approval authority.
- New business units adopting a shared AI platform.

The governance process should confirm that control owners remain assigned, access is adjusted appropriately, and operational procedures remain effective.

A previously approved assessment may no longer be sufficient if the organization can no longer perform required monitoring, incident response, or remediation activities.

**Required evidence:** Ownership-change records, updated responsibility matrix, capability assessment, and operational readiness review.

### 100. Security Assessment Methodology Change Control

The organization should maintain controlled governance over changes to the AI Security Assessment methodology.

Changes may be required because of emerging attack techniques, regulatory developments, internal incidents, new AI capabilities, or weaknesses discovered in the assessment process.

Methodology changes may affect:

- Assessment tiers.
- Threat taxonomies.
- Risk-rating criteria.
- Mandatory test scenarios.
- Evidence requirements.
- Control mappings.
- Review and approval thresholds.
- Reassessment triggers.
- Reporting metrics.
- Automated workflow rules.

The organization should evaluate whether a methodology change affects assessments already completed.

Where necessary, previously approved systems should be reviewed or reassessed against the revised requirements.

The change process should maintain historical versions so that earlier decisions can be reconstructed using the methodology applicable at the time.

**Required evidence:** Methodology version history, change approval, impact analysis, updated guidance, and records of required reassessments.

### 101. Suspension, Restriction, and Withdrawal Governance

The organization should establish conditions under which an AI system must be restricted, suspended, or withdrawn because of unacceptable security exposure.

Triggers may include:

- Active exploitation.
- Material unauthorized data disclosure.
- Compromise of model or system integrity.
- Unauthorized privileged agent actions.
- Loss of essential security controls.
- A critical vulnerability without effective mitigation.
- Expired authorization for a material risk.
- Provider compromise affecting the service.
- Inability to monitor or respond to material threats.
- Discovery that a key security assumption is invalid.

The suspension procedure should define who may initiate the action, who authorizes restoration, what evidence is required before resumption, and how business continuity is maintained.

For urgent situations, the organization should allow designated security or operational personnel to invoke emergency containment within their authority.

Resumption should require confirmation that the relevant conditions have been addressed or that a valid, authorized decision permits restricted operation.

**Required evidence:** Suspension criteria, emergency authority matrix, containment records, restoration requirements, and resumption approval.

### 102. Board-Level AI Security Reporting

The board or its designated committee should receive information about material AI security exposures that could affect enterprise objectives, obligations, or resilience.

Board-level reporting should emphasize decision-relevant information rather than technical detail alone.

Reporting may include:

- Material AI security risks.
- Significant incidents and near misses.
- Unresolved critical findings.
- Exposure arising from shared platforms.
- Major provider dependencies.
- Exceptions outside approved thresholds.
- Trends in remediation performance.
- Changes in the AI security risk profile.
- Significant resource or capability gaps.
- Decisions requiring board-level attention.

Reports should explain the business consequences, current safeguards, residual exposure, and actions being taken.

The organization should distinguish between a portfolio with many low-severity findings and a portfolio with a small number of potentially catastrophic weaknesses.

**Required evidence:** Board reports, supporting metrics, escalation records, and documented decisions.

### 103. Management-Level AI Security Reporting

Management reporting should support operational decisions and timely remediation.

Unlike board reporting, management reporting should provide enough detail for accountable owners to assign resources, investigate deficiencies, and monitor individual systems.

Reports should cover:

- Assessment status by system and business unit.
- Overdue assessments.
- Findings by severity and age.
- Remediation progress.
- Expired and approaching-expiry exceptions.
- Failed or incomplete security tests.
- Systems awaiting deployment authorization.
- Reassessment triggers.
- Common-control deficiencies.
- Incident-driven corrective actions.

Management should define the cadence of reporting and establish escalation thresholds for overdue actions.

Where reporting reveals repeated weaknesses, management should determine whether the root cause is a single system, a shared platform, insufficient capability, unclear ownership, or ineffective governance.

**Required evidence:** Management dashboards, action trackers, escalation logs, and records of corrective decisions.

### 104. Independent Assurance and Audit Readiness

The organization should maintain sufficient evidence to demonstrate that AI Security Assessments are performed consistently and that resulting security decisions are controlled.

Assurance activities may include internal audits, independent technical reviews, control testing, external assessments, and targeted examinations of high-exposure systems.

Audit readiness should include the ability to reconstruct:

- Why the system required an assessment.
- What scope and methodology were applied.
- Which threats and controls were evaluated.
- What evidence supported the findings.
- How deficiencies were prioritized.
- Which remediation actions were completed.
- How residual risks were accepted.
- Who authorized deployment.
- What restrictions and monitoring requirements apply.
- Whether reassessment triggers were followed.

Evidence should be retained according to the organization's approved retention requirements and protected against unauthorized alteration or disclosure.

Audit readiness does not mean that the assessment must produce a favorable result. It means that the process and decisions are transparent, traceable, and supported by reliable evidence.

**Required evidence:** Assessment workpapers, version history, evidence repository, approval records, and assurance findings.

### 105. Continuous Improvement and Governance Effectiveness

The organization should periodically evaluate whether the AI Security Assessment governance model remains effective as its AI portfolio, threat environment, and operational requirements evolve.

Continuous improvement should consider:

- Security incidents and near misses.
- Independent assurance findings.
- Repeated assessment deficiencies.
- Changes in AI architecture and capabilities.
- Provider and supply-chain developments.
- Emerging attack techniques.
- Remediation performance.
- Quality of assessment evidence.
- Stakeholder feedback.
- Effectiveness of governance decisions.
- Resource and skills requirements.

Improvement actions should have accountable owners, completion dates, and validation criteria.

The organization should distinguish between improving documentation and improving security outcomes. A revised template is useful only if it helps identify threats more accurately, evaluate controls more effectively, or improve the quality of security decisions.

Governance effectiveness should therefore be measured using both process indicators and substantive security outcomes.

**Required evidence:** Governance review, effectiveness metrics, improvement backlog, assigned actions, and validation of completed improvements.

### Part 3 Core Implementation Principle

AI Security Assessment governance should establish clear accountability for system ownership, independent technical challenge, remediation, residual-risk acceptance, deployment authorization, and ongoing oversight.

Governance must connect technical evidence to authorized decisions. It should prevent material security findings from being bypassed through informal approvals, unclear ownership, expired exceptions, or pressure to deploy.

The organization should distinguish between **operational responsibility and independent oversight**, **technical finding severity and business risk acceptance**, **provider assurance and system-specific validation**, **nominal human oversight and effective intervention**, and **assessment completion and continuing authorization**.

**Core Principle:** An AI system should be deployed and operated only within a clearly defined security authorization, supported by credible evidence, accountable risk ownership, enforceable restrictions, and governance mechanisms that can respond when the system's security posture changes.

## Part 4 — Security Architecture, Assessment Implementation, Evidence Engineering, and Operational Integration

### 106. Reference Architecture for the AI Security Assessment Process

The AI Security Assessment process should be supported by a reference architecture that connects governance requirements, technical assessment activities, evidence repositories, risk management, and deployment authorization.

The architecture should ensure that assessment results remain traceable to the actual AI system, its deployed configuration, its security controls, and the decisions made by authorized stakeholders.

A reference architecture should include the following logical components:

- **AI system inventory:** Authoritative records of AI systems, owners, use cases, deployment environments, and lifecycle status.
- **Assessment orchestration:** Workflows for initiating assessments, assigning reviewers, tracking completion, and enforcing approval gates.
- **Threat modeling repository:** Documented attack surfaces, trust boundaries, threat scenarios, and security assumptions.
- **Control catalogue:** Standardized security requirements, test procedures, evidence expectations, and applicability rules.
- **Technical testing integrations:** Connections to vulnerability scanners, application security tools, cloud security platforms, and authorized AI red-team tooling.
- **Evidence repository:** Controlled storage for assessment records, test results, approvals, and remediation evidence.
- **Risk management integration:** Links to risk registers, exceptions, corrective actions, and risk acceptance records.
- **Authorization service:** Enforcement of deployment conditions and required approvals.
- **Monitoring and reporting:** Operational metrics, overdue actions, security findings, and portfolio-level risk indicators.

Reference architecture:

```
                  AI GOVERNANCE
                        |
                        v
              AI SYSTEM INVENTORY
                        |
                        v
             ASSESSMENT ORCHESTRATION
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
     THREAT MODEL   CONTROL REVIEW   TEST PLAN
          |             |             |
          +-------------+-------------+
                        |
                        v
               EVIDENCE COLLECTION
                        |
          +-------------+-------------+
          |             |             |
          v             v             v
       SECURITY      FINDING AND    INDEPENDENT
        TESTING      RISK RECORDS     REVIEW
          |             |             |
          +-------------+-------------+
                        |
                        v
              SECURITY DECISION
                        |
            +-----------+-----------+
            |           |           |
            v           v           v
         APPROVE     CONDITIONAL   REJECT /
                     APPROVAL      RESTRICT

            v
        DEPLOYMENT
            |
            v
       CONTINUOUS MONITORING
            |
            v
       REASSESSMENT TRIGGERS
            |
            +------> ASSESSMENT
```

The architecture should avoid treating the assessment application as the sole source of truth for every underlying security control. For example, vulnerability scanners, identity platforms, cloud security systems, and incident management tools may remain authoritative for their respective operational records.

The assessment repository should maintain reliable references to these sources and preserve the evidence needed to support the final decision.

**Required evidence:** Reference architecture, component inventory, integration specifications, data-flow diagrams, and documented system-of-record ownership.

### 107. Authoritative Assessment System of Record

The organization should designate an authoritative repository for AI Security Assessment records.

The repository may be an AI governance platform, GRC platform, security risk management system, or an integrated enterprise workflow solution.

The selected system should support:

- Unique assessment identifiers.
- Stable AI system identifiers.
- Assessment versioning.
- Control-level status.
- Evidence references.
- Finding and remediation tracking.
- Reviewer assignments.
- Approval history.
- Exception references.
- Deployment decisions.
- Reassessment schedules.
- Record retention and access control.

The organization should define which system is authoritative for each record type.

For example, an assessment platform may hold the assessment conclusion while the vulnerability management system remains authoritative for the lifecycle of individual vulnerabilities.

Duplicated records should be synchronized or linked through stable identifiers. Where data conflicts arise, the organization should have defined reconciliation rules rather than relying on informal manual correction.

The system of record should also support the reconstruction of a decision as it existed at the time it was made.

**Required evidence:** System-of-record designation, data ownership matrix, record identifiers, reconciliation rules, and retention configuration.

### 108. Logical Data Model for AI Security Assessments

The assessment solution should use a logical data model that connects systems, assets, threats, controls, tests, findings, evidence, and decisions.

A practical model includes the following entities:

| Entity             | Purpose                                | Example attributes                                 |
| ------------------ | -------------------------------------- | -------------------------------------------------- |
| AI System          | Identifies the assessed system         | System ID, owner, use case, environment            |
| Assessment         | Records a specific assessment instance | Assessment ID, version, scope, status              |
| Asset              | Identifies a relevant component        | Asset ID, type, classification, owner              |
| Threat Scenario    | Describes a credible attack path       | Threat ID, actor, entry point, consequence         |
| Control            | Defines a security requirement         | Control ID, objective, owner, applicability        |
| Test Case          | Defines a validation procedure         | Test ID, procedure, expected result                |
| Test Result        | Records test execution                 | Result ID, date, outcome, tester                   |
| Finding            | Records an identified weakness         | Finding ID, severity, affected component           |
| Evidence           | Supports a conclusion                  | Evidence ID, source, timestamp, integrity metadata |
| Remediation        | Tracks corrective action               | Action ID, owner, due date, status                 |
| Exception          | Records an approved deviation          | Exception ID, justification, expiry                |
| Risk Decision      | Records acceptance or rejection        | Decision ID, authority, rationale, conditions      |
| Approval           | Records formal authorization           | Approval ID, approver, timestamp, scope            |
| Reassessment Event | Records a trigger for reassessment     | Event ID, trigger type, decision, due date         |

Relationships should preserve traceability. A single finding may relate to multiple threat scenarios, and one control may mitigate several findings. A control may also fail across multiple systems because it depends on a shared service.

The data model should support these relationships without forcing all records into a single flat assessment form.

**Required evidence:** Logical data model, entity definitions, relationship mapping, data dictionary, and validation rules.

### 109. Assessment Metadata and Record Schema

The organization should establish mandatory metadata fields to ensure that assessment records are complete, consistent, and machine-readable.

At minimum, an assessment record should contain:

- Assessment ID.
- AI system ID.
- Assessment version.
- Assessment type.
- Scope and exclusions.
- Assessment tier.
- Business and technical owners.
- Assessor and reviewer.
- Applicable methodology version.
- Start and completion dates.
- Current assessment status.
- Findings summary.
- Residual-risk status.
- Required approvals.
- Deployment decision.
- Review or expiry date.
- Evidence references.

The schema should define permitted values, required fields, data types, and conditional requirements.

For example, an assessment marked as conditionally approved should require documented conditions, accountable owners, due dates where applicable, and a mechanism for tracking compliance.

The schema should also distinguish between a missing value, a value that is not applicable, and a value that is unknown. These states have different governance implications.

**Required evidence:** Approved schema, data dictionary, field validation rules, and sample validated assessment records.

### 110. Security Control Catalogue and Mapping Engine

The organization should maintain a reusable security control catalogue to support consistent assessments across different AI systems.

Each control should have a unique identifier and clearly defined objective, applicability, implementation expectations, testing method, and evidence requirements.

The catalogue should distinguish among:

- Enterprise-wide mandatory controls.
- AI-specific security controls.
- Technology-specific controls.
- Risk-based controls.
- Compensating controls.
- Controls not applicable to a system.
- Controls inherited from shared platforms.

A mapping engine may link controls to recognized frameworks, internal policies, and regulatory obligations where relevant.

Mappings should be treated as relationships rather than proof of equivalence. A control mapped to multiple frameworks may still require additional implementation or evidence to satisfy each framework's specific requirements.

The catalogue should be version-controlled so that assessments retain the control definitions applicable at the time of execution.

**Required evidence:** Control catalogue, control-to-framework mappings, applicability rules, version history, and catalogue governance records.

### 111. Risk Rating and Scoring Architecture

The assessment platform should implement a documented methodology for rating security findings and determining residual risk.

The methodology should consider both technical characteristics and business consequences.

Potential factors include:

- Exploitability.
- Required access or privileges.
- Attack complexity.
- Exposure of the vulnerable component.
- Sensitivity of accessible data.
- Potential operational disruption.
- Scope of affected systems.
- Effectiveness of existing safeguards.
- Detectability and response capability.
- Reversibility of the resulting harm.
- Uncertainty in available evidence.

The organization may use qualitative categories, quantitative models, or a combination of approaches.

A simple risk matrix can support consistency, but it should not replace analysis of the actual attack path. Two findings with identical technical severity may have materially different consequences depending on whether the affected AI system is isolated or can execute privileged actions.

Where numeric scores are used, the organization should document their meaning, limitations, and aggregation rules.

It should avoid combining unrelated risk dimensions into a single number without explaining what that number represents.

**Required evidence:** Approved rating methodology, scoring criteria, calibration examples, aggregation rules, and validation results.

### 112. Assessment Workflow State Machine

The assessment workflow should be implemented as a controlled sequence of states with defined entry criteria, exit criteria, and authorized transitions.

An example workflow is:

```
REGISTERED
    |
    v
SCREENING
    |
    v
SCOPE DEFINED
    |
    v
ASSESSMENT IN PROGRESS
    |
    v
TECHNICAL REVIEW
    |
    v
FINDINGS TRIAGED
    |
    v
REMEDIATION / RISK TREATMENT
    |
    v
INDEPENDENT REVIEW
    |
    v
AUTHORIZATION DECISION
    |
    +------> APPROVED
    |
    +------> CONDITIONALLY APPROVED
    |
    +------> REJECTED / RESTRICTED
```

The workflow should define mandatory gates and prevent unauthorized state transitions.

For example, an assessment should not reach the approved state if mandatory evidence is missing, a required independent review is incomplete, or a non-waivable deployment condition remains unsatisfied.

Conditional approval should be a distinct state with enforceable restrictions rather than a general comment in the assessment record.

The workflow should also support suspension, withdrawal, and reassessment when material changes occur after deployment.

**Required evidence:** Workflow specification, state-transition rules, approval gates, exception logic, and workflow testing results.

### 113. Integration Architecture and Data Exchange

The assessment platform should integrate with relevant enterprise systems while preserving the security and integrity of exchanged information.

Potential integrations include:

- AI inventory and discovery platforms.
- GRC and enterprise risk systems.
- Vulnerability management tools.
- Source-code repositories.
- CI/CD pipelines.
- Cloud security platforms.
- Identity and access management.
- Security information and event management systems.
- Incident management.
- Procurement and vendor risk management.
- Change management.
- Document and evidence repositories.

Integration requirements should specify the data exchanged, system of record, synchronization frequency, failure handling, and access restrictions.

Where data is exchanged automatically, the organization should validate identifiers and data integrity before updating assessment status or triggering a decision.

A failed integration should not silently cause an assessment to appear complete or cause a critical finding to disappear from reporting.

**Required evidence:** Integration catalogue, interface specifications, data-flow diagrams, error-handling procedures, and integration test results.

### 114. API Security for Assessment Integrations

Assessment APIs and connectors should be protected against unauthorized access, manipulation, data leakage, and abuse.

Controls should include, where applicable:

- Strong service authentication.
- Least-privilege authorization.
- Secure transport.
- Input validation.
- Rate limiting.
- Schema validation.
- Credential protection.
- Audit logging.
- Request integrity controls.
- Restricted administrative operations.
- Monitoring of failed or anomalous requests.

The platform should not allow an integrated tool to modify assessment conclusions or approve a deployment unless that integration is explicitly authorized for the relevant operation.

For example, a vulnerability scanner may submit technical findings, but it should not independently accept residual business risk or grant deployment authorization.

The organization should also define how API credentials are rotated and how compromised integrations are revoked.

**Required evidence:** API security specification, integration permissions, authentication tests, audit records, and credential lifecycle procedures.

### 115. Identity, Access Control, and Segregation of Duties

Access to assessment records and functions should be governed by role-based or attribute-based authorization appropriate to the sensitivity of the information.

Relevant roles may include:

- Assessment initiator.
- Business owner.
- Technical owner.
- Security assessor.
- Independent reviewer.
- Remediation owner.
- Risk approver.
- Platform administrator.
- Auditor.

Permissions should distinguish between viewing, editing, submitting, reviewing, approving, and administrating records.

The platform should prevent unauthorized users from changing findings, deleting evidence, modifying risk acceptance records, or altering approval history.

Administrative privileges should be restricted, monitored, and periodically reviewed.

Where a single person must perform multiple roles because of organizational size, the platform should support compensating approvals and enhanced auditability.

**Required evidence:** Role and permission matrix, access review records, privileged activity logs, and segregation-of-duties tests.

### 116. Evidence Repository, Provenance, and Integrity

The organization should maintain an evidence repository that preserves the relationship between assessment conclusions and the information supporting them.

Evidence may include:

- Architecture diagrams.
- Configuration exports.
- Security test results.
- Vulnerability reports.
- Threat models.
- Access-control test records.
- Red-team reports.
- Supplier assurance documents.
- Remediation verification.
- Approval records.
- Monitoring evidence.

Each evidence item should have sufficient metadata to identify its source, creation time, applicable system, relevant assessment version, and integrity status.

The repository should protect evidence against unauthorized modification and deletion. Appropriate measures may include access restrictions, immutable retention capabilities, cryptographic integrity checks, versioning, and audit logging.

Evidence should be reviewed for relevance and currency. A configuration export from a previous deployment may not support a conclusion about the current production environment.

The repository should also distinguish direct test evidence from statements supplied by system owners or third-party providers.

**Required evidence:** Evidence management standard, repository configuration, provenance metadata, integrity controls, and sample traceability tests.

### 117. Versioning and Historical Decision Reconstruction

The assessment solution should preserve historical versions of the assessment methodology, control catalogue, threat model, evidence, findings, and approval decisions.

Versioning should support the reconstruction of the system's assessed security posture at a specific point in time.

The organization should be able to determine:

- Which system version was assessed.
- Which model and provider were in scope.
- Which configuration was evaluated.
- Which control definitions applied.
- Which tests were executed.
- Which findings were open or closed.
- Which exceptions were active.
- Who approved the decision.
- Which conditions governed deployment.

Updates should create traceable changes rather than silently overwriting material historical records.

When an assessment is reopened or revised, the system should preserve the original decision and document why the revised assessment was necessary.

**Required evidence:** Versioning specification, audit trail, historical records, and successful reconstruction test.

### 118. Privacy-by-Design for Assessment Data

Assessment repositories may contain personal data, confidential architecture details, credentials inadvertently captured in logs, vulnerability information, and sensitive supplier documentation.

The assessment platform should therefore implement privacy and data protection controls appropriate to the evidence it stores.

Controls should address:

- Data minimization.
- Purpose limitation.
- Access restrictions.
- Retention periods.
- Secure deletion.
- Sensitive evidence redaction.
- Data-subject information where relevant.
- Provider processing.
- Cross-border transfers where applicable.
- Protection of logs and exports.

The organization should avoid retaining full prompts, model outputs, or production datasets when a smaller, redacted, or synthetic sample is sufficient to demonstrate a security conclusion.

Where assessment evidence must be retained for audit or legal purposes, the retention rationale and access safeguards should be documented.

**Required evidence:** Assessment-data classification, privacy review, retention schedule, redaction rules, and access controls.

### 119. Threat Modeling the Assessment Platform

The assessment platform itself should undergo threat modeling because it may contain sensitive security information and influence production deployment decisions.

Potential threats include:

- Unauthorized modification of findings.
- Forged approvals.
- Deletion or alteration of evidence.
- Privilege escalation.
- Compromise of integration credentials.
- Manipulation of risk scores.
- Unauthorized access to sensitive architecture.
- Suppression of critical findings.
- Abuse of workflow automation.
- Compromise of assessment templates or control definitions.

The threat model should identify trust boundaries between users, the assessment application, integrated tools, evidence storage, and authorization services.

The organization should assess whether an attacker could manipulate the assessment record to create a false appearance of security approval.

Controls should include strong authorization, protected audit trails, separation of duties, integrity verification, and monitoring of sensitive administrative actions.

**Required evidence:** Platform threat model, attack scenarios, security requirements, and validation results.

### 120. Secure Configuration and Platform Hardening

The assessment platform and its supporting infrastructure should be configured according to approved security baselines.

Hardening requirements may cover:

- Administrative interfaces.

- Encryption settings.
- Database access.
- Service accounts.
- API permissions.
- Logging.
- Backup configuration.
- Software dependencies.

Configuration drift should be detected and managed through established change and remediation processes.

**Required evidence:** Hardening baseline, configuration assessment, drift monitoring, remediation records, and provider assurance where relevant.

### 121. Backup and Disaster Recovery for Assessment Records

The organization should protect assessment records and supporting evidence against accidental deletion, corruption, ransomware, and service disruption.

Recovery requirements should reflect the importance of the records to security governance, auditability, and deployment authorization.

The recovery design should address:

- Backup frequency.
- Retention periods.
- Protection of backup credentials.
- Backup encryption.
- Separation of backup administration.
- Recovery of metadata and relationships.
- Recovery of evidence attachments.
- Integrity verification.
- Recovery-time objectives.
- Recovery-point objectives.
- Restoration testing.

Recovery should preserve the traceability of assessment records, findings, exceptions, and approvals.

If the platform becomes unavailable, the organization should have a documented procedure for maintaining critical security decisions without creating an uncontrolled alternative approval process.

**Required evidence:** Backup policy, recovery procedures, restoration test results, and continuity arrangements.

### 122. Retention, Archiving, and Secure Disposal

The organization should define how assessment records are retained, archived, and disposed of.

Retention should account for:

- Internal governance requirements.
- Audit obligations.
- Applicable legal requirements.
- Contractual commitments.
- Incident investigation needs.
- System lifecycle.
- Risk acceptance periods.
- Litigation or investigation holds.

Records should remain accessible for the period required to support governance and assurance, while unnecessary retention should be avoided.

Secure disposal should cover assessment documents, exported reports, evidence attachments, temporary files, and relevant copies held in connected systems.

The organization should ensure that deletion from the primary application does not leave unmanaged copies in integrations, backups, or external repositories.

**Required evidence:** Retention schedule, archive controls, disposal procedure, legal-hold process, and disposal records.

### 123. Workflow Automation and Orchestration

The assessment platform may automate repeatable activities to improve consistency, reduce administrative effort, and enforce governance requirements.

Examples include:

- Creating an assessment when an AI system is registered.
- Selecting assessment templates based on system classification.
- Assigning reviewers according to defined criteria.
- Requesting required evidence.
- Importing technical findings.
- Creating remediation tasks.
- Sending deadline notifications.
- Escalating overdue critical actions.
- Triggering reassessment after material changes.
- Generating management reports.

Automation should be designed so that important decisions remain attributable to authorized people or explicitly approved decision logic.

A workflow should not automatically approve a high-exposure system merely because every form field has been populated.

Automated decisions should be tested, version-controlled, logged, and subject to appropriate change approval.

**Required evidence:** Workflow rules, automation inventory, test cases, execution logs, and change approvals.

### 124. Continuous Monitoring and Reassessment Feedback Loop

The assessment architecture should connect operational monitoring to the reassessment process.

Security telemetry, incident reports, vulnerability disclosures, provider updates, and configuration changes should be evaluated against defined reassessment criteria.

The feedback loop should determine:

- Which event occurred.
- Which systems may be affected.
- Whether the event invalidates existing assumptions.
- Whether immediate containment is required.
- Whether targeted testing is sufficient.
- Whether a full reassessment is necessary.
- Who owns the resulting action.
- Whether deployment authorization remains valid.

Not every alert should automatically trigger a full assessment. The organization should apply documented triage criteria to avoid unnecessary workload while ensuring that material changes receive appropriate attention.

The platform should preserve the link between the triggering event, the reassessment decision, and any resulting change to the system's authorized status.

**Required evidence:** Reassessment trigger catalogue, event-to-system mapping, triage decisions, and completed reassessment records.

### 125. Security Dashboard and Reporting Architecture

The assessment platform should provide reporting that supports operational management, risk oversight, and executive decision-making.

Dashboard design should separate process performance from actual security exposure.

Potential reporting categories include:

| Reporting category | Example indicators                                                    |
| ------------------ | --------------------------------------------------------------------- |
| Coverage           | Percentage of in-scope systems with current assessments               |
| Readiness          | Percentage of required assessments completed before deployment        |
| Findings           | Open critical and high-severity findings                              |
| Remediation        | Overdue actions and remediation age                                   |
| Authorization      | Systems approved, conditionally approved, restricted, or rejected     |
| Exceptions         | Active exceptions, approaching expirations, and overdue reviews       |
| Testing            | Required security tests completed and failed                          |
| Governance         | Independent reviews outstanding and material risks awaiting decisions |
| Change management  | Material changes awaiting security reassessment                       |
| Portfolio exposure | Common-control weaknesses and shared-provider dependencies            |

Each metric should have a clear definition, data source, owner, calculation method, and reporting cadence.

Dashboards should provide drill-down capability so that management can move from aggregate indicators to affected systems and accountable owners.

**Required evidence:** Metric catalogue, dashboard specifications, data-quality checks, and reporting access controls.

### 126. Assessment Platform Quality Assurance and Testing

The assessment solution should be tested to ensure that its workflows, controls, integrations, and records behave as intended.

Testing should cover:

- Mandatory field validation.
- Workflow state transitions.
- Role-based permissions.
- Approval enforcement.
- Evidence attachment and retrieval.
- Finding creation and closure.
- Exception expiry.
- Integration failure handling.
- Historical version reconstruction.
- Dashboard calculation accuracy.
- Reassessment trigger execution.
- Backup and recovery.
- Audit logging.

Negative tests are particularly important.

For example, the organization should attempt to determine whether an unauthorized user can approve an assessment, whether a system can be marked approved with a mandatory critical finding unresolved, or whether an integration error can suppress a finding.

Defects affecting authorization, evidence integrity, or security decision accuracy should be treated according to their materiality.

**Required evidence:** Test plan, test cases, execution results, defect register, and release approval.

### 127. DevSecOps and Change Management for the Assessment Platform

Changes to the assessment platform, control catalogue, automation rules, and integrations should be managed through a controlled development and release process.

Controls should include:

- Version-controlled configuration.
- Peer review.
- Security testing.
- Dependency management.
- Segregation of development and production.
- Approval of material changes.
- Release records.
- Rollback procedures.
- Monitoring after deployment.

Changes to assessment logic deserve particular attention because they may affect multiple systems and decisions.

For example, an incorrect rule that treats a missing control result as a pass could produce widespread false approvals.

The organization should evaluate the potential governance impact of platform changes and determine whether historical assessments require review.

**Required evidence:** Change records, code or configuration review, test results, release approvals, and rollback documentation.

### 128. Scalability, Resilience, and Performance

The assessment platform should support the expected size and complexity of the organization's AI portfolio.

Capacity planning should consider:

- Number of AI systems.
- Assessment frequency.
- Number of control records.
- Evidence volume.
- Integration traffic.
- Concurrent users.
- Automated workflow volume.
- Reporting requirements.
- Retention and archive growth.

The platform should remain reliable during periods of increased activity, such as a large AI deployment program, an incident-driven reassessment campaign, or a new mandatory security review.

Performance degradation should not cause assessment records to be lost, approvals to become inconsistent, or critical alerts to go unnoticed.

The organization should also evaluate the resilience of dependencies such as identity providers, databases, evidence storage, and integration services.

**Required evidence:** Capacity model, resilience design, performance tests, monitoring thresholds, and continuity arrangements.

### 129. Cost, Resource, and Operating Model

The organization should define the resources required to operate the AI Security Assessment process effectively.

Costs may include:

- Assessment platform licensing.
- Security testing tools.
- Cloud infrastructure.
- Evidence storage.
- Specialist security assessors.
- AI red-team services.
- Independent reviews.
- Integration development.
- Training and methodology maintenance.
- Continuous monitoring.
- Remediation activities.

The operating model should identify which activities are performed centrally, which are delegated to business units, and which require external specialists.

The organization should also estimate assessment demand based on portfolio size, risk tiers, deployment frequency, and reassessment triggers.

A process that requires more specialist effort than the organization can sustain may result in backlogs, superficial reviews, or delayed remediation. Resource planning should therefore support both assessment quality and operational feasibility.

**Required evidence:** Operating model, resource plan, cost assumptions, capacity forecast, and service ownership assignments.

### 131. Key Performance Indicators and Key Risk Indicators

The organization should define indicators that measure assessment efficiency, control effectiveness, and unresolved security exposure.

Examples include:

**Key Performance Indicators (KPIs)**

- Percentage of assessments completed within target timeframes.
- Percentage of required assessments completed before deployment.
- Median time from finding identification to remediation.
- Percentage of remediation actions verified by retesting.
- Percentage of assessments with complete mandatory evidence.

**Key Risk Indicators (KRIs)**

- Number of unresolved critical findings.
- Number of high-exposure systems operating under expired exceptions.
- Percentage of deployed systems with overdue reassessments.
- Number of systems with unverified privileged tool access.
- Number of systems affected by a common-control weakness.
- Number of material provider changes not assessed within the required period.
- Number of systems operating without required monitoring.

The organization should avoid targets that encourage undesirable behavior, such as reducing reported findings rather than reducing actual exposure.

Indicators should be interpreted in context. An increase in reported findings may reflect improved testing coverage rather than deteriorating security.

**Required evidence:** KPI/KRI definitions, thresholds, ownership, data sources, and documented management responses.

### 132. Architecture Review Checklist

Before accepting the assessment platform or its integration architecture, the organization should confirm that the following design requirements have been addressed.

- Each AI system has a stable identifier and accountable owner.
- Assessment records are linked to the authoritative inventory.
- Threat scenarios and security controls are traceable.
- Control definitions are version-controlled.
- Mandatory assessment gates are enforced.
- Risk acceptance is restricted to authorized roles.
- Evidence is protected against unauthorized modification.
- Findings are linked to remediation and verification records.
- Shared controls and inherited dependencies are documented.
- Integration identities follow least-privilege principles.
- API integrations are authenticated and monitored.
- Assessment history can be reconstructed.
- Reassessment triggers are defined and tested.
- Dashboards distinguish process metrics from actual risk.
- Backup, recovery, retention, and disposal are addressed.
- Platform security has been independently reviewed where required.
- Operational ownership and support arrangements are documented.

The checklist should include an explicit disposition for each item: satisfied, partially satisfied, not satisfied, or not applicable. Material deficiencies should be linked to findings and tracked through the established risk process.

**Required evidence:** Completed architecture checklist, review comments, deficiency records, and approval decision.

### 133. Control Acceptance Testing

The organization should define how it determines whether a security control has been implemented correctly and operates effectively.

Control acceptance testing should specify:

- The control objective.
- The applicable system or component.
- The expected behavior.
- The test procedure.
- The required evidence.
- The acceptance criteria.
- The tester and reviewer.
- The result.
- Any limitations.
- The required remediation or follow-up.

For example, a least-privilege requirement for an AI agent should not be accepted merely because its permissions are documented. Testing should verify that unauthorized actions are actually rejected by the execution layer.

Similarly, a logging requirement should be validated by generating representative security events and confirming that they are recorded, protected, and available to authorized investigators.

Control acceptance criteria should be established before testing where practical to reduce inconsistent interpretation of results.

**Required evidence:** Control test specifications, execution records, acceptance criteria, and independently verified results where required.

### 134. Limitations, Exceptions, and Technical Debt Register

The assessment process should maintain a structured record of limitations that affect confidence in the security conclusion.

These may include:

- Incomplete architecture visibility.
- Restricted access to provider-controlled components.
- Unavailable model internals.
- Incomplete test coverage.
- Unverified security assumptions.
- Temporary control deficiencies.
- Unsupported monitoring capabilities.
- Legacy integration constraints.
- Deferred remediation.
- Unavailable evidence.

Each limitation should identify its impact on the assessment, the associated risk, and the action required to address or manage it.

The organization should distinguish between a documented limitation and an approved exception. Recording a limitation does not authorize continued operation where approval is required.

Technical debt should be prioritized according to its effect on the system's security posture, future remediation cost, and potential to create recurring weaknesses.

**Required evidence:** Limitation and technical debt register, risk links, assigned owners, target dates, and exception references where applicable.

### 137. Continuous Improvement and Optimization

The organization should periodically optimize the assessment process using operational data, security findings, incidents, and independent review results.

Improvement opportunities may include:

- Removing redundant assessment questions.
- Improving the quality of threat scenarios.
- Adding tests for emerging AI attack techniques.
- Improving evidence collection.
- Reducing unnecessary manual administration.
- Strengthening deployment gates.
- Improving finding prioritization.
- Increasing consistency across assessors.
- Improving visibility into shared-platform exposure.
- Revising control mappings.
- Improving integration reliability.

Automation should be introduced where it improves consistency or reduces repetitive work without weakening the quality of judgment.

The organization should measure whether improvements reduce meaningful security exposure, increase the reliability of decisions, or improve the timeliness of remediation.

**Required evidence:** Improvement backlog, prioritization rationale, implementation records, and effectiveness measurements.

### 138. Final Acceptance Criteria for the AI Security Assessment Capability

The AI Security Assessment capability should be accepted for operational use only when the organization has demonstrated that the process is repeatable, traceable, enforceable, and supported by accountable owners.

Final acceptance should verify that:

- The assessment methodology is approved.
- Required roles and decision rights are defined.
- The control catalogue and test procedures are available.
- Assessment records can be linked to AI inventory entries.
- Threat scenarios and findings can be traced to evidence.
- Mandatory workflow gates operate correctly.
- Risk acceptance and exceptions require authorized approval.
- Technical findings can be tracked through remediation and retesting.
- Required integrations are functioning.
- Evidence and approval history are protected.
- Reassessment triggers are operational.
- Reporting is sufficiently accurate for management use.
- Backup, retention, and recovery arrangements are documented.
- Operational ownership and support are established.
- Material implementation deficiencies have been addressed or formally managed.

Acceptance should be based on demonstrated results rather than the existence of documents alone.

The organization should record any residual implementation limitations and determine whether they prevent operational use, require restricted use, or can be managed under an approved improvement plan.

**Required evidence:** Final acceptance report, test results, operational readiness review, open-deficiency register, and authorized approval.

### 139. Final Implementation Principle

An effective AI Security Assessment capability combines security methodology, technical validation, governance, evidence management, controlled authorization, and continuous monitoring into a single traceable operating process.

The process should be sufficiently standardized to support consistent decisions across the AI portfolio while remaining adaptable to differences in architecture, deployment model, privileges, data sensitivity, and business consequences.

It should also preserve a clear distinction between an assessment record and an actual security outcome. A completed template, successful workflow, or high control-completion percentage does not independently demonstrate that an AI system is secure.

The organization must be able to show which threats were considered, which safeguards were tested, which weaknesses remain, who accepted any residual risk, and what conditions must remain true for continued operation.

**Core Principle:** The AI Security Assessment Template becomes an enterprise security capability when its requirements are implemented in the architecture, its controls are validated through evidence, its decisions are enforced through governance and workflow, and its conclusions are continuously reassessed as the AI system and threat environment evolve.
