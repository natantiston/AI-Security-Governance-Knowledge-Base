# 20.13 — AI Security Architecture Review Template

## Part 1 — Architecture Review Foundations, Scope, System Context, and Security Requirements

### 1. Introduction to the AI Security Architecture Review Template

An **AI Security Architecture Review** is a structured assessment of an AI system's architecture, trust boundaries, data flows, security controls, dependencies, and operational design to determine whether the system can be deployed and operated within the organization's security and risk requirements.

The review examines how the AI system is constructed, how it interacts with users and enterprise systems, how data moves through the environment, and how security controls protect the system against misuse, unauthorized access, data exposure, manipulation, and operational compromise.

Unlike a conventional application security review, an AI security architecture review must account for risks introduced by model behavior, training or retrieval data, prompts, model-serving infrastructure, external model providers, retrieval-augmented generation (RAG), AI tools, and autonomous or semi-autonomous execution.

The review should be tailored to the architecture being assessed. A traditional machine-learning prediction service, a generative AI assistant, a RAG-based enterprise knowledge assistant, and an agentic AI system do not have identical attack surfaces or control requirements.

#### 1.1 Objectives of an AI security architecture review

The review should establish whether:

- The AI system's intended purpose, capabilities, and security boundaries are clearly defined.
- The architecture provides appropriate authentication, authorization, and access control.
- Sensitive data is protected throughout collection, processing, storage, retrieval, transmission, and disposal.
- Model inputs, outputs, and interactions with external systems are subject to appropriate security controls.
- The system's trust boundaries and attack surfaces are identified.
- The architecture addresses relevant AI-specific threats, including prompt injection, insecure output handling, data leakage, model abuse, and unsafe tool execution.
- Third-party models, AI services, datasets, libraries, and infrastructure dependencies are assessed.
- Logging, monitoring, incident response, and operational recovery capabilities are adequate.
- Residual risks are documented and assigned to authorized risk owners.
- The system meets applicable internal security requirements and relevant legal, regulatory, contractual, and industry obligations.

The review is not intended to prove that an AI system is completely secure. Its purpose is to identify architectural weaknesses, evaluate the adequacy of proposed controls, and determine whether the remaining risks are acceptable under the organization's governance framework.

#### 1.2 Architecture review versus other AI assessments

Several assessment activities contribute to AI security governance, but they serve different purposes.

| Assessment Type | Primary Focus | Typical Questions | Main Deliverable |
|---|---|---|---|
| AI Use-Case Assessment | Business purpose and appropriateness | Is the proposed AI use case justified and permitted? | Use-case assessment |
| AI Risk Assessment | Overall risk exposure | What risks could arise, and how should they be treated? | AI risk assessment and risk register |
| AI Security Architecture Review | Technical design and security controls | Does the architecture adequately protect the AI system and its dependencies? | Architecture review report |
| AI Model Risk Assessment | Model behavior and model-specific risks | Could model limitations, drift, bias, or unreliable outputs create unacceptable exposure? | Model risk assessment |
| LLM Security Assessment | Large language model-specific threats | Can prompts, retrieved content, or outputs compromise the application? | LLM security assessment |
| AI Vendor Assessment | Third-party provider risks | Can the supplier meet the organization's security, privacy, resilience, and contractual requirements? | Vendor assessment |
| AI Impact Assessment | Potential effects on people, groups, and society | Could the system produce significant adverse impacts on affected parties? | AI impact assessment |
| AI Penetration Test | Exploitable weaknesses under defined test conditions | Can an attacker exploit identified attack paths? | Penetration test report |
| AI Compliance Assessment | Conformity with applicable obligations | Are relevant requirements implemented and evidenced? | Compliance assessment |

These assessments should inform one another. For example, a security architecture review may identify excessive agent permissions, while an AI risk assessment evaluates the resulting business impact and the AI risk register tracks treatment.

A successful architecture review does not replace penetration testing, privacy assessment, legal review, model validation, or formal deployment authorization.

### 2. Scope and Applicability of the Architecture Review

The review must establish precisely what is being assessed. AI systems frequently span multiple services, providers, business applications, infrastructure environments, and organizational boundaries.

A narrowly defined review may overlook important dependencies. Conversely, an unnecessarily broad scope can make the assessment difficult to complete and obscure the most material risks.

The reviewer should therefore document the system boundary, connected components, relevant external dependencies, and exclusions before evaluating controls.

#### 2.1 Components that may fall within scope

Depending on the system design, the review may include:

| Architecture Component | Examples | Security Review Focus |
|---|---|---|
| User interface | Web application, mobile application, employee portal | Authentication, session security, input validation |
| Application layer | API gateway, backend services, orchestration service | Authorization, secure processing, API protection |
| AI model | Hosted LLM, self-hosted LLM, classification model | Model access, configuration, abuse resistance |
| Model-serving infrastructure | Inference server, GPU cluster, model endpoint | Isolation, administrative access, network exposure |
| Prompt management | System prompts, templates, prompt configuration | Integrity, access control, change governance |
| Retrieval layer | Vector database, search engine, RAG service | Document authorization, retrieval isolation, injection risks |
| Data sources | CRM, ERP, knowledge repositories, data lakes | Data classification, permissions, provenance |
| Agent framework | Planning engine, tool router, workflow orchestrator | Tool permissions, action authorization, execution limits |
| Enterprise tools | Salesforce APIs, ticketing systems, email, databases | Least privilege, transaction controls, auditability |
| Identity services | Identity provider, IAM, service identities | Authentication, role assignment, credential protection |
| External AI services | Model APIs, hosted embedding services | Data disclosure, supplier controls, endpoint security |
| Logging and monitoring | SIEM, application logs, model telemetry | Detection, evidence integrity, sensitive-data minimization |
| Security infrastructure | WAF, network controls, secrets management, EDR | Threat prevention, containment, credential protection |
| Deployment pipeline | CI/CD, model registry, artifact repository | Artifact integrity, approvals, supply-chain security |
| Human oversight | Review console, escalation workflow | Decision authority, override capability, traceability |

The review should distinguish between components controlled directly by the organization and those operated by a third party.

This distinction affects which controls can be implemented internally, which must be verified through supplier evidence, and which risks must be addressed contractually or through compensating measures.

#### 2.2 In-scope and out-of-scope documentation

The reviewer should record the following before beginning the assessment:

| Scope Element | Required Information |
|---|---|
| System name | Official name of the AI application or service |
| System identifier | Unique inventory or architecture reference |
| Business owner | Accountable business representative |
| Technical owner | Person responsible for technical operation |
| Intended purpose | Business objective and authorized use |
| User population | Employees, customers, suppliers, or other users |
| Deployment environment | Cloud, on-premises, hybrid, or third-party SaaS |
| AI capability | Predictive ML, generative AI, RAG, agentic AI, or another approach |
| Model dependencies | Model provider, model version, endpoint, or deployed artifact |
| Data categories | Personal, confidential, financial, regulated, public, or other data |
| Connected systems | Applications, databases, APIs, identity services, and infrastructure |
| External dependencies | Suppliers, APIs, hosted models, and other third-party services |
| Review boundaries | Components and interfaces explicitly included |
| Exclusions | Components not assessed and the rationale |
| Assumptions | Conditions assumed to be true during the review |
| Known limitations | Missing documentation, unavailable evidence, or untested components |
| Review date | Date of assessment and relevant architecture version |

Exclusions must not be interpreted as evidence that an excluded component is secure. Dependencies outside the formal review boundary may still create material risk and should be documented.

#### 2.3 Architecture review triggers

An AI security architecture review should be considered at appropriate lifecycle decision points, including:

- Introduction of a new AI use case.
- Adoption of a new model provider or materially different model.
- Introduction of RAG or new data retrieval capabilities.
- Addition of AI agents or new tool permissions.
- Connection to a sensitive enterprise system.
- Expansion from internal use to customer-facing deployment.
- Introduction of personal, confidential, regulated, or otherwise sensitive data.
- Significant changes to hosting, network exposure, identity, or trust boundaries.
- Material changes to prompts, orchestration, permissions, or execution logic.
- Significant security incidents or newly identified attack paths.
- Major changes to regulatory, contractual, or organizational requirements.

The organization should define mandatory review triggers in its architecture governance and change management processes.

### 3. AI System Architecture Context and Reference Model

An AI security architecture review begins with an accurate understanding of how the system works.

A component list alone is insufficient. The reviewer must understand how users, applications, models, data stores, tools, and external services interact, including which components can initiate actions and which trust boundaries are crossed.

A reference architecture provides a common vocabulary for discussing these interactions.

#### 3.1 Logical architecture layers

A typical enterprise AI application can be represented using the following logical layers.

```text id="a13arch"
+-----------------------------------------------------------+
|                    1. USER EXPERIENCE                     |
| Employees | Customers | Administrators | External Users   |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                    2. ACCESS AND IDENTITY                 |
| SSO | MFA | IAM | RBAC/ABAC | API Authentication          |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                    3. APPLICATION LAYER                   |
| Web/API Services | Business Logic | Input Validation      |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                    4. AI ORCHESTRATION                    |
| Prompt Assembly | Context Management | Routing | Policies  |
+---------------+----------------------+--------------------+
                |                      |
                v                      v
+---------------------------+  +-----------------------------+
| 5. MODEL SERVICES         |  | 6. RETRIEVAL AND DATA       |
| Hosted or Self-Hosted LLM |  | Search | Vector DB | RAG    |
| Inference Endpoints       |  | Documents | Enterprise APIs |
+-------------+-------------+  +---------------+-------------+
              |                                |
              +----------------+---------------+
                               |
                               v
+-----------------------------------------------------------+
|                    7. TOOLS AND ACTIONS                   |
| CRM | ERP | Ticketing | Email | Databases | Workflows     |
+-----------------------------+-----------------------------+
                              |
                              v
+-----------------------------------------------------------+
|                    8. BUSINESS OUTCOMES                   |
| Answers | Recommendations | Records | Approved Actions   |
+-----------------------------------------------------------+

Cross-Cutting Security and Governance:
Identity | Data Protection | Secrets | Network Security
Logging | Monitoring | Testing | Change Control | Incident Response
```

This is a logical model, not a mandatory physical deployment pattern. A particular implementation may combine layers, separate them across services, or omit components that are not applicable.

#### 3.2 Questions the reviewer should answer

**User and access layer**
- Who can use the system?
- How are users authenticated?
- Are administrative and ordinary user privileges separated?
- Can users access AI capabilities beyond their business authorization?

**Application and orchestration layer**
- Where are input validation and policy enforcement performed?
- Can users manipulate system prompts or other privileged configuration?
- Does the orchestration layer enforce authorization independently of model-generated instructions?
- Can an error in one component expose sensitive context to another?

**Model layer**
- Is the model hosted internally or by an external provider?
- What data is transmitted to the model?
- Which model versions and configurations are permitted?
- How are model updates, endpoint changes, and provider changes controlled?

**Retrieval and data layer**
- Are retrieval permissions aligned with the user's authorization?
- Can the system retrieve information across tenants, departments, or customer accounts?
- Are documents and embeddings protected against unauthorized modification?
- Can retrieved content contain instructions designed to manipulate the model?

**Tools and action layer**
- Which actions can the AI system perform?
- Are tool permissions limited to the minimum required?
- Are high-impact actions independently authorized?
- Can the model initiate irreversible transactions without confirmation?

**Operational layer**
- Are material AI interactions logged appropriately?
- Can security teams detect abuse or unauthorized activity?
- Is there a defined process to disable model access or revoke tool permissions?
- Can the system recover safely from a compromise?

The architecture review should produce a coherent account of these interactions before concluding that individual controls are adequate.

### 4. Establishing Trust Boundaries and Security Zones

A **trust boundary** is a point where information or control passes between components with different security assumptions, ownership, privilege levels, or exposure to threats.

AI systems often contain more trust boundaries than conventional applications because model services, retrieved content, user instructions, external tools, and generated outputs may originate from sources with different levels of trust.

The reviewer must identify these boundaries and determine which controls protect each transition.

#### 4.1 Common trust boundaries

| Boundary | Example | Primary Security Concern |
|---|---|---|
| External user to application | Customer submits a question to an AI chatbot | Malicious input, authentication bypass |
| User to orchestration service | Employee submits prompts to an internal assistant | Unauthorized access, prompt manipulation |
| Application to model provider | Backend sends context to an external LLM API | Data disclosure, endpoint security |
| Retrieval service to document repository | RAG service searches enterprise content | Permission leakage, unauthorized retrieval |
| Retrieved content to model context | Documents are inserted into a prompt | Indirect prompt injection, untrusted instructions |
| Model to tool router | Model requests a CRM or database operation | Unauthorized actions, unsafe tool selection |
| Tool router to enterprise API | Agent executes a transaction | Excessive privilege, transaction abuse |
| Tenant to tenant | Shared service processes data for multiple customers | Cross-tenant access and data leakage |
| Development to production | Model configuration or artifacts are promoted | Supply-chain compromise, unauthorized changes |
| Organization to supplier | Hosted AI service processes enterprise data | Supplier risk, contractual and operational dependency |
| Administrator to production environment | Engineer changes model or agent configuration | Privileged misuse, configuration tampering |

Each boundary should have a documented security purpose and a corresponding set of controls.

#### 4.2 Trust-boundary review questions

For each boundary, ask:

1. What information or authority crosses the boundary?
2. Which component initiates the interaction?
3. Which component receives and processes the request?
4. Is the sender authenticated?
5. Is the requested operation authorized independently of the AI model's decision?
6. Is the data validated and classified?
7. Can instructions or data from a lower-trust source influence a higher-trust component?
8. Are credentials or secrets exposed across the boundary?
9. Are interactions logged and monitored?
10. What happens if the receiving component is compromised or behaves unexpectedly?

#### 4.3 Example: Trust-boundary failure in an AI agent

Suppose an enterprise AI agent can retrieve a customer's account information and use a CRM API to update account records.

A user submits a request that causes the model to generate a tool call. If the tool router accepts the model-generated action without checking the user's authorization, the model may become an unintended route around the application's access controls.

The architectural weakness is not simply that the model generated an unsafe response. The system allowed an untrusted model output to influence a privileged operation without an independent authorization decision.

Appropriate controls may include:

- Explicit allowlisting of permitted tools and operations.
- Server-side authorization checks for each requested action.
- Binding tool permissions to the authenticated user and approved workflow.
- Restricting service identities to the minimum necessary permissions.
- Human confirmation for designated high-impact actions.
- Validation of tool arguments and target resources.
- Rate limits and transaction limits.
- Logging of the requesting user, selected tool, parameters, authorization result, and outcome.
- A mechanism to revoke agent permissions or disable affected tools.

The reviewer should verify that these controls are implemented at enforceable system boundaries rather than relying solely on instructions in the system prompt.

### 5. AI Security Threat Modeling and Attack-Surface Identification

Threat modeling is the systematic process of identifying how a system could be attacked or misused, what assets may be affected, which weaknesses create exposure, and what controls can reduce the resulting risk.

For AI architecture reviews, threat modeling must consider conventional application threats alongside threats arising from AI-specific behavior and integrations.

A useful threat model connects each threat to a specific asset, entry point, trust boundary, attack path, business impact, and mitigation.

#### 5.1 AI attack-surface categories

| Category | Example Attack Surface | Example Threat |
|---|---|---|
| User inputs | Prompts, uploaded files, API requests | Prompt injection or malicious content |
| Model interface | Inference endpoint, model API | Unauthorized model access or service abuse |
| System prompts | Prompt templates and privileged instructions | Prompt disclosure or unauthorized modification |
| Retrieval system | Vector database, search index, document store | Cross-user data leakage or indirect prompt injection |
| Training and fine-tuning | Training pipeline, datasets, model artifacts | Data poisoning or compromised artifacts |
| Tool integration | Tool router, plugins, external APIs | Unauthorized action execution |
| Identity and secrets | Service identities, API keys, tokens | Credential theft or privilege escalation |
| Application output | Generated HTML, SQL, commands, or workflow parameters | Unsafe output handling or injection |
| Model supply chain | External models, libraries, containers | Malicious or vulnerable dependencies |
| Infrastructure | Cloud workloads, containers, network services | Runtime compromise or unauthorized exposure |
| Monitoring and logs | Prompts, outputs, traces, telemetry | Sensitive-data leakage or detection gaps |
| Human workflows | Review queues, approval interfaces | Automation bias or approval bypass |
| Availability and cost | Inference endpoints and expensive tool calls | Resource exhaustion or economic abuse |
| Multi-tenant architecture | Shared models, storage, or orchestration | Tenant isolation failure |

Not every threat category applies to every system. The reviewer should document applicability and justify material exclusions.

#### 5.2 Threat-modeling workflow

```text id="a13threat"
1. Define System Purpose and Boundaries
                 |
                 v
2. Identify Assets and Security Objectives
                 |
                 v
3. Map Components, Data Flows, and Trust Boundaries
                 |
                 v
4. Identify Threat Actors and Attack Surfaces
                 |
                 v
5. Develop Plausible Threat Scenarios
                 |
                 v
6. Evaluate Existing and Proposed Controls
                 |
                 v
7. Assess Likelihood, Impact, and Residual Risk
                 |
                 v
8. Define Mitigations and Accountable Owners
                 |
                 v
9. Validate Controls Through Testing and Evidence
                 |
                 v
10. Record Findings and Obtain Required Decisions
```

#### 5.3 Threat scenario template

Each material threat scenario should capture:

| Field | Description |
|---|---|
| Threat ID | Unique reference |
| Threat Name | Short descriptive title |
| Threat Actor | External attacker, malicious insider, compromised supplier, or other actor |
| Asset at Risk | Data, model, credential, service, transaction, or business process |
| Entry Point | Prompt, API, uploaded document, tool, endpoint, or other interface |
| Trust Boundary | Boundary crossed during the attack |
| Preconditions | Required access, configuration, or environmental conditions |
| Attack Path | Sequence of actions that could produce the threat |
| Vulnerability or Weakness | Architectural or control weakness |
| Threat Event | What the attacker or system could cause |
| Potential Impact | Confidentiality, integrity, availability, safety, compliance, or business consequences |
| Existing Controls | Safeguards currently implemented |
| Control Gaps | Missing or insufficient safeguards |
| Recommended Mitigations | Proposed preventive, detective, or corrective measures |
| Residual Risk | Remaining risk after proposed treatment |
| Owner | Person accountable for treatment |
| Validation Method | Inspection, testing, simulation, or other verification |
| Status | Open, in treatment, accepted, closed, or another defined state |

The threat model should remain a living artifact. Material architecture changes, new tool integrations, new data sources, and significant incidents should trigger review when they alter the system's threat profile.

### 6. Security Requirements for AI Architecture

Security requirements define the outcomes the architecture must achieve. They should be specific enough to guide design, implementation, testing, and assurance.

Requirements should be derived from the organization's security policies, data classification rules, threat model, risk assessment, contractual commitments, and applicable legal or regulatory obligations.

The reviewer should avoid treating a general statement such as "the AI system must be secure" as an actionable requirement.

#### 6.1 Core security requirement domains

| Domain | Example Requirement |
|---|---|
| Identity and authentication | Access to the AI service must be authenticated through approved identity mechanisms. |
| Authorization | Every access to protected resources must be authorized independently of model-generated instructions. |
| Least privilege | AI components and service identities must receive only the permissions necessary for their approved functions. |
| Data protection | Sensitive data must be protected in transit and at rest according to organizational requirements. |
| Data minimization | Only data necessary for the approved purpose should be transmitted to model services or retrieval components. |
| Tenant isolation | Data and operations must remain isolated according to tenant boundaries and authorization requirements. |
| Prompt and configuration integrity | Privileged prompts and security-relevant configurations must be protected against unauthorized modification. |
| Input handling | User inputs and retrieved content must be handled according to their trust level and the application's threat model. |
| Output handling | Model-generated content must be validated before it is used in executable contexts or consequential business actions. |
| Tool execution | Tool calls must be restricted, validated, authorized, and logged according to their potential impact. |
| Secrets management | API keys, tokens, and credentials must be stored and accessed through approved secrets-management mechanisms. |
| Network security | Model endpoints, data stores, and tools must have appropriate network exposure restrictions. |
| Logging and monitoring | Security-relevant events must be recorded and monitored with appropriate privacy and retention controls. |
| Resilience | The architecture must address service failure, rate limiting, recovery, and relevant availability risks. |
| Supply-chain security | Model artifacts, dependencies, images, and external services must be subject to appropriate integrity and supplier controls. |
| Change management | Material changes to models, prompts, permissions, and architecture must follow defined approval and validation processes. |
| Incident response | The organization must be able to investigate, contain, and recover from relevant AI security incidents. |
| Human oversight | High-impact decisions or actions must include the human review or authorization required by the system's risk classification. |
| Data retention and deletion | Data, logs, prompts, embeddings, and other artifacts must follow applicable retention and deletion requirements. |
| Secure decommissioning | AI services, credentials, integrations, and retained artifacts must be managed when the system is retired. |

These are example requirement statements. The organization should adapt them to the system's capabilities and define measurable acceptance criteria.

#### 6.2 Turning requirements into verifiable controls

Each requirement should be associated with:

- A unique requirement identifier.
- The security objective.
- The relevant architectural component.
- The control owner.
- The implementation method.
- The evidence required.
- The verification method.
- The acceptance criteria.
- The applicable risk or threat scenario.
- The status and any approved exception.

For example:

| Field | Example |
|---|---|
| Requirement ID | AISAR-REQ-001 |
| Security Objective | Prevent unauthorized access to customer records |
| Requirement | The AI service must enforce server-side authorization for every customer-record retrieval and action. |
| Component | AI orchestration service and CRM integration |
| Threat Addressed | Cross-customer data access through manipulated prompts or tool calls |
| Control Owner | Application Security Lead and CRM Technical Owner |
| Implementation | Identity-bound authorization checks and least-privilege service permissions |
| Evidence | Architecture diagram, access-control configuration, test results |
| Verification | Negative authorization tests using users with different access rights |
| Acceptance Criteria | Unauthorized record retrieval and modification attempts are denied and logged. |
| Status | To be determined during review |

A requirement should not be marked as implemented merely because a design document mentions it. The reviewer should seek appropriate implementation evidence and validation results.

### 7. AI Security Architecture Review Governance and Responsibilities

The architecture review must have clear ownership, defined decision authority, and appropriate independence between design, assessment, and risk acceptance.

The exact roles will depend on the organization's structure. In a smaller organization, one person may perform multiple functions, but the organization should identify conflicts of interest and ensure that material risks are reviewed by an appropriately authorized party.

#### 7.1 Key roles

| Role | Primary Responsibility |
|---|---|
| Business Owner | Defines the business purpose and remains accountable for the business outcome |
| AI System Owner | Coordinates lifecycle ownership, documentation, and operational responsibilities |
| Enterprise Architect | Evaluates architecture alignment, integration, and design principles |
| AI Security Architect | Leads or contributes to AI-specific security architecture analysis |
| Security Engineering | Evaluates security control implementation and technical feasibility |
| CISO or Security Authority | Establishes security requirements and exercises assigned security decision rights |
| Data Owner | Defines permitted data use, access, and classification requirements |
| Data Protection Officer or Privacy Function | Advises on privacy obligations and relevant assessment requirements |
| Legal and Compliance | Evaluates applicable legal, regulatory, and contractual obligations |
| Model Owner | Manages model configuration, versioning, validation, and relevant lifecycle controls |
| AI Engineering Lead | Explains implementation details and addresses technical findings |
| Cloud or Infrastructure Team | Provides evidence about hosting, network, identity, and infrastructure controls |
| Third-Party Risk Management | Assesses relevant external provider and supplier risks |
| Enterprise Risk Management | Supports risk evaluation and governance escalation |
| Internal Audit or Independent Assurance | Evaluates control design or effectiveness within its independent mandate |
| Authorized Risk Owner | Accepts residual risk where permitted and within delegated authority |
| Deployment or Release Authority | Authorizes production release under the organization's formal release process |

The same person may hold multiple roles, but the assignment must not undermine required independent challenge, control ownership, or formal approval authority.

#### 7.2 Responsibilities across the review lifecycle

| Activity | Responsible Party | Accountable Party | Consulted Parties |
|---|---|---|---|
| Initiate architecture review | AI System Owner or Project Lead | Designated Review Sponsor | Enterprise Architect, Security |
| Define review scope | Architecture Review Lead | Designated Review Sponsor | System Owner, Security, Privacy |
| Provide architecture documentation | Architecture and Engineering Teams | AI System Owner | Infrastructure, Data Owners |
| Perform threat modeling | Security Architecture | Designated Security Authority for the assigned review outcome | Engineering, Enterprise Architecture |
| Assess data flows | Architecture and Data Teams | Designated System Owner or Data Authority | Privacy, Security |
| Evaluate security controls | Security Architecture and Security Engineering | Designated Security Authority | Relevant Technical Owners |
| Record architecture findings | Review Lead | Designated Review Sponsor | Control Owners |
| Define remediation | Relevant Engineering or Control Owners | Assigned Remediation Owner | Security Architecture |
| Evaluate residual risk | Risk Owner and relevant specialists | Authorized Risk Acceptance Authority | Security, Business, Compliance |
| Approve architecture or recommend approval | Designated Architecture or Security Authority | Authority defined by organizational governance | System Owner, Risk Owner |
| Authorize production deployment | Designated Release Authority | Authority defined by release governance | Business Owner, Security, Operations |
| Validate remediation | Designated independent or appropriately separate reviewer | Assigned Control or Release Authority | Engineering, Security |
| Preserve review evidence | Review Lead or designated record owner | AI Governance Function or designated owner | System Owner, Risk Management |

The table is a starting point, not a universal assignment of authority. The organization's approved RACI and delegated authority matrix take precedence.

#### 7.3 Distinguishing architecture approval from risk acceptance

Architecture approval, security review completion, and residual-risk acceptance are related but distinct decisions.

- **Architecture approval** confirms that the design meets the applicable architecture decision criteria.
- **Security review completion** confirms that the defined review has been conducted and findings have been documented.
- **Risk acceptance** records an authorized decision to tolerate a specific residual risk where acceptance is permitted.
- **Production authorization** confirms that the system satisfies the applicable release conditions.

A positive architecture review does not automatically authorize production deployment. Similarly, a business sponsor cannot automatically accept security risk beyond their delegated authority.

The governance framework should define how these decisions interact and which conditions must be met before the system may proceed.

### 8. Architecture Review Evidence and Documentation Requirements

A reliable architecture review depends on accurate and sufficiently current evidence.

Reviewers should not rely exclusively on verbal assurances, presentation slides, or diagrams that do not reflect the implemented system. Where possible, documentation should be corroborated with configuration evidence, access-control settings, test results, supplier documentation, and relevant operational records.

#### 8.1 Minimum evidence package

| Evidence ID | Evidence Item | Purpose |
|---|---|---|
| EVD-01 | System overview and intended-purpose statement | Establish the system's business function and boundaries |
| EVD-02 | Current logical and physical architecture diagrams | Identify components and deployment relationships |
| EVD-03 | Data-flow diagrams | Trace data movement, processing, storage, and external transfers |
| EVD-04 | Trust-boundary diagram | Identify transitions between different trust domains |
| EVD-05 | Asset and dependency inventory | Identify models, services, libraries, APIs, and connected systems |
| EVD-06 | Data classification and handling requirements | Establish permitted use and protection requirements |
| EVD-07 | Identity and access-control design | Evaluate authentication, authorization, and privilege boundaries |
| EVD-08 | Threat model | Identify attack paths and associated mitigations |
| EVD-09 | Security requirements and control mapping | Establish expected security outcomes |
| EVD-10 | Model and provider documentation | Understand relevant model characteristics and provider responsibilities |
| EVD-11 | RAG and retrieval configuration | Assess retrieval authorization, document sources, and indexing controls |
| EVD-12 | Agent tool inventory and permission matrix | Assess permitted actions and execution authority |
| EVD-13 | Secrets and network security design | Review credential protection and network exposure |
| EVD-14 | Logging and monitoring design | Evaluate detection and investigation capabilities |
| EVD-15 | Security testing results | Review evidence of control validation |
| EVD-16 | Vulnerability and remediation records | Identify unresolved weaknesses |
| EVD-17 | Supplier assessment and contractual requirements | Evaluate third-party dependencies |
| EVD-18 | Incident response and recovery procedures | Assess containment and recovery readiness |
| EVD-19 | Change management and release procedures | Evaluate configuration integrity and deployment controls |
| EVD-20 | Risk assessment and risk acceptance records | Establish residual-risk decisions and ownership |

Not all evidence items will apply to every system. The review lead should document applicable evidence requirements and explain significant gaps.

#### 8.2 Evidence quality criteria

Evidence should be evaluated against the following criteria:

- **Relevance:** Does the evidence support the control or requirement being assessed?
- **Currency:** Does it reflect the architecture and configuration currently under review?
- **Completeness:** Does it cover the relevant components and trust boundaries?
- **Authenticity:** Can its origin and integrity be reasonably established?
- **Traceability:** Can the evidence be linked to a requirement, finding, decision, or control owner?
- **Reproducibility:** Can another qualified reviewer verify the result where appropriate?
- **Confidentiality:** Is the evidence stored and shared according to its classification?
- **Independence:** Where required, does the evidence come from a source sufficiently separate from the activity being assessed?

If evidence is missing, outdated, or inconclusive, the reviewer should record the limitation rather than assuming that the relevant control is effective.

### 9. Initial Architecture Review Checklist

The initial checklist establishes whether the review has sufficient information to proceed. It is not a final security approval.

A system with missing architecture diagrams, unclear data ownership, undocumented external dependencies, or unknown tool permissions may require additional discovery before a reliable security conclusion can be reached.

| ID | Review Question | Expected Evidence | Initial Status |
|---|---|---|---|
| ARC-CHK-01 | Is the system's intended purpose documented? | Approved use-case description | Not assessed |
| ARC-CHK-02 | Is the system owner identified? | Ownership record | Not assessed |
| ARC-CHK-03 | Is the technical architecture documented? | Current architecture diagrams | Not assessed |
| ARC-CHK-04 | Are major components and dependencies identified? | Component and dependency inventory | Not assessed |
| ARC-CHK-05 | Are data flows documented? | Data-flow diagrams | Not assessed |
| ARC-CHK-06 | Are trust boundaries identified? | Trust-boundary diagram or equivalent analysis | Not assessed |
| ARC-CHK-07 | Are data classifications known? | Data inventory and classification records | Not assessed |
| ARC-CHK-08 | Are external model providers identified? | Provider and model inventory | Not assessed |

Recommended status values include:

- **Not assessed:** The review has not evaluated the requirement.
- **Met:** Sufficient evidence supports the requirement.
- **Partially met:** Some elements are implemented, but gaps remain.
- **Not met:** The requirement is not satisfied.
- **Not applicable:** The requirement does not apply, with documented justification.
- **Unable to verify:** Available evidence is insufficient to determine whether the requirement is met.

The status values should be applied consistently across the organization's architecture review process.

### 10. Core Principle — Architecture Security Must Be Demonstrated, Not Assumed

An AI security architecture review establishes whether the system's design provides appropriate protection for its data, models, integrations, identities, tools, and business processes.

The review must account for both conventional cybersecurity weaknesses and AI-specific risks arising from model behavior, untrusted inputs, retrieved content, external model services, and model-mediated actions.

Its conclusions should be based on documented architecture, explicit security requirements, credible threat scenarios, implementation evidence, and validation appropriate to the system's risk.

**The central principle is that an AI system should not be considered architecturally secure merely because its model performs as expected or its application passes functional testing. Security depends on the complete system—including its trust boundaries, data flows, access controls, external dependencies, execution permissions, monitoring, and governance decisions.**

#### Key Conceptual Distinctions

| Concept | Meaning |
|---|---|
| Model security vs. system security | Model safeguards address model-specific risks; system security includes the surrounding application, data, infrastructure, and integrations |
| Logical architecture vs. physical architecture | Logical architecture describes functions and relationships; physical architecture describes deployment and infrastructure |
| Trust boundary vs. network boundary | A trust boundary represents a change in security assumptions; it may exist even when components share a network |
| Prompt instruction vs. security enforcement | Instructions influence model behavior; enforceable controls restrict what the system can actually do |
| Threat identification vs. risk assessment | Threat identification describes plausible attack scenarios; risk assessment evaluates their likelihood, impact, and treatment |
| Architecture review vs. penetration testing | Architecture review evaluates design and controls; penetration testing attempts to identify exploitable weaknesses under defined test conditions |
| Security finding vs. accepted risk | A finding identifies a weakness or gap; risk acceptance is an authorized decision about specified residual risk |
| Architecture approval vs. production authorization | Architecture approval addresses design criteria; production authorization addresses release conditions |
| Documentation vs. implementation evidence | Documentation describes intended controls; implementation evidence supports whether those controls exist and operate |
| AI capability vs. AI authority | A model may generate a proposed action, but the surrounding system must independently enforce whether that action is permitted |

**Completion criterion:** The foundational review package should be considered ready for detailed control evaluation when the review scope, system context, architecture components, data flows, trust boundaries, threat-modeling approach, security requirements, review responsibilities, and minimum evidence requirements have been documented sufficiently to support a structured and traceable assessment.
