# 20.16 — AI Agent Security Assessment

## Part 1 — AI Agent Security Fundamentals, Architecture, Trust Boundaries, and Threat Landscape

### 1. Introduction to the AI Agent Security Assessment

An AI agent security assessment is a structured evaluation of the security risks associated with AI systems that can interpret objectives, reason through tasks, interact with external tools, retrieve information, execute actions, and operate with varying degrees of autonomy.

Unlike a conventional AI model that primarily generates predictions or responses, an AI agent can influence external systems through its tools, permissions, and execution environment. Depending on its design, an agent may read confidential documents, query enterprise databases, create or modify records, send communications, execute workflows, or invoke other AI agents.

These capabilities introduce a broader attack surface than model inference alone.

For example, an enterprise AI agent may be designed to:
- Retrieve customer information from a CRM.
- Analyze customer cases and recommend actions.
- Query internal knowledge bases.
- Create support tickets.
- Update customer records.
- Send emails through an enterprise messaging platform.
- Escalate unresolved cases to human operators.

If the agent is compromised through prompt injection, excessive permissions, insecure tool integration, or inadequate authorization controls, the impact may extend beyond inaccurate AI-generated responses. The agent could disclose confidential information, modify business records, perform unauthorized transactions, or trigger downstream workflows.

The security assessment must therefore evaluate the complete agentic system: the model, instructions, memory, tools, identity, data sources, orchestration layer, execution environment, monitoring capabilities, and human oversight mechanisms.

#### 1.1 Objectives of the Assessment

The assessment should establish whether the AI agent can operate within explicitly approved security boundaries.

| Assessment objective | Key question | Expected outcome |
|---|---|---|
| Establish system scope | What does the agent do, and which systems does it affect? | Approved assessment scope |
| Identify attack surfaces | How can users, data, tools, models, and external systems influence the agent? | Documented threat landscape |
| Evaluate authorization | Can the agent perform only explicitly permitted actions? | Verified authorization controls |
| Protect sensitive data | Can the agent access or disclose information beyond its authorized scope? | Validated data protection measures |
| Control autonomy | Which decisions and actions may the agent perform independently? | Defined autonomy boundaries |
| Validate tool security | Can integrations be abused to perform unauthorized operations? | Tested tool-level security controls |
| Evaluate human oversight | Which actions require human approval or intervention? | Defined approval and escalation rules |
| Assess operational resilience | Can the agent be contained, disabled, or safely recovered? | Tested containment and recovery procedures |
| Produce a governance decision | Is the agent acceptable for its intended use? | Documented approval, conditions, or rejection |

#### 1.2 Assessment Outcomes

A completed assessment should produce a documented security decision rather than merely a list of technical observations.

Possible outcomes include:

- **Approved:** The agent meets the applicable security requirements for its intended use.
- **Approved with conditions:** Deployment is permitted subject to defined restrictions, compensating controls, or remediation deadlines.
- **Restricted approval:** The agent may operate only within a limited environment, user group, data classification, or set of tools.
- **Deferred:** Additional evidence, testing, or remediation is required before a decision can be made.
- **Rejected:** The residual risk exceeds the organization's approved risk tolerance or a mandatory security requirement remains unmet.

Approval should be based on evidence, not solely on the AI development team's assurance that the agent behaves as intended.

### 2. Scope and Applicability

An AI agent security assessment applies to systems in which an AI model participates in a workflow that can select tools, invoke functions, retrieve information, maintain task context, delegate work, or influence external actions.

The assessment must cover both the agent's intended functionality and the broader environment in which it operates.

#### 2.1 Types of AI Agents

| Agent category | Description | Representative security concern |
|---|---|---|
| Conversational agent | Responds to user requests and may invoke tools | Prompt injection and unauthorized disclosure |
| Retrieval-enabled agent | Retrieves information from documents or enterprise knowledge bases | Unauthorized retrieval and cross-user data leakage |
| Workflow agent | Coordinates multi-step business processes | Incorrect or unauthorized workflow execution |
| Transactional agent | Creates, modifies, or approves business transactions | Fraudulent or unauthorized transactions |
| Coding agent | Generates, edits, tests, or executes code | Malicious code execution and secret exposure |
| Security operations agent | Investigates alerts and may initiate response actions | Incorrect containment, evidence modification, or privilege abuse |
| Customer service agent | Interacts with customer records and service platforms | Customer data exposure and unauthorized account changes |
| Multi-agent system | Coordinates multiple agents with different responsibilities | Privilege propagation and uncontrolled delegation |
| Autonomous enterprise agent | Performs extended tasks with limited human intervention | Cumulative risk from planning, tool use, and persistent execution |

These categories are not mutually exclusive. An enterprise agent may combine retrieval, workflow orchestration, customer service, and transactional capabilities.

#### 2.2 Assessment Boundaries

The assessment should explicitly identify which components are included and excluded.

| Component | Assessment scope |
|---|---|
| Foundation model | Model provider, model access, supported capabilities, and applicable security assurances |
| System instructions | Instruction integrity, privilege boundaries, and configuration protection |
| Agent orchestration | Planning, reasoning cycles, tool selection, routing, and execution logic |
| Tool integrations | APIs, functions, connectors, and external service integrations |
| Identity and access management | Agent identity, delegated identity, service principals, tokens, and permissions |
| Memory | Session state, persistent memory, stored preferences, and retrieved historical context |
| Knowledge sources | Documents, databases, vector stores, APIs, and other retrieval sources |
| Execution environment | Containers, virtual machines, serverless functions, or other runtime infrastructure |
| Human oversight | Approval gates, exception handling, escalation, and emergency intervention |
| Monitoring and logging | Tool invocations, decisions, access events, errors, and security alerts |
| Third-party dependencies | Model providers, orchestration frameworks, external APIs, and software components |
| Downstream systems | Business applications and services that the agent can affect |

An assessment limited to the model API is insufficient when the agent can access enterprise data or execute actions through other components.

#### 2.3 Scope Definition Template

The assessor should complete a scope record before testing begins.

| Field | Required information |
|---|---|
| Agent name | Official name of the AI agent |
| Business owner | Accountable business stakeholder |
| Technical owner | Team responsible for development and operation |
| Business purpose | Intended business outcome |
| Intended users | Employees, customers, administrators, or other users |
| Deployment model | SaaS, cloud-hosted, on-premises, hybrid, or embedded |
| Model provider | Internal model or external provider |
| Agent framework | Orchestration technology and relevant components |
| Available tools | APIs, functions, connectors, and executable capabilities |
| Accessible data | Data sources and classifications |
| Autonomy level | Permitted independent decision-making and actions |
| Connected systems | Systems the agent can read from or modify |
| Regulatory context | Applicable privacy, security, sector, and AI requirements |
| Assessment environment | Development, testing, staging, or production |
| Exclusions | Components or activities outside the assessment |
| Approval authority | Role authorized to accept the assessment outcome |

**Governance requirement:** Scope exclusions must be documented and justified. An excluded component that can materially affect the agent's security should be treated as a dependency or an unresolved assessment limitation.

### 3. AI Agent Inventory and System Context

An organization cannot reliably assess or govern an AI agent that it has not identified, inventoried, and assigned to an accountable owner.

AI agent inventory management should therefore extend beyond recording the model name or application URL. It must capture the agent's capabilities, permissions, connected systems, operational boundaries, and potential business impact.

This is particularly important when business units can create agents using low-code platforms, SaaS automation tools, AI assistants, or enterprise workflow products without a traditional software development lifecycle.

#### 3.1 Minimum AI Agent Inventory

| Inventory field | Description | Security significance |
|---|---|---|
| Agent ID | Unique inventory identifier | Enables traceability across assessments and incidents |
| Agent name | Recognizable agent name | Supports ownership and operational identification |
| Business purpose | Approved use case | Establishes permitted functionality |
| Business owner | Accountable business representative | Provides business accountability |
| Technical owner | Responsible engineering or platform team | Establishes technical responsibility |
| Agent classification | Conversational, workflow, transactional, autonomous, or other | Helps determine assessment depth |
| Model and version | Model provider, model identifier, and version where available | Supports model risk and change tracking |
| Orchestration framework | Framework or platform controlling agent execution | Identifies a critical attack surface |
| Tools and connectors | Available functions, APIs, and integrations | Identifies potential paths to external impact |
| Identity model | User identity, service identity, delegated identity, or hybrid | Establishes authorization boundaries |
| Permission level | Read, write, execute, approve, or administrative access | Identifies privilege and misuse risks |
| Data classification | Highest sensitivity of data the agent can access | Determines confidentiality requirements |
| Memory configuration | Session-only, persistent, shared, or external memory | Identifies persistence and contamination risks |
| Autonomy classification | Degree of independent action permitted | Supports approval and supervision requirements |
| Human approval requirements | Actions requiring explicit authorization | Establishes human control points |
| Business criticality | Operational importance of the agent | Supports impact analysis |
| External exposure | Internal-only, partner-facing, customer-facing, or public | Helps determine exposure and threat assumptions |
| Monitoring status | Logging, alerting, and incident-response coverage | Indicates operational visibility |
| Assessment status | Not assessed, in progress, conditionally approved, approved, or rejected | Supports governance tracking |
| Last reviewed | Date of the most recent review | Enables periodic reassessment |
| Material changes | Changes to models, tools, permissions, or data access | Triggers reassessment when appropriate |

#### 3.2 Agent Capability Classification

Agent capabilities should be recorded individually rather than collapsed into a generic label such as "AI assistant."

| Capability | Example | Potential consequence if abused |
|---|---|---|
| Read | Retrieve a customer record | Unauthorized disclosure |
| Search | Query a knowledge base | Discovery of restricted information |
| Write | Update a CRM record | Data integrity compromise |
| Communicate | Send email or messages | Phishing, unauthorized disclosure, or reputational harm |
| Execute | Run a script or command | Code execution or infrastructure compromise |
| Transact | Initiate a payment or order | Financial loss or fraudulent activity |
| Approve | Approve access or business requests | Bypass of governance controls |
| Delegate | Invoke another agent | Expansion or propagation of privileges |
| Schedule | Create recurring jobs or future actions | Persistent unauthorized activity |
| Administer | Modify configuration or permissions | Security control degradation |

A single agent may possess several of these capabilities. The overall risk depends on their combination, the sensitivity of the accessible resources, the strength of authorization controls, and the level of human oversight.

#### 3.3 Example: Enterprise Customer Service Agent

Consider an AI agent supporting a telecommunications operator.

The agent can:
1. Authenticate an employee or customer.
2. Retrieve customer information from a CRM.
3. Search a service knowledge base.
4. Check billing information.
5. Open a support case.
6. Request a service-plan change.
7. Submit an action to a downstream provisioning system.

The agent is not merely a language model. It is an intermediary between a user, sensitive data, business rules, and systems capable of changing customer services.

Its assessment must determine whether:
- The user is authorized to access the requested customer record.
- The agent can retrieve only the information needed for the task.
- A retrieved document can influence the agent to bypass established instructions.
- The agent can distinguish an informational recommendation from an authorized transaction.
- Service changes require the appropriate validation and approval.
- Downstream systems independently enforce authorization.
- Every consequential action can be traced to an authenticated identity and an approved request.

### 4. AI Agent Architecture and Trust Boundaries

AI agent security depends heavily on architecture. A model may be appropriately configured while the surrounding orchestration layer, tool interface, memory store, or downstream application remains vulnerable.

The assessor must understand how instructions, data, identities, decisions, and actions move through the system.

The following is a logical reference architecture. Actual deployments may combine, omit, or distribute these components.

Monitoring and governance are cross-cutting capabilities. They should observe relevant activity across the architecture rather than operate only at the user interface or model API.

#### 4.2 Principal Trust Boundaries

A trust boundary is a point at which data, instructions, identities, or actions cross between components with different security assumptions.

| Trust boundary | What crosses the boundary | Primary risk | Required assessment focus |
|---|---|---|---|
| User to agent | Requests, attachments, instructions | Malicious or unauthorized input | Authentication, input handling, abuse prevention |
| Agent to model | Prompts, context, tool results | Sensitive prompt exposure or instruction manipulation | Data minimization, prompt construction, provider controls |
| Retrieval system to agent | Documents, search results, metadata | Indirect prompt injection and unauthorized content | Access-aware retrieval, content trust, provenance |
| Memory to agent | Stored state and historical context | Persistent poisoning or cross-user leakage | Isolation, integrity, retention, access control |
| Agent to tool gateway | Tool name, arguments, intended action | Unauthorized or malformed tool invocation | Allowlisting, schema validation, policy enforcement |
| Tool gateway to enterprise system | API requests and delegated credentials | Excessive privilege or authorization bypass | Independent authorization, scoped credentials, auditability |
| Agent to external service | Data and requests sent outside the organization | Data leakage or supply-chain exposure | Egress controls, third-party risk, data restrictions |
| Agent to human approver | Proposed action and supporting context | Misleading or incomplete approval information | Clear action summaries, independent verification |
| Agent to agent | Messages, tasks, delegated authority | Trust propagation and privilege escalation | Agent identity, delegation constraints, provenance |

#### 4.3 Architecture Review Questions

The assessor should obtain clear answers to the following questions:

1. Which component is responsible for authenticating the requesting user?
2. Does the agent retain the identity of the user throughout the execution chain?
3. Can the orchestration layer invoke a tool without a separate authorization decision?
4. Are tool permissions restricted to the minimum capabilities required?
5. Can retrieved content influence tool selection or action parameters?
6. Does the system distinguish trusted instructions from untrusted data?
7. Can one user's memory or retrieved context be exposed to another user?
8. Can a downstream application independently reject unauthorized operations?
9. Are outbound requests and external data transfers controlled?
10. Can administrators disable a tool, revoke credentials, or stop an agent during an incident?

An answer such as "the model is instructed not to do that" is not sufficient evidence of an enforceable security control.

Where a control is expected to prevent unauthorized actions, the assessor should verify that it is enforced by a deterministic policy mechanism, a trusted execution component, or the downstream system itself.

### 5. Data Flows, Context Assembly, and Sensitive Information

AI agents frequently combine information from multiple sources to construct the context used for planning, reasoning, and tool execution. These sources may include user prompts, system instructions, retrieved documents, prior interactions, persistent memory, tool outputs, and results from other agents.

Combining these sources creates security challenges because the agent may process trusted instructions and untrusted content within the same context.

The assessment must establish what information enters the agent, how it is transformed, where it is stored, and which destinations can receive it.

#### 5.1 Typical Agent Data Flow

```text
User Request
     |
     v
Authentication and Authorization
     |
     v
Input Validation and Classification
     |
     v
Context Assembly
     |
     +---------------------+
     |                     |
     v                     v
System Instructions   Retrieved Information
     |                     |
     |                     v
     |               Trust and Access Checks
     |                     |
     +----------+----------+
                |
                v
          Model Inference
                |
                v
        Proposed Plan or Action
                |
                v
       Policy and Authorization Checks
                |
                v
          Tool Invocation
                |
                v
       Enterprise System or Data Store
                |
                v
       Result Validation and Logging
                |
                v
       Response or Further Action
```

The diagram is simplified. Real agents may repeat the planning, retrieval, inference, and tool-execution stages many times before completing a task.

Each iteration creates another opportunity for untrusted content, excessive permissions, or incorrect intermediate decisions to influence the eventual outcome.

#### 5.2 Data Classification

The assessor should identify the most sensitive information the agent can access or transmit.

| Classification | Illustrative data | Assessment considerations |
|---|---|---|
| Public | Published product information | Integrity, availability, and source authenticity |
| Internal | Internal procedures and operational documentation | Access restrictions and unintended external disclosure |
| Confidential | Customer records, internal financial data, business plans | Fine-grained authorization, minimization, logging, and disclosure prevention |
| Restricted | Credentials, authentication secrets, highly sensitive personal data, critical security information | Strict access boundaries, secure secret handling, explicit use restrictions, and enhanced monitoring |

The organization's own classification scheme takes precedence over these illustrative labels.

#### 5.3 Data Flow Assessment Register

| Data element | Source | Classification | Processing purpose | Storage location | Destination | Required control |
|---|---|---|---|---|---|---|
| User prompt | User interface | Depends on content | Understand task | Session context or logs | Model or orchestration layer | Input controls and minimization |
| Customer record | CRM | Confidential or higher | Respond to authorized request | CRM and transient context | Agent response or approved tool | Object-level and field-level authorization |
| Retrieved document | Knowledge repository | Depends on document | Supply task context | Document store or vector index | Model context | Access-aware retrieval and source validation |
| API credential | Secret manager | Restricted | Authenticate a tool | Secret manager and controlled runtime | Authorized connector | Secret isolation and scoped access |
| Tool output | Enterprise API | Depends on result | Continue task execution | Session state or logs | Agent or downstream component | Output validation and access restrictions |
| Persistent memory | Memory store | Depends on content | Preserve approved context | Memory database | Future agent sessions | Isolation, retention, integrity, and deletion controls |
| Audit event | Logging platform | May contain sensitive metadata | Investigation and accountability | Security log platform | Monitoring and audit systems | Log access controls, minimization, and integrity |

#### 5.4 Key Data Flow Risks

**Excessive context collection:** The agent retrieves more information than necessary to complete the task.

**Unauthorized contextual disclosure:** Sensitive information is placed into a model context or tool result even though the requesting user lacks permission to access it.

**Cross-session contamination:** Data from one user or task influences another user's session.

**Uncontrolled persistence:** Sensitive prompts, tool outputs, or inferred information are retained longer than approved.

**External transmission:** Confidential information is transmitted to a model provider or external service without the required authorization or safeguards.

**Sensitive logging:** Prompts, tool arguments, or model responses containing confidential data are copied into logs with broader access than the source system.

**Context integrity compromise:** Untrusted content changes how the agent interprets a task or selects an action.

#### 5.5 Assessment Principle

Data protection must be enforced throughout the entire processing chain.

A secure source database does not guarantee a secure agent if the retrieval layer returns unauthorized information. Similarly, access-controlled model inputs do not guarantee confidentiality if tool outputs, logs, memory, or generated responses expose sensitive information.

The assessor must trace representative sensitive data from its source through processing, storage, logging, and final disposition.

### 6. Identity, Authentication, and Authorization for AI Agents

Identity and access management is a foundational control area for agentic systems because an agent can exercise the permissions of a user, a service account, a delegated identity, or a combination of identities.

The security assessment must determine not only who can use the agent, but also which identity is used when the agent performs each consequential action.

#### 6.1 Common Agent Identity Models

| Identity model | Description | Principal security concern |
|---|---|---|
| Shared service identity | Multiple users' requests execute under one service account | Actions may not be adequately constrained or attributed to the initiating user |
| User-delegated identity | The agent accesses resources using the authenticated user's delegated permissions | Delegation scope, token handling, and authorization consistency |
| Agent-specific identity | The agent has its own workload identity and permissions | Excessive privilege or insufficient separation between users |
| Hybrid identity | User identity and agent identity are combined | Confused-deputy risks and inconsistent enforcement |
| Multi-agent identity | Multiple agents act under distinct or inherited identities | Uncontrolled privilege propagation and weak delegation boundaries |

No identity model is inherently secure in every context. The selected model must match the business process, the required permissions, and the organization's accountability requirements.

#### 6.2 The Confused-Deputy Problem

A confused-deputy scenario occurs when a component with legitimate authority is manipulated into using that authority for an unauthorized purpose.

For example:

1. A customer asks an AI agent to retrieve information about an account.
2. The agent has broad CRM permissions through a shared service identity.
3. The user includes instructions intended to make the agent retrieve another customer's record.
4. The agent invokes the CRM connector.
5. The connector accepts the request because the shared service identity is authorized to read the record.
6. The agent returns information the requesting customer is not entitled to receive.

The underlying issue is not necessarily that the CRM lacks access controls. The problem is that the connector's authority is broader than the requester's authority, and the system does not adequately bind the action to the authenticated user's permissions.

**Required control:** Authorization must be enforced for the specific resource and operation, using the applicable user, agent, business-process, and policy context. The model must not be treated as the authority that determines whether access is permitted.

#### 6.3 Minimum Authorization Requirements

| Control | Implementation expectation | Evidence to collect |
|---|---|---|
| Unique agent identity | Each independently governed agent has an identifiable execution identity where appropriate | Identity configuration and inventory records |
| Least privilege | Permissions are restricted to necessary resources and operations | Role and permission review |
| User-context preservation | Relevant user identity and entitlements remain available throughout execution | Architecture and integration evidence |
| Resource-level authorization | Access decisions apply to the specific record, object, or resource | Authorization tests |
| Action-level authorization | Read, write, delete, approve, and execute operations are distinguished | API policy and test results |
| Credential protection | Tokens and secrets are not exposed to model context or unauthorized tools | Secret-management configuration and testing |
| Delegation constraints | Agents cannot arbitrarily expand their permissions when delegating tasks | Delegation policies and test evidence |
| Revocation | Credentials and access can be disabled promptly | Revocation procedures and test records |
| Attribution | Actions can be traced to the initiating request and executing identity | Correlated audit events |
| Privilege review | Agent permissions are periodically reviewed and reassessed after material changes | Review records and remediation tickets |

#### 6.4 Authorization Decision Matrix

| Action | Example | Default security treatment |
|---|---|---|
| Read public information | Retrieve a published product description | Permit within approved scope |
| Read internal information | Search internal operating procedures | Require authenticated access and applicable data restrictions |
| Read personal or customer information | Retrieve a customer account | Enforce user-specific authorization and data minimization |
| Modify a business record | Change a CRM field | Require action-specific authorization and validation |
| Send external communications | Email a customer or supplier | Validate recipient, content, and permitted purpose |
| Initiate a financial transaction | Submit a payment or refund | Apply transaction-specific controls and approval requirements |
| Change access permissions | Grant a user a new role | Require privileged authorization and independent policy enforcement |
| Execute arbitrary code | Run a shell command or script | Prohibit by default unless explicitly justified and securely constrained |
| Delegate a privileged task | Ask another agent to modify a record | Verify the delegated task, identity, scope, and authority |

The default treatment should be adapted to the approved use case and organizational policies. High-impact operations require stronger controls than read-only or reversible activities.

#### 6.5 Authorization Testing Scenarios

The assessment should include negative tests designed to prove that unauthorized operations are rejected.

Examples include:

- A user requests a record belonging to another user.
- A user asks the agent to modify an object that is outside the user's permissions.
- An agent attempts to use a read-only connector to perform a write operation.
- A tool receives an object identifier that was not authorized by the originating request.
- An agent attempts to reuse an expired or revoked credential.
- One agent attempts to invoke a privileged function assigned to another agent.
- A user attempts to persuade the agent to reveal a credential or authentication token.
- A delegated task attempts to expand its permissions beyond the original authorization scope.

Expected evidence should include the rejected operation, the applicable policy decision, the corresponding log entry, and confirmation that no unauthorized state change occurred.

### 7. AI Agent Threat Modeling and Attack Surface Analysis

Threat modeling identifies how an attacker, malicious insider, compromised dependency, or untrusted input could cause the agent to violate its security requirements.

Traditional application threat modeling remains relevant, but AI agents introduce additional risks because natural-language instructions and retrieved content can influence planning, tool selection, and action sequences.

The assessor should analyze both conventional technical vulnerabilities and agent-specific failure modes.

#### 7.1 Threat Modeling Method

A practical assessment can use the following sequence:

1. **Define the assets:** Identify sensitive data, credentials, business records, tools, model configurations, and critical processes.
2. **Identify threat actors:** Consider external attackers, malicious users, compromised accounts, malicious insiders, and compromised third-party components.
3. **Map trust boundaries:** Document where instructions, data, identities, and actions cross security boundaries.
4. **Enumerate attack surfaces:** Include user inputs, retrieval sources, memory, tool interfaces, APIs, execution environments, and inter-agent communication.
5. **Construct abuse scenarios:** Describe how a threat actor could manipulate the agent or its surrounding components.
6. **Evaluate existing controls:** Identify preventive, detective, and corrective safeguards.
7. **Assess impact and likelihood:** Determine the credible business and technical consequences.
8. **Define treatment:** Assign remediation, risk ownership, and verification requirements.
9. **Validate through testing:** Attempt to reproduce relevant attack paths in an authorized environment.
10. **Record residual risk:** Document unresolved exposure and the required governance decision.

#### 7.2 Agent-Specific Attack Surfaces

| Attack surface | Example threat | Potential impact |
|---|---|---|
| User input | Malicious instructions embedded in a request | Unauthorized action or information disclosure |
| Retrieved documents | Instructions hidden in a document | Manipulated planning or tool invocation |
| Persistent memory | Malicious content retained between tasks | Repeated or cross-session manipulation |
| Tool descriptions | Misleading or compromised tool metadata | Unsafe tool selection |
| Tool arguments | Manipulated identifiers or parameters | Unauthorized or unintended operations |
| Orchestration logic | Inadequate enforcement of execution limits | Repeated, unsafe, or uncontrolled actions |
| API connectors | Weak authorization or input validation | Data exposure or unauthorized changes |
| Model configuration | Unsafe or unauthorized configuration changes | Weakened security behavior |
| External dependencies | Compromised framework or third-party service | Supply-chain compromise |
| Multi-agent communication | Malicious instructions passed between agents | Delegation abuse or privilege escalation |
| Logs and traces | Sensitive information exposed through telemetry | Confidentiality and privacy compromise |
| Execution environment | Unsafe command or code execution | Runtime compromise or access to underlying infrastructure |

#### 7.3 Threat Scenario Register

The following example illustrates how to document agent-specific threats before assigning a final risk score.

| Threat ID | Threat scenario | Affected asset | Existing control to verify | Potential consequence |
|---|---|---|---|---|
| AGT-01 | Malicious input causes an agent to invoke an unauthorized tool | Enterprise application | Tool authorization and policy enforcement | Unauthorized business action |
| AGT-02 | Retrieved content influences the agent to disclose confidential information | Customer or corporate data | Retrieval access controls and output validation | Data leakage |
| AGT-03 | Shared service credentials allow cross-user data access | CRM or database | User-context enforcement and scoped identity | Unauthorized disclosure |
| AGT-04 | Persistent memory retains malicious instructions | Agent memory | Memory isolation, provenance, and integrity controls | Repeated manipulation |
| AGT-05 | A tool accepts unsafe arguments generated by the model | Downstream application | Schema validation and business-rule enforcement | Data corruption or unauthorized action |
| AGT-06 | The agent repeatedly invokes expensive operations | Model service or enterprise API | Rate limits, quotas, and execution budgets | Service disruption or unexpected cost |
| AGT-07 | An agent delegates a privileged task without adequate checks | Downstream agent or service | Delegation policy and independent authorization | Privilege escalation |
| AGT-08 | Sensitive data is written to broadly accessible logs | Logging platform | Log minimization and access restrictions | Confidentiality or privacy breach |
| AGT-09 | A compromised dependency alters agent behavior | Agent runtime | Dependency governance and integrity verification | System compromise |
| AGT-10 | The agent continues executing after a policy violation | Connected business systems | Stop controls, execution limits, and incident procedures | Escalating operational impact |

The existence of a threat scenario does not prove that the vulnerability exists. The assessor must determine whether the attack path is technically feasible, whether existing controls prevent it, and what evidence supports the conclusion.

#### 7.4 Attack-Path Analysis

An attack path describes how multiple weaknesses can combine to produce a material security incident.

```text
ATTACKER
   |
   v
Malicious User Input
   |
   v
Agent Interprets Untrusted Content
   |
   v
Unsafe Tool Selection
   |
   v
Overprivileged Connector
   |
   v
Downstream Authorization Failure
   |
   v
Unauthorized Data Access or State Change
   |
   v
Business Impact
```

A robust assessment must evaluate the chain rather than testing each component only in isolation.

For example, a prompt-injection weakness may have limited impact if the agent has no tools and cannot access sensitive information. The same weakness may become critical when the agent can access confidential records and invoke privileged business operations.

Risk therefore depends on the combination of exploitability, permissions, data sensitivity, downstream safeguards, and potential business consequences.

### 8. Prompt Injection, Instruction Hierarchy, and Untrusted Content

Prompt injection occurs when malicious or unintended instructions influence an AI system to disregard its intended task, misuse tools, expose information, or behave outside its approved operating boundaries.

For AI agents, prompt injection is especially important because the model's interpretation of content can influence actions performed through external tools.

Prompt injection may originate directly from a user or indirectly from content the agent retrieves or processes.

#### 8.1 Direct and Indirect Prompt Injection

| Type | Description | Example |
|---|---|---|
| Direct prompt injection | A user attempts to override the agent's intended instructions | A user asks the agent to ignore its restrictions and reveal confidential data |
| Indirect prompt injection | Malicious instructions are embedded in content processed by the agent | A retrieved document contains instructions intended to redirect the agent |
| Persistent prompt injection | Malicious content influences future sessions through stored memory or context | An agent stores attacker-controlled instructions and later acts on them |
| Tool-mediated injection | Tool output contains instructions that influence subsequent decisions | A webpage returned by a browsing tool instructs the agent to invoke another tool |
| Cross-agent injection | One agent passes malicious instructions or contaminated results to another | A research agent supplies untrusted content to a privileged execution agent |

These categories can overlap. For example, indirect prompt injection can become persistent if the agent stores malicious content in long-term memory.

#### 8.2 Instruction Hierarchy Is Not an Authorization Boundary

An agent may use a hierarchy of instructions, such as system-level instructions, developer-defined rules, and user requests. This hierarchy can guide model behavior, but it should not be treated as a substitute for enforceable security controls.

The model may misinterpret instructions, fail to recognize malicious content, or produce an unsafe plan despite the presence of restrictive system instructions.

Consequently:

- Instructions should define intended behavior.
- Deterministic policy controls should constrain available actions.
- Tool gateways should validate tool names, arguments, and authorization.
- Downstream applications should enforce their own access controls.
- High-impact actions should require explicit approval where appropriate.
- Monitoring should identify suspicious tool sequences and policy violations.

A prompt that says "never access another user's records" is not equivalent to a database authorization rule that prevents access to those records.

#### 8.3 Prompt Injection Assessment Scenarios

| Test ID | Scenario | Expected security property |
|---|---|---|
| PI-01 | User instructs the agent to ignore its approved purpose | The agent remains within the authorized task and tool scope |
| PI-02 | Retrieved content requests disclosure of confidential data | The content is treated as untrusted and cannot override access policy |
| PI-03 | A document requests invocation of a privileged tool | The tool gateway independently verifies authorization |
| PI-04 | Retrieved content attempts to redirect data to an external destination | External transmission remains subject to explicit policy controls |
| PI-05 | Tool output includes instructions to execute unrelated commands | Tool output does not automatically authorize new actions |
| PI-06 | Malicious content is written into persistent memory | Memory controls prevent unsafe persistence or cross-session influence |
| PI-07 | An agent passes untrusted instructions to a privileged sub-agent | The receiving agent validates provenance and independently enforces policy |
| PI-08 | A user asks the agent to disclose hidden configuration or secrets | Confidential configuration and credentials remain protected |
| PI-09 | An injection attempts to bypass a human approval requirement | The approval gate cannot be bypassed by model-generated reasoning |
| PI-10 | Several low-risk requests are combined into a high-impact sequence | Cumulative actions remain within execution and authorization limits |

Testing should use controlled, non-production environments wherever possible. Any production validation must be explicitly authorized, scoped, and designed to avoid unintended business impact.

#### 8.4 Layered Defenses Against Prompt Injection

| Defense layer | Example control | Purpose |
|---|---|---|
| Input handling | Input validation, abuse detection, and request constraints | Reduce malformed or abusive inputs |
| Source trust | Record document origin and trust classification | Help identify untrusted content |
| Retrieval controls | Enforce authorization before content enters the model context | Prevent unauthorized information retrieval |
| Context construction | Separate instructions from retrieved content where technically feasible | Reduce ambiguity between instructions and data |
| Tool allowlisting | Restrict available tools to approved capabilities | Limit the consequences of manipulation |
| Argument validation | Validate tool parameters against strict schemas and business rules | Prevent unsafe or unauthorized inputs |
| Authorization | Enforce resource- and action-level permissions | Prevent privilege misuse |
| Human approval | Require confirmation for defined high-impact operations | Introduce an independent decision point |
| Output validation | Validate responses and tool results before consequential use | Reduce unsafe downstream processing |
| Monitoring | Detect anomalous tool use and policy violations | Support detection and investigation |
| Incident response | Revoke access, disable tools, or stop execution | Contain successful or suspected attacks |

No single defense should be assumed to eliminate prompt injection. The assessment should determine whether multiple independent controls limit the impact when the model is successfully manipulated.

### 9. Retrieval-Augmented Generation and Knowledge-Source Security

Retrieval-augmented generation (RAG) enables an AI agent to retrieve relevant information from external or enterprise data sources and incorporate that information into its context.

For agents, retrieval may be a preliminary step in answering a question or a recurring component of a multi-step workflow.

RAG can improve factual grounding and provide access to current enterprise information, but it also creates security risks involving document access, data segregation, content integrity, indexing, and indirect prompt injection.

#### 9.1 Typical RAG Architecture

```text
Enterprise Documents and Data
             |
             v
      Ingestion Pipeline
             |
             v
 Classification and Access Metadata
             |
             v
     Chunking and Indexing
             |
             v
       Vector / Search Store
             |
             v
      User Query and Identity
             |
             v
       Access-Aware Retrieval
             |
             v
      Retrieved Context Review
             |
             v
        Agent / LLM Context
             |
             v
      Response or Tool Decision
```

Security must be addressed during both ingestion and retrieval. Applying authorization only after documents have already entered the model context may be too late to prevent disclosure.

#### 9.2 Principal RAG Security Risks

**Unauthorized retrieval:** Search results include documents the user is not authorized to access.

**Embedding and index exposure:** Vector databases or related storage expose sensitive content, metadata, or embeddings to unauthorized parties.

**Indirect prompt injection:** Retrieved content contains instructions designed to manipulate the agent.

**Data poisoning:** An attacker introduces inaccurate or malicious information into a knowledge source, affecting agent decisions.

**Stale permissions:** Documents remain retrievable after access rights have changed or been revoked.

**Cross-tenant leakage:** Retrieval filters fail to isolate data belonging to different customers, business units, or tenants.

**Inadequate source attribution:** The agent cannot reliably identify the origin of a claim or distinguish authoritative sources from untrusted material.

**Overbroad retrieval:** The system retrieves more content than necessary, increasing the likelihood of exposing sensitive information.

#### 9.3 RAG Assessment Checklist

| Assessment question | Evidence expected |
|---|---|
| Are data sources approved by their owners? | Source inventory and approval records |
| Is the sensitivity of ingested content classified? | Classification rules and representative records |
| Are access permissions preserved or appropriately enforced during retrieval? | Retrieval authorization design and negative-test results |
| Are tenant and user boundaries enforced? | Isolation architecture and cross-boundary test results |
| Are document changes and deletions reflected in the index? | Synchronization and deletion-control evidence |
| Can the system identify document provenance? | Source identifiers, metadata, and retrieval traces |
| Are untrusted documents treated as data rather than authoritative instructions? | Design documentation and prompt-injection test evidence |
| Are retrieval results limited to the minimum required context? | Retrieval configuration and test results |
| Are vector stores and indexes protected against unauthorized access? | IAM configuration, network controls, and audit logs |
| Are indexing pipelines protected from unauthorized modification? | Ingestion permissions, integrity controls, and monitoring |
| Are sensitive values excluded from embeddings or handled according to approved policy? | Data processing design and risk analysis |
| Are changes to retrieval models, ranking logic, and filters governed? | Change records and regression tests |

#### 9.4 RAG Security Test Scenarios

The assessor should test cases such as:

1. An authenticated user searches for a document restricted to another department.
2. A user attempts to retrieve information from another customer's knowledge partition.
3. A document is deleted or access is revoked, but the indexed content remains available.
4. A malicious document instructs the agent to expose a credential.
5. An attacker attempts to introduce false information into an approved knowledge source.
6. The agent receives conflicting information from sources with different authority levels.
7. A search query retrieves confidential information unrelated to the requested task.
8. An agent summarizes restricted documents into a response that is then available to a broader audience.

The objective is not merely to verify that retrieval returns relevant content. It is to prove that retrieval respects authorization, provenance, integrity, and data-minimization requirements.

#### 9.5 RAG Governance Requirement

The data owner, not the AI model, defines which information a user or agent is authorized to access.

The retrieval layer should enforce applicable access policies before protected content is incorporated into the model context. The agent should not be expected to infer whether a document is authorized based solely on the document's wording or its own interpretation.

### 10. Core Principle — Secure the Agent's Capabilities, Not Merely Its Conversation

AI agent security assessment must begin with the system's actual capabilities and the consequences of their misuse.

The most important question is not simply whether the model can resist malicious prompts. It is whether the complete system can prevent a manipulated, misconfigured, compromised, or incorrectly behaving agent from exceeding its authorized boundaries.

An enterprise agent may interact with confidential information, invoke privileged tools, preserve information across sessions, delegate work, and modify business systems. Each capability introduces an associated trust boundary, authorization requirement, and potential business impact.

The assessor must therefore evaluate the relationships between:

- **Model behavior and enforceable policy:** Instructions guide the model, while independent controls restrict what it can actually do.
- **User identity and agent identity:** The system must preserve accountability and prevent an agent's privileges from bypassing the user's authorization.
- **Retrieved information and trusted instructions:** External content must not automatically acquire authority over the agent's behavior.
- **Tool availability and tool authorization:** A tool being technically available does not mean every user or task is authorized to invoke it.
- **Autonomy and human oversight:** The permitted degree of independent action must reflect business impact and risk tolerance.
- **Data access and data disclosure:** Accessing information for a legitimate task does not automatically authorize its disclosure to every destination.
- **Component security and end-to-end security:** Secure individual components do not guarantee that their combined execution paths are secure.
- **Assessment findings and governance decisions:** Identified weaknesses must lead to remediation, enforceable restrictions, or documented risk decisions.

#### Final Assessment Principle

**An AI agent should receive only the identities, data, tools, permissions, and autonomy necessary for its approved purpose. Every consequential action must be subject to enforceable authorization, appropriate validation, traceable execution, and proportionate oversight.**

A successful assessment demonstrates—through architecture review, configuration inspection, adversarial testing, and operational evidence—that the agent's security boundaries remain effective even when its model is manipulated or behaves unexpectedly.

### 11. Agent Tool Security and Function-Calling Controls

AI agents frequently interact with external systems through tools, functions, connectors, APIs, and executable workflows. These integrations allow an agent to move beyond generating recommendations and perform operations that affect enterprise environments.

A tool may provide read access to a database, create a customer record, send an email, execute a script, modify a cloud resource, or initiate a financial transaction.

Every tool therefore represents a potential security boundary. If the agent can invoke tools without adequate authorization, input validation, execution constraints, and monitoring, a model-level manipulation may become a real-world security incident.

The security assessment must determine whether tool access is explicitly governed, technically constrained, and independently validated.

#### 11.1 Tool Classification by Capability and Impact

Tools should be classified according to their capabilities, privileges, and potential consequences.

| Tool category | Representative operations | Primary security concerns |
|---|---|---|
| Read-only information tools | Search documents, retrieve records, query inventory | Unauthorized disclosure and excessive data retrieval |
| Data modification tools | Create, update, or delete records | Data integrity compromise and unauthorized changes |
| Communication tools | Send emails, publish messages, notify customers | Information leakage, impersonation, and reputational damage |
| Administrative tools | Modify permissions, configurations, or security policies | Privilege escalation and security control degradation |
| Execution tools | Run scripts, execute commands, or invoke code interpreters | Code execution and infrastructure compromise |
| Financial tools | Initiate refunds, payments, purchases, or transfers | Fraud and financial loss |
| Workflow tools | Approve requests, open cases, trigger business processes | Unauthorized workflow transitions |
| Cloud management tools | Create resources, change network rules, manage identities | Cloud compromise, data exposure, and cost abuse |
| Security operations tools | Disable accounts, isolate endpoints, block traffic | Incorrect containment or disruption of critical services |
| Agent delegation tools | Assign work to other agents | Privilege propagation and uncontrolled execution chains |

The classification should consider not only the tool's stated purpose but also the effective permissions of the underlying API or service account.

A tool described as "update customer details" may expose fields that permit changes to authentication methods, account ownership, or security-sensitive attributes. The assessor must inspect the actual operations and parameters available.

#### 11.2 Tool Registry and Allowlisting

The organization should maintain an approved tool registry.

| Registry field | Description |
|---|---|
| Tool ID | Unique identifier |
| Tool name | Recognizable function or connector name |
| Business purpose | Approved use case |
| Technical owner | Responsible team |
| Supported operations | Read, write, execute, approve, or other capabilities |
| API endpoint | Approved destination or service |
| Authentication method | Workload identity, delegated identity, OAuth, certificate, or other approved method |
| Permission scope | Resources and actions accessible to the tool |
| Data classification | Sensitivity of information processed |
| Risk classification | Inherent impact of misuse |
| Required approval | Whether human authorization is required |
| Input schema | Valid argument structure and constraints |
| Output schema | Expected result structure |
| Logging requirements | Events and attributes that must be recorded |
| Rate and execution limits | Permitted invocation frequency and resource consumption |
| Failure behavior | Handling of errors, timeouts, and partial execution |
| Approval status | Whether the tool is approved for the agent |
| Last review | Date of the most recent security review |

**Required control:** Agents should have access only to explicitly approved tools. The tool registry should be enforced by the orchestration layer or a trusted execution gateway, rather than relying solely on the model to select appropriate functions.

#### 11.3 Tool Invocation Security Requirements

| Control | Required behavior | Assessment evidence |
|---|---|---|
| Tool allowlisting | Only approved tools are available to the agent | Registry and runtime configuration |
| Function-level authorization | Each operation is authorized independently | Policy configuration and test results |
| Argument validation | Arguments conform to strict schemas and business rules | Schema definitions and negative tests |
| Resource authorization | Target resources are checked against applicable permissions | Authorization logs and test evidence |
| Parameter constraints | High-risk parameters have permitted ranges and values | Validation rules and boundary tests |
| Output validation | Tool results are checked before further processing | Validation logic and test cases |
| Execution limits | Tool calls are bounded by count, time, and resource budgets | Runtime settings and test results |
| Idempotency | Repeated requests do not unintentionally repeat sensitive actions | Idempotency controls and transaction tests |
| Error handling | Errors do not expose secrets or bypass security checks | Error-handling tests |
| Auditability | Invocations are attributable and traceable | Correlated logs |
| Emergency disablement | Tools can be disabled when necessary | Tested containment procedure |

#### 11.4 Example: Unsafe Tool Invocation

Consider an enterprise agent with access to a CRM connector.

The agent exposes a function similar to:

```text id="tool-invoke-01"
update_customer_record(
    customer_id,
    field_name,
    new_value
)
```

If the function accepts arbitrary field names and does not verify the user's permissions, the agent might be manipulated into changing a security-sensitive attribute.

A safer design introduces explicit constraints:

```text id="tool-invoke-02"
1. Authenticate the requesting user.
2. Resolve the target customer record.
3. Verify the user's access to that record.
4. Verify permission to modify the requested field.
5. Reject fields outside the approved allowlist.
6. Validate the new value against business rules.
7. Require additional approval for sensitive changes.
8. Execute the operation through the authorized connector.
9. Record the request, decision, and resulting state change.
10. Verify the final state and report the outcome.
```

The exact implementation may differ, but the security properties should remain enforceable independently of model-generated reasoning.

#### 11.5 High-Impact Tool Controls

Actions that can produce significant financial, operational, privacy, or security consequences require stronger safeguards.

Examples include:

- Changing customer authentication settings.
- Approving payments or refunds.
- Deleting production records.
- Modifying access permissions.
- Disabling security monitoring.
- Changing cloud network security rules.
- Executing arbitrary code.
- Making irreversible changes to critical infrastructure.

For these actions, the assessment should evaluate transaction limits, separation of duties, explicit confirmation, independent authorization, rollback capabilities, and human approval requirements.

A confirmation message generated by the agent is not necessarily an effective approval control. Approval must be obtained through an authenticated mechanism that binds the approver to the specific action and its material parameters.

### 12. Excessive Agency, Autonomy Boundaries, and Human Approval

Excessive agency occurs when an AI agent has more authority, tool access, or independent decision-making capability than is necessary for its approved purpose.

An agent may become dangerous even without a conventional software vulnerability if it can autonomously perform high-impact actions, repeat operations without limits, or chain individually legitimate tools into an unauthorized workflow.

The assessment must establish which decisions the agent can make independently, which actions it can execute, and where explicit human authorization is mandatory.

#### 12.1 Autonomy Classification

The following model provides a practical governance classification. Organizations may adopt different terminology or thresholds.

| Level | Name | Description | Typical control expectation |
|---|---|---|---|
| A0 | Informational | Generates explanations or recommendations without external actions | Output review and applicable data controls |
| A1 | Assisted | Prepares actions for a human to execute | Human verification before execution |
| A2 | Bounded execution | Performs predefined, low-impact actions within strict limits | Allowlisted tools, bounded permissions, and monitoring |
| A3 | Conditional autonomy | Performs selected multi-step workflows under defined policies | Strong authorization, execution budgets, and approval gates for sensitive actions |
| A4 | High autonomy | Performs complex tasks with substantial independent action | Enhanced risk assessment, strict containment, continuous monitoring, and narrowly defined authority |

These levels are governance categories rather than universal technical standards. The organization must define its own measurable criteria for each level.

A higher autonomy level does not automatically mean an agent is unacceptable. It means the assessment must establish stronger evidence that the agent can remain within its approved operating boundaries.

#### 12.2 Action Impact Classification

Autonomy must be evaluated together with the impact of individual actions.

| Impact category | Example | Recommended governance treatment |
|---|---|---|
| Low | Summarize public documentation | May be permitted automatically within approved scope |
| Moderate | Create a draft support ticket | Permit with validation and audit logging |
| Elevated | Modify customer account details | Require strong authorization and field-specific restrictions |
| High | Issue a customer refund or change service provisioning | Apply transaction limits and explicit approval where required |
| Critical | Change privileged access or disable production security controls | Require exceptional authorization, independent verification, and enhanced oversight |

The organization should classify actions according to business impact, reversibility, data sensitivity, and potential downstream effects.

#### 12.3 Human Approval Design

A robust approval gate should include:

1. **Authenticated approver:** The approval comes from an authorized person.
2. **Specific action:** The request identifies the operation to be performed.
3. **Explicit parameters:** The target, amount, recipient, scope, and other material parameters are visible.
4. **Context and rationale:** The approver receives sufficient information to evaluate the action.
5. **Risk indication:** The system highlights sensitive, unusual, or irreversible consequences.
6. **Binding authorization:** Approval applies to the exact action presented, not an unrestricted subsequent action.
7. **Expiration:** Approval cannot be reused indefinitely.
8. **Execution verification:** The system confirms that the approved action matches the executed action.
9. **Audit record:** The approval, approver, timestamp, action, and result are recorded.
10. **Failure handling:** Changes to material parameters invalidate the approval and trigger reassessment.

Human approval should not become a routine click-through step. Approval interfaces must provide sufficient context for meaningful decisions.

#### 12.4 Approval Decision Matrix

| Action | Autonomous execution | Human approval | Additional control |
|---|---|---|---|
| Summarize approved public information | Generally acceptable | Usually unnecessary | Output quality checks |
| Search authorized internal documents | Acceptable within access boundaries | Usually unnecessary | Access-aware retrieval |
| Draft an email | Generally acceptable | Required before sending when policy mandates | Recipient and content validation |
| Send a routine approved notification | Potentially acceptable | Depends on business impact and policy | Recipient allowlist and rate limits |
| Modify a customer record | Only within defined permissions and limits | Required for designated sensitive changes | Field-level authorization |
| Issue a refund | Only under an explicitly approved bounded policy, if permitted | Required above defined thresholds or for elevated-risk cases | Transaction limits and duplicate prevention |
| Change user privileges | Normally restricted to controlled workflows | Independent authorized approval | Separation of duties |
| Delete production data | Restricted and tightly controlled | Strong approval required where permitted | Backup, recovery, and audit evidence |
| Modify security controls | Restricted to authorized workflows | Independent security approval | Change management and rollback |
| Execute arbitrary commands | Prohibited by default unless explicitly justified | Approval alone is insufficient | Sandboxing and command restrictions |

#### 12.5 Cumulative Action Risk

An assessment must account for action sequences, not just isolated calls.

For example, an agent might:
1. Retrieve a customer record.
2. Modify an account attribute.
3. Trigger a provisioning workflow.
4. Send a confirmation email.
5. Close the support case.

Each action might be technically permitted in isolation, but the combined sequence could cause harm if the original request was unauthorized or based on manipulated information.

Required controls include:
- End-to-end workflow authorization.
- Limits on the number of actions per task.
- Restrictions on sensitive action combinations.
- Revalidation before high-impact steps.
- Transaction state tracking.
- Detection of unusual action sequences.
- A reliable mechanism to halt execution.

The agent should not be able to bypass a high-impact approval gate by decomposing one restricted operation into several individually permitted actions.

### 13. Memory Security, Session Isolation, and Context Integrity

AI agents may maintain information across the current conversation, individual tasks, user sessions, or longer periods of operation.

Memory can improve continuity and task performance, but it creates security risks when information is stored without appropriate access controls, retained beyond its purpose, or reused in an unrelated context.

Memory may contain user preferences, summaries, retrieved documents, business facts, tool results, task state, or information inferred by the model. Its contents should be treated according to their sensitivity and potential to influence future behavior.

#### 13.1 Memory Types

| Memory type | Description | Primary security concern |
|---|---|---|
| Working context | Information used during the current reasoning cycle | Exposure through prompts, traces, or tool calls |
| Session memory | Information retained during one conversation or task | Cross-user access and excessive retention |
| Persistent user memory | Information reused across separate sessions for one user | Unauthorized reuse and privacy concerns |
| Shared agent memory | Information available to multiple users or tasks | Cross-user leakage and privilege boundary failures |
| Enterprise knowledge memory | Retrieved or indexed business information | Access-control inconsistency and stale permissions |
| Task state | Progress and intermediate results for a workflow | Unauthorized continuation or tampering |
| Episodic memory | Records of previous actions, outcomes, or experiences | Incorrect reuse and persistent contamination |
| Externalized memory | Information stored in databases, files, vector stores, or other services | Storage security, retention, integrity, and access control |

The same underlying information may be copied into several memory types. Security controls must account for all relevant copies.

#### 13.2 Memory Threat Scenarios

**Cross-user memory leakage:** One user's information appears in another user's session.

**Persistent poisoning:** Malicious or incorrect content is stored and influences later tasks.

**Unauthorized memory modification:** A user or compromised component changes stored context to manipulate future actions.

**Sensitive information retention:** Credentials, personal data, or confidential records remain in memory beyond the approved purpose.

**Stale authorization:** Information remains available through memory after the user's access rights have been revoked.

**Uncontrolled sharing:** A memory intended for one agent or business unit becomes available to another agent with broader permissions.

**Incorrect attribution:** Information from one person, source, or task is associated with another.

**Unsafe task continuation:** A resumed workflow executes based on stale state or outdated authorization.

#### 13.3 Memory Security Control Matrix

| Control | Requirement | Evidence |
|---|---|---|
| Memory classification | Memory contents are classified according to sensitivity | Data classification and design records |
| Ownership | Memory has a defined user, agent, tenant, or business owner | Data model and ownership documentation |
| Session isolation | Session-specific information cannot be accessed by unauthorized sessions | Isolation tests |
| Tenant isolation | Shared services enforce tenant boundaries | Architecture and penetration-test evidence |
| Access control | Read and write access are independently restricted | IAM and application configuration |
| Integrity protection | Unauthorized modifications are prevented or detected | Integrity controls and audit logs |
| Provenance | Stored content retains source and context information where necessary | Metadata and trace records |
| Retention | Memory is retained only for an approved period and purpose | Retention policy and configuration |
| Deletion | Applicable deletion requests and retention rules are enforced across relevant stores | Deletion tests and evidence |
| Revocation | Access is re-evaluated when permissions change | Authorization and revocation tests |
| Sensitive-data minimization | Unnecessary secrets and restricted data are not persisted | Data-flow review and testing |
| Recovery | Memory corruption or poisoning can be investigated and remediated | Recovery and incident procedures |

#### 13.4 Memory Poisoning Assessment

The assessor should test whether an attacker can introduce information that changes future agent behavior.

A controlled scenario might involve a test user attempting to store a false instruction in a persistent knowledge or memory store. The assessor then initiates a separate task and evaluates whether the stored content improperly influences the agent.

The test should examine:
- Whether untrusted content can be written to persistent memory.
- Whether the source and author of stored information are retained.
- Whether the agent treats stored content as data rather than elevated instructions.
- Whether one user's memory can influence another user's tasks.
- Whether suspicious or incorrect memory entries can be identified.
- Whether affected memory can be removed or corrected.
- Whether downstream actions remain subject to independent authorization.

A successful response to the initial conversation does not prove that memory is secure. Persistence introduces a separate attack surface that requires dedicated testing.

        v

        |
        v

        |
        v
Approved Memory Storage
        |

Access-Controlled Retrieval

### 14. Multi-Agent Security, Delegation, and Trust Propagation

Multi-agent systems distribute work among two or more AI agents. A coordinating agent may assign tasks to specialized agents responsible for research, analysis, planning, code execution, customer communication, or system administration.

This architecture can improve modularity and efficiency, but it introduces additional security boundaries. Agents may have different permissions, access different data sources, and rely on outputs produced by other agents.

A secure design must prevent the delegation process from becoming a way to bypass authorization, conceal accountability, or propagate malicious instructions.

#### 14.1 Example Multi-Agent Architecture

```text id="multi-agent-01"
                    USER REQUEST
                         |
                         v
                +------------------+
                | ORCHESTRATOR     |
                | Agent            |
                +--------+---------+
                         |
             +-----------+-----------+
             |           |           |
             v           v           v
      +-----------+ +-----------+ +-----------+
      | Research  | | Analysis  | | Execution |
      | Agent     | | Agent     | | Agent     |
      +-----+-----+ +-----+-----+ +-----+-----+
            |             |             |
            v             v             v
      Knowledge       Analytics      Approved
      Sources         Services       Business Tools
            |             |             |
            +-------------+-------------+
                          |
                          v
                  Result Validation
                          |
                          v
                   Final Response
```

This diagram represents a logical pattern. Actual implementations may use centralized orchestration, event-driven communication, message queues, or peer-to-peer delegation.

#### 14.2 Multi-Agent Threats

| Threat | Description | Potential impact |
|---|---|---|
| Privilege propagation | A low-privilege agent causes a higher-privilege agent to perform an unauthorized operation | Privilege escalation |
| Untrusted instruction forwarding | One agent passes malicious content to another without appropriate validation | Cross-agent prompt injection |
| Identity confusion | The receiving agent cannot establish which user or agent initiated the request | Weak accountability and authorization |
| Delegation scope expansion | A delegated task acquires broader permissions than the original task | Unauthorized access or execution |
| Result tampering | An agent returns false or manipulated findings | Incorrect decisions and downstream actions |
| Circular delegation | Agents repeatedly delegate work to one another | Resource exhaustion and uncontrolled execution |
| Excessive fan-out | One request triggers a large number of agent tasks | Availability degradation and cost escalation |
| Conflicting decisions | Agents apply inconsistent policies or produce contradictory actions | Unsafe or inconsistent outcomes |
| Inadequate traceability | The system cannot reconstruct the complete chain of delegated operations | Investigation and audit failure |
| Compromised agent | A compromised agent influences downstream agents or tools | Expanded security impact |

#### 14.3 Delegation Security Requirements

Each delegation request should carry sufficient information to preserve authorization and accountability.

| Delegation attribute | Required purpose |
|---|---|
| Parent task ID | Connects the delegated operation to the originating workflow |
| Initiating identity | Identifies the user or process that initiated the original request |
| Delegating agent identity | Identifies the agent assigning the work |
| Receiving agent identity | Identifies the agent responsible for the delegated task |
| Task description | Defines the approved purpose and scope |
| Permitted data sources | Restricts accessible information |
| Permitted tools | Restricts available capabilities |
| Permission scope | Defines allowed operations and resources |
| Expiration | Limits how long the delegation remains valid |
| Execution budget | Limits calls, time, and resource consumption |
| Approval requirements | Preserves required human authorization |
| Output contract | Defines the expected result and validation requirements |
| Trace identifier | Supports end-to-end monitoring and auditability |

Delegation should not automatically transfer every permission held by the parent agent. The receiving agent should receive only the authority required for its assigned task.

#### 14.4 Multi-Agent Assessment Scenarios

The assessment should test whether:

1. A research agent can persuade an execution agent to run an unapproved operation.
2. A lower-privilege agent can indirectly access resources available only to a privileged agent.
3. The receiving agent validates the source and authority of incoming instructions.
4. Delegated tasks preserve the originating user's authorization restrictions.
5. One agent can repeatedly spawn tasks without exceeding execution limits.
6. A compromised agent can alter the final result without detection.
7. The system can identify which agent invoked each tool.
8. Revoking an agent's credentials stops further delegated execution.
9. A high-impact action still requires approval when initiated through a sub-agent.
10. The organization can reconstruct the complete execution chain during an incident.

#### 14.5 Required Governance Principle

Every agent-to-agent interaction is a security-relevant transaction.

The organization must establish who initiated the work, which agent delegated it, what authority was granted, which resources were accessed, and what actions were ultimately performed.

A multi-agent design should not be considered secure merely because each individual agent has passed a separate security review. The interactions and delegation paths must also be assessed.

### 15. Model Denial of Service, Resource Abuse, and Uncontrolled Execution

AI agents may repeatedly call models, retrieve large volumes of data, invoke expensive APIs, launch subtasks, or execute long-running workflows.

An attacker may deliberately exploit these behaviors, but excessive consumption can also arise from faulty planning, ambiguous objectives, tool failures, or recursive delegation.

The assessment must determine whether the agent can exhaust resources, degrade service availability, generate uncontrolled costs, or continue operating after a task has exceeded its approved limits.

#### 15.1 Resource Abuse Scenarios

| Scenario | Example | Potential impact |
|---|---|---|
| Excessive model calls | The agent repeatedly retries a task | Cost escalation and capacity consumption |
| Recursive tool invocation | A tool result causes the agent to call the same tool repeatedly | Resource exhaustion |
| Unbounded planning | The agent generates an excessive number of subtasks | Increased latency and cost |
| Retrieval amplification | The agent repeatedly retrieves large datasets | Database load and data exposure |
| Parallel task explosion | One request creates many concurrent subtasks | Service degradation |
| Repeated external API calls | The agent retries failed requests without adequate limits | API throttling or service disruption |
| Large-context abuse | Excessive input and retrieval content increase inference costs | Unexpected expenditure and performance degradation |
| Long-running execution | A task continues without a reliable deadline | Resource contention |
| Repeated transaction attempts | The agent resubmits a business operation after a timeout | Duplicate transactions or inconsistent state |
| Unrestricted code execution | An agent launches resource-intensive or unsafe code | Runtime instability or infrastructure compromise |

#### 15.2 Resource Control Baseline

| Control | Implementation expectation |
|---|---|
| Maximum task duration | Each task has a defined deadline |
| Model-call budget | Each task has a maximum number of model invocations |
| Tool-call budget | Each task has limits on total and per-tool invocations |
| Retry limits | Retries are bounded and follow approved backoff rules |
| Concurrency limits | Parallel execution is constrained |
| Delegation limits | The number and depth of delegated tasks are bounded |
| Token and context limits | Inputs and context sizes remain within approved limits |
| Retrieval limits | Query scope, result count, and retrieval size are constrained |
| API quotas | External and internal service consumption is limited |
| Financial thresholds | Cost ceilings and alert thresholds are defined |
| Circuit breakers | Repeated failures can halt further calls |
| Cancellation | Authorized operators can terminate a running task |
| Idempotency | Repeated requests do not unintentionally repeat state-changing operations |
| Monitoring | Consumption anomalies trigger alerts or protective action |

Limits should be enforced by the orchestration platform, API gateway, runtime, or underlying service—not solely through model instructions.

#### 15.3 Safe Failure Behavior

When a limit is reached, the agent should fail in a controlled and observable manner.

The expected behavior should include:
- Stop additional tool calls when the execution budget is exhausted.
- Avoid continuing a high-impact operation after authorization or validation fails.
- Prevent retries from duplicating completed transactions.
- Preserve enough diagnostic information to investigate the failure.
- Avoid including secrets or sensitive payloads in error messages.
- Clearly communicate incomplete results.
- Allow authorized operators to cancel the task.
- Require explicit authorization before resuming a suspended high-impact workflow.

An agent should not silently bypass a limit by switching to another tool, creating a new sub-agent, or starting a parallel task.

#### 15.4 Resource Abuse Test Cases

| Test ID | Test | Expected result |
|---|---|---|
| RES-01 | Submit a task designed to generate many planning iterations | Execution stops at the defined budget |
| RES-02 | Cause a tool to return repeated errors | Retry policy prevents indefinite loops |
| RES-03 | Trigger a large number of concurrent subtasks | Concurrency limits are enforced |
| RES-04 | Provide an oversized request or retrieval result | Input or context limits are enforced |
| RES-05 | Cause repeated external API calls | Rate limits and quotas prevent uncontrolled consumption |
| RES-06 | Simulate a timeout after a transaction may have succeeded | The agent verifies transaction state before retrying |
| RES-07 | Attempt to bypass limits through delegation | Aggregate task limits remain effective |
| RES-08 | Request a long-running task beyond its approved deadline | The task terminates or transitions to an approved safe state |
| RES-09 | Reach a configured cost threshold | Monitoring and protective controls activate |
| RES-10 | Attempt to continue after cancellation | Further execution is blocked |

### 16. AI Agent Supply Chain, Model Provenance, and Third-Party Dependencies

AI agents often depend on multiple external and internal components, including foundation models, orchestration frameworks, plugins, connectors, tool APIs, software libraries, container images, vector databases, and hosted services.

A vulnerability or compromise in one component can affect the entire agentic system. An agent may also inherit risks from a provider's data processing practices, authentication model, service availability, or security configuration.

The assessment must therefore evaluate the supply chain as part of the complete system rather than treating the model provider as the only third party.

#### 16.1 AI Agent Supply Chain Components

| Component | Representative risk | Assessment focus |
|---|---|---|
| Foundation model provider | Data processing, service compromise, or model changes | Provider assurance, contractual controls, configuration, and change notification |
| Model artifact | Untrusted or compromised model weights | Provenance, integrity, and approved acquisition channels |
| Agent framework | Vulnerabilities in orchestration or tool execution | Dependency security and supported versions |
| Plugins and connectors | Excessive permissions or insecure integration logic | Code review, authorization, and scope restriction |
| External APIs | Weak authentication or compromised service | Third-party assessment and secure API configuration |
| Package dependencies | Vulnerable or malicious software packages | Software composition analysis and dependency governance |
| Container images | Vulnerable base images or unauthorized modifications | Image provenance, scanning, signing, and deployment controls |
| Vector database | Unauthorized data access or weak tenant isolation | Access controls, encryption, and configuration review |
| Hosted memory service | Data retention and isolation weaknesses | Provider assessment and contractual safeguards |
| Agent marketplace | Malicious or inadequately reviewed agent definitions | Approval workflow and provenance verification |
| Model gateway | Insecure routing or policy enforcement | Configuration governance and monitoring |
| Monitoring provider | Sensitive telemetry exposure | Data minimization, access control, and retention review |

#### 16.2 Model and Dependency Provenance

Provenance is the documented origin and history of a component, including its provider, version, integrity, acquisition channel, and relevant changes.

The assessor should verify that the organization can identify:
- Which model or model service is being used.
- Which framework and dependency versions are deployed.
- Which plugins and connectors are enabled.
- Which external services process data.
- Whether components originate from approved sources.
- Whether integrity verification is applied where technically appropriate.
- Whether material provider or version changes are communicated and reviewed.
- Whether vulnerabilities can be associated with affected agent deployments.

For hosted models, traditional artifact-level verification may not be available to the customer. In that case, the assessment should focus on available provider assurances, contractual commitments, service configuration, version controls, change notifications, and compensating controls.

#### 16.3 Third-Party Risk Assessment Questions

| Assessment domain | Questions |
|---|---|
| Security assurance | What independent security assessments or certifications are available, and what scope do they cover? |
| Data processing | What information is processed, stored, retained, or used for provider purposes? |
| Data residency | Where is data processed and stored, subject to applicable contractual and legal requirements? |
| Identity and access | How are service identities, delegated credentials, and administrative permissions protected? |
| Vulnerability management | How are vulnerabilities identified, disclosed, prioritized, and remediated? |
| Change management | How are model, framework, API, and service changes communicated? |
| Availability | What service continuity and recovery commitments exist? |
| Incident notification | How are security incidents communicated to customers? |
| Subprocessors | Which additional parties may process relevant information? |
| Exit and portability | Can data, configurations, and workflows be migrated or securely deleted? |
| Contractual restrictions | Are security, confidentiality, privacy, audit, and incident obligations defined? |
| AI-specific risks | What assurances exist concerning model changes, output limitations, and agent-related integration risks? |

The assessor must distinguish documented contractual commitments from marketing claims or assumptions about provider behavior.

#### 16.4 Dependency Change Management

A change to a model, framework, connector, or external API can alter the agent's security properties even when the business use case remains unchanged.

Material changes should trigger an impact assessment covering:
- Permissions and identity behavior.
- Tool invocation and argument handling.
- Prompt and context construction.
- Data processing and retention.
- Model behavior and output characteristics.
- Security monitoring and audit evidence.
- Compatibility with existing controls.
- Previously identified attack paths.
- Required regression testing.
- Approval and deployment conditions.

**Required control:** The organization should maintain a relationship between each deployed agent, its material dependencies, and the security assessment evidence applicable to those versions or configurations.

### 17. Agent Logging, Monitoring, and Security Detection

AI agent monitoring must capture more than model availability and response errors. The organization needs sufficient visibility to determine what the agent was asked to do, which identities and permissions were involved, which tools were invoked, what decisions were enforced, and what effects occurred in connected systems.

The monitoring design must also protect the sensitive information that may appear in prompts, retrieved context, tool arguments, and generated responses.

#### 17.1 Minimum Security Event Categories

| Event category | Examples | Security purpose |
|---|---|---|
| Authentication | Login success, login failure, identity changes | Detect unauthorized access |
| Authorization | Allowed or denied resource and action requests | Detect privilege misuse and access violations |
| Agent task lifecycle | Task creation, completion, cancellation, failure | Establish execution history |
| Tool invocation | Tool name, operation, target, outcome | Trace external actions |
| Approval workflow | Approval request, approver identity, decision | Demonstrate human oversight |
| Retrieval activity | Source identifier, access decision, retrieval result metadata | Investigate data exposure and injection risks |
| Memory operations | Memory read, write, update, or deletion | Detect unauthorized persistence or tampering |
| Policy enforcement | Rule triggered, action blocked, restriction applied | Verify security controls |
| Resource consumption | Model calls, tool calls, latency, cost, and retries | Detect abuse and runaway execution |
| Delegation | Parent task, receiving agent, delegated scope | Trace multi-agent activity |
| Configuration changes | Model version, tools, permissions, policy updates | Identify unauthorized or material changes |
| Security incidents | Suspected injection, unusual behavior, containment | Support response and investigation |

#### 17.2 Correlation and Traceability

A security event should be linked to the relevant user request, agent task, tool call, and downstream transaction whenever technically feasible.

A useful trace model is:

#### 17.3 Security Monitoring Use Cases

| Detection use case | Indicator | Potential response |
|---|---|---|
| Repeated authorization failures | Repeated denied access attempts | Investigate misuse and apply appropriate rate limits |
| Unusual tool sequence | Unexpected combination of privileged operations | Suspend the task and review the execution trace |
| Prompt-injection indicators | Suspicious instructions combined with abnormal tool activity | Apply policy restrictions and investigate |
| Excessive tool invocation | Tool-call frequency exceeds expected thresholds | Halt execution or enforce a stricter budget |
| Unexpected data egress | Sensitive information is sent to an unapproved destination | Block transmission and initiate incident handling |
| Cross-user access attempts | Requests target resources outside the user's entitlement | Deny access and investigate |
| Abnormal delegation | Excessive agent spawning or privilege escalation attempts | Restrict delegation and inspect the task chain |
| Configuration drift | Unapproved changes to tools, models, or permissions | Revert or suspend the affected configuration |
| Repeated failed transactions | Retries occur after ambiguous outcomes | Reconcile transaction state before further execution |
| Agent activity outside operating hours | Unexpected actions occur outside approved patterns | Validate the event against business requirements |

These are detection candidates, not universal indicators of compromise. Detection logic must account for approved business processes to minimize false positives.

#### 17.4 Logging Privacy and Security

Agent logs may contain personal data, confidential business information, access tokens, system instructions, or details about security controls.

The organization should:
- Minimize collection of sensitive content.
- Redact credentials and authentication secrets.
- Restrict access to detailed traces.
- Apply retention schedules.
- Protect log integrity.
- Record administrative access to sensitive telemetry.
- Separate operational metrics from sensitive conversation content where appropriate.
- Define procedures for legal holds and incident investigations.
- Ensure logging controls do not inadvertently transmit sensitive data to unauthorized monitoring providers.

The objective is to establish accountability without creating a second uncontrolled repository of confidential information.

### 18. LLM and Agent Security Testing

Security testing must determine whether the agent's actual behavior and surrounding technical controls meet the approved requirements.

Traditional testing remains necessary for APIs, infrastructure, authentication, authorization, dependencies, and data stores. Agent-specific testing adds scenarios involving instruction manipulation, tool selection, context contamination, memory, delegation, and autonomous action sequences.

Testing should be based on documented threats and risk priorities rather than relying on a small collection of generic adversarial prompts.

#### 18.1 Security Testing Layers

| Testing layer | Purpose | Example activities |
|---|---|---|
| Architecture review | Identify design weaknesses and missing boundaries | Inspect trust boundaries and execution paths |
| Configuration review | Verify approved security settings | Review tool permissions, model settings, and network access |
| Identity testing | Validate identity and authorization enforcement | Attempt unauthorized resource and action access |
| API testing | Identify weaknesses in tool and connector interfaces | Test authentication, schemas, rate limits, and error handling |
| Prompt-injection testing | Evaluate resistance to instruction manipulation | Test direct and indirect injection scenarios |
| Data protection testing | Verify confidentiality and isolation | Test unauthorized retrieval and cross-user leakage |
| Memory testing | Validate persistence and session boundaries | Test poisoning, isolation, deletion, and revocation |
| Multi-agent testing | Evaluate delegation and trust propagation | Test privilege inheritance and task boundaries |
| Resource testing | Verify execution budgets and availability safeguards | Test loops, retries, concurrency, and task cancellation |
| Adversarial workflow testing | Assess complete action chains | Attempt to manipulate multi-step tasks within an authorized environment |
| Regression testing | Detect security regressions after changes | Re-run approved security test cases |
| Operational testing | Verify detection and containment | Trigger controlled events and test response procedures |

#### 18.2 Risk-Based Test Design

Each test should be linked to an identified threat, a security requirement, and an expected result.

| Test field | Required content |
|---|---|
| Test ID | Unique test identifier |
| Related threat | Threat scenario or risk register reference |
| Security objective | Property being evaluated |
| Preconditions | Required identities, permissions, configuration, and test data |
| Test scenario | Specific action or attack sequence |
| Test environment | Approved environment and scope |
| Expected result | Explicit security outcome |
| Actual result | Observed behavior |
| Evidence | Logs, screenshots, API responses, state changes, or test records |
| Severity | Importance of any observed failure |
| Finding reference | Associated remediation record |
| Retest status | Not retested, passed, failed, or blocked |
| Tester and date | Accountability and reproducibility |

#### 18.3 Negative Testing

Negative testing verifies that the agent rejects prohibited operations.

Examples include:
- Attempting to access a record outside the user's authorization.
- Invoking a tool that is not on the approved allowlist.
- Supplying an invalid or prohibited argument.
- Attempting to execute a high-impact action without required approval.
- Using a revoked credential.
- Attempting to delegate a task beyond the receiving agent's permissions.
- Attempting to continue after a task has been cancelled.
- Reusing an approval after the underlying action parameters change.

A negative test passes only when the prohibited action is blocked and the test confirms that no unintended side effect occurred.

A refusal message alone does not prove that the operation was blocked. The assessor should verify the underlying system state and relevant execution logs.

The assessor should evaluate realistic attack chains that cross multiple components.

Testing must be conducted within authorized boundaries, with appropriate safeguards against unintended changes, sensitive data exposure, or disruption of production services.

### 19. AI Agent Red Teaming and Evidence-Based Validation

AI agent red teaming is a structured exercise designed to discover how an agent and its connected systems may be manipulated into violating security requirements.

It differs from ordinary functional testing because it deliberately explores adversarial behavior, unexpected tool combinations, boundary conditions, and failures in layered defenses.

Red teaming should complement—not replace—architecture reviews, secure development practices, vulnerability management, and formal risk assessment.

#### 19.1 Red Team Objectives

A scoped AI agent red-team exercise may evaluate whether an attacker can:

- Extract confidential information through prompts, retrieval, memory, or outputs.
- Manipulate the agent into invoking unauthorized tools.
- Bypass required approval gates.
- Exploit excessive permissions in connected systems.
- Poison persistent memory or trusted knowledge sources.
- Cause unauthorized actions through delegated agents.
- Exhaust model, tool, or infrastructure resources.
- Abuse error handling or retries to cause duplicate operations.
- Hide consequential actions through inadequate logging.
- Continue execution after access revocation or cancellation.

The exercise should prioritize scenarios with credible business impact.

#### 19.2 Rules of Engagement

Before testing, the assessment owner should document the following.

| Rule | Required definition |
|---|---|
| Authorization | Named authority approving the exercise |
| Scope | Agents, environments, tools, data, and connected systems included |
| Exclusions | Systems and activities that must not be tested |
| Test identities | Approved accounts and permission levels |
| Data restrictions | Prohibited data access, extraction, or modification |
| Action restrictions | Transactions or operational changes that are not permitted |
| Environment | Isolated test, staging, or specifically authorized production scope |
| Time window | Approved testing period |
| Safety limits | Maximum execution budgets and conditions requiring immediate stop |
| Monitoring | Teams and controls responsible for observing the exercise |
| Escalation | Contacts for unexpected exposure or operational impact |
| Evidence handling | Storage, access, redaction, and retention of test artifacts |
| Stop conditions | Circumstances requiring immediate termination |
| Reporting | Required findings, severity, and remediation documentation |

Testing must not exceed the authorization granted. A test that unexpectedly reveals access to sensitive production information should follow the agreed containment and escalation procedure.

#### 19.3 Red Team Scenario Matrix

| Scenario ID | Attack objective | Primary control being evaluated | Success criterion |
|---|---|---|---|
| RT-01 | Cause unauthorized information disclosure | Retrieval and output authorization | No protected information reaches an unauthorized recipient |
| RT-02 | Invoke an unapproved tool | Tool allowlisting | The invocation is rejected |
| RT-03 | Modify a restricted record | Resource and action authorization | The change is blocked and no state change occurs |
| RT-04 | Bypass human approval | Approval enforcement | Execution cannot proceed without valid authorization |
| RT-05 | Poison persistent memory | Memory integrity and provenance | Malicious content cannot improperly control future tasks |
| RT-06 | Escalate privileges through delegation | Delegation boundaries | The receiving agent cannot exceed authorized scope |
| RT-07 | Trigger excessive resource consumption | Execution budgets and quotas | Limits activate before unacceptable impact |
| RT-08 | Conceal or obscure an action | Logging and traceability | The relevant events remain attributable and reconstructable |
| RT-09 | Abuse retries after an ambiguous transaction | Idempotency and state reconciliation | Duplicate or unauthorized transactions are prevented |
| RT-10 | Continue after emergency cancellation | Runtime containment | Further execution is stopped within the defined response target |

#### 19.4 Evidence Requirements

Each test should produce evidence sufficient for an independent reviewer to understand what was tested and whether the control worked.

Acceptable evidence may include:
- Architecture and configuration records.
- Sanitized request and response traces.
- Tool invocation records.
- Authorization decisions.
- Before-and-after system state.
- Human approval records.
- Security alerts.
- Test scripts or reproducible test procedures.
- Relevant API responses.
- Retest results.

Evidence should be protected according to its sensitivity. A test report should not reproduce credentials, confidential records, or harmful operational details unnecessarily.

#### 19.5 Distinguishing Model Refusal from Security Enforcement

A key assessment distinction is whether the agent merely declines a request or whether the system technically prevents the prohibited action.

| Observation | Interpretation | Required verification |
|---|---|---|
| Agent says it cannot perform an action | The model expressed a refusal | Verify that no tool was invoked |
| Agent generates an unsafe tool request, but the gateway blocks it | Independent control operated as intended | Verify the denial and absence of side effects |
| Agent invokes a tool, but the downstream system rejects it | Downstream authorization prevented the operation | Verify the rejection and final state |
| Agent reports that an action succeeded | A claim has been generated | Confirm the actual transaction outcome |
| Agent reports that an action failed | A claim has been generated | Check whether a partial or completed side effect occurred |
| Agent refuses a request, but an asynchronous task continues | The conversational response did not stop execution | Verify cancellation and runtime state |

**Evidence-based principle:** A model's statement about what it did is not sufficient proof that the underlying operation occurred—or that it did not occur.

The assessor must use independent system evidence to validate security outcomes.

### 20. Core Principle — Validate the Agent Under Adversarial and Realistic Operating Conditions

AI agent security depends on the combined effectiveness of tool controls, authorization, autonomy restrictions, memory protection, delegation boundaries, resource limits, supply-chain governance, monitoring, and incident containment.

A control that works in an isolated demonstration may fail when the agent receives malicious retrieved content, invokes several tools in sequence, delegates a task, or retries an operation after a partial failure.

The assessment must therefore evaluate both individual components and complete execution paths.

The following distinctions are fundamental:

- **Tool availability versus tool authorization:** A registered tool must not be available for every operation or every user.
- **Human confirmation versus enforceable approval:** Approval must be authenticated, specific, and bound to the action being executed.
- **Session context versus persistent memory:** Information that is safe to use temporarily may be unsafe to retain or reuse.
- **Individual agent security versus multi-agent security:** Each agent's controls must be complemented by controls over delegation and communication.
- **Model refusal versus technical prevention:** Security must not depend exclusively on the model choosing to behave correctly.
- **Resource monitoring versus resource enforcement:** Alerts alone may be insufficient when an agent can exhaust resources before an operator responds.
- **Provider assurance versus deployed-system assurance:** Third-party certifications do not replace validation of the organization's actual integration and configuration.
- **Test execution versus verified outcome:** A test is not complete until the assessor verifies the actual system state and relevant evidence.

#### Final Assessment Principle

**An AI agent must be constrained by enforceable security controls at every point where it can access data, invoke tools, delegate work, consume resources, or change external systems. Those controls must remain effective even when the agent receives malicious instructions, produces incorrect decisions, or behaves outside its intended operating pattern.**

A defensible assessment demonstrates that unauthorized actions are prevented, permitted actions remain within approved boundaries, failures can be detected and contained, and the resulting evidence supports a documented risk decision.

## Part 3 — Security Control Baseline, Secure Deployment, Incident Response, and Operational Assurance

### 21. AI Agent Security Control Baseline and Defense-in-Depth

An enterprise AI agent requires a documented security control baseline that defines the minimum safeguards necessary for its approved operating environment. The baseline should address the complete agentic system, including the model, orchestration framework, tools, identities, data sources, memory, execution environment, connected applications, and operational monitoring.

The purpose of the baseline is to translate identified risks into enforceable security requirements that can be implemented, tested, monitored, and audited.

A control baseline should not assume that the model will always interpret instructions correctly. It should establish security boundaries that remain effective when the model produces an incorrect response, receives malicious content, selects an inappropriate tool, or attempts an action outside its intended purpose.

#### 21.1 Core Security Control Domains

| Control domain | Security objective | Example controls |
|---|---|---|
| Governance and accountability | Establish ownership and approval authority | Named business owner, technical owner, risk owner, and approval record |
| Identity and access management | Prevent unauthorized access and privilege misuse | Workload identity, least privilege, scoped tokens, and resource-level authorization |
| Data protection | Protect sensitive information throughout processing | Data classification, minimization, encryption, retention controls, and access-aware retrieval |
| Model and instruction security | Reduce manipulation and configuration risks | Approved configurations, controlled system instructions, and adversarial testing |
| Tool security | Restrict the agent's ability to affect external systems | Tool allowlisting, schema validation, action-level authorization, and execution limits |
| Memory security | Protect stored context and prevent cross-session leakage | Memory isolation, provenance, retention controls, and integrity monitoring |
| Application security | Protect APIs and agent interfaces | Secure development, authentication, input validation, and API security testing |
| Infrastructure security | Protect the execution environment | Network segmentation, hardened workloads, patching, and runtime restrictions |
| Human oversight | Ensure appropriate control of consequential actions | Approval gates, separation of duties, and escalation procedures |
| Monitoring and detection | Identify abnormal or unauthorized behavior | Correlated logs, behavioral alerts, and policy-violation detection |
| Incident response | Contain and recover from security incidents | Emergency stop, credential revocation, investigation, and recovery procedures |
| Third-party risk management | Manage external dependencies and providers | Due diligence, contractual safeguards, dependency monitoring, and exit planning |
| Change management | Prevent unreviewed changes from weakening controls | Version control, impact assessment, regression testing, and release approval |
| Assurance and audit | Demonstrate that controls operate effectively | Test evidence, control ownership, independent review, and remediation tracking |

The baseline should identify which controls are mandatory, which are conditional, and which may be justified as not applicable. Exceptions must be documented and approved through the organization's risk management process.

#### 21.2 Preventive, Detective, and Corrective Controls

Defense-in-depth requires multiple control layers with different purposes.

| Control category | Purpose | AI agent example |
|---|---|---|
| Preventive | Stop unauthorized or unsafe activity before it occurs | Tool allowlisting, authorization checks, and restricted execution environments |
| Detective | Identify suspicious activity or control failures | Alerts for abnormal tool sequences or repeated authorization failures |
| Corrective | Restore a secure state after an incident or failure | Revoke credentials, remove poisoned memory, and restore approved configuration |
| Recovery | Restore approved service operation | Rebuild the runtime, restore validated state, and verify control effectiveness |
| Governance | Ensure accountability and risk-based decisions | Formal approval, risk acceptance, and independent assurance |

A mature implementation does not depend on a single control category.

For example, tool authorization may prevent an unauthorized operation, monitoring may identify repeated attempts to bypass the restriction, and incident response may disable the affected integration if the attempts indicate compromise.

#### 21.3 Minimum Control Baseline by Agent Risk

The required baseline should be proportionate to the agent's capabilities, data access, exposure, autonomy, and potential business impact.

| Risk tier | Illustrative agent profile | Baseline expectations |
|---|---|---|
| Tier 1 — Low | Internal assistant restricted to approved public or low-sensitivity information | Authentication where required, basic access controls, approved configuration, and operational logging |
| Tier 2 — Moderate | Internal agent accessing non-public information or creating draft records | Least privilege, access-aware retrieval, data minimization, tool restrictions, and security testing |
| Tier 3 — High | Agent modifying customer records or executing consequential workflows | Strong resource-level authorization, action validation, approval gates for designated actions, detailed auditability, and adversarial testing |
| Tier 4 — Critical | Agent controlling highly privileged systems, sensitive transactions, or critical operations | Enhanced isolation, strict execution boundaries, independent authorization, robust human oversight, tested emergency containment, and formal security approval |

These tiers are a proposed governance model, not a universal industry classification. The organization must define objective classification criteria and map them to its enterprise risk framework.

### 22. Secure Design for AI Agent Components

Secure design translates the security baseline into an architecture that restricts the agent's capabilities and limits the consequences of incorrect or malicious behavior.

The central design objective is to prevent the model from becoming an unrestricted authority over external systems.

The model may propose a plan, select from approved capabilities, and interpret results. However, trusted application components should determine whether an action is permitted, validate its parameters, and enforce the relevant authorization and business rules.

#### 22.1 Secure Component Responsibilities

| Component | Primary security responsibility | Design requirement |
|---|---|---|
| User interface | Collect requests and present results | Authenticate users where required and prevent unauthorized access to session data |
| Identity provider | Establish identity and authentication status | Apply approved authentication and session policies |
| Policy enforcement layer | Determine whether requested actions are permitted | Enforce rules independently of model-generated instructions |
| Agent orchestrator | Coordinate planning and execution | Enforce execution budgets, tool restrictions, and task boundaries |
| Model interface | Submit approved context and obtain model outputs | Minimize sensitive inputs and apply approved provider configuration |
| Context builder | Assemble instructions, memory, and retrieved content | Preserve provenance and distinguish trusted policy from untrusted content |
| Retrieval service | Find relevant enterprise information | Enforce access restrictions and return only authorized content |
| Memory service | Store and retrieve approved context | Apply isolation, retention, integrity, and access controls |
| Tool gateway | Mediate access to external capabilities | Validate tool names, arguments, authorization, and execution constraints |
| Downstream application | Enforce its own business and security rules | Reject unauthorized or invalid operations regardless of the agent's request |
| Monitoring platform | Capture security-relevant activity | Maintain traceability while protecting sensitive telemetry |
| Administrative interface | Manage agent configuration and permissions | Restrict administrative actions and record changes |

Responsibilities should be explicitly assigned. A design in which every component assumes that another component performs authorization creates a significant risk of control gaps.

#### 22.2 The Policy Enforcement Point

A policy enforcement point is a component that applies security decisions to requests before the requested operation is allowed to proceed.

For AI agents, this may be implemented through an API gateway, tool gateway, authorization service, application middleware, or a combination of these components.

A policy decision may depend on:

- The authenticated user.
- The executing agent identity.
- The target resource.
- The requested operation.
- The sensitivity of the data.
- The business purpose.
- The transaction amount or impact.
- The current approval status.
- The environment in which the action will execute.
- Applicable time, location, or operational restrictions.

The decision should not depend solely on whether the model claims that an operation is legitimate.

#### 22.3 Secure Action Execution Pattern

```text
1. Receive the requested action
             |
             v
2. Identify the initiating user and agent
             |
             v
3. Validate the task and business purpose
             |
             v
4. Validate the tool and its parameters
             |
             v
5. Evaluate resource and action permissions
             |
             v
6. Check transaction limits and policy restrictions
             |
             v
7. Determine whether approval is required
             |
             v
8. Execute through an authorized component
             |
             v
9. Verify the resulting system state
             |
             v
10. Record the action and evidence
```

The workflow should fail safely if a required authorization service is unavailable, an approval cannot be verified, or a security-critical validation fails.

For certain low-risk functions, the organization may approve alternative failure behavior. However, a temporary infrastructure failure should not silently disable a mandatory security restriction.

#### 22.4 Secure-by-Design Requirements

| Requirement | Implementation approach | Verification method |
|---|---|---|
| Least functionality | Expose only the capabilities required for the approved use case | Tool inventory and permission review |
| Least privilege | Limit each identity to necessary resources and actions | IAM review and authorization tests |
| Separation of duties | Separate sensitive execution from approval where required | Workflow and role review |
| Fail-secure authorization | Reject protected operations when mandatory authorization cannot be established | Failure-injection testing |
| Explicit trust boundaries | Identify where data and instructions cross components | Architecture review |
| Secure defaults | Disable unapproved tools and optional capabilities by default | Configuration inspection |
| Input validation | Enforce schemas, formats, and business constraints | Negative and boundary testing |
| Output validation | Validate data before downstream execution or disclosure | Integration tests |
| Isolation | Separate environments, tenants, sessions, and privileges where required | Isolation testing |
| Bounded execution | Limit duration, tool calls, delegation, and resource use | Runtime tests |
| Independent authorization | Enforce access controls outside the model | End-to-end authorization tests |
| Recoverability | Support containment and restoration of an approved state | Recovery exercises |

#### 22.5 Safe Degradation

A secure agent should have a defined behavior when a model, tool, policy service, retrieval system, or identity provider becomes unavailable.

Examples include:
- Switching to read-only functionality when write authorization cannot be verified.
- Providing a draft instead of sending a message when a required approval service is unavailable.
- Suspending a transaction when its completion status is uncertain.
- Disabling an affected connector when its security configuration cannot be validated.
- Requiring a human operator to complete a high-impact task through an approved alternative process.

Safe degradation should preserve critical security properties while allowing appropriate business continuity.

### 23. Data Governance, Privacy, and Retention Controls

AI agents may process personal data, confidential corporate information, commercial records, authentication metadata, and information inferred from user interactions.

Data governance must therefore address the complete lifecycle of information processed by the agent, including collection, retrieval, context assembly, model processing, tool execution, memory, logging, sharing, retention, and deletion.

The objective is to ensure that the agent processes information for an authorized purpose and does not create uncontrolled copies or disclosure paths.

#### 23.1 Data Governance Requirements

| Requirement | Security and governance objective |
|---|---|
| Defined purpose | Establish why each data category is required |
| Data minimization | Restrict collection and processing to what is necessary |
| Classification | Apply appropriate controls based on sensitivity |
| Access authorization | Limit data access to authorized identities and purposes |
| Source integrity | Maintain confidence in the origin and accuracy of relevant data |
| Processing transparency | Document where information is processed and which services receive it |
| Retention limitation | Retain data only for approved purposes and periods |
| Secure deletion | Remove information according to approved deletion requirements |
| Data subject rights handling | Support applicable legal obligations concerning personal data |
| Third-party governance | Assess external data processors and service providers |
| Logging minimization | Avoid unnecessary duplication of sensitive information in telemetry |
| Data residency management | Address applicable legal, contractual, and organizational location requirements |
| Breach response | Identify and investigate unauthorized disclosure or access |
| Accountability | Maintain evidence of data governance decisions and controls |

The organization must determine the applicable legal obligations based on its role, jurisdiction, data categories, and deployment model.

#### 23.2 Data Lifecycle Control Matrix

| Lifecycle stage | Principal risk | Required safeguard | Example evidence |
|---|---|---|---|
| Collection | Excessive or unauthorized data collection | Purpose limitation and collection controls | Data-flow inventory |
| Ingestion | Untrusted or incorrectly classified data | Source validation and classification | Ingestion rules and source approvals |
| Indexing | Sensitive information enters an inadequately protected index | Access controls and indexing restrictions | Index configuration and access tests |
| Retrieval | Unauthorized information enters model context | Authorization-aware retrieval | Negative-test results |
| Context assembly | Excessive information is supplied to the model | Context minimization and data filtering | Design review and test evidence |
| Model processing | Information is transmitted to an unapproved service | Provider and data-processing controls | Configuration and contractual evidence |
| Tool execution | Sensitive information is passed to an inappropriate destination | Destination validation and purpose restrictions | Tool gateway logs |
| Memory | Information persists beyond its intended use | Retention, isolation, and deletion controls | Memory configuration and deletion tests |
| Logging | Sensitive information is duplicated in telemetry | Redaction and access restrictions | Logging configuration |
| Sharing | Information reaches unauthorized recipients | Output authorization and recipient validation | Disclosure tests |
| Archival | Data remains available without appropriate safeguards | Controlled archival and access restrictions | Retention records |
| Deletion | Copies remain in indexes, caches, or downstream stores | Verified deletion procedures | Deletion evidence and exception records |

#### 23.3 Privacy Impact and Data Protection Assessment

Where an agent processes personal data, the organization should determine whether a privacy impact assessment or a formal data protection impact assessment is required.

The assessment should consider:
- The categories and volume of personal data.
- The purposes and legal basis for processing, where applicable.
- Whether sensitive or special-category data is involved.
- The people affected by the system.
- Whether decisions are made or materially supported by the agent.
- Whether the agent creates profiles, predictions, or inferred attributes.
- Whether data is transferred to external providers.
- Whether retention and deletion controls are adequate.
- Whether individuals can exercise applicable rights.
- Whether the processing creates elevated risks to individuals.
- Whether human oversight and challenge mechanisms are appropriate.

A privacy assessment and an AI agent security assessment are related but distinct. Privacy compliance does not automatically demonstrate technical security, and technical security controls do not by themselves establish lawful processing.

#### 23.4 Data Leakage Through Agent Outputs

An agent may disclose information through a response, generated document, tool invocation, email, summary, or delegated task.

Output security must therefore evaluate the destination and authorization of the disclosure, not only the accuracy of the generated content.

For example, an agent may legitimately retrieve a confidential internal report for an authorized employee but must not automatically include the report's sensitive contents in an email to an external recipient.

Required controls may include:
- Recipient authorization checks.
- Data classification-aware output policies.
- Sensitive-data detection and redaction.
- Restrictions on external transmission.
- Explicit confirmation for high-impact disclosures.
- Review of generated documents before publication.
- Independent authorization for sharing links or files.
- Logging of material disclosures.

A model's assessment that a recipient appears trustworthy is not a substitute for a verifiable authorization decision.

#### 23.5 Retention and Deletion Verification

Deletion requirements may apply to several separate storage locations:
- Session state.
- Persistent memory.
- Vector indexes.
- Source documents.
- Application databases.
- Tool execution records.
- Observability platforms.
- Backups and archives.
- External providers' systems.

The organization should define which locations must be deleted, which may retain records under an approved legal or operational exception, and how deletion is verified.

Where immediate deletion from backups or immutable logs is technically or legally constrained, the limitation should be documented, access should remain controlled, and the applicable retention or deletion policy should determine the permitted treatment.

### 24. Identity and Access Control for Agent Tools and Integrations

Agent tools should operate under an explicit identity and authorization model. An agent's ability to reason about a task does not establish its authority to execute the task.

This control domain focuses on the security of tool credentials, delegated access, API permissions, service identities, and the relationship between the requesting user and the executing agent.

#### 24.1 Identity Architecture Requirements

A secure implementation should answer the following questions:

1. Who authenticated the original request?
2. Which identity executes the tool call?
3. Is the initiating user's authorization preserved?
4. Which permissions belong to the agent itself?
5. Can the agent impersonate another identity?
6. How are credentials issued, stored, rotated, and revoked?
7. Can the agent obtain permissions dynamically?
8. Are privileged actions separated from routine operations?
9. Can an administrator identify which identity performed each action?
10. What happens when the user's access is revoked during a long-running task?

The answers should be documented for each high-impact integration.

#### 24.2 Credential Security Controls

| Control | Requirement |
|---|---|
| Centralized secret management | Store credentials in an approved secret-management service or equivalent protected mechanism |
| No model-context exposure | Prevent raw secrets from being inserted into prompts, memory, or ordinary model-visible tool output |
| Short-lived credentials | Use limited-duration credentials where supported and appropriate |
| Narrow permission scopes | Restrict tokens to required resources and operations |
| Rotation | Rotate credentials according to policy and risk |
| Revocation | Support prompt revocation of compromised or unnecessary credentials |
| Workload identity | Prefer managed or federated identities where suitable |
| Environment separation | Prevent development credentials from granting production access |
| Administrative access control | Restrict who can retrieve or modify credentials |
| Auditability | Record relevant credential lifecycle and privileged access events |
| Delegation constraints | Prevent unrestricted forwarding or reuse of credentials across agents |
| Secret scanning | Detect accidentally committed or exposed credentials where applicable |

Credentials should not be placed in system instructions as a convenient way to make them available to the model. Tool implementations should obtain secrets through controlled execution mechanisms.

#### 24.3 Authorization Matrix for Agent Integrations

| Integration | Read access | Write access | Administrative access | Required restrictions |
|---|---|---|---|---|
| CRM | Approved customer and case records | Specific permitted fields and operations | Disabled unless explicitly justified | Record-level authorization and field allowlisting |
| ERP | Required inventory or order data | Approved transaction operations | Disabled by default | Transaction limits and business-rule validation |
| Email | Approved templates or authorized messages | Send within defined scope | Mailbox administration restricted | Recipient validation and sending limits |
| Knowledge base | Authorized documents | Limited or no write access | Restricted | Source-level permissions and provenance |
| Cloud management | Required resource metadata | Specific approved changes | Restricted | Workload identity, policy enforcement, and change approval |
| Security operations platform | Approved alerts and evidence | Controlled response actions | Restricted | Human oversight for designated containment actions |
| Code execution environment | Approved test inputs and files | Controlled output artifacts | Restricted | Sandboxing, network restrictions, and resource limits |

This matrix is illustrative. Actual access rights should be derived from the approved business process and the organization's security architecture.

#### 24.4 Privilege Escalation Assessment

The assessor should test whether the agent can:
- Use a tool with permissions broader than the requesting user's authority.
- Reuse another user's token or session.
- Change its own permissions.
- Request or obtain new credentials without approval.
- Access production resources using development credentials.
- Invoke administrative functions through an ordinary business connector.
- Continue executing after a credential is revoked.
- Use one integration to bypass restrictions imposed by another.
- Delegate a task to an agent with excessive privileges.
- Perform an unauthorized action through a downstream service that trusts the agent's identity.

Testing should verify both the immediate authorization result and the final state of the affected system.

#### 24.5 Separation of Duties

For sensitive business operations, the agent's ability to prepare a transaction should be separated from the authority to approve or finalize it when required by policy.

For example, an agent may collect evidence and prepare a refund request, while an authorized human or independent approval service decides whether the refund may proceed.

Separation of duties is especially important when the same workflow involves:
- Creating and approving financial transactions.
- Requesting and granting privileged access.
- Preparing and executing security configuration changes.
- Modifying and validating critical records.
- Initiating and closing security incidents.

The agent must not be able to satisfy both sides of a mandatory approval process simply by generating a second tool request under its own control.

### 25. Secure Deployment, Environment Segregation, and Runtime Protection

AI agent security depends on the infrastructure that hosts the model integration, orchestration logic, memory, tools, and supporting services.

A well-designed agent can still be compromised if its runtime permits unrestricted network access, exposes administrative interfaces, executes untrusted code without isolation, or uses credentials that grant broad access to enterprise resources.

The assessment should establish whether deployment controls are appropriate for the agent's risk classification and operational environment.

#### 25.1 Environment Segregation

Development, testing, staging, and production environments should be separated according to the organization's security requirements.

| Environment | Intended purpose | Required safeguards |
|---|---|---|
| Development | Build and modify agent components | Restricted data, controlled dependencies, and non-production credentials |
| Testing | Validate functionality and security | Approved test data, isolated resources, and controlled adversarial testing |
| Staging | Validate production-like configuration | Restricted access, representative configuration, and release validation |
| Production | Deliver approved business functionality | Hardened deployment, controlled changes, least privilege, monitoring, and incident response |

Separation must extend beyond naming conventions. Environments should use appropriately isolated identities, secrets, network permissions, data stores, and execution resources.

Production data should not be copied into lower environments without an approved purpose and appropriate safeguards.

#### 25.2 Network Security

The runtime should have only the network connectivity necessary for its approved purpose.

Relevant controls include:
- Explicit outbound destination restrictions.
- Inbound access restrictions.
- Network segmentation.
- Controlled access to internal APIs.
- Restrictions on access to cloud metadata services and administrative endpoints.
- Private connectivity where justified.
- DNS and domain controls where appropriate.
- Monitoring of unusual outbound traffic.
- Restrictions on arbitrary downloads and external code retrieval.
- Protection of management and orchestration interfaces.

Network controls are particularly important for agents that can execute code, browse external content, or invoke dynamic tools.

#### 25.3 Runtime Isolation and Execution Controls

Where an agent can execute code or process untrusted files, the assessment should verify that the execution environment limits potential damage.

| Control | Security purpose |
|---|---|
| Sandboxing | Restrict the effect of unsafe code or file processing |
| Non-privileged execution | Reduce the impact of runtime compromise |
| Filesystem restrictions | Prevent unauthorized access to sensitive files |
| Network restrictions | Limit unauthorized external communication |
| Resource quotas | Prevent excessive CPU, memory, storage, or execution consumption |
| Process isolation | Separate tasks and reduce cross-task interference |
| Ephemeral environments | Reduce persistence between tasks where suitable |
| Image and dependency scanning | Identify known vulnerabilities |
| Runtime monitoring | Detect suspicious execution behavior |
| Controlled artifact handling | Prevent untrusted outputs from becoming executable inputs |
| Emergency termination | Stop unsafe or runaway tasks |
| Secure cleanup | Remove temporary files and task-specific artifacts according to policy |

Not every agent requires a code execution environment. Controls should be selected according to the actual capabilities and architecture.

#### 25.4 Secure Configuration Management

The following configuration items should be governed:
- Model provider and model identifier.
- Tool registry and enabled capabilities.
- Identity assignments and permission scopes.
- System instructions and policy configuration.
- Retrieval sources and access filters.
- Memory settings and retention.
- Network destinations.
- Execution budgets and concurrency limits.
- Logging and monitoring settings.
- Human approval requirements.
- Administrative interfaces.
- Third-party integrations.

Configuration changes should be attributable, reviewed, and recoverable.

The assessment should verify that unauthorized users cannot weaken the agent's restrictions by modifying configuration, changing tool descriptions, adding connectors, disabling logging, or altering approval rules.

#### 25.5 Deployment Security Verification Checklist

| Check | Expected evidence |
|---|---|
| Only approved components are deployed | Deployment manifests and component inventory |
| Production uses approved identities | IAM configuration and deployment records |
| Secrets are managed securely | Secret-management configuration and access logs |
| Network access is restricted | Network rules and connectivity test results |
| Runtime permissions are limited | Container, workload, or execution configuration |
| Dependencies are reviewed | Dependency inventory and vulnerability results |
| Security configuration is version-controlled | Change history and approved release records |
| Administrative access is restricted | Role assignments and access reviews |
| Logging is enabled and protected | Monitoring configuration and sample traces |
| Emergency termination is available | Runbook and test evidence |
| Recovery procedures are documented | Recovery plan and exercise results |
| Production changes are controlled | Release approvals and deployment evidence |

A deployment should not be considered production-ready until material security requirements have been verified and unresolved risks have been reviewed through the appropriate approval process.

### 26. Change Management, Model Versioning, and Security Regression Testing

AI agent security can change when the model, prompts, tools, data sources, memory configuration, dependencies, permissions, or orchestration logic changes.

A change that improves task performance may also alter tool-selection behavior, output patterns, execution frequency, or the effectiveness of existing safeguards.

Consequently, AI agent change management must consider both traditional software changes and changes in model behavior or agent capabilities.

#### 26.1 Changes That May Require Reassessment

| Change category | Example | Potential security effect |
|---|---|---|
| Model | Change the model provider or model version | Different instruction-following behavior or tool-selection patterns |
| System instructions | Modify operational or security instructions | Changed task boundaries or policy interpretation |
| Tools | Add a new connector or function | Expanded attack surface and permissions |
| Permissions | Grant additional API scopes | Increased impact of misuse |
| Retrieval | Add a new document source | New sensitive data or prompt-injection exposure |
| Memory | Enable persistent memory | Increased persistence and cross-session risk |
| Orchestration | Change planning or retry logic | Different execution paths or resource consumption |
| Autonomy | Allow additional actions without human approval | Increased operational impact |
| Infrastructure | Change runtime, network, or hosting configuration | New exposure or isolation weaknesses |
| Dependencies | Update an orchestration framework or plugin | New vulnerabilities or behavioral changes |
| Logging | Change telemetry collection or retention | Increased exposure of sensitive data |
| Business process | Expand the agent to another department | New users, data, permissions, and legal requirements |
| Delegation | Introduce another agent | New trust boundaries and privilege propagation paths |

#### 26.2 Change Classification

A practical classification can help determine the level of review required.

| Change class | Description | Typical review |
|---|---|---|
| Class 1 — Minor | Change with no material effect on security boundaries or permissions | Documented review and targeted regression tests |
| Class 2 — Material | Change that affects behavior, data handling, dependencies, or a limited set of capabilities | Security impact assessment and focused security testing |
| Class 3 — Major | Change that expands privileges, introduces high-impact tools, changes deployment architecture, or materially increases autonomy | Formal reassessment, adversarial testing, and approval before deployment |
| Class 4 — Emergency | Urgent change required to address an active vulnerability or incident | Emergency change process, minimum safe validation, explicit authorization, and retrospective review |

These classifications are illustrative and should be aligned with the organization's established change management process.

#### 26.3 Model and Configuration Version Records

Each production agent should have a record of its material security-relevant configuration.

| Field | Purpose |
|---|---|
| Agent version | Identifies the deployed agent release |
| Model identifier and version | Identifies the model configuration in use |
| Prompt or policy version | Identifies the approved instruction and policy configuration |
| Orchestration version | Identifies the execution framework |
| Tool registry version | Identifies available capabilities |
| Permission configuration | Records approved access rights |
| Retrieval configuration | Records authorized sources and filters |
| Memory configuration | Records persistence and isolation settings |
| Dependency inventory | Records relevant software components |
| Test suite version | Identifies the security tests applied |
| Approval record | Establishes authorization for deployment |
| Deployment timestamp | Supports event correlation |
| Rollback target | Identifies a known approved version where rollback is supported |

Where a provider controls model updates, the organization should record the model identifier and available version information, monitor provider change notices, and establish compensating controls if exact version pinning is unavailable.

#### 26.4 Security Regression Testing

Regression testing should verify that existing controls continue to operate after changes.

A regression suite should include tests for:
- Unauthorized data retrieval.
- Prompt-injection resistance and impact containment.
- Tool allowlisting.
- Resource-level and action-level authorization.
- Human approval enforcement.
- Memory isolation and retention.
- Delegation boundaries.
- Resource limits and retry handling.
- Logging and traceability.
- Emergency cancellation.
- Sensitive output handling.
- Recovery from tool or model failures.

Tests should be prioritized according to risk and change impact. A change to the model version may require behavioral and adversarial regression testing, while a change to an API permission scope requires focused authorization testing and potentially broader end-to-end validation.

#### 26.5 Release Approval Criteria

A production release should meet documented criteria, such as:

1. The change has an accountable owner and an approved business purpose.
2. The security impact assessment is complete.
3. Mandatory controls have been verified.
4. Required regression and adversarial tests have passed.
5. High-severity findings have been resolved or explicitly handled under approved policy.
6. Material residual risks have been reviewed by authorized risk owners.
7. Monitoring and incident-response arrangements are ready.
8. Rollback or containment arrangements are documented.
9. The deployed configuration matches the approved release.
10. Evidence is retained for audit and future reassessment.

A release should not be approved merely because functional acceptance tests pass.

### 27. AI Agent Incident Response and Containment

An AI agent security incident may involve unauthorized data access, prompt-injection exploitation, compromised credentials, unsafe tool execution, malicious memory, excessive resource consumption, or unintended changes to connected systems.

Incident response must account for the fact that an agent may continue executing tasks, retry failed operations, delegate work, or retain state even after a user-facing conversation has ended.

The organization should define how to detect, investigate, contain, eradicate, recover from, and learn from agent-related incidents.

#### 27.1 AI Agent Incident Categories

| Incident category | Example | Potential impact |
|---|---|---|
| Unauthorized disclosure | Agent returns confidential information to an unauthorized user | Privacy, confidentiality, or regulatory impact |
| Unauthorized action | Agent modifies a record without required authority | Integrity and business-process compromise |
| Prompt-injection exploitation | Malicious content influences a consequential action | Policy bypass or data exposure |
| Credential compromise | A tool token is exposed or misused | Unauthorized access to connected systems |
| Memory poisoning | Persistent context is manipulated | Repeated unsafe behavior |
| Agent delegation abuse | A sub-agent performs an unauthorized operation | Expanded compromise |
| Resource abuse | The agent generates excessive calls or tasks | Availability degradation and financial loss |
| Supply-chain compromise | A vulnerable or malicious dependency affects the agent | Runtime or application compromise |
| Monitoring failure | Consequential actions cannot be reconstructed | Delayed response and audit failure |
| Configuration compromise | Unauthorized changes weaken security controls | Persistent exposure |
| Unsafe output processing | Generated content is executed or trusted without validation | Code execution or data integrity compromise |
| Unauthorized external communication | Agent transmits sensitive data to an unapproved destination | Confidentiality and compliance impact |

#### 27.2 Incident Response Lifecycle

```text id="incident-lifecycle-01"
Detection or Report
        |
        v
Initial Triage and Severity
        |
        v
Containment Decision
        |
        v
Stop Tasks / Disable Tools / Revoke Access
        |
        v
Preserve Evidence and Establish Scope
        |
        v
Investigate Root Cause and Impact
        |
        v
Eradicate Cause and Correct Controls
        |
        v
Recover Under Controlled Conditions
        |
        v
Validate Security Effectiveness
        |
        v
Risk Review and Lessons Learned
```

The exact sequence may vary. For example, immediate containment may be necessary before full evidence collection if the agent is actively exposing sensitive information or making unauthorized changes.

#### 27.3 Containment Options

| Containment action | Purpose | Important consideration |
|---|---|---|
| Cancel the active task | Stop further execution | Confirm that asynchronous or delegated tasks also stop |
| Disable a tool | Prevent further use of a compromised capability | Verify that alternative connectors cannot perform the same operation |
| Revoke credentials | Remove access from compromised identities | Identify all tokens, sessions, and dependent tasks |
| Restrict agent permissions | Reduce the available attack surface | Confirm that policy changes are effective at runtime |
| Disable persistent memory writes | Prevent further contamination | Preserve evidence before remediation where appropriate |
| Isolate the runtime | Limit network or system access | Avoid disrupting unrelated critical services unnecessarily |
| Block external destinations | Prevent further unauthorized transmission | Identify approved dependencies that must remain accessible |
| Suspend deployment | Stop new requests from reaching the agent | Account for existing in-flight tasks |
| Restrict affected users or sessions | Limit suspected misuse | Preserve legitimate access where safe |
| Invoke downstream controls | Freeze transactions or reverse unauthorized changes where possible | Coordinate with system owners and preserve transaction evidence |

Containment must be based on the incident's scope and impact. Disabling the conversational interface alone may not stop background tasks, scheduled jobs, or delegated agents.

#### 27.4 Investigation Evidence

The incident team should attempt to reconstruct:
- The initiating identity and request.
- The agent and model configuration in use.
- Relevant prompts and retrieved-content metadata, subject to data access rules.
- The tool invocation sequence.
- Authorization and approval decisions.
- Credentials or permissions involved.
- Changes to external systems.
- Data accessed, disclosed, or transmitted.
- Delegated tasks and associated identities.
- Relevant security alerts.
- The point at which the incident began and ended.
- Whether the agent continued operating after containment.
- Whether similar deployments share the same weakness.

The investigation should distinguish confirmed facts from model-generated claims, assumptions, and incomplete telemetry.

#### 27.5 Incident Severity Assessment

Severity should consider:
- Sensitivity and volume of exposed information.
- Privilege level of the affected agent.
- Number of affected users or systems.
- Whether a transaction or external action occurred.
- Whether the activity is ongoing.
- Whether the incident is reproducible.
- Whether other agents share the same vulnerability.
- Applicable legal, contractual, and regulatory notification requirements.
- The availability of reliable evidence.
- Potential impact on safety, business continuity, or critical operations.

An incident should not be classified as low severity solely because the model later apologizes, denies the action, or produces a reassuring explanation.

#### 27.6 Post-Incident Requirements

Following containment and recovery, the organization should:
1. Determine the root cause and contributing conditions.
2. Identify all affected systems, users, data, and agents.
3. Remediate the technical and governance weaknesses.
4. Review whether the incident reveals a broader design flaw.
5. Update threat models, risk registers, and test cases.
6. Validate the effectiveness of corrective controls.
7. Review relevant third-party dependencies.
8. Determine whether risk acceptance or deployment approval must be revisited.
9. Record lessons learned and assign corrective actions.
10. Retain evidence according to applicable policy and legal requirements.

### 28. Business Continuity, Recovery, and Safe Degradation

AI agents can become operational dependencies when integrated into customer service, security operations, financial processing, internal support, or critical business workflows.

A security incident or service failure may require the agent to be disabled. The organization must therefore define how essential business processes continue without relying on the affected agent.

Business continuity planning should account for model-provider outages, compromised integrations, corrupted memory, unsafe behavior, identity failures, and the need to suspend autonomous execution.

#### 28.1 Failure Scenarios

| Failure scenario | Potential business impact | Required continuity consideration |
|---|---|---|
| Model provider outage | Agent becomes unavailable | Approved manual process or alternative service |
| Orchestration failure | Tasks cannot be coordinated reliably | Safe suspension and task recovery |
| Identity provider outage | Authorization cannot be verified | Fail-secure behavior for protected actions |
| Retrieval outage | Agent lacks required information | Restricted functionality or approved alternative source |
| Tool compromise | Connected actions may be unsafe | Disable the affected tool and reroute work |
| Memory corruption | Context may be unreliable | Quarantine affected memory and reconstruct approved state |
| Runaway execution | Resources or connected services are overloaded | Circuit breakers, cancellation, and resource controls |
| Security incident | Agent may be unsafe to operate | Incident containment and manual fallback |
| Provider configuration change | Previously validated behavior may change | Suspend or restrict affected functionality pending review |
| Loss of auditability | Actions cannot be reliably reconstructed | Restrict high-impact operations until traceability is restored |

#### 28.2 Recovery Requirements

A recovery plan should define:
- Recovery time objectives for the relevant business process.
- Recovery point objectives where persistent state must be restored.
- The process for identifying the last known approved configuration.
- The conditions under which the agent may be re-enabled.
- How compromised credentials are replaced.
- How poisoned or corrupted memory is isolated and restored.
- How incomplete transactions are reconciled.
- How delegated and asynchronous tasks are verified.
- Which manual procedures are available.
- Who authorizes return to service.
- What security tests are required before restoration.

Recovery targets should be based on business impact analysis rather than assumed to be the same for every agent.

#### 28.3 Safe Degradation Patterns

| Pattern | Description | Appropriate use |
|---|---|---|
| Read-only mode | Disable modifications while preserving approved retrieval and analysis | Temporary uncertainty about write authorization |
| Draft-only mode | Allow the agent to prepare content without sending or publishing it | Messaging or publishing workflows with unavailable approval services |
| Human-operated fallback | Transfer execution to an authorized human process | High-impact workflows requiring continuity |
| Restricted tool mode | Disable affected integrations while preserving unrelated safe functions | A compromised or unavailable connector |
| Task suspension | Preserve the task state without further execution | An ambiguous transaction or unresolved authorization decision |
| Controlled restart | Resume from a validated state after security checks | Recoverable runtime failures |
| Full shutdown | Disable the agent and its execution paths | Severe compromise or uncontrolled behavior |

The organization should define which degradation patterns are permitted for each agent and which actions must stop completely when a security-critical dependency fails.

#### 28.4 Recovery Validation Checklist

Before returning an agent to normal operation, verify that:

- The root cause has been addressed or sufficiently contained.
- Compromised credentials have been revoked or replaced.
- Unapproved tools and permissions have been removed.
- Memory and task state have been validated.
- Incomplete or duplicate transactions have been reconciled.
- Security logging and alerting are operational.
- Required regression tests have passed.
- Relevant vulnerabilities have been remediated or formally dispositioned.
- The deployment matches the approved configuration.
- The authorized service owner has approved restoration.
- Residual risks and recovery limitations are documented.

An agent should not return to service merely because its interface responds successfully. Recovery must restore the required security properties.

### 29. Evidence Collection, Control Effectiveness, and Assessment Quality

A security assessment is defensible only when its conclusions are supported by evidence appropriate to the claim being made.

AI agent security reviews often combine architectural documentation, configuration inspection, test results, monitoring records, provider assurances, and interviews. These sources do not all provide the same level of assurance.

For example, an interview may establish that a team intends to enforce least privilege, but it does not demonstrate that the deployed tool identity actually has restricted permissions.

The assessment should therefore distinguish between control design, implementation, operating effectiveness, and residual risk.

#### 29.1 Control Assurance Dimensions

| Dimension | Assessment question | Example evidence |
|---|---|---|
| Design effectiveness | Is the control appropriately designed to address the risk? | Architecture, policy, and control specification |
| Implementation | Has the control been deployed in the relevant environment? | Configuration exports, deployment records, and access settings |
| Operating effectiveness | Does the control work consistently under realistic conditions? | Test results, operational logs, and sampled execution records |
| Coverage | Does the control apply to all relevant agents, tools, and environments? | Inventory reconciliation and deployment coverage reports |
| Monitoring | Can control failures or policy violations be detected? | Alert configuration and detection-test results |
| Remediation | Are identified weaknesses corrected and verified? | Findings register, tickets, and retest evidence |
| Accountability | Are owners and approval authorities defined? | RACI, ownership records, and approval decisions |
| Sustainability | Will the control remain effective after changes? | Change management, regression testing, and periodic review |

#### 29.2 Evidence Quality Levels

The following classification can help reviewers understand the strength of the available evidence.

| Evidence level | Description | Example |
|---|---|---|
| E0 — Absent | No evidence is available | No documented authorization design or test record |
| E1 — Asserted | A person or team states that the control exists | Interview statement without corroboration |
| E2 — Documented | A policy or design describes the control | Approved access-control specification |
| E3 — Implemented | Configuration or deployment evidence shows the control exists | Tool gateway configuration and IAM settings |
| E4 — Tested | A repeatable test demonstrates the control's behavior | Negative authorization test with verified system state |
| E5 — Operationally evidenced | Ongoing evidence demonstrates operation over time | Sampled audit records, monitoring results, and periodic control testing |

This is a proposed internal evidence scale, not a universal assurance standard. Organizations should define the evidence level required for each control based on risk and applicable audit requirements.

A high-impact authorization control may require tested and operationally evidenced enforcement rather than a documented design alone.

| Field | Description |
|---|---|
| Evidence ID | Unique identifier |
| Related requirement | Security control or assessment question |
| Related risk | Associated risk-register reference |
| Agent and environment | System under assessment |
| Evidence description | What the evidence demonstrates |
| Source | Configuration, log, test, document, or interview |
| Collection date | When evidence was obtained |
| Collector | Person or team responsible |
| Evidence owner | Team responsible for the source |
| Sensitivity | Applicable classification |
| Integrity reference | Hash, version, or other integrity information where appropriate |
| Assessment result | Pass, fail, partial, inconclusive, or not applicable |
| Limitation | Known gap or restriction |
| Finding reference | Associated finding, if any |
| Retention requirement | Applicable retention period or policy |

Evidence should be collected and stored through approved channels. Sensitive prompts, credentials, personal information, and confidential customer records should not be copied into assessment reports unnecessarily.

#### 29.4 Control Effectiveness Rating

| Rating | Meaning | Typical treatment |
|---|---|---|
| Effective | The control is appropriately designed, implemented, and supported by sufficient evidence | Maintain and periodically verify |
| Partially effective | The control exists but has material coverage or implementation weaknesses | Remediate identified gaps |
| Ineffective | The control does not adequately prevent or detect the relevant risk | Prioritize remediation and reassess exposure |
| Not implemented | The required control is absent | Implement or obtain an authorized exception where permitted |
| Not tested | Evidence is insufficient to determine effectiveness | Conduct testing before making an assurance claim |
| Not applicable | The control does not apply to the documented system scope | Record the rationale and obtain review where required |

"Not tested" must not be treated as equivalent to "effective." Similarly, "not applicable" requires a defensible rationale rather than an assumption that the control is unnecessary.

#### 29.5 Independent Review and Quality Assurance

For high-risk agents, an independent reviewer should examine:
- Whether the assessment scope covers material capabilities and dependencies.
- Whether threat scenarios reflect realistic attack paths.
- Whether required controls are enforceable.
- Whether test cases cover negative and adversarial conditions.
- Whether test results are supported by independent system evidence.
- Whether findings are consistently rated.
- Whether residual risk is calculated or evaluated using the approved methodology.
- Whether remediation owners and deadlines are appropriate.
- Whether exceptions and approvals are valid.
- Whether the final recommendation is supported by the evidence.

The reviewer should be sufficiently independent of the development and operation of the agent to challenge unsupported assumptions.

### 30. Core Principle — AI Agent Security Must Be Enforced Through Architecture and Operations

A secure AI agent requires more than an approved model, a carefully written system prompt, or a policy stating that users must behave responsibly.

Security must be built into the architecture, enforced at the execution boundaries, validated through adversarial testing, monitored during operation, and maintained through controlled change management.

The organization must be able to demonstrate that:

- **Controls are enforceable:** The model cannot independently override mandatory authorization, execution, or approval rules.
- **Data remains governed:** Sensitive information is protected throughout retrieval, context assembly, processing, memory, output, logging, and deletion.
- **Permissions remain bounded:** Each agent and tool operates with only the authority required for the approved purpose.
- **Deployment remains controlled:** Runtime isolation, network restrictions, configuration governance, and dependency management limit the impact of compromise.
- **Changes remain assessable:** Model, prompt, tool, permission, and infrastructure changes trigger proportionate security review and regression testing.
- **Incidents remain containable:** Operators can stop execution, revoke access, disable tools, preserve evidence, and recover safely.
- **Continuity does not bypass security:** Alternative operating modes preserve required authorization and data protection controls.
- **Assurance remains evidence-based:** Control effectiveness is established through appropriate implementation evidence, testing, and operational records.
- **Risk decisions remain accountable:** Residual risks, exceptions, and approvals are documented and assigned to authorized owners.

#### Final Assessment Principle

**AI agent security is an ongoing operational capability, not a one-time model review. The organization must maintain enforceable controls, reliable evidence, tested containment procedures, and accountable governance throughout the agent's lifecycle.**

An agent should remain authorized to operate only while its deployed capabilities, security controls, and residual risks remain consistent with the organization's approved business purpose and risk tolerance.

### 31. End-to-End AI Agent Security Assessment Workflow

An AI Agent Security Assessment must produce a structured, evidence-based decision about whether an agent can be deployed, continue operating, or requires remediation.

The assessment should connect business objectives, technical architecture, threat scenarios, security controls, test evidence, and residual risk. Its purpose is not merely to document vulnerabilities; it is to establish whether the agent's capabilities can be operated within the organization's approved risk tolerance.

The workflow should be repeatable across development, pre-production, production, and material changes to an existing deployment.

#### 31.1 Assessment Lifecycle

| Stage | Activity | Principal output | Accountable role |
|---|---|---|---|
| 1. Initiation | Establish the business purpose and assessment trigger | Assessment request | Business owner |
| 2. Scoping | Define capabilities, users, data, integrations, and environments | Approved assessment scope | AI system owner |
| 3. Classification | Determine the agent's risk tier and assessment depth | Risk classification | AI risk owner |
| 4. Architecture review | Examine components, trust boundaries, identities, and data flows | Architecture assessment | Security architect |
| 5. Threat modeling | Identify attack paths, abuse cases, and potential business impacts | Threat model | Security assessment lead |
| 6. Control assessment | Evaluate preventive, detective, and corrective safeguards | Control assessment matrix | Security and control owners |
| 7. Security testing | Perform technical validation and adversarial testing | Test results and evidence | Security testing team |
| 8. Findings evaluation | Rate deficiencies and determine their significance | Findings register | Assessment lead |
| 9. Remediation | Correct weaknesses and perform retesting | Remediation evidence | Assigned control owners |
| 10. Residual risk analysis | Evaluate remaining exposure after implemented controls | Residual risk assessment | Risk owner |
| 11. Approval | Determine whether the agent may proceed | Formal security decision | Authorized approver |
| 12. Operational monitoring | Monitor control performance and changing risks | Monitoring records | Service owner |
| 13. Periodic reassessment | Review effectiveness, changes, and emerging threats | Updated assessment | AI system owner |

The workflow should allow an assessment to return to an earlier stage when evidence reveals a previously unidentified dependency, an inadequate control, or a material change in the system's risk profile.

#### 31.2 Assessment Entry Criteria

Before technical assessment begins, the assessment team should obtain:

- An approved business use case.
- A named business owner and technical owner.
- An initial AI agent inventory record.
- An architecture diagram and data-flow description.
- An inventory of tools, integrations, and external providers.
- An initial data classification and access assessment.
- A preliminary risk classification.
- A defined deployment environment.
- A list of applicable security and compliance requirements.
- Authorization to conduct the required security testing.

If critical information is unavailable, the assessment should record the gap and determine whether the missing information prevents a reliable security decision.

#### 31.3 Assessment Exit Criteria

The assessment should not be considered complete until:

1. The agreed scope has been assessed.
2. Material threats and attack paths have been documented.
3. Mandatory security controls have been evaluated.
4. Required technical tests have been performed or their limitations recorded.
5. Findings have been rated and assigned to accountable owners.
6. Remediation evidence has been reviewed where remediation is claimed.
7. Residual risks have been evaluated.
8. Required exceptions and risk acceptances have been approved.
9. The final recommendation has been documented.
10. Monitoring, incident response, and reassessment requirements have been established.

An assessment may conclude that an agent is not ready for deployment. Completion of the assessment does not imply approval of the system.

### 32. AI Agent Security Risk Scoring and Prioritization

Risk scoring enables the organization to compare findings, prioritize remediation, and make consistent approval decisions.

An AI agent assessment should consider both the likelihood of a threat scenario and its potential consequences. It should also account for the agent's autonomy, tool privileges, data sensitivity, exposure, and ability to create persistent or cascading effects.

A scoring model is useful only when its criteria are defined consistently and applied transparently.

#### 32.1 Risk Scoring Formula

A simple qualitative model is:

**Inherent Risk Score = Likelihood × Impact**

A second assessment evaluates the remaining exposure after considering the effectiveness of implemented controls.

For a five-by-five matrix:

- Likelihood: 1–5.
- Impact: 1–5.
- Inherent score: 1–25.

| Score | Likelihood | Description |
|---|---|---|
| 1 | Rare | The scenario is unlikely under the assessed conditions |
| 2 | Unlikely | The scenario is possible but not expected |
| 3 | Possible | The scenario could occur under realistic conditions |
| 4 | Likely | The scenario is expected to occur in relevant circumstances |
| 5 | Almost certain | The scenario is highly likely or repeatedly observed |

Likelihood ratings should consider relevant threat intelligence, exposure, exploitability, existing controls, and test results. They should not be based solely on the development team's confidence in the model.

#### 32.2 Impact Assessment Criteria

Impact should be evaluated across multiple dimensions.

| Impact dimension | Assessment considerations |
|---|---|
| Confidentiality | Unauthorized disclosure of personal, financial, customer, or corporate information |
| Integrity | Unauthorized modification of records, configurations, transactions, or decisions |
| Availability | Disruption of the agent or connected business services |
| Financial | Fraud, financial loss, remediation costs, or resource consumption |
| Operational | Disruption to business processes and dependent services |
| Legal and regulatory | Potential breaches of legal, regulatory, or contractual obligations |
| Safety | Potential harm to individuals or unsafe operation of connected systems |
| Reputation | Loss of trust, customer confidence, or business credibility |
| Cascading effects | Ability to affect multiple systems, agents, or downstream workflows |

The organization should define how these dimensions are consolidated into a single impact rating. A severe impact in one critical dimension may justify a high overall rating even if other dimensions are limited.

#### 32.3 Illustrative Risk Matrix

| Likelihood \ Impact | 1 — Negligible | 2 — Minor | 3 — Moderate | 4 — Major | 5 — Severe |
|---|---:|---:|---:|---:|---:|
| 5 — Almost certain | 5 | 10 | 15 | 20 | 25 |
| 4 — Likely | 4 | 8 | 12 | 16 | 20 |
| 3 — Possible | 3 | 6 | 9 | 12 | 15 |
| 2 — Unlikely | 2 | 4 | 6 | 8 | 10 |
| 1 — Rare | 1 | 2 | 3 | 4 | 5 |

An organization might adopt the following thresholds:

| Score | Illustrative rating | Typical treatment |
|---|---|---|
| 1–4 | Low | Maintain controls and monitor |
| 5–9 | Moderate | Remediate according to the approved treatment plan |
| 10–15 | High | Require formal remediation planning and risk-owner review |
| 16–25 | Critical | Restrict or suspend affected functionality pending urgent review |

These thresholds are examples, not universal standards. They should be calibrated against the organization's enterprise risk methodology.

#### 32.4 AI Agent Risk Multipliers and Escalation Factors

A basic likelihood-impact score may not fully capture agent-specific risks.

The assessment should consider whether escalation is warranted when an agent:

- Can execute irreversible or high-impact actions.
- Has broad administrative permissions.
- Can access highly sensitive data.
- Can delegate work to other agents.
- Can execute code or access external networks.
- Can persist information across sessions.
- Can initiate financial or customer-impacting transactions.
- Operates without human approval for consequential actions.
- Can affect multiple connected systems.
- Has limited auditability or uncertain containment capability.

Rather than applying arbitrary numerical multipliers, an organization can define explicit escalation rules.

For example, an agent with broad production write permissions might be classified as high risk even when the estimated likelihood of misuse is low.

#### 32.5 Residual Risk Assessment

Residual risk is the exposure remaining after implemented controls have been considered.

| Risk element | Assessment question |
|---|---|
| Inherent risk | What could happen before considering the relevant controls? |
| Control design | Are the controls capable of addressing the scenario? |
| Control implementation | Are the controls actually deployed? |
| Control effectiveness | Do tests and operational evidence demonstrate that they work? |
| Remaining exposure | What risk persists after accounting for effective controls? |
| Uncertainty | Are there evidence gaps or untested attack paths? |
| Risk treatment | Should the risk be avoided, mitigated, transferred, or accepted? |
| Approval authority | Who is authorized to approve the remaining exposure? |

Residual risk should not be calculated by mechanically subtracting an arbitrary number of control points from the inherent score. The assessor should evaluate how the controls change the likelihood, impact, or both, and document the rationale.

### 33. AI Agent Findings Register and Remediation Management

The findings register is the authoritative record of security deficiencies identified during the assessment.

It connects each finding to the affected agent, underlying risk, evidence, remediation action, accountable owner, target date, and verification result.

A well-maintained register prevents significant security issues from disappearing into informal discussions or being treated as resolved without adequate evidence.

| Finding title | Concise description of the deficiency |
| Agent name and version | Identifies the affected deployment |
| Environment | Identifies development, testing, staging, or production |
| Assessment reference | Links the finding to the assessment |
| Related risk ID | Connects the finding to the risk register |
| Affected component | Identifies the tool, model integration, data source, or runtime |
| Finding description | Explains the observed weakness |
| Threat scenario | Describes how the weakness could be exploited or fail |
| Evidence | Records the supporting test result or configuration evidence |
| Severity | Indicates the assessed significance |
| Business impact | Describes the potential consequences |

#### 33.2 Finding Severity Definitions

| Severity | Definition | Example |
|---|---|---|
| Critical | A weakness enables or could readily enable catastrophic impact or severe compromise of critical systems or sensitive data | An agent can perform unrestricted privileged production actions without independent authorization |
| High | A weakness creates significant exposure or enables consequential unauthorized actions | An agent can disclose restricted customer information through an inadequately controlled integration |
| Medium | A weakness creates material but more limited exposure | Sensitive tool outputs are logged without adequate redaction |

Severity must be based on the actual context, exploitability, business impact, exposure, and available controls. A generic severity label from a testing tool may be an input, but it should not replace the organization's risk assessment.

#### 33.4 Root Cause Categories

Classifying root causes helps the organization identify recurring control failures.

| Root cause category | Example |
|---|---|

| Third-party weakness | Provider controls or contractual protections are insufficient |
| Governance weakness | No authorized owner is assigned to residual risk |

| Change management weakness | Model or tool changes bypass security review |

Root-cause analysis should focus on the conditions that permitted the deficiency, rather than simply attributing the issue to a model's unexpected output.

#### 33.5 Closure Criteria

A finding should be closed only when:
1. The remediation has been implemented.
2. The affected configuration or code has been identified.
3. Appropriate retesting has been completed.
4. Test results demonstrate that the weakness is adequately addressed.
5. Relevant evidence has been retained.
6. Residual risk has been reassessed.
7. Any remaining limitations have been documented.
8. The authorized reviewer has approved closure.

For significant findings, remediation should be verified by someone other than the individual who implemented the change, where practical.

### 34. AI Agent Security Approval and Risk Acceptance Decisions

The assessment process must distinguish technical findings from the business decision to operate the agent.

Security assessors provide evidence-based recommendations. Business owners understand the operational purpose. Technical owners understand the architecture and remediation options. Risk owners evaluate residual exposure. Authorized approvers determine whether deployment is permitted under the organization's governance model.

These responsibilities should not be conflated.

#### 34.1 Possible Assessment Outcomes

| Outcome | Meaning | Typical condition |
|---|---|---|
| Approved | The agent satisfies applicable requirements and residual risk is within approved tolerance | Required controls are implemented and verified |
| Approved with conditions | Operation is permitted subject to explicit restrictions and deadlines | Outstanding issues are controlled and formally approved |
| Restricted approval | Only specified capabilities or environments are permitted | Higher-risk tools or functions remain disabled |
| Remediation required | Deployment or affected functionality must wait for corrective action | A material deficiency remains unresolved |
| Rejected | The agent is not authorized to operate in the proposed form | Risk exceeds tolerance or mandatory requirements are not satisfied |
| Suspended | An operating agent is temporarily disabled or restricted | New evidence, incidents, or changes invalidate the previous decision |
| Reassessment required | Existing approval is insufficient for the changed system | Material change or new threat invalidates the previous assessment |

An approval decision should state exactly which agent version, configuration, environment, and capabilities are covered.

#### 34.3 Conditions for Risk Acceptance

Risk acceptance should be considered only when the organization permits acceptance of the specific risk and the approving individual has the necessary authority.

The acceptance record should identify:
- The specific risk being accepted.
- The business justification.
- The affected agent and capabilities.
- The likelihood and impact assessment.
- The controls already implemented.
- The remaining exposure.
- Alternative treatments considered.

- The accountable risk owner.

### 35. AI Agent Security Reporting and Executive Metrics

Security reporting should translate technical findings into information that supports business decisions, investment prioritization, and accountability.

Executives generally need to understand whether agents are appropriately controlled, where material exposure remains, whether remediation is progressing, and whether the organization can demonstrate compliance with its requirements.

A useful report should not merely count vulnerabilities. It should connect security conditions to business impact and deployment decisions.

#### 35.1 Executive Report Structure

A standard AI Agent Security Assessment report should include:

1. **Executive summary:** Overall assessment outcome and major concerns.
2. **System overview:** Business purpose, deployment model, and principal capabilities.
3. **Assessment scope:** Components, environments, integrations, and exclusions.
4. **Risk classification:** Risk tier and rationale.
5. **Architecture findings:** Material trust boundaries and dependencies.
6. **Control effectiveness:** Summary of mandatory and risk-relevant controls.
7. **Security testing:** Scope, scenarios, limitations, and results.
8. **Findings:** Prioritized deficiencies and remediation status.
9. **Residual risk:** Remaining exposure after implemented safeguards.
10. **Compliance considerations:** Relevant obligations and evidence gaps.
11. **Approval decision:** Approved outcome or required actions before approval.
12. **Action plan:** Owners, deadlines, and verification requirements.
13. **Monitoring plan:** Operational metrics and reassessment triggers.

#### 35.2 Core Metrics

| Metric | Calculation or definition | Management value |
|---|---|---|
| Assessment coverage | Assessed in-scope agents ÷ total agents requiring assessment | Shows governance coverage |
| High-risk assessment completion | High-risk agents assessed ÷ total high-risk agents requiring assessment | Shows coverage of material exposure |
| Mandatory control pass rate | Mandatory controls passing ÷ mandatory controls tested | Shows control effectiveness |
| Critical findings outstanding | Count of open critical findings | Highlights urgent exposure |
| High findings overdue | Count of high-severity findings past target date | Highlights remediation delays |
| Mean time to remediate | Average time from finding creation to verified remediation | Measures remediation efficiency |
| Retest failure rate | Findings failing retest ÷ findings retested | Indicates remediation quality |
| Risk acceptance count | Number of active accepted risks | Shows accepted exposure |
| Expired risk acceptance count | Number of active records past their review or expiry date | Highlights governance exceptions |
| Unauthorized action attempts | Count of detected or tested unauthorized action attempts | Supports monitoring and control review |
| Approval-gate effectiveness | Results of tests verifying required approval enforcement | Evaluates a critical execution boundary |
| Emergency-stop test coverage | Agents with tested containment capability ÷ agents requiring it | Measures operational readiness |
| Reassessment timeliness | Agents reassessed by required date ÷ agents due for reassessment | Measures lifecycle governance |
| Evidence completeness | Required evidence items available ÷ required evidence items | Supports audit readiness |

Each metric needs a clear definition, owner, reporting frequency, data source, and interpretation guidance.

#### 35.3 Interpreting Metrics Correctly

Metrics can be misleading if their definitions are weak.

For example:
- A high control pass rate may conceal controls that were never tested.
- A low finding count may indicate weak testing rather than strong security.
- A high remediation rate may hide repeated reopening of findings.
- A low number of incidents may reflect inadequate detection.
- A high assessment completion rate may conceal incomplete scope coverage.
- A large number of risk acceptances may indicate poor design or weak remediation discipline.

Reports should therefore include limitations and supporting context.

### 36. AI Agent Assessment Quality Assurance and Independent Review

Quality assurance establishes whether the assessment is sufficiently complete, consistent, and evidence-based to support a reliable decision.

Because AI agents combine probabilistic model behavior with conventional software, APIs, identities, and business workflows, a superficial review of the model alone is insufficient.

Quality assurance should test the assessment process itself, including its scope, assumptions, methodology, evidence, findings, and final recommendation.

#### 36.1 Assessment Quality Checklist

| Quality area | Review question |
|---|---|
| Scope | Are all material capabilities, integrations, and environments included? |
| Architecture | Are trust boundaries and external dependencies documented? |
| Threat modeling | Are realistic misuse and adversarial scenarios covered? |
| Identity | Are user and agent permissions independently evaluated? |
| Tool security | Are tool authorization, argument validation, and execution restrictions tested? |
| Data protection | Are retrieval, memory, logging, output, and retention risks addressed? |
| Testing | Are negative and adversarial test cases appropriate for the agent's risk? |
| Evidence | Are conclusions supported by reliable evidence? |
| Findings | Are severity and remediation requirements justified? |
| Risk analysis | Are inherent and residual risks evaluated consistently? |
| Governance | Are accountable owners and approval authorities identified? |
| Exceptions | Are accepted risks valid, bounded, and appropriately authorized? |
| Reporting | Does the report accurately reflect the evidence and limitations? |
| Monitoring | Are detection and response requirements defined? |
| Lifecycle | Are change management and reassessment triggers established? |

#### 36.2 Common Assessment Failures

| Assessment failure | Why it matters | Corrective approach |
|---|---|---|
| Reviewing only the model | Ignores application and integration risks | Assess the complete agentic system |
| Trusting system instructions as the primary safeguard | Instructions do not independently enforce authorization | Implement external policy enforcement |
| Testing only expected user behavior | Misses adversarial and misuse scenarios | Include negative, boundary, and adversarial tests |
| Ignoring delegated agents | Misses privilege propagation and accountability gaps | Assess delegation boundaries and identities |
| Accepting screenshots without context | May not establish configuration scope or operating effectiveness | Corroborate with reproducible tests and source evidence |
| Treating provider assurances as sufficient | May not address the organization's own implementation | Validate integration-specific controls |
| Ignoring persistent memory | Misses retention, poisoning, and cross-session risks | Assess memory lifecycle and isolation |
| Closing findings without retesting | Does not demonstrate that the weakness is resolved | Require verification evidence |
| Treating approval as permanent | Fails to account for model and capability changes | Define reassessment triggers |
| Failing to test emergency containment | Leaves uncertainty about the ability to stop unsafe behavior | Conduct containment exercises |
| Ignoring downstream state | May miss completed unauthorized actions | Verify external-system outcomes |
| Using risk acceptance to bypass mandatory controls | Weakens governance and can violate requirements | Enforce explicit non-acceptance criteria |

#### 36.3 Independent Review Requirements

For high-impact agents, independent review should examine the assessment's critical assumptions and the validity of the evidence.

The reviewer should consider whether:
- The assessment team had appropriate competence and independence.
- The system scope matches the actual deployed architecture.
- The tests represent realistic threat scenarios.
- Security controls operate independently of model-generated decisions where necessary.
- High-severity findings have been appropriately escalated.
- Residual risk is supported by evidence.
- Risk acceptance has been approved by the correct authority.
- The final decision is consistent with mandatory requirements.
- The organization can monitor and contain the system after deployment.

Independent review should be proportionate to the system's risk and the consequences of an incorrect approval decision.

### 37. Enterprise Implementation Roadmap for an AI Agent Security Assessment Program

Organizations should implement an AI agent security assessment program incrementally, beginning with visibility and accountability before expanding into standardized testing, automated evidence collection, and continuous assurance.

The objective is to create a repeatable operational capability rather than a collection of isolated assessment documents.

#### 37.1 Phase 1 — Establish Visibility and Ownership

**Indicative timeframe:** Days 1–30.

Activities:
- Identify known AI agents and agentic capabilities.
- Establish a common inventory and ownership model.
- Define assessment triggers and minimum scope requirements.
- Identify high-impact tools, data sources, and integrations.
- Establish preliminary risk classification criteria.
- Identify applicable enterprise policies and legal obligations.
- Define the approval and exception process.
- Select an initial group of agents for assessment.

Deliverables:
- AI agent inventory.
- Ownership and accountability matrix.
- Initial risk classification.
- Assessment procedure.
- Preliminary assessment schedule.

Success criteria:
- Material agents are identifiable.
- Each in-scope agent has an accountable owner.
- High-risk deployments can be prioritized.

#### 37.2 Phase 2 — Standardize Controls and Assessments

**Indicative timeframe:** Days 31–60.

Activities:
- Establish a baseline of mandatory security controls.
- Develop architecture and threat-model templates.
- Define standard assessment questions and test cases.
- Create a findings register and remediation workflow.
- Establish evidence requirements.
- Define severity and residual-risk criteria.
- Conduct pilot assessments.
- Validate approval and risk-acceptance procedures.

Deliverables:
- Approved control baseline.
- Assessment templates.
- Threat-modeling methodology.
- Test-case library.
- Findings and remediation process.
- Pilot assessment reports.

Success criteria:
- Assessments are repeatable.
- Findings have owners and remediation dates.
- Security decisions are supported by documented evidence.

#### 37.3 Phase 3 — Integrate Testing and Operational Assurance

**Indicative timeframe:** Days 61–90.

Activities:
- Integrate security assessments into the software development lifecycle.
- Establish model, prompt, tool, and configuration change controls.
- Introduce regression testing for material changes.
- Validate emergency-stop and credential-revocation procedures.
- Integrate relevant security telemetry into monitoring platforms.
- Establish periodic reassessment requirements.
- Define management reporting metrics.
- Conduct independent review of selected high-risk assessments.

Deliverables:
- Integrated assessment workflow.
- Regression-testing baseline.
- Incident-response procedures.
- Monitoring and reporting requirements.
- Reassessment schedule.
- Independent assurance results.

Success criteria:
- Material changes trigger security review.
- High-risk agents have tested containment mechanisms.
- Governance reporting reflects actual assessment and remediation status.

The 90-day timeline is illustrative. Organizations with large agent inventories, complex regulated environments, or extensive legacy integrations may require a longer implementation period.

#### 37.4 Program Maturity Model

| Level | Description | Characteristics |
|---|---|---|
| Level 1 — Ad hoc | Security review is inconsistent | Limited inventory, informal testing, unclear ownership |
| Level 2 — Defined | Standard procedures exist | Documented assessment templates, risk classification, assigned owners |
| Level 3 — Implemented | Assessments are integrated into delivery and operations | Standard controls, repeatable testing, remediation tracking, formal approvals |
| Level 4 — Measured | Effectiveness is measured | Defined metrics, periodic assurance, trend analysis, risk-based reassessment |
| Level 5 — Adaptive | The program responds to changing risk | Continuous improvement, threat-informed testing, automated evidence where appropriate, integrated lifecycle governance |

Maturity should be evaluated against demonstrated operating practices, not the number of documents produced.

### 38. Mapping the AI Agent Security Assessment to Recognized Frameworks

An enterprise AI agent assessment should align with relevant security, risk management, privacy, and AI governance frameworks without treating any single framework as a complete substitute for technical assessment.

Framework mapping helps demonstrate traceability between internal controls and external expectations. The exact mapping depends on the agent's deployment model, business purpose, jurisdiction, and risk classification.

#### 38.1 Framework Mapping

| Framework or reference | Relevant assessment focus | Practical application |
|---|---|---|
| NIST AI Risk Management Framework (AI RMF) | AI risk governance, mapping, measurement, and management | Organize risk identification, evaluation, treatment, and monitoring |
| NIST Cybersecurity Framework (CSF) | Cybersecurity governance and lifecycle risk management | Connect agent controls to enterprise cybersecurity functions |
| ISO/IEC 42001 | AI management system governance | Establish organizational accountability, documented processes, and continual improvement |
| ISO/IEC 23894 | AI risk management guidance | Structure AI-specific risk identification and treatment |
| ISO/IEC 27001 | Information security management | Align agent security controls with the organizational ISMS |
| ISO/IEC 27701 | Privacy information management | Support privacy governance where applicable to the organization's implementation |
| OWASP Top 10 for LLM Applications | Common LLM application security risks | Inform testing for prompt injection, sensitive information disclosure, excessive agency, and related risks |
| MITRE ATLAS | Adversarial threats to AI-enabled systems | Support threat modeling and adversarial scenario development |
| EU AI Act | Applicable obligations for AI systems and relevant operators | Determine regulatory applicability, role, risk category, and required controls |
| GDPR | Personal data processing and individual rights | Assess lawful processing, data protection, security, and applicable individual rights |
| CIS Controls | Enterprise cybersecurity safeguards | Map relevant foundational security practices to the agent's environment |

Framework references should be validated against the versions adopted by the organization. Applicability and conformity must not be claimed solely because a framework appears in an assessment report.

#### 38.2 Mapping Methodology

A practical mapping process should:

1. Identify the organization's applicable frameworks and requirements.
2. Extract the relevant control or requirement.
3. Map it to an internal security control.
4. Identify the agent components within scope.
5. Define the required evidence.
6. Assess implementation and effectiveness.
7. Record gaps and remediation actions.
8. Document justified exclusions.
9. Assign accountability for unresolved issues.
10. Retain the mapping for audit and reassessment.

#### 38.3 Example Control Traceability

| Security requirement | Internal control | Example evidence | Assessment result |
|---|---|---|---|
| Prevent unauthorized tool execution | Tool gateway enforces action-level authorization | Configuration and negative authorization tests | Effective, partially effective, or ineffective |
| Protect sensitive information | Retrieval and output controls enforce data access restrictions | Access-control tests and data-flow review | Assessed against defined criteria |
| Maintain accountability | Consequential tool actions are attributable to identities | Correlated execution logs | Assessed against defined criteria |
| Control material changes | Changes trigger risk-based review and regression testing | Change tickets and test reports | Assessed against defined criteria |
| Support incident containment | Operators can disable affected tools and revoke access | Exercise results and runbooks | Assessed against defined criteria |
| Govern residual risk | Authorized owners approve risk treatment decisions | Risk acceptance records | Assessed against defined criteria |

The mapping should identify the actual requirement and its applicable version. A broad framework reference is not sufficient evidence of conformity.

### 40. Final Core Principle — AI Agent Security Assessment Must Produce an Enforceable Security Decision

An AI agent security assessment is complete only when the organization can demonstrate that it understands the agent's capabilities, has evaluated material risks, has verified required controls, and has made an accountable decision about whether and how the agent may operate.

The assessment must connect technical evidence with governance authority.

**The core principles are:**

- **Assess the complete system:** Include the model, orchestration, tools, identities, memory, data sources, infrastructure, and downstream applications.
- **Enforce authorization outside the model:** Model-generated decisions must not override mandatory access controls, business rules, or approval requirements.
- **Verify controls through evidence:** Policies and design documents must be supported by implementation evidence and appropriate testing.
- **Prioritize consequential risks:** Privileged access, sensitive-data exposure, autonomous execution, delegation, and cascading effects require particular scrutiny.
- **Maintain accountable risk decisions:** Residual risk must be assigned to authorized owners and treated consistently with organizational policy.
- **Govern the entire lifecycle:** Changes, incidents, new integrations, and emerging threats must trigger appropriate review.
- **Preserve operational control:** The organization must be able to suspend unsafe activity, revoke access, investigate incidents, and recover securely.
- **Measure effectiveness:** Assessment coverage, control performance, remediation progress, and operational readiness must be monitored.
- **Make approval conditional on evidence:** An agent should operate only within its approved scope and subject to its documented restrictions.

**Final assessment principle:** An AI agent is not secure merely because it performs its intended task. It is secure enough to operate only when the organization has established and verified appropriate boundaries around what it can access, what it can execute, what it can change, what it can disclose, and how quickly it can be contained when those boundaries fail.
