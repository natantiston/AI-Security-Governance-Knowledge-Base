# 09.06 — Model Extraction

## Part 1

### 1. Model Extraction

Model extraction is an attack in which an adversary interacts with a machine-learning model, typically through an inference interface, to reconstruct or approximate the model's behavior.

Unlike direct model theft, the attacker does not necessarily obtain the original model artifact.

```text
 id="me01"
Attacker
   ↓
Model API
   ↓
Queries
   ↓
Model Responses
   ↓
Collected Knowledge
   ↓
Reconstructed / Approximate Model
```

The resulting model may reproduce some or many of the capabilities of the original model.

---

### 2. Model Extraction vs Model Theft

The distinction is important.

**Model theft** generally involves obtaining an existing model artifact.

**Model extraction** involves learning the behavior of a model through interaction and using that information to construct another model.

```text
 id="me02"
MODEL THEFT

Original Model
     ↓
Unauthorized Access
     ↓
Model File Obtained


MODEL EXTRACTION

Original Model
     ↓
Query Interface
     ↓
Responses
     ↓
Learned Behavior
     ↓
Approximate Model
```

Model extraction can therefore occur even when the underlying model weights remain protected.

---

### 3. Why Model Extraction Matters

A proprietary ML model may represent substantial:

* Research investment.
* Engineering effort.
* Training expenditure.
* Intellectual property.
* Business differentiation.

An attacker who can reproduce the model's behavior may reduce the value of that investment.

---

### 4. Extraction as an Intellectual-Property Risk

A model can be considered proprietary intellectual property even when customers never receive the underlying model.

The organization may expose only:

```text
Input → API → Output
```

However, repeated interaction with that interface may reveal information about how the model behaves.

---

### 5. Black-Box Model Extraction

The most common conceptual setting is a **black-box model**.

The attacker knows little or nothing about the internal implementation.

They may know only:

* How to access the service.
* What inputs are accepted.
* What outputs are returned.

```text
 id="me03"
          UNKNOWN
     ┌──────────────┐
Input│              │Output
 ───►│  ML MODEL    │───►
     │              │
     └──────────────┘
          UNKNOWN
```

The attacker attempts to infer the model's behavior from observations.

---

### 6. White-Box vs Black-Box

A simplified distinction is:

| Environment | Attacker Knowledge                   |
| ----------- | ------------------------------------ |
| White-box   | Significant internal model knowledge |
| Gray-box    | Some internal information            |
| Black-box   | Primarily input/output behavior      |

Model extraction is particularly relevant to black-box and gray-box systems.

---

### 7. Query-Based Extraction

The attacker submits inputs to the target model and records its responses.

Conceptually:

```text
 id="me04"
Query 1 → Target Model → Response 1
Query 2 → Target Model → Response 2
Query 3 → Target Model → Response 3
Query 4 → Target Model → Response 4
...
```

The collected observations can then be used to train or construct another model.

---

### 8. The Target Model

The original model being attacked is commonly referred to as the **target model**.

It may be:

* A classification model.
* A computer-vision model.
* A recommendation model.
* A speech model.
* A language model.
* A fraud-detection model.
* Another ML inference system.

---

### 9. The Substitute Model

The attacker may construct a **substitute model** or **surrogate model** using information obtained from the target.

```text
 id="me05"
Target Model
     ↓
Observed Outputs
     ↓
Training Data
     ↓
Substitute Model
```

The substitute does not necessarily need to be identical internally to the target.

The objective is often to reproduce useful behavior.

---

### 10. Functional Similarity

Model extraction does not necessarily require exact duplication.

An attacker may consider the extraction successful if the substitute model behaves sufficiently similarly for the intended purpose.

For example:

```text
Target:
Input A → Class 1

Substitute:
Input A → Class 1
```

The internal architectures may be completely different.

---

### 11. Fidelity

**Fidelity** describes how closely the extracted or substitute model reproduces the target model's behavior.

Higher fidelity generally means greater similarity between:

```text
Target Model
     ↕
Substitute Model
```

The required level of fidelity depends on the attacker's objective.

---

### 12. Extraction Objectives

An attacker may attempt extraction for different reasons.

Potential objectives include:

* Reproducing a commercial capability.
* Avoiding API costs.
* Creating an offline version.
* Conducting security research.
* Enabling downstream attacks.
* Circumventing access restrictions.
* Replicating proprietary functionality.

The security impact depends heavily on the model and intended use.

---

### 13. Commercial Model Extraction

Suppose an organization operates a proprietary model:

```text
Customer
   ↓
Paid API
   ↓
Proprietary Model
   ↓
Prediction
```

An attacker may attempt to construct a substitute model that performs sufficiently similarly without paying for continued access.

---

### 14. Cost Avoidance

If inference is expensive, extraction could allow an attacker to shift computation from the provider to their own infrastructure.

For example:

```text
Before:
Attacker → Provider → Paid Inference

After:
Attacker → Local Substitute Model
```

This may undermine the provider's business model.

---

### 15. Offline Replication

An extracted model can potentially be operated independently of the original provider.

This may provide:

* Offline access.
* Greater control.
* Reduced provider dependency.
* Potentially unlimited local inference.

---

### 16. Competitive Replication

A competitor could attempt to reproduce a proprietary capability without investing the same amount of time and resources in model development.

This creates a significant intellectual-property concern.

---

### 17. Security Implications

Model extraction is not limited to economic loss.

A reconstructed model may also help attackers understand or approximate a security-sensitive decision system.

For example:

```text
Security Model
      ↓
Extraction
      ↓
Approximate Behavior
      ↓
Attacker Understands Decision Boundary
```

This can potentially facilitate further attacks.

---

### 18. Decision Boundary

For classification systems, an attacker may attempt to approximate the **decision boundary** of the target model.

Conceptually:

```text
          Class A
        /─────────\
       /           \
------|-------------|------
       \           /
        \─────────/
          Class B
```

Learning where the model changes decisions can reveal useful information about its behavior.

---

### 19. Classification Models

Consider a model that determines:

```text
Input
  ↓
Fraud?
  ↓
YES / NO
```

Repeated queries may allow an attacker to learn patterns associated with the model's decisions.

The attacker could then attempt to reproduce those decisions with another model.

---

### 20. Confidence Information

Some model APIs expose more than a simple prediction.

For example:

```text
Prediction:
Cat

Confidence:
0.94
```

or:

```text
Class A: 0.91
Class B: 0.06
Class C: 0.03
```

Such information can provide significantly more information for behavioral reconstruction than a simple label.

---

### 21. Rich Outputs

The more information returned by an inference service, the more information may be available for extraction.

Potential output information includes:

* Class labels.
* Confidence scores.
* Probability distributions.
* Rankings.
* Scores.
* Explanations.
* Intermediate information.

Security design should consider whether every returned field is necessary.

---

### 22. Information Leakage

Model extraction is fundamentally related to information leakage.

A simplified relationship is:

```text
More Output Information
          ↓
More Information Available
          ↓
Potentially Easier Reconstruction
```

This does not mean outputs should always be minimized; rather, organizations should balance utility and exposure.

---

### 23. API Design

The inference API becomes part of the model's security boundary.

Security teams should consider:

* What inputs are accepted?
* What outputs are returned?
* Who can query the model?
* How frequently can they query it?
* Are confidence values necessary?
* Are explanations exposed?
* Are model versions identifiable?

---

### 24. Public Model APIs

Public APIs have a larger potential attack surface because anyone who can legitimately access the service may potentially submit large numbers of queries.

Authentication and authorization therefore become important controls.

---

### 25. Authenticated APIs

Requiring authentication can establish accountability.

For example:

```text
 id="me06"
Client
  ↓
Authentication
  ↓
Authorization
  ↓
Model API
  ↓
Output
```

The organization can then associate model usage with an identity.

---

### 26. Anonymous Access

Anonymous access increases uncertainty because the provider may have limited ability to associate activity with a specific user.

For sensitive proprietary models, anonymous access may therefore increase extraction risk.

---

### 27. API Keys

API keys can identify clients accessing the model.

However, they should be treated as sensitive credentials because compromised keys may be used to generate unauthorized queries.

---

### 28. Account-Level Controls

Organizations can establish limits at the account level, such as:

* Query quotas.
* Rate limits.
* Usage thresholds.
* Concurrent-request limits.

These controls can make large-scale extraction more difficult.

---

### 29. Rate Limiting

Rate limiting restricts how quickly requests can be submitted.

```text
 id="me07"
Client
  ↓
100 requests/sec
  ↓
Rate Limiter
  ↓
Allowed / Blocked
```

This can increase the cost and time required for large-scale extraction.

---

### 30. Query Budgets

A model provider may allocate a maximum number of queries to a user or application during a period.

For example:

```text
Daily Query Budget
       ↓
Allowed Requests
       ↓
Budget Exhausted
       ↓
Further Requests Restricted
```

The appropriate threshold depends on legitimate business requirements.

---

### 31. Adaptive Rate Limiting

Static limits are not always sufficient.

A more mature approach can adjust controls based on behavior.

For example:

```text
Normal Activity
     ↓
Standard Limits

Suspicious Activity
     ↓
Stricter Limits
```

---

### 32. Behavioral Detection

Model extraction may produce distinctive usage patterns.

Potential indicators include:

* Very high query volume.
* Systematic input variation.
* Repeated probing.
* Unusual query distributions.
* Multiple accounts targeting the same model.
* Continuous automated access.

No single indicator proves extraction.

---

### 33. Systematic Querying

An attacker may submit carefully selected inputs rather than ordinary business requests.

For example:

```text
Input 1
Input 2
Input 3
...
Input N
```

The objective may be to obtain informative observations rather than business results.

---

### 34. Automated Query Generation

Extraction can be automated.

```text
Query Generator
      ↓
Model API
      ↓
Responses
      ↓
Training Dataset
      ↓
Substitute Model
```

Automation can dramatically increase the number of observations collected.

---

### 35. Query Diversity

Attackers may deliberately vary inputs to explore different regions of the model's behavior.

For example:

```text
Normal Inputs
      +
Edge Cases
      +
Boundary Inputs
      +
Rare Inputs
```

This can provide a broader picture of model behavior.

---

### 36. Strategic Query Selection

Not all queries provide equal information.

An attacker may attempt to select inputs that reveal useful distinctions in model behavior.

From a defensive perspective, unusual patterns of highly systematic probing can be a useful detection signal.

---

### 37. Extraction Dataset

The attacker's collected responses may become a training dataset:

```text
Target Model
     ↓
Input / Output Pairs
     ↓
Extraction Dataset
     ↓
Substitute Training
```

The dataset can encode observed behavior without containing the original model weights.

---

### 38. Knowledge Transfer

The target model effectively becomes a source of behavioral information for the substitute model.

```text
Target
  ↓
Behavioral Knowledge
  ↓
Substitute
```

This is why model extraction is sometimes discussed in the context of **knowledge transfer**.

---

### 39. Distillation Relationship

Model extraction can overlap conceptually with **knowledge distillation**.

In legitimate knowledge distillation:

```text
Teacher Model
      ↓
Student Model
```

The student learns from the teacher's outputs.

In unauthorized extraction:

```text
Proprietary Target
      ↓
Unauthorized Queries
      ↓
Substitute Model
```

The technical mechanisms can overlap even though the governance context is different.

---

### 40. Legitimate vs Malicious Distillation

Knowledge transfer is not inherently malicious.

Organizations may legitimately create smaller models based on a larger model.

The security concern arises when the process is unauthorized or attempts to reproduce proprietary capabilities.

---

### 41. Model Extraction and Access Control

Access control remains one of the primary defenses.

The organization should determine:

```text
Who?
 ↓
Can Query?
 ↓
Which Model?
 ↓
With What Limits?
```

---

### 42. Model-Specific Authorization

Different models may require different access policies.

For example:

```text
Public Model
→ Broad Access

Internal Model
→ Employee Access

Confidential Model
→ Approved Applications

Highly Sensitive Model
→ Restricted Access
```

---

### 43. Application Identity

Rather than treating every API request equally, organizations can identify the calling application.

This can help establish:

* Which application is querying.
* Which business process it supports.
* Expected usage patterns.

---

### 44. Service-to-Service Authentication

Internal model access can use strong service identities rather than relying solely on network location.

```text
Application
   ↓
Service Identity
   ↓
Authorization
   ↓
Model
```

---

### 45. Tenant Isolation

Multi-tenant systems should ensure that one customer cannot use access intended for another customer to systematically interrogate a protected model.

Tenant boundaries should therefore be part of model-security architecture.

---

### 46. API Gateway Controls

An API gateway can enforce controls before requests reach the model.

```text
Client
  ↓
API Gateway
  ├── Authentication
  ├── Authorization
  ├── Rate Limiting
  ├── Logging
  └── Threat Detection
  ↓
Model
```

This provides a centralized enforcement point.

---

### 47. Monitoring Query Patterns

Security monitoring should consider not only how many requests are made but **how they are made**.

For example:

```text
Normal:
Business Queries

Potentially Suspicious:
Highly Systematic Queries
```

Context remains important.

---

### 48. Baseline Behavior

An organization should understand normal model usage.

A baseline might include:

* Typical requests per user.
* Typical request frequency.
* Normal geographic sources.
* Normal applications.
* Typical model versions.
* Typical output patterns.

Anomalies can then be detected more effectively.

---

### 49. Detection Thresholds

Detection thresholds should be calibrated carefully.

Too low:

```text
Many False Positives
```

Too high:

```text
Extraction May Continue Undetected
```

The goal is an appropriate balance between security and operational usability.

---

### 50. Core Principle

Model extraction protection begins with understanding that **an inference interface can become an indirect channel for learning proprietary model behavior**.

The security objective is therefore to balance:

```text
Model Utility
      +
Customer Access
      +
Performance
      +
Security
      +
Intellectual-Property Protection
```

while ensuring that legitimate users can continue to obtain the intended model service without unnecessarily exposing information that makes unauthorized reconstruction easier.


# 09.06 — Model Extraction

## Part 2

### 51. Extraction Attack Surface

The model extraction attack surface consists of every interface through which an attacker can obtain information about model behavior.

This may include:

* Public APIs.
* Internal APIs.
* Web applications.
* Mobile applications.
* SDKs.
* Batch inference services.
* Interactive AI interfaces.
* Model-as-a-service platforms.

The broader the accessible interface, the greater the potential observation surface.

---

### 52. Direct Query Interface

The most straightforward extraction scenario involves direct access to a prediction API.

```text
Attacker
   ↓
Inference API
   ↓
Target Model
   ↓
Prediction
```

The attacker repeatedly collects input/output relationships.

---

### 53. Indirect Query Interface

The model may not be directly exposed.

Instead:

```text
User
  ↓
Application
  ↓
Business Logic
  ↓
Model
  ↓
Application Response
```

Even in this architecture, application responses may reveal information about model decisions.

---

### 54. Web Application Exposure

A web application may expose a proprietary model indirectly.

For example, an application could use an ML model to:

* Classify transactions.
* Recommend products.
* Detect fraud.
* Rank content.
* Assess risk.

Repeated interaction with the application may provide observations about model behavior.

---

### 55. Mobile Application Exposure

A mobile application may interact with a remote model service.

Security teams should consider whether:

* API endpoints are discoverable.
* Authentication can be bypassed.
* Excessive output information is exposed.
* Requests can be automated.

---

### 56. SDK Exposure

An SDK may simplify legitimate access to a model but can also make systematic querying easier.

Security controls should therefore be enforced at the service layer rather than relying solely on the client SDK.

---

### 57. Batch Inference

Batch inference interfaces can present a different extraction risk.

A service that accepts large numbers of inputs simultaneously may allow an attacker to generate substantial observations efficiently.

---

### 58. Interactive Interfaces

Interactive model services may expose additional information through:

* Explanations.
* Confidence values.
* Scores.
* Rankings.
* Generated outputs.

The more information returned, the greater the potential information available to an attacker.

---

### 59. Output Granularity

Consider two APIs:

```text
API A:
Approved

API B:
Approved
Confidence: 97.3%
Risk Score: 0.027
Model Version: 4.2
```

API B provides considerably more information.

Security architecture should therefore evaluate whether each output element is necessary.

---

### 60. Confidence Score Exposure

Confidence scores can provide information about how strongly the model favors a prediction.

This may assist an attacker attempting to reproduce model behavior.

For sensitive models, confidence exposure should be deliberately evaluated rather than automatically enabled.

---

### 61. Probability Distribution Exposure

Returning the full probability distribution may provide even more information.

For example:

```text
Class A: 0.82
Class B: 0.12
Class C: 0.06
```

A simple classification label would reveal less information.

---

### 62. Ranking Information

Recommendation and ranking systems may expose relative model preferences.

For example:

```text
Item A → Rank 1
Item B → Rank 2
Item C → Rank 3
```

Repeated observations can reveal aspects of the underlying scoring behavior.

---

### 63. Score Exposure

A numerical score can reveal more than a binary decision.

```text
Decision:
Reject

Score:
0.91
```

The numerical output may provide additional information useful for behavioral approximation.

---

### 64. Explanation Exposure

Explainability features can improve transparency for legitimate users but may also expose information about model behavior.

Security teams should therefore evaluate the security implications of:

* Feature importance.
* Reason codes.
* Explanations.
* Decision rationale.

---

### 65. Model Version Disclosure

An API that explicitly returns the model version may reveal information about the underlying system.

For example:

```text
Model-Version: fraud-model-7.4
```

Whether such metadata should be exposed depends on the application and threat model.

---

### 66. Error Messages

Errors can also reveal information.

For example:

```text
Invalid request
```

reveals less than:

```text
Model fraud-v7.4 rejected feature X
```

Production systems should avoid unnecessarily detailed model-related error messages.

---

### 67. Timing Information

Response timing can sometimes reveal information about the underlying processing path.

For example:

```text
Input A → 40 ms
Input B → 110 ms
```

Differences may result from many legitimate factors, so timing should be interpreted cautiously.

---

### 68. Side-Channel Considerations

Model extraction can sometimes intersect with side-channel analysis.

Potential observable characteristics may include:

* Response time.
* Resource behavior.
* Error behavior.
* Output structure.

These should be considered within the organization's broader application-security threat model.

---

### 69. Query Authentication

Authentication establishes the identity associated with a request.

Possible mechanisms include:

* API keys.
* OAuth.
* Mutual TLS.
* Federated identity.
* Signed requests.

The appropriate mechanism depends on the deployment model.

---

### 70. Strong Client Identity

For sensitive model services, identifying the requesting application can be more useful than relying solely on anonymous requests.

```text
Application Identity
       ↓
Authenticated Request
       ↓
Model Service
```

This improves accountability.

---

### 71. Authorization Scope

Authorization should determine what the authenticated client can do.

For example:

```text
Client A
→ Model A

Client B
→ Model B

Admin
→ Approved administrative operations
```

Access should not automatically extend across all models.

---

### 72. Per-Model Policies

A mature architecture may define security policies individually for high-value models.

For example:

```text
Model A → 1,000 requests/hour
Model B → 100 requests/hour
Model C → Internal only
```

The appropriate policies depend on business requirements.

---

### 73. Per-User Quotas

Query quotas can limit the number of requests a user can make within a defined period.

This can reduce the amount of information an attacker can collect.

---

### 74. Per-Application Quotas

Applications may also receive individual quotas.

This is particularly useful when different applications have different legitimate usage patterns.

---

### 75. Per-Tenant Quotas

In multi-tenant environments, query limits can be enforced at the tenant level.

This helps prevent one tenant from consuming disproportionate inference capacity or systematically probing a shared service.

---

### 76. Global Model Quotas

Organizations may also establish aggregate limits for particularly sensitive models.

This can provide an additional control if multiple accounts are used to target the same model.

---

### 77. Account Multiplication

An attacker may attempt to circumvent per-account limits by creating multiple accounts.

```text
Account A ─┐
Account B ─┤
Account C ─┼→ Target Model
Account D ─┤
Account E ─┘
```

Therefore, account-level controls may need to be complemented by broader behavioral monitoring.

---

### 78. Sybil-Like Behavior

Multiple accounts controlled by one actor can make extraction more difficult to detect.

Organizations can look for relationships between:

* Account creation.
* Device characteristics.
* Network origins.
* Request patterns.
* Payment information.
* Application identifiers.

Such signals should be evaluated according to applicable privacy and security requirements.

---

### 79. Distributed Querying

An attacker may distribute requests across multiple systems or identities.

```text
Source A ─┐
Source B ─┤
Source C ─┼→ Model API
Source D ─┘
```

This can bypass simple source-based rate limits.

---

### 80. Detection Beyond IP Addresses

IP-based controls alone may be insufficient.

An organization can consider additional signals such as:

* User identity.
* API key.
* Device identity.
* Application identity.
* Tenant.
* Behavioral patterns.

---

### 81. Query Fingerprinting

Security teams can look for characteristic patterns in model queries.

For example:

```text
Repeated
Systematic
Automated
High-volume
Input Variation
```

These characteristics may indicate behavior inconsistent with normal application use.

---

### 82. Normal Usage vs Extraction

Consider two users:

```text
User A:
20 business requests/day

User B:
20,000 systematically varied requests/day
```

The second pattern warrants investigation even if both users are authenticated.

---

### 83. Temporal Patterns

Extraction activity may occur continuously or in bursts.

Examples:

```text
Normal:
09:00 → 17:00 business activity

Potentially suspicious:
02:00 → 05:00 automated burst
```

Time is only one contextual signal.

---

### 84. Query Diversity

Normal business applications often have predictable input distributions.

An extraction attempt may deliberately generate a much wider range of inputs.

```text
Normal:
Common Inputs

Potential Extraction:
Broad Input Space
```

Monitoring unusual input distributions can therefore contribute to detection.

---

### 85. Boundary Exploration

An attacker may be interested in inputs around classification boundaries.

Conceptually:

```text
Class A
─────────────
       ↑
   Boundary
       ↓
─────────────
Class B
```

Systematic exploration of such areas can potentially provide useful information about model behavior.

---

### 86. Adaptive Querying

An attacker may use each response to determine what query to submit next.

```text
Query
 ↓
Response
 ↓
Analysis
 ↓
Next Query
 ↓
Response
 ↓
Analysis
```

This creates a feedback loop.

---

### 87. Automated Extraction Pipeline

A conceptual extraction pipeline can be represented as:

```text
Query Generator
       ↓
Target API
       ↓
Response Collector
       ↓
Dataset
       ↓
Training Process
       ↓
Substitute Model
       ↓
Evaluation
```

Automation can significantly accelerate this process.

---

### 88. Substitute Model Architecture

The substitute model does not necessarily need to use the same architecture as the target.

For example:

```text
Target:
Architecture A

Substitute:
Architecture B
```

The objective is behavioral similarity rather than architectural duplication.

---

### 89. Architecture Agnosticism

This creates an important security consideration:

> Protecting the architecture does not necessarily prevent behavioral extraction.

Even if the attacker cannot determine the original architecture, they may still approximate its outputs.

---

### 90. Model Behavior as an Asset

Traditional security programs often focus on protecting:

* Source code.
* Databases.
* Credentials.
* Files.

Model extraction demonstrates that **model behavior itself can be a valuable asset**.

---

### 91. Behavioral Confidentiality

Organizations may therefore consider whether the behavior of a high-value model should be treated as confidential.

This can influence:

* API design.
* Output design.
* Access control.
* Monitoring.
* Rate limits.

---

### 92. Model Complexity

More complex models may require more observations to approximate accurately, but complexity alone should not be treated as a security control.

An attacker may still obtain a useful approximation.

---

### 93. Model Size

Large models may be more difficult and expensive to reproduce.

However, an attacker may not need an identical model.

A smaller substitute that reproduces the relevant behavior may still be valuable.

---

### 94. Partial Extraction

An attacker may target only a subset of model behavior.

For example:

```text
Entire Model
     ↓
Relevant Capability
     ↓
Partial Substitute
```

Partial extraction can still have significant business or security impact.

---

### 95. Domain-Specific Extraction

A general-purpose model may be too broad to reproduce completely.

An attacker may instead focus on a particular domain:

* Fraud detection.
* Medical classification.
* Product recommendation.
* Financial risk.
* Image recognition.

---

### 96. Targeted Behavioral Reconstruction

For a targeted attack, the attacker may only need to reproduce decisions relevant to a specific objective.

This can make extraction more practical than attempting to replicate the entire model.

---

### 97. Extraction Quality

Security teams should understand that extraction success is not binary.

A substitute model can have:

* Low similarity.
* Moderate similarity.
* High similarity.

The business impact depends on what the attacker can accomplish with the resulting model.

---

### 98. Evaluation of Extraction Risk

An organization can assess:

1. How accessible is the model?
2. How informative are its outputs?
3. How many queries can a client submit?
4. How easy is automated querying?
5. How valuable is the model?
6. How detectable would systematic querying be?

These factors can help prioritize controls.

---

### 99. Risk Reduction Strategy

A practical strategy is:

```text
Reduce Unnecessary Access
          ↓
Reduce Output Exposure
          ↓
Limit Query Volume
          ↓
Monitor Behavior
          ↓
Detect Anomalies
          ↓
Respond to Abuse
```

No individual measure is necessarily sufficient.

---

### 100. Core Principle

Model extraction protection should recognize that **every legitimate inference interaction can potentially reveal information about model behavior**.

The objective is not to prevent legitimate model use. It is to control the amount of information that can be systematically collected while maintaining:

```text
Legitimate Utility
        +
Strong Identity
        +
Appropriate Authorization
        +
Controlled Query Volume
        +
Minimal Necessary Output
        +
Behavioral Monitoring
        +
Abuse Response
```

This allows organizations to preserve the usefulness of model services while reducing the opportunity for unauthorized behavioral reconstruction.

# 09.06 — Model Extraction

## Part 3

### 101. Extraction Methodologies

Model extraction can occur through different methodological approaches depending on the type of model, information exposed by the interface, and objective of the attacker.

At a conceptual level, extraction can involve:

* Querying the model with existing data.
* Generating informative inputs.
* Learning from model outputs.
* Training a substitute model.
* Comparing substitute and target behavior.

The exact technique depends on the target architecture and available information.

---

### 102. Label-Based Extraction

A target model may return only a predicted label.

For example:

```text id="p7v3ka"
Input
  ↓
Target Model
  ↓
Class A
```

The attacker can collect many input/label pairs and use them to train a substitute.

This provides less information than probability-based outputs but can still reveal useful behavior.

---

### 103. Score-Based Extraction

If the service returns numerical scores, the attacker may obtain more information.

```text id="m4q8xn"
Input
  ↓
Target Model
  ↓
Class A
Score: 0.87
```

The additional score can help characterize how strongly the model responds to different inputs.

---

### 104. Probability-Based Extraction

A model may expose a probability vector:

```text id="w8c2pf"
A = 0.78
B = 0.17
C = 0.05
```

This provides substantially richer information than a single class label.

The security team should therefore assess whether full probability disclosure is necessary.

---

### 105. Ranking-Based Extraction

Recommendation systems may expose ranked outputs rather than explicit classifications.

For example:

```text id="z6n4vb"
Input
  ↓
Recommendation Model
  ↓
1. Product A
2. Product B
3. Product C
```

Repeated queries can reveal aspects of the ranking function.

---

### 106. Regression Model Extraction

Extraction is not limited to classification.

A regression model may return a numerical prediction:

```text id="f5x7mc"
Input
  ↓
Model
  ↓
Prediction: 73.4
```

A sufficiently large collection of input/output observations may allow an attacker to approximate the function.

---

### 107. Recommendation Model Extraction

Recommendation systems can be particularly interesting because their outputs reveal preferences or ranking behavior.

An attacker may observe:

```text id="q9k3wp"
User / Context
       ↓
Recommended Items
       ↓
Ranking
```

Repeated observations can expose aspects of the recommendation logic.

---

### 108. Fraud Model Extraction

Consider a fraud-detection system:

```text id="b3m8qa"
Transaction
    ↓
Fraud Model
    ↓
Risk Decision
```

An attacker could potentially attempt to learn how transaction characteristics influence the model's decisions.

This creates both intellectual-property and security concerns.

---

### 109. Credit or Risk Models

Models used for risk assessment may also represent valuable proprietary decision logic.

Behavioral extraction could expose how different input characteristics affect the resulting risk assessment.

Because such systems can be highly sensitive, access and output controls should be carefully designed.

---

### 110. Computer-Vision Models

A vision model may expose predictions such as:

```text id="n6v4xz"
Image
 ↓
Model
 ↓
Object A: 0.91
Object B: 0.06
```

Repeated queries can provide observations about how the model responds to different visual inputs.

---

### 111. Natural-Language Models

Language models introduce additional considerations because outputs are often rich rather than simple labels.

Potentially exposed information can include:

* Generated text.
* Rankings.
* Scores.
* Tool decisions.
* Structured outputs.
* Model metadata.

The extraction problem can therefore differ significantly from conventional classification.

---

### 112. API-Based Language Model Extraction

A simplified architecture is:

```text id="c8p5vn"
Attacker
   ↓
Prompt
   ↓
Language Model API
   ↓
Generated Response
   ↓
Collected Dataset
```

The attacker may attempt to use repeated interactions to reproduce selected capabilities.

---

### 113. Capability-Focused Extraction

For complex models, complete reproduction may be unnecessary.

An attacker may target a particular capability:

```text id="x4m7ka"
Large Model
    ↓
Target Capability
    ↓
Approximate Substitute
```

This can reduce the amount of information required.

---

### 114. Functional Extraction

Functional extraction focuses on reproducing what the model does rather than how it does it.

For example:

```text id="g7n2wp"
Original:
Input → Proprietary Model → Decision

Extracted:
Input → Substitute Model → Similar Decision
```

The internal implementations can differ.

---

### 115. Architecture Extraction

In some circumstances, an attacker may also attempt to infer architectural characteristics.

Potential observations might include:

* Response behavior.
* Output dimensions.
* Model metadata.
* API characteristics.
* Performance patterns.

However, architecture inference and behavioral extraction are distinct objectives.

---

### 116. Parameter Extraction

Direct recovery of model parameters is generally more difficult than simply learning model behavior.

An attacker may therefore focus on producing a functionally equivalent substitute rather than recovering the exact original parameters.

---

### 117. Exact vs Approximate Extraction

Two broad outcomes can be considered:

```text id="h5x9qc"
Exact Recovery
    ↓
Original Parameters / Artifact

Approximate Recovery
    ↓
Behaviorally Similar Substitute
```

Approximate extraction can still represent a major security concern.

---

### 118. Query Efficiency

The number of queries required is an important factor.

A highly query-efficient extraction process requires fewer interactions to obtain useful information.

From a defender's perspective:

> **Reducing unnecessary information per query can increase the difficulty of extraction.**

---

### 119. Query Complexity

Extraction difficulty can depend on:

* Model complexity.
* Input space.
* Output information.
* Query budget.
* Substitute architecture.
* Quality of available data.

No single factor determines extraction feasibility.

---

### 120. Extraction Cost

Attackers must generally invest resources in:

* Queries.
* Compute.
* Storage.
* Training.
* Evaluation.

Defensive controls can increase these costs without necessarily preventing all extraction.

---

### 121. Economic Deterrence

Rate limits and usage pricing can increase the economic cost of large-scale querying.

For example:

```text id="k2w6pm"
More Queries
    ↓
Higher Cost
    ↓
Higher Extraction Barrier
```

This is especially relevant for public commercial APIs.

---

### 122. Query Pricing

Charging for inference does not automatically prevent extraction.

An attacker may determine that the value of the resulting model exceeds the cost of the queries.

Therefore, pricing should be considered a complementary control rather than a security mechanism by itself.

---

### 123. Query Budgets and Risk

A fixed query budget can reduce extraction opportunity.

For sensitive services, the organization may establish:

* Per-user limits.
* Per-application limits.
* Per-model limits.
* Time-based quotas.

---

### 124. Adaptive Controls

Controls can become stricter when suspicious activity is detected.

```text id="q4m7xa"
Normal Usage
     ↓
Normal Limits

Suspicious Pattern
     ↓
Increased Restrictions
     ↓
Investigation
```

This reduces unnecessary friction for legitimate users.

---

### 125. Progressive Friction

A service may introduce additional controls as risk increases.

For example:

```text id="b6n3wp"
Normal
 ↓
Rate Limit
 ↓
Challenge
 ↓
Temporary Restriction
 ↓
Manual Review
```

The exact controls should be appropriate to the service.

---

### 126. Behavioral Rate Limiting

Traditional rate limiting asks:

> How many requests were made?

Behavioral rate limiting can additionally ask:

> What kind of requests are being made?

This distinction is important because extraction can be systematic rather than merely high-volume.

---

### 127. Input Distribution Monitoring

Security teams may establish expected input distributions.

A sudden shift can indicate:

* Abuse.
* Automation.
* Testing.
* Extraction.
* A legitimate change in business use.

Context is therefore essential.

---

### 128. User Behavior Analytics

User and entity behavior analytics can identify unusual activity across multiple signals.

For example:

```text id="r8x5mc"
Identity
  +
Device
  +
Application
  +
Query Pattern
  +
Volume
      ↓
Risk Score
```

This can be integrated with existing enterprise security monitoring.

---

### 129. Detection Engineering

Organizations should define detection rules around meaningful extraction indicators.

Examples may include:

* Abnormally high model-query volume.
* Systematic query patterns.
* Unusual API clients.
* Repeated access to sensitive models.
* Unusual activity outside normal business patterns.

---

### 130. Detection Without False Positives

High-volume usage is not automatically malicious.

For example:

```text id="n7k4wp"
Legitimate:
Automated Business Application

Suspicious:
Unauthorized Automated Querying
```

Detection should therefore incorporate identity, application purpose, historical behavior, and other contextual signals.

---

### 131. Canary Inputs

Some organizations may use controlled test inputs to evaluate whether a service is being systematically probed.

This should be implemented carefully and consistently with the organization's security and privacy requirements.

---

### 132. Honeytokens for Model Services

A service may include carefully controlled markers or identifiers that help identify unauthorized use.

Such mechanisms can support investigation but should not replace fundamental security controls.

---

### 133. Model Fingerprinting

Organizations can maintain behavioral or cryptographic fingerprints where appropriate.

For example:

```text id="v4p8qa"
Trusted Model
     ↓
Reference Behavior
     ↓
Comparison
     ↓
Potential Copy Identified
```

Behavioral fingerprinting can be challenging and should be interpreted carefully.

---

### 134. Detecting a Stolen Substitute

An extracted model may be deployed somewhere outside the organization's environment.

Detection may therefore depend on:

* Public-service observation.
* Known model characteristics.
* Legal monitoring.
* Threat intelligence.
* Watermarking or fingerprinting mechanisms.

---

### 135. Model Watermarks

A watermark can potentially help demonstrate that a model or its behavior is derived from a protected source.

However, watermarking methods vary significantly in strength and should not be treated as universally reliable.

---

### 136. Extraction Resilience Testing

Organizations can conduct authorized testing to determine how easily a model could be approximated.

The test can evaluate:

```text id="e5q8xm"
Query Budget
     ↓
Observed Outputs
     ↓
Substitute Model
     ↓
Similarity Assessment
```

This allows defenders to understand practical exposure.

---

### 137. Red-Team Model Extraction

A security or AI red team can simulate extraction against an authorized target.

The objective is to determine:

* What information is exposed?
* How many queries are needed?
* Which controls detect the activity?
* How effective are rate limits?
* How quickly can access be contained?

---

### 138. Extraction Security Testing

Testing should ideally be performed in a controlled environment or under explicit authorization.

The results can then be used to improve:

* API design.
* Access controls.
* Monitoring.
* Detection rules.
* Model governance.

---

### 139. Extraction Success Metrics

A security assessment can measure:

* Query count.
* Time required.
* Cost.
* Substitute-model accuracy.
* Similarity to target.
* Detection time.
* Response time.

These provide measurable indicators of exposure.

---

### 140. Fidelity Testing

A substitute model can be evaluated against the target using an authorized evaluation dataset.

Conceptually:

```text id="w3n7kp"
Target Prediction
       ↕
Substitute Prediction
       ↓
Similarity / Fidelity
```

Higher similarity indicates greater behavioral reproduction.

---

### 141. Security vs Utility Trade-Off

Defensive controls can affect legitimate users.

For example:

```text id="x8m4qa"
More Restrictions
      ↓
Lower Extraction Risk
      +
Potentially Lower Usability
```

Security architecture must therefore balance protection against legitimate operational requirements.

---

### 142. Output Reduction

One defensive strategy is to return only the information necessary for the intended use case.

For example:

```text id="q5c8mn"
Instead of:
Label + probabilities + scores + metadata

Return:
Required business result
```

This can reduce unnecessary information exposure.

---

### 143. Confidence Quantization

Where appropriate, organizations may reduce the precision of confidence information.

For example:

```text id="p4w7xa"
0.937481
   ↓
0.94
```

Whether this is appropriate depends on the application's requirements.

---

### 144. Output Rounding

Rounding numerical outputs can reduce precision while preserving business utility in some use cases.

It is not a universal defense and should be evaluated against actual extraction risk.

---

### 145. Output Transformation

In some systems, raw model scores may be transformed into application-level decisions.

```text id="m7x2pc"
Raw Model Score
      ↓
Business Logic
      ↓
Application Result
```

This can reduce direct exposure of internal model behavior.

---

### 146. Model Ensemble Considerations

Some systems use multiple models or ensemble methods.

The observable behavior may then result from several components:

```text id="f8n3qa"
Model A ─┐
Model B ─┼→ Ensemble → Output
Model C ─┘
```

This can alter extraction characteristics but should not be assumed to make extraction impossible.

---

### 147. Randomization

Certain systems may introduce controlled randomness in outputs.

However, randomness can reduce legitimate predictability and should only be considered where it does not compromise business requirements.

---

### 148. Defensive Model Design

Model extraction should be considered during model and API design rather than only after deployment.

Design questions include:

* What must the API return?
* What can remain internal?
* Who needs access?
* What usage level is legitimate?
* What behavior should trigger investigation?

---

### 149. Secure-by-Design Model APIs

A secure-by-design API considers:

```text id="z6k4wp"
Identity
   ↓
Authorization
   ↓
Minimal Output
   ↓
Rate Control
   ↓
Logging
   ↓
Monitoring
   ↓
Response
```

These controls should be integrated into the service architecture.

---

### 150. Core Principle

Model extraction defense requires treating **model inference as an information-exposure channel**.

A mature security posture therefore combines:

```text id="c7m2xa"
Access Control
      +
Output Minimization
      +
Query Governance
      +
Behavioral Monitoring
      +
Detection
      +
Authorized Security Testing
```

The goal is to make unauthorized reconstruction sufficiently difficult, expensive, and detectable while preserving the legitimate functionality of the model service.

# 09.06 — Model Extraction

## Part 4

### 151. Model Extraction Governance

Model extraction should be treated as an enterprise AI-security and intellectual-property risk rather than solely as an API-security issue.

Governance should define:

* Which models are considered sensitive.
* Who owns each model.
* Who may access each model.
* Which interfaces expose the model.
* What level of output may be returned.
* What constitutes suspicious usage.
* Who responds to suspected extraction.

---

### 152. Model Classification

Not every model requires the same level of protection.

A practical classification could be:

| Classification   | Example                     | Protection                          |
| ---------------- | --------------------------- | ----------------------------------- |
| Public           | Open model                  | Standard controls                   |
| Internal         | Internal business model     | Authenticated access                |
| Confidential     | Proprietary ML model        | Restricted access + monitoring      |
| Highly Sensitive | Strategic/crown-jewel model | Strong access + enhanced monitoring |

Classification should reflect business value and potential impact.

---

### 153. Model Owner

Every sensitive model should have an accountable owner.

The owner may be responsible for:

* Business justification.
* Access approval.
* Risk acceptance.
* Security requirements.
* Model retirement.
* Incident escalation.

---

### 154. Model Security Requirements

Security requirements should be defined before deployment.

For example:

```text id="8x3mqp"
Model
 ↓
Classification
 ↓
Security Requirements
 ↓
API Design
 ↓
Deployment
```

This prevents security controls from becoming an afterthought.

---

### 155. Model Threat Model

The threat model should identify extraction paths.

Questions may include:

* Is the model public?
* Is the API Internet-facing?
* Can users make unlimited requests?
* Are probability scores exposed?
* Are explanations exposed?
* Can users automate requests?
* Can multiple accounts access the same model?

---

### 156. Crown-Jewel Models

Some models may represent significant competitive advantage.

These should receive enhanced protection.

Potential examples include:

* Proprietary recommendation algorithms.
* High-value fraud models.
* Strategic forecasting models.
* Specialized AI systems.
* Models incorporating substantial proprietary research.

---

### 157. Model Registry Controls

The model registry should enforce appropriate access restrictions.

Potential controls include:

* Role-based access control.
* Strong authentication.
* Approval workflows.
* Audit logging.
* Version control.
* Artifact integrity verification.

---

### 158. Separation of Model Permissions

Model permissions should distinguish between different actions.

For example:

```text id="r6m8wc"
View Metadata
      ≠
Run Inference
      ≠
Download Model
      ≠
Modify Model
      ≠
Delete Model
```

This reduces unnecessary privilege.

---

### 159. Read vs Export Permissions

A user may legitimately need to inspect model metadata without needing permission to export the model.

Similarly, an application may need inference access without needing access to the underlying artifact.

---

### 160. Administrative Access

Administrative access to model infrastructure should be tightly controlled.

Potential controls include:

* Privileged access management.
* MFA.
* Just-in-time access.
* Session monitoring.
* Strong audit trails.

---

### 161. Service Accounts

Service accounts should have only the permissions necessary for their function.

For example:

```text id="n4q7xp"
Application A
    ↓
Inference Permission
    ↓
Model A

No:
Model Download
Model Modification
Model Deletion
```

---

### 162. Secrets Management

API credentials, service credentials, and other secrets used by model services should be stored using approved enterprise secrets-management mechanisms.

Secrets should not be embedded in:

* Source code.
* Containers.
* Configuration files.
* Public repositories.

---

### 163. Credential Rotation

Credentials associated with sensitive model services should be rotated according to organizational policy and immediately when compromise is suspected.

---

### 164. Network Architecture

A sensitive model should ideally reside within a controlled architecture.

```text id="x5k9va"
Internet
   ↓
WAF / API Gateway
   ↓
Application
   ↓
Inference Service
   ↓
Protected Model
```

Each layer can provide an additional security boundary.

---

### 165. Web Application Firewall

Where appropriate, a WAF can help protect Internet-facing application interfaces.

However, WAF controls primarily address application-layer threats and should not be considered a dedicated model-extraction defense.

---

### 166. API Gateway

The API gateway can act as a centralized enforcement point for:

* Authentication.
* Authorization.
* Rate limiting.
* Logging.
* Request validation.
* Traffic analysis.

---

### 167. Model Endpoint Isolation

Sensitive model endpoints should not necessarily be directly accessible from the public Internet.

A common architecture is:

```text id="c8n4qm"
Public Client
      ↓
Public API
      ↓
Private Network
      ↓
Model Service
```

This separates the public interface from the model execution environment.

---

### 168. Egress Restrictions

Inference environments can be restricted from making unnecessary outbound connections.

This can reduce opportunities for an attacker who compromises the environment to exfiltrate model artifacts.

---

### 169. Artifact Repository Protection

The repository storing model artifacts should have strong controls around:

* Authentication.
* Authorization.
* Encryption.
* Versioning.
* Integrity.
* Logging.
* Export.

---

### 170. Backup Protection

Model backups should receive protection comparable to production copies.

Otherwise:

```text id="q3m7xa"
Production Model
     ↓
Strong Security

Backup Model
     ↓
Weak Security
     ↓
Potential Attack Path
```

The weakest copy can become the practical target.

---

### 171. Development Security

Development environments should be considered part of the model protection boundary.

Developers may have access to:

* Model checkpoints.
* Training artifacts.
* Evaluation datasets.
* Source code.
* Configuration.

Access should be controlled according to business need.

---

### 172. Testing Environment

Test environments should not automatically receive unrestricted copies of production models.

Where possible, organizations should use:

* Appropriate model variants.
* Restricted access.
* Synthetic or approved test data.
* Controlled model copies.

---

### 173. Model Copy Tracking

Organizations should maintain visibility over where sensitive models are copied.

For example:

```text id="z9k4wp"

  ├── Production
  ├── DR
  ├── Testing
```

Unauthorized copies should be investigated.

### 176. Cloud Security Monitoring

### 200. Core Principle

Model extraction represents a fundamental challenge for organizations that expose proprietary models through inference services.

The model does not need to be directly downloaded for its value to be compromised.

A mature enterprise approach therefore combines:

```text id="x6q3mp"
MODEL CLASSIFICATION
        ↓
CLEAR OWNERSHIP
        ↓
LEAST-PRIVILEGE ACCESS
        ↓
SECURE API DESIGN
        ↓
MINIMAL NECESSARY OUTPUT
        ↓
QUERY GOVERNANCE
        ↓
BEHAVIORAL MONITORING
        ↓
EXTRACTION TESTING
        ↓
DETECTION
        ↓
RAPID RESPONSE
```

The fundamental security objective is to **preserve control over proprietary model behavior while allowing legitimate users and applications to obtain the functionality they require**.
