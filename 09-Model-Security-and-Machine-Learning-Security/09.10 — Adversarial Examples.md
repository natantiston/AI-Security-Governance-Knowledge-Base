# 09.10 — Adversarial Examples

## Part 1

### 1. Adversarial Examples

An **adversarial example** is an input intentionally modified to cause a machine-learning model to produce an incorrect or undesirable output.

The defining characteristic is that the modification is designed specifically to exploit weaknesses in the model's learned decision behavior.

```text
Legitimate Input
       ↓
Adversarial Modification
       ↓
Adversarial Example
       ↓
ML Model
       ↓
Incorrect / Undesired Output
```

---

### 2. Why Adversarial Examples Matter

Traditional applications generally process inputs according to explicitly programmed rules.

Machine-learning models instead learn statistical relationships from data.

This creates a different security problem:

```text
Traditional Software
Input → Explicit Logic → Output

Machine Learning
Input → Learned Representation → Prediction
```

An attacker may exploit weaknesses in those learned representations without exploiting a conventional software vulnerability.

---

### 3. The Fundamental Security Problem

The central problem can be expressed as:

> **A small or carefully designed change to an input can produce a disproportionately large change in the model's prediction.**

Conceptually:

```text
Input A
   ↓
Model
   ↓
Correct Prediction

Input A + Adversarial Modification
   ↓
Model
   ↓
Incorrect Prediction
```

The model itself may remain completely operational.

---

### 4. Adversarial Example vs. Ordinary Error

Not every incorrect prediction is an adversarial example.

An ordinary model error may occur because:

* The input is ambiguous.
* The model lacks sufficient training data.
* The environment changed.
* The model is inherently imperfect.

An adversarial example involves **intentional manipulation designed to influence the model**.

---

### 5. Adversarial Example vs. Data Poisoning

These attacks occur at different stages.

| Attack              | Primary Stage                |
| ------------------- | ---------------------------- |
| Adversarial example | Inference                    |
| Data poisoning      | Training                     |
| Backdoor            | Usually training/development |
| Model tampering     | Deployment/runtime           |
| Model extraction    | Inference/API                |

An adversarial example primarily targets a model that is already being used for prediction.

---

### 6. Inference-Time Attack

Adversarial examples are generally associated with inference-time manipulation.

```text
Training
   ↓
Model
   ↓
Deployment
   ↓
Attacker Manipulates Input
   ↓
Prediction
```

The attacker does not necessarily need to modify the model itself.

---

### 7. Input Space

Every ML model operates on some representation of input data.

Examples include:

* Images.
* Text.
* Audio.
* Video.
* Network traffic.
* Financial transactions.
* Sensor measurements.
* User behavior.

The collection of possible inputs is commonly referred to as the **input space**.

---

### 8. Perturbation

The modification applied to an input is commonly called a **perturbation**.

Conceptually:

```text
Adversarial Input = Original Input + Perturbation
```

The perturbation may be designed to alter the model's prediction while keeping the input sufficiently usable or realistic.

---

### 9. Digital Perturbation

A digital perturbation directly modifies the machine-readable representation.

Examples include changes to:

* Image pixels.
* Text tokens.
* Audio samples.
* Numerical features.
* File characteristics.

The modification may not be obvious to a human observer.

---

### 10. Physical Perturbation

A physical adversarial example attempts to survive the transition from the physical world into the ML system.

For example:

```text
Physical Object
      ↓
Camera / Sensor
      ↓
Digital Representation
      ↓
ML Model
      ↓
Prediction
```

The attacker must account for real-world conditions.

---

### 11. Image-Based Adversarial Examples

Computer-vision systems are a widely studied environment for adversarial examples.

A model may correctly identify an image under normal conditions but produce a different prediction after carefully designed modifications.

```text
Original Image
     ↓
"Class A"

Modified Image
     ↓
"Class B"
```

---

### 12. Human Perception vs. Model Perception

A major security challenge is that a modification can be relatively difficult for humans to notice while still influencing the model.

```text
Human Observer
      ↓
"Appears Normal"

ML Model
      ↓
"Different Classification"
```

This demonstrates that human perception and machine representation are not equivalent.

---

### 13. Text-Based Adversarial Examples

Text classifiers can also be targeted.

Potentially affected systems include:

* Spam detection.
* Phishing detection.
* Sentiment classification.
* Content classification.
* Fraud detection.
* Security analytics.

Attackers may manipulate textual characteristics to influence classification.

---

### 14. Text Perturbations

Possible forms of textual modification include changes to:

* Words.
* Characters.
* Formatting.
* Tokenization.
* Sentence structure.
* Context.

The effectiveness depends heavily on the model and tokenizer.

---

### 15. Audio-Based Adversarial Examples

Audio ML systems can also be exposed to adversarial inputs.

Examples include:

* Speech recognition.
* Speaker identification.
* Voice authentication.
* Audio classification.

```text
Audio
  ↓
Adversarial Modification
  ↓
Speech / Audio Model
  ↓
Unexpected Result
```

---

### 16. Video-Based Adversarial Examples

Video models process sequences of visual information.

Potential targets include:

* Surveillance.
* Object detection.
* Activity recognition.
* Autonomous systems.

The attacker may attempt to influence the model's interpretation of the video stream.

---

### 17. Sensor-Based Systems

ML systems may consume data from:

* Cameras.
* GPS.
* Accelerometers.
* Temperature sensors.
* Industrial sensors.
* IoT devices.

Manipulation of sensor inputs can potentially become an adversarial ML problem.

---

### 18. Network Security Models

ML-based network security systems may classify:

* Network flows.
* Packets.
* Connection behavior.
* User activity.
* Traffic patterns.

Attackers may attempt to modify observable characteristics while retaining malicious objectives.

---

### 19. Fraud Detection

Fraud detection models can be targeted by manipulating transaction characteristics.

```text
Fraudulent Activity
        ↓
Feature Manipulation
        ↓
ML Fraud Model
        ↓
Lower-Risk Prediction
```

The security concern is that the adversarial example may result in an incorrect business decision.

---

### 20. Malware Detection

ML-based malware detection can also be exposed to adversarial manipulation.

The attacker may attempt to alter observable properties of malicious software while preserving its intended malicious behavior.

---

### 21. Spam and Phishing Detection

Attackers may manipulate messages so that their content appears more consistent with legitimate communications.

The objective is to reduce the likelihood of detection.

---

### 22. Intrusion Detection

Network intrusion detection models can be targeted by attempts to make malicious traffic resemble legitimate traffic.

The attacker is effectively attempting to move the input representation into a region that the model associates with benign behavior.

---

### 23. Identity and Authentication

Adversarial examples can be relevant to ML-based:

* Facial recognition.
* Voice recognition.
* Behavioral authentication.

Because these systems can influence access decisions, their adversarial robustness can have direct security implications.

---

### 24. Autonomous Systems

Autonomous systems may use ML for:

* Object detection.
* Navigation.
* Classification.
* Decision support.

An adversarial input can therefore potentially influence a physical action.

```text
Adversarial Input
       ↓
Perception Model
       ↓
Incorrect Interpretation
       ↓
Decision
       ↓
Physical Action
```

---

### 25. Safety Implications

When ML controls or influences physical systems, adversarial examples should be considered alongside safety engineering.

Potential consequences can include:

* Unsafe operation.
* Incorrect routing.
* Incorrect object identification.
* Failure to recognize hazards.

---

### 26. Targeted Adversarial Examples

A **targeted** adversarial example attempts to force a model toward a particular incorrect output.

```text
Original
   ↓
Class A

Adversarial Input
   ↓
Specifically Desired Class B
```

The attacker cares about the exact incorrect outcome.

---

### 27. Untargeted Adversarial Examples

An **untargeted** adversarial example attempts to cause any incorrect prediction.

```text
Original
   ↓
Class A

Adversarial Input
   ↓
Class B / C / D / ...
```

The attacker does not necessarily care which incorrect class is selected.

---

### 28. Targeted vs. Untargeted Security Risk

Targeted attacks can be particularly important when a specific outcome is required.

For example, an attacker may need a system to classify malicious activity as a specific trusted category rather than merely causing an arbitrary error.

---

### 29. Confidence Manipulation

Some attacks attempt to influence not only the predicted class but also the model's confidence.

For example:

```text
Original:
Malicious → 95% confidence

Manipulated:
Benign → 90% confidence
```

High-confidence incorrect predictions can be particularly dangerous when applications automatically trust model outputs.

---

### 30. Decision Thresholds

Many ML applications convert model scores into decisions.

```text
Model Score
     ↓
Threshold
     ↓
ALLOW / BLOCK
```

An adversarial example may attempt to push the score across the relevant decision boundary.

---

### 31. Decision Boundary

A decision boundary represents a region where the model changes its classification.

Conceptually:

```text
          Class A
        /         \
       /           \
------ Decision Boundary ------
       \           /
        \         /
          Class B
```

An adversarial perturbation may move an input across that boundary.

---

### 32. Why Small Changes Can Matter

ML models operate in high-dimensional mathematical spaces.

A change that appears insignificant to a human may correspond to a meaningful change in the model's internal representation.

```text
Human Perspective
Small Difference
      ↓
"Essentially Same"

Model Representation
      ↓
Different Region
      ↓
Different Prediction
```

---

### 33. High-Dimensional Input

Images, text, audio, and other complex inputs can contain very large numbers of dimensions.

This creates a large mathematical input space in which decision boundaries can be complex.

---

### 34. Feature Space

Models often transform raw inputs into internal representations or features.

```text
Raw Input
   ↓
Feature Representation
   ↓
Decision Function
   ↓
Prediction
```

Adversarial manipulation can affect the representation used by the model.

---

### 35. Representation Vulnerability

If the model learns features that can be manipulated without destroying the legitimate appearance or functionality of the input, an attacker may exploit those features.

This is one reason adversarial robustness is a model-security concern rather than simply an application-validation issue.

---

### 36. Gradient Information

In some ML architectures, gradients describe how the model's output changes with respect to its inputs.

When an attacker has access to sufficient model information, gradients can potentially assist in constructing adversarial inputs.

---

### 37. White-Box Adversarial Attacks

In a white-box scenario, the attacker has substantial knowledge of the model.

Potentially available information includes:

* Architecture.
* Parameters.
* Weights.
* Gradients.
* Preprocessing.

This allows more direct analysis of the model's behavior.

---

### 38. Black-Box Adversarial Attacks

In a black-box scenario, the attacker may only have access to the model through an interface.

```text
Attacker
   ↓
Input
   ↓
API
   ↓
Model
   ↓
Output
```

The attacker can use observable behavior to develop candidate inputs.

---

### 39. Gray-Box Attacks

A gray-box attacker has partial knowledge.

This may include information about:

* Model type.
* Input structure.
* Output classes.
* General architecture.

This falls between full white-box and limited black-box knowledge.

---

### 40. Query-Based Attacks

An attacker may submit multiple inputs and analyze the resulting predictions.

```text
Query 1 → Output
Query 2 → Output
Query 3 → Output
   ↓
Behavioral Analysis
   ↓
Candidate Adversarial Input
```

This is why unrestricted model querying can increase exposure.

---

### 41. Transferability

An important property of adversarial examples is **transferability**.

An adversarial input developed against one model may sometimes affect another model performing a similar task.

```text
Source Model
     ↓
Adversarial Example
     ↓
Target Model
     ↓
Potential Misclassification
```

---

### 42. Security Significance of Transferability

Transferability means an attacker may not need complete knowledge of the target model.

They may develop attacks against a substitute or surrogate model and test whether they work against the target.

---

### 43. Surrogate Models

A surrogate model approximates the behavior of a target model.

The attacker can use the surrogate to study potential weaknesses.

```text
Target Behavior
      ↓
Observed Outputs
      ↓
Surrogate Model
      ↓
Adversarial Testing
```

---

### 44. Physical Transferability

Transferability can also have physical implications.

An attack developed in one environment may behave differently when exposed to:

* Lighting.
* Camera changes.
* Distance.
* Angle.
* Environmental noise.

Therefore, laboratory success does not necessarily mean real-world success.

---

### 45. Robustness

Model robustness refers broadly to the model's ability to maintain acceptable behavior under perturbations and unexpected conditions.

For adversarial examples, robustness means reducing the likelihood that maliciously crafted inputs cause unacceptable model behavior.

---

### 46. Robustness Is Not Absolute

A model should not be described simply as:

> “Adversarial-proof.”

Security should instead specify:

* Which attacks were tested.
* Under what assumptions.
* Against which perturbations.
* With what success criteria.

---

### 47. Threat Model Dependency

Adversarial robustness depends on the threat model.

For example:

```text
Threat Model
     ↓
Attacker Capabilities
     ↓
Allowed Perturbations
     ↓
Security Test
     ↓
Robustness Result
```

Changing attacker capabilities can change the assessment.

---

### 48. Perturbation Constraints

Security testing may define constraints around how much an input can change.

For example:

* Maximum numerical change.
* Maximum visual difference.
* Maximum text modification.
* Maximum sensor deviation.

The constraint should reflect realistic attack conditions.

---

### 49. Imperceptibility

Some adversarial examples are designed to remain difficult for humans to notice.

However, imperceptibility is not always the relevant security requirement.

For many enterprise attacks, the more important question is whether the manipulation is **operationally feasible**.

---

### 50. Operational Feasibility

A useful security assessment asks:

> Can an attacker realistically create and deliver the adversarial input in the target environment?

This includes considering:

* Access.
* Time.
* Equipment.
* Query limitations.
* Physical constraints.
* Detection mechanisms.

---

### 51. Adversarial Example Lifecycle

A simplified lifecycle is:

```text
Reconnaissance
      ↓
Model Understanding
      ↓
Attack Construction
      ↓
Input Delivery
      ↓
Model Prediction
      ↓
Observe Impact
      ↓
Adapt / Repeat
```

The attacker may iterate depending on the available feedback.

---

### 52. Reconnaissance

The attacker may first determine:

* What the model detects.
* What inputs it accepts.
* What outputs it returns.
* How decisions are made.
* Whether the system exposes confidence information.

---

### 53. Attack Construction

The attacker develops an input that attempts to achieve the desired model behavior.

The exact construction technique depends on:

* Model type.
* Attacker knowledge.
* Input modality.
* Attack objective.

---

### 54. Delivery

The adversarial example must eventually reach the model.

Possible delivery paths include:

* API request.
* Uploaded file.
* Email.
* Transaction.
* Camera.
* Sensor.
* User interface.

---

### 55. Model Response

The model processes the manipulated input and produces an output.

The attacker may then determine whether the desired effect occurred.

---

### 56. Feedback Loop

When feedback is available:

```text
Attack
  ↓
Prediction
  ↓
Feedback
  ↓
Attack Adjustment
  ↓
New Prediction
```

This can make iterative attacks more effective.

---

### 57. Security Monitoring

Organizations should monitor for suspicious patterns around ML endpoints.

Potential signals include:

* High query volumes.
* Repeated similar inputs.
* Systematic input variation.
* Unusual confidence patterns.
* Abnormal prediction distributions.

---

### 58. Rate Limiting

Rate limiting can restrict repeated probing.

Possible mechanisms include:

* Per-user limits.
* Per-application limits.
* Per-IP limits.
* Adaptive throttling.
* Usage quotas.

---

### 59. Output Minimization

Where business requirements permit, organizations can reduce unnecessary information returned by model APIs.

For example, an application may need only:

```text
ALLOW
```

rather than exposing:

```text
Class A: 0.02
Class B: 0.91
Class C: 0.07
```

Reducing output detail can limit information available to attackers.

---

### 60. Core Principle

Adversarial examples demonstrate that **an ML system can be manipulated through carefully crafted inputs even when the underlying model, software, and infrastructure remain operational**.

The enterprise security model should therefore consider:

```text
Input
  ↓
Perturbation
  ↓
Model Representation
  ↓
Prediction
  ↓
Decision
  ↓
Business / Security Impact
```

Adversarial-example security is ultimately about ensuring that the model's behavior remains sufficiently trustworthy when exposed to **intentional, realistic, and potentially malicious input manipulation**.

# 09.10 — Adversarial Examples

## Part 2

### 61. Adversarial Example Attack Surface

The attack surface for adversarial examples extends beyond the model itself.

A complete view includes:

```text
User / Attacker
      ↓
Input Interface
      ↓
Input Processing
      ↓
Feature / Representation
      ↓
ML Model
      ↓
Decision Logic
      ↓
Business Action
```

An attacker may target any stage that influences the final prediction.

---

### 62. Input Interface as a Security Boundary

The interface through which data enters the ML system should be treated as a security boundary.

Examples include:

* Web forms.
* Mobile applications.
* APIs.
* File uploads.
* Email gateways.
* Network sensors.
* Cameras.
* IoT devices.

The interface determines what an attacker can submit and how much control they have over the input.

---

### 63. Attacker-Controlled Inputs

Security teams should explicitly identify which portions of an input are attacker-controlled.

For example:

```text
Transaction
├── Amount           → User-controlled
├── Account ID       → System-controlled
├── Timestamp        → System-generated
├── Device ID        → Partially controlled
└── Risk Features   → Derived
```

The more influence an attacker has over security-sensitive features, the greater the potential exposure.

---

### 64. Partial Input Control

An attacker does not need complete control over an input.

Even controlling a subset of features may be sufficient to influence a prediction.

```text
Feature A → Trusted
Feature B → Trusted
Feature C → Attacker-controlled
Feature D → Trusted
```

Threat modeling should therefore examine feature-level control.

---

### 65. Feature Dependency

A derived feature may appear trusted while ultimately depending on attacker-controlled information.

```text
User Input
    ↓
Application Logic
    ↓
Derived Feature
    ↓
ML Model
```

The security team should trace the full lineage rather than trusting the feature merely because it is generated internally.

---

### 66. Feature Lineage

Feature lineage documents how a model feature is produced.

It can identify:

* Source system.
* Transformation.
* Owner.
* Validation.
* Update frequency.
* Trust level.

This is useful for determining whether an adversary can influence the feature.

---

### 67. Preprocessing Attacks

Preprocessing can introduce opportunities for manipulation.

Potential targets include:

* Parsing.
* Tokenization.
* Normalization.
* Encoding.
* Feature extraction.
* Image resizing.
* Audio processing.

```text
Raw Input
   ↓
Preprocessor
   ↓
Feature Representation
   ↓
Model
```

---

### 68. Parser Differences

Different components may interpret the same input differently.

This can create inconsistencies between:

* Security validation.
* Application processing.
* ML preprocessing.

Such inconsistencies can become security weaknesses.

---

### 69. Canonicalization

Canonicalization attempts to transform equivalent representations into a consistent form.

For example:

```text
Multiple Representations
        ↓
Canonical Form
        ↓
Validation
        ↓
Model
```

This can reduce ambiguity between validation and model processing.

---

### 70. Encoding Manipulation

Inputs may use different:

* Encodings.
* Character representations.
* Unicode forms.
* Serialization formats.

Security controls should consider whether attackers can exploit representation differences.

---

### 71. Tokenization

Text-based ML systems commonly transform text into tokens.

An attacker may exploit characteristics of tokenization to influence model behavior.

The security assessment should therefore include the tokenizer and associated preprocessing pipeline.

---

### 72. Image Preprocessing

Computer-vision systems frequently resize, crop, normalize, or otherwise transform images.

```text
Image
 ↓
Resize
 ↓
Normalize
 ↓
Feature Extraction
 ↓
Model
```

An adversarial input must therefore be assessed against the actual preprocessing pipeline.

---

### 73. Audio Preprocessing

Audio systems may perform:

* Sampling.
* Filtering.
* Noise reduction.
* Normalization.
* Feature extraction.

These transformations can influence whether an adversarial modification survives processing.

---

### 74. Transformation Robustness

An adversarial example that works against raw input may fail after preprocessing.

Conversely, preprocessing may unintentionally preserve or amplify a manipulation.

Security testing should therefore evaluate the complete processing chain.

---

### 75. Adversarial Examples and Model Architecture

Different model architectures can exhibit different robustness characteristics.

Relevant factors may include:

* Architecture.
* Training method.
* Input representation.
* Regularization.
* Data distribution.
* Optimization method.

Therefore, adversarial testing should be model-specific.

---

### 76. Model-Specific Attack Surface

Two models performing the same task may have different vulnerabilities.

```text
Same Business Function
        ↓
Model A → Attack Surface A
Model B → Attack Surface B
```

Replacing a model should therefore trigger a new security assessment.

---

### 77. Model Updates

A new model version may introduce new adversarial weaknesses.

```text
Model v1
 ↓
Security Testing
 ↓
Production

Model v2
 ↓
New Security Testing
 ↓
Production
```

Previous test results should not automatically be inherited.

---

### 78. Regression of Robustness

A model update may improve accuracy while reducing adversarial robustness.

For example:

```text
Accuracy ↑
Robustness ↓
```

Security and performance must therefore be evaluated together.

---

### 79. Security-Performance Tradeoff

Some robustness techniques can affect:

* Accuracy.
* Latency.
* Compute requirements.
* Memory.
* User experience.

These tradeoffs should be explicitly assessed for production systems.

---

### 80. Robustness Budget

For high-value systems, organizations can define acceptable levels of:

* Accuracy degradation.
* False positives.
* False negatives.
* Attack success.
* Latency.

This provides measurable security requirements.

---

### 81. Attack Success Rate

A common concept in adversarial testing is the **attack success rate**.

Conceptually:

```text
Successful Adversarial Attacks
───────────────────────────────
Total Adversarial Attempts
```

The metric can help compare defenses under a defined threat model.

---

### 82. Robust Accuracy

Another useful concept is performance on adversarially perturbed inputs.

```text
Robust Accuracy =
Correct Predictions Under Defined Attack Conditions
```

This should be interpreted within the exact threat model used for testing.

---

### 83. Clean Accuracy

**Clean accuracy** measures performance on normal, non-adversarial inputs.

A model may have:

```text
High Clean Accuracy
+
Low Robust Accuracy
```

This combination indicates that normal performance does not necessarily imply adversarial resilience.

---

### 84. Robustness Evaluation

A meaningful evaluation may therefore compare:

| Metric              | Normal Inputs | Adversarial Inputs |
| ------------------- | ------------: | -----------------: |
| Accuracy            |             ✓ |                  ✓ |
| Precision           |             ✓ |                  ✓ |
| Recall              |             ✓ |                  ✓ |
| False Positive Rate |             ✓ |                  ✓ |
| False Negative Rate |             ✓ |                  ✓ |

The exact metrics should reflect the model's business function.

---

### 85. False Positives

An adversarial input may cause legitimate activity to be classified as malicious.

This can produce:

* Account blocks.
* Transaction declines.
* Service interruptions.
* Investigation workload.

---

### 86. False Negatives

A more serious security consequence may occur when malicious activity is classified as legitimate.

```text
Malicious Activity
      ↓
Adversarial Manipulation
      ↓
False Negative
      ↓
Security Control Bypass
```

The business impact depends on the use case.

---

### 87. Asymmetric Risk

False positives and false negatives may not have equal consequences.

For example:

```text
False Positive → Customer inconvenience

False Negative → Fraudulent transaction
```

Risk evaluation should therefore consider consequence rather than simply counting errors.

---

### 88. Cost-Sensitive Security

Where appropriate, model evaluation can assign different costs to different errors.

This helps align technical model behavior with business risk.

---

### 89. Security Thresholds

Thresholds should be selected according to the required risk tolerance.

```text
Model Score
     ↓
Decision Threshold
     ↓
Business Outcome
```

Changing the threshold can significantly change false-positive and false-negative rates.

---

### 90. Threshold Security

Thresholds themselves should be protected.

Unauthorized threshold modification could effectively change the security posture without modifying the underlying model.

---

### 91. Monitoring Prediction Changes

Unexpected changes in prediction behavior can provide an early warning.

For example:

```text
Normal Prediction Pattern
          ↓
Sudden Shift
          ↓
Investigation
```

Possible explanations include:

* Adversarial activity.
* Data drift.
* Business changes.
* Pipeline errors.
* Model degradation.

---

### 92. Monitoring Input Changes

Input characteristics should also be monitored.

Potential signals include:

* Unusual feature combinations.
* Repeated similar inputs.
* Sudden distribution shifts.
* Abnormal request patterns.

---

### 93. Monitoring Model Confidence

Where confidence information is available internally, monitoring changes in confidence distributions may help identify unusual conditions.

However, confidence should not automatically be interpreted as a reliable probability of correctness.

---

### 94. Prediction Entropy

For some classification systems, changes in prediction uncertainty can provide an additional monitoring signal.

For example:

```text
Normal:
Stable prediction distribution

Anomalous:
Unusual concentration or uncertainty
```

This is a supporting signal rather than definitive evidence of an attack.

---

### 95. Input Anomaly Detection

Anomaly-detection mechanisms can be placed before the model.

```text
Input
 ↓
Anomaly Detection
 ↓
Model
```

Potentially suspicious inputs can receive additional scrutiny.

---

### 96. Limitations of Anomaly Detection

Anomaly detection is not a universal solution.

An adversarial input may resemble legitimate traffic closely enough to avoid detection.

Additionally, aggressive anomaly detection can generate excessive false positives.

---

### 97. Layered Input Defense

A stronger approach combines multiple controls.

```text
Input Validation
       ↓
Schema Validation
       ↓
Anomaly Detection
       ↓
Rate Limiting
       ↓
ML Model
       ↓
Decision Controls
```

---

### 98. Randomization

Some defensive approaches introduce controlled randomness into model processing.

The objective may be to make precise attack construction more difficult.

However, randomization should be evaluated carefully because attackers may adapt.

---

### 99. Input Transformation

Defensive transformations can modify inputs before inference.

Examples can include:

* Normalization.
* Resizing.
* Filtering.
* Compression.

Such techniques may reduce some attacks but should not be considered universally effective.

---

### 100. Core Principle

The security of an adversarial-example defense depends on the **entire inference pipeline**, not merely on the model.

```text
Attacker
   ↓
Input
   ↓
Validation
   ↓
Preprocessing
   ↓
Feature Generation
   ↓
Model
   ↓
Decision Logic
   ↓
Business Action
```

A mature security program must therefore identify which portions of the input are attacker-controlled, protect the transformations that process those inputs, test model robustness under realistic threat assumptions, and monitor both input and prediction behavior throughout the model's operational lifecycle.
