# 09.10 — Adversarial Examples

## Part 1

### 1. Adversarial Examples

An **adversarial example** is an input intentionally modified to cause a machine-learning model to produce an incorrect or undesirable output.

The defining characteristic is that the modification is designed specifically to exploit weaknesses in the model's learned decision behavior.

```text
Legitimate Input
       ↓
Adversarial Modification
       ↓
Adversarial Example
       ↓
ML Model
       ↓
Incorrect / Undesired Output
```

---

### 2. Why Adversarial Examples Matter

Traditional applications generally process inputs according to explicitly programmed rules.

Machine-learning models instead learn statistical relationships from data.

This creates a different security problem:

```text
Traditional Software
Input → Explicit Logic → Output

Machine Learning
Input → Learned Representation → Prediction
```

An attacker may exploit weaknesses in those learned representations without exploiting a conventional software vulnerability.

---

### 3. The Fundamental Security Problem

The central problem can be expressed as:

> **A small or carefully designed change to an input can produce a disproportionately large change in the model's prediction.**

Conceptually:

```text
Input A
   ↓
Model
   ↓
Correct Prediction

Input A + Adversarial Modification
   ↓
Model
   ↓
Incorrect Prediction
```

The model itself may remain completely operational.

---

### 4. Adversarial Example vs. Ordinary Error

Not every incorrect prediction is an adversarial example.

An ordinary model error may occur because:

* The input is ambiguous.
* The model lacks sufficient training data.
* The environment changed.
* The model is inherently imperfect.

An adversarial example involves **intentional manipulation designed to influence the model**.

---

### 5. Adversarial Example vs. Data Poisoning

These attacks occur at different stages.

| Attack              | Primary Stage                |
| ------------------- | ---------------------------- |
| Adversarial example | Inference                    |
| Data poisoning      | Training                     |
| Backdoor            | Usually training/development |
| Model tampering     | Deployment/runtime           |
| Model extraction    | Inference/API                |

An adversarial example primarily targets a model that is already being used for prediction.

---

### 6. Inference-Time Attack

Adversarial examples are generally associated with inference-time manipulation.

```text
Training
   ↓
Model
   ↓
Deployment
   ↓
Attacker Manipulates Input
   ↓
Prediction
```

The attacker does not necessarily need to modify the model itself.

---

### 7. Input Space

Every ML model operates on some representation of input data.

Examples include:

* Images.
* Text.
* Audio.
* Video.
* Network traffic.
* Financial transactions.
* Sensor measurements.
* User behavior.

The collection of possible inputs is commonly referred to as the **input space**.

---

### 8. Perturbation

The modification applied to an input is commonly called a **perturbation**.

Conceptually:

```text
Adversarial Input = Original Input + Perturbation
```

The perturbation may be designed to alter the model's prediction while keeping the input sufficiently usable or realistic.

---

### 9. Digital Perturbation

A digital perturbation directly modifies the machine-readable representation.

Examples include changes to:

* Image pixels.
* Text tokens.
* Audio samples.
* Numerical features.
* File characteristics.

The modification may not be obvious to a human observer.

---

### 10. Physical Perturbation

A physical adversarial example attempts to survive the transition from the physical world into the ML system.

For example:

```text
Physical Object
      ↓
Camera / Sensor
      ↓
Digital Representation
      ↓
ML Model
      ↓
Prediction
```

The attacker must account for real-world conditions.

---

### 11. Image-Based Adversarial Examples

Computer-vision systems are a widely studied environment for adversarial examples.

A model may correctly identify an image under normal conditions but produce a different prediction after carefully designed modifications.

```text
Original Image
     ↓
"Class A"

Modified Image
     ↓
"Class B"
```

---

### 12. Human Perception vs. Model Perception

A major security challenge is that a modification can be relatively difficult for humans to notice while still influencing the model.

```text
Human Observer
      ↓
"Appears Normal"

ML Model
      ↓
"Different Classification"
```

This demonstrates that human perception and machine representation are not equivalent.

---

### 13. Text-Based Adversarial Examples

Text classifiers can also be targeted.

Potentially affected systems include:

* Spam detection.
* Phishing detection.
* Sentiment classification.
* Content classification.
* Fraud detection.
* Security analytics.

Attackers may manipulate textual characteristics to influence classification.

---

### 14. Text Perturbations

Possible forms of textual modification include changes to:

* Words.
* Characters.
* Formatting.
* Tokenization.
* Sentence structure.
* Context.

The effectiveness depends heavily on the model and tokenizer.

---

### 15. Audio-Based Adversarial Examples

Audio ML systems can also be exposed to adversarial inputs.

Examples include:

* Speech recognition.
* Speaker identification.
* Voice authentication.
* Audio classification.

```text
Audio
  ↓
Adversarial Modification
  ↓
Speech / Audio Model
  ↓
Unexpected Result
```

---

### 16. Video-Based Adversarial Examples

Video models process sequences of visual information.

Potential targets include:

* Surveillance.
* Object detection.
* Activity recognition.
* Autonomous systems.

The attacker may attempt to influence the model's interpretation of the video stream.

---

### 17. Sensor-Based Systems

ML systems may consume data from:

* Cameras.
* GPS.
* Accelerometers.
* Temperature sensors.
* Industrial sensors.
* IoT devices.

Manipulation of sensor inputs can potentially become an adversarial ML problem.

---

### 18. Network Security Models

ML-based network security systems may classify:

* Network flows.
* Packets.
* Connection behavior.
* User activity.
* Traffic patterns.

Attackers may attempt to modify observable characteristics while retaining malicious objectives.

---

### 19. Fraud Detection

Fraud detection models can be targeted by manipulating transaction characteristics.

```text
Fraudulent Activity
        ↓
Feature Manipulation
        ↓
ML Fraud Model
        ↓
Lower-Risk Prediction
```

The security concern is that the adversarial example may result in an incorrect business decision.

---

### 20. Malware Detection

ML-based malware detection can also be exposed to adversarial manipulation.

The attacker may attempt to alter observable properties of malicious software while preserving its intended malicious behavior.

---

### 21. Spam and Phishing Detection

Attackers may manipulate messages so that their content appears more consistent with legitimate communications.

The objective is to reduce the likelihood of detection.

---

### 22. Intrusion Detection

Network intrusion detection models can be targeted by attempts to make malicious traffic resemble legitimate traffic.

The attacker is effectively attempting to move the input representation into a region that the model associates with benign behavior.

---

### 23. Identity and Authentication

Adversarial examples can be relevant to ML-based:

* Facial recognition.
* Voice recognition.
* Behavioral authentication.

Because these systems can influence access decisions, their adversarial robustness can have direct security implications.

---

### 24. Autonomous Systems

Autonomous systems may use ML for:

* Object detection.
* Navigation.
* Classification.
* Decision support.

An adversarial input can therefore potentially influence a physical action.

```text
Adversarial Input
       ↓
Perception Model
       ↓
Incorrect Interpretation
       ↓
Decision
       ↓
Physical Action
```

---

### 25. Safety Implications

When ML controls or influences physical systems, adversarial examples should be considered alongside safety engineering.

Potential consequences can include:

* Unsafe operation.
* Incorrect routing.
* Incorrect object identification.
* Failure to recognize hazards.

---

### 26. Targeted Adversarial Examples

A **targeted** adversarial example attempts to force a model toward a particular incorrect output.

```text
Original
   ↓
Class A

Adversarial Input
   ↓
Specifically Desired Class B
```

The attacker cares about the exact incorrect outcome.

---

### 27. Untargeted Adversarial Examples

An **untargeted** adversarial example attempts to cause any incorrect prediction.

```text
Original
   ↓
Class A

Adversarial Input
   ↓
Class B / C / D / ...
```

The attacker does not necessarily care which incorrect class is selected.

---

### 28. Targeted vs. Untargeted Security Risk

Targeted attacks can be particularly important when a specific outcome is required.

For example, an attacker may need a system to classify malicious activity as a specific trusted category rather than merely causing an arbitrary error.

---

### 29. Confidence Manipulation

Some attacks attempt to influence not only the predicted class but also the model's confidence.

For example:

```text
Original:
Malicious → 95% confidence

Manipulated:
Benign → 90% confidence
```

High-confidence incorrect predictions can be particularly dangerous when applications automatically trust model outputs.

---

### 30. Decision Thresholds

Many ML applications convert model scores into decisions.

```text
Model Score
     ↓
Threshold
     ↓
ALLOW / BLOCK
```

An adversarial example may attempt to push the score across the relevant decision boundary.

---

### 31. Decision Boundary

A decision boundary represents a region where the model changes its classification.

Conceptually:

```text
          Class A
        /         \
       /           \
------ Decision Boundary ------
       \           /
        \         /
          Class B
```

An adversarial perturbation may move an input across that boundary.

---

### 32. Why Small Changes Can Matter

ML models operate in high-dimensional mathematical spaces.

A change that appears insignificant to a human may correspond to a meaningful change in the model's internal representation.

```text
Human Perspective
Small Difference
      ↓
"Essentially Same"

Model Representation
      ↓
Different Region
      ↓
Different Prediction
```

---

### 33. High-Dimensional Input

Images, text, audio, and other complex inputs can contain very large numbers of dimensions.

This creates a large mathematical input space in which decision boundaries can be complex.

---

### 34. Feature Space

Models often transform raw inputs into internal representations or features.

```text
Raw Input
   ↓
Feature Representation
   ↓
Decision Function
   ↓
Prediction
```

Adversarial manipulation can affect the representation used by the model.

---

### 35. Representation Vulnerability

If the model learns features that can be manipulated without destroying the legitimate appearance or functionality of the input, an attacker may exploit those features.

This is one reason adversarial robustness is a model-security concern rather than simply an application-validation issue.

---

### 36. Gradient Information

In some ML architectures, gradients describe how the model's output changes with respect to its inputs.

When an attacker has access to sufficient model information, gradients can potentially assist in constructing adversarial inputs.

---

### 37. White-Box Adversarial Attacks

In a white-box scenario, the attacker has substantial knowledge of the model.

Potentially available information includes:

* Architecture.
* Parameters.
* Weights.
* Gradients.
* Preprocessing.

This allows more direct analysis of the model's behavior.

---

### 38. Black-Box Adversarial Attacks

In a black-box scenario, the attacker may only have access to the model through an interface.

```text
Attacker
   ↓
Input
   ↓
API
   ↓
Model
   ↓
Output
```

The attacker can use observable behavior to develop candidate inputs.

---

### 39. Gray-Box Attacks

A gray-box attacker has partial knowledge.

This may include information about:

* Model type.
* Input structure.
* Output classes.
* General architecture.

This falls between full white-box and limited black-box knowledge.

---

### 40. Query-Based Attacks

An attacker may submit multiple inputs and analyze the resulting predictions.

```text
Query 1 → Output
Query 2 → Output
Query 3 → Output
   ↓
Behavioral Analysis
   ↓
Candidate Adversarial Input
```

This is why unrestricted model querying can increase exposure.

---

### 41. Transferability

An important property of adversarial examples is **transferability**.

An adversarial input developed against one model may sometimes affect another model performing a similar task.

```text
Source Model
     ↓
Adversarial Example
     ↓
Target Model
     ↓
Potential Misclassification
```

---

### 42. Security Significance of Transferability

Transferability means an attacker may not need complete knowledge of the target model.

They may develop attacks against a substitute or surrogate model and test whether they work against the target.

---

### 43. Surrogate Models

A surrogate model approximates the behavior of a target model.

The attacker can use the surrogate to study potential weaknesses.

```text
Target Behavior
      ↓
Observed Outputs
      ↓
Surrogate Model
      ↓
Adversarial Testing
```

---

### 44. Physical Transferability

Transferability can also have physical implications.

An attack developed in one environment may behave differently when exposed to:

* Lighting.
* Camera changes.
* Distance.
* Angle.
* Environmental noise.

Therefore, laboratory success does not necessarily mean real-world success.

---

### 45. Robustness

Model robustness refers broadly to the model's ability to maintain acceptable behavior under perturbations and unexpected conditions.

For adversarial examples, robustness means reducing the likelihood that maliciously crafted inputs cause unacceptable model behavior.

---

### 46. Robustness Is Not Absolute

A model should not be described simply as:

> “Adversarial-proof.”

Security should instead specify:

* Which attacks were tested.
* Under what assumptions.
* Against which perturbations.
* With what success criteria.

---

### 47. Threat Model Dependency

Adversarial robustness depends on the threat model.

For example:

```text
Threat Model
     ↓
Attacker Capabilities
     ↓
Allowed Perturbations
     ↓
Security Test
     ↓
Robustness Result
```

Changing attacker capabilities can change the assessment.

---

### 48. Perturbation Constraints

Security testing may define constraints around how much an input can change.

For example:

* Maximum numerical change.
* Maximum visual difference.
* Maximum text modification.
* Maximum sensor deviation.

The constraint should reflect realistic attack conditions.

---

### 49. Imperceptibility

Some adversarial examples are designed to remain difficult for humans to notice.

However, imperceptibility is not always the relevant security requirement.

For many enterprise attacks, the more important question is whether the manipulation is **operationally feasible**.

---

### 50. Operational Feasibility

A useful security assessment asks:

> Can an attacker realistically create and deliver the adversarial input in the target environment?

This includes considering:

* Access.
* Time.
* Equipment.
* Query limitations.
* Physical constraints.
* Detection mechanisms.

---

### 51. Adversarial Example Lifecycle

A simplified lifecycle is:

```text
Reconnaissance
      ↓
Model Understanding
      ↓
Attack Construction
      ↓
Input Delivery
      ↓
Model Prediction
      ↓
Observe Impact
      ↓
Adapt / Repeat
```

The attacker may iterate depending on the available feedback.

---

### 52. Reconnaissance

The attacker may first determine:

* What the model detects.
* What inputs it accepts.
* What outputs it returns.
* How decisions are made.
* Whether the system exposes confidence information.

---

### 53. Attack Construction

The attacker develops an input that attempts to achieve the desired model behavior.

The exact construction technique depends on:

* Model type.
* Attacker knowledge.
* Input modality.
* Attack objective.

---

### 54. Delivery

The adversarial example must eventually reach the model.

Possible delivery paths include:

* API request.
* Uploaded file.
* Email.
* Transaction.
* Camera.
* Sensor.
* User interface.

---

### 55. Model Response

The model processes the manipulated input and produces an output.

The attacker may then determine whether the desired effect occurred.

---

### 56. Feedback Loop

When feedback is available:

```text
Attack
  ↓
Prediction
  ↓
Feedback
  ↓
Attack Adjustment
  ↓
New Prediction
```

This can make iterative attacks more effective.

---

### 57. Security Monitoring

Organizations should monitor for suspicious patterns around ML endpoints.

Potential signals include:

* High query volumes.
* Repeated similar inputs.
* Systematic input variation.
* Unusual confidence patterns.
* Abnormal prediction distributions.

---

### 58. Rate Limiting

Rate limiting can restrict repeated probing.

Possible mechanisms include:

* Per-user limits.
* Per-application limits.
* Per-IP limits.
* Adaptive throttling.
* Usage quotas.

---

### 59. Output Minimization

Where business requirements permit, organizations can reduce unnecessary information returned by model APIs.

For example, an application may need only:

```text
ALLOW
```

rather than exposing:

```text
Class A: 0.02
Class B: 0.91
Class C: 0.07
```

Reducing output detail can limit information available to attackers.

---

### 60. Core Principle

Adversarial examples demonstrate that **an ML system can be manipulated through carefully crafted inputs even when the underlying model, software, and infrastructure remain operational**.

The enterprise security model should therefore consider:

```text
Input
  ↓
Perturbation
  ↓
Model Representation
  ↓
Prediction
  ↓
Decision
  ↓
Business / Security Impact
```

Adversarial-example security is ultimately about ensuring that the model's behavior remains sufficiently trustworthy when exposed to **intentional, realistic, and potentially malicious input manipulation**.

# 09.10 — Adversarial Examples

## Part 2

### 61. Adversarial Example Attack Surface

The attack surface for adversarial examples extends beyond the model itself.

A complete view includes:

```text
User / Attacker
      ↓
Input Interface
      ↓
Input Processing
      ↓
Feature / Representation
      ↓
ML Model
      ↓
Decision Logic
      ↓
Business Action
```

An attacker may target any stage that influences the final prediction.

---

### 62. Input Interface as a Security Boundary

The interface through which data enters the ML system should be treated as a security boundary.

Examples include:

* Web forms.
* Mobile applications.
* APIs.
* File uploads.
* Email gateways.
* Network sensors.
* Cameras.
* IoT devices.

The interface determines what an attacker can submit and how much control they have over the input.

---

### 63. Attacker-Controlled Inputs

Security teams should explicitly identify which portions of an input are attacker-controlled.

For example:

```text
Transaction
├── Amount           → User-controlled
├── Account ID       → System-controlled
├── Timestamp        → System-generated
├── Device ID        → Partially controlled
└── Risk Features   → Derived
```

The more influence an attacker has over security-sensitive features, the greater the potential exposure.

---

### 64. Partial Input Control

An attacker does not need complete control over an input.

Even controlling a subset of features may be sufficient to influence a prediction.

```text
Feature A → Trusted
Feature B → Trusted
Feature C → Attacker-controlled
Feature D → Trusted
```

Threat modeling should therefore examine feature-level control.

---

### 65. Feature Dependency

A derived feature may appear trusted while ultimately depending on attacker-controlled information.

```text
User Input
    ↓
Application Logic
    ↓
Derived Feature
    ↓
ML Model
```

The security team should trace the full lineage rather than trusting the feature merely because it is generated internally.

---

### 66. Feature Lineage

Feature lineage documents how a model feature is produced.

It can identify:

* Source system.
* Transformation.
* Owner.
* Validation.
* Update frequency.
* Trust level.

This is useful for determining whether an adversary can influence the feature.

---

### 67. Preprocessing Attacks

Preprocessing can introduce opportunities for manipulation.

Potential targets include:

* Parsing.
* Tokenization.
* Normalization.
* Encoding.
* Feature extraction.
* Image resizing.
* Audio processing.

```text
Raw Input
   ↓
Preprocessor
   ↓
Feature Representation
   ↓
Model
```

---

### 68. Parser Differences

Different components may interpret the same input differently.

This can create inconsistencies between:

* Security validation.
* Application processing.
* ML preprocessing.

Such inconsistencies can become security weaknesses.

---

### 69. Canonicalization

Canonicalization attempts to transform equivalent representations into a consistent form.

For example:

```text
Multiple Representations
        ↓
Canonical Form
        ↓
Validation
        ↓
Model
```

This can reduce ambiguity between validation and model processing.

---

### 70. Encoding Manipulation

Inputs may use different:

* Encodings.
* Character representations.
* Unicode forms.
* Serialization formats.

Security controls should consider whether attackers can exploit representation differences.

---

### 71. Tokenization

Text-based ML systems commonly transform text into tokens.

An attacker may exploit characteristics of tokenization to influence model behavior.

The security assessment should therefore include the tokenizer and associated preprocessing pipeline.

---

### 72. Image Preprocessing

Computer-vision systems frequently resize, crop, normalize, or otherwise transform images.

```text
Image
 ↓
Resize
 ↓
Normalize
 ↓
Feature Extraction
 ↓
Model
```

An adversarial input must therefore be assessed against the actual preprocessing pipeline.

---

### 73. Audio Preprocessing

Audio systems may perform:

* Sampling.
* Filtering.
* Noise reduction.
* Normalization.
* Feature extraction.

These transformations can influence whether an adversarial modification survives processing.

---

### 74. Transformation Robustness

An adversarial example that works against raw input may fail after preprocessing.

Conversely, preprocessing may unintentionally preserve or amplify a manipulation.

Security testing should therefore evaluate the complete processing chain.

---

### 75. Adversarial Examples and Model Architecture

Different model architectures can exhibit different robustness characteristics.

Relevant factors may include:

* Architecture.
* Training method.
* Input representation.
* Regularization.
* Data distribution.
* Optimization method.

Therefore, adversarial testing should be model-specific.

---

### 76. Model-Specific Attack Surface

Two models performing the same task may have different vulnerabilities.

```text
Same Business Function
        ↓
Model A → Attack Surface A
Model B → Attack Surface B
```

Replacing a model should therefore trigger a new security assessment.

---

### 77. Model Updates

A new model version may introduce new adversarial weaknesses.

```text
Model v1
 ↓
Security Testing
 ↓
Production

Model v2
 ↓
New Security Testing
 ↓
Production
```

Previous test results should not automatically be inherited.

---

### 78. Regression of Robustness

A model update may improve accuracy while reducing adversarial robustness.

For example:

```text
Accuracy ↑
Robustness ↓
```

Security and performance must therefore be evaluated together.

---

### 79. Security-Performance Tradeoff

Some robustness techniques can affect:

* Accuracy.
* Latency.
* Compute requirements.
* Memory.
* User experience.

These tradeoffs should be explicitly assessed for production systems.

---

### 80. Robustness Budget

For high-value systems, organizations can define acceptable levels of:

* Accuracy degradation.
* False positives.
* False negatives.
* Attack success.
* Latency.

This provides measurable security requirements.

---

### 81. Attack Success Rate

A common concept in adversarial testing is the **attack success rate**.

Conceptually:

```text
Successful Adversarial Attacks
───────────────────────────────
Total Adversarial Attempts
```

The metric can help compare defenses under a defined threat model.

---

### 82. Robust Accuracy

Another useful concept is performance on adversarially perturbed inputs.

```text
Robust Accuracy =
Correct Predictions Under Defined Attack Conditions
```

This should be interpreted within the exact threat model used for testing.

---

### 83. Clean Accuracy

**Clean accuracy** measures performance on normal, non-adversarial inputs.

A model may have:

```text
High Clean Accuracy
+
Low Robust Accuracy
```

This combination indicates that normal performance does not necessarily imply adversarial resilience.

---

### 84. Robustness Evaluation

A meaningful evaluation may therefore compare:

| Metric              | Normal Inputs | Adversarial Inputs |
| ------------------- | ------------: | -----------------: |
| Accuracy            |             ✓ |                  ✓ |
| Precision           |             ✓ |                  ✓ |
| Recall              |             ✓ |                  ✓ |
| False Positive Rate |             ✓ |                  ✓ |
| False Negative Rate |             ✓ |                  ✓ |

The exact metrics should reflect the model's business function.

---

### 85. False Positives

An adversarial input may cause legitimate activity to be classified as malicious.

This can produce:

* Account blocks.
* Transaction declines.
* Service interruptions.
* Investigation workload.

---

### 86. False Negatives

A more serious security consequence may occur when malicious activity is classified as legitimate.

```text
Malicious Activity
      ↓
Adversarial Manipulation
      ↓
False Negative
      ↓
Security Control Bypass
```

The business impact depends on the use case.

---

### 87. Asymmetric Risk

False positives and false negatives may not have equal consequences.

For example:

```text
False Positive → Customer inconvenience

False Negative → Fraudulent transaction
```

Risk evaluation should therefore consider consequence rather than simply counting errors.

---

### 88. Cost-Sensitive Security

Where appropriate, model evaluation can assign different costs to different errors.

This helps align technical model behavior with business risk.

---

### 89. Security Thresholds

Thresholds should be selected according to the required risk tolerance.

```text
Model Score
     ↓
Decision Threshold
     ↓
Business Outcome
```

Changing the threshold can significantly change false-positive and false-negative rates.

---

### 90. Threshold Security

Thresholds themselves should be protected.

Unauthorized threshold modification could effectively change the security posture without modifying the underlying model.

---

### 91. Monitoring Prediction Changes

Unexpected changes in prediction behavior can provide an early warning.

For example:

```text
Normal Prediction Pattern
          ↓
Sudden Shift
          ↓
Investigation
```

Possible explanations include:

* Adversarial activity.
* Data drift.
* Business changes.
* Pipeline errors.
* Model degradation.

---

### 92. Monitoring Input Changes

Input characteristics should also be monitored.

Potential signals include:

* Unusual feature combinations.
* Repeated similar inputs.
* Sudden distribution shifts.
* Abnormal request patterns.

---

### 93. Monitoring Model Confidence

Where confidence information is available internally, monitoring changes in confidence distributions may help identify unusual conditions.

However, confidence should not automatically be interpreted as a reliable probability of correctness.

---

### 94. Prediction Entropy

For some classification systems, changes in prediction uncertainty can provide an additional monitoring signal.

For example:

```text
Normal:
Stable prediction distribution

Anomalous:
Unusual concentration or uncertainty
```

This is a supporting signal rather than definitive evidence of an attack.

---

### 95. Input Anomaly Detection

Anomaly-detection mechanisms can be placed before the model.

```text
Input
 ↓
Anomaly Detection
 ↓
Model
```

Potentially suspicious inputs can receive additional scrutiny.

---

### 96. Limitations of Anomaly Detection

Anomaly detection is not a universal solution.

An adversarial input may resemble legitimate traffic closely enough to avoid detection.

Additionally, aggressive anomaly detection can generate excessive false positives.

---

### 97. Layered Input Defense

A stronger approach combines multiple controls.

```text
Input Validation
       ↓
Schema Validation
       ↓
Anomaly Detection
       ↓
Rate Limiting
       ↓
ML Model
       ↓
Decision Controls
```

---

### 98. Randomization

Some defensive approaches introduce controlled randomness into model processing.

The objective may be to make precise attack construction more difficult.

However, randomization should be evaluated carefully because attackers may adapt.

---

### 99. Input Transformation

Defensive transformations can modify inputs before inference.

Examples can include:

* Normalization.
* Resizing.
* Filtering.
* Compression.

Such techniques may reduce some attacks but should not be considered universally effective.

---

### 100. Core Principle

The security of an adversarial-example defense depends on the **entire inference pipeline**, not merely on the model.

```text
Attacker
   ↓
Input
   ↓
Validation
   ↓
Preprocessing
   ↓
Feature Generation
   ↓
Model
   ↓
Decision Logic
   ↓
Business Action
```

A mature security program must therefore identify which portions of the input are attacker-controlled, protect the transformations that process those inputs, test model robustness under realistic threat assumptions, and monitor both input and prediction behavior throughout the model's operational lifecycle.

# 09.10 — Adversarial Examples

## Part 3

### 101. White-Box Adversarial Example Attacks

In a **white-box** threat model, the attacker has substantial knowledge of the target model.

Potentially available information includes:

* Model architecture.
* Model parameters.
* Weights.
* Gradients.
* Preprocessing.
* Loss function.
* Decision thresholds.

This knowledge can make adversarial-example construction more precise.

---

### 102. Gradient-Based Attacks

Gradient-based approaches use information about how the model's output changes in response to changes in the input.

Conceptually:

```text id="aex102"
Input
  ↓
Model
  ↓
Gradient Information
  ↓
Input Modification
  ↓
Adversarial Example
```

The attacker attempts to identify an input direction that increases the likelihood of the desired incorrect prediction.

---

### 103. Fast Gradient Sign Method

**Fast Gradient Sign Method (FGSM)** is a well-known adversarial-example technique.

It uses the sign of the gradient of the loss with respect to the input to construct a perturbation.

Conceptually:

```text id="aex103"
Original Input
      +
Gradient-Based Perturbation
      ↓
Adversarial Input
```

FGSM is important conceptually because it demonstrates how model gradients can be used to construct adversarial inputs.

---

### 104. Iterative Gradient Attacks

Instead of applying a single perturbation, an attacker may repeatedly modify the input.

```text id="aex104"
Original Input
      ↓
Small Modification
      ↓
Evaluate
      ↓
Another Modification
      ↓
Evaluate
      ↓
Final Adversarial Input
```

Iterative approaches can be more effective but generally require additional computation.

---

### 105. Projected Gradient Descent

**Projected Gradient Descent (PGD)** is commonly used in adversarial robustness research.

The basic concept is iterative optimization while constraining the perturbation within a defined region.

```text id="aex105"
Input
 ↓
Gradient Step
 ↓
Constraint / Projection
 ↓
Gradient Step
 ↓
Constraint / Projection
 ↓
Adversarial Example
```

PGD is often used as a strong baseline for evaluating robustness.

---

### 106. Perturbation Constraint

The constraint determines how far the adversarial input can move from the original input under a selected mathematical measure.

This matters because unrestricted changes could simply produce a completely different legitimate input rather than a meaningful adversarial example.

---

### 107. Norm-Based Constraints

Adversarial research commonly uses mathematical norms to quantify perturbation magnitude.

Examples include:

* L0.
* L1.
* L2.
* L∞.

Each captures a different notion of how the input has been modified.

---

### 108. L0 Perspective

An L0-style constraint focuses on the number of input elements that have been changed.

Conceptually:

```text id="aex108"
Original:
A B C D E F G

Modified:
A B X D E F G

Changed Elements = 1
```

This can be useful when sparse changes are relevant.

---

### 109. L2 Perspective

An L2-style measure considers the overall Euclidean magnitude of the perturbation.

It is useful for quantifying the aggregate numerical difference between the original and modified input.

---

### 110. L∞ Perspective

An L∞-style constraint focuses on the largest individual change made to an input component.

This is useful when limiting the maximum change to any single feature is important.

---

### 111. Why the Norm Matters

Different norms represent different attack assumptions.

```text id="aex111"
Attack Model
     ↓
Perturbation Definition
     ↓
Norm / Constraint
     ↓
Robustness Result
```

A model robust under one constraint is not necessarily robust under another.

---

### 112. Optimization-Based Attacks

Some adversarial-example methods formulate the attack as an optimization problem.

The attacker attempts to find an input that:

1. Produces the desired model behavior.
2. Minimizes the required perturbation.

Conceptually:

```text id="aex112"
Desired Misclassification
          +
Minimum Effective Change
          ↓
Adversarial Example
```

---

### 113. Optimization Objective

An adversarial attack can be conceptualized as balancing:

```text id="aex113"
Attack Effectiveness
        ↕
Perturbation Size
        ↕
Attack Cost
```

The attacker seeks a practical balance between these factors.

---

### 114. Confidence-Based Attacks

If a model exposes confidence or probability information, the attacker can potentially use that information to determine whether a modification is moving toward the desired outcome.

```text id="aex114"
Input
 ↓
Prediction + Confidence
 ↓
Evaluate Direction
 ↓
Modify Input
```

---

### 115. Decision-Based Attacks

When only a final decision is exposed, the attacker can still attempt to determine whether modifications cross the decision boundary.

```text id="aex115"
Input
 ↓
ALLOW / BLOCK
 ↓
Modify
 ↓
ALLOW / BLOCK
```

This provides less information than detailed confidence scores.

---

### 116. Score-Based Attacks

A score-based interface provides more information than a decision-only interface but less internal information than a white-box model.

For example:

```text id="aex116"
Input
 ↓
Risk Score = 0.82
```

Repeated observations may reveal useful information about model behavior.

---

### 117. Query-Efficient Attacks

Black-box attacks can be expensive when each model query has a cost.

Attack methods can therefore attempt to minimize the number of queries required.

This creates an important security metric:

> **How much information can an attacker obtain per model query?**

---

### 118. Query Budget Controls

Organizations can reduce exposure through:

* Rate limiting.
* Request quotas.
* Authentication.
* Adaptive throttling.
* Monitoring.
* Account-level restrictions.

These controls can increase the cost of systematic probing.

---

### 119. Transfer-Based Attacks

An attacker may construct adversarial examples against a substitute model and then attempt to use them against the target.

```text id="aex119"
Target Model
     ↑
Transfer
     ↑
Adversarial Example
     ↑
Surrogate Model
```

This is possible because some adversarial examples can transfer between models.

---

### 120. Model Similarity

Transferability can be influenced by similarities between:

* Training data.
* Architecture.
* Task.
* Learned representations.
* Decision boundaries.

Higher similarity can sometimes increase transfer potential.

---

### 121. Ensemble Models

Organizations sometimes use multiple models rather than a single model.

```text id="aex121"
              ┌→ Model A ─┐
Input ────────┼→ Model B ─┼→ Decision
              └→ Model C ─┘
```

The security benefit depends on how the ensemble is designed.

---

### 122. Ensemble Limitations

Using multiple models does not automatically eliminate adversarial risk.

If models share:

* Training data.
* Architecture.
* Features.
* Vulnerabilities.

an adversarial input may still affect multiple components.

---

### 123. Input Diversity

Different representations or independent models can potentially make attacks more difficult.

However, independence must be genuine rather than merely cosmetic.

---

### 124. Adversarial Training

Adversarial training incorporates adversarial examples into the training process.

Conceptually:

```text id="aex124"
Normal Training Data
        +
Adversarial Examples
        ↓
Training
        ↓
Robustness-Oriented Model
```

The objective is to teach the model to maintain acceptable behavior under defined attack conditions.

---

### 125. Adversarial Training Limitations

Adversarial training is not a universal solution.

Limitations can include:

* Increased computational cost.
* Reduced clean accuracy in some circumstances.
* Robustness limited to evaluated threat models.
* New attacks emerging after training.

---

### 126. Robust Optimization

Robust optimization attempts to optimize model performance while accounting for defined perturbations or uncertainties.

It can be viewed as:

```text id="aex126"
Expected Performance
        +
Perturbation Consideration
        ↓
Robustness Objective
```

---

### 127. Certified Robustness

Some techniques attempt to provide mathematical guarantees about model behavior within defined perturbation bounds.

Conceptually:

```text id="aex127"
Defined Input Region
        ↓
Mathematical Guarantee
        ↓
Prediction Stability
```

Such guarantees are typically limited to specified assumptions and perturbation regions.

---

### 128. Empirical vs. Certified Robustness

Two broad evaluation approaches are:

| Approach  | Meaning                                                    |
| --------- | ---------------------------------------------------------- |
| Empirical | Test against selected attacks                              |
| Certified | Establish mathematical guarantees under defined conditions |

Neither should be interpreted outside its stated assumptions.

---

### 129. Robustness Benchmarking

Organizations can establish standardized adversarial testing.

A benchmark may define:

* Attack categories.
* Perturbation limits.
* Test datasets.
* Success criteria.
* Reporting requirements.

---

### 130. Security Test Dataset

A dedicated adversarial test dataset can complement ordinary validation datasets.

```text id="aex130"
Training Dataset
        ↓
Model Training

Clean Test Dataset
        ↓
Normal Performance

Adversarial Test Dataset
        ↓
Robustness Assessment
```

---

### 131. Test Dataset Isolation

Adversarial test datasets should be controlled so that testing material does not unintentionally contaminate training data.

This is especially important in organizations that continuously retrain models.

---

### 132. Red Team Testing

ML red teams can simulate adversarial behavior against models and their surrounding systems.

They may evaluate:

* Model endpoints.
* Input processing.
* Model behavior.
* API controls.
* Monitoring.
* Detection.
* Response.

---

### 133. Purple Teaming

A purple-team approach combines offensive testing with defensive improvement.

```text id="aex133"
Red Team
   ↓
Attack Simulation
   ↓
Blue Team
   ↓
Detection / Defense
   ↓
Control Improvement
```

---

### 134. Adversarial ML Penetration Testing

An AML security assessment can combine conventional penetration testing with model-specific testing.

This recognizes that an ML system contains both:

* Traditional software attack surfaces.
* ML-specific attack surfaces.

---

### 135. Test Environment

Adversarial testing should preferably occur in an environment representative of production.

Important components include:

* Same preprocessing.
* Similar model configuration.
* Similar APIs.
* Similar authentication.
* Similar decision logic.

---

### 136. Production Safety

Security testing should not unintentionally create operational harm.

For critical systems, organizations should establish:

* Testing boundaries.
* Approved test windows.
* Synthetic data.
* Rollback procedures.
* Emergency contacts.

---

### 137. Attack Detection

Organizations should determine whether adversarial activity can be detected.

Detection may use:

* Input anomaly detection.
* Query analysis.
* Prediction monitoring.
* Authentication telemetry.
* Network telemetry.
* SIEM correlation.

---

### 138. Detection vs. Prevention

Not every adversarial example can necessarily be prevented.

Therefore:

```text
Prevention
    +
Detection
    +
Response
    =
Layered Defense
```

---

### 139. Adversarial Input Detection

An input detector can attempt to identify suspicious characteristics before inference.

However, attackers may adapt their inputs to evade the detector.

---

### 140. Detector Robustness

The detector itself can become an ML security target.

```text id="aex140"
Attacker
   ↓
Input Detector
   ↓
Model
```

Security architecture should avoid creating a false assumption that a detector is automatically trustworthy.

---

### 141. Detection Evasion

Attackers may attempt to construct inputs that:

1. Fool the primary model.
2. Avoid the adversarial-input detector.

This creates a multi-objective attack problem.

---

### 142. Cascaded Defenses

Multiple detection stages can increase attacker complexity.

```text id="aex142"
Input
 ↓
Validation
 ↓
Anomaly Detection
 ↓
Model
 ↓
Decision Verification
```

Each stage provides an additional security boundary.

---

### 143. Human Review

For high-risk decisions, suspicious or uncertain predictions can be routed to human review.

```text id="aex143"
Input
 ↓
ML Model
 ↓
High Risk / Uncertain
 ↓
Human Review
```

This can reduce the consequences of individual model failures.

---

### 144. Decision Verification

A downstream rule engine can verify certain high-impact model decisions.

For example:

```text id="aex144"
ML Prediction
     ↓
Business Rules
     ↓
Final Decision
```

This prevents the model from having unrestricted authority.

---

### 145. Defense-in-Depth

A mature architecture should avoid relying exclusively on model robustness.

```text id="aex145"
Secure Input
      ↓
Secure API
      ↓
Robust Model
      ↓
Decision Controls
      ↓
Monitoring
      ↓
Human / Automated Response
```

---

### 146. Model-Independent Controls

Some of the strongest defenses do not depend on the ML algorithm itself.

Examples include:

* Authentication.
* Authorization.
* Network segmentation.
* Rate limiting.
* Input validation.
* Logging.
* Access control.

---

### 147. Security Architecture Principle

An ML model should generally be treated as **one component of a security decision system**, not as the sole security boundary.

---

### 148. High-Risk Decisions

For decisions with substantial consequences, organizations should consider additional safeguards.

Examples include:

* Financial approval.
* Identity verification.
* Security access.
* Fraud blocking.
* Safety-critical control.

---

### 149. Fail-Safe Behavior

Where appropriate, systems should define what happens when model confidence, integrity, or security telemetry indicates abnormal conditions.

Possible responses include:

* Manual review.
* Secondary verification.
* Temporary restriction.
* Fallback rules.
* Service degradation.

---

### 150. Core Principle

Adversarial-example defense requires **multiple layers spanning model robustness, input security, API protection, monitoring, and decision controls**.

```text id="aex150"
MODEL ROBUSTNESS
       +
INPUT VALIDATION
       +
ACCESS CONTROL
       +
QUERY PROTECTION
       +
ADVERSARIAL TESTING
       +
MONITORING
       +
HUMAN / RULE-BASED OVERSIGHT
       ↓
RESILIENT ML DECISION SYSTEM
```

The objective is not merely to make adversarial examples difficult to construct. The objective is to ensure that **even when an attacker succeeds in manipulating model behavior, the resulting security or business impact remains contained, detectable, and recoverable**.

# 09.10 — Adversarial Examples

## Part 4

### 151. Adversarial Example Risk Assessment

Adversarial-example risk should be assessed using the same structured approach applied to other enterprise security risks.

A practical model is:

```text id="aex151"
Threat
  ↓
Attacker Capability
  ↓
Attack Surface
  ↓
Attack Feasibility
  ↓
Model Impact
  ↓
Business Impact
  ↓
Residual Risk
```

The assessment should focus on realistic attack paths rather than theoretical vulnerabilities alone.

---

### 152. Attack Feasibility

A theoretically possible attack may have little practical significance if it requires:

* Complete model access.
* Large amounts of computation.
* Thousands of queries.
* Specialized equipment.
* Unreasonable physical access.

Security teams should distinguish **technical possibility** from **operational feasibility**.

---

### 153. Attacker Capability Matrix

A useful assessment can classify attackers by capability.

| Capability | Example                              |
| ---------- | ------------------------------------ |
| Low        | Ordinary API user                    |
| Moderate   | Authenticated malicious user         |
| High       | Skilled external attacker            |
| Very High  | Insider / compromised ML environment |

The required controls should reflect the expected threat level.

---

### 154. Model Exposure Level

Model exposure also affects risk.

```text id="aex154"
Private Model
     ↓
Internal Model
     ↓
Partner-Accessible Model
     ↓
Public API
     ↓
Public Model Artifact
```

Greater exposure generally provides more opportunities for reconnaissance and attack.

---

### 155. Public Model APIs

Publicly accessible models can receive large numbers of adversarial queries.

Security controls should therefore consider:

* Authentication requirements.
* Rate limits.
* Usage quotas.
* Abuse detection.
* Output restrictions.

---

### 156. Public Model Artifacts

If model artifacts are publicly distributed, attackers may obtain significant information about:

* Architecture.
* Parameters.
* Preprocessing.
* Decision behavior.

This can change the threat model from black-box toward white-box.

---

### 157. Model Confidentiality

Protecting model artifacts can therefore have security value.

Controls may include:

* Access restrictions.
* Encryption.
* Secure repositories.
* Artifact signing.
* Download monitoring.

---

### 158. Security Through Obscurity

Model secrecy should not be treated as the primary security control.

A robust design should assume that an attacker may eventually learn significant information about the model.

Security should instead rely on:

* Robustness.
* Authentication.
* Authorization.
* Monitoring.
* Rate limiting.
* Defense-in-depth.

---

### 159. Adversarial Examples and Model Extraction

Adversarial-example attacks and model-extraction attacks can reinforce one another.

An attacker may first learn about the target model and then use that knowledge to construct adversarial inputs.

```text id="aex159"
Model Queries
     ↓
Behavioral Learning
     ↓
Model Approximation
     ↓
Adversarial Testing
```

---

### 160. Adversarial Examples and Model Inversion

Model inversion attempts to infer information about the data or characteristics represented by a model.

Although distinct from adversarial examples, both exploit information exposed through model behavior.

---

### 161. Adversarial Examples and Membership Inference

Membership inference attempts to determine whether specific data was included in model training.

Again, this is a different threat, but excessive model output information can increase the overall information available to attackers.

---

### 162. Unified Model Threat Surface

These threats should therefore be considered together.

```text id="aex162"
              ML MODEL
                 │
     ┌───────────┼───────────┐
     ↓           ↓           ↓
 Adversarial   Extraction  Inference
 Examples
     │
     ↓
Manipulated Inputs
```

Model security should not treat each threat as completely isolated.

---

### 163. Security Testing Strategy

An enterprise testing program should combine:

1. Normal functional testing.
2. Robustness testing.
3. Adversarial testing.
4. Application-security testing.
5. Infrastructure-security testing.
6. Monitoring validation.

This provides broader assurance than model accuracy testing alone.

---

### 164. Threat-Based Test Cases

Adversarial testing should be derived from the threat model.

For example:

```text id="aex164"
Threat:
Fraudster Manipulates Transaction

        ↓

Test:
Can attacker-controlled features
change the risk decision?

        ↓

Measure:
Attack success + business impact
```

---

### 165. Test Case Documentation

Each security test should record:

* Attack scenario.
* Attacker assumptions.
* Model version.
* Dataset.
* Input constraints.
* Attack method.
* Results.
* Detection capability.
* Business impact.

This creates reproducible security evidence.

---

### 166. Attack Reproducibility

Security findings should be reproducible where possible.

A finding that can be consistently reproduced is easier to:

* Validate.
* Remediate.
* Regression-test.
* Communicate to risk owners.

---

### 167. Model Version Association

Every adversarial test result should identify the model version tested.

```text id="aex167"
Model v3.2
   ↓
Adversarial Test
   ↓
Finding
```

Without version association, the finding may become difficult to interpret after model updates.

---

### 168. Dataset Version Association

The relevant dataset or test corpus should also be recorded.

This is particularly important because changing the data distribution can change model robustness.

---

### 169. Security Baselines

Organizations can establish minimum adversarial-security baselines.

For example:

```text id="aex169"
Required:
✓ Threat model
✓ Adversarial testing
✓ Input controls
✓ Model integrity
✓ Monitoring
✓ Incident response
```

High-impact models may require additional controls.

---

### 170. Risk-Based Security Tiers

A practical governance structure can define different requirements.

| Tier   | Example                   | Controls               |
| ------ | ------------------------- | ---------------------- |
| Tier 1 | Low-impact recommendation | Basic testing          |
| Tier 2 | Business decision support | Enhanced testing       |
| Tier 3 | Fraud/security decision   | Adversarial assessment |
| Tier 4 | Safety/critical decision  | Extensive assurance    |

---

### 171. Security Acceptance Criteria

Before production deployment, the model should satisfy predefined security requirements.

Potential requirements include:

* No unresolved critical adversarial findings.
* Model integrity verified.
* Attack surface documented.
* Monitoring operational.
* Recovery mechanism tested.

---

### 172. Exception Management

If a model cannot meet a security requirement, the exception should be formally documented.

It should include:

* Reason.
* Risk.
* Compensating controls.
* Risk owner.
* Expiration or review date.

---

### 173. Compensating Controls

If model robustness cannot be sufficiently improved, other controls may reduce the risk.

Examples include:

* Human approval.
* Secondary model.
* Rule-based validation.
* Transaction limits.
* Additional authentication.

```text id="aex173"
Model Weakness
      ↓
Compensating Control
      ↓
Reduced Business Impact
```

---

### 174. Transaction Limits

For financial or transactional systems, limits can reduce the impact of successful model manipulation.

For example:

```text id="aex174"
ML Approval
     ↓
Transaction Limit
     ↓
Additional Verification
```

This prevents a single prediction from necessarily enabling unlimited activity.

---

### 175. Secondary Verification

A second security control can independently validate high-risk decisions.

This could involve:

* Another model.
* Deterministic rules.
* Human approval.
* Additional identity verification.

---

### 176. Human-in-the-Loop

Human review can provide an additional control layer when the model is uncertain or the potential consequence is high.

```text id="aex176"
ML Prediction
      ↓
Risk / Uncertainty
      ↓
Human Review
      ↓
Final Decision
```

---

### 177. Human Review Limitations

Human oversight is not automatically effective.

Organizations should consider:

* Reviewer expertise.
* Workload.
* Decision time.
* Alert volume.
* Automation bias.

A poorly designed human-review process can become another operational weakness.

---

### 178. Automation Bias

Users may over-trust automated predictions.

Therefore, human reviewers should understand:

* Model limitations.
* Confidence limitations.
* Adversarial risks.
* Appropriate escalation procedures.

---

### 179. Model Output Governance

The application should define how model outputs may be used.

For example:

```text id="aex179"
Model Output
     ↓
Decision Support
     ↓
Human / Rules
     ↓
Final Action
```

or, for lower-risk applications:

```text id="aex179b"
Model Output
     ↓
Automated Action
```

The more authority given to the model, the greater the security requirement.

---

### 180. Model Authority

A useful governance question is:

> **What is the maximum authority this model has over a real-world decision?**

A recommendation engine and an automated security-blocking system should not necessarily receive the same security treatment.

---

### 181. Blast Radius

Organizations should assess the potential **blast radius** of a successful adversarial example.

Questions include:

* Does one input affect one transaction?
* Can one input affect many users?
* Can manipulation persist?
* Can the attacker automate the attack?
* Can the attack propagate to another system?

---

### 182. Single-Input Impact

Some attacks may affect only one decision.

```text id="aex182"
Adversarial Input
      ↓
One Incorrect Decision
```

The risk may be relatively contained.

---

### 183. Systemic Impact

Other weaknesses may affect large numbers of decisions.

```text id="aex183"
Adversarial Technique
       ↓
Model
       ↓
Many Predictions
       ↓
Systemic Impact
```

Systemic vulnerabilities require significantly stronger controls.

---

### 184. Persistence

Security teams should determine whether the attack effect is:

* Temporary.
* Per-request.
* Persistent.
* Embedded into the model.

A persistent effect generally creates greater risk.

---

### 185. Attack Automation

Automation can dramatically increase attack scale.

```text id="aex185"
Manual Attack
   ↓
One / Few Inputs

Automated Attack
   ↓
Thousands of Inputs
```

Monitoring should therefore identify automated probing and abuse patterns.

---

### 186. Abuse Prevention

ML APIs should have appropriate abuse-prevention mechanisms.

Possible controls include:

* Rate limits.
* Quotas.
* Account restrictions.
* Behavioral monitoring.
* Automated blocking.
* Authentication.

---

### 187. Detection Coverage

Organizations should measure whether their monitoring can identify adversarial behavior.

Useful questions include:

* Would repeated probing generate an alert?
* Would unusual inputs be detected?
* Would model-output anomalies be detected?
* Would unauthorized model changes be detected?

---

### 188. Mean Time to Detect

For important ML systems, organizations can measure the time between malicious activity and detection.

```text id="aex188"
Attack Begins
     ↓
Detection
     ↓
MTTD
```

---

### 189. Mean Time to Respond

Similarly, organizations can measure the time required to contain an adversarial ML incident.

```text id="aex189"
Detection
   ↓
Response
   ↓
MTTR
```

---

### 190. Security Observability

Effective monitoring requires sufficient telemetry.

Relevant telemetry may include:

* Requests.
* Inputs or privacy-safe representations.
* Model versions.
* Predictions.
* Confidence information.
* Authentication events.
* Administrative actions.

---

### 191. Privacy Considerations

Logging model inputs can create privacy risks.

Security monitoring should therefore balance:

```text id="aex191"
Security Visibility
       ↕
Data Minimization
       ↕
Privacy Protection
```

Sensitive inputs should not be retained unnecessarily.

---

### 192. Data Protection

Where model inputs contain personal or confidential information, logging should follow the organization's applicable privacy and data-protection requirements.

---

### 193. Secure Logging

Security logs should be:

* Access controlled.
* Integrity protected.
* Appropriately retained.
* Monitored.
* Protected against unauthorized modification.

---

### 194. Alert Triage

Not every unusual model behavior represents an adversarial attack.

Possible explanations include:

* Legitimate user behavior.
* Data drift.
* Software defects.
* Configuration changes.
* Model degradation.
* Actual attack activity.

Analysts should correlate multiple signals.

---

### 195. Security Correlation

A stronger detection strategy correlates ML telemetry with conventional security telemetry.

```text id="aex195"
ML Anomaly
   +
API Anomaly
   +
Identity Anomaly
   +
Network Anomaly
   ↓
Higher-Confidence Investigation
```

---

### 196. SIEM Integration

Important ML security events can be integrated into the enterprise SIEM.

This allows analysts to correlate model-related activity with:

* Identity events.
* Endpoint events.
* Network events.
* Cloud activity.
* Application logs.

---

### 197. Incident Escalation

An adversarial-example event should have predefined escalation criteria.

For example:

```text id="aex197"
Suspicious Input
      ↓
Automated Detection
      ↓
Analyst Review
      ↓
Risk Assessment
      ↓
Incident Escalation
```

---

### 198. Recovery

Recovery should include more than simply restoring service.

The organization should determine:

* Whether the model was compromised.
* Whether training data was affected.
* Whether previous predictions are trustworthy.
* Whether downstream decisions require review.

---

### 199. Post-Incident Model Review

After a confirmed adversarial incident, the organization should reassess:

* Threat model.
* Model robustness.
* Input controls.
* Monitoring.
* API protections.
* Business decision controls.

The incident should improve the overall security posture.

---

### 200. Core Governance Principle

Adversarial examples should be managed as an **enterprise model-security risk rather than merely an algorithmic research problem**.

```text id="aex200"
THREAT MODEL
     ↓
MODEL / INPUT SECURITY
     ↓
ADVERSARIAL TESTING
     ↓
DEFENSE-IN-DEPTH
     ↓
MONITORING
     ↓
INCIDENT RESPONSE
     ↓
RECOVERY
     ↓
CONTINUOUS IMPROVEMENT
```

A mature organization does not require the impossible standard that adversarial examples can never succeed. Instead, it establishes **defined robustness expectations, limits attacker opportunities, detects abnormal behavior, restricts the authority of model outputs, contains successful manipulation, and maintains the ability to recover trusted operations**.
