# 09.12 — Backdoors and Model Manipulation

## Part 1

### 1. Backdoors and Model Manipulation

**Backdoors and model manipulation** are model-security threats in which an attacker intentionally causes a machine-learning model to behave differently from its intended design.

A backdoored model may behave normally under ordinary conditions while producing attacker-influenced behavior when a particular condition or trigger is present.

```text
Normal Input
     ↓
   Model
     ↓
Expected Output

Trigger Condition
     ↓
   Model
     ↓
Manipulated Output
```

---

### 2. Model Manipulation

**Model manipulation** is the broader concept.

It can involve unauthorized changes to:

* Model parameters.
* Architecture.
* Configuration.
* Training process.
* Fine-tuning.
* Model artifacts.
* Inference behavior.

A backdoor is one possible outcome of model manipulation.

---

### 3. Backdoor vs. General Model Manipulation

| Concept             | Description                                         |
| ------------------- | --------------------------------------------------- |
| Model manipulation  | Unauthorized alteration of model behavior           |
| Backdoor            | Hidden conditional behavior introduced into a model |
| Poisoning           | Manipulation of training data/process               |
| Adversarial example | Manipulation of inference input                     |

These concepts can overlap.

---

### 4. Why Backdoors Are Dangerous

A backdoored model can be difficult to identify because its normal performance may remain acceptable.

```text
Standard Validation
        ↓
     PASS ✓

Backdoor Test
        ↓
     FAIL ✗
```

This creates a significant challenge for traditional model-validation processes.

---

### 5. Hidden Conditional Behavior

The defining characteristic of many backdoors is conditional behavior.

```text
IF normal_condition
    → normal prediction

IF trigger_condition
    → attacker-influenced prediction
```

The trigger may be associated with a particular input characteristic or combination of characteristics.

---

### 6. Backdoor Lifecycle

A generalized lifecycle can be represented as:

```text
Attack Preparation
       ↓
Model / Training Compromise
       ↓
Backdoor Introduction
       ↓
Model Validation
       ↓
Deployment
       ↓
Trigger Activation
       ↓
Manipulated Behavior
```

---

### 7. Backdoor Introduction Points

Backdoors can potentially enter through different stages:

* Training data.
* Fine-tuning.
* Training code.
* Model parameters.
* Model artifacts.
* Third-party models.
* Model conversion processes.
* Deployment infrastructure.

---

### 8. Training-Based Backdoors

A training-based backdoor may be introduced by manipulating the training process so that the model learns an unintended association.

Conceptually:

```text
Training Data
     +
Trigger Pattern
     +
Target Behavior
        ↓
Training
        ↓
Backdoored Model
```

---

### 9. Artifact-Level Manipulation

An attacker does not necessarily need to manipulate training.

If an attacker gains access to the model artifact, they may attempt to alter the artifact directly.

```text
Trusted Model
      ↓
Unauthorized Modification
      ↓
Modified Model
      ↓
Deployment
```

This is why model-artifact integrity is a critical security control.

---

### 10. Model Artifact

A model artifact may include:

* Parameters.
* Weights.
* Architecture.
* Tokenizer.
* Configuration.
* Metadata.
* Supporting files.

The complete artifact should be treated as a security-sensitive asset.

---

### 11. Model Integrity

Model integrity means that the deployed model is the authorized model produced by an approved process.

A useful chain is:

```text
Approved Training
      ↓
Validated Model
      ↓
Signed Artifact
      ↓
Verified Deployment
```

---

### 12. Cryptographic Integrity

Cryptographic mechanisms can help detect unauthorized artifact modification.

Examples include:

* Hashes.
* Digital signatures.
* Signed manifests.
* Trusted artifact registries.

---

### 13. Hash Verification

A hash can establish whether an artifact changed after a known reference was created.

```text
Approved Model
     ↓
Hash A

Deployed Model
     ↓
Hash B

A = B → Integrity Match
A ≠ B → Investigate
```

---

### 14. Digital Signatures

Digital signatures can provide stronger assurance about both integrity and authorized origin.

```text
Authorized Builder
       ↓
Sign Model
       ↓
Registry
       ↓
Deployment System
       ↓
Verify Signature
```

---

### 15. Model Provenance

Security teams should know:

* Who created the model.
* Which dataset was used.
* Which code was used.
* Which dependencies were used.
* Which training run generated it.
* Who approved it.
* Where it was deployed.

This creates model provenance.

---

### 16. Provenance Chain

```text
Data
 ↓
Training Code
 ↓
Training Environment
 ↓
Training Run
 ↓
Model Artifact
 ↓
Security Validation
 ↓
Approval
 ↓
Deployment
```

A break in this chain creates uncertainty about model trustworthiness.

---

### 17. Unauthorized Model Changes

Potential unauthorized changes include:

* Parameter modification.
* Architecture modification.
* Configuration changes.
* Added model components.
* Removed safety mechanisms.
* Changed preprocessing.
* Changed output logic.

---

### 18. Configuration Manipulation

An attacker may manipulate configuration without changing model weights.

Examples include:

* Model selection.
* Thresholds.
* Routing.
* Preprocessing.
* Post-processing.
* Feature mappings.

Therefore, model security must protect both the model and its surrounding configuration.

---

### 19. Preprocessing Manipulation

The model can behave differently if the preprocessing pipeline is modified.

```text
Input
 ↓
Modified Preprocessing
 ↓
Model
 ↓
Unexpected Output
```

A model may therefore appear intact while its effective behavior has been altered.

---

### 20. Post-Processing Manipulation

Similarly, an attacker could manipulate the logic applied after model inference.

```text
Model
 ↓
Prediction
 ↓
Modified Post-Processing
 ↓
Final Decision
```

This can create model-manipulation risk even when the model itself has not changed.

---

### 21. Model Wrapper Security

Production models are often accessed through APIs or application wrappers.

Security assessment should therefore include:

* Model-serving code.
* API logic.
* Input transformation.
* Output transformation.
* Routing logic.

---

### 22. Model Routing

Large ML platforms may route requests to different models.

```text
Request
   ↓
Router
 ┌─┴──────┐
 ↓        ↓
Model A  Model B
```

Manipulating routing rules can effectively change which model makes the decision.

---

### 23. Multi-Model Systems

Modern enterprise systems may contain:

* Primary models.
* Secondary models.
* Safety classifiers.
* Moderation models.
* Ranking models.
* Fraud models.

An attacker may target any component in the chain.

---

### 24. Cascading Manipulation

One compromised model can influence downstream models or systems.

```text
Model A
  ↓
Output
  ↓
Model B
  ↓
Business Decision
```

Therefore, model dependencies should be documented.

---

### 25. Backdoor Activation

A backdoor generally requires some condition to activate.

The condition may be:

* Specific input characteristics.
* A combination of features.
* A contextual condition.
* A particular data pattern.

The security concern is that normal testing may never activate it.

---

### 26. Trigger Visibility

A trigger may be:

* Obvious.
* Rare.
* Subtle.
* Distributed across multiple features.

The less obvious the trigger, the harder detection may become.

---

### 27. Static vs. Dynamic Detection

Backdoor detection can use two broad approaches.

**Static analysis:**

```text
Inspect Model
     ↓
Parameters / Structure
     ↓
Potential Anomaly
```

**Dynamic analysis:**

```text
Test Inputs
     ↓
Observe Behavior
     ↓
Unexpected Conditional Response
```

Both approaches have limitations.

---

### 28. Behavioral Testing

Behavioral testing examines whether the model behaves consistently with its intended specification.

Testing can include:

* Normal cases.
* Edge cases.
* Rare cases.
* Security-sensitive cases.
* Unexpected combinations.

---

### 29. Specification-Based Testing

Testing should begin with a clear statement of intended behavior.

For example:

> Inputs meeting defined business criteria should produce decisions within the approved decision boundaries.

Without a defined expected behavior, detecting manipulation becomes more difficult.

---

### 30. Security Invariants

Security invariants are properties that should remain true regardless of normal input variation.

Examples may include:

* Unauthorized users cannot trigger privileged actions.
* Certain prohibited conditions must never result in approval.
* Security controls cannot be bypassed through model output.

---

### 31. Invariant Testing

```text
Input Variations
      ↓
Model
      ↓
Security Invariants
      ↓
Must Remain True
```

This can help identify unexpected model behavior.

---

### 32. Differential Testing

A suspicious model can be compared with:

* Previous trusted versions.
* Independently trained models.
* Reference implementations.

Significant behavioral differences can provide investigation signals.

---

### 33. Version Comparison

For example:

```text
Trusted Model v4
       vs.
Candidate Model v5
       ↓
Behavioral Comparison
```

Unexpected changes should be explained before approval.

---

### 34. Independent Validation

Validation should ideally not be performed exclusively by the same process that produced the model.

An independent validation layer can reduce the risk of a compromised training process approving its own output.

---

### 35. Separation of Model Creation and Validation

A mature workflow can separate:

```text
Model Engineering
       ↓
Independent Validation
       ↓
Security Approval
       ↓
Deployment
```

---

### 36. Model Security Testing

Security testing should consider:

* Model integrity.
* Backdoor behavior.
* Unauthorized modifications.
* Input manipulation.
* Output manipulation.
* Serving-layer attacks.

---

### 37. Red-Team Testing

A model-security red team can attempt to identify unintended behavior under controlled conditions.

The purpose is defensive:

> Discover weaknesses before a malicious actor does.

---

### 38. Threat Modeling

Before testing, security teams should identify:

* Valuable assets.
* Trust boundaries.
* Attacker capabilities.
* Model dependencies.
* Potential manipulation points.
* Business consequences.

---

### 39. Attack Surface Mapping

A model attack surface can be represented as:

```text
              MODEL
                │
     ┌──────────┼──────────┐
     ↓          ↓          ↓
 Training    Artifact    Serving
    │           │           │
    ↓           ↓           ↓
  Data       Registry       API
```

Each branch should receive appropriate security controls.

---

### 40. Core Principle

Backdoor and model-manipulation security begins with a simple assumption:

> **A model can be compromised without appearing obviously broken.**

Therefore, enterprise protection must combine:

```text
Strong Provenance
       +
Artifact Integrity
       +
Access Control
       +
Independent Validation
       +
Behavioral Testing
       +
Continuous Monitoring
```

A trusted model is not simply a model that produces accurate predictions. It is a model whose **origin, training process, artifact integrity, configuration, deployment path, and runtime behavior can all be established as trustworthy**.

# 09.12 — Backdoors and Model Manipulation

## Part 2

### 41. Backdoor Attack Surface

A backdoor can potentially be introduced at multiple points in the model lifecycle.

```text id="bm201"
Data
 ↓
Labeling
 ↓
Training
 ↓
Fine-Tuning
 ↓
Model Artifact
 ↓
Model Registry
 ↓
Deployment
 ↓
Inference
```

Security teams should therefore avoid limiting backdoor analysis to the training dataset.

---

### 42. Training-Time Backdoors

Training-time backdoors are introduced while the model is being created or modified.

Potential pathways include:

* Poisoned training data.
* Malicious labels.
* Compromised training code.
* Manipulated fine-tuning.
* Unauthorized training configurations.

The resulting model may appear legitimate after training.

---

### 43. Fine-Tuning Backdoors

Fine-tuning is particularly important because organizations frequently customize existing models.

```text id="bm203"
Base Model
    ↓
Fine-Tuning Dataset
    ↓
Fine-Tuning Process
    ↓
Enterprise Model
```

A compromised fine-tuning process can alter the behavior of an otherwise trusted base model.

---

### 44. Transfer Learning Risk

When knowledge is transferred from one model into another, trust in the source model becomes part of the security boundary.

Organizations should therefore assess:

* Source model provenance.
* Model integrity.
* License and distribution source.
* Known security issues.
* Modification history.

---

### 45. Third-Party Model Risk

Third-party models introduce additional trust dependencies.

Potential risks include:

* Unknown training history.
* Unknown modifications.
* Malicious components.
* Insufficient documentation.
* Unverified model artifacts.

---

### 46. Pretrained Model Verification

Before an external model is used, organizations should establish:

```text id="bm206"
Source
 ↓
Provenance
 ↓
Integrity
 ↓
Security Assessment
 ↓
Behavioral Validation
 ↓
Approval
```

---

### 47. Model Import Controls

Production environments should not necessarily allow developers to import arbitrary models.

A controlled model-import process can require:

* Approved source.
* Artifact verification.
* Malware/security scanning.
* Dependency review.
* Model testing.
* Formal approval.

---

### 48. Model Artifact Scanning

Security scanning may examine:

* File structure.
* Metadata.
* Dependencies.
* Serialization format.
* Unexpected components.

Scanning should complement, not replace, behavioral validation.

---

### 49. Unsafe Model Serialization

Some model formats or loading mechanisms can introduce security risks beyond the model's mathematical behavior.

A model file may potentially contain executable or unsafe components depending on the framework and serialization mechanism.

Therefore:

> **Model files should be treated as untrusted software artifacts until verified.**

---

### 50. Secure Model Loading

Production systems should use controlled mechanisms for loading models.

Security controls may include:

* Trusted formats.
* Sandboxed processing.
* Dependency restrictions.
* Artifact verification.
* Least-privilege execution.

---

### 51. Model Registry as a Trust Boundary

The model registry should be treated as a security-critical system.

```text id="bm211"
Validated Model
      ↓
Model Registry
      ↓
Approved Artifact
      ↓
Production
```

Unauthorized modification within the registry could undermine downstream security controls.

---

### 52. Registry Access Control

Registry permissions should distinguish between:

* Upload.
* Modify.
* Approve.
* Promote.
* Deploy.
* Delete.

These permissions do not necessarily need to be assigned to the same identities.

---

### 53. Model Promotion

A model should pass defined gates before moving into production.

```text id="bm213"
Development
    ↓
Validation
    ↓
Security Testing
    ↓
Approval
    ↓
Production
```

---

### 54. Deployment-Time Manipulation

An attacker may target the deployment environment rather than the model itself.

Potential targets include:

* Model path.
* Container image.
* Configuration.
* Environment variables.
* Routing rules.
* Serving framework.

---

### 55. Container Image Integrity

If a model is packaged into a container, the container image becomes part of the model's security chain.

```text id="bm215"
Model
 +
Dependencies
 +
Serving Code
      ↓
Container Image
      ↓
Deployment
```

---

### 56. Container Image Signing

Signed container images can help ensure that only approved artifacts are deployed.

This extends model integrity controls into the application infrastructure.

---

### 57. Infrastructure-as-Code

Deployment configuration should also be protected.

Unauthorized infrastructure changes could alter:

* Which model is deployed.
* Which model receives traffic.
* Which configuration is used.
* Which external services are accessible.

---

### 58. Configuration Drift

A model may be validated correctly but later operate with altered configuration.

```text id="bm218"
Validated Model
      ↓
Production Configuration Changes
      ↓
Different Effective Behavior
```

Configuration monitoring is therefore part of model security.

---

### 59. Runtime Model Replacement

Serving infrastructure should prevent unauthorized replacement of the active model.

Potential controls include:

* Restricted filesystem permissions.
* Artifact signatures.
* Immutable deployments.
* Registry authorization.
* Deployment auditing.

---

### 60. Model Shadowing

An attacker may attempt to introduce an unauthorized model that appears legitimate.

For example:

```text id="bm220"
Approved Model
     ↓
Expected Path

Malicious Model
     ↓
Unexpected Path
```

Asset inventory and deployment verification help detect such conditions.

---

### 61. Model Identity

Every production model should have a unique identity.

Useful identifiers include:

* Model name.
* Version.
* Artifact hash.
* Registry identifier.
* Build identifier.

---

### 62. Model Identity Verification

At deployment:

```text id="bm222"
Expected Model Identity
        ↓
Compare
        ↓
Running Model Identity
```

A mismatch should trigger investigation or deployment failure.

---

### 63. Runtime Attestation

Where supported, infrastructure can provide evidence about the environment in which the model is running.

This can strengthen assurance that the approved artifact is executing in an approved environment.

---

### 64. Trusted Execution Environment

For particularly sensitive workloads, hardware-backed isolation may provide additional protection for:

* Model artifacts.
* Inference processing.
* Sensitive data.

Such controls are most relevant to high-value or highly confidential models.

---

### 65. Model Parameter Manipulation

An attacker with sufficient access might attempt to modify model parameters.

The impact depends on:

* Model architecture.
* Parameter sensitivity.
* Attacker's access.
* Ability to bypass integrity controls.

---

### 66. Parameter Integrity

Model parameters should be protected as part of the model artifact.

```text id="bm226"
Architecture
+
Parameters
+
Configuration
      ↓
Model Identity
```

Protecting only the model filename or registry record is insufficient.

---

### 67. Partial Model Manipulation

Attackers do not necessarily need to replace an entire model.

A smaller unauthorized modification could potentially alter behavior while preserving most of the original artifact.

This reinforces the value of cryptographic integrity verification.

---

### 68. Configuration-Based Backdoors

A malicious behavior may be introduced through external configuration rather than model weights.

Potential examples include:

* Special routing.
* Hidden thresholds.
* Conditional rules.
* Feature overrides.

Therefore, security testing should evaluate the **effective model system**, not just the model file.

---

### 69. Feature Manipulation

A backdoor may exploit a particular feature or feature combination.

If feature processing is compromised, the model may receive attacker-controlled representations.

```text id="bm229"
Raw Input
    ↓
Feature Pipeline
    ↓
Manipulated Feature
    ↓
Model
    ↓
Unexpected Result
```

---

### 70. Feature Store Security

Enterprise feature stores should protect:

* Feature definitions.
* Feature values.
* Access permissions.
* Version history.
* Data lineage.

A compromised feature store can affect multiple models simultaneously.

---

### 71. Shared Feature Dependencies

When several models consume the same feature, one compromised feature pipeline may influence many models.

```text id="bm231"
Feature Store
    ↓
 ┌──┼──┐
 ↓  ↓  ↓
M1 M2 M3
```

Shared infrastructure therefore increases potential blast radius.

---

### 72. Model Dependency Chains

Complex AI systems can contain multiple model dependencies.

For example:

```text id="bm232"
Input
 ↓
Classifier
 ↓
Risk Model
 ↓
Decision Model
 ↓
Business Action
```

A manipulation in an upstream model can affect downstream decisions.

---

### 73. Cascading Trust

Trust must propagate through the entire dependency chain.

If Model A depends on Model B, the security posture of Model A partially depends on the integrity of Model B.

---

### 74. Model-to-Model Validation

Organizations should test whether a manipulated upstream output can cause unsafe downstream behavior.

This is particularly important in automated decision systems.

---

### 75. Guardrail Models

Some systems use secondary models to detect unsafe or abnormal outputs.

```text id="bm235"
Primary Model
     ↓
Guardrail
     ↓
Approved / Blocked
```

Guardrails can reduce risk but should themselves be secured and validated.

---

### 76. Guardrail Bypass

If the primary model is manipulated, attackers may attempt to produce outputs that bypass secondary controls.

Security testing should therefore assess the complete control chain.

---

### 77. Independent Control Layers

For high-impact decisions, deterministic controls may provide an additional layer beyond another ML model.

```text id="bm237"
ML Model
   ↓
Rule-Based Control
   ↓
Final Decision
```

This can reduce dependence on a single learned component.

---

### 78. Model Manipulation Through APIs

APIs can expose administrative functions such as:

* Model upload.
* Model replacement.
* Configuration changes.
* Retraining.
* Deployment.

These endpoints require strong authentication and authorization.

---

### 79. API Authorization

A user who can invoke inference should not automatically be able to:

* Upload models.
* Modify models.
* Change thresholds.
* Trigger production retraining.

Least privilege should apply to model-management APIs.

---

### 80. Administrative API Monitoring

Sensitive model-management operations should generate security events.

Examples include:

```text id="bm240"
Model Uploaded
Model Replaced
Model Promoted
Model Rolled Back
Configuration Changed
Deployment Triggered
```

---

### 81. Insider Threat

Insiders with legitimate access can represent a significant model-manipulation risk.

Potential scenarios include:

* Malicious modification.
* Unauthorized model replacement.
* Bypassing validation.
* Manipulating datasets.
* Abuse of administrative privileges.

---

### 82. Privileged Insider Controls

Controls may include:

* Least privilege.
* Separation of duties.
* MFA.
* Privileged access management.
* Approval workflows.
* Audit logging.

---

### 83. Developer Environment Risk

A compromised developer workstation can become a path into the ML lifecycle.

For example:

```text id="bm243"
Developer Device
      ↓
Source Code
      ↓
Training Pipeline
      ↓
Model
```

Endpoint security therefore contributes to model security.

---

### 84. CI/CD Security

ML CI/CD pipelines should be protected similarly to conventional software pipelines.

Controls include:

* Protected branches.
* Code review.
* Build identity.
* Artifact signing.
* Secret management.
* Deployment authorization.

---

### 85. Build Integrity

The build process should produce traceable artifacts.

```text id="bm245"
Source Code
    ↓
Controlled Build
    ↓
Artifact
    ↓
Hash / Signature
    ↓
Registry
```

---

### 86. Build Pipeline Compromise

If an attacker compromises the build pipeline, they may be able to alter the model or its supporting components before the artifact reaches production.

Therefore, pipeline security is part of model integrity.

---

### 87. Reproducible Builds

Where feasible, organizations should be able to reproduce the model artifact from the documented source materials.

Unexpected differences can then become investigation signals.

---

### 88. Model Release Manifest

A model release can include a manifest containing:

* Model version.
* Artifact hash.
* Dataset version.
* Code commit.
* Dependency versions.
* Configuration.
* Security-test results.

This creates a release-level integrity record.

---

### 89. Release Approval

Production model releases should have explicit approval status.

For example:

```text id="bm249"
Candidate
   ↓
Security Review
   ↓
Approved
   ↓
Production
```

An unapproved artifact should not be deployable through the normal release path.

---

### 90. Emergency Releases

Emergency model changes should still preserve traceability.

Even when normal approval processes are accelerated, organizations should record:

* Who authorized the change.
* Why it was required.
* What artifact was deployed.
* What validation was performed.

---

### 91. Backdoor Detection Challenges

Backdoor detection is difficult because malicious behavior can be:

* Conditional.
* Rare.
* Hidden.
* Trigger-dependent.
* Absent from ordinary validation datasets.

---

### 92. Clean Accuracy Is Insufficient

A model can have excellent performance on standard validation data while containing malicious conditional behavior.

Therefore:

> **High model accuracy does not prove model integrity.**

---

### 93. Trigger-Agnostic Testing

Organizations should avoid relying exclusively on known trigger patterns.

Security testing can include broader exploration of:

* Rare combinations.
* Unexpected inputs.
* Boundary conditions.
* Sensitive features.
* Out-of-distribution scenarios.

---

### 94. Out-of-Distribution Testing

Testing behavior outside the normal training distribution can reveal unexpected model responses.

However, unusual behavior alone does not prove a backdoor.

It should be investigated in context.

---

### 95. Explainability as an Investigation Aid

Model-explainability techniques can sometimes help investigators identify unusual relationships between inputs and predictions.

They should be treated as investigative evidence rather than definitive proof of a backdoor.

---

### 96. Feature Importance Changes

Unexpected changes in feature importance between trusted and candidate models may warrant investigation.

```text id="bm256"
Trusted Model
Feature A → High
Feature B → Medium

Candidate Model
Feature A → Low
Feature B → Very High
```

Such differences require contextual analysis.

---

### 97. Behavioral Fingerprinting

Organizations can create a behavioral baseline for important models.

A fingerprint may include:

* Representative predictions.
* Performance metrics.
* Sensitivity characteristics.
* Important security behaviors.

Future versions can be compared against the baseline.

---

### 98. Model Integrity Baseline

A model integrity baseline should include more than the artifact hash.

It can combine:

```text id="bm258"
Artifact Identity
+
Training Lineage
+
Configuration
+
Performance
+
Security Properties
+
Deployment Identity
```

---

### 99. Defense-in-Depth

No single control should be expected to detect every backdoor.

A mature architecture combines:

```text id="bm259"
Access Control
      +
Provenance
      +
Artifact Integrity
      +
Secure CI/CD
      +
Independent Validation
      +
Behavioral Testing
      +
Runtime Monitoring
```

---

### 100. Core Principle

Backdoor defense requires organizations to establish **trust before deployment and continuously verify that trust afterward**.

```text id="bm260"
CREATE
  ↓
VERIFY
  ↓
SIGN
  ↓
APPROVE
  ↓
DEPLOY
  ↓
VERIFY AGAIN
  ↓
MONITOR
```

A secure model lifecycle therefore treats **model weights, training data, code, configuration, dependencies, registry records, deployment infrastructure, and runtime behavior as interconnected components of one security boundary**.

# 09.12 — Backdoors and Model Manipulation

## Part 3

### 101. Model Manipulation Threat Model

Model manipulation should be analyzed by identifying who could alter the model, what access they possess, and what business consequences could result.

```text id="mm301"
Threat Actor
     ↓
Access Path
     ↓
Manipulation Point
     ↓
Model Behavior
     ↓
Business Decision
     ↓
Impact
```

Potential threat actors include:

* External attackers.
* Malicious insiders.
* Compromised developers.
* Compromised service accounts.
* Malicious suppliers.
* Attackers controlling third-party infrastructure.

---

### 102. Attacker Access Levels

Different levels of access create different manipulation opportunities.

| Access                | Potential Capability                 |
| --------------------- | ------------------------------------ |
| Inference only        | Observe model behavior               |
| Data access           | Influence training inputs            |
| Training access       | Influence model creation             |
| Registry access       | Replace model artifacts              |
| Deployment access     | Change active model                  |
| Administrative access | Potentially control entire lifecycle |

Security controls should be designed around these access levels.

---

### 103. Black-Box Model Manipulation

In a black-box environment, the attacker does not directly access the model internals.

They may only observe:

```text id="mm303"
Input
  ↓
Model
  ↓
Output
```

The attacker may attempt to infer model behavior from repeated observations.

---

### 104. White-Box Model Manipulation

In a white-box environment, the attacker may have access to:

* Model architecture.
* Parameters.
* Weights.
* Training information.
* Configuration.

This creates a substantially different threat model.

---

### 105. Gray-Box Access

Many enterprise environments fall somewhere between black-box and white-box.

For example, an attacker may know:

* Model architecture.
* API behavior.
* Some training characteristics.

but not possess the complete model artifact.

---

### 106. Insider Manipulation

An insider with legitimate access may have opportunities that an external attacker does not.

For example:

```text id="mm306"
Authorized User
      ↓
Legitimate Access
      ↓
Unauthorized Modification
      ↓
Compromised Model
```

This is why authorization and auditing are essential.

---

### 107. Privilege Escalation

An attacker may first compromise a lower-privileged account and then attempt to obtain model-management privileges.

Security architecture should prevent:

```text id="mm307"
Low Privilege
     ↓
Privilege Escalation
     ↓
Model Administration
```

---

### 108. Service Account Abuse

Automated ML services often have broad permissions.

If compromised, such accounts may provide access to:

* Datasets.
* Model registries.
* Training systems.
* Cloud storage.
* Deployment platforms.

Service identities should therefore follow least privilege.

---

### 109. Credential Rotation

Credentials associated with model-management systems should be rotated and revoked according to organizational security requirements.

Compromised credentials should be capable of rapid invalidation.

---

### 110. Short-Lived Credentials

Where technically feasible, short-lived credentials reduce the window during which compromised access can be abused.

---

### 111. Model Registry Compromise

A compromised registry can represent a particularly significant security event.

```text id="mm311"
Attacker
   ↓
Registry
   ↓
Replace / Modify Model
   ↓
Deployment
   ↓
Compromised Behavior
```

Registry security should therefore receive the same seriousness as other critical software-artifact repositories.

---

### 112. Registry Integrity

Important registry records should be protected against unauthorized:

* Modification.
* Deletion.
* Replacement.
* Promotion.
* Metadata changes.

---

### 113. Immutable Releases

Approved production model versions should ideally be immutable.

If changes are required, a new version should be created rather than silently modifying the existing artifact.

```text id="mm313"
Model v4
   ↓
Immutable

Change Required
   ↓
Model v5
```

---

### 114. Version Traceability

Every production model should be traceable to:

* A specific artifact.
* A specific training run.
* A specific dataset version.
* A specific code version.

---

### 115. Rollback Integrity

Rollback mechanisms must themselves be protected.

An attacker should not be able to claim that a malicious model is the "known-good" version.

---

### 116. Trusted Model Repository

Organizations should maintain a controlled repository for approved production models.

Access should be restricted and model artifacts should have verifiable integrity.

---

### 117. Model Approval State

A useful registry state model is:

```text id="mm317"
Development
     ↓
Testing
     ↓
Security Review
     ↓
Approved
     ↓
Production
     ↓
Retired
```

Only appropriate states should be eligible for deployment.

---

### 118. Unauthorized Promotion

A model should not be deployable simply because it exists in the registry.

Deployment systems should verify that the artifact has the required approval state.

---

### 119. Deployment Authorization

Deployment should require both:

* An authorized deployment identity.
* An authorized model artifact.

```text id="mm319"
Authorized Identity
        +
Approved Artifact
        ↓
Deployment Allowed
```

---

### 120. Runtime Integrity Verification

Where practical, the serving system can verify the identity of the model when it starts.

This can detect cases where an unexpected artifact has been mounted or supplied.

---

### 121. Model Startup Verification

Conceptually:

```text id="mm321"
Model Loaded
     ↓
Verify Hash / Signature
     ↓
Valid?
  ↙     ↘
Yes      No
 ↓        ↓
Start    Reject
```

---

### 122. Runtime Monitoring

Security monitoring should detect unexpected changes to:

* Model files.
* Containers.
* Configuration.
* Serving processes.
* Deployment identities.

---

### 123. File Integrity Monitoring

File integrity monitoring can provide alerts when protected model artifacts are modified unexpectedly.

This is particularly useful for environments where models are stored locally.

---

### 124. Container Runtime Monitoring

Containerized model-serving environments should monitor for:

* Unexpected processes.
* Unauthorized file changes.
* Privilege escalation.
* Unexpected network activity.

---

### 125. Network Controls

Model-serving environments should have controlled network connectivity.

A model-serving workload should not automatically have unrestricted access to internal systems.

---

### 126. Egress Restrictions

Restricting unnecessary outbound connectivity can reduce the consequences of a compromised model-serving environment.

This can limit potential:

* Data exfiltration.
* Command-and-control.
* Unauthorized downloads.

---

### 127. Model Isolation

High-value models may benefit from dedicated:

* Compute resources.
* Network segments.
* Service identities.
* Storage boundaries.

Isolation reduces cross-system compromise.

---

### 128. Multi-Tenant ML Platforms

Shared ML platforms create additional security considerations.

A compromise affecting one tenant should not allow unauthorized access to another tenant's:

* Models.
* Data.
* Credentials.
* Training jobs.

---

### 129. Tenant Isolation

Controls may include:

* Namespace separation.
* Identity isolation.
* Storage permissions.
* Network policies.
* Resource boundaries.

---

### 130. Model Manipulation Through Shared Infrastructure

A shared dependency can become a common attack path.

```text id="mm330"
Shared Infrastructure
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
 M1    M2    M3
```

Security architecture should account for this potential blast radius.

---

### 131. Model Dependency Inventory

Organizations should maintain an inventory of:

* Models.
* Versions.
* Owners.
* Dependencies.
* Data sources.
* Applications.
* Deployment environments.

---

### 132. Critical Model Identification

Not every model requires the same level of protection.

Organizations should identify models whose compromise could cause:

* Significant financial loss.
* Security failures.
* Regulatory impact.
* Safety consequences.
* Major operational disruption.

---

### 133. Critical Model Controls

High-criticality models may require:

* Stronger authentication.
* Multi-person approval.
* Enhanced integrity verification.
* More extensive testing.
* Increased monitoring.
* Faster incident response.

---

### 134. Backdoor Detection Through Validation

Validation should examine both expected and unexpected behaviors.

```text id="mm334"
Expected Behavior
       +
Edge Cases
       +
Security Scenarios
       +
Unexpected Conditions
       ↓
Behavioral Assessment
```

---

### 135. Negative Testing

Negative testing examines how the model behaves when presented with conditions that should not result in a particular outcome.

This can help verify that security boundaries remain intact.

---

### 136. Boundary Testing

Models should be tested around important decision boundaries.

```text id="mm336"
Low Risk
──────────────
      Boundary
──────────────
High Risk
```

Unexpected behavior near the boundary may indicate model weakness or manipulation.

---

### 137. Sensitivity Testing

Security teams can assess how much predictions change when relevant inputs are changed.

Large unexplained changes can warrant investigation.

---

### 138. Controlled Perturbation

Controlled changes to inputs can help establish whether model behavior is consistent with its intended design.

The purpose is defensive validation, not exploitation.

---

### 139. Robustness Baseline

A trusted model can establish a robustness baseline against which future versions are compared.

```text id="mm339"
Trusted Version
      ↓
Security Baseline
      ↓
Candidate Version
      ↓
Compare
```

---

### 140. Model Behavior Drift vs. Manipulation

Unexpected behavior does not necessarily mean malicious manipulation.

Potential causes include:

* Data drift.
* Model updates.
* Configuration changes.
* Dependency changes.
* Software defects.
* Actual compromise.

Security teams should distinguish these possibilities.

---

### 141. Change Correlation

A model anomaly becomes more suspicious when it coincides with an unauthorized change.

```text id="mm341"
Behavior Change
      +
Unauthorized Access
      +
Artifact Change
      ↓
High-Priority Investigation
```

---

### 142. Security Event Correlation

Model-security events should be correlated with:

* Identity logs.
* Cloud logs.
* CI/CD logs.
* Registry logs.
* Endpoint telemetry.
* Network telemetry.

---

### 143. Security Operations Integration

Model security should be integrated into the organization's broader SOC processes where appropriate.

This allows ML-related events to be handled alongside conventional security events.

---

### 144. Model Security Alerts

Potential high-value alerts include:

* Unsigned model deployed.
* Unexpected model hash.
* Unauthorized model promotion.
* Production artifact modified.
* Training configuration changed.
* Unapproved model source detected.

---

### 145. Alert Severity

Alert severity should consider:

* Model criticality.
* Type of change.
* Identity involved.
* Deployment status.
* Business impact.

---

### 146. Automated Blocking

For high-confidence integrity violations, deployment systems may automatically reject the model.

```text id="mm346"
Integrity Check
      ↓
FAIL
      ↓
Deployment Blocked
      ↓
Security Alert
```

Automation can reduce the time between detection and containment.

---

### 147. Manual Investigation

Automated blocking should still preserve evidence for investigation.

Security teams need sufficient context to understand:

* What changed.
* Who initiated it.
* Which artifact was affected.
* Whether production was impacted.

---

### 148. Incident Response Playbook

A model-manipulation playbook should define:

1. Detection.
2. Verification.
3. Containment.
4. Model rollback.
5. Evidence preservation.
6. Scope assessment.
7. Root-cause analysis.
8. Recovery.
9. Lessons learned.

---

### 149. Recovery Validation

After rollback or replacement, verify:

```text id="mm349"
Artifact Integrity
      ↓
Configuration Integrity
      ↓
Deployment Identity
      ↓
Behavioral Testing
      ↓
Production Monitoring
```

---

### 150. Core Principle

**Backdoor defense requires control over both the model and everything that can influence the model's effective behavior.**

```text id="mm350"
MODEL
 +
DATA
 +
CODE
 +
CONFIGURATION
 +
DEPENDENCIES
 +
REGISTRY
 +
DEPLOYMENT
 +
RUNTIME
      ↓
TRUSTED AI SYSTEM
```

Protecting only the model artifact is insufficient. Enterprise model security must establish **who can modify each component, how changes are verified, how approved versions are distinguished from unauthorized ones, how unexpected behavior is detected, and how a compromised model can be rapidly isolated and replaced with a verified trusted version**.

# 09.12 — Backdoors and Model Manipulation

## Part 4

### 151. Enterprise Backdoor Security Architecture

An enterprise model-security architecture should treat backdoor prevention and detection as a **defense-in-depth problem**.

```text id="bda151"
                    MODEL SECURITY
                          │
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
     PREVENT            DETECT            RESPOND
        │                 │                 │
     Access            Integrity         Containment
     Provenance        Behavior          Rollback
     Validation        Monitoring        Recovery
     Isolation         Testing           Investigation
```

No single control should be considered sufficient.

---

### 152. Preventive Controls

Preventive controls reduce the probability that an attacker can introduce unauthorized model behavior.

Important controls include:

* Least-privilege access.
* Strong authentication.
* Separation of duties.
* Secure development pipelines.
* Dataset governance.
* Model provenance.
* Artifact signing.
* Controlled model registries.

---

### 153. Detective Controls

Detective controls identify suspicious activity or behavior after it occurs.

Examples include:

* Model integrity verification.
* Behavioral monitoring.
* File-integrity monitoring.
* Registry auditing.
* Deployment monitoring.
* Security analytics.

---

### 154. Corrective Controls

Corrective controls restore the system to a trusted state.

Examples include:

* Model rollback.
* Dataset restoration.
* Credential revocation.
* Model replacement.
* Pipeline remediation.
* Security patching.

---

### 155. Model Security Control Matrix

| Security Objective            | Example Control        |
| ----------------------------- | ---------------------- |
| Protect model integrity       | Hashes / signatures    |
| Protect model provenance      | Lineage records        |
| Prevent unauthorized changes  | RBAC / least privilege |
| Detect manipulation           | Behavioral monitoring  |
| Prevent unapproved deployment | Release gates          |
| Recover from compromise       | Trusted rollback       |
| Investigate incidents         | Immutable audit logs   |

---

### 156. Backdoor Risk Assessment

Backdoor risk should be assessed based on:

* Model criticality.
* Model exposure.
* Training architecture.
* Data sources.
* Third-party dependencies.
* Number of users.
* Automation level.
* Potential business impact.

```text id="bda157"
   ↓

High Risk
   ↓
Continuous / Frequent Validation
```

The exact frequency should be determined by the organization's risk framework.

Security requirements should be defined before the model enters production development.

Examples:

* Approved model sources.

* Integrity requirements.
* Testing requirements.
* Deployment requirements.

### 160. Secure Training Environment

Training environments should be isolated and appropriately controlled.

Controls may include:

* Dedicated identities.
* Controlled dependencies.
* Protected datasets.
* Logging.
* Resource isolation.

### 161. Training Environment Integrity

The training environment itself can influence the resulting model.

Therefore, organizations should maintain visibility into:

* Software versions.

### 162. Dependency Security

A model can inherit risk from dependencies used during:

* Training.
* Fine-tuning.
* Conversion.
* Evaluation.
* Serving.

Dependency management should therefore be part of model security.

Where appropriate, production training and serving environments should use controlled dependency versions.

### 164. Dependency Verification

### 200. Core Principle

**A trustworthy model is not merely a model whose predictions appear correct. It is a model whose complete lifecycle can be trusted and verified.**

```text id="bda200"
TRUSTED SOURCE
      ↓
TRUSTED DATA
      ↓
TRUSTED CODE
      ↓
CONTROLLED TRAINING
      ↓
VALIDATED MODEL
      ↓
VERIFIED ARTIFACT
      ↓
AUTHORIZED DEPLOYMENT
      ↓
VERIFIED RUNTIME
      ↓
CONTINUOUS MONITORING
```

The enterprise objective is therefore to ensure that **unauthorized model manipulation is prevented where possible, backdoors are difficult to introduce and difficult to conceal, suspicious behavior is detectable, production impact can be contained, trusted versions can be restored, and every significant model change remains attributable and auditable.**
