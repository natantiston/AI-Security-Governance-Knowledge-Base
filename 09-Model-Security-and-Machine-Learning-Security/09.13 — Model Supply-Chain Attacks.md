# 09.13 — Model Supply-Chain Attacks

## Part 1

### 1. Model Supply-Chain Attacks

A **model supply-chain attack** occurs when an attacker compromises a component, dependency, provider, or process involved in creating, distributing, deploying, or operating an AI/ML model.

The attacker may not need to compromise the target organization directly.

```text
id="msa101"
Third Party
    ↓
Compromised Component
    ↓
AI/ML Supply Chain
    ↓
Enterprise Model
    ↓
Production System
```

---

### 2. The ML Supply Chain

The machine-learning supply chain can include:

* Training datasets.
* Data providers.
* Labeling services.
* Pretrained models.
* Model repositories.
* Software libraries.
* Frameworks.
* Development tools.
* Container images.
* APIs.
* Cloud services.
* CI/CD systems.
* Model registries.
* Deployment infrastructure.

Each dependency can introduce security risk.

---

### 3. Traditional Software Supply Chain vs. ML Supply Chain

Traditional software supply chains primarily focus on:

```text
Source Code
   ↓
Dependencies
   ↓
Build
   ↓
Application
```

ML systems expand this chain:

```text
Data
 ↓
Features
 ↓
Training Code
 ↓
Dependencies
 ↓
Training
 ↓
Model
 ↓
Model Runtime
 ↓
Application
```

The model itself becomes a major supply-chain artifact.

---

### 4. Why Model Supply Chains Are Different

ML systems have a unique dependency on **data and learned parameters**.

A conventional application can often be rebuilt from trusted source code.

A model may additionally depend on:

* Dataset versions.
* Labels.
* Feature engineering.
* Training configuration.
* Randomization.
* Pretrained model weights.

Therefore, software integrity alone does not establish ML integrity.

---

### 5. Supply-Chain Trust Problem

An organization may trust an external model because it comes from a reputable source.

However:

> **Reputation does not replace technical verification.**

The organization should independently establish whether the artifact is authentic, intact, and appropriate for use.

---

### 6. Supply-Chain Attack Objectives

An attacker may seek to:

* Introduce malicious behavior.
* Create a backdoor.
* Steal sensitive information.
* Reduce model accuracy.
* Bypass safety controls.
* Gain persistence.
* Compromise downstream systems.
* Establish access to enterprise infrastructure.

---

### 7. Compromise of a Trusted Supplier

A common supply-chain scenario is:

```text
id="msa107"
Enterprise
    ↓
Trusted Supplier
    ↓
Supplier Compromised
    ↓
Malicious Artifact
    ↓
Enterprise Deployment
```

The enterprise may initially believe it is receiving a legitimate artifact.

---

### 8. Upstream Compromise

The attack may occur upstream from the enterprise.

Potentially affected parties include:

* Model provider.
* Dataset provider.
* Software vendor.
* Cloud provider.
* Repository.
* Build system.
* Managed ML platform.

---

### 9. Downstream Impact

A single compromised upstream component may affect many customers.

```text
id="msa109"
Compromised Supplier
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
Org A Org B Org C
```

This is one reason supply-chain attacks can have significant blast radius.

---

### 10. Model Repository Risk

Public or private model repositories may contain:

* Legitimate models.
* Modified models.
* Experimental models.
* Malicious models.
* Models with unsafe dependencies.

Organizations should therefore establish controls before importing models.

---

### 11. Model Provenance

Model provenance answers questions such as:

* Where did the model originate?
* Who created it?
* Which organization released it?
* Which version is it?
* Has it been modified?
* What process produced it?

---

### 12. Model Authenticity

Authenticity asks:

> **Is this actually the model produced or released by the claimed source?**

Integrity asks:

> **Has the model changed since it was authenticated?**

These are related but different security properties.

---

### 13. Integrity and Authenticity

```text
id="msa113"
Authenticity
     ↓
"Who produced this?"

Integrity
     ↓
"Was it changed?"
```

Both should be considered when accepting external model artifacts.

---

### 14. Cryptographic Hashes

A cryptographic hash can provide an artifact fingerprint.

```text
id="msa114"
Model Artifact
     ↓
SHA-256 Hash
     ↓
Known Fingerprint
```

A later hash comparison can detect changes to the artifact.

---

### 15. Digital Signatures

Digital signatures can provide stronger assurance about:

* Artifact integrity.
* Artifact origin.
* Authorized publication.

Conceptually:

```text
id="msa115"
Trusted Publisher
      ↓
Sign Artifact
      ↓
Enterprise
      ↓
Verify Signature
```

---

### 16. Signed Model Releases

For critical models, organizations should prefer releases that can be cryptographically verified.

The verification process should occur before the model enters a trusted environment.

---

### 17. Dependency Confusion

Supply-chain attacks can also target software dependencies.

An attacker may attempt to cause an organization to retrieve a malicious package instead of the intended trusted dependency.

This risk exists in ML environments because training and inference systems rely heavily on software packages.

---

### 18. Malicious Packages

A compromised dependency could affect:

* Training.
* Data processing.
* Model conversion.
* Evaluation.
* Model serving.

Therefore, package security is part of model security.

---

### 19. Typosquatting

Attackers may publish packages with names that resemble legitimate libraries.

```text
id="msa119"
Legitimate Package
       vs.
Similar-Looking Malicious Package
```

Developers may unintentionally install the wrong package.

---

### 20. Dependency Pinning

Organizations should control dependency versions where practical.

Pinning reduces the risk of an unexpected package update changing the training or serving environment.

---

### 21. Dependency Lock Files

Lock files can record the exact versions of dependencies used by a project.

This improves:

* Reproducibility.
* Change tracking.
* Investigation.
* Build consistency.

---

### 22. Software Bill of Materials

An **SBOM** provides an inventory of software components used by a system.

For an ML platform, the SBOM can include:

* Frameworks.
* Libraries.
* Packages.
* Runtime components.
* Operating-system dependencies.

---

### 23. Model Bill of Materials

An enterprise can extend this concept into a broader **Model Bill of Materials**.

```text
id="msa123"
Model
 ├── Dataset
 ├── Base Model
 ├── Code
 ├── Libraries
 ├── Containers
 ├── Configuration
 └── Runtime
```

This provides a more complete view of the model's supply chain.

---

### 24. Base Model Dependencies

An enterprise model may not be built from scratch.

It may depend on:

```text
id="msa124"
Base Model
     ↓
Fine-Tuning
     ↓
Enterprise Model
```

The security of the enterprise model is therefore partially dependent on the security and provenance of the base model.

---

### 25. Model Forking

Organizations may modify or fork an external model.

After modification, they should preserve lineage between:

* Original model.
* Modified version.
* Training data.
* Fine-tuning process.
* Final artifact.

---

### 26. Model Lineage

A useful lineage representation is:

```text
id="msa126"
External Model v1
       ↓
Approved Import
       ↓
Fine-Tuning
       ↓
Enterprise Model v1.1
       ↓
Security Validation
       ↓
Production
```

---

### 27. Dataset Providers

External datasets can also become supply-chain dependencies.

Risks may include:

* Incorrect data.
* Malicious records.
* Manipulated labels.
* Unauthorized changes.
* Unknown provenance.

---

### 28. Dataset Authenticity

Organizations should establish:

* Dataset owner.
* Source.
* Version.
* Collection process.
* Modification history.
* Integrity information.

---

### 29. Dataset Versioning

A dataset should ideally have identifiable versions.

```text
id="msa129"
Dataset v1
Dataset v2
Dataset v3
```

This allows organizations to determine exactly which data contributed to a model.

---

### 30. Dataset Integrity

Where appropriate, organizations can use:

* Hashes.
* Signed manifests.
* Access controls.
* Immutable storage.
* Version control.

These mechanisms help detect unauthorized changes.

---

### 31. Data Labeling Supply Chain

Labeling may be performed by:

* Internal teams.
* Contractors.
* Crowdsourcing services.
* Specialized vendors.

The labeling process can therefore become a supply-chain dependency.

---

### 32. Label Manipulation

If labels are manipulated, the resulting model may learn incorrect relationships.

```text
id="msa132"
Raw Data
   ↓
Labeling Service
   ↓
Incorrect Labels
   ↓
Training
   ↓
Model Behavior
```

---

### 33. Human Annotation Security

Organizations should consider:

* Annotator access.
* Quality controls.
* Reviewer permissions.
* Audit logs.
* Conflict management.
* Data confidentiality.

---

### 34. Training Infrastructure

The infrastructure used to train models can also become part of the supply chain.

Examples include:

* Cloud compute.
* Managed ML services.
* GPU platforms.
* Training clusters.
* Build systems.

---

### 35. Cloud Dependency Risk

A compromised or misconfigured cloud environment could potentially affect:

* Training data.
* Training processes.
* Model artifacts.
* Credentials.
* Deployment systems.

Cloud security therefore contributes directly to ML supply-chain security.

---

### 36. Container Supply Chain

Container images can contain:

* Operating-system packages.
* Libraries.
* Runtime components.
* Serving frameworks.
* Model artifacts.

A compromised image can therefore introduce malicious components into production.

---

### 37. Container Image Provenance

Organizations should verify:

* Image source.
* Image digest.
* Publisher.
* Version.
* Signature.
* Vulnerability status.

---

### 38. CI/CD Supply Chain

ML pipelines often use automated CI/CD.

```text
id="msa138"
Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Registry
 ↓
Deployment
```

A compromise at any stage may affect the final model release.

---

### 39. Build-System Compromise

If an attacker controls the build environment, they may alter the output without directly modifying the developer's source code.

This makes build integrity a critical security concern.

---

### 40. Pipeline Identity

Automated pipelines should use controlled service identities.

These identities should have only the permissions necessary to:

* Build.
* Test.
* Register.
* Deploy.

---

### 41. Secrets in ML Pipelines

Training pipelines may access sensitive credentials for:

* Data stores.
* Cloud services.
* Model registries.
* External APIs.

Secrets should not be embedded directly in source code or model artifacts.

---

### 42. Secret Management

Organizations should use centralized secret-management mechanisms where appropriate.

Security controls should include:

* Least privilege.
* Rotation.
* Access auditing.
* Revocation.

---

### 43. Model Distribution

The distribution path from model producer to enterprise should be controlled.

```text
id="msa143"
Publisher
   ↓
Distribution Channel
   ↓
Enterprise Repository
   ↓
Validation
   ↓
Production
```

---

### 44. Trusted Distribution Channels

Organizations should prefer controlled distribution mechanisms that provide:

* Authentication.
* Integrity verification.
* Versioning.
* Auditability.

---

### 45. Offline Verification

For highly sensitive models, artifacts may be verified before entering production environments.

This can provide an additional security boundary.

---

### 46. Quarantine

External models and datasets can initially be placed into a quarantine environment.

```text
id="msa146"
External Artifact
       ↓
Quarantine
       ↓
Security Validation
       ↓
Approved / Rejected
```

---

### 47. Sandboxed Analysis

Untrusted model artifacts may be analyzed in isolated environments before they are permitted into trusted infrastructure.

This is particularly important for formats or frameworks capable of loading executable components.

---

### 48. Supply-Chain Security Gate

A model-import security gate can evaluate:

* Source.
* Authenticity.
* Integrity.
* Dependencies.
* Vulnerabilities.
* Provenance.
* Behavioral characteristics.

---

### 49. Third-Party Risk Management

Organizations should incorporate AI/ML suppliers into their broader third-party risk-management program.

This may include:

* Security assessments.
* Contractual requirements.
* Assurance evidence.
* Incident notification.
* Dependency reviews.

---

### 50. Core Principle

**The security of an enterprise model depends partly on the trustworthiness of everything used to create, modify, distribute, and operate it.**

```text
id="msa150"
DATA
  ↓
SOFTWARE
  ↓
BASE MODEL
  ↓
TRAINING
  ↓
BUILD
  ↓
REGISTRY
  ↓
DEPLOYMENT
  ↓
RUNTIME
```

A mature ML security program therefore treats **models, datasets, dependencies, infrastructure, suppliers, build pipelines, and distribution channels as one interconnected supply chain that must be governed, verified, monitored, and traceable.**

# 09.13 — Model Supply-Chain Attacks

## Part 2

### 51. Supply-Chain Trust Boundaries

Every external dependency introduces a trust boundary.

```text id="sca251"
External Supplier
       ↓
Trust Boundary
       ↓
Enterprise Environment
       ↓
Production Model
```

The organization should explicitly identify where externally controlled components enter the ML environment.

---

### 52. Direct vs. Indirect Dependencies

A dependency can be **direct** or **indirect**.

```text id="sca252"
Enterprise Model
      ↓
Direct Dependency
      ↓
Indirect Dependency
      ↓
Underlying Package
```

An organization may know its direct dependencies while remaining unaware of deeper dependencies.

---

### 53. Transitive Dependencies

Software frameworks often depend on other libraries.

For example:

```text id="sca253"
ML Framework
    ↓
Library A
    ↓
Library B
    ↓
Library C
```

A vulnerability or compromise in a lower-level dependency can propagate upward.

---

### 54. Dependency Visibility

A mature supply-chain program should maintain visibility into both:

* Direct dependencies.
* Transitive dependencies.

This supports vulnerability management and incident response.

---

### 55. Dependency Inventory

The organization should maintain an inventory covering relevant:

* Libraries.
* Frameworks.
* Packages.
* Containers.
* Models.
* Datasets.
* External APIs.

---

### 56. Model Dependency Graph

A dependency graph can represent relationships between components.

```text id="sca256"
Dataset A ──┐
             ↓
Base Model ─→ Enterprise Model
             ↓
        Serving Framework
             ↓
          Application
```

This makes potential attack paths easier to understand.

---

### 57. Critical Dependency Identification

Not every dependency has equal importance.

Organizations should identify dependencies whose compromise could affect:

* Multiple models.
* Critical applications.
* Sensitive data.
* Security decisions.
* Production availability.

---

### 58. Single Points of Failure

A shared dependency may become a single point of failure.

```text id="sca258"
Shared Component
   ↓
 ┌─┼─┐
 ↓ ↓ ↓
M1 M2 M3
```

Compromise of the shared component could affect all dependent models.

---

### 59. Dependency Concentration Risk

Organizations should evaluate whether too many critical models rely on:

* One model provider.
* One repository.
* One dataset provider.
* One cloud service.
* One software framework.

High concentration can increase systemic risk.

---

### 60. Supplier Diversity

Where justified by risk, organizations may consider alternative suppliers or fallback mechanisms for critical dependencies.

The objective is resilience rather than unnecessary duplication.

---

### 61. Vendor Lock-In

Strong dependence on one supplier can complicate recovery if that supplier becomes unavailable or compromised.

Critical AI systems should therefore consider exit and recovery requirements.

---

### 62. Supplier Security Assessment

Before accepting a critical AI/ML dependency, organizations may evaluate:

* Security practices.
* Development processes.
* Artifact integrity.
* Vulnerability management.
* Incident response.
* Access controls.
* Data governance.

---

### 63. Supplier Assurance

Evidence may include:

* Independent assessments.
* Security certifications.
* Audit reports.
* Vulnerability-management processes.
* Secure-development documentation.

The level of assurance should be proportional to the dependency's risk.

---

### 64. Contractual Security Requirements

Contracts with critical suppliers can establish requirements for:

* Security controls.
* Vulnerability notification.
* Incident notification.
* Data protection.
* Model provenance.
* Artifact integrity.
* Change management.

---

### 65. Right-to-Audit Considerations

For particularly important suppliers, contractual arrangements may provide appropriate assurance or audit rights.

The objective is to maintain sufficient visibility into critical dependencies.

---

### 66. Supplier Change Notification

Organizations should understand how suppliers communicate significant changes to:

* Models.
* Datasets.
* Dependencies.
* Infrastructure.
* Security controls.

Unexpected supplier changes can affect enterprise risk.

---

### 67. Model Version Substitution

A supplier may update a model while keeping the same product or API name.

```text id="sca267"
"Model-X"
    ↓
Version 1
    ↓
Supplier Update
    ↓
Version 2
```

If the enterprise cannot identify the exact version, reproducibility and security assurance become difficult.

---

### 68. Exact Model Versioning

Critical systems should record the exact model version or artifact identity used in production.

This can include:

* Version number.
* Digest.
* Hash.
* Build identifier.
* Provider release identifier.

---

### 69. Silent Model Changes

A provider-controlled model may change without the customer directly modifying its application.

Such changes can alter:

* Accuracy.
* Behavior.
* Security properties.
* Performance.
* Output characteristics.

Organizations should understand the supplier's change-management model.

---

### 70. API Dependency

Some enterprises do not host the model themselves.

Instead:

```text id="sca270"
Enterprise Application
       ↓
External AI API
       ↓
Provider Model
```

The provider's infrastructure and model lifecycle become part of the enterprise's effective supply chain.

---

### 71. External AI Service Risk

External AI services introduce dependencies involving:

* Availability.
* Authentication.
* Data handling.
* Model behavior.
* Provider security.
* Service configuration.

These should be evaluated according to business criticality.

---

### 72. Provider Authentication

Applications consuming external AI services should use secure authentication mechanisms.

Credentials should be:

* Protected.
* Scoped.
* Rotated.
* Monitored.

---

### 73. API Key Protection

API keys should not be embedded in:

* Source code.
* Public repositories.
* Model files.
* Client-side applications.

Centralized secret management should be used where appropriate.

---

### 74. External API Integrity

Organizations should consider whether responses from external AI services can be trusted for security-sensitive decisions.

Where appropriate, independent validation or deterministic controls should be used.

---

### 75. Model Supply-Chain Attack Through Dependencies

A generalized attack chain can look like:

```text id="sca275"
Compromise Dependency
        ↓
Enterprise Imports Dependency
        ↓
Training / Serving
        ↓
Compromised Component
        ↓
Model or Application Impact
```

---

### 76. Malicious Update

A legitimate package or model can become dangerous if a trusted distribution channel is compromised.

```text id="sca276"
Trusted Package
      ↓
Supplier Compromise
      ↓
Malicious Update
      ↓
Enterprise Installation
```

---

### 77. Version Pinning vs. Updating

There is a balance between:

**Pinning versions**

* Improves reproducibility.
* Reduces unexpected changes.

and

**Updating versions**

* Addresses vulnerabilities.
* Provides security fixes.

A mature process combines controlled updates with testing.

---

### 78. Dependency Update Pipeline

A controlled update process may be:

```text id="sca278"
New Version
    ↓
Security Review
    ↓
Compatibility Testing
    ↓
Model Testing
    ↓
Approval
    ↓
Production
```

---

### 79. Vulnerability Scanning

Software dependencies should be scanned for known vulnerabilities.

However:

> **A vulnerability scan does not establish that a model or package is free from malicious behavior.**

It is one layer of assurance.

---

### 80. Malware Analysis

Where appropriate, imported artifacts may undergo malware or security analysis before entering trusted environments.

---

### 81. Behavioral Analysis

A model can also be evaluated based on its behavior.

```text id="sca281"
Imported Model
      ↓
Controlled Testing
      ↓
Behavioral Analysis
      ↓
Security Assessment
```

---

### 82. Static and Dynamic Analysis

A mature assessment may combine:

**Static analysis**

* Artifact inspection.
* Dependency inspection.
* Configuration inspection.

**Dynamic analysis**

* Controlled execution.
* Runtime observation.
* Behavioral testing.

---

### 83. Quarantine Environment

Untrusted artifacts should be analyzed in an isolated environment when appropriate.

```text id="sca283"
External Artifact
       ↓
Quarantine
       ↓
Analysis
       ↓
Approved
```

---

### 84. Network Isolation

The quarantine environment should have controlled connectivity.

This reduces the risk that an untrusted component can interact with sensitive enterprise systems during analysis.

---

### 85. Least Privilege for Analysis

Security analysis environments should not automatically provide broad permissions to imported models or packages.

---

### 86. Import Approval

Critical models should require formal approval before entering production repositories.

Approval may consider:

* Source.
* Integrity.
* Provenance.
* Dependencies.
* Testing.
* Business owner.

---

### 87. Model Intake Process

A structured model-intake process can be:

```text id="sca287"
Request
  ↓
Source Verification
  ↓
Artifact Verification
  ↓
Security Assessment
  ↓
Behavioral Testing
  ↓
Business Approval
  ↓
Registry
```

---

### 88. Model Acceptance Criteria

Acceptance criteria can include:

* Known provenance.
* Verified artifact integrity.
* Approved license.
* Acceptable dependencies.
* Security testing completed.
* Documented owner.
* Defined rollback mechanism.

---

### 89. Model Rejection Criteria

A model may be rejected or quarantined when:

* Provenance cannot be established.
* Artifact integrity cannot be verified.
* Critical vulnerabilities exist.
* Security behavior is unexplained.
* Required documentation is missing.
* Supplier assurance is insufficient.

---

### 90. Exception Management

If an organization accepts a model despite a control gap, the exception should be:

* Documented.
* Risk-assessed.
* Approved.
* Time-bounded.
* Reviewed.

---

### 91. Supply-Chain Monitoring

Supply-chain security is not a one-time assessment.

Organizations should monitor important dependencies for:

* New vulnerabilities.
* Security incidents.
* Version changes.
* Supplier changes.
* Model changes.

---

### 92. Vulnerability Intelligence

Security teams should monitor relevant sources for vulnerabilities affecting:

* ML frameworks.
* Model-serving software.
* Container images.
* Operating systems.
* Dependencies.

---

### 93. Supplier Incident Monitoring

A supplier compromise may become an enterprise security event even if the enterprise infrastructure was never directly breached.

```text id="sca293"
Supplier Incident
      ↓
Dependency Assessment
      ↓
Affected Enterprise Assets?
      ↓
Response
```

---

### 94. Emergency Dependency Response

When a critical dependency is compromised, organizations may need to:

* Stop new deployments.
* Block affected versions.
* Remove affected artifacts.
* Rotate credentials.
* Investigate dependent systems.
* Deploy trusted alternatives.

---

### 95. Dependency Blast Radius

The first question during a supply-chain incident should often be:

> **Which enterprise assets depend on the affected component?**

Dependency mapping makes this answer significantly faster.

---

### 96. Reverse Dependency Mapping

The organization should be able to trace:

```text id="sca296"
Compromised Component
        ↓
Dependent Models
        ↓
Dependent Applications
        ↓
Affected Business Processes
```

---

### 97. Model Recall

If a compromised model has already been distributed, the organization should have a process for identifying and recalling affected versions.

---

### 98. Artifact Revocation

Where supported, compromised artifacts should be marked as:

* Revoked.
* Deprecated.
* Blocked.
* Unsafe.

Deployment systems should prevent revoked artifacts from being used.

---

### 99. Supply-Chain Resilience

The ultimate objective is not simply to prevent every supply-chain attack.

It is to ensure the organization can:

```text id="sca299"
Detect
  ↓
Identify
  ↓
Contain
  ↓
Recover
  ↓
Verify
  ↓
Resume
```

---

### 100. Core Principle

**A trusted supplier does not eliminate supply-chain risk.**

Enterprise ML security should continuously establish:

```text id="sca300"
WHO
created it?
   ↓
WHAT
exactly is it?
   ↓
WHERE
did it come from?
   ↓
WHAT
does it depend on?
   ↓
HAS
it changed?
   ↓
IS
it safe to deploy?
```

The fundamental objective is to maintain **verifiable trust across every external model, dataset, software dependency, service provider, build system, and distribution channel that contributes to the enterprise AI ecosystem**.

# 09.13 — Model Supply-Chain Attacks

## Part 3

### 101. Supply-Chain Attack Lifecycle

A model supply-chain attack can occur across multiple stages rather than at a single point.

```text
Supplier
   ↓
Development
   ↓
Packaging
   ↓
Distribution
   ↓
Enterprise Import
   ↓
Integration
   ↓
Deployment
   ↓
Runtime
```

Each stage represents a potential attack surface.

---

### 102. Attack-Path Analysis

Security teams should identify how an attacker could move from an external dependency into the enterprise environment.

```text
External Component
        ↓
Trust Boundary
        ↓
ML Platform
        ↓
Model
        ↓
Application
        ↓
Business Process
```

This helps identify where preventive and detective controls should be placed.

---

### 103. Compromise Before Acquisition

A model may already be compromised before an organization acquires it.

Potential causes include:

* Malicious publisher.
* Compromised development environment.
* Manipulated training data.
* Compromised build system.
* Unauthorized modification.

The enterprise may therefore inherit risk at the point of acquisition.

---

### 104. Compromise During Distribution

The distribution channel itself may be targeted.

```text
Publisher
   ↓
Distribution Channel
   ↓
Attacker Interference
   ↓
Enterprise
```

Integrity verification helps detect unauthorized modifications.

---

### 105. Compromise After Acquisition

An artifact may initially be legitimate but later become compromised within the enterprise.

Potential targets include:

* Model repositories.
* Storage.
* CI/CD.
* Deployment systems.
* Serving infrastructure.

---

### 106. Multi-Stage Supply-Chain Attacks

A sophisticated attack may involve several compromised components.

```text
Compromised Package
       ↓
Compromised Build
       ↓
Modified Model
       ↓
Compromised Container
       ↓
Production
```

This is why supply-chain security requires controls at multiple layers.

---

### 107. Attack Surface Inventory

Organizations should identify all components that can influence a production model.

The inventory can include:

* Source code.
* Training data.
* Feature pipelines.
* Base models.
* Fine-tuning datasets.
* Libraries.
* Containers.
* Configuration.
* Registry.
* Deployment platform.

---

### 108. Critical Supply-Chain Assets

Some components deserve stronger protection because they influence many downstream systems.

Examples include:

* Central model registries.
* Shared feature stores.
* Common ML frameworks.
* Central CI/CD pipelines.
* Enterprise base models.

---

### 109. Shared Model Dependencies

An organization may reuse a single base model across multiple applications.

```text id="sc30109"
              Base Model
             /    |    \
            ↓     ↓     ↓
          App A App B App C
```

Compromise of the base model could affect multiple applications.

---

### 110. Shared Dataset Dependencies

The same principle applies to datasets.

```text id="sc30110"
           Dataset
          /   |   \
         ↓    ↓    ↓
       M1    M2    M3
```

A compromised shared dataset may influence multiple models.

---

### 111. Common Infrastructure Dependencies

Shared infrastructure can create systemic risk.

Examples include:

* Central Kubernetes clusters.
* Shared container registries.
* Common storage.
* Central model-serving platforms.

---

### 112. Dependency Criticality Scoring

Organizations can classify dependencies using factors such as:

* Number of dependent models.
* Business criticality.
* Data sensitivity.
* Exposure.
* Replacement difficulty.
* Recovery time.

---

### 113. Supply-Chain Risk Score

A simplified conceptual model is:

```text
Supply-Chain Risk
=
Likelihood of Compromise
×
Exposure
×
Business Impact
```

Organizations can adapt the calculation to their existing enterprise risk methodology.

---

### 114. Attack Feasibility

Assessment should consider whether an attacker can realistically:

* Access the dependency.
* Modify the artifact.
* Bypass verification.
* Reach production.
* Remain undetected.

---

### 115. Trust Level Classification

External components can be classified according to trust.

```text
Level 1 — Fully Verified
Level 2 — Approved Supplier
Level 3 — Limited Assurance
Level 4 — Untrusted
```

The exact classification should follow organizational policy.

---

### 116. Zero-Trust Principle for Model Imports

A useful principle is:

> **Never treat an external model as trusted solely because it comes from an external trusted source.**

Instead:

```text
External Artifact
      ↓
Verify
      ↓
Validate
      ↓
Authorize
```

---

### 117. Supplier Identity Verification

Organizations should verify the identity of the entity publishing the artifact.

This helps distinguish:

* Official publisher.
* Unofficial mirror.
* Impersonator.
* Unknown source.

---

### 118. Repository Verification

Organizations should establish which repositories are approved for enterprise use.

Unapproved repositories may be blocked or restricted.

---

### 119. Artifact Allowlisting

Production systems can maintain an allowlist of approved:

* Model hashes.
* Model versions.
* Container digests.
* Package versions.

An artifact outside the allowlist can be rejected.

---

### 120. Deny-by-Default

For critical environments:

```text
Unknown Artifact
      ↓
DENY
```

rather than:

```text
Unknown Artifact
      ↓
Allow unless blocked
```

This reduces the opportunity for unauthorized artifacts to enter production.

---

### 121. Artifact Signing Infrastructure

An organization may establish a trusted signing process.

```text
Build System
    ↓
Approved Artifact
    ↓
Signing Service
    ↓
Signed Artifact
    ↓
Registry
```

---

### 122. Signature Verification

Deployment systems can verify the artifact before execution.

```text
Signed Artifact
      ↓
Signature Verification
      ↓
Valid?
  ↙       ↘
YES        NO
 ↓          ↓
Deploy     Reject
```

---

### 123. Key Management

Signing keys must themselves be protected.

Compromise of the signing key could undermine artifact trust.

Important controls can include:

* Restricted access.
* Hardware-backed protection where appropriate.
* Key rotation.
* Audit logging.
* Revocation.

---

### 124. Key Separation

Different environments may use separate signing authorities.

For example:

```text
Development Signing
        ≠
Production Signing
```

This reduces the consequences of compromise in a lower-trust environment.

---

### 125. Promotion Rather Than Direct Deployment

A model should ideally move through controlled promotion stages.

```text
External
   ↓
Quarantine
   ↓
Validated
   ↓
Approved
   ↓
Production Registry
   ↓
Production
```

---

### 126. Production Registry Isolation

The production model registry should be more tightly controlled than development repositories.

Production artifacts should not be freely writable by development identities.

---

### 127. Separation of Duties

The person who creates or modifies a model should not necessarily be the only person who can approve its production deployment.

This reduces the risk of unilateral manipulation.

---

### 128. Four-Eyes Principle

High-risk model changes may require two authorized individuals.

```text
Developer
   +
Security / Approver
   ↓
Production Release
```

---

### 129. Privileged Access Management

Privileged model-management accounts should be tightly controlled.

Controls can include:

* MFA.
* Just-in-time access.
* Session monitoring.
* Approval workflows.
* Privilege expiration.

---

### 130. Access Review

Access to critical ML supply-chain systems should be reviewed periodically.

Inactive or unnecessary permissions should be removed.

---

### 131. Build Reproducibility

A reproducible build helps determine whether the expected inputs produce the expected artifact.

```text
Source
+
Dependencies
+
Data
+
Configuration
      ↓
Expected Artifact
```

Unexpected differences should be investigated.

---

### 132. Build Attestation

A build attestation can provide evidence about how an artifact was created.

It may record:

* Source revision.
* Build system.
* Dependencies.
* Build identity.
* Build timestamp.
* Resulting artifact.

---

### 133. Provenance Attestation

Model provenance can be represented as:

```text
Model Artifact
      ↓
Training Run
      ↓
Code Version
      ↓
Dataset Version
      ↓
Base Model
      ↓
Dependencies
```

This allows investigators to trace the origin of the artifact.

---

### 134. Provenance Gaps

A model with unknown provenance should receive greater scrutiny.

For example:

```text
Known Source
     ↓
Known Build
     ↓
Known Dataset
     ↓
Known Artifact
```

is substantially easier to trust than:

```text
Unknown Source
     ↓
Unknown Build
     ↓
Unknown Dataset
     ↓
Unknown Artifact
```

---

### 135. Provenance Tampering

Attackers may attempt to modify metadata to make a malicious artifact appear legitimate.

Therefore, provenance records themselves require integrity protection.

---

### 136. Immutable Audit Records

Important supply-chain events should be recorded in tamper-resistant or otherwise strongly protected logs.

Examples include:

* Artifact creation.
* Artifact import.
* Signature verification.
* Approval.
* Promotion.
* Deployment.
* Revocation.

---

### 137. Chain of Custody

The organization should be able to answer:

> **Who handled this model and what happened to it from acquisition through deployment?**

This is the model equivalent of maintaining chain-of-custody evidence.

---

### 138. Model Custody Record

A custody record can track:

```text
Source
 ↓
Imported By
 ↓
Validated By
 ↓
Approved By
 ↓
Promoted By
 ↓
Deployed By
```

---

### 139. Unauthorized Modification Detection

Security monitoring should detect unexpected changes to protected artifacts.

Potential indicators include:

* Hash mismatch.
* Signature failure.
* Unexpected version.
* Unauthorized registry activity.
* Unexpected deployment.

---

### 140. Deployment-Time Verification

The deployment platform should verify the model **at the time of deployment**, not only when it entered the repository.

This protects against changes occurring after initial validation.

---

### 141. Runtime Verification

Where practical, the runtime environment should also confirm that the deployed artifact matches the approved artifact.

This creates another trust checkpoint.

---

### 142. Continuous Verification Model

A mature architecture can use:

```text
IMPORT
  ↓ Verify
REGISTRY
  ↓ Verify
DEPLOYMENT
  ↓ Verify
RUNTIME
  ↓ Monitor
```

---

### 143. Supply-Chain Monitoring

Monitoring should cover both technical and organizational events.

Technical events include:

* Artifact changes.
* Dependency changes.
* Vulnerabilities.

Organizational events include:

* Supplier incidents.
* Ownership changes.
* Service changes.
* Security advisories.

---

### 144. Vulnerability-to-Model Mapping

When a dependency vulnerability is discovered, organizations should identify which models and applications depend on the affected component.

```text
Vulnerability
      ↓
Dependency
      ↓
Models
      ↓
Applications
      ↓
Business Processes
```

---

### 145. Automated Dependency Mapping

Automated inventories can accelerate this process.

The objective is to quickly determine the potential blast radius of a supply-chain vulnerability.

---

### 146. Emergency Blocking

If a dependency becomes actively compromised, the organization may need to block:

* Affected versions.
* New deployments.
* Model promotion.
* Dependency updates.

---

### 147. Artifact Revocation

Compromised artifacts should be explicitly revoked.

Revocation should propagate to systems responsible for deployment where feasible.

---

### 148. Model Kill Switch

For highly critical AI systems, organizations may consider mechanisms capable of rapidly disabling a compromised model or routing traffic away from it.

```text
Compromised Model
       ↓
Traffic Disabled
       ↓
Trusted Alternative
```

---

### 149. Business Continuity

Supply-chain security should account for the possibility that a critical model or provider becomes unavailable.

Organizations should determine:

* Whether an alternative exists.
* How quickly it can be activated.
* Whether it has been tested.
* What degraded operation looks like.

---

### 150. Core Principle

**Supply-chain security is fundamentally about maintaining verifiable trust across a chain of dependencies that the enterprise does not fully control.**

```text
SUPPLIER
   ↓
MODEL
   ↓
DATA
   ↓
CODE
   ↓
DEPENDENCIES
   ↓
BUILD
   ↓
REGISTRY
   ↓
DEPLOYMENT
   ↓
RUNTIME
```

The enterprise must therefore maintain **visibility, provenance, integrity, authorization, separation of duties, monitoring, revocation, and recovery capabilities across the entire model supply chain.**

### 151. Enterprise Model Supply-Chain Security Framework

### 152. Supply-Chain Governance

Governance establishes the organizational rules for acquiring and operating external AI/ML components.

It should define:

* Approved suppliers.
* Approved repositories.
* Model intake requirements.
* Security requirements.
* Risk classifications.
* Approval authorities.
* Exception processes.

### 153. Supply-Chain Policy

An enterprise policy may require that externally sourced models and ML components:

* Have identifiable provenance.
* Come from approved sources.
* Undergo security assessment.
* Have controlled versions.
* Meet defined integrity requirements.
* Have an accountable owner.

### 154. Model Classification

Models should be classified according to business and security impact.

For example:

```text id="mss154"

      ↓
Standard Controls

Medium Criticality
      ↓

High Criticality
      ↓
Strongest Controls
```

Controls should be proportional to risk.

### 155. Supplier Classification

Suppliers can similarly be classified based on:

* Business dependency.
* Data access.
* Model criticality.

* Recovery difficulty.

### 157. Supply-Chain Risk Register

### 158. Risk Acceptance

### 200. Core Principle

**The objective of model supply-chain security is not to eliminate every external dependency. It is to ensure that every dependency is understood, appropriately trusted, continuously controlled, and recoverable when that trust is broken.**

```text id="mss200"
UNDERSTAND
    ↓
IDENTIFY
    ↓
VERIFY
    ↓
CONTROL
    ↓
MONITOR
    ↓
DETECT
    ↓
CONTAIN
    ↓
RECOVER
```

An enterprise should ultimately be able to answer four fundamental questions for every critical model:

**Where did it come from?**

**What has happened to it?**

**Who is authorized to change it?**

**Can we safely replace it if its trust is compromised?**
