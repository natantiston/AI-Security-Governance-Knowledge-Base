# 09.13 — Model Supply-Chain Attacks

## Part 1

### 1. Model Supply-Chain Attacks

A **model supply-chain attack** occurs when an attacker compromises a component, dependency, provider, or process involved in creating, distributing, deploying, or operating an AI/ML model.

The attacker may not need to compromise the target organization directly.

```text
id="msa101"
Third Party
    ↓
Compromised Component
    ↓
AI/ML Supply Chain
    ↓
Enterprise Model
    ↓
Production System
```

---

### 2. The ML Supply Chain

The machine-learning supply chain can include:

* Training datasets.
* Data providers.
* Labeling services.
* Pretrained models.
* Model repositories.
* Software libraries.
* Frameworks.
* Development tools.
* Container images.
* APIs.
* Cloud services.
* CI/CD systems.
* Model registries.
* Deployment infrastructure.

Each dependency can introduce security risk.

---

### 3. Traditional Software Supply Chain vs. ML Supply Chain

Traditional software supply chains primarily focus on:

```text
Source Code
   ↓
Dependencies
   ↓
Build
   ↓
Application
```

ML systems expand this chain:

```text
Data
 ↓
Features
 ↓
Training Code
 ↓
Dependencies
 ↓
Training
 ↓
Model
 ↓
Model Runtime
 ↓
Application
```

The model itself becomes a major supply-chain artifact.

---

### 4. Why Model Supply Chains Are Different

ML systems have a unique dependency on **data and learned parameters**.

A conventional application can often be rebuilt from trusted source code.

A model may additionally depend on:

* Dataset versions.
* Labels.
* Feature engineering.
* Training configuration.
* Randomization.
* Pretrained model weights.

Therefore, software integrity alone does not establish ML integrity.

---

### 5. Supply-Chain Trust Problem

An organization may trust an external model because it comes from a reputable source.

However:

> **Reputation does not replace technical verification.**

The organization should independently establish whether the artifact is authentic, intact, and appropriate for use.

---

### 6. Supply-Chain Attack Objectives

An attacker may seek to:

* Introduce malicious behavior.
* Create a backdoor.
* Steal sensitive information.
* Reduce model accuracy.
* Bypass safety controls.
* Gain persistence.
* Compromise downstream systems.
* Establish access to enterprise infrastructure.

---

### 7. Compromise of a Trusted Supplier

A common supply-chain scenario is:

```text
id="msa107"
Enterprise
    ↓
Trusted Supplier
    ↓
Supplier Compromised
    ↓
Malicious Artifact
    ↓
Enterprise Deployment
```

The enterprise may initially believe it is receiving a legitimate artifact.

---

### 8. Upstream Compromise

The attack may occur upstream from the enterprise.

Potentially affected parties include:

* Model provider.
* Dataset provider.
* Software vendor.
* Cloud provider.
* Repository.
* Build system.
* Managed ML platform.

---

### 9. Downstream Impact

A single compromised upstream component may affect many customers.

```text
id="msa109"
Compromised Supplier
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
Org A Org B Org C
```

This is one reason supply-chain attacks can have significant blast radius.

---

### 10. Model Repository Risk

Public or private model repositories may contain:

* Legitimate models.
* Modified models.
* Experimental models.
* Malicious models.
* Models with unsafe dependencies.

Organizations should therefore establish controls before importing models.

---

### 11. Model Provenance

Model provenance answers questions such as:

* Where did the model originate?
* Who created it?
* Which organization released it?
* Which version is it?
* Has it been modified?
* What process produced it?

---

### 12. Model Authenticity

Authenticity asks:

> **Is this actually the model produced or released by the claimed source?**

Integrity asks:

> **Has the model changed since it was authenticated?**

These are related but different security properties.

---

### 13. Integrity and Authenticity

```text
id="msa113"
Authenticity
     ↓
"Who produced this?"

Integrity
     ↓
"Was it changed?"
```

Both should be considered when accepting external model artifacts.

---

### 14. Cryptographic Hashes

A cryptographic hash can provide an artifact fingerprint.

```text
id="msa114"
Model Artifact
     ↓
SHA-256 Hash
     ↓
Known Fingerprint
```

A later hash comparison can detect changes to the artifact.

---

### 15. Digital Signatures

Digital signatures can provide stronger assurance about:

* Artifact integrity.
* Artifact origin.
* Authorized publication.

Conceptually:

```text
id="msa115"
Trusted Publisher
      ↓
Sign Artifact
      ↓
Enterprise
      ↓
Verify Signature
```

---

### 16. Signed Model Releases

For critical models, organizations should prefer releases that can be cryptographically verified.

The verification process should occur before the model enters a trusted environment.

---

### 17. Dependency Confusion

Supply-chain attacks can also target software dependencies.

An attacker may attempt to cause an organization to retrieve a malicious package instead of the intended trusted dependency.

This risk exists in ML environments because training and inference systems rely heavily on software packages.

---

### 18. Malicious Packages

A compromised dependency could affect:

* Training.
* Data processing.
* Model conversion.
* Evaluation.
* Model serving.

Therefore, package security is part of model security.

---

### 19. Typosquatting

Attackers may publish packages with names that resemble legitimate libraries.

```text
id="msa119"
Legitimate Package
       vs.
Similar-Looking Malicious Package
```

Developers may unintentionally install the wrong package.

---

### 20. Dependency Pinning

Organizations should control dependency versions where practical.

Pinning reduces the risk of an unexpected package update changing the training or serving environment.

---

### 21. Dependency Lock Files

Lock files can record the exact versions of dependencies used by a project.

This improves:

* Reproducibility.
* Change tracking.
* Investigation.
* Build consistency.

---

### 22. Software Bill of Materials

An **SBOM** provides an inventory of software components used by a system.

For an ML platform, the SBOM can include:

* Frameworks.
* Libraries.
* Packages.
* Runtime components.
* Operating-system dependencies.

---

### 23. Model Bill of Materials

An enterprise can extend this concept into a broader **Model Bill of Materials**.

```text
id="msa123"
Model
 ├── Dataset
 ├── Base Model
 ├── Code
 ├── Libraries
 ├── Containers
 ├── Configuration
 └── Runtime
```

This provides a more complete view of the model's supply chain.

---

### 24. Base Model Dependencies

An enterprise model may not be built from scratch.

It may depend on:

```text
id="msa124"
Base Model
     ↓
Fine-Tuning
     ↓
Enterprise Model
```

The security of the enterprise model is therefore partially dependent on the security and provenance of the base model.

---

### 25. Model Forking

Organizations may modify or fork an external model.

After modification, they should preserve lineage between:

* Original model.
* Modified version.
* Training data.
* Fine-tuning process.
* Final artifact.

---

### 26. Model Lineage

A useful lineage representation is:

```text
id="msa126"
External Model v1
       ↓
Approved Import
       ↓
Fine-Tuning
       ↓
Enterprise Model v1.1
       ↓
Security Validation
       ↓
Production
```

---

### 27. Dataset Providers

External datasets can also become supply-chain dependencies.

Risks may include:

* Incorrect data.
* Malicious records.
* Manipulated labels.
* Unauthorized changes.
* Unknown provenance.

---

### 28. Dataset Authenticity

Organizations should establish:

* Dataset owner.
* Source.
* Version.
* Collection process.
* Modification history.
* Integrity information.

---

### 29. Dataset Versioning

A dataset should ideally have identifiable versions.

```text
id="msa129"
Dataset v1
Dataset v2
Dataset v3
```

This allows organizations to determine exactly which data contributed to a model.

---

### 30. Dataset Integrity

Where appropriate, organizations can use:

* Hashes.
* Signed manifests.
* Access controls.
* Immutable storage.
* Version control.

These mechanisms help detect unauthorized changes.

---

### 31. Data Labeling Supply Chain

Labeling may be performed by:

* Internal teams.
* Contractors.
* Crowdsourcing services.
* Specialized vendors.

The labeling process can therefore become a supply-chain dependency.

---

### 32. Label Manipulation

If labels are manipulated, the resulting model may learn incorrect relationships.

```text
id="msa132"
Raw Data
   ↓
Labeling Service
   ↓
Incorrect Labels
   ↓
Training
   ↓
Model Behavior
```

---

### 33. Human Annotation Security

Organizations should consider:

* Annotator access.
* Quality controls.
* Reviewer permissions.
* Audit logs.
* Conflict management.
* Data confidentiality.

---

### 34. Training Infrastructure

The infrastructure used to train models can also become part of the supply chain.

Examples include:

* Cloud compute.
* Managed ML services.
* GPU platforms.
* Training clusters.
* Build systems.

---

### 35. Cloud Dependency Risk

A compromised or misconfigured cloud environment could potentially affect:

* Training data.
* Training processes.
* Model artifacts.
* Credentials.
* Deployment systems.

Cloud security therefore contributes directly to ML supply-chain security.

---

### 36. Container Supply Chain

Container images can contain:

* Operating-system packages.
* Libraries.
* Runtime components.
* Serving frameworks.
* Model artifacts.

A compromised image can therefore introduce malicious components into production.

---

### 37. Container Image Provenance

Organizations should verify:

* Image source.
* Image digest.
* Publisher.
* Version.
* Signature.
* Vulnerability status.

---

### 38. CI/CD Supply Chain

ML pipelines often use automated CI/CD.

```text
id="msa138"
Code
 ↓
Build
 ↓
Test
 ↓
Package
 ↓
Registry
 ↓
Deployment
```

A compromise at any stage may affect the final model release.

---

### 39. Build-System Compromise

If an attacker controls the build environment, they may alter the output without directly modifying the developer's source code.

This makes build integrity a critical security concern.

---

### 40. Pipeline Identity

Automated pipelines should use controlled service identities.

These identities should have only the permissions necessary to:

* Build.
* Test.
* Register.
* Deploy.

---

### 41. Secrets in ML Pipelines

Training pipelines may access sensitive credentials for:

* Data stores.
* Cloud services.
* Model registries.
* External APIs.

Secrets should not be embedded directly in source code or model artifacts.

---

### 42. Secret Management

Organizations should use centralized secret-management mechanisms where appropriate.

Security controls should include:

* Least privilege.
* Rotation.
* Access auditing.
* Revocation.

---

### 43. Model Distribution

The distribution path from model producer to enterprise should be controlled.

```text
id="msa143"
Publisher
   ↓
Distribution Channel
   ↓
Enterprise Repository
   ↓
Validation
   ↓
Production
```

---

### 44. Trusted Distribution Channels

Organizations should prefer controlled distribution mechanisms that provide:

* Authentication.
* Integrity verification.
* Versioning.
* Auditability.

---

### 45. Offline Verification

For highly sensitive models, artifacts may be verified before entering production environments.

This can provide an additional security boundary.

---

### 46. Quarantine

External models and datasets can initially be placed into a quarantine environment.

```text
id="msa146"
External Artifact
       ↓
Quarantine
       ↓
Security Validation
       ↓
Approved / Rejected
```

---

### 47. Sandboxed Analysis

Untrusted model artifacts may be analyzed in isolated environments before they are permitted into trusted infrastructure.

This is particularly important for formats or frameworks capable of loading executable components.

---

### 48. Supply-Chain Security Gate

A model-import security gate can evaluate:

* Source.
* Authenticity.
* Integrity.
* Dependencies.
* Vulnerabilities.
* Provenance.
* Behavioral characteristics.

---

### 49. Third-Party Risk Management

Organizations should incorporate AI/ML suppliers into their broader third-party risk-management program.

This may include:

* Security assessments.
* Contractual requirements.
* Assurance evidence.
* Incident notification.
* Dependency reviews.

---

### 50. Core Principle

**The security of an enterprise model depends partly on the trustworthiness of everything used to create, modify, distribute, and operate it.**

```text
id="msa150"
DATA
  ↓
SOFTWARE
  ↓
BASE MODEL
  ↓
TRAINING
  ↓
BUILD
  ↓
REGISTRY
  ↓
DEPLOYMENT
  ↓
RUNTIME
```

A mature ML security program therefore treats **models, datasets, dependencies, infrastructure, suppliers, build pipelines, and distribution channels as one interconnected supply chain that must be governed, verified, monitored, and traceable.**
