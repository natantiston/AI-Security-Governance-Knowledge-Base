# 09.11 — Model and Training Data Poisoning

## Part 1

### 1. Model and Training Data Poisoning

**Model and training data poisoning** refers to attacks in which an adversary intentionally introduces malicious, misleading, or manipulated information into the machine-learning lifecycle to influence model behavior.

The core distinction is that the attacker is attempting to affect the **learning or model-building process**, rather than merely manipulating an input at inference time.

```text id="mtp001"
Attacker
   ↓
Data / Training Process
   ↓
Manipulated Learning
   ↓
Compromised Model
   ↓
Production
   ↓
Undesired Predictions
```

---

### 2. Why Poisoning Is a Model-Security Threat

Traditional application security often focuses on protecting executable code and infrastructure.

ML systems introduce another critical asset:

> **The integrity of the information from which the model learns.**

If that information is maliciously manipulated, the resulting model may become unreliable even though the training process completes successfully.

---

### 3. Poisoning vs. Adversarial Examples

The two attacks occur primarily at different stages.

| Characteristic     | Poisoning                  | Adversarial Example  |
| ------------------ | -------------------------- | -------------------- |
| Primary stage      | Training                   | Inference            |
| Target             | Training process/data      | Input                |
| Model modification | Indirectly                 | Usually no           |
| Persistence        | Potentially persistent     | Usually per-input    |
| Main objective     | Influence learned behavior | Influence prediction |

```text id="mtp003"
Poisoning:
Data → Training → Model

Adversarial Example:
Input → Model → Prediction
```

---

### 4. Poisoning Attack Lifecycle

A generalized poisoning attack can be represented as:

```text id="mtp004"
Reconnaissance
      ↓
Identify Data Source
      ↓
Gain / Influence Data Access
      ↓
Inject or Manipulate Data
      ↓
Data Enters Training Pipeline
      ↓
Model Training
      ↓
Model Behavior Changes
      ↓
Deployment
```

The attacker may attempt to remain undetected throughout the process.

---

### 5. Poisoning Attack Surface

Potential attack surfaces include:

* Data collection.
* Data ingestion.
* Data labeling.
* Data storage.
* Data preprocessing.
* Feature engineering.
* Training datasets.
* Fine-tuning datasets.
* Training code.
* Model-building pipelines.

---

### 6. Data Collection

Data collection is the first potential poisoning boundary.

Examples include:

* Web scraping.
* User submissions.
* Customer-generated content.
* Sensors.
* Logs.
* External feeds.
* Third-party datasets.

Any source that can be influenced by an attacker deserves security assessment.

---

### 7. User-Generated Data

User-generated content can create particular challenges.

For example:

```text id="mtp007"
Users
 ↓
Content
 ↓
Data Collection
 ↓
Training Dataset
 ↓
Model
```

If collected data is automatically reused for future training, attackers may attempt to influence the model through ordinary application interactions.

---

### 8. Feedback Loops

Automated feedback loops can increase poisoning risk.

```text id="mtp008"
User Activity
     ↓
Production System
     ↓
Data Collection
     ↓
Future Training
     ↓
Updated Model
     ↓
Production
```

The attacker may intentionally manipulate today's system to influence tomorrow's model.

---

### 9. Continuous Learning Risk

Systems that continuously learn from production data require additional controls.

A compromised input can potentially become part of future training material.

This creates a security concern:

> **Production input can become future model knowledge.**

---

### 10. Data Ingestion

The ingestion layer determines how external data enters the controlled ML environment.

Security controls should verify:

* Source identity.
* Data integrity.
* Schema.
* Expected volume.
* Timestamp.
* Provenance.
* Authorization.

---

### 11. Data Integrity

Training data should be protected against unauthorized modification.

Potential controls include:

* Cryptographic hashes.
* Digital signatures.
* Access controls.
* Immutable storage.
* Versioning.
* Audit logs.

---

### 12. Dataset Integrity

Dataset integrity means that the organization can establish confidence that the dataset used for training has not been unexpectedly altered.

```text id="mtp012"
Approved Dataset
      ↓
Integrity Verification
      ↓
Training
```

---

### 13. Data Provenance

**Data provenance** records where data originated and how it was processed.

Useful provenance information includes:

* Source.
* Collection time.
* Owner.
* Processing steps.
* Transformations.
* Labels.
* Dataset version.

---

### 14. Provenance Chain

A useful provenance chain is:

```text id="mtp014"
Original Source
      ↓
Collection
      ↓
Transformation
      ↓
Validation
      ↓
Dataset
      ↓
Training Run
      ↓
Model
```

This allows investigators to trace suspicious model behavior back toward its source.

---

### 15. Data Lineage

Data lineage focuses on how data moves and changes through the environment.

It can answer:

> Where did this training record come from?

and:

> Which models were trained using it?

---

### 16. Dataset Versioning

Training datasets should be versioned where practical.

```text id="mtp016"
Dataset v1
   ↓
Model v1

Dataset v2
   ↓
Model v2

Dataset v3
   ↓
Model v3
```

Unexpected changes between versions can then be investigated.

---

### 17. Dataset Change Detection

Organizations can compare datasets to identify:

* Unexpected records.
* Missing records.
* Label changes.
* Distribution shifts.
* Unusual source contributions.

---

### 18. Poisoning Indicators

Potential indicators include:

* Unusual data patterns.
* Unexpected source activity.
* Large numbers of similar records.
* Suspicious labels.
* Abnormal class distributions.
* Sudden changes in feature distributions.

No individual indicator proves poisoning.

---

### 19. Poisoning and Data Quality

Poisoning can sometimes appear initially as a data-quality problem.

```text id="mtp019"
Unexpected Data
      ↓
Data Quality Investigation
      ↓
Possible Causes
 ┌───────────────┐
 │ Error         │
 │ Drift         │
 │ Pipeline Bug  │
 │ Poisoning     │
 └───────────────┘
```

Security teams should therefore collaborate closely with data and ML engineering teams.

---

### 20. Label Poisoning

**Label poisoning** occurs when an attacker causes incorrect labels to enter the training data.

For example:

```text id="mtp020"
Malicious Sample
      ↓
Incorrect Label
      ↓
Training
      ↓
Incorrect Learned Association
```

The attacker attempts to influence what the model learns about the relationship between inputs and outcomes.

---

### 21. Labeling Systems

Labeling systems can themselves become attack surfaces.

Potential weaknesses include:

* Excessive permissions.
* Weak authentication.
* Automated labeling.
* Unverified contributors.
* Poor review processes.

---

### 22. Human Labeling

Human annotation does not automatically eliminate poisoning risk.

Attackers may attempt to:

* Influence annotators.
* Submit large numbers of malicious samples.
* Exploit weak reviewer controls.
* Manipulate labeling workflows.

---

### 23. Label Quality Controls

Organizations can improve label assurance through:

* Multiple reviewers.
* Sampling.
* Quality scoring.
* Disagreement analysis.
* Trusted annotators.
* Review thresholds.

---

### 24. Label Disagreement

Unexpected disagreement between annotators can be a useful investigation signal.

```text id="mtp024"
Sample
 ↓
Annotator A → Malicious
Annotator B → Benign
Annotator C → Malicious
```

The disagreement itself does not prove an attack but may justify review.

---

### 25. Data Injection

Data injection occurs when an attacker succeeds in introducing additional records into a training dataset.

The attacker's goal may be to:

* Alter model boundaries.
* Change class distributions.
* Create false correlations.
* Reduce model performance.
* Establish a backdoor.

---

### 26. Data Modification

Instead of adding records, an attacker may modify existing records.

Potentially manipulated fields include:

* Features.
* Labels.
* Metadata.
* Timestamps.
* Source identifiers.

---

### 27. Data Deletion

Poisoning is not limited to adding malicious information.

An attacker may attempt to remove useful training data.

```text id="mtp027"
Expected Dataset
      ↓
Selective Data Removal
      ↓
Altered Dataset
      ↓
Model
```

Removing specific classes or examples can influence what the model learns.

---

### 28. Availability-Oriented Poisoning

Some poisoning attacks attempt to reduce overall model performance rather than produce one specific prediction.

The objective may be:

> Make the model broadly less accurate or reliable.

---

### 29. Targeted Poisoning

Targeted poisoning focuses on influencing specific model behavior.

For example, an attacker may attempt to cause a particular category of input to receive an undesirable classification while leaving general model performance relatively intact.

---

### 30. Targeted vs. Availability Poisoning

| Type                   | Objective                   |
| ---------------------- | --------------------------- |
| Targeted poisoning     | Specific model behavior     |
| Availability poisoning | Broad degradation           |
| Backdoor poisoning     | Hidden conditional behavior |

---

### 31. Backdoor Poisoning

A poisoning attack may attempt to create a hidden backdoor.

The resulting model behaves normally under ordinary inputs but produces an attacker-desired output when a trigger is present.

```text id="mtp031"
Normal Input
     ↓
Normal Behavior

Trigger + Input
     ↓
Attacker-Desired Behavior
```

---

### 32. Backdoor Persistence

Unlike a temporary adversarial example, a successful backdoor can persist in the model after training.

This makes backdoor poisoning particularly important for model integrity.

---

### 33. Poisoning Through Fine-Tuning

Fine-tuning creates another potential poisoning surface.

```text id="mtp033"
Base Model
    ↓
Fine-Tuning Dataset
    ↓
Fine-Tuning
    ↓
Modified Model
```

If the fine-tuning dataset is compromised, the resulting model may inherit undesirable behavior.

---

### 34. Transfer Learning

Organizations frequently build models by adapting existing models.

The security assessment should therefore cover:

* Base model provenance.
* Fine-tuning data.
* Training process.
* Resulting artifact.

---

### 35. Retrieval and External Data

AI systems that dynamically retrieve external information can introduce additional trust dependencies.

```text id="mtp035"
External Source
      ↓
Retrieval
      ↓
Context
      ↓
Model
```

If retrieved information becomes part of a future learning process, the poisoning risk can become more significant.

---

### 36. Automated Data Collection

Automation can increase the scale of poisoning.

A malicious actor may attempt to generate large volumes of data that are automatically collected.

This is particularly relevant to systems that ingest data without strong source validation.

---

### 37. Data Volume Manipulation

An attacker may attempt to influence the relative importance of malicious records by generating unusually large quantities of data.

The resulting distribution may affect training.

---

### 38. Class Distribution Manipulation

An attacker may attempt to alter the balance between classes.

```text id="mtp038"
Normal:
Class A = 50%
Class B = 50%

Manipulated:
Class A = 80%
Class B = 20%
```

Such changes can influence model behavior.

---

### 39. Feature Distribution Manipulation

Attackers may also attempt to alter the statistical distribution of important features.

Potential indicators include:

* Sudden shifts.
* Unexpected clusters.
* New correlations.
* Unusual ranges.

---

### 40. Temporal Poisoning

If training data is collected continuously, attackers may manipulate data during a specific period.

```text id="mtp040"
Normal Data
     ↓
Poisoning Period
     ↓
Normal Data
```

The malicious period may be difficult to identify without historical monitoring.

---

### 41. Data Window Manipulation

Organizations should understand which time windows are used for training.

Attackers who understand the training schedule may attempt to influence data immediately before a retraining event.

---

### 42. Retraining Schedule Exposure

Information about:

* Training frequency.
* Dataset collection periods.
* Model deployment schedules.

can potentially help an attacker time poisoning activity.

Operational information should therefore be appropriately protected.

---

### 43. Training Pipeline Security

The training pipeline should be treated as critical infrastructure.

```text id="mtp043"
Data
 ↓
Preprocessing
 ↓
Training
 ↓
Validation
 ↓
Model Registry
 ↓
Deployment
```

Compromise of any stage can potentially affect the resulting model.

---

### 44. Pipeline Access Control

Only authorized identities should be able to:

* Modify datasets.
* Modify training code.
* Start production training.
* Approve models.
* Promote artifacts.

---

### 45. Separation of Duties

Critical ML workflows should avoid concentrating all permissions in one identity.

For example:

```text id="mtp045"
Data Engineer
      ↓
Prepares Dataset

ML Engineer
      ↓
Trains Model

Security / Risk
      ↓
Validates

Release Authority
      ↓
Approves Deployment
```

---

### 46. Training Code Integrity

Poisoning does not necessarily require manipulating data.

An attacker may instead manipulate training code.

Potential consequences include:

* Selective data processing.
* Malicious labeling.
* Feature manipulation.
* Hidden model behavior.
* Altered optimization.

---

### 47. Configuration Integrity

Training configuration should also be protected.

Relevant configuration can include:

* Dataset references.
* Hyperparameters.
* Feature definitions.
* Model architecture.
* Training schedules.

---

### 48. Reproducible Training

Where practical, organizations should maintain sufficient information to reproduce a model-training run.

This may include:

* Dataset version.
* Code version.
* Dependency versions.
* Configuration.
* Model architecture.
* Training parameters.

---

### 49. Training Run Metadata

Each training run should have a traceable identity.

```text id="mtp049"
Training Run ID
      ↓
Dataset Version
      ↓
Code Version
      ↓
Configuration
      ↓
Generated Model
```

This creates accountability across the ML lifecycle.

---

### 50. Core Principle

Training-data poisoning demonstrates that **model security begins before the model exists**.

The organization must protect not only the final model artifact but also the entire chain through which the model learns:

```text id="mtp050"
DATA SOURCE
    ↓
DATA COLLECTION
    ↓
DATA INGESTION
    ↓
DATA VALIDATION
    ↓
DATASET
    ↓
TRAINING PIPELINE
    ↓
MODEL
    ↓
VALIDATION
    ↓
DEPLOYMENT
```

If an attacker can silently manipulate a trusted input to this chain, the resulting model may become compromised while still appearing to be a legitimate, successfully trained model.

# 09.11 — Model and Training Data Poisoning

## Part 2

### 51. Poisoning Through Data Supply Chains

Training data rarely originates from a single internal source.

Enterprise ML systems may consume:

* Public datasets.
* Commercial datasets.
* Open-source repositories.
* Web-crawled content.
* Partner-provided data.
* Customer-generated data.
* Internal databases.
* Telemetry.
* Human annotations.

Every external dependency introduces a potential poisoning path.

---

### 52. Data Supply-Chain Trust

A useful security model is:

```text
External Source
      ↓
Source Verification
      ↓
Data Ingestion
      ↓
Integrity Validation
      ↓
Approved Dataset
      ↓
Training
```

The organization should establish why each source is trusted before allowing it to influence a production model.

---

### 53. Third-Party Dataset Risk

Third-party datasets may be:

* Incorrect.
* Outdated.
* Incomplete.
* Manipulated.
* Poorly documented.
* Inconsistently labeled.

Security review should therefore consider both **malicious manipulation** and **unintentional integrity problems**.

---

### 54. Dataset Provenance Records

For important datasets, maintain records such as:

| Attribute         | Example           |
| ----------------- | ----------------- |
| Source            | External provider |
| Owner             | Data team         |
| Collection date   | Recorded          |
| Dataset version   | v4.2              |
| Integrity value   | Hash              |
| License           | Documented        |
| Validation status | Approved          |

This establishes an auditable chain of trust.

---

### 55. Source Reputation

Source reputation can be a useful input to risk assessment.

However, reputation should not replace technical validation.

A previously trusted source can still become compromised.

---

### 56. Source Authentication

Where supported, data ingestion should authenticate the source.

Possible mechanisms include:

* Mutual TLS.
* API authentication.
* Signed artifacts.
* Cryptographic credentials.
* Trusted service identities.

---

### 57. Data Integrity Verification

A dataset can be verified using a cryptographic hash.

```text
Approved Dataset
      ↓
SHA-256 / Integrity Value
      ↓
Stored Reference

New Dataset
      ↓
Recalculate
      ↓
Compare
```

A mismatch indicates that the artifact has changed.

---

### 58. Hashing Limitations

Hashing establishes **integrity relative to a known reference**.

It does not establish:

* Whether the original dataset was trustworthy.
* Whether the data was malicious before hashing.
* Whether labels are correct.
* Whether the source itself was compromised.

---

### 59. Digital Signatures

Digital signatures can provide stronger provenance assurance by allowing an organization to verify that a dataset or artifact originated from an authorized signer and was not modified afterward.

```text
Authorized Source
      ↓
Sign Dataset
      ↓
Transfer
      ↓
Verify Signature
```

---

### 60. Immutable Training Data

For high-value training datasets, immutable or append-only storage can reduce unauthorized modification risk.

This makes silent changes more difficult.

---

### 61. Data Access Control

Training data should follow least privilege.

Not every ML engineer, analyst, application, or service should have write access to production training datasets.

---

### 62. Read vs. Write Permissions

A useful separation is:

```text
Data Consumers
      ↓
READ

Data Maintainers
      ↓
WRITE

Dataset Approvers
      ↓
RELEASE
```

Separating these capabilities reduces opportunities for unauthorized manipulation.

---

### 63. Privileged Dataset Operations

Sensitive operations should generate audit events.

Examples include:

* Dataset creation.
* Dataset modification.
* Record deletion.
* Label changes.
* Dataset promotion.
* Training-data replacement.

---

### 64. Dataset Audit Trails

An audit trail should help answer:

> Who changed the training data, what changed, when did it change, and why?

This is essential during poisoning investigations.

---

### 65. Unexpected Dataset Changes

A significant increase or decrease in records may indicate:

* Legitimate business activity.
* Collection changes.
* Pipeline failure.
* Data corruption.
* Attack activity.

The change should therefore be investigated rather than automatically classified.

---

### 66. Statistical Monitoring

Organizations can monitor statistical characteristics of training datasets.

Potential measurements include:

* Feature distributions.
* Class frequencies.
* Missing-value rates.
* Unique-value counts.
* Source proportions.
* Label distributions.

---

### 67. Distribution Baselines

Historical datasets can establish expected ranges.

```text
Historical Baseline
        ↓
Current Dataset
        ↓
Compare
        ↓
Unexpected Deviation
```

Large deviations should trigger investigation.

---

### 68. Data Quality Rules

Automated quality controls can identify suspicious records.

Examples:

* Invalid values.
* Impossible combinations.
* Missing required fields.
* Duplicate records.
* Unexpected formats.
* Out-of-range values.

---

### 69. Duplicate Data

Attackers may attempt to submit repeated records to increase the influence of particular examples.

Therefore, duplicate detection can be relevant to poisoning defense.

---

### 70. Near-Duplicate Data

Exact duplicate detection may not be sufficient.

Near-duplicates can also alter dataset composition.

Organizations may therefore use similarity analysis where appropriate.

---

### 71. Outlier Detection

Outlier detection can identify unusual records.

However:

> **An outlier is not necessarily poisoned data.**

Legitimate rare events can be extremely valuable for training.

---

### 72. Security vs. Data Diversity

Aggressive removal of unusual data can reduce model quality.

Security controls should therefore avoid automatically deleting rare records solely because they appear unusual.

---

### 73. Quarantine Workflow

Suspicious records can be isolated for review.

```text
Incoming Data
     ↓
Validation
     ↓
Suspicious?
   ↙     ↘
 Yes      No
 ↓         ↓
Quarantine  Dataset
 ↓
Review
```

This is often safer than immediate deletion.

---

### 74. Trusted Data Zones

Organizations can establish different trust levels.

```text
Raw Data
   ↓
Untrusted Zone
   ↓
Validated Data
   ↓
Trusted Zone
   ↓
Training Dataset
```

Only approved data should enter high-trust training environments.

---

### 75. Data Promotion

Moving data between trust levels should require controlled processes.

For example:

```text
Raw
 ↓
Validated
 ↓
Approved
 ↓
Production Training
```

Each transition should be traceable.

---

### 76. Training Data Approval

High-impact models may require formal dataset approval before training.

Approval can confirm:

* Source.
* Integrity.
* Quality.
* Provenance.
* Intended use.
* Security review.

---

### 77. Dataset Attestation

An organization can maintain an attestation describing the dataset's security and governance status.

Conceptually:

```text
Dataset
   ↓
Security / Quality Checks
   ↓
Attestation
   ↓
Training Authorization
```

---

### 78. Training Authorization

A production model should not necessarily be trainable from arbitrary datasets.

The training system can enforce:

```text
Approved Dataset?
       ↓
    Yes → Train
       ↓
     No → Reject
```

---

### 79. Policy-as-Code

Training controls can be automated through policy enforcement.

Example policies:

```text
IF dataset_source NOT trusted
THEN reject_training

IF dataset_integrity != verified
THEN reject_training

IF dataset_version NOT approved
THEN reject_training
```

This reduces dependence on manual enforcement.

---

### 80. Training Pipeline Isolation

Training workloads should be isolated from unnecessary production access.

This limits the consequences if the training environment is compromised.

---

### 81. Network Segmentation

A secure architecture may separate:

```text
Data Zone
    │
    ↓
Training Zone
    │
    ↓
Model Registry
    │
    ↓
Production Zone
```

Each boundary can enforce appropriate controls.

---

### 82. Training Environment Credentials

Training workloads often require access to:

* Datasets.
* Object storage.
* Registries.
* Compute infrastructure.
* Secrets.

These credentials should be scoped to the minimum necessary permissions.

---

### 83. Credential Compromise

If an attacker obtains training-pipeline credentials, they may be able to manipulate:

* Training data.
* Training configurations.
* Model artifacts.
* Deployment processes.

Therefore, ML security must include conventional identity security.

---

### 84. Secrets Management

Training pipelines should not embed credentials directly in:

* Source code.
* Configuration files.
* Notebooks.
* Dataset files.

Centralized secrets management and short-lived credentials can reduce exposure.

---

### 85. Notebook Security

Interactive notebooks can become a poisoning pathway.

A malicious or compromised notebook may:

* Modify data.
* Change preprocessing.
* Alter training parameters.
* Export sensitive information.
* Produce a compromised model.

Notebook execution should therefore be controlled in production ML environments.

---

### 86. Training Code Review

Changes to training code should undergo appropriate review.

Security-sensitive changes include:

* Data-source modifications.
* Label-processing changes.
* Feature transformations.
* Training objective changes.
* Dataset filters.

---

### 87. Dependency Security

Training environments depend on:

* Python packages.
* ML frameworks.
* Data-processing libraries.
* System packages.

A compromised dependency can influence the training process even when the dataset itself is clean.

---

### 88. Dependency Pinning

Training environments should use controlled dependency versions where practical.

```text
Training Run
   ↓
Dependency Manifest
   ↓
Approved Versions
```

This improves reproducibility and reduces unexpected changes.

---

### 89. Software Supply Chain

Poisoning risk therefore extends beyond data.

The broader training supply chain includes:

```text
Data
+
Code
+
Dependencies
+
Configuration
+
Compute Environment
+
Model Artifacts
```

Any compromised component can affect the resulting model.

---

### 90. Training Configuration Integrity

Training parameters can influence model behavior substantially.

Examples include:

* Learning rate.
* Number of epochs.
* Batch size.
* Optimization method.
* Dataset selection.
* Sampling strategy.

Unauthorized changes should be detectable.

---

### 91. Sampling Manipulation

Training pipelines often sample data rather than using the entire dataset.

An attacker who influences sampling may alter which records the model sees.

This creates another potential poisoning surface.

---

### 92. Data Filtering

Filters determine which records enter training.

A malicious modification to filtering logic could selectively:

* Include malicious samples.
* Exclude legitimate samples.
* Remove specific classes.
* Change training distribution.

---

### 93. Feature Engineering

Feature-engineering pipelines can also be manipulated.

```text
Raw Data
   ↓
Feature Engineering
   ↓
Training Features
   ↓
Model
```

A malicious feature transformation may produce unintended model behavior without changing the raw dataset.

---

### 94. Feature Pipeline Integrity

Feature definitions should therefore be:

* Version controlled.
* Reviewed.
* Tested.
* Access controlled.
* Traceable to model versions.

---

### 95. Data Validation Before Training

Validation should occur before the training process consumes the dataset.

Possible checks include:

```text
Schema
 ↓
Integrity
 ↓
Provenance
 ↓
Quality
 ↓
Distribution
 ↓
Security Review
```

---

### 96. Validation Limitations

No validation mechanism can guarantee that a dataset is completely free from malicious content.

Attackers may deliberately create poisoned data that appears statistically normal.

Therefore, validation must be combined with other controls.

---

### 97. Poisoning That Mimics Legitimate Data

Sophisticated poisoning attempts may avoid obvious anomalies.

```text
Legitimate Data
      +
Carefully Designed Malicious Data
      ↓
Apparently Normal Dataset
      ↓
Subtle Model Manipulation
```

This makes provenance and behavioral validation particularly important.

---

### 98. Small-Scale Poisoning

An attacker may not need to modify a large percentage of the dataset.

Depending on the attack objective and model, a relatively small amount of strategically positioned malicious data may influence behavior.

Therefore:

> Dataset size alone is not a reliable indicator of poisoning risk.

---

### 99. Poisoning Detection After Training

Organizations should also assess the resulting model.

Potential indicators include:

* Unexpected prediction behavior.
* Abnormal performance on specific subsets.
* Unusual sensitivity to certain inputs.
* Unexpected associations.
* Backdoor-like behavior.

---

### 100. Core Principle

Training-data poisoning defense requires **end-to-end integrity controls**.

```text
SOURCE TRUST
     ↓
PROVENANCE
     ↓
INTEGRITY
     ↓
DATA QUALITY
     ↓
ACCESS CONTROL
     ↓
PIPELINE SECURITY
     ↓
TRAINING VALIDATION
     ↓
MODEL VALIDATION
     ↓
CONTROLLED DEPLOYMENT
```

The key enterprise principle is:

> **Never allow the model-training process to implicitly trust data merely because the data successfully entered the pipeline.**

Trust should be established through provenance, integrity verification, controlled access, validation, traceability, and independent model-security testing.

# 09.11 — Model and Training Data Poisoning

## Part 3

### 101. Poisoning Attack Objectives

Poisoning attacks can pursue different objectives depending on the attacker's goals.

Common objectives include:

* Reducing overall model accuracy.
* Causing targeted misclassification.
* Creating hidden backdoors.
* Manipulating specific classes.
* Increasing false positives.
* Increasing false negatives.
* Undermining trust in the model.

The objective determines which poisoning strategy and detection mechanisms are most relevant.

---

### 102. Integrity vs. Availability vs. Security Impact

Poisoning can affect different security properties.

| Property        | Potential Impact                           |
| --------------- | ------------------------------------------ |
| Integrity       | Model learns incorrect behavior            |
| Availability    | Model becomes unreliable or unusable       |
| Confidentiality | Poisoning may support information exposure |
| Accountability  | Training provenance becomes questionable   |

The primary concern is generally **model integrity**.

---

### 103. Availability Poisoning

An availability-oriented attack attempts to degrade the usefulness of the model broadly.

```text id="mtp103"
Poisoned Training Data
        ↓
Model Degradation
        ↓
Poor Predictions
        ↓
Reduced Service Reliability
```

This may affect many legitimate users rather than one specific target.

---

### 104. Targeted Integrity Poisoning

A targeted poisoning attack attempts to alter a specific model behavior while keeping the rest of the model apparently normal.

```text id="mtp104"
Normal Inputs
      ↓
Normal Predictions

Specific Pattern
      ↓
Manipulated Prediction
```

This can make detection more difficult.

---

### 105. Backdoor Behavior

A particularly important targeted outcome is a **backdoor**.

The model appears normal during ordinary testing but responds incorrectly when a specific condition is present.

```text id="mtp105"
Normal Input
     ↓
Expected Output

Trigger + Input
     ↓
Unexpected Output
```

---

### 106. Trigger Characteristics

A trigger can theoretically be associated with:

* A visual characteristic.
* A textual pattern.
* A feature combination.
* A contextual condition.
* A specific data characteristic.

Security teams should test for unexpected conditional behavior without assuming a particular trigger exists.

---

### 107. Clean-Set Performance

Backdoored or poisoned models may maintain strong performance on normal validation data.

```text id="mtp107"
Clean Validation
      ↓
High Accuracy ✓

Special Test Condition
      ↓
Unexpected Behavior ✗
```

Therefore, clean accuracy alone cannot establish model integrity.

---

### 108. Behavioral Validation

Model validation should include tests designed to detect unexpected behavior.

Potential testing areas include:

* Rare inputs.
* Edge cases.
* Important classes.
* Security-sensitive scenarios.
* Known abuse patterns.

---

### 109. Subpopulation Testing

A model may perform well overall while behaving poorly for a specific subset of data.

Security testing should therefore evaluate relevant subpopulations.

```text id="mtp109"
Overall Dataset
      ↓
 ┌───────────────┐
 │ Group A       │
 │ Group B       │
 │ Group C       │
 │ Edge Cases    │
 └───────────────┘
```

---

### 110. Differential Testing

A model can be compared against:

* Previous model versions.
* Independently trained models.
* Baseline algorithms.
* Trusted reference datasets.

Unexpected behavioral differences can provide investigation signals.

---

### 111. Model-to-Model Comparison

For example:

```text id="mtp111"
Trusted Model
      +
Candidate Model
      ↓
Prediction Comparison
      ↓
Significant Difference?
```

Differences do not automatically indicate poisoning, but they may justify further investigation.

---

### 112. Shadow Evaluation

A candidate model can be evaluated against production-like traffic without immediately controlling production decisions.

```text id="mtp112"
Production Input
      ↓
 ┌──────────────┐
 │ Current Model│
 │ Candidate    │
 └──────────────┘
      ↓
Compare Results
```

This can identify unexpected behavior before deployment.

---

### 113. Canary Deployment

A new model can be exposed to a limited portion of traffic.

```text id="mtp113"
New Model
   ↓
Small Traffic Segment
   ↓
Monitor
   ↓
Accept / Roll Back
```

This limits the potential impact of a compromised or defective model.

---

### 114. Rollback Capability

Every important model deployment should have a defined rollback mechanism.

```text id="mtp114"
Model v5
   ↓
Unexpected Behavior
   ↓
Rollback
   ↓
Model v4
```

Rollback should restore a known-good model rather than simply redeploying an unverified artifact.

---

### 115. Known-Good Model

Organizations should maintain trusted model versions whose:

* Artifact integrity is verified.
* Training lineage is known.
* Validation results are documented.
* Deployment history is available.

---

### 116. Model Artifact Integrity

The model artifact should be protected against unauthorized modification after training.

Possible controls include:

* Cryptographic hashes.
* Digital signatures.
* Artifact repositories.
* Access control.
* Immutable storage.

---

### 117. Signed Model Artifacts

A model can be digitally signed after validation.

```text id="mtp117"
Validated Model
      ↓
Digital Signature
      ↓
Model Registry
      ↓
Signature Verification
      ↓
Deployment
```

This helps ensure that the deployed artifact is the approved artifact.

---

### 118. Model Registry Controls

The model registry should enforce:

* Authentication.
* Authorization.
* Versioning.
* Artifact integrity.
* Approval status.
* Audit logging.

---

### 119. Model Promotion

A controlled promotion workflow may look like:

```text id="mtp119"
Development
    ↓
Testing
    ↓
Security Validation
    ↓
Approval
    ↓
Staging
    ↓
Production
```

A model should not bypass these stages without a formally governed exception.

---

### 120. Training Run Approval

High-risk models may require approval of the training run itself.

This provides assurance that the model was generated using an authorized:

* Dataset.
* Code version.
* Configuration.
* Environment.

---

### 121. Reproducibility

Reproducibility is valuable during poisoning investigations.

If the organization can reproduce a training run, investigators can compare:

```text id="mtp121"
Expected Training Run
        vs.
Actual Training Run
```

This can help identify where behavior changed.

---

### 122. Deterministic Training

Where practical, organizations may control sources of randomness to make training behavior more reproducible.

However, many ML systems still contain nondeterministic elements.

Therefore, reproducibility should be understood as a goal rather than an absolute guarantee.

---

### 123. Training Run Fingerprint

A training run can be associated with a set of identifiers:

```text id="mtp123"
Dataset Hash
+
Code Commit
+
Dependency Versions
+
Configuration
+
Training Parameters
        ↓
Training Run Identity
```

This creates a stronger chain of evidence.

---

### 124. Dataset-to-Model Lineage

The organization should be able to establish:

> Which dataset produced this model?

And ideally:

> Which records and transformations contributed to that dataset?

---

### 125. Model-to-Dataset Reverse Traceability

Investigators should also be able to determine:

```text id="mtp125"
Suspicious Model
      ↓
Training Run
      ↓
Dataset Version
      ↓
Data Sources
      ↓
Suspicious Records
```

This greatly improves incident investigation.

---

### 126. Data Contribution Analysis

Where feasible, teams can examine whether particular sources contribute disproportionately to unexpected model behavior.

This can be useful when multiple external datasets are combined.

---

### 127. Source-Level Monitoring

Organizations can monitor how much data originates from each source.

```text id="mtp127"
Source A → 40%
Source B → 35%
Source C → 20%
Source D → 5%
```

A sudden change in these proportions may warrant investigation.

---

### 128. Source Isolation

If one source becomes suspicious, the organization should ideally be able to isolate it without rebuilding the entire data ecosystem.

```text id="mtp128"
Sources
 ├── A ✓
 ├── B ✓
 ├── C ⚠
 └── D ✓
       ↓
Isolate C
```

---

### 129. Data Quarantine

Suspicious datasets or records should be placed into quarantine rather than automatically entering production training.

Quarantine provides time for:

* Investigation.
* Validation.
* Reprocessing.
* Approval.

---

### 130. Poisoning Incident Classification

A suspected poisoning event should be classified according to:

* Scope.
* Persistence.
* Model impact.
* Data impact.
* Business impact.
* Attacker access.
* Affected systems.

---

### 131. Initial Response

A basic response sequence can be:

```text id="mtp131"
Detect
  ↓
Contain
  ↓
Preserve Evidence
  ↓
Investigate
  ↓
Validate Model
  ↓
Recover
```

---

### 132. Containment

Potential containment actions include:

* Stop affected training jobs.
* Freeze suspicious datasets.
* Disable compromised accounts.
* Prevent model promotion.
* Restrict affected pipelines.

The appropriate response depends on the incident.

---

### 133. Training Freeze

When poisoning is suspected, temporarily freezing automated retraining can prevent contaminated data from producing additional compromised models.

```text id="mtp133"
Suspicious Data
      ↓
Training Freeze
      ↓
Investigation
```

---

### 134. Model Deployment Freeze

If a newly trained model is suspected of poisoning, production deployment can be paused until validation is completed.

---

### 135. Evidence Preservation

Investigation evidence may include:

* Dataset versions.
* Dataset hashes.
* Training logs.
* Pipeline logs.
* Access logs.
* Model artifacts.
* Configuration.
* Code versions.

---

### 136. Audit Log Correlation

Data changes should be correlated with identity and infrastructure events.

```text id="mtp136"
Data Modification
       +
User Identity
       +
API Activity
       +
Training Job
       ↓
Investigation Timeline
```

---

### 137. Timeline Reconstruction

A poisoning investigation should attempt to establish:

1. When the data changed.
2. Who or what changed it.
3. When training consumed it.
4. When the model changed.
5. When the model was deployed.
6. When abnormal behavior began.

---

### 138. Blast-Radius Assessment

Investigators should determine how many models may have been affected.

```text id="mtp138"
Poisoned Dataset
      ↓
Training Run A → Model A
      ↓
Training Run B → Model B
      ↓
Training Run C → Model C
```

One compromised dataset can potentially affect multiple models.

---

### 139. Cross-Model Contamination

Shared datasets can create common dependencies between models.

If a poisoned dataset is reused, the problem may propagate across multiple applications.

---

### 140. Dataset Dependency Mapping

Organizations should maintain a map showing which models depend on which datasets.

This supports rapid incident containment.

---

### 141. Retraining After Poisoning

Simply retraining a model does not guarantee recovery.

If contaminated data remains in the training dataset, the new model may remain affected.

```text id="mtp141"
Poisoned Dataset
      ↓
Retraining
      ↓
Potentially Poisoned Model
```

---

### 142. Data Remediation

Before retraining, organizations should determine:

* Which data is trusted.
* Which data is suspicious.
* Which records require removal or correction.
* Whether historical versions are available.

---

### 143. Trusted Dataset Reconstruction

Where feasible, the organization should reconstruct a dataset from verified sources.

```text id="mtp143"
Trusted Sources
      ↓
Reconstruct Dataset
      ↓
Validate
      ↓
Retrain
      ↓
Security Test
```

---

### 144. Historical Data Recovery

Versioned and immutable storage can make recovery significantly easier.

Without historical copies, organizations may struggle to determine what the dataset looked like before compromise.

---

### 145. Prediction Retrospective

If a compromised model was active in production, organizations should determine whether historical predictions remain trustworthy.

Potentially affected decisions may require:

* Reprocessing.
* Manual review.
* Customer notification.
* Financial correction.
* Security investigation.

---

### 146. Business Impact Analysis

The technical discovery of poisoning is only one part of incident management.

The organization must assess:

```text id="mtp146"
Technical Compromise
        ↓
Affected Predictions
        ↓
Affected Decisions
        ↓
Business / Security Impact
```

---

### 147. High-Impact Models

Additional controls are warranted when model decisions influence:

* Security controls.
* Financial transactions.
* Identity decisions.
* Access permissions.
* Safety systems.
* Critical operations.

---

### 148. Risk Acceptance

If an organization knowingly operates a model with residual poisoning risk, that risk should be formally documented and accepted by the appropriate authority.

---

### 149. Continuous Improvement

Every poisoning incident or significant near miss should feed back into:

* Data controls.
* Training security.
* Model validation.
* Monitoring.
* Access management.
* Incident response.

---

### 150. Core Principle

Model poisoning defense must assume that **a compromised dataset can produce a legitimate-looking model artifact**.

Therefore:

```text id="mtp150"
Trusted Data
      ↓
Trusted Training
      ↓
Validated Model
      ↓
Signed Artifact
      ↓
Controlled Deployment
      ↓
Continuous Monitoring
```

Security assurance must exist at every stage because **successful training does not prove trustworthy training**.

# 09.11 — Model and Training Data Poisoning

## Part 4

### 151. Enterprise Poisoning Risk Model

An enterprise should assess poisoning risk across the complete ML lifecycle rather than treating the training dataset as an isolated asset.

```text
Data Source
    ↓
Collection
    ↓
Ingestion
    ↓
Validation
    ↓
Storage
    ↓
Preprocessing
    ↓
Training
    ↓
Validation
    ↓
Model Registry
    ↓
Deployment
    ↓
Monitoring
```

Each stage represents a potential integrity boundary.

---

### 152. Trust Boundaries

Security architecture should explicitly identify where data changes from one trust level to another.

For example:

```text
External
   ↓
Untrusted
   ↓
Validated
   ↓
Approved
   ↓
Training
   ↓
Production Model
```

Crossing each boundary should require appropriate controls.

---

### 153. Zero-Trust Principle for ML Data

A useful principle is:

> **Do not trust training data simply because it originated from an internal system.**

Internal systems can themselves be compromised.

Data should be validated according to its security requirements regardless of its origin.

---

### 154. Identity-Based Data Access

Training-data access should be associated with identifiable identities rather than shared credentials.

This improves:

* Accountability.
* Revocation.
* Investigation.
* Least privilege.

---

### 155. Service Identity

Automated training pipelines should use dedicated service identities.

```text
Training Pipeline
       ↓
Dedicated Identity
       ↓
Approved Dataset
```

The identity should have only the permissions required for its function.

---

### 156. Privileged Access Management

Administrative access to critical ML infrastructure should be controlled using appropriate privileged-access mechanisms.

Particularly sensitive permissions include the ability to:

* Modify production datasets.
* Change training pipelines.
* Approve models.
* Promote models.
* Delete historical artifacts.

---

### 157. Multi-Factor Authentication

Human administrative access to sensitive ML infrastructure should use strong authentication, including MFA where applicable.

This reduces the risk that stolen credentials can be used to manipulate training assets.

---

### 158. Access Reviews

Permissions should be periodically reviewed.

Questions include:

* Who can modify datasets?
* Who can launch training?
* Who can approve models?
* Who can modify pipeline configuration?
* Who can deploy models?

---

### 159. Separation of Data and Model Authority

Where practical, organizations should separate authority over:

```text
Dataset
   ↓
Training
   ↓
Model Approval
   ↓
Deployment
```

This reduces the possibility that one compromised identity can manipulate the entire lifecycle.

---

### 160. Four-Eyes Principle

For high-impact models, critical changes may require approval from more than one authorized person.

Examples include:

* Production dataset replacement.
* Model promotion.
* Training-pipeline changes.
* Emergency rollback.

---

### 161. Dataset Change Approval

Not every dataset modification needs manual approval.

However, changes to critical training datasets may require stronger governance depending on their risk classification.

---

### 162. Automated Security Gates

Security gates can prevent compromised or unapproved data from progressing through the pipeline.

```text
Dataset
   ↓
Security Gate
   ↓
PASS → Training
FAIL → Quarantine
```

---

### 163. Data Quality Gate

A quality gate can evaluate:

* Schema.
* Completeness.
* Duplicates.
* Distribution.
* Labels.
* Expected volume.

---

### 164. Integrity Gate

An integrity gate can verify:

* Hash.
* Signature.
* Version.
* Source.
* Expected artifact identity.

---

### 165. Provenance Gate

A provenance gate determines whether the organization can establish where the data came from.

```text
Unknown Source
     ↓
REJECT / QUARANTINE

Known Source
     ↓
Continue Validation
```

---

### 166. Security Gate Composition

A mature training pipeline may combine multiple gates:

```text
Source Verification
        ↓
Integrity
        ↓
Quality
        ↓
Provenance
        ↓
Security Analysis
        ↓
Training Authorization
```

---

### 167. Data Classification

Training data should be classified according to its sensitivity and business importance.

Potential categories include:

* Public.
* Internal.
* Confidential.
* Highly restricted.

Classification helps determine appropriate protection requirements.

---

### 168. Model Criticality

Data classification should be combined with model criticality.

For example:

```text
Low-Criticality Model
       ↓
Standard Controls

High-Criticality Model
       ↓
Enhanced Controls
```

---

### 169. Risk-Based Controls

Not every ML model requires the same poisoning defenses.

Controls should consider:

* Business impact.
* Data sensitivity.

* Regulatory obligations.

Organizations can maintain a dedicated risk register.

### 174. Auditability

### 177. Third-Party Assurance

For externally supplied training data, organizations may request evidence such as:

### 178. Contractual Controls

Where external datasets are business-critical, contracts can define requirements concerning:

### 182. Baseline Establishment

Traditional performance testing should be complemented by security-focused tests.

* Targeted behavior.

### 186. Regression Testing

```text
  ↓

  ↓
```

### 187. Security Regression Suite

### 188. Continuous Model Assurance

```text
 ↓
Validate
 ↓
Deploy
 ↓
Monitor
 ↓
Test
 ↓
Retrain
 ↓
Revalidate
```

Every retraining cycle creates another opportunity to verify integrity.

### 189. Secure Retraining

A secure retraining process should not simply consume all available production data.

```text
      ↓

      ↓
```

### 190. Feedback Data Governance

Feedback used for future training should be governed as a security-sensitive asset.

This includes:

* User feedback.
* Corrections.
* Labels.
* Human decisions.
* Automated outcomes.

---

### 191. Feedback Manipulation

Attackers may intentionally submit false feedback if they know it will influence future training.

Therefore:

> **Feedback should not automatically be considered trustworthy merely because it comes from users.**

---

### 192. Trusted Feedback

Higher-confidence feedback may be associated with:

* Verified users.
* Authorized reviewers.
* Independent validation.
* Multiple observations.

The appropriate method depends on the application.

---

### 193. Human Feedback Security

Human feedback processes should protect against:

* Unauthorized access.
* Reviewer manipulation.
* Excessive influence by one contributor.
* Conflicts of interest.
* Poor-quality annotations.

### 194. Automated Feedback Security

```text
       ↓

       ↓
Future Training
       ↓
```

If yes, the system contains a feedback loop requiring additional governance.

### 200. Core Principle

**Training-data poisoning is fundamentally an integrity problem across the ML lifecycle.**

A secure organization must protect the complete chain:

```text
SOURCE
  ↓
PROVENANCE
  ↓
DATA
  ↓
LABELS
  ↓
FEATURES
  ↓
TRAINING PIPELINE
  ↓
MODEL
  ↓
MODEL ARTIFACT
  ↓
DEPLOYMENT
  ↓
PRODUCTION BEHAVIOR
```

The strongest enterprise approach is therefore not to assume that poisoning can always be prevented. Instead, the organization should ensure that **unauthorized changes are difficult, legitimate changes are traceable, suspicious changes are detectable, compromised assets can be isolated, affected models can be rolled back, and the entire training lineage can be reconstructed during an investigation.**
