# 09.05 — Model Theft

## Part 1

### 1. Model Theft

Model theft is the unauthorized acquisition, copying, or exfiltration of a machine-learning model or its valuable components.

A stolen model may represent significant:

* Intellectual property.
* Research investment.
* Commercial advantage.
* Security-sensitive logic.
* Proprietary capabilities.

Model theft is therefore both a **cybersecurity risk** and a **business risk**.

---

### 2. What Can Be Stolen?

Model theft does not necessarily mean stealing a single model file.

An attacker may target:

* Model weights.
* Model architecture.
* Model configuration.
* Tokenizers.
* Training artifacts.
* Fine-tuned parameters.
* Model checkpoints.
* Deployment packages.
* Proprietary inference logic.

---

### 3. Model Weights

Model weights are among the most valuable assets in many ML systems.

They represent learned parameters generated during training or fine-tuning.

Conceptually:

```text id="x7m4qp"
Training
   ↓
Learned Parameters
   ↓
Model Weights
   ↓
Inference
```

Obtaining the weights may allow an attacker to reproduce or operate the model outside the organization's environment.

---

### 4. Model Architecture

An attacker may also seek information about:

* Number of layers.
* Layer types.
* Network structure.
* Attention configuration.
* Parameter counts.
* Specialized components.

Architecture information can reduce the effort required to reproduce a proprietary model.

---

### 5. Model Configuration

Configuration can contain valuable information such as:

* Hyperparameters.
* Thresholds.
* Inference settings.
* Fine-tuning parameters.
* Runtime configuration.

Configuration theft may therefore complement model-weight theft.

---

### 6. Training Artifacts

Training artifacts may include:

* Checkpoints.
* Optimizer states.
* Training logs.
* Intermediate models.
* Experiment outputs.

These can reveal information about how the model was developed.

---

### 7. Fine-Tuned Models

A base model may be publicly available while the organization's fine-tuned version is proprietary.

For example:

```text id="p6z3nc"
Public Base Model
       ↓
Enterprise Data
       ↓
Fine-Tuning
       ↓
Proprietary Model
```

The proprietary value may reside primarily in the resulting fine-tuned model.

---

### 8. Why Model Theft Matters

A stolen model can provide an attacker with capabilities that would otherwise require significant resources to develop.

Potential consequences include:

* Intellectual-property loss.
* Competitive disadvantage.
* Revenue loss.
* Loss of research investment.
* Unauthorized commercial use.
* Security exposure.

---

### 9. Model Theft vs Model Extraction

These concepts should be distinguished.

**Model theft** generally involves obtaining an existing model artifact or its internal components.

**Model extraction** involves reconstructing or approximating a model through interaction with a model service.

```text id="c8v5jw"
MODEL THEFT
Access Model Artifact
        ↓
Copy / Exfiltrate

MODEL EXTRACTION
Query Model
        ↓
Infer / Reconstruct
```

Both can result in loss of model intellectual property.

---

### 10. Direct Model Theft

Direct theft occurs when an attacker obtains the actual model artifact.

For example:

```text id="m4k8sx"
Model Registry
      ↓
Unauthorized Access
      ↓
Download Model
      ↓
Exfiltration
```

This is one of the most straightforward forms of model theft.

---

### 11. Indirect Model Theft

An attacker may obtain model components without accessing the complete artifact.

Examples include:

* Configuration files.
* Checkpoints.
* Intermediate artifacts.
* Container images.
* Model caches.

These components may still provide substantial value.

---

### 12. Model Theft Through Storage

Poorly secured model storage can expose models.

Potential storage locations include:

* Object storage.
* File servers.
* Model registries.
* Developer workstations.
* Backup systems.
* Cloud storage.
* Artifact repositories.

---

### 13. Object Storage Risk

Enterprise models are frequently stored in object-storage systems.

If access permissions are overly broad:

```text id="s7n2xd"
Model Storage
      ↓
Excessive Permissions
      ↓
Unauthorized Download
```

The model may be exposed without compromising the ML application itself.

---

### 14. Model Registry Theft

Model registries are particularly attractive targets because they may contain multiple versions.

An attacker gaining registry access could potentially obtain:

* Production models.
* Development models.
* Historical versions.
* Experimental models.
* Metadata.

---

### 15. Historical Model Versions

Older versions may remain valuable.

For example:

```text id="h5c9qa"
Model v1
Model v2
Model v3
Model v4
Model v5
```

An organization should not assume that only the current production version requires protection.

---

### 16. Backup Theft

Backups can contain complete model artifacts.

An attacker targeting backup systems may avoid attacking production infrastructure directly.

Therefore:

> **Model protection requirements should extend to backup and recovery environments.**

---

### 17. Developer Workstations

Models or checkpoints may be temporarily downloaded to developer machines.

This creates another potential theft path.

```text id="b8v4mk"
Model Registry
      ↓
Developer Machine
      ↓
Local Copy
      ↓
Potential Exfiltration
```

---

### 18. Model Theft Through CI/CD

CI/CD pipelines may have access to model artifacts.

A compromised pipeline could potentially:

* Read model files.
* Copy artifacts.
* Upload artifacts externally.
* Modify deployment packages.

Pipeline identities therefore require strong protection.

---

### 19. Service Account Risk

Automated ML services may have broad permissions.

For example:

```text id="q3x7np"
ML Service Account
      ↓
Read All Models
      ↓
Compromise
      ↓
Mass Model Access
```

Least privilege can reduce this risk.

---

### 20. Excessive Permissions

A user who only needs access to Model A should not automatically receive access to:

```text id="n6m2yc"
Model A
Model B
Model C
Model D
Model E
```

Access should be scoped to actual business requirements.

---

### 21. Privileged Insider Threat

Model theft may involve an insider with legitimate access.

Potential actors include:

* Employees.
* Contractors.
* Administrators.
* Developers.
* Researchers.
* Third-party personnel.

Legitimate access does not eliminate the need for monitoring.

---

### 22. Malicious Insider

A malicious insider may intentionally copy a model for:

* Personal use.
* Competitive advantage.
* Financial gain.
* Unauthorized disclosure.

Controls should therefore address both external attackers and insiders.

---

### 23. Negligent Insider

Model exposure does not always require malicious intent.

Examples include:

* Uploading a model to an unauthorized service.
* Sharing model files through personal storage.
* Sending checkpoints by email.
* Committing artifacts to public repositories.

Human error can therefore create model-theft exposure.

---

### 24. Public Repository Exposure

An employee may accidentally publish a proprietary model.

For example:

```text id="f4z8qa"
Private Model
      ↓
Developer Repository
      ↓
Public Visibility
      ↓
Model Download
```

Repository controls and secret/data scanning should therefore consider model artifacts.

---

### 25. Cloud Misconfiguration

A cloud storage bucket or model repository may accidentally become publicly accessible.

Potential consequences include:

* Unauthorized downloads.
* Automated harvesting.
* Permanent loss of confidentiality.

---

### 26. Model Theft Through Compromised Credentials

An attacker who obtains valid credentials may appear to be a legitimate user.

For example:

```text id="c7m5wd"
Stolen Credential
      ↓
Authenticated Access
      ↓
Model Registry
      ↓
Model Download
```

This is why authentication alone is insufficient.

---

### 27. Strong Authentication

Sensitive model repositories should use strong authentication mechanisms where appropriate.

Potential controls include:

* Multi-factor authentication.
* Federated identity.
* Conditional access.
* Privileged-access management.
* Short-lived credentials.

---

### 28. Authorization

After authentication, the organization should determine:

> **What is this identity actually allowed to access?**

Authorization should consider:

* Model sensitivity.
* User role.
* Business need.
* Environment.
* Action requested.

---

### 29. Read vs Write Permissions

Model access should distinguish between:

* Read.
* Write.
* Modify.
* Delete.
* Approve.
* Deploy.

A user who needs to run inference may not need permission to download or modify the underlying model.

---

### 30. Download Permissions

Model download is a particularly sensitive operation.

Organizations may consider restricting downloads of highly valuable models to:

* Approved systems.
* Controlled environments.
* Specific personnel.
* Managed workflows.

---

### 31. Model Export

Export functionality can create a significant theft risk.

For example:

```text id="v9x2kc"
Production Model
      ↓
Export
      ↓
External Location
```

Export should therefore be governed and logged.

---

### 32. Network Exfiltration

An attacker may attempt to transfer stolen models through:

* HTTPS.
* Cloud storage.
* File-transfer services.
* Remote repositories.
* Other external channels.

Network controls can help identify suspicious outbound transfers.

---

### 33. Data Loss Prevention

DLP mechanisms may help detect unauthorized movement of model artifacts.

Potential signals include:

* Large binary files.
* Known model formats.
* Model repository paths.
* Unusual outbound transfers.

---

### 34. Model File Types

Organizations may identify common model artifact formats relevant to their environment.

Examples can include:

* Framework-specific checkpoint formats.
* Serialized model files.
* ONNX artifacts.
* Tensor formats.
* Container images.

Detection should be tailored to the organization's actual technology stack.

---

### 35. Model Theft Detection

Detection mechanisms can monitor for unusual activity.

Examples include:

* Unexpected model downloads.
* Bulk downloads.
* Access outside normal hours.
* Access from unusual locations.
* Large outbound transfers.
* New identities accessing sensitive models.

---

### 36. Behavioral Monitoring

A user who normally accesses one model may suddenly download dozens.

For example:

```text id="r6w4mh"
Normal:
Model A → 2 accesses/week

Abnormal:
Models A–Z → 30 downloads/hour
```

This could represent a potential model-theft event.

---

### 37. User and Entity Behavior Analytics

UEBA-style monitoring can identify unusual behavior involving:

* Users.
* Service accounts.
* Administrators.
* Applications.

This can complement traditional access controls.

---

### 38. Download Volume

Download volume can be an important indicator.

For example:

```text id="y8n3qp"
Single Model Download
        ↓
Potentially Normal

100 Model Downloads
        ↓
Potentially Suspicious
```

Context is critical; automated systems may legitimately download many artifacts.

---

### 39. Geographic Anomalies

Unexpected geographic access may warrant investigation.

For example:

```text id="c2v7mx"
Normal:
Madrid → Model Registry

Unexpected:
Unknown Region → Model Registry
```

Geographic anomalies are signals, not proof of compromise.

---

### 40. Time-Based Anomalies

Unexpected access outside normal operational patterns can also be useful.

For example:

```text id="m5q8za"
Normal:
Business Hours

Unexpected:
Large Model Export at 03:00
```

Again, automation and global operations must be considered before classifying the event.

---

### 41. Model Theft Prevention

A layered approach can be represented as:

```text id="x4k9pc"
IDENTITY
   ↓
AUTHENTICATION
   ↓
AUTHORIZATION
   ↓
ACCESS CONTROL
   ↓
ENCRYPTION
   ↓
MONITORING
   ↓
DLP
   ↓
INCIDENT RESPONSE
```

No single control should be expected to prevent every theft scenario.

---

### 42. Encryption at Rest

Models stored on infrastructure should generally be protected using appropriate encryption mechanisms.

Encryption helps reduce exposure if storage media or unauthorized copies are obtained.

---

### 43. Encryption in Transit

Models transmitted between trusted systems should use protected communication channels.

For example:

```text id="z6r2vn"
Registry
   ↓
Encrypted Connection
   ↓
ML Platform
```

This reduces interception risk during legitimate transfers.

---

### 44. Encryption Does Not Solve Authorization

Encryption alone does not prevent an authorized user from downloading and copying a model.

Therefore:

```text id="p7m4xa"
Encryption
+
Access Control
+
Monitoring
```

provides stronger protection than encryption alone.

---

### 45. Key Management

Encryption effectiveness depends on appropriate key management.

Organizations should govern:

* Key access.
* Key rotation.
* Key storage.
* Key lifecycle.
* Key revocation.

---

### 46. Hardware-Backed Protection

For highly sensitive models, organizations may consider hardware-backed mechanisms for protecting cryptographic keys.

These mechanisms can strengthen protection against unauthorized key extraction.

---

### 47. Secure Model Repositories

A model repository should be treated as a sensitive enterprise asset.

Controls may include:

* Strong authentication.
* Role-based access.
* Encryption.
* Logging.
* Network restrictions.
* Integrity verification.
* Backup protection.

---

### 48. Model Repository Segmentation

Critical models may be separated from lower-risk artifacts.

For example:

```text id="k9c5wv"
Development Models
       │
       ├──────────────┐
       ↓              ↓
Development      Production
Repository       Repository
                     ↓
              Restricted Access
```

Segmentation can reduce the blast radius of compromise.

---

### 49. Production Model Isolation

Production models should generally have stronger protection than experimental models.

A simplified principle is:

> **The more valuable and business-critical the model, the stronger its access and monitoring controls should be.**

---

### 50. Core Model Theft Principle

Model theft represents the loss of a valuable digital asset.

A strong security strategy should therefore protect the model throughout its lifecycle:

```text id="w3m8qa"
CREATE
  ↓
STORE
  ↓
TRAIN
  ↓
REGISTER
  ↓
TRANSFER
  ↓
DEPLOY
  ↓
OPERATE
  ↓
ARCHIVE
```

At every stage, the organization should consider:

> **Who can access the model, what can they do with it, how is that activity monitored, and how would the organization detect and respond if the model were being stolen?**

# 09.05 — Model Theft

## Part 2

### 51. Model Theft Attack Surface

The model attack surface includes every location, system, identity, and process through which a model can be accessed or copied.

```text
                 MODEL
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
   Storage      Pipeline    Runtime
       │           │           │
       ↓           ↓           ↓
    Users       Services     APIs
       │           │           │
       └───────────┼───────────┘
                   ↓
              EXFILTRATION
```

A complete model-theft assessment therefore needs to look beyond the model registry itself.

---

### 52. Model Theft Attack Paths

An attacker may reach a model through several paths:

```text
Compromised User
      ↓
Model Repository
      ↓
Model Download
      ↓
External Transfer
```

or:

```text
Compromised CI/CD
      ↓
Artifact Repository
      ↓
Model Access
      ↓
Exfiltration
```

or:

```text
Compromised Cloud Account
      ↓
Object Storage
      ↓
Model Copy
```

---

### 53. Model Theft Kill Chain

A simplified attack chain can be represented as:

```text
RECONNAISSANCE
      ↓
INITIAL ACCESS
      ↓
PRIVILEGE ESCALATION
      ↓
MODEL DISCOVERY
      ↓
MODEL ACCESS
      ↓
MODEL COLLECTION
      ↓
EXFILTRATION
      ↓
EXTERNAL USE
```

Security controls should ideally interrupt the chain before the model leaves the trusted environment.

---

### 54. Model Discovery

Before stealing a model, an attacker may need to determine:

* Where models are stored.
* Which models are valuable.
* Which identities have access.
* What file formats are used.
* How models are deployed.
* Where backups are maintained.

Asset inventory and repository security can reduce this discovery advantage.

---

### 55. Model Value Discovery

Attackers may prioritize models based on:

* Commercial value.
* Competitive advantage.
* Strategic importance.
* Proprietary training.
* Customer impact.
* Research investment.

Not every model represents the same theft risk.

---

### 56. Crown-Jewel Models

Some models should be classified as **crown-jewel assets** because compromise would create substantial business impact.

Examples might include:

* Proprietary recommendation models.
* Fraud-detection models.
* Pricing models.
* High-value research models.
* Specialized industrial models.

These models may justify enhanced controls.

---

### 57. Model Classification

An organization can classify models according to sensitivity.

For example:

| Classification      | Example                  | Protection        |
| ------------------- | ------------------------ | ----------------- |
| Public              | Open model               | Standard          |
| Internal            | Internal analytics model | Controlled        |
| Confidential        | Proprietary model        | Restricted        |
| Highly Confidential | Strategic model          | Highly restricted |

Classification should drive security requirements.

---

### 58. Intellectual Property Classification

Model classification should align with the organization's broader information-classification scheme.

A model may be considered intellectual property even when the model does not contain obvious business data.

Its value may arise from the learned behavior itself.

---

### 59. Model Value Is Not Always Visible

A model file may look like a collection of numerical parameters.

However, those parameters can represent:

* Years of research.
* Significant training expenditure.
* Proprietary engineering.
* Specialized knowledge.
* Competitive differentiation.

Therefore, model artifacts should not be treated as ordinary application files.

---

### 60. Economic Impact of Model Theft

The financial impact can include:

```text
Development Investment
       +
Training Cost
       +
Engineering Cost
       +
Data Preparation
       +
Lost Competitive Advantage
       +
Potential Revenue Loss
```

The total impact may substantially exceed the storage value of the model file itself.

---

### 61. Competitive Intelligence

A stolen model may provide a competitor with insight into an organization's capabilities.

Even if the competitor cannot deploy it directly, the model may reveal:

* Technical sophistication.
* Domain expertise.
* Research direction.
* Product capabilities.

---

### 62. Unauthorized Replication

The attacker may use a stolen model to create a competing service.

For example:

```text
Organization's Model
        ↓
Unauthorized Copy
        ↓
Attacker Infrastructure
        ↓
Competing Service
```

This can convert intellectual-property theft into direct commercial competition.

---

### 63. Unauthorized Modification

A stolen model can also be modified.

For example:

```text
Legitimate Model
      ↓
Copied
      ↓
Modified
      ↓
Attacker-Controlled Model
```

The attacker may then attempt to pass the modified version off as legitimate.

---

### 64. Model Theft and Authenticity

Model theft and authenticity are connected.

If attackers obtain a model and modify it, they may attempt to redistribute the altered version.

Provenance and cryptographic verification can help consumers determine whether the artifact is legitimate.

---

### 65. Theft of Base and Fine-Tuned Models

Organizations may have:

```text
Base Model
    ↓
Fine-Tuning
    ↓
Enterprise Model
```

The fine-tuned model may contain proprietary value even if the base model is publicly available.

Protection should therefore focus on the organization's unique artifact.

---

### 66. Theft of Model Checkpoints

Training checkpoints may contain partially trained versions of a model.

These can still be valuable because they may reveal:

* Training progress.
* Model architecture.
* Learned parameters.
* Optimization behavior.

Checkpoint repositories should therefore be protected.

---

### 67. Theft Through Experiment Tracking

ML experiment platforms may contain model artifacts and metadata.

An attacker compromising such a platform could potentially access:

* Experiments.
* Checkpoints.
* Parameters.
* Training datasets.
* Model versions.

Experiment-management systems should therefore be included in the model security boundary.

---

### 68. Theft Through Artifact Repositories

General artifact repositories may store model packages alongside software components.

A compromise of the repository could expose multiple forms of intellectual property simultaneously.

---

### 69. Containerized Model Theft

A model may be packaged inside a container.

```text
Container
 ├── Runtime
 ├── Dependencies
 ├── Configuration
 └── Model
```

Obtaining the container image may therefore expose the model.

---

### 70. Container Registry Risk

Container registries should be treated as potential model repositories when model artifacts are embedded in images.

Controls should include:

* Access control.
* Image signing.
* Registry logging.
* Network restrictions.
* Vulnerability scanning.
* Artifact integrity validation.

---

### 71. Model Theft Through Build Artifacts

Build pipelines may generate temporary artifacts.

For example:

```text
Source
 ↓
Build
 ↓
Temporary Artifact
 ↓
Model Package
 ↓
Production
```

Temporary locations can become overlooked copies of valuable models.

---

### 72. Temporary File Risk

Security teams should consider:

* Build directories.
* Temporary storage.
* Caches.
* Worker nodes.
* CI/CD workspaces.

A model may exist in several locations during a single deployment process.

---

### 73. Model Cache Risk

Inference systems may cache model files locally for performance.

For example:

```text
Central Registry
      ↓
Inference Server
      ↓
Local Model Cache
```

The local cache becomes another asset that requires appropriate protection.

---

### 74. Ephemeral Infrastructure

Cloud workloads may create temporary compute environments containing model artifacts.

When these environments terminate, organizations should ensure that sensitive artifacts are handled appropriately.

---

### 75. Snapshot Risk

Virtual-machine or storage snapshots may contain complete model artifacts.

Therefore, snapshot repositories should be included in the model protection strategy.

---

### 76. Backup and Replication

Replication creates additional copies:

```text
Primary Model
      ↓
Backup
      ↓
Replica
      ↓
Disaster Recovery
```

Every additional copy increases the number of locations that require appropriate controls.

---

### 77. Data Residency and Model Copies

Organizations operating across regions may replicate models across geographic locations.

Governance should understand:

* Where models are stored.
* Which regions can access them.
* Which personnel can access those copies.
* What legal or contractual requirements apply.

---

### 78. Third-Party Model Hosting

A model may be hosted by an external provider.

The organization should understand:

* Who owns the artifact.
* Who can access it.
* Where it is stored.
* How it is protected.
* Whether copies are retained.
* How the model is deleted or returned.

---

### 79. Vendor Access

Third-party support personnel may require access to model infrastructure.

Vendor access should be:

* Authorized.
* Time-bound where practical.
* Logged.
* Least-privileged.
* Reviewed.

---

### 80. Remote Administration

Administrative access to model infrastructure creates a high-value attack path.

Controls may include:

* Privileged-access management.
* MFA.
* Bastion hosts.
* Session logging.
* Network restrictions.

---

### 81. Administrative Separation

Model security should avoid unnecessary concentration of privileges.

For example:

```text
Developer
   ↓
Can Develop

Security
   ↓
Can Assess

Model Owner
   ↓
Can Approve

Platform
   ↓
Can Deploy
```

Separating responsibilities can reduce insider and accidental risks.

---

### 82. Separation of Duties

A single individual should not necessarily be able to:

```text
Create Model
      ↓
Approve Model
      ↓
Deploy Model
      ↓
Export Model
```

without independent oversight, particularly for high-risk models.

---

### 83. Privileged Model Access

Administrative privileges should be carefully controlled because administrators may have broad access to:

* Model repositories.
* Storage.
* Backups.
* Deployment systems.

Privileged access is therefore a major model-theft concern.

---

### 84. Just-in-Time Access

For sensitive model environments, privileged access can be granted only when required.

Conceptually:

```text
Request
  ↓
Approval
  ↓
Temporary Access
  ↓
Activity Logged
  ↓
Access Removed
```

This reduces persistent privileged access.

---

### 85. Break-Glass Access

Emergency access may be required for critical systems.

Break-glass access should be:

* Restricted.
* Strongly authenticated.
* Logged.
* Reviewed afterward.

Emergency access should not become permanent administrative access.

---

### 86. Insider Monitoring

Monitoring should identify unusual activity involving sensitive model assets.

Potential indicators include:

* Bulk downloads.
* Repeated exports.
* Unusual repository access.
* Access to models unrelated to the user's role.
* Unexpected access shortly before account termination.

These are indicators for investigation, not automatic proof of malicious behavior.

---

### 87. Offboarding Risk

Employee offboarding can create model-theft exposure if access is not promptly removed.

A strong process should address:

```text
Employee Departure
      ↓
Identity Disabled
      ↓
Repository Access Removed
      ↓
Cloud Access Removed
      ↓
Privileged Credentials Revoked
      ↓
Tokens / Keys Reviewed
```

---

### 88. Contractor Offboarding

The same principle applies to contractors and temporary personnel.

Their access should expire when the business requirement ends.

---

### 89. Dormant Accounts

Dormant accounts can become attractive targets.

An account that has not been used for months but retains model-repository access represents unnecessary exposure.

---

### 90. Access Review

Periodic access reviews should determine:

* Who can access models?
* Why do they need access?
* Is access still required?
* What level of access do they have?
* Are service accounts still necessary?

---

### 91. Model Access Recertification

For sensitive models, access can be periodically recertified.

```text
Current Access
      ↓
Owner Review
      ↓
Still Required?
   ↙       ↘
 YES       NO
  ↓         ↓
Keep      Remove
```

---

### 92. Dormant Model Access

An identity may retain access even after changing roles.

For example:

```text
ML Engineer
    ↓
Transfers to Finance
    ↓
Still Has Model Access
```

This is an authorization hygiene issue.

---

### 93. Least Privilege

The principle of least privilege means identities should have only the access required to perform their responsibilities.

For model environments:

> **Access to a model should not imply unrestricted access to every model.**

---

### 94. Attribute-Based Access

More mature environments may consider attributes such as:

* User role.
* Model classification.
* Environment.
* Location.
* Device trust.
* Business unit.

Access can then be evaluated dynamically.

---

### 95. Environment Separation

Development, testing, and production environments should have appropriate separation.

```text
DEVELOPMENT
     ↓
TEST
     ↓
PRODUCTION
```

Access to development should not automatically provide unrestricted production-model access.

---

### 96. Production Model Restrictions

Production models should generally receive stronger controls because they may represent:

* Critical business logic.
* High-value intellectual property.
* Operational decision-making.

---

### 97. Model Download vs Inference

A critical distinction is:

**Inference access**

allows a user or application to submit input and receive an output.

**Model download access**

allows the user to obtain the underlying model artifact.

These are fundamentally different levels of exposure.

```text
Inference
Input → Model → Output

Download
User → Model Artifact
```

---

### 98. Restricting Direct Downloads

Where practical, users may be allowed to use a model through controlled inference services without receiving the underlying artifact.

This can significantly reduce direct model-theft exposure.

---

### 99. API-Based Model Access

A controlled API can act as an abstraction layer:

```text
Consumer
   ↓
API
   ↓
Inference Service
   ↓
Protected Model
```

The model remains inside the controlled environment.

---

### 100. Core Protection Principle

The fundamental protection strategy is:

```text
                PROTECT
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      ACCESS     STORAGE    EXPORT
        ↓          ↓          ↓
    CONTROL      SECURE     RESTRICT
        │          │          │
        └──────────┼──────────┘
                   ↓
              MONITORING
                   ↓
             DETECTION
                   ↓
             RESPONSE
```

Model theft prevention is therefore not a single technical control. It requires **identity, authorization, storage security, artifact protection, monitoring, and governance to work together**.

# 09.05 — Model Theft

## Part 3

### 101. Model Theft Through Inference Infrastructure

Even when the model is never directly exposed through a download interface, the infrastructure performing inference may contain the model artifact.

```text id="n4k8wp"
Client
  ↓
API
  ↓
Inference Server
  ↓
Model Memory / Storage
```

Compromise of the inference infrastructure can therefore create a path to model theft.

---

### 102. Model Memory Exposure

A model may be loaded into system or GPU memory during inference.

An attacker who compromises the execution environment may attempt to access model-related information from memory.

This makes runtime security an important part of model protection.

---

### 103. GPU Infrastructure

Large models may execute on GPU infrastructure.

The security boundary may therefore include:

* GPU servers.
* GPU memory.
* Drivers.
* Runtime libraries.
* Container environments.
* Orchestration platforms.

A compromise of the underlying infrastructure may expose the model.

---

### 104. Shared Infrastructure

When multiple workloads share infrastructure, isolation becomes important.

```text id="w8m3ra"
Shared Host
 ├── Model A
 ├── Model B
 └── Model C
```

A vulnerability affecting the host or isolation layer could potentially increase exposure across multiple models.

---

### 105. Multi-Tenant Environments

Cloud-based ML platforms may use multi-tenant infrastructure.

Organizations should understand:

* Tenant isolation.
* Storage isolation.
* Runtime isolation.
* Administrative boundaries.
* Provider access.

---

### 106. Hypervisor and Container Security

If a model runs inside virtualized or containerized infrastructure, compromise of the isolation layer may create additional exposure.

Model protection therefore depends partly on the security of the underlying platform.

---

### 107. Inference Server Access

Inference servers should be protected against unauthorized administrative access.

Potential controls include:

* Strong authentication.
* Network segmentation.
* Privileged access management.
* Secure administration.
* Logging.

---

### 108. Model Theft Through APIs

APIs can expose more than inference functionality.

An insecure API might accidentally provide:

* Model download functionality.
* Debugging endpoints.
* Administrative functions.
* Model metadata.
* Internal file paths.

API security should therefore be included in model-theft assessments.

---

### 109. Debug Interfaces

Debugging functions can unintentionally expose sensitive information.

For example:

```text id="h5q2mk"
Production Service
      ↓
Debug Endpoint
      ↓
Model Metadata
      ↓
Potential Artifact Exposure
```

Debug interfaces should not be unnecessarily exposed in production.

---

### 110. Administrative APIs

Administrative APIs should be separated from ordinary inference interfaces where practical.

```text id="c9w4zs"
Inference API
    ↓
Normal Users

Admin API
    ↓
Restricted Administrators
```

This reduces unnecessary exposure.

---

### 111. API Authentication

Inference and administrative APIs should use appropriate authentication.

However, authentication alone is not enough.

The organization should also validate:

* Authorization.
* Request origin.
* Session security.
* Rate limits.
* Privilege boundaries.

---

### 112. API Authorization

A client authorized to perform inference should not automatically be authorized to retrieve model artifacts.

For example:

```text id="y7p3nc"
Inference Permission
        ≠
Model Download Permission
```

This distinction is fundamental.

---

### 113. API Rate Limiting

Rate limiting can reduce abusive interaction with model services.

It is particularly useful when attackers attempt large-scale probing or automated collection.

Rate limiting does not replace model protection but can reduce attack efficiency.

---

### 114. Model Endpoint Exposure

Externally accessible model endpoints should receive stronger security controls than internal-only services.

Risk factors include:

* Internet exposure.
* Number of users.
* Sensitivity of the model.
* Business criticality.
* Authentication method.

---

### 115. Network Segmentation

A model repository should not necessarily be directly reachable from every network segment.

For example:

```text id="u8m4qa"
Corporate Network
       ↓
Application Layer
       ↓
Inference Layer
       ↓
Protected Model Repository
```

Segmentation can reduce unauthorized access paths.

---

### 116. Private Model Networks

Highly sensitive model repositories may be placed within restricted network zones.

Only approved systems may be permitted to communicate with them.

---

### 117. Egress Controls

Outbound network controls can help limit model exfiltration.

For example:

```text id="p3x7vn"
Model Environment
      ↓
Egress Policy
      ↓
Approved Destinations
```

Unexpected outbound transfers can then be blocked or investigated.

---

### 118. Network-Level Detection

Security monitoring can identify suspicious transfers based on:

* Destination.
* Volume.
* Frequency.
* Protocol.
* Source identity.
* Timing.

Large model files may create distinctive network patterns.

---

### 119. Data Loss Prevention for Models

Traditional DLP often focuses on documents and structured data.

Organizations should also consider whether their DLP controls can identify proprietary model artifacts.

---

### 120. Model Fingerprinting

Organizations can establish fingerprints for important model artifacts.

For example:

```text id="g6n2xc"
Model v5.0
     ↓
Cryptographic Fingerprint
     ↓
Known Trusted Identity
```

If a matching artifact appears somewhere unexpected, it may warrant investigation.

---

### 121. Canary Models

Organizations may use specially designed internal artifacts or monitoring mechanisms to help identify unauthorized access or copying.

Such mechanisms should be carefully governed and should not be treated as a substitute for access control.

---

### 122. Watermarking

Model watermarking can sometimes help establish ownership or identify unauthorized copies.

Conceptually:

```text id="b8c5mz"
Original Model
      ↓
Watermark
      ↓
Authorized Model
```

If the model later appears elsewhere, the watermark may support attribution.

---

### 123. Limitations of Watermarking

Watermarking is not a complete theft-prevention mechanism.

Potential limitations include:

* Removal attempts.
* Model modification.
* Detection difficulty.
* False positives.
* Compatibility issues.

It should therefore complement—not replace—security controls.

---

### 124. Ownership Metadata

Models can include metadata indicating:

* Organization.
* Model owner.
* Version.
* Release identifier.
* Copyright or licensing information.

Metadata improves traceability but can potentially be modified.

---

### 125. Cryptographic Model Identity

A stronger approach is to associate the artifact with cryptographic identity.

```text id="r2w8fk"
Model
 ↓
Hash
 ↓
Digital Signature
 ↓
Trusted Identity
```

This can provide stronger evidence than editable metadata.

---

### 126. Model Encryption

Sensitive model artifacts may be encrypted so that possession of the file alone does not provide immediate access to the model.

The effectiveness depends on secure key management and controlled decryption.

---

### 127. Encryption During Deployment

Some environments may use encryption or protected mechanisms to reduce exposure of models during deployment.

The exact protection depends on the platform and threat model.

---

### 128. Confidential Computing

Confidential-computing technologies can potentially protect sensitive workloads from certain classes of infrastructure-level access.

For highly sensitive models, this may be considered as part of a broader protection architecture.

---

### 129. Trusted Execution Environments

A trusted execution environment can provide hardware-assisted isolation for sensitive computations.

Conceptually:

```text id="z6m3qa"
Protected Model
      ↓
Trusted Execution Environment
      ↓
Inference
```

The applicability depends on model architecture, performance requirements, and platform support.

---

### 130. Model Access Broker

An organization may introduce an access layer between users and sensitive models.

```text id="c4x7vn"
User
 ↓
Access Broker
 ↓
Authorization
 ↓
Protected Model
```

The broker can enforce consistent access policies and logging.

---

### 131. Centralized Model Gateway

A centralized gateway can provide:

* Authentication.
* Authorization.
* Rate limiting.
* Logging.
* Policy enforcement.
* Monitoring.

This can make model access easier to govern.

---

### 132. Model Download Gateway

For highly sensitive models, direct downloads can be replaced by controlled workflows.

```text id="m8q5yd"
Download Request
      ↓
Business Justification
      ↓
Approval
      ↓
Temporary Access
      ↓
Logged Download
```

This provides stronger accountability.

---

### 133. Justification-Based Access

Some organizations may require users to provide a business reason before accessing particularly sensitive model artifacts.

This creates an additional governance layer.

---

### 134. Approval-Based Export

Exporting a crown-jewel model may require explicit approval.

For example:

```text id="f7n3wc"
Export Request
      ↓
Model Owner
      ↓
Security / GRC
      ↓
Approved
      ↓
Controlled Export
```

---

### 135. Temporary Model Access

Access should ideally expire when the legitimate business requirement ends.

For example:

```text id="y5q8ka"
Access Granted
      ↓
4 Hours
      ↓
Access Automatically Removed
```

Temporary access reduces long-lived exposure.

---

### 136. Model Access Logging

Every sensitive model access should ideally produce an audit record.

Potential fields include:

```text id="d3m6xp"

Model
Version
Action
Timestamp

Result
```

---

### 137. Download Logging

Downloads deserve particular attention.

For example:

```text id="q9v4mb"
↓

↓
Download
↓
14:32
↓

```

Such records can support both detection and investigations.

---

### 138. Export Monitoring

Security teams can monitor:

* Number of exports.
* Export size.
* Destination.
* User identity.
* Frequency.
* Time of day.

---

### 139. Bulk Download Detection

A sudden bulk download can represent a potential theft event.

For example:

```text id="t6k2wp"
Normal:
1–2 models/day

Observed:
150 models/hour
```

The event should trigger investigation according to the organization's detection policy.

---

### 140. Anomalous Service Account Activity

Service accounts may normally access predictable model sets.

A service account suddenly accessing unrelated models can be suspicious.

---

### 141. Credential Theft Detection

If an attacker uses compromised credentials, behavioral analytics may identify:

* New device.
* New location.
* Unusual access time.
* Unusual model access.
* Abnormal download volume.

---

### 142. Session Monitoring

Highly privileged sessions may be monitored more closely.

This can include:

* Session recording.
* Command logging.
* Access duration.
* Administrative actions.

---

### 143. Security Information and Event Management

Model access logs can be integrated with enterprise security monitoring.

```text id="k3x7pm"
Model Registry
      ↓
Access Logs
      ↓
SIEM
      ↓
Correlation
      ↓
Security Alert
```

This connects model security with the wider SOC.

---

### 144. Security Correlation

A model download becomes more significant when correlated with other events.

For example:

```text id="s8w4na"
Credential Login
      +
Privilege Escalation
      +
Model Download
      +
Large Outbound Transfer
      ↓
HIGH-RISK EVENT
```

Correlation improves detection accuracy.

---

### 145. Insider Risk Correlation

A model export may warrant additional review when combined with:

* Unusual account activity.
* Policy violations.
* Large data transfers.
* Unauthorized repository access.

Security teams should use established investigation and privacy procedures.

---

### 146. Exfiltration Destination

The destination of a transfer can provide useful context.

Examples include:

* Approved corporate storage.
* Known backup infrastructure.
* Personal storage.
* Unknown external service.

Destination alone should not determine whether activity is malicious.

---

### 147. Cloud Storage Exfiltration

Attackers may attempt to copy models to external cloud storage.

Organizations can use cloud security controls to monitor unusual object-storage transfers and account activity.

---

### 148. Personal Storage Risk

Personal cloud storage can create a significant model-theft risk when employees use it to move proprietary artifacts.

Enterprise policy should clearly define acceptable storage locations.

---

### 149. Removable Media

For highly sensitive model environments, removable-media access may require additional controls.

Potential controls include:

* Device restrictions.
* Endpoint controls.
* DLP.
* Monitoring.
* Administrative approval.

---

### 150. Core Defensive Architecture

A comprehensive model-theft defense can be represented as:

```text id="w7n4cp"
             MODEL ASSET
                  ↓
        ┌─────────┴─────────┐
        ↓                   ↓
      IDENTITY           STORAGE
        ↓                   ↓
  Authentication       Encryption
        ↓                   ↓
  Authorization        Integrity
        ↓                   ↓
      ACCESS            BACKUP
        └─────────┬─────────┘
                  ↓
             DEPLOYMENT
                  ↓
             MONITORING
                  ↓
              DETECTION
                  ↓
              RESPONSE
```

The central principle is to **reduce unnecessary access, protect every copy, verify model identity, monitor model movement, and maintain enough evidence to detect and investigate unauthorized acquisition**.

### 151. Model Theft Risk Assessment

An enterprise should formally assess the risk of model theft rather than assuming that all models have the same exposure.

A practical assessment can consider:

* External exposure.
* Storage locations.
* Third-party dependencies.
* Existing security controls.

```text id="r8k4mz"
     +
Threat
     +
```

### 152. Model Theft Threat Modeling

Threat modeling should identify realistic ways an attacker could obtain the model.

```text id="c5n7wp"

     ↓

     ↓

     ↓
Unauthorized Download
     ↓
Exfiltration
```

```text id="m9q3xa"
     ↓

     ↓

     ↓
```

The organization should assess the paths most relevant to its environment.

### 153. Threat Actors

Potential model-theft actors include:

* Cybercriminals.
* Competitors.
* Nation-state actors.
* Malicious insiders.
* Disgruntled employees.
* Contractors.
* Compromised third parties.

The likelihood and capability of each actor will vary by organization and model value.

### 159. Data Discovery for Model Artifacts

Security tooling can sometimes search enterprise environments for known model artifacts.

### 162. Model Lifecycle and Theft Exposure

Risk changes throughout the model lifecycle.

```text id="z5n7xr"
   ↓

   ↓

   ↓

```

Development environments may contain many experimental copies, while production environments may contain fewer but more valuable artifacts.

### 163. Development Environment Risk

Development environments can have weaker controls than production.

However, they may contain:

* New models.
* Checkpoints.
* Proprietary experiments.
* Unreleased capabilities.

Therefore:

---

### 164. Research Environment Risk

Research environments may contain highly valuable intellectual property before it reaches production.

Security controls should account for the value of unpublished work.

---

### 165. Production Environment Risk

Production models may have higher business impact because they directly support operational processes.

Potential consequences of theft include:

* Competitive loss.
* Unauthorized reuse.
* Exposure of proprietary logic.

---

### 166. Archived Models

Archived models may remain valuable.

Organizations should determine:

* Whether they still require access.
* Whether they should be retained.
* How they are protected.
* When they can be securely deleted.

---

### 167. Model Retention

Retaining every model indefinitely increases the number of sensitive artifacts that must be protected.

Retention should therefore be governed by:

* Business requirements.
* Legal requirements.
* Regulatory requirements.
* Research needs.
* Security considerations.

---

### 168. Secure Model Disposal

When a model is no longer required, disposal should consider all copies.

```text id="k4p9xm"

   ↓
Backup
   ↓
Cache
   ↓
Development
   ↓
Temporary Files
```

Deleting one copy does not necessarily eliminate the artifact.

### 169. Cryptographic Erasure

Where encryption is used, secure destruction of encryption keys can be one component of model-data disposal.

The suitability of this approach depends on the storage architecture and applicable requirements.

### 171. Detection

The organization should determine how a suspected theft will be identified.

* SIEM.
* DLP.
* EDR.

* Access analytics.

* Legitimate activity.

If theft is suspected, relevant evidence should be preserved.

* Access logs.
* Authentication records.
* Download records.
* Network logs.
* Repository events.

### 174. Containment

Containment may include:

* Revoking credentials.

* Disabling compromised accounts.
* Restricting network paths.
* Quarantining systems.
* Suspending model exports.

### 176. Model Integrity After Theft

### 177. Credential Rotation

If model theft involved compromised credentials, appropriate credentials should be rotated or revoked.

### 178. Key Rotation

### 179. Model Replacement

### 181. Revoking Model Access

* Was access necessary?
* Was access excessive?

### 182. Third-Party Notification

* Cloud providers.

### 183. Legal and Intellectual Property Response

Model theft may involve intellectual-property rights.

* Cybersecurity.
* Legal.
* Privacy.
* Compliance.
* Intellectual-property teams.
* Executive management.

Determining who stole a model can be difficult.

Evidence may indicate:

* Account used.

* Destination.
* Time of access.
