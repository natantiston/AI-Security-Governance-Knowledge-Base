# 09.03 — Model Integrity

## Part 1

### 1. Model Integrity

Model integrity is the assurance that a machine-learning model is **complete, authentic, and has not been modified in an unauthorized or unintended way**.

At its simplest:

> **Model integrity means that the model being used is the model that was approved.**

This is a fundamental model-security property because an attacker who can modify a model may be able to change its behavior without changing the surrounding application.

---

### 2. Why Model Integrity Matters

A machine-learning model is executable logic expressed through learned parameters, architecture, configuration, and supporting artifacts.

If an attacker modifies any security-relevant component, the model may behave differently.

For example:

```text id="n7p2qm"
Approved Model
      ↓
Unauthorized Modification
      ↓
Altered Model
      ↓
Different Predictions
      ↓
Business Impact
```

The modification may be obvious or deliberately subtle.

---

### 3. Integrity Is Different From Confidentiality

Model security involves several distinct security properties.

**Confidentiality**

> Prevent unauthorized disclosure of the model.

**Integrity**

> Prevent unauthorized modification of the model.

**Availability**

> Ensure the model remains accessible when required.

A model can have strong confidentiality while having poor integrity.

For example, an organization may prevent users from downloading a model but fail to prevent an administrator or compromised service from replacing the production artifact.

---

### 4. Integrity in the CIA Triad

Model integrity is part of the broader **CIA triad**:

```text id="z5h4cw"
             MODEL SECURITY
                  │
       ┌──────────┼──────────┐
       ↓          ↓          ↓
CONFIDENTIALITY  INTEGRITY  AVAILABILITY
       │          │          │
 Protect Model   Protect    Keep Model
 from Theft      Model      Operational
                from Change
```

All three properties are relevant, but integrity is particularly important when model outputs influence decisions.

---

### 5. What Constitutes a Model

Model integrity should not be limited to a single model file.

Depending on the ML system, the model may include:

* Model weights.
* Architecture.
* Configuration.
* Tokenizer.
* Preprocessing logic.
* Post-processing logic.
* Model metadata.
* Runtime dependencies.
* Supporting files.

Therefore:

> **Integrity protection must cover the complete model package and the components required to produce the intended behavior.**

---

### 6. Model Artifact

A model artifact is the stored representation of a trained model.

Examples include:

* Serialized model files.
* Neural-network weight files.
* Checkpoints.
* Containerized model packages.
* Model bundles.

The artifact should be treated as a controlled enterprise asset.

---

### 7. Model Integrity Threat

A model integrity threat occurs when an unauthorized party can alter the model or associated components.

Potential attackers include:

* External attackers.
* Malicious insiders.
* Compromised accounts.
* Compromised CI/CD systems.
* Compromised model repositories.
* Compromised dependencies.

---

### 8. Unauthorized Model Modification

Unauthorized modification could involve:

* Changing model weights.
* Replacing the model file.
* Modifying configuration.
* Altering preprocessing.
* Changing post-processing.
* Adding malicious components.

The attacker may attempt to make the change difficult to detect.

---

### 9. Why Small Changes Can Matter

Machine-learning models can contain very large numbers of parameters.

An attacker does not necessarily need to modify the entire model.

A relatively targeted modification may potentially produce a specific behavioral effect.

Conceptually:

```text id="h1f5y4"
Large Model
     ↓
Small Targeted Modification
     ↓
Specific Behavioral Change
```

This is one reason integrity verification is important.

---

### 10. Model Integrity vs Model Accuracy

Integrity and accuracy are different concepts.

**Accuracy asks:**

> Is the model producing correct predictions?

**Integrity asks:**

> Has the model remained the authorized artifact?

A compromised model may continue producing apparently accurate results in ordinary testing.

```text id="3v1zbc"
Accuracy Test
     ↓
PASS

Integrity Verification
     ↓
FAIL
```

Therefore, performance testing cannot replace integrity controls.

---

### 11. Model Integrity vs Model Robustness

Robustness concerns how well a model behaves under challenging or manipulated inputs.

Integrity concerns whether the model itself has been altered.

For example:

```text id="g6z3cu"
Robustness
→ Can the model withstand difficult inputs?

Integrity
→ Has the model itself been changed?
```

They are related but distinct security properties.

---

### 12. Integrity Across the Lifecycle

Model integrity must be protected throughout the lifecycle.

```text id="j3k7xv"
Development
     ↓
Training
     ↓
Validation
     ↓
Registry
     ↓
Deployment
     ↓
Production
     ↓
Monitoring
     ↓
Retirement
```

An integrity failure at any stage can affect downstream stages.

---

### 13. Integrity During Development

During development, integrity involves protecting:

* Source code.
* Model configuration.
* Training scripts.
* Dependencies.
* Development artifacts.

Unauthorized code modification can eventually result in an unauthorized model.

---

### 14. Integrity During Training

Training integrity means ensuring that the training process produces the expected model.

Relevant controls include:

* Controlled training environments.
* Trusted datasets.
* Protected training code.
* Controlled dependencies.
* Access restrictions.
* Training logs.

---

### 15. Integrity During Validation

The model tested during validation should be the same model that is approved.

A dangerous scenario is:

```text id="h6qv5e"
Model A
 ↓
Security Testing
 ↓
PASS
 ↓
Model A Modified
 ↓
Production
```

The production artifact is no longer the tested artifact.

---

### 16. Integrity During Approval

Approval should be associated with a specific model version.

For example:

```text id="5o0j4v"
Model: Fraud Detection
Version: 4.2
Hash: ABC123...
Status: APPROVED
```

This creates a clear relationship between approval and the exact artifact.

---

### 17. Integrity in the Model Registry

The model registry should protect model artifacts and metadata from unauthorized modification.

Controls may include:

* Access control.
* Role separation.
* Versioning.
* Audit logging.
* Integrity verification.
* Approval-state protection.

---

### 18. Integrity During Deployment

Deployment systems should ensure that only approved artifacts are deployed.

A simplified control is:

```text id="z0p2ks"
Deployment Request
       ↓
Identify Model
       ↓
Verify Version
       ↓
Verify Integrity
       ↓
Verify Approval
       ↓
Deploy
```

If verification fails, deployment should be blocked or escalated.

---

### 19. Integrity in Production

Once deployed, the model should remain protected against unauthorized modification.

Production integrity controls may include:

* Restricted file permissions.
* Immutable storage.
* Integrity monitoring.
* Digital signatures.
* Hash verification.
* Privileged-access controls.
* Deployment controls.

---

### 20. Integrity After Deployment

Integrity verification should not necessarily stop after deployment.

A production model can be modified after deployment through:

* Compromised infrastructure.
* Administrative access.
* Vulnerable deployment pipelines.
* Malware.
* Insider activity.

Continuous or event-driven integrity verification can help detect these conditions.

---

### 21. Model Integrity Boundary

A useful security concept is to define the **integrity boundary**.

The integrity boundary identifies which components must remain trustworthy for the model to behave as intended.

For example:

```text id="u4q2tq"
┌────────────────────────────────┐
│       MODEL INTEGRITY          │
│                                │
│  Weights                       │
│  Architecture                 │
│  Configuration                │
│  Tokenizer                    │
│  Preprocessing                │
│  Post-processing              │
│  Critical Dependencies        │
└────────────────────────────────┘
```

The exact boundary depends on the model architecture.

---

### 22. Trusted Computing Base

The model-serving environment may contain a set of components that must be trusted for secure operation.

These may include:

* Model runtime.
* Operating system.
* Container.
* Deployment platform.
* Identity system.
* Model registry.
* Configuration system.

Compromise of a trusted component can undermine model integrity.

---

### 23. Integrity Chain

Model integrity can be viewed as a chain:

```text id="u3o6n8"
Trusted Source
     ↓
Trusted Build
     ↓
Trusted Artifact
     ↓
Trusted Registry
     ↓
Trusted Deployment
     ↓
Trusted Runtime
```

A weak link can compromise the overall chain.

---

### 24. Chain of Custody

A model's chain of custody describes how the artifact moves between environments and responsible parties.

For example:

```text id="j8k6sc"
Data Scientist
      ↓
ML Pipeline
      ↓
Model Registry
      ↓
Security Validation
      ↓
Approval
      ↓
Deployment Pipeline
      ↓
Production
```

Each transition should be controlled and traceable.

---

### 25. Model Integrity Evidence

Organizations should maintain evidence demonstrating that integrity controls are operating.

Examples include:

* Hash values.
* Digital signatures.
* Registry records.
* Deployment logs.
* Access logs.
* Change records.
* Integrity alerts.
* Approval records.

---

### 26. Cryptographic Hashing

A cryptographic hash produces a fixed-length representation of an artifact.

Conceptually:

```text id="8f6f3e"
Model Artifact
      ↓
Hash Function
      ↓
Hash Value
```

If the artifact changes, its hash will normally change.

This makes hashing useful for integrity verification.

---

### 27. Hash Comparison

A simple integrity mechanism is:

```text id="5cm3nq"
Approved Model
      ↓
Hash = X

Production Model
      ↓
Hash = X

       ↓
MATCH
```

A mismatch can indicate that the production artifact differs from the approved artifact.

---

### 28. Hash Mismatch

A mismatch does not automatically prove malicious activity.

Possible causes include:

* Authorized update.
* File corruption.
* Repackaging.
* Deployment process.
* Storage issue.
* Unauthorized modification.

The correct response is to investigate the discrepancy.

---

### 29. Hash Limitations

Hashing provides evidence of whether the artifact changed, but it does not by itself establish:

* Who created the artifact.
* Whether the original artifact was trustworthy.
* Who authorized it.
* Whether the runtime environment is secure.

Therefore, hashing should be combined with other controls.

---

### 30. Digital Signatures

Digital signatures provide stronger assurance around authenticity and integrity.

A trusted party can sign an approved model artifact.

Conceptually:

```text id="h9d1sa"
Approved Model
      ↓
Private Signing Key
      ↓
Digital Signature
      ↓
Signed Model
```

The receiving system can verify the signature using the corresponding public key.

---

### 31. Signature Verification

During deployment:

```text id="e9m4nt"
Signed Model
      ↓
Signature Verification
      ↓
VALID → Continue
INVALID → Reject / Investigate
```

This provides stronger control than relying solely on an untrusted filename or version number.

---

### 32. Trusted Signing Authority

The organization should control who or what is permitted to sign production model artifacts.

Signing authority should be:

* Restricted.
* Protected.
* Audited.
* Subject to key-management controls.

Compromise of the signing key could undermine the trust model.

---

### 33. Immutable Model Storage

Immutable storage prevents or restricts modification of stored artifacts.

This can help protect:

* Approved models.
* Model versions.
* Evidence.
* Backup artifacts.

Immutability can be especially valuable for high-risk models.

---

### 34. Write Protection

Write protection limits who can modify a model artifact.

For example:

```text id="1j4c8r"
Developers → Read
Security → Verify
Deployment System → Controlled Read
Registry Admin → Restricted
```

The exact permissions should reflect organizational requirements.

---

### 35. Least Privilege

Model integrity depends heavily on least privilege.

Users and systems should receive only the permissions necessary to perform their responsibilities.

For example:

> A user who only needs to run inference should not automatically have permission to replace the model artifact.

---

### 36. Privileged Access Management

Highly privileged model-management accounts should receive additional protection.

Controls may include:

* Strong authentication.
* Just-in-time access.
* Session monitoring.
* Approval workflows.
* Privileged activity logging.

---

### 37. Separation of Duties

Model integrity can be strengthened by separating sensitive responsibilities.

For example:

```text id="c4s0wt"
Build
 ≠
Approve
 ≠
Deploy
```

This reduces the likelihood that one compromised account can independently introduce an unauthorized production model.

---

### 38. Model Integrity and CI/CD

Machine-learning environments increasingly use automated pipelines.

A compromised CI/CD pipeline can potentially modify or replace model artifacts.

Therefore, CI/CD integrity becomes part of model integrity.

```text id="7j6y1e"
Source Code
     ↓
CI/CD
     ↓
Build
     ↓
Model
     ↓
Deployment
```

Every step should have appropriate security controls.

---

### 39. Pipeline Integrity

Pipeline controls may include:

* Protected repositories.
* Build authentication.
* Trusted runners.
* Dependency controls.
* Artifact verification.
* Approval gates.
* Pipeline logging.

---

### 40. Build Reproducibility

Reproducible builds can help verify that a model artifact was generated from the expected inputs and process.

Relevant information can include:

* Code version.
* Dataset version.
* Configuration.
* Dependencies.
* Framework version.
* Training environment.

This strengthens provenance and integrity assurance.

---

### 41. Model Integrity Baseline

A baseline represents the approved state of the model.

It may contain:

```text id="e3n7tq"
Model ID
Version
Hash
Signature
Configuration
Dependencies
Deployment Location
Approval Status
```

Production can then be compared against the approved baseline.

---

### 42. Integrity Monitoring

Integrity monitoring detects deviations from the approved state.

For example:

```text id="r0h5yc"
Approved Baseline
      ↓
Continuous / Periodic Check
      ↓
Current State
      ↓
Compare
```

Any unexpected difference should generate an appropriate response.

---

### 43. File Integrity Monitoring

File integrity monitoring can detect changes to model artifacts and related files.

Potential monitored assets include:

* Model files.
* Configuration.
* Runtime files.
* Deployment manifests.
* Container images.

---

### 44. Runtime Integrity

Integrity does not end with the stored artifact.

The organization should consider whether the runtime environment itself remains trustworthy.

Potential controls include:

* Trusted container images.
* Secure boot where applicable.
* Runtime protection.
* Container integrity.
* Host monitoring.
* Configuration monitoring.

---

### 45. Container Integrity

When a model is deployed in a container, the container image becomes part of the trusted deployment chain.

```text id="b1k7wa"
Model
 +
Runtime
 +
Libraries
 +
Configuration
      ↓
Container Image
      ↓
Production
```

An altered container can compromise model behavior even if the model weights are unchanged.

---

### 46. Dependency Integrity

Dependencies can affect model behavior.

An attacker who modifies a critical dependency may influence:

* Data processing.
* Model execution.
* Input handling.
* Output handling.

Therefore, dependency integrity is part of the broader model integrity problem.

---

### 47. Configuration Integrity

Configuration changes can sometimes have effects comparable to changing the model itself.

Examples include:

* Thresholds.
* Feature configuration.
* Preprocessing parameters.
* Endpoint settings.
* Safety controls.

Configuration should therefore be version-controlled and protected.

---

### 48. Preprocessing Integrity

A model may receive data after preprocessing.

If preprocessing is modified:

```text id="e8n8u0"
Original Input
      ↓
Expected Preprocessing
      ↓
Model
```

can become:

```text id="2xj8dv"
Original Input
      ↓
Modified Preprocessing
      ↓
Model
```

The model artifact may remain unchanged while the system's behavior changes.

---

### 49. Post-Processing Integrity

The same principle applies after inference.

If post-processing changes:

```text id="f3k0xa"
Model Output
      ↓
Modified Post-Processing
      ↓
Application Decision
```

the final business result may differ from the approved design.

---

### 50. Integrity as a System Property

Therefore, model integrity should ultimately be viewed as more than:

> “The model file has not changed.”

A stronger definition is:

> **The model and the security-relevant components surrounding its execution remain consistent with the authorized, validated, and approved state.**

## Part 2

### 51. Model Integrity Threat Sources

Model integrity can be threatened by many sources, not only external attackers.

Common sources include:

* External attackers.
* Malicious insiders.
* Compromised user accounts.
* Compromised administrator accounts.
* Vulnerable CI/CD pipelines.
* Compromised repositories.
* Malicious dependencies.
* Supply-chain compromise.
* Misconfiguration.
* Accidental modification.

A mature integrity program therefore considers both **malicious and accidental changes**.

---

### 52. External Attackers

An external attacker may attempt to gain access to:

* Model repositories.
* Model APIs.
* Cloud storage.
* Deployment infrastructure.
* CI/CD systems.

If successful, the attacker may attempt to modify or replace a model.

---

### 53. Insider Threat

An insider may already possess legitimate access.

The risk arises when legitimate privileges are abused.

For example:

```text id="u1j7px"
Legitimate Access
      ↓
Unauthorized Modification
      ↓
Compromised Model
```

This is why authentication alone is insufficient.

---

### 54. Compromised Account

An attacker does not necessarily need to compromise the model directly.

They may first compromise an account with model-management privileges.

```text id="2v9m2p"
User Account
      ↓
Credential Theft
      ↓
Privileged Access
      ↓
Model Modification
```

Identity security is therefore part of model integrity.

---

### 55. Privilege Escalation

An attacker may attempt to move from a low-privilege account to a higher privilege level.

For example:

```text id="9m2b7a"
Inference User
      ↓
Privilege Escalation
      ↓
Model Administrator
      ↓
Model Modification
```

Privileged-access controls help reduce this risk.

---

### 56. CI/CD Compromise

The deployment pipeline is a particularly important integrity boundary.

If an attacker compromises the pipeline, they may be able to deploy an altered artifact without directly modifying the model registry.

```text id="d5r2ka"
Compromised Pipeline
        ↓
Altered Artifact
        ↓
Authorized Deployment Process
        ↓
Production
```

The deployment process may appear legitimate even though its inputs have been manipulated.

---

### 57. Repository Compromise

Model repositories and source-code repositories can also become attack targets.

Potential consequences include:

* Model replacement.
* Version manipulation.
* Unauthorized configuration changes.
* Malicious code insertion.

Repository security should therefore be included in integrity controls.

---

### 58. Model Registry Compromise

A compromised model registry can undermine several lifecycle controls simultaneously.

An attacker may attempt to:

* Replace an artifact.
* Modify metadata.
* Change approval status.
* Delete versions.
* Manipulate deployment information.

Because the registry is a central trust point, it should receive strong protection.

---

### 59. Version Manipulation

An attacker may attempt to make an unauthorized model appear legitimate by changing its version information.

For example:

```text id="c0e7m3"
Malicious Model
      ↓
Rename as
Approved_Model_v5
      ↓
Deployment
```

Therefore, filenames and version numbers alone should not be trusted as proof of authenticity.

---

### 60. Model Replacement

A particularly direct integrity attack is replacing an approved model with a malicious model.

```text id="m8x3az"
Approved Model
      ↓
Unauthorized Replacement
      ↓
Malicious Model
      ↓
Production
```

Cryptographic verification and controlled deployment can help prevent this.

---

### 61. Model Tampering

Tampering refers to unauthorized modification of the model or associated artifacts.

It may involve:

* Weights.
* Architecture.
* Configuration.
* Metadata.
* Supporting files.

Tampering may be broad or highly targeted.

---

### 62. Subtle Tampering

Attackers may deliberately make changes that are difficult to identify.

For example:

```text id="0p7g1m"
Normal Inputs
     ↓
Normal Behavior
```

while:

```text id="h1n9dr"
Specific Trigger
     ↓
Unexpected Behavior
```

This type of manipulation can make conventional testing less effective.

---

### 63. Targeted Model Manipulation

A model may be manipulated to behave differently under a particular condition.

The attacker may attempt to preserve normal behavior for ordinary testing while creating abnormal behavior for selected inputs.

This creates a particularly difficult integrity challenge.

---

### 64. Integrity Attack Surface

The attack surface may include:

```text id="0j7nqz"
Source Code
    ↓
Training Data
    ↓
Training Pipeline
    ↓
Model Artifact
    ↓
Model Registry
    ↓
Deployment Pipeline
    ↓
Runtime
    ↓
Configuration
```

Each stage can become a potential integrity target.

---

### 65. Model Integrity Threat Modeling

Threat modeling should ask:

* What can modify the model?
* Who can modify it?
* What systems can modify it?
* Where is the model stored?
* How is it transferred?
* How is authenticity verified?
* How is modification detected?
* How is recovery performed?

---

### 66. Integrity Threat Scenario

A simplified threat scenario could be:

```text id="k9w4dy"
Attacker
   ↓
Compromises Developer Account
   ↓
Modifies Training Code
   ↓
Runs Training Pipeline
   ↓
Creates Altered Model
   ↓
Uploads Model
   ↓
Attempts Production Deployment
```

Controls should interrupt this chain at multiple points.

---

### 67. Defense in Depth

Model integrity should use multiple layers of protection.

For example:

```text id="h7x2pb"
Identity Security
      ↓
Repository Security
      ↓
Pipeline Security
      ↓
Artifact Signing
      ↓
Registry Controls
      ↓
Deployment Verification
      ↓
Runtime Monitoring
```

If one control fails, another may detect or prevent the attack.

---

### 68. Preventive Controls

Preventive integrity controls attempt to stop unauthorized modification before it happens.

Examples include:

* Least privilege.
* Strong authentication.
* Access control.
* Immutable storage.
* Protected branches.
* Approval gates.
* Digital signatures.
* Restricted deployment permissions.

---

### 69. Detective Controls

Detective controls identify unauthorized changes.

Examples include:

* Hash comparison.
* File integrity monitoring.
* Registry monitoring.
* Deployment monitoring.
* Audit logs.
* Configuration monitoring.
* Security alerts.

---

### 70. Corrective Controls

Corrective controls respond after an integrity problem has been identified.

Examples include:

* Rollback.
* Model replacement.
* Credential revocation.
* Pipeline isolation.
* Incident response.
* Restoration from a trusted backup.

---

### 71. Preventive + Detective + Corrective

A mature model integrity architecture combines all three.

```text id="v7h5qf"
PREVENT
   ↓
DETECT
   ↓
RESPOND
   ↓
RECOVER
   ↓
IMPROVE
```

This creates a complete security cycle.

---

### 72. Model Integrity Verification

Integrity verification determines whether an artifact corresponds to the expected trusted state.

A verification process may compare:

* Hash.
* Signature.
* Version.
* Registry metadata.
* Approval record.

---

### 73. Verification Before Deployment

Before deployment:

```text id="p6r1ty"
Requested Model
      ↓
Hash Verification
      ↓
Signature Verification
      ↓
Registry Verification
      ↓
Approval Verification
      ↓
DEPLOY
```

Any failed check should trigger an appropriate control response.

---

### 74. Verification During Deployment

Integrity checks can also occur while the artifact moves between environments.

For example:

```text id="j8d2qm"
Registry
  ↓
Deployment Pipeline
  ↓
Staging
  ↓
Production
```

The artifact should remain consistent throughout the transfer.

---

### 75. Verification After Deployment

After deployment, the organization may verify that the running environment corresponds to the approved artifact.

This can establish:

> **The model that is actually running is the model that was authorized.**

---

### 76. Periodic Integrity Verification

Integrity verification can be performed periodically.

For example:

```text id="8w0w0p"
Scheduled Check
      ↓
Current Model Hash
      ↓
Approved Hash
      ↓
Compare
```

The frequency should reflect the model's risk.

---

### 77. Event-Driven Integrity Verification

Verification can also occur when specific events happen.

Examples:

* Deployment.
* Configuration change.
* Infrastructure migration.
* Security incident.
* Registry change.
* Administrative access.

This is useful when continuous verification is unnecessary or impractical.

---

### 78. Continuous Integrity Monitoring

For highly critical systems, integrity may be monitored continuously or near-continuously.

The objective is to reduce the time between unauthorized modification and detection.

The appropriate monitoring model depends on:

* Criticality.
* Performance requirements.
* Architecture.
* Operational cost.

---

### 79. Baseline Establishment

Before integrity can be monitored effectively, the organization needs a trusted baseline.

The baseline should be established from an authorized model.

```text id="1k9yq3"
Validated Model
      ↓
Approved
      ↓
Integrity Baseline
```

An untrusted baseline provides little security value.

---

### 80. Baseline Components

A baseline may include:

* Model hash.
* Digital signature.
* Version.
* Configuration.
* Dependencies.
* Container image.
* Runtime requirements.

---

### 81. Trusted Baseline Storage

The integrity baseline should itself be protected.

If an attacker can modify both:

```text id="d0r8sv"
Production Model
      +
Approved Hash
```

then a simple hash comparison may no longer detect the attack.

Therefore, baseline information should be stored in a trusted location with appropriate access controls.

---

### 82. Independent Verification

For high-risk models, verification may be performed by an independent security mechanism rather than by the same system responsible for deployment.

This creates stronger separation between:

```text id="5f3vxy"
SYSTEM THAT DEPLOYS
        ≠
SYSTEM THAT VERIFIES
```

---

### 83. Root of Trust

Integrity verification depends on a trusted starting point.

A **root of trust** is a trusted component or mechanism from which integrity decisions can be anchored.

Examples may include:

* Trusted signing keys.
* Hardware-backed keys.
* Trusted identity systems.
* Secure registries.

---

### 84. Key Protection

If digital signatures are used, signing keys become highly sensitive assets.

The organization should protect them against:

* Unauthorized access.
* Theft.
* Export.
* Misuse.
* Unauthorized signing.

A stolen signing key can allow an attacker to create artifacts that appear legitimate.

---

### 85. Key Rotation

Signing and encryption keys may require controlled rotation.

Key-management processes should define:

* Rotation frequency.
* Emergency rotation.
* Key revocation.
* Replacement.
* Historical verification.

---

### 86. Signature Revocation

If a signing key is compromised, previously trusted signatures may require reassessment.

The organization should have a mechanism to determine:

* Which artifacts were signed.
* Which key was used.
* Whether the key remained trusted.
* Whether affected artifacts need replacement.

---

### 87. Model Integrity and Supply Chain

Model integrity cannot be separated completely from supply-chain security.

A model may depend on:

* External libraries.
* Base models.
* Container images.
* Third-party datasets.
* External APIs.

A compromised upstream component can affect downstream integrity.

---

### 88. Trusted Dependencies

Organizations should maintain a trusted dependency process.

This may include:

* Approved sources.
* Version control.
* Vulnerability scanning.
* Integrity verification.
* Dependency inventories.

---

### 89. Dependency Verification

Before use, dependencies may be verified against approved versions.

```text id="g0k9rt"
Dependency
     ↓
Version Check
     ↓
Source Check
     ↓
Integrity Check
     ↓
Approved?
```

This helps reduce supply-chain risks.

### 90. Base Model Integrity

When an organization builds upon an existing model, the base model becomes part of the trust chain.

For example:

```text id="2x7k6m"

       ↓
Fine-Tuning
       ↓
Enterprise Model
```

If the base model is compromised or untrusted, downstream assurance becomes more difficult.

### 91. Model Import Controls

Models obtained from external sources should not automatically be placed into production.

An import process may require:

* Source verification.
* Provenance review.
* Security assessment.
* Malware analysis where applicable.
* Integrity verification.
* Approval.

### 92. External Model Repository Risk

External repositories may contain models that:

* Have unknown provenance.
* Include malicious components.
* Contain vulnerabilities.
* Have unclear licensing.
* Have been modified after publication.

The organization should establish approved acquisition channels.

### 93. Model Integrity and Data

Model integrity also depends indirectly on training-data integrity.

If an attacker modifies training data:

```text id="e7k8a2"

      ↓
Training
      ↓
Altered Model
```

The resulting model may technically be an authentic artifact, but its behavior may not represent the intended training process.

### 94. Model Integrity vs Data Integrity

These are separate but connected properties.

**Data integrity:**

> Has the data remained accurate and unaltered?

**Model integrity:**

> Has the approved model artifact remained unaltered?

Both may be required to maintain trustworthy model behavior.

### 95. Training Pipeline Integrity

```text id="w2c4qn"

      +

      +

      ↓
```

* Feature selection.
* Runtime parameters.
* Safety settings.
* API behavior.

A secure model with insecure configuration may still produce an unauthorized outcome.

### 97. Model Integrity and Infrastructure

Infrastructure can also affect model integrity.

Examples include:

* Operating system.
* Container runtime.
* Cloud infrastructure.
* Storage.
* Network controls.

If infrastructure is compromised, an attacker may potentially manipulate the model environment.

### 99. Integrity Alert Response

An integrity alert should trigger a defined response.

Possible actions include:

1. Validate whether the change was authorized.
2. Identify the changed component.

### 100. Integrity as a Governance Control

From a GRC perspective, model integrity should become a measurable control objective:

> **Production models must remain consistent with their authorized, validated, and approved state, and unauthorized changes must be prevented or detected within defined timeframes.**

### 101. Model Integrity Control Framework

A mature model integrity program should translate the integrity objective into a structured set of controls.

The framework can be organized into five control areas:

```text
                    MODEL INTEGRITY
                           │
       ┌───────────────────┼───────────────────┐
       ↓                   ↓                   ↓
    PREVENT              VERIFY              DETECT
       │                   │                   │
       └───────────────────┼───────────────────┘
                           ↓
                        RESPOND
                           ↓
                        RECOVER
```

This provides a complete control lifecycle rather than relying on a single technical mechanism.

---

### 102. Integrity Control Objectives

Typical control objectives include:

* Prevent unauthorized model modification.
* Ensure approved models can be identified.
* Verify model authenticity.
* Detect unauthorized changes.
* Maintain traceability.
* Support rapid recovery.
* Preserve evidence.
* Periodically reassess integrity controls.

### 103. Model Identification

Every enterprise model should have a unique identity.

A model record might contain:

```text
Model ID: MOD-00452
Model Name: Fraud Detection
Owner: Fraud Analytics
Version: 3.4
Environment: Production
Risk: High
Status: Approved
```

Unique identification prevents ambiguity between models and versions.

### 104. Model Version Control

Every material model change should result in a traceable version.

For example:

```text
v1.0
 ↓
v1.1
 ↓
v1.2
 ↓
v2.0
```

The organization should be able to determine:

* What changed.
* Why it changed.
* Who made the change.
* Who approved it.
* What testing was performed.

---

### 105. Immutable Version History

Previous approved versions should not simply be overwritten.

A stronger approach is:

```text

v1.1 → RETIRED
v1.2 → APPROVED
v2.0 → DEVELOPMENT
```

This preserves historical traceability.

### 106. Model Fingerprinting

A model can be represented through a cryptographic fingerprint.

For example:

```text

      ↓

      ↓

```

The fingerprint can be recorded as part of the model's security metadata.

### 107. Fingerprint Comparison

```text

        ↓
     Compare
        ↑
Current Fingerprint
```

A mismatch should trigger investigation.

---

### 108. Signed Model Artifacts

For stronger assurance, model artifacts can be digitally signed.

```text
Approved Artifact
       ↓
Trusted Signing Process
       ↓
Digital Signature
       ↓
Signed Artifact
```

The deployment system can then verify that the artifact was signed by an authorized source.

---

### 109. Artifact Verification Policy

An enterprise may define a rule such as:

> Production model artifacts must pass integrity verification before deployment.

The technical implementation can include:

* Signature verification.
* Hash verification.
* Registry verification.
* Version validation.

```text
Approved
```

| Registry Admin |    ✓ |      ✓ |       — | Restricted |

Production artifacts should receive stronger protection than development artifacts.

```text
   ↓
```

* Restricted write access.
* Immutable storage.

* Deployment verification.

```text
     ↓

     ↓

   ↓

   ↓
```

```text
   ↓

   ↓
```

### 118. Model Integrity Testing

### 130. Model Integrity and Zero Trust

Model integrity aligns with zero-trust principles.

* Authorization.
* Context.
* Integrity.

A model should not be considered trusted simply because it resides in:

* Corporate cloud.
* Private network.

### 132. Verify Before Use

A strong principle is:

* Update.
* Recovery.
* Migration.

Artifact-level verification remains important.

### 135. Model Integrity During Backup

### 151. Model Integrity Governance

Model integrity should be governed as an enterprise security requirement rather than treated only as an ML engineering concern.

* Model versions remain traceable.

| ----------------- | ---------------------------------------------- |

### 182. Model Integrity and Encryption

Encryption primarily protects confidentiality, but it can also support integrity when authenticated encryption mechanisms are used.

However:

> **Encryption should not be treated as a substitute for artifact authenticity and authorization.**

A perfectly encrypted malicious model is still a malicious model.

---

### 183. Authenticated Encryption

Authenticated encryption can provide confidentiality and integrity for protected data during storage or transmission.

However, model-security architecture may still require:

* Signing.
* Authorization.
* Version control.
* Provenance.

These controls address different trust questions.

### 194. Model Integrity Risk Statement

A formal risk statement could be:

### 195. Model Integrity Control Statement

A corresponding control statement could be:

> **Production model artifacts and associated security-relevant configurations shall be protected against unauthorized modification, verified against an approved baseline, and monitored for unauthorized changes.**

### 196. Model Integrity Assurance Statement

An assurance statement might be:

> **The organization maintains mechanisms to establish, verify, monitor, and preserve the integrity of production models throughout their operational lifecycle.**

---

### 197. Model Integrity Maturity

A practical maturity progression is:

**Level 1 — Ad Hoc**

Models are stored and deployed without consistent integrity controls.

**Level 2 — Basic**

Versioning and access controls exist.

**Level 3 — Managed**

Hashes, approvals, controlled deployment, and logging are implemented.

**Level 4 — Measured**

Integrity verification and monitoring are measured and audited.

**Level 5 — Optimized**

Integrity verification is automated across the lifecycle with strong cryptographic trust, continuous monitoring, and rapid recovery.

### 199. Enterprise Model Integrity Principle

The enterprise should be able to answer five fundamental questions:

```text id="k6r2xp"
1. WHAT model is this?
2. WHO authorized it?
3. HAS it changed?
4. WHO changed it?
5. CAN we recover a trusted version?
```

If the organization cannot reliably answer these questions, model integrity governance is incomplete.

### 200. Model Integrity — GRC Perspective

Model integrity ultimately connects **technical trust** with **enterprise accountability**.

A mature organization does not simply assume that a model is trustworthy because it resides inside an approved environment.

Instead, it establishes trust through:

```text id="v4q7cw"
IDENTITY
   +
AUTHORIZATION
   +
VERSION CONTROL
   +
CRYPTOGRAPHIC VERIFICATION
   +
SECURE DEPLOYMENT
   +
MONITORING
   +
AUDITABILITY
   +
RECOVERY
```

The fundamental principle is:

> **Trust in a model must be established, verified, maintained, and continuously reassessed.**

Model integrity therefore becomes a lifecycle-wide security control that protects the model from unauthorized modification while providing the organization with evidence that the model operating in production remains the model that was actually **developed, validated, approved, and authorized**.
