# 09.09 — Adversarial Machine Learning

## Part 1

### 1. Adversarial Machine Learning

Adversarial Machine Learning (AML) is the study and practice of understanding how machine-learning systems can be attacked, manipulated, deceived, or otherwise compromised through deliberately crafted inputs, training data, model interactions, or system behavior.

The fundamental security concern is that an attacker can intentionally influence the machine-learning lifecycle in ways that cause the model to behave incorrectly or outside its intended security boundaries.

```text id="aml09p1"
Attacker
   ↓
Manipulated Data / Input
   ↓
ML System
   ↓
Unexpected Model Behavior
   ↓
Business / Security Impact
```

---

### 2. The Adversarial Nature of Machine Learning

Traditional software security generally focuses on exploiting implementation weaknesses.

Machine-learning security introduces another dimension:

> The attacker may manipulate the data or inputs that the model uses to make decisions.

This means a model can be technically functioning as designed while still producing an attacker-induced outcome.

---

### 3. Machine Learning as an Attack Surface

An ML system should be treated as an additional attack surface within an enterprise architecture.

```text id="aml09p3"
Enterprise System
      │
      ├── Applications
      ├── Networks
      ├── APIs
      ├── Databases
      └── ML Models
              ↓
        ML Attack Surface
```

The model should therefore be incorporated into the organization's security architecture and threat model.

---

### 4. Adversarial Objective

An adversary may attempt to influence a model for different purposes.

Possible objectives include:

* Causing incorrect predictions.
* Evading detection.
* Triggering unauthorized actions.
* Manipulating classifications.
* Degrading model availability.
* Corrupting training data.
* Influencing future model behavior.
* Extracting sensitive information.

---

### 5. Security Impact

The impact of adversarial ML depends on how the model is used.

A manipulated recommendation may have limited consequences.

A manipulated security model could potentially result in:

* Unauthorized access.
* Fraud.
* Security-control bypass.
* Incorrect risk decisions.
* Malicious transactions being approved.

Therefore, model security must be evaluated in its business context.

---

### 6. ML Security Is Broader Than Model Security

Adversarial ML encompasses more than the trained model itself.

The relevant environment includes:

```text id="aml09p6"
Data
 ↓
Training
 ↓
Model
 ↓
Inference
 ↓
Application
 ↓
Business Decision
```

An attack against any relevant stage may ultimately affect model security.

---

### 7. Adversarial ML Lifecycle

A useful security perspective is to consider the entire ML lifecycle.

```text id="aml09p7"
Data Collection
      ↓
Data Preparation
      ↓
Training
      ↓
Validation
      ↓
Deployment
      ↓
Inference
      ↓
Monitoring
      ↓
Retraining
```

Each stage can introduce different adversarial opportunities.

---

### 8. Training-Time Attacks

Training-time attacks attempt to influence the model before or during training.

Potential objectives include:

* Corrupting training data.
* Introducing malicious examples.
* Altering labels.
* Creating backdoors.
* Manipulating training pipelines.

These attacks can affect the model before it reaches production.

---

### 9. Inference-Time Attacks

Inference-time attacks occur when the model is already deployed.

The attacker manipulates inputs presented to the model.

```text id="aml09p9"
Legitimate Input
        ↓
       Model
        ↓
    Prediction
```

versus:

```text id="aml09p9b"
Adversarial Input
        ↓
       Model
        ↓
Incorrect Prediction
```

---

### 10. Evasion

Evasion attacks attempt to cause a deployed model to misclassify or overlook malicious or undesirable input.

The attacker changes the input while preserving its usefulness for the attacker's objective.

A common security example is attempting to make malicious activity appear legitimate to a detection model.

---

### 11. Poisoning

Poisoning attacks target the training process.

The attacker attempts to introduce manipulated data that changes the model's learned behavior.

```text id="aml09p11"
Legitimate Training Data
          +
Malicious Training Data
          ↓
      Training
          ↓
    Compromised Model
```

---

### 12. Backdoor Attacks

A backdoor attack attempts to create hidden behavior that activates when a particular condition or trigger appears.

Conceptually:

```text id="aml09p12"
Normal Input
    ↓
Normal Prediction

Trigger + Input
    ↓
Unexpected Prediction
```

The model may appear normal during ordinary testing while behaving differently when the trigger is present.

---

### 13. Model Manipulation

An attacker may attempt to modify an existing model artifact, configuration, parameters, or associated components.

The objective may be to alter model behavior without authorization.

---

### 14. Model Tampering

Model artifacts should therefore be treated as security-sensitive assets.

Potential protections include:

* Integrity verification.
* Digital signatures.
* Access control.
* Secure storage.
* Version control.
* Deployment validation.

---

### 15. Adversarial Examples

An adversarial example is an input deliberately modified to cause a model to produce an incorrect or undesirable result.

Conceptually:

```text id="aml09p15"
Original Input
      ↓
Small / Carefully Designed Modification
      ↓
Adversarial Example
      ↓
Model
      ↓
Incorrect Prediction
```

The modification may be difficult for a human observer to recognize while still affecting the model.

---

### 16. Human-Model Perception Gap

One of the important characteristics of adversarial examples is that humans and ML models may perceive the same input differently.

```text id="aml09p16"
Human
 ↓
"Looks Normal"

Model
 ↓
"Classified Differently"
```

This difference creates a unique security challenge.

---

### 17. Image Classification Example

Consider an image-classification system.

An attacker may make a carefully designed modification to an image so that:

```text id="aml09p17"
Human → Correct Object

Model → Incorrect Classification
```

The objective is not necessarily to make the image visibly meaningless.

---

### 18. Security-Camera Example

A computer-vision security system may identify objects, people, vehicles, or suspicious activity.

An attacker could attempt to manipulate the visual input so the system produces an incorrect classification.

The resulting security impact depends on whether the prediction controls a consequential decision.

---

### 19. Malware Detection Example

An ML-based malware detector may classify files according to learned characteristics.

An attacker may attempt to alter a malicious file so that its observable characteristics resemble benign software.

```text id="aml09p19"
Malicious File
      ↓
Adversarial Modification
      ↓
ML Detector
      ↓
"Benign"
```

This is an example of an evasion objective.

---

### 20. Spam Detection Example

An attacker may manipulate a malicious message so that it resembles legitimate communications.

```text id="aml09p20"
Malicious Message
       ↓
Input Manipulation
       ↓
Spam Classifier
       ↓
"Legitimate"
```

The attacker is attempting to evade the model's classification.

---

### 21. Fraud Detection Example

Fraud detection models may evaluate:

* Transactions.
* User behavior.
* Device information.
* Geographic information.
* Historical patterns.

An attacker may attempt to alter observable characteristics to reduce the likelihood that the transaction is classified as fraudulent.

---

### 22. Authentication Systems

ML may be used in:

* Behavioral authentication.
* Facial recognition.
* Voice recognition.
* Risk-based authentication.

Adversarial manipulation may attempt to cause an unauthorized individual to be recognized as legitimate.

---

### 23. Biometric Systems

Biometric ML systems are particularly sensitive because model decisions can influence identity verification.

Security assessment should consider whether an attacker can manipulate:

* Images.
* Audio.
* Video.
* Sensor inputs.
* Presentation characteristics.

---

### 24. Autonomous Systems

ML models can influence autonomous or semi-autonomous systems.

Potential environments include:

* Vehicles.
* Industrial systems.
* Drones.
* Robotics.
* Security systems.

In these environments, an incorrect prediction can potentially produce a physical consequence.

---

### 25. Critical Decision Systems

The higher the consequence of a model's decision, the greater the importance of adversarial robustness.

```text id="aml09p25"
Model Prediction
      ↓
Automated Decision
      ↓
Operational Action
      ↓
Potential Impact
```

A security assessment should therefore consider the complete decision chain.

---

### 26. Attack Surface Categories

Adversarial ML threats can broadly be organized into several categories:

| Category             | Objective                         |
| -------------------- | --------------------------------- |
| Evasion              | Manipulate inference inputs       |
| Poisoning            | Manipulate training               |
| Backdoor             | Introduce hidden trigger behavior |
| Extraction           | Reproduce model behavior          |
| Inversion            | Infer training information        |
| Membership inference | Determine training participation  |
| Tampering            | Alter model artifacts             |

These categories can overlap in complex attacks.

---

### 27. Attack Lifecycle

An adversarial campaign may follow a sequence such as:

```text id="aml09p27"
Reconnaissance
      ↓
Model Understanding
      ↓
Attack Development
      ↓
Input / Data Manipulation
      ↓
Model Interaction
      ↓
Observe Result
      ↓
Adapt Attack
```

The exact sequence depends on the attack type.

---

### 28. Reconnaissance

Before attempting an attack, an adversary may seek information about:

* Model purpose.
* Input format.
* Output format.
* Model architecture.
* Model version.
* Available APIs.
* Security controls.
* Training characteristics.

---

### 29. Model Knowledge

Adversarial ML attacks can be classified according to how much the attacker knows about the target.

Possible levels include:

* Black-box.
* Gray-box.
* White-box.

---

### 30. Black-Box Scenario

In a black-box scenario, the attacker does not have access to the model's internal parameters.

The interaction may look like:

```text id="aml09p30"
Input
  ↓
Target Model
  ↓
Output
```

The attacker learns primarily from observable behavior.

---

### 31. Gray-Box Scenario

A gray-box attacker has partial information.

For example, the attacker may know:

* Model type.
* Input structure.
* General architecture.
* Output classes.

But the attacker may not have the model parameters.

---

### 32. White-Box Scenario

A white-box attacker has significant internal knowledge or access.

Potentially available information could include:

* Model architecture.
* Parameters.
* Gradients.
* Weights.
* Training configuration.
* Model artifacts.

This can make certain attacks substantially easier to design.

---

### 33. Transferability

Some adversarial examples created against one model may also affect another model.

This property is commonly referred to as **transferability**.

```text id="aml09p33"
Source Model
     ↓
Adversarial Example
     ↓
Target Model
     ↓
Potential Misclassification
```

This is significant because an attacker may not require direct access to the target model during attack development.

---

### 34. Surrogate Models

An attacker can sometimes develop a surrogate model that approximates the target model.

The surrogate may then be used to develop candidate adversarial inputs.

```text id="aml09p34"
Target Model
   ↓
Observed Behavior
   ↓
Surrogate Model
   ↓
Attack Development
   ↓
Target Model
```

---

### 35. Query-Based Attacks

When a model can be queried, attackers may use responses to learn about its decision behavior.

Repeated interaction can reveal information about:

* Decision boundaries.
* Confidence.
* Classification patterns.
* Input sensitivity.

---

### 36. Decision Boundary

A model's decision boundary separates regions of input space associated with different predictions.

An attacker may attempt to identify areas near the boundary where small changes can cause a different classification.

```text id="aml09p36"
Class A
──────────────
      ↑
Decision Boundary
      ↓
──────────────
Class B
```

---

### 37. Input Sensitivity

Some models are highly sensitive to particular input characteristics.

An attacker may identify these characteristics and manipulate them to influence predictions.

Security testing should therefore consider sensitivity to realistic perturbations.

---

### 38. Perturbation

A perturbation is a change made to an input.

It can be:

* Digital.
* Physical.
* Numerical.
* Visual.
* Audio-based.
* Textual.

The security relevance depends on whether the modification changes the model's decision.

---

### 39. Digital Perturbations

Digital perturbations occur directly within the data presented to the model.

Examples include modifications to:

* Image pixels.
* Text.
* Audio signals.
* Numerical features.
* File characteristics.

---

### 40. Physical Perturbations

Physical-world attacks attempt to create adversarial conditions that survive real-world processes.

For example, a visual system may receive an object through a camera rather than directly receiving a digital image.

This creates additional environmental variables.

---

### 41. Physical-World Robustness

A model may perform well against digitally generated adversarial examples but behave differently under physical conditions.

Security testing should therefore consider realistic deployment conditions where appropriate.

---

### 42. Environmental Factors

Physical ML systems may encounter:

* Lighting changes.
* Camera angle.
* Distance.
* Noise.
* Weather.
* Occlusion.
* Sensor variation.

These conditions can influence model robustness.

---

### 43. Evasion Against Security Controls

Adversarial ML becomes especially important when the model itself performs a security function.

Examples include:

* Intrusion detection.
* Fraud detection.
* Malware detection.
* Spam filtering.
* Identity verification.
* Phishing detection.

An attacker may deliberately target the model because bypassing it creates a path around another security control.

---

### 44. Security Control Dependency

Organizations should identify whether critical controls depend on ML predictions.

```text id="aml09p44"
Threat
  ↓
ML Detection
  ↓
Security Decision
  ↓
Control Action
```

If the model fails, the downstream control may also fail.

---

### 45. Cascading Failure

An ML prediction may feed another system.

```text id="aml09p45"
Model A
   ↓
Risk Score
   ↓
Model B / Rule Engine
   ↓
Automated Decision
```

An adversarial manipulation at the first stage can therefore propagate through the system.

---

### 46. Model Dependency Mapping

Security teams should document dependencies between:

* Models.
* APIs.
* Applications.
* Data sources.
* Decision engines.
* Human operators.

This helps identify where an adversarial model failure could propagate.

---

### 47. Human-in-the-Loop Systems

Not all ML decisions are fully automated.

A model may produce a recommendation that a human reviews.

```text id="aml09p47"
Model
 ↓
Recommendation
 ↓
Human Review
 ↓
Decision
```

Human review can reduce some risks but should not be assumed to eliminate adversarial influence.

---

### 48. Automation Level

The level of automation should influence risk classification.

```text id="aml09p48"
Advisory
   ↓
Human-Assisted
   ↓
Semi-Automated
   ↓
Fully Automated
```

Higher automation can increase the consequences of model manipulation.

---

### 49. Attack Impact Classification

Organizations can classify adversarial ML impacts according to:

* Confidentiality.
* Integrity.
* Availability.
* Privacy.
* Safety.
* Financial impact.
* Regulatory impact.

This allows AML to integrate with established enterprise risk frameworks.

---

### 50. Integrity Risk

Many adversarial ML attacks primarily affect integrity.

The core issue is:

```text id="aml09p50"
Expected Prediction
        ≠
Actual Prediction
```

When the incorrect prediction influences an important decision, the integrity failure becomes a business risk.

---

### 51. Availability Risk

An attacker may also attempt to degrade the usefulness or availability of an ML service.

Possible objectives include:

* Causing excessive processing.
* Triggering resource consumption.
* Generating abnormal workloads.
* Preventing legitimate inference.

---

### 52. Confidentiality Risk

Adversarial ML can also create confidentiality risks.

Certain attacks attempt to extract information about:

* Training data.
* Model parameters.
* Sensitive records.
* Proprietary model behavior.

---

### 53. Privacy Risk

Privacy-related adversarial attacks can attempt to determine information about individuals represented in training data.

This connects adversarial ML with:

* Model inversion.
* Membership inference.
* Data leakage.

---

### 54. Safety Risk

When ML influences physical systems, adversarial manipulation can become a safety concern.

Examples include:

* Autonomous vehicles.
* Industrial control.
* Medical systems.
* Robotics.

Safety analysis should therefore extend beyond traditional cybersecurity impact.

---

### 55. Threat Actor Categories

Potential adversaries include:

* Cybercriminals.
* Nation-state actors.
* Competitors.
* Malicious insiders.
* Researchers.
* Fraudsters.
* Hacktivists.
* Compromised third parties.

The relevant threat actors depend on the organization's business environment.

---

### 56. Attacker Motivation

Motivations may include:

* Financial gain.
* Fraud.
* Espionage.
* Competitive advantage.
* Security bypass.
* Disruption.
* Data acquisition.
* Reputation damage.

Understanding motivation helps prioritize realistic attack scenarios.

---

### 57. Insider Threat

Employees or contractors with legitimate access may have greater knowledge of:

* Model behavior.
* Training processes.
* Data sources.
* Deployment architecture.
* Security controls.

Insider threats should therefore be considered in adversarial ML threat modeling.

---

### 58. Compromised Accounts

An attacker may obtain legitimate credentials for an ML platform or application.

The attacker can then operate within the permissions assigned to the compromised identity.

This makes identity security an important component of AML defense.

---

### 59. Compromised ML Pipeline

A software or data pipeline may also become an attack target.

```text id="aml09p59"
Source
 ↓
Data Pipeline
 ↓
Training
 ↓
Model Registry
 ↓
Deployment
```

Compromise at any stage may influence the final model.

---

### 60. Supply-Chain Exposure

Third-party components can introduce additional adversarial ML risks.

Potential dependencies include:

* Datasets.
* Pre-trained models.
* ML libraries.
* Training infrastructure.
* Model repositories.
* External APIs.

The security of the complete ML supply chain therefore matters.

---

### 61. Pre-Trained Models

Organizations frequently build systems using pre-trained models.

These models may originate from:

* Internal teams.
* Vendors.
* Open-source projects.
* Public model repositories.
* Commercial AI providers.

The organization should assess their provenance and integrity before deployment.

---

### 62. Model Provenance

Model provenance establishes where a model came from and how it was produced.

Relevant information can include:

* Source.
* Creator.
* Training lineage.
* Version.
* Modifications.
* Dependencies.
* Approval history.

---

### 63. Model Integrity

Organizations should verify that the model deployed into production is the approved artifact.

```text id="aml09p63"
Approved Model
      ↓
Integrity Verification
      ↓
Deployment
```

Unexpected modifications should trigger investigation.

---

### 64. Cryptographic Verification

Cryptographic mechanisms can help establish artifact integrity.

Examples include:

* Hashes.
* Digital signatures.
* Signed model manifests.

These controls help detect unauthorized modifications.

---

### 65. Secure Model Registry

A model registry should provide controlled management of model artifacts.

Security capabilities may include:

* Authentication.
* Authorization.
* Version control.
* Audit logging.
* Artifact integrity.
* Approval workflows.

---

### 66. Deployment Verification

Before deployment, organizations should verify:

* Model identity.
* Version.
* Integrity.
* Dependencies.
* Configuration.
* Approval status.

This reduces the risk of deploying an unauthorized model.

---

### 67. Configuration Security

The model may be secure while its deployment configuration is not.

Relevant configurations include:

* Input preprocessing.
* Output handling.
* Thresholds.
* Feature mappings.
* Model endpoints.
* Authentication settings.

Configuration changes should therefore be governed.

---

### 68. Threshold Manipulation

Many ML systems use thresholds to convert model scores into decisions.

For example:

```text id="aml09p68"
Risk Score
    ↓
Threshold
    ↓
Approve / Reject
```

Unauthorized threshold modification could change the security behavior of the entire system.

---

### 69. Feature Manipulation

If an attacker can influence model features, they may be able to influence the resulting prediction.

Therefore, security controls should protect both:

* The model.
* The data pipeline feeding the model.

---

### 70. Feature Integrity

Organizations should validate important features where appropriate.

Controls can include:

* Input validation.
* Schema enforcement.
* Range checks.
* Source validation.
* Anomaly detection.

---

### 71. Data Validation

Training and inference data should be subject to appropriate validation.

```text id="aml09p71"
Incoming Data
      ↓
Validation
      ↓
Approved Data
      ↓
Model
```

The validation layer can reduce opportunities for malformed or manipulated data to influence decisions.

---

### 72. Data Provenance

The organization should understand where model inputs originate.

Questions include:

* Who generated the data?
* Which system supplied it?
* Has it been transformed?
* Was it validated?
* Can its integrity be established?

---

### 73. Trust Boundaries

ML architectures should explicitly identify trust boundaries.

```text id="aml09p73"
Untrusted Input
       │
       ↓
[ Validation Boundary ]
       │
       ↓
Trusted Processing
       │
       ↓
Model
```

This is especially important when model inputs originate outside the organization's control.

---

### 74. External Inputs

Examples of external model inputs include:

* Customer submissions.
* Internet content.
* Uploaded files.
* Images.
* Emails.
* Third-party feeds.
* User-generated content.

These inputs should not automatically be considered trustworthy.

---

### 75. Input Validation

Input validation should ensure that data conforms to expected requirements.

Potential checks include:

* Format.
* Size.
* Type.
* Range.
* Encoding.
* Schema.
* Content constraints.

---

### 76. Input Sanitization

Where appropriate, systems may transform or sanitize incoming data before it reaches the model.

However, sanitization should be designed carefully because excessive transformation can reduce legitimate model functionality.

---

### 77. Preprocessing Security

Preprocessing is part of the model's effective security boundary.

For example:

```text id="aml09p77"
Raw Input
 ↓
Preprocessing
 ↓
Feature Extraction
 ↓
Model
```

An attacker may target preprocessing rather than the model itself.

---

### 78. Feature Engineering

Feature engineering can introduce security assumptions.

If a feature depends on attacker-controlled data, the attacker may attempt to manipulate the feature before it reaches the model.

---

### 79. Data Pipeline Security

ML pipelines should receive controls comparable to other critical enterprise data pipelines.

These may include:

* Identity controls.
* Access restrictions.
* Integrity checks.
* Logging.
* Monitoring.
* Change management.

---

### 80. Change Management

Changes to:

* Models.
* Datasets.
* Features.
* Algorithms.
* Thresholds.
* Preprocessing

should follow appropriate change-management procedures.

Unexpected changes can alter the model's security posture.

---

### 81. Adversarial Testing

Adversarial testing evaluates how a model behaves under intentionally manipulated conditions.

The objective is to identify weaknesses before an attacker exploits them.

---

### 82. Security Test Categories

Testing may cover:

* Evasion.
* Poisoning.
* Robustness.
* Input manipulation.
* Model integrity.
* Access control.
* Data leakage.

---

### 83. Red Teaming

AI red teams can simulate realistic adversarial behavior against ML systems.

A red-team exercise may evaluate:

```text id="aml09p83"
Reconnaissance
      ↓
Attack Development
      ↓
Controlled Attack
      ↓
Detection
      ↓
Response
```

---

### 84. Purple Teaming

Purple-team activities can combine offensive testing with defensive monitoring.

The objective is to determine not only whether an attack succeeds, but whether the organization can detect and respond to it.

---

### 85. Detection Engineering

Security teams should develop detections for unusual ML behavior.

Potential signals include:

* Abnormal model queries.
* Unexpected input distributions.
* Sudden prediction changes.
* Unusual model access.
* Unauthorized model changes.

---

### 86. Behavioral Baselines

Normal model behavior should be established where practical.

```text id="aml09p86"
Normal Behavior
      ↓
Baseline
      ↓
Anomaly Detection
```

A baseline allows security teams to identify significant deviations.

---

### 87. Prediction Distribution Monitoring

A sudden change in the distribution of model predictions may indicate:

* Data drift.
* Pipeline failure.
* Model degradation.
* Adversarial manipulation.

The signal should therefore be investigated rather than automatically attributed to an attack.

---

### 88. Input Distribution Monitoring

Changes in input characteristics may also indicate unusual activity.

For example:

```text id="aml09p88"
Normal Input Distribution
          ↓
Sudden Shift
          ↓
Investigation
```

---

### 89. Model Performance Monitoring

Security teams should monitor whether model performance changes unexpectedly.

Relevant indicators can include:

* Accuracy.
* Precision.
* Recall.
* False-positive rate.
* False-negative rate.
* Business-specific performance metrics.

---

### 90. Security vs Performance

A model may continue operating technically while its security effectiveness deteriorates.

For example, an ML-based fraud detector could remain available while becoming increasingly ineffective against manipulated transactions.

Availability alone is therefore insufficient.

---

### 91. Resilience

Model resilience refers to the ability of an ML system to continue performing acceptably under unexpected or malicious conditions.

Resilience can involve:

* Robust model design.
* Input validation.
* Monitoring.
* Fallback mechanisms.
* Human review.
* Incident response.

---

### 92. Defense in Depth

Adversarial ML defense should not depend on a single mechanism.

```text id="aml09p92"
Secure Data
    +
Secure Pipeline
    +
Robust Model
    +
Input Validation
    +
Access Control
    +
Monitoring
    +
Human Oversight
    +
Incident Response
```

---

### 93. Fail-Safe Design

Critical ML-enabled systems should consider what happens when the model is uncertain or unavailable.

Possible responses include:

* Human review.
* Secondary detection mechanism.
* Rule-based fallback.
* Transaction hold.
* Safe-state operation.

---

### 94. Confidence Handling

Low-confidence predictions may warrant additional controls in high-impact applications.

```text id="aml09p94"
High Confidence
      ↓
Normal Processing

Low Confidence
      ↓
Additional Validation
```

---

### 95. Ensemble Approaches

Some systems use multiple models or complementary detection mechanisms.

The objective may be to reduce dependence on a single model's decision.

---

### 96. Model Diversity

Different models may fail differently.

Using sufficiently diverse detection mechanisms can reduce the likelihood that one adversarial technique defeats every layer.

---

### 97. Rule-Based Controls

Traditional security rules can complement ML-based detection.

```text id="aml09p97"
ML Detection
     +
Rule-Based Detection
     ↓
Combined Security Decision
```

This can provide defense in depth.

---

### 98. Human Oversight

Human review can provide an additional control for high-impact decisions.

However, reviewers should have sufficient context and authority to challenge model outputs.

---

### 99. Enterprise Risk Perspective

Adversarial ML should ultimately be evaluated in terms of business risk.

The key question is not simply:

> “Can the model be attacked?”

A more useful enterprise question is:

> **“What happens to the organization if an attacker successfully manipulates this model?”**

---

### 100. Core Principle

Adversarial Machine Learning recognizes that machine-learning systems must be defended not only against traditional infrastructure attacks, but also against **intentional manipulation of data, inputs, model behavior, and decision processes**.

The fundamental security relationship is:

```text id="aml09p100"
Attacker
    ↓
Data / Input / Model / Pipeline
    ↓
ML System
    ↓
Manipulated Behavior
    ↓
Decision
    ↓
Business / Security Impact
```

A secure ML program must therefore treat the model as part of a larger security system and evaluate adversarial threats across the complete lifecycle—from data acquisition and training through deployment, inference, monitoring, and ongoing model change.

## Part 2

### 101. Adversarial Machine Learning Threat Model

A formal adversarial ML threat model identifies the relationship between the attacker, the ML system, the attacker's capabilities, and the desired impact.

```text
Threat Actor
     ↓
Capabilities
     ↓
Attack Surface
     ↓
Attack Technique
     ↓
Model Behavior
     ↓
Business Impact
```

The purpose is to establish what an attacker can realistically manipulate and what consequences could result.

---

### 102. Adversary Knowledge

The attacker's knowledge can significantly influence the threat.

An attacker may know:

* The model's purpose.
* Input requirements.
* Output format.
* Model family.
* Model architecture.
* Training data characteristics.
* Feature engineering.
* Decision thresholds.
* Deployment environment.

Security assessments should distinguish between realistic and unrealistic attacker assumptions.

---

### 103. Adversary Capability

Threat modeling should also define what the attacker can do.

Examples include:

* Submit inputs.
* Modify user-controlled data.
* Query an API.
* Access training data.
* Modify pipeline components.
* Access model artifacts.
* Influence third-party data sources.
* Obtain legitimate credentials.

---

### 104. Adversary Access

Access can be categorized according to the attacker's position.

```text id="aml104"
External
   ↓
Authenticated User
   ↓
Internal User
   ↓
Developer
   ↓
ML Engineer
   ↓
Administrator
```

Greater access generally provides more opportunities for manipulation, although external attacks can still be highly effective.

---

### 105. Black-Box Threat Model

In a black-box scenario, the attacker interacts primarily through the exposed interface.

```text id="aml105"
Attacker
   ↓
API / Application
   ↓
Model
   ↓
Prediction
```

The attacker does not have direct access to internal model parameters.

---

### 106. Gray-Box Threat Model

A gray-box attacker possesses partial internal knowledge.

For example, they may know the:

* Model family.
* Input features.
* Output classes.
* Approximate architecture.
* General training approach.

---

### 107. White-Box Threat Model

A white-box attacker has substantial knowledge of the model.

Potentially exposed information includes:

* Parameters.
* Weights.
* Architecture.
* Gradients.
* Training configuration.
* Model artifacts.

This scenario is particularly relevant to insider threats and compromised ML environments.

---

### 108. Attacker Goals

The same model may face different attacks depending on the attacker's objective.

Common goals include:

| Goal            | Example                        |
| --------------- | ------------------------------ |
| Evasion         | Avoid malicious classification |
| Integrity       | Cause incorrect predictions    |
| Poisoning       | Corrupt future model behavior  |
| Backdoor        | Create hidden trigger behavior |
| Availability    | Disrupt model operation        |
| Confidentiality | Extract sensitive information  |
| Fraud           | Manipulate automated decisions |

---

### 109. Attack Surface Mapping

The ML attack surface should be mapped across the complete architecture.

```text id="aml109"
Data Sources
    ↓
Data Pipeline
    ↓
Feature Store
    ↓
Training Environment
    ↓
Model Registry
    ↓
Deployment Platform
    ↓
Inference API
    ↓
Application
    ↓
Business Decision
```

Each component may introduce different attack opportunities.

---

### 110. Data Source Attacks

Data sources may be manipulated before reaching the training pipeline.

Potential sources include:

* User-generated content.
* External feeds.
* Sensors.
* Web data.
* Third-party databases.
* Customer submissions.

Data provenance and integrity therefore become important security controls.

---

### 111. Data Pipeline Attacks

The data pipeline can be targeted to alter:

* Records.
* Labels.
* Features.
* Sampling.
* Filtering.
* Transformation.

Pipeline compromise can therefore influence the model indirectly.

---

### 112. Feature Store Attacks

Where organizations use centralized feature stores, unauthorized modification of features could influence both training and inference.

Security controls should protect:

* Feature definitions.
* Feature values.
* Access permissions.
* Version history.
* Data lineage.

---

### 113. Training Environment Attacks

The training environment may contain:

* Source code.
* Training data.
* Credentials.
* Model artifacts.
* Configuration.
* Compute resources.

Compromise of this environment can have significant consequences.

---

### 114. Training Code Integrity

Training code should be treated as a security-sensitive artifact.

Unauthorized code changes could:

* Alter training behavior.
* Change datasets.
* Introduce malicious logic.
* Modify model outputs.
* Create hidden behaviors.

---

### 115. Dependency Attacks

Training environments often depend on external libraries.

A compromised dependency can potentially affect:

* Data processing.
* Training.
* Model generation.
* Model serialization.
* Deployment.

Software supply-chain security therefore applies directly to ML systems.

---

### 116. Model Registry Attacks

A model registry is a critical trust point.

An attacker who can replace an approved model with a malicious artifact could compromise production behavior.

```text id="aml116"
Approved Model
      ↓
Model Registry
      ↓
Production
```

The registry must protect model integrity and authorization.

---

### 117. Model Artifact Tampering

Model files should be protected against unauthorized modification.

Controls can include:

* Cryptographic hashes.
* Digital signatures.
* Immutable storage.
* Access control.
* Versioning.
* Deployment verification.

---

### 118. Deployment Pipeline Attacks

The CI/CD or ML deployment pipeline may also be targeted.

```text id="aml118"
Model
 ↓
CI/CD
 ↓
Validation
 ↓
Deployment
```

Security controls should ensure that only approved artifacts reach production.

---

### 119. Inference API Attacks

The inference interface is often the most exposed part of an ML system.

Attackers may attempt to:

* Send malicious inputs.
* Abuse query volume.
* Discover decision behavior.
* Manipulate features.
* Exploit weak authentication.
* Exploit application-layer vulnerabilities.

---

### 120. Input Manipulation

Input manipulation is central to many adversarial ML attacks.

The attacker attempts to create an input that satisfies the application's interface while producing an undesirable model outcome.

---

### 121. Malicious Feature Values

If users can directly or indirectly control features, they may attempt to manipulate them.

For example:

```text id="aml121"
Legitimate Transaction
        ↓
Feature Manipulation
        ↓
Lower Risk Score
        ↓
Approval
```

The security boundary therefore includes the feature-generation process.

---

### 122. Feature Trust

Every feature should ideally have a defined trust classification.

For example:

| Feature                       | Trust                 |
| ----------------------------- | --------------------- |
| Internal system-generated ID  | High                  |
| Authenticated account history | High/Medium           |
| Customer-provided value       | Lower                 |
| External third-party feed     | Depends on validation |
| User-entered metadata         | Lower                 |

The classification should influence validation requirements.

---

### 123. Input Constraints

Security controls should enforce appropriate constraints on model inputs.

Examples include:

* Data type validation.
* Range validation.
* Schema validation.
* Length restrictions.
* Encoding validation.
* Required-field validation.

---

### 124. Out-of-Distribution Inputs

Models may receive inputs significantly different from their training distribution.

These are commonly described as out-of-distribution inputs.

```text id="aml124"
Training Distribution
       ↓
Expected Input

Different Distribution
       ↓
Potentially Unreliable Prediction
```

---

### 125. OOD Detection

Where appropriate, systems can attempt to identify inputs that fall outside expected distributions.

Such detection should be treated as a supporting security mechanism rather than a universal defense.

---

### 126. Distribution Shift

Not every distribution shift is malicious.

Changes can result from:

* Seasonality.
* Business changes.
* New customers.
* New technologies.
* Market changes.
* Genuine environmental changes.

Security monitoring should therefore distinguish potential attacks from legitimate change.

---

### 127. Adversarial Distribution Shift

An attacker may intentionally manipulate input distributions to influence model behavior.

This can make distinguishing attack activity from natural drift more difficult.

---

### 128. Evasion Attack Lifecycle

A conceptual evasion attack can be represented as:

```text id="aml128"
Target Model
     ↓
Understand Behavior
     ↓
Construct Candidate Input
     ↓
Submit Input
     ↓
Observe Prediction
     ↓
Modify Input
     ↓
Repeat
```

The attack may be iterative.

---

### 129. Query Feedback

When a model provides detailed feedback, it can help an attacker refine inputs.

For example, richer outputs can reveal more about:

* Confidence.
* Class probabilities.
* Ranking.
* Decision thresholds.

Output minimization can therefore reduce attack information.

---

### 130. Decision-Only Models

Some systems return only a final decision.

```text id="aml130"
Input
 ↓
Model
 ↓
ALLOW / BLOCK
```

This provides less information than a system returning a detailed probability distribution.

---

### 131. Confidence Scores

A confidence score can be operationally useful but may also provide additional information to an attacker.

Organizations should evaluate whether the precision of confidence information is necessary.

---

### 132. API Rate Limiting

Rate limiting can restrict systematic probing.

Possible controls include:

* Requests per minute.
* Requests per account.
* Requests per IP.
* Adaptive throttling.
* Quotas.

Rate limiting is not a complete AML defense, but it can make repeated probing more difficult.

---

### 133. Authentication

Sensitive model endpoints should require appropriate authentication.

Anonymous access should only be permitted where the business purpose genuinely requires it.

---

### 134. Authorization

Authentication establishes identity.

Authorization determines what that identity is permitted to do.

```text id="aml134"
Identity
  ↓
Authentication
  ↓
Authorization
  ↓
Model Access
```

---

### 135. Least Privilege

Model access should follow the principle of least privilege.

Users and services should receive only the permissions required for their legitimate function.

---

### 136. Service-to-Service Security

ML models frequently communicate with other enterprise services.

These connections should be protected through:

* Strong service identities.
* Mutual authentication where appropriate.
* Authorization.
* Encryption.
* Logging.

---

### 137. API Gateway Controls

An API gateway can provide centralized controls around model endpoints.

Potential controls include:

* Authentication.
* Rate limiting.
* Request validation.
* Logging.
* Threat detection.
* Access policies.

---

### 138. WAF and Application Security

Where the model is exposed through a web application, conventional application-security controls remain important.

Adversarial ML security does not replace:

* Secure coding.
* WAF controls.
* API security.
* Authentication.
* Authorization.
* Vulnerability management.

---

### 139. Defense Against Input Abuse

Input controls should combine traditional application security with ML-specific validation.

```text id="aml139"
Request
 ↓
Application Validation
 ↓
Security Controls
 ↓
ML-Specific Validation
 ↓
Model
```

---

### 140. Input Normalization

Where technically appropriate, normalization can reduce certain input variations.

However, normalization must not be treated as a guaranteed defense against adversarial examples.

---

### 141. Robust Training

Models can be trained or optimized with robustness considerations in mind.

The goal is to reduce sensitivity to undesirable manipulations.

---

### 142. Adversarial Training

Adversarial training incorporates adversarially modified examples into the training process.

Conceptually:

```text id="aml142"
Training Data
      +
Adversarial Examples
      ↓
Training
      ↓
More Robust Model
```

Its effectiveness depends heavily on the attack types represented during training.

---

### 143. Robust Optimization

Robust optimization approaches attempt to optimize model performance under defined perturbations or uncertainty.

The threat model must clearly define what constitutes a realistic perturbation.

---

### 144. Robustness Boundaries

A model cannot necessarily be made robust against every conceivable attack.

Organizations should define:

* Threat assumptions.
* Perturbation limits.
* Relevant attack classes.
* Acceptable degradation.
* Operational constraints.

---

### 145. Security Testing Before Production

A high-impact ML system should undergo adversarial testing before deployment.

Testing should be aligned with:

* Business use case.
* Threat model.
* Data sensitivity.
* Model exposure.
* Potential impact.

---

### 146. Testing in Production-Like Conditions

Security testing should, where possible, reflect the actual deployment environment.

Differences between laboratory and production conditions can affect the validity of results.

---

### 147. Regression Testing

When a model is updated, previously identified adversarial weaknesses should be retested.

```text id="aml147"
Model v1
 ↓
Security Finding
 ↓
Remediation
 ↓
Model v2
 ↓
Regression Test
```

---

### 148. Security Acceptance Criteria

Production approval should include defined AML security requirements.

Examples:

* No unresolved critical findings.
* Required robustness tests completed.
* Model integrity verified.
* Input controls implemented.
* Monitoring operational.
* Incident response established.

---

### 149. Residual Risk

No ML system is likely to be completely immune to adversarial manipulation.

Organizations should document residual risk.

```text id="aml149"
Threat
 ↓
Controls
 ↓
Residual Risk
 ↓
Risk Acceptance / Further Mitigation
```

Risk acceptance should be performed by an appropriately authorized business or risk owner.

---

### 150. Core Governance Principle

Adversarial ML should be governed as an **enterprise security risk spanning data, models, infrastructure, applications, identities, and business decisions**.

The organization should continuously ask:

```text id="aml150"
What can the attacker control?
          ↓
What can the attacker observe?
          ↓
What can the attacker manipulate?
          ↓
What model behavior can change?
          ↓
What business decision can change?
          ↓
What is the resulting impact?
```

This threat-oriented approach allows adversarial ML controls to be connected directly to enterprise cybersecurity, privacy, resilience, and risk-management practices.

# 09.09 — Adversarial Machine Learning

## Part 3

### 151. Adversarial Attack Taxonomy

Adversarial ML attacks can be organized according to **where the attacker acts, what the attacker controls, and what outcome the attacker seeks**.

A practical taxonomy is:

| Attack Dimension   | Examples                                   |
| ------------------ | ------------------------------------------ |
| Attack stage       | Training, inference, deployment            |
| Attack target      | Data, model, pipeline, interface           |
| Attacker knowledge | Black-box, gray-box, white-box             |
| Objective          | Evasion, poisoning, extraction, disruption |
| Scope              | Targeted, untargeted                       |
| Interaction        | One-shot, iterative                        |
| Environment        | Digital, physical                          |

This taxonomy helps security teams build consistent threat models.

---

### 152. Targeted vs. Untargeted Attacks

An adversarial attack can be **targeted** or **untargeted**.

A targeted attack attempts to force a specific incorrect outcome.

```text id="aml152"
Input
  ↓
Model
  ↓
Desired Incorrect Class
```

An untargeted attack simply attempts to cause the model to make an incorrect prediction.

---

### 153. Targeted Attack Example

Suppose a model identifies objects.

An attacker may attempt to cause:

```text id="aml153"
Actual Object
     ↓
Model
     ↓
Specific Incorrect Classification
```

The attacker cares about the particular incorrect classification.

---

### 154. Untargeted Attack Example

The attacker may only need the model to stop correctly identifying the object.

```text id="aml154"
Correct Classification
        ↓
Adversarial Manipulation
        ↓
Any Incorrect Classification
```

The objective is broader.

---

### 155. One-Shot Attacks

A one-shot attack attempts to manipulate the model using a single carefully constructed interaction.

This can be important where:

* Queries are expensive.
* Rate limits are strict.
* Detection is strong.
* The attacker has limited access.

---

### 156. Iterative Attacks

Iterative attacks repeatedly interact with the model.

```text id="aml156"
Input
 ↓
Prediction
 ↓
Adjustment
 ↓
Prediction
 ↓
Adjustment
 ↓
Final Attack
```

Feedback from the model can help the attacker refine the input.

---

### 157. Query Budget

An attacker may have a limited number of queries.

This is referred to conceptually as a **query budget**.

Security controls such as rate limiting and quotas can therefore increase the cost of iterative attacks.

---

### 158. Attack Cost

Attack feasibility should consider:

* Time.
* Compute.
* Number of queries.
* Required knowledge.
* Required access.
* Data availability.
* Operational complexity.

An attack that is theoretically possible may not be practically viable.

---

### 159. Attack Feasibility

A useful enterprise assessment considers:

```text id="aml159"
Capability
   +
Access
   +
Knowledge
   +
Resources
   +
Opportunity
   ↓
Attack Feasibility
```

---

### 160. Attack Success vs. Business Impact

A technically successful attack does not necessarily represent a significant business incident.

Security teams should distinguish:

> **Can the model be manipulated?**

from:

> **Can the manipulation produce a meaningful business consequence?**

---

### 161. Threat-to-Impact Chain

```text id="aml161"
Adversarial Input
       ↓
Model Error
       ↓
Incorrect Decision
       ↓
Operational Action
       ↓
Business Impact
```

Risk assessment should follow this complete chain.

---

### 162. Evasion Attack Classes

Evasion attacks can occur against many ML-based security functions.

Examples include:

* Malware detection.
* Spam detection.
* Fraud detection.
* Intrusion detection.
* Phishing detection.
* Identity verification.

The attacker modifies observable characteristics to evade classification.

---

### 163. Malware Evasion

A malware author may attempt to alter a malicious sample while retaining its malicious functionality.

The goal is:

```text id="aml163"
Malicious Behavior
       +
Changed Features
       ↓
ML Detector
       ↓
Benign Classification
```

This illustrates why ML-based security controls should not operate without complementary defenses.

---

### 164. Fraud Evasion

Fraudsters may attempt to manipulate transaction characteristics.

Potentially manipulated characteristics could include:

* Transaction timing.
* Amount.
* Device attributes.
* Account behavior.
* Transaction patterns.

The model may then produce a lower-risk assessment.

---

### 165. Phishing Evasion

An attacker may attempt to modify a malicious communication so it resembles legitimate content.

This may challenge ML-based phishing detection.

Traditional controls such as domain reputation, authentication, URL analysis, and user reporting can provide additional layers.

---

### 166. Intrusion Detection Evasion

Network-based ML detection systems can potentially be targeted through traffic manipulation.

An attacker may attempt to make malicious activity resemble normal traffic.

---

### 167. Behavioral Detection Evasion

Behavioral ML systems can be challenged when attackers deliberately mimic legitimate user behavior.

This is especially relevant to:

* UEBA.
* Fraud detection.
* Account takeover detection.
* Insider-threat detection.

---

### 168. Data Poisoning

Poisoning attacks target the model's learning process.

An attacker attempts to introduce malicious or misleading training data.

```text id="aml168"
Legitimate Data
       +
Poisoned Data
       ↓
Training
       ↓
Manipulated Model
```

---

### 169. Availability Poisoning

Some poisoning attacks seek to degrade general model performance.

The attacker does not necessarily want one particular prediction.

The objective may simply be to make the model less reliable.

---

### 170. Targeted Poisoning

Targeted poisoning attempts to influence specific decisions or subsets of inputs.

This is potentially more difficult to detect because the overall model may continue to perform normally.

---

### 171. Label Manipulation

If attackers can influence training labels, they may attempt to introduce incorrect labels.

```text id="aml171"
Input
  +
Incorrect Label
  ↓
Training
  ↓
Incorrect Learned Association
```

---

### 172. Data Injection

Attackers may attempt to insert malicious records into a training dataset.

The effectiveness depends on whether the attacker can influence:

* Data collection.
* Data ingestion.
* Data storage.
* Data preprocessing.

---

### 173. Data Integrity Controls

Training datasets should therefore have controls such as:

* Source validation.
* Integrity verification.
* Access control.
* Provenance tracking.
* Anomaly detection.
* Change monitoring.

---

### 174. Data Provenance

Every important training dataset should have traceable provenance.

The organization should be able to determine:

* Where the data originated.
* Who supplied it.
* When it was collected.
* What transformations occurred.
* Which model versions used it.

---

### 175. Dataset Versioning

Dataset versions should be retained where practical.

```text id="aml175"
Dataset v1
 ↓
Training Run 1
 ↓
Model v1

Dataset v2
 ↓
Training Run 2
 ↓
Model v2
```

This allows suspicious changes to be investigated.

---

### 176. Dataset Diffing

Comparing dataset versions can help identify unexpected changes.

Potential indicators include:

* Sudden record additions.
* Unusual label changes.
* Large distribution changes.
* Unexpected source contributions.

---

### 177. Poisoning Detection

Potential poisoning indicators include:

* Unusual samples.
* Abnormal feature distributions.
* Unexpected labels.
* Duplicate patterns.
* Suspicious data sources.
* Abrupt changes in model behavior.

No single indicator proves poisoning.

---

### 178. Data Quality vs. Security

Data-quality monitoring can also contribute to security.

```text id="aml178"
Data Quality
      +
Security Monitoring
      ↓
Training Data Assurance
```

This demonstrates the overlap between ML engineering and cybersecurity.

---

### 179. Backdoor Attacks

A backdoor attack introduces hidden conditional behavior.

The model behaves normally for most inputs but behaves differently when a trigger is present.

```text id="aml179"
Normal Input
    ↓
Normal Output

Trigger + Input
    ↓
Unexpected Output
```

---

### 180. Backdoor Trigger

A trigger can conceptually be:

* A specific pattern.
* A characteristic.
* A particular token.
* A visual feature.
* A combination of features.

The trigger depends on the attack design.

---

### 181. Dormant Malicious Behavior

Backdoors can be difficult to detect because the malicious behavior may remain dormant during ordinary testing.

```text id="aml181"
Normal Testing
     ↓
Model Appears Normal

Trigger Present
     ↓
Malicious Behavior
```

---

### 182. Backdoor Detection

Testing should attempt to determine whether unusual input patterns produce disproportionately abnormal model behavior.

Potential approaches include:

* Trigger analysis.
* Behavioral testing.
* Dataset inspection.
* Model analysis.
* Statistical testing.

---

### 183. Model Tampering

Attackers may attempt to directly modify a model artifact.

Potential targets include:

* Weights.
* Configuration.
* Model files.
* Deployment parameters.
* Supporting libraries.

---

### 184. Model Integrity Chain

A secure deployment process should establish:

```text id="aml184"
Approved Artifact
      ↓
Integrity Verification
      ↓
Authorized Deployment
      ↓
Runtime Verification
```

---

### 185. Cryptographic Hashing

A cryptographic hash can provide an integrity fingerprint.

If the artifact changes unexpectedly:

```text id="aml185"
Expected Hash
      ≠
Actual Hash
      ↓
Integrity Alert
```

Hashing detects modification but does not by itself establish who authorized the artifact.

---

### 186. Digital Signatures

Digital signatures can provide stronger authenticity and integrity assurance when implemented correctly.

The deployment system can verify that the model was signed by an authorized source.

---

### 187. Trusted Model Sources

Organizations should establish trusted sources for production models.

Examples include:

* Approved internal repositories.
* Controlled model registries.
* Verified vendor sources.

Untrusted model artifacts should not automatically be deployed.

---

### 188. Pre-Trained Model Risk

Pre-trained models can introduce inherited risks.

The organization may not have complete visibility into:

* Training data.
* Training methodology.
* Hidden behaviors.
* Dependencies.
* Model modifications.

---

### 189. Third-Party Model Assessment

Before deploying a third-party model, organizations should evaluate:

* Provenance.
* Security documentation.
* Licensing.
* Model integrity.
* Known vulnerabilities.
* Dependencies.
* Intended use.
* Data requirements.

---

### 190. Model Supply Chain

The ML supply chain may include:

```text id="aml190"
Dataset
 ↓
Libraries
 ↓
Pre-Trained Model
 ↓
Training Code
 ↓
Model Artifact
 ↓
Registry
 ↓
Deployment
```

Every component represents a potential trust dependency.

---

### 191. Dependency Integrity

ML applications should maintain an inventory of relevant dependencies.

Security teams should know:

* Which versions are deployed.
* Which components are externally sourced.
* Which dependencies are critical.
* Whether known vulnerabilities exist.

---

### 192. Serialization Risks

Model serialization mechanisms can create security risks if untrusted model files are processed unsafely.

Organizations should treat model artifacts from untrusted sources as potentially dangerous files rather than ordinary data.

---

### 193. Secure Model Loading

Model loading should use trusted formats and controlled execution environments where practical.

Untrusted artifacts should not be granted unnecessary privileges.

---

### 194. Sandboxing

Sandboxing can isolate risky model-processing operations from sensitive enterprise systems.

```text id="aml194"
Untrusted Artifact
       ↓
Sandbox
       ↓
Security Validation
       ↓
Approved Environment
```

---

### 195. Runtime Isolation

Production models should operate with only the permissions required for their function.

A compromised model process should not automatically have access to unrelated enterprise systems.

---

### 196. Container Security

Where ML models run in containers, standard container-security principles remain applicable.

These include:

* Minimal images.
* Dependency scanning.
* Least privilege.
* Image integrity.
* Runtime monitoring.
* Network restrictions.

---

### 197. Infrastructure Security

Adversarial ML security depends partly on conventional infrastructure security.

A secure model running on a compromised host remains vulnerable.

---

### 198. Identity Security

ML platforms should use strong identity controls.

Examples include:

* MFA for administrative users.
* Service identities.
* Role-based access control.
* Privileged-access management.
* Credential rotation.

---

### 199. Logging and Auditability

Security-relevant ML events should be logged.

Examples include:

* Model access.
* Model changes.
* Dataset changes.
* Deployment events.
* Configuration changes.
* Administrative actions.
* Unusual API activity.

---

### 200. Core Security Principle

Adversarial ML requires **defense across the entire machine-learning attack surface**.

The security model should therefore connect:

```text id="aml200"
DATA SECURITY
      ↓
PIPELINE SECURITY
      ↓
MODEL SECURITY
      ↓
DEPLOYMENT SECURITY
      ↓
API SECURITY
      ↓
RUNTIME SECURITY
      ↓
MONITORING
      ↓
INCIDENT RESPONSE
```

A model should not be considered secure merely because its algorithm performs well under normal testing. Enterprise security requires confidence that the **data, model, infrastructure, interfaces, and surrounding decision process can resist, detect, and recover from deliberate manipulation**.
