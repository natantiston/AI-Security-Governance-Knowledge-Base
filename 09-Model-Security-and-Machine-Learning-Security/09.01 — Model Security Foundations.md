# 09.01 — Model Security Foundations

## Part 1

### 1. Model Security

Model security is the discipline of protecting machine-learning and AI models against threats that could compromise their **confidentiality, integrity, availability, reliability, or intended behavior**.

A model should not be treated merely as a software component.

It may represent:

* Proprietary intellectual property.
* Organizational knowledge.
* Embedded business logic.
* Learned patterns from sensitive datasets.
* Security-sensitive decision logic.
* A valuable commercial asset.

Therefore, model security sits at the intersection of:

```text
AI GOVERNANCE
      +
CYBERSECURITY
      +
DATA GOVERNANCE
      +
SOFTWARE SECURITY
      +
RISK MANAGEMENT
      +
THIRD-PARTY RISK
```

---

### 2. Why Model Security Matters

Traditional application security primarily protects software, infrastructure, identities, and data.

Machine-learning systems introduce another security object:

> **The trained model itself.**

An attacker may attempt to:

* Steal the model.
* Reconstruct the model.
* Manipulate its behavior.
* Poison its training process.
* Discover sensitive information encoded in it.
* Bypass its intended safeguards.
* Exploit weaknesses in its deployment.
* Cause incorrect or harmful predictions.

The security objective is therefore broader than simply protecting the application hosting the model.

---

### 3. The Model as an Asset

From a GRC perspective, the first question is:

> **What exactly are we protecting?**

A model environment may contain several assets:

```text
Training Data
      ↓
Training Pipeline
      ↓
Model Code
      ↓
Model Parameters
      ↓
Model Artifact
      ↓
Inference Service
      ↓
API
      ↓
AI Application
```

Each component can have different ownership, classification, and risk.

---

### 4. Model Asset Classification

Organizations should classify models according to business importance and sensitivity.

Possible categories include:

* Public or open models.
* Internal models.
* Proprietary models.
* Business-critical models.
* Safety-sensitive models.
* Security-sensitive models.
* Regulated-use models.

The classification should influence the controls applied to the model.

---

### 5. Model Confidentiality

Model confidentiality protects the model from unauthorized disclosure.

For example, a proprietary model may contain commercially valuable capabilities.

Unauthorized access could allow an attacker to:

* Download the model.
* Copy its parameters.
* Analyze its architecture.
* Reproduce its functionality.
* Identify weaknesses.

Confidentiality therefore includes protection of both the **model artifact** and information about the model.

---

### 6. Model Integrity

Model integrity ensures that the model has not been improperly modified.

For example:

```text
Approved Model
      ↓
Unauthorized Modification
      ↓
Altered Model
      ↓
Incorrect Output
```

A model may continue to operate normally from an infrastructure perspective while producing manipulated results.

This makes model integrity particularly important.

---

### 7. Model Availability

Model availability ensures that authorized users and applications can access the model when required.

Threats may include:

* Denial-of-service attacks.
* Resource exhaustion.
* Infrastructure failure.
* Malicious inference requests.
* Dependency failures.
* Model-serving failures.

Availability requirements should be based on business criticality.

---

### 8. Model Reliability

Security and reliability are closely connected.

A model can be operationally available while producing unreliable results.

For example:

```text
SERVICE = AVAILABLE
MODEL = RESPONDING
OUTPUT = INCORRECT
```

Therefore, simply monitoring whether an API is online is insufficient for model security.

---

### 9. Model Behavior

A model's behavior is one of its most important security properties.

A secure model should behave within its approved operating boundaries.

Unexpected behavior can result from:

* Adversarial inputs.
* Poisoned training data.
* Model manipulation.
* Distribution changes.
* Model drift.
* Implementation errors.
* Compromised dependencies.

---

### 10. Model Security Objectives

A basic model-security objective can be represented as:

These objectives complement the traditional CIA triad.

### 11. Model Authenticity

Authenticity establishes confidence that the model being deployed is the model that was actually approved.

For example:

```text
Approved Model
      ↓
Hash / Signature
      ↓
Registry
      ↓
Deployment
      ↓
Verification
```

If the deployed artifact does not match the approved artifact, deployment should be investigated or blocked.

### 12. Model Provenance

Provenance answers:

A model's provenance may include:

* Developer.

* Source repository.
* Base model.
* Training dataset.
* Fine-tuning dataset.
* Training process.
* Dependencies.
* Model version.
* Build process.
* Approval history.

Strong provenance improves trust and accountability.

It may contain:

* Model parameters.
* Architecture information.
* Configuration.
* Tokenizer.
* Metadata.
* Supporting files.
* Dependencies.

Depending on the framework, the artifact can take different technical forms.

From a GRC perspective, the important issue is that the artifact should be treated as a controlled asset.

### 19. Model Classification and GRC

Model classification should consider more than the model's file size or technical complexity.

Relevant factors include:

* Sensitivity of training data.
* Regulatory significance.
* Decision impact.

### 20. Business-Critical Models

Some models may support essential business operations.

Examples include models used for:

* Fraud detection.
* Network security.
* Financial forecasting.
* Customer operations.
* Industrial processes.
* Service availability.

A compromise could therefore have significant business consequences.

---

### 21. High-Impact Models

Some models influence decisions affecting individuals or organizations.

Examples can include:

* Credit-related decisions.
* Employment-related processes.
* Insurance processes.
* Security decisions.
* Customer eligibility.

These models may require stronger governance, validation, monitoring, and human oversight.

---

### 22. Security-Sensitive Models

A model may be security-sensitive when its compromise could directly affect security operations.

Examples include:

* Threat-detection models.
* Malware-classification models.
* Fraud-detection models.
* Identity-risk models.
* Security analytics models.

Manipulation could potentially reduce an organization's ability to detect threats.

### 23. Model Attack Surface

The model attack surface includes all locations where an attacker might interact with or influence the model.

For example:

```text
Training Data
     ↓
Training Pipeline
     ↓
Model Artifact
     ↓
Model Registry
     ↓
Deployment Platform
     ↓
Inference API
     ↓
Application
     ↓

```

Every stage represents a potential attack surface.

---

### 24. Training-Time Threats

Threats can occur before a model reaches production.

Examples include:

* Training-data poisoning.
* Malicious dependencies.
* Compromised training infrastructure.
* Unauthorized model modification.
* Credential compromise.
* Manipulated datasets.

This demonstrates why model security begins before deployment.

---

### 25. Development-Time Threats

During development, attackers may target:

* Source code.
* Training scripts.
* Configuration.
* Development credentials.
* Experiment environments.
* Model artifacts.
* Dataset repositories.

Development environments should therefore receive appropriate security controls.

---

### 26. Deployment-Time Threats

During deployment, attackers may target:

* Model files.
* Containers.
* APIs.
* Serving infrastructure.
* Credentials.
* Configuration.
* Network interfaces.

Secure deployment must protect both the model and the infrastructure surrounding it.

---

### 27. Runtime Threats

Once operational, the model may face:

* Malicious inputs.
* Adversarial examples.
* Model extraction.
* Abuse of inference APIs.
* Denial of service.
* Unauthorized access.
* Data leakage.

Runtime monitoring therefore forms an important part of model security.

### 29. Security by Design

Model security should not be added only after a model has been developed.

Security requirements should be identified during design.

For example:

```text

        ↓

        ↓

```

This reduces the likelihood of expensive remediation later.

### 30. Secure Model Development

Secure model development can include:

* Secure coding.
* Controlled repositories.
* Protected datasets.
* Dependency management.
* Identity controls.
* Secrets management.
* Code review.
* Model validation.
* Experiment tracking.

### 31. Model Development Environment

Development environments should have appropriate separation from production.

A typical architecture might be:

```text
DEVELOPMENT
     ↓
TESTING
     ↓
STAGING
     ↓
PRODUCTION
```

Sensitive production model artifacts should not be freely accessible from development environments.

---

### 32. Environment Separation

Environment separation reduces the likelihood that compromise of one environment automatically compromises another.

Controls may include:

* Separate accounts.
* Separate credentials.
* Network segmentation.
* Role-based access.
* Separate storage.
* Approval gates.

---

### 33. Model Access Control

Access should follow least privilege.

Users should receive only the permissions necessary to perform their role.

For example:

```text
Developer
 → Read / Experiment

ML Engineer
 → Train / Update

Model Owner
 → Approve

Production Platform
 → Deploy

Security
 → Audit / Monitor
```

---

### 34. Privileged Model Access

Highly privileged actions should receive stronger controls.

Examples include:

* Replacing a production model.
* Changing model configuration.
* Approving a new version.
* Modifying registry metadata.
* Exporting model artifacts.

Such actions should be logged and monitored.

---

### 35. Separation of Duties

Critical model-management activities should not always be performed by the same person.

For example:

```text

   ↓
Creates Model

Security / Validation
   ↓
Reviews Model

Approver
   ↓
Authorizes Production

Operations
   ↓
Deploys Model
```

This reduces the risk of unauthorized changes.

### 36. Model Change Management

Changes to production models should be governed through formal change management.

Examples include:

* New training data.
* New model version.
* Fine-tuning.
* Parameter changes.
* Architecture changes.
* Dependency changes.

A model change should be treated as a potentially security-relevant change.

---

### 50. GRC View of Model Security

From a GRC perspective, the central question is not:

> **“Is the model technically secure?”**

It is broader:

> **“Have we identified the model's risks, assigned accountability, implemented appropriate controls, verified those controls, and established evidence that the model remains secure throughout its lifecycle?”**

That distinction is fundamental to enterprise model security governance.

### 51. Model Security Risk Identification

Model security begins with identifying what can go wrong and why.

A structured risk identification process should consider:

* The model itself.
* Training data.
* Development environment.
* Training pipeline.
* Model registry.
* Deployment infrastructure.
* APIs.
* Users.
* External providers.
* Connected systems.

A useful relationship is:

```text id="r1m8sx"
ASSET
  ↓
THREAT
  ↓
VULNERABILITY
  ↓
ATTACK
  ↓
IMPACT
  ↓
RISK
```

### 52. Asset-Threat-Vulnerability Relationship

Consider a production fraud-detection model.

**Asset:**

Fraud detection model.

**Threat:**

Attacker attempts to manipulate model behavior.

**Vulnerability:**

Insufficient protection of the model artifact.

**Attack:**

Unauthorized modification.

**Impact:**

Fraudulent transactions may not be detected.

**Risk:**

Financial loss and reduced fraud-detection effectiveness.

This structure allows technical findings to be translated into GRC language.

---

### 53. Model Security Threat Modeling

Threat modeling should occur before deployment and should be revisited when the model architecture changes.

A threat model may examine:

```text id="f8r2ku"

       ↓

       ↓
WHAT CAN THEY MODIFY?
       ↓
WHAT CAN THEY LEARN?
       ↓
WHAT CAN THEY INFLUENCE?
       ↓
```

### 54. Model Trust Boundaries

### 56. Threat Modeling Questions

A GRC or security professional should ask:

1. Who can access the model?
2. Who can modify it?
3. Who can approve changes?
4. Where is it stored?
5. How is integrity verified?
6. What data was used to train it?
7. What external dependencies exist?
8. How is deployment controlled?
9. How is runtime behavior monitored?
10. How can the model be recovered?

### 61. Confidentiality Risk

Confidentiality risk exists when unauthorized parties may gain access to:

* Model parameters.
* Training information.
* Proprietary architecture.
* Model configuration.
* Sensitive outputs.

Potential controls include:

* IAM.
* Encryption.
* Network segmentation.
* Secure storage.
* Monitoring.
* Data-loss prevention.

---

### 62. Integrity Risk

Integrity risk exists when unauthorized parties can change the model or its supporting components.

Potential attack targets include:

* Model weights.
* Training datasets.
* Training code.
* Configuration.
* Dependencies.
* Deployment packages.

Controls should establish confidence that production artifacts are authentic and unaltered.

---

### 63. Availability Risk

Availability risk occurs when the model becomes unavailable or unusable.

Potential causes include:

* Infrastructure failure.
* Denial of service.
* Resource exhaustion.
* Corrupted model artifacts.
* Dependency failures.

Business continuity requirements should determine the appropriate recovery objectives.

---

### 64. Robustness Risk

Robustness risk concerns how the model behaves under unexpected or malicious inputs.

For example:

```text id="2e1x8f"
Normal Input
      ↓
Expected Output

Manipulated Input
      ↓
Unexpected Output
```

Robustness is particularly important where model outputs influence security or business decisions.

---

### 65. Model Security vs. Model Performance

A model can have excellent performance metrics while still having security weaknesses.

For example:

```text id="l4px93"
Accuracy = Excellent
Security = Poor
```

Accuracy alone does not demonstrate security.

Security assessment should therefore be separate from ordinary performance evaluation.

### 66. Model Validation

Model validation should examine whether the model performs as intended within its approved operating conditions.

Validation may consider:

* Functional behavior.
* Performance.
* Robustness.
* Security.
* Data assumptions.
* Bias and fairness where applicable.
* Operational constraints.

### 67. Independent Validation

Higher-risk models may benefit from independent validation.

This helps reduce the risk that the same team:

* Builds the model.
* Tests the model.

### 72. Model Artifact Integrity

Integrity can be supported through cryptographic hashes.

Conceptually:

```text id="1l1i5d"
Approved Artifact
      ↓
SHA-256 Hash
      ↓
Registry

Production Artifact
      ↓
SHA-256 Hash
      ↓
Compare
```

If the values differ, the artifact should be investigated.

### 73. Digital Signatures

Digital signatures can provide stronger authenticity assurances.

A simplified process is:

```text id="1y7y5r"
Approved Model
      ↓
Private Key
      ↓
Digital Signature
      ↓
Model Registry

Deployment
      ↓
Public Key Verification
      ↓
Trusted / Rejected
```

This can help establish that the artifact originated from an authorized source and was not modified after signing.

### 74. Key Management

If cryptographic signing is used, key management becomes a critical dependency.

Organizations should protect:

* Private keys.
* Certificates.
* Key access.
* Key rotation.
* Key revocation.

A weak key-management process can undermine otherwise strong model-integrity controls.

### 75. Secure Model Registry

A model registry should itself be secured.

Security controls may include:

* Strong authentication.
* Role-based authorization.
* Administrative separation.
* Audit logging.
* Version control.
* Approval workflows.
* Integrity protection.

The registry is a high-value target because it can control which models reach production.

### 182. Control Testing

Control testing evaluates whether controls are:

1. Properly designed.
2. Implemented.
3. Operating effectively.

For example:

> Does the deployment pipeline actually prevent unauthorized model artifacts from reaching production?

That is stronger than merely verifying that a policy exists.

---

### 183. Design Effectiveness

A control is design-effective when it is capable of addressing the intended risk.

Example:

> Requiring approval for model deployment is a potentially appropriate control for unauthorized deployment risk.

But the design should also specify:

* Who approves.
* What is reviewed.
* What evidence is produced.
* What happens when approval is absent.

```text id="8g2xw1"
        ↓
```
