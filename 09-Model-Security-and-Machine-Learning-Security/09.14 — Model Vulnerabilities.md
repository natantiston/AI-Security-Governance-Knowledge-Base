# 09.14 — Model Vulnerabilities

## Part 1

### 1. Model Vulnerabilities

A **model vulnerability** is a weakness in an AI/ML model that can be exploited, triggered, or abused to produce an unintended security, privacy, safety, or operational outcome.

A model vulnerability may originate from:

* Model architecture.
* Training process.
* Training data.
* Model parameters.
* Feature engineering.
* Input handling.
* Output handling.
* Deployment configuration.
* Model dependencies.

---

### 2. Model Vulnerability vs. Software Vulnerability

Traditional software vulnerabilities commonly involve weaknesses such as:

* Memory corruption.
* Authentication flaws.
* Authorization failures.
* Injection vulnerabilities.

Model vulnerabilities can instead involve weaknesses in the model's **learned behavior**.

```text id="mv102"
Software
   ↓
Code Weakness
   ↓
Exploit
   ↓
Unauthorized Behavior
```

versus:

```text id="mv103"
ML Model
   ↓
Learned Weakness
   ↓
Manipulated Input / Condition
   ↓
Unexpected Prediction
```

---

### 3. Security Boundary

The model should not be considered in isolation.

A more accurate representation is:

```text id="mv104"
Input
  ↓
Preprocessing
  ↓
Model
  ↓
Postprocessing
  ↓
Application
  ↓
Business Decision
```

A weakness anywhere in this chain can affect the security of the overall AI system.

---

### 4. Model Vulnerability Lifecycle

Model vulnerabilities should be managed throughout the model lifecycle.

```text id="mv105"
Design
 ↓
Training
 ↓
Validation
 ↓
Deployment
 ↓
Monitoring
 ↓
Detection
 ↓
Remediation
```

---

### 5. Vulnerability Sources

Potential sources include:

* Poor training data.
* Biased or incomplete datasets.
* Weak model architecture.
* Insufficient validation.
* Unsafe assumptions.
* Excessive model permissions.
* Insecure integrations.
* Uncontrolled model updates.

---

### 6. Inherent Model Weaknesses

Some vulnerabilities are inherent to the model rather than caused by an external compromise.

For example, a classifier may systematically misclassify certain unusual inputs.

This can become a security concern when attackers deliberately exploit that weakness.

---

### 7. Exploitability

Not every model weakness is equally exploitable.

Security assessment should consider:

* Attacker access.
* Required knowledge.
* Required input control.
* Attack complexity.
* Reliability.
* Detection likelihood.
* Potential impact.

---

### 8. Model Attack Surface

The attack surface can include:

```text id="mv108"
             MODEL
               │
    ┌──────────┼──────────┐
    ↓          ↓          ↓
  Input      API       Model File
    ↓          ↓          ↓
Features   Config    Parameters
    │          │          │
    └──────────┼──────────┘
               ↓
          Deployment
```

---

### 9. Input Vulnerabilities

Models may behave unexpectedly when receiving:

* Malformed inputs.
* Unexpected formats.
* Extreme values.
* Rare combinations.
* Out-of-distribution data.

Input validation can reduce some of these risks.

---

### 10. Input Validation

A secure application should validate inputs before they reach the model where appropriate.

```text id="mv110"
External Input
      ↓
Validation
      ↓
Normalization
      ↓
Model
```

Input validation should not be assumed to eliminate model-level vulnerabilities.

---

### 11. Out-of-Distribution Inputs

An out-of-distribution input differs significantly from the data distribution used during model development.

A model may still produce a confident prediction even when the input is unfamiliar.

This creates a potential security and reliability concern.

---

### 12. Confidence Misuse

Model confidence scores can be misunderstood.

A high confidence value does not necessarily mean:

> "The prediction is correct."

It may simply indicate that the model strongly prefers one output.

---

### 13. Confidence Thresholds

Organizations may establish thresholds for specific applications.

```text id="mv113"
Prediction
    ↓
Confidence
    ↓
Threshold
 ┌──┴──┐
 ↓     ↓
Accept Review
```

The threshold should reflect the application's risk.

---

### 14. Abstention

For certain high-risk applications, the model may be designed to abstain when confidence or input quality is insufficient.

```text id="mv114"
Input
 ↓
Model
 ↓
Confidence
 ├── High → Prediction
 └── Low  → Human Review
```

---

### 15. Classification Errors

False positives and false negatives can have different security consequences.

For example:

```text id="mv115"
Security Detection Model

False Negative
     ↓
Threat Not Detected
     ↓
Potential Security Impact
```

---

### 16. False Positive Risk

A model may also incorrectly classify legitimate activity as malicious.

Excessive false positives can:

* Overload security teams.
* Trigger unnecessary actions.
* Reduce trust.
* Cause operational disruption.

---

### 17. False Negative Risk

False negatives may be more serious where the model is responsible for detecting:

* Fraud.
* Malware.
* Intrusion.
* Account abuse.
* Safety violations.

Risk depends on the use case.

---

### 18. Decision Boundary Weaknesses

ML models make decisions based on learned boundaries.

```text id="mv118"
Class A
──────────────
     Decision
      Boundary
──────────────
Class B
```

Inputs near or across boundaries may produce unstable or unexpected predictions.

---

### 19. Model Sensitivity

A model can be highly sensitive to small input changes.

Security teams should understand whether small perturbations can cause disproportionate output changes.

---

### 20. Stability

Model stability refers to whether small, reasonable changes in inputs produce reasonably consistent outputs.

Unstable behavior may create an exploitable condition.

---

### 21. Robustness

Robustness describes the model's ability to maintain acceptable behavior when encountering challenging or altered inputs.

A robust model should not fail catastrophically under minor or expected variations.

---

### 22. Adversarial Robustness

Some attackers deliberately construct inputs designed to cause incorrect predictions.

This creates the field of adversarial machine learning.

Model vulnerabilities therefore overlap with adversarial attack techniques.

---

### 23. Data Quality Vulnerabilities

A model can inherit weaknesses from poor-quality training data.

Potential problems include:

* Missing values.
* Incorrect labels.
* Duplicates.
* Outliers.
* Inconsistent formats.
* Sampling problems.

---

### 24. Data Distribution Problems

If production data differs substantially from training data, model performance may degrade.

```text id="mv124"
Training Distribution
        ↓
       Model
        ↓
Production Distribution
        ↓
Potential Performance Degradation
```

---

### 25. Training Data Poisoning

An attacker may deliberately manipulate training data.

The objective could be to influence the resulting model.

This represents a model vulnerability involving the training pipeline rather than only the final artifact.

---

### 26. Label Vulnerabilities

Incorrect or manipulated labels can cause the model to learn incorrect relationships.

```text id="mv126"
Training Data
     ↓
Labels
     ↓
Training
     ↓
Incorrect Learned Behavior
```

---

### 27. Feature Vulnerabilities

Features may contain weaknesses that attackers can manipulate.

Examples include:

* User-controlled attributes.
* External feeds.
* Automatically generated values.
* Shared feature stores.

---

### 28. Feature Leakage

A feature may unintentionally expose information that should not be available to the model at decision time.

This can create both security and reliability problems.

---

### 29. Training-Serving Skew

A model may receive data during production that is processed differently from training data.

```text id="mv129"
Training Processing
       ≠
Production Processing
```

This can cause unexpected behavior.

---

### 30. Model Configuration Vulnerabilities

Model behavior may depend on configuration such as:

* Thresholds.
* Feature selection.
* Preprocessing.
* Postprocessing.
* Routing.
* Safety controls.

Unauthorized configuration changes can therefore create a model vulnerability.

---

### 31. Model Parameter Exposure

Sensitive model parameters may themselves be valuable assets.

Unauthorized access can enable:

* Model theft.
* Reverse engineering.
* Replication.
* Security analysis by attackers.

---

### 32. Model Extraction

An attacker may attempt to reconstruct model behavior by repeatedly querying an exposed model.

```text id="mv132"
Attacker
  ↓
Queries
  ↓
Model API
  ↓
Outputs
  ↓
Approximate Model
```

This can create intellectual-property and security concerns.

---

### 33. Model Inversion

Model outputs may potentially reveal information about characteristics of the training data.

This is particularly relevant where models are trained on sensitive information.

---

### 34. Membership Inference

An attacker may attempt to determine whether a particular record was part of a model's training data.

This creates a privacy-related model vulnerability.

---

### 35. Information Leakage

A model can unintentionally expose information through:

* Predictions.
* Confidence scores.
* Error messages.
* Logs.
* Metadata.
* APIs.

---

### 36. Excessive Output Detail

Providing more model information than necessary can increase attack surface.

For example, exposing internal confidence values or detailed diagnostic information may help attackers understand model behavior.

---

### 37. API Exposure

A model API should be protected according to its risk.

Controls can include:

* Authentication.
* Authorization.
* Rate limiting.
* Input validation.
* Logging.
* Monitoring.

---

### 38. Rate Limiting

Rate limiting can reduce large-scale automated querying.

```text id="mv138"
Client
 ↓
API
 ↓
Rate Limit
 ├── Allowed
 └── Blocked
```

This can help mitigate some model extraction and abuse scenarios.

---

### 39. Query Monitoring

Organizations should monitor unusual query patterns.

Potential indicators include:

* Very high request volume.
* Systematic input variation.
* Repeated probing.
* Unusual geographic or identity patterns.

---

### 40. Model Endpoint Abuse

A legitimate model endpoint can be abused even when the model itself has not been modified.

This highlights the distinction between:

**Model vulnerability**

and

**Model-service vulnerability**.

---

### 41. Model-Service Dependency

```text id="mv141"
Client
 ↓
API Gateway
 ↓
Model Service
 ↓
Model
 ↓
Application
```

Security controls should cover the complete chain.

---

### 42. Authorization Weakness

A model may be appropriately secured internally but exposed to users who should not have access to it.

Access control should consider:

* User identity.
* Application identity.
* Role.
* Data sensitivity.
* Model criticality.

---

### 43. Excessive Model Permissions

A model-serving service should not automatically have unrestricted access to:

* Databases.
* File systems.
* Internal APIs.
* Cloud resources.

Least privilege limits potential impact.

---

### 44. Model-to-System Interaction

Some models can trigger automated actions.

```text id="mv144"
Model
 ↓
Decision
 ↓
Automation
 ↓
Real-World Action
```

The risk increases when incorrect predictions directly produce consequential actions.

---

### 45. Human-in-the-Loop Controls

For high-impact decisions, human review can provide an additional control.

```text id="mv145"
Model
 ↓
Recommendation
 ↓
Human Review
 ↓
Decision
```

The effectiveness depends on the quality and authority of the human review process.

---

### 46. Automation Bias

Humans may over-trust model outputs simply because they are generated by an AI system.

Security and governance programs should account for this behavioral risk.

---

### 47. Model Cascades

Multiple models may depend on each other.

```text id="mv147"
Model A
  ↓
Model B
  ↓
Model C
  ↓
Final Decision
```

A weakness in an upstream model may propagate downstream.

---

### 48. Cascading Failure

A vulnerable model can create consequences beyond its own output.

Potential effects include:

* Incorrect downstream classifications.
* Incorrect automated actions.
* Security-control bypass.
* Operational disruption.

---

### 49. Model Vulnerability Assessment

A structured assessment should examine:

1. Model purpose.
2. Attack surface.
3. Input exposure.
4. Data dependencies.
5. Model architecture.
6. Deployment environment.
7. Attack scenarios.
8. Business impact.
9. Existing controls.
10. Residual risk.

---

### 50. Core Principle

**A model vulnerability is not limited to a defect inside the model itself. It can exist anywhere a weakness allows an attacker, malicious input, compromised dependency, or unsafe condition to influence model behavior or the consequences of that behavior.**

```text id="mv150"
DATA
 ↓
FEATURES
 ↓
MODEL
 ↓
API
 ↓
APPLICATION
 ↓
DECISION
 ↓
BUSINESS IMPACT
```

A mature model-security program therefore evaluates the **entire model ecosystem**, not merely the model's prediction accuracy.

# 09.14 — Model Vulnerabilities

## Part 2

### 51. Model Vulnerability Taxonomy

Model vulnerabilities can be organized into several broad categories:

```text
Model Vulnerabilities
        │
 ┌──────┼────────┬──────────┐
 ↓      ↓        ↓          ↓
Input  Data    Model      Deployment
       /Train  Behavior
```

A practical taxonomy includes:

* Input vulnerabilities.
* Training vulnerabilities.
* Behavioral vulnerabilities.
* Privacy vulnerabilities.
* Integrity vulnerabilities.
* Interface vulnerabilities.
* Deployment vulnerabilities.
* Operational vulnerabilities.

---

### 52. Input-Space Vulnerabilities

An input-space vulnerability exists when an attacker can manipulate inputs in a way that causes unintended model behavior.

Examples include:

* Carefully crafted inputs.
* Extreme values.
* Unexpected combinations.
* Malformed data.
* Out-of-distribution inputs.

---

### 53. Input Manipulation

The attacker may not need to compromise the model.

Instead, the attacker changes what the model receives.

```text
Legitimate Input
      ↓
Attacker Manipulation
      ↓
Modified Input
      ↓
Model
      ↓
Incorrect Output
```

---

### 54. Input Normalization

Normalization can reduce unexpected variation in inputs.

Examples include:

* Standardizing formats.
* Validating ranges.
* Removing invalid values.
* Enforcing expected structures.

However, normalization should not be treated as a complete defense against adversarial manipulation.

---

### 55. Boundary Inputs

Inputs close to a model's decision boundary can be particularly sensitive.

```text
Class A
────────────
       ↑
   Boundary
       ↓
────────────
Class B
```

Small changes may cause the classification to change.

---

### 56. Extreme-Value Vulnerabilities

Models may behave unpredictably when inputs contain values outside expected ranges.

Examples include:

* Extremely large numbers.
* Extremely small numbers.
* Unusual frequencies.
* Unexpected categorical values.

Input constraints can reduce this risk.

---

### 57. Out-of-Distribution Detection

Organizations may implement mechanisms to identify inputs that differ significantly from the model's expected operating distribution.

```text
Input
 ↓
Distribution Check
 ├── Expected → Model
 └── Unexpected → Review / Reject
```

---

### 58. Data Representation Vulnerabilities

The same real-world information may be represented differently between training and production.

Examples include:

* Different encodings.
* Different units.
* Different categorical mappings.
* Different missing-value handling.

These differences can produce unexpected predictions.

---

### 59. Preprocessing Vulnerabilities

Preprocessing is part of the model's effective security boundary.

A weakness in preprocessing can alter the data presented to the model.

```text
Raw Input
   ↓
Preprocessing
   ↓
Model Input
```

---

### 60. Preprocessing Consistency

Training and production preprocessing should be controlled to reduce **training-serving skew**.

The same transformations should be applied consistently where appropriate.

---

### 61. Postprocessing Vulnerabilities

The model output may be transformed before reaching the user or downstream system.

```text
Model Output
     ↓
Postprocessing
     ↓
Application Decision
```

A vulnerability may therefore exist after the model itself.

---

### 62. Threshold Manipulation

A model may generate a score while a separate system determines whether that score triggers an action.

```text
Model Score
    ↓
Threshold
    ↓
Decision
```

Unauthorized modification of the threshold can materially change security outcomes.

---

### 63. Decision Logic Vulnerabilities

The model may be functioning correctly while the application interprets its output incorrectly.

For example:

```text
Model: "Risk = 0.70"

Application:
"Risk > 0.60 → Block"
```

If the application threshold is changed incorrectly, the overall security behavior changes.

---

### 64. Model-Application Contract

Organizations should clearly define the expected interface between a model and its consuming application.

The contract can specify:

* Input format.
* Output format.
* Valid ranges.
* Confidence interpretation.
* Error behavior.
* Timeout behavior.

---

### 65. Error Handling

Model failures should not automatically result in unsafe behavior.

A secure design should explicitly define what happens when:

* The model times out.
* The model returns invalid output.
* The model becomes unavailable.
* Confidence is too low.

---

### 66. Fail-Safe vs. Fail-Open

For security-sensitive applications, the failure mode matters.

```text
Model Failure
     ↓
 ┌───┴────┐
 ↓        ↓
Fail-Safe Fail-Open
```

The appropriate choice depends on the business process and risk.

---

### 67. Fail-Safe Behavior

A fail-safe approach generally moves the system toward a controlled or restrictive state when the model cannot provide a reliable decision.

---

### 68. Fail-Open Behavior

A fail-open design may allow activity to continue when the model is unavailable.

This may be appropriate in some availability-sensitive applications but dangerous in others.

---

### 69. Model Availability

Availability is also a model-security concern.

An attacker may attempt to prevent a critical model from operating.

Potential consequences include:

* Security-control degradation.
* Business disruption.
* Manual processing.
* Increased operational risk.

---

### 70. Resource Exhaustion

An attacker may generate excessive requests that consume:

* CPU.
* GPU.
* Memory.
* Network bandwidth.
* API capacity.

This can create a denial-of-service condition against model services.

---

### 71. Model API Denial of Service

```text
Attacker
   ↓
大量 Requests
   ↓
Model API
   ↓
Resource Exhaustion
   ↓
Service Degradation
```

Controls may include:

* Rate limiting.
* Authentication.
* Quotas.
* Request-size limits.
* Autoscaling controls.

---

### 72. Large Input Abuse

Where models accept large inputs, attackers may intentionally submit unusually large requests.

Security controls should establish reasonable input-size limits.

---

### 73. Computational Complexity

Some model operations may require significant computational resources.

Security testing should consider whether attacker-controlled inputs can cause disproportionately expensive processing.

---

### 74. Resource Governance

Critical model services should have defined:

* Resource quotas.
* Scaling limits.
* Timeout values.
* Queue limits.
* Concurrency limits.

---

### 75. Model Confidentiality

The model itself may be confidential intellectual property.

Unauthorized disclosure can enable:

* Replication.
* Competitive loss.
* Security analysis.
* Evasion research.

---

### 76. Model Access Exposure

Model files should not be exposed unnecessarily.

Access should follow:

```text
Need
 ↓
Authorization
 ↓
Access
```

rather than unrestricted internal availability.

---

### 77. Model Theft vs. Model Vulnerability

**Model theft** involves unauthorized acquisition of the model.

A model vulnerability may enable that theft through weaknesses such as:

* Excessive API access.
* Weak authentication.
* Unrestricted model downloads.
* Poor registry permissions.

---

### 78. Model Extraction

Model extraction can occur through repeated queries.

The attacker attempts to learn enough about the model to reproduce its behavior.

Controls may include:

* Rate limiting.
* Query monitoring.
* Access restrictions.
* Output minimization.

---

### 79. Model Inversion Risk

A model may unintentionally reveal information about its training data.

The risk becomes more significant when the training dataset contains sensitive information.

---

### 80. Membership Inference Risk

An attacker may attempt to determine whether a specific record was included in training.

Potential contributing factors include:

* Overfitting.
* Excessively informative outputs.
* Confidence information.

---

### 81. Privacy Leakage

Model outputs should be evaluated for unintended disclosure.

The relevant question is:

> **Can an attacker learn something sensitive from interacting with the model that they were not authorized to know?**

---

### 82. Overfitting as a Security Concern

Overfitting is primarily a machine-learning quality problem, but it can also become a security and privacy issue.

A highly overfit model may retain characteristics of individual training examples.

---

### 83. Memorization

Models can sometimes memorize portions of training information.

The security significance depends on:

* What was memorized.
* How sensitive it is.
* Whether it can be extracted.
* Who can query the model.

---

### 84. Output Leakage

Potential leakage can occur through:

* Predictions.
* Confidence scores.
* Explanations.
* Error messages.
* Debug information.

The principle of **data minimization** should also apply to model outputs.

---

### 85. Model Integrity Vulnerabilities

Integrity vulnerabilities allow unauthorized modification of the model or components influencing its behavior.

Examples include:

* Unauthorized model replacement.
* Parameter modification.
* Registry compromise.
* Build compromise.
* Unauthorized fine-tuning.

---

### 86. Model Replacement

An attacker may replace a legitimate model with a malicious or weaker model.

```text
Approved Model
      ↓
Attacker Access
      ↓
Replacement
      ↓
Malicious Model
```

Strong artifact verification can help detect this.

---

### 87. Model Tampering

Tampering may involve modification rather than complete replacement.

For example:

```text
Model v1
   ↓
Unauthorized Modification
   ↓
Modified Model
```

Cryptographic integrity mechanisms can detect unauthorized changes.

---

### 88. Configuration Tampering

The model artifact may remain unchanged while surrounding configuration is altered.

Examples include:

* Thresholds.
* Feature mappings.
* Routing.
* Preprocessing.
* Model selection.

Therefore, configuration integrity is part of model integrity.

---

### 89. Model Routing Vulnerability

Applications may dynamically select among multiple models.

```text
Request
   ↓
Router
 ┌─┴─┐
 ↓   ↓
M1   M2
```

A compromised routing mechanism could direct requests to an unauthorized model.

---

### 90. Shadow Models

An attacker or unauthorized user may deploy a separate model outside approved governance.

Such models can create:

* Data leakage.
* Uncontrolled decision-making.
* Unknown dependencies.
* Security blind spots.

---

### 91. Unauthorized Model Deployment

Organizations should detect models deployed outside approved infrastructure.

Controls can include:

* Asset discovery.
* Registry enforcement.
* Cloud inventory.
* Deployment monitoring.

---

### 92. Model Dependency Vulnerabilities

A model can depend on vulnerable software components.

```text
Model
 ↓
Runtime
 ↓
Framework
 ↓
Library
 ↓
Operating System
```

A model-security assessment should therefore consider its software dependencies.

---

### 93. Unsafe Model Formats

Some model serialization mechanisms may have security implications if they allow executable or otherwise unsafe components to be loaded.

Organizations should use trusted formats and secure loading practices where applicable.

---

### 94. Deserialization Risk

Untrusted serialized model artifacts should not automatically be loaded into privileged environments.

A safer approach is:

```text
External Model
      ↓
Quarantine
      ↓
Inspection
      ↓
Validation
      ↓
Trusted Environment
```

---

### 95. Runtime Dependency Vulnerabilities

Even a trusted model can run on vulnerable serving infrastructure.

Security therefore requires protection of:

* Model artifact.
* Runtime.
* Host.
* Network.
* Identity.
* Application.

---

### 96. Container Vulnerabilities

Containerized model services can inherit vulnerabilities from:

* Base images.
* Packages.
* Runtime libraries.
* Configuration.

Container scanning and controlled image provenance can reduce this risk.

---

### 97. GPU and Accelerator Risks

Models may depend on specialized hardware and drivers.

Vulnerabilities in:

* GPU drivers.
* Runtime libraries.
* Accelerator software.

can affect model-serving security.

---

### 98. Cloud Configuration Vulnerabilities

Cloud-hosted model services can be exposed through:

* Excessive permissions.
* Public storage.
* Weak network controls.
* Misconfigured endpoints.

The model itself may be secure while its hosting environment is not.

---

### 99. Defense-in-Depth

No single control should be expected to eliminate model vulnerabilities.

A layered architecture may include:

```text
Identity
   ↓
Network
   ↓
Input Validation
   ↓
Model Controls
   ↓
Output Validation
   ↓
Application Controls
   ↓
Monitoring
```

---

### 100. Core Principle

**Model vulnerabilities must be assessed as weaknesses across the complete path from input to model to decision, including the data, interfaces, dependencies, infrastructure, and controls surrounding the model.**

```text
INPUT
  ↓
VALIDATION
  ↓
PREPROCESSING
  ↓
MODEL
  ↓
POSTPROCESSING
  ↓
APPLICATION
  ↓
DECISION
  ↓
IMPACT
```

Security assurance requires understanding not only **whether the model works**, but also **how it can fail, how it can be manipulated, what information it can reveal, and what happens when its output is wrong or unavailable**.

# 09.14 — Model Vulnerabilities

## Part 3

### 101. Model Vulnerability Discovery

Model vulnerability discovery is the process of systematically identifying weaknesses that could affect model confidentiality, integrity, availability, privacy, safety, or decision-making.

A mature discovery process should combine:

* Technical testing.
* Model evaluation.
* Data analysis.
* Threat modeling.
* Dependency analysis.
* Operational testing.

---

### 102. Threat Modeling the Model

Threat modeling should begin by identifying:

```text id="mvd102"
Assets
  ↓
Trust Boundaries
  ↓
Threat Actors
  ↓
Attack Paths
  ↓
Potential Impact
  ↓
Security Controls
```

The model should be treated as part of a larger system rather than as an isolated artifact.

---

### 103. Model Assets

Potential assets include:

* Model weights.
* Architecture.
* Training data.
* Training metadata.
* Feature definitions.
* Model configuration.
* Inference API.
* Predictions.
* Confidence information.
* Intellectual property.

---

### 104. Threat Actors

Potential threat actors can include:

* External attackers.
* Malicious users.
* Compromised accounts.
* Malicious insiders.
* Third-party suppliers.
* Competitors.
* Automated attack systems.

The relevant threat actors depend on the model's exposure and business context.

---

### 105. Attack Preconditions

A vulnerability should be assessed according to the conditions required for exploitation.

Examples:

* Public API access.
* Authenticated user access.
* Access to training data.
* Access to model files.
* Developer privileges.
* Registry permissions.

---

### 106. Attack Surface Mapping

A model attack-surface map may include:

```text id="mvd106"
              MODEL
                │
      ┌─────────┼─────────┐
      ↓         ↓         ↓
   Training   API      Registry
      ↓         ↓         ↓
    Data     Clients   Developers
      │         │         │
      └─────────┼─────────┘
                ↓
           Production
```

---

### 107. Threat Modeling Questions

Security teams should ask:

1. Who can submit inputs?
2. Who can access the model?
3. Who can modify the model?
4. Who can modify training data?
5. Who can change model configuration?
6. What outputs are exposed?
7. What downstream actions can the model trigger?

---

### 108. Abuse Cases

An abuse case describes how a legitimate capability could be misused.

Examples include:

* Querying the model to extract behavior.
* Manipulating inputs to evade detection.
* Using outputs to infer sensitive information.
* Abusing model-generated decisions.

---

### 109. Security Test Categories

Model vulnerability testing can include:

```text id="mvd109"
Functional Testing
       +
Robustness Testing
       +
Adversarial Testing
       +
Privacy Testing
       +
Security Testing
```

Each category addresses different failure modes.

---

### 110. Functional Testing

Functional testing verifies that the model performs its intended task correctly under expected conditions.

It establishes the baseline against which abnormal behavior can be identified.

---

### 111. Robustness Testing

Robustness testing evaluates how the model behaves when inputs change within reasonable or challenging boundaries.

Questions include:

* Does the output remain stable?
* Does accuracy degrade gradually?
* Does the model fail safely?

---

### 112. Adversarial Testing

Adversarial testing evaluates deliberate attempts to cause incorrect model behavior.

This can include:

* Input perturbation.
* Evasion attempts.
* Manipulated features.
* Structured probing.

---

### 113. Privacy Testing

Privacy testing examines whether model interaction can reveal information that should remain confidential.

Relevant areas include:

* Membership inference.
* Model inversion.
* Memorization.
* Output leakage.

---

### 114. Security-Focused Evaluation

Traditional model evaluation often emphasizes:

* Accuracy.
* Precision.
* Recall.
* F1 score.

Security evaluation must additionally consider:

* Exploitability.
* Abuse resistance.
* Confidentiality.
* Integrity.
* Availability.

---

### 115. Security Metrics

A model may have excellent accuracy while still presenting security weaknesses.

For example:

```text id="mvd115"
Accuracy:        High
Robustness:      Low
Privacy:         Weak
Extraction Risk: High
```

Model quality and model security are therefore different dimensions.

---

### 116. Attack Success Rate

For adversarial scenarios, organizations may measure the percentage of attacks that successfully cause the desired attacker outcome.

A higher attack success rate generally indicates greater vulnerability under the tested conditions.

---

### 117. Robustness Evaluation

A robustness assessment can compare:

```text id="mvd117"
Normal Input
     ↓
Expected Output

Modified Input
     ↓
Expected Security Behavior
```

The objective is to determine how easily behavior can be manipulated.

---

### 118. Perturbation Testing

Controlled perturbations can be applied to inputs to determine whether small changes produce disproportionate changes in output.

---

### 119. Sensitivity Analysis

Sensitivity analysis examines how strongly outputs respond to changes in individual features.

This can reveal:

* Overly influential features.
* Unexpected dependencies.
* Potential manipulation opportunities.

---

### 120. Feature Importance

Feature-importance analysis can help identify which inputs have significant influence over predictions.

However, feature importance alone does not prove that a feature is secure or exploitable.

---

### 121. Feature Manipulation Testing

If an attacker can control a feature, security teams should evaluate whether manipulating it can materially alter the model's decision.

```text id="mvd121"
Feature
  ↓
Attacker Control?
  ↓
Model Influence?
  ↓
Security Impact?
```

---

### 122. Counterfactual Testing

Counterfactual testing evaluates how model outputs change when specific input characteristics are changed.

This can help identify unexpected decision dependencies.

---

### 123. Boundary Testing

Testing should include values:

* Near decision thresholds.
* At minimum limits.
* At maximum limits.
* Slightly outside expected ranges.

---

### 124. Stress Testing

Stress testing examines model behavior under extreme operational conditions.

Examples include:

* High request volume.
* Large inputs.
* High concurrency.
* Resource constraints.

---

### 125. Fault Injection

Security teams can intentionally introduce controlled failures.

Examples include:

* Model unavailable.
* Dependency unavailable.
* Invalid response.
* Missing feature.
* Timeout.

The objective is to determine whether the system fails safely.

---

### 126. Failover Testing

If the model is critical, organizations should test whether traffic can be redirected to an alternative model or process.

---

### 127. Rollback Testing

A production model should have a known trusted previous version where appropriate.

Rollback testing verifies that the organization can actually return to that version.

---

### 128. Model Integrity Testing

Integrity testing can verify:

* Hash.
* Signature.
* Version.
* Artifact identity.
* Registry metadata.

```text id="mvd128"
Production Model
      ↓
Integrity Verification
      ↓
Expected Artifact?
```

---

### 129. Model File Inspection

Where appropriate, model artifacts should be inspected before loading them into trusted environments.

This is especially important for externally sourced artifacts.

---

### 130. Dependency Inspection

Model vulnerability assessment should include dependencies such as:

* Frameworks.
* Libraries.
* Runtime components.
* Containers.
* Drivers.

---

### 131. Vulnerability Scanning

Known software vulnerabilities should be identified and assessed according to their relevance to the model environment.

---

### 132. Dependency Exploitability

A vulnerable dependency is not automatically an exploitable model vulnerability.

Security teams should evaluate:

* Whether the vulnerable component is actually used.
* Whether the vulnerable function is reachable.
* Whether an attacker can influence it.
* What impact exploitation would have.

---

### 133. Model Configuration Review

Configuration should be reviewed for:

* Unsafe defaults.
* Excessive permissions.
* Weak thresholds.
* Debug settings.
* Unnecessary interfaces.

---

### 134. Security Configuration Baseline

Critical model-serving environments should have documented security baselines.

A baseline establishes the expected minimum configuration.

---

### 135. Model API Testing

API testing can examine:

* Authentication.
* Authorization.
* Input validation.
* Rate limiting.
* Error handling.
* Output exposure.

---

### 136. Authentication Testing

Security teams should verify that unauthorized users cannot access protected model functionality.

---

### 137. Authorization Testing

Authenticated access does not automatically mean unrestricted model access.

Testing should determine whether users can access only the models and functions appropriate to their role.

---

### 138. Rate-Limit Testing

Testing should determine whether automated clients can issue excessive numbers of queries.

This is particularly relevant to:

* Model extraction.
* Enumeration.
* Resource exhaustion.

---

### 139. Output-Control Testing

Security teams should determine whether the API exposes unnecessary information.

Potentially sensitive information includes:

* Internal scores.
* Model metadata.
* Debug details.
* Training information.

---

### 140. Error-Message Testing

Error messages should not unnecessarily reveal:

* Internal paths.
* Model architecture.
* Dependency versions.
* Infrastructure information.
* Sensitive configuration.

---

### 141. Logging Review

Model-related logs should be evaluated for both:

**Security value**

and

**privacy risk**.

Logging too little can impair detection; logging too much can expose sensitive data.

---

### 142. Security Telemetry

Useful telemetry can include:

* Request identity.
* Timestamp.
* Model version.
* Endpoint.
* Response status.
* Security events.
* Rate-limit events.

---

### 143. Model Behavior Monitoring

Production monitoring should establish expected behavioral patterns.

```text id="mvd143"
Expected Behavior
       ↓
Continuous Observation
       ↓
Deviation
       ↓
Investigation
```

---

### 144. Behavioral Baselines

A baseline can include:

* Normal request volume.
* Typical input distributions.
* Expected output distributions.
* Normal confidence patterns.
* Expected error rates.

---

### 145. Anomaly Detection

Significant deviations from established behavior may indicate:

* Attack activity.
* Model degradation.
* Data drift.
* Configuration changes.
* Service abuse.

---

### 146. Security vs. Performance Anomaly

Not every anomaly is an attack.

An abnormal model output could result from:

* Legitimate business changes.
* New data.
* Model drift.
* Software changes.
* Infrastructure problems.

Investigation should distinguish security events from normal operational changes.

---

### 147. Model Vulnerability Severity

A vulnerability can be prioritized using factors such as:

```text id="mvd147"
Exploitability
      ×
Impact
      ×
Exposure
```

Organizations can integrate this into their existing risk-rating methodology.

---

### 148. High-Severity Model Vulnerability

A model weakness should generally receive greater attention when:

* Exploitation is practical.
* The model is externally exposed.
* The model supports critical decisions.
* Sensitive information may be disclosed.
* Exploitation can affect many systems.

---

### 149. Vulnerability Remediation

Remediation options can include:

* Retraining.
* Fine-tuning.
* Input controls.
* Output controls.
* Model replacement.
* Configuration changes.
* Access restrictions.
* Additional monitoring.

The appropriate remediation depends on the root cause.

---

### 150. Core Principle

**Model vulnerability management requires more than discovering weaknesses. It requires understanding how those weaknesses can be exploited, determining their real-world impact, applying proportionate controls, and continuously verifying that the controls remain effective.**

```text id="mvd150"
DISCOVER
   ↓
VALIDATE
   ↓
ASSESS
   ↓
PRIORITIZE
   ↓
REMEDIATE
   ↓
VERIFY
   ↓
MONITOR
```

A mature program treats model security as a **continuous risk-management process**, combining model evaluation with application security, data security, infrastructure security, privacy protection, and operational monitoring.
