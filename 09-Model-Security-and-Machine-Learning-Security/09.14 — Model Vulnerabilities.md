# 09.14 — Model Vulnerabilities

## Part 1

### 1. Model Vulnerabilities

A **model vulnerability** is a weakness in an AI/ML model that can be exploited, triggered, or abused to produce an unintended security, privacy, safety, or operational outcome.

A model vulnerability may originate from:

* Model architecture.
* Training process.
* Training data.
* Model parameters.
* Feature engineering.
* Input handling.
* Output handling.
* Deployment configuration.
* Model dependencies.

---

### 2. Model Vulnerability vs. Software Vulnerability

Traditional software vulnerabilities commonly involve weaknesses such as:

* Memory corruption.
* Authentication flaws.
* Authorization failures.
* Injection vulnerabilities.

Model vulnerabilities can instead involve weaknesses in the model's **learned behavior**.

```text id="mv102"
Software
   ↓
Code Weakness
   ↓
Exploit
   ↓
Unauthorized Behavior
```

versus:

```text id="mv103"
ML Model
   ↓
Learned Weakness
   ↓
Manipulated Input / Condition
   ↓
Unexpected Prediction
```

---

### 3. Security Boundary

The model should not be considered in isolation.

A more accurate representation is:

```text id="mv104"
Input
  ↓
Preprocessing
  ↓
Model
  ↓
Postprocessing
  ↓
Application
  ↓
Business Decision
```

A weakness anywhere in this chain can affect the security of the overall AI system.

---

### 4. Model Vulnerability Lifecycle

Model vulnerabilities should be managed throughout the model lifecycle.

```text id="mv105"
Design
 ↓
Training
 ↓
Validation
 ↓
Deployment
 ↓
Monitoring
 ↓
Detection
 ↓
Remediation
```

---

### 5. Vulnerability Sources

Potential sources include:

* Poor training data.
* Biased or incomplete datasets.
* Weak model architecture.
* Insufficient validation.
* Unsafe assumptions.
* Excessive model permissions.
* Insecure integrations.
* Uncontrolled model updates.

---

### 6. Inherent Model Weaknesses

Some vulnerabilities are inherent to the model rather than caused by an external compromise.

For example, a classifier may systematically misclassify certain unusual inputs.

This can become a security concern when attackers deliberately exploit that weakness.

---

### 7. Exploitability

Not every model weakness is equally exploitable.

Security assessment should consider:

* Attacker access.
* Required knowledge.
* Required input control.
* Attack complexity.
* Reliability.
* Detection likelihood.
* Potential impact.

---

### 8. Model Attack Surface

The attack surface can include:

```text id="mv108"
             MODEL
               │
    ┌──────────┼──────────┐
    ↓          ↓          ↓
  Input      API       Model File
    ↓          ↓          ↓
Features   Config    Parameters
    │          │          │
    └──────────┼──────────┘
               ↓
          Deployment
```

---

### 9. Input Vulnerabilities

Models may behave unexpectedly when receiving:

* Malformed inputs.
* Unexpected formats.
* Extreme values.
* Rare combinations.
* Out-of-distribution data.

Input validation can reduce some of these risks.

---

### 10. Input Validation

A secure application should validate inputs before they reach the model where appropriate.

```text id="mv110"
External Input
      ↓
Validation
      ↓
Normalization
      ↓
Model
```

Input validation should not be assumed to eliminate model-level vulnerabilities.

---

### 11. Out-of-Distribution Inputs

An out-of-distribution input differs significantly from the data distribution used during model development.

A model may still produce a confident prediction even when the input is unfamiliar.

This creates a potential security and reliability concern.

---

### 12. Confidence Misuse

Model confidence scores can be misunderstood.

A high confidence value does not necessarily mean:

> "The prediction is correct."

It may simply indicate that the model strongly prefers one output.

---

### 13. Confidence Thresholds

Organizations may establish thresholds for specific applications.

```text id="mv113"
Prediction
    ↓
Confidence
    ↓
Threshold
 ┌──┴──┐
 ↓     ↓
Accept Review
```

The threshold should reflect the application's risk.

---

### 14. Abstention

For certain high-risk applications, the model may be designed to abstain when confidence or input quality is insufficient.

```text id="mv114"
Input
 ↓
Model
 ↓
Confidence
 ├── High → Prediction
 └── Low  → Human Review
```

---

### 15. Classification Errors

False positives and false negatives can have different security consequences.

For example:

```text id="mv115"
Security Detection Model

False Negative
     ↓
Threat Not Detected
     ↓
Potential Security Impact
```

---

### 16. False Positive Risk

A model may also incorrectly classify legitimate activity as malicious.

Excessive false positives can:

* Overload security teams.
* Trigger unnecessary actions.
* Reduce trust.
* Cause operational disruption.

---

### 17. False Negative Risk

False negatives may be more serious where the model is responsible for detecting:

* Fraud.
* Malware.
* Intrusion.
* Account abuse.
* Safety violations.

Risk depends on the use case.

---

### 18. Decision Boundary Weaknesses

ML models make decisions based on learned boundaries.

```text id="mv118"
Class A
──────────────
     Decision
      Boundary
──────────────
Class B
```

Inputs near or across boundaries may produce unstable or unexpected predictions.

---

### 19. Model Sensitivity

A model can be highly sensitive to small input changes.

Security teams should understand whether small perturbations can cause disproportionate output changes.

---

### 20. Stability

Model stability refers to whether small, reasonable changes in inputs produce reasonably consistent outputs.

Unstable behavior may create an exploitable condition.

---

### 21. Robustness

Robustness describes the model's ability to maintain acceptable behavior when encountering challenging or altered inputs.

A robust model should not fail catastrophically under minor or expected variations.

---

### 22. Adversarial Robustness

Some attackers deliberately construct inputs designed to cause incorrect predictions.

This creates the field of adversarial machine learning.

Model vulnerabilities therefore overlap with adversarial attack techniques.

---

### 23. Data Quality Vulnerabilities

A model can inherit weaknesses from poor-quality training data.

Potential problems include:

* Missing values.
* Incorrect labels.
* Duplicates.
* Outliers.
* Inconsistent formats.
* Sampling problems.

---

### 24. Data Distribution Problems

If production data differs substantially from training data, model performance may degrade.

```text id="mv124"
Training Distribution
        ↓
       Model
        ↓
Production Distribution
        ↓
Potential Performance Degradation
```

---

### 25. Training Data Poisoning

An attacker may deliberately manipulate training data.

The objective could be to influence the resulting model.

This represents a model vulnerability involving the training pipeline rather than only the final artifact.

---

### 26. Label Vulnerabilities

Incorrect or manipulated labels can cause the model to learn incorrect relationships.

```text id="mv126"
Training Data
     ↓
Labels
     ↓
Training
     ↓
Incorrect Learned Behavior
```

---

### 27. Feature Vulnerabilities

Features may contain weaknesses that attackers can manipulate.

Examples include:

* User-controlled attributes.
* External feeds.
* Automatically generated values.
* Shared feature stores.

---

### 28. Feature Leakage

A feature may unintentionally expose information that should not be available to the model at decision time.

This can create both security and reliability problems.

---

### 29. Training-Serving Skew

A model may receive data during production that is processed differently from training data.

```text id="mv129"
Training Processing
       ≠
Production Processing
```

This can cause unexpected behavior.

---

### 30. Model Configuration Vulnerabilities

Model behavior may depend on configuration such as:

* Thresholds.
* Feature selection.
* Preprocessing.
* Postprocessing.
* Routing.
* Safety controls.

Unauthorized configuration changes can therefore create a model vulnerability.

---

### 31. Model Parameter Exposure

Sensitive model parameters may themselves be valuable assets.

Unauthorized access can enable:

* Model theft.
* Reverse engineering.
* Replication.
* Security analysis by attackers.

---

### 32. Model Extraction

An attacker may attempt to reconstruct model behavior by repeatedly querying an exposed model.

```text id="mv132"
Attacker
  ↓
Queries
  ↓
Model API
  ↓
Outputs
  ↓
Approximate Model
```

This can create intellectual-property and security concerns.

---

### 33. Model Inversion

Model outputs may potentially reveal information about characteristics of the training data.

This is particularly relevant where models are trained on sensitive information.

---

### 34. Membership Inference

An attacker may attempt to determine whether a particular record was part of a model's training data.

This creates a privacy-related model vulnerability.

---

### 35. Information Leakage

A model can unintentionally expose information through:

* Predictions.
* Confidence scores.
* Error messages.
* Logs.
* Metadata.
* APIs.

---

### 36. Excessive Output Detail

Providing more model information than necessary can increase attack surface.

For example, exposing internal confidence values or detailed diagnostic information may help attackers understand model behavior.

---

### 37. API Exposure

A model API should be protected according to its risk.

Controls can include:

* Authentication.
* Authorization.
* Rate limiting.
* Input validation.
* Logging.
* Monitoring.

---

### 38. Rate Limiting

Rate limiting can reduce large-scale automated querying.

```text id="mv138"
Client
 ↓
API
 ↓
Rate Limit
 ├── Allowed
 └── Blocked
```

This can help mitigate some model extraction and abuse scenarios.

---

### 39. Query Monitoring

Organizations should monitor unusual query patterns.

Potential indicators include:

* Very high request volume.
* Systematic input variation.
* Repeated probing.
* Unusual geographic or identity patterns.

---

### 40. Model Endpoint Abuse

A legitimate model endpoint can be abused even when the model itself has not been modified.

This highlights the distinction between:

**Model vulnerability**

and

**Model-service vulnerability**.

---

### 41. Model-Service Dependency

```text id="mv141"
Client
 ↓
API Gateway
 ↓
Model Service
 ↓
Model
 ↓
Application
```

Security controls should cover the complete chain.

---

### 42. Authorization Weakness

A model may be appropriately secured internally but exposed to users who should not have access to it.

Access control should consider:

* User identity.
* Application identity.
* Role.
* Data sensitivity.
* Model criticality.

---

### 43. Excessive Model Permissions

A model-serving service should not automatically have unrestricted access to:

* Databases.
* File systems.
* Internal APIs.
* Cloud resources.

Least privilege limits potential impact.

---

### 44. Model-to-System Interaction

Some models can trigger automated actions.

```text id="mv144"
Model
 ↓
Decision
 ↓
Automation
 ↓
Real-World Action
```

The risk increases when incorrect predictions directly produce consequential actions.

---

### 45. Human-in-the-Loop Controls

For high-impact decisions, human review can provide an additional control.

```text id="mv145"
Model
 ↓
Recommendation
 ↓
Human Review
 ↓
Decision
```

The effectiveness depends on the quality and authority of the human review process.

---

### 46. Automation Bias

Humans may over-trust model outputs simply because they are generated by an AI system.

Security and governance programs should account for this behavioral risk.

---

### 47. Model Cascades

Multiple models may depend on each other.

```text id="mv147"
Model A
  ↓
Model B
  ↓
Model C
  ↓
Final Decision
```

A weakness in an upstream model may propagate downstream.

---

### 48. Cascading Failure

A vulnerable model can create consequences beyond its own output.

Potential effects include:

* Incorrect downstream classifications.
* Incorrect automated actions.
* Security-control bypass.
* Operational disruption.

---

### 49. Model Vulnerability Assessment

A structured assessment should examine:

1. Model purpose.
2. Attack surface.
3. Input exposure.
4. Data dependencies.
5. Model architecture.
6. Deployment environment.
7. Attack scenarios.
8. Business impact.
9. Existing controls.
10. Residual risk.

---

### 50. Core Principle

**A model vulnerability is not limited to a defect inside the model itself. It can exist anywhere a weakness allows an attacker, malicious input, compromised dependency, or unsafe condition to influence model behavior or the consequences of that behavior.**

```text id="mv150"
DATA
 ↓
FEATURES
 ↓
MODEL
 ↓
API
 ↓
APPLICATION
 ↓
DECISION
 ↓
BUSINESS IMPACT
```

A mature model-security program therefore evaluates the **entire model ecosystem**, not merely the model's prediction accuracy.
