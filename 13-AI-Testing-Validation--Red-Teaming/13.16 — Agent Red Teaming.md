# 13.16 — Agent Red Teaming

## Part 1 — Agent Red Teaming Foundations

### 1. Definition of Agent Red Teaming

Agent Red Teaming is the authorized, controlled, adversarial assessment of AI agents to determine whether an attacker can manipulate agent reasoning, planning, memory, tool use, identity, permissions, workflows, or autonomous actions in ways that create security, privacy, operational, or business risk.

Unlike conventional LLM red teaming, agent red teaming must evaluate not only what the model says, but **what the agent can cause the surrounding system to do**.

---

### 2. Purpose of Agent Red Teaming

The purpose is to determine whether an AI agent can be manipulated into:

* Performing unauthorized actions
* Accessing unauthorized information
* Misusing tools
* Escalating privileges
* Violating workflow constraints
* Circumventing human approval
* Manipulating memory
* Delegating malicious tasks
* Crossing trust boundaries
* Creating unintended business impact

The assessment must distinguish theoretical model behavior from actual executable impact.

---

### 3. Agent Red Teaming vs LLM Red Teaming

LLM red teaming primarily examines adversarial manipulation of language-model behavior.

Agent red teaming extends this assessment into the **execution environment**.

```text id="agent003a"
LLM Red Teaming
      |
      v
Model Behavior
      |
      v
Prompt / Context
      |
      v
Security Response


Agent Red Teaming
      |
      v
Model Behavior
      |
      v
Agent Planning
      |
      v
Tool Selection
      |
      v
Authorization
      |
      v
Execution
      |
      v
Enterprise Impact
```

An agent assessment therefore requires analysis of both cognitive behavior and technical execution paths.

### 5. Agent Red Teaming Objectives

Core objectives include determining whether the agent can resist:

* Prompt manipulation
* Goal manipulation
* Tool abuse
* Authorization bypass
* Privilege escalation
* Memory poisoning
* Context poisoning
* Identity manipulation
* Workflow manipulation
* Agent-to-agent attacks
* Data exfiltration
* Persistence
* Lateral movement

The objective is not merely to make the agent produce an undesirable response, but to determine whether the manipulation can create meaningful security consequences.

---

### 6. Risk-Based Agent Red Teaming

Testing depth should correspond to the agent's risk.

Risk factors include:

* Degree of autonomy
* Tool privileges
* Data sensitivity
* External exposure
* Business criticality
* Identity privileges
* Transaction capability
* Financial authority
* Network access
* Persistence
* Human oversight

An agent capable of changing production systems requires substantially stronger testing than an agent limited to generating informational responses.

---

### 7. Agent Red-Team Scope

Scope should cover the complete agent execution ecosystem.

This may include:

* Agent model
* System instructions
* Planning engine
* Memory
* Context
* RAG
* Tools
* APIs
* Identity
* Authorization
* Workflow engine
* Human approval
* Agent-to-agent communication
* Infrastructure
* Monitoring

Testing only the model is insufficient when the security impact occurs through downstream execution.

### 12. Agent Adversarial Reconnaissance

Reconnaissance should determine how the agent operates within its authorized environment.

Testing may identify:

* Available tools
* Tool permissions
* Supported workflows
* Agent roles
* Accessible data
* Approval requirements
* Memory behavior
* External integrations
* Identity context
* Network reach

Reconnaissance should remain within the approved scope.

---

### 13. Agent Prompt Attack Red Teaming

Agent prompts should be tested for manipulation that changes the agent's intended behavior.

Testing should evaluate whether attackers can cause the agent to:

* Ignore security instructions
* Change goals
* Select unauthorized tools
* Reveal protected information
* Bypass workflow restrictions
* Execute unintended actions

The critical question is whether prompt manipulation crosses into unauthorized execution.

---

### 14. Agent Indirect Prompt Injection Red Teaming

Indirect prompt injection occurs when malicious instructions enter the agent through external content rather than directly through the user.

Potential sources include:

* Documents
* Websites
* Email
* Search results
* RAG repositories
* Tool responses
* API responses

The agent should distinguish untrusted content from authoritative instructions.

---

### 15. Agent Jailbreak Red Teaming

Agent jailbreak testing evaluates whether adversarial interactions can cause the agent to circumvent its intended restrictions.

Testing should evaluate whether jailbreaks result in:

* Unauthorized tool use
* Data access
* Policy circumvention
* Privilege escalation
* Workflow bypass
* Autonomous execution

A jailbreak that changes wording without creating security impact should not automatically be treated as equivalent to an authorization failure.

---

### 16. Agent Goal Manipulation Testing

Agentic systems introduce an additional attack surface: the goal.

Testing should determine whether an attacker can manipulate:

* Objectives
* Priorities
* Constraints
* Success criteria
* Task interpretation

The agent should preserve security constraints even when an attacker attempts to redefine the objective.

---

### 17. Agent Planning Manipulation Testing

The planning process should be evaluated for adversarial manipulation.

Testing may determine whether attackers can cause the agent to:

* Select unsafe steps
* Skip security checks
* Misinterpret prerequisites
* Create excessive permissions
* Execute unnecessary actions
* Chain tools improperly

A plan generated by the model should not itself authorize execution.

---

### 18. Agent Instruction Hierarchy Testing

Agents may receive instructions from multiple sources.

These may include:

* System instructions
* Developer instructions
* User instructions
* Retrieved content
* Tool output
* Memory
* Agent-to-agent messages

Testing should determine whether lower-trust inputs can improperly override higher-trust security constraints.

---

### 19. Agent Role Manipulation Testing

Role-based agent behavior should be assessed for privilege manipulation.

An attacker should not be able to convince an agent that it has become:

* Administrator
* Security operator
* Database administrator
* Financial approver
* System owner

unless the underlying identity and authorization systems independently establish that authority.

---

### 20. Agent Multi-Turn Attack Testing

Agents should be tested against attacks that gradually manipulate behavior across multiple interactions.

Testing should evaluate:

* State accumulation
* Progressive manipulation
* Context contamination
* Memory influence
* Goal drift
* Delayed execution

Single-turn testing is insufficient for agents with persistent state.

---

### 21. Agent Context Manipulation Testing

The agent's complete context should be considered an attack surface.

Testing should address:

* Context poisoning
* Malicious retrieved information
* Conflicting instructions
* Context flooding
* Instruction displacement
* Tool-output manipulation

---

### 22. Agent Long-Context Attack Testing

Large context windows can provide attackers with additional opportunities to manipulate agent behavior.

Testing should evaluate:

* Hidden instructions
* Instruction displacement
* Context saturation
* Malicious content placement
* Conflicting instructions
* Security-control degradation

---

### 23. Agent Memory Attack Testing

Persistent memory introduces long-lived attack possibilities.

Testing should determine whether attackers can:

* Inject malicious memories
* Modify trusted memories
* Retrieve another user's memory
* Create persistent behavioral influence
* Cause future unauthorized actions

Memory should therefore be treated as a security boundary rather than merely a convenience feature.

---

### 25. Agent Retrieval Authorization Testing

The agent should not retrieve information merely because the model can formulate a valid retrieval request.

Testing should determine whether:

* User permissions are enforced
* Agent identity is enforced
* Document permissions are enforced
* Tenant boundaries are enforced
* Retrieval scope is independently authorized

**Retrieval capability ≠ retrieval authorization.**

---

### 26. Agent Tool Abuse Red Teaming

Tool abuse testing evaluates whether an attacker can manipulate the agent into misusing legitimate tools.

Examples include:

* Calling tools outside intended workflows
* Supplying malicious parameters
* Chaining tools improperly
* Increasing execution frequency
* Using tools for unauthorized objectives

Tool gateways should independently enforce authorization.

---

### 27. Agent Tool-Parameter Manipulation Testing

Tool parameters should be treated as untrusted input.

Testing should assess whether attackers can manipulate:

* Resource identifiers
* File paths
* Queries
* Transaction amounts
* Recipient information
* API parameters
* Permission values

Parameter validation should exist outside the model.

---

### 28. Agent Tool Authorization Testing

Agent tool requests should pass through an independent authorization layer.

### 29. Agent Identity Red Teaming

Testing should determine whether an attacker can manipulate the identity under which the agent operates.

Relevant attacks include:

* Identity confusion
* Session manipulation
* Token substitution
* Service-account abuse
* Delegation abuse
* Identity spoofing

The identity system must remain authoritative.

---

### 30. Agent Authentication Red Teaming

Authentication mechanisms should be tested for:

* Bypass
* Session fixation
* Token theft
* Token replay
* Credential substitution
* Weak service authentication

Agent identity should be cryptographically and operationally attributable.

---

### 31. Agent Authorization Red Teaming

Authorization must be evaluated independently from agent reasoning.

Testing should determine whether an agent can perform actions outside its assigned permissions.

The fundamental boundary is:

     |
     v

     |
 +---+---+
 |       |

### 32. Agent Privilege Escalation Red Teaming

Testing should determine whether the agent can obtain or influence higher privileges.

Potential paths include:

* Tool misuse
* Credential exposure
* IAM manipulation
* Delegation abuse
* Configuration modification
* API authorization weaknesses

Privilege escalation should be assessed across the complete execution chain.

---

### 33. Agent Cross-User Attack Testing

Testing should determine whether an agent can be manipulated into accessing another user's:

* Conversations
* Memory
* Documents
* RAG data
* Tool results
* Transactions

User isolation must be enforced independently from model behavior.

---

### 34. Agent Cross-Tenant Attack Testing

Multi-tenant agents should be tested for tenant-boundary violations.

Testing should cover:

* Retrieval
* Memory
* APIs
* Tools
* Shared infrastructure
* Agent state

A model's ability to reference another tenant must never become sufficient for access.

---

### 35. Agent Data Exfiltration Testing

Testing should identify whether an attacker can manipulate the agent into extracting protected information.

Potential channels include:

* Direct output
* Tool results
* Memory
* RAG
* APIs
* Agent-to-agent messages
* External communication tools

---

### 36. Agent Secrets Exposure Testing

Agents should be tested for exposure of:

* API keys
* Access tokens
* Credentials
* Internal URLs
* Configuration
* Infrastructure information

Synthetic secrets should preferably be used in controlled assessments.

---

### 37. Agent Security-Control Bypass Testing

Testing should determine whether agent behavior can circumvent independent controls such as:

* IAM
* DLP
* Network restrictions
* Tool gateways
* Human approval
* API authorization
* Transaction controls

Security controls should remain effective even when the agent is compromised.

---

### 38. Agent Human-Approval Bypass Testing

Human-in-the-loop controls should be tested as security boundaries.

Testing should determine whether an agent can:

* Skip approval
* Misrepresent an action
* Trigger approval for a different action
* Execute before approval
* Split an action into smaller unauthorized steps

Human approval should authorize the actual action, not merely the agent's description of it.

---

### 39. Agent Autonomous Action Testing

Autonomous execution should be tested according to the agent's permitted autonomy.

Testing should evaluate whether the agent can:

* Execute outside its scope
* Continue after denial
* Repeat prohibited actions
* Escalate through chained operations
* Bypass stop conditions

High-impact actions should remain bounded by independent controls.

---

### 40. Agent Multi-Agent Attack Testing

Multi-agent systems should be assessed for attacks involving:

* Malicious agents
* Agent impersonation
* Instruction manipulation
* Delegation abuse
* Message tampering
* Privilege propagation
* Shared-memory manipulation

Trust should not automatically propagate between agents.

---

### 41. Agent-to-Agent Trust Testing

Each agent-to-agent interaction should have explicit trust assumptions.

Testing should determine whether a lower-trust agent can convince a higher-trust agent to:

* Execute unauthorized actions
* Reveal information
* Grant privileges
* Change configuration
* Access protected resources

---

Testing should determine whether adversarial influence survives:

* Memory resets
* Model changes
* Workflow changes

Potential persistence mechanisms include memory, stored configuration, poisoned data, agent state, and credentials.

Potential paths include:

* Internal applications
* Network services
* Credentials

The assessment should determine the maximum realistic impact of a successful agent compromise.

### 47. Agent Detection and Monitoring Testing

Red-team activity should determine whether agent attacks are detectable.

Monitoring should capture:

* Prompts
* Plans
* Tool requests
* Authorization decisions
* Tool execution

* Memory changes
* Agent-to-agent communication

The organization should evaluate whether security operations can respond to agent compromise.

Testing should include:

* Detection

* Credential revocation

The organization should test whether compromised agents can be safely contained and restored.

Containment may include:

### 50. Core Principle of Agent Red Teaming

Agent Red Teaming is a **controlled, authorized, risk-based, adversarial assurance discipline that evaluates the complete agentic execution chain—from input and model behavior through planning, memory, retrieval, identity, authorization, tool use, autonomous execution, downstream systems, detection, containment, and recovery.**

The assessment must preserve the fundamental security separation:

**Model behavior ≠ agent authority.
Agent intent ≠ authorization.
Agent plan ≠ permission.
Tool request ≠ tool authorization.
Tool capability ≠ tool permission.
Agent capability ≠ agent authority.
Agent identity ≠ user authority unless explicitly delegated.
Successful manipulation ≠ enterprise compromise.
A jailbreak ≠ unrestricted execution.
A test result ≠ permanent trust.
Red-team capability ≠ security assurance.**

Every significant finding should be attributable to the exact agent state, model version, prompt configuration, memory state, RAG state, tool configuration, identity, authorization context, and execution environment under assessment.

Material changes to **models, prompts, planning logic, memory, RAG, tools, agents, identities, privileges, workflows, APIs, infrastructure, security controls, or autonomy** should be capable of triggering renewed adversarial testing.

The central objective is therefore not simply to determine whether an attacker can manipulate an agent's reasoning, but whether the enterprise architecture ensures that **agent compromise remains bounded, observable, independently authorized, containable, recoverable, and incapable of automatically becoming enterprise compromise**.

* Acting autonomously

### 117. Core Control Principle

Agent Red Teaming controls must establish a **controlled, authorized, attributable, repeatable, evidence-producing mechanism for challenging the complete agentic system**.

The control chain should remain:

**Threat → Risk → Attack Scenario → Authorization → Exact Agent State → Adversarial Execution → Security-Control Response → Impact → Evidence → Finding → Remediation → Retest → Security Decision.**

The most important architectural separation must remain:

**Agent behavior ≠ authorization.
Agent intent ≠ permission.
Agent plan ≠ authorized action.
Tool request ≠ tool authorization.
Retrieval capability ≠ retrieval authorization.
Agent capability ≠ agent authority.
Successful manipulation ≠ enterprise compromise.
Red-team capability ≠ security assurance.**

Critical findings must be capable of triggering appropriate enforcement, including **release blocking, capability restriction, human-approval requirements, containment, suspension, rollback, remediation, retesting, or reauthorization** according to risk.

Testing should therefore demonstrate not only whether an agent can be manipulated, but whether the surrounding security architecture ensures that **successful manipulation remains bounded by independent identity, authorization, segmentation, monitoring, containment, and recovery controls**.
