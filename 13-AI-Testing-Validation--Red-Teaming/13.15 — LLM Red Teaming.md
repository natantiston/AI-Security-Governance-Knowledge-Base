# 13.15 — LLM Red Teaming

## Part 1 — LLM Red Teaming Foundations

### 1. Definition of LLM Red Teaming

LLM Red Teaming is an authorized adversarial security-assurance activity focused specifically on identifying, demonstrating, and evaluating security weaknesses in Large Language Model-based systems.

It evaluates not only the underlying LLM but the complete interaction between:

* Model
* System instructions
* User prompts
* Context
* Retrieved information
* Memory
* Tools
* Agents
* APIs
* Identity
* Authorization
* Security controls
* Monitoring

The objective is to understand how an adversary could manipulate an LLM and translate that manipulation into security, privacy, safety, operational, or business impact.

---

### 2. Purpose of LLM Red Teaming

The purpose of LLM red teaming is to provide realistic adversarial evidence about the security behavior of LLM-based systems.

It should determine whether an attacker can:

* Circumvent instructions
* Bypass guardrails
* Extract protected information
* Manipulate context
* Influence downstream actions
* Abuse tools
* Manipulate agents
* Escalate privileges
* Cross user or tenant boundaries
* Evade detection

---

### 3. LLM Red Teaming vs Conventional Red Teaming

Conventional red teaming evaluates enterprise systems from an attacker perspective. LLM red teaming adds model-specific attack surfaces and behavioral manipulation techniques.

```text id="llm31a"
Conventional Red Team
        |
        v
Network / Application / Identity
        |
        v
Vulnerability
        |
        v
Exploitation


LLM Red Team
        |
        v
Prompt / Context / Model / RAG / Memory
        |
        v
Behavior Manipulation
        |
        v
Tool / Agent / Authorization
        |
        v
Exploitation
```

LLM red teaming therefore complements conventional application, cloud, infrastructure, and penetration testing.

### 5. LLM Red Teaming Objectives

LLM red teaming should establish whether realistic adversarial behavior can compromise defined security objectives.

Primary objectives include:

1. Discover LLM-specific attack paths.
2. Validate security controls.
3. Identify behavioral weaknesses.
4. Demonstrate practical exploitation.
5. Determine attack-chain potential.
6. Measure blast radius.
7. Evaluate detection.
8. Evaluate containment.
9. Test recovery.
10. Produce actionable evidence.

---

### 6. Risk-Based LLM Red Teaming

Red-team depth should be proportional to LLM system risk.

Higher-risk systems may include LLMs that:

* Process sensitive information
* Access confidential enterprise data
* Execute privileged tools
* Operate autonomous agents
* Control business workflows
* Interact with external users
* Make high-impact recommendations or decisions

### 9. LLM Red-Team Rules of Engagement

Every engagement should have documented rules of engagement.

They should define:

* Authorized targets
* Testing period
* Approved attack classes
* Prohibited activities
* Test identities
* Data restrictions
* Tool restrictions
* Maximum permitted impact
* Stop conditions
* Escalation procedures

The rules should prevent adversarial testing from causing uncontrolled operational impact.

### 10. LLM Threat Modeling

Threat categories may include:

* Prompt injection
* Jailbreaking
* Instruction manipulation
* Context poisoning
* RAG attacks
* Memory attacks
* Data extraction
* Model manipulation
* Tool abuse
* Agent manipulation
* Authorization bypass
* Identity attacks

Threat models should guide testing while leaving room for novel attack-path discovery.

### 12. LLM Adversarial Reconnaissance

### 13. LLM Prompt Injection Red Teaming

Prompt injection testing evaluates whether attacker-controlled instructions can influence trusted LLM behavior.

Testing may target:

* System instructions
* Developer instructions
* User prompts
* Retrieved content
* Tool output
* Memory

The assessment should determine whether manipulation produces meaningful security consequences.

---

### 14. LLM Indirect Prompt Injection Red Teaming

Indirect prompt injection occurs when malicious instructions enter the LLM through content that the system retrieves or processes.

---

### 15. LLM Jailbreak Red Teaming

Jailbreak red teaming evaluates whether an attacker can circumvent defined LLM restrictions.

Testing may examine:

* Direct jailbreaks
* Multi-turn manipulation
* Role manipulation
* Obfuscation
* Context manipulation
* Language variation

A successful refusal bypass should be evaluated according to its actual security impact.

---

### 16. LLM Instruction Hierarchy Testing

The red team should evaluate whether lower-trust instructions can override higher-trust instructions.

The assessment should consider:

```text id="llm161g"
System Instruction
       |
       v
Developer Instruction
       |
       v
Application Context
       |
       v
User Instruction
       |
       v
External / Untrusted Content
```

The system should preserve the intended trust hierarchy.

---

### 17. LLM Role Manipulation Testing

Role manipulation testing evaluates whether attackers can cause the LLM to incorrectly interpret the identity or authority of an interaction.

Examples include attempts to make the LLM treat:

* A user as an administrator
* Untrusted content as system instructions
* Model output as authorization
* Agent messages as trusted commands

---

### 18. LLM Multi-Turn Attack Testing

LLM red teams should evaluate attacks that develop gradually across multiple interactions.

Testing should consider:

* Conversation history
* Context accumulation
* Memory
* Progressive instruction manipulation
* Trust establishment
* Persistent influence

Some attacks may not be observable during a single prompt.

---

### 19. LLM Context Manipulation Testing

Context manipulation evaluates whether changes to model context can alter security-relevant behavior.

Scenarios may include:

* Context poisoning
* Context flooding
* Instruction conflicts
* Ordering manipulation
* Malicious retrieved content
* Missing security context

---

### 20. LLM Long-Context Attack Testing

Long-context LLMs introduce additional attack surfaces.

Red-team scenarios may evaluate:

* Large untrusted content
* Instruction displacement
* Context saturation
* Hidden malicious instructions
* Conflicting instructions

The complete context supplied to the LLM should be preserved as evidence.

---

### 21. LLM Obfuscation Testing

Red teams should evaluate whether superficial transformations allow attackers to circumvent LLM security controls.

Testing may vary:

* Formatting
* Character representation
* Language
* Indirect phrasing
* Structural presentation

The objective is to evaluate the underlying security boundary rather than a single attack string.

---

### 22. LLM Multilingual Red Teaming

LLM security should be evaluated across relevant supported languages.

Testing may consider:

* Language switching
* Mixed-language prompts
* Translation
* Language-specific manipulation
* Security-control consistency

A security boundary should not depend solely on behavior in one language.

---

### 23. LLM Cross-Model Red Teaming

Organizations using multiple LLMs should assess whether model substitution changes security posture.

Testing may compare:

* Refusal behavior
* Prompt-injection resistance
* Tool behavior
* Data handling
* Agent behavior
* Security-control interaction

---

### 26. LLM RAG Red Teaming

### 32. LLM Identity and Authentication Testing

Identity controls should be tested against LLM-specific attack paths.

* Authentication bypass
* Session manipulation
* Identity switching
* Credential misuse
* Service-account abuse

---

### 33. LLM Authorization Testing

LLM red teams should independently evaluate authorization.

The assessment should determine whether model-generated requests can obtain capabilities beyond the user's authorized permissions.

A model's confidence, reasoning, or output must never be treated as authorization.

---

### 34. LLM Privilege Escalation Testing

The assessment should determine whether LLM manipulation can produce a privilege transition.

Testing should establish:

* Initial identity
* Initial privilege
* Exploitation path
* Requested privilege
* Authorization decision
* Effective privilege
* Resulting access

### 49. LLM Red-Team Findings and Remediation

Findings should describe the complete attack path rather than only the final symptom.

A finding should identify:

* Initial condition
* Vulnerability
* Exploitation technique
* Attack chain
* Security-control failure
* Privileges obtained
* Data accessed
* Business impact
* Detection status
* Containment status

Remediation should address the underlying weakness and should be followed by retesting.

### 50. Core Principle of LLM Red Teaming

LLM Red Teaming must be treated as a **realistic, authorized, risk-based adversarial assurance discipline that evaluates whether LLM-specific weaknesses can be exploited across the complete AI system and converted into meaningful security, privacy, safety, operational, or business impact**.

The assessment must extend beyond the LLM itself:

```text id="llm50l"
Attacker
   |
   v
Prompt / Context
   |
   v
LLM
   |
   +---- RAG
   +---- Memory
   +---- Tools
   +---- Agents
   |
   v
Identity / Authorization
   |
   v
Enterprise Systems
   |
   v
Business Impact
```

LLM red teaming should evaluate:

* Prompt injection
* Jailbreaking
* Instruction manipulation
* Context poisoning
* Long-context attacks
* Obfuscation
* Multilingual attacks
* RAG manipulation
* Memory attacks
* Model-version changes
* Tool abuse
* Agent manipulation
* Identity attacks
* Authorization bypass
* Privilege escalation
* Cross-user attacks
* Cross-tenant attacks
* Data extraction
* Secrets exposure
* Security-control bypass
* Persistence
* Lateral movement
* Detection
* Containment
* Recovery

The red team should seek realistic attack paths and meaningful impact rather than merely demonstrating that an LLM can produce an unexpected response.

Most importantly, LLM red teaming must preserve the separation between **model behavior and enterprise authority**:

**LLM capability ≠ authorization.
LLM output ≠ permission.
Tool request ≠ tool permission.
Agent plan ≠ authorized action.
Jailbreak success ≠ enterprise compromise.
LLM vulnerability ≠ unrestricted access.
Passing one LLM test ≠ universal security.
Red-team capability ≠ security assurance.**

The objective is not to prove that an LLM can never be manipulated. The objective is to establish evidence about **how the LLM behaves under realistic attack, what independent controls prevent that behavior from becoming unauthorized action, what impact remains possible, how attacks are detected, and whether the organization can contain and recover from compromise**.

Material changes to models, prompts, context, RAG, memory, tools, agents, APIs, identity, authorization, infrastructure, or security controls should be capable of triggering renewed LLM red teaming and regression assessment.
