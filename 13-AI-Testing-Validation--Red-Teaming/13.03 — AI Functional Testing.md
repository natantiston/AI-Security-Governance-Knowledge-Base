# 13.03 — AI Functional Testing

## Part 1 — AI Functional Testing Foundations

### 1. Definition of AI Functional Testing

AI functional testing is the systematic assessment of whether an AI system performs the functions it is designed and authorized to perform.

Unlike traditional software, AI functionality may be probabilistic, context-dependent, adaptive, or generated dynamically. Functional testing must therefore evaluate both conventional software behavior and AI-specific behavioral outcomes.

---

### 2. Purpose of AI Functional Testing

The purpose of functional testing is to establish evidence that required AI capabilities operate correctly under defined conditions.

Functional testing should determine whether:

* Required functions are available
* Inputs are processed correctly
* Outputs satisfy defined requirements
* Workflows execute correctly
* Errors are handled appropriately
* Integrations operate as designed
* AI behavior remains within defined functional boundaries

---

### 3. Functional Requirements

AI functional testing should originate from explicit functional requirements.

Requirements may define:

* Supported use cases
* Required inputs
* Expected outputs
* Workflow behavior
* Performance expectations
* Error handling
* Integration behavior
* Human interaction requirements

A functional requirement should be sufficiently precise to support objective testing.

---

### 5. AI System Under Test

The system under test should be explicitly identified.

The test scope may include:

* AI application
* Model
* Dataset
* Prompt
* Retrieval layer
* Tools
* APIs
* User interface
* Supporting infrastructure

Testing only the underlying model may fail to identify defects introduced by the surrounding application.

---

### 7. Positive Functional Testing

Positive testing verifies that the AI system performs correctly when provided with valid and expected inputs.

Examples include:

* Valid user requests
* Supported file formats
* Authorized operations
* Normal workflow sequences
* Expected API requests

Positive testing establishes baseline functional behavior.

---

### 8. Negative Functional Testing

Negative testing evaluates how the system behaves when inputs or conditions are invalid.

Examples include:

* Invalid input
* Missing information
* Unsupported format
* Incorrect parameters
* Invalid workflow sequence

The system should fail in an expected and controlled manner.

---

### 9. Boundary Functional Testing

Boundary testing evaluates behavior at or near defined functional limits.

Examples include:

* Maximum input length
* Minimum required information
* Maximum file size
* Token limits
* Maximum supported records
* Processing thresholds

Boundary failures can reveal defects that normal functional testing does not identify.

---

### 10. AI Input Testing

AI inputs should be tested for both functional correctness and supported usage conditions.

Testing may include:

* Text
* Images
* Audio
* Documents
* Structured data
* API requests
* Multi-modal inputs

Input testing should determine whether valid inputs are correctly processed and invalid inputs are appropriately rejected or handled.

---

### 11. AI Output Testing

Outputs should be evaluated against defined functional expectations.

Testing may assess:

* Format
* Completeness
* Required information
* Structural correctness
* Consistency
* Actionability

For generative systems, exact output matching may not always be appropriate. Functional assertions may instead evaluate whether required properties are present.

---

### 12. Deterministic vs Probabilistic Functionality

Traditional software often produces deterministic outputs for a given input.

AI systems may produce different but functionally acceptable outputs.

Therefore, functional testing may require:

* Output ranges
* Semantic assertions
* Required attributes
* Behavioral criteria
* Statistical thresholds

* Output requirements
* Error conditions
* Performance boundaries

* Application-to-model integration

* Correct request formatting

Testing should evaluate whether prompts produce the required behavior for approved use cases.

Changes to:

* System prompts
* Developer instructions
* Templates
* Few-shot examples

* Context handling

Instruction-following behavior should be evaluated against predefined functional requirements.

### 49. Functional Testing and Assurance

Functional testing establishes evidence about whether the AI system performs required functions under defined conditions.

It does **not**, by itself, establish:

* Security
* Privacy
* Fairness
* Robustness
* Safety
* Operational suitability

```text id="aift49i"
Functional Testing
       |
       v
Functional Evidence
       |
       +------> Security Testing
       +------> Robustness Testing
       +------> Privacy Testing
       +------> Reliability Testing
       +------> Validation
```

Functional correctness is one component of broader AI assurance.

---

### 50. Core Principle of AI Functional Testing

**AI functional testing must establish, through controlled and traceable evidence, that an AI system performs its intended functions according to defined requirements, approved use cases, and acceptable behavioral criteria. Functional testing must encompass not only the underlying model but the complete AI application and its material interactions with prompts, datasets, retrieval systems, tools, APIs, dependencies, users, and downstream workflows. Because AI systems may produce variable or probabilistic outputs, functional acceptance should evaluate defined behavioral properties and acceptable outcome ranges rather than relying exclusively on exact-output comparison. Testing must include positive, negative, boundary, integration, end-to-end, error-handling, recovery, and regression scenarios appropriate to risk. Functional test results must remain attributable to the exact system, model, data, configuration, and environment evaluated. Functional correctness establishes evidence that required capabilities work; it does not establish security, privacy, robustness, fairness, or overall operational trust.**

## Part 2 — AI Functional Testing Controls

### 51. AI Functional Testing Control Framework

The AI functional testing control framework establishes the controls required to demonstrate that AI systems perform their approved functions correctly and consistently within defined conditions.

The framework should govern:

* Functional requirements
* Test cases
* Test data
* Test environments
* Expected behavior
* Acceptance criteria
* Defect management
* Regression testing
* Evidence
* Functional release gates

---

### 52. Functional Test Planning Control

Every material AI capability should have a documented functional testing plan.

The plan should identify:

* Functions being tested
* Requirements being validated
* Test scenarios
* Test data
* Expected outcomes
* Acceptance criteria
* Test environment
* Required evidence
* Retesting requirements

Planning should occur before formal execution wherever practical.

---

### 53. Functional Test Scope Control

The scope of functional testing must correspond to the AI system's approved capabilities.

Scope should include material:

* Features
* User workflows
* Interfaces
* AI components
* Integrations
* Supported input types
* Output formats

Uncovered functionality should be explicitly identified rather than implicitly treated as tested.

---

### 54. Functional Requirement Mapping Control

Each material functional requirement should map to one or more functional tests.

```text id="aift54a"

        |
        v

        |
        v
Test Execution
        |
        v
Result
        |
        v

```

Requirements without supporting test evidence should be treated as functional assurance gaps.

---

### 55. Functional Test Case Control

Functional test cases must be uniquely identified and version-controlled.

Each test case should define:

* Test ID
* Requirement
* Objective
* Preconditions
* Input
* Expected behavior
* Acceptance criteria
* Execution procedure
* Evidence requirements

Material test modifications should be attributable.

---

### 56. Functional Test Data Control

Test data should be controlled throughout its lifecycle.

Controls should establish:

* Data source
* Dataset version
* Integrity
* Relevance
* Authorization
* Classification
* Retention

Test data should represent the conditions under which the AI functionality is expected to operate.

---

### 57. Functional Test Data Representativeness Control

Test data should adequately represent approved functional use cases.

The test dataset should consider:

* Normal inputs
* Typical users
* Edge cases
* Input diversity
* Expected operating conditions
* Material variations

Unrepresentative data can create misleading functional assurance.

---

### 58. Functional Test Environment Control

Functional testing must occur in a controlled environment appropriate to the test objective.

The environment should have known:

* Application version
* Model version
* Configuration
* Dependencies
* Dataset
* Infrastructure

Environmental differences should be documented when they could affect results.

---

### 59. Functional Environment Integrity Control

The integrity of the functional test environment should be verified before execution.

Controls should detect unauthorized changes to:

* Application components
* Models
* Prompts
* Configuration
* Dependencies
* Test datasets

---

### 60. AI Version Identification Control

Every functional test execution must identify the exact AI system version being tested.

Where applicable, records should include:

* Application version
* Model version
* Prompt version
* Dataset version
* Dependency versions
* Configuration version

---

### 61. Functional Configuration Control

Configurations affecting AI functionality should be version-controlled.

Examples include:

* Model parameters
* System instructions
* Temperature
* Retrieval settings
* Tool configuration
* API parameters
* Feature flags

Functional results should be associated with the configuration under which they were produced.

---

### 62. Functional Test Identity Control

Functional test activities must be attributable to a verified identity.

The architecture should distinguish:

* Developers
* Test engineers
* QA personnel
* Security testers
* Automated test workloads
* Approvers

Shared accounts should be avoided for material testing activities.

---

### 63. Functional Test Authorization Control

Access to execute or modify functional tests should be controlled.

Authorization should determine who may:

* Create tests
* Modify tests
* Execute tests
* Change expected results
* Override failures
* Approve results

Test execution authority should not automatically equal result-approval authority.

---

### 64. Positive Functional Testing Control

Positive test cases should verify that valid inputs produce the expected functional outcome.

Examples include:

* Supported requests
* Valid documents
* Normal workflows
* Correct parameters
* Authorized functionality

Positive tests establish expected baseline behavior.

### 65. Negative Functional Testing Control

Examples include:

* Invalid inputs

### 117. Core Control Principle

**AI functional testing controls must establish a continuously traceable mechanism for determining whether approved AI capabilities operate according to defined functional requirements and acceptance criteria. Every material function should map to controlled test cases and representative test data, with execution performed against an identified system, model, configuration, dataset, and environment. Controls must cover positive, negative, boundary, component, integration, end-to-end, multi-turn, multi-modal, error-handling, recovery, and regression scenarios according to risk. For probabilistic AI systems, functional acceptance must evaluate defined behavioral properties and acceptable outcome ranges rather than relying exclusively on exact-output matching. Material failures must be attributable, recorded, remediated, and retested, while critical failures should be capable of automatically blocking relevant lifecycle transitions. Functional testing establishes evidence that an AI capability performs as intended under defined conditions; it must not be incorrectly interpreted as evidence that the capability is secure, private, robust, fair, or suitable for unrestricted production use.**

### 177. Strategic Governance Principle

**AI functional testing governance must treat functional correctness as a continuously governed property rather than a permanent characteristic established by a single successful test cycle. Every material change to an AI model, dataset, prompt, application, dependency, integration, configuration, workflow, or operating context must be capable of triggering renewed functional assessment proportional to its impact. Governance must preserve traceability from requirements and approved use cases through test cases, execution, evidence, defects, remediation, retesting, and authorization decisions. Passing functional tests establishes evidence that defined capabilities operated acceptably under defined conditions; it does not prove that those capabilities will remain correct after subsequent changes or environmental shifts. The fundamental governance principle is that functional evidence supports trust but does not permanently own trust: continued production acceptance must remain attributable, risk-based, challengeable, and subject to revalidation whenever material conditions change.**

### 239. Continuous AI Functional Testing and Assurance Architecture

**Enterprise AI functional testing architecture must operate as a continuously assured technical system that establishes whether approved AI capabilities remain functionally correct across applications, models, prompts, datasets, retrieval systems, tools, APIs, dependencies, integrations, user journeys, and downstream workflows. The architecture must connect functional requirements to controlled test cases, representative test data, identified system versions, controlled configurations, automated and manual execution, evidence, defect management, regression testing, and release gates. It must support probabilistic and multi-modal AI behavior through behavioral assertions and defined acceptance ranges rather than relying exclusively on deterministic output comparison. Test environments, identities, datasets, and execution workloads must remain isolated and attributable; results and evidence must be integrity-protected; and mandatory functional gates must resist bypass, manipulation, and alternate deployment paths. Most importantly, functional testing capability must never equal functional assurance authority: a test harness, evaluation engine, automated pipeline, or development team may generate evidence, but acceptance must remain governed according to risk and appropriate independence. When models, prompts, datasets, applications, dependencies, configurations, workflows, or operating conditions materially change, the architecture must be capable of triggering regression testing, reassessment, revalidation, release blocking, containment, rollback, or other appropriate actions so that historical functional evidence cannot be incorrectly treated as permanent trust.**
