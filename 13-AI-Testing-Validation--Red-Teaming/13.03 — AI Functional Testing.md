# 13.03 — AI Functional Testing

## Part 1 — AI Functional Testing Foundations

### 1. Definition of AI Functional Testing

AI functional testing is the systematic assessment of whether an AI system performs the functions it is designed and authorized to perform.

Unlike traditional software, AI functionality may be probabilistic, context-dependent, adaptive, or generated dynamically. Functional testing must therefore evaluate both conventional software behavior and AI-specific behavioral outcomes.

---

### 2. Purpose of AI Functional Testing

The purpose of functional testing is to establish evidence that required AI capabilities operate correctly under defined conditions.

Functional testing should determine whether:

* Required functions are available
* Inputs are processed correctly
* Outputs satisfy defined requirements
* Workflows execute correctly
* Errors are handled appropriately
* Integrations operate as designed
* AI behavior remains within defined functional boundaries

---

### 3. Functional Requirements

AI functional testing should originate from explicit functional requirements.

Requirements may define:

* Supported use cases
* Required inputs
* Expected outputs
* Workflow behavior
* Performance expectations
* Error handling
* Integration behavior
* Human interaction requirements

A functional requirement should be sufficiently precise to support objective testing.

---

### 4. AI Functional Testing Lifecycle

Functional testing should operate throughout the AI lifecycle.

Functional testing should not be limited to the final pre-production stage.

---

### 5. AI System Under Test

The system under test should be explicitly identified.

The test scope may include:

* AI application
* Model
* Dataset
* Prompt
* Retrieval layer
* Tools
* APIs
* User interface
* Supporting infrastructure

Testing only the underlying model may fail to identify defects introduced by the surrounding application.

---

### 6. Functional Testing Scope

The functional testing scope should be determined by the intended AI use case.

Testing should cover all material functions that users, applications, or downstream systems depend upon.

For an AI assistant, for example, this may include:

```text id="aift06b"
User Request
     |
     v
Input Processing
     |
     v
Model
     |
     v
Retrieval / Tools
     |
     v
Response Generation
     |
     v
Output Handling
     |
     v
User / Enterprise System
```

---

### 7. Positive Functional Testing

Positive testing verifies that the AI system performs correctly when provided with valid and expected inputs.

Examples include:

* Valid user requests
* Supported file formats
* Authorized operations
* Normal workflow sequences
* Expected API requests

Positive testing establishes baseline functional behavior.

---

### 8. Negative Functional Testing

Negative testing evaluates how the system behaves when inputs or conditions are invalid.

Examples include:

* Invalid input
* Missing information
* Unsupported format
* Incorrect parameters
* Invalid workflow sequence

The system should fail in an expected and controlled manner.

---

### 9. Boundary Functional Testing

Boundary testing evaluates behavior at or near defined functional limits.

Examples include:

* Maximum input length
* Minimum required information
* Maximum file size
* Token limits
* Maximum supported records
* Processing thresholds

Boundary failures can reveal defects that normal functional testing does not identify.

---

### 10. AI Input Testing

AI inputs should be tested for both functional correctness and supported usage conditions.

Testing may include:

* Text
* Images
* Audio
* Documents
* Structured data
* API requests
* Multi-modal inputs

Input testing should determine whether valid inputs are correctly processed and invalid inputs are appropriately rejected or handled.

---

### 11. AI Output Testing

Outputs should be evaluated against defined functional expectations.

Testing may assess:

* Format
* Completeness
* Required information
* Structural correctness
* Consistency
* Actionability

For generative systems, exact output matching may not always be appropriate. Functional assertions may instead evaluate whether required properties are present.

---

### 12. Deterministic vs Probabilistic Functionality

Traditional software often produces deterministic outputs for a given input.

AI systems may produce different but functionally acceptable outputs.

Therefore, functional testing may require:

* Output ranges
* Semantic assertions
* Required attributes
* Behavioral criteria
* Statistical thresholds

```text id="aift12c"
Input
  |
  v
AI System
  |
  +----> Output A
  +----> Output B
  +----> Output C
          |
          v
   Functional Criteria
          |
          v
   Acceptable / Unacceptable
```

---

### 13. Functional Acceptance Criteria

Each material AI function should have defined acceptance criteria.

Criteria may specify:

* Required behavior
* Forbidden behavior
* Output requirements
* Error conditions
* Performance boundaries

Acceptance criteria should be established before formal testing wherever practical.

---

### 14. AI Use-Case Testing

Functional testing should represent the AI system's approved use cases.

Each material use case should identify:

* User
* Objective
* Input
* Expected workflow
* Expected outcome
* Functional acceptance criteria

Testing should verify that the implemented system supports its approved business purpose.

---

### 15. User Journey Testing

AI systems should be tested across complete user journeys rather than isolated requests.

```text id="aift15d"

 |
 v

 |
 v

 |
 v

 |
 v

 |
 v

 |
 v

 |
 v

```

This identifies defects that may appear only across multiple workflow steps.

---

### 16. End-to-End Functional Testing

End-to-end testing evaluates the complete AI workflow.

It should verify interactions between:

* User interface
* Application
* Model
* Data
* Retrieval
* Tools
* APIs
* Downstream systems

A component may function correctly in isolation while the complete workflow fails.

---

### 17. Component Functional Testing

Individual AI components should also be tested independently where practical.

Components may include:

* Prompt processor
* Model interface
* Retrieval service
* Tool connector
* Output validator
* Safety filter
* API gateway

Component testing enables faster identification of functional defects.

---

### 18. Integration Functional Testing

Integration testing evaluates whether AI components work correctly together.

Examples include:

* Application-to-model integration
* Model-to-RAG integration
* Agent-to-tool integration
* AI-to-API integration
* AI-to-database integration

Integration testing is particularly important because AI behavior can change when external context or tools are introduced.

---

### 19. API Functional Testing

AI APIs should be tested for functional correctness.

Testing should evaluate:

* Request structure
* Required parameters
* Response structure
* Error codes
* Authentication-dependent behavior
* Rate-limit behavior
* Version compatibility

---

### 20. Model Interface Functional Testing

The interface between the application and model should be tested independently.

Testing should verify:

* Correct model selection
* Correct request formatting
* Correct parameter handling
* Correct response parsing
* Correct error handling

A model may be functioning correctly while the application invokes it incorrectly.

---

### 21. Prompt Functional Testing

Prompts should be treated as functional components where they influence system behavior.

Testing should evaluate whether prompts produce the required behavior for approved use cases.

Changes to:

* System prompts
* Developer instructions
* Templates
* Few-shot examples

may require functional regression testing.

---

### 22. Instruction Following Testing

Functional testing should determine whether the AI system follows legitimate instructions correctly.

Testing may evaluate:

* Required task execution
* Formatting requirements
* Context handling
* Multi-step instructions
* Priority rules

Instruction-following behavior should be evaluated against predefined functional requirements.

---

### 23. Context Handling Testing

AI systems should be tested for correct handling of conversational or contextual information.

Testing should determine whether the system:

* Uses relevant context
* Ignores irrelevant context
* Preserves required information
* Handles conflicting context appropriately
* Maintains correct state

---

### 24. Multi-Turn Functional Testing

Conversational AI should be tested across multiple interactions.

```text id="aift24e"
Turn 1
  |
  v
Turn 2
  |
  v
Turn 3
  |
  v
Turn 4
  |
  v
Final Functional Outcome
```

Testing should determine whether earlier interactions affect later behavior correctly.

---

### 25. Stateful AI Functional Testing

Systems that maintain state should be tested for correct state transitions.

Testing may evaluate:

* Session state
* Conversation state
* Workflow state
* User preferences
* Transaction state

Unexpected state persistence can create functional defects.

---

### 26. Stateless AI Functional Testing

Stateless systems should be tested to ensure that unintended state is not retained between requests.

Testing should verify appropriate isolation between:

* Users
* Sessions
* Requests
* Tenants
* Workflows

---

### 27. RAG Functional Testing

Retrieval-augmented generation systems should be functionally tested across retrieval and generation.

Testing should determine whether:

* Relevant documents are retrieved
* Retrieved context reaches the model
* Appropriate context is used
* Irrelevant context is handled correctly
* Responses reflect available source information

---

### 28. Retrieval Functional Testing

Retrieval systems should be evaluated independently.

Testing may measure:

* Retrieval relevance
* Recall
* Ranking
* Filtering
* Query handling
* Metadata filtering

Functional retrieval failure can produce incorrect AI outputs even when the model itself performs correctly.

---

### 29. AI Tool Functional Testing

AI systems using tools should be tested for correct tool behavior.

Testing should determine whether the system:

* Selects the appropriate tool
* Provides valid parameters
* Processes tool responses correctly
* Handles tool failures
* Completes the intended workflow

Functional testing should remain separate from authorization testing.

---

### 30. Agent Functional Testing

Agent functionality should be tested across complete workflows.

 |
 v

 |
 v

 |
 v

 |
 v

Testing should determine whether the agent can complete its authorized tasks correctly and reliably.

---

### 31. Multi-Agent Functional Testing

Where multiple AI agents interact, testing should evaluate coordination.

Testing may cover:

* Message exchange
* Task delegation
* Role assignment
* Shared context
* Handoff
* Conflict handling
* Completion criteria

Unexpected agent interactions can produce functional failures not present in individual agents.

---

### 32. Human-in-the-Loop Functional Testing

AI systems requiring human approval should be tested across the human-AI workflow.

Testing should verify:

* Approval requests appear correctly
* Required information is displayed
* Human decisions are captured
* Approved actions proceed
* Rejected actions stop
* Timeout behavior operates correctly

---

### 33. Human Override Functional Testing

Where human override is part of the design, testing should establish that override mechanisms function correctly.

Testing should verify:

* Override availability
* Authorization
* Response time
* Action cancellation
* Recovery behavior

---

### 34. Error Handling Functional Testing

AI systems should be tested under expected error conditions.

Examples include:

* Model unavailable
* Retrieval unavailable
* Tool failure
* API timeout
* Invalid response
* Data unavailable

The system should transition into its defined error-handling behavior.

---

### 35. Graceful Degradation Testing

Where graceful degradation is required, functional testing should determine whether the system remains useful when components fail.

Examples include:

```text id="aift35g"

       |
       v

       |
       v
Fallback
       |
       +--> Reduced Capability
       |
       +--> Human Workflow
       |
       +--> Safe Service State
```

---

### 36. Recovery Functional Testing

Recovery behavior should be tested after failures.

Testing should determine whether the system:

* Restores service
* Preserves required state
* Avoids duplicate actions
* Correctly resumes workflows
* Maintains data consistency

---

### 37. Performance-Functional Testing

Performance can become a functional requirement when response time affects usability or business operations.

Testing may measure:

* Response time
* Throughput
* Processing time
* Concurrent workload
* Timeout behavior

Functional acceptance criteria should distinguish acceptable performance from purely optimization-related metrics.

---

### 38. Availability Functional Testing

Where availability is a functional requirement, testing should evaluate service continuity.

Testing may include:

* Service restart
* Failover
* Dependency outage
* Network interruption
* Capacity limitations

---

### 39. Data Transformation Testing

AI systems that transform or classify data should be tested for correct transformation behavior.

Examples include:

* Classification
* Extraction
* Summarization
* Translation
* Categorization
* Structured-data generation

Testing should verify both output structure and required semantic properties.

---

### 40. Structured Output Testing

Where AI output must conform to a schema, functional testing should validate the structure.

Testing should verify:

* Required fields
* Data types
* Valid values
* Field relationships
* Schema compliance

```text id="aift40h"
AI Output
    |
    v
Schema Validator
    |
    +--> Valid --> Continue
    |
    +--> Invalid --> Reject / Repair
```

---

### 41. Classification Functional Testing

AI classification systems should be tested against representative test cases.

Evaluation may consider:

* Correct classification
* False positives
* False negatives
* Confidence behavior
* Edge cases

Classification criteria should align with the intended business function.

---

### 42. Extraction Functional Testing

AI extraction systems should be tested for accurate identification and extraction of required information.

Testing should include:

* Complete documents
* Missing fields
* Ambiguous fields
* Different formats
* Noisy inputs

---

### 43. Summarization Functional Testing

Summarization systems should be tested for required functional properties.

Testing may evaluate:

* Required information retention
* Relevant content coverage
* Length constraints
* Format requirements
* Source alignment

Functional testing does not replace separate factuality or security testing.

---

### 44. Translation Functional Testing

AI translation functionality should be tested using representative language pairs and use cases.

Testing may examine:

* Meaning preservation
* Required terminology
* Format preservation
* Handling of ambiguous text
* Language-specific behavior

---

### 45. Multi-Modal Functional Testing

Multi-modal AI systems require testing across supported modalities.

Examples include:

* Text + image
* Text + audio
* Image + document
* Audio + text

Testing should also evaluate transitions between modalities.

---

### 46. Functional Regression Testing

Previously validated functionality should be retested after material changes.

Triggers may include:

* Model changes
* Prompt changes
* Application changes
* Dataset changes
* Dependency updates
* Provider changes

Regression testing determines whether new changes unintentionally break established functionality.

---

### 47. Functional Test Coverage

Functional test coverage should be measured against requirements and approved use cases.

Coverage should consider:

* Requirements
* User journeys
* Features
* Interfaces
* Components
* Failure modes
* Supported input types

High test volume does not necessarily equal high functional coverage.

---

### 48. Functional Test Evidence

Functional test results should generate traceable evidence.

Evidence should identify:

* System version
* Model version
* Test case
* Input
* Output
* Expected result
* Actual result
* Test environment
* Timestamp

This ensures that functional conclusions can be independently reviewed.

---

### 49. Functional Testing and Assurance

Functional testing establishes evidence about whether the AI system performs required functions under defined conditions.

It does **not**, by itself, establish:

* Security
* Privacy
* Fairness
* Robustness
* Safety
* Operational suitability

```text id="aift49i"
Functional Testing
       |
       v
Functional Evidence
       |
       +------> Security Testing
       +------> Robustness Testing
       +------> Privacy Testing
       +------> Reliability Testing
       +------> Validation
```

Functional correctness is one component of broader AI assurance.

---

### 50. Core Principle of AI Functional Testing

**AI functional testing must establish, through controlled and traceable evidence, that an AI system performs its intended functions according to defined requirements, approved use cases, and acceptable behavioral criteria. Functional testing must encompass not only the underlying model but the complete AI application and its material interactions with prompts, datasets, retrieval systems, tools, APIs, dependencies, users, and downstream workflows. Because AI systems may produce variable or probabilistic outputs, functional acceptance should evaluate defined behavioral properties and acceptable outcome ranges rather than relying exclusively on exact-output comparison. Testing must include positive, negative, boundary, integration, end-to-end, error-handling, recovery, and regression scenarios appropriate to risk. Functional test results must remain attributable to the exact system, model, data, configuration, and environment evaluated. Functional correctness establishes evidence that required capabilities work; it does not establish security, privacy, robustness, fairness, or overall operational trust.**
