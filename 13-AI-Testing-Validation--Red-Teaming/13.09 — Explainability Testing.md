# 13.09 — Explainability Testing

## Part 1 — Explainability Testing Foundations

### 1. Definition of AI Explainability Testing

AI Explainability Testing is the systematic evaluation of whether an AI system can provide meaningful, accurate, consistent, and appropriate explanations about its inputs, outputs, decisions, recommendations, or behavior.

The objective is not simply to determine whether an explanation exists. Testing must establish whether the explanation is:

* Relevant to the decision or output
* Consistent with the system's actual behavior
* Appropriate for its intended audience
* Understandable at the required level
* Sufficient for the applicable use case
* Resistant to misleading interpretation
* Traceable to the system state that produced it

---

### 2. Purpose of AI Explainability Testing

The purpose of explainability testing is to establish evidence that explanations provide useful insight into AI behavior without creating false confidence.

Testing should determine whether explanations support appropriate activities such as:

* User understanding
* Human review
* Decision challenge
* Error investigation
* Risk assessment
* Compliance review
* Audit
* Incident investigation
* Model debugging

Explainability should therefore be evaluated as a measurable AI-system property rather than assumed from the presence of an explanation interface.

---

### 3. Explainability Testing vs Transparency

Transparency concerns whether information about an AI system is made available.

Explainability concerns whether the system can provide meaningful information about why or how a particular output was produced.

For example:

| Property               | Question                                                     |
| ---------------------- | ------------------------------------------------------------ |
| Transparency           | What model is being used?                                    |
| Documentation          | What is the model intended to do?                            |
| Interpretability       | Can model behavior be understood?                            |
| Explainability         | Can this output or decision be meaningfully explained?       |
| Explainability testing | Does the explanation actually correspond to system behavior? |

A system can be transparent without producing useful explanations.

---

The lifecycle should be integrated with AI development, validation, release, governance, and monitoring activities.

---

### 5. Explainability Testing Objectives

Explainability testing should establish whether explanations satisfy defined objectives.

Objectives may include:

* Accuracy
* Consistency
* Relevance
* Completeness
* Stability
* Understandability
* Traceability
* Timeliness
* Reproducibility
* User usefulness

The appropriate objectives depend on the AI system's purpose, risk, audience, and decision impact.

---

### 6. Risk-Based Explainability Testing

Explainability testing should be proportional to AI risk.

Higher-risk systems may require deeper testing where AI outputs influence:

* Financial decisions
* Employment
* Access to services
* Security decisions
* Healthcare-related decisions
* Legal or compliance processes
* High-impact organizational decisions

Lower-risk systems may require simpler explanation testing focused on user understanding and operational transparency.

---

### 7. Explainability Test Scope

The testing scope should cover the complete explanation-producing mechanism.

This may include:

* Input data
* Features
* Prompts
* Context
* Retrieval results
* Model
* Model configuration
* Explanation method
* Explanation interface
* Human reviewer
* Final decision

Testing only the explanation interface may miss inaccuracies introduced by the underlying explanation mechanism.

---

### 8. AI System Under Explainability Testing

The system under test should be precisely identified.

The test record should capture, where applicable:

* Application version
* Model version
* Model configuration
* Prompt version
* Dataset version
* Retrieval configuration
* Explanation method
* Explanation parameters
* User role
* Test environment

This allows explanation results to be associated with the exact AI behavior being evaluated.

---

### 9. Explainability Requirements

Explainability requirements should define what users and reviewers need to understand.

Requirements may specify:

* What must be explained
* Who receives the explanation
* Required explanation detail
* Required terminology
* Explanation timing
* Required limitations
* Required confidence information
* Required supporting evidence

Requirements should be testable rather than expressed only as general statements such as "the AI must be explainable."

---

### 10. Explanation Target Definition

Testing must identify exactly what is being explained.

Possible targets include:

* Classification
* Prediction
* Recommendation
* Ranking
* Generated text
* Generated image
* Risk score
* Alert
* Automated action
* Agent decision
* Tool selection

An explanation appropriate for one target may be inappropriate for another.

---

### 11. Local Explainability Testing

Local explainability testing evaluates explanations for a specific prediction, decision, or output.

For example, a test may ask:

> Why did the system classify this transaction as suspicious?

The test should determine whether the explanation accurately identifies the factors that materially influenced that particular result.

---

### 12. Global Explainability Testing

Global explainability testing evaluates whether explanations provide meaningful understanding of overall model behavior.

Testing may examine:

* Important features
* General decision patterns
* Model limitations
* Behavioral tendencies
* Consistent relationships between inputs and outputs

Global explanations should not be assumed to accurately explain every individual decision.

---

### 13. Feature Importance Testing

Where feature importance is provided, testing should evaluate whether the reported important features correspond meaningfully to model behavior.

Testing may compare:

* Feature importance rankings
* Controlled feature changes
* Model-output changes
* Explanation changes

Unexpected discrepancies may indicate an explanation-quality problem.

---

### 14. Input Attribution Testing

Input attribution testing evaluates whether the system correctly identifies which portions of an input contributed to an output.

For language models, this may involve:

* Words
* Tokens
* Sentences
* Documents
* Retrieved passages
* Prompt components

For multimodal systems, it may include:

* Image regions
* Audio segments
* Text
* Video frames

---

### 15. Counterfactual Explainability Testing

Counterfactual testing evaluates whether explanations remain meaningful when relevant inputs are changed.

```text id="aiext15b"
Original Input
      |
      v
Original Output
      |
      v
Explanation
      |
      v
Controlled Input Change
      |
      v
New Output
      |
      v
New Explanation
      |
      v
Compare Behavior
```

Testing should determine whether meaningful changes in inputs produce appropriately corresponding changes in outputs and explanations.

---

### 16. Explanation Faithfulness Testing

Faithfulness testing evaluates whether an explanation actually reflects the mechanism influencing the AI output.

A system should not receive credit merely because its explanation sounds plausible.

Testing should compare explanation claims with controlled changes in the underlying inputs, model behavior, or decision pathway.

---

### 17. Explanation Consistency Testing

The same or materially equivalent conditions should produce sufficiently consistent explanations where consistency is an expected property.

Testing should identify unexplained variations caused by:

* Randomness
* Model changes
* Prompt changes
* Explanation configuration
* Retrieval changes
* Context changes

---

### 18. Explanation Stability Testing

Stability testing evaluates whether small, irrelevant changes produce disproportionately different explanations.

For example:

```text id="aiext18c"
Input A
  |
  v
Output X
  |
Explanation X

Input A + irrelevant variation
  |
  v
Output X
  |
Explanation Y
```

If the output remains materially unchanged but the explanation changes dramatically, the explanation mechanism may be unstable.

---

### 19. Explanation Completeness Testing

Testing should determine whether explanations contain the information necessary for the intended decision context.

Completeness does not necessarily mean revealing every internal model operation.

It means providing enough relevant information to satisfy the defined explanation objective.

---

### 20. Explanation Accuracy Testing

Explanation accuracy evaluates whether factual claims contained in explanations are correct.

Testing should identify:

* Unsupported claims
* Incorrect causal statements
* Invented reasoning
* Incorrect feature attribution
* Incorrect references
* Misrepresentation of model behavior

This is particularly important for generative AI systems capable of producing convincing but inaccurate explanations.

---

### 21. Explanation Relevance Testing

An explanation should focus on information relevant to the decision or output.

Testing should identify explanations containing:

* Irrelevant information
* Generic statements
* Boilerplate
* Unrelated factors
* Post-hoc rationalizations

An explanation can be factually correct while still being irrelevant to the decision being explained.

---

### 22. Explanation Understandability Testing

Explanations should be evaluated against the intended audience.

Testing may consider:

* Technical expertise
* Language
* Terminology
* Cognitive complexity
* Explanation length
* Required domain knowledge

A technically accurate explanation may still fail if the intended user cannot understand it.

---

### 23. Explanation Audience Testing

Different audiences may require different explanation forms.

Testing should evaluate explanations for:

* End users
* Analysts
* Administrators
* Developers
* Auditors
* Risk teams
* Regulators or authorized reviewers

The explanation should provide appropriate detail without exposing information that the recipient is not authorized to receive.

---

### 24. Explanation Consistency Across Users

Testing should evaluate whether materially equivalent users receive consistent explanations where appropriate.

Differences may be legitimate when caused by:

* User role
* Authorization
* Data access
* Context
* Language
* Workflow

Unexpected differences may indicate explanation or authorization defects.

---

### 25. Explainability Under Probabilistic Behavior

AI systems may produce different outputs or explanations for the same or similar inputs.

Testing must therefore distinguish:

* Legitimate probabilistic variation
* Unacceptable inconsistency
* Explanation instability
* Explanation inaccuracies

Acceptance criteria should account for the probabilistic nature of the underlying system.

---

### 26. Explainability Testing for Generative AI

Generative AI requires specialized explanation testing because a model may generate an explanation that sounds authoritative without accurately describing its internal processing.

Testing should evaluate whether the system falsely claims:

* It used a particular source
* It performed a particular calculation
* It followed a particular reasoning process
* It accessed a particular document
* It used a particular tool
* It considered a particular factor

Generated explanations should not automatically be treated as reliable evidence of internal model reasoning.

---

### 27. Prompt Explainability Testing

Prompts can materially influence AI behavior and therefore should be included in explainability testing.

Testing may evaluate whether explanations correctly reflect:

* System instructions
* User instructions
* Retrieved context
* Tool results
* Conversation history

Testing should also identify whether prompt changes produce explanation changes that are consistent with actual system behavior.

---

### 28. Context Explainability Testing

For context-dependent AI systems, testing should determine whether explanations accurately identify relevant contextual information.

This may include:

* Conversation history
* Retrieved documents
* User profile information
* System instructions
* Tool outputs

The explanation should not claim that information influenced the decision when it was not actually available to the model.

---

### 29. RAG Explainability Testing

RAG systems should be tested to determine whether explanations accurately represent retrieved sources.

Testing should verify:

* Source identification
* Citation correctness
* Retrieved-document relevance
* Source-to-output relationship
* Access authorization

A citation attached to an answer does not automatically prove that the cited source caused the answer.

---

### 30. Citation and Source Attribution Testing

Where AI systems provide citations or source references, testing should evaluate whether they are:

* Correct
* Relevant
* Accessible to the intended user
* Associated with the claimed information
* Consistent with retrieved content

Fabricated or mismatched citations should be treated as explainability failures.

---

### 31. Tool-Use Explainability Testing

AI systems that invoke tools should be tested for accurate representation of tool usage.

Testing should determine whether the system correctly identifies:

* Which tool was used
* Why the tool was used
* What information was obtained
* Whether the tool succeeded
* Whether the result influenced the final output

The model should not claim tool execution when the architecture shows that no tool was invoked.

---

### 32. Agent Explainability Testing

AI agents require testing of explanations across multi-step workflows.

Testing should examine:

* Goal interpretation
* Planning
* Tool selection
* Tool execution
* Intermediate results
* State changes
* Final action
* Human approvals

Agent explanations should not be assumed to represent an authoritative record of the actual execution path.

---

### 33. Multi-Agent Explainability Testing

Multi-agent systems should be tested for attribution across agent interactions.

Testing should determine whether the system can appropriately identify:

* Which agent generated information
* Which agent made a recommendation
* Which agent invoked a tool
* Which agent modified state
* Which agent produced the final result

---

### 34. Human-in-the-Loop Explainability Testing

Where humans review or approve AI decisions, testing should evaluate whether explanations provide sufficient information for meaningful human oversight.

Testing should determine whether reviewers can:

* Understand the AI output
* Identify important factors
* Detect potential errors
* Challenge the recommendation
* Make an informed override

Human presence alone does not establish effective explainability.

---

### 35. Explanation and Human Override Testing

Explainability should support meaningful human intervention.

Testing may evaluate whether a reviewer can determine:

* Why the AI made the recommendation
* What evidence supports it
* What uncertainties exist
* What would change the result

If explanations are misleading, human override may become ineffective even though an override mechanism technically exists.

---

### 36. Explanation Uncertainty Testing

Where uncertainty information is appropriate, testing should evaluate whether it accurately represents uncertainty.

Testing should identify:

* False confidence
* Missing uncertainty
* Misleading confidence values
* Inconsistent confidence explanations

A confident explanation should not be interpreted as evidence that the underlying prediction is reliable.

---

### 37. Explanation Limitation Testing

AI systems should be tested to determine whether important limitations are communicated appropriately.

Testing may examine whether the system identifies:

* Missing information
* Data limitations
* Model limitations
* Out-of-distribution conditions
* Uncertainty
* Known failure modes

Explanations that omit material limitations may create false assurance.

---

### 38. Explainability and Privacy Testing

Explainability must not become a mechanism for disclosing protected information.

Testing should verify that explanations do not expose:

* Personal information
* Sensitive attributes
* Confidential records
* Other users' data
* Hidden prompts
* Restricted retrieval content

Explainability and privacy requirements must therefore be evaluated together where they interact.

---

### 39. Explainability and Security Testing

Explanations can create additional security exposure.

Testing should determine whether explanations reveal:

* System prompts
* Internal architecture
* Security controls
* Credentials or secrets
* Restricted policies
* Hidden tool information
* Security-sensitive implementation details

Explanations should provide useful transparency without unnecessarily exposing attack-enabling information.

---

### 40. Explainability Under Adversarial Conditions

Explainability should be tested under adversarial inputs.

Testing may examine whether attackers can manipulate explanations through:

* Prompt injection
* Context manipulation
* Malicious documents
* Crafted inputs
* Retrieval poisoning
* Tool manipulation

The explanation mechanism should not become an additional channel for attacker-controlled misinformation.

---

### 41. Explanation Robustness Testing

Explainability should remain meaningful under relevant input and environmental variations.

Testing may introduce controlled changes to:

* Input structure
* Wording
* Context
* Data quality
* Retrieval results
* Model configuration

The objective is to determine whether explanation quality degrades unexpectedly.

---

### 42. Explanation Regression Testing

Material changes should trigger explainability regression testing.

Regression tests should cover known failures involving:

* Incorrect attribution
* Inconsistent explanations
* False citations
* Missing uncertainty
* Misleading reasoning
* Tool-use misrepresentation

Previous explanation failures should remain testable after system changes.

---

### 43. Explainability Test Evidence

Explainability testing must produce evidence sufficient to demonstrate what was evaluated.

Evidence should include:

* Test case
* Input
* Output
* Explanation
* Model version
* Prompt/context
* Explanation method
* Evaluation criteria
* Test environment
* Tester
* Timestamp
* Result

Evidence should allow an independent reviewer to determine whether the explanation actually supports the claimed behavior.

---

### 44. Explainability Findings

Explainability findings should identify weaknesses such as:

* Inaccurate explanations
* Unsupported causal claims
* Incorrect attribution
* Explanation instability
* Missing information
* Misleading confidence
* False citations
* Incorrect tool attribution
* Privacy leakage
* Security exposure

Findings should be linked to the underlying system component and risk.

---

### 45. Explainability Defect Remediation

Explainability defects should be remediated at their underlying source.

Possible remediation may involve:

* Model changes
* Prompt changes
* Explanation algorithms
* Retrieval changes
* Attribution methods
* User-interface changes
* Evidence-linking mechanisms
* Tool-execution logging
* Human-review workflows

Simply rewriting explanation wording may not correct an underlying faithfulness problem.

---

### 46. Explainability Retesting

Material explainability remediation must be retested.

Retesting should verify that:

1. The original explanation defect is corrected.
2. Explanations remain faithful to actual system behavior.
3. No new privacy or security exposure was introduced.
4. Explanation quality remains acceptable across relevant scenarios.
5. Previously validated explanation properties remain intact.

---

### 47. Explainability Testing Independence

High-risk explainability assessments should receive appropriate independent validation.

Independent testing may be performed by:

* AI assurance teams
* Model validation
* AI security
* Risk specialists
* Internal audit
* Qualified external assessors

Independence reduces the risk of accepting explanations simply because they appear plausible to the system's developers.

---

### 48. Explainability Test Coverage

Explainability test coverage should reflect the AI system's meaningful behavioral surface.

Coverage should consider:

* Major use cases
* High-risk decisions
* Important user groups
* Model behaviors
* Prompt variations
* Context variations
* Retrieval scenarios
* Tool usage
* Agent workflows
* Known failure modes
* Adversarial conditions

Coverage should be measured against risk rather than simply the number of executed test cases.

---

### 49. Explainability Testing and Assurance

Explainability testing generates evidence about whether explanations satisfy defined requirements under defined conditions.

Assurance requires determining whether that evidence is:

* Sufficient
* Current
* Relevant
* Reliable
* Traceable
* Independent where required

```text id="aiext49d"
Explainability Requirement
          |
          v
Test Scenario
          |
          v
AI Behavior + Explanation
          |
          v
Faithfulness / Accuracy / Relevance
          |
          v
Evidence
          |
          v
Assurance Decision
```

**An explanation that sounds reasonable is not necessarily an explanation that accurately represents AI behavior.**

---

### 50. Core Principle of AI Explainability Testing

**AI explainability testing must establish evidence that explanations are meaningful representations of defined AI behavior, not merely plausible narratives generated after the fact.**

Testing must evaluate explainability across the complete AI system, including models, applications, prompts, context, retrieval, tools, agents, human review, and explanation mechanisms. It should assess faithfulness, accuracy, relevance, consistency, stability, completeness, understandability, uncertainty, source attribution, tool attribution, privacy, and security according to risk.

Every explanation result must be associated with the exact system state, model, configuration, prompt, context, data, explanation method, and evaluation conditions that produced it. Explainability evidence must be attributable, integrity-protected, and traceable.

**Explanation capability ≠ Explanation accuracy ≠ Assurance.**

A system may generate detailed explanations while those explanations remain inaccurate, incomplete, unstable, misleading, or disconnected from the actual causal behavior of the system. Therefore, passing an explainability test establishes evidence for defined conditions at a defined point in time; it does not establish permanent explainability assurance.

Material changes to the model, prompts, context, retrieval, tools, agents, explanation method, datasets, configuration, or operating environment must be capable of triggering renewed explainability testing, regression testing, validation, or reassessment.
