# 13.09 — Explainability Testing

## Part 1 — Explainability Testing Foundations

### 1. Definition of AI Explainability Testing

AI Explainability Testing is the systematic evaluation of whether an AI system can provide meaningful, accurate, consistent, and appropriate explanations about its inputs, outputs, decisions, recommendations, or behavior.

The objective is not simply to determine whether an explanation exists. Testing must establish whether the explanation is:

* Relevant to the decision or output
* Consistent with the system's actual behavior
* Appropriate for its intended audience
* Understandable at the required level
* Sufficient for the applicable use case
* Resistant to misleading interpretation
* Traceable to the system state that produced it

---

### 2. Purpose of AI Explainability Testing

The purpose of explainability testing is to establish evidence that explanations provide useful insight into AI behavior without creating false confidence.

Testing should determine whether explanations support appropriate activities such as:

* User understanding
* Human review
* Decision challenge
* Error investigation
* Risk assessment
* Compliance review
* Audit
* Incident investigation
* Model debugging

Explainability should therefore be evaluated as a measurable AI-system property rather than assumed from the presence of an explanation interface.

---

### 3. Explainability Testing vs Transparency

Transparency concerns whether information about an AI system is made available.

Explainability concerns whether the system can provide meaningful information about why or how a particular output was produced.

For example:

| Property               | Question                                                     |
| ---------------------- | ------------------------------------------------------------ |
| Transparency           | What model is being used?                                    |
| Documentation          | What is the model intended to do?                            |
| Interpretability       | Can model behavior be understood?                            |
| Explainability         | Can this output or decision be meaningfully explained?       |
| Explainability testing | Does the explanation actually correspond to system behavior? |

A system can be transparent without producing useful explanations.

### 5. Explainability Testing Objectives

Explainability testing should establish whether explanations satisfy defined objectives.

Objectives may include:

* Accuracy
* Consistency
* Relevance
* Completeness
* Stability
* Understandability
* Traceability
* Timeliness
* Reproducibility
* User usefulness

The appropriate objectives depend on the AI system's purpose, risk, audience, and decision impact.

---

### 6. Risk-Based Explainability Testing

Explainability testing should be proportional to AI risk.

Higher-risk systems may require deeper testing where AI outputs influence:

* Financial decisions
* Employment
* Access to services
* Security decisions
* Healthcare-related decisions
* Legal or compliance processes
* High-impact organizational decisions

Lower-risk systems may require simpler explanation testing focused on user understanding and operational transparency.

---

### 7. Explainability Test Scope

The testing scope should cover the complete explanation-producing mechanism.

This may include:

* Input data
* Features
* Prompts
* Context
* Retrieval results
* Model
* Model configuration
* Explanation method
* Explanation interface
* Human reviewer
* Final decision

Testing only the explanation interface may miss inaccuracies introduced by the underlying explanation mechanism.

---

### 8. AI System Under Explainability Testing

The system under test should be precisely identified.

The test record should capture, where applicable:

* Application version
* Model version
* Model configuration
* Prompt version
* Dataset version
* Retrieval configuration
* Explanation method
* Explanation parameters
* User role
* Test environment

This allows explanation results to be associated with the exact AI behavior being evaluated.

---

### 9. Explainability Requirements

Explainability requirements should define what users and reviewers need to understand.

Requirements may specify:

* What must be explained
* Who receives the explanation
* Required explanation detail
* Required terminology
* Explanation timing
* Required limitations
* Required confidence information
* Required supporting evidence

Requirements should be testable rather than expressed only as general statements such as "the AI must be explainable."

---

### 10. Explanation Target Definition

Testing must identify exactly what is being explained.

Possible targets include:

* Classification
* Prediction
* Recommendation
* Ranking
* Generated text
* Generated image
* Risk score
* Alert
* Automated action
* Agent decision
* Tool selection

An explanation appropriate for one target may be inappropriate for another.

---

### 11. Local Explainability Testing

Local explainability testing evaluates explanations for a specific prediction, decision, or output.

For example, a test may ask:

> Why did the system classify this transaction as suspicious?

The test should determine whether the explanation accurately identifies the factors that materially influenced that particular result.

---

### 12. Global Explainability Testing

Global explainability testing evaluates whether explanations provide meaningful understanding of overall model behavior.

Testing may examine:

* Important features
* General decision patterns
* Model limitations
* Behavioral tendencies
* Consistent relationships between inputs and outputs

Global explanations should not be assumed to accurately explain every individual decision.

---

### 13. Feature Importance Testing

Where feature importance is provided, testing should evaluate whether the reported important features correspond meaningfully to model behavior.

Testing may compare:

* Feature importance rankings
* Controlled feature changes
* Model-output changes
* Explanation changes

Unexpected discrepancies may indicate an explanation-quality problem.

---

### 14. Input Attribution Testing

Input attribution testing evaluates whether the system correctly identifies which portions of an input contributed to an output.

For language models, this may involve:

* Words
* Tokens
* Sentences
* Documents
* Retrieved passages
* Prompt components

For multimodal systems, it may include:

* Image regions
* Audio segments
* Text
* Video frames

---

### 15. Counterfactual Explainability Testing

Counterfactual testing evaluates whether explanations remain meaningful when relevant inputs are changed.

```text id="aiext15b"
Original Input
      |
      v
Original Output
      |
      v
Explanation
      |
      v
Controlled Input Change
      |
      v
New Output
      |
      v
New Explanation
      |
      v
Compare Behavior
```

Testing should determine whether meaningful changes in inputs produce appropriately corresponding changes in outputs and explanations.

---

### 16. Explanation Faithfulness Testing

Faithfulness testing evaluates whether an explanation actually reflects the mechanism influencing the AI output.

A system should not receive credit merely because its explanation sounds plausible.

Testing should compare explanation claims with controlled changes in the underlying inputs, model behavior, or decision pathway.

---

### 17. Explanation Consistency Testing

The same or materially equivalent conditions should produce sufficiently consistent explanations where consistency is an expected property.

Testing should identify unexplained variations caused by:

* Randomness
* Model changes
* Prompt changes
* Explanation configuration
* Retrieval changes
* Context changes

---

### 18. Explanation Stability Testing

Stability testing evaluates whether small, irrelevant changes produce disproportionately different explanations.

For example:

```text id="aiext18c"
Input A
  |
  v
Output X
  |
Explanation X

Input A + irrelevant variation
  |
  v
Output X
  |
Explanation Y
```

If the output remains materially unchanged but the explanation changes dramatically, the explanation mechanism may be unstable.

---

### 19. Explanation Completeness Testing

Testing should determine whether explanations contain the information necessary for the intended decision context.

Completeness does not necessarily mean revealing every internal model operation.

It means providing enough relevant information to satisfy the defined explanation objective.

---

### 20. Explanation Accuracy Testing

Explanation accuracy evaluates whether factual claims contained in explanations are correct.

Testing should identify:

* Unsupported claims
* Incorrect causal statements
* Invented reasoning
* Incorrect feature attribution
* Incorrect references
* Misrepresentation of model behavior

This is particularly important for generative AI systems capable of producing convincing but inaccurate explanations.

---

### 21. Explanation Relevance Testing

An explanation should focus on information relevant to the decision or output.

Testing should identify explanations containing:

* Irrelevant information
* Generic statements
* Boilerplate
* Unrelated factors
* Post-hoc rationalizations

An explanation can be factually correct while still being irrelevant to the decision being explained.

---

### 22. Explanation Understandability Testing

Explanations should be evaluated against the intended audience.

Testing may consider:

* Technical expertise
* Language
* Terminology
* Cognitive complexity
* Explanation length
* Required domain knowledge

A technically accurate explanation may still fail if the intended user cannot understand it.

---

### 23. Explanation Audience Testing

Different audiences may require different explanation forms.

Testing should evaluate explanations for:

* End users
* Analysts
* Administrators
* Developers
* Auditors
* Risk teams
* Regulators or authorized reviewers

The explanation should provide appropriate detail without exposing information that the recipient is not authorized to receive.

---

### 24. Explanation Consistency Across Users

Testing should evaluate whether materially equivalent users receive consistent explanations where appropriate.

Differences may be legitimate when caused by:

* User role
* Authorization
* Data access
* Context
* Language
* Workflow

Unexpected differences may indicate explanation or authorization defects.

---

### 25. Explainability Under Probabilistic Behavior

AI systems may produce different outputs or explanations for the same or similar inputs.

Testing must therefore distinguish:

* Legitimate probabilistic variation
* Unacceptable inconsistency
* Explanation instability
* Explanation inaccuracies

Acceptance criteria should account for the probabilistic nature of the underlying system.

---

### 26. Explainability Testing for Generative AI

Generative AI requires specialized explanation testing because a model may generate an explanation that sounds authoritative without accurately describing its internal processing.

Testing should evaluate whether the system falsely claims:

* It used a particular source
* It performed a particular calculation
* It followed a particular reasoning process
* It accessed a particular document
* It used a particular tool
* It considered a particular factor

Generated explanations should not automatically be treated as reliable evidence of internal model reasoning.

---

### 27. Prompt Explainability Testing

Prompts can materially influence AI behavior and therefore should be included in explainability testing.

Testing may evaluate whether explanations correctly reflect:

* System instructions
* User instructions
* Retrieved context
* Tool results
* Conversation history

Testing should also identify whether prompt changes produce explanation changes that are consistent with actual system behavior.

---

### 28. Context Explainability Testing

For context-dependent AI systems, testing should determine whether explanations accurately identify relevant contextual information.

This may include:

* Conversation history
* Retrieved documents
* User profile information
* System instructions
* Tool outputs

The explanation should not claim that information influenced the decision when it was not actually available to the model.

---

### 29. RAG Explainability Testing

RAG systems should be tested to determine whether explanations accurately represent retrieved sources.

Testing should verify:

* Source identification
* Citation correctness
* Retrieved-document relevance
* Source-to-output relationship
* Access authorization

A citation attached to an answer does not automatically prove that the cited source caused the answer.

---

### 30. Citation and Source Attribution Testing

Where AI systems provide citations or source references, testing should evaluate whether they are:

* Correct
* Relevant
* Accessible to the intended user
* Associated with the claimed information
* Consistent with retrieved content

Fabricated or mismatched citations should be treated as explainability failures.

---

### 31. Tool-Use Explainability Testing

AI systems that invoke tools should be tested for accurate representation of tool usage.

Testing should determine whether the system correctly identifies:

* Which tool was used
* Why the tool was used
* What information was obtained
* Whether the tool succeeded
* Whether the result influenced the final output

The model should not claim tool execution when the architecture shows that no tool was invoked.

---

### 32. Agent Explainability Testing

AI agents require testing of explanations across multi-step workflows.

Testing should examine:

* Goal interpretation
* Planning
* Tool selection
* Tool execution
* Intermediate results
* State changes
* Final action
* Human approvals

Agent explanations should not be assumed to represent an authoritative record of the actual execution path.

---

### 33. Multi-Agent Explainability Testing

Multi-agent systems should be tested for attribution across agent interactions.

Testing should determine whether the system can appropriately identify:

* Which agent generated information
* Which agent made a recommendation
* Which agent invoked a tool
* Which agent modified state
* Which agent produced the final result

---

### 34. Human-in-the-Loop Explainability Testing

Where humans review or approve AI decisions, testing should evaluate whether explanations provide sufficient information for meaningful human oversight.

Testing should determine whether reviewers can:

* Understand the AI output
* Identify important factors
* Detect potential errors
* Challenge the recommendation
* Make an informed override

Human presence alone does not establish effective explainability.

---

### 35. Explanation and Human Override Testing

Explainability should support meaningful human intervention.

Testing may evaluate whether a reviewer can determine:

* Why the AI made the recommendation
* What evidence supports it
* What uncertainties exist
* What would change the result

If explanations are misleading, human override may become ineffective even though an override mechanism technically exists.

---

### 36. Explanation Uncertainty Testing

Where uncertainty information is appropriate, testing should evaluate whether it accurately represents uncertainty.

Testing should identify:

* False confidence
* Missing uncertainty
* Misleading confidence values
* Inconsistent confidence explanations

A confident explanation should not be interpreted as evidence that the underlying prediction is reliable.

---

### 37. Explanation Limitation Testing

AI systems should be tested to determine whether important limitations are communicated appropriately.

Testing may examine whether the system identifies:

* Missing information
* Data limitations
* Model limitations
* Out-of-distribution conditions
* Uncertainty
* Known failure modes

Explanations that omit material limitations may create false assurance.

---

### 38. Explainability and Privacy Testing

Explainability must not become a mechanism for disclosing protected information.

Testing should verify that explanations do not expose:

* Personal information
* Sensitive attributes
* Confidential records
* Other users' data
* Hidden prompts
* Restricted retrieval content

Explainability and privacy requirements must therefore be evaluated together where they interact.

---

### 39. Explainability and Security Testing

Explanations can create additional security exposure.

Testing should determine whether explanations reveal:

* System prompts
* Internal architecture
* Security controls
* Credentials or secrets
* Restricted policies
* Hidden tool information
* Security-sensitive implementation details

Explanations should provide useful transparency without unnecessarily exposing attack-enabling information.

---

### 40. Explainability Under Adversarial Conditions

Explainability should be tested under adversarial inputs.

Testing may examine whether attackers can manipulate explanations through:

* Prompt injection
* Context manipulation
* Malicious documents
* Crafted inputs
* Retrieval poisoning
* Tool manipulation

The explanation mechanism should not become an additional channel for attacker-controlled misinformation.

---

### 41. Explanation Robustness Testing

Explainability should remain meaningful under relevant input and environmental variations.

Testing may introduce controlled changes to:

* Input structure
* Wording
* Context
* Data quality
* Retrieval results
* Model configuration

The objective is to determine whether explanation quality degrades unexpectedly.

---

### 42. Explanation Regression Testing

Material changes should trigger explainability regression testing.

Regression tests should cover known failures involving:

* Incorrect attribution
* Inconsistent explanations
* False citations
* Missing uncertainty
* Misleading reasoning
* Tool-use misrepresentation

Previous explanation failures should remain testable after system changes.

---

### 43. Explainability Test Evidence

Explainability testing must produce evidence sufficient to demonstrate what was evaluated.

Evidence should include:

* Test case
* Input
* Output
* Explanation
* Model version
* Prompt/context
* Explanation method
* Evaluation criteria
* Test environment
* Tester
* Timestamp
* Result

Evidence should allow an independent reviewer to determine whether the explanation actually supports the claimed behavior.

---

### 44. Explainability Findings

Explainability findings should identify weaknesses such as:

* Inaccurate explanations
* Unsupported causal claims
* Incorrect attribution
* Explanation instability
* Missing information
* Misleading confidence
* False citations
* Incorrect tool attribution
* Privacy leakage
* Security exposure

Findings should be linked to the underlying system component and risk.

---

### 45. Explainability Defect Remediation

Explainability defects should be remediated at their underlying source.

Possible remediation may involve:

* Model changes
* Prompt changes
* Explanation algorithms
* Retrieval changes
* Attribution methods
* User-interface changes
* Evidence-linking mechanisms
* Tool-execution logging
* Human-review workflows

Simply rewriting explanation wording may not correct an underlying faithfulness problem.

---

### 46. Explainability Retesting

Material explainability remediation must be retested.

Retesting should verify that:

1. The original explanation defect is corrected.
2. Explanations remain faithful to actual system behavior.
3. No new privacy or security exposure was introduced.
4. Explanation quality remains acceptable across relevant scenarios.
5. Previously validated explanation properties remain intact.

---

### 47. Explainability Testing Independence

High-risk explainability assessments should receive appropriate independent validation.

Independent testing may be performed by:

* AI assurance teams
* Model validation
* AI security
* Risk specialists
* Internal audit
* Qualified external assessors

Independence reduces the risk of accepting explanations simply because they appear plausible to the system's developers.

---

### 48. Explainability Test Coverage

Explainability test coverage should reflect the AI system's meaningful behavioral surface.

Coverage should consider:

* Major use cases
* High-risk decisions
* Important user groups
* Model behaviors
* Prompt variations
* Context variations
* Retrieval scenarios
* Tool usage
* Agent workflows
* Known failure modes
* Adversarial conditions

Coverage should be measured against risk rather than simply the number of executed test cases.

---

### 49. Explainability Testing and Assurance

Explainability testing generates evidence about whether explanations satisfy defined requirements under defined conditions.

Assurance requires determining whether that evidence is:

* Sufficient
* Current
* Relevant
* Reliable
* Traceable
* Independent where required

```text id="aiext49d"
Explainability Requirement
          |
          v
Test Scenario
          |
          v
AI Behavior + Explanation
          |
          v
Faithfulness / Accuracy / Relevance
          |
          v
Evidence
          |
          v
Assurance Decision
```

**An explanation that sounds reasonable is not necessarily an explanation that accurately represents AI behavior.**

---

### 50. Core Principle of AI Explainability Testing

**AI explainability testing must establish evidence that explanations are meaningful representations of defined AI behavior, not merely plausible narratives generated after the fact.**

Testing must evaluate explainability across the complete AI system, including models, applications, prompts, context, retrieval, tools, agents, human review, and explanation mechanisms. It should assess faithfulness, accuracy, relevance, consistency, stability, completeness, understandability, uncertainty, source attribution, tool attribution, privacy, and security according to risk.

Every explanation result must be associated with the exact system state, model, configuration, prompt, context, data, explanation method, and evaluation conditions that produced it. Explainability evidence must be attributable, integrity-protected, and traceable.

**Explanation capability ≠ Explanation accuracy ≠ Assurance.**

A system may generate detailed explanations while those explanations remain inaccurate, incomplete, unstable, misleading, or disconnected from the actual causal behavior of the system. Therefore, passing an explainability test establishes evidence for defined conditions at a defined point in time; it does not establish permanent explainability assurance.

Material changes to the model, prompts, context, retrieval, tools, agents, explanation method, datasets, configuration, or operating environment must be capable of triggering renewed explainability testing, regression testing, validation, or reassessment.

## Part 2 — AI Explainability Testing Controls

### 51. AI Explainability Testing Control Framework

The AI Explainability Testing Control Framework establishes the controls required to determine whether explanations generated or presented by an AI system are accurate, faithful, relevant, understandable, consistent, and appropriate for the intended use.

The framework should connect requirements, AI behavior, explanation mechanisms, testing, evidence, findings, remediation, and ongoing assurance.

```text id="aiext51a"

          |
          v

          |
          v

          |
          v

          |
          v

          |
     +----+----+
     |         |
     v         v
Remediation  Risk Decision
     |         |
     +----+----+
          |
          v
       Retest
          |
          v
Continuous Evaluation
```

---

### 52. AI Explainability Test Planning Control

Explainability testing must be planned according to the AI system's intended use and risk.

The test plan should define:

* Explanation objectives
* Explanation audience
* Decision or output types
* Test scenarios
* Evaluation methods
* Acceptance criteria
* Required evidence
* Independence requirements
* Retesting requirements

---

### 53. AI Explainability Test Scope Control

The testing scope must cover the components responsible for producing or presenting explanations.

Scope may include:

* Input data
* Features
* Prompts
* Context
* Retrieval
* Model
* Model configuration
* Explanation method
* Tool execution
* Agent workflow
* User interface
* Human review

Testing only the final explanation screen may fail to detect weaknesses in the underlying explanation mechanism.

---

### 54. AI Explainability Test Classification Control

Explainability tests should be classified according to the property being evaluated.

| Test Classification | Primary Objective                                      |
| ------------------- | ------------------------------------------------------ |
| Faithfulness        | Determine whether explanation reflects actual behavior |
| Accuracy            | Detect false explanation claims                        |
| Relevance           | Determine whether explanation addresses the decision   |
| Stability           | Evaluate sensitivity to minor changes                  |
| Consistency         | Evaluate equivalent scenarios                          |
| Completeness        | Determine whether material information is omitted      |
| Understandability   | Evaluate audience comprehension                        |
| Attribution         | Evaluate feature/source/tool attribution               |
| Uncertainty         | Evaluate representation of uncertainty                 |
| Security            | Identify sensitive implementation disclosure           |

---

### 55. Risk-Based Explainability Test Selection Control

Explainability testing must be selected according to risk.

High-impact AI systems may require:

* Local and global explanation testing
* Counterfactual testing
* Faithfulness evaluation
* Independent validation
* Adversarial testing
* Human-review testing
* Privacy and security evaluation
* Continuous monitoring

Testing depth should increase as the consequences of misleading explanations increase.

The intended explanation audience must be explicitly identified.

Possible audiences include:

* End users
* Analysts
* Managers
* Developers
* Model validators
* Auditors
* Risk personnel
* Compliance personnel

Testing should determine whether the explanation is appropriate for the intended audience.

### 59. AI Explainability Test Data Control

Test data must adequately represent relevant AI behaviors and explanation scenarios.

Testing data should include, where appropriate:

### 60. AI Explainability Test Environment Control

Explainability testing must occur in an environment that accurately represents the configuration being evaluated.

The testing environment must be protected from unauthorized modification.

Changes to the:

* Model

* Configuration

### 62. AI System Version Identification Control

### 63. AI Explainability Configuration Control

### 64. AI Explainability Tester Identity Control

Explainability tests must be attributable to an authorized human or automated identity.

Evidence should identify:

* Tester
* Workload identity
* Test tool
* Test execution
* Target system
* Timestamp

Shared identities should not be used for material assurance activities.

---

### 65. AI Explainability Test Authorization Control

Testing must be authorized according to its potential impact.

Authorization should define:

* Target system
* Test environment
* Data
* Test techniques
* Duration
* Tester
* Evidence handling

Testing involving sensitive production information requires appropriate additional controls.

---

### 66. AI Explainability Baseline Control

Approved explainability baselines should be established for important AI systems.

* Expected explanation structure
* Required explanation attributes

* Accuracy thresholds
* Citation requirements

* Uncertainty requirements

### 67. AI Local Explainability Testing Control

Local explanations must be tested against individual AI outputs or decisions.

Testing should determine whether the explanation accurately describes the factors relevant to that specific result.

### 68. AI Global Explainability Testing Control

Global explanation mechanisms should be tested for whether they accurately describe broader model behavior.

Testing may evaluate:

* Feature relationships
* General behavioral patterns
* Model limitations
* Decision tendencies
* Known behavioral boundaries

Global explanation results should not automatically be interpreted as explanations for individual predictions.

### 70. AI Input Attribution Testing Control

Where attribution is provided, testing should determine whether identified input elements correspond to actual behavioral influence.

Testing may cover:

* Features
* Tokens
* Words
* Sentences
* Documents
* Images
* Audio segments
* Retrieved passages

---

### 71. AI Counterfactual Explainability Testing Control

Counterfactual testing should evaluate whether explanations behave appropriately when material input conditions change.

Testing should determine whether:

* Relevant changes affect outputs appropriately.
* Explanations identify meaningful changes.
* Irrelevant changes do not create disproportionate explanation changes.

---

### 72. AI Explanation Faithfulness Testing Control

Faithfulness testing must determine whether explanations correspond to actual AI behavior.

Testing should use controlled methods such as:

* Input perturbation
* Feature removal
* Counterfactual changes
* Controlled context changes
* Model behavior comparison

A plausible explanation must not be treated as faithful without supporting evidence.

---

### 73. AI Explanation Accuracy Testing Control

Explanations must be tested for factual and behavioral accuracy.

Testing should detect:

* False claims
* Incorrect attribution
* Unsupported causal explanations
* Fabricated evidence
* Incorrect source claims
* Misrepresented tool usage

---

### 74. AI Explanation Relevance Testing Control

Testing should determine whether explanations address the actual decision or output.

The assessment should identify:

* Generic explanations
* Irrelevant factors
* Boilerplate
* Unsupported reasoning
* Information unrelated to the decision

---

### 75. AI Explanation Consistency Testing Control

Equivalent or materially similar scenarios should produce sufficiently consistent explanations where consistency is required.

Testing should control for:

* Randomness
* Prompt variation
* Context variation
* Model version
* Explanation configuration

---

### 76. AI Explanation Stability Testing Control

Testing should evaluate whether small irrelevant input changes create disproportionate explanation changes.

Stability testing should distinguish legitimate AI variation from unacceptable explanation instability.

---

### 77. AI Explanation Completeness Testing Control

Testing should determine whether explanations contain the material information required by the defined explanation objective.

Completeness criteria should be explicitly defined rather than assuming that longer explanations are automatically better.

---

### 78. AI Explanation Understandability Testing Control

Explanations should be tested against the knowledge level of the intended audience.

Evaluation may consider:

* Terminology
* Complexity
* Length
* Clarity
* Required domain knowledge
* Language

---

### 79. AI Explanation Audience Appropriateness Control

Testing should verify that explanations provide appropriate information to different user roles.

A technical explanation suitable for an AI engineer may be inappropriate for an end user.

Conversely, excessive simplification may prevent a qualified reviewer from identifying important limitations.

---

### 80. AI Explanation Uncertainty Testing Control

Where uncertainty information is provided, testing must evaluate whether it accurately represents uncertainty.

Testing should identify:

* False confidence
* Misleading confidence
* Missing uncertainty
* Inconsistent uncertainty statements

---

### 81. AI Explanation Limitation Testing Control

AI explanations should be tested for appropriate disclosure of material limitations.

Testing should determine whether the system communicates relevant:

* Data limitations
* Model limitations
* Uncertainty
* Missing information
* Out-of-distribution conditions
* Known failure modes

---

### 82. AI Generative Explanation Testing Control

Generative AI explanations must be specifically tested for fabricated or post-hoc reasoning.

Testing should determine whether the model falsely claims:

### 117. Core Control Principle

**AI Explainability Testing controls must establish a controlled, measurable, attributable, and repeatable mechanism for determining whether explanations accurately and meaningfully represent defined AI behavior under defined conditions.**

Controls must cover the complete explanation surface, including model behavior, inputs, features, prompts, context, retrieval, tools, agents, explanation methods, citations, human review, interfaces, privacy, and security. Testing must distinguish **explanation availability from explanation accuracy, explanation accuracy from faithfulness, and explanation capability from assurance**.

Every material explainability requirement should map to a test objective, test case, evaluation method, acceptance criterion, and evidence record. Tests must identify the exact model, application, prompt, context, dataset, configuration, explanation method, environment, tester, and execution conditions.

Testing should evaluate local and global explanations, feature and input attribution, counterfactual behavior, faithfulness, accuracy, relevance, consistency, stability, completeness, understandability, audience appropriateness, uncertainty, limitations, generative explanations, RAG citations, tool attribution, agent workflows, multi-agent attribution, human oversight, privacy leakage, security disclosure, adversarial manipulation, and regression according to risk.

Automated failures must be capable of triggering enforcement actions such as findings, escalation, remediation, additional validation, release blocking, or operational restriction. Evidence must maintain integrity, provenance, and appropriate retention. Material findings must be remediated, independently validated where required, and retested.

**A plausible explanation is not sufficient evidence of explainability. An explanation must be evaluated against the actual behavior and system state it claims to describe.** Material changes to models, prompts, datasets, context, retrieval, tools, agents, explanation mechanisms, configurations, or operating conditions must be capable of triggering renewed explainability testing and reassessment.

### 176. Enterprise Security Principle

**AI explainability governance must ensure that explanation quality is independently challengeable, risk-based, traceable, and accountable.**

An explanation must not receive assurance merely because it exists, appears understandable, or is generated by the same AI system that produced the decision.

Governance must distinguish:

* Explanation availability
* Explanation accuracy
* Explanation faithfulness
* Explanation relevance
* Explanation usability
* Explanation assurance

Explanations must also be governed as potential privacy and security disclosure channels. Increased transparency must not automatically justify disclosure of personal information, confidential data, system prompts, security controls, or other restricted information.

**AI capability to generate an explanation does not constitute authority to define that explanation as trustworthy.**

---

### 177. Strategic Governance Principle

**AI explainability assurance must be governed as a continuously reassessed trust condition rather than a one-time documentation or testing exercise.**

Governance must maintain traceability from explainability requirements through risk classification, test methodology, system state, explanation generation, evaluation, evidence, findings, remediation, retesting, risk acceptance, and authorization.

Material changes to models, prompts, datasets, context, retrieval, tools, agents, explanation mechanisms, configurations, user populations, or decision contexts must be capable of invalidating previous explainability evidence and triggering renewed assessment.

New explanation failures, misleading outputs, user complaints, model changes, security or privacy findings, unexplained attribution changes, or deterioration in explanation metrics must be capable of triggering additional testing, remediation, independent validation, release restriction, operational limitation, containment, suspension, rollback, or reauthorization according to risk.

**Explainability evidence is always conditional on the system state, explanation method, decision context, audience, assumptions, and evaluation criteria under which it was generated.**

An AI system may be capable of producing explanations without those explanations being sufficiently faithful, accurate, stable, relevant, understandable, secure, or trustworthy for the intended use. Governance therefore determines whether the available evidence is sufficient for the level of reliance being placed on the AI system.

**Testing capability ≠ explanation authority ≠ risk acceptance ≠ AI authorization.**

### 239. Continuous AI Explainability Testing and Assurance Architecture

**AI explainability architecture must operate as a continuous technical assurance system in which explanations are independently evaluated against the behavior and evidence of the AI system they describe.**

The architecture must support the complete explainability lifecycle across local and global explanations, feature attribution, input attribution, counterfactuals, faithfulness, accuracy, relevance, consistency, stability, completeness, understandability, uncertainty, limitations, generative explanations, prompts, context, RAG, citations, tools, agents, multi-agent workflows, human review, privacy, security, and adversarial conditions.

Every material evaluation must be tied to the exact system state, model, dataset, prompt, context, configuration, explanation method, environment, tester, and execution conditions. Evidence must maintain integrity and provenance, while sensitive explanations and test data must remain isolated and protected.

The architecture must preserve a fundamental separation:

```text id="aiext239n"
AI Capability
     |
     v
AI Output / Decision
     |
     v
Explanation
     |
     v
Independent Evaluation
     |
     v
Evidence
     |
     v
Assurance Decision
     |
     v
Authorization
```

**The AI's ability to generate an explanation does not authorize that explanation as truthful, faithful, complete, or trustworthy. The explanation mechanism must not become the sole authority for validating itself.**

Authoritative system telemetry, controlled behavioral testing, source records, tool-execution records, model and configuration identity, and independent evaluation should be used wherever higher assurance is required.

The architecture must resist:

* Explanation manipulation
* Test bypass
* Evidence alteration
* False attribution
* Fabricated citations
* False tool-use claims
* Privacy leakage
* Security disclosure
* Explanation instability
* False assurance

Security gates must be enforceable, material failures must be capable of blocking release or restricting operation, and containment, suspension, rollback, and recovery mechanisms must be available where explanation failures create material risk.

Material changes to models, prompts, datasets, context, retrieval, tools, agents, explanation mechanisms, configurations, user populations, or decision contexts must be capable of triggering renewed testing and reassessment.

**Continuous explainability assurance therefore represents a controlled trust-transition system: explanation capability produces an assertion, testing challenges that assertion, evidence establishes what can actually be demonstrated, governance determines whether the evidence is sufficient, and authorization determines whether the AI system may continue operating under the evaluated conditions.**
