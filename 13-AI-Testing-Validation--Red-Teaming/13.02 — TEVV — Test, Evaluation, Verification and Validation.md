# 13.02 — TEVV — Test, Evaluation, Verification and Validation

## Part 1 — TEVV Foundations

### 1. Definition of TEVV

TEVV stands for **Test, Evaluation, Verification, and Validation**.

It is a structured assurance discipline used to establish whether an AI system:

* Performs according to defined requirements
* Produces acceptable results
* Was built according to specifications
* Satisfies its intended purpose in its operational context

TEVV combines multiple forms of technical evidence rather than relying on a single test or metric.

---

### 2. Purpose of TEVV

The purpose of TEVV is to establish defensible evidence that an AI system is suitable for its intended use.

TEVV should support decisions involving:

* Development
* Model promotion
* Security authorization
* Production deployment
* Risk acceptance
* Operational continuation
* Change approval
* Retirement

---

### 3. Test, Evaluation, Verification and Validation

The four TEVV activities answer different questions.

| Activity         | Primary Question                                                                        |
| ---------------- | --------------------------------------------------------------------------------------- |
| **Test**         | What happens when the system is subjected to defined conditions?                        |
| **Evaluation**   | How well does the system perform against defined criteria?                              |
| **Verification** | Was the system built according to specified requirements?                               |
| **Validation**   | Does the system satisfy its intended purpose in its real or intended operating context? |

These activities are complementary and should not be treated as interchangeable.

---

Testing may examine:

* Inputs
* Outputs
* Security controls
* Error handling
* Boundary conditions
* Failure behavior

A test design should specify:

* Objective
* Preconditions

* Execution conditions
* Expected results
* Failure criteria
* Evidence requirements

### 13. Evaluation

Evaluation determines how system behavior compares with defined criteria.

Examples include:

* Accuracy
* Error rate
* Robustness
* Security performance
* Fairness
* Reliability
* Attack resistance

Evaluation transforms raw test observations into meaningful performance or assurance measurements.

---

### 14. Evaluation Criteria

Evaluation requires predefined criteria wherever practical.

Criteria may establish:

* Acceptable performance
* Maximum error
* Minimum security resistance
* Maximum leakage
* Required reliability
* Required fairness

Criteria should be established before results are interpreted to reduce subjective result manipulation.

---

### 15. Evaluation Metrics

AI systems may require multiple evaluation metrics.

For example:

| Domain       | Possible Metric         |
| ------------ | ----------------------- |
| Functional   | Accuracy                |
| Security     | Attack success rate     |
| Reliability  | Failure rate            |
| Privacy      | Leakage rate            |
| Robustness   | Performance degradation |
| Fairness     | Outcome disparity       |
| Availability | Service availability    |

No single metric should automatically represent overall AI assurance.

### 16. Verification

Verification determines whether the system was constructed according to specified requirements.

Examples include verifying:

* Required controls were implemented
* Required configurations exist
* Approved components were used
* Security requirements were addressed
* Architecture matches approved design

Verification focuses primarily on **conformance to specification**.

---

### 17. Verification of AI Architecture

Verification should examine:

* Trust boundaries
* Identity
* Authorization
* Data flows
* Model interfaces

* Infrastructure

---

### 18. Verification of AI Configuration

Security-sensitive configuration should be verified against approved baselines.

Examples include:

* Access policies
* Network rules
* Model settings
* Tool permissions
* Security thresholds
* Logging

Configuration verification can identify deviations that functional testing may not detect.

---

### 19. Verification of AI Artifacts

AI artifacts should be verified before promotion.

Verification should establish:

* Correct identity
* Integrity
* Provenance
* Expected version
* Approved dependencies
* Required security status

---

### 20. Validation

Validation determines whether the AI system satisfies its intended purpose in the intended operational context.

Validation considers questions such as:

* Does the system solve the intended problem?
* Does it operate appropriately in its real environment?
* Are its outcomes acceptable for the intended users?
* Does it remain within defined risk boundaries?

---

### 21. Verification vs Validation

The distinction is fundamental.

```text id="tevv21d"

     |                   |
```

A system may be correctly built according to specifications but still be unsuitable for its intended use.

### 50. Core Principle of TEVV

**Test, Evaluation, Verification, and Validation must operate as complementary assurance disciplines that establish evidence about whether an AI system is correctly built, performs according to defined criteria, satisfies its specified requirements, and remains suitable for its intended operational purpose. TEVV must cover the complete AI system according to risk, including applications, datasets, models, prompts, retrieval systems, tools, dependencies, infrastructure, and human workflows. Testing must establish observed behavior, evaluation must measure that behavior against defined criteria, verification must establish conformance to requirements, and validation must establish suitability for the intended operational context. The resulting evidence must remain attributable, integrity-protected, traceable, and subject to independent review where required. TEVV evidence establishes bounded knowledge about a defined system under defined conditions; it does not create permanent trust. As AI systems, threats, data, models, dependencies, and operating environments change, TEVV must be capable of triggering reassessment, remediation, retesting, revalidation, and renewed assurance decisions.**

## Part 2 — TEVV Controls

### 51. TEVV Control Framework

The TEVV control framework establishes the mandatory controls required to plan, execute, document, evaluate, and govern Test, Evaluation, Verification, and Validation activities across the AI lifecycle.

The framework should define controls for:

* TEVV planning
* Test execution
* Evaluation criteria
* Verification evidence
* Validation evidence
* Independence
* Findings
* Retesting
* Evidence retention
* Continuous reassessment

---

### 52. TEVV Planning Control

Every material AI system should have a documented TEVV plan before formal assurance activities begin.

The plan should define:

* Scope
* Objectives
* System version
* Model version
* Dataset versions
* Test environments
* Evaluation criteria
* Verification criteria
* Validation criteria
* Required independence
* Evidence requirements

---

### 53. TEVV Scope Control

TEVV scope must be explicitly defined and approved according to AI risk.

Scope should identify which components are included and excluded.

```text id="tevv53a"
AI System
   |
   +-- Application
   +-- Model
   +-- Dataset
   +-- Prompt
   +-- Retrieval
   +-- Tools
   +-- APIs
   +-- Dependencies
   +-- Infrastructure
   +-- Human Workflow
```

Excluded components should have documented justification where their exclusion could affect assurance conclusions.

---

### 54. TEVV Classification Control

TEVV activities should be classified according to their purpose.

| Classification | Primary Objective                         |
| -------------- | ----------------------------------------- |
| Test           | Observe behavior under defined conditions |
| Evaluation     | Measure performance against criteria      |
| Verification   | Establish conformance to requirements     |
| Validation     | Establish suitability for intended use    |

This classification prevents different forms of evidence from being incorrectly treated as equivalent.

---

### 55. Risk-Based TEVV Selection Control

TEVV depth should be proportional to AI risk.

Higher-risk systems should receive stronger assurance activities, including:

* Broader testing
* More extensive evaluation
* Stronger verification
* Realistic validation
* Independent review
* Adversarial assessment
* More frequent reassessment

---

### 56. TEVV Requirement Mapping Control

Every material security and functional requirement should be mapped to an appropriate TEVV activity.

```text id="tevv56b"
Requirement
     |
     v
TEVV Mapping
     |
     +--> Test
     +--> Evaluation
     +--> Verification
     +--> Validation
     |
     v
Evidence
```

Requirements without an appropriate assurance mechanism should be treated as assurance gaps.

---

### 57. TEVV Traceability Control

Organizations should maintain bidirectional traceability between requirements and TEVV evidence.

The organization should be able to determine:

* Which requirement was evaluated
* Which test or evaluation addressed it
* Which version was evaluated
* What result was produced
* Which evidence supports the result
* Which decision resulted from the evidence

---

### 58. TEVV Test Case Control

Test cases should be uniquely identified and controlled.

Each test case should define:

* Objective
* Preconditions
* Inputs
* Expected behavior
* Execution procedure
* Acceptance criteria
* Evidence requirements

Changes to critical test cases should be controlled and attributable.

---

### 59. TEVV Test Data Control

Test data must be managed as a controlled assurance asset.

Controls should address:

* Dataset identity
* Version
* Provenance
* Integrity
* Classification
* Authorization
* Modification
* Retention

Production-sensitive data should not be copied into test environments without appropriate authorization and protection.

---

### 60. TEVV Test Data Isolation Control

Sensitive test and evaluation data should be isolated according to its classification and risk.

Isolation may include:

* Access restrictions
* Separate storage
* Encryption
* Environment segmentation
* Dataset-specific permissions
* Controlled export

Test environments must not become uncontrolled repositories of sensitive enterprise information.

---

### 61. TEVV Environment Control

Testing should occur in controlled environments appropriate to the assurance objective.

The environment should have known:

* Software versions
* Model versions
* Dataset versions
* Configuration
* Dependencies
* Infrastructure
* Security controls

Unknown environmental differences can invalidate test conclusions.

---

### 62. TEVV Environment Integrity Control

The integrity of the TEVV environment should be verified before execution.

Controls should detect unauthorized:

* Software changes
* Configuration changes
* Model substitutions
* Dataset substitutions
* Dependency modifications
* Security-control disabling

---

### 63. AI Version Control for TEVV

Every TEVV activity should identify the exact AI system version evaluated.

Version identification should include, where applicable:

* Application version
* Model version
* Dataset version
* Prompt version
* Configuration version
* Dependency versions
* Infrastructure version

A test result should never be ambiguously associated with a moving target.

---

### 64. TEVV Configuration Control

Configuration used during TEVV should be captured and controlled.

Important configuration may include:

* Model parameters
* System prompts
* Safety policies
* Retrieval configuration
* Tool permissions
* API settings
* Security controls
* Infrastructure settings

---

### 65. TEVV Identity Control

Every TEVV activity should be attributable to a verified identity.

The identity model should distinguish:

* Test engineers
* Evaluators
* Developers
* Security personnel
* Validators
* Approvers
* Automated test workloads

Shared accounts should be prohibited for material assurance activities wherever technically feasible.

---

### 66. TEVV Authorization Control

TEVV activities must be authorized according to their scope and risk.

Authorization should determine who may:

* Create tests
* Modify tests
* Execute tests
* Access evaluation data
* Approve results
* Override failures
* Accept residual risk

Execution authority should not automatically provide approval authority.

---

### 117. Core Control Principle

Every material TEVV activity must be attributable to the exact AI system, model, dataset, configuration, dependencies, and environment evaluated. Testing and evaluation must measure defined conditions and criteria; verification must establish conformance to specified requirements; and validation must establish suitability for the intended operational context. Controls must protect test environments and evidence, enforce appropriate independence, automate mandatory gates where feasible, and prevent material failures from being silently ignored. TEVV evidence must remain bounded to the conditions under which it was produced and must be reassessed when the AI system, threat environment, data, model, dependencies, or operating context materially changes.**

### 176. Enterprise Security Principle

**Enterprise TEVV governance must establish clear accountability, risk-based assurance requirements, appropriate independence, evidence integrity, traceability, finding management, and continuous reassessment across the AI lifecycle. Governance must distinguish testing, evaluation, verification, and validation while connecting their evidence into a coherent assurance decision process. Every material requirement should map to appropriate assurance activities, every significant finding should remain attributable through remediation and retesting, and every exception or risk acceptance should be explicitly authorized and time-bounded. TEVV governance must remain integrated with AI risk management, security governance, GRC, change management, and release authorization so that technical evidence directly informs enterprise security decisions without allowing testing teams, development teams, automated pipelines, or AI systems to independently establish enterprise trust.**

---

### 177. Strategic Governance Principle

**TEVV governance must treat assurance as a continuously governed trust decision rather than a one-time testing milestone. The organization must maintain the ability to challenge, reassess, and invalidate previously accepted evidence whenever AI capabilities, models, datasets, prompts, retrieval systems, tools, dependencies, infrastructure, threats, vulnerabilities, or operating conditions materially change. Testing establishes observations, evaluation establishes measured performance, verification establishes conformance, and validation establishes suitability for intended use; none of these activities alone creates permanent security authorization. Enterprise governance must therefore preserve traceability from requirements and threats through TEVV activities, evidence, findings, remediation, retesting, risk acceptance, and authorization. The fundamental governance principle is that evidence supports trust but does not own trust: production trust remains conditional, attributable, risk-based, independently challengeable where required, and continuously subject to reauthorization.**

### 239. Continuous AI Testing and Assurance Architecture

**Enterprise TEVV architecture must operate as a continuously assured technical trust system in which testing, evaluation, verification, and validation are connected to requirements, threats, controls, evidence, release decisions, and production assurance. The architecture must preserve the distinction between observing behavior, measuring performance, verifying conformance, and validating operational suitability while allowing their evidence to contribute to a coherent assurance decision. Every material TEVV activity must be attributable to the exact AI system, model, dataset, configuration, dependencies, environment, tester or workload, and evaluation methodology used. Test environments and adversarial activities must be isolated and bounded, evidence must be integrity-protected and traceable, mandatory assurance gates must resist bypass, and TEVV infrastructure must fail securely when required evidence cannot be established. Most importantly, testing capability must never equal assurance authority: a test harness, evaluation engine, automated pipeline, red team, or AI system may generate evidence, but enterprise trust must remain an independently governed and risk-based decision. When system conditions, threats, data, models, dependencies, or operational contexts change, the architecture must be capable of triggering renewed testing, evaluation, verification, validation, containment, release blocking, rollback, or revocation so that previously generated evidence cannot be incorrectly treated as permanent security trust.**
