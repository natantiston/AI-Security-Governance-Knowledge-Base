# 13.02 — TEVV — Test, Evaluation, Verification and Validation

## Part 1 — TEVV Foundations

### 1. Definition of TEVV

TEVV stands for **Test, Evaluation, Verification, and Validation**.

It is a structured assurance discipline used to establish whether an AI system:

* Performs according to defined requirements
* Produces acceptable results
* Was built according to specifications
* Satisfies its intended purpose in its operational context

TEVV combines multiple forms of technical evidence rather than relying on a single test or metric.

---

### 2. Purpose of TEVV

The purpose of TEVV is to establish defensible evidence that an AI system is suitable for its intended use.

TEVV should support decisions involving:

* Development
* Model promotion
* Security authorization
* Production deployment
* Risk acceptance
* Operational continuation
* Change approval
* Retirement

---

### 3. Test, Evaluation, Verification and Validation

The four TEVV activities answer different questions.

| Activity         | Primary Question                                                                        |
| ---------------- | --------------------------------------------------------------------------------------- |
| **Test**         | What happens when the system is subjected to defined conditions?                        |
| **Evaluation**   | How well does the system perform against defined criteria?                              |
| **Verification** | Was the system built according to specified requirements?                               |
| **Validation**   | Does the system satisfy its intended purpose in its real or intended operating context? |

These activities are complementary and should not be treated as interchangeable.

---

TEVV should operate as an integrated evidence framework.

### 6. Requirements as the Foundation of TEVV

TEVV activities should originate from explicit requirements.

Requirements may describe:

* Functional behavior
* Security
* Performance
* Reliability
* Privacy
* Fairness
* Robustness
* Explainability
* Availability

A requirement that cannot be evaluated represents an assurance challenge.

---

### 7. TEVV and Risk Management

TEVV depth should be proportional to AI system risk.

High-risk systems generally require:

* Broader test coverage
* Stronger evaluation criteria
* Greater verification depth
* More realistic validation
* Independent assurance
* More frequent reassessment

```text id="tevv07c"
AI Risk
   |
   v

   |

   |
   v

```

---

### 8. TEVV Scope

The scope of TEVV should encompass the complete AI system where appropriate.

It may include:

* Application
* Model
* Dataset
* Prompt
* Retrieval system
* Tools
* APIs
* Dependencies
* Infrastructure
* Human workflows
* External providers

Testing only the model may provide incomplete system assurance.

---

### 9. System Under Evaluation

The exact AI system being evaluated should be clearly identified.

Identification should include:

* System
* Version
* Model
* Dataset
* Configuration
* Environment
* Dependencies
* Evaluation date

This establishes the precise object to which TEVV evidence applies.

---

### 10. Test

Testing involves controlled execution of an AI system under defined conditions.

Testing may examine:

* Inputs
* Outputs
* Security controls
* Error handling
* Boundary conditions
* Failure behavior

Testing produces observed evidence.

---

### 11. Test Design

Tests should be designed before execution wherever practical.

A test design should specify:

* Objective
* Preconditions
* Inputs
* Execution conditions
* Expected results
* Failure criteria
* Evidence requirements

---

### 12. Test Case

A test case defines a specific scenario used to evaluate system behavior.

It should identify:

* Test identifier
* Test objective
* Input
* Expected behavior
* Actual behavior
* Pass/fail criteria

---

### 13. Evaluation

Evaluation determines how system behavior compares with defined criteria.

Examples include:

* Accuracy
* Error rate
* Robustness
* Security performance
* Fairness
* Reliability
* Attack resistance

Evaluation transforms raw test observations into meaningful performance or assurance measurements.

---

### 14. Evaluation Criteria

Evaluation requires predefined criteria wherever practical.

Criteria may establish:

* Acceptable performance
* Maximum error
* Minimum security resistance
* Maximum leakage
* Required reliability
* Required fairness

Criteria should be established before results are interpreted to reduce subjective result manipulation.

---

### 15. Evaluation Metrics

AI systems may require multiple evaluation metrics.

For example:

| Domain       | Possible Metric         |
| ------------ | ----------------------- |
| Functional   | Accuracy                |
| Security     | Attack success rate     |
| Reliability  | Failure rate            |
| Privacy      | Leakage rate            |
| Robustness   | Performance degradation |
| Fairness     | Outcome disparity       |
| Availability | Service availability    |

No single metric should automatically represent overall AI assurance.

---

### 16. Verification

Verification determines whether the system was constructed according to specified requirements.

Examples include verifying:

* Required controls were implemented
* Required configurations exist
* Approved components were used
* Security requirements were addressed
* Architecture matches approved design

Verification focuses primarily on **conformance to specification**.

---

### 17. Verification of AI Architecture

AI architecture should be verified against approved security and functional requirements.

Verification should examine:

* Trust boundaries
* Identity
* Authorization
* Data flows
* Model interfaces
* Tool interfaces
* Security controls
* Infrastructure

---

### 18. Verification of AI Configuration

Security-sensitive configuration should be verified against approved baselines.

Examples include:

* Access policies
* Network rules
* Model settings
* Tool permissions
* Security thresholds
* Logging

Configuration verification can identify deviations that functional testing may not detect.

---

### 19. Verification of AI Artifacts

AI artifacts should be verified before promotion.

Verification should establish:

* Correct identity
* Integrity
* Provenance
* Expected version
* Approved dependencies
* Required security status

---

### 20. Validation

Validation determines whether the AI system satisfies its intended purpose in the intended operational context.

Validation considers questions such as:

* Does the system solve the intended problem?
* Does it operate appropriately in its real environment?
* Are its outcomes acceptable for the intended users?
* Does it remain within defined risk boundaries?

---

### 21. Verification vs Validation

The distinction is fundamental.

```text id="tevv21d"
Verification
     |
     v
"Was the system built correctly?"
     |
     +-------------------+
                         |
Validation               |
     |                   |
     v                   |
"Is it the right system?"
     |
     v
Intended Operational Purpose
```

A system may be correctly built according to specifications but still be unsuitable for its intended use.

---

### 22. Technical Validation

Technical validation should examine whether the AI system performs appropriately under realistic operating conditions.

It may include:

* Realistic datasets
* Production-like workloads
* User workflows
* Integration behavior
* Security conditions
* Operational constraints

---

### 23. Operational Validation

Operational validation evaluates the AI system within the context in which it will actually operate.

It should consider:

* Users
* Processes
* Infrastructure
* Data
* Dependencies
* Security controls
* Operational procedures

---

### 24. Security Validation

Security validation determines whether security protections remain effective in the intended operational environment.

Validation may assess:

* Authorization
* Data protection
* Model security
* Tool restrictions
* Monitoring
* Incident response

---

### 25. TEVV Across the AI Lifecycle

TEVV should be applied at multiple lifecycle stages.

| Stage        | TEVV Focus                  |
| ------------ | --------------------------- |
| Requirements | Requirement validation      |
| Design       | Architecture verification   |
| Development  | Functional/security testing |
| Training     | Model evaluation            |
| Pre-release  | Verification and validation |
| Deployment   | Environment verification    |
| Production   | Operational validation      |
| Change       | Regression and reassessment |

### 26. Dataset TEVV

Datasets should be evaluated as part of AI assurance.

Dataset TEVV may examine:

* Provenance
* Integrity
* Quality
* Representativeness
* Sensitive information
* Poisoning
* Contamination
* Version

Dataset problems can invalidate conclusions about model performance or security.

---

### 27. Model TEVV

Models should receive dedicated TEVV activities.

Evaluation may include:

* Accuracy
* Robustness
* Security
* Fairness
* Privacy
* Reliability
* Adversarial resistance

---

### 28. Application TEVV

The surrounding AI application should also be evaluated.

Testing should cover:

* APIs
* Authentication
* Authorization
* Input handling
* Output handling
* Retrieval
* Tools
* Session management

---

### 30. TEVV for Generative AI

Generative AI requires evaluation beyond traditional deterministic software testing.

TEVV should examine:

* Output variability
* Instruction following
* Refusal behavior
* Hallucination
* Prompt injection
* Data leakage
* Jailbreak resistance
* Unsafe outputs

---

### 31. TEVV for LLMs

LLM TEVV should account for context-dependent and probabilistic behavior.

Evaluation should consider:

* Prompt variations
* Context variations
* Model versions
* Temperature or generation settings
* System instructions
* Tool interactions

A single successful prompt test is insufficient to characterize LLM security.

Retrieval-augmented systems should be evaluated across both retrieval and generation.

Testing should assess:

* Retrieval authorization
* Document isolation
* Context integrity
* Injection resistance
* Sensitive information exposure
* Output behavior

### 34. TEVV for AI Tools and APIs

Tool and API interactions should be independently verified and validated.

Testing should determine whether:

* Authorization is enforced
* Parameters are validated
* Sensitive actions are restricted
* Errors are safely handled
* Abuse limits operate correctly

### 36. TEVV and Adversarial Conditions

TEVV should include adversarial conditions where relevant.

Adversarial evaluation may include:

* Malicious prompts
* Data manipulation
* Context manipulation
* Tool abuse
* Model attacks
* Infrastructure attacks

---

### 37. TEVV and Negative Testing

Negative testing should evaluate how systems behave when conditions are invalid or malicious.

Examples include:

* Unauthorized access
* Invalid inputs
* Malformed requests
* Conflicting instructions
* Excessive requests
* Unexpected dependencies

---

### 38. TEVV and Robustness

Robustness evaluation determines whether security and functional properties remain acceptable when conditions vary.

Testing may introduce:

* Noise
* Perturbations
* Distribution shifts
* Unexpected inputs
* Adversarial variations

---

### 39. TEVV and Reliability

Reliability evaluation determines whether AI systems perform consistently over time.

Metrics may address:

* Failure rates
* Error rates
* Availability
* Recovery
* Performance stability

---

### 40. TEVV and Privacy

Privacy TEVV should determine whether AI systems protect sensitive information under expected and adversarial conditions.

Evaluation may include:

* Data leakage
* Memorization
* Inference
* Unauthorized retrieval
* Sensitive output

---

### 41. TEVV and Fairness

Where applicable, TEVV should evaluate fairness properties across relevant populations and use cases.

Evaluation should use predefined and contextually appropriate criteria.

---

### 42. TEVV and Explainability

Where explainability is required, TEVV should evaluate whether explanations satisfy defined expectations.

This may include:

* Consistency
* Relevance
* Interpretability
* Completeness
* Alignment with observed behavior

---

### 43. TEVV Evidence

TEVV should produce defensible evidence.

Evidence may include:

* Test results
* Evaluation metrics
* Verification records
* Validation reports
* Configuration
* Model version
* Dataset version
* Environment information

---

### 44. TEVV Evidence Integrity

TEVV evidence must be protected against unauthorized modification.

Evidence should be:

* Attributable
* Integrity-protected
* Traceable
* Time-associated
* Accessible to authorized reviewers

---

### 45. TEVV Traceability

TEVV results should remain traceable to the system and requirements being evaluated.

### 46. TEVV Independence

Independence should be proportional to risk.

High-risk systems should receive appropriate independent verification and validation.

This reduces the risk of development teams becoming the sole authority over the adequacy of their own systems.

---

### 47. TEVV Acceptance

TEVV results should be evaluated against predefined acceptance criteria.

Possible decisions include:

* Accept
* Conditionally accept
* Remediate
* Retest
* Reject
* Escalate

Acceptance should remain attributable to an authorized decision-maker.

---

### 48. TEVV Continuous Evaluation

TEVV should continue after production deployment.

Reevaluation may be triggered by:

* Model changes
* Dataset changes
* New vulnerabilities
* New threats
* Architecture changes
* Provider changes
* Material behavioral changes

---

### 50. Core Principle of TEVV

**Test, Evaluation, Verification, and Validation must operate as complementary assurance disciplines that establish evidence about whether an AI system is correctly built, performs according to defined criteria, satisfies its specified requirements, and remains suitable for its intended operational purpose. TEVV must cover the complete AI system according to risk, including applications, datasets, models, prompts, retrieval systems, tools, dependencies, infrastructure, and human workflows. Testing must establish observed behavior, evaluation must measure that behavior against defined criteria, verification must establish conformance to requirements, and validation must establish suitability for the intended operational context. The resulting evidence must remain attributable, integrity-protected, traceable, and subject to independent review where required. TEVV evidence establishes bounded knowledge about a defined system under defined conditions; it does not create permanent trust. As AI systems, threats, data, models, dependencies, and operating environments change, TEVV must be capable of triggering reassessment, remediation, retesting, revalidation, and renewed assurance decisions.**
