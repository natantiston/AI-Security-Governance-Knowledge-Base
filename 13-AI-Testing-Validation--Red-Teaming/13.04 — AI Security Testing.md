# 13.04 — AI Security Testing

## Part 1 — AI Security Testing Foundations

### 1. Definition of AI Security Testing

AI security testing is the systematic assessment of an AI system's ability to resist, detect, contain, and recover from security threats and unauthorized behavior.

It extends conventional application security testing to address AI-specific attack surfaces, including:

* Models
* Prompts
* Training and evaluation data
* Retrieval systems
* AI memory
* Tool use
* Agent workflows
* Model APIs
* AI supply chains
* AI-specific security controls

---

### 2. Purpose of AI Security Testing

The purpose of AI security testing is to generate evidence about whether an AI system's security requirements and controls operate effectively under expected and adversarial conditions.

Security testing should help determine whether the system can:

* Prevent unauthorized access
* Protect sensitive information
* Resist manipulation
* Maintain authorization boundaries
* Protect model integrity
* Resist prompt-based attacks
* Control tool execution
* Detect security violations
* Fail safely

---

### 3. AI Security Testing vs Functional Testing

Functional testing determines whether the AI system performs intended functions.

Security testing determines whether those functions can be abused, bypassed, manipulated, or exploited.

```text id="aist03a"
Functional Testing
      |
      v
"Does it work correctly?"
      |
      v
Security Testing
      |
      v
"Can it be made to work
in an unauthorized or
unsafe way?"
```

A system can be functionally correct while still containing serious security vulnerabilities.

---

### 50. Core Principle of AI Security Testing

**AI security testing must systematically challenge the complete AI attack surface to establish evidence that security requirements and controls operate effectively under realistic, unauthorized, adversarial, and failure conditions appropriate to risk. Testing must extend beyond conventional application security to include models, prompts, datasets, retrieval systems, memory, tools, function calling, agent workflows, APIs, dependencies, containers, infrastructure, and AI supply chains. Every material security requirement and threat should map to an appropriate testing activity, with results attributable to the exact system, model, data, configuration, and environment evaluated. Security testing must deliberately challenge authentication, authorization, data isolation, integrity, privilege boundaries, prompt defenses, tool controls, monitoring, and failure behavior. A passing security test establishes evidence about a defined condition at a defined point in time; it does not establish permanent security trust. AI security testing must therefore remain risk-based, repeatable where practical, continuously reassessable, and capable of triggering remediation, retesting, release blocking, containment, rollback, or renewed authorization when security conditions change.**

### 117. Core Control Principle

**AI security testing controls must establish a continuously enforceable evidence chain from security requirements and threats through test design, controlled execution, results, findings, remediation, retesting, and security decision-making. Every material AI security boundary and attack surface must be tested according to risk, including applications, models, datasets, prompts, retrieval systems, memory, tools, APIs, identities, dependencies, containers, infrastructure, and external AI services. Test execution must be authorized, attributable, isolated where necessary, and tied to the exact system version, model, dataset, configuration, and environment evaluated. Security tests must deliberately challenge both preventive and detective controls, including authentication, authorization, data isolation, integrity, privilege boundaries, prompt defenses, tool controls, monitoring, and failure behavior. Automated security tests should enforce defined security gates where appropriate, while high-risk testing should receive independent validation. Security evidence must be protected against manipulation and retained with sufficient provenance to support audit, investigation, and reassessment. Material failures must be classified, escalated, remediated, and retested, with critical failures capable of blocking release or triggering containment. A security test result is evidence about a defined condition, not permanent trust; therefore, material system, model, data, configuration, dependency, threat, or operating-context changes must be capable of triggering renewed security testing and reassessment.**

### 239. Continuous AI Security Testing and Assurance Architecture

**AI security testing architecture must operate as a continuously reassessable technical trust system rather than a collection of isolated testing tools. The architecture must connect security requirements, threat models, attack scenarios, test execution, evaluation, evidence, findings, remediation, retesting, release gates, runtime monitoring, and reauthorization across the complete AI attack surface. Models, applications, datasets, prompts, retrieval systems, memory, tools, agents, APIs, identities, dependencies, containers, infrastructure, and external AI services must be independently testable according to risk while remaining connected through bidirectional traceability. Testing environments and workloads must be strongly identified, authorized, segmented, integrity-protected, observable, and constrained by blast-radius controls. Security-test evidence must possess sufficient provenance and integrity to support audit and assurance, while security gates must technically resist bypass and test systems must fail securely. Testing capability must remain distinct from authorization authority: a test platform may generate evidence, but it must not independently establish production trust. When test evidence becomes invalid, incomplete, manipulated, contradicted, or outdated because of material changes or emerging threats, the architecture must support renewed testing, reassessment, release blocking, containment, suspension, rollback, revocation, or reauthorization.**
