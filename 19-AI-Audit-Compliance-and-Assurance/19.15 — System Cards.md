# 19.15 — System Cards

## Part 1 — System Card Foundations, Purpose, Structure, and Governance Requirements

### 1. Defining System Cards in AI Governance

A system card is a structured governance and technical documentation artifact that describes an AI system as deployed or intended to be deployed within a defined operational context. It communicates the system's purpose, architecture, components, data flows, capabilities, limitations, risk controls, evaluation results, operational dependencies, and conditions for appropriate use.

Unlike documentation focused exclusively on an individual model, a system card considers the broader system in which one or more models operate.

An AI system may include:

- One or more machine learning models.
- Foundation models or externally hosted AI services.
- Training, validation, and inference pipelines.
- Input data sources and data transformation processes.
- Retrieval-augmented generation (RAG) components.
- Application interfaces and orchestration services.
- External tools, APIs, and enterprise integrations.
- Identity and access management mechanisms.
- Human review and approval workflows.
- Monitoring, logging, and incident response capabilities.
- Infrastructure, network boundaries, and deployment configurations.

A system card describes how these elements interact and how their combined behavior affects the system's intended purpose, risk profile, and governance obligations.

The card should distinguish verified system characteristics from design assumptions, supplier claims, planned controls, and unresolved uncertainties.

Its purpose is to provide an authoritative, structured account of the AI system that supports technical review, risk management, deployment decisions, operational oversight, audit, and appropriate transparency.

### 2. Distinguishing System Cards from Model Cards

System cards and model cards are complementary artifacts with different scopes.

A model card primarily documents an individual model's intended use, technical characteristics, evaluation results, limitations, and relevant governance considerations.

A system card documents the larger solution in which models operate, including the application architecture, integrations, data flows, user interactions, security controls, and operational context.

| Dimension                   | Model card                                                  | System card                                                                                 |
| --------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Primary scope               | Individual model                                            | Complete AI system or defined system boundary                                               |
| Main subject                | Model characteristics and behavior                          | End-to-end system behavior and interactions                                                 |
| Architecture                | Model-level architecture where relevant                     | Models, applications, services, interfaces, and dependencies                                |
| Data                        | Training, evaluation, and model input characteristics       | End-to-end data flows, transformations, access, storage, and outputs                        |
| Evaluation                  | Model-level performance and limitations                     | System-level functional, security, safety, and operational evaluation                       |
| Security                    | Model-related security considerations                       | End-to-end controls, integrations, infrastructure, and attack paths                         |
| Human oversight             | Model-related use restrictions and oversight considerations | Actual decision workflows, escalation paths, and human intervention                         |
| Dependencies                | Base models and relevant model dependencies                 | Models, vendors, APIs, infrastructure, tools, and enterprise services                       |
| Change management           | Model updates, retraining, and version changes              | Changes to models, applications, configurations, data sources, and integrations             |
| Primary governance question | What are the model's characteristics and limitations?       | How does the complete AI system operate, and under what conditions is it acceptable to use? |

A system card may reference multiple model cards where several models contribute to the system.

The system card should not simply copy every model-level detail. It should summarize the characteristics relevant to system behavior and maintain traceable references to authoritative model documentation.

**Example:** An enterprise assistant may use a third-party language model, an internal document retrieval service, an identity provider, and a ticketing API. The model card describes the language model, while the system card explains how the assistant retrieves information, enforces user permissions, generates responses, and initiates ticketing actions.

### 3. Distinguishing System Cards from System Architecture Documentation

System architecture documentation describes components, interfaces, deployment patterns, technical decisions, and system structure. A system card uses relevant architectural information to explain the AI system's capabilities, limitations, risks, controls, and operating conditions.

Architecture documentation may show how services communicate without explaining whether the resulting system behavior has been evaluated for its intended use.

A system card should connect architecture to governance-relevant implications.

For example, an architecture diagram may show that an AI assistant connects to an enterprise document repository. The system card should additionally explain whether retrieval respects source-system permissions, how unauthorized data access is tested, and what happens when the assistant receives a request for information the user is not authorized to view.

The system card may reference architecture diagrams, data-flow diagrams, interface specifications, threat models, and deployment records rather than reproducing all technical details.

The distinction is functional:

- **Architecture documentation** explains how the system is designed and assembled.
- **System cards** explain the system's relevant characteristics, limitations, controls, risks, and conditions for responsible operation.

Both artifacts should remain consistent and should be updated through coordinated change management.

### 4. The Governance Purpose of System Cards

System cards help organizations make informed decisions about AI systems across their lifecycle.

Their governance purpose includes:

- Establishing a common understanding of system scope and purpose.
- Identifying components that influence AI behavior.
- Communicating dependencies and integration risks.
- Documenting intended and prohibited uses.
- Describing the operational context in which evaluations apply.
- Identifying security, privacy, safety, and reliability considerations.
- Connecting risks to controls and accountable owners.
- Supporting deployment authorization.
- Providing evidence for monitoring and reassessment.
- Facilitating internal audit and external assurance.
- Supporting appropriate disclosure to users and other stakeholders.

A system card can reduce the risk that different teams maintain inconsistent assumptions about how an AI system operates.

For example, a business team may believe an assistant only provides recommendations, while the engineering team has enabled it to execute actions through external APIs. The system card should make the actual authority and capabilities of the deployed system explicit.

System cards also support organizational accountability by clarifying which controls are implemented, which remain planned, and which risks have not been resolved.

They do not replace the need for effective controls, risk assessments, validation, or formal approval.

### 5. Establishing the System Boundary

The system boundary defines which components, processes, services, data flows, and actors are included in the system card's scope.

A clear boundary is essential because AI system risks frequently arise from interactions between components rather than from the model alone.

The boundary should identify relevant elements such as:

- User interfaces and client applications.
- Model endpoints and inference services.
- Data ingestion and transformation pipelines.
- Retrieval and indexing services.
- Internal databases and document repositories.
- External APIs and third-party services.
- Tool execution environments.
- Identity and access management systems.
- Human decision and approval processes.
- Monitoring and logging services.
- Hosting infrastructure and network boundaries.

The system card should also identify relevant external dependencies that sit outside the organization's direct control.

For example, a third-party model provider may operate the inference infrastructure, while the deploying organization controls the user interface, retrieval service, and access policies.

The card should distinguish organizationally controlled components from externally operated components and clarify where responsibility is shared or limited.

System boundaries should be sufficiently precise to support risk assessment, testing, and incident investigation.

An overly narrow boundary can omit important attack paths and dependencies. An excessively broad boundary can make the card difficult to maintain and obscure the system's actual governance responsibilities.

### 6. Identifying the System and Its Intended Purpose

A system card should provide a clear, stable identity for the AI system and describe the purpose for which it is designed or approved.

The identification section should normally include:

- System name and unique identifier.
- System owner.
- Business owner or sponsoring function.
- System version or release identifier.
- Current lifecycle status.
- Deployment environment.
- Intended users.
- Intended business purpose.
- Approved use cases.
- Prohibited or unsupported uses.
- Relevant geographic or organizational scope.
- Applicable risk classification.
- Links to related model cards and governance records.

The intended purpose should be specific enough to support meaningful risk assessment.

For example, “AI assistant” is too broad to establish appropriate use boundaries. “Internal assistant that retrieves approved human resources policies and drafts responses for review by authorized HR personnel” communicates a more precise purpose.

The system card should distinguish the intended purpose from possible technical capabilities. A system may be capable of performing tasks that have not been approved for organizational use.

Where the system's intended purpose changes, the organization should reassess whether the existing card, risk assessment, evaluation evidence, and approvals remain applicable.

### 7. Describing System Capabilities and Limitations

A system card should describe what the complete system can do, what it cannot reliably do, and which conditions affect its performance.

Capabilities may arise from the combined behavior of models, retrieval services, application logic, tools, and human workflows.

Relevant capabilities may include:

- Classification and prediction.
- Text generation and summarization.
- Image, audio, or video processing.
- Information retrieval.
- Recommendation generation.
- Decision support.
- Tool execution.
- Workflow orchestration.
- Data extraction and transformation.
- Multistep planning or agentic behavior.

Limitations should be documented at the level where they arise.

For example, an underlying model may be capable of generating a coherent answer, while the deployed system may lack access to current source data. Alternatively, the model may support a language that the surrounding user interface or evaluation process does not adequately support.

The card should identify limitations that could affect intended use, including unsupported inputs, unreliable outputs, integration constraints, restricted operating conditions, and known failure scenarios.

Capabilities should not be inferred solely from marketing claims, demonstration results, or model benchmark scores.

The organization should distinguish demonstrated capability from theoretical capability, intended capability, and unverified supplier claims.

### 8. Documenting the System Architecture and Components

A system card should provide an understandable description of the system's major components and their roles.

Depending on system complexity, the documentation may include an architecture diagram, component inventory, deployment view, or references to controlled architecture records.

For each material component, the card should identify its function, ownership, dependencies, and relevance to system behavior or risk.

A component inventory may include:

| Component              | Function                                           | Governance relevance                                            |
| ---------------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| AI model               | Generates predictions, classifications, or content | Model limitations, evaluation, and version control              |
| Data ingestion service | Collects and transforms source data                | Data quality, provenance, and access restrictions               |
| Retrieval service      | Selects relevant documents or records              | Source permissions, retrieval quality, and information exposure |
| Orchestration layer    | Coordinates model and application operations       | Workflow integrity and control enforcement                      |
| Tool connector         | Allows interaction with external services          | Authorization, input validation, and action risk                |
| User interface         | Presents outputs and receives instructions         | Transparency, user understanding, and misuse prevention         |
| Identity service       | Establishes user or service identity               | Authentication and authorization                                |
| Monitoring service     | Records events and detects relevant anomalies      | Traceability, incident detection, and operational assurance     |

The table should reflect the actual system rather than a generic architecture.

Where components are shared across multiple systems, the card should explain which functions are inherited and which controls must be implemented or verified at the system level.

### 9. Documenting Data Flows and Information Processing

A system card should describe how information moves through the system from initial input to final output or action.

Data-flow documentation should identify relevant sources, transformations, processing stages, destinations, storage locations, and access boundaries.

For AI systems, relevant information may include:

- User prompts and uploaded content.
- Training or fine-tuning data where applicable.
- Retrieved documents.
- Context supplied to a model.
- Intermediate model outputs.
- Tool requests and tool responses.
- Generated content.
- Logs and telemetry.
- Feedback and evaluation records.
- Data retained by external providers.

The card should identify material data flows that influence model behavior, security, privacy, or system reliability.

For example, an assistant may retrieve an internal document and include selected passages in a prompt sent to a hosted model. The system card should describe the relevant information transfer and identify the controls governing access, processing, and retention.

The organization should distinguish between data processed temporarily, data retained by the application, and data potentially retained by external services.

Where precise data-flow details are maintained in a separate architecture or privacy record, the system card should reference the authoritative record and summarize the implications necessary for understanding the system.

### 10. Identifying Models and Model Dependencies

An AI system may use several models, including a primary model, embedding model, reranking model, classification model, moderation model, or specialized vision or speech model.

The system card should identify models that materially influence the system's behavior or risk profile.

Relevant information includes:

- Model name and provider.
- Model identifier and version.
- Model role within the system.
- Hosting or execution arrangement.
- Relationship to other models.
- Relevant model card or technical documentation.
- Known limitations affecting system behavior.
- Update and replacement arrangements.
- Dependency on external services.
- Applicable licensing or usage restrictions.

The card should distinguish between the model selected in configuration and the actual model version or endpoint serving production requests, where these can differ.

If a provider uses a managed endpoint that can change behavior without exposing a stable underlying model version, the organization should document that limitation and identify the mechanisms available to detect or assess changes.

For systems with multiple models, the organization should explain how outputs from one model influence subsequent processing.

For example, an embedding model determines which documents are retrieved, while a language model generates the final answer. Poor retrieval quality may therefore undermine answer quality even when the language model performs well independently.

### 11. Defining System Inputs, Outputs, and Operating Conditions

A system card should define the types of inputs the system accepts, the outputs it produces, and the conditions under which those operations are supported.

Input characteristics may include:

- Data format.
- Supported languages.
- File types and size limits.
- Required fields.
- Input quality expectations.
- Allowed content categories.
- Authentication requirements.
- Validation and sanitization rules.

Output characteristics may include:

- Output format.
- Confidence or uncertainty indicators where available.
- Expected response structure.
- Permitted downstream actions.
- Human review requirements.
- Output validation mechanisms.
- Restrictions on automated reliance.

Operating conditions may include hardware, software, network connectivity, external service availability, model endpoint configuration, and required security controls.

The system card should also describe behavior when inputs are incomplete, malformed, ambiguous, or outside the system's supported scope.

For example, an AI document-processing system may accept specific file types but produce unreliable extraction results for low-resolution scans. The card should identify this limitation and describe the relevant validation or escalation process.

Documenting inputs and outputs helps establish test boundaries and provides a basis for determining whether observed behavior is consistent with approved operation.

### 12. Documenting Human Oversight and Decision Authority

A system card should describe how humans interact with the system and which decisions remain under human authority.

Human oversight should be documented as an actual operational mechanism rather than a general statement that a person remains responsible.

Relevant elements include:

- Roles authorized to use the system.
- Roles responsible for reviewing outputs.
- Decisions the system may support.
- Actions the system may execute independently.
- Actions requiring human approval.
- Conditions requiring escalation.
- Methods for overriding or stopping system behavior.
- Procedures for correcting erroneous outputs.
- Responsibilities for handling complaints or adverse outcomes.

The card should distinguish between human review before an action, review after an action, and retrospective sampling.

These arrangements provide different levels of control.

For example, requiring approval before an AI agent transfers funds differs materially from reviewing a sample of completed transactions after execution.

The organization should assess whether reviewers have sufficient information, competence, time, and authority to exercise meaningful oversight.

Where a system is designed to operate without routine human review, the card should explain the approved autonomy boundaries and the controls used to detect and manage failures.

### 13. Documenting System-Level Evaluation and Validation

A system card should summarize evaluation evidence relevant to the complete deployed or intended system.

Model-level testing remains important, but it does not establish that the system behaves correctly when models interact with data pipelines, retrieval services, application logic, tools, and users.

System-level evaluation may include:

- Functional testing.
- End-to-end performance testing.
- Integration testing.
- Security testing.
- Privacy testing.
- Robustness testing.
- Safety testing.
- User acceptance testing.
- Human oversight testing.
- Failure recovery testing.
- Resilience testing.
- Monitoring and alert validation.

The card should identify the scope, methodology, relevant system version, major findings, and known limitations of the evaluation.

It should distinguish between tests completed successfully, tests that identified unresolved issues, and tests that have not been performed.

For example, a model may pass an isolated prompt-injection evaluation but remain vulnerable when retrieved documents contain malicious instructions that influence a downstream tool-enabled workflow.

System-level testing should examine the interaction between components where that interaction can introduce new risks.

The card should reference the authoritative evaluation reports rather than attempting to reproduce all test results in a single document.

### 14. Documenting Security Architecture and Trust Boundaries

System cards should communicate the security characteristics that are necessary to understand how the system is protected and where material security risks may arise.

The documentation may cover:

- Authentication and authorization.
- Network segmentation.
- Data encryption.
- Secrets and credential management.
- API security.
- Input validation.
- Output handling.
- Logging and audit trails.
- Tool execution restrictions.
- Isolation of untrusted content.
- Dependency management.
- Vulnerability management.
- Security monitoring.
- Incident response.
- Recovery and containment mechanisms.

Trust boundaries are particularly important in AI systems because instructions and data may arrive from users, retrieved documents, external services, and model-generated content.

The system card should identify where information crosses a trust boundary and what controls govern that transition.

For example, retrieved documents should not automatically be treated as trusted instructions simply because they originate from an internal repository. Their content may be outdated, maliciously modified, or inappropriate for the user's permissions.

The card should summarize relevant security controls and identify supporting evidence, such as threat models, penetration-test reports, security assessments, or architecture records.

It should avoid disclosing sensitive implementation details to audiences that do not require them. A restricted internal version may contain more technical detail than a public-facing summary.

### 15. Documenting Privacy and Data Protection Characteristics

A system card should identify privacy and data protection considerations relevant to the system's data processing and operating context.

Depending on the system, these may include:

- Categories of personal data processed.
- Sources and purposes of processing.
- Data minimization controls.
- Access restrictions.
- Retention and deletion arrangements.
- Data transfers to external providers.
- Use of data for training or service improvement.
- Data subject rights support.
- Privacy risks arising from generated outputs.
- Potential disclosure of personal or confidential information.
- Applicable privacy assessments.
- Relevant contractual and regulatory obligations.

The card should describe the system's actual processing arrangements rather than relying on general assurances about the model provider.

For example, a system may use a third-party language model while separately retaining prompts and responses in the organization's own logging platform. Both processing activities may be relevant to privacy governance.

The system card should reference applicable privacy assessments and authoritative records without attempting to replace a data protection impact assessment or other required privacy analysis.

Where the organization has not established a material processing detail, the card should identify the uncertainty and its governance implications rather than implying that the issue has been resolved.

### 16. Documenting Reliability, Resilience, and Failure Handling

AI systems can fail because of model behavior, data quality, external service outages, integration errors, infrastructure failures, or interactions between components.

A system card should identify significant failure scenarios and explain how the system detects, handles, and recovers from them.

Relevant considerations include:

- Model endpoint unavailability.
- Excessive response latency.
- Invalid or malformed outputs.
- Retrieval service failure.
- Data source unavailability.
- Tool execution failure.
- Inconsistent results across components.
- Unexpected resource consumption.
- Loss of required context.
- Monitoring or logging failure.
- Dependency outages.
- Recovery and rollback limitations.

The card should describe fallback behavior where it materially affects the system's risk.

For example, an AI-assisted support workflow may be designed to route requests to a human agent when the model service becomes unavailable. The card should document the fallback condition and relevant operational dependency.

Fallback mechanisms must not silently introduce new risks. Switching to a less capable model, bypassing a validation step, or allowing a workflow to proceed without required approval may change the system's risk profile.

The organization should maintain supporting resilience tests, recovery procedures, and service-level requirements where applicable.

### 17. Documenting Third-Party Services and External Dependencies

AI systems frequently rely on external services, including hosted models, cloud infrastructure, APIs, data providers, and specialized processing services.

The system card should identify dependencies that materially affect system functionality, security, privacy, availability, or compliance.

For relevant dependencies, it should record:

- Provider identity.
- Service or component used.
- Purpose within the system.
- Dependency criticality.
- Data exchanged.
- Relevant service and security commitments.
- Versioning and change arrangements.
- Availability and recovery assumptions.
- Known provider limitations.
- Relevant contractual restrictions.
- Alternative arrangements where available.

The organization should identify which dependencies it controls directly and which depend on provider commitments or external operating conditions.

For example, an AI service may depend on a hosted model endpoint that the organization cannot independently inspect or validate at the underlying model level.

The system card should communicate this limitation and reference the relevant supplier assessment and compensating controls.

Third-party dependency information should be maintained in coordination with procurement, vendor risk management, architecture governance, and incident response processes.

### 18. Identifying System-Level Risks and Controls

A system card should summarize material risks arising from the complete system and identify the controls used to manage them.

System-level risks may include:

- Unauthorized data access.
- Prompt injection.
- Insecure tool execution.
- Incorrect or misleading outputs.
- Failure to enforce source permissions.
- Excessive autonomy.
- Privacy leakage.
- Inadequate human oversight.
- Unreliable external dependencies.
- Uncontrolled model changes.
- Inadequate logging or incident detection.
- Unintended downstream decisions.
- Misuse outside approved boundaries.

The card should establish traceability between material risks and the organization's risk management records.

For each significant risk, relevant information may include the risk description, affected components, potential consequences, applicable controls, control owners, residual uncertainty, and references to supporting assessments.

The card does not need to reproduce the full enterprise risk register. It should provide sufficient context for stakeholders to understand the system's principal risks and locate the authoritative risk records.

The presence of a documented control does not establish that it operates effectively. Where the effectiveness of a material control has not been verified, that limitation should be communicated accurately.

### 19. Establishing System Card Ownership and Approval

A system card requires clear ownership and controlled approval.

The system owner should be accountable for ensuring that the card reflects the system's approved design and operational context. Contributors should provide authoritative information about the components and controls under their responsibility.

Relevant contributors may include:

- AI or machine learning engineering.
- Enterprise architecture.
- Application development.
- Data engineering and data governance.
- Cybersecurity.
- Privacy and data protection.
- Legal and compliance.
- Business operations.
- Third-party risk management.
- Model validation.
- Site reliability or platform engineering.

The organization should distinguish contributors from reviewers and approving authorities.

A system card may require multiple reviews because its content spans technical architecture, operational behavior, security, privacy, and business use.

The approval workflow should establish which deficiencies prevent approval, which can be accepted through a formal exception, and which require further testing or remediation.

Approval of the card should not be confused with approval to deploy the system. The deployment authority must consider all required governance gates, including risk acceptance and operational readiness.

### 20. Defining System Card Lifecycle Status

System cards should have an explicit lifecycle status that indicates their current governance state.

A useful lifecycle model may include:

- **Draft:** Documentation is being prepared and has not completed required review.
- **Under review:** Required contributors or reviewers are assessing the card.
- **Approved:** The card has passed the defined approval process.
- **Conditionally approved:** Use is permitted subject to documented conditions and authorized exceptions.
- **Superseded:** A newer approved version has replaced the card.
- **Suspended:** The card or associated approval is temporarily inactive because of a governance or operational concern.
- **Retired:** The associated system is no longer approved for active use.

The organization should define these statuses consistently and establish the conditions under which a status can change.

A card's status should not be inferred from a file name, document location, or the date it was last edited.

The status should be linked to the controlled approval record where possible.

If a material system change invalidates the existing approval, the organization should determine whether the card must return to review, whether deployment authorization must be reconsidered, or whether the system must be restricted pending reassessment.

Historical versions should remain identifiable so that past decisions can be reconstructed when required.

### 21. Part 1 Core Principle

> **A system card describes the complete AI system within a defined operational boundary, connecting its architecture, components, data flows, capabilities, limitations, controls, and dependencies to accountable governance decisions.**

Model cards explain individual model characteristics. System cards explain how models and surrounding components interact to produce the behavior experienced by users and downstream processes.

Effective system cards provide a traceable, evidence-based view of the system as actually deployed or intended to be deployed. They identify material risks and limitations, distinguish verified facts from unresolved assumptions, and connect technical information to risk management, approval, monitoring, and change control.

The central governance principle is that **the system must be assessed and documented as an integrated whole, because the risks and behavior of an AI-enabled solution cannot be understood from the underlying model alone.**

# 19.15 — System Cards

## Part 2 — System Card Design, Content Requirements, and Technical Implementation

### 22. Establishing a Standardized System Card Template

A standardized system card template establishes a consistent structure for documenting AI systems across the organization. Standardization improves completeness, comparability, review efficiency, and integration with enterprise governance processes.

The template should define required sections, conditional fields, evidence references, ownership requirements, and approval metadata.

A comprehensive template may include the following sections:

1. System identification and ownership.
2. Intended purpose and approved use cases.
3. System boundary and operating context.
4. Architecture and component inventory.
5. Model inventory and dependencies.
6. Data flows and information processing.
7. Inputs, outputs, and operating conditions.
8. Capabilities and known limitations.
9. System evaluation and validation.
10. Security architecture and controls.
11. Privacy and data protection.
12. Safety, reliability, and resilience.
13. Human oversight and decision authority.
14. Third-party dependencies.
15. Risk assessment and control mapping.
16. Monitoring and incident management.
17. Change management and review triggers.
18. Regulatory and contractual considerations.
19. Approval status and exceptions.
20. Version history and supporting evidence.

The template should support both simple and complex systems without requiring every system to complete every field identically.

For example, a deterministic application containing a single predictive model may not need the same level of tool-orchestration documentation as an autonomous AI agent that accesses multiple enterprise services.

The organization should define the minimum required content and the conditions that trigger enhanced documentation.

### 23. Defining Mandatory, Conditional, and Optional Fields

System card templates should distinguish between mandatory, conditional, and optional information.

**Mandatory fields** are required for every in-scope system unless an explicitly authorized exception applies.

Examples include system identifier, accountable owner, intended purpose, lifecycle status, system boundary, and approval state.

**Conditional fields** become mandatory when specific characteristics or risks are present.

Examples include tool permissions for agentic systems, personal data processing for systems handling personal information, and external-provider information for systems dependent on third-party AI services.

**Optional fields** provide additional context when relevant but are not required for every system.

Examples may include specialized hardware benchmarks, detailed modality-specific performance information, or additional architecture views.

The template should specify how users record information that is unavailable, unknown, not assessed, or not applicable.

These states should not be treated as interchangeable:

- **Not applicable:** The field does not apply to the system, with a defensible rationale.
- **Unknown:** The relevant information has not been established.
- **Not assessed:** The organization has not performed the required assessment.
- **Unavailable:** The information cannot currently be obtained from the responsible source.
- **Pending:** The information is expected but has not yet been finalized.

This distinction is important because missing information may indicate a governance gap, whereas a genuinely inapplicable field may require no further action.

### 24. Defining Field-Level Documentation Requirements

Every important system card field should have a defined purpose, expected content, source of truth, responsible contributor, and validation rule where appropriate.

Without field-level requirements, teams may complete the same template using inconsistent interpretations.

For example, a field labeled "Security Controls" may receive a vague response such as "The system is protected by enterprise security." This statement does not identify the controls, their scope, or the evidence supporting their effectiveness.

A better field definition would require a description of the relevant controls, affected components, accountable control owners, and references to supporting security assessments.

A field specification should define:

- Field name and unique identifier.
- Description and intended governance purpose.
- Required or conditional status.
- Accepted data type or format.
- Permitted values, where applicable.
- Responsible information provider.
- Authoritative source.
- Evidence requirements.
- Validation criteria.
- Review and approval requirements.

For material risk-related claims, the template should favor precise, evidence-based statements over broad assurances.

### 25. Representing System Cards as Structured Data

Although a system card may be presented as a document, its underlying information can be maintained as structured data.

Structured representations support automated validation, reporting, integration with governance platforms, and comparisons across systems.

A system card data model may include entities such as:

- AI system.
- System version.
- Component.
- Model dependency.
- Data source.
- Data flow.
- Interface.
- External provider.
- Risk.
- Control.
- Evaluation.
- Incident.
- Approval.
- Evidence record.
- Responsible person or organizational function.

Relationships between these entities are especially important.

For example, a system may contain several models, use multiple data sources, depend on external providers, and implement controls across different components.

The data model should represent these relationships without duplicating information unnecessarily.

A simplified conceptual structure might be:

```
system:
  system_id: AI-SYS-0042
  name: Internal Knowledge Assistant
  version: "2.1"
  owner: Enterprise AI Product Owner
  status: approved

  intended_purpose:
    - Retrieve approved internal knowledge
    - Draft responses for employee review

  components:
    - component_id: retrieval-service
      type: retrieval
    - component_id: language-model
      type: foundation-model
    - component_id: access-control
      type: security-control

  dependencies:
    - provider: External AI Provider
      dependency_type: hosted-model-service

  governance:
    risk_assessment_id: RISK-0042
    approval_record_id: APPROVAL-0042
```

This example illustrates a possible structure rather than a mandatory schema. Actual field names, identifiers, and accepted values should be defined by the organization's governance architecture.

Structured data should not be treated as authoritative merely because it is machine-readable. Its accuracy depends on source quality, ownership, validation, and controlled updates.

### 26. Maintaining a Canonical System Identifier

Every in-scope AI system should have a stable, unique identifier that distinguishes it from related models, applications, deployments, and system versions.

A canonical identifier helps link the system card to the AI inventory, risk register, architecture repository, model registry, incident management platform, and approval records.

The organization should distinguish among:

- System identifier.
- Model identifier.
- Component identifier.
- Deployment identifier.
- Version or release identifier.
- Environment identifier.
- Governance record identifier.

These identifiers serve different purposes and should not be substituted for one another.

For example, one AI system may use the same foundation model across development, testing, and production environments while applying different configurations and permissions.

The system card should identify the relevant deployment context and version so that reviewers can determine which configuration the documentation describes.

Identifier conventions should remain stable even when system names, business owners, or hosting arrangements change.

### 27. Maintaining System Versions and Configuration Baselines

A system card should identify the version or configuration baseline to which its contents apply.

AI system behavior may change without a corresponding change to the underlying model. Changes to prompts, retrieval logic, data sources, orchestration, tool permissions, filters, or application code may materially alter the system's behavior.

A system version should therefore represent the relevant combination of components and configuration needed to identify the evaluated and approved system.

Depending on the architecture, the configuration baseline may reference:

- Model names and versions.
- Application release.
- Prompt or instruction-set version.
- Retrieval and indexing configuration.
- Data source versions or snapshots.
- Tool definitions and permissions.
- Security policy versions.
- Evaluation dataset versions.
- Deployment configuration.
- Relevant external service versions.

The organization should define which changes require a new system version and which can be managed as controlled configuration updates.

The card should avoid claiming that a system is unchanged merely because its primary model identifier remains the same.

### 28. Establishing Authoritative Sources for System Card Information

System cards frequently consolidate information maintained by several technical and governance teams.

To reduce inconsistency, the organization should identify an authoritative source for each important field.

| Information category        | Potential authoritative source                        |
| --------------------------- | ----------------------------------------------------- |
| System identifier and owner | AI inventory or enterprise service registry           |
| Model identity and version  | Model registry or provider documentation              |
| Architecture                | Approved architecture repository                      |
| Data flows                  | Data-flow inventory or privacy documentation          |
| Risk assessment             | Enterprise AI risk register                           |
| Security controls           | Security architecture and control records             |
| Privacy assessment          | Privacy management repository                         |
| Evaluation results          | Testing and validation repository                     |
| Third-party dependencies    | Vendor and third-party risk management system         |
| Approval status             | Governance workflow or approval register              |
| Production deployment       | Release management or configuration management system |
| Incidents                   | Incident management platform                          |
| Change history              | Change management system                              |

These are illustrative mappings. The organization should use its actual systems of record.

Where information is imported automatically, the process should preserve source identity, retrieval time, and relevant version metadata.

Where information is entered manually, the workflow should identify the responsible contributor and provide a mechanism for review.

Conflicts between authoritative sources should be investigated rather than resolved through silent overwriting.

### 29. Linking System Cards to Architecture Diagrams

Architecture diagrams can make complex system interactions easier to understand, but they should be maintained as controlled artifacts.

The system card should reference diagrams that accurately represent the documented system boundary and relevant deployment configuration.

Useful diagram types include:

- System context diagrams.
- Logical architecture diagrams.
- Deployment architecture diagrams.
- Data-flow diagrams.
- Trust-boundary diagrams.
- Integration and dependency diagrams.
- AI processing and orchestration flows.

The level of detail should be appropriate to the system's complexity and the card's audience.

A high-level business audience may need to understand which systems exchange information and where human approval occurs. A security reviewer may require additional detail about trust boundaries, service identities, and external endpoints.

The card should identify the diagram's version or authoritative location and indicate whether the diagram reflects the current approved configuration.

A diagram should not be considered current merely because it remains accessible in the architecture repository.

Material architecture changes should trigger a review of both the diagram and the system card.

### 30. Documenting Component-Level Responsibility

Complex AI systems may contain components owned by different teams or suppliers.

A system card should clarify responsibility for material components and identify the interfaces between their control responsibilities.

For example:

- The AI engineering team maintains the model integration.
- The data platform team manages ingestion and indexing.
- The cybersecurity team establishes security requirements.
- The business owner defines approved workflows.
- The cloud provider operates underlying infrastructure.
- The application team maintains authorization and user interfaces.

These arrangements should be reflected in the card where they affect risk ownership, incident response, change approval, or control effectiveness.

Responsibility should be assigned for both component operation and cross-component risks.

A security control implemented by one team may depend on a configuration maintained by another. The card should identify the relevant dependency and the mechanism for confirming that the control continues to operate as intended.

Component ownership does not remove the system owner's accountability for understanding the integrated system and ensuring that material system-level risks are addressed.

### 31. Integrating System Cards with Model Registries and AI Inventories

System cards should be connected to the organization's AI inventory and relevant model registry.

An AI inventory provides visibility into the systems and use cases in scope. A model registry maintains information about model artifacts, versions, and lifecycle states.

A system card adds structured context about how the system is assembled, deployed, evaluated, and governed.

The integration should allow authorized users to navigate between:

- The AI system record.
- Related model records.
- Deployment environments.
- System and model versions.
- Risk assessments.
- Evaluation evidence.
- Security and privacy assessments.
- Approval decisions.
- Incident records.
- Relevant supplier assessments.

This relationship is particularly important where a model is reused in multiple systems.

A model-level limitation may affect several downstream systems, but its operational consequences may differ depending on each system's data, users, controls, and intended purpose.

The organization should therefore maintain shared model information centrally where feasible while preserving system-specific assessments and approvals.

### 32. Linking System Cards to Risk and Control Records

A system card should provide traceable links to the risk assessments and control records relevant to the system.

This avoids treating the card as an isolated narrative and enables governance teams to determine how documented system characteristics relate to identified risks and implemented safeguards.

A useful mapping may connect:

1. System component.
2. Threat or failure scenario.
3. Identified risk.
4. Applicable control.
5. Control owner.
6. Test or assessment evidence.
7. Residual risk.
8. Approval or acceptance decision.

For example, a retrieval component may create a risk of unauthorized information disclosure if document permissions are not enforced correctly.

The system card should identify the relevant component and summarize the risk. The detailed risk register should record the risk analysis, while the control repository should identify the applicable access-control requirements and supporting tests.

The system card should reference the authoritative records rather than reproduce them in full.

Where a risk has no implemented control or where control effectiveness remains unverified, the documentation should reflect that status accurately.

### 33. Designing Audience-Specific System Card Views

Different audiences require different levels of system information.

A system card may be maintained as one controlled source with audience-specific views, or as coordinated versions derived from the same authoritative information.

Typical audiences include:

- Business owners and senior management.
- System operators.
- AI engineers and architects.
- Cybersecurity and privacy teams.
- Risk and compliance functions.
- Internal audit.
- Customers and business partners.
- Regulators and other authorized external stakeholders.
- End users affected by the system.

A management view may emphasize intended purpose, principal risks, accountability, approval status, and residual concerns.

An engineering view may include component versions, interfaces, evaluation evidence, and operational dependencies.

A security view may include trust boundaries, access controls, attack surfaces, and incident response arrangements.

An external view may explain capabilities, limitations, appropriate use, and relevant transparency information without disclosing confidential implementation details.

Audience-specific views must not introduce contradictory statements or conceal material information necessary for the audience's authorized role.

Access restrictions should protect sensitive information while preserving the transparency required by applicable law, contracts, and governance policies.

### 34. Establishing Evidence Requirements for System Card Claims

System card statements should be supported by evidence proportionate to their significance and the risk of relying on them.

Evidence may include:

- Architecture records.
- Configuration snapshots.
- Model cards.
- Test and validation reports.
- Threat models.
- Security assessment reports.
- Privacy assessments.
- Data-flow records.
- Monitoring results.
- Supplier documentation.
- Contractual commitments.
- Incident reports.
- Approval records.
- Operational procedures.

The card should distinguish between claims supported by independent testing, claims supported by internal testing, claims reported by suppliers, and claims that remain unverified.

For example, stating that a system enforces access restrictions should be supported by relevant design information and evidence that the restrictions operate as intended.

A description of an intended control is not proof that the control is implemented or effective.

The organization should define evidence acceptance criteria for material claims and determine when independent review is required.

Where evidence is unavailable, the card should identify the resulting uncertainty and its implications for deployment or continued use.

### 35. Establishing Automated System Card Validation

Automated validation can detect structural deficiencies and inconsistencies before a system card enters formal review.

Validation rules may check:

- Required fields are populated.
- System identifiers are unique.
- Version information is present.
- Owner references resolve to valid records.
- Approval status is consistent with workflow records.
- Referenced models exist in the model registry.
- Risk and control links resolve.
- Required evidence references are present.
- Conditional sections are completed.
- Review dates are valid.
- Exceptions have an authorized status.
- Retired systems are not incorrectly represented as actively approved.

Validation should distinguish structural correctness from substantive accuracy.

A field may be populated but contain misleading information. A risk record may exist but fail to address the relevant system risk. A reference may resolve successfully while pointing to outdated evidence.

Automated checks should therefore support, rather than replace, human review and risk-based assurance.

The organization should record validation failures, assign remediation owners, and define which failures block approval.

### 36. Establishing the System Card Approval Workflow

The approval workflow should reflect the system's risk classification, technical complexity, and applicable governance requirements.

A typical workflow may include the following stages:

1. **Preparation:** The system owner coordinates completion of the card.
2. **Technical review:** Relevant engineering and architecture teams verify system characteristics.
3. **Security and privacy review:** Applicable security and privacy considerations are assessed.
4. **Risk review:** Material risks, controls, and unresolved uncertainties are examined.
5. **Business review:** The intended purpose and operational assumptions are confirmed.
6. **Compliance review:** Relevant legal, regulatory, and contractual requirements are considered.
7. **Approval:** The authorized authority approves the card or identifies required conditions.
8. **Publication:** The approved version is made available to authorized stakeholders.
9. **Lifecycle maintenance:** The card is reviewed and updated when required.

Not every system requires identical reviewers. The organization should define which reviews are mandatory and which depend on system characteristics.

The workflow should record review outcomes, outstanding actions, exceptions, and approval conditions.

Approval should be withheld where a material deficiency prevents an informed decision or where required evidence has not been obtained.

### 37. Managing System Card Exceptions and Unresolved Information

System card preparation may identify information gaps that cannot be resolved immediately.

Examples include incomplete provider documentation, uncertain behavior in an external service, unavailable historical configuration records, or an evaluation that has not covered a relevant operating condition.

The organization should record the gap, its cause, the potential consequences, and the actions required to resolve it.

An exception record should include:

- The unmet requirement.
- The affected system and component.
- The reason for the gap.
- The associated risk.
- Available compensating controls.
- The responsible owner.
- The approving authority.
- The permitted operating conditions.
- The remediation target date.
- The review or expiry date.

The organization should determine whether the gap is acceptable, requires additional safeguards, or prevents deployment.

A system card should not present an unknown characteristic as a verified fact simply to complete the template.

Material uncertainties should remain visible to the decision-makers responsible for approving or accepting the associated risks.

### 38. Controlling System Card Versions and Changes

System cards should be maintained through formal document and configuration management.

Each approved version should identify the system configuration it describes and preserve the relevant approval history.

Changes that may require card review include:

- Introduction or replacement of a model.
- Changes to model versions or provider endpoints.
- Changes to data sources or retrieval logic.
- Changes to prompts or orchestration.
- Addition of tools or external integrations.
- Changes to permissions or trust boundaries.
- Changes to intended purpose.
- Changes to human oversight arrangements.
- Changes to security or privacy controls.
- Changes to operating conditions.
- Material evaluation findings.
- Security or safety incidents.
- Changes in applicable obligations.

The organization should classify changes according to their potential effect on system behavior and risk.

Minor administrative corrections may require a controlled revision without renewed deployment approval. Material changes may require new evaluation, updated risk assessment, formal approval, or restrictions on use.

The change process should preserve the ability to determine which card version applied to a particular deployment at a particular time.

### 39. Maintaining System Card Consistency Across Environments

AI systems are often deployed in development, testing, staging, and production environments.

These environments may differ in model versions, data access, security configuration, external integrations, and permissions.

A system card should identify the environment to which it applies and document material differences where they affect system behavior or risk.

The organization should avoid assuming that successful testing in one environment establishes equivalent behavior in another.

For example, a test environment may use synthetic data and restricted tools, while the production environment accesses sensitive business records and can execute actions through external APIs.

The production system therefore has a different risk profile, even if both environments use the same underlying model.

Where the organization maintains a common system card across multiple environments, it should identify the approved configuration for each environment and document significant differences.

Production authorization should be based on evidence that the actual deployment configuration satisfies the applicable requirements.

### 40. Part 2 Core Principle

**System card design and technical implementation must produce a controlled, traceable, and maintainable record of the complete AI system.**

A standardized template establishes consistency, but effective implementation also requires structured identifiers, authoritative information sources, version control, evidence traceability, integration with enterprise governance records, and controlled approval workflows.

The system card should accurately represent the system configuration to which it applies. It should distinguish verified information from assumptions and unresolved gaps, connect material risks to authoritative records, and remain consistent with the AI inventory, model registry, architecture documentation, and operational configuration.

The central implementation principle is that **system card quality depends not only on what the document contains, but also on the reliability of its sources, the integrity of its lifecycle controls, and its alignment with the system actually operating in production.**

## Part 3 — Operational Governance, Monitoring, Change Management, and Assurance

### 41. Operational Governance of System Cards

A system card must remain an operational governance artifact throughout the AI system lifecycle, rather than becoming a static document completed during design or approval. Its value depends on whether the documented system accurately reflects the system operating in production and whether accountable stakeholders use the information to make governance decisions.

Operational governance establishes how system cards are maintained, reviewed, challenged, and used to support ongoing risk management.

Key operational governance activities include:

- **Ownership:** Assign accountability for maintaining the system card to a designated system owner or authorized delegate.
- **Technical validation:** Require engineering or architecture personnel to verify that the documented components, interfaces, integrations, and configurations match the deployed system.
- **Security validation:** Confirm that security controls, trust boundaries, privileged access paths, monitoring mechanisms, and incident response arrangements are accurately documented.
- **Risk review:** Reassess whether the documented risks remain valid and whether existing controls continue to address the system's actual exposure.
- **Compliance review:** Verify that applicable legal, regulatory, contractual, and internal policy requirements are reflected in the system's governance record.
- **Independent challenge:** Where risk warrants it, require a second-line risk function or independent assurance team to challenge material claims and supporting evidence.

The governance process should distinguish between preparing a system card, validating its technical accuracy, approving its governance status, and independently assuring its effectiveness. These responsibilities may be distributed across several roles.

A completed system card does not automatically establish that a system is secure, compliant, or acceptable for deployment. It establishes a documented basis for evaluating those conditions.

### 42. Production Monitoring and System Card Accuracy

Production monitoring generates evidence about how an AI system behaves under real operating conditions. System cards should identify the monitoring mechanisms that provide this evidence and explain how significant findings affect the documented risk profile.

Monitoring coverage may include:

- Availability, latency, throughput, and service reliability.
- Model performance, output quality, and degradation.
- Input and output validation failures.
- Unauthorized access attempts and privilege misuse.
- Prompt injection, jailbreak attempts, and other AI-specific attack patterns.
- Sensitive-data exposure, data leakage, and inappropriate retention.
- Tool invocation, agent actions, and interactions with external systems.
- Human override rates, escalation frequency, and rejected recommendations.
- Third-party service failures and dependency changes.
- Policy violations, anomalous behavior, and unexpected system outputs.

The system card should not reproduce every operational metric or monitoring event. Instead, it should identify the relevant telemetry sources, responsible monitoring functions, escalation thresholds, and relationships between monitoring results and governance decisions.

For example, a system card for an AI customer-support assistant may identify output filtering, sensitive-data detection, retrieval monitoring, and tool-call auditing as key safeguards. It should also explain where these controls are implemented, which team operates them, and how material failures are escalated.

Monitoring information should be used to reassess documented assumptions. If production evidence shows that the system behaves differently from its approved description, the discrepancy should trigger investigation and, where appropriate, a system-card update, risk reassessment, or restriction of system functionality.

### 43. Change Triggers and Mandatory Reassessment

System-card maintenance should be driven by defined change triggers rather than relying exclusively on periodic reviews. A material system change can invalidate previously documented assumptions, control mappings, evaluations, and approvals.

Organizations should establish criteria that determine when a change requires documentation updates, formal risk reassessment, renewed approval, or a combination of these actions.

Common change triggers include:

- **Model changes:** Replacing a model, changing its version, modifying model weights, or introducing a different model provider.
- **Prompt and policy changes:** Revising system instructions, safety policies, refusal behavior, or decision logic in ways that affect risk.
- **Data changes:** Introducing new data sources, changing retrieval corpora, modifying training or fine-tuning data, or expanding access to sensitive information.
- **Architecture changes:** Adding components, APIs, services, integrations, or trust boundaries.
- **Permission changes:** Expanding tool permissions, service-account privileges, administrative access, or autonomous execution capabilities.
- **Deployment changes:** Moving between environments, changing hosting arrangements, or introducing new geographic processing locations.
- **User and purpose changes:** Extending the system to new populations, business functions, or decision contexts.
- **Regulatory changes:** Introducing new obligations or materially changing the applicability of existing requirements.
- **Incident-driven changes:** Identifying a vulnerability, control failure, harmful output pattern, or unanticipated misuse scenario.
- **Supplier changes:** Replacing a third-party model, changing contractual terms, or introducing a new external dependency.

Change classification should be proportionate to risk. A routine maintenance change may require a controlled documentation update, whereas a change that expands access to sensitive data or enables autonomous external actions may require renewed testing, risk acceptance, and approval before release.

A change record should identify the affected system-card fields, the reason for the change, the assessment performed, the evidence reviewed, the approving authority, and the effective date.

### 44. Connecting System Cards to Change Management and Release Controls

System cards should integrate with established change-management and software-release processes. Maintaining a separate governance document without linking it to engineering workflows creates a risk that changes reach production before their governance implications have been assessed.

An effective integration connects the system card to:

1. The change request or engineering work item.
2. The affected system and component identifiers.
3. The proposed technical or operational change.
4. The change's security, privacy, safety, and compliance implications.
5. Required testing and validation evidence.
6. The updated risk assessment and control mappings.
7. Required governance approvals.
8. The release record and deployed configuration.
9. Post-deployment verification where warranted.

The release process should define when a system-card update is mandatory and whether the updated card must be approved before deployment.

For higher-risk systems, release gates can require confirmation that material changes have been reflected in the system card and that required evaluations have passed. Emergency changes may follow an expedited procedure, but the organization should retain traceability and require retrospective review within a defined period.

The objective is not to introduce unnecessary documentation overhead. It is to ensure that governance information remains synchronized with the technical change lifecycle and that material changes cannot bypass risk-based oversight.

### 45. Incident Management and System Card Updates

AI-related incidents can reveal weaknesses in system design, incomplete assumptions, ineffective controls, or undocumented dependencies. The system card should provide information that supports incident response and should be updated when an incident materially changes the understanding of the system.

Relevant incident scenarios include:

- Exposure of confidential information through generated outputs.
- Prompt injection leading to unauthorized tool execution.
- Compromise of an AI component or its supporting infrastructure.
- Inaccurate or harmful outputs that affect consequential decisions.
- Unauthorized modification of prompts, retrieval data, models, or system configuration.
- Excessive autonomous actions or actions performed outside approved boundaries.
- Failure of a critical supplier or external AI service.
- Circumvention or degradation of safety and security controls.

During incident response, the system card can help responders identify system owners, model providers, data flows, external dependencies, trust boundaries, logging sources, and containment options.

Following an incident, the organization should determine whether the card requires updates to:

- Known threats and abuse scenarios.
- Risk ratings and risk acceptance conditions.
- Control descriptions and implementation status.
- Monitoring and detection coverage.
- Incident escalation and recovery procedures.
- System limitations and prohibited uses.
- Residual-risk statements and approval conditions.

An incident does not automatically require rewriting the entire card. Updates should reflect validated findings and material changes to the system's documented risk and control position. Unconfirmed hypotheses should remain distinguishable from established facts.

Incident-driven changes should also be linked to the incident record, root-cause analysis, corrective actions, and relevant assurance findings. This creates traceability from the operational event to the resulting governance response.

### 46. System Cards for AI Agents and Tool-Enabled Systems

AI agents require particularly careful system-card documentation because their behavior may depend on model reasoning, tool permissions, external data, memory, orchestration logic, and multi-step execution.

A system card for an agent should describe the complete operational system, not merely the underlying foundation model.

Important elements include:

- **Agent objectives:** The tasks the agent is authorized to perform and the conditions under which it must stop.
- **Available tools:** APIs, databases, browsers, code execution environments, communication channels, and other callable capabilities.
- **Permission boundaries:** The actions permitted for each tool, including read, write, delete, execute, and administrative operations.
- **Execution constraints:** Limits on the number of steps, duration, transaction value, resource consumption, or external actions.
- **Human approval gates:** Actions that require explicit review before execution.
- **Memory and state:** Information retained across steps or sessions, its storage location, retention rules, and access restrictions.
- **Delegation and sub-agents:** Whether the system can invoke other agents, transfer tasks, or delegate authority.
- **External communication:** How the agent accesses external content and how untrusted instructions are isolated from authorized system instructions.
- **Action logging:** How prompts, tool calls, approvals, outputs, and consequential actions are recorded.
- **Recovery and containment:** How operators revoke credentials, disable tools, interrupt execution, or return the system to a safe state.

The card should distinguish between the agent's intended capabilities and the capabilities technically available to it. If an agent is intended only to read customer records but possesses write permissions, the discrepancy represents a governance concern even if the write functionality is not part of its normal workflow.

For agentic systems, documentation should also identify the boundaries between model-generated recommendations and actions that change external state. This distinction is essential for assessing autonomy, accountability, and the effectiveness of human oversight.

### 47. System Cards for Retrieval-Augmented Generation Systems

Retrieval-augmented generation (RAG) systems introduce risks arising from the interaction between a model and external information sources. Their system cards should describe the retrieval pipeline and its security boundaries in addition to the model and application components.

Relevant documentation includes:

- Source repositories, databases, document stores, and indexing services.
- Data ingestion, transformation, chunking, embedding, and indexing processes.
- Retrieval methods, relevance thresholds, filtering, and ranking.
- Authorization checks applied to users and retrieved documents.
- Treatment of confidential, personal, regulated, or restricted information.
- Protection against poisoned documents and malicious embedded instructions.
- Separation between trusted system instructions and untrusted retrieved content.
- Citation, provenance, and source-attribution mechanisms.
- Index refresh, deletion propagation, and stale-data handling.
- Monitoring for unauthorized retrieval, data leakage, and anomalous queries.

A RAG system card should document whether access restrictions are enforced at retrieval time and whether they remain effective across caches, vector stores, generated summaries, and downstream processing.

For example, a document repository may enforce access permissions correctly while a separately maintained vector index does not. The system card should identify the relevant enforcement point and supporting evidence rather than assuming that the security of the source repository guarantees the security of the complete AI system.

Where retrieved content can contain adversarial instructions, the card should document how those instructions are treated as untrusted input and what controls limit their ability to influence tool use or access restricted information.

### 48. System Cards for Third-Party and Externally Hosted AI Services

Organizations frequently deploy AI systems whose models, infrastructure, or operational controls are managed by external providers. In these situations, the system card should distinguish controls directly implemented by the organization from controls operated by suppliers.

Documentation should identify:

- The provider and relevant service or model identifiers.
- The service version or model reference, where available.
- The hosting and deployment arrangement.
- Data transmitted to the provider and the purposes of processing.
- Available configuration and security options.
- Provider responsibilities and customer responsibilities.
- Relevant contractual commitments and service-level conditions.
- Available assurance reports, certifications, and other supporting evidence.
- Limitations in provider transparency or independent verification.
- Dependency, availability, portability, and exit considerations.
- Procedures for evaluating provider changes and material service updates.

Supplier documentation should not be treated as sufficient proof of the security of the organization's complete implementation. A provider may offer secure infrastructure, for example, while the customer exposes sensitive information through excessive permissions, unsafe prompts, or inappropriate retention settings.

The system card should record material gaps between provider assurances and the organization's own requirements. Where the organization cannot verify a relevant control directly, it should identify the evidence relied upon, the limitations of that evidence, and the resulting residual risk.

For externally hosted models that change without a fixed version identifier, the organization should document the provider's change-notification mechanisms, available version controls, evaluation procedures, and contingency arrangements for unexpected behavioral changes.

### 49. Periodic Review and Event-Driven Review

A mature system-card program combines scheduled review with event-driven review.

Scheduled reviews provide a minimum governance cadence. Event-driven reviews respond to changes or findings that could invalidate the existing record before the next scheduled review.

The review frequency should reflect the system's risk, rate of change, operational criticality, regulatory exposure, and degree of autonomy. A low-impact internal productivity assistant may require a different review cadence from an AI system used in consequential decisions or one capable of executing privileged actions.

A review should assess whether:

- The system remains within its approved purpose and scope.
- Documented components and dependencies remain accurate.
- Model, data, and configuration references reflect the deployed system.
- Risks and controls remain relevant.
- Monitoring and evaluation results reveal material degradation.
- Outstanding exceptions remain valid and properly authorized.
- Incident findings and corrective actions have been incorporated.
- Applicable obligations and contractual commitments have changed.
- Ownership and approval responsibilities remain current.
- The system's operational status still matches its recorded lifecycle state.

The review outcome should be recorded even when no changes are required. A documented no-change decision provides evidence that the system was reviewed rather than simply left untouched.

Where a review identifies material inaccuracies, unresolved risk, or expired approval conditions, the system should be escalated according to the organization's governance process. The appropriate response may include remediation, restricted operation, renewed approval, suspension, or retirement.

### 50. Governance Metrics and Operational Effectiveness

System-card metrics should measure whether the documentation process improves governance and control effectiveness, rather than merely counting completed documents.

Useful metrics may include:

| Metric                       | What it measures                                                          | Governance interpretation                                   |
| ---------------------------- | ------------------------------------------------------------------------- | ----------------------------------------------------------- |
| System-card coverage         | Percentage of in-scope AI systems with required cards                     | Indicates completeness of governance documentation          |
| Mandatory-field completeness | Percentage of required fields populated and validated                     | Identifies missing core information                         |
| Review timeliness            | Percentage of cards reviewed within the required period                   | Indicates adherence to review requirements                  |
| Change-update latency        | Time between a material system change and the corresponding card update   | Identifies synchronization weaknesses                       |
| Approval traceability        | Percentage of applicable systems with recorded, current approval evidence | Measures approval-record completeness                       |
| Evidence freshness           | Percentage of evidence references that remain valid and current           | Indicates whether documented control claims are supportable |
| Accuracy findings            | Number or rate of material discrepancies discovered during validation     | Reveals documentation quality issues                        |
| Exception aging              | Number or proportion of overdue system-card exceptions                    | Identifies unresolved governance weaknesses                 |
| Incident-driven updates      | Percentage of relevant incidents followed by documented review or update  | Measures integration with incident management               |
| Audit finding recurrence     | Frequency of repeated system-card-related findings                        | Indicates whether corrective actions address root causes    |

Metrics should have defined owners, calculation rules, reporting periods, and escalation thresholds. Results should be segmented where appropriate by risk tier, business unit, system type, and lifecycle stage.

Organizations should avoid optimizing for superficial completeness. A system card with every field populated can still be inaccurate, outdated, or unsupported by evidence. Quantitative measures should therefore be complemented by risk-based sampling, technical validation, and independent review.

### 51. Evidence Requirements for Operational Claims

System cards frequently contain statements such as “access is restricted,” “outputs are monitored,” or “human approval is required.” These claims should be supported by evidence appropriate to their risk and significance.

Evidence may include:

- Architecture and data-flow diagrams.
- Approved configuration baselines.
- Identity and access-management policies.
- Access-control test results.
- Security evaluation and adversarial testing reports.
- Logging and monitoring configurations.
- Incident records and post-incident reviews.
- Privacy assessments and data-processing records.
- Vendor assurance documentation.
- Release approvals and change records.
- Control test results and audit workpapers.
- Human oversight procedures and operating records.

Evidence should be traceable to the relevant system, component, control, environment, and review period. Where practical, references should point to authoritative records instead of copying large volumes of evidence into the system card.

The organization should distinguish between different levels of assurance:

- **Documented design:** Evidence that a control has been specified.
- **Implemented configuration:** Evidence that the control has been configured or deployed.
- **Operational execution:** Evidence that the control is functioning in practice.
- **Effectiveness testing:** Evidence that the control achieves its intended outcome under relevant conditions.

For example, an approved policy requiring human review does not demonstrate that review actually occurs. Operational records, workflow enforcement, sampling, and effectiveness testing may be needed to support that claim.

Evidence limitations should be recorded where they affect the reliability of a governance conclusion. Missing evidence must not be silently interpreted as proof that a control is absent, nor should the existence of a policy be treated as proof that a control is effective.

### 52. Exceptions, Risk Acceptance, and Compensating Controls

Some systems may not satisfy every system-card requirement immediately. Legacy architectures, provider limitations, emergency deployments, or unavailable technical evidence can create temporary or justified exceptions.

Exceptions should be managed through a formal process that identifies:

- The specific requirement that cannot be met.
- The affected system and component.
- The reason for the exception.
- The risk created by the deviation.
- The proposed compensating controls.
- The accountable risk owner.
- The approving authority.
- The effective date and expiration or review date.
- The remediation plan, where remediation is required.
- The evidence supporting closure.

A system-card exception must not automatically authorize the underlying AI risk. Approval to omit a documentation field is different from acceptance of a security vulnerability or regulatory non-compliance.

Where a missing field prevents the organization from understanding a material risk, the exception should be escalated according to risk appetite and approval authority. Some gaps may be incompatible with deployment or continued operation.

Compensating controls should be assessed for effectiveness, independence, and coverage of the original risk. For example, if a supplier does not expose detailed model-level telemetry, the organization might implement additional application-level logging and output monitoring. Such measures may reduce observability risk, but they do not necessarily provide equivalent visibility into the supplier's internal model behavior.

Exceptions should be reviewed when their assumptions change, their validity period expires, incidents reveal control weaknesses, or the system's risk profile increases.

### 53. Retirement, Decommissioning, and Historical Records

System-card governance continues through system retirement and decommissioning. A system that is no longer intended for use may still leave behind active credentials, retained data, external integrations, scheduled jobs, or dependencies that create security and compliance exposure.

The system card or its linked retirement record should document:

- The retirement decision and approving authority.
- The effective retirement date.
- The final production status.
- The disposition of models, application components, and infrastructure.
- Revocation of credentials, tokens, service accounts, and access permissions.
- Removal or disabling of external integrations.
- Data retention, archival, deletion, and legal-hold requirements.
- Treatment of logs, audit records, and evidence.
- Closure or transfer of outstanding risks and exceptions.
- Supplier contract termination or service transition.
- Confirmation that decommissioning activities were completed.

Historical system cards should be retained according to applicable legal, regulatory, contractual, audit, and records-management requirements. Retaining the approved record and its significant revisions supports reconstruction of the system's historical configuration, risk decisions, and governance status.

The organization should distinguish between an inactive system, a retired system, and a system that has been fully decommissioned. These states have different operational implications and should not be used interchangeably.

### 54. Cross-Functional Responsibilities and Accountability

System-card maintenance often crosses organizational boundaries. Engineering may understand the architecture, security may understand threat exposure, privacy teams may understand data-processing obligations, and business owners may understand the intended use and consequences of failure.

A responsibility model should make these contributions explicit.

| Role                                    | Typical responsibility                                                                                |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Business or system owner                | Owns the business purpose, operational accountability, and governance status                          |
| AI or application engineering           | Maintains technical descriptions, component references, and implementation details                    |
| Security architecture                   | Validates trust boundaries, security controls, threat assumptions, and technical safeguards           |
| AI governance or risk function          | Defines documentation requirements, risk classification, review expectations, and governance criteria |
| Privacy or data protection function     | Reviews personal-data processing, privacy risks, and applicable data-protection requirements          |
| Compliance or legal function            | Assesses applicable obligations and relevant contractual or regulatory requirements                   |
| Operations or SRE                       | Provides deployment, availability, monitoring, recovery, and operational evidence                     |
| Procurement or third-party risk         | Maintains supplier information, contractual dependencies, and provider assurance records              |
| Internal audit or independent assurance | Independently evaluates the reliability of documentation and supporting controls where within scope   |

The precise allocation will depend on organizational structure. In smaller organizations, one individual may perform several roles, but accountability for material risk decisions and independent challenge should remain clear.

A responsibility matrix should specify who prepares, validates, approves, maintains, and independently reviews the system card. It should also define escalation paths for disputed risk ratings, incomplete evidence, overdue updates, and proposed exceptions.

### 55. Integrating System Cards with the AI Governance Operating Model

System cards are most effective when integrated with the wider AI governance operating model. They should connect system-level facts to enterprise-level governance decisions without duplicating every detail held in other authoritative records.

Typical integrations include:

- **AI inventory:** Establishes the canonical system identity, ownership, lifecycle state, and classification.
- **AI risk register:** Links system-specific risks to enterprise risk treatment and acceptance decisions.
- **AI control library:** Identifies applicable controls and records implementation status.
- **Model cards:** Connects model-level capabilities and limitations to the complete system implementation.
- **AI impact assessments:** Connects intended use, affected stakeholders, and potential consequences to system design and operational safeguards.
- **Data inventories:** Identifies data sources, processing purposes, sensitivity, and retention requirements.
- **Third-party risk management:** Connects external models, APIs, datasets, and infrastructure to supplier assessments.
- **Change management:** Links technical modifications to documentation updates, testing, and approvals.
- **Incident management:** Connects incidents and lessons learned to changes in risk assumptions and control requirements.
- **Audit and assurance:** Provides traceable evidence for testing, findings, remediation, and governance conclusions.
- **Management review:** Supplies information about material risks, exceptions, overdue actions, and systemic weaknesses.

Each integration should use stable identifiers and defined relationships. A system card should not become a parallel risk register or a substitute for the AI inventory. It should function as a structured system-level view that links to authoritative governance records.

The organization should also establish data ownership and synchronization rules. Where a system name or lifecycle status is maintained in a central inventory, manually maintained copies across multiple documents can diverge. Canonical records, automated references, and validation checks help reduce these inconsistencies.

### 56. Implementation Scenario: Enterprise AI Customer-Support Assistant

Consider an enterprise deploying an AI assistant that retrieves internal knowledge, drafts customer responses, and invokes approved service APIs.

The system card documents the complete system, including the user interface, orchestration layer, model provider, retrieval service, knowledge repositories, identity controls, output filtering, monitoring, and service APIs.

During initial approval, the card records that the assistant may draft responses and retrieve customer information but cannot issue refunds or modify customer account settings without an authorized workflow.

Three months after deployment, the engineering team introduces a new tool that allows the assistant to update customer records. The model itself has not changed, and the feature is described as a minor application enhancement.

Under an effective system-card process, the new tool triggers reassessment because it expands the system's action capabilities and changes its risk profile.

The organization should:

1. Update the system's tool inventory, data flows, permission boundaries, and approved-use description.
2. Assess risks involving unauthorized changes, prompt injection, privilege misuse, and unintended execution.
3. Verify that authentication, authorization, input validation, and transaction controls are enforced at the API boundary.
4. Define which actions require human approval and how approval is verified.
5. Test whether untrusted customer content can cause unauthorized tool execution.
6. Update monitoring, logging, incident response, and recovery arrangements.
7. Reassess residual risk and obtain the required approval before enabling the new capability.
8. Link the revised card to the change request, evaluation evidence, and production release record.

This scenario illustrates why system-card governance must consider changes to the complete system, not just model versions. An unchanged model can participate in a materially different risk environment when permissions, data access, orchestration, or external actions change.

### 57. Implementation Scenario: Third-Party Model Replacement

An organization replaces its existing hosted language model with a different provider's model to reduce cost and improve response latency. The application interface remains unchanged, and the replacement is presented as a provider-level substitution.

The system card identifies the model provider, model reference, data-processing arrangements, system dependencies, and evaluation evidence. The replacement triggers a review because model behavior, provider terms, data handling, availability, and safety characteristics may differ.

The organization should assess whether the replacement changes:

- Input and output behavior.
- Resistance to prompt injection and jailbreak attempts.
- Sensitive-data handling and output leakage.
- Tool-selection behavior and authorization assumptions.
- Accuracy, reliability, and performance.
- Content safety and refusal behavior.
- Data location, retention, and processing arrangements.
- Logging, monitoring, and available assurance evidence.
- Service availability, contractual commitments, and exit options.

Regression testing should cover relevant system-level use cases, not merely benchmark scores or generic model evaluations. If the replacement changes how the model interprets instructions or selects tools, the organization should verify that existing safeguards remain effective.

The system card should reference the new model and provider information, record the assessment results, and identify any new limitations or residual risks. The release should proceed only after required validation and approval activities are complete.

### 58. Implementation Scenario: Inaccurate System Card Discovered During Audit

An internal audit discovers that a production AI assistant's system card lists a retrieval service that was replaced six months earlier. The card also states that all retrieved documents are checked against user permissions, but the implementation evidence does not establish that authorization is enforced in every retrieval path.

The finding raises two distinct concerns: the system description is inaccurate, and a material security-control claim lacks sufficient supporting evidence.

The organization should first establish the actual production architecture and determine whether the authorization gap is a documentation problem, an implementation defect, or both.

The response should include:

- Verifying the current deployed components and data flows.
- Testing access restrictions across relevant retrieval paths.
- Determining whether unauthorized information could have been exposed.
- Correcting the system card and linking it to the authoritative architecture and configuration records.
- Reassessing the system's risk rating and existing approval conditions.
- Raising a security finding if the control is ineffective or insufficiently implemented.
- Defining corrective actions, accountable owners, deadlines, and verification criteria.
- Assessing whether similar inaccuracies exist in other system cards.

The audit finding should not be closed solely because the card has been corrected. Closure depends on the nature of the finding. If the issue is limited to inaccurate documentation, verified correction may be sufficient. If the underlying authorization control is ineffective, the organization must also validate remediation of the technical control.

This scenario demonstrates that documentation accuracy and control effectiveness are related but separate assurance objectives.

### 59. Common Operational Failure Modes

System-card programs can appear mature while failing to provide reliable governance information. Common failure modes include:

- **Point-in-time documentation:** Cards are created for initial approval but are not maintained as systems evolve.
- **Unclear ownership:** No individual or function is accountable for updates and review.
- **Model-centric documentation:** The card describes the model but omits application logic, data pipelines, tools, permissions, and external dependencies.
- **Unverified claims:** Controls are marked as implemented without configuration evidence or operational testing.
- **Weak change integration:** Engineering releases do not trigger system-card reassessment.
- **Excessive manual duplication:** The same facts are copied into multiple records and become inconsistent.
- **Inadequate third-party transparency:** Provider assurances are treated as equivalent to verified end-to-end system security.
- **Missing incident feedback:** Incidents are investigated without updating relevant risk assumptions or control descriptions.
- **Expired exceptions:** Temporary deviations remain open after their justification or approval period has ended.
- **Misleading metrics:** High documentation-completion rates conceal inaccurate or unsupported content.
- **Unclear lifecycle status:** Retired or inactive systems remain represented as active, or operational dependencies remain after decommissioning.
- **Insufficient independent challenge:** The same team prepares, validates, and approves all material claims without appropriate review.

Organizations should address these failure modes through clear ownership, risk-based validation, automated integration where practical, evidence traceability, and meaningful assurance testing.

### 60. Assessing Operational Maturity

An organization can evaluate system-card maturity by examining whether cards are complete, accurate, maintained, integrated, and used in governance decisions.

| Maturity level                 | Characteristics                                                                                                                                                  |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Level 1 — Ad hoc               | Documentation is inconsistent, ownership is unclear, and updates depend on individual initiative                                                                 |
| Level 2 — Defined              | Standard templates, minimum requirements, named owners, and basic review procedures are established                                                              |
| Level 3 — Operationalized      | System cards are integrated with risk management, change control, incident management, and approval workflows                                                    |
| Level 4 — Measured             | Timeliness, accuracy, evidence quality, and control traceability are monitored through defined metrics and risk-based testing                                    |
| Level 5 — Continuously assured | Automated discovery and synchronization are used where feasible, material changes trigger reassessment, and independent assurance informs continuous improvement |

These levels are an illustrative internal maturity model, not a universal regulatory scale. Organizations should adapt the criteria to their size, risk profile, operating model, and applicable obligations.

Maturity assessment should consider both process design and demonstrated operation. A documented procedure is not evidence that the procedure is consistently followed. Higher maturity requires records showing that updates occur when triggered, approvals are traceable, evidence is reliable, and identified weaknesses result in effective remediation.

### 61. Part 3 Core Principle

A system card is an operational governance record whose accuracy must be maintained as the AI system changes, operates, encounters incidents, and moves through its lifecycle. Effective governance connects the card to production monitoring, change management, incident response, third-party oversight, risk treatment, and independent assurance. The organization must be able to demonstrate not only that a system card exists, but also that it reflects the deployed system, that material claims are supported by evidence, and that discrepancies lead to appropriate governance action.

## Part 4 — System Card Assurance, Auditability, Implementation, and Continuous Improvement

### 62. System Card Assurance Objectives

System card assurance determines whether the documented description of an AI system is sufficiently accurate, complete, current, and supported by evidence to serve its intended governance purpose.

The assurance objective extends beyond verifying that a document exists. It examines whether the card provides a reliable representation of the system's intended purpose, technical implementation, operational behavior, risk exposure, and control environment.

A system-card assurance process should evaluate five core dimensions:

- **Completeness:** Required information is documented, including applicable components, dependencies, risks, controls, limitations, and accountable owners.
- **Accuracy:** Documented information agrees with the actual system design, configuration, deployment, and operational arrangements.
- **Currency:** The card reflects relevant changes and has been reviewed within the required period.
- **Traceability:** Material statements can be linked to authoritative records, supporting evidence, approvals, and responsible parties.
- **Governance effectiveness:** The card is used to support risk decisions, change approvals, incident response, and assurance activities rather than functioning solely as a compliance artifact.

These dimensions should be assessed according to system risk. A system used for low-impact internal productivity may require a proportionate level of verification, while a system that processes sensitive information, performs consequential tasks, or executes autonomous actions may require more extensive technical testing and independent review.

Assurance conclusions should identify both the condition of the system card and any limitations that prevent the organization from reaching a reliable conclusion about the underlying system.

### 63. Risk-Based Assurance and Review Depth

Not every system card requires the same level of assurance. Review depth should be determined by the potential consequences of inaccurate documentation, the complexity of the system, the degree of autonomy, and the organization's reliance on the system card for material decisions.

Relevant factors include:

- Potential impact on individuals, customers, employees, and other affected stakeholders.
- Sensitivity and volume of data processed.
- Privilege level and external actions available to the system.
- Complexity of the architecture and number of external dependencies.
- Regulatory classification and applicable obligations.
- History of incidents, control failures, and audit findings.
- Frequency and significance of system changes.
- Degree of transparency provided by model and service providers.
- Criticality to business operations.
- Extent to which the system influences consequential decisions.

A risk-based assurance model may distinguish between three broad review levels.

**Baseline review**

Confirms required fields, ownership, lifecycle status, review dates, key dependencies, and approval records. This level is suitable for systems with relatively limited impact and complexity, provided the risk assessment supports that approach.

**Enhanced review**

Adds technical validation of architecture, data flows, security controls, risk statements, model dependencies, evaluation results, and evidence references. It may include interviews with system owners and targeted sampling of configuration or operational records.

**Independent or specialized assurance**

Uses personnel sufficiently independent of the implementation team to assess high-impact claims. It may include architecture inspection, control testing, adversarial evaluation, access-control testing, or specialist reviews of privacy, safety, security, and regulatory requirements.

These levels are an illustrative operating model rather than a universal classification scheme. Organizations should define explicit selection criteria and ensure that the level of assurance is appropriate to the system's risk and intended use.

### 64. Audit Testing of System Card Accuracy

Audit testing should establish whether material system-card statements are supported by observable evidence.

The auditor or assurance reviewer should select claims that are important to understanding the system's risk and control environment. Examples include statements that a system cannot access restricted records, that human approval is required for consequential actions, or that all external model calls are logged.

Testing methods may include:

- **Document inspection:** Compare the system card with approved architecture documents, technical specifications, policies, and release records.
- **Configuration inspection:** Verify relevant deployment settings, permissions, service connections, model identifiers, and security configurations.
- **Record sampling:** Inspect a sample of change requests, approvals, incidents, access reviews, or evaluation records.
- **Technical testing:** Test whether specified safeguards behave as documented under relevant conditions.
- **Interviews:** Confirm ownership, operating procedures, exception handling, and the responsibilities of relevant teams.
- **Reconciliation:** Compare system-card entries with AI inventory records, cloud inventories, service registries, deployment records, and supplier inventories.
- **Observation:** Observe operational workflows to determine whether documented approvals, restrictions, or monitoring activities are actually performed.

The reviewer should distinguish between evidence that confirms a design decision and evidence that establishes operational effectiveness.

For example, an architecture diagram may show that an authorization service exists. It does not, by itself, establish that every relevant API call passes through that service or that unauthorized access is prevented.

Testing should therefore follow material claims through to the relevant implementation or operational evidence. Where a claim cannot be verified, the reviewer should document the evidence limitation and determine whether additional testing or remediation is necessary.

### 65. System Card Findings and Deficiency Classification

System-card reviews may identify documentation defects, technical control weaknesses, governance failures, or combinations of these conditions. Findings should be classified according to their underlying cause and risk significance.

A useful classification distinguishes the following categories:

| Finding category                 | Description                                                            | Example                                                             |
| -------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Documentation deficiency         | Required information is missing, inaccurate, or unclear                | An external API dependency is not documented                        |
| Evidence deficiency              | A material claim lacks sufficient supporting evidence                  | A control is marked effective without test results                  |
| Technical control deficiency     | An implemented safeguard is absent, misconfigured, or ineffective      | Unauthorized users can retrieve restricted records                  |
| Governance deficiency            | Required accountability, approval, or escalation is missing            | A material capability change was deployed without required approval |
| Lifecycle deficiency             | Review, change, incident, or retirement requirements were not followed | A retired system remains listed as active                           |
| Third-party assurance deficiency | Supplier dependencies or limitations are not adequately assessed       | A provider change is not reflected in the risk assessment           |

Severity should be assigned using defined criteria. Factors may include potential impact, likelihood, exposure, duration, affected systems, regulatory implications, and the effectiveness of existing compensating controls.

A documentation error should not automatically be classified as a high-severity security failure. Conversely, an inaccurate card can conceal a significant control weakness and should not be dismissed as an administrative issue without investigation.

Where a documentation discrepancy reveals that the organization does not know how a material control operates, the uncertainty itself may increase governance risk. The organization should investigate the underlying condition before determining whether the finding is limited to documentation.

### 66. Evidence Traceability and Audit Trails

A reliable system-card program maintains traceability between documented claims and the records that substantiate them.

Each material claim should be linked to evidence appropriate to its nature. Where possible, the evidence reference should identify the authoritative source, relevant version or date, responsible owner, and applicable system or component.

Examples include:

- Architecture claims linked to approved architecture records.
- Model references linked to deployment configuration or provider records.
- Data-processing claims linked to data-flow records and privacy assessments.
- Security-control claims linked to implementation records and test results.
- Risk decisions linked to the applicable risk register entry.
- Approval statements linked to approval records and decision dates.
- Change statements linked to change requests and release records.
- Incident-related updates linked to incident investigations and corrective actions.

The audit trail should preserve the relationship between a system-card revision and the evidence used to approve it.

When a card is updated, the organization should retain enough historical information to determine what changed, why it changed, who authorized the change, and which evidence supported the decision.

Historical traceability is particularly important when investigating incidents, demonstrating compliance, responding to regulatory inquiries, or reconstructing the basis for a past risk acceptance decision.

Access to system-card records and their evidence should also be controlled. Sensitive architecture information, security weaknesses, credentials references, data-flow details, and supplier information may require restricted access. Documentation should not expose secrets or sensitive operational details unnecessarily.

### 67. Version Control and Reproducibility of Governance Decisions

Version control enables an organization to reconstruct the system description and governance position that applied at a particular point in time.

Each approved version should be associated with a defined system identity and an identifiable revision. Depending on the system, the revision may reference application releases, model versions, deployment configurations, prompt or policy versions, retrieval datasets, or other material dependencies.

The organization should preserve:

- The previous approved system-card version.
- The updated version and change summary.
- The effective date of the change.
- The person or function responsible for the update.
- Validation and approval records.
- Links to associated risk assessments and control evidence.
- Any conditions or exceptions attached to the approval.

Version control should distinguish between editorial changes and material governance changes. Correcting a typographical error may not require the same approval as changing a system's intended use, expanding its privileges, or replacing a critical model dependency.

Reproducibility does not necessarily mean that every output from a probabilistic AI system can be recreated exactly. It means that the organization retains sufficient information to understand the relevant configuration, dependencies, controls, and decisions that applied at the time.

For systems using continuously updated external models or changing retrieval content, exact behavioral reproducibility may be limited. Such limitations should be documented, and the organization should preserve the available version identifiers, configuration records, evaluation results, and provider change information.

### 68. System Cards and Regulatory Evidence

System cards can support regulatory compliance by providing structured information about system purpose, architecture, data processing, risks, controls, oversight, and lifecycle management.

However, a system card is not automatically a legally sufficient compliance record. Its relevance depends on the applicable legal requirements, the system's classification, and the evidence required for the specific regulatory obligation.

Depending on the context, a system card may help reviewers locate or validate evidence relating to:

- AI system identification and inventory.
- Intended purpose and reasonably foreseeable misuse.
- Risk-management activities.
- Data governance and processing arrangements.
- Technical documentation.
- Human oversight.
- Accuracy, robustness, and cybersecurity.
- Logging and monitoring.
- Change management and lifecycle controls.
- Supplier and third-party dependencies.
- Incident handling and corrective action.
- Accountability and approval decisions.

Where the EU AI Act or another regulatory regime applies, the organization should map relevant system-card fields to the actual requirements and maintain any additional records required by law.

The mapping should identify the applicable provision or obligation, the system or activity in scope, the evidence required, the authoritative record, the responsible owner, and the review process.

A generic statement that a system card supports regulatory compliance is insufficient. The organization should be able to explain which obligation is supported, how the supporting information is validated, and what other documentation or evidence is required.

### 69. Alignment with Recognized AI Governance and Risk Frameworks

System-card governance can be aligned with recognized frameworks and standards, provided the organization distinguishes the purpose of each framework and avoids claiming conformity solely because a card exists.

Examples include:

- **NIST AI Risk Management Framework (AI RMF):** System cards can support the documentation and communication of system context, risk identification, measurement, management, and governance activities.
- **ISO/IEC 42001:** System cards can contribute to documented information and operational governance within an AI management system, where relevant to the organization's defined scope.
- **ISO/IEC 23894:** System-card information can support AI risk-management activities by documenting system context, dependencies, limitations, and relevant risk treatments.
- **ISO/IEC 27001:** Security-related system-card content can support information-security risk assessment, control implementation, asset context, and operational evidence.
- **NIST Cybersecurity Framework:** Relevant system information can support cybersecurity asset identification, protection, detection, response, and recovery activities.
- **Applicable regulatory requirements:** System-card fields can be mapped to required documentation, oversight, risk management, and accountability obligations.

The organization should maintain an explicit mapping between relevant framework requirements and its system-card governance process.

Such a mapping should distinguish among documentation that directly satisfies a defined requirement, documentation that provides supporting evidence, and documentation that merely helps locate evidence held elsewhere.

Framework alignment is a structured mapping exercise, not proof of compliance or certification. The organization must assess applicable requirements and verify that the underlying activities and controls operate as intended.

### 70. System Card Governance for Multiple Environments

AI systems may operate across development, testing, staging, and production environments. These environments may use different models, datasets, credentials, permissions, safety configurations, and external integrations.

The system-card program should establish whether a single system card with environment-specific sections is appropriate or whether materially different deployments require separate cards linked to a common system identity.

A shared card may be suitable when environments differ only in controlled operational details and the governance implications remain consistent. Separate cards or deployment-specific records may be warranted when environments use different models, process different data, expose different capabilities, or have materially different risk profiles.

Environment-specific documentation should identify:

- The environment and deployment identifier.
- The model and application versions.
- Relevant configuration differences.
- Data sources and data sensitivity.
- Identity and access controls.
- Network exposure and external integrations.
- Logging, monitoring, and retention settings.
- Evaluation and approval status.
- Restrictions on real-world actions.
- Conditions for promotion to another environment.

Development environments may present different risks from production environments, particularly when they use copied production data, broadly accessible test credentials, experimental models, or less restrictive security controls.

The organization should not assume that approval of a production deployment automatically authorizes a materially different test or development configuration. Each environment should be governed according to its actual risk and purpose.

### 71. System Card Governance for Continuous Delivery

Organizations using continuous integration and continuous delivery may release AI application changes frequently. In these environments, purely manual system-card maintenance can become difficult to sustain.

Automation can help detect changes, validate metadata, and identify conditions that require governance review.

Potential automation capabilities include:

- Retrieving deployed component and version information from approved configuration sources.
- Comparing registered dependencies with the actual deployment inventory.
- Validating mandatory fields and identifier formats.
- Detecting missing or expired evidence references.
- Flagging changes to model identifiers, tool permissions, data sources, or external integrations.
- Linking system-card revisions to source-control changes and release records.
- Enforcing approval gates for defined high-risk changes.
- Notifying owners when reviews, exceptions, or approvals become overdue.
- Maintaining revision history and recording validation outcomes.

Automation should be used where reliable source data and clear governance rules exist. It should not replace judgment where changes affect intended use, consequential decisions, residual risk, or the adequacy of human oversight.

For example, a pipeline can detect that a new model identifier has been introduced. It may not be able to determine independently whether the model's behavior changes the system's safety profile or whether the existing risk acceptance remains appropriate.

The organization should therefore combine automated change detection with risk-based review and accountable approval.

### 72. Data Quality Controls for System-Card Registries

Where system cards are managed through a central registry, data quality becomes a governance control in its own right.

Poor-quality registry information can create false assurance, impair audit sampling, and undermine enterprise-level risk reporting.

Data quality rules should address:

- **Uniqueness:** Each system has a stable identifier that prevents accidental duplication.
- **Completeness:** Mandatory fields are populated or carry an explicitly authorized exception.
- **Validity:** Values conform to defined formats, enumerations, and business rules.
- **Consistency:** Related fields agree with one another and with authoritative source records.
- **Referential integrity:** Linked models, controls, risks, components, owners, and evidence records resolve to valid identifiers.
- **Timeliness:** Records are updated within the required period after material changes.
- **Provenance:** The origin of important data is identifiable.
- **Accountability:** Each record has an assigned owner and a defined review responsibility.

Validation should distinguish between syntactic correctness and substantive correctness. A valid model identifier may refer to a model that is no longer deployed, while a populated risk field may contain an unsupported assessment.

Automated checks should therefore be complemented by reconciliation with deployment records, targeted technical validation, and review of material governance claims.

Data-quality exceptions should be visible to the responsible owner and escalated when they prevent the organization from reliably identifying systems or understanding their risk exposure.

### 73. Measuring the Quality of System-Card Evidence

Evidence quality determines how confidently an organization can rely on system-card statements.

A practical evidence assessment should consider relevance, reliability, sufficiency, currency, and traceability.

- **Relevance:** Does the evidence directly support the claim being made?
- **Reliability:** Is the source authoritative and sufficiently independent for the intended conclusion?
- **Sufficiency:** Is there enough evidence to support the conclusion within the required scope?
- **Currency:** Does the evidence reflect the current system and relevant review period?
- **Traceability:** Can the evidence be linked to the correct system, control, configuration, and decision?

Evidence should be evaluated in context. A supplier assurance report may provide useful evidence about a provider's control environment, but it may not establish that the organization's own application permissions are configured correctly.

Likewise, a successful test of one API endpoint may not establish that all interfaces enforce the same authorization requirements.

Where evidence is incomplete, the organization should document the scope limitation and determine whether additional testing is necessary. The resulting assurance conclusion should not exceed what the available evidence supports.

### 74. Management Reporting and Escalation

System-card governance should generate management information that helps accountable leaders understand the state of the AI portfolio and the reliability of the supporting documentation.

Reporting should emphasize material exceptions, risk exposure, trends, and decisions required rather than presenting only document-completion statistics.

Useful reporting dimensions include:

- Coverage of in-scope AI systems.
- Distribution of systems by risk tier and lifecycle state.
- Material discrepancies between documented and deployed configurations.
- Overdue reviews and unapproved material changes.
- Missing or unreliable evidence for important controls.
- Open exceptions and approaching expiration dates.
- Significant changes to model, data, supplier, or tool dependencies.
- Recurring audit findings and unresolved root causes.
- Incidents that reveal weaknesses in documented assumptions.
- Systems requiring renewed approval, restricted operation, or retirement.

Escalation criteria should specify which conditions require notification to the system owner, risk committee, security leadership, compliance function, or other designated authority.

For example, an overdue review may require routine escalation, while an unresolved discrepancy involving unauthorized access to sensitive information may require immediate security escalation and operational containment.

Management reporting should distinguish between a documentation backlog and an underlying control weakness. Both may require action, but their operational consequences and urgency may differ.

### 75. Continuous Improvement of the System-Card Program

A mature system-card program should improve based on audit results, incidents, system changes, user feedback, control testing, and evolving governance requirements.

Continuous improvement should focus on recurring weaknesses and systemic causes rather than treating each documentation error as an isolated problem.

The improvement process should examine:

- Whether templates capture the information needed for actual governance decisions.
- Whether system owners understand their responsibilities.
- Whether review and approval requirements are proportionate to risk.
- Whether material system changes reliably trigger reassessment.
- Whether evidence references remain usable and authoritative.
- Whether registry integrations reduce duplication and inconsistency.
- Whether audit findings recur after corrective actions.
- Whether monitoring and incident lessons are reflected in system documentation.
- Whether third-party limitations are adequately represented.
- Whether governance metrics provide meaningful evidence of effectiveness.

Changes to the program should be documented, approved where required, communicated to affected stakeholders, and assessed for their effect on existing system cards.

Where a recurring problem affects many systems, remediation should address the shared cause. For example, repeated omissions of tool permissions may indicate that the template, inventory integration, or review procedure needs improvement rather than simply requiring individual owners to correct their cards.

The effectiveness of improvement activities should be verified. Closing an action because a template was updated does not establish that the revised template prevents the original issue. Follow-up sampling or control testing may be needed to demonstrate that the change produced the intended result.

### 76. System Card Acceptance and Closure Criteria

A system card should satisfy defined acceptance criteria before it is treated as an approved governance record.

Depending on the organization's operating model and the system's risk, acceptance criteria may include:

- A unique system identifier and clearly defined system boundary.
- A documented intended purpose, scope, and relevant limitations.
- Identified owners and accountable approval authorities.
- Accurate descriptions of material components, data flows, and dependencies.
- Appropriate references to the model and deployment configuration.
- Documented risk and control relationships.
- Identification of relevant security, privacy, safety, and compliance considerations.
- Evidence supporting material claims.
- Completed required validation and approval steps.
- Recorded exceptions and risk decisions.
- Defined review triggers and lifecycle status.
- Traceable revision history.

Acceptance should be based on the applicable requirements, not on a universal expectation that every possible field must be populated for every system.

Where a required condition is not met, the organization should determine whether the deficiency can be remediated, whether a formal exception is permitted, or whether the system should not proceed to the next lifecycle stage.

Closure of a system-card review should record the outcome, material findings, required actions, accountable owners, and any restrictions or conditions that remain in effect.

An approved card provides a governance baseline. It does not eliminate the need for ongoing monitoring, risk reassessment, control testing, or independent assurance.

### 77. Part 4 Core Principle

System-card assurance must establish that the documented AI system is accurate, current, traceable, and supported by evidence appropriate to its risk. Effective governance combines risk-based review, technical validation, version control, regulatory mapping, environment-specific documentation, and independent challenge where warranted. System cards should remain integrated with enterprise risk management and operational controls throughout the system lifecycle, providing a reliable basis for approval, monitoring, audit, incident response, and management decisions without being mistaken for proof of security, compliance, or control effectiveness on their own.
