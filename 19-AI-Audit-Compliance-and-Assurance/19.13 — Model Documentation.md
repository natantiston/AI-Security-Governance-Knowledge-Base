# 19.13 — Model Documentation

## Part 1 — Foundations and Core Principles

### 1. Definition of AI Model Documentation

AI model documentation is the structured collection of technical, operational, governance, security, risk, and lifecycle information that explains how an AI model was developed, evaluated, approved, deployed, maintained, and retired.

It provides an authoritative record of the model's characteristics, intended purpose, design assumptions, data dependencies, limitations, evaluation results, security considerations, and operational requirements. It enables authorized stakeholders to understand what the model does, how it works at an appropriate level of abstraction, under which conditions it can be used, and what controls are necessary to manage its risks.

Model documentation serves multiple organizational functions:

- **Governance:** Demonstrates that model development and use are subject to defined policies, ownership, approval, and oversight.
- **Risk management:** Records model-specific risks, assumptions, limitations, and mitigation measures.
- **Security:** Documents security requirements, dependencies, access restrictions, threat considerations, and protective controls.
- **Compliance:** Provides evidence that applicable regulatory, contractual, and internal documentation requirements have been addressed.
- **Audit and assurance:** Enables independent reviewers to examine the model's development, evaluation, approval, and operational history.
- **Operational management:** Supports deployment, monitoring, troubleshooting, change management, incident investigation, and retirement.
- **Accountability:** Identifies the people, teams, and decision-making authorities responsible for the model and its lifecycle.

Model documentation is not simply a technical report produced at the end of development. It is a controlled information asset that evolves as the model, its operating environment, its intended purpose, and its associated risks change.

For example, a model initially approved to classify internal support tickets may later be adapted to prioritize customer complaints. Although the underlying model may remain unchanged, its intended purpose, affected individuals, business impact, and risk profile may change. Its documentation must reflect the revised use case and any resulting reassessment or approval requirements.

### 2. Purpose and Objectives of Model Documentation

The primary purpose of model documentation is to preserve reliable, reviewable information about an AI model throughout its lifecycle.

Organizations cannot effectively govern a model if they cannot establish which model is in use, why it was selected, how it was evaluated, what limitations were identified, who approved it, and what conditions apply to its continued operation.

A mature documentation process should achieve the following objectives.

**2.1 Establish model identity**

Documentation identifies the model through a unique identifier, name, version, owner, development or acquisition source, and lifecycle status. These attributes prevent confusion between different models, versions, environments, or deployments.

**2.2 Explain intended purpose and boundaries**

Documentation defines the business problem the model is designed to address, its intended users, expected inputs and outputs, operating conditions, and prohibited or unsupported uses.

**2.3 Preserve development and configuration decisions**

Documentation records relevant design decisions, model selection criteria, architecture choices, training approaches, configuration parameters, dependencies, and material assumptions.

**2.4 Demonstrate evaluation and approval**

Documentation preserves test methodologies, evaluation results, acceptance criteria, identified deficiencies, risk assessments, and approval decisions.

**2.5 Enable reproducibility and traceability**

Documentation provides enough information for authorized personnel to identify the model version, relevant data and software dependencies, configuration, and evaluation context associated with a particular result or deployment.

Reproducing an AI result exactly may not always be possible, particularly for nondeterministic systems, externally hosted models, or models whose underlying service changes without full customer visibility. Documentation should state such limitations rather than imply guaranteed reproducibility.

**2.6 Support operational resilience**

Documentation helps operators identify dependencies, recovery procedures, monitoring requirements, escalation paths, rollback conditions, and other measures necessary to maintain controlled operation.

**2.7 Facilitate audit and regulatory examination**

Documentation enables internal audit, external assessors, regulators, and other authorized reviewers to examine whether required governance processes and controls were implemented and whether supporting evidence exists.

The quality of model documentation should therefore be evaluated by its usefulness, accuracy, completeness, traceability, and fitness for the model's risk level—not merely by the number of pages produced.

### 3. Model Documentation Within the AI Governance Framework

Model documentation is a foundational component of an AI governance operating model. It connects technical model development with organizational accountability, risk management, security controls, compliance obligations, and operational oversight.

A governance framework establishes the rules under which AI systems are developed, acquired, deployed, and monitored. Model documentation translates those rules into model-specific records that demonstrate how they have been applied.

For example, an organizational AI policy may require human oversight for consequential decisions. Model documentation should identify the applicable oversight requirement, the roles responsible for review, the decision points requiring human intervention, and the evidence demonstrating that the oversight mechanism has been implemented and evaluated.

A model documentation framework commonly incorporates the following governance elements:

| Governance element      | Documentation contribution                                                            |
| ----------------------- | ------------------------------------------------------------------------------------- |
| AI policy and standards | Records applicable requirements and how they apply to the model                       |
| Model ownership         | Identifies accountable business and technical owners                                  |
| AI risk management      | Records identified risks, assessments, treatments, and residual risks                 |
| Security governance     | Documents security requirements, controls, dependencies, and limitations              |
| Data governance         | Records relevant data sources, provenance, quality considerations, and permitted uses |
| Model validation        | Preserves evaluation methods, results, limitations, and validation conclusions        |
| Change management       | Establishes the model's approved baseline and records material changes                |
| Compliance management   | Maps applicable obligations to documentation and supporting evidence                  |
| Internal audit          | Enables independent testing of governance and control implementation                  |
| Operational monitoring  | Connects documented performance and risk thresholds to monitoring activities          |

The governance framework should define minimum documentation requirements, mandatory approval points, ownership responsibilities, retention rules, access restrictions, and the process for handling missing or inaccurate information.

Documentation requirements should be proportionate to risk. A low-impact internal classification model may require a relatively lightweight documentation package, whereas a model supporting regulated, safety-critical, or high-impact decisions may require substantially more detailed records and formal approval.

Proportionality does not mean that low-risk models should have no documentation. It means that the depth, formality, and assurance requirements should reflect the model's characteristics, intended use, foreseeable consequences, and applicable obligations.

### 4. Distinction Between Model Documentation, Model Cards, and System Cards

Model documentation is the broader collection of information maintained about an AI model. Model cards and system cards are specific documentation artifacts that can form part of that collection.

These concepts are related, but they are not interchangeable.

**Model documentation** may include architecture descriptions, development records, training and evaluation information, configuration baselines, validation reports, security assessments, risk records, change histories, operational requirements, and approval evidence.

**Model cards** are structured summaries designed to communicate essential information about a model, such as its intended use, evaluation results, performance characteristics, limitations, and relevant ethical or risk considerations. Their content and format depend on the applicable methodology or organizational standard.

**System cards** generally describe an AI system in its broader operational context, potentially including the model, surrounding services, interfaces, data flows, safeguards, deployment arrangements, and system-level limitations.

The distinction can be represented as follows:

```
AI Governance and Assurance Records
                |
                +-- Model Documentation Package
                |       |
                |       +-- Model identity and version records
                |       +-- Development and configuration records
                |       +-- Data and dependency documentation
                |       +-- Evaluation and validation evidence
                |       +-- Security and risk assessments
                |       +-- Approval and change records
                |       +-- Operational and lifecycle records
                |
                +-- Model Card
                |       |
                |       +-- Structured model summary
                |       +-- Intended use and limitations
                |       +-- Selected evaluation results
                |
                +-- System Card
                        |
                        +-- System context and architecture
                        +-- Interfaces and operational safeguards
                        +-- System-level risks and limitations
```

This structure is conceptual rather than a mandatory document hierarchy. Organizations may implement the artifacts as separate files, sections of a central repository, or linked records in a model management platform.

The key requirement is that each artifact has a defined purpose and that the information needed for governance, security, operations, and assurance remains accessible and traceable.

A model card should not be assumed to contain every technical detail needed for an audit. Likewise, a system card should not automatically be treated as evidence that every underlying model has been adequately documented.

### 5. Model Documentation Across the AI Lifecycle

Model documentation should be maintained throughout the AI lifecycle rather than created as a one-time deliverable.

The information required at each stage differs. Early development may involve assumptions, proposed architectures, data suitability assessments, and preliminary risk analysis. Later stages require evidence of implementation, evaluation, approval, deployment, and operational performance.

A lifecycle-based approach helps organizations identify when information must be created, reviewed, approved, and updated.

| Lifecycle stage                | Typical documentation requirements                                                              | Governance objective                                             |
| ------------------------------ | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Intake and use-case definition | Business justification, intended purpose, stakeholders, preliminary risk classification         | Establish whether the proposed use is appropriate                |
| Design and planning            | Architecture decisions, requirements, assumptions, design alternatives                          | Establish an approved design baseline                            |
| Data preparation               | Data provenance, collection methods, permitted uses, quality and representativeness assessments | Demonstrate responsible data management                          |
| Development or acquisition     | Model identity, source, development records, configuration, dependencies                        | Establish model lineage and technical accountability             |
| Testing and validation         | Test plans, datasets or dataset references, metrics, results, limitations, defects              | Demonstrate that defined acceptance criteria have been evaluated |
| Risk and security assessment   | Threat analysis, risk register, security controls, residual risks                               | Determine whether identified risks are adequately addressed      |
| Approval                       | Approval records, exceptions, unresolved issues, deployment conditions                          | Establish authorization to proceed                               |
| Deployment                     | Release identifier, environment, configuration, access requirements, rollback plan              | Preserve the approved production baseline                        |
| Monitoring and maintenance     | Performance trends, incidents, drift assessments, control tests, corrective actions             | Maintain continued oversight                                     |
| Material change                | Change request, impact assessment, regression testing, reapproval where required                | Prevent uncontrolled changes                                     |
| Retirement                     | Decommissioning decision, dependency removal, archival and retention records                    | Ensure controlled termination of use                             |

Documentation should be generated as close as practical to the activity it describes. Retrospective reconstruction increases the likelihood of missing information, inaccurate dates, incomplete decision histories, and unsupported assertions.

For example, a team that records evaluation results but fails to retain the corresponding model version, evaluation configuration, and dataset reference may be unable to establish which model was actually tested.

A lifecycle-based process therefore links documentation activities to workflow gates. A model should not automatically advance to the next stage merely because a document exists; the organization should verify that the required information is sufficiently complete, accurate, reviewed, and supported by evidence.

### 6. Core Principles of Effective Model Documentation

Effective model documentation follows a set of principles that help ensure records remain reliable, usable, and suitable for governance and assurance.

**6.1 Accuracy**

Documentation must reflect the actual model, its configuration, its capabilities, and its operating environment. Proposed designs must not be presented as implemented controls, and planned evaluations must not be represented as completed tests.

**6.2 Completeness**

Documentation should cover all information required for the model's risk level, intended use, lifecycle stage, and applicable obligations. Completeness is assessed against defined requirements, not against an arbitrary document length.

**6.3 Traceability**

Material statements should be traceable to their source, such as an approved design decision, test result, configuration record, risk assessment, or change request.

**6.4 Consistency**

Information should be consistent across the model inventory, model documentation, risk register, deployment records, validation reports, and approval systems. Conflicting model identifiers or version numbers create assurance gaps.

**6.5 Timeliness**

Records should be updated when material changes occur. Outdated documentation may be more dangerous than an explicitly incomplete record because users may rely on information that no longer describes the deployed model.

**6.6 Accountability**

Each documentation component should have an assigned owner responsible for its creation, review, maintenance, and correction.

**6.7 Proportionality**

Documentation depth and review rigor should reflect the model's risk, complexity, impact, and applicable legal or contractual requirements.

**6.8 Accessibility**

Authorized users should be able to locate and understand the information they need without unnecessary delays. Accessibility must be balanced with confidentiality, privacy, intellectual property protection, and security restrictions.

**6.9 Integrity**

Documentation should be protected against unauthorized modification, deletion, or substitution. Material changes should be attributable to authorized actors and supported by appropriate records.

**6.10 Verifiability**

Important claims should be supported by evidence where appropriate. Statements such as "the model passed security testing" should identify the relevant test, scope, date, version, results, and approval or disposition.

These principles reinforce one another. A technically accurate report that cannot be linked to the deployed model is not sufficiently traceable. A complete document that has not been updated after a significant model change is not timely. A signed approval that lacks supporting evaluation evidence may demonstrate that a decision was recorded, but it does not independently establish that the model was adequately assessed.

### 7. Model Documentation as a Controlled Information Asset

Model documentation should be managed as an organizational information asset with defined ownership, classification, access controls, retention requirements, and lifecycle management.

This approach is important because documentation may contain sensitive technical information, personal data, proprietary intellectual property, confidential business information, security architecture details, or information that could assist an attacker.

Examples include:

- Model architecture and deployment configuration.
- Training-data descriptions and sensitive dataset references.
- API endpoints, integration details, and service dependencies.
- Security testing findings and known vulnerabilities.
- Prompt templates, model behavior constraints, or sensitive system configuration.
- Evaluation weaknesses that could facilitate targeted manipulation.
- Incident reports containing personal or confidential information.
- Commercially sensitive information about externally supplied models.

Organizations should classify documentation according to its actual content and associated risks. Not every model document requires the same security classification, and classification should not be used to prevent legitimate governance or assurance access without justification.

A practical documentation asset management model includes the following controls:

| Control area         | Expected control                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------- |
| Ownership            | Assign a document owner and, where necessary, a technical subject-matter owner              |
| Classification       | Apply information classification based on confidentiality, sensitivity, and business impact |
| Access management    | Grant access according to role, business need, and least-privilege principles               |
| Version control      | Maintain identifiable versions and an authoritative current record                          |
| Integrity protection | Restrict unauthorized edits and preserve change history                                     |
| Retention            | Define retention periods and legal holds where applicable                                   |
| Backup and recovery  | Protect important records against accidental loss or system failure                         |
| Disposal             | Securely dispose of records when retention obligations expire and disposal is permitted     |
| Review               | Periodically verify accuracy, relevance, ownership, and access rights                       |
| Auditability         | Record material access, modification, approval, and disposition events where appropriate    |

The authoritative repository may be a document management platform, a model registry, a GRC system, a version-controlled repository, or an integrated combination of these technologies.

The technology is less important than the control outcome: the organization must know which record is authoritative, who may change it, which version was approved, and how previous versions and decisions can be retrieved when required.

For instance, keeping an approved model evaluation report in a shared folder where anyone can overwrite the file creates a weakness in integrity and accountability. A controlled repository with version history, role-based permissions, and recorded approvals provides stronger assurance.

### 8. Model Documentation Requirements and Regulatory Context

Model documentation requirements arise from multiple sources, including legislation, regulations, technical standards, contractual commitments, organizational policies, and risk management frameworks.

The exact requirements depend on the model's intended purpose, deployment context, jurisdiction, organizational role, sector, and applicable legal classification. There is no single universal documentation checklist that is sufficient for every AI model.

A model documentation framework should distinguish between mandatory obligations, adopted standards, contractual requirements, and internal good practices.

**8.1 Regulatory requirements**

Applicable AI legislation may require specific technical documentation, record-keeping, transparency, risk management, human oversight, or post-deployment monitoring information for certain categories of AI systems.

For example, the EU Artificial Intelligence Act establishes specific technical documentation and record-keeping obligations for relevant categories of AI systems, including high-risk AI systems. The precise obligations depend on the applicable provisions, the organization's role, the system's classification, and the relevant implementation timeline.

An organization should not assume that every model automatically falls into the same regulatory category or that a generic internal model document satisfies a statutory requirement.

**8.2 Management system standards**

Standards such as ISO/IEC 42001 can support the establishment of documented information and management-system processes for AI governance. Their application should be mapped to the organization's chosen management-system scope and relevant requirements.

**8.3 Risk management frameworks**

Frameworks such as the NIST AI Risk Management Framework can inform the documentation of context, risks, evaluation, measurement, management activities, and governance decisions. Organizations should distinguish framework guidance from legal obligations.

**8.4 Security and privacy requirements**

Information security, privacy, data protection, and sector-specific requirements may influence how model documentation is created, protected, shared, and retained. Documentation practices must not introduce unnecessary personal-data collection or expose sensitive information.

**8.5 Contractual and supplier requirements**

Organizations may need documentation from model providers, cloud platforms, data suppliers, or external development partners. Contracts should establish which technical information will be provided, how often it will be updated, what evidence may be requested, and how material changes will be communicated.

A regulatory and standards mapping should connect each applicable requirement to the relevant documentation artifact and supporting evidence.

| Requirement source                | Documentation question                                                  | Typical governance evidence                                    |
| --------------------------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------- |
| Applicable legislation            | What information must be documented or retained?                        | Obligation assessment and compliance mapping                   |
| AI management system              | What documented processes and records are required?                     | Controlled procedures, records, and review evidence            |
| Risk management framework         | How are risks identified, assessed, treated, and monitored?             | Risk assessments, treatment decisions, and monitoring records  |
| Information security requirements | How are model-related assets and records protected?                     | Security requirements, access records, and control assessments |
| Privacy obligations               | What personal data is involved, and how is it governed?                 | Data-flow documentation and applicable privacy assessments     |
| Supplier contracts                | What information must external providers supply?                        | Contract clauses, supplier documentation, and review records   |
| Internal policy                   | What minimum documentation and approvals does the organization require? | Policy mapping, checklists, and approval records               |

The compliance team should validate the applicable requirements rather than relying solely on a generic template. A template is a useful starting point, but it cannot independently determine legal applicability.

### 9. Model Documentation Versus Supporting Evidence

Model documentation and audit evidence are closely related, but they serve different purposes.

Model documentation describes the model, its development, its characteristics, its risks, its controls, and its lifecycle decisions. Supporting evidence demonstrates that particular activities occurred or that stated controls and outcomes can be substantiated.

For example, a model document may state that robustness testing was completed. Supporting evidence could include the approved test plan, test execution logs, test environment details, model version identifiers, recorded results, defect tickets, and the reviewer's conclusion.

The distinction matters because an assertion in a document is not necessarily proof that the asserted activity was performed correctly.

A useful evidence structure is:

```
Documented Claim
      |
      v
Defined Requirement or Acceptance Criterion
      |
      v
Supporting Evidence
      |
      +-- Test plan and methodology
      +-- Model and configuration identifiers
      +-- Execution records and results
      +-- Defect and exception records
      +-- Review and approval
      |
      v
Evaluation of Sufficiency
      |
      v
Recorded Conclusion and Follow-up
```

Supporting evidence should be sufficient, relevant, reliable, and attributable to the activity being evaluated.

For a high-impact model, evidence may need to be preserved in a controlled repository with restricted modification rights and reliable timestamps. For a low-risk model, a simpler evidence trail may be proportionate, provided that it satisfies the applicable requirements.

The organization should also distinguish between original evidence and derived summaries. A dashboard showing evaluation results may be useful for management review, but the underlying test records may still be necessary to verify how the results were produced.

Where evidence cannot be obtained—for example, because a third-party provider does not disclose certain internal development details—the limitation should be explicitly documented, along with its governance implications, compensating measures, and any resulting approval restrictions.

### 10. Model Documentation Governance Roles and Responsibilities

Model documentation requires clear accountability across business, technical, risk, security, compliance, and audit functions.

A frequent governance weakness occurs when a team assumes that another department owns the documentation. Technical teams may consider documentation a compliance responsibility, while compliance teams may lack the technical information needed to maintain accurate records.

The organization should therefore assign responsibilities explicitly.

| Role                                       | Primary documentation responsibility                                                                   |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| Business or use-case owner                 | Defines business purpose, intended use, expected outcomes, and operational constraints                 |
| Model owner                                | Accountable for the model's lifecycle records, completeness, and continued suitability                 |
| Model developer or engineering team        | Produces development, architecture, configuration, dependency, and evaluation records                  |
| Data owner or data steward                 | Documents relevant data provenance, quality, permitted uses, and governance constraints                |
| Model validator                            | Records independent evaluation methodology, findings, limitations, and validation conclusions          |
| AI risk manager                            | Ensures relevant risks, treatments, residual risks, and acceptance decisions are documented            |
| Information security team                  | Defines security documentation requirements and reviews relevant security controls and findings        |
| Privacy or data protection function        | Reviews applicable personal-data processing and related documentation obligations                      |
| Legal and compliance teams                 | Interpret applicable obligations and maintain the compliance mapping                                   |
| Change advisory or approval authority      | Reviews material changes and ensures required approvals are recorded                                   |
| Internal audit                             | Independently evaluates whether documentation controls are suitably designed and operating effectively |
| Records or information management function | Establishes retention, classification, access, archival, and disposal requirements                     |

These roles may be combined in smaller organizations, but accountability should remain clear. Combining responsibilities does not remove the need for appropriate independent review where required by policy, regulation, or risk.

Internal audit should generally assess the adequacy and effectiveness of documentation controls independently rather than become the operational owner responsible for creating or approving the records it later audits.

A responsibility assignment matrix can make the governance model operational. For each required artifact, the organization should identify who prepares it, who reviews it, who approves it, and who is responsible for maintaining it after approval.

### 11. The Model Documentation Lifecycle

A controlled model documentation lifecycle defines how records are created, reviewed, approved, updated, retained, and retired.

The lifecycle should align with the model lifecycle but should not be limited to it. Some documentation must be retained after a model is decommissioned because it supports regulatory accountability, incident investigation, contractual obligations, or future audit activities.

The main lifecycle activities are as follows.

**11.1 Initiation**

Create the documentation record when a model or AI use case enters the organization's governance process. Assign a unique identifier, owner, preliminary classification, and intended purpose.

**11.2 Collection**

Gather information from development teams, data owners, suppliers, validation teams, security assessments, and operational systems. Identify required information that is unavailable or not applicable.

**11.3 Review**

Check the accuracy, completeness, consistency, and evidence supporting the information. Review should be performed by people with appropriate competence and authority.

**11.4 Approval**

Record the relevant approval decision, approving authority, date, applicable model version, unresolved issues, and any conditions attached to approval.

**11.5 Publication and controlled access**

Make the approved documentation available to authorized stakeholders through a defined authoritative repository. Clearly distinguish approved records from working drafts.

**11.6 Maintenance**

Update records following material changes to the model, data, configuration, intended purpose, provider, deployment environment, risk profile, or applicable requirements.

**11.7 Periodic review**

Conduct risk-based reviews to verify that documentation remains accurate, current, and aligned with the deployed model and organizational requirements.

**11.8 Archival and retirement**

Preserve records according to retention rules and applicable legal or contractual obligations. Record retirement decisions and ensure that documentation remains retrievable for the required period.

A simplified workflow is:

```
Model or Use Case Registered
              |
              v
Documentation Requirements Identified
              |
              v
Information Collected and Linked to Evidence
              |
              v
Completeness and Accuracy Review
              |
              v
Risk, Security, and Compliance Review
              |
              v
Authorized Approval
              |
              v
Controlled Publication
              |
              v
Monitoring and Change Management
              |
              v
Periodic Review or Material-Change Review
              |
              v
Archival and Controlled Retirement
```

The workflow should include exception handling. If mandatory information is missing, the responsible authority should determine whether the gap can be remediated before approval, whether a time-limited exception is permitted, or whether deployment must be restricted.

An exception should identify the missing information, the reason for the gap, the associated risk, the compensating controls, the accountable risk owner, the approval authority, and the remediation deadline.

### 12. Minimum Model Documentation Baseline

Organizations should define a minimum documentation baseline for each model, then expand it according to risk, complexity, intended use, and applicable requirements.

A minimum baseline is not a universal legal checklist. It is an internal governance mechanism designed to prevent important information from being omitted.

A practical baseline may include the following categories.

| Documentation category     | Minimum information to consider                                                                             |
| -------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Model identification       | Unique ID, model name, version, status, owner, provider, and relevant registry reference                    |
| Intended purpose           | Business objective, intended users, use cases, assumptions, restrictions, and prohibited uses               |
| Technical description      | Model type, relevant architecture, interfaces, major components, and dependencies                           |
| Data information           | Relevant data sources, provenance, permitted use, quality limitations, and data dependencies                |
| Development or acquisition | Development approach, supplier information, relevant design decisions, and configuration baseline           |
| Evaluation and validation  | Evaluation scope, methodology, metrics, results, acceptance criteria, and known limitations                 |
| Risk assessment            | Identified risks, risk ratings, treatments, residual risks, and risk acceptance decisions                   |
| Security and privacy       | Applicable security controls, relevant privacy considerations, known weaknesses, and restrictions           |
| Human oversight            | Required review or intervention points, responsible roles, and escalation conditions                        |
| Approval                   | Approval records, dates, decision authority, conditions, exceptions, and unresolved issues                  |
| Deployment                 | Environment, deployed version, configuration reference, operational dependencies, and rollback arrangements |
| Monitoring and maintenance | Monitoring requirements, performance thresholds, review frequency, incident procedures, and change triggers |
| Change history             | Version history, material changes, impact assessments, test results, and reapproval records                 |
| Retention and access       | Repository location, classification, access controls, retention rules, and archival requirements            |

The baseline should be adapted to the organization's operating model. For example, an organization using a third-party foundation model may be unable to obtain full training-data details or internal architecture documentation. It should record what is known, identify provider limitations, preserve available contractual and technical evidence, and assess whether the information gap creates unacceptable risk.

Similarly, a model that is never retrained but is used in a changing operational environment may still require documentation updates when its integrations, configuration, intended purpose, or surrounding controls change.

A model documentation baseline should be implemented as a controlled set of requirements, with each requirement mapped to an artifact, owner, review method, and acceptance criterion.

### 13. Common Model Documentation Deficiencies

Documentation deficiencies can undermine AI governance even when the model itself appears to operate correctly.

The most common weaknesses involve missing information, stale records, unsupported claims, inconsistent identifiers, unclear ownership, and insufficient links between documentation and the actual deployed model.

**13.1 Incomplete technical information**

The documentation describes the model's business purpose but omits material details about its version, configuration, interfaces, or dependencies.

**13.2 Unclear intended use**

The document states a broad objective without defining prohibited uses, operational boundaries, or the conditions under which the model has been evaluated.

**13.3 Unsupported evaluation claims**

The documentation states that the model is accurate, secure, fair, or robust without identifying the relevant tests, acceptance criteria, evidence, and limitations.

**13.4 Stale documentation**

The production model has changed, but the documentation still describes an earlier version or configuration.

**13.5 Inconsistent records**

The model registry, risk register, validation report, and deployment record use different identifiers or version numbers without a clear mapping.

**13.6 Missing accountability**

No individual or function is explicitly responsible for maintaining the documentation.

**13.7 Unrecorded exceptions**

Known limitations or unresolved findings are discussed informally but are not included in the controlled record or linked to an approved risk decision.

**13.8 Excessive reliance on supplier claims**

The organization copies vendor statements into internal documentation without evaluating their relevance, scope, evidence, or applicability to its own deployment.

**13.9 Poor evidence preservation**

Reports refer to test results that can no longer be located, or the evidence does not identify the model version that was evaluated.

**13.10 Inadequate access and integrity controls**

Documentation can be modified without authorization, or sensitive technical information is broadly accessible without a justified business need.

**13.11 Overly generic templates**

Templates are completed with boilerplate statements that do not describe the specific model, its actual controls, or its real limitations.

**13.12 Failure to address unavailable information**

The documentation silently omits important information that the organization could not obtain from a provider or supplier.

These deficiencies should be evaluated according to their consequences. A missing administrative field may be a minor issue for a low-impact model, whereas the absence of reliable version identification or validation evidence may prevent an organization from demonstrating that a high-impact model was appropriately assessed.

A mature governance process defines severity criteria, remediation requirements, escalation paths, and approval restrictions for significant documentation gaps.

### 14. Model Documentation Quality Assurance

Model documentation quality assurance is the process of verifying that records meet defined requirements before and after approval.

It differs from model performance testing. Performance testing evaluates the model's behavior; documentation quality assurance evaluates whether the information needed to understand, govern, operate, and assess the model is sufficiently accurate, complete, current, and traceable.

A quality assurance process should evaluate several dimensions.

| Quality dimension    | Example verification question                                                            |
| -------------------- | ---------------------------------------------------------------------------------------- |
| Completeness         | Are all required sections and supporting artifacts present?                              |
| Accuracy             | Do the records describe the actual model and its approved configuration?                 |
| Currency             | Does the documentation reflect the latest approved model version and material changes?   |
| Consistency          | Are identifiers and key facts consistent across related systems?                         |
| Traceability         | Can material claims be linked to supporting evidence?                                    |
| Clarity              | Can the intended audience understand the information and its limitations?                |
| Ownership            | Are document owners and reviewers identified?                                            |
| Approval             | Are required reviews and decisions recorded by authorized personnel?                     |
| Security             | Are classification, access, integrity, and retention controls appropriate?               |
| Regulatory alignment | Have applicable documentation and record-keeping requirements been mapped and addressed? |

Quality assurance may use automated checks, manual reviews, or a combination of both.

Automated checks can identify missing fields, invalid identifiers, expired review dates, broken evidence links, and inconsistent version references. Manual review remains important for assessing the quality of explanations, the adequacy of risk descriptions, the validity of conclusions, and the relevance of supporting evidence.

For example, an automated rule may verify that a validation report exists and contains a model identifier. A competent reviewer must still determine whether the report evaluates the correct use case, uses appropriate methods, addresses material risks, and supports the stated approval decision.

Quality assurance findings should be recorded and tracked through remediation. Where documentation does not meet mandatory requirements, the organization should apply its established exception, escalation, and approval procedures rather than silently treating the missing information as acceptable.

### 15. Practical Example — Documenting an AI Customer Support Classification Model

Consider an organization that deploys an AI model to classify customer support messages into operational categories and recommend routing destinations.

The model helps service teams prioritize requests and direct them to the appropriate department. It does not independently resolve customer complaints, but its classifications can influence response times and the handling of sensitive cases.

The organization creates a model documentation package covering the following areas.

**Model identity and ownership**

The package records the model identifier, version, business owner, technical owner, provider, lifecycle status, and deployment environment.

**Intended purpose and boundaries**

The model is approved to classify incoming support messages into defined categories. Its documentation specifies that the output is a routing recommendation and that certain sensitive or high-impact cases require human review.

**Data information**

The documentation identifies the relevant input sources, permitted processing purposes, data quality considerations, and applicable restrictions on personal or confidential information.

**Technical configuration**

The package records the model version, relevant configuration, interface dependencies, deployment settings, and the relationship between the approved configuration and the production deployment.

**Evaluation and validation**

The validation record describes the test methodology, representative test scenarios, classification metrics, error patterns, acceptance criteria, and known limitations. It also records how the organization evaluates misclassification risks for sensitive complaint categories.

**Security and risk management**

The package identifies relevant risks, such as unauthorized access to customer messages, manipulation of input content, inappropriate disclosure of sensitive information, and misrouting of important requests. It links these risks to the applicable controls and residual-risk decisions.

**Human oversight and operations**

The documentation defines which cases require manual review, who is responsible for escalation, how operational failures are reported, and what conditions trigger investigation or suspension.

**Approval and change history**

The package records the applicable approval decision, the model version approved, outstanding conditions, subsequent changes, regression test results, and any required reapproval.

**Monitoring and maintenance**

The organization establishes monitoring for classification quality, unusual error patterns, operational incidents, and relevant changes in incoming message characteristics. Material findings are linked to the model's risk and change records.

This example demonstrates why model documentation must connect technical information with governance decisions. A list of model parameters alone would not explain how the organization controls misclassification risks, assigns accountability, or determines whether the model remains suitable for its intended purpose.

It also illustrates why the documentation must be specific to the actual deployment. A general vendor description cannot replace evidence that the organization's selected configuration and operational controls have been assessed.

### 16. Model Documentation Maturity

Organizations can assess model documentation maturity to understand whether their processes are informal, repeatable, controlled, or continuously improved.

A maturity model provides a practical way to prioritize improvements and communicate documentation governance capabilities to management.

The following five-level model is an illustrative internal assessment framework, not a prescribed maturity scale from a particular standard.

| Level                | Maturity state                                        | Characteristics                                                                                               |
| -------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Level 1 — Ad hoc     | Documentation is inconsistent and reactive            | Records are created when requested; ownership and templates are unclear                                       |
| Level 2 — Repeatable | Basic documentation practices exist                   | Common templates and informal review processes are used by teams                                              |
| Level 3 — Defined    | Requirements and responsibilities are standardized    | Policies, templates, ownership, approval gates, and retention rules are formally established                  |
| Level 4 — Managed    | Compliance and quality are measured                   | Completeness, currency, evidence traceability, exceptions, and remediation are monitored                      |
| Level 5 — Optimized  | Documentation is integrated and continuously improved | Lifecycle workflows, registries, automated validation, change triggers, and assurance feedback are integrated |

A Level 1 organization may have technically capable development teams but still struggle to answer basic governance questions because records are scattered across personal folders and collaboration tools.

A Level 3 organization should have defined documentation requirements, clear accountability, controlled repositories, and consistent review practices.

A Level 4 organization should additionally be able to demonstrate measurable performance, such as the percentage of models with current documentation, the number of overdue reviews, the proportion of required evidence links that remain valid, and the time required to remediate significant gaps.

A Level 5 organization may integrate documentation updates with model registry changes, release pipelines, validation workflows, and GRC systems. Automation should support accountability rather than replace meaningful technical and governance review.

Maturity assessments should distinguish between the existence of a process and its effectiveness. A policy may be formally approved while teams routinely fail to follow it. Assessment should therefore combine document review, interviews, sampled record inspection, and testing of relevant workflows.

### 17. Key Performance Indicators for Model Documentation

Model documentation KPIs help management determine whether the documentation process is complete, current, efficient, and suitable for assurance activities.

Metrics should measure meaningful control outcomes rather than reward document volume or superficial completion.

Useful indicators include the following.

**17.1 Documentation completeness rate**

The percentage of in-scope models whose required documentation elements satisfy the organization's defined completeness criteria.

[\
\text{Completeness Rate} =\
\frac{\text{Models Meeting Documentation Criteria}}\
{\text{Models in Scope}} \times 100\
]

**17.2 Documentation currency rate**

The percentage of models whose documentation has been reviewed within the applicable review period and reflects the current approved model state.

**17.3 Evidence traceability rate**

The percentage of sampled material claims or control assertions that can be linked to appropriate supporting evidence.

**17.4 Overdue review rate**

The proportion of required documentation reviews that have passed their due dates without completion or an authorized exception.

**17.5 Documentation remediation time**

The average or median time taken to correct identified documentation deficiencies, reported by severity where appropriate.

**17.6 Material-change update compliance**

The percentage of sampled material model changes for which required documentation was updated and reviewed within the defined timeframe.

**17.7 Approval completeness**

The percentage of models requiring formal approval for which the applicable decision, authority, date, conditions, and model version are properly recorded.

**17.8 Significant documentation gap rate**

The proportion of models with one or more unresolved documentation gaps that exceed the organization's defined significance threshold.

An example dashboard could be structured as follows:

| KPI                        | Measurement objective                                   | Suggested management response                   |
| -------------------------- | ------------------------------------------------------- | ----------------------------------------------- |
| Completeness rate          | Identify missing required information                   | Prioritize remediation by risk                  |
| Currency rate              | Identify outdated records                               | Trigger owner reviews and change-linked updates |
| Evidence traceability rate | Assess the substantiation of material claims            | Improve evidence linking and retention          |
| Overdue review rate        | Identify governance review delays                       | Escalate overdue high-risk model reviews        |
| Remediation time           | Evaluate the effectiveness of corrective action         | Address recurring bottlenecks                   |
| Change update compliance   | Verify documentation maintenance after material changes | Strengthen change-management gates              |
| Approval completeness      | Verify documented authorization                         | Investigate missing or invalid approvals        |
| Significant gap rate       | Measure unresolved material deficiencies                | Apply risk-based restrictions or escalation     |

KPIs should be interpreted in context. A high completeness rate does not necessarily mean that the documents are accurate or that the model is safe. A low remediation time is not necessarily positive if teams are closing findings without adequately correcting the underlying issue.

Metrics should therefore be complemented by qualitative review, risk-based sampling, and independent assurance where appropriate.

### 18. Integration of Model Documentation With GRC Systems

Model documentation becomes more effective when it is integrated with the organization's governance, risk, and compliance processes.

Without integration, teams may maintain separate model inventories, risk registers, validation records, security assessments, and compliance trackers that contain inconsistent information.

Integration creates relationships between these records and supports a coherent view of model risk, control implementation, approval status, and unresolved deficiencies.

Common integration points include:

- **AI inventory:** Provides the authoritative reference for model identity, ownership, purpose, and lifecycle status.
- **Risk register:** Links identified risks, risk ratings, treatment plans, residual risks, and acceptance decisions to the relevant model.
- **Control library:** Connects documentation requirements to applicable governance, security, privacy, and compliance controls.
- **Issue and remediation management:** Tracks documentation deficiencies, assigned owners, deadlines, escalation, and closure evidence.
- **Change management:** Connects model updates to impact assessments, testing, documentation revisions, and approvals.
- **Supplier risk management:** Records provider responsibilities, information limitations, contractual commitments, and supplier assurance evidence.
- **Incident management:** Links relevant incidents to affected model versions, known limitations, investigation records, and corrective actions.
- **Internal audit:** Enables auditors to identify in-scope models, select samples, retrieve documentation, and verify the operation of documentation controls.
- **Records management:** Enforces retention, archival, access, and disposition requirements.

A simplified GRC relationship model is:

```
AI Inventory
     |
     +----> Model Documentation
     |            |
     |            +----> Technical and Evaluation Evidence
     |            +----> Approval and Change Records
     |
     +----> AI Risk Register
     |            |
     |            +----> Risk Treatment
     |            +----> Residual Risk Acceptance
     |
     +----> Control Library
     |            |
     |            +----> Control Implementation Evidence
     |            +----> Testing and Assurance Results
     |
     +----> Issue and Remediation Management
                  |
                  +----> Corrective Actions
                  +----> Closure Evidence
```

Integration should preserve clear record ownership. A risk register should not become an uncontrolled duplicate of the model documentation, and a model repository should not be assumed to replace the organization's formal risk acceptance or compliance approval process.

The objective is to establish reliable relationships between authoritative records, minimize conflicting information, and make it possible to trace a governance requirement through implementation, evidence, review, and decision-making.

### 19. Documentation of Third-Party and Externally Hosted Models

Organizations frequently acquire models from external providers rather than developing them entirely in-house. Such arrangements create specific documentation challenges because the deploying organization may not have access to the provider's internal development records, training data, model architecture, or detailed evaluation results.

The organization should distinguish between information it controls directly, information supplied by the provider, information that can be independently verified, and information that remains unavailable.

**19.1 Provider documentation**

Collect relevant technical descriptions, usage restrictions, evaluation summaries, known limitations, security information, versioning details, and other documentation available under the provider's terms and applicable requirements.

**19.2 Deployment-specific documentation**

Record how the organization uses the model, including its configuration, interfaces, input and output handling, integration architecture, access controls, intended purpose, and operational safeguards.

**19.3 Information gaps**

Identify material information that the provider does not disclose. Explain why it matters, whether the gap affects risk assessment or compliance, and what alternative evidence or controls are available.

**19.4 Contractual accountability**

Where appropriate, establish contractual expectations for documentation availability, version-change notifications, incident cooperation, security information, audit rights, and retention or deletion obligations.

**19.5 Change transparency**

Record changes communicated by the provider and assess whether they affect the organization's approved use, evaluation assumptions, security posture, or risk profile.

**19.6 Independent assurance**

Evaluate whether supplier certifications, assessment reports, test summaries, or other assurances are relevant to the actual service and deployment. Such evidence should not automatically be treated as proof that the organization's specific implementation is compliant.

For example, an organization using an externally hosted language model may receive documentation about the service's general capabilities and safety limitations but no access to its full training dataset or internal model weights. Its documentation should accurately record this boundary, the provider's commitments, the organization's own integration controls, and the residual risks arising from limited transparency.

The organization should not invent unavailable technical details or represent assumptions as verified facts. It should assess whether the available information is sufficient for the intended use and whether additional safeguards, contractual protections, or deployment restrictions are necessary.

### 20. Establishing an Effective Model Documentation Program

An effective model documentation program combines policy, standardized requirements, assigned accountability, controlled repositories, lifecycle integration, quality assurance, and continuous improvement.

The objective is not to create the largest possible collection of documents. It is to ensure that the organization can establish what each model is, how it is used, what risks and limitations are known, which controls apply, who authorized its use, and what evidence supports those decisions.

A practical implementation sequence is as follows.

**Step 1 — Define the scope**

Determine which models and AI-enabled components fall within the documentation program. Establish how the organization treats internally developed models, third-party models, externally hosted services, embedded models, and material model updates.

**Step 2 — Map applicable requirements**

Identify relevant legal, regulatory, contractual, standards-based, and internal requirements. Distinguish mandatory obligations from voluntary practices and internal enhancements.

**Step 3 — Establish documentation standards**

Define the minimum documentation baseline, required artifacts, quality criteria, versioning rules, retention periods, and acceptable evidence sources.

**Step 4 — Assign ownership**

Identify the model owner and the people responsible for preparing, reviewing, approving, and maintaining each required artifact.

**Step 5 — Implement a controlled repository**

Establish authoritative storage, appropriate access controls, version history, integrity protection, retention mechanisms, and reliable retrieval.

**Step 6 — Integrate documentation into lifecycle workflows**

Make documentation requirements part of model intake, development, acquisition, validation, deployment, change management, monitoring, and retirement.

**Step 7 — Apply quality assurance**

Verify completeness, accuracy, consistency, evidence traceability, and approval status before relevant governance gates.

**Step 8 — Manage deficiencies**

Record missing information, assign remediation owners, establish deadlines, assess risk, and escalate material gaps through defined governance channels.

**Step 9 — Measure effectiveness**

Track documentation quality and process performance through risk-based KPIs, management reporting, sampled reviews, and independent assurance.

**Step 10 — Improve continuously**

Use audit findings, incidents, regulatory developments, operational feedback, and changes in AI technology to refine documentation requirements and control effectiveness.

The program should be supported by clear management sponsorship and a defined operating model. Documentation requirements that exist only in policy, without integration into actual engineering and governance workflows, are unlikely to remain consistently effective.

Ultimately, model documentation provides the information foundation for accountable AI governance. It enables organizations to connect technical implementation with risk decisions, operational controls, compliance obligations, and independent assurance while preserving an accurate record of how models are developed, approved, deployed, changed, and retired.

## Part 2 — Documentation Architecture, Technical Content, and Traceability

### 21. Model Documentation Architecture and Information Structure

A model documentation architecture defines how information about an AI model is organized, related, stored, maintained, and retrieved throughout its lifecycle. It establishes a consistent structure so that technical teams, model owners, risk managers, security professionals, compliance officers, and auditors can locate the information required for their respective responsibilities.

Without a defined architecture, organizations often accumulate disconnected documents, spreadsheets, presentations, test reports, and approval records. These artifacts may contain valuable information, but their relationships to the model, its version, its deployment, and its governance decisions can be difficult to establish.

A structured architecture should organize information into logical documentation domains while preserving relationships between them.

A practical architecture includes the following domains:

| Documentation domain            | Principal content                                                           | Primary purpose                                |
| ------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------- |
| Identification and ownership    | Model ID, name, version, provider, owner, lifecycle status                  | Establish model identity and accountability    |
| Business and intended use       | Business objective, users, context, limitations, prohibited uses            | Define the authorized application              |
| Technical architecture          | Model type, components, interfaces, dependencies, configuration             | Explain the technical implementation           |
| Data and provenance             | Data sources, lineage, quality, permitted uses, transformations             | Establish data-related traceability            |
| Development and acquisition     | Design decisions, development approach, supplier information                | Preserve relevant development history          |
| Evaluation and validation       | Test plans, metrics, results, acceptance criteria, limitations              | Demonstrate evaluation activities              |
| Risk and security               | Risk assessments, threats, controls, residual risks                         | Support risk treatment and security governance |
| Deployment and operations       | Environment, release baseline, monitoring, recovery, operational procedures | Support controlled operation                   |
| Governance and approval         | Review records, approvals, exceptions, risk acceptance                      | Demonstrate authorization and accountability   |
| Change and lifecycle management | Change history, impact assessments, revalidation, retirement                | Maintain documentation over time               |

These domains do not necessarily require separate files. They may be implemented as sections within a controlled document, linked records in a model registry, or structured entries in a centralized AI governance platform.

The architecture should distinguish between the **documentation record**, which organizes information about the model, and the **supporting artifacts**, which substantiate specific claims or decisions.

For example, the model record may contain the approved validation conclusion and a link to the validation report. The validation report may, in turn, reference test execution logs, evaluation datasets, configuration files, and defect records.

This separation supports maintainability and reduces unnecessary duplication. If the validation report is updated, the model record can reference the authoritative version rather than maintaining a separate copy that may become inconsistent.

An effective architecture should answer five fundamental questions:

1. Which model and version does this information describe?
2. What purpose and operating conditions does the model support?
3. What evidence supports its documented characteristics and evaluation results?
4. Which governance decisions and controls apply?
5. How can the information be retrieved, verified, and updated?

The answers should remain clear even when documentation is distributed across multiple systems or supplied by external providers.

### 22. Model Identity, Metadata, and Version Identification

Model identity and metadata provide the foundation for reliable documentation. If an organization cannot identify the exact model and version associated with a document, test result, approval, or production event, it may be unable to demonstrate that the correct model was evaluated or authorized.

A model name alone is insufficient because the same name may refer to multiple versions, configurations, deployments, or provider offerings.

A robust identification scheme should distinguish between the model itself, its version, its configured instance, and its deployment.

**22.1 Model identifier**

A unique identifier links the model to the organizational AI inventory and its related governance records. The identifier should remain stable even when the model is updated, unless the organization's identity policy explicitly requires a new identity for a materially different model.

**22.2 Model version**

The version identifies a particular release or state of the model. It should correspond to the versioning scheme used by the development team or provider.

**22.3 Configuration identifier**

A configuration identifier distinguishes operational settings that may materially affect model behavior. Examples include selected parameters, system prompts, retrieval settings, safety policies, inference options, or feature-processing configurations, depending on the model type.

**22.4 Deployment identifier**

A deployment identifier identifies where and how a model is operated, such as a production endpoint, cloud environment, business application, or regional instance.

**22.5 Artifact fingerprint**

Where technically and operationally appropriate, a cryptographic hash or other integrity mechanism can help verify that a stored model artifact or configuration file matches a known version. A hash does not independently prove that the artifact is safe, correctly developed, or approved; it supports integrity verification.

**22.6 Provider and source metadata**

For externally supplied models, records should identify the provider, product or service, available release information, relevant contractual reference, and any known limitations in version transparency.

A model identity record may contain the following fields:

| Field                   | Example or expected content                                       |
| ----------------------- | ----------------------------------------------------------------- |
| Model ID                | `AI-MDL-0042`                                                     |
| Model name              | Customer Support Classifier                                       |
| Model version           | `2.3.1`                                                           |
| Configuration reference | `CFG-0042-PROD-07`                                                |
| Deployment ID           | `DEP-CRM-PROD-03`                                                 |
| Business owner          | Customer Operations                                               |
| Technical owner         | AI Engineering                                                    |
| Provider                | Internal development team or named external provider              |
| Lifecycle status        | Development, validation, approved, production, suspended, retired |
| Approval reference      | `APR-0042-2026-03`                                                |
| Registry reference      | Link to the authoritative model record                            |
| Artifact fingerprint    | Hash or equivalent integrity reference, if applicable             |
| Last reviewed           | Date of the latest required documentation review                  |

The example identifiers are illustrative, not prescribed formats.

Organizations should establish rules for identity creation, version changes, model replacement, configuration updates, and provider-side changes. A change to a model version should not silently overwrite the historical record for the previously approved version.

The identification scheme should also distinguish between a model version and a model's behavior in a specific application. The same underlying model may produce materially different results when deployed with different prompts, retrieval sources, tools, policies, or input-processing logic.

Consequently, the documentation record should capture the relevant combination of model version, configuration, and deployment context needed to understand the approved implementation.

### 23. Intended Purpose, Scope, and Authorized Use Documentation

Intended-purpose documentation defines the specific business or operational function for which a model is developed, acquired, evaluated, and authorized.

A model's intended purpose is more precise than a general description of its capabilities. A model may technically be capable of generating recommendations, classifying information, or analyzing documents, but those capabilities do not automatically establish that every possible use is appropriate or authorized.

The documentation should describe the business problem, intended users, operational context, expected outputs, decision-making role, and conditions under which the model may be used.

It should also identify unsupported or prohibited uses where necessary.

For example, a customer support classification model may be approved to recommend ticket categories. It may not be approved to determine whether a customer is eligible for a refund, automatically close a complaint, or assess a customer's credibility.

The distinction prevents capability from being mistaken for authorization.

A complete intended-purpose section should address:

- **Business objective:** The problem the model is intended to solve.
- **Target users:** The people or systems that interact with the model.
- **Input scope:** The data and input formats the model is designed to process.
- **Output scope:** The classifications, scores, recommendations, generated content, or other outputs it produces.
- **Decision role:** Whether the output informs a human decision, automates a defined action, or supports another system.
- **Operating context:** The environments, workflows, populations, and conditions in which the model is expected to function.
- **Performance expectations:** The relevant accuracy, reliability, latency, robustness, or other acceptance criteria.
- **Limitations:** Known conditions under which performance or reliability may deteriorate.
- **Prohibited uses:** Uses that are expressly disallowed by policy, contract, law, or risk decision.
- **Escalation conditions:** Circumstances requiring human review, additional testing, or suspension.

The documentation should distinguish intended use from foreseeable misuse. Intended use describes the approved application, while foreseeable misuse considers how users, integrated systems, or external actors might use the model outside its intended boundaries.

This distinction is important for risk assessment. A model designed to summarize internal documents may be exposed to attempts to extract confidential information, process unauthorized personal data, or follow malicious instructions embedded in retrieved content.

A controlled intended-purpose statement should be reviewed when the business workflow, affected population, decision authority, or consequences of model outputs materially change.

Where a new use case is proposed, the organization should assess whether the existing documentation and evaluation remain applicable. Reusing an existing model does not automatically justify reusing its previous risk assessment or approval.

### 24. Technical Architecture and Model Design Documentation

Technical architecture documentation explains the model's relevant components, interfaces, dependencies, processing stages, configuration, and deployment relationships.

Its purpose is to provide sufficient technical understanding for development, operations, security assessment, troubleshooting, change management, and assurance.

The required level of detail depends on the model type and deployment context. An internally trained machine-learning model may require documentation of its training pipeline, feature-processing components, and model artifact. An externally hosted generative AI service may require more emphasis on service configuration, APIs, data flows, retrieval components, access controls, and provider dependencies.

Technical documentation may include the following elements:

**24.1 Model type and approach**

Describe the model category and relevant approach, such as a classification model, regression model, computer vision model, language model, recommendation model, or other AI technique.

**24.2 Architecture and components**

Identify the major technical components and how they interact. For a composite AI solution, this may include preprocessing, the model, postprocessing, retrieval, orchestration, external tools, and downstream applications.

**24.3 Interfaces and integrations**

Document relevant APIs, input and output schemas, integration points, service dependencies, and interface constraints.

**24.4 Configuration**

Record configuration parameters that materially affect behavior, security, performance, or reproducibility. Protect sensitive values such as credentials and secret keys; document their management references rather than exposing secrets in ordinary model documentation.

**24.5 Execution environment**

Identify relevant runtime, hardware, software, hosting, and deployment characteristics where they affect model behavior, security, performance, or operational support.

**24.6 Dependencies**

Document important libraries, services, external models, retrieval systems, feature stores, and other dependencies. Detailed software component information may be maintained in a separate software bill of materials or dependency inventory and linked to the model record.

**24.7 Design rationale**

Preserve important architecture decisions, including significant alternatives considered, constraints, assumptions, and reasons for selecting the chosen approach.

**24.8 Technical limitations**

Describe relevant architectural constraints, failure modes, unsupported configurations, and known dependencies that can affect the model's operation.

A simplified architecture diagram for an AI-enabled support application might be:

```
Customer Support Application
             |
             v
Input Validation and Data Filtering
             |
             v
Preprocessing and Feature Extraction
             |
             v
AI Model Inference
             |
             v
Output Validation and Policy Checks
             |
             v
Human Review or Approved Routing Logic
             |
             v
Customer Support Workflow
```

The diagram should be accompanied by explanatory text describing the boundaries, responsibilities, and dependencies of each component.

For a generative AI application, the architecture may also include prompt templates, retrieval-augmented generation, vector databases, external tools, content filtering, and response postprocessing. These components should be documented when they materially affect behavior or risk.

Architecture documentation should describe the implemented system rather than only the intended design. Material differences between the approved design and the deployed configuration should be recorded and assessed.

### 25. Data Provenance, Lineage, and Processing Documentation

Data provenance and lineage documentation explain where model-related data originates, how it is obtained, what transformations it undergoes, and how it is used throughout the model lifecycle.

Data provenance concerns the origin and history of data. Data lineage focuses on the movement and transformation of data across systems and processing stages. Both are important for understanding model behavior, investigating defects, evaluating data suitability, and demonstrating responsible data governance.

The required information depends on the model's data dependencies. Training data may be central to a model developed internally, while inference-time data and retrieval sources may be more important for an externally hosted model.

Documentation may cover:

- Data source identifiers and responsible data owners.
- Collection or acquisition methods.
- Relevant licensing, contractual, and permitted-use restrictions.
- Data preparation and transformation procedures.
- Data quality, completeness, representativeness, and known limitations.
- Labeling and annotation approaches, where applicable.
- Relevant dataset versions or reproducible dataset references.
- Data retention and deletion requirements.
- Personal-data or confidential-data considerations.
- Relationships between datasets, model versions, and evaluation results.
- Relevant limitations arising from provider opacity or inaccessible training information.

A data lineage record may describe a sequence such as:

```
Approved Data Source
        |
        v
Collection or Acquisition
        |
        v
Validation and Quality Checks
        |
        v
Cleaning and Transformation
        |
        v
Feature Engineering or Preparation
        |
        v
Training or Evaluation Dataset
        |
        v
Model Development or Validation
        |
        v
Recorded Dataset and Model References
```

This is a conceptual sequence; not every model uses every stage.

Documentation should preserve enough information to understand which data sources and transformations influenced the model or a particular evaluation. Where retaining the underlying data is restricted or impractical, a dataset identifier, approved metadata record, or controlled reference may be more appropriate than duplicating the data itself.

Data documentation must also account for privacy and confidentiality. Model documentation should not unnecessarily reproduce personal data, authentication secrets, confidential records, or proprietary datasets. Where detailed data cannot be included directly, the documentation can refer to a controlled data catalog or authorized evidence repository.

For externally supplied models, complete training-data lineage may be unavailable. The organization should distinguish verified information from provider assertions, assumptions, and unknowns, then evaluate whether the resulting limitations are acceptable for the intended use.

### 26. Training, Fine-Tuning, and Model Development Records

For models developed or modified internally, development documentation preserves the information necessary to understand how the model was produced and which decisions influenced its resulting characteristics.

Training documentation should be sufficiently detailed to support technical review, evaluation, controlled change, and investigation of unexpected behavior. It should not be assumed that every internal parameter or intermediate artifact must be included in a single narrative document; detailed technical records can be maintained in linked repositories.

Relevant information may include:

- The development objective and model selection rationale.
- The training approach and applicable methodology.
- References to training and validation datasets.
- Relevant preprocessing and feature-engineering methods.
- Material training parameters and configuration.
- Relevant software, framework, and runtime versions.
- Experiment identifiers and selected results.
- Model checkpoint or artifact references, where applicable.
- Fine-tuning data and configuration, where applicable.
- Relevant human feedback or annotation processes.
- Known limitations and unresolved development issues.
- Reproducibility constraints and unavailable information.
- The rationale for selecting the release candidate.
- Links to validation and approval records.

For example, a team developing a fraud-detection model may compare several candidate models using defined performance and operational criteria. The documentation should explain the selection rationale and preserve references to the evaluation results supporting the chosen model.

It should not merely state that the selected model was the "best-performing" option. That statement is incomplete unless the organization defines the relevant metrics, evaluation conditions, constraints, and trade-offs.

Development documentation should also distinguish training, validation, and test activities. Reusing evaluation data improperly can produce misleading performance estimates and weaken the evidence supporting a model's approval.

Where development is outsourced or the model is acquired from a provider, the organization should document the information it receives, the provenance of available claims, and any significant limitations in its ability to independently examine the development process.

### 27. Model Evaluation and Validation Documentation

Evaluation and validation documentation records how the model was assessed, what the assessment established, what limitations were identified, and whether the evidence supports the intended use.

Although the terms are sometimes used interchangeably, organizations should define them consistently. Evaluation may refer broadly to measurement against specified criteria, while validation commonly concerns whether the model is fit for its intended purpose. The exact distinction should follow the organization's methodology and applicable requirements.

A complete evaluation record should identify:

**27.1 Evaluation objective**

Explain the question being assessed, such as predictive performance, robustness, fairness, security, reliability, or operational suitability.

**27.2 Scope and conditions**

Identify the model version, configuration, use case, test environment, data references, and relevant assumptions.

**27.3 Methodology**

Describe the test procedures, metrics, sampling approach, test scenarios, and acceptance criteria.

**27.4 Results**

Record the observed results, relevant uncertainty, performance differences across important scenarios, and deviations from expectations.

**27.5 Limitations**

Identify aspects not evaluated, data constraints, testing limitations, and conditions under which the results may not generalize.

**27.6 Findings and remediation**

Record identified defects, risk implications, corrective actions, retesting, and unresolved issues.

**27.7 Conclusion**

State whether the results support the defined acceptance criteria and intended purpose, including any conditions or restrictions.

**27.8 Review and approval**

Identify the evaluator, reviewer, date, and relevant decision authority.

For example, a classification model may achieve acceptable overall accuracy while producing materially higher error rates for a particular category of customer request. The evaluation record should document the overall result, the category-specific finding, its potential impact, and the organization's response.

A single performance metric rarely provides sufficient evidence for all governance objectives. Accuracy testing does not automatically establish security, fairness, privacy compliance, robustness, or operational suitability.

Evaluation records should therefore be linked to the relevant requirements and risk assessments. This relationship enables reviewers to determine which claims were tested, what evidence supports the conclusions, and which limitations remain unresolved.

### 28. Model Limitations, Assumptions, and Uncertainty Documentation

Model limitations, assumptions, and uncertainty should be explicitly documented because they define the boundaries of what the organization can reasonably expect from the model.

A model can perform adequately under evaluated conditions and still produce unreliable results when input data, operating conditions, user behavior, or environmental assumptions change.

Documentation should distinguish among three related concepts.

**Limitations** are known constraints on the model's capabilities or reliability. Examples include poor performance on certain input types, limited language coverage, sensitivity to noisy data, or inability to explain some predictions adequately.

**Assumptions** are conditions taken to be valid when the model is designed, evaluated, or operated. Examples include assumptions about data availability, input quality, user behavior, system availability, or the stability of relevant operating conditions.

**Uncertainty** concerns the degree to which predictions, measurements, or conclusions are uncertain. Its meaning and measurement depend on the model type and evaluation methodology.

A useful limitations register may contain:

| Field                 | Purpose                                                                       |
| --------------------- | ----------------------------------------------------------------------------- |
| Limitation ID         | Unique reference                                                              |
| Description           | Clear statement of the known limitation                                       |
| Affected use case     | Identifies where the limitation matters                                       |
| Evidence source       | Links the limitation to testing, incidents, analysis, or provider information |
| Potential consequence | Explains the possible operational or risk impact                              |
| Required safeguard    | Identifies applicable restrictions or compensating controls                   |
| Owner                 | Assigns responsibility for monitoring or remediation                          |
| Review trigger        | Defines when the limitation must be reassessed                                |
| Status                | Records whether the limitation is open, mitigated, accepted, or resolved      |

Limitations should be written in operationally meaningful language.

For example, "the model may be inaccurate" is too vague to support effective governance. A more useful statement identifies the relevant conditions, expected failure mode, potential consequence, and required response.

Documentation should not conceal limitations to make a model appear more mature or commercially attractive. A transparent record of known limitations supports more defensible decisions than unsupported claims of reliability.

Where uncertainty cannot be quantified reliably, the organization should explain the qualitative assessment and the reasons a quantitative estimate is unavailable.

### 29. Security Requirements and Threat-Related Documentation

Security documentation records the security properties expected of the model and its surrounding environment, the threats considered, the controls implemented, and the limitations that remain.

AI security cannot be adequately documented by recording only the model's architecture or general security classification. Security risks may arise from training data, inference inputs, model outputs, APIs, external tools, deployment infrastructure, supply-chain dependencies, and interactions with other systems.

The security documentation should be proportionate to the model's architecture, exposure, intended use, and potential impact.

Relevant areas may include:

- Identity and access management for model development and inference.
- Protection of model artifacts, configuration, and sensitive parameters.
- Data confidentiality, integrity, and permitted processing.
- Input validation and protection against malicious or malformed inputs.
- Model-specific threats, such as adversarial manipulation or model extraction, where relevant.
- Prompt injection and unsafe tool invocation for applicable generative AI systems.
- API security, rate limiting, and abuse prevention.
- Dependency and supply-chain security.
- Logging, monitoring, and incident investigation requirements.
- Security testing, findings, and remediation.
- Secrets management and privileged access.
- Availability, resilience, and recovery requirements.
- Security-related limitations and residual risks.

Security documentation should link identified threats to controls and supporting evidence. A statement that a model is "secure by design" is not sufficient without an explanation of the security requirements, implementation decisions, and assessment results supporting that conclusion.

For example, an AI application that retrieves internal documents may face risks from unauthorized retrieval, prompt injection within retrieved content, or disclosure of information beyond a user's permissions. Its documentation should describe the relevant trust boundaries, access-control enforcement, retrieval restrictions, testing, and operational monitoring.

Where a security assessment identifies a material unresolved weakness, the documentation should record its severity, potential consequences, owner, remediation plan, and any decision restricting deployment.

Security-sensitive documentation must itself be protected. Detailed threat scenarios, exploitability findings, and deployment weaknesses should be accessible to authorized personnel without being unnecessarily exposed to general users.

### 30. Human Oversight and Decision Accountability Documentation

Human oversight documentation explains how people remain appropriately involved in AI-supported or AI-assisted decisions and how responsibility is allocated when model outputs influence consequential actions.

The level of oversight depends on the model's intended use, degree of automation, risk, applicable legal requirements, and potential consequences of incorrect outputs.

Documentation should distinguish between a nominal human review and a meaningful oversight mechanism. A process that requires a person to approve every output but provides insufficient information, time, authority, or competence may not provide effective oversight.

Relevant documentation should describe:

**30.1 Oversight roles**

Identify who reviews model outputs, who can override recommendations, and who is accountable for the resulting operational decision.

**30.2 Review criteria**

Specify the conditions that require review, such as low-confidence outputs, sensitive categories, unusual cases, conflicting evidence, or detected policy violations.

**30.3 Decision authority**

Define whether the human reviewer can approve, reject, modify, escalate, or suspend the model's output.

**30.4 Reviewer information**

Describe what information, explanation, confidence indicator, supporting evidence, or limitation notice is available to the reviewer.

**30.5 Escalation procedures**

Document the process for unresolved cases, suspected model failures, complaints, and incidents.

**30.6 Oversight evidence**

Identify the records needed to demonstrate that required review and intervention occurred, subject to applicable privacy, retention, and proportionality requirements.

**30.7 Training and competence**

Record relevant user training, operating instructions, and competence requirements where these are necessary for effective oversight.

For example, if an AI system recommends prioritization of customer complaints, the documentation should identify which categories require mandatory human review and what the reviewer must do when the recommendation conflicts with the available evidence.

The organization should also evaluate whether the oversight process is effective in practice. Evidence may include sampled decisions, override rates, reviewer feedback, incident records, and assessments of whether users understand the model's limitations.

Documentation should avoid implying that the presence of a human reviewer automatically eliminates model risk. Human oversight is a control that must be appropriately designed, implemented, and assessed.

### 31. Operational Documentation and Production Readiness

Operational documentation describes the conditions and procedures necessary to operate the model safely, reliably, and consistently in its approved environment.

A model that performs well during development may still fail operationally because of incorrect configuration, unavailable dependencies, inadequate monitoring, excessive latency, insufficient capacity, or poorly defined incident procedures.

Operational documentation should connect the approved model baseline to the procedures used by the teams responsible for production operation.

Relevant content includes:

- Approved deployment version and configuration.
- Environment and service dependencies.
- Deployment and rollback procedures.
- Operational acceptance criteria.
- Availability and performance requirements.
- Monitoring and alerting thresholds.
- Error handling and fallback behavior.
- Access and privileged-operation requirements.
- Capacity and resource constraints.
- Backup and recovery arrangements where applicable.
- Incident escalation and response procedures.
- Maintenance windows and change restrictions.
- Support ownership and escalation contacts.
- Decommissioning and dependency-removal procedures.

For models whose behavior depends on external services, documentation should identify the relevant service dependencies and the operational consequences of service changes or outages.

For example, a production application may depend on a third-party model API, an internal retrieval service, and a policy-enforcement layer. The operational documentation should identify the consequences of failure in each component and specify whether the application should stop processing, switch to a controlled fallback, or route the case for manual handling.

Operational documentation should also distinguish between a documented procedure and a tested procedure. A rollback plan may exist on paper but remain ineffective if it has never been tested or if its assumptions no longer match the production architecture.

Where production readiness depends on mandatory criteria, the relevant evidence and approval decision should be linked to the model's documentation record.

### 32. Model Configuration and Environment Baselines

A model configuration baseline defines the approved combination of model artifacts, parameters, dependencies, policies, and environment settings relevant to a particular deployment.

Configuration documentation is important because model behavior can change without retraining the model itself.

Examples include changes to inference parameters, system prompts, retrieval indexes, preprocessing rules, safety filters, API versions, feature transformations, or external service settings.

The documentation should identify configuration elements that can materially influence behavior, risk, security, performance, or compliance.

A configuration baseline may include:

| Configuration element              | Documentation consideration                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------- |
| Model artifact or provider release | Identify the approved model version or available provider release reference           |
| Inference parameters               | Record behavior-affecting settings and applicable constraints                         |
| Prompt and instruction templates   | Identify approved versions and change-control requirements where relevant             |
| Preprocessing and postprocessing   | Document transformations and output-handling logic                                    |
| Retrieval configuration            | Record relevant knowledge sources, retrieval settings, and access restrictions        |
| Tool and API permissions           | Document the functions available to the model and associated authorization boundaries |
| Safety and policy controls         | Identify relevant filters, enforcement mechanisms, and their versions                 |
| Environment                        | Record material runtime, deployment, and dependency information                       |
| Monitoring thresholds              | Link the approved operational criteria to the monitoring configuration                |
| Integrity reference                | Record hashes or other verification references where appropriate                      |

The baseline should distinguish between values that are operationally sensitive and values that can safely be disclosed in general documentation. Secrets and credentials should be stored in appropriate secrets-management systems and referenced through controlled identifiers.

Where an organization uses immutable deployment artifacts or version-controlled configuration, documentation can link to those authoritative records instead of copying their entire contents.

Any material baseline change should be assessed through the organization's change-management process. The required assessment may include regression testing, security review, impact analysis, risk reassessment, and reapproval.

For externally hosted models whose underlying behavior can change without the customer controlling the model artifact, the organization should document the available versioning and notification mechanisms, monitor relevant provider changes, and assess the residual uncertainty.

### 33. Model Dependencies and Supply-Chain Documentation

Model dependency documentation identifies the components, services, datasets, libraries, providers, and other resources on which the model depends.

These dependencies may influence security, reliability, legal compliance, availability, performance, and the ability to maintain the model over time.

The dependency inventory should distinguish direct dependencies from material indirect dependencies where those relationships are relevant to risk.

For an internally developed model, dependencies may include training frameworks, preprocessing libraries, model-serving components, container images, feature stores, and data pipelines.

For an AI application using an external foundation model, dependencies may include the provider's API, orchestration frameworks, retrieval systems, vector databases, third-party tools, and content-processing services.

A dependency record should identify:

- Dependency name and type.
- Provider or maintainer.
- Version or available release reference.
- Relationship to the model or deployment.
- Security and operational significance.
- Known limitations or support constraints.
- Relevant licensing or contractual restrictions.
- Update and vulnerability-management responsibilities.
- Fallback or replacement options, where applicable.
- Links to supplier assessments and supporting evidence.

Dependency documentation supports change impact analysis. If a critical library becomes vulnerable or an external service changes its behavior, the organization can identify which models and deployments may be affected.

A dependency map can also support resilience planning by revealing concentration risk, single points of failure, unsupported components, and reliance on a provider whose service terms or availability may change.

The documentation should not imply that listing a dependency proves it has been assessed. Supplier and component risks must be evaluated through appropriate security, procurement, legal, and operational processes.

### 34. Model Documentation Change Control

Model documentation change control ensures that records remain aligned with the approved model and its actual operating context.

Changes may originate from model retraining, fine-tuning, configuration updates, revised prompts, data-source changes, infrastructure migrations, provider releases, new integrations, regulatory developments, or changes to intended use.

Not every change has the same impact. An administrative correction may require a simple review, while a change to model behavior, data processing, access permissions, or decision authority may require renewed evaluation and formal approval.

A controlled change process should include the following activities.

**34.1 Change identification**

Record the proposed change, its origin, the affected model and deployment, and the reason for the change.

**34.2 Impact assessment**

Determine which documentation artifacts, controls, tests, risk assessments, contracts, and approvals may be affected.

**34.3 Classification**

Classify the change according to the organization's change policy, distinguishing administrative, routine technical, material, and emergency changes where appropriate.

**34.4 Documentation update**

Revise affected records and preserve the relationship between the previous approved baseline and the proposed new baseline.

**34.5 Evaluation and review**

Perform the testing, risk assessment, security review, or compliance analysis required by the change's nature and risk.

**34.6 Approval**

Obtain the required authorization before implementation, except where an approved emergency process permits a different sequence with appropriate safeguards and retrospective review.

**34.7 Release and traceability**

Record the deployed version, configuration, implementation date, test evidence, approval reference, and any remaining conditions.

**34.8 Post-change verification**

Confirm that the implemented state matches the approved change and that the relevant documentation is current.

A change-control record may contain:

| Field                         | Purpose                                                             |
| ----------------------------- | ------------------------------------------------------------------- |
| Change ID                     | Unique reference                                                    |
| Model and deployment          | Identifies affected assets                                          |
| Previous baseline             | Records the existing approved state                                 |
| Proposed change               | Describes what will change                                          |
| Reason                        | Explains the business, technical, security, or compliance rationale |
| Impact assessment             | Identifies affected requirements and documentation                  |
| Risk and testing requirements | Defines necessary assessment and verification                       |
| Approval                      | Records the authorized decision                                     |
| Implementation result         | Confirms what was deployed                                          |
| Documentation references      | Links updated records and evidence                                  |
| Closure status                | Records completion or outstanding actions                           |

Change control is particularly important for generative AI applications. Updating a system prompt, retrieval corpus, tool permission, or content-filtering policy may materially alter behavior even when the underlying model version remains unchanged.

The organization should therefore define materiality based on potential impact rather than assuming that only model retraining requires documentation updates.

### 35. Documentation of Model Incidents, Defects, and Corrective Actions

Model incident and defect documentation preserves information about failures, unexpected behavior, security events, performance deterioration, control weaknesses, and corrective actions.

These records help organizations determine what happened, which model or configuration was involved, whether the issue reflects a known limitation, and what action is necessary to reduce recurrence.

Documentation should distinguish among a model defect, an operational incident, a security incident, and a governance or compliance deficiency. These categories may overlap, but their investigation and reporting requirements may differ.

A useful incident record should include:

- Incident or defect identifier.
- Detection source and date.
- Affected model, version, configuration, and deployment.
- Description of the observed behavior.
- Expected behavior or applicable requirement.
- Impact assessment and affected stakeholders.
- Relevant logs, test results, and other evidence references.
- Immediate containment actions.
- Root-cause analysis, where established.
- Corrective and preventive actions.
- Required documentation updates.
- Retesting and verification results.
- Approval for closure and residual concerns.

For example, an AI classification model may begin misrouting a category of customer complaints after an upstream data transformation changes. The incident record should link the observed failure to the relevant model deployment, preprocessing configuration, input characteristics, and operational evidence.

If the investigation establishes that the documentation failed to identify the dependency on the upstream transformation, the organization should update both the model documentation and the relevant dependency or change-management records.

Corrective action should address the underlying cause rather than merely amend the narrative. If the problem resulted from an ineffective change-control process, updating a document without strengthening that process may leave the same weakness in place.

Incident records may contain sensitive operational details and personal information. Access, retention, and disclosure should therefore follow the organization's incident management, privacy, security, and records management requirements.

### 36. Documentation of Model Retirement and Decommissioning

Model retirement documentation establishes when and why a model was removed from service, what dependencies were affected, which records must be retained, and how the organization verified that the model is no longer used in an unauthorized or unintended manner.

Retirement may occur because the model is obsolete, replaced, no longer economically viable, no longer compliant, too risky, unsupported by its provider, or no longer required for the original business purpose.

A retirement decision should consider more than the removal of the model artifact. A model may remain accessible through an API, embedded in an application, referenced by scheduled jobs, or retained in a fallback configuration after its formal retirement date.

The retirement record should address:

**36.1 Retirement rationale**

Record the reason for retirement and the authority responsible for approving the decision.

**36.2 Impact assessment**

Identify dependent applications, business processes, downstream systems, users, and records affected by decommissioning.

**36.3 Replacement or transition**

Document any replacement model, migration plan, transition arrangements, and necessary validation of the replacement.

**36.4 Access and deployment removal**

Record the removal or disabling of endpoints, credentials, scheduled jobs, integrations, and other operational access paths as appropriate.

**36.5 Data and artifact disposition**

Document how model artifacts, associated data, and supporting records are retained, archived, transferred, or securely disposed of in accordance with applicable obligations.

**36.6 Evidence preservation**

Preserve the records needed for audit, incident investigation, legal obligations, contractual requirements, and historical accountability.

**36.7 Closure verification**

Record evidence that decommissioning was completed and that the relevant inventory, documentation, access, and operational records were updated.

Retirement should not automatically trigger deletion of all associated documentation. Historical records may remain necessary to explain past decisions, investigate incidents, demonstrate prior compliance, or respond to an audit.

The organization should also distinguish between removing a model from production and permanently deleting its artifacts. These are separate decisions governed by different operational, security, legal, and records-management requirements.

### 37. Model Documentation Review and Approval Controls

Documentation review and approval controls establish whether required information has been checked by appropriately qualified personnel and whether the model is authorized to proceed through relevant lifecycle stages.

A review should be meaningful, proportionate, and linked to explicit acceptance criteria. Merely recording a reviewer's name or collecting an electronic signature does not establish that the review was adequate.

A controlled review process should define:

- Required review roles and their competence.
- Mandatory documentation sections and supporting evidence.
- Completeness and accuracy criteria.
- Risk-based review depth.
- Independence requirements where applicable.
- Treatment of unresolved findings.
- Exception and waiver procedures.
- Approval authority and delegation limits.
- Required approval conditions.
- Review frequency and change-triggered reassessment.

The organization should distinguish between technical review, risk review, compliance review, and final authorization where these serve different purposes.

For example, a technical reviewer may determine whether the architecture and evaluation results are adequately documented. A risk owner may assess whether residual risks are acceptable within their authority. A deployment authority may then determine whether the model satisfies the conditions for production release.

These decisions should be connected but should not be treated as interchangeable.

Where a review identifies missing mandatory evidence, the reviewer should record the gap and determine whether it blocks approval, requires remediation before deployment, or can be addressed through a formally authorized exception.

Approval records should identify the exact model and configuration baseline covered by the decision. An approval that cannot be linked to the relevant version may be insufficient to establish which implementation was authorized.

Periodic review should also verify that the original decision remains valid. A previously approved model may require reassessment if its intended use, data sources, dependencies, operating conditions, or applicable obligations change.

### 38. Documentation Retention, Archival, and Retrieval

Documentation retention and archival controls ensure that records remain available, protected, and retrievable for the period required by organizational policy, applicable law, regulation, contracts, and legitimate business needs.

Retention should be determined by record type and context rather than applying an arbitrary single period to every model artifact.

For example, a model's current configuration record, an evaluation report, a security incident record, a supplier contract, and a model retirement decision may be subject to different retention requirements.

A retention framework should establish:

- Record categories and ownership.
- Applicable retention rules and triggering events.
- Legal holds and investigation requirements.
- Archival formats and preservation requirements.
- Access restrictions for archived records.
- Integrity verification where appropriate.
- Retrieval procedures and expected response times.
- Rules for deletion and secure disposal.
- Handling of duplicate records and obsolete drafts.
- Responsibilities for third-party repositories and supplier-held records.

Archived documentation should retain sufficient context to remain understandable. A report that refers to an obsolete internal system, unavailable dataset, or undocumented model identifier may be difficult to interpret years later.

Organizations should therefore preserve relevant metadata and relationships between artifacts, even when the original technical environment can no longer be recreated.

Where the documentation is maintained in a supplier platform, the organization should consider what happens if the contract ends, the provider changes its service, or access to historical records is lost. Contractual arrangements and export procedures should support the required retention and retrieval outcomes.

Retention controls should also account for privacy and data minimization. Keeping every record indefinitely may create unnecessary risk. Records should be retained for justified periods and securely disposed of when applicable obligations permit and require their removal.

### 39. Documentation Access Control and Information Classification

Model documentation access control ensures that people can obtain the information required for their responsibilities while reducing the risk of unauthorized disclosure, modification, or destruction.

Documentation may need to be shared across engineering, governance, audit, legal, security, operations, suppliers, and regulators. These stakeholders do not necessarily require identical access to every artifact.

The organization should classify documentation according to its sensitivity and define access rules appropriate to each category.

For example:

- A general model description may be accessible to a broad internal audience.
- Detailed architecture and configuration records may be restricted to authorized technical personnel.
- Security vulnerabilities and exploitation findings may require more restrictive access.
- Personal-data processing records may require privacy-related access restrictions.
- Credentials and secret keys should remain in dedicated secrets-management systems rather than ordinary documentation.
- Certain records may require controlled disclosure to auditors, regulators, or contractual counterparties.

Access controls should address both reading and modification. A user who may view a document should not automatically be allowed to edit or approve it.

Appropriate controls may include role-based access control, least-privilege permissions, multifactor authentication for sensitive repositories, controlled sharing, access reviews, version history, and audit logging.

The organization should also consider the security of document exports, email attachments, local copies, and shared links. A well-protected central repository can be undermined if sensitive copies are distributed without equivalent controls.

For high-value records, integrity protection may include immutable storage, signed approvals, cryptographic fingerprints, or other mechanisms suitable for the organization's threat model.

Access control should support legitimate assurance activities. Internal audit and authorized assessors should be able to obtain the evidence necessary to perform their responsibilities through approved channels, even when the underlying documentation is sensitive.

### 40. Cross-Referencing and Traceability Between Documentation Artifacts

Cross-referencing connects related records so that reviewers can follow the relationship between a requirement, a model characteristic, a risk, a control, an evaluation result, and a governance decision.

Without cross-referencing, organizations may have all the required documents but still struggle to demonstrate how they fit together.

A traceability structure can connect:

```
Business Requirement
        |
        v
Intended Purpose and Model Requirement
        |
        v
Risk Assessment
        |
        v
Required Control or Acceptance Criterion
        |
        v
Implementation Reference
        |
        v
Evaluation or Control-Test Evidence
        |
        v
Review and Approval Decision
        |
        v
Monitoring and Change Records
```

This structure enables a reviewer to move in both directions. Starting from a requirement, the reviewer can identify the implementation and supporting evidence. Starting from an observed failure, the reviewer can trace the affected requirement, control, model version, approval, and risk decision.

Cross-references should use stable identifiers wherever possible. Document titles alone are unreliable because titles may change, duplicate names may exist, and files may be moved.

Useful identifiers include:

- Model ID and version.
- Requirement ID.
- Risk ID.
- Control ID.
- Test or evaluation ID.
- Finding or incident ID.
- Change request ID.
- Approval ID.
- Supplier or contract reference.
- Evidence artifact ID.

The traceability mechanism should also preserve status and context. A link to a superseded test report may still be useful for historical analysis, but it should not be mistaken for evidence that the current production version passed the same test.

A mature documentation architecture distinguishes current approved records from historical records and makes their relationship explicit.

Cross-referencing is particularly valuable during internal audit, regulatory examination, material change assessment, and incident investigation because it reduces the effort required to reconstruct the model's governance history.

### 41. Model Documentation Automation and Workflow Integration

Documentation automation uses controlled tools and workflows to create, validate, link, update, and maintain model records with reduced manual effort.

Automation can improve consistency and timeliness, but it should not be treated as a substitute for technical judgment, risk ownership, or authorized approval.

Appropriate automation opportunities include:

- Creating a documentation record when a model is registered.
- Populating stable metadata from an authoritative model registry.
- Linking deployment identifiers to release records.
- Checking for mandatory fields and missing references.
- Triggering review tasks when a document approaches its review date.
- Detecting changes to approved configuration baselines.
- Linking evaluation reports to the corresponding model version.
- Opening remediation tasks when documentation checks fail.
- Updating lifecycle status after an approved workflow transition.
- Producing management reports on documentation completeness and currency.

Automation should use authoritative sources for populated fields. If a model name is copied from an ungoverned spreadsheet, automated population may reproduce incorrect information more efficiently rather than improve accuracy.

The workflow should distinguish between automatically generated facts and human-reviewed conclusions. For example, a system may automatically record the deployed model version, but a qualified reviewer may still need to assess whether the associated evaluation results support the intended use.

Automated checks should also detect stale or broken relationships. A document may contain all mandatory fields yet reference an obsolete model version or a test report that no longer supports the current configuration.

For generative AI applications, automated documentation generation may assist with summarizing architecture descriptions, development notes, or evaluation results. Generated content should be verified against authoritative records before it is approved as a governance artifact.

Organizations should document the automation mechanism itself where it materially affects the reliability of the documentation process. This may include data sources, transformation rules, validation logic, access permissions, error handling, and review requirements.

Automation should reduce administrative burden while preserving clear accountability for the correctness and approval of the resulting records.

### 42. Documentation of Model Reproducibility and Reconstructability

Reproducibility and reconstructability are related but distinct documentation objectives.

**Reproducibility** concerns the ability to repeat a process under sufficiently equivalent conditions and obtain results that are consistent within the expected tolerance.

**Reconstructability** concerns the ability to establish what model, configuration, data references, environment, and operational conditions were associated with a historical result or decision.

Exact reproducibility may be difficult or impossible in some AI environments. Nondeterministic inference, stochastic training, hardware differences, changing external services, inaccessible provider internals, and evolving data sources may prevent identical results.

Documentation should therefore define the level of reproducibility that is realistically achievable and appropriate to the model's purpose.

Relevant information may include:

- Model and artifact identifiers.
- Training or fine-tuning configuration references.
- Dataset versions or controlled data references.
- Software, library, and runtime versions.
- Relevant hardware or execution-environment details.
- Random seeds and deterministic settings, where applicable.
- Inference parameters and configuration.
- Prompt, retrieval, or tool configuration, where relevant.
- External service versions or available provider release identifiers.
- Test scripts, procedures, and execution records.
- Known sources of nondeterminism.
- Expected result tolerances and limitations.

The organization should not promise exact replication when its environment cannot support it. Instead, it should define the practical objective, such as reproducing an evaluation within a specified tolerance or reconstructing the conditions associated with a historical decision.

For example, an externally hosted model may change internally without exposing its full release details to the customer. The organization may be able to reconstruct the API configuration, request parameters, application version, and timestamp of a historical interaction, but not reproduce the provider's exact internal inference process.

Such limitations should be documented because they affect the strength of incident investigation, validation, and assurance conclusions.

### 43. Documentation of Model Performance Baselines and Acceptance Criteria

A performance baseline records the expected behavior of a model under defined evaluation or operational conditions. Acceptance criteria establish the conditions that must be met before a model is approved for a particular use or continues operating without additional intervention.

Baselines are essential because statements such as "the model performs well" do not provide an objective basis for approval, monitoring, or change assessment.

A documented baseline should identify:

- The intended use and evaluated population or operating context.
- The model version and relevant configuration.
- The dataset or evaluation scenario references.
- The selected metrics and their definitions.
- The measured baseline results.
- The acceptance thresholds or decision criteria.
- Known limitations and uncertainty.
- The approval authority and applicable restrictions.
- The conditions that trigger reassessment.

Metrics should reflect the intended use. A classification model may require precision, recall, false-positive and false-negative analysis, and category-specific evaluation. A generative AI application may require task-specific quality assessment, factuality evaluation, safety testing, or other suitable measures.

No single metric should be assumed sufficient for every model type or risk.

Acceptance criteria should also distinguish between technical performance and governance acceptability. A model may meet a predefined accuracy threshold but still be unsuitable because of unresolved security weaknesses, inadequate documentation, unacceptable privacy risks, or missing mandatory approvals.

Performance baselines should be used to assess material changes and operational deterioration. When results move outside defined thresholds, the organization should document the investigation, impact assessment, corrective action, and decision about continued use.

Baselines should be reviewed when the intended purpose, affected population, data distribution, model configuration, or operating conditions materially change.

### 44. Documentation of Data Drift, Concept Drift, and Model Degradation

Documentation should explain how the organization identifies and responds to changes that may reduce the suitability or reliability of a model after deployment.

**Data drift** generally refers to changes in the distribution or characteristics of model inputs compared with a defined reference distribution.

**Concept drift** generally refers to changes in the relationship between inputs and the outcome the model is intended to predict.

**Model degradation** is a broader operational description of declining model performance or suitability. It may result from data changes, concept drift, configuration changes, external dependencies, process changes, or other factors.

The terminology and measurement approach should be defined consistently within the organization's monitoring methodology.

Documentation should identify the baseline used for comparison, the monitoring metrics, the review frequency, the thresholds for investigation, and the actions required when a threshold is exceeded.

Relevant records may include:

- Reference dataset or baseline period.
- Drift metrics and calculation methods.
- Monitoring data sources.
- Alert thresholds and rationale.
- Observed deviations and trends.
- Investigation results.
- Model or process changes associated with degradation.
- Corrective actions and retesting.
- Decisions to continue, restrict, retrain, replace, or suspend the model.

A drift alert does not automatically establish that a model has become unsafe or inaccurate. It indicates that a defined change has been observed and may require investigation.

Conversely, the absence of a drift alert does not prove that model performance remains acceptable. Monitoring may not detect all relevant changes, and some forms of degradation may occur without a significant shift in the monitored input distribution.

The documentation should therefore explain what the monitoring process can and cannot establish.

For high-impact applications, the organization may require additional review or validation before accepting a materially changed operating context. The resulting decision should be linked to the relevant risk assessment, performance baseline, and approval record.

### 45. Documentation of Model Explainability and Interpretability

Explainability and interpretability documentation describes what can be understood about a model's behavior, which explanation methods are available, what those methods establish, and what limitations apply.

The terms are related and are not always used consistently. An organization should define them according to its adopted methodology and intended use.

**Interpretability** commonly concerns how directly a model's internal structure or decision logic can be understood.

**Explainability** commonly concerns methods used to provide information about a model's outputs or behavior to users, developers, reviewers, or affected stakeholders.

Documentation should identify the explanation approach used, its intended audience, the types of questions it can help answer, and the conditions under which the explanation may be unreliable or misleading.

Relevant information may include:

- The model's general decision approach.
- Available feature importance or attribution methods.
- Local or global explanation techniques, where applicable.
- Known limitations of the selected methods.
- Whether explanations are approximate or post hoc.
- The intended audience and operational use of explanations.
- Relevant validation of explanation quality.
- How explanations are presented to human reviewers.
- Restrictions on using explanations as definitive causal evidence.

For example, a feature-attribution method may indicate that certain input features contributed strongly to a prediction. This does not necessarily prove that those features caused the real-world outcome or that the model relied on them in a simple, human-like reasoning process.

Documentation should avoid presenting explanations as more definitive than the methodology supports.

Explainability requirements should also be tied to the model's purpose and risk. An internal anomaly-detection model may require different explanation capabilities from a model that supports consequential decisions affecting individuals.

Where a model is inherently difficult to interpret, documentation should describe the limitation and identify alternative governance measures, such as stronger validation, constrained use, independent review, monitoring, or additional human oversight.

### 46. Documentation of Model Bias, Fairness, and Representativeness

Bias, fairness, and representativeness documentation records how the organization evaluates whether the model's behavior creates unacceptable differences across relevant groups, contexts, or input conditions.

These concepts are related but distinct.

**Bias** can refer to systematic errors or distortions arising from data, model design, measurement, deployment, or decision processes.

**Fairness** concerns whether the model's outcomes satisfy the fairness criteria relevant to the use case, affected stakeholders, and applicable requirements.

**Representativeness** concerns whether the data and evaluation scenarios adequately reflect the population, environments, or conditions for which the model is intended.

Documentation should not assume that one fairness metric or test is universally appropriate. Different metrics may reflect different objectives and may be incompatible under certain conditions.

A model fairness assessment should document:

- The relevant use case and affected groups.
- The rationale for the selected fairness criteria.
- The data and evaluation population used.
- Relevant data limitations and representativeness concerns.
- The selected metrics and evaluation methodology.
- Results and material differences across relevant groups.
- Statistical uncertainty and sample-size limitations.
- Identified causes or plausible explanations for disparities.
- Mitigation measures and their evaluation.
- Residual concerns and risk acceptance decisions.
- Restrictions or monitoring requirements.

For example, a model that classifies customer requests may show similar overall accuracy across all requests while performing less reliably for a particular language group. Aggregate performance could conceal this weakness.

The documentation should explain how the group-specific issue was identified, how its operational consequences were assessed, and what mitigation or restrictions were implemented.

Fairness documentation should also address the limitations of available data. Sensitive attributes may be unavailable or legally restricted, and proxy measures may be imperfect. The organization should not assume that the absence of group-specific measurements proves the absence of unfair outcomes.

Where fairness cannot be adequately assessed, the documentation should identify the limitation and explain its implications for approval and continued use.

### 47. Documentation of Privacy and Personal-Data Considerations

Privacy documentation records how personal data may be collected, accessed, processed, disclosed, retained, or otherwise used in connection with model development and operation.

It should connect model-specific data flows and behavior to the organization's privacy governance processes and applicable data protection requirements.

Relevant documentation may include:

- The purposes for which personal data is processed.
- Categories of personal data and data subjects, where applicable.
- Sources of personal data and the legal basis where required.
- Data-flow diagrams and processing locations.
- Data minimization and purpose limitation measures.
- Retention and deletion requirements.
- Access and disclosure controls.
- Data-subject rights processes where applicable.
- Relevant privacy risks and mitigations.
- Applicable privacy assessments and review decisions.
- Provider and processor responsibilities.
- Restrictions on secondary use, training, or reuse of submitted data.

The model documentation should identify relevant privacy artifacts rather than duplicating every record held by the privacy function.

For example, a model may process customer messages containing names, account details, or other personal information. The model documentation should explain the role of that information, the relevant processing components, and the controls applied to protect it. A detailed processing inventory or privacy impact assessment may be maintained separately and referenced through a stable identifier.

Privacy documentation should also consider the possibility that a model's outputs, memorization behavior, retrieval configuration, or integrations could expose personal information.

The organization should not assume that removing direct identifiers automatically eliminates all privacy risks. Re-identification, inference, unauthorized disclosure, and excessive retention may remain relevant depending on the use case.

Where a formal data protection impact assessment or another privacy assessment is required, the model documentation should record the applicable assessment reference, findings, mitigation measures, and relevant approval or consultation outcomes.

### 48. Documentation of Third-Party Assurance and Evidence Limitations

Third-party assurance documentation records the external evidence available about a model, its provider, or the services supporting it, together with an assessment of how relevant that evidence is to the organization's own use.

External evidence may include technical documentation, security assessment reports, certifications, independent assurance reports, evaluation summaries, contractual commitments, and supplier responses.

The existence of an external assurance artifact does not automatically demonstrate that the organization's model deployment satisfies its own requirements.

A structured review should establish:

**48.1 Scope**

Identify the service, model, environment, provider entity, and activities covered by the external evidence.

**48.2 Currency**

Determine whether the evidence covers a sufficiently recent period or version for the intended assessment.

**48.3 Independence and methodology**

Understand who produced the evidence, what methodology was applied, and whether relevant limitations are disclosed.

**48.4 Relevance**

Determine which organizational requirements and risks the evidence actually addresses.

**48.5 Coverage gaps**

Identify important controls, model characteristics, or deployment-specific risks not covered by the external assessment.

**48.6 Reliance decision**

Record whether the evidence can be relied upon, what additional verification is required, and who authorized that reliance.

**48.7 Ongoing monitoring**

Define how the organization will identify changes in provider status, scope, service configuration, or available assurance information.

For example, a provider's security certification may provide evidence about its management system, but it does not necessarily demonstrate that a particular model is suitable for a specific high-impact use case or that the organization's integration is correctly configured.

The documentation should preserve the distinction between provider-level assurance and deployment-level assurance.

Where external evidence is unavailable or insufficient, the organization should record the limitation, evaluate alternative assessment methods, and determine whether the intended use remains acceptable.

### 49. Documentation of Exceptions, Deviations, and Residual Risks

Exceptions and deviations document circumstances in which a model or its documentation does not fully meet an established requirement, standard, control, or acceptance criterion.

Residual risk refers to the risk remaining after the selected risk treatments and controls have been applied.

These records are important because governance decisions sometimes require a model to proceed despite known limitations, incomplete information, or temporary control gaps. Such decisions should be explicit, justified, authorized, and subject to appropriate monitoring.

An exception record should include:

- A unique exception identifier.
- The affected model, version, deployment, and requirement.
- A clear description of the deviation.
- The reason the requirement cannot currently be met.
- The risk and potential consequences.
- Existing and proposed compensating controls.
- The responsible risk owner.
- The authorized approval authority.
- The approval date and expiration or review date.
- Remediation actions and deadlines.
- Conditions that trigger escalation or suspension.
- Evidence supporting closure or renewal.

A deviation should not be treated as accepted merely because a project manager or developer acknowledges it. Acceptance must follow the organization's authority structure and applicable legal or regulatory requirements.

Some requirements may not be waivable through internal risk acceptance. An organization cannot assume that management approval makes a legal obligation optional.

Residual-risk documentation should explain the basis of the risk assessment, the limitations of the available evidence, and why the proposed operating conditions are considered acceptable within the decision-maker's authority.

Where the risk is unacceptable or a mandatory requirement remains unmet, the appropriate decision may be to restrict, delay, suspend, or reject the deployment.

Exceptions should be reviewed before expiry and reassessed when the model, its environment, or the relevant threat and regulatory landscape changes materially.

### 50. Building an Integrated Model Documentation Record

An integrated model documentation record brings together the identity, purpose, technical description, data relationships, evaluation evidence, risk information, governance decisions, and lifecycle history needed to understand and manage a model.

Integration does not require every item to be stored in one file. It requires a coherent record structure in which authoritative information can be located and its relationships verified.

A practical integrated record should contain the following elements:

| Record component               | Core questions answered                                                          |
| ------------------------------ | -------------------------------------------------------------------------------- |
| Identity and metadata          | Which model, version, and deployment are covered?                                |
| Purpose and boundaries         | What is the model authorized to do, and what is outside its scope?               |
| Architecture and dependencies  | How is the model implemented, and what does it depend on?                        |
| Data provenance                | Which relevant data sources and transformations are involved?                    |
| Development and configuration  | How was the model produced or acquired, and which configuration is approved?     |
| Evaluation and validation      | What was tested, under which conditions, and with what results?                  |
| Limitations and uncertainty    | What is not established, and where may the model fail?                           |
| Security, privacy, and risk    | Which material risks and controls apply?                                         |
| Human oversight and operations | How is the model supervised and operated?                                        |
| Approval and exceptions        | Who authorized its use, under which conditions, and with what unresolved issues? |
| Change history                 | What has changed, and how were changes assessed?                                 |
| Monitoring and incidents       | How is continued suitability evaluated, and how are failures recorded?           |
| Retention and retirement       | How are records preserved, and how is use formally terminated?                   |

The record should include stable references to the supporting artifacts required to substantiate important statements.

An integrated record should also identify unavailable information. An explicit statement that a provider does not disclose a particular development detail is more useful than silently omitting the field or presenting an assumption as a fact.

Finally, the organization should be able to retrieve the documentation applicable to a historical model version or deployment. This is essential when investigating incidents, evaluating previous decisions, responding to audits, or determining whether a material change invalidated an earlier approval.

A well-designed model documentation architecture therefore functions as a controlled information structure rather than a static document. It connects the model's technical identity and characteristics to the evidence, risks, controls, approvals, and lifecycle events necessary for accountable AI governance.

## Part 3 — Documentation Controls, Auditability, and Assurance Implementation

### 51. Establishing a Model Documentation Control Framework

A model documentation control framework defines the policies, procedures, responsibilities, validation mechanisms, and oversight activities required to ensure that AI model records remain accurate, complete, current, secure, and suitable for governance and assurance.

While a documentation architecture establishes how information is organized, the control framework establishes how that information is created, verified, approved, maintained, and protected.

Without effective controls, an organization may possess extensive documentation but still be unable to demonstrate that the records describe the actual model in production, that the evidence supports the stated conclusions, or that required governance decisions were authorized.

A model documentation control framework should establish the following control objectives:

- **Completeness:** Required documentation elements exist for every in-scope model.
- **Accuracy:** Documented information reflects the actual model and its operating environment.
- **Authorization:** Required reviews, approvals, and exceptions are performed by authorized personnel.
- **Traceability:** Material statements and decisions can be linked to supporting records.
- **Currency:** Documentation remains aligned with the current approved model state.
- **Integrity:** Records are protected against unauthorized modification or destruction.
- **Confidentiality:** Sensitive model information is available only to authorized users.
- **Retention:** Documentation remains available for the required period.
- **Accountability:** Documentation responsibilities and review activities are attributable to identified roles.
- **Effectiveness:** Controls operate as intended and deficiencies are identified and remediated.

These objectives should be translated into specific control activities with defined owners, frequencies, evidence requirements, and acceptance criteria.

For example, a control objective requiring documentation currency could be implemented through a mandatory review after material model changes, automated detection of version mismatches, and periodic reconciliation between the model registry and production deployment records.

The control framework should distinguish between preventive, detective, and corrective controls.

| Control type | Purpose                                               | Model documentation example                                                    |
| ------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| Preventive   | Prevent documentation deficiencies before they occur  | Require mandatory documentation fields before deployment approval              |
| Detective    | Identify deficiencies or unauthorized changes         | Compare approved model versions with production deployment records             |
| Corrective   | Resolve identified deficiencies and reduce recurrence | Update inaccurate documentation and remediate the underlying workflow weakness |

A mature framework combines all three types. Preventive controls reduce errors, detective controls identify failures that escape prevention, and corrective controls restore compliance and address root causes.

The framework should be proportionate to model risk, but minimum requirements must remain clear and enforceable.

### 52. Designing Documentation Controls With Defined Acceptance Criteria

A documentation control is more effective when its expected outcome can be objectively evaluated.

Statements such as "maintain complete documentation" or "review model records regularly" are too broad unless the organization defines what complete documentation means, which records require review, who performs the review, and how successful execution is demonstrated.

A well-designed control specification should include:

1. **Control objective:** The risk or governance requirement the control addresses.
2. **Control activity:** The specific action that must occur.
3. **Control owner:** The role accountable for execution.
4. **Control frequency or trigger:** When the activity must occur.
5. **Population:** The models, documents, or transactions covered.
6. **Acceptance criteria:** The conditions that constitute satisfactory execution.
7. **Evidence requirements:** The records demonstrating that the control operated.
8. **Exception handling:** The process for deficiencies and authorized deviations.
9. **Monitoring method:** How control effectiveness is assessed.
10. **Escalation requirements:** The conditions requiring management intervention.

Consider a control designed to ensure that model documentation matches the production deployment.

| Control attribute   | Example specification                                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------- |
| Control ID          | DOC-CTRL-001                                                                                    |
| Objective           | Ensure production deployments correspond to an approved model baseline                          |
| Activity            | Reconcile production model identifiers and configuration references against approved records    |
| Owner               | Model Operations                                                                                |
| Frequency           | At deployment and following material configuration changes                                      |
| Acceptance criteria | Every in-scope production deployment maps to an approved baseline or an authorized exception    |
| Evidence            | Deployment record, reconciliation result, approval reference, exception record where applicable |
| Failure response    | Investigate mismatches, assess impact, and restrict or suspend the deployment when required     |
| Assurance method    | Sample reconciliation records and verify the underlying deployment state                        |

The example is illustrative and should be adapted to the organization's risk and operating model.

Acceptance criteria should be sufficiently precise to prevent subjective interpretations of control success. However, numerical thresholds should not be introduced merely to make a control appear measurable. Some controls require qualitative assessment by competent reviewers.

For example, the existence of a model limitation statement can be verified mechanically, but determining whether that statement adequately explains the operational implications of the limitation may require technical judgment.

### 53. Model Documentation Risk Assessment

Documentation itself introduces risks that should be identified, assessed, and managed.

These risks arise when documentation is incomplete, inaccurate, outdated, inaccessible, excessively exposed, or disconnected from the actual model and its governance decisions.

A documentation risk assessment should consider both the likelihood of a deficiency and the consequences of relying on incorrect or unavailable information.

Common documentation risks include:

- An unapproved model being deployed because required approval evidence is missing.
- A model being used outside its authorized purpose because restrictions are not documented.
- Incorrect evaluation conclusions being relied upon because test evidence is incomplete.
- A security incident being difficult to investigate because the affected model version cannot be identified.
- A material configuration change escaping review because documentation updates are not linked to change management.
- Sensitive architecture information being disclosed through an inadequately protected repository.
- A regulatory examination identifying missing or unreliable technical documentation.
- Historical records becoming unavailable after a supplier relationship ends.
- Risk owners accepting residual risks without understanding important limitations.
- Automated documentation processes generating inaccurate or unsupported statements.

A documentation risk register should identify the risk, affected models or processes, causes, potential consequences, existing controls, residual risk, and treatment actions.

| Risk scenario                        | Potential consequence                                      | Example treatment                                                              |
| ------------------------------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Documentation is outdated            | Decisions rely on an obsolete model state                  | Trigger updates through change management and perform periodic reconciliation  |
| Evidence cannot be retrieved         | Audit or investigation conclusions cannot be substantiated | Use controlled repositories and test retrieval procedures                      |
| Model identity is inconsistent       | Evidence is associated with the wrong model or version     | Enforce unique identifiers and registry integration                            |
| Supplier information is insufficient | Risk assessment is based on unsupported assumptions        | Establish contractual information requirements and assess residual uncertainty |
| Unauthorized document changes occur  | Approval history or technical facts may be manipulated     | Apply access controls, version history, and integrity protection               |
| Limitations are omitted              | Users overestimate model capabilities                      | Require limitation review and explicit acceptance criteria                     |
| Approval evidence is missing         | Deployment authorization cannot be demonstrated            | Enforce approval gates and retain decision records                             |

Risk assessment should prioritize the consequences of the documentation failure, not merely the administrative inconvenience of correcting a record.

For a low-impact internal model, an outdated descriptive field may have limited consequences. For a model supporting safety-critical or legally significant decisions, missing validation evidence or incorrect version identification may constitute a material governance failure.

The treatment decision should reflect the affected model's risk classification, applicable requirements, and the organization's authority to accept residual risk.

### 54. Model Documentation Control Testing

Documentation control testing evaluates whether documentation controls are suitably designed and operate effectively.

Design effectiveness concerns whether the control, if performed as specified, is capable of addressing the relevant risk. Operating effectiveness concerns whether the control was actually performed, at the required frequency, by an appropriate person, and with the expected result.

Both dimensions matter.

A control may be well designed but consistently bypassed by project teams. Conversely, a control may be performed consistently but remain ineffective because its acceptance criteria do not address the actual risk.

A structured testing approach should include the following stages.

**54.1 Define the control objective**

Identify the requirement or risk addressed by the control.

**54.2 Understand the control design**

Review the procedure, ownership, trigger, acceptance criteria, evidence requirements, and exception process.

**54.3 Define the population**

Identify all models, changes, approvals, or documentation reviews within the control's scope.

**54.4 Select the test method**

Determine whether inquiry, inspection, observation, reperformance, data analysis, or a combination of methods is appropriate.

**54.5 Execute the test**

Obtain the relevant evidence and evaluate whether the control operated as designed.

**54.6 Record exceptions**

Document deviations, missing evidence, incorrect results, or instances in which the control was not performed.

**54.7 Evaluate the implications**

Assess the significance of the exceptions, the potential affected population, and whether the issue indicates a broader control weakness.

**54.8 Report and remediate**

Communicate findings to the responsible owner and track corrective actions to verified closure.

For example, an auditor testing the control that requires model documentation to be updated after material changes may select a sample of change records and compare each record against the associated model documentation.

The auditor should establish whether:

- The change was correctly classified.
- The documentation impact assessment was completed.
- Required artifacts were updated.
- Relevant evaluation or security reviews occurred.
- Required approvals were recorded.
- The deployed state matches the approved change.
- Any exceptions were appropriately authorized.

A completed change ticket alone does not prove that the control operated effectively. The auditor should inspect the underlying evidence and verify that the documented activities actually occurred.

### 55. Designing Evidence Requirements for Documentation Controls

Evidence requirements determine what records must be retained to demonstrate that a documentation control was performed and achieved its intended result.

Evidence should be relevant to the control objective, sufficiently reliable, attributable to the activity, and available for independent review.

For a documentation review control, suitable evidence may include the reviewed document version, review checklist, identified deficiencies, reviewer identity, review date, approval decision, and remediation records.

For a deployment reconciliation control, evidence may include the production deployment inventory, approved model baseline, reconciliation output, identified mismatches, and documented disposition.

Evidence should demonstrate more than the existence of a procedure. It should establish that the procedure was applied to the relevant population or transaction.

The organization should distinguish among:

- **Control design evidence:** Documentation showing how the control is intended to operate.
- **Control execution evidence:** Records showing that the activity was performed.
- **Control outcome evidence:** Information showing whether the expected result was achieved.
- **Exception evidence:** Records showing deficiencies and how they were handled.
- **Remediation evidence:** Records demonstrating that corrective actions were completed and verified.

These evidence types support different assurance questions.

For example, a policy requiring approval before production deployment demonstrates the intended control design. A dated approval record demonstrates that an approval was recorded. A comparison of the approval's model version with the actual production deployment helps establish whether the approved control outcome was achieved.

Where automated controls produce logs or reports, the organization should assess whether the source system, configuration, and records are sufficiently reliable for the intended assurance purpose.

If evidence can be modified by the same person whose activity is being assessed, additional verification may be necessary. Depending on risk, this may include restricted administrative access, independent review, immutable logging, or corroboration from another authoritative source.

### 56. Documentation Completeness and Consistency Reconciliation

Reconciliation controls compare model documentation against authoritative sources to identify missing, conflicting, or outdated information.

These controls are especially valuable when model information is distributed across multiple systems, such as an AI inventory, model registry, deployment platform, risk management system, and document repository.

Reconciliation should focus on fields and relationships that materially affect governance, security, compliance, and operational accountability.

Common reconciliation checks include:

- Model identifiers match across the inventory, registry, and documentation.
- Production versions correspond to approved model baselines.
- Material configuration references are current.
- Model owners and business owners are correctly assigned.
- Approval references correspond to actual authorized decisions.
- Risk records reference the correct model and intended use.
- Required evaluation reports exist for the relevant version.
- Open findings are reflected in the model's current governance status.
- Retired models are no longer represented as active production deployments.
- Supplier information reflects known provider changes.

A reconciliation process may use automated data comparison for structured fields and manual review for qualitative information.

For example, an automated check may identify that a production endpoint runs version 2.4 while the documentation records version 2.3. The mismatch should trigger investigation, but it does not by itself establish whether the deployment is unauthorized. The organization must determine whether version 2.4 has been approved, whether the registry is stale, or whether the deployment platform is reporting incorrect metadata.

Reconciliation controls should record the population assessed, comparison criteria, exceptions identified, responsible owners, and resolution evidence.

Organizations should also monitor the reconciliation process itself. A failed or incomplete data feed can create the appearance of consistency when the comparison is based on stale or partial information.

Accordingly, the control should establish that the source data was sufficiently complete and current before treating a successful comparison as evidence of compliance.

### 57. Documentation Governance for Generative AI and Foundation Models

Generative AI and foundation models introduce documentation challenges that differ from those associated with many traditional predictive models.

These models may be accessed through external APIs, adapted through fine-tuning, configured through prompts, connected to retrieval systems, or integrated with tools capable of taking actions.

Consequently, the effective behavior of the deployed application may depend on multiple components beyond the underlying model artifact.

Documentation should identify the model and provider where known, the available version information, the application's configuration, relevant prompts, retrieval sources, tool permissions, output-handling logic, and the safeguards applied around model interaction.

The documentation should also address relevant limitations, including hallucination, prompt sensitivity, context limitations, nondeterministic output, and the possibility that behavior changes when surrounding components are modified.

For retrieval-augmented generation, documentation may need to cover:

- Approved knowledge sources and their owners.
- Data ingestion and indexing procedures.
- Retrieval permissions and access-control enforcement.
- Embedding model and relevant version information.
- Retrieval configuration and ranking behavior.
- Context construction and prompt assembly.
- Citation or source attribution behavior, where applicable.
- Handling of stale, conflicting, or missing source information.
- Restrictions on external tools and actions.
- Evaluation scenarios and known failure modes.

For tool-enabled systems, documentation should explain which tools the model may invoke, what permissions those tools possess, how authorization is enforced, and which actions require human approval.

The model should not be documented as having only conversational capabilities if the surrounding application allows it to access records, execute transactions, send messages, or modify systems.

A practical generative AI documentation structure is:

```
Foundation Model or External Model
                 |
                 v
Application Configuration
                 |
                 +----> System Instructions
                 |
                 +----> Retrieval and Knowledge Sources
                 |
                 +----> Tool Integrations and Permissions
                 |
                 +----> Input and Output Safeguards
                 |
                 v
Application-Level Evaluation
                 |
                 v
Approved Deployment and Monitoring
```

This structure highlights an important governance distinction: evidence about the foundation model does not automatically establish the safety or suitability of the complete application.

The organization must evaluate the combination of model, configuration, data sources, integrations, controls, and intended purpose that it actually deploys.

### 58. Documentation Governance for Agentic AI Systems

Agentic AI systems can plan tasks, invoke tools, interact with external services, maintain state, or execute sequences of actions with varying degrees of autonomy.

Their documentation requirements must account for both the underlying model and the operational mechanisms that determine what actions the system can take.

A conventional model description may explain input processing and output generation but fail to capture the risks introduced by action execution, persistent memory, delegated tasks, or interactions among multiple agents.

Agentic system documentation should therefore identify:

- The system's intended objectives and authorized tasks.
- The agents, models, tools, and services involved.
- The permissions available to each component.
- The conditions under which actions may be initiated.
- The boundaries between recommendation and execution.
- Human approval requirements and escalation conditions.
- State management and memory behavior.
- Inter-agent communication and delegation rules.
- Action logging and traceability requirements.
- Error handling, stopping conditions, and recovery mechanisms.
- Security testing and adversarial evaluation.
- Known limitations and prohibited actions.

The documentation should describe how the system behaves when an action fails, a tool returns unexpected information, a task exceeds its authorized scope, or the model receives conflicting instructions.

For example, an agent authorized to prepare purchase orders may be permitted to retrieve supplier information and draft transactions but prohibited from submitting orders above a defined threshold without human approval.

The documentation should specify the permission boundaries, enforcement mechanism, approval workflow, and evidence required to establish whether those restrictions operated correctly.

The organization should distinguish between policy statements and technical enforcement. A document stating that an agent must not exceed its permissions is insufficient if the tools available to it permit unrestricted actions.

Agentic systems also require attention to cumulative behavior. Individual tool calls may appear permissible while a sequence of actions produces an unintended result. Documentation should therefore explain relevant workflow constraints, transaction limits, monitoring, and intervention mechanisms.

For high-impact agentic applications, the organization should assess whether the documentation adequately supports reconstruction of action sequences, identification of the responsible components, and investigation of unintended outcomes.

### 59. Documentation Governance for Continuously Learning and Adaptive Models

Continuously learning or adaptive models may change their behavior as they receive new data, update parameters, incorporate feedback, or modify internal representations during operation.

These characteristics create challenges for conventional documentation and version control because the model's state may evolve more frequently than a traditional release-based model.

The organization should determine whether the system actually changes its learned parameters during operation or whether it merely receives updated inputs, retrieval content, configuration, or external data. These are different mechanisms and should be documented accurately.

For a genuinely adaptive model, documentation may need to address:

- The mechanism that triggers or permits learning.
- The data or feedback used for adaptation.
- Validation and filtering of incoming learning data.
- Constraints on permissible model updates.
- The frequency and conditions of adaptation.
- Monitoring for unintended behavioral changes.
- Versioning or state-identification mechanisms.
- Rollback or recovery options.
- Approval requirements for material behavioral changes.
- The ability to reconstruct historical model states.
- Restrictions on autonomous adaptation in sensitive contexts.

For example, a fraud-detection model may update its behavior using newly confirmed transaction outcomes. The documentation should explain how those outcomes are validated, how updates are evaluated, and how the organization detects harmful changes in performance.

An organization should not assume that the original validation result remains sufficient after repeated material adaptations. It should establish criteria for determining when changes require additional evaluation, risk reassessment, or renewed approval.

Where complete historical state reconstruction is technically infeasible, the limitation should be documented and assessed against the system's intended purpose and risk.

For some high-impact uses, inability to identify or reconstruct the model state associated with a consequential decision may be unacceptable. The organization may need to constrain adaptation, preserve snapshots, maintain event histories, or require controlled release cycles.

### 60. Documentation Governance for Multimodal AI Models

Multimodal AI models process or combine multiple forms of information, such as text, images, audio, video, sensor data, or structured records.

Their documentation should explain how the different modalities are received, transformed, combined, evaluated, and used to generate outputs.

A text-only model documentation approach may fail to capture risks introduced by image metadata, audio transcription, video frames, cross-modal correlations, or inconsistencies between different input modalities.

Relevant documentation may include:

- Supported input and output modalities.
- Input format and preprocessing requirements.
- Data sources and transformation pipelines for each modality.
- Relationships between modalities and relevant synchronization assumptions.
- Modality-specific quality limitations.
- Evaluation methodology and metrics for each relevant task.
- Cross-modal failure scenarios.
- Privacy and sensitive-information considerations.
- Security threats associated with media inputs and embedded content.
- Output validation and human review requirements.
- Known limitations under low-quality, ambiguous, or conflicting inputs.

For example, a multimodal model used to analyze industrial equipment may process camera images, audio recordings, and sensor readings. Documentation should identify the role of each input, the conditions under which the inputs may be unreliable, and the controls used when they disagree.

A model that performs adequately on high-quality images may fail under poor lighting, unusual camera angles, or partial obstruction. These conditions should be reflected in evaluation records and operating limitations.

The organization should also assess risks associated with the combination of modalities. Individually acceptable inputs may create new privacy, inference, or security risks when combined.

Where the model supports consequential decisions, documentation should establish which input modalities are required, which may be omitted, and what actions are permitted when one or more inputs are unavailable or unreliable.

### 61. Model Documentation for High-Risk and High-Impact Applications

Models used in high-risk or high-impact contexts require documentation that supports a more rigorous understanding of their intended purpose, limitations, risk controls, evaluation evidence, and governance decisions.

The appropriate requirements depend on the relevant legal classification, sector, intended use, and potential consequences. High impact is a useful risk-management concept, but it should not be treated as interchangeable with a specific legal category such as a high-risk AI system under the EU AI Act.

For these applications, the organization should assess whether documentation is sufficiently detailed to support independent scrutiny and informed decision-making.

Additional documentation considerations may include:

- A more detailed description of intended purpose and operating boundaries.
- Explicit mapping of applicable legal and regulatory obligations.
- Comprehensive risk assessment and risk treatment records.
- Stronger evidence of data quality and representativeness.
- Detailed evaluation of foreseeable failure modes.
- Clear human oversight responsibilities and intervention procedures.
- Traceable technical and configuration baselines.
- Documented validation independence where required.
- More rigorous change assessment and reapproval criteria.
- Defined monitoring, incident response, and suspension triggers.
- Formal residual-risk acceptance by an authorized decision-maker.
- Reliable retention and retrieval of relevant historical records.

For example, a model supporting decisions about access to essential services may require stronger evidence concerning data quality, error patterns, limitations, human review, and the consequences of incorrect outputs than an internal tool used only to organize non-sensitive documents.

Documentation should demonstrate how the organization evaluated the actual risks of the use case, not simply assign a high-risk label and attach a generic checklist.

Where applicable legislation prescribes specific technical documentation or record-keeping requirements, those requirements must be mapped and satisfied according to the relevant legal provisions. Internal risk-based enhancements may supplement these obligations but cannot replace them.

### 62. Documentation of Model Evaluation Environments and Test Conditions

Evaluation results are meaningful only when the conditions under which they were produced are sufficiently understood.

Documentation should identify the environment, model version, configuration, input data, evaluation procedure, relevant dependencies, and acceptance criteria associated with each material test.

Without this information, an organization may incorrectly compare results from different configurations or assume that evidence obtained in one environment applies to another.

Relevant test-condition records may include:

- Model and configuration identifiers.
- Evaluation dataset and version references.
- Data preparation and filtering methods.
- Runtime and relevant software dependencies.
- Hardware or execution constraints where material.
- Test scripts, procedures, and metric definitions.
- Relevant random seeds or nondeterministic settings.
- External services and provider versions where available.
- Test date, execution identity, and result references.
- Known deviations from the intended production environment.
- Limitations affecting the interpretation of results.

The documentation should distinguish between development testing, independent validation, pre-production acceptance testing, and production monitoring. These activities may use different environments and address different questions.

For example, a model may pass evaluation in a controlled environment but behave differently in production because the production application uses different preprocessing, a different retrieval corpus, or additional postprocessing rules.

The evaluation record should explain material differences between the tested configuration and the deployed configuration. Where those differences could affect the conclusion, additional testing or formal approval may be necessary.

Test-condition documentation is particularly important when results are used as evidence of regulatory compliance, security effectiveness, or fitness for a high-impact purpose.

### 63. Documentation of Model Evaluation Limitations and Evidence Boundaries

Evaluation documentation should explain not only what the assessment established but also what it did not establish.

A test result is always bounded by its methodology, data, assumptions, environment, metrics, and execution conditions. Presenting a limited result as proof of a broader property can lead to unsupported assurance claims.

For example, successful testing against a defined set of adversarial prompts does not prove that a generative AI application is resistant to every prompt-injection technique. Testing a classifier on a representative historical dataset does not establish that performance will remain unchanged after a major change in the operating population.

An evaluation record should therefore document:

**63.1 Scope boundaries**

Identify the features, behaviors, risks, and operating conditions covered by the assessment.

**63.2 Exclusions**

Record material aspects that were not evaluated and explain why they were excluded.

**63.3 Methodological constraints**

Describe limitations in the test method, metrics, data, sample size, or execution environment.

**63.4 Uncertainty**

Explain relevant uncertainty in the observed results and any constraints on interpretation.

**63.5 Generalization limitations**

Identify conditions under which the results may not apply to other populations, configurations, or environments.

**63.6 Residual concerns**

Record material questions that remain unresolved after the assessment.

**63.7 Reliance restrictions**

Specify which conclusions may be drawn from the evidence and which broader claims are not justified.

These limitations should be reflected in the model's risk assessment and approval conditions when material.

An assurance conclusion should be proportionate to the strength and scope of the evidence. The absence of a detected defect should not automatically be described as proof that no defect exists.

### 64. Documentation of Model Ownership, Accountability, and Delegation

Model ownership documentation identifies the roles responsible for decisions and activities throughout the model lifecycle.

Clear ownership is necessary because documentation tasks often cross functional boundaries. Engineering may control technical records, business teams may define intended use, risk teams may assess residual risks, and compliance functions may interpret applicable obligations.

The organization should distinguish between ownership of the model, ownership of individual documents, ownership of specific risks, and authority to approve deployment.

These responsibilities may be assigned to different people or functions.

A governance record should identify:

- The accountable model owner.
- The business or use-case owner.
- The technical owner or development team.
- Owners of relevant data sources and dependencies.
- The responsible risk owner.
- Required security, privacy, and compliance reviewers.
- The approval authority.
- Delegation arrangements and their limits.
- Escalation paths for unresolved issues.
- Succession or reassignment procedures when ownership changes.

Delegation should not create ambiguity about accountability. A person may be responsible for preparing a validation report without having authority to accept the residual risk identified in that report.

Similarly, a model owner may coordinate documentation maintenance but lack authority to waive a mandatory legal requirement or approve a high-impact deployment.

The organization should define how ownership changes are recorded and how the incoming owner receives the information needed to assume responsibility.

A periodic ownership review can identify models with vacant owners, outdated contacts, conflicting assignments, or unclear approval authority.

Where an owner leaves the organization or a supplier relationship ends, the documentation process should ensure that responsibility is reassigned and that access to relevant records is maintained.

### 65. Documentation Quality Metrics and Control Thresholds

Documentation quality metrics enable management to monitor the health of the documentation program and identify areas requiring intervention.

The metrics selected should correspond to defined control objectives and should distinguish between administrative completion and substantive documentation quality.

Useful measures include:

- Percentage of models with a current approved documentation baseline.
- Percentage of required artifacts with valid evidence references.
- Percentage of material changes accompanied by required documentation updates.
- Number of production models with unresolved mandatory documentation gaps.
- Number of overdue reviews by model risk category.
- Percentage of sampled records with consistent model identifiers.
- Average time to remediate documentation findings.
- Number of repeated documentation deficiencies.
- Percentage of retired models with completed archival records.
- Percentage of critical documentation controls tested within the planned period.

Management should define thresholds and escalation conditions appropriate to the organization's risk appetite and obligations.

For example, the organization may require that every production model subject to mandatory approval has an identifiable approved baseline. A failure to meet that requirement may trigger immediate escalation rather than being treated as a minor percentage deviation.

Metrics should be interpreted carefully. A high documentation completion rate can coexist with poor evidence quality, inaccurate descriptions, or weak operational controls.

The organization should therefore combine quantitative metrics with qualitative assessment, risk-based sampling, and verification of underlying evidence.

Where a metric deteriorates, management should investigate the cause rather than merely instruct teams to improve the reported number. Repeated overdue reviews may indicate inadequate ownership, poorly designed workflows, unrealistic review schedules, or insufficient resources.

### 66. Documentation Exception Management and Remediation Tracking

Documentation exception management provides a controlled mechanism for recording and resolving situations in which required information or controls are missing, inaccurate, outdated, or not yet available.

A deficiency should not disappear from governance reporting simply because a team has acknowledged it or opened a remediation ticket.

The process should preserve the relationship between the original requirement, the identified gap, the risk assessment, the corrective action, and the evidence demonstrating closure.

A controlled remediation workflow should include:

```
Documentation Deficiency Identified
                |
                v
Requirement and Affected Model Confirmed
                |
                v
Severity and Risk Impact Assessed
                |
                v
Owner and Remediation Deadline Assigned
                |
                v
Immediate Restrictions Applied if Required
                |
                v
Corrective Action Implemented
                |
                v
Closure Evidence Reviewed
                |
                v
Deficiency Closed or Reopened
```

Each remediation record should identify the deficiency, root cause where known, owner, deadline, required action, risk implications, and closure criteria.

Closure should be based on evidence that the deficiency has been corrected, not merely on the submission of an updated document.

For example, if a missing model version caused evaluation evidence to be associated with the wrong release, the corrective action may require updating the documentation, validating the version mapping, correcting affected approval records, and reviewing whether other models have the same problem.

Remediation should also address systemic causes. Repeated failures to update documentation after configuration changes may indicate that the change-management workflow does not enforce documentation review.

Where remediation is delayed, the responsible authority should reassess the risk and determine whether the existing exception remains acceptable. High-risk or mandatory deficiencies may require deployment restrictions, escalation, or suspension.

### 67. Independent Review of Model Documentation

Independent review provides an additional level of assurance that model documentation is reliable and that material governance decisions are supported by appropriate information.

The degree of independence required depends on the review's purpose, the model's risk, the organization's governance framework, and applicable obligations.

Technical peer review, risk review, compliance review, independent model validation, and internal audit are different activities. They may examine overlapping evidence but have different responsibilities and levels of independence.

A review should establish whether the documentation accurately describes the model, supports its intended use, addresses material risks, and provides evidence for relevant decisions.

Reviewers may assess:

- Model identity and configuration consistency.
- Alignment between intended use and evaluation scope.
- Completeness of material risk and limitation records.
- Adequacy of supporting evidence.
- Compliance with internal documentation requirements.
- Traceability between risks, controls, tests, and approvals.
- Treatment of unresolved findings and exceptions.
- Appropriateness of retention and access controls.
- Whether the deployment matches the approved baseline.
- Whether previous findings have been effectively remediated.

Independence should not be assumed merely because a different person signs the document. The reviewer should have sufficient competence, access to relevant evidence, and freedom from inappropriate conflicts of interest.

Where independent validation is required, the organization should define the separation between development responsibilities and validation responsibilities.

Internal audit should retain appropriate independence from the operational activities it evaluates. It may assess documentation controls, inspect model records, test selected controls, and report deficiencies, but should not ordinarily assume responsibility for preparing or approving the operational documentation that it later audits.

### 68. Management Review of Model Documentation Effectiveness

Management review evaluates whether the model documentation program remains suitable, adequate, and effective in supporting organizational objectives and governance obligations.

The review should consider both process performance and substantive risk. A program may achieve high completion rates while failing to capture material changes, preserve reliable evidence, or support meaningful oversight.

Management review inputs may include:

- Documentation completeness and currency metrics.
- Material documentation deficiencies.
- Open and overdue remediation actions.
- Audit findings and independent review results.
- Incidents involving missing or inaccurate documentation.
- Changes in the model inventory and risk profile.
- New or amended legal and regulatory requirements.
- Supplier transparency and documentation issues.
- Retention, access, and integrity-control weaknesses.
- Resource constraints and recurring workflow problems.

Management decisions may include changes to documentation standards, additional resources, revised ownership, improved automation, new review requirements, or restrictions on models with unresolved gaps.

The review should produce an attributable record of decisions, assigned actions, deadlines, and follow-up requirements.

Management should distinguish between accepting a documented risk and determining that a documentation control is effective. A risk acceptance decision may authorize a specific deviation within the decision-maker's authority, but it does not prove that the underlying control operated as designed.

The effectiveness of management review should be evaluated by checking whether decisions lead to appropriate action and whether recurring issues are reduced over time.

### 69. Model Documentation in Internal Audit Planning

Model documentation supports internal audit planning by helping auditors understand the organization's AI inventory, governance model, risk exposure, control environment, and available evidence.

The documentation should allow auditors to identify the models within scope, understand their intended purposes, assess relevant risk factors, and determine which controls require testing.

An AI documentation review may be included in an audit of AI governance, information security, model risk management, regulatory compliance, data governance, or a specific business process.

Planning activities may include:

**69.1 Establishing the audit population**

Obtain the relevant model inventory and determine whether it is complete enough to support audit scoping.

**69.2 Understanding model risk**

Review intended use, impact, risk classification, dependencies, and material limitations.

**69.3 Identifying applicable requirements**

Map relevant policies, standards, regulations, contracts, and governance decisions to the audit scope.

**69.4 Understanding the control environment**

Identify the controls governing documentation creation, review, approval, change, retention, and access.

**69.5 Identifying assurance gaps**

Consider missing records, inconsistent versions, unresolved exceptions, and previous findings.

**69.6 Designing procedures**

Determine which records to inspect, which controls to test, and which evidence sources are necessary.

**69.7 Defining reporting criteria**

Establish the requirements against which documentation and control performance will be evaluated.

Audit planning should not assume that the documentation inventory is complete merely because a formal register exists. Auditors may need to reconcile the register with production systems, procurement records, cloud services, application inventories, or other sources to identify potentially unregistered AI models.

The scope should reflect the audit objective. A review of documentation controls may focus on record completeness and integrity, whereas an audit of a specific high-impact model may require deeper examination of technical, evaluation, and risk documentation.

### 70. Model Documentation in Regulatory Compliance Assessment

Model documentation supports regulatory compliance assessment by providing the records needed to determine which obligations apply, how they have been implemented, and what evidence supports the organization's compliance position.

The organization should maintain a structured relationship between applicable requirements and the documentation or records that demonstrate how those requirements are addressed.

A compliance mapping may include:

| Field                   | Purpose                                                                         |
| ----------------------- | ------------------------------------------------------------------------------- |
| Requirement ID          | Identifies the relevant legal, regulatory, contractual, or internal requirement |
| Source                  | Identifies the authoritative requirement source                                 |
| Applicability rationale | Explains why the requirement applies or does not apply                          |
| Responsible owner       | Identifies the accountable function                                             |
| Required documentation  | Lists the relevant artifact or record                                           |
| Supporting evidence     | Links evidence that substantiates the compliance claim                          |
| Assessment status       | Records the current compliance assessment                                       |
| Identified gap          | Describes missing or insufficient evidence                                      |
| Remediation action      | Identifies the planned corrective action                                        |
| Review date             | Records when applicability and implementation were last assessed                |

Applicability analysis is especially important where regulatory obligations depend on the AI system's classification, intended purpose, organizational role, or deployment context.

The compliance record should distinguish between a requirement that does not apply, a requirement that applies but is not yet implemented, and a requirement for which implementation has not been adequately evidenced.

These states have different implications and should not be collapsed into a generic "not applicable" or "complete" status.

Where legal interpretation is required, the organization should involve appropriately qualified legal or compliance personnel. A model documentation template cannot independently determine whether a legal obligation applies.

For EU AI Act-related assessments, organizations should map applicable requirements to the relevant system classification, role, and legal provisions, then maintain the technical documentation and records required by those provisions. Internal documentation may provide additional evidence but should not be assumed to replace legally prescribed documentation.

### 71. Evidence Traceability Testing Across Model Documentation

Evidence traceability testing determines whether an organization can follow the relationship between a material claim, the underlying requirement, the model version, the supporting evidence, and the resulting governance decision.

This is particularly important when information is distributed across several systems or maintained by different teams.

A traceability test should select a claim or requirement and attempt to follow the complete evidence chain.

For example, an auditor may select the statement that a model satisfies a defined robustness criterion and determine whether the documentation identifies:

1. The requirement and acceptance criterion.
2. The model and configuration tested.
3. The evaluation method and test conditions.
4. The supporting execution records and results.
5. Any relevant limitations or failed cases.
6. The reviewer's conclusion.
7. The approval decision relying on the evidence.
8. Subsequent changes that may affect the conclusion.

The auditor should verify that the evidence supports the claim rather than merely confirming that related documents exist.

Traceability testing can also begin with an observed failure. If an incident occurred, the reviewer may trace the incident to the affected deployment, documented limitations, risk assessment, relevant control requirements, and prior approval decision.

A complete traceability chain helps establish whether the issue was previously identified, whether required safeguards existed, and whether governance decisions were supported by the information available at the time.

Traceability gaps should be recorded with sufficient detail to identify the missing relationship. A broken link may result from poor repository design, inconsistent identifiers, deleted evidence, or inadequate lifecycle procedures.

Remediation should address both the missing reference and the underlying cause where appropriate.

### 72. Documentation Integrity and Authenticity Verification

Documentation integrity controls protect records against unauthorized modification, deletion, substitution, or loss of historical context.

Authenticity concerns whether a record can reasonably be attributed to the person, system, or process claimed to have produced it.

These properties are essential when documentation is used to support approvals, compliance assessments, incident investigations, and audit conclusions.

Potential integrity and authenticity controls include:

- Role-based write permissions.
- Version-controlled repositories.
- Attributable approval workflows.
- Time-stamped change histories.
- Cryptographic hashes for suitable artifacts.
- Digital signatures where appropriate.
- Immutable or tamper-evident storage for selected records.
- Separation of duties for material approval activities.
- Periodic verification of stored artifacts.
- Controlled export and archival procedures.

The appropriate combination depends on the sensitivity and risk of the documentation.

A cryptographic hash can help identify whether a file has changed relative to a known fingerprint. It does not establish that the original file was accurate, that the person who created it was authorized, or that the model described in the file was compliant.

Similarly, an electronic signature may demonstrate approval attribution, but the approval's substantive adequacy depends on the review process and supporting evidence.

Integrity controls should cover not only individual documents but also the relationships among them. An unchanged approval document may become misleading if its referenced model version is replaced or if the underlying evidence is silently redirected to another artifact.

The organization should therefore preserve stable references and historical relationships, especially for records associated with material governance decisions.

### 73. Documentation Controls for External Model Updates and Provider Changes

External model providers may update model behavior, supported features, service interfaces, safety mechanisms, or availability without the deploying organization controlling the underlying implementation.

Such changes can affect the validity of existing documentation and approval decisions.

Organizations should establish a process for identifying and assessing provider changes that may materially affect the deployed model or service.

The process should address:

- Provider release notices and change communications.
- Available model-version identifiers.
- Changes to service terms or technical interfaces.
- Changes to data handling and retention arrangements.
- Changes to safety features or supported capabilities.
- Changes to service availability or performance.
- Relevant security advisories.
- Changes to available technical documentation.
- Impact on evaluation assumptions and acceptance criteria.
- Required testing, approval, and documentation updates.

The organization should document what the provider has communicated and distinguish those statements from independently verified results.

Where the provider offers a stable version or explicit release identifier, the organization should record it when available. Where the service is updated without sufficient version transparency, the organization should document the limitation and determine what monitoring, testing, contractual safeguards, or usage restrictions are necessary.

For example, if a provider changes a language model used to summarize sensitive internal documents, the organization should assess whether the change affects output quality, confidentiality safeguards, prompt behavior, tool interactions, or previously established acceptance criteria.

A provider update should not automatically be treated as harmless merely because the service retains the same product name.

The change assessment should determine whether the existing documentation remains valid, which claims require revalidation, and whether continued operation is acceptable under the revised conditions.

### 74. Documentation Governance for Model Replacement and Migration

Model replacement and migration occur when an organization substitutes one model, provider, deployment environment, or technical architecture for another.

The process may be driven by performance improvements, security concerns, cost, provider changes, end-of-life announcements, regulatory requirements, or operational resilience needs.

Replacement should be treated as a governed transition rather than a simple technical substitution.

Documentation should identify the previous model, replacement model, business rationale, migration scope, dependencies, evaluation requirements, approval decisions, and retirement arrangements.

The transition assessment should consider:

- Differences in intended capabilities and limitations.
- Differences in data requirements and processing.
- Changes in interfaces and integration behavior.
- Changes in performance and acceptance criteria.
- Security and privacy implications.
- Changes to supplier and contractual dependencies.
- Operational continuity and fallback arrangements.
- Impact on users and downstream systems.
- Required regression testing and validation.
- Changes to risk assessments and controls.
- Approval requirements for the replacement.
- Retention of historical records from the previous model.

A replacement model should not automatically inherit the previous model's approval. Even when the business use case remains unchanged, the replacement may have different error patterns, data dependencies, security characteristics, or operational constraints.

The organization should establish whether the replacement meets the requirements of the intended use and whether any new risks require treatment.

A migration record should preserve the relationship between the previous and replacement models so that historical decisions, incidents, and outcomes remain attributable to the correct model.

Following migration, the organization should verify that inventories, configuration records, risk registers, monitoring systems, supplier records, and operational procedures have been updated consistently.

### 75. Documentation Governance for Model Suspension and Emergency Shutdown

Model suspension or emergency shutdown documentation records the conditions under which a model is restricted or taken out of service and the decisions and actions associated with that intervention.

Suspension may be necessary when a model exhibits severe performance degradation, a security incident occurs, required controls fail, material information becomes unavailable, or continued operation presents unacceptable risk.

The organization should define the authority and criteria for suspension before an emergency occurs.

Documentation should establish:

- Conditions that trigger suspension or shutdown.
- Roles authorized to initiate or approve the action.
- Immediate containment and communication procedures.
- Dependencies and business processes affected.
- Fallback or manual operating arrangements.
- Evidence to preserve before or during shutdown.
- Criteria for resumption of service.
- Required reassessment and approval.
- Incident reporting and corrective action requirements.
- Records of the final decision and implementation.

For example, if a model begins producing outputs that create a material security or safety concern, the organization may need to disable an endpoint, revoke tool permissions, or redirect the workflow to human review.

The documentation should distinguish between the decision to suspend, the technical action taken, and the subsequent determination that service may resume.

Resumption should be based on defined criteria, such as successful remediation, required testing, updated documentation, risk reassessment, and authorized approval.

The organization should preserve relevant evidence and historical records so that the shutdown and subsequent recovery can be independently reviewed.

### 76. Documentation Governance for AI Model Portfolio Management

Model portfolio documentation provides a consolidated view of the organization's models, their owners, intended purposes, lifecycle states, dependencies, risk classifications, and documentation status.

A portfolio view is important because documentation deficiencies may be systemic rather than limited to one model.

For example, multiple models may use the same external provider, depend on the same data platform, or follow the same approval workflow. A provider-level change or a weakness in the shared workflow may therefore affect many models simultaneously.

Portfolio-level documentation should support:

- Identification of all in-scope models.
- Risk-based prioritization of documentation work.
- Monitoring of ownership and lifecycle status.
- Identification of common dependencies and providers.
- Assessment of shared control weaknesses.
- Tracking of documentation completeness and currency.
- Identification of overdue reviews and unresolved exceptions.
- Planning of audits and independent assurance.
- Assessment of retirement and replacement needs.
- Reporting to governance committees and management.

Portfolio reporting should distinguish between model-level status and shared-control status. Ten models may each have complete documentation while all ten rely on an inadequately assessed provider.

Conversely, a single model may have a documentation deficiency that does not affect the rest of the portfolio.

The organization should therefore combine model-level metrics with analysis of common dependencies, shared risks, and common control processes.

Portfolio information should be reconciled against relevant enterprise inventories and operational sources to identify models that may have been deployed outside the formal governance process.

A complete portfolio view enables management to allocate resources according to risk and address systemic documentation weaknesses before they produce broader assurance failures.

### 77. Integrating Documentation With Enterprise Change and Release Management

Enterprise change and release management provide a mechanism for ensuring that model documentation remains aligned with the actual implementation throughout controlled deployment activities.

The integration should make documentation updates a defined part of the release process rather than an optional administrative task performed after implementation.

A release workflow should identify which documentation artifacts are affected by the proposed change, which tests must be completed, which approvals are required, and which evidence must be retained before the release can proceed.

For example, a change to a model's inference configuration may require:

- An updated configuration baseline.
- An impact assessment.
- Regression testing.
- A review of relevant performance and security criteria.
- Updated risk information if the change affects material risks.
- Approval by the appropriate authority.
- A deployment record identifying the released version.
- Post-deployment verification.

The workflow should prevent the release process from treating documentation completion as a purely formal checkbox. The relevant information must be accurate and sufficiently reviewed.

Emergency changes may require expedited procedures, but the organization should define the permitted scope, safeguards, retrospective review, and documentation deadlines in advance.

The release record should establish which documentation baseline and approval decision applied to the deployed implementation.

Integration with enterprise change management is particularly valuable when model changes are implemented through automated deployment pipelines. It allows the organization to link release artifacts, configuration identifiers, test results, and approvals without relying entirely on manual copying.

### 78. Documentation Governance for Multi-Model and Composite AI Systems

Composite AI systems combine multiple models or AI-enabled components to deliver a broader business capability.

Examples include systems that combine document extraction, classification, retrieval, language generation, recommendation, and decision support.

In these environments, documenting each model independently may be necessary but insufficient. The organization must also document the relationships and dependencies that determine the behavior of the complete system.

System-level documentation should identify:

- The models and components involved.
- The purpose of each component.
- The data and control flows between components.
- Dependencies and shared infrastructure.
- The sequence in which outputs are processed.
- Interfaces and trust boundaries.
- Error propagation and fallback behavior.
- System-level evaluation criteria.
- Security and privacy controls across components.
- Ownership and responsibility for each relevant component.
- The effect of changing or replacing a component.

For example, an application may use one model to extract information from documents, another to classify the extracted content, and a third to generate a summary. Each model may perform adequately in isolation, while errors in extraction propagate into classification and then into the final summary.

System-level documentation should explain these dependencies and identify how the organization evaluates the combined workflow.

It should also establish whether component-level approvals remain valid when the components are integrated into a new application or used in a different decision-making context.

The organization should maintain traceability between component documentation and system documentation. A change to one model may require reassessment of the composite system even when the changed model's own documentation appears complete.

### 79. Documentation Governance for AI Model Decommissioning Across Multiple Systems

Decommissioning a model across an enterprise can be more complex than removing a single deployment.

The same model may be used by multiple applications, business units, APIs, scheduled processes, or regional environments. Some integrations may be undocumented or maintained by teams outside the original development group.

A controlled decommissioning process should identify the full scope of use and verify that all relevant deployments and dependencies have been addressed.

Documentation should cover:

- The model's complete inventory and deployment references.
- Known consuming applications and integrations.
- Business owners responsible for affected processes.
- Replacement or fallback arrangements.
- Revocation of relevant access and credentials.
- Removal of scheduled jobs and obsolete endpoints.
- Treatment of cached outputs and derived artifacts where applicable.
- Retention and disposal of model artifacts.
- Archival of required historical documentation.
- Confirmation from relevant system owners.
- Final reconciliation of inventory and deployment records.

The organization should not assume that changing the model's status to "retired" in the AI inventory proves that all operational uses have ended.

Verification may require reconciling inventory records with API gateways, deployment platforms, service catalogs, application configurations, and other relevant sources.

Where an undocumented integration is discovered during retirement, the organization should assess its risk, identify the responsible owner, and determine whether continued use is authorized.

The retirement record should include evidence that the required decommissioning activities were completed and that any remaining uses have been explicitly addressed.

### 80. Building an Evidence-Based Model Documentation Assurance Program

An evidence-based model documentation assurance program evaluates whether the documentation framework and its associated controls provide reliable support for AI governance, risk management, compliance, security, and operational oversight.

The program should assess both the design of documentation processes and their actual implementation across the model portfolio.

It should not rely exclusively on policy reviews, completed templates, or management attestations. Assurance should include examination of underlying records and verification that documented claims correspond to the relevant model state and control activities.

A practical assurance program should include the following components.

**80.1 Defined assurance objectives**

Establish which aspects of documentation are being assessed, such as completeness, accuracy, version traceability, evidence quality, approval integrity, or regulatory alignment.

**80.2 Risk-based scope**

Prioritize models and controls according to risk, impact, regulatory relevance, change activity, incident history, and previous findings.

**80.3 Defined criteria**

Identify the policies, control requirements, contractual commitments, and applicable legal obligations against which documentation will be evaluated.

**80.4 Reliable evidence sources**

Use authoritative registries, controlled repositories, deployment records, evaluation artifacts, approval records, and other relevant evidence.

**80.5 Testing methodology**

Define procedures for document inspection, version reconciliation, evidence traceability testing, control sampling, and independent verification.

**80.6 Findings and classification**

Record deficiencies according to their significance, affected population, consequences, and required remediation.

**80.7 Corrective action and follow-up**

Assign accountable owners, establish deadlines, verify remediation, and escalate overdue or ineffective actions.

**80.8 Management reporting**

Report meaningful measures of documentation quality, material gaps, recurring control weaknesses, and residual risk.

**80.9 Continuous improvement**

Use audit findings, incidents, regulatory changes, and operational feedback to improve the documentation framework.

The assurance program should distinguish between the presence of documentation, the quality of documentation, and the effectiveness of the underlying controls.

A model may have a complete documentation package that accurately describes an ineffective security control. In that situation, the documentation may be adequate as a record, but the underlying security control may still require remediation.

Conversely, a control may operate correctly in practice while the documentation needed to demonstrate its operation is missing. That situation creates a separate governance and assurance deficiency.

An effective assurance program identifies both conditions and ensures that findings are assigned to the appropriate owners.

Ultimately, model documentation assurance should establish whether the organization can reliably demonstrate what a model is, how it is used, which risks and controls apply, what evidence supports its approval, how changes are governed, and whether its current operation remains within the conditions under which it was authorized.

## Part 4 — Enterprise Implementation, Practical Documentation, Maturity, and Continuous Improvement

### 81. Translating Model Documentation Requirements Into Operational Practice

A model documentation framework becomes effective only when its requirements are incorporated into the organization's normal AI lifecycle processes.

A documentation requirement should not remain an isolated statement in a policy. It should specify what information must be produced, who is responsible for producing it, when it must be available, how its accuracy is verified, and where the approved record is maintained.

For example, a requirement stating that every production model must have documented limitations is incomplete unless the organization also defines:

- Which limitations must be recorded.
- Who validates the technical content.
- Who determines the business implications.
- Which approval is required before deployment.
- How limitations are communicated to users.
- When the documentation must be reassessed.
- What happens when the documentation is missing or materially inaccurate.

The operational objective is to transform documentation from a passive repository of information into a controlled component of model governance.

### 82. Establishing Minimum Documentation Requirements by Model Type

Not every model requires the same documentation depth. Requirements should reflect the model's purpose, complexity, impact, autonomy, deployment context, and applicable obligations.

A practical approach is to define documentation profiles.

| Model or System Type                  | Core Documentation Focus                                                                                             |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Traditional predictive model          | Training data, features, methodology, performance, assumptions, limitations                                          |
| Classification model                  | Class definitions, thresholds, error rates, validation populations, decision implications                            |
| Generative AI application             | Model provider, version, intended use, prompts, grounding sources, output limitations, safety evaluations            |
| Retrieval-augmented generation system | Knowledge sources, ingestion process, indexing, retrieval configuration, access boundaries, freshness                |
| AI agent                              | Model configuration, available tools, permissions, action boundaries, approval requirements, intervention procedures |
| Multimodal model                      | Supported modalities, data-processing paths, modality-specific limitations, evaluation coverage                      |
| High-impact decision system           | Intended purpose, affected populations, validation evidence, human oversight, limitations, accountability            |
| Third-party model service             | Provider information, available technical documentation, contractual commitments, versioning, assurance limitations  |

These profiles should establish minimum expectations rather than rigidly prescribing identical documentation for every implementation.

Additional documentation should be required when a model introduces unusual risks, material uncertainty, complex dependencies, or significant consequences for affected stakeholders.

### 83. Defining a Minimum Model Documentation Baseline

An enterprise should establish a minimum documentation baseline that applies to all models within its defined governance scope.

A baseline may include the following elements:

1. **Identification:** Model identifier, name, version, owner, status, and associated AI system.
2. **Purpose:** Intended use, business objectives, users, and prohibited or unsupported uses.
3. **Architecture:** Model type, deployment arrangement, dependencies, and relevant system boundaries.
4. **Data:** Data sources, provenance, preparation, relevant characteristics, and known limitations.
5. **Development:** Development methodology, significant assumptions, configuration, and material design decisions.
6. **Evaluation:** Evaluation methodology, test conditions, datasets or test populations, metrics, and results.
7. **Limitations:** Known weaknesses, uncertainty, operating constraints, and conditions under which performance may deteriorate.
8. **Risk and controls:** Relevant risks, mitigations, residual concerns, and required oversight.
9. **Deployment:** Approved environment, release version, configuration, and deployment authorization.
10. **Operation:** Monitoring requirements, performance thresholds, review frequency, and escalation conditions.
11. **Change history:** Material modifications, approvals, evaluation results, and superseded versions.
12. **Retirement:** Decommissioning decision, dependencies, retention obligations, and final disposition.

The baseline should be adapted to the organization's risk classification and applicable requirements. Where an element is not applicable, the rationale should be documented rather than silently omitting it.

### 84. Building a Model Documentation Responsibility Matrix

Documentation quality depends on clearly assigned responsibilities.

The organization should identify who prepares, validates, approves, maintains, and uses each material documentation artifact.

A responsibility matrix may look like this:

The precise allocation will differ across organizations.

Where one individual performs multiple roles, the organization should consider whether independent review is still necessary. A model developer should not automatically be treated as an independent validator of the same model's critical evaluation claims.

### 85. Embedding Documentation Into AI Lifecycle Gates

Model documentation should be integrated into formal lifecycle decisions.

A model should not progress through a governance gate merely because its technical implementation is complete.

```

       ↓
Documentation Prepared
       ↓
Technical Validation
       ↓
Risk and Compliance Review
       ↓
Documentation Completeness Check
       ↓
Authorized Approval
       ↓
Production Deployment
       ↓
Operational Review
       ↓
Change or Retirement
```

At each gate, the organization should define mandatory documentation, acceptance criteria, authorized approvers, and exception procedures.

For example, a production-release gate may require:

- An approved model identifier and version.
- Documented intended use and limitations.
- Completed evaluation evidence.
- Reviewed security and privacy considerations.
- Approved operational monitoring requirements.
- Defined rollback or suspension arrangements.
- Traceability between the evaluated model and the release candidate.

A failed documentation gate should result in remediation, formal risk-based exception approval where permitted, or a decision not to proceed.

### 87. Establishing Documentation Acceptance Criteria

A completed document is not necessarily an acceptable document.

Acceptance criteria should determine whether the documentation is sufficiently complete, accurate, consistent, current, understandable, and supported by evidence.

For example:

| Criterion             | Acceptance Question                                                                 |
| --------------------- | ----------------------------------------------------------------------------------- |
| Completeness          | Are all mandatory sections addressed?                                               |
| Accuracy              | Does the content match the actual model and its configuration?                      |
| Traceability          | Can material claims be linked to supporting evidence?                               |
| Version alignment     | Does the documentation identify the model version that was evaluated and approved?  |
| Clarity               | Can intended readers understand the purpose, limitations, and operating conditions? |
| Consistency           | Do related documents agree on material facts?                                       |
| Currency              | Has the document been reviewed after relevant changes?                              |
| Accountability        | Are the author, reviewer, owner, and approval status identifiable?                  |
| Limitation disclosure | Are known weaknesses and evaluation boundaries clearly recorded?                    |
| Accessibility         | Can authorized stakeholders retrieve the information when needed?                   |

Acceptance criteria should be measurable wherever practical.

For instance, requiring every production model to have an identified owner is more testable than requiring documentation to be “well maintained.” Requiring an explicit rationale for unassessed evaluation scenarios is more meaningful than merely requiring an evaluation section to exist.

### 88. Distinguishing Mandatory, Conditional, and Optional Documentation

Documentation requirements should distinguish between three categories.

**Mandatory documentation** is required for every model within the relevant scope.

Examples include model identification, ownership, intended purpose, lifecycle status, and approved version.

**Conditional documentation** is required when a specific characteristic, risk, use case, or obligation applies.

Examples include subgroup performance analysis, specialized safety testing, human-oversight procedures, or detailed third-party assurance limitations.

**Optional documentation** provides additional information that may improve understanding or operational effectiveness but is not universally required.

Examples may include supplementary visualizations, additional research notes, or extended technical commentary.

This distinction prevents two opposite problems: under-documenting material risks and imposing unnecessary documentation burdens on low-risk systems.

Conditional requirements should have explicit applicability criteria. If a required artifact is considered not applicable, the decision and rationale should be recorded and, where appropriate, reviewed.

### 89. Managing Model Documentation Exceptions

Exceptions occur when a documentation requirement cannot be met, is temporarily incomplete, or does not apply to a particular model.

An exception should not be treated as an informal agreement to ignore a requirement.

A controlled exception record should include:

- The requirement that cannot be met.
- The affected model and documentation artifact.
- The reason for the exception.
- The associated risk and potential consequences.
- Available compensating controls.
- The accountable risk owner.
- The authorized approver.
- The permitted duration or review date.
- The remediation plan, if required.
- The conditions that trigger escalation or suspension.

For example, a third-party provider may not disclose proprietary training details. The organization should record the unavailable information, explain why it cannot be obtained, assess the resulting assurance limitation, identify alternative evidence, and determine whether the remaining uncertainty is acceptable for the intended use.

An exception does not automatically make a model unacceptable. Equally, management approval does not eliminate the underlying risk or remove applicable legal obligations.

### 90. Managing Proprietary and Confidential Model Information

Model documentation can contain commercially sensitive or security-relevant information.

Examples include:

- Proprietary architecture details.
- Model weights or configuration.
- Training-data descriptions.
- Security testing results.
- System prompts and internal instructions.
- Vulnerability details.
- Supplier-confidential information.
- Information about security boundaries and defensive controls.

Organizations should classify documentation according to its sensitivity and establish appropriate access, storage, transmission, and retention controls.

Access should be granted according to business need and authorized responsibilities. Sensitive documentation should not be distributed broadly merely because it is required for governance.

At the same time, confidentiality controls should not prevent legitimate oversight. Authorized risk owners, compliance personnel, auditors, regulators, or other entitled parties may require sufficient information to perform their responsibilities.

Where full technical disclosure is unavailable or inappropriate, the organization should consider controlled access, redacted documentation, summaries, independent assurance, or other suitable mechanisms. The documentation should make clear what was withheld and how that restriction affects the conclusions that can be supported.

### 91. Governing Model Documentation in Third-Party AI Services

Third-party AI services create a particular documentation challenge because the organization may not control model development, training data, internal testing, or release decisions.

The organization should distinguish between information it can produce directly and information it must obtain from a provider.

Potential documentation sources include:

- Provider model cards or technical reports.
- Product and service specifications.
- Contractual commitments.
- Security and assurance reports.
- Provider statements about intended use and limitations.
- Evaluation results available to customers.
- Version and change notifications.
- Service availability and incident information.
- Data-processing and retention terms.
- Supplier risk assessments.

Provider documentation should be assessed for applicability rather than accepted at face value.

A document describing a model family may not establish the properties of the exact version or configuration used by the organization. A general security certification may not provide assurance about model accuracy, fairness, robustness, or suitability for a particular business purpose.

Where provider information is insufficient, the organization should document the limitation, assess the potential consequences, identify additional evidence or controls, and determine whether the service remains appropriate for the intended use.

### 92. Documentation for Model Updates and Version Transitions

A model update can change performance, output characteristics, limitations, security behavior, or compatibility with the surrounding application.

Documentation should preserve the relationship between each relevant model version and its approval status.

A version transition record should identify:

1. The previous and proposed versions.
2. The reason for the change.
3. The expected benefits and potential risks.
4. The changes in functionality, configuration, or behavior.
5. The evaluation performed against relevant acceptance criteria.
6. The updated limitations and operating assumptions.
7. The impact on users, downstream systems, and controls.
8. The approval decision and responsible authorities.
9. The deployment date and rollback arrangements.
10. The documentation artifacts replaced or amended.

For externally managed models, the organization should record provider-reported version information and any limitations in its ability to independently verify the change.

Where a provider changes a model without adequate notice, the organization should determine whether additional evaluation, temporary restrictions, increased monitoring, or suspension is necessary.

### 93. Maintaining Traceability Between Model Documentation Artifacts

A model's documentation is usually distributed across multiple records.

For example, the model description may refer to an evaluation report, which refers to a dataset version, which refers to a development release and an approval record.

Without explicit relationships, reviewers may struggle to establish whether the records describe the same model and evaluation context.

A traceability structure may look like this:

```
AI System ID
     ↓
Model ID
     ↓
Model Version
     ↓
Development / Configuration Record
     ↓
Evaluation Record
     ↓
Risk Assessment
     ↓
Approval Decision
     ↓
Deployment Record
     ↓
Monitoring Requirements
     ↓
Change and Incident Records
```

Each artifact should have a stable identifier, version or revision information where appropriate, an owner, and a defined relationship to the relevant model.

Traceability should support both forward and backward navigation. A reviewer should be able to move from a deployed model to its supporting approval evidence, and from an evaluation result to the exact model version and intended use to which the result applies.

### 94. Managing Conflicting Documentation

Conflicts may arise when different artifacts describe the same model differently.

For example:

- The model card identifies one intended use, while the deployment specification identifies another.
- The evaluation report records a threshold that differs from the production configuration.
- The provider documentation identifies a different model version from the operational inventory.
- The risk assessment assumes mandatory human review, while the operating procedure permits automated execution.
- The monitoring plan uses performance limits that differ from those approved during validation.

These inconsistencies should be investigated rather than resolved by automatically selecting the most recent-looking document.

A reconciliation process should:

1. Identify the conflicting statements.
2. Determine the authoritative source for each type of information.
3. Verify the actual deployed configuration where relevant.
4. Establish whether the discrepancy reflects an approved change or a control failure.
5. Correct affected artifacts.
6. Assess whether prior approvals or risk decisions remain valid.
7. Record the resolution and required follow-up actions.

If the conflict cannot be resolved, the uncertainty should be documented and escalated according to its potential significance.

### 95. Using Documentation Metrics to Improve Quality

Documentation metrics can help management determine whether the documentation framework is operating effectively.

Useful measures may include:

| Metric                                  | What It Indicates                                                                         |
| --------------------------------------- | ----------------------------------------------------------------------------------------- |
| Mandatory documentation completion rate | Proportion of in-scope models with required artifacts completed                           |
| Documentation approval coverage         | Proportion of models with required approvals recorded                                     |
| Version alignment rate                  | Proportion of sampled models whose documentation matches the approved or deployed version |
| Overdue review rate                     | Proportion of documents past their required review date                                   |
| Traceability coverage                   | Proportion of material claims linked to supporting evidence                               |
| Exception aging                         | Duration of unresolved documentation exceptions                                           |
| Change-update timeliness                | Time taken to update documentation after material model changes                           |
| Reconciliation defect rate              | Frequency of material inconsistencies across documentation artifacts                      |
| Remediation closure rate                | Proportion of documentation-related findings closed and validated                         |
| Repeated finding rate                   | Frequency of recurring documentation deficiencies                                         |

Metrics should be interpreted carefully.

A high completion rate does not prove that documentation is accurate or useful. A low number of exceptions may indicate effective controls, but it may also indicate that teams are failing to record or escalate deficiencies.

Metrics should therefore be combined with sample-based quality reviews, stakeholder feedback, and evidence of actual documentation use.

### 96. Avoiding Documentation Theater

Documentation theater occurs when records are produced primarily to demonstrate apparent compliance rather than to support real governance decisions.

Typical indicators include:

- Repeated generic descriptions across unrelated models.
- Limitations copied from templates without technical validation.
- Evaluation reports that omit unfavorable results.
- Approval records created after deployment without explanation.
- Model cards that describe intended behavior but not observed behavior.
- Risk assessments that do not reflect known operational incidents.
- Documentation marked complete despite unresolved contradictions.
- Review dates updated without substantive reassessment.
- Evidence references that do not lead to retrievable records.

The solution is not simply to demand more documentation.

Organizations should test whether documentation is accurate, whether material claims are supported, whether decision-makers understand the information, and whether the records change when the underlying model changes.

A concise, evidence-supported model description can be more valuable than a lengthy document that conceals uncertainty or repeats generic statements.

### 97. Practical Example — Documentation for an Enterprise AI Assistant

Consider an organization deploying an AI assistant that answers employee questions using internal policies, HR information, and corporate documents.

The documentation package should establish:

**Model and system identity**

- The model and provider.
- The approved model version or service configuration.
- The application and retrieval components.
- The responsible business and technical owners.

**Data and retrieval**

- The knowledge sources available to the assistant.
- The process for ingesting and updating documents.
- Access-control assumptions.
- Relevant data-classification and retention requirements.
- Known gaps in source coverage or freshness.

**Evaluation**

- The test scenarios used to assess answer quality.
- Tests for incorrect or unsupported answers.
- Tests for unauthorized information retrieval.
- Relevant adversarial and prompt-injection scenarios.
- The acceptance criteria and observed results.
- The limits of the evaluation.

**Limitations and use restrictions**

- Situations where answers may be incomplete or inaccurate.
- Topics requiring authoritative human confirmation.
- Prohibited uses, such as treating an informational response as an approved HR decision where that is outside scope.
- Known limitations in source freshness and retrieval.
- Conditions requiring escalation to a human specialist.

**Operation and governance**

- Monitoring requirements.
- Review responsibilities.
- Model and knowledge-source change triggers.
- Incident reporting arrangements.
- Approval records.
- Suspension and rollback procedures.

Suppose the assistant is later connected to a restricted HR database. This is a material system change, even if the underlying language model remains unchanged.

The organization should update the relevant architecture, data-flow, access-control, risk, evaluation, and operational documentation. It should also determine whether additional approval is required before the new capability is enabled.

The example demonstrates that model documentation must describe the model in its actual operating context, including dependencies and capabilities that materially affect risk.

### 98. Practical Example — Documentation for an AI Agent

Consider an AI agent that can read emails, search internal documents, update CRM records, and send messages to customers.

Documentation should describe not only the model's capabilities but also the authority granted to the agent.

The documentation package should identify:

- Available tools and APIs.
- Permissions assigned to each tool.
- Data accessible to the agent.
- Permitted and prohibited actions.
- Conditions requiring human approval.
- Limits on automated transactions or communications.
- Handling of ambiguous or conflicting instructions.
- Controls against prompt injection and unauthorized tool use.
- Logging and monitoring requirements.
- Procedures for revoking access or suspending the agent.

The evaluation documentation should cover relevant action sequences, not merely isolated text responses.

For example, a test might assess whether the agent can be manipulated into sending confidential information to an unauthorized recipient. Another might examine whether the agent requests approval before executing a consequential CRM change.

If the agent receives new tools or broader permissions, its documentation must be reassessed. A model with unchanged weights can acquire a substantially different risk profile when its authority or operating environment changes.

### 99. Practical Example — Documentation for a Third-Party Foundation Model

Assume an organization uses a commercial foundation model through an external API and receives only limited information about its training data and internal architecture.

The organization should not invent missing technical details or imply that it independently validated information supplied solely by the provider.

Instead, it should distinguish clearly between:

| Information Category             | Documentation Treatment                                            |
| -------------------------------- | ------------------------------------------------------------------ |
| Independently verified facts     | Record the evidence and verification method                        |
| Provider statements              | Identify the provider and source document                          |
| Organization-specific evaluation | Record the test methodology, conditions, and results               |
| Assumptions                      | State the assumption and its relevance                             |
| Unavailable information          | Explain what is unavailable and why                                |
| Unverified claims                | Label the claim and describe the assurance limitation              |
| Residual uncertainty             | Assess the implications for the intended use and required controls |

The organization can then determine whether its own evaluations, contractual protections, operational controls, and independent assurance provide sufficient confidence for the intended application.

The documentation should support a defensible decision about suitability without claiming knowledge the organization does not possess.

### 100. Integrating Model Documentation With Enterprise GRC

Model documentation should connect to the organization's broader governance, risk, and compliance processes.

Relevant connections may include:

- AI inventory and ownership records.
- Enterprise risk registers.
- Security and privacy assessments.
- Regulatory obligation registers.
- Third-party risk management.
- Change and release management.
- Incident management.
- Internal audit and compliance assurance.
- Business continuity and operational resilience.
- Records management and retention.

The integration should avoid unnecessary duplication.

Where an authoritative risk record or approval exists in another system, model documentation may reference that record using a stable identifier rather than maintaining an inconsistent duplicate.

However, references must remain usable. The organization should ensure that authorized reviewers can locate the underlying evidence and understand its relationship to the model.

A well-integrated documentation framework allows the organization to move from a model record to its material risks, controls, approvals, evaluation results, and lifecycle changes without relying on informal knowledge held by individual employees.

### 101. Documentation Governance for Regulatory and Assurance Requests

Regulatory inquiries, customer due diligence, contractual reviews, and internal assurance engagements may require evidence about a model's purpose, operation, performance, or governance.

An effective documentation framework should make relevant evidence retrievable without requiring teams to reconstruct the model's history from scattered files.

The organization should establish procedures for:

1. Identifying the request and its authorized scope.
2. Determining which models, versions, and periods are relevant.
3. Mapping the request to existing documentation and evidence.
4. Validating the accuracy and currency of the records.
5. Identifying gaps, confidentiality restrictions, and unresolved limitations.
6. Obtaining the required internal review and authorization.
7. Providing the appropriate evidence through approved channels.
8. Recording what was provided and preserving relevant correspondence where required.

The response should distinguish between documented facts, provider statements, organizational assessments, and information that is unavailable.

The organization should not imply that an assessment covers a broader model population, time period, or set of requirements than the evidence supports.

### 102. Preserving Historical Model Documentation

Current documentation explains the current model state. Historical documentation explains how the model reached that state and what was known or approved at earlier points in time.

Both may be necessary.

Historical records can be important when investigating incidents, evaluating previous decisions, responding to disputes, assessing the effects of model updates, or establishing which controls were in place at a particular time.

The organization should define retention requirements for relevant artifacts, including:

- Superseded model descriptions.
- Previous evaluation reports.
- Historical configurations and version records.
- Approval and exception decisions.
- Material change assessments.
- Incident-related documentation.
- Decommissioning records.

Retention should follow applicable legal, contractual, operational, and records-management requirements. Not every temporary working file needs indefinite retention, but material evidence should not disappear merely because a newer model version has been deployed.

Where records must be deleted or anonymized, the organization should assess the effect on traceability and retain any information that must lawfully be preserved.

### 103. Establishing a Model Documentation Maturity Model

An organization can assess its documentation capability across five maturity levels.

**Level 1 — Ad Hoc**

Documentation is produced inconsistently. Ownership is unclear, artifacts are scattered, and model changes may not trigger documentation updates.

**Level 2 — Repeatable**

Basic templates and minimum documentation requirements exist. Some teams follow consistent practices, but completeness and quality vary.

**Level 3 — Defined**

A formal documentation standard, responsibility model, approval process, and lifecycle requirements are established. Documentation is subject to defined quality checks.

**Level 4 — Integrated**

Documentation is linked to AI inventory, risk management, model validation, change management, incident management, and compliance processes. Traceability is supported by enterprise systems.

**Level 5 — Continuously Assured**

Documentation quality is monitored through defined metrics, risk-based reviews, automated consistency checks where appropriate, and recurring assurance activities. Material changes trigger reassessment, and findings drive continuous improvement.

Maturity should be assessed based on demonstrated practices rather than the existence of policies alone.

For example, an organization may have a comprehensive documentation standard but remain at a low maturity level if deployed models regularly lack approved evaluation records or if model updates are not reflected in their documentation.

### 104. Conducting a Model Documentation Gap Assessment

A gap assessment determines whether current documentation practices satisfy the organization's defined requirements.

A practical assessment process is:

```
1. Establish the Documentation Standard
                 ↓
2. Identify the In-Scope Model Population
                 ↓
3. Collect Existing Documentation
                 ↓
4. Map Artifacts to Required Elements
                 ↓
5. Test Completeness and Accuracy
                 ↓
6. Verify Version and Evidence Traceability
                 ↓
7. Identify Deficiencies and Exceptions
                 ↓
8. Assess Risk and Prioritize Remediation
                 ↓
9. Assign Owners and Target Dates
                 ↓
10. Validate Remediation Effectiveness
```

The assessment should consider both document-level and process-level deficiencies.

A missing evaluation report is a document-level gap. A workflow that repeatedly permits deployment without an approved evaluation report is a broader control-design or operating-effectiveness issue.

Remediation should address the underlying cause where appropriate. Recreating a missing document may resolve one instance, but it will not correct a release process that routinely bypasses documentation requirements.

### 105. Prioritizing Documentation Remediation

Not all documentation gaps have equal significance.

Remediation priorities should reflect the potential consequences of the missing or inaccurate information, the criticality of the model, the applicable obligations, and the likelihood that the gap impairs a governance decision.

High-priority issues may include:

- No reliable identification of the deployed model version.
- Missing evidence for a critical safety or performance claim.
- Undocumented limitations affecting a consequential decision.
- Incorrect information about access permissions or system capabilities.
- Missing approval for a material model change.
- Inadequate documentation of required human oversight.
- Material discrepancies between approved and deployed configurations.
- Missing evidence needed to demonstrate compliance with an applicable requirement.

Lower-priority issues may include non-material formatting inconsistencies or supplementary information that does not affect the understanding or governance of the model.

The classification should follow the organization's approved methodology and relevant obligations. A seemingly minor documentation defect may become significant when it prevents the organization from establishing whether a critical control is effective.

### 106. Validating Documentation Remediation

A remediation item should not be closed merely because an updated document has been uploaded.

Validation should determine whether the underlying deficiency has actually been corrected.

For example, if a model's documentation did not identify its deployed version, remediation may require more than adding a version field. The organization may need to establish reliable links between the model registry, deployment records, evaluation evidence, and documentation repository.

A closure review should verify:

- The original deficiency and its cause.
- The corrective action performed.
- The updated documentation or control.
- The evidence supporting the correction.
- The relationship between the record and the actual model state.
- Whether related models or processes are affected.
- Whether residual issues remain.
- Whether the corrective action is operating as intended.

Where the deficiency is systemic, testing should determine whether the fix applies consistently across the relevant population rather than only to the example that exposed the problem.

### 107. Designing an Annual Model Documentation Review

Periodic review helps ensure that documentation remains relevant even when no formal model update has been recorded.

A review should examine whether:

- The model remains in use for the documented purpose.
- The owner and responsible stakeholders remain correct.
- The documented version matches the operational state.
- Data sources and dependencies remain accurate.
- Evaluation conclusions remain applicable.
- Known limitations have changed.
- Monitoring requirements remain appropriate.
- Relevant risks and controls have been reassessed.
- Outstanding exceptions remain authorized.
- Planned changes or retirement decisions have been documented.

Review frequency should be risk-based and consistent with applicable obligations. A fixed annual review may be a minimum requirement for some models, but it may be insufficient for rapidly changing or high-impact systems.

Periodic review should complement, not replace, event-driven updates after material changes or incidents.

### 108. Using Automation to Support Documentation Quality

Automation can reduce administrative effort and improve consistency when applied to suitable documentation controls.

Potential uses include:

- Populating model identifiers and versions from authoritative registries.
- Detecting missing mandatory fields.
- Checking approval status before release.
- Comparing deployed versions with documented versions.
- Identifying overdue reviews.
- Flagging references to superseded artifacts.
- Detecting inconsistent metadata across repositories.
- Triggering review tasks after material changes.
- Producing portfolio-level completeness reports.

Automation should not be assumed to validate the substantive accuracy of every technical statement.

For example, an automated check may confirm that a model card contains a section titled “Limitations.” It cannot, by that fact alone, establish that the limitations are complete, accurate, or meaningful.

A reliable approach combines automated structural checks with qualified human review of material technical claims and governance judgments.

### 109. Establishing Evidence Requirements for Documentation Claims

Material claims in model documentation should be supported by appropriate evidence.

Consider the following statements:

| Documentation Claim                                | Potential Supporting Evidence                                                 |
| -------------------------------------------------- | ----------------------------------------------------------------------------- |
| The model passed performance validation            | Approved evaluation report and test results                                   |
| The deployed version matches the approved version  | Model registry and deployment records                                         |
| Sensitive data is excluded from a defined workflow | Data-flow analysis, configuration evidence, and relevant testing              |
| Human approval is required for specified actions   | Approved workflow configuration and execution records                         |
| A model limitation is understood and communicated  | Evaluation findings, limitation statements, and user-facing guidance          |
| A provider update was assessed                     | Provider notice, impact assessment, test results, and approval record         |
| Monitoring thresholds are approved                 | Monitoring specification and approval evidence                                |
| A model has been retired                           | Decommissioning record and evidence that relevant dependencies were addressed |

The evidence should be appropriate to the claim. A policy may establish what is required, but it does not necessarily prove that the requirement operated effectively for a specific model.

Similarly, an interview can explain a process, but important claims may require corroboration through records, demonstrations, configurations, or testing.

### 110. Separating Model Facts, Assumptions, and Judgments

Model documentation should make clear distinctions between facts, assumptions, estimates, and judgments.

**Fact:** The approved evaluation recorded a particular performance result under specified test conditions.

**Assumption:** The evaluation population is sufficiently representative of a defined future operating population.

**Judgment:** The observed performance and remaining uncertainty are acceptable for the intended use under the organization's risk criteria.

These categories serve different purposes.

A fact should be supported by evidence. An assumption should be stated explicitly and reviewed when circumstances change. A judgment should identify the relevant criteria, rationale, responsible decision-maker, and material uncertainty.

Combining all three into a single unsupported statement can create false confidence.

For example, stating that a model “is reliable in production” may conceal the distinction between historical test performance and an assumption that future operating conditions will remain similar.

A stronger record identifies the observed evidence, the conditions under which it was obtained, the assumptions required to apply it to production, and the decision about whether the remaining uncertainty is acceptable.

### 111. Model Documentation Challenge Questions for GRC Professionals

A GRC professional reviewing model documentation should ask questions that test whether the documentation supports meaningful governance.

**Identification and accountability**

1. Can the model be uniquely identified?
2. Is the documented version traceable to the deployed version?
3. Are the model owner and business owner clearly identified?
4. Is the intended purpose explicitly defined?
5. Are prohibited or unsupported uses documented where relevant?

**Technical accuracy and evidence**

6. Does the documentation reflect the actual architecture and configuration?
7. Are material claims supported by retrievable evidence?
8. Are the evaluation conditions and limitations clearly recorded?
9. Are provider statements distinguished from independently verified facts?
10. Are assumptions and uncertainties explicit?

**Risk and operational governance**

11. Are material risks and relevant controls documented?
12. Are required human-oversight arrangements clear?
13. Are monitoring and escalation requirements defined?
14. Are material changes linked to updated documentation and approvals?
15. Are unresolved exceptions appropriately authorized and tracked?

**Lifecycle and assurance**

16. Can historical versions and approvals be reconstructed where required?
17. Is documentation reviewed at defined intervals and after material events?
18. Can relevant stakeholders retrieve the records they need?
19. Have documentation deficiencies been assessed for systemic causes?
20. Is there evidence that documentation supports actual decisions rather than merely satisfying a checklist?

These questions help distinguish the presence of documentation from the effectiveness of documentation governance.

### 112. Integrating Model Documentation Into Management Reporting

Management reporting should communicate the state of model documentation in terms that support decisions.

Useful reporting dimensions include:

- Documentation coverage across the AI portfolio.
- Models lacking mandatory artifacts.
- Material version-alignment discrepancies.
- High-risk models with overdue reviews.
- Open documentation exceptions.
- Repeated deficiencies across business units.
- Significant limitations in third-party documentation.
- Remediation progress and overdue actions.
- Documentation issues that constrain risk assessment or compliance assurance.

Reporting should avoid presenting a single completeness percentage as a complete measure of documentation effectiveness.

For example, 98% completion may conceal a critical gap affecting the organization's most consequential model. Portfolio metrics should therefore be accompanied by risk-based analysis and escalation of material exceptions.

Management should be able to determine where intervention, additional resources, restricted deployment, or a formal risk decision is required.

### 113. Continuous Improvement Through Documentation Lessons Learned

Documentation practices should improve as the organization gains experience with model development, deployment, incidents, changes, and assurance reviews.

Lessons may reveal that:

- A template omits an important category of limitation.
- A review process does not identify mismatches between evaluated and deployed versions.
- Business users cannot understand the technical documentation provided.
- Provider notifications do not supply enough information to assess model changes.
- Evaluation reports do not adequately describe test populations.
- Documentation ownership is unclear during transitions between teams.
- Retirement procedures do not address dependent systems.

The organization should assess whether each lesson requires a change to templates, standards, workflows, training, system integrations, control requirements, or accountability.

Changes should be governed and communicated. Where a revised standard introduces new mandatory requirements, the organization should determine whether existing models must be reassessed and establish an appropriate implementation plan.

Continuous improvement should focus on preventing recurring deficiencies rather than repeatedly correcting individual documents.

### 114. The Model Documentation Assurance Cycle

A mature documentation program operates as a recurring assurance cycle.

```
Define Documentation Requirements
              ↓
Prepare Model Documentation
              ↓
Review and Validate Evidence
              ↓
Approve for Intended Use
              ↓
Maintain During Operation
              ↓
Update After Changes and Incidents
              ↓
Assess Completeness and Effectiveness
              ↓
Remediate Deficiencies
              ↓
Improve Standards and Controls
              ↓
Repeat Across the Model Lifecycle
```

The cycle connects documentation production with operational governance and independent assurance.

It should provide evidence that documentation is not only created but also maintained, relied upon, challenged, and corrected when necessary.

The assurance process should remain proportionate to the model's risk and complexity while preserving mandatory requirements and appropriate independence.

### 115. Part 4 Core Principle

> **Enterprise model documentation is an operational governance capability that connects model identity, intended use, technical characteristics, evaluation evidence, limitations, risks, approvals, changes, and lifecycle decisions into a coherent and verifiable record.**

The objective is not to maximize document volume or standardize every model into an identical report.

The objective is to ensure that authorized stakeholders can understand what the model is, how it is intended to be used, what evidence supports its use, where its limitations lie, who is accountable for it, and how its status is governed as it changes over time.

Documentation is effective when it supports informed decisions, exposes uncertainty, enables traceability, and provides credible evidence of the organization's governance practices.
