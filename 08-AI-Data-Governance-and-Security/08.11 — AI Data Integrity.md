# 08.11 — AI Data Integrity

## Part 1

### 1. Introduction to AI Data Integrity

**AI data integrity** is the assurance that data used, processed, stored, transmitted, and produced by AI systems remains **accurate, complete, consistent, trustworthy, and protected against unauthorized or unintended alteration**.

Data quality asks whether data is fit for purpose.

Data integrity asks whether the data has remained trustworthy and has not been improperly changed, corrupted, or manipulated.

For AI systems, integrity is especially important because corrupted data can influence:

* Training.
* Model behavior.
* Retrieval.
* Inference.
* Automated decisions.
* Security controls.
* Compliance outcomes.

---

### 2. Why Data Integrity Matters to AI

Traditional applications may use incorrect data to produce an incorrect transaction.

AI systems can amplify the effect.

```text id="a81d4f"
Corrupted Data
      ↓
Training / Retrieval
      ↓
AI System
      ↓
Incorrect Pattern
      ↓
Large Number of Outputs
      ↓
Business Impact
```

Therefore:

> **A small integrity failure in AI data can potentially propagate across many AI decisions or outputs.**

---

### 3. Data Integrity vs Data Quality

These concepts are closely related but should not be treated as identical.

| Concept         | Primary Question                                                                              |
| --------------- | --------------------------------------------------------------------------------------------- |
| Data Quality    | Is the data fit for its intended purpose?                                                     |
| Data Integrity  | Has the data remained accurate, complete, consistent, and protected from improper alteration? |
| Data Security   | Is the data protected from unauthorized access, modification, disclosure, or destruction?     |
| Data Governance | Are rules, ownership, accountability, and controls established?                               |

They work together.

```text id="c72m1e"
Governance
    ↓
Security + Integrity + Quality
    ↓
Trustworthy AI Data
```

---

### 4. Integrity as a Security Property

Data integrity is one of the fundamental security objectives traditionally associated with the **CIA triad**:

```text id="f34k9q"
Confidentiality
      +
Integrity
      +
Availability
      ↓
Information Security
```

For AI:

* **Confidentiality** protects AI data from unauthorized disclosure.
* **Integrity** protects AI data from unauthorized or unintended modification.
* **Availability** ensures required AI data remains accessible.

All three can affect AI trustworthiness.

---

### 6. Integrity at Data Collection

Data should be protected from unauthorized manipulation at the point of collection.

Controls may include:

* Authenticated collection systems.
* Input validation.
* Trusted source identification.
* Secure devices.
* Controlled interfaces.
* Timestamping.
* Audit logging.

Example:

```text id="p64m2s"
Trusted Source
      ↓
Authenticated Collection
      ↓
Validated Data
```

---

### 7. Integrity at Data Ingestion

When data enters an AI platform, integrity controls should verify that the received data is what the organization expected.

Controls may include:

* Schema validation.
* File integrity validation.
* Checksum verification.
* Digital signatures.
* Record-count reconciliation.
* Source authentication.
* Transfer logging.

---

### 8. Data Transmission Integrity

AI data frequently moves between systems.

For example:

```text id="z91v6c"
CRM
 ↓
API
 ↓
Data Platform
 ↓
Feature Store
 ↓
AI Model
```

Each transfer creates an opportunity for:

* Corruption.
* Truncation.
* Modification.
* Replay.
* Injection.

Secure transmission mechanisms help protect integrity.

---

### 9. Cryptographic Integrity

Cryptographic mechanisms can help detect unauthorized modification.

A common concept is the **cryptographic hash**.

```text id="r52k8n"
Original Data
      ↓
Hash Function
      ↓
Hash Value
```

Later:

```text id="b73m4q"
Current Data
      ↓
Hash Function
      ↓
New Hash
```

If the values differ, the data may have changed.

---

### 10. Hashing for Dataset Integrity

A dataset can be associated with a cryptographic hash.

Example:

```text id="n84x2v"
Dataset v5
     ↓
SHA-256
     ↓
Hash A
```

When the dataset is later retrieved:

```text id="q62m8w"
Dataset v5
     ↓
SHA-256
     ↓
Hash B
```

If:

```text id="h37p5m"
Hash A ≠ Hash B
```

the organization should investigate.

A hash does not by itself explain *why* the data changed or whether the change was authorized.

---

### 11. Digital Signatures

Digital signatures can provide stronger assurance of:

* Authenticity.
* Integrity.
* Non-repudiation in appropriate contexts.

Conceptually:

```text id="v92k4x"
Data
  ↓
Private Key
  ↓
Digital Signature
```

The recipient can use the corresponding public key to verify the signature.

This can help establish that data originated from an expected signing party and was not altered after signing.

---

### 12. Checksums

Checksums are commonly used to detect accidental corruption.

For example:

```text id="m73q8v"
File Created
    ↓
Checksum
    ↓
Transfer
    ↓
Checksum Verification
```

Checksums can be useful for detecting transmission or storage errors.

However, stronger cryptographic mechanisms are generally more appropriate when protection against deliberate manipulation is required.

---

### 13. Integrity and Authentication

Integrity controls work closely with authentication.

The system should know:

> **Who or what produced this data?**

Example:

```text id="x48m2q"
Source System
      ↓
Authentication
      ↓
Trusted Identity
      ↓
Data
```

Without source authentication, an attacker may attempt to introduce malicious data while appearing to be a legitimate source.

---

### 14. Trusted Data Sources

AI systems should identify approved sources.

Example:

```text id="p85v3m"
Approved CRM
Approved ERP
Approved Data Warehouse
Approved External Provider
```

Unknown or unauthorized sources should be subject to additional scrutiny before entering an AI pipeline.

---

### 15. Data Source Trust

A source should not automatically be trusted simply because it is internal.

Internal systems can experience:

* Misconfiguration.
* Compromise.
* Human error.
* Unauthorized access.
* Software defects.
* Data corruption.

Therefore:

> **Trust should be established through controls, not assumptions.**

---

### 16. Data Integrity and Zero Trust

A zero-trust approach reinforces this principle:

```text id="q74m8x"
Source
  ↓
Verify
  ↓
Authenticate
  ↓
Authorize
  ↓
Validate Integrity
  ↓
Use
```

The fact that data comes from an internal network does not automatically make it trustworthy.

---

### 17. Storage Integrity

AI datasets may be stored in:

* Databases.
* Object storage.
* Data lakes.
* Data warehouses.
* Feature stores.
* Vector databases.
* File systems.

Integrity controls should protect against unauthorized modification across these environments.

---

### 18. Access Controls and Integrity

Access control is a major integrity protection.

The principle should be:

> **Only authorized identities should be able to modify AI data.**

Example:

```text id="m52q8v"
Read Access
    ≠
Write Access
    ≠
Delete Access
```

Separating permissions reduces the risk of unauthorized changes.

---

### 19. Least Privilege

AI data access should follow least privilege.

Users and systems should receive only the permissions necessary to perform their responsibilities.

For example:

```text id="z83m4q"
Data Scientist
→ Read Training Data

Data Engineer
→ Modify Pipeline Data

Data Owner
→ Approve Dataset

Administrator
→ Controlled Administrative Access
```

Not every role should have unrestricted write access.

---

### 20. Separation of Duties

Critical AI data operations may require separation of responsibilities.

Example:

```text id="v62q9m"
Data Engineer
    ↓
Prepares Dataset

Data Owner
    ↓
Approves Dataset

AI/ML Team
    ↓
Uses Dataset
```

This reduces the possibility that one person can manipulate and approve the same critical data without oversight.

---

### 21. Immutable Data

For some high-value datasets, organizations may use immutable or append-only storage.

The objective is to make historical data difficult or impossible to alter without detection.

Example:

```text id="k95x3m"
Dataset Snapshot
      ↓
Immutable Storage
      ↓
Training
```

This can be particularly valuable for audit evidence and reproducibility.

---

### 22. Versioned Data

AI datasets should be versioned where appropriate.

Example:

```text id="p38m7q"
Dataset v1.0
Dataset v1.1
Dataset v1.2
Dataset v2.0
```

Versioning makes it possible to identify which dataset was used by a specific model or training run.

---

### 23. Dataset Snapshots

A snapshot represents the state of a dataset at a defined point in time.

Example:

```text id="x74q8m"
Customer Dataset
Snapshot: 2026-08-31
Version: v7.2
```

Snapshots support:

* Reproducibility.
* Investigations.
* Audits.
* Model validation.
* Incident response.

---

### 24. Integrity and Data Lineage

Data lineage helps identify where data originated and how it changed.

```text id="m84v2q"
Source
 ↓
Ingestion
 ↓
Transformation
 ↓
Dataset
 ↓
Feature
 ↓
Model
```

Integrity controls help ensure that unauthorized changes do not occur along this chain.

---

### 25. Integrity and Data Provenance

**Provenance** provides the history and origin of data.

Integrity asks whether that data remained trustworthy during its lifecycle.

Together:

```text id="q63m9x"
Provenance
     +
Integrity
     ↓
Traceable and Trustworthy Data
```

---

### 26. Integrity of Transformations

Data transformations can unintentionally alter information.

Example:

```text id="v72m5q"
Raw:
€1,250.50

Transformation:
Currency Conversion

Expected:
Correct Converted Value

Actual:
Incorrect Value
```

Transformation logic must therefore be validated and controlled.

---

### 27. Transformation Integrity

A transformation pipeline should provide assurance that:

* The intended code executed.
* The correct source was used.
* The correct version was deployed.
* Data was not unexpectedly modified.
* Results match expected behavior.

This connects data integrity with software and pipeline security.

---

### 28. Pipeline Integrity

AI pipelines should be protected from unauthorized changes.

```text id="n53x8m"
Source
 ↓
Pipeline
 ↓
Transformation
 ↓
Dataset
```

If an attacker modifies the pipeline, they may manipulate the resulting dataset without directly changing the source.

Therefore, pipeline integrity is part of AI data integrity.

---

### 29. Code Integrity

The code that processes AI data should also be protected.

Controls may include:

* Source-code repositories.
* Code review.
* Branch protection.
* Signed commits where appropriate.
* CI/CD controls.
* Artifact integrity verification.
* Deployment approvals.

A secure dataset processed by compromised code may still produce compromised results.

---

### 30. Build Artifact Integrity

AI systems may use:

* Data-processing containers.
* ETL applications.
* Feature-generation services.

Build artifacts should be controlled and verified.

```text id="q86m4z"
     ↓
```

AI data-processing pipelines may depend on third-party libraries.

Examples:

* Python packages.

* Container images.

A compromised dependency can alter how data is processed.

Dependency management therefore contributes indirectly to data integrity.

### 33. Third-Party Dataset Integrity

Third-party data should be assessed for:

* Source authenticity.

Contracts can also establish requirements for material data changes.

---

### 34. Data Integrity and APIs

APIs are common data-delivery mechanisms for AI systems.

Controls should consider:

* Authentication.
* Authorization.
* Transport security.
* Input validation.
* Rate limiting.
* Replay protection where appropriate.
* Logging.
* Integrity verification.

---

### 35. Replay Attacks

An attacker may attempt to resend previously valid data.

Example:

```text id="x63m9q"
Valid Transaction
       ↓
Captured
       ↓
Replayed
       ↓
AI System
```

The data may appear legitimate even though it is being used outside its original context.

Controls such as timestamps, unique identifiers, sequence numbers, or protocol-level protections can help address replay risks.

---

### 36. Timestamp Integrity

Timestamps can be important for:

* Fraud detection.
* Event sequencing.
* Financial models.
* Security analytics.
* Time-series forecasting.

Incorrect timestamps can alter how AI interprets events.

---

### 37. Clock Synchronization

Distributed systems should maintain appropriate time synchronization.

Example:

```text id="m85q3v"
System A → 10:00:01
System B → 10:07:42
System C → 09:53:18
```

Significant clock discrepancies can make event ordering unreliable.

Time synchronization therefore contributes to data integrity.

---

### 38. Record Integrity

Individual records should maintain logical consistency.

Example:

```text id="q74m8z"
Customer ID = 1054
Transaction ID = TX8821
Amount = €500
Currency = EUR
Timestamp = Valid
```

A record containing contradictory or impossible combinations may indicate corruption or processing errors.

---

### 39. Referential Integrity

Relationships between records should remain valid.

Example:

```text id="v93m6q"
Transaction
    ↓
Customer ID
    ↓
Customer Master
```

If the referenced customer does not exist, the relationship may be broken.

Broken relationships can affect AI features and predictions.

---

### 40. Constraint Integrity

Organizations can define constraints such as:

```text id="x58q3m"
Age ≥ 0
Amount ≥ 0
Country ∈ Approved Values
Timestamp ≤ Current Time
Customer_ID ≠ NULL
```

Violations can indicate data corruption or invalid processing.

---

### 41. Database Integrity Controls

Database controls can include:

* Primary keys.
* Foreign keys.
* Constraints.
* Transactions.
* Referential integrity.
* Access control.
* Audit logging.

These controls can prevent or detect inconsistent data.

---

### 42. Transaction Integrity

Transactional systems help ensure that related changes occur consistently.

For example:

```text id="p84m7x"
Payment Created
     +
Account Balance Updated
```

If one operation succeeds while the other fails, data may become inconsistent.

Transactional controls help preserve integrity.

---

### 43. ACID Principles

Traditional databases often use **ACID** properties:

* **Atomicity**
* **Consistency**
* **Isolation**
* **Durability**

These properties can help maintain reliable data states.

AI platforms may use different architectures, so the appropriate integrity mechanisms depend on the storage technology.

---

### 44. Data Integrity in Data Lakes

Data lakes may contain massive volumes of structured and unstructured data.

Integrity risks include:

* Unauthorized modification.
* Accidental deletion.
* Duplicate ingestion.
* Corrupted files.
* Incomplete uploads.
* Uncontrolled overwriting.

Governance should therefore define appropriate integrity controls for critical datasets.

---

### 45. Object Storage Integrity

AI datasets commonly use object storage.

Important controls may include:

* Versioning.
* Object locking where appropriate.
* Access policies.
* Encryption.
* Integrity checks.
* Audit logging.
* Retention controls.

The objective is to protect both the contents and the historical state of important datasets.

---

### 46. Data Integrity in Feature Stores

Feature stores contain values used directly by models.

An integrity failure can therefore directly affect predictions.

```text id="m63q8v"
Source Data
    ↓
Feature Pipeline
    ↓
Feature Store
    ↓
Model
    ↓
Prediction
```

Feature integrity should be treated as a critical AI control.

---

### 47. Feature Integrity Checks

Controls may verify:

* Expected range.
* Data type.
* Calculation logic.
* Source.
* Timestamp.
* Version.
* Missing values.
* Unexpected changes.

---

### 48. Data Integrity in RAG Systems

RAG systems introduce another integrity chain:

```text id="q85m3x"
Source Document
      ↓
Ingestion
      ↓
Chunking
      ↓
Embedding
      ↓
Vector Store
      ↓
Retrieval
      ↓
LLM
```

If an attacker modifies an authoritative document, the AI may retrieve and reproduce the malicious content.

---

### 49. RAG Source Integrity

RAG systems should establish controls around authoritative documents.

Possible controls include:

* Document authentication.
* Version control.
* Hash verification.
* Access control.
* Source ownership.
* Approval.
* Effective dates.
* Retirement controls.

---

### 50. AI Data Integrity Governance Principle

The foundational governance principle is:

> **AI data should remain trustworthy from its point of origin through collection, transmission, storage, transformation, training, retrieval, inference, and archival, with appropriate controls to detect or prevent unauthorized, unintended, or unexplained changes.**

For AI GRC, data integrity should therefore be treated as a **continuous control objective**, not merely a technical property of a database.

### 51. Data Integrity Threat Model

AI data integrity should be evaluated against both accidental and malicious threats.

Common threats include:

* Unauthorized modification.
* Accidental modification.
* Data corruption.
* Pipeline manipulation.
* Dataset replacement.
* Malicious data injection.
* Replay of valid data.
* Deletion or truncation.
* Unauthorized transformation.
* Compromised third-party sources.

A useful model is:

```text id="p8m4vx"
Threat
  ↓
Integrity Weakness
  ↓
Data Modification
  ↓
AI Processing
  ↓
Incorrect / Manipulated Output
  ↓
Business Impact
```

---

### 52. Accidental vs Malicious Integrity Failure

Not every integrity problem is an attack.

**Accidental:**

* Human error.
* Incorrect transformation.
* Software defect.
* Failed synchronization.
* Corrupted file.
* Misconfigured pipeline.

**Malicious:**

* Data tampering.
* Data poisoning.
* Unauthorized modification.
* Insider manipulation.
* Supply-chain compromise.

The response should depend on the cause and potential impact.

---

### 53. Integrity Failure Modes

A practical classification is:

| Failure              | Description                         |
| -------------------- | ----------------------------------- |
| Corruption           | Data becomes technically damaged    |
| Alteration           | Data values are changed             |
| Deletion             | Required data is removed            |
| Injection            | Unauthorized data is added          |
| Substitution         | Legitimate data is replaced         |
| Reordering           | Event sequence is changed           |
| Replay               | Previously valid data is reused     |
| Transformation Error | Processing changes data incorrectly |

Each failure mode can affect AI differently.

---

An AI GRC assessment should consider:

```text id="m7q3vz"
Likelihood
    ×
Impact
    ↓
Integrity Risk
```

Impact may include:

* Incorrect AI decisions.
* Financial loss.
* Regulatory exposure.
* Customer harm.
* Security incidents.
* Operational disruption.
* Reputational damage.

### 55. Criticality-Based Integrity Controls

Not every dataset requires the same controls.

Controls should be proportional to AI risk.

### 56. AI Data Criticality

A dataset may be considered critical when its integrity failure could materially affect:

* Safety.
* Financial decisions.
* Regulatory compliance.
* Security operations.
* Customer eligibility.
* Business continuity.
* High-impact automated decisions.

Criticality should be documented.

### 58. Data Integrity Control Objectives

* Role-based access control.

* Write restrictions.

* Network segmentation.
* Immutable storage.

* Change management.

```text id="v63q8m"

       ↓

```

### 60. Detective Integrity Controls

Detective controls identify changes after they occur.

Examples:

* Hash comparison.
* File integrity monitoring.

```text id="m84q2v"

Detection
       ↓
Alert
       ↓
```

### 61. Corrective Integrity Controls

Corrective controls restore trusted conditions.

Examples:

* Re-run pipeline.

### 62. Compensating Integrity Controls

Compensating controls may include:

* Human approval.

### 64. Integrity and Identity

Data integrity depends on knowing **who or what is allowed to modify data**.

Important identities include:

* Human users.
* Service accounts.
* Applications.
* APIs.
* Pipelines.
* AI agents.
* External providers.

Every important modification should be attributable to an authorized identity.

---

### 65. Service Account Integrity

AI pipelines frequently use service accounts.

Example:

```text id="p63m8x"
ETL Service Account
       ↓
Reads Source
       ↓
Writes Dataset
```

The service account should have only the permissions required.

If compromised, excessive privileges could allow unauthorized modification of large datasets.

---

### 66. AI Agent Data Integrity

AI agents may increasingly interact with enterprise data.

An agent might:

```text id="m74q8z"
Read Data
   ↓
Transform Data
   ↓
Write Data
```

Agent permissions should therefore be carefully controlled.

An AI agent should not receive unrestricted write access simply because it is an approved application.

---

### 67. Human vs Machine Modifications

Organizations should distinguish between:

```text id="x85m3q"
Human Modification
Machine Modification
Automated Pipeline
AI Agent Modification
Third-Party Modification
```

Different controls may apply to each.

Audit logs should identify the actor responsible for the change.

---

### 68. Data Integrity and Audit Logging

Audit logs should capture significant data changes.

Useful information includes:

* Who made the change.
* What changed.
* When it changed.
* Source system.
* Previous value where appropriate.
* New value where appropriate.
* Reason or ticket.
* Approval reference.

---

### 69. Immutable Audit Logs

Audit records should themselves be protected against modification.

Otherwise:

```text id="q38m7v"
Data Tampered
     ↓
Audit Log Modified
     ↓
Evidence Lost
```

Protected or immutable logging can improve forensic reliability.

---

### 70. Data Change Attribution

For important AI datasets, the organization should ideally answer:

> **Who changed this data, what did they change, when did they change it, and why?**

This is a core GRC accountability question.

---

### 71. Authorized Change vs Unauthorized Change

Not every modification is an integrity violation.

Example:

```text id="v64q8m"
Approved Change Request
        ↓
Authorized Pipeline Update
        ↓
Dataset Updated
```

The change is expected and traceable.

By contrast:

```text id="m83x5q"
Unknown Actor
     ↓
Dataset Modification
     ↓
No Approval
```

should be treated as suspicious.

---

### 72. Change Management

Material changes to AI data should follow controlled change management.

Example:

```text id="p75m3q"

      ↓

      ↓
Approval
```

### 73. Emergency Changes

Emergency changes may be necessary during incidents.

However, they should still be:

* Authorized.
* Logged.
* Reviewed afterward.
* Validated.
* Reconciled with normal change procedures.

Emergency status should not become a permanent bypass of governance.

---

### 74. Data Integrity and Configuration

Integrity can be affected by configuration changes.

Examples:

* Validation rules.
* Pipeline parameters.
* Feature calculations.
* RAG retrieval filters.
* Database permissions.
* Retention settings.

Configuration should therefore be version-controlled and governed.

---

### 75. Integrity of Quality Rules

Quality rules themselves must be protected.

Example:

```text id="x48m7q"
Original Rule:
Amount > 0

Modified Rule:
Amount >= -1,000,000
```

If the rule is maliciously weakened, bad data may pass validation.

Therefore, **the integrity of the control is itself a governance concern**.

### 76. Control Integrity

A mature GRC framework should protect:

```text id="q73m8x"

+
Pipeline
+
Validation Rules
+
Configuration
+

```

Compromising any of these can undermine the integrity assurance process.

### 79. Dual Control

Sensitive data changes may require two authorized parties.

Example:

```text id="q84m3x"

          ↓
Authorized Reviewer
          ↓
Change Approved
          ↓
Implementation
```

This reduces the risk of unilateral manipulation.

---

### 80. Four-Eyes Principle

The **four-eyes principle** means that critical activities require review or approval by another authorized person.

Potential applications include:

* Critical dataset changes.
* Production AI configuration.
* High-impact model deployment.
* RAG knowledge-base updates.

---

### 81. Integrity and Separation of Environments

AI data should be separated appropriately between:

* Development.
* Testing.
* Staging.
* Production.

Example:

```text id="m74q8x"
Development
     ↓
Testing
     ↓
Staging
     ↓
Production
```

Production data should not be casually modified by development processes.

---

### 82. Production Data Protection

Production AI datasets should have stronger controls because changes can directly affect live systems.

Controls may include:

* Restricted write access.
* Approval.
* Monitoring.
* Backup.
* Versioning.
* Immutable snapshots.
* Change logging.

---

### 83. Backup Integrity

Backups are only useful if they can be trusted.

Organizations should periodically verify:

* Backup completeness.
* Backup integrity.
* Restoration capability.
* Version correctness.
* Protection against unauthorized modification.

---

### 84. Restore Testing

A backup should not simply be assumed to work.

A restore test can follow:

```text id="x58m3q"
Backup
  ↓
Restore
  ↓
Integrity Verification
  ↓
Quality Validation
  ↓
Usable Dataset
```

This is especially important for critical AI systems.

---

### 85. Backup Immutability

For high-value datasets, immutable backups can reduce ransomware and tampering risk.

Conceptually:

```text id="p73m8v"
Production Dataset
       ↓
Backup
       ↓
Immutable Copy
```

An attacker who compromises the production environment should not automatically be able to alter every recovery copy.

---

### 86. Integrity and Disaster Recovery

A disaster recovery plan should answer:

> **How will the organization restore a trusted AI dataset after corruption or unauthorized modification?**

Recovery should include both:

* Availability.
* Integrity verification.

Restoring corrupted data does not solve the problem.

---

### 87. Recovery Point Objective

**RPO** determines how much data loss is acceptable.

Example:

```text id="q84m3x"
RPO = 1 hour
```

The organization may need recovery to a point no more than one hour before the incident.

The appropriate RPO depends on business criticality.

---

### 88. Recovery Time Objective

**RTO** determines how quickly the service should be restored.

Example:

```text id="m63q8v"
RTO = 4 hours
```

For critical AI services, the recovery process should consider both speed and data trustworthiness.

---

### 89. Integrity Recovery Sequence

A secure recovery process can be:

```text id="v75m3x"
Identify Incident
      ↓
Isolate Affected Systems
      ↓
Identify Last Trusted State
      ↓
Restore
      ↓
Verify Integrity
      ↓
Validate Quality
      ↓
Resume AI Processing
```

The "last trusted state" is particularly important.

---

### 90. Last Known Good Dataset

Organizations should maintain a concept of a **last known good dataset** for critical AI workloads.

Example:

```text id="q48m7x"
v8.1 → Valid
v8.2 → Valid
v8.3 → Suspected Compromise
```

The organization may need to roll back to v8.2.

---

### 91. Integrity Monitoring

Continuous monitoring can identify unexpected changes.

Potential monitoring signals include:

* Hash changes.
* File changes.
* Database changes.
* Permission changes.
* Schema changes.
* Volume anomalies.
* Source changes.
* Pipeline changes.

---

### 92. File Integrity Monitoring

File Integrity Monitoring (**FIM**) can detect unexpected changes to protected files.

For AI environments, this can potentially apply to:

* Dataset manifests.
* Model artifacts.
* Configuration files.
* Prompt templates.
* RAG source files.
* Pipeline definitions.

---

### 93. Dataset Integrity Monitoring

A dataset-monitoring system might compare:

```text id="m85q4v"
Expected Version
       vs
Observed Version
```

Unexpected differences can trigger investigation.

---

### 94. Hash-Based Monitoring

A simplified approach is:

```text id="x73m8q"
Approved Dataset
      ↓
Hash
      ↓
Stored Reference
```

Periodically:

```text id="q64m3v"
Current Dataset
      ↓
Hash
      ↓
Compare
```

Mismatch:

```text id="p85m7x"
Mismatch
   ↓
Alert
   ↓
Investigation
```

---

### 95. Limitations of Hash Monitoring

Hash comparison is useful, but it has limitations.

A changed hash tells you:

> **The data is different.**

It does not automatically tell you:

* Whether the change was authorized.
* What changed.
* Why it changed.
* Whether the new data is better or worse.

Hashing should therefore be combined with versioning, change management, and audit logs.

---

### 96. Integrity Monitoring vs Quality Monitoring

These should not be confused.

**Integrity monitoring:**

> Did the data change unexpectedly?

**Quality monitoring:**

> Is the resulting data still fit for purpose?

Example:

```text id="v83m6q"
Authorized Change
      ↓
Hash Changed
      ↓
Integrity = Expected

But...

Quality = Failed
```

A legitimate change can still create poor-quality data.

---

### 97. Integrity and Data Drift

Data drift does not necessarily indicate an integrity violation.

For example:

```text id="m74q8x"
Customer Behavior Changes
      ↓
Natural Distribution Shift
```

The data may remain completely authentic.

Therefore:

> **Drift is a signal requiring investigation, not automatic proof of tampering.**

---

### 98. Integrity and Anomaly Detection

Anomaly detection can identify suspicious patterns such as:

* Unexpected record volumes.
* Sudden value changes.
* Unusual source behavior.
* Unexpected geographic distribution.
* Abrupt feature changes.

These signals can support integrity investigations.

---

### 99. Security Monitoring Integration

AI data-integrity monitoring should integrate with security monitoring where appropriate.

```text id="q53m8v"
Data Monitoring
      +
IAM Logs
      +
Pipeline Logs
      +
Network Logs
      +
Security Alerts
      ↓
Integrity Investigation
```

Correlating signals improves detection.

---

### 100. AI Data Integrity Governance Principle

The central principle is:

> **AI data integrity requires the organization to establish trusted sources, restrict unauthorized modification, maintain traceability, verify important data states, monitor unexpected changes, protect recovery copies, and preserve evidence throughout the AI data lifecycle.**

Integrity is therefore not simply:


> "The database has not been hacked."

It is a broader governance question:

> **Can the organization demonstrate that the data used by the AI system is trustworthy, traceable, authorized, and protected against unauthorized or unexplained change?**

### 102. Integrity Boundary

Each major stage should have a defined **integrity boundary**.

An integrity boundary identifies:

* What enters the system.
* What leaves the system.

* What validation occurs.
* What evidence is generated.

Example:

```text

│                              │

│              Output          │
```

AI architectures may contain multiple trust zones.

```text

     │
     ▼

     │
     ▼

     │
     ▼
[Trust Boundary]
     │
     ▼
```

Data crossing a trust boundary should be appropriately authenticated, validated, and monitored.

For AI systems, contracts can additionally specify:

* Freshness.

### 119. Schema Integrity

Unexpected schema changes can cause AI systems to behave incorrectly.

Example:

```text id="m74q8x"
Expected:
customer_age = integer

Changed:
customer_age = string
```

Even if the values look correct, downstream processing may fail or behave unexpectedly.

---

### 120. Schema Change Detection

Controls can detect:

* Added fields.
* Removed fields.
* Renamed fields.
* Data-type changes.
* Constraint changes.

Material changes should trigger review.

---

### 121. Data Type Integrity

AI pipelines should ensure that values conform to expected types.

Examples:

```text id="q85m3v"

Amount → Decimal
Timestamp → Datetime
Country → Approved Code
```

Type violations may indicate corruption or transformation errors.

---

### 122. Semantic Integrity

Technical validity does not guarantee semantic correctness.

Example:

```text id="x63m8q"
Country Code = "ES"
```

The value may be syntactically valid.

But if the record belongs to a customer physically located elsewhere, the semantic interpretation may be incorrect.

AI governance should therefore consider **meaning**, not only format.

---

### 123. Business Rule Integrity

Business rules can protect semantic integrity.

Examples:

```text id="p74q3x"
Contract Start Date
≤
Contract End Date

Invoice Amount
≥
0

Customer Status
∈
Approved Values
```

AI datasets may require many such rules.

---

### 124. Referential Integrity in AI

Relationships between entities should remain valid.

Example:

```text id="m85q4v"
Transaction
    ↓
Customer ID
    ↓
Customer Record
```

If the customer record is missing or incorrectly linked, model features may become unreliable.

---

### 125. Temporal Integrity

AI systems often depend on the correct sequence of events.

For example:

```text id="q63m8x"
Application
   ↓
Approval
   ↓
Transaction
```

If timestamps are incorrectly reordered:

```text id="v75q3m"
Transaction
   ↓
Application
```

the model may learn an impossible relationship.

---

### 126. Temporal Leakage

Temporal integrity is particularly important in machine learning.

Training data should not contain information that would only have become available **after** the prediction point.

Example:

```text id="x84m7q"
Prediction Date
      ↓
Allowed Data
      ↓
Future Outcome
      ✕
```

Future information can create artificially strong model performance.

---

### 127. Point-in-Time Integrity

A training feature should represent the value that would have been available at the time the prediction was made.

This is known as **point-in-time correctness**.

It is particularly important for:

* Fraud models.
* Credit models.
* Customer-risk models.
* Forecasting.
* Recommendation systems.

---

### 128. Training Dataset Integrity

Before training, organizations should verify:

```text id="m73q8x"

      ↓
Correct Version
      ↓
Correct Labels
      ↓
Correct Features
      ↓
Correct Time Window
      ↓
Approved Training Set
```

An attacker could attempt to alter labels.

Example:

```text id="q85m3v"

  ↓

  ↓
```

Label integrity is therefore a security concern.

Training data tampering occurs when an unauthorized party modifies training data to influence model behavior.

Potential objectives include:

* Changing model behavior.
* Introducing hidden weaknesses.

Data may be contaminated by:

### 151. AI Data Integrity Control Framework

A mature enterprise should manage AI data integrity through a structured control framework.

The framework should connect:

```text
GOVERNANCE
     ↓

CONTROL DESIGN
     ↓
IMPLEMENTATION
     ↓
MONITORING
     ↓

     ↓

```

The objective is not simply to prevent unauthorized modification. It is to provide **reasonable, demonstrable assurance that AI data remains trustworthy throughout its lifecycle**.

---

### 152. AI Data Integrity Control Categories

Controls can be organized into six major categories:

| Category     | Purpose                                            |
| ------------ | -------------------------------------------------- |
| Preventive   | Stop unauthorized or unintended changes            |
| Detective    | Identify integrity failures                        |
| Corrective   | Restore trustworthy data                           |
| Compensating | Reduce risk when primary controls are insufficient |
| Governance   | Establish accountability and requirements          |
| Assurance    | Demonstrate controls work effectively              |

This structure is useful when building an AI GRC control library.

Preventive controls may include:

* Identity and access management.
* Least privilege.
* Role-based access control.
* Separation of duties.
* Change approval.
* Immutable storage.
* Secure APIs.
* Network segmentation.
* Protected pipelines.
* Controlled service accounts.

Example:

```text
Authorized User
      ↓
Authentication
      ↓
Authorization
      ↓
Approved Change
```

### 154. Detective Integrity Controls

Detective controls may include:

* Hash verification.
* File integrity monitoring.
* Dataset comparison.
* Database audit logs.
* Anomaly detection.
* Schema monitoring.
* Record reconciliation.
* Pipeline monitoring.
* Access monitoring.

Example:

```text

      ↓

      ↓

      ↓
```

### 155. Corrective Integrity Controls

* Restore trusted dataset.

* Reprocess affected data.

### 177. Five Whys for Integrity

Example:

**Why did the AI use corrupted data?**

→ Validation failed.

**Why did validation fail?**

→ Validation service was not running.

**Why was it not running?**

→ Deployment changed the configuration.

**Why was configuration changed?**

→ Change bypassed review.

**Why was review bypassed?**

→ Emergency procedure lacked sufficient governance.

The real issue may therefore be **change governance**, not simply data corruption.

### 213. Final GRC Principle

For an AI GRC professional, the most important principle is:

> **Do not simply ask whether AI data is correct. Ask whether the organization can demonstrate that the data came from an authorized source, remained protected from unauthorized modification, was processed through trusted pipelines, can be traced to its approved version, and can be recovered to a known-good state if integrity is compromised.**

The ultimate objective is:

```text
Trusted Source
      +
Protected Pipeline
      +
Controlled Transformation
      +
Verified Dataset
      +
Traceable Version
      +
Continuous Monitoring
      +
Tested Recovery
      +
Independent Assurance
      ↓
TRUSTWORTHY AI DATA
      ↓
TRUSTWORTHY AI
```

**AI data integrity is therefore an enterprise governance capability that connects data governance, cybersecurity, data engineering, MLOps, incident management, risk management, and assurance.**
