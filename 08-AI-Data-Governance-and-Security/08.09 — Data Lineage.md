# 08.09 — Data Lineage

## Part 1

### 1. Introduction to Data Lineage

**Data lineage** is the documented path that data follows as it moves through systems, processes, transformations, and AI workflows.

In simple terms:

> **Data lineage shows where data came from, where it went, and what happened to it along the way.**

For AI governance, lineage is critical because AI data rarely moves directly from a source system into a model.

A typical enterprise AI flow may look like:

```text
Source Systems
      ↓
Data Ingestion
      ↓
Data Lake
      ↓
Data Processing
      ↓
AI Dataset
      ↓
Training / RAG
      ↓
Model
      ↓
AI Application
      ↓
AI Output
```

Data lineage provides visibility across this chain.

---

### 2. Why Data Lineage Matters in AI

AI systems increasingly depend on complex data pipelines.

A single AI application may consume data from:

* Databases.
* Data warehouses.
* Data lakes.
* APIs.
* SaaS platforms.
* Documents.
* External datasets.
* Vector databases.
* User inputs.
* Real-time streams.

Without lineage, an organization may not know exactly how information reached an AI system.

This creates risks involving:

* Security.
* Privacy.
* Data quality.
* Compliance.
* Model reliability.
* Data leakage.
* Regulatory accountability.
* Incident response.

---

### 3. Data Lineage vs Data Provenance

**Data provenance** focuses primarily on the **origin and history of data**.

**Data lineage** focuses primarily on the **movement and transformation of data across systems**.

A useful distinction is:

```text
Provenance:
"Where did this data originate?"

Lineage:
"How did this data travel and change?"
```

They overlap significantly and are often implemented together.

### 6. Source-to-Target Lineage

A basic lineage relationship can be represented as:

```text
Source → Transformation → Target
```

Example:

```text
CRM.Customer_Name
        ↓
PII Redaction
        ↓
AI.Customer_Name_Masked
```

This shows the relationship between the original field and the resulting field.

---

### 7. Dataset-Level Lineage

At the dataset level:

```text
CRM Dataset
    ↓
ETL Process
    ↓
Analytics Dataset
    ↓
AI Training Dataset
```

This provides a high-level view of how datasets depend on one another.

---

### 8. Table-Level Lineage

Lineage can be more granular.

Example:

```text
CRM.Customer
      ↓
DWH.Customer_Master
      ↓
AI.Customer_Profile
```

This shows relationships between tables rather than entire systems.

---

### 9. Column-Level Lineage

For more sensitive or regulated environments, lineage can operate at the field or column level.

Example:

```text
CRM.Email
   ↓
Hashing
   ↓
AI.Customer_Email_Hash
```

Another example:

```text
CRM.Date_of_Birth
       ↓
Age Calculation
       ↓
AI.Customer_Age
```

Column-level lineage provides much greater visibility.

---

### 10. Why Granularity Matters

Different use cases require different lineage granularity.

```text
Low Risk
→ Dataset-level

Medium Risk
→ Table-level

High Risk
→ Column-level

Very High Risk
→ Record / transaction-level
```

Organizations should select the appropriate level based on risk, regulatory requirements, and operational needs.

A mature governance program should connect these perspectives.

### 60. Data Lineage as an AI GRC Capability

Data lineage ultimately provides the **map of the AI data ecosystem**.

```text
                SOURCE
                   ↓
              INGESTION
                   ↓
                STORAGE
                   ↓
             TRANSFORMATION
                   ↓
                DATASET
                   ↓
           TRAINING / RETRIEVAL
                   ↓
                 MODEL
                   ↓
              APPLICATION
                   ↓
                 OUTPUT
```

For AI GRC, the objective is not merely to draw a technical diagram.

The objective is to establish **trusted, actionable visibility into how data moves, changes, and supports AI systems**.

> **Data lineage turns the movement of AI data into a traceable and governable flow.**

A mature organization should be able to answer:

**Where did the data come from?**

**What systems processed it?**

**What transformations occurred?**

**Where did the data go?**

**Which AI datasets and models depend on it?**

**What downstream applications could be affected by a change?**

These capabilities make data lineage a foundational component of **AI data governance, security, privacy, risk management, compliance, incident response, and AI assurance**.

### 61. Data Lineage Architecture

Enterprise data lineage is best understood as a connected representation of how data moves across the organization's technology environment.

A simplified architecture is:

```text
┌───────────────────────────────────────────────────────┐
│                    DATA SOURCES                       │
│                                                       │
│ CRM │ ERP │ HR │ APIs │ Files │ SaaS │ External Data │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼
┌───────────────────────────────────────────────────────┐
│                  DATA INGESTION                       │
│                                                       │
│ ETL │ ELT │ APIs │ Streaming │ File Transfer          │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼
┌───────────────────────────────────────────────────────┐
│                  DATA PLATFORM                        │
│                                                       │
│ Lake │ Warehouse │ Database │ Data Mesh               │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼
┌───────────────────────────────────────────────────────┐
│               DATA PROCESSING                         │
│                                                       │
│ Cleaning │ Filtering │ Transformation │ Aggregation   │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼
┌───────────────────────────────────────────────────────┐
│                    AI DATA                            │
│                                                       │
│ Training │ Validation │ Test │ RAG │ Features         │
└───────────────────────┬───────────────────────────────┘
                        │
                        ▼

│                    AI LAYER                           │

                        │

```

The lineage capability sits across these layers and records the relationships between them.

### 62. Lineage Metadata

A lineage system requires metadata describing the movement and transformation of data.

Typical metadata includes:

* Source system.
* Destination system.
* Dataset.
* Table.
* Column.
* Transformation.
* Timestamp.
* Pipeline.
* Pipeline version.
* Owner.
* Classification.
* Data steward.
* Processing purpose.
* Model dependency.

For example:

```text
Source:
CRM.Customer

Transformation:
PII Masking

Destination:
AI.Customer_Profile

Pipeline:
customer_ai_pipeline_v4

Timestamp:
2026-08-31 08:30 UTC
```

---

### 63. Lineage Metadata vs Business Data

It is important to distinguish the **data itself** from the **metadata describing its movement**.

```text
Business Data
     │
     └── Customer Name
     └── Customer Email
     └── Customer ID

Lineage Metadata
     │
     └── Source
     └── Destination
     └── Transformation
     └── Timestamp
     └── Owner
```

The lineage system should avoid unnecessarily copying sensitive business data.

---

### 64. Lineage Capture

Lineage can be captured in several ways.

#### Automated capture

The data platform automatically records:

```text
Source → Pipeline → Destination
```

#### Tool-based capture

Data-management platforms collect lineage from supported technologies.

#### Manual capture

Teams document relationships manually.

Automated capture is generally preferable for large and dynamic environments.

---

### 65. Active vs Passive Lineage

**Active lineage** is generated dynamically from actual system activity.

Example:

```text
Pipeline Execution
       ↓
Lineage Event
       ↓
Lineage Repository
```

**Passive lineage** is documented separately, such as in architecture diagrams or spreadsheets.

Active lineage generally provides stronger evidence of actual system behavior.

---

### 66. Design-Time Lineage

Design-time lineage describes how a system is **intended** to operate.

Example:

```text

 ↓
Data Lake
 ↓
AI Platform
```

It is commonly documented during:

* Architecture design.
* Solution design.
* Data modeling.
* AI system development.

---

### 67. Runtime Lineage

Runtime lineage describes what **actually happened** during execution.

Example:

```text
Pipeline Run #8291
 ↓
CRM
 ↓
Dataset A
 ↓
Feature Store
 ↓
```

Runtime lineage is particularly valuable for investigations and audits.

---

### 68. Design vs Runtime Lineage

These should be compared.

```text
DESIGNED FLOW

CRM → Lake → AI Platform


ACTUAL FLOW

CRM → Lake → External API → AI Platform
```

The unexpected API connection may represent a security or compliance issue.

Therefore:

> **Lineage can be used to identify differences between approved architecture and actual data movement.**

### 155. Lineage RACI

A simplified RACI model:

```text id="n4m8q2"
Activity                  Owner  Steward  AI  Security  GRC
------------------------------------------------------------
Define lineage standard     A       R      C      C       C
Capture lineage             C       R      R      C       C
Protect lineage             C       C      C      R       C
Review lineage              A       R      C      C       R
Test controls               C       C      C      C       A
Remediate issues            A       R      R      R       C
```

This avoids the common problem where everyone assumes another team owns lineage.

### 156. Lineage Control Objectives

An enterprise lineage control framework should address:

1. **Completeness**
2. **Accuracy**
3. **Timeliness**
4. **Integrity**
5. **Availability**
6. **Traceability**
7. **Security**
8. **Accountability**

These dimensions determine whether lineage can actually be trusted.

---

### 157. Completeness

**Completeness** asks:

> Are all required data relationships captured?

Example:

```text id="x7m3q8"
Required AI Datasets: 200
With Lineage:         194

Coverage = 97%
```

The organization should establish an acceptable threshold based on risk.

---

### 158. Accuracy

A lineage record may exist but still be wrong.

Example:

```text id="p4q8m2"
Documented:
CRM → AI Platform

Actual:
CRM → Data Lake → External API → AI Platform
```

The lineage is technically documented but operationally inaccurate.

Runtime validation can improve confidence.

---

### 159. Timeliness

Lineage should reflect relevant changes.

If an integration changes on Monday but the lineage repository is updated weeks later, governance visibility is reduced.

Therefore:

> **Lineage should be updated within a defined timeframe following material changes.**

---

### 160. Integrity

Lineage information should be protected from unauthorized modification.

Controls may include:

* Access controls.
* Immutable logging.
* Cryptographic hashes.
* Change monitoring.
* Separation of duties.
* Versioning.

---

### 161. Availability

Lineage should be available when needed for:

* Security investigations.
* Data-quality incidents.
* Privacy assessments.
* Regulatory reviews.
* Internal audits.
* Model investigations.

An unavailable lineage repository reduces its governance value.

---

### 200. Final Enterprise Data Lineage Framework

The complete concept can be summarized as:

```text id="v8m3q5"
                       DATA SOURCES
                            │
                            ▼
                      INGESTION
                            │
                            ▼
                       STORAGE
                            │
                            ▼
                    TRANSFORMATION
                            │
                            ▼
                        DATASETS
                            │
                ┌───────────┴───────────┐
                ▼                       ▼
             TRAINING                 RAG
                │                       │
                ▼                       ▼
             MODEL                 RETRIEVAL
                │                       │
                └───────────┬───────────┘
                            ▼
                     AI APPLICATION
                            │
                            ▼
                         OUTPUT
                            │
                            ▼
                    BUSINESS PROCESS
```

Across the entire flow, lineage should provide visibility into:

```text id="n7q4m8"
WHERE did the data come from?
WHERE did it go?
WHAT changed?
WHO owns it?
WHO accessed it?
WHICH models depend on it?
WHICH applications depend on those models?
WHAT happens if the source changes?
```

For an AI GRC professional, the most important principle is:

> **Data lineage converts complex data movement into a traceable dependency structure that can be governed, monitored, tested, and audited.**

The ultimate enterprise objective is **end-to-end, trustworthy, risk-based lineage** connecting:

```text id="c5m8q2"
SOURCE
   ↓
DATA
   ↓
TRANSFORMATION
   ↓
DATASET
   ↓
TRAINING / RETRIEVAL
   ↓
MODEL
   ↓
APPLICATION
   ↓
DECISION / OUTPUT
```

When implemented properly, data lineage becomes more than a technical diagram. It becomes a **GRC control capability** supporting **data governance, privacy, cybersecurity, AI risk management, data quality, regulatory compliance, incident response, model governance, third-party risk, and audit assurance**.

The key distinction from the previous topic remains important:

> **Data provenance establishes the history and origin of data; data lineage establishes the relationships and flow of data across the enterprise.**

Together, they provide the foundation for trustworthy AI data governance.


This creates stronger governance over AI data sharing.
