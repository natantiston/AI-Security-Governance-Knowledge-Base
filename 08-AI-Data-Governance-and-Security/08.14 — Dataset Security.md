# 08.14 — Dataset Security

## Part 1

### 1. Dataset Security Foundations

Dataset security is the discipline of protecting datasets used by AI systems against **unauthorized access, modification, destruction, disclosure, corruption, loss, and misuse**.

In AI environments, datasets can include:

* Training datasets.
* Fine-tuning datasets.
* Validation datasets.
* Test datasets.
* Evaluation datasets.
* Inference datasets.
* Reference datasets.
* RAG knowledge sources.
* Synthetic datasets.
* Feature datasets.
* Embedding-related data.

The objective is to ensure that datasets remain:

> **Confidential, trustworthy, available, traceable, and appropriately governed throughout their lifecycle.**

---

### 2. Why Dataset Security Matters

AI models are highly dependent on the quality and security of their underlying data.

A compromised dataset can result in:

```text
Dataset Compromise
       ↓
Incorrect / Manipulated Data
       ↓
Model Behavior Changes
       ↓
Incorrect AI Output
       ↓
Business / Security Impact
```

Therefore, dataset security is not simply a storage-security concern.

It can directly affect:

* Model behavior.
* AI reliability.
* Security decisions.
* Regulatory compliance.
* Privacy.
* Business operations.
* Intellectual property.
* Customer trust.

---

### 3. Dataset Security vs Data Governance

These concepts are related but different.

**Data governance** determines:

> What data may be collected, used, shared, retained, and for what purpose.

**Dataset security** determines:

> How that dataset is protected against unauthorized or harmful activity.

For example:

```text
Data Governance
      ↓
"Can this dataset be used for AI?"

Dataset Security
      ↓
"How do we protect the dataset?"
```

---

### 4. Dataset Security vs Data Quality

Data quality asks:

> Is the dataset accurate, complete, consistent, relevant, and fit for purpose?

Dataset security asks:

> Is the dataset protected against unauthorized access, alteration, destruction, or disclosure?

A dataset can therefore be:

```text
High Quality + Poor Security
```

or:

```text
Strong Security + Poor Quality
```

A mature AI program requires both.

---

### 5. Dataset Security Objectives

A dataset security program should address at least:

1. Confidentiality.
2. Integrity.
3. Availability.
4. Authenticity.
5. Accountability.
6. Traceability.
7. Controlled access.
8. Secure retention.
9. Secure transfer.
10. Secure disposal.

These objectives extend the traditional CIA triad.

---

### 6. Confidentiality

Confidentiality protects datasets from unauthorized disclosure.

Examples of sensitive dataset information include:

* Customer records.
* Employee information.
* Financial information.
* Source code.
* Security configurations.
* Business strategies.
* Proprietary research.
* Credentials.

Controls may include:

* Encryption.
* Access control.
* Data masking.
* Tokenization.
* DLP.
* Network segmentation.

---

### 7. Dataset Integrity

Dataset integrity ensures that information has not been modified without authorization.

Potential unauthorized changes include:

* Adding records.
* Removing records.
* Changing labels.
* Modifying values.
* Replacing files.
* Altering metadata.
* Manipulating dataset versions.

Integrity is particularly important because AI systems may learn from manipulated information.

---

### 8. Dataset Availability

Datasets must remain available when required by authorized AI processes.

Availability risks include:

* Storage failure.
* Accidental deletion.
* Ransomware.
* Infrastructure outage.
* Corrupted datasets.
* Failed data pipelines.
* Cloud-service disruption.

Availability controls may include:

* Backups.
* Replication.
* Redundancy.
* Disaster recovery.
* Versioned storage.

---

### 9. Dataset Authenticity

Authenticity establishes confidence that the dataset is actually what it claims to be.

Questions include:

* Who created it?
* Where did it originate?
* Was it altered?
* Is the source trusted?
* Is the dataset genuine?
* Can its origin be verified?

This becomes especially important when datasets are obtained from external sources.

---

### 10. Dataset Provenance

Dataset provenance describes the history and origin of a dataset.

It can answer:

```text
Where did the data come from?
        ↓
Who collected it?
        ↓
How was it transformed?
        ↓
Who modified it?
        ↓
Which version was used?
        ↓
Where was it used?
```

Provenance supports both security and governance.

---

### 11. Dataset Lineage

Dataset lineage describes how data moves and changes through processing.

Example:

```text
Source Systems
      ↓
Raw Dataset
      ↓
Cleaning
      ↓
Transformation
      ↓
Curated Dataset
      ↓
Training Dataset
      ↓
AI Model
```

Security controls should be considered at each stage.

---

### 12. Dataset Lifecycle

A dataset should be secured throughout its lifecycle:

```text
Create / Collect
      ↓
Ingest
      ↓
Store
      ↓
Process
      ↓
Transform
      ↓
Validate
      ↓
Use
      ↓
Share
      ↓
Archive
      ↓
Delete
```

Security cannot stop at the dataset repository.

---

### 13. Dataset Collection Security

Security begins when data is collected.

Organizations should establish:

* Authorized collection methods.
* Approved sources.
* Secure transfer mechanisms.
* Collection controls.
* Data classification.
* Validation procedures.

Unauthorized or uncontrolled data collection can introduce risk before the dataset even enters the AI environment.

---

### 14. Dataset Ingestion Security

Data ingestion is the process of bringing data into an AI environment.

Potential threats include:

* Malicious files.
* Unauthorized datasets.
* Corrupted data.
* Malware.
* Unexpected formats.
* Poisoned records.
* Excessive data.

Ingestion should therefore be treated as a security boundary.

---

### 15. Dataset Intake Controls

An enterprise dataset intake process can include:

```text
Dataset Submitted
       ↓
Source Verification
       ↓
Security Scan
       ↓
Classification
       ↓
Quality Validation
       ↓
Authorization
       ↓
Approved Repository
```

Only approved datasets should enter controlled AI environments.

---

### 16. Trusted Dataset Sources

Organizations should establish approved dataset sources.

Examples include:

* Internal enterprise systems.
* Approved data providers.
* Government datasets.
* Licensed datasets.
* Approved research repositories.
* Controlled synthetic-data platforms.

External sources should not automatically be considered trustworthy.

---

### 17. Untrusted Dataset Sources

Potentially untrusted sources include:

* Unknown websites.
* Unverified repositories.
* Anonymous uploads.
* Uncontrolled public datasets.
* Unapproved third-party providers.

The issue is not that public data is inherently unsafe.

The issue is:

> **The organization may not have sufficient assurance about its origin, integrity, licensing, or security.**

---

### 18. Dataset Repository Security

Datasets should be stored in controlled repositories.

Examples include:

* Object storage.
* Data lakes.
* Data warehouses.
* Database systems.
* Dataset management platforms.
* Model-development repositories.

The repository should enforce enterprise security controls.

---

### 19. Repository Access Control

Dataset repositories should implement least-privilege access.

Example:

```text
Data Scientist
→ Approved Training Dataset

Data Engineer
→ Data Pipeline Dataset

Data Owner
→ Dataset Governance

Security Team
→ Security Investigation

Administrator
→ Platform Administration
```

Access should be based on business need.

---

### 20. Dataset Ownership

Every important dataset should have an identified owner.

The owner may be responsible for:

* Business purpose.
* Classification.
* Access approval.
* Retention.
* Data quality expectations.
* Risk acceptance.
* Security requirements.

Without ownership, dataset governance becomes difficult to enforce.

---

### 21. Dataset Custodianship

A dataset owner and dataset custodian may have different responsibilities.

**Data Owner**

Determines:

> Who should be allowed to use the dataset?

**Data Custodian**

Implements:

> How is the dataset technically protected?

This separation supports governance and accountability.

---

### 22. Dataset Classification

Datasets should inherit or receive an appropriate classification.

Example:

| Classification | Dataset Example                       |
| -------------- | ------------------------------------- |
| Public         | Public research dataset               |
| Internal       | Internal operational dataset          |
| Confidential   | Customer dataset                      |
| Restricted     | Highly sensitive or regulated dataset |

Classification determines the required security controls.

---

### 23. Dataset Metadata

Security-relevant metadata may include:

* Dataset name.
* Owner.
* Source.
* Classification.
* Purpose.
* Creation date.
* Version.
* Retention period.
* Access groups.
* License.
* Geographic restrictions.

Metadata itself should be protected when it contains sensitive information.

---

### 24. Dataset Inventory

An enterprise should maintain an inventory of significant AI datasets.

A dataset inventory can answer:

```text
What datasets exist?
        ↓
Who owns them?
        ↓
Where are they stored?
        ↓
What classification do they have?
        ↓
Which AI systems use them?
        ↓
Who can access them?
```

This creates visibility for GRC and security teams.

---

### 25. Shadow Datasets

A security concern arises when teams create uncontrolled copies of enterprise datasets.

For example:

```text
Official Dataset
      ↓
Developer Copy
      ↓
Laptop Copy
      ↓
Cloud Storage Copy
      ↓
Personal Repository
```

Each copy creates another potential leakage or integrity risk.

---

### 26. Dataset Duplication

Dataset duplication should be governed.

Organizations should know:

* Why the copy exists.
* Where it is stored.
* Who owns it.
* Who can access it.
* How long it is retained.
* Whether it is synchronized with the original.

---

### 27. Dataset Copy Controls

Where possible:

> **Prefer controlled access to the authoritative dataset over uncontrolled duplication.**

If copies are necessary, they should inherit:

* Classification.
* Access controls.
* Retention requirements.
* Security requirements.

---

### 28. Dataset Encryption

Encryption should be considered for datasets:

* At rest.
* In transit.
* During transfer.
* In backups.

The required encryption level should depend on data sensitivity and organizational policy.

---

### 29. Encryption Key Management

Dataset encryption should be supported by appropriate key management.

Controls can include:

* Centralized key management.
* Access-controlled keys.
* Key rotation.
* Key usage monitoring.
* Separation of duties.

The encryption key itself must be protected as a security asset.

---

### 30. Dataset Access Logging

Access to sensitive datasets should be auditable.

Logs may capture:

* User or service identity.
* Dataset accessed.
* Timestamp.
* Action performed.
* Source system.
* Success/failure.
* Volume accessed.

This supports detection and investigations.

---

### 31. Dataset Activity Monitoring

Monitoring should identify unusual behavior.

Example:

```text
Normal Access
→ 500 records

Abnormal Access
→ 5 million records
```

Potential indicators include:

* Sudden bulk downloads.
* Access outside normal patterns.
* Repeated failed access.
* Access to previously unused datasets.
* Unusual geographic locations.

---

### 32. Dataset Download Controls

Bulk dataset downloads can create significant leakage risk.

Controls may include:

* Approval requirements.
* Download restrictions.
* DLP.
* Encryption.
* Watermarking.
* Monitoring.
* Volume limits.

---

### 33. Dataset Transfer Security

When datasets move between systems:

```text
Repository A
      ↓
Secure Transfer
      ↓
Repository B
```

The transfer should maintain:

* Confidentiality.
* Integrity.
* Authentication.
* Authorization.
* Traceability.

---

### 34. Dataset Integrity Verification

Integrity can be verified using mechanisms such as:

* Cryptographic hashes.
* Digital signatures.
* Checksums.
* Version identifiers.
* Trusted manifests.

Example:

```text
Dataset
   ↓
SHA-256 Hash
   ↓
Stored Reference
```

A later hash comparison can identify unauthorized modification.

---

### 35. Dataset Hashing

Hashing provides an integrity-verification mechanism.

Conceptually:

```text
Original Dataset
      ↓
Hash A

Current Dataset
      ↓
Hash B
```

If:

```text
Hash A ≠ Hash B
```

the dataset has changed.

A hash does not by itself prove whether the change was authorized.

---

### 36. Digital Signatures

Digital signatures can provide stronger authenticity and integrity assurance.

They can help establish:

* Who signed the dataset.
* Whether it was modified after signing.
* Whether the dataset came from an approved source.

This is particularly useful for high-value or externally supplied datasets.

---

### 37. Dataset Versioning

Datasets should be version-controlled where practical.

Example:

```text
Dataset v1.0
Dataset v1.1
Dataset v1.2
Dataset v2.0
```

Versioning allows teams to identify exactly which dataset was used for:

* Training.
* Validation.
* Testing.
* Evaluation.

---

### 38. Why Dataset Versioning Matters

Suppose a model performs poorly after retraining.

Without dataset versioning:

```text
Which data changed?
Unknown.
```

With versioning:

```text
Model v4
      ↓
Dataset v2.3
      ↓
Transformation Pipeline v5
```

The organization can investigate systematically.

---

### 39. Immutable Dataset Versions

For critical datasets, immutable versions can prevent unauthorized modification of historical data.

Example:

```text
Approved Dataset v3
       ↓
Immutable
       ↓
Used for Model Training
```

If a change is required, a new version is created instead of silently changing the old one.

---

### 40. Dataset Backup

Important datasets should be backed up according to their business criticality.

Backup considerations include:

* Frequency.
* Retention.
* Encryption.
* Geographic redundancy.
* Access control.
* Restoration testing.

A backup that cannot be restored is not a reliable recovery control.

---

### 41. Dataset Recovery

Recovery procedures should answer:

> How quickly can the organization restore an approved dataset?

Important parameters include:

* Recovery Point Objective (RPO).
* Recovery Time Objective (RTO).
* Backup frequency.
* Restoration procedures.

---

### 42. Dataset Backup Isolation

Backups should be protected from the same threats affecting production datasets.

For example:

```text
Production Dataset
       ↓
Backup
       ↓
Same Credentials
       ↓
Same Attack
```

This can allow a compromise to spread into backups.

Strong backup architecture should consider isolation and independent access controls.

---

### 43. Ransomware and Dataset Security

Ransomware can affect AI operations by encrypting or destroying datasets.

Potential impact includes:

* Training interruption.
* Model redevelopment.
* Loss of historical data.
* Loss of evaluation baselines.
* Business disruption.

Dataset recovery should therefore be included in ransomware resilience planning.

---

### 44. Dataset Repository Segmentation

Highly sensitive datasets may require separate security boundaries.

For example:

```text
Public Data
      │
Internal Data
      │
Confidential Data
      │
Restricted Data
```

Segmentation reduces unnecessary exposure.

---

### 45. Network Security

Dataset repositories should be protected using appropriate network controls such as:

* Network segmentation.
* Firewalls.
* Private endpoints.
* Access gateways.
* Secure APIs.
* Zero-trust access controls.

The objective is to prevent unauthorized network paths to sensitive datasets.

---

### 46. Dataset API Security

Datasets may be accessed through APIs.

API security should address:

* Authentication.
* Authorization.
* Rate limiting.
* Input validation.
* Output filtering.
* Logging.
* Encryption.

An API should expose only the data required for the authorized operation.

---

### 47. Dataset Service Accounts

Automated AI pipelines may use service accounts.

These accounts should have:

* Unique identities.
* Least privilege.
* Credential protection.
* Rotation.
* Monitoring.
* Defined ownership.

Shared service credentials should be avoided where possible.

---

### 48. Dataset Pipeline Security

A typical AI data pipeline may look like:

```text
Source
  ↓
Ingestion
  ↓
Validation
  ↓
Transformation
  ↓
Storage
  ↓
Training
```

Every stage can introduce security risk.

A secure pipeline must protect both the data and the mechanisms that process it.

---

### 49. Pipeline Authentication

Each pipeline component should authenticate appropriately.

For example:

```text
Ingestion Service
      ↓
Authenticated Connection
      ↓
Data Repository
```

Trust should not be based solely on network location.

---

### 50. Pipeline Authorization

A pipeline should only access the datasets necessary for its function.

Example:

```text
Training Pipeline
→ Training Dataset

Not:
→ HR Repository
→ Legal Repository
→ Finance Repository
```

This implements least privilege at the data-processing layer.

### 51. Dataset Access Control Architecture

Dataset security requires a structured access-control model that determines **who or what can access a dataset, what operations are permitted, and under what conditions**.

A typical architecture is:

```text
User / Service / AI Pipeline
            ↓
       Authentication
            ↓
       Authorization
            ↓
      Dataset Policy
            ↓
      Dataset Repository
            ↓
       Audit Logging
```

Authentication establishes identity.

Authorization determines whether that identity is permitted to perform the requested operation.

---

### 52. Dataset Authentication

Dataset access should require an identifiable identity.

Possible identities include:

* Human users.
* Applications.
* AI services.
* Data pipelines.
* Service accounts.
* Automated agents.

Anonymous access should generally be prohibited for sensitive datasets unless explicitly approved.

---

### 53. Dataset Authorization

Authorization should consider:

* User role.
* Dataset classification.
* Business purpose.
* Department.
* Environment.
* Tenant.
* Operation requested.

For example:

```text
User
 ↓
Finance Role
 ↓
Confidential Finance Dataset
 ↓
Read Access
```

The same user may not have access to an HR dataset.

---

### 54. Read vs Write Permissions

Dataset permissions should distinguish between operations.

Typical permissions include:

* Read.
* Create.
* Update.
* Delete.
* Export.
* Share.
* Approve.
* Administer.

A data scientist who needs to train a model may only require **read access**.

They should not automatically receive delete permissions.

---

### 55. Dataset Administrative Access

Administrative access should be tightly controlled.

Administrators may be capable of:

* Changing permissions.
* Deleting datasets.
* Modifying repositories.
* Exporting data.
* Changing retention.
* Disabling security controls.

Privileged access should therefore receive enhanced monitoring and governance.

---

### 56. Privileged Access Management

For sensitive datasets, privileged access management may provide:

* Just-in-time access.
* Approval workflows.
* Session recording.
* Credential vaulting.
* Time-limited permissions.
* Privileged activity monitoring.

This reduces the risk of permanent administrative access.

---

### 57. Role-Based Dataset Access

RBAC can associate dataset permissions with organizational roles.

Example:

```text
Data Scientist
→ Read Training Data

Data Engineer
→ Read / Write Pipeline Data

Data Owner
→ Approve Access

Security Administrator
→ Security Administration
```

Roles should be periodically reviewed.

---

### 58. Attribute-Based Dataset Access

ABAC provides more granular controls.

A policy could evaluate:

```text
User Department
+
Dataset Classification
+
Business Purpose
+
Environment
+
Device Trust
```

Example:

```text
IF
Department = Research
AND
Dataset = Research
AND
Environment = Development

THEN
Allow Read
```

---

### 59. Environment Separation

Dataset access should distinguish between:

* Development.
* Testing.
* Staging.
* Production.

Production datasets should not automatically be available in development environments.

```text
Production Data
      ↓
Controlled / Masked Copy
      ↓
Development
```

---

### 60. Development Dataset Security

Development environments often have weaker controls than production.

This creates risk when production information is copied into them.

Organizations should prefer:

* Synthetic data.
* Masked data.
* Tokenized data.
* Anonymized data where appropriate.

---

### 61. Test Dataset Security

Test datasets may contain realistic information.

They should therefore be governed similarly to production information when they contain sensitive data.

The label "test data" does not automatically make the information non-sensitive.

---

### 62. Dataset Segregation

Datasets should be segregated where required by:

* Classification.
* Business unit.
* Tenant.
* Regulatory requirement.
* Purpose.
* Environment.

Example:

```text
Tenant A
 └── Dataset A

Tenant B
 └── Dataset B
```

Access paths should prevent unauthorized cross-boundary access.

---

### 63. Multi-Tenant Dataset Security

Multi-tenant AI platforms create additional risks.

A failure could result in:

```text
Tenant A
    ↓
Unauthorized Query
    ↓
Tenant B Dataset
```

Tenant isolation should therefore be explicitly designed and tested.

---

### 64. Dataset Isolation

Isolation can be achieved through:

* Separate storage.
* Separate databases.
* Separate encryption keys.
* Tenant-aware authorization.
* Logical partitions.
* Network segmentation.

The required architecture depends on risk and platform design.

---

### 65. Dataset Access Reviews

Access to important datasets should be periodically reviewed.

The review should ask:

* Who has access?
* Why do they have access?
* Is access still required?
* Is the assigned role correct?
* Are excessive permissions present?
* Have inactive accounts been removed?

---

### 66. Joiner, Mover, Leaver Controls

Dataset access should align with workforce lifecycle processes.

**Joiner**

Grant only approved access.

**Mover**

Review and adjust access when the employee changes role.

**Leaver**

Remove access promptly when employment or authorization ends.

```text
Join → Approve
Move → Reassess
Leave → Revoke
```

---

### 67. Orphaned Dataset Accounts

Orphaned accounts can remain after:

* Employee departure.
* Project completion.
* Vendor termination.
* Application retirement.

These accounts can create unnecessary dataset exposure.

---

### 68. Temporary Dataset Access

Temporary access should have an expiration date.

Example:

```text
Access Granted
     ↓
Valid for 24 Hours
     ↓
Automatically Revoked
```

This is particularly useful for troubleshooting, investigations, and privileged operations.

---

### 69. Dataset Access Approval

Sensitive dataset access may require approval from the data owner.

Example:

```text
User Request
     ↓
Business Justification
     ↓
Data Owner Approval
     ↓
IAM Provisioning
     ↓
Time-Limited Access
```

This provides governance evidence.

---

### 70. Business Purpose

Access requests should identify the legitimate purpose.

For example:

> "Required to train the approved customer-support classification model."

This is stronger than:

> "Needed for AI project."

Purpose-based access improves accountability.

---

### 71. Dataset Usage Restrictions

Authorization can include usage conditions.

For example:

```text
Allowed:
Internal model training

Not Allowed:
External sharing
Public AI upload
Commercial redistribution
```

Access does not necessarily mean unrestricted use.

---

### 72. Data Use Policy Enforcement

Technical controls should support governance policies.

Example:

```text
Policy:
Restricted dataset cannot leave enterprise environment.

Technical Control:
External transfer blocked.

Monitoring:
Attempt logged.

Governance:
Exception requires formal approval.
```

This connects policy to technical enforcement.

---

### 73. Dataset Export Controls

Exporting a dataset can create substantial risk.

Controls may include:

* Export authorization.
* DLP.
* Volume restrictions.
* Encryption.
* Watermarking.
* Approval.
* Logging.

---

### 74. Bulk Export Detection

Bulk exports should be monitored.

Example:

```text
Normal:
100 records

Potentially Suspicious:
500,000 records
```

Large-volume activity should be evaluated based on business context.

---

### 75. Dataset Sharing

Dataset sharing should be controlled both internally and externally.

Before sharing, verify:

1. Recipient identity.
2. Authorization.
3. Business purpose.
4. Classification.
5. Contractual requirements.
6. Transfer mechanism.
7. Retention requirements.

---

### 76. External Dataset Sharing

External sharing introduces additional risk.

Potential recipients include:

* AI vendors.
* Consultants.
* Research partners.
* Cloud providers.
* Contractors.

External sharing should be explicitly governed.

---

### 77. Secure Dataset Transfer

A secure transfer should provide:

```text
Authentication
+
Authorization
+
Encryption
+
Integrity
+
Traceability
```

The organization should be able to demonstrate what was transferred and to whom.

---

### 78. Dataset Integrity Controls

Dataset security must protect against unauthorized modification.

Controls include:

* Hashing.
* Digital signatures.
* Immutable storage.
* Version control.
* Access restrictions.
* Change monitoring.

---

### 79. Change Management

Significant dataset changes should be governed through change management.

For example:

```text
Change Requested
      ↓
Impact Assessment
      ↓
Approval
      ↓
Implementation
      ↓
Validation
      ↓
Evidence
```

This is especially important for production datasets.

---

### 80. Dataset Change Logging

Changes should be traceable.

The organization should ideally know:

* Who changed the dataset.
* What changed.
* When it changed.
* Why it changed.
* Which version resulted.

---

### 81. Immutable Storage

For high-value datasets, immutable storage can prevent modification or deletion for a defined period.

This can be useful for:

* Audit datasets.
* Regulatory records.
* Security evidence.
* Approved training baselines.

---

### 82. Write Protection

Write protection can prevent unauthorized changes to finalized datasets.

Example:

```text
Approved Dataset
      ↓
Read-Only
      ↓
Model Training
```

If changes are required, a new controlled version can be created.

---

### 83. Dataset Version Control

Version control should capture:

* Version number.
* Creation date.
* Source.
* Transformation.
* Changes.
* Approver.
* Hash.
* Associated AI model.

This creates reproducibility and accountability.

---

### 84. Dataset-to-Model Traceability

An organization should be able to establish:

```text
Model v5
   ↓
Training Dataset v3.2
   ↓
Source Dataset v7
   ↓
Source System
```

This allows investigators to determine exactly which information contributed to a model.

---

### 85. Model Reproducibility

If a model needs to be reproduced, the organization should know:

* Dataset version.
* Code version.
* Transformation pipeline.
* Model version.
* Configuration.
* Training parameters.

Dataset security therefore supports broader AI lifecycle governance.

---

### 86. Dataset Pipeline Integrity

Data pipelines should be protected from unauthorized changes.

Threats include:

* Modified transformation code.
* Unauthorized pipeline execution.
* Malicious dependencies.
* Altered configuration.
* Manipulated source data.

Pipeline security directly affects dataset trustworthiness.

---

### 87. Pipeline Code Security

Dataset-processing code should use:

* Source control.
* Code review.
* Branch protection.
* CI/CD security.
* Dependency management.
* Change approval.

The pipeline is part of the dataset security boundary.

---

### 88. Pipeline Identity

Pipeline components should use identifiable service identities.

Avoid:

```text
One Shared Account
        ↓
All Data Pipelines
```

Prefer:

```text
Pipeline A → Identity A
Pipeline B → Identity B
Pipeline C → Identity C
```

This improves accountability and access control.

---

### 89. Pipeline Secrets

Pipeline credentials should be protected using appropriate secrets-management mechanisms.

Avoid embedding credentials directly in:

* Scripts.
* Source code.
* Configuration files.
* Dataset files.
* Notebooks.

---

### 90. Notebook Security

AI development notebooks can create dataset leakage risks.

A notebook may contain:

* Dataset samples.
* Credentials.
* Queries.
* Model outputs.
* Personal information.

### 101. Dataset Security Monitoring

Dataset security requires continuous monitoring to identify unauthorized access, unexpected changes, abnormal transfers, and other indicators of compromise.

Monitoring should provide visibility into:

* Who accessed the dataset.
* Which dataset was accessed.
* What operation was performed.
* When the activity occurred.
* From where the access originated.
* How much data was accessed.
* Whether the activity was authorized.

A mature monitoring capability connects dataset activity with broader enterprise security monitoring.

---

An audit trail should provide sufficient evidence to reconstruct significant dataset activity.

```text id="dsa01"

   ↓

   ↓

   ↓
```

* Permission changes.
* Dataset creation.
* Dataset deletion.
* Dataset export.
* Dataset sharing.
* Dataset modification.
* Dataset restoration.

### 105. Behavioral Monitoring

Static access rules may not detect every threat.

Behavioral monitoring can identify unusual patterns such as:

* Access at unusual times.
* Unusual geographic origin.
* Sudden increase in volume.
* Access to unrelated datasets.
* Repeated permission failures.
* Unusual administrative activity.

The objective is to identify deviations from expected behavior.

Anomaly detection can use:

* Historical activity.
* User behavior.
* Dataset sensitivity.
* Access frequency.
* Data volume.
* Geographic information.
* Time of access.

Risk-based detection is generally more useful than alerting on every dataset event.

### 108. Dataset DLP Monitoring

DLP controls can monitor attempts to move sensitive datasets outside approved boundaries.

Potential destinations include:

* Personal cloud storage.
* External email.
* USB devices.
* Public repositories.

* External APIs.

Potential indicators include:

* Unusual external connections.
* Unauthorized cloud synchronization.
* Data copied to unmanaged devices.

These indicators should be correlated with user context before determining whether an incident occurred.

| Restricted dataset bulk exported        | High     |

The exact severity model should align with enterprise SOC procedures.

### 175. Dataset Decommissioning

An AI dataset should be formally decommissioned when:

* Business purpose ends.
* Retention expires.
* Dataset becomes obsolete.

* Security risk becomes unacceptable.

### 190. Dataset Security Architecture Principles

A mature architecture should follow principles such as:

**Least privilege**

Only required access is granted.

**Defense in depth**

Multiple security controls protect important datasets.

**Secure by design**

Security requirements are established before deployment.

**Zero trust**

Access is continuously evaluated rather than automatically trusted.

**Separation of duties**

Critical actions are distributed among appropriate roles.

**Traceability**

Dataset activity can be reconstructed.

**Data minimization**

Only necessary data is retained and processed.

### 200. Dataset Security Control Framework

An enterprise dataset-security framework can be structured around eight control domains:

| Domain            | Primary Objective                       |
| ----------------- | --------------------------------------- |
| Governance        | Establish accountability                |
| Classification    | Determine protection requirements       |
| Access            | Restrict unauthorized use               |
| Protection        | Safeguard confidentiality and integrity |
| Pipeline Security | Secure data movement and transformation |
| Monitoring        | Detect abnormal activity                |
| Resilience        | Recover trusted datasets                |
| Assurance         | Demonstrate control effectiveness       |

These domains should operate together rather than as isolated security activities.
