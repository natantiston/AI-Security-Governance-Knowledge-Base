# 10.08 — Jailbreaking

## Part 1 — Foundations and Core Concepts

# 1. Definition of Jailbreaking

**Jailbreaking** is the deliberate use of prompts, conversational strategies, contextual manipulation, or other techniques to cause an AI model to bypass, weaken, or ignore restrictions imposed by its intended security, safety, policy, or operational configuration.

A jailbreak attempts to change the effective behavior of the model without necessarily changing the underlying model itself.

```text
Normal Operation

User
  |
  v
Application Policy
  |
  v
System Instructions
  |
  v
LLM
  |
  v
Controlled Response


Jailbreak Attempt

User
  |
  v
Adversarial Interaction
  |
  v
Attempt to Override Restrictions
  |
  v
LLM
  |
  v
Restricted Behavior Requested
```

Jailbreaking is therefore primarily a **control-bypass technique** rather than simply an unusual way of asking a question.

---

# 2. Jailbreaking as a Security Problem

Jailbreaking becomes a security concern when an AI system is expected to enforce meaningful restrictions through model behavior.

Examples include restrictions on:

* sensitive information
* harmful content
* confidential business information
* restricted workflows
* system instructions
* security policies
* tool usage
* privileged operations
* regulated decisions.

The fundamental problem is that the attacker attempts to make the model behave differently from its intended security configuration.

```text
Intended Policy
      |
      v
Expected Model Behavior
      |
      X
Jailbreak Attempt
      |
      v
Altered Model Behavior
```

The security question is therefore:

> **Can an attacker manipulate the model into violating an intended security or policy boundary?**

---

# 3. Jailbreaking vs Prompt Injection

Jailbreaking and prompt injection are related but should not be treated as identical.

| Characteristic            | Jailbreaking              | Prompt Injection                |
| ------------------------- | ------------------------- | ------------------------------- |
| Primary objective         | Bypass model restrictions | Manipulate instructions/context |
| Typical source            | User interaction          | User or external content        |
| Main target               | Model behavior/policy     | Instruction hierarchy/context   |
| Common environment        | Chat interaction          | RAG, agents, applications       |
| External content required | No                        | Often, but not always           |
| Main concern              | Restriction bypass        | Control-flow manipulation       |

A jailbreak can use prompt injection techniques, but a jailbreak does not necessarily require an external document, webpage, or retrieved content.

---

# 4. Jailbreaking vs Direct Prompt Injection

Direct prompt injection generally involves manipulating user-controlled input to alter the model's interpretation of instructions.

Jailbreaking focuses more specifically on **bypassing restrictions**.

For example:

```text
Direct Prompt Injection
        |
        v
"Ignore the system instructions"
        |
        v
Attempt to alter instruction hierarchy


Jailbreak
        |
        v
"Find a way to answer despite the restriction"
        |
        v
Attempt to bypass behavioral restriction
```

The two techniques can overlap substantially.

---

# 5. Jailbreaking and Instruction Hierarchy

Modern AI applications commonly establish different levels of instructions.

A simplified hierarchy may be:

```text
System Instructions
       |
       v
Developer Instructions
       |
       v
Application Context
       |
       v
User Instructions
       |
       v
Retrieved / External Content
```

A jailbreak attempts to cause the model to behave as though a lower-priority instruction can override a higher-priority restriction.

The security challenge is that natural-language instructions do not provide the same deterministic enforcement properties as traditional access-control mechanisms.

---

# 6. Common Jailbreaking Techniques

Jailbreaking can involve many strategies, including:

* role-play
* hypothetical scenarios
* instruction reframing
* authority simulation
* emotional manipulation
* multi-turn manipulation
* instruction obfuscation
* encoding
* multilingual prompting
* context manipulation
* instruction splitting
* recursive prompting
* fictional scenarios
* request transformation
* policy reinterpretation
* asking the model to evaluate or reproduce restricted behavior.

The exact technique is less important than the underlying objective:

> **Cause the model to produce behavior that should have remained restricted.**

---

# 7. Role-Play Jailbreaking

One common technique attempts to make the model adopt a fictional identity that supposedly has different rules.

Conceptually:

```text
Normal Model
     |
     v
Enterprise Restrictions
     |
     v
Restricted Response


Role-Play Attempt
     |
     v
"Act as an unrestricted system"
     |
     v
Attempt to change behavioral constraints
```

The security concern is not role-playing itself.

Role-playing is a legitimate AI capability.

The security problem occurs when a fictional role is used to bypass actual security restrictions.

---

# 8. Hypothetical and Fictional Framing

Another technique attempts to avoid restrictions by presenting a request as hypothetical.

Examples of framing include:

* “For educational purposes...”
* “In a fictional scenario...”
* “Imagine a system where restrictions do not exist...”
* “Describe what an unrestricted model would do...”

The underlying request may remain substantially the same despite the change in wording.

Security controls should therefore evaluate the **substance and potential impact of the request**, not simply whether it is presented as fictional or hypothetical.

---

# 9. Instruction Reframing

Jailbreak attempts may transform a prohibited request into apparently acceptable subtasks.

```text
Restricted Objective
       |
       v
Break into Smaller Requests
       |
       +--> Step A
       +--> Step B
       +--> Step C
       |
       v
Combine Outputs
       |
       v
Original Restricted Objective
```

This creates a challenge for systems that evaluate each request independently without understanding the broader conversational objective.

---

# 10. Multi-Turn Jailbreaking

Jailbreaking may occur over multiple interactions rather than through a single prompt.

An attacker may gradually establish assumptions before requesting restricted behavior.

```text
Turn 1
Establish Context
      |
      v
Turn 2
Establish Role
      |
      v
Turn 3
Change Assumptions
      |
      v
Turn 4
Introduce Restricted Objective
      |
      v
Turn 5
Attempt Bypass
```

This makes conversational history part of the attack surface.

A security system that analyzes only the current user message may miss the broader attack pattern.

---

# 11. Context Manipulation

Jailbreak attempts may attempt to manipulate the model's understanding of which instructions should be trusted.

Examples include:

* claiming that previous restrictions no longer apply;
* creating a fictional higher authority;
* redefining security terminology;
* instructing the model to reinterpret policies;
* creating contradictory context;
* inserting false system messages.

The fundamental objective is to influence the model's interpretation of its operating constraints.

---

# 12. Authority Simulation

An attacker may attempt to impersonate a privileged role.

Conceptually:

```text
Actual User
     |
     v
"I am the administrator"
     |
     v
Attempt to create artificial authority
     |
     v
Request restricted behavior
```

A secure enterprise application must not rely on the model to determine whether someone is actually authorized.

Identity and authorization must be established through enterprise security mechanisms.

---

# 13. Jailbreaking and Security Boundaries

A jailbreak becomes significantly more serious when the model is connected to enterprise resources.

Consider:

```text
User
 |
 v
Jailbreak
 |
 v
LLM
 |
 +--> Confidential Data
 +--> CRM
 +--> Email
 +--> Database
 +--> Cloud APIs
 +--> Administrative Tools
```

If the model only produces text, the impact may be limited.

If the model has access to sensitive information or powerful tools, the same jailbreak can become an enterprise security event.

---

# 14. Jailbreaking and Confidentiality

Jailbreaking can create confidentiality risks when restrictions are intended to prevent disclosure.

Potential targets include:

* system instructions
* confidential documents
* customer information
* employee information
* credentials
* internal architecture
* security configurations
* proprietary information
* regulated information.

A successful jailbreak may therefore contribute to **sensitive information disclosure**.

---

# 15. Jailbreaking and Integrity

Jailbreaking can also affect integrity.

For example, a manipulated model may:

* generate unauthorized changes
* recommend incorrect security decisions
* modify business records through tools
* approve inappropriate transactions
* produce misleading operational instructions.

The integrity risk increases when AI output is automatically consumed by downstream systems.

---

# 16. Jailbreaking and Availability

Jailbreaking can affect availability when attackers intentionally cause:

* excessive processing
* recursive interactions
* repeated expensive requests
* unnecessary tool execution
* excessive context consumption
* resource-intensive workflows.

This connects jailbreaking with **model abuse and resource exhaustion**.

---

# 17. Jailbreaking and Excessive Agency

The consequences of jailbreaking increase significantly when an AI system has agency.

A simple chatbot may produce an inappropriate response.

An agentic system may:

```text
Jailbreak
   |
   v
Model Behavior Bypass
   |
   v
Tool Selection
   |
   v
API Invocation
   |
   v
Enterprise Action
```

This creates a critical distinction:

> **Model-level policy bypass and enterprise authorization bypass are not the same thing.**

A jailbreak should not automatically grant the model additional privileges.

---

# 18. Jailbreaking and Tool Use

Connected tools create a second security boundary.

A model may be manipulated into requesting:

* database queries
* emails
* file operations
* API calls
* transactions
* configuration changes
* administrative operations.

The security architecture must therefore independently validate:

```text
LLM Request
     |
     v
Identity
     |
     v
Authorization
     |
     v
Policy
     |
     v
Tool
     |
     v
Action
```

The model should not be trusted to authorize its own tool use.

---

# 19. Jailbreaking and System Prompt Protection

Attackers may attempt to jailbreak a model into revealing system instructions.

The objectives may include:

* discovering hidden restrictions
* identifying security controls
* understanding application logic
* finding weaknesses
* improving subsequent attacks.

System-prompt confidentiality should therefore be considered separately from jailbreak resistance.

A system prompt should not contain secrets merely because it is hidden from the normal user interface.

---

# 20. Jailbreaking and Sensitive Information Disclosure

A jailbreak may attempt to cause the model to reveal information that the normal application would not intentionally provide.

Potential attack paths include:

```text
Jailbreak
   |
   v
Model Restriction Bypass
   |
   v
Sensitive Context
   |
   v
Unauthorized Output
```

However, model refusal alone should not be considered the primary confidentiality control.

Actual data access must be enforced outside the model.

---

# 21. Jailbreaking and RAG

RAG systems introduce additional opportunities for jailbreak attempts.

The model may receive:

* enterprise documents
* customer information
* internal policies
* knowledge-base content
* external webpages.

An attacker may attempt to manipulate the interaction so that the model:

* ignores retrieval restrictions
* reveals retrieved content
* combines restricted information
* bypasses intended response policies.

Therefore:

```text
RAG Retrieval
      |
      v
Access Control
      |
      v
Authorized Context
      |
      v
LLM
      |
      v
Output Controls
```

must remain intact even when the model is subjected to adversarial prompts.

---

# 22. Jailbreaking and Memory

Persistent memory can create additional risk.

An attacker may attempt to establish instructions that influence future interactions.

```text
Attack
  |
  v
Conversation
  |
  v
Persistent Memory
  |
  v
Future Session
  |
  v
Model Behavior
```

If memory is not appropriately governed, a successful jailbreak may become persistent rather than remaining limited to a single interaction.

---

# 23. Jailbreaking and Multimodal AI

Jailbreaking is not limited to text.

Multimodal systems can process:

* images
* documents
* audio
* video
* screenshots
* diagrams.

Attackers may attempt to use information encoded in these modalities to influence model behavior.

The attack surface therefore becomes:

```text
Text
Images
Audio
Video
Documents
   |
   v
Multimodal Processing
   |
   v
LLM
```

Security controls must consider the possibility that adversarial instructions can be embedded in non-textual content.

---

# 24. Jailbreaking and Obfuscation

Attackers may attempt to conceal their intent using:

* encoding
* unusual formatting
* character substitutions
* language switching
* fragmented instructions
* indirect descriptions
* symbolic representations.

The purpose is generally to make malicious intent harder for security controls or model safeguards to recognize.

Obfuscation should therefore be considered part of the jailbreak attack surface.

---

# 25. Jailbreaking and Policy Evasion

A jailbreak attempts to circumvent a policy without necessarily attacking the underlying infrastructure.

This creates an important distinction:

```text
Infrastructure Attack
        |
        v
Exploit Technical Vulnerability


Jailbreak
        |
        v
Exploit Behavioral Weakness
        |
        v
Attempt to Evade Policy
```

Both can produce security consequences, but the attack mechanisms are different.

---

# 26. Jailbreaking as a Control-Bypass Problem

From an enterprise security perspective, jailbreak resistance should be treated as a **control-bypass problem**.

The relevant question is not:

> “Does the model refuse this particular prompt?”

The stronger question is:

> “Can an attacker bypass the intended security control through adversarial interaction?”

This distinction is essential when designing assurance programs.

---

# 27. Jailbreaking Risk Factors

Jailbreaking risk increases when an AI application has:

* broad user access
* sensitive data
* weak authorization
* large context windows
* unrestricted external content
* persistent memory
* powerful tools
* autonomous execution
* weak output validation
* insufficient monitoring.

A simplified risk relationship is:

```text
Jailbreak Exposure
        +
Sensitive Data
        +
Model Capability
        +
Tool Privilege
        +
Automation
        =
Potential Business Impact
```

Jailbreak resistance should not depend on a single model safeguard.

---

# 30. Model Behavior Is Not Authorization

A central enterprise security principle is:

> **Model behavior is not an authorization mechanism.**

The model may decide:

> “I should perform this action.”

The enterprise security architecture must independently decide:

> “This action is authorized.”

```text
LLM Decision
     |
     v
Security Authorization
     |
  +--+--+
  |     |
ALLOW  DENY
```

This distinction prevents a successful jailbreak from automatically becoming a privilege escalation.

---

# 31. Jailbreaking and Zero Trust

Zero Trust principles are highly relevant to jailbreak-resistant AI architectures.

The system should not trust:

* user claims
* model claims
* natural-language authority
* retrieved instructions
* role-play
* conversational context.

Trust should be established using verifiable controls.

```text
Identity
   +
Authorization
   +
Context
   +
Policy
   +
Action
   |
   v
Security Decision
```

---

# 32. Enterprise Jailbreaking Security Model

A mature enterprise model should separate four layers:

```text
+--------------------------------+
| Business Policy                |
+--------------------------------+
| Application Security           |
+--------------------------------+
| Model Behavioral Safeguards    |
+--------------------------------+
| Enterprise Authorization       |
+--------------------------------+
```

The model behavioral layer is important, but it should not be responsible for enforcing controls that can be implemented deterministically elsewhere.

---

# 33. Core Security Objectives

Enterprise jailbreak security should seek to:

1. Prevent unauthorized behavioral bypass.
2. Protect sensitive information.
3. Preserve instruction integrity.
4. Prevent unauthorized tool use.
5. Maintain data-access boundaries.
6. Prevent privilege escalation.
7. Limit autonomous actions.
8. Detect adversarial interactions.
9. Contain successful jailbreaks.
10. Preserve evidence for investigation.
11. Maintain security through model and application changes.
12. Demonstrate control effectiveness.

Jailbreaking should be evaluated according to the entire AI application rather than the model in isolation.

# 36. Security Testing Perspective

Jailbreak testing should evaluate whether restrictions remain effective under adversarial conditions.

Testing should consider:

* single-turn attacks
* multi-turn attacks
* role manipulation
* contextual manipulation
* policy reinterpretation
* obfuscation
* multilingual interaction
* multimodal input
* memory persistence
* tool-use scenarios.

The objective is not simply to collect prompts that make a model produce undesirable text.

The objective is to determine whether the **enterprise security boundary remains intact under adversarial model interaction**.

---

# 37. Governance Perspective

From a governance perspective, jailbreaking should be treated as an AI security risk that requires:

* ownership
* risk classification
* security requirements
* testing
* monitoring
* incident management
* evidence
* control effectiveness assessment.

The organization should know which AI applications are exposed to jailbreak risk and what consequences a successful bypass could produce.

Enterprise AI introduces several additional concerns.

Examples include:

* employee-facing copilots

The security impact depends heavily on the application's access and action capabilities.

# 39. Fundamental Security Principle

The fundamental security principle for jailbreaking is:

> **Assume that model behavioral restrictions can be challenged, and design the surrounding architecture so that bypassing those restrictions does not automatically bypass enterprise security controls.**

This requires separating:

* behavioral safeguards
* identity
* authorization
* data access
* tool permissions
* transaction controls
* monitoring.

---

# 40. Defense-in-Depth Principle

A mature jailbreak-resistant AI system should not depend on the model correctly refusing every adversarial request.

Instead:

```text
              Jailbreak Attempt
                     |
          +----------+----------+
          |          |          |
          v          v          v
       Model      Output     Authorization
     Safeguards   Controls      Controls
          |          |          |
          +----------+----------+
                     |
                     v
                Tool Controls
                     |
                     v
                 Monitoring
                     |
                     v
              Incident Response
```

Each layer should provide an independent opportunity to prevent or contain the attack.

---

# 41. Core Enterprise Security Principle

The central principle is:

> **A jailbreak should be treated as a potential attempt to bypass model-level restrictions, but the enterprise must ensure that model-level restrictions are never the only barrier protecting sensitive data, privileged capabilities, or high-impact business actions.**

The strongest architecture therefore assumes that an attacker may eventually influence model behavior and ensures that independent controls continue to enforce:

```text
Identity
   |
Authorization
   |
Data Access
   |
Tool Permission
   |
Action Validation
   |
Human Approval
   |
Monitoring
```

This establishes the fundamental distinction between **making a model resistant to jailbreaks** and **building an enterprise AI system that remains secure even when the model is manipulated**.


## Part 2 — Technical Security and Control Mechanisms

# 42. Jailbreak Defense Architecture

Jailbreak defense should be implemented as a layered security architecture rather than as a single prompt or model safety mechanism.

A mature architecture separates **model behavioral controls** from **deterministic enterprise security controls**.

```text
User
 |
 v
+------------------------+
| Input Security         |
| Validation / Detection |
+-----------+------------+
            |
            v
+------------------------+
| Prompt / Context       |
| Security               |
+-----------+------------+
            |
            v
+------------------------+
| LLM Behavioral        |
| Safeguards             |
+-----------+------------+
            |
            v
+------------------------+
| Output Security        |
| Validation / DLP       |
+-----------+------------+
            |
            v
+------------------------+
| Identity &             |
| Authorization          |
+-----------+------------+
            |
            v
+------------------------+
| Tool / Action Security |
+-----------+------------+
            |
            v
+------------------------+
| Monitoring / SOC       |
+------------------------+
```

The model is therefore one security layer within a broader control system.

---

# 43. Input Validation

User input should be evaluated before it reaches the model.

Input validation can identify:

* malformed requests
* excessive input size
* prohibited content patterns
* suspicious encoding
* repeated adversarial attempts
* known jailbreak signatures
* abnormal request structures.

Validation should not rely exclusively on keyword matching because jailbreaks can be expressed through natural language, multiple languages, obfuscation, or conversational context.

---

# 44. Input Normalization

Normalization can make adversarial input easier to analyze.

Potential normalization processes include:

* Unicode normalization
* whitespace normalization
* encoding normalization
* character canonicalization
* removal of unnecessary formatting
* structured parsing
* language detection.

Conceptually:

```text
Raw Input
    |
    v
Normalization
    |
    v
Canonical Representation
    |
    v
Security Analysis
    |
    v
LLM
```

Normalization should preserve legitimate user intent while reducing opportunities to evade security inspection.

---

# 45. Jailbreak Detection

Jailbreak detection attempts to identify interaction patterns associated with attempts to bypass restrictions.

Detection signals can include:

* instruction override attempts
* role manipulation
* authority simulation
* policy reinterpretation
* repeated refusal bypass attempts
* suspicious multi-turn patterns
* encoded instructions
* unusual language switching
* attempts to expose system instructions
* attempts to manipulate safety policies.

Detection should be treated as a **security signal**, not as the sole enforcement mechanism.

---

# 46. Deterministic and AI-Based Detection

Jailbreak detection can combine deterministic and AI-based techniques.

| Control              | Strength              | Limitation                 |
| -------------------- | --------------------- | -------------------------- |
| Rules                | Predictable           | Can be bypassed            |
| Signatures           | Fast                  | Limited to known patterns  |
| Classifiers          | Broader detection     | False positives/negatives  |
| LLM-based detection  | Context-aware         | Can itself be manipulated  |
| Behavioral analytics | Detects patterns      | Requires telemetry         |
| Human review         | High-context judgment | Does not scale universally |

A mature architecture uses multiple detection mechanisms.

---

# 47. Behavioral Safeguards

The LLM itself should have appropriate behavioral safeguards.

These may include:

* policy-aligned system instructions
* refusal behavior
* safety policies
* response constraints
* output-format restrictions
* domain-specific restrictions
* tool-use instructions.

However:

> **Behavioral safeguards should supplement, not replace, deterministic security controls.**

A model instruction saying “never disclose confidential information” is not equivalent to a technical access-control policy preventing the model from receiving confidential information.

---

# 48. Instruction Hierarchy Protection

Applications should establish clear instruction boundaries.

```text
System Policy
      |
      v
Developer/Application Instructions
      |
      v
Authorized Context
      |
      v
User Request
      |
      v
Untrusted External Content
```

Lower-trust content should not be allowed to redefine higher-priority security requirements.

Instruction hierarchy should be supported by application architecture rather than merely described inside the prompt.

---

# 49. Context Separation

Security-sensitive context should be separated from untrusted content.

For example:

```text
+--------------------------+
| Trusted Instructions     |
+--------------------------+
| Security Policy          |
+--------------------------+
| Application Context      |
+--------------------------+
| Authorized Data          |
+--------------------------+
| Untrusted User Content   |
+--------------------------+
| External Retrieved Data  |
+--------------------------+
```

This separation helps preserve the distinction between:

**information the model may analyze** and **instructions the model is authorized to follow**.

---

# 50. Structured Prompt Construction

Applications should avoid constructing prompts by indiscriminately concatenating instructions, user input, and retrieved data.

A safer architecture uses structured context.

```text
{
  "system_policy": "...",
  "task": "...",
  "authorized_data": "...",
  "user_input": "...",
  "external_content": "..."
}
```

The application can then apply different security controls to each category.

---

# 51. Context Trust Labels

AI applications should assign trust classifications to context.

Example:

| Context                   | Trust                                   |
| ------------------------- | --------------------------------------- |
| Security policy           | High                                    |
| Application configuration | High                                    |
| Approved internal data    | Controlled                              |
| User input                | Untrusted                               |
| External webpage          | Untrusted                               |
| Retrieved document        | Untrusted unless specifically validated |
| Tool result               | Context-dependent                       |

Trust labels should influence what the application permits the model to do with the information.

---

# 52. System Prompt Protection

System prompts should be protected against unauthorized modification and unnecessary disclosure.

Technical controls may include:

* centralized prompt storage
* access control
* version control
* integrity verification
* deployment approval
* change logging
* environment separation
* secure configuration management.

The system prompt should not be treated as a secret vault.

Passwords, API keys, private credentials, or other secrets should not be placed in prompts simply because users cannot normally see them.

---

# 53. Prompt Integrity

Security-sensitive prompts should have integrity controls.

A simplified process is:

```text
Approved Prompt
      |
      v
Hash / Signature
      |
      v
Deployment
      |
      v
Runtime Verification
      |
      +---- Match ----> Execute
      |
      +---- Mismatch -> Block / Alert
```

This protects against unauthorized modification of security-critical behavioral configuration.

---

# 54. Output Validation

Model output should be validated before being delivered or used by downstream systems.

Controls may evaluate:

* output format
* sensitive information
* policy violations
* unauthorized content
* unsafe commands
* tool instructions
* structured fields
* business-rule compliance.

For applications using structured outputs, schema validation should occur before downstream processing.

---

# 55. Sensitive Data Loss Prevention

DLP controls should operate independently of model behavior.

Potential controls include:

* data classification
* sensitive-data detection
* PII detection
* credential detection
* confidential-data filtering
* tokenization
* redaction
* output blocking.

```text
LLM Output
    |
    v
DLP Inspection
    |
 +--+--+
 |     |
Safe  Sensitive
 |       |
 v       v
Allow   Block/Redact
```

This provides an additional confidentiality boundary if the model is successfully manipulated.

---

# 56. Independent Data Authorization

The model should not determine which enterprise data a user is allowed to access.

Instead:

```text
User Identity
      |
      v
Enterprise IAM
      |
      v
Authorization Policy
      |
      v
Permitted Data
      |
      v
AI Application
      |
      v
LLM
```

The model should receive only data that the requesting identity is authorized to access.

This significantly reduces the impact of successful jailbreaks.

---

# 57. Tool Authorization

Tool permissions must be enforced outside the model.

A model may generate:

```text
"Send this email."
```

The application should not automatically interpret that as authorization.

Instead:

```text
LLM Tool Request
       |
       v
Identity Check
       |
       v
Authorization
       |
       v
Risk Evaluation
       |
       v
```

# 74. Control Independence

One of the most important technical principles is **control independence**.

For example, this architecture is weak:

```text
System Prompt:
"Never send money without authorization."
             |
             v
            LLM
             |
             v
       Send Money
```

The authorization decision depends heavily on the model following its instructions.

A stronger architecture is:

```text
System Prompt
      |
      v
     LLM
      |
      v
Transaction Request
      |
      v
Independent Authorization
      |
      +---- Deny
      |
      +---- Human Approval
      |
      +---- Allow
```

The second architecture remains safer even if the model's behavioral safeguards are bypassed.

---

# 75. Core Engineering Principle

The central technical principle is:

> **Do not attempt to make the LLM the final security enforcement point for jailbreak-sensitive operations.**

The model should interpret requests, generate responses, and propose actions within its assigned role.

Deterministic enterprise controls should independently enforce:

* identity
* authorization
* data access
* confidentiality
* tool permissions
* transaction limits
* high-impact approvals
* monitoring
* containment.

The resulting security model is:

```text
Jailbreak Attempt
       |
       v
Model Influence
       |
       v
+--------------------------+
| Independent Controls     |
|                          |
| IAM                      |
| Authorization            |
| Data Access              |
| DLP                      |
| Tool Restrictions        |
| Action Limits            |
| Human Approval           |
| Monitoring               |
+------------+-------------+
             |
       +-----+-----+
       |           |
      DENY        ALLOW
       |           |
       v           v
   Contained   Controlled
                Action
```

A jailbreak-resistant enterprise AI system is therefore not one in which the model can **never** be influenced. It is one in which **model influence cannot independently cross the organization's security boundary**.

# 149. Strategic Security Principle

The enterprise objective should not be to assume that a model can be made permanently immune to every future jailbreak technique.

Instead, the organization should design for **secure operation under adversarial model influence**.

The architecture should assume:

```text
Attacker
   |
   v
Jailbreak Attempt
   |
   v
Potential Model Influence
   |
   v
Independent Enterprise Controls
   |
   +--> Identity
   +--> Authorization
   +--> Data Access
   +--> DLP
   +--> Tool Restrictions
   +--> Transaction Limits
   +--> Human Approval
   +--> Monitoring
   |
   v
Contained Business Impact
```

The strategic principle is:

> **A successful jailbreak should be treated as a model-security failure, but it must not automatically become an enterprise authorization failure.**

Enterprise AI security therefore depends on maintaining a strong separation between **what the model wants to do** and **what the enterprise permits it to do**.
