# 10.14 — Data Extraction Attacks

## Part 1 — Foundations and Core Concepts

# 1. Definition of Data Extraction Attacks

Data extraction attacks are attempts to cause an AI system to reveal, reconstruct, retrieve, or reproduce information that the requester is not authorized to obtain.

The targeted information may include:

* training data;
* fine-tuning data;
* system instructions;
* confidential documents;
* RAG knowledge;
* personal information;
* credentials or secrets;
* proprietary business information;
* model-generated representations;
* previous conversation information;
* information belonging to another tenant or user.

The attack is fundamentally concerned with **unauthorized information disclosure through an AI system**.

---

# 2. Data Extraction as an AI Security Threat

Traditional applications generally expose data through explicit interfaces such as databases, APIs, files, or application screens.

AI systems introduce an additional disclosure interface:

```text
Sensitive Data
      |
      v
 AI Processing
      |
      v
 Model / RAG / Memory
      |
      v
Natural-Language Interface
      |
      v
 Attacker
```

An attacker may therefore attempt to use natural-language interaction, retrieval behavior, model inference, or connected tools to obtain information that should remain protected.

---

# 3. The Fundamental Security Problem

The fundamental problem is that an AI system may have access to information that the requester should not be able to access directly.

The model can potentially transform, summarize, retrieve, infer, or reproduce information.

Therefore:

> **Model access must not be treated as equivalent to authorization to access every piece of information available to the model.**

The AI system must enforce authorization independently of the model's ability to process information.

---

# 4. Data Extraction vs Normal Data Retrieval

Legitimate data retrieval occurs when:

```text
Authorized User
      |
      v
Authorization Check
      |
      v
Approved Data
      |
      v
Response
```

Data extraction occurs when the attacker attempts to bypass, manipulate, or exploit that process:

```text
Attacker
   |
   v
AI Interface
   |
   +----> Prompt Manipulation
   |
   +----> Retrieval Abuse
   |
   +----> Context Leakage
   |
   +----> Tool Abuse
   |
   +----> Model Probing
   |
   v
Unauthorized Information
```

The difference is therefore primarily one of **authorization and security boundary enforcement**.

---

# 5. Data Extraction vs Data Exfiltration

Data extraction and data exfiltration are related but not identical.

**Data extraction** focuses on obtaining information from the AI system.

**Data exfiltration** focuses on transferring protected information outside its authorized security boundary.

An AI extraction attack can therefore become an exfiltration event when the attacker successfully obtains sensitive information and moves it outside the organization.

---

# 6. Data Extraction vs Model Inversion

Model inversion attempts to infer characteristics or information associated with data learned by a model.

Data extraction is broader.

It can include:

* direct reproduction;
* retrieval of stored documents;
* extraction of system information;
* secret disclosure;
* conversation leakage;
* RAG document retrieval;
* tool-mediated extraction;
* training-data extraction.

A single AI application may be exposed to both threats simultaneously.

---

# 7. Data Extraction vs Membership Inference

Membership inference attempts to determine whether a particular record was included in a dataset used by a model.

Data extraction attempts to obtain the information itself.

For example:

```text
Membership Inference:
"Was John Smith's record used?"

Data Extraction:
"What information about John Smith can you provide?"
```

Membership inference is therefore primarily concerned with **membership**, while extraction is concerned with **obtaining information**.

---

# 8. Data Extraction vs Prompt Injection

Prompt injection is an attack technique.

Data extraction is often an attack objective.

For example:

```text
Prompt Injection
      |
      v
Instruction Manipulation
      |
      v
Security Boundary Bypass
      |
      v
Data Extraction
```

An attacker may use prompt injection to persuade the model to reveal information that should not be disclosed.

Therefore, prompt injection and data extraction should not be treated as mutually exclusive threats.

---

# 9. Data Extraction vs System Prompt Leakage

System prompt leakage specifically targets system instructions or configuration information.

Data extraction is broader and may target:

* system prompts;
* RAG documents;
* user information;
* training data;
* secrets;
* databases;
* API responses;
* tool outputs;
* conversation history.

System prompt leakage can therefore be considered one possible form of AI information extraction.

---

# 10. Direct Data Extraction

Direct extraction occurs when the attacker explicitly requests protected information.

Examples include requests for:

* confidential records;
* previous conversation contents;
* internal policies;
* restricted documents;
* credentials;
* private user information.

The attack may be obvious, but simple requests should not automatically be assumed to be harmless.

---

# 11. Indirect Data Extraction

Indirect extraction occurs when the attacker manipulates an intermediate component to expose information.

Potential intermediaries include:

* RAG systems;
* web retrieval;
* email processing;
* databases;
* APIs;
* plugins;
* tools;
* memory;
* enterprise search.

```text
Attacker
   |
   v
AI Application
   |
   v
Connected Component
   |
   v
Sensitive Data
   |
   v
AI Response
```

This is particularly important in agentic AI systems.

---

# 12. Training Data Extraction

Training-data extraction attempts to cause a model to reproduce information contained in training data.

The risk may increase when training data contains:

* unique records;
* secrets;
* personal information;
* proprietary documents;
* credentials;
* highly repetitive information.

Memorization can create conditions in which information is more reproducible.

---

# 13. Fine-Tuning Data Extraction

Fine-tuning can introduce organization-specific information into model behavior.

Examples include:

* internal procedures;
* proprietary terminology;
* customer information;
* technical documentation;
* private datasets.

If improperly protected, an attacker may attempt to use the resulting model as an information-disclosure interface.

---

# 14. RAG Data Extraction

RAG systems introduce a distinct extraction surface.

```text
User
 |
 v
AI Application
 |
 v
Retriever
 |
 v
Vector Database
 |
 v
Documents
 |
 v
Context
 |
 v
LLM
 |
 v
Response
```

If retrieval authorization is incorrectly implemented, a user may obtain documents that they could not legitimately access.

---

# 15. Knowledge-Base Extraction

Enterprise knowledge bases may contain:

* contracts;
* customer information;
* internal procedures;
* financial documents;
* security documentation;
* intellectual property;
* employee information.

The AI interface can unintentionally become an alternative search interface that bypasses normal access controls.

---

# 16. Vector Database Extraction

Vector databases can become targets because they may contain representations associated with sensitive documents.

Potential risks include:

* unauthorized retrieval;
* cross-tenant retrieval;
* metadata exposure;
* document reconstruction;
* embedding access;
* similarity-query abuse.

Vector access must therefore be governed independently from the LLM.

---

# 17. Conversation Data Extraction

AI applications may store:

* prompts;
* responses;
* uploaded documents;
* user identifiers;
* session information;
* tool results;
* conversation history.

Attackers may attempt to retrieve another user's historical information through:

* session manipulation;
* authorization flaws;
* prompt injection;
* identifier manipulation;
* application vulnerabilities.

Conversation history should therefore be treated as protected enterprise data.

---

# 18. Memory-Based Extraction

Long-term AI memory creates another potential information source.

```text
User A
  |
  v
Memory Store
  |
  +---- Personal Information
  +---- Preferences
  +---- Previous Conversations
  +---- Business Context
  |
  v
AI Model
```

If memory is not properly scoped, information associated with one user, tenant, or business process may become available to another.

---

# 19. Tool-Mediated Data Extraction

AI agents may have access to tools such as:

* databases;
* CRM systems;
* cloud storage;
* email;
* ticketing systems;
* APIs;
* internal search;
* financial systems.

An attacker may attempt to manipulate the model into invoking those tools inappropriately.

The resulting attack chain can be:

```text
Attacker
   |
   v
Prompt Manipulation
   |
   v
Agent
   |
   v
Tool Invocation
   |
   v
Protected System
   |
   v
Sensitive Data
   |
   v
Attacker
```

Tool authorization must therefore exist outside the model.

---

# 20. API-Based Data Extraction

AI applications frequently depend on APIs.

An extraction attack may target:

* excessive API permissions;
* weak object-level authorization;
* predictable identifiers;
* unrestricted search;
* excessive response fields;
* insufficient tenant filtering.

The AI model may simply become the interface through which an underlying API weakness is exploited.

---

# 21. Data Extraction Through Excessive Agency

Excessive agency occurs when an AI system can perform actions or retrieve information beyond what is necessary for its business purpose.

For example:

```text
Business Need:
Read Customer A's Support Ticket

Actual Capability:
Read All Customer Tickets
       +
Search CRM
       +
Export Records
       +
Send Email
```

The broader the model's authority, the greater the potential extraction impact.

---

# 22. Data Extraction and Least Privilege

Least privilege is therefore fundamental.

An AI application should receive only:

* the data it needs;
* the tools it needs;
* the fields it needs;
* the actions it needs;
* the access duration it needs.

The model should not receive unrestricted access simply because doing so simplifies application development.

---

# 23. Data Extraction and Confidentiality

Confidentiality is the primary security objective affected by extraction.

```text
Unauthorized Request
       |
       v
Protected Information
       |
       v
Unauthorized Disclosure
       |
       v
Confidentiality Loss
```

However, extraction can also support integrity and availability attacks when obtained information is subsequently used to manipulate systems or disrupt operations.

---

# 24. Data Extraction and Privacy

Privacy risk arises when extracted information relates to identifiable individuals.

Potentially sensitive information includes:

* identity information;
* financial information;
* employment information;
* communications;
* customer records;
* behavioral information;
* authentication information.

The organization must consider not only whether data can be accessed, but whether it can be **reconstructed or disclosed through AI interaction**.

---

# 25. Data Extraction and Integrity

Extraction can expose information that enables subsequent attacks.

For example:

```text
Information Extraction
        |
        v
Reconnaissance
        |
        v
Security Detail Discovery
        |
        v
Targeted Manipulation
        |
        v
Integrity Attack
```

Sensitive information disclosure can therefore increase the probability of later compromise.

---

# 26. Data Extraction and Availability

Extraction attacks may also consume significant resources.

An attacker could generate:

* excessive queries;
* repeated retrieval operations;
* large document requests;
* expensive agent workflows;
* repeated model calls.

This can create:

* latency;
* resource exhaustion;
* increased infrastructure cost;
* service degradation.

Therefore, extraction protection should include resource controls.

---

# 27. Data Extraction Attack Surface

The enterprise attack surface can include:

```text
                 AI Application
                      |
       +--------------+--------------+
       |              |              |
     Model           RAG           Memory
       |              |              |
     Prompt        Documents      History
       |              |              |
       +--------------+--------------+
                      |
                 Agent / Tools
                      |
          +-----------+-----------+
          |           |           |
        APIs       Databases     SaaS
```

Every connected information source becomes potentially relevant to data-extraction risk.

---

# 28. Trusted Systems Can Still Become Extraction Sources

A common misconception is:

> "The data comes from an approved enterprise system, so it is safe."

The source may be trusted while the **requester's authorization is not**.

For example:

```text
Trusted Database
      |
      v
Trusted API
      |
      v
Poor Authorization
      |
      v
AI Application
      |
      v
Unauthorized User
```

Trust in the source does not eliminate the need for authorization at the point of access.

---

# 29. Data Provenance vs Data Authorization

Provenance answers:

> Where did this information come from?

Authorization answers:

> Who is allowed to receive it?

These are different security questions.

```text
Document
   |
   +--> Provenance: Internal HR System
   |
   +--> Authorization: User NOT permitted
```

A document can have excellent provenance and still be unauthorized for a particular user.

---

# 30. Data Extraction Through Context Manipulation

Attackers may attempt to influence the context supplied to the model.

Potential methods include:

* prompt injection;
* malicious documents;
* manipulated retrieval queries;
* conversation-state manipulation;
* memory poisoning;
* conflicting instructions.

The objective may be to cause the model to disclose information from a protected context.

---

# 31. Multi-Turn Data Extraction

Extraction does not always occur in a single interaction.

An attacker may gradually probe the system:

```text
Query 1
  |
  v
Small Information
  |
  v
Query 2
  |
  v
Additional Information
  |
  v
Query 3
  |
  v
More Information
  |
  v
Combined Dataset
```

Individually harmless responses may collectively disclose sensitive information.

Security monitoring should therefore analyze interaction sequences.

---

# 32. Extraction Through Transformation

An attacker may avoid explicitly asking for protected information and instead request transformations.

Examples of transformation objectives include:

* summarization;
* translation;
* classification;
* formatting;
* comparison;
* conversion;
* extraction into structured fields.

The security issue is not the transformation itself.

The issue is whether the transformation causes protected information to cross an authorization boundary.

---

# 33. Extraction Through Aggregation

Sensitive information can sometimes be reconstructed through multiple individually permitted responses.

```text
Response A
    +
Response B
    +
Response C
    +
Response D
    |
    v
Sensitive Picture
```

This is an important reason to consider cumulative disclosure rather than evaluating every response independently.

---

# 34. Extraction Through Metadata

Attackers may target metadata instead of the underlying document.

Potentially sensitive metadata includes:

* document names;
* usernames;
* timestamps;
* record counts;
* database fields;
* source identifiers;
* system names;
* access patterns.

Metadata can provide valuable reconnaissance even when document content itself is protected.

---

# 35. Extraction Through Error Messages

AI applications may unintentionally expose information through errors.

Examples include:

* database errors;
* API responses;
* tool failures;
* retrieval errors;
* stack traces;
* internal identifiers;
* provider messages.

Error handling should therefore be treated as part of the AI data-disclosure boundary.

---

# 36. Extraction Through System and Tool Descriptions

AI applications may expose descriptions of:

* available tools;
* API capabilities;
* database schemas;
* internal workflows;
* system architecture.

Even when these descriptions do not contain the target data, they may provide reconnaissance information that makes subsequent extraction easier.

---

# 37. Data Extraction Attack Lifecycle

A generalized extraction attack may follow:

```text
Reconnaissance
      |
      v
Identify Data Source
      |
      v
Identify AI Interface
      |
      v
Probe Authorization
      |
      v
Manipulate Interaction
      |
      v
Retrieve / Infer Data
      |
      v
Aggregate Information
      |
      v
Exfiltrate
      |
      v
Reuse Information
```

Not every attack requires every stage.

---

# 38. Factors Increasing Data Extraction Risk

Risk increases when an AI system has:

* broad data access;
* weak authorization;
* excessive model context;
* unrestricted RAG;
* unrestricted tool access;
* long-term memory;
* large output limits;
* weak tenant isolation;
* detailed API responses;
* poor monitoring;
* sensitive training data;
* weak query controls.

The combination of several weaknesses can create significant exposure.

---

# 39. Data Extraction and Agentic AI

Agentic AI increases extraction risk because the model may decide which information sources to access.

```text
User
 |
 v
Agent
 |
 +--> Search
 |
 +--> Database
 |
 +--> CRM
 |
 +--> Files
 |
 +--> API
 |
 v
Collected Context
 |
 v
Model
 |
 v
Response
```

The agent must not be allowed to turn its reasoning capability into unrestricted enterprise data access.

---

# 40. Data Extraction and Zero Trust

Zero Trust principles require every data request to be evaluated independently.

```text
Identity
   +
Device / Application
   +
Tenant
   +
Purpose
   +
Data Classification
   +
Requested Operation
   |
   v
Authorization Decision
   |
   v
Allow / Deny / Review
```

The model should not be considered inherently trusted merely because it operates inside the corporate environment.

---

# 41. Data Extraction Security Boundaries

The security boundary should include:

* data repositories;
* retrieval systems;
* vector databases;
* model context;
* memory;
* model APIs;
* agent tools;
* application sessions;
* outputs;
* logging;
* monitoring.

A narrow database-centric security boundary is insufficient for modern AI architectures.

---

# 42. Data Extraction and High-Impact AI

Extraction risk becomes particularly significant when AI systems process information associated with high-impact decisions or critical business processes.

Examples may include:

* financial services;
* healthcare;
* employment;
* identity;
* legal services;
* critical infrastructure;
* government services.

Unauthorized disclosure may create significant legal, operational, financial, or societal consequences.

---

# 43. Enterprise Data Extraction Risk Model

Enterprise risk assessment should consider:

```text
Extraction Risk
=
Data Sensitivity
×
AI Access Scope
×
Authorization Weakness
×
Extraction Capability
×
Potential Impact
```

Additional factors may include:

* attacker capability;
* model exposure;
* tenant architecture;
* monitoring effectiveness;
* data volume;
* persistence of extracted information.

---

# 44. Data Extraction Security Objectives

An enterprise data-extraction security program should aim to:

1. prevent unauthorized data from entering model context;
2. restrict AI access to approved information;
3. prevent unauthorized retrieval;
4. minimize unnecessary output;
5. prevent cross-user and cross-tenant disclosure;
6. restrict tool-mediated access;
7. detect systematic extraction;
8. limit cumulative disclosure;
9. contain compromised AI applications;
10. maintain evidence of security decisions.

---

# 45. Defense-in-Depth Principle

No single AI security control should be expected to prevent all extraction attacks.

A mature architecture should combine:

```text
Identity
   +
Authorization
   +
Data Classification
   +
RAG Access Control
   +
Tool Authorization
   +
Context Filtering
   +
Output DLP
   +
Query Controls
   +
Monitoring
   +
Incident Response
```

If one layer fails, another should prevent the information from crossing the enterprise security boundary.

---

# 46. Model Behavior Is Not Authorization

The model may be instructed:

> "Never reveal confidential information."

That instruction is useful but insufficient.

A secure architecture instead implements:

```text
             Authorization Layer
                     |
             +-------v-------+
             | Can user see  |
             | this data?    |
             +-------+-------+
                     |
                YES / NO
                     |
             +-------v-------+
             | Data Retrieval|
             +-------+-------+
                     |
             +-------v-------+
             | AI Processing |
             +-------+-------+
                     |
             +-------v-------+
             | Output Policy |
             +---------------+
```

The critical authorization decision must exist outside the model.

---

# 47. Fundamental Security Principle

> **Sensitive information must be authorized before it enters the AI context and must be validated again before it leaves the AI system.**

Data extraction protection therefore requires security controls across the complete **data-to-context-to-model-to-output** lifecycle.

The model should be treated as a potential information-disclosure channel—not as a trusted confidentiality boundary.
