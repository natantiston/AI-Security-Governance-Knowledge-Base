# 10.14 — Data Extraction Attacks

## Part 1 — Foundations and Core Concepts

# 1. Definition of Data Extraction Attacks

Data extraction attacks are attempts to cause an AI system to reveal, reconstruct, retrieve, or reproduce information that the requester is not authorized to obtain.

The targeted information may include:

* training data;
* fine-tuning data;
* system instructions;
* confidential documents;
* RAG knowledge;
* personal information;
* credentials or secrets;
* proprietary business information;
* model-generated representations;
* previous conversation information;
* information belonging to another tenant or user.

The attack is fundamentally concerned with **unauthorized information disclosure through an AI system**.

---

# 2. Data Extraction as an AI Security Threat

Traditional applications generally expose data through explicit interfaces such as databases, APIs, files, or application screens.

AI systems introduce an additional disclosure interface:

```text
Sensitive Data
      |
      v
 AI Processing
      |
      v
 Model / RAG / Memory
      |
      v
Natural-Language Interface
      |
      v
 Attacker
```

An attacker may therefore attempt to use natural-language interaction, retrieval behavior, model inference, or connected tools to obtain information that should remain protected.

---

# 3. The Fundamental Security Problem

The fundamental problem is that an AI system may have access to information that the requester should not be able to access directly.

The model can potentially transform, summarize, retrieve, infer, or reproduce information.

Therefore:

> **Model access must not be treated as equivalent to authorization to access every piece of information available to the model.**

The AI system must enforce authorization independently of the model's ability to process information.

---

# 4. Data Extraction vs Normal Data Retrieval

Legitimate data retrieval occurs when:

```text
Authorized User
      |
      v
Authorization Check
      |
      v
Approved Data
      |
      v
Response
```

Data extraction occurs when the attacker attempts to bypass, manipulate, or exploit that process:

```text
Attacker
   |
   v
AI Interface
   |
   +----> Prompt Manipulation
   |
   +----> Retrieval Abuse
   |
   +----> Context Leakage
   |
   +----> Tool Abuse
   |
   +----> Model Probing
   |
   v
Unauthorized Information
```

The difference is therefore primarily one of **authorization and security boundary enforcement**.

---

# 5. Data Extraction vs Data Exfiltration

Data extraction and data exfiltration are related but not identical.

**Data extraction** focuses on obtaining information from the AI system.

**Data exfiltration** focuses on transferring protected information outside its authorized security boundary.

An AI extraction attack can therefore become an exfiltration event when the attacker successfully obtains sensitive information and moves it outside the organization.

---

# 6. Data Extraction vs Model Inversion

Model inversion attempts to infer characteristics or information associated with data learned by a model.

Data extraction is broader.

It can include:

* direct reproduction;
* retrieval of stored documents;
* extraction of system information;
* secret disclosure;
* conversation leakage;
* RAG document retrieval;
* tool-mediated extraction;
* training-data extraction.

A single AI application may be exposed to both threats simultaneously.

---

# 7. Data Extraction vs Membership Inference

Membership inference attempts to determine whether a particular record was included in a dataset used by a model.

Data extraction attempts to obtain the information itself.

For example:

```text
Membership Inference:
"Was John Smith's record used?"

Data Extraction:
"What information about John Smith can you provide?"
```

Membership inference is therefore primarily concerned with **membership**, while extraction is concerned with **obtaining information**.

---

# 8. Data Extraction vs Prompt Injection

Prompt injection is an attack technique.

Data extraction is often an attack objective.

For example:

```text
Prompt Injection
      |
      v
Instruction Manipulation
      |
      v
Security Boundary Bypass
      |
      v
Data Extraction
```

An attacker may use prompt injection to persuade the model to reveal information that should not be disclosed.

Therefore, prompt injection and data extraction should not be treated as mutually exclusive threats.

---

# 9. Data Extraction vs System Prompt Leakage

System prompt leakage specifically targets system instructions or configuration information.

Data extraction is broader and may target:

* system prompts;
* RAG documents;
* user information;
* training data;
* secrets;
* databases;
* API responses;
* tool outputs;
* conversation history.

System prompt leakage can therefore be considered one possible form of AI information extraction.

---

# 10. Direct Data Extraction

Direct extraction occurs when the attacker explicitly requests protected information.

Examples include requests for:

* confidential records;
* previous conversation contents;
* internal policies;
* restricted documents;
* credentials;
* private user information.

The attack may be obvious, but simple requests should not automatically be assumed to be harmless.

---

# 11. Indirect Data Extraction

Indirect extraction occurs when the attacker manipulates an intermediate component to expose information.

Potential intermediaries include:

* RAG systems;
* web retrieval;
* email processing;
* databases;
* APIs;
* plugins;
* tools;
* memory;
* enterprise search.

```text
Attacker
   |
   v
AI Application
   |
   v
Connected Component
   |
   v
Sensitive Data
   |
   v
AI Response
```

This is particularly important in agentic AI systems.

---

# 12. Training Data Extraction

Training-data extraction attempts to cause a model to reproduce information contained in training data.

The risk may increase when training data contains:

* unique records;
* secrets;
* personal information;
* proprietary documents;
* credentials;
* highly repetitive information.

Memorization can create conditions in which information is more reproducible.

---

# 13. Fine-Tuning Data Extraction

Fine-tuning can introduce organization-specific information into model behavior.

Examples include:

* internal procedures;
* proprietary terminology;
* customer information;
* technical documentation;
* private datasets.

If improperly protected, an attacker may attempt to use the resulting model as an information-disclosure interface.

---

# 14. RAG Data Extraction

RAG systems introduce a distinct extraction surface.

```text
User
 |
 v
AI Application
 |
 v
Retriever
 |
 v
Vector Database
 |
 v
Documents
 |
 v
Context
 |
 v
LLM
 |
 v
Response
```

If retrieval authorization is incorrectly implemented, a user may obtain documents that they could not legitimately access.

---

# 15. Knowledge-Base Extraction

Enterprise knowledge bases may contain:

* contracts;
* customer information;
* internal procedures;
* financial documents;
* security documentation;
* intellectual property;
* employee information.

The AI interface can unintentionally become an alternative search interface that bypasses normal access controls.

---

# 16. Vector Database Extraction

Vector databases can become targets because they may contain representations associated with sensitive documents.

Potential risks include:

* unauthorized retrieval;
* cross-tenant retrieval;
* metadata exposure;
* document reconstruction;
* embedding access;
* similarity-query abuse.

Vector access must therefore be governed independently from the LLM.

---

# 17. Conversation Data Extraction

AI applications may store:

* prompts;
* responses;
* uploaded documents;
* user identifiers;
* session information;
* tool results;
* conversation history.

Attackers may attempt to retrieve another user's historical information through:

* session manipulation;
* authorization flaws;
* prompt injection;
* identifier manipulation;
* application vulnerabilities.

Conversation history should therefore be treated as protected enterprise data.

---

# 18. Memory-Based Extraction

Long-term AI memory creates another potential information source.

```text
User A
  |
  v
Memory Store
  |
  +---- Personal Information
  +---- Preferences
  +---- Previous Conversations
  +---- Business Context
  |
  v
AI Model
```

If memory is not properly scoped, information associated with one user, tenant, or business process may become available to another.

---

# 19. Tool-Mediated Data Extraction

AI agents may have access to tools such as:

* databases;
* CRM systems;
* cloud storage;
* email;
* ticketing systems;
* APIs;
* internal search;
* financial systems.

An attacker may attempt to manipulate the model into invoking those tools inappropriately.

The resulting attack chain can be:

```text
Attacker
   |
   v
Prompt Manipulation
   |
   v
Agent
   |
   v
Tool Invocation
   |
   v
Protected System
   |
   v
Sensitive Data
   |
   v
Attacker
```

Tool authorization must therefore exist outside the model.

---

# 20. API-Based Data Extraction

AI applications frequently depend on APIs.

An extraction attack may target:

* excessive API permissions;
* weak object-level authorization;
* predictable identifiers;
* unrestricted search;
* excessive response fields;
* insufficient tenant filtering.

The AI model may simply become the interface through which an underlying API weakness is exploited.

---

# 21. Data Extraction Through Excessive Agency

Excessive agency occurs when an AI system can perform actions or retrieve information beyond what is necessary for its business purpose.

For example:

```text
Business Need:
Read Customer A's Support Ticket

Actual Capability:
Read All Customer Tickets
       +
Search CRM
       +
Export Records
       +
Send Email
```

The broader the model's authority, the greater the potential extraction impact.

---

# 22. Data Extraction and Least Privilege

Least privilege is therefore fundamental.

An AI application should receive only:

* the data it needs;
* the tools it needs;
* the fields it needs;
* the actions it needs;
* the access duration it needs.

The model should not receive unrestricted access simply because doing so simplifies application development.

---

# 23. Data Extraction and Confidentiality

Confidentiality is the primary security objective affected by extraction.

```text
Unauthorized Request
       |
       v
Protected Information
       |
       v
Unauthorized Disclosure
       |
       v
Confidentiality Loss
```

However, extraction can also support integrity and availability attacks when obtained information is subsequently used to manipulate systems or disrupt operations.

---

# 24. Data Extraction and Privacy

Privacy risk arises when extracted information relates to identifiable individuals.

Potentially sensitive information includes:

* identity information;
* financial information;
* employment information;
* communications;
* customer records;
* behavioral information;
* authentication information.

The organization must consider not only whether data can be accessed, but whether it can be **reconstructed or disclosed through AI interaction**.

---

# 25. Data Extraction and Integrity

Extraction can expose information that enables subsequent attacks.

For example:

```text
Information Extraction
        |
        v
Reconnaissance
        |
        v
Security Detail Discovery
        |
        v
Targeted Manipulation
        |
        v
Integrity Attack
```

Sensitive information disclosure can therefore increase the probability of later compromise.

---

# 26. Data Extraction and Availability

Extraction attacks may also consume significant resources.

An attacker could generate:

* excessive queries;
* repeated retrieval operations;
* large document requests;
* expensive agent workflows;
* repeated model calls.

This can create:

* latency;
* resource exhaustion;
* increased infrastructure cost;
* service degradation.

Therefore, extraction protection should include resource controls.

---

# 27. Data Extraction Attack Surface

The enterprise attack surface can include:

```text
                 AI Application
                      |
       +--------------+--------------+
       |              |              |
     Model           RAG           Memory
       |              |              |
     Prompt        Documents      History
       |              |              |
       +--------------+--------------+
                      |
                 Agent / Tools
                      |
          +-----------+-----------+
          |           |           |
        APIs       Databases     SaaS
```

Every connected information source becomes potentially relevant to data-extraction risk.

---

# 28. Trusted Systems Can Still Become Extraction Sources

A common misconception is:

> "The data comes from an approved enterprise system, so it is safe."

The source may be trusted while the **requester's authorization is not**.

For example:

```text
Trusted Database
      |
      v
Trusted API
      |
      v
Poor Authorization
      |
      v
AI Application
      |
      v
Unauthorized User
```

Trust in the source does not eliminate the need for authorization at the point of access.

---

# 29. Data Provenance vs Data Authorization

Provenance answers:

> Where did this information come from?

Authorization answers:

> Who is allowed to receive it?

These are different security questions.

```text
Document
   |
   +--> Provenance: Internal HR System
   |
   +--> Authorization: User NOT permitted
```

A document can have excellent provenance and still be unauthorized for a particular user.

---

# 30. Data Extraction Through Context Manipulation

Attackers may attempt to influence the context supplied to the model.

Potential methods include:

* prompt injection;
* malicious documents;
* manipulated retrieval queries;
* conversation-state manipulation;
* memory poisoning;
* conflicting instructions.

The objective may be to cause the model to disclose information from a protected context.

---

# 31. Multi-Turn Data Extraction

Extraction does not always occur in a single interaction.

An attacker may gradually probe the system:

```text
Query 1
  |
  v
Small Information
  |
  v
Query 2
  |
  v
Additional Information
  |
  v
Query 3
  |
  v
More Information
  |
  v
Combined Dataset
```

Individually harmless responses may collectively disclose sensitive information.

Security monitoring should therefore analyze interaction sequences.

---

# 32. Extraction Through Transformation

An attacker may avoid explicitly asking for protected information and instead request transformations.

Examples of transformation objectives include:

* summarization;
* translation;
* classification;
* formatting;
* comparison;
* conversion;
* extraction into structured fields.

The security issue is not the transformation itself.

The issue is whether the transformation causes protected information to cross an authorization boundary.

---

# 33. Extraction Through Aggregation

Sensitive information can sometimes be reconstructed through multiple individually permitted responses.

```text
Response A
    +
Response B
    +
Response C
    +
Response D
    |
    v
Sensitive Picture
```

This is an important reason to consider cumulative disclosure rather than evaluating every response independently.

---

# 34. Extraction Through Metadata

Attackers may target metadata instead of the underlying document.

Potentially sensitive metadata includes:

* document names;
* usernames;
* timestamps;
* record counts;
* database fields;
* source identifiers;
* system names;
* access patterns.

Metadata can provide valuable reconnaissance even when document content itself is protected.

---

# 35. Extraction Through Error Messages

AI applications may unintentionally expose information through errors.

Examples include:

* database errors;
* API responses;
* tool failures;
* retrieval errors;
* stack traces;
* internal identifiers;
* provider messages.

Error handling should therefore be treated as part of the AI data-disclosure boundary.

---

# 36. Extraction Through System and Tool Descriptions

AI applications may expose descriptions of:

* available tools;
* API capabilities;
* database schemas;
* internal workflows;
* system architecture.

Even when these descriptions do not contain the target data, they may provide reconnaissance information that makes subsequent extraction easier.

---

# 37. Data Extraction Attack Lifecycle

A generalized extraction attack may follow:

```text
Reconnaissance
      |
      v
Identify Data Source
      |
      v
Identify AI Interface
      |
      v
Probe Authorization
      |
      v
Manipulate Interaction
      |
      v
Retrieve / Infer Data
      |
      v
Aggregate Information
      |
      v
Exfiltrate
      |
      v
Reuse Information
```

Not every attack requires every stage.

---

# 38. Factors Increasing Data Extraction Risk

Risk increases when an AI system has:

* broad data access;
* weak authorization;
* excessive model context;
* unrestricted RAG;
* unrestricted tool access;
* long-term memory;
* large output limits;
* weak tenant isolation;
* detailed API responses;
* poor monitoring;
* sensitive training data;
* weak query controls.

The combination of several weaknesses can create significant exposure.

---

# 39. Data Extraction and Agentic AI

Agentic AI increases extraction risk because the model may decide which information sources to access.

```text

 |
 v

 |
 +--> Search
 |
 +--> Database
 |
 +--> CRM
 |
 +--> Files
 |
 +--> API
 |
 v
Collected Context
 |
 v

 |
 v

```

The agent must not be allowed to turn its reasoning capability into unrestricted enterprise data access.

---

# 40. Data Extraction and Zero Trust

Zero Trust principles require every data request to be evaluated independently.

```text
Identity
   +
Device / Application
   +
Tenant
   +
Purpose
   +
Data Classification
   +
Requested Operation
   |
   v
Authorization Decision
   |
   v
Allow / Deny / Review
```

The model should not be considered inherently trusted merely because it operates inside the corporate environment.

---

# 41. Data Extraction Security Boundaries

The security boundary should include:

* data repositories;
* retrieval systems;
* vector databases;
* model context;
* memory;
* model APIs;
* agent tools;
* application sessions;
* outputs;
* logging;
* monitoring.

A narrow database-centric security boundary is insufficient for modern AI architectures.

---

# 42. Data Extraction and High-Impact AI

Extraction risk becomes particularly significant when AI systems process information associated with high-impact decisions or critical business processes.

Examples may include:

* financial services;
* healthcare;
* employment;
* identity;
* legal services;
* critical infrastructure;
* government services.

Unauthorized disclosure may create significant legal, operational, financial, or societal consequences.

---

# 43. Enterprise Data Extraction Risk Model

Enterprise risk assessment should consider:

```text
Extraction Risk
=
Data Sensitivity
×
AI Access Scope
×
Authorization Weakness
×
Extraction Capability
×
Potential Impact
```

Additional factors may include:

* attacker capability;
* model exposure;
* tenant architecture;
* monitoring effectiveness;
* data volume;
* persistence of extracted information.

---

# 44. Data Extraction Security Objectives

An enterprise data-extraction security program should aim to:

1. prevent unauthorized data from entering model context;
2. restrict AI access to approved information;
3. prevent unauthorized retrieval;
4. minimize unnecessary output;
5. prevent cross-user and cross-tenant disclosure;
6. restrict tool-mediated access;
7. detect systematic extraction;
8. limit cumulative disclosure;
9. contain compromised AI applications;
10. maintain evidence of security decisions.

---

# 45. Defense-in-Depth Principle

No single AI security control should be expected to prevent all extraction attacks.

A mature architecture should combine:

```text
Identity
   +
Authorization
   +
Data Classification
   +
RAG Access Control
   +
Tool Authorization
   +
Context Filtering
   +
Output DLP
   +
Query Controls
   +
Monitoring
   +
Incident Response
```

If one layer fails, another should prevent the information from crossing the enterprise security boundary.

---

# 46. Model Behavior Is Not Authorization

The model may be instructed:

> "Never reveal confidential information."

That instruction is useful but insufficient.

A secure architecture instead implements:

```text
             Authorization Layer
                     |
             +-------v-------+
             | Can user see  |
             | this data?    |
             +-------+-------+
                     |
                YES / NO
                     |
             +-------v-------+
             | Data Retrieval|
             +-------+-------+
                     |
             +-------v-------+
             | AI Processing |
             +-------+-------+
                     |
             +-------v-------+
             | Output Policy |
             +---------------+
```

The critical authorization decision must exist outside the model.

---

# 47. Fundamental Security Principle

> **Sensitive information must be authorized before it enters the AI context and must be validated again before it leaves the AI system.**

Data extraction protection therefore requires security controls across the complete **data-to-context-to-model-to-output** lifecycle.

The model should be treated as a potential information-disclosure channel—not as a trusted confidentiality boundary.

## Part 2 — Technical Security and Control Mechanisms

Data extraction protection should use multiple independent security layers rather than relying on the LLM to refuse unauthorized requests.

```text id="d3k8pa"

                    | Identity &   |
                    | Access       |
                    +------+------+ 
                           |
                           v
                    +-------------+
                    | AI Security  |
                    | Gateway      |
                    +------+------+
                           |
              +------------+------------+
              |                         |
              v                         v
       Query Security            Data Authorization
              |                         |
              +------------+------------+
                           |
                           v
                    +-------------+
                    | RAG / Tools |
                    | / APIs      |
                    +------+------+
                           |
                           v
                    +-------------+
                    | LLM / Agent |
                    +------+------+
                           |
                           v
                    +-------------+
                    | Output DLP  |
```

The security boundary should surround the entire information flow.

---

# 49. Data Source Authentication

Every data source connected to an AI application should be authenticated.

Sources may include:

* databases;
* document repositories;
* APIs;
* cloud storage;
* CRM platforms;
* knowledge bases;
* vector databases;
* enterprise search systems.

Authentication establishes the identity of the source but does not establish whether a particular user is authorized to receive its information.

---

# 50. Data Source Authorization

AI applications should enforce authorization before retrieving protected information.

```text id="a9m4qe"
User
 |
 v
Identity
 |
 v
Authorization Policy
 |
 +---- Deny --> No Retrieval
 |
 +---- Allow --> Retrieve Approved Data
```

Authorization should be evaluated at the data-access layer rather than delegated to the model.

---

# 51. Fine-Grained Data Authorization

Authorization should operate at the smallest practical level.

Depending on the system, controls may apply to:

* database;
* table;
* row;
* document;
* folder;
* field;
* record;
* object;
* API resource.

For example, allowing access to a customer record does not necessarily authorize access to every field within that record.

---

# 52. Attribute-Based Access Control

Attribute-Based Access Control (ABAC) can evaluate multiple attributes before allowing AI-mediated data access.

```text id="v4w1rz"
User Role
   +
Department
   +
Tenant
   +
Data Classification
   +
Business Purpose
   +
Application
   |
   v
Authorization Decision
```

This is particularly useful for enterprise AI systems operating across multiple business functions.

---

# 53. Role-Based Access Control

Role-Based Access Control (RBAC) can restrict AI capabilities according to defined enterprise roles.

For example:

```text id="x2g6mp"
Analyst
  --> Aggregated Data

Manager
  --> Approved Detailed Data

Security Administrator
  --> Security-Restricted Data

External User
  --> Public / Authorized Data Only
```

RBAC should be supplemented with contextual controls where roles alone are insufficient.

---

# 54. Data Classification

Data should be classified before being exposed to AI systems.

Example classification:

| Classification | AI Treatment         |
| -------------- | -------------------- |
| Public         | Generally permitted  |
| Internal       | Controlled           |
| Confidential   | Restricted           |
| Restricted     | Highly restricted    |
| Regulated      | Specialized controls |

Classification should influence retrieval, context construction, output handling, logging, and monitoring.

---

# 55. Data Minimization

Only the information required to complete the approved task should enter the model context.

```text id="1xj5ch"
Source Dataset
     |
     v
Required Fields
     |
     v
Minimal Context
     |
     v
AI Model
```

Sending an entire database record when only two fields are required unnecessarily increases the extraction surface.

---

# 56. Field-Level Filtering

Sensitive fields should be removed before data reaches the model when they are not required.

Potential fields include:

* passwords;
* authentication tokens;
* national identifiers;
* payment information;
* private contact details;
* internal security metadata.

Field-level filtering provides a deterministic boundary between authorized application functionality and unnecessary model exposure.

---

# 57. Record-Level Filtering

The AI application should retrieve only records the requester is authorized to access.

For example:

```text id="7n5jvc"
Query:
"Show my customer cases"

Backend Policy:
WHERE customer_owner = authenticated_user
```

The authorization constraint should be enforced by the underlying data system rather than merely inserted into the prompt.

---

# 58. Document-Level Access Control

RAG systems should enforce permissions at document level.

Each retrieved document should be evaluated against:

* user identity;
* tenant;
* role;
* classification;
* business purpose;
* document permissions.

Unauthorized documents should not enter the context window.

---

# 59. Row-Level Security for AI Applications

Database row-level security can provide an important deterministic control.

```text id="e7j2nq"
AI Query
   |
   v
Database
   |
   v
Row-Level Security
   |
   +---- Authorized Rows
   |
   +---- Unauthorized Rows Blocked
```

This prevents the LLM from obtaining records it should never have access to.

---

# 60. Tenant Isolation

Multi-tenant AI systems must prevent one tenant's data from becoming available to another.

Tenant identity should be propagated through:

```text id="3q5m0v"
User
 |
 v
Session
 |
 v
Application
 |
 v
Retriever / API
 |
 v
Database / Vector Store
```

Every layer should preserve tenant boundaries.

---

# 61. Context Isolation

Context should be isolated according to security scope.

A context may contain:

* user data;
* retrieved documents;
* tool responses;
* memory;
* system instructions.

Each component should have an explicit trust and authorization boundary.

---

# 62. Session Isolation

Conversation sessions should be independently scoped.

A new user session should not inherit:

* another user's conversation;
* another user's memory;
* previous sensitive context;
* unauthorized retrieved documents.

Session identifiers must not be treated as sufficient authorization by themselves.

---

# 63. Conversation History Controls

Conversation history should be treated as protected data.

Controls should include:

* authenticated access;
* session ownership;
* retention limits;
* encryption;
* tenant isolation;
* deletion controls.

The model should not be allowed to retrieve arbitrary historical conversations simply because they exist within the same AI platform.

---

# 64. Memory Security

Long-term memory should have explicit authorization boundaries.

```text id="r6m0pb"
Memory
 |
 +--> User Scope
 |
 +--> Tenant Scope
 |
 +--> Application Scope
 |
 +--> Retention Policy
 |
 +--> Access Policy
```

Memory should not become a hidden cross-session data repository.

---

# 65. RAG Retrieval Authorization

Retrieval should enforce authorization **before** context assembly.

The secure sequence is:

```text id="h3p7zv"
User Query
    |
    v
Identity
    |
    v
Authorization
    |
    v
Filtered Retrieval
    |
    v
Approved Documents
    |
    v
LLM Context
```

The insecure sequence is:

```text id="7p4xcs"
User Query
    |
    v
Retrieve Everything
    |
    v
LLM decides what to hide
```

The second architecture depends excessively on model behavior.

---

# 66. Retrieval Result Filtering

Even authorized retrieval results should be filtered for unnecessary information.

Filtering may consider:

* document classification;
* requested fields;
* task purpose;
* sensitivity;
* data age;
* tenant;
* business unit.

The objective is to provide the model with the minimum necessary context.

---

# 67. Context Window Controls

Large context windows can increase the amount of potentially extractable information.

Controls may include:

* maximum retrieved documents;
* maximum tokens;
* document prioritization;
* sensitivity filtering;
* field filtering;
* duplicate removal;
* context expiration.

Context size should be aligned with the application's legitimate business requirement.

---

# 68. Query Validation

AI queries should be validated before processing.

Validation may identify:

* malformed requests;
* prohibited operations;
* suspicious extraction patterns;
* excessive scope;
* unsupported requests;
* unusual data requests.

Validation should not attempt to determine every malicious intent solely through an LLM classifier.

---

# 69. Query Normalization

Requests can be normalized before security analysis.

Normalization may address:

* encoding;
* Unicode variations;
* excessive whitespace;
* repeated instructions;
* obfuscation;
* unusual formatting.

This reduces opportunities for attackers to bypass simple security rules through representation changes.

---

# 70. Data Extraction Detection

Detection mechanisms can look for patterns associated with extraction attempts.

Examples include:

* repeated requests for internal data;
* requests for large datasets;
* attempts to enumerate records;
* repeated requests using different wording;
* requests for secrets;
* requests for other users' information.

Detection should operate across sessions where appropriate.

---

# 71. Extraction Pattern Detection

An attacker may gradually modify queries:

```text id="z7x8j1"
Query A
   |
Query B
   |
Query C
   |
Query D
   |
   v
Same Extraction Objective
```

Therefore, detection should identify **behavioral sequences**, not only individual malicious phrases.

---

# 72. Enumeration Protection

Applications should detect attempts to systematically enumerate protected information.

Examples include:

* sequential customer IDs;
* employee records;
* document identifiers;
* database objects;
* ticket numbers.

Enumeration controls can include:

* rate limits;
* authorization checks;
* query quotas;
* anomaly detection;
* account restrictions.

---

# 73. Query Rate Limiting

Rate limiting restricts how rapidly an actor can interrogate an AI system.

```text id="g1s7nq"
Normal Requests
      |
      v
Allowed

High-Frequency Requests
      |
      v
Throttle
      |
      v
Potential Security Event
```

Rate limiting should be applied based on risk rather than relying only on a single global threshold.

---

# 74. Query Quotas

Quotas can limit cumulative access over a period.

Quotas may apply to:

* requests per minute;
* documents retrieved;
* records accessed;
* tokens processed;
* tool calls;
* data volume.

Quotas are particularly useful where attackers can distribute requests over time.

---

# 75. Output Minimization

The response should contain only the information necessary to fulfill the approved task.

For example:

```text id="k9n4dt"
Backend Data:
20 Sensitive Fields

Required Output:
2 Approved Fields

Model Context:
2 Fields

User Response:
2 Fields
```

Output minimization reduces the amount of information available for extraction.

---

# 76. Output DLP

Data Loss Prevention controls should inspect model outputs for sensitive information.

Potential detections include:

* credentials;
* API keys;
* payment information;
* personal identifiers;
* confidential business data;
* regulated information.

DLP should operate independently of the model's own instructions.

---

# 77. Semantic Output Inspection

Pattern matching alone may not detect every disclosure.

Semantic inspection can identify whether a response reveals:

* confidential business information;
* restricted records;
* private user information;
* sensitive operational details.

Semantic inspection should complement deterministic DLP rules rather than replace them.

---

# 78. Secret Detection

AI outputs should be scanned for secrets such as:

* passwords;
* API keys;
* tokens;
* certificates;
* private keys;
* connection strings.

Secrets should ideally never enter model context in the first place.

Output detection is therefore a secondary control.

---

# 79. Tool Authorization

Every AI tool should have explicit authorization boundaries.

```text id="h2k8fs"
Agent
 |
 +--> Search Tool       --> Approved
 |
 +--> CRM Tool          --> Restricted
 |
 +--> Database Tool     --> Restricted
 |
 +--> Export Tool       --> Denied
```

The agent's decision to call a tool should not constitute authorization.

---

# 80. Tool Argument Validation

Tool parameters should be validated before execution.

For example:

```text id="y4c7kw"

     |
     v
Tool Argument Validation
     |
     +---- Invalid Scope --> Block
     |
     +---- Excessive Data --> Block
     |
     +---- Unauthorized Tenant --> Block
     |
     +---- Approved --> Execute
```

This prevents the model from constructing overly broad requests.

# 81. API Response Minimization

Connected APIs should return only the fields required by the AI application.

Instead of:

```text id="e5h3pu"

    |
    v
50 fields
```

prefer:

```text id="0z3n8m"
Customer API
    |
    v
3 approved fields
```

This creates an additional data-minimization boundary.

---

# 82. Database Query Controls

Controls can include:

* query allowlists;
* schema restrictions;
* row limits;
* execution time limits;
* tenant filters;
* sensitive-table restrictions.

The model should never receive unrestricted database privileges merely because it can generate SQL.

---

# 83. Export and Bulk-Extraction Controls

Bulk extraction should receive stronger controls than ordinary responses.

Examples:

```text id="j6v4qr"

    --> Normal Authorization

10 Records
    --> Enhanced Logging

1,000 Records
    --> Restricted

Bulk Export
    --> Approval / Denial
```

Large-volume requests can indicate an extraction attempt even when each individual record is technically accessible.

# 84. Data Aggregation Controls

The system should consider cumulative disclosure.

For example:

```text id="b8x0sq"
100 individually permitted queries
              |
              v
Combined Sensitive Dataset
```

Controls should detect unusually broad cumulative access across a time window.

---

# 85. Output Pagination Controls

Controls may include:

* maximum records;
* time-based limits;
* cumulative query limits;
* elevated authorization for continued retrieval.

* business purpose;
* tenant;
* regulatory requirements.

The final response should be treated as a security-controlled data egress point.

# 96. Control Independence

Critical controls should remain effective even when the model behaves unexpectedly.

For example:

```text id="c4m8zy"

        X

"Access denied."
```

The authorization engine must control the actual data access.

Similarly:

```text id="p7r3jk"

        +

        |
        v

```

Independent enforcement creates meaningful defense in depth.

# 98. Core Engineering Principle

> **Do not allow the AI model to become the sole decision-maker over whether information may be accessed or disclosed.**

Sensitive data should be:

* authorized before retrieval;
* minimized before context construction;
* isolated by user and tenant;
* constrained when accessed through tools;
* minimized in responses;
* inspected before egress;
* monitored for cumulative extraction;
* protected by independent deterministic controls.

The fundamental technical objective is to ensure that even if an attacker manipulates the model, **the surrounding security architecture prevents unauthorized information from crossing the enterprise security boundary.**

# 194. Strategic Security Principle

> **An AI system must never become an alternative path around enterprise information-security authorization.**

The strongest enterprise architecture assumes that:

* users may intentionally attempt extraction;
* models may behave unexpectedly;
* prompts may be manipulated;
* RAG results may be over-broad;
* agents may request excessive information;
* tools may expose sensitive systems;
* multiple harmless responses may create cumulative disclosure;
* legitimate credentials may be abused.

Therefore, the enterprise must enforce the security boundary independently across **identity, authorization, data retrieval, context construction, model interaction, tool execution, output, monitoring, and incident response**.

The fundamental architectural principle is:

> **Authorize before data enters the AI context, minimize what the model receives, independently authorize every sensitive action, validate what leaves the system, and continuously monitor for cumulative extraction.**
