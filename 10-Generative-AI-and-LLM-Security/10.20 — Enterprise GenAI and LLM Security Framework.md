# 10.20 — Insecure AI Model Configuration

## Part 1 — Foundations and Core Concepts

### 1. Definition of Insecure AI Model Configuration

Insecure AI Model Configuration is the condition in which an AI model, model-serving environment, inference configuration, or associated security setting is configured in a way that creates unnecessary security exposure, weakens required protections, or allows the AI system to operate outside its approved security and business requirements.

Configuration includes more than model parameters. It may encompass:

* model selection;
* model version;
* inference parameters;
* context limits;
* output limits;
* safety settings;
* tool permissions;
* system-level configuration;
* model-serving settings;
* API configuration;
* authentication requirements;
* logging;
* network connectivity;
* data access;
* resource limits;
* fallback models;
* routing rules;
* agent settings.

The fundamental problem is that a technically functional AI system can still be insecure because its configuration establishes an unsafe security posture.

---

### 2. Insecure Configuration as an AI Security Threat

AI security depends not only on the capabilities of the underlying model but also on how that model is configured and deployed.

An incorrectly configured model may:

* expose excessive functionality;
* accept unnecessary input;
* generate excessive output;
* access sensitive data;
* invoke privileged tools;
* communicate with external systems;
* retain information unnecessarily;
* operate without appropriate monitoring;
* bypass intended security controls;
* use an inappropriate model or version;
* operate with excessive resource limits.

Therefore, configuration itself becomes part of the AI attack surface.

---

### 3. Fundamental Security Problem

The central security problem is:

> **An AI system may be technically secure in design but become insecure through configuration that grants excessive capability, weakens controls, exposes sensitive interfaces, or violates the approved security architecture.**

This is particularly important because configuration changes can occur without changing application code.

```text
Secure AI Design
       ↓
Configuration Change
       ↓
Security Control Weakened
       ↓
New Attack Surface
       ↓
Potential Exploitation
```

Configuration security must therefore be treated as an independent security concern.

---

### 4. Configuration vs Model Capability

Model capability describes what the model can technically do.

Configuration determines how those capabilities are exposed.

For example:

```text
Model Capability:
Generate code

Secure Configuration:
Code generation → review → validation → sandbox

Insecure Configuration:
Code generation → automatic production execution
```

The underlying model has not changed, but the security risk has changed substantially.

---

### 5. Configuration vs Application Security

AI application security focuses on how the surrounding application is designed and implemented.

Model configuration focuses on the security-relevant settings governing AI behavior and operation.

They overlap but are not identical.

A secure application can still be exposed by an insecure model configuration, while a well-configured model cannot compensate for fundamentally insecure application architecture.

---

### 6. Configuration vs Prompt Security

Prompt security protects instructions, context, and prompt construction.

Configuration security governs the technical settings surrounding the model.

For example:

```text
Prompt Security
     ↓
System Instructions
Context Handling
Prompt Integrity
Injection Protection

Model Configuration
     ↓
Model Version
Token Limits
Safety Settings
Tool Access
Routing
Logging
Network
```

Prompt controls and configuration controls should therefore operate together.

---

### 7. Configuration vs Excessive Agency

Excessive agency concerns excessive authority or autonomy.

Insecure configuration can create excessive agency by configuring an AI system with:

* unnecessary tools;
* excessive permissions;
* unrestricted execution;
* excessive transaction limits;
* broad API scopes;
* unrestricted network access.

Therefore:

> **Insecure configuration can be a root cause of excessive agency.**

---

### 8. Configuration vs Model Denial of Service

Resource-related configuration can also create availability risks.

Examples include:

* unlimited context;
* excessive output limits;
* unlimited agent iterations;
* excessive concurrency;
* unrestricted file processing;
* unlimited tool calls;
* uncontrolled retries.

A model that is secure from an authorization perspective may still create a denial-of-service or financial-risk condition through unsafe resource configuration.

---

### 9. Model Version Configuration

The selected model version is a security-sensitive configuration decision.

Changing a model may alter:

* instruction following;
* refusal behavior;
* tool-use behavior;
* output patterns;
* context handling;
* memorization characteristics;
* security-control interactions;
* resource consumption.

Therefore, replacing a model should not be treated as a simple functional upgrade.

---

### 10. Model Selection Risk

Different models may have different:

* capabilities;
* security characteristics;
* data-processing behavior;
* supported features;
* tool interfaces;
* geographic processing locations;
* provider dependencies;
* operational risks.

Selecting a model solely on performance or cost can therefore create security exposure.

---

### 11. Safety Configuration

Many AI platforms expose configurable safety or moderation mechanisms.

Security-relevant settings may influence:

* harmful-content filtering;
* input moderation;
* output moderation;
* content classification;
* policy enforcement;
* refusal behavior.

Disabling or weakening such mechanisms without an approved security rationale can materially change the application's risk profile.

---

### 12. Context-Window Configuration

Context-window configuration affects both functionality and security.

A larger context may increase:

* information exposure;
* prompt-injection surface;
* sensitive-data exposure;
* memory requirements;
* processing cost;
* opportunities for context manipulation.

A context window should therefore be sized according to the business requirement rather than simply maximizing available capacity.

---

### 13. Output-Length Configuration

Unrestricted output can create:

* excessive resource consumption;
* information disclosure;
* data exfiltration opportunities;
* application-layer injection risks;
* downstream processing problems.

Output limits should be aligned with the application's legitimate business requirement.

---

### 14. Temperature and Sampling Configuration

Inference parameters such as temperature and sampling can affect behavioral consistency.

In security-sensitive applications, excessive variability may make:

* testing;
* validation;
* monitoring;
* policy enforcement;
* reproducibility

more difficult.

Configuration should therefore consider whether deterministic or constrained behavior is required.

---

### 15. Tool Configuration

AI tools should be explicitly configured according to business necessity.

An insecure configuration might expose:

```text
AI Agent
   |
   +-- Database
   +-- Email
   +-- Shell
   +-- Cloud Administration
   +-- Internet
   +-- File System
```

when the approved business process requires only:

```text
AI Agent
   |
   +-- Read-Only Knowledge Search
```

Tool configuration is therefore an authorization boundary.

---

### 16. API Configuration

AI APIs may expose configuration options affecting:

* authentication;
* authorization;
* rate limits;
* model selection;
* data retention;
* logging;
* allowed operations;
* network access.

Misconfigured APIs can expose AI functionality to unauthorized users or systems.

---

### 17. Authentication Configuration

An AI service should not be deployed with weaker authentication than its risk level requires.

Potential insecure configurations include:

* anonymous access;
* shared credentials;
* permanent credentials;
* disabled authentication;
* excessive service-account permissions.

Authentication should be independently enforced rather than relying on the model to recognize authorized users.

---

### 18. Authorization Configuration

Authentication establishes identity.

Authorization determines what that identity can do.

An insecure AI configuration may authenticate users correctly but grant excessive permissions.

```text
User Authenticated
       ↓
Incorrect Authorization
       ↓
Excessive AI Capability
       ↓
Unauthorized Action
```

Therefore, authorization configuration is at least as important as authentication configuration.

---

### 19. Identity Configuration

AI applications, agents, services, and tools should have appropriately defined identities.

Identity configuration may include:

* service accounts;
* managed identities;
* workload identities;
* agent identities;
* API identities;
* delegated user identities.

Shared identities can make accountability and containment more difficult.

---

### 20. Credential Configuration

Credentials associated with AI systems should be:

* scoped;
* protected;
* rotated;
* monitored;
* revocable;
* preferably short-lived.

Embedding privileged credentials directly into prompts, model configuration, code, or agent instructions creates significant security risk.

---

### 21. Secret Exposure Through Configuration

Configuration can accidentally become a secret-storage mechanism.

Examples include:

* API keys;
* passwords;
* tokens;
* certificates;
* cloud credentials;
* database connection strings.

Security principle:

> **AI configuration must never become an uncontrolled repository for secrets.**

Secrets should be managed through dedicated secrets-management mechanisms.

---

### 22. Network Configuration

AI services should have only the network connectivity required for their approved purpose.

Potentially dangerous configurations include:

* unrestricted Internet access;
* unrestricted internal network access;
* direct access to production systems;
* unrestricted outbound connections;
* unrestricted inbound connections.

Network configuration should reinforce application authorization.

---

### 23. Egress Configuration

Outbound connectivity is particularly important for AI systems capable of:

* browsing;
* API calls;
* email;
* file transfers;
* webhooks;
* agent actions.

A compromised or manipulated AI system should not automatically gain unrestricted data-exfiltration capability.

---

### 24. Ingress Configuration

Inbound access should also be controlled.

Security considerations include:

* who can access the AI service;
* which applications may call it;
* which networks are trusted;
* what protocols are permitted;
* whether administrative interfaces are exposed.

Administrative interfaces should not be exposed through the same unrestricted paths used for normal inference.

---

### 25. Data-Access Configuration

AI systems should receive only the data access required by their business purpose.

```text
Business Requirement
       ↓
Required Data
       ↓
Minimum Authorization
       ↓
AI Context
```

Granting broad database or document access because “the AI may need it later” violates least privilege.

---

### 26. RAG Configuration

RAG configuration may determine:

* which repositories are searchable;
* which documents are indexed;
* who can retrieve them;
* which metadata is exposed;
* retrieval limits;
* filtering;
* tenant boundaries.

An incorrectly configured RAG system can turn a legitimate AI assistant into an unauthorized enterprise search mechanism.

---

### 27. Memory Configuration

Memory settings may determine:

* what information is retained;
* how long it is retained;
* which users can access it;
* whether memory is shared;
* whether memory crosses sessions;
* whether memory crosses tenants.

Insecure memory configuration can create privacy and confidentiality risks.

---

### 28. Logging Configuration

AI security monitoring depends heavily on appropriate logging.

Insecure configurations may involve:

* logging disabled;
* insufficient security events;
* excessive sensitive-content logging;
* no administrative audit trail;
* no configuration-change logging.

Logging should balance security visibility with privacy and data-minimization requirements.

---

### 29. Monitoring Configuration

A system that is not configured to generate appropriate telemetry can become difficult to defend.

Monitoring should provide visibility into:

* authentication;
* authorization;
* model usage;
* tool calls;
* configuration changes;
* data access;
* errors;
* abnormal behavior;
* resource consumption.

---

### 30. Rate-Limit Configuration

Rate limits protect against:

* abuse;
* enumeration;
* excessive consumption;
* automated extraction;
* denial of service.

AI systems should have appropriate limits at multiple layers:

```text
User
 ↓
Application
 ↓
Agent
 ↓
Model
 ↓
Provider
 ↓
Infrastructure
```

---

### 31. Resource-Limit Configuration

Security-relevant resource limits may include:

* input tokens;
* output tokens;
* context size;
* concurrent requests;
* agent iterations;
* tool calls;
* file size;
* processing time;
* API calls.

Unlimited configuration should be considered a risk requiring explicit justification.

---

### 32. Fallback Model Configuration

AI platforms sometimes use fallback models when the primary model is unavailable.

An insecure fallback configuration may:

* use an unapproved provider;
* have weaker security controls;
* process data in a different jurisdiction;
* have different privacy characteristics;
* lack equivalent safety controls.

Fallback models must therefore be governed as part of the production architecture.

---

### 33. Model Routing Configuration

Routing rules can determine which model receives particular requests.

Security considerations include:

* data sensitivity;
* business criticality;
* model authorization;
* provider restrictions;
* geographic requirements;
* compliance requirements.

Sensitive data should not automatically be routed to any model capable of processing it.

---

### 34. Multi-Model Configuration

Organizations may operate several models simultaneously.

This creates additional risks:

* inconsistent security controls;
* different data-handling practices;
* inconsistent output validation;
* different tool capabilities;
* different retention policies.

A common enterprise security baseline should therefore apply across approved models.

---

### 35. Environment Configuration

AI configuration should be separated across:

* development;
* testing;
* staging;
* production.

Production should not inherit unrestricted development privileges.

```text
Development
   ↓
Testing
   ↓
Staging
   ↓
Production
```

Promotion should occur through controlled processes.

---

### 36. Configuration Drift

Configuration drift occurs when the actual production configuration differs from the approved configuration.

Examples:

* a new tool enabled;
* logging disabled;
* token limit increased;
* model changed;
* network rule modified;
* safety control weakened.

Drift can create security exposure without an obvious software release.

---

### 37. Unauthorized Configuration Change

Security-sensitive configuration changes should require:

* authenticated identity;
* authorization;
* change record;
* approval where required;
* testing;
* audit logging;
* rollback capability.

Administrative configuration interfaces should therefore be treated as privileged security functions.

---

### 38. Configuration Integrity

Security-critical AI configuration should be protected against unauthorized modification.

Controls may include:

* version control;
* signed configuration;
* immutable records;
* access controls;
* configuration baselines;
* integrity monitoring.

Configuration integrity is particularly important for high-impact AI systems.

---

### 39. Configuration as an Attack Surface

An attacker does not necessarily need to compromise the model itself.

They may instead target:

```text
Model
  ↑
Configuration
  ↑
Deployment
  ↑
Identity
  ↑
CI/CD
  ↑
Administrator
```

Compromising configuration management can therefore become an indirect path to compromising AI behavior or security controls.

---

### 40. Configuration Supply-Chain Risk

Configuration can also originate from:

* infrastructure-as-code;
* deployment templates;
* Helm charts;
* environment variables;
* CI/CD pipelines;
* third-party modules;
* managed AI platforms.

A compromised configuration dependency can introduce insecure settings into otherwise legitimate deployments.

---

### 41. Configuration and Prompt Injection

Prompt injection may attempt to exploit or bypass configuration-defined capabilities.

For example:

```text
Prompt Injection
       ↓
Manipulated Model Behavior
       ↓
Tool Invocation
       ↓
Configuration Allows Tool
       ↓
Unauthorized Action
```

Strong configuration controls should therefore limit what a manipulated model can actually do.

---

### 42. Configuration and System Prompt Leakage

System prompt leakage may reveal configuration-related information such as:

* available tools;
* internal workflows;
* model behavior;
* hidden instructions;
* operational assumptions.

However, knowledge of configuration should not itself provide authorization.

This reinforces:

> **Configuration knowledge ≠ Configuration authority.**

---

### 43. Configuration and Data Exfiltration

Weak configuration can create direct exfiltration paths.

Examples include:

* unrestricted external APIs;
* unrestricted browsing;
* unrestricted email;
* broad cloud-storage access;
* unrestricted file export.

Egress controls should therefore remain independent of model configuration.

---

### 44. Configuration and Improper Output Handling

Unsafe output configuration may allow model-generated content to flow directly into:

* code execution;
* SQL;
* shell commands;
* APIs;
* files;
* infrastructure systems.

Configuration should never assume that model output is inherently trustworthy.

---

### 45. Configuration and Data Poisoning

Insecure ingestion or retraining configuration may allow untrusted data to influence:

* RAG knowledge;
* fine-tuning;
* evaluation;
* feedback;
* model behavior.

Data pipelines must therefore be configured with appropriate trust, validation, provenance, and approval controls.

---

### 46. Configuration and Model Inversion

Model-serving configuration can influence exposure to inference attacks.

Risk increases when systems expose:

* excessive query access;
* detailed confidence information;
* unrestricted repeated queries;
* sensitive model interfaces.

Configuration should therefore minimize information unnecessarily exposed through model APIs.

---

### 47. Configuration and Model Denial of Service

Unbounded configuration can amplify availability risk.

Examples include:

```text
Unlimited Context
       +
Unlimited Output
       +
Unlimited Concurrency
       +
Unlimited Agent Loops
       =
Potential Resource Exhaustion
```

Resource governance must therefore be independently enforced.

---

### 48. Configuration and LLM Supply-Chain Security

Model configuration determines which components enter the effective AI security boundary.

Changing:

* model;
* provider;
* plugin;
* dependency;
* embedding model;
* RAG source;
* tool;

can materially change supply-chain risk.

Configuration changes should therefore trigger appropriate supply-chain assessment.

---

### 49. Confidentiality Impact

Insecure configuration can expose confidential information through:

* excessive data access;
* logging;
* memory;
* RAG;
* APIs;
* external providers;
* unrestricted egress.

Confidentiality must be assessed at both model and surrounding infrastructure layers.

---

### 50. Integrity Impact

Configuration can affect the integrity of:

* AI decisions;
* business workflows;
* tool execution;
* model routing;
* retrieved information;
* downstream actions.

Unauthorized configuration changes can therefore alter system behavior without modifying application source code.

---

### 51. Availability Impact

Configuration can create availability problems through:

* excessive resource limits;
* unrestricted concurrency;
* aggressive retries;
* poor fallback configuration;
* inefficient model routing;
* uncontrolled agent execution.

Availability controls should therefore be treated as security controls.

---

### 52. Accountability and Auditability

Every security-sensitive configuration should ideally be attributable to:

* who changed it;
* what changed;
* when it changed;
* why it changed;
* who approved it;
* what system was affected;
* what security tests were performed.

Without this information, incident investigation and audit become significantly more difficult.

---

### 53. Non-Repudiation Considerations

For high-impact AI environments, configuration changes may require stronger evidence mechanisms.

Examples include:

* authenticated administrative identities;
* signed change records;
* immutable audit logs;
* cryptographically protected configuration versions.

The objective is to establish reliable evidence of configuration state and change history.

---

### 54. Configuration Lifecycle

AI configuration should follow a controlled lifecycle:

```text
Design
  ↓
Define Security Requirements
  ↓
Configure
  ↓
Review
  ↓
Test
  ↓
Approve
  ↓
Deploy
  ↓
Monitor
  ↓
Detect Drift
  ↓
Reassess
  ↓
Retire / Replace
```

Configuration should not be treated as a one-time deployment activity.

---

### 55. Configuration Risk Factors

Important risk factors include:

* high-impact AI use;
* privileged tools;
* sensitive data;
* external connectivity;
* autonomous agents;
* multiple providers;
* complex dependencies;
* weak change control;
* unmanaged environments;
* excessive configuration flexibility;
* poor visibility;
* lack of rollback.

Risk generally increases when configuration complexity exceeds the organization's ability to govern it.

---

### 56. High-Impact AI Considerations

High-impact AI systems require stronger configuration assurance because configuration errors may affect:

* financial decisions;
* employment processes;
* security operations;
* healthcare-related workflows;
* critical infrastructure;
* customer eligibility;
* regulatory decisions.

For these systems, configuration changes may require formal security and business approval.

---

### 57. Configuration and Zero Trust

Zero Trust requires continuous verification rather than permanent trust.

For AI configuration this means:

> **An approved configuration should remain trusted only while its identity, integrity, authorization, context, and security posture remain valid.**

Configuration should therefore be continuously evaluated rather than trusted indefinitely.

---

### 58. Configuration and Defense in Depth

No single configuration setting should be expected to protect the entire AI system.

A resilient architecture uses multiple independent layers:

```text
Identity
   ↓
Authorization
   ↓
Configuration Security
   ↓
Prompt Security
   ↓
Data Security
   ↓
Tool Security
   ↓
Network Security
   ↓
Output Validation
   ↓
Monitoring
```

Failure of one layer should not automatically result in enterprise compromise.

---

### 59. Configuration Security Governance

Organizations should establish governance covering:

* configuration ownership;
* approved baselines;
* security requirements;
* change management;
* access control;
* testing;
* monitoring;
* exception management;
* evidence;
* periodic review.

Configuration should therefore become a formal AI governance domain.

---

### 60. Enterprise AI Configuration Risk Model

A useful risk model is:

```text
Configuration Risk
=
Exposure
×
Privilege
×
Sensitivity
×
Changeability
×
Business Impact
```

Additional factors may include:

* exploitability;
* external connectivity;
* autonomy;
* configuration complexity;
* provider dependency.

---

### 61. AI Configuration Security Objectives

The primary objectives are to ensure that AI configuration is:

1. **Authorized**
2. **Secure**
3. **Minimal**
4. **Integrity-protected**
5. **Version-controlled**
6. **Tested**
7. **Auditable**
8. **Monitored**
9. **Recoverable**
10. **Aligned with business purpose**

---

### 62. Model Behavior Is Not Configuration Security

A model may behave correctly under normal testing while the surrounding configuration remains insecure.

For example:

```text
Model:
"Do not access unauthorized data."

Configuration:
Database Tool → Full Production Database Access
```

The model's instruction-following behavior does not replace authorization.

Therefore:

> **Model behavior is not configuration security.**

---

### 63. Fundamental Security Principle

> **AI model configuration must be treated as a security-critical control surface: every model, parameter, permission, tool, data connection, network path, provider, resource limit, safety setting, and operational configuration must be explicitly authorized, securely configured, integrity-protected, tested, monitored, and subject to controlled change so that configuration failure does not become AI-system or enterprise compromise.**


## Part 2 — Technical Security and Control Mechanisms

### 64. Insecure AI Model Configuration Defense Architecture

A mature defense architecture should treat AI configuration as a controlled security layer between the model and the surrounding enterprise environment.

```text
                    AI Configuration Security
                              |
        +---------------------+---------------------+
        |                     |                     |
   Model Config          Security Config       Environment Config
        |                     |                     |
   Model Version        Authentication         Network
   Parameters           Authorization          Egress
   Context Limits       DLP                   Resources
   Output Limits        Logging               Isolation
        |                     |                     |
        +---------------------+---------------------+
                              |
                       AI Application
                              |
                +-------------+-------------+
                |             |             |
               Data         Tools          APIs
```

Configuration should be controlled independently from model behavior.

---

### 65. Secure Configuration Baseline

Every production AI system should have an approved configuration baseline.

The baseline should define:

* approved model;
* approved version;
* permitted parameters;
* context limits;
* output limits;
* enabled capabilities;
* tool permissions;
* data sources;
* network paths;
* authentication;
* authorization;
* logging;
* monitoring;
* resource limits.

Any deviation should be detectable and appropriately handled.

---

### 66. Configuration Allowlisting

Security-sensitive configuration values should use allowlists where practical.

Examples include:

* approved models;
* approved providers;
* approved plugins;
* approved tools;
* approved APIs;
* approved data repositories;
* approved network destinations.

```text
Requested Configuration
          |
          v
       Allowlist
       /       \
   Approved   Unknown
      |          |
    Permit      Block
```

---

### 67. Configuration Denylisting

Denylisting may supplement allowlisting for explicitly prohibited configurations.

Examples include:

* deprecated models;
* unsupported providers;
* known vulnerable dependencies;
* prohibited plugins;
* unrestricted network destinations.

Denylisting should not be the sole security mechanism where an allowlist is practical.

---

### 68. Model Version Pinning

Production applications should normally use explicitly approved model versions rather than silently consuming the latest available version.

Version pinning improves:

* reproducibility;
* security testing;
* change control;
* incident investigation;
* rollback.

Automatic model upgrades should be treated as controlled changes.

---

### 69. Model Update Verification

Before deploying a new model version, organizations should verify:

* model identity;
* provenance;
* integrity;
* provider;
* version;
* security characteristics;
* performance;
* safety behavior;
* compatibility;
* data-handling implications.

A successful functional test does not establish security equivalence.

---

### 70. Configuration Version Control

Security-sensitive AI configuration should be version-controlled.

Configuration history should identify:

* previous state;
* new state;
* change author;
* timestamp;
* approval;
* reason;
* associated ticket;
* testing results.

This creates traceability between configuration changes and security outcomes.

---

### 71. Immutable Configuration Records

Critical configuration records should be protected against unauthorized modification.

Potential mechanisms include:

* immutable storage;
* signed commits;
* protected branches;
* cryptographic hashes;
* controlled repositories;
* append-only audit records.

---

### 72. Cryptographic Configuration Integrity

Where appropriate, critical configuration can be cryptographically signed.

```text
Configuration
      ↓
Hash
      ↓
Digital Signature
      ↓
Approved Repository
      ↓
Deployment
      ↓
Signature Verification
```

Deployment should fail or enter controlled exception handling when integrity verification fails.

---

### 73. Configuration Change Authentication

Only authenticated administrative identities should be able to modify security-sensitive AI configuration.

Administrative access should use:

* strong authentication;
* centralized identity;
* privileged access management;
* role-based permissions;
* appropriate session controls.

Anonymous configuration modification should never be permitted for production AI systems.

---

### 74. Configuration Authorization

Not every administrator should be authorized to change every AI setting.

Permissions should be separated according to risk.

For example:

| Configuration            | Typical Control                |
| ------------------------ | ------------------------------ |
| Model version            | Controlled deployment          |
| Tool permissions         | Security approval              |
| Network access           | Network/security authorization |
| Data access              | Data-owner authorization       |
| Resource limits          | Platform authorization         |
| Safety settings          | Security approval              |
| Production configuration | Restricted administrators      |

---

### 75. Separation of Duties

High-risk configuration changes should involve appropriate separation of responsibilities.

For example:

```text
Developer
   ↓
Creates Configuration
   ↓
Security Review
   ↓
Business Approval
   ↓
Controlled Deployment
```

The person creating a highly privileged configuration should not necessarily be the sole person approving and deploying it.

---

### 76. Environment Separation

Configuration should be separated between:

* development;
* testing;
* staging;
* production.

Production credentials, data access, and privileges should not automatically be inherited by lower environments.

---

### 77. Configuration Promotion Controls

Configuration should move through controlled environments.

```text
Development
     ↓
Automated Validation
     ↓
Security Testing
     ↓
Staging
     ↓
Approval
     ↓
Production
```

Direct modification of production configuration should be restricted.

---

### 78. Configuration-as-Code

Where practical, AI configuration should be represented as code or structured configuration rather than unmanaged manual settings.

Benefits include:

* version control;
* peer review;
* repeatability;
* automated testing;
* policy enforcement;
* rollback.

Configuration-as-code should itself be secured as part of the software supply chain.

---

### 79. Infrastructure-as-Code Security

AI infrastructure configuration may include:

* compute;
* networking;
* storage;
* identity;
* model serving;
* API gateways;
* containers.

Infrastructure-as-code should be scanned for insecure AI-specific settings before deployment.

---

### 80. Policy Validation Before Deployment

AI configuration should be evaluated against security policies before reaching production.

```text
Configuration
      ↓
Syntax Validation
      ↓
Security Policy Validation
      ↓
Risk Evaluation
      ↓
Security Testing
      ↓
Approval
      ↓
Deployment
```

A syntactically valid configuration is not necessarily a secure configuration.

---

### 81. Policy-as-Code

Security policies can be expressed as machine-enforceable rules.

Example:

```text
IF model_version NOT approved
    THEN BLOCK

IF external_network_access = unrestricted
    THEN BLOCK

IF production_database_access = true
AND business_requirement = false
    THEN BLOCK

IF logging = disabled
    THEN BLOCK

IF output_limit > approved_threshold
    THEN REQUIRE_REVIEW
```

This reduces dependence on manual configuration review.

---

### 82. Secure Parameter Management

Model parameters should be constrained according to application requirements.

Security-sensitive parameters may include:

* temperature;
* maximum output tokens;
* context limits;
* sampling parameters;
* repetition controls;
* timeout;
* concurrency;
* tool-call limits.

Parameters should not be exposed to untrusted users when unrestricted modification could change the security posture.

---

### 83. Context-Window Controls

Context limits should be explicitly defined.

Controls may include:

* maximum input tokens;
* maximum retrieved content;
* maximum conversation history;
* maximum document size;
* maximum memory injection;
* maximum tool response size.

This reduces both resource and information-exposure risks.

---

### 84. Output-Length Controls

Output limits should be independently enforced by the application or gateway.

```text
Model
  ↓
Requested Output
  ↓
External Limit
  ↓
Approved Maximum
  ↓
Output
```

The model should not be trusted to voluntarily remain within security limits.

---

### 85. Tool Allowlisting

Only approved tools should be available to an AI system.

Examples:

* approved search;
* approved database queries;
* approved ticketing systems;
* approved email services;
* approved cloud APIs.

Unused tools should not remain enabled merely for future convenience.

---

### 86. Tool Capability Segmentation

Tools should expose the smallest necessary capability.

Instead of:

```text
Database Tool → Full Database
```

prefer:

```text
Database Tool
   ↓
Approved Database
   ↓
Approved Tables
   ↓
Approved Operations
```

This limits the consequences of model manipulation or tool compromise.

---

### 87. Independent Tool Authorization

Tool authorization should exist outside the model.

```text
AI Requests Tool
       ↓
Identity Check
       ↓
Authorization
       ↓
Policy Evaluation
       ↓
Tool Execution
```

The model's instruction to use a tool must not itself constitute authorization.

---

### 88. Tool Argument Validation

Tool parameters should be validated before execution.

Controls may verify:

* data types;
* permitted values;
* target resources;
* transaction size;
* destination;
* operation type;
* user authorization.

This prevents a valid tool from becoming dangerous through malicious arguments.

---

### 89. Database Access Configuration

AI database access should use:

* least privilege;
* restricted schemas;
* restricted tables;
* row-level authorization;
* read/write separation;
* query controls;
* transaction limits.

Broad database credentials should not be provided to AI applications.

---

### 90. Read/Write Separation

Where possible, AI applications should separate read and write capabilities.

```text
AI Assistant
    |
    +---- Read Service
    |
    +---- Controlled Write Service
                 |
             Authorization
                 |
              Approval
```

This reduces the impact of compromised or manipulated AI behavior.

---

### 91. Network Segmentation

AI workloads should be segmented according to trust and function.

Potential zones include:

* model serving;
* application;
* data;
* tools;
* management;
* external services.

A compromised AI component should not automatically gain unrestricted lateral network access.

---

### 92. Egress Controls

Outbound communication should be independently restricted.

Controls may include:

* destination allowlists;
* DNS filtering;
* proxy enforcement;
* API restrictions;
* firewall policies;
* DLP inspection.

This is particularly important for browsing-enabled and agentic AI systems.

---

### 93. Ingress Controls

Inbound access should be limited to approved sources.

Controls may include:

* API authentication;
* network allowlists;
* service identity;
* mutual TLS;
* gateway enforcement.

Administrative interfaces should have stronger restrictions than normal inference endpoints.

---

### 94. Authentication Configuration

Authentication should be enforced outside the model.

Possible mechanisms include:

* SSO;
* OAuth;
* workload identity;
* managed identity;
* mutual TLS;
* API authentication.

The model should never be responsible for deciding whether a caller is authenticated.

---

### 95. Authorization Configuration

Authorization should be independently enforced at the application and resource layers.

```text
Identity
   ↓
Application Authorization
   ↓
Data Authorization
   ↓
Tool Authorization
   ↓
Action Authorization
```

This creates multiple independent security boundaries.

---

### 96. Credential Isolation

AI applications should not receive credentials broader than necessary.

Credentials should be isolated by:

* application;
* environment;
* agent;
* tool;
* transaction;
* tenant.

Compromise of one credential should not provide broad enterprise access.

---

### 97. Short-Lived Credentials

Short-lived credentials reduce the impact of configuration compromise.

Benefits include:

* smaller attack window;
* easier revocation;
* reduced persistence;
* improved accountability.

Long-lived static credentials should be avoided where practical.

---

### 98. Secrets Management

Secrets should be stored in dedicated secrets-management systems rather than:

* prompts;
* model configurations;
* source code;
* environment files;
* agent instructions.

AI applications should retrieve only the secrets required for an authorized operation.

---

### 99. Data-Access Filtering

Configuration should specify which data sources an AI application may access.

```text
AI Application
      ↓
Approved Data Sources
      ↓
Authorized Records
      ↓
Minimum Required Context
```

Access to an entire enterprise repository should not be granted when a smaller dataset satisfies the use case.

---

### 100. RAG Retrieval Controls

RAG configuration should enforce:

* source allowlisting;
* authorization;
* tenant separation;
* document permissions;
* retrieval limits;
* metadata filtering;
* provenance.

Retrieval configuration should not bypass existing enterprise access controls.

---

### 101. Memory Isolation

Memory configuration should define:

* retention;
* scope;
* access;
* expiration;
* tenant boundaries;
* session boundaries.

Shared memory should require explicit business and security justification.

---

### 102. Safety-Control Configuration

Safety controls should be centrally governed where possible.

Disabling or weakening safety mechanisms should require:

* documented justification;
* risk assessment;
* approval;
* testing;
* monitoring.

Security-sensitive controls should not be freely configurable by ordinary users.

---

### 103. Content Moderation Configuration

Where content moderation is part of the security architecture, configurations should define:

* applicable policies;
* input inspection;
* output inspection;
* escalation;
* failure behavior.

Moderation should complement—not replace—authorization and application security.

---

### 104. Resource Limits

AI systems should have independent resource boundaries.

Controls should include, where appropriate:

* token limits;
* request limits;
* concurrency limits;
* agent iteration limits;
* tool-call limits;
* processing-time limits;
* file-size limits.

---

### 105. Retry Configuration

Retries can amplify resource consumption and operational failures.

Retry policies should define:

* maximum attempts;
* exponential backoff;
* timeout;
* circuit-breaking;
* retryable errors.

Unbounded retries should not be permitted.

---

### 106. Timeout Configuration

Every AI operation with meaningful resource or business impact should have an appropriate timeout.

Timeouts may apply to:

* model inference;
* tool calls;
* database queries;
* external APIs;
* agent execution;
* file processing.

---

### 107. Fallback Configuration

Fallback mechanisms should maintain equivalent security requirements.

A fallback service should not silently introduce:

* weaker authentication;
* broader data access;
* weaker DLP;
* different retention;
* unapproved provider exposure.

---

### 108. Logging Configuration

Security logging should capture relevant configuration events.

Examples include:

* configuration creation;
* modification;
* deletion;
* model change;
* permission change;
* tool activation;
* provider change;
* security-control modification.

---

### 109. Configuration Change Monitoring

Changes should be monitored against approved change records.

```text
Configuration Change
        ↓
Change Record?
    /       \
  Yes        No
   |          |
Continue     Alert
   |
Validate
   |
Monitor
```

Unauthorized changes should trigger investigation or automated remediation according to risk.

---

### 110. Configuration Drift Detection

Production configuration should be continuously compared with its approved baseline.

Drift may involve:

* model version;
* tool access;
* network permissions;
* data sources;
* security settings;
* resource limits;
* logging.

---

### 111. Runtime Configuration Validation

Configuration should be validated not only before deployment but also during runtime.

This helps detect:

* unauthorized changes;
* provider changes;
* platform changes;
* accidental misconfiguration;
* compromised administration.

---

### 112. Runtime Vulnerability Monitoring

Configuration security should be integrated with vulnerability monitoring.

A previously secure configuration may become unsafe when:

* a dependency becomes vulnerable;
* a model version is compromised;
* a provider reports an incident;
* a tool vulnerability emerges.

---

### 113. Behavioral Configuration Monitoring

Configuration changes can cause behavioral changes.

Monitoring should correlate:

```text
Configuration Change
        ↓
Behavior Change
        ↓
Security Impact
```

Unexpected behavioral changes following configuration modifications should receive additional investigation.

---

### 114. Secure Failure Handling

When security configuration cannot be validated, systems should fail safely.

Examples:

```text
Cannot Verify Model
      → Do Not Deploy

Cannot Verify Configuration
      → Do Not Activate

Cannot Verify Authorization
      → Do Not Execute

Cannot Verify Security Policy
      → Do Not Proceed
```

Security controls should not be silently disabled to preserve availability.

---

### 115. Emergency Configuration Controls

Critical AI systems should provide controlled emergency mechanisms to:

* disable tools;
* revoke credentials;
* block models;
* restrict network access;
* disable external providers;
* reduce resource limits;
* stop agent execution.

Emergency controls should be independently protected and auditable.

---

### 116. Configuration Rollback

Every material configuration change should have a validated rollback path.

```text
Current Configuration
        ↓
Security Problem
        ↓
Rollback
        ↓
Known-Good Configuration
        ↓
Validation
        ↓
Resume Operation
```

Rollback configurations must themselves be verified and protected.

---

### 117. Core Engineering Principle

> **Never rely on the AI model to enforce the security properties of its own configuration.**

The enterprise should independently enforce:

* identity;
* authorization;
* model selection;
* configuration integrity;
* tool permissions;
* data access;
* network connectivity;
* resource limits;
* safety controls;
* logging;
* monitoring;
* deployment approval.

The mature technical model is:

```text
Define Baseline
      ↓
Version Configuration
      ↓
Verify Integrity
      ↓
Validate Policy
      ↓
Test Security
      ↓
Authorize Change
      ↓
Deploy with Least Privilege
      ↓
Monitor Runtime State
      ↓
Detect Drift
      ↓
Contain / Roll Back
```

**Core principle:**

> **AI configuration must be independently enforceable, integrity-protected, least-privileged, continuously monitored, and recoverable. A secure model cannot compensate for an insecure configuration, and a model's behavior must never be treated as a substitute for deterministic security controls.**

## Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. Insecure AI Model Configuration Governance Framework

Organizations should establish a formal governance framework for AI model and system configuration.

The framework should define:

* configuration ownership;
* security requirements;
* approved baselines;
* configuration classification;
* change-management requirements;
* access-control requirements;
* testing requirements;
* monitoring;
* exception handling;
* evidence requirements;
* assurance responsibilities.

Configuration should be governed as an AI security asset throughout its lifecycle.

---

### 119. Configuration Ownership and Accountability

Every production AI configuration should have an accountable owner.

Responsibilities should include:

* maintaining the approved baseline;
* reviewing configuration risk;
* approving appropriate changes;
* ensuring security testing;
* monitoring drift;
* coordinating remediation;
* maintaining evidence.

Ownership should be explicit rather than assumed.

---

### 120. Configuration Risk Classification

Configuration should be classified according to its potential security impact.

A useful classification is:

| Classification | Example                                                 |
| -------------- | ------------------------------------------------------- |
| Low            | Presentation or formatting parameters                   |
| Moderate       | Model behavior or resource parameters                   |
| High           | Data access or external connectivity                    |
| Critical       | Privileged tools, production actions, security controls |

The higher the potential impact, the stronger the governance requirements should be.

---

### 121. AI Application Risk Tiering

AI applications should be assigned risk tiers based on:

* business criticality;
* data sensitivity;
* autonomy;
* privilege;
* external connectivity;
* regulatory impact;
* potential financial impact.

Configuration requirements should inherit the application's risk tier.

---

### 122. Insecure Configuration Risk Register

Configuration risks should be recorded in the enterprise AI risk register.

A risk entry may include:

* AI asset;
* configuration;
* vulnerability;
* affected environment;
* business impact;
* likelihood;
* existing controls;
* risk owner;
* remediation;
* target date;
* residual risk.

---

### 123. Risk Appetite and Tolerance

Organizations should define acceptable configuration risk.

Examples:

* prohibited production configurations;
* maximum privileged tool access;
* maximum external connectivity;
* permitted model providers;
* acceptable configuration drift;
* maximum exception duration.

High-risk deviations should require formal risk acceptance.

---

### 124. Configuration Baseline Governance

Every production AI application should have an approved security baseline.

The baseline should document:

* approved model;
* version;
* inference settings;
* context limits;
* output limits;
* tools;
* data sources;
* network paths;
* authentication;
* authorization;
* logging;
* monitoring;
* resource limits.

---

### 125. Model Selection Governance

Model selection should be governed by business, technical, privacy, and security requirements.

Assessment should consider:

* provider;
* model provenance;
* security capabilities;
* data handling;
* geographic processing;
* supported features;
* known vulnerabilities;
* business criticality.

Performance alone should not determine model selection.

---

### 126. Model Version Governance

Model versions should be formally managed.

Organizations should know:

* which version is approved;
* where it is deployed;
* who approved it;
* when it was introduced;
* what security testing was completed;
* what versions remain available for rollback.

---

### 127. Configuration Parameter Governance

Security-sensitive parameters should have defined acceptable ranges.

Examples include:

* maximum tokens;
* context size;
* temperature;
* concurrency;
* timeout;
* retry count;
* agent iterations;
* tool calls.

Users should not be allowed to arbitrarily change security-sensitive parameters.

---

### 128. Tool Configuration Governance

Each AI-enabled tool should have:

* owner;
* business purpose;
* approved users or agents;
* permitted operations;
* data-access scope;
* risk classification;
* security controls.

Unused tools should be disabled rather than left available indefinitely.

---

### 129. Agent Configuration Governance

Agent configurations should document:

* agent identity;
* purpose;
* allowed tools;
* data access;
* maximum autonomy;
* execution limits;
* human approval requirements;
* external communication;
* termination controls.

Agent configuration should be treated as a privileged security asset.

---

### 130. Data Access Governance

AI data access should follow least privilege.

Governance should define:

* approved data sources;
* authorized identities;
* permitted datasets;
* access duration;
* sensitivity classification;
* retention;
* tenant boundaries.

AI access should inherit enterprise data-governance requirements rather than creating a parallel authorization system.

---

### 131. Sensitive Data Governance

Sensitive data should receive additional configuration protections.

Examples include:

* personal data;
* financial information;
* credentials;
* confidential business information;
* intellectual property;
* security information.

Configuration should prevent unnecessary exposure to models or providers.

---

### 132. RAG Configuration Governance

RAG systems should have formal governance over:

* approved knowledge sources;
* repository ownership;
* document permissions;
* indexing;
* retrieval;
* embeddings;
* metadata;
* retention;
* tenant isolation.

Changes to RAG configuration should be treated as potentially security-impacting changes.

---

### 133. Memory Configuration Governance

Memory governance should establish:

* what information may be retained;
* retention periods;
* access rules;
* session boundaries;
* tenant boundaries;
* deletion requirements.

Persistent AI memory should not become an unmanaged repository of enterprise information.

---

### 134. Credential and Secrets Governance

AI credentials should be governed through enterprise IAM and secrets-management processes.

Requirements should include:

* least privilege;
* ownership;
* rotation;
* expiration;
* revocation;
* monitoring;
* environment separation.

Secrets should never be embedded directly into model prompts or uncontrolled configuration.

### 135. Network and Egress Governance

Governance should identify:

Unrestricted AI network connectivity should require explicit justification.
