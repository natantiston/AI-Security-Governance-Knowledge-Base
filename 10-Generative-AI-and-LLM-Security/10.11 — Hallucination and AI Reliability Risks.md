# 10.11 — Data Poisoning

## Part 1 — Foundations and Core Concepts

# 1. Definition of Data Poisoning

Data poisoning is a deliberate attempt to manipulate, corrupt, or influence data used by an AI system so that the resulting model, retrieval system, embeddings, decisions, or behavior becomes unreliable, unsafe, biased, compromised, or otherwise inconsistent with its intended purpose.

In traditional cybersecurity, attackers may alter databases, configuration files, or software dependencies. In AI systems, attackers can target the **data used to train, fine-tune, retrieve, evaluate, or operate the system**.

The fundamental security problem is:

> **An attacker does not necessarily need to compromise the AI model directly if they can compromise the information from which the AI derives behavior or knowledge.**

Data poisoning can therefore become an upstream attack against the AI security lifecycle.

---

# 2. Data Poisoning as an AI Security Threat

Data poisoning should be treated as an AI security threat rather than simply a data-quality problem.

A conventional data-quality issue may result from:

* accidental corruption;
* incomplete records;
* outdated information;
* incorrect data entry;
* system failures.

Data poisoning is different because the manipulation is intentionally introduced to influence AI behavior or undermine security.

```text
Normal Data Problem
       |
       v
Incorrect Result
       |
       v
Business/Data Quality Issue


Data Poisoning
       |
       v
Intentional Manipulation
       |
       v
AI Behavior / Knowledge Manipulation
       |
       v
Security or Business Impact
```

The distinction is particularly important for security monitoring and incident response.

---

# 3. Why AI Systems Are Vulnerable to Data Poisoning

AI systems depend heavily on data.

Data may influence:

* model training;
* fine-tuning;
* reinforcement processes;
* evaluation;
* retrieval;
* embeddings;
* knowledge bases;
* memory;
* classification;
* recommendations;
* automated decisions.

If an attacker can influence one of these data sources, they may be able to influence the resulting AI behavior.

This creates an important security relationship:

```text
Data
  |
  v
Learning / Retrieval
  |
  v
Model Behavior
  |
  v
Decision
  |
  v
Action
```

A compromise at the data layer can therefore propagate into higher layers of the AI system.

---

# 4. Data Poisoning vs Data Corruption

Data poisoning should be distinguished from ordinary data corruption.

| Characteristic      | Data Corruption       | Data Poisoning                |
| ------------------- | --------------------- | ----------------------------- |
| Intent              | Usually accidental    | Deliberate                    |
| Objective           | Damage or loss        | Influence AI behavior         |
| Target              | Data integrity        | AI learning/retrieval process |
| Security Motivation | Not necessarily       | Usually present               |
| Detection           | Data validation       | Requires security analysis    |
| Impact              | Incorrect information | Potential AI manipulation     |

Not every incorrect dataset represents a poisoning attack.

The security question is whether the data was intentionally manipulated to create an adverse AI outcome.

---

# 5. Data Poisoning vs Prompt Injection

Data poisoning and prompt injection can interact but occur at different stages.

**Prompt injection** attempts to manipulate the model during an interaction.

**Data poisoning** attempts to manipulate information that the AI system will learn from or retrieve.

```text
Data Poisoning
      |
      v
Compromise Data
      |
      v
AI Learns / Retrieves Poisoned Information
      |
      v
Future Behavior


Prompt Injection
      |
      v
Manipulate Current Context
      |
      v
Immediate Model Behavior
```

A poisoned knowledge source can subsequently become a vehicle for indirect prompt injection.

---

# 6. Data Poisoning vs Indirect Prompt Injection

Indirect prompt injection involves malicious instructions embedded in external content that the AI processes.

Data poisoning is broader.

For example:

```text
Attacker
   |
   v
Compromises Knowledge Base
   |
   v
Adds Malicious Content
   |
   v
RAG Retrieval
   |
   v
AI Processes Content
```

If the malicious content contains instructions, the resulting attack may involve **both data poisoning and indirect prompt injection**.

The distinction is useful because the security controls are not identical.

---

# 7. Data Poisoning vs Model Poisoning

Model poisoning targets the model or model-development process directly.

Data poisoning targets the data used by the AI lifecycle.

```text
AI Supply Chain
      |
      +--> Training Data
      |       |
      |       +--> Data Poisoning
      |
      +--> Fine-Tuning Data
      |       |
      |       +--> Data Poisoning
      |
      +--> Model
      |       |
      |       +--> Model Poisoning
      |
      +--> Deployment
```

In practice, the distinction may overlap because poisoned training or fine-tuning data can produce a compromised model.

---

# 8. Training Data Poisoning

Training data poisoning occurs when an attacker intentionally introduces malicious or misleading examples into training datasets.

Potential objectives include:

* changing model behavior;
* introducing bias;
* degrading accuracy;
* creating targeted behavior;
* weakening security controls;
* influencing classifications;
* creating hidden triggers.

The attack may be difficult to detect because the resulting model can appear normal for most inputs.

---

# 9. Fine-Tuning Data Poisoning

Fine-tuning creates another opportunity for poisoning.

An attacker who can influence fine-tuning datasets may attempt to alter:

* model responses;
* preferred behavior;
* domain knowledge;
* refusal behavior;
* classification decisions;
* security-related responses.

Fine-tuning data should therefore receive security controls comparable to other production software and configuration assets.

---

# 10. RAG Data Poisoning

RAG systems create a particularly important data-poisoning attack surface.

```text
      Ingestion
          |
          v
     Processing
          |
          v
    Vector Database
          |
          v
       Retrieval
          |
          v
        LLM
```

If an attacker can insert or modify documents in the knowledge source, the AI may later retrieve the malicious content.

Possible outcomes include:

* false answers;
* manipulated recommendations;
* malicious instructions;
* unauthorized information disclosure;
* fraudulent business guidance;
* incorrect security procedures.

# 11. Knowledge Base Poisoning

Enterprise knowledge bases can become poisoning targets.

Examples include:

* internal wikis;
* document repositories;
* knowledge-management systems;
* ticketing systems;
* CRM records;
* technical documentation;
* policy repositories.

A malicious modification may appear legitimate to the AI if the source is considered trusted.

Therefore:

> **Source accessibility does not automatically establish content integrity.**

# 12. Embedding and Vector Store Poisoning

AI systems frequently transform source content into embeddings.

An attacker may attempt to manipulate:

* source documents;
* metadata;
* embeddings;
* vector indexes;
* retrieval rankings.

The objective may be to make malicious information more likely to enter the AI context.

```text

       |
       v

       |

       |
       v

       |

```

This makes vector infrastructure part of the AI security boundary.

# 13. Evaluation Data Poisoning

Evaluation datasets can also be targeted.

If attackers manipulate evaluation data, organizations may incorrectly conclude that an AI system is secure or accurate.

For example:

```text

      |
      v

      |
```

Evaluation poisoning can therefore attack **security assurance itself**.

# 14. Safety and Security Test Poisoning

Security testing datasets can also be manipulated.

An attacker may attempt to:

* remove difficult test cases;
* add favorable examples;
* alter expected results;
* reduce adversarial coverage;
* hide known weaknesses.

This creates a governance risk because the organization may believe that security controls are effective when they have not been properly tested.

---

# 15. Data Poisoning Through External Sources

AI systems increasingly consume information from external sources.

Potential sources include:

* websites;
* public datasets;
* third-party APIs;
* open-source repositories;
* social media;
* public documents;
* external knowledge bases.

An attacker may deliberately publish manipulated information hoping that an AI system will ingest it.

This creates an AI supply-chain security problem.

---

# 16. Data Poisoning Through Trusted Enterprise Systems

Attackers do not necessarily need to compromise an AI platform directly.

They may instead compromise a connected enterprise system.

The AI may unintentionally amplify the compromised information.

---

# 17. Targeted Data Poisoning

Targeted poisoning attempts to influence specific behaviors rather than degrade the entire AI system.

For example, an attacker may attempt to cause:

```text
Normal Requests
      |
      v
Normal Behavior

Specific Trigger
      |
      v
Manipulated Behavior
```

Targeted poisoning can be particularly dangerous because broad testing may not reveal the malicious behavior.

---

# 18. Availability-Oriented Data Poisoning

Some attacks focus on degrading model or application performance rather than controlling a specific decision.

Potential objectives include:

* reducing model accuracy;
* increasing false positives;
* increasing false negatives;
* degrading retrieval quality;
* creating excessive processing;
* disrupting automated workflows.

This makes data poisoning relevant to both **integrity and availability**.

---

# 19. Integrity Impact

Integrity is often the primary security property affected by poisoning.

A poisoned system may:

* produce incorrect answers;
* recommend unsafe actions;
* misclassify information;
* prioritize malicious content;
* suppress legitimate information;
* make incorrect decisions.

The attacker effectively attempts to alter the AI's information environment.

---

# 20. Confidentiality Impact

Data poisoning can also create confidentiality risks.

For example, malicious data could influence an AI agent to:

* retrieve sensitive records;
* expose information;
* redirect queries;
* trigger unauthorized tools;
* reveal data through manipulated workflows.

A poisoned knowledge source can therefore become part of a larger data-disclosure attack chain.

---

# 21. Availability Impact

Poisoning can affect availability by causing:

* retrieval failures;
* excessive processing;
* incorrect routing;
* unstable model behavior;
* operational disruption;
* excessive resource consumption.

In high-availability AI systems, malicious data manipulation can therefore become an operational resilience concern.

---

# 22. Backdoor Behavior

One of the more advanced poisoning objectives is to introduce hidden behavior that activates under particular conditions.

Conceptually:

```text
Ordinary Input
      |
      v
Expected Behavior


Specific Trigger
      |
      v
Hidden / Manipulated Behavior
```

This can make detection difficult because the system may appear normal during ordinary testing.

Backdoor-oriented poisoning is particularly important for high-impact AI systems and AI supply-chain assurance.

---

# 23. Trigger-Based Poisoning

A poisoning attack may attempt to establish a specific trigger condition.

Triggers could conceptually involve:

* particular phrases;
* combinations of attributes;
* specific data patterns;
* particular users;
* specific workflows;
* contextual conditions.

Security testing should therefore avoid relying solely on random or generic test cases.

---

# 30. Data Provenance and Trust

Data provenance identifies where information originated and how it moved through the AI pipeline.

Important provenance attributes include:

* source;
* owner;
* timestamp;
* acquisition method;
* transformation;
* processing stage;
* version;
* classification;
* integrity status.

A useful security distinction is:

```text
Known Source
      ≠
Trusted Content
```

A legitimate system can contain compromised or manipulated information.

---

# 31. Data Integrity vs Data Trust

Data integrity asks:

> Has the data been altered without authorization?

Data trust asks:

> Should this data be relied upon for this AI purpose?

A dataset can have technically valid integrity while still being unsuitable for a particular AI use case.

For example, a legitimate employee may intentionally enter incorrect information into an enterprise system. The record may be authentic but not necessarily trustworthy for automated decision-making.

---

# 32. Poisoning Detection Challenge

Data poisoning can be difficult to detect because the malicious data may resemble legitimate data.

Potential indicators include:

* unusual distributions;
* anomalous records;
* unexpected source changes;
* sudden shifts in labels;
* abnormal metadata;
* unusual document authors;
* unexplained retrieval-frequency changes;
* unexpected model behavior.

Detection should therefore combine data-quality controls with cybersecurity analytics.

---

# 34. Data Poisoning Risk Factors

Risk increases when an AI system has:

* untrusted data sources;
* automated ingestion;
* weak provenance;

* limited data validation;
* uncontrolled feedback;
* large external datasets;
* automated retraining;
* persistent memory;
* high model autonomy;
* powerful tools;
* weak monitoring.

The combination of **untrusted data + automated ingestion + autonomous action** represents a particularly significant risk pattern.

# 38. Data Poisoning and High-Impact AI

Data poisoning becomes particularly significant when AI is used for:

* financial decisions;

# 39. Data Poisoning Security Objectives

Enterprise defenses should pursue several objectives:

1. **Data Integrity** — prevent unauthorized modification.
2. **Data Authenticity** — establish the origin of information.
3. **Data Provenance** — track where information came from.
4. **Data Trustworthiness** — determine whether information is suitable for use.
5. **Detection** — identify suspicious manipulation.
6. **Containment** — prevent poisoned information from propagating.
7. **Recovery** — restore known-good data.
8. **Assurance** — demonstrate that AI inputs remain trustworthy.

These objectives should apply across training, retrieval, evaluation, and operational data.

---

# 41. Data Poisoning and Governance

Data poisoning is also a governance problem.

Governance should establish:

* who owns AI data;
* who may modify it;
* what sources are approved;
* how data is validated;
* how provenance is maintained;
* when datasets may be used;
* how poisoning is investigated;
* who accepts residual risk.

Without governance, technical teams may have difficulty determining whether a dataset is authorized and trustworthy.

---

# 43. Fundamental Security Principle

> **Do not allow unverified data to become trusted AI knowledge solely because an AI system can technically ingest or retrieve it.**

Data should retain appropriate security classification, provenance, integrity, and authorization throughout the AI lifecycle.

A trusted AI system requires not only a protected model, but also a trustworthy information environment.

---

# 44. Core Enterprise Security Principle

The core enterprise principle for data poisoning is:

> **Protect the integrity and trustworthiness of AI data before it enters the learning or inference pipeline, continuously validate its provenance and behavior, and prevent compromised data from independently driving high-impact AI decisions or actions.**

The model should consume information within a controlled security boundary, while data integrity, authorization, provenance, and business-critical decisions remain subject to independent enterprise controls.


## Part 2 — Technical Security and Control Mechanisms

A mature data-poisoning defense should protect the complete AI data lifecycle rather than focusing only on the model.

The architecture should prevent suspicious or untrusted information from becoming trusted AI knowledge without appropriate validation.

---

# 46. Data Source Authentication

AI data pipelines should authenticate the systems and identities providing data.

Controls may include:

* service identities;
* API authentication;
* mutual TLS;
* signed requests;
* identity-aware access;
* trusted connectors;
* authenticated ingestion pipelines.

Authentication establishes **who supplied the information**, but does not by itself establish that the information is trustworthy.

---

# 47. Data Source Authorization

Only approved sources should be permitted to contribute information to an AI system.

Example:

```text id="z8w2c6"
Data Source
    |
    v
Source Authorization
    |
    +---- Approved ---> Continue
    |
    +---- Unknown ----> Reject / Quarantine
```

Authorization should consider:

* source identity;
* business purpose;
* data classification;
* AI use case;
* environment;
* tenant;
* permitted dataset.

---

# 48. Data Integrity Validation

Integrity controls should detect unauthorized modification.

Potential mechanisms include:

* cryptographic hashes;
* digital signatures;
* checksums;
* immutable storage;
* signed datasets;
* version-controlled artifacts;
* trusted timestamps.

For example:

```text id="q7m3s9"
Approved Dataset
      |
      v
Hash / Signature
      |
      v
Ingestion
      |
      v
Integrity Verification
      |
      +---- Match ---> Accept
      |
      +---- Mismatch -> Quarantine
```

Integrity verification is particularly valuable for controlled datasets and model-development pipelines.

---

# 49. Cryptographic Dataset Integrity

Security-sensitive datasets can be cryptographically signed.

The organization can verify:

* dataset identity;
* dataset version;
* publisher;
* integrity;
* approval status.

This creates stronger assurance than relying solely on filenames, timestamps, or storage permissions.

---

# 50. Dataset Version Control

Datasets used for training, fine-tuning, evaluation, and RAG should be version-controlled where practical.

Versioning should allow the organization to determine:

* what changed;
* who changed it;
* when it changed;
* why it changed;
* whether the change was approved.

Example:

```text id="x6f8q1"
Dataset v1.4
     |
     v
Approved

Dataset v1.5
     |
     +--> Change Review
     +--> Security Testing
     +--> Approval
```

Unexpected dataset changes should trigger investigation.

Provenance enables security teams to trace suspicious AI behavior back to the originating data.

# 53. Data Trust Classification

Not every source should receive the same level of trust.

A practical model may include:

| Trust Level           | Example                                              |
| --------------------- | ---------------------------------------------------- |
| Trusted               | Controlled internal dataset with verified provenance |
| Conditionally Trusted | Approved third-party source                          |
| Untrusted             | Public web content                                   |
| Unknown               | Unverified external content                          |
| Quarantined           | Suspicious or compromised content                    |

Trust classification should influence whether information can be used for training, retrieval, or automated decision-making.

---

# 54. Data Validation

Data should be validated before entering sensitive AI workflows.

Validation may examine:

* schema;
* format;
* completeness;
* duplicate records;
* unexpected values;
* source consistency;
* metadata;
* statistical distributions.

Security validation should operate alongside normal data-quality validation.

---

# 55. Content Sanitization

Content-processing pipelines should remove or isolate elements that may create security risks.

For example:

* executable content;
* malicious HTML;
* unexpected scripts;
* suspicious metadata;
* embedded instructions;
* unsupported file types.

Sanitization should not be treated as a substitute for provenance and authorization.

---

# 56. Malicious Content Detection

AI ingestion systems can use detection mechanisms to identify potentially malicious content.

Indicators may include:

* suspicious instructions;
* anomalous metadata;
* unexpected encoded content;
* unusual document structures;
* known malicious patterns;
* abnormal source behavior.

Detection may combine deterministic rules with machine-learning-based analysis.

---

# 57. Statistical Anomaly Detection

Poisoning may change the statistical characteristics of a dataset.

Detection can monitor:

* label distribution;
* class frequency;
* feature distributions;
* duplicate rates;
* source distribution;
* vocabulary changes;
* embedding distributions.

Example:

```text id="7d5j1x"
Historical Distribution
        |
        v
Expected Range
        |
        v
New Dataset
        |
        +---- Normal ------> Continue
        |
        +---- Significant
              Deviation
                 |
                 v
             Investigate
```

Anomaly detection should identify candidates for investigation rather than automatically declare every anomaly malicious.

---

# 58. Duplicate and Near-Duplicate Detection

Attackers may insert large numbers of similar records to influence training or retrieval.

Controls can detect:

* exact duplicates;
* near duplicates;
* repeated phrases;
* duplicated metadata;
* repeated embeddings;
* abnormal source concentration.

This can identify suspicious attempts to disproportionately influence AI behavior.

---

# 59. Outlier Detection

Outlier analysis can identify unusual records that differ significantly from expected patterns.

Potential methods include:

* statistical thresholds;
* clustering;
* distance-based analysis;
* embedding analysis;
* rule-based validation.

Outliers should be investigated in context because legitimate rare data is not necessarily malicious.

---

# 60. Label Integrity Controls

For supervised learning, labels are security-sensitive inputs.

Controls should protect against:

* unauthorized label changes;
* suspicious label distributions;
* mass relabeling;
* inconsistent annotations;
* malicious annotators.

High-impact datasets should have controlled labeling workflows and audit trails.

---

Suspicious data should be isolated before entering production AI pipelines.

RAG ingestion should be treated as a controlled security pipeline.

7. Integrity validation.

Retrieval results should be validated before entering the model context.

Controls may verify:

* source authorization;
* document status;
* classification;
* tenant;
* freshness;

# 88. Core Engineering Principle

> **Do not trust AI input merely because it is syntactically valid, comes from an approved system, or has successfully passed a single validation mechanism.**

Data poisoning defenses should combine **source authentication, authorization, provenance, integrity verification, content validation, anomaly detection, quarantine, controlled training/retrieval pipelines, behavioral monitoring, and recoverability**.

The security boundary must exist around the entire AI data lifecycle—not only around the model.

# 170. Data Poisoning Incident Playbook

Stop additional contaminated data from entering the AI pipeline.

Remove poisoned data and rebuild affected artifacts.

Restore approved datasets, indexes, and models.

Perform security and behavioral testing.

Preserve relevant logs, versions, hashes, and investigation records.

Update controls, threat models, and detection rules.
