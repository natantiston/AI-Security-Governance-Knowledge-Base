# 10.01 — Generative AI Security Foundations

## Part 1

### 1. Introduction to Generative AI Security

**Generative AI security** is the discipline of protecting AI systems capable of generating new content—including text, images, audio, video, code, and other outputs—from malicious use, unintended behavior, unauthorized access, data exposure, manipulation, and operational failure.

Generative AI introduces security considerations that differ from traditional software and conventional machine-learning systems.

A traditional application generally follows:

```text id="gais101"
INPUT
  ↓
APPLICATION LOGIC
  ↓
OUTPUT
```

A Generative AI application introduces a probabilistic model capable of interpreting natural-language instructions and generating dynamic responses:

```text id="gais102"
USER INPUT
    ↓
PROMPT
    ↓
LLM
    ↓
GENERATED OUTPUT
```

When the LLM is connected to enterprise data and tools, the architecture becomes substantially more complex:

```text id="gais103"
                    USER
                     ↓
                  PROMPT
                     ↓
              GENAI APPLICATION
                     ↓
                    LLM
                ↙    ↓    ↘
             RAG    TOOLS   APIs
              ↓      ↓       ↓
            DATA   ACTIONS  SYSTEMS
```

Security must therefore protect not only the model, but the **entire GenAI ecosystem**.

---

# 2. What Is Generative AI?

Generative AI refers to AI systems designed to generate new content based on learned patterns.

Examples include:

* Text generation.
* Code generation.
* Image generation.
* Audio generation.
* Video generation.
* Document generation.
* Synthetic data generation.

Large Language Models (**LLMs**) are one important category of Generative AI.

```text id="gais104"
GENERATIVE AI
      │
      ├── Text
      │    └── LLMs
      │
      ├── Images
      │
      ├── Audio
      │
      ├── Video
      │
      └── Multimodal
```

---

# 3. What Is an LLM?

A **Large Language Model** is a machine-learning model trained on large quantities of data to understand and generate language.

At a simplified level:

```text id="gais105"
Training Data
     ↓
Model Training
     ↓
LLM
     ↓
Prompt
     ↓
Generated Response
```

An LLM does not operate like a conventional deterministic database.

It generates responses based on learned statistical patterns and contextual information.

This creates unique security and reliability challenges.

---

# 4. Why LLM Security Is Different

Traditional application security typically assumes that application logic determines how inputs are processed.

LLMs introduce a different paradigm:

```text id="gais106"
Traditional Application

Input
 ↓
Rules
 ↓
Deterministic Logic
 ↓
Output
```

versus:

```text id="gais107"
LLM Application

Input
 ↓
Natural-Language Instructions
 ↓
Probabilistic Model
 ↓
Generated Output
```

The model may interpret instructions in ways that developers did not explicitly anticipate.

---

Each layer can introduce different vulnerabilities.

# 7. Core Security Objectives

Generative AI security should preserve the traditional **CIA triad**:

### Confidentiality

Prevent unauthorized disclosure of:

* Prompts.
* System instructions.
* Enterprise data.
* Model information.
* User information.
* Credentials.

### Integrity

Prevent unauthorized manipulation of:

* Models.
* Prompts.
* Retrieval data.
* Configuration.
* Outputs.
* Tool actions.

### Availability

Ensure AI services remain available and resilient.

```text id="gais111"
             GENAI SECURITY
                   ↓
        ┌──────────┼──────────┐
        ↓          ↓          ↓
 Confidentiality Integrity Availability
```

# 10. User Input as an Attack Surface

Natural-language input cannot automatically be considered trusted.

A user may intentionally provide malicious instructions.

Example:

```text id="gais114"
Legitimate User Input
        ↓
Application
        ↓
LLM

Malicious User Input
        ↓
Application
        ↓
LLM
        ↓
Unexpected Behavior
```

This is the foundation for understanding **prompt injection**, which will be examined in later topics.

---

# 11. Prompt as a Security Boundary

In traditional applications, developers often rely on programmatic authorization.

In GenAI applications, instructions may be conveyed through prompts.

This creates a critical distinction:

> **A prompt is an instruction mechanism, not a security boundary by itself.**

For example, telling an LLM:

> "Never reveal confidential information."

does not guarantee that confidential information cannot be exposed.

Security controls must exist outside the model's instructions where appropriate.

---

# 12. System Prompts

A system prompt establishes instructions or behavioral constraints for an LLM.

A simplified architecture is:

```text id="gais116"
SYSTEM INSTRUCTIONS
       +
USER PROMPT
       +
CONTEXT
       ↓
      LLM
       ↓
    OUTPUT
```

System prompts can contain sensitive business logic or behavioral instructions and therefore require appropriate protection.

---

# 13. Prompt Hierarchy

GenAI applications may process multiple instruction sources.

For example:

```text id="gais117"
System Instructions
        ↓
Developer Instructions
        ↓
Retrieved Context
        ↓
User Input
        ↓
Model Response
```

Security architecture should define how these instruction sources interact.

---

# 14. Prompt Injection

Prompt injection occurs when an attacker manipulates the instructions provided to an AI system in order to influence its behavior contrary to the application's intended purpose.

A simplified example:

```text id="gais118"
Attacker Input
      ↓
Malicious Instruction
      ↓
LLM
      ↓
Unexpected Response
```

Prompt injection is one of the defining security challenges of LLM applications.

---

# 15. Direct vs. Indirect Prompt Injection

Prompt injection can generally be considered in two broad forms.

### Direct Prompt Injection

The attacker directly submits malicious instructions to the model.

```text id="gais119"
Attacker
   ↓
Malicious Prompt
   ↓
LLM
```

### Indirect Prompt Injection

The malicious instruction is embedded in content that the model later processes.

```text id="gais120"
Malicious Document / Web Page
             ↓
         Retrieval
             ↓
            LLM
```

Both can create security consequences.

---

# 16. Jailbreaking

Jailbreaking refers to attempts to bypass an AI system's intended safety or behavioral restrictions.

Conceptually:

```text id="gais121"
Security Restriction
        ↓
Attacker
        ↓
Bypass Attempt
        ↓
Model
        ↓
Restricted Behavior
```

Jailbreaking is therefore primarily concerned with circumventing model-level restrictions.

---

# 17. Sensitive Information Disclosure

GenAI systems may expose sensitive information through:

* User prompts.
* Retrieved documents.
* Model responses.
* Logs.
* Application interfaces.
* Training or fine-tuning data.

Potential information includes:

* Personal data.
* Credentials.
* Internal documents.
* Proprietary information.
* Confidential business information.

---

# 18. Hallucination as a Security Concern

An LLM can produce information that appears credible but is inaccurate or unsupported.

This is commonly referred to as **hallucination**.

Hallucination is primarily a reliability issue, but it can become a security or business risk when outputs influence consequential actions.

```text id="gais123"
Incorrect Output
      ↓
Human / Application Trust
      ↓
Decision / Action
      ↓
Business Impact
```

---

# 19. Retrieval-Augmented Generation

Many enterprise GenAI systems use **Retrieval-Augmented Generation (RAG)**.

A simplified architecture is:

```text id="gais124"
User Question
      ↓
Retriever
      ↓
Relevant Documents
      ↓
Context
      ↓
LLM
      ↓
Response
```

RAG improves access to enterprise-specific information but introduces additional security surfaces.

---

# 20. RAG Security

RAG introduces risks involving:

* Document access.
* Data poisoning.
* Retrieval manipulation.
* Unauthorized retrieval.
* Sensitive information exposure.
* Malicious documents.
* Access-control failures.

The security model therefore becomes:

```text id="gais125"
USER
 ↓
APPLICATION
 ↓
RETRIEVER
 ↓
VECTOR STORE
 ↓
DOCUMENTS
 ↓
LLM
 ↓
OUTPUT
```

Every component requires appropriate controls.

---

# 21. Vector Database Security

RAG systems frequently use vector databases or vector stores.

They contain embeddings representing information extracted from source content.

Security considerations include:

* Access control.
* Tenant isolation.
* Encryption.
* Data integrity.
* Query authorization.
* Logging.
* Data lifecycle management.

---

# 22. Embedding Security

Embeddings are numerical representations of information.

Conceptually:

```text id="gais127"
Document
   ↓
Embedding Model
   ↓
Vector
   ↓
Vector Database
```

Although embeddings are not simply copies of the original text, they can still represent sensitive information and therefore require appropriate security controls.

---

# 23. Retrieval Manipulation

An attacker may attempt to influence which information is retrieved by the AI system.

```text id="gais128"
Attacker-Controlled Content
        ↓
Vector Store
        ↓
Retrieval
        ↓
LLM Context
        ↓
Manipulated Output
```

This makes data integrity and provenance important components of RAG security.

---

# 24. Excessive Agency

Some GenAI systems can perform actions rather than merely generate responses.

For example:

```text id="gais129"
LLM
 ├── Read Email
 ├── Send Email
 ├── Query Database
 ├── Create Ticket
 └── Call API
```

The more capabilities the model receives, the greater the potential impact of misuse.

---

# 25. Principle of Least Agency

AI systems should receive only the capabilities necessary for their approved purpose.

```text id="gais130"
Business Requirement
       ↓
Required Capability
       ↓
Minimum Tool Permission
       ↓
Controlled Execution
```

This extends the traditional cybersecurity principle of **least privilege** into the AI-agent environment.

---

# 26. Insecure Output Handling

LLM outputs should not automatically be trusted.

For example:

```text id="gais131"
LLM Output
    ↓
Application
    ↓
Database / Browser / Command / API
```

If the application executes model-generated content without appropriate validation, an LLM response could become an attack vector against downstream systems.

---

# 27. Unbounded Consumption

GenAI services can consume substantial computational resources.

Attackers may exploit this through:

* Excessive requests.
* Very large inputs.
* Long-running interactions.
* Repeated generation.
* Automated abuse.

```text id="gais132"
Attacker
   ↓
大量 Requests
   ↓
LLM Service
   ↓
Resource Consumption
   ↓
Cost / Availability Impact
```

Therefore, rate limiting, quotas, input limits, and monitoring can be important controls.

---

# 29. Third-Party LLM Providers

Organizations may consume LLMs through external providers.

Security assessment should consider:

* Data handling.
* Retention.

* Access controls.

---

# 30. The GenAI Security Mindset

A traditional security mindset may ask:

> "Is the application secure?"

For Generative AI, the better question is:

> **"Can the entire AI system be manipulated, misused, exposed, or caused to take unintended actions?"**

The security boundary therefore extends beyond the model.

```text id="gais135"
                 GENAI SYSTEM
                      │
        ┌─────────────┼─────────────┐
        ↓             ↓             ↓
       USER          MODEL         DATA
        ↓             ↓             ↓
      PROMPT       BEHAVIOR       RAG
        │             │             │
        └─────────────┼─────────────┘
                      ↓
                   TOOLS
                      ↓
                    APIs
                      ↓
                  ENTERPRISE
```

### Core Principle

> **Generative AI security is the discipline of protecting the model, prompts, data, applications, integrations, tools, infrastructure, users, and downstream systems against manipulation, unauthorized access, information disclosure, unsafe behavior, and operational abuse throughout the AI lifecycle.**
