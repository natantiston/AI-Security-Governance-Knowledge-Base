# 10.18 — Model Denial of Service and Unbounded Consumption

## Part 1 — Foundations and Core Concepts

# 1. Definition of Model Denial of Service and Unbounded Consumption

Model Denial of Service (DoS) and Unbounded Consumption describes security and resilience conditions in which AI systems become unavailable, degraded, excessively expensive, or operationally unstable because model resources are consumed beyond intended capacity.

Unlike traditional network DoS, AI systems can be exhausted through the **computational characteristics of legitimate-looking AI requests**.

Potentially expensive resources include:

* model inference capacity;
* GPU/accelerator capacity;
* CPU and memory;
* context-window processing;
* token generation;
* embedding generation;
* vector searches;
* agent execution;
* tool calls;
* API capacity;
* storage;
* bandwidth;
* third-party model quotas;
* cloud spending.

# 2. Model Denial of Service as an AI Security Threat

AI workloads have distinctive consumption characteristics.

A single request can potentially trigger:

```text id="a18d01"
User Request
     |
     v
Large Context
     |
     v
LLM Inference
     |
     +----> Multiple Tool Calls
     |
     +----> Retrieval
     |
     +----> Additional Model Calls
     |
     +----> Long Output
     |
     v
High Resource Consumption
```

An attacker does not necessarily need to compromise the AI model.

They may instead exploit the cost, latency, or resource intensity of normal AI functionality.

---

# 3. Fundamental Security Problem

The fundamental problem is the mismatch between:

> **How much resource an AI request can consume and how little authority is required to submit that request.**

Traditional applications often have relatively predictable request costs.

AI applications may have highly variable costs depending on:

* input length;
* output length;
* model;
* reasoning complexity;
* retrieval depth;
* number of tools;
* agent loops;
* multimodal processing;
* retries;
* parallel execution.

Therefore:

```text id="m18d02"
Low Request Privilege
        +
High Computational Cost
        =
Potential AI DoS Risk
```

---

# 4. Model DoS vs Traditional DoS

Traditional DoS commonly targets:

* network bandwidth;
* connection capacity;
* CPU;
* memory;
* application threads.

AI-specific DoS may additionally target:

* token processing;
* context windows;
* inference queues;
* GPU time;
* model API quotas;
* agent execution;
* retrieval infrastructure;
* tool calls;
* external API quotas;
* inference spending.

AI DoS should therefore be considered both an **availability risk and a resource-governance risk**.

---

# 5. Unbounded Consumption

Unbounded consumption occurs when an AI system allows resource usage to grow without an effective upper limit.

Examples include:

* unlimited prompt size;
* unlimited output length;
* unlimited agent iterations;
* unlimited tool calls;
* unlimited retries;
* unlimited retrieval;
* unlimited file processing;
* unlimited concurrent requests.

The absence of explicit limits creates an exploitable security condition.

---

# 6. Resource Exhaustion as an AI Security Boundary

Resource limits should be treated as security boundaries.

```text id="r18d03"
Request
   |
   v

   |
   v
Authorization
   |
   v
Resource Policy
   |
   +--> Token Limit
   +--> Time Limit
   +--> Tool Limit
   +--> Cost Limit
   +--> Concurrency Limit
   |
   v
Execution
```

The AI model itself should not be responsible for enforcing these boundaries.

# 7. Token Consumption

Tokens are a fundamental AI resource.

Consumption can occur through:

* input tokens;
* output tokens;
* retrieved context;
* conversation history;
* system instructions;
* tool results;
* memory;
* multimodal representations.

Large token volumes can increase both:

* processing requirements;
* financial cost.

# 8. Context-Window Exhaustion

AI applications may process large context windows.

Potential sources include:

* long documents;
* large conversation histories;
* RAG results;
* memory;
* tool responses;
* uploaded files.

An attacker may attempt to cause excessive context processing.

This can result in:

* latency;
* queue growth;
* increased cost;
* reduced availability;
* resource starvation.

# 9. Output Amplification

A relatively small request can potentially generate a very large response.

For example:

```text id="x18d04"

     |

     |
     v

     |
```

Output limits are therefore an important AI security control.

# 10. Computationally Expensive Requests

Different AI requests can have dramatically different computational costs.

Examples include:

* long-context reasoning;
* large-document processing;
* multimodal analysis;
* complex transformations;
* extensive retrieval;
* repeated tool execution.

A request-count-only security model may therefore fail to accurately measure AI resource consumption.

# 11. Model Selection and Resource Consumption

Organizations often expose multiple models with different resource requirements.

```text id="c18d05"

   +--> Small Model
   |
   +--> Large Model
   |
   +--> Specialized Model
   |
   +--> Multimodal Model
```

Allowing every user or agent to automatically select the most expensive model can create unnecessary resource exposure.

Model selection should therefore be governed.

# 15. Agent Loop Risk

Agents may repeatedly execute reasoning or tool cycles.

An uncontrolled loop can resemble:

```text id="l18d10"

 ↓
Action
 ↓
Result
 ↓
Replan
 ↓
Action
 ↓
Result
 ↓
Replan
 ↓

```

Without a maximum iteration count or termination condition, resource consumption may become effectively unbounded.

# 16. Recursive Agent Invocation

One agent may invoke another agent, which invokes another service.

```text id="r18d11"
Agent A
   |
   v
Agent B
   |
   v
Agent C
   |
   v
Agent D
   |
   v
More Model Calls
```

This creates the possibility of recursive or cascading resource consumption.

Agent delegation should therefore have explicit boundaries.

# 17. Tool-Call Amplification

AI agents may consume resources through repeated tool calls.

Examples include:

* database queries;
* web searches;
* API requests;
* file operations;
* cloud operations;
* security scans.

A tool-call limit should therefore be considered an AI availability control.

---

# 18. Retrieval Amplification

RAG systems can consume substantial resources through:

* repeated vector searches;
* large top-k retrieval;
* multiple retrieval passes;
* reranking;
* document expansion;
* repeated queries.

A single user request may therefore produce significant backend activity.

---

# 19. Embedding Consumption

Embedding pipelines can also become resource targets.

Potentially expensive workloads include:

* large file ingestion;
* repeated embedding generation;
* bulk document processing;
* re-indexing;
* continuous ingestion.

Embedding services should therefore have capacity and quota controls.

---

# 20. Multimodal Resource Consumption

AI systems processing images, audio, video, or other modalities may have substantially different resource profiles.

Examples include:

* high-resolution image analysis;
* long audio transcription;
* video processing;
* large multimodal contexts.

Simple request-count limits may not adequately protect these workloads.

---

# 21. File Processing and Resource Exhaustion

AI applications may accept uploaded files.

Potential resource consumption can arise from:

* large files;
* many files;
* complex documents;
* compressed content;
* repeated processing;
* conversion;
* OCR;
* parsing;
* embedding.

File-size and processing limits should therefore form part of the security boundary.

---

# 22. API Quota Exhaustion

AI applications frequently depend on external services.

Examples include:

* model providers;
* embedding providers;
* search APIs;
* cloud services;
* translation APIs;
* external business systems.

An AI workload can consume third-party quotas and cause service disruption.

---

# 23. Financial Resource Exhaustion

AI DoS is not limited to technical availability.

Unbounded inference can generate unexpected financial costs.

```text id="f18d12"
   |
```

# 24. Economic Denial of Service

Economic DoS occurs when an attacker causes the organization to consume expensive resources at a rate that creates unacceptable financial impact.

Potential targets include:

* token-based APIs;
* GPU workloads;
* cloud inference;
* embedding generation;
* storage;
* external APIs.

The objective may be to increase cost even when complete service unavailability is not achieved.

---

# 25. Availability vs Cost Impact

AI resource attacks may produce different outcomes.

| Outcome             | Impact                        |
| ------------------- | ----------------------------- |
| Increased latency   | User experience degradation   |
| Queue saturation    | Reduced availability          |
| Timeout             | Failed requests               |
| Resource exhaustion | Service outage                |
| Quota exhaustion    | External service interruption |
| Cost spike          | Financial loss                |
| Cascading overload  | Enterprise-wide disruption    |

Availability and financial controls should therefore be considered together.

# 26. Concurrency

Concurrency controls limit the number of simultaneous AI operations.

Without concurrency controls:

```text id="c18d13"
User A ─┐
User B ─┤
User C ─┤
User D ─┼──> AI Service
User E ─┤
User F ─┤
User G ─┘
```

A relatively small number of identities may still create substantial parallel consumption.

---

# 27. Per-User Resource Limits

Resource consumption should often be bounded per identity.

Possible limits include:

* requests per minute;
* concurrent requests;
* tokens per period;
* maximum output;
* maximum processing time;
* maximum tool calls.

This prevents a single identity from consuming disproportionate resources.

---

# 28. Per-Application Resource Limits

Applications may have different resource requirements.

For example:

```text id="p18d14"
Application A → 10,000 tokens/min
Application B → 100,000 tokens/min
Application C → 1,000,000 tokens/min
```

Quotas should reflect approved business requirements rather than allowing unlimited consumption.

---

# 29. Per-Agent Resource Limits

Agents should have their own resource budgets.

A budget may cover:

* model calls;
* tool calls;
* retrieval operations;
* execution time;
* tokens;
* external API requests.

Agent-level controls are important because the agent may amplify a single user request.

---

# 30. Session Resource Limits

Long-running sessions can accumulate resource consumption.

Controls may include:

* maximum session duration;
* maximum conversation length;
* maximum cumulative tokens;
* maximum tool calls;
* idle timeouts.

Sessions should not remain indefinitely active without explicit business justification.

---

# 31. Tenant Resource Isolation

Multi-tenant AI platforms should prevent one tenant from consuming resources needed by others.

```text id="t18d15"
Tenant A ──> Resource Pool A
Tenant B ──> Resource Pool B
Tenant C ──> Resource Pool C
```

Where shared infrastructure is required, fair-use and quota controls should prevent resource starvation.

---

# 32. Resource Fairness

Enterprise AI platforms should establish fair resource allocation.

Resource fairness may consider:

* business priority;
* tenant;
* application criticality;
* user;
* workload type;
* service tier.

Critical workloads should not necessarily compete equally with low-priority workloads.

---

# 35. Request Cost Estimation

AI systems can estimate resource consumption before execution.

Potential factors include:

* input token count;
* expected output size;
* model;
* context size;
* number of tools;
* retrieval depth;
* modality.

This enables more intelligent admission and quota decisions.

# 36. Token Budgets

Token budgets provide explicit boundaries around model consumption.

```text id="k18d18"

     v
```

# 37. Time Budgets

Each AI operation should have a maximum execution duration where practical.

Time limits protect against:

* stalled operations;
* excessive reasoning;
* tool loops;
* external service delays;
* resource starvation.

Timeouts should fail safely rather than trigger uncontrolled retries.

---

# 38. Tool-Call Budgets

Agentic systems should limit tool invocation.

For example:

```text id="u18d19"
Maximum:
20 Tool Calls / Task

Maximum:
5 Database Queries / Task

Maximum:
3 External API Calls / Task
```

The specific limits should be risk-based.

---

# 39. Cost Budgets

AI applications should have financial consumption boundaries.

Possible controls include:

* daily spend limits;
* monthly quotas;
* per-application budgets;
* per-user budgets;
* per-agent budgets;
* anomaly alerts.

Cost governance should be integrated with security monitoring.

---

# 40. Rate Limiting

Rate limiting remains a fundamental control.

However, AI rate limits should account for more than request count.

Possible dimensions include:

* requests per minute;
* tokens per minute;
* concurrent operations;
* model calls;
* tool calls;
* data volume;
* compute time.

---

# 41. Adaptive Rate Limiting

# 42. Queue Management

Queue controls should prevent a large number of expensive requests from overwhelming inference infrastructure.

Controls include:

* queue limits;
* request prioritization;
* queue expiration;
* workload isolation;
* admission control;
* backpressure.

# 43. Backpressure

Backpressure allows downstream systems to signal that they cannot safely accept additional workload.

```text id="b18d21"

    |

    |
```

# 44. Cascading Failure

AI applications frequently depend on multiple services.

```text id="c18d22"
AI Request
    |
    +--> LLM
    +--> Vector DB
    +--> Search
    +--> API
    +--> Database
    +--> Tool
```

Overload in one component may propagate into others.

This creates a cascading-failure risk.

---

# 45. Retry Storms

When multiple components retry simultaneously, an initial failure can become an amplification event.

```text id="r18d23"
Service Failure
      |
      +--> Retry
      +--> Retry
      +--> Retry
      |
      v
More Load
      |
      v
Further Failure
```

AI architectures should use bounded retries, backoff, and circuit breakers.

---

# 46. Circuit Breakers

Circuit breakers can temporarily stop requests to overloaded or failing dependencies.

```text id="s18d24"
AI Service
    |
    v
Circuit Breaker
    |
 +--+--+
 |     |
Closed Open
 |     |
 v     v
Call   Fail Fast
```

This prevents repeated AI requests from worsening an existing outage.

---

# 47. Fail-Safe Resource Handling

When resource limits are reached, the system should fail safely.

Appropriate behavior may include:

* reject the request;
* reduce workload;
* disable optional tools;
* switch to a lower-cost model;
* require user retry;
* route to a fallback service.

It should not silently remove security controls to preserve functionality.

---

# 51. Key Risk Factors

Risk increases when an AI system has:

* unlimited requests;
* unrestricted token budgets;
* unrestricted context;
* autonomous agents;
* many tool integrations;
* unrestricted recursion;

# 52. Model DoS and Confidentiality

Although primarily an availability threat, resource attacks can create confidentiality risks.

For example, overloaded systems may:

* disable security checks;
* fall back to weaker configurations;
* expose debugging information;
* trigger unsafe fail-open behavior;
* bypass normal review processes.

Availability failures can therefore become security-boundary failures.

---

# 53. Model DoS and Integrity

Resource exhaustion can also affect integrity.

Under extreme conditions, systems may:

* process incomplete requests;
* skip validation;
* execute degraded workflows;
* use stale information;
* produce inconsistent results.

Security controls should therefore remain active during resource pressure.

# 54. Model DoS and Availability

Availability is the primary security objective.

The goal is to ensure that:

* legitimate users retain service;
* critical AI workloads remain operational;
* inference capacity remains available;
* dependencies do not cascade into failure;
* recovery can occur quickly.

Availability should be treated as an AI security property.

# 65. Security Boundary Principle

The AI model should never be allowed to determine how much enterprise resource it is entitled to consume.

Resource authority should be enforced outside the model.

```text id="s18d33"
AI Model
   |
   | "I need 100 more tool calls"
   v
Policy Engine
   |
   +--> Budget
   +--> Identity
   +--> Risk
   +--> Capacity
   |
   v
Allow / Limit / Deny
```

The model may request work; the enterprise control plane determines whether that work is permitted.

---

# 66. Model Behavior Is Not Resource Governance

A system prompt may instruct an agent:

> "Do not make more than ten tool calls."

That instruction is useful but insufficient.

A compromised, manipulated, malfunctioning, or misconfigured agent could ignore it.

Therefore:

> **Prompt instructions are not resource quotas.**

The actual limit must be enforced by infrastructure or deterministic policy.

# 72. Fundamental Security Principle

> **No AI user, application, model, or agent should be capable of consuming unlimited enterprise or third-party resources merely because the underlying AI capability technically permits it.**

The secure operating model is:

```text id="f18d36"
Request
```

## Part 2 — Technical Security and Control Mechanisms

# 73. Model Denial of Service Defense Architecture

AI resource protection should use multiple independent enforcement layers.

```text id="d18p01"
User / Agent
     |
     v
API Gateway
     |
     +--> Authentication
     +--> Rate Limiting
     +--> Quotas
     +--> Request Limits
     |
     v
AI Security Control Layer
     |
     +--> Token Budget
     +--> Context Limit
     +--> Cost Policy
     +--> Risk Assessment
     |
     v

     |
     +--> Agent Limits
     +--> Tool Limits
     +--> Retry Limits
     |
     v
Model / Vector / Tool Infrastructure
     |
     v
Capacity + Monitoring + Containment
```

The objective is to prevent any single request, identity, agent, or application from obtaining unlimited access to computational resources.

---

# 74. Identity-Based Resource Controls

Resource consumption should be associated with authenticated identities.

Controls may be applied to:

* users;
* service accounts;
* applications;
* agents;
* tenants;
* API clients.

Identity-based attribution enables both enforcement and investigation.

Each user should have defined request limits appropriate to the business function.

Limits may include:

* requests per minute;
* requests per hour;
* tokens per minute;
* concurrent requests.

High-risk or expensive workloads may require lower limits.

# 76. Per-Application Rate Limiting

AI applications should have application-specific consumption policies.

For example:

```text id="d18p02"

→ Lower Volume / Higher Compute

Experimental AI
→ Restricted Quota
```

Limits should reflect approved business requirements.

---

```text id="d18p03"
     +--> Model Call
     +--> API
```

* concurrent requests;
* storage;
* embedding generation;
* vector queries.

Multiple layers provide stronger protection against abuse.

Applications should define maximum acceptable input sizes.

Controls may include:

* maximum prompt length;
* maximum document size;
* maximum conversation history;
* maximum retrieved context;
* maximum multimodal payload.

Input limits reduce unnecessary computation before inference begins.

---

# 81. Output Token Limits

Generated responses should have explicit limits.

Output limits reduce:

* compute consumption;
* latency;
* response bandwidth;
* storage;
* downstream processing.

A model should not be permitted to generate unlimited output merely because the provider supports a large context or output capacity.

# 82. Context Budgeting

```text id="d18p05"

       +
User Input
       +
Conversation
       +
RAG Results
       +
Memory
       +
Tool Results
       =
Context Budget
```

The application should enforce a maximum context budget before sending the request to the model.

Where business requirements permit, excessive context can be reduced through:

* summarization;
* deduplication;
* relevance filtering;
* document chunking;
* retrieval limits.

Compression should not be used to bypass security or authorization controls.

# 84. Retrieval Limits

RAG systems should limit the amount of retrieved information per request.

Controls may include:

* maximum top-k;
* maximum total retrieved tokens;
* maximum documents;
* maximum retrieval rounds;

Vector databases should have independent query controls.

Possible limits include:

* queries per user;
* queries per agent;
* concurrent searches;
* maximum result size.

* repeated retries;
* resource locking.

Time limits should be independent of the model's own instructions.

Limits should be adjusted according to application risk.

* application;

* terminate;
* degrade safely.

* bypass validation;
* increase privileges;
* silently increase quotas.

Resource exhaustion must never become a reason to weaken security controls.

# 133. Core Engineering Principle

> **Never rely on the AI model to regulate its own resource consumption.**

The model may request computation, generate additional tasks, invoke tools, or continue an agent loop.

```text id="d18p21"
Using Which Tools?
At What Cost?
For Which Identity?
```

* increased concurrency;

* new external APIs.

---

# 155. Model Change Governance

Changing the underlying model can alter:

* token consumption;
* latency;
* output length;
* reasoning behavior;
* tool-calling frequency;
* cost.

Model changes should therefore trigger resource-impact assessment.

---

# 156. Agent Configuration Governance

Agent configuration changes should be treated as security-relevant changes.

Examples include:

* increasing iteration limits;
* adding tools;
* increasing context;
* changing retry behavior;
* increasing execution duration;
* enabling parallel tool calls.

Each change can materially alter the application's resource-exhaustion profile.

---

# 157. Testing Governance

AI applications should undergo resource security testing before production deployment.

Testing should cover:

* normal load;
* peak load;
* burst load;
* abuse;
* maximum request size;
* maximum output;
* agent loops;
* tool amplification;
* dependency failure;
* recovery.

---

# 158. Load Testing

Load testing should establish expected capacity under legitimate demand.

Metrics should include:

* throughput;
* latency;
* queue depth;
* token consumption;
* compute utilization;
* failure rates;
* cost.

Results should establish operational baselines.

---

# 159. Stress Testing

Stress testing should determine how the system behaves beyond normal capacity.

The objective is not merely to determine when the service fails, but whether it:

* throttles;
* queues;
* rejects;
* degrades;
* isolates workloads;
* preserves critical services.

---

# 160. Adversarial Resource Testing

Security teams should intentionally test resource-abuse scenarios.

Examples include:

```text id="g18p03"
Large Input
    +
Maximum Output
    +
Repeated Requests
    +
Agent Loops
    +
Tool Amplification
```

The purpose is to validate that independent resource controls actually enforce their limits.

---

# 161. Agent Runaway Testing

Agents should be tested against:

* infinite loops;
* repeated tool failures;
* conflicting instructions;
* unavailable dependencies;
* recursive delegation;
* repeated retries.

The expected result should be deterministic termination rather than indefinite execution.

---

# 162. Control Effectiveness Testing

Controls should be tested against defined objectives.

Example:

| Control           | Test                | Expected Result     |
| ----------------- | ------------------- | ------------------- |
| Token quota       | Exceed quota        | Request limited     |
| Tool limit        | Call beyond maximum | Call denied         |
| Iteration limit   | Continue loop       | Agent terminated    |
| Concurrency limit | Exceed capacity     | Requests throttled  |
| Cost budget       | Exceed budget       | Consumption blocked |
| Kill switch       | Activate            | AI execution stops  |

---

# 163. Resource Security Baselines

Organizations should establish expected baselines for:

* tokens/request;
* requests/user;
* requests/application;
* tool calls/task;
* agent iterations;
* execution time;
* cost;
* latency;
* concurrency.

Baselines allow abnormal behavior to be identified.

---

# 164. Monitoring and Key Risk Indicators

Key risk indicators may include:

* token consumption growth;
* cost per request;
* requests per identity;
* concurrent executions;
* agent iterations;
* tool calls;
* queue depth;
* model utilization;
* GPU utilization;
* external API consumption;
* throttling rate.

Thresholds should be defined according to application risk.

---

# 165. Security Monitoring

AI resource monitoring should integrate with enterprise security monitoring.

Relevant events include:

* quota exhaustion;
* unusual consumption;
* repeated maximum-size requests;
* abnormal agent execution;
* excessive tool usage;
* unusual model selection;
* repeated retries;
* sudden cost spikes.

---

# 166. Incident Classification

Resource incidents should have defined severity levels.

Example:

| Severity | Example                                            |
| -------- | -------------------------------------------------- |
| Low      | Individual user exceeds quota                      |
| Medium   | Application resource degradation                   |
| High     | Significant service disruption                     |
| Critical | Enterprise-wide outage or major financial exposure |

Severity should consider both technical and business impact.

---

# 167. Incident Response Governance

The incident response process should define:

1. detection;
2. validation;
3. containment;
4. resource protection;
5. service restoration;
6. root-cause analysis;
7. evidence preservation;
8. corrective action.

Response procedures should distinguish malicious abuse from accidental runaway behavior.

---

# 168. SOC Integration

The SOC should receive relevant AI resource-security telemetry.

Potential detections include:

```text id="g18p04"
Identity
   ↓
Abnormal Consumption
   ↓
AI Security Analytics
   ↓
SOC Alert
   ↓
Investigation
   ↓
Throttle / Block / Isolate
```

AI resource abuse should be treated as a security signal, not only an operations metric.

---

# 169. Business Continuity and Resilience

Critical AI applications should have documented continuity strategies.

These may include:

* alternate models;
* alternate providers;
* reserved capacity;
* degraded modes;
* manual processes;
* workload prioritization;
* emergency quotas.

Fallback mechanisms must preserve security requirements.

---

# 170. Disaster Recovery

Recovery planning should establish:

* recovery time objectives;
* recovery point objectives where applicable;
* dependency recovery;
* capacity restoration;
* quota restoration;
* configuration recovery;
* provider failover.

Recovery should not depend on unrestricted resource provisioning.

---

# 171. Cost Governance and FinOps Integration

AI security should integrate with financial governance.

Security and FinOps teams should jointly monitor:

* model spend;
* token usage;
* cost per application;
* cost anomalies;
* provider usage;
* budget consumption.

A major cost anomaly may represent either operational failure or security abuse.

---

# 172. Exception Management

Exceptions to resource limits should be formally documented.

An exception should identify:

* affected application;
* requested limit;
* business justification;
* risk;
* compensating controls;
* approval authority;
* expiration date.

Permanent undocumented exceptions create unmanaged resource risk.

---

# 173. Risk Acceptance

Where resource limits cannot technically meet business requirements, residual risk should be explicitly accepted by an authorized risk owner.

Risk acceptance should not be implied by production deployment.

---

AI resource security should not operate as an isolated AI engineering practice.

Continuous monitoring reduces the time between control failure and detection.

* agents gain tools;

* autoscaling expands;

Drift detection should compare actual configuration with the approved security baseline.

# 185. Resource Security Maturity Model

A practical maturity model can be:

| Level          | Capability                                  |
| -------------- | ------------------------------------------- |
| 1 — Initial    | Basic provider limits                       |
| 2 — Managed    | User/application quotas                     |
| 3 — Controlled | Agent, token, tool and cost controls        |
| 4 — Measured   | Continuous monitoring and adaptive controls |
| 5 — Optimized  | Automated risk-based resource governance    |

Maturity should be assessed according to business criticality.

# 186. Enterprise Security Principle

AI resource consumption should be governed as an enterprise security boundary.

The organization should be able to answer:

* Who can consume AI resources?
* How much can they consume?
* Which models can they use?
* Which agents can execute?
* How many tools can they invoke?
* How much can the operation cost?
* What happens when limits are reached?
* Who can activate emergency controls?

---

# 187. Strategic Security Principle

> **AI resource consumption must remain bounded, attributable, risk-based, and independently enforceable so that no user, application, model, agent, or dependency can convert AI capability into uncontrolled computational, operational, or financial consumption.**
