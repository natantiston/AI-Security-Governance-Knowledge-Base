# 10.16 — Excessive Agency

## Part 1 — Foundations and Core Concepts

# 1. Definition of Excessive Agency

Excessive agency is an AI security condition in which an AI system, agent, or AI-enabled application is granted more authority, autonomy, access, or operational capability than is necessary to perform its intended business function.

The risk becomes significant when an AI system can independently:

* access sensitive information;
* execute privileged operations;
* modify enterprise data;
* communicate externally;
* execute code;
* create or delete resources;
* initiate transactions;
* invoke multiple tools;
* make consequential decisions;
* continue operating without meaningful human intervention.

The fundamental problem is not simply that the AI can perform actions.

The problem is that **the AI can perform actions with insufficiently constrained authority**.

---

# 2. Excessive Agency as an AI Security Threat

Traditional software generally performs predefined operations according to deterministic logic.

Agentic AI introduces a different security model:

```text
Traditional Application

User
  |
  v
Application
  |
  v
Predefined Function
  |
  v
Result
```

An AI agent may instead operate as:

```text
User
  |
  v
AI Agent
  |
  +--> Reason
  |
  +--> Select Tool
  |
  +--> Retrieve Data
  |
  +--> Execute Action
  |
  +--> Evaluate Result
  |
  +--> Select Another Tool
  |
  +--> Continue
```

This additional autonomy creates new security boundaries that must be explicitly governed.

---

# 3. The Fundamental Security Problem

The fundamental problem is the potential mismatch between:

**what the AI needs to do**

and

**what the AI is technically capable of doing**.

For example, an AI assistant may only need to read a customer's account balance but could potentially have permissions to:

* modify the account;
* issue refunds;
* change customer information;
* access other customers;
* send external communications;
* execute administrative APIs.

This creates unnecessary attack surface.

The security principle is:

> **An AI system should have only the minimum authority necessary to perform its approved function.**

---

# 4. Agency vs Capability

Agency refers to the ability of an AI system to independently determine and execute actions.

Capability refers to what the system is technically able to access or perform.

These are related but different.

```text
Capability
    |
    v
"What can the system do?"

Agency
    |
    v
"What can the system decide and execute
without additional human direction?"
```

An AI system can therefore have:

* low capability and low agency;
* high capability and low agency;
* low capability and high agency;
* **high capability and high agency**.

The last combination creates the greatest security concern.

---

# 5. Excessive Agency vs Normal Automation

Automation is not inherently insecure.

A traditional automated process may execute a narrowly defined workflow:

```text
IF condition = true
THEN execute predefined action
```

An AI agent may instead determine:

```text
Goal
 ↓
Interpret situation
 ↓
Select action
 ↓
Select tool
 ↓
Generate parameters
 ↓
Execute
 ↓
Interpret result
 ↓
Choose next action
```

The larger decision space increases the possibility of unintended or manipulated behavior.

---

# 6. Excessive Agency and Least Privilege

Least privilege is one of the primary security principles for controlling excessive agency.

The AI should receive only:

* required permissions;
* required data;
* required tools;
* required network access;
* required execution capability;
* required duration of access.

For example:

```text
Business Requirement:
"Prepare a customer report"

Required:
Read approved customer data
Generate report

Not Required:
Delete records
Modify accounts
Send external email
Create users
Access administrator APIs
```

Unused capabilities should not be granted merely because the AI platform supports them.

---

# 7. Excessive Agency and Privilege Creep

AI systems can experience privilege creep as new capabilities are added.

```text
Initial Deployment
      |
      v
Read Database
      |
      v
Add CRM Tool
      |
      v
Add Email
      |
      v
Add File Upload
      |
      v
Add External API
      |
      v
Add Code Execution
      |
      v
Excessive Agency
```

Each additional capability can increase the potential blast radius of compromise or misuse.

---

# 8. Excessive Agency and Prompt Injection

Prompt injection becomes significantly more dangerous when an AI agent has powerful tools.

A simple injection may attempt to manipulate the model:

```text
Malicious Instruction
        |
        v
AI Agent
        |
        v
Tool Invocation
        |
        v
Sensitive Action
```

The security concern is therefore not merely whether the model follows the malicious instruction.

The critical question is:

**What authority does the model possess after following it?**

---

# 9. Excessive Agency and Jailbreaking

A successful jailbreak can weaken model-level behavioral restrictions.

If the model has no meaningful external authority, the impact may remain limited.

If the model controls powerful tools, the same jailbreak can become an enterprise security incident.

```text
Jailbreak
   |
   v
Model Behavior Compromised
   |
   +---- Limited Permissions
   |         |
   |         v
   |      Limited Impact
   |
   +---- Excessive Permissions
             |
             v
       Major Security Impact
```

This creates a critical architectural distinction:

> **Model compromise does not have to become enterprise authorization compromise.**

---

# 10. Excessive Agency and Tool Access

Tools are a major source of agency risk.

Examples include:

* databases;
* email;
* file systems;
* cloud APIs;
* ticketing systems;
* payment systems;
* identity systems;
* network infrastructure;
* code execution;
* enterprise applications.

Every tool expands the potential action space of the AI system.

Therefore:

```text
More Tools
    +
More Permissions
    +
More Autonomy
    =
Greater Agency Risk
```

---

# 11. Excessive Agency and Autonomous Decision-Making

Agency risk increases when the AI can independently make consequential decisions.

Examples include:

* approving transactions;
* changing access rights;
* terminating accounts;
* modifying security policies;
* approving financial activity;
* prioritizing security incidents;
* changing production infrastructure.

High-impact decisions should normally have additional authorization and oversight mechanisms.

---

# 12. Excessive Agency and Sensitive Data

An AI agent with broad data access can potentially retrieve information beyond the user's legitimate business requirement.

Potentially sensitive resources include:

* customer records;
* employee information;
* financial information;
* credentials;
* security logs;
* intellectual property;
* legal documents;
* source code;
* strategic information.

Data access should therefore be governed independently from the AI's reasoning process.

---

# 13. Excessive Agency and Data Exfiltration

Excessive agency can transform an information-disclosure vulnerability into an actual data-transfer event.

```text
Sensitive Data
     |
     v
AI Agent
     |
     v
Unauthorized Tool
     |
     v
External API / Email / Storage
     |
     v
Data Exfiltration
```

This is why outbound capabilities should be independently controlled.

The AI should not be able to decide both:

1. what sensitive information to access; and
2. where that information should be sent.

---

# 14. Excessive Agency and Data Extraction

An agent with unrestricted query capabilities may perform repeated or large-scale extraction.

For example:

```text
Agent
 |
 +--> Query 1
 +--> Query 2
 +--> Query 3
 +--> Query 4
 +--> Query 5
 |
 v
Large Dataset
```

Individual queries may appear legitimate while the cumulative activity creates a significant security event.

Agency governance therefore needs to consider **cumulative behavior**, not only individual actions.

---

# 15. Excessive Agency and Privileged Operations

An AI agent should generally not possess unrestricted administrative privileges.

High-risk capabilities include:

* creating administrators;
* changing IAM policies;
* disabling security controls;
* modifying firewall rules;
* changing production configurations;
* deleting infrastructure;
* rotating credentials;
* modifying audit settings.

Privileged operations should require stronger authorization boundaries.

---

# 16. Excessive Agency and Code Execution

Code execution can significantly increase AI agency.

An agent with code execution may potentially:

* manipulate files;
* access APIs;
* process sensitive information;
* execute system commands;
* interact with networks;
* install software;
* modify resources.

Therefore, code execution should be treated as a distinct high-risk capability rather than an ordinary AI feature.

---

# 17. Excessive Agency and Network Access

Network connectivity expands the potential attack and exfiltration surface.

An AI agent with unrestricted network access may be capable of interacting with:

* internal systems;
* cloud services;
* external websites;
* APIs;
* remote storage;
* command-and-control infrastructure.

A secure architecture should therefore control:

```text
AI Agent
   |
   v
Network Policy
   |
   +--> Approved Destination
   |
   +--> Restricted Destination
   |
   +--> Blocked Destination
```

---

# 18. Excessive Agency and External Communication

AI systems capable of sending emails, messages, files, or API requests can create external impact.

Examples include:

* sending confidential reports;
* communicating with customers;
* sending internal messages;
* uploading files;
* posting to external platforms;
* submitting transactions.

External communication should generally require destination and action authorization.

---

# 19. Excessive Agency and Transaction Execution

Financial and business transactions create especially high agency risk.

Examples include:

* payments;
* refunds;
* purchases;
* transfers;
* orders;
* contract changes;
* account modifications.

A safer architecture separates:

```text
AI Decision
     |
     v
Transaction Request
     |
     v
Independent Authorization
     |
     v
Execution
```

The AI should not be the sole authority deciding whether a transaction is permitted.

---

# 20. Excessive Agency and Human Oversight

Human oversight becomes increasingly important as the consequences of autonomous actions increase.

A practical model is:

```text
Low Risk
   |
   v
Fully Automated

Medium Risk
   |
   v
Automated + Monitoring

High Risk
   |
   v
Automated + Approval

Critical Risk
   |
   v
Human Decision Required
```

Human involvement should be based on risk rather than applied identically to every AI interaction.

---

# 21. Excessive Agency and Human-in-the-Loop

Human-in-the-loop controls can provide an authorization boundary before high-impact actions.

However, simply presenting an approval screen is not sufficient.

The human reviewer should have enough information to understand:

* what action will occur;
* what data will be used;
* who requested it;
* which destination is involved;
* what impact may result.

Approval should be meaningful rather than a routine click-through process.

---

# 22. Excessive Agency and Human-on-the-Loop

For lower-risk workflows, humans may supervise AI activity rather than approve every action.

```text
AI Agent
   |
   v
Automated Actions
   |
   v
Continuous Monitoring
   |
   +--> Normal --> Continue
   |
   +--> Anomaly --> Human Intervention
```

This model can improve scalability while maintaining a mechanism for intervention.

---

# 23. Excessive Agency and Agent Chaining

Multiple agents can create compounded agency risk.

```text
Agent A
   |
   v
Agent B
   |
   v
Agent C
   |
   v
External Tool
   |
   v
Enterprise Resource
```

The security problem becomes more complex because authority may propagate across multiple components.

Each agent-to-agent interaction should therefore have defined trust and authorization boundaries.

---

# 24. Excessive Agency and Multi-Agent Systems

In multi-agent architectures, one compromised or manipulated agent may attempt to influence another.

Potential risks include:

* privilege propagation;
* unauthorized delegation;
* malicious task instructions;
* data transfer between agents;
* tool escalation;
* circular execution;
* uncontrolled task delegation.

Agent identity and permissions should remain independently enforceable.

---

# 25. Excessive Agency and Delegation

Delegation creates an important security question:

> Can an AI agent delegate authority that it does not itself possess?

The answer should generally be **no**.

A delegated agent should not receive broader authority than the originating authorization permits.

```text
User Authority
      |
      v
Agent A
      |
      v
Delegation
      |
      v
Agent B
      |
      v
Must Remain Within
Original Authorization
```

---

# 26. Excessive Agency and Privilege Escalation

An AI agent may become an avenue for privilege escalation if it can:

* request elevated permissions;
* modify IAM settings;
* invoke privileged APIs;
* obtain credentials;
* create service accounts;
* alter authorization policies.

Privilege elevation should therefore require an independent security decision.

---

# 27. Excessive Agency and Credential Access

Credentials should not be broadly exposed to AI agents.

High-risk credentials include:

* administrator credentials;
* database credentials;
* cloud keys;
* API secrets;
* service-account tokens;
* privileged certificates.

Where possible, agents should use short-lived, narrowly scoped credentials rather than persistent privileged secrets.

---

# 28. Excessive Agency and Secrets

An AI system should not become a general-purpose secrets repository.

Secrets should be:

* centrally managed;
* scoped;
* short-lived where possible;
* inaccessible unless required;
* excluded from unnecessary model context;
* protected from output disclosure.

The agent should receive the minimum authorization required for the specific operation.

---

# 29. Excessive Agency and Context

The amount of context available to an agent can affect its effective authority.

Broad context may expose:

* internal policies;
* customer information;
* credentials;
* operational information;
* other users' conversations;
* security architecture.

Context should therefore be treated as part of the authorization boundary.

---

# 30. Excessive Agency and Memory

Persistent AI memory can increase agency over time.

```text
Interaction 1
     |
     v
Memory
     |
Interaction 2
     |
     v
Memory
     |
Interaction 3
     |
     v
Expanded Context
```

Without appropriate controls, an agent may gradually accumulate information beyond its intended operational scope.

Memory requires:

* access control;
* retention rules;
* isolation;
* classification;
* deletion;
* purpose limitation.

---

# 31. Excessive Agency and RAG

RAG can increase agency by giving an agent access to enterprise knowledge.

The presence of a document in a knowledge repository should not automatically authorize the agent to retrieve or use it.

The architecture should preserve:

```text
User Identity
      +
Business Purpose
      +
Document Authorization
      |
      v
Permitted Context
```

---

# 32. Excessive Agency and Model Autonomy

Autonomy exists on a spectrum.

```text
Level 1
Model Only
  |
Level 2
Model Suggests Action
  |
Level 3
Model Requests Tool
  |
Level 4
Model Executes Approved Tool
  |
Level 5
Model Selects and Executes Multiple Actions
  |
Level 6
Model Operates Continuously
```

Higher autonomy generally requires stronger controls.

---

# 33. Excessive Agency and Continuous Operation

Persistent agents introduce additional risks because they can continue acting without a new user request.

Potential risks include:

* repeated execution;
* unintended loops;
* changing environmental conditions;
* accumulating privileges;
* persistent access;
* continuous data retrieval;
* repeated external communication.

Time limits and execution boundaries become important security controls.

---

# 34. Excessive Agency and Action Loops

An agent may repeatedly invoke tools based on its own previous results.

```text
Goal
 |
 v
Action
 |
 v
Result
 |
 v
AI Reasoning
 |
 v
Next Action
 |
 +------------------+
                    |
                    v
                  Loop
```

Without limits, this can produce:

* excessive resource consumption;
* repeated transactions;
* data extraction;
* repeated external communication;
* operational disruption.

---

# 35. Excessive Agency and Unintended Actions

AI systems may perform actions that are technically consistent with a goal but inconsistent with business expectations.

For example:

```text
Goal:
"Clean up old accounts"

Potential AI interpretation:
Delete accounts
Disable users
Remove data
Cancel subscriptions
```

The system must therefore distinguish between **goal interpretation** and **authorized action**.

---

# 36. Excessive Agency and Ambiguous Instructions

Natural-language objectives may be ambiguous.

Statements such as:

* "fix the issue";
* "clean up the data";
* "handle the customer";
* "resolve the incident";
* "optimize the environment"

do not necessarily define what actions are authorized.

High-impact actions should use explicit action constraints and authorization boundaries.

---

# 37. Excessive Agency and Goal Misalignment

The AI may optimize for an objective in ways that produce undesirable outcomes.

This can occur when:

* objectives are incomplete;
* constraints are unclear;
* success metrics are poorly defined;
* business rules are absent;
* the model interprets goals differently from humans.

Security governance should therefore define both:

**what the agent should accomplish**

and

**what the agent must never do**.

---

# 38. Excessive Agency and Instruction Hierarchy

System instructions can attempt to limit agent behavior.

However:

> **Prompt instructions are not equivalent to authorization controls.**

A system prompt saying:

```text
"Never delete customer records."
```

is not sufficient if the agent possesses an unrestricted deletion API.

The stronger architecture is:

```text
Prompt Restriction
      +
Tool Authorization
      +
API Authorization
      +
Transaction Control
```

---

# 39. Excessive Agency and Zero Trust

Zero Trust principles are particularly relevant to agentic AI.

The system should not assume that:

* the model is trustworthy;
* the prompt is trustworthy;
* the agent's reasoning is trustworthy;
* the previous action was legitimate;
* the tool request is legitimate.

Every sensitive action should be independently evaluated.

---

# 40. Excessive Agency and Defense in Depth

Agency risk should be controlled through multiple independent layers.

```text
                AI Agent
                   |
          +--------+--------+
          |        |        |
       Identity  Policy   Context
          |        |        |
          +--------+--------+
                   |
              Tool Control
                   |
            Action Validation
                   |
            Human Approval
                   |
             Egress Control
                   |
              Monitoring
```

The objective is to prevent a single compromised model behavior from becoming an unrestricted enterprise action.

---

The agency attack surface includes:

* system prompts;

* tools;

* databases;
* credentials;
* network access;
* file systems;
* memory;
* RAG;
* agent-to-agent communication;
* external integrations;
* autonomous workflows;
* scheduling;

Every capability should have a defined owner and security boundary.

---

# 42. Excessive Agency Attack Lifecycle

A typical excessive-agency attack may follow:

```text
Reconnaissance
      |
      v
Identify AI Capabilities
      |
      v
Identify Available Tools
      |
      v
Manipulate AI
      |
      v
Trigger Unauthorized Action
      |
      v

      |

```

The attack does not necessarily require compromising the underlying infrastructure.

Manipulating the AI's decision process may be sufficient if the surrounding authorization model is weak.

---

# 43. Excessive Agency Risk Factors

Risk increases when an AI system has:

* broad permissions;
* sensitive data access;
* unrestricted tools;
* external connectivity;
* privileged credentials;
* persistent memory;
* autonomous execution;
* long-running sessions;
* weak authorization;
* weak monitoring;
* limited human oversight.

The combination of multiple factors is particularly dangerous.

---

# 44. Excessive Agency and High-Impact AI

High-impact AI systems require stronger agency controls.

Examples may include AI used for:

* financial decisions;
* healthcare operations;
* critical infrastructure;
* identity management;
* cybersecurity;
* employment decisions;
* legal processes;
* customer account management;
* production infrastructure.

The greater the potential consequence, the stronger the authorization boundary should be.

---

# 45. Excessive Agency and Confidentiality

Excessive agency can compromise confidentiality when an AI agent has broad access and communication capabilities.

```text
Broad Data Access
       +
External Communication
       +
Autonomous Execution
       |
       v
Confidentiality Risk
```

Controls should prevent the agent from independently combining these capabilities in unauthorized ways.

---

# 46. Excessive Agency and Integrity

Agency can create integrity risks when an AI system can modify enterprise information.

Examples include:

* changing records;
* modifying configurations;
* changing security policies;
* altering customer information;
* deleting data;
* changing financial values.

Integrity controls should independently validate sensitive modifications.

---

# 47. Excessive Agency and Availability

Autonomous AI can also create availability risks.

Examples include:

* repeated API calls;
* excessive resource consumption;
* uncontrolled workflows;
* infrastructure modifications;
* service restarts;
* mass deletion;
* automated transaction loops.

Execution limits and emergency controls are therefore important.

---

# 48. Excessive Agency and Accountability

Every consequential AI action should be attributable.

The enterprise should be able to determine:

* which user initiated the activity;
* which agent executed it;
* which model was used;
* which tools were invoked;
* which permissions were applied;
* what data was accessed;
* what action occurred;
* when it occurred.

An action that cannot be attributed cannot be reliably governed.

---

# 49. Excessive Agency and Non-Repudiation

For high-impact actions, security records should provide reliable evidence of what occurred.

Relevant information may include:

```text

Agent Identity
     +
Model Version
     +
Tool
     +
Action
     +
Parameters
     +
Authorization Decision
     +
Timestamp
```

This supports investigation, accountability, and auditability.

---

# 50. Excessive Agency and Security Boundaries

```text
 v

 v
```

# 51. Excessive Agency and Blast Radius

Blast radius describes the potential impact if an AI agent is compromised or manipulated.

A high-agency system may have:

```text
One Compromised Agent
        |
        +--> Multiple Databases
        +--> Multiple APIs
        +--> Multiple Tools
        +--> External Network
        +--> Privileged Systems
```

A secure architecture reduces this blast radius through:

* least privilege;
* segmentation;
* scoped identities;
* tool isolation;
* transaction limits;
* egress controls.

---

# 52. Excessive Agency and Fail-Safe Design

AI agents should fail safely when authorization or security decisions cannot be established.

Examples:

```text
Authorization Unavailable
        |
        v
DENY

Destination Unknown
        |
        v
DENY

Policy Evaluation Failed
        |
        v
DENY / HUMAN REVIEW
```

Fail-safe behavior prevents technical failures from becoming authorization bypasses.

---

# 53. Excessive Agency and Fail-Open Behavior

Fail-open behavior can create significant agency risk.

For example:

```text
Policy Engine Unavailable
        |
        v
"Allow Action"
```

This can allow an AI agent to continue operating without effective authorization.

Security-critical agent operations should generally fail closed unless an explicitly approved risk model requires otherwise.

---

# 54. Excessive Agency and Emergency Controls

High-risk AI systems should have mechanisms for rapid containment.

Possible controls include:

* agent kill switch;
* tool disablement;
* credential revocation;
* network isolation;
* session termination;
* API blocking;
* workflow suspension.

These controls should operate independently of the AI model.

---

# 55. Excessive Agency and Governance

Excessive agency is both a technical and governance problem.

Governance should establish:

* permitted autonomy;
* prohibited actions;
* approved tools;
* authorization requirements;
* human approval requirements;
* data-access boundaries;
* external communication rules;
* monitoring;
* testing;
* incident response.

The enterprise should know **what every AI agent is authorized to do before it is deployed**.

---

# 59. Excessive Agency Security Objectives

The primary security objectives are to:

1. minimize AI privileges;
2. constrain autonomous actions;
3. separate reasoning from authorization;
4. isolate sensitive tools;
5. limit data access;

# 60. Defense-in-Depth Principle

No single mechanism should be trusted to control excessive agency.

The security architecture should combine:

```text
Least Privilege
      +

      +

      +

      +

      +
```

---

# 61. Model Behavior Is Not Authorization

A foundational principle for agentic AI security is:

> **The model should recommend or request an action; an independent security mechanism should determine whether that action is authorized.**

The architecture should therefore distinguish:

```text
Model:
"What should I do?"

Policy Engine:
"Are you allowed to do it?"

Tool:
"Execute the authorized action."
```

This separation prevents model manipulation from directly becoming privilege escalation.

---

# 62. Security Boundary Principle

The AI model, agent, or orchestration layer should never be considered a trusted authorization boundary merely because it is operating within an enterprise environment.

Trust should be established through:

* identity;
* policy;
* authorization;
* capability restriction;
* data controls;
* network controls;
* monitoring.

Enterprise security boundaries must remain enforceable even when the AI behaves incorrectly or is deliberately manipulated.

---

# 63. Fundamental Security Principle

> **Give AI systems the minimum authority required to accomplish their approved purpose, and enforce every consequential action through independent authorization controls.**

An AI agent should not be trusted simply because it is aligned, instructed, internally deployed, or operating on behalf of an authorized user.

Its effective authority should remain:

```text
User Authority
        ∩
Business Purpose
        ∩
Data Authorization
        ∩
Tool Authorization
        ∩
Action Policy
        ∩
Risk Constraints
```

The resulting permission set should define what the AI is actually allowed to do—not what the model believes it is allowed to do.
