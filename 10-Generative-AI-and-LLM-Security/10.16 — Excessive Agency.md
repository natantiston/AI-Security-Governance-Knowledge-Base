# 10.16 — Excessive Agency

## Part 1 — Foundations and Core Concepts

# 1. Definition of Excessive Agency

Excessive agency is an AI security condition in which an AI system, agent, or AI-enabled application is granted more authority, autonomy, access, or operational capability than is necessary to perform its intended business function.

The risk becomes significant when an AI system can independently:

* access sensitive information;
* execute privileged operations;
* modify enterprise data;
* communicate externally;
* execute code;
* create or delete resources;
* initiate transactions;
* invoke multiple tools;
* make consequential decisions;
* continue operating without meaningful human intervention.

The fundamental problem is not simply that the AI can perform actions.

The problem is that **the AI can perform actions with insufficiently constrained authority**.

---

# 2. Excessive Agency as an AI Security Threat

Traditional software generally performs predefined operations according to deterministic logic.

Agentic AI introduces a different security model:

```text
Traditional Application

User
  |
  v
Application
  |
  v
Predefined Function
  |
  v
Result
```

An AI agent may instead operate as:

```text
User
  |
  v
AI Agent
  |
  +--> Reason
  |
  +--> Select Tool
  |
  +--> Retrieve Data
  |
  +--> Execute Action
  |
  +--> Evaluate Result
  |
  +--> Select Another Tool
  |
  +--> Continue
```

This additional autonomy creates new security boundaries that must be explicitly governed.

---

# 3. The Fundamental Security Problem

The fundamental problem is the potential mismatch between:

**what the AI needs to do**

and

**what the AI is technically capable of doing**.

For example, an AI assistant may only need to read a customer's account balance but could potentially have permissions to:

* modify the account;
* issue refunds;
* change customer information;
* access other customers;
* send external communications;
* execute administrative APIs.

This creates unnecessary attack surface.

The security principle is:

> **An AI system should have only the minimum authority necessary to perform its approved function.**

---

# 4. Agency vs Capability

Agency refers to the ability of an AI system to independently determine and execute actions.

Capability refers to what the system is technically able to access or perform.

These are related but different.

```text
Capability
    |
    v
"What can the system do?"

Agency
    |
    v
"What can the system decide and execute
without additional human direction?"
```

An AI system can therefore have:

* low capability and low agency;
* high capability and low agency;
* low capability and high agency;
* **high capability and high agency**.

The last combination creates the greatest security concern.

---

# 5. Excessive Agency vs Normal Automation

Automation is not inherently insecure.

A traditional automated process may execute a narrowly defined workflow:

```text
IF condition = true
THEN execute predefined action
```

An AI agent may instead determine:

```text
Goal
 ↓
Interpret situation
 ↓
Select action
 ↓
Select tool
 ↓
Generate parameters
 ↓
Execute
 ↓
Interpret result
 ↓
Choose next action
```

The larger decision space increases the possibility of unintended or manipulated behavior.

---

# 6. Excessive Agency and Least Privilege

Least privilege is one of the primary security principles for controlling excessive agency.

The AI should receive only:

* required permissions;
* required data;
* required tools;
* required network access;
* required execution capability;
* required duration of access.

For example:

```text
Business Requirement:
"Prepare a customer report"

Required:
Read approved customer data
Generate report

Not Required:
Delete records
Modify accounts
Send external email
Create users
Access administrator APIs
```

Unused capabilities should not be granted merely because the AI platform supports them.

---

# 7. Excessive Agency and Privilege Creep

AI systems can experience privilege creep as new capabilities are added.

```text
Initial Deployment
      |
      v
Read Database
      |
      v
Add CRM Tool
      |
      v
Add Email
      |
      v
Add File Upload
      |
      v
Add External API
      |
      v
Add Code Execution
      |
      v
Excessive Agency
```

Each additional capability can increase the potential blast radius of compromise or misuse.

---

# 8. Excessive Agency and Prompt Injection

Prompt injection becomes significantly more dangerous when an AI agent has powerful tools.

A simple injection may attempt to manipulate the model:

```text
Malicious Instruction
        |
        v
AI Agent
        |
        v
Tool Invocation
        |
        v
Sensitive Action
```

The security concern is therefore not merely whether the model follows the malicious instruction.

The critical question is:

**What authority does the model possess after following it?**

---

# 9. Excessive Agency and Jailbreaking

A successful jailbreak can weaken model-level behavioral restrictions.

If the model has no meaningful external authority, the impact may remain limited.

If the model controls powerful tools, the same jailbreak can become an enterprise security incident.

```text
Jailbreak
   |
   v
Model Behavior Compromised
   |
   +---- Limited Permissions
   |         |
   |         v
   |      Limited Impact
   |
   +---- Excessive Permissions
             |
             v
       Major Security Impact
```

This creates a critical architectural distinction:

> **Model compromise does not have to become enterprise authorization compromise.**

---

# 10. Excessive Agency and Tool Access

Tools are a major source of agency risk.

Examples include:

* databases;
* email;
* file systems;
* cloud APIs;
* ticketing systems;
* payment systems;
* identity systems;
* network infrastructure;
* code execution;
* enterprise applications.

Every tool expands the potential action space of the AI system.

Therefore:

```text
More Tools
    +
More Permissions
    +
More Autonomy
    =
Greater Agency Risk
```

---

# 11. Excessive Agency and Autonomous Decision-Making

Agency risk increases when the AI can independently make consequential decisions.

Examples include:

* approving transactions;
* changing access rights;
* terminating accounts;
* modifying security policies;
* approving financial activity;
* prioritizing security incidents;
* changing production infrastructure.

High-impact decisions should normally have additional authorization and oversight mechanisms.

---

# 12. Excessive Agency and Sensitive Data

An AI agent with broad data access can potentially retrieve information beyond the user's legitimate business requirement.

Potentially sensitive resources include:

* customer records;
* employee information;
* financial information;
* credentials;
* security logs;
* intellectual property;
* legal documents;
* source code;
* strategic information.

Data access should therefore be governed independently from the AI's reasoning process.

---

# 13. Excessive Agency and Data Exfiltration

Excessive agency can transform an information-disclosure vulnerability into an actual data-transfer event.

```text
Sensitive Data
     |
     v
AI Agent
     |
     v
Unauthorized Tool
     |
     v
External API / Email / Storage
     |
     v
Data Exfiltration
```

This is why outbound capabilities should be independently controlled.

The AI should not be able to decide both:

1. what sensitive information to access; and
2. where that information should be sent.

---

# 14. Excessive Agency and Data Extraction

An agent with unrestricted query capabilities may perform repeated or large-scale extraction.

For example:

```text
Agent
 |
 +--> Query 1
 +--> Query 2
 +--> Query 3
 +--> Query 4
 +--> Query 5
 |
 v
Large Dataset
```

Individual queries may appear legitimate while the cumulative activity creates a significant security event.

Agency governance therefore needs to consider **cumulative behavior**, not only individual actions.

---

# 15. Excessive Agency and Privileged Operations

An AI agent should generally not possess unrestricted administrative privileges.

High-risk capabilities include:

* creating administrators;
* changing IAM policies;
* disabling security controls;
* modifying firewall rules;
* changing production configurations;
* deleting infrastructure;
* rotating credentials;
* modifying audit settings.

Privileged operations should require stronger authorization boundaries.

---

# 16. Excessive Agency and Code Execution

Code execution can significantly increase AI agency.

An agent with code execution may potentially:

* manipulate files;
* access APIs;
* process sensitive information;
* execute system commands;
* interact with networks;
* install software;
* modify resources.

Therefore, code execution should be treated as a distinct high-risk capability rather than an ordinary AI feature.

---

# 17. Excessive Agency and Network Access

Network connectivity expands the potential attack and exfiltration surface.

An AI agent with unrestricted network access may be capable of interacting with:

* internal systems;
* cloud services;
* external websites;
* APIs;
* remote storage;
* command-and-control infrastructure.

A secure architecture should therefore control:

```text
AI Agent
   |
   v
Network Policy
   |
   +--> Approved Destination
   |
   +--> Restricted Destination
   |
   +--> Blocked Destination
```

---

# 18. Excessive Agency and External Communication

AI systems capable of sending emails, messages, files, or API requests can create external impact.

Examples include:

* sending confidential reports;
* communicating with customers;
* sending internal messages;
* uploading files;
* posting to external platforms;
* submitting transactions.

External communication should generally require destination and action authorization.

---

# 19. Excessive Agency and Transaction Execution

Financial and business transactions create especially high agency risk.

Examples include:

* payments;
* refunds;
* purchases;
* transfers;
* orders;
* contract changes;
* account modifications.

A safer architecture separates:

```text
AI Decision
     |
     v
Transaction Request
     |
     v
Independent Authorization
     |
     v
Execution
```

The AI should not be the sole authority deciding whether a transaction is permitted.

---

# 20. Excessive Agency and Human Oversight

Human oversight becomes increasingly important as the consequences of autonomous actions increase.

A practical model is:

```text
Low Risk
   |
   v
Fully Automated

Medium Risk
   |
   v
Automated + Monitoring

High Risk
   |
   v
Automated + Approval

Critical Risk
   |
   v
Human Decision Required
```

Human involvement should be based on risk rather than applied identically to every AI interaction.

---

# 21. Excessive Agency and Human-in-the-Loop

Human-in-the-loop controls can provide an authorization boundary before high-impact actions.

However, simply presenting an approval screen is not sufficient.

The human reviewer should have enough information to understand:

* what action will occur;
* what data will be used;
* who requested it;
* which destination is involved;
* what impact may result.

Approval should be meaningful rather than a routine click-through process.

---

# 22. Excessive Agency and Human-on-the-Loop

For lower-risk workflows, humans may supervise AI activity rather than approve every action.

```text
AI Agent
   |
   v
Automated Actions
   |
   v
Continuous Monitoring
   |
   +--> Normal --> Continue
   |
   +--> Anomaly --> Human Intervention
```

This model can improve scalability while maintaining a mechanism for intervention.

---

# 23. Excessive Agency and Agent Chaining

Multiple agents can create compounded agency risk.

```text
Agent A
   |
   v
Agent B
   |
   v
Agent C
   |
   v
External Tool
   |
   v
Enterprise Resource
```

The security problem becomes more complex because authority may propagate across multiple components.

Each agent-to-agent interaction should therefore have defined trust and authorization boundaries.

---

# 24. Excessive Agency and Multi-Agent Systems

In multi-agent architectures, one compromised or manipulated agent may attempt to influence another.

Potential risks include:

* privilege propagation;
* unauthorized delegation;
* malicious task instructions;
* data transfer between agents;
* tool escalation;
* circular execution;
* uncontrolled task delegation.

Agent identity and permissions should remain independently enforceable.

---

# 25. Excessive Agency and Delegation

Delegation creates an important security question:

> Can an AI agent delegate authority that it does not itself possess?

The answer should generally be **no**.

A delegated agent should not receive broader authority than the originating authorization permits.

```text
User Authority
      |
      v
Agent A
      |
      v
Delegation
      |
      v
Agent B
      |
      v
Must Remain Within
Original Authorization
```

---

# 26. Excessive Agency and Privilege Escalation

An AI agent may become an avenue for privilege escalation if it can:

* request elevated permissions;
* modify IAM settings;
* invoke privileged APIs;
* obtain credentials;
* create service accounts;
* alter authorization policies.

Privilege elevation should therefore require an independent security decision.

---

# 27. Excessive Agency and Credential Access

Credentials should not be broadly exposed to AI agents.

High-risk credentials include:

* administrator credentials;
* database credentials;
* cloud keys;
* API secrets;
* service-account tokens;
* privileged certificates.

Where possible, agents should use short-lived, narrowly scoped credentials rather than persistent privileged secrets.

---

# 28. Excessive Agency and Secrets

An AI system should not become a general-purpose secrets repository.

Secrets should be:

* centrally managed;
* scoped;
* short-lived where possible;
* inaccessible unless required;
* excluded from unnecessary model context;
* protected from output disclosure.

The agent should receive the minimum authorization required for the specific operation.

---

# 29. Excessive Agency and Context

The amount of context available to an agent can affect its effective authority.

Broad context may expose:

* internal policies;
* customer information;
* credentials;
* operational information;
* other users' conversations;
* security architecture.

Context should therefore be treated as part of the authorization boundary.

---

# 30. Excessive Agency and Memory

Persistent AI memory can increase agency over time.

```text
Interaction 1
     |
     v
Memory
     |
Interaction 2
     |
     v
Memory
     |
Interaction 3
     |
     v
Expanded Context
```

Without appropriate controls, an agent may gradually accumulate information beyond its intended operational scope.

Memory requires:

* access control;
* retention rules;
* isolation;
* classification;
* deletion;
* purpose limitation.

---

# 31. Excessive Agency and RAG

RAG can increase agency by giving an agent access to enterprise knowledge.

The presence of a document in a knowledge repository should not automatically authorize the agent to retrieve or use it.

The architecture should preserve:

```text
User Identity
      +
Business Purpose
      +
Document Authorization
      |
      v
Permitted Context
```

---

# 32. Excessive Agency and Model Autonomy

Autonomy exists on a spectrum.

```text
  |
```

---

# 33. Excessive Agency and Continuous Operation

Persistent agents introduce additional risks because they can continue acting without a new user request.

Potential risks include:

* repeated execution;
* unintended loops;
* changing environmental conditions;
* accumulating privileges;
* persistent access;
* continuous data retrieval;
* repeated external communication.

Time limits and execution boundaries become important security controls.

---

# 34. Excessive Agency and Action Loops

An agent may repeatedly invoke tools based on its own previous results.

```text
Goal
 |
 v
Action
 |
 v
Result
 |
 v
AI Reasoning
 |
 v
Next Action
 |
 +------------------+
                    |
                    v
                  Loop
```

Without limits, this can produce:

* excessive resource consumption;
* repeated transactions;
* data extraction;
* repeated external communication;
* operational disruption.

---

# 35. Excessive Agency and Unintended Actions

AI systems may perform actions that are technically consistent with a goal but inconsistent with business expectations.

For example:

```text
Goal:
"Clean up old accounts"

Potential AI interpretation:
Delete accounts
Disable users
Remove data
Cancel subscriptions
```

The system must therefore distinguish between **goal interpretation** and **authorized action**.

---

# 36. Excessive Agency and Ambiguous Instructions

Natural-language objectives may be ambiguous.

Statements such as:

* "fix the issue";
* "clean up the data";
* "handle the customer";
* "resolve the incident";
* "optimize the environment"

do not necessarily define what actions are authorized.

High-impact actions should use explicit action constraints and authorization boundaries.

---

# 37. Excessive Agency and Goal Misalignment

The AI may optimize for an objective in ways that produce undesirable outcomes.

This can occur when:

* objectives are incomplete;
* constraints are unclear;
* success metrics are poorly defined;
* business rules are absent;
* the model interprets goals differently from humans.

Security governance should therefore define both:

**what the agent should accomplish**

and

**what the agent must never do**.

---

# 38. Excessive Agency and Instruction Hierarchy

System instructions can attempt to limit agent behavior.

However:

> **Prompt instructions are not equivalent to authorization controls.**

A system prompt saying:

```text
"Never delete customer records."
```

is not sufficient if the agent possesses an unrestricted deletion API.

The stronger architecture is:

```text
Prompt Restriction
      +
Tool Authorization
      +
API Authorization
      +
Transaction Control
```

---

# 39. Excessive Agency and Zero Trust

Zero Trust principles are particularly relevant to agentic AI.

The system should not assume that:

* the model is trustworthy;
* the prompt is trustworthy;
* the agent's reasoning is trustworthy;
* the previous action was legitimate;
* the tool request is legitimate.

Every sensitive action should be independently evaluated.

---

# 40. Excessive Agency and Defense in Depth

Agency risk should be controlled through multiple independent layers.

The objective is to prevent a single compromised model behavior from becoming an unrestricted enterprise action.

# 47. Excessive Agency and Availability

# 48. Excessive Agency and Accountability

Every consequential AI action should be attributable.

The enterprise should be able to determine:

* which user initiated the activity;
* which agent executed it;
* which model was used;
* which tools were invoked;
* which permissions were applied;
* what data was accessed;
* what action occurred;
* when it occurred.

An action that cannot be attributed cannot be reliably governed.

# 52. Excessive Agency and Fail-Safe Design

AI agents should fail safely when authorization or security decisions cannot be established.

# 53. Excessive Agency and Fail-Open Behavior

Security-critical agent operations should generally fail closed unless an explicitly approved risk model requires otherwise.

# 61. Model Behavior Is Not Authorization

A foundational principle for agentic AI security is:

> **The model should recommend or request an action; an independent security mechanism should determine whether that action is authorized.**

The architecture should therefore distinguish:

```text
Model:
"What should I do?"

Policy Engine:
"Are you allowed to do it?"

Tool:
"Execute the authorized action."
```

This separation prevents model manipulation from directly becoming privilege escalation.

---

# 62. Security Boundary Principle

The AI model, agent, or orchestration layer should never be considered a trusted authorization boundary merely because it is operating within an enterprise environment.

Trust should be established through:

* identity;
* policy;
* authorization;
* capability restriction;
* data controls;
* network controls;
* monitoring.

Enterprise security boundaries must remain enforceable even when the AI behaves incorrectly or is deliberately manipulated.

---

# 63. Fundamental Security Principle

> **Give AI systems the minimum authority required to accomplish their approved purpose, and enforce every consequential action through independent authorization controls.**

An AI agent should not be trusted simply because it is aligned, instructed, internally deployed, or operating on behalf of an authorized user.

Its effective authority should remain:

```text
User Authority
        ∩
Business Purpose
        ∩
Data Authorization
        ∩
Tool Authorization
        ∩
Action Policy
        ∩
Risk Constraints
```

The resulting permission set should define what the AI is actually allowed to do—not what the model believes it is allowed to do.

* identity;

* authorization;
* action execution;
* network connectivity;
* monitoring.

A secure architecture should follow:

```text id="e2n4qa"
User
 |
 v
AI Application
 |
 v
AI Model / Agent
 |
 | Action Request
 v

 +---- DENY
```

# 65. Identity-Based Agent Access

Every agent should have a distinct, attributable identity.

Agent identity should support:

* authentication;
* authorization;
* accountability;
* credential management;
* auditability;
* lifecycle management.

The system should be able to distinguish:

```text id="v4w7qk"
Human User
    |
    v
Application
    |
    v
AI Agent Identity
    |
    v
Tool Identity
```

Shared administrator credentials should not be used by AI agents.

---

# 66. Least-Privilege Agent Permissions

Agent permissions should be limited to the minimum required for the approved use case.

For example:

```text id="5b7c2p"
Customer Support Agent

ALLOW:
Read assigned customer tickets
Read approved customer profile

DENY:
Delete customer
Change billing
Create administrator
Access unrelated customers
Send unrestricted external email
```

Permissions should be scoped by resource and operation whenever possible.

---

# 67. Fine-Grained Authorization

Authorization should distinguish between:

* read;
* create;
* update;
* delete;
* execute;
* approve;
* export;
* transmit.

An agent authorized to read information should not automatically receive permission to modify or export it.

```text id="9m2h5d"
Read
  ≠
Modify
  ≠
Delete
  ≠
Export
  ≠
Execute
```

---

# 68. Independent Action Authorization

The AI should not be the final authority for its own actions.

A stronger architecture is:

```text id="u1b6pq"
AI Decision
    |
    v
Action Request
    |
    v
Independent Policy Engine
    |
    +--> ALLOW
    +--> DENY
    +--> REQUIRE APPROVAL
```

Authorization should evaluate the requested operation independently of the model's reasoning.

---

# 69. Tool Allowlisting

Only explicitly approved tools should be available to an AI agent.

Example:

```text id="0n7g2k"
Approved Tools
 ├── CRM Read
 ├── Ticket Update
 └── Knowledge Search

Restricted
 ├── Shell
 ├── Admin API
 ├── Payment API
 └── External Upload
```

Allowlisting reduces the number of actions available if the agent is manipulated.

---

# 70. Tool Capability Segmentation

Tools should be segmented according to risk.

| Capability                    | Security Tier |
| ----------------------------- | ------------- |
| Read public information       | Low           |
| Read internal information     | Medium        |
| Modify business data          | High          |
| External communication        | High          |
| Financial transaction         | Critical      |
| Identity administration       | Critical      |
| Infrastructure administration | Critical      |
| Unrestricted code execution   | Critical      |

Higher-risk tools should require stronger authorization.

---

# 71. Tool Argument Validation

Tool access alone is insufficient.

The arguments supplied by the AI should also be validated.

```text id="t4x1r8"
AI
 |
 v
Tool Request
 |
 +--> Tool Allowed?
 |
 +--> User Authorized?
 |
 +--> Resource Authorized?
 |
 +--> Parameters Valid?
 |
 +--> Risk Acceptable?
 |
 v
Execution
```

This prevents an authorized tool from being abused through malicious parameters.

---

# 72. Action Allowlisting

For sensitive operations, allowed actions should be explicitly defined.

For example:

```text id="v2a8hs"
Agent:
Customer Support

Allowed:
- create support ticket
- update ticket status
- retrieve customer order

Not Allowed:
- delete customer
- issue unrestricted refund
- change account ownership
- export customer database
```

Action allowlisting provides a narrower boundary than general tool access.

---

# 73. Transaction Limits

AI systems should have limits on the number, size, or value of actions they can execute.

Examples include:

* maximum transaction value;
* maximum records modified;
* maximum API calls;
* maximum files processed;
* maximum emails sent;
* maximum execution duration.

```text id="3z6w5k"
Action
  |
  v
Threshold Check
  |
  +--> Within Limit --> Continue
  |
  +--> Exceeds Limit --> Review / Deny
```

---

# 74. Cumulative Action Controls

Limits should account for multiple actions within a session or workflow.

An agent might otherwise bypass individual limits:

```text id="2f0d9q"
Action 1 = 10 records
Action 2 = 10 records
Action 3 = 10 records
...
Action 20 = 10 records

Total = 200 records
```

Cumulative thresholds help prevent this form of privilege abuse.

---

# 75. Execution Time Limits

Long-running autonomous agents should have explicit execution boundaries.

Controls can include:

* maximum runtime;
* maximum number of iterations;
* maximum tool calls;
* inactivity timeout;
* workflow expiration.

This reduces the possibility of uncontrolled autonomous behavior.

---

# 76. Agent Loop Protection

Agents should be protected against uncontrolled reasoning and action loops.

```text id="7s4z8x"
Agent
 |
 v
Tool
 |
 v
Result
 |
 v
Agent
 |
 v
Tool
 |
 v
Result
 |
 +------> Loop Detection
```

Security controls should detect:

* repeated identical actions;
* excessive retries;
* circular workflows;
* repeated API calls;
* abnormal execution duration.

---

# 77. Network Segmentation

Agent network access should be restricted according to business requirements.

```text id="q4p7yd"
AI Agent
   |
   v
Network Policy
   |
   +--> Approved Internal API
   |
   +--> Approved External API
   |
   X--> Internal Admin Network
   |
   X--> Unrestricted Internet
```

Network segmentation limits the consequences of compromised agent behavior.

---

# 78. Egress Controls

Outbound communication should be independently controlled.

Potential controls include:

* destination allowlisting;
* DNS filtering;
* HTTP proxy;
* API gateway;
* firewall policy;
* DLP inspection;
* transfer limits.

The AI should not be able to establish arbitrary outbound communication simply because network connectivity exists.

---

# 79. Credential Isolation

Agent credentials should be isolated by:

* agent;
* application;
* environment;
* tenant;
* capability.

A compromise of one agent should not expose credentials belonging to unrelated systems.

```text id="q8z2d0"
Agent A
  |
  +--> Credential A

Agent B
  |
  +--> Credential B

No Shared Privileged Credential
```

---

# 80. Short-Lived Credentials

Where practical, agents should use short-lived credentials.

Advantages include:

* reduced exposure window;
* easier revocation;
* reduced credential persistence;
* improved attribution.

Static, highly privileged credentials create unnecessary agency risk.

---

# 81. Secrets Management

Secrets should remain outside normal model context.

Secure systems should use controlled mechanisms to provide an agent with access required for a specific operation without exposing the underlying secret unnecessarily.

```text id="8f6r2s"
Agent
 |
 | Request Operation
 v
Secrets / Credential Service
 |
 | Scoped Credential
 v
Approved Tool
```

The model should not become a repository of API keys or passwords.

---

# 82. Data Access Controls

Agent data access should be independently authorized.

Controls should include:

* identity-based access;
* role-based access;
* attribute-based access;
* record-level controls;
* field-level controls;
* tenant isolation.

The agent should receive only information required for the authorized operation.

---

# 83. Context Minimization

The model context should contain only information required for the task.

For example:

```text id="q8r0sm"
Database
   |
   v
Authorization
   |
   v
Filtering
   |
   v
Required Fields Only
   |
   v
AI Context
```

This limits the information available if the agent is manipulated.

---

# 84. Context Isolation

Contexts should be isolated across:

* users;
* tenants;
* applications;
* workflows;
* sessions.

One agent session should not automatically inherit another session's sensitive context.

---

# 85. Memory Access Controls

Persistent memory should be subject to authorization controls.

The system should determine:

* who can create memory;
* what can be stored;
* who can retrieve it;
* how long it remains;
* whether it can be transferred across sessions.

Memory should not become an uncontrolled privilege-expansion mechanism.

---

# 86. RAG Authorization

RAG retrieval should enforce data authorization before information reaches the model.

```text id="0r3h8s"
User
 |
 v
Authorization
 |
 v
RAG Query
 |
 v
Document ACL
 |
 v
Authorized Retrieval
 |
 v
AI Context
```

Similarity ranking should never override access permissions.

---

# 87. Tenant Isolation

Multi-tenant AI systems require strong isolation.

Controls should prevent:

* cross-tenant retrieval;
* shared memory leakage;
* cross-tenant tool execution;
* unauthorized database access;
* cross-tenant agent delegation.

Tenant boundaries should be enforced outside the model.

---

# 88. Session Isolation

Each AI session should have explicitly defined:

* identity;
* permissions;
* context;
* memory;
* tools;
* execution limits.

A new session should not automatically inherit unrestricted privileges from previous activity.

---

# 89. Human Approval Gates

High-impact actions should require human approval where appropriate.

Examples:

* financial transactions;
* privileged IAM changes;
* production changes;
* external data transfers;
* deletion of sensitive data.

```text id="j3r8m1"
AI Action
   |
   v
Risk Assessment
   |
   v
Human Approval
   |
   +--> Approve --> Execute
   |
   +--> Reject --> Stop
```

---

# 90. Two-Person or Dual-Control Operations

Critical operations may require more than one human authorization.

Examples include:

* disabling major security controls;
* deleting critical infrastructure;
* changing highly privileged IAM policies;
* large financial transfers.

This provides stronger protection against both AI error and human error.

---

# 91. Action Preview and Confirmation

Before high-risk execution, the system should present:

* requested action;
* affected resource;
* data involved;
* destination;
* expected impact;
* authorization basis.

The human should approve the actual action rather than merely approve the AI's general objective.

---

# 92. Output Validation

AI-generated action parameters should be validated before execution.

For example:

```text id="9s8k1m"
AI:
"Delete customer ID 12345"

Validator:
Is deletion permitted?
Is customer ID valid?
Is agent authorized?
Is deletion allowed?
Is approval required?
```

Only after validation should execution occur.

---

# 93. Semantic Action Validation

Validation should consider the meaning of an action, not merely its syntax.

A syntactically valid request can still be dangerous.

```text id="2q4w6e"
Valid API Request
       ≠
Authorized Business Action
```

Semantic validation should detect actions inconsistent with policy or business intent.

---

# 94. Policy Enforcement Outside the Model

Security-critical controls should be enforced independently of model instructions.

Examples:

* IAM;
* database authorization;
* API authorization;
* network controls;
* DLP;
* transaction limits;
* approval workflows.

This creates an important separation:

```text id="8t5n2k"
Model Policy
    +
Enterprise Security Policy
    |
    v
Independent Enforcement
```

---

# 95. Prompt and Instruction Integrity

System instructions should still be protected because compromised instructions can influence agent behavior.

Controls include:

* controlled prompt repositories;
* version control;
* integrity verification;
* change approval;
* secure deployment;
* environment separation.

Prompt protection is necessary but does not replace action authorization.

---

# 96. Untrusted Input Isolation

External content should not automatically become authoritative agent instructions.

Potential sources include:

* emails;
* websites;
* documents;
* tickets;
* user messages;
* retrieved content.

```text id="2t5x8n"
Untrusted Content
       |
       v
Content Boundary
       |
       v
AI Context
       |
       X
Direct Authorization
```

Retrieved content should not be allowed to grant permissions.

---

# 97. Prompt Injection Detection

AI applications should detect suspicious instructions attempting to manipulate agent behavior.

Detection can consider:

* instruction overrides;
* role manipulation;
* tool-use requests;
* hidden instructions;
* malicious documents;
* unusual action sequences.

Detection should complement independent authorization controls.

---

# 98. Agent Behavior Monitoring

Agent behavior should be continuously monitored.

Useful signals include:

* tool usage;
* action frequency;
* data-access volume;
* destination changes;
* privilege use;
* failed authorization attempts;
* execution duration;
* unusual action sequences.

Behavioral anomalies should trigger investigation or additional restrictions.

---

# 99. Anomaly Detection

Anomaly detection can identify behavior inconsistent with established baselines.

```text id="q3n5k7"

5 API calls / session

Observed:
500 API calls / session
        |
        v
Anomaly
        |
        v
Throttle / Block / Investigate
```

Anomaly detection should not be the only security mechanism because sophisticated attacks may imitate normal behavior.

---

Rate limits should apply to:

* model requests;
* tool calls;
* database queries;
* API calls;
* external transfers;
* workflow executions.

Rate limiting reduces the ability to abuse high-agency capabilities at scale.

Agents should have bounded resource consumption.

Examples:

* CPU;
* memory;
* storage;
* API calls;
* tokens;
* database queries;
* file operations;
* network bandwidth.

Quotas reduce both security and availability risks.

---

# 102. Sandbox Execution

High-risk agent operations should execute in isolated environments where appropriate.

Sandboxing can restrict:

* file access;
* process execution;
* network connectivity;
* operating-system permissions;
* installed software.

```text id="7v0k3m"
   v

   +--> Limited Network
   +--> Limited Processes

```

---

Code generated by an AI should not automatically receive unrestricted execution privileges.

Controls should include:

* sandboxing;
* static analysis;
* execution restrictions;
* network restrictions;
* filesystem isolation;
* runtime monitoring.

Code execution should be treated as a high-risk agent capability.

---

# 104. Database Query Controls

Agents accessing databases should be constrained by:

* approved queries;
* query templates;
* row limits;
* field restrictions;
* read/write separation;
* transaction limits.

```text id="4s9v0n"
 |

        |

```

# 106. Destructive Action Protection

Destructive operations should receive additional safeguards.

Examples:

* deletion;
* account termination;
* infrastructure destruction;
* bulk modification;
* irreversible data changes.

Potential controls include:

* explicit confirmation;
* dual approval;
* transaction limits;
* soft-delete;
* rollback capability.

---

# 107. Reversibility Controls

Where feasible, AI actions should be reversible.

Examples:

```text id="7w3f8q"
   |
   v
Validation

   |

```

Reversibility reduces the consequences of erroneous or malicious autonomous actions.

---

# 108. Kill Switch for Agentic AI

High-risk AI systems should have an independent mechanism to immediately stop agent execution.

The kill switch should ideally be capable of:

* stopping active workflows;
* disabling tools;
* revoking credentials;
* blocking network access;
* terminating sessions.

It should not depend on the AI agent cooperating with the shutdown request.

---

# 109. Credential Revocation

When an agent is suspected of compromise, its credentials should be immediately revocable.

```text id="3q8m2x"
   |
   v
Agent Compromise Suspected

   v
Revoke Credentials
   |
   v
Disable Tools
   |
   v
Block Network
```

This should be integrated with enterprise IAM and privileged-access infrastructure.

---

# 110. Agent Isolation

A compromised agent should be capable of being isolated without necessarily disrupting unrelated AI applications.

Isolation may include:

* session termination;
* container isolation;
* network isolation;
* tool disablement;
* credential revocation;
* tenant isolation.

---

# 111. Security Logging

Every consequential agent action should generate security telemetry.

* agent identity;
* model version;
* tool;
* action;
* resource;
* authorization decision;
* timestamp;
* result;
* destination.

This enables investigation and accountability.

---

# 112. Tamper-Resistant Logging

Security logs should be protected from modification by the AI system or compromised application.

Controls may include:

* centralized collection;
* immutable storage;
* access separation;
* cryptographic integrity;
* restricted administrative access.

An agent should not be able to erase evidence of its own actions.

The technical control objectives are to:

2. enforce least privilege;

Critical controls should remain independent of the AI model.

# 116. Secure Agent Control Boundary

The technical security boundary should encompass every capability that allows the AI to affect the enterprise environment.

# 117. Core Engineering Principle

> **Do not give the AI more authority than the business process requires, and never allow the model to be the sole mechanism that determines whether a consequential action is authorized.**

The secure engineering model is:

```text id="2q7x5m"
Minimum Required Capability
            +
Least Privilege
            +
Independent Authorization
            +
Action Validation
            +
Bounded Execution
            +
Human Oversight
            +
Monitoring
            +
Rapid Containment
```

The objective is not to eliminate AI autonomy. It is to ensure that **autonomy remains bounded, attributable, reversible where possible, and independently enforceable by enterprise security controls**.

## Part 3 — Governance, Risk, GRC, and Operational Controls

# 118. Excessive Agency Governance Framework

Excessive agency should be governed as an enterprise AI security risk covering the authority, autonomy, data access, tool access, and operational capabilities granted to AI systems.

The governance framework should define:

* permitted AI capabilities;
* prohibited capabilities;
* autonomy levels;
* data-access boundaries;
* tool authorization;
* transaction limits;
* human approval requirements;
* monitoring;
* incident response;
* assurance requirements.

The central governance question should be:

> **What is this AI system authorized to do, under which conditions, and who is accountable for that authority?**

---

# 119. Ownership and Accountability

Every AI agent should have clearly assigned ownership.

| Function          | Primary Responsibility               |
| ----------------- | ------------------------------------ |
| AI Product Owner  | Business purpose and functionality   |
| Application Owner | Application implementation           |
| AI Security       | Agency security controls             |
| Data Owner        | Data-access authorization            |
| IAM               | Identity and privilege management    |
| Network Security  | Connectivity and egress              |
| Privacy           | Personal-data requirements           |
| SOC               | Monitoring and detection             |
| GRC               | Risk, policy, and control governance |
| Internal Audit    | Independent assurance                |

Ownership should remain clear even when multiple vendors and platforms participate in the AI workflow.

---

# 120. Excessive Agency Risk Classification

Agency risk should be classified according to the authority and potential impact of the AI system.

Relevant factors include:

* autonomy;
* privilege;
* data sensitivity;
* tool capability;
* external connectivity;
* transaction authority;
* reversibility;
* business impact.

Example:

| Risk     | Example                                                        |
| -------- | -------------------------------------------------------------- |
| Low      | AI generates recommendations only                              |
| Medium   | AI reads internal information and proposes actions             |
| High     | AI executes business operations                                |
| Critical | AI executes privileged or irreversible operations autonomously |

---

# 121. AI Application Risk Tiering

AI applications should be assigned risk tiers based on their effective agency.

```text id="f5m8x1"
Tier 1
Recommendation Only
       |
Tier 2
Limited Read Access
       |
Tier 3
Controlled Tool Execution
       |
Tier 4
Multiple Business Actions
       |
Tier 5
Privileged / Autonomous Operations
```

The higher the tier, the stronger the required governance, testing, monitoring, and approval controls.

---

# 122. Excessive Agency Risk Register

Agency-related risks should be documented in the enterprise risk register.

Example:

| Risk                   | Cause              | Impact               | Treatment            |
| ---------------------- | ------------------ | -------------------- | -------------------- |
| Excessive permissions  | Broad IAM role     | Unauthorized actions | Least privilege      |
| Tool abuse             | Unrestricted tools | Business disruption  | Tool allowlisting    |
| Autonomous transaction | No approval gate   | Financial loss       | Dual authorization   |
| Privilege escalation   | Admin API access   | System compromise    | Privileged isolation |
| Agent persistence      | Unlimited runtime  | Repeated actions     | Execution limits     |

Each risk should have an owner, treatment plan, residual-risk rating, and review cadence.

---

# 123. Risk Appetite and Tolerance

Organizations should explicitly define acceptable levels of AI autonomy.

Examples:

* unrestricted autonomous administrative operations are prohibited;
* critical financial transactions require human approval;
* AI agents may not modify IAM policies autonomously;
* unrestricted external communication is prohibited;
* autonomous deletion of critical information is prohibited.

Risk appetite should be converted into enforceable technical requirements.

---

# 124. Agency Level Governance

Organizations should formally classify autonomy levels.

```text id="0q9c5f"
Level 1 — Advisory
AI recommends

Level 2 — Assisted
Human initiates action

Level 3 — Controlled Autonomous
AI executes approved actions

Level 4 — Multi-Step Autonomous
AI chains multiple approved actions

Level 5 — High-Impact Autonomous
AI independently executes consequential operations
```

Higher autonomy should require stronger controls and assurance.

---

# 125. Capability Inventory Governance

Organizations should maintain an inventory of AI capabilities.

The inventory should identify:

* models;
* agents;
* tools;
* APIs;
* databases;
* network access;
* credentials;
* memory;
* RAG repositories;
* external destinations.

```text id="8c4r6m"
Agent
 |
 +--> Data
 +--> Tools
 +--> APIs
 +--> Credentials
 +--> Network
 +--> Memory
 +--> External Services
```

Unknown capabilities represent unknown security exposure.

---

# 126. Agent Identity Governance

Each production agent should have an identifiable security identity.

Governance should define:

* identity owner;
* authentication mechanism;
* credential lifecycle;
* privilege scope;
* expiration;
* revocation;
* audit requirements.

Agent identities should not be treated as generic application accounts.

---

# 127. Agent Privilege Governance

Agent permissions should be reviewed against the approved business purpose.

The review should ask:

1. What data can the agent access?
2. What systems can it modify?
3. What tools can it invoke?
4. What external destinations can it reach?
5. What transactions can it execute?
6. What actions require approval?

Unused privileges should be removed.

---

# 128. Tool Governance

Every AI-accessible tool should have:

* an owner;
* a business purpose;
* a risk classification;
* permitted users/agents;
* permitted operations;
* data-access restrictions;
* approval requirements.

Tools should not become available to AI applications simply because they are technically integrated.

---

# 129. Agent Delegation Governance

AI-to-AI delegation should be governed explicitly.

Policies should define:

* which agents may delegate;
* which agents may receive delegated tasks;
* what authority may be delegated;
* maximum delegation depth;
* inherited permissions;
* prohibited privilege expansion.

A delegated agent should not receive authority greater than the originating authorization permits.

---

# 130. Data Access Governance

AI data access should remain subject to enterprise data governance.

Requirements should address:

* data classification;
* purpose;
* identity;
* authorization;
* tenant;
* retention;
* minimization.

The AI should not receive broad access simply because the underlying user has broad organizational privileges.

---

# 131. Sensitive Data Governance

Sensitive data should have explicit AI-processing requirements.

Policies should define whether particular data categories may be:

* accessed;
* analyzed;
* stored in memory;
* included in context;
* exported;
* transmitted externally.

Highly sensitive data may require dedicated AI environments or prohibit autonomous processing.

---

# 132. RAG Governance

RAG repositories should be governed as controlled enterprise information sources.

Governance should address:

* source ownership;
* classification;
* document permissions;
* retrieval authorization;
* tenant boundaries;
* indexing;
* deletion;
* retention;
* provenance.

A document being searchable does not automatically authorize an agent to use it.

---

# 133. Memory Governance

Persistent AI memory should have defined governance requirements.

These should include:

* what information may be stored;
* who can access it;
* retention period;
* deletion process;
* tenant boundaries;
* classification;
* cross-session usage.

Memory should not silently expand the effective authority of an AI system.

---

# 134. Credential and Secrets Governance

Agent credentials should be governed through enterprise identity and secrets-management processes.

Requirements should include:

* least privilege;
* short-lived credentials where possible;
* rotation;
* revocation;
* ownership;
* privileged-access controls;
* monitoring.

AI agents should not be granted persistent administrative credentials without exceptional justification.

---

# 135. Network and Egress Governance

AI network access should be explicitly approved.

Governance should identify:

* permitted networks;
* approved APIs;
* approved destinations;
* prohibited destinations;
* transfer limits;
* proxy requirements;
* inspection requirements.

External connectivity should be treated as an explicit capability rather than a default feature.

---

# 136. External Communication Governance

AI systems capable of sending information externally should be subject to specific policies.

Governance should address:

* approved recipients;
* domains;
* communication channels;
* data classifications;
* message types;
* file attachments;
* approval requirements.

For sensitive communications, automated execution may be prohibited.

---

# 137. Transaction Governance

AI-driven transactions should have defined authorization thresholds.

Example:

```text id="2d8m4x"

       |
       +--> Low --> Automated
       |
       +--> Medium --> Additional Controls
       |
```

# 211. Strategic Security Principle

> **AI autonomy must never exceed the authority necessary to perform its approved business purpose, and every consequential action must remain subject to independent authorization, bounded execution, continuous monitoring, and effective human or automated intervention.**

The enterprise objective is not to prevent AI from acting. It is to ensure that **AI action remains bounded, attributable, reversible where possible, proportionate to risk, independently authorized, and incapable of converting model manipulation into unrestricted enterprise authority.**
