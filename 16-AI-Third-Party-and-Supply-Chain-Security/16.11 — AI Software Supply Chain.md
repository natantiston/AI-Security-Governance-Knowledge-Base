# 16.11 — AI Software Supply Chain

## Part 1 — Foundations, AI Software Supply-Chain Dependency, Provenance, Integrity, Components, Vulnerabilities and Governance

### 1. AI Software Supply-Chain Risk

AI software supply-chain risk is the risk arising from software components, libraries, frameworks, tools, packages, containers, SDKs, services, and development dependencies used to build, deploy, operate, or secure AI systems.

The supply chain may include:

* application code;
* AI frameworks;
* machine-learning libraries;
* SDKs;
* APIs;
* packages;
* containers;
* operating systems;
* infrastructure software;
* build systems;
* development tools;
* security tools;
* third-party services.

A compromise anywhere in this chain may affect downstream AI systems.

**Control ID: AI-SWSC-001**

---

### 2. Objective of AI Software Supply-Chain Governance

The objective of AI software supply-chain governance is to establish reasonable assurance that software components used by AI systems are:

* identified;
* sourced from appropriate channels;
* authenticated;
* integrity-protected;
* maintained;
* vulnerability-managed;
* appropriately licensed;
* monitored;
* securely built;
* securely deployed.

Governance should extend beyond internally written code.

**Control ID: AI-SWSC-002**

---

### 3. AI Software Supply Chain

The AI software supply chain is the collection of software components, development processes, suppliers, repositories, build systems, distribution channels, and operational dependencies involved in an AI system.

**Control ID: AI-SWSC-003**

---

### 4. AI Software Dependency

An AI software dependency is a software component or service required by an AI system to function as intended.

Dependencies may be:

* direct;
* transitive;
* runtime;
* development-time;
* build-time;
* infrastructure-level;
* security-related.

An organization should not assume that only directly imported packages represent its software dependency risk.

**Control ID: AI-SWSC-004**

---

### 5. Direct Software Dependency

A direct dependency is a component explicitly selected or referenced by the organization or application.

Examples include:

* machine-learning frameworks;
* AI SDKs;
* Python packages;
* JavaScript packages;
* database drivers;
* API clients.

Direct dependencies should be inventoried where practical.

**Control ID: AI-SWSC-005**

---

### 6. Transitive Software Dependency

A transitive dependency is a component required by another dependency.

```text id="q7n4mv"
AI Application
      |
Framework
      |
Library A
      |
Library B
      |
Library C
```

A vulnerability in a deeply nested dependency can therefore affect an AI application even when developers did not directly select that component.

**Control ID: AI-SWSC-006**

---

### 7. Build-Time Dependency

A build-time dependency is required to compile, package, test, generate, or otherwise construct an AI software artifact.

Examples include:

* compilers;
* package managers;
* build frameworks;
* code generators;
* testing frameworks;
* CI/CD plugins.

Build-time components can affect the integrity of the resulting artifact.

**Control ID: AI-SWSC-007**

---

### 8. Runtime Dependency

A runtime dependency is required while an AI application or service is executing.

Examples include:

* inference libraries;
* runtime frameworks;
* operating-system components;
* database drivers;
* authentication libraries;
* model-serving software.

Runtime dependencies should be monitored throughout the operational lifecycle.

**Control ID: AI-SWSC-008**

---

### 9. Development Dependency

Development dependencies support software development but may not be deployed into production.

They can nevertheless create risk through:

* developer compromise;
* malicious packages;
* credential access;
* build manipulation;
* source-code modification.

Development dependencies should therefore be governed according to their potential impact.

**Control ID: AI-SWSC-009**

### 17. Artifact Integrity

Artifact integrity is the property that a software artifact has not been altered without authorization.

Integrity mechanisms may include:

* cryptographic hashes;
* digital signatures;
* signed releases;
* immutable repositories;
* controlled build pipelines.

**Control ID: AI-SWSC-017**

---

### 18. Software Hash

A cryptographic hash can provide a reference value for a particular software artifact.

Hash verification can establish whether the received artifact matches the expected artifact.

However:

> **Hash verification establishes artifact consistency; it does not establish that the artifact itself is trustworthy or free from vulnerabilities.**

**Control ID: AI-SWSC-018**

---

### 19. Software Signature

A digital signature can provide evidence concerning artifact integrity and the identity associated with the signing key.

Signature verification should consider:

* signing identity;
* key trust;
* certificate status where applicable;
* signature validity;
* artifact association.

**Control ID: AI-SWSC-019**

### 20. Software Authenticity

Software authenticity concerns whether an artifact originated from the expected publisher or trusted distribution channel.

Authenticity controls may include:

* signed releases;
* authenticated repositories;
* trusted certificates;
* verified publisher identities;
* secure acquisition channels.

Authenticity does not establish that software is secure.

**Control ID: AI-SWSC-020**

### 50. AI Software Supply-Chain Trust Principle

Software used by AI systems should not be considered trustworthy merely because it is:

* open source;
* widely used;
* available from a public repository;
* highly downloaded;
* published by a recognized organization;
* digitally signed.

Trust should be established through appropriate combinations of:

* provenance;
* authenticity;
* integrity;
* vulnerability management;
* secure development;
* build assurance;
* dependency governance;
* monitoring;
* testing.

The organization should distinguish **artifact integrity from software security**, **publisher identity from publisher trustworthiness**, **package popularity from assurance**, and **a clean vulnerability scan from proof that the software is safe**.

Internal `AI-SWSC-*` identifiers represent the knowledge-base control taxonomy and are not statutory provisions or regulatory requirements unless a separate legal or regulatory mapping explicitly establishes that relationship.

The organization should not assume that a software component is trustworthy merely because it is:

* open source;
* widely used;
* highly downloaded;
* digitally signed;
* hosted in a reputable repository;
* free of currently known vulnerabilities.

Similarly, the existence of an SBOM, security questionnaire, certification, contractual commitment, or automated scanner does not by itself establish complete software supply-chain assurance.

Internal `AI-SWSC-*` identifiers are organizational governance taxonomy identifiers. They are not provisions of legislation or regulation. Where a control is presented as mandatory, its actual legal, regulatory, contractual, or authoritative source should be separately identified and mapped.
