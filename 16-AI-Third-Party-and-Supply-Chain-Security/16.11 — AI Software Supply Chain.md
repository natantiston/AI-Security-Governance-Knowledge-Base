# 16.11 — AI Software Supply Chain

## Part 1 — Foundations, Software Supply-Chain Classification, Dependency Mapping, Provenance and Risk Architecture

### 1 — AI Software Supply-Chain Risk Definition

AI software supply-chain risk is the risk that software, libraries, packages, frameworks, SDKs, tools, build systems, repositories, dependencies, or other software components used to develop, deploy, operate, or secure AI systems introduce:

* vulnerabilities;
* malicious functionality;
* compromised dependencies;
* licensing restrictions;
* integrity failures;
* unauthorized access;
* availability failures;
* privacy risks;
* operational dependencies.

### 2 — AI Software Supply-Chain Governance Objective

Organizations should establish governance capable of identifying, assessing, controlling, monitoring, and managing material software dependencies throughout the AI-system lifecycle.

### 3 — AI Software Supply Chain

An AI software supply chain may include:

**Developer → Source Code → Dependency → Package Repository → Build System → CI/CD → Artifact Repository → Deployment → Runtime → AI Application**

### 4 — AI Software Component

An AI software component is any software element materially involved in:

* AI development;
* model integration;
* data processing;
* model serving;
* inference;
* monitoring;
* security;
* orchestration.

### 5 — Direct Software Dependency

A direct dependency is a software component explicitly selected or declared by an application or project.

### 6 — Transitive Software Dependency

A transitive dependency is a software component required indirectly through another dependency.

### 7 — Hidden Dependency

A hidden dependency is a component used by an AI system without being adequately represented in organizational dependency records.

### 8 — AI Software Dependency Inventory

Material AI applications should maintain an inventory of relevant software dependencies where feasible.

### 9 — Software Dependency Mapping

Organizations should map material dependencies between:

* applications;
* libraries;
* packages;
* frameworks;
* SDKs;
* services;
* infrastructure.

### 10 — AI Software Bill of Materials

An AI Software Bill of Materials should identify material software components associated with an AI system where appropriate.

### 11 — SBOM Definition

A Software Bill of Materials is a structured inventory describing software components and their relationships within a software product or system.

### 12 — AI SBOM Scope

For AI systems, SBOM scope may include software supporting:

* model serving;

* training;
* evaluation;
* orchestration;
* security controls.

### 13 — AI Bill of Materials Relationship

### 14 — AI BOM Scope

An AI BOM may include relationships among:

* software;

* datasets;
* model-serving infrastructure;
* external services.

### 15 — Software Supply-Chain Trust Boundary

### 16 — Repository Trust Boundary

### 19 — CI/CD Trust Boundary

### 20 — Runtime Trust Boundary

# 16.11 — AI Software Supply Chain — Part 2

## Part 2 — Software Supply-Chain Due Diligence, Dependency Security, SBOM, Build Integrity, Vulnerability Management and Secure Delivery

### Software Supply-Chain Due Diligence

211 — **AI-SWSC-211 — Software Supply-Chain Due-Diligence Requirement**
Organizations should perform proportionate due diligence before introducing externally sourced software components, libraries, packages, frameworks, SDKs, plugins, extensions, containers, build tools, deployment components, or other software dependencies into AI environments.

212 — **AI-SWSC-212 — Dependency Due-Diligence Scope**
Dependency due diligence should consider the component's source, publisher, maintainer, ownership, provenance, licensing, security history, vulnerability exposure, maintenance status, dependency structure, privilege requirements, network behavior, and business criticality.

213 — **AI-SWSC-213 — Publisher Verification Control**
The identity of a software publisher or package maintainer should be verified before a component is approved for material AI workloads.

214 — **AI-SWSC-214 — Repository Verification Control**
Organizations should verify that software is obtained from an authorized repository, registry, package index, source repository, vendor channel, or other approved distribution mechanism.

215 — **AI-SWSC-215 — Repository Trust Assessment**
Approved repositories should be assessed for authentication, access control, integrity protection, availability, package provenance, malware controls, security response, and administrative governance.

216 — **AI-SWSC-216 — Repository Allowlist Control**
Production AI environments should use an approved repository allowlist where practical, with exceptions subject to documented security review.

217 — **AI-SWSC-217 — Repository Denylist Control**
Known malicious, compromised, unauthorized, or prohibited repositories and package sources should be blocked where technically feasible.

218 — **AI-SWSC-218 — Package Source Verification**
Dependency acquisition processes should verify the expected package source and detect unexpected changes in source location, publisher identity, repository, namespace, or distribution mechanism.

219 — **AI-SWSC-219 — Package Identity Verification**
Each approved dependency should have a sufficiently precise identity record covering package name, ecosystem, publisher or namespace, version, artifact identifier, and repository source.

220 — **AI-SWSC-220 — Package Version Approval**
Organizations should approve specific dependency versions or controlled version ranges rather than allowing unrestricted dependency resolution in production environments.

221 — **AI-SWSC-221 — Dependency Pinning Control**
Critical dependencies should be pinned to approved versions or immutable references where practical to reduce uncontrolled dependency drift.

222 — **AI-SWSC-222 — Lockfile Integrity Control**
Dependency lockfiles should be generated, reviewed, protected, and monitored for unauthorized modification where the software ecosystem supports them.

223 — **AI-SWSC-223 — Dependency Resolution Control**
Automated dependency resolution should be controlled so that newly introduced or changed transitive dependencies cannot bypass established security, licensing, and approval requirements.

224 — **AI-SWSC-224 — Dependency Confusion Control**
Organizations should implement controls to reduce dependency-confusion risk, including namespace controls, private package configuration, repository precedence controls, and package-source validation.

225 — **AI-SWSC-225 — Typosquatting Detection Control**
Dependency acquisition should include controls for detecting suspicious package names that resemble trusted packages or namespaces.

226 — **AI-SWSC-226 — Malicious Package Screening**
Externally sourced software should be screened for malicious code, suspicious behavior, unauthorized network activity, credential theft, persistence mechanisms, and other indicators of compromise before production deployment.

227 — **AI-SWSC-227 — Package Acquisition Quarantine**
New or untrusted software dependencies should initially be acquired into a controlled environment where security, licensing, provenance, and compatibility checks can be performed.

228 — **AI-SWSC-228 — Dependency Admission Control**
A dependency should not enter a production AI environment until required admission criteria have been satisfied or an authorized exception has been approved.

229 — **AI-SWSC-229 — Dependency Ownership Assignment**
Material software dependencies should have an accountable technical or service owner responsible for lifecycle, security, remediation, and evidence management.

230 — **AI-SWSC-230 — Dependency Criticality Classification**
Dependencies should be classified according to factors such as business criticality, AI workload dependency, privilege, data access, network access, execution capability, exploitability, and replacement difficulty.
