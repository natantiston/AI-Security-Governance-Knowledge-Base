# 16.05 — Cloud AI Provider Risk

## Part 1 — Foundations, Cloud AI Provider Classification, Dependency and Risk Architecture

### 1 — Cloud AI Provider Risk Definition

Cloud AI provider risk is the risk arising from an organization’s dependency on a cloud service provider for artificial intelligence capabilities, infrastructure, platforms, models, data processing, security services, or AI-enabled managed services.

Cloud AI providers may supply infrastructure-level capabilities such as GPU computing, AI accelerators, storage, networking, and managed Kubernetes; platform-level capabilities such as model hosting, machine-learning platforms, vector databases, AI development environments, and model operations; or managed AI services such as generative AI APIs, foundation models, speech services, computer vision, document intelligence, and agentic AI platforms.

Cloud AI provider risk therefore extends beyond conventional cloud outsourcing risk because the provider may influence not only infrastructure availability and data processing but also model behavior, inference processing, AI safety controls, model lifecycle, training dependencies, content filtering, AI-specific telemetry, and downstream AI functionality.

### 2 — Cloud AI Provider Risk Objective

The objective of cloud AI provider risk management is to ensure that the organization understands, assesses, controls, monitors, and governs risks arising from its dependency on cloud providers for AI capabilities.

The organization should establish sufficient visibility into:

* cloud AI services being used;
* data processed by those services;
* AI models and model providers involved;
* geographic processing locations;
* identities and privileged access;
* integrations and downstream dependencies;
* security responsibilities;
* provider and customer responsibilities;
* subcontractors and subprocessors;
* model and service lifecycle;
* service availability and resilience;
* regulatory obligations;
* contractual commitments;
* portability and exit feasibility.

### 3 — Cloud AI Provider vs Traditional Cloud Provider

A traditional cloud provider primarily supplies computing, storage, networking, databases, and related infrastructure or platform services.

A cloud AI provider may provide those capabilities while additionally supplying:

* foundation models;
* managed inference;
* model training infrastructure;
* machine-learning platforms;
* generative AI services;
* AI APIs;
* vector search;
* embeddings;
* AI agents;
* AI orchestration;
* model monitoring;
* AI security controls;
* content moderation;
* retrieval-augmented generation capabilities;
* AI development environments.

The additional AI layer creates risks that cannot always be addressed through conventional cloud security controls alone.

### 4 — Cloud AI Provider Classification

An organization should classify the provider according to the actual services consumed rather than relying solely on the provider's corporate identity.

Possible classifications include:

1. Infrastructure cloud provider
2. AI infrastructure provider
3. Managed machine-learning platform provider
4. Managed foundation-model provider
5. Generative AI service provider
6. AI API provider
7. AI application platform provider
8. AI agent platform provider
9. Model hosting provider
10. AI development platform provider
11. AI security service provider
12. AI data platform provider
13. Vector database provider
14. GPU-as-a-Service provider
15. Managed AI operations provider

A single provider may belong to multiple categories simultaneously.

### 5 — Cloud AI Service Classification

Each cloud AI service should be classified separately because risk may differ significantly between services offered by the same provider.

For example, an organization may use the same cloud provider for:

* virtual machines;
* object storage;
* managed databases;
* a foundation-model API;
* model training;
* AI agents;
* vector search;
* security monitoring.

These services should not automatically inherit the same risk classification.

### 6 — Cloud AI Provider Dependency

A cloud AI dependency exists when an organization's AI capability depends on a cloud provider for one or more critical functions.

Dependencies may include:

* compute;
* GPU capacity;
* model inference;
* model hosting;
* training;
* storage;
* networking;
* identity;
* secrets management;
* AI APIs;
* vector databases;
* data pipelines;
* observability;
* security controls;
* backup;
* disaster recovery;
* model deployment;
* AI orchestration.

The dependency should be documented according to the actual technical architecture.

### 7 — Direct Cloud AI Dependency

A direct dependency exists when an AI system directly consumes a cloud provider service.

Examples include:

* an application calling a managed LLM API;
* a machine-learning platform using cloud GPU instances;
* an AI application storing embeddings in a cloud vector database;
* an AI agent using a managed model endpoint.

Direct dependencies should be recorded in the organization's AI system and third-party risk inventories.

### 8 — Indirect Cloud AI Dependency

An indirect dependency exists when an AI system depends on a cloud provider through another service, platform, vendor, or application.

For example:

**Enterprise application → SaaS provider → cloud AI service → foundation model**

The enterprise may initially identify only the SaaS provider while remaining unaware that the SaaS service depends on a cloud AI platform.

Indirect dependencies can create visibility, concentration, resilience, contractual, and regulatory challenges.

### 9 — Hidden AI Provider Dependency

A hidden dependency exists when an organization uses an AI-enabled service without sufficient visibility into the underlying cloud provider, model provider, infrastructure provider, or downstream service dependency.

Potential examples include:

* SaaS applications using third-party LLM APIs;
* AI security products using external foundation models;
* AI development platforms using managed cloud inference;
* model marketplaces hosting models on third-party infrastructure;
* AI agents calling external cloud services.

Vendor due diligence should therefore address material fourth-party and downstream AI dependencies.

Dependency mapping enables risk analysis at both the application and provider levels.

### 11 — Cloud AI Trust Boundary

The trust boundary identifies where organizational data, identities, models, prompts, outputs, credentials, and execution authority cross from organizational control into cloud-provider-controlled environments.

Typical trust-boundary crossings include:

* prompt transmission;
* document upload;
* API requests;
* inference processing;
* model hosting;
* training jobs;
* embedding generation;
* vector retrieval;
* logging;
* telemetry;
* support access;
* backup;
* administrative access.

Every material trust-boundary crossing should have an identified security and governance owner.

### 12 — Cloud AI Shared Responsibility

Cloud AI security is generally governed through a shared-responsibility model.

Responsibilities may be divided among:

* the cloud provider;
* the AI model provider;
* the SaaS provider;
* the organization;
* application developers;
* security teams;
* data owners;
* administrators;
* users.

The organization should document the actual allocation of responsibilities for each service.

Provider documentation should not automatically be treated as evidence that the organization has fulfilled its own responsibilities.

A Cloud AI Shared Responsibility Matrix should identify responsibility for controls such as:

* physical security;
* infrastructure security;
* hypervisor security;
* network security;
* identity management;
* encryption;
* key management;
* data classification;
* data retention;
* model access;

* business continuity;
* backup;
* disaster recovery;
* configuration management.

The matrix should identify whether each responsibility belongs to the provider, customer, or is shared.

### 14 — Responsibility Ambiguity Risk

Responsibility ambiguity occurs when neither the organization nor the provider has clearly established who is responsible for a security, privacy, operational, or AI governance control.

Examples include uncertainty regarding:

* model vulnerability management;
* prompt logging;
* AI abuse monitoring;
* model change notification;
* output filtering;
* incident notification;
* data deletion;
* security testing;
* model rollback.

Unclear responsibility creates control gaps even when both parties maintain otherwise mature security programs.

### 15 — Cloud AI Criticality

Cloud AI services should be classified according to their business and operational criticality.

Criticality may consider:

* business-process dependency;
* revenue impact;
* customer impact;
* regulatory significance;
* safety implications;
* data sensitivity;
* operational dependency;
* recovery requirements;
* substitution difficulty;
* provider concentration.

A cloud AI service supporting a critical business process should receive more stringent governance than an experimental AI service with no material business dependency.

### 16 — AI Service Criticality vs Cloud Account Criticality

The criticality of a cloud account, subscription, or tenant does not necessarily equal the criticality of an AI service deployed within it.

A low-volume AI endpoint could support a highly critical business process, while a large cloud environment may contain only noncritical experimentation.

Risk assessment should therefore be performed at the relevant AI-service and use-case level.

Cloud AI provider risk should be assessed across multiple dimensions, including:

### 18 — Cybersecurity Risk

Cybersecurity risk may arise from:

* compromised cloud accounts;
* exposed API credentials;
* excessive privileges;
* insecure APIs;
* vulnerable AI workloads;
* compromised model artifacts;
* malicious dependencies;
* insecure containers;
* exposed storage;
* network misconfiguration;
* inadequate monitoring;
* compromised administrative identities.

AI workloads should therefore be incorporated into the organization's cloud security architecture.

### 19 — AI-Specific Security Risk

AI-specific risks may include:

* prompt injection;
* adversarial inputs;
* model extraction;
* model abuse;
* data poisoning;
* training-data compromise;
* model artifact tampering;
* hallucination;
* unsafe tool invocation;
* excessive agent autonomy;
* unauthorized model access;
* model degradation;
* model supply-chain compromise.

Traditional cloud controls remain necessary but may not address these risks completely.

### 20 — Cloud AI Data Risk

Cloud AI services may process:

* prompts;
* files;
* personal data;
* confidential information;
* proprietary source code;
* business records;
* customer information;
* embeddings;
* model outputs;
* telemetry;
* logs;
* feedback data.

Data classification should therefore occur before material data is submitted to a cloud AI service.

### 21 — Data Flow Visibility

The organization should understand where AI-related data:

1. originates;
2. is transmitted;
3. is processed;
4. is stored;
5. is logged;
6. is backed up;
7. is replicated;
8. is accessed;
9. is transferred to subprocessors;
10. is deleted.

Data-flow visibility is particularly important where cloud AI services operate across multiple regions or involve multiple providers.

### 22 — Prompt Data Classification

Prompts should be treated as potential business data rather than automatically as low-risk user input.

A prompt may contain:

* personal information;
* customer information;
* credentials;
* source code;
* trade secrets;
* confidential strategy;
* security information;
* regulated information.

Organizations should establish rules defining what classes of information may be submitted to each cloud AI service.

### 23 — AI Output Classification

AI outputs may also contain sensitive or regulated information.

Outputs may include:

* personal data;
* confidential information;
* proprietary code;
* security findings;
* customer information;
* copyrighted material;
* generated decisions;
* recommendations affecting individuals.

Output handling should therefore follow appropriate information-classification requirements.

### 24 — Data Minimization

Organizations should minimize the amount and sensitivity of information transmitted to cloud AI services to what is necessary for the approved use case.

Potential controls include:

* prompt minimization;
* data filtering;
* redaction;
* masking;
* pseudonymization;
* DLP inspection;
* field-level restrictions;
* attachment restrictions;
* tokenization.

Data minimization is a governance control that reduces exposure independently of provider security maturity.

### 25 — Cloud AI Data Retention

The organization should establish how long cloud AI providers may retain:

* prompts;
* uploaded files;
* outputs;
* logs;
* telemetry;
* embeddings;
* training data;
* abuse-monitoring records;
* support information.

Retention requirements should be evaluated against the organization's legal, regulatory, contractual, and internal policy obligations.

### 26 — AI Training-Use Risk

Some cloud AI services may offer capabilities in which customer content can potentially be used for service improvement, model development, abuse detection, or other secondary purposes, depending on the service and applicable terms.

The organization should establish whether customer data may be used for:

* model training;
* fine-tuning;
* service improvement;
* abuse detection;
* human review;
* analytics;
* product development.

The organization's assessment should rely on applicable contractual terms and service documentation rather than marketing descriptions alone.

### 27 — Data Residency

Data residency refers to the geographic location in which relevant AI data is stored or processed.

AI services may involve different locations for:

* data storage;
* inference;
* logging;
* backup;
* disaster recovery;
* support;
* security monitoring;
* subprocessors.

Residency requirements should therefore be evaluated against the complete processing architecture rather than a single advertised region.

### 28 — Cross-Border AI Processing

Cloud AI architectures may transmit information across jurisdictions even when the primary cloud region is located within the organization's preferred geography.

Potential cross-border processing points include:

* model inference;
* support operations;
* telemetry;
* security monitoring;
* subprocessors;
* backups;
* centralized logging;
* provider administration.

The organization should identify material cross-border flows and assess applicable legal and contractual requirements.

### 29 — Cloud AI Identity Dependency

Cloud AI services frequently depend on cloud identity infrastructure for:

* authentication;
* authorization;
* service accounts;
* managed identities;
* API access;
* administrative access;
* workload identity;
* federation.

Compromise of the underlying identity environment may therefore compromise multiple AI workloads simultaneously.

### 30 — Privileged Access Risk

Privileged cloud identities may have the ability to:

* modify AI endpoints;
* change model configuration;
* access training data;
* alter network controls;
* change storage permissions;
* retrieve secrets;
* modify logging;
* disable security controls;
* deploy new AI services.

Privileged access should therefore be governed using least privilege, strong authentication, segregation of duties, and appropriate monitoring.

### 31 — AI Model Dependency

A cloud AI service may depend on:

* proprietary models;
* third-party foundation models;
* open-source models;
* fine-tuned models;
* specialized models;
* multiple model providers.

The organization should identify the model dependency underlying each material AI capability.

### 32 — Model Provider Transparency

The organization should seek sufficient information to determine:

* who provides the model;
* where the model is hosted;
* whether the model is proprietary or open source;
* whether the model can change;
* how model versions are identified;
* whether the provider can substitute models;
* whether model behavior is materially affected by provider updates.

Lack of transparency should be treated as a risk factor where model behavior is material to the use case.

### 33 — Model Version Dependency

AI applications may depend on a specific model version even when the cloud service abstracts the model infrastructure.

Model changes may affect:

* accuracy;
* latency;
* cost;
* safety behavior;
* refusal behavior;
* output structure;
* tool invocation;
* security controls;
* application compatibility.

Model version dependencies should therefore be documented for material AI systems.

### 34 — Model Change Risk

Changes to an underlying model can create operational or security consequences without requiring changes to the organization's application code.

Examples include:

* changed output behavior;
* altered content filtering;
* changed context handling;
* different tool-use behavior;
* changed token limits;
* altered performance;
* changed data-processing characteristics.

Organizations should establish model-change governance proportional to system criticality.

### 35 — Cloud AI Configuration Risk

Cloud AI security depends significantly on customer configuration.

Potential configuration areas include:

* IAM;
* network access;
* private endpoints;
* encryption;
* logging;
* retention;
* model permissions;
* API access;
* endpoint exposure;
* data-loss prevention;
* monitoring;
* geographic restrictions.

Provider security capabilities do not compensate for insecure customer configuration.

### 36 — Configuration Drift

Configuration drift occurs when an approved AI security configuration changes over time.

Examples include:

* public endpoint exposure;
* modified IAM permissions;
* disabled logging;
* altered retention;
* newly enabled AI models;
* changed network routes;
* unauthorized API access;
* changed data-processing regions.

Material AI services should have appropriate configuration monitoring.

### 37 — Cloud AI API Dependency

AI applications commonly depend on APIs for:

* model inference;
* embeddings;
* content moderation;
* speech;
* vision;
* document processing;
* agent tools;
* retrieval;
* model management.

API dependency creates risks involving authentication, availability, rate limits, version changes, data exposure, and provider outages.

### 38 — API Credential Risk

API credentials can provide direct access to AI capabilities and may enable:

* unauthorized inference;
* sensitive-data submission;
* excessive consumption;
* cost generation;
* model abuse;
* data extraction.

Credentials should be protected through appropriate secrets-management and access-control mechanisms.

### 39 — Cloud AI Network Dependency

AI services may depend on:

* internet connectivity;
* private networks;
* VPNs;
* private endpoints;
* DNS;
* firewalls;
* proxies;
* API gateways;
* service meshes.

Network architecture should reflect the sensitivity and criticality of the AI workload.

### 40 — AI Egress Risk

Uncontrolled outbound traffic from AI workloads may permit:

* unauthorized data transfer;
* malicious model downloads;
* command-and-control communication;
* unauthorized API calls;
* exfiltration through external AI services.

Appropriate egress controls should be considered for material AI workloads.

### 41 — Cloud Storage Dependency

AI workloads commonly depend on cloud storage for:

* training datasets;
* model artifacts;
* prompts;
* documents;
* embeddings;
* logs;
* evaluation results;
* backups.

Storage misconfiguration can therefore expose both conventional business information and AI-specific artifacts.

### 42 — Model Artifact Storage Risk

Model artifacts may include:

* model weights;
* checkpoints;
* configuration files;
* tokenizers;
* adapters;
* embeddings;
* evaluation datasets;
* inference configurations.

Unauthorized modification of these artifacts can affect model integrity and AI behavior.

### 43 — AI Supply-Chain Dependency

Cloud AI environments may incorporate components from multiple suppliers, including:

* cloud infrastructure;
* foundation-model providers;
* open-source libraries;
* container images;
* model repositories;
* datasets;
* APIs;
* security tools;
* monitoring platforms.

The organization should consider these dependencies as part of the AI supply chain.

### 44 — Fourth-Party AI Dependency

A cloud provider may itself rely on another organization for:

* foundation models;
* GPUs;
* software;
* security services;
* data;
* managed infrastructure;
* content moderation;
* AI components.

Material fourth-party dependencies should be considered where they can affect security, resilience, regulatory compliance, or business continuity.

### 45 — Cloud AI Concentration Risk

Concentration risk arises when multiple critical AI capabilities depend on the same provider.

For example:

**Identity + compute + storage + AI inference + monitoring → One cloud provider**

A provider-wide outage or security incident could therefore affect multiple control layers simultaneously.

### 46 — Correlated Failure Risk

Multiple AI systems may appear operationally independent while sharing the same underlying cloud dependency.

A common provider failure could simultaneously affect:

* AI applications;
* model endpoints;
* storage;
* authentication;
* logging;
* security monitoring;
* backup;
* recovery infrastructure.

Architecture reviews should therefore consider correlated failure rather than evaluating systems only individually.

### 47 — Geographic Concentration

Cloud AI deployments may become concentrated in a single:

* country;
* region;
* availability zone;
* cloud provider;
* legal jurisdiction.

Geographic concentration can increase exposure to:

* regional outages;
* natural disasters;
* regulatory restrictions;
* geopolitical events;
* connectivity failures.

### 48 — Provider Lock-In

Cloud AI lock-in may occur when an organization becomes difficult to migrate because it depends on proprietary:

* APIs;
* model formats;
* orchestration;
* vector databases;
* evaluation frameworks;
* prompts;
* agent workflows;
* identity integrations;
* data formats;
* infrastructure services.

Lock-in should be assessed as part of business resilience and lifecycle governance.

### 49 — AI Portability

Portability refers to the practical ability to move an AI workload to another provider or architecture.

Relevant portability dimensions include:

* data;
* model;
* prompts;
* system instructions;
* embeddings;
* evaluation datasets;
* application code;
* APIs;
* configurations;
* workflows;
* agent tools;
* monitoring;
* security policies.

Technical portability should be distinguished from merely having contractual permission to export data.

### 50 — Alternative Provider Assessment

For material cloud AI dependencies, organizations should assess whether credible alternatives exist.

The assessment may consider:

* technical compatibility;
* model capability;
* security;
* privacy;
* regulatory requirements;
* geographic coverage;
* performance;
* cost;
* migration complexity;
* data portability;
* operational maturity.

The purpose is to understand resilience and exit feasibility rather than automatically requiring multiple providers.

### 51 — Cloud AI Availability Risk

Cloud AI availability risk includes disruption to:

* inference;
* model endpoints;
* training;
* data storage;
* AI APIs;
* identity;
* networking;
* monitoring;
* security services.

Availability requirements should be proportional to business criticality.

### 52 — AI Service-Level Dependency

Service-level requirements should address relevant AI service characteristics, which may include:

* availability;
* latency;
* throughput;
* capacity;
* incident response;
* support;
* maintenance;
* planned changes;
* service restoration.

Traditional infrastructure availability metrics may not fully capture AI service dependencies.

### 53 — Cloud AI Capacity Risk

AI workloads can be sensitive to provider capacity constraints involving:

* GPU availability;
* inference quotas;
* API rate limits;
* regional capacity;
* training capacity;
* storage;
* network throughput.

Capacity limitations may affect both normal operations and emergency recovery.

### 54 — Cloud AI Cost Risk

Cloud AI consumption can generate unpredictable costs through:

* high-volume inference;
* token consumption;
* model training;
* GPU usage;
* data transfer;
* storage;
* vector search;
* agent execution;
* repeated automated requests.

Cost controls should therefore be considered part of operational risk management.

### 55 — Denial-of-Wallet Risk

Denial-of-wallet risk occurs when malicious or uncontrolled AI usage generates excessive cloud consumption and financial impact.

Potential causes include:

* compromised API keys;
* automated loops;
* malicious prompts;
* runaway agents;
* excessive model calls;
* unrestricted user access.

Controls may include quotas, budgets, rate limits, anomaly detection, and automated shutdown mechanisms.

### 56 — Cloud AI Incident Dependency

An incident involving the cloud provider may affect:

* confidentiality;
* integrity;
* availability;
* privacy;
* model behavior;
* AI output;
* credentials;
* logs;
* evidence;
* regulatory obligations.

Provider incident notification should therefore feed into the organization's own incident-management process.

### 57 — Provider Notification vs Organizational Reporting

A cloud provider's notification to its customers does not automatically satisfy the organization's independent incident-notification or regulatory-reporting obligations.

The organization should independently assess:

* incident scope;
* affected systems;
* affected data;
* affected individuals;
* regulatory significance;
* contractual requirements;
* reporting deadlines.

### 58 — Cloud AI Regulatory Dependency

The legal and regulatory implications of cloud AI use depend on factors such as:

* jurisdiction;
* AI use case;
* data involved;
* role of the organization;
* role of the provider;
* sector;
* applicable contracts;
* applicable AI regulation.

Regulatory applicability should therefore be assessed based on the actual processing and deployment context.

### 59 — Legal and Governance Classification

Cloud AI requirements should be classified according to their source.

Possible classifications include:

* applicable law;
* regulatory requirement;
* regulator guidance;
* contractual obligation;
* industry standard;
* voluntary framework;
* internal policy;
* governance control;
* implementation practice;
* recommended practice.

Internal knowledge-base controls should not be represented as provisions of external law unless a specific legal source establishes the requirement.

### 60 — Regulatory Traceability

For material cloud AI systems, organizations should maintain traceability between:

**Regulatory requirement → organizational obligation → risk → control → implementation → evidence → monitoring**

This allows governance teams to demonstrate how external requirements are translated into operational controls.

### 61 — Cloud AI Risk Assessment

A cloud AI risk assessment should consider:

* service purpose;
* business criticality;
* data sensitivity;
* AI model dependency;
* provider dependency;
* identity architecture;
* network architecture;
* integration;
* geographic processing;
* concentration;
* resilience;
* contractual protections;
* regulatory exposure;
* exit feasibility.

The assessment should reflect the actual architecture rather than relying exclusively on generic provider-level risk ratings.

### 62 — Use-Case-Specific Risk

The same cloud AI service can present materially different risk depending on its use case.

For example, using an AI model for:

* internal brainstorming;
* source-code assistance;
* customer support;
* fraud detection;
* medical decision support;
* employment decisions;
* security operations;

may create substantially different risk profiles.

Cloud AI provider assessment should therefore be combined with use-case risk assessment.

### 63 — Risk Tiering

Organizations may establish internal cloud AI risk tiers such as:

* low;
* moderate;
* high;
* critical.

The tier should be based on organizational risk criteria and should not be confused with legally defined AI classifications established by applicable regulation.

### 64 — Critical Cloud AI Provider

An organization may designate a provider as critical where disruption, compromise, or material degradation could significantly affect:

* critical business services;
* regulated operations;
* sensitive information;
* security operations;
* customer services;
* safety-related functions;
* major AI capabilities.

“Critical cloud AI provider” is an organizational risk classification unless a specific regulatory framework defines a different legal classification.

### 65 — Cloud AI Provider Risk Appetite

The organization should define its tolerance for dependency on cloud AI providers.

Risk appetite may address:

* acceptable provider concentration;
* acceptable geographic concentration;
* acceptable outage exposure;
* acceptable data-processing exposure;
* acceptable model dependency;
* acceptable portability limitations;
* acceptable regulatory uncertainty.

Risk appetite should be approved at the appropriate governance level.

### 66 — Risk Acceptance

Risk acceptance should be performed by an authorized risk owner and should consider:

* identified risk;
* business justification;
* control effectiveness;
* residual risk;
* legal constraints;
* contractual requirements;
* compensating controls;
* duration;
* review date.

Risk acceptance should not be used to override mandatory legal or regulatory requirements.

### 67 — Cloud AI Governance Ownership

Ownership should be explicitly assigned across relevant functions.

Potential responsibilities include:

* business owner;
* AI system owner;
* cloud platform owner;
* data owner;
* security;
* privacy;
* legal;
* procurement;
* enterprise architecture;
* risk management;
* compliance;
* internal audit.

Ownership should reflect the organization's operating model.

### 68 — Three Lines Model

Cloud AI governance can be structured using the Three Lines model:

**First Line:** business, engineering, application, and cloud operations responsible for managing risks directly.

**Second Line:** risk, security governance, privacy, compliance, legal, and related oversight functions.

**Third Line:** internal audit providing independent assurance.

The model should clarify accountability without transferring first-line responsibility to oversight functions.

### 69 — Cloud AI Governance Evidence

Relevant evidence may include:

* provider contracts;

* configuration records;
* IAM reviews;

Evidence should be sufficiently specific to the actual service and configuration.

### 70 — Provider Assurance Scope

Provider assurance evidence should be evaluated for:

* scope;
* service coverage;
* geographic coverage;
* assessment period;
* control objectives;
* exceptions;
* limitations;
* customer responsibilities.

A provider certification or assurance report should not automatically be treated as evidence that every customer workload is secure or compliant.

### 71 — Assurance Gap

An assurance gap exists when available provider evidence does not sufficiently address the organization's risk or control requirements.

Examples include:

* certification excludes the AI service being used;
* assurance covers infrastructure but not model behavior;
* report does not cover the required region;
* evidence is outdated;
* customer-configured controls are excluded;
* fourth-party dependencies are not addressed.

Assurance gaps should be documented and managed according to risk.

### 72 — Cloud AI Provider Due Diligence

Due diligence should establish sufficient information about:

* provider identity;

* identity model;

### 73 — Pre-Procurement Cloud AI Assessment

Material cloud AI services should undergo appropriate assessment before production adoption.

Assessment may include:

* security review;
* privacy review;
* architecture review;
* AI risk assessment;
* legal review;
* procurement review;

### 74 — Shadow Cloud AI

Shadow cloud AI occurs when employees or teams deploy or consume AI capabilities without appropriate organizational approval or visibility.

Examples include:

* personal AI API keys;
* unmanaged cloud AI accounts;
* unauthorized model endpoints;
* unsanctioned AI SaaS services;
* unapproved cloud GPU resources.

Shadow AI can bypass security, privacy, procurement, and regulatory controls.

### 83 — Cloud AI Governance Principle

Cloud AI provider risk should be governed as a **technology, AI, data, security, operational, regulatory, contractual, and supply-chain dependency**, rather than treated solely as conventional cloud infrastructure risk.

The organization's control environment should reflect the actual AI services consumed, the data processed, the underlying model and infrastructure dependencies, the shared-responsibility boundary, and the business consequences of provider failure or change.

### 184 — Cloud AI Technical Control Principle

Cloud AI provider risk should be controlled through a combination of **provider assurance, customer configuration, identity security, network security, data protection, model governance, application controls, monitoring, contractual safeguards, and lifecycle management**.
