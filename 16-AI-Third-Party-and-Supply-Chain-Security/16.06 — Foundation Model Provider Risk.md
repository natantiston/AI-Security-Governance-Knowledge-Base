# 16.06 — Foundation Model Provider Risk

## Part 1 — Foundations, Foundation-Model Dependency, Provider Boundaries, Model Governance, Data and Accountability

### 1. Foundation Model Provider Risk

Foundation Model Provider Risk is the risk arising from an organization's dependence on an external provider that develops, hosts, operates, distributes, or materially supports a general-purpose or foundation model used by the organization.

Foundation-model providers may supply models through:

* APIs;
* managed cloud services;
* hosted inference platforms;
* downloadable model artifacts;
* model repositories;
* enterprise platforms;
* embedded AI services.

The risk extends beyond the model itself to the provider's:

* infrastructure;
* training practices;
* model-development lifecycle;
* data practices;
* security controls;
* release process;
* service availability;
* supply chain;
* subcontractors;
* contractual commitments;
* governance practices.

**Control ID: AI-FM-001**

---

### 2. Objective of Foundation Model Provider Governance

The objective is to ensure that reliance on a foundation-model provider remains consistent with the organization's:

* security requirements;
* privacy requirements;
* data-governance requirements;
* AI governance requirements;
* business requirements;
* resilience requirements;
* contractual requirements;
* applicable legal and regulatory obligations.

Governance should address the provider throughout the model lifecycle rather than only during initial procurement.

**Control ID: AI-FM-002**

---

### 3. Foundation Model Provider as a Third-Party Dependency

A foundation-model provider should be treated as a material third-party dependency when the organization's applications, processes, data, or decisions rely on the provider's model capabilities.

Dependency may exist even when:

* the provider is invisible to end users;
* the model is embedded within another SaaS product;
* the organization accesses the model through a cloud platform;
* another vendor manages the application;
* the organization does not directly control the model.

The organization should identify the provider relationship and its position within the dependency chain.

**Control ID: AI-FM-003**

---

### 4. Foundation Model Versus Conventional Software Dependency

A foundation model differs from a conventional software component because its behavior may depend on:

* model parameters;
* training data;
* fine-tuning;
* system instructions;
* inference configuration;
* safety mechanisms;
* provider-side updates;
* routing;
* contextual inputs.

Consequently, software-version management alone may not adequately capture model dependency risk.

**Control ID: AI-FM-004**

---

### 5. Foundation Model Provider Scope

Provider governance should establish exactly what is being obtained from the provider.

Scope may include:

* model access;

* model evaluation;
* training services;
* model hosting;
* model customization;
* agent capabilities;
* tool integration.

Different services may create different risk profiles even when supplied by the same provider.

**Control ID: AI-FM-005**

A commercial platform name may not identify the organization actually responsible for developing or operating the underlying model.

### 10. Direct Foundation Model Dependency

A direct dependency exists when the organization obtains model functionality directly from the foundation-model provider.

Examples include:

* direct model APIs;
* enterprise model subscriptions;
* direct model hosting;
* provider-managed fine-tuning.

Direct relationships generally provide greater contractual visibility but do not necessarily provide greater technical control over the underlying model.

**Control ID: AI-FM-010**

---

### 11. Indirect Foundation Model Dependency

An indirect dependency exists when another service embeds or relies upon a foundation model.

Examples include:

* AI SaaS;
* cloud AI platforms;
* developer tools;
* security products;
* productivity platforms;
* customer-service platforms.

Indirect dependencies can be difficult to discover because the underlying foundation model may not be visible in the primary service interface.

**Control ID: AI-FM-011**

---

### 12. Foundation Model as a Shared Dependency

The same foundation model may support multiple organizational applications.

```text id="p3c8kv"

                 |

                 |
                 +--> Application C
                 |
                 +--> Application D
```

A model-level failure can therefore have an enterprise-wide impact even when individual applications appear independent.

### 13. Foundation Model Business Criticality

The organization should determine how critical the foundation model is to business operations.

Criticality may consider:

* number of dependent applications;
* business processes supported;
* customer impact;
* operational dependency;
* recovery requirements;
* financial impact;
* regulatory significance.

Critical models should receive proportionately stronger governance and resilience controls.

**Control ID: AI-FM-013**

* automated action;
* regulated processing.

Risk assessment should therefore consider the use case rather than treating the model as inherently safe or unsafe.

### 22. Foundation Model Data Minimization

Only data necessary for the approved use case should be provided to the model.

Minimization may involve:

* removing unnecessary identifiers;
* redacting sensitive information;
* reducing context;
* filtering documents;
* limiting retrieval;
* tokenization;
* pseudonymization.

Minimization reduces exposure regardless of whether the provider has contractual restrictions on data use.

**Control ID: AI-FM-022**

### 23. Foundation Model Provider Data Use

The organization should determine how the provider may process customer-provided information.

Relevant questions include:

* Is input content retained?
* Is it used for service operation?
* Is it used for abuse monitoring?

* Is it used for training?
* Is it accessible to provider personnel?
* Is it processed by subprocessors?

Provider documentation and contractual terms should be evaluated together.

Training-use governance should distinguish:

* contractual restrictions;

* organizational policy;
* applicable legal requirements.

### 28. Foundation Model Model Portability

Portability may depend on:

* API compatibility;
* prompt compatibility;
* model behavior;
* context handling;
* tool calling;
* evaluation portability;
* application architecture;
* alternative model availability.

Behavioral differences should be considered during migration planning.

* proprietary model features;
* proprietary embeddings;
* provider-specific tool frameworks;
* proprietary fine-tuning;
* provider-specific evaluation;
* provider-specific safety controls.

Architecture should identify dependencies that make provider replacement difficult.

### 30. Foundation Model Provider Concentration

Concentration risk exists when multiple business services rely on the same foundation-model provider or model family.

For example:

```text id="u5r9cw"
                Provider A
                    |
        +-----------+-----------+
        |           |           |
      Model 1     Model 2     Model 3
        |           |           |
        v           v           v
      App A       App B       App C
```

An incident affecting Provider A could therefore affect several apparently independent applications.

**Control ID: AI-FM-030**

---

### 31. Foundation Model Effective Diversification

Using multiple model names does not necessarily establish meaningful diversification.

Models may share:

* the same provider;
* the same infrastructure;
* the same underlying organization;
* the same geographic dependency;
* common supply-chain components.

Diversification should therefore be assessed based on actual independence rather than model count.

**Control ID: AI-FM-031**

* authorization;
* access control;
* data protection;
* transaction validation;
* security policy enforcement.

An AI model may generate or recommend an action, but conventional deterministic controls should govern actions where required.

### 46. Foundation Model Prompt-Injection Risk

Prompt injection can cause a model to follow instructions embedded within untrusted content.

Potential sources include:

* documents;
* web pages;
* emails;
* retrieved content;
* user inputs;
* tool responses.

Mitigations may include:

* content separation;
* instruction hierarchy;
* retrieval controls;
* output validation;
* tool authorization;
* human approval for high-impact actions.

**Control ID: AI-FM-046**

---

### 47. Foundation Model Tool-Use Risk

Foundation models increasingly support tool or function invocation.

Tools may provide access to:

* databases;
* cloud services;
* code execution;
* email;
* ticketing;
* financial systems;
* administrative APIs.

The security boundary should therefore include both the model and every downstream tool it can influence.

**Control ID: AI-FM-047**

---

### 48. Foundation Model Human Oversight

Human oversight should be proportionate to the consequences of model error.

Higher-impact uses may require:

* human review;
* approval;
* escalation;
* transaction confirmation;
* exception handling;
* ability to override model recommendations.

Human oversight should not be treated as meaningful if the human cannot understand, challenge, or prevent the relevant action.

### 50. Foundation Model Governance Principle

Foundation-model provider governance should recognize that **the model, provider, infrastructure, data, application, downstream tools, and supply chain form an interconnected dependency system**.

The organization should therefore maintain visibility into:

* who provides the model;
* which model is actually used;
* what data reaches the provider;
* how provider changes affect behavior;
* which applications depend on the model;
* what downstream tools can be influenced;
* how provider concentration affects resilience;
* what evidence supports provider assurance;
* what controls remain the organization's responsibility.

Foundation-model provider governance should distinguish provider-controlled risks from customer-controlled risks and should preserve accountability for the organization's own use of the model.

**Control ID: AI-FM-050**

### Core Principles

1. **Provider-Dependency Principle** — A foundation-model provider should be treated as a third-party dependency when organizational operations materially rely on it.
2. **Model-Identity Principle** — Material model dependencies should be identifiable and traceable.
3. **Use-Case Principle** — Foundation-model risk depends on how the model is used, not solely on the model itself.
4. **Capability Principle** — Model capabilities should be assessed according to the risks they create.
5. **Trust-Boundary Principle** — The provider represents an external trust boundary when organizational information is transmitted to the service.
6. **Data-Boundary Principle** — Data flows into, through, and out of foundation-model services should be understood.
7. **Minimization Principle** — Only necessary information should be exposed to the foundation-model provider.
8. **Data-Use Principle** — Provider data-use practices should be understood and governed.
9. **Retention Principle** — Model-input and model-output retention should be assessed according to applicable requirements.
10. **Portability Principle** — Practical portability should be assessed rather than assumed.
11. **Lock-In Principle** — Provider-specific dependencies should be identified before they become difficult to reverse.
12. **Concentration Principle** — Multiple applications may create common dependency on one foundation-model provider.
13. **Diversification Principle** — Model count does not necessarily equal effective provider independence.
14. **Identity Principle** — Provider API and administrative identities should follow least-privilege principles.
15. **API-Security Principle** — Foundation-model interfaces should be protected as security-sensitive APIs.
16. **Change Principle** — Material provider and model changes should be assessed.
17. **Behavioral-Assurance Principle** — Model availability does not prove behavioral stability.
18. **Evaluation Principle** — Material use cases should have appropriate evaluation and regression-testing mechanisms.
19. **Tool-Authorization Principle** — Model access to downstream tools should be explicitly controlled.
20. **Accountability Principle** — Provider assurance does not transfer responsibility for the organization's own use of the foundation model.

## Part 2 — Foundation Model Due Diligence, Security Controls, Model Assurance, Data Governance and Provider Risk

### 51. Foundation Model Provider Due Diligence

Foundation-model provider due diligence should establish whether the provider can support the organization's intended use case within its security, privacy, resilience, contractual, and governance requirements.

Due diligence should consider:

* provider identity;
* model identity;
* service architecture;
* security controls;
* data practices;
* model lifecycle;
* provider assurance;
* incident management;
* resilience;
* subcontractors;
* contractual protections;
* exit capability.

The depth of due diligence should correspond to the materiality and criticality of the dependency.

**Control ID: AI-FM-051**

---

### 52. Foundation Model Organizational Due Diligence

Organizational due diligence should assess the provider's ability to operate and support the service.

Potential areas include:

* organizational structure;
* security governance;
* AI governance;
* risk management;
* privacy governance;
* incident management;
* business continuity;
* personnel security;
* provider financial and operational stability.

The purpose is to understand the provider as an organization rather than evaluating only the technical model.

### Core Principles

1. **Due-Diligence Principle** — Foundation-model providers should undergo proportionate due diligence before material use.
2. **Lifecycle Principle** — Provider and model governance should cover development, deployment, change, and retirement.

4. **Evaluation Principle** — Provider model evaluation should be considered as one input into organizational assurance.

7. **Version Principle** — Model versions should be traceable where technically possible.
8. **Data-Processing Principle** — Model inputs and outputs should be governed as organizational data.
9. **Minimization Principle** — Unnecessary sensitive information should not be transmitted to external models.
10. **Retention Principle** — Provider retention should be understood and governed.
11. **Encryption Principle** — Relevant data should be appropriately protected in transit and at rest.
12. **Identity Principle** — Provider identities should be attributable and least privileged.

14. **Tool-Authorization Principle** — Model access to tools should be explicitly constrained.
15. **Agent-Governance Principle** — Agentic model capabilities require governance beyond ordinary model invocation.

18. **Resilience Principle** — Material model dependencies should have proportionate continuity and recovery arrangements.

Foundation-model provider governance should treat the model dependency as a continuously changing risk relationship.

### Core Principles

1. **Continuous-Monitoring Principle** — Foundation-model dependencies should be monitored throughout their lifecycle.
2. **Change-Assessment Principle** — Material model, provider, configuration, data, or architecture changes should be assessed.
3. **Behavioral-Assurance Principle** — Model availability does not establish behavioral stability.
4. **Regression Principle** — Material changes should be evaluated against established behavioral and security baselines.
5. **Configuration-Integrity Principle** — Approved model configurations should be protected against unmanaged drift.
6. **Identity-Monitoring Principle** — Provider and application identities should remain subject to continuous oversight.
7. **Data-Boundary Principle** — Material changes in model data flows should be identified and assessed.
8. **Subprocessor-Principle** — Material provider and fourth-party dependencies should remain visible.
9. **Incident-Principle** — Provider incidents should be assessed according to the organization's own impact and obligations.
10. **Evidence-Principle** — Monitoring should generate reliable evidence for governance and assurance.
11. **Regulatory-Applicability Principle** — Regulatory developments should be evaluated for actual applicability.
12. **Concentration-Principle** — Provider and model concentration should be evaluated across the complete dependency chain.
13. **Resilience-Principle** — Recovery capabilities should be tested rather than merely documented.
14. **Fallback-Principle** — Material model dependencies should have appropriate fallback or graceful-degradation capabilities.
15. **Portability-Principle** — Model migration should consider behavioral as well as technical portability.
16. **Exit-Readiness Principle** — Critical foundation-model dependencies should have realistic exit arrangements.
17. **Assurance-Principle** — Provider assurance should be evaluated for scope, currency, independence, and limitations.
18. **Automation Principle** — Automated model controls should be governed, tested, and auditable.
19. **Human-Accountability Principle** — Human accountability should remain for material risk decisions.
20. **Continuous-Assurance Principle** — Monitoring, testing, incidents, assurance, and risk decisions should operate as an integrated lifecycle.

### 400. Foundation Model Provider Governance Principle

Foundation-model provider governance should recognize that **provider risk, model risk, application risk, data risk, infrastructure risk, supply-chain risk, and enterprise dependency are related but distinct governance domains**.

The following distinctions should remain explicit:

* provider certification ≠ complete assurance over the organization's model use;
* provider security controls ≠ customer security controls;
* model availability ≠ model behavioral stability;
* model version ≠ behavioral equivalence;
* provider count ≠ effective diversification;
* alternative model ≠ tested substitute;
* data export ≠ practical portability;
* documented recovery ≠ tested recovery;
* contractual rights ≠ demonstrated operational capability;
* provider notification ≠ the organization's own legal reporting obligation;
* regulatory mapping ≠ regulatory applicability;
* internal governance control ≠ statutory or regulatory requirement;
* model evaluation ≠ assurance over every production use case;
* model safety controls ≠ complete application security;
* human oversight ≠ effective oversight unless the human can meaningfully intervene.

The enterprise objective is therefore to maintain an evidence-based, continuously updated understanding of foundation-model dependencies while preserving clear accountability for the organization's own deployment, data, security controls, business decisions, and risk acceptance.

**Control ID: AI-FM-400**

### Core Principles

1. **Enterprise-Governance Principle** — Foundation-model dependencies should operate within a defined enterprise governance framework.
2. **Ownership Principle** — Material model and provider risks should have accountable owners.
3. **Three-Lines Principle** — Operational ownership, oversight, and independent assurance should remain appropriately separated.
4. **Risk-Appetite Principle** — Model-provider decisions should operate within defined risk appetite and tolerance.
5. **Inventory Principle** — Material models and provider dependencies should remain visible in an enterprise inventory.
6. **Lifecycle Principle** — Governance should cover model onboarding, deployment, change, operation, reassessment, and retirement.
7. **Architecture Principle** — Model architecture should explicitly address trust boundaries, dependencies, data flows, tools, and attack paths.
8. **Data-Protection Principle** — Sensitive information should remain within defined and controlled processing boundaries.
9. **Least-Privilege Principle** — Models, applications, agents, identities, and tools should receive only required authority.
10. **Defense-in-Depth Principle** — Foundation-model security should use multiple complementary control layers.
11. **Resilience Principle** — Material model dependencies should have proportionate recovery and fallback capabilities.
12. **Concentration Principle** — Provider and model concentration should be evaluated across the complete dependency chain.
13. **Portability Principle** — Practical technical and behavioral portability should be assessed.
14. **Exit Principle** — Critical foundation-model dependencies should have realistic exit arrangements.
15. **Assurance Principle** — Provider assurance should be supplemented by customer-side validation where necessary.
16. **Evidence Principle** — Material decisions should be supported by current, relevant, and traceable evidence.
17. **Regulatory-Traceability Principle** — Legal requirements should remain distinguishable from internal governance practices.
18. **Automation Principle** — Governance automation should remain controlled, auditable, and testable.
19. **Human-Accountability Principle** — Automation should not eliminate human accountability for material governance decisions.
20. **Continuous-Improvement Principle** — Monitoring, incidents, testing, assurance, and audit findings should continuously improve the foundation-model control environment.
