# 16.06 — Foundation Model Provider Risk

## Part 1 — Foundations, Provider Classification, Model Dependency and Risk Architecture

### 1 — Foundation Model Provider Risk Definition

Foundation model provider risk is the risk arising from an organization's dependency on an external provider for a general-purpose or broadly reusable AI model that serves as the underlying model for one or more applications, services, products, or AI workflows.

Foundation model providers may supply models through:

* APIs;
* managed cloud services;
* hosted endpoints;
* model platforms;
* downloadable model artifacts;
* enterprise AI platforms;
* integrated AI applications.

The risk extends beyond conventional vendor risk because the provider can materially influence model behavior, availability, security characteristics, data processing, model lifecycle, safety controls, and downstream AI functionality.

### 2 — Foundation Model Definition

A foundation model is a model trained on broad data at scale and designed to support adaptation or use across multiple tasks and applications.

Examples of capabilities that may be provided through foundation models include:

* text generation;
* reasoning;
* coding;
* image generation;
* image understanding;
* speech;
* multimodal processing;
* document analysis;
* classification;
* summarization;
* agentic task execution.

The governance assessment should focus on the actual model and service being consumed rather than assuming that all foundation models present identical risks.

### 3 — Foundation Model Provider

A foundation model provider may be responsible for:

* model development;
* training;
* model evaluation;
* model release;
* model hosting;
* API delivery;
* safety mechanisms;
* model updates;
* model retirement.

The provider's exact role should be established because responsibility may be distributed across multiple organizations.

### 4 — Foundation Model Provider vs Cloud Provider

A cloud provider may host or distribute a foundation model without being the original model developer.

For example:

**Enterprise → Cloud AI platform → Foundation model provider**

The organization should identify both the cloud platform dependency and the underlying foundation-model dependency where material.

### 5 — Direct Foundation Model Dependency

A direct dependency exists when an organization directly consumes a foundation model from its provider.

Examples include:

* calling a model API;
* using a provider-managed model endpoint;
* deploying a provider's model through an enterprise AI platform.

### 6 — Indirect Foundation Model Dependency

An indirect dependency exists when an application consumes a model through another provider.

Example:

**Enterprise → AI SaaS → Cloud provider → Foundation model provider**

The organization may therefore depend on a foundation model without having a direct contractual relationship with its developer.

### 7 — Foundation Model Dependency Mapping

Material foundation-model dependencies should be mapped across:

* business process;
* AI use case;
* application;
* model;
* model provider;
* hosting provider;
* cloud infrastructure;
* data;
* integrations.

This mapping enables impact analysis when the underlying model changes or becomes unavailable.

### 8 — Foundation Model Provider Classification

Organizations may classify foundation model providers according to their role, such as:

1. Model developer
2. Model owner
3. Model licensor
4. Model host
5. API provider
6. Cloud marketplace provider
7. Model distributor
8. Fine-tuning provider
9. Managed inference provider
10. AI platform provider

A single organization may perform several roles.

### 9 — Model Distribution Model

The organization should identify how the foundation model is obtained.

Possible models include:

* direct API;
* managed cloud endpoint;
* marketplace;
* downloadable artifact;
* self-hosted model;
* managed private deployment;
* embedded model within SaaS.

Each distribution model creates different control responsibilities.

### 10 — Hosted Model Dependency

A hosted model remains under provider-controlled infrastructure while the customer consumes its capabilities.

The organization should assess:

* provider availability;
* data processing;
* access controls;
* model changes;
* service limits;
* provider support;
* contractual protections.

### 11 — Downloaded Model Dependency

A downloadable foundation model may reduce direct runtime dependency on the original provider but introduce additional responsibilities for:

* model artifact integrity;
* infrastructure;
* patching;
* model lifecycle;
* security testing;
* licensing;
* deployment.

Reduced provider dependency does not automatically mean reduced overall risk.

### 12 — Self-Hosted Foundation Model

Self-hosting transfers certain responsibilities from the provider to the organization.

The organization may become responsible for:

* infrastructure security;
* model artifact protection;
* deployment;
* access control;
* vulnerability management;
* monitoring;
* updates;
* incident response.

### 13 — Managed Foundation Model

A managed foundation model is operated by an external provider on infrastructure controlled by that provider or its platform.

The organization should identify the provider-controlled and customer-controlled portions of the environment.

### 14 — Foundation Model Criticality

Foundation model criticality should reflect the consequences of model disruption, degradation, compromise, or retirement.

Criticality may consider:

* business-process dependency;
* customer impact;
* regulatory significance;
* safety implications;
* data sensitivity;
* substitution difficulty;
* model uniqueness.

### 15 — Model Criticality vs Provider Criticality

The criticality of a model and the criticality of its provider are related but not necessarily identical.

An organization may depend critically on a particular model while using several services from the same provider that have different business importance.

Foundation model provider risk should consider:

* cybersecurity;

* privacy;

* AI safety;
* reliability;
* availability;
* intellectual property;
* licensing;

### 17 — Model Behavior Dependency

Applications may become dependent on specific model behavior.

Dependencies can include:

* response structure;
* reasoning behavior;
* refusal behavior;
* context handling;
* tool use;
* token limits;
* latency;
* output formatting.

A model change may therefore create application-level impact even when the provider maintains the same API.

### 18 — Model Capability Dependency

Organizations may become dependent on specialized model capabilities such as:

* multimodal reasoning;
* coding;
* long-context processing;
* structured output;
* function calling;
* vision;
* speech;
* domain-specific performance.

Substitution should therefore be assessed against actual capability requirements.

### 19 — Model Version Dependency

A production application may depend on a specific model version.

The organization should identify:

* model name;
* version;
* release date where relevant;
* retirement status;
* replacement model;
* compatibility requirements.

### 20 — Model Family Dependency

Some applications depend on a model family rather than a single version.

Even so, changes within the model family may affect:

* accuracy;
* latency;
* output;
* safety;
* cost;
* application behavior.

### 21 — Model Lifecycle Dependency

Foundation models have lifecycles that may include:

**Development → Release → Adoption → Update → Deprecation → Retirement**

Organizations should understand how lifecycle events affect dependent systems.

### 22 — Model Deprecation Risk

Model deprecation can require:

* application modification;
* regression testing;
* model evaluation;
* prompt modification;
* security reassessment;
* migration.

Material applications should identify their exposure to model retirement.

### 23 — Model Retirement Risk

Retirement creates a stronger dependency event than routine model updating because the original capability may become unavailable.

Organizations should maintain appropriate migration or fallback strategies for critical dependencies.

### 24 — Model Change Risk

Foundation model changes may affect:

* output quality;
* safety behavior;
* security;
* hallucination;
* refusal patterns;
* tool invocation;
* latency;
* cost;
* compatibility.

### 25 — Model Change Notification

Where available, organizations should seek appropriate provider notification concerning material model changes.

Notification expectations should be established through available provider capabilities and contractual arrangements.

### 26 — Model Change Assessment

Material model changes should be assessed against:

* business use case;
* security;
* privacy;
* AI risk;
* regulatory requirements;
* application compatibility.

### 27 — Model Regression Testing

Regression testing should evaluate whether a new model version continues to meet defined:

* functional;
* security;
* safety;
* reliability;
* performance

requirements.

### 28 — Model Approval

Organizations may establish an internal approval process for foundation models used in production.

Approval criteria may include:

* provider assurance;
* security;
* privacy;
* licensing;
* performance;
* risk;
* regulatory applicability.

### 29 — Approved Model Registry

Organizations may maintain a registry of approved foundation models.

Registry information may include:

* model;
* provider;
* version;
* approved use cases;
* permitted data;
* criticality;

* approval date;
* retirement date.

### 30 — Model Allowlist

A model allowlist may restrict production applications to approved foundation models.

This can reduce uncontrolled model adoption.

### 31 — Model Denylist

A denylist may identify models that should not be used because of:

* security concerns;
* unsupported licensing;
* insufficient assurance;
* prohibited data-processing characteristics;
* unacceptable risk.

### 32 — Foundation Model Provider Assurance

Provider assurance should be assessed according to the services and models actually being used.

Relevant evidence may include:

* independent assurance reports;
* certifications;
* security documentation;
* model documentation;
* testing summaries;
* contractual commitments.

### 33 — Assurance Scope

Assurance should be evaluated for:

* specific model;
* specific service;
* applicable region;
* relevant environment;
* assessment period;
* control scope.

### 34 — Assurance Gap

An assurance gap exists where available provider evidence does not adequately address the organization's identified risk.

Examples include:

* infrastructure assurance without model assurance;
* outdated evidence;
* incomplete service coverage;
* unclear data-processing practices.

### 35 — Provider Transparency

The organization should seek sufficient transparency concerning:

* model identity;
* model lifecycle;
* training practices where relevant;
* data-processing practices;
* security controls;
* model limitations;
* known dependencies.

Transparency requirements should be proportionate to risk and available provider information.

### 36 — Model Documentation

Model documentation may provide information about:

* intended use;
* limitations;
* capabilities;
* evaluation;
* safety considerations;
* performance characteristics.

Documentation should be treated as evidence to evaluate, not automatically as proof of suitability.

### 37 — Model Card or Equivalent Documentation

Where available, model cards or equivalent documentation can support assessment of:

* intended use;
* limitations;
* risks;
* evaluation methods;
* known constraints.

### 38 — Training Data Transparency

Organizations may seek information about the provenance or categories of training data where relevant to:

* legal;
* intellectual-property;
* privacy;
* security;
* model-risk

assessment.

The level of transparency available varies substantially between providers and models.

### 39 — Training Data Provenance Risk

Limited knowledge of training-data provenance may create uncertainty concerning:

* intellectual-property exposure;
* privacy;
* bias;
* model behavior;
* data provenance.

The organization should document material uncertainty rather than assume that unknown provenance is either safe or unsafe.

### 40 — Training Data Quality Risk

Foundation model performance can be affected by characteristics of training data such as:

* quality;
* completeness;
* representativeness;
* duplication;
* contamination;
* outdated information.

Organizations should consider these factors where model performance is material.

### 41 — Training Data Poisoning Risk

Training-data poisoning involves malicious or harmful manipulation of training data intended to influence model behavior.

Potential consequences include:

* biased outputs;
* hidden behaviors;
* degraded accuracy;
* targeted responses.

### 42 — Model Supply-Chain Risk

Foundation models may depend on:

* datasets;
* pretrained models;
* open-source libraries;
* training infrastructure;
* third-party tools;
* external evaluators;
* model hosting.

These dependencies form part of the model supply chain.

### 43 — Model Artifact Integrity

Where model artifacts are downloaded or transferred, organizations should assess their integrity.

Controls may include:

* trusted repositories;
* cryptographic hashes;
* signatures;
* access control;
* provenance records.

### 44 — Model Provenance

Model provenance records may identify:

* model origin;
* provider;
* version;
* source;
* modifications;
* fine-tuning;
* deployment history.

Provenance supports traceability and incident investigation.

### 45 — Model Modification

A foundation model may be modified through:

* fine-tuning;
* adapters;
* quantization;
* pruning;
* safety layers;
* system configuration.

Modified models should be distinguishable from the original model where the difference affects risk.

### 46 — Fine-Tuned Foundation Model

Fine-tuning can create a model that behaves differently from the original foundation model.

The organization should therefore assess:

* training data;
* fine-tuning process;
* security;
* model integrity;
* evaluation;
* lifecycle.

### 47 — Model Adapter Dependency

Adapters such as parameter-efficient fine-tuning components may materially affect model behavior.

Their provenance, integrity, and compatibility should be managed.

### 48 — Model Quantization Risk

Quantization can change model behavior and performance.

For material applications, organizations should validate whether quantization affects:

* accuracy;
* security;
* reliability;
* latency.

### 49 — Model Wrapper Dependency

Wrappers may affect:

* prompts;

### 50 — Model Routing Dependency

AI platforms may dynamically route requests among multiple models.

Organizations should determine whether routing can change:

* model identity;
* processing location;
* data handling;
* output behavior;
* risk classification.

### 51 — Dynamic Model Selection

Where the provider can automatically select or replace models, the organization should understand the governance implications.

Material applications may require controls that prevent unexpected model substitution.

### 52 — Model Substitution Risk

Unexpected model substitution can change:

* behavior;
* security;
* performance;
* regulatory characteristics;
* data processing.

Model substitution should therefore be governed according to materiality.

Access to model endpoints should be controlled according to:

* identity;

* data sensitivity.

Access to foundation models may be segmented by:

* business unit;

Where multiple customers share provider infrastructure, the organization should assess available controls for appropriate logical tenant isolation.

* model training;

### 61 — Secondary Data Use

Potential secondary uses of customer data should be identified and assessed against organizational requirements.

### 63 — Abuse Monitoring Data

Providers may process certain information for abuse prevention or security monitoring.

### 66 — Data Deletion

* deletion;

Potential locations include:

* inference;

### 68 — Cross-Border Processing

Foundation-model services may process information across multiple jurisdictions.

Organizations should assess relevant cross-border processing according to applicable requirements.

### 69 — Subprocessor Dependency

Foundation-model providers may use subprocessors for:

* infrastructure;
* security;
* support;
* data processing;
* content moderation.

Material subprocessors should be identified and governed appropriately.

### 70 — Fourth-Party Model Dependency

A provider may itself depend on:

* cloud infrastructure;
* GPU suppliers;
* third-party models;
* external datasets;

Availability risk may arise from:

* provider outages;
* regional failures;

Foundation-model services may impose:

* token limits;

Applications dependent on provider rate limits may experience degraded service when demand exceeds available capacity.

### 74 — Model Latency Dependency

Model latency may affect customer-facing and operational applications.

### 75 — Model Cost Dependency

Foundation-model pricing may depend on:

* input tokens;

* model type;
* compute;

Cost changes can therefore affect business viability and architecture.

### 76 — Pricing Change Risk

Provider pricing changes may affect:

* operating costs;
* model selection;
* application architecture;

Material commercial changes should be considered during provider and model reviews.

Uncontrolled model consumption can generate excessive financial cost.

Potential causes include:

* compromised credentials;
* malicious usage;
* runaway automation;

### 78 — Model Abuse Risk

Foundation models can be abused to:

* generate malicious content;
* automate attacks;
* process unauthorized information;
* consume excessive resources.

Provider and customer abuse controls should be evaluated according to the use case.

### 79 — Model Extraction Risk

Some attack techniques attempt to infer or reproduce information about a model through repeated interaction.

Organizations using or exposing model endpoints should consider whether model extraction creates material risk.

### 80 — Prompt Injection Risk

Applications using foundation models may be exposed to malicious instructions embedded within user input or external content.

Controls should distinguish:

**trusted instructions** from **untrusted data**.

### 81 — Indirect Prompt Injection

Indirect prompt injection can occur when a model processes external content containing instructions designed to influence model behavior.

Potential sources include:

* websites;
* documents;
* emails;
* retrieved records.

### 82 — Retrieval-Augmented Foundation Model Risk

RAG architectures introduce dependencies on:

* document repositories;
* retrieval systems;
* vector stores;
* access controls;
* embeddings.

Security controls should protect the complete retrieval chain.

### 83 — Embedding Dependency

Foundation-model applications may use embeddings for:

* retrieval;
* semantic search;
* classification;
* recommendations.

Embeddings should be governed according to the sensitivity of the source information.

### 84 — Vector Store Dependency

A foundation model may depend on an external vector database for contextual information.

Failure or compromise of the vector store can affect:

* availability;
* confidentiality;
* integrity;
* AI output.

### 85 — Grounding Dependency

AI outputs may depend on external grounding sources.

The organization should assess whether grounding information is:

* authoritative;
* current;
* protected;
* appropriately authorized.

### 86 — Hallucination Risk

Foundation models may generate plausible but inaccurate information.

The impact depends on the use case and should be controlled where inaccurate outputs could cause material consequences.

### 87 — Output Validation

Output validation may include:

* deterministic rules;
* schema validation;
* source verification;
* retrieval checks;
* human review;
* domain-specific validation.

### 88 — Structured Output Dependency

Applications may depend on a model returning a specific structured format.

Model updates can break downstream processing even when the model remains generally functional.

### 89 — Function Calling Dependency

Applications may rely on foundation-model function-calling capabilities to invoke tools.

Changes in model behavior may affect:

* tool selection;
* parameter generation;
* authorization;
* execution frequency.

### 90 — Tool Invocation Risk

Foundation models connected to tools may create actions beyond simple content generation.

Tool permissions should therefore be independently governed.

### 91 — Agentic Foundation Model Risk

Foundation models used within agents may gain the ability to:

* execute actions;
* access systems;
* retrieve information;
* communicate externally;
* modify data.

The risk profile increases when model output can directly trigger consequential actions.

### 92 — Agent Privilege Boundary

The privileges available to an AI agent should be limited to those necessary for its approved purpose.

### 93 — Human Approval Boundary

Where appropriate, consequential model-driven actions should require human approval before execution.

### 94 — Model Safety Dependency

Applications may rely partly on provider-level:

* content filters;
* safety classifiers;
* refusal mechanisms;
* abuse detection.

These controls should be assessed for suitability rather than assumed to provide complete application security.

### 95 — Safety Control Dependency

A provider safety mechanism may not address application-specific risks such as:

* authorization;
* data leakage;
* business logic abuse;
* unsafe tool execution.

Customer-side controls may therefore remain necessary.

### 96 — Model Reliability

Reliability should consider whether the model performs consistently enough for its approved use case.

Relevant factors may include:

* accuracy;
* reproducibility;
* latency;
* availability;
* output consistency.

### 97 — Model Evaluation

Evaluation may cover:

* accuracy;
* security;
* safety;
* robustness;
* bias;
* hallucination;
* application compatibility.

### 98 — Model Benchmarking

Benchmark results can support comparison of model capabilities, but generic benchmarks should not automatically be treated as proof of suitability for an organization's specific use case.

### 99 — Use-Case Evaluation

### 106 — Model Rollback

### 107 — Rollback Feasibility

Rollback capability depends on:

### 110 — Model Portability

Model portability should be evaluated according to whether the application can practically move to another model or provider.

### 111 — Provider Lock-In

Foundation-model lock-in can result from dependence on:

* proprietary APIs;
* model-specific prompts;
* proprietary tools;
* provider-specific orchestration;

* specialized model behavior.

Prompts may become optimized for a particular model and perform poorly after migration.

Prompt portability should therefore be evaluated for critical systems.

### 113 — Evaluation Lock-In

* APIs;
* SDKs;
* response formats;
* tool interfaces;
* authentication.

### 115 — Data Lock-In

AI applications may become dependent on provider-specific storage or data structures.

### 116 — Embedding Lock-In

Embeddings generated using one model may not be directly interchangeable with embeddings generated by another model.

Migration may therefore require re-embedding source data.

### 117 — Model Marketplace Dependency

* marketplace provider;

Foundation-model use may create intellectual-property questions involving:

* training data;

### 120 — Generated Code Risk

Where foundation models generate source code, organizations should apply appropriate:

### 121 — Provider Contract Requirements

Material foundation-model relationships should include appropriate contractual requirements addressing relevant:

* security;
* data processing;

### 124 — Provider Exit Requirement

Material provider agreements should address practical termination and data-export requirements where appropriate.

### 125 — Foundation Model Governance Principle

Foundation model provider risk should be governed as a **model, data, cybersecurity, AI safety, operational, regulatory, intellectual-property, supply-chain, concentration, and lifecycle dependency**.

The organization's assessment should identify the actual foundation model, provider roles, hosting arrangement, data-processing model, model lifecycle, downstream dependencies, assurance limitations, and practical substitution or exit requirements.

### 126 — Foundation Model Provider Responsibility Principle

Responsibility should be explicitly allocated among the:

* foundation model provider;
* cloud provider;
* AI platform;
* application provider;
* organization;
* application owner;
* security;
* privacy;
* AI governance functions.

Provider responsibility should not be assumed to eliminate customer responsibility for risks arising from the organization's own deployment and use.

### 127 — Foundation Model Evidence Principle

Provider documentation, certifications, model documentation, security attestations, and other assurance evidence should be evaluated according to:

* scope;
* currency;
* applicability;
* limitations;
* actual service configuration.

Such evidence should not automatically be treated as universal proof of security, compliance, or suitability.

### 128 — Foundation Model Risk Decision Principle

Model selection decisions should consider the organization's:

* business purpose;
* risk profile;
* data;
* security requirements;
* regulatory obligations;
* operational requirements;
* resilience requirements;
* portability needs.

## Part 2 — Foundation Model Due Diligence, Security, Data Protection, Model Assurance and Technical Controls

### 129 — Foundation Model Provider Due Diligence

Foundation model provider due diligence should determine whether the provider, model, service architecture, and contractual environment are appropriate for the intended use case.

Assessment should consider:

* provider identity;
* model identity;
* model lifecycle;
* data processing;
* security;
* privacy;
* model assurance;
* licensing;
* availability;
* resilience;
* supply chain;
* regulatory exposure;
* portability.

### 130 — Due Diligence Proportionality

The depth of assessment should be proportional to:

* model criticality;
* business impact;
* data sensitivity;
* regulatory exposure;
* degree of model autonomy;
* provider dependency;
* substitution difficulty.

A model used for low-risk experimentation does not necessarily require the same assessment depth as a model supporting a critical business process.

### 131 — Provider Legal Entity Assessment

The organization should identify the relevant legal entities associated with:

* model development;
* model ownership;
* contracting;
* hosting;
* data processing;
* support.

This supports contractual and accountability analysis.

### 132 — Model Identity Verification

The organization should establish the exact model being assessed.

Relevant information may include:

* model name;
* version;
* model family;
* deployment identifier;
* provider;
* hosting arrangement.

Generic provider-level approval should not automatically imply approval of every model offered by that provider.

### 133 — Model Service Identification

The assessment should identify whether the organization is consuming the model through:

* direct API;
* managed cloud service;
* AI platform;
* marketplace;
* SaaS;
* self-hosted deployment.

The delivery mechanism affects the applicable control boundary.
