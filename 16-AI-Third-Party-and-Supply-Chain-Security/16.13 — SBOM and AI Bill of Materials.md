# 16.13 — SBOM and AI Bill of Materials

## Part 1 — Foundations, SBOM, AI BOM, Component Inventory, Dependency Visibility and Governance

### 1. SBOM and AI BOM Risk

Software Bill of Materials (SBOM) and AI Bill of Materials (AI BOM) governance provides visibility into the components and dependencies that constitute an AI system.

AI systems may depend on:

* application software;
* open-source packages;
* AI frameworks;
* model runtimes;
* models;
* model adapters;
* datasets;
* APIs;
* containers;
* infrastructure;
* third-party services.

Incomplete component visibility can make vulnerability management, incident response, licensing analysis, provenance verification, and supply-chain risk management more difficult.

**Control ID: AI-BOM-001**

---

### 2. Objective of SBOM and AI BOM Governance

The objective is to establish reliable visibility into material components of an AI system and their relationships.

Governance should support:

* component identification;
* dependency analysis;
* vulnerability management;
* provenance;
* license management;
* change management;
* incident response;
* resilience;
* assurance.

**Control ID: AI-BOM-002**

---

### 3. Software Bill of Materials

An SBOM is a structured inventory of software components associated with an application or software artifact.

Depending on the implementation, an SBOM may identify:

* component name;
* version;
* supplier;
* dependency relationship;
* package identifier;
* license;
* vulnerability information.

SBOM content and format should be appropriate to the organization's use case.

**Control ID: AI-BOM-003**

---

### 4. AI Bill of Materials

An AI BOM extends component visibility beyond conventional software dependencies to material AI-specific components.

An AI BOM may identify:

* models;
* model versions;
* datasets;
* AI frameworks;
* model runtimes;
* adapters;
* embeddings;
* vector stores;
* AI APIs;
* AI services;
* software dependencies.

An AI BOM should complement rather than automatically replace an SBOM.

**Control ID: AI-BOM-004**

---

### 5. AI BOM Scope

The scope of an AI BOM should be defined according to the AI system being governed.

Potential scope includes:

```text
AI Application
      |
      +-- Application Code
      |
      +-- Software Dependencies
      |
      +-- AI Framework
      |
      +-- Model
      |
      +-- Model Adapter
      |
      +-- Dataset
      |
      +-- Runtime
      |
      +-- External AI API
      |
      +-- Infrastructure
```

**Control ID: AI-BOM-005**

---

### 6. AI System Component

An AI system component is an identifiable element that contributes materially to the system's operation.

Components may include:

* software;
* model artifacts;
* datasets;
* services;
* infrastructure;
* configuration elements.

The organization should define what constitutes a material component for its AI BOM methodology.

**Control ID: AI-BOM-006**

---

### 7. Direct Dependency

A direct dependency is a component explicitly required by an AI application or system.

Examples include:

* an AI framework directly imported by an application;
* a model directly configured for inference;
* an external AI API directly called by the application.

**Control ID: AI-BOM-007**

---

### 8. Transitive Dependency

A transitive dependency is a dependency introduced indirectly through another component.

For example:

```text
AI Application
      |
AI Framework
      |
Package A
      |
Package B
      |
Package C
```

The application may not directly reference Package C, but Package C may still affect the application's security.

**Control ID: AI-BOM-008**

---

### 9. Model Dependency

A model dependency is a model required for an AI system to perform its intended function.

It may be:

* locally hosted;
* obtained from a model repository;
* supplied through an API;
* hosted by a cloud provider;
* derived from another model.

**Control ID: AI-BOM-009**

---

### 10. Model Version Dependency

The AI BOM should distinguish the model identity from the specific model version where version information is available.

This distinction is important because different versions may have different:

* behavior;
* vulnerabilities;
* licenses;
* dependencies;
* evaluation results;
* security characteristics.

**Control ID: AI-BOM-010**

---

### 11. Dataset Dependency

A dataset dependency identifies a dataset materially used by an AI system.

It may include:

* training datasets;
* fine-tuning datasets;
* evaluation datasets;
* retrieval datasets;
* reference datasets.

Dataset inventory should consider the applicable data-governance requirements.

**Control ID: AI-BOM-011**

---

### 12. Software Component

Software components may include:

* libraries;
* packages;
* frameworks;
* SDKs;
* operating-system components;
* containers;
* runtime components.

The SBOM should provide sufficient identity information to support security and lifecycle management.

**Control ID: AI-BOM-012**

---

### 13. AI Framework Dependency

AI frameworks can introduce substantial software dependencies into an AI system.

Examples may include:

* machine-learning frameworks;
* deep-learning frameworks;
* model-serving frameworks;
* orchestration frameworks;
* agent frameworks.

Framework versions should be identifiable where material to security and lifecycle management.

**Control ID: AI-BOM-013**

---

### 14. AI SDK Dependency

AI SDKs may provide access to:

* model APIs;
* inference services;
* vector databases;
* AI platforms;
* agent services.

An AI BOM should identify material SDK dependencies when they affect the system's security or operational behavior.

**Control ID: AI-BOM-014**

---

### 15. Model Runtime Dependency

A model may require a specific runtime or inference engine.

Examples include:

* inference servers;
* model execution engines;
* hardware acceleration libraries;
* serialization libraries.

A model artifact should therefore not necessarily be treated as an isolated dependency.

**Control ID: AI-BOM-015**

---

### 16. Model Adapter Dependency

AI systems may use:

* adapters;
* parameter-efficient fine-tuning components;
* LoRA-style adaptations;
* prompt-tuning artifacts;
* other model modifications.

These should be represented when they materially affect the deployed model.

**Control ID: AI-BOM-016**

---

### 17. Model Parentage

Where a model is derived from another model, the relationship should be represented where technically and operationally relevant.

For example:

```text
Base Model
    |
Fine-Tuning
    |
Derived Model
    |
Adapter
    |
Production Model Configuration
```

Parentage improves understanding of model lineage and dependency.

**Control ID: AI-BOM-017**

---

### 18. Component Supplier

The supplier or publisher associated with a material component should be identifiable where possible.

Supplier information may support:

* vulnerability response;
* incident communication;
* licensing;
* due diligence;
* concentration analysis.

**Control ID: AI-BOM-018**

---

### 19. Component Publisher

The publisher is the party responsible for publishing or distributing a component.

Publisher information should be distinguished from:

* repository;
* hosting provider;
* distributor;
* deployment platform.

These parties may represent different trust relationships.

**Control ID: AI-BOM-019**

---

### 20. Component Repository

A repository is a location from which a component is obtained or maintained.

Examples include:

* source-code repositories;
* package repositories;
* model repositories;
* container registries;
* private artifact repositories.

Repository identity should be recorded where relevant.

**Control ID: AI-BOM-020**

---

### 21. Component Provenance

Component provenance describes the origin and history of a component.

For an AI system, provenance may include:

* original source;
* publisher;
* repository;
* acquisition path;
* transformation;
* version;
* deployment artifact.

Provenance information supports supply-chain analysis.

**Control ID: AI-BOM-021**

---

### 22. BOM Provenance

The organization should also consider the provenance of the BOM itself.

The organization should be able to determine:

* who generated the BOM;
* when it was generated;
* from which artifact;
* using which tooling;
* under which process.

A BOM is therefore itself an assurance artifact requiring appropriate governance.

**Control ID: AI-BOM-022**

---

### 23. BOM Integrity

BOM records should be protected against unauthorized modification.

Controls may include:

* access control;
* version control;
* cryptographic integrity mechanisms;
* immutable storage;
* audit logging.

Integrity protection does not by itself prove that the BOM is complete or accurate.

**Control ID: AI-BOM-023**

---

### 24. BOM Authenticity

Where appropriate, organizations should establish confidence that a BOM originated from the expected source.

Possible mechanisms include:

* digital signatures;
* trusted build systems;
* authenticated generation pipelines;
* controlled repositories.

Authenticity should be distinguished from completeness and correctness.

**Control ID: AI-BOM-024**

---

### 25. BOM Completeness

BOM completeness describes the extent to which the BOM identifies relevant components.

A BOM may be incomplete because:

* dependencies are omitted;
* transitive dependencies are unavailable;
* proprietary components are not disclosed;
* dynamically loaded components are missed;
* runtime dependencies are unknown.

Completeness should therefore be assessed rather than assumed.

**Control ID: AI-BOM-025**

---

### 26. BOM Accuracy

BOM accuracy concerns whether the information recorded corresponds to the actual system.

Examples of inaccurate information include:

* incorrect version;
* incorrect supplier;
* obsolete dependency;
* missing component relationship;
* incorrect model identifier.

**Control ID: AI-BOM-026**

---

### 27. BOM Freshness

BOM information becomes stale as systems change.

Freshness should therefore be evaluated against:

* software changes;
* model changes;
* dependency updates;
* dataset changes;
* infrastructure changes.

Critical systems may require more frequent BOM regeneration.

**Control ID: AI-BOM-027**

---

### 28. BOM Versioning

BOMs should be versioned so that changes in system composition can be reconstructed.

Version history can help identify:

* added components;
* removed components;
* upgraded dependencies;
* model changes;
* changed suppliers.

**Control ID: AI-BOM-028**

---

### 29. BOM Baseline

An approved BOM may serve as a baseline for comparison.

The baseline can support detection of:

* unauthorized components;
* unexpected versions;
* dependency changes;
* model substitutions.

**Control ID: AI-BOM-029**

---

### 30. BOM Drift

BOM drift occurs when the recorded component inventory diverges from the actual deployed system.

Potential causes include:

* manual changes;
* automatic updates;
* emergency deployments;
* unmanaged dependencies;
* configuration changes.

BOM drift should be detected and investigated according to risk.

**Control ID: AI-BOM-030**

---

### 31. Runtime Component Discovery

Static BOM generation may not identify every component active at runtime.

Runtime discovery may identify:

* dynamically loaded libraries;
* external services;
* APIs;
* model endpoints;
* runtime plugins;
* ephemeral dependencies.

Organizations should determine whether runtime discovery is necessary for the relevant system.

**Control ID: AI-BOM-031**

---

### 32. Build-Time Component Discovery

Build pipelines can generate component information during:

* compilation;
* packaging;
* container creation;
* model packaging;
* deployment preparation.

Build-time discovery can provide an auditable source for BOM generation.

**Control ID: AI-BOM-032**

---

### 33. Deployment-Time BOM

A deployment-time BOM should reflect the components actually intended for a production deployment.

This can help identify differences between:

* development;
* testing;
* staging;
* production.

**Control ID: AI-BOM-033**

---

### 34. Runtime BOM

A runtime BOM represents components observed or required during actual execution.

It can complement build-time and deployment-time BOMs.

```text
Build BOM
    |
Deployment BOM
    |
Runtime BOM
    |
Actual Dependency View
```

Differences should be analyzed where material.

**Control ID: AI-BOM-034**

---

### 35. SBOM and AI BOM Relationship

SBOM and AI BOM should generally be treated as complementary views.

```text
                    AI System
                       |
          +------------+------------+
          |                         |
         SBOM                      AI BOM
          |                         |
 Software Components       Models / Data / AI Components
          |                         |
          +------------+------------+
                       |
              Enterprise Inventory
```

The exact implementation should reflect organizational architecture.

**Control ID: AI-BOM-035**

---

### 36. Software-to-Model Relationship

The BOM should represent relationships between software and models where technically feasible.

For example:

```text
Application
    |
Inference Framework
    |
Runtime
    |
Model
```

This relationship supports impact analysis when any component changes.

**Control ID: AI-BOM-036**

---

### 37. Model-to-Dataset Relationship

Where a model depends materially on a dataset, the relationship should be represented where feasible.

Examples include:

* training;
* fine-tuning;
* evaluation;
* retrieval.

**Control ID: AI-BOM-037**

---

### 38. Model-to-API Relationship

Where an AI application depends on an external model API, the dependency should be represented.

Relevant information may include:

* provider;
* service;
* model;
* version;
* endpoint;
* contractual dependency.

**Control ID: AI-BOM-038**

---

### 39. Model-to-Infrastructure Relationship

A model may depend on infrastructure such as:

* GPU platforms;
* storage;
* networking;
* container platforms;
* inference servers;
* cloud services.

Material infrastructure dependencies should be visible where they affect resilience or security.

**Control ID: AI-BOM-039**

---

### 40. Dependency Relationship

BOMs should represent meaningful relationships between components rather than providing only a flat list.

Relationship types may include:

* depends-on;
* contains;
* derived-from;
* trained-on;
* deployed-with;
* communicates-with.

**Control ID: AI-BOM-040**

---

### 41. Dependency Graph

A dependency graph provides a visual representation of component relationships.

```text
                    AI Application
                    /      |      \
                   /       |       \
             Software    Model      API
                |          |         |
            Framework    Dataset   Provider
                |
             Package
                |
             Package
```

Dependency graphs support impact and blast-radius analysis.

**Control ID: AI-BOM-041**

---

### 42. BOM Component Identity

Each material component should have sufficiently precise identity information.

Identity may include:

* name;
* version;
* supplier;
* package identifier;
* model identifier;
* dataset identifier;
* artifact digest.

Ambiguous component identity reduces the usefulness of vulnerability and dependency analysis.

**Control ID: AI-BOM-042**

---

### 43. Component Version Identity

Version information should distinguish among:

* major version;
* minor version;
* patch version;
* release identifier;
* commit identifier;
* model revision;
* artifact digest.

The appropriate identifier depends on the component type.

**Control ID: AI-BOM-043**

---

### 44. Cryptographic Component Identity

Cryptographic identifiers such as hashes or digests can help establish whether an artifact corresponds to a known byte-level representation.

However:

```text
Hash Match
    ≠
Security Assurance
```

A verified hash does not establish that the underlying artifact is free from vulnerabilities or malicious behavior.

**Control ID: AI-BOM-044**

---

### 45. BOM License Information

Where available and relevant, BOMs should capture licensing information for material components.

This may support:

* license review;
* redistribution analysis;
* procurement;
* legal assessment;
* open-source governance.

License information in a BOM should not automatically be treated as a legal opinion.

**Control ID: AI-BOM-045**

---

### 46. BOM Vulnerability Information

BOM data can support vulnerability management by connecting components to relevant vulnerability information.

The process may identify:

* vulnerable software packages;
* affected versions;
* vulnerable runtimes;
* vulnerable model dependencies.

A vulnerability record should still be assessed for actual applicability and exploitability.

**Control ID: AI-BOM-046**

---

### 47. BOM Security Use

BOM information can support security processes including:

* vulnerability management;
* incident response;
* threat intelligence;
* attack-surface analysis;
* dependency monitoring;
* supply-chain risk assessment.

A BOM is an enabling control artifact rather than a complete security control by itself.

**Control ID: AI-BOM-047**

---

### 48. BOM Incident Response

During a supply-chain incident, BOM information can help determine:

* affected systems;
* affected versions;
* affected models;
* shared dependencies;
* potential blast radius;
* remediation scope.

The usefulness of this analysis depends on BOM completeness and freshness.

**Control ID: AI-BOM-048**

---

### 49. SBOM and AI BOM Governance Principle

Effective BOM governance should establish:

* defined scope;
* component identity;
* dependency relationships;
* provenance;
* integrity;
* versioning;
* freshness;
* ownership;
* access control;
* lifecycle management.

BOM generation should be integrated into appropriate engineering and governance processes.

**Control ID: AI-BOM-049**

---

### 50. SBOM and AI BOM Trust Principle

An SBOM or AI BOM should not automatically be treated as a complete representation of an AI system merely because it has been generated successfully.

The organization should distinguish:

* BOM existence from BOM completeness;
* BOM integrity from BOM accuracy;
* BOM accuracy from BOM completeness;
* component identity from component trust;
* vulnerability visibility from vulnerability absence;
* provenance visibility from provenance verification;
* static inventory from runtime reality;
* model inventory from model behavioral assurance.

The fundamental principle is:

```text
Know What Is Present
        |
Know Where It Came From
        |
Know How It Is Related
        |
Know Which Version Is Deployed
        |
Know What Has Changed
        |
Know Which Risks Apply
        |
Use the BOM as Evidence
        |
Do Not Treat the BOM as Complete Assurance
```

Internal `AI-BOM-*` identifiers are organizational governance taxonomy identifiers. They are not provisions of legislation or regulation. Where an SBOM, AI BOM, component inventory, vulnerability disclosure, or related control is legally or contractually mandatory, the applicable authoritative requirement should be identified separately rather than inferred from the internal control identifier.
