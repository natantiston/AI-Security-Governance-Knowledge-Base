# 16.13 — SBOM and AI Bill of Materials

## Part 1 — Foundations, SBOM/AIBOM Concepts, Scope, Inventory, Component Identification and Dependency Architecture

### 1. Definition of Software Bill of Materials

A Software Bill of Materials (SBOM) is a structured inventory describing the software components, dependencies, versions, suppliers, and relationships that compose a software product or service.

An SBOM provides visibility into software composition.

```text
Software Product
       |
       +--> Application
       |
       +--> Libraries
       |
       +--> Packages
       |
       +--> Frameworks
       |
       +--> Dependencies
       |
       +--> Container
       |
       +--> Operating System Components
```

---

### 2. Purpose of an SBOM

The primary purpose of an SBOM is to provide sufficient component visibility to support security, vulnerability management, supply-chain risk management, licensing analysis, incident response, and operational assurance.

An SBOM should therefore be treated as an operational security artifact rather than merely a documentation file.

---

### 3. Definition of AI Bill of Materials

An AI Bill of Materials (AIBOM) extends software-composition visibility into AI systems.

An AIBOM can describe AI-specific components including:

* AI models
* Model versions
* Model variants
* Model artifacts
* Datasets
* AI frameworks
* Tokenizers
* Embedding models
* Vector databases
* Retrieval components
* AI APIs
* Tool integrations
* Agent frameworks
* Guardrails
* Evaluation components
* AI monitoring components

---

### 4. SBOM versus AIBOM

An SBOM primarily describes software composition.

An AIBOM additionally describes AI-specific composition, provenance, dependencies, and relationships.

```text
SBOM
 |
 +--> Software
 +--> Packages
 +--> Libraries
 +--> Dependencies
 +--> Containers
 +--> Build Components

AIBOM
 |
 +--> Everything relevant from SBOM
 |
 +--> Models
 +--> Datasets
 +--> Model Versions
 +--> Embeddings
 +--> RAG
 +--> Agents
 +--> Tools
 +--> AI Runtime
```

**AIBOM ≠ merely an SBOM with a model name added.**

---

### 5. AI System Composition

An AI system should be viewed as a composition of interconnected technical and non-technical components.

```text
                    AI System
                        |
        +---------------+---------------+
        |               |               |
      Data            Model          Software
        |               |               |
    Datasets       Model Version    Frameworks
        |               |               |
        +---------------+---------------+
                        |
                  AI Application
                        |
             +----------+----------+
             |          |          |
            RAG       Tools      Agents
             |          |          |
             +----------+----------+
                        |
                 Infrastructure
```

An effective AIBOM should represent relevant relationships across these layers.

---

### 6. SBOM/AIBOM Governance Objective

The governance objective is to maintain an accurate, current, trustworthy, and actionable representation of the components and dependencies forming an AI-enabled system.

The objective is not simply:

> “Produce an SBOM.”

The objective is:

> **Know what the AI system contains, where components came from, how they are related, what they depend on, and what risks those dependencies create.**

### 62. Direct Dependency

A direct dependency is a component explicitly required by another component or system.

```text
Application
     |
     v
Library A
```

---

### 63. Transitive Dependency

A transitive dependency is a dependency introduced through another dependency.

```text
Application
     |
     v
Library A
     |
     v
Library B
     |
     v
Library C
```

Transitive dependencies are important because they may remain invisible during basic inventory processes.

---

### 64. Hidden Dependency

A hidden dependency is a dependency that exists operationally but is not adequately represented in the organization's inventory.

Hidden dependencies create visibility gaps.

---

Examples include:

* Depends-on
* Contains
* Built-from
* Uses
* Calls
* Embeds
* Retrieves-from
* Runs-on
* Deployed-with

---

### 66. Depends-On Relationship

A `depends-on` relationship identifies a functional dependency.

```text
Application
     |
     | depends on
     v
AI Framework
```

---

### 67. Contains Relationship

A `contains` relationship identifies composition.

```text
Container
   |
   +--> Application
   +--> Runtime
   +--> Libraries
```

---

### 68. Built-From Relationship

A built-from relationship identifies the source components used to create an artifact.

```text
Source
  |
  +--> Dependencies
  |
  v
Build
  |
  v
Artifact
```

---

### 69. Derived-From Relationship

AI models may be derived from other models through:

* Fine-tuning
* Distillation
* Merging
* Quantization
* Conversion
* Adaptation

These relationships should remain traceable.

---

### 70. Fine-Tuned-From Relationship

A fine-tuned model should maintain lineage to its base model where known.

```text
Base Model
     |
     v
Fine-Tuning Dataset
     |
     v
Fine-Tuned Model
```

---

### 71. Quantized-From Relationship

A quantized model should retain a relationship to the source model.

Quantization can alter artifact identity without necessarily representing an entirely independent model lineage.

---

### 72. Distilled-From Relationship

A distilled model should identify its source or teacher model where known.

This improves model provenance and dependency analysis.

---

### 73. Merged-From Relationship

Merged models should preserve relationships to relevant source models.

```text
Model A
    \
     +--> Merge --> Model C
    /
Model B
```

---

### 74. Adapter Relationship

Adapters such as LoRA-style components can create dependencies on a base model.

The AIBOM should represent the relationship where material.

---

### 75. Wrapper Relationship

A wrapper may modify how a model is accessed without changing the underlying model artifact.

The inventory should distinguish:

* Model
* Wrapper
* Runtime
* Application

### 76. Runtime Relationship

### 77. Framework Relationship

**Component criticality ≠ dependency criticality in every case.**

### 93. Runtime Criticality

### 94. Common-Mode Dependency

```text

              /      |      \
             v       v       v
           AI-1    AI-2    AI-3
```

Common-mode dependencies should be identified for resilience analysis.

---

### 95. Dependency Blast Radius

The blast radius represents the potential scope of impact if a component or dependency fails or is compromised.

Relevant factors include:

* Number of workloads
* Business services
* Data domains
* Geographic scope
* Privilege
* Connected systems

---

### 96. Attack-Path Dependency

```text

       |
       v
AI Application
       |
       v
Model Runtime
       |
       v
Sensitive Data
```

The inventory should support analysis of such paths.

### 111. Test-Time Dependency

### 400. SBOM/AIBOM Due-Diligence and Integration Principle

An effective SBOM/AIBOM program should preserve the following principles:

**Generation ≠ validation.**

**Validation ≠ assurance.**

**Inventory ≠ complete visibility unless completeness is tested.**

**Declared composition ≠ actual runtime composition.**

**Provider-generated inventory ≠ independent assurance.**

**Component identity ≠ component provenance.**

**Provenance ≠ integrity.**

**Integrity ≠ security.**

**SBOM ≠ AIBOM.**

**Software dependency ≠ complete AI dependency.**

**Model identity ≠ model artifact identity.**

**Dataset name ≠ dataset version or snapshot.**

**Vulnerability severity ≠ organizational risk.**

**Vulnerability detection ≠ exploitability.**

**Vulnerability correlation ≠ vulnerability remediation.**

**Remediation ticket ≠ remediation validation.**

**Inventory coverage ≠ inventory accuracy.**

**Inventory accuracy ≠ inventory currency.**

**Automation ≠ assurance.**

**Format compatibility ≠ information preservation.**

**External evidence ≠ validated evidence.**

**Technical dependency ≠ business impact without impact analysis.**

**Third-party SBOM ≠ automatically trusted SBOM.**

**AIBOM completeness requires AI-specific dependency visibility.**

**SBOM/AIBOM evidence should remain traceable to the actual artifact, release, deployment, and relevant system state.**

Internal `AI-SBOM-*` identifiers used in this knowledge base are organizational taxonomy identifiers and are not statutory provisions, regulatory article numbers, or mandatory identifiers from external legislation or standards.

### 1000. AI Model and Software Supply-Chain Governance Principle

An effective SBOM/AIBOM governance framework should maintain an end-to-end chain of accountability:

```text id="sbom16p13-42"

   |
   v

   |
   v

   |

   |

   |
   v

   |
   v

```

The fundamental governance principles are:

**SBOM ≠ supply-chain security.**

**AIBOM ≠ merely an expanded SBOM.**

**Inventory ≠ assurance.**

**Visibility ≠ risk elimination.**

**Generation ≠ validation.**

**Validation ≠ continuous assurance.**

**Declared composition ≠ actual composition.**

**Static inventory ≠ runtime visibility.**

**Runtime visibility ≠ complete dependency visibility.**

**Component identity ≠ provenance.**

**Provenance ≠ integrity.**

**Integrity ≠ security.**

**Vulnerability detection ≠ remediation.**

**Remediation ≠ verified remediation.**

**Risk acceptance ≠ risk elimination.**

**Supplier evidence ≠ independent assurance.**

**Alternative ≠ independent alternative.**

**Fallback plan ≠ tested resilience.**

**Exit plan ≠ executable exit capability.**

**Lifecycle visibility ≠ lifecycle governance.**

**Regulatory traceability ≠ regulatory obligation.**

**Internal control ≠ statutory requirement.**

**Continuous monitoring ≠ continuous compliance.**

**AI-assisted analysis ≠ verified assurance.**

**Technical dependency ≠ business impact without impact analysis.**

**Unknown dependency ≠ safe dependency.**

**A critical AI system should have sufficient composition, dependency, provenance, integrity, vulnerability, runtime, lifecycle, resilience, and governance visibility to support informed enterprise risk decisions.**

Internal `AI-SBOM-*` identifiers used in this knowledge base are organizational taxonomy identifiers and are not statutory provisions, regulatory article numbers, or mandatory identifiers from external legislation or standards.
