# 16.09 — AI API Security and Third-Party Services

## Part 1 — Foundations, API Dependency, Trust Boundaries, Authentication, Authorization, Data Governance and Security

### 1. AI API Security and Third-Party Services

AI applications increasingly depend on external APIs for model inference, embeddings, moderation, speech processing, vision, retrieval, agents, and other AI capabilities.

These APIs create third-party security and governance dependencies because the organization may send data, credentials, prompts, model instructions, files, metadata, or business transactions to services outside its direct operational boundary.

AI API governance should therefore address not only API security but also:

* third-party dependency;
* data governance;
* identity;
* authorization;
* model behavior;
* availability;
* logging;
* supply-chain risk;
* privacy;
* contractual obligations;
* resilience;
* exit capability.

**Control ID: AI-API-001**

---

### 2. Objective of AI API Governance

The objective of AI API governance is to ensure that external AI services are used in a controlled, secure, accountable, and risk-proportionate manner.

Governance should establish:

* approved AI APIs;
* permitted use cases;
* data restrictions;
* identity requirements;
* authorization boundaries;
* security controls;
* monitoring;
* incident procedures;
* supplier oversight;
* resilience requirements;
* lifecycle controls.

**Control ID: AI-API-002**

---

### 3. AI API

An AI API is an interface through which an application interacts programmatically with an AI capability.

Examples include APIs for:

* large language models;
* embeddings;
* image generation;
* speech recognition;
* speech synthesis;
* computer vision;
* content moderation;
* classification;
* translation;
* agent execution.

The API is a technical interface, but the underlying service may represent a significant third-party dependency.

**Control ID: AI-API-003**

---

### 4. Third-Party AI Service

A third-party AI service is an externally operated service that provides AI functionality to the organization.

The organization may have limited control over:

* infrastructure;
* model development;
* training;
* service operations;
* personnel;
* underlying dependencies;
* security architecture.

The organization's governance should therefore account for the boundary between internal controls and third-party controls.

**Control ID: AI-API-004**

Dependency may be:

* technical;

* contractual;

The dependency should be identified in the organization's relevant inventories.

### Core Principles

1. **API-Governance Principle** — AI APIs should be governed as both technology interfaces and third-party dependencies.
2. **Trust-Boundary Principle** — Data, credentials, instructions, and responses crossing an external AI API boundary should be explicitly governed.
3. **Data-Minimization Principle** — Only information necessary for the approved use case should be transmitted where minimization is appropriate.
4. **Data-Classification Principle** — AI API processing should respect the organization's existing data-classification framework.
5. **Purpose Principle** — AI API data processing should correspond to an approved business purpose.
6. **Retention Principle** — AI API retention should be understood and governed according to applicable requirements.
7. **Training-Use Principle** — Organizations should understand and govern whether submitted information may be used for model training or other secondary purposes.
8. **Subprocessor Principle** — Material downstream dependencies of AI API providers should be considered in third-party risk assessment.
9. **Authentication Principle** — AI API access should use appropriate and controlled authentication mechanisms.
10. **Credential Principle** — API credentials should be securely stored, rotated, monitored, and revoked when required.
11. **Authorization Principle** — Authentication should be complemented by explicit authorization controls.
12. **Least-Privilege Principle** — AI API clients should receive only the permissions required for approved functions.
13. **Environment-Separation Principle** — Production and non-production AI API access should be appropriately separated.
14. **Network-Security Principle** — External AI API communications should be protected through appropriate network and transport controls.
15. **Egress-Control Principle** — Outbound AI API connectivity should be controlled to reduce unauthorized external data transfer.
16. **Gateway Principle** — Enterprise AI gateways can centralize policy enforcement but should themselves be governed as critical infrastructure where applicable.
17. **Rate-Limiting Principle** — API consumption should be controlled to reduce abuse, availability, and unexpected-cost risks.
18. **Logging Principle** — AI API activity should generate appropriate evidence while avoiding unnecessary exposure of sensitive prompt and response content.
19. **Monitoring Principle** — AI API usage should be monitored for unauthorized, anomalous, and potentially malicious activity.
20. **Layered-Trust Principle** — Trust in an external AI API should be established through layered governance and security controls rather than provider reputation or documentation alone.

## Part 2 — AI API Due Diligence, Security Controls, Model Assurance, Data Governance and Third-Party Risk

Due diligence should consider:

* provider identity;
* service architecture;
* security controls;
* data handling;
* privacy;
* model governance;
* subprocessors;
* incident management;
* resilience;
* contractual commitments;
* assurance evidence.

The depth of due diligence should reflect the service's criticality and risk.

### Core Principles

1. **Due-Diligence Principle** — Material AI APIs should undergo risk-based provider and service assessment.
2. **Evidence Principle** — Provider claims should be evaluated against evidence appropriate to the risk.
3. **Scope Principle** — Assurance should be evaluated according to its actual scope, period, service, and limitations.
4. **Contract Principle** — Material AI API relationships should include appropriate contractual security and data-governance requirements.
5. **Incident-Cooperation Principle** — Provider cooperation should be addressed for material security and service incidents.
6. **Model-Assurance Principle** — AI API models should be evaluated in the context of their actual organizational use.
7. **Version-Control Principle** — Material model versions and configurations should be identifiable and controlled where technically feasible.
8. **Change-Management Principle** — Material AI API and model changes should undergo appropriate assessment and testing.
9. **Regression Principle** — Significant model or service changes should be evaluated against relevant baselines.
10. **Prompt-Security Principle** — Prompts and system instructions should be governed where they materially affect security or business behavior.
11. **Tool-Authorization Principle** — AI models should not independently determine authorization for consequential tool actions.
12. **Output-Validation Principle** — Material AI outputs should be validated before consequential downstream use.
13. **Privacy Principle** — Personal-data processing through AI APIs should be governed according to applicable privacy requirements.
14. **Supply-Chain Principle** — AI API governance should consider software, model, infrastructure, and subprocessor dependencies.
15. **Resilience Principle** — Material AI API dependencies should have appropriate recovery and continuity arrangements.
16. **Fallback Principle** — Critical AI-dependent services should have appropriate fallback capabilities where justified by risk.
17. **Concentration Principle** — Multiple AI APIs do not necessarily create effective diversification if common dependencies remain.
18. **Portability Principle** — API portability should consider application behavior, data, configuration, and model-specific dependencies.
19. **Exit Principle** — Material AI API dependencies should have credible exit considerations.
20. **Control-Governance Principle** — AI API controls should clearly distinguish legal requirements from contractual obligations, internal controls, implementation practices, and recommended governance measures.

20. **Continuous-Assurance Principle** — Monitoring, incidents, changes, testing, and assurance findings should continuously feed AI API risk management.

### 400. AI API Governance Principle

AI API governance should operate as an integrated enterprise capability connecting:

```text id="p8w4qn"
Provider
    |
AI API
    |

    |

    |

    |

    |

    |

```

Effective governance requires provider due diligence, strong authentication and authorization, controlled data flows, model and behavioral assurance, secure application integration, continuous monitoring, incident readiness, resilience, concentration management, practical portability, credible exit capability, evidence-based assurance, and accountable decision-making.

The organization should distinguish between **the security of the provider**, **the security of the API**, **the security of the integrated application**, and **the governance of the resulting business process**. A secure provider does not automatically make every customer integration secure, and an available API does not automatically provide business resilience.

Internal `AI-API-*` control identifiers represent the knowledge-base control taxonomy. They should not be interpreted as statutory provisions or regulatory requirements unless a separate legal or regulatory mapping explicitly establishes that relationship.

**Control ID: AI-API-400**

### Core Principles

1. **Enterprise-Governance Principle** — AI API dependencies should be governed within enterprise AI, cybersecurity, third-party-risk, privacy, and enterprise-risk frameworks.
2. **Accountability Principle** — Material AI API dependencies should have identifiable accountable owners.
3. **Lifecycle Principle** — Governance should cover discovery, assessment, integration, deployment, monitoring, change, and retirement.
4. **Architecture Principle** — AI API integrations should operate within defined security and trust boundaries.
5. **Threat-Modeling Principle** — Material AI API dependencies should be assessed against realistic attack paths and failure scenarios.
6. **Least-Privilege Principle** — AI API clients, models, and tools should receive only the permissions required for approved purposes.
7. **Data-Boundary Principle** — External AI services should have controlled access to enterprise information according to classification and business need.
8. **Supply-Chain Principle** — AI API governance should consider providers, models, SDKs, software dependencies, subprocessors, and infrastructure.
9. **Concentration Principle** — Provider and infrastructure concentration should be assessed for common-mode failure.
10. **Strategic-Dependency Principle** — Material AI API dependencies should be visible within enterprise strategic-risk management.
11. **Resilience Principle** — Critical AI API-dependent services should have appropriate continuity and recovery arrangements.
12. **Portability Principle** — Portability should be assessed through realistic technical and behavioral testing where material.
13. **Exit Principle** — Material AI API dependencies should have credible and, where appropriate, tested exit arrangements.
14. **Assurance Principle** — Assurance should consider evidence quality, scope, recency, relevance, and independence.
15. **Evidence Principle** — Material AI API decisions should be supported by traceable evidence.
16. **Automation Principle** — Automated API governance controls should be bounded, auditable, and resilient to automation failure.
17. **Human-Accountability Principle** — Significant AI API risk decisions should retain appropriate human accountability.
18. **Continuous-Improvement Principle** — Incidents, testing, audits, provider changes, and assurance findings should improve governance.
19. **Legal-Distinction Principle** — Legal requirements, regulatory powers, contractual obligations, internal controls, implementation practices, and recommendations should be explicitly distinguished.
20. **Enterprise-Assurance Principle** — Effective AI API governance requires evidence that controls operate across the complete dependency lifecycle rather than relying solely on provider claims, certifications, documentation, or contractual commitments.
