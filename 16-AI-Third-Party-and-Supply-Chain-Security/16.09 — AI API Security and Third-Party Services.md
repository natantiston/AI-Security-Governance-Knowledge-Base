# 16.09 — AI API Security and Third-Party Services

## Part 1 — Foundations, API Provider Classification, Dependency, Trust Boundaries and Risk Architecture

### 1 — AI API Security and Third-Party Service Risk Definition

AI API security and third-party service risk is the risk that externally provided AI application programming interfaces, supporting services, integrations, or service components introduce cybersecurity, privacy, data, model, operational, regulatory, contractual, supply-chain, or business risks into an organization's AI environment.

### 2 — AI API Governance Objective

The governance objective is to ensure that AI APIs and third-party services are:

* identified;
* assessed;
* authorized;
* securely integrated;
* monitored;
* governed throughout their lifecycle;
* capable of controlled suspension or replacement.

### 3 — AI API Definition

An AI API is an interface through which an organization accesses AI capabilities provided by an external or internal service.

Examples include APIs for:

* large language models;
* embeddings;
* speech recognition;
* image generation;
* computer vision;
* moderation;
* translation;
* classification;
* agent services;
* AI search;
* retrieval.

### 4 — Third-Party AI Service Definition

A third-party AI service is an externally operated capability that provides AI functionality or materially supports an AI workload.

It may include:

* model inference;
* model hosting;
* vector search;
* AI orchestration;
* evaluation;
* monitoring;
* security;
* data processing.

### 5 — AI API Provider

The AI API provider is the organization operating or commercially providing the API service.

The API provider may also be:

* the model provider;
* the cloud provider;
* an AI SaaS provider;
* an intermediary;
* a platform provider.

### 6 — API Provider and Model Provider Distinction

The API provider and underlying model provider should not automatically be assumed to be the same entity.

An API may expose:

* internally developed models;
* third-party models;
* open-source models;
* multiple foundation models;
* dynamically selected models.

### 7 — API Aggregator

An API aggregator may provide access to multiple AI models or services through a common interface.

Aggregator risk should include the possibility of hidden dependencies on multiple upstream providers.

### 8 — AI API Broker

An AI API broker may abstract model-provider relationships from the consuming organization.

Organizations should understand the underlying providers where they are material to risk.

### 9 — AI API Gateway

An AI API gateway is an intermediary layer that can provide controls such as:

* authentication;
* authorization;
* routing;
* rate limiting;
* logging;
* DLP;
* policy enforcement.

### 10 — Direct API Dependency

A direct API dependency exists when an application communicates directly with an external AI API.

### 11 — Indirect API Dependency

An indirect dependency exists when an internal application consumes a service that itself calls an external AI API.

### 12 — Hidden API Dependency

Hidden API dependencies may exist inside:

* SaaS applications;
* software libraries;
* development tools;
* security products;
* business applications;
* agent frameworks.

### 13 — API Dependency Discovery

Organizations should identify material AI APIs used across:

* production applications;
* development environments;
* SaaS platforms;
* automation;
* scripts;
* agent workflows.

### 14 — API Dependency Mapping

Material dependencies should be mapped from:

**User → Application → API Gateway → Third-Party API → Model → Upstream Services**

where applicable.

### 15 — API Trust Boundary

An external AI API represents a trust boundary between the organization's environment and the service provider.

* authentication information.

### 17 — API Response Trust Boundary

### 18 — Third-Party Service Trust Boundary

* third-party risk.

### 974 — API Trust Principle

Trust in an AI API should be based on **verifiable evidence, controlled access, validated data flows, security testing, monitored operation, and accountable governance**, rather than provider reputation alone.

### 975 — API Dependency Principle

Critical AI API dependencies should be visible, assessed, monitored, and supported by proportionate resilience and exit capabilities.

### 976 — API Security Principle

AI API security should protect the complete chain from **request creation through external processing to response consumption and downstream action**.

### 977 — API Data Protection Principle

Information transmitted through AI APIs should remain subject to appropriate organizational data-governance and privacy controls.

### 978 — API Identity Principle

AI API identities, credentials, and privileges should be uniquely attributable, appropriately scoped, protected, and reviewable.

### 979 — API Output Trust Principle

AI API outputs should be treated according to their risk and should not automatically be considered authoritative, accurate, or safe for execution.

### 980 — API Tool Governance Principle

Where AI APIs can invoke tools or external actions, permissions, parameters, authorization, monitoring, and human oversight should be proportionate to the potential impact.

### 981 — API Resilience Principle

Critical AI API dependencies should have proportionate continuity, fallback, recovery, and migration capabilities.

### 982 — API Concentration Principle

API concentration should be assessed across provider, model, gateway, cloud, network, infrastructure, and upstream-service layers.

### 983 — API Independence Principle

Alternative APIs and providers should only be treated as independent when material common-mode dependencies have been evaluated.

### 984 — API Supply-Chain Principle

AI API governance should consider the complete supply chain, including:

**API Provider → Model Provider → SDK → Gateway → Cloud → Network → Application**

### 985 — API Change Principle

Material changes to provider, API, model, SDK, configuration, data processing, architecture, or use case should receive appropriate reassessment.

### 986 — API Assurance Principle

Provider assurance should supplement rather than replace assessment of the organization's own API integration.

### 987 — API Evidence Principle

Material AI API decisions should be supported by evidence that is sufficiently relevant, current, complete, and traceable.

### 988 — API Accountability Principle

Externalizing AI functionality to a third-party API does not automatically eliminate the organization's responsibility for governing its use.

### 989 — API Lifecycle Principle

AI APIs should be governed throughout their lifecycle from:

**Assessment → Approval → Integration → Production → Monitoring → Reassessment → Renewal or Exit**

### 990 — API Exit Principle

Critical API dependencies should be designed so that exit remains technically and operationally feasible within required continuity constraints.

### 991 — API Regulatory Traceability Principle

Applicable legal and regulatory requirements should be traceable to organizational controls, responsible owners, and supporting evidence.

### 992 — API Governance Evidence Principle

Material governance decisions should be reproducible from documented requirements, evidence, analysis, authorization, and decision records.

### 993 — API Control Effectiveness Principle

AI API governance should be evaluated based on demonstrated control effectiveness and risk outcomes rather than policy existence alone.

### 994 — API Continuous Improvement Principle

AI API governance should incorporate lessons from:

* incidents;
* vulnerabilities;
* testing;
* audits;
* provider changes;
* regulatory developments;
* technology changes.

### 995 — API Defense-in-Depth Principle

No single AI API control should be relied upon as the sole protection against material third-party AI risk.

### 996 — API Responsibility Principle

Responsibility boundaries among API providers, model providers, cloud providers, application owners, and organizational governance functions should be explicit.

### 997 — API Risk Decision Principle

Material AI API decisions should be based on the **specific provider, API, model, data, architecture, dependencies, use case, contractual environment, business criticality, and available evidence**.

### 998 — API Governance Maturity Principle

AI API governance maturity should be evaluated through the organization's ability to consistently identify, control, monitor, evidence, and respond to AI API risks.

### 999 — API Enterprise Integration Principle

AI API security and third-party-service governance should be integrated with enterprise:

* cybersecurity;
* GRC;
* AI governance;
* privacy;
* data governance;
* procurement;
* architecture;
* business continuity;
* incident management.

### 1000 — AI API Governance Principle

AI API and third-party AI service governance should provide **end-to-end accountability, security, data protection, operational resilience, supply-chain assurance, regulatory traceability, continuous monitoring, controlled lifecycle management, and feasible exit** for every material AI API dependency.
