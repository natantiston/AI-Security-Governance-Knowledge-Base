# 16.12 — AI Model Supply Chain — Part 1

## Part 1 — Foundations, Model Supply-Chain Classification, Provenance, Integrity, Dependency Mapping and Risk Architecture

### AI Model Supply-Chain Foundations

1 — **AI-MSC-001 — AI Model Supply-Chain Definition**
The AI model supply chain comprises the people, organizations, datasets, software, models, model artifacts, repositories, platforms, infrastructure, services, processes, and dependencies involved in acquiring, developing, modifying, distributing, deploying, operating, monitoring, and retiring AI models.

2 — **AI-MSC-002 — Model Supply-Chain Security Objective**
AI model supply-chain governance should protect the confidentiality, integrity, availability, authenticity, provenance, reliability, security, and appropriate use of models throughout their lifecycle.

3 — **AI-MSC-003 — Model Supply-Chain Risk Definition**
AI model supply-chain risk arises when weaknesses or compromise affecting a model, model artifact, provider, publisher, repository, dataset, software dependency, transformation process, distribution mechanism, or deployment environment can adversely affect an AI system.

4 — **AI-MSC-004 — Model Supply-Chain Scope Principle**
Model supply-chain governance should address both the model itself and material dependencies required to create, transform, distribute, deploy, serve, evaluate, secure, and operate it.

5 — **AI-MSC-005 — Model Supply-Chain Lifecycle Principle**
Model supply-chain controls should apply from model sourcing and acquisition through validation, approval, deployment, operation, modification, monitoring, migration, and retirement.

6 — **AI-MSC-006 — Model Supply-Chain Trust Principle**
Trust in an AI model should be based on appropriate evidence concerning identity, provenance, integrity, security, quality, intended use, licensing, and operational context.

7 — **AI-MSC-007 — Model Supply-Chain Accountability Principle**
Organizations should establish clear accountability for model acquisition, validation, approval, deployment, monitoring, incident response, and retirement.

8 — **AI-MSC-008 — Model Supply-Chain Risk-Based Governance**
The depth of supply-chain controls should be proportionate to model criticality, intended use, data sensitivity, autonomy, exposure, privilege, downstream impact, and dependency concentration.

9 — **AI-MSC-009 — Model Supply-Chain Defense-in-Depth Principle**
Model supply-chain security should use multiple complementary controls across acquisition, provenance, integrity, validation, deployment, monitoring, and recovery.

10 — **AI-MSC-010 — Model Supply-Chain Zero-Trust Principle**
Models and model artifacts should not receive implicit trust solely because they originate from a known marketplace, repository, provider, publisher, research organization, or open-source ecosystem.

### Model Supply-Chain Participants

11 — **AI-MSC-011 — Model Provider Role**
A model provider is an organization or service responsible for supplying, hosting, distributing, or otherwise making a model available.

12 — **AI-MSC-012 — Model Publisher Role**
A model publisher is the party that publishes or distributes a model artifact, model release, repository, package, or associated documentation.

13 — **AI-MSC-013 — Model Developer Role**
The model developer is the party responsible for developing or materially modifying the model or its associated training and engineering processes.

14 — **AI-MSC-014 — Model Maintainer Role**
The model maintainer is responsible for maintaining model releases, documentation, updates, security information, or related project infrastructure.

15 — **AI-MSC-015 — Model Consumer Role**
The model consumer is the organization or party that acquires or uses a model within an AI system.

16 — **AI-MSC-016 — Model Owner Role**
The model owner is accountable for the governance and operational use of a model within the organization.

17 — **AI-MSC-017 — Model Custodian Role**
The model custodian is responsible for technical storage, access, integrity, deployment, or operational administration of model artifacts.

18 — **AI-MSC-018 — Model Distributor Role**
A distributor is a party that makes a model available through a marketplace, repository, registry, API, hosted service, package, or other distribution mechanism.

19 — **AI-MSC-019 — Model Service Provider Role**
A model service provider operates infrastructure or services through which an organization consumes model capabilities without necessarily possessing the underlying model artifact.

20 — **AI-MSC-020 — Upstream Dependency Role**
An upstream dependency is any external model, dataset, software component, service, infrastructure component, or other resource materially required by a downstream model.

21 — **AI-MSC-021 — Downstream Consumer Role**
A downstream consumer is an application, model, service, business process, or organization that relies upon the outputs or capabilities of a model.

22 — **AI-MSC-022 — Fourth-Party Model Dependency**
A fourth-party model dependency exists where an organization's provider itself relies on another model provider, repository, dataset, software component, cloud platform, or other upstream dependency.

23 — **AI-MSC-023 — Supply-Chain Responsibility Mapping**
Material relationships among providers, publishers, developers, maintainers, distributors, consumers, and upstream dependencies should be documented where they affect security or accountability.

24 — **AI-MSC-024 — Responsibility Boundary Principle**
Organizations should identify which supply-chain controls are performed internally, by the model provider, by another third party, or through shared responsibility.

25 — **AI-MSC-025 — Accountability Persistence Principle**
Use of a third-party model does not by itself eliminate the organization's responsibility for risks arising from its own deployment and use of that model.

### Model Distribution and Deployment Classification

26 — **AI-MSC-026 — Hosted Model Classification**
A hosted model is consumed through a provider-controlled service without the organization necessarily obtaining the underlying model artifact.

27 — **AI-MSC-027 — Downloadable Model Classification**
A downloadable model is distributed as an artifact that can be obtained and potentially operated within an organization's environment.

28 — **AI-MSC-028 — Open-Weight Model Classification**
An open-weight model provides model parameters or weights under specified terms but may not provide complete source code, training data, or unrestricted rights.

29 — **AI-MSC-029 — Open-Source Model Classification**
A model should not be classified as fully open-source merely because weights are publicly available; source, licensing, training information, and other relevant openness characteristics should be separately assessed.

30 — **AI-MSC-030 — Source-Available Model Classification**
Source-available model distributions should be evaluated according to their actual licensing, source availability, weights availability, modification rights, redistribution rights, and operational restrictions.

31 — **AI-MSC-031 — API Model Classification**
An API model is accessed through an external interface and may create dependencies on provider infrastructure, model versions, service availability, authentication, data processing, and contractual terms.

32 — **AI-MSC-032 — Self-Hosted Model Classification**
A self-hosted model is operated within infrastructure controlled by the organization or its designated infrastructure provider.

33 — **AI-MSC-033 — Managed Model Classification**
A managed model is operated through a platform where the organization may control some configuration or deployment characteristics while the provider manages other elements of the model environment.

34 — **AI-MSC-034 — Hybrid Model Classification**
Hybrid model deployments may combine locally operated models with external APIs, hosted components, cloud services, datasets, software dependencies, or external inference services.

35 — **AI-MSC-035 — Model Distribution-Path Principle**
The organization should identify how each material model is acquired, transported, stored, transformed, deployed, and accessed.

36 — **AI-MSC-036 — Distribution Trust-Boundary Principle**
Trust boundaries should be identified between model publishers, repositories, distribution services, organizational environments, and production deployments.

37 — **AI-MSC-037 — Model Deployment Boundary**
The boundary between externally supplied model artifacts and organizational deployment environments should be explicitly defined.

38 — **AI-MSC-038 — Model Hosting Boundary**
Where models are hosted externally, organizations should identify which model, infrastructure, data, security, and operational controls are managed by the provider and which remain under organizational control.

39 — **AI-MSC-039 — Model Transfer Boundary**
Model transfer processes should protect model artifacts against unauthorized modification, substitution, interception, or corruption.

40 — **AI-MSC-040 — Model Storage Boundary**
Stored model artifacts should be protected according to their confidentiality, integrity, licensing, business value, and security requirements.

### Model Criticality and Risk Classification

41 — **AI-MSC-041 — Model Criticality Classification**
Organizations should classify models according to their potential impact on business operations, security, safety, privacy, compliance, financial outcomes, and customers.

42 — **AI-MSC-042 — Model Business Criticality**
Business-critical models should receive enhanced supply-chain governance proportional to the consequences of compromise or unavailability.

43 — **AI-MSC-043 — Model Security Criticality**
Models supporting security controls, fraud detection, identity decisions, monitoring, threat detection, or other security-sensitive functions should receive appropriate enhanced assurance.

44 — **AI-MSC-044 — Model Data Sensitivity Classification**
Model supply-chain risk should consider the sensitivity of data that the model processes, accesses, generates, stores, or may infer.

45 — **AI-MSC-045 — Model Privilege Classification**
Models with access to privileged applications, systems, credentials, tools, APIs, or administrative functions should receive enhanced security controls.

46 — **AI-MSC-046 — Model Autonomy Classification**
Models capable of independently initiating actions, invoking tools, executing code, modifying systems, or influencing external processes should receive controls proportionate to their autonomy.

47 — **AI-MSC-047 — Model Exposure Classification**
Internet-facing, externally accessible, multi-tenant, or broadly distributed models should receive controls proportionate to their exposure.

48 — **AI-MSC-048 — Model Dependency Criticality**
Model criticality should consider dependencies on external providers, repositories, software, datasets, cloud infrastructure, and other supply-chain components.

49 — **AI-MSC-049 — Model Replacement Difficulty**
Risk assessment should consider the difficulty and time required to replace a material model.

50 — **AI-MSC-050 — Model Supply-Chain Risk Tiering**
Organizations may establish internal risk tiers for models based on criticality, sensitivity, autonomy, exposure, dependency, and potential downstream impact.

### Model Inventory and Discovery

51 — **AI-MSC-051 — Enterprise Model Inventory**
Organizations should maintain an inventory of material AI models used, developed, hosted, or integrated within their environment.

52 — **AI-MSC-052 — Model Identity Record**
Each material model should have a sufficiently precise identity record.

53 — **AI-MSC-053 — Model Name and Identifier**
Model inventories should record model name, identifier, repository or provider reference, and other information necessary to distinguish the model.

54 — **AI-MSC-054 — Model Version Record**
Material model versions should be recorded and associated with deployment and approval information.

55 — **AI-MSC-055 — Model Variant Record**
Material variants such as quantized, distilled, fine-tuned, merged, adapter-enhanced, or converted versions should be separately identifiable where their security or behavior differs.

56 — **AI-MSC-056 — Model Artifact Identifier**
Material model artifacts should have unique or sufficiently precise identifiers supporting integrity and traceability.

57 — **AI-MSC-057 — Model Deployment Record**
Inventory records should identify where each material model is deployed or consumed.

58 — **AI-MSC-058 — Model Application Mapping**
Models should be mapped to applications, services, business processes, and relevant infrastructure.

59 — **AI-MSC-059 — Model Dataset Mapping**
Where known and appropriate, material relationships between models and datasets should be recorded.

60 — **AI-MSC-060 — Model Software Dependency Mapping**
Material relationships between models and software dependencies should be documented.

61 — **AI-MSC-061 — Model Provider Mapping**
Inventory records should identify the provider, publisher, developer, or other relevant upstream party associated with a material model.

62 — **AI-MSC-062 — Model Supply-Chain Dependency Graph**
Organizations should maintain sufficient dependency information to identify upstream and downstream relationships involving material models.

63 — **AI-MSC-063 — Shadow Model Discovery**
Organizations should periodically identify models operating outside approved inventory, procurement, development, or governance processes.

64 — **AI-MSC-064 — Unauthorized Model Detection**
Unauthorized model artifacts, repositories, APIs, or model services should be detected where technically feasible.

65 — **AI-MSC-065 — Model Inventory Reconciliation**
Model inventories should be reconciled against model registries, repositories, deployment platforms, API usage, container images, storage systems, and relevant application inventories.

66 — **AI-MSC-066 — Model Inventory Completeness**
Organizations should periodically assess whether their model inventory adequately represents material models across development, testing, staging, production, and externally hosted environments.

67 — **AI-MSC-067 — Model Inventory Accuracy**
Material model inventory information should remain sufficiently accurate and current to support security, governance, incident response, and audit activities.

68 — **AI-MSC-068 — Model Inventory Ownership**
Material model inventories should have accountable ownership for maintenance, reconciliation, and data quality.

69 — **AI-MSC-069 — Model Discovery Principle**
Model discovery should consider both formally registered models and models acquired or deployed through less-controlled channels.

70 — **AI-MSC-070 — Model Portfolio Visibility Principle**
Organizations should maintain sufficient portfolio-level visibility to understand the number, type, criticality, ownership, dependency, and exposure of material models.

### Model Provenance

71 — **AI-MSC-071 — Model Provenance Requirement**
Material model artifacts should have sufficient provenance information to establish their origin and relevant transformation history.

72 — **AI-MSC-072 — Model Origin Record**
The origin of a material model should be recorded where reasonably available and relevant to the organization's risk.

73 — **AI-MSC-073 — Model Publisher Provenance**
The publisher or source responsible for distributing a material model should be identifiable.

74 — **AI-MSC-074 — Model Developer Provenance**
Where relevant and available, the developer or organization responsible for model development should be recorded.

75 — **AI-MSC-075 — Model Training Provenance**
Material information concerning the model's training process should be recorded where available and appropriate to the use case.

76 — **AI-MSC-076 — Training Dataset Provenance**
Where training-data provenance information is available and material to risk, it should be evaluated as part of model supply-chain due diligence.

77 — **AI-MSC-077 — Fine-Tuning Provenance**
Fine-tuned models should maintain sufficient provenance concerning the base model, fine-tuning process, relevant datasets, and material modifications.

78 — **AI-MSC-078 — Adapter Provenance**
Adapters, LoRA components, prompt-tuning artifacts, or other model modifications should maintain provenance linking them to the underlying model where relevant.

79 — **AI-MSC-079 — Quantization Provenance**
Quantized model artifacts should retain sufficient information to identify the source model, quantization process, tooling, and resulting artifact.

80 — **AI-MSC-080 — Distillation Provenance**
Distilled models should maintain relevant provenance concerning the source or teacher model, distillation process, and resulting model artifact.

81 — **AI-MSC-081 — Model Merge Provenance**
Merged models should maintain sufficient provenance to identify contributing models, merge methodology, tooling, and resulting artifact.

82 — **AI-MSC-082 — Model Conversion Provenance**
Models converted between formats should maintain traceability to the source artifact and conversion process.

83 — **AI-MSC-083 — Model Wrapper Provenance**
Material wrappers, orchestration layers, inference adapters, or other software components that materially alter model behavior should be identifiable.

84 — **AI-MSC-084 — Model Transformation Lineage**
Material model transformations should maintain lineage information sufficient to understand how the deployed artifact was derived.

85 — **AI-MSC-085 — Model Lineage Record**
Model lineage should connect relevant source model, modifications, transformation tools, artifacts, versions, and deployment instances.

86 — **AI-MSC-086 — Provenance Completeness Assessment**
Organizations should assess whether available provenance information is sufficiently complete for the intended risk decision.

87 — **AI-MSC-087 — Provenance Currency**
Provenance records should remain current when models are materially modified or transformed.

88 — **AI-MSC-088 — Provenance Evidence Retention**
Relevant provenance evidence should be retained according to organizational requirements and the model's risk.

89 — **AI-MSC-089 — Provenance Gap Management**
Material gaps in model provenance should be documented and considered in the model risk decision.

90 — **AI-MSC-090 — Provenance Trust Principle**
Model provenance should be evaluated using evidence rather than relying solely on documentation or publisher assertions.

### Model Artifact Integrity

91 — **AI-MSC-091 — Model Artifact Integrity Requirement**
Material model artifacts should be protected against unauthorized modification, substitution, corruption, or tampering.

92 — **AI-MSC-092 — Model Hash Control**
Cryptographic hashes should be used where appropriate to establish the integrity of model artifacts.

93 — **AI-MSC-093 — Model Signature Control**
Digital signatures or equivalent integrity mechanisms should be used for material model artifacts where supported and justified by risk.

94 — **AI-MSC-094 — Signature Verification Control**
Model deployment processes should verify required artifact signatures before allowing models into protected environments.

95 — **AI-MSC-095 — Model Integrity Baseline**
Approved model artifacts should have a trusted integrity baseline against which subsequent copies or deployments can be compared.

96 — **AI-MSC-096 — Model Artifact Reconciliation**
Deployed model artifacts should be reconciled against approved model versions, hashes, signatures, or other trusted identifiers.

97 — **AI-MSC-097 — Model Tampering Detection**
Organizations should implement mechanisms appropriate to detect unauthorized modification of material model artifacts.

98 — **AI-MSC-098 — Model Substitution Detection**
Organizations should detect unauthorized replacement of an approved model with another model or variant.

99 — **AI-MSC-099 — Model Mirror Integrity**
Models obtained through mirrors or secondary repositories should be validated against trusted origin and integrity information where possible.

100 — **AI-MSC-100 — Model Distribution Integrity**
Model integrity controls should extend across acquisition, transfer, storage, transformation, deployment, and runtime environments.

101 — **AI-MSC-101 — Model Repository Integrity**
Repositories storing material model artifacts should implement controls against unauthorized modification or replacement.

102 — **AI-MSC-102 — Model Registry Integrity**
Model registries should protect model metadata, version records, deployment references, and approval status against unauthorized modification.

103 — **AI-MSC-103 — Model Storage Integrity**
Storage systems holding material model artifacts should implement appropriate integrity protection and access controls.

104 — **AI-MSC-104 — Model Backup Integrity**
Backups of critical model artifacts should retain sufficient integrity and provenance information to support trusted recovery.

105 — **AI-MSC-105 — Model Artifact Immutability**
Material approved model artifacts should be stored immutably or otherwise protected against unauthorized post-approval modification where practical.

106 — **AI-MSC-106 — Model Promotion Integrity**
Models should move through controlled acquisition, validation, approval, staging, and production promotion processes.

107 — **AI-MSC-107 — Model Deployment Artifact Control**
Production deployment should use an approved model artifact rather than an independently retrieved or reconstructed version.

108 — **AI-MSC-108 — Model Rollback Integrity**
Rollback procedures should use previously validated model artifacts whose integrity and provenance remain sufficiently established.

109 — **AI-MSC-109 — Model Integrity Exception**
Where integrity cannot be established for a material model artifact, the organization should document the resulting uncertainty and risk decision.

110 — **AI-MSC-110 — Model Integrity Principle**
Material model artifacts should remain traceable to approved and integrity-validated versions throughout their operational lifecycle.

Repositories used to acquire, publish, store, or distribute material models should be governed according to their security and operational importance.

112 — **AI-MSC-112 — Repository Authentication Control**

115 — **AI-MSC-115 — Repository MFA Control**
Multi-factor authentication should be used for privileged access to material model repositories where supported and appropriate.

117 — **AI-MSC-117 — Repository Credential Protection**
Repository credentials, tokens, API keys, certificates, and other secrets should be protected against unauthorized access.

118 — **AI-MSC-118 — Repository Audit Logging**
Material repository activities should generate audit records sufficient to support security monitoring and investigation.

119 — **AI-MSC-119 — Model Publication Control**
Publication of material models or model versions should require appropriate authorization and integrity controls.

120 — **AI-MSC-120 — Model Version Publication Control**
New model versions should have controlled publication processes that preserve version identity and provenance.

121 — **AI-MSC-121 — Repository Change Monitoring**
Material changes to repository configurations, access controls, model artifacts, metadata, or administrative settings should be monitored.

122 — **AI-MSC-122 — Publisher Account Protection**

### Model Acquisition and Admission

127 — **AI-MSC-127 — Model Acquisition Governance**
Acquisition of material third-party models should follow defined security, governance, licensing, provenance, and approval processes.

128 — **AI-MSC-128 — Model Acquisition Source Control**
Models should be acquired from approved sources or undergo additional assessment when obtained through nonstandard channels.

129 — **AI-MSC-129 — Model Acquisition Identity Verification**
Organizations should verify the identity and expected source of material model artifacts before use.

130 — **AI-MSC-130 — Model Download Security**
Downloaded model artifacts should be subject to appropriate integrity, malware, file, archive, serialization, and provenance checks.

131 — **AI-MSC-131 — Model Acquisition Quarantine**
New or untrusted model artifacts should initially be placed in controlled environments before production admission where appropriate.

132 — **AI-MSC-132 — Model Admission Criteria**
Organizations should define model admission criteria covering identity, provenance, integrity, licensing, security, evaluation, intended use, and other material risk factors.

133 — **AI-MSC-133 — Model Allowlist Control**
Critical production environments should use approved model allowlists where practical.

134 — **AI-MSC-134 — Model Denylist Control**
Known malicious, compromised, prohibited, or unauthorized models should be blocked where technically feasible.

135 — **AI-MSC-135 — Shadow Model Admission Control**
Models discovered outside approved processes should not automatically be promoted to production without appropriate assessment.

136 — **AI-MSC-136 — Model Environment Separation**
Experimental, research, development, testing, and production models should be appropriately separated.

137 — **AI-MSC-137 — Model Promotion Gate**
Model promotion should require completion of applicable security, evaluation, provenance, licensing, and approval controls.

138 — **AI-MSC-138 — Model Admission Exception**

139 — **AI-MSC-139 — Model Admission Evidence**
Model admission decisions should retain evidence supporting the decision.

140 — **AI-MSC-140 — Model Acquisition Principle**
Model acquisition should establish sufficient trust before a model is introduced into a material AI environment.

### Model Security and Malicious Model Risk

141 — **AI-MSC-141 — Malicious Model Risk**
Organizations should consider the possibility that externally acquired models may contain malicious, compromised, manipulated, or intentionally unsafe behavior.

142 — **AI-MSC-142 — Model Backdoor Risk**
Model supply-chain assessments should consider the possibility of hidden behaviors triggered by specific inputs, patterns, conditions, or activation mechanisms.

143 — **AI-MSC-143 — Model Poisoning Risk**
Where relevant evidence exists, organizations should consider whether compromised training or fine-tuning processes could introduce malicious or degraded model behavior.

144 — **AI-MSC-144 — Triggered-Behavior Assessment**
Material models should be evaluated for unexpected behavior under relevant input conditions where justified by risk.

145 — **AI-MSC-145 — Model Behavior Baseline**
Organizations should establish appropriate behavioral baselines for material models to support detection of significant unexpected changes.

146 — **AI-MSC-146 — Model Evasion Risk**
Models used in security-sensitive applications should be assessed for evasion or adversarial manipulation risks appropriate to the use case.

147 — **AI-MSC-147 — Model Extraction Risk**
Where model confidentiality is material, organizations should consider risks associated with unauthorized model extraction or replication.

148 — **AI-MSC-148 — Model Membership-Inference Risk**
Where applicable, organizations should consider whether model behavior could reveal information about training data or other protected information.

149 — **AI-MSC-149 — Model Memorization Risk**
Material models should be assessed for inappropriate memorization or disclosure behavior where relevant to the use case.

150 — **AI-MSC-150 — Model Integrity Attack Surface**
Supply-chain assessments should consider attacks against model files, weights, metadata, conversion tools, serialization formats, repositories, and deployment pipelines.

151 — **AI-MSC-151 — Unsafe Serialization Risk**
Model acquisition and deployment processes should consider risks associated with unsafe model serialization and deserialization formats.

152 — **AI-MSC-152 — Model Artifact Malware Risk**
Model artifacts and associated files should be screened for malicious content where technically feasible.

153 — **AI-MSC-153 — Model Archive Security**
Compressed model archives should be inspected and processed securely to reduce archive-based attack risks.

154 — **AI-MSC-154 — Model Parser Security**
Software used to parse model formats should be treated as part of the model supply-chain attack surface.

155 — **AI-MSC-155 — Model Conversion Security**
Model conversion tools should be assessed for vulnerabilities, malicious behavior, integrity risks, and unauthorized code execution.

156 — **AI-MSC-156 — Model Runtime Isolation**
Untrusted or high-risk models should be executed within appropriate isolation boundaries.

157 — **AI-MSC-157 — Model Runtime Least Privilege**
Model runtimes should receive only the system, filesystem, network, cloud, and application privileges necessary for operation.

158 — **AI-MSC-158 — Model Network Restriction**
Model runtimes should have controlled network access appropriate to the model's intended functionality and risk.

159 — **AI-MSC-159 — Model Egress Control**
Outbound network connections initiated by model-serving environments should be restricted and monitored where appropriate.

160 — **AI-MSC-160 — Model Execution Boundary**
Where a model can indirectly influence code execution, tool invocation, package installation, or external actions, additional execution boundaries should be implemented.

Material model versions should be uniquely identifiable and governed throughout their lifecycle.

Model changes should be classified according to their potential impact on security, behavior, reliability, privacy, compliance, and operational performance.

Material changes to model architecture, weights, training, fine-tuning, or capabilities should undergo appropriate review and validation.

179 — **AI-MSC-179 — Minor Model Change Control**

184 — **AI-MSC-184 — Model Security Regression Testing**

185 — **AI-MSC-185 — Model Evaluation Reassessment**

186 — **AI-MSC-186 — Model Rollback Control**

187 — **AI-MSC-187 — Model Rollback Validation**

190 — **AI-MSC-190 — Model Change Evidence**
