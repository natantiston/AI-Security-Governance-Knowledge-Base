# 16.14 — AI Software Supply-Chain Assurance

## Part 1 — Foundations, Assurance Scope, Software Supply-Chain Trust, Assurance Objectives, Evidence and Risk Architecture

### 1. AI Software Supply-Chain Assurance Definition

AI software supply-chain assurance is the structured process of obtaining, evaluating, validating, and maintaining evidence that software used to build, deploy, operate, secure, and govern AI systems is sufficiently trustworthy for its intended use.

AI software supply-chain assurance extends conventional software assurance to account for AI-specific dependencies such as:

* Machine-learning frameworks
* Inference engines
* Model-serving runtimes
* Tokenizers
* Embedding libraries
* Vector-database clients
* AI SDKs
* Agent frameworks
* Tool-integration libraries
* Model-conversion utilities
* Evaluation frameworks
* AI security tooling
* Data-processing libraries

---

### 2. Assurance Objective

The primary objective is to provide reasonable confidence that material AI software dependencies:

* Are correctly identified
* Originate from sufficiently trusted sources
* Have appropriate provenance
* Have not been materially tampered with
* Are appropriately secured
* Are evaluated for vulnerabilities
* Are subject to appropriate lifecycle management
* Remain consistent with approved architecture and risk decisions

---

### 3. Assurance Is Not Absolute Trust

Assurance does not establish that a software component is universally safe.

It establishes a level of confidence based on:

* Scope
* Evidence
* Testing
* Validation
* Risk
* Context
* Time

**Assurance ≠ absolute security.**

* Unsafe software behavior

The core principles are:

**Software inventory ≠ assurance.**

**SBOM ≠ assurance.**

**AIBOM ≠ assurance.**

**Supplier assertion ≠ independent assurance.**

**Certification ≠ universal security.**

**Vulnerability scanning ≠ vulnerability elimination.**

**Vulnerability severity ≠ complete risk assessment.**

**Remediation reported ≠ remediation verified.**

**Artifact signature ≠ trusted software unless the signing trust chain is appropriately validated.**

**Build provenance ≠ build integrity.**

**Static composition ≠ runtime composition.**

**Approved software ≠ permanently trusted software.**

**Open-source software ≠ automatically trusted software.**

**Commercial software ≠ automatically secure software.**

**Popular software ≠ automatically low-risk software.**

**Continuous monitoring ≠ guaranteed detection.**

**Recovery capability ≠ recovery assurance unless recovery is appropriately tested.**

**Alternative provider ≠ independent alternative.**

**Exit plan ≠ executable exit capability.**

**Internal assurance control ≠ statutory requirement.**

**Regulatory mapping ≠ regulatory applicability.**

**AI-assisted analysis ≠ independent assurance.**

**Risk acceptance ≠ risk elimination.**

**Assurance evidence must remain sufficiently current, relevant, traceable, and proportionate to the decision being made.**
