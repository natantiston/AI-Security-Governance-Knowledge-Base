# 16.14 — Model Provenance and Supply-Chain Integrity

## Part 1 — Model Provenance, Supply-Chain Integrity, Trust Boundaries and Governance Foundations

### 1. Definition of Model Provenance

Model provenance is the documented history and origin of an AI model and its significant transformations throughout its lifecycle.

Provenance can describe:

* Model origin
* Model publisher
* Model developer
* Parent model
* Training process
* Training datasets
* Fine-tuning datasets
* Fine-tuning activities
* Model transformations
* Model versions
* Evaluation activities
* Distribution channels
* Deployment artifacts
* Model consumers

Model provenance therefore answers a fundamental governance question:

**Where did this model come from, and what happened to it before it reached the organization?**

### 2. Purpose of Model Provenance

The purpose of model provenance is to establish sufficient evidence about the origin, lineage, transformation, ownership, and distribution of a model to support security, governance, risk management, assurance, and incident investigation.

Provenance can help an organization determine:

* Who produced the model
* Which model version was obtained
* Which parent model was used
* Which datasets contributed to development
* Which transformations occurred
* Which evaluation activities were performed
* Which repository or marketplace supplied the artifact
* Whether the deployed model corresponds to the approved model
* Whether unauthorized modifications occurred

Provenance is therefore an important component of model supply-chain visibility.

---

### 3. Definition of Model Supply-Chain Integrity

Model supply-chain integrity is the ability to maintain confidence that a model artifact, its associated metadata, and relevant supply-chain processes have not been improperly altered, substituted, corrupted, or compromised.

Integrity concerns whether an approved artifact remains the artifact that was intended to be acquired, evaluated, approved, distributed, and deployed.

```text id="mpsi16p14-02"
        Approved Model Artifact
                 |
                 v
          Integrity Controls
                 |
       +---------+---------+
       |         |         |
      Hash    Signature   Provenance
       |         |         |
       +---------+---------+
                 |
                 v
        Deployment Artifact
```

Model integrity should be considered across the complete supply chain rather than only at the point of model download.

---

### 4. Model Provenance versus Model Integrity

Model provenance and model integrity address different questions.

**Provenance** asks:

> Where did the model come from and how did it evolve?

**Integrity** asks:

> Has the model or relevant artifact been altered or substituted in an unauthorized manner?

A model may have well-documented provenance but still be modified after acquisition.

Conversely, an artifact may have a verified hash while its original source, development history, or training provenance remains unknown.

Therefore:

**Provenance ≠ Integrity.**

### 6. Model Lineage

Model lineage describes the relationships between a model and the models, datasets, processes, or artifacts from which it was derived.

Lineage can include:

* Parent models
* Fine-tuned models
* Distilled models
* Quantized models
* Converted models
* Adapted models
* Merged models
* Specialized variants
* Deployment-specific versions

Lineage is particularly important when an organization uses a model that is derived from another model but is distributed under a different name or identifier.

### 7. Model Parentage

Model parentage identifies the model or models from which a derivative model originated.

For example:

* Security analysis
* Licensing
* Evaluation scope
* Vulnerability assessment
* Model behavior
* Regulatory analysis
* Supply-chain dependency
* Exit planning

A derivative model should not automatically be treated as independent from its parent model.

### 8. Model Transformation

Model transformation is any material process that changes a model artifact or its operational characteristics.

Examples include:

* Fine-tuning
* Quantization
* Pruning
* Distillation
* Weight conversion
* Architecture conversion
* Adapter application
* Merging
* Compression
* Serialization
* Optimization
* Format conversion

Each material transformation can create a new provenance event.

### 9. Model Artifact

A model artifact is the technical representation of a model that can be stored, transferred, evaluated, or deployed.

Examples include:

* Model weights
* Checkpoints
* Serialized models
* Model packages
* Containerized model artifacts
* Adapter packages
* Configuration files
* Tokenizer files
* Supporting model metadata

The artifact may consist of multiple files or components.

Therefore, model integrity should not necessarily be assessed only against a single file.

---

### 10. Model Weights

Model weights are numerical parameters that encode learned representations within a machine-learning model.

Weights can represent a critical security and intellectual-property component of an AI system.

Unauthorized modification of model weights may affect:

* Model behavior
* Security properties
* Safety characteristics
* Accuracy
* Bias
* Classification behavior
* Refusal behavior
* Tool-use behavior
* Output generation

Weight integrity should therefore be considered separately from application-code integrity.

---

### 11. Model Checkpoint

A model checkpoint is a saved representation of model state at a particular stage of development or training.

Checkpoints can exist during:

* Pre-training
* Fine-tuning
* Reinforcement learning
* Evaluation
* Experimentation
* Recovery
* Production deployment

Checkpoint governance should establish:

* Identity
* Version
* Storage location
* Access control
* Integrity protection
* Retention
* Provenance
* Approval status

Unauthorized checkpoint substitution can introduce supply-chain risk.

---

### 12. Model Serialization

Model serialization is the representation of model data and associated state in a format that can be stored or transferred.

Serialization formats can introduce security considerations because loading a model may involve processing structured or executable content depending on the technology used.

Organizations should therefore evaluate:

* Serialization format
* Deserialization behavior
* Parser security
* Code-execution risk
* Dependency requirements
* File integrity
* Source trust
* Compatibility
* Validation controls

**Model file ≠ automatically safe model file.**

---

### 13. Model Repository

A model repository is a storage or distribution location from which model artifacts can be obtained or managed.

Repositories may be:

* Internal
* Private
* Vendor-operated
* Public
* Community-operated
* Marketplace-based
* Cloud-hosted
* Enterprise-managed

Repository governance should consider:

* Ownership
* Authentication
* Authorization
* Artifact integrity
* Version management
* Access logging
* Retention
* Availability
* Change history

### 14. Trusted Model Repository

A trusted model repository is a repository that has been explicitly approved by the organization based on defined security, governance, provenance, and operational criteria.

Trust should not be based solely on:

* Popularity
* Download volume
* Public availability
* Brand recognition
* Community reputation
* Repository age

An organization should establish objective criteria for repository trust.

### 15. Model Publisher

A model publisher is the organization, group, or individual responsible for distributing a model artifact.

Publisher identity can be relevant to:

* Accountability
* Support
* Security notifications
* Licensing
* Provenance
* Vulnerability disclosure
* Incident coordination
* Model updates

Publisher identity should be distinguished from the repository hosting the model.

**Repository ≠ Publisher.**

### 16. Model Maintainer

Maintainer assessment can consider:

* Identity
* Organizational ownership
* Security practices
* Release practices
* Vulnerability handling
* Update frequency
* Documentation
* Responsiveness
* Change governance
* Continuity

A repository can remain available even when active maintenance has effectively stopped.

### 18. Model Acquisition

### 21. Model Hash

A model hash is a cryptographic digest calculated from a model artifact or relevant set of files.

Hash verification can determine whether the artifact being examined corresponds to the artifact associated with the expected digest.

```text id="mpsi16p14-10"
Expected Model
      |
      v
Expected Hash
      |
      |
Actual Model
      |
      v
Calculated Hash
      |
      +------ Match ------> Integrity Consistent
      |
      +------ Mismatch ---> Investigate
```

A hash mismatch can indicate:

* Modification
* Corruption
* Wrong version
* File replacement
* Incomplete download
* Packaging difference

However:

**Hash verification ≠ Model Trustworthiness.**

A malicious artifact can have a perfectly valid hash.

---

### 22. Model Signature

A model signature is a cryptographic mechanism used to provide evidence regarding the origin and integrity of an artifact.

Signature verification can help establish that an artifact corresponds to a signing identity and has not been modified after signing, assuming the signing infrastructure and key are trusted.

Organizations should consider:

* Signing authority
* Key protection
* Certificate validity
* Key rotation
* Revocation
* Signature verification
* Trusted root
* Signing-process security

**Valid signature ≠ Secure Model.**

---

### 23. Model Authenticity

Model authenticity concerns whether the model artifact actually originated from the claimed source or signing authority.

Authenticity controls can include:

* Verified publisher identity
* Cryptographic signatures
* Trusted certificates
* Secure distribution channels
* Repository authentication
* Provenance evidence
* Artifact identifiers

Authenticity should be distinguished from security.

An authentic model can still contain:

* Vulnerabilities
* Unsafe behavior
* Malicious design choices
* Inadequate safeguards
* Defective dependencies

Therefore:

**Authenticity ≠ Security.**

---

### 24. Model Tampering

Model tampering is unauthorized modification of a model artifact, associated metadata, or relevant supply-chain component.

Tampering may occur during:

* Storage
* Transfer
* Packaging
* Conversion
* Registry operations
* Deployment
* Maintenance

Potential consequences include:

* Behavioral modification
* Backdoor insertion
* Security degradation
* Safety degradation
* Unauthorized functionality
* Data leakage
* Policy bypass

Tampering controls should therefore cover both technical artifacts and relevant supply-chain processes.

---

### 25. Model Substitution

Model substitution occurs when an expected model is replaced with a different model.

Substitution can be accidental or malicious.

Examples include:

* Wrong model version
* Wrong repository artifact
* Compromised download
* Registry replacement
* Deployment configuration error
* Dependency redirection
* Unauthorized model update

     |
     v

### 26. Model Backdoor Risk

A model backdoor is behavior intentionally or unintentionally introduced so that the model behaves differently under specific conditions.

A backdoor may be triggered by:

* Specific inputs
* Tokens
* Images
* Patterns
* Context
* Metadata
* Hidden conditions
* Specific users
* Specific environments

Supply-chain governance should recognize that provenance and integrity controls alone may not detect every behavioral backdoor.

---

Potential poisoning locations include:

* Training datasets
* Fine-tuning datasets
* Labels
* Training pipelines
* Checkpoints
* Evaluation datasets
* Model repositories
* Feedback systems

### 28. Model Supply-Chain Compromise

A model supply-chain compromise occurs when an attacker or unauthorized party compromises one or more components involved in the development, distribution, storage, evaluation, or deployment of a model.

Potential compromise points include:

* Developer accounts
* Source repositories
* Model repositories
* Training infrastructure
* Evaluation infrastructure
* Signing keys
* CI/CD systems
* Model registries
* Cloud storage
* Deployment pipelines

Supply-chain security should therefore address the complete chain rather than only the model file.

### 35. Provenance Completeness

Provenance completeness is the degree to which relevant stages and dependencies in the model's history are known and documented.

Complete provenance may be difficult when models originate from complex external ecosystems.

Examples of provenance gaps include:

* Unknown parent model
* Unknown training dataset
* Unknown transformation
* Unknown maintainer
* Unknown release history
* Unknown evaluation process
* Unknown dependency

A provenance gap should not automatically be interpreted as evidence of compromise, but it should be recognized as an assurance limitation.

### 36. Provenance Verification

Provenance verification is the process of evaluating whether available provenance claims are supported by credible evidence.

Verification can include:

* Source validation
* Publisher verification
* Repository verification
* Signature validation
* Release-history review
* Lineage validation
* Metadata consistency checks
* Artifact comparison
* Independent evidence

A provenance statement should not automatically be treated as verified merely because it is published by the model provider.

### 37. Model Integrity Monitoring

Model integrity monitoring involves ongoing mechanisms for detecting unexpected changes to model artifacts or relevant supply-chain components.

### 39. Model Version Pinning

Model version pinning means explicitly specifying which model version or artifact an application is authorized to use.

Version pinning can reduce unexpected behavioral or security changes caused by automatic model replacement.

However, version pinning can also create:

* Patch delays
* Vulnerability exposure
* Unsupported-version risk
* Operational maintenance burden

Therefore, version pinning should operate together with vulnerability and lifecycle management.

### 41. Model Change

A model change is any material modification to the model, model artifact, configuration, dependencies, or supporting supply-chain components that may affect security, behavior, performance, privacy, or operational risk.

Examples include:

* New model version
* Fine-tuning
* Weight modification
* Quantization
* New adapter
* New tokenizer
* New runtime
* New API provider
* New deployment environment

Material changes should be subject to an appropriate change-management process.

### 42. Model Behavioral Integrity

Model behavioral integrity concerns whether the model continues to behave within approved and expected boundaries.

This is distinct from cryptographic integrity.

A model can have the same hash and still produce outputs that are inappropriate for a particular business context because:

* The evaluation criteria were inadequate
* The original model was unsuitable
* The deployment context changed
* Inputs changed
* Prompts changed
* External tools changed
* Retrieval data changed

Therefore:

**Cryptographic integrity ≠ Behavioral integrity.**

### 49. Model Provenance and Supply-Chain Integrity Principle

An organization should treat model provenance and supply-chain integrity as complementary governance objectives.

```text id="mpsi16p14-22"
                  Model Trust
                      |
          +-----------+-----------+
          |                       |
     Provenance                Integrity
          |                       |
     Where from?             Was it altered?
          |                       |
          +-----------+-----------+
                      |
                      v
              Security Assurance
```

Provenance helps establish **history and origin**.

Integrity helps establish **consistency and protection against unauthorized modification**.

Neither objective alone establishes complete model security assurance.

### 50. Core Principle of Model Provenance and Supply-Chain Integrity

**Model provenance and supply-chain integrity should be treated as foundational elements of AI supply-chain governance, but neither should be interpreted as complete assurance of model security, safety, privacy, or regulatory compliance.**

The fundamental distinctions are:

**Provenance ≠ Integrity.**

**Integrity ≠ Authenticity.**

**Authenticity ≠ Security.**

**Hash verification ≠ Model Trustworthiness.**

**Signature verification ≠ Model Security.**

**Model identity ≠ Model Safety.**

**Model lineage ≠ Complete Provenance.**

**Model provenance claim ≠ Verified Provenance.**

**Repository availability ≠ Repository Trust.**

**Publisher identity ≠ Publisher Assurance.**

**Model popularity ≠ Model Security Assurance.**

**Public availability ≠ Organizational Approval.**

**Model artifact integrity ≠ Behavioral Integrity.**

**Cryptographic integrity ≠ Behavioral integrity.**

**Model version identity ≠ Behavioral Stability.**

**Model availability ≠ Supply-Chain Resilience.**

**Documented lineage ≠ Complete lineage.**

**Known dependency ≠ Trusted dependency.**

**Model acquisition ≠ Model authorization.**

**Model evaluation ≠ Complete Assurance.**

**Security testing ≠ Regulatory Compliance.**

**Provenance evidence ≠ Proof of Safety.**

**Internal trust classification ≠ Legal classification.**

**Internal governance control ≠ Statutory or regulatory requirement.**

The `AI-MPSI-*` identifiers used in this knowledge base are **internal governance taxonomy identifiers**. They are not provisions of legislation, regulations, standards, or regulatory guidance unless a separate authoritative mapping explicitly establishes that relationship.

## Part 2 — Model Provenance Due Diligence, Integrity Controls, Lineage Verification, Model Assurance and Supply-Chain Security

### 51. Model Provenance Due Diligence

Model provenance due diligence is the structured process of evaluating the origin, ownership, lineage, transformation history, distribution path, integrity evidence, and relevant dependencies of a model before organizational use.

The depth of due diligence should be proportionate to:

* Model criticality
* Business impact
* Data sensitivity
* Deployment scope
* Decision impact
* Regulatory exposure
* Supply-chain complexity
* Replacement difficulty
* Dependency concentration

Due diligence should distinguish verified evidence from supplier assertions.

---

### 52. Model Publisher Due Diligence

Publisher due diligence evaluates the organization or individual responsible for distributing the model.

Assessment areas may include:

* Publisher identity
* Organizational ownership
* Security practices
* Release governance
* Vulnerability management
* Incident history
* Security contact
* Documentation
* Model maintenance
* Change-management practices
* Support arrangements

Publisher reputation can provide context but should not substitute for technical evidence.

**Publisher reputation ≠ Model Assurance.**

---

### 53. Model Maintainer Due Diligence

Maintainer due diligence evaluates whether the model remains actively maintained and whether material security issues are addressed appropriately.

Relevant indicators include:

* Recent releases
* Security advisories
* Issue-management practices
* Vulnerability response
* Release documentation
* Maintainer identity
* Repository activity
* Support channels
* End-of-life information

A model with no active maintenance may create increased operational and security risk.

---

### 54. Model Repository Due Diligence

Repository due diligence evaluates the security and governance characteristics of the location from which model artifacts are obtained.

Assessment areas can include:

* Repository ownership
* Authentication
* Access control
* Artifact protection
* Version control
* Integrity mechanisms
* Audit logging
* Availability
* Change history
* Administrative security
* Account-protection mechanisms

A trusted repository should be an explicit governance decision rather than an implicit assumption.

### 59. Model Hash Verification

Hash verification compares the cryptographic digest of an acquired artifact against an expected digest.

This can detect:

* Modification
* Corruption
* Incorrect version
* Incomplete transfer
* Unexpected replacement

Hash verification should be performed using a trusted reference value.

A hash calculated from an untrusted artifact and compared only against itself provides limited assurance.

### 60. Model Signature Verification

Controls may include:

* Trusted signing keys
* Certificate validation
* Key-status checking
* Signature verification
* Revocation checking
* Key-rotation procedures
* Signing-policy enforcement

A valid signature provides evidence about artifact integrity and signing identity, but it does not establish that the model itself is secure or suitable for the intended use.

### 62. Model Artifact Immutability

Model artifact immutability means that an approved artifact cannot be silently modified while retaining the same approved identity.

* Immutable storage

* Access controls
* Write protection
* Versioned repositories
* Cryptographic digests
* Signed artifacts
* Administrative controls

### 63. Model Version Pinning

Model version pinning explicitly identifies the approved model version or artifact that a workload is authorized to consume.

* Approved version
* Update monitoring
* Vulnerability status
* Update exceptions
* Reassessment triggers
* Rollback capability

* Supply-chain integrity
* Dependency vulnerabilities

* Prompt attacks
* Adversarial inputs
* Tool abuse

* Jailbreak testing
* Backdoor detection
* Supply-chain manipulation scenarios
* Privilege-boundary testing

Red-team scope should be based on realistic threat scenarios and model criticality.

Model safety evaluation examines whether the model behaves within defined safety boundaries for its intended use.

* Configuration

* Network connectivity

**Model provenance and supply-chain integrity should establish trustworthy visibility into where models originate, how they are transformed, how their identity and integrity are protected, what dependencies support them, and whether the resulting AI capability remains appropriately governed throughout its lifecycle.**

The core distinctions are:

**Provenance ≠ Integrity.**

**Integrity ≠ Authenticity.**

**Authenticity ≠ Security.**

**Repository Trust ≠ Model Trust.**

**Model Identity ≠ Behavioral Stability.**

**Model Integrity ≠ Application Security.**

**Cryptographic Integrity ≠ Behavioral Integrity.**

**Known Dependency ≠ Independent Dependency.**

**Multiple Models ≠ Effective Diversification.**

**Alternative Model ≠ Tested Substitute.**

**Documented Recovery ≠ Tested Recovery.**

**Exit Plan ≠ Exit Readiness.**

**Current Evidence ≠ Permanent Assurance.**

**Monitoring ≠ Assurance.**
