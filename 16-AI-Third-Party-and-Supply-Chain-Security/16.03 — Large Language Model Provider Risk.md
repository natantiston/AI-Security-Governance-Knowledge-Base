# Part 1 — Foundations, Risk Architecture, Provider Classification, and Governance

### 1 — AI-LLM-001 — Large Language Model Provider Risk Definition

Large Language Model (LLM) provider risk is the risk introduced when an organization depends on an external provider for access to, operation of, hosting of, or services built around a large language model.

LLM provider risk can arise from:

* model security;
* data processing;
* prompt handling;
* output handling;
* model training;
* model changes;
* service availability;
* API security;
* provider infrastructure;
* subprocessors;
* model supply chain;
* regulatory exposure;
* intellectual property;
* concentration;
* vendor lock-in; and
* provider failure.

LLM provider risk is therefore broader than conventional SaaS vendor risk.

---

### 2 — AI-LLM-002 — LLM Provider Risk Governance Objective

The objective of LLM provider risk governance is to ensure that external LLM dependencies are:

* identified;
* understood;
* assessed;
* authorized;
* securely integrated;
* monitored;
* reassessed when material conditions change; and
* capable of being restricted, replaced, or terminated when required.

---

### 3 — AI-LLM-003 — LLM Provider Versus AI Vendor

An LLM provider is a specific category of AI vendor that supplies access to a language model or model-related capability.

Examples of provider relationships include:

* direct model API;
* hosted LLM;
* managed enterprise LLM;
* foundation-model service;
* cloud-hosted LLM;
* self-hostable model supplied by a provider;
* fine-tuning service;
* inference service; and
* LLM-powered application.

An organization should identify the actual role performed by the provider rather than treating all AI vendors as equivalent.

---

### 4 — AI-LLM-004 — LLM Provider Role Classification

An LLM provider may perform one or more roles:

1. model developer;
2. model owner;
3. model distributor;
4. model host;
5. inference provider;
6. API provider;
7. fine-tuning provider;
8. application provider;
9. infrastructure provider;
10. model marketplace operator; or
11. intermediary between the organization and another model provider.

The role determines which risks and controls should be assessed.

---

### 5 — AI-LLM-005 — Direct LLM Provider Dependency

A direct LLM dependency exists when the organization's application communicates directly with the provider's model or API.

The organization should identify:

* endpoint;
* model;
* authentication;
* data transmitted;
* provider processing;
* response handling;
* logging;
* retention;
* model version;
* service tier; and
* contractual relationship.

---

### 6 — AI-LLM-006 — Indirect LLM Provider Dependency

An indirect LLM dependency exists when another application or service uses an external LLM provider on the organization's behalf.

For example:

**Organization → AI SaaS → LLM Provider → Cloud Infrastructure**

The organization should identify the underlying LLM dependency where material risk could propagate through the service.

---

### 7 — AI-LLM-007 — LLM Dependency Mapping

Material LLM dependencies should be mapped through the relevant technology stack.

A dependency map may identify:

**Business Process → Application → AI Service → LLM → Hosting Provider → Infrastructure → Supporting Services**

The objective is to identify hidden dependencies and potential correlated failures.

---

### 8 — AI-LLM-008 — LLM Provider Criticality

An LLM provider should be classified according to the impact of its failure or compromise on the organization.

Criticality may depend on:

* business-process dependency;
* transaction volume;
* customer impact;
* sensitive data;
* regulatory significance;
* automation level;
* availability requirements;
* replacement difficulty; and
* concentration.

This is an internal governance classification and is not itself a regulatory classification.

### 10 — AI-LLM-010 — LLM Cybersecurity Risk

Cybersecurity risk may arise from:

* compromised provider infrastructure;
* compromised API credentials;
* unauthorized access;
* insecure integrations;
* vulnerable model-serving systems;
* malicious model changes;
* data leakage;
* compromised plugins;
* supply-chain attacks; and
* provider-side security incidents.

---

### 11 — AI-LLM-011 — LLM API Security Risk

Where an LLM is accessed through an API, the organization should assess:

* authentication;
* authorization;
* API-key management;
* rate limiting;
* quotas;
* TLS;
* endpoint security;
* logging;
* abuse prevention;
* credential rotation; and
* API-version management.

---

### 12 — AI-LLM-012 — LLM Credential Risk

LLM API credentials can provide direct access to AI services and may also expose sensitive organizational data through prompts.

Credentials should therefore be protected through:

* secure storage;
* least privilege;
* rotation;
* monitoring;
* revocation;
* separation;
* secret-management systems; and
* controlled issuance.

---

### 13 — AI-LLM-013 — LLM API Key Exposure

API keys should not be embedded unnecessarily in:

* source code;
* client-side applications;
* public repositories;
* documentation;
* browser applications;
* tickets; or
* unprotected configuration files.

Where exposure is suspected, the credential should be treated as potentially compromised and handled according to incident procedures.

---

### 14 — AI-LLM-014 — LLM Provider Authentication

The organization should evaluate the provider's authentication mechanisms.

Relevant capabilities may include:

* multifactor authentication;
* federated identity;
* service identities;
* role-based access;
* API credentials;
* workload identities; and
* privileged-access controls.

---

### 15 — AI-LLM-015 — LLM Provider Authorization

Authorization should restrict access according to:

* user;
* application;
* environment;
* model;
* function;
* data;
* administrative role; and
* permitted action.

An authenticated user should not automatically receive unrestricted access to every model or capability.

---

### 16 — AI-LLM-016 — LLM Provider Least Privilege

Access to external LLM services should follow least-privilege principles.

Examples include:

* separate development and production credentials;
* restricted model access;
* restricted administrative access;
* application-specific credentials;
* limited API scopes; and
* restricted tool permissions.

---

### 17 — AI-LLM-017 — LLM Provider Administrative Access

The organization should understand how provider personnel can access customer environments or data.

Assessment should consider:

* authorized personnel;
* access conditions;
* privileged access;
* monitoring;
* logging;
* approval;
* emergency access;
* access revocation; and
* geographic location.

---

### 18 — AI-LLM-018 — LLM Provider Support Access

Customer-support processes can create an additional access path to organizational information.

The organization should assess whether support personnel can access:

* prompts;
* uploaded files;
* outputs;
* account information;
* logs;
* configuration;
* incident data; or
* other customer content.

---

### 19 — AI-LLM-019 — LLM Data Processing Model

The organization should establish how data is processed by the LLM provider.

The assessment should identify:

* input;
* processing;
* storage;
* inference;
* logging;
* monitoring;
* backup;
* support access;
* model-improvement processing; and
* deletion.

---

### 20 — AI-LLM-020 — LLM Prompt Data Classification

Prompts should be classified according to the information they may contain.

Prompts can contain:

* personal data;
* confidential information;
* trade secrets;
* source code;
* credentials;
* customer information;
* financial information;
* security information; and
* proprietary business information.

The organization should not classify prompts as low risk merely because they are text.

---

### 21 — AI-LLM-021 — LLM Input Data Governance

Approved LLM use should define what types of information may be submitted to the provider.

Controls may include:

* data classification;
* DLP;
* prompt filtering;
* user restrictions;
* application controls;
* data masking;
* pseudonymization; and
* technical blocking.

---

### 22 — AI-LLM-022 — LLM Sensitive Data Restrictions

Where organizational policy or applicable requirements restrict external processing of sensitive data, the LLM deployment should enforce those restrictions.

Possible approaches include:

* blocking;
* masking;
* tokenization;
* pseudonymization;
* dedicated environments;
* approved enterprise services; or
* alternative processing.

---

### 23 — AI-LLM-023 — LLM Data Minimization

The organization should minimize information submitted to an external LLM to what is necessary for the approved purpose.

For example, a document-classification task may not require transmitting unrelated customer identifiers.

---

### 24 — AI-LLM-024 — LLM Prompt Redaction

Where appropriate, prompts should be processed to remove or transform unnecessary sensitive information before transmission.

Redaction mechanisms should be tested for:

* completeness;
* bypass;
* false positives;
* false negatives; and
* preservation of task functionality.

---

### 25 — AI-LLM-025 — LLM Data Masking

Sensitive fields may be masked before transmission to the provider.

The organization should ensure that masking:

* is applied consistently;
* does not expose the original information;
* preserves required functionality; and
* can be reversed only by authorized processes where reversibility is required.

---

### 26 — AI-LLM-026 — LLM Pseudonymization

Where appropriate, identifiers may be pseudonymized before being submitted to an external LLM.

The organization should separately protect the mapping between pseudonyms and original identities.

---

### 27 — AI-LLM-027 — LLM Provider Data Retention

The organization should determine how long the provider retains:

* prompts;
* files;
* outputs;
* logs;
* telemetry;
* account information;
* security records; and
* backups.

Different data categories may have different retention periods.

---

### 28 — AI-LLM-028 — LLM Zero-Retention Claims

Claims that an LLM service provides “zero retention” should be validated against:

* contractual terms;
* service documentation;
* technical configuration;
* logging;
* abuse monitoring;
* backup architecture;
* support processes; and
* applicable service tier.

“Zero retention” should not be interpreted as an absolute absence of every form of provider-side data processing.

---

### 29 — AI-LLM-029 — LLM Training Data Use

The organization should establish whether its prompts, files, outputs, feedback, or telemetry may be used to:

* train models;
* fine-tune models;
* improve services;
* evaluate models;
* detect abuse;
* develop products; or
* support other provider functions.

---

### 30 — AI-LLM-030 — LLM Customer Data Training Restriction

Where the organization prohibits customer data from being used for model training or improvement, that restriction should be technically and contractually supported where feasible.

The organization should verify that the selected service configuration implements the intended restriction.

---

### 31 — AI-LLM-031 — LLM Human Review of Customer Content

The organization should determine whether provider personnel may review customer prompts, files, or outputs.

Where human review is possible, the organization should understand:

* purpose;
* authorization;
* scope;
* retention;
* personnel access;
* confidentiality controls; and
* opt-out or configuration mechanisms where available.

---

### 32 — AI-LLM-032 — LLM Abuse Monitoring Data

Providers may process certain customer interactions for security, abuse prevention, or service protection.

The organization should understand such processing separately from model-training use.

This distinction is important because a prohibition on training does not necessarily mean that no provider-side processing occurs.

---

### 33 — AI-LLM-033 — LLM Data Secondary Use

The organization should identify secondary uses of customer data beyond the primary inference purpose.

Potential uses include:

* analytics;
* product improvement;
* abuse detection;
* benchmarking;
* research;
* quality assurance; and
* support.

Each use should be evaluated against organizational and applicable legal requirements.

### 38 — AI-LLM-038 — LLM Generated-Code Risk

When LLMs generate source code, the organization should assess:

* security;
* licensing;
* provenance;
* vulnerabilities;
* malicious code;
* dependency insertion;
* secrets;
* quality; and
* human review.

Generated code should follow the organization's secure-development controls.

---

### 39 — AI-LLM-039 — LLM Output Reliability Risk

LLM outputs may contain:

* factual errors;
* hallucinations;
* omissions;
* inconsistent responses;
* unsafe recommendations;
* outdated information; or
* fabricated references.

Reliability controls should therefore be aligned with the consequences of the use case.

---

### 40 — AI-LLM-040 — LLM Hallucination Risk

Hallucination risk should be assessed where incorrect output could cause material harm.

Controls may include:

* retrieval augmentation;
* grounding;
* source validation;
* confidence mechanisms;
* human review;
* deterministic processing where possible;
* output constraints; and
* post-processing validation.

---

### 41 — AI-LLM-041 — LLM Grounding Controls

Where factual accuracy is material, the organization should evaluate mechanisms that ground model outputs in trusted information sources.

Potential mechanisms include:

* retrieval-augmented generation;
* approved knowledge bases;
* authoritative datasets;
* document retrieval;
* citation requirements; and
* controlled context.

---

### 42 — AI-LLM-042 — LLM Retrieval Dependency Risk

If an LLM application uses retrieval-augmented generation, vendor risk extends to:

* vector databases;
* retrieval services;

* embedding models;
* indexing pipelines;
* access controls; and
* source-data integrity.

---

### 43 — AI-LLM-043 — LLM Embedding Dependency

Where embeddings are generated by an external provider, the organization should assess:

* data transmission;
* retention;
* model use;

* provider access;

### 44 — AI-LLM-044 — LLM Context Window Dependency

Changes to an LLM provider's context-window capability may affect:

* application functionality;
* data transmission;
* prompt construction;
* cost;
* performance; and
* security controls.

Material changes should therefore be assessed where they affect the organization's use case.

* manual fallback.

---

* monitoring;
* testing;

* governance.

* exit feasibility.

### 260 — AI-LLM-260 — Provider Documentation Monitoring

### 261 — AI-LLM-261 — Provider Trust-Center Monitoring

### 262 — AI-LLM-262 — Provider Assurance Expiration

### 263 — AI-LLM-263 — Assurance Revalidation

### 264 — AI-LLM-264 — Evidence Currency

### 267 — AI-LLM-267 — Evidence Limitation Record

### 268 — AI-LLM-268 — Provider Attestation Assessment

### 269 — AI-LLM-269 — Independent Assurance Assessment

### 270 — AI-LLM-270 — Control Applicability Review

### 271 — AI-LLM-271 — Shared Responsibility Mapping

### 272 — AI-LLM-272 — Shared Responsibility Validation

### 273 — AI-LLM-273 — Customer-Control Verification

### 274 — AI-LLM-274 — Provider-Control Dependency

### 275 — AI-LLM-275 — External Control Dependency Register

### 276 — AI-LLM-276 — Control Dependency Ownership

### 277 — AI-LLM-277 — Provider Risk Dashboard

Critical LLM providers should be represented in an appropriate risk dashboard containing relevant risk, assurance, incident, availability, dependency, and remediation information.

### 278 — AI-LLM-278 — Provider Key Risk Indicators

### 279 — AI-LLM-279 — Provider Performance Indicators

### 280 — AI-LLM-280 — Provider Risk Thresholds

### 281 — AI-LLM-281 — Threshold Governance

### 282 — AI-LLM-282 — Provider Risk Exceptions

### 283 — AI-LLM-283 — Provider Exception Expiration

### 284 — AI-LLM-284 — Exception Remediation

Temporary provider-risk exceptions should have remediation plans where remediation is feasible.

### 285 — AI-LLM-285 — Provider Risk Acceptance

### 286 — AI-LLM-286 — Provider Risk Escalation

Material provider risks exceeding approved thresholds should be escalated to the appropriate risk, security, privacy, legal, or executive governance function.

### 287 — AI-LLM-287 — Provider Risk Decision Record

Material decisions concerning continued use, restriction, migration, suspension, or termination of an LLM provider should be documented.

### 288 — AI-LLM-288 — Provider Risk Review Frequency

### 289 — AI-LLM-289 — Event-Driven Reassessment

Material provider events should trigger reassessment where required by organizational policy, contract, risk methodology, or applicable legal or regulatory obligations.

### 290 — AI-LLM-290 — Provider Incident Classification

Provider-related incidents should be classified according to organizational incident-management criteria.

### 291 — AI-LLM-291 — Provider Incident Intake

The organization should maintain a process for receiving, recording, and evaluating provider incident notifications.

### 292 — AI-LLM-292 — Provider Incident Verification

Provider incident information should be evaluated against available organizational telemetry and business impact information.

### 293 — AI-LLM-293 — Provider Incident Correlation

Provider incidents should be correlated with internal security events, application failures, data events, and service anomalies where technically feasible.

### 294 — AI-LLM-294 — Provider Incident Impact Assessment

The organization should assess whether a provider incident affected confidentiality, integrity, availability, privacy, safety, regulatory compliance, contractual obligations, or business operations.

### 295 — AI-LLM-295 — Provider Data Exposure Assessment

Where a provider incident may involve customer data, the organization should assess what categories of organizational data may have been affected.

### 296 — AI-LLM-296 — Data-Flow Reconstruction

Material provider incidents should support reconstruction of relevant data flows, including inputs, outputs, logs, metadata, administrative access, subprocessors, and affected services.

### 297 — AI-LLM-297 — Provider Incident Evidence Preservation

Evidence relevant to provider incidents should be preserved according to incident-response and legal-hold requirements.

### 298 — AI-LLM-298 — Provider Incident Timeline

Material provider incidents should have an established timeline documenting detection, provider notification, internal assessment, containment, escalation, and resolution.

### 299 — AI-LLM-299 — Provider Incident Communications

Incident communications should distinguish confirmed facts, provider assertions, internal findings, assumptions, and unresolved questions.

### 300 — AI-LLM-300 — Provider Incident Regulatory Assessment

Potential regulatory implications of provider incidents should be assessed by the appropriate legal, privacy, compliance, or security function.

### 301 — AI-LLM-301 — Provider Incident Reporting Responsibility

A provider's incident notification should not automatically be treated as satisfying the organization's own reporting obligations. Applicable reporting responsibilities should be assessed independently.

### 302 — AI-LLM-302 — Provider Incident Contractual Notification

Provider contractual requirements for incident notification should be tracked and evaluated against actual provider performance.

### 303 — AI-LLM-303 — Notification Timing Assessment

Material delays in provider incident notification should be documented and considered in the provider risk assessment.

### 304 — AI-LLM-304 — Provider Incident Escalation

Incidents exceeding defined impact or severity thresholds should be escalated through the organization's incident-management process.

### 305 — AI-LLM-305 — Provider Containment

Where a provider incident creates unacceptable exposure, the organization should have mechanisms to restrict, disable, isolate, or reroute affected LLM services.

### 306 — AI-LLM-306 — Credential Containment

Provider credentials suspected of compromise should be capable of being revoked, rotated, or otherwise contained.

### 307 — AI-LLM-307 — API Key Rotation

Critical provider API keys should support controlled rotation and emergency replacement.

### 308 — AI-LLM-308 — Credential Segmentation

Provider credentials should be segmented by application, environment, workload, or business function where practical.

### 309 — AI-LLM-309 — Emergency Provider Disablement

Critical LLM integrations should have an operationally tested mechanism for emergency disablement.

### 310 — AI-LLM-310 — Emergency Disablement Authorization

Emergency service disablement should have predefined authorization rules so that urgent containment does not depend on an improvised approval process.

### 311 — AI-LLM-311 — Provider Service Isolation

Where feasible, applications should be architected so that a compromised or unavailable LLM provider can be isolated from other enterprise systems.

### 312 — AI-LLM-312 — LLM Network Segmentation

Network and application architectures should limit unnecessary connectivity between LLM integrations and sensitive enterprise resources.

### 313 — AI-LLM-313 — Egress Governance

Outbound communications from systems using LLM providers should be governed to reduce unauthorized data transmission.

### 314 — AI-LLM-314 — Sensitive Data Egress Control

### 315 — AI-LLM-315 — Prompt Gateway Control

### 316 — AI-LLM-316 — Prompt Inspection

### 317 — AI-LLM-317 — Output Inspection

Where appropriate, LLM outputs should be inspected for security, privacy, policy, content, or data-leakage risks before reaching downstream systems.

### 318 — AI-LLM-318 — Provider Policy Enforcement

Enterprise policy controls should be enforced independently of provider-side safety or policy controls when organizational requirements demand additional protection.

### 319 — AI-LLM-319 — Provider Control Independence

The organization should avoid treating provider-managed safety controls as a complete substitute for enterprise governance controls.

### 320 — AI-LLM-320 — Model Guardrail Dependency

### 323 — AI-LLM-323 — Tool-Use Risk

### 325 — AI-LLM-325 — High-Impact Action Control

Actions capable of producing material financial, operational, security, legal, or data consequences should have appropriate authorization and validation controls.

### 336 — AI-LLM-336 — Provider Personnel Controls

### 337 — AI-LLM-337 — Support Escalation Path

### 338 — AI-LLM-338 — Critical Incident Support

### 339 — AI-LLM-339 — Provider Support Evidence

### 340 — AI-LLM-340 — Provider Resilience Assessment
