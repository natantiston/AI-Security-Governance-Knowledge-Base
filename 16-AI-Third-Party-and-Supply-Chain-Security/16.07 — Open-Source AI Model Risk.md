# 16.07 — Open-Source AI Model Risk

## Part 1 — Foundations, Open-Source Model Dependency, Provenance, Trust Boundaries, Licensing, Security and Governance

### 1. Open-Source AI Model Risk

Open-source AI model risk is the risk arising from the acquisition, deployment, modification, distribution, integration, and operation of AI models whose weights, code, architecture, datasets, documentation, or associated components are made available under an open-source or otherwise permissive-access model.

The risk is broader than whether a model can be downloaded freely.

An organization may face risk from:

* model provenance;
* licensing;
* malicious modification;
* compromised distribution channels;
* vulnerable dependencies;
* inadequate documentation;
* unknown training data;
* model behavior;
* model integrity;
* unsupported versions;
* lack of provider accountability;
* downstream redistribution;
* model concentration;
* operational dependency.

**Control ID: AI-OSM-001**

---

### 2. Objective of Open-Source AI Model Governance

The objective is to enable the organization to use open-source AI models while maintaining appropriate control over:

* provenance;
* authenticity;
* integrity;
* licensing;
* security;
* data;
* model behavior;
* dependencies;
* modifications;
* deployment;
* monitoring;
* lifecycle;
* accountability.

The governance model should be proportionate to the model's intended use and organizational risk.

**Control ID: AI-OSM-002**

---

### 3. Open-Source Model Versus Proprietary Model

An open-source or openly distributed model may differ from a proprietary model in the degree of organizational control and visibility available.

Potential differences include:

| Dimension                   | Open / Open-Source Model          | Proprietary Model                 |
| --------------------------- | --------------------------------- | --------------------------------- |
| Model access                | May be downloadable               | Usually provider-controlled       |
| Weights                     | May be available                  | Usually unavailable               |
| Modification                | Often possible                    | Usually restricted                |
| Deployment                  | Can often be self-hosted          | Often provider-hosted             |
| Provider dependency         | May be reduced                    | Often significant                 |
| Supply-chain responsibility | More customer-side responsibility | More provider-side responsibility |
| Licensing                   | Must be assessed                  | Contract terms usually dominate   |
| Update mechanism            | May be decentralized              | Usually provider-controlled       |

These characteristics do not automatically make either model category secure or insecure.

**Control ID: AI-OSM-003**

---

### 4. Meaning of Open-Source in AI

The term "open-source AI" can refer to different components being available under different terms.

An organization should determine whether the openness applies to:

* source code;
* model weights;
* training code;
* training datasets;
* evaluation datasets;
* documentation;
* inference software;
* deployment tools;
* fine-tuning tools.

Availability of one component does not establish that all components are open.

**Control ID: AI-OSM-004**

### 10. Direct Open-Source Model Dependency

A direct dependency exists when the organization explicitly acquires or deploys an open-source model.

Examples include:

* downloading model weights;
* deploying a model container;
* hosting a model internally;
* integrating a model into an application;
* fine-tuning a model.

Direct dependencies should be recorded in the AI inventory.

Indirect dependencies can be difficult to discover and should be considered during third-party assessment.

### 13. Model Publisher

The publisher is the entity or community responsible for releasing the model artifact.

Due diligence may examine:

* identity;
* reputation;
* development practices;
* security practices;
* maintenance activity;
* documentation;
* licensing;
* vulnerability handling;
* release process.

The publisher should not automatically be treated as a security authority merely because the model is widely used.

**Control ID: AI-OSM-013**

The maintainer may differ from the original publisher.

Maintenance governance should consider:

* current ownership;
* repository activity;
* release management;
* security responsiveness;
* vulnerability handling;
* issue management;
* contributor governance.

A widely adopted model may still have limited active maintenance.

**Control ID: AI-OSM-014**

### 15. Model Repository

The repository or distribution platform is a material supply-chain component.

Controls should consider:

* account security;
* repository authenticity;
* access controls;
* release integrity;
* artifact hashes;
* signing;
* version history;
* download provenance.

The organization should verify that the acquired artifact originated from an approved source.

### 16. Model Provenance

Model provenance establishes where the model originated and how the artifact reached the organization.

Provenance information may include:

* publisher;
* repository;
* release;
* source artifact;
* download location;
* acquisition date;
* hash;
* signer;
* transformation history;
* modification history.

Provenance should be retained for material models.

**Control ID: AI-OSM-016**

### 17. Model Authenticity

Authenticity concerns whether the model artifact is genuinely associated with the claimed publisher or source.

Verification mechanisms may include:

* cryptographic signatures;
* trusted repository identities;
* checksums;
* hashes;
* trusted release records.

File names and repository popularity alone should not be treated as sufficient authenticity evidence.

**Control ID: AI-OSM-017**

### 18. Model Integrity

Integrity concerns whether the acquired model remains unchanged from the verified artifact.

Integrity controls may include:

* cryptographic hashes;
* signatures;
* immutable storage;
* controlled repositories;
* access controls;
* deployment verification.

Integrity should be verified before production use where appropriate.

**Control ID: AI-OSM-018**

---

### 19. Model Artifact Verification

Before deployment, the organization should verify the model artifact against the approved reference.

Verification may include:

1. source verification;
2. version verification;
3. hash verification;
4. signature verification;
5. package verification;
6. malware scanning where appropriate;
7. configuration comparison.

Verification evidence should be retained.

**Control ID: AI-OSM-019**

### 20. Model Tampering Risk

Model artifacts may be altered before or after acquisition.

Potential tampering scenarios include:

* compromised repository;
* compromised maintainer account;
* malicious contributor;
* substituted model file;
* compromised download;
* unauthorized modification;
* compromised storage.

The organization should establish controls appropriate to the model's criticality.

**Control ID: AI-OSM-020**

### 21. Model Backdoor Risk

A model may contain behavior that is not apparent from ordinary functional testing.

Potential concerns include:

* trigger-based behavior;
* malicious output patterns;
* hidden functionality;
* compromised fine-tuning;
* manipulated weights.

Security evaluation should therefore consider adversarial and behavioral testing where justified.

**Control ID: AI-OSM-021**

---

### 22. Model Poisoning Risk

Model poisoning refers to malicious or undesirable manipulation of training or fine-tuning processes that can affect model behavior.

Potential sources include:

* compromised datasets;
* malicious training examples;
* compromised fine-tuning;
* untrusted adapters;
* malicious contributors.

Organizations should assess provenance and trust of material model-development artifacts.

**Control ID: AI-OSM-022**

---

### 23. Fine-Tuned Open-Source Model Risk

A fine-tuned model should be treated as a distinct artifact when its behavior, data, or configuration materially differs from the base model.

Governance should record:

* base model;
* fine-tuning dataset;
* training process;
* hyperparameters where relevant;
* resulting artifact;
* evaluator;
* version;
* approval status.

**Control ID: AI-OSM-023**

---

### 24. Open-Source Adapter Risk

Adapters, such as parameter-efficient fine-tuning components, may materially alter model behavior.

They should be assessed for:

* provenance;
* integrity;
* compatibility;
* licensing;
* security;
* behavior;
* dependencies.

An approved base model does not automatically approve every adapter.

**Control ID: AI-OSM-024**

### 25. Quantized Model Risk

Assessment may consider:

* accuracy;
* security behavior;
* compatibility;
* performance;
* numerical effects;
* model integrity.

The quantized artifact should have its own identifiable version or hash.

**Control ID: AI-OSM-025**

### 26. Model Conversion Risk

Converting a model between formats may introduce:

* integrity issues;
* compatibility issues;
* unexpected behavior;

* configuration changes.

Accountability may be distributed across:

* software maintainers;

### 50. Open-Source Model Governance Principle

Open-source AI model governance should treat the model as a **supply-chain artifact and operational dependency**, not merely as downloadable software.

The organization should establish visibility into:

* what model is actually deployed;
* where it came from;
* which license applies;
* how its integrity is verified;
* what components surround it;
* who maintains it;
* what modifications were made;
* what data it processes;
* what privileges it receives;
* what security controls protect it;
* how changes are governed;
* how vulnerabilities are handled;
* how the model can be replaced or retired.

Open-source availability can increase organizational control over deployment, but it can also shift responsibility for security, maintenance, provenance, licensing, and lifecycle management toward the organization.

**Control ID: AI-OSM-050**

### Core Principles

1. **Provenance Principle** — The origin and acquisition path of material model artifacts should be identifiable.
2. **Authenticity Principle** — Model artifacts should be obtained from trusted sources and appropriately authenticated.
3. **Integrity Principle** — Material model artifacts should be protected against unauthorized modification.
4. **Lineage Principle** — Modified models should remain traceable to their source artifacts.
5. **Supply-Chain Principle** — Model governance should include material software, infrastructure, dataset, and distribution dependencies.
6. **Licensing Principle** — Model, code, dataset, and dependency licenses should be assessed according to their applicable terms.
7. **Modification Principle** — Fine-tuning, quantization, conversion, adapters, and other material modifications should be governed.
8. **Runtime-Security Principle** — Model security should include the inference runtime and supporting infrastructure.
9. **Isolation Principle** — Model workloads should receive appropriate execution and network isolation.
10. **Least-Privilege Principle** — Model-serving workloads should receive only the access required for their function.
11. **Data-Boundary Principle** — Organizational data access should remain controlled throughout the model-processing lifecycle.
12. **Dependency Principle** — Open-source status does not eliminate third-party or supply-chain dependencies.
13. **Verification Principle** — Model artifacts should be verified before material deployment.
14. **Version Principle** — Model versions and material variants should remain identifiable and controlled.
15. **Monitoring Principle** — Material deployments should be monitored for security, integrity, operational, and behavioral indicators.
16. **Vulnerability Principle** — Vulnerability management should cover the complete model deployment environment.
17. **Accountability Principle** — The organization should identify which party owns each material risk.
18. **Change-Governance Principle** — Model updates and modifications should be assessed before production adoption.
19. **Isolation-of-Trust Principle** — Popularity, community adoption, or repository visibility should not by itself establish trust.
20. **Governance Principle** — Open-source AI model governance should remain risk-based, evidence-driven, and lifecycle-oriented.


## Part 2 — Open-Source Model Due Diligence, Security Controls, Model Assurance, Licensing, Data Governance and Supply-Chain Security

### 51. Open-Source Model Due Diligence

Due diligence should be performed before an open-source AI model is approved for material organizational use.

The assessment should consider:

* model provenance;
* publisher and maintainer;
* repository;
* licensing;
* model architecture;
* training and fine-tuning information;
* known vulnerabilities;
* dependencies;
* release practices;
* security controls;
* documentation;
* model evaluation;
* community and maintenance activity;
* organizational criticality.

The depth of due diligence should be proportionate to the intended use.

**Control ID: AI-OSM-051**

---

### 52. Open-Source Model Publisher Assessment

Publisher assessment should establish whether sufficient information exists to understand the model's origin and development.

Assessment may include:

* publisher identity;
* organizational ownership;
* development history;
* release history;
* security practices;
* documentation;
* vulnerability-management process;
* model evaluation information.

Lack of information should be recorded as an uncertainty rather than automatically interpreted as evidence of malicious behavior.

**Control ID: AI-OSM-052**

---

### 53. Open-Source Model Maintainer Assessment

The organization should determine whether the model is actively maintained.

Indicators may include:

* recent releases;
* issue activity;
* vulnerability responses;
* documentation updates;
* security advisories;
* contributor activity;
* release cadence.

Maintenance activity should be considered in lifecycle and operational risk.

**Control ID: AI-OSM-053**

---

### 54. Open-Source Repository Assessment

The repository should be assessed for:

* ownership;
* authenticity;
* access controls;
* release history;
* artifact integrity;
* versioning;
* security advisories;
* repository transfer history where relevant.

The organization should distinguish the authoritative repository from mirrors and unofficial copies.

**Control ID: AI-OSM-054**

---

### 55. Open-Source Model Distribution Assessment

Distribution channels should be evaluated for:

* authenticity;
* integrity;
* availability;
* version consistency;
* signing;
* hash verification;
* access controls.

A model downloaded from an unverified mirror should not automatically receive the same trust level as an approved source.

**Control ID: AI-OSM-055**

---

### 56. Open-Source Model Trust Classification

Models may be classified according to the strength of available trust evidence.

Possible dimensions include:

* verified provenance;
* verified integrity;
* maintainer confidence;

* evaluation evidence;

Trust classification should influence deployment approval.

**Control ID: AI-OSM-056**

### 61. Open-Source Model Hash Verification

Cryptographic hashes can establish whether an artifact matches a known reference.

The organization should retain:

* hash algorithm;
* expected hash;
* observed hash;
* verification date;
* artifact version.

A matching hash establishes integrity relative to the trusted reference; it does not establish that the reference itself is trustworthy.

**Control ID: AI-OSM-061**

---

### 62. Open-Source Model Signature Verification

Where model publishers provide verifiable signatures, organizations should consider signature verification as part of artifact authentication.

The process should validate:

* signer identity;
* trusted key;
* signature;
* artifact;
* release association.

Signature verification should complement rather than replace provenance assessment.

**Control ID: AI-OSM-062**

---

### 63. Open-Source Model Trusted Registry

A controlled internal registry can provide a trusted source for approved model artifacts.

Registry controls may include:

* access control;
* immutable versions;

* metadata;
* deployment history;
* retirement status.

**Control ID: AI-OSM-063**

---

### 64. Open-Source Model Artifact Immutability

Production model artifacts should be protected against unauthorized replacement.

Controls may include:

* immutable storage;
* write restrictions;
* version locking;
* signed artifacts;
* deployment verification.

Immutability should apply to the appropriate production artifact rather than necessarily preventing legitimate version changes.

### 65. Open-Source Model Environment Separation

Development, testing, staging, and production environments should be appropriately separated.

This reduces the likelihood that:

* untested models;
* unauthorized modifications;
* experimental dependencies;
* developer credentials

are introduced directly into production.

### Core Principles

1. **Due-Diligence Principle** — Material open-source models should undergo proportionate due diligence before approval.
2. **Source-Verification Principle** — Model acquisition should use verified and controlled sources.
3. **Artifact-Verification Principle** — Material artifacts should be verified before production deployment.
4. **Registry Principle** — Approved artifacts should be maintained in controlled repositories where practical.
5. **Version-Control Principle** — Production model versions should be explicitly identified.
6. **Reproducibility Principle** — Material deployments should be reproducible where operationally feasible.
7. **Change-Control Principle** — Material model changes should undergo proportionate assessment.
8. **Evaluation Principle** — Models should be evaluated against the intended use case.
9. **Regression Principle** — Material model changes should be tested for regression.
10. **Runtime-Security Principle** — Security assessment should include the inference runtime and dependencies.
11. **Least-Privilege Principle** — Model workloads should receive only necessary privileges.
12. **Network-Security Principle** — Model network connectivity should be controlled according to risk.
13. **Data-Minimization Principle** — Only necessary data should be processed by the model.
14. **Dataset-Governance Principle** — Training and evaluation datasets should be governed as controlled assets.
15. **Privacy Principle** — Applicable privacy requirements should be assessed across the model lifecycle.
16. **Supply-Chain Principle** — Model security should include material upstream and downstream dependencies.
17. **Incident-Principle** — Model and supply-chain incidents should have defined response procedures.
18. **Evidence-Principle** — Material security and governance decisions should be supported by traceable evidence.
19. **Assurance-Principle** — Model assurance should cover both the artifact and its operational environment.
20. **Accountability Principle** — Open-source deployment should have clearly assigned organizational ownership.

### Core Principles

1. **Continuous-Monitoring Principle** — Material open-source model deployments should remain subject to proportionate ongoing monitoring.
2. **Integrity-Monitoring Principle** — Production artifacts should be monitored for unauthorized modification.
3. **Version-Monitoring Principle** — The running model should remain aligned with the approved version.
4. **Repository-Monitoring Principle** — Relevant upstream repositories and maintainers should be monitored for material changes.
5. **Dependency-Monitoring Principle** — Supporting software and infrastructure dependencies should be continuously assessed.
6. **Vulnerability Principle** — Newly identified vulnerabilities should be assessed against actual deployment context.
7. **Behavioral-Assurance Principle** — Material behavioral changes should be detected and investigated.
8. **Configuration-Integrity Principle** — Production configuration should remain aligned with approved baselines.
9. **Incident Principle** — Model and supply-chain incidents should have defined detection, containment, recovery, and learning processes.
10. **Evidence Principle** — Monitoring and incident activities should generate traceable evidence.
11. **Regulatory-Applicability Principle** — Regulatory notification and applicability should be assessed according to the actual circumstances rather than assumed from generic AI risk.
12. **Concentration Principle** — Open-source deployments should be assessed for shared model, software, infrastructure, and maintainer dependencies.
13. **Resilience Principle** — Material deployments should have proportionate recovery and fallback capabilities.
14. **Fallback Principle** — An alternative should be considered tested resilience only when its operational suitability has been established.
15. **Portability Principle** — Technical portability and behavioral portability should be assessed separately.
16. **Exit-Readiness Principle** — Critical dependencies should have realistic and periodically reassessed exit arrangements.
17. **Assurance Principle** — Assurance should be refreshed when material changes or new evidence alter the risk profile.
18. **Automation Principle** — Automated monitoring and response should remain auditable and controlled.
19. **Human-Accountability Principle** — Material automated governance decisions should retain appropriate human accountability.
20. **Continuous-Assurance Principle** — Monitoring, testing, incidents, assurance, and governance decisions should operate as an integrated feedback loop.

The assurance objective is to establish confidence in the actual deployed model ecosystem rather than merely the original model artifact.

**Control ID: AI-OSM-398**

### 399. Open-Source Model Enterprise Governance Principle

Enterprise governance should provide a complete view of the open-source AI model lifecycle.

For every material model, the organization should be able to determine:

* What model is deployed?
* Which exact version or artifact is being used?
* Where did it originate?
* How was authenticity verified?
* What license applies?
* What modifications were made?
* Which datasets and dependencies are involved?
* Which software and infrastructure components support it?
* What data does it process?
* What privileges does it have?
* Which applications depend on it?
* What vulnerabilities affect it?
* What evidence supports its security?
* How is behavioral change detected?
* What happens if the model or its ecosystem becomes unavailable?
* Can the model be replaced?
* What residual risk has been accepted?

### 400. Open-Source AI Model Governance Principle

Open-source AI model governance should recognize that **model openness, model security, model provenance, software supply-chain security, licensing, operational resilience, and organizational accountability are distinct but interconnected governance domains**.

The following distinctions should remain explicit:

* open-source availability ≠ security assurance;
* public repository ≠ trusted artifact;
* popular model ≠ verified model;
* model hash verification ≠ proof that the original artifact is trustworthy;
* model integrity ≠ model behavioral safety;
* model security ≠ application security;
* model license ≠ license for every associated component;
* code license ≠ model-weight license;
* dataset availability ≠ unrestricted dataset rights;
* open-source model ≠ absence of third-party dependency;
* multiple models ≠ effective diversification;
* alternative model ≠ tested substitute;
* model portability ≠ behavioral equivalence;
* documented recovery ≠ tested recovery;
* maintainer activity ≠ guaranteed long-term support;
* repository availability ≠ organizational resilience;
* framework mapping ≠ regulatory applicability;
* internal control ≠ statutory requirement;
* automated verification ≠ complete assurance;
* provider independence ≠ dependency independence.

The enterprise objective is to maintain an evidence-based understanding of the complete open-source model ecosystem throughout acquisition, verification, deployment, operation, modification, monitoring, incident response, reassessment, and retirement.

**Control ID: AI-OSM-400**

### Core Principles

1. **Enterprise-Governance Principle** — Open-source AI model use should operate within a defined enterprise governance framework.
2. **Provenance Principle** — Material model artifacts should have identifiable origin and acquisition history.
3. **Integrity Principle** — Production artifacts should be protected and continuously assessed for unauthorized modification.
4. **Licensing Principle** — Model, code, dataset, adapter, and dependency licenses should be assessed according to their applicable terms.
5. **Supply-Chain Principle** — Governance should address the complete model and software dependency chain.
6. **Dependency Principle** — Open-source status does not eliminate operational, technical, or ecosystem dependencies.
7. **Least-Privilege Principle** — Model workloads and agents should receive only necessary authority.
8. **Defense-in-Depth Principle** — Security should use multiple complementary controls across artifact, runtime, application, data, and monitoring layers.
9. **Data-Boundary Principle** — Model access to organizational data should remain explicitly controlled.
10. **Behavioral-Assurance Principle** — Model behavior should be evaluated independently from artifact integrity.
11. **Continuous-Monitoring Principle** — Material models should remain subject to proportionate ongoing monitoring.
12. **Concentration Principle** — Shared models, runtimes, maintainers, infrastructure, and ecosystems should be evaluated for common-mode dependency.
13. **Resilience Principle** — Critical model capabilities should have proportionate recovery and fallback arrangements.
14. **Portability Principle** — Technical portability and behavioral portability should be assessed separately.
15. **Exit-Readiness Principle** — Critical models should have realistic replacement and retirement arrangements.
16. **Assurance Principle** — Assurance should combine artifact, technical, behavioral, supply-chain, and operational evidence.
17. **Evidence Principle** — Material governance decisions should be supported by current and traceable evidence.
18. **Regulatory-Traceability Principle** — Legal requirements should remain distinguishable from internal governance practices.
19. **Automation Principle** — Automated governance should remain controlled, auditable, and resilient.
20. **Human-Accountability Principle** — Human accountability should remain for material model-governance decisions.
