# 11.18 — Agent Monitoring and Observability

## 1. Definition of Agent Monitoring

Agent monitoring is the continuous observation of AI agent behavior, activity, decisions, interactions, tool usage, resource consumption, security events, and autonomous actions throughout the agent lifecycle.

Unlike conventional application monitoring, agent monitoring must evaluate not only whether the system is functioning, but **what the agent is attempting to accomplish and whether its behavior remains within its authorized security boundary**.

A simplified model is:

```text
Agent
  |
  v
Activity
  |
  +--> Decisions
  +--> Tool Calls
  +--> Data Access
  +--> Communications
  +--> Transactions
  +--> Delegation
  +--> Memory
  |
  v
Monitoring
  |
  v
Security Analysis
```

---

## 2. Agent Observability

Agent observability is the ability to understand the internal and external behavior of an autonomous system from its available telemetry.

Observability should allow security teams to answer:

* What did the agent do?
* Why did it attempt the action?
* Which identity was used?
* Which user initiated the workflow?
* What tools were invoked?
* What data was accessed?
* Which agents were contacted?
* What authorization decisions occurred?
* What changed?
* What happened afterward?

Observability therefore extends beyond traditional availability monitoring.

---

## 3. Agent Monitoring as a Security Discipline

Agent monitoring should be treated as a core agentic AI security capability.

It supports:

* Threat detection
* Incident response
* Fraud detection
* Policy enforcement
* Risk management
* Compliance
* Investigation
* Performance analysis
* Behavioral assurance

Without sufficient monitoring, organizations may be unable to determine whether an autonomous agent is operating safely.

---

## 4. Monitoring vs Observability

Monitoring generally focuses on known conditions and predefined metrics.

Observability provides the evidence necessary to investigate unknown or unexpected conditions.

| Monitoring              | Observability                  |
| ----------------------- | ------------------------------ |
| Detect known conditions | Investigate unknown conditions |
| Metrics                 | Metrics + logs + traces        |
| Threshold-oriented      | Context-oriented               |
| Health-focused          | Behavior-focused               |
| Alerting                | Investigation                  |
| "Something is wrong"    | "What happened and why?"       |

Agentic systems require both.

---

## 5. Agent Behavior as a Security Signal

Agent behavior itself can provide security signals.

Examples include:

* Unusual tool selection
* Unexpected data access
* Excessive requests
* New communication relationships
* Unusual transaction patterns
* Unexpected delegation
* Repeated authorization failures
* Abnormal execution duration

The monitoring system should therefore analyze behavioral deviations, not merely infrastructure failures.

---

Agent activity includes all meaningful actions performed or attempted by an agent.

Examples include:

```text id="4v8z2x"

     |

     |

     |
     v
API Call
     |
     v
Data Retrieval
     |
     v

     |
     v

```

Each significant stage should generate appropriate security telemetry.

---

## 7. Agent Execution Monitoring

Monitoring should cover the agent execution lifecycle.

Key observations include:

* Execution start
* Execution end
* Execution duration
* Current state
* Iteration count
* Tool calls
* Errors
* Retries
* Delegations
* Transactions
* Security events

Long-running or persistent agents require continuous monitoring rather than only per-session monitoring.

---

## 8. Agent Decision Monitoring

Where an agent makes autonomous decisions, monitoring should capture decision-related security information.

This may include:

* Decision identifier
* Agent identity
* Decision context
* Decision type
* Risk classification
* Authorization result
* Human approval requirement
* Final action

The objective is not necessarily to record every internal reasoning detail, but to maintain sufficient evidence for security accountability.

---

## 9. Agent Action Monitoring

Monitoring should distinguish between:

```text id="z5y9kp"
Recommendation
     |
     v
Decision
     |
     v
Authorization
     |
     v
Action
```

An agent may recommend an action without being authorized to execute it.

Monitoring should therefore record both proposed and executed actions.

---

## 10. Agent Tool Monitoring

Every significant tool invocation should be observable.

Telemetry may include:

* Agent
* Tool
* Function
* Parameters
* Target
* Authorization decision
* Result
* Duration
* Error
* Transaction identifier

Example:

```text id="m7q3ws"
Agent: Finance-Agent-01
Tool: PaymentAPI
Function: create_payment
Amount: €8,500
Authorization: APPROVED
Result: SUCCESS
```

Sensitive parameters should be protected or masked where required.

---

## 11. Agent-to-Agent Monitoring

Multi-agent systems require monitoring of relationships between agents.

Monitoring should capture:

* Initiating agent
* Receiving agent
* Message type
* Purpose
* Delegation
* Data exchanged
* Authorization
* Result
* Relationship frequency

Example:

```text id="k2f7vx"
Agent A
   |
   | Request
   v
Agent B
   |
   | Delegation
   v
Agent C
```

Unexpected relationships can be security indicators.

---

## 12. Agent Identity Monitoring

Every monitored activity should be attributable to a specific agent identity.

Monitoring should distinguish:

* Agent identity
* Agent instance
* User identity
* Session identity
* Execution identity
* Model identity
* Provider identity

This prevents different security subjects from being incorrectly treated as the same actor.

---

## 13. User-to-Agent Attribution

Where a human initiates an agent workflow, monitoring should preserve the relationship between the user and agent.

```text id="8x3qvz"
User
 |
 v
Agent
 |
 v
Tool
 |
 v
Resource
```

This allows investigators to determine:

* Who initiated the activity.
* Which agent executed it.
* What authority was used.
* Which resource was affected.

---

## 14. Agent Session Monitoring

Sessions should be monitored for:

* Creation
* Authentication
* Context changes
* Tool activity
* Authorization changes
* Session duration
* Termination

Persistent agents may have long-lived sessions, making session-state monitoring especially important.

---

## 15. Agent Context Monitoring

Monitoring should identify the security-relevant context influencing agent behavior.

This may include:

* User instructions
* System policies
* Retrieved information
* Tool results
* Memory
* External content
* Agent-to-agent messages

The monitoring system should distinguish trusted context from untrusted content.

---

## 16. Agent Memory Monitoring

Memory operations should be observable.

Examples include:

* Memory creation
* Memory retrieval
* Memory modification
* Memory deletion
* Memory source
* Memory access identity

Suspicious patterns may include:

```text id="y8p4nc"
Unexpected Memory Write
        |
        v
Repeated Retrieval
        |
        v
Behavior Change
```

Such relationships can indicate memory poisoning or unauthorized manipulation.

---

## 17. Persistent Context Monitoring

Persistent context should be monitored for:

* Unexpected changes
* New instruction content
* Source changes
* Integrity violations
* Access anomalies
* Cross-user contamination
* Cross-tenant access

Persistent context should not be treated as inherently trustworthy simply because it originated inside the enterprise.

---

## 18. Agent Credential Monitoring

Monitoring should track the use of agent credentials.

Relevant events include:

* Credential issuance
* Credential use
* Credential rotation
* Credential expiration
* Credential revocation
* Failed authentication
* Unexpected credential use

Unexpected credential use can be an early indicator of compromise.

---

## 19. Agent Authorization Monitoring

Authorization decisions should be observable.

For example:

```text id="f5z2kr"
Agent Request
      |
      v
Authorization
      |
      +--> ALLOW
      +--> DENY
      +--> REQUIRE APPROVAL
      +--> ESCALATE
```

Repeated denied requests may indicate:

* Misconfiguration
* Privilege escalation attempts
* Prompt manipulation
* Compromised behavior

---

## 20. Agent Permission Monitoring

Monitoring should identify how agents actually use granted permissions.

An agent may technically have access to a resource but rarely use it.

A sudden change from:

```text id="d7q4xp"
Normal:
Read CRM Records

Observed:
Read CRM
+
Export Data
+
Modify Accounts
```

should trigger appropriate analysis.

---

## 21. Least-Privilege Monitoring

Monitoring can validate whether agents continue to operate within least-privilege expectations.

Questions include:

* Which permissions are actually used?
* Which permissions are never used?
* Which permissions have increased usage?
* Which new permissions appeared?
* Are high-risk permissions being exercised?

Monitoring therefore supports continuous permission optimization.

---

## 22. Agent Network Monitoring

Network activity should be monitored for:

* Destination
* Source
* Protocol
* Port
* Volume
* Frequency
* Geographic or logical location
* Data transfer

Unexpected network destinations may indicate:

* Data exfiltration
* Command-and-control activity
* Tool misuse
* Unauthorized external communication

---

## 23. Agent Egress Monitoring

Outbound communication is particularly important for autonomous systems.

Monitoring should detect:

```text id="z3v6mc"
Approved Destination
      |
      v
Normal

Unknown Destination
      |
      v
Risk Evaluation

Sensitive Data + Unknown Destination
      |
      v
```

Egress monitoring should operate independently of the agent.

---

## 24. Agent Data Access Monitoring

Agents should be monitored for data access patterns.

Relevant observations include:

* Dataset
* Resource
* Records accessed
* Query type
* Volume
* User/tenant
* Agent identity
* Time

Large deviations from normal access patterns may indicate compromise or misuse.

---

## 25. Sensitive Data Monitoring

Monitoring should provide additional visibility for access to:

* Personal data
* Financial information
* Credentials
* Security information
* Confidential business data
* Regulated information

Sensitive-data access should be correlated with agent identity, purpose, and authorization.

---

## 26. Agent Transaction Monitoring

Autonomous transactions should be monitored continuously.

Examples include:

* Payments
* Purchases
* Account changes
* Configuration changes
* Resource creation
* Data exports

Monitoring should consider both individual and cumulative activity.

---

Transaction velocity can be an important behavioral signal.

## 28. Agent Execution Loop Monitoring

Agents can enter unintended loops.

Monitoring should track:

* Iteration count
* Repeated tool calls
* Repeated decisions
* Repeated errors
* Recursive delegation
* Execution duration

Example:

```text id="x5k8vc"

  |
  v
Action B
  |
  v
Action A
  |
  v
Action B
  |
  v
```

Loop detection should be capable of triggering containment controls.

## 30. Agent Behavioral Baselines

Organizations should establish behavioral baselines for agents.

A baseline may include:

* Typical tools
* Typical destinations
* Typical data
* Typical transactions
* Typical execution duration
* Typical agent relationships
* Typical activity volume
* Typical authorization patterns

The baseline should represent legitimate operational behavior rather than simply historical averages.

---

## 32. Agent Risk Monitoring

Agent risk should be continuously evaluated rather than determined only during initial deployment.

Risk signals may include:

* Behavioral anomalies
* New permissions
* New tools
* New relationships
* Failed authorizations
* Sensitive-data access
* Transaction anomalies
* External connectivity

This supports dynamic agent risk management.

## 34. Agent Health vs Agent Security

Operational health does not necessarily indicate security.

An agent can be:

```text id="v5m8pr"
Healthy
+
Available
+
Performing Successfully
+
Compromised
```

Therefore, monitoring must distinguish:

* System health
* Security health
* Behavioral correctness
* Authorization compliance

A successful action can still be an unauthorized action.

---

## 35. Agent Monitoring and Prompt Injection

Monitoring should detect behavioral indicators associated with prompt injection.

Possible signals include:

* Sudden tool changes
* New external destinations
* Unexpected instructions
* Abnormal data access
* Security-policy bypass attempts
* Unusual action sequences

Detection should focus on observable behavior rather than attempting to perfectly classify every malicious prompt.

---

Tool results may influence future agent actions.

Monitoring should therefore correlate:

```text id="h8k4zw"
    |
    v
```

Unexpected decisions following suspicious tool results may require investigation.

## 37. Agent Monitoring and Memory Poisoning

Monitoring should correlate memory changes with subsequent agent behavior.

Example:

```text id="n7x3qc"

Agent Behavior Changes

      |
```

## 38. Agent Monitoring and Agent Hijacking

Monitoring should detect potential hijacking indicators such as:

* Identity changes
* Credential anomalies
* Unexpected execution location
* Unexpected tools
* Abnormal context
* Unusual transactions
* Security-policy violations

Monitoring should be capable of distinguishing normal adaptation from potentially malicious control.

---

## 39. Agent Monitoring and Excessive Agency

Monitoring should identify when agents begin exercising capabilities outside their expected operational pattern.

Examples include:

* Accessing unnecessary systems
* Creating additional agents
* Expanding permissions
* Contacting unauthorized agents
* Performing unrelated transactions

This supports detection of excessive agency.

---

## 40. Agent Monitoring and Availability

Monitoring should also protect against availability failures.

Signals include:

* Resource exhaustion
* Infinite execution
* Excessive API calls
* Agent crashes
* Dependency failures
* Queue saturation

Availability monitoring is part of security because runaway agents can consume shared enterprise resources.

Resources may include:

* CPU
* Memory
* API calls
* Tokens
* Storage
* Network bandwidth
* Database queries
* Concurrent executions

Unexpected resource consumption may indicate either operational failure or malicious activity.

## 46. Agent Non-Repudiation Considerations

High-impact actions may require stronger evidence that a particular identity initiated or approved an action.

Relevant controls may include:

* Cryptographic identity
* Signed transactions
* Immutable logs
* Approval records
* Secure timestamps
* Correlation identifiers

Monitoring should preserve evidence sufficient for later investigation.

## 49. Core Principles of Agent Monitoring and Observability

The core principles are:

1. **Every significant autonomous action should be observable.**
2. **Every action should be attributable to an agent identity.**
3. **User-to-agent attribution should be preserved where applicable.**
4. **Agent activity should be correlated across tools, systems, and workflows.**
5. **Monitoring should cover decisions, actions, and outcomes.**
6. **Tool use should be independently observable.**
7. **Agent-to-agent relationships should be monitored.**
8. **Memory and persistent context changes should be observable.**
9. **Sensitive-data access should receive enhanced monitoring.**
10. **Autonomous transactions should be continuously monitored.**
11. **Behavioral baselines should support anomaly detection.**
12. **Security monitoring must distinguish health from authorization.**
13. **Monitoring should support incident response and forensic investigation.**
14. **Telemetry must be protected from unauthorized modification.**
15. **Observability should support continuous security assurance.**

---

## 50. Core Principle of Agent Monitoring and Observability

**An autonomous system cannot be securely governed if the enterprise cannot reliably observe, attribute, analyze, and investigate its behavior.**

The fundamental monitoring chain is:

```text id="r4m7xs"
Agent
  |
  v
Identity
  |
  v
Context
  |
  v
Decision
  |
  v
Authorization
  |
  v
Action
  |
  v
Tool / Resource
  |
  v
Outcome
  |
  v
Telemetry
  |
  v
Security Analysis
  |
  v
Detection / Response
```

Monitoring must therefore extend beyond conventional uptime and performance metrics into **behavior, authority, identity, context, tool usage, data access, transactions, delegation, memory, communication, and security state**.

The fundamental security principle is:

**If autonomous behavior cannot be observed and attributed, it cannot be reliably governed, investigated, or contained.**
