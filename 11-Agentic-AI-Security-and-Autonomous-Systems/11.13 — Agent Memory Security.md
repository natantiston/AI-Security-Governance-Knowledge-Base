# 11.13 — Agent Memory Security

### Part 1 — Foundations and Core Concepts

### 1. Definition of Agent Memory Security

Agent Memory Security is the discipline of protecting information retained by an AI agent from unauthorized access, manipulation, poisoning, disclosure, misuse, or persistence.

Agent memory may contain:

* user information;
* previous interactions;
* instructions;
* preferences;
* retrieved knowledge;
* decisions;
* task state;
* credentials or sensitive references;
* operational history.

Because memory can influence future autonomous behavior, it must be treated as a security boundary rather than merely a convenience feature.

---

### 2. Agent Memory as a Security Boundary

Memory creates a persistent boundary between past information and future agent behavior.

```text
Past Interaction
      ↓
Memory
      ↓
Future Context
      ↓
Agent Decision
      ↓
Agent Action
```

If an attacker can manipulate memory, they may influence future decisions without directly attacking the model.

---

### 3. Memory vs Context

Memory and context are related but different.

**Context** is information currently supplied to the agent for a particular execution.

**Memory** is information retained for possible use during future executions.

```text
Current Context
      ↓
Current Execution

Persistent Memory
      ↓
Future Executions
```

The persistence of memory creates additional security risks.

---

### 4. Short-Term Agent Memory

Short-term memory contains information maintained during an active interaction or execution.

Examples include:

* recent conversation history;
* current task state;
* temporary observations;
* intermediate decisions.

Security controls should prevent untrusted temporary information from being incorrectly treated as authoritative information.

---

### 5. Long-Term Agent Memory

Long-term memory retains information beyond a single session.

Examples include:

* user preferences;
* historical interactions;
* learned operational information;
* persistent task information.

Long-term memory creates greater persistence risk because malicious information can influence multiple future sessions.

---

### 6. Episodic Agent Memory

Episodic memory represents specific events or previous interactions.

Examples include:

```text
Customer requested refund
Previous incident occurred
User approved a particular workflow
Agent completed a previous task
```

The security challenge is determining whether the stored event is authentic, relevant, current, and authorized for future use.

---

### 7. Semantic Agent Memory

Semantic memory stores generalized knowledge or facts.

Examples include:

* organizational information;
* business rules;
* known relationships;
* frequently used concepts.

Semantic memory can become dangerous if an attacker successfully inserts false information that is later treated as trusted knowledge.

---

### 8. Procedural Agent Memory

Procedural memory represents how an agent performs a task.

It may contain:

* workflow preferences;
* procedural instructions;
* task sequences;
* operational patterns.

Because procedural memory can influence future actions, unauthorized modification can create persistent behavioral manipulation.

---

### 9. Memory State

Agent memory should be understood as a managed state.

```text
Create
  ↓
Store
  ↓
Retrieve
  ↓
Use
  ↓
Modify
  ↓
Retain / Expire
  ↓
Delete
```

Each stage introduces security considerations.

---

### 10. Memory Creation

Memory creation occurs when information is selected for persistent storage.

The agent should not automatically persist every piece of information it encounters.

Memory creation should consider:

* source trust;
* sensitivity;
* business purpose;
* relevance;
* retention requirements;
* authorization.

---

### 11. Memory Retrieval

Memory retrieval determines which stored information becomes available to an agent.

Retrieval should be controlled according to:

* agent identity;
* user identity;
* tenant;
* session;
* purpose;
* sensitivity;
* authorization.

A memory repository should not be treated as universally accessible agent knowledge.

---

### 12. Memory Modification

Memory modification changes information that may influence future behavior.

Unauthorized modification is particularly significant because the attacker may not need to compromise the agent continuously.

A single malicious memory modification can potentially affect many future executions.

---

### 13. Memory Deletion

Memory deletion removes retained information.

Deletion must be controlled to prevent:

* unauthorized destruction;
* evidence removal;
* loss of critical state;
* accidental deletion;
* manipulation of historical records.

Deletion events should be auditable where appropriate.

---

### 14. Memory Persistence

Persistence determines how long information remains available to the agent.

```text
Temporary
   ↓
Session
   ↓
Long-Term
   ↓
Indefinite
```

Longer retention increases the potential window for malicious information to influence future behavior.

---

### 15. Memory Trust

Not all memory should have the same level of trust.

Memory may originate from:

* system processes;
* approved enterprise sources;
* users;
* agents;
* external documents;
* websites;
* tools;
* other agents.

Each source should have an appropriate trust classification.

---

### 16. Trusted Memory

Trusted memory contains information that has passed appropriate validation and originates from an authorized source.

Trusted memory should still not automatically become security policy or authorization.

---

### 17. Untrusted Memory

Untrusted memory contains information whose origin, integrity, or authority has not been sufficiently established.

Examples include:

* externally supplied instructions;
* unverified user claims;
* retrieved web content;
* tool-generated content.

Untrusted memory should not silently acquire privileged status simply because it has been stored.

---

### 18. Memory Provenance

Memory provenance identifies where stored information originated.

A provenance record may identify:

```text
Source
 ↓
Identity
 ↓
Timestamp
 ↓
Session
 ↓
Transformation
 ↓
Storage
```

Provenance helps determine whether memory should be trusted and supports forensic investigation.

---

### 19. Memory Integrity

Memory integrity ensures that stored information has not been modified without authorization.

Integrity controls may include:

* cryptographic validation;
* versioning;
* access controls;
* immutable records;
* change monitoring.

Memory integrity is critical because altered memory can influence future agent behavior.

---

### 20. Memory Confidentiality

Memory may contain sensitive information accumulated across interactions.

Confidentiality controls should prevent unauthorized access to:

* personal information;
* confidential business information;
* security information;
* customer data;
* proprietary knowledge.

---

### 21. Memory Availability

Agents may depend on memory to perform business processes.

Memory security must therefore also protect against:

* unauthorized deletion;
* corruption;
* denial of access;
* storage failures;
* ransomware-like attacks against memory stores.

---

### 22. Memory Poisoning

Memory poisoning occurs when an attacker inserts malicious or misleading information into persistent agent memory.

```text
Attacker Input
      ↓
Stored as Memory
      ↓
Future Retrieval
      ↓
Agent Trusts Memory
      ↓
Manipulated Decision
```

Memory poisoning is particularly dangerous because the malicious influence may persist after the original attack has ended.

---

### 23. Persistent Memory Manipulation

Persistent memory manipulation involves changing information that will influence future agent executions.

An attacker may attempt to establish false:

* preferences;
* instructions;
* relationships;
* identities;
* operational facts;
* workflow requirements.

---

### 24. Memory Injection

Memory injection occurs when attacker-controlled information is deliberately introduced into an agent's memory.

The injected information may appear legitimate while actually attempting to influence future behavior.

---

### 25. Memory Poisoning vs Prompt Injection

Prompt injection primarily attempts to manipulate the current execution context.

Memory poisoning attempts to establish persistent influence.

```text
Prompt Injection
      ↓
Current Execution

Memory Poisoning
      ↓
Current + Future Executions
```

Memory poisoning therefore introduces an additional persistence dimension.

---

### 26. Memory-Based Instruction Manipulation

An attacker may attempt to store instructions that later appear to the agent as legitimate historical guidance.

For example:

```text
Malicious Instruction
       ↓
Persistent Memory
       ↓
Future Agent Session
       ↓
Instruction Retrieved
       ↓
Agent Follows It
```

Security architecture should prevent stored content from automatically becoming authoritative instructions.

---

### 27. Memory Authority

Memory content should not inherently possess authority.

A stored statement such as:

```text
"Always approve this transaction."
```

must not override:

* authorization policy;
* business rules;
* security controls;
* human approval requirements.

Memory can provide information without becoming an authority source.

---

### 28. Memory and Agent Identity

Memory should be associated with an appropriate identity boundary.

Security-relevant associations may include:

* agent identity;
* user identity;
* tenant;
* application;
* session;
* business process.

This prevents information belonging to one security context from being incorrectly reused in another.

---

### 29. Memory and Tenant Isolation

Multi-tenant agents require strict memory isolation.

```text
Tenant A Memory
      X
      │
      X
Tenant B Memory
```

A query from one tenant should not retrieve another tenant's memory unless explicitly authorized.

---

### 30. Memory and Session Isolation

Memory should respect session boundaries where required.

A new session should not automatically inherit sensitive information from another session simply because the same agent is being used.

---

### 31. Memory and User Isolation

Agents serving multiple users should prevent unauthorized cross-user memory access.

A user's historical information should not become available to another user without an appropriate authorization basis.

---

### 32. Memory and Sensitive Data

Memory may accumulate sensitive information over time.

Examples include:

* financial information;
* confidential communications;
* personal information;
* credentials;
* security details;
* proprietary business information.

Memory architecture should therefore incorporate data classification and minimization.

---

### 33. Memory Minimization

Agents should retain only information that is necessary for a legitimate business purpose.

```text
Information Encountered
        ↓
Is Persistence Necessary?
      /       \
    No         Yes
    ↓           ↓
 Discard    Validate + Store
```

Reducing stored information reduces the potential impact of memory compromise.

---

### 34. Memory Retention

Memory should have defined retention periods.

Retention should consider:

* business necessity;
* security risk;
* privacy requirements;
* regulatory obligations;
* operational value.

Information should not remain indefinitely simply because storage is technically inexpensive.

---

### 35. Memory Expiration

Memory should be capable of becoming invalid or automatically expiring.

Expiration is particularly important for:

* temporary instructions;
* session-specific information;
* outdated business conditions;
* temporary permissions;
* time-sensitive data.

---

### 36. Memory Freshness

Stored information may become inaccurate over time.

An agent should distinguish between:

```text
Stored Information
      ≠
Current Authoritative State
```

For example, historical memory should not override a current enterprise system of record.

---

### 37. Memory Integrity vs Memory Accuracy

Memory integrity means that stored information has not been improperly modified.

Memory accuracy means that the information is actually correct.

These are different properties.

```text
Authentically Stored False Information
      ↓
High Integrity
      ↓
Still Incorrect
```

Security architecture should address both integrity and trustworthiness.

---

### 38. Memory Retrieval Trust

Retrieved memory should be evaluated before it influences security-sensitive decisions.

Factors may include:

* provenance;
* age;
* source;
* sensitivity;
* integrity;
* relevance;
* authorization.

---

### 39. Memory Context Injection

Retrieved memory becomes part of the agent's effective context.

Therefore:

```text
Memory Store
     ↓
Memory Retrieval
     ↓
Agent Context
     ↓
Model Reasoning
```

A malicious memory entry can function as an indirect influence mechanism.

---

### 40. Memory Access as a Security Operation

Reading memory should be considered a security-sensitive operation when memory contains confidential or operationally significant information.

Access controls should determine:

* who can read;
* which memory can be read;
* under what purpose;
* under what conditions.

---

### 41. Memory Write as a Security Operation

Writing memory can be even more sensitive than reading it because the write may influence future decisions.

Memory writes should therefore have explicit controls around:

* source;
* authorization;
* content;
* classification;
* provenance;
* persistence.

---

### 42. Memory Trust Boundaries

Memory architecture should separate different trust classes.

```text
┌──────────────────────────────┐
│ Authoritative Enterprise Data│
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ Validated Agent Memory       │
└──────────────┬───────────────┘
               │
┌──────────────▼───────────────┐
│ User / External Information  │
└──────────────────────────────┘
```

Information should not automatically move upward in trust.

---

### 43. Memory and Prompt Security

Memory can become a delivery mechanism for malicious instructions.

A prompt-injection attack may therefore have two stages:

```text
Initial Injection
      ↓
Memory Persistence
      ↓
Future Retrieval
      ↓
Future Agent Manipulation
```

Memory security must account for this persistence path.

---

### 44. Memory and Tool Security

Tool outputs may be stored in memory and later influence agent behavior.

A malicious or compromised tool could therefore introduce persistent malicious information.

Tool-originated memory should retain appropriate provenance and trust classification.

---

### 45. Memory and Agent-to-Agent Communication

Agents may exchange information that is subsequently stored in memory.

This creates a potential propagation path:

```text
Compromised Agent A
       ↓
Malicious Message
       ↓
Agent B Memory
       ↓
Future Agent B Behavior
```

Cross-agent memory trust must therefore be explicitly governed.

---

### 46. Memory and Autonomous Actions

Memory may influence autonomous decisions and actions.

```text
Memory
  ↓
Context
  ↓
Reasoning
  ↓
Decision
  ↓
Tool
  ↓
Action
```

A compromised memory layer can therefore indirectly affect enterprise operations.

---

### 47. Memory and Agent Hijacking

Memory can become a persistence mechanism for agent hijacking.

Instead of repeatedly controlling an agent, an attacker may attempt to alter its memory once and allow the malicious influence to continue.

This makes memory integrity an important component of hijacking resistance.

---

### 48. Memory Accountability

Organizations should be able to determine:

* who created memory;
* what was stored;
* when it was stored;
* who modified it;
* what source provided it;
* which agent retrieved it;
* which actions were influenced by it.

This supports investigation and accountability.

---

### 49. Core Principles of Agent Memory Security

Core principles include:

1. **Memory is a security boundary.**
2. **Stored information is not automatically trusted.**
3. **Memory must have provenance.**
4. **Memory writes require authorization.**
5. **Memory access requires appropriate authorization.**
6. **Memory should be minimized.**
7. **Memory should have defined retention.**
8. **Memory integrity must be protected.**
9. **Tenant and user memory must remain isolated.**
10. **Memory must not independently grant authority.**

---

### 50. Core Principle of Agent Memory Security

The fundamental principle is:

> **Agent memory must remain an authorized, integrity-protected, provenance-aware source of information—not an uncontrolled source of persistent authority.**

The security boundary can be represented as:

```text
Memory Source
      ↓
Trust Classification
      ↓
Integrity Validation
      ↓
Authorization
      ↓
Controlled Retrieval
      ↓
Agent Context
      ↓
Independent Security Controls
      ↓
Authorized Action
```

A memory entry may influence what an agent knows, but it must never independently determine what the agent is authorized to do.

# Part 2 — Technical Security and Control Mechanisms

### 51. Agent Memory Security Control Architecture

Agent memory security should use layered controls protecting the complete memory lifecycle.

```text
Memory Source
     ↓
Memory Ingestion
     ↓
Trust / Provenance Validation
     ↓
Memory Store
     ↓
Access Authorization
     ↓
Memory Retrieval
     ↓
Integrity Validation
     ↓
Agent Context
     ↓
Decision / Action
```

No single memory control should be treated as sufficient.

---

### 52. Memory Identity Control

Every memory operation should be associated with a verifiable identity.

The identity context should establish:

* which agent is accessing memory;
* which user or workload initiated the operation;
* which tenant is involved;
* which session or execution is active.

---

### 53. Memory Access Authentication

Agents should authenticate before accessing protected memory.

Authentication should establish that the requesting workload is the legitimate agent associated with the requested memory operation.

---

### 54. Strong Memory Authentication

High-sensitivity memory stores should require strong workload authentication.

Appropriate mechanisms may include:

* mutual TLS;
* workload identity;
* signed tokens;
* certificate-based authentication.

Authentication strength should correspond to memory sensitivity.

---

### 55. Fine-Grained Memory Authorization

Authorization should determine exactly which memory an agent may access.

```text
Agent
  +
Memory Object
  +
Operation
  +
Context
  ↓
Authorization Decision
```

Access to one memory partition should not imply access to every memory partition.

---

### 56. Independent Memory Authorization Service

Memory authorization should be independently enforced where risk warrants it.

The agent should not be able to decide:

> "I am allowed to access this memory."

An independent security layer should make that decision.

---

### 57. Memory Access Allowlisting

Only approved agents, applications, and services should access protected memory repositories.

Allowlisting should consider:

* identity;
* purpose;
* environment;
* tenant;
* memory classification.

---

### 58. Memory Type Allowlisting

Only approved memory types should be available to an agent.

Examples:

```text
User Preferences      → Allowed
Task State             → Allowed
Security Credentials   → Denied
Other Tenant Memory    → Denied
Administrative Memory  → Restricted
```

---

### 59. Memory Namespace Segmentation

Memory should be logically or physically segmented.

Possible namespaces include:

* tenant;
* user;
* agent;
* application;
* session;
* business process;
* environment.

Segmentation reduces accidental and malicious cross-boundary retrieval.

---

### 60. Memory Object Authorization

Individual memory objects or records should be subject to access policies when necessary.

This prevents a legitimate agent from receiving excessive information merely because it has access to a memory database.

---

### 61. Memory Write Authorization

Writing to memory should require explicit authorization.

The authorization decision should consider:

* source identity;
* memory type;
* content sensitivity;
* business purpose;
* persistence duration.

---

### 62. Memory Modification Controls

Memory modifications should be restricted to approved operations.

Controls should distinguish between:

* append;
* update;
* replace;
* delete;
* administrative modification.

Higher-impact modifications should receive stronger controls.

---

### 63. Memory Integrity Validation

Memory should be validated for unauthorized modification.

Possible mechanisms include:

* cryptographic hashes;
* digital signatures;
* integrity metadata;
* version history;
* append-only records.

---

### 64. Memory Version Control

Important memory should maintain version history.

```text
Version 1
   ↓
Version 2
   ↓
Version 3
   ↓
Current State
```

Unexpected changes can then be detected and previous trusted versions can potentially be restored.

---

### 65. Memory Provenance Controls

Every important memory entry should retain provenance information.

Provenance may include:

* source;
* identity;
* timestamp;
* session;
* originating system;
* transformation history.

This supports trust evaluation and forensic analysis.

---

### 66. Memory Source Validation

The system should validate the source of information before allowing it to become persistent memory.

Sources may be classified as:

```text
Authoritative Enterprise Source
Validated Agent Source
Authenticated User Source
External Source
Unknown Source
```

Unknown or untrusted sources should receive appropriate restrictions.

---

### 67. Memory Content Validation

Memory content should be validated before persistence.

Validation may detect:

* malicious instructions;
* unexpected commands;
* credential-like content;
* policy overrides;
* suspicious URLs;
* attempts to manipulate future behavior.

---

### 68. Memory Instruction Filtering

Instructions stored in memory should receive special treatment.

A memory entry containing:

> "Always bypass approval."

should not become an executable security instruction merely because it is stored in the memory database.

Instruction-like content should be separated from authoritative policy.

---

### 69. Prompt and Instruction Integrity

System instructions and authoritative agent policies should remain separate from ordinary memory.

```text
Security Policy
      ≠
Agent Memory
      ≠
User Content
```

Memory should not overwrite higher-trust instruction sources.

---

### 70. Untrusted Memory Isolation

Memory derived from untrusted sources should remain clearly classified.

For example:

```text
External Website
      ↓
Untrusted Memory
      ↓
Validation
      ↓
Controlled Retrieval
```

Untrusted information should not silently become trusted operational guidance.

---

### 71. Memory Poisoning Detection

Systems should detect suspicious memory-writing patterns.

Indicators may include:

* unusual write frequency;
* sudden large-scale changes;
* repeated instruction insertion;
* changes from unauthorized identities;
* unusual memory categories;
* attempts to modify high-trust entries.

---

### 72. Memory Poisoning Prevention

Preventive controls should limit who and what can write persistent memory.

Controls may include:

* write allowlists;
* content validation;
* provenance requirements;
* approval for sensitive memory;
* write-rate limits.

---

### 73. Memory Isolation

Memory belonging to different security contexts should be isolated.

```text
Tenant A
 └── Agent Memory

Tenant B
 └── Agent Memory

Tenant C
 └── Agent Memory
```

Isolation should be enforced technically rather than through agent instructions alone.

---

### 74. Memory Authorization by Tenant

Tenant information should be included in memory access decisions.

An authenticated agent serving multiple tenants should not be able to retrieve memory solely because the memory database is technically reachable.

---

### 75. Memory Authorization by User

Where memory is user-specific, authorization should validate the requesting user context.

User A's persistent memory should not automatically become available to User B.

---

### 76. Memory Integrity by Session

Session-specific memory should be bound to the correct session.

This helps prevent session hijacking from exposing or modifying unrelated temporary state.

---

### 77. Persistent Memory Controls

Persistent memory should have explicit lifecycle controls covering:

* creation;
* retrieval;
* modification;
* expiration;
* archival;
* deletion.

---

### 78. Data Access Authorization

Sensitive information retrieved from memory should remain subject to normal data-access controls.

Memory should not become an authorization bypass around enterprise data governance.

---

### 79. Data Minimization

Only information required for the approved purpose should be stored.

```text
Information
     ↓
Necessary?
  /     \
No       Yes
↓         ↓
Discard   Store Minimally
```

---

### 80. Field-Level Memory Protection

Sensitive memory fields should receive additional protection.

For example:

| Memory Field   | Control                       |
| -------------- | ----------------------------- |
| Preference     | Normal access                 |
| Customer ID    | Restricted                    |
| Financial Data | Highly restricted             |
| Credential     | Prohibited / isolated         |
| Security Token | Prohibited from normal memory |

---

### 81. Tenant Isolation

Tenant memory should be separated through enforceable boundaries.

Controls may include:

* tenant-specific encryption keys;
* separate namespaces;
* row-level security;
* database policies;
* separate storage where necessary.

---

### 82. Session Isolation

Session-specific memory should not leak across sessions.

Session identifiers should be bound to memory access requests and validated independently.

---

### 83. Network Segmentation

Memory infrastructure should be placed in controlled network zones.

```text
Agent Runtime
      ↓
Memory Security Gateway
      ↓
Memory Service
      ↓
Protected Memory Store
```

Direct unrestricted network access should be avoided.

---

### 84. Memory Egress Controls

Memory data leaving the trusted environment should be restricted.

Egress controls should address:

* external APIs;
* email;
* web requests;
* agent-to-agent communication;
* third-party services.

---

### 85. External Memory Communication Controls

If memory is synchronized with external systems, the synchronization channel should be controlled.

Controls should include:

* authenticated connections;
* approved destinations;
* encryption;
* data classification;
* integrity verification.

---

### 86. Memory Encryption Controls

Sensitive memory should be protected through encryption:

* at rest;
* in transit;
* during controlled processing where appropriate.

Encryption keys should remain outside ordinary agent memory.

---

### 87. Memory Key Isolation

Encryption keys should be isolated from:

* prompts;
* agent context;
* memory records;
* model outputs.

An agent should not be able to retrieve its own memory encryption keys through normal reasoning.

---

### 88. Human Approval for Sensitive Memory Changes

High-impact memory changes may require human approval.

Examples include modifications to:

* security policies;
* privileged workflows;
* financial instructions;
* administrative relationships.

---

### 89. Memory Change Preview

Sensitive memory modifications should be previewed before approval.

The preview should show:

* current value;
* proposed value;
* source;
* reason;
* affected agent;
* affected scope.

---

### 90. Dual Authorization for Critical Memory

Critical memory modifications should require independent authorization.

This is appropriate for memory that can materially influence:

* privileged operations;
* financial decisions;
* security controls;
* production workflows.

---

### 91. Memory Reversibility Controls

Memory changes should be reversible where practical.

Controls may include:

* version rollback;
* soft deletion;
* restore points;
* change history.

This limits the persistence of successful memory poisoning.

---

### 92. Memory Access Limits

Agents should have limits on memory operations.

Examples include:

* maximum retrieval volume;
* maximum writes;
* maximum modifications;
* maximum deletion operations.

---

### 93. Memory Retrieval Loop Detection

Repeated or abnormal memory retrieval should be detected.

```text
Query A
 ↓
Query B
 ↓
Query A
 ↓
Query B
 ↓
...
```

Such behavior may indicate malfunction, abuse, or an attempt to extract large amounts of memory.

---

### 94. Recursive Memory Access Controls

Agents should not be allowed to recursively expand memory access through references or linked memory stores without explicit authorization.

---

### 95. Agent-to-Agent Memory Authentication

When one agent requests another agent's memory or memory-derived information, the requesting agent should authenticate.

Agent-to-agent trust should never be assumed.

---

### 96. Agent-to-Agent Memory Integrity

Memory information exchanged between agents should preserve integrity and provenance.

The receiving agent should know:

* which agent supplied the information;
* when it was supplied;
* what authority the source has;
* whether it has been modified.

---

### 97. Delegated Memory Access Constraints

Delegated access to memory should be explicitly scoped.

```text
Agent A
   ↓
Delegates
   ↓
Agent B
   ↓
Specific Memory Scope
```

Delegation should not create unrestricted memory access.

---

### 98. Memory Retrieval Validation

Retrieved memory should be validated before it enters sensitive agent context.

Validation may include:

* schema validation;
* provenance verification;
* integrity verification;
* classification;
* freshness checks.

---

### 99. Output Validation Before Memory Write

Agent-generated content should be validated before being committed to persistent memory.

This is particularly important where the agent itself is allowed to create memory.

---

### 100. Business Rule Enforcement

Business rules affecting memory should be enforced outside the model.

For example:

```text
Retention ≤ Approved Period
Sensitive Memory → Restricted
Credential Data → Never Persist
Tenant ID → Must Match Session
```

---

### 101. Memory Resource Controls

Memory resources should be constrained.

Controls may include:

* storage quotas;
* maximum record sizes;
* retrieval limits;
* write limits;
* retention limits.

---

### 102. Memory Rate Limiting

Memory operations should be rate-limited to prevent:

* bulk extraction;
* memory flooding;
* automated poisoning;
* denial-of-service conditions.

---

### 103. Memory Concurrency Controls

Concurrent memory modifications should be controlled to prevent conflicting updates and race conditions.

Critical memory should use appropriate locking or transactional mechanisms.

---

### 104. Memory Timeout Controls

Memory requests should have bounded execution times.

Timeouts reduce the risk of:

* hanging operations;
* resource exhaustion;
* uncontrolled retrieval;
* persistent execution loops.

---

### 105. Memory Retry Controls

Retry behavior should be bounded.

A failed memory operation should not create unlimited retries that could amplify:

* writes;
* queries;
* deletion requests;
* synchronization traffic.

---

### 106. Memory Circuit Breakers

Circuit breakers should suspend memory operations when abnormal behavior is detected.

Triggers may include:

* excessive writes;
* abnormal retrieval volume;
* integrity failures;
* repeated authorization failures;
* suspicious modification patterns.

---

### 107. Emergency Memory Controls

Security teams should have emergency mechanisms to:

* block memory writes;
* restrict memory reads;
* isolate memory stores;
* suspend synchronization;
* freeze sensitive memory.

---

### 108. Agent Memory Kill Switch

For high-risk environments, a kill switch should be capable of stopping the agent's access to memory independently of the agent.

```text
Security Operator
      ↓
Emergency Control
      ↓
Block Agent Memory Access
      ↓
Suspend Writes / Reads
```

---

### 109. Memory Credential Revocation

Credentials used to access memory should be rapidly revocable.

Revocation should prevent continued access even if the agent runtime remains active.

---

### 110. Memory Isolation During Incident Response

During suspected memory poisoning, the affected memory should be isolated.

Possible actions include:

### 194. Short-Lived Memory Authority

Memory access authority should expire automatically.

Short-lived authorization should be combined with:

* narrow scope;
* session binding;
* tenant binding;
* operation restrictions;
* revocation.

This reduces the persistence of compromised memory access.

---

### 196. Memory Integrity Controls

Critical memory should use strong integrity mechanisms.

Potential mechanisms include:

* cryptographic hashes;
* digital signatures;
* immutable records;
* append-only storage;
* versioning;
* integrity monitoring.

Integrity validation should occur before high-impact memory is trusted.

```text

      ≠
```

### 201. High-Impact Memory Protection

Memory that can materially influence high-impact operations should receive enhanced protection.

Examples include memory affecting:

* financial transactions;
* privileged administration;
* production changes;
* security configurations;
* identity decisions;
* critical business workflows.

Such memory may require approval, dual control, or stronger integrity guarantees.

### 202. Human Approval Architecture

High-risk memory modifications should be routed through an independent approval service.

```text
Agent
 ↓

 ↓
Risk Evaluation
 ↓
Human Approval
 ↓
Authorization
 ↓
Memory Commit
```

The agent should not be able to create or fabricate its own approval.

---

### 203. Approval Integrity

Approval should be bound to the exact memory operation being authorized.

The system should verify:

* approver identity;
* memory object;
* proposed change;
* scope;
* timestamp;
* approval status.

Approval should not be reusable for unrelated modifications.

---

### 204. Dual Control and Segregation of Duties

Critical memory modifications should require independent authorization.

For example:

```text
Agent / Operator A
       ↓
Proposes Change
       ↓
Independent Reviewer B
       ↓
Approval
       ↓
Memory Commit
```

This reduces the risk of a single compromised identity controlling critical persistent state.

---

### 205. Memory Suspension Architecture

The enterprise should be capable of suspending memory operations independently from the agent.

Suspension may include:

* block writes;
* restrict reads;
* freeze sensitive records;
* stop synchronization;
* isolate memory repositories.

### 206. Memory Revocation Architecture

Memory access authority should be rapidly revocable.

* active tokens;
* sessions;
* delegated access;
* service credentials;
* agent memory permissions.

### 207. Memory Blast-Radius Reduction

Memory architecture should limit the impact of a compromised memory store.

Controls include:

* agent-specific namespaces;
* limited retrieval;

### 234. Memory Integrity Is Not Memory Trust

A memory record can be perfectly intact and still be untrustworthy.

```text

      ↓
Integrity = Valid
      ↓
Source = Malicious
      ↓
Information = Untrusted
```

Therefore, memory security must evaluate both **integrity** and **trustworthiness**.

### 235. Memory Information Is Not Memory Authority

Stored information should never automatically become an authorization mechanism.

```text
Memory:
"User approved transaction."

        ≠

Authorization:
"Transaction is authorized."
```

Authorization must be independently established by the appropriate control system.

### 236. Memory Persistence Must Not Create Persistent Authority

Persistent storage must not create persistent authorization.

```text
Memory Persistence
        ≠
Permission Persistence
        ≠
Authority Persistence
```

An agent should still require current authorization even when historical memory indicates that an action was previously permitted.
