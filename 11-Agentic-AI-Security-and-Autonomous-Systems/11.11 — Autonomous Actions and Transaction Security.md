# 11.11 — Autonomous Actions and Transaction Security

## Part 1 — Foundations and Core Concepts

### 1. Definition of Autonomous Actions

An autonomous action is an operation initiated or executed by an AI agent without requiring a human to manually perform each individual step.

Examples include:

* creating or modifying records;
* sending communications;
* changing configurations;
* provisioning infrastructure;
* executing workflows;
* initiating financial transactions;
* approving operational requests.

```text
Goal
 ↓
Agent Decision
 ↓
Action Selection
 ↓
Authorization
 ↓
Execution
```

Autonomous actions transform AI from an information-processing capability into an active participant in business operations.

---

### 2. Definition of Transaction Security

Transaction security is the discipline of protecting actions that create, modify, transfer, approve, or delete business or technical state.

A transaction may involve:

* money;
* data;
* identities;
* infrastructure;
* contractual commitments;
* security configurations;
* business records.

Transaction security ensures that an autonomous action is legitimate, authorized, bounded, attributable, and appropriately controlled.

---

### 3. Autonomous Actions as a Security Boundary

An autonomous action crosses from **decision space into execution space**.

```text
Agent Reasoning
      │
      ▼
Action Proposal
      │
      ▼
Security Boundary
      │
      ▼
External Effect
```

This boundary must be protected because an incorrect or malicious action can create real-world consequences.

---

### 4. Decision vs Action

A decision determines what should happen.

An action actually causes something to happen.

```text
Decision:
"Refund the customer."

Action:
"Execute €2,000 refund."
```

The security requirements for these two stages are different.

A model may recommend an action, but execution should require independent authorization.

---

### 5. Action vs Authorization

The ability to perform an action is not evidence that the action is authorized.

```text
Action Capability
       ≠
Authorization
```

For example, an agent may technically be capable of deleting a database record while policy prohibits deletion without approval.

---

### 6. Transaction vs Tool Invocation

A tool invocation is the technical mechanism used to perform an operation.

A transaction represents the business or operational effect of that operation.

```text
Agent
 ↓
Tool Invocation
 ↓
Transaction
 ↓
Business Effect
```

Not every tool call is a transaction, but every high-impact transaction performed through an agent should be treated as security-sensitive.

---

### 7. Autonomous Transaction

An autonomous transaction is a transaction initiated or completed by an AI agent with limited or no human intervention at the point of execution.

Examples:

* payment;
* refund;
* purchase;
* account modification;
* resource provisioning;
* production deployment.

Autonomous transactions require stronger controls than ordinary informational interactions.

---

### 8. Transaction Authority

Transaction authority defines what an agent is permitted to execute.

It should specify:

* transaction types;
* transaction value;
* permitted resources;
* permitted recipients;
* frequency;
* duration;
* approval requirements.

```text
Agent
 ↓
Transaction Authority
 ├── Type
 ├── Amount
 ├── Resource
 ├── Recipient
 └── Time
```

---

### 9. Action Scope

Action scope defines the boundaries within which an autonomous action may operate.

Scope may include:

* specific resources;
* specific users;
* specific tenants;
* specific environments;
* specific transaction types;
* specific amounts.

A narrow scope reduces the consequences of agent misuse.

---

### 10. Transaction Boundaries

Transaction boundaries define where one autonomous operation begins and ends.

Clear boundaries are important for:

* authorization;
* logging;
* rollback;
* monitoring;
* accountability.

```text
Transaction Start
      ↓
Authorization
      ↓
Execution
      ↓
Commit
      ↓
Transaction End
```

---

### 11. Transaction Context

A transaction should carry sufficient security context to support authorization and attribution.

Relevant context may include:

* initiating user;
* agent identity;
* session;
* tenant;
* resource;
* purpose;
* transaction type;
* approval status;
* timestamp.

---

### 12. Trusted and Untrusted Transaction Inputs

Not every input influencing a transaction should be trusted.

Inputs may originate from:

```text
Trusted:
Identity System
Authorization System
Business Policy

Potentially Untrusted:
User Input
External Documents
Web Content
Tool Results
Agent-Generated Data
```

Transaction controls must distinguish authoritative security context from untrusted content.

---

### 13. Transaction Integrity

Transaction integrity means that the transaction executed is the transaction that was actually authorized.

```text
Authorized Transaction
        ↓
Execution Request
        ↓
Actual Transaction
```

The system should detect unauthorized changes between these stages.

---

### 14. Transaction Authenticity

Transaction authenticity establishes that the request originated from the claimed authorized agent or principal.

Authentication provides evidence of **who initiated the transaction**.

It does not independently establish whether the transaction is permitted.

---

### 15. Transaction Authorization

Transaction authorization determines whether a specific transaction is allowed.

A decision may consider:

* identity;
* permission;
* resource;
* transaction type;
* amount;
* context;
* risk;
* approval.

```text
Identity
   +
Permission
   +
Transaction
   +
Context
   ↓
Authorization Decision
```

---

### 16. Transaction Risk

Transaction risk represents the potential impact of an autonomous action.

Risk may increase with:

* monetary value;
* data sensitivity;
* privilege;
* irreversibility;
* external exposure;
* number of affected records;
* business criticality.

```text
Transaction Risk =
Impact × Exposure × Autonomy
```

The exact calculation should be defined according to enterprise risk methodology.

---

### 17. Transaction Value

Transaction value is not limited to monetary value.

It may represent:

* financial amount;
* number of records;
* infrastructure capacity;
* number of users affected;
* sensitivity of data;
* operational impact.

A transaction involving no money can still have very high business value.

---

### 18. Transaction Limits

Autonomous transactions should operate within explicit limits.

Examples:

```text
Maximum Payment       €1,000
Maximum Records       100
Maximum Instances     5
Maximum Daily Spend   €5,000
```

Limits should be enforced independently of agent reasoning.

---

### 19. Cumulative Transaction Limits

A series of individually acceptable actions may create unacceptable aggregate risk.

```text
€900 × 1  → Acceptable

€900 × 100 → Potentially Excessive
```

Therefore, transaction security should consider cumulative activity over defined periods.

---

### 20. Transaction Frequency

Agents may execute transactions much faster than humans.

This can amplify errors and attacks.

```text
Human:
10 actions/hour

Agent:
10,000 actions/hour
```

Transaction frequency controls should prevent excessive autonomous execution.

---

### 21. Transaction Velocity

Transaction velocity measures how rapidly transactions occur.

High velocity may indicate:

* automation failure;
* runaway behavior;
* compromised credentials;
* fraud;
* malicious agent manipulation.

Velocity thresholds can therefore become important security controls.

---

### 22. Reversible Transactions

A reversible transaction can be safely undone.

Examples:

* changing a draft;
* updating a configuration with rollback;
* moving a file where restoration is available.

Reversibility reduces the potential impact of autonomous mistakes.

---

### 23. Irreversible Transactions

An irreversible transaction cannot easily be undone.

Examples may include:

* permanent deletion;
* external financial transfer;
* publication of sensitive information;
* destruction of infrastructure;
* legally binding communication.

Irreversible actions require stronger controls.

---

### 24. Transaction Commit

Commit represents the point at which the transaction becomes effective.

```text
Proposal
 ↓
Validation
 ↓
Authorization
 ↓
Approval
 ↓
COMMIT
```

High-impact systems should provide a security checkpoint immediately before commit.

---

### 25. Pre-Commit Security Validation

Before committing a high-impact autonomous transaction, the system should revalidate:

* identity;
* authorization;
* parameters;
* limits;
* approval;
* transaction state;
* risk.

This protects against changes that occur after the original authorization decision.

---

### 26. Transaction Atomicity

Where technically possible, autonomous transactions should be atomic.

Either:

```text
All Required Operations
        ↓
     COMMIT
```

or:

```text
Failure
  ↓
ROLLBACK
```

Partial execution can create inconsistent or unsafe states.

---

### 27. Transaction Idempotency

Idempotency prevents repeated execution from producing unintended duplicate effects.

For example:

```text
Agent Retry
   ↓
Same Transaction ID
   ↓
System Detects Duplicate
   ↓
No Duplicate Payment
```

This is especially important for autonomous retries.

---

### 28. Duplicate Transaction Risk

Agents may retry operations after:

* network failures;
* timeouts;
* unclear responses;
* tool errors.

Without duplicate detection, one intended transaction could become multiple transactions.

---

### 29. Transaction State

Transaction state should be explicitly tracked.

Typical states include:

```text
PROPOSED
   ↓
VALIDATED
   ↓
AUTHORIZED
   ↓
APPROVED
   ↓
EXECUTING
   ↓
COMMITTED
```

Failed or rejected transactions should not accidentally transition into an executable state.

---

### 30. Transaction Lifecycle

A secure autonomous transaction lifecycle can be represented as:

```text
Intent
 ↓
Proposal
 ↓
Validation
 ↓
Risk Assessment
 ↓
Authorization
 ↓
Approval
 ↓
Execution
 ↓
Commit
 ↓
Verification
 ↓
Audit
```

Each stage creates an opportunity for security enforcement.

---

### 31. Autonomous Action Chains

An agent may perform several related actions to accomplish one goal.

```text
Action A
 ↓
Action B
 ↓
Action C
 ↓
Transaction
```

Security controls should evaluate both individual actions and the overall chain.

---

### 32. Cascading Transactions

One autonomous transaction can trigger another.

```text
Agent
 ↓
Transaction A
 ↓
Workflow
 ↓
Transaction B
 ↓
Transaction C
```

This can create unexpected amplification.

Transaction security should identify and control cascading effects.

---

### 33. Transaction Dependency

Transactions may depend on previous actions.

For example:

```text
Create Account
      ↓
Assign Role
      ↓
Activate Account
```

If one transaction is compromised, subsequent dependent transactions may magnify the impact.

---

### 34. Transaction Delegation

An agent may delegate a transaction to another agent or service.

Delegation should preserve the original transaction constraints.

```text
Agent A
 ↓
Delegates
 ↓
Agent B
 ↓
Transaction
```

Agent B should not receive broader transaction authority than Agent A possessed.

---

### 35. Transaction Authority Propagation

Authority should not automatically expand as transactions move through systems.

```text
Original Authority
       ↓
Delegated Authority
       ↓
Equal or Reduced Scope
```

Any expansion should require an independent authorization decision.

---

### 36. Human-in-the-Loop Transactions

A human-in-the-loop model requires human intervention before certain transactions execute.

```text
Agent
 ↓
Transaction Proposal
 ↓
Human Review
 ↓
Approval
 ↓
Execution
```

This is appropriate for high-impact or sensitive transactions.

---

### 37. Human-on-the-Loop Transactions

Human-on-the-loop models allow autonomous execution while maintaining human monitoring and intervention capability.

```text
Agent
 ↓
Autonomous Execution
 ↓
Human Monitoring
 ↓
Intervention if Required
```

This model requires strong detection and emergency controls.

---

### 38. Approval Thresholds

Organizations should define transaction thresholds that determine when human approval is required.

Example:

| Transaction    | Control                   |
| -------------- | ------------------------- |
| < €100         | Autonomous                |
| €100–€1,000    | Notification / monitoring |
| €1,000–€10,000 | Human approval            |
| > €10,000      | Dual approval             |

Actual thresholds should be established according to business risk.

---

### 39. Transaction Preview

High-impact transactions should support an action preview before execution.

```text
Transaction Preview
 ├── What will happen?
 ├── Who is affected?
 ├── What data is involved?
 ├── What is the value?
 └── Can it be reversed?
```

The preview should correspond to the actual transaction that will execute.

---

### 40. Transaction Confirmation

Confirmation should be tied to the specific transaction.

A generic approval such as:

```text
"Agent may process payments."
```

is weaker than:

```text
"Approve payment of €2,500 to Vendor X."
```

Transaction-specific authorization reduces ambiguity.

---

### 41. Transaction Attribution

Every autonomous transaction should be attributable.

The organization should be able to establish:

```text
Who initiated it?
Which agent executed it?
Under whose authority?
Which policy allowed it?
Which tool executed it?
What resource changed?
When did it occur?
```

---

### 42. Transaction Auditability

Transaction records should provide sufficient evidence for reconstruction.

Important evidence may include:

* initiating identity;
* agent identity;
* transaction ID;
* authorization decision;
* approval;
* parameters;
* policy version;
* execution result;
* timestamp.

---

### 43. Transaction Non-Repudiation Considerations

For high-value or sensitive transactions, organizations may require stronger evidence that an authorized principal approved or initiated the transaction.

Possible mechanisms include:

* cryptographic signatures;
* signed approvals;
* immutable audit records;
* trusted timestamps.

Non-repudiation requirements should be proportional to transaction risk.

---

### 44. Transaction Monitoring

Autonomous transactions should be continuously monitored for abnormal behavior.

Monitoring may detect:

* unusual values;
* unusual frequency;
* unusual recipients;
* unusual resources;
* unexpected transaction sequences;
* deviations from normal behavior.

---

### 45. Transaction Anomaly Detection

Behavioral analytics can identify transactions that deviate from expected patterns.

```text
Normal:
€200–€500 transactions

Observed:
€25,000 transaction

→ Anomaly
→ Enhanced Control
```

Anomaly detection should complement deterministic transaction limits.

---

### 46. Transaction Failure Handling

Failed transactions should fail safely.

The system should prevent failures from causing:

* duplicate execution;
* partial authorization;
* uncontrolled retries;
* inconsistent state.

```text
Failure
 ↓
Stop
 ↓
Determine State
 ↓
Rollback / Compensate
 ↓
Record
```

---

### 47. Transaction Kill Switch

High-risk autonomous transaction systems should have emergency controls.

A kill switch may:

* stop new transactions;
* terminate active execution;
* revoke credentials;
* disable specific transaction types;
* isolate the agent.

---

### 48. Transaction Circuit Breaker

Circuit breakers can automatically halt transactions after abnormal behavior.

```text
Normal Activity
      ↓
Threshold Exceeded
      ↓
Circuit OPEN
      ↓
Transactions Blocked
```

This is particularly useful for runaway autonomous systems.

---

### 49. Transaction Governance

Autonomous transactions should be governed as enterprise risk objects.

Governance should define:

* ownership;
* transaction classification;
* risk tier;
* authorization;
* approval;
* monitoring;
* evidence;
* exception handling;
* reauthorization.

---

### 50. Core Principle of Autonomous Actions and Transaction Security

The fundamental principle is:

> **An autonomous agent may propose or initiate an action, but the authority to execute a consequential transaction must remain independently governed, authorized, bounded, attributable, monitored, and recoverable.**

The secure model is:

```text
Agent Intent
     ↓
Action Proposal
     ↓
Risk Evaluation
     ↓
Independent Authorization
     ↓
Human Approval if Required
     ↓
Transaction Validation
     ↓
Bounded Execution
     ↓
Commit
     ↓
Verification
     ↓
Audit
```

Autonomy should therefore increase execution efficiency without eliminating the security controls that protect the enterprise from unauthorized, excessive, irreversible, or manipulated transactions.

# Part 2 — Technical Security and Control Mechanisms

### 51. Autonomous Action Security Control Architecture

Autonomous action security requires multiple independent controls between an agent's decision and the resulting business or technical effect.

```text
Agent
  ↓
Action Request
  ↓
Identity Verification
  ↓
Authorization
  ↓
Transaction Validation
  ↓
Risk Evaluation
  ↓
Approval Gate
  ↓
Execution Controls
  ↓
Protected System
  ↓
Monitoring + Audit
```

No single model-generated decision should be sufficient to authorize a consequential transaction.

---

### 52. Action Identity Control

Every autonomous action should be bound to an identifiable security principal.

The action record should establish:

* executing agent;
* initiating user, where applicable;
* session;
* tenant;
* execution environment;
* transaction identifier.

This enables accountability and investigation.

---

### 53. Workload Identity for Autonomous Actions

Agents should execute under controlled workload identities rather than shared human credentials.

```text
Agent
  ↓
Workload Identity
  ↓
Authorized Transaction
  ↓
Target System
```

Workload identity allows transactions to be distinguished from actions performed directly by humans.

---

### 54. Strong Action Authentication

Systems receiving autonomous transactions should authenticate the calling agent or workload.

Appropriate mechanisms may include:

* mutual TLS;
* signed tokens;
* workload identity;
* short-lived credentials;
* certificate-based authentication.

Authentication should establish the identity of the caller without automatically granting transaction authority.

---

### 55. Fine-Grained Transaction Authorization

Authorization should evaluate the specific transaction rather than merely whether the agent has access to a system.

```text
Agent
+
Function
+
Resource
+
Parameters
+
Transaction
+
Context
   ↓
Authorization Decision
```

This prevents broad application access from becoming unrestricted transaction authority.

---

### 56. Independent Transaction Authorization Service

High-impact autonomous transactions should be evaluated by an authorization component independent of the agent.

```text
Agent
  │
  ├── Proposes Transaction
  │
  ▼
Authorization Service
  │
  ├── Policy
  ├── Identity
  ├── Limits
  ├── Risk
  └── Context
  │
  ▼
ALLOW / DENY
```

The agent must not be the final authority over its own transaction.

---

### 57. Transaction Allowlisting

Only explicitly approved transaction types should be available to autonomous execution.

Example:

```text
Approved:
CREATE_REFUND       ✓
UPDATE_ORDER        ✓
SEND_NOTIFICATION   ✓

Not Approved:
DELETE_ACCOUNT      ✗
CHANGE_ADMIN_ROLE   ✗
TRANSFER_FUNDS      ✗
```

Allowlisting reduces the autonomous action surface.

---

### 58. Action Allowlisting

Individual actions should also be constrained.

An agent authorized to process orders, for example, should not automatically receive authority to modify pricing, customer permissions, or financial settlement.

---

### 59. Tool Allowlisting

Agents should only access tools explicitly approved for their operating role.

```text
Agent
 ├── CRM Read API       ✓
 ├── Order Update API   ✓
 ├── Payment API        → Restricted
 └── Infrastructure API ✗
```

Tool access should be evaluated independently from model instructions.

---

### 60. Tool Capability Segmentation

Individual capabilities within a tool should be separated.

```text
Order API
 ├── READ       → Allowed
 ├── UPDATE     → Allowed
 ├── CANCEL     → Restricted
 └── DELETE     → Denied
```

This limits the effect of compromised or misbehaving agents.

---

### 61. Transaction Parameter Validation

Transaction parameters should be validated before execution.

Validation may include:

* data type;
* allowed range;
* destination;
* quantity;
* amount;
* resource;
* timestamp;
* transaction state.

```text
Amount = €50,000
Allowed Maximum = €5,000

→ DENY
```

---

### 62. Transaction Schema Validation

The transaction structure itself should be validated against an approved schema.

Required controls may include:

* mandatory fields;
* permitted values;
* field length;
* enumerations;
* nested-object restrictions;
* prohibited fields.

Malformed or unexpected transactions should fail closed.

---

### 63. Transaction Limits

Explicit limits should constrain autonomous activity.

Limits can apply to:

* transaction amount;
* quantity;
* affected records;
* execution frequency;
* resource consumption;
* cumulative value.

---

### 64. Cumulative Transaction Limits

Security controls should evaluate aggregate activity.

```text
Transaction 1 → €500
Transaction 2 → €500
Transaction 3 → €500
...
Daily Limit   → €2,000
```

A series of individually permitted transactions must not circumvent the overall risk limit.

---

### 65. Time-Bounded Transaction Authority

Transaction authority should expire after a defined period.

```text
Authority Granted
      ↓
Valid for 30 Minutes
      ↓
Transaction Execution
      ↓
Authority Expires
```

Time boundaries reduce the exposure created by persistent autonomous privileges.

---

### 66. Short-Lived Transaction Credentials

Where supported, autonomous systems should use credentials that automatically expire.

Short-lived credentials reduce the usefulness of stolen credentials and limit prolonged unauthorized execution.

---

### 67. Credential Isolation

Credentials used for autonomous transactions should be isolated by:

* agent;
* application;
* environment;
* transaction type;
* privilege level.

Shared privileged credentials make attribution and containment significantly more difficult.

---

### 68. Secrets Management

Secrets should be stored and retrieved through approved enterprise secrets-management mechanisms.

Agents should not receive unrestricted access to:

* passwords;
* API keys;
* private keys;
* database credentials;
* service-account secrets.

The agent should receive only the credential required for the authorized transaction.

---

### 69. Transaction Context Security Controls

Transaction context should be protected against manipulation.

Security-critical context should come from authoritative systems rather than from model-generated claims.

```text
Model Context
     ≠
Security Context
```

For example, an agent stating that a transaction has been approved should not constitute proof of approval.

---

### 70. Prompt and Instruction Integrity

Instructions that influence autonomous actions should be protected from unauthorized modification.

Security controls should distinguish:

```text
Trusted Policy
     ↓
System Instruction
     ↓
Agent Reasoning
     ↓
Untrusted Content
```

Lower-trust content must not override higher-authority transaction controls.

---

### 71. Untrusted Input Isolation

External content should be isolated from transaction authorization decisions.

Potentially untrusted inputs include:

* emails;
* documents;
* web pages;
* customer messages;
* tool results;
* retrieved data.

Such content may influence reasoning but should not directly grant transaction authority.

---

### 72. Prompt Injection Detection

Prompt injection defenses should identify attempts to manipulate an agent into performing unauthorized actions.

Examples include instructions attempting to:

* bypass approval;
* increase transaction limits;
* change recipients;
* disclose credentials;
* execute prohibited operations.

Detection should complement, not replace, independent authorization.

---

### 73. Memory Isolation

Agent memory should not automatically become a source of transaction authority.

A memory entry such as:

```text
"Finance manager approved unlimited payments."
```

must not be treated as authoritative authorization.

Transaction permissions should come from trusted authorization systems.

---

### 74. Memory Authorization

Access to memory should itself be controlled.

Agents should only access memory relevant to their authorized business purpose.

Sensitive transaction information should receive additional restrictions.

---

### 75. Memory Integrity

Security-sensitive transaction information stored in memory should be protected against unauthorized modification.

Integrity controls may include:

* access restrictions;
* cryptographic integrity;
* provenance;
* versioning;
* tamper detection.

---

### 76. Persistent Transaction Context Controls

Persistent context should not silently expand future transaction authority.

For example:

```text
Previous Approval
      ≠
Permanent Approval
```

Approvals and transaction permissions should have explicit validity periods and scopes.

---

### 77. Data Access Authorization

Before a transaction uses sensitive data, data access must be independently authorized.

An agent should not be permitted to retrieve additional information merely because it believes the information is useful for completing a transaction.

---

### 78. Data Minimization

Only data necessary for the transaction should be exposed to the agent.

```text
Required Data
     ↓
Minimum Dataset
     ↓
Transaction
```

Data minimization reduces both privacy risk and the potential impact of agent compromise.

---

### 79. Field-Level Data Protection

Sensitive fields should receive granular protection.

For example:

```text
Customer Record
 ├── Name        → Read
 ├── Address     → Read
 ├── Account ID  → Read
 ├── Bank Data   → Restricted
 └── Credentials → Denied
```

Transaction authorization should not automatically provide access to every field.

---

### 80. Tenant Isolation

Multi-tenant systems must prevent an autonomous transaction for one tenant from affecting another.

```text
Agent
 ├── Tenant A → Authorized
 ├── Tenant B → Denied
 └── Tenant C → Denied
```

Tenant identity should be independently verified.

---

### 81. Session Isolation

Transaction execution should be associated with an appropriate session boundary.

A session compromise should not automatically expose transactions belonging to unrelated sessions.

---

### 82. Network Segmentation

Autonomous transaction systems should be segmented according to risk.

```text
Agent Network
      ↓
Security Gateway
      ↓
Transaction Zone
      ↓
Protected Business System
```

High-impact transaction services should not be directly reachable from unrestricted agent environments.

---

### 83. Egress Controls

Outbound autonomous transactions should be restricted to approved destinations.

Examples include:

* approved payment endpoints;
* approved SaaS services;
* approved APIs;
* approved communication platforms.

```text
Approved Destination → ALLOW
Unknown Destination  → DENY
```

---

### 84. External Communication Controls

Autonomous agents capable of sending messages should have controls over:

* recipients;
* message types;
* attachments;
* data classification;
* sending frequency;
* external domains.

This prevents transaction-like actions from being hidden inside communications.

---

### 85. Code Execution Isolation

If an agent can execute code as part of a transaction, execution should be isolated.

Controls may include:

* sandboxing;
* container isolation;
* restricted filesystem access;
* restricted network access;
* resource limits;
* ephemeral environments.

---

### 86. Database Security Controls

Database transactions initiated by agents should use tightly scoped database privileges.

```text
Agent
 ↓
Database Policy
 ↓
Approved Schema / Table
 ↓
Approved Operation
```

Broad database administrator privileges should not be assigned to general-purpose agents.

---

### 87. Read/Write Separation

Read and write operations should be separately controlled.

```text
READ
 ↓
Lower Risk

WRITE
 ↓
Higher Risk

DELETE / ADMIN
 ↓
Critical Risk
```

Separating privileges makes it harder for a compromised agent to transition from observation to destructive action.

---

### 88. Human Approval Controls

Human approval should be required for transactions whose risk exceeds defined autonomous thresholds.

Approval requirements should be determined by policy rather than by the agent.

---

### 89. Action Preview

Before high-impact execution, the system should provide an accurate transaction preview.

The preview should show:

* action;
* target;
* amount;
* affected resources;
* destination;
* relevant data;
* expected effect.

---

### 90. Dual Authorization

Critical transactions should require two independent authorization decisions where appropriate.

```text
Transaction
    │
    ├── Authorization A
    │
    └── Authorization B
          ↓
        Execute
```

This reduces single-point authorization failure.

---

### 91. Reversibility Controls

Where possible, autonomous transactions should support rollback or compensation.

Examples include:

* database rollback;
* configuration restoration;
* payment cancellation;
* workflow reversal.

Irreversible operations should receive stronger controls.

---

### 92. Agent Execution Limits

Agents should have limits on:

* number of actions;
* execution duration;
* transaction volume;
* concurrent operations;
* resource consumption.

These limits reduce runaway execution.

---

### 93. Transaction Loop Detection

Security controls should identify repetitive autonomous transaction loops.

```text
Action A
 ↓
Action B
 ↓
Action A
 ↓
Action B
 ↓
...
```

Repeated cycles may indicate faulty logic, prompt manipulation, or compromised behavior.

---

### 94. Recursive Transaction Controls

Agents should not recursively generate unlimited transaction chains.

Controls should define:

* maximum recursion depth;
* maximum delegated actions;
* maximum transaction chain length;
* maximum cumulative impact.

---

### 95. Agent-to-Agent Transaction Authentication

When one agent requests another agent to execute a transaction, both agents should be authenticated.

```text
Agent A
   ↓
Authenticated Request
   ↓
Agent B
```

The identity of the requesting and executing agents must remain distinguishable.

---

### 96. Agent-to-Agent Transaction Integrity

Messages carrying transaction requests between agents should be protected against unauthorized modification.

Security controls should protect:

* transaction parameters;
* destination;
* amount;
* authority scope;
* expiration;
* request identity.

---

### 97. Delegated Transaction Authority Constraints

Delegation should not increase transaction authority.

```text
Agent A Authority
       ↓
Delegation
       ↓
Agent B Authority
       ↓
Equal or Reduced Scope
```

Agent B should not be able to execute a transaction that Agent A could not legitimately authorize.

---

### 98. Tool Result Validation

Tool results influencing transactions should be validated before being trusted.

Examples:

* returned prices;
* account balances;
* inventory levels;
* customer status;
* approval state.

A manipulated tool result could otherwise cause an unsafe transaction.

---

### 99. Output Validation Before Action

Model-generated transaction parameters should be validated before execution.

```text
Model Output
     ↓
Schema Validation
     ↓
Business Rules
     ↓
Security Policy
     ↓
Authorization
     ↓
Execution
```

The model output should never directly control a privileged transaction endpoint.

---

### 100. Business Rule Enforcement

Business rules should be enforced outside the model.

Examples:

```text
Refund ≤ Original Purchase
Payment Recipient = Approved Vendor
Discount ≤ Authorized Maximum
Production Change = Approved Window
```

The model may propose an action, but authoritative business systems should enforce these rules.

---

### 101. Resource Controls

Autonomous transactions should have explicit resource boundaries.

Controls may limit:

* CPU;
* memory;
* storage;
* API calls;
* database operations;
* cloud resources;
* affected records.

This protects availability and limits operational impact.

---

### 102. Rate Limiting

Rate limiting should restrict transaction frequency.

```text
100 Requests / Minute
        ↓
101st Request
        ↓
THROTTLE / DENY
```

Rate limits should be appropriate to the transaction's risk and business requirements.

---

### 103. Concurrency Controls

Agents should not execute excessive numbers of transactions simultaneously.

Concurrency controls prevent:

* resource exhaustion;
* race conditions;
* duplicate actions;
* uncontrolled transaction bursts.

---

### 104. Timeout Controls

Transactions should have explicit execution timeouts.

Long-running autonomous operations can otherwise consume resources or remain active after the original context has expired.

---

### 105. Retry Controls

Retries should be carefully bounded.

A secure retry mechanism should consider:

```text
Failure
 ↓
Determine Transaction State
 ↓
Is Retry Safe?
 ├── No → Stop
 └── Yes
       ↓
Bounded Retry
```

Retries should not convert transient failures into duplicate transactions.

---

### 106. Circuit Breakers

Circuit breakers should automatically stop transaction execution when abnormal conditions occur.

Triggers may include:

* excessive transaction failures;
* unusual transaction volume;
* repeated authorization failures;
* abnormal destinations;
* anomalous transaction values.

---

### 107. Emergency Transaction Controls

Emergency controls should provide immediate mechanisms to restrict autonomous transaction execution.

They may include:

* disable transaction type;
* suspend agent;
* revoke credentials;
* block destination;
* stop workflow;
* isolate execution environment.

---

### 108. Agent Kill Switch

The kill switch should provide a rapid mechanism to stop autonomous execution.

```text
Security Event
      ↓
Kill Switch
      ↓
Stop New Actions
      ↓
Terminate / Isolate Execution
      ↓
Revoke Authority
```

The mechanism should remain independent of the agent.

---

### 109. Credential Revocation

Compromised or suspicious transaction credentials should be rapidly revocable.

Revocation should propagate to:

* active sessions;
* delegated agents;
* tools;
* APIs;
* transaction services.

---

### 110. Agent Isolation

A compromised agent should be isolated without unnecessarily disrupting unrelated enterprise systems.

Isolation may restrict:

* network connectivity;
* tools;
* credentials;
* data access;
* transaction execution.

---

### 111. Behavioral Transaction Monitoring

Transaction behavior should be continuously monitored.

Indicators may include:

* unusual transaction values;
* abnormal frequency;
* unusual destinations;
* unexpected transaction sequences;
* unusual operating times;
* deviations from established patterns.

---

### 112. Agent Activity Logging

Every consequential autonomous action should generate an auditable record.

A transaction log should capture:

```text
Agent
User / Initiator
Transaction ID
Action
Target
Parameters
Authorization
Approval
Timestamp
Result
```

---

### 113. Tamper-Resistant Transaction Audit Logging

Security-sensitive transaction logs should be protected against unauthorized modification.

Controls may include:

* append-only storage;
* centralized logging;
* cryptographic integrity;
* restricted administrative access;
* immutable retention.

---

### 114. Autonomous Transaction Observability

Organizations should maintain visibility from agent intent through final transaction effect.

```text
Intent
 ↓
Decision
 ↓
Request
 ↓
Authorization
 ↓
Approval
 ↓
Execution
 ↓
Commit
 ↓
Business Effect
```

This enables accurate forensic reconstruction.

---

### 115. Transaction Risk Detection

Security monitoring should identify transactions whose risk exceeds expected boundaries.

Detection can combine:

* deterministic rules;
* transaction limits;
* behavioral analytics;
* identity signals;
* threat intelligence;
* contextual risk.

---

### 116. Secure Transaction Failure Handling

When a transaction cannot be safely completed, the system should fail closed where appropriate.

```text
Validation Failure
       ↓
Authorization Failure
       ↓
Execution Blocked
       ↓
State Recorded
       ↓
Investigation / Recovery
```

Failure should not silently result in unauthorized partial execution.

---

### 117. Core Engineering Principle

The core engineering principle is:

> **An autonomous action must never move directly from model decision to consequential execution.**

A secure transaction architecture inserts independent controls between intent and effect:

```text
Agent Intent
     ↓
Action Proposal
     ↓
Validation
     ↓
Risk Assessment
     ↓
Independent Authorization
     ↓
Human Approval if Required
     ↓
Bounded Execution
     ↓
Transaction Integrity Check
     ↓
Commit
     ↓
Monitoring
     ↓
Audit
```

The fundamental control objective is to ensure that **autonomy determines what may be proposed, while independently enforced security controls determine what may actually happen**.
