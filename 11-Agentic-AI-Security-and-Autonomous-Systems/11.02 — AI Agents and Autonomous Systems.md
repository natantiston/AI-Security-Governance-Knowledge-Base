# 11.02 — AI Agents and Autonomous Systems

## Part 1 — Foundations and Core Concepts

### 1. Definition of an AI Agent

An **AI agent** is a software system capable of pursuing a defined objective by:

* receiving information;
* interpreting context;
* reasoning about possible actions;
* planning tasks;
* selecting actions;
* invoking tools;
* observing results;
* adapting subsequent actions.

A conventional application generally follows predefined execution logic.

An agent can dynamically determine **what it should do next** within the boundaries established by its architecture and authorization model.

---

### 2. Definition of an Autonomous System

An autonomous system is a system capable of performing actions with limited or no direct human intervention after receiving an objective, trigger, or instruction.

A simplified model is:

```text
Input / Objective
       ↓
Perception
       ↓
Reasoning
       ↓
Planning
       ↓
Decision
       ↓
Action
       ↓
Observation
       ↓
Adaptation
       ↓
Next Action
```

Security becomes more complex because the system can continue acting after the original user interaction has ended.

---

### 3. AI Agent vs Autonomous System

The terms are related but should not automatically be treated as identical.

| Concept                   | Primary Characteristic                                                   |
| ------------------------- | ------------------------------------------------------------------------ |
| AI Model                  | Produces predictions or generated outputs                                |
| LLM Application           | Uses a model within an application workflow                              |
| AI Agent                  | Uses reasoning and tools to pursue an objective                          |
| Autonomous System         | Can execute activities with limited human intervention                   |
| Agentic Autonomous System | Combines AI reasoning, tools, persistent state, and autonomous execution |

An AI agent may have limited autonomy, while an autonomous system may operate with substantially broader authority.

---

### 4. The Fundamental Difference from Conventional Software

Traditional software generally follows:

```text
Input
 ↓
Predefined Logic
 ↓
Output
```

An agentic system may operate as:

```text
Objective
 ↓
Interpret
 ↓
Plan
 ↓
Select Action
 ↓
Execute
 ↓
Observe
 ↓
Replan
 ↓
Execute Again
```

The security challenge therefore extends beyond protecting the software itself.

Security must also control the **decisions and actions produced during execution**.

---

### 5. Agentic Behavior

Agentic behavior refers to the ability of a system to determine and execute a sequence of actions in pursuit of an objective.

Important characteristics include:

* goal orientation;
* planning;
* action selection;
* environmental observation;
* adaptation;
* persistence;
* tool usage;
* delegation;
* feedback processing.

The greater the system's ability to independently determine its next actions, the greater the need for explicit security boundaries.

---

### 6. Agency

Agency is the degree to which an AI system can independently influence its environment.

Agency can exist at different levels:

```text
Level 0
No Action
   ↓
Level 1
Recommendation
   ↓
Level 2
Human-Approved Action
   ↓
Level 3
Limited Autonomous Action
   ↓
Level 4
Multi-Step Autonomous Execution
   ↓
Level 5
Broad Autonomous Authority
```

Increasing agency should result in increasing security controls.

---

### 7. Autonomy

Autonomy represents how independently the system can perform actions without requiring human intervention.

Autonomy should not be treated as a binary property.

It can be evaluated across:

* decision autonomy;
* execution autonomy;
* duration;
* tool access;
* transaction authority;
* delegation;
* data access;
* environmental control.

An agent may be highly autonomous in planning but minimally autonomous in execution.

---

### 8. Degrees of Autonomy

A useful enterprise model is:

| Level | Description                                              |
| ----- | -------------------------------------------------------- |
| A0    | Human performs all actions                               |
| A1    | AI provides information                                  |
| A2    | AI recommends actions                                    |
| A3    | AI prepares actions for approval                         |
| A4    | AI performs limited approved actions                     |
| A5    | AI performs multi-step actions within defined boundaries |
| A6    | AI operates continuously within delegated authority      |

Higher levels require stronger authorization, monitoring, and emergency controls.

---

### 9. Agent Goals

An agent normally operates toward an objective or goal.

Goals may be:

* explicitly provided by a user;
* defined by an application;
* generated by an orchestration workflow;
* derived from business rules;
* delegated by another agent.

Security governance must distinguish between:

**What the agent is trying to accomplish** and **what the agent is actually authorized to do**.

A legitimate goal does not automatically authorize every action that might achieve that goal.

---

### 10. Goal vs Authority

For example:

```text
Goal:
"Resolve the customer's issue."

Possible Agent Actions:
 ├── Read customer record
 ├── Modify customer record
 ├── Issue refund
 ├── Change account configuration
 └── Contact external provider
```

The goal does not automatically authorize all five actions.

Each action requires independent authorization.

---

### 11. Agent Perception

Agents obtain information through various inputs.

These may include:

* user messages;
* application data;
* APIs;
* databases;
* documents;
* sensors;
* web content;
* tool responses;
* other agents;
* event streams.

Every input should be evaluated according to its trust level.

An agent should not automatically treat every observed input as a trusted instruction.

---

### 12. Agent Environment

An agent operates within an environment containing systems, data, users, tools, and external entities.

A simplified environment is:

```text
             ┌─────────────────────┐
             │       USER          │
             └──────────┬──────────┘
                        │
                        ▼
                 ┌────────────┐
                 │    AGENT   │
                 └─────┬──────┘
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
      Data           Tools          Other Agents
        │              │               │
        └──────────────┼───────────────┘
                       ▼
                Enterprise Systems
```

The environment defines the agent's potential attack surface.

---

### 13. Agent State

Agent state represents information maintained during execution.

State may include:

* current objective;
* task status;
* previous actions;
* tool results;
* intermediate reasoning artifacts;
* session information;
* workflow state;
* authorization context.

State can influence future actions and must therefore be protected.

---

### 14. Stateless Agents

A stateless agent does not retain meaningful information between independent executions.

Example:

```text
Request
 ↓
Agent
 ↓
Response
 ↓
Session Ends
```

Stateless designs can reduce certain persistence risks because compromised information may not survive beyond the execution context.

However, stateless does not mean secure by default.

---

### 15. Stateful Agents

A stateful agent maintains information across execution steps or sessions.

```text
Session 1
   ↓
State
   ↓
Session 2
   ↓
State Updated
   ↓
Session 3
```

State persistence introduces additional security requirements around:

* integrity;
* authorization;
* retention;
* isolation;
* provenance;
* deletion.

---

### 16. Agent Memory

Agent memory is persistent or semi-persistent information used to improve future decisions or maintain continuity.

Memory may contain:

* user preferences;
* historical interactions;
* task state;
* retrieved information;
* business information;
* operational data.

Because memory can influence future behavior, it should be treated as a security-sensitive component.

---

### 17. Agent Planning

Planning allows an agent to decompose a goal into multiple actions.

For example:

```text
Goal:
Prepare customer report

Plan:
  1. Retrieve customer data
  2. Analyze transactions
  3. Identify anomalies
  4. Generate report
  5. Store report
  6. Notify authorized user
```

Every step potentially introduces a new security decision.

A secure architecture should not authorize the entire plan merely because the initial objective was approved.

---

### 18. Dynamic Planning

Agent plans may change during execution.

```text
Initial Plan
     ↓
Action 1
     ↓
Observation
     ↓
New Information
     ↓
Revised Plan
     ↓
Action 2
```

This creates a significant security consideration:

> Authorization must remain valid when the agent changes its plan.

A plan that was safe initially may become unsafe after new information is introduced.

---

### 19. Agent Execution Loop

Many agents operate through an iterative execution loop.

```text
┌──────────────────────┐
│      Objective       │
└──────────┬───────────┘
           ↓
      Reason / Plan
           ↓
       Select Tool
           ↓
        Execute
           ↓
      Observe Result
           ↓
      Evaluate State
           │
      ┌────┴────┐
      │ Continue│
      └────┬────┘
           ↓
      Next Action
```

Security controls must apply to each significant execution cycle.

---

### 20. Agent Action

An agent action is an operation that changes or interacts with its environment.

Examples include:

* reading data;
* writing data;
* sending messages;
* invoking APIs;
* executing code;
* modifying configuration;
* creating records;
* deleting resources;
* initiating transactions.

Actions should be classified according to impact and privilege.

---

### 21. Read vs Write Actions

Read and write operations have different risk characteristics.

```text
READ
 ↓
Observe Information

WRITE
 ↓
Change Information

DELETE
 ↓
Destroy Information

TRANSACTION
 ↓
Create External Consequence
```

Security controls should become progressively stronger as the potential impact increases.

---

### 22. Reversible vs Irreversible Actions

Action reversibility is a major security factor.

| Action                       | Typical Risk  |
| ---------------------------- | ------------- |
| Read data                    | Lower         |
| Create draft                 | Low–Moderate  |
| Modify record                | Moderate      |
| Send external message        | Moderate–High |
| Financial transaction        | High          |
| Delete production resource   | Very High     |
| Irreversible external action | Critical      |

Irreversible actions should generally require stronger authorization and oversight.

---

### 23. Agent Tools

Tools provide an agent with capabilities beyond language generation.

Examples include:

* search;
* database queries;
* APIs;
* ticketing systems;
* email;
* cloud management;
* code execution;
* financial systems;
* identity systems.

A tool therefore represents an extension of the agent's operational authority.

---

### 24. Tool Capability

A tool may expose multiple capabilities.

For example:

```text
CRM Tool
 ├── customer.read
 ├── customer.create
 ├── customer.update
 └── customer.delete
```

The agent should not automatically receive every capability exposed by the tool.

Tool capabilities should be independently controlled.

---

### 25. Agent Tool Chain

An agent may use multiple tools sequentially.

```text
Agent
 ↓
Search Tool
 ↓
Database Tool
 ↓
Analysis Tool
 ↓
CRM Tool
 ↓
Notification Tool
```

The cumulative security impact of the chain may be substantially greater than the risk of any individual tool.

---

### 26. Tool Chaining

Tool chaining allows the output of one operation to influence another operation.

Example:

```text
Search
 ↓
Retrieve Data
 ↓
Analyze
 ↓
Generate Decision
 ↓
Modify System
```

An attacker who manipulates an early stage may influence later actions.

Therefore, security validation should exist between consequential stages.

---

### 27. Agent-to-Agent Interaction

Agents may communicate with other agents to distribute work.

```text
User
 ↓
Agent A
 ├──→ Agent B
 │      └──→ Agent C
 │
 └──→ Agent D
```

This introduces additional risks:

* impersonation;
* unauthorized delegation;
* malicious instructions;
* privilege inheritance;
* data leakage;
* cascading failures.

Agent-to-agent relationships therefore require explicit trust boundaries.

---

### 28. Delegation

Delegation occurs when one agent requests another agent to perform a task.

Delegation should preserve:

* identity;
* purpose;
* authority boundaries;
* accountability;
* scope;
* expiration.

An agent should not be able to delegate unlimited authority simply because it possesses greater authority itself.

---

### 29. Agent Identity

Every production agent should have a unique identity.

Identity enables:

* authentication;
* authorization;
* auditing;
* attribution;
* monitoring;
* incident response;
* lifecycle management.

Without a reliable identity, security teams cannot confidently determine which agent performed an action.

---

### 30. Agent Identity vs Human Identity

Agent identity should not be confused with the identity of the human who initiated the workflow.

A useful attribution chain is:

```text
Human User
     ↓
Application
     ↓
Agent Identity
     ↓
Tool Identity
     ↓
Target Resource
```

This allows security teams to answer both:

**Who initiated the activity?**

and

**Which autonomous component actually performed it?**

---

### 31. Agent Authentication

Authentication establishes confidence that an agent is the identity it claims to be.

Potential mechanisms include:

* workload identity;
* certificates;
* mutual TLS;
* signed tokens;
* cloud workload credentials;
* attestation mechanisms.

Authentication should occur independently of the model's textual claims.

---

### 32. Agent Authorization

Authorization determines what an authenticated agent is permitted to do.

A secure decision may consider:

```text
Agent Identity
+
Human Initiator
+
Action
+
Resource
+
Business Purpose
+
Data Sensitivity
+
Transaction Value
+
Context
=
Authorization Decision
```

The model should not make this authorization decision by itself.

---

### 33. Agent Permissions

Agent permissions define the specific resources and actions available to an agent.

Permissions should be:

* explicit;
* limited;
* reviewable;
* revocable;
* attributable;
* time-bounded where appropriate.

Permissions should not be broader than required for the agent's approved business purpose.

---

### 34. Least Privilege

Least privilege requires that an agent receive only the minimum authority necessary to perform its approved function.

This applies to:

* data;
* APIs;
* tools;
* credentials;
* networks;
* transactions;
* compute;
* delegation;
* autonomy.

Least privilege is particularly important because agents may execute multiple actions without continuous human intervention.

---

### 35. Agent Authority

Agent authority represents the actual security power available to the agent.

Authority should be understood as:

```text
Identity
+
Permissions
+
Credentials
+
Tool Access
+
Network Access
+
Transaction Authority
+
Delegation Authority
```

Technical capability alone does not establish authority.

---

### 36. Agent Autonomy Boundary

An autonomy boundary defines what an agent may do without additional approval.

Example:

```text
Agent
 │
 ├── Read approved data → Autonomous
 │
 ├── Create draft → Autonomous
 │
 ├── Modify customer record → Conditional
 │
 ├── Issue refund → Human Approval
 │
 └── Delete account → Prohibited
```

The boundary should be explicitly defined and technically enforced.

---

### 37. Human-in-the-Loop

Human-in-the-loop means a human participates directly in a decision or action before execution.

This may be required for:

* high-value transactions;
* sensitive data disclosure;
* destructive actions;
* legal decisions;
* security-policy changes;
* privileged operations.

Human involvement should be meaningful rather than merely ceremonial.

---

### 38. Human-on-the-Loop

Human-on-the-loop means the agent operates autonomously while humans supervise activity and can intervene.

This model may be appropriate for lower-risk workflows.

```text
Agent
 ↓
Autonomous Execution
 ↓
Monitoring
 ↓
Human Intervention When Required
```

The organization must ensure that humans can actually detect and interrupt unsafe behavior.

---

### 39. Human Approval Boundary

Approval requirements should be tied to action risk rather than simply to the existence of an agent.

Factors may include:

* financial impact;
* data sensitivity;
* privilege;
* reversibility;
* regulatory impact;
* external consequences;
* uncertainty.

The higher the impact, the stronger the approval requirement should generally be.

---

### 40. Agent Failure Modes

Agent failures can occur at multiple layers.

Examples include:

* incorrect reasoning;
* incorrect planning;
* tool failure;
* authorization failure;
* corrupted state;
* malicious input;
* excessive execution;
* unexpected delegation;
* infrastructure failure.

Security architecture must assume that agent behavior can fail without malicious intent.

---

### 41. Unsafe Autonomous Behavior

An agent may behave unsafely even when there is no attacker.

Examples include:

* executing an incorrect plan;
* repeatedly invoking a tool;
* misunderstanding a business rule;
* modifying the wrong record;
* sending excessive communications;
* consuming excessive resources.

Security controls should therefore protect against both malicious and accidental autonomous behavior.

---

### 42. Runaway Agent Behavior

A runaway agent continues performing actions without achieving a valid stopping condition.

Example:

```text
Action
 ↓
Unexpected Result
 ↓
Replan
 ↓
Action
 ↓
Unexpected Result
 ↓
Replan
 ↓
Action
 ↓
...
```

Potential consequences include:

* resource exhaustion;
* excessive API usage;
* repeated transactions;
* data modification;
* communication flooding.

Execution limits and circuit breakers are therefore essential.

---

### 43. Agent Persistence

Persistence determines how long an agent remains capable of acting.

Persistence can exist across:

* requests;
* sessions;
* days;
* workflows;
* system restarts.

Greater persistence increases the potential impact of compromised state or credentials.

---

### 44. Continuous Operation

Some autonomous agents may operate continuously.

```text
Monitor
 ↓
Detect Event
 ↓
Analyze
 ↓
Act
 ↓
Monitor Again
```

Continuous operation creates additional security requirements around:

* credential lifetime;
* monitoring;
* resource limits;
* state management;
* emergency shutdown;
* periodic reauthorization.

---

### 45. Agent Context

Agent context includes information available to the agent when making decisions.

Context may contain:

* system instructions;
* user instructions;
* retrieved information;
* memory;
* tool results;
* policies;
* application state;
* messages from other agents.

Context should be treated as a security boundary because manipulated context can influence subsequent actions.

---

### 46. Trusted and Untrusted Context

Not all context should receive the same trust level.

```text
Trusted
 ├── Security Policy
 ├── Authorization Decision
 └── Verified System Configuration

Controlled
 ├── Approved Enterprise Data
 └── Authorized Memory

Untrusted
 ├── User Input
 ├── External Web Content
 ├── Tool Results
 └── Unknown Agent Messages
```

Trust classification should influence how context is processed.

---

### 47. Agent Objective Manipulation

An attacker may attempt to alter what an agent believes its objective is.

Potential mechanisms include:

* prompt injection;
* malicious documents;
* manipulated tool results;
* poisoned memory;
* compromised upstream agents;
* malicious external content.

Objective integrity should therefore be protected.

---

### 48. Agent Hijacking

Agent hijacking occurs when an attacker gains influence over an agent's behavior or execution.

The attacker may attempt to:

* redirect the objective;
* alter instructions;
* invoke unauthorized tools;
* access sensitive data;
* modify memory;
* perform unauthorized transactions.

The impact depends heavily on the authority available to the compromised agent.

---

### 49. Autonomous Systems as Security Subjects

An autonomous agent should be treated as an identifiable security subject rather than simply as a software process.

It has:

* identity;
* authority;
* permissions;
* responsibilities;
* operational state;
* security events;
* lifecycle;
* risk.

This enables traditional security concepts such as IAM, Zero Trust, least privilege, monitoring, and incident response to be applied to autonomous systems.

---

### 50. Core Principle of AI Agents and Autonomous Systems

The foundational security principle is:

> **An agent may reason autonomously, but its authority must remain explicitly defined, independently authorized, bounded, observable, and interruptible.**

The architecture must preserve the distinction between:

```text
What the Agent Can Conceptually Do
                ≠
What the Agent Is Technically Capable of Doing
                ≠
What the Agent Is Authorized to Do
                ≠
What the Agent Is Permitted to Execute Autonomously
```

This distinction forms the foundation for securely governing increasingly autonomous AI systems.

## Part 2 — Technical Security and Control Mechanisms

### 51. AI Agent Security Control Architecture

AI agent security controls should be implemented across the complete agent execution path.

```text
User / Event
     ↓
Application
     ↓
Agent Identity
     ↓
Authentication
     ↓
Policy / Authorization
     ↓
Agent Runtime
     ↓
Context / Memory
     ↓
Tool Authorization
     ↓
Tool Execution
     ↓
Enterprise Resource
     ↓
Monitoring / Audit
```

Security controls should not exist exclusively inside the agent runtime.

---

### 52. Agent Identity Control

Every production agent should receive a unique machine identity.

The identity should support:

* authentication;
* authorization;
* logging;
* attribution;
* access reviews;
* lifecycle management;
* incident response.

Example:

```text
Agent: Finance-Reconciliation-01
Owner: Finance Operations
Environment: Production
Identity: workload://finance/reconciliation/01
Risk Tier: High
```

---

### 53. Workload Identity

Agent identity should preferably integrate with enterprise workload identity systems.

Possible mechanisms include:

* cloud workload identity;
* service identities;
* certificates;
* SPIFFE-style identities;
* managed service principals;
* workload attestation.

This avoids treating an agent as an anonymous application component.

---

### 54. Strong Agent Authentication

High-risk agents should use strong authentication mechanisms.

Controls may include:

* mutual TLS;
* certificate authentication;
* signed tokens;
* workload attestation;
* short-lived credentials;
* cryptographic identity.

Authentication should establish the identity of the executing agent independently from its generated text.

---

### 55. Fine-Grained Agent Authorization

Authorization should evaluate the complete security context.

```text
Agent Identity
+
Human Initiator
+
Application
+
Action
+
Target Resource
+
Business Purpose
+
Data Sensitivity
+
Transaction Value
+
Environment
+
Risk
=
Authorization Decision
```

Authorization should occur before consequential actions.

---

### 56. Independent Authorization

The agent should not authorize itself.

The security architecture should separate:

```text
AI Decision
     ↓
Requested Action
     ↓
Independent Policy Engine
     ↓
ALLOW / DENY / APPROVAL
     ↓
Execution
```

The model's confidence, reasoning, or generated statement should never substitute for an enterprise authorization decision.

---

### 57. Least-Privilege Agent Permissions

Agents should receive only the permissions necessary for their approved purpose.

Least privilege should apply to:

* APIs;
* databases;
* files;
* cloud resources;
* tools;
* credentials;
* network destinations;
* transactions;
* delegation.

Permissions should be reviewed periodically and removed when no longer required.

---

### 58. Capability Allowlisting

Agent capabilities should be explicitly allowlisted.

Example:

```text
Customer Support Agent

Allowed:
 ├── customer.read
 ├── ticket.read
 └── ticket.create

Denied:
 ├── customer.delete
 ├── payment.execute
 └── iam.modify
```

An allowlist provides a stronger boundary than relying on the agent to voluntarily avoid dangerous capabilities.

---

### 59. Tool Allowlisting

Only approved tools should be exposed to an agent.

Tool approval should consider:

* business purpose;
* privilege;
* data access;
* external connectivity;
* transaction capability;
* risk;
* reversibility.

Adding a new tool should trigger security reassessment where it changes the agent's authority.

---

### 60. Tool Capability Segmentation

Tools should expose only the capabilities required by the specific agent.

Instead of:

```text
CRM API
 └── Full Access
```

use:

```text
CRM API
 ├── Customer Read
 ├── Customer Update
 ├── Customer Delete
 └── Administrative Access

Agent
 └── Customer Read
```

Segmentation reduces the impact of agent compromise.

---

### 61. Tool Argument Validation

Tool parameters should be validated independently of the AI model.

Validation should examine:

* parameter type;
* permitted values;
* resource scope;
* transaction limits;
* destination;
* data classification;
* business rules.

Example:

```text
Agent:
refund(customer=123, amount=50000)

Policy:
Maximum autonomous refund = €500

Result:
DENY
```

---

### 62. Action Allowlisting

Security policies should define permitted actions explicitly.

For example:

```text
Agent
 ├── read_customer → ALLOW
 ├── create_ticket → ALLOW
 ├── issue_refund → APPROVAL
 ├── delete_customer → DENY
 └── modify_iam → DENY
```

This creates an enforceable boundary around autonomous behavior.

---

### 63. Transaction Limits

Agents capable of transactions should have explicit limits.

Limits may apply to:

* individual transaction value;
* daily value;
* transaction frequency;
* cumulative exposure;
* destination;
* account;
* resource.

Limits should be enforced by the transaction-control layer rather than by the model.

---

### 64. Cumulative Action Limits

Individual actions may appear harmless while their cumulative effect becomes dangerous.

Example:

```text
€400 × 20 transactions = €8,000
```

Therefore, controls should monitor cumulative activity across:

* sessions;
* users;
* agents;
* accounts;
* time windows.

---

### 65. Time-Bounded Agent Authority

Agent authority should expire after a defined period where practical.

```text
Authorization
     ↓
Valid for 30 minutes
     ↓
Execution
     ↓
Expiration
     ↓
New Authorization Required
```

Time-bounded authority reduces the opportunity for persistent misuse.

---

### 66. Short-Lived Credentials

Agent credentials should have limited lifetimes.

Short-lived credentials reduce:

* credential theft exposure;
* persistence;
* unauthorized reuse;
* blast radius.

Credential lifetime should correspond to the operational risk of the agent.

---

### 67. Credential Isolation

Credentials should be isolated by:

* agent;
* environment;
* application;
* business function;
* tenant.

A compromised development agent should not possess credentials capable of accessing production systems.

---

### 68. Secrets Management

Agent secrets should be managed through approved enterprise secrets-management mechanisms.

Secrets should not be stored directly in:

* prompts;
* system instructions;
* memory;
* source code;
* logs;
* tool descriptions;
* configuration files.

Agents should receive secrets only when required and for the minimum necessary duration.

---

### 69. Context Security

Agent context should be separated according to trust and authority.

```text
Trusted Policy
     ↓
System Configuration
     ↓
Authorized Business Context
     ↓
Approved Memory
     ↓
User Input
     ↓
External Content
     ↓
Tool Results
     ↓
Other-Agent Messages
```

Lower-trust content must not automatically override higher-trust security instructions.

---

### 70. Prompt and Instruction Integrity

Critical agent instructions should be protected against unauthorized modification.

Controls may include:

* version control;
* access control;
* signed configuration;
* change approval;
* integrity monitoring;
* deployment validation.

A prompt or instruction change that increases authority should be treated as a security-relevant change.

---

### 71. Untrusted Input Isolation

Untrusted content should be isolated from privileged instructions.

Examples include:

* external web pages;
* uploaded documents;
* emails;
* user-provided files;
* third-party API responses;
* unknown agent messages.

The architecture should prevent untrusted content from becoming an implicit command to privileged tools.

---

### 72. Prompt Injection Detection

Agent environments should implement protections against prompt injection.

Controls may include:

* input classification;
* content isolation;
* instruction hierarchy;
* policy enforcement;
* tool authorization;
* output validation;
* behavioral detection.

Prompt injection defense should not rely solely on asking the model to ignore malicious instructions.

---

### 73. Memory Isolation

Agent memory should be logically isolated.

Isolation may occur by:

* user;
* tenant;
* application;
* agent;
* session;
* business process.

Example:

```text
Tenant A
 └── Agent Memory A

Tenant B
 └── Agent Memory B
```

Cross-tenant memory access should be explicitly prohibited unless authorized.

---

### 74. Memory Authorization

Memory access should be subject to authorization controls.

Authorization should consider:

* agent identity;
* user identity;
* tenant;
* data classification;
* purpose;
* operation.

Reading memory should not automatically imply permission to modify it.

---

### 75. Memory Integrity

Security-sensitive memory should have integrity protections.

Possible controls include:

* provenance metadata;
* versioning;
* access logging;
* integrity checks;
* controlled updates;
* anomaly detection.

Memory poisoning should be treated as a potential security incident.

---

### 76. Persistent Context Controls

Persistent context should have explicit lifecycle controls.

These include:

* creation;
* validation;
* authorization;
* retention;
* modification;
* review;
* deletion.

Persistent context should not become an uncontrolled secondary database of enterprise information.

---

### 77. Data Access Authorization

Agents should use the enterprise authorization model when accessing data.

The agent should not receive broad access simply because the model can technically formulate a query.

```text
Agent
 ↓
Data Request
 ↓
Identity
 ↓
Authorization
 ↓
Resource Policy
 ↓
ALLOW / DENY
 ↓
Data
```

---

### 78. Data Minimization

Agents should receive only the data necessary for the task.

Instead of:

```text
Agent → Entire Customer Database
```

prefer:

```text
Agent → Required Customer Fields
```

Data minimization reduces both accidental disclosure and attack impact.

---

### 79. Field-Level Data Protection

Sensitive fields should be protected individually where appropriate.

For example:

```text
Customer Record

Name       → ALLOW
Email      → ALLOW
Phone      → CONDITIONAL
Payment ID → RESTRICTED
Password   → DENY
```

Field-level authorization can significantly reduce agent exposure.

---

### 80. Tenant Isolation

Multi-tenant agent systems require strong tenant isolation.

Controls should ensure:

```text
Tenant A Agent
      ↓
Tenant A Data

Tenant B Agent
      ↓
Tenant B Data
```

An agent compromise must not become a cross-tenant compromise.

---

### 81. Session Isolation

Agent sessions should maintain appropriate security boundaries.

Session isolation should prevent:

* cross-user context leakage;
* unauthorized memory reuse;
* session confusion;
* credential reuse;
* unintended task inheritance.

A new session should not automatically inherit sensitive context from another session.

---

### 82. Network Segmentation

Agent infrastructure should be segmented according to risk.

Example:

```text
Agent Zone
    │
    ├── Approved API Zone
    │
    ├── Data Access Zone
    │
    └── Restricted Enterprise Zone
```

High-risk agents should not receive unrestricted access to the enterprise network.

---

### 83. Egress Controls

Outbound agent communication should be controlled.

Controls should define:

* permitted destinations;
* ports;
* protocols;
* domains;
* data-transfer rules;
* bandwidth;
* rate limits.

Unexpected external connections should be detectable and, where appropriate, blocked.

---

### 84. External Communication Controls

Agents capable of email, messaging, web access, or external APIs require additional controls.

Policies may restrict:

* recipients;
* domains;
* attachment types;
* sensitive data;
* message frequency;
* external destinations.

External communication can convert an internal agent compromise into data exfiltration or reputational damage.

---

### 85. Code Execution Isolation

Agents capable of executing code should use sandboxed environments.

Controls may include:

* isolated containers;
* restricted system calls;
* ephemeral execution environments;
* filesystem restrictions;
* network restrictions;
* resource quotas;
* execution time limits.

Agent-generated code should never automatically inherit the privileges of the host system.

---

### 86. Database Security Controls

Database access should use standard database security principles.

Controls include:

* separate service identities;
* role-based permissions;
* read/write separation;
* row-level security;
* field-level security;
* query restrictions;
* audit logging.

Agent access should remain subordinate to database security policies.

---

### 87. Read/Write Separation

Where practical, read and write operations should use separate security paths.

```text
Agent
 ├── Read Path
 │      └── Read Replica / Read Role
 │
 └── Write Path
        └── Controlled Write API
                 ↓
            Authorization
                 ↓
              Execute
```

This prevents a broad read privilege from becoming unrestricted modification authority.

---

### 88. Human Approval Controls

Human approval should be technically enforced for designated high-risk actions.

Approval requirements may apply to:

* financial transactions;
* destructive operations;
* privileged access changes;
* sensitive data disclosure;
* legally significant actions.

The approval mechanism should be independent of the agent.

---

### 89. Action Preview

Before high-impact execution, the system should present the proposed action for review.

A preview should show:

* action;
* target;
* parameters;
* expected impact;
* data involved;
* transaction value;
* agent identity;
* reason.

This enables the human reviewer to understand what the agent is actually attempting to do.

---

### 90. Dual Authorization

Critical actions may require two independent authorization decisions.

```text
Agent Request
      ↓
Policy Validation
      ↓
Approver 1
      ↓
Approver 2
      ↓
Execution
```

This provides stronger segregation of duties for high-impact operations.

---

### 91. Reversibility Controls

Where possible, agent actions should be reversible.

Examples include:

* soft delete;
* transaction cancellation;
* rollback;
* version restoration;
* staged deployment;
* draft-before-send.

Reversibility reduces the impact of incorrect autonomous decisions.

---

### 92. Agent Execution Limits

Execution limits should constrain autonomous activity.

Limits may include:

* maximum steps;
* maximum runtime;
* maximum tool calls;
* maximum transactions;
* maximum resource consumption;
* maximum delegation depth.

Example:

```text
Maximum:
100 steps
20 tool calls
30 minutes
€1,000 cumulative transaction value
```

---

### 93. Loop Detection

The runtime should detect repetitive or circular behavior.

Potential indicators include:

* repeated identical tool calls;
* recurring state transitions;
* repeated failed actions;
* recursive delegation;
* excessive retries.

When detected, the system should pause or terminate execution.

---

### 94. Recursive Delegation Controls

Agents should have limits on how deeply they can delegate.

```text
Agent A
 ↓
Agent B
 ↓
Agent C
 ↓
Agent D
 ↓
DENY
```

Delegation depth limits reduce cascading behavior and make accountability easier to maintain.

---

### 95. Agent-to-Agent Authentication

Agents communicating with one another should authenticate their identities.

The receiving agent should establish:

* who sent the request;
* whether that identity is trusted;
* whether the communication channel is protected.

Agent names or natural-language claims should not establish identity.

---

### 96. Agent-to-Agent Message Integrity

Messages between agents should have integrity protection.

Controls may include:

* authenticated channels;
* signed messages;
* message identifiers;
* timestamps;
* replay protection.

This reduces the risk of forged or modified instructions.

---

### 97. Delegated Authority Constraints

Delegated authority should be explicitly scoped.

For example:

```text
Agent A Authority:
customer.read + ticket.update

Delegation to Agent B:
customer.read ONLY

Agent B:
Cannot delegate ticket.update
```

Delegation should never silently expand authority.

---

### 98. Tool Result Validation

Tool results should be treated as potentially untrusted data.

A tool result should not automatically become an instruction.

```text
Tool Result
     ↓
Parse
     ↓
Validate
     ↓
Classify
     ↓
Agent Context
```

This is particularly important when tools consume external or user-controlled information.

---

### 99. Output Validation Before Action

Agent-generated outputs should be validated before they trigger consequential operations.

Validation may include:

* schema validation;
* authorization;
* business rules;
* parameter validation;
* risk scoring;
* destination validation.

The architecture should prevent raw model output from directly executing privileged actions.

---

### 100. Business Rule Enforcement

Critical business rules should exist outside the model.

Example:

```text
Model:
"Customer should receive €10,000 refund."

Business Rule Engine:
Maximum autonomous refund = €500

Result:
REJECT / REQUIRE APPROVAL
```

Business rules should be deterministic and independently enforceable.

---

### 101. Resource Controls

Agents should have limits on compute and infrastructure resources.

Controls may cover:

* CPU;
* memory;
* storage;
* API consumption;
* network bandwidth;
* execution time.

Resource controls help prevent denial-of-service conditions caused by runaway agents.

---

### 102. Rate Limiting

Rate limits should apply to agent actions and tool calls.

Examples:

* API calls per minute;
* emails per hour;
* database queries;
* transactions per hour;
* external requests.

Rate limiting reduces both accidental and malicious excessive activity.

---

### 103. Concurrency Controls

Agents should have controlled limits on parallel execution.

```text
Agent
 ├── Task 1
 ├── Task 2
 ├── Task 3
 └── Task 4
       ↓
Maximum Concurrent Tasks = 2
```

Concurrency limits prevent an agent from multiplying its impact through uncontrolled parallel activity.

---

### 104. Timeout Controls

Each agent operation should have defined timeouts.

Timeouts should apply to:

* model calls;
* tools;
* APIs;
* database queries;
* external connections;
* complete agent workflows.

An operation that exceeds its security-relevant execution window should be terminated or escalated.

---

### 105. Retry Controls

Retries should be explicitly limited.

Poorly controlled retries can result in:

```text
Failure
 ↓
Retry
 ↓
Failure
 ↓
Retry
 ↓
Transaction
 ↓
Retry
 ↓
Duplicate Transaction
```

Sensitive operations should use idempotency controls where possible.

---

### 106. Circuit Breakers

Circuit breakers should automatically stop or restrict agents when abnormal behavior is detected.

Potential triggers include:

* repeated failures;
* authorization violations;
* excessive tool usage;
* abnormal transaction volume;
* unusual destinations;
* recursive execution.

Circuit breakers provide an automated containment mechanism.

---

### 107. Emergency Agent Controls

Emergency controls should provide security teams with immediate intervention capability.

Possible controls include:

* suspend agent;
* revoke credentials;
* disable tools;
* block network access;
* terminate sessions;
* isolate runtime;
* prevent restart.

Emergency controls must remain operational even when the agent is malfunctioning.

---

### 108. Agent Kill Switch

A kill switch should immediately terminate autonomous activity.

```text
Security Operator
       ↓
KILL
       ↓
Agent Suspended
       ↓
Credentials Revoked
       ↓
Tools Disabled
       ↓
Sessions Terminated
```

The kill switch should not depend on the agent agreeing to stop.

---

### 109. Credential Revocation

When compromise is suspected, credentials should be revocable independently of the agent.

Revocation should cover:

* API tokens;
* certificates;
* service accounts;
* cloud credentials;
* database credentials;
* delegated credentials.

Rapid revocation reduces attacker dwell time.

---

### 110. Agent Isolation

A compromised agent should be capable of being isolated without necessarily shutting down unrelated enterprise services.

Isolation may include:

* runtime isolation;
* network quarantine;
* tool disablement;
* credential removal;
* memory isolation.

The objective is to contain the compromised autonomous component.

---

### 111. Behavioral Monitoring

Security monitoring should examine agent behavior rather than only infrastructure events.

Indicators may include:

* unusual tool usage;
* unexpected destinations;
* unusual data access;
* abnormal transaction patterns;
* excessive execution;
* unexpected delegation;
* repeated authorization failures.

Behavioral monitoring can identify attacks that traditional infrastructure monitoring may miss.

---

### 112. Agent Activity Logging

Agent activity should generate structured audit events.

A useful event should include:

```text
Timestamp
Human Initiator
Agent Identity
Session
Action
Tool
Target
Authorization Decision
Policy
Result
```

Logs should support forensic reconstruction.

---

### 113. Tamper-Resistant Audit Logging

Security-relevant agent logs should be protected against unauthorized modification.

Controls may include:

* centralized logging;
* access restrictions;
* immutable storage;
* cryptographic integrity;
* separation of duties.

The agent should not be able to delete evidence of its own activity.

---

### 114. Agent Security Observability

Observability should provide visibility across the complete agent workflow.

```text
User
 ↓
Application
 ↓
Agent
 ↓
Decision
 ↓
Authorization
 ↓
Tool
 ↓
Resource
 ↓
Result
 ↓
Next Decision
```

This enables security teams to reconstruct multi-step autonomous behavior.

---

### 115. Agent Risk Detection

Risk detection should combine static and dynamic signals.

Static signals:

* privilege;
* tools;
* data access;
* autonomy;
* network connectivity.

Dynamic signals:

* unusual behavior;
* failed authorization;
* abnormal tool usage;
* transaction anomalies;
* suspicious delegation.

Combining both provides stronger detection than either approach alone.

---

### 116. Secure Failure Handling

Agent systems should fail safely.

When authorization, identity, policy, or security validation cannot be established:

```text
Security Decision Unavailable
          ↓
Do Not Execute
          ↓
Restrict / Pause
          ↓
Alert
          ↓
Human Review
```

Security-critical uncertainty should result in restriction rather than autonomous continuation.

---

### 117. Core Engineering Principle

The central engineering principle is:

> **Never rely on the AI agent or underlying model to enforce the security properties of its own authority.**

The model may reason about an action, but independent security controls must determine whether the action is:

```text
Identified
     ↓
Authenticated
     ↓
Authorized
     ↓
Within Scope
     ↓
Within Limits
     ↓
Approved
     ↓
Executed
     ↓
Observed
     ↓
Audited
```

**Agent Capability ≠ Agent Authority.**

**Model Behavior ≠ Security Authorization.**

## Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. AI Agent Governance Framework

AI agent governance establishes the organizational controls required to ensure that agents operate within approved business, security, legal, and risk boundaries.

The governance framework should define:

* approved agent purposes;
* ownership and accountability;
* autonomy levels;
* permitted capabilities;
* data access;
* tool access;
* authorization requirements;
* human oversight;
* monitoring;
* incident response;
* lifecycle management;
* retirement requirements.

Agent governance should cover both the **agent itself** and the environment in which it operates.

---

### 119. Agent Ownership and Accountability

Every enterprise agent should have a clearly identified accountable owner.

Ownership should distinguish between:

| Role            | Primary Responsibility             |
| --------------- | ---------------------------------- |
| Business Owner  | Business purpose and value         |
| Agent Owner     | Overall agent accountability       |
| Technical Owner | Implementation and maintenance     |
| Security Owner  | Security architecture and controls |
| Data Owner      | Data-access authorization          |
| Risk Owner      | Residual-risk acceptance           |
| Platform Owner  | Runtime infrastructure             |
| SOC             | Security monitoring and response   |
| Internal Audit  | Independent assurance              |

An agent without accountable ownership should not be permitted to operate in production.

---

### 120. Agent Inventory and Registry

Organizations should maintain an authoritative inventory of AI agents.

The registry should capture:

* agent name;
* unique identity;
* business owner;
* technical owner;
* purpose;
* model;
* environment;
* autonomy level;
* risk tier;
* tools;
* APIs;
* data sources;
* credentials;
* network access;
* human approval requirements;
* monitoring status;
* lifecycle status.

The inventory should provide a single source of truth for agent governance.

---

### 121. Agent Classification

Agents should be classified according to their technical capability and business impact.

Classification factors should include:

* autonomy;
* privilege;
* data sensitivity;
* transaction capability;
* persistence;
* external connectivity;
* tool count;
* delegation capability;
* reversibility;
* regulatory significance.

A classification should be established before production deployment.

---

### 122. Agent Risk Tiering

A practical risk model may classify agents as:

| Tier       | Characteristics                      | Minimum Governance                         |
| ---------- | ------------------------------------ | ------------------------------------------ |
| **Tier 1** | Informational / advisory             | Basic security                             |
| **Tier 2** | Internal operational assistance      | Standard controls                          |
| **Tier 3** | Sensitive data or controlled actions | Enhanced controls                          |
| **Tier 4** | High-impact autonomous activity      | Strong approval and monitoring             |
| **Tier 5** | Critical / highly privileged         | Maximum controls and independent assurance |

Risk tier should determine the required control baseline.

---

### 123. Autonomy Classification

Autonomy should be formally recorded as a governance attribute.

Example:

```text id="i9l9h1"
A0 → Human Only
A1 → AI Information
A2 → AI Recommendation
A3 → AI Preparation
A4 → Limited Autonomous Action
A5 → Multi-Step Autonomous Execution
A6 → Continuous Autonomous Operation
```

Increasing autonomy should require corresponding increases in security assurance.

---

### 124. Agent Risk Assessment

Agent risk assessments should evaluate both inherent and residual risk.

Key dimensions include:

* confidentiality;
* integrity;
* availability;
* financial impact;
* operational impact;
* regulatory impact;
* privacy;
* safety;
* reputational impact;
* potential blast radius.

The assessment should consider not only what the agent does intentionally, but also what could happen if it behaves incorrectly or is compromised.

---

### 125. Agent Risk Register

Significant risks should be maintained in the enterprise risk register.

Typical risks include:

* agent hijacking;
* excessive privilege;
* unauthorized tool use;
* memory poisoning;
* malicious delegation;
* unauthorized data access;
* credential compromise;
* runaway execution;
* unauthorized transactions;
* cross-tenant access;
* external data exfiltration.

Each risk should have an owner, treatment strategy, control mapping, and review date.

---

### 126. Risk Appetite for Agentic Systems

The organization should define its tolerance for autonomous activity.

Risk appetite may establish:

* maximum transaction values;
* permitted autonomy levels;
* prohibited actions;
* maximum data sensitivity;
* acceptable external connectivity;
* permitted delegation;
* mandatory approval thresholds.

For example:

```text id="b8v8ay"
Low Impact
    ↓
Autonomous

Moderate Impact
    ↓
Conditional Authorization

High Impact
    ↓
Human Approval

Critical / Irreversible
    ↓
Restricted or Prohibited
```

---

### 127. Agent Purpose Limitation

Each agent should have an explicitly documented business purpose.

The purpose should describe:

* why the agent exists;
* what business process it supports;
* what users it serves;
* what systems it interacts with;
* what outcomes it is permitted to achieve.

Capabilities that are unrelated to the approved purpose should be removed or prohibited.

---

### 128. Agent Authority Governance

Agent authority should be explicitly documented.

The authority model should identify:

```text id="y0ut1a"
Agent
 ↓
Identity
 ↓
Permitted Data
 ↓
Permitted Tools
 ↓
Permitted Actions
 ↓
Transaction Limits
 ↓
Delegation Rights
 ↓
Autonomy Boundary
```

This prevents technical functionality from being mistaken for approved authority.

---

### 129. Agent Identity Governance

Agent identities should follow enterprise IAM lifecycle processes.

Governance should cover:

* identity creation;
* ownership;
* naming;
* authentication;
* authorization;
* access reviews;
* credential rotation;
* suspension;
* revocation;
* retirement.

Agent identities should never become orphaned identities.

---

### 130. Agent Access Reviews

Agent permissions should be periodically reviewed.

Reviews should verify:

* permissions remain necessary;
* tools remain necessary;
* data access remains justified;
* privilege has not expanded;
* ownership remains valid;
* business purpose remains unchanged.

High-risk agents should receive more frequent reviews than low-risk agents.

---

### 131. Agent Least-Privilege Governance

Least privilege should be an explicit governance requirement.

The review should consider:

* minimum required APIs;
* minimum data scope;
* minimum tool capability;
* minimum network access;
* minimum transaction authority;
* minimum delegation authority;
* minimum autonomy.

Excessive privilege should be treated as a governance issue as well as a technical issue.

---

### 132. Tool Governance

Tools exposed to agents should be governed as controlled enterprise capabilities.

Each tool should have:

* owner;
* description;
* security classification;
* approved agents;
* permitted operations;
* authentication method;
* authorization requirements;
* data classification;
* logging requirements;
* risk classification.

Tool access should not be granted simply because the agent framework supports the tool.

---

### 133. Capability Governance

Organizations should maintain an explicit mapping between agent capabilities and business requirements.

```text id="m6r42d"
Business Requirement
       ↓
Required Capability
       ↓
Approved Tool
       ↓
Permitted Operation
       ↓
Authorized Resource
```

Capabilities without a documented business requirement should be challenged during security review.

---

### 134. Agent-to-Agent Governance

Agent relationships should be formally governed.

Governance should define:

* trusted agents;
* approved communication paths;
* delegation permissions;
* data-sharing limits;
* authority boundaries;
* delegation depth;
* accountability.

An agent should not automatically trust another agent simply because both belong to the same enterprise.

---

### 135. Delegation Governance

Delegated work should preserve the original authority boundaries.

A governance model should establish:

* who may delegate;
* to whom;
* for what purpose;
* for how long;
* with what authority;
* within which resource scope.

Delegation should never create uncontrolled privilege amplification.

---

### 136. Data Governance for Agents

Agent data access should align with enterprise data governance.

Requirements should address:

* data classification;
* purpose limitation;
* access control;
* data minimization;
* retention;
* geographic restrictions;
* privacy;
* tenant isolation;
* export restrictions.

Agent access should not create a parallel data-governance model.

---

### 137. Memory Governance

Persistent memory should be governed as an enterprise information asset.

Governance should define:

* approved memory types;
* data classification;
* retention periods;
* access rights;
* modification rights;
* deletion;
* provenance;
* integrity requirements.

Sensitive information should not be persistently stored merely because the agent can technically do so.

---

### 138. Context Governance

Agent context should be governed according to trust and sensitivity.

The organization should distinguish:

```text id="xg9d0a"

      ↓

      ↓

      ↓
Approved Memory
      ↓

      ↓

      ↓

      ↓
```

The governance framework should define how each context category may influence agent behavior.

---

### 139. Credential Governance

Governance should define:

* credential issuance;
* privilege;
* storage;
* rotation;
* expiration;
* access;
* revocation;
* emergency response.

Long-lived high-privilege credentials should be avoided where practical.

---

### 140. Network Governance

Agent network access should be explicitly approved.

Governance should define:

* approved network zones;
* permitted destinations;
* external connectivity;
* egress requirements;
* prohibited destinations;
* monitoring;
* data-transfer restrictions.

---

### 141. Human Oversight Governance

Human oversight should be determined by risk rather than by convenience.

Governance should define when:

* no human approval is required;
* human review is required;
* human approval is mandatory;
* dual authorization is required;
* autonomous execution is prohibited.

Oversight requirements should be embedded in the workflow and security architecture.

---

### 142. Approval Threshold Governance

Approval thresholds should be explicitly defined.

Examples:

| Action                        | Governance Requirement        |
| ----------------------------- | ----------------------------- |

### 155. Control Effectiveness Testing

Organizations should test whether controls actually prevent or detect the risks they are intended to address.

For example:

```text id="j1szx4"
Risk:
Unauthorized Refund
```

### 231. Model Behavior Is Not Security Authorization

Model behavior should never be treated as an authorization mechanism.

A model may:

* understand policy;
* generate compliant responses;
* select appropriate tools;
* follow instructions.

However, these behaviors are not equivalent to technical enforcement.

```text id="p8j4k1"
Model Says:
"I am authorized."

       ≠

Security System:
"Authorization Granted."
```

Authorization must be established by an independent security mechanism.

---

### 232. Agent Capability Is Not Agent Authority

An agent may technically possess a capability without being authorized to use it in every situation.

For example:

```text id="f6r2x8"

Delete Only After Approved Request

Security Authority:
Delete Only If
  ├── Correct Agent
  ├── Correct User
  ├── Correct Record
  ├── Correct Purpose
  ├── Correct Approval
  └── Policy Allows Action
```

This distinction should remain fundamental throughout enterprise agent architecture.

### 233. Autonomous Execution Must Remain Bounded

A mature autonomous system should have:

* transaction limits;
* execution limits;
* delegation limits;
* human approval boundaries;

The objective is not to eliminate autonomy, but to make autonomy **controlled autonomy**.

### 237. Enterprise Agent Security Control Set

A mature enterprise should maintain a standardized control set covering the complete autonomous-system lifecycle.

| Control Domain    | Core Controls                                        |
| ----------------- | ---------------------------------------------------- |
| **Identity**      | Agent identity, authentication, credential lifecycle |
| **Authorization** | Fine-grained authorization, policy enforcement       |
| **Privilege**     | Least privilege, segmentation, short-lived authority |
| **Tools**         | Allowlisting, validation, invocation controls        |
| **Data**          | Data authorization, minimization, isolation          |
| **Memory**        | Integrity, provenance, access control                |
| **Network**       | Segmentation, egress restrictions                    |
| **Autonomy**      | Execution limits, approval boundaries                |
| **Transactions**  | Limits, validation, fraud controls                   |
| **Delegation**    | Authentication, bounded delegation                   |
| **Monitoring**    | Telemetry, behavioral detection, SIEM                |
| **Response**      | Kill switch, isolation, credential revocation        |
| **Assurance**     | Testing, independent assessment, evidence            |
| **Lifecycle**     | Reauthorization, change control, retirement          |

The control set should be mapped to agent risk tiers.

### 238. Enterprise Agent Security Operating Principle

The enterprise operating principle should be:

> **Autonomous agents may perform actions only within authority that has been explicitly granted, independently enforced, continuously monitored, and appropriately bounded by risk.**

This requires separation between:

```text id="q2x7m4"
What the model can reason about
              ↓
What the agent can technically perform
              ↓
What the agent is authorized to perform
              ↓
What the agent is allowed to perform autonomously
              ↓
What the enterprise is willing to accept as risk
```

These are separate security decisions and should remain separately enforceable.

---

### 239. Strategic Architecture Principle

The fundamental enterprise architecture principle for AI agents and autonomous systems is:

> **Separate intelligence from authority.**

The model provides reasoning, planning, and decision capability.

The security architecture provides:

* identity;
* authentication;
* authorization;
* least privilege;
* policy enforcement;
* transaction controls;
* human oversight;
* monitoring;
* emergency intervention;
* auditability.

Therefore:

```text id="u1k6p9"
                ┌─────────────────────┐
                │     AI MODEL        │
                │ Reason / Plan /     │
                │ Recommend / Adapt   │
                └──────────┬──────────┘
                           │
                           ▼
                    Proposed Action
                           │
                           ▼
                ┌─────────────────────┐
                │ SECURITY CONTROL    │
                │ Identity            │
                │ Authorization       │
                │ Policy              │
                │ Risk                │
                │ Limits              │
                │ Approval            │
                └──────────┬──────────┘
                           │
                    Authorized?
                      /          \
                    NO            YES
                    │              │
                  DENY             ▼
                              ┌──────────┐
                              │  TOOL /  │
                              │  SYSTEM  │
                              └────┬─────┘
                                   │
                                   ▼
                                ACTION
                                   │
                                   ▼
                          LOG / MONITOR /
                            RESPOND
```

**The model decides what it wants to do.
The security architecture decides what it is allowed to do.**
