# 11.02 — AI Agents and Autonomous Systems

## Part 1 — Foundations and Core Concepts

### 1. Definition of an AI Agent

An **AI agent** is a software system capable of pursuing a defined objective by:

* receiving information;
* interpreting context;
* reasoning about possible actions;
* planning tasks;
* selecting actions;
* invoking tools;
* observing results;
* adapting subsequent actions.

A conventional application generally follows predefined execution logic.

An agent can dynamically determine **what it should do next** within the boundaries established by its architecture and authorization model.

---

### 2. Definition of an Autonomous System

An autonomous system is a system capable of performing actions with limited or no direct human intervention after receiving an objective, trigger, or instruction.

A simplified model is:

```text
Input / Objective
       ↓
Perception
       ↓
Reasoning
       ↓
Planning
       ↓
Decision
       ↓
Action
       ↓
Observation
       ↓
Adaptation
       ↓
Next Action
```

Security becomes more complex because the system can continue acting after the original user interaction has ended.

---

### 3. AI Agent vs Autonomous System

The terms are related but should not automatically be treated as identical.

| Concept                   | Primary Characteristic                                                   |
| ------------------------- | ------------------------------------------------------------------------ |
| AI Model                  | Produces predictions or generated outputs                                |
| LLM Application           | Uses a model within an application workflow                              |
| AI Agent                  | Uses reasoning and tools to pursue an objective                          |
| Autonomous System         | Can execute activities with limited human intervention                   |
| Agentic Autonomous System | Combines AI reasoning, tools, persistent state, and autonomous execution |

An AI agent may have limited autonomy, while an autonomous system may operate with substantially broader authority.

---

### 4. The Fundamental Difference from Conventional Software

Traditional software generally follows:

```text
Input
 ↓
Predefined Logic
 ↓
Output
```

An agentic system may operate as:

```text
Objective
 ↓
Interpret
 ↓
Plan
 ↓
Select Action
 ↓
Execute
 ↓
Observe
 ↓
Replan
 ↓
Execute Again
```

The security challenge therefore extends beyond protecting the software itself.

Security must also control the **decisions and actions produced during execution**.

---

### 5. Agentic Behavior

Agentic behavior refers to the ability of a system to determine and execute a sequence of actions in pursuit of an objective.

Important characteristics include:

* goal orientation;
* planning;
* action selection;
* environmental observation;
* adaptation;
* persistence;
* tool usage;
* delegation;
* feedback processing.

The greater the system's ability to independently determine its next actions, the greater the need for explicit security boundaries.

---

### 6. Agency

Agency is the degree to which an AI system can independently influence its environment.

Agency can exist at different levels:

```text
Level 0
No Action
   ↓
Level 1
Recommendation
   ↓
Level 2
Human-Approved Action
   ↓
Level 3
Limited Autonomous Action
   ↓
Level 4
Multi-Step Autonomous Execution
   ↓
Level 5
Broad Autonomous Authority
```

Increasing agency should result in increasing security controls.

---

### 7. Autonomy

Autonomy represents how independently the system can perform actions without requiring human intervention.

Autonomy should not be treated as a binary property.

It can be evaluated across:

* decision autonomy;
* execution autonomy;
* duration;
* tool access;
* transaction authority;
* delegation;
* data access;
* environmental control.

An agent may be highly autonomous in planning but minimally autonomous in execution.

---

### 8. Degrees of Autonomy

A useful enterprise model is:

| Level | Description                                              |
| ----- | -------------------------------------------------------- |
| A0    | Human performs all actions                               |
| A1    | AI provides information                                  |
| A2    | AI recommends actions                                    |
| A3    | AI prepares actions for approval                         |
| A4    | AI performs limited approved actions                     |
| A5    | AI performs multi-step actions within defined boundaries |
| A6    | AI operates continuously within delegated authority      |

Higher levels require stronger authorization, monitoring, and emergency controls.

---

### 9. Agent Goals

An agent normally operates toward an objective or goal.

Goals may be:

* explicitly provided by a user;
* defined by an application;
* generated by an orchestration workflow;
* derived from business rules;
* delegated by another agent.

Security governance must distinguish between:

**What the agent is trying to accomplish** and **what the agent is actually authorized to do**.

A legitimate goal does not automatically authorize every action that might achieve that goal.

---

### 10. Goal vs Authority

For example:

```text
Goal:
"Resolve the customer's issue."

Possible Agent Actions:
 ├── Read customer record
 ├── Modify customer record
 ├── Issue refund
 ├── Change account configuration
 └── Contact external provider
```

The goal does not automatically authorize all five actions.

Each action requires independent authorization.

---

### 11. Agent Perception

Agents obtain information through various inputs.

These may include:

* user messages;
* application data;
* APIs;
* databases;
* documents;
* sensors;
* web content;
* tool responses;
* other agents;
* event streams.

Every input should be evaluated according to its trust level.

An agent should not automatically treat every observed input as a trusted instruction.

---

### 12. Agent Environment

An agent operates within an environment containing systems, data, users, tools, and external entities.

A simplified environment is:

```text
             ┌─────────────────────┐
             │       USER          │
             └──────────┬──────────┘
                        │
                        ▼
                 ┌────────────┐
                 │    AGENT   │
                 └─────┬──────┘
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
      Data           Tools          Other Agents
        │              │               │
        └──────────────┼───────────────┘
                       ▼
                Enterprise Systems
```

The environment defines the agent's potential attack surface.

---

### 13. Agent State

Agent state represents information maintained during execution.

State may include:

* current objective;
* task status;
* previous actions;
* tool results;
* intermediate reasoning artifacts;
* session information;
* workflow state;
* authorization context.

State can influence future actions and must therefore be protected.

---

### 14. Stateless Agents

A stateless agent does not retain meaningful information between independent executions.

Example:

```text
Request
 ↓
Agent
 ↓
Response
 ↓
Session Ends
```

Stateless designs can reduce certain persistence risks because compromised information may not survive beyond the execution context.

However, stateless does not mean secure by default.

---

### 15. Stateful Agents

A stateful agent maintains information across execution steps or sessions.

```text
Session 1
   ↓
State
   ↓
Session 2
   ↓
State Updated
   ↓
Session 3
```

State persistence introduces additional security requirements around:

* integrity;
* authorization;
* retention;
* isolation;
* provenance;
* deletion.

---

### 16. Agent Memory

Agent memory is persistent or semi-persistent information used to improve future decisions or maintain continuity.

Memory may contain:

* user preferences;
* historical interactions;
* task state;
* retrieved information;
* business information;
* operational data.

Because memory can influence future behavior, it should be treated as a security-sensitive component.

---

### 17. Agent Planning

Planning allows an agent to decompose a goal into multiple actions.

For example:

```text
Goal:
Prepare customer report

Plan:
  1. Retrieve customer data
  2. Analyze transactions
  3. Identify anomalies
  4. Generate report
  5. Store report
  6. Notify authorized user
```

Every step potentially introduces a new security decision.

A secure architecture should not authorize the entire plan merely because the initial objective was approved.

---

### 18. Dynamic Planning

Agent plans may change during execution.

```text
Initial Plan
     ↓
Action 1
     ↓
Observation
     ↓
New Information
     ↓
Revised Plan
     ↓
Action 2
```

This creates a significant security consideration:

> Authorization must remain valid when the agent changes its plan.

A plan that was safe initially may become unsafe after new information is introduced.

---

### 19. Agent Execution Loop

Many agents operate through an iterative execution loop.

```text
┌──────────────────────┐
│      Objective       │
└──────────┬───────────┘
           ↓
      Reason / Plan
           ↓
       Select Tool
           ↓
        Execute
           ↓
      Observe Result
           ↓
      Evaluate State
           │
      ┌────┴────┐
      │ Continue│
      └────┬────┘
           ↓
      Next Action
```

Security controls must apply to each significant execution cycle.

---

### 20. Agent Action

An agent action is an operation that changes or interacts with its environment.

Examples include:

* reading data;
* writing data;
* sending messages;
* invoking APIs;
* executing code;
* modifying configuration;
* creating records;
* deleting resources;
* initiating transactions.

Actions should be classified according to impact and privilege.

---

### 21. Read vs Write Actions

Read and write operations have different risk characteristics.

```text
READ
 ↓
Observe Information

WRITE
 ↓
Change Information

DELETE
 ↓
Destroy Information

TRANSACTION
 ↓
Create External Consequence
```

Security controls should become progressively stronger as the potential impact increases.

---

### 22. Reversible vs Irreversible Actions

Action reversibility is a major security factor.

| Action                       | Typical Risk  |
| ---------------------------- | ------------- |
| Read data                    | Lower         |
| Create draft                 | Low–Moderate  |
| Modify record                | Moderate      |
| Send external message        | Moderate–High |
| Financial transaction        | High          |
| Delete production resource   | Very High     |
| Irreversible external action | Critical      |

Irreversible actions should generally require stronger authorization and oversight.

---

### 23. Agent Tools

Tools provide an agent with capabilities beyond language generation.

Examples include:

* search;
* database queries;
* APIs;
* ticketing systems;
* email;
* cloud management;
* code execution;
* financial systems;
* identity systems.

A tool therefore represents an extension of the agent's operational authority.

---

### 24. Tool Capability

A tool may expose multiple capabilities.

For example:

```text
CRM Tool
 ├── customer.read
 ├── customer.create
 ├── customer.update
 └── customer.delete
```

The agent should not automatically receive every capability exposed by the tool.

Tool capabilities should be independently controlled.

---

### 25. Agent Tool Chain

An agent may use multiple tools sequentially.

```text
Agent
 ↓
Search Tool
 ↓
Database Tool
 ↓
Analysis Tool
 ↓
CRM Tool
 ↓
Notification Tool
```

The cumulative security impact of the chain may be substantially greater than the risk of any individual tool.

---

### 26. Tool Chaining

Tool chaining allows the output of one operation to influence another operation.

Example:

```text
Search
 ↓
Retrieve Data
 ↓
Analyze
 ↓
Generate Decision
 ↓
Modify System
```

An attacker who manipulates an early stage may influence later actions.

Therefore, security validation should exist between consequential stages.

---

### 27. Agent-to-Agent Interaction

Agents may communicate with other agents to distribute work.

```text
User
 ↓
Agent A
 ├──→ Agent B
 │      └──→ Agent C
 │
 └──→ Agent D
```

This introduces additional risks:

* impersonation;
* unauthorized delegation;
* malicious instructions;
* privilege inheritance;
* data leakage;
* cascading failures.

Agent-to-agent relationships therefore require explicit trust boundaries.

---

### 28. Delegation

Delegation occurs when one agent requests another agent to perform a task.

Delegation should preserve:

* identity;
* purpose;
* authority boundaries;
* accountability;
* scope;
* expiration.

An agent should not be able to delegate unlimited authority simply because it possesses greater authority itself.

---

### 29. Agent Identity

Every production agent should have a unique identity.

Identity enables:

* authentication;
* authorization;
* auditing;
* attribution;
* monitoring;
* incident response;
* lifecycle management.

Without a reliable identity, security teams cannot confidently determine which agent performed an action.

---

### 30. Agent Identity vs Human Identity

Agent identity should not be confused with the identity of the human who initiated the workflow.

A useful attribution chain is:

```text
Human User
     ↓
Application
     ↓
Agent Identity
     ↓
Tool Identity
     ↓
Target Resource
```

This allows security teams to answer both:

**Who initiated the activity?**

and

**Which autonomous component actually performed it?**

---

### 31. Agent Authentication

Authentication establishes confidence that an agent is the identity it claims to be.

Potential mechanisms include:

* workload identity;
* certificates;
* mutual TLS;
* signed tokens;
* cloud workload credentials;
* attestation mechanisms.

Authentication should occur independently of the model's textual claims.

---

### 32. Agent Authorization

Authorization determines what an authenticated agent is permitted to do.

A secure decision may consider:

```text
Agent Identity
+
Human Initiator
+
Action
+
Resource
+
Business Purpose
+
Data Sensitivity
+
Transaction Value
+
Context
=
Authorization Decision
```

The model should not make this authorization decision by itself.

---

### 33. Agent Permissions

Agent permissions define the specific resources and actions available to an agent.

Permissions should be:

* explicit;
* limited;
* reviewable;
* revocable;
* attributable;
* time-bounded where appropriate.

Permissions should not be broader than required for the agent's approved business purpose.

---

### 34. Least Privilege

Least privilege requires that an agent receive only the minimum authority necessary to perform its approved function.

This applies to:

* data;
* APIs;
* tools;
* credentials;
* networks;
* transactions;
* compute;
* delegation;
* autonomy.

Least privilege is particularly important because agents may execute multiple actions without continuous human intervention.

---

### 35. Agent Authority

Agent authority represents the actual security power available to the agent.

Authority should be understood as:

```text
Identity
+
Permissions
+
Credentials
+
Tool Access
+
Network Access
+
Transaction Authority
+
Delegation Authority
```

Technical capability alone does not establish authority.

---

### 36. Agent Autonomy Boundary

An autonomy boundary defines what an agent may do without additional approval.

Example:

```text
Agent
 │
 ├── Read approved data → Autonomous
 │
 ├── Create draft → Autonomous
 │
 ├── Modify customer record → Conditional
 │
 ├── Issue refund → Human Approval
 │
 └── Delete account → Prohibited
```

The boundary should be explicitly defined and technically enforced.

---

### 37. Human-in-the-Loop

Human-in-the-loop means a human participates directly in a decision or action before execution.

This may be required for:

* high-value transactions;
* sensitive data disclosure;
* destructive actions;
* legal decisions;
* security-policy changes;
* privileged operations.

Human involvement should be meaningful rather than merely ceremonial.

---

### 38. Human-on-the-Loop

Human-on-the-loop means the agent operates autonomously while humans supervise activity and can intervene.

This model may be appropriate for lower-risk workflows.

```text
Agent
 ↓
Autonomous Execution
 ↓
Monitoring
 ↓
Human Intervention When Required
```

The organization must ensure that humans can actually detect and interrupt unsafe behavior.

---

### 39. Human Approval Boundary

Approval requirements should be tied to action risk rather than simply to the existence of an agent.

Factors may include:

* financial impact;
* data sensitivity;
* privilege;
* reversibility;
* regulatory impact;
* external consequences;
* uncertainty.

The higher the impact, the stronger the approval requirement should generally be.

---

### 40. Agent Failure Modes

Agent failures can occur at multiple layers.

Examples include:

* incorrect reasoning;
* incorrect planning;
* tool failure;
* authorization failure;
* corrupted state;
* malicious input;
* excessive execution;
* unexpected delegation;
* infrastructure failure.

Security architecture must assume that agent behavior can fail without malicious intent.

---

### 41. Unsafe Autonomous Behavior

An agent may behave unsafely even when there is no attacker.

Examples include:

* executing an incorrect plan;
* repeatedly invoking a tool;
* misunderstanding a business rule;
* modifying the wrong record;
* sending excessive communications;
* consuming excessive resources.

Security controls should therefore protect against both malicious and accidental autonomous behavior.

---

### 42. Runaway Agent Behavior

A runaway agent continues performing actions without achieving a valid stopping condition.

Example:

```text
Action
 ↓
Unexpected Result
 ↓
Replan
 ↓
Action
 ↓
Unexpected Result
 ↓
Replan
 ↓
Action
 ↓
...
```

Potential consequences include:

* resource exhaustion;
* excessive API usage;
* repeated transactions;
* data modification;
* communication flooding.

Execution limits and circuit breakers are therefore essential.

---

### 43. Agent Persistence

Persistence determines how long an agent remains capable of acting.

Persistence can exist across:

* requests;
* sessions;
* days;
* workflows;
* system restarts.

Greater persistence increases the potential impact of compromised state or credentials.

---

### 44. Continuous Operation

Some autonomous agents may operate continuously.

```text
Monitor
 ↓
Detect Event
 ↓
Analyze
 ↓
Act
 ↓
Monitor Again
```

Continuous operation creates additional security requirements around:

* credential lifetime;
* monitoring;
* resource limits;
* state management;
* emergency shutdown;
* periodic reauthorization.

---

### 45. Agent Context

Agent context includes information available to the agent when making decisions.

Context may contain:

* system instructions;
* user instructions;
* retrieved information;
* memory;
* tool results;
* policies;
* application state;
* messages from other agents.

Context should be treated as a security boundary because manipulated context can influence subsequent actions.

---

### 46. Trusted and Untrusted Context

Not all context should receive the same trust level.

```text
Trusted
 ├── Security Policy
 ├── Authorization Decision
 └── Verified System Configuration

Controlled
 ├── Approved Enterprise Data
 └── Authorized Memory

Untrusted
 ├── User Input
 ├── External Web Content
 ├── Tool Results
 └── Unknown Agent Messages
```

Trust classification should influence how context is processed.

---

### 47. Agent Objective Manipulation

An attacker may attempt to alter what an agent believes its objective is.

Potential mechanisms include:

* prompt injection;
* malicious documents;
* manipulated tool results;
* poisoned memory;
* compromised upstream agents;
* malicious external content.

Objective integrity should therefore be protected.

---

### 48. Agent Hijacking

Agent hijacking occurs when an attacker gains influence over an agent's behavior or execution.

The attacker may attempt to:

* redirect the objective;
* alter instructions;
* invoke unauthorized tools;
* access sensitive data;
* modify memory;
* perform unauthorized transactions.

The impact depends heavily on the authority available to the compromised agent.

---

### 49. Autonomous Systems as Security Subjects

An autonomous agent should be treated as an identifiable security subject rather than simply as a software process.

It has:

* identity;
* authority;
* permissions;
* responsibilities;
* operational state;
* security events;
* lifecycle;
* risk.

This enables traditional security concepts such as IAM, Zero Trust, least privilege, monitoring, and incident response to be applied to autonomous systems.

---

### 50. Core Principle of AI Agents and Autonomous Systems

The foundational security principle is:

> **An agent may reason autonomously, but its authority must remain explicitly defined, independently authorized, bounded, observable, and interruptible.**

The architecture must preserve the distinction between:

```text
What the Agent Can Conceptually Do
                ≠
What the Agent Is Technically Capable of Doing
                ≠
What the Agent Is Authorized to Do
                ≠
What the Agent Is Permitted to Execute Autonomously
```

This distinction forms the foundation for securely governing increasingly autonomous AI systems.
