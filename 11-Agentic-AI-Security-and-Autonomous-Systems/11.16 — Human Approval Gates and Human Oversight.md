# 11.16 — Human Approval Gates and Human Oversight

## 1. Definition of Human Approval Gates

A human approval gate is a security control that requires an authorized human to review and approve an agent-proposed action before that action can be executed.

In agentic AI systems, approval gates provide an independent decision boundary between:

```text
Agent Recommendation
        |
        v
Human Approval Gate
        |
        v
Authorized Execution
```

The purpose is not to make humans approve every agent activity, but to ensure that appropriately selected high-risk actions cannot be completed solely through autonomous agent behavior.

---

## 2. Human Oversight as an Agentic AI Security Control

Human oversight is a security mechanism that allows authorized personnel to monitor, review, intervene in, or stop autonomous agent activity.

It provides an additional control layer when:

* Agent decisions have significant consequences.
* Actions are difficult to reverse.
* Sensitive data is involved.
* Financial value is involved.
* Privileged systems are affected.
* Security boundaries may be crossed.
* Agent confidence is low.
* Risk exceeds autonomous execution thresholds.

Human oversight should therefore be treated as part of the security architecture rather than merely an operational convenience.

---

## 3. Human Approval vs Human Oversight

Human approval and human oversight are related but different controls.

| Control            | Primary Function                             |
| ------------------ | -------------------------------------------- |
| Human approval     | Authorizes a specific action                 |
| Human oversight    | Monitors ongoing agent behavior              |
| Human intervention | Changes or stops agent behavior              |
| Human review       | Evaluates decisions or outcomes              |
| Human escalation   | Transfers a decision to an authorized person |

Approval is generally **pre-action**.

Oversight may be:

* Pre-action
* During execution
* Post-action
* Continuous

---

## 4. Approval as an Independent Security Boundary

An agent should not be able to approve its own proposed action.

The approval mechanism must be logically and operationally independent from the agent.

```text
+-------------+
| AI Agent    |
+------+------+
       |
       | Proposed Action
       v
+----------------------+
| Approval Control     |
+----------+-----------+
           |
           | Approved
           v
+----------------------+
| Authorization Layer  |
+----------+-----------+
           |
           v
+----------------------+
| Target System        |
+----------------------+
```

This prevents the agent from converting its own recommendation into authorization.

---

## 5. Human Approval and Agent Authority

Human approval should not become a mechanism through which an agent obtains unrestricted authority.

The approval must remain:

* Specific
* Limited
* Contextual
* Time-bound
* Traceable
* Revocable where possible

For example, approval to:

```text
Transfer €5,000 to Supplier A
```

should not imply authorization to:

```text
Transfer unlimited funds to any supplier.
```

---

## 6. Approval Thresholds

Approval thresholds define when autonomous execution must stop and human authorization must occur.

Thresholds may be based on:

* Financial value
* Data sensitivity
* Business impact
* Security impact
* Transaction type
* Privilege level
* Reversibility
* Regulatory significance
* Risk score

Example:

```text
Low Risk
   -> Autonomous

Medium Risk
   -> Enhanced Validation

High Risk
   -> Human Approval

Critical Risk
   -> Dual Approval
```

Thresholds should be formally defined rather than determined dynamically by the agent itself.

---

## 7. Risk-Based Human Approval

Not every agent action requires human intervention.

A risk-based model evaluates the proposed action before determining the required level of human involvement.

Conceptually:

```text
Action
  |
  v
Risk Evaluation
  |
  +---- Low ------> Autonomous
  |
  +---- Medium ---> Oversight
  |
  +---- High -----> Approval
  |
  +---- Critical --> Dual Approval / Block
```

This approach preserves the efficiency benefits of autonomous systems while maintaining stronger controls for high-risk operations.

---

## 8. Human-in-the-Loop

Human-in-the-loop means the agent cannot complete a defined action until a human provides authorization.

Example:

```text
Agent
  |
  | Proposed Action
  v
Human Reviewer
  |
  +--> Approve
  |
  +--> Reject
  |
  +--> Modify
  |
  +--> Escalate
```

The human therefore becomes an explicit decision point in the execution path.

---

## 9. Human-on-the-Loop

Human-on-the-loop means the agent can operate autonomously while humans continuously monitor its behavior and retain the ability to intervene.

Example:

```text
              +----------------+
              | Human Oversight|
              +-------+--------+
                      |
                      v
Agent ---> Decision ---> Action
  ^                       |
  |                       |
  +---- Monitoring -------+
```

This model is appropriate when requiring approval for every action would create unacceptable operational delays.

---

## 10. Human Approval Authority

Not every human is authorized to approve every agent action.

Approval authority should be determined by:

* Role
* Responsibility
* Organizational authority
* Security clearance where applicable
* Business ownership
* Transaction authority
* Separation-of-duties requirements

An agent should not select an approver merely because that person is available.

---

## 11. Approval Identity

Every approval should be bound to a verified human identity.

The system should establish:

```text
Who approved?
      +
What was approved?
      +
When was it approved?
      +
Under what authority?
```

Approval records should therefore be associated with authenticated identities rather than generic accounts.

---

## 12. Approval Context

A human reviewer must receive sufficient context to make an informed security decision.

Relevant context may include:

* Agent identity
* Original user request
* Proposed action
* Target system
* Target resource
* Data involved
* Transaction value
* Security risk
* Reason for the action
* Previous related actions
* Delegation chain
* Policy requiring approval

Approval without sufficient context can become a superficial control.

---

## 13. Action Preview

Before approval, the system should present the actual action the agent intends to perform.

For example:

```text
Agent:
Finance-Agent-01

Action:
Create payment

Beneficiary:
Supplier A

Amount:
€8,500

Source Account:
Corporate Account X

Reason:
Invoice INV-20481

Risk:
High

Approval Required:
Yes
```

The human should approve the concrete action rather than an abstract statement such as:

```text
"Allow the agent to continue."
```

---

## 14. Approval vs Recommendation

An agent may recommend an action, but the recommendation itself is not authorization.

```text
Agent Recommendation
        |
        v
Human Review
        |
        v
Authorization Decision
```

The human approval must be an independent security decision.

This distinction prevents the system from treating model confidence or persuasive reasoning as equivalent to authorization.

---

## 15. Approval Integrity

Approval integrity ensures that an approval cannot be altered, substituted, replayed, or detached from the action that was reviewed.

The approval should be bound to relevant parameters such as:

* Agent
* Action
* Resource
* Transaction
* Amount
* Recipient
* Time
* Policy context

A change to a material parameter should invalidate the previous approval.

---

## 16. Approval Expiration

Human approvals should generally have defined validity periods.

Example:

```text
Approval Created
      |
      v
Valid for 10 Minutes
      |
      v
Execution
      |
      v
Approval Expires
```

An expired approval should not automatically authorize later execution.

This reduces the risk of delayed or replayed approvals.

---

## 17. Approval Replay Risk

An approval should not be reusable for multiple independent actions unless that behavior has been explicitly authorized.

For example:

```text
Approval #1001
   |
   +--> Transaction A     ALLOWED
   |
   +--> Transaction B     DENIED
   |
   +--> Transaction C     DENIED
```

This prevents an agent from capturing a legitimate approval and repeatedly applying it to unauthorized transactions.

---

## 18. Approval Scope

Approval scope defines exactly what the human has authorized.

Scope can include:

* Specific agent
* Specific tool
* Specific resource
* Specific transaction
* Specific amount
* Specific recipient
* Specific action
* Specific time period

The principle is:

**Approval should grant only the authority explicitly approved.**

---

## 19. Approval Escalation

When an action exceeds an approver's authority or risk threshold, the system should escalate it.

Example:

```text
Agent Request
      |
      v
Manager Approval
      |
      | Above Authority
      v
Director Approval
      |
      | Critical
      v
Security / Executive Approval
```

Escalation should be determined by policy rather than by the agent.

---

## 20. Approval Delegation

Approval responsibilities may sometimes be delegated, but delegation must itself be controlled.

A delegated approver should have:

* Defined authority
* Defined scope
* Defined duration
* Authenticated identity
* Appropriate business role

Delegation should not allow an individual to approve actions that exceed the authority of the original approval chain.

---

## 21. Segregation of Duties

Human approval should preserve segregation-of-duties requirements.

An individual who creates or controls a sensitive transaction may be prohibited from approving the same transaction.

For example:

```text
Agent Creates Payment
        |
        v
Requester Reviews
        |
        X
Requester Cannot Approve
        |
        v
Independent Approver
```

Agentic systems should inherit existing enterprise segregation-of-duties requirements rather than bypassing them.

---

## 22. Dual Approval

Critical actions may require two independent human approvals.

Examples include:

* Large financial transactions
* Privileged identity changes
* Production security changes
* Destructive operations
* Critical infrastructure actions

Example:

```text
Agent Proposal
      |
      +----> Approver A
      |
      +----> Approver B
                |
          Both Required
                |
                v
           Authorization
```

Dual approval reduces dependence on a single human decision.

---

## 23. Human Approval and Least Privilege

Approval should follow the principle of least privilege.

A human should receive only the authority necessary to evaluate and approve the relevant action.

The approval mechanism should not grant broad administrative permissions merely because the user has approved one agent transaction.

---

## 24. Human Approval and Agent Identity

The approval process must clearly identify which agent generated the proposed action.

For example:

```text
Initiating User
      |
      v
Agent A
      |
      v
Agent B
      |
      v
Proposed Action
      |
      v
Human Approval
```

The approver should know whether the action came from:

* A trusted internal agent
* A delegated agent
* An external agent
* A newly registered agent
* An agent operating under elevated authority

---

## 25. Approval and Delegated Authority

Where multiple agents are involved, the approval system should preserve the delegation chain.

Example:

```text
User
 |
 v
Agent A
 |
 | Delegated Authority
 v
Agent B
 |
 | Proposed Action
 v
Human Approver
```

The approver should be able to determine whether Agent B actually possesses the authority necessary to request the action.

Human approval must not conceal invalid delegation.

---

## 26. Human Approval and Prompt Injection

Prompt injection may cause an agent to propose actions that the legitimate user never intended.

Therefore, human approval should not simply ask:

```text
"Approve what the agent wants to do?"
```

Instead, the interface should clearly identify:

* Original user intent
* Agent interpretation
* Proposed action
* Security implications
* Relevant inputs
* Data sources
* Transaction parameters

This enables the human to detect when the agent's proposed action diverges from legitimate intent.

---

## 27. Human Oversight and Agent Manipulation

Agents can potentially influence human reviewers through:

* Misleading explanations
* Selective information
* Excessive confidence
* Omitted context
* Urgency claims
* Repeated approval requests
* Manipulated summaries

Human oversight therefore requires protection against **automation bias** and agent-generated misinformation.

The approval interface should present objective security-relevant information independently of the agent's narrative.

---

## 28. Automation Bias

Automation bias occurs when humans excessively trust automated recommendations.

In agentic systems, this can result in:

```text
Agent Recommendation
       |
       v
Human Assumes Correctness
       |
       v
Approval
       |
       v
Unsafe Action
```

Human approval is ineffective if the human simply approves whatever the agent proposes.

Organizations should therefore design approval processes that encourage meaningful verification.

---

## 29. Human Approval Fatigue

Excessive approval requests can reduce the effectiveness of human oversight.

If users receive hundreds of approvals per day, they may begin approving requests without adequate review.

Therefore:

```text
Too Few Approvals
       -> Excessive Autonomous Risk

Too Many Approvals
       -> Approval Fatigue

Risk-Based Approvals
       -> Balanced Control
```

Approval thresholds should be calibrated to focus human attention on genuinely important actions.

---

## 30. Human Oversight Coverage

Organizations should define which agent activities require human oversight.

Coverage may include:

| Activity                       | Possible Oversight |
| ------------------------------ | ------------------ |
| Low-risk read                  | Monitoring         |
| Sensitive data access          | Approval           |
| Financial transaction          | Approval           |
| Privileged change              | Dual approval      |
| Destructive action             | Mandatory approval |
| Security policy change         | Dual approval      |
| Critical infrastructure action | Human-controlled   |

Coverage should be documented as part of the agent security policy.

---

## 31. Human Oversight Boundaries

Human oversight should have clearly defined boundaries.

The organization should establish:

* What humans can approve
* What humans can reject
* What humans can modify
* What humans can stop
* What humans can override
* What requires escalation
* What can never be overridden

Without explicit boundaries, human intervention can itself become an uncontrolled privilege mechanism.

---

## 32. Human Override

Human override allows an authorized human to intervene in autonomous execution.

Examples include:

```text
STOP
PAUSE
REJECT
REVOKE
ESCALATE
ROLL BACK
```

Override capabilities should themselves require authentication and authorization.

A human override should not become an unrestricted administrative backdoor.

---

## 33. Human Intervention During Execution

For long-running autonomous workflows, intervention may be required while the agent is already executing.

Example:

```text
Agent Workflow
     |
     v
Step 1
     |
     v
Step 2
     |
     v
Human Intervention
     |
     +--> Continue
     +--> Modify
     +--> Stop
     +--> Escalate
```

The architecture should support interruption at meaningful control points.

---

## 34. Human Approval for Irreversible Actions

Irreversible or difficult-to-reverse actions generally warrant stronger human control.

Examples include:

* Permanent deletion
* Financial transfer
* Destructive infrastructure changes
* Account termination
* Permanent configuration changes
* Legal or regulatory submissions

The more difficult an action is to reverse, the stronger the justification for human authorization should be.

---

## 35. Human Approval for High-Impact Actions

High-impact actions should have explicit approval requirements based on business and security consequences.

A high-impact action may affect:

* Safety
* Financial assets
* Customer rights
* Sensitive information
* Production availability
* Security controls
* Regulatory obligations

Agent autonomy should decrease as potential impact increases.

---

## 36. Approval Failure Handling

The system must define what happens when approval fails.

Possible outcomes include:

```text
Approval Denied
      |
      +--> Stop Action
      |
      +--> Return to Agent
      |
      +--> Request Clarification
      |
      +--> Escalate
```

The agent must not interpret a denial as permission to find another path to the same action.

---

## 37. Approval Timeout Handling

If a human does not respond within the required time, the system should follow a predefined policy.

For security-sensitive actions, the default should generally be:

```text
No Approval
     |
     v
No Execution
```

Silence should not be interpreted as authorization unless a formally governed workflow explicitly defines otherwise.

---

## 38. Human Approval and Fail-Safe Behavior

Approval mechanisms should fail safely.

If the approval service becomes unavailable:

```text
Approval Service Unavailable
          |
          v
High-Risk Action
          |
          v
BLOCK
```

The system should not automatically bypass human approval because the approval infrastructure is temporarily unavailable.

---

## 39. Human Approval and Business Continuity

Fail-safe approval controls must still consider business continuity.

Organizations may define controlled alternatives such as:

* Secondary approvers
* Emergency approval procedures
* Backup approval systems
* Emergency operating procedures
* Predefined continuity authorities

These alternatives must remain governed and auditable.

---

## 40. Human Approval Logging

Every approval event should generate an auditable record.

Relevant information includes:

* Approver identity
* Agent identity
* Original request
* Proposed action
* Approval decision
* Timestamp
* Approval scope
* Risk score
* Policy requiring approval
* Transaction identifier
* Relevant authorization context

This creates evidence of how autonomous actions were authorized.

---

## 41. Human Approval Non-Repudiation

For high-impact operations, organizations may require stronger evidence that an approval was genuinely issued by the authorized person.

Controls may include:

* Strong authentication
* Cryptographic signing
* Tamper-resistant records
* Secure timestamps
* Transaction binding
* Immutable audit trails

The objective is to establish reliable evidence of the approval event.

---

## 42. Human Oversight Monitoring

Organizations should monitor the effectiveness of human oversight itself.

Metrics may include:

* Approval rate
* Rejection rate
* Escalation rate
* Approval response time
* Approval volume
* Override frequency
* Approval fatigue indicators
* Post-approval incident rate
* Incorrect approval rate

Oversight should be treated as a measurable security control.

---

## 43. Human Approval Abuse

Approval mechanisms can themselves be abused.

Potential risks include:

* Compromised approver accounts
* Unauthorized delegation
* Approval replay
* Social engineering
* Approval flooding
* Approval interface manipulation
* Privilege escalation
* Collusion
* Inadequate review

Therefore, the human approval layer requires its own security controls.

---

## 44. Human Approval and Zero Trust

Human approval should follow Zero Trust principles.

The system should continuously verify:

```text
Approver Identity
      +
Approver Authority
      +
Requested Action
      +
Approval Context
      +
Current Risk
```

Being an authorized employee does not automatically make every approval valid.

---

## 45. Human Oversight Across Agent Chains

In multi-agent environments, oversight must account for the entire execution chain.

Example:

```text
User
 |
 v
Agent A
 |
 v
Agent B
 |
 v
Agent C
 |
 v
Tool
 |
 v
Transaction
```

A human approving Agent B's request should understand the downstream consequences when Agent B will delegate further to Agent C or invoke a high-impact tool.

Approval should not become a blind checkpoint within a complex autonomous chain.

---

## 46. Approval Context Integrity

The information presented to a human approver must be protected from manipulation.

The approval interface should independently retrieve or verify critical information such as:

* Transaction amount
* Target
* Agent identity
* Authorization scope
* Data classification
* Risk level

The agent should not be the sole source of truth for the information used to approve its own action.

---

## 47. Human Approval and Separation of Decision Authority

The architecture should separate:

```text
Model Decision
       |
       v
Agent Recommendation
       |
       v
Security Authorization
       |
       v
Human Approval
       |
       v
Execution
```

Depending on risk, some of these functions may be combined operationally, but security-critical authority should remain independently controlled.

This separation prevents one compromised component from controlling the entire action chain.

---

## 48. Human Oversight as a Governance Object

Human oversight should be formally governed.

Governance should define:

* Which agents require oversight
* Which actions require approval
* Approval thresholds
* Authorized approvers
* Escalation procedures
* Override rules
* Emergency procedures
* Logging requirements
* Review frequency
* Control effectiveness measures

Human oversight should therefore be included in the enterprise AI governance framework.

---

## 49. Core Principles of Human Approval Gates and Human Oversight

The following principles should guide enterprise implementation:

1. **Approval must be independent of agent behavior.**
2. **Human approval must authorize a specific action, not unlimited authority.**
3. **High-impact actions require stronger oversight.**
4. **Approval must be bound to the action being approved.**
5. **Approver identity and authority must be verified.**
6. **Approval must preserve least privilege.**
7. **Segregation of duties must remain effective.**
8. **Approval interfaces must provide trustworthy context.**
9. **Human oversight must be resistant to automation bias.**
10. **Approval volume must be controlled to prevent approval fatigue.**
11. **Denial must not trigger autonomous attempts to bypass the decision.**
12. **Approval failures must fail safely.**
13. **Emergency overrides must remain controlled and auditable.**
14. **Every material approval must be attributable.**
15. **Human oversight must be continuously evaluated for effectiveness.**

---

## 50. Core Principle of Human Approval Gates and Human Oversight

**Human approval is a security boundary, not a formality.**

An autonomous agent may analyze information, formulate a recommendation, and prepare an action, but where governance requires human authorization, the agent must stop at the approval boundary.

The fundamental control model is:

```text
                    AGENT
                      |
                      v
              Proposed Action
                      |
                      v
             Risk Evaluation
                      |
          +-----------+-----------+
          |                       |
       Low Risk               High Risk
          |                       |
          v                       v
   Autonomous Control      Human Approval Gate
                                  |
                         +--------+--------+
                         |                 |
                      APPROVE           REJECT
                         |                 |
                         v                 v
                  Authorization         STOP
                         |
                         v
                     Execution
```

The governing principle is:

**The agent may recommend, but the authorized human and independent security controls determine whether a high-impact action may proceed.**
