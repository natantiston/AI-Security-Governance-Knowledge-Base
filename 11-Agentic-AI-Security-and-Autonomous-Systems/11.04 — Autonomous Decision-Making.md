# 11.04 — Autonomous Decision-Making

## Part 1 — Foundations and Core Concepts

### 1. Definition of Autonomous Decision-Making

Autonomous decision-making is the capability of an AI agent or autonomous system to evaluate information, determine an appropriate course of action, and initiate or recommend execution with limited or no direct human intervention.

In conventional software, decisions are generally encoded through deterministic rules:

```text
Input
 ↓
Predefined Rule
 ↓
Deterministic Decision
 ↓
Action
```

In an agentic system, the decision process may involve:

```text
Input
 ↓
Context
 ↓
Memory
 ↓
Reasoning
 ↓
Planning
 ↓
Decision
 ↓
Authorization
 ↓
Action
```

The security challenge is that the decision may be generated dynamically rather than explicitly programmed.

---

### 2. Autonomous Decision-Making as a Security Concern

Autonomous decision-making creates a new security boundary between **what an agent determines should happen** and **what the enterprise permits to happen**.

A decision can be logically reasonable while still being:

* unauthorized;
* unsafe;
* outside business policy;
* based on manipulated information;
* excessive in scope;
* legally restricted;
* financially inappropriate;
* destructive;
* inconsistent with the agent's approved purpose.

Therefore:

> **A valid AI decision is not automatically an authorized enterprise action.**

---

### 3. Decision vs Action

Decision-making and execution must be treated as separate security stages.

```text
Agent
 ↓
Decision
 ↓
Proposed Action
 ↓
Security Evaluation
 ↓
Authorization
 ↓
Execution
```

The agent can propose an action, but an independent control layer should determine whether the action is permitted.

This distinction prevents autonomous reasoning from becoming an uncontrolled source of authority.

---

### 4. Decision vs Authorization

A fundamental architectural distinction is:

| Function          | Question                            |
| ----------------- | ----------------------------------- |
| AI Decision       | What should be done?                |
| Policy Evaluation | What is permitted?                  |
| Authorization     | Is this specific action authorized? |
| Execution Control | Can the action actually occur?      |

The agent may answer the first question.

It should not independently answer all four.

---

### 5. Autonomous Decision-Making vs Deterministic Decision-Making

Traditional systems typically rely on predefined decision logic.

Autonomous systems may generate decisions dynamically based on context.

```text
Deterministic System:

IF condition A
THEN action B


Autonomous Agent:

Goal
 ↓
Context
 ↓
Reasoning
 ↓
Potential Actions
 ↓
Selected Action
```

The second model introduces uncertainty because the exact decision path may not have been explicitly defined in advance.

---

### 6. Decision Autonomy

Decision autonomy describes how independently an agent can determine its course of action.

A useful classification is:

| Level   | Decision Capability               |
| ------- | --------------------------------- |
| Level 0 | No autonomous decision            |
| Level 1 | Recommendation only               |
| Level 2 | Decision with mandatory approval  |
| Level 3 | Limited autonomous decisions      |
| Level 4 | Broad autonomous decisions        |
| Level 5 | Highly autonomous decision-making |

Higher autonomy should require stronger controls.

---

### 7. Recommendation vs Autonomous Decision

A recommendation does not necessarily create direct operational impact.

```text
Recommendation:

Agent
 ↓
Recommendation
 ↓
Human Decision
 ↓
Action
```

Autonomous decision-making changes the control model:

```text
Agent
 ↓
Decision
 ↓
Authorization
 ↓
Action
```

The security architecture must therefore distinguish between **advisory intelligence** and **operational autonomy**.

---

### 8. Decision Authority

Decision authority represents the degree to which an agent is permitted to determine outcomes within a business process.

An agent may have authority to:

* classify information;
* prioritize tasks;
* recommend actions;
* modify records;
* initiate workflows;
* approve transactions;
* communicate externally;
* execute operational changes.

Decision authority should be explicitly defined rather than inferred from the tools available to the agent.

---

### 9. Decision Scope

Every autonomous decision should have a defined scope.

Scope may include:

* business process;
* systems;
* users;
* data;
* geography;
* transaction types;
* financial limits;
* time period;
* operational environment.

For example:

```text
Agent Authority

Process:
Invoice Processing

Data:
Approved Supplier Records

Transaction:
≤ €5,000

Environment:
Production

Duration:
8 Hours
```

A decision outside this scope should be rejected or escalated.

---

### 10. Decision Boundaries

Decision boundaries define where autonomous reasoning must stop and another control must take over.

Examples include:

```text
Low Risk
→ Autonomous Decision

Medium Risk
→ Additional Validation

High Risk
→ Human Approval

Critical Risk
→ Autonomous Decision Prohibited
```

Boundaries should be technically enforceable.

---

### 11. Decision Context

Autonomous decisions depend heavily on context.

Context may include:

* user instructions;
* system instructions;
* retrieved information;
* memory;
* business data;
* tool results;
* environmental state;
* previous actions.

However:

> **Context is information, not authority.**

Information appearing in an agent's context should not automatically grant permission to act.

---

### 12. Trusted and Untrusted Decision Inputs

Decision inputs should be classified according to trust.

```text
                Decision Context
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
   Trusted Data    Controlled Data   Untrusted Data
        │              │              │
        ▼              ▼              ▼
    Policy        Validation       Validation
        │              │              │
        └──────────────┼──────────────┘
                       ▼
                   Reasoning
```

External content, user-provided information, retrieved documents, and tool results should not automatically be treated as trusted decision inputs.

---

### 13. Decision Integrity

Decision integrity concerns whether the information and reasoning process leading to a decision have been manipulated.

Threats may include:

* prompt injection;
* malicious documents;
* poisoned retrieval results;
* manipulated memory;
* compromised tools;
* false sensor data;
* malicious user instructions;
* compromised agents.

Decision integrity therefore requires controls across the entire decision pipeline.

---

### 14. Decision Provenance

Security-sensitive decisions should have sufficient provenance to determine how they were reached.

Relevant information may include:

* initiating user;
* agent identity;
* model version;
* relevant context;
* data sources;
* retrieved information;
* tools consulted;
* policy evaluations;
* authorization decision;
* final action.

Conceptually:

```text
Decision
 ↓
Evidence
 ↓
Reasoning Context
 ↓
Policy
 ↓
Authorization
 ↓
Action
```

This supports investigation, audit, and accountability.

---

### 15. Decision Explainability

For high-impact decisions, organizations may require an understandable explanation of the basis for the decision.

The objective is not necessarily to expose internal model reasoning.

Instead, organizations should capture structured decision evidence such as:

* inputs considered;
* applicable policy;
* decision category;
* risk classification;
* authorization result;
* approval requirement;
* resulting action.

This creates useful auditability without treating internal model reasoning as the security control.

---

### 16. Decision Confidence

Agents may produce confidence estimates or probability-like assessments.

Confidence can be useful for determining whether additional review is appropriate.

However:

> **Model confidence is not equivalent to security authorization.**

A highly confident model can still produce an incorrect or unauthorized decision.

Therefore:

```text
Model Confidence
       +
Security Policy
       +
Risk Assessment
       +
Authorization
       ↓
Final Control Decision
```

---

### 17. Decision Uncertainty

Autonomous systems operate under uncertainty.

Uncertainty can result from:

* incomplete information;
* conflicting information;
* ambiguous objectives;
* unreliable sources;
* changing environments;
* unavailable tools;
* model limitations.

High uncertainty should generally reduce autonomous authority rather than encourage unrestricted action.

---

### 18. Ambiguous Decisions

An agent should not automatically resolve every ambiguity through autonomous action.

Example:

```text
Ambiguous Request
       ↓
Can Scope Be Determined?
       │
    ┌──┴──┐
   Yes    No
    │      │
    ▼      ▼
Continue  Escalate
```

Security architecture should define escalation conditions for ambiguous or incomplete decisions.

---

### 19. Conflicting Instructions

Agents may encounter conflicting instructions from:

* users;
* system policies;
* business rules;
* retrieved documents;
* tools;
* other agents;
* memory.

A defined instruction hierarchy should determine which sources can influence decisions.

Security policy must have precedence over lower-trust instructions.

---

### 20. Objective Alignment

An agent's objective should align with its approved business purpose.

Potential risks occur when:

```text
Business Objective
       ↓
Agent Objective
       ↓
Operational Goal
       ↓
Autonomous Action
```

becomes misaligned.

Objective manipulation can cause the agent to optimize for an outcome that conflicts with organizational security requirements.

---

### 21. Goal vs Security Policy

Business goals should not override security policies.

For example:

```text
Goal:
Complete payment processing quickly.

Security Policy:
Payments above €10,000 require approval.

Agent:
"Completing the task is important."

Security Control:
"Approval is mandatory."

→ Approval remains required.
```

Security controls must remain authoritative even when autonomous reasoning identifies a potentially beneficial shortcut.

---

### 22. Decision Optimization Risk

Agents may optimize toward a defined goal in ways that create unintended security consequences.

For example, an agent optimizing for:

**"Resolve incidents as quickly as possible"**

might attempt:

* disabling security controls;
* terminating services;
* changing firewall rules;
* deleting suspicious accounts.

The objective may be legitimate while the autonomous implementation is unsafe.

Therefore, optimization objectives require explicit security constraints.

---

### 23. Goal Misalignment

Goal misalignment occurs when the agent's behavior does not adequately correspond to the organization's intended objective.

Misalignment can arise from:

* poorly defined goals;
* ambiguous instructions;
* incomplete policies;
* conflicting objectives;
* malicious input;
* model limitations;
* changing environments.

Governance should define acceptable and prohibited outcomes.

---

### 24. Action Selection

An autonomous agent may identify multiple possible actions.

Conceptually:

```text
Goal
 ↓
Possible Actions
 ├── Action A
 ├── Action B
 ├── Action C
 └── Action D
        ↓
     Selection
        ↓
 Proposed Action
```

Security controls should evaluate the selected action independently rather than trusting the selection process.

---

### 25. Action Risk

Not every autonomous decision has the same consequence.

A useful classification is:

| Action                        | Typical Risk  |
| ----------------------------- | ------------- |
| Generate report               | Low           |
| Read internal record          | Low–Moderate  |
| Modify record                 | Moderate      |
| Send external communication   | Moderate–High |
| Change security configuration | High          |
| Transfer funds                | High          |
| Delete production data        | Critical      |

Risk should be associated with the **action and consequence**, not only the model.

---

### 26. Reversible vs Irreversible Decisions

Decision architecture should distinguish reversible actions from irreversible actions.

```text
Reversible
→ Autonomous execution may be acceptable

Difficult to Reverse
→ Additional validation

Irreversible
→ Strong authorization / approval
```

Examples of irreversible or difficult-to-reverse actions include:

* deleting data;
* terminating services;
* financial transfers;
* sending legally significant communications;
* changing critical infrastructure.

---

### 27. Decision Consequence

The security impact of a decision depends on its downstream consequences.

An apparently simple decision can trigger a large chain:

```text
Agent Decision
 ↓
API Call
 ↓
Workflow
 ↓
Database Change
 ↓
External Notification
 ↓
Business Impact
```

Risk assessment must therefore consider the complete action chain.

---

### 28. Cascading Decisions

One autonomous decision can create additional decisions.

```text
Decision A
 ↓
Action A
 ↓
New State
 ↓
Decision B
 ↓
Action B
 ↓
New State
 ↓
Decision C
```

This creates the possibility of compounding errors or unintended escalation.

Execution limits and state controls should constrain cascading decisions.

---

### 29. Decision Loops

Autonomous systems may repeatedly evaluate and act.

```text
Observe
 ↓
Decide
 ↓
Act
 ↓
Observe
 ↓
Decide
 ↓
Act
 ↺
```

Without controls, the loop can continue indefinitely.

Security controls should establish:

* maximum iterations;
* time limits;
* resource limits;
* stop conditions;
* anomaly detection.

---

### 30. Recursive Decision-Making

Agents may invoke other agents or create additional subtasks.

Recursive decision-making increases complexity because authority can propagate through multiple components.

```text
Agent A
 ↓
Agent B
 ↓
Agent C
 ↓
Tool
 ↓
Enterprise System
```

Each delegation step should preserve or reduce authority.

---

### 31. Decision Delegation

An agent may delegate a decision or task to another agent.

Delegation should include:

* originating identity;
* delegated identity;
* purpose;
* authority scope;
* resource scope;
* expiration;
* permitted actions.

Delegation should never implicitly transfer unrestricted authority.

---

### 32. Decision Chain of Responsibility

Enterprise architectures should maintain attribution across autonomous decision chains.

```text
Human
 ↓
Application
 ↓
Agent A
 ↓
Agent B
 ↓
Tool
 ↓
Enterprise Resource
```

Security logs should preserve the complete chain.

This allows the organization to determine who or what initiated an action and which autonomous components participated.

---

### 33. Human-in-the-Loop Decision-Making

Human-in-the-loop architectures require explicit human intervention before defined actions can proceed.

```text
Agent
 ↓
Decision
 ↓
Risk Assessment
 ↓
Human Approval
 ↓
Authorization
 ↓
Execution
```

The human approval requirement should be enforced by the control architecture rather than merely suggested to the agent.

---

### 34. Human-on-the-Loop Decision-Making

Human-on-the-loop systems allow autonomous execution while maintaining human monitoring and intervention capabilities.

```text
Agent
 ↓
Decision
 ↓
Authorization
 ↓
Execution
 ↓
Human Monitoring
 ↓
Intervention if Required
```

This model is appropriate only when the consequences of autonomous execution are sufficiently controlled and intervention can occur before unacceptable harm.

---

### 35. Human Approval Thresholds

Organizations should establish objective thresholds for human involvement.

Examples:

* transaction amount;
* data sensitivity;
* privilege level;
* external impact;
* destructive potential;
* regulatory significance;
* business criticality.

Thresholds should be policy-controlled and independently enforced.

---

### 36. Decision Escalation

An agent should be capable of escalating decisions it cannot safely resolve.

Escalation triggers may include:

* insufficient information;
* conflicting instructions;
* high risk;
* policy ambiguity;
* unusual behavior;
* authorization failure;
* unavailable security service;
* irreversible consequences.

Safe escalation is preferable to unsafe autonomous completion.

---

### 37. Fail-Safe Decision-Making

When required security information is unavailable, the system should fail safely.

For example:

```text
Authorization Service Unavailable
          ↓
Can Authorization Be Verified?
          ↓
             NO
          ↓
Do Not Execute
          ↓
Escalate / Queue / Fail Safely
```

An agent should not interpret security-control failure as permission to proceed.

---

### 38. Fail-Closed Decision-Making

High-risk autonomous actions should generally fail closed.

Examples:

* authorization unavailable → deny;
* identity unavailable → deny;
* policy unavailable → deny or hold;
* required approval unavailable → hold;
* transaction validation unavailable → do not execute.

This prevents availability problems from becoming authorization bypasses.

---

### 39. Decision Manipulation

Autonomous decisions can be manipulated by altering information presented to the agent.

Attack vectors include:

* prompt injection;
* indirect prompt injection;
* malicious documents;
* poisoned retrieval data;
* manipulated memory;
* false tool results;
* compromised agents.

Decision security therefore requires protection of the entire information pipeline.

---

### 40. Decision Poisoning

Decision poisoning occurs when malicious or incorrect information influences an autonomous decision.

A simplified attack path is:

```text
Malicious Input
 ↓
Context
 ↓
Agent Reasoning
 ↓
Incorrect Decision
 ↓
Authorized Execution
```

Even if authorization is functioning correctly, a legitimate identity may execute an unsafe decision.

This demonstrates why authorization alone is insufficient for agentic security.

---

### 41. Decision Integrity vs Decision Correctness

These concepts should be distinguished.

**Decision integrity** asks:

> Was the decision process protected from unauthorized manipulation?

**Decision correctness** asks:

> Was the resulting decision actually appropriate?

Security architecture can strongly protect integrity without guaranteeing that an AI decision is correct.

Both dimensions should be addressed separately.

---

### 42. Decision Monitoring

Autonomous decisions should be monitored for anomalous behavior.

Monitoring may include:

* unusual decision frequency;
* unusual action types;
* abnormal transaction values;
* unexpected data access;
* unusual tool combinations;
* deviations from normal workflows;
* repeated authorization failures.

Behavioral monitoring provides an additional layer of protection when deterministic prevention cannot identify every unsafe decision.

---

### 43. Decision Logging

Security-relevant decisions should generate auditable events.

A decision event may contain:

```text
Timestamp
Agent Identity
User / Initiator
Task
Decision Type
Requested Action
Risk Classification
Policy Result
Authorization Result
Approval Status
Tool
Target Resource
Outcome
```

Logs should be protected against unauthorized modification.

---

### 44. Decision Accountability

Every consequential autonomous decision should be attributable.

Accountability should identify:

* who initiated the task;
* which agent acted;
* which model was used;
* what policies applied;
* which authorization decision occurred;
* which tool executed the action;
* what resource was affected.

This creates an auditable chain from human intent to autonomous execution.

---

### 45. Decision Non-Repudiation Considerations

For high-impact decisions, organizations may require stronger evidence that an action originated from a particular authenticated agent and was processed through approved controls.

Potential mechanisms include:

* cryptographically signed requests;
* authenticated identities;
* immutable audit records;
* transaction identifiers;
* policy decision records.

The objective is to preserve trustworthy evidence of autonomous activity.

---

### 46. Decision Risk Classification

Autonomous decisions should be classified according to potential impact.

A practical model:

```text
Tier 1 — Informational
No operational impact

Tier 2 — Operational
Limited reversible impact

Tier 3 — Sensitive
Material business or data impact

Tier 4 — High Impact
Significant financial / security / operational impact

Tier 5 — Critical
Potential severe enterprise consequences
```

Higher tiers should require stronger authorization and oversight.

---

### 47. Decision Authority Must Be Explicit

An agent should never gain decision authority simply because a technical integration makes an action possible.

The relationship should be:

```text
Capability
    ≠
Authority
    ≠
Authorization
    ≠
Execution
```

An agent may have the technical capability to perform an operation without having authority to make the corresponding decision.

---

### 48. Decision Boundaries Must Be Independent

Security boundaries should not depend solely on the agent correctly interpreting its own instructions.

For example, this is weak:

```text
System Prompt:
"Never delete production data."
```

A stronger architecture is:

```text
Agent Requests Delete
        ↓
Authorization Policy
        ↓
Delete Not Permitted
        ↓
Request Blocked
```

Prompt-level restrictions can support security but should not be the primary enforcement mechanism for high-impact actions.

---

### 49. Autonomous Decision-Making as a Governance Object

Organizations should govern autonomous decision-making explicitly.

Governance should define:

* permitted decision types;
* decision authority;
* risk tiers;
* human approval requirements;
* prohibited decisions;
* evidence requirements;
* monitoring;
* reassessment;
* accountability.

Autonomous decision-making should therefore be included in AI governance, security governance, and enterprise risk management.

---

### 50. Core Principle of Autonomous Decision-Making

The foundational principle is:

> **An autonomous agent may determine what it proposes to do, but an independent security architecture must determine what it is authorized to do.**

The secure decision model is therefore:

```text
              AUTONOMOUS INTELLIGENCE
                       │
              Observe / Reason
                       │
                    Decide
                       │
                Propose Action
                       │
                       ▼
              INDEPENDENT CONTROL
                       │
              Policy Evaluation
                       │
               Risk Assessment
                       │
                Authorization
                       │
            Human Approval if Required
                       │
                       ▼
                   EXECUTION
                       │
                       ▼
                 MONITORING
```

This separation establishes the foundation for safely governing autonomous decisions without treating model-generated decisions as equivalent to enterprise authorization.

## Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. Autonomous Decision Governance Framework

Organizations should establish a formal governance framework for autonomous decision-making that defines how decisions are designed, classified, approved, monitored, challenged, and retired.

The framework should address:

* decision authority;
* autonomy levels;
* permitted decision types;
* prohibited decisions;
* risk classification;
* human oversight;
* authorization;
* evidence;
* monitoring;
* incident response;
* reauthorization.

Governance should focus on the **consequences of decisions**, not merely the capabilities of the underlying model.

---

### 119. Decision Ownership and Accountability

Every autonomous decision process should have an accountable business and technical owner.

| Role           | Responsibility                           |
| -------------- | ---------------------------------------- |
| Business Owner | Business purpose and acceptable outcomes |
| Agent Owner    | Agent behavior and lifecycle             |
| Security Owner | Security requirements and controls       |
| Data Owner     | Data use and access                      |
| Risk Owner     | Residual risk                            |
| GRC            | Governance and compliance                |
| SOC            | Monitoring and incident response         |
| Internal Audit | Independent assurance                    |

Ownership must remain clear even when the decision itself is generated autonomously.

---

### 120. Autonomous Decision Inventory

Organizations should maintain an inventory of significant autonomous decision processes.

The inventory should capture:

* decision identifier;
* business process;
* agent;
* owner;
* model;
* decision type;
* decision authority;
* affected systems;
* data involved;
* tools;
* risk tier;
* human approval requirements;
* transaction limits;
* deployment environment.

The inventory should distinguish between **agents** and the **decisions those agents are authorized to make**.

---

### 121. Decision Classification

Autonomous decisions should be classified according to their potential impact.

A practical classification may include:

```text
Class 1 — Informational
Class 2 — Low-Impact Operational
Class 3 — Sensitive
Class 4 — High-Impact
Class 5 — Critical
```

Classification should consider both direct and downstream consequences.

---

### 122. Decision Risk Tiering

Risk tiering should incorporate multiple dimensions:

* autonomy;
* privilege;
* data sensitivity;
* financial exposure;
* reversibility;
* affected users;
* regulatory impact;
* business criticality;
* external impact.

A low-complexity agent can still be a high-risk system if its decisions affect critical enterprise resources.

---

### 123. Decision Governance Board

High-impact autonomous decision processes should be subject to formal governance review.

The review body may include:

* AI governance;
* cybersecurity;
* enterprise architecture;
* legal;
* privacy;
* compliance;
* business leadership;
* risk management.

The review should determine whether the proposed level of autonomy is acceptable.

---

### 124. Decision Authority Governance

Decision authority should be explicitly documented.

For each autonomous process, governance should define:

```text
Agent
 ↓
Permitted Decisions
 ↓
Permitted Resources
 ↓
Permitted Actions
 ↓
Limits
 ↓
Approval Requirements
```

Authority should never be inferred solely from available technical capabilities.

---

### 125. Autonomy Classification Governance

Organizations should formally classify how much autonomy an agent possesses.

| Level               | Governance Requirement |
| ------------------- | ---------------------- |
| Advisory            | Standard oversight     |
| Approval-Based      | Mandatory approval     |
| Limited Autonomous  | Defined boundaries     |
| Broad Autonomous    | Enhanced assurance     |
| Critical Autonomous | Exceptional governance |

Increasing autonomy should trigger additional risk assessment and control requirements.

---

### 126. Decision Purpose Limitation

Autonomous decision-making should remain aligned with an explicitly approved business purpose.

An agent approved to:

> classify customer support tickets

should not automatically receive authority to:

> terminate customer accounts.

Purpose limitation prevents capability expansion from silently becoming authority expansion.

---

### 127. Decision Risk Register

Material autonomous decision risks should be recorded in the enterprise risk register.

Examples:

| Risk                 | Cause               | Impact               |
| -------------------- | ------------------- | -------------------- |
| Incorrect decision   | Model error         | Business disruption  |
| Manipulated decision | Prompt injection    | Unauthorized action  |
| Excessive authority  | Broad permissions   | Privilege abuse      |
| Decision cascade     | Autonomous chaining | Large-scale impact   |
| Data poisoning       | Manipulated context | Incorrect outcome    |
| Runaway decisions    | Missing limits      | Resource exhaustion  |
| Delegation abuse     | Unbounded authority | Privilege escalation |

---

### 128. Risk Appetite for Autonomous Decisions

The organization should establish risk appetite for autonomous decision-making.

For example:

```text
Low Risk
→ High Automation

Moderate Risk
→ Controlled Automation

High Risk
→ Human Approval

Critical Risk
→ No Autonomous Execution
```

Risk appetite should be approved by appropriate governance authorities.

---

### 129. Decision Control Requirements

Each decision category should have defined security requirements.

Requirements may include:

* identity;
* authentication;
* authorization;
* least privilege;
* data protection;
* human approval;
* transaction limits;
* logging;
* monitoring;
* reversibility;
* emergency controls.

Controls should be proportional to the consequences of failure.

---

### 130. Decision Authorization Governance

Authorization policies should be formally owned and maintained.

Governance should define:

* who can authorize decisions;
* which agents may receive authority;
* which resources are in scope;
* approval thresholds;
* expiration;
* review frequency;
* revocation conditions.

Authorization should remain separate from autonomous reasoning.

---

### 131. Agent Access Reviews

Agent decision authority should undergo periodic access review.

Reviews should verify:

* current business purpose;
* current permissions;
* tools;
* data access;
* network access;
* transaction authority;
* delegation rights.

Unused or excessive authority should be removed.

---

### 132. Decision Least Privilege

Autonomous decision-making should follow least privilege.

The agent should receive:

> **The minimum decision authority required to perform its approved function.**

For example:

```text
Required:
Approve invoices ≤ €5,000

Not Required:
Approve all financial transactions
```

Decision scope should therefore be narrower than general system capability.

---

### 133. Tool Governance for Autonomous Decisions

Tools that can materially affect decisions should be formally governed.

Each tool should have:

* owner;
* purpose;
* risk rating;
* permitted agents;
* operations;
* data scope;
* transaction limits;
* approval requirements;
* logging.

Adding a high-impact tool should trigger architecture and risk review.

---

### 134. Capability Governance

Agent capabilities should be explicitly documented.

Governance should distinguish:

```text
Technical Capability
        ↓
Permitted Capability
        ↓
Decision Authority
        ↓
Specific Authorization
```

This prevents an agent's technical capabilities from being mistaken for permanent authority.

---

### 135. Data Governance for Decisions

Data used by autonomous decisions should be governed according to:

* classification;
* purpose;
* accuracy;
* provenance;
* access;
* retention;
* privacy;
* geographic restrictions.

Decision-critical data should have stronger integrity requirements than ordinary informational context.

---

### 136. Decision Data Quality Governance

Where decisions depend on enterprise data, governance should define acceptable data-quality requirements.

Important dimensions include:

* accuracy;
* completeness;
* timeliness;
* consistency;
* provenance.

If required data quality cannot be established, autonomous execution may need to be suspended or escalated.

---

### 137. Memory Governance

Persistent memory influencing autonomous decisions should be governed.

Governance should define:

* what can be stored;
* who can modify it;
* how it is validated;
* retention;
* deletion;
* provenance;
* access control.

Memory should not become an uncontrolled source of decision authority.

---

### 138. Context Governance

Context sources should be classified according to trust.

```text
System Policy
→ Highest Trust

Approved Enterprise Data
→ Controlled Trust

User Input
→ Context-Dependent

External Content
→ Untrusted by Default
```

Governance should define how each category may influence autonomous decisions.

---

### 139. Model Governance

Models supporting autonomous decisions should be governed throughout their lifecycle.

Governance should cover:

* model approval;
* model version;
* provider;
* limitations;
* security testing;
* data handling;
* change management;

### 177. Strategic Governance Principle

### 213. Autonomous Decision Containment

Containment should focus first on preventing further actions.

Available controls may include:

* authorization revocation;
* credential revocation;
* tool disablement;
* network isolation;
* transaction blocking;
* session termination;
* agent suspension.

Containment should be possible without requiring the agent to recognize that it has been compromised.

### 231. Model Behavior Is Not Security Authorization

A model may determine:

> “This action appears appropriate.”

The authorization system must separately determine:

> “This action is permitted.”

```text id="p6j2yd"

      ↓
Authorization
      ↓
```

### 232. Agent Capability Is Not Agent Authority

An agent may possess the technical capability to perform an action without having authority to perform that action in a particular situation.

```text id="t7q1bc"

May initiate this payment

Execution:
This request passes validation
```

These are separate security concepts and should remain separately controlled.

### 238. Enterprise Autonomous Decision Operating Principle

The enterprise operating principle should be:

> **Autonomous intelligence may recommend and execute within defined boundaries, but enterprise security controls must independently determine and enforce what the system is authorized to do.**

The architecture should therefore maintain separation between:

```text id="j4w6zs"

     ↓

     ↓

     ↓

     ↓
Policy
     ↓

     ↓

     ↓

     ↓

```

No individual component should be able to bypass this chain for consequential actions.

---

### 239. Strategic Architecture Principle

The strategic principle for autonomous decision-making is:

> **Separate decision intelligence from decision authority.**

A secure enterprise architecture does not attempt to eliminate autonomous decision-making. Instead, it surrounds autonomy with independently enforced boundaries.

The model can reason.

The agent can plan.

The system can propose.

The policy engine determines what is permitted.

The authorization system determines whether the specific action is authorized.

The execution layer enforces the decision.

Monitoring determines whether behavior remains within expected boundaries.

Governance determines whether the authority should continue to exist.

This separation creates the architectural foundation for deploying autonomous decision-making while maintaining enterprise control, accountability, and security.
