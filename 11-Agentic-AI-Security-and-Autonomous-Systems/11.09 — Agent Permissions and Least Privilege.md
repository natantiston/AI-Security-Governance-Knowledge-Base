# 11.09 — Agent Permissions and Least Privilege

## Part 1 — Foundations and Core Concepts

### 1. Definition of Agent Permissions and Least Privilege

Agent permissions and least privilege define the boundaries of what an AI agent can access, use, modify, or execute within an enterprise environment.

**Agent permissions** specify the operations and resources available to an agent.

**Least privilege** requires that an agent receive only the minimum authority necessary to accomplish its approved purpose.

The fundamental relationship is:

```text id="p7m4x2"
Agent
  ↓
Required Capability
  ↓
Required Permission
  ↓
Minimum Necessary Authority
```

---

### 2. Agent Permissions as a Security Boundary

Permissions represent a critical boundary between an agent and enterprise resources.

```text id="k8q3v6"
Agent
  │
  ▼
Permission Boundary
  │
  ├── Resource
  ├── Action
  └── Scope
       │
       ▼
Protected Resource
```

A compromised agent should encounter permission boundaries before it can affect protected systems.

---

### 3. Least Privilege for AI Agents

Least privilege means granting an agent only the authority necessary to perform its approved function.

For example:

```text id="m5r8n2"
Invoice Agent

Needs:
✓ Read invoices
✓ Update invoice status

Does Not Need:
✗ Delete invoices
✗ Modify payroll
✗ Manage users
✗ Access HR records
```

Least privilege should be designed deliberately rather than assumed.

---

### 4. Why Least Privilege Is Critical for Agentic AI

Traditional applications often execute predictable workflows.

Agents can dynamically:

* select tools;
* retrieve information;
* call APIs;
* create actions;
* delegate tasks;
* interact with multiple systems.

Therefore, excessive permissions can create a much larger attack surface.

```text id="v4k9p3"
Agent Compromise
      ↓
Excessive Permissions
      ↓
Multiple Resources
      ↓
Multiple Actions
      ↓
Expanded Blast Radius
```

---

### 5. Permission vs Capability

A **capability** describes what an agent or system can technically do.

A **permission** describes what the agent is allowed to do.

```text id="x6m2q8"
Capability:
Can Delete Records

Permission:
Delete Records = DENIED
```

Technical capability should never automatically imply permission.

---

### 6. Permission vs Authority

Authority represents the broader ability to cause an enterprise action.

Permissions are one mechanism through which authority is technically constrained.

```text id="r8p3v5"
Agent Authority
      ↓
Permissions
      ↓
Resources + Actions
      ↓
Actual Access
```

A secure architecture should ensure that authority is expressed through controlled permissions.

---

### 7. Permission vs Authentication

Authentication establishes the identity of an agent.

It does not establish unrestricted permissions.

```text id="q4n7m2"
Authentication
"Who are you?"

        ↓

Permissions
"What are you allowed to access?"
```

A successfully authenticated agent can still have zero permission to access a particular resource.

---

### 8. Permission vs Authorization

Authorization is the decision process that determines whether a requested action is permitted.

Permissions represent the defined access boundaries evaluated during authorization.

```text id="n5v8k3"
Agent
 ↓
Requested Action
 ↓
Authorization
 ↓
Permission Evaluation
 ↓
ALLOW / DENY
```

---

### 9. Permission Scope

Permissions should be explicitly scoped.

Scope may include:

* resource;
* operation;
* data;
* tenant;
* environment;
* time;
* transaction;
* business function.

Example:

```text id="m7q2p9"
Agent:
AGT-INVOICE-001

Permission:
READ

Resource:
Invoice Database

Tenant:
Finance-EU

Environment:
Production
```

---

### 10. Resource Permissions

Permissions should define which resources an agent can access.

Examples include:

* databases;
* APIs;
* files;
* cloud resources;
* applications;
* queues;
* object stores;
* enterprise services.

An agent should not receive access to resources simply because they are reachable from its runtime.

---

### 11. Action Permissions

Permissions should distinguish between different operations.

```text id="c9m4r7"
Customer Database

READ      → ALLOW
CREATE    → ALLOW
UPDATE    → LIMITED
DELETE    → DENY
EXPORT    → DENY
```

This provides more precise control than simply granting database access.

---

### 12. Read Permissions

Read permissions allow an agent to retrieve information.

Read access should still be controlled according to:

* data sensitivity;
* resource;
* tenant;
* purpose;
* volume;
* environment.

Read-only access is safer than write access but is not inherently low risk.

---

### 13. Write Permissions

Write permissions allow an agent to modify enterprise state.

Examples include:

* creating records;
* updating records;
* changing configurations;
* submitting requests;
* modifying workflows.

Write permissions should normally receive greater scrutiny than read permissions.

---

### 14. Delete Permissions

Delete permissions can have irreversible consequences.

```text id="p3k8v5"
Agent
  ↓
DELETE
  ↓
Critical Data
  ↓
Potential Irreversible Impact
```

Delete authority should therefore be explicitly granted and strongly controlled.

---

### 15. Execute Permissions

Execute permissions allow an agent to cause a system or process to run.

Examples include:

* executing commands;
* triggering workflows;
* invoking administrative APIs;
* running scripts;
* initiating transactions.

Execution authority can be significantly more powerful than simple data access.

---

### 16. Administrative Permissions

Administrative permissions allow an agent to modify security or system configuration.

Examples include:

* creating users;
* changing roles;
* modifying security policies;
* changing infrastructure;
* altering access controls.

Administrative permissions should be treated as high-risk agent authority.

---

### 17. Permission Granularity

Permissions should be sufficiently granular to prevent unnecessary authority.

```text id="x7m4q2"
Coarse Permission:
"Access Finance"

Granular Permissions:
READ Invoices
READ Approved Vendors
UPDATE Invoice Status
CREATE Payment Request
DELETE Invoice = DENY
```

Granularity should reflect the sensitivity and consequence of the resource.

---

### 18. Resource-Level Least Privilege

An agent should receive access only to the resources required for its task.

```text id="v5p8n3"
Agent
 ├── Required Resource A → ✓
 ├── Required Resource B → ✓
 ├── Unrelated Resource C → ✗
 └── Restricted Resource D → ✗
```

---

### 19. Action-Level Least Privilege

Even when a resource is authorized, the agent should receive only the operations required.

```text id="k2r7m9"
Resource:
Customer Database

Agent:
Support Assistant

READ      → ✓
UPDATE    → ✓
DELETE    → ✗
ADMIN     → ✗
```

---

### 20. Data-Level Least Privilege

Permissions should also restrict which data an agent can access.

For example:

```text id="m8q4v6"
Customer Record

Name       → ✓
Email      → ✓
Address    → ✓
Password   → ✗
Payment PIN → ✗
```

The goal is to prevent unnecessary exposure even when the agent legitimately accesses the underlying resource.

---

### 21. Tenant-Level Least Privilege

Multi-tenant environments require strict tenant boundaries.

```text id="q6n3p8"
Agent A
  │
  └── Tenant A → ✓

Agent A
  │
  └── Tenant B → ✗
```

An agent should not inherit cross-tenant permissions simply because it operates within shared infrastructure.

---

### 22. Environment-Level Least Privilege

Permissions should distinguish environments.

```text id="r4m8k2"
Development → ✓
Testing     → ✓
Production  → ✗
```

An agent designed for development should not automatically possess production authority.

---

### 23. Time-Based Least Privilege

Permissions can be limited to specific periods.

```text id="p9v3m6"
Permission:
READ Production Data

Valid:
09:00–17:00

Outside Period:
DENY
```

Time restrictions reduce exposure from continuously active authority.

---

### 24. Temporary Permissions

Temporary permissions should be used when elevated access is required only for a specific task.

```text id="x5q8r3"
Normal State
   ↓
Temporary Permission
   ↓
Approved Task
   ↓
Permission Expires
   ↓
Normal State
```

Temporary authority is preferable to permanent privilege where operationally feasible.

---

### 25. Just-in-Time Agent Permissions

Just-in-time access provides permissions only when required.

```text id="k7m2p9"
Agent
  ↓
Requests Temporary Access
  ↓
Policy Evaluation
  ↓
Approval
  ↓
Permission Issued
  ↓
Task Completed
  ↓
Permission Revoked
```

This reduces the amount of standing authority.

---

### 26. Standing Privilege

Standing privilege exists continuously even when the agent does not need it.

Example:

```text id="n4r8v5"
Agent has:
ADMIN = Always Active
```

Standing privilege creates unnecessary exposure and should be minimized for high-risk capabilities.

---

### 27. Privilege Escalation

Privilege escalation occurs when an agent obtains authority beyond its approved permissions.

Examples include:

* acquiring administrator access;
* accessing restricted databases;
* obtaining another agent's credentials;
* changing its own authorization;
* exploiting an overly broad role.

```text id="q8m3p6"
Normal Permission
      ↓
Unauthorized Expansion
      ↓
Higher Privilege
```

---

### 28. Self-Escalation

An agent must not be able to grant itself additional authority.

```text id="v6k2r9"
Agent
  │
  X
  └── Grant itself ADMIN
```

Authorization changes must be controlled by an independent authority.

---

### 29. Permission Boundaries

Permission boundaries define the maximum authority available to an agent.

```text id="m5p8q3"
        Agent
          │
   ┌──────┴──────┐
   │ Permission  │
   │  Boundary   │
   └──────┬──────┘
          │
     Authorized
       Actions
```

Even if the agent requests an action outside the boundary, enforcement should block it.

---

### 30. Permission Inheritance

Permission inheritance can simplify management but creates risk if authority propagates unintentionally.

```text id="r3k7n8"
Parent Role
    ↓
Agent Role
    ↓
Inherited Permissions
```

Inherited permissions should be reviewed to ensure they do not create unnecessary authority.

---

### 31. Role-Based Agent Permissions

Role-based access control can associate agents with predefined roles.

Example:

```text id="x9m4q2"
Invoice-Agent
      ↓
Invoice-Processor Role
      ↓
Approved Invoice Permissions
```

Roles should be carefully scoped and governed.

---

### 32. Attribute-Based Agent Permissions

Attribute-based access control can evaluate multiple attributes.

```text id="p6v8k3"
Agent
+
Resource
+
Action
+
Tenant
+
Environment
+
Risk
      ↓
Permission Decision
```

This supports more dynamic authorization.

---

### 33. Policy-Based Permissions

Policy-based permission models allow enterprises to express detailed access requirements.

Example:

```text id="q5r2m9"
IF
  agent = AGT-SUPPORT-001
AND
  action = READ
AND
  resource = CUSTOMER_PROFILE
AND
  tenant = CURRENT_TENANT

THEN
  ALLOW
```

Policy-based controls are particularly useful for dynamic agent environments.

---

### 34. Permission Allowlisting

Only explicitly approved permissions should be available to sensitive agents.

```text id="n8k4p6"
Approved Permissions
├── READ Invoice
├── UPDATE Invoice Status
└── CREATE Payment Request

Everything Else
→ DENY
```

Allowlisting is generally safer than attempting to deny every possible dangerous operation individually.

---

### 35. Permission Denylists

Deny rules explicitly prohibit dangerous operations.

Examples:

```text id="m7q3v8"
DELETE Customer Database → DENY
CREATE Admin Account      → DENY
READ Password Store       → DENY
```

Denylists can complement allowlists but should not become the sole security strategy for high-risk agents.

---

### 36. Permission Separation

Different permissions should be separated when combining them creates excessive authority.

For example:

```text id="r8p5k2"
Agent A
  └── Create Payment Request

Agent B
  └── Approve Payment
```

This reduces the possibility that one compromised agent can independently initiate and approve a sensitive transaction.

---

### 37. Permission Dependencies

Some permissions create additional authority when combined.

For example:

```text id="x4m9q7"
READ Credential Store
      +
EXECUTE Authentication Service
      ↓
Potential Credential Abuse
```

Permission design should therefore consider combinations, not only individual permissions.

---

### 38. Permission Aggregation Risk

Multiple individually reasonable permissions may collectively create excessive authority.

```text id="k6p3v8"
READ Customer Data
+
EXPORT Data
+
External Network Access
      ↓
Potential Data Exfiltration Capability
```

Least privilege must therefore evaluate the combined permission set.

---

### 39. Permission and Agent Autonomy

Higher autonomy increases the importance of precise permission boundaries.

```text id="v2r8m5"
Low Autonomy
   ↓
Limited Permission Risk

High Autonomy
   ↓
Dynamic Decisions
   ↓
Greater Permission Risk
```

An autonomous agent should not receive broad permissions merely because automation is the business objective.

---

### 40. Permission and Tool Use

Tool access effectively extends an agent's permission set.

```text id="m8q4p1"
Agent
  ↓
Tool
  ↓
API
  ↓
Resource
```

A tool should therefore be evaluated based on the authority it can exercise on behalf of the agent.

---

### 41. Permission and API Access

API access should be governed by explicit permissions.

An agent authorized to call an API should not automatically be allowed to invoke every endpoint.

```text id="q7n3k9"
API
 ├── GET /invoices     → ✓
 ├── POST /invoices    → ✓
 ├── DELETE /invoices  → ✗
 └── ADMIN /users      → ✗
```

---

### 42. Permission and Database Access

Database access should be constrained by the agent's business purpose.

Controls can distinguish:

* database;
* schema;
* table;
* row;
* column;
* operation.

The goal is to prevent an agent from receiving unnecessary database authority.

---

### 43. Permission and External Connectivity

An agent's permissions should account for external communication.

For example:

```text id="p5m8r3"
Agent
  ↓
Read Sensitive Data
  +
External Network Access
  ↓
High Exfiltration Risk
```

Data access and network permissions should therefore be evaluated together.

---

### 44. Permission and Sensitive Data

Sensitive data should require appropriately restricted permissions.

Examples include:

* personal data;
* financial information;
* credentials;
* security information;
* regulated records;
* intellectual property.

The more sensitive the information, the stronger the permission boundary should be.

---

### 45. Permission and Irreversible Actions

Irreversible operations should receive stronger permission controls.

Examples include:

* permanent deletion;
* financial transfers;
* security policy changes;
* account termination;
* infrastructure destruction.

```text id="n4v7k2"
Irreversible Action
       ↓
Elevated Permission Requirement
       ↓
Additional Controls
```

---

### 46. Permission and Human Approval

Some permissions should require human approval before execution.

```text id="x8q3m5"
Agent
 ↓
Requests Sensitive Permission
 ↓
Policy Evaluation
 ↓
Human Approval
 ↓
Temporary Permission
 ↓
Action
 ↓
Permission Removed
```

This is particularly useful for high-impact operations.

---

### 47. Permission Revocation

Permissions must be revocable.

Revocation should occur when:

* the agent is compromised;
* business purpose changes;
* ownership changes;
* permissions are no longer required;
* credentials are compromised;
* the agent is retired.

```text id="r6m2p8"
Permission
   ↓
Revocation
   ↓
Access Blocked
```

---

### 48. Permission Expiration

Permissions should have lifecycle controls.

Temporary permissions should expire automatically.

Permanent permissions should also be periodically reviewed rather than assumed to remain appropriate indefinitely.

---

### 49. Core Principles of Agent Permissions and Least Privilege

The foundational principles are:

1. Grant only necessary authority.
2. Separate capability from permission.
3. Separate authentication from access.
4. Scope permissions to specific resources and actions.
5. Minimize standing privilege.
6. Prefer temporary authority for elevated operations.
7. Prevent agents from modifying their own permissions.
8. Consider combinations of permissions, not only individual permissions.
9. Apply stronger controls to sensitive and irreversible actions.
10. Continuously review and revoke unnecessary authority.

---

### 50. Core Principle of Agent Permissions and Least Privilege

The fundamental principle is:

> **An AI agent must receive only the minimum permissions necessary to perform its explicitly approved business function, with authority constrained by resource, action, data, environment, tenant, time, and risk, and with no ability for the agent to independently expand, transfer, or redefine its own permissions.**

The core security model is:

```text id="c7m4v9"
                    Agent
                      │
                      ▼
              Approved Purpose
                      │
                      ▼
              Required Capability
                      │
                      ▼
              Minimum Permission
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       Resource      Action      Scope
          │           │           │
          └───────────┼───────────┘
                      ▼
             Authorization
                      │
               ┌──────┴──────┐
               ▼             ▼
             ALLOW          DENY
               │
               ▼
          Enforcement
               │
               ▼
            Resource
```

The critical principle is:

> **An agent should be capable of performing only what it needs, authorized to perform only what it is permitted to do, and technically prevented from expanding that authority on its own.**

## Part 2 — Technical Security and Control Mechanisms

### 51. Agent Permission Security Control Architecture

Agent permissions should be implemented through a layered technical control architecture that separates the agent's requested action from the mechanisms that determine and enforce its permitted authority.

```text id="q7m3x8"
                    AI Agent
                       │
                       ▼
                Action Request
                       │
                       ▼
             ┌──────────────────┐
             │ Identity Context │
             └────────┬─────────┘
                      │
                      ▼
             ┌──────────────────┐
             │ Permission       │
             │ Policy Engine    │
             └────────┬─────────┘
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
    Resource         Action         Context
       │              │              │
       └──────────────┼──────────────┘
                      ▼
                Allow / Deny
                      │
                      ▼
              Enforcement Point
                      │
                      ▼
                 Resource
```

The agent should not control the permission decision.

---

### 52. Agent Permission Identity Binding

Permissions should be bound to an authenticated agent identity.

```text id="m4p8r2"
Agent Identity
      ↓
Permission Assignment
      ↓
Authorized Resource
      ↓
Authorized Action
```

This prevents one agent from simply presenting another agent's permissions.

---

### 53. Fine-Grained Permission Controls

Permissions should be sufficiently granular to distinguish specific resources and actions.

```text id="v6k2n9"
Agent
 ├── READ Invoice A       ✓
 ├── READ Invoice B       ✓
 ├── UPDATE Invoice A     ✓
 ├── DELETE Invoice A     ✗
 └── ADMIN Finance DB     ✗
```

Granularity should increase as the potential impact of an action increases.

---

### 54. Independent Permission Decision Service

Permission decisions should preferably be made by an independent policy component.

```text id="r5m8q3"
Agent
  │
  │ Request
  ▼
Permission Decision Service
  │
  ├── Identity
  ├── Resource
  ├── Action
  ├── Context
  └── Policy
  │
  ▼
ALLOW / DENY
```

This reduces the risk that a compromised agent can manipulate its own permissions.

---

### 55. Permission Allowlisting

Sensitive agents should use explicit permission allowlists.

```text id="x3q7m5"
Approved Permissions
├── READ invoices
├── UPDATE invoice status
└── CREATE payment request

All Other Permissions
→ DENY
```

Allowlisting reduces unintended access paths.

---

### 56. Resource Allowlisting

Resources should be explicitly approved for agent access.

```text id="k8m4p2"
Agent
 ├── Invoice API       ✓
 ├── Vendor API        ✓
 ├── HR Database       ✗
 ├── IAM System        ✗
 └── Payroll System    ✗
```

Resource reachability should not automatically imply authorization.

---

### 57. Action Allowlisting

Authorized actions should also be explicitly defined.

```text id="n6r2v8"
Invoice API

GET    → ✓
POST   → ✓
PUT    → Limited
DELETE → ✗
ADMIN  → ✗
```

This prevents an agent from converting a resource-level permission into unrestricted control.

---

### 58. Permission Segmentation

Permissions should be separated by security domain.

```text id="p4k9m3"
Finance Permissions
       │
       X
       │
HR Permissions

Security Permissions
       │
       X
       │
Customer Permissions
```

An agent should not receive cross-domain permissions unless explicitly required.

---

### 59. Permission Scope Validation

Every access request should be evaluated against its approved scope.

```text id="q8m3v6"
Agent
+
Resource
+
Action
+
Tenant
+
Environment
+
Time
      ↓
Permission Evaluation
```

A permission valid in one environment or tenant should not automatically apply elsewhere.

---

### 60. Permission Parameter Validation

Permission enforcement should validate relevant operation parameters.

For example:

```text id="v5r8k2"
Agent:
CREATE PAYMENT

Amount:
€2,000 → ALLOW

Amount:
€50,000 → DENY / APPROVAL
```

Authorization should therefore consider not only the action but also its parameters.

---

### 61. Transaction Permission Limits

Financial or other high-impact permissions should include transaction limits.

Possible limits include:

* maximum transaction value;
* maximum daily value;
* maximum number of transactions;
* maximum cumulative value;
* approved recipients.

---

### 62. Cumulative Permission Limits

An agent's authority should be evaluated across cumulative activity.

```text id="m7p4x9"
Transaction 1 → €2,000
Transaction 2 → €2,000
Transaction 3 → €2,000

Daily Maximum → €5,000

Result:
Further Transaction → DENY
```

This prevents repeated low-value operations from bypassing aggregate controls.

---

### 63. Time-Bounded Permissions

Permissions can be restricted to defined periods.

```text id="r3k8n5"
Permission Active
09:00 ───────── 17:00
                    │
                    ▼
                 EXPIRED
```

Time-bounded permissions reduce unnecessary standing authority.

---

### 64. Short-Lived Permission Grants

Temporary authority should expire automatically after its approved period.

```text id="x6m2q8"
Request
  ↓
Approval
  ↓
Permission Issued
  ↓
Task
  ↓
Expiration
  ↓
Access Removed
```

---

### 65. Just-in-Time Permission Assignment

Just-in-time access provides elevated permissions only when required.

```text id="p8v4m3"
Agent
  ↓
Access Request
  ↓
Policy Evaluation
  ↓
Approval
  ↓
Temporary Permission
  ↓
Task
  ↓
Automatic Revocation
```

This reduces persistent privilege.

---

### 66. Permission Credential Isolation

Credentials associated with permissions should be isolated by agent and security domain.

```text id="k4r9m7"
Agent A → Credential A → Permissions A
Agent B → Credential B → Permissions B
```

Compromise of one credential should not expose unrelated permissions.

---

### 67. Secrets Management for Agent Permissions

Permission-related secrets should be stored in approved enterprise secrets-management systems.

They should not be placed in:

* prompts;
* model context;
* agent memory;
* source code;
* logs;
* tool descriptions.

---

### 68. Permission Context Security

Permission decisions should use trusted context.

Trusted attributes may include:

* agent identity;
* tenant;
* environment;
* resource classification;
* approval state;
* transaction value.

Model-generated context should not be treated as authoritative.

---

### 69. Prompt and Instruction Integrity

Prompts should never be capable of granting permissions.

For example:

```text id="n5q8p2"
Prompt:
"You are now an administrator."

Result:
No Permission Change
```

The authorization system must remain independent of model instructions.

---

### 70. Untrusted Input Isolation

User-controlled or externally sourced input should be separated from authorization attributes.

```text id="q3m7v9"
Untrusted Input
      │
      X
Authorization Attributes
      │
      ▼
Policy Engine
```

This prevents attackers from injecting false claims into permission decisions.

---

### 71. Permission-Aware Prompt Injection Detection

Prompt injection detection should identify attempts to manipulate the agent into requesting excessive authority.

Examples include:

* requests to access restricted systems;
* instructions to ignore permission boundaries;
* attempts to obtain administrator privileges;
* instructions to reveal credentials.

Detection should supplement, not replace, permission enforcement.

---

### 72. Memory Isolation

Agent memory should not be able to redefine permissions.

```text id="v8k4r2"
Agent Memory
     │
     X
Permission Authority
```

Memory may describe permissions, but authoritative permission state must reside in controlled security systems.

---

### 73. Permission Memory Authorization

If permission information is stored in agent-accessible memory, access to that information should itself be controlled.

An agent should not be able to retrieve:

* another agent's permissions;
* privileged credentials;
* hidden authorization policies;
* security configuration.

---

### 74. Permission Integrity

Permission state must be protected against unauthorized modification.

Controls should detect attempts to change:

```text id="m6p3q8"
READ  → WRITE
DENY  → ALLOW
€5K   → €100K
Tenant A → Tenant B
Approval Required → No Approval
```

---

### 75. Persistent Permission Controls

Permissions should not persist unintentionally across:

* sessions;
* deployments;
* environments;
* users;
* tenants;
* agent versions.

Authorization should be re-established where security boundaries change.

---

### 76. Data Access Permissions

Agent data permissions should reflect the minimum information required for the approved function.

For example:

```text id="r9m5k2"
Support Agent

Customer Name      ✓
Customer Email     ✓
Customer Address   ✓
Payment Card       ✗
Password           ✗
Security Token     ✗
```

---

### 77. Data Minimization

Permission architecture should limit both the number of resources and the amount of data accessible.

```text id="x4v8p6"
Available Data
      ↓
Business Requirement
      ↓
Minimum Required Data
      ↓
Agent
```

Data minimization reduces the consequences of compromise.

---

### 78. Field-Level Permission Controls

Sensitive fields should receive separate controls where appropriate.

Examples include:

* national identifiers;
* payment information;
* credentials;
* medical records;
* security secrets;
* confidential business data.

Field-level controls can prevent an agent from accessing sensitive information unnecessarily.

---

### 79. Tenant Isolation

Permissions must enforce tenant boundaries.

```text id="q7m3r8"
Agent
 │
 ├── Tenant A → ✓
 │
 ├── Tenant B → ✗
 │
 └── Tenant C → ✗
```

Cross-tenant access should require explicit authorization.

---

### 80. Session Isolation

Permissions should be bound to the appropriate session context where required.

This prevents authorization state from being accidentally reused between:

* users;
* tasks;
* sessions;
* tenants.

---

### 81. Network Segmentation

Permission failures should default toward secure behavior.

```text id="r8m3q6"

       ↓
```

### 117. Core Engineering Principle

The fundamental engineering principle is:

> **Agent permissions must be explicitly defined, minimally scoped, independently evaluated, technically enforced, continuously monitored, and revocable, with no mechanism through which the agent can expand, transfer, or redefine its own authority.**

The complete technical control chain is:

```text id="c4q7m9"
                 Agent
                   │
                   ▼
             Action Request
                   │
                   ▼
           Authenticated Identity
                   │
                   ▼
        ┌─────────────────────────┐
        │ Permission Policy Engine│
        └────────────┬────────────┘
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
     Resource       Action       Context
        │            │            │
        └────────────┼────────────┘
                     ▼
              Risk / Policy
                 Evaluation
                     │
                ┌────┴────┐
                ▼         ▼
             ALLOW       DENY
                │
                ▼
         Enforcement Point
                │
                ▼
             Resource
                │
                ▼
        Logging / Monitoring
```

**The security objective is not merely to ensure that an agent has permissions. It is to ensure that every permission is necessary, bounded, independently enforced, observable, temporary where appropriate, and incapable of becoming unrestricted authority through autonomous behavior.**

# Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. Agent Permission Governance Framework

Agent permissions should be governed through an enterprise framework that defines how permissions are requested, approved, assigned, reviewed, monitored, changed, and revoked.

```text id="g8m4p2"
Business Purpose
      ↓
Permission Requirement
      ↓
Risk Assessment
      ↓
Approval
      ↓
Permission Assignment
      ↓
Monitoring
      ↓
Periodic Review
      ↓
Revocation / Renewal
```

Governance should ensure that technical access remains aligned with the agent's approved business purpose.

---

### 119. Agent Permission Ownership and Accountability

Every production agent should have an accountable owner responsible for its permission profile.

The owner should understand:

* why permissions are required;
* which resources are accessible;
* what actions are authorized;
* what risks exist;
* when permissions must be reviewed;
* when access should be removed.

An agent should never be treated as an owner of its own authority.

---

### 120. Enterprise Agent Permission Inventory

The organization should maintain an inventory of agent permissions.

The inventory should identify, where applicable:

| Attribute        | Example            |
| ---------------- | ------------------ |
| Agent            | AGT-FIN-001        |
| Business purpose | Invoice processing |
| Resource         | Invoice API        |
| Action           | Read/Update        |
| Scope            | Finance-EU         |
| Environment      | Production         |
| Owner            | Finance Operations |
| Risk tier        | High               |
| Approval         | Required           |
| Review date      | Defined            |

The inventory provides the foundation for access governance and auditability.

---

### 121. Agent Permission Classification

Permissions should be classified according to their security and business impact.

A basic classification may include:

```text id="m5q8r3"
Low
 ↓
Moderate
 ↓
High
 ↓
Critical
```

Classification should consider the consequences of misuse rather than merely the technical type of permission.

---

### 122. Permission Risk Tiering

Permission risk should consider factors such as:

* resource sensitivity;
* action sensitivity;
* data sensitivity;
* transaction value;
* reversibility;
* external exposure;
* privilege level;
* autonomy of the agent.

For example:

```text id="v7k3p9"
READ Public Information
→ Low

UPDATE Customer Record
→ Moderate

DELETE Critical Data
→ High

Modify IAM Policy
→ Critical
```

---

### 123. Permission Approval Governance

Permission assignments should follow defined approval requirements.

```text id="p4m8x2"
Permission Request
      ↓
Risk Classification
      ↓
Required Approver
      ↓
Approval / Rejection
      ↓
Assignment
```

High-risk permissions should require stronger approval than routine permissions.

---

### 124. Permission Purpose Limitation

Every permission should have a documented business purpose.

Example:

```text id="q6r2m8"
Purpose:
Process approved invoices

Permission:
UPDATE Invoice Status

Unrelated:
Modify Payroll
→ Not Justified
```

Permissions without a legitimate business purpose should not be granted.

---

### 125. Agent Authority Governance

Governance should distinguish between:

* what an agent can technically perform;
* what it is authorized to perform;
* what it is permitted to perform under policy.

The approved authority should be documented and enforceable.

---

### 126. Agent-to-Resource Access Governance

Access relationships between agents and resources should be governed explicitly.

```text id="k8p3v5"
Agent
  │
  ├── Resource A → Approved
  ├── Resource B → Approved
  └── Resource C → Not Approved
```

Resource access should not emerge accidentally through inherited infrastructure privileges.

---

### 127. Agent Permission Access Reviews

Permissions should undergo periodic access reviews.

Reviewers should determine:

* whether access is still required;
* whether scope remains appropriate;
* whether permissions are excessive;
* whether the business purpose has changed;
* whether permissions should be removed.

---

### 128. Least-Privilege Governance

Least privilege should be an explicit governance requirement rather than an informal engineering preference.

Governance should require evidence that:

```text id="n4m7q2"
Business Need
      ↓
Required Access
      ↓
Minimum Permission
```

was considered before permission assignment.

---

### 129. Agent Capability Governance

Agent capabilities should be documented separately from permissions.

For example:

```text id="x5r8m3"
Capability:
Can execute SQL

Permission:
Production Database = DENIED
```

This distinction prevents technical capability from being interpreted as approved authority.

---

### 130. Permission Combination Governance

Governance should evaluate dangerous combinations of permissions.

For example:

```text id="p7k4v9"
READ Customer Data
+
EXPORT Data
+
External Network Access
```

may create significant data-exfiltration capability even though each permission appears reasonable individually.

---

### 131. Permission Inheritance Governance

Inherited permissions should be identified and reviewed.

Governance should prevent agents from receiving unnecessary authority through:

* inherited roles;
* group membership;
* service accounts;
* cloud roles;
* shared credentials.

---

### 132. Permission Delegation Governance

Delegated permissions should have explicit governance.

Requirements may include:

* approved delegator;
* approved recipient;
* delegated scope;
* expiration;
* purpose;
* maximum delegation depth.

---

### 133. Permission Propagation Governance

Permissions should not propagate automatically across agent chains.

```text id="m9q3r7"
Agent A
  ↓
Agent B
  ↓
Agent C
```

Each transfer should preserve the original authorization boundary.

### 134. Data Governance for Agent Permissions

### 176. Enterprise Security Principle

Enterprise agent permission governance should enforce:

> **No agent should receive access merely because a technical capability exists, a role permits it indirectly, or the model requests it. Permission must be explicitly justified, risk assessed, approved where required, technically enforced, monitored, and revocable.**

---

### 177. Strategic Governance Principle

The strategic governance principle is:

> **Agent permissions must remain subordinate to enterprise policy, business purpose, risk appetite, and independently enforced authorization boundaries throughout the complete agent lifecycle.**

Agent permissions should therefore be treated as a continuously governed security asset rather than as a one-time application configuration.
