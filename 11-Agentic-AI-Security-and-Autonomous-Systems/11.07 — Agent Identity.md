# 11.07 — Agent Identity

## Part 1 — Foundations and Core Concepts

### 1. Definition of Agent Identity

Agent identity is the unique, attributable representation of an AI agent within an enterprise environment.

It establishes **which agent is participating in an interaction**, independently of the model's generated text or the human user who initiated the broader workflow.

An agent identity may represent:

* a specific AI agent;
* an agent application;
* an autonomous workload;
* an agent deployment;
* an agent instance;
* a specialized business-function agent.

Agent identity provides the foundation for authentication, authorization, accountability, monitoring, and lifecycle governance.

---

### 2. Agent Identity as a Security Primitive

Identity is a fundamental security primitive for autonomous systems.

Without reliable identity, an enterprise cannot reliably determine:

```text
Who is this agent?
        ↓
What agent is operating?
        ↓
Which deployment is running?
        ↓
Who owns it?
        ↓
What environment is it operating in?
        ↓
Which actions did it initiate?
```

Agent identity therefore becomes foundational to every subsequent security control.

---

### 3. Why Agent Identity Is Different from User Identity

An AI agent may act on behalf of a human user without being identical to that user.

For example:

```text
Human User
     │
     │ Request
     ▼
AI Agent
     │
     │ Autonomous Action
     ▼
Enterprise System
```

The enterprise needs to know both:

* **who the human is**, and
* **which agent actually performed the action**.

Replacing agent identity with user identity can destroy important accountability information.

---

### 4. Human Identity vs Agent Identity

A human identity represents a person.

An agent identity represents an autonomous software entity.

| Identity                | Represents                    | Example                      |
| ----------------------- | ----------------------------- | ---------------------------- |
| Human Identity          | Person                        | Employee-4821                |
| Service Identity        | Application/service           | Payroll-Service              |
| Agent Identity          | Autonomous AI workload        | Payroll-Agent-07             |
| Agent Instance Identity | Specific execution/deployment | Payroll-Agent-07-Instance-03 |

These identities may be related but should not be treated as interchangeable.

---

### 5. Agent Identity and Accountability

Every significant autonomous action should be attributable to an identifiable agent.

For example:

```text
User
 │
 ▼
Agent A
 │
 ├── Agent B
 │     └── Tool
 │
 └── Agent C
       └── Database
```

Security records should allow investigators to reconstruct which agent initiated each stage.

This is particularly important when autonomous systems perform multi-step operations.

---

### 6. Agent Identity and Ownership

An agent identity should be associated with an accountable owner.

Ownership may include:

* business owner;
* technical owner;
* security owner;
* AI governance owner;
* operating team.

The identity itself should not merely say **what the agent is**; the enterprise should also know **who is responsible for it**.

---

### 7. Agent Identity Attributes

An enterprise agent identity may contain attributes such as:

```text
Agent ID
Agent Name
Agent Type
Business Owner
Technical Owner
Business Purpose
Environment
Risk Tier
Deployment
Lifecycle Status
Capabilities
Data Classification
Communication Relationships
```

Not every attribute needs to be exposed to the model or transmitted to other agents.

---

### 8. Unique Agent Identification

Each production agent should have a unique identifier.

Example:

```text
Agent ID:
AGT-FIN-0427
```

The identifier should be:

* unique;
* stable;
* attributable;
* centrally managed;
* lifecycle-aware.

Duplicate or ambiguous identities create significant accountability problems.

---

### 9. Agent Identity vs Agent Name

A human-readable agent name is not sufficient as a security identity.

For example:

```text
"Finance Assistant"
```

may identify several deployments.

A security identity should distinguish them:

```text
Agent ID: AGT-FIN-0427
Deployment: PROD-EU
Instance: 03
Environment: Production
```

Names support usability; authoritative identifiers support security.

---

### 10. Agent Instance Identity

An enterprise may need to distinguish between the logical agent and individual execution instances.

```text
Logical Agent
AGT-FIN-0427
      │
      ├── Instance 01
      ├── Instance 02
      └── Instance 03
```

This allows security teams to determine whether suspicious behavior originates from:

* the agent design;
* a specific deployment;
* a particular execution instance;
* a compromised runtime.

---

### 11. Agent Identity Lifecycle

Agent identity should exist throughout the agent lifecycle.

```text
Registration
    ↓
Activation
    ↓
Operation
    ↓
Modification
    ↓
Suspension
    ↓
Retirement
```

Identity records should be updated as the agent changes.

An identity should not remain active indefinitely after an agent has been retired.

---

### 12. Agent Registration

Before an agent becomes operational, it should be registered with the enterprise's authoritative agent inventory.

Registration should establish:

* identity;
* purpose;
* ownership;
* environment;
* capabilities;
* risk classification;
* lifecycle status.

This creates an authoritative reference for the agent.

---

### 13. Agent Identity Authority

The organization should define an authoritative source for agent identity.

Potential sources include:

* enterprise IAM;
* workload identity platforms;
* cloud identity systems;
* service registries;
* agent registries.

There should be a clear distinction between:

```text
Authoritative Identity
        ≠
Agent-Generated Identity Claim
```

An agent should not be able to create an authoritative identity merely by declaring one.

---

### 14. Identity Provenance

Identity provenance establishes where an identity originated and how it was established.

For example:

```text
Agent Identity
     │
     ├── Registered By
     ├── Registration Date
     ├── Owner
     ├── Deployment
     └── Identity Provider
```

Provenance strengthens accountability and supports investigations.

---

### 15. Agent Identity Context

Identity should be understood as more than a simple identifier.

Relevant context may include:

* agent role;
* business purpose;
* environment;
* tenant;
* deployment;
* lifecycle state;
* ownership;
* risk classification.

This context helps downstream security systems make informed decisions.

---

### 16. Agent Role Identity

Agents may perform specialized business roles.

Examples include:

* security analysis agent;
* finance processing agent;
* HR information agent;
* customer-support agent;
* infrastructure operations agent.

Role information can help distinguish the intended function of an agent.

However:

> **An agent's role does not automatically determine its authority.**

Authority must remain separately governed and enforced.

---

### 17. Agent Identity and Business Purpose

Agent identity should be associated with a defined business purpose.

For example:

```text
Agent:
Customer-Support-Agent-01

Purpose:
Resolve customer support cases.

Not inherently authorized:
- Issue refunds
- Modify payment details
- Change account privileges
```

Purpose establishes context for governance but does not replace security controls.

---

### 18. Agent Identity and Environment

The same logical agent may operate in multiple environments.

```text
Development
    │
    └── Agent A

Testing
    │
    └── Agent A

Production
    │
    └── Agent A
```

These environments should be distinguishable because an identity operating in development should not automatically be trusted as a production identity.

---

### 19. Agent Identity and Tenant

In multi-tenant systems, identity should include tenant context.

For example:

```text
Tenant A
 └── Agent-A1

Tenant B
 └── Agent-B1
```

The identity system should prevent an agent associated with one tenant from being ambiguously represented as belonging to another.

---

### 20. Agent Identity and Deployment

An agent identity should be associated with the deployment from which it operates.

Deployment context can include:

* cloud account;
* cluster;
* namespace;
* host;
* container;
* workload;
* region;
* environment.

This enables security teams to correlate agent activity with its underlying infrastructure.

---

### 21. Agent Identity and Workload Identity

Agent identity can be anchored to workload identity.

```text
Agent
  │
  ▼
Application Workload
  │
  ▼
Runtime Identity
  │
  ▼
Enterprise Identity Infrastructure
```

This provides a stronger foundation than relying on identifiers stored inside application configuration.

---

### 22. Logical Agent Identity

A logical agent represents the persistent identity of an agent function or application.

Example:

```text
AGT-SEC-001
Security Investigation Agent
```

The logical identity can remain consistent even when the underlying runtime instances change.

---

### 23. Runtime Agent Identity

Runtime identity identifies the specific execution environment operating at a particular time.

```text
Logical Agent:
AGT-SEC-001

Runtime:
K8S-POD-88421

Execution:
RUN-20260905-1837
```

Runtime identity supports forensic analysis and precise attribution.

---

### 24. Session Identity

An agent may participate in multiple sessions.

```text
Agent Identity
      │
      ├── Session 001
      ├── Session 002
      └── Session 003
```

Session identity allows security teams to distinguish separate interactions and execution contexts.

---

### 25. Execution Identity

A single session may involve multiple executions or actions.

For example:

```text
Agent
  │
  └── Session
        │
        ├── Execution 01
        ├── Execution 02
        └── Execution 03
```

Execution identity supports detailed traceability without requiring a new permanent identity for every action.

---

### 26. Identity Hierarchy

Enterprise agent identity can therefore be represented as a hierarchy:

```text
Enterprise
   │
   ▼
Logical Agent
   │
   ▼
Deployment
   │
   ▼
Runtime Instance
   │
   ▼
Session
   │
   ▼
Execution
```

This hierarchy allows activity to be traced from the enterprise agent record down to a specific execution.

---

### 27. Agent Identity vs Model Identity

An AI model is not necessarily the same thing as an agent.

```text
Model
  │
  ▼
Agent Application
  │
  ├── Instructions
  ├── Memory
  ├── Tools
  ├── Policies
  └── Runtime
```

The same underlying model may operate inside many different agents.

Therefore:

> **Model identity must not be confused with agent identity.**

---

### 28. Agent Identity vs Model Provider

The provider of an underlying model does not establish the identity of the enterprise agent using that model.

For example:

```text
Model Provider
      │
      ▼
Foundation Model
      │
      ▼
Enterprise Agent
```

The enterprise must still maintain its own identity for the agent.

---

### 29. Agent Identity vs User Intent

A user may initiate a workflow, but the agent may independently make subsequent decisions.

Therefore:

```text
User Intent
     ≠
Agent Identity
     ≠
Agent Decision
     ≠
Agent Action
```

Each layer should remain attributable.

This distinction becomes increasingly important as agent autonomy increases.

---

### 30. Agent Identity and Delegation

When Agent A delegates a task to Agent B, both identities must remain visible.

```text
Agent A
   │
   │ Delegates
   ▼
Agent B
```

The resulting activity should not appear simply as:

```text
Agent A → Enterprise System
```

if Agent B actually performed the action.

Attribution must preserve the complete chain.

---

### 31. Identity Propagation

When an agent communicates with another agent, identity context may need to propagate through the workflow.

For example:

```text
Agent A
   │
   ▼
Agent B
   │
   ▼
Agent C
```

The system should preserve enough identity information to establish:

* original initiator;
* immediate sender;
* receiving agent;
* executing agent.

Identity propagation should not become an uncontrolled transfer of authority.

---

### 32. Original Initiator vs Executing Agent

A critical distinction is between the entity that initiated a workflow and the entity that actually performed an action.

```text
Human
  │
  ▼
Agent A  ← Original AI initiator
  │
  ▼
Agent B  ← Executing agent
  │
  ▼
Enterprise System
```

Audit records should preserve both identities.

This prevents the system from incorrectly attributing every downstream action to the original requester.

---

### 33. Identity Chain of Custody

For high-impact workflows, identity should be preserved throughout the execution chain.

```text
Human
  ↓
Agent A
  ↓
Agent B
  ↓
Tool
  ↓
Enterprise System
```

Each transition should be attributable.

This provides an identity chain of custody for autonomous operations.

---

### 34. Agent Identity and Accountability Boundaries

Identity boundaries should correspond to meaningful security boundaries.

If two agents have different:

* owners;
* purposes;
* risk levels;
* data scopes;
* operating environments;

they should normally have distinguishable identities.

Combining them under a single identity can obscure security responsibility.

---

### 35. Shared Agent Identities

Shared identities can create significant accountability problems.

For example:

```text
Agent A ─┐
Agent B ─┼──► Shared Identity
Agent C ─┘
```

If the identity performs a sensitive operation, investigators may be unable to determine which agent actually initiated it.

Individual attribution should therefore be preferred for security-relevant autonomous workloads.

---

### 36. Identity Collision

Identity collision occurs when two separate agents are represented by the same or ambiguous identity.

Potential consequences include:

* incorrect authorization;
* incorrect audit records;
* confused incident response;
* accidental privilege inheritance;
* inability to distinguish compromised workloads.

Identity uniqueness is therefore a foundational security requirement.

---

### 37. Identity Spoofing

An attacker may attempt to represent one agent as another.

Examples include:

* forged identity claims;
* stolen credentials;
* manipulated metadata;
* compromised workloads;
* fraudulent agent registration.

Identity architecture should make impersonation difficult and detectable.

---

### 38. Identity Confusion

Identity confusion occurs when the system cannot clearly distinguish:

* human;
* agent;
* service;
* model;
* agent instance;
* delegated agent.

For example:

```text
"John approved the transaction."

But the actual chain was:

John
 ↓
Finance Agent
 ↓
Payment Agent
 ↓
Payment System
```

The record should not collapse the entire chain into the human identity.

---

### 39. Identity and Non-Repudiation

Reliable agent identity contributes to stronger attribution of autonomous actions.

For high-impact operations, identity records should support evidence showing:

```text
Which agent?
Which instance?
Which session?
Which request?
Which owner?
Which workflow?
Which downstream action?
```

Identity alone does not prove that an action was legitimate, but it establishes who or what performed it.

---

### 40. Identity and Auditability

Agent identity should be embedded in security-relevant audit records.

A useful event structure may include:

```text
Timestamp
Agent ID
Instance ID
Session ID
Request ID
Owner
Environment
Action
Target
Result
```

This allows security teams to correlate agent behavior across systems.

---

### 41. Identity and Observability

Agent identity should be consistently represented across:

* application logs;
* API gateways;
* identity systems;
* SIEM;
* workflow engines;
* databases;
* tool gateways;
* cloud infrastructure.

Inconsistent identity representations make cross-system investigation difficult.

---

### 42. Identity Correlation

Different infrastructure systems may use different identifiers.

For example:

```text
Agent ID:
AGT-SEC-001

Workload ID:
WL-88421

Container:
POD-33218

Session:
SES-98172

Trace:
TRACE-77123
```

These identifiers should be correlatable.

Identity correlation creates a continuous chain from logical agent to infrastructure execution.

---

### 43. Identity and Security Boundaries

Identity should correspond to security boundaries wherever meaningful.

For example:

```text
Development Agent
       X
Production Agent
```

A production system should not automatically accept an identity originating from a development environment.

Identity therefore contributes directly to environment isolation.

---

### 44. Identity State

Agent identities should have explicit lifecycle states.

Example:

```text
REGISTERED
     ↓
ACTIVE
     ↓
SUSPENDED
     ↓
REACTIVATED
     ↓
RETIRED
```

A retired or suspended identity should not continue operating as though it were active.

---

### 45. Identity Suspension

An agent identity may need to be temporarily suspended because of:

* suspected compromise;
* policy violation;
* security investigation;
* operational issue;
* ownership change;
* unauthorized behavior.

Suspension should be independently enforceable and should not depend on the agent's cooperation.

---

### 46. Identity Revocation

Identity revocation permanently or administratively invalidates an agent's identity.

Revocation may be required when:

* the agent is retired;
* the workload is compromised;
* ownership is terminated;
* the identity is exposed;
* the agent is replaced.

Revocation should propagate to relevant enterprise security systems.

---

### 47. Identity Recovery and Reissuance

After a security incident, simply restoring an old identity may be unsafe.

A recovery process may require:

```text
Compromise
   ↓
Suspend
   ↓
Investigate
   ↓
Remediate
   ↓
Validate
   ↓
Reissue / Reactivate
```

Identity recovery should therefore be controlled as part of the agent lifecycle.

---

### 48. Identity Governance

Agent identity should be governed throughout its lifecycle.

Governance should establish:

* who can create identities;
* who can modify identities;
* who can suspend identities;
* who can revoke identities;
* who owns identities;
* how identity records are audited;
* how inactive identities are detected.

Identity governance provides the administrative foundation for secure autonomous systems.

---

### 49. Core Principles of Agent Identity

The foundational principles are:

1. Every production agent should have a unique identity.
2. Agent identity should be distinguishable from human identity.
3. Agent identity should be distinguishable from model identity.
4. Identity should be attributable to an accountable owner.
5. Identity should persist across the appropriate lifecycle.
6. Runtime instances should remain traceable to their logical agent.
7. Delegated workflows should preserve identity chains.
8. Shared identities should be avoided where they weaken accountability.
9. Identity state should be independently enforceable.
10. Identity should support audit, monitoring, and incident response.

---

### 50. Core Principle of Agent Identity

The fundamental security principle is:

> **Every autonomous AI agent must possess a unique, attributable, lifecycle-managed identity that allows the enterprise to distinguish the agent from its human users, underlying models, execution environments, and delegated agents.**

The identity model should preserve the complete chain:

```text
Human / Business Actor
          ↓
    Initiating Agent
          ↓
    Delegated Agent
          ↓
   Runtime Instance
          ↓
      Execution
          ↓
 Enterprise System
```

The essential rule is:

> **Identity establishes who or what is acting; it does not by itself establish what that entity is permitted to do.**

This separation is foundational for the next layers of agent security: authentication, authorization, permissions, and least-privilege enforcement.

## Part 2 — Technical Security and Control Mechanisms

### 51. Agent Identity Security Control Architecture

Agent identity security requires a dedicated control architecture that establishes, validates, protects, and monitors agent identities throughout their operational lifecycle.

A representative architecture is:

```text
                    ┌──────────────────────┐
                    │ Enterprise Identity  │
                    │ Authority / IAM       │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Agent Identity       │
                    │ Registry             │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Agent Identity        │
                    │ Provider              │
                    └──────────┬───────────┘
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
        Authentication   Authorization      Credential
           Controls          Controls         Controls
             │                 │                 │
             └─────────────────┼─────────────────┘
                               ▼
                    ┌──────────────────────┐
                    │ Agent Runtime        │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │ Monitoring / Audit   │
                    └──────────────────────┘
```

Identity must be an independently managed security control rather than merely an attribute supplied by the agent application.

---

### 52. Agent Identity Registration Controls

Agent registration should require controlled creation of an authoritative identity.

Registration should validate:

* agent purpose;
* owner;
* deployment;
* environment;
* business function;
* risk classification;
* expected capabilities;
* identity requirements.

Unauthorized applications should not be able to self-register production identities.

---

### 53. Unique Agent Identifier Controls

Each agent should receive a unique identifier generated or approved by an authoritative identity system.

Example:

```text
AGT-HR-00217
AGT-FIN-00431
AGT-SOC-00108
```

Identifiers should avoid ambiguity and should not depend solely on human-readable names.

The identifier should remain stable enough to support lifecycle tracking and audit correlation.

---

### 54. Agent Identity Provider Integration

Agent identity should integrate with enterprise identity infrastructure where possible.

The identity provider may establish:

* identity issuance;
* identity validation;
* credential binding;
* lifecycle status;
* trust relationships;
* identity revocation.

This prevents each agent application from independently inventing its own identity model.

---

### 55. Cryptographic Agent Identity

For security-sensitive environments, agent identities should be cryptographically bound to credentials or attestable workloads.

Conceptually:

```text
Agent Identity
      │
      ▼
Cryptographic Credential
      │
      ▼
Authenticated Runtime
```

The cryptographic binding provides stronger assurance than an identity string transmitted in application data.

---

### 56. Workload-Bound Agent Identity

An agent identity should ideally be bound to the workload authorized to operate it.

For example:

```text
Agent Identity
      │
      ▼
Approved Workload
      │
      ▼
Approved Runtime
      │
      ▼
Execution
```

This reduces the risk of an attacker copying an identity identifier into an unauthorized workload.

---

### 57. Runtime Identity Binding

The enterprise should be able to establish that a runtime instance is legitimately operating as the registered agent.

Relevant attributes may include:

* workload identity;
* deployment identity;
* runtime environment;
* container or pod identity;
* cloud workload identity;
* platform attestation.

Runtime identity binding creates stronger assurance between the logical agent and its actual execution environment.

---

### 58. Agent Identity Attestation

Where supported, workload or platform attestation can provide evidence about the environment running the agent.

Conceptually:

```text
Runtime
   │
   ▼
Platform Evidence
   │
   ▼
Identity Verification
   │
   ▼
Agent Trust Decision
```

Attestation can help establish that an identity is operating from an expected environment rather than an unauthorized runtime.

---

### 59. Agent Identity Authentication

Authentication establishes whether an entity claiming an agent identity actually controls the corresponding credential or trusted workload.

Authentication should not rely on:

* agent self-declaration;
* prompt content;
* model-generated identity claims;
* user-provided identity strings.

Instead, authentication should rely on independently verifiable security mechanisms.

---

### 60. Mutual Agent Authentication

Where Agent A communicates directly with Agent B, both parties may need to authenticate each other.

```text
Agent A ───── Authentication ─────► Agent B
Agent A ◄──── Authentication ────── Agent B
```

Mutual authentication reduces the risk that either side unknowingly communicates with an impersonated agent.

---

### 61. Agent Identity Credential Protection

Credentials associated with agent identities should be protected against:

* theft;
* copying;
* disclosure;
* unauthorized reuse;
* accidental exposure;
* credential harvesting.

Credentials should not be embedded directly into prompts, agent memory, source code, or static configuration where stronger mechanisms are available.

---

### 62. Short-Lived Identity Credentials

Long-lived credentials increase the potential impact of compromise.

A stronger architecture uses short-lived credentials:

```text
Issue
  ↓
Use
  ↓
Expire
  ↓
Renew if authorized
```

This limits the useful lifetime of stolen credentials.

---

### 63. Credential Rotation

Identity credentials should be rotated according to security requirements.

Rotation may be triggered by:

* scheduled policy;
* suspected exposure;
* personnel or ownership changes;
* infrastructure changes;
* security incidents;
* identity reauthorization.

Credential rotation should not require uncontrolled changes to the agent's logical identity.

---

### 64. Credential Isolation

Credentials for different agents should remain isolated.

```text
Agent A → Credential A
Agent B → Credential B
Agent C → Credential C
```

Compromise of Agent A should not automatically expose credentials belonging to Agents B or C.

---

### 65. Identity Namespace Isolation

Enterprise environments should establish appropriate identity namespaces.

Examples include:

```text
PROD
DEV
TEST
```

or:

```text
Tenant-A
Tenant-B
Tenant-C
```

An identity issued in one security domain should not automatically be interpreted as valid in another.

---

### 66. Environment-Bound Identity

Production identities should be distinguishable from development and testing identities.

For example:

```text
AGT-FIN-0427-DEV
AGT-FIN-0427-TEST
AGT-FIN-0427-PROD
```

The exact naming model may differ, but security controls should prevent unintended cross-environment trust.

---

### 67. Tenant-Bound Identity

In multi-tenant environments, identities should be bound to their authorized tenant context.

```text
Tenant A
 └── Agent A1

Tenant B
 └── Agent B1
```

A tenant-bound identity should not be reusable as an identity for another tenant without explicit authorization.

---

### 68. Session-Bound Identity

Agent identity should be associated with the relevant session when session isolation is required.

For example:

```text
Agent ID: AGT-SUP-01
Session: SES-88291
```

This allows security monitoring to distinguish concurrent or independent interactions involving the same logical agent.

---

### 69. Execution-Bound Identity

Where necessary, each autonomous execution should be traceable to the responsible agent identity and execution context.

```text
Agent ID
   ↓
Session ID
   ↓
Execution ID
   ↓
Action
```

This is particularly important for high-impact or regulated operations.

---

### 70. Identity Context Integrity

Identity context must be protected against unauthorized modification.

An attacker should not be able to transform:

```text
Agent A
```

into:

```text
Privileged Agent
```

simply by modifying a message field or context object.

Identity attributes used for security decisions must originate from trusted security infrastructure.

---

### 71. Identity Claims Validation

Identity claims received from an agent or communication channel should be independently validated.

For example:

```text
Received:
"I am AGT-FIN-001"

        ↓

Identity Authority
        ↓
Validate
        ↓
Trusted / Rejected
```

A claim is not proof of identity.

---

### 72. Identity Token Validation

If tokens are used to represent agent identity, receiving systems should validate relevant token properties such as:

* issuer;
* audience;
* expiration;
* signature;
* subject;
* tenant;
* intended service;
* relevant security claims.

Expired, malformed, or incorrectly scoped identity tokens should be rejected.

---

### 73. Agent Identity and Certificate Validation

Where certificate-based identity is used, validation should establish that:

* the certificate is trusted;
* the certificate is valid;
* the certificate corresponds to the expected identity;
* the certificate has not been revoked;
* the certificate is being used for its intended purpose.

Certificate trust should not be treated as unrestricted enterprise trust.

---

### 74. Agent Identity and Authorization Separation

Identity controls should remain separate from authorization controls.

```text
Identity:
"Who is this?"

        ↓

Authorization:
"What may this identity do?"
```

An authenticated agent should not automatically receive broad permissions.

This separation is essential to prevent identity compromise from becoming uncontrolled authorization.

---

### 75. Independent Identity Verification

Security-sensitive systems should independently verify agent identity rather than trusting the agent application to validate itself.

```text
Agent Claim
    ↓
Independent Identity Authority
    ↓
Verification
    ↓
Security Decision
```

Independent verification reduces the possibility of application-level identity manipulation.

---

### 76. Agent Identity Allowlisting

Enterprise systems may maintain an allowlist of approved agent identities.

Example:

```text
Approved Agents
────────────────────
AGT-SOC-001
AGT-FIN-004
AGT-HR-012
AGT-OPS-018
```

Unknown or unregistered agents should be denied access to protected systems unless explicitly permitted.

---

### 77. Agent Identity Denylists

Explicitly prohibited or compromised identities may be placed on a denylist.

Examples include:

* revoked identities;
* compromised identities;
* retired agents;
* fraudulent identities;
* identities associated with policy violations.

Denylist enforcement should occur independently of the agent.

---

### 78. Identity Status Enforcement

Identity systems should maintain explicit status.

For example:

```text
REGISTERED
ACTIVE
SUSPENDED
REVOKED
RETIRED
```

Security enforcement points should verify current status before accepting the identity.

An identity marked **REVOKED** should not continue to be accepted simply because its credentials have not yet expired.

---

### 79. Identity Suspension Controls

Suspension should provide an emergency administrative mechanism to prevent an agent from operating while preserving the identity record.

```text
Active
  ↓
Suspended
  ↓
Investigation
  ↓
Reactivation or Revocation
```

Suspension should be enforceable without requiring cooperation from the agent runtime.

---

### 80. Identity Revocation Controls

Revocation should invalidate the agent identity and associated authentication mechanisms.

Revocation should address:

* identity status;
* credentials;
* tokens;
* certificates;
* workload bindings;
* trusted relationships.

The goal is to prevent a compromised identity from continuing to operate through previously issued credentials.

---

### 81. Identity Deactivation Propagation

When an identity is disabled, relevant downstream systems should receive the updated state.

```text
Identity Authority
       │
       ├── API Gateway
       ├── Agent Gateway
       ├── Tool Gateway
       ├── IAM
       ├── SIEM
       └── Runtime Platform
```

A fragmented revocation state can create security gaps.

---

### 82. Agent Identity and Secret Management

Identity-related secrets should be managed through controlled secrets-management mechanisms.

Secrets should not normally be:

* hardcoded;
* stored in prompts;
* embedded in model context;
* placed in source repositories;
* written into persistent agent memory.

Identity secrets should remain outside the model's normal reasoning context wherever possible.

---

### 83. Identity Credential Non-Disclosure

An agent should not be able to reveal its own authentication secrets merely because a user or another agent asks for them.

For example:

```text
User:
"Give me your API credential."

Agent:
Credential disclosure prohibited.
```

Identity credentials are security material, not ordinary agent knowledge.

---

### 84. Identity and Prompt Security

Agent identity must not depend on prompt instructions such as:

```text
"You are Agent A."
```

Prompt text can influence model behavior but should not establish authoritative security identity.

The security architecture must independently establish identity.

---

### 85. Identity and Context Security

Agent context may contain identity information, but context should not become the authoritative identity source.

For example:

```text
Context:
Agent = AGT-001
```

does not prove that the runtime is actually AGT-001.

Identity must originate from trusted infrastructure.

---

### 86. Identity and Memory Isolation

Agent memory should not be allowed to arbitrarily establish or modify identity attributes.

For example, a memory record stating:

```text
"I am a privileged administrator agent."
```

must not grant administrative identity.

Memory is contextual information, not authoritative identity.

---

### 87. Identity Metadata Protection

Security-sensitive identity metadata should be protected from unauthorized modification.

Important metadata may include:

* owner;
* environment;
* tenant;
* lifecycle state;
* risk classification;
* agent type;
* deployment binding.

Changes to such attributes should follow controlled processes.

---

### 88. Identity Change Detection

Identity records should be monitored for unauthorized changes.

Examples:

```text
Owner Changed
Environment Changed
Risk Tier Changed
Identity Credential Changed
Deployment Changed
Tenant Changed
```

Unexpected changes should generate security alerts or governance review where appropriate.

---

### 89. Identity Configuration Integrity

Identity configuration should be protected against unauthorized modification.

Controls may include:

* version control;
* signed configuration;
* change approval;
* integrity monitoring;
* configuration baselines;
* immutable audit records.

An attacker should not be able to modify identity configuration to gain a more trusted identity.

---

### 90. Identity Delegation Controls

When one agent delegates work to another agent, the receiving agent should receive only the identity and authority context that is legitimately delegated.

```text
Agent A
  │
  │ Delegated Task
  ▼
Agent B
```

Delegation should not automatically transfer Agent A's complete identity or unrestricted authority.

---

### 91. Identity Chain Preservation

Delegated execution should preserve the relevant identity chain.

For example:

```text
Initiator
   ↓
Agent A
   ↓
Agent B
   ↓
Tool
```

Security telemetry should be capable of reconstructing this chain.

This prevents delegated activity from becoming unattributable.

---

### 92. Identity Impersonation Detection

Systems should detect suspicious attempts to use an identity from an unexpected:

* location;
* runtime;
* deployment;
* tenant;
* environment;
* communication path;
* workload.

Behavior inconsistent with the identity's expected operating context may indicate compromise.

---

### 93. Identity Anomaly Detection

Identity monitoring should identify anomalous patterns such as:

* unusual authentication frequency;
* unexpected deployments;
* simultaneous use from incompatible environments;
* abnormal identity relationships;
* sudden ownership changes;
* unexpected geographic or infrastructure changes.

Identity anomalies can provide early indicators of agent compromise.

---

### 94. Agent Identity Rate Controls

Authentication and identity-related operations should be subject to rate controls where appropriate.

This can reduce:

* credential abuse;
* identity enumeration;
* authentication flooding;
* automated identity attacks.

Rate controls should be designed so legitimate autonomous workflows remain operational.

---

### 95. Identity Relationship Controls

The enterprise should define which agents may establish trusted relationships.

For example:

```text
Agent A ───► Agent B    Allowed
Agent A ───► Agent C    Allowed
Agent A ───► Agent D    Denied
```

Agent identity alone should not automatically create trust between agents.

---

### 96. Identity Trust Boundary Enforcement

Security boundaries should validate identity before permitting an agent to cross into another trust zone.

```text
Zone A
Agent
  │
  ▼
[Identity Verification]
  │
  ▼
Zone B
```

Identity verification should occur at meaningful trust boundaries rather than only at initial deployment.

---

### 97. Identity Correlation Across Enterprise Systems

Agent identity should be consistently correlated across:

* IAM;
* API gateways;
* cloud platforms;
* agent runtimes;
* tool gateways;
* SIEM;
* workflow systems;
* databases.

A single authoritative agent identity should be traceable across these systems.

---

### 98. Agent Identity Logging

Identity-related security events should be logged.

Examples include:

```text
Identity Created
Identity Activated
Authentication Attempt
Credential Issued
Credential Rotated
Identity Suspended
Identity Revoked
Identity Reactivated
Identity Modified
```

Logging should provide sufficient evidence for investigation and audit.

---

### 99. Tamper-Resistant Identity Audit Records

Identity events should be protected against unauthorized modification or deletion.

For high-value environments, audit records should support:

* integrity protection;
* centralized collection;
* restricted access;
* retention controls;
* reliable timestamps;
* correlation identifiers.

This ensures identity history remains trustworthy during investigations.

---

### 100. Identity-to-Action Traceability

Identity controls should ultimately allow the enterprise to connect an agent identity to actions.

```text
Agent Identity
      ↓
Authentication
      ↓
Session
      ↓
Request
      ↓
Decision
      ↓
Action
      ↓
Target System
```

This provides an identity foundation for end-to-end accountability.

---

### 101. Identity Resource Controls

Agent identity operations should consume controlled resources.

Examples include:

* authentication attempts;
* token issuance;
* session creation;
* identity registration;
* credential requests.

Resource controls reduce opportunities for identity infrastructure abuse.

---

### 102. Identity Concurrency Controls

Security systems may restrict simultaneous sessions or authentication activity associated with sensitive agent identities.

Unexpected concurrency can indicate:

* credential sharing;
* cloning;
* compromised credentials;
* unauthorized deployments.

Concurrency limits should be based on legitimate operational requirements.

---

### 103. Identity Timeout Controls

Authentication sessions and identity assertions should have appropriate expiration or timeout controls.

Long-lived sessions increase the period during which a compromised identity can remain useful.

Shorter validity periods reduce exposure while maintaining operational continuity through controlled renewal.

---

### 104. Identity Token Expiration

Identity assertions should have bounded lifetimes.

Conceptually:

```text
Token Issued
     │
     ▼
Valid
     │
     ▼
Expiration
     │
     ▼
Rejected
```

Expired identity assertions should not remain valid indefinitely.

---

### 105. Identity Replay Protection

An attacker should not be able to capture a valid identity assertion and replay it later to impersonate an agent.

Controls may include:

* expiration;
* nonces;
* timestamps;
* unique request identifiers;
* audience binding;
* cryptographic signatures;
* replay detection.

---

### 106. Identity Audience Restriction

An identity credential intended for one service should not automatically be accepted by another.

For example:

```text
Agent
 │
 └── Credential for Tool A
          X
          └── Tool B
```

Audience restrictions reduce credential reuse across unrelated systems.

---

### 107. Identity Scope Restriction

Identity credentials should contain only the security context required for their intended purpose.

A credential issued for:

```text
Agent → Reporting API
```

should not inherently grant:

```text
Agent → Payment System
```

Identity scope and authorization scope should remain appropriately constrained.

---

### 108. Agent Identity Isolation

Agents with materially different security requirements should use separate identities.

For example:

```text
Customer Support Agent
        X
Payment Processing Agent
```

This prevents compromise or misuse of one agent from automatically inheriting the identity of another.

---

### 109. Identity Recovery Controls

Identity recovery after compromise should require controlled validation.

A recovery process may include:

```text
Compromise Suspected
        ↓
Identity Suspended
        ↓
Credentials Revoked
        ↓
Runtime Investigated
        ↓
Security Validation
        ↓
Identity Reissued / Reactivated
```

Recovery should not simply restore compromised credentials.

---

### 110. Agent Identity Isolation During Incident Response

During an incident, a compromised agent should be isolatable without unnecessarily disabling unrelated agents.

```text
Agent A ── COMPROMISED ──► ISOLATE

Agent B ── NORMAL ────────► CONTINUE
Agent C ── NORMAL ────────► CONTINUE
```

This reduces operational blast radius.

---

### 111. Identity Behavioral Monitoring

Identity security should include behavioral monitoring.

Monitoring can compare:

```text
Expected Identity Behavior
          vs
Observed Identity Behavior
```

Unexpected changes may indicate compromise, misuse, credential theft, or unauthorized deployment.

---

### 112. Identity Activity Logging

Security-relevant agent activity should include the responsible identity.

Useful fields may include:

```text
Agent ID
Instance ID
Session ID
Request ID
Timestamp
Environment
Tenant
Action
Target
Result
```

This enables reliable correlation between identity and activity.

---

### 113. Identity Security Observability

Identity systems should expose sufficient telemetry to security operations.

Relevant signals include:

* authentication failures;
* identity creation;
* credential issuance;
* credential rotation;
* identity changes;
* identity suspension;
* identity revocation;
* anomalous identity use.

Identity telemetry should integrate with broader enterprise security monitoring.

---

### 114. Agent Identity Risk Detection

Identity-related risk detection should identify conditions such as:

* unknown agent identities;
* duplicate identities;
* inactive identities still operating;
* unexpected identity changes;
* identity use outside approved environments;
* revoked identities attempting access;
* suspicious credential reuse.

Identity risk detection should prioritize conditions that could lead to unauthorized autonomous activity.

---

### 115. Secure Identity Failure Handling

Identity failures should default to secure behavior.

Examples:

```text
Identity Cannot Be Verified
        ↓
       DENY
```

```text
Identity Status Unknown
        ↓
   Fail Closed
```

```text
Credential Invalid
        ↓
       DENY
```

An inability to establish identity should not result in implicit trust.

---

### 116. Independence of Agent Identity Controls

Agent identity controls should remain sufficiently independent from the agent itself.

The agent should not be able to:

* define its own authoritative identity;
* approve its own identity;
* modify its own trust level;
* reactivate itself after revocation;
* issue itself privileged credentials.

This establishes an important security boundary:

```text
Agent
  │
  X── Cannot Authoritatively Define Its Own Identity
  │
  ▼
Independent Identity Authority
```

---

### 117. Core Engineering Principle

The fundamental engineering principle for agent identity is:

> **An agent must never be trusted merely because it claims an identity. Identity must be independently established, cryptographically or otherwise securely bound to the authorized workload, continuously validated at appropriate boundaries, lifecycle-managed, and traceable to every security-relevant autonomous action.**

The complete technical model is:

```text
        ┌──────────────────────────┐
        │ Agent Registration       │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Unique Agent Identity    │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Credential / Workload    │
        │ Binding                  │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Authentication           │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Identity Validation      │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Identity Context         │
        │ Validation               │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Controlled Agent         │
        │ Execution                │
        └────────────┬─────────────┘
                     ↓
        ┌──────────────────────────┐
        │ Identity Correlation     │
        │ + Audit + Monitoring     │
        └──────────────────────────┘
```

The central control boundary remains:

**Identity establishes who or what the agent is. Authentication proves control of that identity. Authorization determines what the identity may do.**
