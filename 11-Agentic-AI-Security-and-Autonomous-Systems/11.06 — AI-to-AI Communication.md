# 11.06 — AI-to-AI Communication

## Part 1 — Foundations and Core Concepts

### 1. Definition of AI-to-AI Communication

AI-to-AI communication is the exchange of information, instructions, requests, decisions, status messages, data, or task results between two or more AI agents or autonomous AI systems.

Unlike traditional application-to-application communication, AI-to-AI communication may involve agents interpreting messages, making decisions, delegating tasks, invoking tools, and generating subsequent messages dynamically.

```text
Agent A
   │
   │ Request / Task / Data
   ▼
Agent B
   │
   │ Decision / Result / Delegation
   ▼
Agent A
```

The security concern is therefore not simply protecting the communication channel. The organization must also control **what authority an agent can communicate, delegate, transfer, or cause another agent to exercise**.

---

### 2. AI-to-AI Communication as a Security Boundary

Every communication path between agents represents a potential security boundary.

A message received from another agent can influence:

* decisions;
* tool selection;
* data access;
* task execution;
* delegation;
* transaction creation;
* downstream agent behavior;
* security policy interpretation.

Therefore, an enterprise must not automatically treat an agent message as trusted merely because it originated from another AI system.

```text
Agent A
   │
   │ Message
   ▼
[Communication Boundary]
   │
   ├── Identity Verification
   ├── Authorization
   ├── Message Validation
   ├── Policy Evaluation
   └── Trust Evaluation
   │
   ▼
Agent B
```

AI-to-AI communication should be treated as a controlled security interaction rather than unrestricted internal messaging.

---

### 3. AI-to-AI Communication vs Human-to-AI Communication

Human-to-AI interaction normally involves a human initiating a request and an AI system responding.

AI-to-AI communication is different because an agent may initiate communication autonomously.

| Characteristic      | Human-to-AI       | AI-to-AI                          |
| ------------------- | ----------------- | --------------------------------- |
| Initiator           | Human             | Agent                             |
| Frequency           | Usually bounded   | Potentially continuous            |
| Intent              | Human-defined     | May be dynamically generated      |
| Interpretation      | Human can clarify | Agents may interpret autonomously |
| Delegation          | Usually explicit  | Can be recursive                  |
| Authority           | Human-controlled  | Must be independently constrained |
| Risk of propagation | Limited           | Potentially cascading             |

The absence of a human at every communication step increases the importance of independent authorization and monitoring.

---

### 4. Agent Communication as an Autonomous Trust Relationship

When Agent A communicates with Agent B, the interaction creates a trust relationship.

However, the existence of communication does not automatically establish authorization.

```text
Communication
      ≠
Trust
      ≠
Authorization
      ≠
Permission
```

An agent may be permitted to communicate with another agent without being permitted to instruct that agent to perform sensitive actions.

---

### 5. Agent Identity in AI-to-AI Communication

Each agent participating in an enterprise communication environment should have a distinct and attributable identity.

An agent identity should allow the organization to determine:

* which agent initiated a message;
* which deployment instance sent it;
* which workload executed it;
* which human or business owner is responsible for it;
* which authorization policy applied;
* which downstream actions resulted.

Agent identity should therefore be treated as an enterprise security object.

```text
Agent Identity
      │
      ├── Agent ID
      ├── Application / Workload
      ├── Owner
      ├── Environment
      ├── Risk Tier
      ├── Authorized Capabilities
      └── Lifecycle Status
```

---

### 6. Authentication Between Agents

Authentication establishes confidence that a message originates from the claimed agent.

Possible mechanisms include:

* workload identity;
* mutual TLS;
* signed requests;
* service credentials;
* short-lived tokens;
* cryptographic message signatures;
* platform-native workload authentication.

Authentication should occur before sensitive AI-to-AI interactions are accepted.

However:

> Authentication proves identity; it does not prove authorization.

An authenticated malicious or compromised agent can still issue unauthorized requests.

---

### 7. Authorization Between Agents

Authorization determines what one agent is permitted to request from another agent.

For example, an HR agent may be authorized to ask a payroll agent for salary calculations but not to instruct it to modify employee bank-account information.

```text
Agent A
   │
   │ "Update employee bank account"
   ▼
Authorization Policy
   │
   ├── Agent Identity
   ├── Requested Capability
   ├── Data Scope
   ├── Transaction Risk
   └── Delegated Authority
   │
   ▼
ALLOW / DENY / ESCALATE
```

Authorization must therefore evaluate the **requested capability**, not merely the identity of the requesting agent.

---

### 8. Agent-to-Agent Trust Levels

Organizations may classify agent relationships according to defined trust levels.

For example:

| Trust Level    | Example                              | Permitted Interaction                   |
| -------------- | ------------------------------------ | --------------------------------------- |
| Untrusted      | External agent                       | Limited exchange                        |
| Restricted     | Internal low-risk agent              | Approved requests                       |
| Trusted        | Security-controlled enterprise agent | Expanded capabilities                   |
| Highly trusted | Critical enterprise agent            | Highly controlled privileged operations |

Trust classification should never replace authorization.

A highly trusted agent should still operate within explicit permissions.

---

### 9. Agent Communication Intent

An agent message should have a recognizable purpose or intent.

Examples include:

* requesting information;
* submitting a task;
* requesting approval;
* requesting a tool operation;
* returning a result;
* delegating work;
* reporting an event;
* escalating an exception.

Security controls should distinguish between these communication types because they can carry very different risks.

---

### 10. Message Semantics

AI-generated messages are not necessarily deterministic.

Two messages expressing similar natural-language intent may be interpreted differently by another agent.

For example:

```text
"Please handle this customer."

could potentially mean:

- retrieve customer information;
- contact the customer;
- modify customer records;
- create a support case;
- issue a refund.
```

Therefore, enterprise agent communication should prefer structured and constrained message semantics where possible.

---

### 11. Structured Agent Messages

Structured messages reduce ambiguity by explicitly defining fields such as:

```text
{
    sender_agent,
    recipient_agent,
    message_type,
    requested_action,
    resource,
    scope,
    authorization_context,
    expiration,
    correlation_id
}
```

Natural language can still be used for reasoning and explanation, but security-sensitive decisions should rely on machine-enforceable attributes.

---

### 12. Message Integrity

Message integrity ensures that a communication has not been modified after being generated by the sender.

Integrity protection may involve:

* cryptographic signatures;
* message authentication codes;
* secure transport;
* immutable identifiers;
* integrity-protected metadata.

A modified message can be particularly dangerous in an autonomous system because downstream agents may execute the altered instruction without human review.

---

### 13. Message Confidentiality

AI-to-AI communications may contain sensitive information such as:

* customer data;
* credentials;
* financial information;
* security findings;
* internal documents;
* personal information;
* business strategies;
* proprietary data.

Communication channels should therefore protect sensitive information against unauthorized disclosure.

Confidentiality must apply both **in transit** and, where necessary, to stored communication histories.

---

### 14. Message Authenticity vs Message Trustworthiness

A message can be authentic but still unsafe.

For example:

```text
Authenticated Agent A
        │
        │ "Delete all archived records."
        ▼
       Agent B
```

Agent B may successfully verify that Agent A sent the message.

That does not establish that:

* Agent A was authorized to request deletion;
* the request is within Agent A's delegated authority;
* the action complies with business policy;
* the request has not resulted from agent compromise.

Authentication therefore cannot be used as a substitute for authorization and policy enforcement.

---

### 15. Agent-to-Agent Delegation

One agent may delegate a task to another agent.

For example:

```text
Supervisor Agent
      │
      │ Delegate investigation
      ▼
Security Agent
      │
      │ Delegate log analysis
      ▼
Analysis Agent
```

Delegation introduces a critical security question:

**How much authority is transferred with the delegated task?**

The answer should be explicitly defined rather than inferred by the receiving agent.

---

### 16. Delegation of Authority

Delegation should not automatically transfer the full authority of the delegating agent.

If Agent A has permission to access a sensitive database and delegates a task to Agent B, Agent B should not automatically inherit unrestricted database access.

```text
Agent A Authority
       │
       │ Delegation
       ▼
Reduced Delegated Authority
       │
       ▼
Agent B
```

Delegated authority should be:

* explicit;
* limited;
* time-bound;
* scope-bound;
* attributable;
* revocable.

---

### 17. Transitive Authority

Transitive authority occurs when authority is indirectly transferred through multiple agents.

```text
Agent A
  │
  │ delegates
  ▼
Agent B
  │
  │ delegates
  ▼
Agent C
  │
  │ delegates
  ▼
Agent D
```

Without controls, Agent D could eventually exercise capabilities that were originally granted only to Agent A.

This creates a significant risk of **authority amplification**.

---

### 18. Authority Amplification

Authority amplification occurs when communication or delegation causes an agent to obtain more effective power than it was directly authorized to possess.

Example:

```text
Agent A:
Can approve invoices up to €10,000

        ↓ delegates

Agent B:
Can process invoices

        ↓ delegates

Agent C:
Can execute payments
```

If delegation controls are poorly designed, Agent C could indirectly execute a financial action exceeding its intended authority.

The security architecture must prevent delegation from creating capabilities that were never explicitly granted.

---

### 19. Confused Deputy Risk in AI-to-AI Communication

A confused deputy occurs when an agent with legitimate privileges is manipulated into using those privileges on behalf of another entity or agent.

AI-to-AI communication can amplify this risk because agents routinely request actions from other agents.

```text
Low-Privilege Agent
       │
       │ Manipulated request
       ▼
Privileged Agent
       │
       │ Uses its authority
       ▼
Sensitive System
```

The privileged agent must independently determine whether the requested action is authorized.

---

### 20. Agent Impersonation

An attacker may attempt to impersonate a legitimate agent.

Potential consequences include:

* unauthorized requests;
* fraudulent delegation;
* data extraction;
* malicious tool invocation;
* transaction manipulation;
* unauthorized configuration changes.

Strong workload identity and cryptographic authentication are therefore fundamental requirements for high-value agent communication.

---

### 21. Agent Hijacking Through Communication

A compromised agent may be used to influence other agents.

For example:

```text
Compromised Agent A
       │
       │ Malicious instruction
       ▼
Agent B
       │
       │ Tool request
       ▼
Enterprise System
```

The compromise of Agent A should not automatically provide Agent B with unrestricted authority.

Each receiving agent must independently validate the request.

---

### 22. Prompt Injection Across Agents

Prompt injection can propagate from one agent to another.

A malicious instruction could be embedded within:

* an agent message;
* tool output;
* retrieved data;
* memory;
* a generated task;
* an external document.

```text
External Content
      │
      ▼
Agent A
      │
      │ contaminated output
      ▼
Agent B
      │
      ▼
Tool / System
```

Therefore, AI-to-AI communication creates a potential **cross-agent prompt injection propagation path**.

---

### 23. Instruction vs Data

An important security distinction is whether an incoming message represents:

* data to be analyzed; or
* an instruction to be executed.

For example:

```text
Agent A:
"Customer requested account deletion."

Agent B:
Should interpret this as information.

versus

Agent A:
"Delete customer account."

Agent B:
Should interpret this as an executable request.
```

The architecture should not allow arbitrary content to silently cross from **data context into instruction context**.

---

### 24. Agent Communication and Data Classification

Messages should be evaluated according to the sensitivity of the information they contain.

Possible classifications include:

| Classification    | Example                                             |
| ----------------- | --------------------------------------------------- |
| Public            | Public product information                          |
| Internal          | Internal operational information                    |
| Confidential      | Business-sensitive information                      |
| Restricted        | Sensitive customer or employee data                 |
| Highly Restricted | Credentials, secrets, critical security information |

Agent communication policies should restrict which agents may exchange particular data classifications.

---

### 25. Data Minimization Between Agents

Agents should exchange only the information necessary to accomplish the requested task.

Instead of:

```text
Agent A → Entire customer database → Agent B
```

the preferred model is:

```text
Agent A → Required customer attributes → Agent B
```

Data minimization reduces:

* confidentiality exposure;
* privacy risk;
* lateral movement opportunities;
* accidental disclosure;
* downstream compromise impact.

---

### 26. Context Propagation

An agent may pass context from one interaction to another.

For example:

```text
User
  ↓
Agent A
  ↓
Agent B
  ↓
Agent C
```

Context may include:

* user identity;
* authorization claims;
* business purpose;
* previous instructions;
* retrieved information;
* risk classification;
* transaction state.

Security controls must distinguish between **trusted security context** and **ordinary model-generated context**.

---

### 27. Security Context Integrity

An agent must not be allowed to freely modify security-sensitive context.

For example, an agent should not be able to generate:

```text
"user_is_admin = true"
```

and have a downstream agent treat that statement as an authoritative authorization claim.

Security attributes should originate from trusted infrastructure rather than from model-generated text.

---

### 28. Agent-to-Agent Communication and Zero Trust

Zero Trust principles apply directly to AI-to-AI communication.

The fundamental assumptions should be:

* do not automatically trust an agent;
* verify identity;
* verify authorization;
* validate requests;
* minimize permissions;
* continuously evaluate risk;
* monitor behavior.

```text
Agent A
   │
   ▼
Verify Identity
   │
   ▼
Evaluate Authorization
   │
   ▼
Validate Request
   │
   ▼
Evaluate Risk
   │
   ▼
Permit / Deny / Escalate
   │
   ▼
Agent B
```

---

### 29. Agent Communication Loops

Agents can unintentionally create communication loops.

```text
Agent A → Agent B
   ↑         ↓
   └─────────┘
```

More complex systems can create recursive loops:

```text
A → B → C → D → A
```

Such loops can cause:

* excessive resource consumption;
* repeated actions;
* conflicting decisions;
* transaction duplication;
* uncontrolled message generation.

Agent communication therefore requires explicit loop and recursion boundaries.

---

### 30. Communication Cascades

A single message can trigger multiple downstream actions.

```text
Agent A
   │
   ├──► Agent B
   │       ├──► Agent D
   │       └──► Agent E
   │
   └──► Agent C
           ├──► Agent F
           └──► Agent G
```

This creates a communication cascade.

The security impact of one compromised or manipulated agent can therefore spread across an entire agent ecosystem.

---

### 31. Cascading Failure

A failure in one agent can propagate through dependent agents.

Examples include:

* incorrect data;
* incorrect authorization assumptions;
* malformed messages;
* repeated retries;
* invalid transactions;
* corrupted context;
* excessive workload.

Agent ecosystems should therefore be designed with containment boundaries that prevent local failures from becoming enterprise-wide failures.

---

### 32. Agent Communication Dependency

An agent may become dependent on another agent for:

* identity information;
* decisions;
* data;
* approvals;
* task execution;
* risk scoring;
* security recommendations.

Dependency creates additional availability and integrity risks.

Critical agents should not blindly depend on another agent for the only mechanism capable of validating its authority.

---

### 33. Circular Trust Dependencies

Circular trust occurs when agents rely on each other to establish trust.

```text
Agent A trusts Agent B
        ▲          │
        │          ▼
Agent C ◄──────── Agent B
```

A particularly dangerous pattern is:

```text
Agent A authorizes B
Agent B authorizes A
```

Security authorization should ultimately rely on independent enterprise policy rather than circular agent assertions.

---

### 34. Agent Communication and Tool Access

AI-to-AI communication can indirectly trigger tool use.

For example:

```text
Agent A
   │
   │ "Ask Agent B to refund customer"
   ▼
Agent B
   │
   │ Function Call
   ▼
Payment System
```

Agent B must independently authorize the transaction.

Agent A's request should not bypass the controls normally required for direct access to the payment capability.

---

### 35. Agent Communication and Transaction Security

When an agent-to-agent message can result in a financial, legal, operational, or destructive transaction, communication becomes part of the transaction security boundary.

Examples include:

* approving payments;
* modifying customer accounts;
* changing infrastructure;
* deleting data;
* provisioning privileges;
* changing security policies.

Higher-risk communications require stronger authorization, validation, and potentially human approval.

---

### 36. Message Replay Risk

A valid message may be captured and replayed later.

For example:

```text
Original:
Agent A → "Approve transaction #1234"

Attacker:
replays same message

Agent B:
"Approve transaction #1234"
```

Controls such as:

* timestamps;
* nonces;
* unique message identifiers;
* expiration;
* replay detection;

can prevent previously valid instructions from being reused improperly.

---

### 37. Message Ordering

The order of agent messages can affect security and business outcomes.

For example:

```text
Message 1: Suspend account
Message 2: Transfer funds
```

is materially different from:

```text
Message 1: Transfer funds
Message 2: Suspend account
```

Systems performing sensitive workflows should therefore maintain transaction state and enforce valid sequencing rather than assuming messages will always arrive in the correct order.

---

### 38. Agent Communication Attribution

Every security-relevant agent interaction should be attributable.

The organization should be able to determine:

```text
Who initiated?
Which agent sent it?
Which agent received it?
What was requested?
What authority applied?
What policy evaluated it?
What action occurred?
What downstream actions resulted?
```

Attribution is essential for:

* incident response;
* investigations;
* audit;
* accountability;
* regulatory evidence;
* forensic reconstruction.

---

### 39. Non-Repudiation Considerations

For high-impact interactions, the enterprise may require evidence that a specific agent instance generated or authorized a message.

Cryptographically protected records can support stronger attribution.

However, non-repudiation should not be interpreted as proof that the action was legitimate.

A message can be cryptographically attributable and still represent malicious or unauthorized behavior from a compromised agent.

---

### 40. Agent Communication Availability

Communication infrastructure itself can become an attack target.

Threats include:

* message flooding;
* excessive agent requests;
* recursive communication;
* queue exhaustion;
* denial of service;
* dependency failure.

Availability controls should therefore include:

* rate limits;
* quotas;
* concurrency limits;
* timeouts;
* queue controls;
* circuit breakers.

---

### 41. Agent Communication Confidentiality Boundaries

Agents operating at different trust or data-classification levels should not necessarily communicate directly.

For example:

```text
Highly Restricted Agent
        │
        X  Direct unrestricted communication
        │
Internal General Agent
```

A controlled gateway or mediation layer may be required.

```text
Restricted Agent
      │
      ▼
[Agent Security Gateway]
      │
      ├── Identity
      ├── Authorization
      ├── Data Policy
      ├── Message Validation
      └── Risk Evaluation
      │
      ▼
Internal Agent
```

---

### 42. Agent Communication and Tenant Isolation

In multi-tenant environments, agents serving different customers or organizational tenants must not exchange data or authority across tenant boundaries without explicit authorization.

A compromised agent in Tenant A should not be able to use AI-to-AI communication to obtain access to Tenant B.

Tenant identity should therefore remain part of the authorization context throughout the communication chain.

---

### 43. Cross-Agent Privilege Escalation

AI-to-AI communication can become a privilege-escalation mechanism when a lower-privileged agent persuades a higher-privileged agent to perform an action on its behalf.

```text
Low Privilege Agent
        │
        │ Request
        ▼
High Privilege Agent
        │
        │ Sensitive operation
        ▼
Enterprise System
```

The receiving agent must evaluate whether the requester is authorized to cause the requested action—not merely whether the receiving agent itself has permission to perform it.

---

### 44. Agent Communication as an Attack Surface

The AI-to-AI communication attack surface can include:

* agent discovery;
* agent identity;
* authentication;
* authorization;
* message transport;
* message schemas;
* message contents;
* delegation;
* context propagation;
* memory propagation;
* tool requests;
* agent discovery metadata;
* response handling;
* retries;
* queues;
* logs;
* communication gateways.

This attack surface grows rapidly as the number of agents and relationships increases.

---

### 45. Agent Relationship Graph

Enterprise agent ecosystems can be modeled as communication graphs.

```text
              Agent A
             /       \
            ▼         ▼
        Agent B     Agent C
          /  \          \
         ▼    ▼          ▼
     Agent D Agent E   Agent F
```

Security analysis should consider not only individual agents but also the relationships between them.

A highly connected agent may represent a disproportionately important attack or failure point.

---

### 46. Agent Communication Blast Radius

Blast radius represents the potential impact of a compromised or manipulated agent.

An agent with ten unrestricted downstream relationships may have significantly greater risk than an isolated agent with one narrowly scoped relationship.

Therefore:

> The security risk of an agent depends not only on its capabilities but also on the capabilities reachable through its communication relationships.

Network-style segmentation concepts can therefore be applied to agent ecosystems.

---

### 47. Communication Boundary Enforcement

Security boundaries must be technically enforced rather than documented only in governance policies.

Controls may include:

* agent gateways;
* service meshes;
* API gateways;
* policy enforcement points;
* identity-aware proxies;
* authorization services;
* message validation services.

An agent should not be able to bypass these controls simply by communicating directly with another internal agent.

---

### 48. Agent Communication Governance

Organizations should define governance requirements for:

* approved agent relationships;
* permitted message types;
* allowed delegation;
* data exchanged;
* trust levels;
* authorization requirements;
* logging requirements;
* monitoring;
* human approval;
* retention;
* incident response.

Agent communication should therefore become an explicit object within the AI governance and GRC model.

---

### 49. Core Security Principles for AI-to-AI Communication

The following principles establish the foundation for secure agent communication:

1. **Every agent must have an attributable identity.**
2. **Communication does not imply authorization.**
3. **Authentication does not imply trust.**
4. **Trust does not imply unrestricted authority.**
5. **Delegated authority must be explicitly bounded.**
6. **Agent-generated instructions must not become trusted security claims automatically.**
7. **Sensitive actions require independent authorization.**
8. **Agent communication must be observable and attributable.**
9. **Communication failures must be contained.**
10. **Compromise of one agent must not automatically compromise connected agents.**

---

### 50. Core Principle of AI-to-AI Communication

The fundamental security principle is:

> **Agent-to-agent communication must be treated as an independently governed security interaction in which identity, authorization, message integrity, delegated authority, data access, and downstream actions are separately controlled.**

The fact that one AI agent requests an action from another AI agent does not make that request trustworthy or authorized.

The receiving system must independently determine:

```text
Who is requesting?
        ↓
What is being requested?
        ↓
Is the message authentic?
        ↓
Is the request authorized?
        ↓
Is the requested capability permitted?
        ↓
Is the data scope appropriate?
        ↓
Is the action within delegated authority?
        ↓
What is the potential impact?
        ↓
Should the action be allowed, denied, or escalated?
```

This establishes the foundational security model for AI-to-AI interactions: **communication must never become an implicit transfer of trust or authority.**

## Part 2 — Technical Security and Control Mechanisms

### 51. AI-to-AI Communication Security Control Architecture

AI-to-AI communication requires a security control architecture that protects the communication channel, validates the participating agents, evaluates requests, and prevents unauthorized authority propagation.

A reference architecture can be structured as:

```text
Agent A
   │
   ▼
[Agent Communication Gateway]
   │
   ├── Agent Identity
   ├── Authentication
   ├── Message Integrity
   ├── Schema Validation
   ├── Authorization
   ├── Delegation Validation
   ├── Data Policy
   ├── Risk Evaluation
   └── Rate / Resource Controls
   │
   ▼
Agent B
   │
   ▼
[Independent Policy Enforcement]
   │
   ▼
Tool / Data / Enterprise System
```

The key architectural principle is that the receiving agent must not rely exclusively on the sender's claims about identity, authority, or security context.

---

### 52. Agent Identity Control

Every participating agent should have a unique enterprise identity.

The identity should be associated with:

* agent identifier;
* application or workload;
* deployment environment;
* owner;
* business purpose;
* risk classification;
* lifecycle status;
* permitted communication relationships.

Identity should remain stable enough to support attribution while individual execution credentials can remain short-lived.

---

### 53. Agent-to-Agent Authentication

Agent-to-agent authentication establishes that the communicating workload is the entity it claims to be.

Possible mechanisms include:

* mutual TLS;
* workload identity;
* signed requests;
* service identity tokens;
* short-lived access tokens;
* cryptographic signatures.

Authentication should occur before an agent accepts sensitive requests.

```text
Agent A
   │
   │ Authentication Request
   ▼
Identity Infrastructure
   │
   │ Verified Identity
   ▼
Agent B
```

Authentication should be performed independently of the model's natural-language claims.

---

### 54. Strong Agent Authentication

High-risk agent interactions should use strong authentication mechanisms resistant to credential theft and impersonation.

Security controls may include:

* certificate-based authentication;
* hardware-backed workload identity;
* short-lived credentials;
* automated credential rotation;
* mutual authentication;
* cryptographic request signing.

Long-lived static credentials should be avoided where practical because compromise can provide persistent access to multiple downstream agents.

---

### 55. Fine-Grained Agent Authorization

Authorization should evaluate the complete request context.

A policy decision may consider:

```text
Agent Identity
      +
Requested Capability
      +
Resource
      +
Data Scope
      +
Business Context
      +
Delegated Authority
      +
Risk Level
      +
Transaction Value
      +
Time
      ↓
Authorization Decision
```

Authorization should not be based solely on whether the sender is an approved agent.

---

### 56. Independent Authorization Service

For sensitive operations, authorization should be enforced by a security component independent of the agent's reasoning process.

```text
Agent A
   │
   │ Request
   ▼
Agent B
   │
   │ Authorization Check
   ▼
[Policy Decision Point]
   │
   ├── ALLOW
   ├── DENY
   └── ESCALATE
   │
   ▼
[Policy Enforcement Point]
   │
   ▼
Enterprise System
```

This prevents an agent from determining its own authorization.

---

### 57. Agent Communication Allowlisting

Organizations should explicitly define which agents are permitted to communicate.

Example:

| Sender          | Receiver           | Status     |
| --------------- | ------------------ | ---------- |
| Security Agent  | SOC Agent          | Allowed    |
| HR Agent        | Payroll Agent      | Allowed    |
| Marketing Agent | Payment Agent      | Restricted |
| External Agent  | Core Banking Agent | Denied     |

Allowlisting reduces the attack surface and prevents unauthorized agent discovery and communication.

---

### 58. Message Type Allowlisting

Not every agent relationship should permit every type of message.

For example:

```text
Agent A → Agent B

ALLOWED:
✓ Information request
✓ Status request
✓ Task submission

RESTRICTED:
⚠ Transaction request
⚠ Privilege change

DENIED:
✕ Credential extraction
✕ Security-policy modification
```

Message-type policies provide a second authorization layer beyond the communication relationship itself.

---

### 59. Tool Capability Segmentation

Agents should not inherit all capabilities of another agent merely because they can communicate with it.

For example:

```text
Payment Agent
 ├── Read Transaction
 ├── Create Payment
 ├── Approve Payment
 └── Cancel Payment
```

A reporting agent may be permitted to request only:

```text
Read Transaction
```

while payment creation and approval remain inaccessible.

---

### 60. Message Schema Validation

AI-to-AI messages should use controlled schemas for security-sensitive interactions.

Example:

```text
Message
├── sender_id
├── receiver_id
├── message_type
├── request_id
├── requested_capability
├── resource
├── scope
├── expiration
└── authorization_context
```

Schema validation prevents malformed or unexpected content from being interpreted as legitimate requests.

---

### 61. Message Content Validation

Valid schema does not necessarily mean valid content.

The receiving system should validate:

* permitted values;
* resource identifiers;
* requested operations;
* parameter types;
* maximum sizes;
* allowed scopes;
* expected relationships.

For example, a syntactically valid request to delete a production database should still be rejected if the agent is not authorized for that operation.

---

### 62. Agent Message Integrity

Messages should be protected against unauthorized modification.

Controls can include:

* cryptographic signatures;
* message authentication codes;
* secure transport;
* integrity-protected metadata;
* sequence identifiers.

Integrity controls are especially important where messages trigger automated actions.

---

### 63. Message Replay Protection

The communication layer should detect and reject previously used messages.

Useful mechanisms include:

* unique request IDs;
* nonces;
* timestamps;
* expiration timestamps;
* sequence numbers;
* replay caches.

```text
Request ID: 8F21A
Timestamp: 14:31:05
Expiration: 14:31:35

Request received again:
→ REJECT: replay detected
```

---

### 64. Message Expiration

Security-sensitive agent instructions should have an explicit validity period.

For example:

```text
Created:     10:00
Valid until: 10:05
```

After expiration, the receiving system should reject the request even if the message is authentic.

This limits the usefulness of intercepted or delayed instructions.

---

### 65. Time-Bounded Agent Communication Authority

Communication authorization itself should be time-bounded.

For example:

```text
Agent A
   │
   │ Authorized to communicate with Agent B
   │
   ├── Start: 09:00
   └── End:   17:00
```

Temporary workflows should not create permanent communication privileges.

---

### 66. Short-Lived Agent Credentials

Agents should use short-lived credentials wherever possible.

```text
Agent
 │
 ├── Request credential
 │
 ▼
Identity Provider
 │
 └── 5-minute token
        │
        ▼
     Agent B
```

Short-lived credentials reduce the impact of credential theft and limit persistent unauthorized communication.

---

### 67. Credential Isolation

Credentials used for AI-to-AI communication should be isolated from:

* model context;
* prompts;
* agent memory;
* tool outputs;
* user-visible content;
* general application data.

An agent should never need to expose a reusable secret to another agent simply to establish trust.

---

### 68. Secrets Management

Communication credentials should be managed through centralized secrets or identity infrastructure rather than embedded in:

* prompts;
* system instructions;
* source code;
* agent memory;
* configuration files;
* message content.

Agents should receive only the credentials necessary for their specific communication role.

---

### 69. Context Security Controls

Security-relevant context should be separated from model-generated context.

For example:

```text
Trusted Security Context
├── Authenticated Agent ID
├── Tenant ID
├── Authorization Claims
├── Risk Tier
└── Policy Decision

Model Context
├── Conversation
├── Retrieved Data
├── Agent Reasoning
└── Generated Text
```

The model should not be able to arbitrarily modify trusted security attributes.

---

### 70. Prompt and Instruction Integrity

Instructions passed between agents should be protected from unauthorized modification and clearly separated from untrusted content.

The architecture should distinguish:

```text
Trusted Policy
      ≠
Agent Instruction
      ≠
External Data
      ≠
Tool Output
```

This prevents untrusted content from silently becoming authoritative instructions.

---

### 71. Untrusted Input Isolation

Messages received from another agent should be treated according to their trust classification.

If Agent A is compromised, its output may contain malicious instructions.

Therefore:

```text
Agent A Output
      │
      ▼
[Untrusted Input Boundary]
      │
      ├── Validate
      ├── Classify
      ├── Sanitize
      └── Authorize
      │
      ▼
Agent B
```

Agent B should not automatically treat Agent A's generated text as trusted policy.

---

### 72. Prompt Injection Detection

AI-to-AI communication channels should incorporate controls capable of detecting suspicious instructions.

Potential indicators include:

* attempts to override system policies;
* requests for privileged credentials;
* instructions to bypass approval;
* attempts to disable monitoring;
* unexpected authority claims;
* requests outside normal business workflows.

Detection should supplement, not replace, authorization enforcement.

---

### 73. Memory Isolation

Agent memories should be isolated according to:

* agent identity;
* tenant;
* user;
* application;
* sensitivity;
* business purpose.

An agent should not be able to retrieve another agent's persistent memory simply because communication between them is permitted.

---

### 74. Memory Authorization

Memory access should require explicit authorization.

```text
Agent A
   │
   │ Request memory
   ▼
Memory Authorization
   │
   ├── Identity
   ├── Scope
   ├── Tenant
   ├── Purpose
   └── Sensitivity
   │
   ▼
ALLOW / DENY
```

Memory should be treated as a data system, not as an unrestricted extension of the model context.

---

### 75. Memory Integrity

An agent should not be able to silently modify security-sensitive memories used by another agent.

Integrity controls may include:

* provenance;
* versioning;
* access control;
* cryptographic integrity;
* write authorization;
* immutable audit records.

This reduces the risk of persistent cross-agent manipulation.

---

### 76. Persistent Context Controls

When context is transferred between agents, the receiving agent should know:

* where the context originated;
* when it was created;
* which agent generated it;
* whether it has been validated;
* what trust level applies;
* whether it contains executable instructions.

This creates a security distinction between **context provenance** and **context content**.

---

### 77. Data Access Authorization

An agent requesting information from another agent should be evaluated against the underlying data authorization policy.

Example:

```text
Agent A
   │
   │ "Give me employee salary data"
   ▼
Agent B
   │
   ▼
Data Authorization
   │
   ├── Agent identity
   ├── Business purpose
   ├── Data classification
   └── User / tenant scope
```

Agent B should not disclose data merely because Agent A is another internal AI system.

---

### 78. Data Minimization

AI-to-AI responses should contain only the data necessary to satisfy the request.

Instead of:

```text
Agent A → Complete customer profile
```

prefer:

```text
Agent A → Required customer attribute
```

Data minimization reduces the consequences of both communication compromise and downstream agent compromise.

---

### 79. Field-Level Data Protection

Sensitive fields should be independently protected.

For example:

```text
Customer Record
├── Name          → Allowed
├── Account ID    → Allowed
├── Address       → Restricted
├── Payment Data  → Denied
└── Credentials   → Denied
```

An agent relationship should not automatically grant access to every field in a data object.

---

### 80. Tenant Isolation

AI-to-AI communication must preserve tenant boundaries.

```text
Tenant A
Agent A1 ───► Agent A2

Tenant B
Agent B1 ───► Agent B2
```

Cross-tenant communication should require explicit authorization and policy enforcement.

A compromised agent in one tenant must not be able to use another agent as a bridge into another tenant.

---

### 81. Session Isolation

Agent interactions should maintain session boundaries.

A request associated with one:

* user;
* transaction;
* tenant;
* workflow;
* business process;

should not automatically inherit context from another.

Session isolation reduces context confusion and cross-session data leakage.

---

### 82. Network Segmentation

Agent communication should be segmented according to trust and risk.

```text
                 Agent Network
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
   Low Risk       Restricted      Critical
    Agents          Agents         Agents
       │              │              │
       └────── Controlled Gateway ───┘
```

Network reachability should be narrower than general enterprise network access.

---

### 83. Egress Controls

Agents should not be allowed to establish arbitrary external communication channels.

Egress policies should restrict:

* destinations;
* protocols;
* ports;
* domains;
* APIs;
* data classifications;
* communication frequency.

This is particularly important for agents capable of autonomous external interaction.

---

### 84. External Communication Controls

When an internal agent communicates with an external AI agent, the organization should evaluate:

* external identity;
* provider trust;
* data classification;
* contractual requirements;
* jurisdiction;
* permitted capabilities;
* retention;
* logging;
* authorization.

External agent communication should normally receive stronger controls than equivalent internal communication.

---

### 85. Code Execution Isolation

If AI-to-AI messages can trigger code execution, execution should occur within isolated environments.

```text
Agent Message
      │
      ▼
Execution Policy
      │
      ▼
Sandbox
 ├── CPU Limit
 ├── Memory Limit
 ├── Network Limit
 ├── File Limit
 └── Time Limit
```

The receiving agent should not be able to execute arbitrary code simply because another agent requested it.

---

### 86. Database Security Controls

Database operations initiated through agent communication should remain subject to conventional database security controls.

These include:

* database identity;
* role-based access;
* row-level security;
* query controls;
* transaction controls;
* auditing;
* encryption.

Agent-to-agent communication must not become a mechanism for bypassing database authorization.

---

### 87. Read/Write Separation

Where practical, agents should have separate permissions for reading and modifying information.

```text
Agent
 ├── READ → Customer Data
 └── WRITE → Restricted / Approval Required
```

A reporting agent, for example, should not receive write privileges simply because it can communicate with an administrative agent.

---

### 88. Human Approval Controls

High-impact agent-to-agent requests should require human approval before execution.

Examples include:

* large financial transactions;
* privileged access changes;
* destructive operations;
* legal commitments;
* production changes;
* sensitive data transfers.

```text
Agent A
   ↓
Agent B
   ↓
Risk Evaluation
   ↓
Human Approval
   ↓
Execution
```

Human approval should occur at the appropriate control boundary, not merely as a conversational acknowledgment.

---

### 89. Action Preview

Before executing a high-impact request, the system should generate a structured preview.

Example:

```text
REQUEST
Action: Transfer funds
Amount: €25,000
Source: Account A
Destination: Account B
Requester: Agent-17
Executor: Payment-Agent-04
Risk: HIGH

Decision:
[Approve] [Reject]
```

Action preview allows humans or independent systems to evaluate the actual consequence rather than relying on the agent's explanation.

---

### 90. Dual Authorization

Critical AI-to-AI actions may require two independent approvals.

```text
Agent Request
      │
      ├──► Authorization A
      │
      └──► Authorization B
               │
               ▼
          Execute Action
```

Dual authorization reduces the possibility that one compromised agent can independently trigger a critical operation.

---

### 91. Reversibility Controls

Where possible, agent actions should be reversible.

Examples include:

* transaction cancellation;
* configuration rollback;
* account restoration;
* version rollback;
* staged deployment;
* soft deletion.

Irreversible operations should receive stronger controls than reversible operations.

---

### 92. Agent Execution Limits

Agents should have limits on the number and scope of actions they can cause through communication.

Examples:

* maximum transactions;
* maximum records modified;
* maximum monetary value;
* maximum downstream requests;
* maximum execution duration.

Limits reduce blast radius if an agent becomes compromised.

---

### 93. Loop Detection

The communication platform should detect recurring agent interaction patterns.

```text
A → B → C → A
```

Possible controls include:

* maximum delegation depth;
* correlation IDs;
* recursion counters;
* maximum message hops;
* duplicate request detection.

Communication should terminate when defined boundaries are exceeded.

---

### 94. Recursive Delegation Controls

Agents should not be able to delegate indefinitely.

Example:

```text
A
 ↓
B
 ↓
C
 ↓
D
 ↓
X  ← Maximum Delegation Depth
```

Delegated authority should normally become narrower—not broader—as it moves through the chain.

---

### 95. Agent-to-Agent Authentication

Every agent relationship should independently authenticate both sides where mutual trust is required.

```text
Agent A
  │
  │ prove identity
  ▼
Agent B
  │
  │ prove identity
  ▼
Agent A
```

This prevents one-sided assumptions about the identity of the communication partner.

---

### 96. Agent-to-Agent Message Integrity

For high-value communications, message integrity should extend beyond the transport layer.

The security record may bind:

```text
Sender
+
Receiver
+
Message
+
Timestamp
+
Request ID
+
Authorization Context
```

This provides stronger protection against message substitution and manipulation.

---

### 97. Delegated Authority Constraints

Delegated authority should explicitly define:

* who delegated it;
* who received it;
* what capability was delegated;
* resource scope;
* transaction limits;
* expiration;
* whether further delegation is permitted.

Example:

```text
Agent A
  │
  │ Delegate:
  │ "Read invoice data"
  │ Scope: Finance-Tenant-01
  │ Duration: 30 minutes
  │ No further delegation
  ▼
Agent B
```

---

### 98. Tool Result Validation

Agent B should not blindly trust information returned from Agent A if that information can influence a sensitive action.

Tool and agent outputs should be validated for:

* authenticity;
* schema;
* expected source;
* data type;
* business consistency;
* authorization relevance.

Generated output is not automatically trusted merely because it came from an internal agent.

---

### 99. Output Validation Before Action

Before an agent acts on another agent's recommendation, the proposed action should pass through an independent validation layer.

```text
Agent Recommendation
        │
        ▼
Output Validation
        │
        ├── Schema
        ├── Policy
        ├── Scope
        ├── Risk
        └── Authorization
        │
        ▼
Execution
```

This creates a separation between **reasoning** and **execution authority**.

---

### 100. Business Rule Enforcement

AI-to-AI interactions must remain subject to deterministic business rules.

For example:

```text
Agent:
"Approve refund."

Business Rule:
Refund > €5,000 requires human approval.

Result:
Agent request → ESCALATE
```

The agent cannot override deterministic enterprise controls through reasoning or persuasive messaging.

---

### 101. Resource Controls

Communication resources should be constrained.

Controls may include:

* CPU quotas;
* memory quotas;
* message size limits;
* queue limits;
* token budgets;
* API quotas;
* execution budgets.

This prevents AI-to-AI interactions from consuming uncontrolled enterprise resources.

---

### 102. Rate Limiting

Each agent relationship should have defined request limits.

```text
Agent A → Agent B

100 requests/minute
10 concurrent requests
Maximum message size: defined
```

Unexpected spikes can indicate:

* runaway behavior;
* loops;
* compromise;
* denial-of-service activity;
* misconfiguration.

---

### 103. Concurrency Controls

Agents should not be allowed to create unlimited simultaneous interactions.

Concurrency limits reduce:

* resource exhaustion;
* duplicate transactions;
* race conditions;
* communication storms.

Critical workflows should use controlled concurrency and transaction coordination.

---

### 104. Timeout Controls

Agent-to-agent requests should have defined timeouts.

```text
Request
  │
  ├── Processing
  │
  └── Timeout → Terminate / Escalate
```

Timeouts prevent stalled agents from holding resources indefinitely.

---

### 105. Retry Controls

Retries should be bounded.

An uncontrolled retry chain can produce:

```text
Agent A
 ↓ retry
Agent B
 ↓ retry
Agent A
 ↓ retry
Agent B
 ↓
Communication Storm
```

Controls should define:

* maximum retries;
* retry intervals;
* exponential backoff;
* retryable errors;
* termination conditions.

---

### 106. Circuit Breakers

Circuit breakers should automatically stop communication when abnormal behavior is detected.

```text
Normal
  │
  ▼
Communication
  │
  ▼
Failure Threshold
  │
  ▼
[CIRCUIT OPEN]
  │
  X
Communication stopped
```

Circuit breakers can contain cascading failures and agent compromise.

---

### 107. Emergency Agent Controls

Emergency controls should allow security teams to rapidly restrict agent communication.

Possible actions include:

* block agent-to-agent traffic;
* revoke credentials;
* disable tools;
* isolate the workload;
* freeze transactions;
* suspend delegation;
* force human approval.

Emergency controls should be independently accessible from the affected agent.

---

### 108. Agent Kill Switch

A kill switch should provide a rapid mechanism to stop an agent or prevent it from performing further autonomous operations.

```text
Security Operations
        │
        ▼
   [KILL SWITCH]
        │
        ├── Stop Agent
        ├── Revoke Credentials
        ├── Block Communication
        └── Freeze Actions
```

The kill mechanism should not depend on the agent cooperating with the shutdown request.

---

### 109. Credential Revocation

When an agent is suspected of compromise, its communication credentials should be immediately revocable.

Revocation should ideally propagate to:

* agent gateways;
* service meshes;
* APIs;
* identity providers;
* downstream agents;
* tool authorization systems.

Credential revocation is one of the primary mechanisms for rapidly reducing an agent's communication authority.

---

### 110. Agent Isolation

A compromised agent should be capable of being isolated without necessarily shutting down unrelated agents.

```text
Agent A  ← COMPROMISED
   X
   │
   │ blocked
   │
Agent B ─── Agent C ─── Agent D
```

Isolation reduces the probability of lateral movement and communication-based compromise propagation.

---

### 111. Behavioral Monitoring

Communication behavior should be continuously monitored.

Relevant indicators include:

* unusual communication partners;
* abnormal request frequency;
* unexpected delegation;
* unusual data volumes;
* unusual message types;
* repeated authorization failures;
* abnormal transaction patterns.

Behavioral monitoring complements deterministic security controls.

---

### 112. Agent Activity Logging

Security-relevant interactions should be logged.

At minimum:

```text
Timestamp
Sender Agent
Receiver Agent
Message Type
Request ID
Requested Capability
Resource
Authorization Result
Execution Result
Risk Decision
```

Logs should support reconstruction of the complete communication chain.

---

### 113. Tamper-Resistant Audit Logging

Security logs should be protected against modification by the agents being monitored.

Controls may include:

* centralized logging;
* immutable storage;
* append-only records;
* cryptographic integrity;
* restricted administrative access;
* separate security ownership.

An agent should not be able to erase evidence of its own communication activity.

---

### 114. Agent Security Observability

Observability should provide visibility into the complete agent communication lifecycle.

```text
Agent A
   │
   ├── Request
   ▼
Gateway
   │
   ├── Authentication
   ├── Authorization
   ├── Policy
   ├── Risk
   ▼
Agent B
   │
   ├── Tool
   ├── Data
   └── Transaction
```

Security teams should be able to correlate these events into one trace.

---

### 115. Agent Risk Detection

Risk detection should identify communication patterns that may indicate compromise or misuse.

Examples include:

* privilege-seeking behavior;
* unusual agent discovery;
* rapid expansion of communication relationships;
* unauthorized delegation;
* repeated policy violations;
* abnormal transaction requests;
* communication with blocked agents.

Risk detection should feed security operations and automated containment mechanisms.

---

### 116. Secure Failure Handling

When communication security controls fail, the default behavior should be secure.

Examples:

```text
Authentication failure → DENY
Authorization unavailable → DENY or HOLD
Policy service unavailable → FAIL CLOSED
Message integrity failure → REJECT
Unknown agent → DENY
Expired request → REJECT
Delegation invalid → DENY
```

For high-impact operations, uncertainty should not result in autonomous execution.

---

### 117. Core Engineering Principle

The core engineering principle for AI-to-AI communication is:

> **AI agents must communicate through independently enforced identity, authorization, integrity, data, delegation, and execution controls; no agent should gain authority merely because another agent requested an action.**

The security architecture must preserve the distinction:

```text
Agent Capability
       ≠
Agent Authority
       ≠
Delegated Authority
       ≠
Authorization to Execute
```

AI-to-AI communication should therefore be designed as a **zero-trust, policy-enforced, observable, bounded, and independently authorized interaction model**.

## Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. AI-to-AI Communication Governance Framework

Organizations should establish a formal governance framework for AI-to-AI communication that defines how agents may discover, communicate, delegate, exchange information, and initiate downstream actions.

The governance framework should address:

* approved agent relationships;
* communication purposes;
* agent ownership;
* trust classifications;
* authorization requirements;
* delegation boundaries;
* data-sharing restrictions;
* monitoring requirements;
* incident response;
* audit evidence;
* lifecycle management.

AI-to-AI communication should therefore be governed as an enterprise security capability rather than treated as an internal application feature.

---

### 119. Agent Ownership and Accountability

Every production agent should have an accountable business and technical owner.

Ownership should establish responsibility for:

* agent purpose;
* communication relationships;
* authorized capabilities;
* security configuration;
* risk acceptance;
* monitoring;
* incident response;
* lifecycle decisions.

A communication relationship without accountable ownership creates an unmanaged security dependency.

---

### 120. Enterprise Agent Communication Inventory

Organizations should maintain an inventory of agents and their communication relationships.

A communication inventory should identify:

| Attribute           | Example                  |
| ------------------- | ------------------------ |
| Sender Agent        | Security-Agent-01        |
| Receiver Agent      | Incident-Agent-02        |
| Purpose             | Incident enrichment      |
| Data Classification | Confidential             |
| Risk Tier           | Medium                   |
| Delegation          | Not permitted            |
| Human Approval      | Required for containment |
| Owner               | Security Operations      |
| Status              | Approved                 |

The inventory should represent both **agents** and the **relationships between agents**.

---

### 121. Agent Communication Classification

Agent communication relationships should be classified according to factors such as:

* business purpose;
* data sensitivity;
* autonomy;
* transaction capability;
* downstream reach;
* external connectivity;
* delegation capability;
* potential impact.

A simple classification could be:

```text id="o3l2sv"
Tier 1 — Informational
Tier 2 — Operational
Tier 3 — Sensitive
Tier 4 — High Impact
Tier 5 — Critical Autonomous Interaction
```

Higher-risk communication should require stronger governance and assurance.

---

### 122. Communication Risk Tiering

Risk should be evaluated based on the consequences of a compromised communication path.

For example:

| Risk      | Communication          | Example                          |
| --------- | ---------------------- | -------------------------------- |
| Low       | Read-only information  | Product lookup                   |
| Moderate  | Operational task       | Create support ticket            |
| High      | Sensitive data         | Employee records                 |
| Very High | Financial action       | Payment request                  |
| Critical  | Privileged/destructive | Production infrastructure change |

Communication risk should be based on **potential downstream impact**, not merely message sensitivity.

---

### 123. Agent Communication Approval Governance

New high-risk agent relationships should undergo formal approval before production use.

Approval should evaluate:

* business necessity;
* agent identities;
* permissions;
* data flows;
* delegated authority;
* transaction capabilities;
* security controls;
* monitoring;
* recovery mechanisms.

The approval should be documented as part of the AI governance record.

---

### 124. Communication Purpose Limitation

Every approved agent relationship should have a defined business purpose.

For example:

```text id="4w3s7q"
Agent A → Agent B

Approved Purpose:
"Retrieve approved customer account status."

Not automatically approved:
- Modify account
- Delete account
- Change privileges
- Export customer database
```

Communication authorization should therefore be constrained by purpose rather than treated as unrestricted connectivity.

---

### 125. Agent Authority Governance

Governance should define what authority may be exercised through AI-to-AI communication.

The critical distinction is:

> **An agent may be capable of requesting an action without being authorized to cause that action.**

Authority should be explicitly documented and technically enforced.

---

### 126. Agent-to-Agent Access Governance

Agent relationships should be governed similarly to enterprise access relationships.

Governance should establish:

* approved sender;
* approved receiver;
* allowed operations;
* allowed resources;
* allowed data;
* permitted time;
* transaction limits;
* delegation restrictions.

This creates an explicit access model for autonomous communication.

---

### 127. Agent Communication Access Reviews

Communication relationships should be periodically reviewed.

Reviews should determine whether:

* the relationship is still required;
* the business purpose remains valid;
* permissions remain appropriate;
* data access remains justified;
* risk has changed;
* the connected agents have changed;
* delegation remains necessary.

Unused or unnecessary relationships should be removed.

---

### 128. Least-Privilege Communication Governance

Agent communication should follow least privilege.

An agent should receive only the communication capabilities required for its business function.

```text id="hps7du"
Required Capability
       │
       ▼
Minimum Communication Permission
       │
       ▼
Limited Data
       │
       ▼
Limited Action
```

Least privilege should apply to both **who an agent can communicate with** and **what it can request through that communication**.

---

### 129. Agent Capability Governance

Organizations should maintain a defined capability model for agents.

Capabilities may include:

* read data;
* write data;
* execute transactions;
* invoke tools;
* initiate workflows;
* delegate tasks;
* communicate externally;
* modify configuration.

Capabilities should be explicitly mapped to risk classifications.

---

### 130. Communication Relationship Governance

An approved relationship should define more than connectivity.

For example:

```text id="myu4u0"
Agent A
   │
   ├── Can communicate with → Agent B
   ├── Allowed message → Information Request
   ├── Data scope → Customer Status
   ├── Delegation → No
   ├── Transaction → No
   └── Duration → Continuous
```

This provides governance over the **meaning and consequences** of communication.

---

### 131. Agent Discovery Governance

Agents should not automatically discover every other agent in the enterprise.

Agent discovery should be governed through:

* approved registries;
* identity directories;
* access policies;
* environment boundaries;
* service catalogs.

Unrestricted discovery increases the potential attack surface and makes unauthorized agent relationships easier to establish.

---

### 132. Agent Registry Governance

The enterprise agent registry should maintain authoritative information about:

* agent identity;
* owner;
* purpose;
* risk tier;
* capabilities;
* communication relationships;
* data access;
* external dependencies;
* lifecycle status.

The registry should become a foundational GRC data source.

---

### 133. Agent-to-Agent Governance

Multi-agent environments require governance over how agents interact as a system.

Governance should address:

* peer communication;
* hierarchical communication;
* supervisor relationships;
* delegation;
* escalation;
* shared memory;
* shared tools;
* cross-agent workflows.

A collection of individually compliant agents can still create systemic risk when their relationships are poorly governed.

---

### 134. Delegation Governance

Delegation should be explicitly governed.

The policy should define:

* who can delegate;
* who can receive delegated authority;
* what capabilities can be delegated;
* maximum delegation depth;
* whether further delegation is allowed;
* maximum duration;
* transaction limits;
* revocation mechanisms.

Delegation should never silently expand authority.

---

### 135. Transitive Authority Governance

Organizations should explicitly prevent uncontrolled authority propagation.

For example:

```text id="h4x7fy"
Agent A
  │
  │ Authority: Read
  ▼
Agent B
  │
  │ Delegation
  ▼
Agent C
```

Agent C should not receive more authority than Agent B was legitimately granted.

A useful governance principle is:

> **Delegated authority must not exceed the authority of the delegating context.**

---

### 136. Data Governance for AI-to-AI Communication

### 203. Approval Integrity

Human approvals should be:

* authenticated;
* attributable;
* time-bound;
* action-specific;
* tamper-resistant;
* auditable.

An agent should not be able to manufacture an approval statement and present it to another agent as legitimate authorization.

---

### 204. Dual Control and Segregation of Duties

Critical agent transactions should support separation of responsibilities.

```text
Agent Request
     │
     ├── Requesting Function
     │
     ├── Authorization Function
     │
     └── Execution Function
```

No single agent should necessarily control the entire sequence for high-impact operations.

---

### 205. Agent Communication Kill-Switch Architecture

Emergency controls should be capable of stopping communication independently of the affected agents.

```text
Security Operations
        │
        ▼
Communication Control Plane
        │
        ├── Block Agent A
        ├── Block Agent B
        ├── Revoke Credentials
        └── Freeze Transactions
```

The control must remain operational even when an agent is malfunctioning or compromised.

---

### 206. Blast-Radius Reduction

Agent communication architecture should minimize the number of systems affected by a compromised agent.

Methods include:

* communication allowlisting;
* privilege segmentation;
* transaction limits;
* delegation restrictions;
* tenant isolation;
* network segmentation;
* independent authorization.

```text
Compromised Agent
       │
       ▼
Restricted Relationships
       │
       ▼
Limited Downstream Impact
```

---

### 207. Agent Communication Circuit Breakers

Circuit breakers should interrupt abnormal communication behavior.

Triggers may include:

* excessive request volume;
* repeated authorization failures;
* unusual delegation;
* abnormal transaction activity;
* communication loops;
* rapid expansion of downstream interactions.

Once triggered, the system can:

```text
STOP → ISOLATE → ALERT → INVESTIGATE → RECOVER
```

* identity;

Testing should include both normal and adversarial communication patterns.

### 233. Agent Security Boundary Enforcement

Security boundaries must exist independently of agent reasoning.

An agent should not be able to say:

```text
"I am authorized."
```

and thereby become authorized.

Authorization must be enforced by trusted infrastructure.

The architecture should preserve:

```text
Model Decision
      ≠
Security Decision
      ≠
Execution Authorization
```

### 234. Model Behavior Is Not Security Authorization

A model may determine that an action appears appropriate.

That does not authorize the action.

```text
Agent Reasoning
      ↓
Proposed Request
      ↓
Independent Authorization
      ↓
Policy Enforcement
      ↓
Execution
```

This separation is fundamental to secure autonomous systems.

---

### 235. Agent Capability Is Not Agent Authority

An agent may technically possess the capability to communicate with another agent while being prohibited from exercising certain functions through that relationship.

For example:

```text
Capability:
Can send message to Payment Agent

Authority:
Cannot request payments above €1,000
```

Security architecture must enforce authority independently of technical capability.

### 236. Autonomous Execution Must Remain Bounded

AI-to-AI communication should always operate within explicit boundaries.

Those boundaries should include:

* identity;
* purpose;
* scope;
* permissions;
* data;
* time;
* transaction value;
* delegation depth;
* downstream reach.

```text
Autonomous Communication
        │
        ▼
Bounded Authority
        │
        ▼
Independent Controls
        │
        ▼
Controlled Execution
```

Autonomy should never mean unrestricted authority propagation.

---

### 237. Agent Compromise Must Not Equal Enterprise Compromise

The compromise of one agent should not provide unrestricted access to connected agents or enterprise systems.

The architecture should enforce:

```text
Compromised Agent
       ↓
Restricted Communication
       ↓
Independent Authorization
       ↓
Limited Capabilities
       ↓
Contained Blast Radius
```

This principle should influence identity, authorization, network design, delegation, monitoring, and incident response.

---

### 238. Autonomous Systems Require Independent Control

The final security control cannot reside entirely within the agent being controlled.

Critical functions should therefore have independent mechanisms for:

* authorization;
* policy enforcement;
* monitoring;
* credential revocation;
* isolation;
* transaction blocking;
* emergency shutdown.

The agent should never be the sole authority responsible for deciding whether its own behavior is permissible.

AI-to-AI communication security requires continuous assurance because agent behavior, models, tools, relationships, data, and threat conditions can change over time.
