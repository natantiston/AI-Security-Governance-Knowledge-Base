# 11.15 — Agent-to-Agent Security Risks

## Part 1

### 1. Definition of Agent-to-Agent Security Risk

Agent-to-Agent Security Risk is the potential for one AI agent to negatively affect the confidentiality, integrity, availability, authorization, or security posture of another agent or of the enterprise systems connected to those agents.

The risk exists because agents can exchange:

* Instructions
* Data
* Context
* Decisions
* Credentials
* Delegated authority
* Tool capabilities
* Transaction requests
* Security-relevant information

An agent relationship therefore creates a security dependency that must be explicitly controlled.

---

### 2. Agent-to-Agent Risk as a Distinct Security Domain

Agent-to-agent interactions introduce security risks that do not exist in the same form within isolated single-agent systems.

An agent may:

```text
Receive information
      ↓
Trust another agent
      ↓
Accept a recommendation
      ↓
Delegate authority
      ↓
Invoke tools
      ↓
Execute an action
```

A compromise at one point in this chain can propagate through otherwise legitimate agents.

Agent-to-agent security therefore requires independent analysis of the relationships between agents.

---

### 3. Trust Between Agents

Trust between agents represents the degree to which one agent is permitted to rely on another agent's identity, messages, decisions, data, or delegated authority.

Trust should never be interpreted as unrestricted confidence.

A trusted relationship should specify:

* Who is trusted
* For what purpose
* Under which conditions
* For which resources
* For which operations
* For how long
* With what authority

---

### 4. Agent Relationship Risk

Every agent-to-agent relationship creates a security relationship that can introduce:

* Dependency
* Privilege propagation
* Data exposure
* Instruction propagation
* Credential exposure
* Operational dependency
* Cascading compromise

The security risk depends not only on the individual agents but also on how they interact.

Two individually secure agents can create an insecure system if their relationship permits excessive authority transfer.

---

### 5. Agent Identity Risk

An agent must have a unique and verifiable identity before another agent can safely interact with it.

Identity risk occurs when an agent:

* Cannot be uniquely identified
* Uses shared identities
* Has ambiguous ownership
* Has weak identity binding
* Changes identity unexpectedly
* Cannot be correlated with its execution environment

Without reliable identity, an enterprise cannot confidently determine which agent performed an operation.

---

### 6. Authentication Risk

Authentication risk occurs when an agent accepts communication from another agent without sufficiently establishing its identity.

Weak authentication can allow:

```text
Attacker
   ↓
Impersonates Agent B
   ↓
Agent A trusts attacker
   ↓
Sensitive information disclosed
```

Agent authentication must therefore establish the identity of the communicating workload independently from the content of its message.

---

### 7. Authorization Risk

Authentication determines who an agent is; authorization determines what that agent is allowed to do.

An authenticated agent can still be malicious, compromised, or improperly authorized.

For example:

```text
Agent B = Successfully Authenticated

BUT

Agent B ≠ Authorized to:
- Read Customer Database
- Modify Security Policy
- Execute Financial Transaction
```

Agent-to-agent authentication must therefore never be treated as equivalent to authorization.

---

### 8. Delegation Risk

One agent may delegate work to another agent.

Delegation creates additional risk because authority can move across agent boundaries.

```text
User
 ↓
Agent A
 ↓ delegates
Agent B
 ↓ delegates
Agent C
```

Without explicit controls, Agent C may ultimately receive authority that the original initiating agent was never intended to transfer.

---

### 9. Transitive Authority

Transitive authority occurs when authority granted to one agent is indirectly propagated through additional agents.

For example:

```text
Agent A
  |
  | Authority
  v
Agent B
  |
  | Authority
  v
Agent C
```

If the system does not restrict delegation, Agent C could acquire effective authority far beyond its intended role.

Transitive authority is therefore a major source of agent-to-agent privilege escalation.

---

### 10. Privilege Amplification

Privilege amplification occurs when interaction with another agent enables an agent to perform actions beyond its original authorization.

For example:

```text
Low-Privilege Agent
       |
       v
High-Privilege Agent
       |
       v
Sensitive Enterprise Action
```

The low-privilege agent may exploit the high-privilege agent as an indirect path to protected resources.

This resembles a confused-deputy problem in conventional security, but autonomous reasoning and delegation can make the relationship more dynamic.

---

### 11. Agent Impersonation

Agent impersonation occurs when an unauthorized entity presents itself as a legitimate agent.

Potential consequences include:

* Unauthorized data access
* False instructions
* Malicious delegation
* Tool access
* Transaction requests
* Credential disclosure
* Manipulation of downstream agents

Identity must therefore be cryptographically and operationally bound to the actual executing workload where practical.

---

### 12. Agent Spoofing

Agent spoofing is the presentation of false agent identity or attributes.

An attacker may attempt to spoof:

* Agent name
* Agent identifier
* Agent role
* Agent capability
* Agent environment
* Agent provider
* Agent authorization level

Security controls should validate identity claims rather than trusting self-declared agent attributes.

---

### 13. Agent Hijacking Through Another Agent

An attacker does not always need to compromise an agent directly.

They may compromise another agent that has a trusted relationship with the target.

```text
Attacker
   ↓
Compromise Agent A
   ↓
Trusted Relationship
   ↓
Agent B
   ↓
Enterprise Resources
```

The trusted relationship becomes the attack path.

This creates a critical security requirement: **trust between agents must not become transitive trust in everything an agent says or requests.**

---

### 14. Malicious Agent

A malicious agent is an agent intentionally designed or configured to perform harmful behavior.

It may:

* Exfiltrate data
* Manipulate another agent
* Request excessive privileges
* Circumvent controls
* Send malicious instructions
* Abuse tools
* Initiate unauthorized transactions

The malicious-agent threat must be considered even when the surrounding infrastructure is technically functional.

---

### 15. Compromised Agent

A compromised agent is a legitimate agent whose security boundary has been breached.

The agent may retain valid:

* Identity
* Credentials
* Permissions
* Tool access
* Relationships
* Context

This makes compromise particularly dangerous.

A compromised agent can potentially use legitimate trust relationships to attack other agents.

---

### 16. Rogue Agent

A rogue agent is an agent that operates outside its approved security, business, or governance boundaries.

A rogue agent may result from:

* Unauthorized deployment
* Configuration changes
* Compromised infrastructure
* Shadow AI
* Unapproved integrations
* Malicious modification
* Governance failure

An enterprise agent inventory should therefore account for unauthorized agents, not only approved agents.

---

### 17. Untrusted Agent

An untrusted agent is an agent whose security posture, identity, provenance, ownership, or behavior has not been sufficiently established.

Untrusted agents should not receive privileged access merely because they can communicate using an accepted protocol.

A useful principle is:

```text
Protocol Compatibility
        ≠
Security Trust
```

---

### 18. Agent Discovery Risk

Agents may discover other agents dynamically.

Discovery can expose:

* Agent names
* Capabilities
* Endpoints
* Roles
* Available tools
* Supported operations
* Trust relationships

Excessive discovery information can provide attackers with a map of the agent ecosystem.

Agent discovery should therefore expose only information necessary for legitimate interaction.

---

### 19. Agent Registry Risk

An agent registry may become a high-value security target because it defines which agents exist and how they relate to one another.

Manipulation of the registry could result in:

```text
False Agent Registration
        ↓
False Identity
        ↓
False Trust Relationship
        ↓
Unauthorized Communication
```

Agent registries should therefore have strong integrity, authorization, monitoring, and change-control protections.

---

### 20. Agent Capability Exposure

Agents may advertise capabilities to other agents.

For example:

```text
Agent A:
- Read CRM
- Send Email
- Create Ticket

Agent B:
- Query Finance
- Approve Refund
- Execute Payment
```

Excessive capability disclosure can help attackers identify paths toward sensitive operations.

Capability information should therefore be minimized and appropriately classified.

---

### 21. Agent-to-Agent Message Risk

Messages between agents may contain:

* Instructions
* Data
* Commands
* Decisions
* Tool requests
* Credentials
* Context
* Authorization claims

A malicious or compromised agent can therefore use messages as an attack mechanism.

Message content must not automatically be considered trustworthy merely because it originated from another authenticated agent.

---

### 22. Message Integrity Risk

Message integrity risk occurs when messages are modified, corrupted, or manipulated while in transit or before processing.

For example:

```text
Agent A
  |
  | "Read customer record"
  |
  X  Manipulation
  |
  v
Agent B
  |
  | "Delete customer record"
```

Message integrity mechanisms should ensure that the receiving agent can detect unauthorized modification.

---

### 23. Message Confidentiality Risk

Agent-to-agent messages may contain sensitive enterprise information.

Exposure may involve:

* Personal data
* Credentials
* Business information
* Security information
* Financial information
* Proprietary data
* Customer information

Confidentiality therefore requires appropriate encryption, access controls, data minimization, and routing restrictions.

---

### 24. Message Replay Risk

Replay occurs when a previously valid message is captured and submitted again.

For example:

```text
Agent A → Agent B
"Approve Transaction X"

Attacker captures message

Later:
Attacker → Agent B
"Approve Transaction X"
```

Without replay protection, a valid historical instruction may become an unauthorized new instruction.

---

### 25. Message Injection

Message injection occurs when an attacker introduces unauthorized content into an agent-to-agent communication flow.

The injected content may attempt to:

* Change objectives
* Request sensitive data
* Trigger tools
* Escalate privileges
* Modify persistent context
* Initiate transactions

The receiving agent must distinguish between authenticated message transport and trustworthy message semantics.

---

### 26. Cross-Agent Prompt Injection

Prompt injection can propagate from one agent to another.

For example:

```text
External Content
      ↓
Agent A
      ↓
Malicious Instruction
      ↓
Agent B
      ↓
Tool Invocation
```

Agent B may incorrectly treat information generated or transmitted by Agent A as a trusted instruction.

Cross-agent communication therefore creates a pathway through which injection attacks can propagate.

---

### 27. Instruction Propagation

An instruction generated by one agent may become input to another agent.

This creates a trust problem:

```text
Agent A's Output
        ↓
Agent B's Input
        ↓
Agent B's Reasoning
        ↓
Agent B's Action
```

The receiving agent should not automatically elevate another agent's output to the status of a trusted enterprise instruction.

---

### 28. Context Propagation

Agents may transfer context between one another.

Context can include:

* User information
* Previous decisions
* Historical interactions
* Security state
* Business information
* Instructions
* Retrieved data

Improper context propagation can cause:

* Data leakage
* Trust contamination
* Tenant boundary violations
* Incorrect assumptions
* Unauthorized influence on downstream agents

---

### 29. Memory Propagation

Persistent memory can also propagate between agents.

For example:

```text
Agent A Memory
      ↓
Agent B
      ↓
Agent B Memory
      ↓
Agent C
```

If poisoned information enters the chain, it may persist and spread across multiple agents.

Memory propagation therefore creates a long-lived form of agent-to-agent risk.

---

### 30. Trust Propagation

Trust propagation occurs when one agent implicitly transfers its trust assessment to another agent.

For example:

```text
Agent A trusts Agent B
       ↓
Agent B introduces Agent C
       ↓
Agent A trusts Agent C
```

This assumption is unsafe unless explicitly authorized.

Trust must be evaluated independently at each security boundary.

---

### 31. Credential Propagation

Agents may attempt to pass credentials, tokens, or authentication material to other agents.

This creates significant risk because:

* Credentials may escape their intended scope.
* The receiving agent may have weaker controls.
* Attribution can be lost.
* Revocation becomes more difficult.
* Privileges may be unintentionally combined.

Credentials should generally remain bound to their intended security principal and purpose.

---

### 32. Delegated Credential Risk

Delegated credentials create additional risk because one agent can effectively act on behalf of another.

For example:

```text
Agent A
  |
  | Credential / Token
  v
Agent B
  |
  v
Protected Resource
```

If the delegated credential is broader than necessary, compromise of Agent B can expose the authority of Agent A.

Delegation must therefore be bounded by scope, purpose, time, and resource.

---

### 33. Tool Access Propagation

An agent may ask another agent to perform a tool operation.

For example:

```text
Agent A
  |
  | "Send this payment"
  v
Agent B
  |
  | Payment Tool
  v
Financial System
```

Agent A may not have direct payment authority, but could indirectly obtain it through Agent B.

Tool authority must therefore be evaluated across agent relationships rather than only at the immediate tool boundary.

---

### 34. Permission Propagation

Permissions may unintentionally propagate from one agent to another.

Examples include:

* Data access
* API access
* Database permissions
* Administrative privileges
* Transaction authority
* Tool permissions

The receiving agent should obtain only the specific permissions explicitly delegated to it.

---

### 35. Authority Propagation

Authority propagation is broader than permission propagation because it concerns the effective ability to influence enterprise actions.

An agent may not directly possess a sensitive permission but may control another agent that does.

Therefore:

```text
Direct Authority
        +
Indirect Authority
        =
Effective Authority
```

Security architecture must evaluate both.

---

### 36. Agent Chain Risk

A chain of agents creates multiple security dependencies.

Example:

```text
User
 ↓
Agent A
 ↓
Agent B
 ↓
Agent C
 ↓
Tool
 ↓
Enterprise System
```

Each additional agent can introduce:

* Identity risk
* Authorization risk
* Data exposure
* Delegation risk
* Failure risk
* Monitoring complexity

The security risk of the chain can therefore increase as autonomous dependencies grow.

---

### 37. Cascading Agent Compromise

A compromised agent can potentially influence other agents through legitimate relationships.

```text
Compromised Agent A
        ↓
Agent B
        ↓
Agent C
        ↓
Agent D
```

If each agent trusts the previous agent without independent validation, compromise can propagate rapidly.

Cascading compromise is therefore a major concern in multi-agent environments.

---

### 38. Lateral Movement

Agents can potentially become pathways for lateral movement across enterprise systems.

An attacker may move:

```text
Agent A
 ↓
Agent B
 ↓
CRM
 ↓
Finance
 ↓
Identity System
```

The agent network can therefore become analogous to an enterprise network from a security perspective.

Segmentation must prevent a compromised agent from freely traversing the agent ecosystem.

---

### 39. Cross-Agent Privilege Escalation

Cross-agent privilege escalation occurs when an agent uses another agent's higher authority to perform unauthorized operations.

Example:

```text
Agent A — Low Privilege
       |
       v
Agent B — High Privilege
       |
       v
Sensitive System
```

The security boundary must prevent Agent A from converting communication access into the effective privileges of Agent B.

---

### 40. Circular Trust

Circular trust occurs when agents rely on one another to establish trust.

```text
Agent A trusts B
Agent B trusts C
Agent C trusts A
```

This creates a potentially self-reinforcing trust structure where no independent trust anchor exists.

Critical agent relationships should rely on enterprise-controlled identity and authorization mechanisms rather than circular assertions of trust.

---

### 41. Agent Dependency Risk

An agent may become operationally dependent on another agent.

Failure or compromise of the dependency may therefore affect:

* Availability
* Decision quality
* Transactions
* Business workflows
* Security monitoring
* Incident response

Critical dependencies should be identified and resilience mechanisms established.

---

### 42. Agent Communication Availability

Agent-to-agent communication can become a dependency for autonomous workflows.

Availability risks include:

* Communication failure
* Denial of service
* Excessive message volume
* Resource exhaustion
* Network disruption
* Agent overload

Availability controls should prevent one agent from consuming disproportionate resources of another.

---

### 43. Agent Failure Propagation

A malfunctioning agent can generate incorrect or excessive outputs that cause downstream agents to behave incorrectly.

```text
Agent A Failure
      ↓
Incorrect Message
      ↓
Agent B
      ↓
Incorrect Decision
      ↓
Agent C
      ↓
Enterprise Impact
```

Security architecture must therefore account for failure propagation, not only deliberate attacks.

---

### 44. Agent-to-Agent Transaction Risk

Agents may request or authorize transactions through other agents.

Examples include:

* Financial transactions
* Account changes
* Customer actions
* Infrastructure changes
* Access modifications
* Data deletion

A transaction initiated through an agent relationship must retain clear attribution and independent authorization.

---

### 45. Agent Accountability

Every significant agent-to-agent interaction should be attributable.

The enterprise should be able to determine:

```text
Who initiated?
      ↓
Which agent delegated?
      ↓
Which agent executed?
      ↓
What message was exchanged?
      ↓
What authorization was evaluated?
      ↓
What action occurred?
```

Without this chain, incident investigation and governance become significantly more difficult.

---

### 46. Agent Relationship Monitoring

Agent relationships should be continuously monitored for abnormal behavior.

Monitoring can include:

* Unexpected communication
* New agent relationships
* Unusual delegation
* Excessive requests
* Unexpected data transfer
* Permission changes
* Abnormal transaction patterns
* Communication loops

The objective is to detect both compromised agents and compromised relationships.

---

### 47. Agent-to-Agent Attack Surface

The attack surface includes more than the communication channel.

It includes:

```text
Agent Identity
Agent Authentication
Agent Authorization
Agent Discovery
Agent Registry
Messages
Instructions
Context
Memory
Credentials
Delegation
Tools
Permissions
Transactions
Network Paths
Monitoring
```

Each component can become a pathway for compromise or privilege propagation.

---

### 48. Agent-to-Agent Risk Governance

Agent-to-agent relationships should be treated as governance objects.

Governance should define:

* Approved relationships
* Relationship owners
* Trust levels
* Delegation limits
* Data boundaries
* Authority boundaries
* Monitoring requirements
* Review frequency
* Risk acceptance
* Retirement requirements

An enterprise should know not only which agents exist, but **which agents are permitted to trust, influence, delegate to, or act through other agents**.

---

### 49. Core Principles of Agent-to-Agent Security Risks

The fundamental principles are:

1. **Agent identity must be independently established.**
2. **Authentication must not imply authorization.**
3. **Trust must be explicit and bounded.**
4. **Delegated authority must not exceed the original authority.**
5. **Agent capability must not automatically become agent authority.**
6. **Messages from another agent must not automatically be treated as trusted instructions.**
7. **Context and memory must retain their security boundaries during propagation.**
8. **Credentials must not be freely propagated between agents.**
9. **Agent relationships must be monitored independently.**
10. **A compromised agent must not automatically compromise connected agents.**

---

### 50. Core Principle of Agent-to-Agent Security Risks

**An agent-to-agent relationship must never become an uncontrolled trust or authority propagation mechanism.**

Every agent relationship should preserve:

```text
Identity
   +
Authentication
   +
Authorization
   +
Purpose
   +
Scope
   +
Delegation Boundary
   +
Data Boundary
   +
Time Boundary
   +
Attribution
   +
Monitoring
```

The fundamental security objective is to ensure that **communication between autonomous agents remains bounded, independently authorized, attributable, and incapable of converting one agent's compromise into uncontrolled enterprise-wide authority**.
