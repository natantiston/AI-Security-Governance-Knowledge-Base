# 11.15 — Agent-to-Agent Security Risks

## Part 1

### 1. Definition of Agent-to-Agent Security Risk

Agent-to-Agent Security Risk is the potential for one AI agent to negatively affect the confidentiality, integrity, availability, authorization, or security posture of another agent or of the enterprise systems connected to those agents.

The risk exists because agents can exchange:

* Instructions
* Data
* Context
* Decisions
* Credentials
* Delegated authority
* Tool capabilities
* Transaction requests
* Security-relevant information

An agent relationship therefore creates a security dependency that must be explicitly controlled.

---

### 2. Agent-to-Agent Risk as a Distinct Security Domain

Agent-to-agent interactions introduce security risks that do not exist in the same form within isolated single-agent systems.

An agent may:

```text
Receive information
      ↓
Trust another agent
      ↓
Accept a recommendation
      ↓
Delegate authority
      ↓
Invoke tools
      ↓
Execute an action
```

A compromise at one point in this chain can propagate through otherwise legitimate agents.

Agent-to-agent security therefore requires independent analysis of the relationships between agents.

---

### 3. Trust Between Agents

Trust between agents represents the degree to which one agent is permitted to rely on another agent's identity, messages, decisions, data, or delegated authority.

Trust should never be interpreted as unrestricted confidence.

A trusted relationship should specify:

* Who is trusted
* For what purpose
* Under which conditions
* For which resources
* For which operations
* For how long
* With what authority

---

### 4. Agent Relationship Risk

Every agent-to-agent relationship creates a security relationship that can introduce:

* Dependency
* Privilege propagation
* Data exposure
* Instruction propagation
* Credential exposure
* Operational dependency
* Cascading compromise

The security risk depends not only on the individual agents but also on how they interact.

Two individually secure agents can create an insecure system if their relationship permits excessive authority transfer.

---

### 5. Agent Identity Risk

An agent must have a unique and verifiable identity before another agent can safely interact with it.

Identity risk occurs when an agent:

* Cannot be uniquely identified
* Uses shared identities
* Has ambiguous ownership
* Has weak identity binding
* Changes identity unexpectedly
* Cannot be correlated with its execution environment

Without reliable identity, an enterprise cannot confidently determine which agent performed an operation.

---

### 6. Authentication Risk

Authentication risk occurs when an agent accepts communication from another agent without sufficiently establishing its identity.

Weak authentication can allow:

```text
Attacker
   ↓
Impersonates Agent B
   ↓
Agent A trusts attacker
   ↓
Sensitive information disclosed
```

Agent authentication must therefore establish the identity of the communicating workload independently from the content of its message.

---

### 7. Authorization Risk

Authentication determines who an agent is; authorization determines what that agent is allowed to do.

An authenticated agent can still be malicious, compromised, or improperly authorized.

For example:

```text
Agent B = Successfully Authenticated

BUT

Agent B ≠ Authorized to:
- Read Customer Database
- Modify Security Policy
- Execute Financial Transaction
```

Agent-to-agent authentication must therefore never be treated as equivalent to authorization.

---

### 8. Delegation Risk

One agent may delegate work to another agent.

Delegation creates additional risk because authority can move across agent boundaries.

```text
User
 ↓
Agent A
 ↓ delegates
Agent B
 ↓ delegates
Agent C
```

Without explicit controls, Agent C may ultimately receive authority that the original initiating agent was never intended to transfer.

---

### 9. Transitive Authority

Transitive authority occurs when authority granted to one agent is indirectly propagated through additional agents.

For example:

```text
Agent A
  |
  | Authority
  v
Agent B
  |
  | Authority
  v
Agent C
```

If the system does not restrict delegation, Agent C could acquire effective authority far beyond its intended role.

Transitive authority is therefore a major source of agent-to-agent privilege escalation.

---

### 10. Privilege Amplification

Privilege amplification occurs when interaction with another agent enables an agent to perform actions beyond its original authorization.

For example:

```text
Low-Privilege Agent
       |
       v
High-Privilege Agent
       |
       v
Sensitive Enterprise Action
```

The low-privilege agent may exploit the high-privilege agent as an indirect path to protected resources.

This resembles a confused-deputy problem in conventional security, but autonomous reasoning and delegation can make the relationship more dynamic.

---

### 11. Agent Impersonation

Agent impersonation occurs when an unauthorized entity presents itself as a legitimate agent.

Potential consequences include:

* Unauthorized data access
* False instructions
* Malicious delegation
* Tool access
* Transaction requests
* Credential disclosure
* Manipulation of downstream agents

Identity must therefore be cryptographically and operationally bound to the actual executing workload where practical.

---

### 12. Agent Spoofing

Agent spoofing is the presentation of false agent identity or attributes.

An attacker may attempt to spoof:

* Agent name
* Agent identifier
* Agent role
* Agent capability
* Agent environment
* Agent provider
* Agent authorization level

Security controls should validate identity claims rather than trusting self-declared agent attributes.

---

### 13. Agent Hijacking Through Another Agent

An attacker does not always need to compromise an agent directly.

They may compromise another agent that has a trusted relationship with the target.

```text
Attacker
   ↓
Compromise Agent A
   ↓
Trusted Relationship
   ↓
Agent B
   ↓
Enterprise Resources
```

The trusted relationship becomes the attack path.

This creates a critical security requirement: **trust between agents must not become transitive trust in everything an agent says or requests.**

---

### 14. Malicious Agent

A malicious agent is an agent intentionally designed or configured to perform harmful behavior.

It may:

* Exfiltrate data
* Manipulate another agent
* Request excessive privileges
* Circumvent controls
* Send malicious instructions
* Abuse tools
* Initiate unauthorized transactions

The malicious-agent threat must be considered even when the surrounding infrastructure is technically functional.

---

### 15. Compromised Agent

A compromised agent is a legitimate agent whose security boundary has been breached.

The agent may retain valid:

* Identity
* Credentials
* Permissions
* Tool access
* Relationships
* Context

This makes compromise particularly dangerous.

A compromised agent can potentially use legitimate trust relationships to attack other agents.

---

### 16. Rogue Agent

A rogue agent is an agent that operates outside its approved security, business, or governance boundaries.

A rogue agent may result from:

* Unauthorized deployment
* Configuration changes
* Compromised infrastructure
* Shadow AI
* Unapproved integrations
* Malicious modification
* Governance failure

An enterprise agent inventory should therefore account for unauthorized agents, not only approved agents.

---

### 17. Untrusted Agent

An untrusted agent is an agent whose security posture, identity, provenance, ownership, or behavior has not been sufficiently established.

Untrusted agents should not receive privileged access merely because they can communicate using an accepted protocol.

A useful principle is:

```text
Protocol Compatibility
        ≠
Security Trust
```

---

### 18. Agent Discovery Risk

Agents may discover other agents dynamically.

Discovery can expose:

* Agent names
* Capabilities
* Endpoints
* Roles
* Available tools
* Supported operations
* Trust relationships

Excessive discovery information can provide attackers with a map of the agent ecosystem.

Agent discovery should therefore expose only information necessary for legitimate interaction.

---

### 19. Agent Registry Risk

An agent registry may become a high-value security target because it defines which agents exist and how they relate to one another.

Manipulation of the registry could result in:

```text
False Agent Registration
        ↓
False Identity
        ↓
False Trust Relationship
        ↓
Unauthorized Communication
```

Agent registries should therefore have strong integrity, authorization, monitoring, and change-control protections.

---

### 20. Agent Capability Exposure

Agents may advertise capabilities to other agents.

For example:

```text
Agent A:
- Read CRM
- Send Email
- Create Ticket

Agent B:
- Query Finance
- Approve Refund
- Execute Payment
```

Excessive capability disclosure can help attackers identify paths toward sensitive operations.

Capability information should therefore be minimized and appropriately classified.

---

### 21. Agent-to-Agent Message Risk

Messages between agents may contain:

* Instructions
* Data
* Commands
* Decisions
* Tool requests
* Credentials
* Context
* Authorization claims

A malicious or compromised agent can therefore use messages as an attack mechanism.

Message content must not automatically be considered trustworthy merely because it originated from another authenticated agent.

---

### 22. Message Integrity Risk

Message integrity risk occurs when messages are modified, corrupted, or manipulated while in transit or before processing.

For example:

```text
Agent A
  |
  | "Read customer record"
  |
  X  Manipulation
  |
  v
Agent B
  |
  | "Delete customer record"
```

Message integrity mechanisms should ensure that the receiving agent can detect unauthorized modification.

---

### 23. Message Confidentiality Risk

Agent-to-agent messages may contain sensitive enterprise information.

Exposure may involve:

* Personal data
* Credentials
* Business information
* Security information
* Financial information
* Proprietary data
* Customer information

Confidentiality therefore requires appropriate encryption, access controls, data minimization, and routing restrictions.

---

### 24. Message Replay Risk

Replay occurs when a previously valid message is captured and submitted again.

For example:

```text
Agent A → Agent B
"Approve Transaction X"

Attacker captures message

Later:
Attacker → Agent B
"Approve Transaction X"
```

Without replay protection, a valid historical instruction may become an unauthorized new instruction.

---

### 25. Message Injection

Message injection occurs when an attacker introduces unauthorized content into an agent-to-agent communication flow.

The injected content may attempt to:

* Change objectives
* Request sensitive data
* Trigger tools
* Escalate privileges
* Modify persistent context
* Initiate transactions

The receiving agent must distinguish between authenticated message transport and trustworthy message semantics.

---

### 26. Cross-Agent Prompt Injection

Prompt injection can propagate from one agent to another.

For example:

```text
External Content
      ↓
Agent A
      ↓
Malicious Instruction
      ↓
Agent B
      ↓
Tool Invocation
```

Agent B may incorrectly treat information generated or transmitted by Agent A as a trusted instruction.

Cross-agent communication therefore creates a pathway through which injection attacks can propagate.

---

### 27. Instruction Propagation

An instruction generated by one agent may become input to another agent.

This creates a trust problem:

```text
Agent A's Output
        ↓
Agent B's Input
        ↓
Agent B's Reasoning
        ↓
Agent B's Action
```

The receiving agent should not automatically elevate another agent's output to the status of a trusted enterprise instruction.

---

### 28. Context Propagation

Agents may transfer context between one another.

Context can include:

* User information
* Previous decisions
* Historical interactions
* Security state
* Business information
* Instructions
* Retrieved data

Improper context propagation can cause:

* Data leakage
* Trust contamination
* Tenant boundary violations
* Incorrect assumptions
* Unauthorized influence on downstream agents

---

### 29. Memory Propagation

Persistent memory can also propagate between agents.

For example:

```text
Agent A Memory
      ↓
Agent B
      ↓
Agent B Memory
      ↓
Agent C
```

If poisoned information enters the chain, it may persist and spread across multiple agents.

Memory propagation therefore creates a long-lived form of agent-to-agent risk.

---

### 30. Trust Propagation

Trust propagation occurs when one agent implicitly transfers its trust assessment to another agent.

For example:

```text
Agent A trusts Agent B
       ↓
Agent B introduces Agent C
       ↓
Agent A trusts Agent C
```

This assumption is unsafe unless explicitly authorized.

Trust must be evaluated independently at each security boundary.

---

### 31. Credential Propagation

Agents may attempt to pass credentials, tokens, or authentication material to other agents.

This creates significant risk because:

* Credentials may escape their intended scope.
* The receiving agent may have weaker controls.
* Attribution can be lost.
* Revocation becomes more difficult.
* Privileges may be unintentionally combined.

Credentials should generally remain bound to their intended security principal and purpose.

---

### 32. Delegated Credential Risk

Delegated credentials create additional risk because one agent can effectively act on behalf of another.

For example:

```text
Agent A
  |
  | Credential / Token
  v
Agent B
  |
  v
Protected Resource
```

If the delegated credential is broader than necessary, compromise of Agent B can expose the authority of Agent A.

Delegation must therefore be bounded by scope, purpose, time, and resource.

---

### 33. Tool Access Propagation

An agent may ask another agent to perform a tool operation.

For example:

```text
Agent A
  |
  | "Send this payment"
  v
Agent B
  |
  | Payment Tool
  v
Financial System
```

Agent A may not have direct payment authority, but could indirectly obtain it through Agent B.

Tool authority must therefore be evaluated across agent relationships rather than only at the immediate tool boundary.

---

### 34. Permission Propagation

Permissions may unintentionally propagate from one agent to another.

Examples include:

* Data access
* API access
* Database permissions
* Administrative privileges
* Transaction authority
* Tool permissions

The receiving agent should obtain only the specific permissions explicitly delegated to it.

---

### 35. Authority Propagation

Authority propagation is broader than permission propagation because it concerns the effective ability to influence enterprise actions.

An agent may not directly possess a sensitive permission but may control another agent that does.

Therefore:

```text
Direct Authority
        +
Indirect Authority
        =
Effective Authority
```

Security architecture must evaluate both.

---

### 36. Agent Chain Risk

A chain of agents creates multiple security dependencies.

Example:

```text
User
 ↓
Agent A
 ↓
Agent B
 ↓
Agent C
 ↓
Tool
 ↓
Enterprise System
```

Each additional agent can introduce:

* Identity risk
* Authorization risk
* Data exposure
* Delegation risk
* Failure risk
* Monitoring complexity

The security risk of the chain can therefore increase as autonomous dependencies grow.

---

### 37. Cascading Agent Compromise

A compromised agent can potentially influence other agents through legitimate relationships.

```text
Compromised Agent A
        ↓
Agent B
        ↓
Agent C
        ↓
Agent D
```

If each agent trusts the previous agent without independent validation, compromise can propagate rapidly.

Cascading compromise is therefore a major concern in multi-agent environments.

---

### 38. Lateral Movement

Agents can potentially become pathways for lateral movement across enterprise systems.

An attacker may move:

```text
Agent A
 ↓
Agent B
 ↓
CRM
 ↓
Finance
 ↓
Identity System
```

The agent network can therefore become analogous to an enterprise network from a security perspective.

Segmentation must prevent a compromised agent from freely traversing the agent ecosystem.

---

### 39. Cross-Agent Privilege Escalation

Cross-agent privilege escalation occurs when an agent uses another agent's higher authority to perform unauthorized operations.

Example:

```text
Agent A — Low Privilege
       |
       v
Agent B — High Privilege
       |
       v
Sensitive System
```

The security boundary must prevent Agent A from converting communication access into the effective privileges of Agent B.

---

### 40. Circular Trust

Circular trust occurs when agents rely on one another to establish trust.

```text
Agent A trusts B
Agent B trusts C
Agent C trusts A
```

This creates a potentially self-reinforcing trust structure where no independent trust anchor exists.

Critical agent relationships should rely on enterprise-controlled identity and authorization mechanisms rather than circular assertions of trust.

---

### 41. Agent Dependency Risk

An agent may become operationally dependent on another agent.

Failure or compromise of the dependency may therefore affect:

* Availability
* Decision quality
* Transactions
* Business workflows
* Security monitoring
* Incident response

Critical dependencies should be identified and resilience mechanisms established.

---

### 42. Agent Communication Availability

Agent-to-agent communication can become a dependency for autonomous workflows.

Availability risks include:

* Communication failure
* Denial of service
* Excessive message volume
* Resource exhaustion
* Network disruption
* Agent overload

Availability controls should prevent one agent from consuming disproportionate resources of another.

---

### 43. Agent Failure Propagation

A malfunctioning agent can generate incorrect or excessive outputs that cause downstream agents to behave incorrectly.

```text
Agent A Failure
      ↓
Incorrect Message
      ↓
Agent B
      ↓
Incorrect Decision
      ↓
Agent C
      ↓
Enterprise Impact
```

Security architecture must therefore account for failure propagation, not only deliberate attacks.

---

### 44. Agent-to-Agent Transaction Risk

Agents may request or authorize transactions through other agents.

Examples include:

* Financial transactions
* Account changes
* Customer actions
* Infrastructure changes
* Access modifications
* Data deletion

A transaction initiated through an agent relationship must retain clear attribution and independent authorization.

---

### 45. Agent Accountability

Every significant agent-to-agent interaction should be attributable.

The enterprise should be able to determine:

```text
Who initiated?
      ↓
Which agent delegated?
      ↓
Which agent executed?
      ↓
What message was exchanged?
      ↓
What authorization was evaluated?
      ↓
What action occurred?
```

Without this chain, incident investigation and governance become significantly more difficult.

---

### 46. Agent Relationship Monitoring

Agent relationships should be continuously monitored for abnormal behavior.

Monitoring can include:

* Unexpected communication
* New agent relationships
* Unusual delegation
* Excessive requests
* Unexpected data transfer
* Permission changes
* Abnormal transaction patterns
* Communication loops

The objective is to detect both compromised agents and compromised relationships.

---

### 47. Agent-to-Agent Attack Surface

The attack surface includes more than the communication channel.

It includes:

```text
Agent Identity
Agent Authentication
Agent Authorization
Agent Discovery
Agent Registry
Messages
Instructions
Context
Memory
Credentials
Delegation
Tools
Permissions
Transactions
Network Paths
Monitoring
```

Each component can become a pathway for compromise or privilege propagation.

---

### 48. Agent-to-Agent Risk Governance

Agent-to-agent relationships should be treated as governance objects.

Governance should define:

* Approved relationships
* Relationship owners
* Trust levels
* Delegation limits
* Data boundaries
* Authority boundaries
* Monitoring requirements
* Review frequency
* Risk acceptance
* Retirement requirements

An enterprise should know not only which agents exist, but **which agents are permitted to trust, influence, delegate to, or act through other agents**.

---

### 49. Core Principles of Agent-to-Agent Security Risks

The fundamental principles are:

1. **Agent identity must be independently established.**
2. **Authentication must not imply authorization.**
3. **Trust must be explicit and bounded.**
4. **Delegated authority must not exceed the original authority.**
5. **Agent capability must not automatically become agent authority.**
6. **Messages from another agent must not automatically be treated as trusted instructions.**
7. **Context and memory must retain their security boundaries during propagation.**
8. **Credentials must not be freely propagated between agents.**
9. **Agent relationships must be monitored independently.**
10. **A compromised agent must not automatically compromise connected agents.**

---

### 50. Core Principle of Agent-to-Agent Security Risks

**An agent-to-agent relationship must never become an uncontrolled trust or authority propagation mechanism.**

Every agent relationship should preserve:

```text
Identity
   +
Authentication
   +
Authorization
   +
Purpose
   +
Scope
   +
Delegation Boundary
   +
Data Boundary
   +
Time Boundary
   +
Attribution
   +
Monitoring
```

The fundamental security objective is to ensure that **communication between autonomous agents remains bounded, independently authorized, attributable, and incapable of converting one agent's compromise into uncontrolled enterprise-wide authority**.

# Part 2

## 51. Agent-to-Agent Security Risk Control Architecture

Agent-to-agent security controls must protect the complete relationship between communicating agents rather than securing only the communication channel.

The control architecture should address:

* Agent identity
* Authentication
* Authorization
* Trust relationships
* Message integrity
* Delegation
* Permission propagation
* Context propagation
* Credential use
* Tool access
* Transaction authority
* Monitoring
* Containment

A representative architecture is:

```text
+-------------------+          +-------------------+
|     Agent A       |          |     Agent B       |
+---------+---------+          +---------+---------+
          |                              |
          +------------+  +--------------+
                       |  |
                       v  v
              +-------------------+
              | Agent Security    |
              | Gateway / Policy  |
              +---------+---------+
                        |
              +---------+---------+
              | Identity / Auth   |
              | Authorization     |
              | Policy Engine     |
              +---------+---------+
                        |
                        v
              +-------------------+
              | Security Controls |
              +-------------------+
```

The architecture should prevent an authenticated agent from automatically acquiring the authority of another agent.

---

## 52. Agent Identity Control

Every agent participating in an agent-to-agent relationship should have a unique, verifiable identity.

Identity controls should establish:

* Unique agent identifier
* Agent owner
* Deployment environment
* Application association
* Tenant association
* Agent version
* Runtime identity
* Identity status

Agent identity should be bound to the actual workload wherever technically feasible.

---

## 53. Agent-to-Agent Authentication

Agents should authenticate one another before exchanging security-sensitive information or requesting protected operations.

Authentication mechanisms may include:

* Mutual TLS
* Workload identity
* Cryptographic tokens
* Signed assertions
* Platform-attested identities
* Enterprise identity services

Authentication should occur at the communication boundary rather than relying solely on application-level claims.

---

## 54. Strong Agent Authentication

Strong authentication should protect high-value agent relationships against impersonation and spoofing.

Controls should include:

* Cryptographic authentication
* Mutual authentication
* Credential protection
* Certificate validation
* Token validation
* Audience restriction
* Expiration
* Replay protection

The authentication mechanism should establish the identity of the executing agent, not merely the identity claimed within its message.

---

## 55. Fine-Grained Agent Authorization

Authorization should determine exactly what one agent may request from another.

Authorization should consider:

```text
Initiating Agent
      +
Receiving Agent
      +
Requested Operation
      +
Resource
      +
Purpose
      +
Context
      +
Risk
      =
Authorization Decision
```

A relationship allowing Agent A to query Agent B should not automatically allow Agent A to modify Agent B's resources.

---

## 56. Independent Authorization Service

Critical agent-to-agent authorization should be enforced by an authorization mechanism independent of the agent's reasoning process.

For example:

```text
Agent A
   |
   | Request
   v
Authorization Service
   |
   +--> ALLOW
   |
   +--> DENY
   |
   +--> REQUIRE APPROVAL
   |
   v
Agent B
```

Agent B should not rely exclusively on Agent A's assertion that the request is authorized.

---

## 57. Agent Communication Allowlisting

Agent-to-agent relationships should be explicitly allowlisted where practical.

Example:

```text
Agent A → Agent B       ALLOW
Agent A → Agent C       DENY
Agent B → Agent C       ALLOW
Agent C → Agent A       DENY
```

Allowlisting reduces the attack surface by preventing arbitrary agents from initiating relationships.

---

## 58. Message Type Allowlisting

Not every type of message should be permitted between every agent.

Allowed message categories may include:

* Query
* Response
* Recommendation
* Task request
* Delegation request
* Status update
* Transaction request

High-risk message types should require stronger authorization.

---

## 59. Tool Capability Segmentation

Agent-to-agent relationships should not provide unrestricted access to another agent's tools.

Tool capabilities should be segmented according to:

* Function
* Sensitivity
* Business impact
* Data access
* Transaction authority
* Environment

For example:

```text
Agent B
 ├── Search Tool       → Agent A: Allowed
 ├── Ticket Tool       → Agent A: Allowed
 ├── Admin Tool        → Agent A: Denied
 └── Payment Tool      → Agent A: Approval Required
```

---

## 60. Message Schema Validation

Agent messages should conform to approved schemas.

Validation should check:

* Required fields
* Data types
* Message type
* Agent identifiers
* Requested operation
* Resource identifiers
* Authorization metadata
* Expiration
* Correlation identifiers

Schema validation reduces ambiguity and prevents malformed requests from reaching downstream agents.

---

## 61. Message Content Validation

Valid message structure does not guarantee safe content.

Content validation should identify:

* Unexpected instructions
* Unauthorized commands
* Suspicious parameters
* Embedded credentials
* Injection patterns
* Conflicting authority claims
* Unexpected data classification
* Unsupported operations

Structured communication should therefore be validated semantically as well as syntactically.

---

## 62. Agent Message Integrity

Messages should have appropriate integrity protection so receiving agents can detect unauthorized modification.

Controls may include:

* Digital signatures
* Message authentication codes
* TLS
* Integrity-protected tokens
* Sequence identifiers

Message integrity should cover security-critical fields, not merely the transport envelope.

---

## 63. Message Replay Protection

Agent-to-agent requests should be protected against replay.

Controls may include:

* Nonces
* Timestamps
* Sequence numbers
* Unique request identifiers
* Short-lived tokens
* Expiration timestamps

A previously valid request should not automatically remain valid indefinitely.

---

## 64. Message Expiration

Security-sensitive messages should have explicit validity periods.

Example:

```text
Request ID: REQ-98431
From: Agent-A
To: Agent-B
Operation: Create-Ticket
Issued: 14:20
Expires: 14:25
```

Expiration limits the opportunity for captured or delayed messages to be reused.

---

## 65. Time-Bounded Agent Communication Authority

Agent-to-agent communication authority should be limited in time.

For example:

```text
Agent A
   |
   | Delegated Communication
   | Scope: Customer Support
   | Duration: 15 minutes
   v
Agent B
```

When the authorization expires, communication should be denied until a new authorization decision is made.

---

## 66. Short-Lived Agent Credentials

Credentials used for agent-to-agent communication should preferably be short-lived.

Short-lived credentials reduce:

* Credential theft impact
* Replay opportunities
* Persistent unauthorized access
* Incident-response complexity

Long-lived shared secrets should be avoided for high-risk agent relationships where stronger mechanisms are available.

---

## 67. Credential Isolation

Credentials should be isolated according to agent, environment, purpose, and privilege.

```text
Agent A
 ├── Agent-B Communication Credential
 ├── Database Credential
 └── Tool Credential
```

Compromise of one credential should not expose unrelated privileges.

---

## 68. Secrets Management

Agent credentials, signing keys, API keys, and other secrets should be stored in approved enterprise secrets-management systems.

Agents should not:

* Store secrets in prompts
* Persist credentials in unrestricted memory
* Pass credentials through ordinary agent messages
* Embed secrets in generated responses
* Share master credentials with downstream agents

Secret access should itself be authenticated and authorized.

---

## 69. Context Security Controls

Context exchanged between agents should be treated as a controlled security object.

Controls should address:

* Context source
* Classification
* Provenance
* Integrity
* Authorization
* Tenant
* User
* Purpose
* Retention

Context from one agent should not automatically become trusted context for another.

---

## 70. Prompt and Instruction Integrity

Instructions exchanged between agents should have defined trust levels.

For example:

```text
Enterprise Policy
      ↓
Authorized Agent Instruction
      ↓
Agent Recommendation
      ↓
External Information
```

These categories should not automatically receive equivalent authority.

Agent-generated instructions should remain subject to independent policy enforcement.

---

## 71. Untrusted Input Isolation

Information received from another agent should be isolated from authoritative system instructions unless explicitly validated.

A secure model is:

```text
Trusted Policy
      |
      +----------------+
                       |
Agent A Output → Validation → Agent B
```

The receiving agent should not allow untrusted content to override higher-priority security controls.

---

## 72. Prompt Injection Detection

Agent-to-agent traffic should be evaluated for prompt-injection attempts.

Detection should consider:

* Instruction override attempts
* Role manipulation
* Security-policy bypass attempts
* Requests for secrets
* Privilege escalation
* Tool abuse
* Unexpected system-level instructions

Detection should complement authorization rather than replace it.

---

## 73. Memory Isolation

Memory used by one agent should not automatically become available to another agent.

Isolation should consider:

* Agent identity
* User
* Tenant
* Session
* Workflow
* Data classification
* Business purpose

Cross-agent memory access should require explicit authorization.

---

## 74. Memory Authorization

Memory retrieval and modification should be independently authorized.

For example:

```text
Agent A → Read Agent B Memory       DENY
Agent A → Read Shared Memory        ALLOW
Agent A → Modify Shared Memory      REQUIRE AUTHORIZATION
```

Possessing communication access should not automatically grant memory access.

---

## 75. Memory Integrity

Cross-agent memory should be protected against unauthorized modification.

Controls can include:

* Versioning
* Integrity validation
* Provenance
* Write authorization
* Change logging
* Source validation

This reduces the risk of one compromised agent poisoning information consumed by other agents.

---

## 76. Persistent Context Controls

Persistent context transferred between agents should have controlled lifecycle properties.

Controls should include:

* Access authorization
* Retention limits
* Expiration
* Provenance
* Integrity
* Version control
* Deletion
* Revocation

Persistent context should not become a permanent trust channel between agents.

---

## 77. Data Access Authorization

Agents should access only data explicitly authorized for the relationship.

Authorization should evaluate:

```text
Agent
+
Data Object
+
Operation
+
Purpose
+
Tenant
+
Classification
```

An agent's general ability to communicate with another agent should not provide unrestricted access to that agent's underlying data.

---

## 78. Data Minimization

Agent-to-agent communication should transmit only the information necessary to perform the authorized task.

Instead of:

```text
Agent A → Entire Customer Profile
```

prefer:

```text
Agent A → Required Customer Attribute
```

Data minimization reduces the impact of compromised agents and intercepted messages.

---

## 79. Field-Level Data Protection

Sensitive data should be protected at the field level when appropriate.

For example:

```text
Customer Record
 ├── Name             → Allowed
 ├── Account Status   → Allowed
 ├── Address          → Restricted
 ├── Payment Data     → Denied
 └── Authentication Data → Denied
```

This prevents an agent from receiving more information than required.

---

## 80. Tenant Isolation

Agent-to-agent relationships must preserve tenant boundaries.

```text
Tenant A
 Agent A1 → Agent A2
    |
    X
    |
Tenant B
 Agent B1
```

A valid relationship inside one tenant must not automatically permit cross-tenant communication.

---

## 81. Session Isolation

Agent-to-agent communication should remain bound to the appropriate session or workflow.

This prevents information or authorization from one session being reused in another.

Session isolation should consider:

* Session identifier
* User
* Tenant
* Workflow
* Agent instance
* Authorization state

---

## 82. Network Segmentation

Network controls should restrict which agents can communicate.

Segmentation may be based on:

* Environment
* Business function
* Trust level
* Tenant
* Data classification
* Application zone

Example:

```text
Internet Zone
     X
     |
Agent Zone
     |
     +---- Trusted Agent Zone
     |
     +---- High-Privilege Agent Zone
```

Network segmentation provides an additional boundary if application-level controls fail.

---

## 83. Egress Controls

Agents should have restricted outbound communication.

Egress controls can limit:

* Destination agents
* External services
* Ports
* Protocols
* Data categories
* Communication frequency

An agent should not be able to dynamically discover and communicate with arbitrary systems merely because its model decides to do so.

---

## 84. External Communication Controls

Communication between enterprise agents and external agents should receive additional scrutiny.

Controls may include:

* External identity verification
* Provider allowlisting
* Data filtering
* Encryption
* Contractual requirements
* Additional authorization
* Human approval for high-risk operations

External agent trust should not inherit from internal agent trust.

---

## 85. Code Execution Isolation

If one agent can request code execution through another agent, execution should occur within an isolated environment.

Controls should include:

* Sandboxing
* Resource limits
* Network restrictions
* Filesystem isolation
* Credential isolation
* Execution time limits

Agent-to-agent delegation should not become an unrestricted remote-code-execution pathway.

---

## 86. Database Security Controls

Agents should not gain database access indirectly through another agent without appropriate authorization.

Controls should include:

* Database identity binding
* Query authorization
* Row-level security
* Field-level security
* Read/write separation
* Query validation
* Transaction limits

The downstream agent should enforce its own database security policies.

---

## 87. Read/Write Separation

Read and write operations should have separate security boundaries.

```text
Agent A → Agent B → READ  → Allowed
Agent A → Agent B → WRITE → Additional Authorization
Agent A → Agent B → DELETE → High-Risk Control
```

This prevents a relationship created for information retrieval from becoming a modification channel.

---

## 88. Human Approval Controls

High-impact agent-to-agent operations should require human approval where appropriate.

Examples include:

* Financial transactions
* Security policy changes
* Access-control changes
* Destructive actions
* Sensitive data disclosure
* Production changes

Human approval should apply to the specific proposed operation.

---

## 89. Action Preview

Before high-impact delegated actions are executed, the system should provide a clear action preview.

The preview should identify:

* Initiating agent
* Executing agent
* Requested operation
* Target
* Data involved
* Expected impact
* Authorization
* Risk level

This helps prevent an agent from hiding significant consequences inside a seemingly routine delegation.

---

## 90. Dual Authorization

Critical agent-to-agent operations may require independent authorization from multiple control domains or human actors.

For example:

```text
Agent Request
     |
     +--> Security Authorization
     |
     +--> Business Authorization
     |
     v
Execution
```

Dual authorization reduces the risk of a single compromised agent controlling a high-impact workflow.

---

## 91. Reversibility Controls

Where possible, agent-to-agent actions should be designed to be reversible.

Examples:

* Draft instead of send
* Stage instead of commit
* Disable instead of delete
* Temporary permission instead of permanent permission

Reversibility reduces the consequences of erroneous or malicious autonomous behavior.

---

## 92. Agent Execution Limits

Agents should have explicit limits on the number and scope of operations they can perform through another agent.

Limits can include:

* Maximum requests
* Maximum transactions
* Maximum data volume
* Maximum execution time
* Maximum delegated depth

These controls reduce runaway behavior.

---

## 93. Loop Detection

Agent-to-agent loops can consume resources or cause repeated actions.

Example:

```text
Agent A → Agent B
   ↑         |
   |         ↓
   +---------+
```

Detection should identify:

* Repeated requests
* Circular dependencies
* Excessive retries
* Recursive delegation
* Repeated state transitions

The system should terminate unsafe loops automatically.

---

## 94. Recursive Delegation Controls

An agent should not be able to delegate authority indefinitely.

Example:

```text
A → B → C → D → E
```

Controls should define:

* Maximum delegation depth
* Allowed delegation targets
* Delegated scope
* Expiration
* Original initiator
* Maximum cumulative authority

Delegation should become narrower, not broader, as it propagates.

---

## 95. Agent-to-Agent Authentication

Agent-to-agent authentication should be independently enforced at every meaningful trust boundary.

Even when:

```text
A authenticated B
```

this should not mean:

```text
A automatically trusts C because B introduced C
```

Each new agent relationship should have an explicit authentication requirement.

---

## 96. Agent-to-Agent Message Integrity

Security-sensitive messages should maintain integrity across the entire communication chain.

For:

```text
A → B → C
```

the system should be able to determine whether:

* A originated the message
* B modified it
* C received the original or modified version

Where appropriate, message provenance should survive delegation and forwarding.

---

## 97. Delegated Authority Constraints

Delegated authority should explicitly define:

* Scope
* Resource
* Operation
* Purpose
* Time
* Delegation depth
* Recipient
* Conditions

Example:

```text
Agent A
  ↓
Delegates to B:
  READ / Customer-123
  Purpose: Support
  Duration: 10 minutes
  Delegation: Not permitted
```

Agent B should not be permitted to further delegate that authority.

---

## 98. Tool Result Validation

Outputs received from another agent that originated from a tool should be validated before being trusted.

For example:

```text
Tool
 ↓
Agent A
 ↓
Agent B
 ↓
Decision
```

Agent B should not assume that Agent A's tool result is accurate, complete, or authorized merely because Agent A is authenticated.

---

## 99. Output Validation Before Action

Before an agent executes an action based on another agent's output, the output should pass security validation.

Validation should include:

* Authorization
* Data classification
* Parameter validation
* Business rules
* Risk evaluation
* Target validation
* Context validation

This creates an independent control between recommendation and execution.

---

## 100. Business Rule Enforcement

Agent-to-agent interactions must remain subject to enterprise business rules.

Examples:

```text
Refund > €1,000 → Approval Required
Production Change → Change Control Required
Sensitive Data → Restricted
Account Deletion → Dual Authorization
```

Agents should not be able to bypass business rules by asking another agent to perform the action.

---

## 101. Resource Controls

Resource consumption should be controlled across agent relationships.

Controls should address:

* CPU
* Memory
* Network bandwidth
* API calls
* Storage
* Database queries
* Concurrent tasks

Resource controls reduce denial-of-service and runaway-agent risk.

---

## 102. Rate Limiting

Rate limits should restrict how frequently one agent can communicate with another.

For example:

```text
Agent A → Agent B
Maximum:
100 requests / minute
```

Limits should vary according to:

* Agent relationship
* Operation
* Risk
* Resource sensitivity

---

## 103. Concurrency Controls

Concurrent requests should be controlled to prevent resource exhaustion or race conditions.

High-risk operations may require:

* Single active request
* Serialized execution
* Transaction locking
* Idempotency controls

Concurrency limits are especially important for autonomous workflows.

---

## 104. Timeout Controls

Agent-to-agent requests should have explicit timeouts.

A request that remains unresolved indefinitely can create:

* Resource exhaustion
* Workflow deadlocks
* Repeated retries
* Cascading delays

Timeouts should cause controlled failure rather than indefinite execution.

---

## 105. Retry Controls

Retries should be bounded.

Controls should define:

* Maximum retry count
* Retry interval
* Exponential backoff
* Retryable errors
* Non-retryable security failures

Authorization failures should generally not be converted into repeated authorization attempts.

---

## 106. Circuit Breakers

Circuit breakers should automatically interrupt agent relationships when abnormal behavior occurs.

Example:

```text
Normal
  ↓
Anomaly
  ↓
Threshold Exceeded
  ↓
Circuit Breaker
  ↓
Block / Isolate / Alert
```

Triggers may include:

* Excessive requests
* Repeated authorization failures
* Unexpected delegation
* Abnormal data transfer
* Cascading failures

---

## 107. Emergency Agent Controls

Emergency controls should allow security teams to rapidly restrict agent-to-agent relationships.

Controls may include:

* Communication blocking
* Relationship suspension
* Permission removal
* Credential revocation
* Agent isolation
* Tool restriction

Emergency controls should operate independently of normal agent decision-making.

---

## 108. Agent Kill Switch

A kill switch should provide a mechanism to stop an agent or its autonomous activity when necessary.

It should ideally support:

```text
Stop Agent Execution
       ↓
Block New Requests
       ↓
Revoke Credentials
       ↓
Terminate Delegated Authority
       ↓
Preserve Evidence
```

The kill switch should not depend on the compromised agent voluntarily complying.

---

## 109. Credential Revocation

Credentials associated with compromised or untrusted agent relationships should be rapidly revocable.

Revocation should consider:

* Agent identity
* Communication credentials
* Delegated tokens
* Tool credentials
* Context-access credentials

Revoking the agent alone is insufficient if valid delegated credentials remain active.

---

## 110. Agent Isolation

A compromised agent should be isolated from other agents and enterprise resources.

Isolation may include:

* Network quarantine
* Credential revocation
* Tool restriction
* Context isolation
* Communication blocking
* Runtime suspension

The objective is to prevent lateral movement.

---

## 111. Behavioral Monitoring

Agent relationships should be monitored for behavioral anomalies.

Indicators may include:

* New communication partners
* Unusual request volumes
* Unexpected delegation
* Unusual data access
* Abnormal transaction requests
* Unexpected tool usage
* Changes in communication patterns

Behavioral monitoring should supplement deterministic access controls.

---

## 112. Agent Activity Logging

Security-relevant agent-to-agent activity should be logged.

Logs should capture:

```text
Timestamp
Initiating Agent
Receiving Agent
User / Initiator
Request
Resource
Authorization Result
Delegation
Action
Outcome
Risk
```

Logging should be sufficient to reconstruct the relationship and resulting activity.

---

## 113. Tamper-Resistant Agent-to-Agent Audit Logging

Security logs should be protected against unauthorized modification or deletion.

Controls may include:

* Append-only storage
* Cryptographic integrity
* Centralized logging
* Restricted administrative access
* Time synchronization
* Immutable retention

Audit records should remain available during incident investigation.

---

## 114. Agent-to-Agent Security Observability

Observability should provide visibility into the complete relationship graph.

```text
        Agent A
        /     \
       v       v
   Agent B   Agent C
      |         |
      v         v
    Tool X    Agent D
```

Security teams should be able to determine:

* Which agents communicate
* Why they communicate
* What authority is transferred
* What data is exchanged
* What actions result

---

## 115. Agent-to-Agent Risk Detection

Risk detection should identify behaviors indicating possible compromise or abuse.

Potential indicators include:

* Unexpected agent relationships
* Privilege escalation
* Excessive delegation
* Repeated authorization failures
* Unusual message patterns
* Cross-tenant access attempts
* Abnormal transaction activity
* Unexpected tool use
* Communication loops

Risk detection should feed enterprise incident-response processes.

---

## 116. Secure Agent-to-Agent Failure Handling

When an agent relationship fails, security controls should favor safe failure.

Examples:

```text
Authentication Failure
 → DENY

Authorization Failure
 → DENY

Integrity Failure
 → QUARANTINE

Unknown Agent
 → DENY

Expired Delegation
 → DENY

Critical Anomaly
 → ISOLATE
```

Failure should not result in automatic fallback to broader privileges or uncontrolled alternate agents.

---

## 117. Core Engineering Principle

**Agent-to-agent security must enforce trust, authority, data, and execution boundaries independently at every meaningful relationship boundary.**

A secure multi-agent environment should therefore ensure:

```text
Identity
   +
Authentication
   +
Authorization
   +
Delegation Constraints
   +
Data Isolation
   +
Tool Isolation
   +
Execution Limits
   +
Monitoring
   +
Containment
```

No individual agent should be able to convert another agent's legitimate capabilities into uncontrolled authority.

# Part 3

## 118. Agent-to-Agent Security Risk Governance Framework

Agent-to-agent security risk governance establishes the organizational framework for identifying, assessing, approving, monitoring, and managing risks created by relationships between autonomous agents.

Governance should cover:

* Agent relationships
* Trust relationships
* Delegation
* Authority propagation
* Data exchange
* Context and memory propagation
* Tool access
* Transactions
* External agents
* Incident response
* Continuous assurance

The governance objective is to ensure that agent relationships remain **intentional, authorized, bounded, accountable, and continuously governed**.

---

## 119. Agent-to-Agent Security Ownership and Accountability

Every significant agent relationship should have an accountable owner.

Ownership should identify:

* Business owner
* Technical owner
* Security owner
* Agent owner
* Relationship owner
* Data owner where applicable

The relationship owner should be responsible for ensuring that the interaction remains necessary, authorized, and appropriately controlled.

---

## 120. Enterprise Agent-to-Agent Relationship Inventory

The enterprise should maintain an inventory of approved agent relationships.

The inventory should identify:

| Attribute           | Example          |
| ------------------- | ---------------- |
| Initiating Agent    | Agent-A          |
| Receiving Agent     | Agent-B          |
| Purpose             | Customer Support |
| Trust Level         | Controlled       |
| Data Exchanged      | Customer Profile |
| Delegated Authority | Read Only        |
| Owner               | Business Unit    |
| Risk Tier           | Medium           |
| Approval Date       | 2026-09-01       |
| Review Date         | 2026-12-01       |

The inventory should include both direct and significant delegated relationships.

---

## 121. Agent-to-Agent Relationship Classification

Relationships should be classified according to their security and business characteristics.

Possible classifications include:

* Informational
* Operational
* Data-sharing
* Delegated
* Transactional
* Administrative
* High-impact
* External

Classification determines the minimum security controls and governance requirements.

---

## 122. Agent-to-Agent Risk Tiering

Agent relationships should be assigned risk tiers based on factors such as:

* Data sensitivity
* Privilege
* Transaction authority
* Delegation
* External connectivity
* Number of dependent agents
* Business impact
* Reversibility
* Potential blast radius

Example:

```text id="v8l6v4"
Low
 ↓
Information exchange

Medium
 ↓
Operational task delegation

High
 ↓
Sensitive data / privileged tools

Critical
 ↓
Financial / administrative / destructive authority
```

---

## 123. Agent-to-Agent Security Approval Governance

High-risk agent relationships should require formal approval before activation.

Approval should validate:

* Business necessity
* Agent identity
* Relationship purpose
* Authority scope
* Data exchanged
* Delegation capability
* Security controls
* Monitoring
* Incident-response requirements

Approval should be specific to the relationship rather than an unrestricted approval of the participating agents.

---

## 124. Agent-to-Agent Purpose Limitation

Every relationship should have a clearly defined purpose.

For example:

```text id="u4v1dh"
Approved Purpose:
Agent A → Agent B
"Retrieve customer account status"

Not Automatically Approved:
- Modify account
- Delete account
- Retrieve payment information
- Execute refund
```

Purpose limitation prevents communication privileges from becoming general-purpose authority.

---

## 125. Agent Authority Governance

Agent authority should be explicitly defined and governed.

Governance should identify:

* What the agent may request
* What the agent may receive
* What the agent may delegate
* What actions require approval
* What resources may be accessed
* How long authority remains valid

Authority should be treated as a governed security attribute rather than an emergent property of agent behavior.

---

## 126. Agent-to-Tool Access Governance

Where an agent relationship can indirectly provide tool access, governance must evaluate the complete chain.

```text id="hr5jq9"
Agent A
 ↓
Agent B
 ↓
Payment Tool
 ↓
Financial System
```

The organization should determine whether Agent A is permitted to cause Agent B to invoke the payment tool.

Indirect tool access must be governed just as seriously as direct access.

---

## 127. Agent-to-Agent Access Governance

Access governance should define which agents may communicate and under what conditions.

Policies should address:

* Source agent
* Target agent
* Operation
* Data
* Environment
* Tenant
* Purpose
* Time
* Risk

A relationship should be explicitly denied when no approved business or security purpose exists.

---

## 128. Agent Relationship Access Reviews

Agent-to-agent relationships should undergo periodic access review.

Reviews should verify:

* Relationship still required
* Purpose remains valid
* Permissions remain appropriate
* Delegation remains necessary
* Data scope remains appropriate
* Risk remains acceptable
* Owner remains accountable

Unused or excessive relationships should be removed.

---

## 129. Least-Privilege Agent Relationship Governance

Agent relationships should follow least privilege.

The relationship should provide the minimum:

* Communication capability
* Data access
* Tool access
* Delegated authority
* Transaction capability

required to accomplish the approved purpose.

---

## 130. Agent Capability Governance

Agent capabilities should be governed independently from the relationships through which those capabilities are exposed.

For example:

```text id="x3s4ft"
Agent B Capability:
"Execute Payment"

Does NOT mean:

Agent A → Agent B
"Execute Payment" = Automatically Allowed
```

The relationship must explicitly authorize the capability.

---

## 131. Capability Combination Governance

Risk can increase when individually legitimate capabilities are combined.

For example:

```text id="h2e8e0"
Read Customer Data
       +
Modify Customer Account
       +
Send External Message
       =
High Combined Risk
```

Governance should evaluate the effective capability created by combinations rather than assessing each permission independently.

---

## 132. Permission Inheritance Governance

Permissions should not automatically inherit across agent relationships.

If:

```text id="e9v5ef"
Agent A → Agent B
```

and Agent B has access to a sensitive resource, Agent A should not automatically inherit that access.

Inherited permissions must be explicitly authorized.

---

## 133. Delegation Governance

Delegation should be governed as a separate security capability.

Governance should define:

* Who may delegate
* To whom
* What may be delegated
* Maximum delegation depth
* Duration
* Purpose
* Whether further delegation is permitted

Delegation should always reduce or preserve authority, never silently expand it.

---

## 134. Authority Propagation Governance

Organizations should explicitly govern how authority moves across agent chains.

For:

```text id="k7b3qz"
A → B → C
```

governance should determine whether:

* B may delegate
* C may act on A's behalf
* A's authority can propagate
* The original user remains attributable
* The delegated scope remains bounded

Uncontrolled authority propagation should be prohibited.

---

## 135. Data Governance for Agent-to-Agent Security

Data exchanged between agents should be subject to enterprise data governance.

Requirements should address:

* Classification
* Ownership
* Purpose
* Retention
* Data minimization
* Residency
* Privacy
* Access control
* Cross-border transfer where applicable

Agent communication should not bypass existing enterprise data governance.

---

## 136. Sensitive Data Agent-to-Agent Governance

Sensitive data should require additional controls when transferred between agents.

Examples include:

* Personal data
* Financial information
* Authentication information
* Security information
* Confidential business information
* Regulated data

Controls may include:

* Field-level authorization
* Encryption
* Masking
* Approval
* Restricted relationships
* Enhanced monitoring

---

## 137. Context Governance

Context exchanged between agents should have defined trust and governance properties.

Governance should identify:

* Source
* Classification
* Provenance
* Trust level
* Retention
* Authorized consumers

Information received from another agent should not automatically become trusted enterprise context.

---

## 138. Memory Governance

Cross-agent memory sharing should be explicitly governed.

Governance should address:

* Memory ownership
* Access rights
* Write rights
* Retention
* Provenance
* Tenant boundaries
* User boundaries
* Agent boundaries

Persistent memory should not become an uncontrolled cross-agent trust mechanism.

---

## 139. Credential Governance

Credentials used between agents should be governed according to enterprise identity and secrets-management requirements.

Governance should prohibit unnecessary:

* Credential sharing
* Long-lived tokens
* Shared secrets
* Privileged service accounts
* Credential embedding in messages

Credentials should be scoped to specific agents, purposes, resources, and durations.

---

## 140. Network Governance

Network relationships between agents should be governed according to trust and risk.

Governance should define:

* Permitted network paths
* Agent communication zones
* External connectivity
* Egress restrictions
* Environment boundaries
* Tenant boundaries

Network architecture should reinforce, rather than replace, application-level authorization.

---

## 141. External Agent Governance

External agents should be governed separately from internal agents.

Assessment should consider:

* Provider identity
* Ownership
* Security posture
* Data handling
* Authentication
* Authorization
* Contractual obligations
* Incident notification
* Service dependencies

External-agent relationships should not automatically inherit internal trust.

---

## 142. Agent Provider Governance

Organizations should evaluate providers responsible for agent platforms or infrastructure.

Assessment areas include:

* Identity management
* Security controls
* Data protection
* Logging
* Isolation
* Availability
* Vulnerability management
* Incident response
* Supply-chain security

Provider assurance should be proportional to the risk of the agent relationship.

---

## 143. Agent Provider Risk Management

Agent providers should be included within third-party risk-management processes where appropriate.

Risk assessment should consider:

```text id="n3q8nq"
Provider
   ↓
Agent Platform
   ↓
Agent Identity
   ↓
Agent Relationship
   ↓
Enterprise Resources
```

A weakness at the provider layer can affect multiple agent relationships simultaneously.

---

## 144. Agent-to-Agent Security Requirements

Each approved relationship should have documented security requirements.

Requirements may cover:

* Identity
* Authentication
* Authorization
* Data exchange
* Delegation
* Memory
* Context
* Tools
* Transactions
* Logging
* Monitoring
* Incident response
* Recovery

High-risk relationships should have stronger requirements than low-risk informational relationships.

---

## 145. Agent-to-Agent Threat Modeling

Threat modeling should explicitly model the agent relationship.

Threat scenarios should include:

* Impersonation
* Spoofing
* Message manipulation
* Prompt injection
* Delegation abuse
* Privilege escalation
* Credential propagation
* Memory poisoning
* Data leakage
* Lateral movement
* Cascading compromise
* Transaction abuse

A relationship should not be approved solely because each agent individually passed security review.

---

## 146. Agent Secure Development Lifecycle

Agent-to-agent security requirements should be integrated into the secure development lifecycle.

Security activities should occur during:

```text id="qq0t2x"
Design
 ↓
Threat Modeling
 ↓
Implementation
 ↓
Security Testing
 ↓
Deployment
 ↓
Monitoring
 ↓
Change Management
 ↓
Retirement
```

Security should therefore remain part of the relationship lifecycle.

---

## 147. Model Change Governance

Model changes can alter how agents interpret or use agent-to-agent messages.

Governance should assess changes involving:

* Model version
* Model provider
* System behavior
* Reasoning configuration
* Safety mechanisms
* Tool behavior

Significant model changes should trigger security regression testing.

---

## 148. Prompt and Instruction Change Governance

Changes to agent instructions can alter the security behavior of an agent relationship.

Governance should require appropriate review of:

* System instructions
* Agent policies
* Delegation instructions
* Tool instructions
* Trust assumptions
* Communication rules

Prompt changes should not silently expand effective authority.

---

## 149. Tool Change Governance

Changes to tools accessible through agent relationships should trigger security review.

Changes may involve:

* New tools
* Removed tools
* New permissions
* API changes
* Parameter changes
* Tool ownership
* Tool provider

A tool change can transform a low-risk relationship into a high-risk relationship.

---

## 150. Data-Source Change Governance

Changes to data sources should be governed because new data can alter the information available to downstream agents.

Review should consider:

* Source trust
* Classification
* Provenance
* Data quality
* Access rights
* Regulatory requirements

A new data source should not automatically become trusted simply because an existing agent can access it.

---

## 151. Agent Configuration Management

Agent relationship configurations should be centrally managed and version controlled.

Configuration should include:

* Allowed relationships
* Authorization policies
* Delegation settings
* Trust levels
* Tool permissions
* Data boundaries
* Network policies

Unauthorized configuration changes should be detected and investigated.

---

## 152. Agent-to-Agent Security Testing

Security testing should validate the relationship rather than only individual agents.

Testing should include:

* Authentication
* Authorization
* Delegation
* Message integrity
* Data isolation
* Memory isolation
* Tool access
* Transaction controls
* Failure handling

Testing should verify that controls remain effective under realistic agent behavior.

---

## 153. Adversarial Agent-to-Agent Testing

Adversarial testing should simulate malicious or compromised agents.

Scenarios should include:

```text id="x7m8sv"
Compromised Agent A
        ↓
Unauthorized Request
        ↓
Agent B
        ↓
Attempted Privilege Escalation
```

Testing should determine whether Agent B:

* Rejects unauthorized requests
* Detects manipulation
* Preserves authorization boundaries
* Limits delegation
* Generates security telemetry

---

## 154. Agent-to-Agent Control Effectiveness Testing

Testing should measure whether security controls actually prevent or contain agent-to-agent risks.

Examples:

| Control               | Effectiveness Test                            |
| --------------------- | --------------------------------------------- |
| Mutual Authentication | Can an unknown agent connect?                 |
| Authorization         | Can an agent request unauthorized operations? |
| Delegation Control    | Can authority be delegated beyond scope?      |
| Tenant Isolation      | Can cross-tenant data be accessed?            |
| Circuit Breaker       | Does abnormal traffic trigger blocking?       |
| Kill Switch           | Can communication be stopped independently?   |

Control existence alone should not be considered evidence of effectiveness.

---

## 155. Agent-to-Agent Monitoring Governance

Monitoring requirements should be defined according to relationship risk.

Monitoring should cover:

* Communication volume
* New relationships
* Delegation
* Data transfers
* Authorization failures
* Tool requests
* Transaction requests
* Behavioral anomalies

High-risk relationships should receive enhanced monitoring.

## 157. Security Baseline Compliance

Approved agent relationships should comply with enterprise security baselines.

* Network segmentation
* Credential protection
* Incident-response integration

Exceptions should be documented and governed.

## 158. Continuous Agent-to-Agent Control Monitoring

Controls should be monitored continuously where technically feasible.

Monitoring should verify that:

```text id="9qqr1d"
Approved Relationship
        =
Observed Relationship
```

Differences should generate drift alerts and risk evaluation.

---

## 159. Agent-to-Agent Relationship Drift

Relationship drift occurs when the actual relationship differs from its approved state.

Examples:

* New agent added
* New capability exposed
* Permissions expanded
* New data source connected
* Delegation enabled
* Trust level changed

Drift should trigger review before unauthorized expansion becomes normalized.

---

## 160. Agent Security Drift

Agent security drift can occur when changes to one agent alter the security characteristics of its relationships.

For example:

```text id="x5t3hh"
Agent B
Original:
Read-only capability

After change:
Read + Write + Delete

Agent A relationship unchanged

BUT

Effective Risk ↑
```

Governance must therefore evaluate downstream effects of agent changes.

## 170. Agent-to-Agent Reauthorization

Agent relationships should be periodically reauthorized.

Reauthorization should reassess:

* Business purpose
* Risk tier
* Permissions
* Delegation
* Data access
* Agent behavior
* Provider risk
* Security incidents
* Ownership

Reauthorization should be triggered earlier when material changes occur.

## 171. Agent Retirement Governance

When an agent is retired, its relationships must also be reviewed.

Retirement should include:

* Relationship termination
* Credential revocation
* Delegation revocation
* Tool access removal
* Context access removal
* Memory access removal
* Registry updates
* Evidence preservation

Retiring an agent without removing its delegated authority can leave residual attack paths.

## 176. Enterprise Security Principle

## 177. Strategic Governance Principle

**Trust between autonomous agents must never become uncontrolled propagation of authority.**

Enterprise governance must ensure that every agent-to-agent relationship remains:

```text id="r2n8j9"
Known
  +
Owned
  +
Approved
  +
Least-Privileged
  +
Bounded
  +
Monitored
  +
Auditable
  +
Reversible
  +
Reauthorized
```

The governance objective is to ensure that autonomous collaboration increases enterprise capability without creating an unmanaged pathway for privilege escalation, data propagation, or cascading compromise.
