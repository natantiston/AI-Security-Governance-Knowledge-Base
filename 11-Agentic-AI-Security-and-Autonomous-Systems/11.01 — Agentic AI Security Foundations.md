# 11.01 — Agentic AI Security Foundations

## Part 1 — Foundations and Core Concepts

### 1. Definition of Agentic AI Security

Agentic AI security is the discipline of protecting AI systems that can **independently perceive information, reason about objectives, make decisions, invoke tools, communicate with other systems or agents, maintain state, and execute actions** with varying degrees of autonomy.

Traditional LLM security primarily focuses on protecting model interactions such as:

* prompts;
* context;
* generated responses;
* retrieved information;
* model APIs;
* training and inference data.

Agentic AI security expands this boundary because an agent can move beyond generating information and can **take action on behalf of a user, application, or organization**.

An agentic system may therefore interact with:

* databases;
* APIs;
* SaaS platforms;
* cloud infrastructure;
* enterprise applications;
* files;
* email;
* financial systems;
* security tools;
* development environments;
* other AI agents;
* physical or operational systems.

The fundamental security question changes from:

> **"What can the model generate?"**

to:

> **"What can the AI system autonomously decide and do?"**

---

### 2. Agentic AI as a Security Discipline

Agentic AI introduces a security discipline that combines concepts from:

* application security;
* identity and access management;
* API security;
* cloud security;
* data security;
* endpoint security;
* network security;
* automation security;
* distributed systems security;
* AI/ML security;
* operational technology security;
* governance, risk, and compliance.

An agent may combine multiple capabilities into a single autonomous workflow:

```text
Perceive
   ↓
Interpret
   ↓
Reason
   ↓
Plan
   ↓
Select Tool
   ↓
Authenticate
   ↓
Execute Action
   ↓
Observe Result
   ↓
Update Context
   ↓
Continue / Stop
```

Every transition can introduce a security decision.

---

### 3. Fundamental Security Problem

The fundamental security problem in agentic AI is **autonomous authority**.

An LLM that only produces text generally has a limited direct ability to affect external systems.

An agent may have:

* credentials;
* permissions;
* tools;
* APIs;
* network access;
* persistent memory;
* delegated authority;
* transaction capability;
* autonomous execution loops.

Consequently, compromise of an agent can potentially become compromise of the systems to which that agent is connected.

The security objective is therefore not merely to make the model produce safe responses.

The objective is to ensure:

> **An agent can only perceive, decide, access, communicate, and act within explicitly defined security boundaries.**

---

### 4. Agentic AI vs Conventional LLM Applications

A conventional LLM application may follow:

```text
User
 ↓
Application
 ↓
LLM
 ↓
Response
```

An agentic system may follow:

```text
User
 ↓
Agent
 ↓
Reasoning / Planning
 ↓
Tool Selection
 ↓
API / Database / Service
 ↓
Result
 ↓
Agent
 ↓
Additional Decision
 ↓
Another Tool
 ↓
External Action
```

The second architecture introduces additional security concerns because the AI can participate in a **multi-step execution process**.

The security boundary therefore extends beyond the model itself.

---

### 5. Agency vs Capability

A critical distinction is the difference between **capability** and **agency**.

**Capability** describes what an AI system can technically do.

**Agency** describes the degree to which the AI system can independently decide and execute what it does.

For example, an agent may technically have access to:

* a payment API;
* an email service;
* a database;
* a cloud administration API.

That does not mean the agent should be able to independently decide when to use those capabilities.

Therefore:

> **Technical capability does not imply operational authority.**

---

### 6. Agent Autonomy

Agent autonomy represents the degree to which an AI system can perform activities without direct human intervention.

A simplified model is:

```text
Level 0
Human performs action
        ↓
Level 1
AI recommends action
        ↓
Level 2
AI prepares action
        ↓
Level 3
AI executes approved action
        ↓
Level 4
AI independently executes bounded actions
        ↓
Level 5
AI operates across multiple systems with broad autonomy
```

Higher autonomy can increase efficiency, but it can also increase:

* attack surface;
* privilege requirements;
* blast radius;
* operational uncertainty;
* potential financial impact;
* speed of compromise;
* difficulty of human intervention.

---

The security boundary of an agentic AI system includes substantially more than the model.

```text
        |                  |                  |

              |            |            |

                           |
```

Every component can introduce a security dependency.

---

### 8. Agent Identity

An agent must be treated as an identifiable security principal when it interacts with protected resources.

Identity enables the enterprise to determine:

* which agent acted;
* on whose behalf it acted;
* which application initiated the activity;
* which permissions were used;
* which tools were invoked;
* which resources were accessed;
* which actions were performed.

Without strong agent identity, accountability becomes difficult.

A mature model should distinguish between:

```text
Human Identity
      ↓
Application Identity
      ↓
Agent Identity
      ↓
Tool / Service Identity
      ↓
Resource Identity
```

This supports attribution across autonomous workflows.

---

### 9. Agent Authentication

Authentication establishes whether an agent is genuinely the identity it claims to represent.

Agent authentication may involve:

* service identities;
* workload identities;
* certificates;
* cryptographic credentials;
* federated identity;
* short-lived tokens;
* workload attestation.

Authentication should not be replaced by assumptions such as:

* "the agent is internal";
* "the agent was created by an approved team";
* "the agent runs inside the corporate network."

---

### 10. Agent Authorization

Authorization determines what an authenticated agent is actually permitted to do.

This distinction is fundamental:

```text
Authentication
      ↓
Who is the agent?
      ↓
Authorization
      ↓
What is the agent allowed to do?
      ↓
Policy Enforcement
      ↓
What action is actually permitted?
```

The model should not independently determine authorization.

A secure architecture must enforce authorization outside the model where possible.

---

### 11. Agent Permissions

Agent permissions should be explicitly defined according to business requirements.

Permissions may include:

* read data;
* write data;
* create records;
* modify records;
* delete records;
* invoke APIs;
* execute code;
* send messages;
* access files;
* access cloud resources;
* initiate transactions;
* communicate with other agents.

Permissions should be minimized according to actual business requirements.

---

### 12. Least Privilege for Agents

Least privilege is one of the most important principles in agentic AI security.

An agent should receive only the authority necessary to perform its approved function.

For example:

```text
Business Requirement:
Generate customer reports

Required:
✓ Read approved reporting database
✓ Generate report
✓ Store report in approved location

Not Required:
✗ Delete database records
✗ Modify customer accounts
✗ Send external email
✗ Access payment systems
✗ Modify cloud infrastructure
```

The principle is:

> **Give the agent the minimum capability required to perform the approved business process.**

---

### 13. Excessive Agency

Excessive agency occurs when an AI system possesses more:

* authority;
* autonomy;
* permissions;
* tools;
* credentials;
* data access;
* network access;
* transaction capability

than necessary for its intended purpose.

Risk increases when these characteristics combine:

```text
High Autonomy
      +
High Privilege
      +
Sensitive Data
      +
External Connectivity
      +
Persistent Execution
      =
High Agentic Risk
```

Excessive agency is particularly dangerous because a successful compromise can be converted into real-world action.

---

### 14. Tool Access as an Extension of Agent Authority

Tools effectively extend the operational authority of an agent.

Examples include:

* database tools;
* shell tools;
* browser tools;
* email tools;
* cloud APIs;
* ticketing systems;
* code execution;
* financial APIs;
* identity-management APIs.

Therefore:

> **Every tool available to an agent should be treated as a potential privilege boundary.**

The security question should not simply be:

> "Can the agent call this tool?"

It should be:

> "Is this agent authorized to perform this specific operation against this specific resource under these circumstances?"

---

### 15. Autonomous Decision-Making

Agents may make decisions involving:

* tool selection;
* data selection;
* workflow progression;
* prioritization;
* transaction initiation;
* communication;
* escalation;
* remediation.

This creates a distinction between:

**AI-generated recommendation**

and

**AI-authorized action**.

A recommendation can be reviewed by a human.

An autonomous action can directly change the environment.

Therefore, consequential decisions require stronger controls.

---

### 16. Human Oversight

Human oversight provides an additional control layer for actions that could produce significant consequences.

Human involvement can occur through:

* approval;
* review;
* escalation;
* transaction confirmation;
* exception handling;
* emergency intervention.

The required level of human oversight should be proportional to:

* impact;
* reversibility;
* privilege;
* uncertainty;
* sensitivity;
* financial value;
* regulatory significance.

---

### 17. Reversibility of Agent Actions

Agentic actions should be evaluated according to whether they can be reversed.

Examples:

| Action                           | Reversibility   | Security Concern |
| -------------------------------- | --------------- | ---------------- |
| Generate report                  | High            | Low              |
| Create ticket                    | High            | Moderate         |
| Send internal message            | Moderate        | Moderate         |
| Modify customer record           | Moderate        | High             |
| Delete data                      | Low             | High             |
| Transfer funds                   | Potentially low | Critical         |
| Modify production infrastructure | Potentially low | Critical         |

Irreversible or difficult-to-reverse actions should require stronger authorization and oversight.

---

### 18. Agent Execution Loops

Agents frequently operate through iterative execution loops:

```text
Observe
   ↓
Reason
   ↓
Plan
   ↓
Act
   ↓
Observe Result
   ↓
Reason Again
   ↓
Act Again
   ↓
...
```

These loops introduce security risks such as:

* runaway execution;
* repeated transactions;
* tool abuse;
* resource exhaustion;
* recursive actions;
* unintended escalation;
* cumulative data access;
* repeated external communication.

An agent that can continue operating indefinitely represents a fundamentally different security risk from a single-response LLM.

---

### 19. Persistent State and Memory

Agents may maintain state across interactions.

Memory can contain:

* user information;
* previous decisions;
* workflow state;
* credentials or references to credentials;
* retrieved information;
* task history;
* preferences;
* operational context.

Persistent memory creates additional security requirements involving:

* confidentiality;
* integrity;
* retention;
* authorization;
* tenant isolation;
* poisoning;
* deletion;
* lifecycle management.

A compromised memory store can influence future agent behavior.

---

### 20. Agent Context as a Security Boundary

Agent context may combine:

```text
System Instructions
       +
User Request
       +
Retrieved Data
       +
Memory
       +
Tool Results
       +
Agent State
       +
Other Agent Messages
```

This creates a complex trust environment.

The agent must not automatically treat every item in its context as equally trustworthy.

A core principle is:

> **Context provenance does not automatically establish authorization or trust.**

---

### 21. Agent-to-Agent Communication

Multiple agents may communicate to complete a workflow.

For example:

```text
Customer Agent
      ↓
Research Agent
      ↓
Data Agent
      ↓
Transaction Agent
      ↓
Notification Agent
```

Each communication boundary introduces potential risks involving:

* impersonation;
* message manipulation;
* privilege delegation;
* confused deputy behavior;
* unauthorized instructions;
* data leakage;
* cascading compromise.

Agent-to-agent communication should therefore be treated as a security-sensitive interface.

---

### 22. Delegation of Authority

Agents may delegate work to other agents.

Delegation creates an important security question:

> **Does the delegated agent receive more authority than the originating agent?**

A secure delegation model should ensure:

```text
Originating Authority
        ↓
Delegated Authority
        ↓
Equal or Narrower Scope
```

Delegation should not automatically create privilege escalation.

---

### 23. Confused Deputy Risk

An agent can become a **confused deputy** when it uses its legitimate privileges to perform an action for an unauthorized party.

For example:

```text
Attacker
   ↓
Manipulates Agent
   ↓
Agent Uses Legitimate Credential
   ↓
Protected Enterprise System
```

The enterprise system may see a legitimate agent identity even though the underlying action was unauthorized.

This makes agent identity, authorization context, user attribution, and purpose binding especially important.

---

### 24. Agent Hijacking

Agent hijacking occurs when an attacker gains control over, manipulates, or redirects an agent's behavior or execution.

Potential attack paths include:

* prompt injection;
* compromised memory;
* malicious tool results;
* stolen credentials;
* compromised APIs;
* manipulated agent messages;
* vulnerable dependencies;
* compromised orchestration systems.

A hijacked agent can be significantly more dangerous than a compromised passive chatbot because it may possess operational authority.

---

### 25. Agent Security and Prompt Injection

Prompt injection remains relevant in agentic systems, but its consequences can be substantially greater.

A simplified attack chain is:

```text
Malicious Input
      ↓
Prompt Injection
      ↓
Agent Changes Objective / Behavior
      ↓
Tool Selection
      ↓
Authorized Tool
      ↓
Unauthorized Action
```

The critical security failure is not merely that the model followed malicious instructions.

The greater failure is that the manipulated model was able to convert those instructions into **real-world authority**.

---

### 26. Agent Security and Excessive Agency

Prompt injection, jailbreaking, or model manipulation becomes significantly more dangerous when an agent possesses broad privileges.

The relationship can be represented as:

```text
Model Manipulation
        ×
Agent Authority
        ×
Autonomy
        ×
External Connectivity
        =
Potential Operational Impact
```

Reducing agency therefore reduces the potential consequences of model compromise.

---

### 27. Agent Security and Data Protection

Agents may have access to highly sensitive enterprise information.

Potential data sources include:

* customer records;
* financial information;
* employee information;
* intellectual property;
* security information;
* credentials;
* confidential documents;
* regulated information.

Agentic systems therefore require strict data-access boundaries.

The principle is:

> **An agent should access only the data necessary for its authorized task.**

---

### 28. Agent Security and External Connectivity

External connectivity can significantly increase agent risk.

An agent connected to:

* public websites;
* external APIs;
* email;
* messaging platforms;
* cloud services;
* partner systems

may be able to move information or actions beyond the enterprise security boundary.

Therefore:

```text
Agent
 ↓
Network Access
 ↓
External Destination
```

must be treated as a controlled security pathway rather than an inherent agent capability.

---

### 29. Agent Security and Transaction Risk

An agent that can initiate transactions creates additional security requirements.

Transactions may involve:

* money;
* purchases;
* contracts;
* customer changes;
* infrastructure changes;
* access changes;
* production deployments;
* security remediation.

The higher the transaction impact, the stronger the required authorization and oversight.

---

### 30. Agent Security and Availability

Agentic systems can create availability and resource risks through:

* uncontrolled loops;
* excessive tool calls;
* repeated API requests;
* recursive delegation;
* excessive retrieval;
* high-volume processing;
* resource-intensive tasks.

Therefore, agent security includes not only confidentiality and integrity but also **resource governance and availability protection**.

---

### 31. Confidentiality

Agentic systems can create confidentiality risks through:

* unauthorized data access;
* memory exposure;
* cross-agent data sharing;
* tool results;
* external communication;
* retrieval;
* persistent context;
* compromised credentials.

Confidentiality controls must therefore operate across the complete agent workflow.

---

### 32. Integrity

Agentic systems can affect integrity by:

* modifying records;
* changing configurations;
* creating transactions;
* executing code;
* altering workflows;
* manipulating security controls.

Integrity protection requires strong authorization and validation before consequential actions are executed.

---

### 33. Availability

Availability risks include:

* runaway agents;
* excessive tool execution;
* infinite loops;
* resource exhaustion;
* dependency failures;
* cascading agent failures;
* uncontrolled autonomous workloads.

Agentic systems require explicit execution and resource boundaries.

---

### 34. Accountability and Attribution

Autonomous actions must remain attributable.

The enterprise should be able to determine:

```text
Who initiated the task?
        ↓
Which application created the agent session?
        ↓
Which agent acted?
        ↓
Which identity was used?
        ↓
Which tool was invoked?
        ↓
Which resource was accessed?
        ↓
What decision was made?
        ↓
What action occurred?
```

Without this chain, investigation and governance become significantly more difficult.

---

### 35. Non-Repudiation Considerations

For high-impact actions, the organization may need evidence demonstrating:

* who initiated the workflow;
* which agent executed the action;
* what authorization existed;
* which policy was applied;
* which tool was used;
* what data was involved;
* when the action occurred;
* whether human approval was provided.

This supports auditability and post-incident investigation.

### 40. Zero Trust for Agentic AI

Zero Trust principles are particularly important for autonomous systems.

The enterprise should not assume that an agent is trustworthy because:

* it was created internally;
* it uses an approved model;
* it operates inside the corporate network;
* it has previously behaved correctly;
* its application owner is trusted.

Instead:

```text
Authenticate
    ↓
Authorize
    ↓
Validate Context
    ↓
Limit Privilege
    ↓
Allow Specific Action
    ↓
Monitor
    ↓
Reevaluate
```

### 42. Fail-Safe and Fail-Closed Behavior

Where an agent cannot establish that an action is authorized, the preferred security behavior should generally be:

```text
Uncertain Authorization
        ↓
Do Not Execute
        ↓
Escalate / Request Approval
```

Rather than:

```text
Uncertain Authorization
        ↓
Assume Permission
        ↓
Execute
```

Agentic systems should avoid converting uncertainty into authority.

### 45. Agent Security Objectives

The primary security objectives for agentic AI are to ensure that agents:

1. have identifiable identities;
2. authenticate securely;
3. receive only authorized privileges;
4. access only required data;
5. invoke only approved tools;
6. operate within defined autonomy limits;
7. cannot arbitrarily escalate privileges;
8. cannot bypass enterprise authorization;
9. cannot communicate externally without appropriate controls;
10. cannot execute unlimited actions;
11. remain attributable;
12. remain observable;
13. can be interrupted;
14. can be isolated;
15. can be recovered or terminated safely.

### 46. Model Behavior Is Not Agent Authorization

A critical principle for the entire chapter is:

> **Model Behavior ≠ Agent Authorization**

A model may decide:

> "I should perform this action."

That decision does not mean the action is authorized.

The architecture must separate:

```text
Model Decision
      ↓
Security Policy
      ↓
Authorization
      ↓
Tool Permission
      ↓
Action Validation
      ↓
Execution
```

The model proposes.

The security architecture authorizes.

---

### 47. Agent Capability Is Not Agent Authority

Another foundational distinction is:

> **Agent Capability ≠ Agent Authority**

An agent may have the technical capability to invoke an API without having permission to invoke it in every situation.

Likewise, an agent may be capable of:

* deleting data;
* sending email;
* modifying infrastructure;
* accessing sensitive records;

without being authorized to perform those actions.

This distinction must remain fundamental throughout agentic AI architecture.

---

### 48. Autonomous Execution Must Remain Bounded

Autonomy should never mean unrestricted authority.

A secure agent should operate within explicit boundaries for:

```text

+

+
Transactions
+
Network
+
Time
+
Resources
+
Delegation
+
Autonomy
```

These boundaries reduce the consequences of both accidental and malicious agent behavior.

---

### 49. Agent Security as a System Security Problem

Agentic AI cannot be secured solely by improving the underlying model.

Security must be distributed across the system:

```text

   +

   +

   +

   +
Tools
   +

   +

   +

   +

   +

   +
```

A highly aligned model operating inside an insecure agent architecture can still produce an insecure system.

---

### 50. Fundamental Security Principle

The foundational principle for Agentic AI Security is:

> **An AI agent must never possess more authority, autonomy, data access, tool capability, network connectivity, or transaction capability than is necessary to perform its explicitly approved business purpose. Every consequential action must remain attributable, independently authorized, bounded by security policy, observable, and capable of being interrupted or contained.**

The essential security distinction is:

```text
AI Can Decide
      ≠
AI Can Authorize
      ≠
AI Can Execute
      ≠
AI Can Execute Without Limits
```

A mature agentic AI security architecture therefore treats **autonomy, identity, authority, tools, data, communication, and action execution as separate security boundaries that must be independently controlled**.

## Part 2 — Technical Security and Control Mechanisms

### 51. Agentic AI Security Control Architecture

Agentic AI security requires controls around the complete execution chain rather than controls applied only to the underlying model.

A mature architecture should separate:

```text
User / Application
        ↓
Identity
        ↓
Agent Authentication
        ↓
Agent Authorization
        ↓
Task / Context Validation
        ↓
Agent Runtime
        ↓
Tool Authorization
        ↓
Data Authorization
        ↓
Action Validation
        ↓
Execution
        ↓
Monitoring
        ↓
Detection / Response
```

The objective is to ensure that the agent cannot convert a model decision directly into unrestricted operational authority.

---

### 52. Agent Identity Control

Every production agent should have a distinct, attributable identity where practical.

Agent identities should support:

* unique identification;
* authentication;
* authorization;
* ownership;
* lifecycle management;
* auditability;
* revocation.

Shared credentials between unrelated agents should be avoided because they make attribution and privilege control difficult.

---

### 53. Workload Identity

Agents should preferably use workload or service identities rather than human credentials.

A simplified architecture is:

```text
Human
  ↓
Application
  ↓
Agent Identity
  ↓
Authorized Service
```

rather than:

```text
Human
  ↓
Agent
  ↓
Human's Permanent Credentials
  ↓
Enterprise System
```

Workload identities reduce credential exposure and improve attribution.

---

### 54. Strong Agent Authentication

Agent authentication should establish confidence that the requesting workload is the expected agent.

Controls may include:

* workload identity;
* mutual TLS;
* certificates;
* signed tokens;
* federated identity;
* cryptographic authentication;
* workload attestation.

Authentication should occur before access to protected resources.

---

### 55. Fine-Grained Agent Authorization

Authorization should evaluate more than agent identity.

Relevant attributes can include:

* agent identity;
* initiating user;
* application;
* requested resource;
* requested action;
* business purpose;
* data sensitivity;
* transaction value;
* environment;
* time;
* risk level.

Conceptually:

```text
Agent Identity
      +
User Context
      +
Requested Action
      +
Resource
      +
Business Context
      ↓
Authorization Decision
```

---

### 56. Independent Authorization

The agent should not be the final authority for determining whether its own action is permitted.

Instead:

```text
Agent Decision
      ↓
Authorization Service
      ↓
Policy Evaluation
      ↓
Allow / Deny
      ↓
Tool Execution
```

This prevents manipulated model reasoning from becoming authorization.

---

### 57. Least-Privilege Agent Permissions

Agent permissions should be limited to the minimum required capability.

For example, an agent responsible for generating reports may need:

```text
✓ Read reporting data
✓ Generate report
✓ Store report
```

but should not automatically receive:

```text
✗ Delete records
✗ Modify identities
✗ Change firewall rules
✗ Access payroll
✗ Transfer funds
```

Least privilege reduces blast radius when the agent is compromised.

---

### 58. Capability Allowlisting

Agent capabilities should be explicitly allowlisted.

An agent should have access only to approved:

* tools;
* APIs;
* databases;
* files;
* services;
* network destinations;
* operations.

A secure design is:

```text
Agent
  ↓
Approved Capability Registry
  ↓
Allowed Tool
  ↓
Specific Operation
```

rather than permitting arbitrary capability discovery or invocation.

---

### 59. Tool Allowlisting

Tools should be explicitly approved for each agent.

Tool approval should consider:

* business purpose;
* privilege level;
* data sensitivity;
* external connectivity;
* action impact;
* reversibility;
* authentication requirements;
* monitoring requirements.

Approval of a tool for one agent should not automatically authorize its use by every agent.

---

### 60. Tool Capability Segmentation

A single tool may expose multiple operations with very different risk levels.

For example:

```text
CRM Tool
 ├── Read Customer
 ├── Create Customer
 ├── Modify Customer
 └── Delete Customer
```

These capabilities should not necessarily share the same authorization level.

A mature architecture separates capabilities by risk.

---

### 61. Tool Argument Validation

Tool invocation parameters should be independently validated before execution.

For example:

```text
Agent Request
     ↓
Tool Name Validation
     ↓
Argument Schema Validation
     ↓
Resource Validation
     ↓
Authorization
     ↓
Business Rules
     ↓
Execution
```

Validation should check:

* data type;
* permitted values;
* resource identifiers;
* ranges;
* destination;
* transaction amount;
* requested operation;
* business constraints.

---

### 62. Action Allowlisting

Even when an agent is authorized to use a tool, individual actions should be restricted.

For example:

```text
Tool: Payment API

Allowed:
✓ Check payment status
✓ Retrieve transaction history

Restricted:
△ Create payment

Prohibited:
✗ Change settlement account
✗ Transfer unlimited funds
```

Tool authorization should therefore operate at the **action level**, not merely the tool level.

---

### 63. Transaction Limits

High-impact actions should have explicit transaction boundaries.

Controls may include:

* maximum transaction value;
* maximum number of transactions;
* maximum daily volume;
* approved beneficiaries;
* approved accounts;
* transaction frequency;
* geographic restrictions.

This prevents an authorized agent from converting a legitimate capability into unlimited operational impact.

---

### 64. Cumulative Action Limits

Individual actions may appear harmless while their combined effect becomes dangerous.

For example:

```text
Read 100 records
Read 100 records
Read 100 records
...
```

may eventually create a large-scale data exposure.

Therefore, controls should evaluate cumulative:

* data volume;
* transaction count;
* tool calls;
* financial value;
* external messages;
* infrastructure changes.

---

### 65. Time-Bounded Agent Authority

Agent privileges should preferably be limited to the period required for the task.

For example:

```text
Task Start
    ↓
Short-Lived Authorization
    ↓
Task Execution
    ↓
Authorization Expiration
```

Persistent authorization increases the opportunity for misuse or compromise.

---

### 66. Short-Lived Credentials

Agents should use short-lived credentials where supported.

Advantages include:

* reduced credential exposure;
* reduced replay window;
* easier revocation;
* improved attribution;
* reduced persistence after compromise.

Long-lived static credentials should be avoided for high-risk agent workflows where practical.

---

### 67. Credential Isolation

Agent credentials should be isolated from:

* prompts;
* model context;
* memory;
* retrieved documents;
* user-visible output;
* logs;
* tool results.

A critical rule is:

> **Credentials should never depend on the model correctly keeping secrets.**

Secrets should be supplied through controlled infrastructure.

---

### 68. Secrets Management

Secrets should be stored and managed through dedicated security mechanisms.

The agent should receive only the credential material necessary for the specific operation.

Conceptually:

```text
Agent
 ↓
Secret Request
 ↓
Authorization
 ↓
Secrets Manager
 ↓
Short-Lived Credential
 ↓
Target Service
```

The model should not receive unrestricted access to the enterprise secrets store.

---

### 69. Context Security

Agent context should distinguish between:

* trusted instructions;
* user input;
* retrieved content;
* memory;
* tool results;
* other-agent messages;
* external content.

A simplified model is:

```text
Trusted Policy
      +
Validated Context
      +
Untrusted Content
      ↓
Controlled Agent Context
```

The agent should not treat every context element as equally authoritative.

---

### 70. Prompt and Instruction Integrity

System instructions and agent policies should be protected against unauthorized modification.

Controls should include:

* version control;
* access control;
* integrity verification;
* approval workflows;
* change monitoring;
* controlled deployment.

This reduces the risk that an attacker changes the agent's intended behavior.

---

### 71. Untrusted Input Isolation

External content should be isolated from trusted agent instructions.

Potentially untrusted sources include:

* websites;
* email;
* documents;
* user messages;
* tickets;
* retrieved content;
* API responses;
* other agents.

The architecture should prevent these sources from automatically overriding higher-trust instructions.

---

### 72. Prompt Injection Detection

Agent systems should detect potential prompt injection before untrusted content reaches sensitive execution paths.

Detection may use:

* deterministic rules;
* pattern detection;
* content classification;
* security models;
* behavioral analysis;
* provenance information.

Detection should be treated as an additional control, not the only security boundary.

---

### 73. Memory Isolation

Agent memory should be isolated according to:

* user;
* tenant;
* application;
* agent;
* security domain;
* data classification.

A user's memory should not automatically become available to another user or agent.

---

### 74. Memory Authorization

Access to persistent memory should be independently authorized.

The agent should not be able to arbitrarily:

* read all memory;
* modify protected memory;
* delete audit-critical records;
* access another tenant's memory;
* retrieve unrelated historical information.

Memory access should follow the same authorization principles as enterprise databases.

---

### 75. Memory Integrity

Persistent agent memory can influence future decisions.

Therefore, memory should be protected against:

* unauthorized modification;
* poisoning;
* deletion;
* replay;
* manipulation;
* unauthorized insertion.

Important memory elements should have provenance and integrity controls.

---

### 76. Persistent Context Controls

Persistent context should have explicit:

* retention periods;
* access policies;
* classification;
* integrity protection;
* deletion procedures;
* tenant boundaries.

Persistence should not automatically mean permanent availability.

---

### 77. Data Access Authorization

Agents should obtain data through established enterprise authorization mechanisms.

The secure pattern is:

```text
Agent
 ↓
Identity
 ↓
Authorization
 ↓
Data Query
 ↓
Row / Record / Field Controls
 ↓
Authorized Result
 ↓
Agent
```

The agent should not bypass existing application-level data permissions.

---

### 78. Data Minimization

Only the data required for the agent's task should enter its context.

For example:

```text
Required:
Customer ID
Order Status
Delivery Date

Not Required:
Full Payment Details
Authentication Data
Unrelated Customer Records
```

Data minimization reduces the impact of agent compromise.

---

### 79. Field-Level Data Protection

Sensitive fields should be filtered before data reaches the agent.

For example:

```text
Customer Record
 ├── Name                 → Allowed
 ├── Order Number         → Allowed
 ├── Address              → Conditional
 ├── Payment Token        → Restricted
 └── Authentication Data → Prohibited
```

Field-level controls are especially important when agents operate against large enterprise databases.

---

### 80. Tenant Isolation

Multi-tenant agent systems must prevent unauthorized cross-tenant access.

Controls should apply to:

* identity;
* memory;
* RAG;
* vector stores;
* databases;
* tool results;
* conversation state;
* agent communication.

Tenant boundaries should be enforced independently of model behavior.

---

### 81. Session Isolation

Agent sessions should be isolated where security requirements demand it.

A session should not unintentionally inherit:

* another user's context;
* another user's credentials;
* another agent's memory;
* previous sensitive tool results;
* unrelated task state.

Session isolation reduces cross-user and cross-task contamination.

---

### 82. Network Segmentation

Agents should have only the network connectivity necessary for their approved purpose.

For example:

```text
Agent Network Zone
      |
      +── Approved API
      |
      +── Approved Database
      |
      X── Payment Network
      X── Identity Administration
      X── Unrestricted Internet
```

Network segmentation provides an independent security boundary if the agent is manipulated.

---

### 83. Egress Controls

Outbound communication from agents should be controlled.

Controls may restrict:

* destination;
* protocol;
* port;
* domain;
* data type;
* volume;
* identity;
* business purpose.

This reduces the possibility that a compromised agent becomes an unrestricted exfiltration channel.

---

### 84. External Communication Controls

Agents capable of sending:

* email;
* messages;
* web requests;
* API calls;
* documents;
* notifications

should have destination-specific controls.

External communication should not be enabled simply because the agent technically supports it.

---

### 85. Code Execution Isolation

Agents capable of executing code should operate within controlled environments.

Controls may include:

* sandboxing;
* filesystem isolation;
* network restrictions;
* resource limits;
* process restrictions;
* ephemeral environments;
* restricted credentials.

The agent should not receive unrestricted operating-system privileges.

---

### 86. Database Security Controls

Database-connected agents should use:

* dedicated identities;
* least-privilege accounts;
* read/write separation;
* query controls;
* row-level security;
* field-level restrictions;
* transaction limits;
* audit logging.

For example:

```text
Agent
 ↓
Read-Only Database Identity
 ↓
Approved Query
 ↓
Authorized Data
```

should be preferred over unrestricted database administration access.

---

### 87. Read/Write Separation

Where practical, read and write capabilities should be separated.

```text
Agent
 ├── Read Identity
 │      └── Read-only access
 │
 └── Write Identity
        └── Restricted + separately authorized
```

This reduces the impact of an agent compromise.

---

### 88. Human Approval Controls

High-impact actions should require human approval where appropriate.

Examples include:

* financial transactions;
* production changes;
* privilege changes;
* destructive operations;
* external commitments;
* regulated decisions.

A typical workflow is:

```text
Agent Recommendation
       ↓
Risk Evaluation
       ↓
Human Review
       ↓
Approval / Rejection
       ↓
Authorized Execution
```

---

### 89. Action Preview

Before executing consequential actions, the system should provide an understandable representation of:

* intended action;
* target;
* parameters;
* affected resources;
* expected impact.

This enables human reviewers to validate what the agent is actually attempting to do.

---

### 90. Dual Authorization

Certain high-risk actions may require two independent approvals.

For example:

```text
Agent
 ↓
Action Request
 ↓
Authorization
 ↓
Human Approver 1
 ↓
Human / Security Approver 2
 ↓
Execution
```

This is appropriate for particularly sensitive or irreversible operations.

---

### 91. Reversibility Controls

Where possible, autonomous actions should be designed to be reversible.

Examples:

* staged changes;
* transaction cancellation windows;
* backups;
* snapshots;
* soft deletion;
* deployment rollback;
* temporary permissions.

Reversibility limits the consequences of incorrect or malicious agent decisions.

---

### 92. Agent Execution Limits

Agents should have explicit limits on:

* execution time;
* number of iterations;
* tool calls;
* API calls;
* transaction count;
* data volume;
* memory usage;
* compute consumption.

For example:

```text
Maximum Task Duration: 30 minutes
Maximum Tool Calls:    50
Maximum Transactions:  5
Maximum Data Volume:   Defined by Policy
```

These values should be determined by business and risk requirements.

---

### 93. Loop Detection

Agent runtimes should detect repeated or abnormal execution patterns.

Potential indicators include:

```text
Tool A
 ↓
Tool B
 ↓
Tool A
 ↓
Tool B
 ↓
Tool A
 ↓
...
```

Controls may terminate, pause, or escalate the workflow when execution becomes repetitive or exceeds defined thresholds.

---

### 94. Recursive Delegation Controls

Agents should not be permitted to create unlimited chains of delegated agents.

Controls should define:

* maximum delegation depth;
* approved downstream agents;
* inherited permissions;
* cumulative privileges;
* delegation purpose;
* transaction boundaries.

Delegation should normally preserve or reduce authority.

---

### 95. Agent-to-Agent Authentication

Agent-to-agent communication should authenticate both parties.

```text
Agent A
   ↓
Authenticate
   ↓
Agent B
   ↓
Verify Identity
   ↓
Authorize Message / Request
```

Trust should not be established merely because both agents belong to the same organization.

---

### 96. Agent-to-Agent Message Integrity

Agent messages should be protected against unauthorized modification.

Controls may include:

* authenticated communication;
* integrity-protected messages;
* signatures;
* secure transport;
* sequence controls;
* replay protection.

This is especially important when messages can cause downstream actions.

---

### 97. Delegated Authority Constraints

When Agent A delegates work to Agent B:

```text
Agent A Authority
       ↓
Delegation Policy
       ↓
Agent B Authority
```

Agent B should receive only the authority required for the delegated task.

Delegation must not become an indirect privilege-escalation mechanism.

---

### 98. Tool Result Validation

Tool results should not automatically be treated as trusted instructions.

A tool response may contain:

* unexpected commands;
* malicious content;
* manipulated data;
* prompt injection;
* incorrect information;
* excessive privileges.

The agent runtime should distinguish between **tool data** and **trusted security instructions**.

---

### 99. Output Validation Before Action

Agent-generated actions should undergo validation before execution.

```text
Agent Output
     ↓
Schema Validation
     ↓
Semantic Validation
     ↓
Authorization
     ↓
Business Rules
     ↓
Execution
```

This is especially important when model output is converted into API calls, transactions, database operations, or infrastructure changes.

---

### 100. Business Rule Enforcement

Business rules should be enforced independently of the agent.

Examples:

* maximum transaction amount;
* approved customer status;
* mandatory approval;
* restricted destination;
* separation of duties;
* change windows;
* regulatory restrictions.

The agent should not be trusted to consistently enforce its own business rules.

---

### 101. Resource Controls

Agent workloads should operate within defined resource budgets.

Controls may include:

* CPU;
* memory;
* storage;
* tokens;
* API calls;
* retrieval operations;
* tool calls;
* execution time;
* financial cost.

This prevents autonomous workflows from creating uncontrolled consumption.

---

### 102. Rate Limiting

Rate limits should apply to:

* agent requests;
* tool calls;
* API calls;
* transactions;
* external communication;
* retrieval;
* delegation.

Limits should be applied independently of the model.

---

### 103. Concurrency Controls

An agent should not be able to create unlimited simultaneous operations.

Controls may include:

* maximum concurrent tasks;
* maximum active tool calls;
* per-agent concurrency;
* per-user concurrency;
* per-tenant concurrency.

This protects both availability and operational stability.

---

### 104. Timeout Controls

Every autonomous operation should have appropriate time boundaries.

Timeouts should apply to:

* model inference;
* tool calls;
* API calls;
* database queries;
* external requests;
* agent tasks.

Timeouts prevent indefinitely hanging workflows.

---

### 105. Retry Controls

Retries can amplify failures and create operational incidents.

Agent runtimes should define:

* maximum retries;
* retry intervals;
* exponential backoff;
* retryable errors;
* non-retryable operations.

A failed transaction should not automatically become repeated transactions.

---

### 106. Circuit Breakers

Circuit breakers can temporarily stop agent activity when abnormal conditions occur.

```text
Normal Operation
      ↓
Repeated Failure / Risk
      ↓
Circuit Breaker
      ↓
Stop New Actions
      ↓
Investigate / Recover
```

This helps prevent cascading failures.

---

### 107. Emergency Agent Controls

Production agent platforms should provide emergency controls capable of:

* pausing an agent;
* disabling tools;
* revoking credentials;
* blocking network access;
* terminating sessions;
* isolating workloads;
* stopping transactions.

Emergency controls should operate independently of the model.

---

### 108. Agent Kill Switch

A kill switch should provide a rapid mechanism to stop an agent when continued operation creates unacceptable risk.

A mature design may support:

```text
Detection
   ↓
Risk Threshold Exceeded
   ↓
Kill Switch
   ↓
Terminate Agent Execution
   ↓
Revoke Credentials
   ↓
Disable Tools
   ↓
Preserve Evidence
```

The kill switch should not depend on the agent voluntarily terminating itself.

---

### 109. Credential Revocation

When an agent is suspected of compromise, its credentials should be revocable rapidly.

Revocation should cover:

* service tokens;
* API credentials;
* certificates;
* temporary permissions;
* delegated identities;
* tool credentials.

This limits continued unauthorized activity.

---

### 110. Agent Isolation

A compromised agent should be capable of being isolated from:

* other agents;
* sensitive databases;
* production infrastructure;
* external networks;
* privileged tools;
* enterprise identity systems.

Isolation reduces lateral movement and blast radius.

---

### 111. Behavioral Monitoring

Agent activity should be monitored against expected behavioral baselines.

Indicators may include:

* unusual tools;
* unusual destinations;
* unusual data volume;
* unusual transaction values;
* unusual execution duration;
* unusual delegation;
* unusual access patterns;
* repeated failures.

Behavioral monitoring provides an additional layer beyond static authorization.

---

### 112. Agent Activity Logging

Security-relevant agent events should be logged.

Examples include:

* agent authentication;
* authorization decisions;
* tool invocation;
* tool parameters;
* data access;
* model invocation;
* agent-to-agent messages;
* delegation;
* transaction execution;
* human approval;
* policy violations;
* emergency actions.

Logs should support investigation without unnecessarily exposing sensitive content.

---

### 113. Tamper-Resistant Audit Logging

Security-critical agent logs should be protected against unauthorized modification.

Controls may include:

* centralized logging;
* access restrictions;
* integrity protection;
* immutable storage;
* time synchronization;
* restricted deletion.

This supports incident investigation and accountability.

---

### 114. Agent Security Observability

Observability should provide end-to-end visibility across the agent workflow.

A useful trace is:

```text
User
 ↓
Application
 ↓
Agent
 ↓
Model
 ↓
Decision
 ↓
Tool
 ↓
API
 ↓
Data
 ↓
Action
 ↓
Result
```

This allows security teams to reconstruct autonomous activity.

---

### 115. Agent Risk Detection

Detection should correlate multiple signals rather than relying on a single event.

For example:

```text
New Agent Login
      +
Unusual Tool
      +
Sensitive Data Access
      +
External Destination
      +
High Transaction Value
      ↓
High-Risk Agent Activity
```

Correlation improves detection of complex agent attacks.

---

### 116. Secure Failure Handling

When security controls cannot establish that an action is safe and authorized, the preferred behavior should generally be:

```text
Authorization Uncertain
        ↓
Block / Pause
        ↓
Escalate
        ↓
Human or Security Review
```

rather than:

```text
Authorization Uncertain
        ↓
Assume Permission
        ↓
Execute
```

Agentic systems should fail safely for consequential operations.

---

### 117. Core Engineering Principle

The central technical principle for agentic AI security is:

> **Never rely on the AI agent or underlying model to enforce the security properties of its own authority.**

Identity, authentication, authorization, privilege, tool access, data access, network connectivity, transaction limits, resource consumption, human approval, monitoring, and emergency controls should be **independently enforceable outside the model whenever technically and operationally feasible**.

A mature technical control model is:

```text
Define Agent Identity
        ↓
Authenticate
        ↓
Authorize
        ↓
Apply Least Privilege
        ↓
Validate Context
        ↓
Allow Specific Capabilities
        ↓
Validate Tool / Action Parameters
        ↓
Apply Data / Network / Resource Controls
        ↓
Require Human Approval for High-Risk Actions
        ↓
Execute Within Defined Boundaries
        ↓
Monitor Continuously
        ↓
Detect Anomalies
        ↓
Pause / Isolate / Revoke / Terminate
        ↓
Preserve Evidence
```

The security architecture must ensure that **agent intelligence remains separated from enterprise authority**. An agent may reason about an action, propose an action, or request an action, but the security control plane must independently determine whether that action is permitted.

## Part 3 — Governance, Risk, GRC, and Operational Controls

### 118. Agentic AI Security Governance Framework

Agentic AI security governance establishes the organizational structure required to control autonomous AI systems throughout their lifecycle.

Governance should define:

* who owns the agent;
* why the agent exists;
* what authority it has;
* what data it can access;
* which tools it can use;
* which systems it can affect;
* how much autonomy it has;
* when human approval is required;
* how activity is monitored;
* how the agent can be suspended or terminated.

The governance objective is to ensure that agentic capability remains aligned with approved business purpose and enterprise risk appetite.

---

### 119. Agent Ownership and Accountability

Every production agent should have clearly assigned ownership.

Ownership should identify at least:

| Responsibility      | Example                           |
| ------------------- | --------------------------------- |
| Business Owner      | Defines business purpose          |
| Technical Owner     | Maintains agent implementation    |
| Security Owner      | Defines security requirements     |
| Data Owner          | Approves data access              |
| Agent Administrator | Manages operational configuration |
| Risk Owner          | Accepts residual risk             |
| SOC                 | Monitors security events          |
| Internal Audit      | Provides independent assurance    |

An agent without an accountable owner should not be permitted to operate as an unmanaged production capability.

---

### 120. Agent Risk Classification

Agents should be classified according to their potential impact.

Relevant classification factors include:

* autonomy;
* privilege;
* data sensitivity;
* transaction capability;
* external connectivity;
* persistence;
* number of tools;
* number of systems affected;
* reversibility;
* regulatory impact.

A simple model may be:

```text
Low Risk
   ↓
Informational Agent
   ↓
Operational Agent
   ↓
Privileged Agent
   ↓
High-Impact Autonomous Agent
   ↓
Critical Agent
```

Higher-risk agents require stronger governance and assurance.

---

### 121. AI Application Risk Tiering

Agent risk should be evaluated as part of the broader AI application risk tier.

For example:

| Tier   | Characteristics                          | Governance                                 |
| ------ | ---------------------------------------- | ------------------------------------------ |
| Tier 1 | Low-impact assistance                    | Standard controls                          |
| Tier 2 | Business process support                 | Enhanced controls                          |
| Tier 3 | Sensitive data / operational actions     | Strong authorization and monitoring        |
| Tier 4 | High-impact autonomous actions           | Human approval and enhanced assurance      |
| Tier 5 | Critical or highly privileged operations | Maximum controls and independent assurance |

Risk tiering should determine the minimum security requirements applicable to the agent.

---

### 122. Agentic AI Risk Register

Agentic AI risks should be formally recorded in the enterprise risk register.

Risk scenarios may include:

* unauthorized agent action;
* excessive privilege;
* agent hijacking;
* tool abuse;
* memory poisoning;
* unauthorized data access;
* credential compromise;
* malicious delegation;
* agent-to-agent impersonation;
* uncontrolled autonomous transactions;
* excessive resource consumption;
* external data exfiltration.

Each risk should have:

* risk owner;
* affected assets;
* likelihood;
* impact;
* inherent risk;
* controls;
* residual risk;
* treatment decision;
* review frequency.

---

### 123. Risk Appetite and Tolerance

Organizations should explicitly define how much autonomous AI risk they are willing to accept.

Risk appetite should address:

* maximum autonomous transaction value;
* acceptable autonomy levels;
* permitted data sensitivity;
* acceptable external connectivity;
* acceptable tool privilege;
* permitted delegation;
* acceptable human-oversight requirements.

For example:

```text
Low-Impact Action
      ↓
Autonomous Execution Allowed

High-Impact Action
      ↓
Human Approval Required

Critical / Irreversible Action
      ↓
Restricted or Prohibited
```

---

### 124. Agent Autonomy Governance

Autonomy should be explicitly approved rather than emerging accidentally from technical capability.

Governance should define:

* maximum autonomy level;
* permitted action classes;
* human intervention requirements;
* execution duration;
* transaction limits;
* delegation limits;
* escalation requirements.

Autonomy should be treated as a governed risk attribute.

---

### 125. Agent Identity Governance

Agent identities should be governed similarly to other enterprise identities.

Governance should cover:

* identity creation;
* ownership;
* naming;
* authentication method;
* credential lifecycle;
* privilege assignment;
* access review;
* suspension;
* revocation;
* retirement.

An agent identity should not remain active indefinitely without periodic review.

---

### 126. Agent Authentication Governance

Authentication requirements should be proportional to agent risk.

High-risk agents may require:

* strong workload identity;
* certificate-based authentication;
* mutual TLS;
* cryptographic credentials;
* workload attestation;
* short-lived authentication tokens.

Authentication mechanisms should be formally approved and periodically reviewed.

---

### 127. Agent Authorization Governance

Authorization policies should define:

* who may create agents;
* which agents may access which systems;
* which actions are permitted;
* which resources are restricted;
* which transactions require approval;
* which actions are prohibited.

Authorization should be centrally governed where practical.

---

### 128. Agent Permission Governance

Agent permissions should be reviewed throughout the lifecycle.

Access reviews should evaluate:

* whether each permission remains necessary;
* whether privilege has expanded;
* whether tools are still required;
* whether data access remains justified;
* whether business purpose has changed.

Unused permissions should be removed.

---

### 129. Tool Governance

Every tool exposed to an agent should have an owner and security classification.

Tool governance should consider:

* function;
* privilege;
* data access;
* external connectivity;
* destructive capability;
* reversibility;
* transaction impact;
* authentication;
* monitoring;
* dependencies.

Tool availability should be explicitly approved for specific agents.

---

### 130. Agent Capability Governance

Agent capabilities should be documented as part of the agent inventory.

A capability record should identify:

```text
Agent
 ↓
Capability
 ↓
Tool / API
 ↓
Permitted Operation
 ↓
Permitted Resource
 ↓
Authorization Requirement
 ↓
Risk Level
```

This prevents broad technical capabilities from becoming uncontrolled operational authority.

---

### 131. Data Access Governance

Agent access to enterprise information should follow existing data governance principles.

Governance should define:

* permitted datasets;
* sensitivity classification;
* purpose limitation;
* retention;
* access conditions;
* tenant boundaries;
* export restrictions;
* monitoring.

Agents should not create alternative access paths around established enterprise data controls.

---

### 132. Sensitive Data Governance

Agents processing sensitive information require enhanced governance.

Sensitive data may include:

* personal information;
* financial information;
* authentication information;
* intellectual property;
* security information;
* confidential business data;
* regulated information.

Governance should define when agents may access, process, retain, transform, or transmit such information.

---

### 133. RAG Governance for Agents

When agents use retrieval-augmented generation, governance should cover:

* approved knowledge sources;
* source ownership;
* access control;
* provenance;
* retrieval permissions;
* document classification;
* vector-store access;
* tenant isolation;
* retention;
* poisoning controls.

The agent should not use RAG as a mechanism to bypass normal information-access governance.

---

### 134. Memory Governance

Persistent agent memory should be governed as enterprise data.

Governance should define:

### 225. Model Behavior Is Not Security Authorization

A model may produce:

> “I am authorized to perform this operation.”

That statement has no security authority by itself.

Authorization must be established through trusted enterprise mechanisms.

```text
Model Claim
    ≠
Authenticated Identity

Model Decision
    ≠
Authorization Decision

Model Confidence
    ≠
Security Assurance
```

This distinction should remain fundamental throughout the architecture.

---

### 226. Agent Capability Is Not Agent Authority

An agent may technically possess the ability to invoke a function without being authorized to use it in every context.

For example:

```text
Technical Capability:
delete_customer()

Security Authority:
delete_customer()
     only when:
     - approved workflow
     - authorized agent
     - permitted customer scope
     - valid business purpose
     - required approval
```

Technical capability must therefore remain subordinate to security authority.

### 228. Agent Compromise Must Not Equal Enterprise Compromise

```text
        ↓

        ↓
```

Security architecture should be resilient even when individual AI components fail.

### 229. Autonomous Systems Require Independent Control

An autonomous system should never be the sole mechanism responsible for controlling its own authority.

Critical security functions should remain outside the model's control wherever technically feasible.

These include:

* authentication;
* authorization;
* credential issuance;
* privilege enforcement;
* transaction approval;
* emergency shutdown;
* audit integrity.

This establishes a separation between **AI decision-making** and **security enforcement**.

### 233. Strategic Architecture Principle

The final architectural principle is:

> **Agentic AI security must separate intelligence from authority.**

The AI system may:

* perceive;
* reason;
* plan;
* recommend;
* prioritize;
* request actions.

Enterprise security controls must independently determine whether the requested action may occur.

```text
              AI SYSTEM
                  │
        Perceive / Reason / Plan
                  │
                  ▼
          Action Recommendation
                  │
                  ▼
        ┌─────────────────────┐
        │ SECURITY CONTROL    │
        │                     │
        │ Identity            │
        │ Authorization       │
        │ Policy              │
        │ Risk                │
        │ Limits              │
        │ Human Approval      │
        └──────────┬──────────┘
                   │
             ALLOW / DENY
                   │
                   ▼
              EXECUTION
                   │
                   ▼
        Monitoring / Evidence
```

**Agent Capability ≠ Agent Authority.**

**Model Behavior ≠ Security Authorization.**

An enterprise agent should therefore remain **bounded, independently authorized, least-privileged, attributable, observable, interruptible, and recoverable throughout its operational lifecycle**.
