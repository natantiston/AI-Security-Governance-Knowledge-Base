# 11.12 — Agent Hijacking

## Part 1 — Foundations and Core Concepts

### 1. Definition of Agent Hijacking

Agent hijacking is the unauthorized manipulation or takeover of an AI agent's behavior, execution context, authority, or operational control.

The attacker may attempt to cause the agent to:

* perform unauthorized actions;
* follow malicious instructions;
* misuse legitimate tools;
* disclose protected information;
* alter its operating objectives;
* bypass established security controls.

Agent hijacking is therefore broader than simply compromising a model.

---

### 2. Agent Hijacking as an Agentic AI Security Threat

In conventional applications, compromising a component may provide access to a defined function.

In agentic systems, hijacking can influence:

```text
Perception
   ↓
Reasoning
   ↓
Planning
   ↓
Tool Selection
   ↓
Action
   ↓
External Effect
```

The attacker may therefore manipulate the agent's decision and execution chain.

---

### 3. Agent Hijacking vs Model Compromise

Model compromise concerns the model itself.

Agent hijacking concerns the broader operational system surrounding the model.

```text
Model Compromise
      ↓
Model Behavior

Agent Hijacking
      ↓
Agent Behavior
      ↓
Tools
      ↓
Memory
      ↓
Identity
      ↓
Actions
```

An agent can potentially be hijacked even when the underlying model infrastructure remains uncompromised.

---

### 4. Agent Hijacking vs Account Takeover

Traditional account takeover usually involves gaining control of a user's account.

Agent hijacking may instead involve manipulating:

* agent context;
* instructions;
* memory;
* tools;
* sessions;
* execution state;
* delegated authority.

The attacker may never need to obtain the agent's primary identity credential.

---

### 5. Agent Hijacking vs Prompt Injection

Prompt injection is one possible mechanism for influencing an agent.

Agent hijacking is the broader security outcome.

```text
Prompt Injection
       ↓
Agent Manipulation
       ↓
Agent Hijacking
       ↓
Unauthorized Behavior
```

Not every prompt injection results in successful hijacking, but successful manipulation of agent behavior may constitute an agent-hijacking condition.

---

### 6. Agent Hijacking as a Security Boundary Violation

An agent operates within defined security boundaries.

Hijacking occurs when an attacker causes the agent to operate outside its intended:

* purpose;
* context;
* authority;
* permissions;
* transaction limits;
* tool boundaries.

---

### 7. Agent Control Boundary

The control boundary defines what components can legitimately influence agent behavior.

```text
Trusted Control Plane
        │
        ▼
Agent Runtime
        │
        ├── Model
        ├── Context
        ├── Memory
        ├── Tools
        └── Actions
```

Unauthorized influence crossing this boundary can create hijacking risk.

---

### 8. Agent Execution Context

An agent's execution context may include:

* system instructions;
* user requests;
* retrieved information;
* tool results;
* memory;
* session state;
* environment variables;
* security policies.

Compromise of any security-sensitive component can potentially influence subsequent behavior.

---

### 9. Trusted vs Untrusted Agent Inputs

Agent inputs should be classified according to trust.

```text
Higher Trust
    │
    ├── Security Policy
    ├── Authorization Service
    ├── Identity Provider
    │
    ├── Business Systems
    │
    └── External Content
Lower Trust
```

Untrusted content must not automatically acquire the authority of trusted instructions.

---

### 10. Agent Instruction Hierarchy

Agentic systems often process multiple instruction sources.

For example:

```text
Security Policy
      ↓
System Instructions
      ↓
Application Instructions
      ↓
User Instructions
      ↓
External Content
```

Hijacking may occur when lower-trust content successfully overrides or manipulates higher-trust instructions.

---

### 11. Agent Objective Manipulation

An attacker may attempt to change the effective objective of an agent.

For example:

```text
Original Objective:
Process customer refunds according to policy.

Manipulated Objective:
Refund every request immediately.
```

Objective manipulation is dangerous because the agent may continue operating legitimately from the perspective of its compromised reasoning.

---

### 12. Agent Goal Hijacking

Goal hijacking occurs when an attacker causes an agent to pursue an unauthorized goal.

The malicious goal may be introduced through:

* user input;
* documents;
* websites;
* email;
* tool output;
* memory;
* another agent.

The agent may then perform legitimate actions toward an illegitimate objective.

---

### 13. Agent Context Hijacking

Context hijacking occurs when an attacker manipulates the information available to the agent so that it reaches unauthorized conclusions.

```text
Trusted Context
      +
Manipulated Context
      ↓
Incorrect Agent Decision
      ↓
Potentially Unauthorized Action
```

The attacker does not necessarily need to alter the model itself.

---

### 14. Agent Session Hijacking

Session hijacking involves gaining unauthorized control over an active agent session or manipulating the session's state.

Potential consequences include:

* impersonation;
* unauthorized instructions;
* access to session data;
* tool misuse;
* transaction execution.

Session identity must therefore remain strongly bound to the authorized principal and execution context.

---

### 15. Agent Runtime Hijacking

Runtime hijacking involves compromising the environment in which an agent executes.

Potential targets include:

* agent orchestration services;
* containers;
* virtual machines;
* execution workers;
* runtime configuration;
* environment variables.

Runtime compromise can provide a path to bypass application-level safeguards.

---

### 16. Agent Identity Hijacking

Identity hijacking occurs when an attacker causes actions to appear as though they originated from a legitimate agent.

```text
Attacker
   ↓
Spoofed / Compromised Identity
   ↓
Enterprise System
   ↓
Trusted Agent Assumption
```

Strong workload identity and attribution controls are therefore essential.

---

### 17. Agent Credential Hijacking

An attacker may obtain credentials associated with an agent.

Potential credentials include:

* API tokens;
* service credentials;
* certificates;
* cloud credentials;
* database credentials;
* delegated tokens.

Credential compromise can enable direct impersonation even without manipulating the model.

---

### 18. Agent Tool Hijacking

An attacker may manipulate the tools available to an agent or the way those tools are invoked.

Examples include:

* replacing a legitimate endpoint;
* modifying tool configuration;
* changing tool schemas;
* redirecting API requests;
* introducing a malicious tool.

Tool hijacking can convert legitimate agent capabilities into attack mechanisms.

---

### 19. Agent Memory Hijacking

Attackers may attempt to insert malicious information into persistent agent memory.

```text
Attacker Input
     ↓
Memory
     ↓
Future Agent Session
     ↓
Manipulated Behavior
```

Persistent memory creates a particularly important hijacking risk because malicious influence can survive beyond the original interaction.

---

### 20. Agent Context Persistence Risk

A hijacking condition may persist if malicious instructions or state are stored in:

* long-term memory;
* knowledge bases;
* workflow state;
* configuration;
* task queues.

Persistence can transform a temporary manipulation into a recurring compromise.

---

### 21. Agent-to-Agent Hijacking

In multi-agent systems, one compromised agent may attempt to influence another agent.

```text
Compromised Agent A
        ↓
Malicious Message
        ↓
Trusted Agent B
        ↓
Unauthorized Action
```

The receiving agent must not automatically trust messages merely because they originate from another registered agent.

---

### 22. Delegation Hijacking

An attacker may manipulate delegated authority so that a transaction or task is executed by another agent under apparently legitimate authority.

Potential consequences include:

* privilege propagation;
* unauthorized actions;
* authority amplification;
* loss of attribution.

Delegated authority must therefore remain explicitly bounded.

---

### 23. Agent Authority Hijacking

Authority hijacking occurs when an attacker causes an agent to operate with authority beyond its intended scope.

Examples include:

* accessing restricted records;
* executing administrative actions;
* modifying security policies;
* initiating high-value transactions.

The security architecture must prevent the agent from expanding its own authority.

---

### 24. Agent Behavior Hijacking

Agent behavior may be manipulated without compromising identity or credentials.

For example:

```text
Legitimate Agent
      ↓
Malicious Context
      ↓
Manipulated Reasoning
      ↓
Legitimate Credentials
      ↓
Unauthorized Action
```

This makes behavioral protection as important as credential protection.

---

### 25. Agent Hijacking Through Prompt Injection

Prompt injection may attempt to redirect an agent toward unauthorized actions.

Examples include instructions such as:

* ignore previous restrictions;
* reveal confidential information;
* call a privileged tool;
* change transaction parameters;
* disable security checks.

Independent enforcement must prevent successful injection from becoming unauthorized execution.

---

### 26. Agent Hijacking Through Indirect Prompt Injection

Indirect prompt injection occurs when malicious instructions are embedded in content the agent processes.

Potential sources include:

* websites;
* PDFs;
* emails;
* documents;
* issue trackers;
* knowledge bases;
* retrieved records.

```text
External Content
      ↓
Agent Retrieval
      ↓
Malicious Instruction
      ↓
Agent Reasoning
      ↓
Potential Hijacking
```

---

### 27. Agent Hijacking Through Tool Results

Tool results should be treated as potentially untrusted inputs.

A compromised or manipulated tool could return information designed to influence the agent.

```text
Tool
 ↓
Malicious Result
 ↓
Agent Reasoning
 ↓
Unsafe Decision
```

Tool output must not automatically acquire instruction authority.

---

### 28. Agent Hijacking Through Memory Poisoning

Memory poisoning can create persistent behavioral manipulation.

An attacker may attempt to insert false information such as:

```text
"Security approval has already been granted."
```

If later treated as authoritative, the stored information could influence future transactions.

Memory provenance and authorization boundaries are therefore critical.

---

### 29. Agent Hijacking Through Identity Confusion

An agent may receive conflicting identity information.

For example:

```text
User Identity
      ≠
Agent Identity
      ≠
Delegated Identity
```

If these identities become confused, the agent may perform an action under the wrong authority.

---

### 30. Agent Hijacking Through Authorization Confusion

An attacker may attempt to convince the agent that an action is authorized when it is not.

```text
Agent:
"The user said this is approved."

Authorization Service:
"DENY."
```

The authorization service must remain authoritative.

---

### 31. Agent Hijacking Through Tool Substitution

A malicious tool may be substituted for a trusted tool or an approved tool may be redirected to an unauthorized endpoint.

Tool identity and provenance must therefore be validated.

---

### 32. Agent Hijacking Through Configuration Manipulation

Agent configuration can influence:

* tools;
* permissions;
* prompts;
* endpoints;
* memory;
* execution limits.

Unauthorized configuration changes can therefore create a hijacking condition without directly modifying the model.

---

### 33. Agent Hijacking Through Workflow Manipulation

An attacker may manipulate the workflow surrounding an agent.

Examples include:

* changing task queues;
* inserting malicious jobs;
* altering workflow states;
* modifying approval status;
* changing execution order.

The agent may then execute actions according to a compromised workflow.

---

### 34. Agent Hijacking Through Event Manipulation

Event-driven agents may react automatically to external events.

If event integrity is compromised, an attacker may generate malicious events that trigger autonomous actions.

```text
False Event
    ↓
Agent Trigger
    ↓
Agent Decision
    ↓
Autonomous Action
```

Event authenticity must therefore be verified.

---

### 35. Agent Hijacking Through API Manipulation

APIs connecting agents to enterprise systems can become hijacking paths.

Attackers may attempt:

* request manipulation;
* endpoint substitution;
* parameter tampering;
* token abuse;
* replay;
* response manipulation.

API security must therefore be part of the agent security boundary.

---

### 36. Agent Hijacking Through External Connectivity

Internet access and external services can expose agents to hostile content and systems.

An agent capable of browsing, communicating, or interacting with external services has a broader hijacking surface than an isolated agent.

---

### 37. Agent Hijacking and Excessive Agency

Excessive agency increases the consequences of successful hijacking.

```text
Limited Agent
     ↓
Few Tools
     ↓
Small Impact

Highly Autonomous Agent
     ↓
Many Tools
     ↓
Persistent Access
     ↓
Large Impact
```

Reducing unnecessary autonomy limits hijacking consequences.

---

### 38. Agent Hijacking and Privilege Escalation

A hijacked agent may attempt to obtain greater privileges.

Possible paths include:

* requesting additional credentials;
* manipulating authorization;
* abusing delegated authority;
* exploiting tool permissions;
* convincing another agent to perform privileged actions.

Agent architecture should prevent autonomous self-escalation.

---

### 39. Agent Hijacking and Lateral Movement

A compromised agent may attempt to move across enterprise systems.

```text
Agent A
 ↓
Tool
 ↓
Application B
 ↓
Credential
 ↓
System C
```

Network segmentation, identity boundaries, and least privilege should limit this movement.

---

### 40. Agent Hijacking and Transaction Risk

If a hijacked agent has transaction authority, compromise can produce direct business consequences.

Examples include:

* unauthorized payments;
* fraudulent refunds;
* account changes;
* infrastructure modifications;
* sensitive communications.

Transaction security must therefore remain independent of agent reasoning.

---

### 41. Agent Hijacking and Data Exposure

A hijacked agent may be manipulated into retrieving or transmitting sensitive information.

Potential targets include:

* customer records;
* financial data;
* credentials;
* internal documents;
* security information.

Data access must remain independently authorized.

---

### 42. Agent Hijacking and Persistence

Persistence determines whether hijacking survives beyond the original attack.

Potential persistence mechanisms include:

* memory;
* configuration;
* scheduled tasks;
* workflow state;
* credentials;
* tool modifications;
* delegated permissions.

Security teams should distinguish temporary manipulation from persistent compromise.

---

### 43. Agent Hijacking and Blast Radius

Blast radius represents the maximum potential impact of a hijacked agent.

```text
Hijacked Agent
      ↓
Identity Boundary
      ↓
Tool Boundary
      ↓
Data Boundary
      ↓
Transaction Boundary
      ↓
Enterprise Impact
```

Strong boundaries should progressively reduce the impact.

---

### 44. Detectability of Agent Hijacking

Agent hijacking may be difficult to detect because the compromised agent may continue using legitimate:

* identities;
* credentials;
* tools;
* workflows.

Behavioral monitoring is therefore necessary in addition to traditional authentication monitoring.

---

### 45. Agent Hijacking Indicators

Potential indicators include:

* unexpected tool usage;
* unusual transaction patterns;
* abnormal instruction sequences;
* unauthorized destinations;
* unusual data access;
* repeated authorization failures;
* unexpected memory modifications;
* sudden changes in behavior.

These signals should be correlated across the agent lifecycle.

---

### 46. Agent Hijacking Accountability

A secure system should allow investigators to determine:

```text
Who initiated the interaction?
Which agent was involved?
What context influenced the decision?
Which tools were used?
What authority was available?
What transaction occurred?
What changed?
```

Without attribution, identifying the source and scope of hijacking becomes significantly harder.

---

### 47. Agent Hijacking as a Governance Object

Agent hijacking should be included in:

* AI risk assessments;
* threat models;
* security policies;
* incident-response plans;
* control frameworks;
* security testing;
* audit programs.

It should not be treated solely as a model-level security problem.

---

### 48. Agent Hijacking Lifecycle

Hijacking can be viewed as a lifecycle:

```text
Initial Access
     ↓
Influence
     ↓
Control
     ↓
Privilege / Capability Abuse
     ↓
Action
     ↓
Persistence
     ↓
Impact
```

Security controls should be capable of disrupting the lifecycle at multiple stages.

---

### 49. Core Principles of Agent Hijacking Security

The core principles are:

1. Treat agent context as a security boundary.
2. Separate trusted instructions from untrusted content.
3. Authenticate agent identities independently.
4. Authorize actions independently from model reasoning.
5. Restrict tools and permissions through least privilege.
6. Protect memory and persistent state.
7. Preserve attribution across delegated actions.
8. Monitor behavioral deviations.
9. Maintain independent emergency controls.
10. Limit the blast radius of a compromised agent.

---

### 50. Core Principle of Agent Hijacking

The fundamental principle is:

> **An attacker must not be able to convert influence over an agent into unauthorized enterprise authority.**

The secure architecture therefore separates:

```text
Influence
   ↓
Agent Reasoning
   ↓
Action Proposal
   ↓
Independent Authorization
   ↓
Bounded Execution
   ↓
Business Effect
```

Even if an attacker successfully manipulates the agent's reasoning, independent identity, authorization, transaction, and execution controls should prevent that manipulation from becoming uncontrolled enterprise action.
