# 11.12 — Agent Hijacking

## Part 1 — Foundations and Core Concepts

### 1. Definition of Agent Hijacking

Agent hijacking is the unauthorized manipulation or takeover of an AI agent's behavior, execution context, authority, or operational control.

The attacker may attempt to cause the agent to:

* perform unauthorized actions;
* follow malicious instructions;
* misuse legitimate tools;
* disclose protected information;
* alter its operating objectives;
* bypass established security controls.

Agent hijacking is therefore broader than simply compromising a model.

---

### 2. Agent Hijacking as an Agentic AI Security Threat

In conventional applications, compromising a component may provide access to a defined function.

In agentic systems, hijacking can influence:

```text
Perception
   ↓
Reasoning
   ↓
Planning
   ↓
Tool Selection
   ↓
Action
   ↓
External Effect
```

The attacker may therefore manipulate the agent's decision and execution chain.

---

### 3. Agent Hijacking vs Model Compromise

Model compromise concerns the model itself.

Agent hijacking concerns the broader operational system surrounding the model.

```text
Model Compromise
      ↓
Model Behavior

Agent Hijacking
      ↓
Agent Behavior
      ↓
Tools
      ↓
Memory
      ↓
Identity
      ↓
Actions
```

An agent can potentially be hijacked even when the underlying model infrastructure remains uncompromised.

---

### 4. Agent Hijacking vs Account Takeover

Traditional account takeover usually involves gaining control of a user's account.

Agent hijacking may instead involve manipulating:

* agent context;
* instructions;
* memory;
* tools;
* sessions;
* execution state;
* delegated authority.

The attacker may never need to obtain the agent's primary identity credential.

---

### 5. Agent Hijacking vs Prompt Injection

Prompt injection is one possible mechanism for influencing an agent.

Agent hijacking is the broader security outcome.

```text
Prompt Injection
       ↓
Agent Manipulation
       ↓
Agent Hijacking
       ↓
Unauthorized Behavior
```

Not every prompt injection results in successful hijacking, but successful manipulation of agent behavior may constitute an agent-hijacking condition.

---

### 6. Agent Hijacking as a Security Boundary Violation

An agent operates within defined security boundaries.

Hijacking occurs when an attacker causes the agent to operate outside its intended:

* purpose;
* context;
* authority;
* permissions;
* transaction limits;
* tool boundaries.

---

### 7. Agent Control Boundary

The control boundary defines what components can legitimately influence agent behavior.

```text
Trusted Control Plane
        │
        ▼
Agent Runtime
        │
        ├── Model
        ├── Context
        ├── Memory
        ├── Tools
        └── Actions
```

Unauthorized influence crossing this boundary can create hijacking risk.

---

### 8. Agent Execution Context

An agent's execution context may include:

* system instructions;
* user requests;
* retrieved information;
* tool results;
* memory;
* session state;
* environment variables;
* security policies.

Compromise of any security-sensitive component can potentially influence subsequent behavior.

---

### 9. Trusted vs Untrusted Agent Inputs

Agent inputs should be classified according to trust.

```text
Higher Trust
    │
    ├── Security Policy
    ├── Authorization Service
    ├── Identity Provider
    │
    ├── Business Systems
    │
    └── External Content
Lower Trust
```

Untrusted content must not automatically acquire the authority of trusted instructions.

---

### 10. Agent Instruction Hierarchy

Agentic systems often process multiple instruction sources.

For example:

```text
Security Policy
      ↓
System Instructions
      ↓
Application Instructions
      ↓
User Instructions
      ↓
External Content
```

Hijacking may occur when lower-trust content successfully overrides or manipulates higher-trust instructions.

---

### 11. Agent Objective Manipulation

An attacker may attempt to change the effective objective of an agent.

For example:

```text
Original Objective:
Process customer refunds according to policy.

Manipulated Objective:
Refund every request immediately.
```

Objective manipulation is dangerous because the agent may continue operating legitimately from the perspective of its compromised reasoning.

---

### 12. Agent Goal Hijacking

Goal hijacking occurs when an attacker causes an agent to pursue an unauthorized goal.

The malicious goal may be introduced through:

* user input;
* documents;
* websites;
* email;
* tool output;
* memory;
* another agent.

The agent may then perform legitimate actions toward an illegitimate objective.

---

### 13. Agent Context Hijacking

Context hijacking occurs when an attacker manipulates the information available to the agent so that it reaches unauthorized conclusions.

```text
Trusted Context
      +
Manipulated Context
      ↓
Incorrect Agent Decision
      ↓
Potentially Unauthorized Action
```

The attacker does not necessarily need to alter the model itself.

---

### 14. Agent Session Hijacking

Session hijacking involves gaining unauthorized control over an active agent session or manipulating the session's state.

Potential consequences include:

* impersonation;
* unauthorized instructions;
* access to session data;
* tool misuse;
* transaction execution.

Session identity must therefore remain strongly bound to the authorized principal and execution context.

---

### 15. Agent Runtime Hijacking

Runtime hijacking involves compromising the environment in which an agent executes.

Potential targets include:

* agent orchestration services;
* containers;
* virtual machines;
* execution workers;
* runtime configuration;
* environment variables.

Runtime compromise can provide a path to bypass application-level safeguards.

---

### 16. Agent Identity Hijacking

Identity hijacking occurs when an attacker causes actions to appear as though they originated from a legitimate agent.

```text
Attacker
   ↓
Spoofed / Compromised Identity
   ↓
Enterprise System
   ↓
Trusted Agent Assumption
```

Strong workload identity and attribution controls are therefore essential.

---

### 17. Agent Credential Hijacking

An attacker may obtain credentials associated with an agent.

Potential credentials include:

* API tokens;
* service credentials;
* certificates;
* cloud credentials;
* database credentials;
* delegated tokens.

Credential compromise can enable direct impersonation even without manipulating the model.

---

### 18. Agent Tool Hijacking

An attacker may manipulate the tools available to an agent or the way those tools are invoked.

Examples include:

* replacing a legitimate endpoint;
* modifying tool configuration;
* changing tool schemas;
* redirecting API requests;
* introducing a malicious tool.

Tool hijacking can convert legitimate agent capabilities into attack mechanisms.

---

### 19. Agent Memory Hijacking

Attackers may attempt to insert malicious information into persistent agent memory.

```text
Attacker Input
     ↓
Memory
     ↓
Future Agent Session
     ↓
Manipulated Behavior
```

Persistent memory creates a particularly important hijacking risk because malicious influence can survive beyond the original interaction.

---

### 20. Agent Context Persistence Risk

A hijacking condition may persist if malicious instructions or state are stored in:

* long-term memory;
* knowledge bases;
* workflow state;
* configuration;
* task queues.

Persistence can transform a temporary manipulation into a recurring compromise.

---

### 21. Agent-to-Agent Hijacking

In multi-agent systems, one compromised agent may attempt to influence another agent.

```text
Compromised Agent A
        ↓
Malicious Message
        ↓
Trusted Agent B
        ↓
Unauthorized Action
```

The receiving agent must not automatically trust messages merely because they originate from another registered agent.

---

### 22. Delegation Hijacking

An attacker may manipulate delegated authority so that a transaction or task is executed by another agent under apparently legitimate authority.

Potential consequences include:

* privilege propagation;
* unauthorized actions;
* authority amplification;
* loss of attribution.

Delegated authority must therefore remain explicitly bounded.

---

### 23. Agent Authority Hijacking

Authority hijacking occurs when an attacker causes an agent to operate with authority beyond its intended scope.

Examples include:

* accessing restricted records;
* executing administrative actions;
* modifying security policies;
* initiating high-value transactions.

The security architecture must prevent the agent from expanding its own authority.

---

### 24. Agent Behavior Hijacking

Agent behavior may be manipulated without compromising identity or credentials.

For example:

```text
Legitimate Agent
      ↓
Malicious Context
      ↓
Manipulated Reasoning
      ↓
Legitimate Credentials
      ↓
Unauthorized Action
```

This makes behavioral protection as important as credential protection.

---

### 25. Agent Hijacking Through Prompt Injection

Prompt injection may attempt to redirect an agent toward unauthorized actions.

Examples include instructions such as:

* ignore previous restrictions;
* reveal confidential information;
* call a privileged tool;
* change transaction parameters;
* disable security checks.

Independent enforcement must prevent successful injection from becoming unauthorized execution.

---

### 26. Agent Hijacking Through Indirect Prompt Injection

Indirect prompt injection occurs when malicious instructions are embedded in content the agent processes.

Potential sources include:

* websites;
* PDFs;
* emails;
* documents;
* issue trackers;
* knowledge bases;
* retrieved records.

```text
External Content
      ↓
Agent Retrieval
      ↓
Malicious Instruction
      ↓
Agent Reasoning
      ↓
Potential Hijacking
```

---

### 27. Agent Hijacking Through Tool Results

Tool results should be treated as potentially untrusted inputs.

A compromised or manipulated tool could return information designed to influence the agent.

```text
Tool
 ↓
Malicious Result
 ↓
Agent Reasoning
 ↓
Unsafe Decision
```

Tool output must not automatically acquire instruction authority.

---

### 28. Agent Hijacking Through Memory Poisoning

Memory poisoning can create persistent behavioral manipulation.

An attacker may attempt to insert false information such as:

```text
"Security approval has already been granted."
```

If later treated as authoritative, the stored information could influence future transactions.

Memory provenance and authorization boundaries are therefore critical.

---

### 29. Agent Hijacking Through Identity Confusion

An agent may receive conflicting identity information.

For example:

```text
User Identity
      ≠
Agent Identity
      ≠
Delegated Identity
```

If these identities become confused, the agent may perform an action under the wrong authority.

---

### 30. Agent Hijacking Through Authorization Confusion

An attacker may attempt to convince the agent that an action is authorized when it is not.

```text
Agent:
"The user said this is approved."

Authorization Service:
"DENY."
```

The authorization service must remain authoritative.

---

### 31. Agent Hijacking Through Tool Substitution

A malicious tool may be substituted for a trusted tool or an approved tool may be redirected to an unauthorized endpoint.

Tool identity and provenance must therefore be validated.

---

### 32. Agent Hijacking Through Configuration Manipulation

Agent configuration can influence:

* tools;
* permissions;
* prompts;
* endpoints;
* memory;
* execution limits.

Unauthorized configuration changes can therefore create a hijacking condition without directly modifying the model.

---

### 33. Agent Hijacking Through Workflow Manipulation

An attacker may manipulate the workflow surrounding an agent.

Examples include:

* changing task queues;
* inserting malicious jobs;
* altering workflow states;
* modifying approval status;
* changing execution order.

The agent may then execute actions according to a compromised workflow.

---

### 34. Agent Hijacking Through Event Manipulation

Event-driven agents may react automatically to external events.

If event integrity is compromised, an attacker may generate malicious events that trigger autonomous actions.

```text
False Event
    ↓
Agent Trigger
    ↓
Agent Decision
    ↓
Autonomous Action
```

Event authenticity must therefore be verified.

---

### 35. Agent Hijacking Through API Manipulation

APIs connecting agents to enterprise systems can become hijacking paths.

Attackers may attempt:

* request manipulation;
* endpoint substitution;
* parameter tampering;
* token abuse;
* replay;
* response manipulation.

API security must therefore be part of the agent security boundary.

---

### 36. Agent Hijacking Through External Connectivity

Internet access and external services can expose agents to hostile content and systems.

An agent capable of browsing, communicating, or interacting with external services has a broader hijacking surface than an isolated agent.

---

### 37. Agent Hijacking and Excessive Agency

Excessive agency increases the consequences of successful hijacking.

```text
Limited Agent
     ↓
Few Tools
     ↓
Small Impact

Highly Autonomous Agent
     ↓
Many Tools
     ↓
Persistent Access
     ↓
Large Impact
```

Reducing unnecessary autonomy limits hijacking consequences.

---

### 38. Agent Hijacking and Privilege Escalation

A hijacked agent may attempt to obtain greater privileges.

Possible paths include:

* requesting additional credentials;
* manipulating authorization;
* abusing delegated authority;
* exploiting tool permissions;
* convincing another agent to perform privileged actions.

Agent architecture should prevent autonomous self-escalation.

---

### 39. Agent Hijacking and Lateral Movement

A compromised agent may attempt to move across enterprise systems.

```text
Agent A
 ↓
Tool
 ↓
Application B
 ↓
Credential
 ↓
System C
```

Network segmentation, identity boundaries, and least privilege should limit this movement.

---

### 40. Agent Hijacking and Transaction Risk

If a hijacked agent has transaction authority, compromise can produce direct business consequences.

Examples include:

* unauthorized payments;
* fraudulent refunds;
* account changes;
* infrastructure modifications;
* sensitive communications.

Transaction security must therefore remain independent of agent reasoning.

---

### 41. Agent Hijacking and Data Exposure

A hijacked agent may be manipulated into retrieving or transmitting sensitive information.

Potential targets include:

* customer records;
* financial data;
* credentials;
* internal documents;
* security information.

Data access must remain independently authorized.

---

### 42. Agent Hijacking and Persistence

Persistence determines whether hijacking survives beyond the original attack.

Potential persistence mechanisms include:

* memory;
* configuration;
* scheduled tasks;
* workflow state;
* credentials;
* tool modifications;
* delegated permissions.

Security teams should distinguish temporary manipulation from persistent compromise.

---

### 43. Agent Hijacking and Blast Radius

Blast radius represents the maximum potential impact of a hijacked agent.

```text
Hijacked Agent
      ↓
Identity Boundary
      ↓
Tool Boundary
      ↓
Data Boundary
      ↓
Transaction Boundary
      ↓
Enterprise Impact
```

Strong boundaries should progressively reduce the impact.

---

### 44. Detectability of Agent Hijacking

Agent hijacking may be difficult to detect because the compromised agent may continue using legitimate:

* identities;
* credentials;
* tools;
* workflows.

Behavioral monitoring is therefore necessary in addition to traditional authentication monitoring.

---

### 45. Agent Hijacking Indicators

Potential indicators include:

* unexpected tool usage;
* unusual transaction patterns;
* abnormal instruction sequences;
* unauthorized destinations;
* unusual data access;
* repeated authorization failures;
* unexpected memory modifications;
* sudden changes in behavior.

These signals should be correlated across the agent lifecycle.

---

### 46. Agent Hijacking Accountability

A secure system should allow investigators to determine:

```text
Who initiated the interaction?
Which agent was involved?
What context influenced the decision?
Which tools were used?
What authority was available?
What transaction occurred?
What changed?
```

Without attribution, identifying the source and scope of hijacking becomes significantly harder.

---

### 47. Agent Hijacking as a Governance Object

Agent hijacking should be included in:

* AI risk assessments;
* threat models;
* security policies;
* incident-response plans;
* control frameworks;
* security testing;
* audit programs.

It should not be treated solely as a model-level security problem.

---

### 48. Agent Hijacking Lifecycle

Hijacking can be viewed as a lifecycle:

```text
Initial Access
     ↓
Influence
     ↓
Control
     ↓
Privilege / Capability Abuse
     ↓
Action
     ↓
Persistence
     ↓
Impact
```

Security controls should be capable of disrupting the lifecycle at multiple stages.

---

### 49. Core Principles of Agent Hijacking Security

The core principles are:

1. Treat agent context as a security boundary.
2. Separate trusted instructions from untrusted content.
3. Authenticate agent identities independently.
4. Authorize actions independently from model reasoning.
5. Restrict tools and permissions through least privilege.
6. Protect memory and persistent state.
7. Preserve attribution across delegated actions.
8. Monitor behavioral deviations.
9. Maintain independent emergency controls.
10. Limit the blast radius of a compromised agent.

---

### 50. Core Principle of Agent Hijacking

The fundamental principle is:

> **An attacker must not be able to convert influence over an agent into unauthorized enterprise authority.**

The secure architecture therefore separates:

```text
Influence
   ↓
Agent Reasoning
   ↓
Action Proposal
   ↓
Independent Authorization
   ↓
Bounded Execution
   ↓
Business Effect
```

Even if an attacker successfully manipulates the agent's reasoning, independent identity, authorization, transaction, and execution controls should prevent that manipulation from becoming uncontrolled enterprise action.

# Part 2 — Technical Security and Control Mechanisms

### 51. Agent Hijacking Security Control Architecture

Agent hijacking defenses should protect every layer between external input and autonomous execution.

```text id="8x4v3q"
External Input
      ↓
Input Security
      ↓
Context Isolation
      ↓
Agent Runtime
      ↓
Identity
      ↓
Authorization
      ↓
Tool Gateway
      ↓
Action Controls
      ↓
Protected System
      ↓
Monitoring / SOC
```

The architecture should assume that an attacker may successfully influence the agent and ensure that influence alone cannot produce unauthorized enterprise effects.

---

### 52. Agent Identity Control

Every agent should have a unique, verifiable identity.

Identity controls should prevent:

* identity spoofing;
* shared agent identities;
* unauthorized identity reuse;
* identity substitution.

The executing identity should be recorded with every security-sensitive operation.

---

### 53. Agent Authentication

Agent authentication should verify that the workload executing an operation is the legitimate agent associated with the claimed identity.

Authentication should occur before access to protected:

* tools;
* APIs;
* data;
* workflows;
* transaction services.

---

### 54. Strong Agent Authentication

High-risk agents should use strong workload authentication mechanisms.

Possible mechanisms include:

* mutual TLS;
* workload identity;
* signed tokens;
* certificates;
* hardware-backed identity where appropriate.

Authentication strength should correspond to the impact of the agent's available capabilities.

---

### 55. Fine-Grained Agent Authorization

Authorization should evaluate what the authenticated agent is allowed to do.

```text id="1cxp5w"
Agent Identity
      +
Requested Action
      +
Resource
      +
Context
      +
Risk
      ↓
Authorization Decision
```

Authentication should never be interpreted as unrestricted authority.

---

### 56. Independent Authorization Service

Authorization decisions should be made independently from the agent.

```text id="5o0f3j"
Agent
 ↓
Request
 ↓
Authorization Service
 ├── Identity
 ├── Policy
 ├── Resource
 ├── Context
 └── Risk
 ↓
ALLOW / DENY
```

This prevents a hijacked agent from granting itself additional authority.

---

### 57. Agent Access Allowlisting

Only approved agents should be permitted to access protected services.

Allowlisting should consider:

* agent identity;
* version;
* environment;
* workload;
* business purpose.

Unknown or unauthorized agent instances should be denied.

---

### 58. Authentication Method Allowlisting

Only approved authentication mechanisms should be accepted for sensitive agent operations.

For example:

```text id="6u9v9m"
Approved Workload Identity → ALLOW
Expired Token              → DENY
Unknown Certificate        → DENY
Untrusted Credential       → DENY
```

---

### 59. Authorization Scope Validation

Authorization scope should be checked against the requested action.

A valid identity with access to a system should not automatically receive access to every operation within that system.

---

### 60. Agent Role Validation

The agent's assigned role should be validated before execution.

```text id="fzx3l8"
Agent Role:
Customer Support

Requested:
Delete Production Database

→ Role Mismatch
→ DENY
```

Role validation should be performed by trusted security infrastructure.

---

### 61. Agent Permission Validation

Individual permissions should be validated at the point of use.

This prevents an attacker from exploiting unused or accidentally inherited privileges.

---

### 62. Transaction Authorization Limits

Transactions initiated by agents should have explicit limits.

Limits may include:

* maximum amount;
* number of records;
* number of actions;
* resource scope;
* transaction type.

Limits should be technically enforced.

---

### 63. Cumulative Authorization Limits

Controls should consider cumulative actions.

```text id="i1g3ap"
Action 1 → €500
Action 2 → €500
Action 3 → €500
Action 4 → €500
----------------
Total     → €2,000
```

An attacker should not be able to bypass a limit by dividing one prohibited operation into many permitted operations.

---

### 64. Time-Bounded Agent Authorization

Agent authority should expire automatically.

Short authorization windows reduce the period during which a hijacked agent can operate.

---

### 65. Short-Lived Agent Credentials

Agent credentials should preferably be temporary.

```text id="7s8f8v"
Credential Issued
      ↓
Limited Scope
      ↓
Limited Lifetime
      ↓
Automatic Expiration
```

Short-lived credentials reduce persistence after compromise.

---

### 66. Credential Isolation

Agent credentials should be isolated from:

* prompts;
* memory;
* model context;
* logs;
* tool results;
* user-visible outputs.

Credentials should never become persistent agent knowledge.

---

### 67. Secrets Management

Secrets should be managed through controlled enterprise mechanisms.

Agents should receive only the secrets necessary for an authorized operation and, where possible, only through brokered access.

---

### 68. Context Security Controls

Security-sensitive context should be separated from general agent context.

```text id="x0d0el"
Security Context
      │
      ├── Identity
      ├── Authorization
      ├── Policy
      └── Approval
       
Agent Context
      │
      ├── User Input
      ├── Documents
      ├── Tool Results
      └── Web Content
```

The second category should never be allowed to redefine the first.

---

### 69. Prompt and Instruction Integrity

System instructions and security policies should be protected against unauthorized modification.

Controls should include:

* version control;
* integrity checking;
* restricted modification;
* approval workflows;
* change monitoring.

---

### 70. Untrusted Input Isolation

Potentially hostile inputs should be explicitly isolated.

Examples include:

* websites;
* emails;
* uploaded documents;
* customer messages;
* external API responses;
* retrieved knowledge.

Untrusted content may inform reasoning but must not become authoritative security policy.

---

### 71. Prompt Injection Detection

Systems should detect attempts to manipulate agent instructions.

Detection may identify:

* instruction overrides;
* attempts to reveal system prompts;
* requests to disable controls;
* privilege escalation instructions;
* malicious tool-use directives.

Detection is an additional layer, not the primary authorization boundary.

---

### 72. Memory Isolation

Agent memory should be isolated according to:

* agent;
* user;
* tenant;
* session;
* sensitivity;
* business purpose.

A compromised memory store should not automatically expose unrelated agent contexts.

---

### 73. Memory Authorization

Agents should be authorized before reading or modifying persistent memory.

Security-sensitive memory should have stricter access requirements than ordinary conversational context.

---

### 74. Memory Integrity

Persistent memory should be protected against unauthorized modification.

Controls may include:

* integrity verification;
* provenance;
* versioning;
* restricted writes;
* anomaly detection.

---

### 75. Persistent Context Controls

Persistent context should have explicit lifecycle controls.

These should address:

* creation;
* modification;
* retention;
* expiration;
* deletion;
* authorization.

Persistent instructions should not silently become permanent authority.

---

### 76. Data Access Authorization

Agent data access should be independently authorized.

A hijacked agent should not be able to use legitimate credentials to retrieve arbitrary enterprise data simply because the data is technically accessible.

---

### 77. Data Minimization

Agents should receive only the information required for their approved function.

This limits the consequences of successful hijacking.

---

### 78. Field-Level Data Protection

Sensitive fields should be separately protected.

```text id="8d05lq"
Customer Record
 ├── Name          → Allowed
 ├── Order Status  → Allowed
 ├── Payment Data  → Restricted
 └── Credentials   → Denied
```

Hijacking one agent should not expose an entire database.

---

### 79. Tenant Isolation

Agents operating in multi-tenant environments should be prevented from crossing tenant boundaries.

Tenant identity should be independently validated before data or transaction access.

---

### 80. Session Isolation

Agent sessions should be isolated to prevent hijacking of one session from providing access to another.

Controls should bind sessions to appropriate:

* identities;
* tokens;
* execution contexts;
* tenants.

---

### 81. Network Segmentation

Agent runtimes should be separated from sensitive enterprise systems.

```text id="b7v2n5"
Agent Runtime
      ↓
Agent Security Gateway
      ↓
Controlled Network Zone
      ↓
Protected Service
```

Network segmentation limits lateral movement after hijacking.

---

### 82. Egress Controls

Outbound communication from agents should be restricted to approved destinations.

Controls should prevent a hijacked agent from freely communicating with attacker-controlled infrastructure.

---

### 83. External Communication Controls

Agents capable of sending external communications should have controls over:

* recipient;
* destination;
* content classification;
* attachment;
* frequency;
* channel.

---

### 84. Code Execution Isolation

Agents capable of executing code should operate within isolated environments.

Controls may include:

* sandboxing;
* containerization;
* restricted filesystem access;
* network restrictions;
* CPU and memory limits.

This prevents a hijacked agent from converting code execution into unrestricted host access.

---

### 85. Database Security Controls

Database access should be tightly scoped.

Controls should include:

* restricted schemas;
* restricted tables;
* query controls;
* row-level security;
* read/write separation;
* transaction limits.

---

### 86. Read/Write Separation

Read and write access should be independently controlled.

```text id="q7z1ga"
READ
 ↓
Information Access

WRITE
 ↓
State Modification

DELETE / ADMIN
 ↓
Critical Authority
```

A hijacked read-only agent should not automatically become a destructive agent.

---

### 87. Human Approval Controls

High-risk actions should require human approval before execution.

Approval should occur through an independent mechanism rather than through conversational confirmation alone.

---

### 88. Action Preview

The system should present the exact action that will be executed.

The preview should identify:

* target;
* action;
* parameters;
* affected resources;
* transaction value;
* expected consequence.

---

### 89. Dual Authorization

Critical operations should require two independent authorization decisions.

This creates an additional barrier if one identity, agent, or control path is compromised.

---

### 90. Reversibility Controls

Where possible, autonomous actions should support:

* rollback;
* cancellation;
* compensation;
* restoration.

Reversibility reduces the impact of successful hijacking.

---

### 91. Agent Execution Limits

Agents should have limits on:

* execution duration;
* action count;
* transaction volume;
* resource consumption;
* concurrent operations.

These controls constrain runaway behavior.

---

### 92. Loop Detection

The system should detect repeated autonomous behavior.

```text id="r5vv79"
Action A
 ↓
Action B
 ↓
Action A
 ↓
Action B
 ↓
...
```

A hijacked agent may exhibit unusual repetitive execution patterns.

---

### 93. Recursive Delegation Controls

Agents should not be able to create unlimited chains of delegated authority.

Controls should limit:

* delegation depth;
* delegated scope;
* delegated duration;
* cumulative impact.

---

### 94. Agent-to-Agent Authentication

Agents communicating with one another should mutually authenticate.

The receiving agent should verify the identity of the sender before accepting security-sensitive requests.

---

### 95. Agent-to-Agent Message Integrity

Agent-to-agent messages should be protected against unauthorized modification.

Security-sensitive attributes should include:

* sender;
* recipient;
* action;
* authority;
* parameters;
* expiration.

---

### 96. Delegated Authority Constraints

Delegated authority should be explicitly constrained.

```text id="1v4c9s"
Agent A
 ↓
Delegates
 ↓
Agent B
 ↓
Reduced / Equal Authority
```

Agent B must not receive broader authority than the delegation permits.

---

### 97. Tool Result Validation

Tool results should be validated before influencing security-sensitive decisions.

An attacker who compromises a tool should not automatically control the agent's subsequent actions.

---

### 98. Output Validation Before Action

Model-generated outputs should pass through deterministic validation before they become executable requests.

```text id="6sm2cn"
Model Output
     ↓
Schema Validation
     ↓
Security Policy
     ↓
Business Rules
     ↓
Authorization
     ↓
Execution
```

---

### 99. Business Rule Enforcement

Business rules must be enforced by authoritative systems.

For example:

```text id="8nh1wu"
Refund ≤ Original Payment
Payment Recipient = Approved
Discount ≤ Authorized Limit
Production Change = Approved Window
```

The agent should not be trusted to enforce these rules through reasoning alone.

---

### 100. Resource Controls

Resources available to a potentially hijacked agent should be explicitly limited.

Controls may constrain:

* compute;
* storage;
* API calls;
* database operations;
* cloud resources;
* number of affected records.

---

### 101. Rate Limiting

Rate limiting restricts the speed at which a hijacked agent can perform actions.

```text id="i2jzkg"
Normal:
100 requests/minute

Abnormal:
10,000 requests/minute

→ Throttle / Block
```

---

### 102. Concurrency Controls

Concurrent operations should be limited.

This prevents a hijacked agent from launching large numbers of simultaneous operations before security teams can intervene.

---

### 103. Timeout Controls

Agent operations should have explicit timeouts.

Long-running operations should automatically terminate or require renewed authorization when their permitted execution period expires.

---

### 104. Retry Controls

Retries should be bounded and evaluated for safety.

A hijacked agent should not be able to create an infinite retry loop against a transaction or API.

---

### 105. Circuit Breakers

Circuit breakers should automatically stop operations when suspicious thresholds are exceeded.

Potential triggers include:

* repeated failures;
* excessive volume;
* unusual destinations;
* authorization failures;
* abnormal transaction values.

---

### 106. Emergency Agent Controls

Emergency controls should allow security teams to rapidly restrict an agent.

Controls may include:

* suspend agent;
* disable tools;
* revoke credentials;
* block network access;
* stop workflows;
* deny transactions.

---

### 107. Agent Kill Switch

The kill switch must operate independently of the potentially hijacked agent.

```text id="r4z1nd"
Security Operator
       ↓
Kill Switch
       ↓
Agent Execution Stopped
       ↓
Credentials Revoked
       ↓
Tools / Transactions Blocked
```

The agent should not be capable of disabling its own kill switch.

---

### 108. Credential Revocation

Compromised credentials should be revocable rapidly.

Revocation should propagate across relevant:

* sessions;
* tools;
* APIs;
* workloads;
* delegated identities.

---

### 109. Agent Isolation During Incident Response

During suspected hijacking, the agent should be isolated while preserving sufficient evidence for investigation.

Isolation may include:

* network quarantine;
* tool suspension;
* credential revocation;
* transaction blocking;
* memory write protection.

---

### 110. Agent Isolation

Security architecture should provide isolation boundaries between agents.

A compromised customer-service agent should not automatically gain access to:

* finance agents;
* infrastructure agents;
* privileged administrative agents.

---

### 111. Behavioral Hijacking Monitoring

Security monitoring should establish behavioral baselines and identify deviations.

Indicators include:

* new tool usage;
* unusual transaction patterns;
* abnormal data access;
* unexpected destinations;
* unusual operating times;
* changes in action frequency.

---

### 112. Agent Hijacking Activity Logging

Security-relevant agent activity should be logged.

Logs should capture:

```text id="i1upw0"
Agent Identity
Session
Initiator
Instruction Source

Action
Target
Authorization
Result
Timestamp
```

---

### 113. Tamper-Resistant Hijacking Audit Logging

Logs should be protected against modification by compromised agents or administrators operating within the affected environment.

Controls may include:

* append-only storage;
* centralized collection;
* immutable retention;
* cryptographic integrity.

---

### 114. Agent Hijacking Security Observability

Security teams should be able to correlate the complete chain:

```text id="ub39eu"
Input
 ↓
Context
 ↓
Agent Decision
 ↓
Tool Invocation
 ↓
Authorization
 ↓
Action
 ↓
Business Effect
```

This is essential for distinguishing normal autonomous behavior from hijacking.

---

### 115. Agent Hijacking Risk Detection

Detection should combine multiple signals.

Potential indicators include:

* prompt injection;
* identity anomalies;
* memory changes;
* abnormal tool usage;
* privilege escalation attempts;
* unusual transactions;
* unexpected external communications.

No single indicator should be treated as definitive in isolation.

---

### 116. Secure Hijacking Failure Handling

When hijacking is suspected, the system should fail safely.

```text id="2d8iqr"
Suspicious Behavior
       ↓
Risk Evaluation
       ↓
Restrict / Stop
       ↓
Revoke Authority
       ↓
Preserve Evidence
       ↓
Investigate
```

The priority should be preventing additional unauthorized effects.

---

### 117. Core Engineering Principle

The core engineering principle is:

> **A successfully manipulated agent must still be unable to independently convert that manipulation into unauthorized enterprise authority.**

This requires independent enforcement across:

```text id="1gq5op"
Identity
   ↓
Authentication
   ↓
Authorization
   ↓
Context Security
   ↓
Tool Controls
   ↓
Transaction Controls
   ↓
Execution Limits
   ↓
Monitoring
   ↓
Emergency Response
```

Agent hijacking is therefore controlled not by assuming the agent will always behave correctly, but by architecting the enterprise so that **incorrect agent behavior remains bounded, observable, interruptible, and recoverable**.
